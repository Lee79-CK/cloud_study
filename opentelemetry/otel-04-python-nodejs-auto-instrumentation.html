런타임이 다르면 함정도 다른 곳에 있다

Java는 JVM이 공식 통로를 제공해서 비교적 깔끔했습니다. Python과 Node.js에는 그런 표준 API가 없습니다. 대신 모듈을 가져오는 순간을 가로채 함수를 바꿔치기합니다. 이 방식의 차이 때문에 생기는 문제들 — fork, 로딩 순서, ESM, 번들러 — 을 알아야 "왜 나만 안 되지"에서 벗어날 수 있습니다.

SECTION 01

왜 언어마다 방식이 다른가

자동 계측의 목표는 어느 언어나 같습니다. 내 코드를 고치지 않고 라이브러리 호출 지점에 측정 코드를 끼워 넣는 것. 다만 그 "끼워 넣기"를 허용하는 방식이 런타임마다 다릅니다.

Java · 바이트코드 변환

JVM이 java.lang.instrument라는 공식 API를 제공합니다. 클래스가 로딩될 때 바이트코드를 바꿉니다. 표준 통로라 안정적입니다.

Python · 몽키 패칭

모듈을 import하는 시점에 끼어들어 함수 객체를 감싼 버전으로 교체합니다. 표준 API가 아니라 언어의 동적 특성을 이용한 것입니다.

Node.js · require 후킹

모듈 로딩 함수를 가로채 반환되는 모듈 객체를 수정합니다. 원리는 Python과 비슷하지만 ESM 도입으로 상황이 복잡해졌습니다.

여기서 모든 함정이 파생됩니다

Python과 Node.js는 "모듈을 가져오는 순간"에만 개입할 수 있습니다. 그래서 두 가지 조건이 따라붙습니다. 첫째, 계측이 대상 라이브러리보다 먼저 준비돼 있어야 합니다. 이미 import가 끝난 뒤에는 손댈 수 없습니다. 둘째, 프로세스가 복제되거나(fork) 모듈 참조가 고정되면(번들링) 그 관계가 깨집니다. 앞으로 나올 함정들은 전부 이 두 문장의 변주입니다.

SECTION 02

Python 자동 계측 시작하기

Python은 설치 → 의존성 자동 탐지 → 래퍼 실행의 세 단계로 끝납니다.

1단계 · 배포판 설치

pip install opentelemetry-distro opentelemetry-exporter-otlp

opentelemetry-distro는 API·SDK·설정 로직과 opentelemetry-instrument 명령을 함께 담은 묶음입니다. 익스포터는 별도 패키지라 함께 설치해야 합니다.

2단계 · 계측 라이브러리 자동 설치

# 현재 환경에 설치된 패키지를 훑어 대응하는 계측 패키지를 깔아줍니다
opentelemetry-bootstrap --action=install
순서가 중요합니다

이 명령은 실행 시점에 설치돼 있는 패키지만 봅니다. 나중에 psycopg2나 redis를 추가로 설치했다면 bootstrap을 다시 실행해야 그 라이브러리 계측이 들어갑니다. "DB Span만 안 나온다"는 제보의 첫 번째 확인 사항입니다.

3단계 · 래퍼로 실행

export OTEL_SERVICE_NAME=recommend-api
export OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf

# 앱 실행 명령 앞에 opentelemetry-instrument를 붙입니다
opentelemetry-instrument python app.py
opentelemetry-instrument uvicorn main:app --host 0.0.0.0
opentelemetry-instrument gunicorn -k uvicorn.workers.UvicornWorker main:app

opentelemetry-instrument는 앱이 시작되기 전에 SDK를 구성하고 설치된 계측 패키지들을 모두 활성화한 뒤, 원래 명령을 실행합니다. Java의 -javaagent와 역할이 같습니다.

자동으로 잡히는 것들

웹 프레임워크

Flask, Django, FastAPI, Starlette, Falcon, Pyramid, Tornado

데이터 접근

SQLAlchemy, psycopg, PyMySQL, Redis, PyMongo, Elasticsearch

통신 · 작업

requests, httpx, urllib3, aiohttp, grpcio, boto3, Celery, Kafka

첫 검증은 콘솔로

3편과 같은 원칙입니다. Collector를 붙이기 전에 OTEL_TRACES_EXPORTER=console로 먼저 Span이 찍히는지 확인하세요. Python은 특히 fork나 실행 방식 때문에 계측 자체가 안 걸리는 경우가 많아, 이 단계에서 걸러내면 시간을 크게 아낍니다.

SECTION 03

Python의 함정 여섯 가지

실무 제보의 대부분이 여기 모여 있습니다. 카드를 눌러 원인과 해결책을 확인하세요.

gunicorn --preload에서 계측이 죽는다

워커를 늘렸더니 트레이스가 안 나오거나 일부 워커에서만 나옵니다.

gunicorn은 마스터 프로세스를 fork해서 워커를 만듭니다. --preload를 쓰면 마스터에서 앱과 SDK가 먼저 초기화되는데, fork 이후 자식 프로세스에서는 백그라운드 전송 스레드가 복제되지 않아 데이터가 나가지 않습니다.

해결은 워커가 포크된 뒤에 SDK를 초기화하는 것입니다. gunicorn 설정 파일의 post_fork 훅을 씁니다.

# gunicorn.conf.py
def post_fork(server, worker):
    from opentelemetry.instrumentation.auto_instrumentation \
         import sitecustomize  # 워커별 초기화

더 간단한 대안은 --preload를 쓰지 않는 것입니다. 메모리 이점을 포기하는 대신 문제가 사라집니다.

치명 · 가장 흔함
핫 리로드 모드에서 동작하지 않는다

로컬에서 --reload로 띄우면 Span이 아예 안 보입니다.

리로더는 감시용 부모 프로세스를 두고 실제 앱을 자식으로 재실행합니다. 계측은 부모에만 걸리고 자식은 맨몸으로 뜨는 구조가 됩니다.

  • Flask — FLASK_ENV=development 해제, --no-reload
  • Django — runserver --noreload
  • Uvicorn·FastAPI — --reload 제거

개발 편의를 위해 리로드를 쓰는 건 자연스럽습니다. 다만 계측 검증은 리로드를 끄고 하세요.

치명 · 로컬 검증 실패의 주범
엔드포인트는 4317인데 Python은 4318을 쓴다

Java 앱은 잘 들어가는데 Python만 안 들어갑니다.

Python에서 gRPC 익스포터를 쓰려면 grpcio가 필요한데, 빌드 환경에 따라 설치가 까다로워 HTTP 익스포터를 쓰는 경우가 많습니다. 그런데 엔드포인트만 복사해 오면 포트가 어긋납니다.

  • grpc → 4317 / http/protobuf → 4318
  • 쿠버네티스 Operator의 Instrumentation 리소스는 기본이 http/protobuf이므로 엔드포인트를 4318로 지정해야 합니다
  • 프로토콜과 포트는 항상 짝으로 바꾸세요
치명 · 언어 혼재 환경
새 라이브러리를 추가했는데 Span이 없다

Redis를 붙였는데 관련 Span이 안 나옵니다.

opentelemetry-bootstrap --action=install은 실행 당시의 패키지 목록만 봅니다. 의존성을 추가한 뒤에는 다시 실행해야 합니다.

컨테이너 빌드 단계에서 의존성 설치 → bootstrap 순서를 지키면 이 문제가 구조적으로 사라집니다.

RUN pip install -r requirements.txt
RUN pip install opentelemetry-distro opentelemetry-exporter-otlp
RUN opentelemetry-bootstrap --action=install  # 항상 마지막
주의 · 빌드 순서 문제
ASGI와 WSGI를 혼동한다

FastAPI를 gunicorn으로 띄웠는데 비동기 구간이 이상하게 잡힙니다.

Flask·Django는 WSGI(동기), FastAPI·Starlette는 ASGI(비동기)입니다. 실행기도 이에 맞춰야 합니다.

  • FastAPI를 gunicorn으로 띄우려면 -k uvicorn.workers.UvicornWorker가 필요합니다
  • WSGI 실행기로 ASGI 앱을 띄우면 계측 이전에 앱 자체가 제대로 동작하지 않습니다
  • ASGI 환경에서는 컨텍스트 전파가 contextvars에 의존합니다
주의
일부 ASGI 서버는 fork 안전성 문제로 지원되지 않는다

특정 서버 조합에서는 자동 계측이 공식 지원되지 않습니다.

프로세스 모델이 fork 기반이면서 초기화 순서를 제어할 훅이 없는 서버는 자동 계측이 안정적으로 동작하지 않습니다. 공식 문서에서 지원 여부와 우회 방법을 먼저 확인하세요.

실무에서 가장 무난한 조합은 gunicorn + UvicornWorker(preload 없음)이거나 uvicorn 단독입니다. 워커 수 확장은 쿠버네티스 레플리카로 처리하면 이 문제 자체를 피할 수 있습니다.

참고 · 서버 선택 시
MSP 관점 정리

여섯 개 중 세 개가 프로세스 모델(fork·reload) 문제입니다. 고객사 앱이 Python인데 트레이스가 안 나온다면 "어떤 서버로, 어떤 옵션으로 띄우는가"를 가장 먼저 물어보세요. 코드나 Collector를 들여다보기 전에 이 질문 하나로 절반이 해결됩니다.

Node.js는 설치가 더 간단합니다. 대신 언제 로드되는가가 전부를 결정합니다.

1단계 · 패키지 설치

npm install @opentelemetry/api \
            @opentelemetry/auto-instrumentations-node \
            @opentelemetry/sdk-node \
            @opentelemetry/exporter-trace-otlp-proto

2단계 · 실행 시 미리 로드

export OTEL_SERVICE_NAME=bff-gateway

ESM 지원은 계속 개선되는 영역입니다. 사용하는 Node 버전과 패키지 버전 조합은 공식 문서에서 확인하는 편이 안전합니다.

SECTION 05

Node.js의 함정 다섯 가지

Python이 프로세스 모델 문제라면, Node.js는 모듈 시스템 문제가 중심입니다.

SDK를 앱 코드 안에서 import한다

app.js 맨 위에서 SDK를 불러왔는데 Span이 안 생기거나 일부만 생깁니다.

ESM에서 import 문은 호이스팅되어 파일 맨 위에 쓴 순서와 무관하게 먼저 평가됩니다. Express를 SDK보다 먼저 로드해 버리면, 계측이 붙을 대상이 이미 메모리에 고정된 뒤입니다.

해결은 앱 코드 밖에서 미리 로드하는 것입니다. --require 또는 --import 플래그를 쓰는 이유가 이것입니다.

# 위험 — 앱 안에서 초기화
node app.js

# 안전 — 앱보다 먼저 로드
node --require @opentelemetry/auto-instrumentations-node/register app.js
치명 · 가장 흔함
번들러로 묶으면 계측이 사라진다

로컬에서는 되는데 webpack·esbuild로 빌드한 결과물에서는 Span이 안 나옵니다.

계측은 모듈을 가져오는 순간을 가로채는 방식입니다. 번들러는 모든 모듈을 하나의 파일로 합치면서 그 과정을 없애버립니다. 가로챌 지점 자체가 사라지는 것입니다.

  • 서버 애플리케이션은 번들링하지 않는 것이 가장 단순한 해법입니다
  • 번들이 필요하면 계측 대상 패키지를 external로 제외합니다
  • 서버리스처럼 번들이 필수인 환경은 해당 플랫폼의 전용 배포 방식을 확인하세요
치명 · 빌드 파이프라인
ESM 프로젝트에서 --require를 쓴다

"type": "module"인데 CommonJS용 플래그를 그대로 씁니다.

CommonJS의 require와 ESM의 import는 로딩 메커니즘이 다릅니다. 계측도 각각 다른 후킹 방식을 씁니다.

  • CommonJS → --require
  • ESM → --import (Node 20.6+ / 18.19+)
  • 혼재 프로젝트라면 일부만 계측되는 상태가 될 수 있습니다
  • ESM 계측 지원은 개선 중인 영역이라 버전 조합 확인이 필요합니다
주의 · 모듈 시스템
TypeScript 컴파일 결과와 소스가 헷갈린다

ts-node로는 되는데 빌드한 뒤에는 안 됩니다.

컴파일된 결과물이 CommonJS인지 ESM인지에 따라 플래그가 달라집니다. tsconfig.json의 module 설정과 package.json의 type을 함께 확인하세요.

또한 빌드 산출물이 번들이라면 앞의 번들러 함정과 겹칩니다. 실제로 운영에서 실행되는 파일을 기준으로 판단해야 합니다.

주의
콜백·이벤트 경계에서 컨텍스트가 끊긴다

비동기 처리 이후의 Span이 별도 트레이스로 떨어집니다.

Node.js 계측은 AsyncLocalStorage로 컨텍스트를 이어갑니다. 대부분의 async/await와 Promise 체인은 자동으로 처리되지만, 일부 경계는 끊깁니다.

  • 수동으로 만든 EventEmitter 콜백
  • 계측되지 않은 워커 스레드나 큐 라이브러리
  • 전역 배열에 콜백을 모아뒀다가 나중에 실행하는 패턴

이 경우 컨텍스트를 명시적으로 바인딩해야 합니다. 구체적 방법은 5편에서 다룹니다.

주의 · 비동기 경계
SECTION 06

비동기 컨텍스트 전파 — 3언어 대조

2편에서 "스레드풀을 넘으면 끊긴다"고 했습니다. 그 저장소가 언어마다 다르고, 끊기는 지점도 다릅니다.

저장소 · ThreadLocal

컨텍스트가 스레드 단위로 저장됩니다. 다른 스레드는 그 값을 볼 수 없습니다.

끊기는 곳 — 직접 만든 ExecutorService, CompletableFuture 체인의 일부, 수동 스레드 생성

잡히는 곳 — 서블릿 컨테이너의 요청 스레드, 자동 계측이 감싼 스레드풀

// 직접 만든 Executor는 감싸야 합니다
executor.execute(Context.current().wrap(task));

저장소 · contextvars

Python 3.7부터 표준으로 들어온 컨텍스트 변수입니다. async/await 경계를 자연스럽게 따라갑니다.

끊기는 곳 — ThreadPoolExecutor로 넘긴 작업, multiprocessing으로 만든 프로세스, fork 이후의 자식

잡히는 곳 — asyncio 태스크, ASGI 요청 처리 전체

# 스레드로 넘길 때는 컨텍스트를 함께 전달
import contextvars
ctx = contextvars.copy_context()
executor.submit(ctx.run, task)

Python에서 특히 주의할 것은 프로세스 경계입니다. 스레드보다 프로세스를 쓰는 패턴이 많고, fork된 프로세스는 컨텍스트뿐 아니라 SDK 초기화 자체가 문제가 됩니다.

저장소 · AsyncLocalStorage

Node.js가 제공하는 비동기 컨텍스트 저장소입니다. 이벤트 루프를 넘나드는 Promise 체인을 추적합니다.

끊기는 곳 — 수동 EventEmitter 콜백, 워커 스레드, 콜백을 모아뒀다 나중에 실행하는 패턴

잡히는 곳 — async/await, Promise 체인, 계측된 라이브러리의 콜백 대부분

// 컨텍스트를 명시적으로 묶어 실행
const ctx = context.active();
emitter.on('done', context.bind(ctx, handler));

Node.js는 단일 프로세스·단일 스레드가 기본이라 Python 같은 fork 문제는 적습니다. 대신 모듈 로딩이 약점입니다.

한 문장 요약

Java는 스레드를 넘을 때, Python은 프로세스를 넘을 때, Node.js는 모듈 로딩 순서가 어긋날 때 끊깁니다. 각 언어의 실행 모델에서 가장 흔한 경계가 곧 가장 흔한 함정입니다.

Node.js 개발자에게 줄 5줄

      

        1. @opentelemetry/auto-instrumentations-node 설치

        2. CommonJS는 --require, ESM은 --import

        3. 앱 코드 안에서 SDK를 초기화하지 말 것

        4. 서버 코드는 번들링하지 말 것

        5. 엔드포인트는 4318, 프로토콜은 http/protobuf
