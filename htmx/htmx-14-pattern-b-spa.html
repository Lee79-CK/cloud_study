03

HtmxRegion 컴포넌트

apps/react-console/src/main.jsx (발췌)
function HtmxRegion({ id, url, onSwap, className }) {
  const ref = useRef(null);
  useEffect(() => {
    const el = ref.current;
    stats.loads++;
    // source를 영역 div로 지정해야 htmx 이벤트가 이 div에서 발생·버블링된다 (지정하지 않으면 body가 출처)
    htmx.ajax('GET', url, { source: el, target: el, swap: 'innerHTML' });
    const onAfterSwap = () => onSwap?.(new Date());
    el.addEventListener('htmx:after:swap', onAfterSwap);
    return () => {
      el.removeEventListener('htmx:after:swap', onAfterSwap);
      stats.cleanups++;
      if (window.__regionCleanup !== 'none') htmx.swap({ target: el, swap: 'innerHTML', text: '' });
    };
  }, [url]);
  // children 없음: React는 이 div의 안쪽을 건드리지 않는다
  return <div ref={ref} id={id} className={className} />;
}

영역 안에 들어온 상세 조각에는 13편의 <metric-chart>(React 웹 컴포넌트)도 있습니다. 즉 React SPA → htmx 영역 → React 웹 컴포넌트의 3중 구조인데, 소유권 경계를 지켰기 때문에 측정에서 아무 문제 없이 차트가 그려졌습니다. 다만 콘솔 번들(React 포함, 258.89kB)과 아일랜드 번들(React 포함, 222.64kB)이 각자 React를 하나씩 싣고 있어 이 페이지에는 React가 두 벌 있습니다. 15편의 공유 런타임에서 다룹니다.

04

정리하지 않으면 남는 것

React가 라우트를 바꾸면 HtmxRegion의 div가 통째로 사라집니다. htmx 입장에서는 자기 요소들이 예고 없이 문서에서 빠진 것입니다. htmx의 정리(htmx:before:cleanup, 타이머 해제, 확장의 연결 종료)는 htmx가 직접 스왑할 때만 돕니다.

영역 안의 자원React만 지울 때 (측정·소스)htmx.swap으로 비우고 지울 때
SSE 연결 (hx-sse:connect, 콘솔 홈 "실시간 요약")서버 접속 수가 1로 32초 넘게 유지. 15초마다 오는 : ping 주석 줄로는 끊기지 않았고, 서버가 실제 변경을 보낸 순간(확장이 메시지마다 isConnected 확인) 0이 됨라우트를 떠나는 즉시 0
폴링 (every 10s, 상세의 활동 기록)다음 주기에 htmx가 isConnected를 보고 스스로 타이머를 해제 (4.0.1 소스). 요청은 나가지 않음즉시 해제
요소 리스너노드와 함께 가비지 컬렉션 대상같음
정리 이벤트 (htmx:before:cleanup)발생하지 않음발생. 단 대상이 이미 문서 밖이라 이벤트는 document에서 발생 (측정, 아래 단락)

정리 함수 안에서 htmx.swap을 가로채 보니 대상 div의 isConnected가 이미 false였습니다. React는 useEffect 정리를 DOM 변경을 반영한 뒤에 실행하기 때문입니다. 그래도 htmx 4.0.1은 떨어진 대상의 자식들에 정리를 실행해 SSE 확장이 htmx:sse:close(사유 "cleanup")를 내고 연결을 닫았으며, 정리 이벤트는 요소가 문서 밖이라 document에서 발생했습니다. 그러므로 정리 이벤트를 영역 div에서 들으려 하면 놓칩니다.

"React 홈"으로 가면 영역이 언마운트됩니다. 두 정리 방식 모두 폴링은 곧 멈추지만(위 표의 소스 동작), htmx:before:cleanup 수는 htmx.swap으로 비울 때만 올라갑니다. SSE·WebSocket처럼 "다음 신호가 올 때까지" 기다리는 자원은 이 차이 때문에 남습니다.

05

React 영역과 서버 영역의 대화

방향방법랩 예
서버 영역 → React영역 div에 addEventListener (htmx 이벤트·HX-Trigger 이벤트가 버블링됨). React의 onXxx 속성은 사용자 정의 이벤트에 쓰지 않음htmx:after:swap → "마지막 서버 영역 갱신" 시각
React → 서버 영역htmx.ajax, htmx.trigger(영역 안 요소, 이름), 또는 key를 바꿔 다시 마운트"서버 영역 새로고침" 버튼 → htmx.ajax('GET', '/vms/web-01', {target: '#vm-region'})
React가 hx 속성을 바꿨을 때htmx.process(el, true). 4.0.1 소스 주석: 이미 처리된 요소의 hx 속성을 바꾼 뒤에는 force로 다시 연결(랩에서는 key 재마운트를 씀)

13편의 이벤트 계약도 그대로 통합니다. 영역 안의 차트가 보내는 metric:select는 영역의 htmx 요소가 받고, 이 이벤트는 계속 버블링되어 React 쪽 리스너도 받을 수 있습니다.

06

StrictMode의 이중 실행

React 개발 모드의 <StrictMode>는 버그를 드러내려고 effect를 "마운트 → 정리 → 마운트"로 한 번 더 실행합니다. 정리 함수가 마운트를 정확히 되돌리는지 확인하는 장치입니다.

빌드콘솔 홈 → web-01 이동까지 영역 로드·정리서버가 받은 GET /vms/web-01화면
운영 빌드 (npm run build)로드 2 · 정리 11회정상
개발 빌드 (React 개발 모드)로드 4 · 정리 32회정상 (두 번째 결과가 남음)

개발 모드의 이중 요청은 버그가 아니라 정리 함수가 대칭인지 시험받는 것입니다. 이 컴포넌트는 정리에서 영역을 비우므로 두 번째 마운트가 깨끗한 상태에서 다시 요청해 화면이 정상이었습니다. 정리에서 아무것도 하지 않았다면, 첫 요청과 두 번째 요청이 같은 div에 경쟁적으로 들어갑니다. 서버 로그에 개발 중에만 요청이 두 배로 찍힌다면 이 때문입니다.

측정으로 찾은 것: --mode development만으로는 React 개발 빌드가 아니다

처음에는 vite build --mode development로 개발 빌드를 만들었는데, 번들이 691.97kB로 커지기만 하고 StrictMode 이중 실행이 나타나지 않았습니다(React는 운영 빌드). NODE_ENV=development를 함께 주자 1,110.49kB가 되고 "Download the React DevTools" 문구가 포함되며 이중 실행이 나타났습니다. 그래서 콘솔의 vite.config.js에서 개발 모드일 때 process.env.NODE_ENV를 명시하도록 했습니다(npm run build:dev).

07

라우터와 히스토리의 충돌

7편의 htmx 히스토리는 "주소의 주인은 htmx"를 전제로 합니다. SPA에서는 주인이 React Router입니다. 주인이 둘이면 무슨 일이 생기는지 랩에서 재현했습니다(/console/vms/web-03?hxhistory=on으로 htmx history를 켠 채 SPA를 열고, 영역 안에 hx-push-url="/vms/web-09" 버튼을 넣어 누른 뒤 뒤로 가기).

단계history: true (htmx 기본)history: false (랩 SPA 설정)
버튼 클릭 후 주소/vms/web-09. React 화면은 web-01 그대로 (라우터 몰래 주소 변경)/console/vms/web-01 그대로
history.state{"htmx":true} (React Router의 {usr, key, idx} 대신)React Router 상태 유지
뒤로 가기htmx가 가로채 GET /console/vms/web-01(HX-History-Restore-Request)로 body를 교체 → #root 자식 0개, React 앱이 사라짐React Router가 처리, 콘솔 홈 정상 표시

원인은 7편에서 본 htmx 4의 동작 그대로입니다. 첫 htmx 스왑 때 현재 기록에 {htmx: true}를 찍고, 그런 기록으로 돌아가면 Navigation API를 가로채 서버에 다시 요청해 body를 바꿉니다. SPA 페이지에서는 <meta name="htmx-config" content='{"history": false}'>로 htmx의 주소 관리를 끄고(4.0.1 소스: #handleHistoryUpdate가 첫 줄에서 반환, 초기화 때 가로채기 리스너도 걸지 않음), 영역 안에는 hx-push-url·hx-boost를 쓰지 않습니다. 영역 안 링크가 SPA의 다른 화면으로 가야 한다면 React 쪽에서 클릭을 가로채 navigate()를 부릅니다.
