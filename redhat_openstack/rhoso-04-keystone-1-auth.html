RHOSO 강의 4 / 33편 Level 1 · 핵심 서비스 이해 (첫 편) 기준: RHOSO 18.0 (OpenStack 2023.1 Antelope)

4편Keystone 1: 인증의 원리

OpenStack의 모든 요청은 Keystone에서 시작합니다. 누가(사용자), 어디서(프로젝트), 무엇을 할 수 있는지(역할)를 확인해 짧은 수명의 출입증(토큰)을 내주고, 각 서비스가 어디에 있는지(카탈로그) 알려 주는 것. 이 편은 그 출입증 한 장이 만들어지고 검증되는 전 과정을 따라갑니다.

약 100분예상 학습 시간
1~3편 이수세 개의 문, 열쇠 두 개
명령 실습 포함Level 2 이후 직접 실행
다음 편5편 Keystone 2: 실전 운영

섹션 1

이 편의 목표

  1. Keystone의 다섯 가지 일(신원, 자원, 할당, 토큰, 카탈로그)과, 권한 판단은 각 서비스가 한다는 점을 설명한다.
  2. 도메인·프로젝트·사용자·그룹·역할의 관계와 역할 할당(그룹, 상속, 암묵 역할 포함)으로 실제 권한을 계산한다.
  3. 토큰의 범위(scope) 네 가지와, 같은 사용자라도 범위에 따라 할 수 있는 일이 달라지는 이유를 설명한다.
  4. openstack token issue와 HTTP 요청으로 인증 → 토큰 발급 → 서비스 호출 → 토큰 검증 흐름을 따라간다.
  5. Fernet 토큰의 내용물, 키 저장소(staged·primary·secondary)와 회전, 수명·무효화 규칙을 설명한다.
  6. 서비스 카탈로그의 public·internal·admin 인터페이스와 3편 “세 개의 문”의 관계를 설명한다.
  7. reader·member·admin 역할과 RBAC 기본 정책, 그리고 401과 403의 차이를 구분한다.

이 편을 관통하는 비유: 회사 출입 관리

Keystone은 회사 로비의 출입 관리 데스크입니다. 직원 명부(사용자)를 확인하고, 어느 부서(프로젝트) 소속으로 어떤 등급(역할)인지 보고 하루짜리 방문증(토큰)을 발급하며, 층별 안내도(카탈로그)를 함께 줍니다. 그런데 각 층의 문 앞에서 “이 방문증으로 이 방에 들어갈 수 있나”를 최종 판단하는 것은 각 층의 경비(각 서비스의 정책)입니다. 이 구분이 이 편의 핵심입니다.

섹션 2

Keystone이 하는 다섯 가지 일

Keystone(OpenStack Identity 서비스)은 내부적으로 역할이 다른 다섯 부분으로 나뉩니다. 각각 다른 질문에 답합니다.

Identity신원“너는 누구냐?” 사용자·그룹을 관리하고 비밀번호를 확인합니다. 저장소는 기본 SQL이며, LDAP·외부 IdP와도 연결됩니다(5편).
Resource자원“어디 소속이냐?” 도메인과 프로젝트(계층 포함)를 관리합니다.
Assignment할당“거기서 무슨 역할이냐?” 사용자·그룹에게 프로젝트·도메인·시스템 범위의 역할을 붙입니다.
Token토큰“증표를 내준다.” 확인이 끝나면 짧은 수명의 토큰을 발급하고, 서비스가 물어오면 검증합니다.
Catalog카탈로그“어디에 무엇이 있나.” 서비스와 엔드포인트(주소) 목록을 토큰과 함께 줍니다.

가장 흔한 오해 바로잡기: Keystone은 “판사”가 아니다

Keystone은 “이 사람은 alice이고, a-web 프로젝트에서 member 역할을 가졌다”는 사실 확인서(토큰)를 줄 뿐입니다. “member가 인스턴스를 지울 수 있나?”는 Nova가 자기 정책 규칙(oslo.policy)으로 판단합니다. 그래서 “권한이 없다(403)” 오류의 원인은 Keystone이 아니라 해당 서비스의 정책인 경우가 대부분입니다(섹션 12, 14).

3편의 기동 순서에서 Keystone이 공유 인프라 바로 다음에 서는 이유도 여기에 있습니다. 다른 서비스들은 Keystone에 서비스 사용자를 만들고 카탈로그에 자기 주소를 등록해야 동작할 수 있습니다. Keystone이 멈추면 실행 중인 VM은 그대로지만, 거의 모든 API 호출이 실패합니다(3편 고장 지도).

섹션 3

신원 모델: 도메인·프로젝트·사용자·그룹·역할

Keystone의 데이터 모델은 다섯 개의 명사와 하나의 동사(할당)로 이뤄집니다.

개념뜻예 (MSP 환경)주의
도메인사용자·그룹·프로젝트의 이름 공간이자 관리 경계Default(운영사 자체), cust-a, cust-b (고객사별)도메인이 다르면 같은 이름의 사용자가 있어도 다른 사람. 로그인할 때 도메인을 함께 지정해야 함
프로젝트자원의 소유·격리·쿼터 단위. 상위 프로젝트 아래 하위 프로젝트를 둘 수 있음(계층)cust-a 도메인의 a-web, a-data프로젝트는 반드시 하나의 도메인에 속함
사용자로그인하는 주체(사람 또는 자동화)alice@cust-a, 서비스 사용자 nova@Default서비스 사용자는 Operator가 만든 것. 함부로 바꾸면 서비스 장애
그룹사용자 묶음. 역할을 그룹에 주면 구성원 모두 받음a-devs, msp-operators사람 단위보다 그룹 단위 할당이 관리하기 쉬움
역할권한 등급의 이름표. 실제 허용 동작은 서비스 정책이 정함reader, member, admin역할 자체에는 “무엇을 할 수 있다”는 내용이 없음
역할 할당(누가) × (어떤 역할을) × (어디서) 의 조합“그룹 a-devs에게 a-web 프로젝트에서 member”할당이 없으면 그 프로젝트로 토큰을 받을 수 없음

역할 할당의 세 칸

# (누가: 사용자 또는 그룹)  ×  (역할)  ×  (어디서: 프로젝트 / 도메인 / 시스템)
openstack role add --user alice --user-domain cust-a --project a-web --project-domain cust-a member
openstack role add --group a-devs --group-domain cust-a --project a-web --project-domain cust-a member
openstack role add --group msp-operators --group-domain Default --domain cust-a --inherited reader
openstack role add --user admin --user-domain Default --system all admin

이름으로 지정할 때는 항상 --user-domain, --project-domain처럼 소속 도메인을 함께 적는 습관을 들이세요. 도메인이 여러 개인 환경에서 이름이 겹칠 수 있습니다.

권한을 넓히는 세 가지 장치

장치설명예
그룹그룹에 준 역할은 그룹 구성원 모두가 받습니다.a-devs → member @ a-web 이면 alice·dan 모두 member
상속(--inherited)도메인이나 상위 프로젝트에 “상속” 표시로 준 역할은 그 아래 모든 프로젝트에 적용됩니다. 상속 할당은 그 도메인·상위 프로젝트 자체에는 적용되지 않습니다.msp-operators → reader @ cust-a 도메인(상속) 이면 cust-a의 모든 프로젝트에서 reader
암묵 역할(implied role)한 역할이 다른 역할을 포함하도록 정의. 기본적으로 admin ⊃ member ⊃ readeradmin을 받으면 member·reader도 자동으로 가짐
 
# 실제로 적용되는 권한을 보는 명령: --effective 가 그룹·상속을 풀어서 보여 줌
openstack role assignment list --user alice --user-domain cust-a --names --effective
openstack implied role list      # admin → member → reader 연결 확인

섹션 4

역할 할당 계산기

가상의 MSP 클라우드입니다. 위에는 조직 구조와 할당 규칙, 아래에서 사용자를 고르면 프로젝트별 실제 역할과 그 이유(직접·그룹·상속·암묵)가 계산됩니다. --effective가 머릿속에서 하는 일을 눈으로 보는 연습입니다.

할당 규칙

사용자를 골라 보세요.

계산기에서 꼭 확인할 세 장면

  1. msp-ops: 고객 도메인에 상속 reader를 받아, 고객의 모든 프로젝트를 읽을 수 있습니다. 하지만 상속 할당이라 도메인 자체 관리 권한은 없습니다. MSP 관제 계정의 전형적인 설계입니다.
  2. carol: b-prod에 상속 member를 받아 하위 프로젝트 b-batch에서도 member입니다. 반면 b-prod 자체에는 상속 할당만 있으면 적용되지 않으므로, 이 예시에서는 b-prod에 직접 할당도 따로 주었습니다.
  3. alice: 그룹(a-devs)으로 member, a-data에는 직접 reader. 그룹에서 빠지면 a-web 권한이 즉시 사라집니다(이미 발급된 토큰 처리는 섹션 10).

섹션 5

토큰의 범위(scope)

토큰은 “누구”뿐 아니라 “어디에 대한” 증표입니다. 같은 사용자라도 어떤 범위로 토큰을 받느냐에 따라 토큰 안의 역할과 할 수 있는 일이 달라집니다.

범위받는 법토큰에 담기는 것주로 하는 일
무범위(unscoped)프로젝트·도메인을 지정하지 않고 인증사용자 정보만, 역할·카탈로그 없음“내가 접근 가능한 프로젝트 목록 보기” 후 범위 있는 토큰으로 교환 (Horizon 로그인 첫 단계가 이것)
프로젝트 범위--os-project-name a-web --os-project-domain-name cust-a그 프로젝트에서의 역할 + 카탈로그인스턴스·네트워크·볼륨 등 일상 작업의 대부분
도메인 범위--os-domain-name cust-a그 도메인에서의 역할도메인 안의 사용자·그룹·프로젝트 관리 (도메인 관리자)
시스템 범위--os-system-scope all시스템 전체에 대한 역할엔드포인트·서비스·하이퍼바이저처럼 특정 프로젝트에 속하지 않는 클라우드 전역 자원 관리

비유: 방문증의 출입 구역 표시

같은 직원이라도 “3층 영업부 출입” 방문증과 “건물 전체 시설 관리” 방문증은 다릅니다. 영업부 방문증으로 서버실에 못 들어가고, 시설 관리 방문증에는 영업부 서류 열람 권한이 없을 수 있습니다. 범위는 최소 권한 원칙의 도구입니다. 그때그때 필요한 범위로만 토큰을 받는 것이 좋습니다.

참고: 시스템 범위는 비교적 새로운 개념이라, 서비스마다 “어떤 API를 시스템 범위로만 허용하는가”의 적용 정도가 다릅니다. 실제 동작은 각 서비스의 정책과 RHOSO 설정(섹션 12·13)을 따릅니다.

섹션 7

token issue와 curl로 해부하기

Level 2 이후 openstackclient Pod에서 그대로 따라 할 수 있는 명령들입니다. 출력 값은 예시입니다.

① CLI가 무엇을 보내고 받는지 보기: --debug

$ oc rsh -n openstack openstackclient
sh-5.1$ echo $OS_CLOUD            # 이 Pod는 미리 정해진 cloud 이름을 씀
sh-5.1$ openstack --debug token issue 2>&1 | grep -E "REQ:|RESP:" | head
REQ: curl -g -i -X POST https://keystone-public-openstack.apps.…/v3/auth/tokens …
RESP: [201] … X-Subject-Token: {SHA256}…   ← 디버그 출력은 토큰을 가려 보여 줌

--debug 출력 다루기

--debug 출력에는 요청 본문, 엔드포인트, 경우에 따라 민감한 정보가 담깁니다. 장애 티켓이나 메신저에 그대로 붙이지 말고, 필요한 줄만 골라 비밀번호·토큰을 지운 뒤 공유하세요.

② 토큰을 직접 받아 보기: curl

# 비밀번호 방식 + 프로젝트 범위로 토큰 요청
$ curl -s -i -X POST "$OS_AUTH_URL/v3/auth/tokens" \
    -H "Content-Type: application/json" -d '{
  "auth": {
    "identity": { "methods": ["password"],
      "password": { "user": { "name": "alice", "domain": { "name": "cust-a" }, "password": "…" } } },
    "scope": { "project": { "name": "a-web", "domain": { "name": "cust-a" } } }
  }}'

HTTP/1.1 201 Created
X-Subject-Token: gAAAAABo…          ← 토큰은 본문이 아니라 응답 헤더에!
{ "token": {
    "methods": ["password"],
    "user": { "name": "alice", "domain": { "name": "cust-a" }, … },
    "project": { "name": "a-web", … },
    "roles": [ {"name":"member"}, {"name":"reader"} ],   ← 암묵 역할까지 펼쳐짐

③ 받은 토큰으로 서비스 호출하기

$ TOKEN=gAAAAABo…
$ curl -s -H "X-Auth-Token: $TOKEN" https://nova-public-openstack.apps.…/v2.1/servers | jq '.servers[].name'

④ 토큰 검증과 폐기 (관리자)

# 서비스가 매번 하는 검증을 사람이 해 보기: 내 토큰(X-Auth-Token)으로 남의 토큰(X-Subject-Token)을 검사
$ curl -s -o /dev/null -w "%{http_code}\n" -H "X-Auth-Token: $ADMIN_TOKEN" \
       -H "X-Subject-Token: $TOKEN" "$OS_AUTH_URL/v3/auth/tokens"
200                      # 유효. 만료·폐기됐으면 404
$ openstack token revoke $TOKEN   # 즉시 폐기
헤더뜻
X-Auth-Token“나는 이 토큰의 주인이다.” 모든 API 요청에 붙이는 내 토큰
X-Subject-Token“이 토큰에 대해 말하는 중이다.” 발급 응답에서 새 토큰을 담거나, 검증 요청에서 검사 대상 토큰을 가리킴
X-Service-Token서비스가 사용자 대신 다른 서비스를 부를 때 덧붙이는 자기 토큰 (섹션 10의 만료 허용과 연결)

섹션 8

Fernet 토큰 해부

예전의 UUID·PKI 형식 토큰은 업스트림에서 제거되었고, 현재 Keystone은 Fernet(기본값)과 JWS 형식을 지원합니다. RHOSO의 Keystone은 Fernet을 씁니다.

무엇이 들어 있나

들어 있는 것설명
사용자 ID누구의 토큰인가
인증 방식(methods)password, token, application_credential 등
범위 ID프로젝트·도메인·시스템 중 무엇에 대한 토큰인가
만료 시각언제까지 유효한가
감사 ID(audit_id)토큰을 특정·폐기·추적할 때 쓰는 식별자
들어 있지 않은 것역할 목록, 카탈로그. 검증 시점에 Keystone이 DB에서 다시 계산합니다. 그래서 역할을 빼면 이미 발급된 토큰에도 반영될 수 있습니다(섹션 10).

어떻게 만들어지나

  1. 위 정보를 작게 직렬화(묶기)합니다.
  2. AES(대칭키 암호)로 암호화해 내용을 숨기고, HMAC-SHA256(서명)으로 위조를 막습니다. Fernet은 이 두 가지를 묶은 표준 규격입니다.
  3. URL에 넣어도 안전한 base64 문자열로 바꿉니다. Fernet 토큰이 늘 gAAAAA로 시작하는 것은 규격의 버전 바이트 때문입니다.

장점: DB에 저장하지 않는다

예전 UUID 토큰은 발급할 때마다 DB에 기록해 DB가 계속 커졌습니다. Fernet은 키만 있으면 누구든 복호화해 검증할 수 있어 토큰을 저장하지 않습니다(비영속). Keystone Pod를 여러 개 띄워도 같은 키만 공유하면 됩니다.

대가: 키가 곧 금고 열쇠

Fernet 키를 가진 사람은 유효한 토큰을 위조할 수 있습니다. 그래서 키는 Secret으로 보호하고 주기적으로 회전합니다. 또 모든 Keystone Pod가 같은 키 세트를 가져야 하며, 어긋나면 “어떤 Pod에서는 401”이 납니다.

키 저장소: 세 종류의 키

종류파일 이름(번호)역할
staged (대기)0다음 회전 때 primary가 될 키. 복호화만 가능. 미리 모든 노드에 퍼뜨려 두기 위해 존재
primary (현용)가장 큰 번호새 토큰을 암호화하는 유일한 키. 복호화도 가능
secondary (이전)그 밖의 번호예전 primary. 그 키로 만든 아직 안 끝난 토큰을 복호화하기 위해 남겨 둠

회전 한 번에 일어나는 일: staged → primary(새 번호를 받음), primary → secondary, 새 staged(0) 생성, 키 개수가 최대치(max_active_keys)를 넘으면 가장 오래된 secondary 삭제. 다음 섹션에서 직접 돌려 봅니다.

섹션 9

Fernet 키 회전 시뮬레이터

토큰을 발급하고 키를 회전해 보세요. 핵심 질문은 하나입니다. “아직 만료되지 않은 토큰인데, 그 토큰을 만든 키가 지워져 버리면?” 그러면 멀쩡한 토큰이 갑자기 401이 됩니다. 아래에서 그 상황을 일부러 만들어 보고, 막는 규칙을 찾아보세요.

키 저장소

발급된 토큰

찾아야 할 규칙

토큰이 살아 있는 동안 그 토큰의 키가 남아 있으려면, 최대 키 개수 ≥ (토큰 수명 ÷ 회전 주기) + 2 여야 합니다. “+2”는 staged 키 1개와, 회전 직전에 발급된 토큰을 위한 여유 1개입니다. 예를 들어 토큰 수명 1시간, 회전 주기 15분이면 최소 6개가 필요합니다. 시뮬레이터에서 토큰 수명을 늘리거나 최대 키 개수를 줄여 빨간 토큰(검증 실패)이 생기는지 확인해 보세요.

RHOSO에서는 keystone-operator가 키 생성·회전·배포를 맡습니다. 업스트림 Operator 소스 기준 기본값은 회전 주기 1일(fernetRotationDays), 최대 키 5개(fernetMaxActiveKeys)입니다. 기본 토큰 수명이 1시간이므로 이 조합은 여유가 충분합니다. 키는 Secret에 담겨 모든 Keystone Pod가 같은 세트를 쓰게 됩니다. 설치된 버전의 실제 기본값은 oc explain keystoneapi.spec으로 확인하세요.

사람이 키를 손대지 않는다

Keystone Pod 안에서 keystone-manage fernet_rotate를 직접 실행하거나 키 파일을 바꾸면, Operator가 관리하는 Secret과 어긋나 Pod마다 키가 달라질 수 있습니다. 그러면 “어떤 요청은 되고 어떤 요청은 401”인 간헐 장애가 납니다. 회전 주기·개수 변경은 CR에서 합니다.

운영 함정 두 가지

  • 캐시 지연: 서비스가 검증 결과를 캐시하는 동안(기본 최대 5분)은 폐기된 토큰이 그 서비스에서 계속 통할 수 있습니다. “퇴사자 계정을 막았는데 몇 분간 API가 됐다”는 보고의 원인입니다. 보안 사고 대응 시 이 지연을 감안합니다.
  • 시계 어긋남: 토큰의 발급·만료는 시각으로 판단합니다. 노드 간 시간이 어긋나면 “방금 받은 토큰이 만료됐다”는 이상한 401이 납니다. OCP 노드와 컴퓨트 노드 모두 시간 동기화(NTP, chrony)가 필수입니다.

섹션 12

역할과 RBAC 기본

RBAC(역할 기반 접근 제어)의 실제 판단은 각 서비스의 oslo.policy가 합니다. 서비스마다 “이 API는 어떤 조건에서 허용”이라는 정책 규칙이 코드에 기본값으로 들어 있고, 운영자가 정책 파일로 덮어쓸 수 있습니다(5편).

# 정책 규칙의 생김새 (개념 예시)
"os_compute_api:servers:index":  "role:reader and project_id:%(project_id)s"
"os_compute_api:servers:create": "role:member and project_id:%(project_id)s"
"os_compute_api:os-flavor-manage:create": "role:admin"

“자기 프로젝트의 reader면 목록 보기 가능, member면 생성 가능, 플레이버 생성은 admin만” 같은 식으로 읽습니다.

세 가지 기본 역할과 흔한 기본 정책

OpenStack은 서비스 전반에 reader · member · admin 세 단계를 일관되게 쓰는 새 기본 정책(Secure RBAC)으로 옮겨 왔습니다. 아래는 일반적인 경향을 정리한 표입니다. 실제 허용 여부는 서비스·버전·설정에 따라 다르므로 운영 전에 반드시 확인하세요.

작업readermemberadmin
자기 프로젝트의 인스턴스·네트워크·볼륨 목록·상세 보기✓✓✓
자기 프로젝트에 인스턴스·볼륨·네트워크 생성·삭제✗✓✓
다른 프로젝트의 자원 보기·변경✗✗✓ (주의)
플레이버·공용 이미지·프로바이더 네트워크 생성✗✗✓
쿼터 변경, 컴퓨트 노드 활성/비활성✗✗✓
프로젝트·사용자·역할 할당 관리✗✗✓

가장 중요한 경고: admin은 “그 프로젝트의 관리자”가 아니다

이름 때문에 “a-web 프로젝트에서 admin을 주면 a-web만 관리하겠지”라고 생각하기 쉽지만, OpenStack 대부분의 서비스는 admin 역할을 가진 사람을 클라우드 전체 관리자로 취급합니다. 한 프로젝트에서 받은 admin으로 다른 고객의 자원까지 다룰 수 있게 되는 것입니다. 그래서 고객에게는 절대 admin을 주지 않고 member(필요하면 reader)만 줍니다. 고객이 자기 사용자를 직접 관리해야 하는 요구는 5편에서 다루는 방식으로 풉니다.

RHOSO의 keystone-operator에는 enableSecureRBAC 옵션이 있고, 업스트림 소스 기준 기본값은 켜짐(true)입니다. 이 옵션은 새 기본 정책을 쓰도록 서비스 설정을 맞추는 역할을 합니다. 정확한 적용 범위는 설치된 버전의 문서를 확인하세요.

# 권한을 확인하는 습관
openstack role assignment list --user alice --user-domain cust-a --names --effective
openstack --os-project-name a-web --os-project-domain-name cust-a token issue   # 그 범위로 토큰이 나오나?

openstackclient Pod에는 관리자용 clouds.yaml(접속 정보)이 ConfigMap으로, 비밀번호가 별도 Secret으로 마운트되어 있고, OS_CLOUD 환경 변수로 그 cloud 이름이 지정되어 있습니다. 그래서 Pod에 들어가면 바로 openstack 명령을 관리자 권한으로 쓸 수 있습니다. 이 Pod에 들어갈 수 있는 OCP 권한이 곧 OpenStack 관리자 권한이라는 점을 다시 기억하세요(2편 섹션 11).

clouds.yaml을 찾는 순서

openstack CLI는 현재 디렉터리 → ~/.config/openstack → /etc/openstack 순서로 clouds.yaml을 찾고, 처음 찾은 파일을 씁니다. 작업 PC에 여러 파일이 있으면 의도와 다른 클라우드에 접속할 수 있으니, 고객사가 여러 곳인 MSP 환경에서는 --os-cloud로 매번 명시하는 습관이 안전합니다.

섹션 14

인증 오류 읽기

오류 메시지와 HTTP 코드만 봐도 어느 단계에서 막혔는지 알 수 있습니다. 누르면 뜻, 흔한 원인, 첫 확인이 나옵니다. 깊은 디버깅은 5편에서 다룹니다.

오류를 하나 골라 보세요.

401과 403을 한 문장으로

401은 “당신이 누군지 모르겠다(방문증이 없거나, 위조됐거나, 만료됐다)”, 403은 “누군지는 알지만 이 방엔 못 들어간다(방문증 등급이 부족하다)”. 401이면 인증·토큰·시계·키를, 403이면 역할 할당과 서비스 정책을 봅니다.

섹션 15

보안 기본기

  • 최소 권한: 고객에게는 member, 관제 계정에는 상속 reader, admin은 운영자 중에서도 필요한 사람만.
  • 사람이 아닌 계정: CI·Terraform 같은 자동화에는 개인 비밀번호 대신 애플리케이션 크레덴셜을 씁니다(5편).
  • 필요한 범위로만: 일상 작업은 프로젝트 범위 토큰으로, 전역 관리 작업만 시스템 범위로.
  • 토큰은 비밀번호와 같다: 로그·티켓·메신저에 토큰이나 --debug 출력을 그대로 붙이지 않습니다.
  • 시간 동기화: 모든 노드의 시간이 맞아야 토큰 수명 판단이 정확합니다.
  • Fernet 키와 osp-secret 보호: openstack 네임스페이스 Secret 읽기 권한을 엄격히 제한합니다.
  • 계정 잠금·비밀번호 정책: Keystone의 [security_compliance] 설정(실패 횟수 잠금, 비밀번호 만료 등)으로 강화할 수 있습니다(5편, 28편).

섹션 19

정리와 다음 편

오늘의 핵심 여덟 문장

  • Keystone은 신원·자원·할당·토큰·카탈로그를 맡고, 권한 판단은 각 서비스의 oslo.policy가 한다.
  • 역할 할당은 (사용자·그룹) × 역할 × (프로젝트·도메인·시스템)이며, 그룹·상속·암묵 역할로 실제 권한이 넓어진다. 확인은 --effective.
  • 토큰에는 범위가 있다: 무범위·프로젝트·도메인·시스템. 일상 작업은 프로젝트 범위.
  • 흐름은 발급(한 번) → 검증(매 요청, 캐시) → 판단(서비스). 토큰은 응답 헤더 X-Subject-Token으로 오고, 요청엔 X-Auth-Token으로 붙인다.
  • Fernet 토큰은 DB에 저장하지 않고 키로 암호화·서명한다. 역할·카탈로그는 토큰 안에 없다.
  • 키는 staged(0)·primary(최대 번호)·secondary로 나뉘고, 최대 키 개수 ≥ 수명 ÷ 회전 주기 + 2를 지켜야 한다. RHOSO에서는 Operator가 회전한다.
  • 카탈로그의 public = Route, internal = MetalLB VIP. 리전 기본값은 regionOne.
  • 401은 신원, 403은 권한. admin 역할은 사실상 클라우드 전체 관리자이므로 고객에게 주지 않는다.
