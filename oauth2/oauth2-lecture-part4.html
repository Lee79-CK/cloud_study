이제 서버를 세우는 쪽으로

1편부터 3편까지는 남이 만든 인가 서버를 쓰는 입장이었습니다. 마지막 편에서는 Keycloak과 Cognito로 직접 인가 서버를 세우고, kubectl과 API 게이트웨이를 붙이고, 키를 회전시키고, 기존 인증 시스템에서 옮겨 오는 과정을 다룹니다.

예상 학습 시간 70~90분 선행: 1~3편 전체 실습 요소 6개

사내 서비스 다섯 개에 로그인이 필요합니다. 두 가지 접근 중 하나를 골라 보세요.

00

직접 만들지 않는 이유

로그인 기능은 만들기 쉬워 보입니다. 이메일과 비밀번호를 받고, 해시해서 저장하고, 맞으면 세션을 주면 되니까요. 하루면 됩니다. 문제는 그 하루짜리 기능에 딸려 오는 것들입니다.

비밀번호 재설정, 이메일 인증, 2단계 인증, 로그인 시도 제한, 계정 잠금, 세션 관리, 소셜 로그인, SSO, 감사 로그, 비밀번호 정책, 해시 알고리즘 교체. 여기에 서비스가 다섯 개면 이 목록이 다섯 번 반복되거나, 다섯 개가 제각각 다르게 동작합니다.

인가 서버를 하나 두는 것은 이 공통 기능을 한곳에 모으는 결정입니다. 1편부터 3편까지 본 표준이 그 인터페이스가 됩니다. 서비스들은 표준 방식으로 토큰을 받고 검증하기만 하면 되고, 사용자 관리의 복잡도는 인가 서버가 흡수합니다.

다만 공짜는 아닙니다

인가 서버는 단일 장애점이 됩니다. 이게 멈추면 모든 서비스의 로그인이 멈춥니다. 그래서 가용성 설계, 키 관리, 업그레이드 전략이 따라옵니다. 이 강의 후반부가 그 이야기입니다. "세우는 것"보다 "운영하는 것"이 훨씬 긴 일입니다.

세 가지 선택지

직접 구현

표준을 우리가 구현합니다. 통제권은 최대지만, 보안 결함이 곧 전사 인증 사고가 됩니다. 특별한 이유가 없다면 권하지 않습니다.

오픈소스 자체 호스팅

Keycloak이 대표적입니다. 표준 구현은 검증된 것을 쓰고, 배포와 운영만 우리가 맡습니다. 커스터마이징 여지가 큽니다.

관리형 서비스

Cognito 같은 클라우드 서비스입니다. 운영 부담이 가장 적은 대신 제공되는 범위 안에서만 움직일 수 있습니다.

이번 편은 뒤의 두 가지를 다룹니다. 둘의 성격이 꽤 다르므로, 먼저 무엇이 어떻게 다른지부터 정리하겠습니다.

01

Cognito의 .well-known/openid-configuration에는 end_session_endpoint와 revocation_endpoint가 들어 있지 않습니다. 기능 자체는 있지만(각각 도메인의 /logout, /oauth2/revoke) 디스커버리 문서에 노출되지 않아, 디스커버리만 보고 자동 설정되는 OIDC 라이브러리에서는 로그아웃이 동작하지 않습니다. 이 경우 해당 URL을 수동으로 지정해 줘야 합니다. 2편 8장에서 다룬 로그아웃 문제가 여기서 한 겹 더 까다로워지는 셈입니다.

02

용어 대조표

두 제품은 같은 개념을 다른 이름으로 부릅니다. 한쪽 경험만 있는 상태로 다른 쪽 문서를 읽으면 계속 막히는 이유입니다. 왼쪽에서 개념을 눌러 양쪽 대응을 확인해 보세요. 실무에서 가장 자주 찾게 되는 열두 가지입니다.

03

Keycloak 세우기

로컬에서 띄워 보는 것부터 시작합니다. 개발 모드는 한 줄이면 됩니다.

# 개발용 — 메모리 DB, HTTPS 없음. 운영에 절대 쓰지 마세요.
docker run -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.7 start-dev

realm과 client 만들기

화면에서 클릭해도 되지만, 재현 가능하도록 CLI로 남기는 편이 좋습니다. 운영 환경이라면 이 명령들이 그대로 IaC의 재료가 됩니다.

# 관리자 인증
kcadm.sh config credentials --server http://localhost:8080 \
  --realm master --user admin --password admin

# 1. realm 생성 — 서비스 경계 하나
kcadm.sh create realms -s realm=acme -s enabled=true \
  -s displayName="Acme 사내 서비스"

# 2. 프론트엔드용 공개 클라이언트 — 시크릿 없이 PKCE로
kcadm.sh create clients -r acme \
  -s clientId=web-console \
  -s publicClient=true \
  -s 'attributes."pkce.code.challenge.method"=S256' \
  -s standardFlowEnabled=true \
  -s directAccessGrantsEnabled=false \
  -s 'redirectUris=["https://console.acme.com/callback"]' \
  -s 'webOrigins=["https://console.acme.com"]'

# 3. 백엔드 배치용 기밀 클라이언트 — 1편 5장의 Client Credentials
kcadm.sh create clients -r acme \
  -s clientId=billing-batch \
  -s publicClient=false \
  -s serviceAccountsEnabled=true \
  -s standardFlowEnabled=false

액세스 토큰의 aud를 반드시 손보세요

Keycloak을 처음 붙일 때 거의 모두가 겪는 문제입니다. 기본 설정으로 발급받은 액세스 토큰을 2편의 JWT 해부기에 넣어 보면 이렇게 나옵니다.

{
  "iss": "https://kc.acme.com/realms/acme",
  "aud": "account",          // 우리 API가 아니라 Keycloak 내장 클라이언트입니다
  "azp": "web-console",
  "scope": "openid profile email"
}

이 상태에서 리소스 서버가 2편 4장의 절차대로 aud를 검증하면 전부 실패합니다. 그래서 흔히 "aud 검증을 꺼 두자"는 결론으로 가는데, 그건 2편에서 본 토큰 대체 공격을 다시 여는 일입니다. 올바른 해법은 audience 매퍼를 추가하는 것입니다.

# 1. API를 나타내는 클라이언트를 하나 만든다 (리소스 서버 역할)
kcadm.sh create clients -r acme -s clientId=orders-api -s bearerOnly=true

# 2. 커스텀 스코프를 만들고, 그 스코프에 audience 매퍼를 붙인다
kcadm.sh create client-scopes -r acme \
  -s name=orders-read -s protocol=openid-connect \
  -s 'attributes."include.in.token.scope"=true'

# 3. 매퍼 추가 — 이 스코프가 붙은 토큰의 aud에 orders-api를 넣는다
kcadm.sh create "client-scopes/$SCOPE_ID/protocol-mappers/models" -r acme \
  -s name=orders-audience \
  -s protocol=openid-connect \
  -s protocolMapper=oidc-audience-mapper \
  -s 'config."included.client.audience"=orders-api' \
  -s 'config."access.token.claim"=true'

이제 클라이언트가 scope=openid orders-read로 요청하면 액세스 토큰의 aud에 orders-api가 들어갑니다. 스코프와 대상 API가 함께 움직이므로, 1편 8장에서 설계한 스코프 모델이 그대로 살아납니다.

운영으로 넘어갈 때 꼭 확인할 것

hostname 설정

Keycloak이 만들어 내는 발급자 URL(iss)과 리다이렉트 주소는 KC_HOSTNAME 설정에서 나옵니다. 이게 실제 접속 주소와 다르면, 토큰의 iss가 틀어져 클라이언트의 검증이 전부 실패합니다. 리버스 프록시 뒤에 두는 경우가 대부분이므로 프록시 헤더 설정도 함께 맞춰야 합니다.

# 운영 기동 예시
KC_HOSTNAME=https://kc.acme.com
KC_PROXY_HEADERS=xforwarded
KC_HTTP_ENABLED=true            # TLS 종료를 프록시가 할 때
KC_DB=postgres
KC_DB_URL=jdbc:postgresql://db.internal:5432/keycloak
KC_HEALTH_ENABLED=true
KC_METRICS_ENABLED=true

bin/kc.sh start               # start-dev 가 아닙니다
start-dev로 운영하지 마세요

개발 모드는 HTTPS를 요구하지 않고, 호스트명 검증을 느슨하게 하며, 기본 설정이 메모리 DB입니다. 재시작하면 데이터가 사라집니다. 데모로 올려 둔 것이 그대로 운영이 되는 사고가 드물지 않습니다.

master realm은 관리 전용으로

master realm은 Keycloak 자체를 관리하는 realm입니다. 여기에 서비스 사용자를 넣지 말고, 업무용 realm을 따로 만들어 쓰세요. 관리자 계정에도 2단계 인증을 걸어 두는 것이 좋습니다. 이 realm이 뚫리면 모든 realm이 함께 넘어갑니다.

토큰 수명 조정

기본 액세스 토큰 수명은 짧게 잡혀 있는데, 2편 8장에서 본 것처럼 이 값이 곧 "로그아웃 후에도 API가 동작하는 시간"입니다. 서비스 특성에 맞춰 명시적으로 정하고, 정한 이유를 문서에 남겨 두세요.

04

Cognito 세우기

Cognito는 사용자 풀(User Pool)이 Keycloak의 realm에 해당합니다. 순서대로 만들어 보겠습니다.

# 1. 사용자 풀 생성
aws cognito-idp create-user-pool \
  --pool-name acme-users \
  --auto-verified-attributes email \
  --username-attributes email \
  --mfa-configuration OPTIONAL

# 2. 로그인 화면을 위한 도메인 — 이게 없으면 표준 OIDC 엔드포인트가 열리지 않습니다
aws cognito-idp create-user-pool-domain \
  --user-pool-id ap-northeast-2_EXAMPLE \
  --domain acme-login

# 3. 앱 클라이언트 — 프론트엔드용 공개 클라이언트
aws cognito-idp create-user-pool-client \
  --user-pool-id ap-northeast-2_EXAMPLE \
  --client-name web-console \
  --no-generate-secret \
  --allowed-o-auth-flows code \
  --allowed-o-auth-scopes openid profile email "acme-api/orders.read" \
  --allowed-o-auth-flows-user-pool-client \
  --callback-urls "https://console.acme.com/callback" \
  --supported-identity-providers COGNITO

커스텀 스코프는 리소스 서버로 정의합니다

Keycloak의 client scope에 해당하는 것이 Cognito에서는 리소스 서버입니다. 우리 API를 하나의 리소스 서버로 등록하고 그 아래에 스코프를 정의하면, 스코프 이름이 식별자/스코프명 형태가 됩니다.

aws cognito-idp create-resource-server \
  --user-pool-id ap-northeast-2_EXAMPLE \
  --identifier acme-api \
  --name "Acme 주문 API" \
  --scopes '[
    {"ScopeName":"orders.read",  "ScopeDescription":"주문 내역 조회"},
    {"ScopeName":"orders.write", "ScopeDescription":"주문 생성·취소"}
  ]'

# 결과적으로 클라이언트가 요청할 스코프 이름
scope=openid acme-api/orders.read acme-api/orders.write

토큰의 모양이 Keycloak과 다릅니다

여기가 2편의 검증 로직을 그대로 쓸 수 없는 지점입니다. Cognito의 액세스 토큰에는 aud 클레임이 없습니다. 대신 client_id가 들어 있고, token_use로 토큰 종류를 구분합니다.

id_token
{
  "iss": "https://cognito-idp.ap-northeast-2
         .amazonaws.com/ap-northeast-2_EXAMPLE",
  "sub": "a1b2c3d4-...",
  "aud": "1h57kf5cpparlcea1e57g9v25",
  "token_use": "id",
  "cognito:groups": ["ops", "billing"],
  "email": "alice@acme.com",
  "exp": 1758124800
}
access_token
{
  "iss": "https://cognito-idp.ap-northeast-2
         .amazonaws.com/ap-northeast-2_EXAMPLE",
  "sub": "a1b2c3d4-...",
  "client_id": "1h57kf5cpparlcea1e57g9v25",
  "token_use": "access",
  "scope": "openid acme-api/orders.read",
  "username": "a1b2c3d4-...",
  "exp": 1758124800
}
반드시 token_use를 확인하세요

aud가 없다는 것은 2편에서 배운 주요 방어선 하나가 빠진다는 뜻입니다. 그래서 Cognito를 쓸 때는 검증 절차에 두 가지를 반드시 넣어야 합니다.

  • 리소스 서버는 token_use가 "access"인지 확인합니다. 이게 없으면 누군가 id_token을 API 호출에 들이밀 수 있습니다.
  • 앱은 token_use가 "id"이고 aud가 자기 앱 클라이언트 ID인지 확인합니다.
  • 액세스 토큰의 대상을 좁히려면 client_id를 허용 목록과 대조합니다.

운영에서 걸리는 지점들

디스커버리 문서와 도메인이 따로 논다

혼동하기 쉬운 부분입니다. 디스커버리 문서와 JWKS는 우리가 만든 로그인 도메인이 아니라 리전 엔드포인트에 있습니다.

# 디스커버리와 JWKS — 리전 엔드포인트 (커스텀 도메인 아님)
https://cognito-idp.ap-northeast-2.amazonaws.com/ap-northeast-2_EXAMPLE/.well-known/openid-configuration
https://cognito-idp.ap-northeast-2.amazonaws.com/ap-northeast-2_EXAMPLE/.well-known/jwks.json

# 인가·토큰·로그아웃 — 우리가 만든 도메인
https://acme-login.auth.ap-northeast-2.amazoncognito.com/oauth2/authorize
https://acme-login.auth.ap-northeast-2.amazoncognito.com/oauth2/token
https://acme-login.auth.ap-northeast-2.amazoncognito.com/logout      # 디스커버리에 없음
https://acme-login.auth.ap-northeast-2.amazoncognito.com/oauth2/revoke  # 디스커버리에 없음

커스텀 도메인을 붙여도 디스커버리 경로는 바뀌지 않습니다. "우리 도메인에 .well-known을 붙였는데 404가 난다"는 문의가 여기서 나옵니다.

로그아웃을 수동으로 설정해야 한다

디스커버리에 end_session_endpoint가 없으므로, 자동 설정에 의존하는 라이브러리에서는 로그아웃 기능이 아예 잡히지 않습니다. 로그아웃 URL과 로그아웃 후 이동할 주소를 직접 지정해 주세요. 앱 클라이언트 설정의 로그아웃 URL 목록에 그 주소를 등록해 두는 것도 잊지 마세요.

인트로스펙션이 없다

Cognito에는 표준 introspection_endpoint가 없습니다. 즉 리소스 서버는 로컬 JWT 검증만 할 수 있습니다. 토큰을 즉시 무효화하고 그 효과가 곧바로 API에 반영되기를 기대할 수 없다는 뜻이고, 2편 8장에서 본 "액세스 토큰 수명을 짧게 잡는 것으로 타협" 외에 선택지가 없습니다. 이 제약이 요건과 충돌한다면 제품 선택 단계에서 걸러야 합니다.

클레임을 추가하려면 Lambda

Keycloak의 프로토콜 매퍼에 해당하는 것이 Cognito에서는 사전 토큰 생성 Lambda 트리거입니다. 조직 ID나 테넌트 코드 같은 커스텀 클레임을 넣고 싶다면 이 방식을 씁니다. 다만 모든 토큰 발급 경로에 Lambda 호출이 끼어들므로, 지연 시간과 장애 전파를 고려해야 합니다. Lambda가 실패하면 로그인이 실패합니다.

05

kubectl 연동

3편에서는 파드가 클라우드에 자기를 증명했습니다. 이번엔 반대 방향입니다. 사람이 클러스터에 자기를 증명하는 경우죠. 쿠버네티스에는 사용자 계정이라는 개념이 없습니다. 인증은 외부에 맡기고, 인가(RBAC)만 처리하도록 설계되어 있습니다. 그 외부가 우리가 방금 세운 인가 서버입니다.

이 방식으로 얻는 것이 큽니다. 인증서 기반 접근은 발급하면 회수가 어렵고 만료 관리가 번거로운데, OIDC로 붙이면 퇴사자 계정을 인가 서버에서 비활성화하는 것만으로 모든 클러스터 접근이 끊깁니다. 감사 로그에도 인증서 CN이 아니라 실제 이메일이 남습니다.

그룹 클레임을 RBAC에 연결하기

이 구성의 진짜 값어치는 여기 있습니다. 인가 서버의 그룹이 곧 클러스터 권한이 됩니다. 사람이 팀을 옮기면 인가 서버에서 그룹만 바꿔 주면 되고, 클러스터는 손댈 일이 없습니다.

# 인가 서버가 발급한 id_token의 클레임
{
  "email": "alice@acme.com",
  "groups": ["platform-team", "oncall"]      # Cognito라면 cognito:groups
}

# 이 그룹을 그대로 RBAC 주체로 씁니다
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: platform-team-admin
subjects:
  - kind: Group
    name: oidc:platform-team          # 접두사 설정을 붙인 경우
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: admin
  apiGroup: rbac.authorization.k8s.io
접두사를 반드시 설정하세요

사용자명과 그룹명에 oidc: 같은 접두사를 붙이는 이유는 충돌을 막기 위해서입니다. 접두사가 없으면 외부 사용자가 system:masters라는 그룹 클레임을 받도록 만들어 클러스터 관리자 권한을 얻을 수 있습니다. 인가 서버에서 임의 그룹 생성이 가능한 환경이라면 실제 위험입니다. EKS의 OIDC 연동 설정에도 같은 접두사 옵션이 있습니다.

설정 방식은 두 가지가 있습니다

전통적으로는 API 서버에 --oidc-issuer-url, --oidc-client-id, --oidc-username-claim, --oidc-groups-claim 같은 플래그를 주는 방식이었습니다. 최근 버전에는 파일 기반의 구조화된 인증 설정이 들어와, 발급자를 여러 개 등록하거나 CEL 표현식으로 클레임을 가공하는 것도 가능합니다. 관리형 클러스터는 콘솔이나 API로 같은 설정을 제공하므로, 쓰는 환경의 문서를 확인하세요. 원리는 동일합니다.

06

게이트웨이의 JWT 검증

서비스가 여러 개면 2편 4장의 검증 일곱 단계를 서비스마다 구현하게 됩니다. 언어도 프레임워크도 제각각이라 구현 품질이 고르지 않게 되고, 한 곳에서 aud 검증을 빠뜨리면 그게 구멍이 됩니다. 그래서 검증을 게이트웨이로 끌어올리는 구성을 많이 씁니다.

클라이언트 ──Bearer 토큰──▶  게이트웨이  ──검증된 요청 + 신원 헤더──▶  백엔드 서비스
                                 │
                                 └─ JWKS로 서명·iss·aud·exp·scope 검증

로컬 검증과 인트로스펙션

게이트웨이가 토큰을 확인하는 방법은 둘 중 하나입니다. 2편에서 언급만 하고 넘어갔던 트레이드오프를 여기서 결정해야 합니다.

로컬 JWT 검증인트로스펙션
방법JWKS 공개 키로 서명을 직접 확인매 요청마다 인가 서버에 문의
지연사실상 없음 (수 마이크로초)왕복 한 번 추가
인가 서버 부하JWKS 조회만 (캐싱)요청량에 비례
즉시 폐기 반영안 됨 — 만료까지 유효됨
인가 서버 장애 시기존 토큰으로 계속 동작전체 API 중단
불투명 토큰 지원불가가능
Cognito이 방식만 가능지원하지 않음

대부분은 로컬 검증 + 짧은 토큰 수명으로 갑니다. 인가 서버가 잠깐 죽어도 서비스가 멈추지 않는다는 점이 결정적입니다. 즉시 폐기가 정말 필요한 일부 고위험 API에만 인트로스펙션을 걸어 섞어 쓰는 방식도 씁니다.

게이트웨이별 구성

AWS API Gateway (HTTP API)

발급자 URL과 대상(audience)을 지정하면 검증을 대신해 줍니다. 라우트별로 필요한 스코프도 걸 수 있습니다.

Authorizer:
  Type: JWT
  IdentitySource: $request.header.Authorization
  JwtConfiguration:
    Issuer: https://cognito-idp.ap-northeast-2.amazonaws.com/ap-northeast-2_EXAMPLE
    Audience:
      - 1h57kf5cpparlcea1e57g9v25

Routes:
  GET /orders:
    AuthorizationScopes: ["acme-api/orders.read"]
  POST /orders:
    AuthorizationScopes: ["acme-api/orders.write"]
Cognito 액세스 토큰에는 aud가 없다는 점을 기억하세요

4장에서 본 그 문제가 여기서 바로 걸립니다. 게이트웨이마다 aud가 없을 때 client_id를 대신 보는지 여부가 다릅니다. 설정을 마쳤다고 끝내지 말고, 반드시 실제 토큰으로 호출해 통과·거부가 의도대로 되는지 확인하세요. 특히 "다른 앱 클라이언트로 받은 토큰이 거부되는지"를 꼭 테스트해야 합니다. 이게 통과해 버리면 2편 0장의 토큰 대체 공격이 열립니다.

Application Load Balancer

ALB는 검증을 넘어 로그인 자체를 대신할 수 있습니다. 인증되지 않은 요청을 인가 서버로 리다이렉트하고, 인증이 끝나면 사용자 클레임을 헤더에 실어 백엔드로 넘겨줍니다. 내부 관리 도구처럼 코드를 건드리기 곤란한 곳에 특히 유용합니다. 다만 백엔드가 그 헤더를 무조건 신뢰하게 되므로, ALB를 거치지 않고 백엔드에 직접 접근할 수 있는 경로를 반드시 차단해야 합니다. 보안 그룹으로 ALB에서 오는 트래픽만 허용하세요.

서비스 메시 (Envoy, Istio)

메시를 쓴다면 검증 정책을 리소스로 선언합니다. 어느 발급자를 신뢰할지와 어떤 스코프를 요구할지를 나누어 적을 수 있어, 서비스별 인가 규칙을 코드 밖에서 관리하기 좋습니다. 사이드카가 검증하므로 애플리케이션은 헤더만 읽으면 됩니다.

게이트웨이에서 검증했다고 백엔드가 방심하면 안 됩니다

게이트웨이 뒤라고 해서 백엔드가 아무 검사도 하지 않으면, 내부망에서 게이트웨이를 우회하는 요청 하나로 모든 통제가 무력해집니다. 최소한 게이트웨이를 통해서만 접근 가능하도록 네트워크를 닫거나, 백엔드도 토큰을 한 번 더 확인하는 이중 구성을 권합니다. 어느 쪽을 택했는지는 반드시 문서로 남기세요. 인수인계에서 가장 자주 사라지는 정보입니다.

07

키 회전

2편 5장에서 "새 키를 먼저 올리고 시간을 준 뒤 전환한다"고 설명했습니다. 이제 그 절차를 실행하는 입장이 됐습니다. 순서를 잘못 잡으면 전 서비스의 인증이 동시에 실패하므로, 가장 긴장되는 운영 작업 중 하나입니다.

아래에서 안전한 순서와 성급한 교체를 비교해 보세요. 각 시점에 JWKS에 무엇이 있고, 어떤 클라이언트가 실패하는지 보여줍니다.

키 회전 진행 상황

제품별로 어떻게 하나

Keycloak

realm 설정의 키 관리에서 새 키 제공자를 추가하면 JWKS에 키가 하나 더 노출되고, 우선순위를 올리면 그때부터 새 키로 서명합니다. 옛 키는 우선순위를 낮춘 채 활성 상태로 남겨 두었다가, 기존 토큰이 모두 만료된 뒤 제거합니다. 이 두 단계 사이의 간격이 "클라이언트 JWKS 캐시 수명 + 토큰 수명"보다 길어야 합니다.

Cognito

서명 키는 AWS가 관리하므로 우리가 회전시킬 일이 없습니다. 대신 우리 쪽 클라이언트가 키 변경에 대응할 수 있는 상태인지는 우리 책임입니다. JWKS를 한 번 받아 설정 파일에 하드코딩해 둔 구현이 있다면, 언젠가 AWS가 키를 바꾸는 날 조용히 전부 실패합니다. 이건 실제로 종종 발생하는 사고 유형입니다.

가장 흔한 사고: JWKS 하드코딩

"매번 조회하면 느리니까" 또는 "폐쇄망이라"는 이유로 공개 키를 설정에 박아 두는 경우가 있습니다. 동작은 잘 되다가, 발급자가 키를 회전시키는 순간 전면 장애가 납니다. 게다가 원인을 찾기 어렵습니다. 어제까지 멀쩡했고 우리 코드는 바뀐 게 없으니까요. 반드시 kid를 보고 동적으로 조회하는 구조로 만들고, 조회 실패에 대비한 캐시와 재시도를 넣으세요.

회전 전 점검 목록

  • 모든 클라이언트가 kid로 키를 찾는가, 아니면 어딘가에 키를 고정해 둔 곳이 있는가
  • 클라이언트들의 JWKS 캐시 수명이 얼마인가. 가장 긴 것을 기준으로 대기 시간을 잡는다
  • 현재 발급 중인 토큰의 최대 수명은 얼마인가. 옛 키 제거는 그 시간 이후에
  • 회전 도중 인증 실패율을 볼 수 있는 대시보드가 있는가
  • 실패가 급증했을 때 되돌릴 수 있는가. 옛 키를 다시 우선순위 1위로 올리는 절차를 미리 준비
  • 연동된 외부 시스템 중 수동 설정이 필요한 곳이 있는가
08

관측과 장애 대응

인가 서버는 조용히 잘 돌다가 한 번에 크게 터지는 종류의 시스템입니다. 무엇을 보고 있어야 하는지부터 정리하겠습니다.

봐야 할 지표

인증 성공률과 실패 사유

단순 성공률만으로는 부족합니다. 실패를 사유별로 나눠 보세요. 비밀번호 오류가 느는 것과 invalid_client가 느는 것은 원인이 완전히 다릅니다. 후자는 설정 문제거나 공격입니다.

토큰 발급량과 갱신 비율

갑자기 발급량이 몇 배로 뛴다면, 어딘가에서 토큰을 캐시하지 않고 매 요청마다 새로 받는 코드가 배포됐을 가능성이 높습니다. 3편에서 본 그 실수입니다.

JWKS 엔드포인트 호출량

평소보다 급증하면 키 회전 중이거나, 캐싱이 깨졌거나, 모르는 kid가 대량으로 들어오고 있다는 신호입니다. 마지막 경우는 공격일 수 있습니다.

응답 지연과 DB 상태

Keycloak은 세션과 사용자 정보를 DB에 두므로 DB가 곧 병목입니다. 커넥션 풀 고갈은 로그인 전면 실패로 이어집니다.

로그에 토큰을 남기지 마세요

디버깅하다 보면 토큰 전체를 로그에 찍는 코드를 넣기 쉽고, 그게 그대로 배포됩니다. 로그 수집 시스템에 접근 가능한 사람이 모두 그 토큰을 쓸 수 있게 됩니다. 필요하면 kid, sub의 앞 몇 자리, exp 정도만 남기세요. 1편 9장 체크리스트에 있던 항목입니다.

증상으로 원인 찾기

구축 중이나 운영 중에 마주치는 대표적인 증상들입니다. 눌러서 확인해 보세요.

어떤 증상인가요

09

옮겨가기

새로 만드는 서비스라면 처음부터 인가 서버를 붙이면 됩니다. 문제는 이미 자체 인증으로 운영 중인 시스템들이죠. 사용자가 있고, 세션이 있고, 비밀번호 해시가 있습니다. 한 번에 갈아엎는 방식은 거의 실패합니다.

1

현황을 목록으로 만든다

어떤 서비스가 어떻게 인증하는지 전부 적습니다. 대개 이 단계에서 아무도 몰랐던 인증 경로가 두세 개 나옵니다. 오래된 관리 도구, 배치 전용 계정, 협력사 연동 같은 것들입니다.

  • 서비스별 인증 방식과 사용자 수
  • 사용 중인 비밀번호 해시 알고리즘
  • 세션 저장 방식과 수명
  • 외부 연동 계정과 API 키
2

인가 서버를 세우고 신규부터 적용한다

기존 서비스를 건드리기 전에, 새로 만드는 서비스나 내부 도구 하나를 먼저 붙여 봅니다. 여기서 운영 절차와 모니터링을 다듬습니다. 실패해도 영향이 작은 대상을 고르는 게 핵심입니다.

3

사용자를 옮긴다

두 가지 방법이 있고, 해시 알고리즘이 갈림길입니다.

  • 일괄 이관 — 인가 서버가 기존 해시 알고리즘을 그대로 지원하면 해시째로 옮길 수 있습니다. 사용자는 아무것도 느끼지 못합니다. 가장 깔끔하지만 조건이 맞아야 합니다.
  • 점진적 이관 — 해시를 옮길 수 없을 때 씁니다. 인가 서버에 사용자가 없으면 옛 시스템에 물어보고, 로그인이 성공하면 그 시점의 비밀번호로 계정을 만듭니다. Cognito는 사용자 마이그레이션 Lambda 트리거로, Keycloak은 사용자 저장소 연동으로 구현합니다.
4

병행 운영 기간을 둔다

두 인증 경로가 동시에 살아 있는 기간입니다. 불편하지만 롤백 여지를 남기는 유일한 방법입니다. 이 기간에 옛 경로의 사용량을 계측해서, 언제 닫아도 되는지 데이터로 판단하세요. "이제 아무도 안 쓰겠지"라는 추측으로 닫으면 반드시 누군가 걸립니다.

5

옛 경로를 닫고 정리한다

점진적 이관이었다면, 아직 안 옮겨진 사용자가 남아 있을 수 있습니다. 비밀번호 재설정으로 유도하고 충분히 공지한 뒤 닫습니다. 그리고 옛 비밀번호 해시 테이블을 삭제하세요. 쓰지 않는 자격 증명 데이터를 남겨 두는 것은 그 자체로 위험입니다.

기술보다 커뮤니케이션이 어렵습니다

로그인 화면이 바뀌는 것은 모든 사용자가 체감하는 변화입니다. 도메인이 달라지고, 화면 모양이 달라지고, 기존 즐겨찾기가 안 먹습니다. 사전 공지와 전환 안내, 그리고 전환 당일의 문의 대응 준비가 기술 작업만큼 중요합니다. 전환은 금요일 저녁에 하지 마세요.

    11

    이해도 점검

    마지막 열 문제입니다. 1편부터 4편까지의 내용이 섞여 있습니다.

    4편 정리

    인가 서버를 세우고, 붙이고, 운영하고, 옮겨 오는 전 과정을 봤습니다.

    • 01인가 서버를 두는 것은 인증의 복잡도를 한곳에 모으는 결정이다. 대신 단일 장애점이 생기므로 운영 설계가 따라온다.
    • 02Keycloak은 표준을 넓게 구현하고 커스터마이징 여지가 크다. Cognito는 운영 부담이 적은 대신 제공 범위 안에서만 움직인다.
    • 03Keycloak은 액세스 토큰의 aud가 기본적으로 account다. audience 매퍼를 붙이지 않으면 검증이 통과하지 않는다.
    • 04Cognito 액세스 토큰에는 aud가 없다. client_id와 token_use를 반드시 확인해야 한다.
    • 05kubectl을 OIDC로 붙이면 인가 서버의 그룹이 곧 RBAC 주체가 된다. 접두사 설정을 빠뜨리면 권한 상승 경로가 열린다.
    • 06게이트웨이 검증은 로컬 JWT 검증이 기본이다. 인트로스펙션은 즉시 폐기가 필요한 곳에만 섞어 쓴다.
    • 07키 회전은 추가 → 대기 → 전환 → 만료 대기 → 제거 순서다. JWKS를 하드코딩하면 그날 전면 장애가 난다.
    • 08전환은 한 번에 갈아엎지 않는다. 병행 운영 기간과 롤백 경로를 반드시 남긴다.

    시리즈를 마치며

    네 편에 걸쳐 온 길을 되짚으면 이렇습니다. 1편에서 비밀번호를 넘기지 않고 권한만 빌려주는 방법을 배웠고, 2편에서 그 토큰만으로는 신원을 알 수 없다는 사실과 OpenID Connect가 그 빈틈을 어떻게 메우는지 봤습니다. 3편에서는 사람이 없는 곳 — 파드와 CI 워크플로 — 에서 같은 원리가 어떻게 쓰이는지, 그리고 4편에서 그 모든 것의 중심인 인가 서버를 직접 세웠습니다.

    네 편을 관통하는 감각은 하나입니다. 훔쳐도 쓸모가 적은 것만 위험한 경로로 보내고, 진짜 값어치가 있는 것은 안전한 경로로만 주고받는다. 인가 코드가 그랬고, PKCE가 그랬고, 백채널 토큰 교환이 그랬고, 워크로드 페더레이션이 그랬습니다. 새로운 명세를 마주쳤을 때도 이 질문을 먼저 던져 보세요. "이 값이 어느 경로로 흐르고, 훔친 사람이 그것만으로 무엇을 할 수 있는가." 대부분의 설계 의도가 거기서 읽힙니다.

    이제 남은 것은 직접 해 보는 일입니다. 로컬에 Keycloak을 하나 띄우고, 작은 앱을 붙여 인가 코드 흐름을 끝까지 돌려 보세요. 토큰을 디코딩해 클레임을 하나씩 확인하고, 일부러 state 검증을 빼 보고, aud를 틀려 보세요. 무엇이 어떻게 실패하는지 직접 본 경험이, 나중에 남의 코드에서 빠진 검증을 알아보는 눈이 됩니다.
