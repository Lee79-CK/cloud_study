TraceQL 완전 정복트레이스를 조건으로 찾고, 메트릭으로 세다

아래는 브라우저 안에서 도는 TraceQL 연습장입니다. 가상의 쇼핑몰이 1시간 동안 만든 트레이스 약 700개가 들어 있고, 10:35~10:45에는 결제 대행사(PG) 타임아웃 장애가 숨어 있습니다. 예제를 누르거나 직접 쿼리를 써서 실행해 보세요. 본문의 실행 버튼도 모두 이 연습장으로 연결됩니다.

연습장은 학습용으로 TraceQL의 주요 문법을 직접 구현한 것입니다(스팬셋 필터, 논리·구조 연산자, 집계, by, select, 메트릭 함수, topk, 비교 연산자). 산술 연산, 이벤트·링크 범위, histogram_over_time, compare 등은 지원하지 않으며, 실제 Tempo와 결과 형식이 다를 수 있습니다. Ctrl+Enter로도 실행됩니다.

1

TraceQL의 기본 모양

TraceQL 쿼리는 트레이스 하나씩 평가됩니다. 중괄호 { }는 트레이스 안에서 조건에 맞는 스팬들을 고르고, 이렇게 고른 스팬 묶음을 스팬셋(spanset)이라고 부릅니다. 스팬셋은 파이프(|)를 따라 다음 단계로 흘러가며 걸러지고, 끝까지 살아남은 스팬셋이 있는 트레이스가 결과가 됩니다. 아래 쿼리의 각 부분을 눌러 보세요.

{ resource.service.name = "payment-service" && duration > 300ms } | count() > 1
{ }

조건 없는 { }는 모든 스팬을 고릅니다. 처음엔 넓게 시작해서 조건을 하나씩 더해 좁혀 가는 것이 공식 문서가 권하는 쿼리 작성 습관입니다.

SQL이나 PromQL과 다른 점

SQL은 행(row)을, PromQL은 시계열을 다룹니다. TraceQL이 다루는 기본 단위는 트레이스 안의 스팬 묶음입니다. 그래서 "같은 스팬이 두 조건을 모두 만족"하는지, "한 트레이스 안의 서로 다른 스팬이 각각 만족"하는지를 구분해서 쓸 수 있습니다(4장). 이것이 트레이스 전용 언어가 필요한 이유입니다.

2

필드: 범위와 고유 필드

TraceQL 필드는 범위(scope)와 이름으로 이루어집니다. 사용자가 붙인 속성은 점(.)으로, 스팬이 원래 가진 고유 필드(intrinsic)는 콜론(:)으로 잇습니다.

범위쓰는 법예
span 속성span.속성이름span.http.route, span.db.system.name
resource 속성resource.속성이름resource.service.name, resource.deployment.environment
span 고유 필드span:이름 (자주 쓰는 것은 범위 생략 가능)span:duration(=duration), span:status(=status), span:name(=name), span:kind(=kind)
trace 고유 필드trace:이름trace:duration, trace:rootService, trace:rootName
그 밖의 범위event., link., instrumentation.event.exception.message, instrumentation:name
범위 없음.속성이름.http.route (span과 resource를 모두 찾아봄, 느림)
{ trace:rootService = "api-gateway" && trace:duration > 700ms }
trace 고유 필드는 빠르다

trace:duration, trace:rootName, trace:rootService는 트레이스의 모든 스팬에 같은 값이고, 4편에서 본 Parquet 블록에서 훨씬 작은 열에 저장됩니다. "느린 트레이스"를 찾을 때 스팬별 duration보다 trace:duration을 먼저 쓰면 읽는 데이터가 크게 줄어듭니다. 자식 수를 나타내는 span:childCount는 vParquet5 블록에서만 쓸 수 있습니다(3.0 기본값은 vParquet4).

3

값과 비교 연산자

종류쓰는 법예
문자열큰따옴표name = "Charge"
정수·실수그대로span.http.response.status_code >= 500
시간단위 필수: ns, us, ms, s, m, hduration > 300ms, trace:duration > 2s
상태error, ok, unset (따옴표 없음)status = error
종류server, client, producer, consumer, internalkind = client
없음nilspan.db.system.name != nil (속성이 있는 스팬)

비교 연산자는 =, !=, >, >=, <, <=, 정규식 일치 =~, 정규식 불일치 !~입니다. 한 중괄호 안에서는 &&(그리고), ||(또는), !(부정), 괄호로 조건을 묶습니다.

{ span.db.system.name =~ "postgresql|redis" && duration > 30ms }
정규식은 값 전체와 맞춰 봅니다

Tempo는 모든 정규식 비교를 앞뒤로 고정(anchored)해서 평가합니다. name =~ "Charge"는 ^Charge$와 같아서 "ChargeRefund"와는 일치하지 않습니다. 부분 일치를 원하면 공식 예제처럼 =~ ".*charge.*"로 앞뒤에 .*를 붙이세요. 정규식 문법은 Go 정규식입니다.

{ name =~ "POST.*" }vs{ name =~ "POST" }
4

스팬셋 조합하기

가장 중요한 구분: 중괄호 안의 &&와 밖의 &&

두 쿼리는 비슷해 보이지만 뜻이 완전히 다릅니다. 실행해서 결과 트레이스 수와 강조된 스팬을 비교해 보세요.

같은 스팬{ resource.service.name = "order-service" && kind = client }
다른 스팬도 됨{ resource.service.name = "order-service" } && { kind = client }

첫 번째는 "order-service이면서 client인 그 스팬"(주문 서비스가 DB를 부른 스팬)을 찾습니다. 두 번째는 "order-service 스팬이 있고, 어딘가에 client 스팬도 있는 트레이스"를 찾아 두 스팬셋을 합쳐 돌려줍니다. 두 스팬셋 사이의 ||는 합집합입니다.

구조 연산자: 부모·자식·형제 관계로 찾기

구조 연산자는 두 스팬셋 사이의 트리 관계를 조건으로 씁니다. 결과는 항상 오른쪽 스팬셋에서 나옵니다. 아래에서 왼쪽(A)·오른쪽(B) 조건과 연산자를 바꿔 가며 장애 트레이스 하나에 적용해 보세요.

A에 해당하는 스팬결과 스팬
연산자뜻 (결과는 B에서)
A > B부모가 A인 B (직계 자식)
A >> B조상 중에 A가 있는 B (자손)
A < B자식 중에 A가 있는 B (직계 부모)
A << B자손 중에 A가 있는 B (조상)
A ~ B형제 중에 A가 있는 B
&>, &>> 등합집합 구조 연산자: B뿐 아니라 관계를 이룬 A 스팬도 함께 돌려줌
!>, !>>, !<, !<<, !~부정 구조 연산자(실험적): 그 관계가 없는 B
{ } !< { resource.service.name = "inventory-service" }

위 쿼리는 "자식이 없는 inventory-service 스팬", 즉 그 서비스의 말단(leaf) 스팬을 찾는 공식 문서의 관용구입니다. 말단 스팬은 보통 DB나 외부 API 호출이라 병목 조사의 출발점이 됩니다.

성능 비용이 있습니다

중괄호 하나에 &&만 쓴 쿼리는 Tempo가 조건을 Parquet 읽기 단계까지 내려보내 필요한 행만 읽을 수 있어 가장 빠릅니다. ||나 구조 연산자가 들어가면 더 많은 데이터를 읽고 트리를 조립해야 하므로 느려집니다. 같은 스팬에 대한 조건이라면 하나의 중괄호로 합치세요(8장).

5

파이프라인: 집계·그룹·선택

파이프(|) 뒤에서는 스팬셋 단위로 계산해서 거릅니다.

단계하는 일
count() > N스팬셋의 스팬 개수로 거르기
avg(필드), min, max, sum스팬셋 안 숫자 필드의 평균·최소·최대·합으로 거르기
by(필드)스팬셋을 필드 값별로 나눔. 뒤의 집계는 그룹마다 따로 적용
select(필드, ...)결과에 추가로 보여 줄 필드. 조건을 다 통과한 스팬에서만 가져오므로 가벼움
{ kind = client } | count() > 3

평소 주문 트레이스의 client 스팬은 3개(DB 조회, 재고 DB, PG 호출)입니다. 4개 이상이면 재시도가 있었던 트레이스입니다. 이렇게 "평소와 다른 모양"을 개수로 잡아내는 것이 count()의 대표적인 쓰임입니다.

{ status = error } | by(resource.service.name) | count() > 1
{ resource.service.name = "payment-service" } | avg(duration) > 300ms
{ status = error } | select(span.error.type, span.server.address)
6

TraceQL metrics

스팬셋 뒤에 메트릭 함수를 붙이면 쿼리가 시계열을 돌려줍니다. 미리 metrics-generator로 메트릭을 만들어 두지 않아도, 저장된 트레이스에서 그때그때 계산합니다. Tempo 3.0에서 GA(정식 기능)가 되었습니다.

함수계산
rate()초당 일치 스팬 수
count_over_time()구간(step)마다 일치 스팬 수
sum_over_time(f), avg_over_time(f), min_over_time(f), max_over_time(f)구간마다 숫자 필드의 합·평균·최소·최대
quantile_over_time(f, .99, .5)구간마다 분위수. 여러 개를 한 번에 지정 가능
histogram_over_time(f)구간마다 분포 (히트맵용)
compare({조건})조건에 맞는 스팬과 나머지의 속성 차이를 비교. Grafana Traces Drilldown의 비교 탭이 사용
by (필드)필드 값별로 시계열을 나눔
| topk(N), | bottomk(N)상위·하위 N개 시계열만
> 10 같은 비교 (3.0 신규)기준을 넘는 데이터 포인트만 남김. 경보 쿼리의 기초
{ status = error } | rate() by (resource.service.name)
{ name = "Charge" } | quantile_over_time(duration, .95, .5)
{ kind = server } | quantile_over_time(duration, .99) by (resource.service.name) | topk(3)
{ status = error } | rate() by (resource.service.name) > 0.05
metrics-generator와 무엇이 다른가

metrics-generator(6편)는 스팬이 들어올 때 미리 메트릭을 만들어 Prometheus에 저장합니다. 조회가 가볍고 장기 대시보드와 경보에 적합하지만, 미리 정한 차원(레이블)만 볼 수 있습니다. TraceQL metrics는 저장된 트레이스에서 그때그때 계산하므로 어떤 속성으로든 나눠 볼 수 있지만, 긴 기간일수록 읽는 양이 많습니다. 3편 Jaeger SPM의 두 가지 방식과 같은 관계입니다. 3.0부터 메트릭 쿼리 기본 최대 기간은 1일입니다.

경보는 아직 실험 단계

TraceQL metrics 자체는 GA지만, TraceQL metrics로 경보를 거는 것은 실험적 기능입니다. 운영 경보는 metrics-generator가 만든 메트릭 기반으로 두고, TraceQL metrics 경보는 보조로 시험해 보세요. 큰 데이터에는 with(sample=true) 힌트로 샘플링해 근삿값을 빠르게 얻을 수 있습니다.

7

3.0에서 바뀐 규칙

3.0은 같은 속성에 대한 여러 조건을 하나의 배열 인식 검사로 합치는 최적화를 넣었고, 그 과정에서 배열 속성에 대한 부정 연산의 의미가 바뀌었습니다. 배열 속성은 HTTP 헤더처럼 값이 여러 개인 속성입니다.

연산2.x3.0
=, =~원소 중 하나라도 일치같음 (하나라도 일치)
!=일치하지 않는 원소가 하나라도 있으면NOT IN: 일치하는 원소가 하나도 없어야
!~정규식에 안 맞는 원소가 하나라도 있으면MATCH NONE: 정규식에 맞는 원소가 하나도 없어야

예를 들어 span.tags = ["a","b"]인 스팬에 { span.tags != "a" }를 쓰면, 2.x에서는 "b"가 "a"가 아니므로 일치했지만 3.0에서는 "a"가 들어 있으므로 일치하지 않습니다. 이전 동작이 필요하면 with(skip_optimization=true) 힌트로 최적화를 끌 수 있습니다. 정규식 피연산자는 문자열 또는 문자열 배열이어야 하는 등 검증도 엄격해졌습니다. 대시보드와 경보에 배열 속성의 부정 조건이 있다면 업그레이드 전에 결과를 비교해 보세요.

8

빠른 쿼리 쓰는 법

4편에서 본 원리를 기억하세요. Tempo는 쿼리가 언급한 열만 읽고, 시간 범위가 넓을수록 읽을 블록이 많아집니다. 공식 튜닝 가이드를 MSP 현장 기준으로 정리했습니다.

원칙느린 쿼리빠른 쿼리
같은 스팬 조건은 한 중괄호에 &&로{ span.http.route = "/orders" } && { status = error }{ span.http.route = "/orders" && status = error }
범위를 붙인다{ .http.route = "/orders" }{ span.http.route = "/orders" }
필요한 속성만{ span.http.response.status_code = 500 && status = error }{ span.http.response.status_code = 500 } (의미가 같다면)
trace·resource 필드로 먼저 좁힌다{ duration > 5s }{ trace:duration > 5s && resource.service.name = "api" }
자주 찾는 속성은 전용 열로4편 6장의 parquet_dedicated_columns 설정. tempo-cli analyse blocks로 후보 확인
시간 범위를 좁힌다최근 15분 이내는 live-store만 조회하므로 특히 빠름 (4편 5장)
큰 메트릭 쿼리는 샘플링{ resource.service.name = "api" } | quantile_over_time(duration, .9) with(sample=true)
가장 최근 결과가 필요할 때

Tempo 검색은 속도를 위해 조건에 맞는 트레이스를 먼저 찾은 순서대로 결과 개수 한도까지 돌려주므로, 가장 최신 트레이스가 아닐 수 있습니다. 장애 대응 중 최신 순이 꼭 필요하면 { status = error } with (most_recent=true)처럼 실험적 힌트를 붙입니다. 더 깊이 뒤지므로 느리고, 같은 쿼리도 매번 결과가 조금씩 다를 수 있습니다.

9

MSP 장애 조사 레시피

고객사 문의 유형별로 바로 쓸 수 있는 쿼리입니다. 속성 이름은 OpenTelemetry 시맨틱 규약을 따랐으니, 고객사 계측에 맞게 바꿔 쓰세요. 연습장 데이터로 실행해 볼 수 있습니다.

문의쿼리
조사 순서의 정석

메트릭 쿼리로 언제·어디서를 먼저 찾고(예: 서비스별 에러율 그래프에서 10:35 급증 확인), 검색 쿼리로 그 시간대의 대표 트레이스를 고른 뒤, 워터폴에서 원인 스팬을 확인합니다. 연습장에서 레시피 1 → 2 → 3 순서로 실행하면 이 흐름을 그대로 따라가 볼 수 있습니다. 7편에서는 여기에 로그·프로파일 연결을 더합니다.

어디서 실행하나

정리와 다음 편

  1. TraceQL은 트레이스 하나씩 평가하며, { }로 스팬셋을 고르고 | 파이프라인으로 거릅니다.
  2. 속성은 span.·resource.처럼 점으로, 고유 필드는 span:·trace:처럼 콜론으로 씁니다. 범위를 붙이고 trace 필드로 먼저 좁히면 빠릅니다.
  3. 중괄호 안의 &&는 같은 스팬, 밖의 &&는 트레이스 안의 서로 다른 스팬입니다. 구조 연산자 결과는 항상 오른쪽에서 나옵니다.
  4. 메트릭 함수(rate, quantile_over_time 등)와 by, topk, 비교 연산자로 트레이스에서 바로 시계열을 만듭니다. 3.0에서 GA이며, 경보는 아직 실험적입니다.
  5. 3.0부터 배열에 대한 !=·!~는 "하나도 없음"을 뜻하고, 정규식은 값 전체와 맞춰 봅니다.
