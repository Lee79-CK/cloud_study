14편Octavia · Designate · Barbican

RHOSO의 lb-mgmt 네트워크 구조

  1. 컨트롤러(Worker·Health Manager·Housekeeping Pod)와 amphora VM이 서로 통신해야 합니다. 이 망이 lb-mgmt-net입니다.
  2. RHOSO는 전용 octavia 네트워크(외부 프로바이더 망 역할)를 두고, Pod들은 브리지형 NAD octbr로 이 망에 붙습니다.
  3. Neutron에는 컨트롤 플레인 전용 octavia-provider-net과 amphora가 사는 테넌트 망 lb-mgmt-net이 생기고, 전용 링크 라우터가 둘을 잇습니다. SNAT 없이 라우팅되므로 컨트롤러가 모든 amphora에 직접 닿습니다.
  4. OVN 컨트롤러에 nicMappings: octavia: octbr로 이 프로바이더 망을 매핑합니다(11편).
  5. 컨트롤러와 amphora 사이 통신은 두 개의 CA(인증 기관)로 서로를 인증하는 TLS로 보호됩니다. 같은 망으로 amphora 로그를 rsyslog Pod에 보내는 로그 오프로딩도 지원합니다.
# OpenStackControlPlane 일부 (RHOSO 문서 구조를 단순화)
octavia:
  enabled: true
  template:
    octaviaHousekeeping:  { networkAttachments: [octavia] }
    octaviaHealthManager: { networkAttachments: [octavia] }
    octaviaWorker:        { networkAttachments: [octavia] }
ovn:
  template:
    ovnController:
      nicMappings:
        octavia: octbr

# 확인
openstack network list -c Name | grep -E 'octavia-provider-net|lb-mgmt-net'
openstack loadbalancer provider list                 # amphora, ovn

amphora도 VM이다

amphora는 Octavia 서비스 프로젝트 소유의 VM이라 고객 프로젝트에는 보이지 않지만, 컴퓨트 자원과 쿼터를 씁니다. 고객이 로드밸런서 100개를 만들면(ACTIVE_STANDBY면 200대) VM이 그만큼 생깁니다. 용량 계획(9편)에 반드시 포함하고, 필요하면 Octavia 플레이버로 amphora 크기를 정합니다.

섹션 7

로드밸런서 실습과 분배 알고리즘

# 웹 서버 3대 앞에 HTTP 로드밸런서 (amphora)
openstack loadbalancer create --name web-lb --vip-subnet-id app-subnet --provider amphora
openstack loadbalancer show web-lb -c provisioning_status      # PENDING_CREATE → ACTIVE (기다림)
openstack loadbalancer listener create --name web-http --protocol HTTP --protocol-port 80 web-lb
openstack loadbalancer pool create --name web-pool --lb-algorithm ROUND_ROBIN \
   --listener web-http --protocol HTTP
for ip in 10.0.0.15 10.0.0.16 10.0.0.17; do
  openstack loadbalancer member create --subnet-id app-subnet --address $ip --protocol-port 80 web-pool
done
openstack loadbalancer healthmonitor create --delay 5 --timeout 3 --max-retries 3 \
   --type HTTP --url-path /health web-pool

# 외부 공개: VIP 포트에 플로팅 IP
VIP_PORT=$(openstack loadbalancer show web-lb -f value -c vip_port_id)
openstack floating ip set --port $VIP_PORT 203.0.113.30

# OVN 프로바이더로 단순 TCP (알고리즘은 SOURCE_IP_PORT)
openstack loadbalancer create --name tcp-lb --vip-subnet-id app-subnet --provider ovn
openstack loadbalancer listener create --name tcp-5432 --protocol TCP --protocol-port 5432 tcp-lb
openstack loadbalancer pool create --name pg-pool --lb-algorithm SOURCE_IP_PORT --listener tcp-5432 --protocol TCP

멤버 쪽 보안 그룹을 잊지 마세요

amphora는 멤버 VM에 자기 IP로 접속하고 상태 검사도 보냅니다. 멤버의 보안 그룹이 로드밸런서 쪽(VIP 서브넷 또는 amphora 포트)에서 오는 80번·상태 검사 포트를 허용해야 합니다. 그렇지 않으면 멤버가 전부 ERROR(상태 검사 실패)로 표시되고 503이 납니다.

섹션 8

상태 읽기와 운영

Octavia 객체에는 상태가 두 개 있습니다.

상태값뜻
provisioning_statusPENDING_CREATE · PENDING_UPDATE · PENDING_DELETE · ACTIVE · ERROR설정 작업이 끝났나. PENDING 중에는 다른 변경이 거부됨(“immutable” 오류)
operating_statusONLINE · DEGRADED · OFFLINE · ERROR · NO_MONITOR실제로 동작하나. DEGRADED = 일부 멤버 실패, NO_MONITOR = 상태 검사 없음
 
openstack loadbalancer status show web-lb          # LB → 리스너 → 풀 → 멤버 상태를 나무 구조로
openstack loadbalancer member list web-pool -c address -c operating_status
openstack loadbalancer stats show web-lb           # 연결 수·바이트
openstack loadbalancer amphora list --loadbalancer <LB ID>    # 관리자: amphora VM·역할(MASTER/BACKUP)
openstack loadbalancer failover web-lb             # 관리자: amphora 새로 만들어 교체
openstack loadbalancer quota show <프로젝트>

운영 팁

  • amphora 이미지 갱신: 보안 패치된 새 amphora 이미지가 나오면, 기존 로드밸런서는 failover로 새 이미지의 amphora로 교체합니다(ACTIVE_STANDBY면 무중단에 가깝게).
  • ERROR 상태 LB: 대부분 amphora 생성 실패(Nova 자원 부족, lb-mgmt 망 문제, 이미지 없음)입니다. Worker 로그와 amphora list를 먼저 봅니다.
  • OVN 프로바이더 LB는 amphora가 없으므로 failover·amphora 명령이 해당되지 않고, OVN NB의 Load_Balancer 테이블(12편)에서 확인합니다.

섹션 9

Designate 개념

Designate(DNS 서비스)는 DNS 권한 서버(authoritative, 특정 도메인의 정답을 가진 서버)의 내용을 OpenStack API로 관리하게 해 줍니다. 사용자는 자기 프로젝트의 영역(zone)을 만들고 레코드를 넣으며, Designate가 실제 DNS 서버(BIND 9)에 반영합니다.

개념뜻예
영역 (zone)하나의 도메인과 그 아래 이름들. 끝에 점을 붙인 완전한 이름으로 씀shop.example.com.
레코드셋같은 이름·종류의 레코드 묶음www.shop.example.com. A 203.0.113.30
레코드 종류A(IPv4), AAAA(IPv6), CNAME(별칭), MX(메일), TXT(텍스트·인증), PTR(역방향: IP→이름), NS(위임), SOA(영역 정보)—
TTL다른 DNS 서버가 답을 캐시해도 되는 시간(초)300
풀 (pool)영역을 실제로 서비스할 DNS 서버 묶음BIND 9 서버 3대

구성 요소와 흐름

구성 요소하는 일
designate-apiREST API
designate-central업무 규칙 처리, DB 기록
designate-workerDNS 서버(BIND)에 영역 생성·삭제를 지시
designate-producer주기 작업(영역 상태 점검 등)
designate-mdns (miniDNS)BIND가 영역 내용을 가져가는 출처. 변경 시 BIND에 알림(NOTIFY)을 보내고 BIND가 전송(AXFR·IXFR)으로 받아 감
BIND 9실제로 외부 질의에 답하는 권한 DNS 서버
Unbound (선택)VM 등이 이름 해석에 쓰는 재귀 리졸버
 
openstack zone create --email dnsadmin@example.com shop.example.com.
openstack zone list                                     # status: PENDING → ACTIVE (BIND까지 반영)
openstack recordset create --type A --record 203.0.113.30 shop.example.com. www
openstack recordset create --type CNAME --record www.shop.example.com. shop.example.com. web
openstack recordset list shop.example.com.
dig @<BIND 서버 주소> www.shop.example.com A +short    # 실제 응답 확인

위임: 인터넷에서 보이게 하려면

Designate에 shop.example.com.을 만들어도, 상위 도메인(example.com)을 관리하는 곳에서 NS 레코드로 Designate의 DNS 서버를 가리키게 위임해야 인터넷의 다른 사람이 찾을 수 있습니다. MSP 환경에서는 고객 도메인의 위임을 고객 DNS 담당자와 협의하는 것이 첫 단계입니다.

섹션 10

Neutron 연동: VM과 플로팅 IP에 자동 이름

Designate를 Neutron과 연동하면, VM을 만들거나 플로팅 IP를 붙일 때 레코드가 자동으로 생기고 지울 때 사라집니다.

설정 위치속성결과
네트워크dns_domain (예: cust-a.example.com.)그 망의 포트들이 이 영역에 레코드를 가짐
포트dns_name (VM 생성 시 보통 VM 이름으로 채워짐)web01.cust-a.example.com. A 레코드
플로팅 IPdns_name + dns_domain외부 IP로 A 레코드, 설정에 따라 역방향(PTR) 레코드
 
openstack network set --dns-domain cust-a.example.com. app-net
openstack server create … --network app-net web01        # → web01.cust-a.example.com. 자동 등록
openstack floating ip create --dns-domain shop.example.com. --dns-name www public
openstack recordset list cust-a.example.com.

어떤 포트 종류에 레코드를 만들지(모든 포트 vs 외부 노출 포트만 등)는 Neutron의 DNS 확장 드라이버 설정으로 정해집니다. 영역은 미리 Designate에 있어야 합니다.

내부 DNS와의 차이

Designate 없이도 OVN은 같은 네트워크 안의 VM 이름 해석을 일부 도울 수 있습니다(11편 dns_domain). Designate 연동은 외부에서도 조회되는 정식 DNS 레코드를 수명 주기에 맞춰 자동 관리한다는 점이 다릅니다.

섹션 11

RHOSO의 Designate

지원 상태부터 확인

RHOSO 18.0 릴리스 노트(FR3 기준 신기능 목록)는 DNS 서비스(designate)를 기술 미리보기로 소개합니다. 이후 RHOSO 문서에는 “Configuring DNS as a service” 가이드와 기능 지원 표가 있습니다. 운영 도입 전에는 설치하려는 18.0.x 버전의 릴리스 노트에서 지원 등급을 반드시 확인하세요.

섹션 12

Barbican 개념

Barbican(Key Manager 서비스)은 비밀 정보를 암호화해 보관하고, 허락된 사용자·서비스에게만 꺼내 줍니다. 다른 서비스들(Octavia, Cinder, Nova, Glance)이 “인증서·키를 어디에 둘까”의 답으로 Barbican을 씁니다.

개념뜻예
비밀 (secret)보관할 데이터 하나와 그 종류passphrase(비밀번호), symmetric(대칭 키), private·public 키, certificate, opaque(그 밖의 이진 데이터)
컨테이너여러 비밀을 묶은 것인증서 + 개인 키 + 중간 인증서 묶음 (TLS용)
주문 (order)Barbican에게 키를 만들어 달라고 요청AES 256비트 키 생성
ACL비밀을 다른 사용자(서비스 사용자 포함)가 읽게 허용Octavia 서비스 사용자에게 인증서 읽기 허용
참조 (href)비밀의 주소. 다른 서비스에는 비밀 자체가 아니라 이 주소를 넘김https://barbican…/v1/secrets/<UUID>

암호화 플러그인: 비밀을 무엇으로 감싸나

플러그인방식특징
simple_crypto설정 파일에 있는 마스터 키(KEK, 키를 암호화하는 키)로 각 비밀을 암호화해 DB에 저장추가 장비 불필요, 기본값. KEK가 유출되면 전체가 위험 → KEK 보호·백업이 핵심
PKCS#11 (HSM)마스터 키를 하드웨어 보안 모듈 안에 두고 암호화를 HSM이 수행마스터 키가 장비 밖으로 나오지 않음. 금융·공공 규제 대응. RHOSO에서는 지원 HSM 제품과 단계(기술 미리보기 등)를 문서로 확인
RHOSO 구성 요소하는 일
BarbicanAPIREST API
BarbicanWorker주문(키 생성) 같은 비동기 작업
BarbicanKeystoneListenerKeystone 이벤트(프로젝트 삭제 등)를 받아 정리
 
openstack secret store --name db-password --payload 'S3cr3t!'        # 비밀 저장
openstack secret list
openstack secret get <href> --payload                                  # 내용 꺼내기 (권한 필요)
openstack secret order create --name data-key --algorithm aes --bit-length 256 --mode cbc key
openstack acl user add --user <사용자 ID> <비밀 href>                  # 다른 사용자에게 읽기 허용

Barbican이 사라지면 데이터도 못 연다

암호화된 볼륨의 키, vTPM 키가 Barbican에 있다면 Barbican DB와 KEK(또는 HSM 키)를 잃는 순간 그 데이터를 영원히 열 수 없습니다. Barbican은 “있으면 좋은 부가 서비스”가 아니라 백업·복구 계획(26·27편)의 핵심 대상입니다.

섹션 18

정리와 다음 편

오늘의 핵심 여덟 문장

  • Octavia는 로드밸런서(VIP) → 리스너 → (L7 정책) → 풀 → 멤버 + 상태 검사.
  • amphora는 LB마다 HAProxy VM, L7·TLS 종료 가능, VM 자원 소모. OVN은 VM 없이 L4만, 빠르고 가벼우며 클라이언트 IP 보존.
  • RHOSO amphora는 octavia 네트워크(octbr NAD) + octavia-provider-net + lb-mgmt-net + 링크 라우터로 컨트롤러와 amphora를 SNAT 없이 잇고, 두 CA로 통신을 보호한다.
  • 상태는 provisioning(설정 작업)과 operating(실제 동작) 두 개. 멤버 보안 그룹이 LB 쪽 접근을 허용해야 한다.
  • Designate는 영역·레코드셋을 API로, BIND 9에 반영. 외부 공개에는 상위 도메인의 NS 위임이 필요하다.
  • Neutron 연동(dns_domain · dns_name)으로 VM·플로팅 IP 레코드가 자동으로 생기고 지워진다. RHOSO 18.0 Designate는 지원 등급을 버전별로 확인한다.
  • Barbican은 비밀·컨테이너·주문·ACL, 기본은 simple_crypto(KEK), 규제 환경은 HSM. 다른 서비스에는 비밀의 참조(href)를 넘긴다.
  • HTTPS 리스너·볼륨 암호화·이미지 서명·vTPM이 Barbican에 의존하므로 Barbican DB와 KEK는 백업 1순위다.
