AI 게이트웨이
멀티모델·멀티테넌트 진입점

11편의 Inference Gateway는 “이 모델의 어느 Pod로”를 정했습니다. 이번 편은 그 앞에서 “누가, 얼마나, 어느 모델(또는 어느 공급자)로”를 정하는 층입니다. API 키와 테넌트, 토큰 단위의 속도 제한과 예산, 셀프호스팅 vLLM과 Claude·OpenAI·Gemini API를 하나의 엔드포인트로 묶는 하이브리드 라우팅, 폴백과 캐시, 그리고 MSP가 고객별로 사용량을 재고 청구하는 기반까지 다룹니다.

선행 7·11편 읽는 시간 약 100분 실습 약 120분 기준 2026년 10월
요청 하나가 게이트웨이를 지나는 길

01시작하기 전에

AI 게이트웨이는 “LLM 호출의 관문”이자, 비용과 데이터가 새는 것을 막는 마지막 지점입니다.

2026년에 바뀐 것 (오래된 자료와 다른 점)
  • Envoy AI Gateway → Agent Router: 2026년 6월 v1.0 GA로 주요 CRD(AIGatewayRoute, AIServiceBackend, BackendSecurityPolicy, GatewayConfig, MCPRoute)가 v1beta1 안정 계약이 되었고, 9월 10일 Linux Foundation 산하 Agentic AI Foundation으로 옮겨 이름이 Agent Router로 바뀌었습니다. CRD·API 그룹·CLI(aigw)·네임스페이스·Helm 차트·이미지 이름은 그대로라 기존 매니페스트는 계속 동작합니다. 이 편에서는 “Agent Router(구 Envoy AI Gateway)”로 씁니다.
  • LiteLLM 공급망 사고: 2026년 3월 24일 PyPI에 악성 litellm 1.82.7·1.82.8이 올라와 약 40분간 배포되었습니다(자격 증명 탈취, 쿠버네티스 확산 시도). AI 게이트웨이는 모든 공급자의 API 키를 쥐는 자리라, 게이트웨이 자체의 공급망 관리가 핵심 운영 항목이 되었습니다(8장).

학습 목표

  1. AI 게이트웨이의 기능 열 가지를 설명하고, Inference Gateway와의 역할 경계를 그릴 수 있다.
  2. 키 → 사용자 → 팀 → 테넌트의 식별 계층과 쿼터·예산 계층을 설계할 수 있다.
  3. 요청 수가 아닌 토큰 기반 제한이 필요한 이유와, 스트리밍에서의 사후 차감 방식을 설명할 수 있다.
  4. 폴백·재시도·캐시를 쓰되, 데이터 정책(외부 전송 금지)과 충돌하지 않게 설계할 수 있다.
  5. 공급자 키 보관, 감사 로그, PII 처리, 게이트웨이 공급망 관리 같은 거버넌스 요구를 정리할 수 있다.
  6. LiteLLM으로 셀프호스팅 vLLM과 Claude·OpenAI·Gemini를 한 엔드포인트로 묶고, 가상 키·예산·토큰 제한·폴백을 실습할 수 있다.
이 편의 비유: 회사의 법인카드 시스템

직원(앱)은 각자 카드(가상 키)를 받고, 카드마다 한도(예산)와 사용처(허용 모델)가 정해져 있습니다. 결제는 회사 계좌(공급자 API 키)에서 나가지만 직원은 계좌 번호를 모릅니다. 한 가맹점이 문을 닫으면 지정된 대체 가맹점(폴백)으로 가되, “해외 결제 금지” 카드라면 대체 가맹점이 해외일 때 결제를 거부해야 합니다. 월말에는 부서별(테넌트별) 사용 내역이 정산됩니다.

02AI 게이트웨이가 하는 일

일반 API 게이트웨이의 기능에, “토큰”과 “여러 모델 공급자”라는 LLM 특유의 개념을 더한 것.

#기능내용일반 API 게이트웨이와 다른 점
1통합 API·모델 별칭여러 공급자를 OpenAI 호환(또는 Anthropic 호환) 하나의 API로. 앱은 chat-default 같은 별칭만 앎요청 본문의 model로 백엔드를 고름. 공급자별 요청·응답 형식 변환
2인증·가상 키사용자·앱에 게이트웨이 키를 발급. 공급자 키는 게이트웨이만 앎키마다 허용 모델·예산·만료
3테넌트·팀키를 팀·테넌트로 묶어 정책 상속MSP의 고객 구분 단위
4속도 제한RPM(요청 수)과 TPM(토큰 수)토큰은 응답이 끝나야 확정 (5장)
5예산·비용입력·출력·캐시·추론 토큰별 단가로 비용 계산, 한도 초과 차단셀프호스팅 모델에도 내부 단가를 매겨 원가 배분
6라우팅·폴백·재시도공급자 장애·과부하·문맥 길이 초과 시 대체 모델폴백 대상이 외부 공급자면 데이터 정책 문제 (6장)
7캐시정확 일치·의미 유사 캐시, 공급자 프롬프트 캐시 활용의미 캐시는 “틀린 답 재사용” 위험 (7장)
8가드레일 연동PII 마스킹, 프롬프트 인젝션·유해 출력 검사 (22·24편)본문 내용을 검사·변경
9관측토큰 지표, 공급자별 지연·오류, GenAI 트레이스, 감사 로그OpenTelemetry GenAI 규약 (21편)
10MCP 게이트웨이에이전트가 쓰는 MCP 도구 서버를 한 입구로 모으고 권한 관리최근 AI 게이트웨이 제품들의 새 영역

03어디에 두나: 층 구조

AI 게이트웨이는 “밖으로 나가는 트래픽(외부 API)”과 “안으로 들어오는 트래픽(셀프호스팅)”을 한 곳에서 다룹니다.

경로 ② 셀프호스팅 모델로 가는 요청 (같은 AI 게이트웨이)

앱·에이전트같은 엔드포인트·같은 키

›

  • 정책은 한 곳에서: 키·쿼터·우선순위·cache_salt 주입 같은 정책은 AI 게이트웨이에 둡니다. Inference Gateway는 받은 헤더(우선순위 등)를 믿고 배치만 합니다(11편).
  • 제품 하나로 두 층을 겸할 수 있음: Agent Router(구 Envoy AI Gateway)·agentgateway는 AIGatewayRoute 백엔드로 InferencePool을 직접 가리킬 수 있어, 한 프록시에서 두 층을 처리합니다. LiteLLM 같은 애플리케이션형 게이트웨이는 그 뒤에 Inference Gateway(또는 vLLM Service)를 둡니다.
  • 위치: 사내 앱만 쓰면 클러스터 안, 고객사·외부 개발자에게 제공하면 DMZ의 입구 뒤. 어느 경우든 공급자 API로 나가는 이그레스 경로를 게이트웨이로만 허용해 “키 우회 호출”을 막습니다.

04멀티테넌트 설계

“누구의 요청인가”를 정확히 알아야 쿼터·비용·우선순위·격리가 모두 가능합니다.

계층예 (MSP)붙는 정책
테넌트 (조직)고객사 A월 예산·총 TPM·허용 모델·데이터 정책(외부 전송 허용 여부)·우선순위 등급
팀 (프로젝트)고객사 A의 상담봇팀팀 예산·팀 TPM (테넌트 한도 안에서)
키 (앱·서비스 계정)상담봇 운영 키, 개발 키키별 RPM·TPM·만료·허용 모델·IP 제한
최종 사용자 (선택)상담봇을 쓰는 직원사용자별 공정성 제한, 감사 추적 (헤더로 전달)

게이트웨이가 아래층에 넘겨주는 것

  • 우선순위 헤더: 테넌트 등급에 따라 Objective 헤더를 붙여 Inference Gateway의 흐름 제어가 쓰게 합니다(11편 5장).
  • cache_salt: 테넌트 ID로 엔진의 프리픽스 캐시를 테넌트별로 격리합니다(4편). 앱이 아니라 게이트웨이가 강제로 넣어야 우회되지 않습니다.
  • 추적 정보: 테넌트·팀·키 ID를 트레이스·로그 속성으로 남겨 사용량 리포트와 장애 분석을 테넌트 단위로 할 수 있게 합니다(21편).
데이터 정책은 테넌트 속성이다

“우리 데이터는 외부 API로 나가면 안 된다”는 고객과 “외부 최신 모델을 쓰고 싶다”는 고객이 같은 게이트웨이를 씁니다. 그래서 허용 모델 목록과 폴백 대상은 테넌트 속성(데이터 정책)으로부터 계산되어야 합니다. 셀프호스팅 모델이 장애일 때 외부 모델로 자동 폴백하는 설정이 외부 전송 금지 고객에게도 적용되면, 장애가 곧 계약 위반이 됩니다.

05토큰 기반 속도 제한

LLM의 비용과 부하는 요청 수가 아니라 토큰 수에 비례합니다.

  • RPM만으로는 부족: 분당 10회 제한이라도 한 번에 10만 토큰을 보내는 클라이언트는 짧은 질문 수천 개만큼의 GPU를 씁니다.
  • 토큰 종류별로: 입력·출력·캐시 적중 입력·추론(reasoning) 토큰은 비용과 부하가 다릅니다. 최근 게이트웨이들은 이를 따로 집계해 비용을 배분합니다.
  • 사후 차감: 출력 토큰 수는 응답이 끝나야 압니다. 그래서 요청 시점에는 “남은 한도가 0보다 큰가”만 보고 통과시킨 뒤, 응답이 끝나면 실제 사용량을 차감하는 방식이 일반적입니다. 한 번의 큰 요청이 한도를 넘어 마이너스가 될 수 있으므로 max_tokens 상한도 함께 강제합니다.
  • 분산 카운터: 게이트웨이 레플리카가 여러 개면 카운터를 Redis 같은 공유 저장소에 둡니다(Agent Router는 Envoy의 레이트 리밋 서비스, LiteLLM은 Redis).

RPM 제한 vs TPM 제한 비교

두 테넌트가 같은 GPU 풀(분당 처리 가능 토큰 60만)을 공유합니다. A는 짧은 요청을 많이, B는 긴 문서 요약을 적게 보냅니다. 같은 수준의 “공정한” 제한을 RPM과 TPM으로 걸었을 때 실제 GPU 몫이 어떻게 나뉘는지 봅니다.

06라우팅·폴백·재시도

여러 공급자를 묶는 가장 큰 이유는 “한 곳이 안 될 때 다른 곳으로”입니다. 그리고 가장 큰 위험도 거기에 있습니다.

용량 폴백429(속도 제한), 셀프호스팅 대기열 포화짧은 과부하에 비싼 외부 API로 대량 유출 → 비용 폭증. 폴백에도 예산 한도
문맥 길이 폴백입력이 모델 최대 길이 초과더 긴 문맥 모델은 대개 더 비쌈
비용·지연 기반 라우팅요청 특성(길이·난이도)에 따라 작은·큰 모델분류 오류 시 품질 저하. 평가로 검증 (22편)

07캐시

캐시는 세 층에 있고, 각각 다른 것을 아낍니다.

캐시위치재사용 단위아끼는 것위험
엔진 프리픽스 캐시vLLM (4편)·라우팅(10·11편)공통 앞부분의 KVPrefill 연산·TTFT테넌트 간 타이밍 부채널 → cache_salt
공급자 프롬프트 캐시Claude·OpenAI·Gemini 등공급자 쪽 프롬프트 앞부분외부 API 입력 토큰 비용·지연공급자별 조건(최소 길이·명시 표시·유지 시간)이 다름. 게이트웨이가 형식을 보존해야 함
정확 일치 응답 캐시AI 게이트웨이 (Redis 등)완전히 같은 요청 → 같은 응답호출 자체temperature > 0 요청엔 의미 없음, 테넌트 격리 필수
의미(시맨틱) 캐시AI 게이트웨이 + 임베딩·벡터 저장소“비슷한” 질문 → 과거 응답호출 자체틀린 답 재사용(“3월 매출?”과 “4월 매출?”은 임베딩상 가까움), 개인화 응답 유출. 임계값·대상 엄격히

실무 권장은 단순합니다. 엔진 프리픽스 캐시와 공급자 프롬프트 캐시는 적극 활용하고(정답이 바뀌지 않음), 응답 캐시는 FAQ처럼 답이 고정된 범위에만, 테넌트별로 격리해서 씁니다. 의미 캐시를 켤 때는 반드시 평가 세트로 오답 재사용률을 측정합니다(22편).

08보안·거버넌스·공급망

AI 게이트웨이는 모든 공급자 키와 모든 프롬프트가 지나가는 자리입니다. 가장 강하게 지켜야 하는 구성 요소입니다.

영역요구구현
공급자 키앱·사람이 공급자 키를 보지 않음시크릿 저장소(Vault·외부 시크릿)에서 게이트웨이만 읽기, 정기 교체, 공급자 콘솔에서 키별 사용량 한도
가상 키유출 시 피해 한정최소 권한(허용 모델), 예산, 만료, IP 제한, 즉시 폐기 절차
이그레스게이트웨이를 우회한 공급자 직접 호출 차단NetworkPolicy·방화벽에서 공급자 도메인으로의 이그레스를 게이트웨이 Pod만 허용
로그·감사누가 언제 어떤 모델에 얼마를 썼나. 프롬프트 원문 보관 여부는 정책메타데이터(키·테넌트·모델·토큰·비용)는 항상, 본문은 마스킹 또는 기간 한정
PII·가드레일개인정보가 외부 공급자로 나가지 않게게이트웨이 단계의 탐지·마스킹, 외부 전송 금지 테넌트 강제 (22·24편)
게이트웨이 공급망게이트웨이 소프트웨어 자체가 공격 경로가 되지 않게아래 체크리스트
2026년 3월 LiteLLM 사고에서 배우는 공급망 체크리스트

공격자가 다른 프로젝트(보안 스캐너)의 CI 침해로 얻은 자격 증명을 이용해 litellm PyPI 계정으로 악성 버전을 올렸고, 버전 고정 없이 설치한 환경에서 클라우드·쿠버네티스 자격 증명을 탈취하려 했습니다. 공식 Docker 이미지 경로처럼 버전을 고정한 배포는 영향이 적었던 것으로 공지되었습니다. AI 게이트웨이를 운영한다면:

  • 버전·다이제스트 고정: pip install litellm, :latest, main 태그 금지. 컨테이너는 다이제스트(@sha256:…)로, 패키지는 해시와 함께 고정.
  • 업그레이드 지연: 새 릴리스를 바로 쓰지 않고 며칠의 냉각 기간 + 스테이징 검증. 공지된 안전 버전·체크섬과 대조.
  • 최소 권한: 게이트웨이 Pod의 서비스 계정 권한 최소화, 클러스터 자격 증명·클라우드 메타데이터 접근 차단.
  • 이그레스 허용 목록: 게이트웨이가 나갈 수 있는 도메인을 공급자 API로 제한하면, 악성 코드의 외부 전송도 막힙니다.
  • 탐지: 이미지 스캔과 함께 런타임에서 예상치 못한 외부 연결·프로세스를 감시.

이것은 LiteLLM만의 문제가 아니라 모든 게이트웨이(그리고 모든 파이썬·npm 기반 도구)에 해당합니다.

12실습

LiteLLM으로 셀프호스팅 vLLM과 Claude·OpenAI·Gemini를 한 엔드포인트로 묶고, 고객별 가상 키·예산·토큰 제한·폴백을 확인합니다. 마지막으로 Agent Router를 7편 Envoy Gateway 위에 올려 쿠버네티스 네이티브 구성을 맛봅니다.

실습 환경 전제와 주의
  • 7편 랩의 llm-engine(qwen3-8b, FP8 오버레이 권장)과 bench Pod가 떠 있어야 합니다. 인터넷 접근이 가능해야 외부 공급자를 호출할 수 있습니다.
  • 외부 공급자 키는 가진 것만 넣으면 됩니다. 키가 없는 공급자의 모델은 호출 시 오류가 나며, 나머지 실습에는 지장이 없습니다. 외부 호출은 실제 비용이 발생하므로 공급자 콘솔에서 키별 사용 한도를 먼저 걸어 두세요.
  • OpenAI·Gemini의 모델 ID는 바뀌는 일이 잦아 자리표시자(<OPENAI_MODEL_ID> 등)로 두었습니다. 각 공급자 문서의 현재 모델 ID로 채우세요. Claude는 claude-sonnet-5-5, claude-haiku-5-5를 씁니다.
  • 이미지는 반드시 버전·다이제스트로 고정합니다(8장). main-latest류 태그는 쓰지 않습니다.

실습 12-4 · 하나의 엔드포인트로 네 공급자 호출

python · gw_try.py (bench Pod에서)
"""AI 게이트웨이 하나로 여러 모델을 호출하고 응답 모델·토큰·지연을 비교한다.
사용: python gw_try.py <키> [모델 별칭 ...]"""
import sys, time
from openai import OpenAI
key = sys.argv[1]
models = sys.argv[2:] or ["qwen3-8b", "claude-haiku", "claude-sonnet", "gpt", "gemini"]
cli = OpenAI(base_url="http://litellm:4000/v1", api_key=key, timeout=120)
for m in models:
    t0 = time.perf_counter()
    try:
        r = cli.chat.completions.create(model=m, max_tokens=120,
            messages=[{"role": "user", "content": "쿠버네티스 GPU 노드에 테인트를 거는 이유를 두 문장으로. /no_think"}])
        dt = time.perf_counter() - t0
        u = r.usage
        print(f"[{m:<13}] 실제 응답 모델={r.model}  입력={u.prompt_tokens} 출력={u.completion_tokens}  {dt*1000:.0f} ms")
        print("   ", (r.choices[0].message.content or "").strip().replace("\n", " ")[:110])
    except Exception as e:
        print(f"[{m:<13}] 실패: {type(e).__name__}: {str(e)[:120]}")

실습 12-7 · (선택) Agent Router를 Envoy Gateway 위에

쿠버네티스 네이티브 AI 게이트웨이를 7편 Envoy Gateway에 얹습니다. Agent Router는 Envoy Gateway의 확장 서버로 동작하므로 Envoy Gateway를 Agent Router 문서가 제공하는 값으로 업그레이드해야 합니다. 이 작업은 7편 랩의 입구에 영향을 주므로 시간을 정해 진행하고, 호환되는 Envoy Gateway 버전은 Agent Router 릴리스 노트에서 확인합니다(1.1은 Envoy Gateway v1.8.1 기반).

15정리와 체크리스트

핵심 여섯 문장.

  1. AI 게이트웨이는 “누가·얼마나·어느 모델”의 층이고, Inference Gateway는 “어느 Pod”의 층이다. 정책은 한 곳(AI 게이트웨이)에서 정해 아래로 헤더로 넘긴다.
  2. 식별 계층(테넌트·팀·키·사용자)이 쿼터·비용·우선순위·cache_salt의 기반이다. 데이터 정책은 테넌트 속성이다.
  3. LLM의 제한 단위는 토큰이다. 응답 후 사후 차감하므로 max_tokens 상한을 함께 둔다.
  4. 폴백은 가용성을 사고 데이터 경로와 비용을 판다. 외부 전송 금지 테넌트에는 폴백 없는 별칭만 허용하고, 폴백 발생을 경보로 감시한다.
  5. 캐시는 세 층: 엔진·공급자 프롬프트 캐시는 적극 활용, 응답·의미 캐시는 범위를 좁히고 테넌트별로 격리한다.
  6. 게이트웨이는 모든 키가 모이는 곳이라 공급망 관리가 핵심이다. 다이제스트 고정, 업그레이드 냉각 기간, 이그레스 허용 목록, 최소 권한.
