Kubeflow 강의15편: 관측과 트러블슈팅

관측과
트러블슈팅

운영 중인 플랫폼은 조용할 때보다 시끄러울 때가 더 많습니다. 무엇이 정상인지 숫자로 알고, 이상하면 먼저 알려 주게 하고, 고장 나면 어디부터 볼지 순서를 정해 둡니다. 이 시리즈의 문제 해결 장들을 하나의 진단 지도로 모읍니다.

Level 4 전문가, 전체 16편 중 15편

기준
Prometheus, Grafana, OpenTelemetry, kube-state-metrics, DCGM Exporter
대상 환경
14편의 운영 설치
사전 지식
2편의 Pod 상태와 kubectl, 이 시리즈의 OpenTelemetry 강의
학습 시간
약 90분

증상별 진단 지도

질문에 답해 가면 원인 후보, 확인할 명령, 해결 방법, 자세히 다룬 편이 나옵니다. 1편부터 14편까지의 문제 해결을 한데 모았습니다.

이번 편에서 얻을 것

12편에서 “관측 지표가 재학습과 되돌리기를 깨운다”고 했고, 13편과 14편에서 운영 준비를 마쳤습니다. 이제 운영 중인 플랫폼을 들여다보는 눈을 만듭니다. 이 편을 마치면 다음을 할 수 있습니다.

  • Kubeflow의 층(입구, 제어부, 작업, 자원, 서빙, 모델 품질)마다 볼 핵심 신호를 알고 수집 구성을 설계할 수 있습니다.
  • 플랫폼 운영자와 팀 모두에게 쓸모 있는 대시보드와, 행동으로 이어지는 경보를 만들 수 있습니다.
  • 구성요소별 로그 위치와 트레이스, 모델 품질 관측의 방법을 압니다.
  • 증상에서 출발해 층을 따라 내려가는 진단 순서를 익히고, 반복되는 문제를 런북으로 만들 수 있습니다.

1관측의 기둥과 도구

신호답하는 질문흔한 도구
메트릭지금 얼마나, 정상 범위인가, 언제부터 나빠졌나Prometheus, Grafana. kube-state-metrics(리소스 상태), DCGM Exporter(GPU), Istio(요청)
로그무슨 일이 왜 일어났나Loki, Elasticsearch/OpenSearch, 클라우드 로그 서비스. 수집기는 Fluent Bit나 OpenTelemetry Collector
트레이스요청 하나가 어디서 시간을 썼나OpenTelemetry Collector, Tempo, Jaeger
Kubernetes 이벤트스케줄링, 이미지, 볼륨 단계에서 무엇이 막혔나kubectl get events, 이벤트를 로그로 보내는 수집기
ML 기록어떤 데이터와 코드로 어떤 결과가 나왔나Pipelines 실행 기록, Katib 결과, Hub 메타데이터(5, 8, 9편)
모델 품질운영 중인 모델이 여전히 잘 맞히나예측 로그 분석, 드리프트 지표(7장)

Kubeflow 배포판은 관측 스택을 함께 설치하지 않습니다. 대부분의 조직은 이미 쓰는 관측 스택(예: kube-prometheus-stack과 Grafana, 로그 플랫폼)에 Kubeflow를 대상으로 추가합니다. 수집기를 OpenTelemetry Collector로 통일하는 설계는 이 시리즈의 OpenTelemetry 강의에서 다뤘습니다.

2층별로 볼 신호

1편의 노선도와 3편의 설치 탑을 떠올리며, 층마다 “이것이 나빠지면 사용자가 아프다”는 신호를 고릅니다.

층핵심 신호지표 예
입구 (게이트웨이, oauth2-proxy, Dex)요청 수, 오류율, 지연, 인증서 만료일istio_requests_total(응답 코드별), istio_request_duration_milliseconds, cert-manager의 인증서 만료 지표
제어부 (각 컨트롤러, 웹 앱, API 서버)Pod 재시작, 준비 상태, 웹훅 오류, 조정 대기열kube_pod_container_status_restarts_total, kube_pod_status_ready, 컨트롤러가 내보내는 조정 지표
작업 (파이프라인, TrainJob, Trial, Spark)성공률, 대기 시간, 실행 시간, 실패 이유파이프라인 실행 결과(12편의 알림과 함께), Pending Pod 수, OOMKilled 수
자원 (노드, GPU, 큐, 저장소)사용률, 남은 용량, 대기열DCGM_FI_DEV_GPU_UTIL, DCGM_FI_DEV_FB_USED, kueue_pending_workloads, PVC 사용량
서빙 (InferenceService)요청 수, 오류율, 지연(p50, p95, p99), 복제본 수, 콜드 스타트Istio 요청 지표, 서빙 런타임이 내보내는 지표, Knative 오토스케일러 지표
모델 품질입력 분포 변화, 예측 분포 변화, 사후 정답 대비 정확도예측 로그로 계산한 드리프트 점수(7장)

Kubeflow 구성요소가 직접 내보내는 지표의 이름과 종류는 버전마다 다릅니다. 각 구성요소의 /metrics 엔드포인트를 실제로 열어 보고 필요한 것을 고르세요.

3대시보드 설계

대시보드는 보는 사람에 따라 나눕니다. 모두를 위한 대시보드 하나는 아무에게도 쓸모없기 쉽습니다.

대시보드보는 사람담을 것
플랫폼 상태플랫폼 운영자입구 오류율과 지연, 구성요소별 준비 상태와 재시작, 웹훅 오류, 인증서 만료까지 남은 날, DB와 저장소 용량
자원과 비용운영자, 팀 리더팀(네임스페이스)별 GPU와 CPU 사용 시간, 놀고 있는 GPU, Kueue 큐 대기열과 빌려 쓴 양, 노드 풀별 사용률
작업 운영팀파이프라인 성공률과 실행 시간 추이, 반복 실행 결과, 학습 대기 시간, 실패 이유 상위 목록
서빙팀, 온콜모델별 요청 수, 오류율, 지연 분포, 복제본 수, 카나리와 기존 버전 비교(9편, 12편)
모델 품질데이터 과학자입력과 예측 분포의 변화, 사후 정확도, 재학습 이력
팀이 자기 숫자를 보게 하세요

자원과 비용 대시보드를 팀별로 필터해 보여 주면, 잊힌 GPU 노트북이나 과한 병렬 실행이 운영자의 잔소리 없이도 줄어듭니다. 16편의 비용 이야기로 이어집니다.

4경보 설계

좋은 경보는 사람을 깨울 가치가 있고, 받은 사람이 무엇을 할지 압니다. 원인이 아니라 증상(사용자가 아픈 것)에 걸고, 경보마다 10장의 런북 링크를 붙입니다.

예시 규칙 (PromQL, 레이블 이름은 환경에 맞게 조정)

# 1. 대시보드 입구의 5xx 비율이 5%를 넘음 (10분 지속) → 사용자 전체 영향
sum(rate(istio_requests_total{reporter="destination", destination_workload_namespace="kubeflow", response_code=~"5.."}[5m]))
  / sum(rate(istio_requests_total{reporter="destination", destination_workload_namespace="kubeflow"}[5m])) > 0.05

# 2. 같은 컨테이너가 OOMKilled로 30분 안에 3번 넘게 재시작 → 메모리 설정 문제
increase(kube_pod_container_status_restarts_total[30m]) > 3
  and on (namespace, pod, container)
  kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1

# 3. 할당된 GPU가 2시간째 거의 놀고 있음 → 비용 낭비 (낮은 등급, 업무 시간에만)
avg_over_time(DCGM_FI_DEV_GPU_UTIL[2h]) < 5

# 4. Kueue 대기 작업이 2시간 넘게 쌓여 있음 → 용량 부족 또는 큐 설정 문제
sum by (cluster_queue) (kueue_pending_workloads) > 0      # for: 2h

# 5. 모델 서버의 p95 지연이 500ms를 넘음
histogram_quantile(0.95, sum by (le, destination_service_name) (
  rate(istio_request_duration_milliseconds_bucket{destination_workload_namespace=~"team-.*"}[5m]))) > 500

# 6. 인증서 만료가 14일 이내 → 14편의 자동 갱신이 실패했다는 신호
certmanager_certificate_expiration_timestamp_seconds - time() < 14 * 24 * 3600
등급기준예
긴급 (사람을 깨움)지금 다수 사용자나 운영 서빙이 아픔1번, 운영 모델의 5번, 운영 모델 오류율 급증
경고 (업무 시간에 처리)곧 아플 것, 한 팀만 아픔2번, 4번, 6번, 반복 실행 연속 실패
정보 (보고서로)비용과 효율3번, 팀별 GPU 사용 시간

5로그 찾기

무엇의 로그어디서요령
로그인 문제oauth2-proxy, auth 네임스페이스의 Dex, istio-system의 게이트웨이시각을 맞춰 세 곳을 같이 봄(3편 6장의 흐름 순서대로)
노트북노트북 Pod(이름-0)의 컨테이너, kubeflow의 Notebook 컨트롤러Pod가 안 뜨면 컨트롤러와 Events, 뜬 뒤 문제면 Pod 로그
파이프라인 단계단계 executor Pod의 main 컨테이너, 화면의 Logs 탭실행 ID로 검색할 수 있게 로그 수집 시 Pod 라벨을 함께 저장(5편 8장)
파이프라인이 시작조차 안 됨kubeflow의 KFP API 서버, Argo Workflow 컨트롤러Workflow 리소스가 만들어졌는지부터
학습학습 노드 Pod들, kubeflow-system의 Trainer와 JobSet 컨트롤러rank 0 로그부터. NCCL_DEBUG=INFO(7편)
튜닝Trial Pod, 지표 수집 사이드카, Suggestion Pod, Katib 컨트롤러지표를 못 찾으면 사이드카 로그(8편 6장)
서빙예측 Pod의 kserve-container와 storage-initializer, KServe 컨트롤러READY가 안 되면 storage-initializer부터(9편)

운영에서는 Pod가 지워지면 로그도 사라지므로 중앙 로그 저장소가 필수입니다. 수집할 때 네임스페이스, Pod 이름, 그리고 파이프라인 실행 ID나 TrainJob 이름 같은 라벨을 함께 남기면, 12편의 알림에 든 실행 ID로 바로 해당 로그를 찾을 수 있습니다.

모델 서버의 요청과 응답 자체를 기록하려면 KServe의 요청 로깅(logger)을 켜서 예측 요청과 응답을 CloudEvents로 Knative Eventing 브로커 등에 보낼 수 있습니다. 이 시리즈의 Knative 강의 Eventing 편과 이어집니다. 개인정보가 들어 있을 수 있으므로 보관과 접근 권한을 13편의 기준으로 정합니다.

6트레이스

모델 서버의 지연이 늘었을 때, 그 시간이 게이트웨이, 오토스케일링 대기, 모델 로딩, 실제 추론 중 어디서 쓰였는지는 메트릭만으로 알기 어렵습니다. Istio의 사이드카(Envoy)는 요청마다 트레이스 구간을 만들 수 있고, 이를 OpenTelemetry Collector로 모아 Tempo나 Jaeger에서 봅니다.

  • 서버리스 모드의 KServe라면 요청은 게이트웨이, Knative의 activator(0개에서 깨어날 때), queue-proxy, 예측 컨테이너를 거칩니다. 트레이스에서 activator 구간이 길면 콜드 스타트, 예측 컨테이너 구간이 길면 모델 자체의 문제입니다.
  • 여러 모델을 잇는 추론 그래프나 앞뒤 처리(transformer)가 있다면 트레이스의 가치가 더 커집니다.
  • 트레이스는 양이 많으므로 표본 추출 비율을 정하고, 오류와 느린 요청을 우선 남기는 방식을 씁니다. 구체적인 구성은 OpenTelemetry 강의를 참고하세요.

7모델 품질 관측

서버가 건강해도 모델이 틀릴 수 있습니다. 1편의 핵심 한 줄, “ML 모델은 손대지 않아도 나빠진다”를 숫자로 지켜보는 일입니다.

무엇을어떻게정답이 필요한가
입력 데이터 드리프트주요 피처의 분포를 학습 기간과 비교(PSI, KS 검정 등)아니오. 바로 알 수 있음
예측 분포 변화예측 클래스 비율이나 점수 분포의 변화아니오
실제 성능나중에 들어오는 정답(클릭 여부 등)과 예측을 맞춰 정확도 계산예. 정답이 늦게 옴
업무 지표클릭률, 전환율 등간접적

흐름은 KServe 요청 로깅이나 애플리케이션 로그로 예측을 모으고, 주기적인 분석 작업(파이프라인 하나로 만들어도 좋음)이 드리프트 점수를 계산해 지표로 내보내고, 기준을 넘으면 12편 8장의 성능 저하 트리거가 재학습을 깨우는 것입니다. 드리프트 계산에는 Evidently 같은 오픈소스 도구를 컴포넌트 안에서 쓸 수 있습니다.

8진단의 순서

맨 위 진단 지도는 자주 나오는 증상을 다룹니다. 처음 보는 문제라면 다음 순서를 따릅니다.

  1. 증상을 정확히

    “안 돼요”가 아니라 누가, 언제부터, 어떤 화면이나 명령에서, 어떤 메시지로. 실행 ID, Pod 이름, 시각을 받습니다.

  2. 범위 정하기

    한 사람인가, 한 팀인가, 모두인가. 한 사람이면 권한과 설정(13편), 모두면 입구와 공용 구성요소부터.

  3. 최근 변경 확인

    대부분의 장애는 변경 뒤에 옵니다. Git 기록(12편), 업그레이드(14편), 노드와 인증서 변화를 먼저 봅니다.

  4. 층을 따라 내려가기

    입구 → 인증과 인가 → 해당 구성요소의 컨트롤러와 API → 만들어진 리소스(Workflow, TrainJob, InferenceService) → Pod → 노드와 자원(GPU, 저장소, 할당량). 3편의 설치 탑을 위에서 아래로 훑는 셈입니다.

  5. Events와 로그

    막힌 층에서 kubectl describe의 Events를 먼저 보고, 그다음 로그를 봅니다. Events가 스케줄링, 이미지, 볼륨, 웹훅 문제의 대부분을 말해 줍니다.

  6. 가설을 세우고 하나씩 바꾸기

    여러 설정을 한꺼번에 바꾸면 무엇이 고쳤는지 모릅니다. 하나씩 바꾸고 결과를 기록합니다.

  7. 기록하고 막기

    원인과 조치를 런북으로 남기고, 다시 오지 않게 경보나 입장 정책, 점검표를 고칩니다.

9진단 명령 모음

10런북 만들기

같은 문제를 두 번 겪었다면 런북을 씁니다. 새벽에 경보를 받은 사람이 생각하지 않고 따라 할 수 있어야 합니다.

# 런북: GPU 학습이 오래 대기함
증상:     TrainJob이 30분 넘게 시작되지 않음. Kueue 대기 경보 또는 사용자 신고
영향:     해당 팀의 학습과 야간 파이프라인 지연
확인:
  1. kubectl get workloads -n <ns>  → 대기 이유(admitted 여부)
  2. kubectl describe clusterqueue <q> → 사용량, 빌려 준 양
  3. 들여보내졌는데 Pod가 Pending이면 describe pod의 Events
조치:
  - 몫이 꽉 참: 팀에 알리고 대기. 급하면 우선순위 조정(승인 필요)
  - 다른 팀이 빌려 감: 돌려받기 설정 확인(11편)
  - 노드 부족: GPU 노드 풀 증설 요청
  - toleration/라벨 불일치: ResourceFlavor 설정 수정(PR)
에스컬레이션: 1시간 내 해결 안 되면 플랫폼 팀 온콜
관련:     11편, 경보 4번

맨 위 진단 지도의 항목들이 런북의 초안입니다. 조직의 실제 경험으로 채워 나가세요.

13정리와 다음 편

  1. Kubeflow는 관측 스택을 함께 설치하지 않습니다. 기존 스택에 메트릭, 로그, 트레이스, 이벤트를 연결하고, ML 기록과 모델 품질을 더합니다.
  2. 층마다 사용자가 아파하는 신호를 고릅니다. 입구의 오류율과 지연, 제어부의 재시작, 작업의 성공률과 대기, 자원의 사용률과 대기열, 서빙의 지연 분포, 모델의 드리프트.
  3. 대시보드는 보는 사람별로, 경보는 증상에 걸고 등급을 나누며 런북 링크를 붙입니다.
  4. 진단은 증상, 범위, 최근 변경, 층을 따라 내려가기, Events와 로그, 하나씩 바꾸기, 기록의 순서로.
  5. 두 번 겪은 문제는 런북으로, 세 번은 자동화나 입장 정책으로 막습니다.

현장에서 쓰이는 장면

  • MSP. 고객사 플랫폼의 입구 오류율과 인증서 만료 경보를 중앙 관측 스택에서 한눈에 보고, 증상별 진단 지도로 1차 대응 시간을 줄입니다.
  • 금융. 예측 로그로 드리프트 점수를 계산해 기준을 넘으면 재학습을 깨우고, 그 과정을 감사 기록으로 남깁니다.
  • 연구소. 놀고 있는 GPU 노트북을 사용률 지표로 찾아 연구실에 알려 줍니다.
