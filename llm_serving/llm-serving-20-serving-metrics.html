Level 4 · 모니터링 — 20편 (Level 4 시작)

서빙 지표 체계
엔진·GPU·게이트웨이 메트릭

지금까지 지표는 실험할 때 잠깐 들여다보는 숫자였습니다. Level 4부터는 운영 중 늘 켜져 있는 관측입니다. 이번 편은 어느 층에서 어떤 지표를 모아, 어떤 질문에 답할 것인가를 정리합니다. vLLM 엔진·DCGM GPU·Inference Gateway·AI 게이트웨이의 지표를 하나의 체계로 묶고, 운영용 Prometheus 스택과 기록 규칙·대시보드를 세우며, 엔진 버전마다 지표 이름이 바뀌는 문제에 대비하는 방법까지 다룹니다.

선행 3·11·12·18편 읽는 시간 약 100분 실습 약 150분 기준 vLLM v0.31.0 지표
이 증상이면 어떤 지표부터?

    01시작하기 전에

    좋은 지표 체계는 “무엇이 잘못됐나”보다 “어디가 잘못됐나”에 빨리 답합니다.

    Level 4의 구성

    • 20편 (이번): 지표 — 숫자로 상태를 본다. 체계·수집·기록 규칙·대시보드.
    • 21편: 트레이스·로그와 SLO 운영 — 요청 하나의 경로를 따라가고, SLO와 오류 예산으로 운영한다.
    • 22·23편: 품질 관측과 경보·장애 대응 — 응답 품질을 운영 중에 재고, 경보를 사람이 대응할 수 있는 형태로 만든다.

    학습 목표

    1. LLM 서빙의 지표를 층(GPU·엔진·라우팅·게이트웨이·앱)과 황금 신호(트래픽·오류·지연·포화)로 분류할 수 있다.
    2. vLLM 주요 지표의 뜻과 PromQL 활용, 그리고 엔진 간 대응 지표를 설명할 수 있다.
    3. 엔진 버전에 따른 지표 이름 변화를 기록 규칙·점검 스크립트로 흡수할 수 있다.
    4. DCGM 지표 중 LLM 운영에 의미 있는 것과 GB10의 제약을 구분할 수 있다.
    5. kube-prometheus-stack으로 운영용 수집·기록 규칙·대시보드를 구성할 수 있다.
    6. 히스토그램 백분위의 추정 오차와 올바른 집계 방법을 설명할 수 있다.
    이 편의 비유: 병원 검사 체계

    환자가 “어지럽다”고 하면(사용자 체감 지표) 의사는 혈압·혈액 검사(엔진 지표), 심전도(GPU 지표), 생활 기록(게이트웨이·요청 기록)을 순서대로 봅니다. 검사 항목마다 정상 범위가 있고, 검사 기기가 바뀌면 단위·이름이 달라지므로 검사 결과를 “표준 항목”으로 환산해 차트에 기록합니다(기록 규칙). 좋은 차트는 증상에서 원인까지 몇 번의 클릭으로 내려갈 수 있게 정리되어 있습니다(대시보드).

    03엔진 지표 (vLLM)

    엔진 /metrics는 가장 풍부한 원인 지표의 출처입니다. 카운터는 노출될 때 이름 뒤에 _total이 붙습니다.

    분류지표 (vllm: 접두어)형식읽는 법 (PromQL 예)
    요청 상태num_requests_running · num_requests_waiting · num_requests_waiting_by_reason게이지대기 > 0 지속 = 포화. 대기 사유별로 원인 구분
    지연time_to_first_token_seconds · inter_token_latency_seconds · e2e_request_latency_seconds히스토그램histogram_quantile(0.95, sum by (le, model_name) (rate(…_bucket[5m])))
    지연 분해request_queue_time_seconds · request_prefill_time_seconds · request_decode_time_seconds히스토그램TTFT가 나쁠 때 대기 때문인지 Prefill 때문인지
    토큰prompt_tokens · generation_tokens · prompt_tokens_cached · iteration_tokens_total카운터·히스토그램rate(vllm:generation_tokens_total[5m]) = 출력 tok/s
    요청 크기request_prompt_tokens · request_generation_tokens · request_params_n히스토그램워크로드 변화 감지 (19편 워크로드 카드)
    KV·캐시kv_cache_usage_perc · prefix_cache_queries · prefix_cache_hits · (표본) KV 블록 수명·축출 전 유휴 시간게이지·카운터적중률 = hits ÷ queries (15편)
    선점·결과num_preemptions · request_success카운터선점률 > 0 지속 = KV 부족 (14편)
    고급 기능추측 디코딩(제안·수락 토큰) · LoRA 요청 정보 · KV 커넥터·오프로딩(NIXL·CPU 오프로드) · MFU(옵션)여러 형식16·10·15편 기능을 켰을 때만

    모든 지표에는 model_name·engine 같은 라벨이 붙습니다. 레플리카 여러 개를 합칠 때는 히스토그램을 sum by (le)로 먼저 합친 뒤 백분위를 계산합니다(10장).

    04지표 이름의 변화 다루기

    엔진을 업그레이드했더니 대시보드가 빈 칸이 되는 일은 반드시 일어납니다. 미리 구조로 막아 둡니다.

    • vLLM의 폐기 규칙: 어떤 버전에서 폐기 예정이 된 지표는 다음 버전에서 숨겨지고(옵션으로 다시 켤 수 있음), 그다음 버전에서 제거됩니다. 실제로 V0 시절의 swap 관련 지표나 이전 이름의 KV 사용률 지표가 이렇게 사라졌습니다. 업그레이드 노트의 지표 변경 항목을 반드시 확인합니다.
    • 엔진마다 이름이 다르다: 같은 “실행 중 요청”도 엔진마다 이름이 다릅니다(아래 표). 여러 엔진을 운영하는 MSP라면 엔진 중립 이름이 필요합니다.
    • 해법 ① 기록 규칙을 추상화 층으로: 대시보드·경보·자동 확장은 엔진 지표를 직접 쓰지 않고 llm:ttft_seconds:p95 같은 우리 표준 이름의 기록 규칙만 씁니다. 엔진이 바뀌면 기록 규칙 한 곳만 고칩니다(8장).
    • 해법 ② 업그레이드 점검: 스테이징에서 새 버전의 /metrics 이름 목록을 뽑아 기대 목록과 비교하는 스크립트를 업그레이드 절차에 넣습니다(실습 20-4).
    • 해법 ③ 버전 라벨: 수집 시 엔진 버전·이미지 태그를 라벨(또는 정보 지표)로 붙여, 그래프의 변화가 버전 변경 시점과 겹치는지 바로 보이게 합니다.
    표준 의미vLLMSGLangTensorRT-LLM (serve)
    실행 중 요청vllm:num_requests_runningsglang:num_running_reqstrtllm_num_requests_running
    토큰 간 지연vllm:inter_token_latency_secondssglang:inter_token_latency_secondstrtllm_time_per_output_token_seconds
    KV 사용률vllm:kv_cache_usage_perc(토큰 사용률 계열 지표)(엔진 문서 확인)

    엔진별 이름은 버전에 따라 바뀌므로 5편의 “지표 이름 대응표”를 운영 문서로 관리하고, 업그레이드 때마다 갱신합니다.

    05GPU·노드 지표 (DCGM)

    GPU 지표는 “원인”이 아니라 “하드웨어가 무엇을 하고 있나”를 봅니다. 그중 LLM에 의미 있는 것은 소수입니다.

    DCGM 필드의미LLM 운영에서
    DCGM_FI_DEV_GPU_UTIL커널이 실행 중인 시간 비율배치에 요청이 조금만 있어도 높음. 확장·용량 판단에 쓰지 않음 (18편)
    DCGM_FI_PROF_SM_ACTIVE · SM_OCCUPANCYSM이 실제로 일한 비율·점유연산 쪽 여유. Prefill 비중이 크면 높음
    DCGM_FI_PROF_DRAM_ACTIVE메모리 대역폭 사용 비율Decode 포화의 하드웨어 측 증거 (2편 루프라인)
    DCGM_FI_PROF_PIPE_TENSOR_ACTIVE텐서 코어 활성양자화·커널 효과 확인
    DCGM_FI_DEV_FB_USED · FREEGPU 메모리 사용vLLM이 미리 잡아 부하와 무관. GB10은 “지원 안 됨”
    DCGM_FI_DEV_POWER_USAGE · GPU_TEMP · 클럭 스로틀 사유전력·온도·스로틀링같은 설정인데 성능이 떨어질 때 열·전력 제한 확인
    DCGM_FI_DEV_XID_ERRORS · ECC 오류드라이버가 보고한 GPU 오류즉시 경보 대상 (하드웨어·드라이버 장애)
    NVLink·PCIe 처리량GPU 간·호스트 전송량TP·P/D·오프로딩 통신 확인 (10·15·17편)
    GB10에서의 GPU 지표

    GB10은 통합 메모리 구조라 프레임버퍼 메모리 사용량 같은 메모리 필드가 “지원 안 됨”으로 나옵니다(7·8편). GPU 메모리 대시보드 대신 노드 메모리(node-exporter)와 엔진의 KV 사용률로 봅니다. 일부 프로파일링 필드(SM·DRAM 활성)의 지원 여부는 DCGM Exporter 로그와 실제 수집값으로 확인합니다(실습 20-6).

    06라우팅·게이트웨이 지표

    엔진 하나가 아니라 “풀”과 “테넌트”의 관점은 앞단에서만 보입니다.

    구성 요소지표 (예)답하는 질문
    EPP (llm-d Router)처리 중 요청(llm_d_epp_request_running), 준비된 엔드포인트, 스케줄링 지연, 흐름 제어 대기열·포화도풀 전체가 얼마나 찼나, 라우터가 병목인가, 몇 개 Pod에 보낼 수 있나 (11·18편)
    Envoy·Gateway업스트림 요청 수·응답 코드·지연, 연결 수입구에서의 오류·지연, 엔진 이전 단계의 문제
    AI 게이트웨이테넌트·키·모델별 요청·입력·출력 토큰, 비용, 429, 폴백, 공급자 오류·지연누가 얼마나 쓰나, 한도·폴백이 얼마나 일어나나, 외부 공급자가 느린가 (12편)

    게이트웨이 지표에는 테넌트 라벨이 붙으므로 라벨 수(카디널리티)에 주의합니다. 테넌트·모델 수준까지는 괜찮지만 사용자 ID·요청 ID를 라벨로 넣으면 Prometheus가 감당하지 못합니다. 그런 상세는 로그·트레이스(21편)로 보냅니다.

    07운영용 Prometheus 스택

    18편의 랩용 Prometheus를 운영 표준 구성으로 바꿉니다.

    구성 요소역할운영 포인트
    Prometheus OperatorPrometheus·Alertmanager·규칙을 CRD로 관리ServiceMonitor·PodMonitor·PrometheusRule로 선언적 관리
    ServiceMonitor · PodMonitor수집 대상 선언엔진·EPP·게이트웨이·DCGM을 각각 선언. 라벨 선택자 규칙 통일
    PrometheusRule기록 규칙·경보 규칙표준 이름의 기록 규칙(8장), 경보(23편)
    Grafana대시보드대시보드를 코드(JSON·ConfigMap)로 관리, 기록 규칙 기반
    node-exporter · kube-state-metrics노드·쿠버네티스 상태GB10 메모리는 node-exporter로
    장기 보관 (Thanos·Mimir·VictoriaMetrics 등)보존 기간 연장, 여러 클러스터 통합MSP 다중 고객·다중 클러스터에서 필요 (11장)
    • 수집 주기: 엔진 지표는 10~15초면 충분합니다. 너무 짧으면 엔진 API 서버에 부담이 됩니다.
    • 라벨 설계: cluster, namespace, model_name, variant(7편 오버레이), tenant(게이트웨이)를 표준 라벨로 정해 두면 모든 대시보드가 같은 변수로 움직입니다.
    • 보존 기간: 운영 대시보드는 2~4주, 용량 계획(19편)과 SLA 보고(26편)는 월·분기 단위 집계가 필요하므로 기록 규칙 결과를 장기 저장소에 보관합니다.
    • 네트워크 정책: 7편에서 만든 allow-monitoring 정책은 llm-lab/monitoring: "true" 라벨의 네임스페이스만 엔진 8000번 포트에 접근하게 합니다. 모니터링 네임스페이스에 이 라벨을 붙입니다.

    08기록 규칙

    무거운 쿼리를 미리 계산해 두고, 엔진 이름을 우리 표준 이름으로 바꾸는 층입니다.

    표준 이름 (예)계산 (vLLM 기준)쓰는 곳
    llm:ttft_seconds:p95histogram_quantile(0.95, sum by (le, model_name) (rate(vllm:time_to_first_token_seconds_bucket[5m])))개요 대시보드, SLO (21편)
    llm:itl_seconds:p95같은 방식으로 inter_token_latency_seconds개요, SLO
    llm:ttft_slo_ratioSLO 경계 버킷 이하 비율: rate(bucket{le="SLO"}) ÷ rate(count)SLO 달성률, 오류 예산 (21편)
    llm:requests:rate5msum by (model_name) (rate(vllm:request_success_total[5m]))트래픽, 용량 (19편)
    llm:output_tokens:rate5msum by (model_name) (rate(vllm:generation_tokens_total[5m]))처리량, 비용
    llm:queue:sumsum by (model_name) (vllm:num_requests_waiting)포화, 자동 확장 (18편)
    llm:kv_usage:maxmax by (model_name) (vllm:kv_cache_usage_perc)포화
    llm:preemptions:rate5msum by (model_name) (rate(vllm:num_preemptions_total[5m]))경보
    llm:prefix_hit_ratiorate(prefix_cache_hits_total) ÷ rate(prefix_cache_queries_total)효율 (15편)
    llm:tokens_per_gpu_second출력 토큰 rate ÷ 엔진 Pod가 쓰는 GPU 수효율·비용 (3편 토큰당 비용)

    le 값은 엔진이 노출하는 버킷 경계 중 하나여야 합니다. 경계가 SLO(예: 2.5초)와 다르면 가장 가까운 경계로 근사하게 되므로, 실제 버킷 경계를 /metrics에서 확인하고 SLO를 그 경계에 맞추거나 근사임을 표시합니다(10장).

    09대시보드 설계

    대시보드 하나에 모든 것을 넣지 않습니다. 질문 순서대로 내려가는 네 장으로 나눕니다.

    대시보드보는 사람핵심 패널
    ① 서비스 개요운영 당직, 고객 보고모델별 요청률·TTFT p95·ITL p95·오류율·SLO 달성률·레플리카 수
    ② 엔진 내부원인 분석실행·대기 요청, KV 사용률, 선점, 대기·Prefill·Decode 시간 분해, 캐시 적중, 스텝당 토큰, 요청 크기 분포
    ③ GPU·노드인프라SM·DRAM 활성, 전력·온도·스로틀, XID, 노드 메모리(GB10), Pod 재시작
    ④ 게이트웨이·테넌트·비용MSP 운영·영업테넌트별 토큰·비용·429·폴백, 공급자 지연, 예산 소진

    공통 변수(클러스터·네임스페이스·모델·변형)를 모든 대시보드에 같은 이름으로 두고, ①에서 이상한 모델을 클릭하면 같은 변수로 ②·③으로 넘어가도록 링크를 겁니다. 대시보드 JSON은 Git에 두고 ConfigMap으로 배포합니다(실습 20-5).

    Prometheus의 백분위는 “버킷 안에서 고르게 퍼져 있다고 가정한 추정값”입니다.

    오차—
    • 합친 뒤 계산: 여러 Pod의 p95를 평균 내지 말고, sum by (le)로 버킷을 합친 뒤 histogram_quantile을 씁니다.
    • 창 길이: rate(…[5m])의 창이 짧으면 요청이 적은 시간대에 값이 크게 흔들립니다(19편 표본 수 문제와 같음).
    • 버킷 밖: 가장 큰 버킷 경계를 넘는 값은 그 경계로 잘려 보입니다. 긴 요청의 E2E 지연이 이상하게 일정하면 버킷 상한을 의심합니다.
    • 네이티브 히스토그램: Prometheus 3의 네이티브(지수) 히스토그램은 고정 경계 문제를 줄여 줍니다. 엔진·수집기가 지원하는지 확인하고 도입을 검토합니다.

    11MSP 관점

    여러 고객의 지표를 한 체계로 운영하면서도 고객별로 분리해 보여 줘야 합니다.

    • 표준 지표 카탈로그: 고객 환경이 vLLM이든 SGLang이든 같은 표준 이름(기록 규칙)으로 대시보드·보고서를 만들면 운영팀이 하나의 화면으로 모든 고객을 봅니다.
    • 다중 클러스터 집계: 고객 클러스터마다 Prometheus를 두고, 기록 규칙 결과만 중앙 장기 저장소로 보내면 비용과 데이터 이동을 줄일 수 있습니다. 원본 지표의 반출 범위는 고객 보안 정책과 합의합니다.
    • 고객별 보기: 고객에게 제공하는 대시보드는 테넌트 라벨로 범위를 제한하고, 다른 고객의 지표가 보이지 않도록 권한을 분리합니다.
    • 보고서의 근거: 월간 SLA 보고(26편)의 숫자는 기록 규칙의 장기 보관값에서 나와야 재현 가능합니다.

    실습 20-3 · 표준 기록 규칙

    yaml · llm-recording-rules.yaml
    apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: { name: llm-recording-rules, namespace: monitoring }
spec:
  groups:
  - name: llm-serving.rules
    interval: 30s
    rules:
    # 엔진 이름이 바뀌면 이 파일의 expr만 고친다. 대시보드·경보·자동 확장은 왼쪽 표준 이름만 쓴다.
    - record: llm:requests:rate5m
      expr: sum by (namespace, model_name) (rate(vllm:request_success_total[5m]))
    - record: llm:output_tokens:rate5m
      expr: sum by (namespace, model_name) (rate(vllm:generation_tokens_total[5m]))
    - record: llm:input_tokens:rate5m
      expr: sum by (namespace, model_name) (rate(vllm:prompt_tokens_total[5m]))
    - record: llm:ttft_seconds:p95
      expr: histogram_quantile(0.95, sum by (le, namespace, model_name) (rate(vllm:time_to_first_token_seconds_bucket[5m])))
    - record: llm:itl_seconds:p95
      expr: histogram_quantile(0.95, sum by (le, namespace, model_name) (rate(vllm:inter_token_latency_seconds_bucket[5m])))
    - record: llm:e2e_seconds:p95
      expr: histogram_quantile(0.95, sum by (le, namespace, model_name) (rate(vllm:e2e_request_latency_seconds_bucket[5m])))
    - record: llm:queue_time_seconds:p95
      expr: histogram_quantile(0.95, sum by (le, namespace, model_name) (rate(vllm:request_queue_time_seconds_bucket[5m])))
    - record: llm:queue:sum
      expr: sum by (namespace, model_name) (vllm:num_requests_waiting)
    - record: llm:running:sum
      expr: sum by (namespace, model_name) (vllm:num_requests_running)
    - record: llm:kv_usage:max
      expr: max by (namespace, model_name) (vllm:kv_cache_usage_perc)
    - record: llm:preemptions:rate5m
      expr: sum by (namespace, model_name) (rate(vllm:num_preemptions_total[5m]))
    - record: llm:prefix_hit_ratio
      expr: sum by (namespace, model_name) (rate(vllm:prefix_cache_hits_total[5m])) / clamp_min(sum by (namespace, model_name) (rate(vllm:prefix_cache_queries_total[5m])), 1)
    # SLO 달성률: le 값은 엔진의 실제 버킷 경계 중 SLO에 맞는 값으로 (실습 20-4에서 확인)
    - record: llm:ttft_slo_ratio
      expr: sum by (namespace, model_name) (rate(vllm:time_to_first_token_seconds_bucket{le="2.5"}[5m])) / clamp_min(sum by (namespace, model_name) (rate(vllm:time_to_first_token_seconds_count[5m])), 1e-9)
    - record: gpu:sm_active:avg
      expr: avg by (Hostname, gpu) (DCGM_FI_PROF_SM_ACTIVE)
    - record: gpu:dram_active:avg
      expr: avg by (Hostname, gpu) (DCGM_FI_PROF_DRAM_ACTIVE)

    실습 20-4 · 업그레이드 대비 지표 점검

    python · metric_inventory.py (bench Pod에서)
    """엔진 /metrics의 지표 이름 목록을 저장하고, 표준 기록 규칙이 쓰는 이름이 모두 있는지 확인한다.
사용: python metric_inventory.py [엔진 주소] [저장 파일]   두 버전의 파일을 diff 하면 변경 목록."""
import re, sys, urllib.request
base = sys.argv[1] if len(sys.argv) > 1 else "http://llm-engine:8000"
out = sys.argv[2] if len(sys.argv) > 2 else "/results/metrics-inventory.txt"
txt = urllib.request.urlopen(base + "/metrics", timeout=10).read().decode()
families = sorted(set(m.group(1) for m in re.finditer(r"^# TYPE (\S+) (\w+)", txt, re.M)))
buckets = sorted(set(re.findall(r'vllm:time_to_first_token_seconds_bucket\{[^}]*le="([^"]+)"', txt)), key=lambda x: float(x) if x != "+Inf" else 1e9)
REQUIRED = ["vllm:request_success", "vllm:generation_tokens", "vllm:prompt_tokens", "vllm:time_to_first_token_seconds",
            "vllm:inter_token_latency_seconds", "vllm:e2e_request_latency_seconds", "vllm:request_queue_time_seconds",
            "vllm:num_requests_waiting", "vllm:num_requests_running", "vllm:kv_cache_usage_perc",
            "vllm:num_preemptions", "vllm:prefix_cache_hits", "vllm:prefix_cache_queries"]
names = set(families) | set(f.removesuffix("_total") for f in families)
missing = [r for r in REQUIRED if r not in names]
open(out, "w").write("\n".join(families) + "\n")
print(f"지표 패밀리 {len(families)}개 저장: {out}")
print("TTFT 버킷 경계:", ", ".join(buckets))
print("기록 규칙에 필요한데 없는 지표:", missing or "없음")

    15확인 퀴즈

    9문제.

    16정리와 체크리스트

    핵심 여섯 문장.

    1. 층 × 황금 신호로 지표를 정리하고, 사용자 체감에서 원인으로 내려간다.
    2. vLLM 지표는 원인 분석의 중심: 실행·대기, KV, 선점, 지연 분해(대기·Prefill·Decode), 캐시 적중, 요청 크기.
    3. 지표 이름은 바뀐다. 기록 규칙을 표준 이름 층으로 두고, 업그레이드 때 이름 목록을 점검한다.
    4. GPU 사용률보다 SM·DRAM 활성, 전력·스로틀·XID를 본다. GB10은 메모리 필드 대신 노드 메모리.
    5. 운영 스택은 Operator + PodMonitor + PrometheusRule + 코드화된 대시보드, 라벨 표준과 카디널리티 관리, 장기 보관.
    6. 히스토그램은 버킷을 합친 뒤 백분위, 버킷 경계와 SLO를 맞춘다.
