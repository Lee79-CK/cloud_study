01모든 네트워크가 답해야 하는 다섯 가지 질문

클라우드든 온프레미스든, 네트워크를 설계한다는 건 결국 다섯 개의 질문에 답을 채워 넣는 일입니다. 이 다섯 칸만 채우면 어떤 환경이든 설명할 수 있고, 반대로 낯선 환경에 던져졌을 때도 이 다섯 개만 물어보면 구조가 잡힙니다.

질문 1 — 주소는 누가, 어떻게 주는가

통신하려면 모두가 주소를 가져야 합니다. 누가 주소 대역을 정하고, 개별 장비에는 어떻게 배분되는지가 첫 번째 질문입니다. AWS·Azure는 서브넷 대역에서 자동으로 꺼내 주고, 쿠버네티스는 CNI의 IPAM이 파드마다 하나씩 떼어 주며, 온프레미스는 사람이 엑셀이나 IPAM 도구로 관리합니다.

질문 2 — 경계는 어디까지인가

“한 덩어리”로 취급되는 범위가 어디까지인지입니다. AWS의 VPC, Azure의 VNet, 쿠버네티스의 클러스터, 온프레미스의 VLAN·존이 각각 그 경계입니다. 경계 안에서는 대체로 자유롭게 통신되고, 경계를 넘으려면 별도 장치가 필요합니다.

질문 3 — 길은 누가 정하는가

목적지 IP를 보고 어디로 보낼지 결정하는 주체입니다. 클라우드는 라우트 테이블이라는 설정 화면이고, 쿠버네티스는 노드의 커널 라우팅 테이블과 CNI이며, 온프레미스는 라우터와 L3 스위치가 OSPF·BGP로 서로 학습합니다.

질문 4 — 누가 막는가

허용·차단을 판단하는 지점입니다. 보안 그룹, NSG, NetworkPolicy, 물리 방화벽이 여기에 해당합니다. “기본이 허용인가 차단인가”와 “상태를 기억하는가” 두 가지만 확인하면 절반은 이해한 겁니다.

질문 5 — 바깥과는 어떻게 잇는가

인터넷, 다른 네트워크, 사내 데이터센터와 연결하는 방법입니다. 인터넷 게이트웨이, NAT, VPN, 전용선, 피어링이 모두 이 질문의 답입니다. 실무 장애의 상당수가 이 칸을 비워 두었거나 반쯤 채워서 생깁니다.

계층을 알면 장비 이름이 정리됩니다

네트워크 장비를 외우기 어려운 건 이름이 많아서가 아니라, 각 장비가 패킷의 어느 부분을 보는지를 모르기 때문입니다. L2 장비는 MAC 주소만, L3 장비는 IP까지, L4 장비는 포트 번호까지, L7 장비는 HTTP 헤더와 URL까지 봅니다. 아래 표에 네 환경의 장비를 계층별로 올려놓으면 대응 관계가 바로 보입니다.

02주소 · 서브넷 · CIDR

여기는 네 환경 모두에 똑같이 적용되는 기초입니다. 이 절이 헷갈리면 뒤의 모든 장이 흔들리니, 이미 안다고 생각해도 한 번 훑고 가세요. 현장 장애의 체감 30%는 “대역을 잘못 잡아서”입니다.

CIDR 표기를 읽는 법

10.0.0.0/16 같은 표기에서 슬래시 뒤 숫자는 앞에서부터 몇 비트가 네트워크 주소인지를 뜻합니다. IPv4 주소는 32비트이므로, /16이면 앞 16비트가 네트워크, 나머지 16비트가 호스트 몫입니다. 숫자가 작을수록 큰 대역이라는 점이 처음엔 직관에 어긋나는데, “자물쇠를 몇 칸 잠갔는가”로 생각하면 쉽습니다. 적게 잠글수록 자유로운 칸이 많아집니다.

사설 IP 대역 — 이 세 개만 기억하면 됩니다

인터넷에 직접 나가지 않는 내부망에는 RFC 1918이 정한 사설 대역을 씁니다. 전 세계 누구나 이 대역을 자유롭게 쓰므로, 회사끼리 연결할 때 대역이 겹치는 사고가 끊이지 않습니다.

10.0.0.0/8

1,600만 개. 대기업·클라우드 기본값. AWS·Azure 예제가 대부분 10.으로 시작하는 이유입니다.

172.16.0.0/12

100만 개. 172.16부터 172.31까지만 사설입니다. 172.32는 공인 대역이니 주의하세요.

192.168.0.0/16

65,536개. 가정용 공유기의 기본값이라, 사내 VPN을 쓰는 직원 집 대역과 충돌하기 쉽습니다.

가장 비싼 실수: 대역 겹침 10.0.0.0/16은 예제에서 하도 많이 써서 거의 모든 회사가 하나쯤 갖고 있습니다. 나중에 VPC 피어링이나 VPN으로 두 망을 잇는 순간, 겹친 대역은 라우팅이 불가능해집니다. 이때 할 수 있는 건 한쪽을 통째로 재구축하거나 NAT를 이중으로 거는 것뿐이고, 둘 다 몇 주짜리 작업입니다. 처음부터 회사 전체 대역 관리표를 만들고, 환경(운영/개발), 리전, 용도까지 자리를 정해 두세요. 예: 10.10.x.x=서울 운영, 10.20.x.x=서울 개발, 10.30.x.x=온프레미스.

03직접 해 보는 CIDR 계산

말로 백 번 듣는 것보다 숫자를 한 번 바꿔 보는 게 빠릅니다. 대역과 프리픽스를 바꿔 가며 비트가 어떻게 나뉘는지, 쓸 수 있는 IP가 몇 개로 줄어드는지 확인해 보세요.

서브넷을 쪼개는 실전 감각

VPC 대역 10.10.0.0/16 하나를 받았다고 합시다. 여기서 가용 영역 3개 × 계층 3개(퍼블릭·앱·DB)로 9개 서브넷을 만들어야 합니다. 이때 흔히 저지르는 실수가 “필요한 만큼만 딱 맞게” 자르는 것입니다. 나중에 넓힐 수 없다는 걸 기억하세요. 서브넷 대역은 만든 뒤 변경이 불가능합니다.

권장 배치 예시 — 10.10.0.0/16

10.10.0.0/24    ap-northeast-2a  public-a

10.10.16.0/20   ap-northeast-2a  app-a      # 4,091개
10.10.32.0/20   ap-northeast-2b  app-b
10.10.48.0/20   ap-northeast-2c  app-c

# DB — 인스턴스 수가 예측 가능하므로 작게

# 10.10.80.0 ~ 10.10.255.255 는 비워 둡니다 (미래의 나를 위한 선물)
비워 두는 습관 대역의 절반 정도는 의도적으로 비워 두세요. 몇 달 뒤 “EKS 클러스터를 추가해야 한다”, “전용선 연결용 서브넷이 필요하다”는 요청이 반드시 옵니다. 그때 빈 칸이 없으면 새 VPC를 만들고 피어링으로 붙이는 복잡한 구조로 가게 됩니다.

04라우팅 · NAT · DNS

주소를 나눠 줬으면 이제 길을 알려 줘야 합니다. 이 세 가지는 이름만 다를 뿐 네 환경에서 똑같이 동작하는 원리이고, 신입이 가장 자주 헤매는 지점이기도 합니다.

라우팅 — 가장 구체적인 경로가 이깁니다

라우트 테이블은 “이 목적지로 가려면 저리로 보내라”는 규칙의 목록입니다. 규칙이 여러 개 걸리면 프리픽스가 더 긴(= 더 구체적인) 쪽이 무조건 이깁니다. 이걸 최장 일치(longest prefix match)라고 부릅니다.

10.10.5.20 으로 가는 패킷은 어느 규칙을 탈까
목적지               다음 홉          프리픽스 길이
0.0.0.0/0            NAT 게이트웨이    0     ← 매치되지만 가장 짧음
10.10.0.0/16         local            16    ← 매치, 더 구체적
10.10.5.0/24         피어링 연결       24    ← 매치, 가장 구체적 → 승리

결과: 10.10.5.20 행 패킷은 피어링 연결로 나갑니다.

0.0.0.0/0은 “나머지 전부”라는 뜻이고 기본 경로(default route)라고 부릅니다. 항상 지는 규칙이지만, 아무 규칙도 안 걸렸을 때 마지막으로 받아 주는 역할이라 없으면 인터넷에 못 나갑니다. local은 “내 네트워크 안이니 밖으로 보내지 말라”는 뜻으로, 클라우드에서는 자동으로 들어가 있고 지울 수 없습니다.

AWS는 서브넷에 붙입니다

라우트 테이블을 만들고 서브넷에 연결합니다. 같은 테이블을 여러 서브넷이 공유할 수 있고, 연결을 안 하면 VPC의 메인 라우트 테이블이 적용됩니다. “퍼블릭 서브넷”이라는 리소스 종류는 없습니다. 0.0.0.0/0 → IGW 를 가진 라우트 테이블이 붙어 있으면 퍼블릭, 그게 전부입니다.

Azure는 기본이 이미 깔려 있습니다

VNet을 만들면 보이지 않는 시스템 라우트가 자동 생성되어 인터넷과 VNet 내부 통신이 이미 됩니다. 기본 동작을 바꾸고 싶을 때만 사용자 정의 라우트(UDR)를 만들어 서브넷에 붙입니다. “방화벽을 반드시 거치게 하라” 같은 요구가 UDR의 대표 용도입니다.

NAT — 주소를 갈아 끼우는 일

사설 IP는 인터넷에서 통하지 않습니다. 그래서 밖으로 나갈 때 출발지 주소를 공인 IP로 바꿔치기하는데, 이게 NAT입니다. 방향에 따라 이름이 다릅니다.

  • SNAT (출발지 NAT) — 안에서 밖으로. 내부 서버가 인터넷의 패키지 저장소에서 다운로드할 때 씁니다. AWS·Azure의 NAT 게이트웨이, 쿠버네티스의 노드 마스커레이드, 방화벽의 PAT가 전부 이것입니다.
  • DNAT (목적지 NAT) — 밖에서 안으로. 로드밸런서가 VIP:443으로 온 패킷의 목적지를 실제 서버 IP로 바꾸는 동작이 DNAT입니다. 쿠버네티스의 Service도 본질은 DNAT입니다.
포트 고갈이라는 함정 NAT는 출발지 포트 번호로 세션을 구분합니다. 공인 IP 하나당 쓸 수 있는 포트는 약 64,000개인데, 목적지가 같은 IP:포트라면 한 목적지에 대해 약 64,000 세션이 한계입니다. AWS NAT 게이트웨이의 ErrorPortAllocation 지표나 Azure NAT 게이트웨이의 SNAT 고갈이 바로 이 증상이고, “가끔 연결이 안 돼요”의 흔한 원인입니다. 해결은 공인 IP를 늘리거나, 외부 호출을 커넥션 풀로 재사용하거나, VPC 엔드포인트로 NAT를 우회하는 것입니다.

DNS — 이름이 곧 계약

IP는 바뀌지만 이름은 유지됩니다. 그래서 요즘 아키텍처는 “IP를 코드에 적지 않는다”가 원칙이고, 이걸 가능하게 하는 게 DNS입니다. 네 환경 모두 내부용 DNS와 외부용 DNS를 구분합니다.

05로드밸런서 — L4와 L7의 차이

“ALB를 써야 하나 NLB를 써야 하나”는 신입이 가장 많이 받는 질문 중 하나입니다. 답은 언제나 “패킷의 어디까지 봐야 하는가”에서 나옵니다.

L4 로드밸런서 — 봉투만 보고 배달

출발지·목적지 IP와 포트만 보고 서버를 고릅니다. 안의 내용은 열어 보지 않습니다.

  • 빠르고 지연이 거의 없습니다
  • TCP·UDP 어떤 프로토콜이든 처리합니다
  • URL 기반 분기, 쿠키 세션 유지는 불가능합니다
  • 클라이언트 IP를 그대로 넘기기 쉽습니다

쓰는 경우: 게임 서버, DB 프록시, gRPC, 초저지연이 필요한 서비스, 고정 IP가 필요한 경우

L7 로드밸런서 — 봉투를 열어 보고 배달

HTTP 요청을 해석해 호스트·경로·헤더를 보고 서버를 고릅니다. 자기가 요청을 다시 만들어 보냅니다.

  • /api는 A그룹, /img는 B그룹으로 분기 가능
  • TLS 종료, 인증, 압축, 재시도, 헤더 조작 가능
  • L4보다 느리고 리소스를 더 씁니다
  • 클라이언트 IP는 X-Forwarded-For 헤더로 전달됩니다

쓰는 경우: 일반적인 웹 서비스, 마이크로서비스 라우팅, WAF가 필요한 경우

앱 로그에 로드밸런서 IP만 찍힌다면 L7 로드밸런서를 쓰면 백엔드 입장에서 출발지 IP는 항상 로드밸런서입니다. 실제 사용자 IP는 X-Forwarded-For 헤더 안에 들어 있으니, 앱이나 웹서버 설정에서 이 헤더를 읽도록 바꿔야 합니다(NGINX의 real_ip_header, Tomcat의 RemoteIpValve). 접속 IP 기반 차단이나 감사 로그를 쓰는 곳이라면 반드시 확인하세요. 헤더를 그대로 믿어서도 안 됩니다 — 신뢰하는 프록시에서 온 값만 받도록 설정해야 사용자가 헤더를 위조해 IP 차단을 우회하는 걸 막을 수 있습니다.

헬스체크 — 로드밸런서의 눈

로드밸런서는 주기적으로 각 백엔드에 “살아 있니?”를 물어보고, 답이 없으면 명단에서 뺍니다. 이게 헬스체크이고, 네 환경 모두 같은 개념입니다. 실무에서 문제가 되는 건 대개 무엇을 확인하느냐입니다.

  • TCP 헬스체크는 포트가 열렸는지만 봅니다. 앱이 죽어 있어도 웹서버가 살아 있으면 통과해 버립니다.
  • HTTP 헬스체크는 특정 경로에 200이 오는지 봅니다. 그 경로가 /면 메인 페이지 전체를 렌더링하느라 무거워집니다. /healthz 같은 가벼운 전용 경로를 따로 만드세요.
  • DB까지 확인하는 헬스체크는 위험합니다. DB가 잠깐 느려지면 모든 서버가 동시에 명단에서 빠져 서비스 전체가 멈춥니다.
헬스체크 경로는 두 개로 나누세요 쿠버네티스가 정리한 이 구분은 다른 환경에서도 그대로 쓸 만합니다. liveness는 “프로세스가 살아 있나”만 보고 실패하면 재시작, readiness는 “지금 요청을 받을 준비가 됐나”를 보고 실패하면 트래픽만 끊습니다. 부팅에 시간이 걸리는 앱이라면 startup까지 셋으로 나누세요. 로드밸런서의 헬스체크는 readiness에 해당합니다.

06AWS — VPC로 짓는 네트워크

AWS 네트워크의 핵심 문장은 하나입니다. “서브넷이 모든 것의 단위다.” 가용 영역도 서브넷에 붙고, 라우팅도 서브넷에 붙고, 인터넷에 나갈 수 있는지도 서브넷에 붙은 라우트 테이블이 결정합니다. 이 한 문장을 잡고 가면 나머지는 자연스럽게 따라옵니다.

VPC 서브넷 라우트 테이블 IGW · NAT GW 보안 그룹 · NACL ELB VPC 엔드포인트 TGW · DX

전체 구조 한눈에

퍼블릭 서브넷과 프라이빗 서브넷은 리소스 종류가 아닙니다

콘솔 어디에도 “퍼블릭 서브넷 만들기” 버튼은 없습니다. 서브넷은 다 똑같고, 어떤 라우트 테이블이 붙어 있느냐로 성격이 정해집니다.

서브넷의 성격을 결정하는 건 라우트 테이블 한 줄
# 퍼블릭이 되는 조건
10.10.0.0/16   local
0.0.0.0/0      igw-0a1b2c3d      ← 이 한 줄 때문에 퍼블릭

# 프라이빗 — 나가기는 하지만 밖에서 들어올 수는 없음
10.10.0.0/16   local
0.0.0.0/0      nat-0a1b2c3d      ← NAT를 거치므로 단방향

# 격리 — DB용. 인터넷과 완전 차단
10.10.0.0/16   local
(기본 경로 없음)
EC2에 공인 IP가 있어도 IGW가 없으면 못 나갑니다 퍼블릭 IP를 붙였는데 인터넷이 안 된다는 신고의 90%는 이 셋 중 하나입니다. ① 서브넷의 라우트 테이블에 0.0.0.0/0 → IGW가 없다, ② 보안 그룹 아웃바운드가 막혀 있다, ③ NACL이 돌아오는 임시 포트(1024~65535)를 막고 있다. 이 순서대로 확인하면 거의 다 잡힙니다.

보안 그룹과 NACL — 둘 다 통과해야 합니다

AWS에는 방화벽이 두 겹 있습니다. 신입이 가장 혼란스러워하는 부분인데, 실무에서는 거의 항상 보안 그룹만 쓰고 NACL은 기본값 그대로 둡니다. 그래도 차이는 알아야 장애를 잡을 수 있습니다.

보안 그룹의 진짜 강점: SG를 출발지로 쓰기 DB 보안 그룹에 3306 허용, 출발지 = sg-web이라고 적으면, 웹 서버가 몇 대로 늘어나든 IP가 바뀌든 규칙을 고칠 필요가 없습니다. IP 대신 역할로 정책을 쓰는 것이고, 쿠버네티스의 NetworkPolicy가 라벨로 하는 일과 똑같습니다. CIDR을 하드코딩한 보안 그룹을 보면 대부분 개선 여지가 있습니다.

세 가지 로드밸런서

ALB — 애플리케이션

L7. HTTP/HTTPS와 gRPC. 호스트·경로·헤더 기반 분기, WAF 연동, Cognito 인증까지.

IP가 바뀝니다. 고정 IP가 필요한 고객사 방화벽 등록에는 부적합합니다.

NLB — 네트워크

L4. TCP·UDP·TLS. 초고성능, 낮은 지연. AZ마다 고정 IP를 줄 수 있습니다.

클라이언트 IP가 그대로 보존되므로 백엔드 보안 그룹은 클라이언트 IP를 허용해야 합니다.

GWLB — 게이트웨이

L3. 방화벽·IDS 같은 보안 어플라이언스를 트래픽 경로에 끼워 넣을 때 씁니다.

일반 웹 서비스에서는 쓸 일이 거의 없습니다. 있다는 것만 알아 두세요.

VPC 엔드포인트 — NAT 요금을 줄이는 지름길

프라이빗 서브넷의 서버가 S3에 파일을 올린다고 해 봅시다. 기본 경로대로면 NAT 게이트웨이를 거쳐 인터넷으로 나갔다가 다시 AWS로 들어옵니다. 같은 AWS 안인데 굳이 인터넷을 한 바퀴 도는 셈이고, NAT 처리 요금이 GB당 붙습니다. VPC 엔드포인트는 이 경로를 AWS 내부로 직결시킵니다.

게이트웨이 엔드포인트 — 무료

S3와 DynamoDB 두 개만 지원합니다. 라우트 테이블에 경로가 추가되는 방식이고, 요금이 없습니다. 안 만들 이유가 없으니 VPC를 만들 때 세트로 넣으세요.

인터페이스 엔드포인트 (PrivateLink)

서브넷 안에 ENI가 생기고 사설 IP가 부여됩니다. 대부분의 AWS 서비스와 다른 계정의 서비스까지 연결할 수 있습니다. 시간당 + 데이터 처리 요금이 있으니 실제로 트래픽이 많은 서비스에만 거세요.

다른 네트워크와 잇기

방법연결 대상특징과 주의점
VPC 피어링VPC ↔ VPC1:1 직결. 저렴하고 빠릅니다. 전이가 안 됩니다 — A-B, B-C가 있어도 A는 C와 통신 못 합니다. VPC가 4~5개를 넘으면 연결 수가 폭발합니다.
Transit GatewayVPC 다수 + VPN + DX허브 역할. VPC가 많아지면 정답입니다. 대신 연결당 시간 요금 + 데이터 처리 요금이 붙어 비용이 만만치 않습니다.
Site-to-Site VPN온프레미스인터넷 위에 IPsec 터널. 빠르게 구축되고 저렴하지만 대역폭과 지연이 인터넷에 좌우됩니다. 터널 2개로 이중화하세요.
Direct Connect온프레미스전용 물리 회선. 안정적이고 데이터 전송 요금이 쌉니다. 대신 신청부터 개통까지 몇 주~몇 달 걸립니다. 보통 DX + VPN 백업 조합으로 갑니다.
PrivateLink특정 서비스만네트워크를 통째로 잇지 않고 서비스 하나만 노출합니다. 대역 겹침 문제가 없어 SaaS 제공·구독에 적합합니다.
피어링은 전이되지 않습니다 이 규칙을 몰라서 생기는 문의가 정말 많습니다. VPC A–B를 잇고 B–C를 이었다고 A에서 C로 통신되지 않습니다. 중간의 B가 라우터 역할을 해 주지 않기 때문입니다. VPC 세 개까지는 피어링 세 개로 버티지만, 다섯 개면 열 개가 필요하고, 그때는 이미 Transit Gateway로 갔어야 합니다.

07Azure — VNet으로 짓는 네트워크

AWS를 먼저 배운 사람에게 Azure는 “비슷한데 미묘하게 다른” 느낌을 줍니다. 그 미묘함이 장애로 이어지니, 다른 점을 콕 집어 정리하고 갑니다. Azure의 핵심 문장은 “기본값이 관대한 대신, 리소스가 잘게 쪼개져 있다”입니다.

VNet 서브넷 NSG · ASG UDR Load Balancer · App Gateway Private Endpoint Virtual WAN · ExpressRoute

리소스가 잘게 쪼개져 있다는 것의 의미

AWS에서 EC2를 만들면 ENI와 공인 IP가 딸려 옵니다. Azure에서는 VM, NIC, 공용 IP, 디스크가 전부 독립된 리소스입니다. 처음엔 번거롭지만 장점도 뚜렷합니다. VM을 지워도 NIC과 공용 IP는 남아서, 같은 IP로 새 VM을 붙일 수 있습니다. 반대로 지웠다고 생각한 공용 IP가 계속 과금되는 일도 흔합니다.

Azure의 리소스 계층 구조
구독 (Subscription)          ← 과금과 할당량의 단위
└─ 리소스 그룹 (Resource Group)   ← 생명주기를 함께하는 묶음. 지우면 통째로 사라짐
   ├─ 가상 네트워크 (VNet)       10.20.0.0/16
   │  ├─ 서브넷 snet-web         10.20.1.0/24
   │  └─ 서브넷 snet-db          10.20.2.0/24
   ├─ 네트워크 보안 그룹 (NSG)     ← 서브넷 또는 NIC에 연결
   ├─ 네트워크 인터페이스 (NIC)     ← VM과 별개 리소스
   ├─ 공용 IP 주소              ← NIC이나 LB에 붙이는 별도 리소스
   └─ 가상 머신 (VM)

# 주의: VNet은 리전에 속하고, 리소스 그룹은 리전과 무관합니다.
#       서울 리소스 그룹 안에 도쿄 VNet을 넣는 것도 가능합니다(권장하진 않음).

NSG — 우선순위 번호가 전부입니다

Azure의 방화벽은 NSG 하나입니다. AWS처럼 두 겹이 아니라 한 겹이지만, 서브넷과 NIC 양쪽에 붙일 수 있어서 결과적으로 두 번 평가될 수 있습니다. 둘 다 붙어 있으면 인바운드는 서브넷 → NIC 순으로, 아웃바운드는 NIC → 서브넷 순으로 평가되고 양쪽 모두 허용해야 통과합니다.

  • 규칙마다 100~4096의 우선순위 번호를 부여하고, 낮은 번호부터 평가합니다.
  • 처음 매치되는 규칙에서 판단이 끝납니다. 아래 규칙은 보지 않습니다.
  • SG와 달리 거부(Deny) 규칙을 쓸 수 있습니다.
  • 상태 저장 방식이라 AWS의 SG처럼 응답 트래픽은 자동 허용됩니다.
기본 규칙 — 지울 수 없고, 번호로 덮어쓰는 것만 가능
인바운드
 65000  AllowVnetInBound              VirtualNetwork → VirtualNetwork   Allow
 65001  AllowAzureLoadBalancerInBound AzureLoadBalancer → Any           Allow
 65500  DenyAllInBound                Any → Any                         Deny

아웃바운드
 65000  AllowVnetOutBound             VirtualNetwork → VirtualNetwork   Allow
 65001  AllowInternetOutBound         Any → Internet                    Allow
 65500  DenyAllOutBound               Any → Any                         Deny

# 읽는 법:
#  · VNet 안에서는 서브넷이 달라도 기본적으로 다 통합니다 (65000번)
#  · 아웃바운드는 기본 허용입니다 (65001번)
#  · 막으려면 65000보다 낮은 번호로 Deny 규칙을 추가해야 합니다
AWS 출신이 가장 많이 놀라는 지점 Azure는 같은 VNet 안이면 서브넷이 달라도 기본적으로 통신됩니다. AWS는 서브넷 간 통신도 보안 그룹에서 허용해야 하지만, Azure는 AllowVnetInBound가 이미 열어 두고 있습니다. “DB 서브넷을 분리했으니 안전하다”고 생각했는데 같은 VNet의 모든 서브넷에서 접근 가능한 상태인 경우가 흔합니다. 분리하려면 명시적으로 Deny 규칙을 써야 합니다.

ASG — 라벨로 방화벽 쓰기

AWS의 “SG를 출발지로 참조하기”에 해당하는 기능이 Azure에서는 애플리케이션 보안 그룹(ASG)입니다. VM의 NIC에 ASG 태그를 붙여 두고, NSG 규칙에서 IP 대신 ASG 이름을 씁니다.

IP를 하드코딩하지 않는 NSG 규칙
규칙: allow-web-to-db
  우선순위      : 200
  출발지        : asg-web        ← IP가 아니라 그룹 이름
  목적지        : asg-db
  포트          : 3306
  동작          : Allow

기본 아웃바운드 폐지 — 2025년 9월 30일

최근 변경이라 오래된 문서·블로그와 다릅니다

예전 Azure에서는 VM을 만들면 아무 설정 없이도 인터넷에 나갈 수 있었습니다. Azure가 보이지 않는 공용 IP를 임시로 빌려줬기 때문입니다. 2025년 9월 30일부로 이 기본 동작이 폐지되었습니다.

  • 그 이전부터 쓰던 VNet의 기존 VM은 계속 동작합니다.
  • 하지만 그 이후에 만든 VM은 명시적 아웃바운드 수단이 없으면 인터넷에 못 나갑니다.
  • 명시적 수단은 세 가지입니다: NAT 게이트웨이(권장), 표준 Load Balancer의 아웃바운드 규칙, NIC에 직접 붙인 공용 IP.
  • 증상은 “VM은 만들어졌는데 apt update가 멈춘다”입니다. 신규 구축에서 자주 보게 됩니다.

쿠버네티스 네트워크가 어렵게 느껴지는 이유는 딱 하나입니다. 쿠버네티스 자신은 네트워크를 구현하지 않습니다. 규격만 정해 두고 실제 구현은 CNI 플러그인에게 맡깁니다. 그래서 같은 YAML을 써도 Calico 클러스터와 Cilium 클러스터의 동작이 다를 수 있습니다. 이 사실을 받아들이고 나면 나머지는 논리적입니다.

쿠버네티스가 정한 네 가지 약속

쿠버네티스는 CNI 구현체에게 다음 네 가지만 지키라고 요구합니다. 어떻게 지키는지는 상관하지 않습니다.

  1. 모든 파드는 고유한 IP를 갖는다. 포트 매핑 같은 건 없습니다.
  2. 모든 파드는 NAT 없이 서로 통신할 수 있다. 노드가 달라도 마찬가지입니다.
  3. 노드의 에이전트는 그 노드의 모든 파드와 통신할 수 있다.
  4. 파드가 보는 자기 IP와 남이 보는 그 파드의 IP가 같다.

이 약속 덕분에 쿠버네티스 네트워크는 “하나의 평평한 네트워크”처럼 보입니다. 도커의 포트 매핑(-p 8080:80)이 없는 이유이기도 합니다.

세 개의 IP 대역을 구분하세요

노드 IP

실제 VM이나 서버의 주소. VPC·VNet 서브넷이나 물리 VLAN에서 받습니다.

10.10.16.0/20 같은 대역. 클러스터 밖에서도 보입니다.

파드 CIDR

파드에 주는 주소. 클러스터를 만들 때 --pod-network-cidr로 정합니다.

10.244.0.0/16 같은 대역. 보통 클러스터 안에서만 유효합니다.

서비스 CIDR

ClusterIP에 주는 가상 주소. 실제로 존재하지 않는 IP입니다.

10.96.0.0/12 같은 대역. ping이 안 되는 게 정상입니다.

가장 흔한 초기 구축 사고 이 세 대역 중 하나라도 기존 사내망이나 VPC 대역과 겹치면 반드시 터집니다. 기본값 10.244.0.0/16, 10.96.0.0/12를 그대로 쓰다가 나중에 온프레미스와 VPN을 연결하는 순간 10.96.x.x대의 사내 서버로 못 가게 됩니다. 클러스터를 만들기 전에 세 대역을 회사 IP 관리표에 등록하세요. 만든 뒤에는 클러스터를 다시 세우는 것 말고 방법이 없습니다.

패킷이 클러스터 안에서 지나는 길

CNI — 오버레이냐 라우팅이냐

노드가 다른 파드끼리 통신할 때 CNI가 쓰는 방법은 크게 두 갈래입니다. 이 선택이 성능과 디버깅 난이도를 결정합니다.

오버레이 — 원래 패킷을 한 번 더 감싸기

파드 패킷을 VXLAN이나 IP-in-IP로 감싸 노드 IP로 배달합니다. 밑에 깔린 네트워크는 파드 대역을 몰라도 됩니다.

  • 어디서든 동작합니다. 물리망을 건드릴 필요가 없습니다.
  • 헤더가 붙으므로 실제 쓸 수 있는 MTU가 줄어듭니다(VXLAN은 50바이트).
  • tcpdump로 잡으면 껍데기만 보여 디버깅이 번거롭습니다.

Flannel(VXLAN), Calico(IPIP/VXLAN 모드)

라우팅 — 밑단 네트워크에 파드 대역을 알리기

“10.244.1.0/24는 노드1에 있다”를 물리 라우터나 VPC 라우트 테이블에 직접 등록합니다.

  • 캡슐화가 없어 성능 손실이 거의 없습니다.
  • 패킷이 그대로 보여 디버깅이 쉽습니다.
  • 밑단 네트워크의 협조가 필요합니다(BGP 피어링 또는 클라우드 연동).

Calico(BGP 모드), Cilium(네이티브 라우팅), AWS VPC CNI

관리형 클러스터는 제3의 길을 씁니다 EKS의 AWS VPC CNI는 파드에 VPC 서브넷의 IP를 직접 줍니다. 파드 CIDR이라는 개념이 따로 없고, 파드가 곧 VPC의 일급 시민이 됩니다. 보안 그룹을 파드에 걸 수 있다는 강력한 장점이 있지만, 서브넷 IP가 빠르게 고갈된다는 대가가 따릅니다. 노드 타입별로 최대 파드 수가 ENI 개수에 묶이는 것도 여기서 나옵니다. AKS도 비슷하게 Azure CNI(VNet IP 직접 할당)와 kubenet(오버레이) 중 고를 수 있습니다.

# 다른 파드에서 호출하는 방법
#   같은 네임스페이스면      http://api
#   다른 네임스페이스면      http://api.prod
#   완전한 이름(권장)       http://api.prod.svc.cluster.local

모든 노드의 특정 포트를 열어 외부에 노출합니다. 기본 범위는 30000~32767입니다. 개발·테스트에는 편하지만 운영에는 잘 쓰지 않습니다. 노드 IP를 클라이언트가 알아야 하고, 노드가 죽으면 그 IP로는 접속이 안 되기 때문입니다.

spec:
  type: NodePort
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080   # 생략하면 자동 배정

# externalTrafficPolicy 가 중요한 설정입니다
  externalTrafficPolicy: Cluster  # 기본값
#   Cluster : 어느 노드로 와도 전체 파드로 분산. 대신 한 번 더 홉을 타고
#             SNAT 되어 클라이언트 IP가 사라집니다
#   Local   : 그 노드에 있는 파드로만 보냄. 클라이언트 IP가 보존되지만
#             파드가 없는 노드로 오면 연결이 끊깁니다

Ingress에서 Gateway API로

2026년 3월부로 ingress-nginx는 유지보수가 끝났습니다

쿠버네티스 SIG Network와 보안 대응 위원회는 ingress-nginx의 퇴역을 발표했고, 최선 노력 유지보수는 2026년 3월까지였습니다. 그 이후로는 새 릴리스도, 버그 수정도, 발견되는 보안 취약점에 대한 업데이트도 없습니다. 기존 배포본은 계속 동작하고 설치 아티팩트도 남아 있지만, 위원회는 Gateway API로 즉시 마이그레이션할 것을 권고했습니다.

국내 현장에도 ingress-nginx가 깔린 클러스터가 아주 많습니다. 지금 당장 안 터지지만, 보안 패치가 없는 진입점을 인터넷에 노출한 상태라는 점이 중요합니다. MSP 입장에서는 고객사 클러스터의 인그레스 컨트롤러 종류를 파악해 두는 것이 우선이고, 신규 구축이라면 처음부터 Gateway API 구현체(Envoy Gateway, Cilium, Istio, 클라우드 제공 컨트롤러 등)를 고르는 게 맞습니다.

Gateway API가 기존 Ingress보다 나은 점은 역할 분리입니다. Ingress는 TLS 설정, 로드밸런서 옵션, 라우팅 규칙이 어노테이션 속에 뒤섞여 있어 개발팀이 인프라 설정을 건드릴 수밖에 없었습니다. Gateway API는 이걸 세 개의 객체로 나눕니다.

Gateway API의 역할 분리

kind: GatewayClass
metadata: { name: envoy }
spec: { controllerName: gateway.envoyproxy.io/gatewayclass-controller }
---
# ② 클러스터 운영자가 관리 — 어떤 포트와 인증서를 열 것인가
kind: Gateway
metadata: { name: prod-gw, namespace: infra }
spec:
  gatewayClassName: envoy
  listeners:
    - name: https
      port: 443
      protocol: HTTPS
      tls:
        certificateRefs: [{ name: wildcard-cert }]
      allowedRoutes:
        namespaces: { from: Selector, selector: { matchLabels: { team: app } } }
---
# ③ 애플리케이션 팀이 관리 — 내 서비스로 오는 규칙만
kind: HTTPRoute
metadata: { name: shop, namespace: prod }
spec:
  parentRefs: [{ name: prod-gw, namespace: infra }]
  hostnames: ["shop.example.com"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs: [{ name: api, port: 80 }]
    - matches: [{ path: { type: PathPrefix, value: / } }]
      backendRefs: [{ name: web, port: 80 }]

현재 Gateway API는 GatewayClass, Gateway, ListenerSet, HTTPRoute, GRPCRoute, TLSRoute, TCPRoute, UDPRoute, BackendTLSPolicy, ReferenceGrant까지 정식(GA) 지원합니다. HTTP뿐 아니라 TCP·UDP·gRPC까지 같은 모델로 다룰 수 있다는 뜻이고, Ingress로는 어노테이션 없이는 불가능했던 것들입니다.

NetworkPolicy — 기본은 전면 허용입니다

쿠버네티스의 기본값은 “모든 파드가 모든 파드와 통신 가능”입니다. 네임스페이스를 나눠도 네트워크는 안 나뉩니다. 이걸 제한하려면 NetworkPolicy를 써야 하는데, CNI가 NetworkPolicy를 지원하지 않으면 객체를 만들어도 무시됩니다. Flannel 단독 구성이 대표적인 예이고, 정책이 적용된 줄 알고 있다가 감사에서 지적받는 일이 흔합니다.

기본 차단부터 깔고 필요한 것만 여는 순서
# ① 이 네임스페이스의 모든 인바운드를 차단 (기반 정책)
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: prod }
spec:
  podSelector: {}           # 빈 selector = 네임스페이스의 모든 파드
  policyTypes: [Ingress]
---
# ② 웹 파드에서 API 파드로 가는 8080만 허용
kind: NetworkPolicy
metadata: { name: allow-web-to-api, namespace: prod }
spec:
  podSelector:
    matchLabels: { app: api }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: web }   # IP가 아니라 라벨로 지정
      ports:
        - { protocol: TCP, port: 8080 }

# 잊기 쉬운 것: DNS도 막힙니다.
# default-deny-egress 를 걸었다면 kube-system 의 CoreDNS 로 가는
# UDP/TCP 53 을 반드시 열어 줘야 합니다. 안 그러면 모든 이름 조회가 실패합니다.
네 환경의 방화벽 철학이 여기서 만납니다 AWS는 보안 그룹 ID로, Azure는 ASG로, 쿠버네티스는 라벨로 정책을 씁니다. 셋 다 “IP를 적지 않는다”는 같은 결론에 도달한 겁니다. 반면 온프레미스 방화벽은 여전히 IP와 대역으로 씁니다. 그래서 서버가 늘어날 때마다 방화벽 담당자에게 요청을 넣어야 하고, 이게 온프레미스 운영이 느린 가장 큰 이유입니다.

디버깅 — 순서대로만 하면 됩니다

“파드가 서비스에 접속을 못 해요” 대응 순서
# 1. 이름이 풀리는가 (DNS 문제인지 먼저 가른다)
kubectl run tmp --rm -it --image=nicolaka/netshoot -- \
  nslookup api.prod.svc.cluster.local

# 2. 서비스 뒤에 파드가 실제로 붙어 있는가 — 가장 흔한 원인
kubectl get endpointslice -n prod -l kubernetes.io/service-name=api
#    비어 있다면 selector 라벨 오타이거나, 파드가 Ready가 아닙니다

# 3. 파드가 정말 Ready인가
kubectl get pod -n prod -l app=api -o wide

# 4. 포트가 맞는가 — targetPort와 컨테이너 포트 불일치도 흔합니다
kubectl get svc api -n prod -o yaml | grep -A3 ports

# 5. 파드 IP로 직접 때려 본다 (서비스 문제인지 앱 문제인지 가른다)
kubectl run tmp --rm -it --image=nicolaka/netshoot -- \
  curl -sv 10.244.2.7:8080/healthz

# 6. NetworkPolicy가 막고 있는가
kubectl get networkpolicy -n prod
#    Cilium이면 더 직접적인 확인이 가능합니다
#    cilium monitor --type drop
2번에서 대부분 끝납니다 실무에서 “서비스 접속 안 됨” 신고의 절반 이상이 EndpointSlice가 비어 있는 것입니다. 원인은 거의 항상 둘 중 하나입니다. 서비스의 selector와 파드의 라벨이 다르거나(오타, 대소문자), 파드가 readiness 프로브를 통과하지 못해 Ready가 아니거나. 이 명령어 하나를 먼저 치는 습관을 들이면 조사 시간이 크게 줄어듭니다.

09온프레미스 — VM 기반 데이터센터 네트워크

클라우드만 만져 본 사람이 온프레미스에 처음 들어가면 두 가지에 놀랍니다. 하나는 만질 수 있는 계층이 훨씬 많다는 것이고, 다른 하나는 바꾸는 데 사람과 시간이 든다는 것입니다. 클라우드에서 30초 걸리는 일이 여기서는 결재 → 작업 일정 → 야간 점검 순서를 거칩니다. 구조를 이해하면 그 이유도 납득이 됩니다.

VLAN · 트렁크 LACP 본딩 STP vSwitch · 포트그룹 VXLAN · NSX VRRP · HSRP F5 · L4 스위치 스파인-리프

인터넷에서 VM까지, 전체 경로

VLAN — 온프레미스의 서브넷

VLAN은 물리적으로 같은 스위치에 꽂혀 있어도 논리적으로 다른 네트워크로 나누는 기술입니다. 프레임에 12비트짜리 태그(1~4094)를 붙여서 구분합니다. 클라우드의 서브넷과 역할이 같지만, 결정적 차이가 있습니다.

액세스 포트

VLAN 하나에만 속합니다. 태그가 없는 프레임이 오가고, 스위치가 알아서 붙였다 뗍니다.

일반 PC, 프린터, 단일 용도 서버가 여기 꽂힙니다.

트렁크 포트

여러 VLAN을 한 케이블로 실어 나릅니다. 태그가 붙은 채로 전달됩니다.

하이퍼바이저 서버는 반드시 트렁크여야 합니다. 그래야 한 서버 위의 VM들이 서로 다른 VLAN에 속할 수 있습니다.

“VM을 만들었는데 통신이 안 돼요” 1순위 원인 새 VLAN을 만들어 포트그룹에 배정했는데, ToR 스위치의 트렁크 포트에 그 VLAN을 허용(allowed vlan)하지 않은 경우입니다. 가상 쪽 설정만 보고 있으면 절대 안 보입니다. 서버 담당과 네트워크 담당이 다른 조직이면 이 문제로 반나절이 날아갑니다. 새 VLAN 작업은 항상 “스위치 포트 → 하이퍼바이저 → VM” 세 곳을 함께 확인하세요.
스위치 쪽에서 확인해야 하는 것
# 트렁크 포트에 VLAN 40이 허용되어 있는가 (Cisco 계열 예시)
show interface GigabitEthernet1/0/10 switchport
#   Trunking VLANs Enabled: 10,20,30     ← 40이 없으면 이게 원인

# 허용 VLAN 추가 — 기존 목록을 덮어쓰지 않도록 add 를 꼭 붙입니다
interface GigabitEthernet1/0/10
  switchport trunk allowed vlan add 40

# 서버 쪽(리눅스)에서 본딩과 VLAN 상태 확인
cat /proc/net/bonding/bond0     # LACP 협상 상태, 슬레이브 링크 상태
ip -d link show bond0.40         # VLAN 인터페이스가 올라와 있는지
bridge vlan show                 # OVS·리눅스 브리지의 VLAN 매핑

LACP 본딩 — 케이블 두 가닥을 하나처럼

서버 NIC 두 개를 ToR 스위치 두 대에 각각 꽂고, 논리적으로 하나의 인터페이스(bond0)로 묶습니다. 한쪽 케이블이나 스위치가 죽어도 서비스가 유지되고, 대역폭도 합쳐집니다.

  • LACP (802.3ad) — 서버와 스위치가 협상해서 묶습니다. 가장 권장되는 방식입니다. 스위치 쪽에도 설정이 필요합니다.
  • Active-Backup — 한 가닥만 쓰고 나머지는 대기. 스위치 설정이 필요 없어서 간편하지만 대역폭은 늘지 않습니다.
  • 대역폭이 합쳐진다고 한 세션이 2배 빨라지는 건 아닙니다. 출발지·목적지 해시로 가닥을 고르므로, 한 TCP 세션은 한 가닥만 씁니다. “10G 두 개 묶었는데 왜 단일 전송이 10G밖에 안 나오죠”의 답입니다.

스파인-리프 — 요즘 데이터센터의 표준 모양

예전 3계층(액세스-분배-코어) 구조는 서버 간 통신(동서 트래픽)이 늘면서 한계에 부딪혔습니다. A랙 서버가 B랙 서버와 통신하려면 코어까지 올라갔다 내려와야 하고, 코어가 병목이 됩니다. 스파인-리프는 모든 리프를 모든 스파인에 연결해 어느 서버에서 어느 서버로 가든 홉 수를 똑같이 만듭니다.

3계층 (전통)

액세스 → 분배 → 코어. STP로 루프를 막느라 링크의 절반이 놀고 있습니다.

남북 트래픽(클라이언트↔서버) 중심 시대의 설계입니다.

스파인-리프 (현대)

리프(ToR) ↔ 스파인 전 연결. L3와 ECMP로 모든 링크를 동시에 씁니다.

VXLAN + EVPN을 얹어 L2 구간을 랙 너머로 확장합니다. 용량이 부족하면 스파인을 한 대 더 추가하면 됩니다.

VXLAN이 온프레미스에도 있습니다 쿠버네티스 CNI가 쓰는 그 VXLAN이 맞습니다. 온프레미스에서는 VLAN의 한계 (최대 4094개, 랙을 넘어 확장하기 어려움)를 넘기 위해 씁니다. VXLAN은 24비트 식별자를 써서 1,600만 개의 논리 네트워크를 만들 수 있고, L3 네트워크 위로 L2 구간을 늘릴 수 있습니다. VMware NSX, Cisco ACI 같은 제품이 이 위에 정책 관리를 얹은 것입니다. MTU를 꼭 확인하세요 — VXLAN 헤더 50바이트 때문에 밑단 물리망은 점보 프레임(9000)으로 설정해 두는 것이 정석입니다.

클라우드는 리소스마다 방화벽을 붙이지만, 온프레미스는 존(zone)이라는 큰 덩어리로 나누고 존 사이 통행만 심사합니다. 전형적인 구성은 이렇습니다.

IP 주소 관리 — 엑셀을 벗어나세요

클라우드는 IP를 자동으로 주고 회수하지만, 온프레미스는 사람이 기록합니다. 그래서 시간이 지나면 “이 IP 누가 쓰는지 아무도 모름” 상태가 반드시 옵니다. 퇴사자가 만든 VM이 IP를 붙잡고 있고, 엑셀에는 다른 서버 이름이 적혀 있는 식입니다.

  • 고정 IP 서버라도 DHCP 예약으로 관리하면 중앙에서 현황이 보입니다.
  • phpIPAM, NetBox 같은 IPAM 도구를 쓰면 대역·VLAN·서버를 연결해서 관리할 수 있습니다.
  • 정기적으로 nmap -sn 10.30.10.0/24 같은 스캔을 돌려 실제 사용 현황과 기록을 대조하세요.
  • 서버 폐기 절차에 “IP 반납”과 “DNS 레코드 삭제”를 반드시 넣으세요. 유령 레코드가 남으면 나중에 엉뚱한 서버로 트래픽이 갑니다.

# 1. 내 IP와 게이트웨이부터
ip -br addr ; ip route show default

# 2. 게이트웨이까지 L2가 닿는가 — ARP가 풀리면 VLAN은 정상
ping -c2 10.30.10.1
ip neigh show 10.30.10.1
#   FAILED 또는 incomplete → VLAN·트렁크·포트그룹 문제입니다
#   REACHABLE 인데 그다음이 안 되면 라우팅이나 방화벽 문제입니다

# 3. 어디까지 가는지 경로 추적 — 방화벽에서 끊기면 거기서 멈춥니다
traceroute -n 10.30.30.20
mtr -n -c 20 10.30.30.20      # 구간별 손실률까지 보여 줍니다

nc -zv 10.30.30.20 3306
#   Connection refused → 목적지까지는 갔는데 서비스가 안 떠 있음
#   timeout           → 중간 방화벽에서 버려짐. 정책 신청이 필요합니다

# 5. MTU 문제 의심될 때 — 조각화 금지 비트를 켜고 크기를 키워 본다

ping -M do -s 8972 -c2 10.30.30.20   # 점보 프레임 확인용
#   "message too long" 이 나오면 경로 어딘가의 MTU가 작습니다

# 6. 실제 패킷이 들어오긴 하는가
sudo tcpdump -i bond0.30 -nn host 10.30.30.20 and port 3306
2번에서 문제를 반으로 가릅니다 게이트웨이 ARP가 풀리는지만 보면 L2 문제인지 L3 이상 문제인지가 즉시 갈립니다. ARP가 안 풀리면 VLAN·트렁크·포트그룹·케이블 쪽이고, 풀리는데 안 되면 라우팅·방화벽·서비스 쪽입니다. 클라우드에도 그대로 적용되는 사고법이고, 실제로 이 한 단계 때문에 장애 조사 시간이 크게 줄어듭니다.

12같은 서비스를 네 곳에 올려보기

이론을 붙이는 가장 빠른 방법은 하나의 요구사항을 네 환경에 각각 그려 보는 것입니다. 요구사항은 이렇습니다. “HTTPS 웹 서비스. 앱 서버는 인터넷에서 직접 접근 불가. DB는 앱에서만 접근. 앱은 외부 결제 API를 호출해야 함. 장애 시 서비스 중단 없음.”

구성 요소

  1. VPC 10.10.0.0/16, 가용 영역 2곳에 퍼블릭·앱·DB 서브넷 각 2개씩 총 6개
  2. 퍼블릭 서브넷에 ALB(443 리스너, ACM 인증서)와 NAT 게이트웨이 2대(AZ당 1대)
  3. 앱 서브넷에 오토스케일링 그룹. 라우트 테이블은 0.0.0.0/0 → 같은 AZ의 NAT GW
  4. DB 서브넷에 RDS 다중 AZ. 라우트 테이블에 기본 경로 없음
  5. 보안 그룹 3개: sg-alb(인터넷 443), sg-app(sg-alb에서 8080), sg-db(sg-app에서 3306)

요구사항을 어떻게 만족시키나

  • 앱 직접 접근 차단 — 앱 서브넷에 IGW 경로가 없고, sg-app은 ALB의 보안 그룹만 허용
  • DB 접근 제한 — sg-db가 sg-app을 출발지로 참조. IP를 적지 않음
  • 외부 API 호출 — NAT 게이트웨이 경유. 결제사에 등록할 고정 IP는 NAT의 탄력적 IP
  • 무중단 — ALB가 AZ 2곳에 걸치고, ASG가 AZ에 분산, RDS는 다중 AZ 자동 전환
빠뜨리기 쉬운 것 NAT 게이트웨이를 비용 아끼려고 1대만 두면, 그 AZ가 장애 날 때 반대편 AZ의 앱도 외부 API를 못 부릅니다. 무중단 요구가 있으면 AZ마다 하나씩이 정답입니다. 그리고 S3를 쓴다면 게이트웨이 엔드포인트는 무료이니 반드시 추가하세요.

구성 요소

  1. VNet 10.20.0.0/16. 서브넷은 snet-agw(App Gateway 전용), snet-app, snet-db
  2. Application Gateway v2 + WAF, 영역 중복(zone-redundant) 설정, 정적 공용 IP
  3. snet-app에 VM 확장 집합. 서브넷에 NAT 게이트웨이 연결
  4. Azure SQL 또는 VM DB. PaaS라면 Private Endpoint + 사설 DNS 영역 + VNet 링크
  5. NSG 3개와 ASG 3개(asg-agw, asg-app, asg-db)

요구사항을 어떻게 만족시키나

  • 앱 직접 접근 차단 — 앱 VM에 공용 IP를 붙이지 않고, NSG에서 asg-agw만 허용. 기본 VNet 허용 규칙을 덮는 Deny 규칙을 낮은 번호로 추가
  • DB 접근 제한 — asg-app에서 오는 것만 허용. Private Endpoint면 공용 접근을 아예 비활성화
  • 외부 API 호출 — NAT 게이트웨이의 공용 IP가 고정 출발지가 됨
  • 무중단 — App Gateway를 영역 중복으로, VMSS를 여러 영역에 분산
빠뜨리기 쉬운 것 ① App Gateway 전용 서브넷을 미리 안 잡아 두면 나중에 넣을 자리가 없습니다. ② 기본 아웃바운드 폐지 때문에 NAT 게이트웨이 없이 만든 새 VM은 인터넷에 못 나갑니다. ③ Private Endpoint만 만들고 사설 DNS 영역 링크를 빠뜨리면 여전히 공인 IP로 나갑니다.

구성 요소

  1. 워커 노드 3대 이상, 서로 다른 장애 도메인에 분산
  2. Gateway 하나(443, TLS 인증서) + HTTPRoute로 경로 분기. LoadBalancer 서비스는 이 게이트웨이 하나만
  3. 앱은 Deployment + ClusterIP 서비스. topologySpreadConstraints로 노드 분산
  4. DB는 클러스터 밖의 관리형 DB를 권장. 클러스터 안이라면 StatefulSet + 헤드리스 서비스
  5. NetworkPolicy: 네임스페이스 기본 차단 + 게이트웨이→앱, 앱→DB, 전체→CoreDNS

요구사항을 어떻게 만족시키나

  • 앱 직접 접근 차단 — 앱 서비스는 ClusterIP만. NetworkPolicy로 게이트웨이 네임스페이스에서 오는 것만 허용
  • DB 접근 제한 — 파드 라벨 app: api에서 오는 5432만 허용
  • 외부 API 호출 — 노드 SNAT로 나감. 고정 IP가 필요하면 밑단 NAT 게이트웨이의 IP를 등록하거나 이그레스 게이트웨이를 둠
  • 무중단 — 레플리카를 노드에 분산하고 PodDisruptionBudget을 설정. readiness 프로브를 제대로 구현
빠뜨리기 쉬운 것 ① default-deny를 걸고 DNS를 안 열면 모든 것이 동시에 멈춥니다. CoreDNS로 가는 53 허용을 먼저 넣으세요. ② 서비스마다 type: LoadBalancer를 쓰면 클라우드 LB가 서비스 수만큼 생겨 요금이 폭증합니다. ③ ingress-nginx를 쓰고 있다면 유지보수 종료 대상이니 이전 계획을 세워야 합니다.

구성 요소

  1. VLAN 3개: VLAN 10 DMZ(웹), VLAN 20 앱, VLAN 30 DB. 각 VLAN의 게이트웨이는 코어 스위치의 VRRP 가상 IP
  2. 방화벽 HA 쌍. 존 정의: Untrust · DMZ · Internal · DB · Management
  3. F5 BIG-IP HA 쌍에 VIP 203.0.113.10:443. SSL 오프로드 후 웹 풀로 분배
  4. 하이퍼바이저 호스트는 ToR 스위치 두 대에 LACP 본딩. 트렁크로 VLAN 10·20·30 전달
  5. 포트그룹 3개를 만들고 VM을 역할에 맞는 포트그룹에 연결

요구사항을 어떻게 만족시키나

  • 앱 직접 접근 차단 — 앱 VM은 VLAN 20에만 있고 공인 IP가 없음. 방화벽이 Untrust→Internal 직접 통행을 거부
  • DB 접근 제한 — Internal→DB 존 정책에 3306만 등록. 나머지는 기본 거부
  • 외부 API 호출 — 방화벽 PAT로 나감. 결제사에 방화벽 공인 IP를 등록
  • 무중단 — 모든 계층이 쌍으로. 회선 2개, 방화벽 HA, F5 HA, 코어 VRRP, ToR MLAG, 서버 본딩. VM은 서로 다른 물리 호스트에 배치
빠뜨리기 쉬운 것 ① 이중화 VM 두 대가 같은 물리 호스트에 올라가 있으면 이중화가 아닙니다. 안티어피니티 규칙을 거세요. ② 새 VLAN을 ToR 트렁크에 허용하지 않아 통신이 안 되는 사고가 1순위입니다. ③ 방화벽 정책 신청에 리드타임이 있으니 구축 일정에 미리 반영하세요.

증상 1 — 접속이 “거부됨(refused)”으로 즉시 실패한다

해석: 패킷은 목적지까지 도달했습니다. 방화벽 문제가 아닙니다. 목적지에서 그 포트를 듣고 있는 프로세스가 없다는 뜻입니다.

  1. 서버에 들어가 ss -tlnp로 실제 리스닝 포트 확인
  2. 127.0.0.1에만 바인딩되어 있지 않은지 확인 — 0.0.0.0이어야 외부에서 접속됩니다
  3. 쿠버네티스라면 targetPort와 컨테이너의 실제 포트가 같은지 확인
  4. 애플리케이션 로그에서 기동 실패가 없는지 확인

네트워크 담당을 부를 필요가 없는 증상입니다. 앱이나 서버 쪽 문제입니다.

증상 2 — 접속이 한참 기다리다 타임아웃된다

해석: 패킷이 중간 어딘가에서 조용히 버려지고 있습니다. 방화벽이나 라우팅 문제입니다.

  1. 경로부터 — 출발지 서브넷·VLAN에 목적지로 가는 경로가 있는가
  2. 방화벽 — 양방향 모두 확인. AWS는 SG와 NACL 둘 다, Azure는 list-effective-nsg, K8s는 NetworkPolicy, 온프레미스는 존 정책
  3. 로그 확인 — 플로우 로그에 REJECT가 찍히면 방화벽, 아무것도 없으면 라우팅
  4. 중간 지점에서 확인 — 같은 서브넷의 다른 서버에서 시도해 범위를 좁힙니다

요령: “되는 곳”과 “안 되는 곳”의 차이점을 찾는 게 가장 빠릅니다. 같은 서브넷의 다른 서버는 되는가? 다른 포트는 되는가? 어제는 됐는가?

증상 3 — 이름으로는 안 되는데 IP로는 된다

해석: 순수 DNS 문제입니다. 네트워크 경로는 정상입니다.

  1. nslookup 또는 dig로 실제 응답 확인. 응답 자체가 없는지, 틀린 IP가 오는지 구분
  2. AWS — 프라이빗 호스팅 영역이 해당 VPC에 연결되어 있는가. VPC의 enableDnsSupport가 켜져 있는가
  3. Azure — Private Endpoint용 사설 DNS 영역에 VNet 링크가 걸려 있는가
  4. K8s — CoreDNS 파드가 살아 있는가(kubectl -n kube-system get pod -l k8s-app=kube-dns). NetworkPolicy가 53을 막고 있지 않은가
  5. 온프레미스 — /etc/resolv.conf의 DNS 서버가 맞는가. 레코드가 남아 있는 유령 서버는 아닌가

캐시에 주의하세요. TTL 때문에 고친 뒤에도 한동안 옛날 답이 옵니다. 테스트할 때는 dig +trace나 권한 서버 직접 조회로 확인하세요.

증상 4 — 가끔씩만 실패한다 (간헐적 장애)

해석: 가장 골치 아픈 유형입니다. 원인은 대개 “여러 개 중 하나가 고장” 또는 “한계에 도달”입니다.

  • 백엔드 중 하나만 고장 — 로드밸런서 뒤 서버 4대 중 1대만 이상하면 25% 확률로 실패합니다. 각 백엔드에 직접 요청해 보세요
  • SNAT 포트 고갈 — 트래픽이 몰릴 때만 실패합니다. AWS의 ErrorPortAllocation, Azure의 SNAT 고갈 지표를 확인하세요
  • 커넥션 수 한계 — 방화벽·LB의 동시 세션 한계에 걸렸을 수 있습니다
  • DNS 라운드로빈에 죽은 IP 포함 — 여러 A 레코드 중 하나가 유령이면 간헐적으로 실패합니다
  • MTU 불일치 — 작은 요청은 되고 큰 응답만 멈춥니다. 매우 특징적인 증상입니다
  • 이중화 장비 중 한 쪽만 설정 누락 — 온프레미스에서 흔합니다. Active/Standby 전환 시에만 실패합니다

실패 패턴을 기록하세요. 몇 %가 실패하는지, 특정 시간대인지, 특정 크기 이상에서만인지를 알면 원인이 좁혀집니다.

증상 5 — 작은 요청은 되는데 큰 파일 전송이 멈춘다

해석: 거의 확실히 MTU 문제입니다. TCP 연결은 맺어지는데 큰 패킷만 사라집니다.

  1. ping -M do -s 1472 대상으로 조각화 없이 1500바이트가 가는지 확인
  2. 실패하면 크기를 줄여 가며 경로의 실제 MTU를 찾습니다(1400, 1350, 1300…)
  3. 원인 후보: VPN·VXLAN 터널의 캡슐화 오버헤드, 오버레이 CNI, 경로상 ICMP 차단
  4. 근본 원인은 대개 ICMP 차단입니다. 경로 MTU 탐색은 ICMP “Fragmentation Needed” 메시지에 의존하는데, 이걸 막아 두면 송신 측이 크기를 줄일 줄 모릅니다
  5. 임시 해결: 인터페이스 MTU를 낮추거나 TCP MSS 클램핑 적용. 근본 해결: 해당 ICMP 타입을 허용

ICMP를 전부 막는 건 보안이 아니라 장애 원인입니다. Type 3 Code 4는 반드시 허용하세요.

증상 6 — 어제까지 되던 게 오늘 안 된다

해석: 무언가 바뀌었습니다. 원인 추적보다 변경 찾기가 빠릅니다.

  1. AWS CloudTrail, Azure Activity Log에서 최근 24시간 네트워크 관련 변경 조회
  2. K8s는 kubectl get events -A --sort-by=.lastTimestamp와 Git 커밋 이력
  3. 온프레미스는 변경 관리 대장과 장비 설정 백업 비교(diff)
  4. 인증서 만료도 의심하세요. “갑자기 안 됨”의 흔한 원인이고 날짜가 딱 떨어집니다
  5. 클라우드 제공자의 상태 페이지와 공지도 확인하세요. 오늘 본 기본 아웃바운드 폐지 같은 정책 변경이 실제로 있습니다

“아무것도 안 바꿨는데요”는 대부분 사실이 아닙니다. 다른 팀의 변경, 자동 배포, 만료된 무언가를 찾으세요.

14신입이 자주 밟는 지뢰

실제 현장에서 반복적으로 나오는 실수들입니다. 미리 읽어 두면 한 번은 피할 수 있습니다.

AWS
  • 라우트 테이블을 만들고 서브넷에 연결하지 않음
  • NAT 게이트웨이를 1대만 두고 무중단이라고 생각함
  • 보안 그룹에 IP를 하드코딩해 서버가 늘 때마다 수정
  • NACL을 건드려 놓고 SG만 보며 디버깅
  • S3 게이트웨이 엔드포인트를 안 만들어 NAT 요금 폭탄
  • ALB에 고정 IP가 없다는 걸 모르고 고객사에 IP를 알려 줌
Azure
  • VNet 안에서는 기본 통신이 된다는 걸 몰라 분리했다고 착각
  • NAT 게이트웨이 없이 새 VM을 만들고 인터넷이 안 된다고 함
  • Private Endpoint만 만들고 사설 DNS 영역 링크를 빠뜨림
  • App Gateway·Bastion 전용 서브넷 자리를 안 남겨 둠
  • VM을 지웠는데 NIC과 공용 IP가 남아 계속 과금
  • NSG 우선순위를 65000보다 크게 줘서 기본 규칙에 먼저 걸림
Kubernetes
  • 파드·서비스 CIDR이 사내망과 겹침 (재구축 외 방법 없음)
  • 서비스 selector 오타로 EndpointSlice가 비어 있음
  • default-deny를 걸고 DNS를 안 열어 전면 장애
  • Flannel을 쓰면서 NetworkPolicy가 적용될 거라고 믿음
  • 서비스마다 type: LoadBalancer를 써서 LB 요금 폭증
  • readiness 프로브를 구현 안 해 배포 때마다 순단
온프레미스
  • 새 VLAN을 ToR 트렁크에 허용하지 않음 (1순위 원인)
  • 이중화 VM 두 대가 같은 물리 호스트에 있음
  • 관리 네트워크를 서비스망과 섞어 씀
  • MTU를 한쪽만 9000으로 바꿔 큰 전송이 멈춤
  • 서버를 없앴는데 DNS 레코드와 F5 풀 멤버가 남음
  • 방화벽 정책 리드타임을 일정에 반영하지 않음

구축 전 체크리스트

새 환경을 설계할 때 이 항목들을 훑어보세요. 진행 상황은 브라우저에 저장됩니다.

15용어 사전

회의에서 나왔을 때 “그게 뭐죠?”라고 묻기 애매한 단어들을 모았습니다. 검색으로 바로 찾으세요.

ARPAddress Resolution Protocol
같은 L2 구간에서 IP 주소로 MAC 주소를 알아내는 절차입니다. 게이트웨이 ARP가 안 풀리면 VLAN·포트그룹·케이블 문제이고, 풀리는데 통신이 안 되면 그 위 계층 문제입니다. 장애 조사에서 범위를 반으로 가르는 첫 단계입니다.
ASGApplication Security Group
Azure에서 VM의 NIC에 붙이는 논리적 그룹 태그입니다. NSG 규칙에서 IP 대신 이 이름을 쓰면 서버가 늘어나도 규칙을 고칠 필요가 없습니다. AWS의 보안 그룹 참조에 해당합니다.
BGPBorder Gateway Protocol
서로 다른 조직의 네트워크가 경로 정보를 주고받는 프로토콜입니다. 인터넷 전체가 이걸로 돌아갑니다. 온프레미스 경계 라우터, Direct Connect·ExpressRoute, Calico의 라우팅 모드, MetalLB의 BGP 모드가 모두 BGP를 씁니다.
CIDRClassless Inter-Domain Routing
10.0.0.0/16 같은 표기법입니다. 슬래시 뒤 숫자는 앞에서부터 몇 비트가 네트워크인지를 뜻합니다. 숫자가 작을수록 큰 대역입니다.
CNIContainer Network Interface
쿠버네티스가 정한 네트워크 플러그인 규격입니다. 쿠버네티스 자신은 네트워크를 구현하지 않고, Calico·Cilium·Flannel 같은 CNI가 실제 동작을 담당합니다. 클러스터의 성격을 결정하는 가장 중요한 선택입니다.
CoreDNS
쿠버네티스 클러스터 안의 DNS 서버입니다. 서비스명.네임스페이스.svc.cluster.local 형식의 이름을 ClusterIP로 바꿔 줍니다. 여기가 멈추면 클러스터 전체가 동시에 고장 난 것처럼 보입니다.
DMZDemilitarized Zone
인터넷과 내부망 사이에 둔 완충 구역입니다. 웹 서버나 리버스 프록시처럼 외부에 노출해야 하는 것만 여기 두고, DMZ에서 내부망으로 가는 통신은 엄격히 제한합니다.
ECMPEqual-Cost Multi-Path
비용이 같은 경로가 여러 개일 때 트래픽을 나눠 보내는 기법입니다. 스파인-리프 구조에서 모든 링크를 동시에 쓸 수 있게 해 주는 핵심 기술입니다.
ENIElastic Network Interface
AWS의 가상 랜카드입니다. 사설 IP, 보안 그룹, MAC 주소를 갖고 있고 인스턴스와 별개로 존재합니다. 인스턴스를 바꿔도 ENI를 옮겨 붙이면 IP와 정책이 그대로 따라갑니다.
EndpointSlice
쿠버네티스 Service 뒤에 실제로 붙어 있는 파드 IP 목록입니다. 예전의 Endpoints를 대체했습니다. “서비스 접속 안 됨” 장애에서 가장 먼저 확인할 대상이고, 비어 있다면 라벨 오타이거나 파드가 Ready가 아닌 것입니다.
Gateway API
쿠버네티스의 차세대 트래픽 진입 규격입니다. GatewayClass(인프라), Gateway(운영자), HTTPRoute(앱팀)로 역할을 나눠 어노테이션 범벅이던 Ingress의 문제를 해결했습니다. ingress-nginx 유지보수 종료 이후의 표준 경로입니다.
ICMP
ping과 traceroute가 쓰는 프로토콜이자, 네트워크가 문제를 알려 주는 통로입니다. 보안을 이유로 전부 막으면 경로 MTU 탐색이 깨져 큰 전송이 멈춥니다. 최소한 Type 3 Code 4는 허용해야 합니다.
IGWInternet Gateway
AWS VPC를 인터넷에 잇는 관문입니다. 만들기만 해서는 안 되고 VPC에 붙이고 라우트 테이블에 경로를 추가해야 동작합니다. 대역폭 제한이 없고 요금도 없습니다.
LACPLink Aggregation Control Protocol
여러 물리 링크를 하나의 논리 링크로 묶는 표준입니다. 서버와 스위치 양쪽에 설정이 필요합니다. 대역폭이 합쳐지지만 한 TCP 세션은 한 가닥만 쓴다는 점을 기억하세요.
MetalLB
클라우드가 아닌 환경에서 type: LoadBalancer 서비스를 동작하게 해 주는 도구입니다. L2 모드는 한 노드가 ARP로 VIP를 대표하고, BGP 모드는 여러 노드가 라우터에 광고해 실제로 분산됩니다.
MLAG
스위치 두 대가 한 대인 척 동작해 서버가 양쪽에 동시에 LACP로 묶일 수 있게 하는 기술입니다. 벤더마다 이름이 다릅니다(vPC, MC-LAG, Stacking).
MTUMaximum Transmission Unit
한 번에 보낼 수 있는 최대 패킷 크기입니다. 이더넷 기본값은 1500바이트입니다. VPN이나 VXLAN이 헤더를 덧붙이면 실제 쓸 수 있는 크기가 줄어들고, 이게 맞지 않으면 “작은 건 되는데 큰 건 멈추는” 특유의 증상이 납니다.
NACLNetwork ACL
AWS의 서브넷 단위 방화벽입니다. 무상태라서 응답 트래픽도 별도로 허용해야 하고, 번호 순으로 평가해 첫 매치에서 멈춥니다. 실무에서는 대개 기본값 그대로 둡니다.
NAT 게이트웨이
사설 IP만 가진 서버가 인터넷에 나갈 수 있게 출발지 주소를 공인 IP로 바꿔 주는 관리형 장비입니다. 안에서 밖으로만 가능하고 밖에서 안으로는 못 들어옵니다. 시간당 요금과 처리량 요금이 모두 붙습니다.
ndots
파드의 resolv.conf에 있는 옵션으로, 점이 몇 개 미만이면 검색 도메인을 붙여 볼지를 정합니다. 기본값 5 때문에 외부 도메인 조회가 여러 번 실패한 뒤에야 성공해 느려집니다.
NetworkPolicy
쿠버네티스에서 파드 간 통신을 제한하는 객체입니다. IP가 아니라 라벨로 대상을 지정합니다. CNI가 지원하지 않으면 객체를 만들어도 조용히 무시된다는 점이 가장 중요합니다.
NSGNetwork Security Group
Azure의 방화벽입니다. 서브넷과 NIC 양쪽에 붙일 수 있고 둘 다 통과해야 합니다. 우선순위 번호가 낮은 규칙부터 평가하며 첫 매치에서 멈춥니다. 허용과 거부를 모두 쓸 수 있습니다.
PATPort Address Translation
여러 사설 IP가 공인 IP 하나를 포트로 나눠 쓰는 방식입니다. 가정용 공유기가 하는 일이 이것이고, 온프레미스 방화벽의 아웃바운드도 같습니다. NAT 과부하라고도 부릅니다.
PrivateLink · Private Endpoint
외부 서비스를 내 네트워크 안의 사설 IP로 끌어오는 기능입니다. 인터넷을 거치지 않고, 대역이 겹쳐도 문제가 없습니다. Azure에서는 반드시 사설 DNS 영역까지 연결해야 효과가 납니다.
SNAT · DNAT
SNAT는 출발지 주소를 바꾸는 것(안→밖), DNAT는 목적지 주소를 바꾸는 것(밖→안)입니다. 로드밸런서와 쿠버네티스 Service의 본질이 DNAT입니다.
STPSpanning Tree Protocol
L2 네트워크에서 루프를 막기 위해 일부 링크를 차단하는 프로토콜입니다. 안전하지만 링크의 절반이 놀게 되어, 요즘 데이터센터는 스파인-리프와 L3 라우팅으로 대체하는 추세입니다.
Transit Gateway · Virtual WAN
여러 네트워크를 허브 하나에 모아 연결하는 관리형 서비스입니다. 피어링이 전이되지 않는 한계를 해결합니다. 연결 수와 처리량에 따라 요금이 붙으므로 규모를 먼저 계산하세요.
UDRUser Defined Route
Azure에서 기본 시스템 라우트를 덮어쓰기 위해 만드는 사용자 정의 경로입니다. “모든 트래픽을 방화벽으로 보내라” 같은 요구를 구현할 때 씁니다.
veth 페어virtual ethernet pair
리눅스의 가상 랜 케이블 한 쌍입니다. 한쪽은 파드 안의 eth0, 다른 쪽은 노드의 네트워크 공간에 놓여 파드와 노드를 잇습니다. 컨테이너 네트워킹의 기본 부품입니다.
VIPVirtual IP
특정 장비 하나가 아니라 서비스를 대표하는 주소입니다. 로드밸런서의 서비스 주소, VRRP의 게이트웨이 주소, 쿠버네티스의 ClusterIP가 모두 VIP입니다.
VLAN
물리적으로 같은 스위치에 있어도 논리적으로 네트워크를 나누는 기술입니다. 프레임에 12비트 태그를 붙여 구분하며 최대 4094개까지 만들 수 있습니다. 클라우드의 서브넷에 해당합니다.
VRRP · HSRP
라우터나 스위치 두 대가 게이트웨이 IP 하나를 함께 맡는 프로토콜입니다. 한 대가 죽으면 나머지가 즉시 그 IP를 이어받아 서버들은 아무것도 몰라도 됩니다.
VXLAN
L3 네트워크 위로 L2 구간을 확장하는 오버레이 기술입니다. 24비트 식별자로 1,600만 개의 논리 네트워크를 만들 수 있습니다. 헤더 50바이트가 붙으므로 MTU 설계가 필수입니다.
X-Forwarded-For
L7 프록시가 원래 클라이언트 IP를 담아 전달하는 HTTP 헤더입니다. 앱이 이 헤더를 읽도록 설정해야 실제 사용자 IP가 로그에 남습니다. 위조가 가능하므로 신뢰하는 프록시에서 온 값만 받아야 합니다.
가용 영역Availability Zone
같은 리전 안에서 전원·냉각·네트워크가 독립된 데이터센터 묶음입니다. 하나가 통째로 죽어도 나머지가 살아남도록 설계된 단위이고, 온프레미스의 랙·전원 계통에 해당합니다.
상태 저장 방화벽stateful firewall
나간 연결을 기억해 두었다가 돌아오는 응답을 자동으로 허용하는 방화벽입니다. AWS 보안 그룹, Azure NSG, 대부분의 물리 방화벽이 여기 속합니다. 반대로 AWS NACL은 무상태입니다.
점보 프레임jumbo frame
MTU를 9000바이트로 키운 프레임입니다. 대용량 전송과 스토리지 네트워크에서 효율이 좋아집니다. 경로상의 모든 장비가 같이 설정되어야 하고, 한 곳이라도 빠지면 장애가 납니다.
최장 일치longest prefix match
라우팅 규칙이 여러 개 걸릴 때 프리픽스가 더 긴 쪽이 이기는 규칙입니다. 0.0.0.0/0이 항상 마지막에 적용되는 이유입니다.
