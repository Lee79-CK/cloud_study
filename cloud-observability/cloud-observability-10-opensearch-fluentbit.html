Cloud 모니터링·로깅 실전 강의 10편 (Level 3. 통합 로깅, 마지막 편)

OpenSearch·Fluent Bit 트랙

"누가, 언제, 어디서 접속해 무엇을 바꿨는가"를 1년 넘게 보관하고, 보안관제팀이 아무 필드나 조합해 즉석에서 찾을 수 있어야 하는 로그가 있습니다. Loki가 잘하지 못하는 일입니다. 1편 7장의 "로그는 두 곳에 나눠 담는다"를 실제로 만들어 봅니다.

대상: 1~2년차 클라우드 엔지니어 형식: 개념 + 실습 6개 예상 소요: 4시간 기준: OpenSearch 3.9, Fluent Bit 5.x
이 로그는 어디로 가나cust-a-db VM의 Fluent Bit 설정(Lab 4)과 같은 규칙으로 로그 한 건이 어떤 태그를 받고, 어떤 필터를 거쳐, 어느 저장소의 어느 인덱스로 가는지 보여 줍니다.

0시작하기 전에

Level 3의 마지막 편입니다. 7~9편에서 운영 로그를 Loki로 모았다면, 이번에는 감사·보안 로그를 위한 두 번째 저장소를 세웁니다.

학습 목표

  1. 감사·보안 로그의 요건(장기 보존, 위변조 방지, 자유로운 필드 검색, 접근 통제)을 설명하고 Loki와 OpenSearch 중 어디에 둘지 판단할 수 있다.
  2. OpenSearch의 인덱스, 샤드, 매핑을 이해하고 고객사별, 날짜별 인덱스와 인덱스 템플릿을 설계할 수 있다.
  3. ISM 정책으로 쓰기 → 읽기 전용 → 삭제의 수명주기를 자동화할 수 있다.
  4. Fluent Bit의 YAML 파이프라인(입력, 파서, 필터, 태그 라우팅, 출력, 파일 버퍼)을 작성할 수 있다.
  5. 한 수집기에서 같은 로그를 감사용(OpenSearch)과 운영용(Loki)으로 나눠 보내는 분기 라우팅을 만들 수 있다.
  6. ELK를 유지하는 고객사의 라이선스와 호환성 점검 포인트를 안다.

이 편의 검증 범위 (꼭 읽어 주세요)

작성 환경에서는 OpenSearch와 Fluent Bit 실행 파일을 받을 수 없어 두 프로그램을 직접 실행하지 못했습니다. 대신 Fluent Bit 공식 문서(5.0)의 매개변수 표와 YAML 예시에 맞춰 설정을 작성했고, OpenSearch 차트 values는 저장소의 values.yaml(차트 3.9.0)과 대조했으며, YAML과 JSON 파일은 문법 검사를, 비밀번호를 가리는 Lua 스크립트는 Lua 5.4로 실행해 결과를 확인했습니다. 그래서 이 편에는 다른 편처럼 "작성자 실측" 결과가 없고, 예상 결과는 문서에 근거한 형태로 적었습니다. 실습 중 예상과 다른 동작을 만나면 트러블슈팅 장과 공식 문서를 먼저 확인해 주세요.

메모리 예산

OpenSearch는 JVM 힙 768MB에 운영 오버헤드를 더해 1.5~2GB, Dashboards는 0.5~1GB를 씁니다. 16GB 경량 구성이라면 실습하는 동안 edge의 OTel Demo를 잠시 내려 두세요(kubectl --context kind-edge -n otel-demo scale deploy --all --replicas=0).

1감사·보안 로그는 무엇이 다른가

운영 로그는 "지금 왜 고장 났나"를 위해, 감사 로그는 "나중에 무슨 일이 있었는지 증명"하기 위해 남깁니다. 목적이 다르면 요건도 다릅니다.

요건운영 로그 (Loki)감사·보안 로그 (OpenSearch)
보존수일~수주1년 이상인 경우가 많음 (규정, 계약)
검색 방식서비스, 시간으로 좁힌 뒤 본문 훑기IP, 계정, 결과, DB 이름 등 아무 필드 조합을 즉석에서, 기간 전체로
집계줄 수, 비율"이 IP가 실패한 계정 수", "이 사용자가 접속한 서버 목록" 같은 다차원 집계
보는 사람운영 엔지니어보안관제팀, 감사인, 고객사 보안 담당
무결성상대적으로 덜 중요지난 기록을 고칠 수 없게 (읽기 전용, 스냅샷 보관)
접근 통제테넌트 단위인덱스, 문서, 필드 단위까지

1편 7장에서 본 대로 OpenSearch는 모든 필드를 색인하는 역색인 구조라, 저장 비용은 크지만 이런 질의에 강합니다. 그렇다고 모든 로그를 OpenSearch에 넣으면 비용이 감당이 안 되므로, 감사·보안에 해당하는 로그만 골라서 보내는 것이 이 편의 핵심입니다.

무엇이 감사 로그인가 (이 랩의 기준)

DB 접속, 접속 종료, 인증 실패, 구조 변경(DDL), 권한 변경. 서버의 SSH 접속과 sudo 사용. 국내에서는 개인정보처리시스템의 접속기록을 일정 기간(일반적으로 1년 이상, 처리 규모나 정보 종류에 따라 더 길게) 보관하고 정기적으로 점검하도록 하는 고시가 있고, 금융권에는 별도 기준이 더해집니다. 기준은 개정되므로 고객사의 컴플라이언스 담당과 최신 고시를 확인해 보존 기간과 대상 로그를 정하세요. 이 강의는 법률 자문이 아닙니다.

2OpenSearch 구조

OpenSearch는 2021년 Elasticsearch 7.10.2에서 갈라져 나온 검색 엔진으로, 현재 리눅스 재단 산하 OpenSearch Software Foundation이 관리하며 Apache 2.0 라이선스입니다(1편 9장). 3.x에서 Lucene 10으로 올라갔습니다.

개념뜻Loki에 비유하면
문서 (document)JSON 한 건. 감사 로그 한 줄엔트리
인덱스 (index)문서의 묶음. 같은 매핑을 공유테넌트 + 기간
매핑 (mapping)필드별 타입(keyword, text, date, ip, long...) 정의없음 (Loki는 본문을 해석하지 않음)
샤드 (shard)인덱스를 나눈 조각. 각 샤드가 Lucene 인덱스 하나청크와 인덱스 파일
레플리카 (replica)샤드의 복제본. 노드가 하나면 둘 곳이 없어 0으로 둠Ingester 복제 계수
노드, 클러스터OpenSearch 프로세스 하나, 그 묶음Loki 인스턴스, 링

keyword와 text

같은 문자열도 어떻게 매핑하느냐에 따라 검색 방식이 다릅니다. keyword는 값 전체를 하나의 덩어리로 저장해 정확히 일치, 집계(terms), 정렬에 씁니다(사용자 이름, IP, 결과 코드). text는 단어로 쪼개 저장해 "password authentication" 같은 전문 검색에 씁니다(메시지 본문). 메시지처럼 둘 다 필요하면 text에 keyword 하위 필드(message.raw)를 함께 둡니다.

3인덱스 설계

인덱스를 어떻게 나눌 것인가

방식예장점단점
날짜별 인덱스 (이 랩)audit-cust-a-postgres-2026.10.08단순. 보존 기간이 지난 날짜 인덱스를 통째로 삭제. Fluent Bit의 logstash_format이 그대로 지원로그가 적은 고객사는 작은 인덱스와 샤드가 많아짐

공통 원칙은 세 가지입니다. 고객사를 인덱스 이름에 넣습니다(audit-cust-a-*). 그래야 보안 플러그인의 역할로 "고객사 A의 담당자는 audit-cust-a-* 만 읽기"를 정할 수 있습니다. 샤드 하나는 대략 10~50GB를 목표로 합니다. 너무 작은 샤드가 많으면 클러스터가 관리 부담으로 느려지는 것이 Loki의 작은 청크 문제(7편)와 같은 구조입니다. 그래서 로그가 적은 고객사는 날짜별 대신 월별이나 크기 기반 롤오버를 검토합니다. 마지막으로 매핑을 미리 고정합니다.

인덱스 템플릿과 매핑 함정

새 인덱스가 만들어질 때 이름 패턴에 맞는 템플릿이 설정과 매핑을 입혀 줍니다. 템플릿이 없으면 OpenSearch가 첫 문서를 보고 타입을 추측(동적 매핑)하는데, 여기서 감사 로그에서 흔한 사고가 납니다.

  • 타입 충돌: PostgreSQL의 remote_host는 원격 접속이면 IP지만 로컬 소켓 접속이면 [local]이라는 글자입니다. 이 필드를 ip 타입으로 매핑하면 로컬 접속 문서가 통째로 거부됩니다. 이 랩의 템플릿은 keyword로 둡니다.
  • 매핑 폭발: 동적 매핑을 그대로 두면 로그의 새 키마다 필드가 늘어 클러스터 상태가 커집니다(기본 한도 1,000개). 감사 로그처럼 구조가 정해진 로그는 필요한 필드를 명시합니다.
  • 날짜를 문자열로: 시각 필드가 문자열로 매핑되면 기간 검색이 안 됩니다. Fluent Bit이 넣는 @timestamp를 date로 고정합니다.

4ISM: 인덱스 수명주기

ISM(Index State Management)은 인덱스를 상태 기계로 다룹니다. 조건이 되면 다음 상태로 넘어가며 그 상태의 동작을 실행합니다. Elasticsearch의 ILM에 해당합니다.

현재 상태
이 상태에서 한 일
다음 전환
상태동작 (actions)전환 조건 (transitions)이유
hot없음 (쓰기 중)인덱스 나이 7일 → warm날짜별 인덱스는 그날이 지나면 더 쓰이지 않음

deletedelete없음보존 기간 종료

정책의 ism_template에 audit-*를 적어 두면, 이후에 새로 만들어지는 인덱스에 정책이 자동으로 붙습니다. 이미 있는 인덱스에는 붙지 않으므로 따로 적용 API를 호출해야 합니다. ISM은 기본적으로 약 5분 간격으로 인덱스를 점검하므로 전환은 조건이 된 직후가 아니라 다음 점검 때 일어납니다. 운영에서는 delete 전에 스냅샷을 오브젝트 스토리지(2편에서 만든 opensearch-snapshots 버킷)에 남기는 snapshot 동작을 넣어, OpenSearch에서는 지워도 보관 의무 기간 동안 복원할 수 있게 합니다(14장).

5Fluent Bit 파이프라인

Fluent Bit은 C로 작성된 가벼운 로그 수집기로, CNCF 졸업 프로젝트인 Fluentd 생태계의 일부입니다. 메모리 사용이 적고 출력 플러그인이 많아, OpenSearch, Elasticsearch, Loki, Kafka, 클라우드 서비스로 동시에 보내기 좋습니다.

입력

inputs

tail(파일), systemd(journal), forward, opentelemetry 등. 입력마다 태그를 붙입니다(audit.postgres).

파싱

parsers

문자열을 구조화된 레코드(키-값)로. json, regex, logfmt, 다중 줄.

필터

filters (match로 태그 선택)

modify(필드 추가, 삭제), grep(거르기), lua(스크립트), rewrite_tag(태그 바꿔 다시 넣기), kubernetes(파드 메타데이터) 등.

버퍼

storage

보낼 데이터를 메모리 또는 파일시스템에 쌓습니다. 목적지가 잠시 죽어도 디스크에 남아 있다가 다시 보냅니다. 감사 로그는 유실되면 안 되므로 파일시스템 버퍼를 씁니다.

출력

outputs (match로 태그 선택)

태그 패턴에 맞는 레코드만 그 출력으로 갑니다. 이 태그 기반 라우팅이 분기의 핵심입니다.

설정 형식: YAML을 쓰세요

Fluent Bit 5.0 문서는 기존 클래식 형식([INPUT] 같은 대괄호 섹션)이 2026년 말에 폐기 예정이라고 안내합니다. 클래식 형식은 목록이나 중첩 구조를 표현하지 못해 새 기능 지원이 제한됩니다. 인터넷의 설정 예시는 대부분 클래식 형식이지만, 이 강의는 YAML(fluent-bit.yaml)로 작성합니다. 파일 확장자로 형식이 정해집니다.

Alloy와 Fluent Bit, 언제 무엇을

상황권장이유
Grafana 스택(Loki, Prometheus, Tempo)으로 보냄Alloy (8편)라벨, Structured Metadata, 메트릭, 트레이스까지 한 수집기

6분기 라우팅 설계

PostgreSQL 로그 하나에 감사 정보(접속, DDL)와 운영 정보(쿼리 오류)가 섞여 있습니다. 감사용은 전부 OpenSearch에, 운영용은 오류 수준만 Loki에 보내려면 어떻게 할까요?

단계설정결과
1. 입력에 태그tail → audit.postgres모든 PostgreSQL 로그가 감사 경로에 들어옴
2. 공통 필드modify (match audit.*)customer, host 필드 추가 (OpenSearch 역할, 검색 기준)
3. 마스킹lua (match audit.postgres)SQL 문 안의 PASSWORD '...'를 '[REDACTED]'로
4. 복사rewrite_tag: $error_severity ^(ERROR|FATAL|PANIC)$ ops.postgres true오류 수준만 ops.postgres 태그로 한 부 더 만듦. 끝의 true가 원본 유지
5. 출력audit.postgres → OpenSearch, ops.postgres → Loki감사는 전부, 운영은 오류만

복사본은 마스킹 필터 뒤에서 만들어지므로 Loki에도 가려진 상태로 갑니다. 필터 순서가 곧 보안입니다. 히어로의 시뮬레이터에서 "비밀번호 변경 DDL"과 "없는 테이블 조회"를 비교해 보세요.

원칙: 한 로그는 한 수집기가 읽는다

8편에서 cust-a-db의 Alloy가 이미 PostgreSQL 로그 파일을 읽어 Loki로 보내고 있습니다. 여기에 Fluent Bit이 같은 로그를 또 읽으면 Loki에 중복이 생기고, 두 수집기의 위치 기록(position)이 따로 놀아 장애 때 원인을 찾기 어렵습니다. 이 편에서는 PostgreSQL 로그를 Fluent Bit이 전담하고, Alloy는 journal만 맡도록 바꿉니다(Lab 3). journal에는 sshd와 sudo 기록도 있어 Loki(운영 관점)와 OpenSearch(감사 보관)에 모두 들어가지만, 이것은 목적이 다른 의도적인 이중 보관이며 OpenSearch 쪽은 Fluent Bit이 필터로 그 두 종류만 골라 읽습니다.

7ELK를 유지하는 고객사

1편의 TOP 4 중 4번 조합(Prometheus + ELK)을 쓰는 고객사를 맡았을 때의 점검 포인트입니다.

Elasticsearch 라이선스의 변화

버전라이선스MSP가 볼 점
7.10 이하Apache 2.0 (OSS 배포판), 기본 배포판은 Elastic License오래되어 보안 패치가 끊긴 버전일 가능성. 업그레이드 경로 검토
7.11 ~ 8.15SSPL 또는 Elastic License 2.0(ELv2) 중 선택ELv2는 소프트웨어를 제3자에게 호스팅 또는 관리형 서비스로 제공하는 것을 제한
8.16 이후SSPL, ELv2에 AGPLv3 선택지 추가 (2024년 발표)AGPL은 오픈소스이지만 1편 9장의 네트워크 조항 검토 필요
MSP에게 특히 중요한 점

MSP가 Elasticsearch를 운영해 고객에게 "로그 검색 서비스"로 제공하는 사업 모델이라면, 사용 중인 배포판과 라이선스가 그것을 허용하는지 반드시 법무 검토를 받아야 합니다. 고객사가 자체 라이선스로 자기 환경에서 쓰고 MSP는 운영만 대행하는 경우와는 판단이 달라질 수 있습니다. 보안, 머신러닝 등 일부 기능은 유료 구독 등급에 묶여 있으므로 "어떤 기능을 쓰고 있는가"도 함께 확인합니다.

점검 체크리스트

  • 버전과 배포판: GET /의 version.number와 build_flavor(default, oss).
  • 라이선스 상태: GET _license(basic, trial, 유료 등급).
  • 수집 경로: Beats와 Logstash 버전. 최근 Elastic 클라이언트는 연결 대상이 Elasticsearch인지 확인하므로, OpenSearch로 옮길 때는 Fluent Bit, Logstash와 OpenSearch 출력 플러그인, Data Prepper 같은 대안이 필요합니다.
  • 이전 가능성: Elasticsearch 7.10 이하의 스냅샷은 OpenSearch로 복원할 수 있지만 8.x 스냅샷은 그대로 복원되지 않습니다. 이 경우 원격 재색인(reindex from remote)이나 수집기를 두 곳으로 보내 일정 기간 병행하는 방식을 씁니다.
  • 유지 판단: 대시보드와 알림 자산이 많고 라이선스 조건이 고객사 사용 형태와 맞으면 유지, 그렇지 않으면 OpenSearch 이전을 장기 과제로. 이번 편에서 만든 Fluent Bit 설정은 출력만 es로 바꾸면 Elasticsearch에도 그대로 쓸 수 있습니다.

10Lab 3. PostgreSQL 감사 로그

PostgreSQL 15부터 들어온 jsonlog 형식으로 감사 로그를 남깁니다. JSON이라 Fluent Bit이 파싱할 필요가 거의 없고, 필드(user, dbname, remote_host, error_severity...)가 그대로 OpenSearch 필드가 됩니다. Ubuntu 24.04의 기본 PostgreSQL은 16입니다.

~/obs-lab/vm/postgres/pg-audit.conf

# /etc/postgresql/16/main/conf.d/audit.conf
logging_collector = on
log_destination = 'stderr,jsonlog'
log_directory = '/var/log/postgresql/json'
log_filename = 'postgresql-%Y-%m-%d.log'      # jsonlog 파일은 확장자가 .json으로 바뀌어 생성됨
log_file_mode = 0640
log_rotation_age = 1d
log_connections = on
log_disconnections = on
log_statement = 'ddl'                          # CREATE, ALTER, DROP 등 구조 변경 문을 기록
multipass transfer ~/obs-lab/vm/postgres/pg-audit.conf cust-a-db:/tmp/
multipass exec cust-a-db -- sudo bash -c '
  install -d -o postgres -g adm -m 0750 /var/log/postgresql/json
  install -m 0644 /tmp/pg-audit.conf /etc/postgresql/16/main/conf.d/audit.conf
  systemctl restart postgresql
  sleep 2; ls -l /var/log/postgresql/json/'
예상 결과 postgresql-YYYY-MM-DD.log와 postgresql-YYYY-MM-DD.json이 생깁니다. sudo tail -1 ...json으로 보면 {"timestamp":"...","user":...,"error_severity":"LOG","message":"..."} 형태입니다. log_destination에 stderr를 함께 두어 사람이 읽기 쉬운 텍스트 로그도 같은 폴더에 남깁니다.

Alloy에서 PostgreSQL 수집 빼기

logging_collector를 켜면 PostgreSQL 로그가 새 폴더로 옮겨 가므로, 8편의 Alloy 설정은 더 이상 새 로그를 읽지 못합니다. 6장의 원칙대로 PostgreSQL은 Fluent Bit에 맡기고 Alloy는 journal만 보내게 바꿉니다.

설정 파일

~/obs-lab/vm/fluent-bit/fluent-bit.yaml

# cust-a-db VM용 Fluent Bit 설정 (YAML 형식, Fluent Bit 5.x)
# 감사·보안 로그 → OpenSearch,  그중 오류 수준 로그는 복사해서 → Loki (운영)
service:
  flush: 2
  log_level: info
  http_server: on            # :2020/api/v1/metrics, /api/v2/metrics/prometheus (메트릭)
  http_listen: 0.0.0.0
  http_port: 2020
  storage.path: /var/lib/fluent-bit/buffer     # 전송 실패 시 디스크에 버퍼링
  storage.sync: normal

parsers:
  - name: pg_json
    format: json             # PostgreSQL jsonlog 한 줄 = JSON 한 개

pipeline:
  inputs:
    # 1) PostgreSQL 감사 로그 (jsonlog): 접속, 접속 종료, DDL, 인증 실패
    - name: tail
      tag: audit.postgres
      path: /var/log/postgresql/json/*.json
      parser: pg_json
      db: /var/lib/fluent-bit/pg.db
      read_from_head: true
      storage.type: filesystem

    # 2) SSH 접속 기록 (journal)
    - name: systemd
      tag: audit.access.sshd
      systemd_filter: SYSLOG_IDENTIFIER=sshd
      db: /var/lib/fluent-bit/journal-sshd.db
      strip_underscores: true
      lowercase: true
      storage.type: filesystem

    # 3) sudo 사용 기록 (journal)
    - name: systemd
      tag: audit.access.sudo
      systemd_filter: SYSLOG_IDENTIFIER=sudo
      db: /var/lib/fluent-bit/journal-sudo.db
      strip_underscores: true
      lowercase: true
      storage.type: filesystem

  filters:
    # 모든 감사 로그에 공통 필드
    - name: modify
      match: 'audit.*'
      add:
        - customer cust-a
        - host cust-a-db

    # SQL 문 안의 비밀번호 가리기 (8편의 마스킹 원칙)
    - name: lua
      match: audit.postgres
      script: /etc/fluent-bit/redact.lua
      call: redact

-- 감사 로그의 SQL 문에서 비밀번호 값을 가림 (PostgreSQL은 log_statement로 원문을 그대로 남김)
function redact(tag, timestamp, record)
  local msg = record["message"]
  if msg == nil then
    return 0, timestamp, record            -- 바꿀 것 없음
  end
  local new, n = string.gsub(msg, "([Pp][Aa][Ss][Ss][Ww][Oo][Rr][Dd]%s+)'[^']*'", "%1'[REDACTED]'")
  if n == 0 then
    return 0, timestamp, record
  end
  record["message"] = new
  record["redacted"] = true
  return 2, timestamp, record              -- 2: 레코드만 바꾸고 타임스탬프는 유지
end

Lua 스크립트의 반환값 2는 "레코드를 바꿨지만 시각은 그대로"라는 뜻입니다. 작성 중 이 함수를 Lua 5.4로 실행해, ALTER ROLE ... PASSWORD 'Sup3rS3cret!'와 소문자 password '...'가 모두 '[REDACTED]'로 바뀌고 비밀번호가 없는 DDL은 그대로 통과하는 것을 확인했습니다.

장기 보관: 스냅샷

1년 이상 보관 의무가 있는 감사 로그를 OpenSearch의 디스크에 계속 두면 비쌉니다. 일정 기간이 지난 인덱스는 오브젝트 스토리지로 스냅샷을 떠 두고 클러스터에서는 지우는 것이 일반적입니다. OpenSearch는 S3 호환 저장소를 위한 repository-s3 플러그인과 ISM의 snapshot 동작을 제공합니다. 이 랩에서는 실습하지 않지만, 순서는 플러그인 설치(차트의 plugins.installList), 접근 키를 키스토어에 등록, 2편의 opensearch-snapshots 버킷을 스냅샷 저장소로 등록, ISM 정책의 delete 앞에 snapshot 동작 추가입니다. 복원 훈련을 정기적으로 하지 않은 백업은 백업이 아니라는 점도 함께 기억하세요.

15트러블슈팅

증상을 눌러 원인과 해결 방법을 확인하세요.

OpenSearch 파드가 시작 직후 종료: max virtual memory areas vm.max_map_count is too lowLab 1

호스트의 vm.max_map_count가 262144보다 작습니다. Lab 1의 sysctl을 호스트에서 적용했는지 확인합니다. macOS는 values에 sysctlInit.enabled: true를 넣어 초기화 컨테이너가 설정하게 합니다.

시작 실패: initial admin password 관련 오류Lab 1

2.12 이상은 OPENSEARCH_INITIAL_ADMIN_PASSWORD가 반드시 있어야 하고 복잡도 규칙을 만족해야 합니다. Secret 이름과 키, 비밀번호 강도를 확인합니다.

클러스터 상태 yellowLab 1, 2

노드가 하나인데 레플리카가 1 이상인 인덱스가 있어 복제본을 둘 곳이 없는 상태입니다. 템플릿의 number_of_replicas: 0이 적용되기 전에 만들어진 인덱스라면 PUT 인덱스/_settings {"index":{"number_of_replicas":0}}으로 고칩니다. 시스템 인덱스는 보통 자동으로 맞춰집니다.

Fluent Bit 로그: 401 또는 403Lab 4

401은 사용자, 비밀번호 오류(환경 파일과 Lab 2의 FB_PW), 403은 역할 권한 부족입니다. 403이면 응답에 어떤 동작이 거부됐는지 나오므로 그 동작을 fluentbit-writer 역할에 추가합니다.

Fluent Bit 로그: mapper_parsing_exception, 일부 문서만 거부Lab 4, 5

3장의 매핑 함정입니다. trace_error: on이면 거부된 문서와 이유가 로그에 남습니다. 대표적으로 IP 타입으로 매핑된 필드에 [local] 같은 값이 들어온 경우입니다. 템플릿을 고쳐 다음 날 인덱스부터 적용하고, 당일 인덱스는 재색인합니다.

Fluent Bit 로그: Action/metadata line [1] contains an unknown parameter [_type]Lab 4

suppress_type_name: on이 빠진 경우입니다. OpenSearch 2.0 이상은 매핑 타입을 지원하지 않습니다.

Fluent Bit 시작 실패: 설정 파일 오류Lab 4

--dry-run으로 줄 번호를 확인합니다. YAML 들여쓰기, match 값의 따옴표('audit.*'처럼 별표가 있으면 따옴표 권장), 클래식 형식의 키를 YAML에 섞어 쓴 경우가 흔합니다. 환경 변수가 비어 있으면 ${OS_HOST}가 빈 값이 되어 연결 오류가 납니다.

PostgreSQL 감사 로그가 생기지 않음Lab 3

sudo -u postgres psql -c "show log_destination"로 설정이 적용됐는지 봅니다. logging_collector는 재시작해야 바뀝니다. 로그 폴더의 소유자가 postgres인지, conf.d 디렉터리가 postgresql.conf의 include 대상인지(Ubuntu 기본값은 포함) 확인합니다.

Loki에 PostgreSQL 로그가 두 번씩 들어옴Lab 3

Alloy의 PostgreSQL 수집을 빼지 않아 두 수집기가 같은 로그를 보내는 경우입니다. Lab 3의 Alloy 설정 교체를 확인합니다(6장의 원칙).

Dashboards 로그인 후 인덱스가 안 보임Lab 5

Discover는 인덱스 패턴(또는 최근 버전의 데이터 소스, 데이터셋)을 먼저 만들어야 합니다. 고객사 읽기 역할로 로그인했다면 그 역할의 인덱스 패턴과 일치하는지도 확인합니다.

오늘의 핵심

  1. 감사·보안 로그는 장기 보존, 자유로운 필드 검색과 집계, 무결성, 세밀한 접근 통제가 필요해 OpenSearch에 둡니다. 모든 로그가 아니라 골라서 보냅니다.
  2. 인덱스 이름에 고객사를 넣고, 템플릿으로 매핑을 고정하고(keyword, text, date), 샤드 크기를 관리합니다. 동적 매핑의 타입 충돌을 조심합니다.
  3. ISM으로 hot → warm(읽기 전용, 병합) → delete를 자동화하고, 장기 보관은 스냅샷으로 오브젝트 스토리지에 둡니다.
  4. Fluent Bit은 태그로 라우팅합니다. rewrite_tag로 복사해 감사와 운영을 나누고, 필터 순서(마스킹 다음 복사)가 보안을 결정합니다. 설정은 YAML로 씁니다.
  5. 한 로그는 한 수집기가 읽습니다. Alloy와 Fluent Bit의 담당을 나눕니다.
  6. ELK 고객사는 버전, 배포판, 라이선스(ELv2의 관리형 서비스 제한, AGPL 선택지)와 수집기 호환성을 점검합니다.

Level 3을 마치며

7~10편으로 로그 계층이 완성되었습니다. 운영 로그는 Alloy와 Loki로 싸게 모아 LogQL로 원인을 찾고, 감사·보안 로그는 Fluent Bit과 OpenSearch로 오래, 자유롭게 찾을 수 있게 남깁니다. 1편 히어로의 "그 순간 무슨 일이 있었나"에 답할 수 있게 되었습니다. 남은 질문은 "요청이 어디를 거쳤고 어디서 시간이 사라졌나"입니다.

다음 편 예고: 11편 OpenTelemetry 통합 관점 (Level 4 시작)

트레이스로 넘어가기 전에, 메트릭, 로그, 트레이스를 하나의 표준으로 묶는 OpenTelemetry를 LGTM 스택 관점에서 다시 정리합니다. OTLP와 리소스 속성, 시맨틱 컨벤션, Collector와 Alloy의 세 가지 배치 패턴(에이전트, 게이트웨이, 혼합)을 비교하고, hub에 OTLP 게이트웨이(2편에서 예약한 30317, 30318 포트)를 세워 edge의 OTel Demo와 VM의 데이터가 이 게이트웨이를 거쳐 Prometheus, Loki, 그리고 12편의 Tempo로 가게 합니다. OTel Operator로 코드 수정 없이 자동 계측을 넣는 방법도 다룹니다.
