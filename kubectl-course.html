01 / 기초

kubectl이 실제로 하는 일

kubectl은 클러스터를 직접 조작하지 않습니다. kubectl이 하는 일은 딱 세 가지입니다.

  1. 여러분이 입력한 문장을 HTTP 요청으로 바꾼다.
  2. 그 요청을 API 서버로 보낸다.
  3. 돌아온 JSON을 사람이 읽기 좋은 표로 그려준다.

즉 kubectl은 쿠버네티스 API 서버 전용 HTTP 클라이언트입니다. 이 사실을 이해하면 뒤에 나오는 거의 모든 동작이 설명됩니다. 왜 권한 오류가 나는지, 왜 -o json이 항상 가능한지, 왜 apply가 서버 쪽 상태와 비교되는지 전부 여기서 나옵니다.

신입이 가장 많이 하는 오해

kubectl apply가 성공했다는 건 “요청서가 접수되었다”는 뜻이지 “서비스가 떴다”는 뜻이 아닙니다. 쿠버네티스는 선언형 시스템이라 접수와 실현 사이에 시간이 있습니다. 그래서 apply 뒤에는 항상 rollout status나 get pod -w로 결과를 확인해야 합니다.

직접 확인해 보기

kubectl이 정말 HTTP 요청을 보내는지 -v(verbosity) 플래그로 눈으로 볼 수 있습니다. 이건 문제 해결할 때도 아주 유용합니다.

# -v=6 : 요청 URL만 / -v=8 : 헤더와 응답 본문까지 전부
kubectl get pods -v=6

I0912 10:22:41.113  round_trippers.go:553] GET https://10.0.0.1:6443/api/v1/namespaces/default/pods?limit=500 200 OK in 23 milliseconds

# 한 단계 더: 요청 본문/응답 JSON까지 보고 싶을 때
kubectl get pod nginx -v=8

# API 서버에 프록시를 열고 curl로 직접 두드려 보기 (개념 확인용)
kubectl proxy --port=8080 &
curl -s localhost:8080/api/v1/namespaces/default/pods | head -20

02 / 기초

설치와 버전 규칙

MSP 업무라면 고객사마다 클러스터 버전이 다릅니다. kubectl 버전을 아무렇게나 쓰면 안 되는 이유가 여기 있습니다.

# 1) 최신 안정 버전 번호 확인
curl -sL https://dl.k8s.io/release/stable.txt
v1.31.4

# 2) 원하는 버전 지정해서 내려받기 (고객사 클러스터 버전에 맞춰서)
VER=v1.31.4
curl -LO "https://dl.k8s.io/release/$VER/bin/linux/amd64/kubectl"

# 3) 체크섬 검증 — 운영 환경에서는 건너뛰지 마세요
curl -LO "https://dl.k8s.io/release/$VER/bin/linux/amd64/kubectl.sha256"
echo "$(cat kubectl.sha256)  kubectl" | sha256sum --check
kubectl: OK

# 4) 설치 (install 한 번으로 복사+권한+소유자 처리)
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl

# 5) 확인 — client 버전만 보려면 --client
kubectl version --client
# Homebrew (가장 간단)
brew install kubectl

# Apple Silicon에 특정 버전을 직접 받고 싶을 때
curl -LO "https://dl.k8s.io/release/v1.31.4/bin/darwin/arm64/kubectl"
chmod +x kubectl && sudo mv kubectl /usr/local/bin/

고객사 A는 1.28, 고객사 B는 1.31인 상황. 이럴 땐 버전별 바이너리를 두고 심볼릭 링크를 바꿔 씁니다.

# ~/bin 아래에 버전별로 보관
mkdir -p ~/bin/kube
# kubectl-1.28.9, kubectl-1.31.4 ... 이런 식으로 저장했다고 가정

# 전환용 셸 함수 (~/.bashrc 에 넣기)
kuse() {
  ln -sf ~/bin/kube/kubectl-"$1" ~/bin/kubectl
  kubectl version --client | head -1
}

kuse 1.28.9   # A사 작업 전
kuse 1.31.4   # B사 작업 전

# 더 편한 방법: asdf 또는 krew 플러그인 사용 (17장 참고)

버전 스큐(skew) 규칙 — 시험에도 나오고 실무에도 나옵니다

kubectl은 API 서버와 마이너 버전 기준 ±1까지만 공식 지원됩니다. 즉 API 서버가 1.31이면 kubectl은 1.30 ~ 1.32까지 괜찮습니다.

API 서버지원되는 kubectl벗어나면 생기는 일
v1.31v1.30 / v1.31 / v1.32정상
v1.31v1.26 (너무 낮음)신규 리소스가 안 보이고, apply 시 필드가 조용히 누락될 수 있음
v1.24v1.31 (너무 높음)제거된 API 그룹을 호출해 the server could not find the requested resource 발생
 
kubectl version
Client Version: v1.31.4
Kustomize Version: v5.4.2
Server Version: v1.28.9

# 스크립트에서 쓰려면 JSON으로 뽑아 jq로 비교
kubectl version -o json | jq -r '"client=\(.clientVersion.gitVersion) server=\(.serverVersion.gitVersion)"'
client=v1.31.4 server=v1.28.9

주의 · 조용한 실패가 가장 무섭습니다

버전이 크게 어긋나면 오류가 나는 게 아니라 필드가 무시된 채 성공하기도 합니다. “분명 apply 했는데 설정이 안 먹어요”의 흔한 원인입니다. 고객사 작업 전 kubectl version을 먼저 찍는 습관을 들이세요.

03 / 기초 · 사고 예방 1순위

kubeconfig, 컨텍스트, 네임스페이스

실무 사고의 압도적 1위는 “개발 클러스터인 줄 알고 운영 클러스터에서 실행”입니다. 명령어를 아무리 잘 외워도 이 부분이 흐릿하면 언젠가 사고가 납니다. 먼저 여기부터 확실히 잡고 갑시다.

kubeconfig 파일의 구조

기본 위치는 ~/.kube/config입니다. 이 파일은 세 가지 목록과 그것들을 묶는 하나의 포인터로 되어 있습니다.

clusters

어디로 접속할지. API 서버 주소와 CA 인증서.

users

누구로 접속할지. 인증서, 토큰, 또는 외부 인증 명령(exec).

contexts

cluster + user + namespace 세트. 현재 컨텍스트가 지금 명령이 날아갈 목적지입니다.

apiVersion: v1
kind: Config
current-context: prod-cluster-admin   # ← 지금 명령이 날아가는 곳
clusters:
- name: prod-cluster
  cluster:
    server: https://prod-api.example.com:6443
    certificate-authority-data: LS0tLS1CRUdJTi...
users:
- name: admin
  user:
    client-certificate-data: LS0tLS1CRUdJTi...
    client-key-data: LS0tLS1CRUdJTi...
contexts:
- name: prod-cluster-admin
  context:
    cluster: prod-cluster
    user: admin
    namespace: payment        # 생략하면 default

컨텍스트를 다루는 명령어

# 현재 어디에 연결돼 있나 (가장 자주 쓰는 명령)
kubectl config current-context
dev-cluster-admin

# 등록된 컨텍스트 전체 보기 — * 표시가 현재 컨텍스트
kubectl config get-contexts
CURRENT   NAME                 CLUSTER        AUTHINFO   NAMESPACE
*         dev-cluster-admin    dev-cluster    admin      default
          prod-cluster-admin   prod-cluster   admin      payment

# 컨텍스트 전환
kubectl config use-context prod-cluster-admin

# 현재 컨텍스트의 기본 네임스페이스 바꾸기 (-n 을 매번 안 써도 됨)
kubectl config set-context --current --namespace=payment

# 민감정보 감춘 채 설정 보기 / 전체 보기
kubectl config view
kubectl config view --raw     # 인증서까지 전부 (주의: 화면 공유 중 금지)

# 안 쓰는 컨텍스트 정리
kubectl config delete-context old-cluster-admin

리눅스 조합 · KUBECONFIG 여러 개 합치기

고객사별로 받은 kubeconfig 파일이 흩어져 있을 때, 콜론으로 이어 붙이면 kubectl이 자동으로 병합해서 인식합니다.

# 임시로 합쳐서 보기
export KUBECONFIG=~/.kube/config:~/.kube/custA.yaml:~/.kube/custB.yaml
kubectl config get-contexts

# ~/.kube/configs/ 아래 모든 파일을 자동으로 합치기 (~/.bashrc 에 추가)
export KUBECONFIG=$(find ~/.kube/configs -type f -name '*.yaml' | paste -sd ':' -)

# 병합 결과를 하나의 파일로 영구 저장
KUBECONFIG=~/.kube/config:~/.kube/custA.yaml kubectl config view --flatten > ~/.kube/merged
mv ~/.kube/merged ~/.kube/config

# 특정 명령 한 번만 다른 설정으로 실행 (가장 안전한 방식)
KUBECONFIG=~/.kube/custA.yaml kubectl get nodes

사고를 막는 프롬프트 설정

지금 어느 클러스터인지 항상 눈에 보이게 만드는 것이 가장 값싼 안전장치입니다. 운영 클러스터일 때 빨갛게 표시되도록 해 둡시다.

# 운영(prod) 컨텍스트면 빨강, 아니면 파랑으로 표시
kube_ps1() {
  local ctx ns color
  ctx=$(kubectl config current-context 2>/dev/null) || return
  ns=$(kubectl config view --minify -o jsonpath='{..namespace}' 2>/dev/null)
  ns=${ns:-default}
  if [[ "$ctx" == *prod* ]]; then color='\[\e[1;31m\]'; else color='\[\e[1;36m\]'; fi
  echo -e "${color}(${ctx}:${ns})\[\e[0m\] "
}
PS1='$(kube_ps1)\u@\h:\w\$ '

# 결과 예시
(dev-cluster-admin:default) engineer@bastion:~$ 
(prod-cluster-admin:payment) engineer@bastion:~$   ← 빨간색으로 표시됨

실무 사고 사례

야근 중 터미널 두 개를 띄워 놓고 작업하다가, 개발 창인 줄 알고 운영 창에서 kubectl delete deploy --all을 실행한 사례는 업계에 수없이 많습니다. 탭 이름, 프롬프트 색, 창 배경색 — 세 가지 다 구분해 두세요. 운영 터미널은 배경을 진한 빨강으로 두는 회사도 많습니다.

모든 명령에 통하는 공통 옵션

옵션의미메모
-n, --namespace대상 네임스페이스안 쓰면 컨텍스트의 기본값
-A, --all-namespaces전체 네임스페이스조회 전용으로만 쓰세요
-o, --output출력 형식wide/yaml/json/jsonpath/name 등
-l, --selector레이블 셀렉터8장에서 상세히
--context이 명령만 다른 컨텍스트로컨텍스트 전환 없이 안전하게
--dry-run=client|server실제로 실행하지 않음운영 작업 전 필수

출력 제어와 jsonpath

kubectl의 진짜 힘은 -o 옵션에 있습니다. 원하는 값만 뽑아낼 수 있으면 수작업이 자동화로 바뀝니다. MSP 업무에서 고객사 리포트를 만들 때 가장 많이 쓰는 구간입니다.

-o 값결과주 용도
wide기본 표 + 노드/IP 등 추가 열일상 조회
yaml리소스 전체를 YAML로설정 확인, 백업
json리소스 전체를 JSON으로jq와 조합
namepod/이름 형태만xargs로 넘기기
jsonpath지정한 필드만스크립트에서 값 하나 뽑기
custom-columns내가 정의한 표리포트용 표 만들기
go-templateGo 템플릿으로 자유 출력복잡한 가공

jsonpath — 이것만 알면 됩니다

문법이 어려워 보이지만 실무에서 쓰는 패턴은 다섯 개뿐입니다.

# [1] 값 하나 뽑기 — 중괄호와 점 표기
kubectl get pod api-7d8f -o jsonpath='{.status.podIP}'
10.244.1.15

# [2] 목록 전체 순회 — .items[*]
kubectl get pods -o jsonpath='{.items[*].metadata.name}'
api-7d8f redis-0 worker-2p9k

# [3] 줄바꿈과 탭 — range/end 로 예쁘게
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.podIP}{"\n"}{end}'
api-7d8f      10.244.1.15
redis-0       10.244.2.8

# [4] 조건 필터 — ?(@.필드=="값")
kubectl get pods -o jsonpath='{.items[?(@.status.phase=="Running")].metadata.name}'

# [5] 중첩 배열 — 컨테이너 이미지 전부 뽑기
kubectl get pods -A -o jsonpath='{.items[*].spec.containers[*].image}' | tr ' ' '\n' | sort -u
nginx:1.25
redis:7.2-alpine
registry.example.com/api:v2.3.1

레이블 · 셀렉터 · 필드 선택

쿠버네티스에서 리소스를 이름으로 고르는 일은 드뭅니다. 파드 이름은 배포할 때마다 바뀌니까요. 대신 레이블로 고릅니다. 서비스가 파드를 찾는 방식도, 디플로이먼트가 자기 파드를 관리하는 방식도 전부 레이블입니다.

# 레이블 보면서 조회

kubectl get pods -L app,env

# [등식] 정확히 일치
kubectl get pods -l app=api
kubectl get pods -l app!=api

# [AND] 쉼표는 AND (OR은 없습니다 — 자주 헷갈리는 부분)
kubectl get pods -l app=api,env=prod

# [집합] in / notin
kubectl get pods -l 'env in (prod,staging)'
kubectl get pods -l 'tier notin (frontend)'

kubectl get pods -l app            # app 레이블이 있는 것
kubectl get pods -l '!app'         # app 레이블이 없는 것

# 추가

kubectl label pod api-7d8f env=staging --overwrite

kubectl label pod api-7d8f team-

kubectl label pods -l app=api maintenance=2026-09-12

kubectl annotate deploy api "change-ticket=CHG-10293" --overwrite

문제가 생긴 파드를 지우면 증거가 사라집니다. 대신 서비스 셀렉터와 어긋나게 레이블을 바꾸면, 그 파드는 트래픽에서만 빠지고 살아 있습니다. 디플로이먼트가 대체 파드를 새로 띄워 주므로 서비스 영향도 없습니다. 그 상태로 로그와 힙덤프를 마음껏 확보하세요.

# before: app=api 레이블로 서비스에 물려 있는 상태
kubectl label pod api-7d8f app=api-quarantine --overwrite

# 서비스 엔드포인트에서 빠졌는지 확인
kubectl get endpoints api-service

# 레플리카셋이 부족분을 감지해 새 파드를 띄운다
kubectl get pods -l app=api

# 조사 끝나면 삭제
kubectl delete pod api-7d8f

# 특정 노드 위의 파드만

kubectl get pods -A --field-selector metadata.namespace!=default

생성: create vs apply

쿠버네티스에는 두 가지 작업 방식이 있습니다. 이 차이를 모르면 “왜 두 번째 실행하면 에러가 나죠?”에서 멈춥니다.

명령형 (imperative) — “이렇게 해”

create, run, expose, scale, edit. 빠르고 편하지만 기록이 남지 않습니다. 실습·테스트·긴급 조치용.

선언형 (declarative) — “이 상태가 되게 해”

apply -f. YAML이 곧 문서이자 이력. Git에 넣어 리뷰하고 롤백합니다. 운영은 무조건 이쪽.

createapplyreplace
이미 있으면에러 (AlreadyExists)변경 사항만 반영통째로 교체
없으면생성생성에러 (--force 시 삭제 후 재생성)
반복 실행불가안전하게 가능가능하지만 위험
YAML에 없는 필드—유지됨사라짐
운영 권장△ 일부만표준비권장

replace가 위험한 이유

replace는 YAML에 적히지 않은 필드를 전부 지웁니다. HPA가 조정해 둔 replicas, 운영 중 붙인 어노테이션, 다른 컨트롤러가 채워 넣은 값이 한꺼번에 날아갑니다. replace --force는 리소스를 삭제하고 다시 만들기 때문에 서비스가 잠시 끊깁니다. 습관적으로 쓰지 마세요.

실무 최고의 기술: --dry-run으로 YAML 뼈대 만들기

YAML을 처음부터 손으로 쓰는 사람은 없습니다. 명령형으로 만들고 --dry-run=client -o yaml로 뽑아서 다듬는 것이 표준 작업 흐름입니다. 자격증 시험(CKA)에서도 이 기술로 시간을 법니다.

# 디플로이먼트 뼈대
kubectl create deployment api --image=nginx:1.25 --replicas=3 \
  --dry-run=client -o yaml > deploy.yaml

# 파드 하나
kubectl run debug --image=busybox --dry-run=client -o yaml \
  --command -- sleep 3600 > pod.yaml

# 서비스
kubectl expose deployment api --port=80 --target-port=8080 --name=api-svc \
  --dry-run=client -o yaml > svc.yaml

# 컨피그맵 / 시크릿
kubectl create configmap app-conf --from-literal=LOG_LEVEL=info \
  --from-file=./nginx.conf --dry-run=client -o yaml > cm.yaml

kubectl create secret generic db-cred --from-literal=password='S3cr3t!' \
  --dry-run=client -o yaml > secret.yaml

# 크론잡
kubectl create cronjob backup --image=busybox --schedule="0 3 * * *" \
  --dry-run=client -o yaml -- /bin/sh -c "echo backup" > cj.yaml

# 서비스어카운트 / 롤바인딩
kubectl create sa deploy-bot --dry-run=client -o yaml
kubectl create rolebinding bot-edit --clusterrole=edit --serviceaccount=ci:deploy-bot \
  --dry-run=client -o yaml

client와 server 드라이런의 차이

--dry-run=client는 내 PC에서만 YAML을 만들어 봅니다(서버에 안 감). --dry-run=server는 API 서버까지 보내서 검증만 하고 저장은 안 합니다. 어드미션 웹훅·기본값 주입·쿼터 검사까지 실제와 똑같이 확인되므로, 운영 반영 직전 최종 점검은 server로 하세요.

create로 만든 걸 나중에 apply 하면?

create는 last-applied-configuration 어노테이션을 남기지 않습니다. 그래서 나중에 apply 하면 kubectl이 “이전 상태”를 몰라 필드 삭제를 감지하지 못합니다. 처음부터 apply로 통일하거나, kubectl apply --save-config로 만드세요.

변경: edit · patch · set · scale

이미 떠 있는 것을 고치는 방법은 네 가지가 있고, 고객사 환경에서는 어느 걸 쓰느냐가 곧 사고 여부를 가릅니다.

에디터를 열어 직접 수정합니다. 빠르지만 Git에 흔적이 남지 않아 운영 환경에서는 응급 상황에만 쓰세요.

kubectl edit deployment api

# 에디터 지정 (기본은 vi)
KUBE_EDITOR="nano" kubectl edit deployment api
export KUBE_EDITOR="code --wait"   # VS Code로 열기

# 저장했는데 반영이 안 될 때 → 대개 YAML 문법 오류.
# kubectl은 /tmp 에 임시본을 남기고 경로를 알려 줍니다.
error: ... A copy of your changes has been stored to "/tmp/kubectl-edit-3f9x.yaml"

edit의 함정

edit으로 바꾼 내용은 다음 번 apply -f 때 조용히 덮어써집니다. 급하게 edit으로 조치했다면 반드시 Git의 YAML에도 같은 변경을 반영하세요. 안 그러면 다음 배포 때 장애가 재발합니다.

명령 한 줄로 특정 필드만 바꿉니다. 스크립트·자동화에 가장 적합합니다. 세 가지 방식이 있습니다.

# [1] strategic merge (기본) — 배열을 똑똑하게 병합, 쿠버네티스 전용
kubectl patch deployment api -p \
  '{"spec":{"template":{"spec":{"containers":[{"name":"api","image":"api:v2.3.2"}]}}}}'

# [2] JSON merge patch — 배열을 통째로 교체
kubectl patch deployment api --type=merge -p '{"spec":{"replicas":5}}'

# [3] JSON patch — 경로를 지정해 추가/교체/삭제. 가장 정밀함
kubectl patch deployment api --type=json -p \
  '[{"op":"replace","path":"/spec/replicas","value":4}]'

# 어노테이션 하나 삭제 (~1 은 슬래시의 이스케이프)
kubectl patch deploy api --type=json -p \
  '[{"op":"remove","path":"/metadata/annotations/deprecated~1flag"}]'

# 패치 내용을 파일로
kubectl patch deploy api --patch-file patch.yaml

자주 바꾸는 항목에 대한 전용 단축 명령입니다. 오타 위험이 적어 배포 스크립트에서 선호됩니다.

# 이미지 교체 — 가장 많이 쓰는 배포 명령
kubectl set image deployment/api api=registry.example.com/api:v2.3.2

# 컨테이너가 여러 개면 각각 지정
kubectl set image deploy/api api=api:v2.3.2 sidecar=envoy:1.30

# 리소스 요청/제한 변경
kubectl set resources deployment api -c=api \
  --requests=cpu=200m,memory=256Mi --limits=cpu=1,memory=512Mi

# 환경변수
kubectl set env deployment/api LOG_LEVEL=debug
kubectl set env deployment/api LOG_LEVEL-           # 삭제
kubectl set env deployment/api --from=configmap/app-conf

# 서비스어카운트 교체
kubectl set serviceaccount deployment api deploy-bot
# 레플리카 수 조정
kubectl scale deployment api --replicas=5

# 현재 값이 3일 때만 5로 (경쟁 상태 방지 — 자동화에서 중요)
kubectl scale deployment api --current-replicas=3 --replicas=5

# 레이블로 여러 개 한꺼번에
kubectl scale deployment -l tier=backend --replicas=2

# 0으로 줄이기 = 서비스 중단 (야간 비용 절감, 긴급 차단에 사용)
kubectl scale deployment api --replicas=0

# 오토스케일러 생성
kubectl autoscale deployment api --min=2 --max=10 --cpu-percent=70
kubectl get hpa

HPA가 붙은 워크로드에 scale을 쓰면

수동으로 바꿔도 HPA가 몇 초 뒤 원래대로 되돌립니다. 긴급하게 고정해야 한다면 HPA를 먼저 멈추거나(kubectl delete hpa api) min/max를 조정하세요. 아무 설명 없이 “스케일이 안 먹어요”의 90%가 이 경우입니다.

11 / 쓰기

배포와 롤아웃

디플로이먼트를 바꾸면 새 레플리카셋이 생기고 파드가 차례로 교체됩니다. 이 과정을 지켜보고, 멈추고, 되돌리는 명령이 rollout입니다. MSP 엔지니어가 배포 창구에서 가장 많이 치는 명령이기도 합니다.

# [1] 무엇이 바뀌는지 먼저 확인
kubectl diff -f deploy.yaml

# [2] 적용 (--record 는 폐기됨. 대신 어노테이션으로 이력을 남깁니다)
kubectl apply -f deploy.yaml
kubectl annotate deploy api kubernetes.io/change-cause="CHG-10293 api v2.3.2 배포" --overwrite

# [3] 진행 상황 지켜보기 — 끝날 때까지 블로킹, 실패 시 종료 코드 1
kubectl rollout status deployment/api --timeout=5m
Waiting for deployment "api" rollout to finish: 2 of 3 updated replicas are available...
deployment "api" successfully rolled out

# [4] 파드 상태 눈으로 확인
kubectl get pods -l app=api -o wide

# [5] 문제 있으면 즉시 되돌리기
kubectl rollout undo deployment/api

롤아웃 명령 전체

명령하는 일실무 포인트
rollout status완료될 때까지 대기CI 파이프라인의 성공 판정 기준
rollout history리비전 목록--revision=3으로 상세 확인
rollout undo이전 리비전으로 복귀장애 시 1순위 대응
rollout pause진행 중단카나리 배포에 활용
rollout resume재개pause 후 반드시 쌍으로
rollout restart이미지 변경 없이 전체 재시작컨피그맵/시크릿 변경 반영
 
# 이력 보기
kubectl rollout history deployment/api
REVISION  CHANGE-CAUSE
1         CHG-10120 최초 배포
2         CHG-10240 api v2.3.1 배포
3         CHG-10293 api v2.3.2 배포

# 특정 리비전의 내용 확인
kubectl rollout history deployment/api --revision=2

# 바로 직전으로
kubectl rollout undo deployment/api

# 특정 리비전으로
kubectl rollout undo deployment/api --to-revision=2

# 컨피그맵을 바꾼 뒤 파드에 반영하려면 (파드는 자동 재시작되지 않습니다)
kubectl rollout restart deployment/api

# 진행 중 멈추기 → 일부만 새 버전으로 두고 관찰 → 재개 (수동 카나리)
kubectl rollout pause deployment/api
kubectl rollout resume deployment/api

롤백해도 안 돌아가는 것들

rollout undo는 파드 템플릿만 되돌립니다. 데이터베이스 마이그레이션, 컨피그맵 내용, 외부 시스템에 보낸 요청은 되돌아오지 않습니다. 스키마를 변경하는 배포는 반드시 앞뒤 버전 호환(backward compatible)으로 설계되어야 합니다.

무중단 배포의 전제 조건

롤링 업데이트가 무중단이 되려면 레디니스 프로브가 설정돼 있어야 합니다. 없으면 컨테이너가 뜨자마자 “준비됨”으로 간주돼 아직 초기화 중인 파드로 트래픽이 갑니다. maxUnavailable: 0, maxSurge: 1 조합과 PodDisruptionBudget까지 있으면 더 안전합니다.

삭제 관련 옵션

옵션뜻주의
--grace-period=N종료까지 기다릴 초기본 30초. 앱이 정리할 시간
--forceAPI 객체를 즉시 제거위험 컨테이너가 살아 있을 수 있음
--cascade=background부모 먼저 삭제, 자식은 뒤따라 (기본)—
--cascade=foreground자식이 다 지워질 때까지 대기순서가 중요할 때
--cascade=orphan자식을 남김디플로이먼트만 지우고 파드는 유지
--wait=false삭제 완료를 기다리지 않음대량 삭제 스크립트용

--force --grace-period=0 은 최후의 수단입니다

이 조합은 “API 서버 기록만 지우고 파드가 실제로 죽었는지는 확인하지 않는다”는 뜻입니다. 특히 스테이트풀셋에 쓰면 같은 볼륨에 두 파드가 동시에 쓰는 상황이 생겨 데이터가 깨질 수 있습니다. 노드가 완전히 죽어서 kubelet이 응답하지 않을 때 외에는 쓰지 마세요.

노드 관리: cordon · drain · taint

노드를 점검하거나 교체할 때 쓰는 명령입니다. 이 명령들은 파드를 대규모로 이동시킵니다. 반드시 작업 시간과 절차를 합의한 뒤 실행하세요.

# [1] 노드 상태 확인
kubectl get nodes -o wide
kubectl describe node node-worker-02 | sed -n '/Conditions:/,/Addresses:/p'

# [2] 새 파드 배치 차단 (기존 파드는 그대로 둠)
kubectl cordon node-worker-02
kubectl get nodes
NAME             STATUS                     ROLES    AGE   VERSION
node-worker-02   Ready,SchedulingDisabled   <none>   92d   v1.31.4

# [3] 무엇이 옮겨질지 먼저 확인 — drain 전 필수
kubectl get pods -A --field-selector spec.nodeName=node-worker-02 -o wide

# [4] 실제로 옮겨 보기 전에 드라이런
kubectl drain node-worker-02 --ignore-daemonsets --dry-run=client

# [5] 비우기
kubectl drain node-worker-02 \
  --ignore-daemonsets \            # 데몬셋 파드는 어차피 못 옮김
  --delete-emptydir-data \         # emptyDir 데이터는 사라짐 (확인 필요!)
  --grace-period=60 \
  --timeout=10m

# [6] 작업 (OS 패치, 커널 업데이트 등)

# [7] 복귀
kubectl uncordon node-worker-02

drain 전에 확인할 세 가지

  1. PodDisruptionBudget — 없으면 같은 서비스의 파드가 한꺼번에 내려갈 수 있습니다.
  2. emptyDir 데이터 — --delete-emptydir-data는 그 데이터를 버린다는 뜻입니다. 캐시면 괜찮지만 작업 중인 파일이면 아닙니다.
  3. 남은 노드 용량 — 옮겨갈 자리가 없으면 파드는 Pending에 갇힙니다. 먼저 kubectl describe node로 Allocated resources를 확인하세요.
# 각 노드에 얼마나 할당돼 있는지
kubectl describe node node-worker-01 | sed -n '/Allocated resources:/,/Events:/p'
Resource   Requests      Limits
cpu        3200m (80%)   6000m (150%)
memory     6144Mi (77%)  8192Mi (103%)

# 전체 노드를 한 줄씩 (리눅스 조합)
kubectl get nodes -o name | xargs -I{} sh -c \
  'echo "== {}"; kubectl describe {} | grep -A4 "Allocated resources"'

# 노드별 파드 개수 세기
kubectl get pods -A -o jsonpath='{range .items[*]}{.spec.nodeName}{"\n"}{end}' \
  | sort | uniq -c | sort -rn

taint와 toleration

cordon이 “아무도 오지 마”라면, taint는 “이 조건을 견딜 수 있는 파드만 와”입니다. GPU 노드나 특정 팀 전용 노드를 만들 때 씁니다.

# 형식: key=value:effect
#   NoSchedule        — 새 파드 배치 금지
#   PreferNoSchedule  — 되도록 피함 (강제 아님)
#   NoExecute         — 기존 파드까지 쫓아냄 ← 주의

kubectl taint nodes node-gpu-01 workload=gpu:NoSchedule

# 제거는 끝에 하이픈
kubectl taint nodes node-gpu-01 workload=gpu:NoSchedule-

# 현재 테인트 확인
kubectl get nodes -o custom-columns='NODE:.metadata.name,TAINTS:.spec.taints[*].key'

# 파드 쪽에는 toleration 이 있어야 배치됩니다
kubectl explain pod.spec.tolerations

NoExecute는 즉시 파드를 쫓아냅니다

NoSchedule과 NoExecute를 혼동해 운영 노드에 NoExecute 테인트를 걸면, 그 노드의 파드가 그 자리에서 전부 종료됩니다. 테인트 문자열은 복사 붙여넣기로 만들고 실행 전에 소리 내어 읽으세요.

xargs로 대량 작업

xargs를 쓰기 전 반드시

앞부분(파이프 왼쪽)만 먼저 실행해서 대상 목록을 눈으로 확인하세요. 그다음에 | xargs echo kubectl delete ...처럼 echo를 끼워 명령문을 미리 출력해 보고, 그래도 맞으면 echo를 빼고 실행합니다. 이 3단계가 대량 삭제 사고를 막습니다.

# 1단계: 대상 확인
kubectl get pods -n staging --field-selector status.phase=Failed -o name

# 2단계: 실행될 명령을 글자로만 출력
kubectl get pods -n staging --field-selector status.phase=Failed -o name \
  | xargs -I{} echo kubectl delete {} -n staging

# 3단계: 진짜 실행
kubectl get pods -n staging --field-selector status.phase=Failed -o name \
  | xargs -I{} kubectl delete {} -n staging
# Evicted 파드 일괄 정리 (노드 압박 후 남은 잔해)
kubectl get pods -A --field-selector status.phase=Failed -o \
  jsonpath='{range .items[*]}{.metadata.namespace}{" "}{.metadata.name}{"\n"}{end}' \
  | xargs -r -n2 sh -c 'kubectl delete pod -n "$0" "$1"'

# 모든 네임스페이스의 디플로이먼트를 한 줄씩 롤아웃 상태 확인
kubectl get deploy -A --no-headers | awk '{print $1, $2}' \
  | xargs -n2 sh -c 'echo "--- $1 ($0)"; kubectl rollout status deploy/"$1" -n "$0" --timeout=10s'

# 여러 파드에서 동시에 명령 실행 (-P4 = 4개 병렬)
kubectl get pods -l app=api -o name \
  | xargs -P4 -I{} kubectl exec {} -- sh -c 'echo $(hostname): $(cat /app/version)'

# 특정 레이블 붙은 디플로이먼트 전부 재시작
kubectl get deploy -n web -l tier=frontend -o name \
  | xargs -I{} kubectl rollout restart {} -n web

# 전체 파드 로그를 파드별 파일로 수집 (장애 증적 확보)
mkdir -p evidence && kubectl get pods -n payment --no-headers -o custom-columns=:metadata.name \
  | xargs -I{} sh -c 'kubectl logs -n payment {} --tail=2000 > evidence/{}.log 2>&1'

사고를 부르는 명령어 10선

아래는 실제 운영 환경에서 장애를 만든 패턴들입니다. 각 항목을 펼쳐 무슨 일이 벌어지는지와 어떻게 해야 했는지를 확인하세요.

1 컨텍스트 확인 없이 delete› 
# 개발 클러스터인 줄 알았지만 current-context는 prod였다
kubectl delete deploy --all
deployment.apps "api" deleted
deployment.apps "payment-worker" deleted
deployment.apps "notification" deleted
# → 운영 서비스 전체 중단. 복구는 Git에서 다시 apply 해야 하고,
#    그동안의 요청은 전부 실패합니다.

이렇게 했어야 합니다

# 1) 항상 컨텍스트를 명시 (전환 자체를 하지 않는 것이 더 안전)
kubectl --context=dev-cluster-admin delete deploy -l app=test -n sandbox

# 2) --all 대신 레이블이나 파일로 범위를 좁힌다
kubectl delete -f ./manifests/test/

# 3) 프롬프트에 컨텍스트 표시 (3장 참고)
2 -A 와 변경 명령을 함께 쓰기› 
kubectl delete pods -A -l app=test
# kube-system 을 포함한 모든 네임스페이스에서 실행됩니다.
# CoreDNS나 CNI 파드가 함께 지워지면 클러스터 전체 통신이 끊깁니다.

-A는 조회 전용으로만 쓰는 것을 팀 규칙으로 정하세요. 변경/삭제는 언제나 -n으로 네임스페이스를 명시합니다.

3 --force --grace-period=0 남용› 
kubectl delete pod mysql-0 --force --grace-period=0
# API 서버 기록만 지워집니다. 노드에서 컨테이너가 계속 돌 수 있습니다.
# 스테이트풀셋이 같은 볼륨으로 새 파드를 띄우면 → 두 프로세스가 같은 데이터에 쓰기
# → 데이터 손상. 복구 불가.

파드가 Terminating에서 안 끝난다면 먼저 describe로 원인(finalizer, 볼륨 분리 실패, preStop 훅)을 찾으세요. --force는 노드가 완전히 죽었을 때만 씁니다.

4 edit으로 고치고 Git에 반영하지 않기›

새벽에 kubectl edit으로 메모리 limit을 올려 장애를 막았습니다. 아침에 정기 배포가 돌면서 Git의 예전 값으로 조용히 되돌아가고, 같은 장애가 재발합니다. 이번엔 아무도 원인을 모릅니다.

# 응급 조치 직후, 무엇이 달라졌는지 기록으로 남긴다
kubectl get deploy api -o yaml > /tmp/api-hotfix.yaml
kubectl diff -f git-repo/manifests/api.yaml

# 그리고 같은 변경을 Git에 PR로 올린다. 이게 조치의 절반입니다.
5 drain을 순서 없이 여러 노드에› 
for n in $(kubectl get nodes -o name); do kubectl drain $n --ignore-daemonsets; done
# 모든 노드를 동시에 비우려 하므로 파드가 갈 곳이 없습니다.
# 전체 서비스가 Pending 상태로 멈춥니다.

한 번에 한 노드씩, 파드가 다른 노드에서 Ready가 된 것을 확인한 뒤 다음으로 넘어갑니다. PodDisruptionBudget을 설정해 두면 kubectl이 알아서 막아 줍니다.

for n in node-worker-01 node-worker-02 node-worker-03; do
  echo "=== $n 작업 시작"
  kubectl drain "$n" --ignore-daemonsets --delete-emptydir-data --timeout=10m || break
  # ... OS 패치 ...
  kubectl uncordon "$n"
  kubectl wait --for=condition=Ready node/"$n" --timeout=5m
  read -p "다음 노드로 진행할까요? (Enter)"
done
6 replace --force를 apply 대신 쓰기›

apply가 충돌 오류를 내자 검색해서 나온 kubectl replace --force -f를 실행합니다. 이 명령은 리소스를 삭제하고 새로 만듭니다. 서비스는 끊기고, HPA가 조정해 둔 replicas는 YAML의 값으로 되돌아가며, 다른 컨트롤러가 붙여 둔 어노테이션이 사라집니다.

충돌이 났다면 kubectl apply --server-side --force-conflicts를 검토하거나, 무엇이 충돌하는지 kubectl diff로 먼저 보세요.

7 컨피그맵만 바꾸고 재시작을 안 하기›

컨피그맵을 apply 했는데 설정이 안 먹습니다. 환경변수로 주입된 값은 파드 재시작 전까지 절대 바뀌지 않습니다(볼륨 마운트는 수십 초 뒤 갱신되지만 앱이 다시 읽어야 합니다).

kubectl apply -f configmap.yaml
kubectl rollout restart deployment/api
kubectl rollout status deployment/api

# 근본 해결: 컨피그맵 해시를 파드 어노테이션에 넣어 자동 재시작되게 설계
8 PVC를 지우면 데이터도 지워집니다›

스토리지클래스의 reclaimPolicy가 Delete면 PVC 삭제와 동시에 실제 디스크가 삭제됩니다. 클라우드 환경 기본값이 대개 Delete입니다.

# 이 PVC가 어떤 PV를 쓰고, 정책이 무엇인지
kubectl get pvc data-mysql-0 -o jsonpath='{.spec.volumeName}'; echo
kubectl get pv -o custom-columns='PV:.metadata.name,CLAIM:.spec.claimRef.name,POLICY:.spec.persistentVolumeReclaimPolicy'

# 지우기 전 정책을 Retain 으로 바꿔 두면 디스크는 남습니다
kubectl patch pv pvc-a1b2c3 -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
9 시크릿을 로그·티켓에 그대로 올리기›

kubectl get secret -o yaml의 값은 base64 인코딩일 뿐 암호가 아닙니다. 티켓에 첨부하거나 화면 공유 중 출력하면 자격증명 유출 사고가 됩니다. kubectl describe secret은 값 대신 바이트 수만 보여주니 확인용으로는 이쪽을 쓰세요.

kubectl describe secret db-cred
Data
====
password:  12 bytes
username:  4 bytes
10 운영 클러스터에서 무심코 스케일 0›

야간 비용 절감 스크립트가 네임스페이스를 잘못 참조해 운영 워크로드를 0으로 만든 사례입니다. scale --replicas=0은 에러도 경고도 없이 서비스를 내립니다.

# 스크립트에 네임스페이스 화이트리스트를 둔다
ALLOW="dev staging sandbox"
case " $ALLOW " in
  *" $NS "*) kubectl scale deploy --all -n "$NS" --replicas=0 ;;
  *) echo "차단: $NS 는 허용된 네임스페이스가 아닙니다"; exit 1 ;;
esac

# 되돌리기 전에 원래 값을 저장해 두는 것도 잊지 마세요
kubectl get deploy -n "$NS" -o jsonpath='{range .items[*]}{.metadata.name}={.spec.replicas}{"\n"}{end}' > replicas.bak

여기까지 오셨다면

이제 다음 단계는 직접 만져 보는 것입니다. kind나 minikube로 노트북에 클러스터를 하나 띄우고, 18장의 위험한 명령들을 거기서 전부 실행해 보세요. 무엇이 부서지는지 안전하게 경험해 본 사람이 운영 환경에서 손이 멈춥니다.

# kind (Docker만 있으면 됨)
go install sigs.k8s.io/kind@latest   # 또는 brew install kind
kind create cluster --name lab
kubectl config use-context kind-lab

# 연습용 워크로드 배포
kubectl create deployment web --image=nginx --replicas=3
kubectl expose deployment web --port=80

# 마음껏 부숴 보기
kubectl delete pods --all
kubectl set image deploy/web nginx=nginx:존재하지않는태그
kubectl get pods -w

# 끝나면 정리
kind delete cluster --name lab
