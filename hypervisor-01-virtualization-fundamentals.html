서버 한 대를 여럿처럼 쓰는 기술

하이퍼바이저는 물리 서버 한 대의 CPU·메모리·디스크·네트워크를 쪼개서, 각각의 가상 머신이 "내가 이 서버를 통째로 쓰고 있다"고 착각하게 만드는 소프트웨어입니다. 이 착각을 어떻게 만들어내는지, 왜 x86에서는 그게 20년 동안 어려운 문제였는지를 다룹니다.

대상 · 1~2년차 클라우드 엔지니어 선수 지식 · 리눅스 기본, OS 개념 약간 읽는 시간 · 약 35분
01

서버 한 대에 앱 하나를 올리던 시절

2000년대 초 데이터센터의 기본 단위는 "업무 하나 = 물리 서버 한 대"였습니다. 그룹웨어 서버, 메일 서버, 회계 서버가 각각 따로 있었죠. 이유는 단순했습니다. 한 OS 위에 여러 앱을 올리면 하나가 메모리를 다 먹거나 죽을 때 나머지도 같이 죽었고, 라이브러리 버전도 충돌했으니까요. 격리하려면 하드웨어를 나눌 수밖에 없었습니다.

문제는 그렇게 산 서버들의 평균 CPU 사용률이 대체로 한 자릿수에서 10%대에 머물렀다는 점입니다. 피크 트래픽을 견디도록 사이징하니 평소에는 대부분 놀고, 그렇다고 줄이면 월말 결산 때 죽습니다. 구매비·전력·냉각·랙 공간·OS 라이선스를 전부 지불하면서 성능의 대부분을 버리는 구조였고, 이걸 서버 스프롤(server sprawl)이라고 불렀습니다.

통합 효과 계산기

슬라이더를 움직여 보세요. 물리 서버를 가상화로 합쳤을 때 몇 대로 줄어드는지 계산합니다.

실제 통합 설계는 CPU만 보고 하지 않습니다. 메모리 총량, 디스크 IOPS, 네트워크 대역폭 중 가장 먼저 꽉 차는 자원이 한계를 결정합니다. 현장에서는 CPU보다 메모리가 먼저 바닥나는 경우가 훨씬 많습니다. 여기에 호스트 한 대가 죽어도 버티도록 여유분(N+1)을 얹어야 합니다.

2001년 VMware가 ESX를, 2003년 케임브리지 대학 팀이 Xen을 내놓으면서 이 낭비를 걷어낼 수 있게 됐습니다. "격리는 유지하되 하드웨어는 공유한다" — 이 한 문장이 하이퍼바이저의 존재 이유입니다. 그리고 이 발상은 지금도 유효합니다. AWS·Azure·GCP가 여러분에게 EC2 인스턴스를 파는 방식이 정확히 이것이니까요.

02

하이퍼바이저가 실제로 하는 일

하이퍼바이저(Hypervisor)는 물리 하드웨어와 운영체제 사이에 끼어들어 하드웨어를 추상화하고 여러 가상 머신(VM)에 나눠주는 소프트웨어 계층입니다. 학술적으로는 VMM(Virtual Machine Monitor)이라고 부릅니다. 두 용어는 사실상 같은 뜻으로 쓰입니다.

이름은 OS의 별칭인 "supervisor"에서 왔습니다. 감독자(supervisor) 위에 있는 존재라는 뜻으로 hyper-visor입니다. 이 작명 자체가 계층 관계를 그대로 설명합니다.

세 가지 핵심 역할

추상화

게스트 OS에게 진짜 하드웨어가 아닌 표준화된 가상 하드웨어를 보여줍니다. 물리 NIC이 Intel이든 Broadcom이든, 게스트는 동일한 가상 NIC만 봅니다. 그래서 VM을 다른 서버로 옮겨도 드라이버를 다시 안 잡아도 됩니다.

분할

CPU는 시간으로 쪼개고(스케줄링), 메모리는 공간으로 쪼개고, 디스크는 파일로 쪼갭니다. 물리 코어 16개에서 vCPU 40개를 뽑아내는 오버커밋이 여기서 나옵니다.

격리

VM A가 커널 패닉으로 죽어도 VM B는 멀쩡해야 하고, VM A가 VM B의 메모리를 읽을 수 없어야 합니다. 이 격리 경계가 무너지는 게 나중에 다룰 VM 탈출(VM Escape)입니다.

VM은 결국 파일 몇 개다

추상적으로 느껴진다면 이렇게 보면 됩니다. 실행 중이 아닌 VM은 디스크 위의 파일 묶음입니다. 

# KVM/QEMU 환경의 VM 한 대 실체
/var/lib/libvirt/images/web-01.qcow2   ← 가상 디스크 (실제 데이터)
/etc/libvirt/qemu/web-01.xml          ← 하드웨어 명세서
                                            vCPU 4개, RAM 8GB, NIC 1개, 디스크 1개…

# VMware ESXi 환경
/vmfs/volumes/datastore1/web-01/web-01.vmdk      ← 가상 디스크
/vmfs/volumes/datastore1/web-01/web-01.vmx       ← 설정 파일
/vmfs/volumes/datastore1/web-01/web-01.nvram     ← 가상 BIOS/UEFI 상태

이 사실 하나에서 엄청난 편의가 파생됩니다. 서버를 복제하는 게 파일 복사가 되고, 백업이 파일 백업이 되고, 재해복구가 파일 전송이 됩니다. 물리 서버 시절에는 상상도 못 하던 일입니다.

현장 감각

신입 엔지니어가 가장 먼저 겪는 사고 중 하나가 .qcow2나 .vmdk 파일이 있는 데이터스토어를 꽉 채우는 일입니다. 씬 프로비저닝으로 100GB 디스크를 10대 만들었는데 실제 스토리지는 500GB라면, 게스트들이 데이터를 채우는 순간 전 VM이 동시에 멈춥니다. 가상 디스크의 "할당 용량"과 "실제 점유 용량"은 다른 숫자입니다.

03

Type 1과 Type 2, 무엇이 다른가

하이퍼바이저는 어디에 설치되는가로 두 종류로 나뉩니다. 1974년 제럴드 팝엑과 로버트 골드버그의 논문에서 유래한 분류입니다.

KVM은 Type 1인가 Type 2인가

면접에서도 자주 나오는 논쟁거리입니다. KVM은 리눅스 커널 모듈(kvm.ko)입니다. 리눅스가 이미 떠 있는 상태에서 로드되므로 "OS 위에 올라가니 Type 2"라는 주장이 가능합니다. 반대로, 모듈이 로드되는 순간 리눅스 커널 자체가 하이퍼바이저가 되어 하드웨어를 직접 제어하므로 Type 1이라는 주장도 맞습니다.

실무적으로 통용되는 답은 "Type 1으로 분류한다"입니다. Red Hat, SUSE, 그리고 KVM을 쓰는 모든 퍼블릭 클라우드가 그렇게 씁니다. 다만 면접에서는 "분류는 Type 1이지만, 리눅스 커널에 내장된 형태라 Type 1/2의 경계에 있다"고 답하는 게 가장 정확합니다. 중요한 건 라벨이 아니라 "게스트의 명령이 하드웨어에 닿기까지 몇 개의 계층을 거치는가"입니다.

04

x86은 원래 가상화가 불가능한 CPU였다

여기서부터가 하이퍼바이저의 진짜 이야기입니다. 위에서 "게스트 OS를 속인다"고 했는데, 어떻게 속일까요? 그리고 왜 그게 x86에서는 20년 넘게 풀리지 않은 문제였을까요?

보호 링: CPU의 권한 계층

x86 CPU는 실행 권한을 링(Ring) 0~3으로 나눕니다. 숫자가 작을수록 권한이 큽니다.

x86 보호 링

링을 클릭하면 설명이 바뀝니다.

정상적인 상황에서는 앱이 Ring 3, OS 커널이 Ring 0에 있습니다. 앱이 디스크를 읽고 싶으면 직접 하지 못하고 시스템 콜로 커널에 부탁합니다. 그럼 가상화를 하면 어떻게 될까요? 게스트 OS는 자기가 Ring 0에 있다고 믿지만, 실제로 Ring 0을 내주면 하드웨어를 마음대로 만져버립니다. 하이퍼바이저가 통제권을 잃습니다.

이론적 해법: 트랩 앤 에뮬레이트

팝엑과 골드버그가 1974년 논문에서 제시한 방식은 디프리빌리징(de-privileging)입니다. 게스트 OS를 Ring 0이 아닌 낮은 권한(Ring 1이나 3)에 두고, 하이퍼바이저만 Ring 0을 차지합니다. 게스트 OS가 특권 명령을 실행하려 하면 CPU가 권한 위반 예외(트랩)를 발생시키고, 제어권이 하이퍼바이저로 넘어옵니다. 하이퍼바이저는 그 명령을 대신 흉내 내준 뒤(에뮬레이트) 게스트에게 "정상 처리됐어"라고 돌려줍니다.

같은 논문은 가상화 가능한 CPU의 조건도 정의했습니다. 핵심은 "시스템 상태에 영향을 주는 민감한(sensitive) 명령은 모두 특권(privileged) 명령이어야 한다"는 것입니다. 민감한데 특권이 아니면, 트랩이 안 걸려서 하이퍼바이저가 개입할 기회를 놓칩니다.

x86의 결함

2000년 로빈과 어바인의 연구에서 x86에는 민감하지만 특권이 아닌 명령이 17개 있다는 것이 밝혀졌습니다. SGDT, SIDT, SLDT, SMSW, PUSHF, POPF, LAR, LSL, STR 등입니다. 즉 x86은 팝엑·골드버그 조건을 만족하지 않았고, 이론상 가상화가 불가능한 아키텍처였습니다.

가장 유명한 사고뭉치: POPF

POPF는 스택에서 값을 꺼내 플래그 레지스터에 넣는 명령입니다. 그 플래그 중에 인터럽트 활성화 비트(IF)가 있습니다. 게스트 커널이 "인터럽트 꺼!"라고 POPF를 실행하면, Ring 0에서는 IF가 바뀌지만 Ring 3에서는 예외도 안 나고 그냥 조용히 무시됩니다.

게스트 OS는 인터럽트를 껐다고 믿고 임계 구역에 들어가지만 실제로는 안 꺼졌습니다. 에러도 없으니 하이퍼바이저는 개입할 방법이 없습니다. 조용히 틀리는 것이야말로 가장 고치기 어려운 종류의 버그입니다. 이 하나 때문에 x86 가상화 전체가 막혀 있었습니다.

05

막힌 길을 뚫은 세 가지 해법

업계는 세 가지 서로 다른 방향으로 이 문제를 풀었습니다. 역사적 순서대로 보겠습니다.

해법 비교

지금의 표준: 하드웨어 보조 가상화

2005~2006년 인텔이 VT-x, AMD가 AMD-V(SVM)를 내놓으면서 문제가 CPU 차원에서 해결됐습니다. 해법은 우아합니다. 링 구조를 손대는 대신, 링 체계 전체를 두 벌로 복제했습니다.

  • VMX root 모드 — 하이퍼바이저가 사는 세계. 흔히 "Ring -1"이라 부르는 게 여기입니다.
  • VMX non-root 모드 — 게스트가 사는 세계. 게스트 OS는 진짜로 Ring 0에서 돕니다. 속이지 않아도 됩니다.

게스트는 자기 세계의 Ring 0에서 정상적으로 동작하다가, 하이퍼바이저가 가로채기로 지정한 사건 (I/O 접근, 특정 레지스터 쓰기, CPUID 실행 등)을 만나면 VM Exit이 발생해 제어권이 root 모드로 넘어갑니다. 처리가 끝나면 VM Entry로 돌아갑니다.

이때 게스트의 모든 레지스터 상태를 담아두는 메모리 구조가 인텔의 VMCS이고, AMD에서는 VMCB라고 부릅니다. 이 구조체가 VM의 "저장된 의식"인 셈입니다.

06

VM Exit이라는 청구서

하드웨어 보조 가상화가 모든 걸 공짜로 해주는 건 아닙니다. VM Exit 한 번에는 비용이 듭니다. 게스트의 레지스터 전부를 VMCS에 저장하고, 하이퍼바이저 상태를 복원하고, 파이프라인과 분기 예측기가 무효화되고, 일부 캐시가 날아갑니다.

수백에서 수천 CPU 사이클 규모입니다. 일반 함수 호출이 수 사이클인 걸 생각하면 엄청난 차이입니다. 초기 세대 하드웨어에서는 이 비용이 워낙 커서, VMware의 잘 최적화된 바이너리 변환이 1세대 VT-x보다 빠른 경우도 있었습니다. 세대를 거듭하며 비용이 크게 줄어 지금의 판도가 됐습니다.

그래서 가상화 성능 튜닝의 본질은 "VM Exit을 얼마나 줄이느냐"입니다. 2편에서 다룰 EPT/NPT, virtio, SR-IOV, APICv 같은 기술은 전부 이 목표를 향합니다.

VM Exit 원인언제 생기나줄이는 기술

I/O 포트 접근게스트가 디스크·NIC를 건드릴 때virtio 반가상화 드라이버, SR-IOV 직접 할당
인터럽트 처리게스트가 인터럽트 컨트롤러를 조작할 때APICv / AVIC — 인터럽트 가상화를 하드웨어가 대행
HLT 명령게스트가 할 일이 없어 쉴 때HLT 폴링 — 짧은 대기는 exit 없이 넘김
CPUID게스트가 CPU 기능을 조회할 때가로채기 필수. 대신 라이브 마이그레이션 호환성을 확보
직접 확인해 보기

리눅스에서 KVM을 쓰고 있다면 실제 VM Exit 통계를 볼 수 있습니다.

# CPU가 가상화 확장을 지원하는지 (vmx=인텔, svm=AMD)
grep -c -E 'vmx|svm' /proc/cpuinfo

# KVM 모듈이 올라와 있는지
lsmod | grep kvm

# VM Exit 실시간 통계 (원인별 발생 횟수/초)
sudo kvm_stat

# 정적 카운터로 확인
sudo cat /sys/kernel/debug/kvm/exits

kvm_stat을 띄워 놓고 게스트에서 디스크 I/O를 크게 일으켜 보면, 특정 exit 항목이 급증하는 게 눈에 보입니다. 이론이 숫자로 바뀌는 순간입니다.

07

지금 현장의 제품 지형

필터를 눌러 조건에 맞는 제품만 볼 수 있습니다.

MSP 실무에 직접 영향을 준 변화

2023년 11월 브로드컴이 VMware 인수를 마무리한 뒤 라이선스 체계가 크게 바뀌었습니다. 영구 라이선스 신규 판매가 중단되고 구독제로 전환됐으며, 수십 개 SKU가 VCF(VMware Cloud Foundation)와 VVF(vSphere Foundation) 중심으로 통합됐습니다. 과금 단위는 코어 단위이고 CPU당 최소 코어 수가 적용됩니다. 무료 ESXi 배포도 중단됐습니다.

그 결과 국내외에서 Proxmox VE, Nutanix AHV, XCP-ng, OpenStack, KubeVirt 등으로의 전환 검토가 눈에 띄게 늘었습니다. 고객사 인프라를 운영한다면 갱신 시점의 코어 수 산정과 대안 검토는 이제 정기 업무에 가깝습니다. 정책은 계속 바뀌므로 갱신 전 최신 조건을 반드시 확인하세요.

08

실무에서 만나는 장면들

사례 1 — 고객사 노후 서버 통합

5년 지난 물리 서버 30대를 신규 3노드 클러스터로 옮기는 프로젝트. 이때 쓰는 기술이 P2V(Physical to Virtual)입니다. 물리 서버의 디스크를 통째로 가상 디스크 이미지로 변환합니다.

가장 흔한 함정은 드라이버입니다. 물리 서버용으로 잡혀 있던 RAID 컨트롤러·NIC 드라이버가 가상 하드웨어에서는 존재하지 않아 부팅 직후 블루스크린이 나거나 네트워크가 안 올라옵니다. 전환 전에 virtio·VMware Tools 드라이버를 미리 주입해 두는 게 정석입니다. 라이선스도 점검 대상입니다. MAC 주소나 하드웨어 시리얼에 묶인 소프트웨어는 전환 즉시 인증이 풀립니다.

사례 2 — 15년 된 레거시 시스템 연명

Windows Server 2003에서만 도는 업무 시스템이 아직 살아있고, 개발사는 폐업했고, 서버 하드웨어는 단종. 부품이 고장 나면 끝입니다. 이런 상황에서 하이퍼바이저는 시간을 사는 도구입니다. 물리 서버를 VM으로 떠서 현대 하드웨어 위에 올리면 하드웨어 수명 문제와는 분리됩니다.

다만 보안 문제는 전혀 해결되지 않는다는 점을 고객에게 분명히 전달해야 합니다. 패치 안 되는 OS는 VM 안에 있어도 똑같이 취약합니다. 반드시 네트워크를 분리하고 접근 경로를 최소화한 상태로 운영해야 합니다.

사례 3 — 개발·검증 환경을 몇 분 만에

"운영과 똑같은 환경에서 재현해 보고 싶다"는 요청. 운영 VM의 스냅샷을 떠서 격리된 네트워크에 복제하면 수십 분 안에 동일 환경이 만들어집니다. 물리 서버 시절엔 몇 주짜리 일이었습니다.

주의할 점은 스냅샷은 백업이 아니라는 것입니다. 스냅샷은 원본 디스크에 의존하는 변경분 기록이고, 오래 유지하면 체인이 길어져 성능이 떨어지고 삭제(통합) 작업 자체가 위험해집니다. 며칠 이상 유지되는 스냅샷은 그 자체가 장애 위험 요인입니다.

사례 4 — 재해복구 사이트 구성

VM이 파일이라는 성질을 그대로 활용합니다. 주 사이트의 VM 디스크를 DR 사이트로 복제해 두면, 장애 시 복제본을 부팅하는 것으로 서비스를 살립니다. 물리 서버 기반 DR과 달리 양쪽 하드웨어 모델이 달라도 됩니다. 하이퍼바이저가 하드웨어 차이를 흡수하기 때문입니다.

여기서 합의해야 할 두 숫자가 RPO(얼마나 최근까지의 데이터를 살릴 것인가)와 RTO(몇 분 안에 살릴 것인가)입니다. 이 숫자가 복제 주기와 DR 사이트 사양을 결정합니다.

사례 5 — 퍼블릭 클라우드의 정체

EC2 인스턴스를 띄우는 건 결국 누군가의 하이퍼바이저 위에 VM을 만드는 일입니다. AWS는 Xen에서 시작해 KVM 기반의 Nitro로 전환했습니다. Nitro의 핵심 발상은 네트워크·스토리지·보안 처리를 전용 카드로 떼어내서, 호스트 CPU가 가상화 오버헤드에 거의 쓰이지 않게 만든 것입니다. Azure는 Hyper-V 계열, GCP는 KVM 기반을 씁니다.

이걸 알면 클라우드의 여러 제약이 납득됩니다. 인스턴스 타입별 성능 차이, 전용 호스트 옵션, 네트워크 대역폭 상한, 라이브 마이그레이션 지원 여부는 전부 아래에 깔린 하이퍼바이저의 특성에서 나옵니다. 클라우드를 깊게 이해하려면 하이퍼바이저를 이해해야 하는 이유입니다.

09

자주 헷갈리는 것들

"컨테이너가 VM을 대체한다"

둘은 격리 수준이 다릅니다. 컨테이너는 호스트 커널을 공유하고 네임스페이스·cgroup으로 나눕니다. 가볍고 빠르지만 커널이 하나라 커널 취약점이 곧 전체 위험입니다. VM은 커널까지 따로 가져서 무겁지만 격리가 강합니다. 현실에서는 VM 위에 쿠버네티스를 올려 둘 다 쓰는 구성이 가장 흔합니다.

"vCPU 하나 = 물리 코어 하나"

아닙니다. vCPU는 스케줄링 단위이고, 물리 코어를 시간으로 나눠 씁니다. 16코어 호스트에 vCPU 64개를 배정할 수 있습니다(4:1 오버커밋). 다만 VM들이 동시에 바빠지면 CPU를 기다리는 시간(CPU Ready)이 늘어 체감 성능이 급락합니다.

"하이퍼바이저는 OS가 아니다"

Type 1 하이퍼바이저는 사실상 특수 목적 OS입니다. ESXi의 VMkernel은 스케줄러·메모리 관리자·드라이버·파일시스템을 다 갖고 있습니다. 다만 사용자 앱을 돌리는 대신 VM을 돌리도록 만들어졌을 뿐입니다.

"가상화하면 무조건 느려진다"

CPU·메모리 위주 워크로드는 현대 하드웨어에서 손실이 매우 작습니다. 체감 차이는 주로 I/O와 지연에 민감한 워크로드에서 납니다. 그래서 고빈도 트레이딩이나 일부 실시간 시스템은 여전히 베어메탈을 씁니다.

"VM은 서로 완벽히 격리된다"

논리적으로는 그렇지만 물리 자원은 공유합니다. 한 VM이 디스크를 두들기면 같은 데이터스토어의 다른 VM이 느려지는 시끄러운 이웃 문제가 생깁니다. Spectre·Meltdown 같은 사이드채널 취약점도 이 공유 지점을 노립니다.

"중첩 가상화는 안 된다"

됩니다. VM 안에서 또 하이퍼바이저를 돌리는 중첩 가상화를 KVM·Hyper-V·ESXi가 지원합니다. 다만 VM Exit이 이중으로 발생해 성능 손실이 큽니다. 운영 환경보다는 실습·CI용입니다.
