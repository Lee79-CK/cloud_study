OpenStack은 두 개의 평면으로
쪼개졌습니다.

18 버전에서 Red Hat OpenStack은 "설치형 제품"에서 "쿠버네티스 위에서 사는 워크로드"로 이동했습니다. 제어 평면은 OpenShift 파드가 되고, 데이터 평면은 Ansible이 관리하는 RHEL 서버로 남습니다. 이 강의는 그 경계선을 손으로 만져 보는 것에서 시작합니다.

01 — Why

왜 18에서 제품 이름까지 바뀌었나

17.1까지의 제품명은 RHOSP(Red Hat OpenStack Platform)였습니다. 18부터는 RHOSO(Red Hat OpenStack Services on OpenShift)입니다. "Platform"이 "Services on OpenShift"로 바뀐 건 마케팅이 아니라 설치 방식·운영 주체·장애 도메인이 전부 달라졌다는 신고입니다.

17.1까지의 세계: undercloud가 overcloud를 낳는다

기존 RHOSP는 director(업스트림 TripleO)라는 도구로 배포했습니다. 구조는 이렇습니다.

  • undercloud — OpenStack 하나를 먼저 단일 노드에 깔아 놓고, 이것을 "설치기"로 씁니다. ironic으로 베어메탈을 굽고, heat로 배포를 조립합니다.
  • overcloud — undercloud가 만들어 낸 실제 서비스용 클라우드. Controller 3대 + Compute N대 + Ceph 노드로 구성됩니다.
  • Controller 노드 위에서는 keystone·nova-api·neutron-server·galera·rabbitmq가 모두 컨테이너로 돌고, HA는 Pacemaker/Corosync가 잡습니다.
  • 설정은 THT(TripleO Heat Templates) YAML 수백 줄 + openstack overcloud deploy -e ... 명령으로 주입합니다.
17.1의 실제 통증

① OpenStack을 깔기 위해 OpenStack(undercloud)을 먼저 깔아야 한다 — 학습·운영 비용의 이중화.
② THT는 사실상 Red Hat 전용 DSL이라 이력·검증·되돌리기가 어렵고, 배포가 한 번 시작되면 중간 상태를 관측하기 어렵다.
③ 마이너 업데이트마저 노드를 순차로 재부팅하는 대공사이고, 롤백은 스냅샷 의존.
④ Controller 노드는 "제어 평면 + HA 클러스터 + DB"를 한 몸에 지고 있어 확장 단위가 거칠다.
⑤ 이미 OpenShift를 운영하는 조직이 클러스터 두 종류(OpenStack HA 스택 + 쿠버네티스)를 따로 배워야 한다.

18의 선택: 제어 평면을 OpenShift에 얹는다

Red Hat의 답은 단순합니다. OpenStack의 제어 평면은 그냥 컨테이너 워크로드다. 그러니 컨테이너 오케스트레이터가 관리하게 하고, 하이퍼바이저처럼 진짜 물리 리소스가 필요한 것만 RHEL 서버에 남기자는 것입니다. 실제로 RHOSO의 제어 평면은 RHOCP 클러스터 위의 워크로드로 호스팅·관리되고, 데이터 평면은 외부 RHEL 노드로 구성되어 자동화 실행 환경(Ansible)으로 관리됩니다.

Control plane
OpenShift 파드가 된 OpenStack

keystone, nova-api, neutron-server, glance-api, cinder-*, placement, barbican, galera, rabbitmq, memcached, ovn-northd가 모두 RHOCP 파드로 뜹니다. 죽으면 쿠버네티스가 다시 띄웁니다. Pacemaker는 사라집니다.

Data plane
여전히 물리에 붙어 있는 것들

nova-compute, libvirt/QEMU, ovn-controller, ovs는 RHEL 노드에 그대로 남습니다. VM에 CPU·메모리·NIC·SR-IOV를 꽂아 주는 일은 컨테이너로 추상화할 대상이 아니기 때문입니다.

쉽게 말하면

호텔로 비유해 보죠. 17.1은 프런트 데스크와 객실을 같은 건물, 같은 관리팀이 통째로 운영하는 방식이었습니다. 18은 프런트 데스크(예약·정산·안내 = 제어 평면)를 이미 운영 중인 본사 사무동(OpenShift)으로 옮기고, 객실동(하이퍼바이저 = 데이터 평면)만 현장에 남긴 구조입니다. 본사 사무동에는 이미 경비·전기·백업·모니터링 체계가 있으니, 프런트 데스크는 그 인프라를 그대로 물려받습니다.

02 — Fundamentals

30분 만에 잡는 OpenStack 기초

RHOSO를 이해하려면 OpenStack이 무엇인지가 먼저입니다. 이미 익숙하다면 이 절은 빠르게 훑고 03으로 가세요. 처음이라면 여기서 서비스 이름과 역할만 확실히 붙잡으면 이후가 훨씬 편해집니다.

OpenStack은 "사설 AWS를 만드는 부품 상자"

OpenStack은 서버·스토리지·네트워크를 API로 나눠 주는 IaaS 소프트웨어 모음입니다. 핵심은 "모음"이라는 단어입니다. 하나의 거대한 프로그램이 아니라, 각자 REST API와 DB를 가진 독립 서비스들이 메시지 큐로 대화하는 느슨한 연합체입니다. RHOSO 문서 표현대로, 컴퓨팅·스토리지·네트워킹 자원을 제어하는 상호작용하는 서비스들의 모음으로 IaaS 클라우드가 구현되고, 그 전부가 API로도 노출됩니다.

쉽게 말하면

각 서비스는 관공서 창구입니다. keystone은 신분증 발급소, nova는 차량 배차과, neutron은 도로과, glance는 도서관(이미지 보관), cinder는 창고 임대과(블록 볼륨)입니다. 창구끼리 서류를 주고받는 우편함이 RabbitMQ, 각 창구의 장부가 MariaDB(Galera)입니다.

03 — Upstream vs Product

업스트림 OpenStack과 RHOSO는 어떻게 다른가

"일반 OpenStack과 뭐가 다르냐"는 질문에는 두 층의 답이 필요합니다. ① 코드 층 — 사실 거의 같습니다. nova는 어디서나 nova입니다. ② 배포·운영 층 — 완전히 다릅니다. 여기가 제품의 정체성입니다.

05 — Architecture

제어 평면 · 데이터 평면 구조

RHOSO의 전체 구조는 네 개의 층으로 읽으면 깔끔합니다. ① OpenShift 플랫폼 층 → ② Operator 층 → ③ OpenStack 제어 평면 층(파드) → ④ 데이터 평면 층(RHEL 노드). 아래 탐색기에서 각 블록을 눌러 역할을 확인하세요.

층별로 다시 정리

Layer 1 · Platform
RHOCP 클러스터

마스터 3대 + 워커. 여기에 NMState Operator(노드 NIC 설정), MetalLB Operator(VIP 광고), Multus/Whereabouts(파드 다중 NIC), cert-manager(내부 TLS), Logging/Monitoring 스택이 사전 준비물로 들어갑니다.

Layer 2 · Operators
openstack-operator + 서비스 Operator

OperatorHub에서 openstack-operator 하나만 설치하면 나머지 서비스 Operator를 함께 설치·배치합니다. 즉 이 Operator가 여러분이 다루는 유일한 관리 인터페이스입니다.

Layer 3 · Control plane
OpenStackControlPlane CR

이 CR 하나가 keystone·nova·neutron·glance·cinder·placement·barbican·galera·rabbitmq·memcached·ovn을 파드로 펼칩니다. 서비스별 replica 수, VIP, 스토리지 클래스, 노드 배치까지 여기서 지정합니다.

Layer 4 · Data plane
OpenStackDataPlaneNodeSet + ...Deployment

RHEL 노드 그룹(NodeSet)을 정의하고, Deployment CR로 Ansible을 실행해 노드를 하이퍼바이저로 만들어 놓습니다. 노드 타입은 Compute, Networker, Storage 등으로 나뉩니다.

지원 토폴로지 두 가지

RHOSO는 compact 토폴로지와 dedicated nodes 토폴로지를 지원합니다.

기본값
Compact 토폴로지

RHOCP 제어 평면과 RHOSO 제어 평면이 같은 물리 노드를 공유합니다. 3노드 compact RHOCP 클러스터(마스터=워커) 위에 OpenStack 파드가 함께 올라가고, 데이터 평면은 별도 RHEL 노드입니다. PoC와 중소 규모에 가장 흔한 형태입니다.

대규모
Dedicated nodes 토폴로지

RHOCP 제어 평면용 노드 세트와 RHOSO 제어 평면용 노드 세트를 물리적으로 분리합니다. OpenStack 파드가 etcd·API 서버와 자원을 다투지 않으므로 대규모·성능 민감 환경에 적합합니다.

배치 제어 방법

기본적으로 Operator는 아무 워커 노드에나 OpenStack 서비스를 배치합니다. 특정 노드에 고정하고 싶으면 OpenStackControlPlane의 nodeSelector에 노드 라벨을 지정하고, 파드 분산 정책은 Topology CR로 제어합니다. Topology CR은 CR 최상단에 적용해 전체 기본 정책으로 쓰거나, 서비스별 스펙에서 개별 재정의할 수 있습니다. 예를 들어 cinder-scheduler는 자원을 거의 쓰지 않지만 cinder-api는 목록 조회 요청 때문에 네트워크 사용량이 큽니다 — 이런 서비스별 특성에 따라 배치를 나누는 것이 성능 튜닝의 첫 단계입니다.

NIC 설계 — 최소 2개가 필요한 이유

compact 배포에서는 각 제어 평면 워커 노드에 최소 두 개의 NIC가 필요합니다. 하나는 OpenShift 자체(클러스터 네트워크)용, 다른 하나는 OpenStack 서비스가 데이터 평면의 격리 네트워크와 통신하는 용도입니다. Compute 노드는 최소 1개의 NIC로 시작할 수 있고, 격리 네트워크 연결을 늘리며 확장합니다.

OVN 게이트웨이를 어디에 둘까 — 실무 결정 지점

외부 트래픽을 처리하는 OVN 게이트웨이는 제어 평면 또는 데이터 평면 어디에나 둘 수 있습니다. 제어 평면에 두면 해당 노드에 게이트웨이 전용 NIC가 필요하고, OVN 버전 업데이트 시 OpenShift가 서비스를 재시작해야 하므로 게이트웨이 트래픽에 순단이 생길 수 있습니다. 반면 데이터 평면의 전용 Networker 노드에 두면 OVN 업데이트 후 서비스 재시작이 필요하지 않습니다. 운영 중 순단을 허용할 수 없는 환경이라면 Networker 노드 분리를 강하게 권합니다.

07 — Networking

네트워킹: 가장 어려운 관문

RHOSO 구축에서 실패의 8할은 네트워크입니다. 이유는 명확합니다. OpenStack의 격리 네트워크 모델과 쿠버네티스의 네트워크 모델을 접합해야 하기 때문입니다. 이 절만 이해하면 나머지 구축은 순조롭습니다.

RHOSO 배포에 등장하는 네트워크

네트워크필수무엇을 나르는가
ctlplane (제어 평면 네트워크)필수노드 프로비저닝과 Ansible 접속, 제어 평면 ↔ 데이터 평면 관리 트래픽

세 가지 OpenShift 기능이 세 가지 문제를 푼다

문제 1
워커 노드를 VLAN에 물리기

NMState Operator + NodeNetworkConfigurationPolicy(NNCP). 워커 노드의 물리 NIC에 VLAN 인터페이스와 정적 IP를 만들어 격리 네트워크에 연결합니다.

문제 2
파드를 격리 네트워크에 붙이기

네트워크별 NetworkAttachmentDefinition(NAD) + Multus/macvlan + Whereabouts IPAM. 파드에 두 번째 NIC를 꽂아 internalapi·storage에 직접 통신하게 합니다.

문제 3
서비스 엔드포인트를 노출하기

MetalLB Operator + IPAddressPool + L2Advertisement. 내부 엔드포인트를 격리 네트워크의 VIP로 노출합니다. 공개 엔드포인트는 기본적으로 RHOCP Route로 노출됩니다.

데이터 평면 쪽은 다릅니다. NetConfig CR에 데이터 평면 네트워크의 서브넷을 전부 정의합니다. 최소 하나의 제어 평면 네트워크는 반드시 정의해야 하고, internalapi·storage·external 같은 조합형 네트워크는 VLAN으로 정의해 격리합니다. 각 정의에는 IP 할당 범위가 포함됩니다.

겹치면 안 되는 IP 풀 4종 — 실패의 최대 원인

RHOSO는 네 종류의 IP 풀을 사용하며 서로 겹쳐서는 안 됩니다. 아래는 internalapi 네트워크에 172.17.0.0/24를 배정한 공식 예시를 시각화한 것입니다. 각 구간에 마우스를 올려 보세요.

풀 종류정의 위치누가 쓰나필요 개수 감각
VIP 풀IPAddressPool (MetalLB)서비스 엔드포인트 VIP격리 네트워크당 약 10~15개. keystone·nova·neutron·cinder·glance·placement·heat 등이 internalapi에 VIP를 요구합니다(포트가 다르면 공유 가능)
파드 IPAMNetworkAttachmentDefinition (Whereabouts)격리 네트워크에 붙는 제어 평면 파드네트워크당 40~50개. 레플리카 수와 파드 교체율을 감당해야 합니다

설계 규칙

① 격리 네트워크는 최소 /24를 배정하세요. 네 종류 풀을 담고 성장 여유까지 확보하려면 그 이하는 위험합니다.
② 관례적 배치: 데이터 평면 노드는 상단(.100~.250), VIP는 그 아래(.80~.90), 제어 평면 파드는 중간(.30~.70), NNCP는 하단(.10~.20).
③ 업데이트·장애 시 새 파드가 기존 파드보다 먼저 생성될 수 있어 IPAM 범위에 일시적 초과 수요가 발생합니다. 딱 맞게 잡지 마세요.

데이터 평면 노드의 인터페이스 설정 — os-net-config

데이터 평면 노드의 네트워크 속성은 os-net-config가 구성합니다. 프로바이더는 레거시 ifcfg와 후속인 nmstate 두 가지이며, 현재 릴리스의 기본값은 nmstate입니다. ifcfg 프로바이더는 향후 폐기 예정입니다. 특별한 이유가 없다면 nmstate를 쓰고, 부득이하게 ifcfg가 필요하면 NodeSet CR에 edpm_network_config_nmstate: false를 설정합니다.

노드를 통째로 잃는 실수

NodeSet의 네트워크 설정을 바꿀 때 edpm_network_config_update: true로 두면 이후 configure-network 서비스를 포함한 Deployment가 생성될 때마다 네트워크 설정이 재적용됩니다. 적용 후 false로 되돌리지 않으면 노드가 네트워크 접속을 잃을 수 있습니다. 원격 데이터센터에서 이 사고가 나면 콘솔 출동 외에 방법이 없습니다.

IP 버전과 NFV

  • 거의 모든 물리 네트워크에서 IPv4·IPv6를 쓸 수 있고 일부 용도는 듀얼스택도 지원됩니다. 단 배포 후 Floating IP를 사용하는 외부 네트워크는 IPv4 또는 듀얼스택이어야 합니다 (IPv6는 NAT/FIP 대신 GUA를 전제로 하기 때문). 듀얼스택에서 FIP는 IPv4 서브넷에만 사용됩니다.
  • ironic 프로비저닝 네트워크는 사용례에 따라 지원 IP 버전이 달라지므로 표를 확인해야 합니다. 프로젝트 네트워크 엔드포인트에서 IPv6는 Geneve만 지원됩니다.
  • 통신사 환경이라면 DPDK와 SR-IOV로 패킷 처리 속도를 높이는 NFV 구성을 별도 가이드로 다룹니다. 이 경우 Compute 노드의 NUMA·hugepage·CPU 파티셔닝 설계가 함께 따라옵니다.
08 — Storage

스토리지 설계

RHOSO의 스토리지는 두 갈래로 생각해야 합니다. ① 제어 평면 파드가 쓰는 쿠버네티스 스토리지(PVC)와 ② OpenStack이 테넌트에게 제공하는 스토리지(Ceph 등 백엔드)입니다. 이 둘을 섞어 생각하면 설계가 엉킵니다.

① 제어 평면이 요구하는 OpenShift 스토리지

Galera DB, RabbitMQ, glance 이미지 스테이징, swift 등이 PVC를 사용합니다. 따라서 배포 전 StorageClass 생성이 사전 요구사항입니다. 여기서 두 가지를 챙기세요.

  • 성능 — Galera가 느려지면 모든 OpenStack API가 느려집니다. RWO 블록 스토리지 기반의 빠른 클래스를 쓰세요.
  • 용량 — glance는 이미지 변환·스테이징 시 상당한 공간을 요구하고, swift를 제어 평면에 두면 용량 계획이 더 중요해집니다.

② 테넌트에게 제공하는 스토리지

서비스제공 형태대표 백엔드RHOSO에서의 위치
cinder블록 볼륨Ceph RBD, 벤더 SAN(iSCSI/FC), NFS 4.xAPI·scheduler·volume·backup 모두 제어 평면 파드
glance이미지Ceph RBD, swift, 파일glance-api 파드. 여러 백엔드 동시 구성 가능
manila공유 파일시스템CephFS, CephFS-NFS, 벤더 NAS기본 비활성. 필요 시 활성화
swift객체swift 자체 링, Ceph RGW로 대체 가능기본 활성
Ceph는 어디에 사는가

RHOSO 18.0은 외부(external) Red Hat Ceph Storage 7·8·9를 지원합니다. 즉 Ceph는 RHOSO가 관리하는 대상이 아니라 이미 존재하는 별도 클러스터로 연결합니다. 17.1처럼 director가 Ceph까지 배포해 주던 방식과 다르므로, Ceph 배포·업그레이드·용량 관리는 별도 트랙(cephadm)으로 계획해야 합니다. 문서 예시는 Release 7 기준이며 상위 버전 사용 시 값을 조정합니다.

스토리지 관련 제약 — 미리 알아야 손해가 없다

스토리지 네트워크 실무

cinder와 manila는 백엔드에 따라 요구하는 네트워크 경로가 다릅니다. 특히 manila의 DHSS(driver handles share servers) 설정 여부에 따라 공유 서버를 누가 만들지가 달라지고, 그에 따라 네트워크 연결 설계가 바뀝니다. 제어 평면 파드가 스토리지 네트워크에 붙어야 하는지(NAD 필요 여부)를 설계 단계에서 확정하세요. 배포 후에 추가하려면 파드 재기동과 IP 계획 수정이 함께 필요합니다.

09 — Build

8단계 구축 실습 가이드

공식 절차는 8단계입니다. 아래 스테퍼를 순서대로 따라가면 전체 그림과 각 단계에서 무엇을 왜 하는지가 잡힙니다. YAML은 핵심만 발췌했습니다. 실제 배포에서는 반드시 사용 중인 18.0.x 버전의 공식 문서 예제를 기준으로 쓰세요.

시작 전 필수 조건

① 정상 동작하는 RHOCP 클러스터(x86_64 마스터·워커)
② cluster-admin 권한으로 클러스터에 접근 가능한 작업용 워크스테이션 — 제어 평면 설치와 데이터 평면 생성 작업 전부를 여기서 수행합니다
③ 사전 생성된 StorageClass

⑤ openstack-operators 네임스페이스와 제어 평면 네임스페이스(기본 openstack) 사이 통신을 막는 NetworkPolicy가 없어야 합니다

STEP 1 — RHOCP에 OpenStack Operator 설치

RHOCP OperatorHub에서 openstack-operator를 설치합니다. 이 Operator 하나가 앞서 본 서비스 Operator 전부를 설치하고, 이후 여러분이 그것들을 관리하는 인터페이스가 됩니다. 콘솔에서 클릭으로 해도 되고, 아래처럼 CLI로 해도 됩니다.

operator-install.sh
# 1) Operator용 네임스페이스와 OperatorGroup / Subscription 생성
$ oc new-project openstack-operators

# 2) OperatorHub 카탈로그에서 사용 가능한 채널 확인
$ oc get packagemanifest openstack-operator \
     -n openshift-marketplace -o jsonpath='{.status.channels[*].name}'

# 3) 설치 상태 확인 — 모든 Operator 파드가 Running이 될 때까지 대기
$ oc get pods -n openstack-operators
$ oc get csv -n openstack-operators

# 4) 제어 평면을 올릴 네임스페이스 준비 (기본 이름: openstack)
$ oc new-project openstack
확인 포인트

oc get crd | grep "^openstack"로 CRD가 등록되었는지 확인하세요. 여기서 CRD가 안 보이면 이후 모든 단계가 실패합니다. Operator 파드 로그와 CSV의 PHASE: Succeeded를 먼저 잡고 다음으로 넘어가세요.

STEP 2 — 서비스 접근용 Secret 만들기

OpenStack 서비스 파드들이 서로 인증할 때 쓰는 비밀번호 묶음을 Secret으로 넣습니다. 관례적으로 이름은 osp-secret이며, 제어 평면 CR의 spec.secret이 이것을 참조합니다.

  DatabasePassword: <strong-password>
  KeystoneDatabasePassword: <strong-password>
  NovaPassword: <strong-password>
  NeutronPassword: <strong-password>

데이터 평면용 Secret은 STEP 7에서 별도로 만듭니다(SSH 키, 서브스크립션, libvirt 접근 등).

운영 환경 주의

stringData에 평문을 넣은 파일을 Git에 커밋하지 마세요. Sealed Secrets / External Secrets Operator / Vault 연동이 실무 표준입니다. GitOps로 RHOSO를 관리한다면 이 지점 설계를 초기에 확정해야 나중에 되돌리기 어렵지 않습니다.

STEP 3 — 제어 평면 네트워크 준비

07장에서 본 세 가지를 실제로 만드는 단계입니다. 탭을 눌러 각 리소스를 확인하세요.

워커 노드의 물리 NIC 위에 VLAN 인터페이스를 만들고 정적 IP를 부여합니다. 워커 노드마다 하나씩 필요합니다.

nncp-worker-0.yaml
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: osp-enp6s0-worker-0
spec:
  desiredState:
    interfaces:
    # internalapi VLAN 20
    - name: internalapi
      type: vlan
      state: up
      vlan:
        base-iface: enp6s0
        id: 20
      ipv4:
        enabled: true
        dhcp: false
        address:
        - ip: 172.17.0.10      # NNCP 대역 .10~.20
          prefix-length: 24
      mtu: 1500
    # storage VLAN 21, tenant VLAN 22 도 동일 패턴으로 추가
  nodeSelector:
    kubernetes.io/hostname: worker-0
    node-role.kubernetes.io/worker: ""

STEP 4 — 데이터 평면 네트워크 정의 (NetConfig)

데이터 평면 노드에 부여할 IP·VLAN·게이트웨이를 한 개의 NetConfig CR에 모두 적습니다. 제어 평면 네트워크는 최소 하나 반드시 정의해야 하고, 나머지는 VLAN으로 격리합니다.

netconfig.yaml

    subnets:
    - name: subnet1
      cidr: 172.18.0.0/24

    subnets:
    - name: subnet1
      cidr: 172.19.0.0/24
      vlan: 22
      allocationRanges:

숫자의 출처

제어 평면은 배포 후에도 언제든 서비스를 추가·제거·조정할 수 있습니다. 대표적인 커스터마이즈 네 가지입니다.

a) 서비스 추가·제거

기본값은 "아무 워커 노드". 특정 노드에 고정하려면 노드에 라벨을 붙이고 nodeSelector로 지정합니다. 서비스마다 자원 특성이 다르다는 점을 활용하세요 — cinder-scheduler는 매우 가볍고, cinder-api는 목록 조회 때문에 네트워크를 많이 씁니다.

c) Topology CR로 분산 정책 지정

파드 분산(spread) 정책은 Topology CR로 정의하고, CR 최상단에 적용해 제어 평면 전체 기본값으로 쓰거나 서비스별로 재정의합니다. Galera·RabbitMQ 같은 상태 저장 서비스를 서로 다른 워커에 분산시키는 데 필수입니다.

d) Compute Cell 추가

대규모 배포에서는 Compute 노드를 cell 단위로 나눠 성능과 확장성을 얻습니다. cell을 추가할 때 cell마다 전용 nova metadata API 서비스를 두면 대규모 환경의 성능과 확장성이 개선됩니다. 단 하나의 NodeSet은 하나의 cell에만 연결될 수 있고, cell을 추가했다면 NodeSet에서 연결할 cell을 명시해야 합니다.

외부 Ceph를 붙이는 것이 가장 일반적인 형태입니다. 순서는 ① Ceph 클러스터에서 pool·client 키링 생성 → ② 키링과 ceph.conf를 Secret으로 클러스터에 주입 → ③ extraMounts로 서비스 파드에 마운트 → ④ 각 서비스의 백엔드 설정 추가입니다.

$ oc create secret generic ceph-conf-files -n openstack \
     --from-file=ceph.client.openstack.keyring=./ceph.client.openstack.keyring \

# ② 제어 평면 CR에 extraMounts 로 주입
spec:
  extraMounts:
  - name: v1
    region: r1
    extraVol:
    - propagation: [CinderVolume, GlanceAPI, ManilaShare]
      extraVolType: Ceph
      volumes:
      - name: ceph
        secret:
          secretName: ceph-conf-files
      mounts:
      - name: ceph
        mountPath: /etc/ceph
        readOnly: true

  # ③ cinder RBD 백엔드 설정
  cinder:
    template:
      cinderVolumes:
        ceph:
          networkAttachments: [storage]
          customServiceConfig: |
            [ceph]
            volume_backend_name=ceph
            volume_driver=cinder.volume.drivers.rbd.RBDDriver
            rbd_ceph_conf=/etc/ceph/ceph.conf
            rbd_user=openstack
            rbd_pool=volumes
            rbd_flatten_volume_from_snapshot=False
            rbd_secret_uuid=<fsid>

11 — Adoption

17.1 → 18 Adoption(이관)

Red Hat은 이 과정을 "업그레이드"라 부르지 않고 Adoption(채택)이라 부릅니다. 기존 overcloud의 데이터 평면 노드는 유지하고, 제어 평면만 OpenShift로 옮겨서 새 제어 평면이 기존 노드를 인수하는 방식이기 때문입니다.

두 가지 출발점

경로 A
RHOSP 17.1 overcloud

director로 배포한 일반적인 17.1 환경. Adopting a Red Hat OpenStack Platform 17.1 deployment 가이드를 따릅니다.

경로 B
director Operator 환경

OpenShift 위에서 director Operator로 운영하던 환경. 별도 가이드가 제공됩니다.

데이터 평면 Adoption의 큰 흐름

  1. 17.1 제어 평면의 남은 서비스 정지 — 특히 클라우드 데이터베이스 노드와 메시징 노드를 정지합니다.
  2. 필요한 CR 배포 — 새 제어 평면과 NodeSet 정의를 준비합니다.
  3. Compute 서비스 fast-forward 업그레이드 — 17.1에서 18.0으로 건너뜁니다.
  4. Networker 서비스 Adoption — Controller 노드나 전용 Networker 노드에서 돌던 네트워크 서비스를 인수합니다. 어떤 서비스를 Networker 노드에서 돌릴지 결정한 뒤 별도 NodeSet CR로 정의합니다.
가장 위험한 순간 — 절대 하지 말 것

새 RHOSO 제어 평면이 데이터 평면을 관리하기 시작한 뒤에는 17.1 제어 평면·데이터 평면의 서비스를 절대 다시 활성화해서는 안 됩니다. 두 개의 제어 평면(또는 두 개의 데이터 평면)이 같은 워크로드를 관리하게 되면 데이터 손상, 기존 워크로드 제어 상실, 신규 워크로드 기동 불가가 발생합니다. "롤백해 보자"는 판단이 가장 큰 사고를 만듭니다. 되돌릴 계획은 Adoption 시작 전에 세워야 합니다.

정지해도 되는 것과 안 되는 것

17.1 제어 평면에서 정지해야 하는 것: 클라우드 데이터베이스 노드, 메시징 노드.
정지하면 안 되는 것: Compute·Storage·Networker 역할 노드, 그리고 OVN Controller Gateway 에이전트를 돌리고 있는 Controller 노드. 이 구분을 틀리면 이관 중 워크로드 네트워크가 끊깁니다.

12 — Use cases

사용 사례 5가지

"OpenStack은 이제 안 쓰는 거 아니냐"는 말이 있지만, 실제로는 특정 요구가 있는 곳에서 대체 불가로 남아 있습니다. RHOSO 18이 실제로 채택되는 다섯 가지 맥락을 봅니다.

① 통신사 NFV · 5G Core

요구
패킷 처리 성능과 결정론

vRAN·UPF·5GC 같은 VNF는 밀리초 단위 지연과 라인레이트 패킷 처리를 요구합니다. 일반 가상 NIC로는 불가능합니다.

RHOSO의 답
DPDK · SR-IOV · CPU 피닝

NFV 환경 구성 가이드가 별도로 제공되며, Compute 노드의 hugepage·NUMA·CPU 파티셔닝과 SR-IOV VF 할당을 NodeSet의 Ansible 변수로 선언합니다.

이 사용 사례에서는 Networker 노드 분리가 거의 필수입니다. OVN 게이트웨이를 제어 평면에 두면 OpenShift의 OVN 업데이트가 게이트웨이 순단을 일으키는데, 통신 서비스에서는 허용되지 않기 때문입니다. 또한 FR4에서 Load-balancing service의 OVN provider 드라이버가 기술 프리뷰를 벗어나 정식 지원이 된 점, FWaaS로 라우터 포트 수준의 정책을 걸 수 있게 된 점이 멀티테넌트 통신 환경에 직접 도움이 됩니다.

② VMware 대체 프라이빗 클라우드

최근 가장 문의가 많은 시나리오입니다. vSphere 라이선스 비용 구조 변화 이후, 기존 VM 워크로드를 그대로 받아 줄 수 있는 온프레미스 IaaS를 찾는 수요가 늘었습니다. RHOSO는 VMware Migration Toolkit으로 VM을 이전하는 경로를 제품 문서에 포함하고 있어, "이론적으로 가능"이 아니라 "지원되는 절차"라는 점이 차별점입니다.

현실적인 조언

VMware를 쓰던 팀이 RHOSO로 오면 운영 문화 자체를 바꿔야 합니다. vCenter의 클릭 조작에 익숙한 조직에 CR 기반 선언형 운영을 들이려면 별도 교육 트랙이 필요합니다. 기술 검증(PoC)보다 운영 조직 검증이 더 오래 걸립니다. Horizon은 기본 비활성이지만 이런 조직에는 반드시 켜 주는 것이 현실적입니다.

③ 금융 · 공공 규제 환경

암호화
FIPS 모드

RHOSO는 FIPS 활성화 제어 평면 준비 절차를 문서화하고 있습니다. RHOCP의 FIPS 상태 확인부터 시작합니다.

키 관리
barbican

기본 활성. 볼륨 암호화·인증서 관리의 전제이며, 감사 요건이 있는 환경에서 필수 컴포넌트입니다.

망 분리
격리 네트워크

internalapi/storage/tenant/external의 물리 분리가 설계에 내장되어 있어 망 분리 요건 설명이 쉽습니다.

여기에 하나 더. 단일 RHOCP 클러스터에 여러 RHOSO 환경을 네임스페이스로 나눠 배포하는 구성이 지원됩니다. 네임스페이스별로 OpenStackControlPlane과 NodeSet·Deployment를 따로 만들고, 로드밸런서 주소 풀도 네임스페이스별로 분리합니다(예: internalapi_1). 개발/검증/운영을 물리 클러스터 하나로 묶고 싶은 조직에 유용합니다.

④ AI · GPU 워크로드 인프라

컨테이너로 다 되는 것은 아닙니다. 라이선스가 VM을 요구하는 상용 AI 소프트웨어, 커널 모듈을 직접 다루는 학습 환경, 격리가 필요한 멀티테넌트 GPU 제공 등에서 VM은 여전히 필요합니다. RHOSO는 Virtual acceleration configuration 가이드로 가속기 구성을 다루며, 같은 OpenShift 클러스터 위에서 컨테이너 AI 워크로드와 VM 기반 워크로드를 한 플랫폼 팀이 운영할 수 있다는 점이 이 조합의 핵심 이점입니다.

설계 시 확인

PCI passthrough·vGPU 구성은 Compute 노드의 IOMMU·커널 파라미터·드라이버 버전에 강하게 의존합니다. NodeSet의 Ansible 변수로 관리할 수 있지만, 하드웨어 조합의 지원 여부를 Red Hat 하드웨어 카탈로그에서 먼저 확인하세요. 또한 RHOSO 18.0은 x86_64만 지원하므로 ARM 기반 GPU 서버(예: Grace 계열)를 데이터 평면으로 편입하는 구성은 대상이 아닙니다.

⑤ 엣지 · 다중 사이트

Compute cell로 노드를 그룹화해 대규모·분산 환경의 성능과 확장성을 확보하고, cell마다 전용 metadata API를 두어 지연을 줄이는 구성이 가능합니다. 사이트별 NodeSet을 분리하고 각각 다른 네트워크 설정·tuned 프로파일을 적용하면 "중앙 제어 평면 + 원격 컴퓨트" 형태의 엣지 토폴로지를 만들 수 있습니다.

③ NodeSet만 수정하고 기다려 보기 — 아무 일도 일어나지 않음을 직접 확인하고, 새 Deployment를 만들어 반영되는 것을 보세요. 이 한 번의 경험이 문서 열 줄보다 강합니다.

마지막으로 — 이 강의의 한 문장 요약

RHOSO 18을 이해하는 것은 결국 "어떤 것이 파드가 되었고, 어떤 것이 서버로 남았으며, 그 둘을 무엇이 연결하는가"를 아는 것입니다. 파드가 된 것은 OpenShift의 방식(선언형 CR, 재스케줄, MetalLB, PVC)으로 다루고, 서버로 남은 것은 Ansible의 방식(NodeSet, Deployment 잡, os-net-config)으로 다룹니다. 이 두 문법을 구분해서 쓸 수 있게 되는 순간, 나머지 문서는 그냥 읽힙니다.

본 강의는 Red Hat 공식 문서(RHOSO 18.0 Planning / Deploying / Customizing / Release notes)의 공개 내용을 토대로 한국어 학습자용으로 재구성한 교육 자료입니다. 세부 파라미터와 지원 범위는 사용 중인 18.0.x 버전의 공식 문서를 최종 근거로 삼으세요. YAML 예시는 구조 이해를 위한 발췌본이며 그대로 운영에 사용하기 위한 완전한 매니페스트가 아닙니다.
