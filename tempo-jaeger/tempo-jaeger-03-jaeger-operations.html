Jaeger 구축·운영 실전띄우고, 읽고, 오래 굴리는 법

2편에서 설계도를 읽었다면 이번에는 직접 띄웁니다. 명령 네 번이면 Jaeger, OpenSearch, 예제 앱이 돌아가는 실습 환경이 생깁니다. 탭을 눌러 각 단계에서 무엇을 입력하고 무엇을 확인해야 하는지 먼저 훑어보세요.

출력은 예시입니다. 숫자, 날짜, 컨테이너 이름은 환경에 따라 다릅니다. 필요한 파일은 1장에서 내려받을 수 있습니다.

1

실습 환경 만들기

실습 환경은 컨테이너 세 개로 이루어집니다. 트레이스를 저장할 OpenSearch, 수집과 조회를 함께 하는 Jaeger(all-in-one 구성에 외부 저장소), 그리고 트레이스를 만들어 줄 예제 앱 HotROD입니다. HotROD는 Jaeger 프로젝트가 제공하는 가상의 차량 호출 서비스로, 여러 마이크로서비스가 서로 호출하는 트레이스를 버튼 클릭만으로 만들어 줍니다.

빈 폴더를 하나 만들고 아래 네 파일을 같은 폴더에 저장하세요. 각 탭의 파일 받기 버튼으로 바로 내려받을 수 있습니다.


    

  

  

    
실습용 설정과 운영용 설정의 차이

    
이 실습은 OpenSearch 보안 플러그인을 끄고, 복제본(replica)을 0으로 두고, 모든 포트를 호스트에 열었습니다. 노트북 한 대에서 빠르게 돌려 보기 위한 선택입니다. 운영 환경에서는 인증과 TLS를 켜고, 복제본을 1 이상으로 두고, UI 포트는 인증 프록시 뒤에 둡니다(10장).

  

  

    
메모리가 부족하다면

    
OpenSearch는 설정한 힙(-Xms1g -Xmx1g) 외에도 메모리를 더 씁니다. Docker Desktop에 할당한 메모리가 4GB 미만이면 OpenSearch가 기동 중에 종료될 수 있습니다. Linux 호스트라면 vm.max_map_count를 262144 이상으로 올려야 하는 경우도 있습니다.

  







  
2
첫 트레이스 확인

  
docker compose up -d로 띄운 뒤, 아래 순서로 데이터가 흐르는 길을 앞에서부터 확인합니다. 문제가 생겼을 때도 같은 순서로 점검하면 원인 구간을 빠르게 좁힐 수 있습니다.

  

    
확인 순서명령·위치정상이라면

    
      
1. Jaeger가 살아 있나curl -s localhost:13133/status상태가 정상(OK)으로 표시됨

      
2. 스팬을 받고 있나curl -s localhost:8888/metrics | grep accepted_spansHotROD를 클릭할 때마다 숫자가 증가

      
3. 저장소에 쓰고 있나curl -s localhost:8888/metrics | grep sent_spansaccepted와 비슷한 속도로 증가, send_failed는 0

      
4. 인덱스가 생겼나curl -s 'localhost:9200/_cat/indices/lab-*?v'lab-jaeger-span-날짜, lab-jaeger-service-날짜 인덱스가 보임

      
5. UI에 보이나http://localhost:16686Service 목록에 frontend, customer, driver 등이 보임

    
  

  

    
인덱스 이름 읽기

    
index_prefix: "lab"을 주면 인덱스 이름이 lab-jaeger-span-2026-09-25처럼 됩니다. 접두사 뒤에 jaeger-span(스팬), jaeger-service(서비스·오퍼레이션 목록), jaeger-dependencies(서비스 의존성), jaeger-sampling(적응형 샘플링 데이터)이 붙고, 기본 설정에서는 날짜별로 새 인덱스가 생깁니다. 한 OpenSearch 클러스터에 고객사 여러 곳의 Jaeger를 붙인다면 접두사를 고객사별로 다르게 주는 것이 가장 간단한 분리 방법입니다.

  

  

    
Service 목록에 jaeger가 보이는 이유

    
Jaeger는 UI 조회 요청을 스스로 추적해서 자기 자신을 서비스로 남깁니다. UI를 몇 번 새로 고치면 jaeger 서비스가 생기는 것은 정상입니다. 원치 않으면 Jaeger 컨테이너에 OTEL_TRACES_SAMPLER=always_off 환경 변수를 주면 꺼집니다.

Jaeger UI의 핵심 화면 네 가지를 흉내 낸 모형입니다. 실제 화면과 모양은 조금 다르지만, 무엇을 보고 어떻게 판단하는지는 같습니다. 위쪽 메뉴를 눌러 화면을 바꿔 보세요.

  

    
Jaeger UI

    

  

  
트레이스 화면의 다른 보기

  
트레이스 상세 화면 오른쪽 위에서 보기 방식을 바꿀 수 있습니다. 기본은 Timeline(워터폴)이고, 호출 관계를 그래프로 보는 Graph, 서비스·오퍼레이션별 시간 합계를 표로 보는 Statistics, 스팬을 표로 정렬해 보는 Spans Table, 시간 비중을 불꽃 그래프로 보는 Flamegraph, 원본 데이터를 보는 JSON이 있습니다. 스팬이 수백 개인 트레이스는 Timeline보다 Statistics로 "어느 서비스가 시간을 가장 많이 썼나"를 먼저 보는 편이 빠릅니다.

  

    
System Architecture 탭이 비어 있다면

    
메모리나 Badger 저장소에서는 서비스 의존성 그래프가 저장된 트레이스로부터 바로 계산되지만, OpenSearch·Elasticsearch·Cassandra에서는 별도 배치 작업(spark-dependencies)이 주기적으로 트레이스를 분석해 의존성 인덱스를 채워야 합니다. 실습 환경에서 이 탭이 비어 있는 것은 정상입니다. Helm 차트에는 이 작업을 CronJob으로 켜는 spark.enabled 옵션이 있습니다.

  







  
4
Kubernetes로 옮기기

  
공식 문서가 안내하는 Kubernetes 배포 방법은 두 가지입니다. Jaeger Helm 차트와 OpenTelemetry Operator입니다. v1 시절의 Jaeger Operator는 v1 전용이라 더 이상 쓰지 않습니다.

  

    
Helm 차트 (jaegertracing/jaeger)OpenTelemetry Operator

    
      
배포 단위all-in-one Deployment 하나 (replica 수 조정)OpenTelemetryCollector 리소스 하나당 역할 하나. collector와 query를 따로 만들 수 있음

      
설정 방식userconfig 값에 Jaeger YAML 전체를 넣음리소스의 spec.config에 Jaeger YAML을 넣음

      
부가 기능인덱스 정리·롤오버·의존성 계산 CronJob, OAuth2 Proxy 사이드카, Ingress·HTTPRoute자동 확장(HPA), 이미 OTel Operator를 쓰는 클러스터와 운영 방식 통일

      
주의점차트 스스로 실험적이라고 밝힘. 마이너 버전에서도 변경이 있을 수 있음UI 포트(16686)를 spec.ports에 직접 추가해야 하고, 서비스 이름에 -collector가 붙음

      
잘 맞는 곳중소 규모, 빠른 도입, 저장소 정리 작업까지 한 번에읽기·쓰기를 나눠 확장해야 하는 곳, GitOps로 CR을 관리하는 곳

    
  

  

    

    

    

  

  

    
Helm의 userconfig는 "덮어쓰기"입니다

    
userconfig를 주면 차트는 내장 all-in-one 설정 대신 그 내용만 씁니다. 저장소 부분만 적고 service, receivers, healthcheckv2를 빠뜨리면 기동에 실패하거나 probe가 실패합니다. 차트는 probe로 13133 포트의 /status를 확인하므로 healthcheckv2는 반드시 넣으세요.

  







  
5
보존 기간과 인덱스 관리

  
OpenSearch·Elasticsearch 저장소에서 운영 사고의 1순위는 디스크가 가득 차는 것입니다. 스팬 데이터는 매일 쌓이는데 아무도 지우지 않기 때문입니다. Jaeger는 보존 기간을 스스로 관리하지 않습니다. 인덱스를 어떤 방식으로 나누고 언제 지울지를 운영자가 정해야 합니다.


  

    
문서와 실제 동작이 다른 부분이 있습니다 (v2.20 이후)

    
v2.21 공식 문서의 Elasticsearch 페이지는 아직 use_aliases, use_ilm 설정으로 롤오버를 설명합니다. 그런데 v2.20부터 이 옛 설정은 기본적으로 검증 오류가 되어 Jaeger가 뜨지 않습니다. 인덱스 종류별 rotation 설정이 새 방식이고, 저장소의 예제 설정 파일(config-*-auto-rollover.yaml 등)이 이 방식을 씁니다. 옛 설정을 당장 고칠 수 없다면 --feature-gates=-jaeger.es.config.rejectLegacyRotationFlags로 잠시 끌 수 있지만, 이 기능 게이트는 앞으로 없어질 예정입니다.

  


  
인덱스 회전 방식 네 가지

  

    
rotation 값인덱스 생성오래된 데이터 삭제언제 쓰나

    
      
periodic
기본값		Jaeger가 날짜별(또는 시간별) 인덱스를 직접 만듦. 예: prod-jaeger-span-2026-09-25jaeger-es-index-cleaner를 CronJob으로 매일 실행가장 단순. 대부분의 중소 규모

      
manual_rollover읽기·쓰기 별칭(alias) 사용. 새 인덱스는 jaeger-es-rollover 작업이 만듦rollover·lookback·cleaner 작업을 CronJob으로날짜 단위로는 인덱스 크기가 들쭉날쭉할 때

      
auto_rollover별칭 사용. 크기·기간 조건이 되면 OpenSearch ISM(ES는 ILM) 정책이 자동으로 새 인덱스 생성같은 정책이 자동 삭제대규모, CronJob 관리를 줄이고 싶을 때

      
data_stream데이터 스트림 방식정책으로 관리설정 항목은 있지만 아직 구현 중

    
  


  
용량 계산기

  
보존 기간과 샘플링 비율이 저장 용량을 어떻게 바꾸는지 계산해 보세요. 평균 스팬 크기는 속성 개수와 이벤트 수에 따라 크게 달라지므로, 실제 값은 운영 중인 클러스터에서 _cat/indices의 문서 수와 용량으로 계산해 넣는 것이 가장 정확합니다.

  

    

      
      
      
      
      
    

    

    

  


  
가장 단순한 방법: periodic + index cleaner

  
기본값인 날짜별 인덱스를 쓰고, 매일 한 번 "N일보다 오래된 인덱스 삭제" 작업을 돌립니다. Helm 차트라면 값 두 줄로 CronJob이 생깁니다.


esIndexCleaner:
  enabled: true
  numberOfDays: 7          # 7일보다 오래된 인덱스 삭제 (기본 스케줄 매일 23:55)
storage:
  elasticsearch:
    url: https://opensearch.observability:9200   # 정리 작업이 접속할 주소

  
컨테이너로 직접 돌린다면 이렇습니다. 첫 번째 인자가 보존 일수, 두 번째가 저장소 주소입니다.


docker run --rm -e INDEX_PREFIX=lab \
  jaegertracing/jaeger-es-index-cleaner:latest 7 http://opensearch:9200


  
대규모라면: auto_rollover + ISM 정책

  
날짜가 아니라 크기 기준으로 인덱스를 자르고 삭제까지 OpenSearch에 맡기는 방식입니다. 세 단계로 준비합니다.

  

    

    

    

  







  
6
샘플링 운영

  
샘플링 이론은 OTel 시리즈 9편에서 다뤘으니, 여기서는 Jaeger 백엔드가 개입하는 방식에 집중합니다. 결정 시점에 따라 두 갈래입니다.

  

    
원격 샘플링 (head 기반)tail 샘플링

    
      
결정 시점요청이 시작될 때, 앱의 SDK가 결정트레이스가 끝난 뒤, 수집기가 결정

      
Jaeger의 역할remote_sampling 확장이 서비스·오퍼레이션별 비율을 SDK에 알려 줌tail_sampling processor로 에러·지연 트레이스만 골라 저장

      
장점앱 부하와 네트워크 비용까지 줄어듦. 재배포 없이 비율 변경"에러가 난 트레이스는 모두 남긴다" 같은 결과 기반 정책 가능

      
한계시작 시점엔 결과를 모르므로 에러 트레이스도 확률적으로 버려짐앱은 모든 스팬을 보내야 하고, 수집기가 트레이스를 메모리에 모아 둬야 함

    
  


  
전략 파일 만들기

  
서비스별 초당 요청 수를 보고 샘플링 비율을 정해 보세요. 비율은 그 서비스에서 시작되는(루트 스팬인) 요청에 적용됩니다. 아래에서 만들어진 JSON이 remote_sampling.file.path로 지정하는 파일입니다. 파일을 고치면 Jaeger가 자동으로 다시 읽습니다.

  

    
서비스요청/초샘플링 비율저장/초

    

    

    

    

  

  

    
전략 파일이 실제로 적용되려면

    
앱의 SDK가 Jaeger 원격 샘플러를 쓰도록 설정되어 있어야 합니다. 예를 들어 Java 자동 계측 에이전트는 OTEL_TRACES_SAMPLER=jaeger_remote와 OTEL_TRACES_SAMPLER_ARG=endpoint=http://jaeger:5779,pollingIntervalMs=5000,initialSamplingRate=0.1처럼 설정합니다. 지원 여부와 설정 방법은 언어별 SDK마다 다르므로 각 SDK 문서를 확인하세요. 설정하지 않은 앱(실습의 HotROD 포함)은 이 파일과 무관하게 SDK 기본값대로 동작합니다. 앞단에 OTel Collector가 있다면 Collector가 샘플링 전략 요청을 Jaeger로 대신 전달하게 할 수도 있습니다.

    
서비스 목록에 없는 서비스는 default_strategy를 따르고, 전략 파일이 아예 없으면 Jaeger는 모든 서비스에 0.1%를 알려 줍니다. "원격 샘플링을 켰더니 트레이스가 거의 안 보여요"의 흔한 원인입니다.

  


  
적응형 샘플링으로 바꾸려면

  
서비스가 많아 비율을 사람이 관리하기 어렵다면 적응형 샘플링이 대안입니다. Jaeger가 관찰한 트래픽으로 엔드포인트별 확률을 계산해 초당 목표 트레이스 수를 맞춥니다. 계산 결과를 여러 인스턴스가 공유하도록 sampling_store에 저장하며, memory(all-in-one 전용), Badger, Cassandra, Elasticsearch, OpenSearch를 쓸 수 있습니다.


processors:
  adaptive_sampling:          # 관찰과 확률 계산 (파이프라인에 추가해야 동작)
extensions:
  remote_sampling:
    adaptive:
      sampling_store: main_store
      initial_sampling_probability: 0.1    # 처음 보는 엔드포인트의 시작 비율
      target_samples_per_second: 1.0       # 엔드포인트별 목표
service:
  pipelines:
    traces:
      processors: [memory_limiter, adaptive_sampling, batch]


  
tail 샘플링: 에러와 느린 요청은 전부 남기기


processors:
  tail_sampling:
    decision_wait: 10s        # 트레이스가 끝나기를 기다리는 시간
    num_traces: 50000         # 메모리에 모아 둘 트레이스 수
    policies:
      - name: keep-errors
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: keep-slow
        type: latency
        latency: {threshold_ms: 500}
      - name: baseline
        type: probabilistic
        probabilistic: {sampling_percentage: 5}

  

    
tail 샘플링과 여러 대 배포

    
한 트레이스의 스팬이 서로 다른 Jaeger 인스턴스로 흩어지면 각 인스턴스는 트레이스의 일부만 보고 결정하게 됩니다. 여러 대를 쓸 때는 앞단 OTel Collector에서 trace ID 기준 로드밸런싱(loadbalancing exporter)으로 같은 트레이스를 같은 인스턴스로 보내야 합니다. 구성 방법은 OTel 시리즈 9편을 참고하세요.

  







  
7
Monitor 탭 켜기 (SPM)

  
Jaeger UI의 Monitor 탭(서비스 성능 모니터링, SPM)은 서비스·오퍼레이션별 요청률, 에러율, 지연 시간(P50·P75·P95)을 보여 줍니다. 서비스 이름을 몰라도 "지금 이상한 곳"을 찾아 바로 트레이스 검색으로 넘어갈 수 있다는 것이 장점입니다. 메트릭을 만드는 방법은 두 가지입니다.

  

    
방법 1: spanmetrics + Prometheus방법 2: OpenSearch/ES에서 직접 계산

    
      
원리spanmetrics 커넥터가 스팬을 받을 때 메트릭을 미리 계산해 Prometheus 호환 저장소에 저장조회할 때 Jaeger가 트레이스 저장소에서 바로 집계

      
추가로 필요한 것메트릭 파이프라인, Prometheus(또는 Mimir 등)없음. 실습 환경이 이 방식

      
장점조회가 가볍고, 같은 메트릭으로 Grafana 대시보드·경보도 만들 수 있음구성이 가장 단순

      
주의점카디널리티 관리 필요 (6편 Tempo metrics-generator와 같은 문제)조회할 때마다 집계 부하가 트레이스 저장소로 감

    
  


connectors:
  spanmetrics:
    metrics_flush_interval: 60s
exporters:
  prometheus:
    endpoint: 0.0.0.0:8889          # Prometheus가 이 주소를 수집
extensions:
  jaeger_storage:
    metric_backends:
      prom_store:
        prometheus:
          endpoint: http://prometheus:9090
          normalize_calls: true
          normalize_duration: true
  jaeger_query:
    storage:
      traces: main_store
      metrics: prom_store
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger_storage_exporter, spanmetrics]   # 스팬을 커넥터로도 보냄
    metrics/spanmetrics:
      receivers: [spanmetrics]                              # 커넥터가 메트릭 입구가 됨
      exporters: [prometheus]

  
두 방법 모두 Jaeger가 받은 스팬으로 계산합니다. 앱에서 head 샘플링을 하고 있다면 요청률이 실제보다 낮게 보이니, 절대값보다 추세와 비율(에러율, 지연)을 보세요. 어느 방법이든 마지막으로 UI 설정 파일에 "monitor": {"menuEnabled": true}를 넣어야 메뉴가 나타납니다. 기본값은 꺼짐입니다.

Jaeger 자체 모니터링

  
트레이싱 백엔드가 조용히 스팬을 버리고 있으면, 장애 조사 날에야 "그 시간대 트레이스가 없다"는 걸 알게 됩니다. Jaeger v2는 OTel Collector의 내부 메트릭을 8888 포트로 노출하므로 Prometheus로 수집해 경보를 걸어 두세요. 스팬이 지나가는 길과 각 지점의 메트릭은 이렇습니다.

  

    
받음receiver가 받아들인 스팬
otelcol_receiver_accepted_spans_total

    
거부메모리 한계 등으로 거절 (보낸 쪽이 재시도할 수도)
otelcol_receiver_refused_spans_total

    
대기exporter 큐 사용량과 용량
otelcol_exporter_queue_size
otelcol_exporter_queue_capacity

    
저장저장소에 쓴 스팬
otelcol_exporter_sent_spans_total

    
실패저장소 쓰기 실패
otelcol_exporter_send_failed_spans_total

  

  
정상이라면 받은 양과 저장한 양이 거의 같습니다. Jaeger 저장소의 monitoring/jaeger-mixin에 공식 경보 규칙 예시가 있고, 아래는 그 방식을 참고해 MSP에서 바로 쓰기 좋게 정리한 규칙입니다. 임곗값은 고객사 상황에 맞춰 조정하세요.


groups:
- name: jaeger
  rules:
  - alert: JaegerReceiverRefusingSpans            # 입구에서 거부 (메모리 한계 등)
    expr: |
      sum(rate(otelcol_receiver_refused_spans_total[5m])) by (receiver)
      / (sum(rate(otelcol_receiver_accepted_spans_total[5m])) by (receiver)
       + sum(rate(otelcol_receiver_refused_spans_total[5m])) by (receiver)) > 0.01
    for: 10m
  - alert: JaegerStorageWriteFailing              # 저장소 쓰기 실패
    expr: |
      sum(rate(otelcol_exporter_send_failed_spans_total[5m])) by (exporter)
      / (sum(rate(otelcol_exporter_sent_spans_total[5m])) by (exporter)
       + sum(rate(otelcol_exporter_send_failed_spans_total[5m])) by (exporter)) > 0.01
    for: 10m
  - alert: JaegerExporterQueueNearlyFull          # 곧 유실이 시작될 신호
    expr: otelcol_exporter_queue_size / otelcol_exporter_queue_capacity > 0.8
    for: 5m
  - alert: JaegerNoSpansReceived                  # 수집이 완전히 멈춤
    expr: sum(rate(otelcol_receiver_accepted_spans_total[10m])) == 0
    for: 15m

  

    
저장소 쪽도 함께 보세요

    
Jaeger의 쓰기 실패 대부분은 저장소가 원인입니다. OpenSearch라면 쓰기 스레드 풀 거부(bulk rejection), 디스크 사용률의 watermark 도달, 클러스터 상태(yellow·red)를 함께 경보로 걸어 두면 원인을 한 번에 찾을 수 있습니다. 디스크가 flood-stage watermark(기본 95%)를 넘으면 인덱스가 읽기 전용이 되어 모든 쓰기가 실패합니다.

보안 최소선

  
운영 환경에 올리기 전 최소한 이 네 가지는 확인하세요.

  

    
구간위험대응

    
      
UI·조회 API (16686, 16685)로그인 기능이 없어 URL, 사용자 ID, 내부 주소가 담긴 트레이스가 그대로 노출인증 프록시 뒤에 배치. Helm 차트의 jaeger.oAuthSidecar로 OAuth2 Proxy 사이드카를 붙이고 사내 IdP(OIDC)와 연결

      
수집 포트 (4317, 4318)누구나 가짜 스팬을 넣거나 대량으로 보내 저장소를 채울 수 있음NetworkPolicy로 허용된 네임스페이스만 접근, receiver에 TLS 설정, 외부 수집은 인증을 붙인 OTel Collector gateway를 거치게 함

      
저장소 연결설정 파일에 비밀번호가 평문으로 남음비밀번호는 Secret → 환경 변수 → ${env:...}로 주입. 저장소 계정은 Jaeger 인덱스 접두사에만 권한 부여

      
스팬 속성개인정보·토큰이 속성으로 수집됨앞단 Collector의 attributes·redaction processor로 제거. 계측 단계에서 넣지 않는 것이 최선

    
  

  
receiver에 TLS를 거는 설정은 OTel Collector와 같습니다.


receivers:

    protocols:

        endpoint: 0.0.0.0:4317
