    2설치 방식 고르기
    
  
    Community Distribution을 직접 운영한다면 3편 2장의 원칙, 원본은 고치지 않고 오버레이로 덧씌운다를 끝까지 지킵니다. 원본은 릴리스 태그로 고정해 참조하고, 우리의 변경은 모두 오버레이 폴더에 둡니다.
    

    # overlays/prod/kustomization.yaml (단순화)
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../upstream/26.03.1/example          # 릴리스 태그를 그대로 복사해 둔(vendored) 원본
patches:
- path: patches/gateway-tls.yaml          # 5장
- path: patches/dex-connector.yaml        # 13편
- path: patches/kfp-external-db.yaml      # 4장
- path: patches/replicas-pdb.yaml        # 6장
images:                                  # 7장: 사내 미러
- name: ghcr.io/kubeflow/notebooks/jupyter-web-app
  newName: registry.internal/kubeflow/notebooks/jupyter-web-app
    
  
    
    
    원본을 가져오는 방법장점주의
    
    
      
    릴리스 태그를 저장소에 복사(vendoring)오프라인에서도 build 가능, 업그레이드 때 차이를 Git diff로 검토저장소가 커짐
    
      
    원격 참조(?ref=26.03.1)저장소가 가벼움build마다 외부 접속, 폐쇄망 불가
    
        
  
    
  
    GitOps로 반영할 때는 3편의 설치 탑 순서를 지킵니다. Argo CD의 동기화 순서(sync wave)로 cert-manager, Istio, 인증 구성요소, 플랫폼, ML 구성요소, 프로필 순으로 나눠 반영하면 3편의 “처음 몇 번은 실패” 루프가 필요 없어집니다. 저장소의 experimental 폴더에는 일부 구성요소의 Helm 차트도 있지만 아직 실험적입니다.

    4상태를 밖으로: DB와 저장소
    
  
    Kubeflow에서 잃으면 안 되는 상태는 몇 군데에 모여 있습니다. 클러스터를 다시 만들어도 이것들만 남아 있으면 복구할 수 있습니다.
    
  
    
    
    상태기본 위치운영 선택지
    
    
      
    Pipelines 메타데이터 (실행, 실험, 파이프라인 정의, 계보)클러스터 안 MySQL관리형 MySQL(RDS, Azure Database, Cloud SQL)로 분리
    
      
    Pipelines 아티팩트클러스터 안 SeaweedFS (26.03부터, 예전 MinIO)클라우드 오브젝트 스토리지나 사내 S3 호환 저장소로. 설정 방법은 버전마다 달라 해당 버전 문서 확인
    
      
    Katib 지표클러스터 안 MySQL관리형 DB로 분리하거나, 결과를 Hub와 Git에 옮기고 DB는 짧게 보관
    
      
    Kubeflow Hub 메타데이터클러스터 안 DB관리형 DB로 분리. 9편의 “장부”라 가장 먼저 지킬 대상
    
      
    사용자 PVC (노트북 작업 공간 등)StorageClass의 볼륨스냅샷 정책, 중요 결과는 오브젝트 스토리지로 옮기는 습관(4편)
    
      
    Kubernetes 리소스 (프로필, InferenceService, 반복 실행 등)etcdGit이 원천이면(12편) 다시 반영하면 됨. 그 밖의 것은 Velero 같은 도구로 백업
    
        
  
    
  
    
    외부 DB가 정답은 아닙니다
    
    관리형 DB는 백업, 고가용성, 패치를 맡겨 주지만 비용과 네트워크 경로가 늘고, 폐쇄망 온프레미스에는 없을 수도 있습니다. 클러스터 안에 두기로 했다면 정기 백업과 복구 훈련, 볼륨 스냅샷을 반드시 둡니다. 핵심은 위치가 아니라 “잃어도 되돌릴 수 있는가”입니다.
    
  
    

    


    
  
    5여는 법: HTTPS와 인증서
    
  
    3편 10장에서 보안 쿠키 때문에 외부 주소는 HTTPS여야 한다고 했습니다. 흔한 구성은 클라우드나 MetalLB의 로드밸런서가 Istio 인그레스 게이트웨이로 연결하고, Istio 게이트웨이가 cert-manager가 발급한 인증서로 TLS를 종료하는 방식입니다.
    

    apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: kubeflow-gateway
  namespace: kubeflow
spec:
  selector:
    istio: ingressgateway
  servers:
  - port: {number: 443, name: https, protocol: HTTPS}
    tls:
      mode: SIMPLE
      credentialName: kubeflow-tls        # istio-system의 Secret, cert-manager가 발급하고 갱신
    hosts: ["kubeflow.example.com"]
  - port: {number: 80, name: http, protocol: HTTP}
    tls: {httpsRedirect: true}        # HTTP는 HTTPS로 돌려보냄
    hosts: ["kubeflow.example.com"]
    
  
      
    
    • 인증서 발급: 공개 도메인이면 cert-manager의 ACME(Let's Encrypt 등), 사내 도메인이면 사내 CA를 cert-manager Issuer로 등록합니다. 사내 CA라면 사용자 PC와, 노트북에서 API를 부르는 클라이언트가 그 CA를 믿게 해야 합니다.
      • 
    
    • TLS를 어디서 끝낼까: 클라우드 로드밸런서에서 끝내고 안쪽은 HTTP로 넘기는 구성도 가능합니다. 이때 게이트웨이와 oauth2-proxy가 원래 요청이 HTTPS였음을 알 수 있게 전달 헤더 설정을 확인해야 보안 쿠키 문제가 생기지 않습니다.
      • 
    
    • 게이트웨이 서비스: 게이트웨이 앞에 무엇을 둘지(로드밸런서 직접, 사내 L7 장비, Gateway API 기반 게이트웨이)는 조직의 네트워크 표준에 맞춥니다. 온프레미스의 LoadBalancer 타입 서비스는 이 시리즈의 MetalLB 강의 방식으로 제공할 수 있습니다.
      • 
    
    • 13편에서 바꾼 IdP의 redirect URI와 oauth2-proxy의 외부 주소 설정도 이 도메인과 일치해야 합니다.

    6고가용성과 백업
    
  
    
    
    대상고가용성백업과 복구
    
    
      
    Kubernetes 제어부관리형 서비스에 맡기거나, 온프레미스는 제어부 노드 3대관리형은 공급자 책임. 온프레미스는 etcd 스냅샷
    
      
    Istio 게이트웨이, oauth2-proxy, Dex복제본 2개 이상, PodDisruptionBudget, 여러 영역에 분산설정은 Git
    
      
    Kubeflow 컨트롤러들대부분 리더 선출로 한 개만 일함. 복제본을 늘리면 장애 시 넘겨받는 시간이 줄어듦설정은 Git
    
      
    웹 앱과 API 서버복제본 2개 이상상태 없음
    
      
    DB와 저장소관리형 DB의 다중 영역 구성, 오브젝트 스토리지자동 백업, 시점 복구, 버킷 버전 관리
    
      
    노드시스템 노드 풀과 작업 노드 풀 분리, 여러 영역노드는 소모품
    
        
  
    
  
    
    복구 훈련 없는 백업은 백업이 아닙니다
    
    분기에 한 번은 스테이징에서 “클러스터가 통째로 사라졌다”를 가정하고 복구해 보세요. 새 클러스터에 Git으로 설치를 반영하고, DB를 복원하고, 프로필과 반복 실행이 돌아오는지, 레지스트리의 모델이 다시 서빙되는지 확인합니다. 걸린 시간이 곧 실제 복구 목표 시간입니다.
    
  
    

    


    
  
    7폐쇄망 설치
    
  
    인터넷이 막힌 환경에서는 설치와 운영 중에 밖에서 가져오는 모든 것을 안으로 들여와야 합니다. 이미지만 생각하기 쉽지만 그보다 많습니다.
    
  
    
    
    밖에서 오는 것언제사내 대안
    
    
      
    Kubeflow와 의존 구성요소 이미지설치, 업그레이드사내 레지스트리 미러와 kustomize images 덮어쓰기
    
      
    노트북, 학습, 서빙 런타임 이미지사용자 작업같은 미러. 만들기 화면과 런타임의 이미지 목록을 미러 주소로
    
      
    Python 패키지노트북의 pip, packages_to_install사내 PyPI 미러, pip 설정, pip_index_urls(5편)
    
      
    Hugging Face 모델과 데이터셋LLM 미세 조정과 서빙사내 오브젝트 스토리지에 미리 복사하고 s3:// 경로로
    
      
    Katib 알고리즘, KServe 런타임 등 부가 이미지해당 기능을 처음 쓸 때설정(ConfigMap)의 이미지 주소를 미러로
    
      
    인증서HTTPS사내 CA
    
        
  
    

    # 설치에 필요한 이미지 목록 뽑기 (오버레이를 build한 결과에서)
kustomize build overlays/prod | grep -oE 'image: *[^ ]+' | awk '{print $2}' | sort -u > images.txt

# 목록대로 사내 레지스트리에 복사 (skopeo, crane 등)
while read img; do
  skopeo copy --all docker://$img docker://registry.internal/${img#*/}
done < images.txt
    
  
    이 목록에는 ConfigMap 안에 문자열로 들어 있는 이미지(Katib 알고리즘, KServe 런타임, 노트북 이미지 목록 등)가 빠집니다. 그것들은 기능별로 따로 확인해 추가하세요. 처음 한 번 인터넷이 되는 스테이징에서 모든 기능을 써 보고, 실제로 내려받은 이미지 목록을 노드에서 모으는 방법이 가장 확실합니다.

    제자리 업그레이드같은 클러스터에 새 버전 오버레이를 반영자원 추가 없음문제가 생기면 되돌리기가 어려움. CRD 변경이 큰 버전에서 위험
    
      
    새 클러스터로 이사새 클러스터에 새 버전을 설치하고 DB와 Git의 리소스를 옮긴 뒤 도메인을 전환되돌리기 쉬움. 6장의 복구 훈련과 같은 절차잠시 두 배의 자원. 상태 이전 절차가 필요
    
        
  
    

    


    
  
    9배포판과 관리형 비교
    
  
    1편 7장의 질문으로 돌아갑니다. 정말 직접 운영할까요? 여기까지 읽었다면 직접 운영의 무게를 압니다.
    
  
    
    
    선택지정체강점약점어울리는 곳
    
    
      
    Community Distribution 직접 운영이 시리즈가 다룬 공식 매니페스트를 kustomize와 GitOps로최신 기능, 완전한 통제, 라이선스 비용 없음업그레이드, 보안 패치, 장애 대응이 모두 우리 몫플랫폼 팀이 있는 조직, MSP의 표준 스택
    
      
    Canonical Charmed KubeflowJuju 기반 운영 도구로 패키징한 배포판. 상용 지원과, 클라우드 마켓플레이스의 관리형 상품도 있음설치와 업그레이드 자동화, 지원 계약Juju 방식에 익숙해져야 함. 업스트림 대비 반영 시차지원 계약이 필요한 기업, Ubuntu 중심 환경
    
      
    Red Hat OpenShift AIKubeflow 계열 구성요소(파이프라인, KServe, 모델 레지스트리, 학습, Kueue 등)를 OpenShift에 통합한 제품. 오픈소스 상류는 Open Data HubOpenShift의 보안과 운영 체계에 통합, 상용 지원OpenShift 전제, 구성과 이름이 업스트림과 다름이미 OpenShift를 쓰는 조직
    
      
    클라우드 관리형 MLSageMaker AI, Vertex AI(KFP 호환 파이프라인 실행 포함), Azure Machine Learning운영 부담 최소클라우드 종속, 사용량 비용, 온프레미스 불가한 클라우드에 집중하고 플랫폼 인력이 적은 팀
    
      
    필요한 구성요소만 조합KServe만, Pipelines만, Trainer와 Kueue만 등 단독 설치가볍고 단순로그인, 사용자 격리 등 플랫폼 기능은 직접한두 기능만 필요한 팀(1편 10장)
    
        
  
    
  
    배포판의 구성과 지원 범위는 자주 바뀝니다. 선택 전에 각 공급사의 최신 지원 버전과 구성요소 목록을 확인하세요.

    14정리와 다음 편
    
  
      
    
    1. 운영 설치는 릴리스 태그로 고정한 원본 위의 kustomize 오버레이이고, Git과 Argo CD가 반영합니다. 설치 순서는 동기화 순서로 표현합니다.
      2. 
    
    2. 잃으면 안 되는 상태는 Pipelines와 Hub의 DB, 아티팩트, PVC입니다. 밖으로 빼든 안에 두든 되돌릴 수 있게 백업과 복구 훈련을 합니다.
      3. 
    
    3. 외부 주소는 HTTPS와 자동 갱신 인증서로. 폐쇄망은 이미지뿐 아니라 패키지, 모델, 설정 속 이미지까지 안으로 들여옵니다.
      4. 
    
    4. 업그레이드는 반년마다의 정기 행사입니다. 릴리스 노트, 오버레이 diff, 백업, 스테이징 리허설, 사용자 작업 호환 확인, 단계적 반영 순으로.
      5. 
    
    5. 직접 운영, 상용 배포판, 관리형, 부분 조합 중에서 운영 인력과 지원 요구, 클라우드 전략에 맞게 고릅니다.
      6. 
  
    
    
    현장에서 쓰이는 장면
    
  
    • 제조. 폐쇄망 공장에 이미지, 패키지, 모델 미러를 갖추고 사내 CA로 HTTPS를 연 뒤 설치합니다.
    • MSP. 여러 고객사의 Kubeflow를 같은 오버레이 구조로 관리해 반년 업그레이드를 함대 단위로 돌립니다(16편).
    • 스타트업. 클라우드 관리형 Kubernetes 위에 관리형 DB와 오브젝트 스토리지로 상태를 빼 두어, 클러스터를 지우고 다시 만들어도 복구됩니다.
