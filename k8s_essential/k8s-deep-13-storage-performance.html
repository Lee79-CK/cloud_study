블록·파일·객체 선택과 성능 설계

“디스크가 느려요”라는 신고의 절반은 디스크가 아니라 잘못 고른 스토리지 종류, VM의 대역폭 한도, 큐 깊이 1로 도는 애플리케이션 때문입니다. 이 편은 IOPS·처리량·지연이 서로 어떻게 묶여 있는지부터 시작해, 세 클라우드의 블록 디스크 클래스, RWX를 푸는 파일 스토리지의 성능 절벽, 로컬 NVMe와 객체 스토리지 마운트의 적정 용도를 비교합니다. 마지막에 fio로 직접 벤치마크해 고객에게 내밀 수 있는 워크로드별 StorageClass 설계 가이드를 만듭니다.

이 워크로드에는 어떤 스토리지를?

워크로드 예시를 고르거나 요구 사항을 직접 바꾸면, AWS·Azure·GCP·온프렘에서의 추천 스토리지와 설정값(프로비저닝할 IOPS·처리량), 그리고 놓치기 쉬운 경고가 나옵니다. 수치 한도는 2026년 10월 벤더 문서 기준의 대략값이며 설계 전 반드시 확인하세요.

0

읽는 법과 목표

쉬운 말로 블록 스토리지는 내 컴퓨터에 꽂은 외장 디스크처럼 한 컴퓨터가 독점하는 빠른 저장소, 파일 스토리지는 사무실 공유 폴더처럼 여러 컴퓨터가 함께 쓰는 저장소, 객체 스토리지는 사진을 맡기는 대형 보관소(통째로 넣고 통째로 꺼내는 곳)입니다. 고속도로로 비유하면 IOPS는 1초에 지나가는 차 대수, 처리량은 1초에 옮기는 짐의 총무게, 지연은 차 한 대가 출발해서 도착하기까지 걸리는 시간입니다. 작은 차를 많이 보내는 일(데이터베이스)과 큰 트럭을 적게 보내는 일(로그·백업)은 필요한 도로가 다릅니다.

이 편을 마치면 할 수 있는 것

  • IOPS·처리량·지연·큐 깊이의 관계로 성능 문제를 해석하고, 디스크 한도와 VM 한도를 구분할 수 있습니다.
  • gp3·io2, Premium SSD v2·Ultra, Hyperdisk Balanced·Extreme을 비교하고 VolumeAttributesClass로 무중단 성능 조정을 할 수 있습니다.
  • RWX 요구에 맞는 파일 스토리지를 고르고 각각의 성능 절벽을 미리 경고할 수 있습니다.
  • 로컬 NVMe·emptyDir·객체 스토리지 마운트를 적정한 곳에만 쓸 수 있습니다.
  • fio로 재현 가능한 벤치마크를 하고, 결과로 고객용 StorageClass 설계 가이드를 만들 수 있습니다.
1

성능의 세 숫자: IOPS·처리량·지연

지표뜻지배하는 워크로드함정
IOPS초당 I/O 요청 수데이터베이스, 작은 파일 많은 작업블록 크기를 말하지 않은 IOPS는 의미가 없음(4KiB와 256KiB는 다름). 벤더마다 IOPS를 세는 기준 크기가 다름
처리량초당 옮기는 바이트(MiB/s)로그·Kafka·백업·분석 스캔IOPS × 블록 크기. 둘 중 먼저 닿는 한도가 실제 한도
지연요청 하나의 왕복 시간커밋마다 fsync하는 DB, etcd평균이 아니라 p99를 봐야 함. 네트워크 스토리지는 원리상 로컬보다 김
큐 깊이동시에 처리 중인 요청 수—앱이 한 번에 요청 하나만 보내면 IOPS는 지연이 정한다

리틀의 법칙: IOPS = 큐 깊이 ÷ 지연

지연이 1ms인 디스크에 앱이 요청을 하나씩만 보낸다면(큐 깊이 1) 초당 1,000번이 최대입니다. 디스크에 16,000 IOPS를 프로비저닝해도 쓰지 못합니다. 단일 스레드로 커밋하는 데이터베이스가 “비싼 디스크로 바꿨는데 안 빨라졌다”고 하는 대부분의 이유입니다. 반대로 지연을 줄이면(로컬 NVMe, io2·Ultra·Extreme) 큐 깊이가 낮은 워크로드가 빨라집니다.

시니어 포인트: 디스크보다 VM이 먼저 막힌다 클라우드 VM에는 인스턴스 크기별 디스크 대역폭·IOPS 상한이 있습니다(AWS의 EBS 최적화 대역폭, Azure VM의 디스크 처리량 상한, GCE 머신 유형별 상한). 작은 노드에 80,000 IOPS 디스크를 붙이면 노드 한도에서 막힙니다. 게다가 한 노드의 여러 Pod 디스크가 그 한도를 나눠 씁니다. 성능 설계표에는 디스크 한도와 노드 한도를 나란히 적으세요.

VolumeAttributesClass로 성능 바꾸기

쉬운 말로 StorageClass가 “어떤 회사의 어떤 창고 상품”이라면, VolumeAttributesClass(VAC)는 “같은 창고의 등급(빠름·보통)”입니다. 창고를 옮기지 않고 등급만 바꿀 수 있습니다.
  • 상태. 1.34에서 GA. PVC의 spec.volumeAttributesClassName을 바꾸면 external-resizer가 드라이버의 ControllerModifyVolume을 불러 IOPS·처리량 같은 속성을 바꿉니다(12편 사이드카 표).
  • 지원. EBS CSI(gp3·io2 IOPS·처리량), GCE PD CSI(Hyperdisk), Azure Disk CSI(Premium SSD v2·Ultra) 등 드라이버가 지원하는 키만 쓸 수 있습니다. 드라이버마다 파라미터 이름이 다릅니다.
  • 왜 좋은가. StorageClass를 바꾸려면 새 PVC로 데이터를 옮겨야 하지만, VAC는 같은 디스크의 성능만 조정합니다. 트래픽 시즌에 올렸다가 내리는 운영이 가능해집니다.
  • 제약. 클라우드 쪽 수정 간격 제한(EBS는 수정 후 대기 시간, 11편)이 그대로 적용되고, 수정 중에는 성능이 과도기 상태일 수 있습니다. 실패하면 PVC 상태에 결과가 남습니다.
EBS gp3 성능을 무중단으로 올리기
apiVersion: storage.k8s.io/v1
kind: VolumeAttributesClass
metadata: {name: gp3-fast}
driverName: ebs.csi.aws.com
parameters:
  iops: "10000"
  throughput: "500"            # 10,000 × 0.25 = 2,500 이내라 가능
---
# 기존 PVC에 지정 → 디스크 교체 없이 성능만 변경
# kubectl patch pvc data -p '{"spec":{"volumeAttributesClassName":"gp3-fast"}}'
# kubectl get pvc data -o jsonpath='{.status.currentVolumeAttributesClassName} {.status.modifyVolumeStatus}'

RWX를 푸는 방법과 성능 절벽

쉬운 말로 공유 폴더는 편리하지만, 모든 파일 열기·닫기·잠그기를 네트워크 건너 서버에 물어봐야 합니다. 큰 파일을 쭉 읽는 일은 잘하지만, 작은 파일 수만 개를 만들거나 매번 “확실히 저장됐나요?”(fsync)를 묻는 일에서 갑자기 느려집니다. 이렇게 어느 지점부터 성능이 뚝 떨어지는 곳을 성능 절벽이라고 부릅니다.

  1. 워크로드를 흉내 내라. DB는 4~16KiB 랜덤 혼합과 fsync 지연, 로그는 1MiB 순차 쓰기, 분석은 1MiB 순차 읽기. 하나의 숫자로 스토리지를 평가하지 마세요.

  5. 평균이 아니라 분위수. fio JSON 출력의 지연 p50·p99·p99.9를 남깁니다.
  6. 버스트를 구분. 크레딧 기반 디스크·파일 시스템은 처음 몇 분만 빠를 수 있습니다. 장시간 결과를 따로 측정하세요.

실습 0. 공통 도구

    

    
bench.sh — PVC와 fio Job을 만들고 결과를 요약
#!/usr/bin/env bash
# 사용: ./bench.sh <context> <storageclass> <test> [size_gi] [runtime_s] [accessMode]
# test: randread | randwrite | mixed | seqread | seqwrite | fsync
set -euo pipefail
CTX=$1 SC=$2 T=$3 SIZE=${4:-100} RT=${5:-120} AM=${6:-ReadWriteOnce}
K="kubectl --context $CTX -n bench"
NAME="fio-$T-$(echo "$SC" | tr -c 'a-z0-9-' '-' | cut -c1-24 | sed 's/-*$//')"
FS=$(( SIZE * 7 / 10 ))G                                        # 테스트 파일은 PVC의 70%
case $T in
  randread)  A="--rw=randread --bs=4k --iodepth=32 --numjobs=4 --ioengine=libaio --direct=1" ;;
  randwrite) A="--rw=randwrite --bs=4k --iodepth=32 --numjobs=4 --ioengine=libaio --direct=1" ;;
  mixed)     A="--rw=randrw --rwmixread=70 --bs=8k --iodepth=16 --numjobs=4 --ioengine=libaio --direct=1" ;;
  seqread)   A="--rw=read --bs=1M --iodepth=16 --numjobs=2 --ioengine=libaio --direct=1" ;;
  seqwrite)  A="--rw=write --bs=1M --iodepth=16 --numjobs=2 --ioengine=libaio --direct=1" ;;
  fsync)     A="--rw=write --bs=4k --iodepth=1 --numjobs=1 --ioengine=sync --fdatasync=1"; FS=2G ;;
esac
kubectl --context "$CTX" create ns bench 2>/dev/null || true
$K apply -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: $NAME}
spec: {storageClassName: $SC, accessModes: ["$AM"], resources: {requests: {storage: ${SIZE}Gi}}}
---
apiVersion: batch/v1
kind: Job
metadata: {name: $NAME}
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: fio
        image: alpine:3.21
        command: ["sh", "-c", "apk add --no-cache fio >/dev/null 2>&1 && fio --name=t --filename=/data/fio.bin --size=$FS --time_based --runtime=$RT --ramp_time=15 --group_reporting --output-format=json $A"]
        volumeMounts: [{name: d, mountPath: /data}]
      volumes: [{name: d, persistentVolumeClaim: {claimName: $NAME}}]
EOF
$K wait --for=condition=complete job/$NAME --timeout=$(( RT + 900 ))s
mkdir -p results; OUT="results/$CTX.$SC.$T.json"
$K logs job/$NAME > "$OUT"
NODE=$($K get pod -l job-name=$NAME -o jsonpath='{.items[0].spec.nodeName}')
ITYPE=$(kubectl --context "$CTX" get node "$NODE" -o jsonpath='{.metadata.labels.node\.kubernetes\.io/instance-type}')
jq -r --arg c "$CTX" --arg s "$SC" --arg t "$T" --arg i "$ITYPE" '.jobs[0] as $j |
  [$c,$s,$t,$i,
   (($j.read.iops+$j.write.iops)|floor),
   ((($j.read.bw+$j.write.bw)/1024)|floor),
   ((($j.read.clat_ns.percentile["99.000000"] // $j.write.clat_ns.percentile["99.000000"] // 0)/1000000*100|floor)/100),
   ((($j.sync.lat_ns.percentile["99.000000"] // 0)/1000000*100|floor)/100)] | @tsv' "$OUT" | tee -a results/summary.tsv
$K delete job/$NAME pvc/$NAME --wait=false

현장 사례

    
IOPS를 다섯 배로 올렸는데 DB가 그대로다

      
원인. 두 가지가 겹쳤습니다. 노드가 작은 인스턴스라 EBS 대역폭 한도에 먼저 닿았고, DB의 커밋 경로는 큐 깊이 1의 fsync라 지연이 성능을 정하고 있었습니다.

      
대응. 노드를 디스크 대역폭이 큰 인스턴스로 옮기고, 커밋 지연이 중요한 DB는 io2로 바꿨습니다. 프로비저닝 IOPS는 원래대로 낮춰 비용을 회수했습니다.

      
교훈. “디스크 한도 · VM 한도 · 앱의 큐 깊이” 세 가지를 동시에 봐야 합니다(1장 계산기).

    

    
CI 빌드가 EFS 위에서 열 배 느리다

      
원인. 빌드 작업 공간을 RWX가 필요하다는 이유로 EFS에 두었는데, 의존성 설치가 작은 파일 수십만 개를 만드는 메타데이터 작업이었습니다.

      
대응. 작업 공간은 노드의 emptyDir(로컬 NVMe)로, 공유가 필요한 결과물만 객체 스토리지로 옮겼습니다.

      
교훈. RWX 요구를 받으면 먼저 정말 동시에 쓰는가를 묻고, 공유 파일 시스템의 메타데이터 절벽을 고객에게 미리 알리세요.

    

    
공유 파일 위의 데이터베이스가 가끔 손상된다

      
원인. “여러 노드에서 재시작될 수 있게” 하려고 PostgreSQL 데이터 디렉터리를 SMB 파일 공유에 두었습니다. 잠금 의미 차이와 높은 fsync 지연이 겹쳐 장애 전환 때 손상이 생겼습니다.

      
교훈. DB는 RWO 블록 + 앱 복제 또는 관리형 DB가 정석입니다. 4장 함정을 설계 리뷰 체크리스트에 넣으세요.

    

    
노드 교체 후 캐시 서버의 데이터가 전부 사라졌다

      
원인. 성능 때문에 단일 Redis의 영속 파일을 로컬 NVMe에 두었는데, 노드 그룹 업그레이드로 VM이 교체되며 인스턴스 스토어가 지워졌습니다.

      
교훈. 로컬 NVMe는 복제가 있거나 다시 만들 수 있는 데이터에만 씁니다. 업그레이드 런북에 “로컬 디스크 사용 워크로드” 항목을 두세요.

    

    
S3 마운트에 로그를 이어 쓰려다 실패

      
원인. 기존 파일에 덧붙여 쓰기(append)와 이름 변경을 하는 로그 라이브러리를 객체 스토리지 마운트에 연결했습니다. 마운트 드라이버는 이 동작을 지원하지 않거나 매우 비싸게 처리했습니다.

      
교훈. 객체 마운트는 읽기 위주·새 파일 순차 쓰기에만 씁니다. 로그는 로그 파이프라인으로 보내세요.

    

    
Filestore 비용이 예상의 열 배

      
원인. PVC마다 새 Filestore 인스턴스가 만들어지는 StorageClass를 썼고, 등급의 최소 용량 단위 때문에 작은 PVC 수십 개가 각각 큰 용량으로 과금됐습니다.

      
교훈. 파일 스토리지의 과금 단위와 최소 용량을 StorageClass 설계 단계에서 확인하고, 소용량 다수 패턴은 공유 하나에 여러 PVC를 담는 방식(멀티 공유 등)을 검토하세요.

    

    
벤치마크 결과가 실제보다 열 배 좋았다

      
원인. --direct=1 없이 작은 테스트 파일(1GiB)로 측정해 노드 메모리 캐시에서 읽은 결과였습니다. 고객 보고서에 그대로 들어갈 뻔했습니다.

      
교훈. 7장의 여섯 규칙을 벤치마크 보고서의 앞쪽에 “측정 조건”으로 적으세요.
