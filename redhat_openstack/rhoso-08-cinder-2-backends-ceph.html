8편Cinder 2: 백엔드 연동과 Ceph 기초

6편과 7편에서 “Ceph라면 빠르다”, “접속 설정은 8편에서”라고 미뤄 둔 이야기를 이번 편에서 끝냅니다. Ceph가 데이터를 어떻게 흩어 저장하는지, 그 Ceph를 RHOSO의 Glance·Cinder·Nova에 어떻게 연결하는지, 그리고 볼륨이 error에 빠졌을 때 무엇을 확인하고 어떻게 되살리는지.

섹션 1

이 편의 목표

  1. Ceph의 구성 요소(MON · MGR · OSD)와 풀 · PG · CRUSH · RBD · keyring을 설명한다.
  2. OpenStack용 풀(vms · volumes · images · backups)과 사용자(client.openstack)를 설계한다.
  3. RHOSO에서 Ceph 접속 정보를 Secret + extraMounts로 Glance·Cinder·Cinder backup에, ConfigMap + 사용자 정의 데이터 플레인 서비스로 Nova에 연결한다.
  4. NFS 백엔드와 멀티 백엔드를 구성하고 운영상 차이를 설명한다.
  5. 볼륨 생애주기 전체를 OpenStack과 Ceph 양쪽에서 추적한다.
  6. 볼륨이 error·멈춤 상태일 때 실제 상태를 확인하고 안전하게 복구한다.

이 편의 비유: 대형 물류 창고 체인

Ceph는 물건(데이터)을 작은 상자(객체)로 나눠 여러 창고(OSD)에 사본 세 개씩 보관하는 물류 체인입니다. 어느 상자를 어느 창고에 둘지는 중앙 장부가 아니라 모두가 아는 계산 규칙(CRUSH)으로 정해서, 손님(클라이언트)이 직접 창고로 찾아갑니다. OpenStack 서비스들이 이 창고에 드나들려면 주소록(ceph.conf)과 출입증(keyring)이 필요한데, RHOSO에서는 이 둘을 Secret에 담아 필요한 Pod와 노드에 나눠 줍니다.

섹션 2

왜 OpenStack과 Ceph인가

이유설명
하나로 세 가지블록(RBD → Cinder·Nova·Glance), 파일(CephFS → Manila), 오브젝트(RGW → Swift·S3 대체)를 한 클러스터가 제공
복사 없는 복제Glance·Cinder·Nova가 모두 Ceph를 쓰면 raw 이미지에서 볼륨·VM 디스크를 몇 초 만에 만들 수 있음(6편)
라이브 마이그레이션이 쉬움VM 디스크가 공유 저장소(Ceph)에 있으면 디스크를 옮기지 않고 메모리만 옮기면 됨(10편)
수평 확장서버·디스크를 추가하면 용량과 성능이 함께 늘어남. 특정 벤더 장비에 묶이지 않음
자기 치유디스크·서버가 고장 나면 남은 사본으로 자동 재복제

Ceph는 공짜가 아니다

Ceph는 강력하지만 네트워크(대역폭·지연), 디스크 수, 운영 역량을 요구합니다. 작은 환경에서 무리하게 쓰면 성능이 기대에 못 미치고, 용량이 꽉 차면 클러스터 전체 쓰기가 멈춥니다(섹션 15). 이미 좋은 상용 스토리지 어레이가 있다면 그 벤더의 Cinder 드라이버를 쓰는 것도 훌륭한 선택입니다.

섹션 3

Ceph 최소 구조

데몬 다섯 종류

데몬하는 일보통 몇 개
MON (모니터)클러스터 지도(어느 OSD가 살아 있나, 배치 규칙)를 관리. 과반수 합의로 동작3 또는 5 (홀수)
MGR (매니저)상태 수집, 대시보드, 오케스트레이터(cephadm) 등 관리 기능2 (활성 1 + 대기)
OSD디스크 하나를 맡아 실제 데이터(객체)를 저장하고, 다른 OSD와 복제·복구디스크 수만큼 (수십~수천)
MDSCephFS(파일 시스템)의 메타데이터. RBD만 쓰면 불필요CephFS 사용 시
RGWS3·Swift 호환 오브젝트 게이트웨이오브젝트 사용 시

데이터는 어떻게 저장되나

  1. RBD 이미지(볼륨 하나)는 기본 4MB 크기의 객체들로 잘게 나뉩니다. 100GB 볼륨이면 객체 약 25,600개입니다.
  2. 각 객체는 이름의 해시값으로 PG(배치 그룹) 중 하나에 들어갑니다.
  3. 각 PG는 CRUSH 규칙에 따라 서로 다른 장애 영역(보통 서로 다른 서버)의 OSD 3개에 놓입니다. 첫째가 주(primary) OSD입니다.
  4. 클라이언트(QEMU, Cinder, Glance)는 클러스터 지도만 받아 오면 스스로 계산해 해당 OSD에 직접 읽고 씁니다. 중간 게이트웨이가 없어서 확장성이 좋습니다.
기억할 숫자뜻
size = 3복제 풀의 사본 수 (기본 권장)
min_size = 2사본이 이 수 미만이면 그 PG는 쓰기를 멈춤(데이터 보호)
4MBRBD 객체 기본 크기
85% · 90% · 95%nearfull(경고) · backfillfull(복구 이동 중단) · full(쓰기 중단) 기본 비율

풀과 인증

  • 풀은 데이터를 담는 논리 공간입니다. 풀마다 복제 수, PG 수, 용도(rbd·cephfs·rgw)가 정해집니다.
  • Ceph의 인증 방식은 cephx입니다. 사용자(예: client.openstack)마다 비밀 키와 권한(caps)이 있고, 키를 담은 파일이 keyring입니다.
  • 클라이언트에게는 두 파일이 필요합니다: ceph.conf(모니터 주소 등 주소록)와 ceph.client.openstack.keyring(출입증).
  • 클러스터마다 고유 ID인 FSID가 있습니다. OpenStack 설정의 rbd_secret_uuid에 이 값을 씁니다(섹션 7).

섹션 4

객체 배치 시뮬레이터: OSD가 죽으면?

서버 3대, OSD 6개, 복제 3(서버마다 1개 사본), min_size 2인 작은 클러스터에 볼륨 하나(객체 8개, PG 8개)가 있습니다. OSD를 눌러 고장을 내 보고, PG 상태와 볼륨 입출력이 어떻게 되는지 보세요.

시뮬레이터에서 확인할 것

  • OSD 하나, 심지어 서버 하나가 통째로 죽어도 사본이 서로 다른 서버에 있으므로 볼륨은 계속 읽고 쓸 수 있습니다(degraded). 실제 Ceph는 이후 남은 사본으로 자동 재복제합니다.
  • 서로 다른 서버의 OSD 두 개가 동시에 죽으면 사본이 1개만 남는 PG가 생기고, min_size 2 때문에 그 PG는 입출력을 멈춥니다(inactive). 데이터를 지키기 위한 안전장치지만, VM 입장에서는 디스크가 멈춘 것처럼 보입니다.
  • 그래서 Ceph 노드 점검은 OpenShift 노드처럼 한 번에 하나씩, 그리고 ceph osd set noout으로 불필요한 재복제를 막고 진행합니다(26편).

섹션 5

OpenStack용 풀과 사용자

풀누가 쓰나안에 생기는 RBD 이미지 이름
imagesGlance<이미지 ID> + 보호된 스냅샷 @snap (복제의 원본)
volumesCindervolume-<볼륨 ID>, 스냅샷은 volume-…@snapshot-<스냅샷 ID>
vmsNova (임시 디스크를 Ceph에 둘 때)<인스턴스 ID>_disk
backupsCinder backup (Ceph 백업 드라이버)volume-<ID>.backup.… 형태
CephFS 풀Manila (13편)—

이름 형식은 버전에 따라 조금 다를 수 있지만 “OpenStack ID가 Ceph 이름에 들어간다”는 원칙은 같습니다. 이 덕분에 문제가 생기면 볼륨 ID로 Ceph에서 바로 찾을 수 있습니다.

# Ceph 관리자가 하는 준비 (개념 예)
for p in vms volumes backups images; do
  ceph osd pool create $p
  rbd pool init $p
done
ceph auth get-or-create client.openstack \
  mon 'profile rbd' \
  osd 'profile rbd pool=vms, profile rbd pool=volumes, profile rbd pool=backups, profile rbd pool=images' \
  -o /etc/ceph/ceph.client.openstack.keyring
ceph fsid            # → rbd_secret_uuid 에 쓸 값

사용자 하나 vs 여럿

RHOSO 문서 예시는 client.openstack 하나로 네 풀을 모두 접근합니다. 단순하고 관리가 쉽습니다. 보안 요구가 높다면 서비스별 사용자(예: Glance는 images만)로 권한을 쪼갤 수 있지만, Secret·설정이 그만큼 늘어나므로 운영 부담과 맞바꾸는 선택입니다.

섹션 6

컨트롤 플레인에 Ceph 연결: Secret + extraMounts

① Secret 만들기

# Ceph 관리자에게서 받은 두 파일로
oc create secret generic ceph-conf-files -n openstack \
   --from-file=ceph.conf \
   --from-file=ceph.client.openstack.keyring

② extraMounts로 필요한 서비스에 나눠 주기

OpenStackControlPlane의 최상위 extraMounts에 어떤 서비스에(propagation), 어떤 파일을(volumes), 어디에(mounts) 넣을지 적습니다. 그러면 지정한 서비스 Pod에 /etc/ceph로 두 파일이 들어갑니다.

spec:
  extraMounts:
  - name: v1
    region: r1
    extraVol:
    - propagation: [CinderVolume, CinderBackup, GlanceAPI, ManilaShare]  # Ceph가 필요한 서비스
      extraVolType: Ceph
      volumes:
      - name: ceph
        secret: { secretName: ceph-conf-files }
      mounts:
      - name: ceph
        mountPath: /etc/ceph
        readOnly: true

③ 서비스별 설정

서비스핵심 설정 (customServiceConfig)
Cinder volumevolume_driver = cinder.volume.drivers.rbd.RBDDriver, rbd_ceph_conf = /etc/ceph/ceph.conf, rbd_user = openstack, rbd_pool = volumes, rbd_secret_uuid = <FSID>, rbd_flatten_volume_from_snapshot = False
Cinder backupbackup_driver = cinder.backup.drivers.ceph.CephBackupDriver, backup_ceph_conf, backup_ceph_user = openstack, backup_ceph_pool = backups
Glanceenabled_backends = default_backend:rbd, rbd_store_ceph_conf, rbd_store_user = openstack, rbd_store_pool = images (6편)

rbd_secret_uuid는 왜 FSID인가

Cinder는 볼륨 접속 정보에 “이 Ceph 키를 쓰라”는 표시로 rbd_secret_uuid를 넣어 Nova에 넘깁니다. 컴퓨트 노드의 libvirt는 그 UUID 이름으로 등록된 비밀(키)을 찾아 QEMU가 Ceph에 접속하게 합니다. RHOSO는 이 UUID로 Ceph 클러스터의 FSID를 쓰도록 문서화되어 있어, Cinder 설정과 Nova(데이터 플레인) 설정의 값이 반드시 같아야 합니다. 값이 다르면 볼륨 연결이 “secret not found” 류 오류로 실패합니다.

섹션 7

데이터 플레인(Nova)에 Ceph 연결

컴퓨트 노드는 OCP Pod가 아니므로 extraMounts 대신 NodeSet의 extraMounts와 사용자 정의 데이터 플레인 서비스를 씁니다(3편, 20편).

순서할 일왜
1ConfigMap에 Nova 추가 설정 파일(예: 03-ceph-nova.conf) 작성VM 임시 디스크를 Ceph vms 풀에 두고, rbd 사용자·FSID를 알려 줌
2그 ConfigMap과 ceph-conf-files Secret을 쓰는 OpenStackDataPlaneService(예: nova-custom-ceph) 생성기본 nova 단계 대신, Ceph 설정을 포함한 nova 단계를 실행하기 위해
3NodeSet의 nodeTemplate.extraMounts에 ceph-conf-files를 /etc/ceph로 추가컴퓨트 노드에 ceph.conf·keyring 배포 (libvirt 비밀 등록에 사용)
4NodeSet의 services 목록에서 nova를 nova-custom-ceph로 교체새 서비스가 실행되도록
5새 OpenStackDataPlaneDeployment 생성설정을 실제로 노드에 적용 (3편 원칙)
 
# 1) ConfigMap (RHOSO 문서 예를 단순화)
apiVersion: v1
kind: ConfigMap
metadata: { name: ceph-nova, namespace: openstack }
data:
  03-ceph-nova.conf: |
    [libvirt]
    images_type = rbd
    images_rbd_pool = vms
    images_rbd_ceph_conf = /etc/ceph/ceph.conf
    images_rbd_glance_store_name = default_backend
    rbd_user = openstack
    rbd_secret_uuid = <FSID>
---
# 2) 사용자 정의 데이터 플레인 서비스
apiVersion: dataplane.openstack.org/v1beta1
kind: OpenStackDataPlaneService
metadata: { name: nova-custom-ceph, namespace: openstack }
spec:
  dataSources:
  - configMapRef: { name: ceph-nova }
  - secretRef: { name: nova-cell1-compute-config }   # 기본 nova 서비스가 쓰던 설정도 함께
  - secretRef: { name: nova-migration-ssh-key }     # 라이브 마이그레이션용 SSH 키
  # … 나머지 항목은 기본 nova 서비스를 복사해 시작 (oc get openstackdataplaneservice nova -n openstack -o yaml)
---
# 3·4) NodeSet 수정 부분
nodeTemplate:
  extraMounts:
  - extraVolType: Ceph
    volumes: [ { name: ceph, secret: { secretName: ceph-conf-files } } ]
    mounts:  [ { name: ceph, mountPath: /etc/ceph, readOnly: true } ]
services: [ …, libvirt, nova-custom-ceph, … ]   # 기존 nova 자리

학습용으로 단순화했습니다. 기본 nova 서비스의 내용(플레이북, 기본 dataSources 등)을 복사해 시작하는 것이 안전하며, 정확한 항목은 설치 버전 문서를 따르세요. 컴퓨트 노드에 Ceph를 함께 올린 HCI라면 Nova가 쓸 메모리 예약 같은 설정이 추가됩니다(섹션 9).

Nova가 Ceph를 쓰지 않아도 되는 경우

VM을 모두 부팅 볼륨(Cinder)으로 만든다면 Nova 임시 디스크 설정(images_type = rbd)은 필요 없습니다. 하지만 Cinder RBD 볼륨을 VM에 연결하려면 컴퓨트 노드에 ceph.conf·keyring과 libvirt 비밀이 여전히 필요합니다. 즉 Ceph를 쓰는 환경이라면 데이터 플레인 쪽 Ceph 접속 배포는 사실상 항상 필요합니다.

섹션 9

  
외부 Ceph와 HCI

  
RHOSO 18.0은 외부 Red Hat Ceph Storage 7, 8, 9 배포를 지원합니다(문서 예시는 7 기준). Ceph를 어디에 두느냐에 따라 두 가지 형태가 있습니다.

  

    
형태구성장점주의

    
      
외부 Ceph별도 서버에 Ceph 클러스터, RHOSO는 클라이언트로 연결스토리지와 컴퓨팅을 독립적으로 확장·점검. 장애 영향 분리서버 수 증가. 스토리지 팀과 운영 경계 정의 필요

      
HCI컴퓨트(데이터 플레인) 노드에 Ceph OSD를 함께 배치서버 수 절감. 엣지·소규모에 유리VM과 OSD가 CPU·메모리를 나눠 씀 → Nova에 자원 예약 설정 필요. 노드 점검 시 VM과 스토리지가 함께 영향

    
  

  
HCI 배포는 일반 데이터 플레인 배포보다 단계가 많습니다. 개념적으로는 ① Ceph 없이 노드 기본 구성(네트워크·OS)을 먼저 배포 → ② 그 노드들에 cephadm으로 Ceph 설치 → ③ Ceph 접속 정보를 Secret으로 만들고 Ceph를 쓰는 서비스까지 포함해 다시 배포하는 순서입니다. 세부 절차는 RHOSO의 HCI 배포 문서를 따릅니다.

  

    
여러 Ceph 클러스터 (DCN·엣지)

    
사이트마다 Ceph를 두는 분산 구성에서는 Secret을 사이트별로 만들고(ceph-conf-files-az1 …), Cinder 백엔드마다 rbd_cluster_name·backend_availability_zone을, Glance는 사이트별 glanceAPI와 다중 저장소를 둡니다(6편). 볼륨과 VM이 같은 사이트의 Ceph를 쓰도록 가용 영역을 맞추는 것이 핵심입니다(29편).

  







  
섹션 10

  
NFS 백엔드

  
NFS 백엔드는 NFS 공유 폴더 안에 볼륨마다 파일 하나를 만들어 블록 장치처럼 씁니다. OCP 노드는 추가 준비 없이 NFS에 접속할 수 있습니다(7편 표).

  
# ① 접속 정보는 Secret으로 (비밀이 아니어도 설정을 Secret에 두는 RHOSO 관례)
cat > cinder-nfs.conf <<EOF
[nfs]
nas_host = 192.168.130.1
nas_share_path = /var/nfs/cinder
EOF
oc create secret generic cinder-nfs-config -n openstack --from-file=cinder-nfs.conf

# ② OpenStackControlPlane의 cinderVolumes에 NFS 백엔드 추가
cinderVolumes:
  nfs:
    networkAttachments: [storage]
    replicas: 1
    customServiceConfigSecrets: [cinder-nfs-config]
    customServiceConfig: |
      [DEFAULT]
      enabled_backends = nfs
      [nfs]
      volume_backend_name = nfs
      volume_driver = cinder.volume.drivers.nfs.NfsDriver
      nfs_snapshot_support = true
      nas_secure_file_operations = false
      nas_secure_file_permissions = false

  

    
항목Ceph RBD범용 NFS

    
      
이미지·스냅샷에서 볼륨복사 없는 복제(빠름)파일 복사(크기에 비례해 느림)

      
스냅샷기본 지원nfs_snapshot_support로 켜야 함, 제약 있음

      
용량·성능 확장OSD 추가로 수평 확장NFS 서버 하나의 한계에 묶임

      
가용성자체 복제·자기 치유NFS 서버·공유 스토리지의 가용성에 의존

      
잘 맞는 곳운영 환경 표준랩·소규모·기존 NAS 활용. 운영에는 NAS 벤더 전용 드라이버 검토

    
  

  

    
NFS 권한 옵션의 의미

    
nas_secure_file_operations·nas_secure_file_permissions는 볼륨 파일을 root가 아닌 사용자로 다루고 권한을 좁히는 보안 옵션입니다. 컨테이너 환경과 NFS 서버의 권한 설정(root squash 등)이 맞지 않으면 볼륨 생성이 실패하므로 예시처럼 끄는 경우가 많습니다. NFS 서버 쪽 내보내기(export) 권한을 storage 망으로 좁혀 보완하세요. Glance가 NFS를 쓴다면 glanceAPI는 single 레이아웃이어야 한다는 점도 기억하세요(6편).

섹션 14

  
“볼륨이 error 상태” 복구

  
복구의 네 가지 원칙

  
    
    
  1. 실제 상태를 먼저 본다: Cinder DB의 상태는 기록일 뿐입니다. 백엔드(Ceph에 이미지가 있나, 누가 쓰고 있나)와 컴퓨트 노드(VM에 디스크가 붙어 있나)를 먼저 확인합니다.
    2. 
    
  2. 데이터가 먼저다: 상태를 고치기 전에, 고객 데이터가 있는 볼륨이라면 Ceph에서 스냅샷이나 복사본을 먼저 떠 둡니다.
    3. 
    
  3. 기록을 맞춘다: 실제 상태를 확인한 뒤에 DB 기록을 그것과 같게 맞춥니다(상태 재설정). 그 반대는 안 됩니다.
    4. 
    
  4. 원인을 남긴다: 왜 그 상태가 됐는지(서비스 재시작, 망 단절, 백엔드 오류) 로그로 확인해 재발을 막습니다.
    5. 
  

  

    

    

    

  

  
복구에 쓰는 명령 모음

  
# 실제 상태 확인
openstack volume show <ID> -c status -c attachments -c os-vol-host-attr:host
openstack --os-volume-api-version 3.27 volume attachment list --volume-id <ID>
openstack server show <VM> -c volumes_attached
rbd info volumes/volume-<ID> ; rbd status volumes/volume-<ID> ; rbd snap ls volumes/volume-<ID>

# 기록 맞추기 (관리자, 실제 상태 확인 후에만)
openstack volume set --state available --detached <ID>          # 정말로 아무 VM에도 붙어 있지 않을 때
openstack volume set --state error <ID>                         # 지우기 전에 멈춘 상태를 정리할 때
openstack --os-volume-api-version 3.27 volume attachment delete <어태치먼트 ID>
openstack volume snapshot set --state available <스냅샷 ID>
openstack volume delete --force <ID>                            # 상태와 무관하게 삭제 시도 (마지막 수단)

# Nova 쪽 연결 기록 점검 (Nova 셀 conductor 등 nova-manage 실행 가능한 Pod에서)
nova-manage volume_attachment show <인스턴스 ID> <볼륨 ID>
nova-manage volume_attachment refresh <인스턴스 ID> <볼륨 ID> <커넥터 파일>

  

    
절대 하지 말 것

    
실제로 VM에 붙어 있는 볼륨을 available로 바꾸고 다른 VM에 붙이는 것, 그리고 Ceph에서 rbd rm으로 이미지를 직접 지우는 것입니다. 앞의 것은 두 VM이 같은 디스크에 써서 데이터가 깨지고, 뒤의 것은 Cinder 기록과 실제가 영원히 어긋나는 고아(orphan)를 만듭니다. Ceph 쪽 정리는 Cinder 기록을 정리한 뒤, 반드시 볼륨 ID로 대조해서 합니다.

정리와 다음 편

  
오늘의 핵심 여덟 문장

  
    
    
  • Ceph는 MON(지도)·MGR(관리)·OSD(디스크)로 이뤄지고, RBD 이미지는 4MB 객체로 나뉘어 PG → CRUSH → OSD 3개에 놓인다.
    • 
    
  • size 3 / min_size 2: 서버 하나 고장은 버티지만, 사본이 1개 남은 PG는 쓰기를 멈춘다.
    • 
    
  • OpenStack용 풀은 images · volumes · vms · backups, 사용자는 client.openstack, 필요한 파일은 ceph.conf + keyring.
    • 
    
  • 컨트롤 플레인은 ceph-conf-files Secret + 최상위 extraMounts(propagation)로 Cinder volume·backup, Glance, Manila에 연결한다.
    • 
    
  • 데이터 플레인은 ConfigMap + 사용자 정의 nova 서비스 + NodeSet extraMounts로 연결하고, 새 Deployment로 적용한다.
    • 
    
  • rbd_secret_uuid는 Ceph FSID이며 Cinder와 Nova 설정에서 같아야 한다.
    • 
    
  • NFS는 단순하지만 복제·확장·스냅샷에 제약이 있고, 멀티 백엔드는 백엔드별 Pod + 등급 이름의 볼륨 타입으로 운영한다.
    • 
    
  • error 복구는 실제 상태 확인 → 데이터 보호 → 기록 맞추기 → 원인 기록. Ceph에서 직접 지우지 않는다.
