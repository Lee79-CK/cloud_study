Chapter 01

성능 테스트 기본기

도구를 배우기 전에 용어부터 잡아야 합니다. 성능 테스트에서 나오는 숫자를 잘못 읽으면, 테스트를 아무리 열심히 해도 "우리 서버 괜찮은데요?" 라는 틀린 결론에 도달합니다.

왜 성능 테스트를 하는가

기능 테스트는 "동작하는가?"를 묻습니다. 성능 테스트는 "동시에 몰려와도 동작하는가?"를 묻습니다. 개발 PC에서 0.1초에 끝나던 API가, 사용자 500명이 동시에 호출하면 8초가 되고 타임아웃이 납니다. 이 지점을 배포 전에 찾아내는 것이 목적입니다.

  • 용량 산정(Capacity Planning) — 이 서비스에 Pod 몇 개, CPU 몇 코어가 필요한가?
  • 병목 발견(Bottleneck) — 느린 원인이 WAS인가, DB인가, 네트워크인가?
  • 회귀 방지(Regression) — 지난 배포 대비 응답 시간이 나빠지지 않았는가?
  • SLO 검증 — "p95 응답 300ms 이내, 오류율 0.1% 미만" 같은 목표를 실제로 지키는가?
  • 한계점 확인 — 언제 죽는가, 그리고 죽은 뒤 스스로 회복하는가?

반드시 알아야 할 핵심 지표

지표의미초보가 흔히 하는 오해

Concurrency같은 시점에 처리 중인 요청(가상 사용자) 수."동시 사용자 1,000명" = "가입자 1,000명"이 아닙니다. 훨씬 적은 수입니다.
Little's Law — 딱 하나만 외운다면 이것

동시 사용자 수(N) = 처리량(TPS) × 응답 시간(초)

목표가 "TPS 200, 응답 0.5초"라면 필요한 가상 사용자는 200 × 0.5 = 100명입니다. 거꾸로, 가상 사용자 100명으로 테스트했더니 응답이 2초라면 실제 TPS는 100 ÷ 2 = 50밖에 안 나온 겁니다. 이 식 하나로 "몇 명으로 테스트해야 하나요?"라는 질문의 90%가 해결됩니다.

테스트 유형 6가지

TYPE 01
Smoke Test

사용자 1~5명, 1~2분. 스크립트가 제대로 동작하는지 확인하는 리허설. 모든 부하 테스트 전에 필수.

TYPE 02
Load Test

예상 피크 부하를 그대로 재현. "평소 최대치를 SLO 안에서 버티는가"를 검증. 가장 기본.

TYPE 03
Stress Test

부하를 계속 올려 한계점(knee point)을 찾음. 언제, 어디가, 어떻게 깨지는지 관찰.

TYPE 04
Spike Test

순간적으로 10배 부하. 티켓 오픈, 이벤트 시작 상황. Auto Scaling이 제때 뜨는지 확인.

TYPE 05
Soak / Endurance

중간 부하를 4~24시간 유지. 메모리 누수, 커넥션 풀 고갈, 로그 디스크 폭발을 잡아냄.

TYPE 06
Scalability Test

Pod/노드를 2배로 늘리면 TPS도 2배가 되는지. 수평 확장이 실제로 통하는지 검증.

순서를 지키세요

Smoke → Load → Stress → Spike/Soak. Smoke 없이 바로 1,000명을 때리면 "서버가 죽었다"가 아니라 "내 스크립트가 틀렸다"인 경우가 대부분입니다. 로그인 실패로 전 요청이 401을 받으면서 TPS 3,000이 나오는, 아주 흔한 참사가 여기서 나옵니다.

Chapter 02

JMeter란 무엇인가

Apache JMeter는 Apache 소프트웨어 재단이 관리하는 100% Java로 만든 오픈소스 부하 테스트 도구입니다. 1998년 Apache JServ의 성능 측정용으로 시작해 20년 넘게 발전했고, 라이선스는 Apache License 2.0 — 상업적 사용도 완전 무료입니다.

한 문장 정의

Definition

JMeter는 수많은 가상 사용자(Thread)를 만들어 서버에 요청을 반복적으로 보내고, 그 응답 시간과 성공/실패를 기록해 통계로 보여주는 프로그램입니다.

동작 방식 — "브라우저가 아니다"

초보자가 가장 많이 혼동하는 지점입니다. JMeter는 브라우저가 아니라 HTTP 요청을 직접 조립해서 보내는 프로토콜 레벨 클라이언트입니다.

  • HTML을 렌더링하지 않습니다
  • JavaScript를 실행하지 않습니다 (SPA의 fetch 호출이 자동으로 일어나지 않음)
  • CSS·이미지를 자동으로 받아오지 않습니다 (옵션으로 켤 수는 있음)

즉 JMeter가 측정하는 것은 서버가 응답을 만들어 보내주는 시간이고, 사용자가 화면에서 체감하는 시간(렌더링 포함)은 아닙니다. 화면 체감 성능은 Lighthouse·WebPageTest 같은 프론트엔드 도구의 영역입니다. 이건 단점이 아니라 설계 의도입니다 — 브라우저를 안 띄우기 때문에 PC 한 대로 수천 명을 흉내낼 수 있습니다.

JMeter (Thread 100개)──▶ HTTP Request 조립──▶ 네트워크──▶ L4 / Ingress──▶ WAS──▶ DB

지원 프로토콜 — JMeter의 최대 무기

대부분의 최신 도구가 HTTP만 지원하는 데 비해, JMeter는 범위가 압도적으로 넓습니다.

분류지원 대상
WebHTTP, HTTPS (HTTP/1.1, HTTP/2는 플러그인), REST, SOAP, GraphQL(HTTP Body로)
DatabaseJDBC — Oracle, MySQL, PostgreSQL, MSSQL 등 드라이버만 넣으면 SQL 부하 테스트 가능
MessagingJMS (Queue/Topic), MQTT·Kafka는 플러그인
MailSMTP, POP3, IMAP
NetworkTCP Sampler(원시 소켓), FTP, LDAP
기타Java 클래스 직접 호출, OS 프로세스 실행, gRPC·WebSocket(플러그인)
현장 포인트

"API 부하 테스트"만 필요하면 k6가 더 편할 수 있습니다. 하지만 "DB에 직접 쿼리 부하를 걸고, 동시에 Kafka에 메시지를 밀어넣고, 레거시 TCP 서버도 두드려야 한다"면 한 도구로 다 되는 건 실질적으로 JMeter뿐입니다. 엔터프라이즈에서 아직 JMeter가 표준인 이유입니다.

GUI와 CLI, 두 개의 얼굴

GUI MODE
시나리오를 만드는 곳

마우스로 요소를 추가하며 테스트를 설계하고, 소규모로 디버깅합니다. 결과물은 .jmx라는 XML 파일입니다. 실제 부하 테스트에는 절대 쓰지 않습니다.

NON-GUI (CLI)
실제로 부하를 주는 곳

jmeter -n -t plan.jmx 형태로 터미널에서 실행. GUI 렌더링에 CPU를 안 쓰므로 같은 장비로 몇 배 많은 부하를 낼 수 있습니다. CI/CD도 이 방식.

가장 흔한 초보 실수 1위

GUI 창을 띄운 채로 스레드 500개를 돌리는 것. 이때 측정되는 응답 시간 폭증은 서버가 느린 게 아니라 JMeter GUI가 화면 갱신에 CPU를 다 쓰고 있어서 생깁니다. "GUI는 설계용, CLI는 실행용" — 이 문장은 JMeter 시작 화면에도 경고로 뜹니다.

3단계 — 힙 메모리 조정

JMeter 기본 힙은 1GB입니다. 스레드를 수백 개 돌리거나 응답 본문이 큰 경우 OutOfMemoryError가 납니다. 실행 스크립트에서 조정합니다. 

# bin/jmeter 파일에서 이 줄을 수정
: "${HEAP:="-Xms1g -Xmx1g -XX:MaxMetaspaceSize=256m"}"

# 예: 4GB로 늘리기 (물리 메모리의 절반 이내 권장)
: "${HEAP:="-Xms4g -Xmx4g -XX:MaxMetaspaceSize=512m"}"
:: bin\jmeter.bat 에서
set HEAP=-Xms1g -Xmx1g -XX:MaxMetaspaceSize=256m

:: 수정 후
set HEAP=-Xms4g -Xmx4g -XX:MaxMetaspaceSize=512m
# 파일을 수정하지 않고 실행할 때만 적용
HEAP="-Xms2g -Xmx4g" jmeter -n -t plan.jmx -l r.jtl

# Docker에서
docker run --rm -e HEAP="-Xms2g -Xmx4g" \
  -v $PWD:/test justb4/jmeter -n -t /test/plan.jmx -l /test/r.jtl

실행 순서 — 헷갈리면 여기를 보세요

하나의 Sampler가 실행될 때, 주변 요소들은 정해진 순서로 개입합니다.

Config Element▶ Pre-Processor▶ Timer▶ Sampler▶ Post-Processor▶ Assertion▶ Listener
Timer는 Sampler보다 먼저 실행됩니다

"요청 후 1초 쉬기"를 의도하고 Timer를 Sampler 아래에 뒀는데, 실제로는 그 Sampler가 실행되기 전에 1초를 기다립니다. Timer는 "다음 요청 전 대기"로 이해하세요. 그리고 Timer는 Scope 안의 모든 Sampler에 적용되므로, Thread Group 바로 아래 Timer 하나를 두면 모든 요청마다 대기가 붙습니다.

Scope 규칙 (딱 두 줄)

  • Config/Timer/Assertion/Processor를 Sampler의 자식으로 붙이면 → 그 Sampler에만 적용
  • Thread Group이나 Controller의 자식으로(형제 레벨에) 두면 → 그 아래 모든 Sampler에 적용
Thread Group을 여러 개 두면?

기본값은 모든 Thread Group이 동시에 병렬 실행됩니다. "로그인 그룹 다음에 주문 그룹"처럼 순차 실행하려면 Test Plan 화면의 Run Thread Groups consecutively를 체크하세요. 실무에서는 "조회 사용자 70%, 주문 사용자 30%" 같은 사용자 유형별 혼합 부하를 여러 Thread Group으로 표현합니다.

부하 곡선의 3단 해석

부하를 점점 올리며 관찰할 때 나타나는 전형적인 3구간입니다. 이 패턴을 알면 결과 해석이 쉬워집니다.

ZONE 1
선형 구간

부하↑ → TPS↑, 응답시간은 거의 평평. 서버가 여유로운 상태. 안전 운영 구간.

ZONE 2
포화점 (Knee)

부하↑ → TPS는 정체, 응답시간만 급격히 증가. 이 지점이 최대 처리 용량입니다.

ZONE 3
붕괴 구간

부하↑ → TPS 하락 + 오류 폭증. 큐 적체, 타임아웃, 스레드 고갈. 여기까지 가면 안 됩니다.

보고서에 쓸 결론 문장 템플릿

"현재 구성(Pod 3, 2vCPU)에서 최대 처리량은 약 420 TPS이며, 이때 p95 응답은 780ms, 오류율 0.02%입니다. SLO(p95 < 500ms) 기준으로는 310 TPS가 안전 한계이고, 포화 시점에 병목은 DB 커넥션 풀(최대 20)이었습니다."

숫자 + 조건 + 병목 지점. 이 세 가지가 들어가야 완성된 성능 보고입니다.

직접 확인해 볼 것
  • Ramp-up을 늘려보세요 — 곡선이 완만해지고, 정상 부하 구간(steady state)이 짧아집니다. Ramp-up이 너무 길면 "제대로 부하가 걸린 시간"이 거의 없어집니다.
  • 응답 시간을 3000ms로 올려보세요 — 스레드 수는 그대로인데 TPS가 급락합니다. 느린 API는 같은 스레드로 훨씬 적은 부하만 낼 수 있다는 뜻입니다.
  • 목표 TPS 500을 만들어 보세요 — 응답 200ms라면 스레드 100개가 필요합니다(Little's Law). 스레드를 무작정 늘리는 게 아니라 계산해서 정하는 것입니다.

스레드 수로 TPS를 조절하는 건 간접적입니다. 직접 제어하려면 Timer를 씁니다.

  • Constant Throughput Timer — 분당 목표 샘플 수 지정 (예: 초당 100건 = 6000/min). 단순하지만 정밀도가 낮습니다.

  • All threads — 모든 스레드가 한 줄씩 순서대로 나눠 가짐. 계정 중복 없이 쓰려면 이것.
  • Current thread group — Thread Group 단위로 분리
  • Current thread — 스레드마다 파일을 처음부터 읽음 → 모든 스레드가 user001로 로그인하게 됩니다. 의도한 게 아니라면 함정.

또 하나: 스레드 100개인데 CSV에 계정이 10개면, Recycle=True여도 같은 계정 10명이 동시 로그인합니다. 서버가 중복 세션을 거부하면 오류가 쏟아집니다. 계정 수 ≥ 스레드 수가 안전합니다.

# scripts/check_slo.py — .jtl 을 읽어 SLO 위반 시 파이프라인 실패
import csv, sys, statistics

SLO_P95_MS  = 500
SLO_ERR_PCT = 1.0

elapsed, fails, total = [], 0, 0
with open(sys.argv[1], newline='') as f:
    for row in csv.DictReader(f):
        total += 1
        elapsed.append(int(row['elapsed']))
        if row['success'] != 'true': fails += 1

elapsed.sort()
p95 = elapsed[int(len(elapsed) * 0.95) - 1]
err = fails / total * 100

print(f"total={total} p95={p95}ms error={err:.2f}%")

if p95 > SLO_P95_MS or err > SLO_ERR_PCT:
    print("::error:: SLO VIOLATED"); sys.exit(1)
print("SLO OK")

스트리밍 토큰 단위 지표(TTFT, ITL, TPOT)를 정밀하게 측정하는 것은 JMeter의 강점이 아닙니다. 이 영역에는 전용 도구가 훨씬 낫습니다:

  • vLLM benchmark_serving.py — vLLM 공식 벤치마크. TTFT/TPOT/throughput을 표준 방식으로 산출
  • GuideLLM, LLMPerf — LLM 서빙 전용 부하 도구

JMeter가 유리한 경우는 "LLM 호출이 전체 업무 흐름의 일부인 시나리오"입니다. 로그인 → DB 조회 → 문서 검색(Qdrant) → LLM 호출 → 결과 저장 같은 End-to-End RAG 파이프라인 전체를 한 스크립트로 묶어 측정하려면 JMeter가 여전히 최선입니다.

import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },   // ramp-up
    { duration: '3m',  target: 50 },   // steady
    { duration: '30s', target: 0 },    // ramp-down
  ],
  thresholds: {                        // SLO를 코드에 명시 → 위반 시 종료 코드 1
    http_req_duration: ['p(95)<500'],
    http_req_failed:   ['rate<0.01'],
  },
};

export default function () {
  const res = http.post(
    'https://api.example.com/orders',
    JSON.stringify({ item: 'A1', qty: 2 }),
    { headers: { 'Content-Type': 'application/json' } }
  );
  check(res, {
    'status is 201': (r) => r.status === 201,
    'has orderId':  (r) => r.json('orderId') !== undefined,
  });
  sleep(1);
}

Locust — Python 팀에게 가장 자연스러운 선택

시나리오가 그냥 Python 클래스입니다. 데이터 엔지니어·ML 엔지니어가 많은 조직에서는 학습 비용이 사실상 0입니다. Web UI로 실행 중 사용자 수를 실시간 조절할 수 있고, master/worker 분산이 매우 간단합니다. 대신 GIL 때문에 프로세스를 여러 개 띄워야 하고, 리포트가 상대적으로 빈약합니다. 

from locust import HttpUser, task, between

class OrderUser(HttpUser):
    wait_time = between(1, 3)          # 생각 시간

    def on_start(self):               # 각 가상 사용자 시작 시 1회
        r = self.client.post("/login",
              json={"username": "user1", "password": "pw"})
        self.token = r.json()["accessToken"]

    @task(3)                            # 가중치 3 (조회가 3배 많음)
    def list_orders(self):
        self.client.get("/orders",
              headers={"Authorization": f"Bearer {self.token}"})

    @task(1)
    def create_order(self):
        self.client.post("/orders", json={"item": "A1"},
              headers={"Authorization": f"Bearer {self.token}"})

# 실행: locust -f loadtest.py --host https://api.example.com
#       분산:  locust -f loadtest.py --master
#              locust -f loadtest.py --worker --master-host=10.0.1.5

nGrinder — 국내 환경에서의 실용적 선택

NAVER가 개발한 오픈소스로, 웹 콘솔에서 여러 사람이 테스트를 관리하는 구조입니다. Controller-Agent 분산이 기본 내장이고, 테스트 이력·리포트가 서버에 축적됩니다. 국내 자료와 커뮤니티가 풍부해 사내 공용 성능 테스트 플랫폼을 구축할 때 후보로 자주 오릅니다. 다만 최신 프로토콜 지원이나 업데이트 속도는 JMeter·k6에 비해 느립니다.

wrk / vegeta / oha — 5초 만에 답이 필요할 때

시나리오가 없습니다. 단일 URL을 최대 속도로 두드려 처리량 상한만 봅니다. "이 엔드포인트 최대 TPS가 얼마인지 지금 당장 알고 싶다"면 이게 가장 빠릅니다. 복잡한 시나리오나 로그인 흐름은 불가능하므로 정식 성능 테스트를 대체할 수는 없습니다. 

# wrk — 스레드 4개, 커넥션 100개, 30초
wrk -t4 -c100 -d30s --latency https://api.example.com/health

# vegeta — 초당 500 요청을 30초간 고정 발사 (rate 기반이라 더 정확)
echo "GET https://api.example.com/health" \
  | vegeta attack -rate=500 -duration=30s \
  | vegeta report -type=text

# oha — 진행 상황을 TUI로 보여주는 현대적 도구
oha -z 30s -c 100 https://api.example.com/health

# hey — Go로 만든 간단한 도구
hey -z 30s -c 100 -m GET https://api.example.com/health

장점

PRO 01

Apache License 2.0. 사용자 수 제한도, 라이선스 갱신도 없습니다. 상용 도구는 가상 사용자 수에 따라 비용이 급증합니다.

HTTP뿐 아니라 JDBC, JMS, SMTP, LDAP, TCP까지. 이종 시스템이 섞인 엔터프라이즈에서 대체재를 찾기 어렵습니다.

PRO 03
GUI 덕분에 진입 장벽이 낮음

프로그래밍 없이 클릭으로 시나리오를 만들 수 있습니다. QA 엔지니어, 인프라 담당자도 바로 시작할 수 있습니다.

PRO 04
가장 성숙한 생태계

25년 이상의 역사. 플러그인 수백 개, 한글 자료 다수, StackOverflow 답변 풍부. 막혔을 때 검색하면 대체로 답이 나옵니다.

PRO 05
플랫폼 독립 · 통합 용이

Java만 있으면 Windows·Linux·macOS·컨테이너 어디서든 동일하게 동작. Jenkins·GitLab·Maven 플러그인이 모두 존재합니다.

PRO 06
즉시 쓸 수 있는 리포트

CLI 옵션 하나로 APDEX·백분위·시간대별 그래프가 포함된 HTML 대시보드가 나옵니다. 그대로 보고서로 제출 가능합니다.

단점

CON 01
스레드 1:1 모델의 자원 소모

가상 사용자 1명 = OS 스레드 1개. 수천 명을 만들려면 힙 튜닝과 여러 대의 발생기가 필요합니다. k6·Gatling의 비동기 모델보다 같은 장비에서 낼 수 있는 부하가 적습니다.

CON 02
XML(.jmx) — 코드 리뷰가 어렵다

파라미터 하나만 바꿔도 diff가 수십 줄. Git 병합 충돌 해결이 매우 고통스럽습니다. GUI로 만든 스크립트는 사실상 리뷰 불가입니다.

CON 03
GUI가 유혹이자 함정

편해서 GUI로 부하를 주게 되고, 그러면 측정값이 왜곡됩니다. "GUI는 설계용"이라는 규율을 팀 전체가 지켜야 합니다.

CON 04
JavaScript 미실행

SPA가 렌더링 후 호출하는 API는 자동으로 발생하지 않습니다. 개발자도구로 실제 호출을 직접 확인해 스크립트에 넣어야 합니다.

CON 05
UI/UX가 낡았다

Swing 기반 인터페이스. 요소 이동, 검색, 대량 편집이 불편하고 실수하기 쉽습니다. HiDPI 화면에서 흐릿하게 보이기도 합니다.

CON 06
분산 테스트 구성이 번거롭다

RMI 기반이라 방화벽 포트, SSL 키스토어, 버전 일치를 모두 맞춰야 합니다. 클라우드/쿠버네티스 환경과 잘 맞지 않습니다.

CON 07
실시간 관측이 기본으로 약하다

CLI 실행 중에는 콘솔 요약만 보입니다. 실시간 대시보드가 필요하면 InfluxDB+Grafana를 별도로 구축해야 합니다.

CON 08
잘못 쓰기 쉬운 구조

Assertion 없이, Timer 없이, Listener 켜둔 채로도 "테스트가 성공적으로 끝났다"고 보고됩니다. 틀린 결과가 그럴듯하게 나오는 것이 가장 위험한 단점입니다.

한 줄 결론

JMeter는 "가장 세련된 도구"는 아니지만 "가장 많은 상황을 해결할 수 있는 도구"입니다. 성능 테스트를 처음 배운다면 JMeter로 시작하는 것이 여전히 최선입니다 — 개념(스레드, 램프업, 상관관계, 백분위)이 도구를 바꿔도 그대로 통하기 때문입니다.

테스트 실행 전 체크리스트

  • 테스트 대상 시스템에 대한 서면 승인을 받았다
  • 테스트 환경이 운영 환경과 동등한 스펙이다 (또는 차이를 문서화했다)
  • Smoke 테스트(1~5명)를 먼저 돌려 오류율 0%를 확인했다
  • 모든 주요 요청에 Assertion이 있다
  • 테스트 데이터가 충분히 다양하고 계정 수 ≥ 스레드 수다
  • Listener를 비활성화하고 CLI 모드로 실행한다
  • 대상 서버의 모니터링(APM/메트릭)이 켜져 있다
  • 목표 SLO(예: p95 < 500ms, 오류율 < 0.1%)가 숫자로 정의되어 있다
  • 부하 발생기의 CPU·메모리·포트·FD 여유를 확인했다
  • 테스트 실패 시 중단 기준과 롤백 절차를 정했다

다음 학습 로드맵

1주차 — 손에 익히기

  • 로컬에 nginx 또는 간단한 Spring Boot / FastAPI 앱을 띄운다
  • 사용자 10명 · 반복 10회 테스트를 GUI로 만들고 결과를 읽는다
  • 같은 스크립트를 CLI로 실행하고 HTML 리포트를 생성해 GUI 결과와 비교한다
  • Assertion을 일부러 틀리게 만들어 오류율이 어떻게 잡히는지 확인한다

2주차 — 실전 스크립트

  • 로그인 → 토큰 추출 → 인증 API 호출 흐름을 상관관계로 구현한다
  • CSV Data Set으로 계정 100개를 파라미터화한다
  • Transaction Controller로 비즈니스 단위 리포트를 만든다
  • Plugins Manager로 Concurrency Thread Group을 설치해 목표 동시성 유지형 테스트를 해본다

3주차 — 자동화와 관측

  • ${__P()}로 파라미터를 외부 주입하고 CI 파이프라인에 Smoke 테스트를 등록한다
  • InfluxDB + Grafana를 띄워 Backend Listener로 실시간 대시보드를 붙인다
  • SLO 판정 스크립트를 만들어 임계값 위반 시 빌드가 실패하게 만든다
  • 부하를 올리며 포화점(knee point)을 찾아 보고서를 한 장 작성해 본다

4주차 — 시야 넓히기

  • 같은 시나리오를 k6로 작성해 보고 두 도구의 결과를 비교한다
  • 대상 서버에 APM(Pinpoint, Datadog, OpenTelemetry)을 붙여 병목 지점을 직접 찾아본다
  • Kubernetes 환경에서 Pod 수를 늘려가며 Scalability 테스트를 수행한다
  • Soak 테스트를 4시간 돌려 메모리 누수 여부를 확인한다
마지막으로 — 가장 중요한 것

성능 테스트의 목적은 숫자를 만드는 것이 아니라 병목을 찾아 개선하는 것입니다. "TPS 500 나왔습니다"로 끝나는 보고는 가치가 없습니다. "TPS 500에서 DB 커넥션 풀이 포화되었고, 20 → 50으로 늘려 780까지 올렸습니다" — 이것이 성능 엔지니어링입니다.

JMeter는 그 여정의 측정 도구일 뿐입니다. 도구를 배우되, 시스템을 이해하는 데 시간을 더 쓰세요.
