신호 연결과 장애 조사 실전알림 하나에서 원인까지, 클릭 몇 번으로

10시 35분, 고객사 쇼핑몰의 결제 지연 알림이 울렸습니다. 당신은 당직 MSP 엔지니어입니다. 아래 시뮬레이터에서 다음 행동을 골라 원인을 찾아보세요. 선택마다 시간이 흐르고, 신호를 잘 이어 갈수록 빨리 끝납니다. 시리즈 1편부터 등장한 그 주문 트레이스의 마지막 이야기입니다.

경과 0분

가상의 사례입니다. 화면은 Grafana의 실제 모습을 단순화한 모형이며, 걸리는 시간은 조사 흐름을 비교하기 위한 예시 값입니다.

1

신호를 잇는 네 개의 다리

시뮬레이터에서 빠르게 끝냈다면 신호와 신호 사이를 클릭 한 번으로 건너갔기 때문입니다. 이 다리는 저절로 생기지 않습니다. 모든 다리는 결국 같은 식별자를 양쪽이 공유하는 구조입니다. 그림의 화살표를 눌러 각 다리가 무엇으로 이어지는지 확인해 보세요.

메트릭은 "언제·어디서", 트레이스는 "어느 경로에서", 로그는 "무슨 일이", 프로파일은 "어느 코드가"

1편에서 트레이스를 "메트릭과 로그 사이의 빈칸을 채우는 신호"로 소개했습니다. 7편은 그 빈칸을 양쪽으로 실제로 잇는 작업입니다. 여기에 지속 프로파일링(Pyroscope)을 더하면 느린 스팬 안에서 CPU를 쓴 함수까지 내려갈 수 있습니다.

2

연결은 계측에서 시작된다

Grafana 설정은 다리의 표지판일 뿐이고, 다리 자체는 애플리케이션과 수집 파이프라인이 놓습니다. MSP가 고객사 개발팀에 요청해야 할 항목입니다.

다리필요한 것확인 방법
로그 → 트레이스로그 줄마다 trace_id(와 span_id) 기록. OTel SDK의 로그 브리지나 로깅 라이브러리의 MDC 연동으로 자동 삽입. OTLP로 Loki에 보내면 구조화 메타데이터로 저장됨Loki에서 로그를 펼쳤을 때 trace_id 필드가 보이는지
메트릭 → 트레이스exemplar: 메트릭 데이터 포인트에 대표 trace ID를 붙임. Tempo metrics-generator는 기본 레이블 이름 traceID로 붙여 remote write(send_exemplars: true). Prometheus는 --enable-feature=exemplar-storage 필요Grafana 그래프에 exemplar 점(마름모)이 보이는지
트레이스 → 프로파일Pyroscope span profiles: 앱의 프로파일러가 스팬 ID와 프로파일을 연결하고 스팬에 pyroscope.profile.id 속성을 남김 (언어별 연동 라이브러리 필요)Tempo 트레이스 화면의 스팬에 프로파일 링크가 생기는지
모든 다리의 공통 기반같은 서비스 이름: 트레이스의 service.name과 로그·메트릭·프로파일의 서비스 레이블이 같은 값이어야 함. 레이블 이름이 다르면(service_name, job 등) 데이터 소스 설정에서 대응시킴세 신호에서 같은 서비스를 같은 이름으로 검색해 보기
가장 싸고 효과가 큰 한 가지

하나만 고르라면 로그에 trace_id 넣기입니다. 고객 문의("이 주문이 실패했어요")는 대개 주문 번호로 시작하는데, 주문 번호로 로그를 찾고 그 줄의 trace_id로 트레이스를 여는 동선이 가장 많이 쓰입니다(1편 9장, 3편 트러블슈팅). 대부분의 언어에서 로깅 설정 몇 줄이면 됩니다.

3

Grafana 데이터 소스 설정

Grafana에서 다리는 데이터 소스 설정으로 켭니다. 아래는 6편 실습 환경에 Loki와 Pyroscope를 더했을 때의 프로비저닝 파일입니다. 탭마다 어느 방향의 다리인지 표시했습니다.


    

  

  

    
설정 항목흔한 실수

    
      
tags 대응트레이스의 service.name을 Loki 레이블 service_name으로 대응시키지 않아 로그 검색 결과가 비어 있음

      
시간 창 (spanStartTimeShift, spanEndTimeShift)스팬 시간 그대로 검색하면 로그 수집 지연이나 시계 오차로 로그가 창 밖으로 빠짐. 앞뒤로 몇 분 여유를 둠

      
filterByTraceID켜지 않으면 같은 서비스의 다른 요청 로그까지 섞여 나옴

      
exemplar 레이블 이름Prometheus 데이터 소스의 exemplarTraceIdDestinations.name이 실제 레이블(Tempo 기본 traceID)과 달라 링크가 안 생김

      
멀티테넌시 헤더연결 대상 Tempo 데이터 소스에 X-Scope-OrgID를 넣지 않아 "trace not found". 고객사별 데이터 소스 세트를 같은 테넌트로 맞춰야 함

Jaeger 쪽 연결

  
Jaeger를 쓰는 고객사도 같은 다리를 놓을 수 있습니다. 방법은 두 가지입니다.

  

    
Jaeger UI의 링크 패턴
UI 설정 파일(3편의 ui-config.json)의 linkPatterns로 스팬 속성이나 트레이스 ID를 외부 URL에 끼워 넣은 링크를 만듭니다. 로그가 OpenSearch Dashboards나 Kibana에 있다면 "이 트레이스의 로그 보기" 링크를 트레이스 화면에 달 수 있습니다.

    
Grafana의 Jaeger 데이터 소스
Grafana에 Jaeger를 데이터 소스로 붙이면 Tempo와 같은 방식으로 trace-to-logs, trace-to-metrics 설정을 쓸 수 있습니다. Jaeger를 저장소로 유지하면서 화면만 Grafana로 통일하는 방법입니다(1편 4장, 8편에서 전략으로 다룸).

  


{
  "linkPatterns": [
    {
      "type": "traces",
      "url": "https://dashboards.example.com/app/discover#/?_a=(query:(language:kuery,query:'trace_id:\"#{traceID}\"'))",
      "text": "이 트레이스의 로그 보기 (OpenSearch Dashboards)"
    },
    {
      "type": "tags",
      "key": "k8s.pod.name",
      "url": "https://grafana.example.com/d/pod-overview?var-pod=#{k8s.pod.name}",
      "text": "파드 대시보드 열기"
    }
  ]
}

  

    
다리Tempo + GrafanaJaeger

    
      
트레이스 → 로그tracesToLogsV2 (Loki 등)linkPatterns 또는 Grafana Jaeger 데이터 소스

      
로그 → 트레이스Loki derived fields로그 도구 쪽에서 Jaeger UI URL로 링크 (/trace/<traceID>)

      
메트릭 → 트레이스Prometheus exemplarMonitor 탭(SPM)에서 오퍼레이션 클릭 → 트레이스 검색 (3편 7장)

      
트레이스 → 프로파일tracesToProfiles (Pyroscope)기본 기능 없음. Grafana 경유

      
서비스 관계도service-graphs → Grafana Service GraphSystem Architecture 탭 (ES·OpenSearch는 배치 필요, 3편)

장애 조사 방법론

  
시뮬레이터의 모범 경로를 일반화하면 다섯 단계입니다. 도구가 달라도 순서는 같습니다.

  

    
단계질문쓰는 신호시뮬레이터에서

    
      
1. 범위 정하기언제부터, 어느 서비스, 얼마나 많이?메트릭 (RED, SLO 알림)10:35부터 payment-service p95 급증

      
2. 대표 사례 고르기그 시간대의 전형적인 요청 하나는?exemplar, TraceQL 검색그래프의 exemplar 점 클릭

      
3. 경로에서 위치 찾기시간을 쓴 스팬은 어디인가?트레이스 (Critical Path, 직접 시간)PG 호출 500ms 타임아웃 + 재시도

      
4. 이유 확인하기그 스팬에서 무슨 일이 있었나?로그, 프로파일타임아웃·재시도 로그, CPU는 한가함

      
5. 영향 범위 검증이것이 전체 현상을 설명하는가?TraceQL metrics, 서비스 그래프pg-gateway 구간만 지연, 다른 구간 정상

    
  

  

    
MSP 장애 보고서에 남길 것

    
고객사 보고서에는 결론만이 아니라 근거 링크를 남기세요. 알림 시각과 영향 지표 그래프, 대표 트레이스 ID와 링크, 원인 스팬의 속성(예: server.address, error.type), 관련 로그 줄, 영향 범위를 확인한 TraceQL 쿼리입니다. 트레이스 링크는 보존 기간이 지나면 열리지 않으므로, 중요한 트레이스는 Jaeger의 보관용 저장소(3편)에 보관하거나 JSON으로 내려받아 첨부합니다.

  







  
6
AIOps: MCP로 에이전트에 트레이스 주기

  
MCP(Model Context Protocol)는 LLM 에이전트가 외부 시스템의 기능을 도구(tool)로 호출하게 하는 표준입니다. Tempo와 Jaeger 모두 MCP 서버를 내장하게 되어, 에이전트가 시뮬레이터에서 사람이 한 조사 순서를 도구 호출로 따라 할 수 있습니다. 자체 AIOps 챗봇이나 코딩 에이전트에 붙일 때의 출발점입니다.

  

    
Tempo MCP 서버 (3.0)


query_frontend:
  mcp_server:
    enabled: true
# 주소: http://tempo:3200/api/mcp
# 전송 방식: Streamable HTTP

      
  • traceql-search, get-trace
  • traceql-metrics-instant, traceql-metrics-range
  • get-attribute-names, get-attribute-values
  • docs-traceql, docs-config (문서를 리소스로 제공)

    
Jaeger MCP (v2.21, jaeger_query 내장)


extensions:
  jaeger_query:
    ai:
      mcp: {}
# 주소: http://jaeger:16686/api/ai/mcp/

      
  • get_services, get_span_names, search_traces
  • get_trace_topology, get_span_details
  • get_trace_errors, get_critical_path
  • get_service_dependencies

  

  
Tempo 공식 문서의 빠른 시작은 Claude Code에 claude mcp add --transport=http tempo http://localhost:3200/api/mcp로 연결하는 예를 듭니다. 6편 실습 환경이라면 tempo.yaml에 위 세 줄을 넣고 재시작하면 됩니다. Jaeger MCP 도구 목록은 v2.21 소스 기준이며, 새로 추가된 기능이라 버전마다 달라질 수 있습니다.

  
에이전트에게 맡길 조사 흐름 예시


역할: 당신은 MSP 장애 1차 분석 에이전트입니다. 읽기 도구만 사용합니다.
1. traceql-metrics-range로 최근 1시간 { status = error } | rate() by (resource.service.name)을 조회해
   에러가 급증한 서비스와 시작 시각을 찾는다.
2. traceql-search로 그 서비스·시간대의 에러 트레이스를 최대 5개 찾는다.
3. get-trace로 하나를 열어 소요 시간이 가장 긴 스팬과 그 속성(server.address, error.type)을 정리한다.
4. traceql-metrics-range로 { resource.service.name = "..." } | quantile_over_time(duration, .95) by (span.server.address)
   를 조회해 특정 목적지에만 해당하는지 확인한다.
5. 결과를 "영향 범위 / 추정 원인 / 근거(트레이스 ID·쿼리) / 확인 필요 사항"으로 보고한다. 추측은 추측이라고 표시한다.

  

    
연결하기 전에 반드시 확인할 것

    
MCP 서버는 트레이스 데이터를 에이전트에게, 그리고 그 뒤의 LLM 제공자에게 넘길 수 있습니다. 공식 문서도 이 점을 경고합니다. 고객사 트레이스에 개인정보·토큰이 있을 수 있다면 사내 LLM(로컬 추론 서버 등)을 쓰거나 계약·정책을 먼저 확인하고, 수집 단계에서 민감 정보를 제거하며(3편 10장), 이미 저장된 것은 tempo-cli redact로 지웁니다(6편 7장). Tempo MCP는 일반 API와 같은 인증·멀티테넌시를 따르므로 고객사별 X-Scope-OrgID로 에이전트의 조회 범위를 제한하세요.

  

  

    
LLM용 응답 형식

    
Tempo의 trace by ID v2와 tag values v2 API는 Accept: application/vnd.grafana.llm 헤더를 주면 불필요한 필드를 뺀 단순한 JSON을 돌려줘 토큰 사용량을 줄입니다. 다만 공식 문서는 이 형식이 바뀔 수 있으니 안정적인 연동에는 MCP 서버나 표준 형식을 쓰라고 권합니다.

8편 · Tempo vs Jaeger 선택과 MSP 운영 전략

    
지금까지의 내용을 모아 고객사 조건별로 무엇을 고를지 결정합니다. 비용 구조, 쿼리 모델, 멀티테넌시, 운영 난도를 비교하는 선택 도우미, Jaeger에서 Tempo로(또는 병행) 옮기는 전략, 고객사별 테넌트·비용 배분, 용량 계획, 그리고 트레이스 누락·끊김·느린 조회를 한 번에 점검하는 체크리스트와 종합 실습으로 시리즈를 마무리합니다.
