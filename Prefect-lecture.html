01 문제 정의

왜 cron으로는 부족한가

회사에 들어가면 거의 반드시 이런 스크립트를 만나게 됩니다. 매일 새벽 2시에 API에서 데이터를 받아 정제하고 DB에 넣는 daily_batch.py. 그리고 crontab 한 줄.

# crontab -e
0 2 * * * /usr/bin/python3 /opt/jobs/daily_batch.py >> /var/log/batch.log 2>&1

이 구성은 처음 두 달은 완벽하게 동작합니다. 문제는 그 다음부터입니다.

cron + 스크립트에서 실제로 생기는 일

  • 새벽 2시에 API가 5초 느렸다 → 타임아웃 → 그날 데이터 없음. 아침에 아무도 모름.
  • 실패했는지 알려면 batch.log를 사람이 열어봐야 함.
  • 어제 것만 다시 돌리고 싶은데, 스크립트가 전체를 다시 돈다.
  • "3단계까지는 성공했으니 4단계부터"가 불가능하다.
  • 테이블 12개를 순차 처리해서 4시간 걸린다. 병렬로 바꾸려면 스레드 코드를 직접 쓴다.
  • DB 비밀번호가 스크립트 안에 하드코딩돼 있다.
  • 담당자가 퇴사했고, 이 잡이 몇 개 있는지 아무도 모른다.

오케스트레이터가 대신 해주는 일

  • 실패하면 정해진 간격으로 자동 재시도, 그래도 실패하면 슬랙 알림.
  • 모든 실행 기록이 UI에 남는다. 언제·얼마나·왜 실패했는지 클릭 몇 번.
  • 실패한 실행만 골라 재실행. 성공한 단계는 캐시로 건너뛴다.
  • 태스크 단위 상태 관리라 "어디서 멈췄는지"가 자동으로 보인다.
  • .map() 한 줄로 12개 테이블 병렬 처리.
  • 비밀정보는 Block/Secret으로 분리해 코드에서 사라진다.
  • 어떤 잡이 어떤 일정으로 도는지 한 화면에 모여 있다.

오케스트레이션이라는 단어의 뜻

오케스트라 지휘자를 떠올리면 됩니다. 연주는 각 악기(여러분의 파이썬 코드)가 합니다. 지휘자는 연주를 대신하지 않고, 누가 언제 시작하고, 누가 누구를 기다리고, 실수가 났을 때 어떻게 할지를 관리합니다. Prefect도 여러분의 코드를 대신 쓰지 않습니다. 코드가 어떻게 실행되는지를 관리합니다.

신입이 자주 하는 오해

"Prefect을 쓰면 데이터 처리 코드가 빨라진다"가 아닙니다. pandas 코드는 그대로 pandas 속도로 돕니다. 달라지는 것은 그 코드가 실패했을 때·다시 돌려야 할 때·누가 확인해야 할 때의 운영 비용입니다.

Prefect의 접근 방식이 특이한 점

많은 오케스트레이터는 "먼저 그래프(DAG)를 선언하고, 그 안에 코드를 채워라"고 요구합니다. Prefect은 반대입니다. 평범한 파이썬을 그대로 쓰고, 실행 순서는 함수 호출 순서에서 자동으로 유도합니다. 그래서 if, for, while, 예외 처리 같은 파이썬 문법이 그대로 워크플로 제어 구조가 됩니다.

그래프를 먼저 선언하는 방식

  • 실행할 태스크 목록이 코드 작성 시점에 정해져야 함
  • "파일 개수만큼 태스크 생성" 같은 게 어렵거나 특수 문법 필요
  • 프레임워크 고유 문법을 별도로 배워야 함

Prefect 방식 (동적 워크플로)

  • 런타임에 결정되는 태스크 개수·분기·중첩이 자연스럽다
  • 파이썬을 알면 추가로 배울 문법이 거의 없다
  • 단위 테스트가 그냥 함수 테스트다
02 어휘 익히기

핵심 개념 12가지

Prefect 문서와 동료의 말을 알아듣기 위한 최소 어휘입니다. 지금은 훑어보고, 5장에서 코드로 다시 만나면 자연스럽게 붙습니다.

@flow

워크플로의 진입점. 이 함수가 한 번 호출되면 플로우 실행(flow run) 한 건이 기록됩니다. 스케줄·재시도·알림의 기준 단위.

@task

플로우 안의 작업 단위. 개별 재시도·캐시·병렬 실행·상태 추적을 받습니다. 외부와 통신하거나 실패할 수 있는 부분을 태스크로 쪼갭니다.

State

모든 실행은 상태를 가집니다. Scheduled Pending Running Completed Failed 등. UI의 색이 곧 이 상태입니다.

Task Runner

태스크를 어떻게 실행할지 정하는 엔진. 기본은 스레드풀, 옵션으로 Dask·Ray를 붙여 분산 실행합니다.

Deployment

"이 플로우를, 이 일정으로, 이 인프라에서 실행하라"는 서버에 등록된 명세. 로컬 실행과 운영 실행을 가르는 경계입니다.

Work Pool

실행 인프라의 종류와 기본 설정을 담는 대기열. process / docker / kubernetes / ecs 등 타입이 있습니다.

Worker

워크 풀을 지켜보다가 예약된 실행을 가져와 실제로 프로세스·컨테이너·파드를 띄우는 상주 프로세스.

Block

재사용 가능한 설정·인증정보 묶음. S3 버킷, DB 접속정보, 슬랙 웹훅 같은 것을 UI에서 관리하고 코드에서 이름으로 불러옵니다.

Variable

비밀이 아닌 설정값(임계치, 대상 목록 등)을 서버에 저장. 배포 없이 값만 바꿀 수 있습니다.

Artifact

실행 결과로 남기는 표·마크다운·링크·수치. 실행 화면에 리포트를 붙여 사람이 읽게 만드는 장치입니다.

Event & Automation

상태 변화나 커스텀 이벤트를 조건으로 걸어 알림·재실행·다른 플로우 실행을 자동으로 트리거합니다.

Asset

@materialize로 표시하면 그 워크플로가 만들어내는 테이블·파일을 추적하고 의존 관계를 그려줍니다. (3.7+)

상태 전이를 한 번 정리하면

실행 하나가 살아가는 경로입니다. UI에서 보게 될 색과 단어가 정확히 이 순서로 나타납니다.

Scheduled›Late (지연 시)›Pending›Running›Completed
Running›Failed›AwaitingRetry›Retrying›Completed 또는 Failed
알아두면 디버깅이 쉬워지는 상태

Late는 예약 시각이 지났는데 실행이 시작되지 않은 상태입니다. 거의 항상 원인은 하나입니다 — 해당 워크 풀을 보는 워커가 죽어 있다. Crashed는 코드가 예외를 던진 게 아니라 프로세스나 컨테이너 자체가 사라진 경우(OOM, 노드 축출 등)입니다.

Flow와 Task, 어디까지 쪼개야 하나

신입이 가장 자주 묻는 질문입니다. 기준은 딱 하나입니다 — 독립적으로 재시도하거나 건너뛰고 싶은 단위인가.

상황태스크로 쪼갠다이유
외부 API 호출그렇다네트워크는 언제나 실패한다. 재시도가 필요한 대표 지점.
DB 쓰기 / 파일 업로드그렇다부분 실패를 구분해야 하고 재시도 정책이 다르다.
DataFrame 컬럼 이름 변경아니다실패 가능성이 없고, 태스크 오버헤드만 늘어난다.
반복문 안의 짧은 계산 10만 번아니다태스크 하나마다 상태 기록이 생겨 서버가 과부하된다.
테이블 20개 각각 적재그렇다 (map)병렬화 이득이 크고, 실패한 테이블만 다시 돌릴 수 있다.
03 구조 이해

아키텍처 해부 — 무엇이 어디서 도는가

Prefect의 가장 중요한 설계 결정은 제어와 실행의 분리입니다. 서버는 일정과 상태만 관리하고, 여러분의 코드는 여러분의 인프라에서 실행됩니다. 서버가 여러분의 데이터를 만지지 않는다는 뜻이고, 이것이 사내 자체 호스팅이 편한 이유입니다.

실행 평면 — 여러분의 인프라에서 도는 것
코드 · 부가 서비스

블록을 선택하세요

9개 구성 요소 중 하나를 누르면 역할, 실제로 실행되는 명령, 신입이 자주 겪는 문제를 보여줍니다.

한 번의 예약 실행이 흘러가는 순서

이 순서를 외우면 장애의 90%는 어디를 봐야 할지 바로 알 수 있습니다.

  1. 스케줄러가 배포(Deployment)의 일정을 보고 미래 실행을 Scheduled 상태로 DB에 미리 만들어 둔다.
  2. 실행 시각이 되면 그 실행이 해당 워크 풀의 대기열에 노출된다.
  3. 그 풀을 보고 있는 워커가 실행을 집어 올린다. (워커가 없으면 여기서 멈추고 Late가 된다)
  4. 워커가 배포 명세대로 실행 환경을 만든다 — 서브프로세스를 띄우거나, 도커 컨테이너를 만들거나, 쿠버네티스 잡을 생성한다.
  5. 그 환경이 pull 단계를 수행해 코드를 가져온다 (git clone, S3 다운로드, 또는 이미지에 이미 포함).
  6. 플로우 코드가 실행되며 상태와 로그를 API 서버로 보고한다. 데이터 자체는 서버로 가지 않는다.
  7. 종료 상태가 기록되고, 조건에 맞는 자동화가 있으면 알림이나 후속 작업이 트리거된다.
가장 흔한 초보 실수 세 가지

1. PREFECT_API_URL을 설정하지 않아 실행 기록이 서버에 안 보인다. 2. 워커를 띄우지 않고 배포만 만들어 놓고 "왜 안 돌아요?"라고 묻는다. 3. 워커 환경에 플로우가 쓰는 라이브러리(pandas 등)가 설치되어 있지 않다. 워커는 여러분의 노트북이 아니라 그 서버의 파이썬 환경을 씁니다.

자체 호스팅 서버와 Prefect Cloud의 차이

이 강의는 설치 버전(자체 호스팅) 기준입니다. 오픈소스 서버만으로도 스케줄, 재시도, 이벤트, 자동화, UI가 전부 동작합니다. 상용 서비스와의 차이는 주로 조직 관리 기능입니다.

기능자체 호스팅 (OSS)Prefect Cloud
플로우 실행 · 스케줄 · 재시도가능가능
웹 UI · 로그 · 실행 이력가능가능
이벤트 기반 자동화가능가능 (관리형 자동화 추가)
인증단일 Basic Auth 문자열 수준사용자 · 팀 · 역할 기반 권한 · SSO
감사 로그 · 워크스페이스 분리없음있음
워커 없이 실행 (Managed / Push 풀)없음 — 워커 직접 운영있음
DB · 백업 · 확장 책임여러분Prefect
비용무료 (인프라 비용만)유료 (무료 티어 있음)

세부 기능 경계는 버전마다 바뀌므로, 도입 결정 전에는 공식 문서의 최신 비교표를 확인하는 것이 안전합니다.

단계 1 — 재시도와 타임아웃

외부 API는 반드시 실패합니다. 실패를 예외 처리로 감싸는 대신 정책으로 선언합니다.

import httpx
from prefect import flow, task


@task(
    retries=3,                        # 최대 3번 더 시도
    retry_delay_seconds=[2, 10, 30],  # 지수적 백오프: 2초 → 10초 → 30초
    timeout_seconds=20,               # 20초 넘으면 실패로 간주
    log_prints=True,
)
def get_repo_stars(repo: str) -> int:
    r = httpx.get(f"https://api.github.com/repos/{repo}", timeout=10)
    r.raise_for_status()
    return r.json()["stargazers_count"]


@flow
def star_check(repos: list[str]):
    for repo in repos:
        print(f"{repo}: {get_repo_stars(repo)} stars")


if __name__ == "__main__":
    star_check(["PrefectHQ/prefect", "apache/airflow"])
retry_delay_seconds에 리스트를 넣는 이유

정수 하나를 주면 매번 같은 간격으로 재시도합니다. 리스트를 주면 시도마다 다른 간격을 씁니다. 상대 서버가 과부하일 때 같은 간격으로 계속 두드리는 것은 상황을 악화시키므로, 점점 길어지는 간격이 기본 예의입니다.

단계 2 — 병렬 실행

순차 실행을 병렬로 바꾸는 데 필요한 것은 .submit() 또는 .map()입니다.

from prefect import flow, task
from prefect.task_runners import ThreadPoolTaskRunner


@task
def load_table(name: str) -> int:
    # 실제로는 SELECT / INSERT
    return len(name) * 100


@flow(task_runner=ThreadPoolTaskRunner(max_workers=6))
def load_all(tables: list[str]):
    # submit은 즉시 반환되는 future를 준다 → 6개가 동시에 시작
    futures = [load_table.submit(t) for t in tables]

    # Prefect 3에서는 future가 자동으로 풀리지 않는다.
    # 결과가 필요하면 반드시 .result()를 호출한다.
    total = sum(f.result() for f in futures)
    return total


if __name__ == "__main__":
    print(load_all(["orders", "users", "payments", "logs", "events", "carts"]))
from prefect import flow, task, unmapped


@task
def transform(row_id: int, mode: str) -> dict:
    return {"id": row_id, "mode": mode}


@flow
def bulk(ids: list[int]):
    # 리스트 길이만큼 태스크가 자동 생성된다.
    # unmapped로 감싼 인자는 모든 태스크에 같은 값으로 전달된다.
    futures = transform.map(ids, unmapped("strict"))
    return [f.result() for f in futures]


if __name__ == "__main__":
    print(bulk(list(range(1, 21))))   # 태스크 20개가 병렬 생성

단계 3 — 캐싱

같은 입력으로 이미 성공한 태스크를 다시 실행하지 않게 만듭니다. 실패한 실행을 재시도할 때 앞부분을 건너뛰는 효과가 여기서 나옵니다.

from datetime import timedelta
from prefect import flow, task
from prefect.cache_policies import INPUTS, TASK_SOURCE


@task(
    cache_policy=INPUTS + TASK_SOURCE,   # 입력값 + 함수 소스코드가 같으면 재사용
    cache_expiration=timedelta(hours=6),
)
def expensive_query(target_date: str) -> int:
    print(f"실제 쿼리 실행: {target_date}")
    return 1_234_567


@flow
def daily(target_date: str = "2026-09-07"):
    a = expensive_query(target_date)
    b = expensive_query(target_date)   # 두 번째는 캐시 적중 → 쿼리 안 함
    return a, b
캐시 정책 선택 주의

INPUTS만 쓰면 함수 내용을 고쳐도 옛 결과를 재사용합니다. 개발 중에는 TASK_SOURCE를 함께 더해 코드가 바뀌면 캐시가 무효화되도록 하는 편이 안전합니다. 캐시를 끄려면 cache_policy=NO_CACHE.

단계 4 — 로깅

from prefect import flow, task, get_run_logger


@task
def validate(rows: int, threshold: int = 1000):
    logger = get_run_logger()      # 이 로거의 출력은 서버에 저장되고 UI에서 보인다
    logger.info("검증 시작: 행 %s개", rows)

    if rows < threshold:
        logger.warning("행 수가 기준(%s)보다 적습니다", threshold)
    if rows == 0:
        logger.error("데이터가 비어 있습니다")
        raise ValueError("empty dataset")

    return True


@flow(log_prints=True)   # print()도 로그로 함께 수집

단계 5 — 파라미터와 서브플로우

플로우 인자는 자동으로 타입 검증됩니다(Pydantic 기반). UI에서 수동 실행할 때 입력 폼도 이 타입 정보로 만들어집니다.

from datetime import date
from pydantic import BaseModel, Field
from prefect import flow, task


class IngestConfig(BaseModel):
    source: str
    target_date: date
    batch_size: int = Field(default=1000, ge=1, le=100_000)
    dry_run: bool = False


@task
def pull(cfg: IngestConfig) -> int:
    return cfg.batch_size


@flow                                   # 서브플로우: 다른 플로우 안에서 호출된다
def ingest_one(cfg: IngestConfig) -> int:
    return pull(cfg)


@flow(name="ingest-all", log_prints=True)
def ingest_all(target_date: date, sources: list[str] = ["crm", "erp", "web"]):
    total = 0
    for s in sources:
        cfg = IngestConfig(source=s, target_date=target_date)
        total += ingest_one(cfg)        # 각 호출이 독립된 서브플로우 실행으로 기록된다
    print(f"총 {total}건")
    return total

서브플로우는 UI에서 부모 실행 아래 접히는 트리로 보입니다. 태스크와 다른 점은 서브플로우는 자체 재시도 정책과 자체 태스크 러너를 가질 수 있다는 것입니다. 논리적으로 독립된 파이프라인 조각이면 서브플로우, 단순 작업 단위면 태스크로 두세요.

@task
def write_staging(path: str):

@write_staging.on_rollback
def cleanup(txn):

@task
def validate():

def atomic_load():

06 운영으로 넘기기

배포 — 자체 호스팅 기준

python hello.py는 여러분의 노트북이 켜져 있을 때만 돕니다. 배포(Deployment)는 "이 플로우를, 이 일정으로, 이 인프라에서, 이 파라미터로 실행하라"는 명세를 서버에 등록하는 일입니다. 이걸 하면 노트북을 닫아도 새벽 2시에 잡이 돕니다.

배포 = 세 가지의 묶음

① 코드를 어디서 가져올지 (git 저장소 / 컨테이너 이미지 / 로컬 경로) ② 언제 실행할지 (cron / interval / 이벤트 / 수동) ③ 어디서 실행할지 (워크 풀 = 프로세스인지 도커인지 쿠버네티스인지)

어떤 배포 방식을 골라야 하나

Prefect은 세 가지 배포 방법을 제공합니다. 처음에는 무엇을 써야 할지 헷갈리는데, 기준은 단순합니다.

Q1실행 인프라가 고정되어 있습니까?
Q2배포할 플로우가 몇 개입니까?
Q3설정을 코드에 두고 싶습니까, 파일로 관리하고 싶습니까?

언제 쓰나

학습, 사내 소규모 배치, 그리고 장수명 컨테이너의 ENTRYPOINT. 도커 컨테이너 하나에 이 스크립트를 넣고 재시작 정책만 걸어두면 꽤 견고한 배치 서버가 됩니다. 단점은 이 프로세스가 죽으면 스케줄도 멈추고, 실행마다 격리된 환경을 만들 수 없다는 것입니다.

운영에서 가장 많이 쓰는 파이썬 방식. 워크 풀에 배포를 등록하면, 별도로 떠 있는 워커가 실행마다 새 환경을 만들어 돌립니다.

1) 워크 풀을 만든다

# 타입 확인
prefect work-pool preview-types 2>/dev/null || prefect work-pool create --help

# 서브프로세스로 실행하는 가장 단순한 풀
prefect work-pool create local-pool --type process

# 도커 컨테이너로 실행하는 풀 (prefect-docker 필요)
pip install prefect-docker
prefect work-pool create docker-pool --type docker

prefect work-pool ls

2) 배포를 등록한다

from prefect import flow

if __name__ == "__main__":
    flow.from_source(
        source="https://github.com/myorg/pipelines.git",   # 코드를 가져올 곳
        entrypoint="flows/weather.py:weather_report",       # 파일:함수
    ).deploy(
        name="weather-prod",
        work_pool_name="docker-pool",
        image="registry.internal/pipelines:1.4.0",          # 실행용 이미지
        build=False,                                        # 이미지는 CI가 이미 만들었다
        push=False,
        cron="0 6 * * *",
        parameters={"city": "Seoul"},
        job_variables={"env": {"TZ": "Asia/Seoul"}},
        tags=["prod"],
    )
python deploy.py
# Deployment 'weather-report/weather-prod' 등록 완료

3) 워커를 띄운다

# 이 프로세스가 계속 떠 있어야 예약 실행이 집행된다
prefect worker start --pool docker-pool

# 여러 풀을 동시에 보게 하지 않는다. 풀 하나당 워커 프로세스 하나가 원칙.

4) 수동으로 한 번 돌려본다

prefect deployment ls
prefect deployment run "weather-report/weather-prod"

# 파라미터를 바꿔서 실행
prefect deployment run "weather-report/weather-prod" --param city=Busan

# 터미널에서 실행 상태를 지켜본다
prefect deployment run "weather-report/weather-prod" --watch
로컬 코드로 배포할 때의 함정

from_source 없이 my_flow.deploy(...)를 하면 코드가 이미지에 구워지거나 로컬 경로를 참조합니다. 워커가 다른 머신에 있으면 그 경로가 존재하지 않아 실행이 실패합니다. 워커와 코드가 같은 파일시스템에 있지 않다면 반드시 git 저장소, 오브젝트 스토리지, 또는 컨테이너 이미지 중 하나로 코드를 전달해야 합니다.

팀 단위 운영과 CI/CD에 가장 잘 맞는 방식. 여러 배포를 한 파일에 선언하고 prefect deploy 한 번으로 전부 등록합니다.

# 저장소 루트에 둔다. prefect init 으로 템플릿을 만들 수 있다.
name: data-pipelines
prefect-version: 3.8.2

# ── build: 배포 등록 시 실행되는 준비 단계 (이미지 빌드 등)
build:
  - prefect_docker.deployments.steps.build_docker_image:
      id: build-image
      requires: prefect-docker>=0.6.0
      image_name: registry.internal/pipelines
      tag: "1.4.0"
      dockerfile: Dockerfile

# ── push: 만든 결과물을 원격에 올리는 단계
push:
  - prefect_docker.deployments.steps.push_docker_image:
      requires: prefect-docker>=0.6.0
      image_name: "{{ build-image.image_name }}"
      tag: "{{ build-image.tag }}"

# ── pull: 실행 시점에 워커가 코드를 가져오는 방법 (실행 환경에서 수행됨)
pull:
  - prefect.deployments.steps.git_clone:
      repository: https://github.com/myorg/pipelines.git
      branch: main
      # 비공개 저장소라면 블록으로 인증정보를 참조한다
      # credentials: "{{ prefect.blocks.github-credentials.ci-token }}"

# ── deployments: 실제 배포 목록
deployments:
  - name: weather-hourly
    entrypoint: flows/weather.py:weather_report
    description: 매시 기상 리포트 생성
    tags: [prod, weather]
    parameters:
      city: Seoul
    work_pool:
      name: docker-pool
      job_variables:
        image: "{{ build-image.image }}"
        env:
          TZ: Asia/Seoul
    schedules:
      - cron: "0 * * * *"
        timezone: Asia/Seoul
        active: true

  - name: sales-daily
    entrypoint: flows/sales.py:sales_rollup
    tags: [prod, sales]
    concurrency_limit: 1          # 같은 배포의 동시 실행을 1개로 제한
    work_pool:
      name: docker-pool
    schedules:
      - cron: "30 2 * * *"
        timezone: Asia/Seoul
prefect init                 # 템플릿 생성 (선택)

prefect deploy --all         # 파일에 있는 모든 배포 등록
prefect deploy --name weather-hourly   # 하나만 등록

# CI에서는 이렇게 쓴다
prefect deploy --all --no-prompt

build → push → pull의 역할 구분이 헷갈리기 쉽습니다. build와 push는 배포를 등록하는 지금 이 순간 여러분의 머신이나 CI에서 실행됩니다. pull은 나중에 실제 플로우가 돌 때 실행 환경 안에서 실행됩니다.

운영급 자체 호스팅 — PostgreSQL로 바꾸기

SQLite는 단일 프로세스 학습용입니다. 실제 운영은 PostgreSQL이 사실상 필수입니다.

# 1) 접속 문자열 설정 (asyncpg 드라이버를 쓴다는 점에 주의)
prefect config set PREFECT_SERVER_DATABASE_CONNECTION_URL=\
"postgresql+asyncpg://prefect:비밀번호@db.internal:5432/prefect"

# 2) 스키마 마이그레이션
prefect server database upgrade -y

# 3) 서버 기동
prefect server start --host 0.0.0.0 --port 4200

여러 서버 인스턴스로 확장할 계획이라면 PostgreSQL 14.9 이상이 필요합니다. 상태 동기화에 필요한 기능이 SQLite에는 없습니다.

도커 컴포즈로 전체 스택 한 번에

실습용 사내 서버 한 대에 올리기에 가장 실용적인 구성입니다. PostgreSQL + Redis + 마이그레이션 + 서버 + 워커.

services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: prefect
      POSTGRES_PASSWORD: change-me
      POSTGRES_DB: prefect
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U prefect"]
      interval: 5s
      timeout: 5s
      retries: 15

  redis:
    image: redis:7
    command: redis-server --save "" --appendonly no

  # 서버 기동 전에 스키마를 올린다. 한 번 실행되고 종료되는 컨테이너.
  migrate:
    image: prefecthq/prefect:3-latest
    depends_on:
      postgres:
        condition: service_healthy
    command: prefect server database upgrade -y
    environment:
      PREFECT_SERVER_DATABASE_CONNECTION_URL: postgresql+asyncpg://prefect:change-me@postgres:5432/prefect

  server:
    image: prefecthq/prefect:3-latest
    depends_on:
      migrate:
        condition: service_completed_successfully
    command: prefect server start --host 0.0.0.0 --port 4200
    ports:
      - "4200:4200"
    environment:
      PREFECT_SERVER_DATABASE_CONNECTION_URL: postgresql+asyncpg://prefect:change-me@postgres:5432/prefect
      PREFECT_SERVER_DATABASE_MIGRATE_ON_START: "false"
      # 최소한의 접근 통제. 브라우저가 접속할 때 아이디/비밀번호를 묻는다.
      PREFECT_SERVER_API_AUTH_STRING: "admin:change-me"
      # 브라우저에서 접근할 API 주소. 리버스 프록시를 쓰면 그 도메인으로 바꾼다.
      PREFECT_UI_API_URL: http://localhost:4200/api
    restart: unless-stopped

  worker:
    # 도커 타입 워커는 prefect-docker 가 필요하므로 직접 이미지를 만드는 편이 깔끔하다
    image: prefecthq/prefect:3-latest
    depends_on:
      - server
    entrypoint: /bin/sh
    command: >
      -c "pip install --no-cache-dir prefect-docker &&
          prefect worker start --pool docker-pool --type docker"
    environment:
      PREFECT_API_URL: http://server:4200/api
      PREFECT_API_AUTH_STRING: "admin:change-me"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    restart: unless-stopped

volumes:
  pgdata:
docker compose up -d
docker compose logs -f server

# 워크 풀은 최초 한 번 만들어 준다
docker compose exec server prefect work-pool create docker-pool --type docker

07 실무 감각

운영 체크리스트

설치는 30분이면 끝나지만, 6개월 뒤에도 멀쩡하게 도는 시스템을 만드는 건 다른 일입니다. 자체 호스팅에서 실제로 문제가 되는 지점들입니다.

확장 — 서버를 여러 프로세스/인스턴스로

# 한 호스트에서 API 프로세스를 여러 개 (보통 CPU 코어 수에 맞춘다)
prefect server start --workers 4

# 여러 컨테이너/인스턴스로 나눌 때: API만 담당하는 복제본들
prefect server start --host 0.0.0.0 --no-services

# 그리고 스케줄러·이벤트 처리 등 백그라운드 서비스는 딱 한 세트만 별도로
prefect server services start
여기서 Redis가 필요해집니다

기본 설정의 메시징·이벤트 순서 보장은 프로세스 메모리 안에서만 동작합니다. 프로세스를 여러 개로 늘리면 서로 상태를 공유할 수 없습니다. 그래서 --workers나 다중 인스턴스 구성에서는 Redis 기반 메시징으로 바꿔야 하고, 그러지 않으면 서버가 기동 시점에 검증에 실패하며 종료합니다. 그리고 백그라운드 서비스는 절대 여러 세트를 돌리지 마세요 — 스케줄러가 중복되면 같은 실행이 두 번 만들어집니다.

업그레이드 순서

자체 호스팅 오픈소스 서버는 클라이언트와 서버의 major 버전이 같아야 합니다. 그래서 순서가 중요합니다.

  1. DB 백업. 되돌릴 수 없는 마이그레이션이 있을 수 있습니다.
  2. 워커를 정지(또는 새 실행을 받지 않게 일시 중지).
  3. 서버 정지 → 새 버전 설치 → prefect server database upgrade -y.
  4. 서버 기동 후 UI 정상 확인.
  5. 워커 이미지/패키지 업그레이드 후 재기동.
  6. 문제가 생기면 prefect server database downgrade -y -r -1로 한 단계 되돌립니다.

태스크 중심 — Airflow

"작업들의 실행 순서 그래프"가 1급 개념. 각 태스크가 성공했는지를 추적하지, 데이터 자체를 모델링하지는 않는다.

"이 파이프라인이 만들어내는 테이블/파일"이 1급 개념. 산출물 기준으로 의존성과 최신성을 관리한다.

"평범한 파이썬 함수 호출"이 1급 개념. 실행 흐름을 코드가 결정하고, 오케스트레이터는 그 실행을 관측·복구한다.

Airflow와 Prefect, 같은 일을 하는 코드

가장 자주 비교되는 두 툴입니다. "테이블 세 개를 병렬로 적재하고, 끝나면 리포트를 만든다"를 각각 써보면 차이가 분명해집니다.

from prefect import flow, task
from prefect.task_runners import ThreadPoolTaskRunner


@task(retries=2)
def load(table: str) -> int:
    return 100


@task
def report(counts: list[int]) -> str:
    return f"총 {sum(counts)}건"


@flow(task_runner=ThreadPoolTaskRunner(max_workers=3), log_prints=True)
def etl(tables: list[str] = ["orders", "users", "payments"]):
    futures = load.map(tables)             # 병렬
    counts = [f.result() for f in futures]
    print(report(counts))                  # 의존성은 호출 순서에서 자동 유도

# 테이블 개수가 런타임에 결정돼도 그대로 동작한다.
from datetime import datetime
from airflow.decorators import dag, task


@task(retries=2)
def load(table: str) -> int:
    return 100


@task
def report(counts: list[int]) -> str:
    return f"총 {sum(counts)}건"


@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False)
def etl():
    # 동적 태스크 매핑: expand 로 표현한다
    counts = load.expand(table=["orders", "users", "payments"])
    report(counts)

from prefect import flow, task, get_run_logger
from prefect.artifacts import create_table_artifact


@task(retries=1)
def train(params: dict) -> dict:
    return {"auc": 0.874, "params": params}


@task
def gate(metrics: dict, min_auc: float = 0.86) -> bool:
    logger = get_run_logger()
    if metrics["auc"] < min_auc:
        logger.warning("성능 기준 미달 — 배포를 중단합니다")
        return False
    return True


@flow(log_prints=True)
def training_pipeline(grid: list[dict]):
    # 하이퍼파라미터 조합만큼 태스크가 동적으로 생성된다
    results = [f.result() for f in train.map(grid)]
    best = max(results, key=lambda r: r["auc"])

    create_table_artifact(key="model-metrics", table=results)

    if gate(best):
        print(f"모델 승격: AUC {best['auc']}")

from prefect import flow, task
from prefect.events import emit_event


@task(retries=2)
def check_cert(host: str) -> int:
    return 12          # 만료까지 남은 일수


@flow(log_prints=True)
def cert_watch(hosts: list[str]):
    for host in hosts:
        days = check_cert(host)
        if days < 30:
            print(f"[경고] {host} 인증서 {days}일 후 만료")
            emit_event(
                event="cert.expiring.soon",
                resource={"prefect.resource.id": f"host.{host}"},
                payload={"days_left": days},
            )

발행한 이벤트에 자동화를 걸어두면 슬랙 알림이나 지라 티켓 생성까지 코드 수정 없이 연결됩니다.

Q4prefect.yaml의 pull 단계는 언제 실행됩니까?
build와 push는 배포 등록 시점에, pull은 실행 시점에 실행 환경에서 수행됩니다. 그래서 pull에 쓴 git 저장소는 워커가 접근할 수 있어야 합니다.
Q5운영 환경에서 자체 호스팅 서버의 데이터베이스로 적절한 것은?
SQLite는 단일 프로세스 학습용입니다. Redis는 DB 대체가 아니라 다중 프로세스 확장 시 메시징·순서 보장을 위해 추가로 쓰입니다.
Q6서버를 --workers 4로 여러 프로세스로 띄울 때 반드시 필요한 것은?
기본 메시징은 프로세스 메모리 안에서만 동작하므로, 프로세스가 늘어나면 공유 백엔드가 필요합니다. 설정이 안 되어 있으면 서버가 기동 시점에 검증 실패로 종료합니다.
Q7워커 없이 가장 빠르게 스케줄 실행을 시작하는 방법은?
serve()는 그 프로세스 자체가 스케줄러 겸 실행기가 됩니다. 대신 프로세스가 죽으면 스케줄도 멈추고, 실행마다 격리 환경을 만들 수는 없습니다.
Q8다음 중 태스크로 쪼개면 오히려 해로운 것은?
태스크마다 상태가 기록되므로, 초경량 작업을 수만 개 태스크로 만들면 오버헤드와 서버 부하만 커집니다. 배치 단위로 묶으세요.
Q9DB 비밀번호를 다루는 올바른 방법은?
Variable은 비밀이 아닌 설정값용입니다. 비밀정보는 Secret 블록(또는 외부 시크릿 매니저 연동)을 쓰고, 로그에 절대 출력하지 않습니다.
Q10동적으로 단계 수가 변하는 워크플로(예: 폴더의 파일 개수만큼 처리)에 가장 잘 맞는 도구 특성은?
이것이 Prefect의 핵심 설계이자 가장 뚜렷한 강점입니다. for문과 .map()이 그대로 동적 태스크 생성이 됩니다.
부록 참고 자료

용어집

문서나 동료의 대화에서 막혔을 때 여기서 찾으세요.

Flow 플로우
워크플로 전체의 진입점이 되는 함수. @flow로 표시하며, 한 번 호출되면 플로우 실행 한 건이 기록된다. 스케줄·알림의 단위.
Task 태스크
플로우 안의 작업 단위. @task로 표시. 개별 재시도·캐시·병렬 실행·상태 추적의 단위.
Flow Run / Task Run 실행
플로우 또는 태스크가 실제로 실행된 한 건. UI에 무작위 이름(예: rugged-marmot)으로 표시된다.
State 상태
실행의 현재 단계. Scheduled, Late, Pending, Running, Retrying, Completed, Failed, Crashed, Cancelled 등.
Late 지연
예약 시각이 지났는데 아직 시작되지 않은 상태. 거의 항상 워커 부재가 원인이다.
Crashed 비정상 종료
코드가 예외를 던진 게 아니라 실행 환경 자체가 사라진 경우(OOM, 컨테이너 강제 종료, 노드 축출 등).
Deployment 배포
"이 플로우를, 이 일정으로, 이 인프라에서, 이 파라미터로 실행하라"는 서버에 등록된 명세.
Work Pool 워크 풀
실행 인프라의 종류(process/docker/kubernetes/ecs 등)와 기본 설정을 담는 대기열.
Worker 워커
워크 풀을 지켜보다가 예약된 실행을 가져와 실제 실행 환경을 만드는 상주 프로세스. prefect worker start --pool 이름.
Task Runner 태스크 러너
태스크를 어떻게 실행할지 결정하는 엔진. ThreadPoolTaskRunner(기본), DaskTaskRunner, RayTaskRunner.
Block 블록
타입이 있는 재사용 설정·인증정보 객체. S3 버킷, DB 접속, 슬랙 웹훅 등을 UI에서 관리하고 코드에서 이름으로 불러온다.
Secret 시크릿
비밀정보를 담는 블록 타입. Secret.load("이름").get()으로 읽는다.
Variable 변수
비밀이 아닌 설정값. 배포 없이 UI나 CLI에서 값만 바꿀 수 있다.
Artifact 아티팩트
실행 결과로 남기는 표·마크다운·링크·수치. key별로 이력이 쌓여 실행 간 비교가 가능하다.
Automation 자동화
이벤트나 상태 변화를 조건으로 알림·재실행·다른 배포 실행을 트리거하는 규칙. UI에서 관리한다.
Event 이벤트
시스템 또는 코드가 발행하는 사건 기록. emit_event()로 직접 발행할 수 있고 자동화의 트리거가 된다.
Cache Policy 캐시 정책
태스크 결과 재사용 기준. INPUTS(입력값), TASK_SOURCE(함수 소스), NO_CACHE 등을 조합한다.
Transaction 트랜잭션
with transaction(): 블록. 실패 시 on_rollback 훅으로 부작용을 되돌려 부분 성공 상태를 방지한다.
Asset / materialize 애셋
@materialize로 워크플로의 산출물(테이블·파일)을 선언해 계보와 의존 관계를 추적하는 기능. 3.7 이후 도입.
Profile 프로필
설정값 묶음. 로컬/개발/운영 서버를 프로필로 나눠 prefect profile use로 전환한다.
Concurrency Limit 동시성 제한
같은 배포나 같은 태그의 동시 실행 개수 상한. 중복 적재와 외부 시스템 과부하를 막는다.
prefect-client
서버 컴포넌트와 CLI를 제외한 최소 설치 패키지. 컨테이너 이미지 크기를 줄일 때 쓴다.
PREFECT_API_URL
클라이언트가 어느 서버에 보고할지 정하는 환경변수/설정. 자체 호스팅 기본값은 http://127.0.0.1:4200/api.
DAG
방향성 비순환 그래프. Airflow의 1급 개념이며, Prefect에서는 명시적으로 선언하지 않고 실행 중에 유도된다.
Backfill 백필
과거 기간에 대해 파이프라인을 소급 실행하는 일. Prefect에서는 보통 날짜 파라미터를 받는 플로우를 여러 번 실행해 처리한다.
일치하는 용어가 없습니다. 다른 단어로 검색해 보세요.

다음에 무엇을 배울까

  1. 통합 패키지 하나 익히기. 여러분이 쓰는 클라우드에 맞춰 prefect-aws, prefect-gcp, prefect-azure 중 하나. 여기에 prefect-dbt, prefect-slack이면 대부분의 실무가 커버됩니다.
  2. 테스트 습관. prefect_test_harness로 CI에서 플로우를 검증하는 파이프라인 만들기.
  3. 쿠버네티스 워크 풀. 실행 격리와 리소스 제한이 필요해지는 시점에 반드시 만나게 됩니다.
  4. Airflow도 한 번은 만져 보기. 채용 시장과 기존 시스템에서 여전히 가장 많이 쓰이며, 두 개를 다 알면 선택의 근거를 말할 수 있습니다.
