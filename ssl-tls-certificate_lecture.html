PART 0

기초 — 인증서가 하는 일

암호화는 도청을 막고, 인증서는 "누구와" 암호화하는지를 증명합니다. 둘은 다른 문제입니다.

01암호화만으로는 부족한 이유

HTTPS를 켰다는 말은 두 가지를 동시에 했다는 뜻입니다. 통신 내용을 암호화했고, 상대가 진짜 그 도메인의 서버임을 확인했습니다. 실무 사고는 대부분 두 번째에서 납니다.

클라이언트와 서버가 키를 주고받아 암호화만 하면 도청은 막습니다. 하지만 중간에 누군가 끼어들어 자기 키를 서버 키인 척 건네면, 클라이언트는 공격자와 암호화 통신을 하게 됩니다. 이것이 중간자 공격(MITM)입니다. 암호화 자체는 완벽한데 상대를 확인하지 않았기 때문에 무의미해집니다.

이 문제를 풀려면 "이 공개키는 확실히 shop.customer.co.kr의 것"이라고 보증해 줄 제3자가 필요합니다. 그 보증서가 인증서이고, 보증하는 기관이 CA입니다. 브라우저는 이미 신뢰하는 CA 목록을 갖고 출고되기 때문에, CA가 서명한 인증서를 받으면 처음 보는 서버라도 검증할 수 있습니다.

TLSTransport Layer Security

전송 구간 암호화 프로토콜. SSL의 후속이며 SSL 2.0/3.0은 모두 폐기됐습니다. "SSL 인증서"라는 말은 관례적 표현이고 실제 동작은 전부 TLS입니다.

CACertificate Authority

인증서를 발급·서명하는 기관. 공인 CA(Let's Encrypt, DigiCert, Sectigo 등)와 조직이 직접 운영하는 사설 CA로 나뉩니다.

트러스트 스토어Trust Store

OS나 브라우저에 내장된 "믿어도 되는 루트 CA 목록". 검증의 최종 기준점입니다. 리눅스는 /etc/ssl/certs, 자바는 cacerts, 윈도우는 인증서 저장소를 씁니다.

MITMMan In The Middle

통신 경로 중간에서 양쪽을 속여 트래픽을 가로채는 공격. 인증서 검증이 이를 막는 유일한 장치입니다.

WebPKI

브라우저·OS가 신뢰하는 공개 CA 생태계 전체. 규칙은 CA/Browser Forum의 Baseline Requirements가 정합니다.

Private PKI

조직 내부에서만 신뢰되는 자체 CA 체계. 내부 서비스 간 통신, mTLS, 사내 시스템에 사용합니다.

현장 사례 한 고객사가 내부 API 호출 코드에서 인증서 검증 오류를 없애려고 curl -k와 verify=False를 넣었습니다. 통신은 여전히 암호화되므로 "보안 OK"처럼 보였지만, 검증을 끈 순간 그 구간은 MITM에 무방비가 됩니다. 검증 비활성화는 사고를 숨기는 행위이지 해결이 아닙니다. 원인은 대부분 중간 CA 누락이나 사내 CA 미신뢰이고, 3장과 15장에서 정석 해결법을 다룹니다.

02인증서 해부 — X.509 필드 읽기

인증서는 "공개키 + 그 키의 주인 정보 + CA의 서명"을 담은 구조화된 데이터입니다. 장애의 절반은 이 필드 중 하나를 잘못 봤기 때문에 생깁니다.

아래 덤프는 openssl x509 -text -noout의 실제 출력 형태입니다. 필드를 클릭하면 각각이 무슨 의미이고 어떤 사고와 연결되는지 설명이 나옵니다.

실습X.509 필드 탐색기

왼쪽 덤프에서 밑줄 친 항목을 클릭하세요. 신입 엔지니어가 가장 먼저 외워야 할 필드는 SAN, notAfter, Issuer 세 가지입니다.

openssl x509 -in cert.pem -text -noout

      

      

        
필드를 선택하세요

        
각 항목의 의미, 실무에서 확인하는 방법, 잘못됐을 때 나타나는 증상을 보여줍니다.

      

    

  


  

    
Subject주체
인증서가 증명하는 대상. 과거에는 CN에 도메인을 넣었지만 현재는 SAN이 기준입니다.

    
Issuer발급자
이 인증서에 서명한 CA. 체인 검증은 Issuer를 따라 위로 올라갑니다.

    
SANSubject Alternative Name
이 인증서가 유효한 도메인 목록. 브라우저는 CN을 보지 않고 SAN만 봅니다. 여기 없는 이름으로 접속하면 즉시 오류입니다.

    
KU / EKUKey Usage / Extended Key Usage
키의 용도 제한. 서버 인증서는 serverAuth, 클라이언트 인증서는 clientAuth가 필요합니다. mTLS 실패 원인 단골입니다.

    
SKI / AKISubject/Authority Key Identifier
키 지문. 검증기가 "이 인증서를 서명한 CA 인증서"를 빠르게 찾는 데 씁니다. 체인 구성의 힌트입니다.

    
Basic Constraints
CA:TRUE면 다른 인증서를 서명할 수 있는 CA 인증서, CA:FALSE면 최종 서버/클라이언트용(리프)입니다.

  


  
실무에서 가장 많이 쓰는 확인 명령

  

    
인증서 확인 3종 세트


# 1) 파일에 든 인증서 내용 보기
openssl x509 -in cert.pem -noout -subject -issuer -dates -ext subjectAltName

# 2) 운영 중인 서버가 실제로 내려주는 인증서 보기 (SNI 반드시 지정)
openssl s_client -connect shop.customer.co.kr:443 -servername shop.customer.co.kr </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# 3) 남은 기간만 빠르게 (30일 미만이면 만료 임박 종료코드 0)
openssl x509 -in cert.pem -noout -checkend $((30*86400))

  


  

    주의
    -servername을 빼면 다른 인증서가 나옵니다. 한 IP에 여러 도메인이 올라가 있으면(가상 호스팅, 인그레스 컨트롤러, ALB) 서버는 SNI 값으로 어떤 인증서를 줄지 고릅니다. SNI 없이 조회한 결과로 "인증서가 잘못 설치됐다"고 판단하는 오진이 매우 흔합니다.
  






  
03체인 — 신뢰는 어떻게 이어지는가

  
브라우저는 서버 인증서 하나만 보고 판단하지 않습니다. 루트까지 이어지는 서명 사슬을 끝까지 따라가 봅니다. 이 사슬이 한 칸이라도 끊기면 실패합니다.


  
구조는 3단이 표준입니다. 루트 CA는 OS/브라우저에 내장되어 있고 키는 오프라인 금고에 보관됩니다. 루트가 중간 CA를 서명하고, 중간 CA가 실제 서버 인증서(리프)를 서명합니다. 루트를 직접 쓰지 않는 이유는 단순합니다. 루트 키가 유출되면 전 세계 트러스트 스토어를 갱신해야 하지만, 중간 CA는 폐기하고 새로 만들면 되기 때문입니다.


  
여기서 실무 핵심이 하나 나옵니다. 서버는 리프 인증서와 중간 CA 인증서를 함께 내려줘야 합니다. 루트는 클라이언트가 이미 갖고 있으니 보내지 않아도 되지만, 중간 CA는 클라이언트에 없을 수 있습니다. 중간 CA를 빼먹으면 브라우저에서는 멀쩡하고(브라우저는 캐시나 AIA로 보충하기도 합니다) 서버 간 통신이나 모바일 앱에서만 터지는, 가장 찾기 어려운 형태의 장애가 됩니다.

체인 점검


# 서버가 내려주는 인증서를 순서대로 모두 출력
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# 결과의 Certificate chain 항목을 본다
# 0 s:CN=example.com        i:C=US, O=Let's Encrypt, CN=R11   <- 리프

# Verify return code: 0 (ok)  <- 0이 아니면 검증 실패

    순서 규칙

교차 서명과 루트 만료

  
루트 CA도 만료됩니다. 2021년 Let's Encrypt의 DST Root CA X3 만료 때 오래된 안드로이드·OpenSSL 1.0.x 환경에서 대규모 오류가 발생했고, 2024년에도 유사한 전환이 있었습니다. 신규 루트를 아직 모르는 구형 클라이언트를 위해 CA는 교차 서명된 중간 인증서를 제공합니다. 오래된 장비·임베디드·구형 JVM을 포함한 고객사에서는 체인 선택지가 여러 개일 수 있다는 점을 기억해야 합니다.






  
04키 쌍과 CSR

  
인증서를 받으려면 먼저 키 쌍을 만들고, 공개키와 신원 정보를 담은 신청서(CSR)를 CA에 제출합니다. 개인키는 절대 밖으로 나가지 않습니다.


  

    
개인키Private Key
서버만 갖는 비밀. 유출되면 인증서를 즉시 폐기하고 재발급해야 합니다. 파일 권한은 600, 소유자는 서비스 계정.

    
공개키Public Key
누구에게나 공개되는 짝. 인증서 안에 담겨 배포됩니다.

    
CSRCertificate Signing Request
공개키 + 도메인/조직 정보를 담아 CA에 제출하는 신청서. 개인키로 자체 서명해 소유를 증명합니다.

    
RSA vs ECDSA
RSA 2048은 호환성이 가장 넓고, ECDSA P-256은 키가 짧아 핸드셰이크가 가볍습니다. 신규 구축은 ECDSA, 구형 클라이언트가 섞이면 둘 다 발급해 병행 제공(dual cert)합니다.

05핸드셰이크 — 인증서가 쓰이는 순간

  
인증서는 연결 초반 수십 밀리초 동안만 쓰입니다. 그 짧은 구간에서 무슨 일이 벌어지는지 알아야 "왜 특정 클라이언트만 실패하는지"를 설명할 수 있습니다.


  

    
실습TLS 핸드셰이크 시뮬레이터

    
버전을 고르고 단계를 넘겨 보세요. TLS 1.3은 왕복(RTT)을 한 번 줄였고, 인증서 자체를 암호화해서 전송합니다. 클라이언트 인증(mTLS)을 켜면 추가되는 단계도 확인할 수 있습니다.

    

      

        
        
      

      
      
      
      
      
    

    

    

  


  

    
SNIServer Name Indication
클라이언트가 암호화 전에 "나는 이 도메인에 접속하려 한다"고 알려주는 필드. 한 IP에서 여러 인증서를 서비스할 수 있게 해줍니다. SNI를 안 보내는 아주 오래된 클라이언트는 기본 인증서를 받습니다.

    
ALPNApplication-Layer Protocol Negotiation
핸드셰이크 중에 HTTP/2 사용 여부를 협상하는 확장. TLS-ALPN-01 도메인 검증 방식도 이 확장을 이용합니다.

    
암호 스위트Cipher Suite
키 교환·암호화·해시 알고리즘 조합. TLS 1.3에서 5개로 정리돼 설정 실수 여지가 크게 줄었습니다.

    
PFSPerfect Forward Secrecy
서버 개인키가 나중에 유출돼도 과거 트래픽은 복호화되지 않는 성질. TLS 1.3은 항상 보장합니다.

    
세션 재개Session Resumption
이미 한 번 연결한 클라이언트가 핸드셰이크를 축약하는 기능. 0-RTT는 빠르지만 재전송 공격 위험이 있어 멱등한 요청에만 써야 합니다.

    
TLS 종료TLS Termination
암호화를 푸는 지점. LB에서 풀지, 인그레스에서 풀지, 파드까지 들고 갈지가 곧 인증서를 어디에 둘 것인가의 문제입니다. PART 3의 핵심 주제입니다.

06공인 인증서의 종류 고르기

  
인증서는 "무엇을 검증했는가(DV/OV/EV)"와 "어떤 이름을 담았는가(단일/멀티/와일드카드)"라는 두 축으로 나뉩니다. 이 둘은 독립적입니다.


  
검증 등급

  

    
등급확인하는 것발급 시간비용언제 쓰나

    
      
DV 도메인 검증도메인 제어권만수초 ~ 수분(자동)무료~저가대부분의 웹서비스, API. 자동화의 전제

      
OV 조직 검증도메인 + 법인 실재 여부1~5영업일중금융·공공 등 내부 규정상 요구될 때

      
EV 확장 검증도메인 + 법인 + 실사1~2주고규정 요건. 브라우저 주소창 표시 효과는 사라짐

    
  


  

    오해 정정
    DV라서 암호화가 약한 것이 아닙니다. 세 등급 모두 동일한 암호 알고리즘과 동일한 TLS 보안을 제공합니다. 차이는 오직 CA가 발급 전에 무엇을 확인했는가입니다. 예전에 EV가 주소창에 회사명을 초록색으로 띄우던 UI는 주요 브라우저에서 모두 제거됐고, 지금 EV를 사는 이유는 사실상 내부 규정 충족입니다. 고객사가 "보안 강화를 위해 EV로 올려달라"고 하면 이 점을 설명해 주는 것이 맞습니다.

CAA 레코드 — 누가 우리 도메인의 인증서를 발급할 수 있는가

  
CAA는 DNS에 "이 도메인의 인증서는 이 CA만 발급할 수 있다"고 선언하는 레코드입니다. 다른 CA는 발급 요청을 받아도 거부해야 합니다. 고객사 도메인에서 제3자가 몰래 인증서를 받는 것을 막는 저비용·고효과 장치이므로, 인계 시 기본 체크리스트에 넣는 것이 좋습니다.

  

    
CAA 설정과 확인


# DNS 존에 추가 (Let's Encrypt와 DigiCert만 허용, 위반 시 메일 통보)
customer.co.kr.  IN CAA 0 issue "letsencrypt.org"
customer.co.kr.  IN CAA 0 issue "digicert.com"
customer.co.kr.  IN CAA 0 issuewild "letsencrypt.org"
customer.co.kr.  IN CAA 0 iodef "mailto:secops@customer.co.kr"

# 확인
dig CAA customer.co.kr +short

  

  

    주의
    CAA를 걸어놓고 CA를 교체하면 발급이 조용히 실패합니다. 갱신 자동화가 CAA record prohibits issuance 오류로 멈추는 사고가 실제로 자주 발생하므로, CA 변경은 반드시 CAA 수정과 한 세트로 진행합니다.
  






  
07도메인 검증(DCV) — 세 가지 챌린지

  
CA는 "당신이 정말 이 도메인의 주인인가"를 자동으로 확인합니다. 방식이 셋인데, 어떤 것을 고르느냐가 자동화 구조 전체를 결정합니다.


  

    

      
HTTP-01

      
CA가 http://도메인/.well-known/acme-challenge/<토큰>에 접속해 특정 파일을 확인합니다.

필요 조건: 80포트가 인터넷에 열려 있어야 함
못 하는 것: 와일드카드 발급 불가

    

    

      
DNS-01

      
_acme-challenge.도메인에 TXT 레코드를 넣어 증명합니다.

필요 조건: DNS API 자격증명
강점: 와일드카드 가능, 서버가 인터넷에 노출되지 않아도 됨. 폐쇄망·내부 서비스의 유일한 선택지

    

    

      
TLS-ALPN-01

      
443 포트에서 특별한 ALPN 프로토콜로 인증서를 제시해 증명합니다.

필요 조건: 443 제어권, 지원하는 컨트롤러
용도: 80을 열 수 없는 환경. 와일드카드 불가

    

  


  

    
실습챌린지 방식 선택 도우미

    
환경 조건을 고르면 가능한 방식과 그 이유, 그리고 흔히 막히는 지점을 알려줍니다.

    

      
      
      
    

    

  


  
DNS-01의 실무 무기: CNAME 위임

  
DNS-01이 강력하지만, 자동화 도구에 고객사 전체 DNS 존을 수정할 권한을 주는 것은 부담입니다. 해법은 검증용 레코드만 별도 존으로 위임하는 것입니다. 이러면 자동화 계정은 위임된 존에만 쓰기 권한을 가지면 됩니다.

  

    
acme-dns 방식 위임


# 고객사 존에는 이 CNAME 한 줄만 (한 번 설정 후 변경 없음)
_acme-challenge.shop.customer.co.kr.  IN CNAME  a1b2c3.acme-delegate.msp.co.kr.

# 이후 갱신 때마다 우리가 제어하는 acme-delegate 존에만 TXT를 쓴다
# 고객사 DNS 권한 = 불필요, 감사 추적 = 우리 쪽에 집중

  


  

    2029년 대비
    도메인 검증 결과 재사용 기간(DCV reuse)도 함께 줄어듭니다. 현재 200일, 2027년 3월부터 100일, 2029년 3월부터 10일입니다. 지금은 인증서를 갱신해도 검증을 다시 안 하는 경우가 많지만, 2029년에는 사실상 발급 때마다 매번 도메인 검증을 다시 통과해야 합니다. "갱신은 자동인데 검증은 수동"인 구조는 그때 전부 멈춥니다. DNS-01 + 위임 구조를 지금 깔아두는 것이 가장 확실한 대비입니다.
  






  
08ACME — 발급 자동화 프로토콜

  
ACME는 CA와 대화해서 인증서를 자동으로 받아오는 표준 프로토콜(RFC 8555)입니다. Let's Encrypt로 유명해졌지만 지금은 상용 CA와 사내 CA도 대부분 지원합니다.


  

    
실습ACME 발급 흐름 따라가기

    
클라이언트가 인증서를 받기까지 6단계. 각 단계에서 실패하면 어떤 증상이 나타나는지 함께 표시됩니다.

    

    

      
      
      
    

    

  


  

    
Account Key
ACME 계정을 식별하는 키. 인증서 개인키와는 별개이며, 유실하면 기존 계정의 발급 이력·한도를 못 씁니다. 백업 대상입니다.

    
Order
"이 도메인들로 인증서를 주세요"라는 요청 단위. 유효기간이 있어 오래 방치하면 만료됩니다.

    
Authorization / Challenge
도메인별 검증 과제와 그 결과. 성공한 인증은 일정 기간 재사용됩니다(7장 참고).

    
ARIACME Renewal Information
CA가 "언제 갱신하라"고 알려주는 확장. CA 측 문제로 대량 폐기가 필요할 때 클라이언트를 앞당겨 갱신시킵니다. 수명이 짧아질수록 중요해지며, 최소 하루 한 번은 조회해야 합니다.

    
Profile
발급 프로파일 선택 기능. Let's Encrypt는 classic(90일), tlsserver(45일), shortlived(160시간)을 제공합니다.

    
Rate Limit
CA별 발급 한도. Let's Encrypt는 도메인 기준 주간 한도가 있어, 테스트를 운영 엔드포인트로 돌리다 막히는 사고가 흔합니다. 반드시 staging에서 먼저 시험합니다.

  


  
주요 ACME 클라이언트

  

    
클라이언트특징적합한 곳

    
      
certbot레퍼런스 구현. 플러그인 풍부, 파이썬VM, 표준적인 웹서버

      
acme.sh순수 셸 스크립트, 의존성 없음. DNS 제공자 지원 폭이 가장 넓음경량 VM, 어플라이언스, 폐쇄망

      
legoGo 단일 바이너리. 라이브러리로도 사용컨테이너, 커스텀 도구

      
cert-manager쿠버네티스 컨트롤러. Certificate CRD로 선언적 관리모든 K8S 환경 (18~21장)

      
Caddy웹서버에 ACME 내장. 설정 없이 자동 HTTPS단순한 신규 서비스

    
  


  

    
VM에서 가장 흔한 두 가지 패턴


# [A] certbot + nginx 플러그인, HTTP-01 (가장 단순)
certbot --nginx -d shop.customer.co.kr -d www.shop.customer.co.kr \
  --non-interactive --agree-tos -m secops@msp.co.kr

# [B] acme.sh + Route53 DNS-01, 와일드카드 (내부망도 가능)
export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=...
acme.sh --issue --dns dns_aws \
  -d customer.co.kr -d '*.customer.co.kr' \
  --keylength ec-256 \
  --server letsencrypt

# 설치(배포)는 발급과 분리한다. reloadcmd가 핵심.
acme.sh --install-cert -d customer.co.kr --ecc \
  --key-file       /etc/nginx/tls/customer.key \
  --fullchain-file /etc/nginx/tls/customer.crt \
  --reloadcmd      "systemctl reload nginx"

    90일 인증서를 기준으로 renewBefore: 720h(30일)를 넣어 둔 cert-manager 설정이 있다고 합시다. 여기에 47일짜리 인증서가 들어오면 남은 기간의 절반 이상이 이미 지난 상태로 발급되는 셈이라 발급하자마자 갱신 조건을 만족합니다. 발급 → 즉시 갱신 → 발급의 무한 루프가 돌고, CA 발급 한도에 걸려 결국 인증서를 못 받게 됩니다. 해법은 절대 시간 대신 비율을 쓰는 것입니다. cert-manager 1.13+는 renewBeforePercentage를 지원합니다.

CA가 배포하는 폐기 목록 파일. 클라이언트가 주기적으로 받아 확인합니다. 목록이 커지는 문제가 있었지만 최근 다시 주력으로 돌아왔습니다.

인증서 한 장의 상태를 실시간 조회하는 방식. 사생활·지연 문제로 퇴조 중이며 Let's Encrypt는 OCSP를 더 이상 지원하지 않고 CRL만 제공합니다.

expiry-check.sh — 크론으로 매일 실행


#!/usr/bin/env bash
# 대상 목록: host:port 형식, SNI는 host와 동일하다고 가정
TARGETS="shop.customer.co.kr:443 api.customer.co.kr:443 mail.customer.co.kr:465"
WARN_DAYS=21

for t in $TARGETS; do
  host="${t%%:*}"; port="${t##*:}"
  end=$(echo | openssl s_client -connect "$t" -servername "$host" 2>/dev/null \
        | openssl x509 -noout -enddate 2>/dev/null | cut -d= -f2)

  if [ -z "$end" ]; then
    echo "[CRIT] $t 접속 또는 인증서 조회 실패"; continue
  fi

  left=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))
  if   [ "$left" -lt 0 ];            then echo "[CRIT] $t 이미 만료됨 ($end)"
  elif [ "$left" -lt "$WARN_DAYS" ]; then echo "[WARN] $t ${left}일 남음"
  else                                    echo "[ OK ] $t ${left}일 남음"
  fi
done

14mTLS — 양쪽이 서로를 증명하기

  
일반 TLS는 클라이언트가 서버만 확인합니다. mTLS는 서버도 클라이언트의 인증서를 요구합니다. 네트워크 위치가 아니라 신원으로 접근을 통제하는 제로 트러스트의 기본 도구입니다.


  

    
실습mTLS 검증 랩

    
클라이언트와 서버의 조건을 바꿔가며 어느 쪽에서 왜 거절되는지 확인합니다. mTLS 장애의 90%가 여기 있는 다섯 가지 중 하나입니다.

    

    

      

      

        

          
핸드셰이크 결과

          

        

        

      

    

  


  

    
클라이언트 인증서
클라이언트가 자기 신원을 증명하려고 제시하는 인증서. EKU에 clientAuth가 있어야 합니다.

    
CA 번들 (truststore)
상대 인증서를 검증할 때 신뢰 기준으로 삼는 CA 목록. mTLS에서는 서버에도 클라이언트 CA 번들이 필요합니다. 이 파일을 안 넣어서 실패하는 경우가 가장 많습니다.

    
SPIFFE ID
spiffe://cluster.local/ns/prod/sa/orders 형태의 워크로드 신원 표준. 인증서 SAN의 URI 항목에 담기며, 사람이 아니라 워크로드를 위한 신원 체계입니다.

    
인증 vs 인가
mTLS는 "당신이 누구인지"만 증명합니다(인증). "무엇을 해도 되는지"(인가)는 별도 정책이 결정합니다. mTLS만 켜고 인가 정책을 안 만들면 메시 안의 모든 서비스가 서로 호출 가능한 상태가 됩니다.

    
CRL/OCSP in mTLS
클라이언트 인증서 폐기 확인은 구현이 까다롭습니다. 대안은 역시 짧은 수명입니다.

nginx 클라이언트 인증 설정


server {
    listen 443 ssl;
    server_name api.internal.customer.co.kr;

    ssl_certificate     /etc/nginx/tls/server-fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/server.key;

    # 클라이언트 인증서를 검증할 CA 번들 (내부 CA의 루트+중간)
    ssl_client_certificate /etc/nginx/tls/internal-ca-bundle.pem;
    ssl_verify_client on;          # optional 로 두면 검증 실패해도 통과시킴
    ssl_verify_depth 2;            # 중간 CA 단계 수. 부족하면 검증 실패

    location / {
        # 인가에 활용: 어떤 클라이언트인지 백엔드에 전달
        proxy_set_header X-Client-DN $ssl_client_s_dn;
        proxy_set_header X-Client-Verify $ssl_client_verify;
        proxy_pass http://backend;

        # 특정 클라이언트만 허용하는 간단한 인가
        if ($ssl_client_s_dn !~ "CN=(orders|billing)-service") { return 403; }
    }
}

# --- Debian/Ubuntu ---
sudo cp internal-root.crt /usr/local/share/ca-certificates/internal-root.crt
sudo update-ca-certificates

# --- RHEL/Rocky/Amazon Linux ---
sudo cp internal-root.crt /etc/pki/ca-trust/source/anchors/
sudo update-ca-trust extract

# --- Java (JVM은 OS 저장소를 안 본다!) ---
keytool -importcert -alias internal-root -file internal-root.crt \
  -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit -noprompt
# 컨테이너라면 이미지 빌드 시점에 넣거나, JVM 옵션으로 별도 truststore 지정
# -Djavax.net.ssl.trustStore=/etc/pki/truststore.jks

# --- Python (requests/certifi도 OS 저장소를 안 본다) ---
export REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt
export SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt

# --- Node.js ---
export NODE_EXTRA_CA_CERTS=/etc/pki/internal-root.crt

# --- 컨테이너 이미지 (Dockerfile) ---
COPY internal-root.crt /usr/local/share/ca-certificates/
RUN update-ca-certificates

16워크로드 아이덴티티 — SPIFFE와 서비스메시

  
파드가 수시로 생겼다 사라지는 환경에서는 "서버 하나에 인증서 하나" 모델이 무너집니다. 워크로드마다 자동으로 신원을 발급하는 체계가 필요합니다.


  
SPIFFE는 워크로드 신원의 표준입니다. 각 워크로드는 spiffe://trust-domain/ns/네임스페이스/sa/서비스계정 형태의 ID를 받고, 이것이 인증서 SAN의 URI 항목에 담깁니다. 발급·회전은 전부 자동이고, 수명은 보통 수 시간에서 24시간입니다. 사람이 개입하지 않으니 이렇게 짧게 가져갈 수 있습니다.


  

    
방식신원 발급 주체적용 범위언제 고르나

    
      
cert-manager + 사내 CAcert-managerCertificate 리소스를 만든 워크로드일부 서비스만 mTLS가 필요할 때. 가장 가볍다

      
Istio (sidecar)istiod사이드카가 주입된 파드 전체L7 정책·트래픽 관리까지 필요할 때

      
Istio ambientistiod → ztunnel네임스페이스 라벨만으로 전체사이드카 없이 L4 mTLS만 먼저 깔고 싶을 때

      
Linkerdidentity 컴포넌트메시 가입 파드운영 단순성이 최우선일 때

      
SPIRESPIRE server/agentK8S 밖의 VM·베어메탈 포함클러스터 밖 워크로드까지 한 신원 체계로 묶을 때

    
  


  

    선택 가이드
    "mTLS를 하려면 서비스메시를 깔아야 한다"는 것은 오해입니다. 필요한 것이 서비스 간 암호화와 신원뿐이라면 cert-manager + 사내 CA로 충분하고 운영 부담도 훨씬 적습니다. 메시는 트래픽 분할, 재시도, 서킷브레이커, L7 인가 같은 기능까지 필요할 때 도입하세요. Istio를 새로 도입한다면 사이드카 대신 ambient 모드를 먼저 검토하는 것이 2026년 기준 합리적입니다. ztunnel이 노드 단위로 HBONE 터널 위에 mTLS를 걸어 파드마다 프록시를 붙이지 않습니다.

① 내부 ACME 서버

③ CA Issuer

    ACM의 일반 공인 인증서는 개인키를 내보낼 수 없습니다. 그래서 Istio 게이트웨이 파드나 nginx 인그레스처럼 클러스터 안에서 TLS를 종료해야 하는 구성에는 쓸 수 없습니다. 이 경우 ALB에서 종료하도록 아키텍처를 맞추거나, cert-manager로 별도 발급해야 합니다. 설계 초반에 "TLS를 어디서 풀 것인가"를 먼저 정해야 하는 이유입니다.

  duration: 168h                          # 7일
  renewBeforePercentage: 33

  


  

    종단간 암호화 조합
    규정상 파드까지 암호화가 필요한 경우 실무에서 가장 많이 쓰는 조합은 이렇습니다. 외부 구간은 ACM 인증서를 붙인 ALB에서 종료하고, ALB → 파드 구간은 AWS Private CA로 발급한 인증서로 다시 HTTPS를 겁니다. 이때 ALB는 백엔드 인증서를 엄격히 검증하지 않으므로, 진짜 신원 검증이 필요하면 파드 앞단(Envoy/Istio)에서 mTLS를 걸어야 합니다.
