두 번째 실행은 아무것도 바꾸지 않는다 플레이북 작성 — play·task·모듈 구조, 멱등성, handler·notify, check·diff, 태그, YAML 함정, 실습: 패키지·서비스·파일 관리

13편에서 ad-hoc 명령으로 한 일을 이제 파일로 남깁니다. 플레이북은 “어느 서버에(hosts), 무엇을, 어떤 순서로”를 적은 YAML 파일이고, 좋은 플레이북의 첫 번째 시험은 간단합니다. 두 번 연속 실행했을 때 두 번째는 changed=0이어야 한다. 이번 편은 그 시험을 통과하는 nginx 웹 서버 플레이북을 직접 쓰고, 설정이 바뀔 때만 다시 읽게 하는 핸들러, 바꾸기 전에 미리 보는 check·diff, 일부만 실행하는 태그, 그리고 들여쓰기 한 칸으로 권한이 엉망이 되는 YAML의 함정을 실제 실행 결과로 확인합니다.

1회차

ok=10 changed=7 — 설치·설정·시작·핸들러

2회차

ok=8 changed=0 — 아무것도 바꾸지 않음

설정이 틀렸을 때

검사 핸들러가 실패 → 다시 읽기 생략 → 서비스는 그대로 200

0들어가며

이번 편의 목표와 실습 지도

이번 편을 마치면

  • 플레이북 → 플레이 → 태스크 → 모듈 구조와 주요 키워드를 설명하고, 처음부터 끝까지 읽을 수 있는 플레이북을 씁니다.
  • YAML의 대표 함정(불리언·숫자·8진수·시간 해석, 따옴표, 콜론, 탭, 들여쓰기)을 실측으로 알고 피합니다.
  • 멱등성을 “상태를 선언하는 모듈”로 지키고, command·shell은 creates·changed_when으로 보완합니다.
  • handler·notify·listen의 실행 규칙(한 번, 끝에, 정의 순서, 실패 시)을 알고 “검사 후 다시 읽기” 패턴을 씁니다.
  • --check·--diff로 변경을 미리 보고, 점검 모드의 한계(지원하지 않는 모듈, 새 서버)를 다룹니다.
  • 태그로 일부만 실행하고, PLAY RECAP을 읽어 결과를 판단합니다.

1플레이북 해부

줄을 눌러 각 부분의 역할을 확인하세요 — 실습 플레이북의 앞부분입니다

줄을 선택하세요

플레이북은 플레이의 목록이고, 플레이는 “이 호스트들에 이 태스크들을”이라는 한 묶음입니다. 태스크는 모듈 하나를 호출합니다.

단위무엇비유
플레이북 (파일)플레이들의 목록 (YAML 리스트)작업 지시서 한 권
플레이대상 호스트 + 설정(become·vars) + 태스크 목록 + 핸들러“이 팀은 이 일을”
태스크모듈 하나의 호출 + 키워드(name·notify·tags·when…)작업 한 줄
모듈실제로 원격에서 실행되는 코드 (13편 2장)공구
핸들러notify를 받았을 때만, 플레이 끝에 실행되는 태스크“바뀐 게 있으면 마지막에 재시작”
실행 모델: 태스크 단위로 모든 호스트를 함께

기본 전략(linear)에서 Ansible은 태스크 1을 모든 대상 호스트에 실행하고(forks 수만큼 동시에), 모두 끝나면 태스크 2로 넘어갑니다. 그래서 출력도 “TASK [이름]” 아래에 호스트별 결과가 모여 나옵니다. 한 호스트가 실패하면 그 호스트는 이후 태스크에서 빠지고, 나머지 호스트는 계속 진행합니다(실패 정책은 20편).

2YAML의 함정

Ansible의 YAML 파서는 YAML 1.1 규칙을 따른다 — 그래서 생기는 일들

playbooks/types.yml (각 값이 어떤 타입이 되는지 출력)
- name: YAML 타입 함정
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    country: NO
    answer: yes
    version_a: 1.10
    version_b: "1.10"
    port: 08080
    mode_a: 0644
    mode_b: 644
    mode_c: "0644"
    when_time: 12:30
  tasks:
    - ansible.builtin.debug:
        msg: "{{ item }} = {{ lookup('vars', item) }} ({{ lookup('vars', item) | type_debug }})"
      loop: [country, answer, version_a, version_b, port, mode_a, mode_b, mode_c, when_time]
# 실측 (ansible-core 2.21.5)
country = False (bool)      # NO 는 노르웨이 국가 코드가 아니라 불리언 false!
answer = True (bool)        # yes/no/on/off 도 불리언
version_a = 1.1 (float)     # 1.10 은 숫자 1.1 → "버전 1.10"이 사라진다
version_b = 1.10 (str)
port = 08080 (str)          # 8진수로 해석할 수 없어 문자열이 됨
mode_a = 420 (int)          # 0644 는 8진수 → 10진수 420 (권한으로는 우연히 맞다)
mode_b = 644 (int)          # 644 는 10진수 644 → 권한으로는 완전히 틀린 값
mode_c = 0644 (str)
when_time = 750 (int)       # 12:30 은 60진수! 12×60+30

예측해 보기 — 값을 누르면 Ansible이 해석한 결과가 나옵니다

값을 선택하세요
# 실측: mode에 따옴표 없는 644 를 준 결과
--w----r-T 1 ansible ansible 2 … /tmp/mode_bad.txt    ← 권한이 엉망 (10진수 644 = 8진수 1204)
-rw-r--r-- 1 ansible ansible 2 … /tmp/mode_good.txt    ← mode: "0644"
함정실측 오류·결과규칙
값이 {{로 시작YAML parsing failed: This may be an issue with missing quotes around a template block.msg: "{{ var }}" — 템플릿으로 시작하면 반드시 따옴표
값 안의 : Colons in unquoted values must be followed by a non-space character.msg: "결과: 성공"
탭 문자Tabs are usually invalid in YAML.공백만. 편집기에서 탭을 공백 2칸으로 (2편 VS Code 설정)
모듈 인자의 들여쓰기 어긋남conflicting action statements: ansible.builtin.debug, msg (msg가 모듈 이름과 같은 깊이로 인식)인자는 모듈 이름보다 한 단계 깊게
파일 권한위 실측 --w----r-Tmode: "0644" 항상 문자열
버전·우편번호·전화번호1.10 → 1.1, 앞자리 0 손실숫자처럼 보이는 문자열은 따옴표
불리언 표기yes/no/on/off/NO가 불리언으로불리언은 true/false만, 문자열이면 따옴표 (ansible-lint의 yaml[truthy] 규칙)
여러 줄 문자열—|는 줄바꿈 유지(설정 파일), >는 한 줄로 접기(긴 명령·설명)

5멱등성의 실제 의미

“명령을 실행한다”가 아니라 “상태를 선언한다”

1편 5장에서 멱등성을 “몇 번을 실행해도 결과가 같은 성질”이라고 했습니다. Ansible에서 이것은 구체적으로 현재 상태를 먼저 확인하고, 원하는 상태와 다를 때만 바꾸고, 바꿨는지를 정직하게 보고하는 것입니다. 상태 기반 모듈(package state: present, file state: directory, copy, service state: started)은 이것을 스스로 합니다.

# 실측: 실습 플레이북 1회차와 2회차의 RECAP
node1 : ok=10  changed=7  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0     # 1회차
node1 : ok=8   changed=0  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0     # 2회차: 아무것도 바꾸지 않음
#        ↑ 2회차에 ok가 줄어든 이유: 바뀐 것이 없어 핸들러 2개가 실행되지 않았다
command를 멱등하게: creates · changed_when
- hosts: node1
  gather_facts: false
  tasks:
    - name: 처음 한 번만 실행 (creates)
      ansible.builtin.command:
        cmd: touch /tmp/initialized.flag
        creates: /tmp/initialized.flag
    - name: 조회 명령은 바꾸지 않았다고 알린다
      ansible.builtin.command: uptime
      changed_when: false
# 실측
1회차: changed: [node1]  ok: [node1]   → changed=1    (flag 파일이 없어서 실행)
2회차: ok: [node1]       ok: [node1]   → changed=0    (creates의 파일이 있어 건너뜀, uptime은 changed_when: false)
도구쓰는 때
creates: 경로 / removes: 경로그 파일이 있으면(없으면) 명령을 건너뜀. 초기화 스크립트처럼 한 번만 할 일
changed_when: false조회 명령(상태 확인, 버전 확인). 바꾸지 않는 명령이 CHANGED로 보고되는 것을 막는다
changed_when: "'Updated' in result.stdout"명령 출력으로 실제 변경 여부를 판단
failed_when반환 코드 대신 출력 내용으로 실패 판단 (실습의 응답 확인 태스크)
changed=0 이 목표인 이유

changed가 매번 0이 아니면 ① 핸들러가 매번 실행되어 서비스가 쓸데없이 재시작되고, ② “바뀐 것이 있다”는 신호가 소음이 되어 진짜 드리프트를 알아챌 수 없습니다(Terraform plan이 매번 변경을 보이는 것과 같은 문제, 4편 10장의 timestamp 함정). 2회차 changed=0은 13편부터 계속 쓸 품질 기준입니다.

6handler와 notify

“바뀐 것이 있을 때만, 마지막에, 한 번”

tasks:
  - name: (Debian 계열) 배포판 기본 사이트 끄기
    …
    notify: nginx 설정 변경          # ← 바뀌었을 때만 알린다
  - name: Nginx 사이트 설정
    …
    notify: nginx 설정 변경          # ← 두 태스크가 같은 주제를 알려도

handlers:
  - name: Nginx 설정 검사
    ansible.builtin.command: nginx -t
    changed_when: false
    listen: nginx 설정 변경          # ← 이 주제를 듣는 핸들러들이
  - name: Nginx 다시 읽기
    ansible.builtin.service: { name: nginx, state: reloaded }
    listen: nginx 설정 변경          #    handlers에 적힌 순서대로, 각각 한 번만 실행된다
규칙실측·설명
바뀐 경우에만태스크 결과가 changed일 때만 알림. 2회차에서는 핸들러가 전혀 실행되지 않았다
여러 번 알려도 한 번1회차: 두 태스크가 알렸지만 “Nginx 설정 검사”, “Nginx 다시 읽기”가 각각 한 번씩만 실행
실행 시점기본은 플레이(정확히는 각 태스크 구역)가 끝날 때. 중간에 실행하려면 - ansible.builtin.meta: flush_handlers
실행 순서notify한 순서가 아니라 handlers 섹션에 정의된 순서
listen핸들러 이름 대신 “주제”로 알린다. 여러 핸들러를 한 주제로 묶고, 핸들러 이름을 바꿔도 notify 쪽은 그대로
실패하면그 호스트에서 이후 태스크와 핸들러가 실행되지 않는다. 알림이 있었는데 플레이가 실패하면 핸들러가 실행되지 않은 채 끝날 수 있다 → --force-handlers 또는 플레이의 force_handlers: true
# 실측: 설정에 오류를 넣었을 때 (web_port="8080 bogus")
TASK [Nginx 사이트 설정]                → changed  (잘못된 설정 파일이 써짐)
RUNNING HANDLER [Nginx 설정 검사]       → fatal: nginx: [emerg] invalid parameter "bogus" in /etc/nginx/conf.d/iac-lab.conf:3
                                          (다음 핸들러 "Nginx 다시 읽기"는 실행되지 않음)
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/
200                                     ← 서비스는 이전 설정으로 정상 동작 중
“검사 후 다시 읽기”가 서비스를 지켰다

다시 읽기(reload) 전에 nginx -t를 같은 주제로 앞에 두었기 때문에, 잘못된 설정은 반영되지 않고 서비스는 계속 동작했습니다. 검사가 없었다면 reload가 실패하거나, 재시작(restart) 핸들러였다면 서비스가 내려간 채로 남았을 것입니다. 단, 잘못된 파일은 디스크에 남아 있으므로 고친 값으로 다시 실행해야 합니다(실측: 다음 실행에서 두 핸들러가 정상 실행, changed=2). 설정 파일 하나로 완결되는 경우에는 copy·template의 validate: 인자로 쓰기 전에 검사하는 방법도 있습니다(15편).

10실습: 웹 서버 플레이북

패키지 · 파일 · 서비스 · 핸들러 · 태그를 모두 담은 첫 플레이북

# 14편 실습: 패키지 · 파일 · 서비스를 관리하는 첫 플레이북
- name: 웹 서버 기본 구성
  hosts: lab
  become: true

  vars:
    web_port: 8080
    site_title: "iac-lab"
    site_root: /var/www/iac-lab

  tasks:
    - name: Nginx 패키지 설치
      ansible.builtin.package:
        name: nginx
        state: present
      tags: [packages]

    - name: (Debian 계열) 배포판 기본 사이트 끄기
      ansible.builtin.file:
        path: /etc/nginx/sites-enabled/default
        state: absent
      when: ansible_facts['os_family'] == "Debian"
      notify: nginx 설정 변경
      tags: [config]

    - name: 사이트 디렉터리
      ansible.builtin.file:
        path: "{{ site_root }}"
        state: directory
        owner: root
        group: root
        mode: "0755"
      tags: [content]

    - name: 첫 페이지
      ansible.builtin.copy:
        dest: "{{ site_root }}/index.html"
        content: |
          <h1>{{ site_title }}</h1>
          <p>server: {{ inventory_hostname }}</p>
        owner: root
        group: root
        mode: "0644"
      tags: [content]

    - name: Nginx 사이트 설정
      ansible.builtin.copy:
        dest: /etc/nginx/conf.d/iac-lab.conf
        content: |
          # Ansible이 관리하는 파일입니다. 직접 수정하지 마세요.
          server {
              listen {{ web_port }};
              root {{ site_root }};
              index index.html;
          }
        owner: root
        group: root
        mode: "0644"
      notify: nginx 설정 변경
      tags: [config]

    - name: Nginx 실행 및 부팅 시 자동 시작
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
      tags: [service]

    - name: 응답 확인
      ansible.builtin.uri:
        url: "http://127.0.0.1:{{ web_port }}/"
        return_content: true
      register: page
      failed_when: site_title not in page.content
      changed_when: false
      tags: [verify]

  handlers:
    # 같은 이름(listen)으로 묶인 핸들러는 handlers에 적힌 순서대로 실행된다
    - name: Nginx 설정 검사
      ansible.builtin.command: nginx -t
      changed_when: false
      listen: nginx 설정 변경

    - name: Nginx 다시 읽기
      ansible.builtin.service:
        name: nginx
        state: reloaded
      listen: nginx 설정 변경

12흔한 오류와 해결

플레이북을 쓰다 실제로 만나는 문제 15가지

13MSP 현장 팁

고객사 서버 구성을 플레이북으로 운영하기

변경 작업 표준 순서

① --syntax-check·ansible-lint ② --list-hosts로 대상 확인 ③ --check --diff 결과를 변경 요청서에 첨부 ④ 대표 서버 1대에 --limit으로 실행 ⑤ 전체 실행 ⑥ 한 번 더 실행해 changed=0 확인. Terraform의 plan → apply 흐름과 같은 리듬입니다.

재시작보다 다시 읽기

운영 서비스는 설정 변경 시 restart 대신 reload를 기본으로, 그 앞에 문법 검사 핸들러를 둡니다(6장 실측). 재시작이 꼭 필요한 변경(포트 변경 등)은 롤링(serial, 20편)으로 나눕니다.

“Ansible이 관리하는 파일” 표시

설정 파일 첫 줄에 관리 주석을 넣어 두면, 서버에 들어간 엔지니어가 손으로 고치는 일이 줄어듭니다. 손으로 고친 내용은 다음 실행에서 덮어써진다는 사실을 운영 규칙으로 공지합니다(9편 드리프트와 같은 원칙).

정기 실행 = 구성 드리프트 점검

플레이북을 매일 --check --diff로 돌리면, changed가 생긴 서버와 그 차이가 곧 구성 드리프트 보고서가 됩니다. 실제 적용은 승인 후에. 12편의 드리프트 워크플로와 같은 구조로 CI에 넣을 수 있습니다(22편).

위험한 작업은 never 태그

데이터 초기화, 캐시 삭제, 강제 재시작 같은 태스크는 tags: [never, reset]으로 두어 명시적으로 --tags reset을 줄 때만 실행되게 합니다. 실수로 전체 실행에 섞이지 않습니다.

YAML 규칙을 팀 표준으로

불리언은 true/false, 권한·버전은 따옴표, FQCN, 이름 필수. ansible-lint와 2편의 pre-commit에 넣어 사람이 기억하지 않아도 되게 합니다. 2장의 mode: 644 같은 실수는 보안 점검에서 권한 이상으로 발견되곤 합니다.

playbooks/time.yml을 작성하세요: chrony 패키지 설치, /etc/chrony/chrony.conf(Ubuntu)·/etc/chrony.conf(Rocky)에 사내 NTP 서버 한 줄 보장(lineinfile), 바뀌면 chrony 재시작(핸들러), 서비스 활성화. 2회차 changed=0과 ansible-lint 통과가 완료 조건입니다.

힌트

경로가 배포판마다 다르므로 when: ansible_facts['os_family'] == "Debian"으로 태스크를 둘로 나누거나, 15편에서 배울 변수로 경로를 고르는 방법이 있습니다. 서비스 이름도 Ubuntu는 chrony, Rocky는 chronyd입니다.

과제 2. flush_handlers로 순서 다듬기

실습 플레이북의 서비스 시작 태스크 바로 앞에 - name: 설정 변경 반영 ansible.builtin.meta: flush_handlers를 넣고 새 노드(또는 nginx를 지운 노드)에 실행해, 1회차 출력에서 핸들러가 어디에서 실행되는지 비교하세요. 서비스가 아직 없을 때 “다시 읽기” 핸들러는 어떻게 될까요?

해설

패키지 설치 직후 Debian은 서비스를 자동 시작하므로 다시 읽기가 성공하지만, Rocky는 설치만 하고 시작하지 않아 reload가 실패할 수 있습니다. 그래서 순서는 “설치 → 설정 → 서비스 시작(enabled, started) → 마지막에 핸들러(검사 → 다시 읽기)”가 일반적으로 더 안전합니다. flush_handlers는 그 사이에 반드시 반영되어야 하는 변경(예: 다음 태스크가 새 설정에 의존)이 있을 때 씁니다.

과제 3. never 태그로 초기화 태스크

사이트 디렉터리를 비우는 “콘텐츠 초기화” 태스크를 tags: [never, reset]로 추가하고, 일반 실행에서는 실행되지 않고 --tags reset에서만 실행되는지 확인하세요. --tags reset만 줬을 때 다른 태스크는 어떻게 되나요?

과제 4. YAML 함정 찾기

다음 줄들의 결과를 예측한 뒤 2장의 types.yml에 넣어 확인하세요: zip: 01234, ratio: 1:2, flag: Off, ver: 2.0, id: 1e3, name: ~.

힌트

앞자리 0의 숫자 처리, 콜론이 포함된 60진수, 대소문자를 가리지 않는 불리언, 실수 정규화, 지수 표기, ~는 null입니다. 직접 실행해 보는 것이 가장 정확합니다.

과제 5. 응답 확인을 check 블록처럼

11편의 Terraform check 블록처럼 “실패해도 플레이를 멈추지 않고 경고만” 하도록 응답 확인 태스크를 바꿔 보세요. 어떤 키워드 조합이 필요하고, 그 대가는 무엇인가요?

해설

ignore_errors: true로 RECAP의 ignored로 남기거나, 15편의 block/rescue로 실패 시 알림만 보내는 방법이 있습니다. 대가는 실패가 조용히 묻힐 수 있다는 것 — 정기 실행 결과에서 ignored를 반드시 확인하는 규칙이 필요합니다.
