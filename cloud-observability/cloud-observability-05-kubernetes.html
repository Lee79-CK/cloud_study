Cloud 모니터링·로깅 실전 강의 5편 (Level 2. 메트릭과 알림)

Kubernetes 모니터링

3편에서 손으로 하던 일, 곧 타깃 목록 관리, 설정 파일 배포, 규칙 검증을 Kubernetes에서는 Operator가 대신합니다. 대신 "왜 내 ServiceMonitor가 수집되지 않지?"라는 새로운 질문이 생깁니다. 그 질문부터 풀어 봅니다.

대상: 1~2년차 클라우드 엔지니어 형식: 개념 + 실습 6개 예상 소요: 4시간 기준: kube-prometheus-stack 92.x, Operator v0.94
ServiceMonitor 매칭 디버거현장에서 가장 흔한 질문, "ServiceMonitor를 만들었는데 Targets에 안 보여요"를 단계별로 진단합니다. 설정을 바꿔 가며 어느 단계에서 끊기는지 확인하세요.

0시작하기 전에

Level 2의 세 번째 편입니다. 2편의 kind 클러스터 두 개(edge, hub)를 처음으로 본격 사용합니다.

학습 목표

  1. VM 모니터링과 Kubernetes 모니터링의 차이(동적 타깃, 메타데이터 라벨, 수명이 짧은 파드)를 설명할 수 있다.
  2. node-exporter, cAdvisor, kube-state-metrics, 컨트롤 플레인, 애플리케이션이라는 다섯 메트릭 출처를 구분하고 질문에 맞는 출처를 고를 수 있다.
  3. Prometheus Operator의 조정 루프와 CRD(Prometheus, ServiceMonitor, PodMonitor, PrometheusRule 등)의 선택 규칙을 이해하고, 수집되지 않는 ServiceMonitor를 단계별로 진단할 수 있다.
  4. kube-prometheus-stack을 고객사 표준 values로 설치하고, kind와 관리형 클러스터에서 컨트롤 플레인 메트릭이 다르게 보이는 이유를 설명할 수 있다.
  5. AKS, EKS, OpenShift의 관리형·내장 모니터링과 오픈소스 스택을 어떻게 공존시킬지 판단할 수 있다.
  6. 컨테이너 CPU 스로틀링, OOMKilled, 재시작, Pending을 PromQL로 찾아낼 수 있다.

가장 많이 헷갈리는 둘: cAdvisor와 kube-state-metrics

cAdvisor는 실제로 쓰고 있는 양(사용량)을, kube-state-metrics는 Kubernetes에 적어 둔 것(명세와 상태)을 알려 줍니다. kube-state-metrics는 컨테이너 안을 들여다보지 않고 API 서버의 오브젝트만 읽어 메트릭으로 바꿔 줄 뿐입니다. 그래서 "요청량 대비 실제 사용률"은 언제나 두 출처를 나눠서 구합니다(Lab 6).

메모리는 왜 working_set인가

cAdvisor에는 메모리 메트릭이 여러 개 있습니다(usage, rss, cache, working_set). kubelet이 메모리 압박 때 파드를 쫓아낼지(eviction) 판단하는 기준이 working set이고, OOM에 가까운지도 이 값으로 봅니다. usage에는 언제든 비울 수 있는 페이지 캐시가 섞여 있어 실제보다 커 보입니다.

3Prometheus Operator와 CRD

Operator는 "원하는 상태"를 적은 리소스를 지켜보다가, 실제 상태를 그에 맞게 고치는 컨트롤러입니다. Prometheus Operator는 Prometheus 설정 파일을 사람 대신 써 주는 Operator입니다.

조정 루프

1단계

사용자가 리소스를 적용

kubectl apply -f servicemonitor.yaml. 사람이 하는 일은 여기까지입니다.

2단계

Operator가 변화를 감지

Prometheus 리소스의 선택 조건(selector)에 맞는 ServiceMonitor, PodMonitor, PrometheusRule을 모읍니다.

3단계

설정 생성

모은 리소스를 Prometheus 설정 파일과 규칙 파일로 변환해 Secret과 ConfigMap에 씁니다. 3편에서 손으로 쓰던 scrape_configs와 relabel_configs가 여기서 자동으로 만들어집니다.

4단계

config-reloader가 적용

Prometheus 파드 안의 사이드카 컨테이너가 바뀐 파일을 보고 Prometheus에 다시 읽기를 요청합니다. 3, 4편의 prom-push-config.sh가 하던 일입니다.

5단계

Prometheus가 수집 시작

새 타깃이 Targets 화면에 나타납니다. 보통 1~2분 안에 일어납니다.

대신 3, 4편에 있던 검증 게이트가 사라졌다는 점에 주의하세요. 잘못된 PrometheusRule도 그대로 적용됩니다. kube-prometheus-stack은 이를 막으려고 PrometheusRule을 검사하는 승인 웹훅(admission webhook)을 함께 설치하며, Lab 5에서 이 웹훅이 문법 오류를 거부하는 모습을 봅니다. 규칙의 숫자가 맞는지 보는 단위 테스트는 여전히 CI에서 promtool로 해야 합니다.

선택 규칙: 두 겹의 필터

ServiceMonitor가 수집되려면 두 겹의 필터를 모두 통과해야 합니다. 히어로의 디버거가 바로 이 구조입니다.

  1. Prometheus가 Monitor를 고르는 필터: Prometheus 리소스의 serviceMonitorSelector(ServiceMonitor의 라벨)와 serviceMonitorNamespaceSelector(ServiceMonitor가 있는 네임스페이스의 라벨).
  2. Monitor가 Service를 고르는 필터: ServiceMonitor의 spec.selector(Service의 라벨)와 spec.namespaceSelector(Service가 있는 네임스페이스). 그리고 endpoints[].port가 Service 포트의 이름과 같아야 합니다.
kube-prometheus-stack의 release 라벨 함정

차트 기본값은 serviceMonitorSelectorNilUsesHelmValues: true입니다. 이 상태에서는 Prometheus가 release: <Helm 릴리스 이름> 라벨이 붙은 ServiceMonitor만 고릅니다. 다른 팀이 만든 ServiceMonitor나 다른 차트가 설치한 ServiceMonitor가 조용히 무시되는, 가장 흔한 원인입니다. 이 시리즈에서는 이 값을 false로 바꿔 모든 Monitor를 고르게 하고, 대신 접근 통제는 네임스페이스와 RBAC로 합니다. 반대로 한 클러스터에 Prometheus를 여러 개 두고 Monitor를 나눠 맡긴다면 라벨 선택을 의도적으로 씁니다.

왜 컨트롤 플레인 일부를 끄나

kind는 컨트롤러 매니저, 스케줄러, etcd, kube-proxy의 메트릭 포트를 노드의 127.0.0.1에만 열어 둡니다. 그대로 설치하면 이 네 타깃이 DOWN으로 남고, 관련 기본 알림(예: "스케줄러가 사라졌다")이 계속 울립니다. 클러스터를 만들 때 bind 주소를 바꾸는 방법도 있지만, 여기서는 끄는 쪽을 택했습니다. 실제 AKS, EKS, GKE도 같은 상황이기 때문입니다. 관리형 Kubernetes는 컨트롤 플레인을 클라우드 사업자가 운영하므로 스케줄러나 etcd 메트릭을 고객이 직접 수집할 수 없고(API 서버는 대부분 가능), 사업자의 모니터링 서비스로만 일부를 볼 수 있습니다. 고객사 클러스터 유형마다 이 목록을 다르게 가져가는 것이 MSP 표준 values의 핵심입니다.

5관리형 서비스와 OpenShift

MSP가 맡는 고객사 클러스터에는 이미 클라우드 사업자나 플랫폼의 모니터링이 깔려 있는 경우가 많습니다. 오픈소스 스택을 그대로 덮어쓰면 안 되는 이유와 공존 방법을 정리합니다.

플랫폼제공되는 것수집 대상 선언 방식MSP 판단 포인트
AKSAzure Monitor managed service for Prometheus. 클러스터에 ama-metrics 수집기가 설치되고, 저장과 조회는 Azure Monitor 작업 영역오픈소스와 같은 모양의 PodMonitor, ServiceMonitor를 쓰되 API 그룹만 azmonitoring.coreos.com/v1. 간단한 경우 파드 어노테이션도 지원같은 클러스터에 kube-prometheus-stack을 함께 둘 수 있음(API 그룹이 달라 CRD가 충돌하지 않음). 다만 같은 대상을 두 번 수집하는 비용을 따지고, 애드온이 띄우는 node-exporter와 차트의 node-exporter가 같은 호스트 포트(9100)를 쓰려다 충돌하지 않는지 확인. 충돌하면 한쪽을 끔
EKSAmazon Managed Service for Prometheus(AMP). 클러스터 밖에서 동작하는 에이전트 없는 관리형 수집기(managed collector) 또는 고객이 운영하는 수집기에서 Remote Write관리형 수집기는 Prometheus 호환 scrape 설정을 API로 등록. ServiceMonitor CRD를 그대로 읽지는 않음관리형 수집기는 클러스터, 수집기, 작업 영역이 같은 계정과 리전에 있어야 하는 제약이 있음. 기존 ServiceMonitor 자산이 많으면 클러스터 안에 Prometheus Agent나 Alloy를 두고 AMP로 Remote Write하는 구성이 흔함
GKEGoogle Cloud Managed Service for Prometheus자체 CRD(PodMonitoring, ClusterPodMonitoring, API 그룹 monitoring.googleapis.com)CRD 이름과 필드가 달라 ServiceMonitor를 변환해야 함
OpenShiftCluster Monitoring Operator가 관리하는 내장 스택(openshift-monitoring: Prometheus, Thanos Querier, Alertmanager). 사용자 워크로드 모니터링을 켜면 openshift-user-workload-monitoring에 별도 Prometheus오픈소스와 같은 monitoring.coreos.com의 ServiceMonitor, PodMonitor, PrometheusRule을 사용자 네임스페이스에 만듦커뮤니티 Prometheus Operator를 별도로 설치하는 것은 지원되지 않음. 같은 CRD를 두 Operator가 다투게 됨. 내장 스택을 쓰고, 중앙으로 보낼 때는 내장 스택의 Remote Write 설정을 씀

OpenShift에서 사용자 워크로드 모니터링은 openshift-monitoring 네임스페이스의 ConfigMap 하나로 켭니다.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true

그 뒤에는 이 강의의 Lab 3~5에서 만드는 ServiceMonitor, PodMonitor, PrometheusRule을 거의 그대로 사용자 네임스페이스에 적용할 수 있습니다. 차이는 Prometheus 리소스와 values를 직접 다루지 않는다는 점, 그리고 release 같은 선택 라벨이 필요 없다는 점입니다.

sum by (service) (rate(shop_http_requests_total[5m]))
이상한 결과 frontend, cart, payment 세 줄이 아니라 {service="lab-app"} 한 줄, 값은 약 62(두 파드 × 31)가 나옵니다.

무슨 일이 일어났나: exported_service

count by (service, exported_service) (shop_http_requests_total)

ServiceMonitor로 수집하면 Operator가 모든 시계열에 Kubernetes Service 이름을 service 라벨로 붙입니다(타깃 라벨). 그런데 lab-app도 자기 메트릭에 service 라벨(frontend, cart, payment)을 붙여 보냅니다. 같은 이름의 라벨이 충돌하면 Prometheus는 기본적으로 타깃 라벨을 살리고, 애플리케이션이 보낸 쪽을 exported_service로 이름을 바꿔 보관합니다. 그래서 sum by (service)가 전부 "lab-app"으로 묶였습니다.

VM에서는 타깃 라벨에 service가 없어서 생기지 않던 문제입니다. 실제로 job, instance, namespace, pod, service, container 같은 이름을 애플리케이션이 쓰고 있으면 Kubernetes로 옮기는 순간 대시보드와 알림이 조용히 깨집니다. 작성자가 Prometheus 3.13.1로 같은 상황을 재현해 확인한 동작입니다.

해결 방법설정대가
애플리케이션 라벨 우선endpoint에 honorLabels: trueKubernetes의 service 라벨(lab-app)은 사라짐. job 라벨로 대신 구분
쿼리에서 exported_service 사용설정 변경 없음VM과 Kubernetes에서 쿼리와 Recording Rule이 달라짐
애플리케이션 라벨 이름 변경앱 코드에서 service 대신 app_service 등가장 깨끗하지만 앱 팀의 수정이 필요

이 랩에서는 4편의 쿼리와 Recording Rule을 그대로 쓰기 위해 첫 번째를 택합니다. 실무에서는 신뢰하는 애플리케이션에만 honorLabels를 켭니다. 이 옵션은 애플리케이션이 namespace나 job 같은 라벨을 마음대로 덮어쓰게 허용하기 때문입니다.

# 버전과 track으로 나눠 보기 (4편 21번의 group_left, 짝 기준은 이제 pod)
sum by (version, track) (
  rate(shop_http_requests_total{namespace="shop", service="payment", status=~"5.."}[5m])
  * on (pod, service) group_left (version) shop_build_info{namespace="shop"}

VM에서는 on (instance, service)로 짝을 지었지만, Kubernetes에서는 instance가 파드 IP라 재시작마다 바뀌므로 pod로 짝을 짓습니다. 이렇게 "카나리의 오류율이 기존보다 높은가"를 쿼리로 만들어 두면, 배포 도구(Argo Rollouts, Flagger 등)가 자동으로 카나리를 중단하는 기준으로 쓸 수 있습니다.

10Lab 5. PrometheusRule

4편의 Recording Rule을 PrometheusRule 리소스로 옮기고, 승인 웹훅과 단위 테스트로 3, 4편의 검증 게이트를 Kubernetes 방식으로 되살립니다.

~/obs-lab/apps/shop/prometheusrule.yaml

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: shop-red
  namespace: shop
  labels: { app.kubernetes.io/part-of: shop }
spec:
  groups:
    - name: shop-red
      rules:
        - record: service:shop_http_requests:rate5m
          expr: sum by (service) (rate(shop_http_requests_total[5m]))
        - record: service:shop_http_errors:rate5m
          expr: |
            sum by (service) (rate(shop_http_requests_total{status=~"5.."}[5m]))
            or
            sum by (service) (rate(shop_http_requests_total[5m])) * 0
        - record: service:shop_http_errors_per_requests:ratio_rate5m
          expr: service:shop_http_errors:rate5m / service:shop_http_requests:rate5m
        - record: service_le:shop_http_request_duration_seconds_bucket:rate5m
          expr: sum by (service, le) (rate(shop_http_request_duration_seconds_bucket[5m]))
        - record: service:shop_http_request_duration_seconds:p99_5m
          expr: histogram_quantile(0.99, service_le:shop_http_request_duration_seconds_bucket:rate5m)

4편의 shop-red 그룹만 옮겼습니다. node-use 그룹은 옮기지 않습니다. kube-prometheus-stack의 기본 규칙에 instance:node_cpu_utilisation:rate5m 같은 같은 이름의 규칙이 이미 있어서, 다시 정의하면 같은 시계열을 두 규칙이 쓰려다 충돌합니다. 기본 규칙 목록은 kubectl get prometheusrule -n monitoring으로 확인할 수 있습니다.

kubectl --context kind-edge apply -f ~/obs-lab/apps/shop/prometheusrule.yaml
kubectl --context kind-edge -n shop get prometheusrule

1~2분 뒤 Prometheus의 Rule health 화면에 shop-red 그룹이 나타나고, Query 화면에서 service:shop_http_errors_per_requests:ratio_rate5m을 조회할 수 있습니다. Operator는 PrometheusRule마다 규칙 파일을 만들어 Prometheus 파드에 마운트합니다.

승인 웹훅: 문법 오류는 적용 단계에서 막힘

11Lab 6. 컨테이너 자원과 상태

cAdvisor와 kube-state-metrics를 조합해 Kubernetes 운영에서 가장 자주 보는 다섯 가지 문제(스로틀링, OOMKilled, 재시작, Pending, 레플리카 부족)를 직접 만들고 찾아냅니다.

핵심 쿼리

보고 싶은 것쿼리
네임스페이스별 CPU 사용량(코어)sum by (namespace) (rate(container_cpu_usage_seconds_total{container!="", container!="POD"}[5m]))
CPU 요청량 대비 사용률sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{namespace="shop", container!="", container!="POD"}[5m])) / sum by (namespace, pod) (kube_pod_container_resource_requests{namespace="shop", resource="cpu"})

CPU 스로틀링 비율sum by (namespace, pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="shop", container!=""}[5m])) / sum by (namespace, pod) (rate(container_cpu_cfs_periods_total{namespace="shop", container!=""}[5m]))

디플로이먼트 가용률kube_deployment_status_replicas_available{namespace="shop"} / kube_deployment_spec_replicas{namespace="shop"}
노드 압박 상태kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure", status="true"} == 1

container!=""는 cAdvisor가 파드 전체(cgroup)를 합쳐 내는 시계열을, container!="POD"는 일부 런타임에서 보이는 pause 컨테이너를 빼기 위한 조건입니다. 이 둘을 빼먹으면 같은 사용량이 두세 번 더해집니다. 4편 5장의 "짝 맞추기"가 여기서도 핵심입니다. cAdvisor와 kube-state-metrics는 라벨 구성이 달라서, 양쪽을 by (namespace, pod, container)로 같은 모양으로 만든 뒤 나눕니다.

12MSP 운영 관점 정리

랩에서 만든 values와 매니페스트를 고객사 클러스터 수십 개에 적용할 때 필요한 것들입니다.

values를 층으로 나누기

모든 고객사 클러스터에 같은 values를 쓸 수는 없지만, 클러스터마다 처음부터 쓰면 표준이 무너집니다. Helm은 -f를 여러 번 주면 뒤의 파일이 앞의 값을 덮어쓰므로, 공통, 플랫폼별, 고객사별 세 층으로 나눕니다.

helm upgrade --install kps prometheus-community/kube-prometheus-stack \
  -f values/base.yaml \            # 모든 클러스터: 선택자, 보존, 버전 고정, Grafana/Alertmanager 끔
  -f values/platform-aks.yaml \    # 플랫폼별: 컨트롤 플레인 on/off, StorageClass, node-exporter 충돌 회피
  -f values/cust-a-prod.yaml       # 고객사별: externalLabels, 자원 크기, 보존 기간

이번 편의 두 values 파일은 대부분 같고 externalLabels와 Service 노출만 다릅니다. 연습 삼아 공통 부분을 base.yaml로 빼 보세요. 15편에서 이 구조로 여러 고객사를 한꺼번에 다룹니다.

차트 업그레이드와 CRD

Helm은 차트를 업그레이드할 때 CRD를 갱신하지 않습니다. kube-prometheus-stack의 새 버전이 새 CRD 필드를 쓰는데 클러스터의 CRD가 옛날 것이면 설치가 실패하거나 필드가 조용히 무시됩니다. 방법은 두 가지입니다.

  • 업그레이드 전에 CRD를 먼저 적용: 차트 저장소의 charts/crds/crds/ 디렉터리에 있는 파일들을 kubectl apply --server-side로 적용한 뒤 helm upgrade. CRD 파일이 커서 일반 apply는 어노테이션 크기 제한에 걸리므로 --server-side가 필요합니다.
  • 차트의 CRD 업그레이드 작업 사용: values의 crds.upgradeJob.enabled: true. 작성 시점에는 미리보기(preview) 기능이라 기본으로 꺼져 있습니다.

또한 차트의 메이저 버전이 바뀔 때는 README의 업그레이드 안내를 반드시 읽습니다. 메이저 버전마다 CRD와 values 구조 변경이 따라오는 경우가 많습니다.

13트러블슈팅

증상을 눌러 원인과 해결 방법을 확인하세요.

ServiceMonitor를 만들었는데 Targets에 없음Lab 3

히어로 디버거의 순서대로 확인합니다. ① kubectl -n monitoring get prometheus kps-prometheus -o yaml | grep -A3 serviceMonitorSelector로 Prometheus가 어떤 라벨을 요구하는지 보고, kubectl get servicemonitor -A --show-labels와 비교합니다. ② serviceMonitorNamespaceSelector가 ServiceMonitor의 네임스페이스를 허용하는지. ③ ServiceMonitor의 selector가 Service 라벨과 맞는지 kubectl get svc --show-labels로 확인하고, Service가 다른 네임스페이스에 있으면 namespaceSelector가 필요합니다. ④ endpoints[].port가 Service 포트의 이름인지. ⑤ kubectl get endpoints에 파드 주소가 있는지(Ready가 아닌 파드는 빠짐). Prometheus의 Service discovery 화면에서 dropped로 보이면 ④, 아예 job이 없으면 ①~③입니다.

node-exporter 파드가 CrashLoopBackOff: "path / is mounted on / but it is not a shared or slave mount"macOS

macOS의 Docker Desktop처럼 노드 컨테이너의 루트 마운트 전파 방식이 맞지 않는 환경에서 생깁니다. values에 prometheus-node-exporter.hostRootFsMount.enabled: false를 추가하고 helm upgrade합니다. 파일시스템 메트릭 일부가 부정확해질 수 있지만 랩 진행에는 문제없습니다.

prometheus-kps-prometheus-0이 PendingLab 1, 2

kubectl -n monitoring get pvc로 PVC가 Pending인지 봅니다. StorageClass 이름이 맞지 않는 경우가 대부분입니다(kind는 standard, AKS는 managed-csi 등 플랫폼마다 다름). kubectl get storageclass로 이름을 확인해 values를 고칩니다. 메모리 요청량을 노드가 감당하지 못해도 Pending이 되므로 describe pod의 Events도 확인하세요.

helm install이 시간 초과, admission 관련 Job 실패Lab 1, 2

승인 웹훅용 인증서를 만드는 Job(kps-admission-create, kps-admission-patch)이 이미지를 받지 못했거나 이전 설치의 잔여물과 충돌한 경우입니다. kubectl -n monitoring get jobs,pods로 상태를 보고, 실패한 설치는 helm uninstall 후 남은 ValidatingWebhookConfiguration, MutatingWebhookConfiguration(이름에 kps 포함)을 지우고 다시 설치합니다.

sum by (service) 결과가 Service 이름 하나로 뭉침, exported_service 라벨이 보임Lab 3

애플리케이션의 라벨이 타깃 라벨과 충돌해 exported_ 접두어로 밀려난 것입니다. Lab 3의 세 가지 해결 방법 중 하나를 고릅니다. exported_job, exported_instance, exported_namespace도 같은 원리입니다.

PrometheusRule 적용이 거부됨: admission webhook ... denied the requestLab 5

의도된 동작입니다. 메시지에 포함된 PromQL 파싱 오류의 줄과 위치를 보고 고칩니다. 로컬에서 먼저 확인하려면 k8s-rule-test.sh로 같은 오류를 재현할 수 있습니다.

PrometheusRule을 적용했는데 Rule health에 그룹이 없음Lab 5

ruleSelectorNilUsesHelmValues가 true(기본값)인 Prometheus라면 release: kps 라벨이 없는 규칙은 무시됩니다. 또 ruleNamespaceSelector가 그 네임스페이스를 허용하는지 확인합니다. 반영까지 1~2분 걸리는 것도 기억하세요.

Rule health에 "duplicate sample for timestamp" 또는 같은 이름의 규칙 충돌Lab 5

기본 규칙과 같은 이름(instance:node_cpu_utilisation:rate5m 등)의 Recording Rule을 다시 정의한 경우입니다. 이름을 바꾸거나, 기본 규칙을 그대로 쓰세요. 기본 규칙 이름은 kubectl get prometheusrule -n monitoring -o yaml | grep "record:"로 확인합니다.

kubelet 타깃이 DOWN, 401 또는 403Lab 1

Prometheus의 ServiceAccount가 kubelet 메트릭을 읽을 권한이 없거나, kubelet의 인증서 검증 설정이 맞지 않는 경우입니다. kind에서는 드물고, 직접 구축한 클러스터에서 kubelet의 webhook 인증이 꺼져 있으면 생깁니다. 차트가 만든 ClusterRole이 있는지와 kubelet 설정의 authentication.webhook.enabled를 확인하세요.

helm upgrade 후 "unknown field" 또는 새 기능이 동작하지 않음운영

CRD가 갱신되지 않은 경우입니다. 12장의 방법으로 CRD를 먼저 적용한 뒤 다시 업그레이드합니다.

오늘의 핵심

  1. Kubernetes에서는 타깃을 API로 자동 발견하고, 메타데이터가 namespace, pod, service 같은 라벨이 됩니다. instance는 자주 바뀌므로 pod나 그 위의 단위로 묶습니다.
  2. 사용량은 cAdvisor, 명세와 상태는 kube-state-metrics, 노드는 node-exporter에서 옵니다. 요청량 대비 사용률은 두 출처를 같은 라벨 모양으로 맞춘 뒤 나눕니다.
  3. Prometheus Operator는 CRD를 설정으로 바꿔 주지만, ServiceMonitor는 Prometheus의 선택과 Monitor의 선택이라는 두 겹 필터를 모두 통과해야 수집됩니다. kube-prometheus-stack의 release 라벨 함정을 기억하세요.
  4. kind와 관리형 Kubernetes는 컨트롤 플레인 일부를 수집할 수 없으므로, 플랫폼별 values로 끄고 관련 규칙도 함께 끕니다.
  5. AKS는 다른 API 그룹의 같은 모양 CRD, EKS는 관리형 수집기나 Remote Write, OpenShift는 내장 스택의 사용자 워크로드 모니터링을 쓰고 커뮤니티 Operator를 따로 깔지 않습니다.
  6. VM에서 없던 라벨 충돌(exported_service)이 생기고, 검증 게이트는 승인 웹훅과 CI의 promtool로 나뉩니다. OOM은 사용량이 아니라 종료 이유와 재시작 수로 잡습니다.
