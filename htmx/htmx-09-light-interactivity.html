02

JS를 어디까지 쓸 것인가

hx-live 공식 문서는 판단 순서를 세 줄로 요약합니다. HTML로 되면 HTML, CSS로 표현을 끌어낼 수 있으면 HTML + CSS, 그래도 안 되면 hx-live. 이 시리즈는 여기에 통합 포털의 두 단계를 더해 다섯 단계로 씁니다.

1. HTML로 되는가? <details>, <dialog>, 폼 검증 속성(required, pattern), popover 속성. 되면 끝.
2. CSS로 표현을 끌어낼 수 있는가? :checked, :has(), [aria-expanded="true"] 선택자로 보이기·숨기기·강조.
3. 서버가 알아야 하는가? 상태 변경·권한·검증이 걸리면 htmx 요청 (Level 1의 영역).
4. 화면 안의 작은 상태인가? 클릭 한 번의 반응은 hx-on, 다른 요소에서 계산되는 값이면 hx-live. 이번 편의 영역.
5. 상태가 많고 서로 얽혀 있는가? 1편의 "하이퍼미디어가 안 맞는 경우". React·Vue 아일랜드 (12편 이후).

이 순서의 바탕에는 htmx 진영이 강조하는 동작의 지역성이 있습니다. 8편의 portal.js처럼 "모든 요청에 공통으로 적용되는 정책"은 한 파일에 두는 것이 맞지만, "이 버튼만의 동작"은 이 버튼에 붙어 있어야 읽기 쉽습니다. 이번 편의 도구들은 후자를 위한 것입니다.

03

hx-on

hx-on은 htmx 4 코어에 들어 있어 별도 설치가 필요 없습니다. 4.0.1 소스(#handleHxOnAttributes)가 지원하는 문법은 세 가지입니다.

문법예의미
hx-on:이벤트="코드"hx-on:click="…"DOM 이벤트에 코드 연결
hx-on::htmx이벤트="코드"hx-on::after:swap="…"콜론 두 개는 hx-on:htmx:의 줄임 (htmx 이벤트)
hx-on="트리거 -> 코드; 트리거 -> 코드"hx-on="click once -> …; blur -> …"여러 이벤트를 한 속성에. 트리거 부분은 hx-trigger 문법 그대로라 once, delay:, from: 같은 수식어를 쓸 수 있음

코드 안에서 쓸 수 있는 것

htmx는 코드를 async 함수로 만들어 실행하므로 await를 바로 쓸 수 있습니다. this는 그 요소, event는 이벤트 객체이고, 코드 전체가 with(event.detail)로 감싸져 htmx 이벤트라면 ctx를 이름만으로 씁니다. 여기에 htmx 메서드 전체(ajax, trigger, timeout, process, swap …)가 이름만으로 들어오고, find·findAll은 인자 하나만 주면 현재 요소 기준으로 찾습니다. 코드에서 예외가 나면 htmx:error 이벤트가 발생합니다(콘솔에도 기록).

hx-on 놀이터 (htmx 4.0.1 실동작)

각 카드의 코드가 그대로 동작
① 기본: this와 dataset
hx-on:click="this.dataset.n++;
  this.textContent = '눌림 ' + this.dataset.n + '회'"
② once 수식어 (트리거 문법)
hx-on="click once -> find('next .o').textContent = '…'"
③ await와 htmx.timeout
hx-on:click="this.disabled = true; …
  await timeout('1.2s'); this.disabled = false"
④ htmx 이벤트에서 ctx 고치기
hx-on::config:request="ctx.request.headers['X-From'] = 'hx-on'"
⑤ 요청 취소 (event.preventDefault)
hx-on::before:request="if (…) event.preventDefault()"
⑥ 예외 → htmx:error
hx-on:click="throw new Error('…')"
→ document의 htmx:error 리스너가 받음
문자열 코드는 결국 eval입니다

hx-on 코드는 htmx가 Function 생성자로 만듭니다. 콘텐츠 보안 정책(CSP)에서 'unsafe-eval'을 금지하면 동작하지 않으므로, 엄격한 CSP 환경에서는 hx-csp 확장과 함께 써야 합니다(17편). 또 서버가 사용자 입력을 hx-on 속성값 안에 그대로 넣으면 XSS가 됩니다. 랩의 "이름 복사" 버튼이 VM 이름을 코드에 직접 쓰지 않고 data-name 속성(Eta가 이스케이프)에서 읽는 이유입니다.

04

hx-live

hx-live는 htmx 4와 함께 나온 공식 확장입니다(배포본 dist/ext/hx-live.js, gzip 약 5.7KB). 공식 설명대로 jQuery·Alpine·hyperscript에서 영감을 받았고, 두 가지를 줍니다. 상태를 DOM 속성(data-*, aria-*, 클래스)에 두고 다루는 도우미, 그리고 DOM이 바뀌면 다시 계산되는 반응형 바인딩입니다.

설치 (htmx 다음에 불러오면 전역 등록)
<script src="/vendor/htmx/htmx.min.js"></script>
<script src="/vendor/htmx/ext/hx-live.js" defer></script>
기능예설명
:속성 (긴 표기 hx-live:속성):disabled="!q('#name').value"식의 결과를 속성에 씀. 불리언 속성은 참이면 추가, 거짓이면 제거
:text / :html:text="data.count"textContent / innerHTML (html은 반드시 정제)
:.클래스, :class, :style:.over="len > 500"클래스 하나 / 여러 개 / 스타일
hx-live="…"여러 줄 로직어떤 바인딩에도 맞지 않을 때의 탈출구
q(선택자)q('previous input'), q('.row').count요소 묶음 프록시. 읽기는 첫 요소, 쓰기는 전체. first·last·next·previous·closest·in 문법
data.*, aria.*, attr.*, class.*data.count++타입 있는 상태 읽기·쓰기. data는 가장 가까운 조상의 data-*를 찾음
toggle(), take()take('aria-selected')상태 전환 / 형제에게서 가져오기 (탭)
debounce(), forEvent(), nextFrame()await forEvent('transitionend', 500)비동기 도우미

도우미는 hx-live 식뿐 아니라 hx-on 안에서도 그대로 쓸 수 있습니다. 확장이 htmx의 스크립트 실행 범위에 자기 도우미를 넣기 때문입니다(소스의 htmx:scope 훅). 랩의 전체 선택 체크박스가 hx-on:change="q('#vm-body input[name=sel]').checked = this.checked"로 짧게 끝나는 것도 이 덕분입니다.

hx-live 놀이터 (htmx 4.0.1 + hx-live 실동작)

상태는 모두 DOM 속성에 있다. 개발자 도구로 확인해 보자
① data 상태와 :text·:disabled
<div data-count="0">
  <button hx-on:click="data.count++">
  <button :disabled="!data.count" …>
  <output :text="'count = ' + data.count">
② 탭: take('aria-selected')
hx-on:click="take('aria-selected')"
CSS: [role=tab][aria-selected="true"] { … }
③ 펼치기: aria-expanded
펼쳐진 내용. 버튼의 aria-expanded가 곧 상태.
:hidden="!q('previous .stage button').aria.expanded"
④ 선택 수 세기 (랩의 일괄 선택과 같은 구조)
:text="'선택 ' + q('#liveSel input:checked').count + '개'"
⑤ 입력과 :style
:style="`width:${q('previous .stage input').value}%`"
⑥ 응답이 스스로 사라지기 (공식 예제 응용)
응답: <span hx-on:load="await timeout('2s');
  this.textContent = '(사라짐)'">저장됨</span>
언제 다시 계산되나 (공식 문서)

hx-live는 문서 전체에 MutationObserver 하나를 두고, DOM 추가·삭제·속성·텍스트 변화와 입력 컨트롤의 input·change에 반응해 모든 식을 다시 계산합니다. htmx 스왑 중에는 계산을 멈췄다가 htmx:finally:swap 뒤에 한 번만 합니다. 그래서 랩에서 일괄 재시작 뒤 표가 다시 그려지자 배지가 "선택 0대"로, 알림 폼이 모핑된 뒤에도 미리보기 문장이 새 값으로 다시 계산됐습니다(측정). 반대로 hx-live가 볼 수 없는 JS 변수에 의존하는 식은 htmx.live.refresh()로 직접 다시 계산시켜야 합니다.

모핑은 data-* 상태를 덮어쓴다 (측정)

hx-live의 원칙은 "상태는 DOM에"입니다. 그런데 5편의 모핑은 서버 HTML 기준으로 속성을 맞춥니다. 실험에서 data-mode를 클라이언트에서 b로 바꾼 뒤 outerMorph를 하자 서버 HTML의 a로 돌아갔습니다. 공식 문서도 같은 점을 지적하며 htmx.config.morphIgnore에 "data-" 같은 접두사를 넣으라고 안내합니다. 모핑되는 영역 안에 클라이언트 상태를 둘 때는 이 설정이나, 모핑되지 않는 조상 요소에 상태를 두는 방법 중 하나를 고르세요.

05

Alpine.js와 함께

이미 Alpine을 쓰는 화면을 포털에 통합해야 할 수도 있습니다. Alpine 3.17.5(2026-10-20)는 그대로 htmx와 함께 동작하지만, 모핑과 만나면 문제가 생깁니다. 아래 두 상자는 각각 독립된 iframe 안에서 htmx 4.0.1 + Alpine 3.17.5를 실행합니다. 오른쪽만 hx-alpine-compat 확장을 더했습니다.

Alpine + outerMorph 비교 (실동작)

+를 세 번 → 서버가 영역을 다시 그림(outerMorph) → +를 한 번
hx-alpine-compat 없음
hx-alpine-compat 있음
+3회 후모핑 직후 화면+1회 후
compat 없음 (측정)30 (서버 HTML의 글자로 덮임, Alpine 상태는 3 그대로)4 (화면과 상태가 어긋남)
compat 있음 (측정)334

확장 소스를 보면 이유가 보입니다. hx-alpine-compat는 htmx의 htmx:before:morph:node 훅에서 기존 노드의 Alpine 데이터 스택을 새 노드에 넘기고 Alpine.cloneNode()로 바인딩을 이어 주며, 스왑 동안 Alpine의 DOM 변경 처리를 미뤘다가(deferMutations) 스왑이 끝나면 한 번에 처리합니다. innerHTML 스왑으로 새로 들어온 x-data 요소는 두 경우 모두 Alpine이 알아서 초기화했습니다(측정).

hx-live와 Alpine은 한 페이지에서 :를 다툰다

두 도구 모두 :속성 짧은 표기를 씁니다. hx-live는 초기화 때 Alpine이 있으면 짧은 표기를 끄고 경고를 남기며(측정: hx-live: Alpine detected; set config.live.bindPrefix.), 이 경우 hx-live:text처럼 긴 표기만 동작합니다. 공식 문서는 config.live.bindPrefix를 ""(긴 표기만)나 "hx:"로 명시하라고 안내합니다. 포털 전체에서 두 도구를 섞기보다, 기본은 hx-on + hx-live로 하고 Alpine은 "이미 Alpine으로 만든 레거시 화면"에 한정하는 편이 단순합니다.

증상원인해결

    
      
hx-on:click.once가 동작 안 함속성 이름에는 수식어를 붙일 수 없음hx-on="click once -> …"

      
htmx 이벤트용 hx-on이 안 불림hx-on:after:swap(콜론 하나)은 DOM 이벤트 "after:swap"을 기다림hx-on::after:swap 또는 hx-on:htmx:after:swap

      
:text 바인딩이 그대로 글자로 보임hx-live 확장을 불러오지 않음 (코어 아님)ext/hx-live.js 추가

      
Alpine이 있는 페이지에서 :text가 안 됨hx-live가 Alpine을 감지해 짧은 표기를 끔hx-live:text 또는 config.live.bindPrefix

      
모핑 후 클라이언트에서 바꾼 data-* 값이 되돌아감모핑이 서버 HTML로 속성을 맞춤morphIgnore: ["data-"] 또는 모핑되지 않는 조상에 상태

      
Alpine 숫자가 모핑 후 0으로 보이다가 다음 클릭에 4로 튐모핑이 x-text 글자를 서버 값으로 덮고 Alpine 상태는 유지hx-alpine-compat 확장

      
hx-live 식에서 fetch가 끝없이 반복식은 DOM이 바뀔 때마다 다시 실행됨debounce(), 값이 바뀔 때만 실행하도록 조건

      
엄격한 CSP 환경에서 hx-on·hx-live가 모두 동작 안 함문자열 코드 실행에 eval 필요hx-csp 확장 (17편)

      
hx-on 코드에 서버 데이터를 넣었더니 XSS속성값 안 문자열 이스케이프 문제데이터는 data-* 속성에, 코드는 그것을 읽기만

정리와 다음 편

  
    
    
  1. 판단 순서: HTML → CSS → (서버가 알아야 하면) htmx 요청 → (작은 화면 상태면) hx-on·hx-live → (얽힌 상태면) React·Vue 아일랜드.
    2. 
    
  2. hx-on은 코어 기능이다. hx-on:이벤트, hx-on::htmx이벤트, hx-on="트리거 -> 코드". 코드는 async이며 this·event·ctx·htmx 메서드를 바로 쓴다.
    3. 
    
  3. hx-live는 공식 확장이다. 상태는 DOM(data-*·aria-*)에 두고 :속성으로 파생 값을 그린다. 스왑이 끝나면 한 번 다시 계산하며, 모핑은 data-*를 덮어쓰니 주의한다.
    4. 
    
  4. Alpine은 htmx와 함께 동작하지만 모핑이 섞이면 hx-alpine-compat가 필요하고, hx-live와는 : 표기를 두고 충돌한다.
    5. 
    
  5. 어떤 클라이언트 도구를 쓰든 상태 변경의 최종 판단은 서버다.
    6.
