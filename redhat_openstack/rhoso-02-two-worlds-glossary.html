2편두 세계의 언어 번역표

RHOSO 운영자는 하루에도 수십 번 OpenStack 말과 OpenShift 말을 섞어 씁니다. 문제는 같은 단어가 두 세계에서 전혀 다른 뜻이라는 것. 이 편은 그 두 언어의 사전이자 문법책입니다.

섹션 1

이 편의 목표와 읽는 법

이 편을 마치면 다음을 할 수 있어야 합니다.

  1. OpenStack 사용자 어휘(프로젝트, 인스턴스, 플레이버, 플로팅 IP, 보안 그룹, 토큰, 서비스 카탈로그 등)를 정확한 뜻과 예시 명령으로 설명한다.
  2. OpenShift 어휘(Namespace, Pod, Deployment, Service, Route, CR, OLM, NMState, MetalLB 등)를 RHOSO에서 쓰이는 맥락으로 설명한다.
  3. 두 세계의 개념을 1:1로 짝지어 비교하고, 차이가 나는 지점을 말한다.
  4. 같은 단어인데 뜻이 다른 단어(Project, Service, Operator, Node, Image, Network…)를 문맥으로 구분한다.
  5. 장애 보고 한 문장을 듣고 어느 층(OpenStack / OpenShift / RHEL 호스트 / Operator·CR)의 문제인지 분류한다.

읽는 법

  • 보라색 점선 밑줄 용어는 누르면 쉬운 설명이 뜹니다. 맨 아래 용어 사전에서 검색할 수 있습니다.
  • 색 규칙은 1편과 같습니다. 코랄 = OpenStack, 청록 = OpenShift, 호박색 = RHEL 호스트·데이터 플레인, 보라 = 용어·두 세계를 잇는 것.
  • 이 편은 “외우는 편”이 아니라 “찾아보는 편”입니다. 한 번 끝까지 읽은 뒤, 이후 편을 공부하다 헷갈릴 때마다 돌아와 검색하세요.

섹션 2

왜 번역표가 필요한가

RHOSO 운영팀의 메신저에는 이런 문장이 매일 올라옵니다.

실제로 듣게 될 문장

“openstack 프로젝트에 있는 nova 서비스 Pod가 재시작됐는데, 고객 프로젝트의 인스턴스는 멀쩡하고, compute 서비스는 up이에요. 이미지는 새 이미지로 바뀌었고요.”

이 한 문장에 “프로젝트”가 두 번, “서비스”가 두 번, “이미지”가 두 번 나오는데 각각 뜻이 다릅니다.

  • 첫 번째 “openstack 프로젝트”는 OpenShift의 Namespace(이름이 openstack인 OCP 프로젝트)이고, 두 번째 “고객 프로젝트”는 OpenStack의 테넌트입니다.
  • “nova 서비스 Pod”의 서비스는 OpenStack의 Nova 서비스이고, “compute 서비스 up”은 openstack compute service list에 나오는 nova-compute 프로세스 상태입니다.
  • “새 이미지”는 Glance의 VM 이미지가 아니라, Operator가 Pod를 다시 띄울 때 쓴 컨테이너 이미지입니다.

번역을 잘못하면 엉뚱한 곳을 고칩니다. 예를 들어 “이미지가 바뀌었다”를 Glance 이미지로 알아들으면 고객 VM 이미지를 뒤지게 되고, 실제 원인인 서비스 업데이트는 놓치게 됩니다.

이 편의 핵심 습관

모호한 단어를 들으면 “어느 쪽 ○○요?”라고 되묻는 것입니다. “어느 쪽 프로젝트요? OCP Namespace요, OpenStack 프로젝트요?” 이 질문 하나가 장애 대응 시간을 크게 줄여 줍니다. 숙련자일수록 이 질문을 자주 합니다.

섹션 3

두 언어의 문법 차이

단어를 외우기 전에 문법부터 봅시다. 두 세계는 “일을 시키는 방식” 자체가 다릅니다.

① 명령형 REST API vs 선언형 리소스

OpenStack: “이것을 해라”

REST API에 동사를 보냅니다. POST /servers(만들어라), DELETE /volumes/{id}(지워라), POST /servers/{id}/action(재시작해라). 요청은 한 번 처리되면 끝이고, 실패하면 사람이 다시 요청해야 합니다.

OpenShift: “이렇게 되어 있어야 한다”

리소스의 spec(원하는 상태)을 적어 두면, 컨트롤러가 status(실제 상태)를 계속 맞춥니다. 실패해도 컨트롤러가 다시 시도합니다(리컨실).

RHOSO에서는 두 문법이 층을 이룹니다. 클라우드 사용자는 OpenStack 명령형 API로 VM을 만들고, 클라우드 운영자는 OpenShift 선언형 CR로 OpenStack 자체를 관리합니다. 그래서 “인스턴스를 만들어 줘”는 openstack server create로, “Nova 스케줄러 설정을 바꿔 줘”는 OpenStackControlPlane CR 수정으로 처리합니다.

② CLI 어순: 명사 먼저 vs 동사 먼저

# OpenStack CLI:  openstack  <명사(객체)>  <동사>  [대상]
openstack server list
openstack server show 3f2a…
openstack volume create --size 10 data-vol
openstack compute service list

# OpenShift CLI:  oc  <동사>  <명사(리소스 종류)>  [이름]  -n <네임스페이스>
oc get pods -n openstack
oc describe pod keystone-7d9c… -n openstack
oc get openstackcontrolplane -n openstack
oc explain openstackcontrolplane.spec.keystone   # CR 필드 설명 보기(강력 추천)

어순이 반대라서 처음엔 자주 틀립니다. “openstack은 무엇을(명사) 먼저, oc는 어떻게(동사) 먼저”로 기억하세요.

④ 상태를 표현하는 방식

OpenStack은 하나의 상태 문자열(예: 인스턴스 ACTIVE, 볼륨 in-use)로 말합니다. OpenShift는 여러 개의 조건(conditions)으로 말합니다. 예를 들어 RHOSO의 컨트롤 플레인 CR은 서비스별 Ready 조건을 여러 개 가지고, 전체 요약으로 STATUS True와 MESSAGE Setup complete를 보여 줍니다. 섹션 9에서 상태값을 자세히 번역합니다.

⑥ 자격 증명 파일도 두 개

OpenStack CLI는 clouds.yaml 또는 OS_로 시작하는 환경 변수로 Keystone에 인증합니다. oc는 kubeconfig로 OpenShift API에 인증합니다. 두 열쇠는 완전히 별개입니다. OCP 클러스터 관리자라고 해서 OpenStack 관리자 권한이 자동으로 생기지 않고, 그 반대도 마찬가지입니다. 섹션 11에서 자세히 봅니다.

OpenStack 어휘 카드

카드를 눌러 보세요.

관계를 한 줄로

도메인 안에 프로젝트가 있고, 사용자는 프로젝트에서 역할을 받아 토큰을 얻습니다. 그 토큰으로 이미지와 플레이버를 골라 인스턴스를 만들고, 인스턴스는 포트를 통해 네트워크/서브넷에 붙으며, 보안 그룹이 포트를 지키고, 라우터와 플로팅 IP로 외부와 통합니다. 데이터는 볼륨에 둡니다. 이 문장을 막힘없이 설명할 수 있으면 섹션 4는 통과입니다.

섹션 5

OpenShift 기본 어휘

클라우드 운영자가 RHOSO를 다룰 때 쓰는 단어들입니다. Kubernetes 일반 용어와, RHOSO에 꼭 필요한 OpenShift 부품 용어를 함께 묶었습니다.

OpenShift 어휘 카드

카드를 눌러 보세요.

관계를 한 줄로

OLM이 Operator를 설치하면 Operator는 CRD를 등록합니다. 운영자가 CR을 쓰면 Operator가 이를 보고 Deployment·StatefulSet을 만들고, 이들이 Pod를 띄웁니다. Pod는 Service로 묶여 고정 주소를 얻고, 외부에는 Route나 MetalLB IP로 노출됩니다. 설정은 ConfigMap·Secret으로, 데이터는 PVC로 받습니다. 노드의 추가 네트워크는 NMState가, Pod의 추가 네트워크 연결은 NetworkAttachmentDefinition이 맡습니다.

가장 위험한 착각: 보안 기본값

OpenStack 보안 그룹은 규칙이 없으면 외부에서 들어오는 트래픽을 막습니다(나가는 것은 허용). Kubernetes NetworkPolicy는 반대로, 정책이 하나도 없으면 모든 트래픽을 허용합니다. 한쪽 세계의 감각으로 다른 쪽을 설계하면 “열려 있어야 할 것이 막히거나, 막혀야 할 것이 열리는” 사고가 납니다.

섹션 7

같은 단어, 다른 뜻 (헷갈리는 단어 18선)

외국어 학습에서 “가짜 친구(false friend)”라고 부르는 것들입니다. 철자는 같은데 뜻이 다른 단어죠. RHOSO에는 이런 단어가 특히 많습니다. 각 카드의 구분법을 습관으로 만드세요.

섹션 8

그리고 RHOSO가 의존하는 OpenShift 부품의 CR도 함께 알아 두세요: NodeNetworkConfigurationPolicy(NMState, 노드 네트워크), NetworkAttachmentDefinition(Pod 추가 네트워크), IPAddressPool · L2Advertisement(MetalLB), Subscription · ClusterServiceVersion · InstallPlan(OLM, Operator 설치·업데이트).

CR 안의 자주 나오는 필드 이름

아래는 RHOSO 문서에서 반복해서 보게 될 필드를 한 화면에 모은 학습용 축약 예시입니다. 번호를 따라 읽어 보세요.

kind: OpenStackControlPlane
spec:
  secret: osp-secret                     1
  storageClass: local-storage           2
  nova:
    apiOverride:
      route: {}                         3
    template:                           4
      apiServiceTemplate:
        replicas: 3                      5
        override:
          service:
            internal:
              metadata:
                annotations:
                  metallb.universe.tf/address-pool: internalapi   6
              spec:
                type: LoadBalancer
      schedulerServiceTemplate:
        customServiceConfig: |            7
          [filter_scheduler]
          enabled_filters = …
  glance:
    template:
      glanceAPIs:
        default:
          networkAttachments: [storage]   8
          topologyRef: { name: zone-a }   9
  • 1secret: 각 서비스의 DB·서비스 계정 비밀번호를 담은 Kubernetes Secret 이름. Barbican 시크릿이 아닙니다.
  • 2storageClass: Galera·RabbitMQ 같은 상태 저장 Pod의 PVC를 만들 OCP 스토리지 종류. Cinder 볼륨 타입이 아닙니다.
  • 3apiOverride.route: 이 서비스의 공개(public) API를 OpenShift Route로 노출. Keystone 카탈로그의 public 엔드포인트가 이 주소가 됩니다.
  • 4template: 그 서비스를 어떻게 만들지 적는 “설계도” 칸. Heat 템플릿, OpenShift Template 객체와는 상관없습니다(섹션 7 참고).
  • 5replicas: 그 구성 요소의 Pod 개수.
  • 6override.service + MetalLB 어노테이션: 내부(internal) API를 internalapi 네트워크의 MetalLB IP로 노출. 컴퓨트 노드는 이 주소로 컨트롤 플레인에 접근합니다.
  • 7customServiceConfig: OpenStack 서비스 설정 파일(INI 형식)에 추가할 내용. Pod 안 파일을 직접 고치면 Operator가 되돌리므로, 설정 변경은 반드시 여기서 합니다.
  • 8networkAttachments: 이 Pod를 어떤 격리 네트워크(storage, internalapi 등)에 추가로 연결할지. 실체는 NetworkAttachmentDefinition.
  • 9topologyRef: Pod를 어느 노드·영역에 둘지 정하는 배치 규칙 참조. 분산 영역(DCN·다중 AZ) 구성에서 씁니다.

데이터 플레인 쪽에서 자주 보는 필드도 정리합니다.

필드 (NodeSet)뜻
preProvisionedtrue면 OS가 이미 설치된 RHEL 서버를 사용. false면 OCP의 베어메탈 프로비저닝(BareMetalHost)으로 OS부터 설치
nodeTemplate묶음 안 모든 노드에 공통으로 적용할 값 (SSH 사용자, SSH 키 Secret, 공통 Ansible 변수 등)
nodes노드별 개별 값 (호스트 이름, 접속 IP, 노드별 네트워크 IP)
ansibleVars / edpm_* 변수Ansible에 넘기는 변수. 예: edpm_network_config_template(노드 네트워크 구성 템플릿)
services이 묶음에 순서대로 실행할 OpenStackDataPlaneService 목록
networks노드가 연결될 격리 네트워크와 IP (NetConfig의 대역에서 할당)

RHOSO 운영의 제1원칙

“결과물을 직접 고치지 말고, 원인(CR)을 고친다.” Pod 안 설정 파일, Operator가 만든 ConfigMap, 컴퓨트 노드의 설정 파일을 직접 고치면 다음 리컨실이나 다음 Deployment 때 덮어써집니다. 변경은 OpenStackControlPlane(컨트롤 플레인) 또는 NodeSet(데이터 플레인)에서 하고, 데이터 플레인 변경은 새 OpenStackDataPlaneDeployment로 적용합니다.

필드 이름이 기억나지 않을 때는 oc explain openstackcontrolplane.spec.nova.template --recursive처럼 클러스터에게 직접 물어보면 됩니다. 문서보다 정확합니다. 실제로 설치된 버전 기준이기 때문입니다.

상태값 사전

상태값을 눌러 보세요.

두 가지 “살아 있음”을 구분하기

openstack compute service list에는 칸이 두 개 있습니다. State(up/down)는 “서비스가 실제로 살아서 보고하고 있나”, Status(enabled/disabled)는 “관리자가 이 노드에 새 VM을 배치해도 된다고 허락했나”입니다. 점검 작업 전에는 일부러 disabled로 바꿔 두기도 합니다. OpenShift에서는 비슷하게 노드의 Ready와 SchedulingDisabled(cordon)가 따로 표시됩니다.

RHOSO에는 “관리자”라는 말이 가리킬 수 있는 사람이 둘 이상입니다. 누가 어떤 열쇠로 어느 문을 여는지 구분해야 권한 요청과 장애 보고가 정확해집니다.

  • 도구: openstack CLI (openstackclient Pod)

  • 보는 범위: --all-projects

보안 관점의 핵심

openstack 네임스페이스의 Secret을 읽을 수 있는 OCP 계정은 사실상 OpenStack 전체의 관리자 비밀번호를 볼 수 있는 계정입니다. 그래서 RHOSO에서는 OCP 권한 관리가 곧 OpenStack 보안입니다. 28편(보안 강화)에서 권한 분리를 설계합니다.

섹션 17

정리와 다음 편

오늘의 핵심 일곱 문장

  • OpenStack은 명령형 REST API(“이것을 해라”), OpenShift는 선언형 리소스(“이렇게 되어 있어야 한다”)로 일한다. RHOSO에서 사용자는 전자로, 운영자는 후자로 일한다.
  • CLI 어순은 반대다. openstack 명사 동사, oc 동사 명사.
  • OpenStack 리소스는 이름이 중복될 수 있으므로 위험한 작업은 UUID로 지정한다.
  • Project·Service·Operator·Node·Image·Network·Template·Secret·Role처럼 같은 단어가 두 세계에서 다른 뜻이다. 모호하면 “어느 쪽 ○○?”을 묻는다.
  • 보안 그룹은 기본 차단, NetworkPolicy는 기본 허용이다.
  • RHOSO 설정은 결과물이 아닌 CR(OpenStackControlPlane, NodeSet)에서 바꾼다. 설정 파일 내용은 customServiceConfig로 넣는다.
  • 열쇠는 두 개다: clouds.yaml(Keystone)과 kubeconfig(OpenShift). OCP 권한 관리가 곧 OpenStack 보안이다.
