병렬화 전략과 멀티노드

모델이 GPU 한 장에 들어가지 않거나, 들어가도 KV 공간이 모자라거나, 한 장의 속도로는 TPOT 목표를 못 맞출 때 모델을 여러 GPU에 나눕니다. 어떻게 나누느냐(텐서·파이프라인·데이터·전문가·컨텍스트 병렬)에 따라 GPU 사이로 오가는 데이터의 양과 패턴이 완전히 달라지고, 그래서 어떤 연결(NVLink·PCIe·InfiniBand·RoCE) 위에서 어떤 병렬화를 쓰는가가 성능을 정합니다. 이번 편은 그 원리와 계산, 그리고 쿠버네티스에서 여러 노드를 하나의 엔진으로 묶는 LeaderWorkerSet까지 다룹니다.

01시작하기 전에

병렬화는 “GPU를 더 쓰는 법”이 아니라 “GPU 사이 통신을 어디에 둘지 정하는 법”입니다.

랩의 한계와 이 편의 진행 방식

우리 랩의 GPU 서빙 장치는 GB10 한 장이라 텐서·파이프라인 병렬의 성능은 직접 잴 수 없습니다. 이 편은 계산(통신 비용·메모리 배치)과 설계(병렬화 선택·LWS 매니페스트)를 중심으로 하고, 실습은 LeaderWorkerSet의 그룹 동작을 GPU 없이 확인한 뒤, 멀티 GPU 환경(클라우드·고객사, 또는 DGX Spark·PGX 두 대를 고속 네트워크로 연결한 구성)에서 그대로 쓸 수 있는 매니페스트와 측정 계획을 만듭니다.

학습 목표

  1. 메모리·지연·처리량 중 무엇 때문에 나누는지에 따라 병렬화 방식이 달라지는 이유를 설명할 수 있다.
  2. 텐서·파이프라인·데이터·전문가·컨텍스트 병렬의 통신 패턴과 장단점을 비교할 수 있다.
  3. 텐서 병렬의 스텝당 통신량을 계산하고, 연결(NVLink·PCIe·IB)별로 계산 대비 통신 비중을 판단할 수 있다.
  4. 대형 MoE에서 전문가 병렬과 어텐션 데이터 병렬을 조합하는 이유를 설명할 수 있다.
  5. vLLM의 병렬화·멀티노드 옵션과 프로세스 배치를 연결할 수 있다.
  6. LeaderWorkerSet으로 멀티노드 인스턴스를 구성하고, 그룹 단위 장애·재시작·배치를 설계할 수 있다.
이 편의 비유: 큰 책을 여러 사람이 번역하기

텐서 병렬은 한 페이지를 여러 명이 단락씩 나눠 번역하고 매 문단 끝마다 모여 맞춰 보는 방식입니다. 손이 빠르지만 회의가 잦아 같은 방(NVLink)에 있어야 합니다. 파이프라인 병렬은 1~3장은 A가, 4~6장은 B가 맡고 원고를 넘기는 방식입니다. 넘길 때만 만나므로 다른 건물(다른 노드)에 있어도 되지만, 한 원고가 끝까지 가는 데는 시간이 걸립니다. 데이터 병렬은 같은 책을 여러 팀이 각자 다른 독자에게 번역해 주는 것이고, 전문가 병렬은 법률·의학·기술 담당 전문가가 나뉘어 있어 문장마다 해당 전문가에게 보내는 방식입니다.

02왜 나누나

나누는 이유가 세 가지이고, 이유마다 정답이 다릅니다.

이유증상먼저 볼 것병렬화 방향
메모리: 가중치가 안 들어감한 장에 로딩 불가양자화로 들어가는가 (6편)TP(노드 안) → 그래도 안 되면 PP(노드 간)
메모리: KV 공간이 모자람동시성 상한이 낮음, 긴 문맥 불가 (14편)FP8 KV, 최대 길이 (14·15편)TP로 가중치를 나눠 KV 자리 확보, 또는 레플리카(DP)
지연: TPOT가 목표보다 큼한 장의 대역폭으로 가중치를 읽는 시간이 김 (2편)양자화, 추측 디코딩 (16편)TP: 여러 GPU의 대역폭을 합쳐 한 토큰을 빨리
처리량: 요청이 너무 많음대기열, SLO 용량 부족 (14편)튜닝으로 한 장의 용량부터 최대화DP(레플리카 추가)가 가장 단순하고 효율적 (18편)

원칙: 한 장에 들어가면 나누지 않고 레플리카를 늘린다(DP). 나누는 순간 통신 비용과 장애 범위가 생기기 때문입니다. 나눠야 한다면 가장 빠른 연결 안에서, 가장 적게 나눕니다.

03병렬화 다섯 가지

무엇을 나누는지, 그 대가로 무엇이 GPU 사이를 오가는지가 핵심입니다.

방식나누는 것오가는 것통신 빈도장점단점·주의
텐서 병렬 (TP)각 층의 행렬을 열·행으로층마다 활성값 all-reduce (어텐션 1회 + MLP 1회)매 층, 매 스텝가중치·KV를 n등분, 대역폭을 합쳐 TPOT 단축통신이 잦아 NVLink 도메인 안에서만. 헤드 수 등 나눗셈 제약(2의 거듭제곱 권장)
파이프라인 병렬 (PP)층을 구간(스테이지)으로스테이지 경계의 활성값 (점대점)스테이지 경계에서만통신량이 적어 노드 간에 적합요청 하나가 모든 스테이지를 차례로 지나 지연 증가, 스테이지 불균형 시 빈 시간(버블)
데이터 병렬 (DP)요청 (모델 전체를 복제)없음 (MoE의 어텐션 DP는 일부 동기화)—가장 단순, 처리량 선형 증가복제마다 가중치 전체 메모리 필요

실제 배포는 대개 조합입니다. 예: “노드 안 TP8 × 노드 간 PP2” (16장으로 한 모델), “어텐션은 DP, MoE 층은 EP” (대형 MoE), “TP2 레플리카를 DP4개” (처리량). 이 조합에서 통신이 많은 축(TP·EP)은 가장 빠른 연결 안에, 통신이 적은 축(PP·DP)은 느린 연결을 넘나들게 배치합니다.

06대형 MoE와 전문가 병렬

총 수백 B, 활성 수십 B. MoE는 메모리는 크고 토큰당 계산은 작은 모델이라 나누는 방법도 다릅니다.

  • 왜 TP만으로는 비효율적인가: 전문가가 수백 개인 MoE를 TP로 나누면 모든 GPU가 모든 전문가의 조각을 들고 매 층 all-reduce를 해야 합니다. 전문가를 통째로 GPU에 나눠 주고(EP), 토큰을 담당 전문가가 있는 GPU로 보내는 것(all-to-all)이 더 효율적입니다.
  • 어텐션 DP + MoE EP: 어텐션 층은 각 GPU가 서로 다른 요청을 처리(DP)하고, MoE 층에서만 토큰을 전문가 GPU로 모읍니다. KV는 요청별로 한 GPU에만 있어 KV 중복이 없고, MLA 같은 압축 KV 모델과 궁합이 좋습니다.
  • 대규모 전문가 병렬(Wide EP): 수십 장 이상에 전문가를 펼치는 구성. 전문가 간 부하 불균형을 줄이는 부하 분산(vLLM의 전문가 병렬 부하 분산 옵션), 빠른 all-to-all 커널(DeepEP 등), P/D 분리(10편)와 함께 쓰입니다. llm-d의 잘 닦인 경로 중 하나입니다.
  • 랙 단위 NVLink의 장점: all-to-all은 통신량이 많아 NVL72처럼 랙 전체가 NVLink로 묶인 시스템에서 크게 유리합니다.

07vLLM 설정 매핑

병렬화 개념을 vLLM 옵션과 프로세스로 옮깁니다(4편 프로세스 계산기와 함께 보세요).

옵션의미메모
-tp / --tensor-parallel-size텐서 병렬 크기노드 안 GPU 수 이하, 보통 2의 거듭제곱
-pp / --pipeline-parallel-size파이프라인 스테이지 수노드 간 분할에 주로 사용
-dp / --data-parallel-size엔진 안 데이터 병렬 랭크 수MoE의 어텐션 DP, 또는 한 서버에서 여러 엔진 랭크
--enable-expert-parallelMoE 층을 전문가 병렬로DP·TP와 조합해 EP 크기 결정
--distributed-executor-backendmp(기본, 멀티프로세싱) 또는 ray멀티노드도 mp로 가능 (아래)
--nnodes · --node-rank · --master-addr · --headlessRay 없이 멀티노드: 각 노드에서 vLLM을 띄우고 0번 노드가 API를 맡음0번이 아닌 노드는 --headless로 API 서버 없이 참여
데이터 병렬 주소·로컬 랭크 옵션여러 노드에 걸친 DP 랭크 배치대규모 EP 구성에서 사용 (옵션 이름은 버전 문서)
bash · 두 노드 × 8 GPU에 TP8 × PP2 (Ray 없이)
# 0번 노드 (API 서버 포함)
vllm serve <모델 경로> --tensor-parallel-size 8 --pipeline-parallel-size 2 \
  --nnodes 2 --node-rank 0 --master-addr <0번 노드 IP>
# 1번 노드 (헤드리스)
vllm serve <모델 경로> --tensor-parallel-size 8 --pipeline-parallel-size 2 \
  --nnodes 2 --node-rank 1 --master-addr <0번 노드 IP> --headless

통신이 잦은 TP는 노드 안(8장)에, 통신이 적은 PP는 노드 사이에 둔 배치입니다. 모든 노드가 같은 모델 경로·패키지·병렬화 값을 가져야 합니다. Ray 기반 구성(0번에서 Ray 헤드, 나머지는 Ray 워커, --distributed-executor-backend ray)도 여전히 쓰이며, 일부 프레임워크는 Ray 방식을 택합니다.

08쿠버네티스 멀티노드: LeaderWorkerSet

Deployment는 Pod를 하나씩 다룹니다. 멀티노드 엔진은 “여러 Pod가 한 몸”이라 다른 단위가 필요합니다.

LeaderWorkerSet(LWS)은 쿠버네티스 SIG가 만든 API로, 리더 1개 + 워커 N−1개를 하나의 그룹으로 묶고, 그 그룹을 레플리카 단위로 복제합니다. 그룹 안의 Pod는 리더 주소·그룹 크기·자기 인덱스를 환경 변수로 받아, 위 7장의 --master-addr·--node-rank에 그대로 연결합니다.

기능내용왜 필요한가
그룹 단위 생성·삭제리더와 워커를 한 단위로일부만 떠 있는 엔진은 쓸모가 없음
그룹 재시작 정책그룹 안 Pod 하나가 재시작되면 그룹 전체를 다시 만들 수 있음분산 엔진은 랭크 하나가 죽으면 전체가 망가짐
환경 변수리더 주소, 그룹 크기, 워커 인덱스멀티노드 플래그 자동 연결
그룹 단위 롤링 업데이트그룹 하나씩 교체업데이트 중에도 일부 레플리카 유지
배치 정책그룹을 같은 토폴로지 영역(랙·블록)에 모으는 설정, 그룹 단위 스케줄링과 결합노드 간 통신 성능 (8편 Kueue TAS·DRA)
갱(gang) 스케줄링을 함께

그룹의 Pod 일부만 GPU를 잡고 나머지가 Pending이면 GPU가 놉니다. 그룹 전체가 한 번에 배치되도록 Kueue(LWS 통합, 토폴로지 인지 스케줄링)나 Volcano·KAI 같은 갱 스케줄러와 함께 씁니다(8편). KServe·llm-d·Dynamo의 멀티노드 기능도 내부적으로 LWS나 비슷한 그룹 개념을 씁니다(9편).

09병렬화 고르는 법

히어로의 설계기가 따르는 규칙입니다.

  1. 한 장에 들어가는가?가중치 + 필요한 KV + 여유가 한 장에 들어가면 나누지 않습니다. 처리량은 레플리카(DP)로 늘립니다.
  2. 노드 안에서 해결되는가?들어가는 가장 작은 TP(2·4·8)를 고릅니다. TPOT 목표가 엄격하면 TP를 한 단계 키우는 것도 방법(대역폭 합산)이지만, 통신 비중을 4장 계산기로 확인합니다.
  3. 노드를 넘어야 하는가?노드 안 TP(최대 NVLink 도메인) × 노드 간 PP. 노드 간 TP는 피합니다.
  4. 대형 MoE인가?어텐션 DP + 전문가 병렬, 규모가 크면 Wide EP 경로(llm-d)와 P/D 분리를 검토합니다.
  5. NVLink가 없는 GPU인가?L4·L40S처럼 PCIe만 있으면 TP2 이상은 통신이 큰 비중을 차지합니다. 더 작은(양자화된) 모델로 한 장에 넣거나, 큰 GPU를 쓰는 편이 낫습니다.

10장애와 운영

나누면 장애 범위가 커지고 기동이 길어집니다.

운영 측면단일 GPU 엔진멀티 GPU·멀티노드 엔진
장애 범위GPU 하나 = 레플리카 하나GPU·노드·링크 하나라도 실패하면 인스턴스 전체 중단
기동 시간 (13편)한 장 로딩모든 랭크의 로딩·통신 그룹 초기화가 끝나야 준비. 가장 느린 노드에 맞춰짐
용량 단위GPU 1장TP×PP 장 단위로만 늘고 줆 (18편 자동 확장의 계단이 큼)
업그레이드Pod 단위그룹 단위. 모든 노드의 이미지·드라이버·NCCL 버전 일치 필요
관측 (20·21편)Pod 하나랭크별 GPU 사용률·통신 대기 시간을 함께 봐야 병목 노드를 찾음

11MSP 관점

병렬화 설계는 하드웨어 견적과 SLA의 출발점입니다.

  • 견적의 단위: “70B FP8을 H100에 서빙”은 TP2(한 레플리카 2장)부터 시작하고, 처리량은 TP2 레플리카 수로 셉니다. 계산기 결과를 견적서의 근거로 첨부합니다.
  • NVLink 서버의 가치: 같은 GPU라도 PCIe 서버와 NVLink 서버는 큰 모델에서 성능이 크게 다릅니다. 고객이 저렴한 PCIe 서버를 원하면 모델 크기·양자화 계획을 먼저 맞춥니다.
  • N+1: 멀티노드 인스턴스는 장애 시 통째로 빠지므로, SLA를 위해 여유 그룹 하나를 두는 비용을 단가에 반영합니다.
  • 소규모 고객: DGX Spark·PGX 두 대 연결 같은 소형 클러스터는 “큰 모델을 시험해 보는” 용도에 적합하고, 서비스 용량은 측정 후에 약속합니다.

apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata: { name: lws-demo, namespace: llmsvc-lab }
spec:
  replicas: 1
  leaderWorkerTemplate:
    size: 3                                   # 리더 1 + 워커 2 = 한 그룹
    restartPolicy: RecreateGroupOnPodRestart  # 그룹 안 하나가 재시작되면 그룹 전체를 다시

        containers:
        - name: main

          command: ["sh", "-c", "echo 리더 index=$LWS_WORKER_INDEX size=$LWS_GROUP_SIZE leader=$LWS_LEADER_ADDRESS; sleep 3600"]
          resources: { requests: { cpu: 10m, memory: 16Mi }, limits: { cpu: 100m, memory: 64Mi } }
    workerTemplate:
      spec:
        containers:
        - name: main
          image: busybox:1.36
          command: ["sh", "-c", "echo 워커 index=$LWS_WORKER_INDEX leader=$LWS_LEADER_ADDRESS; until nslookup $LWS_LEADER_ADDRESS >/dev/null 2>&1; do sleep 2; done; echo 리더 주소 확인됨; sleep 3600"]
          resources: { requests: { cpu: 10m, memory: 16Mi }, limits: { cpu: 100m, memory: 64Mi } }

apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata: { name: llm-big, namespace: llmsvc-lab }

          args:
          - >

            --tensor-parallel-size 8 --pipeline-parallel-size 2
            --nnodes $LWS_GROUP_SIZE --node-rank 0 --master-addr $LWS_LEADER_ADDRESS
            --port 8000
          env: &ncclenv

          - { name: NCCL_DEBUG, value: "INFO" }               # 실제 전송 경로 확인용 (확인 후 WARN)
          # - { name: NCCL_SOCKET_IFNAME, value: "<노드 간 NIC 이름>" }
          ports: [ { containerPort: 8000, name: http } ]
          resources:
            limits: { nvidia.com/gpu: 8 }                     # + RDMA 장치 (RDMA 장치 플러그인·SR-IOV·DRA 방식에 맞게)
          readinessProbe: { httpGet: { path: /health, port: 8000 }, periodSeconds: 10 }
          startupProbe:   { httpGet: { path: /health, port: 8000 }, periodSeconds: 10, failureThreshold: 360 }
          volumeMounts: &mounts
          - { name: models, mountPath: /models, readOnly: true }
          - { name: shm, mountPath: /dev/shm }
        volumes: &vols
        - { name: models, persistentVolumeClaim: { claimName: <공유 또는 노드별 모델 볼륨> } }
        - { name: shm, emptyDir: { medium: Memory, sizeLimit: 32Gi } }
    workerTemplate:
      metadata: { labels: { app: llm-big, role: worker } }
      spec:
        containers:
        - name: vllm
          image: vllm/vllm-openai:v0.31.0
          command: ["sh", "-c"]
          args:

            vllm serve /models/<모델> --served-model-name big
            --tensor-parallel-size 8 --pipeline-parallel-size 2
            --nnodes $LWS_GROUP_SIZE --node-rank $LWS_WORKER_INDEX --master-addr $LWS_LEADER_ADDRESS

실습 17-4 · 설계 워크시트

히어로의 설계기와 4장 계산기로 아래 세 고객 요청의 병렬화를 설계하고 근거를 적습니다.

요청설계 (TP·PP·DP·EP, GPU 수)근거 (메모리·통신·SLO)대안·위험
A. 70B FP8, H100 8장 서버 2대, 동시 사용자 200명·문맥 4K
B. 235B MoE FP8, H200 8장 서버, 긴 문맥 RAG
C. 32B, L4 8장 PCIe 서버 (NVLink 없음)

실습 17-5 · (선택) 멀티 GPU 환경 측정 계획

GPU 2장 이상을 쓸 수 있을 때, 같은 8B FP8 모델로 “TP1 × 레플리카 2”와 “TP2 × 레플리카 1”을 14편의 slo_probe.py로 비교합니다.

구성기대측정
TP1 × DP2 (레플리카 2개)처리량 최대, 단일 요청 TPOT는 한 장 속도SLO 용량, TPOT p50
TP2 × 1단일 요청 TPOT 단축(대역폭 합산), 처리량은 통신 비용만큼 손해, KV 공간 증가같은 항목 + 통신 비중(NCCL 로그·GPU 사용률)

“TPOT 목표가 엄격하면 TP, 처리량이 목표면 DP”라는 원칙이 숫자로 확인되어야 합니다. 이것이 18편 자동 확장에서 “확장 단위”를 정하는 근거가 됩니다.

15확인 퀴즈

9문제.

16정리와 체크리스트

핵심 여섯 문장.

  1. 한 장에 들어가면 나누지 않고 레플리카(DP)를 늘린다. 나누면 통신 비용과 장애 범위가 생긴다.
  2. TP는 층마다 all-reduce라 NVLink 도메인 안에서만, PP는 경계에서만 통신해 노드 사이에 둔다.
  3. 통신 비중 = 스텝 통신 시간 ÷ 스텝 계산 시간. PCIe·노드 간 TP는 이 비중이 커서 피한다.
  4. 대형 MoE는 어텐션 DP + 전문가 병렬, 규모가 크면 Wide EP와 전용 all-to-all 커널을 쓴다.
  5. vLLM 멀티노드는 Ray 없이도 --nnodes·--node-rank·--master-addr·--headless로 구성되고, LWS 환경 변수에 그대로 연결된다.
  6. LWS는 리더·워커를 한 그룹으로 만들고, 그룹 재시작·갱 스케줄링·토폴로지 배치와 함께 쓴다. 장애 범위·기동·용량 단위가 커지는 것을 운영 설계에 반영한다.
