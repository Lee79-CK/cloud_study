Eventing 1: 이벤트 배달 구조

Serving이 "요청이 오면 답한다"라면 Eventing은 "무슨 일이 생기면 반응한다"입니다. 이벤트를 담는 표준 봉투 CloudEvents부터, 봉투를 모으고 골라 배달하는 Broker와 Trigger, 그리고 배달 실패를 다루는 재시도와 Dead Letter Sink까지 다룹니다.

기준 버전 Knative v1.23 선수 지식: 1~2편, HTTP 기본 예상 학습 시간 90~110분

왜 이벤트인가

주문 서비스가 주문을 받으면 재고 차감, 결제, 알림 발송, 분석 적재가 필요하다고 해 봅시다. 가장 단순한 방법은 주문 서비스가 네 서비스를 차례로 호출하는 것입니다. 하지만 알림 서비스가 느려지면 주문도 느려지고, 새로 "포인트 적립"이 추가되면 주문 서비스 코드를 고쳐야 합니다.

직접 호출 = 일일이 전화하기

  • 보내는 쪽이 받는 쪽을 모두 알아야 함
  • 받는 쪽이 느리거나 죽으면 보내는 쪽도 막힘
  • 새 수신자가 생기면 보내는 쪽 코드 수정

이벤트 = 우체국에 맡기기

  • 보내는 쪽은 "주문이 생겼다"는 사실만 알림
  • 우체국(Broker)이 관심 있는 곳에 배달
  • 새 수신자는 우체국에 구독 신청(Trigger)만 하면 됨
Knative Eventing이 하는 일

이벤트를 만드는 쪽(생산자)과 받는 쪽(소비자)을 느슨하게 연결하는 배달망입니다. 모든 이벤트는 CloudEvents 형식의 HTTP 요청으로 오가며, 받는 쪽은 대개 Knative Service라서 이벤트가 없을 때는 0개로 쉬고 있다가 이벤트가 오면 깨어납니다. Serving과 Eventing이 만나는 지점입니다.

CloudEvents: 이벤트의 표준 봉투

시스템마다 이벤트 모양이 제각각이면 받는 쪽은 발신처별로 파싱 코드를 따로 짜야 합니다. CloudEvents는 이벤트의 "봉투"에 들어갈 정보를 표준으로 정한 CNCF 명세로, 2024년 CNCF 졸업 프로젝트가 되었습니다. 내용물(data)은 자유지만 봉투 겉면의 속성은 정해져 있습니다.

속성구분뜻예시
specversion필수CloudEvents 명세 버전1.0
id필수이벤트 고유 번호. source와 id 조합이 같으면 같은 이벤트로 봅니다(중복 제거의 기준)ord-20261004-0001
source필수이벤트가 생긴 곳. URI 형식/mycorp/orders
type필수무슨 일이 일어났는지. 역도메인 표기가 관례이며 Trigger 필터에 가장 많이 쓰임com.mycorp.order.created
time선택사건이 일어난 시각 (RFC 3339)2026-10-04T09:00:00Z
subject선택source 안에서 구체적인 대상order/1234
datacontenttype선택data의 형식application/json
dataschema선택data의 스키마 위치https://…/order-v1.json
확장 속성선택필요한 속성을 자유롭게 추가. 영문 소문자와 숫자만. 추적용 traceparent, 파티션용 partitionkey 등tenant: customer-a

HTTP에 싣는 두 가지 방식

Binary 모드

  • 속성은 ce-로 시작하는 HTTP 헤더로
  • 본문에는 data만
  • 기존 HTTP 앱이 본문을 그대로 읽을 수 있어 Knative에서 가장 흔함

Structured 모드

  • 속성과 data를 하나의 JSON에 담아 본문으로
  • Content-Type은 application/cloudevents+json
  • 파일 저장이나 큐 전달처럼 봉투째 다룰 때 편리

Eventing의 부품들

Eventing의 리소스는 역할로 나누면 단순합니다. 만드는 쪽, 나르는 쪽, 받는 쪽입니다.

Source: 만드는 쪽

외부 사건(타이머, 쿠버네티스 변경, Kafka 메시지, 웹훅 등)을 CloudEvents로 바꿔 보냅니다. PingSource, ApiServerSource, KafkaSource 등이 있습니다.

Broker + Trigger: 나르는 쪽 (권장)

Broker는 이벤트를 모으는 우체국, Trigger는 "이런 이벤트는 저기로"라는 구독 규칙입니다. 필터링이 가능합니다.

Channel + Subscription: 나르는 쪽 (저수준)

Channel에 들어온 이벤트를 Subscription을 건 모두에게 그대로 복사합니다. 필터가 없습니다. Broker 내부 구현에도 쓰입니다.

Sink: 받는 쪽

이벤트를 HTTP로 받을 수 있는 모든 것. Knative Service, 쿠버네티스 Service, Broker, Channel, 그리고 임의의 URL까지 가능합니다.

"주소가 있으면 Sink가 될 수 있다": Addressable

Eventing은 리소스 종류가 아니라 모양을 봅니다. status.address.url에 주소를 내놓는 리소스면 무엇이든 이벤트를 받을 수 있는데, 이를 Addressable이라고 합니다. 그래서 Sink는 아래처럼 리소스 참조(ref)로도, 직접 URL(uri)로도 지정할 수 있습니다.

sink 지정 두 가지
# 리소스 참조: 주소가 바뀌어도 자동으로 따라감
sink:
  ref:
    apiVersion: serving.knative.dev/v1
    kind: Service
    name: order-handler
---
# 직접 URL: 클러스터 밖 웹훅 등
sink:
  uri: https://hooks.example.com/knative

Broker와 Trigger 실험실

Broker 하나에 Trigger 넷이 걸려 있습니다. 왼쪽 이벤트를 눌러 발행하면 어떤 Trigger가 받는지 보입니다. Trigger의 필터 값을 고쳐 보세요. 필터를 비우면 모든 이벤트를 받고, 여러 속성을 적으면 모두 일치해야 받습니다.

Brokerdefault
이벤트를 눌러 발행하세요.
Trigger마다 독립 배달

여러 Trigger가 같은 이벤트를 받으면 각각 따로 배달됩니다. 한 구독자가 실패해 재시도하는 동안에도 다른 구독자는 영향을 받지 않습니다. 반대로 말하면, 한 이벤트가 여러 번 처리될 수 있다는 뜻이니 소비자는 같은 이벤트를 두 번 받아도 문제없게(멱등하게) 만들어야 합니다.

필터 문법

Trigger 필터는 두 가지 방식이 있습니다. 기본은 속성 정확 일치(filter.attributes)이고, 더 복잡한 조건은 filters로 표현합니다.

trigger-attributes.yaml
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: order-created-to-billing
spec:
  broker: default
  filter:
    attributes:
      type: com.mycorp.order.created   # 정확히 일치
      tenant: customer-a               # 확장 속성도 가능
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: billing
trigger-filters.yaml (접두사, 조합)
spec:
  broker: default
  filters:
    - prefix:
        type: com.mycorp.order.      # order.로 시작하는 모든 type
    - not:
        exact:
          source: /mycorp/test       # 테스트 발신처는 제외
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: order-audit
filters 방언뜻
exact속성값이 정확히 같음
prefix / suffix속성값이 주어진 문자열로 시작 / 끝남
all / any안에 든 조건이 모두 / 하나라도 참
not안에 든 조건의 반대
cesqlCloudEvents SQL 식. 예: type LIKE 'com.mycorp.%' AND tenant = 'customer-a'
filters 목록은 AND

filters 아래 여러 항목을 나열하면 모두 참이어야 통과합니다. filter와 filters를 함께 적으면 filters가 우선합니다. 사용하는 버전에서 filters가 기본 활성화되어 있는지, Broker 구현체가 지원하는지는 문서에서 확인하세요.

이벤트를 만드는 Source

Source무엇을 이벤트로 만드나쓰임새
PingSourcecron 일정에 맞춰 정해진 데이터를 보냄주기 작업 트리거, 헬스 체크, 정기 리포트
ApiServerSource쿠버네티스 리소스의 생성·변경·삭제Pod 실패 감지, 배포 이벤트 수집, AIOps 알람 처리
SinkBinding이미 있는 Deployment·Job 등에 Sink 주소를 환경 변수(K_SINK)로 주입기존 앱을 이벤트 생산자로 만들 때. 앱은 K_SINK로 POST만 하면 됨
ContainerSource직접 만든 이미지를 실행하고 K_SINK를 주입폴링형 커스텀 소스
KafkaSource 등 확장Kafka 토픽, RabbitMQ 큐 등 외부 메시지기존 메시징 시스템과 연결 (6편)
IntegrationSourceApache Camel Kamelet 기반의 다양한 외부 연동클라우드 서비스, SaaS 연동. 최근 버전에 추가
SinkBinding이 주는 자유

SinkBinding을 쓰면 앱 코드에 Broker 주소를 하드코딩하지 않아도 됩니다. Knative가 K_SINK 환경 변수로 주소를 넣어 주고, Broker가 바뀌어도 자동으로 따라갑니다. 고객사의 기존 배치 Job을 이벤트 기반으로 바꾸는 가장 쉬운 출발점입니다.

답장으로 이어지는 사슬

구독자가 이벤트를 받고 HTTP 응답으로 또 다른 CloudEvent를 돌려주면, Broker는 그 응답을 새 이벤트로 받아 다시 Trigger들에 배달합니다. 이를 이용하면 서비스들이 서로를 모른 채 처리 단계를 이어 갈 수 있습니다.

order.created
›
결제 서비스
›
답장: payment.completed
›
배송 서비스
›
답장: shipment.scheduled
›
알림 서비스
무한 루프 주의

답장 type이 자기 자신의 Trigger 필터에 다시 걸리면 이벤트가 끝없이 돕니다. 필터를 비워 둔 Trigger를 가진 서비스가 답장을 보내면 특히 위험합니다. 답장 type은 받은 type과 다르게, 필터는 구체적으로 적으세요. 답장할 필요가 없다면 본문 없이 2xx만 돌려주면 됩니다.

잃지 않는 배달: 재시도와 Dead Letter Sink

Knative Eventing은 최소 한 번(at-least-once) 배달을 목표로 합니다. 구독자가 2xx로 답하면 성공, 5xx나 일부 4xx(시간 초과, 과다 요청 등)는 재시도 대상입니다. 정해진 횟수를 다 실패하면 이벤트를 Dead Letter Sink(DLS)로 보냅니다. 설정은 Trigger, Subscription, Broker의 delivery에 둡니다.

delivery 설정
spec:
  delivery:
    retry: 5                      # 첫 시도 외 재시도 횟수
    backoffPolicy: exponential    # linear 또는 exponential
    backoffDelay: PT0.5S          # ISO 8601 기간 (0.5초)
    deadLetterSink:
      ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: dead-letter-handler

DLS로 간 이벤트에는 실패 정보가 확장 속성으로 붙습니다. knativeerrordest(어디로 보내다 실패했나), knativeerrorcode(마지막 HTTP 상태 코드), knativeerrordata(응답 본문 일부)입니다. DLS 서비스는 이 정보를 저장하고 알림을 보내, 사람이 원인을 고친 뒤 다시 보낼 수 있게 해야 합니다.

MSP 운영 원칙: DLS 없는 Trigger는 만들지 않는다

DLS가 없으면 재시도를 다 실패한 이벤트는 로그 한 줄 남기고 사라집니다. 고객사 주문이나 결제 이벤트라면 데이터 유실입니다. Broker 수준에 기본 DLS를 두고, 중요한 Trigger에는 전용 DLS를 따로 두세요. DLS 자체도 Knative Service라면 min-scale을 1로 두는 것이 안전합니다.

기본 Broker의 한계와 보안

설치 직후 기본 Broker는 MT Channel Based Broker이고, 그 안의 Channel은 InMemoryChannel입니다. 이름 그대로 메모리에만 이벤트를 들고 있으므로, 디스패처 Pod가 재시작되면 배달 중인 이벤트는 사라집니다.

구분InMemoryChannel 기반Kafka Broker 등 (6편)
영속성없음. 재시작 시 유실 가능디스크에 저장, 복제
순서 보장보장 안 함파티션 단위 순서 옵션
설치 난도기본 포함Kafka 클러스터 필요
적합한 곳학습, 개발, 잃어도 되는 이벤트운영 환경, 업무 데이터
운영 환경 경고

퀵스타트나 기본 설치 그대로 고객사 운영에 쓰면 안 됩니다. 클러스터 기본 Broker 종류는 knative-eventing 네임스페이스의 config-br-defaults에서 정하므로, 운영 클러스터라면 여기서 영속성 있는 Broker를 기본으로 지정하세요.

이벤트 배달 보안

기본: 클러스터 내부 주소

Broker의 수신 주소는 클러스터 내부 주소입니다. 외부에서 이벤트를 받아야 하면 Broker를 직접 노출하지 말고, 인증을 거친 Knative Service가 받아서 Broker로 넘기게 하세요.

발신자 신원: OIDC

기능 플래그를 켜면 Source와 Broker가 이벤트를 보낼 때 OIDC 토큰을 붙여 "누가 보냈는지" 증명합니다. 받는 쪽은 토큰을 검증할 수 있습니다.

수신 허용: EventPolicy

OIDC와 함께 EventPolicy 리소스로 "이 Broker에는 어떤 발신자만 보낼 수 있다"를 정할 수 있습니다. 멀티테넌트 클러스터에서 다른 고객의 이벤트 주입을 막는 장치입니다.

전송 암호화

Eventing 구성요소 간 HTTPS를 쓰는 기능 플래그(transport-encryption)가 있습니다. cert-manager와 함께 씁니다.

OIDC, EventPolicy, 전송 암호화는 knative-eventing의 config-features에서 켜며, Broker 구현체마다 지원 범위가 다를 수 있으니 도입 전 확인이 필요합니다.

실습

퀵스타트 kind 클러스터에는 Eventing이 이미 설치되어 있습니다. 이벤트 내용을 로그로 찍어 주는 공식 예제 이미지 event_display를 받는 쪽으로 씁니다.

  1. Broker와 받는 쪽 준비

    bash
    kn broker create default
kn broker list

kn service create event-display \
  --image gcr.io/knative-releases/knative.dev/eventing/cmd/event_display \
  --scale-min 1

  2. Trigger 만들기: 주문 생성 이벤트만

    bash
    kn trigger create orders \
  --broker default \
  --filter type=com.mycorp.order.created \
  --sink ksvc:event-display

kn trigger list

    bash

    bash
    cat <<'EOF' | kubectl apply -f -
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: will-fail
spec:
  broker: default
  filter:
    attributes:
      type: com.mycorp.test.fail
  subscriber:
    uri: http://nobody.default.svc.cluster.local
  delivery:
    retry: 2
    backoffPolicy: linear
    backoffDelay: PT1S
    deadLetterSink:
      ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: event-display
EOF

# 3단계의 curl에서 Ce-Type만 com.mycorp.test.fail로 바꿔 발행한 뒤

정리와 다음 편

  1. 이벤트 기반 구조는 생산자와 소비자를 느슨하게 연결합니다.
  2. CloudEvents의 필수 속성은 specversion, id, source, type 넷이며, source+id가 이벤트의 정체성입니다.
  3. HTTP에는 Binary(ce- 헤더)와 Structured(JSON 봉투) 두 방식으로 싣습니다.
  4. 부품은 Source(만듦), Broker·Trigger 또는 Channel·Subscription(나름), Sink(받음)입니다. 주소만 있으면 Sink가 됩니다.
  5. Trigger 필터는 속성 정확 일치가 기본이고, filters로 접두사·부정·CESQL 등을 씁니다.
  6. 배달은 최소 한 번입니다. 재시도와 DLS를 설정하고, 소비자는 멱등하게 만드세요.
  7. 기본 InMemoryChannel Broker는 영속성이 없어 운영용이 아닙니다.
