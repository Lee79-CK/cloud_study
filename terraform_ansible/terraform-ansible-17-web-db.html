13~16편에서 배운 것을 모두 모아 실제 서비스를 구성합니다. 고객사 서버를 받았을 때 MSP가 가장 먼저 하는 일 — 운영 계정과 키를 정리하고, 시간을 맞추고, SSH를 잠그고, 방화벽을 켜고, 로그를 남기고, 기본 하드닝을 적용하는 일 — 을 기반 역할 6개로 표준화하고, 그 위에 웹(nginx)과 DB(PostgreSQL) 역할을 올립니다. 2편의 랩 노드에 실제로 적용해 웹 서버가 DB에 접속되는 것까지 확인하고, 같은 역할을 7편 Terraform으로 만든 AWS 인프라(웹 2대 + RDS)에 적용하는 방법으로 Level 3를 마무리합니다.

2base_users: 계정·키·sudo

운영 계정 목록이 곧 접근 권한 대장이다

roles/base_users/tasks/main.yml
---
- name: 운영자 그룹
  ansible.builtin.group:
    name: "{{ base_users_admin_group }}"
    state: present

- name: 운영자 그룹에 sudo 허용 (문법 검사 후 반영)
  ansible.builtin.copy:
    dest: "/etc/sudoers.d/90-{{ base_users_admin_group }}"
    content: "%{{ base_users_admin_group }} ALL=(ALL) NOPASSWD: ALL\n"
    owner: root
    group: root
    mode: "0440"
    validate: /usr/sbin/visudo -cf %s

- name: 계정 만들기·지우기
  ansible.builtin.user:
    name: "{{ item.name }}"
    comment: "{{ item.comment | default(omit) }}"
    shell: "{{ item.shell | default('/bin/bash') }}"
    groups: "{{ [base_users_admin_group] if item.sudo | default(false) else [] }}"
    append: true
    state: "{{ item.state | default('present') }}"
    remove: "{{ (item.state | default('present')) == 'absent' }}"
  loop: "{{ base_users_list }}"
  loop_control:
    label: "{{ item.name }} ({{ item.state | default('present') }})"

- name: SSH 공개 키 (목록에 있는 키만 남긴다)
  ansible.posix.authorized_key:
    user: "{{ item.name }}"
    key: "{{ item.ssh_keys | join('\n') }}"
    exclusive: true
    state: present
  loop: "{{ base_users_list }}"
  loop_control:
    label: "{{ item.name }} (키 {{ item.ssh_keys | default([]) | length }}개)"
  when:
    - item.state | default('present') == 'present'
    - item.ssh_keys | default([]) | length > 0

설계이유
계정마다 state, 퇴사자는 absent로 남겨 둔다목록에서 지우기만 하면 서버에는 계정이 남는다. absent로 한동안 유지해 모든 서버에서 확실히 지운 뒤 목록에서 뺀다
authorized_key의 exclusive: true목록에 없는 키(누군가 몰래 넣은 키, 예전 노트북 키)를 제거. 키 교체가 “목록 수정 + 실행”으로 끝난다
sudo는 그룹으로, sudoers는 validate: visudo -cf %s개인별 sudoers를 늘리지 않는다. 문법 오류로 sudo가 막히는 사고를 방지(15편 8장)
운영자는 개인 계정, 자동화는 별도 계정감사 로그에서 “누가”가 남아야 한다. 공용 계정 금지
NOPASSWD는 고객 정책에 따라

실습은 편의상 운영자 그룹에 비밀번호 없는 sudo를 줬습니다. 고객 보안 기준이 sudo 비밀번호를 요구하면 NOPASSWD:를 빼고, Ansible 실행 계정만 별도로 허용하거나 --ask-become-pass·Vault로 비밀번호를 넘깁니다(19편 become 전략).

3base_time: 시간 동기화

로그 상관 분석, 인증서·토큰 검증, 데이터베이스 복제 — 모두 시간이 맞아야 한다

defaults/main.yml
---
base_time_timezone: Asia/Seoul
# AWS EC2에서는 169.254.169.123(Amazon Time Sync)을 첫 번째로 두는 것이 권장
base_time_ntp_servers:
  - time.bora.net
  - time.kriss.re.kr
templates/chrony.conf.j2
# {{ ansible_managed }}
{% for s in base_time_ntp_servers %}
server {{ s }} iburst
{% endfor %}
driftfile /var/lib/chrony/chrony.drift
makestep 1.0 3
rtcsync
logdir /var/log/chrony
tasks/main.yml
---
- name: 배포판 계열별 내부 변수
  ansible.builtin.include_vars:
    file: "{{ ansible_facts['os_family'] }}.yml"

- name: Chrony 설치
  ansible.builtin.package:
    name: chrony
    state: present

- name: 시간대
  community.general.timezone:
    name: "{{ base_time_timezone }}"

- name: Chrony 설정
  ansible.builtin.template:
    src: chrony.conf.j2
    dest: "{{ __base_time_conf }}"
    owner: root
    group: root
    mode: "0644"
  notify: base_time chrony 재시작

- name: Chrony 실행
  ansible.builtin.service:
    name: "{{ __base_time_service }}"
    state: started
    enabled: true

14·15편 과제의 chrony를 역할로 완성한 것입니다. 배포판별로 설정 경로(/etc/chrony/chrony.conf ↔ /etc/chrony.conf)와 서비스 이름(chrony ↔ chronyd)이 다르므로 vars/Debian.yml·RedHat.yml로 나눴습니다. 시간대는 community.general.timezone으로 Asia/Seoul. AWS에서는 인스턴스 안에서 바로 닿는 Amazon Time Sync(169.254.169.123)를 쓰도록 인벤토리 변수만 바꿉니다(12장).

4base_ssh: SSH 하드닝

가장 위험한 설정 — 잘못되면 Ansible도 더 이상 들어가지 못한다

defaults/main.yml
---
# sshd 설정 조각 (/etc/ssh/sshd_config.d/) 으로 넣는 값
base_ssh_settings:
  PermitRootLogin: "no"
  PasswordAuthentication: "no"
  KbdInteractiveAuthentication: "no"
  PermitEmptyPasswords: "no"
  MaxAuthTries: 4
  LoginGraceTime: 60
  ClientAliveInterval: 300
  ClientAliveCountMax: 3
  X11Forwarding: "no"
  AllowTcpForwarding: "no"
  Banner: /etc/issue.net
base_ssh_banner: |
  인가된 사용자만 접근할 수 있습니다. 모든 접속은 기록됩니다.
  Authorized access only. All activity is logged.
tasks/main.yml
---
- name: 배포판 계열별 내부 변수
  ansible.builtin.include_vars:
    file: "{{ ansible_facts['os_family'] }}.yml"

- name: 접속 경고 문구
  ansible.builtin.copy:
    dest: /etc/issue.net
    content: "{{ base_ssh_banner }}"
    owner: root
    group: root
    mode: "0644"

- name: Sshd 설정 조각 (sshd -t 로 검사 후 반영)

    src: 50-iaclab.conf.j2
    dest: /etc/ssh/sshd_config.d/50-iaclab.conf
    owner: root
    group: root
    mode: "0600"
    validate: /usr/sbin/sshd -t -f %s

{{ k }} {{ v }}
{% endfor %}

안전장치설명
설정 조각(sshd_config.d/50-iaclab.conf)배포판 기본 sshd_config를 통째로 바꾸지 않는다. 패키지 업데이트와 충돌하지 않고, 우리 변경만 한 파일에. Ubuntu 24.04·Rocky 9 모두 Include /etc/ssh/sshd_config.d/*.conf가 기본
validate: /usr/sbin/sshd -t -f %s문법·알 수 없는 항목이 있으면 파일을 쓰지 않는다(실측: 조각 파일만으로도 검사 가능)
재시작이 아니라 다시 읽기(reload)기존 세션(Ansible 자신의 연결 포함)을 끊지 않는다
같은 항목은 먼저 읽힌 값이 이긴다sshd는 첫 값을 쓰므로 50-보다 앞 이름(예: 클라우드 이미지의 50-cloud-init.conf의 PasswordAuthentication yes)이 있으면 무시된다 → sshd -T로 실제 값 확인, 필요하면 10-처럼 앞 번호로
스스로 잠기지 않기 위한 순서

① Ansible 접속 계정이 키로 접속하고 있는지 먼저 확인(PasswordAuthentication no 적용 전) ② root로 접속하는 자동화가 없는지 확인(PermitRootLogin no) ③ AllowUsers·AllowGroups를 쓰려면 Ansible 계정을 반드시 포함 ④ 처음에는 서버 한 대(--limit)에 적용하고, 새 SSH 세션을 열어 접속되는지 확인한 뒤 확대 ⑤ 클라우드는 콘솔·SSM으로 복구할 길이 있는지 미리 확인. 이 실습은 AllowUsers를 일부러 넣지 않았습니다.

5base_firewall: 방화벽

Ubuntu는 ufw, Rocky는 firewalld — 그리고 SSH를 먼저 연다

tasks/main.yml
---
- name: Debian 계열 (ufw)
  when:
    - base_firewall_enabled | bool
    - ansible_facts['os_family'] == "Debian"
  block:
    - name: Ufw 설치
      ansible.builtin.package:
        name: ufw
        state: present

    - name: Ufw가 하드닝 커널 매개변수를 되돌리지 않게 (ufw 기본 sysctl.conf는 log_martians=0)
      ansible.builtin.lineinfile:
        path: /etc/ufw/sysctl.conf
        regexp: "^{{ item | regex_escape }}="
        line: "{{ item }}=1"
      loop:
        - net/ipv4/conf/all/log_martians
        - net/ipv4/conf/default/log_martians

    - name: SSH 먼저 허용 (활성화 전에)
      community.general.ufw:
        rule: allow
        port: "{{ base_firewall_ssh_port | string }}"
        proto: tcp

    - name: 추가 허용 규칙
      community.general.ufw:

CIS 벤치마크 영역과의 대응 — 항목을 눌러 이 강의의 구현과 확인 방법을 보세요

“CIS 일부”의 의미

CIS 벤치마크(Ubuntu 24.04, RHEL 9 등)는 배포판마다 수백 개 항목이며 Level 1(대부분의 서버)·Level 2(높은 보안)로 나뉩니다. 이 역할은 그중 영향이 크고 부작용이 적은 일부만 다룹니다. 전체 적용은 ① 고객과 적용 범위 합의 ② 점검 도구(OpenSCAP oscap, CIS-CAT)로 현재 점수 측정 ③ 커뮤니티 역할(예: ansible-lockdown의 UBUNTU24-CIS·RHEL9-CIS) 검토 ④ 서비스 영향 시험 순서로 진행합니다. 항목 번호는 벤치마크 버전마다 바뀌므로 이 강의는 영역 이름으로만 대응시켰습니다.

하드닝은 단계적으로

SSH·방화벽·sysctl은 서비스 영향이 있을 수 있습니다. 개발계 → 검증계 → 운영계 순서로, 운영계는 한 대씩(serial, 20편) 적용하고 각 단계에서 애플리케이션 확인 절차를 둡니다.

예외는 변수로, 기록과 함께

레거시 앱 때문에 특정 서버만 PasswordAuthentication이 필요하다면 host_vars에서 해당 값만 바꾸고 사유·기한을 주석으로 남깁니다(12편 정책 예외와 같은 원칙). 역할 코드에 고객별 분기를 넣지 않습니다.

보안 점검과 연결

7장의 대응표를 고객 보안 점검표(KISA 주요정보통신기반시설 점검 항목 등)와 매핑해 두면, 점검 결과 지적 사항을 “어느 역할의 어떤 변수로 해결”했는지 바로 답할 수 있습니다.

RDS는 서버가 아니다

관리형 DB에는 OS 하드닝을 할 수 없고, 할 필요도 없습니다. 대신 파라미터 그룹(Terraform)과 DB 안의 계정·권한(Ansible)으로 나눠 관리합니다. 경계를 정해 두면 두 도구가 같은 것을 동시에 관리하는 일이 없습니다(23편).

계정 대장은 인벤토리 하나

base_users_list가 고객별 “서버 접근 권한 대장”입니다. 분기마다 이 파일을 고객과 함께 검토하고, 퇴사·전보 시 absent 처리 PR을 남기면 접근 권한 관리의 감사 증적이 됩니다.
