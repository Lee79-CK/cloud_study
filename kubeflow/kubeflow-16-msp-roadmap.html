이번 편에서 얻을 것

이 시리즈는 1편에서 “Kubeflow가 맞지 않는 경우”를 함께 말하며 시작했습니다. 마지막 편도 같은 정직함으로, MSP가 고객사에 Kubeflow를 제안하고 운영하는 전략을 정리합니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 고객사의 유형, 규모, 인프라, 규제, 운영 역량에 따라 Kubeflow를 권할지, 무엇과 어떤 구조로 권할지 판단할 수 있습니다.
  • MSP 표준 스택과 고객별 변형을 오버레이 계층으로 관리하고, 책임 분담을 명확히 할 수 있습니다.
  • 비용 구조와 GPU 사용률의 관계를 설명하고, 지킬 수 있는 SLA와 SLO를 설계할 수 있습니다.
  • 진단부터 성숙까지 단계별 도입 로드맵과 종료 기준을 세우고, 흔한 실패를 미리 막을 수 있습니다.

1MSP가 파는 것

오픈소스 Kubeflow 자체는 무료입니다. MSP가 파는 것은 13편부터 15편까지의 무게, 즉 안전하게 설치하고, 반년마다 올리고, 지켜보고, 고장 나면 고치는 일과, 고객의 데이터 과학자가 그 위에서 빨리 일하게 돕는 일입니다.

2고객 유형별 권장 구조

고객 유형흔한 상황권장첫 사용 사례
스타트업데이터 과학자 소수, 한 클라우드, 빠른 출시가 우선관리형 ML이나 가벼운 도구. Kubeflow는 팀이 커지고 비용이나 이식성이 문제될 때MLflow와 단일 서빙. 필요하면 KServe만
중견 제조공장 데이터 반출 제한, 온프레미스 GPU, 운영 인력 부족고객 전용 온프레미스 Kubeflow를 MSP가 운영 대행. 1편 9장의 사례비전 불량 검출의 정기 재학습 파이프라인
금융, 공공감사와 설명 책임, 망 분리, 변경 통제고객 전용(폐쇄망 포함) 설치, 13편 보안 전체, 레지스트리 메타데이터 표준화이상거래 탐지의 지속적 학습과 감사 대응
연구소, 대학여러 연구실의 GPU 공유, 노트북 중심공유 클러스터에 연구실별 프로필, Kueue 몫, time-slicing 노트북 풀노트북과 TrainJob, 큐 기반 GPU 공유
대기업 다팀여러 사업부, 사내 플랫폼 팀 존재, 표준화 요구사내 플랫폼 팀과 공동 운영. 표준 스택, 컴포넌트 라이브러리, GitOps팀 공통 파이프라인 템플릿과 레지스트리

어떤 유형이든 13편 1장의 원칙은 같습니다. 서로 다른 고객사는 클러스터(또는 설치)를 나누고, 한 고객사 안의 팀은 프로필로 나눕니다.

3권하지 말아야 할 때

좋은 MSP는 팔지 않을 때를 압니다. 운영 부담이 효익보다 큰 고객에게 Kubeflow를 넣으면, 결국 방치된 플랫폼과 실망한 고객이 남습니다.

신호왜대신 제안할 것
데이터 과학자 1~3명, 모델 몇 개플랫폼 운영비가 효익보다 큼MLflow, 관리형 노트북과 서빙
한 클라우드의 관리형 ML에 깊이 들어가 있음옮기는 비용 대비 효익이 작음현재 플랫폼 위의 MLOps 컨설팅, KFP 호환 관리형 파이프라인
서빙만 필요전체 배포판은 과함KServe 단독 운영(KServe 강의)
데이터 ETL이 대부분ML 기능이 쓰이지 않음Airflow나 데이터 플랫폼
고객이 업그레이드 작업 시간을 끝내 허락하지 않음반년 주기 업그레이드를 못 하면 지원이 끊긴 버전에 묶임상용 배포판의 장기 지원이나 관리형

4표준 스택과 고객별 변형

고객마다 다른 Kubeflow를 운영하면 MSP의 운영 지식이 쌓이지 않습니다. 14편의 오버레이를 한 층 더 쌓아, MSP 표준과 고객별 차이를 분리합니다.

platform/
├─ upstream/26.03.1/                # 원본 (14편)
├─ msp-standard/                    # MSP 표준: 모든 고객에 공통
│  ├─ observability/                 #   15편의 대시보드, 경보, 런북 링크
│  ├─ security/                      #   13편의 PSS, 입장 정책, NetworkPolicy
│  ├─ gateway-tls/, replicas-pdb/    #   14편
│  └─ components/                    #   표준 파이프라인 컴포넌트 라이브러리 (6편, 12편)
├─ customers/
│  ├─ acme-mfg/                      # 고객 A: 온프레미스, 폐쇄망
│  │  ├─ base/   (msp-standard + 이미지 미러, 사내 CA, 사내 IdP)
│  │  ├─ staging/
│  │  └─ prod/
│  └─ beta-fin/                      # 고객 B: 클라우드, 강한 감사
└─ fleet/                            # Argo CD ApplicationSet: 고객과 환경 목록
  • 버전 정책: MSP가 지원하는 Kubeflow 버전을 최신과 그 직전, 두 개로 제한합니다. 고객이 오래된 버전에 머물수록 MSP의 운영 비용이 커지므로 계약에 업그레이드 주기를 넣습니다.
  • 업그레이드 순서: 새 버전은 MSP 내부 검증 환경, 위험이 낮은 고객의 스테이징, 그다음 운영 순으로 퍼뜨립니다. 14편 8장의 절차를 고객마다 반복하지 않고 함대 단위로 돌립니다.
  • 고객별 차이는 목록으로: 표준에서 벗어난 설정은 이유와 함께 기록하고, 다음 업그레이드 때 표준으로 흡수할지 검토합니다.

5비용 모델

Kubeflow 플랫폼의 비용은 대개 GPU가 지배합니다. 그리고 GPU 비용의 효율은 사용률이 좌우합니다. 같은 돈을 내도 사용률이 두 배면 실제로 쓴 GPU 시간당 비용은 절반입니다. 고객사 예시 값으로 계산해 보세요(단위: 만 원, 월 기준).

GPU플랫폼 노드저장소, 네트워크운영 인력
MSP 과금 방식방법주의
운영비 고정 + 자원 실비플랫폼 운영 대행료는 월 고정, 클라우드나 장비 비용은 그대로 전달가장 흔하고 투명함. 고객이 사용률 개선의 이익을 직접 봄
GPU 시간 단가쓴 GPU 시간만큼 과금. 15편의 팀별 사용 시간 집계가 근거MSP가 유휴 자원의 위험을 짐. 단가 설계가 어려움
서비스 등급별 정액Basic(업그레이드와 지원), Standard(공동 운영), Premium(전체 운영 대행과 24시간 대응)등급마다 6장의 SLO와 1장의 책임 분담을 명시

고객사 안에서는 15편의 대시보드로 팀별 사용량을 보여 주는 쇼백(보여 주기)부터 시작하고, 합의가 되면 실제 비용을 나누는 차지백(청구하기)으로 갑니다.

지킬 수 있는 것만 약속합니다. 플랫폼이 통제하는 것과 통제하지 못하는 것을 나눕니다.

약속할 수 있는 것예시 목표근거 지표

백업과 복구복구 목표 시간과 시점14편 6장의 복구 훈련 결과

고객 앱의 서빙 SLA 전체앱, 네트워크, 모델이 함께 결정. 플랫폼 층의 가용성까지만

가용성 목표가 허락하는 한 달의 장애 시간(오류 예산)을 보세요.

8도입 로드맵

한 번에 전부 도입하지 않습니다. 단계마다 종료 기준을 두고, 기준을 넘어야 다음으로 갑니다. 막대를 누르면 내용이 나옵니다. 기간은 중간 규모 고객의 예시입니다.

9흔한 실패와 예방

실패모습예방
PoC에서 멈춤데모는 화려했는데 운영으로 넘어가지 못함PoC 때부터 운영 설치의 뼈대(14편)와 실제 사용 사례 하나를 끝까지
운영 인력 과소 계획설치 후 아무도 업그레이드와 경보를 보지 않음계약에 책임 분담과 운영 인력을 명시(1장)
업그레이드 방치지원이 끊긴 버전에 묶여 보안 패치도 못 함반기 업그레이드를 계약과 일정에 고정(4장)
GPU 낭비비싼 GPU의 사용률이 20%대컬링, 큐, 팀별 쇼백, 사용률 경보(4편, 11편, 15편)
보안은 나중에기본 계정으로 운영 시작, 사고 뒤 재설계파일럿 단계에서 13편의 점검표를 종료 기준에 포함
사용자 교육 부족데이터 과학자가 여전히 노트북에서 사흘짜리 학습이 시리즈의 Level 1~2를 온보딩 교육으로, 파이프라인 템플릿 제공
고객사 공유 클러스터한 고객의 사고가 다른 고객에게 번짐고객사마다 클러스터나 설치 분리(13편 1장)

레벨편얻은 것

13맺음말

  1. MSP가 파는 것은 Kubeflow가 아니라 안전하게 설치하고, 올리고, 지켜보고, 고치는 일과 데이터 과학자의 속도입니다. 책임 분담표가 계약의 중심입니다.
  2. 고객사는 클러스터로, 고객사 안의 팀은 프로필로 나눕니다. 권하지 말아야 할 고객에게는 더 가벼운 길을 제안합니다.
  3. MSP 표준 스택과 고객별 변형을 오버레이 계층으로 나누고, 업그레이드를 함대 단위로 돌립니다.
  4. 비용은 GPU가 지배하고, GPU 효율은 사용률이 좌우합니다. 약속은 플랫폼이 통제하는 것까지만 합니다.
  5. 진단, PoC, 파일럿, 확산, 성숙의 단계마다 종료 기준을 두고, 각 단계에서 이 시리즈의 해당 편을 교재로 씁니다.
