개발자가 아무것도 몰라도 되게 만들기

3편과 4편에서 개발자에게 부탁한 일들 — 에이전트 JAR 받기, 래퍼 명령 붙이기, 환경 변수 채우기, 포트 맞추기. 쿠버네티스에서는 이걸 전부 엔지니어가 가져올 수 있습니다. 개발자는 파드에 어노테이션 한 줄만 붙이면 됩니다. 아래에서 그 한 줄이 파드를 어떻게 바꾸는지 따라가 보세요.

SECTION 01

이 편의 목표

1편에서 그은 경계선을 쿠버네티스 위에서 최대한 엔지니어 쪽으로 밀어내는 것입니다.

작업3·4편 방식 (개발자가 함)8편 방식 (엔지니어가 함)
에이전트·SDK 설치Dockerfile에 JAR 복사, pip installinitContainer가 자동 주입
실행 명령 수정-javaagent, opentelemetry-instrument환경 변수로 자동 설정
엔드포인트·프로토콜개발자가 받아서 설정Instrumentation CR 한 곳에서 관리
샘플링 비율서비스마다 환경 변수CR에서 일괄 관리
에이전트 버전 업그레이드각 팀이 이미지 재빌드CR의 이미지 태그 변경 후 재시작
파드·노드 메타데이터—k8sattributes가 자동 부착
컨테이너 로그 수집—DaemonSet이 노드 로그 파일 수집

이 표가 완성되면 개발자에게 남는 일은 어노테이션 한 줄, 그리고 5·6편의 수동 계측뿐입니다. 수동 계측은 코드의 의미를 아는 사람만 할 수 있으므로 여전히 개발자 몫이고, 그 외 전부는 인프라가 흡수합니다.

MSP 관점에서 이 편이 가장 중요한 이유

고객사 개발팀에게 "이미지를 다시 빌드해 주세요"라는 요청은 협상 비용이 큽니다. 일정이 밀리고, 누락되고, 팀마다 다르게 적용됩니다. Operator 주입을 쓰면 요청이 "어노테이션을 붙여도 될까요"로 줄어듭니다. 그것마저 네임스페이스 단위로 걸면 고객사 개발팀이 전혀 관여하지 않아도 됩니다.

SECTION 02

OpenTelemetry Operator

Operator는 두 가지를 관리합니다. Collector 인스턴스와 워크로드 자동 계측. 각각 전용 커스텀 리소스가 있습니다.

OpenTelemetryCollector

Collector를 선언적으로 관리

7편의 설정 파일을 CR 안에 넣으면 Operator가 DaemonSet·Deployment·서비스·ConfigMap을 알아서 만들어 줍니다. 설정을 바꾸면 롤링 재시작도 처리합니다.

Instrumentation

자동 계측 설정의 단일 원천

엔드포인트, 샘플러, 전파기, 언어별 이미지를 한 곳에 정의합니다. 파드에 어노테이션이 붙으면 이 설정대로 주입됩니다.

설치

# 1. cert-manager — 웹훅 인증서 발급에 필요합니다
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/<버전>/cert-manager.yaml

# 2. Operator — Helm 권장
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm install otel-operator open-telemetry/opentelemetry-operator \
  --namespace observability --create-namespace \
  --set manager.collectorImage.repository=otel/opentelemetry-collector-contrib

# 확인
kubectl get pods -n observability
kubectl get crd | grep opentelemetry
cert-manager를 먼저 설치하세요

Operator의 자동 주입은 Mutating Admission Webhook으로 동작하고, 쿠버네티스 API 서버는 웹훅과 TLS로만 통신합니다. 인증서가 없으면 웹훅이 등록되지 않고, 그러면 어노테이션을 붙여도 아무 일도 일어나지 않습니다. 에러도 나지 않습니다. Helm 차트에는 인증서를 자체 생성하는 옵션도 있으니 cert-manager를 쓸 수 없는 환경이라면 그쪽을 확인하세요.

한 번에 설치하는 차트도 있습니다

Operator, Agent Collector, 클러스터 Collector, 기본 Instrumentation을 묶어 한 번에 올리는 Helm 차트(kube-stack 계열)도 제공됩니다. 처음 구성할 때 뼈대를 빠르게 세우는 용도로 좋습니다. 다만 무엇이 설치되는지는 반드시 values 파일을 읽고 확인하세요. 이 편의 내용을 이해한 상태에서 쓰면 도구가 되고, 모른 채 쓰면 블랙박스가 됩니다.

SECTION 03

OpenTelemetryCollector CR

7편의 설정 파일이 spec.config 안으로 들어갑니다. 바깥쪽에는 어떤 형태로 띄울 것인가를 정합니다.

mode: daemonset

Agent

노드마다 하나. 로그·노드 지표 수집, 파드 메타데이터 부착.

mode: deployment

Gateway

기본값. 레플리카 수를 정해 중앙 처리용으로 씁니다.

mode: statefulset

Target Allocator용

Prometheus 수집 대상을 레플리카에 고르게 나눌 때(9절).

mode: sidecar

파드 동거

어노테이션이 붙은 파드마다 컨테이너로 주입됩니다.

apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: otel-agent
  namespace: observability
spec:
  mode: daemonset
  serviceAccount: otel-agent             # 6절의 RBAC과 연결
  env:
    - name: K8S_NODE_NAME
      valueFrom:
        fieldRef: { fieldPath: spec.nodeName }
  volumes:                                # 7절 로그 수집용
    - name: varlogpods
      hostPath: { path: /var/log/pods }
  volumeMounts:
    - name: varlogpods
      mountPath: /var/log/pods
      readOnly: true
  resources:
    limits:   { cpu: 500m, memory: 512Mi }
    requests: { cpu: 100m, memory: 256Mi }
  config:
    receivers:
      otlp:
        protocols:
          grpc: { endpoint: 0.0.0.0:4317 }
          http: { endpoint: 0.0.0.0:4318 }
    processors:
      memory_limiter: { check_interval: 1s, limit_percentage: 80, spike_limit_percentage: 25 }
      k8sattributes:
        filter:
          node_from_env_var: K8S_NODE_NAME  # 자기 노드 파드만 감시
      batch: {}
    exporters:
      otlp/gateway:
        endpoint: otel-gateway-collector.observability:4317
        tls: { insecure: true }
    service:
      pipelines:
        traces:
          receivers:  [otlp]
          processors: [memory_limiter, k8sattributes, batch]
          exporters:  [otlp/gateway]
서비스 이름 규칙

Operator는 CR 이름 뒤에 -collector를 붙여 서비스를 만듭니다. otel-agent라는 CR을 만들면 서비스 이름은 otel-agent-collector가 됩니다. Instrumentation CR의 엔드포인트나 다른 Collector의 익스포터 주소를 적을 때 이 규칙을 기억하세요.

Agent로 보냈는데 다른 노드로 간다

DaemonSet Agent 앞의 서비스는 기본적으로 모든 노드의 Agent로 부하를 분산합니다. 앱이 서비스 이름으로 보내면 다른 노드의 Agent가 받을 수 있고, 노드 간 트래픽이 생깁니다. 노드 로컬 Agent로만 보내고 싶다면 서비스의 internalTrafficPolicy: Local을 쓰거나, 파드의 status.hostIP를 환경 변수로 받아 hostPort로 보내는 방식을 씁니다.

어노테이션 값의 의미

  

    

      
값의미언제 쓰나

      
        
"true"같은 네임스페이스의 Instrumentation CR을 사용네임스페이스마다 CR이 하나씩 있을 때

        
"my-inst"같은 네임스페이스의 특정 이름 CR 사용한 네임스페이스에 설정이 여러 벌일 때

        
"observability/my-inst"다른 네임스페이스의 CR 사용MSP 환경에서 권장. CR을 중앙 네임스페이스 한 곳에서 관리

        
"false"주입하지 않음네임스페이스 전체 적용에서 특정 파드만 제외할 때

      
    

  


  

    중앙 관리 패턴
    

      Instrumentation CR을 고객사 네임스페이스마다 만들면 버전·엔드포인트가 제각각 흩어집니다.
      observability 같은 운영 네임스페이스에 CR을 두고
      어노테이션에 "observability/default"처럼 네임스페이스를 명시하면
      에이전트 버전 업그레이드가 CR 한 곳 수정으로 끝납니다.
      1편의 회색지대 "SDK 버전 정책"이 여기서 실질적으로 해소됩니다.
    

  










  SECTION 05
  
주입이 안 될 때

  

    자동 주입은 실패해도 조용합니다. 파드는 정상적으로 뜨고, 단지 계측이 안 붙어 있을 뿐입니다.
    순서대로 따라가 보세요.
  


  

    

    

    

  


  
자주 틀리는 다섯 가지

  

    
Deployment 메타데이터에 붙임
어노테이션은 spec.template.metadata.annotations, 즉 파드 템플릿에 붙어야 합니다. Deployment 자체의 metadata에 붙이면 무시됩니다.

    
기존 파드가 그대로
웹훅은 파드가 생성될 때만 동작합니다. CR이나 어노테이션을 추가한 뒤에는 kubectl rollout restart가 필요합니다.

    
엉뚱한 컨테이너에 주입
기본은 파드의 첫 번째 컨테이너입니다. Istio 같은 사이드카가 앞에 오면 그쪽에 주입됩니다. container-names 어노테이션으로 지정하세요.

    
Python이 4317로 보냄
Python 자동 계측은 HTTP 프로토콜을 기본으로 씁니다. 엔드포인트가 4317이면 데이터가 안 들어갑니다. 언어별로 엔드포인트를 따로 지정하세요.

    
Alpine에서 Python 실패
Alpine은 musl 기반이라 glibc용으로 빌드된 패키지가 동작하지 않습니다. 플랫폼 어노테이션으로 musl용 이미지를 지정해야 합니다.

    
ResourceQuota에 막힘
주입되는 initContainer도 리소스를 요청합니다. 네임스페이스 쿼터가 빡빡하면 파드 생성 자체가 실패할 수 있습니다.

  


  

    앱이 이미 설정한 환경 변수는 존중됩니다
    

      앱 매니페스트에 이미 OTEL_SERVICE_NAME이 있다면 Operator는 그 값을 덮어쓰지 않습니다.
      개발자가 서비스 이름을 직접 선언하고 나머지는 CR이 채우는 역할 분담이 자연스럽게 성립합니다.
      반대로, 개발자 이미지 안에 오래된 엔드포인트가 하드코딩돼 있으면 CR을 아무리 고쳐도 반영되지 않습니다.
      3편에서 "앱 이미지에 -D로 OTel 설정을 넣지 말라"고 한 이유입니다.
    

  










  SECTION 06
  
k8sattributes — 메타데이터 자동 부착

  

    2편에서 "k8s.pod.name은 엔지니어가 붙인다"고 했습니다. 그 실체가 이 프로세서입니다.
  


  
동작 원리

  
    
    
  1. Collector가 쿠버네티스 API를 watch해서 파드 목록과 IP를 메모리에 유지합니다
    2. 
    
  2. 데이터가 들어오면 보낸 쪽의 IP를 확인합니다
    3. 
    
  3. 그 IP에 해당하는 파드를 찾아 네임스페이스·파드명·노드명·Deployment명·레이블을 붙입니다
    4. 
  

  

    핵심은 연결 IP로 파드를 식별한다는 점입니다.
    그래서 앱과 k8sattributes 사이에 다른 Collector가 끼어 있으면, 연결 IP가 그 Collector의 IP로 바뀌어 매칭이 틀어집니다.
    파드에서 직접 데이터를 받는 첫 번째 Collector(보통 Agent)에서 처리해야 하는 이유입니다.
  


  
필요한 권한


apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: otel-agent
rules:
  - apiGroups: [""]
    resources: [pods, namespaces, nodes]
    verbs: [get, watch, list]
  - apiGroups: [apps]
    resources: [replicasets]          # Deployment 이름을 알아내려면 필요
    verbs: [get, watch, list]
  - apiGroups: [""]
    resources: [nodes/stats]          # 8절 kubeletstats용
    verbs: [get]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: otel-agent
subjects:
  - kind: ServiceAccount
    name: otel-agent
    namespace: observability
roleRef:
  kind: ClusterRole
  name: otel-agent
  apiGroup: rbac.authorization.k8s.io


  

    권한이 없으면 조용히 빈 값이 됩니다
    

      RBAC이 부족해도 Collector는 죽지 않습니다. 단지 속성이 안 붙을 뿐입니다.
      "트레이스에 파드 이름이 안 보인다"는 제보가 오면 Collector 로그에서 forbidden 메시지를 먼저 찾아보세요.
      replicasets 권한만 빠지면 파드 이름은 보이는데 Deployment 이름만 비는 식으로, 부분적으로 실패하기도 합니다.
    

  


  

    대규모 클러스터라면 필터를 거세요
    

      기본값은 클러스터 전체 파드를 watch합니다. 노드가 수백 대면 Agent 하나하나가 수만 개 파드 정보를 들고 있게 됩니다.
      filter.node_from_env_var로 자기 노드 파드만 보게 하면 메모리와 API 서버 부하가 크게 줄어듭니다.
      3절 예제에 이 설정이 들어 있는 이유입니다.
    

  










  SECTION 07
  
컨테이너 로그 수집

  

    2편에서 "실무 기본값은 stdout 수집"이라고 했습니다.
    쿠버네티스는 컨테이너 stdout을 노드의 파일로 남기고, Agent가 그 파일을 읽습니다.
  



receivers:
  filelog:
    include:
      - /var/log/pods/*/*/*.log
    exclude:
      - /var/log/pods/observability_otel-agent-*/*/*.log   # 자기 로그는 반드시 제외
    include_file_path: true
    start_at: end                    # 재시작 시 처음부터 다시 읽지 않도록
    operators:
      - type: container              # CRI·Docker 포맷 자동 파싱 + 파드 정보 추출
        id: container-parser

extensions:
  file_storage:                      # 어디까지 읽었는지 기록
    directory: /var/lib/otelcol

service:
  extensions: [file_storage]
  pipelines:
    logs:
      receivers:  [filelog]
      processors: [memory_limiter, k8sattributes, batch]
      exporters:  [otlp/gateway]


  

    자기 로그를 제외하지 않으면 무한 루프
    

      Collector가 자기 로그를 읽으면 → 그걸 처리하며 로그를 남기고 → 그 로그를 또 읽는 순환이 생깁니다.
      특히 debug 익스포터를 켜둔 상태라면 순식간에 디스크와 로그 백엔드가 가득 찹니다.
      exclude에 Collector 파드 경로를 넣는 것을 잊지 마세요.
    

  


  
개발자에게 요청할 것은 하나

  

    이 방식에서 개발자가 할 일은 로그를 stdout으로 출력하고, 로그 줄에 trace_id를 포함하는 것뿐입니다.
    JSON 형식이면 파싱이 훨씬 쉬워지고, trace_id 필드를 Collector에서 추출해 LogRecord의 TraceId로 옮길 수 있습니다(9편 OTTL).
    5편의 로그 연결 절이 정확히 이 요청에 대응합니다.

노드와 클러스터 지표

  

    앱 텔레메트리만으로는 "노드 메모리가 부족해서 느렸다"를 알 수 없습니다.
    인프라 지표를 같은 파이프라인으로 모으면 신호 연결이 인프라까지 확장됩니다.
  


  

    

      
리시버수집 대상배포 위치주의

      
        
hostmetrics노드 CPU·메모리·디스크·네트워크Agent (DaemonSet)호스트 파일시스템을 마운트하고 root_path를 지정해야 컨테이너가 아닌 노드 값이 나옵니다

        
kubeletstats파드·컨테이너별 리소스 사용량Agent (DaemonSet)nodes/stats 권한 필요. 자기 노드의 kubelet에만 접근

        
k8s_cluster디플로이먼트 레플리카 수, 파드 상태, 노드 조건Deployment · 레플리카 1개여러 개 띄우면 같은 지표가 중복 수집됩니다

        
k8sobjects쿠버네티스 이벤트 (OOMKilled, 스케줄링 실패 등)Deployment · 레플리카 1개이벤트를 로그 신호로 수집. 장애 원인 추적에 매우 유용

      
    

  


  

    클러스터 Collector를 따로 두는 이유
    

      k8s_cluster와 k8sobjects는 클러스터 전체를 한 번만 봐야 하는 리시버입니다.
      DaemonSet에 넣으면 노드 수만큼 중복 수집되고, Gateway에 넣으면 레플리카 수만큼 중복됩니다.
      그래서 실무에서는 레플리카 1개짜리 전용 Collector를 하나 더 둡니다.
      10절 레퍼런스 구성의 세 번째 층이 이것입니다.
    

  


  

    이벤트 수집의 가치
    

      "파드가 재시작됐다"는 메트릭으로도 알 수 있지만, 왜 재시작됐는지는 이벤트에만 있습니다.
      OOMKilled, 이미지 풀 실패, 프로브 실패, 노드 압박으로 인한 축출.
      이것들을 트레이스·로그와 같은 백엔드에 모아두면 장애 분석 시 한 화면에서 원인을 찾을 수 있습니다.
      AIOps 파이프라인의 입력으로도 가치가 큰 데이터입니다.
    

  










  SECTION 09
  
기존 Prometheus 자산 흡수 — Target Allocator

  

    이미 Prometheus와 ServiceMonitor로 수집하고 있다면, 그 설정을 버리지 않고 Collector로 옮길 수 있습니다.
  


  

    문제는 규모입니다. Collector 하나가 수천 개 대상을 긁으면 버티지 못합니다.
    레플리카를 늘리면 각자 같은 대상을 중복으로 긁습니다.
    Target Allocator는 수집 대상 목록을 받아 Collector 레플리카들에게 고르게 나눠주는 조정자입니다.
  



apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: otel-prom
spec:
  mode: statefulset              # 대상 분배를 위해 고정 식별자 필요
  replicas: 3
  targetAllocator:
    enabled: true
    prometheusCR:
      enabled: true                # 기존 ServiceMonitor·PodMonitor를 그대로 읽음
      serviceMonitorSelector: {}
      podMonitorSelector: {}
  config:
    receivers:
      prometheus:
        config:
          scrape_configs: []       # Target Allocator가 채워 줍니다
    exporters:
      prometheusremotewrite:
        endpoint: http://mimir:9009/api/v1/push
    service:
      pipelines:
        metrics:
          receivers:  [prometheus]
          processors: [batch]
          exporters:  [prometheusremotewrite]


  

    마이그레이션 전략
    

      한 번에 옮기지 마세요. 기존 Prometheus를 그대로 두고 Collector를 병행해서 같은 대상을 양쪽에서 수집해 보고,
      값이 일치하는지 확인한 뒤 Prometheus 쪽을 끕니다.
      ServiceMonitor를 그대로 읽으므로 개발팀이 만들어둔 수집 설정은 한 줄도 바꿀 필요가 없습니다.

Agent CollectorDaemonSet

      
OTLP 수신, k8sattributes로 파드 메타데이터 부착, filelog로 컨테이너 로그 수집, hostmetrics·kubeletstats로 노드·파드 지표 수집. memory_limiter와 batch로 감싸고 Gateway로 보냅니다.

k8s_cluster로 클러스터 상태 지표, k8sobjects로 쿠버네티스 이벤트를 수집합니다. 반드시 레플리카 1개. 필요하면 Target Allocator를 쓰는 StatefulSet Collector를 별도로 둬 기존 Prometheus 대상을 흡수합니다.

    
↓

    
Gateway CollectorDeployment × N

      
테일 샘플링, 민감정보 마스킹, 테넌트 라우팅, 백엔드 인증을 한 곳에서 처리합니다. 테일 샘플링을 쓰면 Agent 쪽에 loadbalancing 익스포터를 둬 같은 trace_id가 같은 인스턴스로 오게 합니다. 9편의 주제입니다.

    
↓
