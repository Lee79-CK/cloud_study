01

시작하기 전에

장애 대응은 지식 싸움이 아니라 순서 싸움입니다. 아는 게 적어도 순서를 지키면 원인에 도달하고, 아는 게 많아도 순서를 건너뛰면 엉뚱한 곳을 고치게 됩니다.

장애 앞에서 지킬 세 가지

먼저 범위를 좁힌다Pod 하나인가, 한 노드의 전부인가, 클러스터 전체인가. 이 세 가지 중 어디인지만 알아도 볼 곳이 10분의 1로 줄어듭니다.
바뀐 것을 먼저 의심한다어제까지 잘 돌던 게 지금 안 된다면 누군가 뭔가를 바꿨습니다. 배포, 설정 변경, 노드 교체, 인증서 만료, 늘어난 트래픽 순으로 확인합니다.
추측 전에 출력을 본다"아마 메모리일 거예요"는 조치가 아닙니다. describe의 Events, 컨테이너 종료 코드, 노드 Condition처럼 클러스터가 이미 알려주고 있는 사실부터 읽습니다.
신입 엔지니어에게

모르는 상태값이 보여도 당황할 필요 없습니다. 쿠버네티스는 대부분의 문제를 이벤트(Event)에 한국어보다 친절한 영어 문장으로 적어 둡니다. kubectl describe 맨 아래 Events 섹션이 이 매뉴얼에서 가장 자주 보게 될 화면입니다.

정보 수집 순서이 순서를 외우면 절반은 끝납니다

어떤 증상이든 아래 다섯 단계를 위에서 아래로 훑습니다. 중간에 원인이 보이면 거기서 멈추면 됩니다.

1. 전체 상태어디가 아픈지 지도를 그립니다. kubectl get pod -A -o wide 로 Running이 아닌 것만 눈에 담습니다.
↓
2. 객체 상세kubectl describe pod <이름>. 맨 아래 Events, 그 위 State/Last State, Conditions 세 군데만 봅니다.
↓
3. 애플리케이션 로그kubectl logs <이름> --previous. 재시작한 Pod은 이전 컨테이너의 로그에 진짜 원인이 있습니다.
↓
4. 주변 객체Service·Endpoints·PVC·ConfigMap·Secret 등 그 Pod이 의존하는 것들이 제대로 존재하는지 확인합니다.
↓
5. 노드와 플랫폼노드 Condition, kubelet 상태, 컨트롤 플레인 지연. 여러 Pod이 동시에 아플 때 여기까지 내려갑니다.
1단계 — 정상이 아닌 것만 골라 보기

대규모 클러스터 주의

노드가 수백 대 넘어가면 kubectl get pods -A 한 번이 API 서버에 수십 MB 응답을 요구합니다. 장애 중에 이 명령을 반복하면 여러분이 두 번째 장애의 원인이 될 수 있습니다. 항상 -n <네임스페이스>, --field-selector, -l <라벨> 로 범위를 좁히세요.

쿠버네티스 객체 계층Pod이 죽었는데 왜 Deployment를 보나요?

Pod은 혼자 태어나지 않습니다. 위에서 아래로 이어지는 이 사슬 중 어느 고리가 끊겼는지 알면, 고쳐야 할 대상이 Pod이 아니라는 걸 알게 됩니다.

누가 누구를 만드는가
Deployment  # 사람이 만드는 것. "이 이미지를 3개 띄워줘"
    │
    └─▶ ReplicaSet  # Deployment가 만듦. 개수를 맞추는 역할
            │
            └─▶ Pod  # ReplicaSet이 만듦. 실제 컨테이너가 사는 집
                    │
                    ├─▶ Init Container   # 순서대로 실행되고 끝나야 함

# Pod을 지워도 다시 살아나는 이유: ReplicaSet이 개수를 맞추기 때문

03

Pod이 안 뜰 때

온콜에서 마주치는 문제의 7할은 이 장에 있습니다. Pod의 STATUS 한 단어가 이미 원인의 절반을 말해 주고 있으니, 그 단어를 정확히 읽는 법부터 시작합니다.

Pod은 이런 순서로 살아납니다

어느 단계에서 멈췄는지 알면 볼 곳이 정해집니다. Pending은 아직 노드도 못 정한 상태고, CrashLoopBackOff는 이미 노드에서 실행까지 갔다가 죽은 상태입니다. 둘은 완전히 다른 문제입니다.

Pod 생명주기와 각 단계에서 터지는 문제
[1] API 서버에 등록       실패하면 → 애초에 Pod이 안 만들어짐 (admission webhook, quota)
      ↓
[2] 스케줄러가 노드 선택   멈추면 → Pending
      ↓
[3] kubelet이 인수         멈추면 → ContainerCreating (CNI/CSI/Secret)
      ↓
[4] 이미지 내려받기        실패하면 → ImagePullBackOff
      ↓

Pending놓을 노드를 못 찾았습니다

3-1 · 스케줄러가 조건에 맞는 노드를 하나도 찾지 못한 상태. 컨테이너는 아직 시작조차 하지 않았습니다.

스케줄러는 모든 노드를 대상으로 거르고(filter) → 점수 매기고(score) → 배치합니다. 거르는 단계에서 전부 탈락하면 Pending에 머뭅니다. Events에 나오는 문장이 곧 탈락 사유입니다.

Events 메시지실제 의미
Insufficient cpu / Insufficient memory남은 request 합계가 부족. 실제 사용량이 아니라 예약량 기준입니다.
node(s) didn't match Pod's node affinity/selectornodeSelector 라벨이 붙은 노드가 없음. 오타이거나 노드 라벨이 빠짐.
node(s) had untolerated taint {key: value}노드에 taint가 있는데 Pod에 toleration이 없음.
pod has unbound immediate PersistentVolumeClaimsPVC가 아직 Bound가 아님. 스토리지 문제가 먼저입니다.
node(s) didn't find available persistent volumes to bind조건에 맞는 PV 없음 (용량·AZ·접근 모드).
node(s) didn't match pod topology spread constraints존/노드 분산 규칙 때문에 남은 자리가 배제됨.

Events가 비어 있음스케줄러 자체가 안 돌고 있을 가능성. 7장으로.
request와 실제 사용량은 다릅니다

kubectl top node에서 메모리 사용률이 40%인데도 Insufficient memory가 뜰 수 있습니다. 스케줄러는 예약된 request의 합만 보기 때문입니다. 아무도 안 쓰는데 크게 잡아둔 request가 자리를 차지하고 있는 상황이 대규모 클러스터에서 매우 흔합니다.

CrashLoopBackOff시작하자마자 죽기를 반복합니다

3-3 · 이건 상태가 아니라 패턴입니다. 컨테이너가 시작 → 종료 → 재시작을 반복하자 kubelet이 재시작 간격을 10초, 20초, 40초… 최대 5분까지 늘린 상태입니다.

원인은 크게 넷입니다. 종료 코드를 먼저 보면 어느 쪽인지 빠르게 갈립니다.

앱이 스스로 죽는다필수 환경변수 누락, DB 접속 실패, 설정 파일 파싱 에러. 종료 코드는 보통 1 또는 2. 로그에 이유가 찍혀 있습니다.
메모리 초과종료 코드 137. 시작 직후 메모리를 많이 쓰는 앱(JVM, 대용량 캐시 로딩)에서 자주 납니다.
프로브가 계속 실패liveness probe가 실패해 kubelet이 죽입니다. 앱은 멀쩡한데 probe 설정이 잘못된 경우가 많습니다.
애초에 계속 살 프로세스가 아니다종료 코드 0인데 재시작이 반복됩니다. 명령이 바로 끝나는 스크립트이거나, 앱이 백그라운드로 떠서 PID 1이 종료된 경우.

OOMKilled메모리 한도를 넘어 커널이 죽였습니다

3-4 · 종료 코드 137 (= 128 + 9, SIGKILL). 앱의 버그가 아니라 한도 설정과 실사용의 불일치인 경우가 많습니다.

컨테이너의 limits.memory는 리눅스 cgroup의 메모리 상한으로 설정됩니다. 그 선을 넘는 순간 커널의 OOM killer가 프로세스를 즉시 죽입니다. 경고도 유예도 없습니다.

컨테이너 OOM노드 OOM
범위그 컨테이너 하나노드 전체가 위험
표시Pod의 Reason이 OOMKilled노드에 MemoryPressure, Pod은 Evicted

3-5 · 컨테이너를 만들기도 전에 실패합니다. 로그가 아예 없으니 describe만 보면 됩니다.

  • 객체는 있는데 키 이름이 다름 — DB_PASSWORD vs db-password

Terminating삭제했는데 안 없어집니다

3-7 · 삭제 요청은 접수됐지만 완료되지 않은 상태. 원인에 따라 기다리면 되는 경우와, 절대 저절로 끝나지 않는 경우가 있습니다.

  1. 앱이 SIGTERM을 무시 — kubelet이 SIGTERM을 보낸 뒤 terminationGracePeriodSeconds(기본 30초)를 기다립니다. 그 안에 안 끝나면 SIGKILL. 즉 최대 30초 뒤에는 사라져야 정상입니다.
  2. finalizer가 걸려 있음 — 누군가(주로 오퍼레이터나 CRD 컨트롤러) 정리 작업을 예약해 뒀는데 그 컨트롤러가 죽어 있으면 영원히 Terminating입니다.
  3. 노드가 응답 없음 — kubelet과 통신이 끊기면 API 서버는 Pod이 정말 죽었는지 알 수 없어 지우지 못합니다. StatefulSet에서 특히 중요합니다.
--force --grace-period=0 을 습관으로 삼지 마세요

이 명령은 "Pod을 죽인다"가 아니라 "API 서버 기록에서 지운다"입니다. 노드가 살아 있다면 컨테이너는 계속 돌면서 볼륨을 잡고 데이터를 씁니다. StatefulSet(DB, 큐)에서 이렇게 하면 같은 볼륨에 두 프로세스가 붙어 데이터가 깨질 수 있습니다. 정말 노드가 죽었다고 확신할 때만 쓰세요.

원인 가려내기
# 1) finalizer가 있는가
$ kubectl get pod cache-node-2 -n prod -o jsonpath='{.metadata.finalizers}{"\n"}'
["kubernetes.io/pv-protection","storage.example.com/cleanup"]

# 2) 그 finalizer의 주인 컨트롤러가 살아 있는가
$ kubectl get pods -n storage-system

# 3) 이 Pod이 있는 노드는 정상인가
$ kubectl get pod cache-node-2 -n prod -o jsonpath='{.spec.nodeName}{"\n"}' | xargs kubectl get node
NAME            STATUS                     AGE
ip-10-40-7-33   NotReady                   62d

# 4) 삭제 요청 시각 — 언제부터 이 상태였나
$ kubectl get pod cache-node-2 -n prod -o jsonpath='{.metadata.deletionTimestamp}{"\n"}'
상황별 조치
  • 노드가 NotReady — 먼저 노드를 살리거나 완전히 종료시킵니다. 노드가 클러스터에서 제거되면 Pod도 정리됩니다.
  • finalizer 대기 — 컨트롤러를 복구하는 것이 정답입니다. 그 오퍼레이터가 이미 제거되어 영원히 돌아오지 않는 경우에만 finalizer를 수동으로 지웁니다.
  • graceful shutdown 지연 — 30초 넘게 걸리는 앱이라면 terminationGracePeriodSeconds를 실제 필요 시간에 맞춰 늘려 주세요. 강제 종료로 요청이 끊기는 것보다 낫습니다.
최후의 수단 — 영향 범위를 이해하고 쓰세요
# finalizer 제거 (컨트롤러가 영구히 없을 때만)
$ kubectl patch pod cache-node-2 -n prod -p '{"metadata":{"finalizers":null}}' --type=merge

# 강제 삭제 — 노드가 확실히 죽었을 때만
$ kubectl delete pod cache-node-2 -n prod --force --grace-period=0

Evicted노드가 자리를 비우라고 했습니다

3-8 · 노드의 자원이 부족해지면 kubelet이 스스로 Pod을 골라 쫓아냅니다. Pod 문제처럼 보이지만 노드 문제입니다.

kubelet은 메모리·디스크·inode가 임계치 아래로 내려가면 축출을 시작합니다. 순서는 QoS 클래스로 정해집니다.

QoS 클래스조건축출 순서
BestEffortrequest·limit 둘 다 없음가장 먼저 쫓겨남
Burstablerequest < limit 이거나 일부만 설정request 초과분이 큰 순서로
Guaranteed모든 컨테이너에 request = limit가장 늦게, 거의 마지막
중요한 워크로드는 Guaranteed로

request와 limit을 같은 값으로 맞추면 됩니다. 자원을 조금 더 예약하게 되지만, 노드가 흔들릴 때 살아남습니다. 반대로 배치 잡이나 개발 환경은 Burstable로 두어 여유를 나눠 쓰게 하는 것이 합리적입니다.

축출 사유와 노드 상태
$ kubectl get pod batch-run-9d2f-xm4kt -n batch -o jsonpath='{.status.message}{"\n"}'

# 어느 노드가 압박 상태인가
$ kubectl get nodes -o json | jq -r '.items[] | select(.status.conditions[] | select(.type|test("Pressure")) | .status=="True") | .metadata.name'

$ kubectl describe node ip-10-40-3-21 | grep -A8 Conditions
  Type             Status
  MemoryPressure   False
  DiskPressure     True
  PIDPressure      False
  Ready            True

# Evicted Pod 정리 (기록만 남아 있는 껍데기들)
$ kubectl get pods -A --field-selector status.phase=Failed -o json | jq -r '.items[] | select(.status.reason=="Evicted") | "\(.metadata.namespace) \(.metadata.name)"' | while read ns n; do kubectl delete pod -n "$ns" "$n"; done

축출이 반복된다면 Pod을 다시 띄우는 것으로는 해결되지 않습니다. 4장의 노드 압박으로 가서 노드 쪽을 고쳐야 합니다.

Init:Error준비 단계에서 멈췄습니다

3-9 · Init 컨테이너는 순서대로, 각각 성공적으로 끝나야 다음으로 넘어갑니다. 하나라도 실패하면 메인 컨테이너는 시작조차 하지 않습니다.

STATUS 표기의미

종료 코드 사전

컨테이너의 Exit Code는 원인을 좁히는 가장 빠른 단서입니다. 128보다 큰 값은 128 + 시그널 번호로 읽습니다.

코드의미보통 이런 상황
0정상 종료Job이면 성공. Deployment인데 이 값이면 앱이 계속 살아있지 않는 구조입니다.
1일반 애플리케이션 오류설정 오류, 예외 미처리, 의존 서비스 접속 실패
2셸 사용법 오류스크립트 문법 오류, 잘못된 인자

137과 143을 헷갈리지 마세요

둘 다 "누군가 죽였다"이지만 143은 예의 있게 부탁받고 응한 것(정상 배포)이고, 137은 말없이 죽임당한 것(OOM 또는 시간 초과)입니다. 배포 로그에서 143이 잔뜩 보인다면 그건 장애가 아닙니다.

04

노드가 이상할 때

Pod 여러 개가 동시에 아프다면 범인은 대개 Pod이 아닙니다. 노드 한 대의 문제가 그 위의 100개 Pod로 번지고, 노드 그룹의 문제가 서비스 전체로 번집니다.

노드 위에는 무엇이 사는가

노드에서 문제가 생기면 아래 네 가지 중 하나입니다. 어느 것인지 알면 볼 로그가 정해집니다.

kubelet노드의 대리인. API 서버와 통신하고 컨테이너를 띄웁니다. 이게 죽으면 노드는 NotReady가 됩니다.
containerd실제 컨테이너 런타임. 이미지를 받고 컨테이너를 실행합니다. 디스크가 차면 여기가 먼저 아픕니다.
kube-proxyService의 가상 IP를 실제 Pod IP로 연결하는 규칙을 관리합니다. 죽으면 새 Service만 안 됩니다.
CNI 플러그인Pod에 IP를 주고 노드 간 통신을 만듭니다. 죽으면 새 Pod이 ContainerCreating에서 멈춥니다.
기억할 한 가지

kubelet이 잠깐 죽어도 이미 돌고 있는 컨테이너는 계속 돕니다. 노드가 NotReady여도 서비스는 멀쩡할 수 있다는 뜻입니다. 반대로, 그 상태로 두면 5분 뒤 컨트롤러가 Pod을 다른 노드로 옮기기 시작하면서 진짜 영향이 생깁니다. 시간 감각이 중요합니다.

NotReady노드가 보고를 멈췄습니다

4-1 · kubelet은 기본 10초마다 상태를 보고합니다. 약 40초 동안 소식이 없으면 컨트롤러가 노드를 NotReady로 표시합니다.

노드가 죽었을 때 클러스터가 무엇을 언제 하는지 알면, 지금 얼마나 급한지 판단할 수 있습니다.

노드 장애 이후 자동으로 일어나는 일
T+0s    kubelet이 상태 보고를 멈춤
T+40s   노드 Ready 조건이 Unknown 으로 바뀜
       → 노드에 node.kubernetes.io/not-ready:NoSchedule taint 자동 부착
       → 이 시점부터 새 Pod은 이 노드로 안 감
T+40s   Service의 Endpoints에서 이 노드의 Pod이 빠짐 (readiness 기준)
       → 트래픽은 이때 이미 빠집니다
T+5m    tolerationSeconds(기본 300초) 만료
       → 컨트롤러가 이 노드의 Pod을 삭제하고 다른 노드에 재생성
       → 여기서부터 실제 재배치가 일어납니다
T+5m~  StatefulSet Pod은 예외 — 볼륨 안전 때문에 자동 재배치되지 않음
       → 수동 개입이 필요할 수 있습니다
대규모 클러스터에서의 연쇄

노드 20대가 동시에 NotReady가 되면 5분 뒤 수천 개 Pod이 한꺼번에 재스케줄됩니다. 남은 노드가 이를 감당 못 하면 Pending이 쏟아지고, 이미지 pull이 동시에 폭주하고, 그 부하로 또 다른 노드가 흔들립니다. 대규모에서는 노드 장애가 클러스터 장애로 번지는 경로가 항상 이 5분 구간입니다.

  --delete-emptydir-data \    # emptyDir 데이터 삭제 동의. 없으면 중단됩니다
  --grace-period=60 \

$ kubectl uncordon ip-10-40-3-21

통신이 안 될 때

"연결이 안 돼요"는 증상이 아니라 감상입니다. 어디에서 어디로 가다가 어디서 막혔는지를 나누는 순간, 원인은 대개 한두 개로 줄어듭니다.

5-1 · 요청 하나가 지나는 길

클러스터 밖에서 들어온 요청이 Pod에 닿기까지 다섯 개의 관문을 지납니다. 각 관문마다 다른 것이 고장 나고, 다른 명령으로 확인합니다. 아래에서 위로 올라가며 테스트하는 것이 가장 빠릅니다.

① 외부 → LB클라우드 로드밸런서. DNS 레코드, 보안그룹, 헬스체크 통과 여부.
↓
② LB → IngressIngress 컨트롤러 Pod. 호스트/경로 규칙 매칭, TLS 인증서.
↓
③ Ingress → ServiceService 이름 해석(DNS)과 백엔드 Service 존재 여부.
↓
④ Service → Endpointsselector가 Pod을 잡는지, 그 Pod이 Ready인지. 여기가 제일 자주 터집니다.
↓
⑤ Pod → 앱컨테이너가 그 포트로 실제 listen하는지, 0.0.0.0인지 127.0.0.1인지.

Endpoints 비어 있음Service가 가리키는 Pod이 없습니다

5-2 · 네트워크 장애 신고의 절반이 여기입니다. Service는 멀쩡히 존재하는데 뒤에 아무도 없는 상태입니다.

  1. selector가 Pod 라벨과 안 맞음 — 한 글자 오타, 또는 Deployment 라벨을 바꾸면서 Service를 안 고침.
  2. Pod이 Ready가 아님 — Endpoints에는 Ready인 Pod만 들어갑니다. readiness probe가 실패하면 Pod은 Running이어도 목록에서 빠집니다.
  3. 포트 이름·번호 불일치 — Service의 targetPort가 컨테이너의 실제 포트와 다름. 이름으로 참조할 땐 컨테이너 포트에 그 이름이 정의돼 있어야 합니다.
Running과 Ready는 다릅니다

READY 0/1인 Pod은 살아 있지만 트래픽을 받지 않습니다. 이건 버그가 아니라 설계된 동작입니다. 아직 준비 안 된 Pod에 요청을 보내지 않으려는 것이죠. 그래서 "Pod은 Running인데 왜 502죠?"의 답은 거의 항상 readiness probe입니다.

NetworkPolicy 차단방화벽이 조용히 막고 있습니다

5-4 · 로그도 에러도 없이 그냥 타임아웃만 납니다. 어제까지 되던 통신이 갑자기 안 된다면 정책이 추가됐는지 확인하세요.

  • 정책이 하나도 없으면 모든 통신이 허용됩니다.
  • 어떤 Pod에 정책이 하나라도 적용되면, 그 Pod은 그 방향(ingress/egress)에서 명시적으로 허용된 것만 통과시킵니다. 나머지는 전부 차단입니다.
  • ingress와 egress는 독립적입니다. egress 정책을 만들면서 DNS(53/UDP)를 허용하지 않으면 이름 해석부터 막힙니다. 이 실수가 정말 잦습니다.
  • 정책은 네임스페이스 범위입니다. 다른 네임스페이스에서 오는 트래픽은 namespaceSelector로 명시해야 합니다.
  • CNI가 정책을 지원해야 동작합니다. 지원하지 않는 CNI에서는 정책을 만들어도 아무 일도 일어나지 않습니다.

5-6 · 규모가 커져야 나타나는 네트워크 문제

노드 10대에서는 한 번도 못 본 것들이 노드 300대에서는 매주 생깁니다. 아래 세 가지는 대규모 클러스터 운영자가 반드시 알아 둬야 합니다.

conntrack 테이블 고갈노드의 커널이 추적하는 연결 수에 상한이 있습니다. 넘치면 새 연결이 조용히 버려지고, 증상은 "간헐적 타임아웃"으로 나타납니다.

07

컨트롤 플레인과 규모

여기가 아프면 클러스터 전체가 아픕니다. 그리고 이 영역의 문제는 대부분 규모가 커지면서 생깁니다. 작은 클러스터에서는 평생 안 볼 수도 있는 것들입니다.

컨트롤 플레인 구성 요소

kube-apiserver모든 요청의 관문. 여기가 느리면 kubectl도, 컨트롤러도, kubelet도 전부 느려집니다.
etcd클러스터의 유일한 진실. 디스크가 느리면 모든 것이 느려집니다.
kube-schedulerPod을 노드에 배치. 죽으면 새 Pod이 전부 Pending에 쌓입니다.
controller-manager선언된 상태를 실제로 맞추는 루프들. 죽으면 Deployment가 반응하지 않습니다.
구분 요령

새 Pod이 Pending에서 안 움직이면 스케줄러, 객체를 만들어도 아무 일도 안 일어나면 컨트롤러 매니저, kubectl 자체가 느리거나 타임아웃이면 API 서버나 etcd입니다. 이 세 갈래만 기억하면 컨트롤 플레인 문제의 방향은 잡힙니다.

API 서버 지연kubectl이 전부 느립니다

7-1 · 대규모 클러스터에서 가장 무서운 증상. 원인은 대개 "누군가 너무 큰 요청을 너무 자주 보내고 있다"입니다.

원인어떻게 알아보나
대량 LIST 요청특정 컨트롤러·에이전트가 get pods -A급 요청을 초당 여러 번. audit 로그에 대량으로 찍힙니다.
etcd 지연API는 멀쩡한데 응답이 느림. etcd 디스크 latency 지표를 봅니다.
watch 폭증Pod 수 × 컨트롤러 수만큼 watch가 열립니다. 메모리 사용량이 계속 증가합니다.
대용량 객체거대한 ConfigMap/Secret, 수천 개의 이벤트. 한 요청이 수십 MB가 됩니다.
APF로 인한 대기429 Too Many Requests. 공정성 제어가 요청을 줄 세우고 있습니다.
인증 백엔드 지연웹훅 인증/인가가 느리면 모든 요청이 그만큼 느려집니다.

최신 쿠버네티스는 요청을 우선순위별로 나눠 처리합니다. 그래서 특정 에이전트가 폭주해도 kubectl은 어느 정도 살아 있습니다. 429가 보인다면 장애가 아니라 보호 장치가 작동 중이라는 신호입니다. 누가 몰아치고 있는지 찾아야 합니다.

etcd 이상클러스터의 기억이 흔들립니다

7-2 · etcd는 디스크 지연에 극도로 민감합니다. 다른 모든 것이 정상인데 클러스터 전체가 느리다면 여기를 보세요.

항목기준넘으면
DB 크기 기본 한도2GB (권장 상한 8GB)알람 NOSPACE → 쓰기 전면 중단
디스크 fsync 지연p99 10ms 미만 권장리더 선출 반복, 전체 지연
멤버 간 네트워크 지연왕복 10ms 미만 권장합의 실패, 불안정
값 하나의 크기기본 1.5MB큰 ConfigMap/Secret 저장 실패
멤버 수3 또는 5 (홀수)짝수면 쿼럼 이점이 없습니다
NOSPACE 알람은 즉시 조치해야 합니다

etcd가 한도에 닿으면 모든 쓰기를 거부합니다. Pod 생성도, 상태 갱신도, 삭제도 안 됩니다. 클러스터가 통째로 얼어붙은 것처럼 보입니다. 조치는 compaction(오래된 리비전 정리) → defrag(공간 회수) → 알람 해제 순서이고, 이 작업은 멤버를 하나씩 순차적으로 해야 합니다.

7-3 · 대규모 클러스터의 공식 한계

쿠버네티스가 공식적으로 지원한다고 말하는 상한입니다. 이 숫자에 가까워지기 전부터 문제가 시작되므로, 70% 지점을 경계선으로 보는 것이 현실적입니다.

08

리소스와 스케줄링

Pending, OOM, 축출, 느린 응답까지 — 겉보기에 다른 문제들이 뿌리를 공유합니다. request와 limit을 제대로 이해하면 이 장의 문제 대부분이 사라집니다.

request와 limit은 전혀 다른 일을 합니다

request — 예약스케줄러가 자리를 잡을 때 쓰는 숫자입니다. "이만큼은 보장받고 싶다." 실제 사용량과 무관하게 노드의 자리를 차지합니다.
limit — 상한런타임이 강제하는 천장입니다. CPU는 스로틀링(느려짐), 메모리는 즉시 종료(OOMKilled). 두 자원의 처벌 방식이 완전히 다릅니다.
설정일어나는 일권장
둘 다 없음BestEffort. 자리 계산에서 0으로 취급되고 가장 먼저 축출됩니다.운영에서는 피하세요
request만자리는 보장, 상한 없음. 이웃 Pod을 굶길 수 있습니다.CPU에는 종종 합리적
limit만request가 limit과 같게 자동 설정됩니다.의도치 않은 Guaranteed
request < limitBurstable. 평소엔 적게, 필요하면 더.일반 워크로드의 기본
request = limitGuaranteed. 가장 안정적이고 가장 늦게 축출됩니다.중요 서비스, 지연에 민감한 앱
CPU limit은 생각보다 위험합니다

CPU limit에 닿으면 프로세스가 강제로 멈춰 세워집니다(cgroup throttling). 평균 사용률이 30%여도 순간적으로 몰리는 순간마다 스로틀링이 걸려 응답 지연(p99)이 크게 나빠집니다. "CPU는 여유로운데 느리다"는 신고의 흔한 정체입니다. 지연에 민감한 서비스라면 CPU limit을 넉넉히 잡거나, request만 정확히 잡고 limit은 두지 않는 선택지도 검토하세요.

CASE 01 · 배포 직후

새 버전을 올렸더니 전면 503, 그런데 Pod은 전부 Running

  • 14:02api-gateway v2.8 배포 시작. CI 파이프라인 정상 종료.
  • 14:05고객사 모니터링에서 5xx 급증 알림. 모든 요청이 503.
  • 14:06kubectl get pods — 6개 Pod 전부 Running. 재시작도 없음. 여기서 혼란이 시작됩니다.
  • 14:08READY 열을 봅니다. 전부 0/1. Running이지만 준비되지 않았습니다.
  • 14:09kubectl get endpoints api-gateway → <none>. Ingress가 보낼 곳이 없어 503을 반환하고 있었습니다.
  • 14:11이벤트에 Readiness probe failed: HTTP 404. 새 버전에서 헬스체크 경로가 /healthz에서 /health로 바뀌어 있었습니다.

  • 14:40probe 경로를 맞춘 v2.8.1 재배포. 정상.
배울 점

CASE 05 · 데이터가 걸린 판단

노드가 죽었는데 DB Pod이 다른 노드에서 안 뜹니다

  • 21:03노드 한 대 NotReady. 그 위에 PostgreSQL StatefulSet의 db-0이 있었습니다.
  • 21:085분 경과 후에도 db-0은 Terminating. StatefulSet은 자동 재배치되지 않습니다.
  • 21:10강제 삭제 후 새 노드에서 재생성 → Multi-Attach error. 볼륨이 아직 죽은 노드에 붙어 있습니다.
  • 21:13갈림길. 여기서 --force로 밀어붙이고 싶은 압박이 큽니다. 하지만 먼저 물어야 할 질문: 그 인스턴스는 정말 죽었는가?
  • 21:15클라우드 콘솔 확인 — 인스턴스는 running 상태였습니다. 네트워크만 끊긴 것이었고, PostgreSQL 프로세스는 계속 디스크에 쓰고 있었습니다. 여기서 강제로 붙였다면 두 프로세스가 같은 파일시스템에 쓰며 데이터가 손상됐을 것입니다.
  • 21:18인스턴스를 콘솔에서 정지. 볼륨 detach 확인.
  • 21:22노드 오브젝트 삭제 → 볼륨이 새 노드에 attach → db-0 정상 기동. 데이터 손상 없음.
배울 점

NotReady는 "노드가 죽었다"가 아니라 "노드와 연락이 안 된다"입니다. 이 둘의 차이가 데이터의 생사를 가릅니다. 스토리지가 걸린 상황에서 --force를 쓰기 전에는 반드시 인프라 계층에서 인스턴스 상태를 확인하세요. 19분이 걸렸지만 데이터는 살았습니다.
