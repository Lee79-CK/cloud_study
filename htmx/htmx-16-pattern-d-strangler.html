02

스트랭글러 피그의 다섯 단계

교살자 무화과(strangler fig)는 숙주 나무를 감싸 자라다가 결국 숙주를 대신하는 덩굴입니다. 소프트웨어에서는 옛 시스템 앞에 경로를 가로채는 층(여기서는 포털 게이트웨이)을 두고, 화면 하나씩 새 구현으로 넘기다가 옛 시스템이 받는 요청이 0이 되면 걷어 내는 방식을 말합니다.

0. 가로채기모든 경로를 게이트웨이 경유로. 동작은 100% 레거시 그대로
1. 그림자사용자는 레거시. 뒤에서 새 구현을 실행해 결과 비교
2. 일부 공개운영자 강제 지정 → 비율 배정(5% → 50%)
3. 전체 공개모드 new. 레거시는 대기 (즉시 되돌릴 수 있게)
4. 걷어 내기레거시 응답 0이 일정 기간 → 경로·코드·데이터 이관 정리

랩은 0단계에서 시작합니다. /customers와 /customers/:id는 처음부터 포털 게이트웨이를 거치지만, 플래그가 전부 legacy라 사용자는 예전과 똑같은 레거시 화면을 봅니다(측정: 첫 요청 X-Served-By: legacy, 제목 "누리로지스 - 고객사 관리 v1"). 쓰기(레거시 폼의 POST)는 처음부터 끝까지 레거시로 보냅니다. 읽기 화면부터 옮기는 것이 위험이 가장 적습니다.

    if (d.shadow) { /* 5절: 응답 후 새 구현 값 계산·비교 */ }

  05
  
그림자 비교

  
그림자(shadow) 모드에서 사용자는 레거시 화면을 받습니다. 게이트웨이는 응답을 보낸 뒤에 새 구현이 같은 화면에 보여 줄 핵심 값을 계산해 레거시와 비교하고 결과를 쌓습니다. 사용자 응답 시간에 영향이 없고, 새 구현이 오류를 내도 사용자는 모릅니다.

  
apps/server/src/app.js (그림자 비교 발췌)


if (d.shadow) {
  customerView(req, id).then(({ c, vms }) => {
    const diff = c.vmCount === vms.length ? null : `VM 수: 레거시 ${c.vmCount} / 새 구현 ${vms.length}`;
    flags.recordShadow({ key: 'customers.detail', id, name: c.name, ok: !diff, diff, rid: req.id.slice(0, 8) });
  }).catch(e => flags.recordShadow({ … ok: false, diff: `새 구현 오류: ${e.message}` … }));
}

  
측정: 그림자 모드에서 고객사 1과 2를 열자 플래그 화면에 "일치 · 한빛물산", "불일치 · 누리로지스 · VM 수: 레거시 11 / 새 구현 12"가 쌓였습니다. 레거시 CRM의 VM 수는 야간 배치로 복사해 둔 값이라 실제(포털 저장소의 12대)와 어긋나 있었던 것입니다. 이런 불일치는 새 구현의 버그일 수도, 이번처럼 레거시의 오래된 데이터일 수도 있습니다. 어느 쪽이 맞는지 판단하고 해결(배치 수정, 또는 새 구현 기준 채택)한 뒤에야 다음 단계로 넘어갑니다. 실제 서비스에서는 비교 결과를 지표(불일치율)로 내보내 대시보드로 봅니다(20편).

  

    
그림자 비교의 조건

    
그림자 쪽 실행은 읽기 전용이어야 합니다. 새 구현이 쓰기(메일 발송, 결제, 데이터 변경)를 하면 사용자가 한 번 누른 일이 두 번 일어납니다. 그래서 랩은 GET 상세에만 그림자 모드를 두었습니다. 또 그림자 실행도 업스트림(레거시 API)을 한 번 더 부르므로 부하가 늘어납니다. 비율과 함께 쓰거나 기간을 정해 켭니다.

  07
  
되돌리기와 걷어 내기

  

    
상황조치랩 측정

    
      
새 구현에서 오류·불만플래그를 legacy로 (배포 없음)모드 변경 직후 다음 요청부터 X-Served-By: legacy

      
특정 사용자만 문제그 사용자 브라우저를 ?ff=legacy로 고정하고 원인 조사쿠키 유지 확인

      
레거시 응답이 0인 기간이 충분히 지남① 플래그 제거(코드에서 분기 삭제) ② 게이트웨이의 레거시 전달 경로 삭제 ③ 레거시 화면 코드 삭제 ④ 데이터 주인 이관 ⑤ 레거시 서버 종료플래그 화면의 경로별 레거시·새 구현 응답 수로 판단

    
  

  
걷어 내기는 이관 못지않게 중요합니다. 플래그 분기가 코드에 남아 있으면 "어느 쪽이 지금 실제로 도는지"를 매번 확인해야 하는 부채가 됩니다. 플래그마다 만료 날짜와 담당자를 정해 두고, 응답 수 지표로 "레거시 0"을 확인한 뒤 위 순서대로 지웁니다.
