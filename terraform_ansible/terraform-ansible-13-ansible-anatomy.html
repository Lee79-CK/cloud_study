Terraform & Ansible 강의 · Level 3 Ansible 기초 · 13편 / 26편 · 시리즈 목차

에이전트 없이, SSH 하나로 Ansible 해부 — 에이전트리스 구조, 연결 방식, 인벤토리와 변수 파일, 호스트 패턴, ad-hoc, ansible.cfg, 2.19+ 템플릿 변화

Terraform이 서버를 만들었다면, 그 안을 구성하는 것은 Ansible의 몫입니다(1편 12장). Ansible은 관리할 서버에 아무것도 설치하지 않고 SSH로 접속해 작은 프로그램(모듈)을 보내 실행하고 결과를 받아 옵니다. 이번 편은 플레이북을 쓰기 전에, 그 밑에서 무슨 일이 일어나는지 — 어떻게 접속하고, 어느 서버에 어떤 값을 줄지 어떻게 정하고, 설정은 어디서 읽는지 — 를 실제 실행 결과로 해부합니다. ansible-core 2.19부터 크게 바뀐 템플릿 처리도 이번 편에서 먼저 짚습니다. 예전 자료의 코드가 지금은 오류가 나기 때문입니다.

컨트롤 노드

Ansible이 설치된 곳(내 PC, CI 러너). 여기서만 명령을 실행한다.

인벤토리

관리할 서버 목록과 그룹, 서버별 값.

관리 노드

SSH와 Python만 있으면 된다. 에이전트 없음.

이번 편의 목표와 실습 지도

이번 편을 마치면

  • Ansible이 에이전트 없이 동작하는 과정(접속 → 인터프리터 탐색 → 모듈 전송·실행 → JSON 결과)을 -vvv 출력으로 설명할 수 있습니다.
  • SSH 연결의 핵심 설정(키, 사용자, 연결 재사용, 파이프라이닝)과 Windows용 WinRM·SSH 연결의 차이를 압니다.
  • INI·YAML 인벤토리, 그룹과 자식 그룹, group_vars·host_vars의 우선순위를 ansible-inventory로 확인할 수 있습니다.
  • 호스트 패턴(와일드카드, 합·교·차집합, 정규식, 슬라이스)으로 대상을 정확히 고릅니다.
  • ad-hoc 명령으로 점검·간단한 변경을 하고, 멱등한 모듈과 그렇지 않은 모듈의 차이를 결과(CHANGED/SUCCESS)로 구분합니다.
  • ansible.cfg를 어디서 찾는지, 설정 값의 우선순위와 확인 방법을 압니다.
  • 2.19 이후의 데이터 태깅·템플릿 변화(불리언 아닌 조건식 오류, 표현식 속 템플릿 금지, 신뢰할 수 없는 문자열, 팩트 변수 주입 지원 중단)를 실측으로 확인합니다.

실측 환경에 대해

이 편의 출력은 ansible-core 2.21.5(2026년 10월 최신)로 실제 실행한 결과입니다. 2편 트랙 B(Docker)와 같은 구조 — 127.0.0.1의 2221·2222·2223 포트, ansible 사용자, lab_ed25519 키, 2편의 ansible.cfg·lab.ini 그대로 — 를 SSH 서버 3개로 재현해 실행했습니다. 다만 세 노드가 같은 운영체제 위에 있어 node3도 Ubuntu로 보고됩니다. 여러분의 2편 랩에서 node3는 Rocky 9이므로 배포판 관련 팩트가 다르게 나옵니다.

2편 설정은 랩 노드가 자주 다시 만들어지기 때문에 호스트 키 검사를 껐습니다. 고객 서버에서 끄면 중간자 공격을 탐지할 방법이 사라집니다. 운영에서는 True로 두고, 새 서버의 호스트 키는 ssh-keyscan 결과를 검증해 known_hosts에 넣거나, 클라우드에서는 인스턴스 콘솔 출력·SSM으로 지문을 확인하는 절차를 둡니다(19편).

4인벤토리: INI와 YAML

같은 구조, 두 가지 문법 — 그리고 값의 타입이 다르다

inventory/lab.ini (2편)
[ubuntu]
node1 ansible_host=127.0.0.1 ansible_port=2221
node2 ansible_host=127.0.0.1 ansible_port=2222

[rocky]
node3 ansible_host=127.0.0.1 ansible_port=2223

[lab:children]
ubuntu
rocky
inventory/lab.yml (같은 구조)
# lab.ini 과 같은 구조를 YAML로 (값의 타입이 그대로 유지된다)
all:
  children:
    lab:
      children:
        ubuntu:
          hosts:
            node1:
              ansible_host: 127.0.0.1
              ansible_port: 2221
            node2:
              ansible_host: 127.0.0.1
              ansible_port: 2222
        rocky:
          hosts:
            node3:
              ansible_host: 127.0.0.1
              ansible_port: 2223
# 실측: ansible-inventory --graph
@all:
  |--@ungrouped:
  |--@lab:
  |  |--@ubuntu:
  |  |  |--node1
  |  |  |--node2
  |  |--@rocky:
  |  |  |--node3
개념설명
all, ungrouped항상 존재하는 그룹. 모든 호스트는 all에, 어느 그룹에도 없으면 ungrouped에 속한다
자식 그룹 (:children, children:)그룹의 그룹. lab = ubuntu + rocky. 호스트는 여러 그룹에 동시에 속할 수 있다
범위 표기정의할 때 web[01:20].example.com처럼 여러 호스트를 한 줄로 (INI·YAML 모두)
인벤토리 디렉터리-i inventory/로 디렉터리를 주면 안의 파일을 모두 합친다. 정적 파일과 동적 플러그인(18편)을 섞을 수 있다

INI 값의 타입 함정 (실측)

# /tmp/ini_types.ini
[web]
node1 ansible_host=127.0.0.1 ansible_port=2221 http_port=8080 enable_tls=true

[web:vars]
max_conn=100
debug_mode=false

# 실측 (ansible-core 2.21.5): ansible … -m debug -a "msg={{변수|type_debug}}"
http_port:  int       # 숫자는 숫자로
enable_tls: str       # "true" 는 문자열! (파이썬 리터럴 True 가 아님)
max_conn:   int
debug_mode: str       # "false" 도 문자열 → 조건식에 쓰면 9장의 오류
불리언·목록·딕셔너리가 필요하면 YAML로

INI에서 true/false는 문자열이 됩니다. 2.18까지는 문자열 "false"를 조건에 쓰면 비어 있지 않은 문자열이라 참으로 평가되는 조용한 버그가 났고, 2.19부터는 “조건식 결과는 불리언이어야 한다” 오류가 납니다(9장). 연결 정보만 INI에 두고 나머지 변수는 YAML(group_vars·host_vars)에 두거나, 인벤토리 자체를 YAML로 쓰는 것이 안전합니다.

5group_vars·host_vars

값을 인벤토리 옆 디렉터리에 두고, 넓은 것에서 좁은 것 순으로 덮어쓴다

ansible/inventory/ ├── lab.yml ├── group_vars/ │ ├── all.yml # 모든 호스트 (가장 약함) │ ├── lab.yml # lab 그룹 │ ├── ubuntu.yml # ubuntu 그룹 (lab의 자식 → lab보다 강함) │ └── rocky.yml └── host_vars/ └── node3.yml # 이 호스트만 (그룹보다 강함)
group_vars/all.yml
# 모든 호스트의 기본값 (가장 약함)
ntp_server: time.example.com
http_port: 80
enable_tls: false
group_vars/ubuntu.yml
pkg_manager: apt
http_port: 8080
group_vars/rocky.yml · lab.yml
pkg_manager: dnf
env_name: lab
host_vars/node3.yml
# 이 호스트만 다른 값 (그룹 변수보다 강함)
http_port: 9090
enable_tls: true

변수 해석기 — 호스트를 고르면 각 값이 어느 파일에서 왔는지 보여 줍니다 (실측 결과 기준)

인벤토리 안에서의 우선순위 (약 → 강)비고
1. group_vars/all기본값
2. 부모 그룹 (lab)자식 그룹이 부모를 덮는다
3. 자식 그룹 (ubuntu, rocky)같은 깊이의 그룹끼리 겹치면 이름 알파벳순으로 뒤가 이긴다 → ansible_group_priority로 조정
4. host_vars/호스트인벤토리 안에서는 가장 강함

이것은 Ansible의 변수 우선순위 22단계 중 인벤토리 부분입니다. 플레이북의 vars, 역할 기본값, -e 추가 변수까지 포함한 전체 순서는 15편에서 다룹니다(-e가 항상 가장 강하다는 것만 먼저 기억하세요). group_vars·host_vars는 인벤토리 파일 옆 또는 플레이북 옆에 둘 수 있으며, 둘 다 있으면 플레이북 쪽이 더 강합니다.

결과 표시뜻

CHANGED바꿨음 (command·shell은 무엇을 했든 항상 CHANGED)
FAILED모듈이 실패를 보고
UNREACHABLE접속 자체가 안 됨 (SSH, 네트워크, 인증)
ad-hoc는 기록이 남지 않는 변경이다

ad-hoc 명령은 점검(ping, setup, 상태 조회)과 긴급 조치에 씁니다. 반복될 변경을 ad-hoc로 하면 1편의 “클릭 운영”과 같은 문제가 터미널에서 재현됩니다. 한 번이라도 다시 할 일이라면 플레이북(14편)으로 만들고 Git에 남기세요. 또한 command·shell로 할 수 있는 일 대부분에는 전용 모듈이 있고, 전용 모듈이 멱등합니다.

92.19+ 데이터 태깅·템플릿 변화

예전 자료의 플레이북이 지금은 오류가 나는 이유

ansible-core 2.19(Ansible 12)는 템플릿 엔진을 전면 개편하고 데이터 태깅(Data Tagging)을 도입했습니다. 모든 값에 “어디서 왔는가(파일·줄 위치), 믿을 수 있는가” 같은 꼬리표가 붙어, 오류 메시지가 정확한 위치를 가리키고 위험한 동작을 막을 수 있게 되었습니다. 그 대가로 예전에 조용히 넘어가던 코드가 오류를 냅니다. 아래는 2.21.5에서 실제로 실행한 결과입니다(실습 C).

변화예전 (≤ 2.18)지금 (2.19+, 실측 2.21.5)고치는 법
① 조건식은 불리언이어야 한다when: enable_tls (값 "true" 문자열) → 비어 있지 않으니 참오류: Conditional result (True) was derived from value of type 'str' … Conditionals must have a boolean result.when: enable_tls | bool, 목록이면 | length > 0, 정의 여부면 is defined
② 표현식 안에 {{ }} 금지when: "{{ n }} == 3" 은 경고만오류: Syntax error in expression. Template delimiters are not supported in expressionswhen: n == 3 (when·assert·changed_when 등은 이미 표현식)
③ 신뢰할 수 없는 문자열은 템플릿으로 실행하지 않음모듈 결과 등은 unsafe 표시로 막았지만 경로에 따라 새는 경우가 있었음명령 결과에 담긴 {{ 7 * 7 }}이 그대로 출력됨 (실행되지 않음)설계상 정상. 템플릿을 동적으로 조립하던 코드는 변수 참조로 바꾼다
④ 팩트의 최상위 변수 주입 지원 중단ansible_distribution지원 중단 경고: INJECT_FACTS_AS_VARS default to True is deprecated … will be removed from ansible-core version 2.24ansible_facts['distribution'] (ansible_ 접두사 없이)
⑤ INI의 true/false문자열이지만 ①이 조용히 참으로 처리①의 오류로 드러남 (4장 실측)YAML 변수 파일, 또는 | bool

ansible lab -b -m ansible.builtin.file -a 'path=/opt/iac-lab state=directory owner=deploy mode=0750'

#   실측(node1): 처음 CHANGED, 다시 하면 SUCCESS (changed: false)

ansible lab -C -b -m ansible.builtin.file -a 'path=/opt/check-mode state=directory'

ansible lab -b -m ansible.builtin.file -a 'path=/opt/iac-lab state=absent'
ansible lab -b -m ansible.builtin.user -a 'name=deploy state=absent remove=true'

관찰 1: command의 CHANGED

4번의 ls처럼 아무것도 바꾸지 않는 명령도 command 모듈은 CHANGED로 보고합니다. Ansible은 명령이 무엇을 했는지 모르기 때문입니다. 플레이북에서는 changed_when: false로 알려 줍니다(14편).

관찰 2: 점검 모드의 한계

점검 모드는 모듈이 지원할 때만 정확합니다. command·shell은 점검 모드에서 실행을 건너뛰고, 앞 단계의 결과에 의존하는 작업(패키지를 설치해야 생기는 설정 파일 등)은 점검 모드에서 실패할 수 있습니다. 14편의 --check --diff로 이어집니다.

15MSP 현장 팁

고객사 서버 수백 대에 Ansible을 붙일 때

접속 계정과 키를 표준화

고객마다 전용 자동화 계정(예: svc-ansible)과 키를 두고, sudo 권한 범위를 문서화합니다. 사람 계정으로 자동화하지 않습니다. 키 교체 주기와 절차는 19편에서 다룹니다.

인벤토리는 고객·환경 단위로

8편과 같은 원칙: inventories/custa-prd/, inventories/custa-dev/처럼 나누고 실행 시 -i로 명시합니다. ansible.cfg의 기본 인벤토리를 운영으로 두면 실수로 운영에 실행하는 사고가 납니다.

첫 접속 점검표

새 고객 서버를 받으면: ① ping 전체 ② setup -a filter=ansible_distribution*로 OS 분포 ③ Python 버전(구형 서버는 3.9 미만일 수 있음 → 대상 Python 업그레이드나 구버전 ansible-core 필요) ④ sudo 동작 ⑤ 호스트 키 수집. 이 결과가 고객 서버 현황표가 됩니다.

오래된 플레이북 인수인계

고객이 쓰던 플레이북을 받으면 사용하던 ansible-core 버전부터 확인합니다. 2.18 이하용이면 9장의 변화 때문에 바로 실패할 수 있습니다. 같은 버전으로 실행 환경을 고정해 두고(20편 Execution Environment), 별도 작업으로 2.19+ 이전을 계획합니다.

ad-hoc 사용 규칙

ad-hoc는 조회와 긴급 조치에만, 변경은 플레이북과 PR로. 긴급 ad-hoc 변경을 했다면 같은 날 플레이북에 반영합니다(Terraform의 드리프트 규칙과 같은 원칙, 9편).

Windows 서버가 섞여 있다면

국내 고객사에는 Windows 서버가 흔합니다. WinRM(HTTPS, Kerberos)과 OpenSSH 중 고객 보안 정책에 맞는 방식을 정하고, Windows 그룹은 별도 그룹·변수 파일로 분리합니다. 모듈도 ansible.windows 컬렉션으로 달라집니다.

18과제

실습 A~C를 마친 뒤에 풀어 보세요

과제 1. 같은 깊이 그룹의 충돌

node1을 ubuntu 그룹과 새 그룹 webservers에 동시에 넣고, 두 그룹의 group_vars에 서로 다른 http_port를 주세요. node1의 값은 무엇이 되나요? ansible_group_priority로 결과를 뒤집어 보세요.

해설

같은 깊이의 그룹은 이름 알파벳순으로 병합되어 뒤(webservers가 ubuntu보다 뒤)가 이깁니다. group_vars/ubuntu.yml에 ansible_group_priority: 10을 주면 우선순위가 높아져 ubuntu 값이 이깁니다(기본 1). 이런 겹침이 생기지 않게 그룹을 역할(webservers)과 속성(ubuntu)으로 나누고, 같은 변수를 두 축에서 정의하지 않는 것이 더 좋은 해법입니다.

과제 2. 파이프라이닝 효과 측정

time ansible lab -m setup > /dev/null을 파이프라이닝 켬·끔(ANSIBLE_PIPELINING=False), ControlPersist 소켓 삭제 전·후로 비교하세요. 무엇이 가장 큰 차이를 만드나요?

과제 3. INI를 YAML로, 타입 바로잡기

4장의 ini_types.ini를 YAML 인벤토리로 옮기고, 네 변수의 타입이 int·bool·int·bool이 되는지 type_debug로 확인하세요. 9장의 ①번 오류가 사라지는지도 확인합니다.

과제 4. Windows 인벤토리 설계

“도메인에 가입된 Windows Server 3대와 리눅스 5대”를 관리하는 인벤토리를 YAML로 설계하세요. 연결 변수는 어느 그룹에 두나요? 비밀번호는 어디에 두면 안 되나요?

해설 요지

windows 그룹의 group_vars에 ansible_connection: winrm, 포트 5986, Kerberos 전송을 두고, 리눅스는 ssh 기본값. 비밀번호·키는 인벤토리 평문에 두지 않고 Ansible Vault나 외부 비밀 저장소로(19편).

과제 5. 고객 서버 현황표 만들기

ad-hoc 명령만으로 lab의 각 노드에 대해 “호스트명, 배포판·버전, Python 버전, CPU 수, 메모리(MB), 루트 디스크 사용률”을 모으는 방법을 찾고, 결과를 표로 정리하세요. 어떤 값은 setup 팩트에 있고 어떤 값은 명령이 필요한가요?

힌트

setup -a 'filter=ansible_distribution*,ansible_python_version,ansible_processor_vcpus,ansible_memtotal_mb'로 대부분 해결되고, 디스크 사용률은 ansible_mounts 팩트나 df 명령으로. --tree 옵션(지원 중단 여부 확인)이나 JSON 콜백으로 저장해 가공하는 방법도 있습니다. 15편에서 팩트와 템플릿으로 이 표를 자동 생성합니다.
