01시작하기 전에

랩은 실험실이자, 앞으로 고객 환경에 가져갈 표준 배포의 축소판입니다.

이 랩의 설계 원칙

  1. 공존: 같은 클러스터의 기존 RAG 플랫폼을 건드리지 않습니다. 네임스페이스·노드 지정·할당량·네트워크 정책으로 경계를 긋고, 클러스터 공용 구성 요소(GPU Operator 등)는 이미 있으면 재설치하지 않습니다.
  2. 재현성: 이미지 태그, 모델 리비전(커밋 해시), 엔진 옵션을 파일로 고정하고 Git으로 관리합니다. 결과를 남길 때 이 값들도 같이 남깁니다(3·5편의 보고 규칙).
  3. 교체 가능성: 엔진·모델·정밀도를 바꿀 때 디렉터리 하나(오버레이)만 바꾸도록 구조화합니다. 이후 편의 실험이 모두 이 방식으로 이루어집니다.
  4. 한 번 받기: 모델은 Job으로 한 번 내려받아 PVC에 캐시하고, 엔진은 오프라인 모드로 그 경로만 읽습니다(6편의 반입 원칙).

학습 목표

  1. RKE2 클러스터에서 GPU Operator의 설치 상태·버전·GB10 호환성을 점검하고, 필요할 때 안전하게 설치·검증할 수 있다.
  2. 할당량·LimitRange·NetworkPolicy·Pod Security를 갖춘 서빙 전용 네임스페이스를 설계할 수 있다.
  3. 모델 캐시 스토리지 방식을 비교하고, 다운로드 Job + PVC + 오프라인 로딩 구조를 만들 수 있다.
  4. Ingress 대신 Gateway API(Envoy Gateway)로 입구를 열고, 스트리밍에 맞는 타임아웃을 설정할 수 있다.
  5. kustomize 베이스·오버레이로 엔진과 모델을 교체 가능한 기준 배포를 만들고 스모크 테스트로 검증할 수 있다.
  6. 이후 편에서 쓸 측정 도구와 lab.sh 도우미를 갖추고, 문제를 계층별로 진단할 수 있다.
1~6편 매니페스트와 달라지는 점
  • runtimeClassName: GPU Operator v25.10 이상은 CDI(Container Device Interface) 방식을 써서 워크로드에 runtimeClassName: nvidia가 더 이상 필요 없습니다. 이전 편 예제에 들어 있던 이 줄은 클러스터에 해당 RuntimeClass가 없으면 오히려 Pod 생성을 실패시킵니다. 이번 랩에서는 기본으로 빼고, 필요한 환경에서만 켜는 구성 요소로 분리했습니다(8장).
  • 노드 지정: 지금까지는 kubernetes.io/arch: arm64로 GB10 노드를 골랐습니다. P3 워크스테이션에도 GPU(RTX A400)가 있어 GPU Operator가 두 노드 모두에 nvidia.com/gpu를 광고할 수 있으므로, 이번부터는 명시적인 노드 라벨(llm-lab/role=gpu-serving)을 씁니다.
  • 모델 로딩: emptyDir에 매번 내려받던 방식에서 PVC 캐시 + 오프라인 모드로 바뀝니다.

04GPU Operator 설치·검증

이미 있으면 검증만, 없으면 RKE2 방식으로 설치. 어느 쪽이든 GB10 특유의 함정을 피합니다.

결정 규칙

현재 상태할 일
설치됨, v25.10 이상, GPU 노드에 nvidia.com/gpu 광고됨건드리지 않는다. 검증 Pod만 돌린다. 기존 RAG 플랫폼이 이 구성에 의존하고 있다.
설치됨, 구버전(v25.3 이하)업그레이드는 랩이 아니라 유지보수 작업으로 따로 계획한다(기존 워크로드 영향). 랩은 runtimeClassName 구성 요소를 켜서 진행.
설치됨, GB10에서 device plugin이 재시작 반복device plugin이 오래된 버전일 가능성. GB10의 통합 메모리는 NVML 메모리 조회가 “Not Supported”라, 구버전 device plugin이 이 때문에 죽는 문제가 알려져 있다. 최신 GPU Operator로의 업그레이드를 계획한다.
미설치아래 RKE2 HelmChart 방식으로 설치. containerd가 재시작되며 RKE2 에이전트가 재시작되므로 기존 Pod에 영향이 있다. 작업 시간을 잡는다.

설치 (미설치인 경우만)

RKE2 공식 문서는 GPU Operator를 RKE2 내장 Helm 컨트롤러의 HelmChart 리소스로 설치하는 방법을 안내합니다. v25.10 이상은 CDI를 사용하고 containerd 2.0 이상이 필요합니다. DGX OS(PGX 포함)는 드라이버가 미리 설치되어 있으므로 드라이버 설치는 끕니다.

yaml · 00-platform/gpu-operator-helmchart.yaml
apiVersion: helm.cattle.io/v1
kind: HelmChart
metadata:
  name: gpu-operator
  namespace: kube-system
spec:
  repo: https://helm.ngc.nvidia.com/nvidia
  chart: gpu-operator
  version: v26.3.2                 # RKE2 문서 기준 예시. 설치 시점의 최신 지원 버전 확인
  targetNamespace: gpu-operator
  createNamespace: true
  valuesContent: |-
    driver:
      enabled: false               # DGX OS·P3 모두 호스트 드라이버 사용
    toolkit:
      env:
      - name: CONTAINERD_SOCKET
        value: /run/k3s/containerd/containerd.sock    # RKE2의 containerd 소켓 경로
bash · 설치와 진행 확인
kubectl apply -f 00-platform/gpu-operator-helmchart.yaml
kubectl -n kube-system get pods -l helmcharts.helm.cattle.io/chart=gpu-operator -w   # helm-install Job 완료 대기
kubectl -n gpu-operator get pods -w                                                  # validator가 Completed가 될 때까지

검증 (설치 여부와 무관하게 항상)

bash · GPU 노드 라벨 지정과 검증
# 1) 랩 전용 노드 라벨 (PGX 노드 이름으로 바꿔서)
kubectl label node <PGX노드> llm-lab/role=gpu-serving --overwrite

# 2) 운영자가 붙인 라벨과 할당 가능 GPU
kubectl get node <PGX노드> -o jsonpath='{.metadata.labels}' | tr ',' '\n' | grep nvidia.com
kubectl get node <PGX노드> -o jsonpath='{.status.allocatable.nvidia\.com/gpu}'; echo

# 3) GPU 검증 Pod (CUDA 이미지 태그는 드라이버가 지원하는 CUDA 버전 이하로)
cat <<'YAML' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: gpu-check, namespace: default }
spec:
  restartPolicy: Never
  nodeSelector: { llm-lab/role: gpu-serving }
  tolerations: [ { key: nvidia.com/gpu, operator: Exists, effect: NoSchedule } ]
  containers:
  - name: smi
    image: nvcr.io/nvidia/cuda:13.0.1-base-ubuntu24.04
    command: ["nvidia-smi"]
    resources: { limits: { nvidia.com/gpu: 1 } }
YAML
kubectl wait --for=jsonpath='{.status.phase}'=Succeeded pod/gpu-check --timeout=5m
kubectl logs gpu-check && kubectl delete pod gpu-check

로그에 GB10이 보이면 성공입니다. runtimeClassName 없이 성공했다면 CDI 경로가 동작하는 것이므로 8장의 runtimeclass 구성 요소는 필요 없습니다. “RuntimeClass not found”나 GPU를 못 찾는 오류가 나면 Operator 버전을 확인하고, 구버전이면 runtimeclass 구성 요소를 켭니다.

GPU를 RAG 플랫폼과 나눠 써야 할 때

PGX의 GPU는 하나라 RAG 플랫폼 Pod가 nvidia.com/gpu: 1을 쥐고 있으면 랩 Pod는 Pending이 됩니다. 두 가지 방법이 있습니다.

  1. 시간으로 나누기(권장): 실습하는 동안만 RAG 플랫폼의 GPU 워크로드를 0으로 줄였다가 되돌립니다. 가장 안전합니다.
  2. 타임 슬라이싱: GPU Operator의 device plugin 설정으로 GPU 하나를 여러 개로 광고하게 합니다. 하지만 메모리 격리가 전혀 없고, GB10은 메모리를 CPU와 공유하므로 두 엔진의 메모리 비율 합과 OS 사용량을 사람이 직접 관리해야 합니다. 클러스터 전체 설정이 바뀌는 작업이므로 8편에서 원리와 함께 다룹니다.

05서빙 전용 네임스페이스

네임스페이스는 이름표가 아니라 울타리입니다. 자원·네트워크·보안 수준을 함께 정합니다.

장치랩 설정왜
라벨 규칙llm-lab/part(serving·models·tools), llm-lab/engine, llm-lab/variant정리·조회·정책 선택자의 기준. 이후 지표 라벨로도 쓰임
ResourceQuotaGPU 1, CPU·메모리 요청 상한, PVC 수실수로 GPU를 여러 개 잡거나 노드 자원을 독점하지 않게
LimitRange기본 요청·상한쿼터가 걸리면 모든 Pod에 요청량이 필요하므로 기본값 제공
NetworkPolicy기본 수신 차단 → 같은 네임스페이스·게이트웨이·모니터링만 허용엔진 포트는 /metrics·관리 경로까지 열려 있다(4편). 외부 직접 접근 차단
Pod Securityenforce: baseline, warn: restricted권한 상승·hostPath 같은 위험 설정 차단, 강화 방향은 경고로 확인

apiVersion: v1
kind: Namespace
metadata:
  name: llmsvc-lab
  labels:
    llm-lab/managed: "true"
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/warn: restricted
---
apiVersion: v1
kind: ResourceQuota
metadata: { name: lab-quota, namespace: llmsvc-lab }
spec:
  hard:
    requests.nvidia.com/gpu: "1"        # GPU는 확장 자원이라 requests. 접두어로 지정
    requests.cpu: "24"
    requests.memory: 96Gi
    persistentvolumeclaims: "5"
---
apiVersion: v1
kind: LimitRange
metadata: { name: lab-defaults, namespace: llmsvc-lab }
spec:
  limits:
  - type: Container
    defaultRequest: { cpu: 250m, memory: 256Mi }
    default:        { cpu: "2",  memory: 2Gi }
yaml · 10-namespace/netpol.yaml
# 1) 기본: 모든 수신 차단

07네트워크: Service와 Gateway

클러스터 안은 Service, 클러스터 밖에서 들어오는 입구는 Gateway API.

왜 Ingress가 아니라 Gateway API인가

  • 쿠버네티스 커뮤니티의 ingress-nginx는 2026년 3월로 지원이 종료되었습니다. RKE2도 v1.36부터 새 클러스터의 기본 입구를 Traefik으로 바꾸고 기존 클러스터용 이전 가이드를 제공합니다. 기존 클러스터에 ingress-nginx가 남아 있을 수 있으니 3장 점검 결과를 확인하세요.
  • 11편의 Gateway API Inference Extension(InferencePool·Endpoint Picker)은 Gateway API 위에서 동작합니다. 지금 Gateway API로 시작하면 11편에서 엔진 앞단만 교체하면 됩니다.
  • Envoy Gateway는 Gateway API의 GA 구현체 중 하나이고, Inference Extension을 지원하는 게이트웨이 계열이며, 12편에서 볼 Envoy AI Gateway의 기반이기도 해서 랩의 입구로 택했습니다. 이미 Traefik·Istio·kgateway 같은 다른 Gateway API 구현을 쓰고 있다면 그것을 써도 Gateway·HTTPRoute 매니페스트는 거의 그대로 쓸 수 있습니다(GatewayClass만 다름).

def get(url, timeout=10):
    with urllib.request.urlopen(url, timeout=timeout) as r:
        return r.status, r.read().decode()

def post(url, body, timeout=120):
    req = urllib.request.Request(url, json.dumps(body).encode(), {"Content-Type": "application/json"})
    return urllib.request.urlopen(req, timeout=timeout)

def health():
    s, _ = get(a.engine + "/health"); assert s == 200, s; return "200"

model = {}
def models():
    _, b = get(a.engine + "/v1/models"); ids = [m["id"] for m in json.loads(b)["data"]]
    model["id"] = ids[0]; return ", ".join(ids)

def chat():
    r = post(a.engine + "/v1/chat/completions", {"model": model["id"], "max_tokens": 64,
          "messages": [{"role": "user", "content": "랩 스모크 테스트입니다. 한 문장으로 인사해 주세요. /no_think"}]})
    o = json.loads(r.read()); txt = o["choices"][0]["message"]["content"] or ""
    assert txt.strip(), "빈 응답"; return f"{txt.strip()[:40]}… (출력 {o['usage']['completion_tokens']}토큰)"

def stream():
    t0 = time.perf_counter()
    r = post(a.engine + "/v1/chat/completions", {"model": model["id"], "max_tokens": 64, "stream": True,
          "messages": [{"role": "user", "content": "하나부터 다섯까지. /no_think"}]})
    first, n = None, 0
    for line in r:
        if line.startswith(b"data: ") and b'"content"' in line:
            first = first or time.perf_counter(); n += 1
    assert first, "스트림 청크 없음"; return f"TTFT {(first - t0) * 1000:.0f} ms, 청크 {n}개"

def metrics():
    _, b = get(a.engine + "/metrics"); k = [l for l in b.splitlines() if l.startswith("vllm:")]
    assert k, "vllm: 지표 없음"; return f"vllm: 지표 {len(k)}줄"

def gw_models():
    _, b = get(a.gateway + "/v1/models"); return "게이트웨이 경유 OK: " + json.loads(b)["data"][0]["id"]

def gw_metrics_blocked():
    try:
        s, _ = get(a.gateway + "/metrics")
    except urllib.error.HTTPError as e:
        return f"차단됨 ({e.code})"
    raise AssertionError(f"/metrics가 게이트웨이로 노출됨 ({s})")

check("엔진 /health", health)
check("엔진 /v1/models", models)
if model:
    check("채팅 응답", chat)
    check("스트리밍 TTFT", stream)
check("지표 /metrics", metrics)
if a.gateway:
    check("게이트웨이 /v1/models", gw_models)
    check("게이트웨이 /metrics 차단", gw_metrics_blocked)

for ok, name, detail, dt in results:
    print(f"{'PASS' if ok else 'FAIL'}  {name:<22} {dt*1000:7.0f} ms  {detail}")
sys.exit(0 if all(r[0] for r in results) else 1)

bash · lab.sh
#!/usr/bin/env bash
#> llm-lab 도우미 — 사용: ./lab.sh <명령> [인자]
#>   preflight            클러스터·GPU·스토리지·입구 상태 점검
#>   init                 네임스페이스·PVC·게이트웨이·bench Pod 생성 (반복 실행 안전)
#>   download REPO [REV]  모델을 model-cache PVC로 받기 (예: Qwen/Qwen3-8B-FP8 <커밋해시>)
#>   up OVERLAY           30-serving/overlays/OVERLAY 배포 + 설정 스냅샷 기록
#>   down                 엔진 내리기 (PVC는 유지)
#>   status | logs [N]    상태 · 엔진 로그
#>   gwurl                게이트웨이 접속 주소 출력
#>   smoke                계층별 스모크 테스트
#>   bench LABEL          engine_bench 실행 후 결과를 /results에 저장
#>   evalq LABEL [--ref /results/eval_X.json]   quick_eval 실행
#>   results              bench Pod의 결과를 로컬 results/로 복사
#>   teardown             엔진·bench 정리 (네임스페이스·PVC는 유지)
set -euo pipefail
NS=${NS:-llmsvc-lab}
ROOT=$(cd "$(dirname "$0")" && pwd)
k(){ kubectl -n "$NS" "$@"; }
say(){ printf '\n\033[1m== %s ==\033[0m\n' "$*"; }

preflight(){
  say "버전·노드"
  kubectl version 2>/dev/null | head -3
  kubectl get nodes -o wide
  kubectl get nodes -L kubernetes.io/arch -L nvidia.com/gpu.product -L llm-lab/role
  say "GPU Operator"
  kubectl get helmchart -A 2>/dev/null | grep -i gpu || true
  helm list -A 2>/dev/null | grep -i gpu-operator || true
  kubectl get pods -n gpu-operator 2>/dev/null || echo "gpu-operator 네임스페이스 없음"
  kubectl get runtimeclass 2>/dev/null || true
  say "GPU 할당·점유"
  kubectl get nodes -o custom-columns='NAME:.metadata.name,ALLOC_GPU:.status.allocatable.nvidia\.com/gpu'
  kubectl get pods -A -o json | jq -r '.items[] | select(.status.phase=="Running")
    | select(any(.spec.containers[]; .resources.limits["nvidia.com/gpu"] != null))
    | "\(.metadata.namespace)/\(.metadata.name)  node=\(.spec.nodeName)"'
  say "스토리지·입구"
  kubectl get storageclass
  kubectl get ingressclass 2>/dev/null || true
  kubectl get gatewayclass 2>/dev/null || echo "GatewayClass 없음"
}

init(){
  kubectl apply -k "$ROOT/10-namespace"
  kubectl apply -f "$ROOT/20-storage/pvc.yaml"
  kubectl apply -k "$ROOT/40-gateway"
  kubectl apply -k "$ROOT/50-tools"
  k wait --for=condition=Ready pod/bench --timeout=10m
}

download(){
  local repo=${1:?REPO} rev=${2:-main}
  local job="dl-$(echo "$repo" | tr 'A-Z/._' 'a-z---' | cut -c1-55)"
  k delete job "$job" --ignore-not-found
  REPO=$repo REV=$rev JOB=$job envsubst '${JOB} ${REPO} ${REV}' < "$ROOT/20-storage/download-job.yaml" | kubectl apply -f -
  k wait --for=condition=complete "job/$job" --timeout=3h
  k logs "job/$job" | tail -3
}

snapshot(){
  mkdir -p "$ROOT/results"
  local f="$ROOT/results/deploy-$(date +%Y%m%d-%H%M%S)-${1:-unknown}.txt"
  { echo "overlay: ${1:-unknown}"
    k get deploy llm-engine -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
    k get cm -l llm-lab/part=serving -o yaml | grep -E "MODEL_PATH|SERVED_NAME|gpu-memory|max-model-len|kv-cache|parser" || true
    k logs deploy/llm-engine 2>/dev/null | grep -Ei "vllm version|non-default args|kv cache|concurrency" | head -8 || true
  } > "$f"
  echo "기록: $f"
}

up(){
  local ov=${1:?OVERLAY}
  kubectl apply -k "$ROOT/30-serving/overlays/$ov"
  time k rollout status deploy/llm-engine --timeout=45m
  snapshot "$ov"
}
down(){ k delete deploy,svc,cm -l llm-lab/part=serving --ignore-not-found; }
status(){ k get deploy,pod,svc,pvc,gateway,httproute -o wide; }
logs(){ k logs deploy/llm-engine --tail="${1:-100}"; }
gwurl(){
  local port ip
  port=$(kubectl -n envoy-gateway-system get svc \
    -l gateway.envoyproxy.io/owning-gateway-name=lab-gw,gateway.envoyproxy.io/owning-gateway-namespace="$NS" \
    -o jsonpath='{.items[0].spec.ports[0].nodePort}')
  ip=$(kubectl get nodes -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
  echo "http://$ip:$port"
}
smoke(){ k exec bench -- python /scripts/smoke.py --engine http://llm-engine:8000 --gateway "$(gwurl)"; }
bench(){ local l=${1:?LABEL}; k exec bench -- sh -c "python /scripts/engine_bench.py --base http://llm-engine:8000/v1 --label $l && cp /tmp/result_$l.json /results/"; }
evalq(){ local l=${1:?LABEL}; shift; k exec bench -- sh -c "python /scripts/quick_eval.py --base http://llm-engine:8000/v1 --label $l $* && cp /tmp/eval_$l.json /results/"; }
results(){
  mkdir -p "$ROOT/results"
  for f in $(k exec bench -- ls /results); do k cp "bench:/results/$f" "$ROOT/results/$f" >/dev/null; done
  ls -1 "$ROOT/results"
}
teardown(){ down; k delete pod bench --ignore-not-found; echo "네임스페이스와 PVC는 남겨 둠. 완전 삭제: kubectl delete ns $NS"; }
help(){ sed -n 's/^#> //p' "$0"; }

cmd=${1:-help}; shift || true
case $cmd in
  preflight|init|download|up|down|status|logs|gwurl|smoke|bench|evalq|results|teardown|help) "$cmd" "$@" ;;
  *) help; exit 1 ;;
esac

11운영 수칙과 문제 해결

랩을 오래 쓰려면 규칙이 필요하고, 문제가 나면 계층 순서로 봅니다.

공존 수칙 여섯 가지

  1. 클러스터 공용 구성 요소(GPU Operator·CNI·스토리지 클래스·게이트웨이 컨트롤러)를 랩 작업 중에 바꾸지 않는다. 바꿔야 하면 별도 작업으로 계획한다.
  2. GPU를 쓰기 전에 점유 현황을 본다(lab.sh preflight). RAG 플랫폼을 줄였다면 실습이 끝난 뒤 반드시 되돌린다.
  3. 메모리 비율의 합을 관리한다. GB10은 CPU와 메모리를 공유하므로, 호스트에서 직접 띄운 엔진이 있다면 그 몫과 OS 몫을 빼고 랩의 gpu-memory-utilization을 정한다.
  4. 모든 실험은 오버레이 + 스냅샷으로 남긴다. up이 기록하는 이미지·모델·옵션·KV 크기가 결과의 조건이다.
  5. 게이트웨이 주소는 사내망 실습용이다. 인증 없는 주소를 외부에 공유하지 않는다.
  6. 정리 습관: 하루 실습이 끝나면 lab.sh down. 모델 캐시는 남긴다.

핵심 여섯 문장. 이것으로 Level 1이 끝납니다.

  1. 랩의 원칙은 공존·재현성·교체 가능성·한 번 받기다. 기존 RAG 플랫폼과 같은 클러스터에서 경계를 긋고 일한다.
  2. GPU Operator는 있으면 검증만, 없으면 RKE2 HelmChart로 설치한다. v25.10 이상은 CDI라 runtimeClassName이 필요 없고, GB10에서는 device plugin 버전에 주의한다.
  3. 서빙 네임스페이스는 울타리다. 할당량·기본값·네트워크 정책·Pod Security를 함께 건다.
  4. 모델은 Job으로 PVC에 한 번 받고, 엔진은 오프라인으로 읽는다. 리비전과 MANIFEST가 조건 기록이다.
  5. 입구는 Gateway API로 연다. ingress-nginx는 지원이 끝났고, 11편의 Inference Extension이 이 위에 올라간다. 스트리밍 타임아웃을 잊지 않는다.
  6. 베이스 + 오버레이 + 스모크 + 스냅샷이 이후 모든 실험의 형식이다.

다음 편 · 8편 Kubernetes 위의 GPU 플랫폼 (Level 2 시작)

이 랩을 무대로 GPU를 “어떻게 나눠 주는가”를 다룹니다. Device Plugin에서 DRA(Dynamic Resource Allocation)로의 전환, 타임 슬라이싱·MPS·MIG의 원리와 LLM 서빙 적합성, GB10의 통합 메모리가 공유에 주는 제약, Kueue로 학습·배치 작업과 서빙의 공존, 노드 풀과 토폴로지 인지 스케줄링까지. 4장에서 미뤄 둔 “RAG 플랫폼과 GPU를 동시에 쓰는 방법”의 답도 여기서 정리합니다.

LLM 서빙 플랫폼 강의 시리즈 · 7편 실습 랩 구축 · 2026년 10월 기준(RKE2 문서의 GPU Operator v26.3 계열 안내, vLLM v0.31.0). Envoy Gateway·local-path-provisioner·CUDA 이미지 태그는 설치 시점의 최신 안정 버전을 확인해 사용하세요. 공용 구성 요소 변경은 기존 워크로드에 영향을 줄 수 있으므로 별도 작업으로 계획하세요.
