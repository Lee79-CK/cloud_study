왜 지금 기밀 컴퓨팅인가

LLM 추론의 위협 모델. 데이터는 저장할 때도, 보낼 때도 아닌 쓰는 순간 가장 약합니다. 이번 편에서는 그 순간에 무엇이, 누구에게, 어떻게 보이는지를 하나씩 확인합니다.

GPU 서버의 추론 프로세스 메모리 (예시) 평문 그대로 보임

서버의 root 권한만 있으면 지금 처리 중인 프롬프트가 이렇게 읽힙니다. 디스크 암호화와 TLS는 이 순간을 지켜주지 못합니다.

이 시리즈는 "LLM을 서빙하는 서버에서 데이터를 어떻게 지킬 것인가"라는 하나의 질문을 12편에 걸쳐 풀어갑니다. 그중 1편은 기술을 배우기 전에 문제부터 정확히 이해하는 편입니다. 명령어도, 설정 파일도 나오지 않습니다. 대신 이야기와 예제가 많이 나옵니다.

  • "누가, 무엇을, 어떻게" 노리는지 위협 모델을 그릴 수 있습니다.
  • TEE와 Trustee가 왜 등장했는지 한 문장으로 말할 수 있습니다.

이번 편의 한 문장

기존 보안은 "정상적인 길"을 지키지만, 서버의 관리자 권한은 그 길을 우회합니다. 기밀 컴퓨팅은 관리자조차 볼 수 없게 하드웨어로 막고, 그 사실을 증명하는 기술입니다.

1

데이터의 세 가지 상태

보안 이야기를 할 때 가장 먼저 나오는 그림이 있습니다. 데이터는 언제나 세 가지 상태 중 하나에 있다는 것입니다.

비유: 비밀 일기장

여러분에게 비밀 일기장이 있다고 해봅시다.

  • 보관할 때는 자물쇠 달린 서랍에 넣습니다. 도둑이 서랍을 통째로 들고 가도 열 수 없습니다. → 저장 중(at rest)
  • 친구에게 보낼 때는 봉인된 등기 봉투에 넣습니다. 우체부가 봉투를 들고 다녀도 내용은 못 봅니다. → 전송 중(in transit)
  • 그런데 읽거나 쓸 때는 어떨까요? 일기장을 책상 위에 펼쳐야 합니다. 이때 누군가 어깨 너머로 보면 그대로 보입니다. → 사용 중(in use)

서랍 자물쇠와 등기 봉투는 아주 잘 발달했습니다. 하지만 "펼쳐 놓은 순간"을 지키는 방법은 오랫동안 없었습니다.

💾디스크·스토리지
📨네트워크
🧠CPU·GPU 메모리

저장 중: 디스크에 가만히 놓여 있는 데이터

클라우드 예시: 모델 가중치 파일이 담긴 블록 스토리지, 오브젝트 스토리지 버킷에 저장된 학습 데이터, DB에 저장된 대화 이력.

지키는 기술: 디스크 암호화, 스토리지 서버 측 암호화(SSE), KMS로 관리하는 키.

그래도 보이는 사람: 디스크를 마운트한 서버에서는 파일이 자동으로 복호화되어 평문으로 읽힙니다. 즉 그 서버의 root는 다 볼 수 있습니다.

대체로 잘 해결됨

전송 중: 네트워크를 타고 이동하는 데이터

클라우드 예시: 사용자가 챗봇 앱에서 보낸 프롬프트가 인터넷을 거쳐 로드밸런서까지 가는 구간, 서비스 간 gRPC 호출.

지키는 기술: TLS(HTTPS), mTLS, VPN, 서비스 메시.

그래도 보이는 사람: TLS가 끝나는 지점(로드밸런서, Ingress, 사이드카 프록시)에서는 평문이 됩니다. 그 지점을 운영하는 사람과 시스템은 내용을 볼 수 있습니다.

대체로 잘 해결됨

사용 중: CPU와 GPU가 계산하고 있는 데이터

클라우드 예시: vLLM 프로세스 메모리에 올라간 프롬프트 텍스트, GPU 메모리에 올라간 70억~수천억 개의 모델 파라미터, 대화를 이어가기 위해 쌓아둔 KV 캐시.

지키는 기술: 오랫동안 사실상 없었습니다. 운영체제의 권한 분리, 컨테이너 격리는 "같은 서버의 다른 일반 사용자"는 막지만, root나 하이퍼바이저는 막지 못합니다.

그래도 보이는 사람: 서버 root, 하이퍼바이저를 다루는 클라우드 운영자, 서버를 장악한 공격자, 메모리를 물리적으로 꺼낼 수 있는 사람.

여기가 빈틈 → 이 빈틈을 메우는 것이 기밀 컴퓨팅(Confidential Computing)입니다.

2

왜 '사용 중' 데이터는 암호화가 어려운가

"사용 중인 데이터도 그냥 암호화하면 되지 않나요?"라는 질문은 아주 자연스럽습니다. 답은 간단합니다. CPU와 GPU는 평문으로만 계산할 수 있기 때문입니다.

예제: 암호화된 숫자로 덧셈하기

계산기에 2 + 3을 입력하면 5가 나옵니다. 그런데 2를 암호화해서 Xq#, 3을 암호화해서 Lp!로 바꿨다면, 계산기는 Xq# + Lp!를 계산할 수 없습니다. 계산하려면 먼저 복호화해서 다시 2와 3으로 되돌려야 합니다.

LLM 추론도 똑같습니다. 프롬프트를 토큰으로 바꾸고, 가중치와 곱하고, 다음 단어 확률을 계산하려면 메모리 안에서 평문 상태여야 합니다.

잠깐, 동형암호는요?

암호문 상태 그대로 계산하는 동형암호(Homomorphic Encryption)라는 기술이 실제로 있습니다. 하지만 일반 계산보다 수천 배 이상 느린 경우가 흔해서, 수십억 번의 곱셈을 하는 LLM 추론에는 아직 현실적이지 않습니다. 그래서 업계는 "계산은 평문으로 하되, 그 평문을 아무도 못 보는 방 안에서 하자"는 방향을 택했습니다. 그 방이 바로 TEE(Trusted Execution Environment, 신뢰 실행 환경)입니다.

직접 해보기: root 권한으로 메모리 들여다보기

아래는 실제 명령을 흉내 낸 시뮬레이션입니다. 공격자(또는 호기심 많은 운영자)가 GPU 서버의 root 권한을 얻었다고 가정합니다. 버튼을 눌러 무슨 일이 벌어지는지 보세요.

# 위 버튼을 눌러 시뮬레이션을 시작하세요.

학습용 시뮬레이션입니다. 실제 명령 출력과 형식은 다를 수 있습니다.

일반 서버에서는 프롬프트에 들어 있던 고객 이름, 대출 금액 같은 정보가 그대로 보였습니다. TEE 서버에서는 같은 위치를 읽어도 의미 없는 암호문만 나옵니다. 그 이유는 다음과 같습니다.

  • CPU 안에 있는 메모리 암호화 엔진이 데이터를 메모리(RAM)에 내보낼 때 자동으로 암호화합니다.
  • CPU 안으로 다시 읽어 들일 때만 복호화합니다. 그래서 계산은 평문으로 정상 진행됩니다.
  • 암호화 키는 CPU 칩 내부에만 있고, 운영체제나 하이퍼바이저도 꺼낼 수 없습니다.
비유: 불투명 유리 작업실

TEE는 불투명 유리로 된 작업실과 같습니다. 안에 있는 사람(내 프로그램)은 서류를 펼쳐놓고 편하게 일합니다. 하지만 밖에 있는 건물 관리인(운영체제, 하이퍼바이저, 클라우드 운영자)은 유리창 너머로 아무것도 볼 수 없습니다. 관리인이 할 수 있는 일은 전기를 끊거나(서비스 중단), 문을 잠그는 것(자원 회수)뿐입니다.

3

추론 요청 하나의 여정

이제 추상적인 이야기를 실제 LLM 서비스에 대입해 보겠습니다. 사용자가 사내 챗봇에 질문 하나를 보내면, 응답이 돌아올 때까지 데이터는 여러 곳을 지나갑니다. 각 지점에서 데이터가 평문으로 존재하는지를 확인해 보세요.

여정에서 배운 것

8개 지점 중 TLS가 지켜주는 곳은 인터넷 구간 하나뿐이었습니다. 나머지 지점에서는 데이터가 메모리 어딘가에 평문으로 존재합니다. 특히 5번(추론 서버)과 6번(GPU)은 가장 값비싼 자산(모델 가중치)과 가장 민감한 자산(프롬프트)이 동시에 평문으로 모이는 곳입니다. 기밀 컴퓨팅이 가장 먼저 지키려는 곳이 바로 여기입니다.

4

지켜야 할 자산 7가지

위협 모델링의 첫 단계는 "무엇을 지킬 것인가"를 정하는 일입니다. 지킬 대상을 자산(asset)이라고 부릅니다. LLM 추론 환경의 자산은 크게 7가지로 나눌 수 있습니다. 각 카드를 열어보세요.

KV 캐시를 쉽게 이해하기

선생님이 학생의 긴 질문을 듣는 상황을 떠올려 보세요. 선생님은 질문을 들으면서 중요한 부분을 포스트잇에 메모해 둡니다. 다음 문장을 들을 때 앞 내용을 처음부터 다시 듣지 않고 메모를 보면 되니까요. LLM의 KV 캐시가 바로 이 포스트잇입니다. 앞서 처리한 토큰의 계산 결과를 GPU 메모리에 저장해두고 재사용합니다.

문제는 이 포스트잇에 질문 내용의 흔적이 고스란히 담긴다는 점입니다. 프롬프트 원문이 지워진 뒤에도 KV 캐시가 남아 있으면, 이를 이용해 원래 질문을 상당 부분 추정할 수 있다는 연구들이 있습니다. 그래서 KV 캐시는 프롬프트와 같은 등급으로 보호해야 합니다.

자산마다 주인이 다르다

MSP 환경에서는 자산의 주인이 여럿입니다. 모델 가중치의 주인은 모델 개발사일 수 있고, 프롬프트의 주인은 고객사 직원, 인프라의 주인은 클라우드 사업자, 운영은 MSP가 합니다. 기밀 컴퓨팅은 "서로 다 믿지 않아도 함께 일할 수 있게" 해주는 기술이기도 합니다. 예를 들어 모델 개발사는 가중치를 고객 인프라에 맡기면서도 복사당하지 않기를 원하고, 고객사는 프롬프트를 모델 개발사나 MSP가 보지 않기를 원합니다.

5

누가 노리는가: 위협 행위자 7유형

자산을 정했으면 다음은 "누가 그 자산을 노리는가"입니다. 이를 위협 행위자(threat actor)라고 부릅니다. 중요한 점은 나쁜 의도가 없는 사람도 위협 모델에 들어간다는 것입니다. 실수로 유출하는 것도 유출이니까요.

🕵️① 외부 공격자

누구: 인터넷 너머의 해커, 랜섬웨어 조직, 경쟁사의 의뢰를 받은 사람.

보통의 경로: 웹 취약점 → 컨테이너 장악 → 컨테이너 탈출 → 호스트 root 획득.

root를 얻으면: 같은 서버의 모든 프로세스 메모리를 읽을 수 있습니다. 2장에서 본 덤프가 바로 이 상황입니다.

예: 공개된 추론 API 서버의 의존 라이브러리 취약점으로 침투 → GPU 노드 장악 → 파인튜닝된 모델 가중치를 통째로 반출.

🧑‍💻② 내부자(운영자 포함)

누구: 클라우드 사업자 직원, MSP 엔지니어, 고객사 인프라 담당자. 대부분은 선의입니다.

위험한 이유: 업무상 root, 하이퍼바이저 콘솔, 스냅샷 기능에 정당하게 접근합니다. 실수로 덤프를 공유하거나, 계정을 탈취당하거나, 드물게는 악의를 품습니다.

예: 장애 대응 중 메모리 덤프를 떠서 사내 메신저에 공유 → 그 안에 고객 프롬프트가 들어 있음.

포인트: 이 시리즈를 듣는 여러분(MSP 엔지니어) 자신도 고객 입장에서는 위협 행위자 목록에 있습니다. 기분 나쁜 이야기가 아니라, 그래야 고객이 안심할 수 있습니다.

☁️③ 클라우드 사업자·하이퍼바이저

누구: 내 VM을 실행시켜 주는 소프트웨어(하이퍼바이저)와 그것을 관리하는 회사.

위험한 이유: 하이퍼바이저는 구조적으로 VM의 메모리 전체를 볼 수 있습니다. VM의 "집주인"이기 때문입니다. 법적 요청, 내부 정책, 하이퍼바이저 자체의 취약점이 모두 경로가 됩니다.

예: 하이퍼바이저 취약점이 악용되어 같은 물리 서버의 VM 메모리가 공격자에게 노출됨.

🏘️④ 공동 테넌트(이웃)

누구: 같은 물리 서버, 같은 GPU, 같은 Kubernetes 노드를 함께 쓰는 다른 고객이나 다른 팀.

보통의 경로: 격리 우회, 캐시·타이밍 같은 사이드채널, 공유 자원(예: 여러 사용자가 공유하는 프리픽스 캐시)을 이용한 정보 추론.

예: 응답 속도 차이를 정밀하게 측정해서 "다른 사용자가 비슷한 시스템 프롬프트를 쓰는지" 추측하는 공격이 연구로 보고된 바 있습니다.

🔧⑤ 물리 접근자

누구: 데이터센터 출입이 가능한 사람, 장비 수리·폐기 업체, 장비를 훔친 사람.

보통의 경로: 메모리 모듈을 얼려서 빼낸 뒤 읽기(콜드 부트 공격), PCIe 장치로 메모리를 직접 읽기(DMA 공격), 메모리 버스에 장치를 끼워 신호 엿보기.

예: 폐기 대상 GPU 서버를 회수한 업체가 디스크뿐 아니라 메모리 잔존 데이터까지 분석.

📦⑥ 공급망 공격자

누구: 컨테이너 이미지, 모델 파일, 펌웨어, 라이브러리를 중간에 바꿔치기하는 사람.

위험한 이유: 메모리가 아무리 안전해도, 그 안에서 돌아가는 프로그램 자체가 변조되었다면 프로그램이 직접 데이터를 밖으로 보냅니다.

예: 추론 서버 이미지에 "프롬프트를 외부로 복사하는" 코드가 몰래 들어감.

🎭⑦ 사칭자(가짜 환경)

누구: "저는 안전한 TEE입니다"라고 거짓말하는 일반 서버를 만들어내는 공격자.

위험한 이유: 모델 복호화 키나 API 시크릿은 "안전한 환경"에만 줘야 합니다. 그런데 상대가 진짜 안전한지 확인하지 않으면, 키를 공격자에게 직접 건네게 됩니다.

예: 공격자가 TEE 흉내만 낸 VM을 띄워 키 서버에 요청 → 키 서버가 그대로 키를 내줌 → 암호화해 둔 모델이 즉시 복호화됨.

포인트: 이 위협 행위자 때문에 원격 증명과 Trustee가 필요합니다. 10장에서 다시 다룹니다.

패턴 하나

①~⑤는 결국 "내 프로그램 바깥에 있으면서 메모리를 볼 수 있는 존재"입니다. TEE는 이들을 막습니다. ⑥과 ⑦은 "내 프로그램이나 환경 자체를 가짜로 만드는 존재"입니다. 이들은 TEE만으로는 막을 수 없고, 원격 증명이 필요합니다.

7

사고 시나리오 6가지

아래는 실제로 자주 지적되는 사고 유형을 바탕으로 만든 학습용 가상 시나리오입니다. 회사와 인물은 모두 가상입니다. 각 시나리오의 마지막에서 "TEE가 막을 수 있었는가"를 함께 확인하세요.

A. 메모리 덤프 한 번이면 충분했다외부 공격자TEE로 막을 수 있음

스타트업 '누리AI'는 직접 파인튜닝한 법률 상담 모델을 GPU 클라우드에서 서빙합니다.

  • D-day 02:10추론 서버가 쓰는 이미지 처리 라이브러리의 알려진 취약점으로 컨테이너 침투
  • 02:40권한 설정이 느슨한 컨테이너에서 탈출해 GPU 노드 root 획득
  • 03:05추론 프로세스 메모리 덤프 → 처리 중이던 상담 내용 수백 건 확보
  • 03:30모델 가중치(디스크에서는 암호화돼 있었지만 메모리에는 평문) 반출

어디서 막을 수 있었나: 침투 자체는 패치와 컨테이너 보안의 영역입니다. 하지만 공격자가 root를 얻은 이후에도 TEE가 있었다면, 메모리 덤프는 암호문만 돌려줬을 것입니다. "뚫리더라도 피해를 줄이는" 마지막 방어선입니다.

B. 친절한 디버깅선의의 운영자일부만 막음

MSP 엔지니어 박 대리는 새벽에 고객사 LLM 서버가 멈췄다는 알림을 받습니다.

  • 01:00원인 분석을 위해 호스트에서 VM 메모리 덤프 수행
  • 01:30덤프 파일을 벤더 기술지원 티켓에 첨부해 업로드
  • 두 달 뒤고객사 감사에서 덤프 안에 직원들의 인사 평가 관련 프롬프트가 포함됐던 사실이 발견됨

어디서 막을 수 있었나: TEE를 쓰면 호스트에서 뜬 VM 메모리 덤프는 암호문입니다. 그래서 이 시나리오는 막힙니다. 하지만 엔지니어가 VM 안으로 들어가서 디버깅 모드로 덤프를 떴다면 TEE도 막지 못합니다. 그래서 원격 증명 단계에서 "디버그 모드가 꺼져 있는가"를 함께 확인하고, 운영 절차로 덤프 반출을 통제해야 합니다.

C. 로그에 다 있었다설계 실수TEE로 못 막음

'한결물류'는 고객 문의 응대용 LLM을 도입하면서 문제 추적을 위해 API 게이트웨이의 요청 바디 로깅을 켭니다.

  • 도입 첫 주모든 프롬프트와 응답이 로그 수집 시스템으로 전송됨
  • 3개월 뒤로그 대시보드 접근 권한이 수십 명에게 퍼짐
  • 6개월 뒤퇴사자 계정이 정리되지 않아 로그 백엔드에서 대량 조회 발생

어디서 막을 수 있었나: TEE는 "TEE 안의 메모리"만 지킵니다. 프로그램이 스스로 데이터를 TEE 밖으로 내보내면 TEE는 막지 않습니다. 로그에 무엇을 남길지는 설계로 정해야 합니다. 10편에서 관측 데이터를 다룰 때 자세히 봅니다.

D. 스냅샷의 함정백업 저장소 접근자TEE로 막을 수 있음

운영팀은 장애 복구를 빠르게 하려고 실행 중인 추론 VM을 메모리 상태까지 포함해 정기적으로 스냅샷합니다.

  • 평소스냅샷은 백업 스토리지에 저장되고 접근 권한은 백업팀이 관리
  • 어느 날백업 스토리지 계정이 탈취됨 → 공격자가 스냅샷을 다른 환경에서 복원
  • 이후복원된 메모리 이미지에서 모델 가중치와 시크릿을 추출

어디서 막을 수 있었나: TEE의 메모리는 CPU 안의 키로 암호화돼 있으므로, 메모리 상태가 담긴 스냅샷도 암호문입니다. 다른 서버에서 복원해도 키가 없어서 읽을 수 없습니다. 대신 TEE 환경에서는 이런 방식의 스냅샷이나 라이브 마이그레이션이 제한될 수 있어, 운영 방식이 바뀝니다(12편).

E. 가짜 금고사칭자원격 증명이 필요

'다온헬스'는 의료 상담 모델 가중치를 암호화해서 저장하고, 추론 서버가 시작될 때 키 서버에서 복호화 키를 받아가게 설계했습니다.

  • 설계키 서버는 "요청에 TEE라는 표시가 있으면" 키를 내주도록 구현
  • 공격공격자가 일반 VM에서 TEE 표시만 흉내 낸 요청을 보냄
  • 결과키 서버가 키를 내줌 → 공격자가 암호화된 가중치를 복호화

어디서 막을 수 있었나: "TEE라고 주장하는 것"과 "진짜 TEE인 것"은 다릅니다. CPU 제조사의 인증서로 서명된 증거(evidence)를 받아 검증하고, 그 안에서 실행 중인 소프트웨어가 우리가 승인한 것인지까지 확인해야 합니다. 이 확인 작업이 원격 증명이고, 이를 대신해 주는 서비스가 Trustee입니다.

F. 이웃의 엿보기공동 테넌트TEE만으로는 부족

비용 절감을 위해 여러 고객사의 요청을 하나의 추론 서버에서 처리하고, 속도를 위해 프롬프트 앞부분 계산 결과(프리픽스 캐시)를 고객사 간에 공유합니다.

  • 관찰캐시에 이미 있는 앞부분으로 시작하는 질문은 응답이 눈에 띄게 빨리 시작됨
  • 공격악의적 고객이 여러 후보 문장을 보내며 응답 시작 시간을 측정 → 다른 고객사의 시스템 프롬프트 일부를 추정

어디서 막을 수 있었나: 모든 고객의 요청이 같은 TEE 안에서 처리되므로, TEE는 이 공격을 막지 못합니다. 고객사별로 캐시를 분리하거나, 고객사별로 TEE를 나누는 격리 설계가 필요합니다. TEE는 "밖으로부터의 시선"을 막는 것이지, "같은 방 안의 사람끼리"를 막는 것이 아닙니다.

시나리오근본 원인TEE원격 증명설계·운영

B 친절한 디버깅운영자 접근·반출일부디버그 모드 차단덤프 반출 통제
C 로그앱이 스스로 내보냄못 막음못 막음로깅 설계가 핵심
D 스냅샷메모리 상태 저장막음—백업 방식 재설계

8

기존 보안 도구의 빈틈

"우리는 이미 보안을 잘하고 있는데요?"라는 반응이 나올 수 있습니다. 맞습니다. 기존 도구들은 각자 중요한 일을 합니다. 다만 공통된 빈틈이 하나 있습니다.

도구지켜주는 것지켜주지 못하는 것비유
디스크 암호화·KMS디스크 도난, 스토리지 유출마운트된 서버 안에서의 평문 읽기, 메모리서랍 자물쇠
TLS·mTLS네트워크 도청TLS 종료 지점 이후, 메모리등기 봉투
IAM·RBAC권한 없는 사용자의 API 호출권한이 있는 사람의 오남용, 탈취된 관리자 계정출입 카드
네트워크 분리·방화벽외부에서의 직접 접근이미 내부에 들어온 공격자, 운영자담장
컨테이너·VM 격리이웃 프로세스·이웃 VM호스트 root, 하이퍼바이저방 칸막이
감사 로그사후 추적과 책임 소재사고 자체를 막는 것, 로그를 지울 수 있는 관리자CCTV
공통된 빈틈

모든 도구가 "시스템을 관리하는 쪽은 믿는다"는 전제 위에 서 있습니다. 출입 카드를 발급하는 사람, 담장 문을 여는 사람, CCTV를 관리하는 사람은 모두 시스템 관리자입니다. 그런데 사고의 상당수는 바로 그 관리자 권한이 탈취되거나 오남용될 때 일어납니다.

기밀 컴퓨팅은 이 전제를 뒤집습니다. "관리하는 쪽도 믿지 않는다. 믿는 것은 CPU 칩과 내가 검증한 소프트웨어뿐이다."

비유: 호텔 금고

호텔 방에는 문 잠금장치(IAM), 복도 CCTV(감사 로그), 정문 경비(방화벽)가 있습니다. 그래도 귀중품은 방 안 금고에 넣습니다. 왜일까요? 호텔 직원은 마스터키로 방에 들어올 수 있기 때문입니다. 그런데 일반 호텔 금고도 관리자용 비상 해제 코드가 있습니다. 기밀 컴퓨팅은 호텔 측에도 비상 해제 코드가 없는 금고를 만드는 일입니다.

9

TCB: 믿어야 하는 것들의 목록

보안 분야에서 아주 중요한 개념 하나를 배울 차례입니다. TCB(Trusted Computing Base, 신뢰 컴퓨팅 기반)는 "내 데이터가 안전하려면 반드시 정상적으로 동작한다고 믿어야 하는 모든 구성 요소의 집합"입니다.

비유: 아파트의 비밀

여러분 집에 비밀 서류가 있다면, 그 서류가 안전하려면 누구를 믿어야 할까요? 가족, 관리사무소(마스터키 보유), 경비원, 열쇠 수리공, 아파트를 지은 건설사… 이 중 한 명이라도 배신하면 비밀은 새어 나갑니다. 그래서 믿어야 하는 사람의 목록은 짧을수록 좋습니다. 이 목록이 TCB입니다.

아래에서 실행 방식을 바꿔가며 TCB가 어떻게 줄어드는지 확인해 보세요. 노란색은 믿어야 하는 것, 점선은 믿지 않아도 되는 것입니다.

TCB를 볼 때 기억할 것
  • TCB에서 빠졌다고 그 구성 요소가 사라지는 것은 아닙니다. 여전히 동작하지만, 그것이 해킹당해도 내 데이터의 기밀성에는 영향이 없다는 뜻입니다.
  • 대신 새로 TCB에 들어오는 것이 있습니다. CPU·GPU 하드웨어와 펌웨어, 그리고 그것을 만든 제조사입니다. 기밀 컴퓨팅은 신뢰를 없애는 것이 아니라, 신뢰의 대상을 "수많은 사람과 소프트웨어"에서 "칩과 제조사"로 옮기고 줄이는 것입니다.
  • 기밀 컨테이너에서는 Kubernetes 컨트롤 플레인과 노드의 kubelet까지 TCB에서 빠집니다. 클러스터 관리자도 파드 안의 데이터를 볼 수 없게 하는 것이 목표입니다(5편).
10

기밀 컴퓨팅 한 장 요약

지금까지의 내용을 모으면 기밀 컴퓨팅은 두 개의 기둥으로 서 있습니다.

🔒기둥 1. 하드웨어 격리·메모리 암호화

CPU(그리고 최신 GPU)가 워크로드의 메모리를 자동으로 암호화하고, 운영체제·하이퍼바이저·운영자가 들여다보지 못하게 막습니다. 이 보호 구역을 TEE라고 부릅니다. 예: Intel TDX, AMD SEV-SNP, Arm CCA, NVIDIA GPU의 기밀 컴퓨팅 모드.

📜기둥 2. 원격 증명(Remote Attestation)

"이 워크로드는 진짜 TEE 안에서, 우리가 승인한 소프트웨어로 실행 중이다"라는 사실을 칩이 서명한 증거로 외부에 증명합니다. 증명에 성공해야만 모델 키나 시크릿을 건네줍니다.

기둥 1만 있으면 시나리오 E(가짜 금고)를 막을 수 없습니다. 기둥 2만 있으면 증명은 했지만 메모리는 여전히 노출됩니다. 둘이 함께 있어야 의미가 있습니다.

Trustee는 어디에 있나

원격 증명은 생각보다 복잡한 작업입니다. 칩 제조사 인증서를 검증하고, 실행 중인 소프트웨어의 지문(측정값)을 기준값과 비교하고, 정책에 따라 키를 내줄지 결정해야 합니다. 이 일을 매번 직접 구현하기는 어렵습니다. Trustee는 이 작업을 대신해 주는 오픈소스 서비스 묶음으로, CNCF 프로젝트인 Confidential Containers(CoCo)에서 만들어졌습니다.

흐름: 증명 에이전트가 칩이 서명한 증거를 KBS에 제출 → AS가 RVPS의 기준값과 비교해 검증 → 통과하면 KBS가 모델 복호화 키를 TEE 안으로만 전달. 세부 프로토콜은 3편과 6편에서 다룹니다.

비유: 은행 대여금고 창구

대여금고 열쇠를 받으려면 창구 직원(KBS)에게 신분증을 내야 합니다. 직원은 신분증이 위조인지 감정 담당자(AS)에게 확인을 맡기고, 감정 담당자는 정부가 발급한 진본 기준표(RVPS)와 비교합니다. 모두 통과해야만 열쇠가 나옵니다. 여기서 신분증을 발급한 기관이 CPU 제조사이고, 신분증이 칩의 서명이 담긴 증거입니다.

11

TEE가 해주지 않는 것

새로운 보안 기술을 배울 때 가장 위험한 것은 과신입니다. 다음 오해들을 미리 바로잡아 두겠습니다.

오해TEE를 쓰면 해킹이 불가능하다.
사실TEE는 "밖에서 메모리를 엿보는 것"을 막습니다. TEE 안의 프로그램에 취약점이 있으면, 공격자는 그 프로그램을 통해 정상적으로 데이터를 빼냅니다.
오해TEE 안에서 돌리면 프롬프트 인젝션도 막힌다.
사실프롬프트 인젝션은 모델에게 "정상적인 입력"으로 들어옵니다. TEE는 입력의 의미를 판단하지 않습니다. 모델이 시스템 프롬프트를 실토하는 문제는 그대로 남습니다.
오해TEE면 로그도 안전하다.
사실프로그램이 로그를 TEE 밖(로그 수집기, 디스크)으로 보내는 순간 보호 범위를 벗어납니다. 시나리오 C처럼 무엇을 남길지는 설계로 정해야 합니다.
오해TEE면 서비스가 멈추지 않는다.
사실TEE는 기밀성과 무결성을 지킵니다. 가용성은 지키지 않습니다. 호스트 운영자는 여전히 VM을 끄거나 자원을 빼앗을 수 있습니다.
오해TEE는 모든 물리 공격도 막는다.
사실메모리 암호화로 콜드 부트 같은 고전적 공격은 크게 어려워집니다. 하지만 사이드채널, 메모리 버스에 장치를 끼워 넣는 고급 물리 공격으로 일부 TEE의 보호를 우회한 연구가 공개된 바 있습니다(11편).
오해CPU TEE만 켜면 GPU 추론도 보호된다.
사실CPU TEE는 CPU 쪽 메모리를 지킵니다. 모델 가중치와 KV 캐시가 올라가는 GPU 메모리, 그리고 CPU와 GPU 사이의 전송 구간은 GPU의 기밀 컴퓨팅 기능이 따로 필요합니다(4편).
오해Trustee를 설치하면 자동으로 안전해진다.
사실Trustee는 정책대로 판단합니다. 정책이 느슨하면(예: 디버그 모드 허용, 아무 측정값이나 통과) 가짜 환경도 통과합니다. Trustee 자체도 취약점이 발견되어 패치된 이력이 있는 소프트웨어이므로 버전 관리가 필요합니다(8편, 11편).
12

MSP 엔지니어의 관점

LLM을 도입하려는 고객사의 보안팀은 거의 예외 없이 이렇게 묻습니다. 기밀 컴퓨팅 전과 후에 MSP가 할 수 있는 대답이 어떻게 달라지는지 비교해 보세요.

고객사 보안팀우리 직원들이 입력하는 프롬프트를 MSP 엔지니어나 클라우드 사업자가 볼 수 있나요?
기존 방식의 답변저희는 접근 권한을 최소화하고, 모든 접근은 감사 로그로 남기며, 직원들은 보안 서약을 했습니다. 믿으셔도 됩니다.
기밀 컴퓨팅 적용 후의 답변추론 서버는 TEE 안에서 실행되어 저희와 클라우드 사업자 모두 메모리를 볼 수 없습니다. 모델과 데이터 키는 귀사가 직접 운영하는 Trustee가 증명을 확인한 뒤에만 내줍니다. 증명 결과는 귀사가 직접 확인하실 수 있습니다.

차이는 한 문장으로 요약됩니다. "믿어주세요"에서 "확인해 보세요"로. 신뢰가 약속에서 검증으로 바뀝니다.

MSP 업무에 생기는 변화 (미리 보기)
  • 디버깅 방식: 호스트에서 메모리를 들여다보는 디버깅이 불가능해집니다. 관측 가능성을 미리 설계해 두어야 합니다.
  • 키 관리 책임: Trustee를 고객이 운영할지, MSP가 운영할지에 따라 신뢰 경계가 완전히 달라집니다. MSP가 Trustee를 운영하면 고객 입장에서는 MSP가 다시 TCB에 들어옵니다.
  • 패치 운영: 펌웨어를 업데이트하면 측정값이 바뀝니다. 기준값을 함께 갱신하지 않으면 증명이 일제히 실패해 서비스가 멈출 수 있습니다.
  • 영업 포인트: 금융, 의료, 공공처럼 규제가 엄격한 고객이 LLM을 도입할 때 기밀 컴퓨팅은 강력한 차별화 요소가 됩니다.

이 내용은 12편에서 운영 전략으로 자세히 다룹니다.

13

실습: 위협 모델 그려보기

위협 모델링은 거창한 문서 작업이 아닙니다. 네 가지 질문에 차례대로 답하는 것입니다. 가상의 고객사 사례로 함께 해보겠습니다.

예제 상황

가상의 금융사 '한빛캐피탈'은 대출 심사 담당자를 돕는 사내 LLM을 도입하려 합니다. 심사 담당자가 신청인의 소득 정보와 상담 메모를 붙여넣으면 모델이 심사 의견 초안을 써줍니다. 모델은 외부 AI 기업이 금융 문서로 파인튜닝한 것을 라이선스로 받았고, 인프라는 퍼블릭 클라우드 GPU, 운영은 MSP가 맡습니다.

  1. 무엇을 지키나? (자산)

    신청인 개인정보가 담긴 프롬프트, 심사 의견(출력), 라이선스 받은 모델 가중치, 내부 심사 기준이 담긴 시스템 프롬프트, KV 캐시, 로그, 모델 복호화 키.

    팁: 자산마다 "주인"을 적어두세요. 프롬프트와 출력의 주인은 한빛캐피탈, 가중치의 주인은 AI 기업입니다.

  2. 누가 노리나? (위협 행위자)

    외부 공격자, 클라우드 사업자, MSP 운영자, 같은 GPU 클라우드의 다른 테넌트, 그리고 가중치 관점에서는 한빛캐피탈 자신도 AI 기업 입장에서는 잠재적 위협입니다(가중치를 복사해 라이선스 없이 쓸 수 있으므로).

  3. 어디로 새나? (경로)

    3장의 여정을 그대로 따라갑니다. TLS 종료 지점, 게이트웨이 로그, 추론 서버 메모리, GPU 메모리, 메모리 스냅샷, 디버그 덤프, 모델 키 전달 과정.

  4. 어떻게 막나? (대응과 우선순위)
    위험대응우선순위
    GPU 노드 root 장악 시 메모리 노출CPU TEE + GPU 기밀 컴퓨팅높음
    가짜 환경에 모델 키 전달원격 증명(Trustee) + 키 해제 정책높음
    게이트웨이·앱 로그에 프롬프트 기록요청 바디 로깅 금지, 마스킹, 보존 기간 단축높음
    TLS 종료 지점의 평문TLS를 TEE 안에서 종료하도록 구조 변경중간
    다른 테넌트의 사이드채널전용 노드·캐시 분리중간
    운영자 디버그 덤프디버그 모드 차단 정책, 덤프 반출 절차중간

내 서비스 자가 진단

지금 운영 중이거나 준비 중인 LLM 서비스를 떠올리며 답해 보세요. 정답은 없고, 어디부터 손대야 할지 보여주는 용도입니다.

정리와 다음 편

  1. 데이터는 저장·전송·사용 중의 세 상태가 있고, 사용 중이 전통적으로 비어 있던 영역입니다.
  2. CPU와 GPU는 평문으로 계산하므로, 해결책은 "평문을 아무도 못 보는 방"인 TEE입니다.
  3. LLM 추론의 자산은 가중치, 프롬프트, 시스템 프롬프트·RAG 문서, KV 캐시, 출력, 로그, 시크릿입니다.
  4. 위협 행위자에는 외부 공격자뿐 아니라 운영자·클라우드 사업자, 이웃, 물리 접근자, 공급망, 사칭자가 있습니다.
  5. 기존 보안은 "관리자는 믿는다"는 전제 위에 있고, 기밀 컴퓨팅은 그 전제를 뒤집어 TCB를 칩과 검증된 소프트웨어로 줄입니다.
  6. 기밀 컴퓨팅의 두 기둥은 메모리 격리·암호화와 원격 증명이며, Trustee(KBS·AS·RVPS)는 원격 증명과 키 전달을 맡습니다.
  7. TEE는 앱 취약점, 프롬프트 인젝션, 로그 설계, 가용성, 같은 방 안의 사이드채널은 해결하지 않습니다.

2편 예고: TEE 하드웨어 해부

이번 편에서 "CPU가 메모리를 암호화한다"고만 말했던 부분을 열어봅니다. 프로세스 단위로 보호하는 SGX와 VM 전체를 보호하는 TDX·SEV-SNP·Arm CCA는 무엇이 다른지, 메모리 암호화 엔진은 어디에 있는지, 하이퍼바이저가 VM 메모리를 못 보게 되면 VM Exit와 페이지 관리는 어떻게 바뀌는지, 그리고 증명의 재료가 되는 "측정값"이 어떻게 만들어지는지를 하이퍼바이저 강의와 연결해 설명합니다.

TEE·Trustee 강의 시리즈 1편. 시나리오의 회사와 인물은 모두 학습용 가상 사례입니다. 제품 기능과 지원 범위는 버전에 따라 달라지므로 실제 도입 시 각 공급사의 최신 문서를 확인하세요.
