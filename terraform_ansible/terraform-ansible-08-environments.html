같은 코드, 세 개의 세상 환경 분리 전략 — workspace · 디렉터리 · 단일 루트 + tfvars, 승격 흐름, Terragrunt, HCP Terraform Stacks

7편까지는 dev 하나였습니다. 실제 고객사에는 개발(dev)·검증(stg)·운영(prd)이 있고, “개발계에서 확인한 것을 운영계에 그대로” 올려야 합니다. 같은 코드를 쓰되 state·자격증명·값은 철저히 나누는 것, 이것이 환경 분리입니다. 방법은 여러 가지이고 각각 다른 곳에서 사고가 납니다. 이번 편은 세 가지 기본 방식을 비용 0원으로 직접 실행해 보고, 실제로 사고를 재현한 뒤, 승격 흐름과 상위 도구(Terragrunt, HCP Terraform Stacks)까지 정리합니다.

workspace

한 디렉터리, 한 백엔드, 이름만 다른 state 여러 개. 가장 간단하고, 가장 조용하게 사고 난다.

환경마다 루트 디렉터리. 가장 명시적이고, 가장 많이 반복된다.

단일 루트 + tfvars

코드 하나, 환경별 값·백엔드 파일. 가장 DRY하고, 래퍼 없이는 위험하다.

1무엇을 나누는가

“환경을 분리했다”는 말은 네 가지를 모두 나눴을 때만 참이다

① state

환경마다 다른 state. 하나의 state에 dev와 prd 리소스가 섞이면, dev를 위한 apply가 prd를 건드립니다. 최소한의 분리이며 모든 방식이 이것은 합니다.

② 자격증명·계정

dev를 다루는 사람·파이프라인이 prd 자격증명을 갖지 않는 것. 가장 강한 분리이고, 실수의 피해 범위를 물리적으로 제한합니다(2장). workspace 방식이 가장 약한 지점입니다.

③ 값

환경마다 달라야 하는 것: 서버 수·크기, Multi-AZ, 삭제 방지, CIDR, 도메인. tfvars나 환경별 파일로 둡니다.

④ 코드 버전

dev는 새 모듈 버전, prd는 검증된 이전 버전을 쓸 수 있어야 “dev에서 확인하고 올린다”가 가능합니다. 같은 코드 커밋을 모든 환경이 공유하면 dev 검증 전에 prd도 새 코드가 됩니다(7장).

달라야 하는 것과 같아야 하는 것

환경 간 구조는 같고 규모·보호 수준만 다른 것이 이상적입니다(환경 일치, environment parity). 구조까지 다르면 dev에서 검증한 것이 prd에서 통한다는 보장이 사라집니다. 7편 3계층을 예로 들면:

2계정 분리

가장 강력한 환경 분리는 Terraform 바깥에 있다

AWS의 권장 구조는 환경마다 별도의 AWS 계정을 두고 AWS Organizations로 묶는 것입니다(멀티 계정 전략). 계정은 IAM 권한·서비스 한도·비용이 완전히 분리되는 경계입니다. dev 계정의 자격증명으로는 prd 리소스를 볼 수조차 없으므로, Terraform 코드나 명령을 아무리 잘못 써도 dev 작업이 prd를 망가뜨릴 수 없습니다.

# 환경마다 다른 계정의 역할을 맡는다 (env와 계정 ID는 tfvars에서)
provider "aws" {
  region = "ap-northeast-2"

  assume_role {
    role_arn     = "arn:aws:iam::${var.account_id}:role/TerraformDeployer"
    session_name = "terraform-${var.env}"
  }

  # 혹시 다른 계정의 자격증명으로 실행해도 이 계정이 아니면 즉시 실패
  allowed_account_ids = [var.account_id]

  default_tags {
    tags = { Env = var.env, ManagedBy = "terraform" }
  }
}
설정역할
assume_role사람·CI는 하나의 기본 자격증명(SSO, OIDC)으로 로그인하고, 환경별 계정의 배포 역할을 맡는다. 역할의 신뢰 정책으로 “prd 역할은 prd 파이프라인만” 같은 통제가 가능
allowed_account_ids프로바이더가 접속한 계정이 목록에 없으면 plan 전에 오류. 엉뚱한 프로필로 실행하는 사고(2편 7-5)를 코드가 막는다
state 위치각 환경 계정 안의 버킷(계정 단위 격리) 또는 공용 “관리 계정”의 버킷(관리 편의). MSP는 고객 계정 안을 선호(5편 16장)
계정을 나눌 수 없는 고객사라면

예산·계약 문제로 dev·prd가 한 계정에 있는 고객사도 흔합니다. 이때는 IAM 정책에서 Env 태그 조건으로 권한을 나누고(ABAC), state 버킷의 경로 권한(5편 6장)을 환경별로 나누고, 환경별로 다른 IAM 역할을 맡게 해서 계정 분리에 최대한 가깝게 만듭니다. 그리고 이 차이를 고객 보고서에 위험 항목으로 남깁니다.

3방식 1: CLI workspace

한 디렉터리, 한 백엔드 설정, 이름만 다른 여러 개의 state

Terraform CLI의 작업공간(workspace)은 같은 코드·같은 백엔드 설정에 대해 state를 여러 개 두는 기능입니다. 처음부터 default라는 작업공간 하나가 있었고, 지금까지 모든 실습은 그 안에서 했습니다. 코드 안에서는 terraform.workspace로 현재 이름을 읽습니다.

명령하는 일
terraform workspace new stg작업공간 생성 후 전환
terraform workspace select prd전환 (1.4+ select -or-create도 가능)
terraform workspace show현재 작업공간 이름
terraform workspace list목록 (현재는 *). 1.16부터 -json 출력 지원
terraform workspace delete stg삭제 (state에 리소스가 남아 있으면 거부, -force로 강제)
TF_WORKSPACE=stg terraform plan환경변수로 작업공간 지정 (CI에서 사용)

variable "env" {
  description = "환경 이름"
  type        = string

  validation {
    condition     = contains(["dev", "stg", "prd"], var.env)
    error_message = "env는 dev, stg, prd 중 하나여야 합니다."
  }
}

variable "web_count" {
  description = "웹 서버 수"
  type        = number
  default     = 1
}

variable "web_instance_type" {
  description = "웹 서버 유형"
  type        = string
  default     = "t3.micro"
}

variable "db_class" {
  description = "DB 클래스"
  type        = string
  default     = "db.t4g.micro"
}

variable "db_multi_az" {
  description = "DB 다중 AZ"
  type        = bool
  default     = false
}

locals {
  module_version = "1.1.0"
}

resource "terraform_data" "web" {
  count = var.web_count
  input = { env = var.env, name = "web${count.index + 1}", type = var.web_instance_type }
}

resource "terraform_data" "db" {
  input = { env = var.env, class = var.db_class, multi_az = var.db_multi_az, backup = "7d" } # v1.1.0: 백업 설정 추가
}

output "summary" {
  value = "${var.env}: web ${var.web_count}×${var.web_instance_type}, db ${var.db_class}${var.db_multi_az ? " (Multi-AZ)" : ""}, module v${local.module_version}"

workspace가 조용히 사고를 내는 방식

사고 재현 카드 — 무슨 일이 일어날지 예측한 뒤 펼쳐 보세요

잘 맞는 곳

개인 실습, 기능 브랜치별 임시 환경(PR마다 workspace를 만들고 병합 후 삭제), 같은 계정·같은 권한에서 구조가 똑같은 복제본을 여러 개 띄울 때.

맞지 않는 곳

dev·prd처럼 다른 자격증명과 접근 통제가 필요한 환경. HashiCorp 공식 문서도 CLI 작업공간은 강한 분리가 필요한 배포 환경 구분에는 적합하지 않다고 안내합니다. 백엔드 설정이 하나라 state 저장소·권한을 환경별로 다르게 하기 어렵고, 현재 작업공간이 코드에도 파일에도 드러나지 않습니다.

HCP Terraform의 “workspace”는 다른 것

HCP Terraform·Terraform Enterprise의 작업공간은 CLI 작업공간과 이름만 같고 개념이 다릅니다. 그쪽 작업공간은 state·변수·권한·실행 이력·연결된 저장소 경로를 각자 따로 가진 독립된 단위로, 사실상 4장의 “디렉터리 분리”를 플랫폼이 관리해 주는 것에 가깝습니다(12편).

래퍼 스크립트: 환경을 한 번만 말하게 만들기

tf.sh
#!/usr/bin/env bash
# 사용법: ./tf.sh <dev|stg|prd> <terraform 명령과 인자...>   예) ./tf.sh stg plan
set -euo pipefail
ENV="${1:?사용법: ./tf.sh <dev|stg|prd> <명령...>}"
shift
case "$ENV" in dev|stg|prd) ;; *) echo "알 수 없는 환경: $ENV" >&2; exit 2 ;; esac
VARS="envs/$ENV.tfvars"
BACKEND="backend/$ENV.s3.tfbackend"
[[ -f $VARS && -f $BACKEND ]] || { echo "$VARS 또는 $BACKEND 가 없습니다" >&2; exit 2; }

# 1) 다른 환경의 백엔드로 초기화되어 있으면 이 환경으로 다시 연결한다
if [[ "$(cat .terraform/ENV 2>/dev/null || true)" != "$ENV" ]]; then
  echo ">> 백엔드를 $ENV 로 다시 연결합니다"
  terraform init -reconfigure -backend-config="$BACKEND" >/dev/null
  echo "$ENV" > .terraform/ENV
fi

# 2) 운영계에 변경 명령이면 한 번 더 확인한다
if [[ $ENV == prd && ${1:-} =~ ^(apply|destroy|import|state)$ ]]; then
  read -r -p "운영(prd)에 '$1' 을(를) 실행합니다. 계속하려면 prd 를 입력하세요: " answer
  [[ $answer == prd ]] || { echo "중단했습니다"; exit 1; }
fi

# 3) 변수가 필요한 명령에만 이 환경의 변수 파일을 붙인다
case "${1:-}" in
  plan | apply | destroy | import | console | refresh) exec terraform "$@" -var-file="$VARS" ;;
  *) exec terraform "$@" ;;
esac
chmod +x tf.sh
./tf.sh dev apply -auto-approve       # >> 백엔드를 dev 로 다시 연결합니다 → dev.tfvars 로 apply
./tf.sh prd plan                      # >> 백엔드를 prd 로 다시 연결합니다 → prd.tfvars 로 plan
./tf.sh prd apply                     # 확인 질문: prd 를 입력해야 진행
./tf.sh qa plan                       # 알 수 없는 환경: qa (종료 코드 2)

실측에서 래퍼는 환경을 바꿀 때마다 백엔드를 다시 연결했고, prd 변경 명령은 “prd” 입력 없이는 중단했으며, 목록에 없는 환경 이름은 거부했습니다. 환경 이름을 한 번만 말하게 하는 것이 핵심입니다. 같은 일을 Makefile(make plan ENV=stg)이나 CI 파이프라인의 환경 매개변수로도 구현할 수 있습니다. 래퍼가 있어도 저장한 plan 파일(apply tfplan)에는 변수 파일을 붙일 수 없으므로, 그 흐름은 CI(12편)에서 다룹니다.

장점

코드가 하나뿐이라 환경 간 구조가 어긋날 수 없습니다(환경 일치가 강제됨). 공통 변경은 한 번만. 환경 추가는 파일 두 개.

단점

모든 환경이 같은 코드 커밋을 공유하므로 “dev만 새 모듈 버전”이 어렵습니다(4장 방식과 비교). 버전 차이가 필요하면 6편의 const 변수(modules_ref)를 tfvars에 두는 방법으로 보완합니다. 래퍼·CI 없이 손으로 쓰면 위 사고가 납니다.

7dev → stg → prd 승격

승격하는 것은 “변경”이 아니라 “검증된 버전”이다

소프트웨어 배포에서 같은 빌드 산출물(아티팩트)을 dev → stg → prd로 옮기듯, 인프라에서도 같은 모듈 버전(태그·커밋)을 순서대로 올립니다. 각 환경은 자기 값(tfvars)을 유지하고, 바뀌는 것은 “어느 버전을 쓰는가” 한 줄입니다. 단계를 눌러 각 관문에서 무엇을 확인하는지 보세요.

버리는 편이 나은 패턴: 환경별 Git 브랜치

dev·stg·prd 브랜치를 두고 브랜치끼리 병합해 승격하는 방식은 직관적으로 보이지만 오래 쓰면 거의 반드시 문제가 됩니다. 브랜치 사이에 핫픽스·실험·되돌리기가 쌓이면서 “prd 브랜치에만 있는 변경”이 생기고, 병합 충돌을 풀다가 환경별 값까지 섞입니다. 어느 커밋이 어느 환경에 있는지 추적하기도 어렵습니다. 한 브랜치(main) + 환경별 디렉터리 또는 파일 + 버전 고정이 현재의 일반적인 권장입니다.

상황흐름
일반 변경모듈 수정 → 태그 → dev ref 올림 → stg ref 올림 → prd ref 올림 (각각 PR + plan 리뷰)
환경 값만 변경 (prd 서버 수)prd tfvars만 PR. 승격 대상이 아님
운영 긴급 수정 (핫픽스)모듈에 수정 → 패치 태그(v1.1.1) → prd에 바로 적용 → 이후 dev·stg도 같은 태그로 맞춤. 환경 간 버전이 역전된 상태를 오래 두지 않는다
되돌리기이전 태그로 ref를 되돌리는 PR. 단, 리소스 교체·삭제를 동반한 변경은 되돌린다고 원상복구되지 않으므로(데이터) plan을 먼저 본다

8Terragrunt

디렉터리 분리의 명시성은 지키고, 반복은 없애는 얇은 래퍼

Terragrunt는 Gruntwork가 만든 오픈소스 도구로, Terraform·OpenTofu를 감싸 실행합니다. 디렉터리 분리 방식에서 반복되던 백엔드·provider 설정을 상위 파일 하나에 두고, 각 환경 디렉터리에는 “다른 것만” 적게 합니다. 2026년 3월 30일 1.0이 나오면서 CLI·설정 문법·출력 형식의 하위 호환을 공식적으로 약속했고, 이 강의 작성 시점의 최신은 1.2.0입니다.

개념설명
유닛 (unit)terragrunt.hcl이 있는 디렉터리 하나 = Terraform 루트 모듈 하나(state 하나)
include상위 설정 파일(관례상 root.hcl)을 상속. find_in_parent_folders("root.hcl")로 위로 올라가며 찾는다
remote_state백엔드 설정을 한 곳에 두고 각 유닛에 backend.tf를 생성(generate). key는 path_relative_to_include()로 경로에서 자동 생성
generateprovider 블록 같은 공통 파일을 각 유닛에 생성
inputs모듈 변수 값. 상위와 하위가 병합된다
dependency다른 유닛의 출력을 입력으로 받기(예: app이 vpc의 vpc_id 사용). 실행 순서도 이 관계로 정해진다
run --all여러 유닛을 의존 순서대로 실행 (1.0 이전의 run-all을 대체)
스택 (terragrunt.stack.hcl)여러 유닛 묶음 자체를 재사용 가능한 패턴으로 정의 (2025년 정식). 대규모 환경에서 반복을 한 단계 더 줄임

4장과 같은 결과를, 백엔드 블록을 한 번도 반복하지 않고 얻었습니다. state key는 iac-lab-tg/dev/app/terraform.tfstate처럼 디렉터리 경로에서 자동으로 만들어집니다. 유닛 디렉터리 안에 생기는 .terragrunt-cache/는 2편 .gitignore에 추가하세요.

쓰면 좋은 경우

고객·환경·구성 요소의 조합이 수십 개 이상이고 디렉터리 분리의 반복이 실제 고통이 될 때. 구성 요소 사이 의존(vpc → app → db)을 여러 환경에 똑같이 펼쳐야 할 때. 팀이 도구 하나를 더 배우고 유지할 여력이 있을 때.

쓰지 않는 편이 나은 경우

루트가 몇 개뿐일 때(반복이 문제가 아님). 팀 전원이 Terraform 기본기를 아직 익히는 중일 때(오류가 Terragrunt에서 났는지 Terraform에서 났는지 구분하기 어려움). HCP Terraform처럼 자체 워크플로를 가진 플랫폼을 이미 쓸 때. 고객사가 “Terraform만” 승인한 경우.

1.0 전후로 명령이 바뀌었다

인터넷의 오래된 예제는 terragrunt run-all apply, terragrunt plan, 루트 파일 이름 terragrunt.hcl을 씁니다. 1.x에서는 terragrunt run --all -- apply, terragrunt run -- plan, 루트 파일은 root.hcl이 권장입니다. 고객사 리포의 Terragrunt 버전을 먼저 확인하고(terragrunt_version_constraint), 문서도 그 버전 기준으로 읽으세요.

9HCP Terraform Stacks 개요

“같은 구성을 여러 곳에 배포”를 Terraform 언어 차원에서 다루는 HashiCorp의 답

Stacks는 모듈 위에 한 층을 더 얹는 구성 언어입니다. “무엇을 만들지”(component)와 “어디에 몇 번 만들지”(deployment)를 분리해 선언하고, HCP Terraform이 배포마다 plan·apply를 조율합니다. Terraform CLI 1.13 이상과 함께 정식(GA) 기능이 되었습니다.

components.tfcomponent.hcl — 무엇을
component "network" {
  source = "./modules/vpc"
  inputs = {
    name       = "${var.project}-${var.env}"
    cidr_block = var.vpc_cidr
  }
  providers = {
    aws = provider.aws.this
  }
}

component "app" {
  source = "./modules/app"
  inputs = {
    vpc_id     = component.network.vpc_id
    subnet_ids = component.network.private_subnet_ids
  }
  providers = {
    aws = provider.aws.this
  }
}
deployments.tfdeploy.hcl — 어디에, 몇 번
identity_token "aws" {
  audience = ["aws.workload.identity"]
}

deployment "dev" {
  inputs = {
    env            = "dev"
    vpc_cidr       = "10.10.0.0/16"
    role_arn       = "arn:aws:iam::111111111111:role/stacks-deployer"
    identity_token = identity_token.aws.jwt
  }
}

deployment "prd" {
  inputs = {
    env            = "prd"
    vpc_cidr       = "10.30.0.0/16"
    role_arn       = "arn:aws:iam::333333333333:role/stacks-deployer"
    identity_token = identity_token.aws.jwt
  }
}
요소설명
컴포넌트 (.tfcomponent.hcl)스택을 이루는 모듈 호출. 컴포넌트 사이 출력→입력 연결(component.network.vpc_id)과 의존 순서를 Stacks가 관리. 변수·provider·출력도 이 파일 종류에 선언
배포 (.tfdeploy.hcl)같은 컴포넌트 묶음의 인스턴스. dev·stg·prd, 리전별, 고객별. 각 배포가 자기 state를 가진다
인증identity_token으로 OIDC 토큰을 받아 배포마다 다른 계정의 역할을 맡는다(장기 키 없음)
배포 그룹 (deployment group)배포들을 묶어 공통 규칙 적용. 사용자 정의 그룹과 자동 승인 검사(예: “삭제가 0개면 자동 승인”)는 HCP Terraform Premium 또는 Terraform Enterprise 2.0 이상, 기본 그룹은 모든 플랜
실행구성을 HCP Terraform에 올리면(terraform stacks configuration upload) 배포마다 plan이 시작되고, 배포별로 승인. 로컬에서 terraform plan·apply로 실행하는 방식이 아니다
과금스택이 관리하는 리소스도 RUM(관리 리소스 수) 과금에 포함
2026년의 요금 상황

HCP Terraform의 예전 무료 플랜(Legacy Free)은 2026년 3월 31일 종료되었고, 남아 있던 조직은 관리 리소스 500개까지의 새 무료 등급(enhanced Free tier)으로 자동 전환되었습니다. 유료 등급은 관리 리소스 수 기반 과금입니다. Stacks를 비롯한 HCP Terraform 기능을 고객사에 제안할 때는 리소스 규모에 따른 월 비용을 먼저 계산해 보고, Terragrunt·Spacelift·env0·Scalr 같은 대안과 비교하는 것이 MSP의 일입니다(12편).

10MSP 권장 구조

고객 × 환경 × 구성 요소를 어떻게 펼칠 것인가

이 강의의 이후 편(그리고 25편 MSP 멀티 고객 운영)은 아래 구조를 기준으로 합니다. 도구 하나 없이 디렉터리 분리를 기본으로 하되, 반복을 줄이기 위해 모듈과 공통 파일을 적극적으로 씁니다. 규모가 커지면 같은 디렉터리 구조 위에 Terragrunt를 얹을 수 있게 설계한 것입니다.

iac-modules/ # 공통 모듈 저장소: label, vpc, alb, app-servers, rds-postgres … (태그로 버전) live-custa/ # 고객사 하나당 라이브 저장소 (권한·감사 경계) ├── dev/ │ ├── network/ main.tf backend.tf terraform.tfvars # key: custa/dev/network │ └── app/ main.tf backend.tf terraform.tfvars # key: custa/dev/app (network 값은 SSM으로) ├── stg/ … ├── prd/ │ ├── network/ │ └── app/ └── README.md # 환경별 계정·모듈 버전 표, 승격 이력
원칙이유
환경 = 디렉터리, 구성 요소 = 하위 디렉터리경로가 곧 대상. 권한(CODEOWNERS·CI)을 경로로 나눌 수 있다
구성 요소마다 state 하나7편의 network/app 분리. 영향 범위 최소화
환경마다 계정 하나 (가능하면)2장. provider에 allowed_account_ids
모듈은 태그로 고정, 환경별로 독립 승격7장 흐름
환경 간 값 전달은 SSM5편 12장, 7편
환경 차이는 tfvars에만main.tf는 환경 간에 (모듈 ref 외에는) 같아야 한다. diff로 쉽게 검사 가능
“환경 간 main.tf가 같은가” 자동 검사

디렉터리 분리의 약점(코드 표류)은 기계로 막을 수 있습니다. 예: diff <(sed 's/ref=[^"]*//' dev/app/main.tf) <(sed 's/ref=[^"]*//' prd/app/main.tf)가 비어 있지 않으면 CI를 실패시킵니다. 모듈 버전 차이는 허용하고 그 밖의 구조 차이는 잡아내는 간단한 규칙입니다(과제 3).

12MSP 현장 팁

고객사마다 다른 환경 구조를 다루는 법

인수인계받은 리포부터 진단

새 고객사 리포를 받으면 먼저 확인할 것: 환경 분리 방식은? 환경별로 state·계정이 실제로 나뉘어 있는가? workspace를 쓴다면 지금 몇 개가 있고 각각 무엇인가(workspace list)? 모듈 버전은 고정되어 있는가? 이 답을 고객 보고서의 “IaC 현황” 항목으로 정리합니다.

방식 전환은 state 이동이다

workspace → 디렉터리로 바꾸려면 각 작업공간의 state를 새 디렉터리의 백엔드 key로 옮겨야 합니다(state pull → 새 위치 init → state push, 또는 백엔드 key를 맞춰 init -migrate-state). 5편의 이전 절차대로, 옮긴 뒤 plan이 “No changes”인지 환경마다 확인합니다(과제 4).

운영계 apply 권한은 사람이 아니라 파이프라인에

prd 계정의 배포 역할은 CI의 OIDC 주체만 맡을 수 있게 하고, 사람에게는 읽기 역할만 줍니다(12편). 래퍼의 “prd 입력” 확인은 개인 실습용 안전장치일 뿐, 운영 통제의 대체물이 아닙니다.

환경별 변경 이력을 고객 보고에

디렉터리 분리 + 버전 고정이면 “이번 달 prd에 적용된 모듈 버전 변경”을 Git 로그(git log -p -- prd/)로 바로 뽑을 수 있습니다. 변경 관리 보고서의 근거 자료가 됩니다.

dev는 자주 지운다

환경 분리가 잘 되어 있으면 dev를 업무 시간 외에 destroy하고 아침에 다시 만드는 비용 절감이 가능합니다(1편 사용 사례 7). 코드가 환경을 완전히 재현할 수 있다는 증거이기도 합니다. state가 깨끗이 나뉘어 있지 않으면 시도조차 할 수 없습니다.

도구 선택은 고객사 정책을 따른다

Terragrunt·HCP Terraform 도입은 고객사의 도구 승인, 비용, 내재화 계획에 달린 문제입니다. MSP가 계약 종료 후에도 고객이 유지할 수 있는 구조를 남기는 것이 원칙입니다. 확신이 없으면 순수 Terraform + 디렉터리 분리가 가장 이식성이 높습니다.

15과제

실습 A~D를 마친 뒤에 풀어 보세요

과제 1. 7편 3계층을 dev·prd로

7편의 06-network·07-app을 10장의 구조(live-iaclab/{dev,prd}/{network,app})로 재배치하세요. prd는 VPC 대역 10.30.0.0/16, 웹 서버 2대, lab_mode = false로. plan까지만 하고 prd는 apply하지 않습니다(비용). 각 디렉터리의 backend key와 SSM 파라미터 경로가 환경별로 겹치지 않는지 확인하세요.

체크포인트

SSM 경로는 /iaclab/dev/network/…와 /iaclab/prd/network/…로 env 변수에 따라 이미 나뉘도록 6편에서 설계했습니다. 그 설계 덕분에 코드를 고치지 않고 값만 바꿔 환경을 늘릴 수 있다는 점을 확인하는 과제입니다. 계정이 하나뿐인 실습 환경이므로 allowed_account_ids에는 같은 계정 번호가 들어갑니다.

과제 2. workspace에 계정 보호 넣기

실습 A의 settings 표에 account_id를 추가하고, AWS 프로바이더의 allowed_account_ids = [local.s.account_id]로 “dev 작업공간인데 prd 계정 자격증명이면 실패”하게 만들어 보세요. 다른 프로필로 plan해서 실패하는지 확인합니다.

과제 3. 환경 간 구조 표류 검사

실습 B의 envs/dev/main.tf와 envs/prd/main.tf에서 모듈 ref, 백엔드 key, 값만 다르고 나머지 구조는 같은지 검사하는 스크립트를 만드세요. 일부러 prd에만 output 블록을 하나 추가해 검사가 실패하는지 확인합니다.

힌트
norm() { sed -E 's/ref=[^"]*//; s#key *= *"[^"]*"#key = KEY#; s/= *("[^"]*"|[0-9]+|true|false)$/= VALUE/' "$1"; }
diff <(norm envs/dev/main.tf) <(norm envs/prd/main.tf) && echo "구조 동일" || { echo "구조 차이 발견"; exit 1; }

값을 VALUE로 바꿔 비교하므로 남는 차이는 구조(블록·인자 이름)뿐입니다. 이런 검사를 pre-commit이나 CI에 넣으면 디렉터리 분리의 가장 큰 약점을 막을 수 있습니다.

과제 4. workspace → 디렉터리 이전

실습 A의 dev·prd 작업공간 state를 실습 B와 같은 디렉터리 구조(08-ws-migrated/envs/{dev,prd})로 옮기세요. 리소스를 다시 만들지 않고 plan이 “No changes”가 되어야 합니다.

해설

① 각 작업공간에서 terraform workspace select dev && terraform state pull > dev.tfstate. ② 새 디렉터리에 같은 모듈 호출(값은 해당 환경)과 새 backend key로 init. ③ terraform state push dev.tfstate (새 위치는 비어 있으므로 serial·lineage 충돌 없음). ④ plan이 No changes인지 확인. 리소스 주소가 같아야 하므로 module 이름(app)을 그대로 씁니다. 원래 작업공간은 확인 후 workspace delete -force로 정리하되, state가 버킷 버전닝에 남아 있는지 먼저 확인합니다.

과제 5. Terragrunt dependency

실습 D의 각 환경에 network 유닛(env-sim으로 흉내 내도 좋음)을 추가하고, app 유닛이 dependency "network"로 network의 출력을 입력으로 받게 해 보세요. terragrunt run --all -- plan의 실행 순서가 network → app인지 확인합니다.

힌트

dependency "network" { config_path = "../network" mock_outputs = { summary = "mock" } }를 쓰고 inputs = { … = dependency.network.outputs.summary }. mock_outputs는 network가 아직 apply되지 않은 상태에서 plan할 때 쓰이는 임시 값입니다. 7편에서 SSM으로 했던 값 전달을 Terragrunt 방식으로 바꿔 보는 것으로, 두 방식의 권한·결합도 차이를 비교해 보세요.
