어디에 쓰는가

Serving, Eventing, Functions를 모두 배웠습니다. 이제 질문은 "어떻게"에서 "어디에"로 바뀝니다. 실제로 효과가 큰 여섯 가지 사례를 설계해 보고, 반대로 Knative를 쓰면 오히려 손해인 경우를 가려내는 기준을 세웁니다.

판단의 틀: 네 가지 질문

새 워크로드를 받으면 다음 네 가지를 먼저 묻습니다. 대부분의 판단은 이 네 답에서 갈립니다.

1. 트래픽 모양은?

들쭉날쭉하거나 쉬는 시간이 길수록 0개 축소의 이득이 큽니다. 하루 종일 일정하면 비용 이득은 거의 없고, 대신 Revision·트래픽 분할 같은 배포 편의가 남습니다.

2. 상태를 들고 있나?

Pod가 언제든 사라져도 되는가. 세션, 캐시, 파일을 Pod 안에 두면 안 됩니다. 상태를 외부(DB, 캐시, 객체 저장소)로 뺄 수 있으면 통과입니다.

3. 프로토콜은?

HTTP/1.1, HTTP/2, gRPC는 최적. WebSocket과 SSE 같은 긴 연결은 가능하지만 확장·축소가 둔해집니다. 원시 TCP·UDP는 대상이 아닙니다.

4. 기동이 얼마나 무거운가?

몇 초 안에 뜨면 0개 축소가 자연스럽습니다. 수십 초에서 수 분이 걸리는 대형 모델이나 JVM 대형 앱은 min-scale 전략과 함께 설계해야 합니다.

적합도 진단기

고객사 워크로드의 특성을 골라 보세요. 적합도와 함께 출발점으로 쓸 설정이 나옵니다. 막는 조건(차단 요인)이 하나라도 있으면 점수와 상관없이 다른 도구를 권합니다.

사례 1: AI 모델 추론 (KServe와 함께)

    maxReplicas: 4          # Knative max-scale로 전달

        name: huggingface

소형 분류·임베딩 모델 (CPU)매우 좋음수 초 안에 기동. 0개 축소를 적극 활용. 여러 모델을 한 클러스터에 많이 올려도 쉬는 모델은 자원을 안 씀

KServe의 배포 모드 기본값은 버전마다 다르다

KServe는 Knative 없이 일반 Deployment로 띄우는 모드도 지원하고, 버전에 따라 기본 모드가 다릅니다. Knative 기능을 쓰려면 모드를 명시하고, 클러스터 전역 기본값(KServe 설정의 deploy 항목)도 확인하세요.

LLM과 0개 축소의 딜레마

GPU는 비쌉니다. 그래서 "안 쓸 때 0개로"는 매력적입니다. 하지만 대형 모델은 이미지 수 GB와 모델 가중치 수십 GB를 받아 GPU 메모리에 올리는 데 분 단위가 걸립니다. 첫 사용자가 2분을 기다린다면 서비스로서는 실패입니다. 해법은 하나가 아니라 조합입니다.

시간대별 min-scale

업무 시간에는 min-scale 1, 야간·주말에는 0. Knative에는 시간 기반 설정이 없으므로 CronJob이나 GitOps 스케줄로 어노테이션을 바꿉니다. 바꾸면 새 Revision이 생긴다는 점도 기억하세요.

모델 캐시

모델 가중치를 노드 로컬 디스크나 빠른 공유 스토리지에 미리 두면 기동 시간의 가장 큰 조각이 줄어듭니다. KServe의 로컬 모델 캐시 기능도 검토 대상입니다.

동시성 목표를 배칭에 맞추기

vLLM 같은 서버는 요청을 묶어(연속 배칭) 처리하므로 Pod 하나가 수십 개 요청을 동시에 다룰 수 있습니다. containerConcurrency를 1로 두면 GPU를 놀리게 됩니다. 서버의 효율적인 배치 크기에 맞춰 target을 잡으세요.

긴 응답과 스트리밍

토큰을 스트리밍(SSE)하는 응답은 연결이 오래 유지됩니다. timeoutSeconds를 생성 길이에 맞게 늘리고, 스트리밍 중인 요청이 끝나야 Pod가 내려간다는 점을 확장 설계에 반영하세요.

GPU 쪼개 쓰기

작은 모델 여러 개라면 MIG나 시간 분할로 GPU 하나를 나눠 쓰고, Knative로 모델별 0개 축소를 하면 GPU 활용률이 크게 오릅니다.

노드 확장 시간

GPU 노드 자체를 새로 띄워야 한다면 클라우드에 따라 수 분이 더 걸립니다. 0개 축소의 이득을 계산할 때 노드 단위 비용과 시간도 함께 봐야 합니다.

현실적인 추천

고객사 LLM 서비스라면 "운영 모델은 min-scale 1 이상 + 카나리로 버전 교체", "실험·내부 평가용 모델은 0개 축소"로 나누는 것이 무난한 출발점입니다. 10장 비용 시뮬레이터의 LLM 프리셋으로 숫자를 직접 비교해 보세요.

외부 시스템이 가끔 보내는 웹훅은 Knative의 교과서적인 사례입니다. 하루 대부분 0개로 쉬다가 호출이 오면 깨어납니다. 설계할 때 지킬 점이 세 가지 있습니다.

빨리 받고 나중에 처리

웹훅을 보낸 쪽은 보통 몇 초 안에 응답을 기대합니다. 수신 서비스는 서명 검증과 접수만 하고, 무거운 일은 Broker로 넘겨 비동기로 처리합니다.

콜드 스타트 vs 발신자 타임아웃

발신자의 타임아웃이 짧고 기동이 느리면 첫 호출이 실패합니다. 대부분의 발신자는 재시도하지만, 결제처럼 중요한 웹훅은 min-scale 1로 두는 편이 안전합니다.

중복 대비

발신자의 재시도로 같은 웹훅이 두 번 올 수 있습니다. 웹훅의 고유 ID를 CloudEvent id로 옮겨 5편의 중복 제거 원칙을 적용하세요.

도메인과 HTTPS

외부에 등록할 주소이므로 DomainMapping으로 고정 주소를 주고 HTTPS를 강제합니다(2·4편). 태그 URL을 외부에 등록하지 마세요.

알람 폭주 대비

대형 장애 때 알람이 수백 개 쏟아집니다. Alertmanager의 group_by로 먼저 묶고, summarizer의 max-scale로 LLM 호출 동시 수를 묶어 비용과 API 한도를 지킵니다. 넘치는 이벤트는 Broker(가능하면 Kafka)에 쌓였다가 차례로 처리됩니다.

같은 장애는 한 번만

adapter가 알람 지문(fingerprint)을 CloudEvent id나 확장 속성으로 옮기면, 요약 서비스가 같은 장애의 반복 알람을 묶을 수 있습니다.

고객사별 분리

멀티테넌트 운영이라면 tenant 확장 속성을 붙여 Trigger 필터로 고객사별 처리 경로와 알림 채널을 나눕니다. 민감한 로그를 외부 LLM API로 보낼지는 고객사 보안 정책과 먼저 합의해야 합니다.

요약 서비스의 기동 시간

외부 LLM API를 호출하는 얇은 서비스라면 몇 초 안에 뜨므로 0개 축소가 적합합니다. 사내 GPU에 모델을 직접 띄운다면 4장의 딜레마가 그대로 적용됩니다.

사례 5: 개발·프리뷰 환경

PR마다 미리보기 환경을 띄우면 리뷰 품질이 오르지만, 상시 Pod라면 PR 수만큼 비용이 늘어납니다. Knative라면 리뷰어가 열어 볼 때만 Pod가 뜹니다.

방법 A: PR마다 별도 Service

  • app-pr-123처럼 서비스를 따로 생성
  • PR 단위로 완전히 독립된 설정과 수명
  • PR이 닫히면 CI가 서비스 삭제

방법 B: 한 Service의 태그 Revision

  • 4편의 다크 런치처럼 0% + pr-123 태그
  • 운영과 같은 서비스 설정으로 검증
  • Revision이 쌓이므로 태그 정리 규칙 필요
수치로 보는 효과

열린 PR이 30개이고 각 프리뷰가 하루에 30분 정도 열린다면, 상시 Pod는 30개 × 24시간, Knative는 대략 30개 × (0.5시간 + 축소 대기 시간)만 씁니다. 개발 클러스터 비용의 상당 부분이 사라지는 셈이고, 고객사에 바로 보여 줄 수 있는 성과입니다.

사례 6: 사내 도구와 AI 에이전트 도구

관리 페이지·내부 대시보드

하루 몇 번 쓰는 도구를 모두 상시 Pod로 두면 의외로 비용이 큽니다. 클러스터 내부 전용(cluster-local)이나 사내 인증 뒤에 두고 0개 축소합니다.

배치 트리거 API

"이 리포트 지금 다시 만들어 줘" 같은 요청을 받아 Job을 만들거나 이벤트를 발행하는 얇은 API. 요청은 짧고 드뭅니다.

ChatOps 봇

메신저 명령을 받아 kubectl 조회나 배포 승인을 처리하는 봇. 명령이 올 때만 깨어나면 충분합니다. 권한은 최소로 묶으세요.

AI 에이전트용 도구 서버

에이전트가 호출하는 HTTP 기반 도구(조회 API, MCP 서버 등)는 호출이 드문드문하므로 잘 맞습니다. 다만 세션을 서버 메모리에 들고 있거나 SSE로 연결을 오래 유지하는 방식이면, 세션을 외부 저장소로 빼거나 min-scale을 두어야 Pod 교체 시 세션이 끊기지 않습니다.

정리와 다음 편

  1. 판단은 트래픽 모양, 상태, 프로토콜, 기동 시간 네 질문에서 시작합니다.
  2. AI 추론은 KServe Serverless 모드로 Knative 위에 올리며, 소형 모델일수록 0개 축소 이득이 큽니다.
  3. LLM은 시간대별 min-scale, 모델 캐시, 배칭에 맞춘 동시성 목표를 조합해 콜드 스타트를 다룹니다.
  4. 웹훅은 빨리 받고 Broker로 넘기며, 중복과 발신자 타임아웃에 대비합니다.
  5. AIOps 알람 처리는 max-scale로 LLM 비용을 묶고, 알람 지문으로 중복을 묶습니다.
  6. 프리뷰 환경과 사내 도구는 비용 절감 효과를 가장 빨리 보여 주는 파일럿 대상입니다.
  7. 상태 저장, 원시 TCP, 장시간 작업은 구조적으로 맞지 않으니 다른 도구를 씁니다.

다음 편: 쿠버네티스 플랫폼별 Knative 래핑 현황

OpenShift Serverless, Google Cloud Run과 GKE용 Knative, IBM Cloud Code Engine, Alibaba Cloud의 Knative, VMware Tanzu, 그리고 관리형 Knative가 없는 EKS·AKS까지. 벤더마다 무엇을 덧붙이고, 업스트림과 버전 차이는 얼마나 나며, 고객사 플랫폼별로 어떻게 접근할지 비교합니다.

Knative 강의 시리즈 8편. Knative v1.23을 기준으로 작성했습니다. KServe 필드와 배포 모드 기본값, JobSink 등 최근 기능의 상태는 버전에 따라 다를 수 있습니다. 비용 시뮬레이터는 시간 단위 단순화 모델이며 실제 청구 금액을 의미하지 않습니다.
