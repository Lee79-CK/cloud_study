1

왜 SAML이 생겼을까

문제를 먼저 보면, 해법의 생김새가 자연스러워집니다.

회사에 막 입사한 신입 엔지니어를 떠올려 봅시다. 첫 주에 받아야 하는 계정이 열 개입니다. 사내 위키, 이슈 트래커, AWS 콘솔, 모니터링 대시보드, 근태, 경비, VPN… 각 서비스가 저마다 아이디와 비밀번호를 따로 관리합니다.

서비스마다 비밀번호를 따로 보관하는 세계

사용자는 비밀번호를 열 번 만들고, 회사는 비밀번호 저장소를 열 개 지키게 됩니다. 퇴사자가 생기면 열 군데를 모두 지워야 하고, 한 곳만 놓쳐도 그 계정은 살아 있습니다.

  • 비밀번호 보관 사내 위키 — 자체 계정 DB
  • 비밀번호 보관 이슈 트래커 — 자체 계정 DB
  • 비밀번호 보관 AWS 콘솔 — IAM 사용자
  • 비밀번호 보관 경비 시스템 — 자체 계정 DB
MSP 관점의 진짜 비용 — 고객사 10곳 × 서비스 10개면 관리 지점이 100개입니다. 계정 회수 누락은 감사에서 가장 흔하게 지적되는 항목이고, 사고가 나면 원인 추적도 서비스별로 따로 해야 합니다.

신원 확인을 한 곳에 몰아둔 세계

비밀번호를 아는 곳은 단 한 곳, 회사의 인증 서버뿐입니다. 나머지 서비스는 “저 서버가 확인해 준 사람”이라는 서명된 증명서만 받습니다. 퇴사 처리는 한 곳에서 끝납니다.

  • 비밀번호 보관 회사 인증 서버 (IdP) — 여기 한 곳뿐
  • 증명서 수신 사내 위키 — 비밀번호 모름
  • 증명서 수신 AWS 콘솔 — 비밀번호 모름
  • 증명서 수신 경비 시스템 — 비밀번호 모름
이 “서명된 증명서”가 SAML Assertion입니다. SAML은 이 증명서의 생김새와, 그것을 주고받는 절차를 표준으로 못박은 규격입니다.

한 줄 정의

SAML(Security Assertion Markup Language)은 서로 다른 보안 도메인 사이에서 인증·인가 정보를 XML 문서로 교환하기 위한 개방형 표준입니다. OASIS가 관리하며, 현재 실무에서 쓰는 것은 2005년에 확정된 SAML 2.0 한 가지입니다.

“보안 도메인”이 뭔가요? 계정과 비밀번호를 스스로 관리하는 하나의 관리 영역을 뜻합니다. 우리 회사 계정 체계가 하나의 도메인, AWS가 또 다른 도메인입니다. SAML은 이 경계를 넘어 신원 정보를 전달하는 다리 역할을 합니다. 이 다리를 놓는 행위를 페더레이션(Federation, 연합)이라고 부릅니다.

여기서 중요한 성질 하나. 사용자의 비밀번호는 절대 서비스 쪽으로 넘어가지 않습니다. 서비스는 비밀번호를 볼 일도, 저장할 일도 없습니다. 대신 “이 증명서에 찍힌 서명이 우리가 아는 그 기관의 것인가”만 확인합니다. 신뢰의 근거가 비밀번호에서 전자서명으로 바뀐 것, 이게 SAML의 핵심 아이디어입니다.

2

등장인물은 딱 셋

카드를 눌러 각 역할이 실제로 무엇을 하는지 펼쳐 보세요.

SAML 문서를 읽다 보면 약어가 쏟아지지만, 실제 등장인물은 세 명뿐입니다. 공항 출국 장면에 그대로 대응시키면 헷갈릴 일이 없습니다.

세 카드 중 하나를 눌러 보세요

각 역할이 무엇을 보관하고, 무엇을 만들고, 무엇을 검증하는지 정리해 두었습니다.

헷갈리기 쉬운 지점 — IdP와 SP는 “회사”가 아니라 역할 이름입니다. 같은 제품이 상황에 따라 양쪽 다 될 수 있습니다. 예를 들어 Keycloak은 사내 앱들에게는 IdP지만, 회사 Entra ID와 연동할 때는 그 앞에서 SP 역할을 합니다. “지금 이 흐름에서 누가 신원을 발급하고 누가 받는가”로 판단하세요.
3

신뢰는 저절로 생기지 않는다

사용자가 로그인하기 전에, 관리자들이 먼저 해두는 일이 있습니다.

SP가 처음 보는 IdP의 증명서를 믿을 이유는 없습니다. 그래서 SAML 연동은 사용자가 등장하기 한참 전에, 양쪽 관리자가 정보를 교환하는 것에서 시작합니다. 이걸 흔히 “SAML 연동을 건다”고 표현합니다.

1

SP가 자기 정보를 공개한다

“나는 이런 Entity ID를 쓰고, 응답은 이 URL(ACS URL)로 받겠다.” 이 내용을 담은 XML 파일이 SP 메타데이터입니다.

2

IdP도 자기 정보를 공개한다

“나는 이런 Entity ID를 쓰고, 로그인 창은 이 URL이며, 내 서명을 검증할 공개키(X.509 인증서)는 이것이다.” 이것이 IdP 메타데이터입니다.

3

서로의 메타데이터를 등록한다

관리자가 상대 XML을 업로드하거나 URL을 입력합니다. 이 순간부터 SP는 “이 인증서로 서명된 문서만 받아들이겠다”는 기준이 생깁니다.

4

속성 매핑을 정한다

IdP가 보낼 사용자 정보(이메일, 부서, 그룹)를 SP의 어떤 항목에 꽂을지 약속합니다. AWS 연동이라면 여기서 IAM Role ARN이 오갑니다.

5

신뢰 관계 완성

이제 사용자가 로그인을 시도하면, 오가는 문서의 서명이 등록된 인증서와 맞는지로 진위를 판단합니다. 비밀번호는 여전히 IdP에만 있습니다.

실무에서 가장 자주 터지는 사고 — 3번에서 등록한 인증서에는 만료일이 있습니다. 보통 1~3년입니다. 이 인증서가 만료되면 연동된 모든 서비스가 동시에 로그인 불가가 됩니다. 인증서 만료일을 캘린더에 걸어두는 일은 SAML 운영의 기본기입니다. 3편에서 롤오버 절차를 다룹니다.
4

Assertion 해부하기

색이 칠해진 부분을 클릭하면 그 요소의 정체와 존재 이유가 아래에 나타납니다.

Assertion(어서션)은 IdP가 발급하는 증명서 본체입니다. 번역하면 “주장” 혹은 “단언”인데, 말 그대로 “이 사용자는 이런 사람이고, 내가 이 방법으로 확인했다”는 IdP의 진술입니다. 아래는 군더더기를 걷어낸 실제 구조입니다.

<!-- IdP가 발급한 증명서 본체 -->
<saml:Assertion ID="_a7f2c91e" IssueInstant="2026-09-18T01:22:10Z">

  <saml:Issuer>https://sso.mycompany.com/idp</saml:Issuer>

  <ds:Signature> ... (전자서명) ... </ds:Signature>

  <saml:Subject>
    <saml:NameID Format="...emailAddress">
        kim.engineer@mycompany.com
    </saml:NameID>
    <saml:SubjectConfirmation Method="...bearer">
      <SubjectConfirmationData
          Recipient="https://app.example.com/saml/acs"
          InResponseTo="_req_88b1"
          NotOnOrAfter="2026-09-18T01:27:10Z"/>
    </saml:SubjectConfirmation>
  </saml:Subject>

  <saml:Conditions
      NotBefore="2026-09-18T01:22:10Z"
      NotOnOrAfter="2026-09-18T01:27:10Z">
    <saml:AudienceRestriction>
      <saml:Audience>https://app.example.com/sp</saml:Audience>
    </saml:AudienceRestriction>
  </saml:Conditions>

  <saml:AuthnStatement AuthnInstant="2026-09-18T01:22:08Z"
      SessionIndex="_sess_4410">
    <saml:AuthnContextClassRef>
        ...ac:classes:PasswordProtectedTransport
    </saml:AuthnContextClassRef>
  </saml:AuthnStatement>

  <saml:AttributeStatement>
    <saml:Attribute Name="department">
      <saml:AttributeValue>Cloud Infra</saml:AttributeValue>
    </saml:Attribute>
    <saml:Attribute Name="groups">
      <saml:AttributeValue>sre-oncall</saml:AttributeValue>
    </saml:Attribute>
  </saml:AttributeStatement>

</saml:Assertion>

클릭해서 살펴보세요

밑줄이 그어진 요소와 속성이 클릭 가능합니다. 각각이 없으면 어떤 공격이 가능해지는지까지 함께 설명합니다.

큰 그림으로 묶어 보면 — Assertion 안의 항목은 결국 네 덩어리입니다. 누가 보냈나(Issuer, Signature), 누구에 대한 이야기인가(Subject, NameID), 언제·누구에게만 유효한가(Conditions, Audience), 무엇을 알려주나(AuthnStatement, AttributeStatement). 처음 보는 Assertion을 만나면 이 네 덩어리로 나눠 읽으면 됩니다.
5

실습: 브라우저가 실어 나르는 문자열 열어보기

개발자 도구에서 보게 될 그 알 수 없는 문자열의 정체.

SAML 문서는 브라우저를 통해 전달되기 때문에, XML 그대로가 아니라 Base64로 인코딩된 한 덩어리 문자열로 이동합니다. 실제로 로그인 과정에서 개발자 도구의 Network 탭을 열면 SAMLResponse라는 폼 필드에 이런 문자열이 들어 있습니다. 아래 상자에서 직접 풀어 보세요.

디코딩 버튼을 누르면 여기에 XML이 나타납니다.
Base64는 암호화가 아닙니다. 누구나 되돌릴 수 있는 단순 인코딩이고, 목적은 “XML을 HTTP 폼이나 URL에 안전하게 실어 나르기”입니다. 그래서 Assertion 내용은 기본적으로 중간에서 읽힐 수 있다고 전제해야 합니다. 내용을 감추고 싶으면 별도로 암호화(EncryptedAssertion)를 걸어야 하고, 위조를 막는 건 암호화가 아니라 전자서명의 역할입니다.
2편 예고 — 방금 본 건 HTTP-POST 바인딩입니다. HTTP-Redirect 바인딩에서는 URL 길이 제한 때문에 Deflate 압축 → Base64 → URL 인코딩 순서를 거칩니다. 그래서 Redirect로 온 문자열은 Base64만 풀면 깨져 보입니다. 압축 해제 단계가 하나 더 필요합니다.
6

명세가 4층으로 되어 있다는 사실

SAML 문서가 어렵게 느껴지는 진짜 이유이자, 알고 나면 가장 든든해지는 지식.

SAML 2.0 명세는 하나의 문서가 아니라 네 개의 층으로 나뉘어 있습니다. 많은 입문자가 “Binding과 Profile이 뭐가 다르냐”에서 막히는데, 층을 알면 간단합니다. 무엇을 담을지 → 어떻게 요청할지 → 무엇에 실어 보낼지 → 언제 어떤 조합을 쓸지의 순서입니다.

Assertion — 무엇을 담는가

주고받을 내용물의 형식을 정의합니다. 4장에서 뜯어본 그 XML 구조가 여기에 해당합니다. “사용자 식별자는 NameID에 넣고, 유효기간은 Conditions에 쓴다” 같은 규칙입니다.

Assertion — 증명서의 내용과 형식
Protocol
Binding
Profile

비유하면: 여권에 어떤 항목이 인쇄되는지에 대한 규정.

Protocol — 어떻게 요청하고 응답하는가

Assertion을 달라고 요청하고 받는 절차를 정의합니다. AuthnRequest(로그인 요청), Response(응답), LogoutRequest(로그아웃 요청) 같은 메시지들이 이 층에 있습니다.

Assertion
Protocol — 요청/응답 메시지 규격
Binding
Profile

비유하면: 심사대에서 “여권 주세요 / 여기 있습니다”라고 주고받는 대화의 규칙.

Binding — 무엇에 실어 보내는가

Protocol 메시지를 실제 통신 수단에 어떻게 얹을지를 정의합니다. 같은 AuthnRequest라도 URL 쿼리스트링에 실을 수도 있고(HTTP-Redirect), HTML 폼의 hidden 필드로 자동 전송할 수도 있습니다(HTTP-POST).

Assertion
Protocol
Binding — 전송 수단 (Redirect / POST / Artifact)
Profile

비유하면: 서류를 손으로 건넬지, 우편으로 보낼지, 보관함 번호표만 줄지의 선택.

Profile — 어떤 조합을 언제 쓰는가

위 세 층을 특정 상황에 맞게 조립한 사용 설명서입니다. 우리가 실무에서 쓰는 SSO는 거의 전부 Web Browser SSO Profile 하나입니다. “요청은 Redirect로, 응답은 POST로, Assertion에는 이 항목이 필수” 같은 조합이 여기서 확정됩니다.

Assertion
Protocol
Binding
Profile — 상황별 조합 (Web Browser SSO 등)

비유하면: “국제선 출국 시에는 이 서류를 이 순서로”라고 정리한 안내문.

실무 요령 — 연동 문서를 읽을 때 “Binding은 POST” 같은 말이 나오면 전송 방식 이야기, “Profile은 Web Browser SSO”면 시나리오 이야기입니다. 대부분의 SaaS 연동 가이드는 Web Browser SSO Profile을 전제로 쓰여 있어서 Profile 이야기는 아예 생략되기도 합니다.
7

OAuth와 헷갈리지 않기

셋은 경쟁 관계가 아니라, 애초에 풀려던 문제가 다릅니다.

“SAML이랑 OAuth랑 뭐가 달라요?”는 이 분야에서 가장 흔한 질문입니다. 답은 간단합니다. SAML은 인증(너 누구야?)을 위해 태어났고, OAuth 2.0은 인가(내 데이터에 접근할 권한을 줄게)를 위해 태어났습니다. OIDC는 그 OAuth 위에 인증 기능을 얹어 만든 후발 주자입니다.

비교 항목SAML 2.0OAuth 2.0OIDC
원래 목적 인증 연동(SSO) 권한 위임 인증 연동(SSO)
나온 해 2005 2012 2014
토큰 형식 XML (Assertion) 정해지지 않음 JSON (JWT)
전달 방식 브라우저 리다이렉트 + 폼 POST HTTP API 호출 HTTP API 호출
주 사용처 기업용 SaaS, 사내 시스템 API 접근 권한 모바일·SPA·마이크로서비스

그럼 SAML은 이제 안 쓰나요? 아닙니다. 새로 만드는 시스템은 OIDC를 고르는 게 일반적이지만, 기업 환경에는 SAML만 지원하는 SaaS가 여전히 많고 교체 비용이 큽니다. 실무에서는 “신규는 OIDC, 기존은 SAML 유지”가 가장 흔한 그림이고, 두 프로토콜을 동시에 운영하는 IdP(Keycloak, Entra ID, Okta)가 그 다리를 놓아 줍니다. 마이그레이션 판단 기준은 4편에서 다룹니다.

1편에서 챙겨 갈 것

  • SAML은 보안 도메인 사이에서 인증 정보를 XML로 교환하는 표준이고, 실무 버전은 2.0 하나다.
  • 등장인물은 Principal(사용자), IdP(신원 제공자), SP(서비스 제공자) 셋뿐이며, IdP/SP는 회사가 아니라 역할이다.
  • 신뢰의 근거는 비밀번호가 아니라 전자서명이고, 그 서명을 검증할 인증서는 메타데이터 교환 단계에서 미리 등록된다.
  • Assertion은 네 덩어리로 읽는다 — 누가 보냈나 / 누구 이야기인가 / 언제·누구에게만 유효한가 / 무엇을 알려주나.
  • Audience와 유효시간은 장식이 아니라, 탈취된 증명서의 재사용을 막는 실질적인 방어선이다.
  • 명세는 Assertion → Protocol → Binding → Profile 네 층이고, 실무 SSO는 대부분 Web Browser SSO Profile이다.
  • Base64는 암호화가 아니다. 위조를 막는 건 서명, 내용을 감추는 건 별도의 암호화다.

2편에서는

사용자가 로그인 버튼을 누른 순간부터 화면이 열릴 때까지, 브라우저와 두 서버 사이에서 벌어지는 일을 한 단계씩 따라갑니다. SP-initiated와 IdP-initiated의 차이, HTTP-Redirect·POST·Artifact 바인딩의 선택 기준, RelayState가 원래 가려던 페이지를 어떻게 기억하는지, 그리고 Single Logout이 현실에서 잘 동작하지 않는 이유까지 다룹니다.
