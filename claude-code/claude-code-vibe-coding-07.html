Git의 네 칸

Git이 어려운 이유는 명령이 많아서가 아니라 파일이 지금 어느 칸에 있는지가 눈에 안 보이기 때문입니다. 네 칸만 기억하세요.

  • 작업 폴더: 지금 디스크에 있는 파일. Claude가 Edit로 고치는 곳.
  • 스테이징: 다음 커밋에 넣기로 고른 변경. git add로 올립니다.
  • 로컬 저장소: 커밋들의 기록. 언제든 돌아갈 수 있는 저장 지점.
  • 원격 저장소: GitHub 같은 서버에 있는 사본. git push로 올리고, 다른 사람과 공유하고, 내 컴퓨터가 고장 나도 남습니다.
6편과 연결하면 체크포인트는 Claude의 편집을 세션 안에서만 되돌리고, 커밋은 누가 어떻게 바꿨든 그 시점의 모든 파일을 기억합니다. push까지 하면 내 노트북이 사라져도 남습니다.

설치와 첫 설정

git --version # 없으면 설치: macOS는 xcode-select --install, Ubuntu는 sudo apt install git git config --global user.name "홍길동" git config --global user.email "gildong@example.com" git config --global init.defaultBranch main

커밋에는 이 이름과 이메일이 기록됩니다. GitHub에 공개 저장소를 올릴 계획이라면 GitHub가 제공하는 noreply 이메일을 쓰는 것도 방법입니다. Windows 네이티브라면 Git for Windows를 설치하면 Claude Code의 Bash 도구도 함께 쓸 수 있습니다(3편).

.gitignore 먼저 커밋하면 안 되는 파일(비밀, 로그, 가상환경, 운영체제 찌꺼기, 6편의 export 파일)을 .gitignore에 적어 두면 git add .에서 빠집니다. 실습 2단계에서 Claude에게 만들게 합니다.

커밋을 Claude에게 맡기기

공식 모범 사례 문서의 4단계 흐름 마지막이 “설명적인 메시지로 커밋하고 PR을 만들어”입니다. Claude는 변경 내용을 읽고 메시지를 꽤 잘 씁니다. 여러분이 할 일은 커밋 직전 한 번 보는 것입니다.

대충
커밋해
검토 지점이 있는 커밋
변경 내용을 커밋해줘. 커밋하기 전에 git status와 스테이징할 파일 목록, 커밋 메시지 초안을 먼저 보여주고 내가 확인하면 진행해. 비밀번호·API 키·.env가 섞여 있으면 멈추고 알려줘.

좋은 커밋 메시지

👍

  • 대시보드: 응답 없는 서버를 병렬로 확인 (서버 9대 기준 9초 → 1초)
  • check_disk.sh: --json 옵션 추가, 기존 텍스트 출력 유지
  • 한 커밋 = 한 가지 이유. 무엇을 했는지보다 왜를 한 줄 더

👎

  • update, 수정, fix bug
  • 대시보드, 인증서 스크립트, README가 한 커밋에
  • “WIP”만 수십 개

Claude 표시(attribution)

Claude Code가 만든 커밋 메시지 끝에는 기본으로 Claude가 함께 작성했다는 Co-Authored-By 줄이 붙고, PR 설명 끝에는 Claude Code로 만들었다는 문구가 붙습니다. 팀 규칙에 맞게 바꾸거나 빼려면 settings.json의 attribution을 씁니다. 빈 문자열이면 해당 문구가 빠집니다.

{ "attribution": { "commit": "", "pr": "" } }

AI가 관여한 코드를 표시하도록 정한 조직도 있습니다. 끄기 전에 회사·고객사의 규칙을 먼저 확인하세요. 설정 파일의 위치와 우선순위는 9편에서 다룹니다.

브랜치로 작업 나누기

브랜치는 main을 건드리지 않고 작업하는 갈래입니다. 실험이 실패하면 브랜치를 버리면 그만이고, 성공하면 PR로 main에 합칩니다. 원칙은 단순합니다: 작업 하나 = 브랜치 하나, main에는 직접 커밋하지 않는다.

브랜치 이름 예용도
feat/dark-mode새 기능
fix/timeout-parallel버그 수정
chore/gitignore잡일·설정
acme/INC2041-db-latencyMSP: 고객사·티켓 단위
6편의 /branch와 헷갈리지 마세요 Claude Code의 /branch는 대화를 갈라내고, Git 브랜치는 코드 기록을 갈라냅니다. 둘은 별개입니다. 그리고 Git 브랜치를 바꿔도(git switch) 작업 폴더는 하나라서, 두 세션이 동시에 다른 브랜치에서 일할 수는 없습니다. 그 문제를 푸는 것이 8장의 worktree입니다.

GitHub와 gh CLI

공식 문서는 GitHub를 쓴다면 gh CLI를 설치하라고 권합니다. Claude는 gh로 이슈를 만들고, PR을 열고, 리뷰 코멘트를 읽을 줄 압니다. gh 없이도 GitHub API를 쓸 수 있지만 인증 없는 요청은 자주 한도에 걸립니다. 4편에서 본 것처럼 CLI는 외부 서비스와 일하는 가장 컨텍스트 효율적인 방법입니다.

# 설치 (하나 골라서) brew install gh # macOS sudo apt install gh # Ubuntu (배포판 저장소. 최신 버전은 GitHub CLI 공식 안내 참고) winget install GitHub.cli # Windows # 로그인은 사람이 직접: 브라우저 인증 gh auth login gh auth status
로그인은 직접 하세요 gh auth login은 대화형 브라우저 인증이라 Claude에게 맡기기 어렵고, 맡겨서도 안 됩니다. 토큰을 대화에 붙여 넣으면 세션 기록(평문)에 남습니다(6편). 회사 GitHub와 개인 GitHub를 함께 쓴다면 지금 gh가 어느 계정으로 로그인했는지 gh auth status로 늘 확인하세요.
MSP: 고객사 코드는 비공개, 그리고 회사 조직에 고객사 서버 목록이나 IP가 담긴 저장소는 반드시 private로 만들고, 개인 계정이 아니라 회사 GitHub 조직(또는 GitLab 등 사내 저장소)에 둡니다. 이 실습의 servers.txt는 가짜 주소지만, 습관은 지금부터. GitLab을 쓴다면 glab CLI가 같은 역할을 합니다.

PR 흐름

PR(Pull Request)은 “내 브랜치의 변경을 main에 합쳐 주세요”라는 요청이자, 합치기 전에 변경을 보여 주고 리뷰받는 자리입니다. 혼자 하는 프로젝트라도 PR을 거치면 diff를 웹에서 한 번 더 보게 되고, 나중에 “이 변경은 왜 했지?”의 답이 남습니다.

1
브랜치에서 작업하고 커밋

“feat/dark-mode 브랜치를 만들고 거기서 작업해줘.”

2
push하고 PR 만들기

“push하고 gh pr create로 PR을 만들어줘. 설명에 변경 요약, 검증한 방법과 결과, 남은 일을 넣어.”

3
리뷰

웹에서 “Files changed”를 직접 봅니다. 5편 8장의 여섯 관점(바인딩, 셸, 경로, 비밀, HTML, 타임아웃). 코멘트를 달았다면 “PR 코멘트를 읽고 반영해줘”라고 하면 Claude가 gh로 읽습니다.

4
머지와 정리

머지는 사람이 결정합니다. 그다음 로컬을 최신으로: “main으로 돌아가서 pull하고, 머지된 브랜치는 지워줘.”

PR과 세션이 연결됩니다 Claude Code 세션에서 만든 PR은 그 세션과 연결되어, 나중에 claude --from-pr <번호>로 그 PR을 만든 대화를 찾아 이어갈 수 있습니다. 세션 선택기에 PR 주소를 붙여 넣어 찾을 수도 있습니다(6편). PR마다 자동 리뷰를 붙이는 GitHub Actions 연동은 19편에서 다룹니다.

worktree: 파일까지 격리

git worktree는 자기만의 파일과 브랜치를 가진 별도의 작업 폴더로, 원래 폴더와 같은 저장소 기록과 원격을 공유합니다. Claude Code 세션마다 worktree를 따로 쓰면 한 세션의 편집이 다른 세션의 파일을 건드리지 않아, 한 터미널에서 기능을 만들며 다른 터미널에서 버그를 고칠 수 있습니다. 6편 실습 4단계에서 겪은 “갈래가 파일을 공유하는” 문제의 해답입니다.

claude --worktree dark-mode # 또는 claude -w dark-mode claude --worktree "#12" # PR 12번 브랜치로 worktree를 만들어 리뷰·수정
알아 둘 것내용
위치와 브랜치기본으로 저장소 루트의 .claude/worktrees/<이름>/에 worktree-<이름> 브랜치로 만들어집니다. 다른 위치를 원하면 WorktreeCreate Hook(11편).
.env 같은 파일worktree는 새로 꺼낸 폴더라 Git에 없는 파일(.env 등)이 없습니다. 루트에 .worktreeinclude(.gitignore 문법)를 두면 그 패턴이면서 gitignore된 파일만 자동으로 복사됩니다.
끝낼 때변경·새 파일·새 커밋이 없으면 worktree와 브랜치가 자동으로 지워집니다(이름 붙인 세션이면 먼저 물어봄). 변경이 있으면 남길지 물어봅니다.
-p로 만든 worktree종료 질문이 없어 자동 정리되지 않습니다. git worktree remove로 지웁니다.
데스크톱 앱새 세션마다 worktree를 자동으로 만듭니다.
권장: worktree 폴더를 .gitignore에 .claude/worktrees/가 저장소 안에 생기므로, .gitignore에 넣어 실수로 커밋되지 않게 해 두면 안심입니다. 그리고 worktree마다 개발 서버를 띄운다면 포트가 겹치지 않게 하세요(5편 확장 과제의 PORT 환경 변수).

위험한 Git 명령 지도

3편에서 본 것처럼 Auto 모드의 분류기는 force push와 git reset --hard 같은 일부 위험한 명령을 기본으로 막습니다. 하지만 Manual로 승인하거나 다른 모드라면 여러분이 마지막 관문입니다. 이 명령이 승인 요청에 보이면 멈추고 읽으세요.

비밀을 커밋해 push했다면 커밋을 지우는 것보다 키를 먼저 폐기·교체하는 것이 우선입니다. 공개 저장소의 키는 수 분 안에 수집될 수 있습니다(1편 리스크 지도). 기록에서 지우는 작업은 그다음이며, 이미 복제된 사본은 지울 수 없다고 가정하세요. 10편·11편에서 커밋 전에 비밀을 자동으로 잡는 Hook을 만듭니다.
