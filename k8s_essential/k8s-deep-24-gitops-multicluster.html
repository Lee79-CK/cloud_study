관측·멀티클러스터·GitOps 운영

MSP는 클러스터 하나가 아니라 수십 개의 서로 다른 클러스터를 운영합니다. 그 클러스터들을 같은 눈으로 보고(관측), 같은 기준선으로 맞추고(멀티클러스터 관리), 같은 저장소에서 배포(GitOps)할 수 있어야 사람 수가 클러스터 수에 비례해 늘지 않습니다. 이 편은 벤더 관측 스택과 자체 Prometheus·Grafana, v1.37에서 stable이 된 metrics.k8s.io와 HPA의 새 기능, Rancher·ACM·Fleet·Azure Arc·GKE Fleet, Argo CD·Flux를 비교하고, 벤더 차이를 오버레이로 흡수하는 패턴으로 하나의 Git 저장소에서 kubeadm·EKS·OpenShift에 같은 앱을 배포합니다.

기준: Kubernetes v1.37 · Argo CD 3.x · Flux 2.x · Kustomize 작성 기준일: 2026-10-24 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

같은 앱, 다른 클러스터: 오버레이 렌더러

하나의 base(공통 매니페스트)에 클러스터별 오버레이를 얹으면 최종 매니페스트가 어떻게 달라지는지 보여 줍니다. 대상 클러스터를 바꿔 오른쪽 “base 대비 바뀐 것” 목록을 비교하세요. 7장 실습의 저장소와 같은 구성입니다. 이 차이를 앱 개발자가 아니라 플랫폼 오버레이가 떠안는 것이 핵심입니다.

읽는 법과 목표

    
쉬운 말로
    프랜차이즈 식당 수십 곳을 운영한다고 생각해 보세요. 모든 지점의 매출·대기 시간을 한 화면에서 보는 것이 관측, 모든 지점에 같은 위생 규칙과 직원 권한을 내려보내는 것이 멀티클러스터 관리, 본사 레시피 책(Git)에 적힌 대로 지점 주방이 스스로 맞춰지는 것이 GitOps입니다. 그런데 지점마다 주방 장비(벤더)가 달라 “오븐 온도”를 지점별로 조금씩 바꿔 적어야 하는데, 그것이 오버레이입니다. 레시피 본문(base)은 하나로 두고, 지점별 메모(오버레이)만 다르게 둡니다.

    

      
이 편을 마치면 할 수 있는 것

      
    
        
  • 벤더 관측 스택과 자체 Prometheus·Grafana를 비용·카디널리티·보존·멀티테넌시 기준으로 비교할 수 있습니다.
    • 
        
  • metrics.k8s.io/v1(1.37 stable), HPA 허용 오차(1.37 stable), HPA 0으로 축소(1.37 베타)를 이해하고 쓸 수 있습니다.
    • 
        
  • Rancher·Red Hat ACM·Fleet·Azure Arc·GKE Fleet로 정책·RBAC·네트워크 설정을 중앙 배포하는 방식을 비교할 수 있습니다.
    • 
        
  • Argo CD와 Flux를 비교하고, Kustomize 오버레이·컴포넌트로 벤더 차이를 흡수하는 저장소를 설계할 수 있습니다.
    • 
        
  • 하나의 저장소로 서로 다른 세 클러스터에 같은 앱과 플랫폼 기준선을 배포할 수 있습니다.

고르는 기준

      
    
        
  • 비용 모델. 관리형 지표는 수집 샘플 수(또는 시계열 수)로, 로그는 수집 GB로 과금됩니다. 자체 운영은 저장소·인력 비용입니다. 아래 계산기로 감을 잡으세요.
    • 
        
  • 카디널리티. 레이블 값 조합 수가 시계열 수를 정합니다. Pod UID·요청 경로·사용자 ID 같은 레이블은 시계열을 폭발시킵니다.
    • 
        
  • 멀티클러스터 시야. 여러 클러스터·여러 클라우드를 한 화면에 모으려면 공통 수집기(OpenTelemetry Collector·Prometheus 원격 쓰기)와 중앙 저장소가 필요합니다. 벤더 스택은 같은 벤더 안에서 강합니다.
    • 
        
  • MSP의 현실적 조합. 각 클라우드의 플랫폼 지표·로그는 벤더 기본으로 받고, 애플리케이션 지표와 경보 규칙은 공통 형식(Prometheus 규칙, OTel)으로 중앙에 모으는 이중 구조가 흔합니다.

metrics.k8s.io/v1과 v1.37 HPA

    

      
API무엇을 주나누가 구현1.37 상태

external.metrics.k8s.io클러스터 밖 지표(큐 길이, 클라우드 지표)Prometheus Adapter, KEDA, 벤더 어댑터—

      
    

    

      
HPA의 1.37 변화

      
    
        
  • 허용 오차(tolerance) GA. 예전에는 클러스터 전체에 고정된 10%였습니다. 이제 HPA마다, 확장·축소 방향마다 따로 정합니다(behavior.scaleUp.tolerance). 대형 서비스는 5%처럼 작게 둬야 작은 부하 증가에도 반응합니다.
    • 
        
  • 0으로 축소(scale to zero) 베타·기본 켜짐. 객체·외부 지표를 쓰는 HPA는 minReplicas: 0으로 워크로드를 0개까지 줄였다가 지표가 생기면 다시 올립니다. HPA가 0으로 줄인 것인지 알 수 있는 ScaledToZero 조건이 생겼습니다. 지표를 읽지 못하면 0에서 다시 올라오지 못하므로 지표 파이프라인 경보가 필수입니다.
    • 
        
  • KEDA와의 관계. KEDA는 다양한 이벤트 소스(큐·스트림·크론)를 external 지표로 바꿔 HPA를 구동하고 0 축소를 오래전부터 지원해 왔습니다. 소스가 다양하면 여전히 KEDA가 편합니다.
    • 
      

    

    
허용 오차와 0 축소를 쓰는 HPA
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: web}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: web}
  minReplicas: 2
  maxReplicas: 30
  metrics:
  - type: Resource
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 60}}
  behavior:
    scaleUp:   {tolerance: 0.05, stabilizationWindowSeconds: 0}    # 5%만 넘어도 확장
    scaleDown: {tolerance: 0.15, stabilizationWindowSeconds: 300}  # 줄일 땐 느긋하게
---
# 큐 소비자: 외부 지표로 0까지
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: queue-worker}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: queue-worker}
  minReplicas: 0
  maxReplicas: 10
  metrics:
  - type: External
    external:
      metric: {name: queue_depth, selector: {matchLabels: {queue: tasks}}}
      target: {type: AverageValue, averageValue: "30"}

멀티테넌시AppProject로 대상 클러스터·네임스페이스·리소스 제한, SSO·RBAC네임스페이스 단위 테넌트, 가장(impersonation)으로 권한 축소

        
순서 제어동기화 웨이브·훅Kustomization 간 dependsOn

보안 관점허브가 모든 클러스터 자격 증명을 가짐 → 허브가 가장 민감한 자산(22편)각 클러스터가 자기 권한만, 중앙 자격 증명 없음

        
벤더 연계OpenShift GitOps(Red Hat 지원), ACMAzure Arc·AKS GitOps 확장, Weave 생태계

      
    

    

      
비밀은 Git에 평문으로 두지 않는다

      
GitOps 저장소에는 비밀 값을 두지 않습니다. 선택지는 Sealed Secrets(공개 키 암호화), SOPS(파일 암호화, Flux가 기본 지원), External Secrets Operator(외부 저장소 참조, 22편)이며, 클라우드 비밀 관리자와 워크로드 아이덴티티(20편) 조합이 가장 깔끔합니다.

저장소 구조와 패턴

      
오버레이를 클러스터마다 복사해 늘리면 몇 달 뒤 서로 달라져 관리 불가가 됩니다. Kustomize 컴포넌트(재사용 가능한 패치 묶음)로 “벤더 특성”을 만들고, 클러스터 오버레이는 컴포넌트를 고르는 짧은 목록으로만 유지합니다. 클러스터 목록은 ApplicationSet 생성기(또는 Fleet·ACM의 레이블 선택)로 만듭니다.

    

    
gitops-lab/
├── platform/                    ← 플랫폼 기준선(플랫폼 팀 소유)
│   ├── base/                    공통: 네임스페이스 web-app (18편 RBAC·9편 기본 거부·21편 VAP를 여기에 추가)
│   └── overlays/{kubeadm,eks,openshift}/   app-block StorageClass(클러스터별 프로비저너), PSA 레이블 여부
├── apps/web/                    ← 애플리케이션(앱 팀 소유)
│   ├── base/                    Deployment·Service·PVC(app-block)·HPA — 벤더 중립, 노출 방식 없음
│   ├── components/
│   │   ├── fixed-uid/           runAsUser·fsGroup 65532 (비 OpenShift)
│   │   ├── gateway-route/       HTTPRoute (Gateway API, 8편)
│   │   ├── aws-lb/              Service를 NLB로 + 어노테이션 (7편)
│   │   └── openshift-route/     Route
│   └── overlays/
│       ├── kubeadm/   components: [fixed-uid, gateway-route]
│       ├── eks/       components: [fixed-uid, aws-lb]
│       └── openshift/ components: [openshift-route]
└── clusters/{kubeadm,eks}/      Flux Kustomization(platform → apps 순서)
    clusters/openshift/          OpenShift GitOps(Argo CD) Application

플랫폼 기준선의 중앙 배포

    

      
Level 1~3에서 만든 것들이 결국 “모든 고객 클러스터에 깔려야 하는 기준선”입니다. 이를 GitOps로 배포하면 새 클러스터도 몇 분 안에 같은 상태가 됩니다.

    

    

      
순서(웨이브)내용출처 편

      
        
-2CRD(Gateway API, 스냅샷, 정책 엔진), 네임스페이스8·12·21

        
-1플랫폼 컨트롤러(Gateway 구현, CSI, External Secrets, 정책 엔진), StorageClass(공통 이름)8·11·13·22

        
0정책: PSA 레이블, VAP·MAP, 기본 거부 NetworkPolicy9·21

        
1RBAC: 조직 역할, 그룹 바인딩(플랫폼별 주체 표기 오버레이)17·18·19

        
2관측 수집기, 감사 로그 포워딩, 백업 스케줄15·22·24

        
3애플리케이션—

      
    

    
함정: 중앙에서 지우면 모든 곳에서 지워진다
    ApplicationSet이나 Fleet 번들에서 클러스터를 빼거나 생성기 조건을 바꾸면, 연결된 Application이 지워지고 자동 정리(prune) 설정에 따라 그 클러스터의 리소스가 모두 삭제될 수 있습니다. 네임스페이스와 PVC가 함께 지워지면 15편의 Delete 정책 디스크까지 사라집니다. 기준선·상태 있는 리소스에는 삭제 보호(preserveResourcesOnDeletion, prune 비활성, 리소스 단위 어노테이션)를 거세요.

실습: 하나의 저장소로 kubeadm·EKS·OpenShift에 같은 앱

    

      
실습 랩의 클러스터들은 서로의 API 서버에 닿지 못할 수 있습니다(멀티패스 VM, CRC, 클라우드). 그래서 중앙 허브가 밀어 주는 방식 대신, 각 클러스터가 같은 저장소를 당겨 오는 방식을 씁니다. lab-native와 lab-eks에는 Flux를, lab-ocp에는 OpenShift GitOps(Argo CD)를 둡니다. 엔진이 달라도 같은 오버레이가 그대로 쓰인다는 것이 이 실습의 요점입니다. GitHub 계정과 개인 접근 토큰이 필요합니다.

      
실습 0. 저장소 만들기 (scaffold.sh)

    

    
scaffold.sh — 저장소 뼈대 생성
#!/usr/bin/env bash
set -e; mkdir -p gitops-lab && cd gitops-lab
mk(){ mkdir -p "$(dirname "$1")"; cat > "$1"; }
# ---------- apps/web/base: 벤더 중립 ----------
mk apps/web/base/deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 2
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      securityContext: {runAsNonRoot: true, seccompProfile: {type: RuntimeDefault}}
      containers:
      - name: web
        image: registry.k8s.io/e2e-test-images/agnhost:2.52
        args: ["netexec", "--http-port=8080"]
        ports: [{containerPort: 8080}]
        readinessProbe: {httpGet: {path: /hostname, port: 8080}}
        resources: {requests: {cpu: 50m, memory: 32Mi}}
        securityContext: {allowPrivilegeEscalation: false, capabilities: {drop: ["ALL"]}}
        volumeMounts: [{name: data, mountPath: /data}]
      volumes: [{name: data, persistentVolumeClaim: {claimName: web-data}}]
EOF
mk apps/web/base/service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata: {name: web}
spec: {selector: {app: web}, ports: [{port: 80, targetPort: 8080}]}
EOF
mk apps/web/base/pvc.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: web-data}
spec: {storageClassName: app-block, accessModes: ["ReadWriteOnce"], resources: {requests: {storage: 1Gi}}}
EOF
mk apps/web/base/hpa.yaml <<'EOF'
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: web}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: web}
  minReplicas: 2
  maxReplicas: 6
  metrics: [{type: Resource, resource: {name: cpu, target: {type: Utilization, averageUtilization: 60}}}]
  behavior: {scaleUp: {tolerance: 0.05}}
EOF
mk apps/web/base/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: web-app
resources: [deployment.yaml, service.yaml, pvc.yaml, hpa.yaml]
EOF
# ---------- 컴포넌트 ----------
mk apps/web/components/fixed-uid/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
patches:
- target: {kind: Deployment, name: web}
  patch: |-
    - {op: add, path: /spec/template/spec/securityContext/runAsUser, value: 65532}
    - {op: add, path: /spec/template/spec/securityContext/fsGroup, value: 65532}
EOF
mk apps/web/components/gateway-route/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
resources: [httproute.yaml]
EOF
mk apps/web/components/gateway-route/httproute.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: web}
spec:
  parentRefs: [{name: shared, namespace: infra}]     # 8편 실습의 공유 Gateway 이름으로 바꿈
  rules: [{backendRefs: [{name: web, port: 80}]}]
EOF
mk apps/web/components/aws-lb/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
patches:
- target: {kind: Service, name: web}
  patch: |-
    apiVersion: v1
    kind: Service
    metadata:
      name: web
      annotations:
        service.beta.kubernetes.io/aws-load-balancer-type: external
        service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
        service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
    spec: {type: LoadBalancer}
EOF
mk apps/web/components/openshift-route/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
resources: [route.yaml]
EOF
mk apps/web/components/openshift-route/route.yaml <<'EOF'
apiVersion: route.openshift.io/v1
kind: Route
metadata: {name: web}
spec: {to: {kind: Service, name: web}, port: {targetPort: 8080}, tls: {termination: edge}}
EOF
# ---------- 앱 오버레이 ----------
ov(){ mk apps/web/overlays/$1/kustomization.yaml <<EOF
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources: [../../base]
components: [$2]
EOF
}
ov kubeadm   "../../components/fixed-uid, ../../components/gateway-route"
ov eks       "../../components/fixed-uid, ../../components/aws-lb"
ov openshift "../../components/openshift-route"
# ---------- 플랫폼: 네임스페이스와 공통 이름 StorageClass ----------
mk platform/base/kustomization.yaml <<'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources: [namespace.yaml]
EOF
mk platform/base/namespace.yaml <<'EOF'
apiVersion: v1
kind: Namespace
metadata: {name: web-app}
EOF
pf(){ # pf 클러스터 프로비저너 [psa]
  mk platform/overlays/$1/storageclass.yaml <<EOF
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: {name: app-block}
provisioner: $2
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
EOF
  if [ "$3" = psa ]; then P='
patches:
- target: {kind: Namespace, name: web-app}
  patch: |-
    - {op: add, path: /metadata/labels, value: {pod-security.kubernetes.io/enforce: restricted}}'; else P=""; fi
  mk platform/overlays/$1/kustomization.yaml <<EOF
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources: [../../base, storageclass.yaml]$P
EOF
}
pf kubeadm   rancher.io/local-path psa
pf eks       ebs.csi.aws.com psa
pf openshift kubevirt.io.hostpath-provisioner        # CRC 기준. oc get sc 로 실제 프로비저너 확인 후 수정
# EKS는 gp3 파라미터 추가
printf 'parameters: {type: gp3}\n' >> platform/overlays/eks/storageclass.yaml
echo "생성 완료"; find . -type f | sort

    
로컬에서 렌더링 비교 (맨 위 렌더러와 같은 결과인지)

실습 1. lab-native·lab-eks: Flux로 당겨 오기

    
Flux 부트스트랩과 클러스터별 Kustomization
export GITHUB_TOKEN=ghp_xxx GITHUB_USER=<계정>
curl -s https://fluxcd.io/install.sh | sudo bash; flux --version
for c in kubeadm:lab-native eks:lab-eks; do n=${c%%:*}; ctx=${c#*:}
  flux check --pre --context $ctx
  flux bootstrap github --context $ctx --owner $GITHUB_USER --repository gitops-lab --personal --branch main --path clusters/$n
done
git pull
# 각 클러스터 경로에 platform → apps 순서의 Kustomization 추가
for n in kubeadm eks; do cat > clusters/$n/web.yaml <<EOF
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata: {name: platform, namespace: flux-system}
spec: {interval: 5m, path: ./platform/overlays/$n, prune: true, sourceRef: {kind: GitRepository, name: flux-system}}
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata: {name: web, namespace: flux-system}
spec:
  interval: 1m
  dependsOn: [{name: platform}]                       # 기준선(StorageClass·네임스페이스) 먼저
  path: ./apps/web/overlays/$n
  prune: true
  sourceRef: {kind: GitRepository, name: flux-system}
EOF
done
git add -A && git commit -qm "kubeadm, eks: platform + web" && git push
flux get kustomizations --context lab-native; flux get kustomizations --context lab-eks

원인. 새 클러스터마다 기존 오버레이 폴더를 복사해 고쳤고, 1년 뒤 같은 벤더 클러스터끼리도 설정이 달랐습니다.

      
교훈. 벤더 특성은 컴포넌트로, 클러스터 오버레이는 컴포넌트 목록만. 공통 이름 StorageClass처럼 차이를 플랫폼 쪽으로 밀어내세요(5장).

    

    
ApplicationSet 수정 한 번으로 여러 클러스터의 앱이 지워졌다

      
원인. 생성기의 클러스터 레이블 조건을 바꾸자 일부 클러스터가 대상에서 빠졌고, prune 설정 때문에 그 클러스터들의 네임스페이스와 PVC가 삭제되었습니다.

      
교훈. 삭제 보호(6장 함정), 생성기 변경은 미리보기(diff)와 승인 후 적용.

    

    
CRD보다 CR이 먼저 동기화돼 계속 실패

      
원인. 새 클러스터 부트스트랩에서 Gateway·정책 CR이 CRD보다 먼저 적용되어 “no matches for kind” 오류가 반복되었습니다.

      
교훈. 동기화 웨이브(Argo CD)·dependsOn(Flux)으로 CRD → 컨트롤러 → 정책 → 앱 순서를 고정하세요(6장 표).

    

    
OpenShift에서만 Pod가 뜨지 않았다

      
원인. base 매니페스트에 runAsUser를 고정해 두었고, restricted-v2 SCC의 UID 범위 밖이라 거부되었습니다.

      
교훈. 고정 UID는 비 OpenShift 컴포넌트로 분리(실습의 fixed-uid). base는 가장 엄격한 공통 분모로.

    

    
정책을 enforce로 배포했더니 운영 리소스가 바뀌었다

      
원인. 중앙 관리 도구의 정책을 처음부터 enforce(자동 교정)로 배포해, 기준과 다른 운영 설정이 자동으로 덮어써졌습니다.

      
교훈. 중앙 정책도 21편처럼 inform·audit → enforce 순서로. 교정 범위를 먼저 보고서로 확인하세요.

    3.

    5. 
        
  5. 벤더 차이는 Kustomize 컴포넌트와 공통 이름(StorageClass 등)으로 흡수하고, 기준선은 웨이브 순서와 삭제 보호를 갖춰 중앙에서 배포합니다.
