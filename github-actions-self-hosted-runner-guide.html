DevOps 온보딩 · 실습형 강의

내 서버를 GitHub Actions의
일꾼(Runner)으로 만드는 법

GitHub Actions는 편하지만, 사내망 DB에 접근해야 하거나 GPU가 필요하거나 빌드 시간을 줄이고 싶을 때가 옵니다. 그때 필요한 게 Self-Hosted Runner입니다. 이 문서는 러너를 한 번도 만져본 적 없는 신입 엔지니어가 개념 → 설치 → 운영 → 장애 대응까지 혼자 완주할 수 있도록 만든 실습 가이드입니다.

01

러너(Runner)가 뭔가요?

CI/CD를 '주문서'와 '주방'으로 이해하기

GitHub Actions를 처음 배울 때 가장 헷갈리는 지점은 "YAML을 쓰면 누가 실행하는가"입니다. 비유로 정리하면 아주 간단합니다.

📝 워크플로우 YAML

주문서. "빌드하고 테스트하고 배포해줘"라고 적어둔 종이일 뿐, 스스로 아무것도 하지 않습니다.

☁️ GitHub (컨트롤 플레인)

주문 접수 카운터. 이벤트(push, PR)를 감지해 잡(Job)을 큐에 넣고 결과를 모아 보여줍니다.

🏃 러너 (Runner)

주방. 실제로 npm ci, docker build를 실행하는 컴퓨터입니다. 여기가 러너입니다.

즉 러너는 GitHub이 내려주는 명령을 대신 실행해주는 에이전트 프로그램이 설치된 머신입니다. 이 머신을 GitHub이 빌려주면 GitHub-hosted runner, 내가 준비하면 Self-hosted runner라고 부릅니다.

용어 정리 Workflow = 파이프라인 전체(.github/workflows/*.yml) · Job = 한 머신에서 실행되는 작업 묶음 · Step = 잡 안의 명령 한 줄 · Runner = 잡 하나를 맡아 처리하는 실행기. 러너 1대는 기본적으로 동시에 잡 1개만 처리합니다(이게 나중에 큐 적체의 원인이 됩니다).
02

GitHub-hosted vs Self-hosted

언제 직접 구축해야 하는지 판단 기준 잡기
비교 항목GitHub-hostedSelf-hosted
준비 작업runs-on: ubuntu-latest 한 줄. 끝.서버 준비 + 에이전트 설치 + 운영 책임
환경 초기화매 잡마다 깨끗한 새 VM기본은 재사용(이전 잡의 흔적이 남음)
사내망 접근불가 (외부 IP에서 실행)가능 — 내부 DB·레지스트리·K8s API 직접 호출
하드웨어표준 스펙 (기본 2~4 vCPU)자유 — GPU, 대용량 RAM, ARM, macOS 실기
빌드 캐시매번 재다운로드 (Actions 캐시 의존)로컬 디스크에 Docker layer·node_modules 잔존 → 빠름
비용 구조실행 분 단위 과금 (Public repo 무료)Actions 사용료 무료, 대신 서버·전기·인건비
OS 업데이트GitHub이 이미지 관리내가 패치·툴체인 관리
보안 리스크낮음 (샌드박스 격리)높음 — Public repo에 붙이면 서버 탈취 위험

이럴 때 Self-hosted를 씁니다

✅ 도입하기 좋은 경우
  • 사내망 전용 자원(사내 Nexus/Harbor, 온프렘 K8s, 폐쇄망 DB)에 붙어야 함
  • GPU 학습·추론 테스트, 대용량 빌드(모노레포, C++, 안드로이드)
  • 빌드 캐시 재사용으로 파이프라인 시간을 크게 줄이고 싶음
  • 특수 하드웨어/OS(ARM 보드, macOS 실기, Windows 라이선스 툴)
  • 월 Actions 사용 분(minutes)이 한도를 계속 초과함
🚫 도입을 미뤄야 하는 경우
  • Public(오픈소스) 리포지토리 — 외부인의 PR이 내 서버에서 실행됨
  • 운영 담당자가 없어 방치될 예정(패치 안 된 러너는 취약점 덩어리)
  • 단순 lint/유닛테스트만 돌리는 소규모 프로젝트
  • 잡 간 격리가 반드시 필요한데 컨테이너/일회성 구성을 못 할 때
실무 팁 둘은 배타적이지 않습니다. 혼합 전략이 정석입니다 — lint·유닛테스트는 ubuntu-latest로, 사내 배포·성능테스트만 runs-on: [self-hosted, deploy]로 분리하세요.
03

동작 원리: 왜 방화벽을 열지 않아도 되나

Long Polling — 러너가 GitHub에게 "일 있어요?"를 먼저 묻는다

신입 엔지니어가 가장 많이 하는 오해가 "GitHub이 우리 서버로 접속하니까 인바운드 포트를 열어야 한다"는 것입니다. 정반대입니다. 러너 에이전트가 GitHub으로 아웃바운드 HTTPS(443) 연결을 먼저 맺고, 그 연결을 열어둔 채(long polling) 새 잡이 생길 때까지 기다립니다.

잡이 러너에게 배정되는 순서

  1. 등록(Registration) — config.sh 실행 시 등록 토큰으로 GitHub에 러너를 등록하고, 장기 인증 정보를 .credentials에 저장합니다.
  2. 리스닝(Long Poll) — run.sh가 실행되면 GitHub에 "잡 주세요" 요청을 걸어두고 약 50초 단위로 재연결합니다. 상태는 Idle.
  3. 라벨 매칭 — 잡의 runs-on 라벨을 모두 만족하는 Idle 러너에게 GitHub이 잡을 할당합니다.
  4. 실행 — 러너는 Runner.Worker 프로세스를 띄워 스텝을 실행하고 로그를 실시간 업로드합니다. 상태는 Active.
  5. 정리 후 복귀 — 잡 종료 후 워크스페이스를 남긴 채(기본값) 다시 Idle로 돌아가 다음 잡을 기다립니다.

여기서 5분 확인하면 뒤에서 2시간을 아낍니다

항목권장 사양메모

실행 계정전용 일반 사용자 (예: actions)root로 run.sh 실행 금지

  • Repository 러너 등록 → 해당 리포지토리 admin 권한
  • Organization 러너 등록 → Org owner 권한
  • Enterprise 러너 등록 → Enterprise 관리자 권한

③ 사전 점검 스크립트

설치 전에 아래를 그대로 붙여 실행하세요. 하나라도 FAIL이면 그 문제부터 해결합니다.

#!/usr/bin/env bash
# 러너 설치 전 환경 점검 — 실패 항목만 고치면 됩니다
set -u
ok(){ echo -e "  \033[32mPASS\033[0m $1"; }
ng(){ echo -e "  \033[31mFAIL\033[0m $1"; }

echo "[1] OS / 아키텍처"
echo "  $(uname -srm)"   # aarch64면 ARM64 패키지를 받아야 함

echo "[2] 필수 명령어"
for c in curl tar git sudo; do
  command -v "$c" >/dev/null && ok "$c" || ng "$c 없음 → 패키지 설치 필요"
done

echo "[3] 디스크 여유 (30GB 이상 권장)"
avail=$(df -BG --output=avail /opt 2>/dev/null | tail -1 | tr -dc '0-9')
[ "${avail:-0}" -ge 30 ] && ok "${avail}GB 사용 가능" || ng "여유 ${avail}GB — 부족"

echo "[4] GitHub 아웃바운드 443 연결"
for h in github.com api.github.com codeload.github.com \
           objects.githubusercontent.com vstoken.actions.githubusercontent.com; do
  code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 6 "https://$h")
  [ "$code" != "000" ] && ok "$h (HTTP $code)" || ng "$h 차단 → 방화벽/프록시 확인"
done

echo "[5] 시간 동기화 (틀어지면 토큰 인증 실패)"
timedatectl show -p NTPSynchronized --value 2>/dev/null | grep -q yes \
  && ok "NTP 동기화됨" || ng "NTP 미동기화 → chrony/systemd-timesyncd 설정"

echo "[6] Docker (컨테이너 잡을 쓸 경우)"
if command -v docker >/dev/null; then
  docker info >/dev/null 2>&1 && ok "docker 사용 가능" \
    || ng "docker 권한 없음 → usermod -aG docker \$USER 후 재로그인"
else echo "  SKIP docker 미설치"; fi

echo "[7] 전용 실행 계정 (root 실행 금지)"
[ "$(id -u)" -ne 0 ] && ok "현재 $(whoami)" || ng "root — 일반 계정으로 전환하세요"
# Windows PowerShell (관리자 아님, 일반 세션에서)
Write-Host "[1] OS"; (Get-ComputerInfo).OsName

Write-Host "[2] 디스크 여유"
Get-PSDrive C | Select-Object @{n='FreeGB';e={[math]::Round($_.Free/1GB,1)}}

Write-Host "[3] GitHub 연결"
'github.com','api.github.com','objects.githubusercontent.com' | ForEach-Object {
  $r = Test-NetConnection -ComputerName $_ -Port 443 -InformationLevel Quiet
  "{0,-40} {1}" -f $_, $(if($r){'PASS'}else{'FAIL'})
}

Write-Host "[4] 실행 정책 (스크립트 차단 여부)"
Get-ExecutionPolicy -List

Write-Host "[5] 경로 길이 제한 해제 여부 (긴 경로 빌드 실패 예방)"
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' -Name LongPathsEnabled
폐쇄망·프록시 환경 주의 Test-NetConnection이나 curl이 막히면 설치 자체가 진행되지 않습니다. 보안팀에 요청할 도메인 목록을 미리 정리해 두세요: github.com, api.github.com, codeload.github.com, *.actions.githubusercontent.com, objects.githubusercontent.com, *.pkg.github.com, ghcr.io. 최신 IP 대역은 https://api.github.com/meta의 actions 항목에서 확인합니다.
05

등록 범위 선택: Repository / Organization / Enterprise

잘못 고르면 나중에 러너를 전부 재등록해야 합니다
추천 처음 실습은 개인 테스트 리포지토리에 Repository 러너로 붙여 감을 잡고, 사내 도입 시에는 Organization 러너 + Runner Group으로 설계하세요. 등록 범위는 나중에 바꿀 수 없어서, 바꾸려면 config.sh remove 후 재등록해야 합니다.

첫 확인용 워크플로우

  
러너가 살아있는지 검증하는 최소 워크플로우입니다. .github/workflows/runner-check.yml로 저장하고 수동 실행하세요.

  

    

      
      
      
    


    
name: 러너 상태 점검
on:
  workflow_dispatch:        # Actions 탭에서 수동 실행 버튼 생성

jobs:
  check:
    runs-on: [self-hosted, Linux, X64]   # ← 라벨 AND 조건
    timeout-minutes: 10                       # 무한 대기 방지 (필수 습관)
    steps:
      - name: 러너 신원 확인
        run: |
          echo "호스트명   : $(hostname)"
          echo "실행 계정  : $(whoami)"
          echo "러너 이름  : $RUNNER_NAME"
          echo "작업 경로  : $RUNNER_WORKSPACE"
          echo "OS/ARCH    : $RUNNER_OS / $RUNNER_ARCH"

      - name: 디스크와 메모리 여유
        run: |
          df -h / | tail -1
          free -h | head -2

      - name: 사내망 접근 확인 (self-hosted의 존재 이유)
        run: curl -sS -m 5 -o /dev/null -w "harbor: %{http_code}\n" https://harbor.corp.local

      - name: 소스 체크아웃
        uses: actions/checkout@v4

      - name: 작업 후 정리 (러너는 재사용되므로 중요)
        if: always()
        run: echo "cleanup done"

#!/usr/bin/env bash
# ephemeral 러너 루프: 잡 1개 실행 → 등록 해제 → 재등록 → 반복
# (실무에서는 ARC나 오토스케일링 그룹이 이 일을 대신합니다)
set -euo pipefail
OWNER="my-company"; REPO="web-service"
GH_PAT="${GH_PAT:?PAT 환경변수 필요}"

while true; do
  # 1) 등록 토큰을 API로 새로 발급 (하드코딩 금지)
  TOKEN=$(curl -sS -X POST \
    -H "Authorization: Bearer $GH_PAT" \
    -H "Accept: application/vnd.github+json" \
    "https://api.github.com/repos/$OWNER/$REPO/actions/runners/registration-token" \
    | jq -r .token)

  # 2) 일회용으로 등록
  ./config.sh --url "https://github.com/$OWNER/$REPO" \
              --token "$TOKEN" \
              --name "eph-$(hostname)-$RANDOM" \
              --labels self-hosted,Linux,X64,ephemeral \
              --ephemeral --unattended --replace

  # 3) 잡 1개 실행 후 스스로 종료됨
  ./run.sh || true

  # 4) 워크스페이스 청소 후 다음 루프
  rm -rf _work/* || true
  sleep 3
done

컨테이너 · Kubernetes(ARC) 러너

    
러너를 손으로 늘리는 단계를 졸업하는 방법

  


  

    VM에 러너를 하나씩 설치하는 방식은 3~4대까지는 괜찮지만, 그 이상이면 버전 관리·오염·스케일 문제가 터집니다.
    해답은 러너를 일회용 컨테이너로 만들고 오토스케일링하는 것입니다.

$ helm install arc-runner-set \
    --namespace arc-runners --create-namespace \
    --set githubConfigUrl="https://github.com/my-company" \
    --set githubConfigSecret.github_token="$GH_PAT" \

# 5) 문제 시 리스너 로그부터 확인

① 디스크 관리 — 장애 원인 1위

  

    self-hosted 러너는 정리를 안 해줍니다. _work의 체크아웃 사본, Docker 이미지·빌드 캐시,
    _diag 로그가 계속 쌓여 몇 주 만에 디스크를 채웁니다. 처음부터 정리 잡을 걸어두세요.
  

  

    

      
      
    

    
#!/usr/bin/env bash
# /opt/actions-runner/cleanup.sh — cron으로 매일 새벽 실행
# crontab: 0 4 * * * /opt/actions-runner/cleanup.sh >> /var/log/runner-clean.log 2>&1
set -uo pipefail
RUNNER_DIR=/opt/actions-runner

echo "=== $(date '+%F %T') 정리 시작 ==="
df -h /opt | tail -1

# 1) 잡 실행 중이면 건너뛴다 (실행 중 삭제는 빌드를 깨뜨림)
if pgrep -f "Runner.Worker" >/dev/null; then
  echo "잡 실행 중 → 정리 연기"; exit 0
fi

# 2) 7일 이상 접근 없는 워크스페이스 삭제
find "$RUNNER_DIR/_work" -maxdepth 1 -mindepth 1 -type d \
     ! -name '_temp' ! -name '_tool' ! -name '_actions' \
     -atime +7 -exec rm -rf {} +

# 3) 임시 디렉터리 비우기
rm -rf "$RUNNER_DIR/_work/_temp"/* 2>/dev/null

# 4) 진단 로그는 14일치만 보관
find "$RUNNER_DIR/_diag" -name '*.log' -mtime +14 -delete

# 5) Docker 정리 — 사용 중 이미지는 남기고 dangling만 제거
if command -v docker >/dev/null; then
  docker container prune -f --filter "until=24h"
  docker image prune -f --filter "until=168h"       # 7일
  docker builder prune -f --filter "until=168h" --keep-storage 20GB
  docker volume prune -f
fi

echo "=== 정리 후 ==="; df -h /opt | tail -1

    
# 잡 자체에 정리 스텝을 넣는 방식 (권장 조합)
jobs:
  build:
    runs-on: [self-hosted, Linux, docker]
    steps:
      # 시작 전 이전 잡 잔여물 제거 (clean: true가 기본이지만 강제)
      - uses: actions/checkout@v4
        with:
          clean: true
          fetch-depth: 1          # 얕은 클론으로 디스크·시간 절약

      - name: 디스크 여유 사전 확인 (부족하면 즉시 실패)
        run: |
          FREE=$(df -BG --output=avail . | tail -1 | tr -dc '0-9')
          echo "여유: ${FREE}GB"
          [ "$FREE" -ge 10 ] || { echo "::error::디스크 부족"; exit 1; }

      - run: docker build -t app:${{ github.sha }} .

      # 성공/실패 무관하게 항상 정리
      - name: 작업 후 정리
        if: always()
        run: |
          docker image rm app:${{ github.sha }} || true
          docker builder prune -f --filter "until=24h" || true
