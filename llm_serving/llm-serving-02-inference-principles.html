LLM 추론의 원리
플랫폼 엔지니어 관점

1편에서 “Prefill은 연산, Decode는 메모리 대역폭”이라고 외웠습니다. 이번 편은 그 문장이 왜 참인지를 숫자로 확인합니다. 토큰 하나가 만들어질 때 GPU가 실제로 무엇을 읽고 계산하는지, KV 캐시가 왜 메모리를 잡아먹는지, 그리고 vLLM이 왜 연속 배칭과 PagedAttention으로 판을 바꿨는지까지. 수식은 곱셈과 나눗셈만 씁니다.

01시작하기 전에

이 편을 마치면 서빙 엔진의 설정값과 로그, 지표가 “왜 그렇게 생겼는지” 읽히기 시작합니다.

플랫폼 엔지니어가 모델 내부를 알아야 하는 이유는 단순합니다. GPU 메모리를 얼마나 잡을지, 동시 요청을 몇 개까지 받을지, 어떤 GPU를 몇 장 살지가 모두 모델 구조에서 계산되기 때문입니다. 이 계산을 못 하면 용량 계획은 감이 되고, 장애 분석은 추측이 됩니다.

학습 목표

  1. 토큰·토크나이저·채팅 템플릿이 무엇이며, 한국어 서비스에서 토큰 수가 비용과 용량에 어떻게 영향을 주는지 설명할 수 있다.
  2. 트랜스포머의 구성 요소(임베딩·어텐션·MLP·출력층)가 각각 GPU 메모리와 연산의 어디를 차지하는지 그릴 수 있다.
  3. Prefill이 연산 집약적이고 Decode가 메모리 대역폭 집약적인 이유를 산술 강도와 루프라인으로 설명할 수 있다.
  4. 모델 설정값(층 수·KV 헤드 수·헤드 차원)으로 토큰당 KV 캐시 크기를 손으로 계산하고, 컨텍스트 길이·동시 요청 수에 따른 총 메모리를 산출할 수 있다.
  5. 정적 → 동적 → 연속 배칭의 차이와 PagedAttention이 해결한 문제를 설명하고, vLLM 로그의 KV 캐시 관련 줄을 해석할 수 있다.
  6. “메모리 → 동시 요청 수 → 처리량 → 토큰당 비용”으로 이어지는 연결을 숫자로 보여 줄 수 있다.
이 편의 비유: 손님이 많은 주방의 요리사

요리사(GPU 연산 장치)는 손이 엄청나게 빠르지만, 재료는 창고(GPU 메모리)에서 카트(메모리 대역폭)로 날라 와야 합니다. Prefill은 단체 주문서를 받아 재료 한 번 가져와서 수십 접시를 동시에 손질하는 일입니다. 손이 바쁩니다. Decode는 접시마다 한 숟갈씩 더 얹을 때마다 창고에서 재료 전체를 다시 가져오는 일입니다. 손은 놀고 카트가 바쁩니다. KV 캐시는 손님별로 “지금까지 무엇을 냈는지” 적어 둔 메모 패드인데, 손님이 많고 코스가 길수록 메모 패드가 주방 선반을 다 차지합니다.

02토큰과 토크나이저

과금, 속도, 컨텍스트 한도, 메모리 모두 “글자”가 아니라 “토큰”으로 셉니다.

LLM은 글자를 직접 보지 않습니다. 토크나이저가 문장을 미리 정해 둔 조각(토큰) 목록에서 찾아 정수 ID 배열로 바꿉니다. 대부분의 최신 모델은 BPE(Byte Pair Encoding) 계열을 씁니다. 자주 나오는 문자열은 하나의 토큰으로, 드문 문자열은 여러 조각이나 바이트 단위로 쪼갭니다.

예시 (실제 분할은 토크나이저마다 다름) Kubernetes에서 GPU를 나눠 쓰는 방법

플랫폼 엔지니어가 챙길 토큰 사실 다섯 가지

  1. 언어마다 토큰 효율이 다르다. 영어는 대략 단어 하나가 1~1.5토큰입니다. 한국어는 토크나이저의 어휘(vocab)에 한국어가 얼마나 들어 있느냐에 따라 같은 의미에 토큰이 더 많이 들 수 있습니다. 최근 대형 모델들은 어휘가 10만~20만 개 이상으로 커져 한국어 효율이 많이 좋아졌지만, 모델마다 차이가 큽니다. 같은 문서를 모델별로 직접 세어 보는 것이 유일하게 믿을 수 있는 방법입니다(실습 2-1).
  2. 토큰 수는 모델(토크나이저)에 묶여 있다. 같은 문장이 Qwen에서 120토큰, 다른 모델에서 160토큰일 수 있습니다. 모델을 바꾸면 비용·지연·컨텍스트 여유가 함께 바뀝니다. 용량 계획과 차지백은 반드시 “어느 토크나이저 기준인지” 적어야 합니다.
  3. 채팅 템플릿이 토큰을 더한다. API에 보내는 messages 배열은 모델 안으로 들어가기 전에 채팅 템플릿으로 하나의 긴 문자열이 됩니다. 역할 표시, 특수 토큰, 시스템 프롬프트, 도구(tool) 정의가 모두 입력 토큰입니다. 도구를 수십 개 정의한 에이전트는 사용자 질문이 짧아도 입력이 수천 토큰입니다.
  4. 잘못된 템플릿은 조용한 장애다. 템플릿이 모델과 맞지 않으면 에러 없이 이상한 답이 나오거나 툴 콜링이 깨집니다. 엔진은 보통 모델 저장소의 템플릿을 쓰지만, 직접 바꿀 때는 회귀 테스트가 필요합니다.
  5. 출력 토큰은 입력 토큰보다 비싸다. 상용 API의 출력 단가가 입력보다 몇 배 높은 이유는 4장에서 볼 Decode의 비용 구조 때문입니다. 셀프호스팅에서도 출력 토큰 하나가 GPU 시간을 훨씬 많이 씁니다.
어휘 크기는 메모리에도 영향

토크나이저 어휘가 클수록 모델 입구의 임베딩 표와 출구의 출력층(LM head)이 커집니다. 어휘 15만 개 × 숨은 차원 4,096이면 표 하나에 약 6억 개 파라미터입니다. 작은 모델에서는 이 부분이 전체 파라미터의 상당 비율을 차지하기도 합니다(일부 모델은 입·출력 표를 공유해 줄임).

03트랜스포머 해부도

학습 이론 없이, “파라미터가 어디 있고 연산이 어디서 일어나나”만 봅니다.

디코더 전용 트랜스포머(오늘날 거의 모든 LLM)는 같은 모양의 블록을 수십 번 쌓은 구조입니다. 토큰 하나가 통과하는 경로는 다음과 같습니다.

토큰 ID정수 하나

›

블록 하나 안에서 일어나는 일

어텐션 (Attention)

현재 토큰이 “앞의 토큰들 중 무엇을 참고할지” 정하는 부분입니다. 토큰마다 세 가지 벡터를 만듭니다: Q(Query, 내가 찾는 것), K(Key, 나를 찾을 때 쓰는 꼬리표), V(Value, 내가 줄 내용). 현재 토큰의 Q를 앞 토큰 전부의 K와 비교해 가중치를 정하고, 그 가중치로 V를 섞습니다. 앞 토큰들의 K와 V는 바뀌지 않으므로 저장해 두고 재사용하는데, 이것이 KV 캐시입니다.

MLP (피드포워드)

토큰마다 독립적으로 적용되는 큰 행렬 곱 두세 개입니다. 파라미터의 대부분(보통 3분의 2 안팎)이 여기에 있습니다. MoE 모델은 이 MLP를 여러 개의 “전문가”로 나눠 두고, 토큰마다 일부 전문가만 계산합니다. 그래서 전체 파라미터는 크지만 토큰당 계산량은 작습니다.

플랫폼 엔지니어용 핵심 숫자 두 개

① 가중치 메모리 ≈ 파라미터 수 × 정밀도 바이트 (8B 모델, BF16 2바이트 → 약 16GB) ② 토큰당 연산량 ≈ 2 × (토큰당 활성) 파라미터 수 FLOPs (8B 모델 → 토큰 하나에 약 160억 번의 곱셈·덧셈)

②의 “2”는 곱셈 한 번과 덧셈 한 번입니다. 어텐션 점수 계산은 컨텍스트 길이에 비례해 추가되는데, 컨텍스트가 아주 길지 않으면 ②가 지배적입니다. 이 두 숫자만으로 다음 장의 Prefill·Decode 차이를 거의 다 설명할 수 있습니다.

04Prefill과 Decode

같은 모델, 같은 GPU인데 왜 두 단계의 성격이 정반대일까.

요청이 들어오면 엔진은 두 단계를 거칩니다. 핵심 차이는 한 번에 몇 개의 토큰을 계산하느냐입니다.

관점Prefill (입력 처리)Decode (출력 생성)

숫자로 확인하기: Qwen3-8B, H100 한 장

8.2B 파라미터 모델을 BF16(2바이트)으로 올렸다고 합시다. 가중치는 약 16.4GB입니다.

[Decode 한 스텝, 동시 요청 1개] 읽어야 할 데이터 ≈ 가중치 16.4 GB (+ 짧은 KV 캐시, 무시) H100 대역폭 ≈ 3.35 TB/s 최소 시간 ≈ 16.4 / 3,350 ≈ 4.9 ms → 이론 상한 약 200 토큰/s 실제로는 대역폭의 60~80%만 쓰므로 → 대략 130~160 토큰/s [Prefill, 입력 2,000 토큰] 연산량 ≈ 2 × 8.2e9 × 2,000 ≈ 3.3e13 FLOPs H100 BF16 연산 ≈ 989 TFLOPS (밀집 기준), 실효 50% 가정 → 약 495 TFLOPS 시간 ≈ 3.3e13 / 4.95e14 ≈ 66 ms

입력 2,000토큰을 처리하는 데 약 66ms, 출력 토큰 하나를 만드는 데 약 5~7ms입니다. 입력 2,000개를 처리하는 시간에 출력은 10여 개밖에 못 만듭니다. 입력 토큰 하나는 출력 토큰 하나보다 GPU 시간을 수십~백 배 적게 씁니다. 상용 API가 출력 토큰을 훨씬 비싸게 받는 이유, 그리고 셀프호스팅에서 “출력 길이 제한(max_tokens)”이 비용 통제 수단이 되는 이유가 여기에 있습니다.

두 단계가 한 GPU에서 섞일 때 생기는 일

한 GPU에서 여러 요청을 처리하면 Prefill과 Decode가 섞입니다. 누군가 3만 토큰짜리 문서를 넣으면 그 Prefill이 수백 ms 동안 GPU 연산을 독차지하고, 그동안 다른 요청들의 Decode가 멈칫합니다. 사용자에게는 “글이 잘 나오다가 갑자기 멈춤”으로 보입니다. 해결책은 두 갈래입니다: 긴 Prefill을 잘게 쪼개 Decode 사이사이에 끼워 넣는 Chunked Prefill(14편), 아예 Prefill과 Decode를 다른 GPU에서 하는 분리 서빙(10편).

05루프라인으로 보는 병목

“연산이 병목인가, 메모리가 병목인가”를 판정하는 단 하나의 그림.

산술 강도(Arithmetic Intensity)는 메모리에서 1바이트를 읽을 때마다 몇 번 계산하느냐입니다. GPU마다 “연산 성능 ÷ 메모리 대역폭”으로 정해지는 경계점(ridge point)이 있어서, 작업의 산술 강도가 경계점보다 낮으면 메모리가 병목, 높으면 연산이 병목입니다.

경계점 = 연산 성능 ÷ 메모리 대역폭 H100 (BF16 밀집) 989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/byte A100 (BF16) 312 TFLOPS ÷ 2.04 TB/s ≈ 153 FLOP/byte L4 (BF16 밀집) 121 TFLOPS ÷ 0.30 TB/s ≈ 403 FLOP/byte Decode, 배치 1, BF16 가중치: 파라미터 1개(2바이트)를 읽어 2 FLOPs 계산 → 산술 강도 ≈ 1 FLOP/byte → 경계점 295보다 훨씬 낮음 → 극단적으로 메모리 병목 (연산 장치의 99%가 놂) Decode, 배치 b: 가중치를 한 번 읽어 b개 시퀀스에 사용 → 강도 ≈ b Prefill, 입력 n: 가중치를 한 번 읽어 n개 토큰에 사용 → 강도 ≈ n (수천)

그래서 Decode는 배치를 키울수록 GPU를 효율적으로 씁니다. 그런데 함정이 있습니다. 가중치는 배치 전체가 공유하지만 KV 캐시는 시퀀스마다 따로입니다. 컨텍스트가 길면 배치를 키워도 읽어야 할 KV 캐시가 같이 늘어나 산술 강도가 잘 오르지 않습니다. 아래 계산기로 직접 확인해 보세요.

꼭 해 볼 실험:

  1. 컨텍스트를 512로 짧게 두고 배치를 1 → 256으로 올려 보세요. 전체 처리량은 수십 배 오르는데 요청당 속도는 처음엔 거의 그대로이다가 어느 순간부터 떨어집니다. 그 꺾이는 지점이 “공짜 배치”가 끝나는 곳입니다. 컨텍스트를 4K 이상으로 올리면 요청당 속도가 처음부터 서서히 떨어지는데, 배치 안 요청 수만큼 KV 읽기가 늘기 때문입니다.
  2. 컨텍스트를 512 → 128K로 늘려 보세요. 같은 배치에서도 KV 읽기가 가중치 읽기를 압도하면서 처리량이 무너집니다. 긴 컨텍스트 서비스가 비싼 이유입니다.
  3. MoE 모델을 고르면 연산은 작지만 가중치 전체(30.5B)는 여전히 메모리에 있어야 합니다. 배치가 작을 때는 “활성 파라미터만큼만 읽는” 이점이 있지만, 배치가 커지면 서로 다른 전문가가 골고루 불려 결국 대부분의 가중치를 읽게 됩니다. 이 계산기는 이를 단순화해 활성 파라미터 비율만큼만 읽는다고 가정하므로, 큰 배치에서는 실제보다 낙관적입니다.
  4. “필요 메모리”가 GPU 용량을 넘으면 그 배치는 실제로는 불가능합니다. 처리량을 결정하는 것이 결국 메모리 용량이라는 6~7장의 결론으로 이어집니다.

06KV 캐시의 정체

가중치는 모델마다 고정이지만, KV 캐시는 트래픽에 따라 늘어납니다. 용량 계획의 진짜 변수는 이쪽입니다.

무엇을 저장하나

3장에서 본 대로, 어텐션은 앞 토큰들의 K와 V를 계속 참조합니다. 이를 매번 다시 계산하면 Decode 한 스텝에 지금까지의 모든 토큰을 다시 Prefill하는 셈이 됩니다. 그래서 엔진은 모든 층, 모든 KV 헤드에 대해 토큰마다 K 벡터와 V 벡터를 GPU 메모리에 보관합니다.

08배칭의 진화

5장에서 “배치를 키우면 공짜로 처리량이 오른다”를 봤습니다. 문제는 요청들이 제각각 다른 시각에 와서 다른 길이로 끝난다는 것입니다.

세 세대의 배칭

정적 배칭

요청이 정해진 개수만큼 모일 때까지 기다렸다가 한 묶음으로 실행하고, 묶음 안에서 가장 긴 요청이 끝날 때까지 다음 묶음을 받지 않습니다. 짧게 끝난 자리는 빈 칸(패딩)으로 놉니다. 이미지 분류처럼 입력·출력 크기가 일정한 모델에서 쓰던 방식입니다.

동적 배칭

“개수가 차거나 일정 시간이 지나면” 묶음을 출발시킵니다. 먼저 온 요청의 대기 시간은 줄지만, 일단 출발하면 여전히 가장 긴 요청이 끝날 때까지 묶음이 유지됩니다. 기존 모델 서버(Triton 등)의 일반 기능입니다.

연속 배칭

토큰 한 스텝마다 배치를 다시 짭니다. 끝난 요청은 즉시 빠지고 기다리던 요청이 그 자리에 바로 들어옵니다. 2022년 Orca 논문이 “반복 단위 스케줄링”으로 제안했고, 지금은 vLLM·SGLang·TensorRT-LLM 등 모든 LLM 엔진의 기본입니다.

연속 배칭이 만든 새로운 문제들

  • Prefill이 끼어드는 순간: 빈 슬롯에 새 요청이 들어오면 그 요청의 Prefill을 해야 합니다. 긴 Prefill이 Decode 중인 다른 요청들을 멈칫하게 만드는 문제를 Chunked Prefill이 완화합니다. 한 스텝에 처리할 토큰 예산(예: vLLM의 --max-num-batched-tokens)을 정하고, 그 안에서 Decode 토큰을 먼저 채운 뒤 남는 만큼만 Prefill 조각을 넣는 방식입니다.
  • 메모리가 새로운 상한: 슬롯 수를 결정하는 것은 이제 연산이 아니라 KV 캐시 공간입니다. 요청마다 최종 길이를 모르는 상태에서 메모리를 어떻게 나눠 줄 것인가가 다음 장 PagedAttention의 주제입니다.
  • 스케줄링 정책: 대기열에서 누구를 먼저 넣을지(FIFO, 우선순위), 메모리가 모자라면 누구를 잠시 빼낼지(선점)가 지연 분포를 좌우합니다(14편).

09PagedAttention

운영체제가 수십 년 전에 해결한 문제를 KV 캐시에 그대로 적용한 아이디어. vLLM의 출발점입니다.

연속 배칭 이전의 서빙 시스템은 요청 하나가 들어오면 최대 길이만큼의 KV 공간을 연속으로 미리 잡아 두었습니다. 요청이 실제로 몇 토큰을 쓸지 모르기 때문입니다. 결과는 세 가지 낭비였습니다: 끝내 쓰지 않은 예약 공간, 요청마다 크기가 달라 생기는 틈(외부 단편화), 같은 내용을 요청마다 복사해 두는 중복. 2023년 vLLM 논문(SOSP 2023)은 기존 시스템에서 KV 메모리의 상당 부분이 실제 토큰 저장에 쓰이지 못하고 낭비된다는 점을 측정해 보였습니다.

해결책: 페이지로 나누기

  • KV 캐시 풀을 같은 크기의 블록(vLLM GPU 기본값은 블록당 16토큰)으로 나눕니다.
  • 요청은 토큰이 늘어날 때마다 필요한 만큼만 블록을 하나씩 받습니다. 블록들은 메모리 여기저기 흩어져 있어도 됩니다.
  • 요청마다 블록 테이블(논리 순서 → 물리 블록 위치)을 두고, 어텐션 커널이 이 표를 따라 읽습니다. 운영체제의 페이지 테이블과 같은 원리입니다.
  • 낭비는 요청마다 마지막 블록의 빈 자리뿐입니다(평균 블록 절반).

시스템 프롬프트처럼 앞부분이 같은 요청들은 같은 물리 블록을 가리키기만 하면 됩니다. 내용이 갈라지는 지점부터만 새 블록을 받습니다(Copy-on-Write). 1편에서 본 “같은 앞부분 재사용”의 실체입니다(15편).

선점 (Preemption)

KV 풀이 가득 차면 엔진은 일부 요청의 블록을 회수해 다른 요청을 계속 진행시킵니다. 회수된 요청은 나중에 다시 계산(recompute)하거나, 버전에 따라 CPU 메모리로 옮겼다 되돌립니다. 지연이 튀는 원인이므로 선점 횟수는 반드시 모니터링할 지표입니다(21편).

finish_reason은 공짜 품질 지표

11메모리 → 동시성 → 비용

이 편의 모든 내용을 한 줄로 연결하면: KV 공간이 동시 요청 수를 정하고, 동시 요청 수가 처리량을 정하고, 처리량이 토큰당 비용을 정합니다.

Qwen3-32B급 모델을 요청당 8K 컨텍스트로 서빙한다고 하고, 구성만 바꿔 봅시다. 아래 표는 5장과 7장의 계산기와 같은 공식으로 페이지를 열 때 계산한 값입니다. GPU 시간당 비용은 예시입니다.

가정: 메모리 활용률 0.9, GPU당 예비 3GB, 모든 요청이 8K까지 찬다고 보는 보수적 동시성, Decode만 고려(Prefill 시간 제외), 실효 대역폭 75%·연산 60%. 실제 처리량은 이보다 낮게 나오는 것이 보통이며 19편에서 실측합니다. 비용은 H100 $3.5/h, H200 $5/h, 2×H100은 $7/h로 가정한 예시입니다.

표에서 읽어야 할 것

  1. BF16으로 H100 한 장에 올리면 “들어가기만” 합니다. KV 공간이 거의 없어 동시 요청이 한두 개뿐이고, 토큰당 비용이 가장 비쌉니다. “모델이 GPU에 들어간다”와 “서비스할 수 있다”는 다른 말입니다.
  2. 가중치 FP8만으로 동시성이 10배 이상 늘고 비용이 크게 내려갑니다. 양자화의 가장 큰 효과는 속도보다 KV 공간 확보인 경우가 많습니다.
  3. KV까지 FP8로 하면 동시성이 다시 두 배 가까이 됩니다.
  4. H200은 같은 BF16이어도 메모리 덕분에 동시성이 크게 늘어납니다. GPU 단가가 높아도 토큰당 비용은 낮을 수 있습니다. GPU는 시간당 가격이 아니라 토큰당 가격으로 비교해야 합니다(3·23편).

"""같은 의미의 한국어·영어 문장을 두 토크나이저로 세고, 채팅 템플릿이 붙이는 토큰을 확인한다."""
from transformers import AutoTokenizer

TOKENIZERS = ["Qwen/Qwen3-0.6B", "openai/gpt-oss-20b"]
SAMPLES = {
    "ko": "쿠버네티스 클러스터에서 여러 팀이 GPU를 나눠 쓸 때는 격리와 쿼터를 먼저 설계해야 합니다.",
    "en": "When multiple teams share GPUs in a Kubernetes cluster, isolation and quotas must be designed first.",
}

for name in TOKENIZERS:
    tok = AutoTokenizer.from_pretrained(name)
    print(f"\n=== {name}  (어휘 크기 {len(tok):,}) ===")
    for lang, text in SAMPLES.items():
        ids = tok.encode(text, add_special_tokens=False)
        pieces = [tok.decode([i]) for i in ids]
        print(f"[{lang}] 글자 {len(text):3d} → 토큰 {len(ids):3d}  (글자당 {len(ids)/len(text):.2f})")
        print("      ", " | ".join(pieces[:24]), "..." if len(pieces) > 24 else "")

    msgs = [
        {"role": "system", "content": "너는 사내 인프라 도우미다."},
        {"role": "user", "content": SAMPLES["ko"]},
    ]
    text = tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
    n_tpl = len(tok(text, add_special_tokens=False)["input_ids"])
    n_raw = sum(len(tok.encode(m["content"], add_special_tokens=False)) for m in msgs)
    print(f"[template] 내용 토큰 {n_raw} → 템플릿 적용 후 {n_tpl} (+{n_tpl - n_raw})")
    print(text)

실습 2-2 · config.json으로 KV 캐시 손 계산

python · kv_from_config.py
"""모델 config.json을 읽어 토큰당 KV 캐시 크기와 컨텍스트별 요청당 KV를 계산한다.
사용: python kv_from_config.py [모델ID 또는 로컬 config.json 경로 ...]"""
import json, sys
from huggingface_hub import hf_hub_download

DEFAULT = ["Qwen/Qwen3-0.6B", "Qwen/Qwen3-8B", "Qwen/Qwen3-32B",
           "Qwen/Qwen3-30B-A3B", "deepseek-ai/DeepSeek-V3", "openai/gpt-oss-20b"]
CONTEXTS = [4096, 32768, 131072]
KV_BYTES = 2  # BF16. FP8 KV면 1

def load(m):
    path = m if m.endswith(".json") else hf_hub_download(m, "config.json")
    with open(path) as f:
        c = json.load(f)
    return c.get("text_config", c)  # 멀티모달 모델은 text_config 안에 있음

def analyze(c):
    L = c["num_hidden_layers"]
    if c.get("kv_lora_rank"):  # MLA: 잠재 벡터 하나(+RoPE)만 저장, K/V 구분 없음
        per_layer = (c["kv_lora_rank"] + c.get("qk_rope_head_dim", 0)) * KV_BYTES
        return "MLA", per_layer, L, 0, None
    heads = c["num_attention_heads"]
    kvh = c.get("num_key_value_heads") or heads
    hd = c.get("head_dim") or c["hidden_size"] // heads
    kind = "MHA" if kvh == heads else ("MQA" if kvh == 1 else f"GQA {heads}:{kvh}")
    per_layer = 2 * kvh * hd * KV_BYTES
    types = c.get("layer_types") or []
    sliding = sum(1 for t in types if "sliding" in t)
    return kind, per_layer, L - sliding, sliding, c.get("sliding_window")

def kv_for(ctx, per_layer, full, sliding, window):
    win = min(ctx, window) if (sliding and window) else ctx
    return per_layer * (full * ctx + sliding * win)

def human(b):
    for u in ["B", "KiB", "MiB", "GiB"]:
        if b < 1024: return f"{b:,.1f} {u}"
        b /= 1024
    return f"{b:,.1f} TiB"

for m in (sys.argv[1:] or DEFAULT):
    try:
        kind, per_layer, full, sliding, window = analyze(load(m))
    except Exception as e:
        print(f"{m}: 읽기 실패 ({e})"); continue
    per_tok = per_layer * (full + sliding)
    note = f", 슬라이딩 {sliding}층(window={window})" if sliding else ""
    print(f"\n{m}  [{kind}, 층 {full + sliding}{note}]")
    print(f"  토큰당 KV (모든 층 기준): {human(per_tok)}")
    for ctx in CONTEXTS:
        print(f"  {ctx:>7,} 토큰 요청 1개: {human(kv_for(ctx, per_layer, full, sliding, window))}")

확인할 것: 6장 표의 Qwen 계열·DeepSeek 값과 일치하는가. gpt-oss처럼 슬라이딩 윈도우 층이 섞인 모델은 컨텍스트가 길어져도 KV가 덜 늘어나는가. 로컬에 받아 둔 다른 모델이 있다면 그 모델 디렉터리의 config.json 경로를 인자로 넣어 계산해 보세요(일부 모델은 설정 키 이름이 달라 스크립트 수정이 필요할 수 있음).

"""A: 긴 입력·짧은 출력 vs 짧은 입력·긴 출력에서 TTFT·TPOT 비교
   B: 동시 요청 수를 늘리며 GPU 전체 처리량과 요청당 속도의 변화 측정"""
import asyncio, time, statistics
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY", timeout=300)
MODEL = "Qwen/Qwen3-0.6B"
EXTRA = {"chat_template_kwargs": {"enable_thinking": False}, "ignore_eos": True}  # 출력 길이를 정확히 고정
LONG = "쿠버네티스 GPU 스케줄링과 쿼터 정책에 대한 회의 메모입니다. " * 150  # 대략 2~3천 토큰

async def one(prompt, max_tokens):
    t0 = time.perf_counter(); first = None; n = 0
    stream = await client.chat.completions.create(
        model=MODEL, messages=[{"role": "user", "content": prompt}],
        max_tokens=max_tokens, stream=True, extra_body=EXTRA)
    async for ev in stream:
        if ev.choices and ev.choices[0].delta.content:
            now = time.perf_counter(); first = first or now; n += 1
    end = time.perf_counter()
    return (first - t0), (end - first) / max(n - 1, 1), n, end - t0

async def part_a():
    print("\n[A] 단계별 시간 (각 5회 중앙값)")
    for label, prompt, mt in [("긴 입력 · 출력 16", LONG, 16), ("짧은 입력 · 출력 512", "안녕?", 512)]:
        rs = [await one(prompt, mt) for _ in range(5)]
        ttft = statistics.median(r[0] for r in rs) * 1000
        tpot = statistics.median(r[1] for r in rs) * 1000
        e2e = statistics.median(r[3] for r in rs)
        print(f"  {label:<18} TTFT {ttft:7.1f} ms  TPOT {tpot:6.2f} ms  전체 {e2e:6.2f} s")

async def part_b():
    print("\n[B] 동시성 스윕 (출력 256 토큰 고정)")
    print(f"  {'동시성':>6} {'전체 토큰/s':>12} {'요청당 토큰/s':>14} {'TTFT p50(ms)':>13}")
    for c in [1, 2, 4, 8, 16, 32, 64]:
        t0 = time.perf_counter()
        rs = await asyncio.gather(*[one("GPU 공유 방식 세 가지를 설명해 줘.", 256) for _ in range(c)])
        wall = time.perf_counter() - t0
        total = sum(r[2] for r in rs)
        per_req = statistics.median(1 / r[1] for r in rs if r[1] > 0)
        ttft = statistics.median(r[0] for r in rs) * 1000
        print(f"  {c:>6} {total / wall:>12.0f} {per_req:>14.1f} {ttft:>13.1f}")

async def main():
    await one("워밍업", 8)
    await part_a()
    await part_b()

asyncio.run(main())

17정리와 체크리스트

핵심 여섯 문장.

  1. 모든 것은 토큰으로 센다. 토큰 수는 토크나이저에 묶여 있고, 채팅 템플릿과 도구 정의도 입력 토큰이다.
  2. 가중치 ≈ 파라미터 × 정밀도 바이트, 토큰당 연산 ≈ 2 × 활성 파라미터. 이 두 숫자로 대부분의 첫 산수를 한다.
  3. Prefill은 가중치를 수천 번 재사용해 연산이 병목, Decode는 거의 재사용하지 못해 대역폭이 병목. 판정 도구는 산술 강도와 GPU 경계점이다.
  4. 토큰당 KV = 2 × 층 × KV 헤드 × 헤드 차원 × 바이트. 컨텍스트와 동시성에 비례해 늘어나며, GQA·MLA·슬라이딩 윈도우·FP8 KV가 이를 줄인다.
  5. 연속 배칭은 스텝마다 배치를 다시 짜고, PagedAttention은 KV를 블록 단위로 필요할 때만 나눠 준다. 둘이 합쳐져 동시성의 상한이 연산이 아니라 KV 공간이 되었다.
  6. KV 공간 → 동시 요청 수 → 처리량 → 토큰당 비용. GPU와 정밀도는 시간당 가격이 아니라 이 사슬의 끝에서 비교한다.
