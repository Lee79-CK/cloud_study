DNS·서비스 메시·멀티클러스터와 종합 트러블슈팅

네트워크 장애 신고의 절반은 “DNS가 이상하다”로 시작해 다른 곳에서 끝납니다. 이 편은 Level 1의 마지막 조각인 DNS(CoreDNS와 ndots), 서비스 메시, 멀티클러스터를 다룬 뒤, 4~9편 전체를 계층별 플레이북 하나로 묶습니다. 그리고 MTU, DNS, 정책, LB 헬스 체크, kube-proxy 동기화라는 다섯 가지 대표 장애를 시간 제한 안에 진단하는 훈련으로 Level 1을 마칩니다.

읽는 법과 목표

쉬운 말로 DNS는 회사 전화번호부, 서비스 메시는 모든 직원 전화기에 붙인 비서(암호화·기록·재시도를 대신 해 줌), 멀티클러스터는 여러 지사 전화망을 하나로 잇는 일입니다. 트러블슈팅 플레이북은 “전화가 안 된다”는 신고를 받았을 때, 번호부 → 교환대 → 회선 → 출입 통제 → 외부 회선 순으로 차례차례 확인하는 점검 순서표입니다.

이 편을 마치면 할 수 있는 것

  • Pod의 DNS 질의 경로와 ndots·검색 도메인이 만드는 질의 수를 계산하고, autopath·FQDN·NodeLocal DNSCache로 줄일 수 있습니다.
  • EKS·AKS·GKE·OpenShift·RKE2의 DNS 구성 차이를 알고 사내 DNS 전달(stub domain)을 설계할 수 있습니다.
  • 사이드카·ambient·노드 단위 프록시 메시를 비교하고, 고객 요구에 맞는 메시(또는 메시 없음)를 고를 수 있습니다.
  • MCS API, Cilium ClusterMesh, Submariner, Istio 멀티클러스터의 전제 조건과 차이를 설명할 수 있습니다.
  • 계층별 플레이북으로 네트워크 장애를 분해하고, 다섯 가지 대표 장애를 15분 안에 진단할 수 있습니다.
1

CoreDNS 심화와 ndots

질의가 지나는 길

  1. kubelet이 Pod의 /etc/resolv.conf를 만듭니다. 기본(dnsPolicy: ClusterFirst)이면 nameserver는 kube-dns Service의 ClusterIP, search는 <ns>.svc.cluster.local svc.cluster.local cluster.local에 노드의 검색 도메인이 더해지고, options ndots:5가 붙습니다.
  2. 질의는 6편의 Service 경로(kube-proxy 또는 eBPF)를 거쳐 CoreDNS Pod에 닿습니다. UDP이므로 conntrack 경쟁(6편 5초 사례)이 여기서 생깁니다.
  3. CoreDNS는 Corefile의 플러그인 순서대로 처리합니다. kubernetes 플러그인이 클러스터 이름을 답하고, 나머지는 forward로 노드의 상위 DNS(클라우드라면 VPC 리졸버)에 넘깁니다. cache가 결과를 재사용합니다.
대표 Corefile 읽기
.:53 {
    errors
    health { lameduck 5s }                       # 종료 전 5초 유예: 롤링 중 질의 유실 방지
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure                             # autopath를 쓰려면 pods verified 필요
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153                             # coredns_dns_requests_total 등 지표
    forward . /etc/resolv.conf { max_concurrent 1000 }
    cache 30
    loop                                         # 상위 DNS가 자기 자신을 가리키는 루프 감지
    reload
    loadbalance
}
corp.example:53 {                                # 사내 도메인은 사내 DNS로 (stub domain)
    forward . 10.10.0.53 10.10.0.54
    cache 60
}

ndots:5가 만드는 질의 폭증

ndots는 “이름에 점이 이 개수보다 적으면 검색 도메인부터 붙여 본다”는 규칙입니다. 클러스터 안의 web.shop 같은 짧은 이름을 쓰기 위한 값이지만, api.github.com(점 2개)처럼 외부 이름도 검색 도메인을 모두 시도한 뒤에야 원래 이름을 묻습니다. A와 AAAA를 함께 물으므로 질의 수는 두 배가 됩니다. 아래 계산기로 확인해 보세요.

Pod는 shop 네임스페이스에 있습니다. 예: web, web.shop, kubernetes.default, registry.k8s.io, 끝에 점을 붙인 api.github.com.

줄이는 방법원리대가
FQDN에 끝 점api.github.com.처럼 쓰면 검색 없이 한 번에앱 설정 변경 필요. 일부 라이브러리·TLS 검증과의 궁합 확인
Pod dnsConfig로 ndots 낮추기options: [{name: ndots, value: "2"}]짧은 클러스터 이름(web.shop)이 바로 외부로 나갈 수 있음. 이름 규칙 정비 필요
CoreDNS autopath서버가 검색 경로를 대신 따라가 첫 질의에 최종 답을 돌려줌pods verified가 필요해 CoreDNS가 Pod 정보를 감시(메모리 증가)
NodeLocal DNSCache노드마다 캐시를 두고 TCP로 상위 질의. conntrack 경쟁 회피DaemonSet 운영, NetworkPolicy에 링크 로컬 IP 허용(9편)
CoreDNS 확장노드·코어 수에 비례한 자동 확장, cache 증가근본 원인(질의 폭증)은 그대로
시니어 포인트: DNS 비용은 클러스터 밖에서도 청구된다 검색 도메인을 거치는 NXDOMAIN 질의는 상위 리졸버로도 나갑니다. 클라우드 VPC 리졸버에는 인터페이스당 초당 패킷 한도(예: AWS의 ENI당 1024 pps)가 있고, 일부 DNS 서비스는 질의 수로 과금됩니다. 대형 클러스터에서 “DNS가 가끔 실패한다”는 신고가 실제로는 이 한도에 걸린 경우가 많습니다. CoreDNS의 NXDOMAIN 비율을 대시보드에 두세요.

서비스 메시 선택

쉬운 말로 서비스 메시는 모든 직원 전화기에 비서를 붙이는 일입니다. 비서가 통화를 자동으로 암호화하고(mTLS), 누가 누구에게 걸었는지 기록하고(관측), 상대가 안 받으면 다시 걸어 줍니다(재시도). 비서를 직원마다 한 명씩 붙이는 방식(사이드카), 층마다 한 명이 그 층 전화를 다 처리하는 방식(ambient, 노드 단위 프록시)이 있습니다.

메시가 주는 것과 받는 것

  • 주는 것. Pod 신원 기반 상호 TLS(mTLS)와 인가, L7 트래픽 관리(재시도·타임아웃·가중치 분할·장애 주입), 서비스 간 지표·추적, 클러스터 내부(동서) 트래픽의 Gateway API 관리(GAMMA, 8편).
  • 받는 것. 프록시 자원(사이드카면 Pod 수만큼), 지연, 업그레이드 부담(컨트롤 플레인과 데이터 플레인 버전 정렬), 장애 지점 추가, 앱 시작 순서 문제(사이드카가 준비되기 전 앱이 나가려는 경우).
  • 메시 없이 되는 것. 네트워크 격리는 NetworkPolicy(9편), 외부 노출은 Gateway(8편), 암호화만 필요하면 CNI 수준 암호화(Cilium·Calico의 WireGuard)로도 됩니다. 메시는 “L7 정책과 서비스 신원”이 필요할 때 선택합니다.
선택지데이터 플레인강점주의
Istio 사이드카Pod마다 Envoy가장 성숙, 기능 최다, Pod 단위 세밀한 설정자원·지연, 사이드카 주입과 앱 시작 순서
Istio ambient노드마다 ztunnel(L4·mTLS) + 필요한 곳에만 waypoint(L7 Envoy)사이드카 없이 mTLS, L7은 선택적. 1.24에서 GA, 사이드카와 공존·이전 지원멀티클러스터는 아직 성숙 중(OSSM 3.4 기준 기술 미리보기). 노드 단위 장애 영향
LinkerdPod마다 Rust 마이크로 프록시가볍고 단순, 기본 mTLS안정판 배포는 Buoyant 경로 확인. 기능 범위가 Istio보다 좁음
Cilium Service MesheBPF + 노드마다 EnvoyCNI와 통합, 사이드카 없음, Hubble 관측Cilium CNI 전제. 상호 인증 기능의 성숙도 확인
벤더 관리형AKS Istio 애드온(리비전 기반 업그레이드), GKE Cloud Service Mesh, OpenShift Service Mesh 3(Istio 1.30 기반 3.4)업그레이드·지원 책임 분담지원 버전·기능이 업스트림보다 늦음. OSSM 2.6은 2026-06-30 종료
AWSApp Mesh는 2026-09-30 종료. EKS는 VPC Lattice(Gateway API 컨트롤러) 권장관리형 서비스 간 연결남은 App Mesh 사용처는 즉시 이전 대상

Multi-Cluster Services API

SIG Multicluster의 MCS API는 클러스터 간 서비스 공유를 표준화합니다. 공유하려는 Service와 같은 이름으로 ServiceExport를 만들면, 같은 클러스터셋의 다른 클러스터에 ServiceImport가 생기고 <svc>.<ns>.svc.clusterset.local로 부를 수 있습니다. GKE 멀티클러스터 서비스, Cilium ClusterMesh, Submariner Lighthouse, AWS Cloud Map 기반 컨트롤러가 이 API를 구현합니다. 핵심 전제는 네임스페이스 동일성입니다. 여러 클러스터의 같은 이름 네임스페이스는 같은 소유자의 것으로 간주되므로, 고객별 클러스터를 묶는 MSP 환경에서는 네임스페이스 이름 규칙이 곧 보안 경계입니다.

MCS API와 Cilium ClusterMesh 표기
# MCS API: 클러스터 A에서 내보내기
apiVersion: multicluster.x-k8s.io/v1alpha1
kind: ServiceExport
metadata: {name: api, namespace: shop}
# 다른 클러스터에서: curl http://api.shop.svc.clusterset.local:8080
---
# Cilium ClusterMesh: 같은 이름의 Service를 모든 클러스터에 두고 전역으로 표시
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: shop
  annotations:
    service.cilium.io/global: "true"
    service.cilium.io/affinity: "local"     # 로컬 엔드포인트 우선, 없으면 원격
spec:
  selector: {tier: api}
  ports: [{port: 8080}]
현장 메모: 멀티클러스터는 IP 계획에서 이미 결정된다 5편의 IP 계산기와 4편의 IPAM에서 클러스터마다 같은 10.244.0.0/16을 쓰면 평면 네트워크 방식(ClusterMesh)은 처음부터 불가능하고, 터널 방식도 Globalnet 같은 주소 변환이 필요합니다. 고객의 두 번째 클러스터를 만들 때 Pod·Service CIDR을 겹치지 않게 잡는 것이 나중의 멀티클러스터 선택지를 지켜 줍니다.

계층별 트러블슈팅 플레이북

6

다섯 가지 장애 런북

맨 위 진단 게임의 다섯 시나리오에 대한 정식 런북입니다. 각 런북은 15분 진단 순서, 흔한 원인, 조치, 재발 방지로 구성됩니다. 고객사 런북의 뼈대로 그대로 쓰세요.

런북 1. MTU: 큰 응답만 멈춘다

증상. 작은 요청은 정상, 큰 응답·파일 전송·TLS 핸드셰이크(인증서가 클 때)만 멈춤. 같은 노드 Pod끼리는 정상이고 다른 노드끼리만 실패.

15분 순서. ① 같은 노드 vs 다른 노드 비교(2분) → ② ping -M do -s로 통과 크기 찾기(3분) → ③ 노드 eth0·터널 장치·Pod eth0의 MTU 비교(3분) → ④ 노드 간 tcpdump로 ICMP “fragmentation needed” 유무(5분).

흔한 원인. 언더레이 MTU 축소(VPN·장비 교체), 오버레이 헤더 미반영(VXLAN 50바이트·Geneve·WireGuard 60바이트), 방화벽의 ICMP 차단으로 경로 MTU 발견 실패.

조치·예방. CNI MTU를 언더레이 − 캡슐화 헤더로 맞추고 Pod를 재시작(새 veth부터 적용). 네트워크 변경 체크리스트에 “클러스터 MTU 영향”을 넣고, 5편의 MTU 시각화를 근거로 씁니다.

런북 2. DNS: 간헐적 지연·실패

증상. 외부 호출이 가끔 정확히 5초 늦음, 또는 일부 이름만 실패. CoreDNS CPU 증가.

15분 순서. ① Pod resolv.conf(ndots·search) 확인(1분) → ② dig +search +stats로 질의 수·시간(3분) → ③ CoreDNS 지표(요청률·NXDOMAIN 비율·forward 지연)(4분) → ④ 노드 conntrack -S의 insert_failed(2분) → ⑤ 상위 리졸버 한도·오류(5분).

흔한 원인. ndots로 인한 검색 폭증, UDP conntrack 경쟁, CoreDNS 복제 부족, 상위 리졸버 pps 한도, 이그레스 정책의 DNS 누락(9편).

조치·예방. FQDN·ndots 조정·autopath, NodeLocal DNSCache, CoreDNS 자동 확장, NXDOMAIN 비율 경보.

런북 3. 정책: 특정 경로만 타임아웃

증상. 특정 출발지→목적지 조합만 타임아웃(거부가 아니라 응답 없음). 다른 경로는 정상. 최근 네임스페이스·정책·레이블 변경.

15분 순서. ① Pod IP 직접 호출로 Service 문제 배제(2분) → ② 양쪽 네임스페이스의 NetworkPolicy·CNP 목록(3분) → ③ 흐름 기록에서 DROPPED·Deny(3분) → ④ 셀렉터가 기대하는 레이블과 실제 레이블 비교(3분).

흔한 원인. 새 기본 거부, 레이블 누락·변경, AND·OR 실수, 이그레스 쪽 허용 누락(양쪽 모두 허용 필요), 강제가 막 켜진 정책(EKS).

조치·예방. 연결 행렬 시험을 배포 파이프라인에, Staged·감사 모드로 사전 확인, 네임스페이스 레이블을 정책 계약으로 문서화.

런북 4. LB 헬스 체크: 외부 사용자 일부만 실패

증상. 외부 요청 일부만 실패·지연. 클러스터 안에서는 정상. 최근 externalTrafficPolicy·LB 어노테이션·노드 풀 변경.

15분 순서. ① Service spec(ETP·healthCheckNodePort·loadBalancerClass)(2분) → ② LB의 대상별 상태(3분) → ③ 노드별 NodePort·헬스 포트 직접 호출(4분) → ④ LB 헬스 체크 설정(경로·포트·임계값)과 Pod 종료 설정(preStop·유예 시간)(4분).

흔한 원인. Local 정책인데 LB가 헬스 포트가 아닌 트래픽 포트를 검사, IP 대상의 등록·해제 지연, 준비 게이트 미사용, 보안 그룹·방화벽이 헬스 체크 대역 차단.

조치·예방. 7편 비교기로 구성 검증, 준비 게이트·preStop, 대상 상태 경보.

런북 5. kube-proxy 동기화: 배포 직후 수 초간 오류

증상. 배포·스케일 직후 짧은 503·연결 거부. EndpointSlice는 정상. 대형 클러스터.

15분 순서. ① EndpointSlice에 새 Pod가 ready인지(2분) → ② 문제 노드의 규칙에 새 Pod IP가 언제 나타나는지(4분) → ③ kubeproxy_sync_proxy_rules_duration_seconds와 마지막 동기화 시각(3분) → ④ 옛 Pod의 종료 순서(preStop 유무)(3분).

흔한 원인. iptables 모드의 규칙 수 증가로 동기화 수 초, minSyncPeriod 과대 설정, kube-proxy CPU 제한, preStop 없이 즉시 종료.

조치·예방. nftables 모드 또는 eBPF 대체(6편), preStop 지연, kube-proxy 자원 여유, 동기화 시간 경보.

실습 2. Istio ambient: 사이드카 없는 mTLS와 waypoint의 L7 인가

설치와 네임스페이스 편입
curl -L https://istio.io/downloadIstio | ISTIO_VERSION=1.30.1 sh -
export PATH=$PWD/istio-1.30.1/bin:$PATH
kubectl get crd gateways.gateway.networking.k8s.io                    # 8편에서 설치한 Gateway API CRD 확인
istioctl install --set profile=ambient --skip-confirmation
kubectl -n istio-system get pods                                       # istiod, istio-cni-node, ztunnel(DaemonSet)

kubectl apply -f shop-app.yaml                                         # 9편 3계층 앱(정책은 아직 적용하지 않음)
kubectl label ns shop istio.io/dataplane-mode=ambient
kubectl -n shop get pods                                               # 컨테이너 수 변화 없음(사이드카 없음)
istioctl ztunnel-config workloads | grep shop                          # PROTOCOL 열이 HBONE
kubectl -n shop exec deploy/frontend -c tool -- curl -s http://api.shop:8080/hostname; echo
kubectl -n istio-system logs ds/ztunnel --since=1m | grep -m3 'shop'    # mTLS로 전달된 연결 기록(신원 포함)
waypoint와 L7 인가 정책
istioctl waypoint apply -n shop --enroll-namespace --wait
kubectl -n shop get gateway                                            # GatewayClass istio-waypoint (8편 Gateway API의 메시 쪽 활용)
kubectl apply -f - <<'EOF'
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: {name: api-l7, namespace: shop}
spec:
  targetRefs: [{kind: Service, group: "", name: api}]
  action: ALLOW
  rules:
  - to: [{operation: {methods: ["GET"], paths: ["/hostname"]}}]
EOF
kubectl -n shop exec deploy/frontend -c tool -- curl -s -o /dev/null -w '%{http_code}\n' http://api.shop:8080/hostname   # 200
kubectl -n shop exec deploy/frontend -c tool -- curl -s -o /dev/null -w '%{http_code}\n' http://api.shop:8080/clientip   # 403
# 9편 Cilium L7 정책과 같은 결과를 메시로 얻었다. 출발지 신원까지 제한하려면 tier별 ServiceAccount를 만들고 principals 조건 추가
함정: 기본 거부 정책과 ambient ambient에서는 ztunnel끼리 HBONE(포트 15008)으로 통신합니다. 9편의 기본 거부 NetworkPolicy가 걸린 네임스페이스를 편입하면 목적지 Pod의 인그레스에 15008 허용이 필요합니다. 메시 도입 전 9편의 연결 행렬을 반드시 다시 돌리세요.

호스트에 Docker·kind·cilium CLI 필요

실습 4. 게임 데이: 다섯 장애를 심고 15분 안에 찾기

한 사람이 아래 스크립트로 장애 하나를 무작위로 심고, 다른 사람이 5장 플레이북과 6장 런북만으로 15분 안에 원인을 찾습니다. 대상은 6편 svc-lab 앱입니다. 끝나면 반드시 restore를 실행합니다.

gameday.sh — 출제자용
#!/usr/bin/env bash
set -euo pipefail
ID_FILE=/tmp/gameday.id
inject(){ case $1 in
  1) multipass exec w2 -- sudo ip link set dev eth0 mtu 1400 ;;                                   # 언더레이 MTU 축소
  2) kubectl -n kube-system get cm coredns -o yaml > /tmp/coredns.bak
     kubectl -n kube-system get cm coredns -o jsonpath='{.data.Corefile}' | sed 's#forward \. /etc/resolv.conf#forward . 192.0.2.53#' > /tmp/Corefile
     kubectl -n kube-system create cm coredns --from-file=Corefile=/tmp/Corefile --dry-run=client -o yaml | kubectl apply -f - ;;   # 외부 이름만 실패
  3) kubectl -n svc-lab apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: hardening-2026q4, namespace: svc-lab}
spec: {podSelector: {matchLabels: {app: web}}, policyTypes: ["Ingress"], ingress: [{from: [{podSelector: {matchLabels: {role: client}}}]}]}
EOF
     ;;                                                                                          # 그럴듯한 이름의 정책
  4) kubectl -n svc-lab patch svc web -p '{"spec":{"externalTrafficPolicy":"Local"}}'
     kubectl -n svc-lab scale deploy web --replicas=1 ;;                                            # 노드 일부만 응답
  5) kubectl -n kube-system get cm kube-proxy -o yaml > /tmp/kube-proxy.bak
     kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.config\.conf}' | sed 's/minSyncPeriod: .*/minSyncPeriod: 45s/' > /tmp/kp.conf
     kubectl -n kube-system create cm kube-proxy --from-file=config.conf=/tmp/kp.conf --from-literal=kubeconfig.conf="$(kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.kubeconfig\.conf}')" --dry-run=client -o yaml | kubectl apply -f -
     kubectl -n kube-system rollout restart ds/kube-proxy ;;                                        # 배포 직후 오류(무작위 재시작으로 확인)
  esac; echo "$1" > $ID_FILE; echo "장애를 심었습니다. 신고: '고객이 svc-lab 앱이 이상하다고 합니다.'"; }
restore(){ case $(cat $ID_FILE) in
  1) multipass exec w2 -- sudo ip link set dev eth0 mtu 1500 ;;
  2) kubectl apply -f /tmp/coredns.bak ;;
  3) kubectl -n svc-lab delete networkpolicy hardening-2026q4 ;;
  4) kubectl -n svc-lab patch svc web -p '{"spec":{"externalTrafficPolicy":"Cluster"}}'; kubectl -n svc-lab scale deploy web --replicas=3 ;;
  5) kubectl apply -f /tmp/kube-proxy.bak; kubectl -n kube-system rollout restart ds/kube-proxy ;;
  esac; rm -f $ID_FILE; echo "복구했습니다."; }
case ${1:-} in
  inject) inject "${2:-$(( RANDOM % 5 + 1 ))}" ;;
  restore) restore ;;
  *) echo "사용법: $0 inject [1-5] | restore" ;;
esac
진행 방법 출제자는 ./gameday.sh inject만 실행하고 번호를 말하지 않습니다. 진단자는 타이머를 15분에 맞추고 맨 위 게임처럼 행동마다 걸린 시간을 기록합니다. 끝나면 출제자가 번호를 공개하고 ./gameday.sh restore로 되돌립니다. 다섯 개를 모두 돌린 뒤 각자의 “첫 행동”을 비교해 보면, 플레이북의 0단계(범위와 최근 변경 확인)를 건너뛴 경우가 가장 오래 걸렸다는 것을 대개 확인하게 됩니다.

현장 사례

매일 밤 CoreDNS 설정이 사라진다

원인. AKS의 기본 coredns ConfigMap에 사내 도메인 전달을 직접 추가했는데, 관리형 애드온 조정이 원래대로 되돌렸습니다.

교훈. 같은 설정을 coredns-custom으로 옮겨 해결했습니다. 2장 표의 “설정 변경 방법” 열이 환경마다 다르다는 것을 런북 첫 줄에 적어 두세요.

DNS가 몇 분에 한 번씩 무더기로 실패한다 (EKS)

원인. CoreDNS Pod가 올라간 노드의 ENI가 VPC 리졸버로 보내는 패킷 한도에 걸렸습니다. 노드의 ENA 드라이버 지표 linklocal_allowance_exceeded가 증가하고 있었습니다. 원인은 ndots로 인한 NXDOMAIN 폭증이었습니다.

대응. NodeLocal DNSCache로 질의를 분산·캐시하고, 주요 외부 호출에 FQDN을 적용하고, CoreDNS를 여러 노드에 분산했습니다.

교훈. DNS 장애는 클러스터 안이 아니라 클라우드 네트워크 한도에서 날 수 있습니다.

사이드카보다 앱이 먼저 떠서 시작 직후 연결이 실패한다

원인. 사이드카 메시에서 앱 컨테이너가 프록시보다 먼저 시작해 첫 외부 호출이 실패하고, 앱이 재시도 없이 종료됐습니다. 종료 때도 프록시가 먼저 내려가 진행 중 요청이 끊겼습니다.

대응. Kubernetes 네이티브 사이드카(1.33 GA, restartPolicy: Always인 초기화 컨테이너)를 쓰는 메시 설정으로 바꿔 시작·종료 순서를 보장했습니다. 일부 워크로드는 ambient로 옮겼습니다.

교훈. 메시 도입 검토표에 컨테이너 수명 주기 순서를 넣으세요.

ambient로 옮긴 뒤 일부 서비스만 연결 실패

원인. 기본 거부 NetworkPolicy가 있는 네임스페이스에서 ztunnel 간 HBONE 포트 15008이 막혔습니다.

교훈. 메시·CNI·정책은 서로의 포트와 경로를 가정합니다. 메시 도입은 9편 연결 행렬 재시험과 한 묶음입니다.

두 번째 클러스터와 서비스를 공유하려 했지만 CIDR이 같았다

상황. 고객이 재해 복구용 두 번째 클러스터를 같은 템플릿으로 만들어 Pod·Service CIDR이 완전히 같았습니다. ClusterMesh는 불가능했습니다.

대응. 당장은 전역 DNS 기반의 독립 클러스터 패턴으로 운영하고, 다음 재구축 때 CIDR을 분리했습니다. 주소 변환이 가능한 Submariner Globalnet도 검토했지만 운영 복잡도 때문에 보류했습니다.

교훈. 클러스터 템플릿(Terraform 모듈 등)에 클러스터별 CIDR 변수를 필수로 두세요.

App Mesh 종료일이 지나고서야 남은 사용처를 발견했다

상황. 2026년 9월 30일 App Mesh가 종료된 뒤, 한 고객의 오래된 EKS 서비스가 App Mesh 리소스에 의존하고 있었다는 것이 장애로 드러났습니다.

교훈. 1편 인벤토리에 메시·게이트웨이·애드온의 지원 종료일 칸을 두고 분기마다 갱신하세요. 이 편의 점검표 14번 항목입니다.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. Pod DNS는 ndots:5와 검색 도메인 때문에 외부 이름 하나에 수많은 NXDOMAIN 질의를 만들며, FQDN·ndots 조정·autopath·NodeLocal DNSCache로 줄이고 환경별 확장 지점으로 설정해야 합니다.
  2. 서비스 메시는 mTLS·L7 관리·관측을 주는 대신 자원·운영 부담을 받으며, 사이드카·ambient·노드 단위 프록시 중 고르고, App Mesh(2026-09-30 종료)·OSSM 2.6(2026-06-30 종료) 같은 지원 종료를 추적해야 합니다.
  3. 멀티클러스터는 독립 + 전역 진입점, 평면 네트워크(ClusterMesh), 터널(Submariner), 메시 연합 중 고르며, CIDR 비중복과 네임스페이스 동일성이 전제입니다.
  4. 네트워크 장애는 범위 → Pod → DNS → Service → 프록시 → 정책 → CNI 경로 → 외부 진입 → 이그레스 순으로 쪼개 진단합니다.
  5. MTU·DNS·정책·LB 헬스 체크·kube-proxy 동기화의 다섯 런북과 게임 데이 훈련이 Level 1의 운영 결론입니다.

다음 편 · 11편 스토리지 모델: Volume → PV·PVC·StorageClass → CSI (Level 2 시작)

Level 2는 스토리지 6편입니다. 첫 편에서는 바인딩 모드(Immediate·WaitForFirstConsumer)와 토폴로지, 리클레임 정책, 접근 모드(RWO·RWX·ROX·RWOP), 볼륨 확장, 임시·프로젝티드 볼륨, in-tree 제거와 CSI Migration의 흔적, v1.37의 PVC 미사용 추적·용량 스코어링·CSI 인지 오토스케일링을 다루고, 멀티 AZ 스케줄링 실패를 재현·해결합니다. CSI 드라이버 내부와 벤더 드라이버 비교는 12편입니다.
