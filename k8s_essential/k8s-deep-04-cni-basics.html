Level 1 네트워크, 4편

Kubernetes 네트워크 모델과 CNI 원리

Kubernetes는 네트워크를 만들지 않습니다. “모든 Pod는 서로 NAT 없이 통신해야 한다”는 계약만 정하고, 그 계약을 지키는 일은 노드에서 실행되는 작은 프로그램, CNI 플러그인에 맡깁니다. 이 편은 그 계약을 문장 하나하나 뜯어보고, netns·veth·브리지·라우팅 테이블만으로 Pod 사이 패킷을 손으로 따라가며, 마지막에는 CNI를 손으로 직접 만들어 봅니다. 5·6편이 서 있는 바닥입니다.

기준: Kubernetes v1.37 · CNI 스펙 1.1 작성 기준일: 2026-10-23 예상 학습: 이론 120분 + 실습 150분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

Pod에서 Pod까지, 한 칸씩

전달 방식과 경로를 고른 뒤 단계를 넘기면, 패킷이 지금 어느 장치에 있는지 강조되고 그 순간의 헤더와 확인 명령이 나옵니다. 주소는 3편 기준선(w1·w2, Pod 대역 10.244.0.0/16)을 따랐습니다.

읽는 법과 목표

쉬운 말로 Pod는 각자 작은 방(netns)에 사는 사람입니다. 방에는 랜선 구멍이 하나 있고, 그 랜선(veth)의 반대쪽 끝은 건물 복도(노드)로 나와 있습니다. CNI는 사람이 입주할 때마다 랜선을 깔고 주소를 붙여 주는 설치 기사이고, 건물과 건물 사이를 잇는 방법(직통 도로를 내느냐, 소포로 감싸 보내느냐)도 CNI가 정합니다.

5·6편처럼 점선 밑줄 용어는 마우스를 올리거나 누르면 설명이 나오고, 12장 사전에 모여 있습니다. 이 편은 커리큘럼상 Level 1의 첫 편이며, 5편(CNI 구현체 비교)과 6편(Service)은 이 편의 개념을 전제로 합니다.

이 편을 마치면 할 수 있는 것

  • 네트워크 모델 4원칙을 정확히 말하고, 주어진 구성이 원칙을 지키는지 판정할 수 있습니다.
  • netns·veth·브리지·라우팅 테이블·터널 장치로 Pod 간 패킷 경로를 명령어 출력으로 추적할 수 있습니다.
  • kubelet → CRI → 런타임 → CNI로 이어지는 Pod IP 생성 과정을 설명하고, 각 단계의 실패 증상을 구분할 수 있습니다.
  • CNI 스펙의 동사(ADD·DEL·CHECK·GC·STATUS·VERSION), 설정 목록, 결과 전달(prevResult), 체이닝을 설명하고 플러그인을 직접 호출할 수 있습니다.
  • CNI 없이 클러스터를 만들어 보고, 손으로 만든 CNI → Flannel → Calico로 바꿔 가며 경로의 차이를 관찰할 수 있습니다.
1

네트워크 모델 4원칙

쉬운 말로 Kubernetes가 CNI에게 요구하는 것은 “평평한 주소 공간”입니다. 모든 Pod가 하나의 큰 사무실에 있는 것처럼, 누구든 상대 주소만 알면 중간에서 이름표를 바꿔 달지 않고(NAT 없이) 바로 말을 걸 수 있어야 합니다.
원칙정확한 의미CNI에게 강제하는 것
1. Pod마다 고유 IP클러스터 안에서 모든 Pod가 겹치지 않는 자기 IP를 가진다. Pod 안 컨테이너들은 그 IP와 포트 공간을 공유한다노드 사이에 겹치지 않게 주소를 나눠 주는 IPAM(노드별 대역 또는 중앙 배정)
2. Pod ↔ Pod, NAT 없이어느 노드의 Pod든 다른 모든 노드의 Pod와, 출발지·목적지 주소를 바꾸지 않고 통신한다노드 사이의 L3 도달성(라우팅·캡슐화·VPC 직결 중 하나)과, 클러스터 내부 트래픽에 SNAT를 걸지 않는 규칙
3. 노드 에이전트 ↔ 그 노드의 Podkubelet·시스템 데몬이 같은 노드의 Pod에 Pod IP로 닿는다(프로브, 메트릭)노드 자신의 라우팅 테이블에 Pod로 가는 경로
4. 내가 아는 내 IP = 남이 보는 내 IPPod가 자기 인터페이스에서 보는 IP와 다른 Pod가 보는 그 Pod의 IP가 같다Docker 기본 브리지처럼 바깥에 다른 주소로 보이는 구조 금지

원칙이 말하지 않는 것

  • 클러스터 밖으로 나가는 트래픽. Pod가 인터넷·사내망으로 나갈 때 노드 IP로 SNAT하는 것은 원칙 위반이 아닙니다. 원칙은 Pod끼리, 노드와 그 Pod 사이만 다룹니다.
  • Service. ClusterIP로 접속할 때 DNAT가 일어나는 것은 별도의 Service 모델(6편)입니다.
  • 캡슐화. VXLAN으로 감싸는 것은 주소를 바꾸는 것이 아니라 봉투에 넣는 것이라 위반이 아닙니다. 상대 Pod가 받는 패킷의 출발지는 원래 Pod IP 그대로입니다.
  • 격리. NetworkPolicy로 통신을 막는 것은 원칙과 충돌하지 않습니다. 원칙은 “기본 연결성”이고, 정책은 그 위에 거는 의도적 제한입니다(9편).
  • hostNetwork Pod. 노드의 네트워크 공간을 그대로 쓰는 Pod는 노드 IP를 공유합니다. 의도된 예외입니다.

Pod 안쪽 배선: netns, pause, veth

네트워크 공간을 붙잡는 pause 컨테이너

Pod가 만들어지면 컨테이너 런타임은 먼저 샌드박스를 만듭니다. 샌드박스의 핵심은 아무 일도 하지 않는 pause 컨테이너 하나와, 그것이 붙잡고 있는 netns입니다. Pod 안의 앱 컨테이너들은 이 netns에 합류하기 때문에 같은 IP와 같은 localhost를 공유합니다. 앱 컨테이너가 재시작해도 IP가 바뀌지 않는 이유는 IP가 앱 컨테이너가 아니라 샌드박스에 붙어 있기 때문입니다. 반대로 샌드박스가 다시 만들어지면(노드 재부팅, 샌드박스 변경) CNI가 다시 불려 IP가 바뀔 수 있습니다.

veth 한 쌍과 노드 쪽 끝의 세 가지 운명

CNI는 veth 한 쌍을 만들어 한쪽 끝은 Pod netns 안으로 옮겨 eth0이라 부르고, 다른 끝은 노드에 남깁니다. 차이는 노드에 남은 끝을 어떻게 처리하느냐에서 납니다.

노드 쪽 처리구조Pod 안 기본 경로쓰는 곳
브리지에 꽂기노드의 가상 스위치(cni0 등)에 모든 Pod veth를 꽂고, 브리지가 게이트웨이 IP를 가짐default via 10.244.1.1(브리지 IP)bridge 플러그인, Flannel, Docker 기본
라우팅으로 처리브리지 없이 veth마다 노드 라우팅 테이블에 Pod IP /32 경로. 게이트웨이는 proxy ARP로 노드가 대신 대답default via 169.254.1.1(가상 게이트웨이)Calico, ptp 플러그인, 일부 클라우드 CNI
eBPF가 받기veth 노드 쪽 끝에 eBPF 프로그램을 붙여 커널 라우팅을 거치지 않고 직접 전달구현마다 다름Cilium, GKE Dataplane V2
노드에서 Pod 배선 들여다보기
# Pod의 샌드박스 ID와 netns 경로 (crictl은 kubeadm 설치에 포함된 cri-tools)
POD_ID=$(sudo crictl pods --name web -q | head -1)
sudo crictl inspectp $POD_ID | jq -r '.info.runtimeSpec.linux.namespaces[] | select(.type=="network") | .path'

# 그 netns 안에서 명령 실행 (pause 프로세스의 PID로 진입)
PID=$(sudo crictl inspectp $POD_ID | jq -r '.info.pid')
sudo nsenter -t $PID -n ip addr show eth0
sudo nsenter -t $PID -n ip route

# Pod eth0의 짝 veth 찾기: eth0@ifN 의 N이 노드 쪽 인터페이스 번호
sudo nsenter -t $PID -n ip -o link show eth0     # 예: eth0@if12
ip -o link | grep '^12:'                        # 노드 쪽 veth 이름과 master(브리지)
ip netns list                                    # 런타임이 이름 붙인 netns 목록(cni-xxxx)

Pod IP가 생기는 순서

“IP가 안 붙는다”는 장애는 이 순서의 어느 단계에서 멈췄는지로 쪼개야 합니다.

단계주체하는 일여기서 멈추면 보이는 것
1스케줄러Pod에 노드 배정. 노드가 NotReady(네트워크 미준비)면 기본 테인트 때문에 배정하지 않음Pod Pending, “node(s) had untolerated taint node.kubernetes.io/not-ready”
2kubeletCRI로 런타임에 RunPodSandbox 요청kubelet 로그의 sandbox 생성 오류
3런타임(containerd·CRI-O)netns 생성, pause 시작, CNI 설정 디렉터리에서 설정 파일을 골라 플러그인에 ADD 호출ContainerCreating, 이벤트 “failed to setup network for sandbox … plugin type=… failed”
4CNI 플러그인veth 생성, IPAM으로 IP 받기, 경로 설정, 결과 JSON 반환“no IP addresses available in range set”, “failed to find plugin … in path”
5런타임 → kubelet결과의 IP를 Pod 상태(status.podIPs)로 보고—
6EndpointSlice 컨트롤러준비된 Pod IP를 Service 명단에 기록(6편)Service 엔드포인트 없음

노드의 “네트워크 준비됨”은 누가 정하나

kubelet은 런타임에게 네트워크가 준비됐는지 묻고, 런타임은 전통적으로 CNI 설정 디렉터리에 유효한 설정 파일이 있는지로 답해 왔습니다. 그래서 CNI DaemonSet이 설정 파일을 써 넣는 순간 노드가 Ready로 바뀝니다. CNI 스펙 1.1의 STATUS 동사는 플러그인이 “지금 ADD를 받을 준비가 됐다”를 직접 보고하게 해, 설정 파일은 있는데 실제 에이전트는 죽어 있는 상태를 구분할 수 있게 합니다. 런타임 버전에 따라 이 동사를 쓰는지 여부가 다릅니다.

containerd 2.x의 CNI 위치 설정
containerd config dump | grep -A6 "io.containerd.cri.v1.runtime'.cni"
# bin_dirs = ['/opt/cni/bin']        플러그인 실행 파일 위치(2.x부터 목록)
# conf_dir = '/etc/cni/net.d'        설정 파일 위치
# max_conf_num = 1                   사용할 설정 파일 개수(기본 1: 이름순 첫 파일)
sudo crictl info | jq '.status.conditions[] | select(.type=="NetworkReady")'
함정: 이름순 첫 파일이 이긴다 런타임은 설정 디렉터리의 파일을 이름순으로 정렬해 첫 번째를 씁니다. CNI를 바꾸고 옛 설정 파일을 지우지 않으면, 이름이 앞선 쪽이 계속 쓰입니다. 예를 들어 10-calico.conflist와 10-flannel.conflist가 함께 있으면 calico가 선택되지만, 옛 cni0 브리지·경로·iptables 규칙은 그대로 남아 있습니다. 많은 CNI가 00-, 05- 같은 접두사로 우선순위를 확보하는 이유이고, Multus가 맨 앞에 자기 설정을 두는 이유입니다(10장 첫 사례).

CNI 스펙: 실행 파일과 표준 입력의 계약

쉬운 말로 CNI는 서버도 데몬도 아닌 “명령 실행 규칙”입니다. 런타임은 플러그인 실행 파일을 한 번 실행하면서, 무엇을 할지는 환경 변수로, 설정은 표준 입력(JSON)으로 넘기고, 결과는 표준 출력(JSON)으로 받습니다. 그래서 사람도 같은 방식으로 플러그인을 손으로 실행해 볼 수 있습니다(9장 실습 1).

동사(CNI_COMMAND)

동사언제하는 일쉬운 말로
ADD샌드박스 생성 시인터페이스 만들고 IP·경로 설정, 결과 반환입주 공사
DEL샌드박스 삭제 시만든 것을 정리하고 IP 반납. 여러 번 불려도 안전해야 함(멱등)퇴거 정리. 이미 비어 있어도 오류 없이
CHECK런타임이 주기적으로(선택)이전 결과대로 아직 설정돼 있는지 확인점검 방문
GC (1.1)런타임이 정리할 때“지금 살아 있는 연결 목록”을 받아 그 밖의 흔적(새 IP 기록 등)을 정리빈집 대청소
STATUS (1.1)런타임이 준비 상태 확인 시플러그인이 ADD를 받을 준비가 됐는지 보고“지금 공사 가능?” 문의
VERSION호환성 확인지원하는 스펙 버전 목록 반환자격증 확인

입력과 출력

  • 환경 변수. CNI_COMMAND, CNI_CONTAINERID(샌드박스 ID), CNI_NETNS(netns 경로), CNI_IFNAME(대개 eth0), CNI_PATH(플러그인 검색 경로), CNI_ARGS(부가 정보. Kubernetes는 Pod 이름·네임스페이스를 넣음).
  • 설정 목록(conflist). 관리자가 쓰는 파일. cniVersion, name, plugins 배열로 이루어지고, 런타임은 배열의 플러그인을 순서대로 호출합니다. 스펙 1.0부터 목록이 아닌 단일 설정 파일 형식은 제거됐습니다(플러그인 자체는 여전히 표준 입력으로 단일 객체를 받음).
  • 결과. 만들어진 interfaces, 배정된 ips, routes, dns. 다음 플러그인에게 prevResult로 전달되고, 마지막 결과가 런타임에 돌아갑니다. 런타임은 이 결과를 캐시해 두었다가 DEL·CHECK 때 다시 넘깁니다.
  • 실행 시 정보(capabilities). 포트 매핑(hostPort), 대역폭 제한처럼 Pod마다 다른 값은 설정 파일이 아니라 실행 시 runtimeConfig로 들어옵니다. 플러그인이 설정에서 해당 capability를 선언해야 런타임이 넘겨 줍니다.
  • 위임(delegation). 플러그인이 다른 플러그인을 직접 실행할 수 있습니다. 대표가 IPAM입니다. bridge 플러그인은 IP를 직접 고르지 않고 ipam.type에 적힌 host-local을 실행해 IP를 받아 옵니다. Flannel 플러그인은 bridge에 통째로 위임합니다.

호출 시뮬레이터

bridge → portmap → bandwidth 체인 설정에서 런타임이 동사별로 무엇을 하는지 순서대로 보여 줍니다. 단계를 누르면 그때 넘겨지는 환경 변수·입력과 돌아오는 출력이 나옵니다.

IPAM: 겹치지 않게 주소 나누기

    
쉬운 말로
    IPAM은 주소 관리 담당입니다. 가장 흔한 방식은 클러스터 전체 대역을 노드마다 한 동(/24)씩 나눠 주고, 각 노드가 자기 동 안에서만 호수를 매기는 것입니다. 노드끼리 상의할 필요가 없어 단순합니다.

    

      
방식누가 대역을 나누나노드에서 IP를 고르는 법쓰는 곳

      
        
Kubernetes 노드 IPAM + host-localkube-controller-manager(--allocate-node-cidrs, --cluster-cidr, 노드당 기본 /24)가 node.spec.podCIDR에 기록host-local이 그 대역에서 골라 /var/lib/cni/networks/<이름>/에 IP별 파일로 기록kubeadm(podSubnet 지정 시) + Flannel·bridge·ptp

        
CNI 자체 IPAMCNI 컨트롤러가 자기 방식으로 블록 배정CNI 에이전트가 블록에서 배정Calico(/26 블록), Cilium cluster-pool

        
클라우드 IPAM클라우드 네트워크(VPC·VNet 서브넷, 보조 범위)클라우드 API로 받아 온 IPEKS VPC CNI, Azure CNI, GKE(5편)

        
static·dhcp사람 또는 외부 DHCP지정 값 또는 DHCP 임대Multus 보조 네트워크, 특수 장비 연결

      
    

    

      
    
        
  • 노드당 /24의 의미. 노드당 Pod 254개까지 가능하지만 kubelet 기본 최대 Pod는 110입니다. 클러스터 대역이 /16이면 노드 256대가 상한입니다. 대역 계획이 곧 클러스터 규모 계획입니다.
    • 
        
  • IP 누수. host-local은 IP를 파일로 기록하므로, DEL이 불리지 못한 채 샌드박스가 사라지면(런타임 비정상 종료, 노드 강제 재부팅) 파일이 남아 그 IP가 영영 재사용되지 않습니다. 쌓이면 “no IP addresses available in range set”으로 새 Pod가 실패합니다. CNI 1.1의 GC가 이 문제를 겨냥하며, libcni는 GC를 지원하지 않는 플러그인에도 남은 캐시 기준으로 DEL을 합성해 정리를 시도합니다(10장 두 번째 사례).
    • 
        
  • 듀얼 스택. IPv4·IPv6 대역을 함께 주면 Pod가 두 주소를 받습니다(status.podIPs에 둘). 1.23에서 GA. IPAM과 경로가 각 패밀리에 대해 따로 동작합니다.
    •

레퍼런스 플러그인과 체이닝

    
CNI 프로젝트가 관리하는 레퍼런스 플러그인(containernetworking/plugins)은 세 부류로 나뉩니다. 대부분의 CNI 구현체가 이 중 일부를 내부적으로 재사용합니다.

    

      
부류플러그인하는 일

      
        
인터페이스bridge, ptp, macvlan, ipvlan, host-device, vlan, loopback, dummy, tapPod netns에 인터페이스를 만들고 노드와 연결

        
IPAMhost-local, dhcp, staticIP 배정만 담당(인터페이스 플러그인이 위임 호출)

        
메타(체인용)portmap, bandwidth, tuning, firewall, sbr, vrf앞 플러그인이 만든 결과 위에 기능을 덧붙임

      
    

    

      
메타 플러그인Kubernetes에서 켜지는 방법내부 동작

      
        
portmapPod 스펙의 hostPort노드 포트 → Pod 포트 DNAT 규칙(iptables·nftables)

        
bandwidthPod 어노테이션 kubernetes.io/ingress-bandwidth, kubernetes.io/egress-bandwidth리눅스 tc로 대역폭 제한

        
tuning설정 파일(또는 Pod별 sysctl)Pod 인터페이스의 sysctl·MTU·MAC 조정

        
firewall설정 파일Pod 트래픽을 허용하는 방화벽 규칙 추가(호스트 방화벽이 엄격할 때)

      
    

    
체인 설정 예 (9장 실습 2에서 실제로 사용)
{
  "cniVersion": "1.0.0",
  "name": "manual",
  "plugins": [
    { "type": "bridge", "bridge": "cni0", "isGateway": true, "ipMasq": true, "hairpinMode": true,
      "ipam": { "type": "host-local",
                "ranges": [[ { "subnet": "10.244.1.0/24" } ]],
                "routes": [ { "dst": "0.0.0.0/0" } ] } },
    { "type": "portmap",   "capabilities": { "portMappings": true } },
    { "type": "bandwidth", "capabilities": { "bandwidth": true } }
  ]
}

    

      
체이닝의 실전형

      
    
        
  • CNI 구현체 내부. Flannel은 자기 플러그인 뒤에 portmap을, Calico는 calico 플러그인 뒤에 bandwidth·portmap을 체인으로 붙입니다. 각 노드의 설정 파일을 열어 보면 바로 보입니다(실습 3·4).
    • 
        
  • 다른 CNI 위에 얹기. 5편에서 본 Cilium 체이닝(EKS VPC CNI가 IP, Cilium이 정책·관측)이 같은 원리입니다. 뒤 플러그인이 prevResult로 앞 플러그인의 인터페이스를 넘겨받아 기능만 붙입니다.
    • 
        
  • Multus. 체이닝이 아니라 “메타 CNI”입니다. 기본 CNI를 호출해 eth0을 만들고, Pod 어노테이션에 적힌 추가 네트워크마다 다른 CNI를 불러 net1, net2…를 붙입니다. OpenShift는 Multus가 항상 맨 앞에 있습니다.
    •

노드 사이 전달: 오버레이가 있을 때와 없을 때

    
쉬운 말로
    같은 건물(노드) 안의 방끼리는 복도(브리지나 노드 라우팅)로 바로 갑니다. 다른 건물로 갈 때는 두 가지입니다. 도로 지도에 “10.244.2.x 동은 저 건물”이라고 적어 두고 그냥 보내거나(라우팅), 편지를 건물 주소가 적힌 큰 봉투에 넣어 보냅니다(오버레이). 맨 위 패킷 추적기가 이 차이를 단계별로 보여 줍니다.

    

      
방식노드 A의 경로 예바깥에서 보이는 패킷요구 조건

      
        
손으로 넣은 정적 경로10.244.2.0/24 via 192.168.64.13 dev eth0Pod IP 그대로노드끼리 같은 L2이거나, 중간 라우터에도 경로가 있어야 함. 노드 추가 때마다 모든 노드 수정

        
Flannel host-gw위와 같은 경로를 flanneld가 자동으로 넣음Pod IP 그대로모든 노드가 같은 L2

        
Calico BGP10.244.2.0/26 via 192.168.64.13 dev eth0 proto birdPod IP 그대로BGP로 경로 교환. 다른 L2라면 라우터와 BGP 또는 CrossSubnet 캡슐화

        
Flannel VXLAN10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink노드 IP → 노드 IP, UDP 8472 안에 Pod 패킷노드끼리 IP로만 통하면 됨

        
Calico VXLAN10.244.2.0/26 via 10.244.2.0 dev vxlan.calico onlink노드 IP → 노드 IP, UDP 4789 안에 Pod 패킷노드끼리 IP로만 통하면 됨

      
    

    

      
VXLAN 터널 장치가 상대를 찾는 법

      
Flannel의 flannel.1은 VTEP(터널 끝점)입니다. 경로가 “다음 홉 10.244.2.0을 flannel.1로”라고 말하면, 커널은 ① 이웃 표(ARP)에서 10.244.2.0의 MAC 주소(상대 노드 VTEP의 MAC)를 찾고, ② 포워딩 표(FDB)에서 그 MAC이 어느 노드 IP 뒤에 있는지 찾아, ③ 그 노드 IP로 UDP 패킷을 만들어 보냅니다. flanneld는 이 세 가지(경로, 이웃, FDB)를 노드가 생길 때마다 미리 채워 넣는 일을 합니다. 9장 실습 3에서 세 표를 직접 봅니다.

      
같은 노드 안에서도 다르다

      
브리지 방식에서 같은 노드의 Pod끼리는 브리지가 L2 스위칭으로 바로 전달합니다. 라우팅 방식(Calico)에서는 같은 노드라도 노드 라우팅 테이블을 거쳐 L3로 전달됩니다. 이 차이 때문에 브리지 방식에서는 br_netfilter가 로드돼야 같은 노드 Pod 사이 트래픽도 iptables(NetworkPolicy, Service DNAT의 되돌림)를 거칩니다. 3편 노드 준비 스크립트가 이 모듈을 켠 이유입니다(10장 다섯 번째 사례).

실습 2. 손으로 만든 클러스터 CNI (bridge + host-local + 정적 경로)

      
Flannel이나 Calico가 자동으로 해 주는 일을 직접 합니다. 노드마다 자기 podCIDR로 설정 파일을 쓰고, 다른 노드의 Pod 대역으로 가는 경로를 손으로 넣습니다. 그러고 나서 원칙 2를 시험합니다.

    
호스트: 설정 파일 템플릿 manual.conflist.tmpl
{
  "cniVersion": "1.0.0",
  "name": "manual",
  "plugins": [
    { "type": "bridge", "bridge": "cni0", "isGateway": true, "ipMasq": __MASQ__, "hairpinMode": true,
      "ipam": { "type": "host-local", "ranges": [[{ "subnet": "__CIDR__" }]], "routes": [{ "dst": "0.0.0.0/0" }] } },
    { "type": "portmap",   "capabilities": { "portMappings": true } },
    { "type": "bandwidth", "capabilities": { "bandwidth": true } }
  ]
}

    
호스트: 배포와 경로 설정
deploy_cni(){   # $1 = true|false (ipMasq)
  for n in cp1 w1 w2; do
    CIDR=$(kubectl get node $n -o jsonpath='{.spec.podCIDR}')
    sed -e "s#__CIDR__#$CIDR#" -e "s#__MASQ__#$1#" manual.conflist.tmpl > /tmp/$n.conflist
    multipass transfer /tmp/$n.conflist $n:/tmp/10-manual.conflist
    multipass exec $n -- sudo install -m644 /tmp/10-manual.conflist /etc/cni/net.d/10-manual.conflist
  done; }
deploy_cni true
kubectl get nodes                                   # 설정 파일이 생기자 Ready

# 다른 노드의 Pod 대역으로 가는 경로를 모든 노드에 (원칙 2의 '도달성')
for n in cp1 w1 w2; do for m in cp1 w1 w2; do [ $n = $m ] && continue
  CIDR=$(kubectl get node $m -o jsonpath='{.spec.podCIDR}')
  IP=$(kubectl get node $m -o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}')
  multipass exec $n -- sudo ip route replace $CIDR via $IP
done; done
multipass exec w1 -- ip route | grep 10.244

kubectl exec cli -- curl -s $SRV:8080/clientip; echo     # 결과가 w1의 노드 IP라면?

    
관찰: ipMasq: true는 원칙 2를 깬다
    bridge 플러그인의 ipMasq는 “자기 노드 대역이 아닌 목적지”로 가는 모든 트래픽을 노드 IP로 바꿉니다. 다른 노드의 Pod도 “자기 대역이 아닌 목적지”이므로, srv는 출발지를 cli의 Pod IP가 아니라 w1의 노드 IP로 봅니다. 아래처럼 바깥(클러스터 대역 밖)으로 가는 트래픽만 직접 SNAT하도록 바꾸면 원칙이 지켜집니다.

    
호스트: ipMasq를 끄고 클러스터 밖으로 나갈 때만 SNAT
deploy_cni false
for n in cp1 w1 w2; do
  multipass exec $n -- sudo iptables -t nat -C POSTROUTING -s 10.244.0.0/16 ! -d 10.244.0.0/16 -j MASQUERADE 2>/dev/null || \
  multipass exec $n -- sudo iptables -t nat -A POSTROUTING -s 10.244.0.0/16 ! -d 10.244.0.0/16 -j MASQUERADE
done
kubectl delete pod srv cli                 # 설정은 새 샌드박스부터 적용되므로 다시 생성
# (위의 kubectl run 두 줄과 wait를 다시 실행)
kubectl exec cli -- curl -s $(kubectl get pod srv -o jsonpath='{.status.podIP}'):8080/clientip; echo   # 이제 cli의 Pod IP
kubectl exec cli -- curl -s -o /dev/null -w '%{http_code}\n' https://registry.k8s.io   # 바깥은 여전히 됨

# 관찰: 브리지, veth, IP 기록, 체인 플러그인의 흔적
multipass exec w1 -- sudo bash -c 'ip -br addr show cni0; bridge link; ls /var/lib/cni/networks/manual/; iptables -t nat -S | grep -i cni | head'
kubectl -n kube-system get pods -o wide | grep coredns   # CoreDNS도 이제 Running

    
정리해 보면
    지금 손으로 한 일이 CNI 구현체가 자동화하는 일의 전부입니다: ① 노드별 설정 파일 배포, ② 노드 사이 경로(또는 터널) 유지, ③ 클러스터 밖으로 나가는 트래픽만 SNAT, ④ 노드가 추가·삭제될 때 이 모든 것을 갱신. 노드를 하나 더 붙인다고 상상해 보면 왜 DaemonSet과 컨트롤러가 필요한지 체감됩니다.

현장 사례

    
CNI를 바꿨는데 일부 노드만 옛 네트워크로 IP를 받는다

      
원인. Flannel에서 Calico로 바꾸면서 일부 노드의 /etc/cni/net.d/에 옛 파일이 남았고, 그 노드에서는 이름순으로 앞선 파일이 선택됐습니다. 남은 cni0 브리지와 경로 때문에 증상이 노드마다 달랐습니다.

      
대응. 모든 노드에서 옛 설정 파일·브리지·경로·iptables 규칙을 지우고 노드를 순차 재부팅했습니다.

      
교훈. 운영 중 CNI 교체는 사실상 재구축입니다. 해야 한다면 노드를 하나씩 비우고(drain) 교체하며, 설정 디렉터리 정리를 절차에 넣으세요.

    

    
“no IP addresses available in range set”

      
상황. 오래 운영한 노드에서만 새 Pod가 ContainerCreating에 멈췄습니다. 노드의 Pod 수는 30개뿐이었습니다.

      
원인. 노드가 여러 번 강제 재부팅되며 DEL이 불리지 못한 샌드박스의 IP 기록 파일이 /var/lib/cni/networks/에 쌓여 /24가 가득 찼습니다.

      
대응. 노드를 비운 뒤 현재 Pod IP 목록과 대조해 고아 파일을 지웠습니다. 런타임·CNI를 GC를 지원하는 버전으로 올렸습니다.

      
교훈. IPAM은 상태를 가집니다. Pod 수가 아니라 기록된 IP 수를 봐야 하고, 강제 재부팅이 잦은 노드는 정리 대상입니다.

    

    
다른 노드의 Pod가 보내는 요청이 모두 노드 IP로 찍힌다

      
원인. 직접 만든 CNI 설정(또는 오래된 사내 구성)에서 bridge의 ipMasq: true를 그대로 써, 노드 간 Pod 트래픽이 SNAT되고 있었습니다. 앱의 IP 기반 접근 제어와 감사 로그가 무의미해졌습니다.

      
교훈. 실습 2에서 본 것처럼 SNAT 범위는 “클러스터 대역 밖으로 나갈 때만”이어야 합니다. 원칙 2 위반은 기능은 동작하게 두고 보안·관측만 조용히 망가뜨립니다.

    

    
노드 재설치 후 hostPort Pod만 실패한다

      
원인. 노드 이미지를 새로 만들면서 /opt/cni/bin/portmap이 빠졌습니다. 체인의 portmap을 쓰는 hostPort Pod만 “failed to find plugin portmap in path”로 실패했고, 나머지 Pod는 정상이었습니다.

      
교훈. 체인의 플러그인 실행 파일도 노드 이미지의 구성 요소입니다. 노드 이미지 검증 항목에 설정 파일이 참조하는 모든 플러그인 실행 파일의 존재를 넣으세요.

    

    
같은 노드의 Pod끼리만 Service 호출이 안 된다

      
원인. 브리지 방식 CNI 노드에서 br_netfilter 모듈이 로드되지 않아, 같은 브리지 안에서 오가는 패킷이 iptables를 거치지 않았습니다. Service DNAT의 응답 되돌림이 어긋나 같은 노드 Pod 사이 Service 호출만 실패했고, NetworkPolicy도 같은 노드 안에서는 적용되지 않았습니다.

      
교훈. 3편 노드 준비 스크립트의 커널 모듈·sysctl은 장식이 아닙니다. 노드 이미지가 바뀔 때마다 lsmod | grep br_netfilter와 sysctl net.bridge.bridge-nf-call-iptables를 확인하세요.

    

    
네트워크 카드가 둘인 노드에서 Pod 응답이 사라진다

      
원인. 관리망과 서비스망 두 인터페이스를 가진 노드에서, 들어온 인터페이스와 나가는 인터페이스가 달라지는 비대칭 경로가 생겼고, 엄격한 역방향 경로 검사(rp_filter=1)가 응답 패킷을 버렸습니다.

      
교훈. 다중 NIC 노드는 CNI의 노드 IP 자동 감지 설정(예: Calico의 IP 자동 감지 방식, Flannel의 --iface)과 rp_filter를 함께 설계해야 합니다. 온프렘 고객에서 자주 만나는 함정입니다.

이 편의 핵심 다섯 줄

      
    
        
  1. 네트워크 모델은 고유 IP, Pod 간 NAT 없음, 노드 에이전트 ↔ Pod 도달, 자기 IP = 남이 보는 IP의 네 원칙이며, 클러스터 밖 SNAT·Service DNAT·캡슐화·정책은 위반이 아닙니다.
    2. 
        
  2. Pod의 IP는 pause 컨테이너가 붙잡은 netns에 있고, veth의 노드 쪽 끝을 브리지·라우팅·eBPF 중 어떻게 처리하느냐가 CNI의 첫 차이입니다.
    3. 
        
  3. CNI는 실행 파일 계약입니다. 동사는 환경 변수로, 설정은 표준 입력으로, 결과는 표준 출력으로 오가며, 체인은 prevResult로 이어지고, 런타임은 설정 디렉터리의 이름순 첫 파일을 씁니다.
    4. 
        
  4. IPAM은 상태를 가지며(host-local 파일), DEL 누락은 IP 누수로 이어집니다. CNI 1.1의 GC·STATUS가 이 운영 문제를 겨냥합니다.
    5. 
        
  5. 노드 사이 전달은 정적 경로·host-gw·BGP(캡슐화 없음)와 VXLAN(캡슐화) 중 하나이며, 경로 표·이웃 표·FDB를 보면 어느 방식인지 바로 알 수 있습니다.
