10편Nova 2: 인스턴스 생명주기 심화

이 시리즈에서 가장 중요한 편입니다. VM 하나가 태어나는 14단계를 로그 수준으로 따라가고, 그 VM이 살아가며 겪는 재시작·크기 변경·재구축·보관·이사(마이그레이션)를 하나씩 해부합니다. 마지막으로 VM을 어느 서버 무리에, 어떤 CPU·메모리 배치로 둘지 정하는 집계·가용 영역·NUMA까지 다룹니다.

섹션 1

이 편의 목표

  1. 인스턴스의 vm_state · task_state · power_state를 구분해 읽고, 작업별 상태 전이를 예측한다.
  2. VM 생성 요청을 14단계로 추적하고, 단계마다 어느 서비스의 어느 로그를 볼지 안다.
  3. 오류 메시지(지문)로 부팅이 몇 단계에서 실패했는지 판별한다.
  4. 재시작·정지·일시 정지·중단·셸브·리사이즈·리빌드·구조 모드·대피의 차이(다운타임, 자원 점유, IP·디스크 보존)를 설명한다.
  5. 콜드·라이브·블록 라이브 마이그레이션의 원리와 실패 원인, 조정값을 설명한다.
  6. 호스트 집계와 가용 영역을 설계하고, 등급·고객 전용 노드를 분리한다.
  7. NUMA · CPU 고정 · 휴즈페이지의 개념과 RHOSO에서의 준비 사항을 설명한다.

9편 비유 이어서: 호텔 투숙객의 일생

9편에서 호텔(Nova)의 부서와 객실 배정 규칙을 봤다면, 이번 편은 투숙객(VM) 한 명의 일생입니다. 체크인(생성), 외출·귀가(정지·시작), 방 바꾸기(리사이즈), 방 리모델링(리빌드), 짐 맡기고 퇴실(셸브), 다른 방으로 옮기기(마이그레이션), 정전 시 다른 동으로 대피(대피·evacuate). 그리고 큰 손님을 위한 “한 층 통째로 예약”(NUMA·CPU 고정)까지.

섹션 2

세 개의 상태 칸

사용자 화면의 Status(ACTIVE, BUILD …)는 사실 Nova 내부의 세 칸을 합쳐 보여 준 것입니다. 장애 분석에서는 세 칸을 따로 봐야 합니다.

칸뜻예보는 법
vm_state안정된 상태. 작업이 끝났을 때 VM이 있는 곳active, stopped, paused, suspended, shelved_offloaded, resized, rescued, errorOS-EXT-STS:vm_state
task_state지금 진행 중인 작업의 단계 (없으면 None)scheduling, networking, block_device_mapping, spawning, resize_migrating, migrating, powering-offOS-EXT-STS:task_state
power_state하이퍼바이저가 보고하는 실제 전원 상태RUNNING(1), PAUSED(3), SHUTDOWN(4), CRASHED(6), SUSPENDED(7), NOSTATE(0)OS-EXT-STS:power_state
 
openstack server show app-01 -c status -c OS-EXT-STS:vm_state -c OS-EXT-STS:task_state -c OS-EXT-STS:power_state -c OS-EXT-SRV-ATTR:host

세 칸이 어긋날 때가 신호

  • vm_state=active인데 power_state=SHUTDOWN: VM 안에서 OS가 스스로 꺼졌거나 하이퍼바이저에서 죽음. Nova가 주기적으로 맞추면서 stopped로 바뀌기도 합니다.
  • task_state가 오래 바뀌지 않음(예: spawning에서 30분): 그 단계의 서비스가 멈춤. 섹션 4의 해당 단계 로그를 봅니다.
  • vm_state=error, 호스트 비어 있음: 배치 실패로 cell0에 기록됨(9편).

섹션 3

상태 전이 탐색기

현재 상태를 고르면 할 수 있는 작업과 결과 상태가 나옵니다. 작업 버튼을 누르면 그 상태로 이동합니다. 각 작업이 호스트 자원을 계속 붙잡고 있는지도 함께 보세요. 이것이 쿼터·용량·과금과 직결됩니다.

요청 ID로 로그를 꿰는 법

    
생성 응답 헤더(x-openstack-request-id)나 openstack server event list의 Request ID로 nova-api·conductor·scheduler 로그를 검색하고, 컴퓨트 노드에서는 인스턴스 UUID로 nova_compute 로그를 검색합니다. 서비스 사이에 요청 ID가 이어지지 않는 구간(예: Neutron 이벤트)은 인스턴스 UUID나 포트 ID로 이어 붙입니다.

  

  
# 컨트롤 플레인 (OCP Pod)
oc logs -n openstack -l service=nova --all-containers --prefix --since=1h | grep req-0b93…
# 컴퓨트 노드 (podman 컨테이너)
sudo podman logs nova_compute 2>&1 | grep <인스턴스 UUID>
# 사용자 관점의 실패 이유와 액션 기록
openstack server show <VM> -c fault
openstack server event show <VM> <요청 ID>

  
레이블 이름은 버전마다 다를 수 있으니 oc get pods -n openstack --show-labels | grep nova로 먼저 확인하세요.

섹션 6

  
생명주기 작업 비교

  

    
작업무엇이 일어나나다운타임호스트 자원IP · 디스크누가

    
      
reboot (soft)게스트 OS에 정상 재시작 요청 (ACPI). 응답 없으면 일정 시간 후 hard로재부팅 시간유지유지사용자

      
reboot --hard전원 껐다 켜기와 같음. 하이퍼바이저가 VM을 다시 정의·시작재부팅 시간유지유지 (쓰기 중 데이터 손실 가능)사용자

      
stop / start전원 끄기·켜기정지 동안유지 (자리를 계속 차지)유지사용자

      
pause / unpause메모리에 그대로 둔 채 CPU만 멈춤멈춘 동안유지유지사용자

      
suspend / resume메모리 내용을 디스크에 저장하고 멈춤 (최대 절전과 비슷)멈춘 동안유지유지사용자

      
shelve / unshelve정지 후 디스크를 이미지로 보관, (offload되면) 호스트에서 내림. unshelve 때 다시 스케줄링보관 동안offload되면 반납IP 유지(포트 유지), 디스크는 이미지·볼륨으로 보존사용자

      
resize다른 플레이버로 변경. 대부분 다른 호스트로 콜드 마이그레이션 후 확인(confirm) 또는 되돌리기(revert)이동 시간확인 전까지 양쪽 모두 점유유지사용자

      
rebuild같은 VM(UUID·IP 유지)을 새 이미지로 다시 설치재설치 시간유지IP 유지, 루트 임시 디스크는 초기화사용자

      
rescue / unrescue구조용 이미지로 부팅하고 원래 디스크를 보조 디스크로 붙임 (비밀번호 분실·부팅 불가 복구)구조 동안유지유지사용자

      
cold migrate정지 후 다른 호스트로 이동 (리사이즈와 같은 흐름, 플레이버만 동일)이동 시간확인 전까지 양쪽유지관리자

      
live migrate실행 상태 그대로 다른 호스트로 이동보통 1초 미만의 짧은 멈춤이동 중 양쪽유지관리자

      
evacuate죽은 호스트의 VM을 다른 호스트에서 다시 만듦재생성 시간새 호스트IP 유지, 공유 저장소·볼륨이 아니면 디스크 초기화관리자

      
snapshot (image create)루트 디스크를 Glance 이미지로 저장 (6편)짧은 정지 가능 (quiesce)유지유지사용자

    
  

  

    
MSP 과금 관점의 함정

    
고객이 “VM을 꺼 두었으니 비용이 안 나와야 한다”고 말할 때가 있습니다. stop은 호스트 자원을 계속 붙잡고 쿼터도 그대로 씁니다. 자원을 반납하려면 shelve(offload)가 필요합니다. 과금 정책(32편)에서 stop과 shelve를 어떻게 구분할지 미리 정해 두세요.

  







  
섹션 7

  
리사이즈 · 리빌드 · 셸브 깊게

  
리사이즈의 흐름

  
    
    
  1. 새 플레이버로 스케줄링(9편). 기본적으로 다른 호스트를 고릅니다(같은 호스트 허용은 설정 allow_resize_to_same_host).
    2. 
    
  2. Placement에 대상 호스트 할당을 만들고, 원래 호스트의 할당은 마이그레이션 기록이 소유하도록 옮깁니다. 그래서 확인 전까지 양쪽 자원이 모두 잡혀 있습니다.
    3. 
    
  3. VM 정지 → 디스크 복사(공유 저장소·볼륨이면 생략) → 대상 호스트에서 새 플레이버로 시작.
    4. 
    
  4. 상태가 VERIFY_RESIZE가 되면 사용자가 확인(resize confirm)하거나 되돌립니다(resize revert). 확인해야 원래 호스트 자원이 풀립니다. 일정 시간 후 자동 확인하려면 resize_confirm_window를 설정합니다(기본 0 = 자동 확인 안 함).
    5. 
  

  
openstack server resize --flavor m1.xlarge app-01
openstack server show app-01 -c status          # VERIFY_RESIZE
openstack server resize confirm app-01          # 또는 resize revert app-01
openstack server migration list --server app-01

  

    
리사이즈의 제약

    
    
      
  • 루트 임시 디스크를 줄이는 리사이즈는 거부됩니다(데이터 손실 방지). 부팅 볼륨은 플레이버 디스크와 무관.
    • 
      
  • VERIFY_RESIZE 상태를 오래 방치하면 양쪽 자원이 계속 묶여 용량이 부족해 보입니다. 정기적으로 찾아 정리하세요(openstack server list --all-projects --status VERIFY_RESIZE).
    • 
      
  • 대상 호스트로 디스크를 옮길 때 컴퓨트 노드끼리 SSH로 통신합니다. RHOSO에서는 데이터 플레인 배포가 마이그레이션용 SSH 키(nova-migration-ssh-key)를 노드에 넣어 둡니다(8편 사용자 정의 nova 서비스에도 포함).
    • 
    

  

  
리빌드

  
같은 인스턴스(UUID, 포트·IP, 플로팅 IP)를 유지하면서 루트 디스크만 새 이미지로 다시 만듭니다. 오염된 서버를 같은 주소로 재설치할 때 유용합니다. 루트 임시 디스크의 데이터는 사라지고, 붙어 있는 Cinder 데이터 볼륨은 유지됩니다. 부팅 볼륨 VM의 리빌드는 최신 API 마이크로버전에서 지원되므로 클라이언트·서버 버전을 확인하세요.

  
openstack server rebuild --image golden-rhel9-2026.10 app-01

  
셸브

  
shelve하면 VM을 끄고 루트 디스크를 이미지로 보관합니다(부팅 볼륨이면 볼륨 그대로). shelved_offload_time(기본 0 = 즉시) 뒤 호스트에서 내려가 SHELVED_OFFLOADED가 되면 호스트 자원(Placement 할당)이 반납됩니다. unshelve 때는 새로 스케줄링되므로 다른 호스트로 갈 수 있고, 자리가 없으면 실패할 수 있습니다.

  
openstack server shelve app-01
openstack server unshelve app-01               # 최신 마이크로버전에서는 가용 영역·호스트 지정도 가능







  
섹션 8

  
콜드 vs 라이브 마이그레이션

  

    
종류VM 상태디스크는언제

    
      
콜드 마이그레이션정지 후 이동, 대상에서 다시 시작공유 저장소(Ceph)·볼륨이면 이동 없음, 로컬이면 SSH로 복사라이브가 불가능한 VM, 다운타임 허용 시

      
라이브 마이그레이션 (공유 저장소·볼륨)실행 중 이동, 마지막에 아주 짧게 멈춤Ceph·볼륨이라 이동 없음, 메모리만 복사노드 점검, 부하 재배치 (가장 흔함)

      
블록 라이브 마이그레이션실행 중 이동로컬 디스크를 네트워크로 복사하면서 이동로컬 디스크 환경. 시간과 네트워크 부하가 큼

    
  

  
라이브 마이그레이션은 이렇게 진행된다

  
    
    
  1. 사전 확인: 대상 호스트 선택(지정하거나 스케줄러), CPU 호환성, 저장소 종류 확인.
    2. 
    
  2. 대상 준비 (pre-live-migration): 대상 노드에서 볼륨 연결, 네트워크 포트를 대상 호스트용으로도 준비(포트 바인딩을 미리 하나 더 만들어 둠).
    3. 
    
  3. 메모리 복사 반복 (pre-copy): 실행 중인 VM의 메모리를 통째로 보내고, 그동안 바뀐(dirty) 페이지를 다시 보내기를 반복합니다.
    4. 
    
  4. 전환 (switch-over): 남은 양이 허용 멈춤 시간(live_migration_downtime, 기본 500ms) 안에 보낼 만큼 줄면 VM을 잠깐 멈추고 나머지를 보낸 뒤 대상에서 재개합니다.
    5. 
    
  5. 정리 (post): 포트 바인딩을 대상으로 활성화, 원본 호스트 정리, Placement 할당 이동.
    6. 
  

  

    
조정값 (컴퓨트 nova.conf [libvirt])뜻업스트림 기본

    
      
live_migration_downtime · _steps · _delay허용 멈춤 시간과, 그 목표를 단계적으로 늘리는 방식500ms · 10단계 · 75초

      
live_migration_completion_timeout메모리 GiB당 최대 진행 시간(초). 넘으면 live_migration_timeout_action(중단 또는 강제 완료)800초/GiB

      
live_migration_permit_auto_converge복사가 따라잡지 못하면 VM CPU를 점점 늦춰 dirty 속도를 줄임꺼짐

      
live_migration_permit_post_copy일정 시점 후 먼저 대상에서 실행하고 남은 페이지는 필요할 때 가져옴. 거의 항상 완료되지만 그동안 성능 저하, 중간에 망이 끊기면 VM이 재시작됨꺼짐

      
live_migration_with_native_tlsQEMU 자체 TLS로 메모리 복사 스트림 암호화 (권장)꺼짐 (PKI 필요)

    
  

  
배포 제품은 이 값들을 업스트림과 다르게 기본 설정할 수 있으므로 RHOSO 환경의 실제 nova.conf(/etc/nova/nova.conf.d/)를 확인하세요. 바꿀 때는 9편의 nova-extra-config 방식으로 넣습니다.

  
openstack server migrate --live-migration app-01                 # 스케줄러가 대상 선택 (권장)
openstack server migrate --live-migration --host compute-3 app-01 # 대상 지정 (검증 포함)
openstack server migrate --live-migration --block-migration app-01 # 로컬 디스크 환경
openstack server migration list --server app-01
openstack server migration show app-01 <마이그레이션 ID>          # 남은 메모리량 등 진행 상황
openstack server migration force complete app-01 <마이그레이션 ID> # 마무리 강제 (잠깐 멈춤)
openstack server migration abort app-01 <마이그레이션 ID>

섹션 10

  
노드 비우기와 대피

  
계획된 점검: 노드 비우기 (drain)

  
    
    
  1. 새 배치 막기: openstack compute service set --disable --disable-reason "점검 #1234" compute-2.example.com nova-compute
    2. 
    
  2. 그 노드의 VM 목록 확인: openstack server list --all-projects --host compute-2.example.com
    3. 
    
  3. 하나씩(또는 몇 개씩) 라이브 마이그레이션. 실패하는 VM은 원인 확인 후 콜드 마이그레이션이나 고객 협의.
    4. 
    
  4. VM이 0개인지 확인하고 점검(커널 업데이트, 하드웨어 교체 등). 노드 재부팅이 필요한 데이터 플레인 작업은 26편.
    5. 
    
  5. 점검 후 다시 받기: openstack compute service set --enable compute-2.example.com nova-compute
    6. 
  

  
예기치 못한 장애: 대피 (evacuate)

  
컴퓨트 노드가 죽어 그 위 VM에 접근할 수 없을 때, 관리자가 다른 노드에서 VM을 다시 만들게 하는 것이 대피입니다.

  
    
    
  1. 노드가 정말 죽었는지(펜싱) 확인합니다. 살아 있는데 대피하면 같은 디스크를 두 VM이 쓰는 사고가 납니다.
    2. 
    
  2. Nova에 노드가 내려갔음을 알립니다: openstack compute service set --down compute-2.example.com nova-compute (강제 down 표시)
    3. 
    
  3. VM별로 대피: 클라이언트 버전에 따라 openstack server evacuate <VM> 또는 nova evacuate <VM>. Ceph·볼륨 부팅 VM은 디스크가 보존되고, 로컬 임시 디스크 VM은 새로 만들어집니다(데이터 손실).
    4. 
    
  4. 노드가 복구되면 남은 흔적을 정리한 뒤 강제 down을 해제합니다(--up).
    5. 
  

  

    
자동으로 해 주는 것은 Instance HA

    
기본 Nova는 노드가 죽어도 VM을 자동으로 살리지 않습니다. 이 과정을 자동화하는 것이 Instance HA이며, 펜싱(죽은 노드 확실히 끄기)이 핵심입니다. 27편에서 다룹니다.

호스트 집계와 가용 영역

  

    
구분호스트 집계 (aggregate)가용 영역 (AZ)

    
      
누가 보나관리자만사용자에게 보임 (생성 시 선택)

      
정체호스트 묶음 + key=value 메타데이터availability_zone 메타데이터가 붙은 집계

      
겹침한 호스트가 여러 집계에 속할 수 있음한 호스트는 하나의 AZ에만

설계 패턴

  

    
요구방법주의

    
      
등급별 노드 (일반·프리미엄·GPU)집계 메타데이터 + 플레이버 extra spec, 또는 Placement trait (trait:CUSTOM_PREMIUM=required)“들어오게”만 하면 일반 VM도 프리미엄 노드에 들어갈 수 있음 → 격리도 필요

      
등급 노드에 다른 VM이 못 들어오게 (격리)집계 메타데이터에 trait:CUSTOM_PREMIUM=required + [scheduler] enable_isolated_aggregate_filtering해당 trait를 요구하지 않는 요청은 그 집계를 피함

      
고객 전용 노드집계 메타데이터 filter_tenant_id=<프로젝트 ID> + [scheduler] limit_tenants_to_placement_aggregate그 고객만 들어오게 하는 것과, 그 고객이 그 노드에만 가게 하는 것은 별개 설정

AZ를 지정하지 않은 VM

섹션 12

  
NUMA · CPU 고정 · 휴즈페이지 개요

  
NUMA란

  
소켓이 둘인 서버는 메모리가 소켓마다 붙어 있습니다. CPU가 자기 소켓의 메모리를 읽으면 빠르고, 다른 소켓 메모리를 읽으면 느립니다. 이 구조를 NUMA라고 하고, 소켓 하나와 그 메모리를 NUMA 노드라고 부릅니다. 성능이 중요한 VM은 vCPU와 메모리를 같은 NUMA 노드 안에 두어야 합니다.

  

    
기능플레이버 extra spec (이미지 속성)호스트 준비

    
      
CPU 고정hw:cpu_policy=dedicated (hw_cpu_policy)[compute] cpu_dedicated_set → Placement에 PCPU 보고 (9편)

      
하이퍼스레드 처리hw:cpu_thread_policy=prefer|isolate|requireSMT(하이퍼스레딩) 켜짐 여부와 맞춤

      
에뮬레이터 스레드 분리hw:emulator_threads_policy=share|isolatecpu_shared_set에 공유 코어 확보

      
NUMA 노드 수hw:numa_nodes=1|2—

      
휴즈페이지hw:mem_page_size=large|2MB|1GB커널 인자로 휴즈페이지 미리 확보, reserved_huge_pages

정리와 다음 편

  
오늘의 핵심 여덟 문장

  
    
    
  • 상태는 vm_state(안정 상태) · task_state(진행 단계) · power_state(실제 전원) 세 칸으로 읽는다.
    • 
    
  • 생성은 API → 상위 conductor → scheduler·Placement → cell1 conductor → nova-compute → Neutron·Glance·Cinder → libvirt → 게스트의 14단계이며, 요청 ID·인스턴스 UUID로 로그를 꿴다.
    • 
    
  • 오류 메시지는 실패 단계의 지문이다. No valid host(배치), Failed to allocate the network(VIF 대기), Exceeded maximum retries(재시도 소진).
    • 
    
  • stop은 자원을 붙잡고, shelve(offload)는 반납한다. 리사이즈는 확인 전까지 양쪽을 점유한다.
    • 
    
  • 라이브 마이그레이션은 메모리 반복 복사 → 짧은 멈춤 → 전환. dirty 속도가 망 속도를 넘으면 수렴하지 않는다(auto-converge·post-copy·망 증설).
    • 
    
  • 점검은 disable → 비우기 → 작업 → enable. 죽은 노드는 펜싱 확인 후 force down → evacuate.
    • 
    
  • 집계(관리자용, 여러 개 가능)와 AZ(사용자용, 호스트당 하나). 등급 노드는 “들어오게”와 “못 들어오게(격리)”를 함께 설정.
    • 
    
  • 성능 VM은 CPU 고정(PCPU) + 같은 NUMA 노드 + 휴즈페이지. RHOSO에서는 NodeSet 커널 인자·tuned·재부팅으로 준비한다.
