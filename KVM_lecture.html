    Chapter 01

    가상화란 무엇인가 — 하드웨어를 속이는 기술

    KVM을 배우기 전에 "하이퍼바이저"라는 단어의 의미부터 정확히 잡습니다.

    서버 한 대에 CPU 64코어, 메모리 512GB가 있다고 합시다. 애플리케이션 하나를 올리면 대부분의 자원이 놀게 됩니다. 그래서 우리는 이 물리 서버 하나를 여러 대의 독립된 컴퓨터처럼 쪼개서 씁니다. 이것이 가상화입니다.

    쪼개는 주체를 하이퍼바이저(Hypervisor) 또는 VMM(Virtual Machine Monitor)이라고 부릅니다. 하이퍼바이저의 일은 딱 하나로 요약됩니다 — 게스트 OS가 "내가 물리 하드웨어를 직접 쓰고 있다"고 착각하게 만드는 것. 착각이 깨지지 않도록 CPU·메모리·디스크·네트워크를 흉내 내거나 중개해 줍니다.

    Type 1 vs Type 2 — 이 분류가 KVM에서 애매해지는 이유

    핵심 포인트 KVM은 Type 1.5로 불립니다. 리눅스 커널 자체가 하이퍼바이저가 되므로 게스트는 하드웨어 위 커널을 바로 타지만(Type 1의 성격), 그 커널은 동시에 범용 OS로도 동작합니다(Type 2의 성격). "리눅스 커널을 하이퍼바이저로 승격시킨다"가 가장 정확한 표현입니다.

    가상화의 3대 자원 문제

    CPU

    게스트가 HLT, CPUID처럼 특권 명령을 실행하면? 실제로 실행하게 두면 호스트가 멈춥니다. 가로채서 흉내 내야 합니다.

    메모리

    게스트는 자기 물리주소가 0번지부터라고 믿습니다. 게스트 물리주소 → 호스트 물리주소 변환 표가 한 겹 더 필요합니다.

    I/O

    게스트 안의 드라이버가 "이 포트에 값을 써라"라고 하면, 그 디스크·NIC를 누군가 소프트웨어로 흉내 내야 합니다.

    이 세 문제 중 CPU와 메모리는 KVM(커널)이, I/O는 QEMU(유저 공간)가 담당합니다. 이 한 줄이 이 강의 전체의 뼈대입니다. 색으로 기억하세요 — 커널 = CPU/메모리 유저 = 장치

    Check 1

    KVM을 Type 1.5로 부르는 가장 큰 이유는?

    정답 B. 전용 하이퍼바이저 커널을 따로 만들지 않고, 리눅스 커널에 kvm.ko 모듈을 넣어 하이퍼바이저 능력을 부여합니다. 그래서 하드웨어에 직접 붙는 Type 1의 성능과, 리눅스의 드라이버·스케줄러·파일시스템 생태계를 동시에 얻습니다.

    KVM이 하는 일 / 하지 않는 일

    KVM 하는 일

    • CPU를 게스트 모드로 진입/이탈시키기
    • 특권 명령 트랩 처리 (VM Exit)
    • EPT/NPT로 게스트 메모리 주소 변환
    • vCPU를 리눅스 스레드로 만들어 스케줄링
    • 인터럽트 컨트롤러(APIC) 가상화
    • 성능에 직결되는 것만, 최소한으로

    KVM 하지 않는 일

    • 가상 디스크·NIC·그래픽카드 흉내 내기
    • BIOS/UEFI 부팅 처리
    • VNC/SPICE 콘솔 제공
    • 스냅샷·라이브 마이그레이션 오케스트레이션
    • 명령줄 UI, 관리 API
    → 전부 QEMU와 libvirt의 몫입니다

    엔지니어의 직관 "KVM은 가속기다"라고 이해하면 편합니다. 혼자서는 VM을 만들 수 없고, 유저 공간 프로그램(QEMU 등)이 /dev/kvm을 통해 부탁해야 비로소 동작하는 커널 서비스입니다.

    하드웨어 가상화 확장이 게임을 바꿨다

    2005년 이전에는 하드웨어 도움이 없어서, 게스트 커널 코드를 실행 직전에 안전한 코드로 바꿔치기하는 바이너리 트랜슬레이션(초기 VMware)이나, 게스트 커널을 아예 수정하는 준가상화(Paravirtualization, 초기 Xen)가 필요했습니다. 둘 다 어렵고 느렸습니다.

    Intel VT-x / AMD-V가 등장하면서 CPU에 게스트 모드라는 새 실행 모드가 생겼습니다. 게스트 코드를 그대로 CPU에 던져도, 위험한 명령을 만나는 순간 CPU가 알아서 하이퍼바이저에게 제어를 되돌려 줍니다. KVM은 처음부터 이 하드웨어 기능만 사용하도록 설계됐기 때문에, 코드가 놀라울 정도로 작습니다.

    Intel VT-x
    VMX 모드, VMXON/VMLAUNCH/VMRESUME 명령, VMCS 구조체
    AMD-V (SVM)
    VMRUN 명령, VMCB 구조체
    EPT / NPT
    2단계 페이지 테이블. 게스트 물리주소→호스트 물리주소를 하드웨어가 변환 (Intel: EPT, AMD: NPT)
    VT-d / AMD-Vi
    IOMMU. 물리 PCI 장치를 VM에 직접 붙일 때(GPU passthrough) 필수
    SR-IOV
    NIC 하나를 여러 개의 가상 함수(VF)로 쪼개 VM에 직접 할당
    ARM64
    EL2 (Hyp mode) + Stage-2 translation. ARM 서버·DGX 계열에서도 KVM 동작
    현장에서 가장 흔한 실수 클라우드 VM 안에서 다시 KVM을 쓰려는데 /dev/kvm이 없다 → Nested Virtualization이 꺼져 있습니다. AWS는 *.metal 인스턴스만 지원, GCP는 라이선스 플래그가 필요하고, 온프렘 VMware의 VM이면 "Expose hardware assisted virtualization to the guest OS" 옵션을 켜야 합니다.
    Chapter 03

    동작 원리 — VM Exit과 vCPU 스레드

    면접에서 "KVM 내부 동작을 설명해 보세요"라는 질문이 나오면 이 챕터를 말하면 됩니다.

    세 개의 실행 모드

    KVM은 CPU 실행 상태를 세 가지로 나눕니다. 이 삼각형을 오가는 것이 VM의 인생 전부입니다.

    실제 코드 흐름 — QEMU가 KVM에 부탁하는 방법

    놀랍게도 KVM API는 ioctl() 몇 개뿐입니다. 개념을 보여 주는 최소 코드입니다.

    /* ① KVM 서브시스템 열기 */
int kvm = open("/dev/kvm", O_RDWR);

/* ② VM 컨테이너 생성 — 아직 CPU도 메모리도 없음 */
int vmfd = ioctl(kvm, KVM_CREATE_VM, 0);

/* ③ 게스트 메모리 등록: QEMU가 mmap한 영역을
      "게스트의 물리주소 0번지"라고 KVM에 알려 줌 */
void *mem = mmap(NULL, 1<<30, PROT_READ|PROT_WRITE,
                  MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
struct kvm_userspace_memory_region region = {
    .guest_phys_addr = 0x0,
    .memory_size     = 1<<30,
    .userspace_addr  = (uint64_t)mem,   /* ← 핵심! */
};
ioctl(vmfd, KVM_SET_USER_MEMORY_REGION, &region);

/* ④ vCPU 생성 — 반환된 fd 하나가 vCPU 하나 */
int vcpufd = ioctl(vmfd, KVM_CREATE_VCPU, 0);

    /* QEMU는 vCPU 하나마다 pthread 하나를 만들고,
   그 스레드는 평생 이 루프를 돕니다 */

while (1) {
    ioctl(vcpufd, KVM_RUN, 0);   /* ← 여기서 게스트 모드로 진입.
                                    게스트 코드가 실제 CPU에서 실행됨.
                                    VM Exit이 나야 이 호출이 반환됨 */

    switch (run->exit_reason) {
    case KVM_EXIT_IO:        /* 게스트가 in/out 명령 실행 */
        emulate_device_io(run->io.port, run->io.data);
        break;
    case KVM_EXIT_MMIO:      /* 가상 장치 레지스터 접근 */
        emulate_mmio(run->mmio.phys_addr);
        break;
    case KVM_EXIT_HLT:       /* 게스트가 idle → 스레드 sleep */
        return;
    }
}
/* 여기서 얻는 통찰:
   vCPU = 그냥 리눅스 스레드
   → top/htop 에 보이고, taskset 으로 핀 고정 가능하고,
     리눅스 CFS 스케줄러가 다른 프로세스와 똑같이 스케줄링합니다. */

    # 실행 중인 VM의 VM Exit 통계를 직접 봅니다 (root 필요)
$ sudo mount -t debugfs none /sys/kernel/debug 2>/dev/null
$ sudo cat /sys/kernel/debug/kvm/*/vcpu0/*exits* 2>/dev/null

# 더 편한 실시간 도구 (kvm_stat)
$ sudo kvm_stat --once

kvm_entry                    412095    3512
kvm_userspace_exit             1204      12   ← 유저공간까지 간 비싼 Exit
kvm_mmio                        903       9

# vCPU가 정말 스레드인지 확인
$ ps -eLo pid,tid,comm | grep -E 'qemu|CPU'

    QEMU와의 관계 — 가장 많이 헷갈리는 부분

    "KVM을 쓴다"는 말은 사실상 "QEMU를 KVM 가속으로 쓴다"는 뜻입니다. 왜 그런지 확실히 정리합니다.

    QEMU(Quick EMUlator)는 KVM보다 먼저(2003년) 나온 완전한 하드웨어 에뮬레이터입니다. CPU 명령어부터 메인보드 칩셋, IDE 컨트롤러, e1000 NIC, VGA 카드까지 전부 소프트웨어로 흉내 냅니다. x86 호스트에서 ARM이나 RISC-V 시스템을 부팅할 수 있을 정도로 완전합니다. 대신 아주 느립니다.

    QEMU 단독 (TCG 모드)

    게스트 명령어를 하나하나 읽어 호스트 명령어로 번역(Tiny Code Generator)합니다. CPU 아키텍처가 달라도 실행 가능하지만 네이티브 대비 5~20배 느립니다.
    → 용도: 크로스 아키텍처 개발, 임베디드 펌웨어 디버깅, ARM 이미지 빌드

    QEMU + KVM (-accel kvm)

    CPU 명령어 실행은 KVM에 위임하고, QEMU는 장치 에뮬레이션·관리만 담당합니다. 게스트 아키텍처가 호스트와 같아야 하지만 네이티브의 95~98% 성능이 나옵니다.
    → 용도: 모든 프로덕션 서버 가상화

    virtio — "게스트야, 우리 서로 VM인 걸 알잖아"

    에뮬레이션의 근본 문제는 게스트가 진짜 하드웨어라고 믿기 때문에 불필요한 절차를 다 밟는다는 점입니다. 실제 IDE 디스크처럼 레지스터를 한 바이트씩 쓰고, 인터럽트를 기다립니다. 그때마다 VM Exit이 발생합니다.

    virtio는 접근법을 뒤집습니다. 게스트 드라이버가 처음부터 "나는 가상 환경이다"라고 인정하고, 하드웨어 흉내를 포기하는 대신 공유 메모리 링 버퍼(virtqueue)에 요청을 쌓아 한 번에 알립니다. Exit 횟수가 수십 분의 일로 줄어듭니다.

    장치에뮬레이션(호환용)virtio(권장)실무 선택 기준
    디스크ide, sata, nvmevirtio-blk, virtio-scsi단순·최고속=blk / 디스크 다수·TRIM·핫플러그=scsi
    네트워크e1000, rtl8139virtio-net (+vhost-net)기본은 virtio-net. 초고속은 SR-IOV/DPDK
    그래픽vga, qxlvirtio-gpu서버는 콘솔만 있으면 충분
    메모리—virtio-balloon오버커밋 환경에서 회수용. DB 서버엔 비권장
    엔트로피—virtio-rng필수 수준. 없으면 부팅·TLS 핸드셰이크가 느려짐

    Chapter 05

    libvirt — 실무에서 실제로 만지는 층

    아무도 프로덕션에서 qemu 명령줄을 직접 치지 않습니다. 그 이유와 대안을 봅니다.

    위 3번째 탭의 옵션 문자열을 보셨죠. 저것을 VM 수백 개에 손으로 관리한다는 건 불가능합니다. 그래서 libvirt가 있습니다. libvirt는 하이퍼바이저를 추상화하는 관리 API + 데몬 + XML 정의의 집합입니다.

    libvirt가 대신 해 주는 것

    선언적 정의

    VM 스펙을 XML로 저장. 재부팅해도 유지되고, 백업·Git 관리·자동화가 가능합니다.

    스토리지 풀

    디렉터리·LVM·NFS·iSCSI·Ceph RBD를 동일한 방식으로 볼륨 생성/삭제/복제.

    가상 네트워크

    NAT 브리지 virbr0, dnsmasq DHCP, 브리지·OVS·SR-IOV 풀 관리.

    보안 격리

    VM별 SELinux(svirt) 레이블·AppArmor 프로파일·cgroup 자동 적용.

    라이브 마이그레이션

    QEMU 마이그레이션 프로토콜을 안전하게 오케스트레이션.

    안정적 API

    QEMU 옵션이 버전마다 바뀌어도 libvirt XML 스키마는 호환을 유지.

conn = libvirt.open("qemu:///system")

# 1) 실행 중 VM의 실시간 CPU/메모리 사용

    # 블록 디바이스 I/O 통계
    for disk in ET.fromstring(dom.XMLDesc()).findall(".//disk/target"):

        rd_req, rd_b, wr_req, wr_b, err = dom.blockStats(d)
        print(f"   {d}: read={rd_b/1e6:.1f}MB write={wr_b/1e6:.1f}MB")

        print(f"[ALERT] {dom.name()} stopped, detail={detail}")

libvirt.virEventRegisterDefaultImpl()
conn.domainEventRegisterAny(None, libvirt.VIR_DOMAIN_EVENT_ID_LIFECYCLE,
                            on_lifecycle, None)
while True:
    libvirt.virEventRunDefaultImpl()

    성능 튜닝 — VM Exit을 줄이는 다섯 가지 무기

    "KVM이 느리다"는 신고의 90%는 설정 문제입니다. 점검 순서를 정해 둡니다.

    ① virtio 전면 적용

    디스크·NIC·RNG·balloon 모두 virtio로. 여기서 나오는 개선폭이 나머지 전부를 합친 것보다 큽니다. 가장 먼저 확인하세요.

    ② CPU 모델 & 토폴로지

    host-passthrough로 AES-NI·AVX 노출. 소켓/코어/스레드를 물리 구조와 맞춰 게스트 스케줄러가 올바르게 판단하도록.

    ③ NUMA 정렬 & CPU 핀 고정

    vCPU와 메모리를 같은 NUMA 노드에 묶습니다. 노드를 넘는 메모리 접근은 지연이 1.5~2배.

    ④ Hugepages

    4KB → 2MB/1GB 페이지로 TLB 미스와 EPT 워크 감소. 메모리 집약 워크로드에서 5~15% 개선.

    ⑤ vhost / 멀티큐

    네트워크·블록 처리를 커널에서 종결시키고, 큐 수를 vCPU 수에 맞춰 락 경합을 분산.

    ⑥ I/O 스레드 분리

    iothread를 지정해 디스크 처리를 vCPU 스레드와 분리하면 지연 편차(jitter)가 줄어듭니다.

    게스트에서 vmstat의 st(steal) 값이 지속적으로 20%입니다. 원인으로 가장 유력한 것은?

    정답 C. steal time은 "vCPU가 실행하고 싶었지만 호스트 스케줄러가 물리 CPU를 주지 않은 시간"입니다. vCPU가 리눅스 스레드라는 사실을 떠올리면 바로 이해됩니다. 해결책은 VM 재배치, vCPU 수 축소, CPU 핀 고정, 또는 호스트 증설입니다.

    ① OpenStack — KVM을 수천 노드로 확장하기

    OpenStack의 컴퓨트 서비스 Nova는 기본 하이퍼바이저로 KVM을 씁니다. 사용자가 "인스턴스 생성" 버튼을 누르면 일어나는 일:

    1. Nova API가 요청을 받아 DB에 기록 → 메시지 큐로 스케줄러 호출
    2. nova-scheduler가 필터·가중치로 배치할 컴퓨트 노드 선택 (CPU·RAM·AZ·어피니티)
    3. 해당 노드의 nova-compute가 Glance에서 이미지를, Cinder에서 볼륨(Ceph RBD)을, Neutron에서 포트(OVS)를 확보
    4. 수집한 정보로 libvirt 도메인 XML을 생성하고 virDomainCreateXML() 호출
    5. libvirtd가 QEMU 프로세스를 띄우고, QEMU가 /dev/kvm으로 vCPU를 실행 → VM 부팅

    ③ AI·MLOps 인프라에서의 KVM

    GPU 워크로드는 보통 컨테이너로 돌리지만, KVM이 필요한 시나리오가 분명히 있습니다.

    • 테넌트 격리가 필요한 GPU 제공 — 고객사별로 GPU를 VM에 passthrough하면 드라이버 버전 충돌 없이 완전 분리됩니다.
    • 커널 버전이 다른 프레임워크 검증 — 특정 CUDA·드라이버 조합이 특정 커널을 요구할 때, VM으로 조합을 병렬 검증합니다.
    • vGPU / MIG 조합 — NVIDIA vGPU로 하나의 물리 GPU를 여러 VM에 시분할 제공하거나, A100/H100의 MIG 인스턴스를 VM에 할당합니다.
    • 기밀 AI 추론 — AMD SEV-SNP나 Intel TDX 기반 Confidential VM 안에서 모델과 데이터를 암호화 상태로 처리합니다. 호스트 관리자조차 메모리를 볼 수 없어, 규제 산업의 LLM 서비스에 활용됩니다.
    • ARM 기반 AI 노드 — Grace 계열 ARM64 서버에서도 KVM이 동작하므로, x86과 동일한 libvirt 워크플로로 관리할 수 있습니다.
    실무 팁: passthrough와 라이브 마이그레이션은 상충합니다 GPU·SR-IOV VF를 직접 할당한 VM은 하드웨어 상태를 옮길 수 없어 라이브 마이그레이션이 불가합니다. 따라서 설계 시 "고성능 노드 풀(passthrough, 마이그레이션 없음)"과 "일반 노드 풀(virtio, 마이그레이션 가능)"을 분리하는 것이 정석입니다. 이 결정을 나중에 바꾸기는 매우 어렵습니다.

    자주 묻는 질문

    KVM과 QEMU 중 무엇을 설치해야 하나요?

    KVM은 이미 커널에 있으므로 설치할 것은 QEMU와 libvirt입니다. qemu-kvm이라는 패키지 이름 때문에 헷갈리지만, 이 패키지는 "KVM 가속을 지원하도록 빌드된 QEMU"입니다. Ubuntu 최신 버전에서는 qemu-system-x86이 실제 알맹이입니다.

    VM 안에서 또 VM을 띄울 수 있나요? (Nested)

    가능하지만 성능이 떨어지고 안정성 보장이 약합니다. 호스트에서 cat /sys/module/kvm_intel/parameters/nested가 Y여야 하고, 게스트 XML의 CPU가 host-passthrough여야 합니다. CI에서 컨테이너 안에 VM을 띄우는 시나리오나 교육용으로 쓰이며, 프로덕션 워크로드용으로는 권장하지 않습니다.

    VM이 사용하는 실제 메모리를 어떻게 확인하나요?

    게스트에 할당한 값이 아니라 호스트에서 실제 점유한 RSS를 봐야 합니다. virsh domstats vm-01 --balloon의 balloon.rss, 또는 호스트에서 ps -o rss= -p $(pgrep -f 'guest=vm-01')를 확인합니다. hugepages를 쓰면 RSS 계산이 달라지므로 /proc/meminfo의 HugePages_Free 감소분으로 판단하는 것이 정확합니다.

    VMware에서 KVM으로 어떻게 옮기나요?

    virt-v2v가 표준 도구입니다. vCenter에 직접 연결해 VM을 가져오면서 VMware Tools 제거, virtio 드라이버 주입, 부트로더 수정까지 자동 처리합니다.
    virt-v2v -ic vpx://user@vcenter/DC/Cluster/esxi -o libvirt -os default -of qcow2 vm-name
    Windows VM은 virtio-win이 호스트에 설치돼 있어야 드라이버 주입이 됩니다. 대량 이관은 MTV(Migration Toolkit for Virtualization)를 검토하세요.

    호스트를 재부팅해야 하는데 VM들은 어떻게 처리하죠?

    정석은 ① 다른 호스트로 라이브 마이그레이션, ② 불가하면 게스트 에이전트를 통한 정상 종료입니다. libvirt-guests 서비스를 활성화하면 호스트 종료 시 VM을 자동으로 suspend 또는 shutdown하고 부팅 시 복구해 줍니다. virsh destroy는 전원 코드를 뽑는 것과 같아 파일시스템 손상 위험이 있으니 최후 수단으로만 씁니다.

    KVM은 보안상 안전한가요?

    하드웨어 가상화 경계 덕분에 컨테이너보다 격리가 강하지만, 만능은 아닙니다. 실무 권고 사항: ① 호스트 커널·QEMU 보안 패치를 최우선 적용(QEMU 장치 에뮬레이션 취약점이 VM 탈출 경로가 됩니다), ② SELinux/svirt 또는 AppArmor를 반드시 활성화, ③ 불필요한 에뮬레이션 장치 제거(-nodefaults), ④ VNC/SPICE는 localhost 리스닝 + SSH 터널, ⑤ 민감 워크로드는 SEV-SNP/TDX 기반 Confidential VM 검토.

    정리와 종합 점검

    한 문장으로 요약하면

    KVM은 리눅스 커널을 하이퍼바이저로 만드는 모듈로 CPU·메모리 가상화만 담당하고, QEMU가 유저 공간에서 장치와 부팅을 맡고, libvirt가 그 위에서 관리 API를 제공합니다. 그리고 OpenStack·KubeVirt·클라우드는 모두 이 세 층을 감싼 오케스트레이션입니다.

    기억할 개념 5개

    1. Type 1.5 = 커널이 하이퍼바이저
    2. VM = 프로세스, vCPU = 스레드
    3. VM Exit이 성능의 전부
    4. virtio = 하드웨어 흉내 포기
    5. libvirt XML = 선언적 정의

    손에 익혀야 할 명령 5개

    virt-host-validate
    virt-install --import
    virsh edit / dumpxml
    virsh console
    kvm_stat

    다음 학습 경로

    → Proxmox VE로 클러스터 감각 익히기
    → OpenStack(DevStack) 한 번 설치
    → KubeVirt로 K8s와 VM 통합
    → SR-IOV·DPDK로 NFV 성능
    → SEV-SNP/TDX 기밀 컴퓨팅

    종합 퀴즈

    6문항입니다. 5개 이상 맞히면 기초는 확실히 잡힌 것으로 봐도 좋습니다.

    Final 1 / 6

    libvirt 도메인 XML에서 <domain type='qemu'>로 정의하면 어떻게 되나요?

    정답 B. type='kvm'이어야 /dev/kvm 가속을 씁니다. "VM이 이유 없이 엄청 느리다"는 신고에서 제일 먼저 확인해야 할 한 줄입니다.
    Final 2 / 6

    vhost-net을 사용하는 목적은?

    정답 C. virtio 백엔드를 커널의 vhost 스레드로 옮기는 것입니다. A는 SR-IOV/passthrough, B는 NAT의 설명입니다.
    Final 3 / 6

    GPU를 VM에 passthrough하려면 반드시 필요한 하드웨어 기능은?

    정답 A. IOMMU가 있어야 장치의 DMA 주소를 안전하게 격리·변환할 수 있습니다. EPT/NPT는 메모리 가상화용이고, 이미 KVM 기본 동작에 쓰입니다.
    Final 4 / 6

    골든 이미지를 만들 때 virt-sysprep을 실행하지 않으면 생기는 문제는?

    정답 B. 같은 machine-id를 가진 VM들은 systemd·DHCP·로그 수집·자산 관리 도구에서 서로를 덮어씁니다. SSH 호스트키 중복은 MITM 탐지를 무력화합니다.
    Final 5 / 6

    라이브 마이그레이션이 계속 완료되지 않고 반복될 때(수렴 실패) 가장 적절한 조치는?

    정답 C. 메모리 변경 속도가 전송 속도보다 빨라 남은 페이지가 줄지 않는 상황입니다. auto-converge는 vCPU를 스로틀해 변경 속도를 낮추고, post-copy는 먼저 전환한 뒤 부족한 페이지를 요구 시 가져옵니다. A는 무중단 목표를 스스로 포기하는 선택입니다.
    Final 6 / 6

    OpenStack 인스턴스가 부팅에 실패했습니다. 컴퓨트 노드에서 가장 먼저 볼 로그는?

    정답 B. QEMU 프로세스가 왜 죽었는지(장치 오류, 파일 권한, hugepage 부족, 이미지 손상)가 가장 직접적으로 기록됩니다. C는 게스트가 부팅조차 못 했으면 존재하지 않습니다. Nova 로그는 그다음입니다.
