01 FOUNDATION

🐘 Postgres와 EDB의 정체

RDBMS, PostgreSQL, EPAS(Enterprise Postgres)의 관계를 가장 먼저 구분합니다.

🧒 중학생 비유

학교 도서관을 생각해 보세요. 책장이 Table, 책 한 권이 Row, 책의 항목(제목·저자·ISBN)이 Column입니다. DBMS는 도서관 사서처럼 데이터를 정리하고 찾아줍니다.

1. Database / DBMS / RDBMS

  • Database: 데이터를 모아 둔 저장소.
  • DBMS: 데이터베이스를 생성·조회·수정·보호하는 소프트웨어.
  • RDBMS: 데이터를 주로 Table(관계) 형태로 관리하는 DBMS.

2. PostgreSQL과 Enterprise Postgres

PostgreSQL은 오픈소스 객체-관계형 데이터베이스입니다. EDB의 Enterprise Postgres (Oracle Compatible), 즉 전통적으로 불리던 EDB Postgres Advanced Server(EPAS)는 PostgreSQL 기반에 엔터프라이즈 기능과 Oracle 호환 기능을 추가합니다.

구분PostgreSQLEnterprise Postgres (Oracle Compatible)
기반오픈소스 PostgreSQLPostgreSQL 기반
핵심 목적범용 RDBMS기업 운영 + Oracle 호환성 강화
추가 기능 예표준 Postgres 기능EDB Audit, Profile, SQL/Protect, Data Redaction, EDB*Loader, EDB*Plus 등
Oracle 마이그레이션애플리케이션 수정이 더 필요할 수 있음Oracle 호환 SQL·데이터 타입·도구로 수정량 감소 목표

3. 시험에서 자주 섞이는 말

Cluster ≠ Database
Postgres의 database cluster는 “한 서버 인스턴스가 관리하는 데이터베이스들의 집합 + 관련 파일”을 의미합니다. Kubernetes Cluster와 같은 뜻이 아닙니다.
🧠 한 줄 암기: PostgreSQL은 기반 엔진, Enterprise Postgres는 PostgreSQL을 확장한 EDB의 Oracle-Compatible 엔터프라이즈 DB.

06 HIGH

🔐 Transaction · MVCC · Lock

ACID, COMMIT/ROLLBACK, isolation, MVCC와 Lock의 관계를 이해합니다.

🧒 중학생 비유

온라인 쇼핑에서 ‘재고 1개 감소’와 ‘결제 1건 증가’가 한 묶음이라면 둘 다 성공해야 합니다. 하나만 성공하면 장부가 틀어집니다. 그 묶음이 Transaction입니다.

1. Transaction = All or Nothing

BEGIN;

UPDATE account SET balance = balance - 10000 WHERE id = 1;
UPDATE account SET balance = balance + 10000 WHERE id = 2;

COMMIT;
-- 중간에 문제가 생기면 ROLLBACK;

2. ACID

A · Atomicity전부 성공 또는 전부 취소
C · Consistency규칙을 깨지 않는 상태 유지
I · Isolation동시에 실행되어도 서로의 중간 상태 간섭 최소화
D · DurabilityCommit 결과는 장애 후에도 보존되어야 함

3. MVCC

MVCC(Multi-Version Concurrency Control)는 같은 데이터의 여러 버전을 활용하여 읽기와 쓰기의 불필요한 충돌을 줄이는 핵심 원리입니다. UPDATE/DELETE로 인해 더 이상 필요한 트랜잭션이 없는 오래된 tuple이 생길 수 있고, 이것이 VACUUM의 중요성과 연결됩니다.

4. Isolation Level

레벨쉽게강도
READ COMMITTED각 statement 시점에 commit된 데이터를 봄기본적으로 많이 사용
REPEATABLE READ한 transaction에서 더 일관된 snapshot더 강함
SERIALIZABLE직렬 실행과 같은 결과를 목표가장 강함, 재시도 필요 가능
Lock이 무조건 나쁜 것은 아닙니다. 동시성 데이터의 정합성을 지키는 안전장치입니다. 문제는 “필요 이상으로 오래 잡힌 Lock”이나 “서로 기다리는 Deadlock”입니다.
07 HIGH

🛡️ Role · 권한 · pg_hba.conf

로그인 인증(authentication)과 객체 권한(authorization)을 분리해서 이해합니다.

🧒 중학생 비유

학교 정문에서 학생증을 보여주는 것이 Authentication, 교무실에 들어갈 수 있는 권한이 있는지 확인하는 것이 Authorization입니다.

1. Authentication vs Authorization

Authentication“너 누구야?” — 접속 자체를 확인
Authorization“무엇을 할 수 있어?” — 객체 권한 확인

2. Role

CREATE ROLE app_login LOGIN PASSWORD 'StrongPassword';
CREATE ROLE app_readonly NOLOGIN;

GRANT app_readonly TO app_login;
GRANT CONNECT ON DATABASE school TO app_readonly;
GRANT USAGE ON SCHEMA public TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;

CREATE USER는 전통적으로 LOGIN 속성을 갖는 Role 생성의 편의 문법으로 이해하면 좋습니다.

3. pg_hba.conf 읽는 법

# TYPE  DATABASE  USER       ADDRESS          METHOD
host    school    app_login  10.10.0.0/16     scram-sha-256
hostssl all       all        0.0.0.0/0        scram-sha-256
필드질문
TYPElocal 소켓인가? TCP(host/hostssl)인가?
DATABASE어느 DB 접속인가?
USER어느 Role인가?
ADDRESS어디서 접속하는가?
METHOD어떤 인증 방식을 쓰는가?
⭐ 매우 중요: pg_hba.conf는 위에서 아래 순서로 처음 매칭되는 규칙이 중요합니다. “가장 구체적인 규칙을 자동으로 골라준다”라고 생각하면 틀리기 쉽습니다.

4. 최소 권한 원칙

애플리케이션 계정에 superuser를 주기보다 필요한 Database/Schema/Table 권한만 부여합니다.

effective_cache_sizePlanner가 사용 가능하다고 추정하는 캐시 규모 힌트실제 메모리 예약이 아님
max_connections동시 연결 상한과 관련증가 시 메모리 영향 고려
max_wal_sizecheckpoint 빈도에 영향을 주는 WAL 규모 목표WAL/Checkpoint 관련
checkpoint_timeoutcheckpoint 시간 간격 상한WAL/복구/IO와 연관
synchronous_commitcommit durability/latency trade-off에 영향성능만 보고 끄면 안 됨
effective_cache_size 함정: 이 값만큼 RAM을 “할당”하는 것이 아니라 optimizer가 OS cache 등을 포함한 캐시 가용성을 추정하도록 주는 힌트입니다.
09 HIGH

💾 WAL · Checkpoint · Tablespace

데이터가 디스크에 안전하게 기록되는 과정과 물리 저장 구조를 이해합니다.

🧒 중학생 비유

시험 답안지를 바로 최종 성적표에 쓰지 않고, 먼저 ‘변경 일지(WAL)’에 기록해 두면 정전이 나도 일지를 보고 복구할 수 있습니다.

1. WAL (Write-Ahead Logging)

핵심 원칙은 이름 그대로 데이터 파일 변경보다 먼저 변경 내용을 WAL에 안전하게 기록하는 것입니다. 이 덕분에 장애 후 crash recovery와 복구 기능의 기반을 마련합니다.

SQL 변경
→
WAL 기록
→
COMMIT
→
Data Page 반영

2. Checkpoint

Checkpoint는 메모리의 dirty page를 데이터 파일에 반영하는 작업과 복구 시작점을 관리하는 중요한 사건입니다. 너무 자주 발생하면 I/O 부담이 커지고, 너무 드물면 장애 복구에 처리할 WAL이 많아질 수 있습니다.

3. Tablespace

Tablespace는 데이터베이스 객체의 물리 파일을 기본 Data Directory 외의 다른 파일 시스템 위치에 배치할 수 있게 해주는 논리적 이름입니다.

CREATE TABLESPACE fastspace LOCATION '/fastdisk/pgdata';
CREATE TABLE big_log(id bigint, msg text) TABLESPACE fastspace;
🧠 연결 암기: WAL = 변경 일지, Checkpoint = 중간 정산, Tablespace = 물리 저장 위치 분산.
10 HIGH

🧹 VACUUM · ANALYZE · Autovacuum

MVCC가 남기는 dead tuple을 관리하고 통계 정보를 최신화하는 방법을 익힙니다.

🧒 중학생 비유

칠판에 내용을 수정할 때 예전 글씨를 덧칠만 하면 지저분해집니다. VACUUM은 더 이상 필요 없는 흔적을 정리하고, ANALYZE는 ‘어떤 자료가 얼마나 있는지’ 목록을 새로 작성합니다.

1. VACUUM

MVCC 환경에서는 UPDATE/DELETE 뒤에 예전 row version이 즉시 파일에서 사라지지 않습니다. 일반 VACUUM은 더 이상 필요 없는 tuple 공간을 재사용할 수 있도록 정리하고, transaction ID wraparound 방지에도 중요합니다.

2. VACUUM FULL

VACUUM FULL은 테이블을 다시 작성하여 공간을 운영체제에 돌려줄 수 있지만 더 강한 lock과 큰 작업 비용을 동반합니다. 일상적인 VACUUM과 같은 것으로 생각하면 안 됩니다.

3. ANALYZE

Planner가 더 좋은 실행 계획을 고를 수 있도록 데이터 분포 통계를 수집/갱신합니다.

VACUUM student;
ANALYZE student;
VACUUM (ANALYZE) student;

4. Autovacuum

변경량을 감시하여 VACUUM/ANALYZE를 자동 수행하는 핵심 운영 기능입니다. 운영 환경에서 단순히 “성능이 느려 보인다”는 이유로 끄는 것은 위험합니다.

작업주목적통계 갱신파일 축소
VACUUMdead tuple 공간 재사용/유지보수기본적으로 별도보통 OS에 직접 반환하지 않음
ANALYZEPlanner 통계 갱신YesNo
VACUUM ANALYZE둘 다Yes일반 VACUUM 특성
VACUUM FULL테이블 rewrite로 공간 회수옵션 조합 가능Yes 가능

🛟 Backup · Restore · PITR

논리 백업과 물리/PITR 계열을 구분하고 RPO/RTO 관점으로 이해합니다.

🧒 중학생 비유

논리 백업은 중요한 노트를 PDF로 다시 저장하는 것, 물리 백업은 노트북 SSD를 통째로 복제하는 것과 비슷합니다. PITR은 ‘어제 오후 3시의 상태’로 시간을 되돌리는 기능에 가깝습니다.

1. 논리 백업

도구범위/용도
pg_dump특정 database의 논리 백업
pg_restorecustom/directory/tar 형식 dump 복원
pg_dumpallcluster의 모든 database와 global object를 SQL 형식으로 덤프하는 데 사용
# custom format
pg_dump -Fc -d school -f school.dump

# 새 DB를 만든 뒤 복원
createdb school_restore
pg_restore -d school_restore school.dump

# plain SQL
pg_dump -Fp -d school > school.sql
psql -d school_restore < school.sql

2. 물리 백업과 PITR

PITR(Point-in-Time Recovery)는 일반적으로 base backup + 지속적으로 보관한 WAL을 조합하여 특정 시점까지 복구합니다.

Base Backup
+
Archived WAL
→
Recovery Target
→
특정 시점 복구

3. RPO / RTO

  • RPO: 어느 정도 데이터 손실까지 감수 가능한가?
  • RTO: 장애 후 얼마 만에 서비스가 살아나야 하는가?
⭐ 함정: pg_dump는 data directory를 통째로 복사하는 물리 백업 도구가 아닙니다. 반대로 PITR은 단순 SQL dump 복원과 다른 복구 전략입니다.

4. 백업은 “성공 로그”가 끝이 아니다

정기적인 restore test, 백업 보관주기, 암호화, 접근통제, 원격 보관, RPO/RTO 검증이 실제 운영에서 중요합니다.

⚡ Index · EXPLAIN · 성능 기초

Index의 장단점과 실행 계획 읽는 기초를 익힙니다.

🧒 중학생 비유

책 뒤의 찾아보기(Index)는 원하는 단어를 빨리 찾게 해주지만, 새 페이지가 추가될 때 찾아보기도 수정해야 합니다. DB Index도 조회는 빨라질 수 있지만 쓰기 비용과 저장공간이 늘어납니다.

1. Index는 공짜가 아니다

장점조건 검색, Join, 정렬 등에서 빠른 접근 가능
비용INSERT/UPDATE/DELETE 시 index 유지 비용 + 디스크

2. 대표 Index

  • B-tree: 등가/범위/정렬 등 일반적인 기본 선택.
  • Hash: 등가 비교에 특화.
  • GIN: 배열, JSONB, full-text 등 복합 값 검색에 활용.
  • GiST: 다양한 검색 구조/범위/공간 데이터 등에 활용.

3. EXPLAIN

EXPLAIN
SELECT * FROM orders WHERE customer_id = 100;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 100;
EXPLAIN ANALYZE 주의: 실제로 쿼리를 실행하여 실제 시간/행 수 등을 수집합니다. UPDATE/DELETE 같은 변경 SQL에 무심코 실행하면 실제 데이터가 바뀔 수 있습니다.

4. Seq Scan이 무조건 나쁜가?

아닙니다. Table이 작거나 많은 행을 읽어야 한다면 Sequential Scan이 더 저렴할 수 있습니다. 좋은 튜닝은 “Index Scan 무조건 승리”가 아니라 실제 비용과 데이터 분포를 보고 판단하는 것입니다.

5. 기본 성능 조사 순서

  1. 느린 SQL을 식별
  2. EXPLAIN/EXPLAIN ANALYZE 확인
  3. 예상 row vs 실제 row 차이 확인
  4. ANALYZE 통계 확인
  5. Index 적합성 확인
  6. Lock/I/O/CPU/Memory 병목 확인

🔎 EDB Security: Audit · Profile · Protect · Redaction

EDB가 PostgreSQL 위에 제공하는 추가 보안 기능을 구분합니다.

🧒 중학생 비유

학교 보안으로 보면 Audit은 CCTV 기록, Profile은 비밀번호 규칙, SQL/Protect는 수상한 출입 시도 탐지, Data Redaction은 성적표에서 주민번호 일부를 가리는 기능입니다.

1. EDB Audit

연결/해제, DDL/DCL/DML, 오류 등 데이터베이스 활동을 추적할 수 있습니다. edb_audit_statement 등 설정으로 기록 범위를 제어할 수 있고 object-level audit도 사용할 수 있습니다.

2. Profile Management

Profile은 비슷한 인증 요구사항을 가진 여러 Role에 적용할 password policy 묶음입니다.

CREATE PROFILE app_profile
LIMIT
  FAILED_LOGIN_ATTEMPTS 5
  PASSWORD_LIFE_TIME 90;

CREATE USER appuser PASSWORD '...' PROFILE app_profile;

3. SQL/Protect

DBA 관점에서 들어오는 query를 분석하여 일반적인 SQL injection profile을 감지하고 경고하거나 차단하는 추가 보호 계층을 제공합니다.

4. Data Redaction

민감 데이터를 실제 저장값 자체를 바꾸지 않고 특정 사용자에게 표시되는 결과를 동적으로 마스킹하는 정책을 구성할 수 있습니다.

🎯 운영 시나리오 & 시험 직전 압축

실제 장애/운영 상황을 문제 형태로 연결하고 시험 직전 암기표로 마무리합니다.

🧒 중학생 비유

축구 규칙을 다 외워도 실제 경기에서 어느 순간 패스하고 슛해야 하는지 모르면 어렵습니다. 마지막에는 기능 이름이 아니라 ‘상황 → 판단 → 명령/도구’로 연결해야 합니다.

시나리오 1 · “접속이 안 됩니다”

  1. 서버 process가 살아 있는가?
  2. listen_addresses / port는 맞는가?
  3. Network/Firewall이 열려 있는가?
  4. pg_hba.conf에서 해당 DB/User/IP가 매칭되는가?
  5. Role이 LOGIN 가능한가? Password/인증 방식은 맞는가?
  6. Server log에 어떤 오류가 있는가?

시나리오 2 · “쿼리가 갑자기 느립니다”

  1. pg_stat_activity에서 오래 실행 중/대기 중인지 확인
  2. pg_locks / wait_event로 Lock 대기 확인
  3. EXPLAIN (ANALYZE, BUFFERS)로 실행 계획 확인
  4. 통계 오래됨 여부 → ANALYZE
  5. Index/Seq Scan 선택의 타당성 확인
  6. Autovacuum, Checkpoint, I/O, CPU, memory까지 함께 확인

시나리오 3 · “실수로 데이터를 삭제했습니다”

논리 dump의 복구 가능 시점, PITR용 base backup/WAL 보관 여부, RPO/RTO에 따라 복구 전략이 달라집니다. 운영 DB에 즉시 무작정 restore하기 전에 격리된 복구 환경에서 필요한 시점/데이터를 검증하는 것이 안전합니다.

시험 직전 20줄

  1. Cluster는 여러 Database를 포함한다.
  2. Database 아래 Schema, Schema 아래 Table/View/Index 등이 있다.
  3. psql 메타 명령은 SQL과 다르다.
  4. DDL=구조, DML=데이터, DCL=권한, TCL=트랜잭션.
  5. COMMIT=확정, ROLLBACK=취소.
  6. MVCC는 여러 row version으로 동시성을 높인다.
  7. VACUUM은 dead tuple 공간 재사용과 xid 관리에 중요하다.
  8. ANALYZE는 planner 통계다.
  9. Autovacuum은 함부로 끄지 않는다.
  10. pg_hba.conf는 접속 인증 규칙이며 위→아래 첫 match가 중요하다.
  11. GRANT/REVOKE는 권한 제어다.
  12. shared_buffers는 공유 cache, work_mem은 연산별 작업 메모리다.
  13. effective_cache_size는 실제 RAM 예약이 아니라 planner 추정 힌트다.
  14. WAL은 데이터 파일보다 먼저 기록되는 변경 로그다.
  15. Checkpoint는 dirty page 반영/복구 지점 관리와 연결된다.
  16. pg_dump는 논리 백업이다.
  17. PITR은 base backup + WAL archive가 핵심 조합이다.
  18. Index는 읽기를 빠르게 할 수 있지만 쓰기/공간 비용이 있다.
  19. EDB Audit=행위 기록, Profile=계정 정책, Redaction=표시 마스킹.
  20. Dynatune=자동 기본 튜닝, Query Advisor=Index 추천, Wait States=대기 원인 분석.
