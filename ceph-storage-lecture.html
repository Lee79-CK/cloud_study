SECTION 01

  
Ceph는 무엇인가

  
"통합 스토리지(Unified Storage)"라는 말의 실제 의미


  

    Ceph는 여러 대의 평범한 서버(commodity server)에 꽂힌 디스크들을 묶어
    하나의 거대한 스토리지 풀로 만드는 오픈소스 소프트웨어입니다.
    전용 스토리지 장비(어플라이언스)를 사지 않고, 일반 x86 서버 + 일반 HDD/SSD + 리눅스만으로
    엔터프라이즈 스토리지를 구성한다는 점이 핵심입니다.
  


  

    Ceph의 가장 큰 차별점은 하나의 클러스터가 세 가지 형태로 동시에 서비스된다는 것입니다.
    보통은 블록 스토리지는 SAN, 파일 스토리지는 NAS, 오브젝트 스토리지는 별도 제품을 각각 도입합니다.
    Ceph는 이 셋을 같은 디스크 풀 위에서 제공합니다.
  


  

    

      
Block · RBD

      
가상 디스크

      
VM에 붙이는 디스크, 컨테이너의 PVC. 리눅스에서 /dev/rbd0 처럼 블록 디바이스로 보입니다.

      
대체 대상 → SAN, iSCSI, AWS EBS

    

    

      
File · CephFS

      
공유 파일시스템

      
POSIX 호환. 여러 서버가 같은 디렉터리를 동시에 mount해서 읽고 씁니다.

      
대체 대상 → NFS, NAS, AWS EFS

    

    

      
Object · RGW

      
S3 호환 오브젝트

      
HTTP로 버킷·키 단위 저장. AWS S3 SDK를 그대로 사용할 수 있습니다.

      
대체 대상 → AWS S3, Swift, MinIO

    

  


  

    
비유로 이해하기

    
블록은 "빈 노트"입니다. 줄도 없고 형식도 없어서, 쓰는 쪽(OS)이 파일시스템을 직접 만들어 씁니다.

    
파일은 "칸이 나뉜 서류함"입니다. 폴더·권한·수정시간이 이미 정의되어 있고 여러 사람이 같이 씁니다.

    
오브젝트는 "택배 보관함"입니다. 이름표(key)를 붙여 통째로 넣고 통째로 꺼냅니다. 일부만 수정하는 건 어렵지만 무한히 늘릴 수 있습니다.

  


  
탄생 배경과 현재 위치

  

    
2004~2007
미국 UCSC에서 Sage Weil의 박사 연구로 시작. CRUSH 알고리즘 논문이 이때 나옵니다.

    
2012
Inktank 설립으로 상용 지원 시작.

    
2014
Red Hat이 Inktank 인수. Red Hat Ceph Storage로 제품화.

    
2018~
Ceph Foundation(Linux Foundation 산하)으로 거버넌스 이관. CERN, 블룸버그, 대형 통신사, 국내 공공/금융 프라이빗 클라우드 등에서 페타바이트급 운영.

    
릴리스 규칙
연 1회 메이저 릴리스, 두족류(cephalopod) 이름을 알파벳 순으로 사용. Nautilus(14) → Octopus(15) → Pacific(16) → Quincy(17) → Reef(18) → Squid(19) → Tentacle(20). 각 릴리스는 약 24개월 지원됩니다.

  


  

    
2026년 8월 현재 버전 상황

    
신규 구축이라면 Tentacle(v20), 안정성 우선의 기존 운영 클러스터는 Squid(v19)가 일반적인 선택입니다.
    Reef(v18)는 이미 EOL이므로 아직 Reef를 쓰고 있다면 업그레이드 계획이 필요합니다. Ceph는 릴리스를 건너뛴 업그레이드를 지원하지 않는 경우가 많으니
    N → N+1 순차 업그레이드를 원칙으로 잡으세요.

  


  
Ceph의 설계 철학 4가지

  

    

      
01

      
단일 장애점 없음

      
모든 구성요소가 다중화됩니다. 컨트롤러 한 쌍에 의존하는 전통 스토리지와 달리, 노드가 죽어도 서비스가 계속됩니다.

    

    

      
02

      
메타데이터 조회 없는 위치 계산

      
"이 데이터 어디 있어?"를 물어볼 중앙 서버가 없습니다. 클라이언트가 CRUSH로 직접 계산합니다. 이것이 확장성의 근원입니다.

    

    

      
03

      
자율 복구(Self-healing)

      
디스크가 죽으면 관리자 개입 없이 남은 복제본으로 데이터를 다시 만들어 재분산합니다.

    

    

      
04

      
스케일 아웃

      
용량이나 성능이 부족하면 서버를 추가합니다. 컨트롤러 교체(scale-up)가 아니라 노드 추가로 늘립니다.

    

  







  
SECTION 02

  
왜 분산 스토리지인가

  
전통 스토리지가 클라우드에서 막히는 지점


  

    Ceph의 구조를 이해하려면, Ceph가 해결하려는 문제를 먼저 봐야 합니다.
    전통적인 스토리지 어레이(SAN/NAS 어플라이언스)는 아주 잘 작동하지만 클라우드 규모에서 세 가지 벽에 부딪힙니다.
  


  

  

    
구분전통 스토리지 어레이Ceph (분산 스토리지)

    
      
확장 방식컨트롤러 성능이 상한. 용량 늘려도 컨트롤러가 병목노드 추가 시 용량과 성능이 함께 증가

      
장애 도메인컨트롤러 이중화 (2대)디스크·호스트·랙·데이터센터 단위로 정의 가능

      
하드웨어벤더 전용 디스크/컨트롤러, 락인일반 서버·일반 디스크 혼용 가능

      
비용 곡선초기 도입비 높음, 증설 시 벤더 단가초기 진입 낮음, 증설은 서버 단가

      
운영 난이도GUI 중심, 학습 곡선 낮음개념 학습 필요, 운영 자동화 필수

      
지연시간매우 낮음 (전용 ASIC, 짧은 경로)네트워크 홉이 있어 상대적으로 높음

    
  

  


  

    
솔직한 이야기

    
Ceph가 항상 정답은 아닙니다. 수십 마이크로초 단위 지연시간이 필요한 OLTP DB나
    디스크 10개 규모의 작은 환경에서는 전통 스토리지나 로컬 NVMe가 더 적합합니다.
    Ceph는 수백 TB 이상, 여러 서비스가 공유하는 플랫폼 스토리지일 때 가치가 폭발합니다.
    강의 9장에서 이 판단 기준을 구체화합니다.

  


  
분산 스토리지가 반드시 풀어야 하는 3대 난제

  
    
    
  1. 위치 문제 — 데이터를 어디에 둘 것인가
      디스크 1,000개 중 어느 것에 저장할지 결정해야 합니다. 중앙 인덱스 서버를 두면 그 서버가 병목이자 단일 장애점이 됩니다.
      → Ceph의 답: CRUSH (계산으로 결정)
    2. 
    
  2. 내구성 문제 — 디스크는 반드시 고장난다
      디스크 1,000개 환경에서는 매주 하나씩 죽는 게 정상입니다. 데이터를 잃지 않으려면 중복이 필요합니다.
      → Ceph의 답: 복제(Replication) 또는 소거 부호(Erasure Coding)
    3. 
    
  3. 일관성 문제 — 여러 복제본이 서로 다르면?
      쓰기 중 노드가 죽으면 복제본 간 내용이 어긋납니다. 누가 최신인지 합의해야 합니다.
      → Ceph의 답: MON의 Paxos 합의 + PG 단위 peering + scrub 검증
    4. 
  


  
이 세 가지 답이 곧 Ceph 아키텍처입니다. 다음 장에서 실체를 봅니다.







  
SECTION 03

  
아키텍처와 데몬 5종

    Ceph를 그림으로 그리면 아래처럼 3층입니다.
    맨 아래에 RADOS가 있고, 그 위에 librados라는 라이브러리, 그 위에 세 가지 인터페이스가 올라갑니다.

데몬별 역할 — 이것만 외우면 됩니다

  

  

    
데몬역할권장 수량죽으면?

    
      

        ceph-mon
Monitor		
        클러스터 지도(MON/OSD/CRUSH/MDS map) 보관. 어떤 OSD가 살아있는지 판정. Paxos로 합의.
        3 또는 5 (홀수)
        과반 미달 시 클러스터 전체 I/O 정지
      

      

        ceph-mgr
Manager		
        메트릭 수집, 대시보드, Prometheus exporter, pg_autoscaler, orchestrator.
        2 (active/standby)
        I/O는 계속되지만 모니터링·자동화 중단
      

      

        ceph-osd
OSD		
        실제 데이터 저장. 디스크 1개당 데몬 1개. 복제·복구·리밸런싱·scrub 수행.
        디스크 수만큼 (최소 3)
        해당 데이터가 degraded → 자동 복구 시작
      

      

        ceph-mds
Metadata Server		
        CephFS의 디렉터리 트리·권한·inode 관리. 데이터는 취급하지 않음.
        2+ (active/standby), CephFS 쓸 때만
        CephFS 접근 불가 (RBD/RGW는 무관)
      

      

        radosgw
RGW		
        HTTP를 RADOS로 번역. S3/Swift API 제공. 사용자·버킷·인증 관리.
        2+ (LB 뒤에 배치), S3 쓸 때만
        S3 접근 불가 (RBD/CephFS는 무관)
      

    
  

  


  

    
초보자가 가장 많이 오해하는 지점

    
MON은 데이터가 지나가는 길이 아닙니다. MON은 "지도 배포처"일 뿐이고,
    실제 읽기/쓰기는 클라이언트가 OSD와 직접 통신합니다.
    그래서 OSD가 1,000개로 늘어나도 MON이 병목이 되지 않습니다.
    마찬가지로 MDS도 파일 데이터를 중계하지 않습니다 — 경로/권한만 알려주고, 데이터는 클라이언트↔OSD 직접 전송입니다.

  


  
BlueStore — OSD가 디스크를 쓰는 방식

  

    OSD는 예전에는 XFS 같은 파일시스템 위에 데이터를 올렸습니다(FileStore).
    현재는 BlueStore가 표준이며, 파일시스템 없이 raw 블록 디바이스를 직접 다룹니다.
    메타데이터는 내부의 RocksDB에 담습니다. 이중 쓰기(journal double-write)가 사라져 성능과 예측 가능성이 좋아졌습니다.
  

  
    
    
  • Data — 오브젝트 본문. 보통 HDD 또는 SSD 전체.
    • 
    
  • block.db — RocksDB 메타데이터. HDD OSD라면 NVMe로 분리하면 성능이 크게 향상됩니다. (권장 크기: 데이터 용량의 약 1~4%)
    • 
    
  • block.wal — 쓰기 선행 로그. 보통 block.db와 같은 장치에 둡니다.
    • 
  

  

    
설계 팁

    
HDD 기반 클러스터를 만들 때 NVMe 1개에 HDD 8~12개의 block.db를 몰아주는 구성이 일반적입니다.
    단, 그 NVMe가 죽으면 연결된 OSD 전부가 함께 죽습니다. 즉 장애 도메인이 커집니다. 복구 트래픽 규모를 미리 계산해 두세요.

  







  
SECTION 04

  
데이터가 저장되는 길 · CRUSH

  
Ceph 학습의 최대 관문 — 그러나 원리는 단순합니다


  

    Ceph에 파일 하나를 쓰면 무슨 일이 벌어질까요. 경로는 4단계입니다.
    이 4단계만 이해하면 Ceph 운영 중 만나는 대부분의 현상(degraded, remapped, backfill…)을 해석할 수 있습니다.
  


  
    
    
  1. 파일 → 오브젝트로 쪼갠다
      100MB RBD 이미지는 기본 4MB 단위로 잘려 25개 오브젝트가 됩니다. 이름은 rbd_data.<id>.0000...0001 형태입니다.
    2. 
    
  2. 오브젝트 이름 → PG로 해싱한다
      오브젝트 이름을 해시해 pg_num으로 나눈 나머지가 PG(Placement Group) ID입니다.
      PG는 "오브젝트들을 담는 논리 바구니"입니다.
    3. 
    
  3. PG → OSD 집합을 CRUSH로 계산한다
      CRUSH가 PG ID와 CRUSH map(디스크 계층 구조), CRUSH rule을 입력받아
      이 PG를 저장할 OSD 3개를 계산해 냅니다. 조회가 아니라 계산입니다.
    4. 
    
  4. OSD에 직접 쓴다
      클라이언트는 첫 번째 OSD(Primary)에 씁니다. Primary가 나머지 복제본에 전달하고,
      모두 완료되면 클라이언트에 ack를 보냅니다.
    5. 
  


  

    
왜 PG라는 중간 단계가 필요한가

    
오브젝트가 1억 개인데 각각의 위치를 따로 관리하면 지도가 너무 커집니다.
    그래서 오브젝트를 수백~수천 개의 PG로 먼저 묶고, "PG가 어느 OSD에 있는지"만 추적합니다.
    

택배에 비유하면, 개별 소포 1억 개의 목적지를 추적하는 대신
    소포를 1,024개의 컨테이너에 나눠 담고 "컨테이너가 어느 창고에 있는지"만 관리하는 것입니다.
    관리 대상이 1억 개에서 1,024개로 줄어듭니다.

  


  
CRUSH — Controlled Replication Under Scalable Hashing

  

    CRUSH는 결정론적 함수입니다. 같은 입력이면 어느 컴퓨터에서 몇 번 실행해도 같은 답이 나옵니다.
    그래서 클라이언트도, OSD도, MON도 각자 계산해서 같은 결론에 도달합니다. 조율이 필요 없습니다.
  

  

    

      
      
      
    

    


# 개념적으로 CRUSH는 이런 함수다
CRUSH( pg_id, cluster_map, rule, replica_count ) → [osd.7, osd.2, osd.11]

# 입력에 "현재 어디에 있나"라는 조회 결과가 없다는 점이 핵심.
# 클러스터 구조(map)만 알면 위치를 스스로 계산한다.

# 따라서:
#  · 중앙 메타데이터 서버 불필요  → 병목 없음
#  · 클라이언트가 직접 OSD 접속  → 홉 최소화
#  · OSD 추가/제거 시 map만 바뀌면 전원이 새 위치를 동일하게 계산

    

    


# ceph osd tree 출력 = CRUSH map 계층
ID  CLASS  WEIGHT   TYPE NAME              STATUS
-1         48.0     root default
-3         24.0         rack rack-a
-5          8.0             host node-01
 0   hdd    2.0                 osd.0          up
 1   hdd    2.0                 osd.1          up
 2   hdd    2.0                 osd.2          up
 3   hdd    2.0                 osd.3          up
-7          8.0             host node-02
 4   hdd    2.0                 osd.4          up
 ...

# WEIGHT = 용량 비중 (보통 TB 단위). 4TB 디스크면 4.0
# CLASS  = 디바이스 종류 (hdd / ssd / nvme) → rule에서 골라 쓸 수 있다
# root → rack → host → osd 계층이 곧 "장애 도메인" 후보다

    

    


# 규칙 1: 호스트 단위로 3개 복제본 분산 (가장 일반적인 기본값)
rule replicated_host {
    id 0
    type replicated
    step take default              # root default 에서 시작
    step chooseleaf firstn 0 type host   # 서로 다른 host 를 골라라
    step emit
}

# 규칙 2: SSD 만 사용하는 고성능 풀
rule ssd_only {
    step take default class ssd
    step chooseleaf firstn 0 type host
    step emit
}

# 규칙 3: 랙 단위 분산 (랙 전체 정전에도 생존)
rule replicated_rack {
    step take default
    step chooseleaf firstn 0 type rack
    step emit
}
# ⚠ 랙 분산은 랙이 최소 3개 있어야 성립한다.

    

  


  

    
장애 도메인(failure domain)의 의미

    
type host는 "복제본 3개를 서로 다른 서버에 두라"는 뜻입니다.
    서버 1대가 통째로 꺼져도 데이터는 살아 있습니다.
    type osd로 두면 같은 서버 안의 다른 디스크에 복제본이 놓일 수 있어서, 서버 1대만 꺼져도 데이터 유실 위험이 생깁니다.
    노드가 3대 미만인 실습 환경에서는 어쩔 수 없이 type osd를 쓰지만, 운영에서는 절대 금물입니다.

PG 개수는 몇 개가 적당한가

    너무 많으면 OSD의 CPU/메모리를 잡아먹고 peering이 느려집니다.
    권장 기준은 OSD 1개당 약 100개의 PG(복제본 포함)입니다.

SECTION 05

  
데이터 보호 · 복제 vs Erasure Coding

  
용량 효율과 성능 사이의 교환


  

    디스크는 반드시 고장납니다. Ceph는 두 가지 보호 방식을 제공하고, 풀(pool) 단위로 선택합니다.
  


  

    

      
Replication

      
복제 — 통째로 복사

      
오브젝트를 그대로 N개 복사해 서로 다른 장애 도메인에 둡니다. 기본값은 size=3, min_size=2.

      
장점 읽기 빠름, 복구 단순, 랜덤 소규모 쓰기에 유리

      
단점 용량 효율 33% (3배 소모)

      
적합 → RBD(VM 디스크), CephFS 메타데이터, DB 볼륨

    

    

      
Erasure Coding

      
EC — 패리티로 복원

      
데이터를 k개로 쪼개고 패리티 m개를 만들어 총 k+m개를 분산. RAID-6의 일반화 버전입니다.

      
장점 용량 효율 높음 (4+2 = 67%)

      
단점 CPU 사용↑, 부분 쓰기 느림, 복구 시 여러 OSD 동시 읽기

      
적합 → RGW 오브젝트, 백업, 아카이브, 로그, 미디어

    

  


  

    
EC를 직관적으로

    
중요한 서류 4장을 지키는 두 가지 방법입니다.
    복제는 4장을 3부씩 복사해 12장을 만들어 세 곳에 나눠 두는 것입니다. 어느 한 곳이 타도 완본이 남습니다.
    

EC(4+2)는 4장 원본에 "검산용 요약지" 2장을 만들어 총 6장을 여섯 곳에 나눠 두는 것입니다.
    어떤 2장이 사라져도 남은 4장으로 원본을 계산해 복원합니다. 종이는 12장이 아니라 6장만 씁니다.
    대신 읽을 때마다 조각을 모아 조립해야 하므로 손이 더 갑니다.

  


  

    
용량 · 내구성 계산기같은 하드웨어에서 실제 쓸 수 있는 용량은?

    

      

        

        

        

        

          
        

      

      

        
—Raw 총용량

        
—사용가능 용량

        
—권장 운영한계 (85%)

        
—용량 효율

        
—동시 장애 허용

      

      

      
사용가능—

      

    

  


  

    
반드시 기억할 두 가지 함정

    
    
      
  • size=2 는 운영에서 쓰지 마세요. 하나가 죽으면 min_size 미달로 쓰기가 즉시 멈추거나,
      복구 중 두 번째 디스크가 죽으면 데이터를 잃습니다. 재구축에 몇 시간이 걸리는 대용량 HDD 시대에는 현실적인 위험입니다.
    • 
      
  • 85% 규칙. Ceph는 기본적으로 OSD 사용률 85%에서 nearfull 경고, 95%에서 full로 쓰기를 차단합니다.
      또한 노드 장애 시 데이터를 재분산할 여유 공간이 필요합니다. 용량 계획은 실사용 65~70%를 목표로 잡으세요.
    • 
    

  


  
EC를 선택할 때 지켜야 할 노드 수

  

    host 장애 도메인에서 EC k+m을 쓰려면 최소 k+m개의 노드가 필요합니다.
    노드 장애 중에도 정상 운영하려면 k+m+1개 이상을 권장합니다.
    예를 들어 EC 4+2는 노드 6대가 최소, 7대 이상이 안전합니다. 위 계산기에서 노드 수를 줄여 보면 경고가 뜹니다.

RBD — 블록 스토리지

  

    RBD(RADOS Block Device)는 Ceph 풀 안에 가상 디스크 이미지를 만들어 블록 디바이스로 노출합니다.
    씬 프로비저닝(실제 쓴 만큼만 소모), 스냅샷, 클론, 다른 클러스터로의 미러링을 지원합니다.
    OpenStack Cinder와 Kubernetes PVC가 가장 대표적인 소비자입니다.
  

  

    

      
      
      
    

    


# 1) 풀 준비
ceph osd pool create rbd-pool 64
ceph osd pool application enable rbd-pool rbd
rbd pool init rbd-pool

# 2) 100GB 이미지 생성 (씬 프로비저닝 — 실제 소모는 0에서 시작)
rbd create rbd-pool/vm-disk-01 --size 100G
rbd ls -l rbd-pool
rbd info  rbd-pool/vm-disk-01

# 3) 리눅스 호스트에 블록 디바이스로 매핑
sudo rbd map rbd-pool/vm-disk-01 --id admin
# → /dev/rbd0

sudo mkfs.xfs /dev/rbd0
sudo mount /dev/rbd0 /mnt/data

# 4) 해제
sudo umount /mnt/data
sudo rbd unmap /dev/rbd0

    

    


# 스냅샷 — 특정 시점 고정 (COW 방식, 순간 완료)
rbd snap create   rbd-pool/vm-disk-01@before-upgrade
rbd snap ls       rbd-pool/vm-disk-01

# 롤백 (되돌리기) — 대상이 unmap 상태여야 안전
rbd snap rollback rbd-pool/vm-disk-01@before-upgrade

# 클론 — 골든 이미지에서 VM 100대를 순식간에 복제
rbd snap protect  rbd-pool/golden-ubuntu@v1
rbd clone         rbd-pool/golden-ubuntu@v1 rbd-pool/vm-042

# 클론을 독립시키기 (부모 의존 제거)
rbd flatten rbd-pool/vm-042

# 원격 클러스터로 비동기 복제 (DR 구성)
rbd mirror pool enable rbd-pool image
rbd mirror image enable rbd-pool/vm-disk-01 snapshot

    

    


# 온라인 확장 (축소는 위험 — 파일시스템 축소 먼저)
rbd resize rbd-pool/vm-disk-01 --size 200G
sudo xfs_growfs /mnt/data

# QoS — 이미지 단위 IOPS/대역폭 제한
rbd config image set rbd-pool/vm-disk-01 rbd_qos_iops_limit 3000
rbd config image set rbd-pool/vm-disk-01 rbd_qos_bps_limit 209715200

# 성능 벤치마크
rbd bench rbd-pool/vm-disk-01 --io-type write \
    --io-size 4K --io-threads 16 --io-total 1G --io-pattern rand

# 클러스터 전체 처짐 확인
ceph osd perf          # OSD 별 commit/apply latency
ceph tell osd.* bench  # OSD 개별 벤치

    

  


  
CephFS — 공유 파일시스템

  

    CephFS는 POSIX 호환 분산 파일시스템입니다. 여러 클라이언트가 같은 경로를 동시에 읽고 쓸 수 있어서
    Kubernetes의 ReadWriteMany 볼륨, AI 학습 데이터셋 공유, 홈 디렉터리 등에 씁니다.
    데이터 풀과 메타데이터 풀을 각각 만들고 MDS를 띄우면 준비됩니다.
  

  

    

      
      
      
    

    


# 1) 메타데이터 풀 + 데이터 풀
#    메타데이터는 작고 IOPS 민감 → SSD 권장, 반드시 복제 풀
ceph osd pool create cephfs_meta 32
ceph osd pool create cephfs_data 128

# 2) 파일시스템 생성
ceph fs new myfs cephfs_meta cephfs_data

# 3) MDS 배치 (cephadm 사용 시)
ceph orch apply mds myfs --placement="2 node-01 node-02"

# 4) 확인
ceph fs ls
ceph fs status myfs
ceph mds stat        # myfs:1 {0=mds.node-01=up:active}

    

    


# 방법 A: 커널 클라이언트 (성능 우수, 권장)
ceph fs authorize myfs client.user / rw -o /etc/ceph/ceph.client.user.keyring

sudo mount -t ceph node-01,node-02,node-03:/ /mnt/cephfs \
    -o name=user,secretfile=/etc/ceph/user.secret

# /etc/fstab 등록
node-01,node-02,node-03:/  /mnt/cephfs  ceph  name=user,secretfile=/etc/ceph/user.secret,_netdev  0 0

# 방법 B: FUSE 클라이언트 (커널 버전 제약 없음, 성능은 낮음)
sudo ceph-fuse /mnt/cephfs

# 방법 C: NFS 게이트웨이로 재노출 (레거시/Windows 클라이언트용)
ceph nfs cluster create mynfs "2 node-01 node-02"
ceph nfs export create cephfs mynfs /export myfs

    •

SECTION 08

  
Kubernetes와 Ceph

  
Rook 오퍼레이터와 CSI 드라이버


  

    쿠버네티스에서 Ceph를 쓰는 방법은 두 가지입니다.
  

  

    

      
Pattern A

      
Rook — 클러스터 안에서 Ceph 운영

      
Rook 오퍼레이터가 Ceph 자체를 쿠버네티스 워크로드로 관리합니다. CR(YAML)로 선언하면 MON/OSD/MDS를 배치하고 장애 복구까지 자동화합니다.

      
적합 → 쿠버네티스가 인프라의 중심인 환경, 하이퍼컨버지드 구성

    

    

      
Pattern B

      
외부 Ceph + CSI

      
Ceph는 별도 클러스터로 두고, ceph-csi 드라이버만 쿠버네티스에 설치해 연결합니다.

      
적합 → OpenStack과 Ceph를 공유하는 환경, 스토리지 팀이 따로 있는 조직

    

  


  

    
어느 쪽을 고를까

    
클러스터가 여러 개거나 VM 워크로드도 함께 쓴다면 외부 Ceph + CSI가 안전합니다.
    쿠버네티스 클러스터를 지웠다가 다시 만들 때 스토리지가 함께 날아가는 위험을 피할 수 있습니다.
    반대로 단일 클러스터에 모든 걸 담는 엣지·소규모 환경이라면 Rook의 운영 편의성이 큽니다.

응용 분야

  
실제로 Ceph가 어디에 쓰이는가


  

    

      
Private Cloud

      
OpenStack 통합 백엔드

      
Ceph의 가장 고전적이고 강력한 용례입니다. 하나의 Ceph 클러스터가 OpenStack의 여러 서비스를 동시에 받칩니다.

      
Cinder → RBD (VM 볼륨)

         Glance → RBD (VM 이미지)

         Nova → RBD (인스턴스 임시 디스크)

         Manila → CephFS (공유 파일)

         Swift API → RGW

      
효과: Glance 이미지에서 Cinder 볼륨 생성이 CoW 클론으로 즉시 완료 — VM 부팅이 수 초로 단축

    

    

      
Kubernetes

      
영구 볼륨 플랫폼

      
StatefulSet의 DB 볼륨은 RBD, 여러 파드가 공유하는 데이터셋은 CephFS, 아티팩트·로그는 RGW로 한 클러스터에서 모두 처리합니다.

      
여러 K8s 클러스터가 하나의 Ceph를 공유하는 구조가 흔합니다

    

    

      
AI / ML

      
학습 데이터·모델 저장소

      
수십 TB 데이터셋을 CephFS RWX로 여러 GPU 노드에 동시 마운트하고,
      체크포인트와 모델 아티팩트는 RGW(S3)에 버전 관리해 저장합니다.
      MLflow, Kubeflow, Argo Workflows의 아티팩트 백엔드로 S3 엔드포인트를 그대로 지정할 수 있습니다.

      
주의: 소용량 파일 수백만 개(이미지 데이터셋)는 CephFS 메타데이터 부하가 큽니다 → 메타데이터 풀을 NVMe에, MDS를 다중 active로, 또는 tar/webdataset 형태로 묶어 사용

    

    

      
Backup / Archive

      
백업 타겟과 장기 보관

      
EC 풀 + RGW 조합이 비용 효율이 가장 좋습니다. Veeam, Commvault, Restic, Velero 등 대부분의 백업 솔루션이 S3 타겟을 지원합니다.
      Object Lock으로 랜섬웨어 방어용 불변 백업(WORM)을 구성할 수 있습니다.

    

    

      
Data Lake

      
온프레미스 데이터 레이크

      
Spark, Trino, Presto가 s3a:// 로 RGW에 직접 질의합니다.
      데이터를 퍼블릭 클라우드로 내보내지 않아도 되어 전송 비용과 데이터 주권 문제를 동시에 해결합니다.

    

    

      
Media / HPC

      
대용량 순차 I/O

      
영상 편집 작업 공간, 위성·관측 데이터 수집, 유전체 분석 등 대용량 순차 읽기/쓰기 워크로드에 잘 맞습니다.
      노드를 늘리면 총 대역폭이 선형에 가깝게 증가합니다.

복습과 다음 단계


  
핵심 용어 30개

  

    
RADOS
Ceph의 핵심 오브젝트 저장 계층. 모든 인터페이스가 결국 여기로 내려온다

    
librados
RADOS에 직접 접근하는 라이브러리 (C/C++/Python/Java/Go)

    
MON
클러스터 맵을 관리하는 모니터. 홀수 개(3/5)로 배치

    
MGR
메트릭·대시보드·오케스트레이터를 담당하는 매니저

    
OSD
Object Storage Daemon. 디스크 1개당 1개, 실제 데이터 저장

    
MDS
CephFS의 메타데이터 서버. 데이터는 다루지 않음

    
RGW
RADOS Gateway. S3/Swift API 제공

    
RBD
RADOS Block Device. 가상 블록 디바이스

    
CephFS
POSIX 호환 분산 파일시스템

    
Pool
논리적 저장 구획. 보호 방식·PG 수·CRUSH rule을 여기서 정한다

    
PG
Placement Group. 오브젝트를 담는 논리 바구니. Ceph 관리의 최소 단위

    
pg_num
풀의 PG 개수. 2의 거듭제곱 권장

    
CRUSH
PG를 어느 OSD에 놓을지 계산하는 결정론적 알고리즘

    
CRUSH map
디스크의 물리 계층 구조 (root→rack→host→osd) + 가중치

    
CRUSH rule
배치 규칙. 장애 도메인과 디바이스 클래스를 지정

    
Failure domain
장애 격리 단위. osd / host / rack / room / datacenter

    
Primary OSD
PG의 대표 OSD. 클라이언트 I/O를 받아 복제본에 전달

    
Acting set
현재 실제로 PG를 담고 있는 OSD 목록

    
Up set
CRUSH가 계산한 이상적인 OSD 목록. acting set과 다르면 데이터 이동 중

    
size / min_size
복제본 총 개수 / 쓰기를 허용할 최소 복제본 수

    
Erasure Coding
데이터 k조각 + 패리티 m조각으로 보호. 용량 효율이 높다

    
BlueStore
OSD의 현행 저장 엔진. raw 블록 디바이스 직접 사용

    
block.db / WAL
BlueStore 메타데이터·로그 영역. NVMe 분리 시 성능 향상

    
Scrub / Deep-scrub
메타데이터 비교 / 실제 데이터 비교로 무결성 검증

    
Backfill
PG 전체를 새 OSD로 복사하는 작업

    
Recovery
누락된 최신 오브젝트만 채우는 작업 (backfill보다 가벼움)

    
Rebalance
OSD 추가/제거로 데이터 분포를 재조정하는 과정

    
Balancer
OSD 사용률 편차를 자동으로 줄이는 MGR 모듈 (upmap 모드 권장)

    
cephadm
컨테이너 기반 공식 배포·관리 도구

    
Rook
쿠버네티스에서 Ceph를 운영하는 오퍼레이터

  


  
다음 단계 학습 로드맵

  
    
    
  1. 가상 환경에 3노드 클러스터 직접 구축
      VM 3대(각 4vCPU/8GB/디스크 3개)로 cephadm bootstrap부터 OSD 추가까지 해 보세요.
      ceph -s가 HEALTH_OK가 되는 순간이 첫 관문입니다.
    2. 
    
  2. 장애를 일부러 만들어 보기
      OSD를 강제 정지하고 ceph -s의 변화를 관찰하세요. degraded → recovering → active+clean의 전이를 눈으로 보는 것이
      문서 100장보다 낫습니다. 노드 1대를 통째로 끄는 실험도 해 보세요.
    3. 
    
  3. 세 인터페이스를 모두 붙여 보기
      RBD를 mount하고, CephFS를 두 대에서 동시에 mount해 파일이 즉시 보이는지 확인하고,
      aws-cli로 RGW에 파일을 올려 보세요.
    4. 
    
  4. Rook으로 쿠버네티스 연동
      kind나 소규모 클러스터에 Rook을 설치하고 PVC를 만들어 보세요. RWO와 RWX의 차이를 실습으로 확인합니다.
    5. 
    
  5. 성능 측정과 튜닝
      rbd bench, fio, s3-benchmark로 기준선을 잡고, block.db를 NVMe로 분리했을 때의 차이를 측정해 보세요.
    6. 
    
  6. 모니터링 스택 구성
      Prometheus 모듈을 켜고 Grafana 공식 대시보드를 연결하세요. 어떤 지표를 봐야 하는지 아는 것이 운영 역량의 절반입니다.
    7. 
    
  7. 공식 문서와 커뮤니티
      docs.ceph.com의 Architecture와 Troubleshooting 챕터, ceph.io 블로그,
      Ceph Days/Cephalocon 발표 자료를 정기적으로 읽으세요. 릴리스 노트는 업그레이드 전 필수입니다.
    8. 
  


  

    
마지막 조언

    
Ceph는 읽어서 익히는 기술이 아니라 부숴 보면서 익히는 기술입니다.

    OSD를 죽이고, 노드를 끄고, 풀을 잘못 만들어 보세요. 그 경험이 새벽 3시 장애 알림 앞에서 당신을 구합니다.
