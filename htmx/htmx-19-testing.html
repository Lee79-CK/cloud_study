def test_hx_ptag_바뀌지_않으면_304(kim):
    r = kim.get("/vms/web-01/activity/live", headers=HX)
    tag = r.headers["hx-ptag"]
    assert kim.get("/vms/web-01/activity/live", headers={**HX, "HX-PTag": tag}).status_code == 304
    kim.post("/vms/web-01/tags", data={"tag": "t1"}, headers=HX)
    assert kim.get("/vms/web-01/activity/live", headers={**HX, "HX-PTag": tag}).status_code == 200

  
TestClient는 ASGI 앱을 서버 없이 직접 호출하므로 11개가 0.1초에 끝납니다. htmx 요청은 결국 헤더가 붙은 HTTP 요청이라, HX-Request·HX-Request-Type을 붙여 보내고 응답 헤더를 검사하면 됩니다. 세션 만료의 401 + HX-Redirect(6편), 데이터 API의 401 JSON(11편), CSRF 403(17편), CSP nonce와 import map의 일치(17편), htmx 응답의 no-store(18편)까지 지금까지 측정으로 정한 규칙을 하나씩 테스트로 고정했습니다.

  

    
측정으로 찾은 것: Starlette 1.10.0 TestClient의 지원 중단 경고

    
처음 실행에서 Using `httpx` with `starlette.testclient` is deprecated; install `httpx2` instead. 경고가 나왔습니다. Starlette 1.10.0 소스를 보면 TestClient가 httpx2를 먼저 찾고 없을 때만 httpx로 대체합니다. httpx2는 Pydantic 팀이 관리하는 후속 패키지로 PyPI 최신이 2.16.0(2026-10-21)입니다. 테스트 전용 requirements-dev.txt에 넣자 경고가 사라졌습니다. 게이트웨이(15편)가 운영 코드에서 쓰는 httpx 0.28.1은 그대로 두었습니다. 옮길지는 별도 판단이 필요합니다.

계약: 두 서버를 맞대어

  
이 시리즈의 랩은 같은 포털을 Express와 FastAPI로 두 번 구현했습니다. 실무에서도 "새 서버가 옛 서버와 같은 HTML을 내는가"(16편 이관), "업스트림 팀이 약속한 조각 구조를 지키는가"(15편)는 늘 생기는 질문입니다. 문구·공백·주석은 달라도 되지만, htmx가 읽는 부분은 같아야 합니다.

  
tests/contract/test_contract.py (구조 추출)


class Sig(HTMLParser):
    """htmx가 보는 구조만 뽑는다: id가 있거나 hx-* 속성이 있는 요소, 사용자 정의 요소, 폼 입력의 name"""
    def handle_starttag(self, tag, attrs):
        a = dict(attrs)
        hx = {k: norm(v) for k, v in a.items() if k.startswith("hx-")}
        if a.get("id") or hx or "-" in tag or (tag in ("input", "select", "textarea") and a.get("name")):
            self.items.append((tag, a.get("id"), tuple(sorted(hx.items())), a.get("name"), " ".join(sorted((a.get("class") or "").split()))))

  
같은 사용자로 두 서버에 같은 요청(목록·검색·상세·요약·활동·메모 편집·없는 VM·재시작·검증 오류·플래그 화면·VM 관리와 랩 점검 전체 페이지·게이트웨이 조각·16편 새 구현)을 보내고, 상태 코드, 추적하는 HX 응답 헤더(JSON이면 값으로), 위 구조 목록을 비교합니다. 비교기가 실제로 차이를 잡는지 확인하는 민감도 테스트(같은 서버의 web-01과 web-02 상세는 달라야 함)도 넣었습니다.

측정으로 찾은 것: SSE가 있는 페이지에서 networkidle을 기다리면 안 된다

    
CSP 테스트를 처음에는 페이지마다 waitForLoadState('networkidle')로 기다렸는데 두 서버 모두 30초 제한 시간을 넘겨 실패했습니다. SSE 연결과 폴링이 있는 페이지는 네트워크가 영원히 "바쁜" 상태라 그 순간이 오지 않습니다. 확인할 요소를 기다리는 단언(expect(locator)…)이나 짧은 고정 대기로 바꾸자 통과했습니다. 또 하나, 첫 실행의 검색 테스트 실패는 테스트가 존재하지 않는 #vm-tbody를 찾은 탓(실제 id는 #vm-body)이었습니다. E2E 실패는 앱이 아니라 테스트 쪽 가정이 틀린 경우도 많으므로, 실패 시 남는 trace(retain-on-failure)부터 봅니다.

  

  
Playwright Test 1.65.0은 Chromium 158(리비전 1254)을 기대합니다. 이 실습 환경에는 Chrome 153이 미리 설치되어 있어 CHROMIUM_PATH 환경 변수로 실행 파일을 지정하는 옵션을 설정에 두었고, 그 조합으로 18개가 통과했습니다. CI에서는 npx playwright install --with-deps chromium으로 짝이 맞는 브라우저를 받습니다.
