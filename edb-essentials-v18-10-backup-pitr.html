RPO와 RTO

  • RPO (Recovery Point Objective) — 장애 시 얼마만큼의 데이터 손실을 허용하나. "최대 5분치까지"처럼 표현합니다. WAL 아카이빙 주기와 복제로 줄입니다.
  • RTO (Recovery Time Objective) — 장애 후 얼마 안에 서비스를 되살려야 하나. 백업 크기, 복원 속도, 재생할 WAL 양, 스탠바이 유무가 좌우합니다.
현장 원칙: 복원해 보지 않은 백업은 백업이 아니다

MSP 계약서의 "일일 백업"은 복원이 되어야 의미가 있습니다. 분기마다 별도 서버에 실제로 PITR을 해 보고 걸린 시간을 기록하세요. 그 시간이 곧 고객에게 약속할 수 있는 RTO입니다. 백업은 원본과 다른 장소(다른 서버·다른 리전·오브젝트 스토리지)에도 두어야 합니다.

2장

WAL 아카이빙

2편에서 본 WAL 파일(16MB)이 다 차면, archiver 프로세스가 그 파일을 별도 저장소로 복사합니다. 이렇게 모은 WAL이 있어야 기본 백업 이후의 변경을 원하는 시점까지 재생할 수 있습니다.

# postgresql.conf
wal_level       = replica         # 기본값. minimal이면 아카이빙 불가
archive_mode    = on              # 변경 시 재시작 (5편)
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'   # reload로 변경 가능
archive_timeout = 300             # 5분마다 WAL 파일을 강제로 넘겨 아카이브 (RPO 상한)
기호뜻
%p아카이브할 WAL 파일의 경로 (PGDATA 기준, 예: pg_wal/000000010000000A0000003F)
%fWAL 파일 이름만

archive_command는 성공했을 때만 0을 반환해야 합니다. 0이 아닌 값을 반환하면 서버는 그 파일을 지우지 않고 잠시 뒤 다시 시도합니다. 셸 명령 대신 라이브러리 모듈로 아카이빙하는 archive_library(PG15+)도 있습니다.

좋은 명령, 위험한 명령

각 archive_command가 안전한지 판단해 보세요.

-- 아카이빙 상태 감시
SELECT archived_count, last_archived_wal, last_archived_time,
       failed_count, last_failed_wal, last_failed_time
FROM   pg_stat_archiver;
SELECT pg_switch_wal();   -- 현재 WAL 파일을 즉시 넘겨 아카이브하게 함
아카이브가 실패하면 pg_wal이 가득 찬다

아카이브에 실패한 WAL은 지워지지 않고 pg_wal에 쌓입니다. 백업 저장소가 가득 찼거나 마운트가 풀린 것을 모르고 두면, 결국 pg_wal이 있는 디스크가 가득 차서 서버가 멈춥니다. 2편에서 말한 "pg_wal 파일을 손으로 지우면 안 되는" 상황이 바로 이때 생깁니다. pg_stat_archiver.failed_count를 모니터링하세요.

3장

pg_basebackup

실행 중인 서버의 데이터 디렉터리 전체를 복제 프로토콜로 복사하는 표준 도구입니다. 서비스를 멈추지 않고 백업합니다.

준비

CREATE ROLE backup_user LOGIN REPLICATION PASSWORD '...';     -- REPLICATION 속성 (7편)
# pg_hba.conf — DATABASE 필드에 replication (all로는 안 됨, 7편)
host  replication  backup_user  10.0.9.0/24  scram-sha-256
# postgresql.conf — max_wal_senders(기본 10)가 0이 아니어야 함

실행

pg_basebackup -h db01 -p 5444 -U backup_user \
  -D /backup/base/2026-09-30 \
  -Ft -z -Xstream -P -c fast
옵션의미
-D백업을 저장할 디렉터리 (비어 있어야 함)
-Fp / -Ftplain(디렉터리 그대로, 기본) / tar 파일
-X stream (기본) / fetch / none백업하는 동안 생긴 WAL을 함께 받는 방식. stream은 별도 연결로 동시에 받아 가장 안전
-z, --compress압축 (tar 포맷)
-c fast / spread(기본)시작 체크포인트를 즉시 할지, 천천히 나눠 할지 (2편 체크포인트)
-P진행률 표시
-R스탠바이 설정(standby.signal, 접속 정보)을 함께 써 줌 (11편)
-T old=newplain 포맷에서 테이블스페이스 위치를 바꿔 저장 (6편)
--incremental=manifest이전 백업의 매니페스트를 기준으로 증분 백업 (PG17+, 4장)

백업 디렉터리에는 모든 파일의 목록과 체크섬을 담은 backup_manifest가 생기며, pg_verifybackup으로 백업이 손상되지 않았는지 검증할 수 있습니다.

pg_verifybackup /backup/base/2026-09-30
시험 포인트

pg_basebackup에는 REPLICATION 속성(또는 슈퍼유저), pg_hba.conf의 replication 항목, max_wal_senders 여유가 필요합니다. 결과물은 클러스터 전체이며 특정 DB만 골라 백업할 수 없습니다. 도구 없이 직접 물리 백업을 할 때 쓰는 저수준 함수는 PG15부터 pg_backup_start() / pg_backup_stop()으로 이름이 바뀌었습니다(옛 이름 pg_start_backup / pg_stop_backup).

4장

증분 백업 (PostgreSQL 17+)

매일 전체 백업을 하면 시간과 공간이 많이 듭니다. PostgreSQL 17부터 pg_basebackup이 이전 백업 이후 바뀐 블록만 받는 증분 백업을 지원합니다. 바뀐 블록을 추적하기 위해 WAL 요약 기능을 켜야 하며, 이때 walsummarizer 프로세스가 동작합니다.

# postgresql.conf
summarize_wal = on

# 일요일: 전체 백업
pg_basebackup -D /backup/full_sun -Xstream -c fast
# 월요일: 일요일 기준 증분
pg_basebackup -D /backup/incr_mon --incremental=/backup/full_sun/backup_manifest
# 화요일: 월요일 기준 증분
pg_basebackup -D /backup/incr_tue --incremental=/backup/incr_mon/backup_manifest

복원할 요일을 누르면 필요한 백업과 합치는 명령을 보여 줍니다.


  

  

    시험 포인트
    
증분 백업은 그대로 서버를 띄울 수 없고, pg_combinebackup으로 전체 백업과 이어지는 증분들을 순서대로 합쳐 완전한 데이터 디렉터리를 만든 뒤 사용합니다. 중간 증분 하나라도 없으면 그 이후 시점은 복원할 수 없습니다.

  







  
5장

  
PITR 절차

  
기본 백업을 풀어 놓고, 아카이브된 WAL을 원하는 시점까지 재생하는 과정입니다. PostgreSQL 12부터는 recovery.conf 파일이 없어졌고, 복구 설정은 postgresql.conf(또는 auto.conf)에 적고, 복구 모드 진입은 데이터 디렉터리의 recovery.signal 파일로 알립니다.

  
순서 맞추기

  
아래 단계를 올바른 순서대로 눌러 보세요.

  

    

    
    
    
    
    
    
  
    

    # 전체 예시 (RHEL 계열, 서비스 중지 후 enterprisedb 사용자)
sudo systemctl stop edb-as-18
mv /var/lib/edb/as18/data /var/lib/edb/as18/data.broken          # 지우지 말고 보관
mkdir /var/lib/edb/as18/data && chmod 700 /var/lib/edb/as18/data
tar -xzf /backup/base/2026-09-30/base.tar.gz -C /var/lib/edb/as18/data
rm -rf /var/lib/edb/as18/data/pg_wal/*                            # 백업에 딸린 오래된 WAL 정리
cp /var/lib/edb/as18/data.broken/pg_wal/0000* /var/lib/edb/as18/data/pg_wal/   # 아직 아카이브 안 된 최신 WAL 살리기

cat >> /var/lib/edb/as18/data/postgresql.auto.conf <<'EOF'
restore_command        = 'cp /backup/wal/%f %p'
recovery_target_time   = '2026-09-30 14:32:00+09'
recovery_target_action = 'pause'
EOF
touch /var/lib/edb/as18/data/recovery.signal
sudo systemctl start edb-as-18

-- 복구가 목표에서 멈추면 데이터 확인 후
SELECT pg_is_in_recovery();          -- t (아직 복구 모드)
SELECT count(*) FROM orders;         -- 원하는 상태인지 확인 (읽기만 가능)
SELECT pg_wal_replay_resume();       -- 복구 종료, 읽기·쓰기 가능 (새 타임라인)
    
  
    
    시험 포인트
    
    ① PG12 이후 recovery.conf는 없습니다. 복구 설정은 postgresql.conf, 신호는 recovery.signal(스탠바이로 계속 운영하려면 standby.signal, 11편). ② WAL을 가져오는 설정은 restore_command로, archive_command와 방향이 반대입니다(cp 아카이브/%f %p). ③ 복구가 끝나면 recovery.signal은 서버가 스스로 지우고, 타임라인이 1 증가합니다(7장).
    
  
    

    



    
  
    6장
    
  
    복구 목표 설정
    
  
    
    
    파라미터의미
    
    
      
    recovery_target_time이 시각까지 재생 (시간대를 꼭 적기: '2026-09-30 14:32:00+09')
    
      
    recovery_target_xid이 트랜잭션 ID까지
    
      
    recovery_target_lsn이 WAL 위치까지
    
      
    recovery_target_name미리 만들어 둔 복원 지점까지. SELECT pg_create_restore_point('before_release_v42');
    
      
    recovery_target = 'immediate'기본 백업이 일관된 상태가 되는 가장 이른 시점에서 멈춤
    
      
    recovery_target_inclusive목표 지점의 트랜잭션을 포함할지 (기본 on)
    
      
    recovery_target_timeline어느 타임라인을 따라갈지 (기본 latest)
    
      
    recovery_target_action목표 도달 후 pause(기본) / promote / shutdown
    
    
    
  
    
    시험 포인트
    
    recovery_target_* 중 하나만 지정할 수 있습니다. 목표를 지정하지 않으면 아카이브의 마지막 WAL까지 모두 재생합니다(가장 최신 상태로 복구). 배포나 대량 작업 직전에 pg_create_restore_point()로 이름 붙은 복원 지점을 만들어 두면, 시각을 추측하지 않고 정확히 되돌릴 수 있습니다.
    
  
    

    



    
  
    7장
    
  
    타임라인
    
  
    PITR로 과거 시점에서 복구를 끝내면, 그 시점부터 원래 역사와 다른 새 역사가 시작됩니다. 두 역사의 WAL이 섞이지 않도록 PostgreSQL은 타임라인 번호를 하나 올립니다. 2편에서 본 WAL 파일 이름의 앞 8자리가 타임라인입니다.
    

    000000010000000A0000003F    ← 타임라인 1 (사고 전의 원래 역사)
000000020000000A0000003F    ← 타임라인 2 (복구 후 새 역사)
00000002.history            ← 타임라인 2가 1의 어느 지점에서 갈라졌는지 기록
    
  
    덕분에 복구를 여러 번 시도해도 이전 시도의 WAL을 덮어쓰지 않고, 필요하면 다른 타임라인을 따라 다시 복구할 수 있습니다. 스탠바이를 주 서버로 승격할 때도 타임라인이 올라갑니다(11편).
    
  
    
    비유: 평행 우주
    
    14시 32분에 테이블이 지워진 우주(타임라인 1)는 그대로 기록으로 남고, 14시 31분에서 갈라져 테이블이 살아 있는 새 우주(타임라인 2)가 시작됩니다. .history 파일이 두 우주가 갈라진 지점을 적어 둔 지도입니다.
    
  
    

    



    
  
    8장
    
  
    Barman과 pgBackRest
    
  
    pg_basebackup과 archive_command만으로도 PITR은 가능하지만, 보관 주기 관리, 백업 목록, 원격 복원, 압축·병렬 처리를 직접 짜야 합니다. 운영에서는 이를 대신해 주는 전용 도구를 씁니다.
    
  
    
    
    BarmanpgBackRest
    
    
      
    관리 주체EDB가 개발·유지하는 오픈소스커뮤니티 오픈소스
    
      
    구조별도 백업 서버에서 여러 DB 서버를 중앙 관리DB 서버와 저장소(repository) 구성, 원격 저장소 가능
    
      
    주요 기능백업 카탈로그, 보관 정책, 스트리밍 WAL 수신, 원격 복원, 클라우드 저장소(barman-cloud)병렬 백업·복원, 전체/차등/증분, 압축·암호화, S3 등 오브젝트 스토리지
    
      
    PITR지원지원
    
    
    

    # Barman 사용 예 (백업 서버에서)
barman backup db01                       # 기본 백업
barman list-backup db01                  # 백업 목록
barman recover db01 latest /var/lib/edb/as18/data \
  --target-time "2026-09-30 14:32:00+09" --remote-ssh-command "ssh enterprisedb@db01-restore"
    
  
    이 시험에서는 두 도구의 이름과 역할(물리 백업·PITR 관리 도구)을 구분하는 수준이면 충분합니다. 세부 설정은 각 도구의 문서를 참고하세요.
    

    



    
  
    9장
    
  
    pg_upgrade — 메이저 업그레이드
    
  
    6편에서 봤듯 메이저 버전 사이에는 저장 형식이 바뀔 수 있습니다. 9편의 덤프·복원은 대용량에서 오래 걸리므로, pg_upgrade로 데이터 파일을 새 버전 클러스터로 옮기는 방법을 주로 씁니다. EPAS도 같은 방식으로 EPAS 간 업그레이드를 합니다.
    

    # 1) 새 버전을 설치하고 initdb (옛 클러스터와 같은 모드·인코딩·로케일로)
# 2) 두 서버 모두 중지 후 점검만 먼저
/usr/edb/as18/bin/pg_upgrade \
  -b /usr/edb/as17/bin -B /usr/edb/as18/bin \
  -d /var/lib/edb/as17/data -D /var/lib/edb/as18/data \
  --check
# 3) 문제 없으면 --check 없이 실행, 새 서버 시작 후 안내된 후속 스크립트 실행
    
  
    
    
    모드동작특징
    
    
      
    --copy (기본)파일 복사가장 안전, 공간 2배·시간 소요. 옛 클러스터가 그대로 남음
    
      
    --link하드 링크매우 빠름. 새 서버를 시작하면 옛 클러스터는 사용 불가
    
      
    --clone파일 시스템 복제(reflink)지원 파일 시스템에서 빠르고 안전
    
      
    --swap디렉터리를 바꿔치기PG18 신규. 가장 빠를 수 있으나 옛 클러스터는 사용 불가
    
    
    
  
    
    시험 포인트: PostgreSQL 18 업그레이드의 두 가지 변화
    
    ① PG18의 pg_upgrade는 옵티마이저 통계를 옮겨 줍니다. 예전에는 업그레이드 직후 통계가 비어 있어 모든 테이블에 ANALYZE(vacuumdb --analyze-in-stages)가 끝날 때까지 성능이 나빴습니다. ② PG18 initdb는 데이터 체크섬이 기본으로 켜지므로(3편), 체크섬이 꺼진 옛 클러스터를 올릴 때는 새 클러스터를 --no-data-checksums로 만들거나 옛 클러스터에 pg_checksums로 체크섬을 먼저 켜야 합니다. 두 클러스터의 체크섬 설정이 다르면 pg_upgrade가 거부합니다.
    
  
    
  
    
    업그레이드 전 백업은 필수
    
    특히 --link·--swap 모드는 되돌릴 수 없습니다. 업그레이드 직전 기본 백업을 받고, 복원 리허설을 거친 뒤 진행하세요. 확장 모듈(PostGIS 등)은 새 버전용이 먼저 설치되어 있어야 --check를 통과합니다.
