ServiceAccount와 워크로드 아이덴티티

사람의 신원은 17편에서 IdP로 정리했습니다. 이제 Pod의 신원입니다. Pod는 Kubernetes API를 부르기도 하고(ServiceAccount 토큰), 클라우드의 S3·Blob·GCS를 부르기도 합니다. 예전에는 후자를 위해 액세스 키를 Secret에 넣었고, 그 키가 유출 사고의 단골이었습니다. 지금은 클러스터가 발급한 짧은 토큰을 클라우드가 믿게 하는 방식(워크로드 아이덴티티)이 표준입니다. 이 편은 ServiceAccount 토큰의 구조부터 EKS IRSA·Pod Identity, AKS Workload Identity, GKE Workload Identity Federation, OpenShift STS, 온프렘 SPIFFE/SPIRE까지 비교하고, 같은 “S3 읽기 전용 Pod”를 세 방식으로 만들어 토큰 흐름을 직접 따라갑니다.

기준: Kubernetes v1.37 · EKS Pod Identity · AKS/GKE Workload Identity · SPIRE 1.x 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

Pod가 클라우드 자격 증명을 얻기까지: 토큰 흐름 비교기

방식을 고르고 단계를 넘기면, 그 순간 일하는 주체(노란색)와 받는 주체(초록색), 오가는 토큰의 발급자(iss)·대상(aud)·주체(sub)가 나옵니다. 아래 표는 방식별 특성 요약입니다.

0

읽는 법과 목표

쉬운 말로 예전 방식은 Pod에게 회사 금고 열쇠의 복사본(액세스 키)을 주는 것이었습니다. 열쇠는 만료되지 않고, 복사되면 누가 쓰는지 알 수 없습니다. 워크로드 아이덴티티는 Pod가 출입증(Kubernetes가 발급한 짧은 토큰)을 들고 금고 경비실(클라우드 STS)에 가면, 경비실이 “이 회사(클러스터)가 발급한 출입증이고, 이 부서(네임스페이스)의 이 직원(ServiceAccount)이니 1시간짜리 임시 열쇠를 주겠다”고 하는 방식입니다. 복사할 영구 열쇠가 없습니다.

이 편을 마치면 할 수 있는 것

  • ServiceAccount 토큰의 발급자·대상·만료·묶인 객체를 읽고, 자동 마운트를 꺼야 할 곳을 판단할 수 있습니다.
  • 워크로드 아이덴티티의 세 원리(OIDC 제휴, 에이전트 중개, SPIFFE)를 구분할 수 있습니다.
  • EKS IRSA와 Pod Identity, AKS·GKE 워크로드 아이덴티티, OpenShift STS, SPIRE를 비교해 고객 환경에 맞게 고를 수 있습니다.
  • 안전한 신뢰 정책(트러스트 정책)을 쓰고 와일드카드·대상 누락 같은 실수를 찾을 수 있습니다.
  • 크로스 클라우드 제휴, 컨트롤러·CI 러너의 신원을 정적 키 없이 설계할 수 있습니다.

ServiceAccount와 토큰의 진화

세대토큰문제·개선
초기(~1.23)SA마다 Secret에 만료 없는 토큰 자동 생성유출 시 영구 유효, Pod가 지워져도 유효
바운드 토큰(1.22 GA, 1.24부터 Secret 자동 생성 중단)kubelet이 TokenRequest로 받아 프로젝티드 볼륨에 넣음대상(aud)·만료·묶인 Pod. Pod 삭제 시 무효. 레거시 토큰 자동 정리(17편)
발급자 공개API 서버가 /.well-known/openid-configuration, /openid/v1/jwks 공개외부(클라우드)가 이 토큰을 검증할 수 있게 됨 → 워크로드 아이덴티티의 출발점
노드 정보·외부 서명(최근)토큰에 노드 이름·UID 클레임, 서명 키를 외부 서명기(KMS 등)로(1.36 GA)도난 토큰의 출처 추적, 서명 키 보호
바운드 토큰의 실제 클레임
{
  "aud": ["https://kubernetes.default.svc"],          // 대상: 기본은 API 서버
  "exp": 1793000000, "iat": 1792996393,               // 약 1시간(kubelet이 만료 전 갱신)
  "iss": "https://kubernetes.default.svc",            // 발급자: --service-account-issuer
  "sub": "system:serviceaccount:s3-lab:reader",
  "kubernetes.io": {
    "namespace": "s3-lab",
    "serviceaccount": {"name": "reader", "uid": "…"},
    "pod":  {"name": "reader-7d9f…", "uid": "…"},       // 묶인 Pod: 지워지면 토큰 무효
    "node": {"name": "w1", "uid": "…"}
  }
}

자동 마운트를 끌 곳

  • 대부분의 앱은 Kubernetes API를 부르지 않습니다. 그런데 기본값으로 모든 Pod에 default SA 토큰이 마운트됩니다. 앱이 침해되면 공격자는 이 토큰으로 API를 탐색합니다(22편).
  • ServiceAccount의 automountServiceAccountToken: false(기본값을 끔)와 Pod의 같은 필드(개별 재정의)로 끄세요. 단, Pod에서 다시 켤 수 있으므로 정책으로 강제하려면 21편의 어드미션이 필요합니다.
  • API를 부르는 앱만 전용 SA를 만들고, 필요한 대상(audience)으로 따로 받은 토큰을 쓰게 합니다(아래 예).
대상이 다른 토큰을 따로 받기 (프로젝티드 볼륨)
apiVersion: v1
kind: ServiceAccount
metadata: {name: reader, namespace: s3-lab}
automountServiceAccountToken: false                 # API 토큰은 필요 없음
---
# Pod 스펙 일부: 외부(예: Vault, 사내 서비스)용 토큰만 원하는 대상·수명으로
volumes:
- name: vault-token
  projected:
    sources:
    - serviceAccountToken: {audience: "vault.lab", expirationSeconds: 900, path: token}

워크로드 아이덴티티의 세 가지 원리

원리어떻게대표장점주의
OIDC 제휴클라우드가 클러스터의 SA 발급자를 OIDC 공급자로 등록하고, Pod의 SA 토큰을 받아 임시 자격 증명으로 교환EKS IRSA, AKS Workload Identity, GKE WIF, OpenShift STS, 셀프 호스팅 IRSA표준(OIDC), 클러스터 밖에서도 같은 방식발급자 공개 키를 클라우드가 읽을 수 있어야 함. 신뢰 정책 조건이 곧 보안 경계
에이전트 중개노드의 에이전트(또는 메타데이터 서버)가 Pod 요청을 받아, 클라우드에 등록된 매핑에 따라 자격 증명을 대신 받아 줌EKS Pod Identity, GKE 메타데이터 서버(WIF의 전달 경로)OIDC 공급자 관리 불필요, 매핑을 클라우드 API로 관리노드 에이전트 의존, 링크 로컬 주소 네트워크 허용(9편)
SPIFFE독립된 신원 체계(SPIRE)가 노드·워크로드를 증명하고 X.509·JWT 신원(SVID)을 발급. JWT-SVID를 클라우드 OIDC 제휴에 사용SPIRE(온프렘·멀티 클라우드), 서비스 메시의 신원플랫폼 중립, 메시 없이 mTLS, 여러 클러스터·VM을 한 신원 체계로SPIRE 서버·에이전트 운영(가용성이 곧 신원 가용성)
시니어 포인트: 신뢰 정책의 조건이 진짜 권한 경계다 OIDC 제휴에서 클라우드는 “이 발급자의 토큰 중 sub·aud가 조건에 맞는 것”을 믿습니다. 조건을 system:serviceaccount:*:*처럼 넓히면, 그 클러스터에서 ServiceAccount를 만들거나 Pod를 띄울 수 있는 누구나(18편의 개발자 포함) 그 클라우드 역할을 쓸 수 있습니다. 3장 생성기로 조건을 확인하는 습관을 들이세요.

EKS: IRSA vs Pod Identity

항목IRSAPod Identity
원리OIDC 제휴(클러스터 발급자 → IAM OIDC 공급자)에이전트 중개(eks-pod-identity-agent DaemonSet)
매핑 위치SA 어노테이션 eks.amazonaws.com/role-arn + IAM 역할 신뢰 정책(sub 조건)EKS API의 Pod Identity 연결(클러스터·네임스페이스·SA → 역할)
신뢰 정책클러스터마다 다른 OIDC 공급자·조건. 클러스터 추가 시 정책 수정주체 pods.eks.amazonaws.com 하나. 여러 클러스터에서 같은 역할 재사용 쉬움
Pod 안에서웹훅이 AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE(aud: sts.amazonaws.com) 주입 → SDK가 STS AssumeRoleWithWebIdentity웹훅이 AWS_CONTAINER_CREDENTIALS_FULL_URI(169.254.170.23), 인증 토큰 파일 주입 → SDK가 에이전트에서 자격 증명 수신
세션 태그(ABAC)없음클러스터·네임스페이스·SA 이름 등 세션 태그 자동 → IAM 조건으로 활용
한도·운영계정당 OIDC 공급자 수, 신뢰 정책 크기 한도에이전트 애드온 필요, 링크 로컬 이그레스 허용, 일부 실행 환경 미지원(문서 확인)
클러스터 밖·셀프 호스팅kubeadm 등에서도 발급자를 공개하면 같은 방식 가능EKS 전용

AKS Workload Identity

    

      
    
        
  1. 클러스터에 OIDC 발급자와 워크로드 아이덴티티를 켭니다(--enable-oidc-issuer --enable-workload-identity).
    2. 
        
  2. 사용자 할당 관리 ID(UAMI)를 만들고 Azure 리소스 권한(예: Storage Blob Data Reader)을 줍니다.
    3. 
        
  3. 그 ID에 페더레이션 자격 증명을 추가합니다: 발급자 = 클러스터 OIDC URL, 주체 = system:serviceaccount:<ns>:<sa>, 대상 = api://AzureADTokenExchange.
    4. 
        
  4. SA에 azure.workload.identity/client-id 어노테이션, Pod에 azure.workload.identity/use: "true" 레이블을 붙이면 웹훅이 AZURE_CLIENT_ID·AZURE_TENANT_ID·AZURE_FEDERATED_TOKEN_FILE을 주입하고, Azure SDK가 Entra ID에서 토큰을 교환합니다.
    5. 
      

      
    
        
  • 예전의 Pod 관리 ID(aad-pod-identity)는 폐기되었으니 이전 대상입니다.
    • 
        
  • 한 관리 ID에 붙일 수 있는 페더레이션 자격 증명 수에 한도가 있어, 네임스페이스·앱이 많으면 ID를 나누는 설계가 필요합니다.
    • 
        
  • 주체 문자열의 오타는 토큰 교환 단계에서 “일치하는 페더레이션 자격 증명 없음” 오류(AADSTS 계열)로 나타납니다.
    • 
      

    

    
AKS 구성 요약
az aks update -g rg-lab -n lab-aks --enable-oidc-issuer --enable-workload-identity
ISSUER=$(az aks show -g rg-lab -n lab-aks --query oidcIssuerProfile.issuerUrl -o tsv)
az identity create -g rg-lab -n blob-reader
CID=$(az identity show -g rg-lab -n blob-reader --query clientId -o tsv)
az identity federated-credential create -g rg-lab --identity-name blob-reader --name s3lab-reader \
  --issuer "$ISSUER" --subject system:serviceaccount:s3-lab:reader --audiences api://AzureADTokenExchange
kubectl -n s3-lab create sa reader && kubectl -n s3-lab annotate sa reader azure.workload.identity/client-id=$CID
# Pod: metadata.labels: {azure.workload.identity/use: "true"}, spec.serviceAccountName: reader

GKE Workload Identity Federation

    

      
    
        
  • 풀. 클러스터에서 켜면 프로젝트의 워크로드 아이덴티티 풀 PROJECT_ID.svc.id.goog에 Kubernetes SA가 주체로 나타납니다.
    • 
        
  • 두 가지 연결 방식. (1) 직접 주체 권한: IAM 정책에 principal://iam.googleapis.com/projects/NUM/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NS/sa/KSA를 직접 바인딩. (2) GSA 가장: KSA에 iam.gke.io/gcp-service-account 어노테이션, GSA에 roles/iam.workloadIdentityUser. 새 구성은 (1)이 단순하고, 일부 서비스가 GSA를 요구하면 (2).
    • 
        
  • 전달 경로. 노드의 GKE 메타데이터 서버가 169.254.169.254 요청을 가로채 Pod의 KSA에 맞는 토큰을 줍니다. 노드 VM의 서비스 계정 권한은 Pod에 노출되지 않습니다.
    • 
        
  • 신원 동일성. 같은 프로젝트(풀)에 있는 모든 클러스터의 같은 네임스페이스·같은 SA 이름은 같은 신원입니다. 개발 클러스터의 payments/api가 운영 클러스터의 payments/api와 같은 권한을 얻습니다(10장 사례). 환경별 프로젝트 분리 또는 네임스페이스 이름 규칙이 경계입니다.
    •

gcloud container clusters update lab-gke --location asia-northeast3-a --workload-pool=$PROJECT.svc.id.goog
gcloud storage buckets add-iam-policy-binding gs://$PROJECT-wi-lab --role roles/storage.objectViewer \
  --member "principal://iam.googleapis.com/projects/$NUM/locations/global/workloadIdentityPools/$PROJECT.svc.id.goog/subject/ns/s3-lab/sa/reader"

OpenShift: STS 모드와 Cloud Credential Operator

    

      
CCO 모드동작장단점

      
        
Mint설치 시 준 관리자 자격 증명으로 컴포넌트별 자격 증명을 만들어 Secret에 넣음편하지만 클러스터 안에 장기 자격 증명과 강한 관리자 키

        
Passthrough설치 자격 증명을 컴포넌트들이 그대로 나눠 씀가장 넓은 권한 공유

        
Manual관리자가 CredentialsRequest를 보고 자격 증명을 직접 준비통제는 좋지만 수작업

        
Manual + 단기 토큰(STS·Azure WI·GCP WIF)ccoctl이 발급자 공개 문서(예: S3)와 컴포넌트별 클라우드 역할을 만들고, 컴포넌트는 SA 토큰으로 단기 자격 증명을 받음클러스터 안에 장기 키 없음. ROSA·ARO는 이 방식이 기본 또는 권장

      
    

    
플랫폼 컴포넌트(이미지 레지스트리, 인그레스, CSI 드라이버) 외에 사용자 워크로드도 같은 방식을 쓸 수 있습니다. AWS 위 OpenShift는 IRSA와 같은 원리의 웹훅으로 SA 어노테이션 기반 역할 연결을 제공합니다. 12편의 “CSI 컨트롤러 권한 누락” 사례가 OpenShift에서는 CredentialsRequest와 ccoctl 산출물 불일치로 나타납니다.

온프렘: SPIFFE/SPIRE

    
쉬운 말로
    SPIFFE는 “모든 프로그램에 붙이는 주민등록번호 형식”(spiffe://회사/ns/결제/sa/api)이고, SPIRE는 그 번호로 신분증(SVID)을 발급하는 동사무소입니다. 동사무소 직원(에이전트)이 각 노드에 상주하며 “이 프로세스가 정말 결제 팀 Pod인가”를 Kubernetes에 확인한 뒤에만 신분증을 내줍니다.

    

      
개념설명

      
        
SPIFFE ID·신뢰 도메인spiffe://lab.local/ns/s3-lab/sa/reader. 신뢰 도메인(lab.local) 안에서 유일

        
SVID신원 증명서. X.509-SVID(mTLS용, 짧은 수명 자동 갱신)와 JWT-SVID(대상 지정 토큰)

        
노드 증명에이전트가 서버에 자기 노드를 증명(Kubernetes에서는 PSAT: 대상이 SPIRE인 SA 토큰)

        
워크로드 증명에이전트가 워크로드 API 소켓에 접속한 프로세스를 kubelet에 확인해 네임스페이스·SA·레이블을 알아냄

        
등록 항목어떤 조건의 워크로드에 어떤 SPIFFE ID를 줄지. SPIRE 컨트롤러 매니저의 ClusterSPIFFEID CRD로 선언

        
Workload API·CSI 드라이버Pod가 SVID를 받는 유닉스 소켓. SPIFFE CSI 드라이버로 hostPath 없이 마운트

        
OIDC Discovery Provider·제휴JWT-SVID 공개 키를 OIDC 형식으로 공개 → AWS·Azure·GCP가 OIDC 공급자로 신뢰. 다른 신뢰 도메인과의 제휴도 가능

      
    

    
현장 메모: 셀프 호스팅 IRSA라는 더 단순한 대안
    온프렘 kubeadm·RKE2에서 AWS만 쓰면 된다면, SPIRE 없이 클러스터의 SA 발급자 문서를 S3 같은 공개 위치에 두고 IRSA와 같은 웹훅(amazon-eks-pod-identity-webhook)을 설치하는 방법도 있습니다. SPIRE는 여러 클러스터·VM·클라우드를 하나의 신원 체계로 묶거나, 메시 없이 mTLS가 필요할 때 가치가 큽니다. 실습 3은 SPIRE로 하되 이 대안과 비교해 보세요.

크로스 클라우드 제휴와 컨트롤러·CI 신원 설계

    

      
출발도착방법

      
        
EKS PodGCPGCP 인력·워크로드 아이덴티티 풀에 EKS 클러스터 발급자를 OIDC 공급자로 등록(또는 AWS 공급자로 IAM 역할 신뢰) → Pod의 SA 토큰으로 GCP 토큰 교환

        
GKE PodAWSGoogle이 발급한 ID 토큰(대상: sts.amazonaws.com)으로 AssumeRoleWithWebIdentity(accounts.google.com 공급자, sub = GSA 고유 ID)

        
AKS PodAWS·GCPAKS OIDC 발급자를 대상 클라우드에 OIDC 공급자로 등록

        
온프렘 Pod모든 클라우드SPIRE JWT-SVID 또는 셀프 호스팅 발급자를 각 클라우드에 등록

        
CI(GitHub Actions 등)클라우드·클러스터CI가 발급한 OIDC 토큰을 클라우드 역할과 Kubernetes(17편 구조화된 인증 설정)에 동시에 신뢰

      
    

    

      
설계 원칙

      
    
        
  1. 정적 키 0개를 목표로. Secret에 들어 있는 클라우드 액세스 키를 목록으로 만들고 하나씩 워크로드 아이덴티티로 옮깁니다. 18편 사례처럼 Secret 읽기 권한이 곧 클라우드 권한이 되는 경로가 사라집니다.
    2. 
        
  2. 컨트롤러마다 전용 SA·전용 역할. 외부 DNS, 로드 밸런서 컨트롤러, CSI 드라이버, 백업 도구(15편)가 같은 SA·같은 역할을 공유하지 않게 합니다.
    3. 
        
  3. 신뢰 조건은 정확히. sub는 네임스페이스와 SA까지, aud는 반드시. 클러스터가 여럿이면 발급자로 구분합니다.
    4. 
        
  4. 강한 신원은 강한 네임스페이스에. Pod를 만들 수 있는 사람은 그 네임스페이스의 SA 신원을 쓸 수 있습니다(18편 실습 3). 클라우드 관리자급 역할을 가진 SA는 전용 네임스페이스로.
    5. 
        
  5. CI 러너는 작업 단위 신원. 클러스터 안 러너(Actions Runner Controller, GitLab Runner)는 작업마다 짧은 토큰을 받고, 저장소·브랜치 조건으로 클라우드 역할을 좁힙니다.
    6. 
        
  6. 감사 추적. 클라우드 감사 로그에 남는 세션 이름·태그로 어떤 클러스터·네임스페이스·SA였는지 알 수 있게 구성합니다(Pod Identity 세션 태그, GKE 주체 문자열).
    7.

실습: 같은 “S3 읽기 전용 Pod”를 세 방식으로

    

      
같은 버킷·같은 읽기 정책을 IRSA(lab-eks), Pod Identity(lab-eks), SPIRE(lab-native)로 각각 연결합니다. 세 경우 모두 Pod에 정적 키는 없습니다. 각 실습에서 토큰의 iss·aud·sub, 자격 증명이 들어오는 경로, 클라우드 감사 로그의 흔적을 기록해 마지막에 비교표를 채웁니다.

      
실습 0. 공통: 버킷과 읽기 정책

    

    
호스트에서
REGION=ap-northeast-2; ACC=$(aws sts get-caller-identity --query Account --output text)
B=wi-lab-$ACC
aws s3 mb s3://$B --region $REGION
echo "hello from $B" > hello.txt && aws s3 cp hello.txt s3://$B/hello.txt
aws iam create-policy --policy-name wi-lab-s3-read --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[
 {\"Effect\":\"Allow\",\"Action\":[\"s3:ListBucket\"],\"Resource\":\"arn:aws:s3:::$B\"},
 {\"Effect\":\"Allow\",\"Action\":[\"s3:GetObject\"],\"Resource\":\"arn:aws:s3:::$B/*\"}]}"
POL=arn:aws:iam::$ACC:policy/wi-lab-s3-read
dec(){ cut -d. -f2 | tr '_-' '/+' | base64 -d 2>/dev/null | jq '{iss,aud,sub,exp}'; }   # JWT 본문 보기

OIDC 공급자·역할·SA·Pod
kubectl config use-context lab-eks
eksctl utils associate-iam-oidc-provider --cluster lab-eks --approve
ISS=$(aws eks describe-cluster --name lab-eks --query cluster.identity.oidc.issuer --output text | sed 's#https://##')
# 3장 생성기(IRSA, 발급자=$ISS, ns=s3-lab, sa=reader-irsa, 정확히 일치, aud 넣음)의 결과를 trust-irsa.json으로 저장
aws iam create-role --role-name wi-lab-irsa --assume-role-policy-document file://trust-irsa.json >/dev/null
aws iam attach-role-policy --role-name wi-lab-irsa --policy-arn $POL
kubectl create ns s3-lab
kubectl -n s3-lab create sa reader-irsa
kubectl -n s3-lab annotate sa reader-irsa eks.amazonaws.com/role-arn=arn:aws:iam::$ACC:role/wi-lab-irsa
mkpod(){ kubectl -n s3-lab run $1 --image=amazon/aws-cli:2.22.0 --restart=Never \
  --overrides="{\"spec\":{\"serviceAccountName\":\"$2\"}}" --command -- sleep 3600

kubectl -n s3-lab exec irsa -- aws s3 cp s3://$B/hello.txt -

실습 3. SPIRE + 셀프 호스팅 OIDC (lab-native → S3)

      
AWS가 SPIRE의 JWT 공개 키를 읽으려면 발급자 문서가 인터넷에서 HTTPS로 보여야 합니다. 운영에서는 SPIRE OIDC Discovery Provider를 공개 인그레스 뒤에 두지만, 실습에서는 문서 두 개를 S3에 올려 발급자로 씁니다. SPIRE는 서명 키를 주기적으로 바꾸므로 키 문서를 다시 올리는 동기화가 필요하다는 점이 이 방식의 한계입니다.

    
(1) 발급자 문서용 버킷
OB=wi-lab-oidc-$ACC; aws s3 mb s3://$OB --region $REGION
OIDC_HOST=$OB.s3.$REGION.amazonaws.com
aws s3api put-public-access-block --bucket $OB --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=false,RestrictPublicBuckets=false
aws s3api put-bucket-policy --bucket $OB --policy "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":\"*\",\"Action\":\"s3:GetObject\",
  \"Resource\":[\"arn:aws:s3:::$OB/.well-known/openid-configuration\",\"arn:aws:s3:::$OB/keys\"]}]}"

    
(2) SPIRE 설치 (spiffe/helm-charts-hardened)
kubectl config use-context lab-native
helm repo add spiffe https://spiffe.github.io/helm-charts-hardened/ && helm repo update
helm upgrade --install -n spire-mgmt spire-crds spiffe/spire-crds --create-namespace
cat > spire-values.yaml <<EOF
global:
  spire:
    trustDomain: lab.local
    clusterName: lab-native
    jwtIssuer: https://$OIDC_HOST          # JWT-SVID의 iss (차트 버전의 values 키 이름 확인)
spiffe-oidc-discovery-provider:
  enabled: true
EOF
helm upgrade --install -n spire-mgmt spire spiffe/spire -f spire-values.yaml --wait
kubectl get pods -A | grep -E 'spire|spiffe'                          # server, agent(DaemonSet), CSI 드라이버, OIDC provider
kubectl get clusterspiffeid                                           # 기본 항목: spiffe://lab.local/ns/{ns}/sa/{sa}

    
(3) 키 문서 게시와 IAM 공급자·역할
sync_oidc(){
  OSVC=$(kubectl get svc -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}' | grep oidc-discovery | head -1)
  kubectl -n ${OSVC%/*} port-forward svc/${OSVC#*/} 18443:443 >/dev/null 2>&1 & PF=$!; sleep 3
  curl -sk https://localhost:18443/keys > keys.json; kill $PF
  jq -n --arg h "https://$OIDC_HOST" '{issuer:$h, jwks_uri:($h+"/keys"), response_types_supported:["id_token"], subject_types_supported:["public"], id_token_signing_alg_values_supported:["RS256","ES256","ES384"]}' > openid-configuration
  aws s3 cp openid-configuration s3://$OB/.well-known/openid-configuration --content-type application/json >/dev/null
  aws s3 cp keys.json s3://$OB/keys --content-type application/json >/dev/null; echo "synced $(jq '.keys|length' keys.json) keys"; }
sync_oidc                                                             # 키가 바뀌면 다시 실행(운영은 공개 엔드포인트로)
aws iam create-open-id-connect-provider --url https://$OIDC_HOST --client-id-list sts.amazonaws.com
# CLI 버전에 따라 --thumbprint-list가 필수면 공급자 인증서 지문을 넣음
# 3장 생성기(SPIRE, 발급자=$OIDC_HOST, ns=s3-lab, sa=reader-spire)의 결과를 trust-spire.json으로
aws iam create-role --role-name wi-lab-spire --assume-role-policy-document file://trust-spire.json >/dev/null
aws iam attach-role-policy --role-name wi-lab-spire --policy-arn $POL

    
(4) spiffe-helper 사이드카로 JWT-SVID를 파일로 받는 Pod
kubectl create ns s3-lab; kubectl -n s3-lab create sa reader-spire
kubectl -n s3-lab apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata: {name: helper-conf}
data:
  helper.conf: |
    agent_address = "/spiffe-workload-api/spire-agent.sock"
    cmd = ""
    cert_dir = "/svid"
    svid_file_name = "svid.pem"
    svid_key_file_name = "svid_key.pem"
    svid_bundle_file_name = "bundle.pem"
    jwt_svids = [{ jwt_audience = "sts.amazonaws.com", jwt_svid_file_name = "jwt_svid.token" }]
    daemon_mode = true
---
apiVersion: v1
kind: Pod
metadata: {name: spire}
spec:
  serviceAccountName: reader-spire
  containers:
  - name: helper
    image: ghcr.io/spiffe/spiffe-helper:0.10.0            # 최신 버전과 설정 키 이름 확인
    args: ["-config", "/conf/helper.conf"]
    volumeMounts: [{name: wl, mountPath: /spiffe-workload-api, readOnly: true}, {name: svid, mountPath: /svid}, {name: conf, mountPath: /conf}]
  - name: aws
    image: amazon/aws-cli:2.22.0
    command: ["sleep", "3600"]
    env:
    - {name: AWS_ROLE_ARN, value: "arn:aws:iam::$ACC:role/wi-lab-spire"}
    - {name: AWS_WEB_IDENTITY_TOKEN_FILE, value: /svid/jwt_svid.token}    # IRSA와 같은 SDK 경로를 재사용
    - {name: AWS_REGION, value: $REGION}
    volumeMounts: [{name: svid, mountPath: /svid, readOnly: true}]
  volumes:
  - {name: wl, csi: {driver: csi.spiffe.io, readOnly: true}}
  - {name: svid, emptyDir: {}}
  - {name: conf, configMap: {name: helper-conf}}
EOF
kubectl -n s3-lab wait pod/spire --for=condition=Ready --timeout=180s
kubectl -n s3-lab exec spire -c aws -- cat /svid/jwt_svid.token | dec     # iss=https://$OIDC_HOST, sub=spiffe://lab.local/ns/s3-lab/sa/reader-spire
kubectl -n s3-lab exec spire -c aws -- aws sts get-caller-identity
kubectl -n s3-lab exec spire -c aws -- aws s3 cp s3://$B/hello.txt -

    
비교표 채우기
    방식(IRSA·Pod Identity·SPIRE) × 항목: 토큰 발급자(iss), 대상(aud), 주체(sub), 역할 매핑 위치(SA 어노테이션·EKS API·SPIRE 등록 + IAM 신뢰 정책), 자격 증명 전달 경로(STS 직접·노드 에이전트·STS 직접), 클러스터 밖 공개가 필요한 것, 세션 태그·감사 로그의 흔적, 키 회전 부담. 3장 표와 맨 위 비교기 결과와 대조하세요.

aws s3 rb s3://$B --force; aws s3 rb s3://$OB --force

현장 사례

    
신뢰 정책의 와일드카드로 클러스터 전체가 운영 버킷에 접근했다

      
원인. IRSA 역할 신뢰 정책의 sub 조건을 system:serviceaccount:*:*로 둬 “나중에 SA 이름이 바뀌어도 동작”하게 했습니다. 개발자가 다른 네임스페이스에서 같은 역할 어노테이션을 단 SA로 Pod를 띄우자 운영 버킷에 접근했습니다.

      
교훈. sub는 네임스페이스와 SA까지 정확히, aud도 반드시. 생성기 경고를 리뷰 체크리스트로 쓰세요.

    

    
개발 클러스터의 Pod가 운영 GCS 버킷을 읽었다

      
원인. 개발·운영 GKE 클러스터가 같은 프로젝트에 있었고, 두 클러스터의 payments/api SA가 워크로드 아이덴티티 풀에서 같은 신원이었습니다.

      
교훈. GKE 신원 동일성은 프로젝트(풀) 단위입니다. 환경별 프로젝트를 분리하세요.

    

    
Secret에 넣어 둔 액세스 키가 유출됐다

      
원인. 백업 도구가 S3 액세스 키를 Secret에 담아 쓰고 있었고, Secret list 권한이 있던 인벤토리 도구(18편 사례)의 토큰이 유출되며 키도 함께 나갔습니다. 키는 만료가 없었습니다.

      
교훈. 클라우드 자격 증명은 워크로드 아이덴티티로 바꾸고 정적 키를 폐기하세요. Velero(15편)도 IRSA·Pod Identity를 지원합니다.

    

    
앱 취약점으로 기본 SA 토큰이 쓰였다

      
원인. API를 쓰지 않는 웹 앱에도 default SA 토큰이 마운트되어 있었고, 누군가 그 default SA에 편의상 view를 바인딩해 둔 상태였습니다. 원격 코드 실행 취약점으로 들어온 공격자가 토큰으로 클러스터 구조를 탐색했습니다.

      
교훈. default SA에 권한을 주지 말고, 자동 마운트를 끄고, 21편 정책으로 강제하세요.

    

    
앱이 받은 SA 토큰을 외부 서비스에 그대로 넘겼다

      
원인. 사내 서비스 인증에 Kubernetes SA 토큰(대상: API 서버)을 그대로 보냈고, 그 서비스가 침해되자 토큰이 API 서버 호출에 재사용되었습니다.

      
교훈. 외부로 보내는 토큰은 그 서비스 전용 audience로 따로 받으세요(1장 프로젝티드 토큰).

    

    
AKS 워크로드 아이덴티티가 특정 네임스페이스에서만 실패

      
원인. 페더레이션 자격 증명의 주체 문자열에 네임스페이스 이름 오타가 있었고, 동시에 관리 ID 하나에 붙일 수 있는 자격 증명 한도에 가까워 새 항목을 추가하지 못하고 있었습니다.

      
교훈. 주체 문자열은 IaC로 생성하고, 앱·환경 단위로 관리 ID를 나누세요.

    

    
Pod Identity로 옮긴 뒤 일부 Pod만 자격 증명을 못 받았다

      
원인. 9편의 기본 거부 이그레스 정책이 있는 네임스페이스에서 에이전트 주소(169.254.170.23)로 가는 트래픽이 막혔습니다. 또 연결을 만들기 전에 떠 있던 Pod에는 환경 변수가 주입되지 않았습니다.

      
교훈. 링크 로컬 이그레스 허용을 정책 템플릿에 넣고, 연결 생성 후 Pod를 재시작하세요.

    

    
SA 발급자를 바꿨더니 IRSA가 모두 실패했다

      
원인. 셀프 호스팅 클러스터에서 --service-account-issuer를 새 주소로 바꾸면서 옛 발급자를 남기지 않았습니다. 기존 토큰과 클라우드의 OIDC 공급자 설정이 모두 어긋났습니다.

      
교훈. 발급자 플래그는 여러 개를 지정해 새·옛 발급자를 함께 받는 기간을 두고, 클라우드 공급자 설정을 먼저 추가한 뒤 바꾸세요.

    

    
SPIRE 서버 장애가 전체 서비스 장애로 번졌다

      
원인. SPIRE 서버가 단일 인스턴스였고 SVID 수명이 짧아, 서버가 내려간 동안 갱신하지 못한 SVID가 만료되며 mTLS·클라우드 접근이 줄줄이 실패했습니다.

      
교훈. 신원 시스템은 가장 높은 가용성 등급으로: 서버 다중화, 데이터스토어 백업, SVID 수명과 서버 복구 목표의 관계를 설계하세요.

정리, 다음 편, 참고 자료

    

      
이 편의 핵심 다섯 줄

      
    
        
  1. ServiceAccount 토큰은 대상·만료·묶인 Pod를 가진 바운드 토큰이 표준이며, API를 부르지 않는 Pod는 자동 마운트를 끄고 외부용 토큰은 전용 대상으로 따로 받습니다.
    2. 
        
  2. 워크로드 아이덴티티는 OIDC 제휴, 에이전트 중개, SPIFFE 세 원리이며, 어느 경우든 신뢰 조건(sub·aud)이 실제 보안 경계입니다.
    3. 
        
  3. EKS는 IRSA(OIDC 제휴, SA 어노테이션)와 Pod Identity(에이전트, EKS API 연결, 세션 태그)를 제공하고, AKS는 UAMI + 페더레이션 자격 증명, GKE는 풀 기반 직접 주체 바인딩과 프로젝트 단위 신원 동일성이 특징입니다.
    4. 
        
  4. OpenShift는 CCO Manual + 단기 토큰(STS 등) 모드로 플랫폼 컴포넌트의 장기 키를 없애고, 온프렘은 SPIRE 또는 셀프 호스팅 발급자로 클라우드와 제휴합니다.
    5. 
        
  5. 정적 키 0개를 목표로, 컨트롤러마다 전용 SA·역할, 강한 신원은 전용 네임스페이스, CI는 작업 단위 OIDC 토큰으로 설계합니다.
    6. 
      

    

    

      
다음 편 · 21편 어드미션 제어와 정책

      
Pod Security Admission(privileged·baseline·restricted)과 PSP 이후, ValidatingAdmissionPolicy와 MutatingAdmissionPolicy(CEL), Kyverno·OPA Gatekeeper와의 비교, OpenShift SCC·GKE Policy Controller·AKS Azure Policy 같은 벤더 정책 계층을 다룹니다. 이 편과 18편에서 RBAC으로 막지 못한 것(특정 SA로 Pod 생성, 자동 마운트 강제 해제, 특권 컨테이너)을 정책으로 막고, 같은 규칙을 VAP·Kyverno·Gatekeeper로 각각 구현해 비교합니다.
