Level 3 RBAC과 접근 제어, 18편

RBAC 모델 완전 해부

17편에서 API 서버가 “누구”인지 알아냈다면, 이제 “무엇을 해도 되는가”입니다. RBAC은 규칙이 단순해 보여 쉽게 쓰지만, 실제 사고는 대부분 규칙이 의도와 다르게 넓은 곳에서 납니다. ClusterRoleBinding 하나, 별표(*) 하나, list 하나, pods 생성 권한 하나가 클러스터 전체를 여는 열쇠가 됩니다. 이 편은 네 객체의 조합 규칙부터 서브리소스·이름 제한·URL 규칙의 함정, 권한 상승을 막는 escalate·bind·impersonate 동사, 기본 역할의 실제 범위를 해부하고, 조직 역할 다섯 가지를 모델링해 검증합니다.

이 사람이 이걸 할 수 있나: RBAC 판정기

7장 조직 역할 모델(실습에서 배포하는 정책)이 미리 들어 있습니다. 사람과 요청을 고르면 허용·거부와 함께 어느 바인딩의 어느 규칙이 허용했는지, 또는 왜 아무것도 맞지 않았는지가 나옵니다. 위험한 조합이면 경고도 함께 나옵니다. 바인딩을 꺼 보며 영향을 확인할 수 있습니다.

0

읽는 법과 목표

쉬운 말로 Role은 “이 방에서 할 수 있는 일 목록”(예: 서류 열람, 서류 작성), ClusterRole은 “모든 방과 복도에 쓸 수 있는 일 목록”입니다. Binding은 그 목록을 사람이나 부서(그룹)에 주는 임명장입니다. RoleBinding은 “이 방에서만” 유효한 임명장, ClusterRoleBinding은 “건물 전체에서” 유효한 임명장입니다. RBAC에는 “금지” 목록이 없고 허용만 더해집니다. 그래서 한 번 넓게 준 권한은 다른 규칙으로 줄일 수 없습니다.

이 편을 마치면 할 수 있는 것

  • Role·ClusterRole·RoleBinding·ClusterRoleBinding의 네 가지 조합이 각각 어디에 권한을 주는지 정확히 말할 수 있습니다.
  • 동사·apiGroups·리소스·서브리소스·resourceNames·nonResourceURLs 규칙의 함정을 피할 수 있습니다.
  • escalate·bind·impersonate 동사와 바인딩 시점의 권한 검사로 권한 상승이 막히는 원리를 설명할 수 있습니다.
  • aggregated ClusterRole로 CRD 권한을 기본 역할에 끼워 넣을 수 있습니다.
  • admin·edit·view와 system:* 역할의 실제 범위를 알고, 조직 역할 다섯 가지를 모델링·검증할 수 있습니다.
1

네 객체와 조합 규칙

바인딩 \ 역할Role(네임스페이스 안)ClusterRole(클러스터 범위 정의)
RoleBinding(네임스페이스 안)그 네임스페이스에서 Role의 권한그 네임스페이스에서만 ClusterRole의 권한(공통 역할 재사용의 정석: admin·edit·view)
ClusterRoleBinding불가(참조할 수 없음)모든 네임스페이스 + 클러스터 범위 리소스 + nonResourceURLs
  • 주체(subjects). User(이름), Group(그룹), ServiceAccount(네임스페이스+이름). 17편에서 본 문자열이 그대로 쓰입니다. ServiceAccount 전체는 그룹 system:serviceaccounts:<ns>로 지정할 수 있습니다.
  • 허용만 있음. 거부 규칙이 없습니다. 여러 바인딩의 권한은 합쳐집니다. “다 주고 하나만 빼기”는 RBAC으로 불가능하며, 필요하면 어드미션 정책(21편)으로 막습니다.
  • roleRef는 바꿀 수 없음. 바인딩이 가리키는 역할은 생성 후 수정할 수 없습니다. 바꾸려면 지우고 다시 만듭니다(kubectl auth reconcile이 이를 처리).
  • 클러스터 범위 리소스(nodes, namespaces, PV, StorageClass, CRD, ClusterRole 자체)는 RoleBinding으로 줄 수 없고 ClusterRoleBinding이 필요합니다.
  • 인가 모드. 보통 Node,RBAC 순서입니다. Node 인가기는 kubelet이 자기 노드의 Pod 관련 객체만 보게 합니다. 웹훅 인가(클라우드 IAM 연동, 19편)가 앞에 붙기도 하며, 1.32부터 구조화된 인가 설정 파일로 순서·조건을 정합니다.
같은 ClusterRole, 다른 범위
# team-dev 안에서만 edit
kubectl -n team-dev create rolebinding dev-edit --clusterrole=edit --group=oidc:dev-team
# 모든 네임스페이스(kube-system 포함!)에서 edit — 실수로 자주 만드는 바인딩
kubectl create clusterrolebinding dev-edit-all --clusterrole=edit --group=oidc:dev-team
# 확인
kubectl auth can-i get secrets -n kube-system --as=oidc:bob --as-group=oidc:dev-team

규칙 한 줄 해부: 동사·리소스·이름·URL

규칙의 다섯 칸
rules:
- apiGroups: ["apps"]                 # "" = core(pods, secrets…), "apps", "batch", CRD 그룹…
  resources: ["deployments", "deployments/scale"]   # 리소스/서브리소스
  verbs: ["get", "list", "watch", "patch"]
  resourceNames: ["web"]              # 선택: 특정 이름만
- nonResourceURLs: ["/metrics", "/healthz/*"]       # 리소스가 아닌 경로(ClusterRole + ClusterRoleBinding에서만)
  verbs: ["get"]
칸함정대책
verbslist·watch는 객체 내용 전체를 돌려줌. Secret에 list만 줘도 값이 모두 보임. *은 escalate·bind·impersonate 같은 특수 동사까지 포함Secret은 get만, 그것도 resourceNames로. * 동사 금지
apiGroups·resources *앞으로 설치될 CRD까지 자동 포함(인증서·비밀을 다루는 CRD 포함)명시적 목록. 오퍼레이터 설치 시 요구 권한 검토
resourceNameslist·watch(이름 필드 선택 없이)와 create(이름을 미리 모름), deletecollection에는 효과가 없거나 의도대로 동작하지 않음이름 제한은 get·update·patch·delete에. 생성 제한은 어드미션 정책으로
서브리소스pods 권한이 pods/exec를 포함하지 않음(반대도). pods/log는 별도. * 리소스는 서브리소스까지 포함필요한 서브리소스를 명시(3장)
nonResourceURLsRoleBinding으로는 효과 없음. /metrics 등은 클러스터 정보 노출모니터링 전용 ClusterRole로 분리
apiGroups 누락Deployment 규칙을 ""(core)에 써서 동작 안 함kubectl api-resources로 그룹 확인
리소스·그룹·동사 확인 도구
kubectl api-resources -o wide | grep -E 'NAME|deployments|secrets|widgets'   # APIGROUP·NAMESPACED·VERBS
kubectl auth can-i --list -n team-dev --as=oidc:bob --as-group=oidc:dev-team
kubectl auth can-i create pods/exec -n team-dev --as=oidc:bob --as-group=oidc:dev-team
kubectl get --raw /apis/rbac.authorization.k8s.io/v1 | jq -r '.resources[].name'

권한 상승 방지: escalate·bind·impersonate

쉬운 말로 임명장을 쓸 수 있는 사람이 자기에게 사장 권한을 쓰면 안 됩니다. 그래서 Kubernetes는 “내가 가진 권한까지만 남에게(또는 역할에) 줄 수 있다”는 규칙을 둡니다. 예외를 허락하는 특별한 도장이 escalate(내게 없는 권한으로 역할을 만들기)와 bind(내게 없는 역할을 남에게 연결하기)이고, impersonate는 “다른 사람인 척하기” 도장입니다.
상황검사통과 조건
Role·ClusterRole 생성·수정새 규칙의 권한을 요청자가 이미 모두 갖고 있나(같은 범위에서)모두 보유, 또는 roles·clusterroles에 escalate 동사
RoleBinding·ClusterRoleBinding 생성·수정참조하는 역할의 권한을 바인딩 범위에서 요청자가 모두 갖고 있나모두 보유, 또는 그 역할에 대한 bind 동사(resourceNames로 특정 역할만 허용 가능)
가장(impersonation)users·groups·serviceaccounts·uids·userextras에 impersonate 동사가장 대상별로 허용. 1.36 베타의 제한된 가장은 가장한 신원으로 할 수 있는 동작까지 좁힐 수 있음

이 검사 덕분에 네임스페이스 admin인 팀 리드는 팀원에게 edit·view를 줄 수 있지만 cluster-admin은 줄 수 없습니다. 반대로 CI 계정에 “역할을 관리하라”며 escalate나 제한 없는 bind를 주면, 그 CI는 스스로 cluster-admin이 될 수 있습니다. 이 검사는 RBAC 객체를 통한 상승만 막습니다. 3장의 Pod 생성, Secret 열람, 노드 접근을 통한 상승은 막지 못합니다(22편에서 공격 경로로 재현).

바인딩 생성 검사기

bind를 특정 역할로만 허용하는 위임 패턴
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: {name: delegate-view-edit}
rules:
- apiGroups: ["rbac.authorization.k8s.io"]
  resources: ["rolebindings"]
  verbs: ["create", "delete", "get", "list"]
- apiGroups: ["rbac.authorization.k8s.io"]
  resources: ["clusterroles"]
  verbs: ["bind"]
  resourceNames: ["view", "edit"]          # 이 두 역할만 연결해 줄 수 있음
5

aggregated ClusterRole

aggregated ClusterRole은 규칙을 직접 적지 않고 aggregationRule의 레이블 선택자로 다른 ClusterRole의 규칙을 모읍니다. 컨트롤러가 결과 규칙을 채워 넣으므로 직접 고친 규칙은 덮어써집니다. 기본 admin·edit·view가 이 방식이라, CRD를 설치하면서 rbac.authorization.k8s.io/aggregate-to-view: "true" 레이블을 단 ClusterRole을 함께 두면 그 CRD 권한이 기존 view 사용자에게 자동으로 생깁니다.

CRD 권한을 기본 역할에 끼워 넣기 + 자체 집계 역할
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: widgets-view
  labels: {rbac.authorization.k8s.io/aggregate-to-view: "true"}
rules:
- {apiGroups: ["example.com"], resources: ["widgets"], verbs: ["get", "list", "watch"]}
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: widgets-edit
  labels: {rbac.authorization.k8s.io/aggregate-to-edit: "true"}
rules:
- {apiGroups: ["example.com"], resources: ["widgets"], verbs: ["create", "update", "patch", "delete"]}
---
# 회사 자체 집계 역할: monitoring.lab/aggregate=true 레이블이 붙은 규칙을 모두 모음
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: {name: monitoring-reader}
aggregationRule:
  clusterRoleSelectors:
  - matchLabels: {monitoring.lab/aggregate: "true"}
rules: []                                  # 컨트롤러가 채움
함정: 오퍼레이터가 몰래 넓히는 기본 역할 서드파티 차트가 aggregate-to-edit나 aggregate-to-admin 레이블을 단 ClusterRole을 설치하면, 기존 edit·admin 사용자 전원의 권한이 늘어납니다. 그 CRD가 비밀을 다루거나(인증서·자격 증명) Pod를 만들 수 있다면 의도치 않은 상승 경로가 됩니다. 설치 후 kubectl get clusterrole -l rbac.authorization.k8s.io/aggregate-to-edit=true로 목록을 확인하세요.
6

기본 ClusterRole의 실제 범위

역할할 수 있는 것오해하기 쉬운 점
cluster-admin모든 것(*)RoleBinding으로 주면 그 네임스페이스 안 모든 것. 클러스터 범위는 아님
admin네임스페이스 안 거의 모든 것 + Role·RoleBinding 관리ResourceQuota·네임스페이스 자체는 못 바꿈. RoleBinding으로 쓰는 것이 원래 용도
edit대부분 리소스 읽기·쓰기, Secret 읽기·쓰기, exec·portforward, ServiceAccount 가장Role·RoleBinding은 못 바꾸지만, Pod 생성과 SA 가장으로 그 네임스페이스 SA 권한을 모두 얻을 수 있음 → 사실상 네임스페이스 admin에 가까움
view대부분 리소스 읽기Secret은 제외(ServiceAccount 토큰 노출 방지). 하지만 ConfigMap·Pod 환경 변수·로그에 비밀이 있으면 그대로 보임
system:basic-user, system:discovery, system:public-info-viewer자기 권한 조회, API 탐색, 버전·헬스 정보system:authenticated(또는 일부는 비인증)에 기본 바인딩. 지우면 클라이언트가 동작하지 않음
system:node, system:kube-controller-manager 등컴포넌트 전용사람·앱에 바인딩 금지. 기본 역할은 API 서버 시작 시 자동 복원(autoupdate 어노테이션)
기본 역할의 실제 규칙을 직접 보기
kubectl get clusterrole edit -o json | jq -c '.rules[] | select(any(.resources[]?; test("secrets|serviceaccounts|pods/exec")))'
kubectl describe clusterrole view | grep -iE 'secrets|configmaps|pods/log'

현장 사례

개발자 그룹이 kube-system의 비밀을 읽을 수 있었다

원인. 개발 네임스페이스에 edit를 주려다 RoleBinding 대신 ClusterRoleBinding을 만들었습니다. edit는 Secret 읽기를 포함하므로 모든 네임스페이스의 비밀이 열렸습니다.

교훈. 공통 역할(admin·edit·view)은 RoleBinding으로만. ClusterRoleBinding으로 이 역할을 쓰는 것을 정책으로 금지하거나 정기 점검하세요.

“view만 줬는데” 데이터베이스 비밀번호가 유출됐다

원인. view는 Secret을 막지만, 앱이 비밀번호를 ConfigMap과 Pod 환경 변수에 넣어 두었고 로그에도 연결 문자열이 찍혔습니다.

교훈. view의 안전함은 비밀이 Secret에만 있다는 전제 위에 있습니다. 비밀 관리 규칙(22편)과 함께 점검하세요.

인벤토리 도구에 secrets list를 줬다

원인. “Secret 개수만 세는” 도구라며 list를 줬지만, list 응답에는 모든 Secret의 값이 들어 있었습니다.

교훈. 메타데이터만 필요하면 메타데이터 전용 조회(PartialObjectMetadata)를 쓰는 도구를 고르고, Secret list는 원칙적으로 주지 마세요.

오퍼레이터의 별표 권한이 새 CRD까지 삼켰다

원인. 한 오퍼레이터의 ClusterRole이 apiGroups: ["*"], resources: ["*"]였고, 나중에 설치된 인증서 관리 CRD와 비밀까지 접근 범위에 들어갔습니다.

교훈. 별표 규칙은 미래의 리소스까지 포함합니다. 설치 전 권한 검토를 체크리스트로 두세요.

모니터링 에이전트의 nodes/proxy로 노드가 장악됐다

원인. 메트릭 수집을 위해 준 nodes/proxy 권한을 가진 토큰이 유출되어, kubelet API를 통해 컨테이너 명령을 실행하는 데 쓰였습니다.

교훈. kubelet API 세분화 인가(1.36 GA)에 맞춰 nodes/metrics·nodes/stats 같은 좁은 권한으로 바꾸세요.

CI가 스스로 cluster-admin이 됐다

원인. “네임스페이스별 역할을 자동으로 만든다”는 이유로 CI 계정에 roles·clusterroles의 escalate와 제한 없는 bind를 주었습니다.

교훈. escalate·bind·impersonate는 cluster-admin과 동급입니다. 위임은 resourceNames로 특정 역할만 bind하게 하세요(4장).

개발자가 같은 네임스페이스의 배포 도구 SA를 빌렸다

원인. 배포 도구의 SA(클러스터 범위 권한)가 앱과 같은 네임스페이스에 있었고, Pod 생성 권한이 있는 개발자가 그 SA로 Pod를 띄웠습니다(실습 3).

교훈. 강한 SA는 전용 네임스페이스로. RBAC은 serviceAccountName을 제한하지 못하므로 어드미션 정책을 함께 쓰세요(21편).

GitOps가 RoleBinding 변경에서 계속 실패한다

원인. RoleBinding의 roleRef를 바꾸는 변경이었는데, roleRef는 수정 불가 필드라 apply가 거부되었습니다.

이 편의 핵심 다섯 줄

  1. RBAC은 허용만 더하는 모델이며, RoleBinding은 네임스페이스 안, ClusterRoleBinding은 모든 네임스페이스·클러스터 범위·URL에 권한을 줍니다. 공통 역할은 RoleBinding으로 씁니다.
  2. list·watch는 내용을 보여 주고, 별표는 미래의 리소스와 특수 동사까지 포함하며, resourceNames는 list·create에 효과가 없습니다.
  3. pods/exec·Pod 생성·Secret·nodes/proxy·SA 토큰·웹훅 설정·CSR 승인은 상승 경로가 되는 위험 권한입니다.
  4. escalate·bind·impersonate와 바인딩 시점 검사가 RBAC 객체를 통한 상승을 막지만, Pod 생성을 통한 SA 빌리기 같은 RBAC 밖의 상승은 막지 못합니다.
  5. admin·edit·view는 aggregation으로 넓어질 수 있고 edit는 사실상 네임스페이스 장악에 가깝습니다. 조직 역할은 그룹·네임스페이스 단위로 설계하고 can-i 행렬로 회귀 검증합니다.
