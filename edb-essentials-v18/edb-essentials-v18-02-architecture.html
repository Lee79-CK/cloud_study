1장

인스턴스와 데이터베이스 클러스터

아키텍처 공부는 두 단어를 구분하는 데서 시작합니다. 이 둘을 섞어 쓰면 뒤의 모든 설명이 흐려집니다.

  • 인스턴스(Instance) — 실행 중인 서버. 메모리에 올라간 프로세스들과 공유 메모리의 묶음입니다. 서버를 멈추면 사라집니다.
  • 데이터베이스 클러스터(Database Cluster) — 디스크에 있는 데이터 디렉터리 하나와 그 안의 모든 데이터베이스입니다. 서버를 멈춰도 남아 있습니다.

인스턴스 하나는 정확히 클러스터 하나를 관리하고, 클러스터 하나는 여러 데이터베이스(edb, postgres, template1, 사용자가 만든 DB 등)를 담습니다. 이 데이터 디렉터리를 흔히 환경변수 이름을 따서 PGDATA라고 부릅니다.

"클러스터"라는 말의 함정

PostgreSQL에서 "데이터베이스 클러스터"는 여러 서버를 묶은 고가용성 클러스터가 아닙니다. 서버 하나가 관리하는 데이터베이스들의 모음입니다. 시험에서 "database cluster"가 나오면 거의 항상 이 뜻이며, 고가용성 묶음은 보통 "HA cluster"처럼 따로 표현합니다.

비유: 도서관

클러스터는 도서관 건물과 서가(디스크의 책), 인스턴스는 개관 시간에 일하는 사서들과 대출 데스크(프로세스와 메모리)입니다. 문을 닫으면 사서는 퇴근하지만 책은 서가에 그대로 남습니다. 이 편 전체에서 이 비유를 계속 씁니다.

시험 포인트

EPAS를 패키지로 설치하면 기본 데이터 디렉터리는 RHEL 계열에서 /var/lib/edb/as18/data입니다. 커뮤니티 PostgreSQL의 /var/lib/pgsql/18/data와 구분해 두세요. 아키텍처 자체(프로세스, 메모리, 파일 구조)는 EPAS와 PostgreSQL이 같습니다. EPAS의 차이는 이 구조 위의 SQL·기능 계층에 있습니다.

2장

프로세스 구조

PostgreSQL 계열은 멀티 프로세스 구조입니다. 스레드 하나가 연결 하나를 맡는 방식이 아니라, 연결마다 운영체제 프로세스가 하나씩 생깁니다. 그래서 ps 명령으로 서버 내부 역할이 그대로 보입니다.

# EPAS 18 서버에서 프로세스 확인 (출력 모양은 예시)
$ ps -ef --forest | grep -v grep | grep -E 'edb-postgres|postgres:'
enterprisedb  1201     1  /usr/edb/as18/bin/edb-postgres -D /var/lib/edb/as18/data
enterprisedb  1202  1201   \_ postgres: logger
enterprisedb  1203  1201   \_ postgres: io worker 0
enterprisedb  1204  1201   \_ postgres: io worker 1
enterprisedb  1205  1201   \_ postgres: io worker 2
enterprisedb  1206  1201   \_ postgres: checkpointer
enterprisedb  1207  1201   \_ postgres: background writer
enterprisedb  1209  1201   \_ postgres: walwriter
enterprisedb  1210  1201   \_ postgres: autovacuum launcher
enterprisedb  1211  1201   \_ postgres: logical replication launcher
enterprisedb  1388  1201   \_ postgres: enterprisedb edb [local] idle

맨 위가 부모 프로세스인 postmaster이고, 나머지는 모두 그 자식입니다. EPAS에서는 서버 실행 파일 이름이 edb-postgres로 보입니다. 마지막 줄의 enterprisedb edb [local] idle은 "enterprisedb 사용자가 edb 데이터베이스에 로컬 소켓으로 접속해 쉬고 있는" 백엔드 프로세스입니다.

SQL로 프로세스 보기

ps에 접근할 수 없는 관리형 환경에서도 pg_stat_activity 뷰로 같은 정보를 볼 수 있습니다. backend_type 컬럼이 프로세스 종류입니다.

SELECT pid, backend_type, usename, datname, state
FROM   pg_stat_activity
ORDER  BY backend_type;
용어: 통계 수집기(stats collector)는 이제 없다

오래된 자료에는 "stats collector" 프로세스가 등장합니다. PostgreSQL 15부터 이 프로세스는 없어졌고, 누적 통계는 공유 메모리에서 관리되다가 정상 종료 시 pg_stat/ 디렉터리에 저장됩니다. 옛 교재로 공부할 때 주의하세요.

시험 포인트: background writer vs checkpointer

둘 다 dirty 페이지를 디스크에 쓰지만 목적이 다릅니다. background writer는 "빈 버퍼를 미리 확보"하려고 조금씩 쓰고, checkpointer는 "복구 시작 지점을 만들려고" 한 시점의 dirty 페이지를 전부 씁니다. "체크포인트를 수행하는 프로세스는?"의 정답은 checkpointer입니다.

3장

연결 요청과 응답

클라이언트가 psql -h db01 -p 5444 -U app -d sales로 접속할 때 벌어지는 일입니다.

① 연결 요청

클라이언트가 서버의 포트(EPAS 기본 5444)나 유닉스 소켓으로 연결을 요청합니다. postmaster가 받습니다.

② 백엔드 생성

postmaster가 fork로 이 연결 전용 백엔드 프로세스를 만들고 연결을 넘깁니다.

③ 인증

백엔드가 pg_hba.conf 규칙에 따라 사용자를 인증합니다. 실패하면 백엔드는 종료됩니다.

④ 요청 처리

인증에 성공하면 연결이 끊길 때까지 이 백엔드가 SQL을 받아 처리하고 결과를 돌려줍니다.

연결마다 프로세스를 새로 만드는 비용이 있기 때문에, 짧은 연결을 수없이 맺었다 끊는 애플리케이션에는 PgBouncer 같은 커넥션 풀러를 앞에 둡니다. 풀러는 11편에서 개요로 다룹니다.

현장 사례: "max_connections를 1000으로 올려 주세요"

애플리케이션 팀이 연결 부족 오류를 이유로 이런 요청을 하는 경우가 흔합니다. 연결 하나가 프로세스 하나이고, 4장에서 보듯 프로세스마다 로컬 메모리를 쓰기 때문에 무작정 올리면 메모리 부족으로 서버 전체가 위험해집니다. 보통은 커넥션 풀러를 먼저 검토합니다. 참고로 max_connections는 서버 재시작이 필요한 파라미터입니다.

4장

메모리 구조

메모리는 두 종류로 나뉩니다. 서버 시작 때 한 번 잡아서 모든 프로세스가 함께 쓰는 공유 메모리, 각 백엔드가 자기 작업을 위해 필요할 때 쓰는 로컬 메모리입니다.

파라미터종류기본값용도
shared_buffers공유128MB테이블·인덱스 페이지를 캐시하는 핵심 영역. 변경 시 재시작 필요
wal_buffers공유-1 (자동)디스크에 쓰기 전 WAL 레코드를 모아 두는 영역. 자동이면 shared_buffers의 1/32(최대 WAL 세그먼트 1개 크기)
work_mem로컬4MB정렬(ORDER BY), 해시 조인·집계 같은 작업 하나가 쓸 수 있는 메모리. 넘치면 임시 파일 사용
maintenance_work_mem로컬64MBVACUUM, CREATE INDEX 같은 유지보수 작업용
temp_buffers로컬8MB세션의 임시 테이블 캐시
effective_cache_size할당 없음4GB메모리를 잡지 않음. 옵티마이저에게 "OS 캐시까지 합치면 이 정도 캐시가 있다"고 알려 주는 힌트
시험 포인트: work_mem은 "연결당"이 아니라 "작업당"

쿼리 하나에 정렬 2개와 해시 조인 1개가 있으면 최대 work_mem의 3배 이상을 쓸 수 있습니다. 해시 작업은 hash_mem_multiplier(기본 2.0)만큼 더 쓸 수도 있습니다. 그리고 effective_cache_size는 실제로 메모리를 할당하지 않는다는 점이 단골 함정입니다.

비유: 도서관의 공용 열람대와 개인 책상

shared_buffers는 모든 사서가 함께 쓰는 공용 열람대입니다. 자주 찾는 책을 여기 펼쳐 두면 서가까지 가지 않아도 됩니다. work_mem은 사서 한 명이 책을 분류할 때 쓰는 개인 책상입니다. 책상이 작으면 바닥(임시 파일)에 늘어놓고 일하게 되어 느려집니다.

메모리 사용량 어림 계산기

대략적인 최악 사용량을 가늠해 보는 계산기입니다. 실제 사용량은 쿼리 형태에 따라 크게 달라지며, 운영 체제와 OS 페이지 캐시에 쓸 여유도 남겨야 합니다.

5장

읽기 경로와 비동기 I/O

SELECT * FROM orders WHERE id = 42;를 실행하면 백엔드는 해당 행이 들어 있는 8KB 페이지가 필요합니다.

  • shared_buffers에 있으면(캐시 적중, hit) — 바로 읽습니다. 가장 빠릅니다.
  • 없으면(miss) — 빈 버퍼를 하나 확보하고, 디스크에서 페이지를 읽어 그 버퍼에 올린 뒤 읽습니다. 이때 "디스크 읽기"는 먼저 운영체제의 페이지 캐시를 거치므로, OS 캐시에 있으면 실제 디스크까지 가지 않습니다.
  • 빈 버퍼가 없으면 — 오래 안 쓴 버퍼를 골라 내보냅니다(clock-sweep 방식). 골라낸 버퍼가 dirty면 먼저 디스크에 써야 해서 느려집니다. background writer가 이런 상황을 줄여 줍니다.

캐시 적중률은 이렇게 확인합니다. 운영 중인 OLTP 시스템이라면 보통 99% 안팎을 기대합니다.

SELECT datname,
       blks_hit, blks_read,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_ratio
FROM   pg_stat_database
WHERE  datname = current_database();
용어: 이중 버퍼링(Double buffering)

같은 페이지가 shared_buffers와 OS 페이지 캐시 양쪽에 올라가는 현상입니다. PostgreSQL은 OS 캐시를 적극 활용하도록 설계되어 있어서, shared_buffers를 서버 메모리의 대부분으로 잡지 않고 보통 1/4 정도에서 시작하는 것이 일반적인 권장입니다.

PostgreSQL 18의 비동기 I/O

예전에는 백엔드가 페이지를 하나 요청하고, 도착할 때까지 기다렸다가 다음 페이지를 요청했습니다. PostgreSQL 18은 필요한 페이지를 여러 개 한꺼번에 요청해 두고 도착하는 대로 처리하는 비동기 I/O를 도입했습니다. 순차 스캔, 비트맵 힙 스캔, VACUUM 같은 대량 읽기에서 효과가 큽니다.

io_method 값동작
worker (기본)io worker 프로세스들이 백엔드 대신 읽기를 수행합니다. 개수는 io_workers(기본 3)로 정합니다.
io_uring리눅스 커널의 io_uring 인터페이스를 직접 씁니다. 해당 기능을 포함해 빌드된 경우에만 선택할 수 있습니다.
sync이전 버전처럼 동기 방식으로 동작합니다.

io_method는 서버 재시작이 필요한 파라미터입니다. 동시에 몇 개까지 미리 요청할지는 effective_io_concurrency로 조절하며, PostgreSQL 18에서 기본값이 16으로 올라갔습니다.

6장

쓰기 경로와 WAL

여기가 이 편의 핵심입니다. 데이터를 바꿀 때 PostgreSQL은 데이터 파일을 바로 고치지 않습니다. 먼저 "무엇을 바꿨는지"를 WAL(Write-Ahead Log, 선행 기록 로그)에 쓰고, 그 WAL이 디스크에 안전하게 기록되면 커밋 완료를 알립니다. 실제 데이터 파일은 나중에 천천히 갱신됩니다.

용어: WAL (Write-Ahead Logging)

"데이터 파일을 고치기 전에 반드시 변경 기록을 먼저 남긴다"는 규칙이자, 그 기록 자체를 말합니다. 서버가 갑자기 죽어도 WAL이 남아 있으면 마지막 체크포인트 이후의 변경을 다시 적용해서(재생, replay) 데이터를 복구할 수 있습니다. 복제와 시점 복구(PITR)도 이 WAL을 이용합니다.

UPDATE 한 건 따라가기

"다음"을 눌러 단계별로 진행하세요. 각 단계에서 어느 위치의 상태가 바뀌는지 강조됩니다. 중간에 "여기서 장애 발생"을 눌러 보세요.

BEGIN;
UPDATE accounts SET balance = balance - 5000 WHERE id = 7;
COMMIT;
시험 포인트: 커밋 시점에 디스크에 반드시 쓰이는 것

COMMIT이 성공했다는 것은 WAL이 디스크(pg_wal)에 flush됐다는 뜻입니다(synchronous_commit = on, 기본값). 데이터 파일의 페이지는 아직 옛 상태일 수 있습니다. "커밋하면 변경된 데이터 페이지가 즉시 데이터 파일에 기록된다"는 선택지는 틀렸습니다.

WAL 관련 핵심 설정

파라미터기본값의미
wal_levelreplicaWAL에 담는 정보 수준. minimal < replica < logical. 복제·PITR에는 replica 이상, 논리 복제에는 logical
synchronous_commiton커밋 시 WAL flush를 기다릴지. off면 빠르지만 장애 시 최근 커밋 몇 건이 사라질 수 있음(데이터 손상은 아님)
fsyncon디스크에 실제로 기록됐는지 운영체제에 확인을 받을지. off는 장애 시 데이터 손상 위험이 있어 운영에서 금지
full_page_writeson체크포인트 후 페이지를 처음 수정할 때 페이지 전체를 WAL에 기록. 쓰다 만 페이지(torn page)로부터 복구하기 위함
wal_writer_delay200mswalwriter가 깨어나는 주기
synchronous_commit = off와 fsync = off는 완전히 다르다

synchronous_commit = off는 "최근 커밋 몇 건을 잃을 수 있지만 데이터베이스는 일관된 상태로 복구된다"이고, fsync = off는 "장애 시 데이터베이스 자체가 손상될 수 있다"입니다. 시험에서 둘을 바꿔 놓은 선택지가 나오기 쉽습니다.

7장

체크포인트와 background writer

WAL 덕분에 데이터 파일 갱신을 미룰 수 있지만, 무한정 미룰 수는 없습니다. 미룰수록 장애 후 재생해야 할 WAL이 늘어나 복구가 오래 걸리고, 보관해야 할 WAL 파일도 쌓입니다. 그래서 주기적으로 체크포인트를 합니다.

체크포인트는 "이 시점까지의 모든 변경은 데이터 파일에 반영됐다"는 표시입니다. checkpointer가 그 시점의 dirty 페이지를 모두 디스크에 쓰고, 체크포인트 레코드를 WAL에 남깁니다. 장애가 나면 마지막 체크포인트의 시작 지점(REDO 위치)부터 WAL을 재생하면 되고, 그 이전 WAL은 복구에 필요 없어져 재활용·삭제할 수 있습니다(아카이빙 중이면 아카이브가 끝난 뒤).

체크포인트가 일어나는 경우

  • checkpoint_timeout(기본 5분)이 지났을 때
  • 마지막 체크포인트 이후 쌓인 WAL이 max_wal_size(기본 1GB) 기준에 가까워졌을 때
  • 관리자가 CHECKPOINT 명령을 실행했을 때
  • 서버를 정상 종료(smart, fast 모드)할 때
  • pg_basebackup 같은 기본 백업을 시작할 때

체크포인트 쓰기를 한꺼번에 몰아서 하면 I/O가 튀기 때문에, checkpoint_completion_target(기본 0.9)에 따라 다음 체크포인트까지 시간의 90%에 걸쳐 나눠 씁니다.

체크포인트 간격 계산기

초당이 아니라 분당 WAL 생성량을 넣으세요. PostgreSQL은 WAL이 max_wal_size를 넘지 않도록 대략 max_wal_size ÷ (1 + checkpoint_completion_target)만큼 쌓이면 체크포인트를 요청합니다. 이 계산기는 그 근사식을 씁니다.

0분30분60분
시험 포인트

체크포인트가 너무 자주 일어나면 서버 로그에 "checkpoints are occurring too frequently" 경고가 남습니다(checkpoint_warning, 기본 30초 이내에 WAL 기준으로 연달아 발생할 때). 해결책은 대개 max_wal_size를 늘리는 것입니다. 체크포인트 통계는 PostgreSQL 17부터 pg_stat_bgwriter에서 분리된 pg_stat_checkpointer 뷰에서 봅니다.

background writer의 몫

background writer는 bgwriter_delay(기본 200ms)마다 깨어나서, 곧 재사용될 것 같은 dirty 버퍼를 최대 bgwriter_lru_maxpages(기본 100)개까지 미리 씁니다. 덕분에 백엔드가 빈 버퍼가 필요할 때 직접 디스크 쓰기를 하는 일이 줄어듭니다.

비유: 사서의 정리 방식

background writer는 틈틈이 열람대의 책 몇 권을 서가에 돌려놓는 사서입니다. 체크포인트는 "지금 열람대에 있는 책을 전부 서가에 정리하고 장부에 시각을 적는" 정기 정리입니다. 정전이 나도 장부(WAL)를 보고 마지막 정리 시각 이후의 대출·반납만 다시 맞추면 됩니다.

10장

파일과 페이지 내부

테이블 하나는 파일 몇 개인가

테이블과 인덱스는 각각 base/<데이터베이스 OID>/ 아래에 숫자 이름의 파일로 저장됩니다. 이 숫자를 relfilenode라고 합니다. 테이블 하나에는 보통 여러 파일이 딸려 있습니다.

파일 이름 예내용
16452본 데이터(main fork). 1GB를 넘으면 16452.1, 16452.2…로 나뉩니다(세그먼트).
16452_fsm여유 공간 맵(Free Space Map). 새 행을 넣을 빈 공간이 있는 페이지를 빨리 찾기 위함
16452_vm가시성 맵(Visibility Map). 모든 행이 모두에게 보이는 페이지를 표시해 VACUUM과 인덱스 전용 스캔을 빠르게 함
16452_initUNLOGGED 테이블에만 있는 초기화용 파일

파일 위치는 직접 찾을 필요 없이 함수로 확인합니다.

SELECT oid, datname FROM pg_database;            -- 데이터베이스 OID 확인
SELECT pg_relation_filepath('accounts');           -- 예: base/16384/16452
SELECT pg_size_pretty(pg_relation_size('accounts'));        -- 본 데이터 크기
SELECT pg_size_pretty(pg_total_relation_size('accounts'));  -- 인덱스·TOAST 포함
용어: OID와 relfilenode

OID(Object Identifier)는 데이터베이스 안의 객체마다 붙는 번호입니다. relfilenode는 테이블이 저장된 파일 번호로, 처음에는 테이블 OID와 같은 경우가 많지만 TRUNCATE, VACUUM FULL, CLUSTER처럼 파일을 새로 만드는 작업 후에는 달라집니다. 그래서 파일 이름으로 테이블을 추측하지 말고 pg_relation_filepath()를 씁니다.

8KB 페이지 한 장의 구조

데이터 파일은 8KB 크기의 페이지(블록)가 이어진 것입니다. 페이지 크기는 빌드할 때 정해지며 기본이 8KB입니다. 영역을 눌러 보세요.

0← 줄 포인터가 자라는 방향 · 튜플이 자라는 방향 →8192

WAL 파일 이름 읽기

pg_wal/의 파일은 기본 16MB 크기이며(initdb --wal-segsize로 변경 가능), 이름은 16진수 24자리입니다.

타임라인은 복구나 승격(스탠바이를 새 주 서버로 올리는 것)을 할 때마다 1씩 늘어납니다. PITR과 복제를 다루는 10·11편에서 다시 만납니다.

시험 포인트: 숫자 세트

페이지 8KB, 데이터 파일 세그먼트 1GB, WAL 세그먼트 16MB, WAL 파일 이름 24자리. 이 네 숫자는 표로 만들어 두세요.
