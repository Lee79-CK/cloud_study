SECTION 01

카디널리티 폭발

가장 비싼 실수입니다. 코드 한 줄로 월 비용이 수십 배가 되고, 쌓인 데이터는 되돌릴 수 없습니다.

왜 곱셈인가

메트릭 백엔드는 속성 조합 하나마다 독립된 시계열을 만듭니다. 속성이 늘어나면 더하기가 아니라 곱하기로 늘어납니다. 

// 안전한 조합
http.request.method (5) × http.route (20) × status_code (8)
  = 800개 시계열  ← 문제없음

// 여기에 사용자 ID 하나를 추가하면
800 × acme.user.id (50,000)
  = 40,000,000개 시계열  ← 시스템이 무너집니다

그리고 히스토그램은 조합 하나당 버킷 수만큼 시계열을 더 만듭니다. 버킷 10개짜리 히스토그램이면 조합당 12개 정도(버킷 + 합계 + 개수)가 됩니다. 계산기의 두 번째 숫자가 그것입니다.

위험한 속성을 알아보는 법

안전 — 값의 가짓수가 고정

HTTP 메서드, 상태 코드, 환경 이름, 결제 수단, 주문 채널. 목록으로 다 적을 수 있으면 안전합니다.

위험 — 값이 요청 수에 비례

사용자 ID, 주문 ID, 세션 ID, UUID, 타임스탬프, 이메일, IP 주소, 전체 URL. 다 적을 수 없으면 넣으면 안 됩니다.

중간 위험 — 조용히 늘어나는 것들

처음엔 안전해 보이지만 시간이 지나며 커지는 속성이 있습니다. 파드 이름은 배포할 때마다 새 값이 생깁니다. 하루 열 번 배포하면 한 달에 300개가 쌓입니다. 고객사 ID는 MSP 환경에서 계속 늘어납니다. 라우트도 동적 라우팅을 쓰면 무한정 늘어날 수 있습니다. 이런 것들은 "지금 몇 개인가"가 아니라 "1년 뒤 몇 개가 되는가"로 판단하세요.

그럼 사용자별 분석은 어떻게 하나

"특정 사용자의 요청만 보고 싶다"는 요구는 정당합니다. 다만 그건 메트릭이 아니라 트레이스의 일입니다.

넣을 곳고카디널리티 값이유
메트릭 속성절대 금지조합마다 시계열이 영구히 생성됨
Span 속성신중하게 허용샘플링으로 일부만 저장되고 시계열을 만들지 않음. 다만 개인정보 여부는 별개 문제
로그 본문적합검색용으로 설계된 저장소. trace_id로 연결하면 트레이스에서도 찾아갈 수 있음

직접 넣은 속성

가장 명백하고, 그래서 코드 리뷰로 잡을 수 있는 유일한 경로입니다.

예외 메시지

recordException은 메시지와 스택 트레이스를 담습니다. 예외 메시지에 사용자 데이터를 넣으면 함께 나갑니다.

DB 쿼리 원문

파라미터가 바인딩된 채로 기록되면 WHERE 절의 값이 그대로 남습니다.

Baggage

HTTP 헤더로 외부 API 호출까지 따라갑니다. 상대 서버 로그에 남을 수 있습니다.

로그 본문 전송

로그를 OTLP로 직접 보내면 기존 로그 마스킹 파이프라인을 우회하게 됩니다.

2차 방어선은 엔지니어가 준비합니다

개발자가 1차로 막고, 엔지니어가 Collector에서 금지 속성 키를 제거하는 규칙을 걸어 2차로 막습니다(9편). 다만 2차 방어선은 알려진 키만 막습니다. acme.customer.email은 걸러도 acme.user.contact는 통과합니다. 그래서 1차가 여전히 중요하고, 조직의 금지 속성 목록이 문서로 있어야 합니다(2편·11편).

SECTION 03

노이즈 — 데이터는 많은데 못 쓰는 상태

비용 문제만이 아닙니다. 트레이스가 300줄이면 아무도 열어보지 않습니다. 관측 가능성을 위해 만든 데이터가 관측을 방해하는 상태가 됩니다.

Span 남발

메서드마다, 루프 반복마다 Span. 트레이스 화면을 열면 스크롤이 끝나지 않고, 어느 것이 중요한지 알 수 없습니다.

헬스체크 계측

프로브 요청이 초당 수 건씩 들어옵니다. 전부 200 OK이고 정보 가치는 0인데, 데이터량의 절반을 차지합니다.

동적 Span 이름

process-order-8f3a처럼 만들면 같은 작업을 묶어 볼 수 없습니다. 이름은 라우트처럼 템플릿이어야 합니다.

ERROR 남발

정상적인 비즈니스 거절까지 ERROR로 찍으면 에러율이 상시 20%가 되고, 알림을 아무도 안 보게 됩니다.

스스로 점검하는 방법

트레이스 하나를 열어서 30초 안에 "이 요청이 무엇을 했고 어디서 시간을 썼는지" 말할 수 있는지 확인해 보세요. 못 하겠다면 Span이 너무 많은 것입니다. 반대로 "여기서 뭘 한 거지?"라는 빈 구간이 있다면 부족한 것입니다. 5편의 판단 트리가 이 균형을 잡는 도구입니다.

SECTION 05

성능 오버헤드 — 기준선부터 만들기

"계측 켜니까 느려졌다"는 제보는 거의 반드시 나옵니다. 문제는 비교할 숫자가 없다는 것입니다.

측정 절차

  1. 부하 테스트 시나리오를 하나 정합니다 — 실제 트래픽 패턴에 가까운 것
  2. 계측을 끄고 실행해 기준선을 기록합니다
  3. 계측을 켜고 같은 시나리오를 실행합니다
  4. 두 결과를 표로 남기고 문서에 첨부합니다
  5. 이후 에이전트 버전을 올릴 때마다 같은 시나리오를 돌립니다

눈에 띄는 성능 저하는 보통 계측 자체가 아니라 계측 방식의 문제입니다. 요청당 Span을 수백 개 만들고 있거나, 배치 프로세서 대신 동기 전송을 쓰고 있거나, 속성 값 계산에 무거운 직렬화가 들어 있는 경우입니다. 숫자를 보고 원인을 좁히세요. "OTel이 무겁다"로 결론 내리기 전에 확인할 것이 많습니다.

1편 회색지대의 해소

오버헤드는 1편에서 공동 책임 회색지대로 분류한 항목입니다. 해소 방법은 간단합니다. 도입 전에 기준선 숫자 두 개를 남기는 것. 이것이 있으면 이후 모든 논쟁이 사실 확인으로 바뀌고, 없으면 영원히 서로 탓하는 상태가 됩니다. 11편 온보딩 체크리스트의 필수 항목입니다.

SECTION 06

계측 코드도 테스트합니다

계측은 조용히 깨집니다. 리팩터링하다 end()를 빼먹어도, 속성 이름을 오타 내도 아무 에러가 없습니다. 테스트로 잡는 것이 유일한 방법입니다.

Java — JUnit5 + opentelemetry-sdk-testing
@RegisterExtension
static final OpenTelemetryExtension OTEL =
    OpenTelemetryExtension.create();

@Test
void 주문_계측이_올바른_속성을_남긴다() {
    orderService.place(sampleRequest());

    var spans = OTEL.getSpans();
    assertThat(spans).hasSize(2);

    var span = spans.get(0);
    assertThat(span.getName()).isEqualTo("allocate-inventory");
    assertThat(span.getAttributes()
        .get(stringKey("acme.order.channel"))).isEqualTo("mobile");

    // 종료되지 않은 Span은 여기 안 나옵니다 — 누락 탐지
    assertThat(span.hasEnded()).isTrue();
}
Python — InMemorySpanExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter \
     import InMemorySpanExporter

@pytest.fixture
def spans():
    exporter = InMemorySpanExporter()
    provider = TracerProvider()
    provider.add_span_processor(SimpleSpanProcessor(exporter))
    trace.set_tracer_provider(provider)
    yield exporter
    exporter.clear()

def test_주문_계측(spans):
    order_service.place(sample_request())

    finished = spans.get_finished_spans()
    assert len(finished) == 2
    assert finished[0].name == "allocate-inventory"
    assert finished[0].attributes["acme.order.channel"] == "mobile"
Node.js — InMemorySpanExporter
const { InMemorySpanExporter, SimpleSpanProcessor,
        BasicTracerProvider } = require('@opentelemetry/sdk-trace-base');

let exporter;
beforeEach(() => {
  exporter = new InMemorySpanExporter();
  const provider = new BasicTracerProvider();
  provider.addSpanProcessor(new SimpleSpanProcessor(exporter));
  provider.register();
});

test('주문 계측이 올바른 속성을 남긴다', async () => {
  await orderService.place(sampleRequest());

  const spans = exporter.getFinishedSpans();
  expect(spans).toHaveLength(2);
  expect(spans[0].name).toBe('allocate-inventory');
  expect(spans[0].attributes['acme.order.channel']).toBe('mobile');
});

무엇을 테스트할 것인가

  • Span이 실제로 종료되는가 — 종료된 Span만 수집되므로 개수 검증이 곧 누락 탐지입니다
  • 속성 이름이 정확한가 — 오타는 런타임에 아무 에러도 내지 않습니다
  • 에러 경로에서 상태가 ERROR인가 — 예외를 던지는 시나리오도 테스트합니다
  • 금지된 속성이 없는가 — 개인정보 키 목록을 검사하는 테스트를 하나 만들어 두면 실수를 자동으로 막습니다
  • Span 개수가 예상 범위인가 — 상한을 걸어두면 루프 안 Span 생성 같은 사고를 CI에서 잡습니다
가장 가성비 좋은 테스트 하나

시간이 없다면 이것 하나만 만드세요. "모든 Span의 속성 키 중에 금지 목록에 있는 것이 없다"를 검사하는 테스트. 개인정보 유출은 되돌릴 수 없는 사고이고, 이 테스트는 20줄이면 만들어집니다.
