Prometheus 해부

Kubernetes와 Helm 차트에 감춰지기 전의 Prometheus를 맨손으로 만납니다. VM에 바이너리로 설치하고, 스크레이프가 오가는 모습과 디스크에 쌓이는 블록을 직접 확인하고, 라벨 하나로 시계열이 수천 개 늘어나는 순간을 일부러 만들어 봅니다.

  2. Pull 모델의 동작 순서와 자동 생성 메트릭을 이해하고, Push 모델과 비교해 MSP 환경에서의 장단점을 말할 수 있다.

1Prometheus는 어떤 시스템인가

Prometheus는 "메트릭을 저장하는 데이터베이스"로 소개되곤 하지만, 실제로는 수집기, 저장소, 쿼리 엔진, 규칙 평가기, 알림 발신기를 한 바이너리에 담은 모니터링 시스템입니다.

짧은 역사

2012년 SoundCloud에서 Google 내부 모니터링 시스템 Borgmon에 영감을 받아 시작되었고, 2016년 Kubernetes에 이어 두 번째로 CNCF에 합류했으며, 2018년 역시 두 번째로 졸업(graduated) 프로젝트가 되었습니다. Go로 작성되었고 Apache 2.0 라이선스입니다. Kubernetes 생태계의 메트릭 표준이 사실상 Prometheus 형식이 된 것은 이 이력 덕분입니다.

한 프로세스 안의 여섯 가지 일

Prometheus가 하지 않는 것

Prometheus 단일 서버는 클러스터링, 복제, 장기 보존을 하지 않습니다. 공식 문서도 로컬 저장소는 임의로 확장하거나 장기간 내구성을 보장하는 용도가 아니라고 설명합니다. 같은 Prometheus를 두 대 띄워 고가용성을 흉내 내거나, 원격 저장소(Mimir, Thanos)로 보내는 것이 표준 해법이며 14편에서 다룹니다. 이 한계를 아는 것이 Prometheus 설계를 이해하는 출발점입니다.

2Pull 모델 해부

Prometheus는 데이터를 받지 않고 가지러 갑니다. 이 선택 하나가 장애 감지 방식, 네트워크 설계, MSP의 고객사 연결 방식까지 결정합니다.

한 번의 스크레이프에서 일어나는 일

1단계

타깃 목록 갱신

서비스 발견이 타깃의 주소와 메타데이터 라벨(__address__, __meta_*)을 만듭니다.

2단계

relabel_configs 적용

메타데이터로 최종 라벨(job, instance, 추가 라벨)을 정하고, 수집하지 않을 타깃을 걸러 냅니다. 이름이 __로 시작하는 라벨은 이 단계 후 버려집니다.

3단계

HTTP GET /metrics

scrape_interval(기본 1분, 보통 15~30초로 설정)마다 요청합니다. Accept 헤더로 Protobuf, OpenMetrics, 텍스트 형식 중 무엇을 원하는지 협상하고, scrape_timeout(기본 10초) 안에 응답이 없으면 실패로 처리합니다.

4단계

파싱과 metric_relabel_configs

응답을 파싱하고 시계열 단위로 라벨을 고치거나 버립니다. sample_limit 같은 한도를 넘으면 그 스크레이프 전체가 실패합니다.

5단계

타깃 라벨 부착과 저장

모든 샘플에 타깃 라벨을 붙이고 스크레이프 시작 시각을 타임스탬프로 하여 head 블록에 넣습니다. 동시에 WAL에 기록해 프로세스가 죽어도 복구할 수 있게 합니다.

6단계

자동 생성 메트릭 기록

타깃이 보낸 것과 별개로 Prometheus가 스스로 아래 시계열을 기록합니다.

7단계

사라진 시계열에 stale marker

직전 스크레이프에 있었는데 이번에 없는 시계열, 또는 스크레이프가 실패한 타깃의 시계열에는 "끝났음" 표시를 기록합니다. 그래서 쿼리 결과에서 즉시 사라집니다.

자동 생성 메트릭의미실무 활용
up스크레이프 성공 1, 실패 0가장 기본적인 타깃 장애 알림. up == 0
scrape_duration_seconds스크레이프에 걸린 시간타임아웃 직전의 느린 Exporter 찾기
scrape_samples_scraped응답에 들어 있던 샘플 수갑자기 늘어난 타깃 = 카디널리티 사고 후보
scrape_samples_post_metric_relabelingmetric_relabel 후 남은 샘플 수버리기 규칙이 제대로 동작하는지 확인
scrape_series_added이번 스크레이프에서 새로 생긴 시계열 수계속 0보다 크면 시계열이 끊임없이 생기고 있다는 신호(churn)

Staleness: 데이터가 언제 "없는 것"이 되는가

PromQL은 특정 시각의 값을 물으면 그 시각 이전 최대 5분(lookback delta) 안의 가장 최근 샘플을 돌려줍니다. 그런데 타깃이 꺼졌는데도 5분 동안 마지막 값이 계속 보이면 곤란하므로, Prometheus는 7단계의 stale marker로 "이 시계열은 끝났다"를 명시합니다. 덕분에 정상 종료한 타깃의 시계열은 바로 그래프에서 사라집니다. 이 개념은 4편에서 range 쿼리와 함께 다시 나옵니다.

MSP에게 Pull이 의미하는 것

관제 센터의 Prometheus가 고객사 서버 수백 대를 직접 스크레이프하려면 관제 센터에서 고객사 내부로 들어가는 방화벽 정책이 필요합니다. 대부분의 고객사 보안 정책은 이것을 허용하지 않습니다. 그래서 현장의 표준은 고객사 안에 Prometheus(또는 Agent 모드, Alloy)를 두고 그 안에서 Pull로 모은 뒤, 밖으로 나가는 방향인 Remote Write로 관제 센터에 밀어 올리는 혼합 구조입니다. 이번 편에서 cust-a-web에 설치하는 Prometheus가 바로 그 "고객사 안의 Prometheus"이고, 14편에서 hub로 연결합니다.

Pushgateway는 Push 시스템이 아닙니다

Pushgateway는 배치 작업처럼 스크레이프되기 전에 끝나 버리는 작업의 결과를 잠시 맡아 두는 용도입니다. 일반 서비스의 메트릭을 Pushgateway로 보내면 up이 의미를 잃고, 한 번 들어간 값은 지우기 전까지 영원히 남으며, Pushgateway 자체가 단일 장애점이 됩니다. Push가 필요하면 OTLP 수신(Lab 7)이나 Remote Write를 검토하세요.

3데이터 모델과 노출 형식

Prometheus가 다루는 데이터는 단 하나의 구조, "이름과 라벨로 식별되는 시계열"입니다. 이 구조를 정확히 이해하면 카디널리티도, PromQL도 쉬워집니다.

시계열, 샘플, 라벨

시계열(Time Series)은 메트릭 이름과 라벨 집합의 조합 하나입니다. 이름은 내부적으로 __name__이라는 라벨로 저장되므로, 정확히 말하면 시계열은 "라벨 집합"으로 식별됩니다. 시계열 안에는 샘플(Sample)이 시간 순서대로 쌓이며, 샘플 하나는 밀리초 단위 타임스탬프와 float64 값의 쌍입니다. 네이티브 히스토그램은 값 자리에 히스토그램 구조 전체가 들어가는 특별한 샘플입니다.

# 아래 두 줄은 서로 다른 시계열입니다. 라벨 값이 하나라도 다르면 다른 시계열.
node_cpu_seconds_total{cpu="0",mode="idle",instance="cust-a-web",job="node"}
node_cpu_seconds_total{cpu="0",mode="user",instance="cust-a-web",job="node"}

(1791443103000, 18234.57)  (1791443118000, 18249.53)  ...

노출 형식: /metrics에 실제로 보이는 것

Exporter가 HTTP로 내보내는 텍스트는 사람이 읽을 수 있습니다. # HELP는 설명, # TYPE은 메트릭 타입이며, 그 아래에 시계열마다 한 줄씩 현재 값이 나옵니다. 타임스탬프는 보통 생략하며 Prometheus가 스크레이프 시각을 씁니다.

이름 짓기 규칙

메트릭 이름은 쿼리를 쓰는 사람의 사전입니다. 공식 가이드의 핵심만 추리면 다음과 같습니다.

  • 접두어로 출처를 밝힙니다. node_, http_, payment_처럼 어느 도메인의 메트릭인지 보이게 합니다.
  • 기본 단위를 쓰고 이름에 붙입니다. 밀리초가 아니라 초(_seconds), 킬로바이트가 아니라 바이트(_bytes)입니다. 단위가 섞이면 대시보드에서 1,000배 오류가 납니다.
  • 카운터는 _total로 끝냅니다. 이름만 보고 rate()를 써야 한다는 것을 알 수 있습니다.
  • 값이 항상 1이고 정보만 라벨에 담는 메트릭은 _info로 끝냅니다. 예: node_uname_info, target_info.
  • 라벨 이름에 __로 시작하는 이름을 쓰지 않습니다. Prometheus 내부용으로 예약되어 있습니다.

디스크 용량 산정

공식 문서는 Prometheus가 압축 덕분에 샘플 하나를 평균 1~2바이트에 저장한다고 설명하며, 필요한 디스크를 다음 식으로 어림하도록 안내합니다. 값을 바꿔 계산해 보세요.

필요 디스크 = 보존 기간(초) × 초당 수집 샘플 수 × 샘플당 바이트

기본값 1,500 시계열은 이번 랩의 VM 두 대 정도 규모입니다. 고객사 서버 500대가 각각 1,000개 시계열을 낸다고 바꿔 넣어 보면(500,000) 같은 15일 보존에도 수십 GB가 필요하다는 것을 알 수 있습니다. 여기에 WAL과 압축 작업 공간을 위해 30% 이상 여유를 두는 것이 안전합니다.

메모리는 디스크와 다르게 움직입니다

디스크는 "샘플 수 × 기간"에 비례하지만, 메모리는 주로 지금 활성 상태인 시계열 수에 비례합니다. 보존 기간을 30일에서 15일로 줄여도 메모리는 거의 줄지 않고, 카디널리티를 줄여야 줄어듭니다. 용량 산정을 할 때 이 둘을 따로 봐야 하는 이유입니다.

#!/usr/bin/env bash
# node_exporter 설치: 체크섬 검증, 전용 사용자, systemd 등록
set -euo pipefail
NE_VER="${NE_VER:?NE_VER를 지정하세요}"

PKG="node_exporter-${NE_VER}.linux-${ARCH}"
BASE="https://github.com/prometheus/node_exporter/releases/download/v${NE_VER}"

curl -fsSLO "${BASE}/sha256sums.txt"

install -m 0755 "${PKG}/node_exporter" /usr/local/bin/node_exporter

id node_exporter &>/dev/null || useradd --system --no-create-home --shell /usr/sbin/nologin node_exporter
install -d -o node_exporter -g node_exporter -m 0755 /var/lib/node_exporter/textfile

cat > /etc/systemd/system/node_exporter.service <<'EOF'
[Unit]
Description=Prometheus node_exporter
Wants=network-online.target
After=network-online.target

[Service]
User=node_exporter
Group=node_exporter
ExecStart=/usr/local/bin/node_exporter \
  --web.listen-address=:9100 \
  --collector.systemd \
  --collector.textfile.directory=/var/lib/node_exporter/textfile
Restart=on-failure
NoNewPrivileges=true
ProtectSystem=full
ProtectHome=true

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now node_exporter
systemctl --no-pager --lines=3 status node_exporter

9Lab 2. Prometheus 설치

cust-a-web에 Prometheus 3.13 LTS를 설치합니다. 설정 파일은 호스트의 ~/obs-lab에서 관리하고, 검증을 통과해야만 VM에 반영되는 흐름을 만듭니다.

왜 최신 버전이 아니라 LTS인가

작성 시점에 Prometheus는 3.14가 최신이지만, 2026년 7월 1일에 나온 3.13이 LTS(장기 지원) 릴리스입니다. 일반 릴리스는 약 6주마다 나오고 다음 버전이 나오면 곧 지원이 끝나므로, 고객사 서버에 깔아 두면 몇 달 만에 보안 패치를 받지 못하는 버전이 됩니다. LTS는 같은 마이너 버전 안에서 더 오래 버그와 보안 수정을 받기 때문에, 자주 업그레이드하기 어려운 고객사 운영 환경에 적합합니다. 랩에서는 3.13 계열의 최신 패치를 씁니다.

설정을 VM에 바로 덮어쓰면 오타 하나로 Prometheus가 설정을 거부합니다. 임시 위치에 올려 promtool로 검사하고, 통과한 경우에만 반영한 뒤 다시 읽게 합니다.

~/obs-lab/scripts/prom-push-config.sh

#!/usr/bin/env bash
# 호스트의 Prometheus 설정을 검증 후 cust-a-web에 반영
set -euo pipefail
VM=cust-a-web
SRC=~/obs-lab/vm/prometheus
multipass exec $VM -- bash -c 'rm -rf /tmp/promcfg && mkdir -p /tmp/promcfg/targets'
multipass transfer $SRC/prometheus.yml $VM:/tmp/promcfg/
for f in $SRC/targets/*.yml; do multipass transfer "$f" $VM:/tmp/promcfg/targets/; done

echo "== 검증"
multipass exec $VM -- promtool check config --syntax-only /tmp/promcfg/prometheus.yml
for f in $SRC/targets/*.yml; do
  python3 -c "import sys,yaml; yaml.safe_load(open('$f'))" || { echo "YAML 오류: $f"; exit 1; }
done

echo "== 반영"
multipass exec $VM -- sudo bash -c '
  cp /tmp/promcfg/prometheus.yml /etc/prometheus/prometheus.yml
  rm -f /etc/prometheus/targets/*.yml
  cp /tmp/promcfg/targets/*.yml /etc/prometheus/targets/
  chown -R prometheus:prometheus /etc/prometheus
  systemctl reload prometheus'
sleep 2
ok=$(multipass exec $VM -- curl -s 'localhost:9090/api/v1/query?query=prometheus_config_last_reload_successful' | jq -r '.data.result[0].value[1]')
[ "$ok" = "1" ] && echo "반영 성공" || { echo "반영 실패: journalctl -u prometheus 확인"; exit 1; }
호스트에 python3-yaml이 없다면

타깃과 서비스 발견 화면

A. OTLP로 메트릭 보내기

Lab 2에서 --web.enable-otlp-receiver를 켜 두었습니다. 애플리케이션 대신 curl로 OTLP/HTTP JSON 요청 하나를 보내 봅니다. 서비스 이름, 인스턴스, 환경 같은 OpenTelemetry 리소스 속성이 Prometheus 라벨로 어떻게 바뀌는지 보는 것이 목적입니다.

multipass exec cust-a-web -- bash -c '

{"resourceMetrics":[{

    {"key":"service.name","value":{"stringValue":"lab-batch"}},
    {"key":"service.instance.id","value":{"stringValue":"cust-a-web"}},
    {"key":"deployment.environment","value":{"stringValue":"lab"}}]},
  "scopeMetrics":[{"scope":{"name":"manual-curl"},"metrics":[{

lab_queue_depth

응답이 404, 415라면

404는 OTLP 수신 플래그가 꺼져 있는 경우입니다(prometheus --version과 서비스 파일의 플래그 확인). 415처럼 형식을 거부하는 응답이면 JSON 대신 Protobuf를 요구하는 것이므로, 11편에서 OTel SDK나 Collector로 보내는 방법을 쓰면 됩니다. Prometheus의 OTLP 수신은 HTTP만 지원하며 gRPC는 지원하지 않습니다.

리소스 속성을 라벨로 올리고 싶다면

매번 target_info와 조인하는 것은 번거롭습니다. 설정의 otlp.promote_resource_attributes에 deployment.environment 같은 속성을 나열하면 모든 시계열에 라벨로 붙일 수 있습니다. 다만 카디널리티와 맞바꾸는 선택이므로 값의 종류가 적은 속성만 올리세요.

B. UTF-8 이름 그대로 저장해 보기 (선택)

변환 방식을 바꾸면 OpenTelemetry 이름을 점이 들어간 그대로 저장할 수 있습니다. 설정 파일 맨 위(전역 수준)에 추가합니다.

C. 네이티브 히스토그램 수집해 보기

Prometheus 자신의 prometheus_http_request_duration_seconds는 클래식 버킷과 네이티브 히스토그램을 함께 내보냅니다. prometheus job에만 수집을 켜 봅니다.

  - job_name: prometheus
    scrape_native_histograms: true
    always_scrape_classic_histograms: true    # 기존 _bucket 쿼리가 깨지지 않게 함께 수집
    static_configs:
      ...
~/obs-lab/scripts/prom-push-config.sh

1~2분 동안 Query 화면을 몇 번 사용해 요청을 만든 뒤 아래를 비교합니다.

# 네이티브: 이름 그대로, le로 묶을 필요 없음
histogram_quantile(0.9, sum(rate(prometheus_http_request_duration_seconds{handler="/api/v1/query"}[5m])))
histogram_count(rate(prometheus_http_request_duration_seconds{handler="/api/v1/query"}[5m]))

# 클래식: 기존 방식
histogram_quantile(0.9, sum by (le) (rate(prometheus_http_request_duration_seconds_bucket{handler="/api/v1/query"}[5m])))
정상이면 두 값이 크게 다르게 나옵니다. 작성자가 3.13.1로 시험했을 때 네이티브는 약 0.002초(2ms), 클래식은 0.09초였습니다. 이 Prometheus의 쿼리는 대부분 수 ms 안에 끝나 클래식의 가장 작은 버킷(0.1초 이하)에 모두 들어가고, histogram_quantile은 버킷 안에서 선형으로 보간하므로 "0.1초의 90% 지점"인 0.09초를 답합니다. 실제보다 수십 배 부풀려진 값입니다. 네이티브 히스토그램은 버킷이 지수 스케일로 촘촘해 실제 분포에 가까운 값을 냅니다. 클래식 히스토그램에서 버킷 경계를 잘못 고르면 분위수가 얼마나 틀어질 수 있는지 보여 주는 결과입니다. 네이티브 쪽 결과가 비어 있다면 아직 데이터가 쌓이지 않았거나, 사용 중인 버전의 Prometheus가 이 메트릭을 네이티브로 내보내지 않는 경우입니다. Table 탭에서 prometheus_http_request_duration_seconds(접미사 없이)를 조회해 히스토그램 값이 나오는지 먼저 확인하세요.

16트러블슈팅

증상을 눌러 원인과 해결 방법을 확인하세요.

체크섬 검사가 FAILED 또는 "no properly formatted checksum lines"Lab 1, 2

다운로드가 중간에 끊겼거나, 버전 번호에 오타가 있어 sha256sums.txt에서 해당 줄을 찾지 못한 경우입니다. ls -la /tmp/*.tar.gz로 파일 크기를 보고, NE_VER와 PROM_VER 값이 실제 릴리스 태그(앞의 v 제외)와 같은지 확인한 뒤 다시 실행하세요. 검사를 건너뛰고 설치하지 마세요.

prometheus 서비스가 시작하지 않음: permission deniedLab 2

journalctl -u prometheus -n 30을 봅니다. /var/lib/prometheus나 /etc/prometheus의 소유자가 prometheus가 아니면 생깁니다. sudo chown -R prometheus:prometheus /var/lib/prometheus /etc/prometheus로 고치고 재시작합니다.

설정 반영 실패: "Error loading config"Lab 2 이후

대부분 YAML 들여쓰기 오류입니다. 검증 게이트를 거치면 반영 전에 막히지만, VM에서 직접 고쳤다면 promtool check config /etc/prometheus/prometheus.yml로 줄 번호를 확인하세요. 반영에 실패해도 Prometheus는 이전 설정으로 계속 동작하며, prometheus_config_last_reload_successful이 0이 됩니다. 이 값을 알림으로 걸어 두는 것이 좋습니다(6편).

file_sd로 추가한 타깃이 나타나지 않음Lab 2

타깃 파일 경로가 files의 패턴(node_*.yml)과 맞는지, 파일 YAML이 올바른지 확인합니다. 문법이 틀린 타깃 파일은 해당 파일 전체가 무시되고 로그에만 경고가 남습니다. UI의 Service discovery 화면에서 job의 발견된 타깃 수를 확인하세요. 반영까지 refresh_interval(1분)이 걸릴 수 있습니다.

호스트 브라우저에서 WEB_IP:9090이 열리지 않음Lab 2

VM 안에서 curl localhost:9090/-/ready가 되는지 먼저 봅니다. VM 안에서는 되는데 밖에서 안 되면 --web.listen-address가 127.0.0.1로 되어 있거나 VM의 ufw가 막는 경우입니다. VM IP가 바뀌었을 수 있으니 multipass list로 다시 확인하세요.

타깃이 DOWN: "received unsupported Content-Type" 또는 형식 관련 오류3.x

Prometheus 3.x는 응답의 Content-Type이 없거나 알 수 없으면 스크레이프를 실패시킵니다. 오래된 Exporter나 직접 만든 스크립트에서 생깁니다. 해당 job에 fallback_scrape_protocol: PrometheusText0.0.4를 지정하면 텍스트 형식으로 간주해 읽습니다. 근본적으로는 Exporter를 고치는 것이 좋습니다.

타깃이 DOWN: "sample limit exceeded"Lab 6

Lab 6에서 의도한 결과입니다. 실무에서 만났다면 scrape_samples_scraped의 추이로 언제부터 늘었는지 확인하고, 그 시점의 배포를 찾습니다. 한도를 올리는 것은 원인을 확인한 뒤의 마지막 선택입니다.

시계열을 지웠는데 메모리와 head_series가 줄지 않음Lab 6

정상입니다. head 블록이 정리될 때(대략 2시간 주기)까지 남습니다. 급하게 줄여야 한다면 재시작하는 방법도 있지만, WAL 재생 때 다시 로드되므로 효과가 제한적이고 그동안 수집이 멈춥니다. 기다리는 것이 정석입니다.

OTLP 전송이 404 또는 415Lab 7

404는 --web.enable-otlp-receiver가 없거나 경로가 틀린 경우입니다(/api/v1/otlp/v1/metrics, 앞부분 /api/v1/otlp까지만 쓰면 안 됨). 415는 형식 문제로, Protobuf로 보내야 합니다. OTLP 데이터의 타임스탬프가 너무 오래되었거나 미래이면 거부될 수 있으므로 date +%s%N으로 현재 시각을 넣었는지도 확인하세요.

Prometheus 재시작이 오래 걸림, "Replaying WAL" 로그가 길게 나옴운영

재시작 시 WAL을 다시 읽어 head를 복원하는 과정입니다. 활성 시계열이 많을수록 길어집니다. systemd의 TimeoutStopSec을 넉넉히 두어 정상 종료를 기다리게 하고, 시계열 수 자체를 관리하는 것이 해법입니다.

오늘의 핵심

  1. Prometheus 서버 하나가 발견, 수집, 저장, 규칙 평가, 조회, 알림 전송을 모두 합니다. 단, 클러스터링과 장기 보존은 하지 않습니다.
  2. Pull 모델은 up으로 타깃 생존을 알 수 있다는 큰 장점이 있지만, 관제 센터에서 고객사로 들어가는 방향의 접근이 필요합니다. 그래서 MSP는 고객사 안에서 Pull하고 밖으로 Remote Write하는 혼합 구조를 씁니다.
  3. 카운터는 rate()로, 게이지는 그대로, 히스토그램은 le를 유지한 채 합쳐 분위수를 계산합니다. 서머리의 분위수는 합칠 수 없습니다.
  4. 시계열 수는 라벨 값 종류의 곱입니다. 무한히 늘어나는 값을 라벨에 넣지 않고, 수집 한도로 사고를 가둡니다. 지운 시계열도 head 정리 전까지는 메모리에 남습니다.
  5. TSDB는 head(메모리)와 WAL, 2시간 단위의 불변 블록, 압축, 블록 단위 보존으로 동작합니다. 디스크는 샘플 수 × 기간, 메모리는 활성 시계열 수에 비례합니다.
  6. 3.x에서는 UTF-8 이름, OTLP 수신, 네이티브 히스토그램 안정화, 스크레이프 형식 엄격화, LTS 릴리스 등이 달라졌습니다. 고객사에는 LTS를 기본으로 씁니다.
