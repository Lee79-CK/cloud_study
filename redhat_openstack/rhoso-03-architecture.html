RHOSO 강의 3 / 33편 Level 0 · 큰 그림과 언어 익히기 (마지막 편) 기준: RHOSO 18.0 (2026년 10월)

3편아키텍처 해부: 컨트롤 플레인과 데이터 플레인

YAML 세 장이 어떻게 수십 개의 Pod, 여러 개의 격리 네트워크, 그리고 VM이 도는 컴퓨트 노드로 바뀌는지. 1편의 큰 그림을 한 단계 열어 부품 하나하나가 어디에 끼워지는지 확인합니다.

섹션 1

이 편의 목표

  1. OpenStackControlPlane CR 하나가 만들어 내는 하위 CR과 Kubernetes 객체를 트리로 설명한다.
  2. 컨트롤 플레인 서비스가 세 가지 문(Pod 내부망, 내부 API용 MetalLB IP, 공개 API용 Route)으로 노출되는 원리를 설명한다.
  3. NodeSet과 Deployment가 Ansible Job으로 바뀌어 컴퓨트 노드를 설정하는 과정과, 그 결과 노드에 생기는 것을 설명한다.
  4. 격리 네트워크 ctlplane · internalapi · storage · storagemgmt · tenant · external의 용도와, 각 트래픽이 어느 망으로 흐르는지 말한다.
  5. NMState · Multus(NAD) · MetalLB · cert-manager · 스토리지가 각각 어느 지점에 끼는지, 고장 나면 무엇이 멈추는지 말한다.

읽는 법

보라색 점선 용어는 누르면 설명이 뜹니다. 이 편은 그림과 인터랙션이 많습니다. 특히 섹션 11(트래픽 경로)과 섹션 14(고장 지도)는 반드시 직접 눌러 보세요. 이 두 그림이 Level 2 설치와 Level 3 장애 대응의 기초 지도가 됩니다.

섹션 2

1·2편에서 3편으로

지금까지 배운 것을 세 문장으로 정리하고 시작합니다.

  • RHOSO는 컨트롤 플레인을 OpenShift Pod로, 데이터 플레인을 RHEL 9 컴퓨트 노드로 운영한다. (1편)
  • 운영자는 CR을 고치고, Operator가 리컨실해 실제 상태를 맞춘다. 결과물을 직접 고치지 않는다. (1·2편)
  • Project·Service·Node·Network 같은 단어는 두 세계에서 뜻이 다르므로 “어느 쪽?”을 구분한다. (2편)

3편은 여기서 한 발 더 들어가 “그래서 실제로 무엇이, 어디에, 어떻게 연결되어 있나”를 다룹니다. 설치 편(Level 2)에서 쓰게 될 YAML의 모든 줄은 이 편의 그림 어딘가에 대응됩니다. 그래서 3편을 “설치 전에 미리 보는 설계도”라고 생각하면 됩니다.

현장에서 이 편이 쓰이는 순간

  • 고객사 네트워크팀에 “VLAN 몇 개, 대역 몇 개가 필요한가요?”라는 질문을 받았을 때 (섹션 9·10)
  • 컴퓨트 노드에서 nova-compute가 down인데 원인이 어느 망인지 좁혀야 할 때 (섹션 11·14)
  • “OCP 노드 하나 재부팅해도 되나요?”라는 변경 요청을 검토할 때 (섹션 13·14)

섹션 3

5층 단면도

RHOSO를 위에서 아래로 자르면 다섯 개 층이 보입니다. 층을 누르면 그 층의 구성 요소, 담당자, 대표 명령이 나옵니다. 장애가 나면 “몇 층 문제인가”부터 정하는 습관을 들이세요.

층을 눌러 보세요.

층 사이의 규칙

위층은 아래층에 의존하지만, 아래층 장애가 위층에 어떻게 보이는지는 층마다 다릅니다. 예를 들어 2층(OpenShift)의 노드 하나가 죽으면 4층(컨트롤 플레인)의 Pod 일부가 다른 노드로 옮겨지는 동안 API가 잠깐 느려질 수 있지만, 5층(컴퓨트 노드)의 고객 VM은 계속 돕니다. 반대로 1층의 스위치 VLAN 설정이 틀어지면 2층부터 5층까지 동시에 이상 증상이 나옵니다.

섹션 4

컨트롤 플레인 해부: CR 하나가 만드는 나무

운영자는 OpenStackControlPlane CR 하나만 씁니다. 그러면 openstack-operator가 이것을 서비스별 CR로 쪼개고, 서비스별 Operator가 다시 Kubernetes 객체(Deployment, StatefulSet, Service, Job 등)를 만듭니다. 아래 나무의 마디를 누르면 설명이 나옵니다.

RHOSO CRKubernetes 객체데이터 플레인에 넘겨지는 것

마디를 눌러 보세요.

기억할 구조적 특징 네 가지

  1. DB와 메시지 큐가 둘씩 있다. 기본 구성에서 Galera는 openstack(대부분 서비스용)과 openstack-cell1(Nova cell1용), RabbitMQ는 rabbitmq와 rabbitmq-cell1로 나뉩니다. 컴퓨트 노드의 nova-compute는 cell1 쪽 큐와 대화합니다. 이렇게 나눠 두면 VM 생성·상태 보고 같은 대량 트래픽이 다른 서비스의 메시지와 섞이지 않습니다.
  2. 상태 없는 API는 Deployment, 상태 있는 것은 StatefulSet. Galera·RabbitMQ·OVN DB처럼 데이터를 가진 구성 요소는 고정 이름과 전용 PVC를 갖는 StatefulSet으로 뜹니다.
  3. 일회성 작업은 Job. DB 스키마 생성(db-sync), Keystone 초기 등록(bootstrap) 같은 작업은 Job으로 한 번 실행되고 Completed로 남습니다. Completed는 정상입니다.
  4. 컴퓨트 노드에 넘겨줄 정보는 Secret·ConfigMap으로 만들어진다. 예를 들어 Nova Operator는 컴퓨트 노드용 설정(어느 큐·어느 API에 붙을지, 접속 비밀번호)을 Secret으로 준비해 두고, 데이터 플레인 배포가 이것을 가져가 노드에 심습니다. 이것이 컨트롤 플레인과 데이터 플레인을 잇는 보이지 않는 다리입니다.

하위 CR은 왜 직접 고치지 않을까

KeystoneAPI, Nova 같은 하위 CR은 openstack-operator가 OpenStackControlPlane을 보고 만든 결과물입니다. 하위 CR을 직접 수정하면 메타 Operator가 다음 리컨실에서 원래 값으로 되돌립니다. 변경은 항상 OpenStackControlPlane의 해당 서비스 칸에서 합니다.

섹션 5

컨트롤 플레인이 서는 순서

CR을 적용하면 모든 것이 동시에 뜨는 것처럼 보이지만, 실제로는 의존 관계에 따라 기다리고 이어집니다. Operator들은 병렬로 일하되, 필요한 것이 준비될 때까지 대기합니다. 아래는 이해를 위해 단계로 단순화한 순서입니다.

설치가 “어디서 멈췄는지” 읽는 법

이 순서를 알면 설치 중 멈춘 지점을 바로 짐작할 수 있습니다. Galera Pod가 Pending이면 1단계(스토리지), Keystone db-sync Job이 실패하면 2~3단계(DB 접속·비밀번호), Nova만 준비가 안 되면 5단계(cell 구성·RabbitMQ cell1)를 봅니다. oc get openstackcontrolplane의 MESSAGE가 어떤 하위 서비스를 기다리는지 알려 주므로, 그 이름을 이 순서표에 대입하면 됩니다. 19편(컨트롤 플레인 배포)에서 실제로 확인합니다.

섹션 6

서비스는 어떻게 노출되나: 세 개의 문

컨트롤 플레인 서비스(예: Keystone)에 접근하는 쪽은 세 부류입니다. 각자 다른 문을 씁니다.

문누가 쓰나실체어느 망카탈로그에서
① 클러스터 내부 주소OCP 안의 다른 Pod (예: nova-api → keystone)Kubernetes Service (ClusterIP)OpenShift Pod 네트워크—
② 내부 API 주소컴퓨트 노드, 다른 내부 구성 요소type: LoadBalancer Service + MetalLB IPinternalapi 격리망internal 엔드포인트
③ 공개 API 주소클라우드 사용자, 외부 자동화 도구OpenShift Route (인그레스 라우터, HTTPS)OCP 기본망(외부에서 접근 가능한 주소)public 엔드포인트

그래서 openstack endpoint list를 보면 같은 Keystone이 두 번 나옵니다. internal은 172.17.0.x 같은 internalapi 대역의 MetalLB 주소, public은 https://keystone-public-openstack.apps.… 같은 Route 주소입니다. CR에서 ②는 override.service.internal + MetalLB 어노테이션으로, ③은 apiOverride.route로 정합니다(2편 섹션 8).

API가 아닌 것들도 MetalLB로 나간다

컴퓨트 노드는 HTTP API만 쓰지 않습니다. RabbitMQ(nova-compute가 cell1 큐에 접속)와 OVN Southbound DB(ovn-controller가 접속)도 컴퓨트 노드에서 닿아야 하므로, 이 둘도 internalapi 망의 MetalLB IP로 노출됩니다. 반면 Galera DB는 컴퓨트 노드에 노출되지 않습니다. 컴퓨트 노드는 DB에 직접 붙지 않고 Conductor를 거치기 때문입니다(1편 요청 흐름). 이 차이를 알면 “컴퓨트 노드에서 어떤 IP에 닿아야 하는가” 점검 목록을 스스로 만들 수 있습니다.

섹션 7

데이터 플레인 해부: NodeSet → Deployment → Ansible Job

데이터 플레인은 세 단계로 만들어집니다.

  1. NodeSet을 만든다. 어떤 노드들이 한 묶음이고, 각 노드의 접속 주소·호스트 이름·망별 IP가 무엇이며, 어떤 서비스를 순서대로 실행할지 적습니다. NodeSet을 만들면 Operator가 IP를 예약(IPSet)하고 DNS 기록(DNSData)을 만들고, Ansible 인벤토리를 준비합니다. 이 시점에는 아직 노드에 아무것도 하지 않습니다.
  2. Deployment를 만든다. “이 NodeSet들에 지금 배포하라”는 실행 주문입니다. 만드는 순간 실행이 시작됩니다.
  3. 서비스마다 Ansible Job이 돈다. NodeSet의 services 목록 순서대로, 서비스 하나당 Ansible 실행 환경 컨테이너(Ansible EE) Job이 생겨 ctlplane 망으로 노드에 SSH 접속해 플레이북을 실행합니다. 한 서비스가 실패하면 그 뒤 서비스는 실행되지 않고 Deployment가 실패로 남습니다.
# 실행 결과를 따라가는 명령 (Level 2에서 실습)
oc get openstackdataplanenodeset -n openstack       # 묶음 상태: SetupReady? Ready?
oc get openstackdataplanedeployment -n openstack    # 배포 실행 기록과 결과
oc get jobs -n openstack | grep <deployment 이름>    # 서비스별 Ansible Job
oc logs -n openstack job/<job 이름>               # 실패한 단계의 Ansible 출력

Job 이름에는 보통 서비스 이름과 Deployment·NodeSet 이름이 들어 있어, 어느 단계에서 실패했는지 이름만으로도 알 수 있습니다.

섹션 8

컴퓨트 노드 안에서 생기는 것

배포가 끝난 컴퓨트 노드에 SSH로 들어가 보면 무엇이 있을까요? 핵심은 OpenStack 구성 요소가 podman 컨테이너로 돌고, systemd가 그 컨테이너를 관리한다는 점입니다. Kubernetes Pod가 아닙니다.

# 컴퓨트 노드에서 (예시 형태, 이름과 개수는 구성에 따라 다름)
$ sudo podman ps --format "{{.Names}}"
ovn_controller              # OVN SB DB에서 규칙을 받아 OVS에 적용
ovn_metadata_agent          # VM 메타데이터(169.254.169.254) 중계
nova_compute                # Nova 지시를 받아 VM 생성·관리
(libvirt 관련 컨테이너들)     # virtqemud 등 모듈형 libvirt 데몬
ceilometer_agent_compute    # VM 사용량 수집
node_exporter               # 노드 메트릭 노출

$ systemctl list-units 'edpm_*'   # 컨테이너를 감싼 systemd 서비스들
$ sudo ovs-vsctl show             # br-int(통합 브리지), 외부·프로바이더 브리지, Geneve 터널 포트
$ ip -br addr                     # ctlplane·internalapi·storage·tenant VLAN 인터페이스와 IP
구성 요소무엇에 붙나 (어느 망)죽으면
nova_computeRabbitMQ cell1, Placement·Glance·Neutron·Cinder internal API (internalapi)State down, 새 VM 배치 불가. 기존 VM은 계속 동작
libvirt (virtqemud 등)로컬 QEMU/KVM 프로세스VM 관리(시작·정지·마이그레이션) 불가. 실행 중인 QEMU 프로세스는 대체로 유지

노드에서 직접 고치고 싶을 때

장애 중에 컨테이너를 재시작(systemctl restart edpm_nova_compute 등)하는 것은 응급 조치로 허용되는 경우가 많지만, 설정 파일을 직접 고치는 것은 피합니다. 다음 Deployment가 덮어쓰고, 노드 간 설정 차이(drift)가 생깁니다. 응급 조치를 했다면 같은 내용을 NodeSet에 반영하고 새 Deployment로 확정하세요.

섹션 9

네트워크 격리: 왜, 그리고 무엇을

RHOSO는 트래픽을 종류별로 서로 다른 네트워크(보통 서로 다른 VLAN과 IP 대역)로 나눕니다. 이를 네트워크 격리라고 합니다.

왜 나누나

  • 보안: 고객 VM 트래픽(tenant)이 내부 API·DB 망에 섞이지 않게
  • 성능: 대용량 스토리지 I/O가 API 응답을 방해하지 않게
  • 장애 격리: 한 망의 문제를 다른 망으로 번지지 않게, 원인을 망 단위로 좁히게
  • 운영: 망마다 MTU·QoS·방화벽 정책을 따로 줄 수 있게

비유: 건물의 배관

상수도·하수도·가스·전기를 한 관에 넣지 않습니다. 고장 나도 어느 관인지 바로 알고, 한 관의 문제가 다른 관으로 번지지 않습니다. 격리 네트워크는 데이터센터의 배관 분리입니다.

기본 격리 네트워크

아래 대역·VLAN 값은 Red Hat 문서의 예시 값입니다. 실제 환경에서는 고객사 네트워크 설계에 맞춰 바꿉니다. 이름과 용도는 그대로 기억하세요.

OCP 자체 네트워크는 별개

위 표와 별도로, OpenShift 클러스터 자신의 기본 노드 네트워크(machine network)와 Pod 네트워크(OVN-Kubernetes)가 있습니다. 공개 API Route와 OCP 웹 콘솔은 machine network 쪽 인그레스로 들어옵니다. 즉 OCP 노드에는 “OCP 기본망 + RHOSO 격리망 여러 개”가 함께 붙습니다. 그래서 RHOSO용 OCP 노드는 보통 NIC가 둘 이상이거나, 하나의 NIC 위에 여러 VLAN을 올립니다.

OVN 게이트웨이는 어디에

VM이 플로팅 IP로 외부와 통신하거나 SNAT로 인터넷에 나갈 때, 트래픽은 OVN 게이트웨이 섀시(gateway chassis)를 지납니다. RHOSO에서 게이트웨이를 두는 방법은 세 가지입니다.

방식설명언제
OCP 노드에 게이트웨이별도 네트워커 노드가 없으면 OCP 노드 위의 ovn-controller Pod가 게이트웨이 역할. OVNController CR의 nicMappings로 외부망 인터페이스를 지정소규모, 랩, 노드 수를 줄일 때
전용 네트워커 NodeSet게이트웨이만 맡는 RHEL 노드 묶음을 데이터 플레인으로 배포 (edpm_enable_chassis_gw: true)외부 트래픽이 많을 때, OCP 노드와 분리하고 싶을 때
컴퓨트 노드에 분산컴퓨트 노드가 외부망에 직접 붙어 플로팅 IP 트래픽을 분산 처리외부 트래픽을 한곳에 모으고 싶지 않을 때 (24편)

섹션 10

IP는 누가 나눠 주나: 한 대역, 네 명의 분배자

internalapi 같은 격리망 하나에는 IP를 나눠 주는 주체가 넷 있습니다. 각자 자기 범위를 쓰므로, 범위가 겹치면 IP 충돌이 납니다. 아래 막대를 눌러 보세요(Red Hat 문서 예시 범위 기준).

172.17.0.0/24 (internalapi) 주소 지도

.0.64.128.192.255

구간을 눌러 보세요.

설계 규칙 세 줄

  1. NNCP 고정 IP, NAD(whereabouts) 범위, MetalLB IPAddressPool, NetConfig allocationRange는 서로 겹치면 안 된다.
  2. 게이트웨이·스위치 SVI 등 네트워크 장비가 쓰는 주소는 어느 범위에도 넣지 않는다 (필요하면 excludeAddresses).
  3. 대역마다 같은 규칙(예: .10대 OCP, .30~.70 Pod, .80~.90 VIP, .100~ 노드)을 쓰면 IP만 보고 무엇인지 알 수 있어 장애 대응이 빨라진다.

섹션 11

트래픽 경로 따라가기

이 편의 핵심 그림입니다. 가로줄은 네트워크, 상자는 장비입니다. 트래픽 종류를 고르면 어느 장비가 어느 망으로 통신하는지 강조됩니다. 실선은 기본 연결, 점선은 구성에 따라 있는 연결입니다.

위에서 트래픽 종류를 골라 보세요.

장애 대응에 쓰는 법

“무엇이 안 되는가”를 이 그림의 트래픽 종류로 바꿔 말하면, 확인할 망이 하나로 좁혀집니다. 예: “새 VM이 BUILD에서 멈춤 + nova-compute down” → nova-compute ↔ RabbitMQ 트래픽 → internalapi 망 → 컴퓨트 노드에서 MetalLB VIP로 ping·포트 확인. 2편 장애 회의에서 팀이 했던 추론이 바로 이것입니다.

세 단 배선을 기억하세요

격리망 하나가 Pod까지 이어지려면 세 단이 모두 맞아야 합니다. ① 스위치 포트에 VLAN 허용 → ② NNCP로 OCP 노드에 VLAN 인터페이스 → ③ NAD로 Pod에 인터페이스. 그리고 바깥(컴퓨트 노드)에서 접근하려면 ④ MetalLB VIP가 더해집니다. 장애 시 ①→④ 순서로 확인하면 빠짐이 없습니다. 18편(네트워크 준비)에서 이 네 단을 직접 만듭니다.

섹션 13

클러스터 토폴로지 선택

RHOSO 컨트롤 플레인을 올릴 OCP 클러스터 모양은 몇 가지가 있습니다. 정확한 최소 하드웨어 요구(코어·메모리·디스크·NIC)는 버전에 따라 바뀌므로 Planning your deployment 문서를 기준으로 하고, 여기서는 선택의 감각을 익힙니다.

형태구성장점주의
소형(compact) 3노드OCP 컨트롤 플레인 노드 3대가 워크로드(RHOSO Pod)도 함께 실행서버 수가 적음. 랩·소규모에 적합OCP 자체와 RHOSO가 자원을 나눠 씀. 분산 영역(distributed zones) 구성에는 쓸 수 없음
표준OCP 컨트롤 플레인 3대 + 워커 3대 이상(RHOSO Pod는 워커에)OCP 관리 기능과 RHOSO 부하 분리, 확장 쉬움서버 수 증가
대규모표준 + RHOSO 전용 워커 그룹, 게이트웨이 전용 노드수백 대 컴퓨트, 대량 API 처리대규모 배포 가이드의 하드웨어 권장치 확인
분산 영역여러 사이트에 걸친 OCP 클러스터, 영역별 서비스 배치(topologyRef)사이트 장애 대비사이트 간 저지연 연결 필요, compact 불가
한 OCP에 여러 RHOSO네임스페이스별로 별도 RHOSO 환경개발·검증 환경 통합, 하드웨어 절약망·IP 범위·리소스를 환경별로 철저히 분리

“OCP 노드 하나 재부팅해도 되나요?”

3노드 클러스터에서 노드 하나를 재부팅하면 Galera·RabbitMQ·OVN DB 같은 3복제 구성 요소가 과반수(2/3)로 버티는 상태가 됩니다. 이때 다른 노드 하나에 문제가 겹치면 과반수가 깨져 컨트롤 플레인 전체가 멈춥니다. 그래서 OCP 노드 작업은 한 번에 하나씩, 앞 노드의 Pod가 모두 Ready로 돌아온 것을 확인한 뒤 다음 노드로 넘어갑니다. 26편(유지보수)에서 절차로 정리합니다.

오늘의 핵심 여덟 문장

  • 사람이 쓰는 주문서는 OpenStackControlPlane, NodeSet, Deployment 세 종류이고, 나머지는 Operator가 만든다.
  • 컨트롤 플레인은 서비스별 CR → Deployment·StatefulSet·Job → Pod 순으로 펼쳐지고, DB·큐는 기본용과 cell1용으로 둘씩 있다.
  • 컨트롤 플레인 서비스는 ClusterIP(Pod 간), MetalLB VIP(internal), Route(public) 세 개의 문으로 노출된다. Galera는 컴퓨트 노드에 노출되지 않는다.
  • 데이터 플레인은 NodeSet이 IP를 예약하고, Deployment가 서비스별 Ansible Job을 순서대로 실행해 노드를 설정한다.
  • 컴퓨트 노드의 OpenStack 구성 요소는 systemd가 관리하는 podman 컨테이너다.
  • 격리망은 ctlplane · internalapi · storage · storagemgmt · tenant · external이 기본이며, 망마다 흐르는 트래픽이 정해져 있다.
  • 한 대역 안에서 NNCP · NAD · MetalLB · NetConfig 네 분배자의 범위가 겹치면 안 된다.
  • 격리망 배선은 스위치 VLAN → NNCP → NAD → MetalLB 네 단을 순서대로 확인한다.
