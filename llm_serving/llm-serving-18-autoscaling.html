01시작하기 전에

오토스케일링은 “늘리는 기술”이 아니라 “늘어나기 전 몇 분을 버티는 설계”입니다.

2026년에 바뀐 것
  • llm-d 0.10이 나왔고, 자동 확장 문서가 KEDA + EPP 지표를 권장 경로로 정리했습니다. 처리 중 요청 수(기본), 흐름 제어 대기열, 풀 포화도, 토큰 적체, 예상 지연(SLO) 신호를 고를 수 있습니다.
  • 워크로드 변형 오토스케일러(WVA)는 사용 중단되었습니다(v0.9.0이 마지막). 10편에서 소개한 WVA 대신 KEDA + EPP 경로를 씁니다.
  • HPA에 사용자 지표를 공급하던 Prometheus Adapter는 사용 중단이 예정되어, KEDA를 쓰는 것이 권장됩니다.

학습 목표

  1. CPU·GPU 사용률이 LLM 확장 신호로 부적합한 이유를 설명할 수 있다.
  2. 대기열·처리 중 요청·KV 사용률·토큰 적체·예상 지연 신호의 장단점을 비교해 고를 수 있다.
  3. 기동 시간과 트래픽 증가 속도로 필요한 여유 용량과 목표 사용률을 계산할 수 있다.
  4. HPA 알고리즘과 동작(behavior), KEDA의 ScaledObject·활성화·쿨다운 구조를 설명할 수 있다.
  5. 0으로 축소의 조건·대가·구현 방법을 설명할 수 있다.
  6. KEDA + Prometheus로 추론 지표 기반 확장을 구성하고, 늘어나고 줄어드는 과정을 관찰할 수 있다.
이 편의 비유: 콜센터 상담원 배치

상담원(레플리카)을 더 부르는 기준은 “상담원들이 얼마나 바빠 보이는가(GPU 사용률)”가 아니라 “대기 중인 고객 수(대기열)”여야 합니다. 상담원은 통화 중이면 항상 바빠 보이니까요. 그리고 새 상담원이 출근해 자리에 앉기까지 20분(기동 시간)이 걸리면, 대기 고객이 생긴 뒤에 부르면 이미 늦습니다. 대기 고객이 생기기 전에, 예상 증가 속도만큼 미리 불러 두는 것이 오토스케일링 설계입니다. 퇴근시키는 것(축소)은 천천히 합니다.

02CPU·GPU 사용률로는 안 되는 이유

일반 웹 서비스의 오토스케일링 습관이 LLM에서는 거꾸로 작동합니다.

지표LLM 엔진에서 실제로 보이는 모습결과
CPU 사용률엔진 코어의 바쁜 루프가 부하와 무관하게 CPU 한 코어를 씀 (4편)항상 비슷 → 신호 없음
GPU 사용률 (DCGM GPU_UTIL)배치에 요청이 하나라도 있으면 거의 100% 가까이 보임 (커널이 실행 중인 시간 비율이라)조금만 부하가 있어도 “포화”로 보여 최대까지 늘리거나, 임계값을 높이면 반응하지 않음
GPU 메모리 사용률vLLM이 기동 시 KV 풀을 미리 잡아 항상 높음 (2·4편)부하와 무관
요청 수 (RPS)요청 하나의 비용이 수백 배 차이 (12편)긴 요청이 몰리면 늦게 반응
지연 (TTFT·TPOT)이미 사용자가 느끼고 난 뒤에야 오름후행 지표. 단독으로는 늦음 (예측값이면 다름, 7장)

필요한 것은 “포화 직전”을 알려 주는 선행 지표입니다. 대기열이 쌓이기 시작하거나, 처리 중 요청이 레플리카 용량에 다가가거나, KV 사용률이 선점 근처로 오르는 것은 지연이 나빠지기 전에 나타납니다.

03확장 신호 지도

무엇을 보고 늘릴지에 따라 반응 속도, 설정 난이도, 낭비 정도가 달라집니다.

신호어디서선행·후행장점주의
처리 중 요청 수 (in-flight)엔진 실행 중 요청, EPP의 처리 중 요청선행단순, 레플리카당 용량과 바로 비교 (llm-d 기본 권장 신호)요청 크기 차이를 반영 못 함
대기열 길이엔진 대기 요청, EPP 흐름 제어 대기열선행~동시“충족 못 한 수요”를 직접 보여 줌엔진 상한(14편)이 높으면 대기열 대신 TPOT가 먼저 나빠짐
KV 캐시 사용률엔진선행메모리 쪽 포화를 미리 감지, 긴 문맥 워크로드에 유효프리픽스 캐시가 남겨 둔 블록 때문에 높게 보일 수 있음

토큰 적체 (초 단위)EPP 처리 중 토큰 ÷ 측정한 Prefill 처리량선행요청 크기 차이를 반영, TTFT SLO에서 임계값을 바로 유도하드웨어·모델마다 보정 측정 1회 필요
예상 지연 ÷ SLOEPP의 예측(또는 실측) TTFT·TPOT예측이면 선행목표(SLO) 자체로 확장예측 모델·기록 규칙 필요
일정 (시간대)KEDA cron예측출근·업무시간처럼 예측 가능한 부하에 가장 확실예외 트래픽엔 다른 신호와 함께

실무 출발점은 “처리 중 요청(또는 대기열) + 일정”입니다. 요청 크기 편차가 크면 토큰 적체, 지연 SLO 계약이 있으면 예상 지연 신호로 발전시킵니다. 여러 신호를 함께 걸면 KEDA·HPA는 그중 가장 많은 레플리카를 요구하는 값을 따릅니다.

04확장 루프의 시간 계산

늘리기로 결정한 순간부터 새 레플리카가 요청을 받기까지의 시간 동안, 기존 레플리카가 버텨야 합니다.

반응 시간 ≈ 지표 수집 주기 + 확장 판단 주기 + (노드 확보) + 기동 시간(13편) 버텨야 할 증가분 ≈ 트래픽 증가 속도 × 반응 시간 목표 사용률 ≤ 1 − (버텨야 할 증가분 ÷ 현재 용량) 예) 레플리카당 2 req/s, 레플리카 5개(용량 10), 분당 0.5 req/s씩 증가, 반응 시간 5분 → 버텨야 할 증가분 2.5 req/s → 목표 사용률 ≤ 1 − 2.5/10 = 0.75
  • 기동이 길수록 목표 사용률을 낮춰(여유를 크게) 잡아야 하고, 그만큼 평소 GPU를 더 씁니다. 13편의 기동 단축이 곧 비용 절감인 이유입니다.
  • 레플리카 단위가 클수록(17편 멀티 GPU) 확장의 계단이 커져 세밀한 조절이 어렵습니다.
  • 히어로 시뮬레이터에서 기동 시간과 목표 사용률을 바꿔, “위반 시간”과 “평균 레플리카(비용)”의 맞교환을 확인해 보세요.

05HPA와 KEDA 구조

KEDA는 HPA를 대체하지 않습니다. 외부 지표를 읽어 HPA를 만들고 먹여 주는 역할입니다.

HPA 기본식: 원하는 레플리카 = ⌈ 현재 레플리카 × (현재 지표 ÷ 목표 지표) ⌉ KEDA Prometheus 트리거 (AverageValue): 원하는 레플리카 = ⌈ 쿼리 결과(합계) ÷ threshold ⌉ → 쿼리는 풀 전체 합계로, threshold는 “레플리카 하나가 맡을 양”으로
구성 요소역할LLM에서의 설정 포인트
HPA behavior · scaleUp늘릴 때의 안정화 창·속도 정책빠르게 (안정화 0~60초), 한 번에 여러 개 허용
HPA behavior · scaleDown줄일 때의 안정화 창·속도 정책천천히 (5~10분 이상), 한 번에 하나씩. 다시 늘리면 기동 비용을 또 냄
KEDA ScaledObject대상(Deployment·LWS 등)·최소·최대·트리거 선언 → HPA 생성최소 = 가용성(보통 2), 최대 = GPU 예산
트리거 (scaler)Prometheus, cron, metrics-api 등Prometheus 쿼리로 추론 지표, cron으로 일정
활성화 (activation)0 ↔ 1 전환 기준 (HPA는 1 이상만 다룸)0으로 축소할 때 “깨울 신호”가 앞단에 있어야 함 (6장)
pollingInterval · cooldownPeriod지표 확인 주기, 마지막 활성 후 0으로 내리기까지 대기짧은 주기는 반응↑ 부하↑. 쿨다운은 기동 비용보다 길게
yaml · ScaledObject 예 (엔진 대기·실행 요청 합계 기준)
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: llm-engine, namespace: llmsvc-lab }
spec:
  scaleTargetRef: { name: llm-engine }          # Deployment (LWS·KServe 대상도 가능)
  minReplicaCount: 1
  maxReplicaCount: 4                            # GPU 예산
  pollingInterval: 15
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:   { stabilizationWindowSeconds: 0,   policies: [ { type: Pods, value: 2, periodSeconds: 60 } ] }
        scaleDown: { stabilizationWindowSeconds: 600, policies: [ { type: Pods, value: 1, periodSeconds: 300 } ] }
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus.llmsvc-lab.svc:9090
      query: sum(vllm:num_requests_running{namespace="llmsvc-lab"}) + sum(vllm:num_requests_waiting{namespace="llmsvc-lab"})
      threshold: "12"                           # 레플리카 하나가 SLO 안에서 동시에 처리할 요청 수 × 목표 사용률

threshold는 14편 실측에서 나옵니다. 예를 들어 SLO 용량에서의 평균 처리 중 요청이 16이고 목표 사용률이 0.75라면 12입니다. 지표 이름은 엔진 버전에 따라 다를 수 있으니 /metrics에서 확인합니다.

08노드 확장과 고정 용량

Pod를 늘리라고 해도 GPU가 없으면 Pending입니다.

  • 클라우드: Cluster Autoscaler·Karpenter가 GPU 노드를 추가합니다. 노드 확보·드라이버 준비·이미지 받기가 수 분 더해지므로 반응 시간(4장)에 넣습니다. GPU 인스턴스 재고 부족도 고려해 예약 용량·여러 인스턴스 유형을 준비합니다.
  • 온프레미스·고정 용량: 늘릴 노드가 없으므로 “누가 GPU를 쓰는가”의 문제가 됩니다. Kueue 우선순위·선점(8편)으로 서빙이 늘 때 배치 작업을 밀어내고, 줄면 돌려줍니다. 최대 레플리카는 실제 GPU 수로 제한합니다.
  • 노드에 캐시가 있는 곳으로: 새 레플리카가 이미지·모델 캐시가 있는 노드로 가면 기동이 짧습니다(13편 노드 친화성).

09임계값과 동작 튜닝

확장 루프도 튜닝 대상입니다. 측정값에서 출발합니다.

설정정하는 법잘못되면
threshold (레플리카당 목표)14편 SLO 용량에서의 처리 중 요청 × 목표 사용률(4장 계산)높으면 위반, 낮으면 낭비
최소 레플리카가용성(장애 1개를 버틸 수) + 업무시간 기본 부하1이면 장애·롤링 업데이트 때 전면 중단
최대 레플리카GPU 예산·실제 GPU 수없으면 비용 폭주, 너무 낮으면 위반
늘리기 안정화짧게 (0~60초)길면 늦게 반응
줄이기 안정화기동 비용보다 길게 (보통 5~10분 이상)짧으면 출렁임(늘렸다 줄였다 반복)
지표 쿼리 창순간값보다 1~2분 평균(rate·avg_over_time)순간값은 출렁임 유발
확장 루프를 끝까지 지켜본다

수요 신호가 오름 → 원하는 레플리카가 오름 → 새 Pod가 준비됨 → 수요 신호가 내려옴. 문제가 생기면 이 고리의 이음매 중 하나가 끊긴 것입니다(지표가 안 읽힘, 원하는 수는 올랐는데 Pod가 Pending, Pod는 떴는데 준비가 안 됨, 늘었는데 신호가 안 내려옴 = 잘못된 신호). 실습 18-3의 관찰 대시보드가 이 고리를 한 화면에 보여 주도록 구성합니다.

10MSP 관점

확장 정책은 성능 설정이자 비용 계약입니다.

  • 예산 상한을 계약에: 최대 레플리카(= 최대 GPU 비용)를 고객과 합의하고, 상한에 닿으면 알림을 보냅니다. 상한 때문에 SLO를 못 지킨 시간은 리포트에 따로 표시합니다.
  • 예측 가능한 부하는 일정으로: 대부분의 사내 서비스는 업무 시간 패턴이 뚜렷합니다. 일정 트리거로 기본 용량을 잡고 추론 지표로 예외를 흡수하는 조합이 가장 안정적입니다.
  • 등급별 정책: 프리미엄 고객은 최소 레플리카·여유 용량을 크게, 표준 고객은 공유 풀·0으로 축소. 12편 게이트웨이의 등급과 맞춥니다.
  • 사용량 리포트: 시간대별 레플리카 수(GPU·시간)와 SLO 달성률을 함께 보여 주면 “왜 이 비용인가”를 설명할 수 있습니다.

12실습

랩용 Prometheus와 KEDA를 세우고, GPU 없는 vLLM 시뮬레이터로 추론 지표 기반 확장·축소를 끝까지 관찰한 뒤, 실제 vLLM에는 일정 기반 확장과 0으로 축소의 한계를 확인합니다.

실습 환경 전제
  • 7편 랩, 10편의 vLLM 시뮬레이터 이미지, 14편 slo_probe.py. GPU가 한 장이라 여러 레플리카 확장은 시뮬레이터(CPU)로 관찰합니다.
  • 여기서 설치하는 Prometheus는 랩 전용 최소 구성입니다. 20편에서 운영용 관측 스택으로 바꿉니다.
  • KEDA는 클러스터 공용 구성 요소입니다. 이미 있으면 버전만 확인합니다.
  • KEDA가 Deployment의 레플리카를 관리하는 동안에는 lab.sh up/down이나 수동 scale과 충돌합니다. 수동 작업 전에는 ScaledObject를 지웁니다.

15정리와 체크리스트

핵심 여섯 문장.

  1. CPU·GPU 사용률은 LLM 확장 신호가 아니다. GPU 사용률은 조금만 부하가 있어도 높게 보인다.
  2. 선행 지표(처리 중 요청·대기열·KV·토큰 적체·예상 지연)로 늘린다. 출발점은 처리 중 요청 + 일정.
  3. 목표 사용률은 기동 시간과 트래픽 증가 속도로 계산한다. 기동이 짧을수록 여유를 줄여 GPU를 아낀다.
  4. KEDA는 외부 지표로 HPA를 만든다. 쿼리는 풀 합계, threshold는 레플리카 하나의 몫. 늘리기는 빠르게, 줄이기는 천천히.
  5. 0으로 축소는 깨울 신호가 앞단에 있어야 하고, 첫 요청은 기동 시간을 기다린다. 예측 가능한 부하는 일정이 가장 확실하다.
  6. llm-d는 KEDA + EPP 지표가 권장 경로이고 WVA는 사용 중단되었다. 노드 확장·고정 용량(Kueue)과 함께 설계한다.
