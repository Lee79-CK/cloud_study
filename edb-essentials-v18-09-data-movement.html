데이터 이동

CSV 몇 줄을 넣는 일부터 Oracle 데이터베이스를 통째로 옮기는 일까지, 데이터를 움직이는 도구는 여러 가지입니다. 도구마다 파일이 어디에 있어야 하는지, 무엇을 담고 무엇을 빠뜨리는지가 다릅니다. 이 편의 목표는 상황을 보고 바로 알맞은 도구를 고르는 것입니다.

기준: EPAS 18 / PostgreSQL 18 읽는 시간 약 65분 추정 출제 비중: 중간

2장

COPY와 \copy

두 명령은 문법이 거의 같지만 파일을 읽고 쓰는 주체가 다릅니다. 이것이 시험에 나오는 핵심 차이입니다.

COPY — 서버가 파일을 읽는다

db01:/data/load/orders.csv

파일은 DB 서버에 있어야 하고, 서버 프로세스(enterprisedb OS 사용자)가 읽을 수 있어야 합니다. 슈퍼유저나 pg_read_server_files(쓰기는 pg_write_server_files) 역할이 필요합니다.

\copy — psql이 파일을 읽어 보낸다

내PC:~/Downloads/orders.csv

파일은 psql을 실행한 곳에 있습니다. psql이 파일을 읽어 연결을 통해 서버의 COPY ... FROM STDIN으로 흘려보내므로 특별한 역할이 필요 없고 테이블 권한만 있으면 됩니다.

-- 서버 쪽 COPY
COPY orders FROM '/data/load/orders.csv' WITH (FORMAT csv, HEADER true);
COPY (SELECT * FROM orders WHERE created_at >= '2026-09-01')
  TO '/data/export/orders_sep.csv' WITH (FORMAT csv, HEADER true);

-- 클라이언트 쪽 \copy (한 줄로 써야 함, 끝에 세미콜론 없음)
\copy orders FROM '~/Downloads/orders.csv' WITH (FORMAT csv, HEADER true)
\copy (SELECT * FROM orders WHERE status = 'PAID') TO 'paid.csv' WITH (FORMAT csv, HEADER true)

자주 쓰는 옵션

옵션의미
FORMAT text | csv | binary기본 text(탭 구분). CSV 파일에는 csv
HEADER true첫 줄을 컬럼 이름으로 취급 (입력 시 건너뜀)
DELIMITER ',', NULL '', QUOTE '"'구분자, NULL 표현, 인용 문자
ENCODING 'EUC_KR'파일 인코딩이 서버와 다를 때
WHERE 조건입력할 때 조건에 맞는 행만 (COPY ... FROM ... WHERE)
ON_ERROR ignore타입 변환 오류가 난 행을 건너뛰고 계속 (PG17+). 기본은 stop: 한 행만 틀려도 전체 실패
REJECT_LIMIT nON_ERROR ignore와 함께, 건너뛸 수 있는 오류 행 수 한도 (PG18+)
FREEZE같은 트랜잭션에서 만들거나 비운 테이블에 적재할 때 행을 바로 동결 (8편)
시험 포인트

"클라이언트 PC에 있는 CSV를 슈퍼유저 권한 없이 테이블에 넣으려면?" → \copy. "COPY의 파일 경로는 누구 기준인가?" → DB 서버. 기본적으로 COPY FROM은 한 행이라도 오류가 나면 전체가 롤백됩니다(하나의 문장이므로). 오류 행을 따로 모으고 싶다면 PG17+의 ON_ERROR나 EPAS의 EDB*Loader(bad 파일)를 씁니다.

3장

대량 적재 빠르게 하기

수백만 행 이상을 넣을 때는 순서와 설정만 바꿔도 몇 배 빨라집니다.

  1. INSERT 대신 COPY — 행마다 문장을 보내는 INSERT보다 COPY가 훨씬 빠릅니다. 꼭 INSERT라면 여러 행을 한 문장에 묶고 한 트랜잭션에 넣으세요.
  2. 인덱스·외래 키는 나중에 — 빈 테이블에 적재한다면 인덱스와 FK 제약을 뒤에 만드는 편이 전체적으로 빠릅니다.
  3. 메모리와 WAL 설정 — 세션에서 maintenance_work_mem을 크게(인덱스 생성용), 서버의 max_wal_size를 크게(체크포인트 빈도 감소, 2편) 잡습니다.
  4. UNLOGGED로 적재 후 LOGGED로 — 중간 작업 테이블이라면 CREATE UNLOGGED TABLE로 WAL 없이 넣고 ALTER TABLE ... SET LOGGED로 바꿀 수 있습니다(6편). 단, 장애 시 비워지고 복제되지 않는 점에 주의합니다.
  5. 마지막에 ANALYZE — 적재 직후 통계가 없으면 옵티마이저가 엉뚱한 계획을 고릅니다(8편).

4장

pg_dump와 출력 포맷

pg_dump는 데이터베이스 하나를 논리적으로 내보냅니다. "테이블을 만들고, 데이터를 넣고, 인덱스를 만드는" SQL 또는 그와 같은 내용을 담은 아카이브 파일을 만듭니다. 실행하는 동안 하나의 일관된 스냅샷(8편)으로 읽으므로 서비스 중에도 일관된 결과를 얻습니다.

큰 DB의 pg_dump는 "오래 열린 트랜잭션"이다

pg_dump가 몇 시간 동안 스냅샷을 쥐고 있으면, 그 사이 생긴 dead tuple을 VACUUM이 치우지 못합니다(8편 2장). 대용량 운영 DB의 정기 백업은 10편의 물리 백업이 주력이고, pg_dump는 특정 DB·스키마의 이전이나 보조 백업에 씁니다.

포맷 고르기

필요한 조건을 체크하면 알맞은 포맷을 추천하고 명령을 만들어 줍니다.

포맷옵션복원 도구선택 복원병렬 덤프병렬 복원압축
plain (SQL)-Fp (기본)psql불가불가불가선택
custom-Fcpg_restore가능불가가능기본

자주 쓰는 옵션

pg_dump -p 5444 -U enterprisedb -Fc -f sales.dump sales          # 전체 DB, custom 포맷
pg_dump -p 5444 -Fd -j 4 -f sales_dir sales                      # directory 포맷 병렬 4
pg_dump -p 5444 -n hr -f hr.sql sales                            # hr 스키마만, plain SQL
pg_dump -p 5444 -t 'hr.emp*' -Fc -f emp.dump sales               # 이름 패턴으로 테이블 선택
pg_dump -p 5444 -s -f schema_only.sql sales                      # 구조만 (-s)
pg_dump -p 5444 -a -f data_only.sql sales                        # 데이터만 (-a)
pg_dump -p 5444 -Fc -Z zstd:5 -f sales.dump sales                # 압축 방식·수준 지정 (PG16+)
pg_dump -p 5444 -Fc -O -x -f sales.dump sales                    # 소유자(-O)·권한(-x) 정보 빼기
시험 포인트

① plain SQL은 psql로, 나머지 세 포맷은 pg_restore로 복원합니다. ② 덤프를 병렬로 할 수 있는 것은 directory 포맷뿐입니다. ③ pg_dump는 역할과 테이블스페이스를 담지 않습니다(클러스터 공용 객체, 6편) — 이것은 pg_dumpall의 몫입니다. ④ EPAS 전용 객체(패키지, 시너님 등)가 있다면 EPAS에 포함된 pg_dump를 쓰세요.

5장

pg_dumpall과 전역 객체

pg_dumpall은 클러스터의 모든 데이터베이스와 전역 객체(역할, 테이블스페이스)를 하나의 plain SQL 스크립트로 내보냅니다. custom 포맷을 지원하지 않으므로 선택·병렬 복원이 불가능합니다. 그래서 실무에서는 보통 둘을 섞어 씁니다.

# 1) 전역 객체만 (역할·테이블스페이스·역할 비밀번호 해시)
pg_dumpall -p 5444 --globals-only -f globals.sql       # -g 와 같음
pg_dumpall -p 5444 --roles-only   -f roles.sql         # 역할만 (-r)

# 2) DB별로는 pg_dump custom 포맷
for db in sales hr_app; do pg_dump -p 5444 -Fc -f ${db}.dump $db; done

# 새 서버에서 복원 순서: 전역 객체 → DB
psql -p 5444 -d edb -f globals.sql
pg_restore -p 5444 -C -d edb sales.dump
시험 포인트

"pg_dump로 옮겼더니 역할이 없어 권한 부여 단계에서 오류가 났다. 무엇이 빠졌나?" → pg_dumpall --globals-only로 역할을 먼저 옮겨야 합니다. pg_dumpall은 plain SQL만 만들고, 복원은 psql로 합니다. 비밀번호 해시가 들어 있으므로 파일 보관에 주의하세요.

6장

pg_restore

pg_restore -p 5444 -d sales_new sales.dump                  # 이미 만든 DB에 복원
pg_restore -p 5444 -C -d edb sales.dump                     # -C: 덤프에 적힌 이름으로 DB를 만들고 복원 (-d는 접속용 DB)
pg_restore -p 5444 -j 4 -d sales_new sales.dump             # 병렬 복원 (custom·directory)
pg_restore -p 5444 -c --if-exists -d sales sales.dump       # 기존 객체를 지우고 다시 만듦
pg_restore -p 5444 -n hr -t emp -d sales_new sales.dump     # 일부만
pg_restore -p 5444 -1 -d sales_new sales.dump               # 하나의 트랜잭션으로 (실패 시 전체 롤백, -j와 함께 불가)
pg_restore -p 5444 --no-owner --role=app_owner -d sales_new sales.dump   # 소유자를 바꿔 복원

# 목차를 뽑아 편집한 뒤 그 순서·항목만 복원
pg_restore -l sales.dump > toc.list      # 필요 없는 줄 앞에 ; 를 붙여 주석 처리
pg_restore -L toc.list -d sales_new sales.dump
용어: 복원 대상 DB는 template0으로

덤프에는 확장과 객체 정의가 모두 들어 있으므로, template1에 회사 표준 객체가 추가되어 있으면 "이미 존재함" 오류가 섞입니다. 복원용 빈 DB는 CREATE DATABASE sales_new TEMPLATE template0;으로 만드는 것이 안전합니다(6편 3장). -C 옵션을 쓰면 pg_restore가 template0으로 알아서 만듭니다.

버전 규칙

  • 새 버전의 pg_dump는 옛 버전 서버를 덤프할 수 있습니다. 반대는 보장되지 않습니다.
  • 덤프 결과는 같거나 새 버전 서버에 복원하는 것이 원칙입니다.
  • 그래서 pg_dump로 메이저 업그레이드를 할 때는 새 버전(목적지)의 pg_dump로 옛 서버를 덤프합니다.
현장 사례: 고객사 DB를 테스트 환경으로 복제

"운영 DB를 개발 서버에 복사해 주세요"는 MSP의 단골 요청입니다. 순서는 ① 개발 서버에 pg_dumpall -g로 역할 이전(필요하면 비밀번호 재설정), ② pg_dump -Fd -j로 운영 부하가 적은 시간에 덤프, ③ pg_restore -C -j로 병렬 복원, ④ ANALYZE입니다. 개인정보가 있다면 복원 후 마스킹하거나, 7편의 Data Redaction 같은 조회 단계 통제와 별개로 데이터 자체를 가공해야 한다는 점을 고객과 먼저 합의하세요.

7장

EDB*Loader

EDB*Loader(실행 파일 edbldr)는 Oracle SQL*Loader와 호환되는 대량 적재 도구입니다. Oracle에서 쓰던 제어 파일(.ctl)을 거의 그대로 쓸 수 있어, 레거시 배치를 옮길 때 특히 유용합니다. 주요 특징은 다음과 같습니다.

  • SQL*Loader의 세 가지 적재 방식: 일반 경로(conventional), 직접 경로(direct), 병렬 직접 경로(parallel direct)
  • 구분자 방식과 고정 폭 필드 모두 지원, 여러 대상 테이블에 나눠 적재
  • 거부된 행을 모으는 bad 파일, 조건에 맞지 않아 걸러진 행을 모으는 discard 파일, 세션 기록인 log 파일

적재 실험

데이터 파일 여섯 줄을 적재합니다. "적재 실행"을 누르면 행마다 어디로 가는지 보여 줍니다.

emp.ctl (제어 파일)
LOAD DATA
  INFILE 'emp.dat'
  BADFILE 'emp.bad'
  DISCARDFILE 'emp.dsc'
  INSERT INTO TABLE emp
  WHEN (deptno != '99')
  FIELDS TERMINATED BY ','
  (empno, ename, job, sal, deptno)
emp.dat (데이터 파일)
# 실행 (enterprisedb 사용자, 파일은 edbldr을 실행한 클라이언트 쪽에 있어야 함)
/usr/edb/as18/bin/edbldr -d edb USERID=enterprisedb CONTROL=emp.ctl LOG=emp.log
/usr/edb/as18/bin/edbldr -d edb CONTROL=emp.ctl BAD=/tmp/emp.bad DIRECT=TRUE   # 직접 경로
시험 포인트

bad 파일은 형식 오류·제약 위반 등으로 거부된 행, discard 파일은 WHEN 조건에 맞지 않아 걸러진 행이 갑니다. EPAS 12 이후 bad 파일은 거부된 행이 있을 때만 만들어집니다. DIRECT=TRUE는 직접 경로 적재로, 기본값은 FALSE(일반 경로)입니다. EDB*Loader는 PgBouncer 같은 커넥션 풀러를 거쳐 쓸 수 없고 서버에 직접 연결해야 합니다. 풀러를 거쳐야 한다면 psql의 \copy 등을 씁니다.

8장

EDB Clone Schema

스키마 하나를 그 안의 테이블, 데이터, 인덱스, 함수, 권한까지 통째로 다른 스키마로 복제하는 EPAS 확장입니다. 원본과 대상은 같은 데이터베이스, 같은 클러스터의 다른 데이터베이스, 다른 서버의 데이터베이스 모두 가능합니다. 개발·테스트용 스키마 사본을 만들거나, 스키마 단위로 데이터를 옮길 때 씁니다.

remotecopyschema다른 DB(같은 클러스터 또는 다른 서버)로 복제
remotecopyschema_nb위와 같지만 백그라운드 작업으로

시험 포인트

대상 스키마는 미리 존재하면 안 됩니다. 함수들은 edb_util 스키마에 만들어지며, 로컬 복제는 외부 서버 하나, 원격 복제는 외부 서버 두 개(원본·대상)를 인자로 받습니다. 확장 자체는 복제되지 않고, 스키마 사이 의존 관계도 자동으로 풀어 주지 않습니다. 병렬 복사 작업은 최대 16개이며, _nb(백그라운드) 함수는 슈퍼유저만 실행할 수 있습니다.

9장

Oracle에서 옮겨 오기

Oracle 애플리케이션을 EPAS로 옮기는 작업은 보통 "평가 → 스키마 변환 → 데이터 이전 → 검증" 순서로 진행합니다. EDB는 단계별 도구를 제공합니다. 이 시험에서는 이름과 역할을 구분하는 수준이면 충분합니다.

도구형태역할
Migration Portal웹 서비스Oracle에서 추출한 DDL을 올리면 EPAS와의 호환성을 평가하고, 호환되지 않는 부분을 보고하며, EPAS용 DDL로 변환해 줍니다. 이전 계획 수립의 출발점
Migration Toolkit (MTK)명령줄 도구원본 DB에 직접 연결해 스키마와 데이터를 EPAS로 옮깁니다. Oracle 외 다른 DBMS 원본도 지원하며, 설정 파일에 원본·대상 접속 정보를 적어 실행
EDB*Loader명령줄 도구Oracle에서 내보낸 파일을 SQL*Loader 제어 파일 그대로 적재 (7장)
Oracle 호환 기능 전반EPAS 자체변환된 스키마가 적은 수정으로 동작하게 해 줌 (12편)

지원하는 원본 DBMS의 종류와 버전, 세부 옵션은 도구 버전마다 달라지므로 EDB 공식 문서를 기준으로 확인하세요.
