1

무엇을 믿고 무엇을 의심할 것인가

모든 검증 규칙은 이 경계선 하나에서 나옵니다.

2편에서 확인한 사실 하나가 보안의 출발점입니다. SAML 메시지는 전부 사용자의 브라우저를 거쳐 옵니다. 브라우저는 사용자의 통제 아래 있고, 그 사용자가 악의를 가진 사람일 수도 있습니다. 그러니 SP에 도착한 모든 값은 일단 “조작 가능한 입력”으로 취급해야 합니다.

믿을 수 있는 것

  • 연동 설정 시 등록해 둔 IdP의 공개키(인증서)
  • SP 서버가 자기 세션에 저장해 둔 요청 ID
  • 서명 검증을 통과한 바로 그 노드의 내용
  • SP 자신의 설정값 (Entity ID, ACS URL)

의심해야 하는 것

  • SAMLResponse 안의 모든 값 — 검증 전까지는 전부
  • RelayState 문자열
  • 메시지에 적힌 Issuer, Destination, ACS URL
  • 서명이 걸리지 않은 영역의 모든 내용
  • 요청받지 않았는데 도착한 응답
핵심 원칙 한 문장 — 서명 검증은 “이 문서가 진짜인가”를 알려줄 뿐, “이 문서가 나에게, 지금, 내가 요청해서 온 것인가”는 알려주지 않습니다. 뒤의 세 가지는 각각 Audience, 유효시간, InResponseTo가 담당합니다. 서명 하나만 보고 통과시키는 구현이 가장 흔한 사고 원인입니다.

그래서 SP가 해야 할 검증은 딱 다섯 갈래로 정리됩니다. 다음 장에서 이 다섯 개를 하나씩 켜고 끄면서, 각각이 없을 때 어떤 공격이 열리는지 직접 확인해 보겠습니다.

3

XML 서명 래핑 (XSW)

SAML 고유의, 그리고 가장 유명한 취약점 유형.

서명은 제대로 검증했는데도 뚫리는 경우가 있습니다. 서명을 검증한 부분과, 애플리케이션이 실제로 읽은 부분이 서로 다른 노드일 때입니다. 이것이 XML Signature Wrapping의 본질입니다.

왜 이런 일이 가능할까요. XML 서명은 “이 문서 전체”가 아니라 ID로 지목한 특정 노드에 걸립니다. 그런데 문서를 파싱해서 사용자 정보를 꺼내는 코드는 대개 “문서 안의 첫 번째 Assertion을 찾아라” 같은 방식으로 동작합니다. 이 둘이 서로 다른 노드를 가리키게 만들 수 있으면 검증은 통과하고 내용은 공격자의 것이 됩니다.

서명 검증기가 보는 노드
애플리케이션이 실제로 읽는 노드
두 관점이 같은 노드를 가리키면 안전합니다. 위 버튼으로 상태를 바꿔 보세요.
무엇이 문제인가 — 서명 자체는 조작되지 않았습니다. 유효한 서명이 유효한 노드에 그대로 걸려 있습니다. 문제는 검증한 노드와 사용한 노드가 다르다는 데 있습니다. 그래서 “서명 검증 통과”라는 로그만 보고는 사고를 알아채기 어렵습니다.

막는 방법

직접 구현하지 마세요 — XSW는 변형이 매우 다양해서, XML 파싱과 서명 검증을 직접 조합하는 방식으로는 막기 어렵습니다. 검증된 SAML 라이브러리를 쓰고 최신 버전을 유지하는 것이 가장 현실적인 방어입니다. 이 계열 취약점은 주요 라이브러리에서 지금도 주기적으로 발견되고 패치됩니다.
4

Golden SAML

IdP의 서명 키가 유출되면 무슨 일이 벌어지는가.

지금까지는 SP의 검증이 부실한 경우를 봤습니다. 이번에는 반대쪽입니다. 검증은 완벽한데, IdP의 서명용 개인키 자체가 공격자 손에 들어간 상황입니다. 이 경우 공격자는 어떤 사용자로든, 어떤 권한이든 담은 Assertion을 마음대로 발급할 수 있습니다. 그리고 그것은 진짜 서명이 걸린 진짜 문서입니다.

평소의 대응Golden SAML 상황에서
비밀번호 강제 변경무의미 — 비밀번호를 거치지 않습니다
MFA 요구무의미 — 인증 단계 자체를 건너뜁니다
IdP 로그인 로그 분석흔적 없음 — IdP에 로그인 기록이 남지 않습니다
계정 잠금우회 가능 — 존재하는 다른 계정으로 발급하면 됩니다
서명 인증서 교체유효 — 유출된 키로 만든 서명이 전부 무효가 됩니다
SP 측 세션 전면 무효화유효 — 이미 발급된 세션까지 끊어야 합니다
탐지가 어려운 이유를 정확히 이해하세요 — IdP에는 아무 기록이 남지 않습니다. 공격자가 IdP를 거치지 않고 직접 문서를 만들어 SP에 제출하기 때문입니다. 흔적은 오직 SP 쪽에 남습니다. 그래서 SP의 인증 로그를 IdP 로그와 대조하는 것이 사실상 유일한 탐지 수단입니다. 7장에서 구체적인 방법을 다룹니다.

키를 지키는 일이 전부입니다

MSP 관점 — 고객사 IdP 서버는 도메인 컨트롤러나 관리자 워크스테이션과 같은 등급으로 다뤄야 합니다. 이 서버에 대한 관리자 접근이 곧 전체 클라우드 환경에 대한 접근이기 때문입니다. 키를 파일로 보관하는 구성이라면, 그 파일에 접근 가능한 계정 목록이 곧 “전 직원으로 위장할 수 있는 사람 목록”입니다.
5

그 밖에 알아둘 공격들

덜 유명하지만 실제로 사고가 났던 유형들입니다.

공통점 하나 — 위 사례 대부분은 파서와 검증기가 같은 문자열을 다르게 해석하거나, 설정 기본값이 느슨해서 발생했습니다. 그래서 대응도 비슷합니다. 라이브러리를 최신으로 유지하고, 기본값에 의존하지 말고 명시적으로 강제 설정을 걸고, 연동 후에는 실제 응답을 뜯어서 기대대로 동작하는지 확인하는 것입니다.
6

인증서와 알고리즘 운영

공격보다 훨씬 자주 겪게 될, 실무의 절반.

1편에서 예고했던 인증서 만료 이야기입니다. SAML 운영에서 가장 자주 발생하는 장애이고, 동시에 가장 예측 가능한 장애이기도 합니다. 날짜가 정해져 있으니까요.

무중단 롤오버 절차

D-90

만료 예정 확인과 일정 잡기

연동된 SP 목록을 뽑고, 각각의 담당자와 변경 창구를 정리합니다. SaaS는 콘솔에서 직접 바꾸지만, 고객사 자체 개발 앱은 배포가 필요할 수 있습니다.

D-30

새 인증서 생성 후 병행 등록

IdP 메타데이터에 신규 인증서를 기존 것과 함께 게시합니다. 이 시점에는 여전히 기존 키로 서명합니다. SP들은 두 인증서를 모두 신뢰하는 상태가 됩니다.

D-21

SP 측 반영 확인

메타데이터 URL을 자동으로 갱신하는 SP는 저절로 반영되지만, 수동 등록 방식은 하나씩 확인해야 합니다. 여기서 누락된 SP가 나중에 장애가 됩니다.

D-14

서명 키 전환

IdP가 새 키로 서명하도록 전환합니다. 반영이 확인된 SP부터 순차적으로 진행할 수 있으면 더 안전합니다. 전환 직후 실제 로그인 테스트는 필수입니다.

D-7

구 인증서 제거

모든 SP가 정상 동작하는 것을 확인한 뒤 기존 인증서를 메타데이터에서 내립니다. 만료일까지 여유를 두는 이유는 문제 발생 시 되돌릴 시간을 확보하기 위해서입니다.

아직 푼 문제가 없습니다

3편에서 챙겨 갈 것

  • 서명 검증은 “진짜인가”만 답한다. “나에게, 지금, 내가 요청해서 왔는가”는 별도 항목이 담당한다.
  • SP의 검증 항목은 여섯 개다 — 서명, Audience, 유효시간, InResponseTo, Recipient, 재사용 방지.
  • XSW는 서명을 검증한 노드와 실제로 읽은 노드가 다를 때 성립한다. 직접 구현하지 말고 검증된 라이브러리를 최신으로 유지한다.
  • Golden SAML은 비밀번호 변경·MFA·계정 잠금이 모두 무력하다. 대응은 인증서 교체와 세션 전면 무효화다.
  • IdP 서명 키는 도메인 컨트롤러급으로 보호한다. 가능하면 HSM에 두고 파일로 꺼내지 않는다.
  • 인증서 롤오버는 신·구 병행 등록 → SP 반영 확인 → 서명 전환 → 구 인증서 제거 순서로 한다.
  • SHA-1과 1024비트 키는 정리 대상이다. 서명은 Assertion에 거는 것을 기본으로 한다.
  • SP 로그인 성공과 IdP 인증 기록을 대조하는 규칙 하나가 가장 가성비 높은 탐지 수단이다.

4편에서는

드디어 손으로 만듭니다. Keycloak을 IdP로 세우고, AWS IAM Identity Center와 Microsoft Entra ID를 실제로 연동합니다. 속성 매핑으로 IAM Role을 제어하는 방법, 고객사 환경에 SAML 연동을 인수인계받았을 때의 점검 순서, 그리고 SAML에서 OIDC로 넘어갈지 판단하는 기준까지 다루며 시리즈를 마무리합니다.
