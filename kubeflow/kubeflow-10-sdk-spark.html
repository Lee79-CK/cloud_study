    SDK는 빠르게 바뀌는 중입니다
    
Kubeflow SDK는 2025년에 처음 공개되어 활발히 개발 중인 프로젝트입니다. 클래스와 함수의 이름, 인자가 버전마다 달라질 수 있습니다. 이 편의 코드는 구조와 흐름을 보여 주는 데 초점을 두었으니, 실제 작업에서는 설치한 버전의 문서(sdk.kubeflow.org)를 함께 보세요.

  






  
1왜 통합 SDK인가

  
지금까지는 구성요소마다 다른 패키지, 다른 인증 방식, 다른 사용법을 익혀야 했습니다. 데이터 과학자에게는 Kubeflow가 하나의 플랫폼이 아니라 다섯 개의 도구로 보였습니다. 통합 Kubeflow SDK는 그 위에 하나의 Python 층을 얹습니다. 각 구성요소를 대체하는 것이 아니라, 같은 방식으로 부르게 해 주는 것입니다.

  

    
하려는 일예전 방식통합 SDK설치

    
      
분산 학습kubeflow-training 패키지, PyTorchJob YAMLkubeflow.trainer.TrainerClientpip install kubeflow

      
하이퍼파라미터 튜닝kubeflow-katib 패키지의 KatibClientkubeflow.optimizer.OptimizerClientpip install kubeflow

      
Spark 처리SparkApplication YAML을 직접 작성kubeflow.spark.SparkClientpip install "kubeflow[spark]"

      
모델 등록model-registry 패키지kubeflow.hub.ModelRegistryClientpip install "kubeflow[hub]"

      
파이프라인kfp 패키지통합이 진행 중. 지금은 kfp 패키지가 기본pip install kfp

    
  

  
실무에서는 두 방식이 한동안 섞여 쓰입니다. 예전 패키지로 쓴 코드가 많고, 통합 SDK가 아직 모든 기능을 덮지 못하기 때문입니다. 새로 시작하는 코드는 통합 SDK로, 기존 코드는 필요할 때 옮기는 것이 현실적입니다.






  
2공통 패턴

  
어느 클라이언트든 쓰는 모양이 비슷합니다. 클라이언트를 만들고, 일을 시키면 이름이 돌아오고, 그 이름으로 기다리고 로그를 보고 지웁니다.


from kubeflow.trainer import TrainerClient, CustomTrainer, KubernetesBackendConfig

# 1. 클라이언트: 어디서(backend), 어느 네임스페이스에서
client = TrainerClient(backend_config=KubernetesBackendConfig(namespace="kubeflow-user-example-com"))

# 2. 일 시키기: 이름이 돌아온다
job = client.train(trainer=CustomTrainer(func=train_fn, num_nodes=2))

# 3. 같은 이름으로 지켜보고 정리한다
client.wait_for_job_status(job)
for line in client.get_job_logs(job):
    print(line)
print(client.list_jobs())
client.delete_job(job)

클러스터에 제출하면 이미지를 받고 Pod가 뜨기까지 몇 분씩 걸립니다. 오타 하나 고치려고 그 시간을 매번 기다리면 개발이 느려집니다. Trainer 클라이언트는 실행 위치(backend)만 바꿔 같은 코드를 세 곳에서 돌릴 수 있습니다. 맨 위 지도에서 TrainerClient를 고르고 실행 위치를 바꿔 보세요.

    좋은 개발 리듬
    
데이터를 아주 작게 줄여 로컬 프로세스에서 로직이 끝까지 도는지 보고, 로컬 컨테이너에서 이미지와 두 노드 통신을 확인한 뒤, 클러스터에 제출합니다. 클러스터에서 실패하는 원인이 권한, 자원, 네트워크처럼 클러스터 고유의 것만 남게 되어 디버깅이 훨씬 쉬워집니다. 파이프라인은 5편 10장의 kfp.local이 같은 역할을 합니다.

  






  
4Spark가 필요한 순간

  
지금까지의 실습 데이터는 1,797건이었습니다. 실제 추천팀의 클릭 로그는 하루 수억 건입니다. pandas는 데이터를 한 대의 메모리에 통째로 올리기 때문에, 데이터가 메모리보다 크면 OOMKilled(2편)로 끝납니다. Apache Spark는 데이터를 파티션이라는 조각으로 나눠 여러 Pod에서 동시에 처리합니다.

  

    
Spark 용어뜻Kubernetes에서

    
      
driver작업 계획을 세우고 일을 나눠 주는 지휘자Pod 하나

      
executor파티션을 실제로 처리하는 일꾼Pod 여러 개

      
파티션데이터의 조각. 조각 하나를 executor의 코어 하나가 처리(task)-

      
셔플groupBy, join처럼 데이터를 키별로 다시 나누느라 executor끼리 대량으로 주고받는 단계Pod 간 네트워크와 로컬 디스크를 많이 씀

      
지연 실행변환은 계획만 세우고, show, write 같은 동작을 만나야 실제로 실행-

    
  

  
Kubeflow에는 Spark Operator가 포함되어 있습니다. 2024년에 Kubeflow 산하 프로젝트가 되었고, 26.03.1에는 2.5 계열이 들어 있습니다. 주요 리소스는 배치 작업용 SparkApplication, 예약 실행용 ScheduledSparkApplication, 대화형 접속용 SparkConnect입니다.

5노트북에서 Spark Connect

  
Spark Connect는 Spark 클러스터를 원격 서버로 띄워 두고, 노트북 같은 가벼운 클라이언트가 접속해 DataFrame 코드를 보내는 방식입니다. 노트북에 Spark를 통째로 설치하거나 노트북 Pod의 메모리로 데이터를 처리할 필요가 없습니다. SDK의 SparkClient().connect()는 SparkConnect 리소스를 만들어 driver와 executor를 띄우고, 접속된 Spark 세션을 돌려줍니다.

  
!pip install "kubeflow[spark]"

from kubeflow.spark import SparkClient
from pyspark.sql import functions as F

client = SparkClient()
spark = client.connect(
    num_executors=2,
    resources_per_executor={"cpu": "1", "memory": "2Gi"},   # kind 실습 규모
)

# 가짜 클릭 로그 1,000만 건: 사용자 1,000명
clicks = spark.range(0, 10_000_000).selectExpr(
    "id", "id % 1000 AS user_id", "rand(42) AS score")

# 사용자별 피처: 여기까지는 계획만 세워짐(지연 실행)
features = clicks.groupBy("user_id").agg(
    F.count("*").alias("events"), F.avg("score").alias("avg_score"))

features.orderBy(F.desc("avg_score")).show(5)   # 이 순간 executor들이 실제로 계산
spark.stop()

  
    
    
  • 계산은 executor Pod들이 하고, 노트북에는 결과의 일부(show의 다섯 줄)만 돌아옵니다. toPandas()로 전체를 가져오면 결국 노트북 메모리에 다 올라오므로 결과가 작을 때만 씁니다.
    • 
    
  • 실무에서는 결과를 features.write.parquet("s3a://...")처럼 오브젝트 스토리지에 쓰고, 다음 단계(학습)가 그 위치를 읽습니다. 이때 Spark 이미지에 S3 연결용 라이브러리와 자격 증명 설정이 필요합니다(8장).
    • 
    
  • 이미 떠 있는 Spark Connect 서버가 있다면 connect(base_url="sc://서버:15002")로 접속만 할 수도 있습니다.

7파이프라인에 Spark 넣기

  
파이프라인의 첫 단계로 Spark 처리를 넣으면, 1편 노선도의 데이터 준비부터 등록까지가 한 줄로 이어집니다. 가장 단순한 방법은 SparkApplication을 만들고 끝날 때까지 기다리는 컴포넌트입니다. 파이프라인 단계 Pod도 프로필의 서비스 계정으로 실행되므로 같은 네임스페이스에 SparkApplication을 만들 수 있습니다.


@dsl.component(base_image="python:3.11", packages_to_install=["kubernetes", "pyyaml"])
def run_spark(app_yaml: str, namespace: str) -> str:
    import time, yaml
    from kubernetes import client, config
    config.load_incluster_config()
    api = client.CustomObjectsApi()
    app = yaml.safe_load(app_yaml)
    name = app["metadata"]["name"]
    api.create_namespaced_custom_object("sparkoperator.k8s.io", "v1beta2", namespace,
                                        "sparkapplications", app)
    while True:
        obj = api.get_namespaced_custom_object("sparkoperator.k8s.io", "v1beta2", namespace,
                                               "sparkapplications", name)
        state = obj.get("status", {}).get("applicationState", {}).get("state", "")
        if state in ("COMPLETED", "FAILED"):
            break
        time.sleep(15)
    if state != "COMPLETED":
        raise RuntimeError(f"Spark 작업 실패: {state}")
    return name

  
    
    
  • SparkApplication 이름은 실행마다 달라야 합니다. 날짜나 5편의 실행 ID를 이름에 붙이세요(6편의 PIPELINE_JOB_ID 같은 자리 표시자 활용).
    • 
    
  • Spark가 쓴 결과 위치(s3a://...)를 출력 파라미터로 내보내면 다음 학습 단계가 받아 씁니다. 다만 이 데이터는 KFP 아티팩트가 아니므로 계보가 자동으로 남지 않습니다. 위치를 9편의 레지스트리 메타데이터에 함께 기록해 두세요.
    • 
    
  • 재시도를 걸 때는 같은 이름이 이미 있으면 지우고 다시 만드는 등 멱등하게 짜야 합니다(6편 4장).

8Spark 운영 포인트

  

    
주제알아 둘 것

    
      
메모리 오버헤드executor 메모리를 8g로 주면 Pod는 그보다 큰 메모리를 요청합니다. JVM 밖에서 쓰는 메모리 몫(기본은 대략 10%, 최소 384MB)이 더해지고, PySpark는 Python 프로세스 몫도 필요합니다. 노드 하나에 몇 개가 들어가는지 계산할 때 빼먹기 쉽습니다

      
권한driver는 executor Pod를 직접 만들므로, driver의 서비스 계정에 Pod와 Service를 만들 권한이 있어야 합니다. 설치 구성에 따라 사용자 네임스페이스에 Spark용 서비스 계정이 준비되어 있는지 확인합니다

      
Istiodriver와 executor는 7편의 분산 학습처럼 서로 직접 통신합니다. 사이드카가 통신을 막거나 작업이 끝나도 Pod가 완료되지 않을 수 있어 Spark Pod에서는 흔히 사이드카를 뺍니다

      
S3 연결s3a:// 경로를 쓰려면 이미지에 hadoop-aws 등 연결 라이브러리가 있어야 하고, 엔드포인트와 자격 증명을 sparkConf나 Secret으로 줍니다

      
셔플 저장소셔플 중간 결과는 executor의 로컬 디스크에 씁니다. 노드 디스크가 부족하면 Evicted(2편)가 납니다. 큰 작업은 로컬 볼륨을 넉넉히 줍니다

      
동적 할당dynamicAllocation을 켜면 처리량에 따라 executor 수가 늘고 줄어 자원을 아낍니다. 상한을 꼭 둡니다

      
비용executor는 중간에 죽어도 Spark가 그 파티션만 다시 계산하므로, 스팟 노드와 잘 맞습니다. driver는 죽으면 전체가 실패하므로 일반 노드에 둡니다
