1

무엇을 만드는가

하나의 IdP에 서로 다른 성격의 SP 세 개를 붙입니다.

실습 구성은 단순합니다. Keycloak을 IdP로 세우고, 여기에 세 종류의 SP를 연결합니다. 각각 연동 방식이 조금씩 달라서, 세 개를 다 해보면 현장에서 만나는 대부분의 패턴을 커버하게 됩니다.

3편의 검증 여섯 항목 적용
Entra ID는 반대편에서 다룹니다 — 5장에서는 Entra ID를 IdP로 두고 SP를 붙입니다. 실무에서는 회사 계정이 이미 Entra ID에 있는 경우가 많아, Keycloak보다 이쪽이 더 자주 만나게 되는 구성입니다. 두 제품의 용어 차이를 비교하는 표도 함께 넣었습니다.
실습 전 준비 — Docker가 설치된 로컬 환경이면 충분합니다. AWS 연동을 끝까지 해보려면 실습용 계정이 필요하고, IAM SAML Provider와 Role을 만들 권한이 있어야 합니다. 운영 계정에서는 절대 진행하지 마세요. 아래 모든 명령은 실습 환경 기준입니다.
2

Keycloak을 IdP로 세우기

컨테이너 하나로 시작해서 서명 키까지 확인합니다.

01

컨테이너 실행

개발 모드로 띄웁니다. 실습용이므로 HTTP로 동작하며, 운영에서는 절대 이 모드를 쓰지 않습니다.

docker run -d --name keycloak -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD='ChangeMe!23' \
  quay.io/keycloak/keycloak:26.0 start-dev

# 브라우저에서 http://localhost:8080 접속 후 admin 로그인

Keycloak 25 이하에서는 환경변수 이름이 KEYCLOAK_ADMIN, KEYCLOAK_ADMIN_PASSWORD입니다. 버전에 따라 다르니 실행 로그를 확인하세요.

02

Realm과 사용자 만들기

Realm은 독립된 계정 공간입니다. 고객사별로 Realm을 나누는 구성이 일반적입니다. 좌측 상단 드롭다운에서 Create realm → 이름은 corp로 합니다. 그다음 Users 메뉴에서 테스트 사용자를 만들고, Credentials 탭에서 비밀번호를 설정합니다. Groups 메뉴에서 sre-oncall 그룹도 만들어 사용자를 넣어 둡니다. 이 그룹이 나중에 AWS 권한으로 연결됩니다.

03

SAML Client 생성

Clients → Create client → Client type을 SAML로 선택합니다. Client ID가 곧 SP의 Entity ID이고, 이후 화면에서 ACS URL(Valid redirect URIs / Master SAML Processing URL)을 지정합니다. 1편에서 본 메타데이터 교환이 여기서 일어납니다.

04

IdP 메타데이터 주소 확인

SP 쪽에 등록할 메타데이터 URL입니다. 여기에 Entity ID, SSO 엔드포인트, 서명 인증서가 모두 들어 있습니다.

# IdP 메타데이터 (SP에 등록할 내용)
http://localhost:8080/realms/corp/protocol/saml/descriptor

# curl로 확인
curl -s http://localhost:8080/realms/corp/protocol/saml/descriptor | head -40
05

서명 키 확인

Realm settings → Keys 탭에서 RSA 키와 인증서를 볼 수 있습니다. 3편에서 다룬 내용을 여기서 실제로 확인하세요. 알고리즘이 RS256인지, 키 길이가 2048 이상인지, 인증서 유효기간이 언제까지인지. 롤오버 실습을 하고 싶다면 이 화면에서 새 키를 추가하고 우선순위를 바꿔 보면 됩니다.

여기서 1~3편이 전부 눈에 보입니다 — Keys 탭의 인증서는 1편의 신뢰 관계, descriptor XML은 메타데이터, Client의 ACS URL은 2편의 응답 수신 주소, 그리고 Keys의 알고리즘 설정은 3편의 권장 설정입니다. 개념이 어디에 대응하는지 한 번씩 짚어 보고 넘어가세요.
3

AWS 직접 페더레이션

IAM SAML Provider와 Role을 쓰는 전통적인 방식입니다.

AWS 콘솔에 회사 계정으로 로그인하는 구성입니다. 핵심은 Assertion의 속성에 담긴 Role ARN이 곧 사용자의 AWS 권한이 된다는 점입니다. 3편에서 속성 매핑을 조심하라고 했던 이유가 여기 있습니다.

AWS 쪽 고정값

항목값
ACS URLhttps://signin.aws.amazon.com/saml
Audience / Entity IDurn:amazon:webservices
NameID Formatpersistent 또는 emailAddress

필수 속성 세 가지

속성 이름값설명
.../SAML/Attributes/Rolerole ARN,provider ARN쉼표로 두 ARN을 이어 붙입니다. 여러 개 보내면 로그인 시 역할을 고를 수 있습니다
.../SAML/Attributes/RoleSessionName이메일 또는 사용자명CloudTrail에 기록되는 이름입니다. 감사 추적의 기준이 됩니다
.../SAML/Attributes/SessionDuration초 단위 (900~43200)선택 항목. 미지정 시 기본 1시간입니다
RoleSessionName을 반드시 개인 식별자로 — 여기에 고정 문자열을 넣으면 CloudTrail에 모든 사용자가 같은 이름으로 기록됩니다. 사고가 났을 때 누가 했는지 추적이 불가능해집니다. 감사에서 반드시 지적되는 항목입니다.

신뢰 정책 생성기

계정 ID와 이름을 넣으면 IAM Role의 신뢰 정책과 Role 속성값을 만들어 줍니다. 그대로 복사해 쓰시면 됩니다.

등록 명령

# 1. IdP 메타데이터를 파일로 저장
curl -s http://localhost:8080/realms/corp/protocol/saml/descriptor \
  -o idp-metadata.xml

# 2. IAM에 SAML Provider 등록
aws iam create-saml-provider \
  --name Keycloak \
  --saml-metadata-document file://idp-metadata.xml

# 3. 신뢰 정책으로 Role 생성 (위 생성기의 JSON을 trust-policy.json으로 저장)
aws iam create-role \
  --role-name SRE-OnCall \
  --assume-role-policy-document file://trust-policy.json

# 4. 권한 정책 연결 (실습용 읽기 전용)
aws iam attach-role-policy \
  --role-name SRE-OnCall \
  --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess
인증서를 교체하면 Provider도 갱신해야 합니다 — 3편의 롤오버 절차에서 "SP 반영 확인" 단계가 AWS에서는 aws iam update-saml-provider 명령입니다. 메타데이터를 다시 내려받아 갱신하지 않으면 서명 검증에 실패합니다.
4

IAM Identity Center 방식

계정이 여러 개라면 이쪽이 정답입니다.

3장의 직접 페더레이션은 계정마다 SAML Provider와 Role을 따로 만들어야 합니다. 계정이 스무 개면 스무 번입니다. IAM Identity Center는 이 문제를 해결합니다. 한 곳에서 외부 IdP를 연결하고, 여러 계정에 권한 세트를 배포하는 구조입니다.

비교직접 페더레이션IAM Identity Center
연동 지점계정마다 개별 설정조직에 한 번
권한 부여 방식Assertion 속성에 Role ARN그룹 → 권한 세트 할당
사용자 동기화없음 (매번 속성으로 전달)SCIM으로 자동 프로비저닝
속성 매핑 실수 위험높음 — ARN 오타가 곧 권한 오류낮음
적합한 상황계정 1~2개, 레거시 구성멀티 계정 조직 (대부분)
01

외부 IdP로 전환

IAM Identity Center 콘솔 → Settings → Identity source → Change to External identity provider. 여기서 AWS 쪽 메타데이터를 내려받고, IdP 메타데이터를 업로드합니다. 양방향 교환이 한 화면에서 끝납니다.

02

SCIM 프로비저닝 켜기

Automatic provisioning을 활성화하면 SCIM 엔드포인트 URL과 액세스 토큰이 발급됩니다. 이 값을 Keycloak 또는 Entra ID에 등록하면 사용자와 그룹이 자동으로 동기화됩니다. 퇴사 처리가 IdP 한 곳에서 끝나는 이유가 이 연결입니다.

03

권한 세트 만들고 할당

Permission sets에서 권한을 정의하고, 그룹 단위로 계정에 할당합니다. 예를 들어 sre-oncall 그룹에 운영 계정의 ReadOnly + 개발 계정의 PowerUser를 주는 식입니다. Assertion에 Role ARN을 실어 보낼 필요가 없어집니다.

04

액세스 포털 확인

사용자에게는 액세스 포털 URL 하나만 안내하면 됩니다. 로그인하면 자신에게 할당된 계정과 역할 목록이 보이고, 콘솔 진입과 CLI 자격 증명 발급을 모두 여기서 합니다.

SCIM 토큰도 관리 대상입니다 — 이 토큰이 있으면 사용자와 그룹을 조작할 수 있습니다. 즉 권한 부여 경로에 직접 개입할 수 있다는 뜻입니다. 만료일이 있으므로 인증서와 같은 선상에서 갱신 일정을 관리하세요. 3편에서 만든 인증서 캘린더에 함께 넣어 두면 좋습니다.
5

Entra ID를 IdP로 쓸 때

실무에서 가장 자주 만나는 구성입니다.

회사가 Microsoft 365를 쓴다면 계정은 이미 Entra ID에 있습니다. 새 IdP를 세울 이유가 없으니, 이 경우 Entra ID가 IdP가 되고 우리는 SP를 붙이는 쪽이 됩니다.

01

엔터프라이즈 애플리케이션 등록

Entra 관리 센터 → Enterprise applications → New application. 갤러리에 있는 SaaS라면 검색해서 추가하고, 자체 앱이면 Create your own application → "Integrate any other application" 을 선택합니다.

02

SAML 기본 구성 입력

Single sign-on → SAML을 선택한 뒤 두 값을 넣습니다. Identifier (Entity ID)는 SP의 Entity ID, Reply URL은 ACS URL입니다. 1편 용어와 그대로 대응합니다.

03

클레임 구성

Attributes & Claims에서 어떤 값을 보낼지 정합니다. AWS 연동이라면 여기서 Role ARN 클레임을 추가합니다. Entra ID는 이 화면에서 소스 속성을 고르거나 변환식을 쓸 수 있습니다.

04

인증서와 엔드포인트 가져오기

SAML Certificates 섹션에서 서명 인증서를, 아래 섹션에서 로그인 URL과 Entra ID 식별자를 복사해 SP에 등록합니다. Federation Metadata XML을 통째로 내려받아 등록하는 쪽이 오타가 없어 안전합니다.

05

사용자·그룹 할당

Users and groups에서 이 앱에 접근할 대상을 지정합니다. 할당하지 않으면 로그인할 수 없습니다. 3편 장애 목록의 "특정 사용자만 로그인이 안 된다"의 흔한 원인이 이 할당 누락입니다.

6

자체 개발 앱을 SP로 붙이기

직접 구현할 때 반드시 확인할 것들.

3편에서 "직접 구현하지 마세요"라고 했습니다. 정확히는 XML 파싱과 서명 검증을 직접 조합하지 말라는 뜻입니다. 검증된 라이브러리를 쓰되, 그 라이브러리가 무엇을 검사하고 무엇을 안 하는지는 반드시 알아야 합니다.

라이브러리를 골랐다면 다음 세 가지를 확인하세요 — ① 최근 릴리스 시점과 보안 공지 이력 ② 3편의 검증 여섯 항목이 기본값으로 켜져 있는지, 아니면 옵션인지 ③ Assertion 서명을 강제하는 설정이 있는지. 특히 ②는 라이브러리마다 기본값이 달라서, 문서를 읽지 않고 쓰면 검증이 꺼진 채로 운영에 올라갑니다.

구현 시 점검 항목

7

인수인계받았을 때의 점검 순서

문서 없는 환경을 넘겨받았을 때 무엇부터 보는가.

운영 중인 고객사 환경을 인계받는 상황을 가정합니다. SAML 연동이 걸려 있는데 설정 문서는 없습니다. 이 순서로 파악하면 반나절 안에 전체 그림이 나옵니다.

01

IdP가 무엇인지, 어디에 있는지 확인

Entra ID인지 Okta인지 자체 구축 Keycloak인지. 자체 구축이라면 서버 위치, 접근 권한, 백업 여부, 그리고 누가 관리자 계정을 갖고 있는지를 먼저 파악합니다.

02

연동된 SP 목록 전수 조사

IdP 콘솔의 애플리케이션 목록이 출발점입니다. 각각에 대해 담당자, 용도, 사용자 수, 그리고 메타데이터를 자동 갱신하는지 수동 등록인지를 기록합니다. 수동 등록분이 인증서 교체 때 사고를 냅니다.

03

인증서 만료일 전수 확인

가장 먼저 해야 할 일일 수도 있습니다. 만료가 한 달 안이면 다른 모든 작업보다 우선합니다. 확인 즉시 캘린더에 등록하고, 3편의 롤오버 일정을 잡으세요.

04

알고리즘과 검증 설정 점검

SHA-1을 쓰는 연동이 있는지, 서명이 Response에만 걸려 있는지, IdP-initiated가 불필요하게 켜져 있는지 확인합니다. 3편의 자가진단 12항목을 그대로 돌리면 됩니다.

05

퇴사자 처리 경로 확인

계정 비활성화가 실제로 모든 SP에 반영되는지 테스트합니다. SCIM이 걸려 있지 않은 SP는 수동 처리 대상이며, 이 목록이 곧 감사 리스크입니다.

06

로그 수집 여부 확인

SP와 IdP 인증 로그가 어디에 얼마나 보관되는지 봅니다. 3편의 대조 탐지 규칙을 적용하려면 양쪽 로그가 같은 곳에 모여야 합니다. 없다면 이것이 첫 개선 과제입니다.

파악한 내용을 문서로 남기기

SAML을 계속 쓸 것인가, OIDC로 갈 것인가

1편에서 "신규는 OIDC, 기존은 SAML 유지"가 일반적이라고 했습니다. 하지만 실제 판단은 상황에 따라 갈립니다. 아래 질문에 답해 보세요.

전환할 때 잊기 쉬운 것 — 두 프로토콜은 세션 관리 방식이 다릅니다. SAML은 IdP 세션과 SP 세션이 따로 놀지만, OIDC는 토큰 만료와 리프레시라는 별도 개념이 들어옵니다. 로그아웃 동작, 세션 유효시간 정책, 그리고 감사 로그 형식까지 전부 재설계 대상이라고 보셔야 합니다.
9

시리즈 정리와 마지막 점검

네 편을 한 장으로 압축했습니다.

1편

개념과 구조

  • Principal · IdP · SP 세 역할
  • 신뢰는 메타데이터 교환과 전자서명으로
  • Assertion은 네 덩어리로 읽는다
  • 명세는 Assertion → Protocol → Binding → Profile
2편

동작 흐름과 바인딩

  • 모든 메시지는 브라우저가 나른다
  • SP-initiated가 기본, IdP-initiated는 신중히
  • 요청은 Redirect, 응답은 POST
  • RelayState는 검증 대상 입력
3편

보안과 검증

  • SP 검증 여섯 항목
  • XSW는 검증 노드와 사용 노드의 불일치
  • Golden SAML은 키 보호가 유일한 답
  • 인증서 롤오버는 병행 등록부터
4편

클라우드 실전

  • Keycloak으로 IdP 구축
  • AWS는 Role ARN 속성 또는 Identity Center
  • 제품이 달라도 찾을 값은 다섯 개
  • 인수인계는 인증서 만료일부터

마지막 퀴즈

아직 푼 문제가 없습니다

4편에서 챙겨 갈 것

  • Keycloak은 컨테이너 하나로 시작할 수 있고, Realm이 계정 공간의 단위다.
  • AWS 직접 페더레이션에서는 Assertion 속성의 Role ARN이 곧 권한이다. RoleSessionName은 반드시 개인 식별자로 넣는다.
  • 멀티 계정 환경이라면 IAM Identity Center가 정답이다. 그룹 기반 권한 세트와 SCIM 동기화를 쓴다.
  • 제품이 달라도 찾을 값은 다섯 개다 — Entity ID, ACS URL, 속성 매핑, 메타데이터, 접근 할당.
  • SAML 라이브러리를 고를 때는 검증 항목이 기본값인지 옵션인지를 문서에서 확인한다.
  • 인수인계는 IdP 파악 → SP 전수 조사 → 인증서 만료일 → 검증 설정 → 퇴사 처리 경로 → 로그 순서로 본다.
  • OIDC 전환은 클라이언트 유형과 SP 지원 여부가 결정한다. 세션·로그아웃·감사 로그가 함께 재설계 대상이다.

시리즈를 마치며

SAML은 2005년에 확정된 오래된 규격이지만, 기업 환경에서는 여전히 현역입니다. 그리고 여기서 익힌 사고방식 — 신뢰를 어떻게 성립시키는가, 무엇을 검증해야 하는가, 키를 어떻게 보호하는가 — 는 OIDC든 워크로드 아이덴티티든 그대로 옮겨 갑니다. 프로토콜은 바뀌어도 질문은 같습니다. 수고하셨습니다.
