01API 테스트가 뭔가요?

"화면 눌러서 확인하면 되는 거 아니에요?" 라는 질문부터 풀어봅시다.

API를 식당에 비유하면

API(Application Programming Interface)는 프로그램끼리 대화하는 창구입니다. 식당에 비유하면 이해가 빠릅니다. 손님(앱)은 주방(서버)에 직접 들어가지 않습니다. 웨이터(API)에게 정해진 형식(메뉴판 = API 명세)으로 주문하고, 웨이터가 음식(데이터)을 가져다 줍니다. API 테스트란 이 웨이터가 주문을 제대로 받고, 제대로 된 음식을 제 시간에 가져오는지 확인하는 일입니다.

왜 화면(UI) 테스트만으로는 부족할까

화면을 눌러 확인하는 테스트를 E2E 테스트라고 합니다. 사용자와 가장 비슷하니 좋아 보이지만, 느리고, 잘 깨지고, 실패했을 때 원인을 찾기 어렵습니다. 버튼 위치가 5px 바뀌었다고 테스트가 빨간불이 되면 아무도 그 테스트를 믿지 않게 됩니다. API 테스트는 화면을 거치지 않고 서버와 직접 대화하므로 훨씬 빠르고 안정적입니다.

비교 항목손으로 화면 클릭API 자동 테스트
200개 검증 소요 시간2~3시간 (사람이 계속 붙어 있어야 함)1~3분 (자동)
실행 시점배포 직전에 한 번, 그것도 급하면 생략커밋할 때마다 매번
실패 원인 파악"뭔가 안 되는데요...""POST /orders 가 400 대신 500 반환"
프런트엔드 완성 전 검증불가능가능 (백엔드만 있으면 됨)
누락·실수사람이 지치면 대충 봄항상 같은 기준으로 검사
정리. API 테스트 = 화면 없이 서버에 직접 요청을 보내고, 돌아온 상태 코드·응답 본문·응답 시간이 약속대로인지 확인하는 것. Postman은 이 일을 GUI로, Newman은 같은 일을 터미널/CI에서 해줍니다.

03요청 보내고 응답 읽기

실습용 공개 API로 손을 먼저 움직여 봅시다. 회원가입도 인증도 필요 없습니다.

연습용 공개 API

  • https://postman-echo.com — 보낸 요청을 그대로 되돌려줌. 헤더/바디 확인에 최적
  • https://jsonplaceholder.typicode.com — 가짜 게시글/사용자 데이터. CRUD 흉내 가능
  • https://httpbin.org — 상태 코드, 지연, 인증 등 다양한 상황을 일부러 만들어 줌
  • https://reqres.in — 로그인/토큰 시나리오 연습에 좋음

HTTP 메서드: 동사 5개만 알면 됩니다

메서드의미예시Body여러 번 호출해도 안전?
GET조회GET /orders/8801없음안전 (멱등)
POST생성POST /orders필수위험 — 주문이 2건 생김
PUT전체 교체PUT /orders/8801필수 (전체 필드)안전 (멱등)
PATCH부분 수정PATCH /orders/8801필수 (바꿀 것만)대체로 안전
DELETE삭제DELETE /orders/8801보통 없음안전 (멱등)
신입이 가장 많이 하는 실수. POST 요청 Body를 raw로 넣어놓고 형식을 Text로 둔 채 보내는 것. 반드시 오른쪽 드롭다운에서 JSON을 선택하세요. 그래야 Content-Type: application/json 헤더가 자동으로 붙습니다. 이걸 놓치면 서버는 400이나 415를 돌려줍니다.

# └──────────┴───────┘

POST https://jsonplaceholder.typicode.com/posts
Content-Type: application/json

{
  "title": "첫 주문",
  "body": "신입 개발자의 첫 API 호출",

# 응답 (201 Created) — 생성된 리소스의 id가 돌아온다
{ "title": "첫 주문", "userId": 1, "id": 101 }
Path Variable — URL에 콜론을 쓰면 아래 표에 입력칸이 생깁니다
GET {{baseUrl}}/users/:userId/orders/:orderId

# Path Variables 표
# userId  = 42
# orderId = 8801

# 실제 전송되는 URL

#   경로 = "무엇을"  ·  쿼리 = "어떻게 걸러서"
파일 업로드 — Body → form-data
POST {{baseUrl}}/v1/files

응답 읽는 법 — 상태 코드

응답의 첫인상은 세 자리 숫자입니다. 앞자리만 봐도 누구 잘못인지 알 수 있습니다.

범위뜻자주 보는 코드누구 책임?
2xx성공200 OK · 201 Created · 204 No Content축하합니다
3xx리다이렉트301 · 302 · 304 Not Modified보통 정상
4xx요청이 잘못됨400 Bad Request · 401 인증 실패 · 403 권한 없음 · 404 없음 · 409 충돌 · 422 검증 실패 · 429 너무 많이 호출보낸 쪽(나)
5xx서버가 터짐500 · 502 Bad Gateway · 503 · 504 Timeout서버 쪽
401과 403 구분. 401은 "당신이 누군지 모르겠다"(토큰 없음/만료), 403은 "누군지는 알겠는데 그럴 권한이 없다"입니다. 401이면 토큰을 다시 발급받고, 403이면 계정 권한을 확인하세요.

인증(Authorization) 붙이기

실무 API의 90%는 인증이 필요합니다. Postman은 Authorization 탭에서 종류만 고르면 헤더를 알아서 만들어 줍니다.

04변수와 환경

"개발 서버에서 테스트한 컬렉션을 운영 서버에서도 그대로 돌리고 싶다"는 요구를 해결하는 장치입니다.

하드코딩의 함정

✗ 이렇게 하면

https://dev-api.corp.com/orders
https://dev-api.corp.com/users
https://dev-api.corp.com/payments
... 요청 87개

운영 서버로 바꾸려면 87개를 전부 수정. 하나 빠뜨리면 운영 DB에 테스트 데이터가 들어갑니다.

✓ 이렇게 하면

{{baseUrl}}/orders
{{baseUrl}}/users
{{baseUrl}}/payments
... 요청 87개

우측 상단 드롭다운에서 Dev → Prod 한 번 클릭이면 끝. 실수할 여지가 사라집니다.

변수의 5단계 우선순위

같은 이름의 변수가 여러 곳에 있으면 더 좁은 범위가 이깁니다. 이 순서를 모르면 "분명히 값을 바꿨는데 안 바뀌어요" 같은 미궁에 빠집니다.

환경 만들기와 코드에서 다루기

Environments ▸ + ▸ 이름: "dev"
# [dev] 환경
baseUrl      = https://dev-api.corp.com
tenantId     = t-dev-001
accessToken  = (비워둠 — 로그인 스크립트가 채움)

# [prod] 환경  ← 같은 변수 이름, 다른 값
baseUrl      = https://api.corp.com
tenantId     = t-prod-001
accessToken  = (비워둠)

# INITIAL VALUE 와 CURRENT VALUE 의 차이 (매우 중요)
#  INITIAL : 팀에 공유될 때 함께 올라가는 값 → 비밀번호 절대 금지
#  CURRENT : 내 PC에만 남는 값        → 여기에 실제 토큰을 넣습니다
Tests / Pre-request Script 탭
// 읽기
const url = pm.environment.get("baseUrl");
const any = pm.variables.get("baseUrl");   // 스코프 상관없이 조회

// 쓰기
pm.environment.set("accessToken", token);   // 환경에 저장
pm.collectionVariables.set("orderId", 8801); // 컬렉션에 저장
pm.globals.set("traceId", id);              // 전역 (되도록 지양)

// 지우기 — 테스트 후 뒷정리
pm.environment.unset("tempId");

// 사용은 어디서나 이중 중괄호로
//   URL:    {{baseUrl}}/orders/{{orderId}}
//   Header: Authorization: Bearer {{accessToken}}
//   Body:   { "tenant": "{{tenantId}}" }
Postman 내장 동적 변수 — 매번 새 값이 생성됩니다
// 중복 이메일 오류를 피하려고 매번 다른 값이 필요할 때
{
  "email":  "{{$randomEmail}}",
  "name":   "{{$randomFullName}}",
  "uuid":   "{{$guid}}",
  "nonce":  "{{$timestamp}}",
  "qty":    {{$randomInt}}
}

// 자주 쓰는 것들
//  {{$guid}}          UUID v4
//  {{$timestamp}}     현재 유닉스 시간(초)
//  {{$isoTimestamp}}  ISO8601 형식
//  {{$randomInt}}     0~1000 정수
//  {{$randomEmail}} {{$randomFirstName}} {{$randomCompanyName}}
보안 주의. 컬렉션을 export한 JSON 파일에는 Initial Value가 그대로 들어갑니다. 실제 토큰이나 비밀번호를 Initial Value에 넣은 채 Git에 커밋하면 그대로 유출됩니다. 비밀값은 반드시 Current Value에만 두고, 변수 타입을 secret으로 지정하세요. CI에서는 뒤에서 배울 --env-var 옵션으로 주입합니다.

05스크립트와 테스트 코드

여기부터가 "요청 보내기 도구"와 "테스트 자동화 도구"를 가르는 분기점입니다.

스크립트가 실행되는 순서

모든 요청에는 Pre-request Script(보내기 전)와 Tests(받은 후) 두 개의 코드 칸이 있습니다. 이름은 Tests지만 사실 응답을 받은 뒤 실행되는 아무 JavaScript나 쓸 수 있습니다.

테스트 코드의 기본 뼈대

07Newman: 터미널에서 컬렉션 실행하기

Postman이 "사람이 클릭하는 도구"라면, Newman은 "기계가 실행하는 도구"입니다. 이름은 Postman(우편배달부)의 라이벌 캐릭터에서 따왔습니다.

왜 Newman이 필요한가

새벽 3시에 배포 파이프라인이 돌 때, Postman 앱을 열어 Run 버튼을 눌러줄 사람은 없습니다. Newman은 Collection Runner와 완전히 동일한 엔진을 CLI로 제공합니다. 같은 컬렉션 파일이 GUI에서도, 젠킨스에서도, 쿠버네티스 Job에서도 똑같이 동작합니다.

🖱️Postman (GUI)탐색·디버깅·시나리오 작성에 강함. 사람이 눈으로 확인. 실행하려면 앱이 켜져 있어야 함.
⌨️Newman (CLI)자동 실행·리포트 파일 생성·종료 코드 반환. 헤드리스 서버, 컨테이너, CI 러너 어디서든 동작.

종료 코드(Exit Code) — CI가 성공/실패를 판단하는 기준

Exit Code의미CI 동작
0모든 assertion 통과다음 단계로 진행 (배포 계속)
1테스트 실패 또는 요청 오류 발생파이프라인 중단 (배포 차단)
이 한 줄이 핵심입니다. Newman이 exit 1을 반환하면 CI 스텝이 빨간불이 되고, 배포가 자동으로 멈춥니다. 즉 테스트 코드가 배포 게이트키퍼가 됩니다. 리포트만 필요하고 파이프라인은 계속 진행해야 한다면 --suppress-exit-code를 씁니다.

최근 Postman은 postman이라는 새 CLI도 제공합니다. 둘 다 컬렉션을 실행하지만 성격이 다릅니다.

구분NewmanPostman CLI
설치npm install -g newman공식 설치 스크립트 / 바이너리
동작 방식완전 로컬. 인터넷·계정 불필요API Key로 로그인, 결과를 클라우드에 보고
결과 확인터미널 + 로컬 리포트 파일Postman 웹 대시보드에 이력 누적
추가 기능실행에 집중API 거버넌스·린팅 검사 등
폐쇄망(air-gapped)적합부적합 (외부 통신 필요)
선택 기준. 사내 폐쇄망이나 외부 연동 없이 순수 실행만 필요하면 Newman. 팀 대시보드에 실행 이력을 모으고 거버넌스까지 쓰고 싶으면 Postman CLI. 학습과 대부분의 CI에는 Newman이면 충분하고, 자료도 훨씬 많습니다.

가장 많이 헷갈리는 것: Newman vs k6/JMeter

Newman = 기능 테스트

"응답이 맞는가?"를 봅니다. 요청 1건씩 순차 실행하며 값이 정확한지 검증합니다.

Newman으로 부하 테스트를 흉내내려고 -n 1000을 주는 경우가 있는데, 이는 순차 반복일 뿐 동시 접속이 아닙니다. 성능 측정 도구로 쓰면 안 됩니다.

k6 / JMeter = 성능 테스트

"동시에 1,000명이 몰리면 버티는가?"를 봅니다. p95 응답시간, TPS, 에러율을 측정합니다.

둘은 대체재가 아니라 보완재입니다. 실무 파이프라인은 보통 Newman으로 기능을 확인한 뒤, 릴리스 전에 k6로 부하를 겁니다.

  MSG=$(jq -r '.run.failures[] | "• \(.source.name): \(.error.message)"' /tmp/r.json)

사례 6 — API 문서 자동 발행

컬렉션에 설명과 예시를 잘 적어두면 View documentation 한 번으로 웹 문서가 만들어집니다. 별도 문서 도구를 유지할 필요가 줄고, "문서와 실제 API가 다른" 고질병도 완화됩니다.

기존 방식컬렉션 기반
위키에 손으로 작성 → 코드가 바뀌면 즉시 낡음테스트에 쓰는 컬렉션이 곧 문서 → 테스트가 통과하면 문서도 유효
예시 요청/응답을 복붙실제 응답을 Example로 저장해 그대로 노출
"이거 어떻게 호출해요?" 질문 반복Run in Postman 버튼으로 상대가 즉시 실행
OpenAPI와의 연결. 이미 Swagger/OpenAPI 명세가 있다면 Postman의 Import로 명세 파일을 넣어 컬렉션을 자동 생성할 수 있습니다. 그러면 요청을 처음부터 만들 필요 없이 Tests 스크립트만 채워 넣으면 테스트 스위트가 완성됩니다. 실무에서 가장 빠른 출발 방법입니다.

서버가 안 떠 있거나 포트가 틀렸습니다. 컨테이너 안에서 localhost를 쓰면 컨테이너 자신을 가리킨다는 점에 주의. Docker에서는 host.docker.internal, 쿠버네티스에서는 서비스명(svc.namespace)을 사용하세요.

🔴 self signed certificate

사내 사설 인증서 환경. Postman은 Settings → General → SSL certificate verification을 끄고, Newman은 --insecure를 붙입니다. 운영 검증에서는 대신 --ssl-extra-ca-certs로 사내 CA를 등록하는 편이 안전합니다.

🟡 변수가 {{baseUrl}} 그대로 나감

환경이 선택되지 않았거나(우측 상단 드롭다운이 No Environment), 변수 이름 오타이거나, Current Value가 비어 있는 경우입니다. 변수에 마우스를 올리면 현재 값이 툴팁으로 보입니다.

🟡 Postman은 되는데 Newman은 실패

거의 항상 환경 변수 미주입입니다. Postman은 내 PC의 Current Value를 쓰지만, export한 파일에는 그 값이 없습니다. --env-var로 CI에서 넣어주세요.

🟡 401이 갑자기 발생

토큰 만료입니다. 로그인 요청을 컬렉션 맨 앞에 두거나, 컬렉션 Pre-request Script에서 만료를 감지해 자동 재발급하도록 만드세요.

🟢 브라우저는 CORS 오류인데 Postman은 성공

정상입니다. CORS는 브라우저의 보안 정책이라 Postman에는 적용되지 않습니다. 서버 문제가 아니라 서버의 CORS 헤더 설정 문제이니, 응답 헤더에서 Access-Control-Allow-Origin을 확인하세요.

🟡 Unexpected token in JSON

pm.response.json()이 실패한 것. 서버가 HTML 오류 페이지를 돌려준 경우가 많습니다. pm.response.text()로 실제 내용을 먼저 확인하세요.

🟡 CI에서만 간헐적 실패(flaky)

비동기 처리 타이밍 문제일 가능성이 큽니다. --delay-request로 간격을 주거나, "생성 직후 즉시 조회" 대신 재시도 로직을 넣으세요. 무작정 재실행하는 습관은 위험합니다.

13요약과 다음 단계

이 강의의 핵심 8줄

  1. API 테스트는 화면 없이 서버와 직접 대화해 응답이 약속대로인지 확인하는 일이다.
  2. Postman은 요청을 만들고 시나리오를 설계하는 GUI, Newman은 같은 컬렉션을 CLI로 실행하는 도구다.
  3. URL은 반드시 {{baseUrl}} 같은 변수로 두고, 환경 전환으로 dev/prod를 오간다.
  4. 변수 우선순위는 Local > Data > Environment > Collection > Global.
  5. 테스트는 pm.test("설명", () => { ... }) 하나로 시작한다. 상태 코드·필수 필드·응답 시간 3종이 기본.
  6. 로그인 응답의 토큰을 변수에 저장하는 체이닝이 실무 시나리오의 뼈대다.
  7. Newman의 exit code가 0이면 통과, 1이면 실패 → CI가 배포를 막는다.
  8. 기능 검증은 Newman, 성능 측정은 k6/JMeter. 둘은 역할이 다르다.
