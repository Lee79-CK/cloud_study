llm-d 해부
분산 추론 플랫폼

2편에서 Prefill은 연산, Decode는 메모리 대역폭이 병목이라는 것과, 둘이 한 GPU에서 섞이면 긴 Prefill이 Decode를 멈칫하게 만든다는 것을 봤습니다. 이번 편은 그 문제를 아예 다른 GPU로 나눠서 푸는 Prefill/Decode 분리, 여러 레플리카 중 캐시를 가진 곳으로 보내는 KV 캐시 인지 라우팅, 그리고 둘을 잇는 KV 전송 계층(NIXL)을 해부합니다. 이 세 가지를 쿠버네티스 위에서 “잘 닦인 경로”로 묶어 둔 것이 llm-d입니다.

01시작하기 전에

분산 추론은 GPU를 더 쓰는 기술이 아니라, 같은 GPU를 더 맞게 쓰는 기술입니다. 그리고 그 효과는 규모가 있어야 나타납니다.

학습 목표

  1. Prefill/Decode 분리가 해결하는 문제(간섭·서로 다른 최적 설정)와 오히려 손해가 되는 조건을 설명할 수 있다.
  2. KV 전송량과 네트워크 대역폭으로 P/D 분리의 TTFT 비용을 계산하고, 선택적 P/D의 기준을 세울 수 있다.
  3. 근사·정밀 프리픽스 캐시 점수와 부하 점수를 조합하는 KV 캐시 인지 라우팅을 설명하고, 라운드로빈과의 차이를 보여 줄 수 있다.
  4. NIXL·UCX·RDMA로 이어지는 KV 전송 경로와 네트워크 요구 사항을 설명할 수 있다.
  5. llm-d Router(프록시+EPP), InferencePool, 모델 서버, P/D 사이드카 등 구성 요소와 요청 흐름을 그릴 수 있다.
  6. llm-d의 설치 방식(standalone·gateway 모드, kustomize 오버레이)과 잘 닦인 경로를 고르고, 시뮬레이터로 라우팅 동작을 실습할 수 있다.
랩의 한계를 먼저 밝혀 둡니다
  • P/D 분리는 GPU가 최소 두 장 있어야 의미가 있습니다. 우리 랩의 GPU 서빙 장치는 GB10 한 장이라 P/D의 성능 효과는 측정할 수 없습니다. 이 편에서는 계산기로 효과를 예측하고, 멀티 GPU 환경에서의 측정 설계와 구성 파일 읽기로 대신합니다.
  • llm-d가 공식 검증하는 NVIDIA 장비는 A100·H100·H200·B200이며, GB10(DGX Spark·PGX)은 목록에 없습니다.
  • 대신 llm-d가 제공하는 GPU 없는 vLLM 시뮬레이터로 여러 레플리카를 만들어 라우팅 동작은 그대로 실습합니다. 8편의 타임 슬라이싱을 쓸 수 있다면 실제 vLLM 두 개로 프리픽스 캐시 라우팅의 TTFT 효과도 측정합니다.
이 편의 비유: 손질 주방과 조리 주방

지금까지의 엔진은 한 주방에서 재료 손질(Prefill)과 조리(Decode)를 같이 했습니다. 단체 주문이 들어오면 손질에 화구를 뺏겨 진행 중이던 요리가 멈칫합니다. P/D 분리는 손질 전용 주방과 조리 전용 주방을 따로 두고, 손질된 재료(KV 캐시)를 컨베이어(NIXL)로 넘기는 방식입니다. KV 캐시 인지 라우팅은 “이 단골의 밑반찬을 이미 준비해 둔 주방”으로 주문을 보내는 홀 매니저입니다.

02왜 Prefill/Decode를 나누나

두 단계는 병목도, 좋아하는 설정도 다릅니다. 한 GPU에 두면 서로 양보해야 합니다.

관점PrefillDecode같은 GPU에 있을 때의 문제
병목 (2편)연산메모리 대역폭한쪽이 쓰는 동안 다른 쪽 자원이 놀거나, 서로 밀어냄
좋은 배치 크기토큰 수천 개를 한 번에요청 수십~수백 개를 함께한 스텝의 토큰 예산을 두고 경쟁 (4편 스케줄러)
좋은 병렬화작은 TP로 여러 레플리카 (처리량)큰 TP로 메모리 확보 (KV 공간·동시성)하나의 설정으로 둘 다 만족할 수 없음
좋은 GPU연산 강한 GPU대역폭·메모리 큰 GPU같은 GPU 종류로 고정
결정하는 지표TTFTITL·TPOT긴 Prefill이 끼어들면 진행 중 요청의 ITL 꼬리가 튐 (3편)

Chunked Prefill(2·4편)은 긴 Prefill을 잘게 쪼개 간섭을 줄이지만 없애지는 못합니다. P/D 분리는 Prefill과 Decode를 서로 다른 Pod(GPU)에 맡겨, Decode 전용 GPU에는 Prefill이 아예 끼어들지 않게 합니다. 대가는 Prefill이 만든 KV 캐시를 Decode GPU로 옮기는 전송 시간과 네트워크, 그리고 두 풀의 비율을 맞추는 운영 복잡도입니다.

P/D가 이기는 조건
  • 입력이 긴 요청이 많다 (RAG·문서 요약·에이전트)
  • ITL·TPOT의 꼬리(p99)에 엄격한 SLO가 있다
  • 대형 모델·대규모 트래픽으로 GPU가 여러 장 이상
  • 노드 간 고속 네트워크(RDMA)가 있다
P/D가 지는 조건
  • 입력이 짧다 (전송 비용이 Prefill 절약보다 큼)
  • 모델이 작고 트래픽이 적다 (GPU 한두 장)
  • 네트워크가 느리다 (일반 이더넷 TCP)
  • 운영 인력이 두 풀의 비율·장애를 관리할 여력이 없다
선택적 P/D

llm-d의 스케줄러에는 입력이 충분히 길 때만 P/D 경로를 쓰고, 짧은 요청은 Decode Pod 하나에서 Prefill까지 처리하게 하는 선택적 P/D 기능이 있습니다(기본은 꺼짐). 프롬프트가 짧아 “나눠서 전송하는 일”이 “한곳에서 다 하는 일”보다 비쌀 때를 피하는 장치입니다. 다음 장 계산기로 그 경계를 가늠해 보세요.

04KV 캐시 인지 라우팅

P/D 분리보다 먼저, 그리고 GPU가 두 장만 있어도 효과를 보는 것은 라우팅입니다.

vLLM의 프리픽스 캐시(4편)는 레플리카마다 따로 있습니다. 같은 시스템 프롬프트·같은 대화의 다음 턴이 지난번과 다른 레플리카로 가면 캐시는 쓸모가 없고 Prefill을 처음부터 다시 합니다. 일반 로드밸런서(라운드로빈)는 이를 모릅니다. llm-d Router의 Endpoint Picker(EPP)는 요청마다 후보 Pod에 점수를 매겨 고릅니다.

05KV 전송 계층: NIXL

P/D 분리의 성패는 Prefill GPU의 KV 블록을 Decode GPU로 얼마나 빨리, 얼마나 적은 CPU 개입으로 옮기느냐에 달렸습니다.

NIXL(NVIDIA Inference Xfer Library)은 GPU 메모리·CPU 메모리·스토리지 사이의 데이터 이동을 하나의 API로 추상화한 라이브러리입니다. 아래에서는 UCX 같은 전송 백엔드가 같은 노드면 NVLink·PCIe, 다른 노드면 RDMA(InfiniBand·RoCE)를, 안 되면 TCP를 고릅니다. vLLM은 이를 KV 커넥터(4편)의 하나인 NixlConnector로 씁니다. llm-d와 NVIDIA Dynamo 모두 NIXL을 씁니다.

P/D 요청 하나의 흐름 (llm-d 기준)

  1. 요청 도착 → llm-d RouterEPP가 P/D 프로파일에 따라 Decode Pod와 Prefill Pod를 고르고, 선택한 Prefill 대상 정보를 요청에 실어 Decode Pod로 보냅니다.
  2. Decode Pod의 사이드카Decode Pod 옆의 라우팅 사이드카가 먼저 Prefill Pod에 “Prefill만 하고 KV는 원격 Decode용으로 남겨 달라”는 요청을 보냅니다.
  3. Prefill Pod입력을 처리해 KV 블록을 만들고, 그 블록의 위치 정보(KV 전송 파라미터)를 응답으로 돌려줍니다.
  4. NIXL 전송Decode Pod의 vLLM이 그 정보로 Prefill Pod GPU 메모리의 KV 블록을 NIXL로 직접 읽어 옵니다(가능하면 RDMA, CPU를 거치지 않음).
  5. Decode받은 KV로 곧바로 토큰 생성을 이어 가고, 응답은 사이드카·Router를 거쳐 클라이언트로 스트리밍됩니다. Prefill Pod의 블록은 해제됩니다.

네트워크 요구 사항

환경전송 경로실효 대역폭 (대략)P/D 적합성
같은 노드, NVLinkGPU ↔ GPU 직접수백 GB/s매우 좋음 (8장 GPU 노드 안에서 P·D 분리)

P/D를 도입하려면 GPU 노드의 RDMA NIC, 스위치 구성(RoCE라면 무손실 설정), GPU와 NIC의 PCIe 정렬(8편 토폴로지), 쿠버네티스에서 RDMA 장치를 Pod에 주는 방법(SR-IOV·RDMA 장치 플러그인 또는 DRA)이 함께 준비되어야 합니다. 최근 llm-d 릴리스는 GB200·GB300용 P/D 구성에 DRA와 RDMA 레시피를 포함합니다. 인프라팀·네트워크팀과 함께 설계해야 하는 이유입니다.

NIXL 외에도 vLLM에는 여러 KV 커넥터가 있습니다(LMCache 연동, CPU 오프로딩, 다른 전송 방식 등). KV를 CPU·스토리지로 내리는 “계층형 프리픽스 캐시”는 15편에서 다룹니다.

07설치 구조와 배포 방식

하나의 거대한 차트가 아니라, Router 차트 + 모델 서버 오버레이 + (선택) 게이트웨이의 조합입니다.

층배포 방법내용
CRDkubectl apply -kGateway API, Gateway API Inference Extension CRD (llm-d 문서 기준 최소 버전 명시)
llm-d Router · standalone 모드Helm 차트InferencePool + EPP + EPP Pod 안의 프록시 사이드카(Envoy 기본). 쿠버네티스 Gateway 불필요. v0.7부터 기본 모드
llm-d Router · gateway 모드Helm 차트InferencePool + EPP를 기존 Gateway(Istio, AgentGateway, Envoy AI Gateway, GKE 등)에 붙이고 HTTPRoute 생성
모델 서버kustomize 오버레이 (레시피 + 경로별 오버레이)vLLM Deployment(통합 또는 Prefill·Decode), 노드 셀렉터·스토리지 등 환경별 패치
경로별 추가 구성 요소kustomize·HelmKV 인덱서, 오토스케일러, 배치 게이트웨이 등
  • 설치 방식의 변화: 예전의 Helmfile·infra·modelservice 차트는 사용 중단되었고, kustomize 우선으로 옮겨 가는 중입니다. 오래된 블로그의 설치 명령은 그대로 동작하지 않을 수 있습니다.
  • 게이트웨이 지원: llm-d 기능 표 기준으로 Istio가 기본, AgentGateway는 새 자체 설치에 권장, GKE Gateway 지원, kgateway는 사용 중단 예정입니다. 우리 랩의 Envoy Gateway는 목록에 없으므로 standalone 모드로 Router를 띄우고, 7편 Gateway의 HTTPRoute가 Router 서비스를 가리키게 합니다(실습).
  • 성숙도: 같은 기능 표에서 통합 서빙 최적화 기본 경로와 vLLM·CUDA P/D 분리는 “높음”, 정밀 프리픽스 라우팅·계층형 캐시·예측 지연 스케줄링은 “중간”, 전문가 병렬·WVA·SGLang P/D는 “실험” 단계로 표시됩니다.

09운영 관점

구성 요소가 늘면 장애 지점도 늘어납니다. 각각이 실패할 때 무슨 일이 생기는지 알아야 합니다.

장애·이상증상먼저 볼 것
EPP(Router) 장애모든 요청 실패 또는 무작위 분배로 후퇴Router 레플리카·실패 시 동작 정책(통과/차단), 11편
지표 수집 실패라우팅이 사실상 라운드로빈이 됨, 캐시 적중률 급락EPP가 모델 서버 지표를 읽는지, 엔진 지표 이름 변경(엔진 업그레이드 후)
KV 전송 실패·지연P/D 요청의 TTFT 급증, 타임아웃NIXL·UCX 로그, RDMA 장치 할당, 네트워크 오류 카운터
Prefill 풀 포화Decode는 한가한데 TTFT만 증가Prefill:Decode 비율, 입력 길이 분포 변화
Decode 풀 KV 포화선점 증가, ITL 꼬리Decode TP·메모리, 동시성 상한(4편)
버전 불일치P/D 전송 실패, 지표 해석 오류Router·사이드카·vLLM·NIXL 버전을 경로가 검증한 조합으로 고정
P:D 비율은 워크로드가 정한다

입력이 길고 출력이 짧으면 Prefill 풀이 더 많이, 입력이 짧고 출력이 길면 Decode 풀이 더 많이 필요합니다. 3장 계산기의 Prefill 시간과 출력 길이로 두 풀의 작업량 비율을 대략 잡고, 19편 방식으로 실측해 맞춥니다. 워크로드가 바뀌면 비율도 다시 맞춰야 하며, 이 조정을 자동화하는 것이 오토스케일러(18편)·Dynamo의 플래너 같은 구성 요소의 역할입니다.

실습 10-4 · 라우팅 결정 관찰

python · route_probe.py (50-tools/scripts에 추가)
"""세션별 공통 앞부분을 가진 요청을 보내고 지연을 기록한다. 같은 트래픽을 Router와 일반 Service에 각각 보내 비교.
사용: python route_probe.py --base http://<router-서비스>/v1 --label router"""
import argparse, random, statistics, time, json, urllib.request

ap = argparse.ArgumentParser()
ap.add_argument("--base", required=True); ap.add_argument("--label", required=True)
ap.add_argument("--model", default="qwen3-8b"); ap.add_argument("--rounds", type=int, default=10)
a = ap.parse_args()
WORDS = "노드 파드 쿼터 지연 처리량 메모리 대역폭 캐시 배치 스케줄러 게이트웨이 장애 알림 예산 토큰".split()
sessions = {s: " ".join(random.Random(s).choice(WORDS) for _ in range(800)) for s in "ABCDEF"}

def ask(prompt):
    body = json.dumps({"model": a.model, "max_tokens": 16,
                       "messages": [{"role": "user", "content": prompt}]}).encode()
    req = urllib.request.Request(a.base + "/chat/completions", body, {"Content-Type": "application/json"})
    t0 = time.perf_counter(); urllib.request.urlopen(req, timeout=60).read()
    return time.perf_counter() - t0

lat = {s: [] for s in sessions}
for r in range(a.rounds):
    for s in ("A", "A", "A", "B", "B", "C", "D", "E", "F"):   # A가 가장 활발한 세션
        lat[s].append(ask(f"[{s}] 공통 맥락: {sessions[s]}\n질문 {r}: 요약해 줘"))
for s, v in lat.items():
    print(f"{a.label} 세션 {s}: {len(v)}건, 중앙값 {statistics.median(v)*1000:.1f} ms, 첫 요청 {v[0]*1000:.1f} ms")
bash · 같은 트래픽을 두 경로로 보내고 Pod별 처리 건수 세기
kubectl cp route_probe.py llmsvc-lab/bench:/tmp/route_probe.py
ROUTER_SVC=<router 프록시 Service 이름>:<포트>        # 10-3에서 확인한 값

count(){  # 각 시뮬레이터 Pod의 요청 로그 줄 수 (패턴은 실제 로그 한 줄을 보고 맞추기)
  for p in $(kubectl -n llmsvc-lab get pods -l app=sim-qwen -o name); do
    echo "$p $(kubectl -n llmsvc-lab logs $p | grep -ciE 'chat/completions|request')"; done; }

kubectl -n llmsvc-lab rollout restart deploy/sim-qwen && kubectl -n llmsvc-lab rollout status deploy/sim-qwen
kubectl -n llmsvc-lab exec bench -- python /tmp/route_probe.py --base http://sim-qwen:8000/v1 --label service
count     # 일반 Service: 4개 Pod에 고르게 퍼짐

kubectl -n llmsvc-lab rollout restart deploy/sim-qwen && kubectl -n llmsvc-lab rollout status deploy/sim-qwen
kubectl -n llmsvc-lab exec bench -- python /tmp/route_probe.py --base http://$ROUTER_SVC/v1 --label router
count     # Router: 세션이 특정 Pod에 붙고, 가장 활발한 세션 A는 부하 점수 때문에 일부 분산되는지 확인

관찰 포인트: 시뮬레이터에는 실제 KV 캐시가 없으므로 지연 차이가 아니라 라우팅 결정을 봅니다. 같은 세션의 요청이 같은 Pod로 모이는지(근사 프리픽스 점수), 한 Pod에만 몰리지는 않는지(부하 점수)를 4장 시뮬레이터의 결과와 비교하세요. 더 정확히 보려면 EPP 로그의 상세 수준을 높여 요청별 선택 결과를 확인할 수 있습니다(설정 키는 차트 값 참고).

실습 10-5 · (선택) 실제 vLLM 두 개로 캐시 효과 측정

8편 실습 8-3의 타임 슬라이싱(GPU를 2개로 광고)을 켤 수 있다면, Qwen3-0.6B vLLM 레플리카 두 개를 띄워 InferencePool로 묶고 같은 측정을 합니다. 이번에는 캐시 적중이 실제 TTFT 차이로 나타납니다.

  • 랩 쿼터의 GPU를 일시적으로 2로 올립니다: kubectl -n llmsvc-lab patch resourcequota lab-quota --type merge -p '{"spec":{"hard":{"requests.nvidia.com/gpu":"2"}}}'
  • 7편 qwen3-0.6b 오버레이를 복사해 replicas: 2, gpu-memory-utilization: 0.12로 바꾼 오버레이를 만들고, Router values의 matchLabels를 app: llm-engine으로 바꿔 다시 설치합니다.
  • route_probe.py --model qwen3-0.6b --rounds 20을 Router와 llm-engine Service에 각각 실행해 세션별 “첫 요청 이후 중앙값”을 비교합니다. Router 쪽이 낮게 나온다면 같은 세션이 캐시를 가진 레플리카로 간 결과입니다.
  • 끝나면 쿼터를 1로, 타임 슬라이싱을 8편 절차로 되돌립니다. 두 엔진이 하나의 GB10을 나눠 쓰므로 절대 지연은 의미가 없고, 두 경로의 상대 차이만 봅니다.

15정리와 체크리스트

핵심 여섯 문장.

  1. P/D 분리는 간섭을 없애고 단계별 최적 설정을 허용한다. 대가는 KV 전송과 두 풀의 운영이다.
  2. 긴 입력·대형 모델·엄격한 ITL SLO·RDMA가 있을 때 이기고, 짧은 입력·작은 규모·느린 네트워크에서는 진다. 선택적 P/D가 그 경계를 다룬다.
  3. KV 캐시 인지 라우팅은 레플리카 두 개부터 효과가 있고, 캐시 점수와 부하 점수의 균형이 핵심이다.
  4. NIXL은 KV 전송을 추상화하고, 성능은 NVLink·RDMA·GPUDirect 같은 아래 경로가 정한다. P/D는 네트워크 프로젝트이기도 하다.
  5. llm-d = Router(프록시+EPP) + GAIE API + vLLM + 경로별 구성 요소. standalone 모드와 kustomize 우선 설치로 바뀌었다.
  6. 도입은 최적화 기본 경로부터, P/D·전문가 병렬은 조건이 맞을 때 잘 닦인 경로 그대로.
