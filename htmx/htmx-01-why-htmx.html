왜 HTMX인가: 하이퍼미디어와 SPA의 갈림길

React와 Vue로 따로 만들어진 웹사이트들을 하나로 묶기 전에, 먼저 질문 하나를 해결해야 합니다. 브라우저와 서버는 무엇을 주고받아야 하는가. JSON인가, HTML인가. 이번 편은 그 갈림길을 지도로 그리고, HTMX가 어느 자리에 서는지 정확히 짚습니다.

01

이번 편의 지도

이 시리즈는 "HTMX 문법 강의"가 아닙니다. 목표는 React 사이트와 Vue 사이트, 그리고 서버 렌더링 페이지가 섞여 있는 현실의 웹 자산을 하나의 사용자 경험으로 통합하는 것이고, HTMX는 그 통합의 접착제이자 공통 셸 역할을 맡습니다.

시작 시나리오

이 시리즈 전체에서 사용할 가상의 상황입니다. 클라우드 MSP 회사 한 곳에 웹 자산이 세 개 있습니다.

경영진의 요구는 단순합니다. "고객이 보기에 하나의 포털이었으면 좋겠다." 선택지는 세 가지쯤 떠오릅니다. 전부 React로 다시 만들기, 전부 Vue로 다시 만들기, 아니면 각자 잘하는 부분은 살리고 공통 부분만 가벼운 계층으로 묶기. 이 시리즈는 세 번째 길을 HTMX로 걷는 방법을 다룹니다. 그리고 1편은 그 길이 언제 맞고 언제 틀린지 판단하는 눈을 기르는 편입니다.

02

웹의 원래 언어, 하이퍼미디어

HTMX를 이해하는 가장 빠른 길은 HTMX를 잠시 잊고, 웹이 처음 만들어졌을 때 어떻게 동작했는지 떠올리는 것입니다.

여러분이 <a href="/vms">서버 목록</a> 링크를 누르면 브라우저는 GET /vms 요청을 보내고, 서버는 완성된 HTML 문서를 돌려주고, 브라우저는 화면 전체를 그 문서로 바꿉니다. 이 과정에서 브라우저는 "서버 목록"이 무엇인지 전혀 모릅니다. 그저 받은 HTML을 그리고, 그 HTML 안에 들어 있는 다음 링크와 폼을 사용자에게 보여 줄 뿐입니다.

이 구조를 하이퍼미디어 시스템이라고 부릅니다. 핵심은 응답 안에 데이터와 "다음에 할 수 있는 행동"이 함께 들어 있다는 점입니다. 링크(<a>)와 폼(<form>)처럼 사용자가 눌러서 다음 요청을 만들 수 있는 요소를 하이퍼미디어 컨트롤이라고 합니다.

HATEOAS를 한 문장으로

REST 아키텍처를 정의한 Roy Fielding은 이 성질에 긴 이름을 붙였습니다. HATEOAS, 즉 "하이퍼미디어가 애플리케이션 상태의 엔진이다". 풀어 말하면 "지금 무엇을 할 수 있는지는 서버가 응답으로 알려 준다"입니다.

예를 들어 서버가 중지 상태의 VM 행을 그릴 때는 "시작" 버튼을 넣고, 실행 중인 VM 행에는 "중지" 버튼을 넣습니다. 권한이 없는 사용자에게는 버튼 자체를 빼고 HTML을 만듭니다. 클라이언트는 상태 전이 규칙을 몰라도 됩니다. 규칙은 서버 한 곳에만 있습니다.

하이퍼미디어 응답 (HTML)
<tr>
  <td>db-02</td>
  <td>중지됨</td>
  <td><button hx-post="/vms/db-02/start">
        시작</button></td>
</tr>

다음 행동(시작)이 응답 안에 들어 있음. 클라이언트는 그냥 보여 주기만 하면 됨.

데이터 응답 (JSON)
{
  "name": "db-02",
  "status": "stopped"
}

"stopped면 시작 버튼을 보여 준다"는 규칙은 클라이언트 코드가 따로 알고 있어야 함. 규칙이 서버와 클라이언트 두 곳에 생김.

💡 JSON API는 REST가 아니라고?

Fielding의 원래 정의로 엄밀히 따지면, 응답에 다음 행동이 없는 순수 JSON API는 REST의 "하이퍼미디어 제약"을 만족하지 않습니다. 업계에서 "REST API"라고 부르는 것은 대부분 "HTTP 위의 JSON API"에 가깝습니다. 이 구분은 학술 논쟁이 아니라 실무적인 의미가 있습니다. 상태 전이 규칙이 어디에 사느냐가 코드 중복과 버그 위치를 결정하기 때문입니다.

03

HTML의 네 가지 족쇄, 그리고 HTMX

HTMX 제작자는 질문을 이렇게 던집니다. 하이퍼미디어 구조가 좋은데, 왜 사람들은 HTML을 버리고 JSON + JavaScript로 갔을까? 답은 순수 HTML이 가진 네 가지 제약 때문입니다.

각 카드를 눌러 HTMX가 그 족쇄를 어떻게 푸는지 확인해 보세요.

네 가지를 모두 풀면 무엇이 남을까요? 서버가 HTML을 만들고, 브라우저는 그것을 끼워 넣는 원래의 웹 구조가 그대로 남습니다. 다만 SPA 수준의 부드러운 상호작용이 붙어서요. HTMX가 스스로를 "새 프레임워크"가 아니라 "HTML의 확장"이라고 부르는 이유입니다.

htmx 4 메모

htmx 4에는 HTTP의 새 메서드인 QUERY를 위한 동사도 내부에 포함되어 있습니다(소스의 지원 동사 목록: get, post, put, patch, delete, query). QUERY는 "본문을 가진 안전한 조회"를 위해 IETF HTTP 작업 그룹이 정의한 새 메서드로, 서버 프레임워크·프록시·CDN의 지원이 아직 고르지 않으니 경로 전체에서 통과되는지 확인한 뒤 쓰는 것이 좋습니다. 시리즈에서는 다섯 가지 전통 메서드를 중심으로 다룹니다.

04

SPA의 등장과 그 비용

SPA가 틀린 선택이었다는 이야기가 아닙니다. SPA는 진짜 문제를 풀었고, 그 대가로 새로운 비용을 만들었습니다. 통합을 설계하려면 양쪽 장부를 모두 봐야 합니다.

SPA가 해결한 것

SPA는 페이지 전체를 다시 받지 않고 브라우저 안에서 화면을 다시 그립니다. 덕분에 드래그로 대시보드 위젯을 재배치하거나, 차트를 줌하거나, 수백 개의 셀이 서로 연동되는 편집기를 만드는 일이 가능해졌습니다. 오프라인에서도 동작할 수 있고, 같은 JSON API를 모바일 앱과 공유할 수도 있습니다.

SPA가 만든 비용

비용무슨 뜻인가통합 관점에서의 영향
상태의 이중화서버 DB에 진짜 상태가 있고, 브라우저 메모리(스토어)에 그 사본이 있음. 둘을 맞추는 코드(캐시 무효화, 낙관적 업데이트 롤백)가 필요React 앱과 Vue 앱이 각자 사본을 가지면 사본이 셋이 됨
규칙의 이중화"이 상태면 이 버튼"이라는 규칙과 권한 검사가 서버·클라이언트 양쪽에 존재권한 정책을 바꿀 때 수정할 곳이 늘어남
번들과 빌드 체인프레임워크 런타임 + 라우터 + 상태 라이브러리 + 앱 코드를 내려받고 실행해야 첫 화면이 상호작용 가능해짐. 빌드 도구·의존성 관리 필요사이트 두 개면 런타임도 두 벌, 빌드 파이프라인도 두 벌
하이드레이션 비용SEO와 첫 화면 속도를 위해 SSR을 붙이면, 브라우저가 같은 화면을 JS로 한 번 더 구성해야 함SSR 프레임워크(Next.js, Nuxt)가 사이트마다 다르면 운영 복잡도 상승
팀 분리백엔드는 JSON, 프론트엔드는 화면. 기능 하나에 두 팀이 협의해야 함통합 포털에서는 협의 대상 팀이 셋 이상으로 늘어남
공정하게 말하면

React와 Vue 진영도 이 비용을 줄이는 방향으로 계속 진화하고 있습니다. React Server Components와 서버 액션, Vue/Nuxt의 서버 컴포넌트와 아일랜드 기능, Astro의 아일랜드 아키텍처 등은 모두 "렌더링을 다시 서버로 가져오자"는 흐름입니다. HTMX는 이 흐름의 가장 단순한 극단에 서 있습니다. 새 렌더링 모델을 배우는 대신 이미 아는 서버 템플릿과 HTML 속성으로 해결한다는 점이 다릅니다. 대안 비교는 22편에서 정식으로 다룹니다.

용어 정리: MPA, SPA, SSR, CSR

      무엇을 관찰해야 하나
      
  
      
    
      해 볼 것사용된 속성관찰 포인트
      
    
      
      페이지 로드hx-trigger="load"표 본문(tbody)이 스스로 요청을 보내 내용을 채움. 초기 데이터 로드에 JS가 한 줄도 없음
      
      
      검색창 입력hx-trigger="input changed delay:300ms"타이핑을 멈추고 0.3초 뒤에 한 번만 요청. changed 때문에 값이 같으면 요청하지 않음. 요청 URL에 q= 값이 붙음
      
      
      검색 결과 건수<hx-partial> (htmx 4 신기능)응답 하나로 표 본문과 건수 배지 두 곳이 동시에 바뀜. 응답 본문 끝의 hx-partial 태그를 확인
      
      
      재시작hx-post + hx-swap="outerHTML"행 전체가 "재시작 중" 행으로 교체되고, 그 새 행이 1.5초 뒤 스스로 다시 요청해 "실행 중"으로 돌아옴. 상태 전이 규칙은 전부 서버에 있음
      
      
      삭제hx-delete + hx-confirm확인 창 → DELETE 요청 → 빈 응답으로 행이 사라짐. 응답 헤더 HX-Trigger가 이벤트를 일으켜 삭제 카운터가 증가
      
      
      404 요청hx-gethtmx 4는 4xx·5xx 응답도 기본으로 스왑하므로 서버가 보낸 오류 HTML이 그대로 보임. htmx 2였다면 아무것도 바뀌지 않음
      
          
  
      

  
      
    
      삭제 카운터에 숨은 함정 하나
      
    
      삭제 버튼은 응답이 스왑되는 순간 행과 함께 DOM에서 사라집니다. htmx 4는 HX-Trigger 이벤트를 기본적으로 요청을 보낸 요소(삭제 버튼)에서 발생시키는데, 이미 문서에서 떨어져 나간 요소의 이벤트는 위로 전파되지 않습니다. 그래서 모의 서버는 HX-Trigger: {"vmRemoved": {"name": "...", "target": "#vm-app"}}처럼 이벤트를 받을 요소를 직접 지정합니다. 이 패턴은 13편에서 React·Vue 아일랜드에 이벤트를 전달할 때 핵심이 됩니다.
      
  
      

  
      이 데모에 쓴 클라이언트 측 JavaScript는 삭제 카운터를 올리는 이벤트 리스너 몇 줄이 전부입니다. 검색, 지연 요청, 로딩 표시, 부분 교체, 확인 창, 자동 갱신은 모두 HTML 속성과 서버 응답으로 해결했습니다.

      요청과 응답에 실리는 것
      
  
      HTMX와 서버는 HTTP 헤더로 대화합니다. 아래 표는 htmx 4.0.1 소스 코드에서 직접 확인한 목록입니다. 각 헤더의 상세 사용법은 6편에서 다루고, 여기서는 "이런 대화가 오간다"는 감만 잡습니다.
      

  
      htmx가 보내는 요청 헤더
      
  
      
    
      헤더값 예시서버가 이걸로 할 수 있는 것
      
    
      
      HX-Requesttrue"htmx가 보낸 요청이다" 판별. 조각을 줄지 전체 페이지를 줄지 결정하는 기본 단서
      
      
      HX-Request-Typepartial / fullhtmx 4에서 새로 생김. 대상이 body 전체이거나 응답 일부를 골라 쓰는(select) 요청이면 full, 그 외엔 partial. 같은 URL에서 전체 페이지와 조각을 나눠 응답할 때 판단 근거
      
      
      HX-Sourcebutton#save요청을 일으킨 요소의 "태그#id". 같은 엔드포인트를 여러 버튼이 쓸 때 구분
      
      
      HX-Targettbody#vm-body응답이 들어갈 자리. 자리에 따라 다른 조각을 줄 수 있음
      
      
      HX-Current-URLhttps://…/vms?page=2사용자가 보고 있던 페이지 주소. 돌아갈 위치 계산 등에 사용
      
      
      Accepttext/htmlhtmx 4는 HTML을 원한다고 명시합니다(2.x는 */*). 콘텐츠 협상으로 같은 URL에서 JSON과 HTML을 나눠 줄 때 단서가 됨
      
      
      HX-Boostedtruehx-boost로 가로챈 일반 링크·폼 요청일 때만 붙음
      
      
      HX-History-Restore-Requesttrue뒤로 가기 복원을 위해 페이지를 다시 받는 요청일 때 붙음 (htmx 4는 localStorage 대신 재요청으로 복원)
      
          
  
      

  
      
    
      2.x에서 넘어오는 분께
      
    
      htmx 2에서는 요청을 일으킨 요소의 id가 HX-Trigger 요청 헤더로, name이 HX-Trigger-Name으로 왔습니다. htmx 4.0.1 소스의 핵심 요청 헤더 목록에는 이 둘 대신 HX-Source가 있습니다. 또 HX-Target 값의 형식도 2.x의 id만(out)에서 4.x의 "태그#id"(div#out)로 바뀌었습니다(두 버전으로 같은 페이지를 띄워 직접 확인한 결과). 서버 코드에서 요청 헤더 HX-Trigger를 읽고 있었다면 이전 시 함께 바꿔야 할 부분입니다. (응답 헤더 HX-Trigger는 그대로 있습니다.)
      
  
      

  
      서버가 돌려줄 수 있는 응답 헤더
      
  
      
    
      헤더하는 일대표 사용처
      
    
      
      HX-Trigger응답 처리 후 클라이언트에 이벤트를 발생시킴. JSON으로 이벤트 이름과 데이터, 받을 요소(target) 지정 가능저장 후 알림 토스트, 다른 영역 새로고침, React·Vue 아일랜드에 신호 보내기
      
      
      HX-Redirect브라우저 전체를 다른 주소로 이동세션 만료 시 로그인 페이지로
      
      
      HX-Location전체 새로고침 없이 htmx 방식으로 다른 주소를 불러와 이동생성 완료 후 상세 화면으로
      
      
      HX-Push-Url / HX-Replace-Url주소창 URL을 히스토리에 추가 / 교체필터 조건을 URL에 남겨 공유 가능하게
      
      
      HX-Refresh페이지 전체 새로고침배포 후 셸 버전이 바뀌었을 때
      
      
      HX-Retarget / HX-Reswap / HX-Reselect클라이언트가 지정한 대상·스왑 방식·선택 영역을 서버가 덮어씀폼 검증 실패 시 오류 영역에 대신 넣기
      
          
  
      

  
      기본값 세 가지만은 지금 외워 두기
      
  
      
    
      설정htmx 4.0.1 기본값의미
      
    
      
      defaultSwapinnerHTMLhx-swap을 안 쓰면 대상 요소의 안쪽을 교체. 요소 자체를 바꾸려면 outerHTML
      
      
      noSwap[204, 304]이 두 코드만 스왑하지 않음. 400·404·500 응답 본문은 스왑됨 (2.x와 가장 체감이 큰 차이)
      
      
      implicitInheritancefalse부모에 단 속성이 자식에게 자동 적용되지 않음. 물려주려면 hx-confirm:inherited처럼 명시
      
          
  
      
  
      참고로 요청 기본 타임아웃(defaultTimeout)은 60초이며, 요청 중인 요소와 인디케이터에는 htmx-request 클래스가 붙습니다. 위 데모의 "검색 중…" 표시가 바로 이 클래스로 보였다 사라집니다.

      공통 레이아웃·헤더·메뉴, 로그인 이후 흐름, 페이지 전환(hx-boost), 목록·상세·폼·설정 같은 CRUD 화면 전부. 사용자가 보는 "포털"의 뼈대
      
    
      React 아일랜드
      이미 잘 만들어진 실시간 메트릭 차트, 드래그로 배치하는 대시보드 위젯. 상태 변화가 잦고 상호의존이 큰 영역만
      
    
      Vue 아일랜드
      여러 단계에 걸친 설정 마법사, 입력값끼리 실시간으로 연동되는 복잡한 폼. 기존 Vue 자산을 그대로 재사용
      
    
      서버 / BFF
      라우팅, 인증·권한, 상태 전이 규칙, HTML 조각 렌더링. 아일랜드가 필요로 하는 JSON API(데이터 API)도 여기서 함께 제공
      
  
      

  
      단 하나의 철칙: DOM 소유권
      
  
      HTMX와 React·Vue를 함께 쓸 때 생기는 버그의 대부분은 한 가지 원칙을 어겨서 생깁니다. DOM의 한 영역에는 주인이 하나뿐이어야 한다.
      
  
      React와 Vue는 자기가 그린 DOM을 가상 DOM 사본과 비교하며 관리합니다. 그런데 HTMX가 그 영역 안의 HTML을 몰래 바꿔 버리면, 프레임워크가 기억하는 모습과 실제 화면이 어긋나 다음 렌더링에서 오류가 나거나 이벤트 핸들러가 사라집니다. 반대로 React가 HTMX가 채운 영역을 다시 그리면 htmx 속성이 붙은 요소가 처리되지 않은 채 남습니다.
      

  
      
    
      
      
      소유권 충돌 (하지 말 것)
      

      <div id="react-root">   ← React가 관리
  ...React가 그린 차트...
</div>

<button hx-get="/chart-legend"
        hx-target="#react-root">
  ← HTMX가 React 영역을 덮어씀 ✗
</button>
      
    
      
    
      
      
      경계 분리 (이렇게)
      

      <section id="panel">     ← HTMX가 관리
  <metric-chart vm="web-01">
    ← 이 태그 안쪽은 React 소유
  </metric-chart>
  <div id="legend">...</div>
</section>
HTMX는 #panel 전체나 #legend만 교체,
React 내부로는 절대 들어가지 않음 ✓
      
    
      
  
      
  
      오른쪽처럼 React 영역을 웹 컴포넌트 같은 경계 태그로 감싸면, HTMX가 바깥 영역을 통째로 교체할 때 태그가 문서에서 떨어지는 순간(disconnectedCallback) React 앱을 정리하고, 새 태그가 붙는 순간(connectedCallback) 다시 마운트할 수 있습니다. 이 기법은 12편에서 직접 구현합니다.

      A. HTMX 셸 + React·Vue 아일랜드

      B. React·Vue 앱 안에 HTMX 영역 넣기

      언제 고르나

      마운트 후 htmx 초기화, 언마운트 정리, React StrictMode의 이중 실행, 라우터와 히스토리 충돌

      언제 고르나
      SPA 유지 비용이 크지만 전면 재작성은 위험할 때
      
          
      핵심 과제
      옮길 화면 고르기, JSON API와 HTML 엔드포인트 병행 운영, 전환 효과 측정

      2.x냐 4.x냐: 무엇으로 시작할까
      
  
      2026년 11월 현재 htmx에는 "최신"이 두 개 있습니다. npm의 latest 태그는 2.0.11을, next 태그는 4.0.1을 가리킵니다. 이 상황을 정확히 이해하지 못하면 문서는 4를 보고 코드는 2를 설치하는 일이 생깁니다.
      

  
      왜 최신이 두 개인가
      
  
      htmx 팀은 4.0을 npm latest로 지정하지 않았습니다. 버전 번호 없이 CDN 주소를 걸어 둔 사이트들이 어느 날 갑자기 4로 강제 업그레이드되는 일을 막기 위해서입니다. 공식 발표에 따르면 2.x는 2027년 초 어느 시점까지 latest로 남고, 4.x는 그때까지 next로 유지됩니다. 반면 공식 웹사이트 문서는 이미 4.0 기준입니다. 그리고 htmx 2는 앞으로도 계속 지원된다고 명시되어 있습니다.
      

  
      설치 명령에 따라 받는 버전이 다르다 (2026-11 기준)
      

      # 버전을 지정하지 않으면 latest 태그 → 2.0.11
npm install htmx.org

# 4.x를 쓰려면 메이저 버전을 명시 → 4.0.1
npm install htmx.org@4

# CDN도 반드시 정확한 버전으로 고정
<script src="https://unpkg.com/htmx.org@4.0.1/dist/htmx.min.js"></script>
      

  
      
    
      운영 환경 수칙
      
    
      https://unpkg.com/htmx.org/dist/htmx.min.js처럼 버전이 없는 주소, @4처럼 범위로 끝나는 주소는 운영에서 쓰지 마세요. 2027년 초 latest가 4로 바뀌는 순간 동작이 달라질 수 있고, 새로 게시된 버전이 검증 없이 바로 들어옵니다. 정확한 버전 고정과 무결성 검증(SRI) 또는 자체 호스팅은 20편 운영 파트에서 다룹니다.
      
  
      

  
      2.x와 4.x의 차이 한눈에
      
  
      
    
      구분htmx 2.xhtmx 4.x
      
    
      
      내부 통신XMLHttpRequestfetch() (스트리밍 HTML 등 새 기능의 기반)
      
      
      속성 상속암묵적 (부모에 달면 자식에 자동 적용)명시적 (hx-confirm:inherited처럼 표시). hx-disinherit 등은 불필요
      
      
      이벤트 이름htmx:afterSwap 등 제각각htmx:after:swap처럼 htmx:단계:동작 규칙으로 통일. 오류는 대부분 htmx:error, HTTP 오류 응답은 htmx:response:error
      
      
      오류 응답 스왑4xx·5xx는 스왑 안 함204·304 외에는 모두 스왑
      
      
      히스토리localStorage에 화면 스냅샷 저장뒤로 가기 시 페이지를 다시 요청. 로컬 캐시가 필요하면 hx-history-cache 확장(sessionStorage)
      
      
      모핑 스왑idiomorph 확장 별도 설치기본 내장
      
      
      여러 곳 동시 갱신OOB 스왑 (hx-swap-oob)OOB 스왑 + 더 명확한 <hx-partial> 태그
      
      
      이름이 바뀐 속성hx-disable = htmx 처리 끄기처리 끄기는 hx-ignore로 이름 변경, hx-disable은 "요청 중 비활성화" 의미로 바뀜
      
      
      제거된 것hx-vars, hx-prompt, htmx.addClass() 등hx-vals의 js: 접두사, hx-prompt 확장, element.classList로 대체
      
      
      응답 헤더HX-Trigger-After-Swap, HX-Trigger-After-Settle 지원4.0.1 코어 소스에서는 처리하지 않음 (HX-Trigger만 처리)
      
          
  
      

  
      새로 생긴 확장과 도구
      
  
      htmx 4의 큰 변화 중 하나는 확장 생태계입니다. hx-preload(마우스를 올리면 미리 받아 두기), hx-download(fetch 기반 파일 다운로드), hx-alpine-compat(Alpine.js와의 호환), hx-history-cache, 스트리밍 HTML을 위한 hx-sse·hx-ws·hx-multipart, 그리고 htmx와 긴밀히 통합된 자체 스크립팅 도구 hx-live가 추가되었습니다. 이런 확장을 한 파일로 묶은 htmax.js 번들도 배포본에 포함됩니다. 배포본의 dist/ext/ 폴더에는 이전을 돕는 htmx-2-compat.js도 들어 있습니다.
      
  
      업그레이드 도구도 함께 나왔습니다. npx htmx.org@4 upgrade-check -- ./templates를 실행하면 상속 표시가 필요한 속성, 옛 이벤트 이름, 제거된 속성과 API를 찾아 줍니다(Python 3 필요). .vue, .svelte 파일은 --ext 옵션으로 검사 대상에 추가할 수 있다는 점이 통합 프로젝트에서 유용합니다. AI 코딩 도구를 위한 스킬 파일(htmx-guidance, htmx-debugging, htmx-extension-authoring, htmx-upgrade-from-htmx2)도 공식 배포됩니다.
      

  
      이 시리즈의 결정
      
  
      
    
      여러분의 상황권장이유
      
    
      
      새로 시작하는 통합 프로젝트4.x (정확한 버전 고정)공식 문서가 4 기준이고, 명시적 상속·통일된 이벤트·fetch 기반 확장이 React·Vue 통합(이벤트 브리지, 스트리밍)에 유리. 2027년 초 latest 전환 이후 다시 이전할 필요가 없음
      
      
      htmx 2.x로 잘 운영 중인 서비스2.x 유지 + 이전 준비2.x는 계속 지원됨. upgrade-check로 이전 범위만 미리 파악해 두고, 서두를 필요는 없음
      
      
      2.x 전용 서드파티 확장에 의존2.x 유지확장이 4로 이식되었는지 먼저 확인
      
          
  
      
  
      이 시리즈는 htmx 4.x를 기준으로 진행하며, 2.x와 동작이 다른 지점마다 "2.x와 다른 점" 박스를 둡니다. 4에서 2 방식으로 잠시 되돌리고 싶다면 htmx.config.implicitInheritance = true와 htmx.config.noSwap = [204, 304, '4xx', '5xx'] 두 설정이 이전 기간의 다리 역할을 합니다.

      1. 웹은 원래 HTML(하이퍼미디어)을 주고받는 구조였고, 응답 안에 "다음에 할 수 있는 행동"이 들어 있다는 점(HATEOAS)이 핵심이다.
        2. 
    
      2. HTMX는 HTML의 네 가지 제약(요청 요소, 트리거, 메서드, 교체 범위)을 풀어 SPA 수준의 상호작용을 서버 렌더링 구조 위에 얹는다.
        3. 
    
      3. 하이퍼미디어는 CRUD·텍스트 중심·블록 단위 갱신에 강하고, 상호의존이 큰 UI·오프라인·초고빈도 상태 변화에는 약하다. 그래서 통합의 질문은 "어느 화면을 누구에게 맡기나"다.
        4. 
    
      4. HTMX와 React·Vue를 함께 쓸 때의 철칙은 DOM 소유권 분리다. 통합 패턴은 A(셸+아일랜드), B(SPA 안의 HTMX), C(서버 측 조합), D(점진적 대체) 네 가지.
        5. 
    
      5. 2026년 11월 현재 npm latest는 htmx 2.0.11, next는 4.0.1이다. 이 시리즈는 정확한 버전을 고정한 4.x 기준으로 진행한다.
