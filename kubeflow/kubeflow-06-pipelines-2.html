2조건 분기

  
5편에서 파이프라인 함수 안의 일반 if는 동작하지 않는다고 했습니다. 컴파일 시점에는 정확도 값이 아직 없기 때문입니다. 조건은 실행 시점에 판단되도록 KFP 문법으로 씁니다.


@dsl.pipeline(name="digits-gate")
def pipeline(threshold: float = 0.95):
    data = load_data(test_size=0.2)
    t = train(n_estimators=200, train_data=data.outputs["train_data"])
    ev = evaluate(test_data=data.outputs["test_data"], model=t.outputs["model"])
    acc = ev.outputs["Output"]           # 반환값 출력의 이름은 Output

    with dsl.If(acc >= threshold, name="good-enough"):
        register_model(model=t.outputs["model"], accuracy=acc)
    with dsl.Elif(acc >= 0.90):
        request_review(accuracy=acc)        # 애매하면 사람이 검토
    with dsl.Else():
        report_low(accuracy=acc, threshold=threshold)

  
    
    
  • 조건에는 파이프라인 인자와 앞 작업의 출력 파라미터를 상수나 서로와 비교해 쓸 수 있습니다(==, !=, <, <=, >, >=). 아티팩트 내용은 조건에 직접 쓸 수 없으므로, 판단에 필요한 값은 5편처럼 반환값으로 내보냅니다.
    • 
    
  • evaluate는 Metrics 아티팩트와 반환값, 두 출력을 가지므로 .output이 아니라 .outputs["Output"]으로 반환값을 꺼냅니다.
    • 
    
  • 조건을 만족하지 않은 쪽의 작업은 실패가 아니라 건너뜀(Skipped)으로 표시됩니다.
    • 
    
  • 예전 자료의 dsl.Condition은 같은 기능의 옛 이름입니다. 새 코드는 dsl.If를 씁니다.
    • 
    
  • 여러 갈래 중 실제로 실행된 쪽의 출력을 하나로 받아 다음 단계에 넘기려면 dsl.OneOf를 씁니다.
    • 
  






  
3반복과 병렬

  
dsl.ParallelFor는 목록의 항목마다 안쪽 작업들을 복제해 실행합니다. 서로 의존하지 않으므로 동시에 돌아갑니다. 결과를 다시 하나로 모을 때는 dsl.Collected를 씁니다.


from typing import List, NamedTuple

@dsl.component(base_image="python:3.11")
def select_best(models: Input[List[Model]], scores: List[float],
                best_model: Output[Model]) -> NamedTuple("Best", [("best_acc", float)]):
    import shutil
    i = max(range(len(scores)), key=lambda k: scores[k])
    shutil.copy(models[i].path, best_model.path)
    return (scores[i],)

@dsl.pipeline(name="digits-sweep")
def pipeline(candidates: List[int] = [100, 200, 400]):
    data = load_data(test_size=0.2)
    with dsl.ParallelFor(items=candidates, parallelism=2) as n:     # 동시에 최대 2개
        t = train(n_estimators=n, train_data=data.outputs["train_data"])
        ev = evaluate(test_data=data.outputs["test_data"], model=t.outputs["model"])
    best = select_best(models=dsl.Collected(t.outputs["model"]),        # 반복 밖에서 모으기
                       scores=dsl.Collected(ev.outputs["Output"]))

  
    
    
  • items에는 고정 목록, 파이프라인 인자(목록 타입), 앞 작업이 내놓은 목록을 쓸 수 있습니다. 딕셔너리 목록이면 n.lr처럼 키로 꺼냅니다.
    • 
    
  • parallelism을 정하지 않으면 모든 항목이 한꺼번에 시작됩니다. 항목이 50개이고 각각 GPU를 1장씩 요청하면, GPU 50장을 한꺼번에 요구하게 됩니다.
    • 
    
  • dsl.Collected는 반복 블록 바깥에서만 씁니다. 모인 순서는 항목 순서와 같다고 가정하지 말고, 필요하면 항목 값을 함께 출력해 짝을 맞춥니다.
    • 
  

  
parallelism이 실행 시간과 자원 요구를 어떻게 바꾸는지 보세요. 항목마다 걸리는 시간이 같다고 단순화했습니다.

  

    

      

      

      

      

    

    

    

  

  

    병렬은 할당량과 함께 생각하세요
    
parallelism을 크게 잡아도 프로필 할당량이나 클러스터의 빈 GPU보다 많이 요청하면, 넘치는 Pod는 Pending으로 기다립니다. 실행은 결국 끝나지만 다른 팀의 작업까지 막을 수 있습니다. 팀 단위 GPU 공유를 큐로 관리하는 방법은 11편에서 다룹니다.

  





  
4실패 다루기

  
재시도: 일시적인 실패만

  
스팟 노드 회수, 잠깐의 네트워크 끊김, 외부 API의 일시적 오류처럼 다시 하면 성공할 실패에는 재시도를 겁니다.


t = train(n_estimators=200, train_data=data.outputs["train_data"])
t.set_retry(num_retries=2,                # 최대 2번 더
            backoff_duration="30s",       # 첫 재시도 전 대기
            backoff_factor=2.0,            # 대기 시간을 매번 2배로
            backoff_max_duration="10m")

  

    
실패의 종류재시도가 맞나이유

    
      
노드 회수, 네트워크 순단맞음같은 일을 다시 하면 성공합니다

      
코드 버그, 잘못된 입력아님몇 번을 해도 같은 결과이고 GPU 시간만 버립니다

      
OOMKilled대개 아님같은 메모리로는 또 죽습니다. 자원을 늘려야 합니다

      
몇 시간짜리 학습의 중간 실패체크포인트가 있을 때만체크포인트가 없으면 처음부터 다시 합니다(2편 4장)

    
  

  

    재시도해도 안전한 단계로 만드세요
    
재시도는 같은 단계를 처음부터 다시 실행합니다. 단계가 외부 DB에 행을 추가하거나 메시지를 보내는 일을 한다면, 두 번 실행되어도 결과가 같도록(멱등하게) 만들어야 합니다. 예를 들어 “추가”보다 “같은 키로 덮어쓰기”가 안전합니다.

  


  
ExitHandler: 무슨 일이 있어도 실행

  
dsl.ExitHandler로 감싼 작업들이 성공하든 실패하든, 블록이 끝나면 지정한 작업이 반드시 실행됩니다. 알림, 임시 자원 정리, 실행 결과 기록에 씁니다.


@dsl.pipeline(name="digits-production")
def pipeline(threshold: float = 0.95):
    done = notify(channel="#reco-ml")               # 블록 밖에서 먼저 만든다
    with dsl.ExitHandler(exit_task=done):
        data = load_data(test_size=0.2)
        ...                                           # 여기서 무엇이 실패해도 done은 실행됨

  
종료 작업 안에서 파이프라인이 성공했는지 실패했는지를 알고 싶다면, 함수 인자에 dsl.PipelineTaskFinalStatus 타입을 선언해 상태와 오류 메시지를 받을 수 있습니다. 실행 환경과 버전에 따라 지원 범위가 다를 수 있으니 처음 쓸 때 시험해 보세요.






  
5단계별 자원과 Kubernetes 설정

  
단계마다 필요한 자원이 다릅니다. 데이터 준비는 CPU와 메모리, 학습은 GPU, 평가는 가볍습니다. KFP 작업의 메서드와 kfp-kubernetes 확장으로 단계별 Pod 설정을 지정합니다. 2편 8장에서 읽은 Job YAML의 필드들이 여기서 Python 한 줄씩이 됩니다.


from kfp import kubernetes            # pip install kfp-kubernetes

t = train(n_estimators=200, train_data=data.outputs["train_data"])
t.set_cpu_request("4").set_memory_request("16G").set_memory_limit("16G")
t.set_accelerator_type("nvidia.com/gpu").set_accelerator_limit(1)
t.set_env_variable("OMP_NUM_THREADS", "4")

kubernetes.add_node_selector(t, label_key="nvidia.com/gpu.present", label_value="true")
kubernetes.add_toleration(t, key="nvidia.com/gpu", operator="Exists", effect="NoSchedule")
kubernetes.use_secret_as_env(t, secret_name="s3-credentials",
    secret_key_to_env={"AWS_ACCESS_KEY_ID": "AWS_ACCESS_KEY_ID",
                       "AWS_SECRET_ACCESS_KEY": "AWS_SECRET_ACCESS_KEY"})
kubernetes.mount_pvc(t, pvc_name="reco-ckpt", mount_path="/ckpt")

set_cpu_limit, set_memory_limitresources.limits넘으면 스로틀링, OOMKilled

      
set_accelerator_type, set_accelerator_limitlimits의 nvidia.com/gpuGPU 장수

      
set_env_variableenv환경 변수

      
kubernetes.add_node_selectornodeSelectorGPU 노드 고르기

      
kubernetes.add_tolerationtolerationsGPU 노드의 taint 통과

      
kubernetes.use_secret_as_envenv의 secretKeyRef비밀 값 주입

      
kubernetes.mount_pvcvolumes와 volumeMounts체크포인트용 PVC

    파이프라인 안에서 PVC를 만들고 지우기
    
kfp-kubernetes에는 실행 중에 PVC를 만들고 지우는 kubernetes.CreatePVC, kubernetes.DeletePVC 컴포넌트도 있습니다. 단계 사이에 아티팩트로 옮기기에는 너무 큰 데이터를 여러 단계가 같은 볼륨으로 공유할 때 씁니다. 다만 이렇게 공유한 파일은 아티팩트처럼 계보가 남지 않습니다.

  






  
6재사용 가능한 컴포넌트

  
평가 단계를 팀마다 따로 만들면 기준도 제각각이 됩니다. 컴포넌트는 YAML로 컴파일해 공유할 수 있고, 다른 파이프라인에서 불러와 그대로 씁니다.


# 만드는 팀: 컴포넌트 하나를 YAML로
compiler.Compiler().compile(evaluate, "components/evaluate/v1.2.0.yaml")

# 쓰는 팀: 파일이나 URL에서 불러오기
from kfp import components
evaluate = components.load_component_from_file("components/evaluate/v1.2.0.yaml")
# components.load_component_from_url("https://git.example.com/.../v1.2.0.yaml")

  
파이프라인을 컴포넌트처럼

  
파이프라인 함수도 다른 파이프라인 안에서 컴포넌트처럼 호출할 수 있습니다. 데이터 검증 묶음, 평가 묶음처럼 여러 단계로 된 덩어리를 하나로 재사용할 때 좋습니다.


@dsl.pipeline
def validate_data(raw: Input[Dataset]) -> Dataset:
    s = check_schema(raw=raw)
    d = check_drift(raw=raw).after(s)
    return d.outputs["clean"]

@dsl.pipeline(name="digits-production")
def pipeline():
    raw = fetch_raw()
    clean = validate_data(raw=raw.output)        # 하위 파이프라인 호출
    ...

  

    
팀 컴포넌트 라이브러리 원칙이유

    
      
컴포넌트 YAML과 이미지 태그에 같은 버전을 붙인다캐시와 재현은 컴포넌트 정의 기준이므로, 버전이 곧 결과의 신분증

      
한 번 낸 버전은 고치지 않고 새 버전을 낸다그 버전을 쓰던 파이프라인의 결과가 몰래 바뀌지 않게

      
입출력 이름과 타입을 계약처럼 문서화한다쓰는 팀은 YAML의 입출력 정의만 보고 연결함

      
Git과 CI에서 컴파일하고 시험한다사람 PC마다 다른 SDK 버전으로 컴파일한 결과가 섞이지 않게

    
  

  
작업 순서를 데이터 연결 없이 정해야 할 때는 위의 .after()처럼 명시합니다. 실행 화면에서 보이는 단계 이름은 set_display_name("...")으로 바꿀 수 있습니다.






  
7예약 실행

  
반복 실행(Recurring Run)은 정해진 일정마다 실행을 만들어 냅니다. 1편에서 말한 지속적 학습(CT)의 가장 단순한 형태입니다. 대시보드의 Recurring Runs 화면이나 SDK로 만듭니다.

  
exp = client.create_experiment("digits-prod", namespace="kubeflow-user-example-com")
client.create_recurring_run(
    experiment_id=exp.experiment_id,
    job_name="digits-nightly",
    cron_expression="0 0 2 * * *",          # 초 분 시 일 월 요일
    pipeline_package_path="digits_production.yaml",
    params={"threshold": 0.95},
    max_concurrency=1,                       # 이전 실행이 안 끝났으면 겹치지 않게
    no_catchup=True,                         # 멈췄다 재개해도 밀린 실행을 몰아서 하지 않음
)

  
KFP의 cron 식은 맨 앞에 초가 붙은 여섯 자리입니다. 리눅스 crontab의 다섯 자리에 익숙하면 가장 많이 틀리는 부분입니다. 식을 고르거나 직접 입력해 보세요.

  

    

    
    

    

  

  
    
    
  • 시간대: 예약 시각이 어느 시간대로 해석되는지는 설치 설정에 따라 다릅니다. 많은 환경이 UTC로 동작하므로, 한국 시간 새벽 2시를 원하면 UTC 17시인지 확인하세요.
    • 
    
  • max_concurrency: 학습이 하루보다 오래 걸리는 날, 다음 실행이 겹쳐 자원을 두 배로 쓰는 일을 막습니다.
    • 
    
  • 파이프라인 버전 고정: 반복 실행은 만들 때 지정한 파이프라인 버전으로 계속 돕니다. 코드를 고쳤다면 새 버전으로 반복 실행을 다시 만들거나 갱신해야 합니다.
    • 
    
  • 데이터가 들어왔을 때 시작하는 이벤트 기반 실행은 반복 실행만으로는 안 되고, 외부 도구(예: Argo Events, 사내 스케줄러)가 API로 실행을 만들게 구성합니다.
