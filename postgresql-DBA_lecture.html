-- 01 · architecture

프로세스 · 메모리 아키텍처

PostgreSQL은 멀티 프로세스 모델입니다(스레드가 아닙니다). 접속 하나당 백엔드 프로세스 하나가 fork되고, 이들이 공유 메모리를 통해 협력합니다. 이 구조를 이해하면 "왜 연결 풀러가 필수인가", "왜 shared_buffers를 무한정 늘리면 안 되는가"가 자연히 설명됩니다.

demo 01

아키텍처 맵 — 구성 요소를 클릭하면 역할과 관련 파라미터가 나옵니다

구성 요소를 클릭해 역할과 관련 파라미터를 확인하세요.

읽기와 쓰기가 흐르는 경로

  1. 접속 — 클라이언트가 5432로 접속하면 postmaster가 인증(pg_hba.conf) 후 backend 프로세스를 fork합니다. fork는 비싸므로(수 ms + 메모리) 짧은 접속이 많은 서비스에서는 pgbouncer 같은 풀러가 사실상 필수입니다.
  2. 조회 — 백엔드가 필요한 8kB 블록을 shared_buffers에서 찾습니다. 있으면 hit, 없으면 OS 캐시/디스크에서 읽어 올립니다.
  3. 변경 — 메모리상의 페이지를 수정하고(더티 페이지) 변경 내역을 WAL 레코드로 먼저 기록합니다.
  4. 커밋 — WAL을 디스크에 fsync합니다. 이 순간 지속성이 확보됩니다. 데이터 파일은 아직 옛 상태여도 무관합니다.
  5. 체크포인트 — checkpointer가 더티 페이지를 데이터 파일에 반영하고, 그 지점 이전 WAL은 재사용 가능해집니다.
핵심 원리 — WAL 우선 기록

Write-Ahead Logging: 데이터 파일을 바꾸기 전에 "무엇을 바꿀 것인지"를 WAL에 먼저 씁니다. 데이터 파일에 대한 랜덤 쓰기를 뒤로 미루고 순차 쓰기 하나만 기다리면 되므로 성능과 안정성을 동시에 얻습니다. 크래시 후 재시작하면 마지막 체크포인트부터 WAL을 재생(REDO)해 일관된 상태로 복구합니다. 백업·복제·PITR이 모두 이 하나의 메커니즘에서 파생됩니다.

SELECT name, setting, unit, source, pending_restart
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','maintenance_work_mem','wal_buffers',
               'effective_cache_size','max_connections','temp_buffers','huge_pages')
ORDER BY name;

-- 실제 shared_buffers 내용 살펴보기 (pg_buffercache 확장)
CREATE EXTENSION IF NOT EXISTS pg_buffercache;
SELECT c.relname,
       count(*) AS buffers,
       pg_size_pretty(count(*) * 8192) AS size,
       round(100.0 * count(*) FILTER (WHERE b.isdirty) / count(*), 1) AS dirty_pct
FROM pg_buffercache b
JOIN pg_class c ON c.relfilenode = b.relfilenode
GROUP BY c.relname ORDER BY buffers DESC LIMIT 15;


-- 버퍼 캐시 적중률: OLTP는 99% 이상이 정상, 90% 미만이면 원인 조사
SELECT datname,
       blks_hit, blks_read,
       round(100.0 * blks_hit / NULLIF(blks_hit + blks_read, 0), 2) AS cache_hit_pct
FROM pg_stat_database
WHERE datname = current_database();

-- 테이블별 적중률과 순차 스캔 비율
SELECT relname,
       heap_blks_hit, heap_blks_read,
       round(100.0*heap_blks_hit/NULLIF(heap_blks_hit+heap_blks_read,0),1) AS hit_pct,
       seq_scan, idx_scan
FROM pg_statio_user_tables s
JOIN pg_stat_user_tables u USING (relid)
ORDER BY heap_blks_read DESC LIMIT 15;

-- 주의: blks_read는 'shared_buffers에 없었다'는 뜻이며,
--       OS 페이지 캐시에서 읽혔을 수 있으므로 실제 디스크 I/O와 동일하지 않습니다.
PostgreSQL 17에서는 I/O 통계가 pg_stat_io로 통합되어 read/write/extend를 컨텍스트별로 구분해 볼 수 있습니다.

TOAST — 큰 값의 저장

한 행은 8kB 페이지를 넘을 수 없습니다. 약 2kB를 넘는 값은 자동으로 압축되고, 그래도 크면 TOAST 테이블(pg_toast.pg_toast_<oid>)에 조각으로 분리 저장됩니다. 그래서 pg_relation_size(본체)와 pg_total_relation_size(TOAST·인덱스 포함)의 값이 크게 다를 수 있습니다. 큰 jsonb·text를 다루는 테이블에서 "테이블 크기가 안 맞다"는 혼란은 대부분 TOAST 때문입니다.

-- 02 · mvcc

MVCC와 튜플 가시성

PostgreSQL 운영 난이도의 거의 모든 것이 이 장에서 출발합니다. UPDATE가 왜 새 행을 만드는지, 왜 삭제해도 용량이 줄지 않는지, 왜 VACUUM이 필요한지, 왜 XID가 소진될 수 있는지가 하나의 원리로 연결됩니다.

모든 행에는 숨은 시스템 컬럼이 있습니다

컬럼뜻가시성 판단에서의 역할
xmin이 행 버전을 만든 트랜잭션 ID내 스냅샷보다 나중에 시작한 트랜잭션이 만든 것은 보이지 않습니다.
xmax이 행 버전을 삭제/갱신한 트랜잭션 ID (0이면 유효)xmax가 커밋되었고 내 스냅샷 이전이면 그 행은 보이지 않습니다.
ctid물리적 위치 (블록번호, 오프셋)UPDATE되면 새 위치로 바뀝니다. 안정적 식별자가 아닙니다.
cmin / cmax트랜잭션 내부 명령 순번같은 트랜잭션 안에서의 순서를 구분합니다.
tableoid이 행이 실제로 속한 테이블 OID파티션 테이블 조회 시 어느 파티션인지 확인할 때 유용합니다.

-- 오래 열린 트랜잭션이 VACUUM을 막습니다. 가장 흔한 bloat 원인입니다.
SELECT pid, state, wait_event_type, wait_event,
       now()-xact_start AS xact_age,
       now()-state_change AS idle_for,
       left(query, 70) AS query
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 10;

-- 이 값들이 곧 VACUUM의 '지울 수 있는 한계선'입니다
SELECT min(age(backend_xmin)) AS oldest_backend_xmin_age FROM pg_stat_activity;
SELECT slot_name, active, age(xmin) AS slot_xmin_age,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained
FROM pg_replication_slots;


/* HOT (Heap Only Tuple) 업데이트
   조건: 인덱스에 포함된 컬럼을 바꾸지 않고, 같은 페이지에 빈 공간이 있을 때
   효과: 새 버전을 같은 페이지에 만들고 인덱스는 갱신하지 않음
         → 인덱스 bloat 방지, 쓰기 비용 대폭 감소                          */

SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0*n_tup_hot_upd/NULLIF(n_tup_upd,0),1) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY n_tup_upd DESC LIMIT 10;

-- hot_pct가 낮다면:
--   1) 자주 갱신되는 컬럼에 걸린 불필요한 인덱스를 제거
--   2) fillfactor를 낮춰 같은 페이지에 여유 공간 확보
ALTER TABLE t SET (fillfactor = 85);
VACUUM FULL t;      -- 또는 pg_repack (fillfactor는 재작성 시 적용)
자주 UPDATE되는 테이블에서 HOT 비율은 가장 저평가된 튜닝 지표입니다. 불필요한 인덱스 하나를 지우는 것만으로 쓰기 성능이 눈에 띄게 개선되는 경우가 많습니다.
DBA가 기억할 결론

1) UPDATE는 제자리 수정이 아니라 새 버전 추가 + 옛 버전 무효화입니다. 2) DELETE는 표시만 하고 공간은 남습니다. 3) 옛 버전을 회수하는 것은 VACUUM이며, 가장 오래된 열린 트랜잭션보다 최근의 것은 회수할 수 없습니다. 4) 따라서 idle in transaction 세션 하나가 수백 GB의 bloat를 만들 수 있습니다.

-- 04 · wal & checkpoint

WAL · 체크포인트 · 아카이브

WAL은 PostgreSQL의 심장입니다. 크래시 복구, 복제, PITR, 논리적 CDC가 모두 하나의 WAL 스트림에서 나옵니다. LSN·타임라인·세그먼트라는 세 용어를 정확히 쓸 수 있어야 복구 작업을 안전하게 지휘할 수 있습니다.

lsn
Log Sequence Number
0/16B3A48 형식의 WAL 스트림 내 바이트 위치입니다. 복제 지연·복구 목표를 표현하는 기준 좌표입니다.
segment
WAL 세그먼트 파일
기본 16MB 파일 하나. 파일명 24자리는 타임라인(8) + 논리 파일(8) + 세그먼트(8)입니다.
timeline
타임라인 ID
복구나 승격이 일어나면 1 증가합니다. 서로 다른 타임라인의 WAL을 섞으면 복구가 실패합니다.

# ── 무엇을 기록할지 ──
wal_level = replica            # minimal | replica(기본) | logical
                               #   replica : 물리 복제·PITR 가능
                               #   logical : 논리 복제·CDC(Debezium) 추가 가능
fsync = on                     # 절대 off 하지 마십시오 (크래시 시 데이터 손상)
synchronous_commit = on        # 커밋 시 WAL fsync 완료까지 대기
full_page_writes = on          # 페이지 부분 쓰기(torn page) 방어

# ── 얼마나 쌓을지 ──
max_wal_size = 8GB             # 체크포인트 간 WAL 총량 상한(소프트)
min_wal_size = 2GB             # 이만큼은 파일을 재활용해 유지
wal_compression = zstd         # PG15+ 알고리즘 선택 가능. full page 이미지 압축
wal_buffers = 16MB             # -1이면 shared_buffers의 1/32 자동

# ── 언제 flush할지 ──
checkpoint_timeout = 15min     # 기본 5min → 늘리면 WAL 증가, 복구 시간 증가
checkpoint_completion_target = 0.9   # PG14+ 기본값. flush를 구간에 고르게 분산
checkpoint_warning = 30s

# ── 보관 (복제 슬롯이 있으면 슬롯이 우선) ──
wal_keep_size = 2GB            # 슬롯 없이 표준 복제를 유지할 최소 보관량
archive_mode = on
archive_timeout = 60s          # 조용한 시스템에서도 강제 세그먼트 전환(RPO 상한)

       round(100.0*num_requested/NULLIF(num_timed+num_requested,0),1) AS requested_pct,

-- 05 · backup & pitr

백업과 복구 · PITR

백업의 성공 기준은 "백업이 돌았는가"가 아니라 "복구가 되는가"입니다. 복구 훈련을 하지 않은 백업은 백업이 아닙니다. 먼저 목표를 숫자로 정의하고, 그 목표를 만족하는 방식을 고릅니다.

RPO — 얼마까지 잃어도 되는가

Recovery Point Objective. "최대 5분 손실 허용"이면 WAL 아카이브 주기(archive_timeout)와 복제 방식이 그 수치를 결정합니다. 하루 한 번 pg_dump만 있다면 RPO는 최대 24시간입니다.

RTO — 얼마 안에 살려야 하는가

Recovery Time Objective. 1TB DB를 논리 백업에서 복원하면 인덱스 재생성까지 수 시간이 걸립니다. RTO가 30분이면 물리 백업 + 대기 서버(standby)가 필요합니다.

방식단위RPORTO적합한 상황
pg_dump / pg_restoreDB·테이블 논리백업 시점느림(재적재+인덱스)버전·플랫폼 이전, 특정 테이블 복원, 소규모 DB
pg_basebackup클러스터 물리백업 시점(WAL 있으면 개선)중간(파일 복사)standby 구축, 단순 물리 백업
basebackup + WAL 아카이브 (PITR)클러스터 물리초 단위중간운영 표준. 원하는 시점으로 복구
pgBackRest / barman클러스터 물리초 단위빠름(병렬·증분)대용량 운영 환경 권장
스트리밍 복제 standby클러스터≈0(동기 시)수십 초(승격)HA. 백업의 대체물이 아닙니다
스토리지 스냅샷볼륨스냅샷 시점매우 빠름PGDATA와 WAL이 같은 정합 그룹일 때만 유효
복제는 백업이 아닙니다

DROP TABLE orders;는 0.2초 뒤에 복제 서버에서도 실행됩니다. 실수·악의·논리적 손상으로부터 보호하려면 시간을 되돌릴 수 있는 백업(PITR)이 별도로 있어야 합니다. 지연 복제(recovery_min_apply_delay)를 1시간 걸어 두면 사고 직후 대응 창을 확보할 수 있습니다.

-- 06 · replication & ha

복제와 고가용성

PostgreSQL은 복제를 내장하지만 자동 페일오버는 내장하지 않습니다. 이 사실이 아키텍처 설계의 출발점입니다. 물리 복제(스트리밍)와 논리 복제는 목적이 다르므로 구분해서 이해해야 합니다.

물리 복제 (스트리밍)

WAL 바이트를 그대로 전송해 클러스터 전체를 블록 단위로 동일하게 유지합니다. 대기 서버는 읽기 전용(hot standby)으로 조회를 받을 수 있습니다. 같은 메이저 버전·같은 아키텍처가 필수이며, 테이블 단위 선택은 불가능합니다. HA와 읽기 확장의 기본입니다.

논리 복제

변경을 행 단위 논리 이벤트로 디코딩해 전송합니다. 테이블 단위 선택, 다른 메이저 버전 간, 양방향·부분 복제가 가능합니다. 무중단 메이저 업그레이드와 CDC 파이프라인의 기반입니다. 대신 DDL은 자동 전파되지 않고, 대상 테이블에 REPLICA IDENTITY가 필요합니다.

파티셔닝

파티셔닝의 진짜 이득은 조회 성능보다 운영 편의성입니다. 3년 지난 로그를 DELETE로 지우면 수 시간의 I/O와 거대한 bloat가 남지만, DETACH + DROP은 초 단위로 끝나고 bloat도 없습니다. VACUUM·인덱스 재생성도 파티션 단위로 나뉘어 관리 가능한 크기가 됩니다.

방식기준주 용도주의
RANGE범위 (날짜·숫자)시계열 로그·주문·이벤트. 가장 흔합니다.미래 파티션을 미리 만들어야 합니다. 없으면 INSERT 실패
LIST값 목록 (지역·테넌트)멀티테넌시, 국가별 분리DEFAULT 파티션을 두면 새 값도 받지만 ATTACH 시 검사 비용 발생
HASH해시 나머지균등 분산으로 경합 완화범위 조회에서 pruning 효과가 없습니다
 

-- 월별 RANGE 파티션. 파티션 키는 PK에 반드시 포함되어야 합니다.
CREATE TABLE events (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  tenant_id  int         NOT NULL,
  payload    jsonb       NOT NULL,
  created_at timestamptz NOT NULL,
  PRIMARY KEY (id, created_at)          -- created_at 없이 PK(id) 불가
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_08 PARTITION OF events
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE TABLE events_2026_09 PARTITION OF events
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

CREATE INDEX ON events (tenant_id, created_at DESC);

인덱스 심화

DBA의 인덱스 업무는 "만들기"보다 고르기와 정리하기입니다. 데이터 타입과 연산자에 맞는 인덱스 종류를 고르고, 쓰이지 않는 인덱스를 걷어내고, 무중단으로 재생성하는 절차를 갖추는 것이 핵심입니다.

인덱스 종류 선택기 — 데이터와 조건을 고르면 적합한 종류를 제안합니다

종류지원 연산전형적 용도특징
B-tree= < <= > >= BETWEEN IN, LIKE '접두%', ORDER BY기본값. 대부분의 컬럼정렬 지원, Index Only Scan 가능, 크기 중간
Hash= 만등호 전용 대용량 키PG10부터 WAL 기록됨(크래시 안전). B-tree보다 작을 수 있으나 이득이 제한적
GIN@> ? && @@ (포함·존재)jsonb, 배열, 전문 검색(tsvector), pg_trgm다중 값 색인. 삽입 비용 큼 → fastupdate와 gin_pending_list_limit 조정
GiST&& @> <-> (겹침·근접)지리정보(PostGIS), 범위 타입, EXCLUDE 제약, KNN 검색손실 압축 기반이라 재검사가 필요할 수 있음
SP-GiST공간 분할형IP 접두사, 텍스트 접두사, 비겹침 데이터특정 패턴에서 GiST보다 작고 빠름
BRIN범위 조건물리 순서와 값 순서가 일치하는 초대형 테이블(시계열 append-only)인덱스 크기가 극단적으로 작음(GB → MB). 정확도는 낮지만 대용량 스캔 축소에 효과적
HNSW / IVFFlat<=> <-> (벡터 거리)pgvector 임베딩 유사도 검색HNSW는 정확도·속도 우수, 빌드 시간과 메모리 요구 큼
 

-- ① 커버링 인덱스 (INCLUDE, PG11+): 키가 아닌 컬럼을 리프에 담아 Index Only Scan 유도
CREATE INDEX idx_ord_cover ON orders (customer_id, ordered_at DESC)
  INCLUDE (amount, status);
--   → SELECT amount, status ... WHERE customer_id=? 가 힙을 읽지 않습니다
--   → 단, Visibility Map이 최신이어야 하므로 VACUUM 상태가 중요합니다

-- ② 부분 인덱스: 대상 행이 소수일 때 압도적으로 효율적
CREATE INDEX idx_ord_pending ON orders (created_at)
  WHERE status IN ('PENDING','RETRY');
--   전체 1억 행 중 수천 건만 색인 → 인덱스 수 MB, 큐 조회가 즉시 응답

-- ③ 표현식 인덱스
CREATE INDEX idx_cust_email_ci ON customers (lower(email));
CREATE INDEX idx_evt_user ON events (((payload->'user'->>'id')::int));

-- ④ 정렬 방향과 NULL 위치를 쿼리와 일치시키기
CREATE INDEX idx_ord_sort ON orders (ordered_at DESC NULLS LAST);

-- ⑤ 중복·부분 문자열 검색
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_prod_trgm ON products USING gin (name gin_trgm_ops);
--   → WHERE name ILIKE '%키보드%' 가 인덱스를 사용합니다

-- ⑥ 확장 통계: 컬럼 간 상관관계로 인한 추정 오차 교정
CREATE STATISTICS st_city_zip (dependencies, ndistinct)
  ON city, zipcode FROM addresses;
ANALYZE addresses;


-- 운영 중에는 반드시 CONCURRENTLY (쓰기를 막지 않음)
CREATE INDEX CONCURRENTLY idx_x ON t (col);
--   · 트랜잭션 블록 안에서 실행할 수 없습니다
--   · 두 번 스캔하므로 느립니다
--   · 실패하면 INVALID 인덱스가 남습니다 → 반드시 확인하고 정리

-- INVALID 인덱스 확인 및 정리
SELECT i.indexrelid::regclass AS idx, i.indrelid::regclass AS tbl
FROM pg_index i WHERE NOT i.indisvalid;
DROP INDEX CONCURRENTLY idx_x;          -- 그리고 다시 생성

-- 재생성 (bloat 해소). PG12+ 는 CONCURRENTLY 지원
REINDEX INDEX CONCURRENTLY idx_x;
REINDEX TABLE CONCURRENTLY orders;
REINDEX DATABASE CONCURRENTLY shop;     -- 유지보수 창에서

-- 제약조건과 함께 무중단으로 유니크 만들기
CREATE UNIQUE INDEX CONCURRENTLY uq_email ON customers (email);
ALTER TABLE customers ADD CONSTRAINT uq_email UNIQUE USING INDEX uq_email;


-- ① 한 번도 쓰이지 않은 인덱스 (PK·UNIQUE 제약은 제외해서 판단)
SELECT s.relname AS tbl, s.indexrelname AS idx, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size,
       i.indisunique, i.indisprimary
FROM pg_stat_user_indexes s JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisprimary AND NOT i.indisunique
ORDER BY pg_relation_size(s.indexrelid) DESC;
--   주의: 통계는 pg_stat_reset() 이후 누적입니다. 최소 한 달, 월말 배치까지 관찰 후 판단하세요.
--   삭제 전 안전장치: 먼저 비활성화해 영향 확인
--     UPDATE pg_index SET indisvalid = false WHERE indexrelid = 'idx'::regclass; -- 신중히

-- ② 중복 인덱스 (선두 컬럼이 겹치는 경우)
SELECT indrelid::regclass AS tbl,
       array_agg(indexrelid::regclass) AS 겹치는_인덱스들,
       (indkey::int2[])[0:0] AS 선두컬럼
FROM pg_index GROUP BY indrelid, (indkey::int2[])[0:0]
HAVING count(*) > 1;
--   (a) 와 (a,b) 가 함께 있으면 (a)는 대개 불필요합니다.

-- ③ 인덱스가 없어서 순차 스캔이 많은 테이블
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       seq_tup_read / NULLIF(seq_scan,0) AS avg_rows_per_seq
FROM pg_stat_user_tables
WHERE seq_scan > 1000 AND pg_relation_size(relid) > 100*1024*1024
ORDER BY seq_tup_read DESC LIMIT 15;


-- 정확한 bloat 측정 (pgstattuple 확장; 전체 스캔이므로 부하 주의)
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT * FROM pgstattuple('orders');
--   tuple_count, dead_tuple_count, dead_tuple_percent, free_percent

SELECT * FROM pgstatindex('idx_orders_customer');
--   avg_leaf_density (낮으면 bloat), leaf_fragmentation

-- 대용량에서는 샘플링 버전을 사용
SELECT * FROM pgstattuple_approx('orders');

-- 처방
--   테이블 bloat 심함 → pg_repack (무중단) 또는 VACUUM FULL (정지 필요)
--   인덱스 bloat 심함 → REINDEX ... CONCURRENTLY
--   재발 방지        → autovacuum 강화, 장기 트랜잭션 차단, fillfactor 조정
인덱스 추가는 조회를 빠르게 하지만 쓰기·VACUUM·디스크·HOT 비율 모두에 비용을 부과합니다. 새 인덱스를 만들 때는 항상 "어떤 쿼리를 위한 것이고, 기존 인덱스로 대체 불가능한가"를 기록해 두세요.

플래너와 EXPLAIN 읽기

PostgreSQL은 비용 기반 옵티마이저입니다. 통계로 행 수를 추정하고, 가능한 실행 경로들의 비용을 계산해 가장 싼 것을 고릅니다. 따라서 느린 쿼리의 원인은 대개 셋 중 하나입니다: 통계가 틀렸다 / 인덱스가 없다 / 비용 상수가 하드웨어와 맞지 않는다.

노드의미좋은 신호 / 나쁜 신호

EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, WAL, FORMAT TEXT)
SELECT ...;

--   ANALYZE  : 실제 실행하고 실측 시간·행 수를 표시 (필수)
--   BUFFERS  : shared hit/read/dirtied/written — 실제 I/O량 (필수)
--   SETTINGS : 기본값과 다른 플래너 파라미터 표시 (PG12+)
--   WAL      : 생성된 WAL 양 (PG13+, 쓰기 쿼리 분석에 유용)
--   TIMING off: 시간 측정 오버헤드를 줄일 때
--   FORMAT JSON: 도구 연동용

BEGIN;
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM orders WHERE ordered_at < '2020-01-01';
ROLLBACK;

-- 운영 중인 세션의 현재 계획 엿보기 (PG14+)

-- pg_show_plans / auto_explain 으로 실계획 로깅
ALTER SYSTEM SET auto_explain.log_min_duration = '3s';
ALTER SYSTEM SET auto_explain.log_analyze = on;
ALTER SYSTEM SET auto_explain.log_buffers = on;

플랜은 안쪽(가장 깊게 들여쓰인 곳)부터 밖으로 실행됩니다.
아래 순서로 점검하면 대부분의 원인이 잡힙니다.

1. actual time 이 가장 큰 노드를 찾는다
   → "(actual time=시작..종료 rows=행 loops=반복)" 에서 (종료 × loops)가 실제 소비 시간

2. rows 추정 vs 실제 차이를 본다
   rows=100 인데 actual rows=250000  → 통계 문제. ANALYZE 또는 확장 통계 필요
   차이가 10배 이상이면 조인 순서·방식 선택이 틀어졌을 가능성이 큽니다

3. loops 를 본다
   Nested Loop 안쪽 노드가 loops=50000 이면 그 노드에 인덱스가 필요합니다

4. Buffers 를 본다
   shared read 가 크다        → 캐시 미스. 데이터가 메모리에 없음
   temp read/written 이 있다  → work_mem 부족으로 디스크 사용
   dirtied 가 크다            → 쓰기 부하 유발

5. Filter 와 Rows Removed by Filter 를 본다
   Rows Removed 가 매우 크다  → 인덱스로 미리 걸러야 할 조건이 뒤늦게 적용됨

6. Sort Method / Batches 를 본다
   external merge Disk        → work_mem 상향 후보
   Hash Batches: 8            → 해시가 메모리에 안 들어감

7. 마지막에 Planning Time 과 Execution Time 을 비교
   Planning Time 이 지나치게 크다 → 파티션이 너무 많거나 준비된 문장 활용 검토

shared_buffers          PostgreSQL 자체 페이지 캐시. RAM의 25%가 통상 출발점.

effective_cache_size    실제 메모리를 할당하지 않습니다. "OS 캐시까지 포함해 이만큼은

                        낮게 두면 플래너가 인덱스 스캔을 과소평가합니다.

                        max_connections × 노드수 × work_mem 이 필요합니다.
                        전역은 보수적으로, 무거운 배치는 세션에서 올리는 것이 안전합니다:

maintenance_work_mem    VACUUM, CREATE INDEX, ALTER TABLE 용. 크게 줘도 동시 실행 수가

                        autovacuum_work_mem 을 따로 지정하면 워커별로 분리됩니다.

temp_buffers            임시 테이블용 세션별 버퍼. 임시 테이블을 많이 쓰면 상향.

wal_buffers             커밋 전 WAL을 담는 공유 버퍼. -1(자동, shared_buffers/32)이면
                        대개 충분하며 16~64MB로 고정해도 무해합니다.

  · 활성 쿼리 수가 CPU 코어 수를 크게 넘으면 처리량이 오히려 떨어집니다
  · 경험 기준: 동시 활성 쿼리 = vCPU × 2 ~ 4 근처가 상한

-- 11 · locks & safe ddl

락 · 안전한 DDL

운영 중 장애의 상당수는 "잘못된 쿼리"가 아니라 잘못된 시점의 DDL에서 발생합니다. ALTER TABLE 한 줄이 ACCESS EXCLUSIVE 락을 얻지 못해 대기하면, 그 뒤에 줄을 서는 모든 SELECT까지 멈춥니다. 락 종류와 호환성을 아는 것은 선택이 아니라 필수입니다.

-- ① 누가 누구를 막고 있는가 (가장 먼저 실행할 쿼리)
SELECT a.pid, a.usename, a.state, a.wait_event_type, a.wait_event,
       now()-a.xact_start AS xact_age,
       pg_blocking_pids(a.pid) AS blocked_by,
       left(a.query, 80) AS query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY xact_age DESC;

-- ② 락 대기 사슬 전체 보기
SELECT w.pid AS waiter, w.mode AS want_mode, w.relation::regclass AS tbl,
       b.pid AS blocker, b.mode AS held_mode,
       left(bq.query, 60) AS blocker_query, now()-bq.xact_start AS blocker_age
FROM pg_locks w
JOIN pg_locks b ON w.relation = b.relation AND b.granted AND NOT w.granted
JOIN pg_stat_activity bq ON bq.pid = b.pid
WHERE w.relation IS NOT NULL;

-- ③ 조치 — 취소 먼저, 종료는 그다음
SELECT pg_cancel_backend(12345);      -- 실행 중 쿼리만 취소 (안전)
SELECT pg_terminate_backend(12345);   -- 세션 강제 종료 (트랜잭션 롤백됨)

-- ④ 대기 이벤트 분포 — 병목 유형 파악
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE state = 'active'
GROUP BY 1,2 ORDER BY 3 DESC;
--   Lock: 잠금 경합 / LWLock: 내부 경합 / IO: 디스크 / Client: 앱 대기(정상)


-- 원칙 1: DDL 세션에는 반드시 lock_timeout을 걸고 재시도한다
--          (무한 대기하며 뒤에 줄을 세우는 것을 방지)
SET lock_timeout = '3s';
SET statement_timeout = '30s';
ALTER TABLE orders ADD COLUMN memo text;   -- 실패하면 잠시 후 재시도

-- 원칙 2: 컬럼 추가는 기본값이 있어도 즉시 완료된다 (PG11+)
ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'NEW';  -- 테이블 재작성 없음
--   단, volatile 기본값(예: random())이나 타입 변경은 재작성이 발생합니다

-- 원칙 3: NOT NULL 추가는 두 단계로 (전체 스캔 잠금 회피)
ALTER TABLE orders ADD CONSTRAINT ck_memo_nn CHECK (memo IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT ck_memo_nn;   -- 약한 잠금으로 검증
ALTER TABLE orders ALTER COLUMN memo SET NOT NULL;   -- PG12+ 는 위 CHECK를 근거로 스캔 생략

-- 원칙 4: FK 추가도 두 단계로
ALTER TABLE orders ADD CONSTRAINT fk_cust
  FOREIGN KEY (customer_id) REFERENCES customers(id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT fk_cust;

-- 원칙 5: 타입 변경은 새 컬럼 + 백필 + 교체로 우회
ALTER TABLE orders ADD COLUMN amount_new numeric(18,2);
-- 배치로 나눠 백필 (한 번에 UPDATE 하면 거대한 트랜잭션 + bloat)
UPDATE orders SET amount_new = amount WHERE id BETWEEN 1 AND 100000;
-- 트리거로 신규 쓰기 동기화 → 짧은 잠금 창에서 컬럼 교체

-- 원칙 6: 인덱스는 CONCURRENTLY, 대량 삭제는 배치로
DELETE FROM logs WHERE created_at < now()-interval '1 year'
  AND id IN (SELECT id FROM logs WHERE created_at < now()-interval '1 year' LIMIT 10000);
--   또는 파티셔닝으로 DETACH (7장)


ACCESS EXCLUSIVE (읽기조차 막음) — 운영 시간에 절대 피할 것
  DROP TABLE, TRUNCATE, VACUUM FULL, CLUSTER
  REINDEX (CONCURRENTLY 아닌 것), REFRESH MATERIALIZED VIEW (CONCURRENTLY 아닌 것)
  ALTER TABLE 대부분: 컬럼 타입 변경, 컬럼 삭제, SET NOT NULL(구버전),
                      RENAME, SET TABLESPACE, 제약 추가(NOT VALID 아닌 경우)
  → 짧게 끝나는 작업이라도 "락을 얻기까지의 대기"가 위험합니다.
     선행 트랜잭션이 5분간 열려 있으면 그 5분간 서비스가 멈춥니다.

SHARE (쓰기 차단, 읽기 허용)
  CREATE INDEX (CONCURRENTLY 아닌 것)

SHARE UPDATE EXCLUSIVE (동시 DML 허용 — 상대적으로 안전)
  VACUUM(FULL 아닌 것), ANALYZE
  CREATE INDEX CONCURRENTLY, REINDEX CONCURRENTLY
  ALTER TABLE VALIDATE CONSTRAINT, ALTER TABLE SET (파라미터)
  DETACH PARTITION CONCURRENTLY

ROW EXCLUSIVE (일반 DML)
  INSERT, UPDATE, DELETE, MERGE, COPY FROM

체크리스트 — 마이그레이션 전에 확인
  □ lock_timeout 설정했는가
  □ 실패 시 재시도 로직이 있는가
  □ 장시간 트랜잭션이 열려 있지 않은가 (pg_stat_activity 확인)
  □ 되돌리는 절차(down migration)가 준비되어 있는가
  □ 대상 테이블 크기와 예상 소요 시간을 스테이징에서 측정했는가

  at timestamptz NOT NULL DEFAULT now(),
  usr text NOT NULL DEFAULT current_user,
  addr inet DEFAULT inet_client_addr(),
  tbl text NOT NULL, op char(1) NOT NULL,
  old_row jsonb, new_row jsonb

CREATE OR REPLACE FUNCTION f_audit() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log (tbl, op, old_row, new_row)
  VALUES (TG_TABLE_NAME, left(TG_OP,1),
          CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END,
          CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END);
  RETURN NULL;
END $$;

-- 14 · upgrade

업그레이드 · 확장 관리

PostgreSQL은 매년 한 번 메이저 버전을 내고, 각 버전을 5년간 지원합니다. 마이너 업그레이드는 쉽고 반드시 해야 하는 일이며, 메이저 업그레이드는 계획이 필요한 프로젝트입니다.

마이너 (17.2 → 17.4)

디스크 포맷이 동일합니다. 바이너리 교체 후 재시작이면 끝이고, 보안 패치와 데이터 손상 버그 수정이 담기므로 미루면 안 됩니다. 다운타임은 재시작 시간(수 초~수십 초)입니다. 릴리스 노트에서 "이 릴리스 후 REINDEX 필요" 같은 예외 안내만 확인하세요.

메이저 (16 → 17)

내부 카탈로그 구조가 바뀌므로 데이터 변환이 필요합니다. pg_upgrade(짧은 다운타임) 또는 논리 복제(거의 무중단)를 선택합니다. 완료 후 ANALYZE로 통계를 다시 만들어야 하며(그 전까지 쿼리가 느립니다), 확장 호환성을 먼저 확인해야 합니다.

CREATE TABLE chunks (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doc_id     bigint NOT NULL,
  tenant_id  int    NOT NULL,
  content    text   NOT NULL,
  meta       jsonb  NOT NULL DEFAULT '{}',
  embedding  vector(1536) NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- HNSW 인덱스: 빌드에 시간과 메모리가 많이 필요합니다
SET maintenance_work_mem = '4GB';
SET max_parallel_maintenance_workers = 4;
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 조회 시 정확도/속도 조절
SET hnsw.ef_search = 100;

-- 메타데이터 필터 + 벡터 검색을 한 쿼리로 (PostgreSQL의 핵심 강점)
SELECT id, content, 1 - (embedding <=> :q) AS score
FROM chunks
WHERE tenant_id = :tenant AND meta @> '{"lang":"ko"}'
ORDER BY embedding <=> :q
LIMIT 10;

Q1테이블에서 100만 행을 DELETE 했는데 디스크 사용량이 줄지 않았습니다. 이유는?
일반 VACUUM은 dead 튜플 공간을 재사용 가능하게 만들지만 파일 크기를 OS에 반환하지는 않습니다. 실제로 줄이려면 VACUUM FULL(ACCESS EXCLUSIVE 잠금) 또는 pg_repack이 필요합니다. 다만 해당 테이블에 다시 데이터가 쌓일 예정이라면 그대로 재사용하는 것이 더 효율적입니다.
Q2VACUUM이 dead 튜플을 회수하지 못하는 가장 흔한 원인은?
VACUUM은 가장 오래된 스냅샷보다 최근의 튜플 버전을 지울 수 없습니다. 장기 트랜잭션, idle in transaction 세션, 비활성 복제 슬롯, 미해결 prepared transaction이 모두 이 한계선을 붙잡습니다. idle_in_transaction_session_timeout 설정이 기본 방어책입니다.
Q3pg_wal 디렉터리가 계속 커지고 있습니다. 확인 순서로 가장 적절한 것은?
pg_wal 증가의 3대 원인은 아카이브 실패, 비활성 복제 슬롯, 거대·장기 트랜잭션입니다. WAL 파일을 직접 rm하면 복구 불가능한 손상이 발생합니다. 절대 하지 마세요. 응급 조치로는 불필요한 슬롯 삭제와 max_slot_wal_keep_size 설정이 있습니다.
Q4EXPLAIN ANALYZE 결과에서 rows=12, actual rows=240000이었습니다. 1차 조치는?
추정과 실제의 큰 차이는 통계 문제입니다. 특히 여러 컬럼이 상관관계를 가질 때(예: 도시와 우편번호) 독립 가정으로 과소 추정됩니다. CREATE STATISTICS로 상관관계를 알려주는 것이 정공법이며, enable_nestloop=off는 증상만 가리는 임시방편입니다.
Q5운영 중 대형 테이블에 인덱스를 추가해야 합니다. 올바른 방법은?
기본 CREATE INDEX는 SHARE 락으로 쓰기를 차단합니다. CONCURRENTLY는 쓰기를 막지 않지만 트랜잭션 블록 안에서 실행할 수 없고, 실패 시 INVALID 인덱스가 남으므로 pg_index.indisvalid 확인이 절차에 포함되어야 합니다.
Q6synchronous_standby_names = 'standby1'로 동기 복제를 구성했고, standby1이 장애로 내려갔습니다. 무슨 일이 생기나요?
지정된 동기 스탠바이가 응답하지 않으면 커밋이 대기합니다. 그래서 실무에서는 'ANY 1 (standby1, standby2)'처럼 여러 후보 중 하나를 요구하도록 구성해 1대 장애를 견디게 합니다. 응급 시에는 synchronous_standby_names를 비우고 reload 하면 비동기로 전환됩니다.
Q7XID 나이가 18억에 도달했습니다. 가장 먼저 할 일은?
약 21억에서 새 트랜잭션이 거부됩니다. 임계값을 올리는 것은 문제를 미루는 것이고, pg_resetwal은 데이터 손실을 유발하는 최후 수단입니다. 방해 요소를 제거하고 vacuumdb --freeze --jobs로 병렬 동결을 진행하는 것이 정답입니다.
Q8운영 표준으로 가장 적절한 백업 구성은?
복제는 실수와 논리적 손상을 막지 못합니다(DROP TABLE이 그대로 전파됨). 논리 백업만으로는 RPO가 하루에 이르고 RTO도 깁니다. 베이스 백업 + WAL 아카이브 조합이 초 단위 RPO를 제공하며, 복구 리허설이 없으면 그 백업은 검증되지 않은 것입니다.
Q9ALTER TABLE ... ADD COLUMN memo text가 5분간 완료되지 않고, 그 뒤로 모든 SELECT까지 멈췄습니다. 원인은?
기본값 없는 컬럼 추가는 카탈로그만 바꾸므로 작업 자체는 즉시입니다. 문제는 앞선 장기 트랜잭션 때문에 락을 얻지 못하고, 락 대기 큐에 걸린 DDL이 이후 모든 요청을 막는 것입니다. 대응은 SET lock_timeout 후 재시도이며, 사전에 장기 트랜잭션을 확인해야 합니다.
Q10work_mem을 설정할 때 반드시 고려해야 하는 것은?
work_mem은 노드당·세션당 상한입니다. 전역 값은 보수적으로 두고, 무거운 배치는 세션에서 SET work_mem으로 올리는 방식이 안전합니다. 컨테이너 환경에서는 이 폭주가 OOM Kill로 직결됩니다.
Q113년 지난 로그 데이터를 매월 정리해야 합니다. 가장 좋은 구조는?
대량 DELETE는 긴 시간, 대량 WAL, 거대한 bloat를 남기고 VACUUM FULL은 서비스 정지를 부릅니다. 파티션 DROP은 파일 삭제 수준으로 즉시 끝나고 bloat도 없습니다. 미래 파티션 사전 생성을 pg_partman이나 cron으로 자동화하는 것이 필수 조건입니다.
Q12메이저 업그레이드(16→17) 직후 모든 쿼리가 느려졌습니다. 가장 먼저 확인할 것은?
pg_upgrade는 통계를 이관하지 않습니다. vacuumdb --all --analyze-in-stages로 재생성해야 하며, postgresql.conf의 튜닝 값도 자동으로 옮겨지지 않습니다. 두 항목이 업그레이드 절차서의 필수 단계입니다. (OS를 함께 올렸다면 콜레이션 변경으로 인한 인덱스 재작성 필요성도 확인하세요.)

좋은 DBA를 만드는 것은 암기가 아니라 습관입니다. 변경은 하나씩 근거와 함께, 조치 전에는 항상 현재 상태를 기록하고, 백업은 복구해 봐야 백업이며, 경보는 대응 절차와 함께 만듭니다. 이 강의의 진단 쿼리를 팀 위키에 옮겨 두고 장애 때 바로 꺼내 쓸 수 있게 정리하는 것이 첫 실천 항목입니다.
