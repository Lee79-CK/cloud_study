CPU·메모리·디스크·네트워크는 실제로 어떻게 나뉘는가

1편이 "왜 하이퍼바이저가 필요하고 어떤 원리로 가능한가"였다면, 2편은 그 아래에서 자원이 실제로 쪼개지는 방식입니다. vCPU 하나에 무엇이 보장되는지, 게스트의 메모리 주소가 물리 주소가 되기까지 몇 번의 번역을 거치는지, 디스크 I/O 한 번이 몇 개의 계층을 통과하는지를 다룹니다.

대상 · 1~2년차 클라우드 엔지니어 선행 · 1편 (특히 VM Exit) 읽는 시간 · 약 45분
01

이번 편은 전부 한 문장으로 요약된다

1편 마지막에서 이렇게 정리했습니다. 가상화 성능 튜닝의 본질은 VM Exit을 얼마나 줄이느냐다. 이번 편에 나오는 EPT, 대용량 페이지, virtio, vhost, SR-IOV, APICv는 전부 이 한 문장의 변주입니다. 기술 이름을 외우는 대신 매번 이렇게 물으면 됩니다. "이 기술은 어떤 계층 전환을 없앴는가?"

자원마다 없애야 할 전환의 종류가 다릅니다. 정리하면 이렇습니다.

02

CPU — 시간을 쪼갠다

메모리와 디스크는 공간을 나누지만 CPU는 시간을 나눕니다. 물리 코어 하나가 짧은 구간씩 번갈아 여러 vCPU를 실행하고, 그 전환이 충분히 빠르면 각 VM은 자기 전용 CPU가 있다고 느낍니다.

하이퍼바이저의 스케줄러는 OS 스케줄러와 구조가 비슷하지만 대상이 다릅니다. OS는 프로세스를 스케줄링하고, 하이퍼바이저는 vCPU를 스케줄링합니다. 그래서 VM 안에서는 스케줄링이 두 번 일어납니다. 게스트 OS가 프로세스를 vCPU에 배치하고, 하이퍼바이저가 그 vCPU를 물리 코어에 배치합니다. 이 이중 구조가 가상화 CPU 문제의 대부분을 설명합니다.

vCPU는 예약이 아니라 대기표다

vCPU 8개를 줬다고 물리 코어 8개가 예약되는 게 아닙니다. "동시에 최대 8개의 실행 흐름을 돌릴 수 있는 권리"일 뿐이고, 실제 코어를 얻으려면 다른 VM들과 경쟁해야 합니다. 이 경쟁에서 밀려 기다린 시간이 CPU Ready입니다.

중요한 건 이 지표가 게스트 안에서는 거의 보이지 않는다는 점입니다. 게스트의 top은 CPU 사용률 30%에 부하도 낮다고 말하는데 응답은 느립니다. 대기 시간은 게스트의 시계에 잡히지 않으니까요. 호스트 쪽 지표를 봐야 원인이 드러납니다. 신입 엔지니어가 "VM이 느린데 이유를 모르겠다"고 할 때 가장 먼저 확인할 곳입니다. 

# 게스트(리눅스) 안에서 — st 컬럼이 steal time
$ vmstat 1
procs -----------memory---------- ---swap-- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so  in   cs us sy id wa st
 2  0      0 812344  24112 391220    0    0 1520 2840 22  6 58  1 13   ← 13% 강탈당함

# 호스트(KVM) 쪽에서 — VM별 CPU 시간
$ virsh domstats --vcpu web-01

# ESXi — esxtop 에서 c(CPU) 화면의 %RDY 컬럼
$ esxtop

오버커밋 비율 판정기

호스트 사양과 배치할 VM 구성을 넣으면 오버커밋 비율과 위험도를 계산합니다.

2.5: 1 오버커밋
총 vCPU80개
권장 상한 (이 워크로드)4 : 1
추가 배치 여력+18대
여유 있습니다.

하이퍼스레딩을 켜도 논리 프로세서 수를 물리 코어로 계산하지 마세요. 논리 프로세서 2개가 물리 코어 1개의 성능을 주지 않습니다. 사이징은 물리 코어 기준으로 하고, 하이퍼스레딩은 여유분으로 보는 편이 안전합니다.

vCPU를 많이 주면 오히려 느려지는 역설

"성능이 안 나오니 vCPU를 8개에서 16개로 올리자"는 판단은 자주 틀립니다. 멀티코어 VM의 vCPU들은 게스트 OS 입장에서 동시에 존재해야 하는 CPU들입니다. 게스트 커널이 스핀락을 걸거나 TLB 셧다운을 하면 다른 vCPU들이 즉시 응답해야 하는데, 그 vCPU가 스케줄링을 못 받고 있으면 전체가 멈춰서 기다립니다.

그래서 하이퍼바이저들은 vCPU들을 어느 정도 함께 진행시키는 코스케줄링을 합니다. vCPU가 많을수록 "동시에 비어 있는 물리 코어 묶음"을 찾기 어려워지고, 대기가 길어집니다.

실무 원칙

vCPU는 실제로 쓰는 만큼만 주고, 부족할 때 늘리세요. 4 vCPU로 충분한 VM에 16 vCPU를 주면 대부분의 경우 더 느려집니다. 특히 단일 스레드 위주 애플리케이션이라면 vCPU를 늘려도 얻는 게 없고 스케줄링 비용만 붙습니다.

CPU 피닝과 토폴로지

지연에 극도로 민감한 워크로드는 vCPU를 특정 물리 코어에 고정하는 CPU 피닝을 씁니다. 스케줄링 지연과 캐시 무효화가 줄어들지만, 유연성을 포기하는 선택입니다. 피닝된 VM은 라이브 마이그레이션이 까다로워지고, 해당 코어는 다른 VM이 쓸 수 없게 됩니다. 

# KVM — vCPU 0,1을 물리 코어 4,5에 고정
virsh vcpupin web-01 0 4
virsh vcpupin web-01 1 5

# 현재 매핑 확인
virsh vcpuinfo web-01

또 하나 놓치기 쉬운 게 CPU 토폴로지 표현입니다. vCPU 8개를 "소켓 8개 × 코어 1개"로 보여줄지 "소켓 1개 × 코어 8개"로 보여줄지에 따라 게스트 OS의 스케줄링 판단이 달라지고, 소켓 단위로 과금되는 소프트웨어의 라이선스 비용이 8배가 될 수 있습니다. 특별한 이유가 없으면 소켓 수는 최소로, 코어 수를 늘리는 쪽으로 설정합니다.

03

메모리 — 주소를 두 번 번역한다

가상화가 없을 때도 이미 주소 변환은 있었습니다. 프로세스의 가상 주소를 물리 주소로 바꾸는 페이지 테이블 변환입니다. 가상화를 하면 여기에 한 겹이 더 얹힙니다.

  • 게스트 가상 주소(GVA) → 게스트가 관리하는 페이지 테이블
  • 게스트 물리 주소(GPA) → 게스트는 이게 진짜 RAM 주소라고 믿는다
  • 호스트 물리 주소(HPA) → 실제 메모리 칩 위의 위치

문제는 게스트가 믿는 "물리 주소"가 사실은 가짜라는 것입니다. 누군가는 GPA를 HPA로 한 번 더 바꿔야 합니다. 이 일을 누가 하느냐로 세대가 갈립니다.

1세대: 섀도 페이지 테이블

하드웨어 지원이 없던 시절, 하이퍼바이저는 GVA를 HPA로 직접 매핑하는 별도의 페이지 테이블을 만들어 CPU에 그것을 물렸습니다. 이게 섀도 페이지 테이블입니다. 변환 자체는 한 번에 끝나니 빠릅니다. 문제는 동기화입니다.

게스트가 자기 페이지 테이블을 수정할 때마다 하이퍼바이저가 섀도 테이블을 갱신해야 합니다. 그러려면 게스트 페이지 테이블을 읽기 전용으로 만들어 두고, 게스트가 쓰기를 시도할 때마다 VM Exit을 일으켜 가로채야 합니다. 프로세스를 자주 생성하는 워크로드에서는 이 exit이 폭발적으로 늘어납니다.

2세대: EPT / NPT

인텔의 EPT(Extended Page Table), AMD의 NPT(Nested Page Table)는 GPA→HPA 변환 테이블을 CPU가 직접 이해하게 만들었습니다. 하이퍼바이저는 이 테이블을 한 번 세팅해 두고 물러나면 되고, 게스트가 자기 페이지 테이블을 아무리 고쳐도 exit이 발생하지 않습니다.

대가는 변환 비용입니다. TLB에 없는 주소는 이제 2차원 페이지 워크를 해야 합니다. 게스트 테이블을 한 단계 내려갈 때마다, 그 단계의 주소 자체가 GPA이므로 또 호스트 테이블을 타야 합니다. 4단계 × 4단계 구조에서 최악의 경우 메모리를 24번 읽습니다.

주소 변환 경로 비교

게스트가 메모리에 접근할 때 벌어지는 일을 단계별로 따라갑니다.

대용량 페이지와 TLB

2차원 페이지 워크가 비싸다면 답은 두 가지입니다. 워크를 줄이거나, TLB 적중률을 높이거나. 대용량 페이지가 둘 다 해결합니다. 기본 페이지는 4KB인데, 2MB나 1GB 단위로 매핑하면 페이지 테이블 단계가 줄어들고 TLB 엔트리 하나가 훨씬 넓은 영역을 커버합니다.

대용량 메모리를 쓰는 DB나 인메모리 캐시에서 체감 효과가 큽니다. 다만 메모리 단편화가 생기면 대용량 페이지 확보가 어려워지고, 페이지 공유 기법과는 상성이 나쁩니다 (2MB 덩어리가 통째로 같아야 공유가 되니까요).

여기에 VPID(인텔) / ASID(AMD)가 더해집니다. 원래는 VM 전환 때마다 TLB를 통째로 비워야 했는데, 이 기능이 TLB 엔트리에 VM 식별자를 붙여 비우지 않고도 섞이지 않게 만들었습니다. VM Exit 직후의 성능 저하가 크게 줄었습니다. 

# 리눅스 호스트에서 대용량 페이지 상태 확인
$ cat /proc/meminfo | grep -i huge
AnonHugePages:   4194304 kB
HugePages_Total:       0
Hugepagesize:       2048 kB

# THP(투명 대용량 페이지) 설정 확인
$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never
04

메모리 오버커밋의 네 단계

CPU 오버커밋은 최악의 경우 느려질 뿐입니다. 메모리 오버커밋은 최악의 경우 멈춥니다. CPU는 기다리면 언젠가 차례가 오지만, 메모리는 없으면 없는 것이기 때문입니다. 그래서 하이퍼바이저는 메모리가 부족해질 때 네 가지 기법을 순서대로 꺼냅니다. 뒤로 갈수록 효과는 크고 대가도 큽니다.

메모리 압박 시뮬레이터

VM들에 할당한 총 메모리를 늘리면서 호스트가 어떤 회수 기법을 꺼내는지 확인해 보세요.

0.86: 1 오버커밋
실제 요구량154GB
호스트 여유102GB
현재 발동 단계없음
안전 구간입니다.

1단계 · 페이지 공유

내용이 완전히 같은 메모리 페이지를 하나만 남기고 나머지는 같은 곳을 가리키게 합니다. 리눅스의 KSM, VMware의 TPS가 이것입니다. 같은 OS 이미지를 쓰는 VM이 많은 VDI 환경에서 효과가 큽니다.

대가 — 페이지를 스캔하는 CPU 비용. 대용량 페이지를 쓰면 효과가 급감합니다.

2단계 · 벌루닝

게스트 안에 설치된 벌룬 드라이버가 게스트 OS에게 메모리를 요청해 "풍선처럼 부풀립니다". 게스트 OS는 정상적인 메모리 압박으로 인식해 자기 판단으로 캐시를 비우고 덜 중요한 것부터 정리합니다. 하이퍼바이저는 그렇게 확보된 영역을 회수합니다.

대가 — 게스트 도구 설치가 전제. 반응이 느려 급격한 압박에는 못 따라갑니다.

3단계 · 압축

디스크로 내보내기 직전에, 페이지를 압축해서 메모리 안에 더 작게 보관합니다. 디스크 접근보다는 훨씬 빠르므로 스와핑을 늦추는 완충재 역할입니다.

대가 — 압축·해제에 드는 CPU. 이미 압축된 데이터에는 효과가 없습니다.

4단계 · 스와핑

게스트 메모리 페이지를 디스크로 강제로 내보냅니다. 확실하게 메모리를 회수하지만 여기까지 왔다는 건 이미 설계가 실패했다는 뜻입니다.

대가 — 치명적. 하이퍼바이저는 어떤 페이지가 중요한지 모르므로 하필 가장 뜨거운 페이지를 내보낼 수 있습니다. 응답 시간이 수십 배로 튑니다.

이중 스와핑이라는 최악의 시나리오

게스트 OS도 자기 안에서 스왑을 합니다. 그 상태에서 하이퍼바이저까지 스왑을 하면, 게스트가 스왑아웃한 페이지를 호스트가 디스크에서 읽어와 다시 스왑아웃하는 일이 벌어집니다. 디스크 I/O가 폭증하고 시스템 전체가 사실상 멈춥니다. 메모리 오버커밋을 공격적으로 잡으면 안 되는 이유가 이것입니다.

실무 기준은 단순합니다. 운영 워크로드는 메모리를 오버커밋하지 않는 것을 기본값으로 두세요. CPU는 3:1도 흔하지만 메모리는 1:1이 출발점입니다. 오버커밋을 한다면 VDI나 개발 환경처럼 "동시에 다 쓰지 않는다"가 통계적으로 확실한 경우에 한정하고, 반드시 벌룬 드라이버가 전 VM에 설치된 상태여야 합니다.

05

NUMA — 메모리에도 거리가 있다

현대 서버는 CPU 소켓마다 자기 메모리 컨트롤러와 메모리 슬롯을 가집니다. 소켓 0의 CPU가 소켓 0에 붙은 메모리를 읽는 건 빠르지만, 소켓 1에 붙은 메모리를 읽으려면 소켓 간 링크를 건너가야 합니다. 이 구조가 NUMA(Non-Uniform Memory Access)이고, 원격 접근은 보통 로컬의 1.5~2배 지연이 걸립니다.

VM 하나가 한 NUMA 노드 안에 들어가면 문제가 없습니다. 문제는 노드 하나보다 큰 VM입니다. vCPU와 메모리가 두 노드에 걸치면 상당량의 메모리 접근이 원격이 되고, 같은 사양인데 성능이 눈에 띄게 떨어집니다.

노드를 넘길 수밖에 없는 큰 VM이라면 vNUMA를 씁니다. 호스트의 NUMA 구조를 게스트에게 그대로 노출해서, 게스트 OS와 그 위의 DB가 스스로 NUMA를 인지하고 지역성을 최적화하도록 맡기는 방식입니다. 대부분의 하이퍼바이저가 일정 크기 이상의 VM에는 자동으로 vNUMA를 켭니다.

실무 규칙 세 가지

하나. 가능하면 VM 하나가 노드 하나 안에 들어가게 사이징합니다.
둘. 노드를 넘길 수밖에 없다면 노드 수의 배수로 맞춰 균등하게 나뉘도록 합니다. 16코어 노드에서 20 vCPU보다 16 또는 32가 낫습니다.
셋. 메모리도 함께 봐야 합니다. vCPU는 노드 안에 들어가는데 메모리가 노드 용량을 넘으면 결국 원격 접근이 발생합니다.

06

스토리지 — 파일을 디스크처럼 보이게

1편에서 VM은 결국 파일이라고 했습니다. 게스트는 그 파일을 SATA나 SCSI 디스크로 인식합니다. 이 착각을 만드는 방식에 따라 성능이 몇 배씩 차이 납니다.

가상 디스크 컨트롤러의 세대

방식동작성능쓰임
IDE / SATA 에뮬레이션실제 칩셋의 레지스터 동작을 소프트웨어로 흉내. 접근마다 VM Exit매우 낮음드라이버 없는 OS 설치 초기, 구형 게스트
virtio-blk게스트가 가상화를 인지하고 공유 링 버퍼로 요청을 전달. 반가상화높음KVM 환경의 일반적 선택
virtio-scsivirtio 기반이면서 SCSI 명령을 지원. 디스크 다수 연결, TRIM/UNMAP 가능높음디스크가 많거나 SCSI 기능이 필요할 때
NVMe 가상화 / 패스스루NVMe 큐 구조를 그대로 노출하거나 물리 NVMe를 직접 할당매우 높음고성능 DB, 지연 민감 워크로드

핵심은 virtio에서 무엇이 사라졌는가입니다. 에뮬레이션은 게스트가 디스크 레지스터를 건드릴 때마다 exit이 나고, 하이퍼바이저가 "이건 섹터 읽기 명령이구나" 하고 해석해야 합니다. virtio는 그 과정을 없앴습니다. 게스트가 공유 메모리 링에 요청을 여러 개 쌓아두고 한 번만 알리면, 하이퍼바이저가 일괄 처리합니다. 요청 수백 개에 exit 한 번으로 줄어듭니다.

qcow2와 raw, 그리고 씬 프로비저닝

raw

가상 디스크 내용이 파일에 그대로 1:1로 들어갑니다. 구조가 없으니 오버헤드도 없습니다. 가장 빠르고 단순하며, 문제가 생겼을 때 복구도 쉽습니다.

대신 스냅샷·압축·암호화 같은 기능은 파일 포맷이 아니라 아래 계층(LVM, 스토리지 장비)에 의존해야 합니다.

qcow2

QEMU Copy-On-Write 포맷. 실제로 쓴 블록만 파일에 할당하고, 어디에 무엇이 있는지를 참조 테이블로 관리합니다. 스냅샷·백킹 파일·압축·암호화를 포맷 자체가 지원합니다.

대신 테이블을 한 번 더 타므로 raw보다 약간 느리고, 파일이 커질수록 메타데이터 관리 부담이 늘어납니다.

씬 프로비저닝은 "100GB 디스크"라고 선언하되 실제로는 쓴 만큼만 차지하는 방식입니다. 공간 효율은 좋지만 두 가지 위험이 따라옵니다. 첫째, 블록을 새로 할당할 때마다 약간의 지연이 생겨 성능이 들쭉날쭉해집니다. 둘째, 과다 할당된 데이터스토어가 실제로 가득 차면 그 위의 모든 VM이 동시에 멈춥니다.

스냅샷은 백업이 아니다

스냅샷을 뜨면 원본 디스크는 동결되고, 이후의 모든 쓰기는 별도의 델타 파일에 쌓입니다. 스냅샷이 오래 유지될수록 델타가 커지고, 여러 개를 쌓으면 읽기 한 번에 체인을 거슬러 올라가야 해서 성능이 떨어집니다. 더 위험한 건 삭제(통합) 시점입니다. 커진 델타를 원본에 합치는 작업 자체가 대량 I/O를 일으키고, 중간에 실패하면 디스크가 깨질 수 있습니다.

원본이 손상되면 스냅샷도 함께 무용지물이 됩니다. 스냅샷은 되돌리기 장치이고, 백업은 별도로 존재해야 합니다. 작업 전 스냅샷은 작업이 끝나면 지우는 것까지가 한 세트입니다.

07

네트워크 — 경로를 짧게 만드는 역사

네트워크는 이 편에서 "계층 하나씩 걷어내기"가 가장 선명하게 보이는 영역입니다. 패킷 하나가 게스트에서 물리 NIC까지 가는 경로를 세대별로 비교해 보겠습니다.

패킷 경로 비교

가상 스위치

물리 NIC 하나에 VM 여럿이 붙으려면 그 사이에 스위치가 필요합니다. 하이퍼바이저는 소프트웨어로 L2 스위치를 구현해 VM들의 가상 NIC을 포트처럼 다룹니다. 리눅스 브리지, Open vSwitch, VMware의 표준/분산 스위치가 그것입니다.

여기서 중요한 성질이 하나 있습니다. 같은 호스트에 있는 VM끼리의 통신은 물리 NIC을 거치지 않습니다. 메모리 안에서 끝나므로 물리 네트워크보다 훨씬 빠릅니다. 반대로 말하면 물리 네트워크의 모니터링 장비나 방화벽이 이 트래픽을 전혀 못 봅니다. VM 간 통신 제어가 필요하면 마이크로세그멘테이션처럼 가상 스위치 계층에서 정책을 걸어야 합니다. 침해 사고에서 같은 호스트 내 횡적 이동이 탐지되지 않는 이유이기도 합니다.

SR-IOV의 대가

SR-IOV는 물리 NIC 하나를 여러 개의 가상 기능(VF)으로 쪼개서 VM에 직접 할당합니다. 하이퍼바이저를 완전히 우회하므로 베어메탈에 근접한 성능이 나옵니다. 하지만 공짜가 아닙니다.

  • 라이브 마이그레이션이 어렵습니다. VM이 특정 물리 NIC의 VF에 묶여 있기 때문입니다.
  • 가상 스위치를 우회합니다. 가상 스위치에 걸어둔 정책·모니터링이 적용되지 않습니다.
  • VF 개수에 상한이 있고, NIC과 BIOS·드라이버가 모두 지원해야 합니다.

그래서 SR-IOV는 "성능이 가장 좋으니 기본으로 쓰자"가 아니라, 유연성을 포기해도 좋을 만큼 지연이 중요한 워크로드에만 선택적으로 적용합니다. NFV, 고성능 패킷 처리, 일부 금융 시스템이 대표적입니다.

08

GPU — 나눌 수 없던 것을 나누기

CPU와 메모리는 오래전부터 나눠 쓸 수 있었지만 GPU는 그렇지 않았습니다. AI 워크로드가 늘면서 "GPU 한 장을 여러 VM이 나눠 쓸 수 있는가"가 실무 질문이 됐고, 현재 세 가지 방식이 있습니다.

방식나누는 단위격리 수준적합한 경우제약
패스스루 나누지 않음 (1 GPU = 1 VM)완전 대규모 학습, GPU를 풀로 쓰는 작업 다른 VM이 전혀 못 씀. 라이브 마이그레이션 불가
vGPU 시간 분할 (여러 VM이 번갈아 사용)중간 — 연산 유닛 공유 VDI, 그래픽 워크스테이션, 경량 추론 별도 라이선스 필요. 이웃 VM 부하에 성능이 영향받음
MIG 물리 분할 (연산·메모리·캐시를 하드웨어로 나눔)강함 — 자원이 실제로 분리됨 멀티테넌트 추론, 성능 예측이 중요한 서비스 지원 GPU 한정. 분할 조합이 정해져 있고 변경 시 작업 중단

셋의 차이를 한 문장으로 하면 이렇습니다. 패스스루는 안 나누고, vGPU는 시간으로 나누고, MIG는 공간으로 나눕니다. 그래서 "다른 테넌트의 부하와 무관하게 일정한 성능을 보장해야 한다"가 요구사항이면 MIG가 답이고, "여러 사용자에게 적당한 그래픽 성능을 싸게 주고 싶다"면 vGPU가 답입니다.

GPU를 VM에 붙일 때 실제로 막히는 지점

패스스루를 하려면 IOMMU(인텔 VT-d / AMD-Vi)가 필요합니다. 장치가 DMA로 아무 메모리나 읽지 못하게 주소를 변환·차단하는 하드웨어이고, 이게 없으면 장치 직접 할당은 보안상 성립하지 않습니다.

현장에서 자주 막히는 건 IOMMU 그룹입니다. 메인보드 배선 구조상 GPU와 다른 장치가 같은 그룹에 묶여 있으면, 그 그룹 전체를 함께 할당해야 해서 원하는 장치만 떼어낼 수 없습니다. 메인보드를 바꾸거나 슬롯을 옮겨야 풀리는 경우가 많습니다. 

# IOMMU 활성화 확인 (커널 파라미터)
$ cat /proc/cmdline | grep -o 'intel_iommu=on'

# IOMMU 그룹 구성 확인 — 같은 그룹의 장치는 함께 할당해야 한다
$ for d in /sys/kernel/iommu_groups/*/devices/*; do
    echo "Group $(basename $(dirname $(dirname $d))): $(basename $d)"
  done | sort -V

현장에서 반복되는 실수

느리다고 vCPU를 늘린다

가장 흔하고 가장 역효과가 큰 조치입니다. 원인이 CPU Ready라면 vCPU를 늘리는 건 불을 끄려고 기름을 붓는 격입니다. 줄이는 게 답인 경우가 많습니다.

게스트 도구를 설치하지 않는다

virtio 드라이버나 VMware Tools 없이 돌아가는 VM은 에뮬레이션 경로로 I/O를 합니다. 성능이 몇 배 차이 나고, 벌루닝도 동작하지 않습니다. 가장 적은 노력으로 가장 큰 효과를 보는 조치입니다.

스냅샷을 지우지 않는다

"혹시 몰라서" 남긴 스냅샷이 몇 달째 쌓여 델타가 원본보다 커진 상태를 자주 봅니다. 성능도 문제지만 통합 작업 자체가 위험해집니다. 작업용 스냅샷은 수명을 정해두고 관리하세요.

하이퍼스레딩을 물리 코어로 센다

논리 프로세서 64개를 코어 64개로 계산하면 실제 오버커밋 비율이 두 배가 됩니다. 사이징 문서에서 이 혼동이 있으면 운영 단계에서 반드시 문제가 터집니다.

메모리를 CPU처럼 오버커밋한다

"CPU도 3:1로 하는데 메모리도 되겠지"가 통하지 않습니다. CPU는 느려지고 말지만 메모리는 스와핑으로 넘어가는 순간 서비스가 사실상 정지합니다.

모니터링을 게스트 안에서만 한다

게스트 에이전트만 보면 CPU Ready, 호스트 메모리 압박, 데이터스토어 경합이 전부 보이지 않습니다. 호스트·클러스터 지표와 게스트 지표를 함께 봐야 그림이 완성됩니다.

3편 — 실전 운영과 클라우드 내부

1편이 원리, 2편이 자원 분할이었다면 3편은 "이걸로 서비스를 어떻게 안 죽게 운영하는가"입니다.

  • 라이브 마이그레이션의 내부 동작 — 프리카피, 더티 페이지 추적, 스톱앤카피 구간
  • HA·FT·클러스터 — 호스트 장애 시 실제로 벌어지는 일과 스플릿 브레인
  • 백업·복제·재해복구 설계, RPO/RTO에서 역산하는 방법
  • 퍼블릭 클라우드 내부 — AWS Nitro, Azure, GCP가 하이퍼바이저를 다루는 방식
  • 컨테이너와의 경계 — KubeVirt, Kata Containers, 그리고 언제 무엇을 쓰는가
  • 가상화 보안 — VM 탈출, 사이드채널, 테넌트 격리 설계
