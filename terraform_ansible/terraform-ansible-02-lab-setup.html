세 구역으로 나누는 이유

① 컨트롤 머신은 코드를 쓰고 도구를 실행하는 곳입니다. ② 로컬 노드는 Ansible이 SSH로 들어가 설정을 바꿔 볼 서버들로, 망가뜨려도 몇 초 만에 다시 만들 수 있고 돈이 들지 않습니다. ③ 클라우드 계정은 Terraform이 진짜 API를 호출해야 하는 실습에만 짧게 씁니다. 이렇게 나누면 실습 비용의 대부분을 0원으로 만들 수 있고, 클라우드 사용 시간이 짧아져 사고 확률도 낮아집니다.

왜 Ubuntu 24.04인가

ansible-core 2.21은 컨트롤 노드에 Python 3.12~3.14를 요구합니다. Ubuntu 24.04는 Python 3.12가 기본이라 추가 작업이 없습니다. Ubuntu 22.04(Python 3.10)를 쓰면 pip가 조용히 예전 버전의 ansible-core를 설치해 버려 강의 내용과 결과가 달라질 수 있습니다(12장 FAQ).

CRLF가 만드는 이상한 오류

Windows 편집기에서 저장된 셸 스크립트가 CRLF 줄바꿈이면 리눅스에서 /bin/bash^M: bad interpreter 오류가 납니다. 10장의 .editorconfig와 .gitattributes로 리포 차원에서도 LF를 강제합니다.

2-3. 랩 전용 SSH 키

Ansible이 대상 노드에 접속할 때 쓸 키를 랩 전용으로 따로 만듭니다. 평소 GitHub나 회사 서버에 쓰는 키를 재사용하지 않는 이유는, 랩 키는 컨테이너 이미지와 VM 설정에 공개키가 박히고 여러 번 재생성되는 “일회용” 성격이기 때문입니다. 키를 분리해 두면 랩 키가 어디에 퍼져도 실제 업무 접근 권한에는 영향이 없습니다.

mkdir -p ~/iac-lab/lab/keys
ssh-keygen -t ed25519 -N "" -C "iac-lab" -f ~/iac-lab/lab/keys/lab_ed25519
ls -l ~/iac-lab/lab/keys
# lab_ed25519      ← 개인키 (Git에 절대 올리지 않음, 10장 .gitignore)
# lab_ed25519.pub  ← 공개키 (대상 노드에 심는다)

비밀번호 없는 키(-N "")는 로컬 랩 노드 전용이기 때문에 허용합니다. 실제 서버용 키에는 반드시 암호를 걸고 ssh-agent를 씁니다.

3Terraform 설치 (tenv)

“최신 버전 하나”가 아니라 “프로젝트가 요구하는 버전”을 설치한다

왜 버전 관리 도구를 쓰는가

MSP 엔지니어는 고객사마다 서로 다른 시기에 만들어진 Terraform 코드를 다룹니다. A사 코드는 1.5.7, B사는 1.14, 새 프로젝트는 1.16으로 고정되어 있는 식입니다. state 파일에는 마지막으로 apply한 Terraform 버전이 기록되고, 새 버전으로 한 번 apply하면 그 state를 구버전에서 다시 열 수 없는 경우가 있습니다. 그래서 “내 PC에 깔린 아무 버전”으로 실행하는 것은 위험합니다.

tenv는 Terraform, OpenTofu, Terragrunt 등의 여러 버전을 설치해 두고, 디렉터리에 있는 버전 파일(.terraform-version)이나 코드의 required_version을 읽어 알맞은 버전을 자동으로 골라 실행해 주는 도구입니다. 예전에 많이 쓰던 tfenv의 후속격이며 Go로 작성된 단일 바이너리입니다.

3-1. tenv 설치

# GitHub 최신 릴리스의 .deb 설치 (x86_64. ARM 리눅스는 amd64 → arm64)
LATEST_VERSION=$(curl -s https://api.github.com/repos/tofuutils/tenv/releases/latest | jq -r .tag_name)
curl -fLO "https://github.com/tofuutils/tenv/releases/latest/download/tenv_${LATEST_VERSION}_amd64.deb"
sudo dpkg -i "tenv_${LATEST_VERSION}_amd64.deb"
tenv --version

snap(sudo snap install tenv)이나 Homebrew on Linux로도 설치할 수 있습니다. LATEST_VERSION이 null로 나오면 GitHub API 호출 한도에 걸린 것입니다(FAQ 16). 릴리스 페이지에서 버전 번호를 보고 직접 넣으세요.

brew install tenv
tenv --version

Homebrew로 terraform을 이미 설치했다면 brew uninstall terraform으로 지워 두세요. PATH에서 tenv의 실행 파일과 충돌합니다.

3-2. Terraform 1.16 설치와 버전 고정

# 1.16 계열의 최신 패치 버전 설치
tenv tf install "~> 1.16.0"
tenv tf list                    # 설치된 버전 목록 확인 (예: 1.16.5)

# 리포 최상위에 버전 파일을 둔다 → 이 디렉터리 아래에서는 항상 이 버전
cd ~/iac-lab
echo "1.16.5" > .terraform-version   # tenv tf list에 나온 실제 번호로
terraform version
Terraform v1.16.5
on linux_amd64

tenv가 버전을 고르는 우선순위는 대략 다음과 같습니다: 환경변수 TFENV_TERRAFORM_VERSION → 현재부터 상위로 올라가며 찾은 .terraform-version → 코드의 required_version 제약 → 전역 기본값. 즉 고객사 리포마다 .terraform-version만 커밋해 두면, 디렉터리를 옮겨 다니는 것만으로 버전이 바뀝니다.

코드 쪽 버전 제약도 함께

terraform {
  required_version = "~> 1.16.0"   # 1.16.x만 허용 (1.17 이상 거부)
}

.terraform-version은 “어떤 바이너리를 실행할지”, required_version은 “이 코드를 어떤 버전이 실행해도 되는지”를 정합니다. 앞의 것은 사람의 PC를 맞추고, 뒤의 것은 CI나 동료가 엉뚱한 버전으로 실행하는 것을 막습니다. 둘 다 둡니다.

3-3. OpenTofu도 함께 (선택)

tenv tofu install "~> 1.13.0"
tofu version
# 리포별로 .opentofu-version 파일을 두면 같은 방식으로 고정된다

고객사가 OpenTofu를 표준으로 쓰는 경우를 대비해 미리 설치해 두면 좋습니다. 이 강의의 기본 명령은 terraform입니다.

3-4. 편의 설정: 프로바이더 캐시와 자동완성

Terraform은 디렉터리마다 terraform init을 할 때 프로바이더를 내려받습니다. AWS 프로바이더는 수백 MB라서, 실습 디렉터리가 늘어날수록 디스크와 시간이 낭비됩니다. 공유 캐시를 켜 두면 한 번 받은 프로바이더를 재사용합니다.

mkdir -p ~/.terraform.d/plugin-cache
cat >> ~/.terraformrc <<'TFRC'
plugin_cache_dir = "$HOME/.terraform.d/plugin-cache"
TFRC

terraform -install-autocomplete   # 셸 자동완성 (새 셸에서 적용)
공식 패키지 저장소 방식은?

HashiCorp는 apt/yum 저장소와 Homebrew tap도 제공합니다. 회사 보안 정책상 서드파티 도구(tenv) 설치가 막힌 서버에서는 이 방식을 씁니다. 다만 시스템에 한 버전만 깔리므로 여러 고객사 코드를 다루는 개인 PC에는 tenv가 유리합니다. 어떤 방식이든 tenv와 공식 배포본은 서명·체크섬 검증을 거칩니다. 출처를 알 수 없는 미러에서 바이너리를 받지 마세요.

4첫 apply: 비용 0원 실습

클라우드 계정 없이 init → plan → apply → destroy 한 바퀴

1편에서 본 작업 흐름을 실제로 돌려 봅니다. 클라우드 대신 random(임의 값 생성)과 local(로컬 파일 생성) 프로바이더를 씁니다. 이 둘은 외부 API를 호출하지 않으므로 어디서든 비용 없이 동작합니다.

~/iac-lab/terraform/00-hello-local/main.tf
terraform {
  required_version = "~> 1.16.0"
  required_providers {
    random = { source = "hashicorp/random", version = "~> 3.7" }
    local  = { source = "hashicorp/local",  version = "~> 2.5" }
  }
}

# 두 단어로 된 임의 이름 (예: "brave-otter")
resource "random_pet" "name" {
  length = 2
}

# random_pet 결과를 참조 → Terraform이 순서를 스스로 정한다
resource "local_file" "hello" {
  filename = "${path.module}/out/hello.txt"
  content  = "안녕하세요, ${random_pet.name.id}! IaC 랩에 오신 것을 환영합니다.\n"
}

output "pet_name" {
  value = random_pet.name.id
}
cd ~/iac-lab/terraform/00-hello-local
terraform init       # 프로바이더 2개 다운로드, .terraform.lock.hcl 생성
terraform plan       # Plan: 2 to add, 0 to change, 0 to destroy.
terraform apply      # yes 입력 → out/hello.txt 생성
cat out/hello.txt

pipx로 격리 설치하고, Python 버전부터 확인한다

먼저 알아둘 두 가지 이름

ansible-core는 엔진입니다. ansible, ansible-playbook 같은 명령과 ansible.builtin 모듈만 들어 있습니다. ansible(커뮤니티 패키지)은 ansible-core에 AWS·Azure·리눅스 관리·네트워크 장비 등 자주 쓰는 컬렉션 수십 개를 묶은 배포판입니다. 처음 배울 때는 커뮤니티 패키지가 편하고, 운영 환경에서는 ansible-core + 필요한 컬렉션만 버전 고정해 쓰는 쪽을 권합니다(16편).

Python 요구사항

2.21 (이 강의 기준)3.12 ~ 3.143.9 ~ 3.142026년 5월 출시

관리 노드 쪽에서 Rocky 9는 Python 3.9, Ubuntu 24.04는 3.12라서 둘 다 범위 안입니다. 컨트롤 노드는 반드시 3.12 이상이어야 합니다.

왜 pipx인가

방법장점문제
sudo apt install ansible간단배포판 시점의 버전에 묶임. 강의 기준보다 오래된 경우가 많음
sudo pip install ansible최신시스템 Python을 오염. Ubuntu 24.04는 PEP 668로 아예 거부
pipx install도구마다 전용 가상환경, 명령만 PATH에 노출, 업그레이드·제거가 깔끔사실상 없음 (권장)
프로젝트별 venv + requirements.txt프로젝트마다 버전 완전 고정매번 활성화 필요. CI·팀 표준화 단계에서 사용(20편)

5-1. 설치

# Homebrew python으로 venv를 만들도록 명시

--include-deps는 의존 패키지(ansible-core)가 가진 실행 파일까지 PATH에 노출하라는 옵션입니다. 커뮤니티 패키지 자체에는 실행 파일이 없고 실제 명령은 ansible-core에 들어 있기 때문에 이 옵션이 필요합니다.

Free plan은 과금 사고를 막아 주지만, 기간이 끝나거나 크레딧이 바닥나면 계정과 그 안의 데이터가 닫힙니다. 실습용으로는 오히려 장점이지만, 이 계정에 중요한 것을 두지 마세요. 그리고 리소스를 켜 둔 채 잊으면 카드 대신 크레딧이 녹아 뒤 편의 실습을 못 하게 됩니다. 정리 습관(9장)은 Free plan에서도 똑같이 필요합니다. 2025년 7월 이전에 만든 계정은 예전 프리 티어(12개월 무료 사용량) 규칙을 따릅니다.

실습 비용 사고는 거의 항상 같은 모양입니다. 무언가를 만들고, 실습이 끝나 노트북을 덮고, 그 무언가가 한 달 동안 돌아갑니다. 혹은 키가 유출되어 누군가 내 계정으로 GPU 인스턴스를 띄웁니다. 아래 다섯 겹의 장치를 오늘 모두 걸어 둡니다.

1겹 · 예산 알림

돈이 나가기 시작하면 메일이 온다.

2겹 · 이상 탐지

평소와 다른 지출 패턴을 자동 감지.

3겹 · 태그

무엇이 실습용인지, 언제 지워도 되는지 리소스에 적는다.

4겹 · destroy 의식

실습이 끝나면 정해진 순서로 정리하고 확인한다.

5겹 · 주간 점검

모든 리전을 훑어 남은 리소스를 찾는다.

0겹 · 키를 만들지 않는다

장기 액세스 키가 없으면 유출될 키도 없다(7장).

9-1. AWS 예산 알림 (Paid plan이라면 필수, Free plan이어도 권장)

  1. 콘솔 → Billing and Cost Management → Budgets → Create budget.
  2. 템플릿 Zero spend budget: 1센트라도 청구되면 메일. 실습 계정에 가장 먼저 겁니다.
  3. 템플릿 Monthly cost budget: 예를 들어 월 10달러, 실제 비용 50%·80%·100%와 예측 비용 100%에서 알림.
  4. 알림 받을 이메일은 평소 확인하는 주소로. 회사 메일로 받는다면 스팸함 규칙도 확인합니다.

예산 자체를 Terraform으로 만들 수도 있습니다(aws_budgets_budget 리소스). 하지만 “Terraform으로 실수했을 때 나를 지켜 줄 장치”를 같은 Terraform state에 두면, destroy 한 번에 안전장치까지 사라집니다. 그래서 랩에서는 콘솔에서 따로 만들고 건드리지 않습니다. 25편에서 고객사 계정에 예산을 표준으로 배포할 때는 별도 state로 분리하는 방법을 다룹니다.

9-2. 비용 이상 탐지와 크레딧 확인

  • Cost Anomaly Detection: Billing 콘솔에서 서비스 단위 모니터를 만들고 일일 요약 알림을 받습니다. 예산이 “얼마 이상”을 본다면 이상 탐지는 “평소와 다름”을 봅니다.
  • 크레딧 잔액: 콘솔 홈의 Explore AWS 위젯과 Billing의 Credits 페이지. Free plan은 50%·25%·10% 시점에 메일이 옵니다.

9-3. Azure

  • Cost Management → Budgets에서 구독 단위 예산과 알림(실제·예측) 설정.
  • 무료 계정의 지출 한도는 켠 상태로 유지.
  • 실습 리소스는 반드시 실습용 리소스 그룹에 넣습니다. 리소스 그룹을 지우면 안의 것이 모두 지워지므로 정리가 쉽습니다.

#!/usr/bin/env bash
# iac-lab 환경 점검 — 2편 기준 (Terraform 1.16 / ansible-core 2.21)
set -u
PASS=0; FAIL=0; WARN=0
ok()   { printf '  \033[32mOK  \033[0m %s\n' "$1"; PASS=$((PASS+1)); }
ng()   { printf '  \033[31mFAIL\033[0m %s\n' "$1"; FAIL=$((FAIL+1)); }
wn()   { printf '  \033[33mWARN\033[0m %s\n' "$1"; WARN=$((WARN+1)); }
has()  { command -v "$1" >/dev/null 2>&1; }
ROOT="$(cd "$(dirname "$0")/.." && pwd)"

echo "[1] 기본 환경"
case "$ROOT" in
  /mnt/[a-z]/*) ng "리포가 Windows 드라이브($ROOT)에 있음 → WSL 홈으로 이동 (1장, FAQ 1)";;
  *)            ok "리포 위치: $ROOT";;
esac
for t in git jq curl ssh; do has "$t" && ok "$t" || ng "$t 없음 (2장)"; done
[ -f "$ROOT/lab/keys/lab_ed25519" ] && ok "랩 SSH 키" || ng "랩 SSH 키 없음 (2장)"

echo "[2] Terraform"
if has tenv; then ok "tenv $(tenv --version 2>/dev/null | head -n1)"; else wn "tenv 없음 (3장)"; fi
if has terraform; then
  V=$(cd "$ROOT" && terraform version -json 2>/dev/null | jq -r .terraform_version)
  case "$V" in 1.16.*) ok "terraform $V";; *) ng "terraform $V — 1.16.x 필요 (3장)";; esac
else ng "terraform 없음 (3장)"; fi
[ -f "$ROOT/.terraform-version" ] && ok ".terraform-version = $(cat "$ROOT/.terraform-version")" || wn ".terraform-version 없음 (3장)"

echo "[3] Ansible"
if has ansible; then
  AV=$(ansible --version 2>/dev/null | head -n1 | sed -E 's/.*core ([0-9.]+).*/\1/')
  PV=$(ansible --version 2>/dev/null | sed -nE 's/^ +python version = ([0-9]+\.[0-9]+).*/\1/p')
  case "$AV" in 2.21.*) ok "ansible-core $AV";; *) ng "ansible-core $AV — 2.21 필요 (5장)";; esac
  case "$PV" in 3.1[2-9]) ok "컨트롤 노드 Python $PV";; *) ng "Python $PV — 3.12 이상 필요 (5장)";; esac
  CFG=$(cd "$ROOT/ansible" 2>/dev/null && ansible --version 2>/dev/null | sed -nE 's/^ +config file = (.*)/\1/p')
  [ "$CFG" != "None" ] && [ -n "$CFG" ] && ok "ansible.cfg 적용: $CFG" || ng "ansible.cfg가 적용되지 않음 (6장, FAQ 1)"
else ng "ansible 없음 (5장)"; fi
has ansible-lint && ok "ansible-lint" || wn "ansible-lint 없음 (5장)"

echo "[4] 대상 노드"
if [ -d "$ROOT/ansible" ] && has ansible; then
  OUT=$(cd "$ROOT/ansible" && ansible lab -m ansible.builtin.ping -o 2>&1)
  N=$(printf '%s\n' "$OUT" | grep -c 'SUCCESS')
  [ "$N" -ge 2 ] && ok "ping 성공 노드 $N대" || ng "ping 성공 $N대 (6장)"
fi

echo "[5] 클라우드 (선택)"
if has aws; then
  ID=$(aws sts get-caller-identity --query Account --output text 2>/dev/null)
  [ -n "$ID" ] && ok "AWS 계정 $ID (프로필: ${AWS_PROFILE:-default}) — 내 실습 계정 맞는지 확인!" || wn "AWS 인증 안 됨 (7장)"
  env | grep -qE '^AWS_(ACCESS_KEY_ID|SECRET_ACCESS_KEY)=' && wn "AWS 키 환경변수가 설정되어 있음 — 의도한 것인지 확인 (7-5)"
else wn "aws CLI 없음 (7장)"; fi
if has az; then
  az account show --query name -o tsv >/dev/null 2>&1 && ok "Azure 로그인됨" || wn "Azure 로그인 안 됨 (8장, 선택)"
fi

echo "[6] 리포 품질 도구"
has pre-commit && ok "pre-commit" || ng "pre-commit 없음 (10장)"
[ -f "$ROOT/.git/hooks/pre-commit" ] && ok "pre-commit 훅 설치됨" || wn "pre-commit install 필요 (10장)"
has tflint && ok "tflint" || wn "tflint 없음 (10장)"

echo
printf '결과: OK %d / WARN %d / FAIL %d\n' "$PASS" "$WARN" "$FAIL"
[ "$FAIL" -eq 0 ]
