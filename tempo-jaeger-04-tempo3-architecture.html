4편 / 8편 Tempo 트랙 1/3 기준: Tempo 3.0.3

Tempo 3.0 아키텍처 해부쓰는 길과 읽는 길을 완전히 떼어 놓다

Tempo 3.0은 2.x의 핵심 부품이던 ingester를 없애고, 쓰기와 읽기를 서로 다른 부품이 맡도록 다시 설계했습니다. 아래 구성도에서 경로를 바꿔 데이터가 흐르는 길을 보고, 배포 모드를 바꿔 Kafka가 있을 때와 없을 때를 비교해 보세요. 부품을 클릭하면 역할이 나옵니다.

쓰기읽기압축·보존 관리

구성도는 공식 문서의 3.0 아키텍처를 단순화한 것입니다. monolithic 모드에서 점선 상자 안의 부품은 모두 tempo -target=all 한 프로세스 안에서 돕니다.

1

Tempo의 설계 목표

1편에서 Tempo를 "물류창고 방식"으로 소개했습니다. 색인을 만들지 않고, 싼 객체 스토리지에 트레이스를 차곡차곡 쌓아 두는 설계입니다. Tempo의 일은 결국 두 가지입니다. 스팬을 받아 Parquet 열 구조로 정리해 객체 스토리지에 넣는 것, 그리고 Trace ID나 TraceQL 조건으로 꺼내 주는 것입니다. 3.0은 이 두 일을 네 가지 목표에 맞춰 다시 짰습니다.

목표어떻게 이루나MSP에게 의미
싼 저장모든 트레이스 데이터를 객체 스토리지(S3, GCS, Azure Blob)에 저장보존 기간을 늘려도 비용 증가가 완만함. 3편의 OpenSearch 계산과 비교해 볼 만함
독립 확장microservices 모드에서 쓰기 경로와 읽기 경로를 분리조회 폭주가 수집을 멈추지 않고, 수집 폭주가 조회를 느리게 하지 않음
추가 복제 없는 내구성Kafka 호환 큐를 WAL로 사용. Kafka가 받았다고 확인하면 데이터는 안전하므로 복제 계수 1(RF1)로 운영2.x 대비 객체 스토리지 사용량이 크게 줄어듦 (9장)
효율적인 속성 조회열 지향 형식인 Parquet으로 블록 저장. 필요한 열만 읽음색인 없이도 TraceQL 검색이 실용적인 속도를 냄 (6장)
WAL이 뭐였더라

WAL(Write-Ahead Log, 선행 기록 로그)은 "본 작업을 하기 전에 일단 안전한 곳에 적어 두는" 기록입니다. 도중에 프로세스가 죽어도 이 기록을 다시 읽어 복구할 수 있습니다. Tempo 3.0에서는 Kafka가 클러스터 전체의 WAL 역할을 맡습니다. 2편에서 Jaeger가 Kafka를 "유실 대신 지연을 택하는 완충 장치"로 선택 사항으로 두었다면, Tempo 3.0 microservices 모드에서 Kafka는 필수 뼈대입니다.

2

2.x에서 3.0으로

인터넷의 Tempo 자료 대부분은 2.x 구조를 설명합니다. 무엇이 바뀌었는지 먼저 비교해 두면 옛 자료를 걸러 읽을 수 있습니다.

2.x의 부품·개념3.0에서
ingester완전히 제거. 최근 데이터 조회는 live-store가, 블록 만들기는 block-builder가 나눠 맡음
compactor제거. backend scheduler(작업 배정)와 backend worker(작업 실행)가 압축·보존을 맡음
복제 계수 3 (RF3)RF1. 같은 데이터를 세 번 쓰는 대신 Kafka의 내구성에 기댐
scalable single binary 모드제거. monolithic과 microservices 두 모드만 남음
metrics-generator가 distributor에서 직접 받음microservices 모드에서는 Kafka에서 독립적으로 소비
vParquet3 블록, v2 블록 인코딩제거. vParquet4가 기본, vParquet5는 선택(운영 가능 등급)
OpenCensus 수신제거. OTLP로 이전
Project Rhythm이라는 이름을 보면

이 새 구조는 개발 중에 "Project Rhythm"이라 불렸고 2.9·2.10에서 실험 기능으로 먼저 나왔습니다. 3.0에서는 기본값이자 유일한 수집 경로가 되었습니다. 2.9·2.10 시절 "Rhythm을 켜는 방법" 글은 이제 설정 이름이 달라졌을 수 있으니 3.0 문서와 대조하세요.

3

쓰기 경로 따라가기

microservices 모드에서 스팬 하나가 객체 스토리지에 도착하기까지의 여정입니다. 단계를 눌러 보세요.

block-builder의 "하드 컷"

block-builder는 정해진 주기(consume_cycle_duration, 기본 5분)마다 Kafka에서 읽은 스팬을 블록으로 만듭니다. 주기가 끝나면 트레이스가 끝났든 말든 무조건 잘라서 블록을 만듭니다. 그래서 두 주기에 걸친 트레이스는 서로 다른 블록에 나뉘어 저장됩니다. block-builder는 "트레이스가 끝났다"는 개념 자체가 없고, 조각을 합치는 일은 조회할 때 querier가 합니다. 1편에서 "트레이스에는 끝이라는 개념이 없다"고 한 것과 같은 이야기입니다.

블록을 안전하게 올리는 순서

block-builder가 블록을 객체 스토리지에 올리다 죽으면 어떻게 될까요? Tempo는 파일을 올리는 순서와 결정적 블록 ID로 이 문제를 풉니다. 블록 ID는 파티션, 테넌트, Kafka 오프셋 범위로 계산되므로 같은 데이터로 다시 만들면 같은 ID가 나옵니다. 각 단계의 "여기서 죽기" 버튼을 눌러 결과를 확인해 보세요.

중복 스팬도 알아서 걸러 냅니다

다시 읽기(rewind) 때문에 같은 스팬이 두 번 들어올 수 있어서, block-builder는 블록을 만들 때 트레이스 안에서 span ID와 span kind로 중복을 제거합니다. 제거된 수는 tempo_block_builder_spans_deduped_total 메트릭으로 확인합니다.

4

live-store와 파티션 링

block-builder가 블록을 올리기까지는 몇 분이 걸립니다. 그 사이에 들어온 트레이스는 객체 스토리지에 없으니, 방금 난 장애의 트레이스를 보려면 다른 곳이 필요합니다. 그 빈틈을 채우는 것이 live-store입니다. Kafka에서 block-builder와 따로 읽어 최근 트레이스를 메모리와 로컬 디스크에 들고 있다가 조회에 답합니다.

live-store 안에서 트레이스가 거치는 단계

1. 활성스팬이 계속 들어오는 중. 메모리에 트레이스 단위로 모음Trace ID 조회 가능
2. 유휴max_trace_idle(기본 10초) 동안 새 스팬이 없으면 유휴 상태로 전환WAL로 내려쓸 차례
3. 로컬 WALParquet 형식으로 로컬 디스크에 기록TraceQL 검색 가능
4. 완료 블록WAL을 블록으로 자름. complete_block_timeout(기본 20분) 동안 보관 후 정리이후엔 객체 스토리지에서 조회
오래 걸리는 트레이스가 조각나 보인다면

배치 작업처럼 스팬 사이 간격이 10초를 넘는 트레이스는 live-store에서 여러 조각으로 내려써질 수 있습니다. max_trace_idle을 늘리면 한 번에 모일 가능성이 커지지만 메모리 사용량도 늘어납니다. 조각이 나뉘어도 조회할 때 합쳐지므로 데이터가 사라지는 것은 아닙니다.

파티션 링: 누가 어느 파티션을 맡는가

Tempo는 Kafka 파티션과 1:1로 대응하는 Tempo 파티션을 따로 관리합니다. 이 목록과 상태를 담은 것이 파티션 링이고, memberlist(gossip 프로토콜)로 클러스터 전체에 퍼집니다. 파티션마다 가용 영역(zone)당 live-store 하나가 주인입니다. distributor는 링을 보고 active 파티션에만 쓰고, querier는 파티션마다 live-store 하나에서만 답을 받으면 됩니다. 아래에서 확장·축소 시나리오를 눌러 보세요.

3.0의 새 기본값: 틀린 답보다 오류가 낫다

live-store가 Kafka를 따라잡지 못해 밀려 있는데(lag) 그 시간대를 조회하면 결과가 빠질 수 있습니다. 3.0부터 live_store.fail_on_high_lag가 기본으로 켜져서 이럴 때 불완전한 결과 대신 오류를 돌려줍니다. 같은 이유로 query_frontend.query_end_cutoff 기본값이 30초가 되어 가장 최근 30초는 조회에서 뺍니다. 고객사에서 "방금 보낸 트레이스가 안 보여요", "조회가 가끔 오류 나요"라는 문의가 오면 이 두 설정과 tempo_live_store_lagged_requests_total 메트릭을 먼저 확인하세요.

5

읽기 경로 따라가기

조회 요청은 query-frontend가 받아 잘게 나눈 뒤(샤딩) querier들에게 나눠 줍니다. querier는 최근 데이터는 live-store에, 오래된 데이터는 객체 스토리지에 물어보고, query-frontend가 결과를 합쳐 돌려줍니다. 여기서 핵심은 시간 범위에 따라 묻는 곳이 달라진다는 점입니다.

설정기본값의미
query_backend_after15m이보다 최근 구간은 live-store에서만, 이보다 오래된 구간은 객체 스토리지에서만 검색
query_end_cutoff30s (3.0부터)가장 최근 이 시간만큼은 결과가 불완전할 수 있어 조회에서 제외
target_bytes_per_job약 100MB작업 하나가 맡을 데이터 크기. 작을수록 병렬성은 높고 오버헤드도 큼
concurrent_jobs2000쿼리 하나가 동시에 큐에 올릴 수 있는 작업 수. 한 테넌트의 큰 쿼리가 클러스터를 독차지하지 않게 함

Trace ID로 찾을 때: 블룸 필터의 역할

색인이 없는데 Trace ID 하나를 어떻게 빨리 찾을까요? 블록마다 붙은 블룸 필터가 "이 블록에는 그 ID가 확실히 없다"를 아주 싸게 알려 주기 때문입니다. 블룸 필터는 "없다"는 틀리지 않지만 "있을 수도"는 가끔 틀립니다(거짓 양성). 단계 버튼으로 querier의 동작을 따라가 보세요.

6

블록 속 들여다보기

블록은 객체 스토리지의 <테넌트ID>/<블록ID>/ 폴더 하나입니다. 안에는 이런 파일이 있습니다.

파일역할
meta.json블록 ID, 테넌트, 시작·종료 시각, 트레이스 수, replaces. 이 파일이 생겨야 블록이 조회 대상이 됨
data.parquet스팬 데이터 본체 (열 지향)
블룸 필터Trace ID가 이 블록에 없는지 빠르게 판별
인덱스Trace ID가 data.parquet의 어느 row group에 있는지 알려 줌
nocompact.flg업로드 중 압축 작업이 건드리지 못하게 하는 임시 표시

열 지향이 검색을 빠르게 하는 원리

Parquet 파일에서는 한 행이 스팬 하나이고, 필드마다 열이 따로 저장됩니다. 쿼리를 골라 보면 어떤 열을 읽어야 하는지 표시됩니다. 주황색이 읽는 열이고 막대 높이는 열의 상대적 크기입니다(개념을 위한 가상 값이며, 실제 스키마는 더 깊게 중첩되어 있습니다).

읽는 양

일부 필드만 자기 열을 가집니다. Trace ID, 스팬 이름, 상태, 소요 시간 같은 고유 필드와 리소스의 service.name 등입니다. 나머지 속성은 모두 범용 Attrs 열에 키-값 쌍으로 들어가서, 그 속성으로 검색하면 큰 열을 훑어야 합니다. 그래서 자주 검색하는 속성을 전용 열로 빼 두는 것이 Tempo 검색 튜닝의 첫 번째 수단입니다.

storage:
  trace:
    block:
      version: vParquet4              # 3.0 기본값
      parquet_dedicated_columns:      # live-store, block-builder 모두 이 설정을 사용
        - name: http.route
          type: string
          scope: span
        - name: k8s.namespace.name
          type: string
          scope: resource
블록 형식3.0에서의 상태비고
vParquet3제거 (2.10에서 사용 중단 예고)3.0으로 올리기 전에 해당 블록이 보존 기간을 지나 사라졌는지 확인
vParquet4기본값전용 열 지정 가능
vParquet5운영 가능, 선택 사항범위(scope)당 전용 문자열 열이 20개로 늘었고, 이벤트 범위 열·배열 전용 열 등을 지원. 켜면 새 블록만 v5로 쓰고 기존 v4 블록은 그대로 읽음
어떤 속성을 전용 열로 뺄까

tempo-cli analyse blocks 명령이 실제 블록을 분석해 크기가 크고 자주 쓰이는 속성과 적절한 전용 열 개수를 추천해 줍니다. 5편 TraceQL과 6편 운영 편에서 직접 써 봅니다.

7

백엔드 스케줄러와 워커

block-builder는 5분마다 테넌트·파티션별로 작은 블록을 만들어 냅니다. 작은 블록이 수만 개 쌓이면 조회할 때 열어 볼 파일이 너무 많아집니다. 그래서 작은 블록을 큰 블록으로 합치고(압축), 오래된 블록을 지우는(보존) 관리 작업이 필요합니다. 3.0에서는 이 일을 두 부품이 나눠 맡습니다.

backend scheduler (1개)
  • 할 일(job)을 만들고 워커에게 배정
  • 작업 진행 상황을 한곳에서 추적하고, 실패한 작업은 자동으로 다시 배정
  • 한 번에 하나만 실행해야 하는 싱글턴
  • /status/backendscheduler에서 작업 현황 확인
backend worker (여러 개)
  • 상태를 갖지 않는 작업 실행기
  • 스케줄러에게 작업을 받아 실행하고 결과를 보고
  • 블록 목록(blocklist) 갱신도 분담
  • 블록이 많아 압축이 밀리면 워커를 늘림
작업 종류하는 일
compaction작은 블록을 큰 블록으로 합쳐 조회 시 열어 볼 블록 수를 줄임
retention보존 기간(compaction.block_retention, 기본 336h = 14일)이 지난 블록 삭제
redaction (3.0 신규)개인정보가 담긴 트레이스를 보존 기간을 기다리지 않고 블록을 다시 써서 제거. tempo-cli redact로 요청
MSP 관점: 삭제 요청 대응

고객사에서 "특정 사용자의 개인정보가 트레이스에 찍혔으니 지워 달라"는 요청이 오면, 2.x에서는 보존 기간이 끝나기를 기다리거나 블록을 직접 다뤄야 했습니다. 3.0의 redaction 작업으로 대응 절차를 표준화할 수 있습니다. 물론 가장 좋은 방법은 수집 단계에서 애초에 넣지 않는 것입니다(3편 10장).

8

배포 모드와 확장

모든 부품은 tempo 바이너리 하나에 들어 있고, -target 값이 그 프로세스에서 어떤 부품을 돌릴지 정합니다. Jaeger v2가 설정 파일로 역할을 정했다면, Tempo는 target으로 정합니다.

monolithic (-target=all, 기본값)microservices (부품별 target)
Kafka필요 없음. distributor가 같은 프로세스의 live-store로 바로 전달필수 (Apache Kafka, Redpanda, WarpStream 등 Kafka 호환)
블록 만들기live-store가 직접 객체 스토리지로 내려씀block-builder
잘 맞는 곳시작 단계, 개발 환경, 적거나 중간 정도의 트래픽운영 환경(공식 권장), 대용량, 고가용성
한계부품이 자원을 공유해 조회 폭주가 수집에 영향. 대용량에서 메모리 부족 위험부품 수가 많고 Kafka 운영 부담이 추가됨

부품별 확장 방법 (공식 가이드)

부품확장 방식기준
distributor수평상태 없음. 수집량에 따라
block-builder수평Kafka 파티션 수가 상한. 데이터 양에 따라
live-store수평Kafka 파티션 수가 상한. 최근 데이터 조회량과 메모리에 따라

metrics-generator수평트레이스 양과 생성하는 시계열 수에 따라
Kafka 파티션 수는 처음부터 넉넉하게

block-builder와 live-store는 파티션 수보다 많이 늘릴 수 없습니다. 파티션을 나중에 늘릴 수는 있지만 live-store 확장 절차(4장의 pending → active)와 맞물려 번거롭습니다. 고객사 트래픽 성장 예측을 반영해 처음부터 여유 있게 잡으세요. 파티션 설계와 실제 배포는 6편에서 다룹니다.

9

RF3에서 RF1로, 비용 계산

2.x는 ingester 세 곳에 같은 데이터를 복제(RF3)했고, 각 ingester가 블록을 만들어 올렸기 때문에 객체 스토리지에 2~2.5배의 중복 데이터가 생겼습니다(압축이 일부 합쳐 주지만 완전하지는 않았습니다). 3.0은 트레이스를 ID 기준으로 Kafka 파티션 하나에만 보내고, 블록은 정확히 한 번 만듭니다. 차이를 계산해 보세요.

단가는 예시입니다. 실제 요금은 클라우드, 리전, 스토리지 등급, 요청(API 호출) 비용에 따라 달라집니다. 3.0은 대신 Kafka 클러스터 비용이 새로 생기므로(보존 기간은 보통 수 시간~하루로 짧음) 두 비용을 함께 비교하세요.

13

정리와 다음 편

  1. Tempo 3.0은 ingester와 compactor를 없애고 쓰기(distributor → Kafka → block-builder)와 읽기(query-frontend → querier → live-store·객체 스토리지)를 분리했습니다.
  2. Kafka가 WAL 역할을 하므로 RF1로 운영하며, 트레이스는 ID 기준으로 한 파티션에 모이고 블록은 정확히 한 번 만들어집니다.
  3. block-builder는 주기마다 하드 컷으로 블록을 만들고, 올리는 순서와 결정적 블록 ID 덕분에 도중에 죽어도 유실·중복이 없습니다.
  4. 최근 15분은 live-store, 그 이전은 객체 스토리지에서 찾습니다. Trace ID는 블룸 필터로, 속성 검색은 Parquet 열 읽기로 풀고, 자주 찾는 속성은 전용 열로 빼 둡니다.
  5. monolithic은 Kafka 없이 한 프로세스, microservices는 Kafka 위에서 부품별 확장. block-builder와 live-store는 Kafka 파티션 수가 상한입니다.
다음 편

5편 · TraceQL 완전 정복

6장에서 본 "어떤 열을 읽느냐"가 곧 TraceQL 쿼리 비용입니다. 스팬 조건과 스팬셋, 부모·자식·형제 관계로 찾는 구조 연산자, 집계, 그리고 3.0에서 GA가 된 TraceQL metrics(rate, quantile_over_time, 비교 연산자)까지 직접 쿼리를 입력하며 익힙니다. 3.0에서 바뀐 배열 비교 규칙도 함께 다룹니다.
