NetworkPolicy와 네트워크 보안 계층

4편의 네트워크 모델은 “모든 Pod는 서로 통신할 수 있다”에서 출발합니다. 보안은 그 반대, “허락한 것만 통신한다”에서 출발해야 합니다. 이 간극을 메우는 도구가 NetworkPolicy인데, 표준 NetworkPolicy는 거부 규칙도, 클러스터 범위도, 로그도, 우선순위도 없습니다. 이 편은 표준이 못 하는 것을 클러스터 범위 정책, CNI 확장 정책, 벤더 기능, 이그레스 통제로 어떻게 채우는지, 그리고 3편 스모크 테스트에서 EKS가 NOT-enforced였던 문제를 어떻게 고치는지 다룹니다.

기준: Kubernetes v1.37 · network-policy-api v0.2(ClusterNetworkPolicy v1alpha2) 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 150분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

읽는 법과 목표

쉬운 말로 클러스터를 회사 건물로 보면, NetworkPolicy는 각 부서(네임스페이스)가 자기 사무실 문에 붙이는 “출입 허용 명단”입니다. 명단을 붙이는 순간 명단에 없는 사람은 못 들어오지만, 명단은 허용만 적을 수 있고 “이 사람은 절대 안 됨”은 못 적습니다. 그래서 건물 보안팀(클러스터 관리자)이 모든 부서보다 먼저 보는 규칙(Admin 계층)과, 부서가 명단을 안 붙였을 때 적용되는 기본 규칙(Baseline 계층)이 따로 필요합니다. 건물 밖으로 나가는 출구 통제(이그레스)는 또 다른 문제입니다.

이 편을 마치면 할 수 있는 것

  • NetworkPolicy의 선택·격리·허용 규칙을 정확히 해석하고, 흔한 YAML 실수(AND·OR 혼동, DNS 누락)를 찾아낼 수 있습니다.
  • ClusterNetworkPolicy(옛 ANP·BANP)의 Admin·Baseline 계층과 Accept·Deny·Pass 동작으로 클러스터 공통 가드레일을 설계할 수 있습니다.
  • Calico·Cilium·OVN-K의 확장 정책(거부, 순서, L7, FQDN, 감사)을 비교해 필요한 곳에 쓸 수 있습니다.
  • EKS·AKS·GKE·OpenShift·RKE2의 정책 엔진 현황을 알고, 기본 거부를 단계적으로(관찰 → 시험 → 적용) 도입할 수 있습니다.
  • NAT·이그레스 게이트웨이·EgressIP·프록시·클라우드 방화벽을 조합해 이그레스를 통제할 수 있습니다.
1

NetworkPolicy 정밀 이해

규칙 다섯 줄

  1. 선택되면 격리된다. 어떤 NetworkPolicy의 podSelector가 Pod를 고르고 policyTypes에 Ingress가 있으면, 그 Pod의 들어오는 방향은 “명시적으로 허용된 것만” 받는 상태가 됩니다. 아무 정책도 고르지 않은 Pod는 전부 허용입니다.
  2. 허용만 있고, 더해진다. 정책끼리는 합집합입니다. 거부 규칙도, 우선순위도 없습니다. 정책 하나가 막고 다른 하나가 열면 열립니다.
  3. 방향은 따로. Ingress와 Egress는 별개로 격리됩니다. 양쪽 끝 Pod 모두에서 허용돼야 연결이 됩니다(출발 Pod의 Egress, 도착 Pod의 Ingress).
  4. 상대는 세 종류. podSelector(같은 네임스페이스), namespaceSelector, ipBlock(CIDR). 한 항목 안에 namespaceSelector와 podSelector를 같이 쓰면 AND, 항목을 나누면 OR입니다.
  5. 응답은 자동. 허용된 연결의 응답 패킷은 별도 규칙 없이 통과합니다(상태 추적).
AND와 OR: 들여쓰기 한 칸이 보안 경계를 바꾼다
ingress:
- from:
  - namespaceSelector: {matchLabels: {team: a}}
    podSelector: {matchLabels: {app: frontend}}     # 한 항목: team=a 네임스페이스의 frontend Pod만 (AND)
---
ingress:
- from:
  - namespaceSelector: {matchLabels: {team: a}}     # 항목 1: team=a 네임스페이스의 모든 Pod
  - podSelector: {matchLabels: {app: frontend}}     # 항목 2: 같은 네임스페이스의 frontend Pod (OR)

못 하는 것결과채우는 방법
명시적 거부“이것만은 막아라”를 쓸 수 없음. 다른 정책이 열면 열림ClusterNetworkPolicy Deny, Calico·Cilium 거부 정책
클러스터 범위모든 네임스페이스 공통 규칙을 한 번에 못 씀. 네임스페이스마다 복제ClusterNetworkPolicy, GlobalNetworkPolicy, CiliumClusterwideNetworkPolicy

도메인 이름외부는 IP·CIDR로만. 클라우드 서비스처럼 IP가 바뀌는 대상에 취약Cilium toFQDNs, OVN EgressFirewall dnsName, EKS ApplicationNetworkPolicy(Auto Mode), GKE FQDN 정책, AKS ACNS
L7HTTP 경로·메서드 단위 통제 불가Cilium L7, 서비스 메시 인가
Service 기준 선택Service가 아닌 Pod 레이블로만 고름(ClusterIP는 DNAT 뒤 Pod 기준으로 판정)레이블 설계로 해결
노드·호스트 트래픽Pod가 자기 노드에서 오는 트래픽(kubelet 프로브 등)을 막을 수 없음. hostNetwork Pod에는 적용 안 됨호스트 정책(Calico HostEndpoint, Cilium host policy)
함정: ipBlock과 SNAT ipBlock은 Pod가 실제로 보는 출발지 IP 기준입니다. 외부 클라이언트를 IP로 허용하려 해도, 6·7편에서 본 것처럼 externalTrafficPolicy: Cluster나 L7 프록시를 거치면 출발지는 노드나 프록시 IP로 바뀌어 있습니다. 외부 출발지 기반 통제는 LB의 loadBalancerSourceRanges나 게이트웨이 정책에서 하는 편이 맞습니다.

클러스터 범위 정책: ANP에서 ClusterNetworkPolicy로

쉬운 말로 건물 보안팀의 규칙은 두 층입니다. 맨 앞의 Admin 층은 “메타데이터 서버 접근 금지”처럼 부서가 절대 못 뒤집는 규칙이고, 맨 뒤의 Baseline 층은 “부서가 따로 정하지 않으면 다른 부서 사람은 출입 금지”처럼 부서가 명단을 붙이면 덮이는 기본값입니다. 보안팀은 특정 연결에 대해 “이건 부서가 정하게 넘긴다(Pass)”고 위임할 수도 있습니다.

API의 변천

SIG Network의 network-policy-api 프로젝트는 처음에 AdminNetworkPolicy(ANP)와 BaselineAdminNetworkPolicy(BANP)라는 두 리소스(v1alpha1)를 만들었고, 2026년 6월 v0.2.0에서 이를 ClusterNetworkPolicy(CNP, v1alpha2) 하나로 합쳤습니다. 모델은 같고, 평가 순서를 리소스 종류 대신 tier 필드(Admin·Baseline)로 정합니다. 동작 이름 Allow는 Accept로 바뀌었고, 포트 필드는 프로토콜별 매칭(protocols)으로 바뀌었습니다. 아직 알파이며, 베타 목표는 2026년 하반기입니다. 구현마다 따르는 버전이 다르다는 점이 운영상 핵심입니다.

개념의미
tier: Admin모든 NetworkPolicy보다 먼저 평가. 여기서 Accept·Deny가 나면 끝(앱 팀이 못 뒤집음)
tier: BaselineNetworkPolicy가 그 Pod를 고르지 않았을 때만 평가. 앱 팀이 정책을 쓰면 덮임
priority같은 계층 안에서 숫자가 작을수록 먼저
actionAccept(허용 확정), Deny(거부 확정), Pass(이 계층을 건너뛰어 NetworkPolicy에 맡김. Admin 계층에서만 의미)
subject정책이 적용될 Pod: 네임스페이스·Pod 셀렉터
peers네임스페이스·Pod, 그리고 노드·CIDR 네트워크 등. 표준 NetworkPolicy보다 넓음
ClusterNetworkPolicy 예 (v1alpha2, 알파 API라 바뀔 수 있음)
# Admin: 모든 Pod의 클라우드 메타데이터 서버 접근 금지 (앱 팀이 못 뒤집음)
apiVersion: policy.networking.k8s.io/v1alpha2
kind: ClusterNetworkPolicy
metadata: {name: deny-imds}
spec:
  tier: Admin
  priority: 10
  subject: {namespaces: {}}
  egress:
  - action: Deny
    to: [{networks: ["169.254.169.254/32"]}]
---
# Baseline: 정책이 없는 네임스페이스는 다른 네임스페이스에서 들어오는 연결 거부 (앱 팀 정책이 있으면 덮임)
apiVersion: policy.networking.k8s.io/v1alpha2
kind: ClusterNetworkPolicy
metadata: {name: baseline-ns-isolation}
spec:
  tier: Baseline
  priority: 10
  subject: {namespaces: {matchLabels: {tenant: "true"}}}
  ingress:
  - action: Deny
    from: [{namespaces: {}}]

Cilium의 도메인 정책이 동작하는 방식

Cilium은 Pod의 DNS 질의를 노드의 DNS 프록시로 가로채 응답 IP를 기록하고, 그 IP로 가는 연결만 TTL 동안 허용합니다. 그래서 DNS 질의 자체를 허용하는 규칙(DNS 프록시 경유)이 반드시 함께 있어야 하고, 앱이 클러스터 DNS를 거치지 않고 외부 DNS(예: 8.8.8.8)에 직접 묻거나 IP를 하드코딩하면 동작하지 않습니다(9장 다섯 번째 사례). 같은 원리를 EKS Auto Mode의 DNS 기반 정책, GKE FQDN 정책, AKS ACNS도 씁니다.

Cilium L7 정책과 FQDN 이그레스 (8장 실습 2에서 사용)
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: {name: api-l7, namespace: shop}
spec:
  endpointSelector: {matchLabels: {tier: api}}
  ingress:
  - fromEndpoints: [{matchLabels: {tier: frontend}}]
    toPorts:
    - ports: [{port: "8080", protocol: TCP}]
      rules:
        http: [{method: GET, path: "/hostname"}]     # 그 밖의 경로는 403
---
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: {name: api-egress-fqdn, namespace: shop}
spec:
  endpointSelector: {matchLabels: {tier: api}}
  egress:
  - toEndpoints:
    - matchLabels: {"k8s:io.kubernetes.pod.namespace": kube-system, k8s-app: kube-dns}
    toPorts:
    - ports: [{port: "53", protocol: ANY}]
      rules: {dns: [{matchPattern: "*"}]}           # DNS 프록시 경유 필수
  - toFQDNs: [{matchName: "registry.k8s.io"}]
    toPorts: [{ports: [{port: "443", protocol: TCP}]}]
  - toEndpoints: [{matchLabels: {tier: db}}]
    toPorts: [{ports: [{port: "8080", protocol: TCP}]}]
OpenShift: EgressFirewall (네임스페이스당 이름 default 하나)
apiVersion: k8s.ovn.org/v1
kind: EgressFirewall
metadata: {name: default, namespace: shop}
spec:
  egress:                              # 위에서부터 첫 일치 규칙 적용
  - type: Allow
    to: {dnsName: registry.k8s.io}
  - type: Allow
    to: {cidrSelector: 10.0.0.0/8}
  - type: Deny
    to: {cidrSelector: 0.0.0.0/0}

기본 거부 설계와 정책 생성기

세 층으로 쌓기

  1. 바닥(관리자). 클러스터 공통 가드레일: 메타데이터 서버 차단(Admin), 네임스페이스 간 기본 차단(Baseline). CNP가 없는 엔진이라면 네임스페이스 생성 템플릿에 기본 거부 NetworkPolicy를 넣습니다.
  2. 플랫폼 필수 허용. 모든 앱 네임스페이스가 필요로 하는 것: DNS 이그레스, 인그레스 게이트웨이 네임스페이스에서의 인그레스(8편), 모니터링 네임스페이스에서의 메트릭 수집, 오퍼레이터라면 API 서버 이그레스. 플랫폼 팀이 소유합니다.
  3. 앱 허용. 계층 간 최소 허용(frontend → api → db). 앱 팀이 소유합니다.

도입 순서: 관찰 → 시험 → 적용

운영 중인 클러스터에 기본 거부를 한 번에 거는 것은 장애 예약입니다. ① 흐름 기록(Hubble·Whisker·OVN 로그)으로 실제 통신 지도를 만들고, ② 시험 적용(Calico Staged 정책, Cilium 감사 모드)으로 “걸었다면 막혔을 것”을 확인하고, ③ 네임스페이스 단위로 적용합니다. 7장 도구가 각 단계를 받칩니다.

함정: DNS 포트는 환경마다 다르다 NetworkPolicy는 DNAT 이후의 Pod 포트로 판정합니다. 대부분은 CoreDNS(kube-system, 레이블 k8s-app: kube-dns)의 53번이지만, OpenShift DNS는 openshift-dns 네임스페이스의 Pod가 5353에서 받습니다. NodeLocal DNSCache를 쓰면 목적지가 링크 로컬 IP(예: 169.254.20.10)라 ipBlock이 필요합니다. 아래 생성기의 DNS 변형을 고르세요.

이그레스 통제

    
쉬운 말로
    건물 밖으로 나가는 통제는 세 가지 질문입니다. 어디로 나가도 되나(목적지 통제), 나갈 때 어떤 주소로 보이나(출발지 고정), 나가는 내용을 누가 검사하나(프록시·방화벽). 하나의 도구가 셋을 다 하지는 않습니다.

    

      
도구목적지 통제출발지 고정내용 검사특징

      
        
NetworkPolicy 이그레스CIDR——Pod 단위, 이식성 높음, 도메인 불가

        
FQDN 정책(Cilium, EgressFirewall, EKS Auto Mode, GKE, AKS ACNS)도메인——DNS 경유 필수

        
클라우드 NAT 게이트웨이—서브넷 단위(모든 Pod가 같은 IP)—가장 단순. 고객·팀별 구분 불가

        
Cilium 이그레스 게이트웨이정책 대상 선택선택한 Pod를 지정 노드·IP로—Pod 레이블 단위 고정 IP. 게이트웨이 노드 이중화 설계 필요

        
OpenShift EgressIP—네임스페이스·Pod 단위 고정 IP—노드 장애 시 다른 노드로 이동

        
이그레스 프록시(명시·투명)URL·도메인프록시 IPTLS 검사 가능앱의 프록시 설정 또는 메시 이그레스 게이트웨이 필요

        
클라우드 방화벽(AWS Network Firewall, Azure Firewall, Cloud NGFW)FQDN·IPNAT와 결합제품별VPC 경계에서 중앙 통제. Pod 식별은 VPC 직결 CNI에서만 가능(5편)

      
    

    
현장 메모: 고객별 고정 IP 요구가 오면
    공용 클러스터의 여러 고객 중 한 고객만 “파트너 방화벽에 등록할 고정 IP”를 요구하는 일이 잦습니다. NAT 게이트웨이 하나로는 모든 고객이 같은 IP가 되므로, OpenShift라면 EgressIP, Cilium이라면 이그레스 게이트웨이 정책, 클라우드라면 그 고객 Pod만 별도 노드 풀·서브넷·NAT로 보내는 설계가 필요합니다. 어느 쪽이든 그 IP를 쓰는 노드의 장애 전환 시험을 반드시 하세요.

#!/usr/bin/env bash
pod(){ kubectl -n "$1" get pod -l tier="$2" -o jsonpath='{.items[0].metadata.name}'; }
chk(){ local sns=$1 stier=$2 url=$3 exp=$4 code got mark
  code=$(kubectl -n "$sns" exec "$(pod "$sns" "$stier")" -c tool -- curl -s -m 3 -o /dev/null -w '%{http_code}' "$url" 2>/dev/null)
  got=BLOCK; [[ "$code" =~ ^[1-5][0-9][0-9]$ ]] && got="OK$code"
  mark="✗"; [[ "$got" == ${exp}* ]] && mark="✓"
  printf '%-18s → %-38s 기대 %-6s 실제 %-7s %s\n' "$sns/$stier" "$url" "$exp" "$got" "$mark"; }
chk shop frontend http://api.shop:8080/hostname   OK
chk shop api      http://db.shop:8080/hostname    OK
chk shop frontend http://db.shop:8080/hostname    BLOCK
chk outsider attacker http://api.shop:8080/hostname BLOCK
chk shop api      https://registry.k8s.io/        OK
chk shop db       https://registry.k8s.io/        BLOCK
chk shop api      http://169.254.169.254/         BLOCK   # 클라우드에서만 의미(로컬 랩에는 IMDS가 없음)

  2. 맨 위 시뮬레이터에서 “Admin Accept(모니터링) + app-a 기본 거부”의 결과를 예측하고, 실습 1 (4)의 CNP로 모니터링 허용을 만들어 실제로 확인하세요.

  3. 담당 고객사 클러스터 하나에 대해 “정책 엔진 강제 여부, 네임스페이스별 기본 거부 여부, DNS 허용 방식, 이그레스 통제 수단, 흐름 기록 수단”을 표로 조사하세요.
    4. 
      

    

  


  
  

    
9

    
현장 사례

    
기본 거부를 걸었더니 모든 서비스가 이름 해석에 실패했다

      
원인. Ingress와 Egress를 함께 기본 거부하면서 DNS 이그레스 허용을 빠뜨렸습니다. 앱 로그에는 연결 실패가 아니라 “호스트를 찾을 수 없음”이 찍혀 원인 파악이 늦었습니다.

      
교훈. 네임스페이스 생성 템플릿에 기본 거부와 DNS 허용을 한 묶음으로 넣으세요. OpenShift는 포트 5353, NodeLocal DNSCache는 링크 로컬 IP라는 환경 차이(4장)도 템플릿에 반영합니다.

    

    
들여쓰기 한 칸이 다른 네임스페이스 전체를 열었다

      
원인. “team-a의 frontend만 허용”을 의도했는데, namespaceSelector와 podSelector를 별개 항목으로 써서 “team-a 네임스페이스 전체 또는 같은 네임스페이스의 frontend”가 됐습니다.

      
교훈. 정책 리뷰는 눈이 아니라 연결 행렬 시험으로 하세요. 막혀야 할 연결을 시험 목록에 반드시 넣어야 이런 실수가 잡힙니다.

    

    
외부 IP 허용 규칙이 아무 효과가 없었다

      
원인. 파트너 IP만 허용하는 ipBlock 인그레스 규칙을 썼지만, LoadBalancer Service가 externalTrafficPolicy: Cluster라 Pod에 도착한 출발지는 노드 IP였습니다. 결국 노드 대역을 허용하는 규칙이 추가되며 사실상 전부 열렸습니다.

      
교훈. 외부 출발지 통제는 LB·게이트웨이에서. NetworkPolicy ipBlock은 출발지가 보존되는 경로(6·7편)에서만 의미가 있습니다.

    

    
3년 동안 강제되지 않던 정책을 켠 날

      
상황. EKS 클러스터에 수백 개 NetworkPolicy가 있었지만 VPC CNI 정책 기능이 꺼져 있어 한 번도 강제된 적이 없었습니다. 감사 지적으로 기능을 켜자 여러 서비스가 동시에 끊겼습니다.

      
대응. 기능을 다시 끄고, 흐름 기록으로 실제 통신 지도를 만든 뒤 정책을 고쳐 네임스페이스 단위로 다시 켰습니다.

      
교훈. 3편 스모크 테스트의 NOT-enforced는 “정책이 없다”보다 위험합니다. 정책이 맞다고 믿게 만들기 때문입니다. 강제를 켜는 일은 새로 정책을 도입하는 일과 같은 절차(관찰 → 시험 → 적용)로 하세요.

    

    
FQDN 허용 정책인데 일부 Pod만 외부 호출이 실패한다

      
원인. 실패한 Pod의 앱이 클러스터 DNS 대신 설정 파일에 박힌 외부 DNS 서버로 직접 질의했습니다. DNS 프록시가 응답 IP를 학습하지 못해 연결이 막혔습니다. 다른 경우는 짧은 TTL로 IP가 자주 바뀌는 서비스에서 학습 시점과 연결 시점이 어긋난 것이었습니다.

      
교훈. 도메인 정책은 모든 이름 해석이 클러스터 DNS를 거친다는 전제 위에 있습니다. 외부 DNS 직접 질의를 막는 규칙을 함께 두세요.

    

    
메타데이터 서버 차단 후 일부 에이전트가 죽었다

      
원인. Admin 계층에서 모든 Pod의 169.254.169.254 접근을 막았는데, 노드 정보를 메타데이터 서버에서 읽는 일부 모니터링 에이전트가 일반 Pod로 돌고 있었습니다.

      
대응. 그 에이전트 네임스페이스를 subject에서 제외하고, 가능하면 워크로드 아이덴티티(20편)로 옮겼습니다.

      
교훈. Admin 계층 규칙은 앱 팀이 못 뒤집는 만큼 예외 목록을 처음부터 설계해야 합니다. 적용 전 흐름 기록으로 해당 목적지를 쓰는 Pod를 먼저 찾으세요.

    

    
한 고객만 고정 출발지 IP가 필요했다

      
상황. 공용 클러스터의 고객 하나가 파트너 방화벽 등록용 고정 IP를 요구했는데, 클러스터 전체가 NAT 게이트웨이 하나를 쓰고 있어 모든 고객이 같은 IP였습니다.

      
대응. OpenShift 클러스터에는 그 고객 네임스페이스에 EgressIP를, Cilium 클러스터에는 이그레스 게이트웨이 정책을 적용하고, 게이트웨이 노드 장애 전환을 시험했습니다.

      
교훈. 출발지 IP는 고객 경계가 될 수 있습니다. 공용 클러스터 설계 단계에서 고객별 이그레스 IP 요구를 질문 목록에 넣으세요.

정리, 다음 편, 참고 자료

    

      
이 편의 핵심 다섯 줄

      
    
        
  1. NetworkPolicy는 선택된 Pod를 방향별로 격리하고 허용만 더하는 모델이며, 거부·클러스터 범위·우선순위·로그·도메인·L7이 없습니다.
    2. 
        
  2. ClusterNetworkPolicy(v1alpha2, 옛 ANP·BANP)는 Admin 계층(못 뒤집는 규칙)과 Baseline 계층(덮일 수 있는 기본값), Accept·Deny·Pass로 관리자 가드레일을 표준화하지만 아직 알파이고 구현마다 지원 형태가 다릅니다.
    3. 
        
  3. Calico·Cilium·OVN-K 확장 정책이 거부·순서·L7·도메인·시험 적용·흐름 기록을 채우며, 도메인 정책은 클러스터 DNS 경유를 전제로 합니다.
    4. 
        
  4. 기본 거부는 관리자 바닥, 플랫폼 필수 허용(DNS·게이트웨이·모니터링), 앱 허용의 세 층으로 쌓고, 관찰 → 시험 → 적용 순으로 도입합니다. EKS는 정책 기능을 켜야 강제됩니다.
    5. 
        
  5. 이그레스는 목적지 통제, 출발지 고정, 내용 검사를 서로 다른 도구(NP·FQDN 정책, NAT·이그레스 게이트웨이·EgressIP, 프록시·방화벽)로 조합해야 합니다.
    6. 
      

    

    

      
다음 편 · 10편 DNS·서비스 메시·멀티클러스터 네트워크와 종합 트러블슈팅 (Level 1 마지막)

      
CoreDNS 심화(ndots:5 문제, autopath, NodeLocal DNSCache, 벤더 DNS 통합), 서비스 메시 선택(Istio 사이드카·ambient, Linkerd, Cilium Service Mesh, 벤더 메시), 멀티클러스터(Multi-Cluster Services API, Cilium ClusterMesh, Submariner)를 다루고, 4~9편 전체를 묶는 계층별 트러블슈팅 플레이북으로 다섯 가지 네트워크 장애(MTU, DNS, 정책, LB 헬스 체크, kube-proxy 동기화)를 시간 제한 안에 진단합니다.
