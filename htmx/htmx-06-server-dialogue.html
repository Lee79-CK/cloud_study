요청 헤더로 판단하기

1편에서 목록만 봤던 요청 헤더를, 이번에는 서버가 실제로 무엇을 판단하는 데 쓰는지 기준으로 정리합니다. 값은 htmx 4.0.1 소스의 #createCoreHeaders와 랩 로그에서 확인했습니다.

헤더서버의 판단랩에서 쓰는 곳
HX-Request: truehtmx가 보낸 요청인가인증 미들웨어: htmx면 401 + HX-Redirect, 아니면 302
HX-Request-Type: partial|full조각을 줄까 전체 페이지를 줄까wantsFragment() (2편부터)
HX-Current-URL사용자가 지금 보고 있는 주소세션 만료 후 돌아올 주소 (요청 URL이 아니라 화면 URL이 필요)
HX-Source / HX-Target무엇이 요청했고 어디에 넣을 것인가로그. 같은 엔드포인트를 여러 곳에서 쓸 때 분기 근거
HX-Boostedhx-boost로 가로챈 링크·폼인가7편
HX-History-Restore-Request뒤로 가기 복원용 재요청인가7편
Accept: text/htmlHTML을 원함데이터 API(/api/*)와 구분할 때
HX-Current-URL이 필요한 이유

사용자가 /vms/web-04를 보다가 VM 이름을 눌러 GET /vms/web-01(조각) 요청을 보냈는데 세션이 끝났다고 합시다. 로그인 후 돌려보낼 곳은 요청 URL인 /vms/web-01(조각 주소)가 아니라 사용자가 보던 화면 /vms/web-04입니다. 랩 테스트에서 세션 만료 뒤 클릭하자 /login?next=%2Fvms%2Fweb-04로 이동했고, 다시 로그인하자 /vms/web-04 전체 페이지로 돌아왔습니다.

03

응답 헤더 총정리

htmx 4.0.1은 응답의 HX-로 시작하는 헤더를 모두 모은 뒤(#extractHxHeaders), 아래 순서로 처리합니다. 순서가 중요합니다. 앞 단계에서 끝나 버리면 뒤 단계는 실행되지 않습니다.

① 응답 수신 직후 (상태 코드 400 이상이면 htmx:response:error 발생)
1HX-Refresh: true → 페이지 새로고침. 여기서 끝 (스왑 없음)
2HX-Redirect: URL → location.href 이동. 여기서 끝
3HX-Location: URL 또는 JSON → 새 htmx GET 요청을 보냄. 여기서 끝 (이 응답의 본문은 버려짐)
② 스왑 준비
4HX-Retarget · HX-Reswap · HX-Reselect → 대상·스왑 방식·선택 영역을 덮어씀
5상태 코드 처리: noSwap(204·304)이면 스왑 없음, 아니면 요소의 hx-status:코드가 있으면 적용 (④의 헤더보다 우선)
③ 스왑
6HX-Push-Url · HX-Replace-Url → 스왑 직전에 주소 기록 갱신
④ 마무리 (finally — 위에서 끝났어도 실행)
7HX-Trigger → 이벤트 발생. Refresh·Redirect·Location으로 끝난 응답에서도 처리됨

응답 헤더 실험실 (htmx 4.0.1 실동작)

마지막 버튼이 중요한 함정을 보여 줍니다. HX-Location(그리고 Redirect·Refresh)이 붙은 응답은 본문 처리 전에 끝나므로, 같은 응답에 담은 본문도 OOB 토스트도 모두 무시됩니다. 기록을 보면 두 번째 GET이 나가고 그 응답만 화면에 들어갑니다. 반면 HX-Trigger는 마무리 단계에서 처리되므로 여전히 동작합니다. 그래서 랩의 VM 등록 성공 응답은 토스트 대신 HX-Trigger: vmChanged만 함께 보냅니다.

  

    
HX-Redirect 도착 지점

    
실험실의 HX-Redirect 버튼은 #redirect-demo로 이동시켜 이 상자로 스크롤합니다. 4.0.1 소스는 이 헤더를 받으면 location.href에 값을 그대로 대입하므로, 실제 서비스에서는 다른 페이지로의 전체 이동이 일어납니다. 같은 이유로 HX-Refresh는 이 강의 파일을 새로고침해 버리기 때문에 실험에서 뺐습니다.

  

  

    
2.x에서 넘어오는 분께

    
2.x의 HX-Trigger-After-Swap, HX-Trigger-After-Settle은 4.0.1 코어에서 처리하지 않습니다(1편). 이벤트 시점을 늦추고 싶다면 HX-Trigger로 보낸 이벤트를 받는 쪽에서 htmx:after:settle 이후에 동작하도록 만드세요.

문서 예시의 함정: hx-status:404="none"

    
공식 문서의 "Requests & Responses" 개념 페이지에는 hx-status:404="none", hx-status:503="none" 형태의 예시가 있습니다. 그러나 값은 HCON 키:값으로 파싱되므로 "none"은 {none: true}가 되어 스왑 방식에 영향을 주지 않습니다. 위 실험에서 "none" 버튼은 404 본문이 그대로 들어가고, "swap:none" 버튼만 화면을 지켰습니다. hx-status 레퍼런스 페이지의 예시처럼 항상 swap:none으로 쓰세요.

  







  06
  
말할 수 있는 오류, 말할 수 없는 오류

  
오류는 두 종류입니다. 서버가 정상적으로 응답을 만들 수 있는 오류(검증 실패, 권한 없음, 세션 만료)는 서버가 헤더와 상태 코드로 화면을 지휘하면 됩니다. 하지만 서버가 죽었거나, 프록시가 대신 502를 내거나, 응답이 오지 않는 경우에는 서버가 아무것도 지휘할 수 없습니다. 이때는 클라이언트가 스스로 처리해야 합니다.

  

    
이벤트언제detail

    
      
htmx:response:error응답은 왔는데 상태 코드가 400 이상ctx.response.status로 코드 확인. 스왑은 규칙대로 진행

      
htmx:error응답 자체가 없음: 연결 실패, 연결 끊김, 시간 초과, 그 밖의 예외error와 ctx. 시간 초과는 ctx.request.signal.reason === 'timeout'

    
  

  

    
시간 초과를 정확히 판별하기 (랩에서 확인한 사실)

    
처음에는 error.name === 'AbortError'로 시간 초과를 구분했는데, 실제 서버 테스트에서 이 조건이 거짓이었습니다. htmx는 시간이 다 되면 abort('timeout')으로 요청을 끊고, 이렇게 이유를 넘겨 중단한 fetch는 AbortError가 아니라 그 이유 값('timeout' 문자열)으로 실패합니다. 랩 로그에 기록된 값도 error='timeout', reason='timeout'이었고, 연결 끊김은 TypeError였습니다. 그래서 판별은 e.detail.ctx.request.signal.reason === 'timeout'으로 합니다. 또 hx-sync의 replace처럼 htmx가 스스로 취소한 요청은 htmx:error를 발생시키지 않습니다(소스 조건).

  

  
views/layout.eta (전역 오류 처리)


document.addEventListener('htmx:response:error', (e) => {      // 4xx·5xx 응답
  const s = e.detail.ctx.response.status;
  if (s >= 500) localToast(`서버 오류가 발생했습니다 (${s}). 잠시 후 다시 시도하세요.`);
});
document.addEventListener('htmx:error', (e) => {               // 연결 실패·시간 초과 (응답 자체가 없음)
  // 시간 초과는 htmx가 abort('timeout')으로 끊으므로 signal.reason이 'timeout'이다
  const timedOut = e.detail.ctx?.request?.signal?.reason === 'timeout';
  localToast(timedOut ? '응답 시간이 초과되었습니다.' : '서버에 연결할 수 없습니다.');
});

  
4xx는 전역 토스트에서 뺐습니다. 401·403·422는 서버가 이미 화면을 지휘하는 "말할 수 있는 오류"이기 때문입니다. 요청 시간 제한은 기본 60초(htmx.config.defaultTimeout)이고, 요소별로 hx-config="timeout:2s"처럼 바꿀 수 있습니다. 4.0.1 소스는 hx-config 값을 요청 객체에 병합하되, 보안에 민감한 mode만은 요소에서 바꾸지 못하게 막습니다.







  07
  
인증·권한 패턴


  
세션 만료: 302가 아니라 401 + HX-Redirect

  
일반 웹에서는 세션이 끝나면 302로 로그인 페이지에 보냅니다. htmx 요청에 똑같이 하면 문제가 생깁니다. fetch()는 리다이렉트를 자동으로 따라가므로 htmx는 로그인 페이지의 200 응답을 받고, 그것을 요청한 자리(표 한 칸, 상세 패널)에 그대로 끼워 넣습니다.

  

    
랩의 "302 리다이렉트 (나쁜 예)" 버튼으로 재현한 결과

    
결과 칸 안에 포털 헤더·메뉴·로그인 사용자 표시까지 포함된 전체 페이지가 통째로 들어갔습니다. 게다가 그 페이지의 인라인 스크립트가 다시 실행되면서 브라우저 콘솔에 Identifier 'dialog' has already been declared 오류가 났습니다. htmx는 스왑한 조각 안의 <script>를 실행하므로(5편 생애의 "조각 만들기" 단계), 전체 페이지를 조각 자리에 넣으면 레이아웃 스크립트가 두 번 실행됩니다.

  

  

    
1세션이 끝난 사용자가 VM 이름 클릭 → GET /vms/web-01, HX-Current-URL: …/vms/web-04

    
2서버: htmx 요청이므로 401 + HX-Redirect: /login?next=%2Fvms%2Fweb-04

    
3htmx: 스왑하지 않고 브라우저 전체를 /login?next=...로 이동

    
4사용자가 로그인 (htmx 없는 일반 폼 POST /login)

    
5서버: 세션 쿠키 발급 + 303 See Other → /vms/web-04

    
6사용자는 원래 보던 화면으로 복귀

  

  
401은 "인증이 필요하다"는 정확한 의미를 갖고, htmx:response:error를 발생시켜 다른 코드가 알아챌 수 있게 합니다. 로그인 폼 처리 뒤에 303을 쓰는 이유는 POST 다음의 이동을 GET으로 바꾸라는 뜻이 명확하기 때문입니다.


  
열린 리다이렉트 막기

  
next 값은 사용자가 조작할 수 있습니다. /login?next=https://evil.example/ 같은 링크를 메일로 받은 사용자가 로그인하면 그대로 피싱 사이트로 보내지는 것이 "열린 리다이렉트(open redirect)" 취약점입니다. 랩의 safeNext()는 값을 현재 사이트 기준 URL로 해석해 출처(origin)가 같을 때만 경로를 돌려줍니다.

  
apps/server/src/auth.js (발췌)


export function safeNext(raw, selfOrigin) {
  if (!raw) return '/vms';
  let u;
  try { u = new URL(raw, selfOrigin); } catch { return '/vms'; }
  if (u.origin !== selfOrigin) return '/vms';
  const path = u.pathname + u.search;
  return path.startsWith('/login') ? '/vms' : path;
}

처음 작성한 버전은 기준 출처를 가짜 값으로 두어 HX-Current-URL처럼 정상적인 같은 사이트 절대 주소까지 막았고, //evil.com을 /로 통과시켰습니다. 실행해 보고 출처 비교 방식으로 고친 것입니다. 보안 함수는 반드시 공격 문자열 목록으로 직접 실행해 보세요.


  
권한: 화면에서 숨기고, 서버에서 막는다

  
조회 전용 사용자에게는 서버가 처음부터 재시작·삭제 버튼을 그리지 않습니다(1편 HATEOAS). 그러나 화면은 오래될 수 있습니다. 탭을 열어 둔 사이 관리자가 권한을 낮췄다면 사용자의 화면에는 버튼이 그대로 있습니다. 랩의 "역할 전환" 버튼이 이 상황을 만듭니다. 그래서 서버 미들웨어가 모든 쓰기 요청을 다시 검사하고, htmx 요청이면 응답 위치를 토스트 영역으로 바꿔 경고만 보여 줍니다.

  
apps/server/src/app.js (②-3 역할 확인)


const ROLE_FREE = [/^\/login/, /^\/logout/, /^\/session\//, /\/alerts\/check$/];
app.use((req, res, next) => {
  const isWrite = ['POST', 'PUT', 'PATCH', 'DELETE'].includes(req.method);
  if (!isWrite || !req.user || req.user.role === 'operator' || ROLE_FREE.some(r => r.test(req.path))) return next();
  if (req.htmx) {
    return res.status(403)
      .set({ 'HX-Retarget': '#toasts', 'HX-Reswap': 'beforeend' })
      .type('html')
      .send(eta.render('./partials/toast-item', { msg: `권한이 없습니다. ...`, kind: 'warn' }));
  }
  res.status(403).type('text').send('Forbidden');
});

  
요청한 버튼의 대상은 closest tr이었지만 서버가 #toasts의 끝으로 바꿨으므로 행은 그대로 남고 경고만 쌓입니다. 클라이언트에 아무 코드도 추가하지 않았다는 점이 핵심입니다. 단, 5절에서 본 대로 요소에 hx-status:403이 있으면 클라이언트 설정이 이기므로, 서버 주도 처리를 쓰는 화면에는 hx-status를 겹쳐 달지 않습니다.

  1. 응답 헤더 처리 순서: Refresh → Redirect → Location(여기서 끝, 본문 무시) → Retarget·Reswap·Reselect → 상태 코드(hx-status가 헤더보다 우선) → Push·Replace → 스왑 → Trigger(항상).
