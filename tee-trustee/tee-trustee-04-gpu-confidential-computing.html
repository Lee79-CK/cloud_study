GPU 기밀 컴퓨팅

LLM의 진짜 보물은 GPU 안에 있습니다. 수십~수백 GB의 가중치, 대화가 쌓인 KV 캐시, 계산 중인 중간값까지. CPU 금고를 아무리 튼튼하게 만들어도, GPU로 가는 길과 GPU 안이 열려 있으면 소용이 없습니다.

시작하기 전에

지금까지 세 편에 걸쳐 CPU 쪽 이야기를 했습니다. 1편에서는 무엇을 왜 지켜야 하는지, 2편에서는 CPU TEE가 메모리를 어떻게 격리·암호화하는지, 3편에서는 그 상태를 어떻게 증명하는지 배웠습니다.

그런데 1편 3장의 "추론 요청 하나의 여정"을 떠올려 보면, 가장 비싼 자산(가중치)과 가장 민감한 자산(프롬프트, KV 캐시)이 모이는 곳은 6번 GPU였습니다. 그리고 1편 11장에서 "CPU TEE만 켜면 GPU 추론도 보호된다"는 오해라고 했죠. 이번 편은 바로 그 빈칸을 채웁니다.

🎯이번 편을 마치면

  • CPU TEE만으로 GPU 추론을 지킬 수 없는 이유를 설명할 수 있습니다.
  • GPU 기밀 컴퓨팅 모드에서 데이터가 GPU로 가는 경로를 그릴 수 있습니다.
  • 성능 비용이 어디서 생기는지 워크로드별로 예측할 수 있습니다.
  • Hopper와 Blackwell의 멀티 GPU 지원 차이를 말할 수 있습니다.
  • CPU 증명과 GPU 증명을 함께 묶어야 하는 이유를 설명할 수 있습니다.

🔗이어지는 개념

  • 2편 10장의 shared 메모리와 바운스 버퍼가 이번 편의 주인공입니다.
  • 3편의 Evidence, Endorser, Reference Value, Verifier가 GPU에도 그대로 적용됩니다.
  • 3편 10장 토큰 예시의 submods.cpu0 옆에 이번 편에서 gpu0가 생깁니다.
1

CPU TEE만으로는 부족한 이유

먼저 LLM 추론에서 데이터가 실제로 어디에 머무는지 크기로 비교해 봅시다. 70B(700억) 파라미터 모델을 16비트로 서빙하는 경우를 예로 들었습니다.

예제: 70B 모델 추론 서버의 데이터 위치 (대략치)

파라미터 1개당 2바이트로 계산한 어림값입니다. KV 캐시는 동시 사용자 수와 대화 길이에 따라 크게 달라집니다.

추론 서버 프로세스가 CPU 메모리에 들고 있는 것은 상대적으로 작습니다. 프롬프트 텍스트, 토크나이저, 스케줄러 상태 정도입니다. 반면 가중치와 KV 캐시, 계산 중간값은 거의 전부 GPU 메모리(HBM)에 있습니다. CPU TEE는 CPU 메모리만 지키므로, 보호 대상의 대부분이 금고 밖에 있는 셈입니다.

비유: 금고 방과 옆 건물 작업장

회계 사무실(CPU TEE)에 최고급 금고를 설치했습니다. 그런데 실제 장부 계산은 옆 건물의 대형 작업장(GPU)에서 합니다. 서류를 금고에서 꺼내 복도(PCIe)를 지나 작업장으로 옮기고, 작업장 책상(HBM)에 펼쳐 놓고 일합니다. 복도에 CCTV가 있고, 작업장 열쇠를 건물 관리인이 가지고 있다면? 금고는 거의 의미가 없습니다. GPU 기밀 컴퓨팅은 복도에 봉인 운반함을 쓰고, 작업장에도 관리인이 못 들어오는 잠금장치를 다는 것입니다.

2

호스트가 GPU에 할 수 있는 일

GPU는 PCIe 장치입니다. 일반 환경에서 호스트(하이퍼바이저, 호스트 OS, 그 관리자)는 PCIe 장치를 꽤 자유롭게 다룰 수 있습니다. GPU 기밀 컴퓨팅이 막아야 할 대상을 구체적으로 정리해 봅시다.

GPU 메모리 창(BAR)을 통한 읽기·쓰기GPU 메모리를 CPU 주소처럼 열어서 들여다보기가중치, KV 캐시, 중간값
DMA 버퍼 엿보기CPU와 GPU가 데이터를 주고받는 공유 버퍼 읽기입력 텐서, 출력 토큰

명령 조작GPU에 보내는 작업 명령을 중간에 바꾸기계산 결과의 무결성

요점

GPU를 지킨다는 것은 세 가지를 막는 일입니다. ① 호스트가 GPU 메모리를 직접 들여다보는 것, ② CPU와 GPU 사이, GPU와 GPU 사이 통로를 엿보는 것, ③ GPU의 펌웨어와 설정을 몰래 바꾸는 것. 그리고 3편에서 배운 대로, 이 모든 게 제대로 켜져 있다는 것을 증명할 수 있어야 합니다.

3

GPU 기밀 컴퓨팅 모드의 부품

NVIDIA는 Hopper 세대(H100)부터 데이터센터 GPU에 기밀 컴퓨팅(CC) 모드를 넣었습니다. GPU가 CPU TEE와 함께 하나의 보호 구역처럼 동작하게 만드는 기능입니다. 주요 부품은 다음과 같습니다.

🌱칩 안의 신뢰 루트

GPU 칩 안에 하드웨어 신뢰 루트가 있습니다. 서명된 펌웨어만 부팅되도록 확인하고(보안 부팅), 칩마다 고유한 신원 키를 가지고 있어 증명 보고서에 서명합니다. 2편의 AMD Secure Processor와 비슷한 역할입니다.

🧱보호 메모리 영역 (CPR)

GPU 메모리 대부분을 Compute Protected Region으로 묶고, 호스트가 BAR나 DMA로 이 영역에 접근하는 것을 하드웨어가 막습니다. CC 모드에서 가중치와 KV 캐시는 여기에 삽니다.

🔐암호화 복사 엔진

CPU와 데이터를 주고받는 GPU의 복사 엔진이 AES-GCM 암호화·복호화를 합니다. GCM은 암호화와 함께 위변조 검사 값을 붙이는 방식이라, 암호문을 바꿔치기하면 바로 들통납니다.

🤝보안 세션 (SPDM)

CPU TEE 안의 GPU 드라이버와 GPU가 SPDM이라는 표준 프로토콜로 서로 확인하고 세션 키를 나눠 갖습니다. 이 키로 데이터와 명령을 암호화합니다. 키는 기밀 VM과 GPU만 압니다.

중요한 차이: GPU 메모리(HBM)는 암호화되지 않는다

2편에서 CPU는 DRAM에 나가는 데이터를 암호화한다고 배웠습니다. 그런데 GPU의 HBM은 보통 암호화하지 않습니다. 대신 HBM은 GPU 칩과 같은 패키지 안에 붙어 있어 메모리 모듈처럼 뽑아갈 수 없고, 호스트의 접근은 위의 CPR 접근 통제로 막습니다. 즉 GPU는 "암호화"가 아니라 "칩 패키지 경계 + 접근 통제"로 메모리를 지킵니다. 암호화가 필요한 곳은 칩 패키지 밖으로 나가는 통로, 즉 PCIe와 NVLink입니다.

비유: 은행 안의 금고실

CPU 쪽 메모리 보호는 "서류를 모두 암호로 적어 일반 창고에 보관하는" 방식이었습니다. GPU 쪽은 "서류를 평문으로 두되, 은행 건물 안쪽 금고실에만 두고 출입을 막는" 방식입니다. 건물 밖으로 서류를 옮길 때만 봉인 운반함(암호화)을 씁니다.

4

데이터가 GPU로 가는 길

2편 10장에서 기밀 VM의 디스크·네트워크 I/O가 shared 메모리의 바운스 버퍼를 거친다고 배웠습니다. GPU도 같은 문제에 부딪힙니다. GPU는 DMA로 CPU 메모리를 읽는데, 기밀 VM의 private 메모리는 바깥 장치가 읽을 수 없기 때문입니다. 그래서 길을 돌아갑니다. 단계를 넘겨보세요.

비유: 택배 재포장

보안 건물(기밀 VM)에서 다른 보안 건물(GPU)로 물건을 보낼 때, 택배 기사(DMA)는 건물 안에 들어올 수 없습니다. 그래서 직원이 물건을 잠금 상자에 넣어(암호화) 건물 입구의 공용 보관함(바운스 버퍼)에 둡니다. 기사는 상자째로 옮기고, 받는 건물의 직원(GPU 복사 엔진)이 상자를 열어 안쪽 금고실(CPR)에 넣습니다. 상자를 열 수 있는 열쇠는 두 건물 직원만 나눠 가졌습니다(SPDM 세션 키).

이 방식은 안전하지만 일이 늘어납니다. 데이터를 한 번 더 복사하고, 암호화와 복호화를 해야 합니다. 이것이 다음 장에서 볼 성능 비용의 정체입니다.

5

성능: 무엇이 느려지나

"기밀 컴퓨팅을 켜면 얼마나 느려지나요?"는 가장 많이 받는 질문입니다. 답은 "무엇을 하느냐에 따라 다르다"입니다. 원리부터 보면 예측할 수 있습니다.

🟢거의 그대로인 것

GPU 안에서의 계산. 행렬 곱셈과 어텐션 계산은 보호 영역(CPR) 안에서 평문으로 그대로 실행됩니다. 암호화가 끼어들지 않으므로 GPU 연산 자체는 거의 느려지지 않습니다.

🟡느려지는 것

CPU와 GPU 사이의 이동. 바운스 버퍼 복사, 암호화·복호화, GPU에 보내는 명령의 보호 처리가 추가됩니다. 데이터를 많이, 자주 옮길수록 영향이 커집니다. 기밀 VM 자체의 비용(2편 10장의 VM Exit, I/O)도 더해집니다.

직접 해보기: 워크로드별 체감 영향 예측

원리에 따른 상대적 경향을 보여주는 학습용 예측입니다. 실제 수치는 모델, 배치 크기, 하드웨어, 드라이버 버전에 따라 크게 다르므로 반드시 직접 측정해야 합니다.

공개된 수치를 읽는 법

NVIDIA는 최근 Blackwell 세대에서 특정 추론 벤치마크 기준으로 CC를 켜도 처리량이 끈 경우의 약 98% 수준이라고 발표했습니다. 외부 연구자들의 측정도 늘고 있는데, 공통된 결론은 GPU 연산은 거의 공짜이고, 비용은 암호화된 이동과 복사에서 생긴다는 것입니다. 다만 이런 수치는 특정 조건의 결과입니다. 우리 고객사의 모델·트래픽 패턴으로 직접 측정한 값이 아니면 견적서에 그대로 쓰면 안 됩니다.

6

여러 GPU를 함께 쓸 때

큰 모델은 GPU 한 장에 들어가지 않아 여러 GPU에 나눠 올립니다(텐서 병렬 등). 이때 GPU끼리 NVLink로 엄청난 양의 데이터를 주고받습니다. 이 통로를 어떻게 보호하느냐가 세대별 차이의 핵심입니다. 모드를 바꿔보세요.

세대·모드기밀 VM당 GPUCPU↔GPUGPU↔GPU (NVLink)
Hopper 단일 GPU 패스스루1개바운스 버퍼 + 암호화사용 안 함
Hopper Protected PCIe플랫폼의 8개 전부바운스 버퍼 + 암호화하드웨어 암호화 없음 (8개를 한 신뢰 단위로 취급)
Blackwell 멀티 GPU1, 2, 4, 8개바운스 버퍼 + 암호화NVLink 하드웨어 암호화

지원 모드와 GPU 조합은 플랫폼(SKU)과 드라이버 버전에 따라 다릅니다. 도입 전에 NVIDIA의 기밀 컴퓨팅 지원 문서에서 정확한 조합을 확인해야 합니다.

7

TEE-I/O: 바운스 버퍼 없는 미래

4장의 "택배 재포장"은 안전하지만 번거롭습니다. 근본 원인은 CPU TEE가 GPU를 믿을 방법이 없어서 외부 장치로 취급하는 데 있습니다. 그래서 업계는 장치 자체를 TEE 안으로 받아들이는 표준을 만들고 있습니다.

🔗PCIe IDE

Integrity and Data Encryption. PCIe 링크 자체를 하드웨어가 암호화합니다. 소프트웨어가 따로 암호화할 필요가 없어집니다.

🪪TDISP

TEE Device Interface Security Protocol. 장치를 증명하고, 확인된 장치에게 기밀 VM의 private 메모리를 직접 읽고 쓸 권한을 줍니다. CPU 쪽에서는 Intel TDX Connect, AMD SEV-TIO 같은 기능이 이를 받쳐줍니다.

비유: 재포장 대신 전용 봉인 파이프

매번 상자에 넣고 열던 택배 대신, 두 보안 건물 사이에 전용 봉인 파이프를 놓는 셈입니다. 파이프 자체가 암호화되어 있고, 파이프 반대편이 진짜 우리 건물이라는 것을 먼저 확인했으니 물건을 그냥 흘려보내면 됩니다. 재포장(바운스 버퍼 복사)이 사라지니 빨라집니다.

NVIDIA는 Blackwell을 업계 첫 TEE-I/O 지원 GPU로 소개하고 있습니다. 다만 이 방식이 실제로 동작하려면 CPU, 펌웨어, 리눅스 커널, 하이퍼바이저, 드라이버가 모두 지원해야 해서 생태계가 아직 갖춰지는 중입니다. 당분간 실무에서는 바운스 버퍼 방식이 기본이고, TEE-I/O는 "곧 올 개선"으로 이해하면 됩니다.

CC 모드를 켰다고 주장하는 GPU를 어떻게 믿을까요? 3편과 똑같습니다. GPU도 Attester가 되어 증거를 내고, 검증자가 이를 확인합니다. RATS 역할에 대응시켜 보면 다음과 같습니다.

CPU와 GPU를 하나로 묶기

CPU 증명도 통과하고 GPU 증명도 통과했습니다. 이제 안전할까요? 한 가지가 더 필요합니다. "그 GPU가 바로 이 기밀 VM에 붙어 있는가"입니다.

비유: 짝이 맞는 부품

정품 엔진과 정품 차체가 각각 검사를 통과했어도, 두 부품이 같은 차에 조립되어 있다는 확인이 없다면 의미가 없습니다. 공격자가 정품 엔진 검사서를 다른 차에 붙여둘 수 있으니까요.

어떻게 묶나

  • 경로로 묶기: GPU 증거는 기밀 VM 안의 드라이버가 SPDM 세션으로 GPU에서 직접 받아옵니다. 호스트가 중간에 끼어들 수 없는 경로입니다.
  • nonce로 묶기: CPU 증거와 GPU 증거가 같은 증명 요청에서 받은 nonce를 사용하게 하면, 둘이 같은 시점, 같은 요청에서 만들어졌음을 확인할 수 있습니다.
  • 한 번에 제출하기: CoCo 환경에서는 Attestation Agent가 CPU TEE 증거와 GPU 증거를 함께 묶어 KBS에 제출하고, AS가 둘을 모두 검증하는 구성을 씁니다. 결과 토큰에는 CPU와 GPU 판정이 각각 담깁니다.

3편 10장의 예시 토큰에 GPU 판정을 더한 학습용 예시입니다. 실제 구성과 필드는 Trustee 버전과 설정에 따라 다릅니다.

KBS의 리소스 정책은 이 토큰을 보고 "cpu0와 gpu0가 모두 affirming일 때만 모델 키를 준다"처럼 쓸 수 있습니다. 6편과 8편에서 실제 정책 문법으로 다룹니다.

11

오해 바로잡기

오해GPU CC 모드는 HBM을 암호화한다.
사실HBM은 칩 패키지 안에 있어 접근 통제(CPR)로 보호합니다. 암호화되는 곳은 패키지 밖으로 나가는 통로(PCIe, 그리고 Blackwell의 NVLink)입니다.
오해GPU CC만 켜면 CPU TEE는 없어도 된다.
사실GPU CC는 CPU TEE와 짝을 이뤄야 의미가 있습니다. 세션 키를 가진 드라이버, 프롬프트 텍스트, 토크나이저가 모두 CPU 쪽에 있습니다. CPU 쪽이 열려 있으면 키도 데이터도 노출됩니다.
오해기밀 컴퓨팅을 켜면 추론이 몇 배 느려진다.
사실GPU 연산 자체는 거의 그대로입니다. 영향은 CPU-GPU 이동량에 비례합니다. 일반적인 LLM 추론은 영향이 작은 편이지만, 입력이 큰 워크로드나 잦은 모델 교체에서는 커질 수 있어 측정이 필요합니다.
오해Hopper 8장 구성도 GPU 간 통신이 암호화된다.
사실Hopper의 Protected PCIe 모드에서 NVLink 통신은 하드웨어 암호화되지 않습니다. 8개 GPU를 하나의 신뢰 단위로 보는 모델입니다. NVLink 암호화는 Blackwell부터입니다.
오해GPU 증명과 CPU 증명을 각각 통과하면 충분하다.
사실그 GPU가 그 기밀 VM에 붙어 있다는 묶음 확인이 필요합니다(9장).

MSP 운영 관점

GPU 기밀 컴퓨팅을 고객사에 적용하면 GPU 노드 운영 방식이 달라집니다.

🔄CC 모드 전환은 계획 작업

GPU의 CC 모드를 바꾸려면 보통 GPU 재설정이 필요해 그 GPU에서 돌던 워크로드를 비워야 합니다. Kubernetes에서는 NVIDIA GPU Operator가 노드의 CC 모드를 관리하는 기능을 제공하므로, 노드 라벨로 원하는 모드를 지정하고 순차적으로 전환하는 절차를 만들어 두는 것이 좋습니다.

🏷️혼합 클러스터 스케줄링

CC 노드와 일반 노드가 섞인 클러스터에서는 기밀 워크로드가 반드시 CC 노드에만 배치되도록 라벨·테인트·RuntimeClass를 설정해야 합니다. 실수로 일반 노드에 뜨면 증명에 실패해 키를 못 받는 것이 정상 동작이지만, 장애처럼 보일 수 있으므로 알림 문구를 명확히 해야 합니다.

🩺장애 대응이 달라진다

호스트에서 GPU 메모리를 덤프하거나 디버그 도구를 붙이는 방식의 분석이 불가능합니다. DevTools 모드는 운영 환경 증명 정책에서 거부해야 하므로, 재현용 비기밀 환경을 따로 두는 것이 현실적입니다. 호스트에서 볼 수 있는 GPU 정보 범위도 달라질 수 있어 모니터링 항목을 미리 확인해야 합니다.

🧾펌웨어·드라이버 업데이트

GPU 펌웨어나 드라이버를 업데이트하면 측정값이 바뀝니다. NVIDIA의 RIM이 새 버전을 반영하고, 우리 증명 정책이 새 버전을 허용해야 업데이트 후에도 키를 받을 수 있습니다. 3편 8장의 TCB 유예 정책과 같은 고민이 GPU에도 생깁니다.

🌐증명 경로의 네트워크

NRAS 같은 원격 검증 서비스를 쓰면 증명할 때마다 외부와 통신해야 합니다. 폐쇄망 고객이라면 로컬 검증 방식과 RIM·인증서 정보의 반입 절차를 설계해야 합니다. 이 경로가 막히면 서비스가 시작되지 못합니다.

💰비용과 견적

CC 지원 CPU·GPU 조합, 플랫폼 인증 여부, 추가 성능 여유분을 견적에 반영해야 합니다. 5장의 원리로 고객 워크로드의 영향을 예측하고, 반드시 PoC에서 측정한 값으로 확정하세요.

정리와 다음 편

  1. LLM의 가중치, KV 캐시, 중간값은 대부분 GPU 메모리에 있으므로 CPU TEE만으로는 부족합니다.
  2. GPU CC 모드는 칩 안의 신뢰 루트, 보호 메모리 영역(CPR), 암호화 복사 엔진, SPDM 세션으로 이뤄집니다.
  3. HBM은 암호화가 아니라 칩 패키지 경계와 접근 통제로 보호하고, 암호화는 PCIe·NVLink 같은 바깥 통로에 씁니다.
  4. CPU→GPU 데이터는 드라이버가 암호화해 바운스 버퍼를 거쳐 보내고, GPU 복사 엔진이 복호화합니다.
  5. 성능 비용은 GPU 연산이 아니라 암호화된 이동과 복사에서 생기며, 이동량이 많은 워크로드일수록 큽니다.
  6. Hopper Protected PCIe는 NVLink를 암호화하지 않고, Blackwell은 NVLink를 하드웨어로 암호화합니다. TEE-I/O는 바운스 버퍼를 없앨 차세대 방식입니다.
  7. GPU도 Attester이며, NVIDIA 인증서 체인과 RIM으로 검증합니다. CPU 판정과 GPU 판정은 반드시 같은 세션으로 묶어 확인해야 합니다.

5편 예고: Confidential Containers 전체 지도

하드웨어 이야기는 여기까지입니다. 5편부터는 소프트웨어로 넘어갑니다. Kubernetes 파드를 기밀 VM 안에서 실행하는 Confidential Containers(CoCo)가 Kata Containers, 게스트 안의 Attestation Agent와 Confidential Data Hub, 이미지 서명·암호화, agent 정책을 어떻게 엮는지 전체 지도를 그립니다. 베어메탈 방식과 클라우드의 peer pods 방식 차이, 그리고 이번 편의 GPU가 CoCo 파드에 어떻게 붙는지도 다룹니다.

TEE·Trustee 강의 시리즈 4편. GPU 세대별 지원 모드와 성능은 SKU, 플랫폼, 드라이버 버전에 따라 달라집니다. 시뮬레이션과 예시 토큰은 학습용으로 단순화했습니다. 실제 도입 시 NVIDIA와 각 공급사의 최신 문서를 확인하세요.
