-- 01 · why postgresql

왜 PostgreSQL인가

PostgreSQL(포스트그레스큐엘, 줄여서 Postgres)은 1986년 UC 버클리의 POSTGRES 프로젝트에서 출발한 오픈소스 관계형 데이터베이스입니다. 30년 넘게 한 번도 상업 라이선스로 전환하지 않았고, 특정 기업이 소유하지 않은 커뮤니티 프로젝트라는 점이 오늘날 클라우드 시대에 가장 큰 무기가 되었습니다.

진짜 자유로운 라이선스
PostgreSQL License는 BSD/MIT 계열입니다. 상업적으로 재배포·수정·SaaS화가 모두 가능해, 클라우드 사업자들이 관리형 서비스로 앞다투어 채택했습니다.
standard
표준 SQL 준수도 1위권
SQL:2016 표준을 가장 충실히 따르는 오픈소스 DB입니다. 여기서 배운 문법 대부분이 다른 DB에서도 통합니다.
extensible
확장(extension) 구조
본체를 고치지 않고 기능을 꽂아 넣습니다. 지리정보(PostGIS), 시계열(TimescaleDB), 벡터 검색(pgvector)까지 같은 DB 안에서 처리합니다.

실무에서 체감하는 세 가지 장면

  • "JSON도 넣고 검색도 해야 합니다" — jsonb 덕분에 별도의 문서 DB 없이 반정형 데이터를 인덱스까지 걸어 다룹니다.
  • "AI 서비스에 벡터 검색이 필요합니다" — pgvector 확장으로 임베딩 검색을 기존 DB 안에서 처리합니다. RAG 파이프라인의 기본 선택지가 되었습니다.
용어 정리

DBMS는 데이터를 저장·검색·보호하는 소프트웨어이고, RDBMS는 그중 데이터를 표(테이블) 형태로 관리하며 표 사이의 관계를 다루는 종류입니다. SQL은 그 RDBMS와 대화하는 언어입니다. PostgreSQL은 RDBMS이고, 우리가 이 강의에서 배우는 언어는 SQL입니다.

이 강의를 마치면 할 수 있는 일

  1. 테이블을 설계하고 제약조건으로 잘못된 데이터를 막을 수 있습니다.
  2. 여러 테이블을 JOIN해 원하는 보고서 형태로 데이터를 뽑을 수 있습니다.
  3. 느린 쿼리를 만나면 인덱스가 필요한 상황인지 판단할 수 있습니다.
  4. 트랜잭션으로 "절반만 반영되는 사고"를 막을 수 있습니다.
  5. MySQL·Oracle 경험자와 대화할 때 차이점을 짚어낼 수 있습니다.

NULL은 "0"도 "빈 문자열"도 아닙니다

NULL은 값이 없음/알 수 없음을 뜻하는 특별한 상태입니다. 초보자가 가장 많이 겪는 버그의 원인이므로 지금 확실히 짚어둡니다.


-- 틀린 방법: NULL은 = 로 비교되지 않습니다. 결과는 항상 '알 수 없음'
SELECT * FROM customers WHERE team_id = NULL;   -- 0건 (에러도 안 남!)

-- 올바른 방법
SELECT * FROM customers WHERE team_id IS NULL;
SELECT * FROM customers WHERE team_id IS NOT NULL;

-- 산술/문자 연결도 NULL에 오염됩니다
SELECT 100 + NULL;              -- NULL
SELECT '등급: ' || NULL;         -- NULL
SELECT count(*), count(team_id) FROM customers;  -- 3, 2  ← count(컬럼)은 NULL을 세지 않음


-- COALESCE: 첫 번째 NULL 아닌 값을 반환
SELECT name, COALESCE(team_id, 0) AS team_id FROM customers;

-- 문자 기본값
SELECT COALESCE(memo, '(작성 없음)') FROM customers;

-- NULLIF: 두 값이 같으면 NULL로 (0으로 나누기 방어)
SELECT total / NULLIF(qty, 0) AS unit_price FROM orders;

-- NULL 정렬 위치 지정
SELECT * FROM customers ORDER BY team_id DESC NULLS LAST;
규칙: NULL과의 비교는 참도 거짓도 아닌 '알 수 없음'입니다. 그래서 WHERE 조건이 조용히 0건을 반환합니다.

테이블을 나누는 이유 — 정규화의 감각

주문 정보를 한 테이블에 몰아넣으면 고객 이름이 주문마다 반복됩니다. 고객이 개명하면 수천 행을 고쳐야 하고, 일부만 고치면 데이터가 서로 모순됩니다. 그래서 중복되는 덩어리를 별도 테이블로 떼어내고 키로 연결합니다. 이것이 정규화이고, 그렇게 나뉜 테이블을 다시 합치는 도구가 JOIN(9장)입니다.


-- 한 테이블에 다 넣기: 고객명/도시가 주문마다 중복
CREATE TABLE orders_bad (
  order_id      int,
  customer_name varchar(50),   -- 중복 저장
  customer_city varchar(30),   -- 중복 저장
  product       varchar(50),
  amount        numeric(12,2)
);


-- 고객과 주문을 분리하고 FK로 연결
CREATE TABLE customers (
  id    int PRIMARY KEY,
  name  varchar(50) NOT NULL,
  city  varchar(30)
);

CREATE TABLE orders (
  id          int PRIMARY KEY,
  customer_id int NOT NULL REFERENCES customers(id),  -- 관계의 핵심
  product     varchar(50),
  amount      numeric(12,2)
);
1:N 관계 — 고객 1명이 주문 여러 건을 가집니다. "N쪽 테이블이 1쪽의 PK를 FK로 들고 있다"가 기본 패턴입니다.

다른 RDBMS와 비교

현장에서는 이미 MySQL이나 Oracle을 쓰는 시스템 옆에서 PostgreSQL을 운영하는 경우가 대부분입니다. "무엇이 더 좋은가"보다 어디가 다른가를 아는 것이 훨씬 실용적입니다.

MySQL에서 온 사람이 가장 많이 놀라는 5가지

1. 데이터베이스 ≠ 스키마

MySQL의 USE db1;은 PostgreSQL에서 \c db1(재접속)입니다. 하나의 접속으로 여러 DB를 넘나드는 쿼리는 불가능하고, 대신 같은 DB 안의 여러 스키마로 논리 분리를 합니다.

2. 문자 비교가 대소문자를 구분

MySQL 기본 콜레이션은 대소문자를 무시하지만 PostgreSQL은 구분합니다. WHERE email = 'A@x.com'이 안 잡힙니다. ILIKE 또는 citext 확장, lower() 인덱스를 사용합니다.

3. 백틱이 없고 큰따옴표는 특별한 의미

`col` 대신 "col"입니다. 그리고 큰따옴표로 감싸면 대소문자가 고정됩니다. "userName"으로 만든 컬럼은 영원히 큰따옴표로만 접근 가능합니다. 그래서 관례는 snake_case입니다.

4. AUTO_INCREMENT 대신 IDENTITY/serial

GENERATED ALWAYS AS IDENTITY가 표준이자 권장 방식입니다. 예전 방식인 serial도 여전히 동작합니다.

5. DDL도 트랜잭션에 들어갑니다

BEGIN; ALTER TABLE ...; ROLLBACK;이 됩니다. MySQL은 DDL이 암묵적 커밋을 일으키죠. 마이그레이션 스크립트를 안전하게 감쌀 수 있는 강력한 장점입니다.

-- 06 · ddl

DDL · 테이블과 제약조건

DDL(Data Definition Language)은 구조를 정의하는 SQL입니다. 핵심은 제약조건입니다. 애플리케이션 코드의 검증은 버그로 뚫릴 수 있지만, DB 제약조건은 어떤 경로로 들어와도 지켜집니다. "데이터의 마지막 방어선"이라고 부릅니다.


CREATE TABLE customers (
  id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text        NOT NULL UNIQUE,
  name       text        NOT NULL,
  city       text,
  grade      char(1)     NOT NULL DEFAULT 'C' CHECK (grade IN ('A','B','C')),
  created_at timestamptz NOT NULL DEFAULT now(),
  attrs      jsonb       NOT NULL DEFAULT '{}'::jsonb
);

CREATE TABLE orders (
  id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint      NOT NULL
              REFERENCES customers(id) ON DELETE RESTRICT,
  product     text        NOT NULL,
  qty         int         NOT NULL CHECK (qty > 0),
  amount      numeric(15,2) NOT NULL CHECK (amount >= 0),
  ordered_at  timestamptz NOT NULL DEFAULT now()
);

-- FK 컬럼 인덱스는 자동 생성되지 않습니다. 반드시 직접!
CREATE INDEX idx_orders_customer_id ON orders(customer_id);

COMMENT ON TABLE  orders IS '고객 주문 원장';
COMMENT ON COLUMN orders.amount IS '주문 총액(부가세 포함, KRW)';


-- PRIMARY KEY : 유일 + NOT NULL. 테이블당 1개
-- UNIQUE      : 유일. NULL은 여러 개 허용 (표준 동작)
-- NOT NULL    : 값 필수
-- CHECK       : 임의의 조건식
-- FOREIGN KEY : 다른 테이블 값 참조 무결성
-- EXCLUDE     : 범위 겹침 금지 등 고급 제약

-- 복합 UNIQUE: 같은 고객이 같은 상품을 같은 날 중복 주문 금지
ALTER TABLE orders
  ADD CONSTRAINT uq_daily UNIQUE (customer_id, product, ordered_at);

-- 여러 컬럼을 함께 보는 CHECK
ALTER TABLE orders
  ADD CONSTRAINT ck_amount_qty CHECK (amount >= qty * 100);

-- FK 삭제 동작 4가지
--   RESTRICT / NO ACTION : 자식이 있으면 부모 삭제 거부 (기본, 안전)
--   CASCADE              : 부모 삭제 시 자식도 삭제 (위험, 신중히)
--   SET NULL / SET DEFAULT


-- ① 생성 컬럼: 파생 값을 DB가 계산해 줍니다 (18부터 VIRTUAL이 기본)
CREATE TABLE order_items (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  qty      int NOT NULL CHECK (qty > 0),
  price    numeric(15,2) NOT NULL,
  total    numeric(15,2) GENERATED ALWAYS AS (qty * price),           -- VIRTUAL: 읽을 때 계산
  total_s  numeric(15,2) GENERATED ALWAYS AS (qty * price) STORED     -- STORED: 저장해 둠
);
--   VIRTUAL : 디스크를 쓰지 않고 항상 최신. 인덱스는 걸 수 없습니다.
--   STORED  : 저장하므로 인덱스를 걸 수 있고 조회가 빠릅니다.
--   17 이하에서는 STORED만 가능했고, 명시하지 않으면 오류였습니다.

-- ② 기간(temporal) 제약: 시간 구간이 겹치는 것을 기본키/유니크로 금지
CREATE TABLE room_booking (
  room_id  int NOT NULL,
  period   tstzrange NOT NULL,
  guest    text NOT NULL,
  PRIMARY KEY (room_id, period WITHOUT OVERLAPS)   -- 같은 방의 겹치는 예약 거부
);

왜 IDENTITY인가

-- 07 · dml

DML · 데이터 넣고 바꾸기

INSERT · UPDATE · DELETE는 단순하지만, 운영에서 사고가 가장 많이 나는 지점입니다. WHERE 없는 UPDATE/DELETE가 대표적입니다. PostgreSQL 고유의 RETURNING과 ON CONFLICT는 실무 생산성을 크게 올려줍니다.


-- 컬럼 이름을 반드시 명시하세요 (테이블 구조가 바뀌어도 안전)
INSERT INTO customers (email, name, city, grade)
VALUES ('a@ex.com', '김서준', '서울', 'A');

-- 여러 행 한 번에 (한 건씩 100번보다 훨씬 빠름)
INSERT INTO customers (email, name, city) VALUES
  ('b@ex.com', '이하윤', '부산'),
  ('c@ex.com', '박도윤', '서울'),
  ('d@ex.com', '최지우', '대전');

-- RETURNING: 생성된 id를 바로 받기 (추가 SELECT 불필요)
INSERT INTO orders (customer_id, product, qty, amount)
VALUES (1, '키보드', 2, 89000)
RETURNING id, ordered_at;

-- PostgreSQL 18: 변경 전(old)과 후(new)를 한 번에 받기
UPDATE customers SET grade = 'A' WHERE id = 3
RETURNING old.grade AS 이전등급, new.grade AS 새등급, new.name;
--   17 이하에서는 UPDATE의 RETURNING이 새 값만 돌려주어,
--   이전 값을 남기려면 SELECT를 먼저 하거나 트리거를 써야 했습니다.
DELETE FROM orders WHERE id = 10 RETURNING old.*;

-- 쿼리 결과를 그대로 삽입
INSERT INTO vip_customers (id, name)
SELECT id, name FROM customers WHERE grade = 'A';


-- 있으면 갱신, 없으면 삽입 (MERGE의 실용판)
INSERT INTO customers (email, name, city)
VALUES ('a@ex.com', '김서준', '성남')
ON CONFLICT (email)                         -- UNIQUE 제약이 있는 컬럼 기준
DO UPDATE SET city = EXCLUDED.city,          -- EXCLUDED = 넣으려던 새 행
              name = EXCLUDED.name
RETURNING id, (xmax = 0) AS inserted;        -- true면 신규, false면 갱신

-- 중복은 그냥 무시하고 넘어가기 (배치 적재에 유용)
INSERT INTO customers (email, name) VALUES ('a@ex.com','중복')
ON CONFLICT DO NOTHING;

-- 조건부 갱신: 더 최신 데이터만 반영
ON CONFLICT (email) DO UPDATE
  SET name = EXCLUDED.name
  WHERE customers.updated_at < EXCLUDED.updated_at;


UPDATE customers SET grade = 'A' WHERE id = 3;

-- 여러 컬럼 동시 변경
UPDATE customers
SET grade = 'B', city = '인천', updated_at = now()
WHERE email = 'b@ex.com';

-- 다른 테이블 값을 참조해 갱신 (PostgreSQL의 UPDATE ... FROM)
UPDATE customers c
SET grade = 'A'
FROM (SELECT customer_id, sum(amount) s FROM orders GROUP BY 1) t
WHERE c.id = t.customer_id AND t.s >= 1000000;

-- 안전 습관: 먼저 SELECT로 대상 확인 → 그다음 UPDATE
SELECT count(*) FROM customers WHERE city IS NULL;  -- 몇 건인지 먼저
UPDATE customers SET city = '미지정' WHERE city IS NULL RETURNING id;


DELETE FROM orders WHERE id = 10;
DELETE FROM orders WHERE ordered_at < now() - interval '3 years';

-- 서브쿼리 조건
DELETE FROM orders
WHERE customer_id IN (SELECT id FROM customers WHERE grade = 'C');

DELETE FROM logs;     -- 행마다 처리 + 트랜잭션 로그, 공간도 즉시 반환 안 됨
TRUNCATE logs;        -- 파일 단위 처리, 즉시 완료

BEGIN;                                  -- 1) 트랜잭션으로 감싸기

-- 결과 행 수 확인 후
ROLLBACK;                               -- 잘못됐으면 되돌리기 / 맞으면 COMMIT
운영 규칙: UPDATE/DELETE는 항상 트랜잭션 안에서, 실행 전 같은 WHERE로 SELECT count(*), RETURNING으로 영향 행 확인.
가장 흔한 사고

UPDATE orders SET amount = 0; — WHERE를 빼먹으면 모든 행이 바뀝니다. 에러도 나지 않습니다. psql에서 \set AUTOCOMMIT off를 켜두거나, 운영 접속은 항상 BEGIN;으로 시작하는 습관을 만드세요. 되돌릴 수 있는 유일한 순간은 COMMIT 전입니다.

-- 08 · select

SELECT 완전 분해

SELECT는 SQL의 90%입니다. 그리고 SQL이 어려워 보이는 이유는 쓰는 순서와 실행 순서가 다르기 때문입니다. 이 순서를 머리에 넣으면 대부분의 혼란이 사라집니다.


SELECT   city, count(*) AS cnt        -- 5. 무엇을 보여줄지
FROM     customers                     -- 1. 어디서
WHERE    grade <> 'C'                  -- 2. 어떤 행만
GROUP BY city                          -- 3. 어떻게 묶어서
HAVING   count(*) >= 2                 -- 4. 묶은 결과 중 어떤 것만
ORDER BY cnt DESC                      -- 6. 어떤 순서로
LIMIT    10;                           -- 7. 몇 개만


1) FROM / JOIN   테이블을 준비한다
2) WHERE         행 단위로 걸러낸다        ← 집계 함수 사용 불가
3) GROUP BY      같은 값끼리 묶는다
4) HAVING        묶인 그룹을 걸러낸다      ← 집계 함수 사용 가능
5) SELECT        컬럼을 계산하고 별칭을 붙인다
6) ORDER BY      정렬한다                  ← 5번의 별칭 사용 가능
7) LIMIT/OFFSET  잘라낸다

이 순서 때문에 생기는 규칙:
  · WHERE에 count(*)를 쓸 수 없다 → HAVING으로
  · WHERE에 SELECT의 별칭을 쓸 수 없다 → ORDER BY에서는 가능
"WHERE에서는 별칭을 못 쓰는데 ORDER BY에서는 되는" 이유가 바로 이 실행 순서입니다.

-- 주문과 고객 이름 함께 보기 (짝 있는 것만)
SELECT o.id, c.name, o.product, o.amount
FROM orders o
JOIN customers c ON c.id = o.customer_id;      -- INNER는 생략 가능

-- 모든 고객 + 주문 요약 (주문 0건인 고객도 포함)
SELECT c.name, count(o.id) AS 주문수, COALESCE(sum(o.amount),0) AS 총액
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY 총액 DESC;

-- 컬럼 이름이 같을 때는 USING으로 짧게
SELECT * FROM orders JOIN customers USING (customer_id);


-- 주문이 한 건도 없는 고객 찾기 (anti-join)
-- 방법 1: LEFT JOIN + IS NULL
SELECT c.*
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- 방법 2: NOT EXISTS (가독성·성능 모두 권장)
SELECT c.*
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- 방법 3: NOT IN  ← 서브쿼리에 NULL이 있으면 결과가 0건이 됩니다. 피하세요.
SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);


SELECT o.id, c.name, p.category, s.status_label
FROM orders o
JOIN customers c   ON c.id = o.customer_id
JOIN products  p   ON p.code = o.product_code
LEFT JOIN statuses s ON s.code = o.status_code   -- 상태 코드가 없는 주문도 살림
WHERE o.ordered_at >= date_trunc('month', now())
ORDER BY o.ordered_at DESC;

-- 각 고객의 '최근 주문 1건'만 붙이기: LATERAL이 가장 깔끔합니다
SELECT c.name, r.product, r.ordered_at
FROM customers c
LEFT JOIN LATERAL (
  SELECT product, ordered_at FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY ordered_at DESC LIMIT 1
) r ON true;


-- 실수 1: LEFT JOIN 후 오른쪽 테이블 조건을 WHERE에 넣으면 INNER가 되어버립니다
SELECT c.name, o.amount
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.amount > 100000;              -- 주문 없는 고객이 사라짐!

-- 해결: 조건을 ON 절로 옮깁니다
SELECT c.name, o.amount
FROM customers c LEFT JOIN orders o
  ON o.customer_id = c.id AND o.amount > 100000;

-- 실수 2: JOIN 조건을 빼먹으면 CROSS JOIN이 되어 행이 폭발합니다 (M×N)
SELECT * FROM orders o, customers c;   -- 8행 × 6행 = 48행

-- 실수 3: 1:N JOIN 후 sum()이 부풀려집니다 (fan-out)
--         고객당 주문이 3건이면 고객 정보가 3번 세어집니다.
--         먼저 집계한 뒤 JOIN하거나 서브쿼리로 분리하세요.
실수 1과 3은 실무 리뷰에서 가장 자주 지적되는 두 가지입니다. LEFT JOIN을 썼다면 WHERE에 오른쪽 컬럼 조건이 없는지 항상 확인하세요.
-- 10 · subquery / cte / window

서브쿼리 · CTE · 윈도우 함수

여기까지 오면 "SQL로 이런 것도 되나?" 싶은 영역이 열립니다. 특히 윈도우 함수는 순위·누적합·전월 대비를 애플리케이션 코드 없이 한 방에 처리해 주는 도구로, 배우는 순간 생산성이 달라집니다.

서브쿼리 — 쿼리 안의 쿼리


-- 1) 스칼라 서브쿼리: 값 하나를 반환 (SELECT 목록/WHERE 우변)
SELECT name, amount,
       amount - (SELECT avg(amount) FROM orders) AS 평균과의차이
FROM orders;

-- 2) IN 서브쿼리: 목록을 반환
SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount > 1000000);

-- 3) FROM 서브쿼리(인라인 뷰): 표를 반환 — 반드시 별칭 필요
SELECT city, avg(cnt) FROM (
  SELECT c.city, count(*) AS cnt
  FROM orders o JOIN customers c ON c.id = o.customer_id
  GROUP BY c.city, c.id
) t
GROUP BY city;


-- EXISTS: 있는지만 확인 (첫 행을 찾으면 즉시 중단해 효율적)
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.customer_id = c.id AND o.amount > 500000);

-- NOT EXISTS: 없는 것 찾기 (NULL에도 안전)
SELECT * FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- IN vs EXISTS: 최신 PostgreSQL 플래너는 대개 같은 계획으로 변환합니다.
-- 다만 서브쿼리에 NULL이 섞이면 NOT IN은 예상과 다른 결과를 냅니다.

CTE(WITH) — 쿼리에 이름을 붙여 계단처럼 쌓기


WITH monthly AS (
  SELECT date_trunc('month', ordered_at) AS m, sum(amount) AS total
  FROM orders
  GROUP BY 1
),
ranked AS (
  SELECT m, total, rank() OVER (ORDER BY total DESC) AS rk
  FROM monthly
)
SELECT * FROM ranked WHERE rk <= 3;

-- 장점: 복잡한 쿼리를 위에서 아래로 읽히게 만듭니다.
-- 참고: PostgreSQL 12부터 CTE는 기본적으로 인라인 처리되어 성능 손실이 거의 없습니다.
--       일부러 분리 실행하려면 MATERIALIZED, 막으려면 NOT MATERIALIZED를 명시합니다.


-- 조직도처럼 자기 자신을 참조하는 계층 구조 순회
WITH RECURSIVE tree AS (
  SELECT id, name, manager_id, 1 AS depth
  FROM employees WHERE manager_id IS NULL      -- 시작점(앵커)
  UNION ALL
  SELECT e.id, e.name, e.manager_id, t.depth + 1
  FROM employees e
  JOIN tree t ON e.manager_id = t.id           -- 반복 부분
)
SELECT repeat('  ', depth - 1) || name AS 조직도, depth FROM tree ORDER BY depth;

-- 날짜 축 만들기 (빈 날짜 없는 리포트용)
SELECT d::date FROM generate_series('2026-08-01'::date, '2026-08-31', '1 day') d;

윈도우 함수 — 그룹으로 묶지 않고 그룹 계산하기

GROUP BY는 여러 행을 하나로 합칩니다. 윈도우 함수는 행을 그대로 두고 옆에 계산 결과 컬럼을 붙입니다. 이 차이가 핵심입니다.


SELECT c.city, c.name, sum(o.amount) AS 총액,
       row_number() OVER (PARTITION BY c.city ORDER BY sum(o.amount) DESC) AS 도시내순번,
       rank()       OVER (ORDER BY sum(o.amount) DESC) AS 전체순위,
       dense_rank() OVER (ORDER BY sum(o.amount) DESC) AS 촘촘한순위
FROM customers c JOIN orders o ON o.customer_id = c.id
GROUP BY c.city, c.id, c.name;

-- PARTITION BY = 그룹 나누기, ORDER BY = 그룹 안 정렬
-- row_number: 1,2,3,4   rank: 1,1,3,4   dense_rank: 1,1,2,3

-- 각 도시의 1위 고객만 뽑기
SELECT * FROM (
  SELECT c.city, c.name, sum(o.amount) t,
         row_number() OVER (PARTITION BY c.city ORDER BY sum(o.amount) DESC) rn
  FROM customers c JOIN orders o ON o.customer_id = c.id
  GROUP BY c.city, c.id, c.name
) x WHERE rn = 1;


-- 누적 합계
SELECT ordered_at, amount,
       sum(amount) OVER (ORDER BY ordered_at
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS 누적액
FROM orders;

-- 7일 이동 평균
SELECT ordered_at, amount,
       round(avg(amount) OVER (ORDER BY ordered_at
             ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 0) AS 이동평균7
FROM orders;

-- 전체 대비 비율
SELECT product, sum(amount) AS s,
       round(100.0 * sum(amount) / sum(sum(amount)) OVER (), 1) AS 비중pct
FROM orders GROUP BY product ORDER BY s DESC;


-- 전월 대비 증감 (lag)
WITH m AS (
  SELECT date_trunc('month', ordered_at) AS mon, sum(amount) AS total
  FROM orders GROUP BY 1
)
SELECT mon, total,
       lag(total) OVER (ORDER BY mon) AS 전월,
       total - lag(total) OVER (ORDER BY mon) AS 증감,
       round(100.0 * (total - lag(total) OVER (ORDER BY mon))
             / NULLIF(lag(total) OVER (ORDER BY mon), 0), 1) AS 증감률pct
FROM m ORDER BY mon;

-- lead(): 다음 행, first_value()/last_value(): 구간의 처음/끝
-- 4분위 나누기
SELECT name, amount, ntile(4) OVER (ORDER BY amount DESC) AS 분위
FROM orders;
순위·누적·전기간 비교를 애플리케이션에서 루프로 계산하고 있다면, 그 코드는 대부분 윈도우 함수 한 줄로 대체됩니다.

인덱스가 동작하는 원리 — B-tree

PostgreSQL의 기본 인덱스는 B-tree입니다. 정렬된 값을 트리 구조로 보관해, 100만 행이라도 3~4번의 점프로 원하는 위치에 도달합니다. 값이 정렬되어 있으므로 =뿐 아니라 <, >, BETWEEN, ORDER BY, LIKE '접두사%'에도 쓰입니다.


-- 기본
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- 운영 중이라면 반드시 CONCURRENTLY (테이블 쓰기를 막지 않음)
CREATE INDEX CONCURRENTLY idx_orders_ordered_at ON orders (ordered_at DESC);

-- 복합 인덱스: 여러 컬럼을 한 인덱스로
CREATE INDEX idx_orders_cust_date ON orders (customer_id, ordered_at DESC);

-- 부분 인덱스: 조건에 맞는 행만 색인 → 크기가 작고 빠름
CREATE INDEX idx_orders_active ON orders (ordered_at)
  WHERE status = 'ACTIVE';

-- 표현식 인덱스: 대소문자 무시 검색용
CREATE INDEX idx_customers_email_lower ON customers (lower(email));
-- 이 인덱스는 다음 쿼리에서만 쓰입니다:
--   WHERE lower(email) = lower('A@Ex.com')

-- 자동으로 만들어지는 인덱스: PRIMARY KEY, UNIQUE 제약
-- 자동으로 만들어지지 않는 것: FOREIGN KEY 컬럼  ← 직접 만들어야 합니다


-- 복합 인덱스 (a, b)는 '전화번호부'와 같습니다: 성 → 이름 순 정렬
CREATE INDEX idx_ab ON t (city, grade);

-- 사용 가능
WHERE city = '서울'                      -- 선두 컬럼만 사용 (OK)
WHERE city = '서울' AND grade = 'A'      -- 둘 다 사용 (최적)
WHERE city = '서울' ORDER BY grade       -- 정렬까지 인덱스로 해결

-- 선두 컬럼 조건이 없는 경우
WHERE grade = 'A'
--   17 이하: 선두 컬럼(city) 조건이 없으면 인덱스를 거의 쓰지 못해 Seq Scan
--   18부터: "스킵 스캔(skip scan)"으로 이 인덱스를 쓸 수 있습니다.
--           city의 값 종류를 하나씩 건너뛰며 grade 조건을 찾는 방식입니다.
--   다만 city의 값 종류가 많으면 건너뛸 횟수도 많아져 이득이 줄어듭니다.
--   → 여전히 (grade, ...) 전용 인덱스가 가장 빠릅니다. 스킵 스캔은 안전망입니다.

-- 순서 정하는 원칙
--   1) 등호(=) 조건 컬럼을 앞에
--   2) 선택도가 높은(값 종류가 많은) 컬럼을 앞에
--   3) 범위(>, <) 조건 컬럼은 뒤에
--   4) ORDER BY 컬럼은 범위 조건 다음에


-- 1) 컬럼에 함수/연산을 씌운 경우
WHERE date_trunc('day', ordered_at) = '2026-08-10'    -- 못 씀
WHERE ordered_at >= '2026-08-10' AND ordered_at < '2026-08-11'  -- 씀

-- 2) 타입이 다른 비교 (암묵적 변환)
WHERE customer_id = '123'      -- 문자와 숫자 비교 → 상황에 따라 못 씀

-- 3) 앞이 열린 LIKE
WHERE name LIKE '%준'          -- 못 씀 → pg_trgm 확장 + GIN 인덱스로 해결

-- 4) NOT / <> 조건, OR 로 흩어진 조건
WHERE status <> 'DONE'         -- 대개 못 씀 (부분 인덱스로 우회)

-- 5) 결과가 테이블의 상당 비율일 때
--    → 플래너가 "전체 읽는 게 더 빠르다"고 판단. 이건 정상 동작입니다.


-- 계획만 보기 (실행하지 않음)
EXPLAIN SELECT * FROM orders WHERE customer_id = 1;

-- 실제 실행하고 실측값까지 보기
EXPLAIN (ANALYZE) SELECT * FROM orders WHERE customer_id = 1;
--   PostgreSQL 18부터 ANALYZE에 BUFFERS가 자동 포함됩니다.
--   17 이하에서는 EXPLAIN (ANALYZE, BUFFERS) 로 직접 켜야 했습니다.

/* 읽는 요령
   Seq Scan on orders        ← 전체 읽음. 큰 테이블이면 개선 후보
   Index Scan using idx_...  ← 인덱스 사용 (좋음)
   Bitmap Heap Scan          ← 인덱스로 위치를 모아 한 번에 읽음 (중간 규모에 적합)
   rows=1000 vs actual rows=98000   ← 추정과 실제가 크게 다르면 ANALYZE 필요
   loops=5000                ← 반복 횟수. 여기에 시간이 곱해집니다
   Index Searches: 4         ← 18부터 표시. 스킵 스캔이 몇 번 건너뛰었는지 알려줍니다
*/
ANALYZE orders;   -- 통계 정보 갱신
인덱스는 공짜가 아닙니다. INSERT/UPDATE/DELETE마다 인덱스도 갱신되고 디스크도 차지합니다. 안 쓰이는 인덱스는 순수한 비용입니다.
인덱스 3원칙

1) WHERE·JOIN·ORDER BY에 자주 등장하는 컬럼에만 만듭니다. 2) 컬럼마다 하나씩 만드는 대신 실제 쿼리 패턴에 맞는 복합 인덱스를 만듭니다. 3) 만든 뒤에는 pg_stat_user_indexes.idx_scan으로 실제 사용 여부를 확인하고, 안 쓰이면 삭제합니다.

트랜잭션과 ACID

계좌 A에서 100원을 빼고 계좌 B에 100원을 넣는 두 문장 사이에서 장애가 나면 돈이 사라집니다. 트랜잭션은 "전부 성공 아니면 전부 취소"를 보장하는 장치입니다.

A
원자성 Atomicity
전부 반영되거나 전부 취소됩니다. 중간 상태는 남지 않습니다.
C
일관성 Consistency
제약조건을 위반하는 상태로 끝나지 않습니다.
I
고립성 Isolation
동시에 실행되는 다른 트랜잭션의 중간 상태가 보이지 않습니다.
D
지속성 Durability
커밋된 결과는 서버가 죽어도 남습니다(WAL 덕분).

   Phantom Read    : 같은 조건 재조회 시 행 수가 달라짐 — RR부터 방지
   Serialization   : SERIALIZABLE에서는 충돌 시 40001 에러 → 애플리케이션이 재시도해야 함

  UPDATE products SET stock = stock - 1 WHERE id = 5;
COMMIT;

-- 기다리지 않고 즉시 실패시키기
SELECT ... FOR UPDATE NOWAIT;
-- 잠긴 행은 건너뛰기 (작업 큐 패턴에 유용)
SELECT ... FOR UPDATE SKIP LOCKED LIMIT 10;

-- 사실 단일 문장이면 잠금을 직접 걸 필요가 없습니다 (원자적으로 처리됨)

알아두면 좋은 사실

PostgreSQL은 MVCC(다중 버전 동시성 제어)로 동작합니다. UPDATE는 기존 행을 덮어쓰지 않고 새 버전을 추가하고 옛 버전에 "여기까지 유효" 표시를 남깁니다. 그래서 읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않습니다. 대신 옛 버전을 정리하는 VACUUM이 필요하며, 이 주제는 고급 강의에서 깊게 다룹니다.

PostgreSQL만의 무기

여기까지는 대부분의 RDBMS에 공통인 내용이었습니다. 이제 "PostgreSQL을 골라야 하는 이유"에 해당하는 기능들을 살펴봅니다.

jsonb — 관계형과 문서형을 한 DB에서


CREATE TABLE events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload jsonb NOT NULL
);
INSERT INTO events (payload) VALUES
 ('{"user":{"id":7,"name":"김서준"},"tags":["ai","gpu"],"latency_ms":231}');

-- 핵심 연산자
SELECT payload -> 'user'            FROM events;  -- jsonb 반환
SELECT payload ->> 'latency_ms'     FROM events;  -- text 반환
SELECT payload #> '{user,name}'     FROM events;  -- 경로로 jsonb
SELECT payload #>> '{user,name}'    FROM events;  -- 경로로 text
SELECT payload ? 'tags'             FROM events;  -- 키 존재 여부
SELECT payload @> '{"tags":["gpu"]}'::jsonb FROM events;  -- 포함 여부


-- 숫자 비교는 명시적 형변환 필요 (->> 는 text)
SELECT * FROM events WHERE (payload ->> 'latency_ms')::int > 200;

-- 포함(@>) 조건을 위한 GIN 인덱스
CREATE INDEX idx_events_payload ON events USING gin (payload);
SELECT * FROM events WHERE payload @> '{"user":{"id":7}}';

-- 특정 키만 자주 쓰면 표현식 B-tree 인덱스가 더 작고 빠릅니다
CREATE INDEX idx_events_user_id ON events (((payload -> 'user' ->> 'id')::int));

-- JSONPath (PostgreSQL 12+)
SELECT * FROM events WHERE payload @@ '$.latency_ms > 200';


-- 값 갱신
UPDATE events SET payload = jsonb_set(payload, '{latency_ms}', '150') WHERE id = 1;
-- 키 추가(병합)
UPDATE events SET payload = payload || '{"region":"kr-central"}'::jsonb;
-- 키 삭제
UPDATE events SET payload = payload - 'region';

-- 배열/객체를 행으로 펼치기
SELECT id, tag FROM events, jsonb_array_elements_text(payload -> 'tags') AS tag;
SELECT id, key, value FROM events, jsonb_each(payload -> 'user');

-- 관계형 결과를 JSON으로 조립 (API 응답에 유용)
SELECT jsonb_build_object('city', city, 'names', jsonb_agg(name))
FROM customers GROUP BY city;
원칙: 검색·집계·제약이 필요한 필드는 일반 컬럼으로, 스키마가 자주 변하는 부수 속성만 jsonb에 담습니다. 전부 jsonb에 넣으면 관계형의 장점을 모두 버리게 됩니다.

알아두면 유용한 나머지

배열과 범위 타입, 그리고 기간 제약

태그 목록을 text[]로, 예약 구간을 tstzrange로 저장합니다. 18부터는 PRIMARY KEY (room_id, period WITHOUT OVERLAPS) 한 줄로 예약 시간 겹침을 기본키가 막아줍니다(이전에는 EXCLUDE USING gist를 써야 했습니다). 애플리케이션 코드로는 동시성 때문에 완벽히 막기 어려운 문제입니다.

생성 컬럼과 IDENTITY

total numeric GENERATED ALWAYS AS (qty * price) — 파생 값을 DB가 계산합니다. 18부터 기본값이 VIRTUAL(읽을 때 계산)이고, 인덱스를 걸어야 하면 STORED를 명시합니다. 애플리케이션이 계산을 빼먹어 데이터가 어긋나는 일이 없습니다.

확장(extension) 생태계

CREATE EXTENSION pg_stat_statements;(쿼리 통계) pg_trgm(부분 문자열 검색) postgis(지리정보) pgvector(임베딩 검색) pgcrypto(암호화) uuid-ossp. 필요한 기능을 DB 안에서 확보합니다.

선언적 파티셔닝

월별로 테이블을 쪼개 오래된 데이터를 DETACH 한 번으로 분리합니다. 로그·이벤트 테이블 운영의 표준 기법이며, 고급 강의에서 자세히 다룹니다.

18의 조회 성능 개선

설정을 바꾸지 않아도 이득을 보는 항목들입니다. 비동기 I/O로 순차 스캔·비트맵 스캔·VACUUM의 읽기가 빨라지고, 스킵 스캔으로 복합 인덱스가 쓰이는 경우가 늘었으며, 불필요한 자기 조인이 자동으로 제거되고 OR 조건이 배열 조건으로 바뀌어 인덱스를 더 잘 씁니다.

전문 검색과 벡터 검색

tsvector 기반 전문 검색이 내장되어 있고, pgvector로 코사인 유사도 검색이 가능합니다. RAG 서비스에서 메타데이터 필터 + 벡터 검색을 한 쿼리로 처리할 수 있는 것이 큰 강점입니다.

논리 복제와 CDC

테이블 단위로 다른 PostgreSQL이나 Kafka(Debezium)로 변경 사항을 흘려보낼 수 있습니다. 무중단 메이저 업그레이드와 데이터 파이프라인의 기반입니다.

실행 순서가 FROM → WHERE → GROUP BY → HAVING이므로, WHERE 시점에는 그룹이 존재하지 않습니다. 그룹에 대한 조건은 HAVING에 씁니다.
Q4"모든 고객과, 주문이 있으면 그 내역"을 함께 보려면?
왼쪽(customers)을 모두 남기고 짝이 없으면 오른쪽을 NULL로 채우는 것이 LEFT JOIN입니다. INNER JOIN은 주문이 없는 고객을 제거합니다.
Q5다음 쿼리의 문제점은?
SELECT c.name FROM customers c LEFT JOIN orders o ON o.customer_id=c.id WHERE o.amount > 1000;
LEFT JOIN으로 채워진 NULL은 > 1000 조건을 만족하지 못해 걸러집니다. 오른쪽 테이블 조건은 ON 절로 옮겨야 LEFT JOIN의 의도가 유지됩니다.
Q6복합 인덱스 (city, grade)가 가장 효율적으로 쓰이지 못하는 조건은?
복합 인덱스는 전화번호부처럼 선두 컬럼부터 정렬됩니다. 선두 컬럼(city) 조건이 없는 경우가 가장 불리합니다. PostgreSQL 18부터는 스킵 스캔으로 이런 조건에서도 인덱스를 쓸 수 있지만, 선두 컬럼의 값 종류가 많으면 건너뛸 횟수가 늘어 이득이 줄어듭니다. 여전히 (grade, …) 전용 인덱스가 가장 빠릅니다.
Q7인덱스가 사용되지 않는 대표적 조건은?
컬럼에 함수를 씌우면 인덱스에 저장된 원본 값과 매칭할 수 없습니다. 범위 조건으로 바꾸거나 표현식 인덱스를 만들어야 합니다.
Q8PostgreSQL의 기본 트랜잭션 격리수준은?
기본값은 READ COMMITTED이며, 매 문장이 시작될 때의 최신 커밋 상태를 봅니다. 참고로 MySQL InnoDB의 기본값은 REPEATABLE READ입니다.
Q9"있으면 갱신, 없으면 삽입"을 한 문장으로 처리하는 PostgreSQL 문법은?
두 번째는 MySQL, 세 번째는 MySQL/SQLite 문법입니다. PostgreSQL은 ON CONFLICT ... DO UPDATE SET col = EXCLUDED.col 형태를 사용합니다.
Q10PostgreSQL 18에서 GENERATED ALWAYS AS (qty * price)로 만든 컬럼은?
18부터 생성 컬럼의 기본값이 VIRTUAL로 바뀌었습니다. 디스크를 쓰지 않고 항상 최신 값을 주지만 인덱스를 걸 수 없습니다. 조회 성능을 위해 인덱스가 필요하면 STORED를 명시하세요. 17 이하에서는 STORED가 필수였습니다.
Q11PostgreSQL과 MySQL의 구조적 차이로 맞는 설명은?
PostgreSQL에서 DB는 완전히 분리된 단위이므로 교차 조회에는 postgres_fdw나 dblink가 필요합니다. 논리 분리는 스키마로 합니다. 또한 DDL은 트랜잭션 안에서 롤백 가능하고, 문자 비교는 대소문자를 구분합니다.
