2장

역할과 속성

PostgreSQL에는 "사용자"와 "그룹"이 따로 없고 모두 역할(role)입니다. 로그인할 수 있는 역할을 사용자라고 부를 뿐입니다. 역할은 클러스터 공용 객체입니다(6편).

CREATE ROLE app_user LOGIN PASSWORD 'S3cure!pass';      -- 로그인 가능한 역할
CREATE USER app_user PASSWORD 'S3cure!pass';            -- 위와 같음 (CREATE USER는 LOGIN이 기본)
CREATE ROLE readonly NOLOGIN;                           -- 권한 묶음용 그룹 역할
GRANT readonly TO app_user;                             -- 멤버로 추가
ALTER ROLE app_user VALID UNTIL '2027-03-31';           -- 비밀번호 만료일
ALTER ROLE app_user CONNECTION LIMIT 50;
DROP ROLE app_user;                                     -- 소유 객체가 있으면 실패 → REASSIGN OWNED / DROP OWNED 먼저

EPAS는 Oracle 방식 문법도 받아들입니다: CREATE USER app_user IDENTIFIED BY 'S3cure!pass';

속성의미
LOGIN접속 가능. 없으면 그룹 역할로만 쓰임
SUPERUSER모든 권한 검사를 건너뜀. 운영 계정에는 주지 않는 것이 원칙
CREATEDB데이터베이스 생성 가능
CREATEROLE역할 생성·관리 가능 (PG16부터 자신이 만든 역할 위주로 제한)

자주 필요한 관리 권한은 슈퍼유저를 주지 않고 미리 정의된 역할로 부여합니다.

MSP 모니터링 에이전트가 쓰는 DB 계정을 편의상 슈퍼유저로 만드는 경우가 많습니다. 에이전트 서버가 뚫리면 곧바로 DB 전체가 넘어갑니다. CREATE ROLE monitor LOGIN PASSWORD '...'; GRANT pg_monitor TO monitor;로 대부분의 수집 항목을 충족할 수 있습니다.

3장

권한: GRANT와 REVOKE

객체를 만든 역할이 소유자가 되고, 소유자와 슈퍼유저는 그 객체에 모든 권한을 가집니다. 다른 역할이 쓰려면 권한을 부여받아야 합니다.

대상권한
데이터베이스CONNECT, CREATE(스키마 생성), TEMPORARY
스키마USAGE(안의 객체에 접근), CREATE(객체 생성)
테이블·뷰SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, MAINTAIN(PG17+). 컬럼 단위 SELECT·UPDATE도 가능
시퀀스USAGE, SELECT, UPDATE
함수·프로시저EXECUTE
테이블스페이스CREATE

테이블 하나를 읽으려면 문이 세 개

app_user가 sales DB의 hr.emp를 조회하려 합니다. 필요한 권한을 하나씩 켜 보세요.

문 1 · 데이터베이스
문 2 · 스키마
문 3 · 테이블
GRANT USAGE ON SCHEMA hr TO readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA hr TO readonly;      -- 지금 있는 테이블만
ALTER DEFAULT PRIVILEGES FOR ROLE hr_owner IN SCHEMA hr
  GRANT SELECT ON TABLES TO readonly;                     -- 앞으로 hr_owner가 만들 테이블까지
GRANT SELECT (empno, ename) ON hr.emp TO intern;          -- 컬럼 단위
GRANT SELECT ON hr.emp TO team_lead WITH GRANT OPTION;    -- 받은 권한을 다시 줄 수 있게
REVOKE CONNECT ON DATABASE sales FROM PUBLIC;             -- 기본 CONNECT 회수
\dp hr.*                                                  -- psql: 권한 목록
시험 포인트

① GRANT ... ON ALL TABLES IN SCHEMA는 실행 시점에 있는 테이블에만 적용되고, 앞으로 만들 테이블은 ALTER DEFAULT PRIVILEGES로 처리합니다. ② PUBLIC(모든 역할)에는 기본적으로 데이터베이스 CONNECT·TEMPORARY, 함수 EXECUTE가 부여되어 있습니다. ③ 테이블 권한이 있어도 스키마 USAGE가 없으면 접근할 수 없습니다.

4장

pg_hba.conf 읽는 법

HBA는 host-based authentication의 약자입니다. 한 줄이 규칙 하나이며, 형식은 다음과 같습니다.

# TYPE    DATABASE    USER        ADDRESS          METHOD          [OPTIONS]
local     all         all                          peer
host      sales       app_user    10.0.3.0/24      scram-sha-256
hostssl   all         dba         0.0.0.0/0        cert
host      replication repl_user   10.0.2.0/24      scram-sha-256
필드값
TYPElocal(유닉스 소켓), host(TCP, SSL 여부 무관), hostssl(TCP+SSL만), hostnossl(SSL 아닌 TCP만), hostgssenc/hostnogssenc
DATABASEDB 이름, all, sameuser, samerole, replication(물리 복제 연결), @파일, 쉼표로 여러 개
USER역할 이름, all, +그룹(그 그룹의 멤버), @파일
ADDRESSCIDR(10.0.3.0/24), 호스트 이름, samehost, samenet. local 줄에는 없음
METHOD인증 방식 (5장)
시험 포인트: 매칭 규칙 네 가지

① 위에서부터 처음 맞는 한 줄만 사용합니다. ② 그 줄의 인증이 실패해도 다음 줄로 넘어가지 않고 접속이 거부됩니다. ③ 맞는 줄이 하나도 없으면 no pg_hba.conf entry for host ... 오류로 거부됩니다. ④ DATABASE의 all은 물리 복제 연결을 포함하지 않으며, 복제는 replication으로 따로 허용해야 합니다. 그래서 좁은 규칙(특정 사용자·주소)을 위에, 넓은 규칙을 아래에 둡니다.

수정 후에는 reload로 적용하고, 적용 전에 pg_hba_file_rules 뷰로 문법 오류를 확인합니다. reload 때 파일에 오류가 있으면 이전 규칙이 그대로 유지됩니다.

SELECT line_number, type, database, user_name, address, auth_method, error
FROM   pg_hba_file_rules;
SELECT pg_reload_conf();

인증 방식

METHOD동작쓰는 곳
trust검사 없이 허용운영 금지. 3편 initdb 경고의 원인
reject무조건 거부특정 대역을 명시적으로 막을 때
scram-sha-256비밀번호를 평문으로 보내지 않는 도전-응답 방식비밀번호 인증의 표준
md5옛 해시 방식. 저장된 비밀번호가 SCRAM이면 자동으로 SCRAM으로 동작PG18에서 MD5 비밀번호 폐지 예고
password평문 비밀번호 전송SSL 없이 쓰면 위험
peerOS 사용자 이름 = DB 사용자 이름이면 허용 (로컬 소켓 전용)서버 안의 관리 작업 (sudo su - enterprisedb 후 psql)
identpeer의 TCP판. 클라이언트의 ident 서버에 물어봄거의 쓰지 않음
cert클라이언트 SSL 인증서로 인증 (hostssl 전용)관리자·서비스 계정의 비밀번호 없는 강한 인증
ldap, radius, pam외부 인증 서버에 확인사내 디렉터리(AD 등) 연동
gss, sspiKerberos 기반Active Directory 통합 인증
oauthOAuth 2.0 토큰(베어러 토큰)으로 인증 (PG18+)외부 ID 공급자 연동. 토큰 검증 모듈이 필요

비밀번호 저장 방식

SHOW password_encryption;      -- scram-sha-256 (PG14부터 기본값)
SELECT rolname, left(rolpassword, 14) FROM pg_authid WHERE rolcanlogin;   -- 슈퍼유저만
--  app_user | SCRAM-SHA-256$     ← 정상
--  old_app  | md5a1b2c3...       ← 옛 방식, 비밀번호를 다시 설정해 전환 필요
시험 포인트: PostgreSQL 18의 MD5 폐지 예고

PostgreSQL 18부터 MD5 비밀번호는 향후 제거 대상(deprecated)으로, MD5 비밀번호를 설정하면 경고가 나옵니다. 오래된 시스템을 옮겨 올 때는 password_encryption = scram-sha-256 상태에서 비밀번호를 다시 설정해 SCRAM으로 바꾸고, pg_hba.conf의 METHOD도 scram-sha-256으로 맞추세요. 오래된 클라이언트 드라이버는 SCRAM을 지원하지 않을 수 있으니 전환 전에 확인합니다.

6장

SSL/TLS 암호화

# postgresql.conf (서버 측)
ssl = on
ssl_cert_file = 'server.crt'          # PGDATA 기준 상대 경로 가능
ssl_key_file  = 'server.key'          # 권한 0600, enterprisedb 소유여야 함
ssl_ca_file   = 'root.crt'            # 클라이언트 인증서 검증용 (cert 인증 시)
ssl_min_protocol_version = 'TLSv1.2'  # 기본값

ssl = on은 SSL 사용을 허용할 뿐, 강제하지는 않습니다. 강제하려면 pg_hba.conf에서 hostssl 줄만 허용하고 host로 들어오는 비SSL 연결을 막아야 합니다. ssl 관련 설정은 reload로 적용됩니다.

클라이언트 sslmode

sslmode암호화서버 인증서 검증막아 주는 것
disable안 함—없음
allow / prefer(기본)서버가 원하면 / 가능하면안 함도청 일부 (강제 아님)
require반드시안 함도청
verify-ca반드시신뢰하는 CA가 서명했는지도청 + 가짜 서버 대부분
verify-full반드시CA + 호스트 이름 일치도청 + 중간자 공격
시험 포인트

중간자(MITM) 공격까지 막으려면 클라이언트가 verify-full을 써야 합니다. require는 암호화만 보장하고 상대가 진짜 서버인지는 확인하지 않습니다. 현재 연결이 SSL인지는 SELECT * FROM pg_stat_ssl WHERE pid = pg_backend_pid();나 psql의 \conninfo로 확인합니다.

7장

행 단위 보안(RLS)

테이블 권한은 "테이블 전체를 볼 수 있나"만 정합니다. 행 단위 보안(Row-Level Security)은 같은 테이블에서도 사용자마다 보이는 행을 다르게 만듭니다. 영업사원은 자기 고객만, 지점장은 자기 지점만 보게 하는 식입니다.

ALTER TABLE sales.orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY own_orders ON sales.orders
  USING (sales_rep = current_user)          -- 조회·수정·삭제할 수 있는 행
  WITH CHECK (sales_rep = current_user);    -- 새로 넣거나 바꾼 결과가 만족해야 할 조건
order_idcustomeramountsales_rep
시험 포인트

RLS를 켰는데 정책이 하나도 없으면 모든 행이 막힙니다(기본 거부). 테이블 소유자는 기본적으로 RLS를 적용받지 않으므로, 소유자에게도 적용하려면 FORCE ROW LEVEL SECURITY가 필요합니다. 슈퍼유저와 BYPASSRLS 역할은 항상 우회합니다. 그래서 백업(pg_dump)을 도는 계정은 전체 데이터를 받기 위해 이 속성이 필요할 수 있습니다.

8장

EPAS 보안 기능

여기부터는 커뮤니티 PostgreSQL에 없는 EPAS 기능입니다. 시험에서 "EPAS가 제공하는 보안 기능은?"처럼 이름과 역할을 묻는 문제가 자주 나옵니다.

EDB Audit — 누가, 언제, 무엇을 했는가

접속·접속 종료·DDL·DML·오류 문장 등을 서버 로그와 별도의 감사 로그 파일로 남기는 기능입니다. 금융·공공 감사 대응에서 핵심이 됩니다. 5편의 log_statement보다 대상 선택이 세밀하고, 형식이 정해져 있어 분석 도구로 넘기기 쉽습니다.

# postgresql.conf
logging_collector   = on                  # EDB Audit의 전제 조건
edb_audit           = 'csv'               # none(기본) | csv | xml | json
edb_audit_directory = 'edb_audit'         # 기본: PGDATA/edb_audit
edb_audit_connect   = 'all'               # 접속 기록
edb_audit_disconnect = 'all'              # 접속 종료 기록
edb_audit_statement = 'ddl, dml, error'   # 기본: ddl, error
-- 대상을 DB·역할 단위로 좁히거나 넓히기 (5편 우선순위와 같은 원리)
ALTER DATABASE sales SET edb_audit_statement TO 'ddl, insert, update, delete';
ALTER ROLE admin SET edb_audit_statement TO 'select, truncate';
시험 포인트

edb_audit를 켜려면 logging_collector = on이어야 합니다. 형식은 csv, xml, json 중에서 고르고, 기본값 none은 감사를 끈 상태입니다. edb_audit_statement는 클러스터·DB·역할·역할+DB 단위로 설정할 수 있으며 기본값은 ddl과 error입니다. syslog로 보내려면 edb_audit_destination을 바꿉니다.

SQL/Protect — SQL 인젝션 방어

보호 대상으로 지정한 역할(보통 애플리케이션 계정)이 보내는 SQL을 검사해, SQL 인젝션으로 의심되는 패턴을 경고하거나 차단합니다. 먼저 learn 모드로 평소에 접근하는 테이블을 학습시키고, passive(경고만)를 거쳐 active(차단)로 올립니다. 모드를 바꿔 가며 아래 문장들의 결과를 확인하세요.

# 설정 (라이브러리 로드는 재시작 필요)
shared_preload_libraries = '...,$libdir/sqlprotect'   # 기존 목록에 덧붙이기 (5편)
edb_sql_protect.enabled = on
edb_sql_protect.level   = learn
-- 보호할 DB마다 한 번: share/contrib의 sqlprotect.sql 실행 후
SELECT sqlprotect.protect_role('app_user');   -- 보호 대상 역할 지정

패스워드 프로파일 — Oracle식 비밀번호 정책

로그인 실패 횟수 제한, 잠금 시간, 비밀번호 만료, 재사용 금지 같은 규칙을 프로파일로 묶어 역할에 붙입니다. Oracle의 프로파일과 같은 방식이라 보안 점검 항목(계정 잠금 정책 등)을 맞추기 쉽습니다. 시간 값의 단위는 일(day)입니다.

CREATE PROFILE app_policy LIMIT
  FAILED_LOGIN_ATTEMPTS 3        -- 3번 실패하면
  PASSWORD_LOCK_TIME    1        -- 1일 동안 잠금
  PASSWORD_LIFE_TIME    90       -- 90일마다 변경
  PASSWORD_GRACE_TIME   7        -- 만료 후 7일 유예
  PASSWORD_REUSE_TIME   365;     -- 1년 안에 같은 비밀번호 재사용 금지

ALTER ROLE app_user PROFILE app_policy;
ALTER ROLE app_user ACCOUNT UNLOCK;   -- 잠긴 계정 해제

app_user · FAILED_LOGIN_ATTEMPTS 3

프로파일을 지정하지 않은 역할에는 DEFAULT 프로파일이 적용됩니다. 프로파일 생성은 슈퍼유저만 할 수 있습니다.

Data Redaction — 조회 결과의 민감 정보 가리기

테이블의 실제 값은 그대로 두고, 조회할 때 정책 조건에 해당하는 사용자에게만 값을 가려서 보여 줍니다. 콜센터 상담원에게 주민번호나 카드번호 일부만 보여 주는 경우가 대표적입니다. 어떤 값을 어떻게 가릴지는 함수로 정의합니다.

CREATE OR REPLACE FUNCTION redact_ssn(ssn text) RETURNS text AS $$
  SELECT overlay(ssn placing '*******' from 8)
$$ LANGUAGE sql;

CREATE REDACTION POLICY ssn_policy ON hr.customers
  FOR (session_user <> 'hr_manager')        -- 이 조건이 참인 세션에 적용
  ADD COLUMN ssn USING redact_ssn(ssn);
hr_manager로 조회

 이서연 | 920315-2345678
상담원(csr01)으로 조회
  name  |      ssn
--------+----------------

RLS가 "어떤 행을 보여 줄지"라면 Data Redaction은 "어떤 값을 가릴지"입니다. 저장된 데이터를 암호화하는 것이 아니므로, 저장 데이터 보호는 TDE 같은 다른 수단과 함께 씁니다.

TDE — 투명 데이터 암호화

데이터 파일과 WAL을 디스크에 쓸 때 암호화하고, 읽을 때 복호화합니다. 애플리케이션은 아무것도 바꿀 필요가 없어서 "투명"이라고 부릅니다. 디스크나 백업 파일을 통째로 가져가도 키 없이는 읽을 수 없게 합니다. EDB Postgres Advanced Server와 EDB Postgres Extended Server가 제공합니다(1편).

TDE는 클러스터를 만들 때(initdb) 활성화하는 기능이며, 데이터 암호화 키를 감싸는(wrap) 방식과 키 관리 도구 연동을 함께 설계해야 합니다. 이미 운영 중인 클러스터에 켜려면 새 클러스터를 만들어 데이터를 옮기는 방식이 일반적입니다. 세부 옵션은 EDB 공식 문서의 TDE 항목을 확인하세요.
