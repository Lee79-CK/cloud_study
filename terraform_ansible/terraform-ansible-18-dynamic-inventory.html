Terraform & Ansible 강의 · Level 4 Ansible 심화·운영 · 18편 / 26편 · 시리즈 목차

목록을 적지 말고, 클라우드에 물어보라 동적 인벤토리와 클라우드 연계 — aws_ec2·azure_rm·gcp_compute 플러그인, 태그 기반 그룹, Terraform 출력 → 인벤토리, 플러그인 조합·캐시·직접 작성, SSM 연결과 엔드포인트

17편까지 인벤토리는 사람이 쓰거나 Terraform 출력을 파일로 옮긴 “목록”이었습니다. 오토스케일링이 서버를 늘리고, 고객이 콘솔에서 서버를 하나 더 만들고, 장애로 인스턴스가 교체되는 순간 그 목록은 거짓말이 됩니다. 동적 인벤토리는 실행할 때마다 클라우드 API에 “지금 어떤 서버가 있나”를 물어 목록과 그룹을 만듭니다. 그룹의 원천은 태그이고, 태그는 Terraform이 붙입니다(6편 label 모듈). 이번 편은 이 연결 고리를 실제로 실행합니다 — AWS가 없는 검증 환경에서 AWS API 모의 서버(moto)에 7편과 같은 태그의 서버 7대를 만들어 aws_ec2 플러그인을 그대로 돌렸습니다.

이번 편의 목표와 실습 지도

이번 편을 마치면

  • aws_ec2 인벤토리 플러그인의 filters·hostnames·keyed_groups·groups·compose를 설계하고 결과를 ansible-inventory로 검증합니다.
  • 태그 표준이 곧 그룹 체계라는 관점으로 Terraform 태그를 설계합니다.
  • azure_rm·gcp_compute의 같은 기능과 차이(조건 그룹, 변수 식, 레이블 규칙)를 압니다.
  • Terraform 결과를 인벤토리로 만드는 다섯 가지 방법의 장단점을 알고, ansible 프로바이더 + cloud.terraform 방식을 실행합니다.
  • 동적·정적 소스를 한 디렉터리로 조합하고 constructed로 그룹을 다시 계산하며, 캐시를 설정합니다.
  • 고객 자산 대장(CSV)을 읽는 인벤토리 플러그인을 직접 작성합니다.
  • SSM 연결을 인벤토리에서 일괄 설정하고, 17편에서 손으로 준비한 SSM 경로를 VPC 모듈 옵션으로 정리합니다.

1정적 목록의 한계와 플러그인

“인벤토리 파일”은 사실 인벤토리 플러그인의 설정 파일이다

상황정적 목록(13~17편)동적 인벤토리
오토스케일링으로 서버가 3 → 7대4대가 빠진 채 실행 (구성 누락)다음 실행에 7대 모두
장애로 인스턴스 교체 (IP 변경)옛 IP로 접속 실패새 IP
고객이 콘솔로 서버 추가 (태그 규칙대로)모른다태그가 맞으면 자동으로 그룹에 들어온다
서버 폐기목록에 남아 UNREACHABLE사라진다 (filters: running)
클라우드 밖 서버적으면 된다정적 파일과 조합 (6장)
인벤토리 플러그인 규칙설명
설정 파일 이름 규칙플러그인마다 끝이 정해져 있다: *.aws_ec2.yml, *.azure_rm.yml, *.gcp_compute.yml, *.terraform_state.yml. 이름이 맞지 않으면 일반 YAML 인벤토리로 읽으려다 “Plugin configuration YAML file, not YAML inventory” (실측)
plugin: 키파일 첫 키로 어느 플러그인인지 지정 (FQCN)
[inventory] enable_plugins허용할 플러그인 목록. 기본에 auto가 있어 컬렉션 플러그인은 plugin: 키로 자동 선택된다. 사용자 정의 플러그인은 목록에 추가해야 한다(8장)
실행 시점 조회ansible-playbook·ansible-inventory를 실행할 때마다 API 호출 → 자격증명(2편 프로필, CI는 OIDC 12편)과 읽기 권한(ec2:DescribeInstances 등) 필요

2aws_ec2 플러그인 해부

무엇을 가져오고(filters), 무엇이라 부르고(hostnames), 어떻게 묶고(keyed_groups·groups), 무엇을 계산하나(compose)

inventories/aws-dev/01-iaclab.aws_ec2.yml
---
# 파일 이름이 aws_ec2.yml(또는 .yaml)로 끝나야 이 플러그인이 읽는다
plugin: amazon.aws.aws_ec2
regions:
  - ap-northeast-2

# 1) 어떤 인스턴스를 가져올지: 이 고객(Project)의 실행 중인 서버만
filters:
  instance-state-name: running
  tag:Project: iaclab
  tag:ManagedBy: terraform

# 2) 인벤토리 이름: Name 태그 (없으면 인스턴스 ID)
hostnames:
  - tag:Name
  - instance-id

# 3) 태그·속성으로 그룹 자동 생성
keyed_groups:
  - key: ec2_tags.Env                 # env_dev, env_prd
    prefix: env
  - key: ec2_tags.Component           # role_web, role_batch
    prefix: role
  - key: placement.availability_zone
    prefix: az
  - key: instance_type
    prefix: type

# 4) 조건식으로 그룹 만들기
groups:
  prd_web: ec2_tags.Env == 'prd' and ec2_tags.Component == 'web'

# 5) 호스트 변수 계산 — 프라이빗 IP로 접속, SSM은 인스턴스 ID로
compose:
  ansible_host: private_ip_address
  instance_id: instance_id
  ansible_aws_ssm_instance_id: instance_id
  env_name: ec2_tags.Env

# 6) 그룹 이름 등 계산 실패를 오류로 볼지 (false: 해당 호스트만 건너뜀)
strict: false
# 모의 AWS에 만든 7대 (7편 태그 형식)
iaclab-dev-app-web1   running   Project=iaclab Env=dev Component=web   t3.micro  2a
iaclab-dev-app-web2   running   Project=iaclab Env=dev Component=web   t3.micro  2b
iaclab-prd-app-web1   running   Project=iaclab Env=prd Component=web   t3.small  2a
iaclab-prd-app-web2   running   Project=iaclab Env=prd Component=web   t3.small  2b
iaclab-prd-batch1     running   Project=iaclab Env=prd Component=batch t3.micro  2a
custb-dev-web1        running   Project=custb  …                                    ← 다른 고객
iaclab-dev-old1       stopped   Project=iaclab Env=dev Component=web                ← 중지됨
# 실측: ansible-inventory -i 01-iaclab.aws_ec2.yml --graph  (발췌·정렬)
@aws_ec2:                      ← 플러그인이 만든 모든 호스트의 그룹 (5대: 다른 고객·중지된 서버는 filters로 제외)
@env_dev:   iaclab-dev-app-web1, iaclab-dev-app-web2
@env_prd:   iaclab-prd-app-web1, iaclab-prd-app-web2, iaclab-prd-batch1
@role_web:  iaclab-dev-app-web1, iaclab-dev-app-web2, iaclab-prd-app-web1, iaclab-prd-app-web2
@role_batch: iaclab-prd-batch1
@prd_web:   iaclab-prd-app-web1, iaclab-prd-app-web2           ← groups: 의 조건식
@az_ap_northeast_2a / @az_ap_northeast_2b                       ← '-'는 '_'로 바뀐다
@type_t3_micro / @type_t3_small                                 ← '.'도 '_'로

# 실측: --host iaclab-dev-app-web1 (38개 변수 중 발췌)
"ansible_host": "10.10.10.4",                       ← compose
"ansible_aws_ssm_instance_id": "i-622bf5c9381509d59",
"env_name": "dev",
"ec2_tags": {"Component": "web", "Env": "dev", "ManagedBy": "terraform", "Name": "iaclab-dev-app-web1", …},
"instance_type": "t3.micro",
"placement": {"availability_zone": "ap-northeast-2a", "region": "ap-northeast-2", …},
"state": {"code": 16, "name": "running"}
옵션하는 일설계 요령
regions조회할 리전고객이 쓰는 리전만. 비우면 모든 리전을 조회해 느려진다
filters (include_filters·exclude_filters)EC2 DescribeInstances 필터 (서버 측에서 거름)고객·환경 경계를 여기서. 실측: 다른 고객(custb)·중지된 서버가 빠졌다. 계정 하나에 여러 고객이 있다면 필수
hostnames인벤토리 이름으로 쓸 속성 우선순위사람이 읽는 Name 태그 → 없으면 instance-id. Name이 겹치면 allow_duplicated_hosts에 주의
keyed_groups값마다 그룹 (env_dev, env_prd …)태그 표준에서 나온다(3장). 그룹 이름 문자는 자동 변환
groups조건식이 참이면 그룹에두 태그의 조합 같은 “의미 있는 그룹”
compose호스트 변수 계산접속 주소(ansible_host), SSM 인스턴스 ID, 짧은 이름의 편의 변수
strict그룹·변수 식 오류를 실패로 볼지운영은 false(태그가 빠진 서버 하나로 전체 실패하지 않게), 개발 중엔 true로 오류 확인
use_ssm_inventorySSM 인벤토리 정보(설치 소프트웨어 등)를 변수로SSM 에이전트가 있는 환경의 보고서용
tags 대신 ec2_tags (amazon.aws 11.x)

호스트 변수 tags는 Ansible 예약어와 충돌해 지원 중단되었고, 11.2.0부터 ec2_tags가 생겼습니다(2026-12-01 이후 릴리스에서 tags 제거). 이 강의의 설정은 모두 ec2_tags를 씁니다. 실측: amazon.aws 11.4.0은 설정과 관계없이 실행할 때마다 이 지원 중단 경고를 한 번 출력합니다(플러그인 코드가 무조건 출력). 경고가 보인다고 설정이 틀린 것은 아닙니다. 인터넷의 오래된 예제(key: tags.Env, ec2_tag_Env)는 바꿔 쓰세요.

3태그가 그룹이 된다

태그 값을 바꿔 보며 어떤 그룹에 들어가는지 확인하세요 — 2장 설정 + 6장 constructed 규칙을 그대로 계산합니다

태그 (6편 label 모듈)만드는 그룹·변수규칙
Project필터 (고객 경계)고객·프로젝트 식별자. 계정을 고객과 공유한다면 반드시
Envenv_dev, env_prd / env_namedev·stg·prd 세 값만 (8편 환경 이름과 동일, 6편 label 모듈의 validation)
Componentrole_web, role_batch플레이북의 hosts가 될 역할 이름. 서버당 하나
Owner(보고서용 변수)담당자 — 그룹으로 쓰지 않는다 (사람이 바뀌면 그룹이 바뀜)
ManagedBy필터terraform이 만든 것만 자동 구성 대상으로 (콘솔로 만든 서버는 9편 흡수 후 포함)
태그를 바꾸면 구성이 바뀐다

동적 인벤토리에서 태그는 단순한 메모가 아니라 “이 서버에 무엇을 구성할지”를 정하는 입력입니다. Component를 web에서 batch로 바꾸면 다음 실행부터 웹 역할 대신 배치 역할이 적용됩니다. 그래서 태그는 Terraform(코드)으로만 바꾸고, 콘솔 태그 수정을 IAM으로 막거나 9편의 드리프트 점검으로 감시합니다. 12편 정책(TAG-001)이 필수 태그를 강제하는 이유이기도 합니다.

4azure_rm · gcp_compute

같은 생각, 다른 이름 — 멀티클라우드 고객을 위한 대응표

iaclab.azure_rm.yml
---
# Azure: 파일 이름이 azure_rm.yml(.yaml)로 끝나야 한다. 인증은 az login·환경 변수·관리 ID 자동 탐색
plugin: azure.azcollection.azure_rm
auth_source: auto
include_vm_resource_groups:
  - rg-iaclab-dev
plain_host_names: true                 # 이름 뒤에 무작위 접미사를 붙이지 않음
# 기본 필터(default_host_filters)가 꺼진 VM·프로비저닝 중인 VM을 이미 제외한다
keyed_groups:
  - prefix: env
    key: tags.Env | default('none')
  - prefix: role
    key: tags.Component | default('none')
  - prefix: loc
    key: location
conditional_groups:                    # AWS의 groups 와 같은 역할
  prd_web: tags.Env | default('') == 'prd' and tags.Component | default('') == 'web'
hostvar_expressions:                   # AWS의 compose 와 같은 역할
  ansible_host: private_ipv4_addresses | first
  env_name: tags.Env | default('none')

---
# GCP: 파일 이름이 gcp_compute.yml(.yaml)로 끝나야 한다

  - asia-northeast3-a
  - asia-northeast3-b

  - name

  - prefix: role
    key: labels.component
compose:
  ansible_host: networkInterfaces[0].networkIP   # 프라이빗 IP
  env_name: labels.env

멀티클라우드 태그 표준은 가장 엄격한 규칙에 맞춘다

GCP 레이블은 대문자를 허용하지 않습니다. 세 클라우드에 같은 태그 표준을 쓰려면 키·값을 모두 소문자(env=prd, component=web)로 정하는 편이 안전합니다. 이 강의의 AWS 태그(Env, Component)는 대문자로 시작하므로, 멀티클라우드 고객이라면 6편 label 모듈에 “레이블용 소문자 출력”을 추가하는 것을 검토하세요(과제 2).

5Terraform → 인벤토리 다섯 가지

Terraform이 만든 것을 Ansible이 아는 방법 — 장단점 비교와 실측

방법동작장점단점이 강의
① 출력 → 파일terraform output을 인벤토리 YAML로 저장단순, 도구 추가 없음, 그룹 변수까지 전달apply 후 손으로 다시 만들어야 함 — 낡기 쉽다7·13·17편
② 태그 + 클라우드 플러그인Terraform은 태그만, Ansible은 API 조회항상 최신, 콘솔·오토스케일링 서버도 포함, Terraform 상태 불필요태그 규율 필요, 서버가 아닌 값(DB 주소)은 따로2·3장 (기본 권장)
③ ansible 프로바이더 + cloud.terraform.terraform_providerTerraform이 ansible_host·ansible_group 리소스를 state에 기록, 플러그인이 terraform show로 읽음Terraform 코드가 그룹·변수를 명시적으로 결정, 클라우드 무관Terraform 프로젝트 디렉터리·state 접근 필요, 프로바이더 하나 추가아래 실측
④ cloud.terraform.terraform_statestate의 aws_instance 등을 직접 읽음 (백엔드 지정)Terraform 코드 변경 없음state 읽기 권한 필요(민감 값 포함 가능, 5편), 모듈 안 리소스는 search_child_modules설정 예
⑤ 혼합: 호스트는 ②, 변수는 ①서버 목록은 API, DB 주소 같은 값은 Terraform 출력 JSON을 group_vars에각자 잘하는 것만두 경로를 이해해야 함10장 실습

규칙설명
파일 이름 순서디렉터리 안 소스는 이름 순(01-, 02-, 03-)으로 읽는다. constructed는 앞 소스의 결과를 쓰므로 반드시 마지막
use_vars_plugins: trueconstructed 조건식에서 group_vars·host_vars 값도 쓸 수 있게 (실측: aws_ec2.yml의 값을 기준으로 연결 방식 결정)
group_vars는 디렉터리 기준인벤토리 디렉터리 안의 group_vars가 모든 소스의 그룹에 적용된다. 플러그인이 만든 그룹(aws_ec2, role_web)에도
그룹 이름 충돌여러 소스가 같은 그룹 이름을 만들면 합쳐진다. 의도하지 않은 합류를 피하려면 접두사(env_, role_, stage_)를 소스마다 구분

8직접 만드는 인벤토리 플러그인

고객 자산 대장(CSV·CMDB)이 원천일 때 — 60줄짜리 플러그인

클라우드 API가 없는 온프레미스, 혹은 고객이 “자산 대장이 공식 원천”이라고 정해 둔 환경에서는 그 대장을 직접 읽는 플러그인이 정답입니다. Constructable을 함께 상속하면 keyed_groups·groups·compose를 그대로 쓸 수 있어, 클라우드 플러그인과 같은 설정 방식이 됩니다.

inventory_plugins/cmdb_csv.py
# -*- coding: utf-8 -*-
# 고객 자산 대장(CSV)을 인벤토리로 읽는 최소 인벤토리 플러그인 (18편 실습)
from __future__ import annotations

import csv
import os

from ansible.errors import AnsibleParserError
from ansible.plugins.inventory import BaseInventoryPlugin, Constructable

DOCUMENTATION = r"""
name: cmdb_csv
short_description: 자산 대장 CSV에서 호스트를 읽는다
description:
  - hostname, ip, env, role 열이 있는 CSV를 읽어 호스트와 변수를 만든다.
  - constructed 기능(keyed_groups, groups, compose)을 함께 쓸 수 있다.
extends_documentation_fragment:
  - constructed
options:
  plugin:
    description: 이 플러그인 이름
    required: true
    choices: ['cmdb_csv']
  path:
    description: CSV 파일 경로 (상대 경로는 인벤토리 설정 파일 기준)
    required: true
    type: str
  only_active:
    description: status 열이 active 인 행만
    type: bool
    default: true
"""


class InventoryModule(BaseInventoryPlugin, Constructable):
    NAME = "cmdb_csv"

    def verify_file(self, path):
        # 설정 파일 이름이 cmdb_csv.yml(.yaml)로 끝날 때만 이 플러그인이 맡는다
        return super().verify_file(path) and path.endswith(("cmdb_csv.yml", "cmdb_csv.yaml"))

    def parse(self, inventory, loader, path, cache=True):
        super().parse(inventory, loader, path, cache)
        self._read_config_data(path)
        csv_path = os.path.expanduser(self.get_option("path"))
        if not os.path.isabs(csv_path):
            # 상대 경로는 인벤토리 설정 파일이 있는 디렉터리 기준
            csv_path = os.path.join(os.path.dirname(path), csv_path)
        strict = self.get_option("strict")
        try:
            with open(csv_path, newline="", encoding="utf-8") as f:
                rows = list(csv.DictReader(f))
        except OSError as e:
            raise AnsibleParserError(f"자산 대장을 읽을 수 없습니다: {csv_path}: {e}")

        for row in rows:
            if self.get_option("only_active") and row.get("status", "active") != "active":
                continue
            host = row["hostname"]
            self.inventory.add_host(host)
            self.inventory.set_variable(host, "ansible_host", row["ip"])
            for key in ("env", "role", "owner", "os"):
                if row.get(key):
                    self.inventory.set_variable(host, f"cmdb_{key}", row[key])
            hostvars = self.inventory.get_host(host).get_vars()
            self._set_composite_vars(self.get_option("compose"), hostvars, host, strict=strict)
            self._add_host_to_composed_groups(self.get_option("groups"), hostvars, host, strict=strict)
            self._add_host_to_keyed_groups(self.get_option("keyed_groups"), hostvars, host, strict=strict)

과제 3. ansible 프로바이더를 7편에

5장의 ansible.tf를 07-app에 실제로 추가해 apply하고, cloud.terraform.terraform_provider 인벤토리로 17편 플레이북을 실행하세요. 동적 인벤토리(aws_ec2)와 결과를 비교하고, 어떤 상황에서 어느 쪽이 유리한지 정리합니다.

생각할 점

ansible 프로바이더 방식은 Terraform이 apply한 시점의 사실, aws_ec2는 지금의 사실입니다. 오토스케일링 그룹의 인스턴스는 Terraform이 개별로 만들지 않으므로 ansible_host 리소스로 표현할 수 없고, 동적 인벤토리만 가능합니다.
