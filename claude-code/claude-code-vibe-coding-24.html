관리형 값은 사용자·프로젝트·로컬·--settings 위에 놓입니다(일부 보안 관련 예외에서는 더 엄격한 하위 값이 반영). 9편의 “deny는 어느 범위에서든 이긴다”가 조직 차원으로 올라간 것입니다.

서버 관리형의 최근 변경

v2.1.316부터 Team·Enterprise 로그인에서 서버에서 받은 정책은 승인 창 없이 바로 적용되고, 검증되지 않는 저장본은 거부됩니다. 서버에 닿지 못해도 정책 없이 시작하지 않게 하려면 forceRemoteSettingsRefresh.

그룹마다 다르게

파일·MDM은 그룹마다 다른 파일·프로필을 배포하면 됩니다. claude.ai 콘솔은 아직 그룹별 정책을 지원하지 않는다고 문서에 나옵니다.

Windows 옛 경로

C:\ProgramData\ClaudeCode\는 v2.1.75부터 지원하지 않습니다. 옛 배포가 있다면 옮기세요.

정말 걸렸나

정책 파일을 배포했다고 걸린 것은 아닙니다. 아래는 같은 컴퓨터에서 정책이 없을 때와 있을 때를 비교한 실제 결과입니다(일반 사용자 계정, CLI 2.1.317).

샌드박스는 조용히 꺼질 수 있습니다 sandbox.enabled: true만 두고 bubblewrap·socat이 없는 Linux에서 실행하자, Claude Code는 “Commands will run WITHOUT sandboxing” 경고만 내고 샌드박스 없이 시작했습니다. failIfUnavailable: true를 더하자 “refusing to start without a working sandbox”로 시작을 거부했고, apt install bubblewrap socat 뒤에는 정상 시작했습니다. 조직 정책이라면 반드시 함께 두세요.

확인 도구: policy_check.py

23편 SDK로 만든 점검기입니다. 일부러 잘못된 API 키로 Claude Code를 초기화 메시지까지만 띄워, bypassPermissions 요청이 거부되는지, 허가 안 된 MCP 서버가 막히는지, 허가된 서버는 붙는지, 금지 모델이 바뀌는지 봅니다. 토큰을 쓰지 않으며, 정책이 있을 때 모두 PASS(종료 0), 없을 때 FAIL(종료 1), root로 실행하면 판단 불가(종료 2)임을 확인했습니다.

관측: OpenTelemetry

공식 비용 문서는 OpenTelemetry를 “모든 접속 방식에서 사용자별 토큰·비용 지표를 거의 실시간으로 내 관측 스택에 보내는 유일한 방법”이라고 합니다. 조직은 관리형 설정의 env로 켭니다. 저장소의 .claude/settings.json에 둔 OTEL 내보내기 변수는 무시된다고 문서에 나옵니다(끄는 값 일부 제외).

"env": { "CLAUDE_CODE_ENABLE_TELEMETRY": "1", "OTEL_METRICS_EXPORTER": "otlp", "OTEL_LOGS_EXPORTER": "otlp", "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc", "OTEL_EXPORTER_OTLP_ENDPOINT": "http://otel-collector.msp.internal:4317" }

실제로 나온 것 (console 내보내기로 확인)

지표

claude_code.session.count, claude_code.active_time.total. 문서상 토큰·비용(token.usage, cost.usage), 코드 줄 수, 커밋·PR 수, 편집 도구 결정도 있습니다(모델 응답이 있어야 쌓이는 것은 이번엔 401이라 나오지 않음).

이벤트

user_prompt, api_error, plugin_loaded, managed_settings_resolved(관리형 설정 출처 file 기록).

프롬프트는 기본 가림

user_prompt 이벤트의 prompt는 <REDACTED>, 길이만 기록(확인함). 내용을 남기려면 OTEL_LOG_USER_PROMPTS=1. 고객 정보가 섞일 수 있으니 MSP에서는 켜지 않는 것을 권합니다.

속성

기본 속성으로 anthropic.provider 등이 붙고(확인함), v2.1.317부터 anthropic.plan·anthropic.seat_type도 추가됐습니다. OTEL_RESOURCE_ATTRIBUTES=department=msp,customer=acme가 모든 지표·이벤트에 붙음(확인함). 값에 공백 금지(W3C Baggage 형식).

함정: 설정 파일의 env 가 실행 환경을 덮습니다 관리형 정책 env에 OTEL_RESOURCE_ATTRIBUTES=department=msp를 넣고, 셸에서 customer=acme를 붙여 실행했더니 customer가 사라졌습니다(18개 기록 모두 department만). 사용자 설정의 env도 마찬가지로 셸 값을 덮었습니다. 그래서 이 강의의 정책은 내보내기 변수만 강제하고, 자원 속성은 7장의 고객사 실행기에서 붙입니다. 이렇게 바꾸자 customer=acme가 모두 붙었습니다.

고객사 경계

MSP의 가장 중요한 거버넌스는 고객사 사이의 벽입니다. 한 세션이 두 고객의 자격 증명을 동시에 쥐지 않게, 그리고 사용량을 고객별로 나눠 볼 수 있게 고객사 전용 실행기를 둡니다.

#!/bin/bash # 고객사 전용 Claude Code 실행기. 고객사마다 복사해 이름과 값을 바꾼다 (예: ~/bin/acme-claude). # 자격 증명은 읽기 전용, 작업 폴더는 그 고객 저장소, 텔레메트리에는 고객 이름을 붙인다. # 주의: 관리형·사용자 설정의 env 가 OTEL_RESOURCE_ATTRIBUTES 를 정하면 이 값은 무시된다. set -euo pipefail CUSTOMER=acme export AWS_PROFILE="${CUSTOMER}-readonly" export KUBECONFIG="$HOME/.kube/${CUSTOMER}-readonly.yaml" export OTEL_RESOURCE_ATTRIBUTES="department=msp,customer=${CUSTOMER}" unset ANTHROPIC_API_KEY_PROD AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY # 손에 남은 다른 자격 증명 비우기 cd "$HOME/customers/${CUSTOMER}" exec claude "$@"

shellcheck 통과. 가짜 claude로 실행해 작업 폴더·프로파일·kubeconfig·속성이 고객사 값으로 바뀌고, 미리 있던 AWS 키가 비워지며, 인자가 그대로 전달되고, 고객 폴더가 없으면 1로 끝나는 것을 확인했습니다.

저장소·자격 증명 분리

고객마다 저장소, 읽기 전용 프로파일, kubeconfig(12·21편). 세션 하나에 고객 하나.

비용 나누기

OTel의 customer 속성, 또는 고객별 API 키·워크스페이스(20편). 청구 근거가 필요하면 둘 다.

로컬 기록

cleanupPeriodDays로 세션 기록 보존 기간을 줄입니다(6편). 고객 계약의 보존 조건을 먼저 확인.

클라우드 기능

Routines·클라우드 세션(19편)에 고객 코드를 올려도 되는지는 계약과 회사 정책이 정합니다. 안 된다면 정책과 교육 자료에 명시.

마치며

1편에서 바이브 코딩을 “건축주와 시공팀”으로 비유했습니다. 스물네 편을 지나며 시공팀은 점점 유능해졌고, 건축주가 할 일은 오히려 분명해졌습니다. 무엇을 지을지 정하고, 하지 않을 것을 정하고, 다 됐는지 검증하고, 되돌릴 길을 남기는 것. 권한·Hook·샌드박스·관리형 정책은 그 결정을 기계가 지키게 하는 장치였습니다.

도구는 빠르게 바뀝니다. 이 과정의 화면과 기본값도 몇 달 뒤엔 달라져 있을 것입니다. 그래도 남는 습관이 있습니다. 근거를 요구하기(16편), 실패하는 테스트를 먼저 보기(17편), plan과 apply를 나누기(21편), 정책이 정말 걸렸는지 확인하기(24편). 새 기능이 나올 때마다 이 질문들로 시험해 보세요.

과정을 마친 뒤

시범 그룹 2~4주 → 측정 → 정책 조정 → 확산(8장). 이 과정의 실습 저장소(vibe-lab, acme-ops-legacy, acme-infra, ops-console, msp-claude-plugins)를 팀 교육용 샌드박스로 쓰고, 여러분의 고객 환경에 맞는 Skill·플러그인·정책으로 바꿔 나가세요. 공식 문서(code.claude.com/docs)의 변경 이력을 정기적으로 확인하는 것도 플랫폼 관리자의 일입니다.

Claude Code 바이브 코딩 마스터 과정 24편(완결) · 관리형 설정·OpenTelemetry 결과는 Claude Code CLI 2.1.317(claude-agent-sdk 0.2.177 번들)로 Linux에서 실행해 확인했고, 정책 키 이름과 전달 방식은 2026년 공식 문서(Example settings files, Deploy managed settings, Monitoring, Manage costs)를 따랐습니다. 실제 배포 전에는 사용 중인 버전의 설정 참조 문서로 키를 확인하세요.
