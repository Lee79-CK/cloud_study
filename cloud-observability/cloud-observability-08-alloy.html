Cloud 모니터링·로깅 실전 강의 8편 (Level 3. 통합 로깅)

Grafana Alloy 실전

7편에서는 curl로 로그를 넣었습니다. 이번에는 진짜 수집기를 씁니다. 고객사 VM 두 대와 Kubernetes 노드 세 대의 로그를 한 Loki로 모으면서, 라벨을 표준에 맞추고, 카드 번호와 비밀번호를 지우고, 쓸모없는 줄을 버리는 일을 수집 단계에서 끝냅니다.

대상: 1~2년차 클라우드 엔지니어 형식: 개념 + 실습 6개 예상 소요: 4시간 기준: Alloy v1.20.1, Alloy 차트 1.13
로그 한 줄이 Alloy를 지나가면이 편의 cust-a-web 설정(loki.process "shop")과 같은 단계를 브라우저에서 그대로 재현합니다. 줄을 고르고 단계를 켜고 꺼 보세요. 같은 설정을 Alloy 1.20.1로 실행한 결과와 일치하도록 만들었습니다.

0시작하기 전에

7편에서 hub에 만든 Loki(테넌트 cust-a, 입구 30100)로 실제 로그를 흘려 넣는 편입니다.

학습 목표

  1. Alloy가 Promtail, Grafana Agent, OpenTelemetry Collector와 어떤 관계인지 설명할 수 있다.
  2. Alloy 설정 문법(블록, 속성, 표현식, 컴포넌트 참조)을 읽고 쓸 수 있으며 alloy validate, alloy fmt로 검사할 수 있다.
  3. discovery, source, process, relabel, write로 이어지는 로그 파이프라인을 설계할 수 있다.
  4. MSP 라벨 표준을 정하고, 값이 많은 정보를 Structured Metadata로 내려 카디널리티를 막을 수 있다.
  5. 수집 단계에서 민감정보를 마스킹하고 불필요한 로그를 버릴 수 있다.
  6. VM에는 systemd 서비스로, Kubernetes에는 DaemonSet으로 Alloy를 배포할 수 있다.
  7. alloy convert로 Promtail 설정을 옮기고 결과를 검토할 수 있다.

1Grafana Alloy는 무엇인가

한 줄로 말하면 "Grafana Labs가 만든 OpenTelemetry Collector 배포판에 Prometheus와 Loki 생태계 기능을 더한 수집기"입니다.

도구관계상태
PromtailLoki 전용 로그 수집기. Alloy의 loki.* 컴포넌트로 흡수2026년 3월 2일 EOL, Loki 3.7.3에서 코드 제거 (1, 7편)
Grafana Agent메트릭, 로그, 트레이스 수집기. Alloy가 공식 후속2025년 11월 1일 EOL
OpenTelemetry CollectorAlloy는 OTel Collector 컴포넌트를 otelcol.*로 내장한 배포판함께 쓰거나 둘 중 하나 선택 (11편)
Prometheus Agentprometheus.scrape, prometheus.remote_write로 같은 역할14편에서 비교

Alloy 하나로 메트릭(Prometheus 방식), 로그(Loki 방식), 트레이스와 OTLP(OpenTelemetry 방식), 프로파일(Pyroscope)을 모두 수집할 수 있어, 고객사 서버에 에이전트를 여러 개 설치하지 않아도 됩니다. Apache 2.0 라이선스입니다(1편 9장). 이번 편은 로그만 다루고, 11편에서 OTLP와 트레이스, 14편에서 메트릭을 같은 Alloy에 더합니다.

Alloy 1.20의 두 가지 실행 방식

작성 시점의 Alloy v1.20.1 명령 목록에는 기본 실행(alloy run) 외에 OpenTelemetry Collector 설정 형식을 그대로 받는 alloy otel(OTel Engine)이 있습니다. 이 강의는 Alloy 고유 문법을 쓰는 기본 엔진으로 진행하고, OTel 형식은 11편에서 비교합니다.

2Alloy 설정 문법

Alloy 설정은 "컴포넌트를 선언하고, 한 컴포넌트의 출력을 다른 컴포넌트의 입력에 연결"하는 방식입니다. 연결이 곧 데이터 흐름 그래프가 됩니다.

// 블록: 컴포넌트이름 "라벨" { ... }  →  같은 종류를 여러 개 둘 때 라벨로 구분
local.file_match "shop" {
  path_targets = [{ __path__ = "/var/log/shop/*.log", service_name = "payment" }]   // 속성 = 값
}

loki.source.file "shop" {
  targets    = local.file_match.shop.targets       // 다른 컴포넌트의 내보낸 값(export) 참조 → 연결
  forward_to = [loki.process.shop.receiver]        // 받을 쪽의 receiver를 목록으로
}

loki.write "hub" {
  endpoint {                                       // 블록 안의 하위 블록
    url = sys.env("LOKI_URL")                      // 표준 라이브러리 함수
  }
  external_labels = { host = constants.hostname }  // 상수
}
요소뜻
컴포넌트종류 "라벨". 예: loki.process "shop". 종류는 discovery.*, local.*, loki.*, prometheus.*, otelcol.* 등
인자(arguments)블록 안에 쓰는 속성과 하위 블록. 그 컴포넌트에 주는 입력
내보내기(exports)컴포넌트가 만들어 다른 곳에서 참조하는 값. targets, receiver, rules, output
표현식문자열 연결("a" + sys.env("X")), 목록, 객체, 함수 호출. 참조가 바뀌면 받는 쪽이 자동으로 다시 평가됨
설정 블록컴포넌트가 아닌 전역 설정. logging, livedebugging, tracing 등
 
alloy validate config.alloy     # 문법과 연결 검사 (실행하지 않음)
alloy fmt -w config.alloy        # 정렬과 들여쓰기 표준화

3, 4편의 promtool check처럼, Alloy 설정도 배포 전에 validate를 통과시키는 것을 원칙으로 합니다. 이 편의 세 설정 파일은 모두 v1.20.1의 validate를 통과했습니다.

3로그 파이프라인 컴포넌트

로그 파이프라인은 대체로 다섯 단계를 거칩니다.

1. 찾기

discovery.* , local.file_match

어떤 파일, 어떤 파드를 읽을지 타깃 목록을 만듭니다. Kubernetes는 discovery.kubernetes, VM 파일은 local.file_match(또는 loki.source.file의 file_match 블록).

2. 다듬기

discovery.relabel

타깃의 메타데이터(__meta_kubernetes_*)로 라벨을 정하고 읽을 파일 경로(__path__)를 만듭니다. 3편 Prometheus의 relabel_configs와 같은 규칙입니다.

3. 읽기

loki.source.*

file(파일 꼬리 읽기), journal(systemd journal), kubernetes(API로 파드 로그), kubernetes_events(이벤트), syslog, api(Push 받기) 등. 어디까지 읽었는지(position)를 저장해 재시작해도 이어 읽습니다.

4. 가공

loki.process (stage들)

줄마다 단계(stage)를 차례로 적용합니다. 파싱, 시각 지정, 버리기, 바꾸기, 라벨과 메타데이터 지정.

5. 보내기

loki.write

묶어서(batch) Loki로 보내고, 실패하면 재시도합니다. 테넌트(tenant_id)와 모든 줄에 붙일 external_labels를 여기서 정합니다.

자주 쓰는 stage

stage하는 일이 편에서
stage.logfmt, stage.json, stage.regex본문을 파싱해 값을 추출 맵(extracted map)에 꺼냄. 추출만으로는 라벨이 되지 않음결제 로그(logfmt), PostgreSQL(regex)
stage.cri, stage.docker컨테이너 런타임의 로그 형식을 풀어 원래 줄을 꺼냄Kubernetes(containerd)
stage.timestamp추출한 값을 엔트리 시각으로결제 로그의 ts
stage.labels추출한 값을 라벨로 승격쓰지 않음(4장 이유)
stage.structured_metadata추출한 값을 Structured Metadata로trace_id, order_id, pod
stage.label_drop, stage.label_keep라벨 제거, 유지pod, filename 제거
stage.drop조건에 맞는 줄 버림. 버린 이유를 메트릭에 남김debug
stage.replace정규식 캡처 그룹 부분을 바꿈카드 번호, 비밀번호
stage.limit, stage.sampling초당 줄 수 제한, 표본 추출13장
stage.multilineJava 스택 트레이스처럼 여러 줄을 한 엔트리로14장
추출 맵과 라벨의 관계

파싱 stage는 값을 추출 맵에 넣을 뿐이고, 무엇을 라벨로, 무엇을 메타데이터로 보낼지는 따로 정합니다. 반대로 추출 맵은 그 줄의 라벨로 초기화되므로, 라벨로 받은 값을 stage.structured_metadata로 옮길 수 있습니다. Kubernetes 설정에서 파드 이름을 이 방법으로 라벨에서 메타데이터로 내렸고, 실측에서 Loki 라벨 목록에 pod가 없고 각 줄의 메타데이터에 pod="lab-app-abc"가 있는 것을 확인했습니다.

5민감정보 마스킹

한 번 Loki에 들어간 로그는 지우기 어렵습니다(7편의 삭제 요청은 무겁고 느립니다). 민감정보는 수집 단계에서 지우는 것이 원칙입니다.

stage.replace의 동작

stage.replace {
  expression = "card=\\d{4}-(\\d{4}-\\d{4})-\\d{4}"   // 괄호(캡처 그룹) 부분만 바뀜
  replace    = "****-****"
}
// card=4111-1111-1111-6146  →  card=4111-****-****-6146   (실측)

stage.replace {
  expression = "password=(\\S+)"
  replace    = "[REDACTED]"
}
// password=Sup3rS3cret!    →  password=[REDACTED]        (실측)

정규식 전체가 아니라 캡처 그룹만 바뀌므로, 앞뒤 맥락(card=, 앞 4자리, 뒤 4자리)을 남겨 어떤 카드였는지 고객 문의에 답할 수 있으면서도 원래 번호는 복원할 수 없게 할 수 있습니다. 설정 파일 안에서 백슬래시는 두 번(\\d) 씁니다.

마스킹은 규칙에 맞는 것만 지웁니다

위 규칙은 card=와 대시 형식만 잡습니다. 공백으로 구분된 번호, JSON의 "cardNumber": "...", 예외 메시지 안에 섞인 번호는 그대로 통과합니다. 고객사마다 실제 로그 표본을 받아 정규식을 만들고, 9편의 LogQL로 "마스킹되지 않은 16자리 숫자가 남아 있는지" 주기적으로 점검하는 질의를 두는 것이 안전합니다. 카드 정보는 PCI DSS가 저장 시 원본 번호를 읽을 수 없게 하도록 요구하고, 개인정보는 국내 개인정보 보호 법령의 적용을 받으므로, 마스킹 규칙은 고객사 보안 담당과 함께 확정합니다.

버리기도 마스킹만큼 중요합니다

debug 로그, 헬스 체크 접근 로그처럼 장애 분석에 쓰이지 않는 줄은 stage.drop으로 버립니다. drop_counter_reason을 주면 버린 줄 수가 loki_process_dropped_lines_total{reason="debug_level"}에 남아, "무엇을 얼마나 버리고 있는지"를 나중에 설명할 수 있습니다. 실측에서 파일의 debug 12줄과 이 메트릭의 값 12가 정확히 일치했습니다.

7Lab 1. 로그 만드는 앱 설치

4편의 lab-app은 메트릭만 내보냅니다. 로그 실습을 위해 가상 결제 로그를 쓰는 shop-logger를 cust-a-web에 추가합니다.

shop-logger는 lab-app과 같은 /etc/lab-app/faults를 읽어, payment_error_rate만큼 "db pool exhausted" 오류 줄을 냅니다. 그래서 4편에서 메트릭으로 본 장애가 로그에서도 같은 비율로 보이고, 9편에서 로그로 만든 메트릭과 4편의 메트릭을 비교할 수 있습니다. 일부 줄에는 마스킹 실습용 가짜 카드 번호와 비밀번호, 버리기 실습용 debug 줄이 섞여 있습니다.

~/obs-lab/vm/shop-logger/shop-logger.py 펼치기 (약 60줄) 
#!/usr/bin/env python3
"""shop-logger: 로그 수집 실습용 가상 결제 서비스 로그 생성기 (표준 라이브러리만 사용)

/var/log/shop/payment.log 에 logfmt 형식으로 초당 약 3줄을 씁니다.
lab-app과 같은 /etc/lab-app/faults 를 읽어 payment_error_rate 만큼 오류 로그를 냅니다.
일부 줄에는 일부러 카드 번호와 비밀번호가 섞여 있습니다(마스킹 실습용, 모두 가짜 값).
"""
import argparse, os, random, time, uuid
from datetime import datetime, timezone

FAULT_FILE = "/etc/lab-app/faults"


def error_rate():
    rate = 0.005
    try:
        for line in open(FAULT_FILE):
            if line.strip().startswith("payment_error_rate="):
                rate = float(line.split("=", 1)[1])
    except (OSError, ValueError):
        pass
    return rate


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--file", default="/var/log/shop/payment.log")
    ap.add_argument("--rps", type=float, default=3.0)
    a = ap.parse_args()
    os.makedirs(os.path.dirname(a.file), exist_ok=True)
    with open(a.file, "a", buffering=1) as f:
        while True:
            now = datetime.now(timezone.utc).isoformat(timespec="milliseconds").replace("+00:00", "Z")
            tid = uuid.uuid4().hex
            oid = f"o-{random.randint(10000, 99999)}"
            user = f"u{random.randint(1, 5000)}"
            ms = int(random.lognormvariate(4.8, 0.5))
            r = random.random()                     # 줄 종류를 정하는 난수 (오류 여부와 별개)
            if random.random() < error_rate():
                line = (f'ts={now} level=error msg="charge failed" reason="db pool exhausted" '
                        f'order_id={oid} user={user} duration_ms={ms * 10} trace_id={tid}')
            elif r < 0.03:
                line = (f'ts={now} level=info msg="card validated" order_id={oid} '
                        f'card=4111-1111-1111-{random.randint(1000, 9999)} trace_id={tid}')
            elif r < 0.08:
                line = f'ts={now} level=debug msg="cache hit" key=price:{random.randint(1, 500)}'
            elif r < 0.09:
                line = (f'ts={now} level=warn msg="pg login retry" user=shop_app '
                        f'password=Sup3rS3cret! attempt={random.randint(1, 3)} trace_id={tid}')
            else:
                line = (f'ts={now} level=info msg="charge ok" order_id={oid} user={user} '
                        f'amount={random.randint(1, 50) * 1000} duration_ms={ms} trace_id={tid}')
            f.write(line + "\n")
            time.sleep(random.expovariate(a.rps))


if __name__ == "__main__":
    main()

loki.process "shop" {

  stage.logfmt {

      level = "",

      level = null,

  }]
  forward_to = [loki.process.shop.receiver]

    enabled = true

}

    source_labels = ["__journal__systemd_unit"]

  }
}

  relabel_rules = discovery.relabel.journal.rules

검토 포인트 작성 중 위 결과는 validate를 그대로 통과했습니다. 그러나 "통과"와 "좋은 설정"은 다릅니다.
  • legacy_positions_file: Promtail이 어디까지 읽었는지 기록한 파일을 이어받아, 전환 순간 로그를 처음부터 다시 보내거나 빠뜨리지 않게 합니다. 변환기가 자동으로 넣어 준 가장 중요한 줄입니다.
  • file_match { enabled = true }: 이 편의 설정처럼 local.file_match를 따로 쓰지 않고 loki.source.file이 직접 경로 패턴을 찾는 방식입니다. 두 방식 모두 유효합니다.
  • stage.labels { level }: Promtail 시절의 습관인 "레벨을 라벨로"까지 그대로 옮겨졌습니다. 4장 기준으로 지우고 Structured Metadata로 바꿔야 합니다. 변환기는 의미를 그대로 옮길 뿐 설계를 고쳐 주지 않습니다.
  • job 라벨: 이 시리즈 표준은 service_name입니다. 바꾸지 않으면 Promtail로 수집하던 서버와 새 서버의 질의가 달라집니다.
  • 테넌트, external_labels: tenant_id는 옮겨졌지만 customer, host 같은 공통 라벨은 없습니다.

14트러블슈팅

증상을 눌러 원인과 해결 방법을 확인하세요.

파일 로그가 하나도 안 감, files_active가 0Lab 2

경로 패턴이 맞는지, alloy 사용자가 그 파일을 읽을 수 있는지 봅니다. sudo -u alloy cat /var/log/shop/payment.log가 실패하면 그룹(id alloy)과 파일 권한을 확인하고, 그룹을 추가한 뒤에는 systemctl restart alloy가 필요합니다. UI에서 loki.source.file의 targets가 비어 있으면 local.file_match 단계의 문제입니다.

journal 로그가 안 감Lab 2, 3

alloy 사용자가 systemd-journal 그룹에 있어야 합니다. VM의 journal이 휘발성(/run/log/journal)인지 영구(/var/log/journal)인지도 확인합니다. max_age보다 오래된 기록은 처음 시작할 때 건너뜁니다.

Alloy 로그에 status=400 "timestamp too new" 또는 "too old", 그리고 "dropping data"운영

작성 중 실제로 겪은 오류입니다. 로그 줄의 시각을 stage.timestamp로 엔트리 시각으로 쓰는데, 그 시각이 Loki 서버 기준으로 미래이거나 너무 과거면 Loki가 400으로 거절하고, Alloy는 재시도 없이 그 묶음을 버립니다. 서버 시계(NTP)와 로그 시각의 시간대 표기를 확인하세요. 시간대 없는 로그 시각은 location 인자로 시간대를 지정해야 합니다.

Alloy 로그에 429, dropped_entries의 reason이 stream_limited 또는 rate_limited운영

7편의 테넌트 한도에 걸린 것입니다. 이 편의 설정에서 값이 많은 라벨이 생기지 않았는지(파드 이름, filename) 라벨 브라우저로 확인하고, 수집 단계에서 양을 줄입니다(13장).

edge에서 같은 로그가 세 번씩 들어옴Lab 4

NODE_NAME 환경 변수가 비어 필드 선택자가 동작하지 않아, 각 노드의 Alloy가 클러스터의 모든 파드를 찾는 경우입니다. values의 extraEnv를 확인하고, UI에서 discovery.kubernetes.pods의 타깃이 자기 노드의 파드만인지 봅니다. 파일은 그 노드에만 있으므로 실제로는 "읽을 수 없는 경로"가 섞여 오류가 나는 경우가 더 흔합니다.

Kubernetes 로그 줄 앞에 "2026-10-08T... stdout F"가 붙어 있음Lab 4

stage.cri가 빠진 경우입니다. containerd는 각 줄 앞에 시각, 스트림, 부분 줄 표시를 붙여 저장합니다. Docker 런타임 노드라면 stage.docker를 씁니다.

customer, zone 라벨이 비어 있음Lab 4

attach_metadata { node = true }가 있는지, Alloy의 ServiceAccount가 노드를 조회할 권한이 있는지(차트 기본 clusterRules에 포함) 확인합니다. 노드 라벨 이름의 점과 슬래시는 밑줄로 바뀌어 __meta_kubernetes_node_label_lab_customer가 됩니다.

Java 스택 트레이스가 줄마다 따로 저장됨운영

stage.multiline으로 "새 엔트리의 시작"을 정규식으로 정의합니다(예: 날짜로 시작하는 줄). 그 사이의 줄들은 앞 엔트리에 붙습니다. 여러 줄을 합치는 동안 메모리를 쓰므로 max_lines와 max_wait_time을 지정합니다.

convert가 오류를 내거나 일부를 옮기지 못함Lab 6

--report=report.txt로 무엇을 못 옮겼는지 확인합니다. 변환기가 지원하지 않는 오래된 Promtail 기능이 있으면 그 부분만 직접 작성하고, 끝까지 막히면 --bypass-errors로 나머지라도 변환한 뒤 보완합니다.

오늘의 핵심

  1. Alloy는 Promtail과 Grafana Agent의 후속이자 OpenTelemetry Collector 배포판입니다. 컴포넌트를 선언하고 참조로 연결하면 그것이 데이터 흐름이 됩니다.
  2. 로그 파이프라인은 찾기, 다듬기, 읽기, 가공, 보내기입니다. 파싱은 추출 맵에 꺼낼 뿐이고 라벨, 메타데이터는 따로 정합니다.
  3. 모든 수집기가 같은 라벨 표준(customer, cluster/host, service_name, namespace...)을 따라야 한 Loki에서 함께 질의할 수 있습니다. 파드 이름, trace_id는 메타데이터로.
  4. 민감정보는 수집 단계에서 캡처 그룹만 바꿔 지우고, 불필요한 줄은 버리되 버린 양을 메트릭으로 남깁니다.
  5. VM은 systemd(adm, systemd-journal 그룹), Kubernetes는 DaemonSet(자기 노드의 파드만, /var/log 마운트)입니다.
  6. alloy convert는 의미를 옮길 뿐 설계를 고쳐 주지 않습니다. position 파일 이어받기를 확인하고 라벨을 표준에 맞춥니다.

다음 편 예고: 9편 LogQL 완전 정복

이제 hub의 Loki에는 고객사 A의 결제 로그, 웹 서버, DB, 시스템, Kubernetes 로그가 표준 라벨로 쌓여 있습니다. 9편에서는 4편처럼 이 데이터로 LogQL을 처음부터 끝까지 다룹니다. 스트림 셀렉터와 줄 필터, logfmt, json, pattern 파서, 라벨 필터와 줄 형식 지정, count_over_time과 rate, unwrap으로 로그 안의 숫자(duration_ms)를 메트릭으로 만들기, Loki Ruler로 로그 기반 알림을 6편의 Alertmanager에 보내기, 그리고 느린 질의의 원인과 튜닝을 단계별 문제로 연습합니다. 오늘 만든 shop-logger의 장애 로그로 4편의 메트릭 오류율과 로그 오류율을 나란히 비교하는 문제도 포함됩니다.
