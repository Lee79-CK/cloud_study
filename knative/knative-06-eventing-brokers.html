Broker는 인터페이스, 구현은 여럿

사용자 입장에서 Broker는 언제나 같습니다. 주소가 있고, CloudEvents를 받고, Trigger로 배달합니다. 하지만 그 뒤에서 이벤트를 어디에 저장하고 어떻게 나르는지는 Broker 클래스에 따라 완전히 다릅니다. 콘센트 모양은 같아도 뒤에 연결된 발전소가 다른 셈입니다.

Broker 클래스 지정
apiVersion: eventing.knative.dev/v1
kind: Broker
metadata:
  name: orders
  namespace: customer-a
  annotations:
    eventing.knative.dev/broker.class: Kafka   # 구현체 선택
spec:
  config:                                      # 구현체별 설정 참조
    apiVersion: v1
    kind: ConfigMap
    name: kafka-broker-config
    namespace: knative-eventing
  delivery:
    deadLetterSink:
      ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: dlq-handler
클래스를 안 적으면?

knative-eventing 네임스페이스의 config-br-defaults가 정한 기본 클래스가 쓰입니다. 클러스터 전체 기본값과 네임스페이스별 기본값을 따로 둘 수 있어서, 예를 들어 개발 네임스페이스는 인메모리, 고객사 운영 네임스페이스는 Kafka로 나눌 수 있습니다.

config-br-defaults 예시
apiVersion: v1
kind: ConfigMap
metadata:
  name: config-br-defaults
  namespace: knative-eventing
data:
  default-br-config: |
    clusterDefault:
      brokerClass: Kafka
      apiVersion: v1
      kind: ConfigMap
      name: kafka-broker-config
      namespace: knative-eventing
    namespaceDefaults:
      dev-sandbox:
        brokerClass: MTChannelBasedBroker
        apiVersion: v1
        kind: ConfigMap
        name: config-br-default-channel
        namespace: knative-eventing

receiver (수신기)

Broker 주소로 들어온 CloudEvent를 받아 Kafka 토픽에 씁니다. 토픽 기록이 확인된 뒤에야 생산자에게 202를 돌려주므로, 202를 받았다면 이벤트는 디스크에 있습니다.

토픽

Broker마다 하나씩 자동 생성됩니다(이름은 보통 knative-broker-네임스페이스-이름). 파티션 수와 복제 수는 Broker가 참조하는 ConfigMap에서 정합니다.

dispatcher (배달기)

Trigger마다 별도의 컨슈머 그룹으로 토픽을 읽고, 필터를 적용한 뒤 구독자에게 HTTP로 보냅니다. Trigger별로 진행 위치(오프셋)가 따로라 한 구독자가 느려도 다른 구독자는 영향이 없습니다.

controller

Broker, Trigger, KafkaSource 등을 보고 토픽 생성, 컨슈머 그룹 구성, 데이터 플레인 설정을 맞춥니다.

kafka-broker-config
apiVersion: v1
kind: ConfigMap
metadata:
  name: kafka-broker-config
  namespace: knative-eventing
data:
  bootstrap.servers: "my-cluster-kafka-bootstrap.kafka:9092"
  default.topic.partitions: "10"          # 순서 보장 시 최대 병렬도
  default.topic.replication.factor: "3"   # 운영은 3 이상
멀티테넌트라면 KafkaNamespaced

기본 Kafka 클래스는 receiver와 dispatcher를 knative-eventing에 하나만 두고 모든 고객사의 Broker가 공유합니다. 한 고객의 폭주가 다른 고객의 배달을 늦출 수 있습니다. KafkaNamespaced 클래스를 쓰면 데이터 플레인이 Broker가 있는 네임스페이스에 따로 뜹니다. 자원은 더 들지만 고객사 간 성능과 장애가 격리됩니다.

순서 보장 실험

Kafka Broker의 Trigger는 기본적으로 unordered입니다. 이벤트를 동시에 여러 개 보내 처리량이 높지만, 도착 순서는 섞일 수 있습니다. kafka.eventing.knative.dev/delivery.order: ordered 어노테이션을 주면 같은 파티션 안에서는 앞 이벤트가 성공해야 다음 이벤트를 보냅니다. 어느 파티션에 들어갈지는 CloudEvent의 partitionkey 확장 속성으로 정합니다.

고객 A, B, C의 주문 이벤트가 1번부터 4번까지 섞여 들어옵니다. 두 모드를 비교해 보세요. 빨간 테두리는 같은 고객의 이벤트가 순서를 어긴 경우입니다.

구독자가 받은 순서

ordered Trigger와 partitionkey
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: ledger
  annotations:
    kafka.eventing.knative.dev/delivery.order: ordered
spec:
  broker: orders
  filter:
    attributes:
      type: com.mycorp.order.updated
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: ledger
# 생산자는 이벤트에 Ce-Partitionkey: customer-a 처럼 키를 붙인다
ordered의 대가

ordered에서는 파티션 하나에 이벤트가 한 번에 하나씩만 흐르므로, 최대 병렬도는 파티션 수입니다. 구독자 하나가 느리거나 실패해 재시도하면 같은 파티션의 뒤 이벤트가 모두 기다립니다. 정말 순서가 필요한 흐름(원장, 상태 전이)에만 쓰고, 파티션 수는 필요한 병렬도를 고려해 처음부터 넉넉히 잡으세요. Kafka 파티션은 늘릴 수는 있어도 늘리는 순간 키와 파티션의 대응이 바뀝니다.

RabbitMQ Broker

RabbitMQ Broker는 Broker마다 RabbitMQ Exchange를 만들고, Trigger마다 그 Exchange에 묶인 Queue를 만듭니다. 필터는 RabbitMQ의 바인딩 규칙으로 처리되어, 조건에 맞는 이벤트만 각 큐에 쌓입니다. RabbitMQ 클러스터 오퍼레이터와 메시징 토폴로지 오퍼레이터를 함께 설치해 운영합니다.

잘 맞는 경우

고객사가 이미 RabbitMQ를 운영하고 있고 운영 노하우가 있을 때. 이벤트 양이 Kafka가 필요할 만큼 많지 않을 때. 큐 단위 관리 화면에 익숙한 팀.

순서와 병렬

Trigger의 병렬도(parallelism) 설정이 1이면 큐 순서대로 하나씩 보내고, 늘리면 동시에 여러 개를 보냅니다. Kafka의 키 단위 순서와 달리 큐 전체 단위입니다.

재처리

Kafka는 오프셋을 되돌려 과거 이벤트를 다시 읽을 수 있지만, RabbitMQ는 소비된 메시지가 큐에서 사라집니다. 사후 재처리가 중요하면 DLS 보관을 꼼꼼히 하거나 Kafka를 고려하세요.

확인할 점

Knative 본체와 별도 저장소(knative-extensions)의 확장이라 지원 버전과 릴리스 주기를 따로 확인해야 합니다.

Sequence와 Parallel

5편에서 답장(reply)으로 처리 단계를 이을 수 있다고 했습니다. 이 사슬을 리소스 하나로 선언하는 것이 Sequence입니다. 한 이벤트를 여러 갈래로 동시에 보내고 각 갈래의 결과를 모으는 것은 Parallel입니다. 둘 다 내부적으로 Channel과 Subscription을 자동으로 만들어 연결합니다.

sequence.yaml
apiVersion: flows.knative.dev/v1
kind: Sequence
metadata:
  name: order-pipeline
spec:
  channelTemplate:
    apiVersion: messaging.knative.dev/v1
    kind: InMemoryChannel   # 운영은 KafkaChannel
  steps:
    - ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: validate
    - ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: enrich
    - ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: fraud-score
  reply:
    ref:
      kind: Broker
      apiVersion: eventing.knative.dev/v1
      name: orders
parallel.yaml
apiVersion: flows.knative.dev/v1
kind: Parallel
metadata:
  name: notify-all
spec:
  channelTemplate:
    apiVersion: messaging.knative.dev/v1
    kind: InMemoryChannel
  branches:
    - filter:                     # 선택: 이 갈래로 보낼지 판단
        ref:
          apiVersion: serving.knative.dev/v1
          kind: Service
          name: is-vip
      subscriber:
        ref:
          apiVersion: serving.knative.dev/v1
          kind: Service
          name: send-sms
    - subscriber:
        ref:
          apiVersion: serving.knative.dev/v1
          kind: Service
          name: send-email
  reply:
    ref:
      kind: Broker
      apiVersion: eventing.knative.dev/v1
      name: orders
Sequence의 실패는 어디서 멈추나

중간 단계가 재시도를 다 실패하면 그 이벤트는 다음 단계로 가지 않고, 해당 단계 Subscription의 DLS로 갑니다. 단계마다 delivery를 설정할 수 있으므로 중요한 단계에는 DLS를 꼭 지정하세요. 단계별 상태를 기록하며 보상 처리까지 해야 하는 긴 업무 흐름이라면 Sequence보다 워크플로 엔진(예: OpenShift Serverless Logic 같은 Serverless Workflow 구현)이 더 맞습니다.

CloudEvents가 아닌 메시지는?

기존 시스템이 쓴 메시지가 CloudEvents 형식이 아니어도 KafkaSource는 받아들입니다. 이때 Knative가 type(dev.knative.kafka.event), source(토픽 정보), id 같은 속성을 채워 CloudEvent로 감쌉니다. Trigger 필터에서 type 구분이 어렵다면 앞단에 변환 서비스를 두어 의미 있는 type으로 바꿔 Broker에 다시 넣는 패턴이 흔합니다.

Knative Eventing vs KEDA

둘 다 "메시지가 오면 처리한다"를 다루지만 방향이 다릅니다. Knative Eventing은 이벤트를 HTTP로 밀어 주고(push), KEDA는 소비자가 큐에서 직접 당겨 가게(pull) 하면서 큐 길이에 맞춰 소비자 수를 조절합니다.

항목Knative Eventing + ServingKEDA
전달 방식Push. 소비자는 HTTP 서버만 있으면 됨Pull. 소비자가 Kafka·SQS 등 클라이언트 라이브러리로 직접 읽음
소비자 코드메시징 라이브러리 불필요. 언어 무관메시징 시스템별 클라이언트 코드 필요
확장 기준들어오는 HTTP 동시성 (KPA)큐 길이, 컨슈머 랙 등 외부 지표
필터·라우팅Trigger로 선언적 필터없음. 소비자가 직접 처리
강점느슨한 결합, 여러 소비자에 팬아웃, 소비자 단순화대량 배치, 긴 작업, 처리량 극대화, 기존 컨슈머 코드 재사용
함께 쓰기KafkaSource 같은 소스의 데이터 플레인 수를 KEDA로 조절하는 연동 확장이 있습니다. "Eventing으로 라우팅, KEDA로 소스 확장"처럼 역할을 나눌 수 있습니다.

로드맵: RequestReply

이벤트 기반 구조의 오래된 고민은 "호출하는 쪽은 동기 응답을 원하는데 처리는 비동기로 흐른다"는 것입니다. 웹 화면은 결과를 기다리는데 뒤에서는 Broker를 거쳐 여러 서비스가 일합니다. Knative 커뮤니티는 이를 위해 RequestReply 리소스를 로드맵에 올려 두었습니다.

개념은 요청을 CloudEvent로 바꿔 Broker에 넣고, 같은 상관관계 ID를 가진 응답 이벤트가 돌아오면 원래 HTTP 요청에 돌려주는 것입니다. 이 강의 기준 시점에 정식 기능이 아니므로, 사용 전 해당 버전의 릴리스 노트와 기능 상태를 확인하세요. 그 전까지는 응답 이벤트를 저장소에 기록하고 클라이언트가 폴링하거나 웹소켓으로 받는 방식이 일반적입니다.

실습: Kafka Broker 구축

자원 주의

kind 위에 Kafka까지 올리면 메모리를 꽤 씁니다. Docker에 메모리 6GB 이상을 권장합니다. 아래 명령의 릴리스 경로와 버전 표기는 설치 시점에 공식 문서에서 다시 확인하세요.

  1. Strimzi로 단일 노드 Kafka 띄우기

    bash
    kubectl create namespace kafka
kubectl create -f 'https://strimzi.io/install/latest?namespace=kafka' -n kafka
kubectl apply -f https://strimzi.io/examples/latest/kafka/kafka-single-node.yaml -n kafka

kubectl wait kafka/my-cluster --for=condition=Ready --timeout=600s -n kafka

  2. Knative Kafka Broker 설치

    bash
    REL=https://github.com/knative-extensions/eventing-kafka-broker/releases/download/knative-v1.23.0
kubectl apply -f $REL/eventing-kafka-controller.yaml
kubectl apply -f $REL/eventing-kafka-broker.yaml

kubectl get pods -n knative-eventing | grep kafka

  3. 설정 ConfigMap과 Broker 만들기

    bash
    cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: kafka-broker-config
  namespace: knative-eventing
data:
  bootstrap.servers: "my-cluster-kafka-bootstrap.kafka:9092"
  default.topic.partitions: "3"
  default.topic.replication.factor: "1"
---
apiVersion: eventing.knative.dev/v1
kind: Broker
metadata:
  name: orders
  annotations:
    eventing.knative.dev/broker.class: Kafka
spec:
  config:
    apiVersion: v1
    kind: ConfigMap
    name: kafka-broker-config
    namespace: knative-eventing
EOF
kubectl get broker orders

  4. ordered Trigger와 받는 쪽

    bash
    kn service create event-display \
  --image gcr.io/knative-releases/knative.dev/eventing/cmd/event_display --scale-min 1

cat <<'EOF' | kubectl apply -f -
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: ledger
  annotations:
    kafka.eventing.knative.dev/delivery.order: ordered
spec:
  broker: orders
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: event-display
EOF

  5. partitionkey를 붙여 이벤트 발행

    bash
    BROKER=$(kubectl get broker orders -o jsonpath='{.status.address.url}')
echo $BROKER

kubectl run curl --image=curlimages/curl --rm -it --restart=Never --env="B=$BROKER" -- sh -c '
for i in 1 2 3 4; do for k in customer-a customer-b; do
  curl -s -o /dev/null -w "%{http_code} " $B \
    -H "Ce-Specversion: 1.0" -H "Ce-Id: $k-$i" -H "Ce-Source: /lab" \
    -H "Ce-Type: com.mycorp.order.updated" -H "Ce-Partitionkey: $k" \
    -H "Content-Type: application/json" -d "{\"seq\":$i,\"key\":\"$k\"}"
done; done; echo'

kubectl logs -l serving.knative.dev/service=event-display -c user-container --tail=80 | grep seq

  6. Kafka 쪽에서 토픽과 컨슈머 그룹 보기

    bash
    kubectl exec -n kafka -it my-cluster-dual-role-0 -- \
  bin/kafka-topics.sh --bootstrap-server localhost:9092 --list | grep knative

kubectl exec -n kafka -it my-cluster-dual-role-0 -- \
  bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --all-groups

    Pod 이름은 Strimzi 예제 버전에 따라 다를 수 있으니 kubectl get pods -n kafka로 먼저 확인하세요.

  7. Sequence 맛보기 (기본 인메모리 Channel)

    Knative 예제 이미지 appender는 받은 메시지 뒤에 문자열을 덧붙여 답장합니다.

    bash
    for n in 1 2 3; do
  kn service create step-$n \
    --image gcr.io/knative-releases/knative.dev/eventing/cmd/appender \
    --env MESSAGE=" - step $n"
done

cat <<'EOF' | kubectl apply -f -
apiVersion: flows.knative.dev/v1
kind: Sequence
metadata:
  name: lab-seq
spec:
  channelTemplate:
    apiVersion: messaging.knative.dev/v1
    kind: InMemoryChannel
  steps:
    - ref: {apiVersion: serving.knative.dev/v1, kind: Service, name: step-1}
    - ref: {apiVersion: serving.knative.dev/v1, kind: Service, name: step-2}
    - ref: {apiVersion: serving.knative.dev/v1, kind: Service, name: step-3}
  reply:
    ref: {apiVersion: serving.knative.dev/v1, kind: Service, name: event-display}
EOF

kn source ping create seq-ping --schedule "*/1 * * * *" \
  --data '{"message":"hello"}' --sink sequence:lab-seq
# 1~2분 뒤 event-display 로그에서 "hello - step 1 - step 2 - step 3" 확인

  8. 정리

    bash
    kn source ping delete seq-ping
kubectl delete sequence lab-seq
kubectl delete trigger ledger
kubectl delete broker orders
for n in 1 2 3; do kn service delete step-$n; done
kn service delete event-display

운영 체크포인트

컨슈머 랙을 첫 번째 지표로
Kafka Broker에서 Trigger별 컨슈머 그룹의 랙(읽지 못하고 쌓인 이벤트 수)은 "구독자가 따라가지 못한다"는 가장 직접적인 신호입니다. 랙이 계속 늘면 구독자 max-scale, 동시성 설정, 하위 시스템 병목을 확인하세요.
토픽 보존 기간과 재처리
Broker 토픽의 보존 기간이 짧으면 장애가 길어졌을 때 아직 배달 못 한 이벤트가 지워질 수 있습니다. 고객사 장애 대응 목표 시간보다 보존 기간을 넉넉하게 잡으세요.
복제 수와 min.insync.replicas
운영은 복제 3 이상을 기본으로 하고, Kafka 쪽 min.insync.replicas 설정과 함께 봐야 "202를 받았다면 디스크에 있다"가 진짜가 됩니다.
이벤트 크기 상한과 Claim Check
Kafka 기본 메시지 최대 크기는 약 1MB입니다. 파일이나 큰 문서를 이벤트에 직접 담지 말고, 객체 저장소에 올린 뒤 위치만 이벤트로 보내는 Claim Check 패턴을 쓰세요.
데이터 플레인 Pod 자원과 격리
공유 Kafka 클래스에서는 kafka-broker-receiver와 dispatcher가 모든 고객 트래픽을 처리합니다. HPA와 자원 요청을 점검하고, 고객사 간 격리가 계약 요건이면 KafkaNamespaced를 쓰세요.
업그레이드 순서
Knative Eventing 본체와 eventing-kafka-broker 같은 확장은 버전을 맞춰 함께 올려야 합니다. 본체만 먼저 올리면 확장이 동작하지 않을 수 있습니다. 10편 운영 편에서 업그레이드 절차를 다룹니다.

정리와 다음 편

  1. Broker는 같은 인터페이스에 여러 구현이 있으며, broker.class와 config-br-defaults로 고릅니다.
  2. 운영 환경의 기본 선택은 Kafka Broker입니다. receiver가 토픽에 쓰고, dispatcher가 Trigger별 컨슈머 그룹으로 배달합니다.
  3. 멀티테넌트 격리가 필요하면 KafkaNamespaced로 데이터 플레인을 네임스페이스별로 띄웁니다.
  4. 순서가 필요하면 Trigger를 ordered로, 생산자는 partitionkey를 붙입니다. 병렬도는 파티션 수가 상한입니다.
  5. Sequence는 단계 사슬, Parallel은 갈래 분기를 선언적으로 만듭니다.
  6. 기존 Kafka와는 KafkaSource·KafkaSink로 잇고, 대량 pull 처리는 KEDA와 역할을 나눕니다.
  7. 컨슈머 랙, 보존 기간, 복제 수, 이벤트 크기가 운영의 핵심 점검 항목입니다.
