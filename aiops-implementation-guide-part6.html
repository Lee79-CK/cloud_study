    대부분의 조직에서 이상탐지 ML은 SLO 알림보다 가치가 작습니다. 그럼에도 이 편이 필요한 이유는, SLO로 못 잡는 영역(용량 포화, 서서히 새는 문제, 사용자 영향 이전의 조짐)이 분명히 있기 때문입니다. 순서를 지키는 것이 이 편의 핵심 메시지입니다.

    CHAPTER 01

    정확도 99% 탐지기가 쓸모없는 이유

    이상탐지를 처음 도입하는 팀이 거의 예외 없이 부딪히는 수학적 현실입니다.

    기저율의 문제

    시계열 하나를 1분 간격으로 본다면 하루에 1,440개의 판정이 생깁니다. 시계열이 500개면 하루 72만 번입니다. 진짜 이상은 하루 한두 번일까요. 이 극단적인 불균형 때문에, 오탐률이 아주 낮아도 알림 수는 감당 불가가 됩니다.

    오탐 계산기

    탐지기 성능을 넣으면, 실제로 담당자가 받게 될 알림 수와 그중 진짜 비율을 계산합니다.

    –
    하루 알림 수
    –
    그중 진짜
    –
    정밀도(PPV)

    슬라이더를 움직여 보면 알 수 있습니다. 오탐률을 0.01% 수준까지 낮춰야 겨우 쓸 만해집니다. 이것이 "정확도"라는 단어가 이 분야에서 무의미한 이유이고, 이상탐지를 개별 시계열이 아니라 서비스·사건 단위로 집계해야 하는 이유이기도 합니다.

    그래서 취하는 전략

    • 대상 축소 — 모든 지표가 아니라 사용자 영향과 연결된 소수 지표만 탐지 대상으로. 보통 서비스당 5~10개면 충분합니다.
    • 집계 후 알림 — 개별 포인트가 아니라 "연속 N회" 또는 "한 서비스에서 동시에 여러 지표"일 때만 사건화합니다.
    • 상관분석과 결합 — 2편의 사건 병합을 거치면 탐지 100건이 사건 3건이 됩니다. 이상탐지의 오탐은 파이프라인 뒷단에서도 흡수됩니다.
    • 심각도 분리 — 모든 이상이 사람을 깨울 필요는 없습니다. 대부분은 "기록하고 아침에 본다"로 충분합니다.
    용어 정리

    재현율(Recall)은 실제 이상 중 잡아낸 비율, 정밀도(Precision)는 울린 알림 중 진짜인 비율입니다. 운영에서 담당자가 체감하는 것은 정밀도이고, 놓친 장애로 드러나는 것은 재현율입니다. 둘은 상충하므로 어느 쪽을 얼마나 포기할지 미리 정해두는 것이 설계의 출발점입니다.

    CHAPTER 02

    신호를 먼저 이해하기

    모델을 고르기 전에 데이터의 성질을 알아야 합니다. 이 단계를 건너뛴 탐지기는 거의 항상 계절성에서 무너집니다.

    지표 유형별 성질

    유형예특징탐지 시 주의
    카운터 비율초당 요청 수, 에러 수강한 일·주 주기계절성 제거 필수. 절대 임계치는 거의 무용
    비율(ratio)에러율, 성공률트래픽이 적으면 분모가 작아 튐최소 요청 수 조건을 함께 걸기
    지연 분위수p50·p95·p99꼬리가 두꺼움. 정규분포 가정이 깨짐평균±3σ 방식 금지. 분위수와 강건 통계 사용
    포화 지표디스크 사용률, 커넥션 풀단조 증가 후 한계 도달임계치보다 도달 시점 예측이 유용
    게이지메모리, 큐 길이재시작 시 급락(계단)재시작을 이상으로 오인하지 않게 처리

    탐지 전에 확인할 데이터 품질 다섯 가지

    • 결측 — 수집 실패로 생긴 공백을 0으로 채우면 "급락"이 만들어집니다. 결측과 0은 다릅니다.
    • 재시작·재배포 — 카운터 리셋과 파드 교체는 정상 사건입니다. 변경 이력(2편 changes)과 대조해 제외하세요.
    • 시계열 수명 — 파드 교체로 새 시계열이 계속 생깁니다. 학습에는 집계된 상위 수준 시계열을 쓰세요.
    • 샘플링 간격 불균일 — 스크레이프 지연으로 간격이 흔들리면 일부 모델이 오작동합니다.
    • 이력 길이 — 주간 계절성을 학습하려면 최소 수 주, 안정적으로는 두세 달의 이력이 필요합니다.
    가장 흔한 실패

    월요일 아침마다, 배포 직후마다, 월말 정산 배치마다 오탐이 발생하는 탐지기. 원인은 모델이 나빠서가 아니라 주기와 알려진 이벤트를 반영하지 않아서입니다. 공휴일·이벤트 달력을 데이터로 갖고 있으면 오탐이 크게 줄어듭니다.

    탐지 방식 선택

    지표 하나를 떠올리고 답해 보세요.

    멈출 줄 아는 것이 실력

    CHAPTER 04

    통계 기준선 — 가장 가성비 높은 탐지

    코드 수십 줄과 며칠간의 이력만 있으면 됩니다. 그리고 대부분의 상황에서 이것으로 충분합니다.

    왜 평균±3σ를 쓰면 안 되는가

    운영 지표는 정규분포가 아닙니다. 꼬리가 두껍고, 과거의 장애가 평균과 표준편차를 오염시킵니다. 장애가 한 번 있었던 지표는 σ가 커져서 다음 장애를 못 잡습니다. 그래서 실무에서는 중앙값과 MAD(중앙값 절대편차) 같은 강건 통계를 씁니다.

    강건 기준선 — 시간대별 프로파일 + MAD
    import numpy as np

def seasonal_baseline(history: np.ndarray, period: int = 24):
    """history: 시간 단위 값 배열(최근 N주). period: 계절 주기(시간)"""
    # 같은 시간대끼리 묶어 중앙값을 구한다 (요일 구분이 필요하면 168로)
    by_phase = [history[i::period] for i in range(period)]
    med = np.array([np.median(p) for p in by_phase])

    # MAD: 이상치에 끌려가지 않는 산포 추정치
    mad = np.array([np.median(np.abs(p - np.median(p))) for p in by_phase])
    # 정규분포 기준 표준편차 환산 계수. 0이 되면 탐지가 폭주하므로 하한을 둔다
    sigma = np.maximum(mad * 1.4826, med * 0.02 + 1e-9)
    return med, sigma

def score(value: float, phase: int, med, sigma) -> float:
    return (value - med[phase]) / sigma[phase]      # 강건 z-score

# 알림 조건 예: z > 4 가 3회 연속 (단발 스파이크를 걸러낸다)

    직접 확인해 보기

    아래는 일주일치 요청량(시간 단위)입니다. 두 개의 진짜 이상이 숨어 있습니다. 하나는 한낮의 급증, 다른 하나는 새벽의 이상 증가입니다. 새벽 이상은 절대값이 한낮 정상값보다 낮기 때문에, 정적 임계치로는 원리적으로 잡을 수 없습니다.

    탐지 방식 비교 실험

    관측값 기준선·임계 탐지된 지점 실제 이상 위치
    실험에서 확인할 것

    정적 임계치를 낮춰 새벽 이상을 잡으려 하면 한낮 정상 구간이 통째로 알림이 됩니다. 계절 기준선은 같은 시간대끼리 비교하므로 둘 다 잡으면서 오탐이 적습니다. 이 차이가 실무에서 알림 수백 건의 차이를 만듭니다.

    변화점 탐지 — 다른 종류의 이상

    스파이크가 아니라 수준이 바뀌는 이상도 있습니다. 배포 후 지연이 20ms에서 35ms로 올라가 그대로 유지되는 경우, 스파이크 탐지기는 아무것도 못 잡습니다. 이때는 변화점 탐지를 씁니다.

    • CUSUM — 누적합이 임계를 넘으면 수준 변화로 판정. 구현이 단순하고 온라인 처리에 적합합니다.
    • 이전 창 vs 현재 창 비교 — 최근 1시간과 직전 24시간의 분포를 비교(예: 분위수 차이). 직관적이고 설명하기 쉽습니다.
    • 배포 전후 비교 — 변경 이력이 있으므로, 배포 시각을 기준으로 전후를 비교하면 회귀 탐지가 됩니다. 이 방식이 실무에서 가장 유용합니다.
    배포 회귀 탐지 — 변경 이력과 결합
    async def detect_deploy_regression(service: str, deploy_at, scope):
    # 배포 직후 안정화 시간을 건너뛴다(웜업·캐시 미스 구간)
    after  = await scope.promql(f'quantile_over_time(0.95, latency{{service="{service}"}}[30m])',
                                at=deploy_at + timedelta(minutes=10))
    # 비교 대상은 '직전'이 아니라 '지난주 같은 시간대'가 더 안전하다
    before = await scope.promql(f'quantile_over_time(0.95, latency{{service="{service}"}}[30m])',
                                at=deploy_at - timedelta(days=7))

    ratio = after / max(before, 1e-9)
    if ratio > 1.3:          # 30% 이상 악화
        return Finding(kind="deploy_regression", service=service,
                       evidence={"before": before, "after": after, "ratio": ratio},
                       confidence="high" if ratio > 2 else "medium")
    CHAPTER 05

    예측 기반 — 터지기 전에 알기

    이상탐지가 "지금 이상한가"를 묻는다면, 예측은 "이대로면 언제 문제가 되는가"를 묻습니다. 운영 가치는 후자가 더 큽니다.

    두 가지 용도

    • 포화 시점 예측 — 디스크, 커넥션 풀, IP 대역, 인증서, 쿼터. "4시간 뒤 가득 참"을 알면 새벽 호출이 업무시간 작업이 됩니다.
    • 예측 구간 이탈 탐지 — 다음 값의 예측 구간을 만들고, 관측값이 벗어나면 이상으로 판정합니다. 계절 기준선의 일반화된 형태입니다.
    포화 시점 추정 — 단순하지만 매우 유용
    # PromQL만으로도 상당 부분 가능하다. 먼저 이것부터 시도할 것
# 6시간 추세로 볼 때 4시간 내 디스크가 가득 차는가
predict_linear(node_filesystem_avail_bytes{mountpoint="/var"}[6h], 4*3600) < 0

# 실무 보정: 단조 증가가 아닌 톱니 패턴(로그 회전)에서는 선형 추세가 왜곡된다
# → 최근 저점들의 추세를 쓰거나, 회전 주기보다 긴 창(24h)을 사용한다
predict_linear(min_over_time(node_filesystem_avail_bytes[1h])[24h:1h], 12*3600) < 0
    가장 저평가된 알림

    "디스크가 95%입니다"(지금 당장 대응)와 "이 추세면 내일 오전 10시에 가득 찹니다"(계획적 대응)는 담당자의 삶의 질이 완전히 다릅니다. 포화형 지표는 전부 예측 기반으로 바꾸는 것을 권합니다. 구현 비용은 PromQL 한 줄 수준인데 효과는 큽니다.

    예측 구간을 알림으로 쓸 때

    • 점 예측이 아니라 구간을 써야 합니다. 예측값 하나와 비교하면 정상 변동도 전부 이상이 됩니다.
    • 구간 폭이 시간대별로 달라야 합니다. 새벽은 변동이 작고 낮은 큽니다. 고정 폭은 한쪽에서 반드시 실패합니다.
    • 예측이 틀리는 구간을 알아야 합니다. 프로모션·이벤트처럼 알려진 급증은 예측에 넣거나 탐지에서 제외합니다.
    • 수평선 길이에 주의 — 짧은 예측은 정확하지만 대응 시간이 없고, 긴 예측은 불확실합니다. 운영 경보는 보통 1~24시간 범위가 실용적입니다.
    CHAPTER 06

    시계열 파운데이션 모델 — 2026년의 새 선택지

    지난 2년 사이 가장 크게 바뀐 부분입니다. 시계열마다 모델을 학습시키던 일이, 모델을 고르는 일로 바뀌었습니다.

    무엇이 달라졌나

    대규모 시계열 코퍼스로 사전학습된 모델들이 제로샷으로, 즉 처음 보는 시계열에 대해 별도 학습 없이 예측을 내놓습니다. 관측 플랫폼처럼 시계열이 수만 개인 환경에서는 이 점이 결정적입니다. 시계열마다 모델을 만들고 재학습하는 운영이 불가능하기 때문입니다.

    벤치마크를 읽을 때 주의할 점

    공개 평가들이 일관되게 보여주는 것은 해상도에 따라 순위가 바뀐다는 점입니다. 쿠버네티스 파드 지표를 대상으로 한 평가에서는 1분 해상도에서 인프라 지표로 학습된 모델이 크게 앞섰고, 1시간 해상도에서는 다른 모델이 앞섰습니다. 즉 "어떤 모델이 최고인가"라는 질문은 성립하지 않습니다. 자기 환경의 해상도·지표 종류·수평선으로 직접 평가해야 합니다.

    이상탐지에 쓰는 방법

    1. 최근 컨텍스트(예: 512 포인트)를 모델에 넣어 다음 구간의 분위수 예측을 받는다
    2. 관측값이 상위/하위 분위(예: p1~p99) 밖이면 이상 후보로 표시한다
    3. 연속 N회 또는 동일 서비스 복수 지표에서 발생할 때만 사건화한다(1장의 기저율 대응)
    4. 변경 이력·점검 창과 대조해 알려진 원인을 제외한다
    도입 전 확인할 현실적 제약

    ① 대부분 모델이 규칙적 샘플링을 가정합니다. 간격이 불규칙하면 그 자체를 신호로 오해합니다.
    ② 학습된 최대 예측 길이를 넘어가면 성능이 떨어집니다. 자기 수평선으로 검증 후 확정하세요.
    ③ 이력이 아주 짧은 새 시계열은 콜드 스타트 문제가 있습니다.
    ④ GPU 비용과 추론 지연이 생깁니다. 수만 시계열을 1분 주기로 돌리는 것은 현실적이지 않습니다.

    현실적인 운영 방식

    • 계층 나누기 — 전체 시계열은 통계 기준선으로, 핵심 지표 수백 개만 파운데이션 모델로.
    • 주기 낮추기 — 1분마다가 아니라 5~15분 주기로 예측을 갱신하고, 그 사이는 예측 구간을 재사용합니다.
    • 배치 추론 — 시계열을 묶어 한 번에 추론하면 GPU 효율이 크게 올라갑니다.
    • 앙상블·보정 — 제로샷 예측은 편향과 분산이 있습니다. 잔차를 보정하거나 통계 방법과 결합하면 실전 성능이 좋아진다는 보고가 많습니다.
    • 폴백 — 모델 서버가 죽어도 통계 기준선으로 계속 탐지되어야 합니다. 3편의 신뢰성 원칙과 같습니다.

    CHAPTER 07

    점수를 알림으로 바꾸기

    탐지기는 점수를 냅니다. 알림은 사람을 깨웁니다. 이 사이에 있는 변환 규칙이 실제 체감 품질을 결정합니다.

    변환 규칙 여섯 가지

    • 지속 시간 조건 — "z > 4가 3회 연속". 단발 스파이크의 대부분은 수집 지연이나 일시적 부하입니다.
    • 히스테리시스 — 발생 임계와 해제 임계를 다르게(예: 발생 4, 해제 2.5). 경계에서 깜빡이는 알림을 막습니다.
    • 최소 볼륨 조건 — 요청이 시간당 10건인 서비스의 에러율 50%는 5건입니다. 분모 조건을 함께 거세요.
    • 알려진 이벤트 억제 — 배포 직후 N분, 점검 창, 고객사 이벤트 기간.
    • 서비스 단위 집계 — 같은 서비스의 여러 지표가 동시에 이상하면 하나의 사건으로. 2편 상관분석의 입력이 됩니다.
    • 심각도 매핑 — 이상 점수의 크기와 영향 범위로 심각도를 정합니다. 모든 이상이 critical이면 아무것도 critical이 아닙니다.
    app/detect/emit.py — 점수 → 사건
    FIRE, CLEAR = 4.0, 2.5          # 히스테리시스
NEED_CONSECUTIVE = 3

def update(state: SeriesState, z: float, ctx: Context) -> Event | None:
    # 알려진 이벤트 구간에서는 점수를 계산하되 알림은 내지 않는다(기록은 남김)
    suppressed = ctx.in_deploy_window or ctx.in_maintenance

    state.streak = state.streak + 1 if abs(z) > FIRE else 0

    if not state.firing and state.streak >= NEED_CONSECUTIVE and not suppressed:
        state.firing = True
        return Event(kind="anomaly", severity=severity_of(z, ctx), z=z,
                     # 근거를 함께 실어야 2편 에이전트가 활용할 수 있다
                     baseline=state.baseline, observed=state.last,
                     phase=state.phase, window=state.window)

    if state.firing and abs(z) < CLEAR:
        state.firing = False
        return Event(kind="anomaly_resolved")
    return None

def severity_of(z, ctx):
    if ctx.user_facing and abs(z) > 8: return "critical"
    if ctx.user_facing:              return "high"
    return "warning"                  # 내부 지표 이상은 기본적으로 깨우지 않는다
    이상탐지 알림에는 맥락을 함께 실으세요

    "anomaly detected on metric X"만 오는 알림은 담당자가 아무것도 할 수 없습니다. 최소한 관측값, 기준선, 벗어난 정도, 같은 시간대의 지난주 값, 최근 변경이 함께 와야 합니다. 이 정보는 2편 에이전트의 조사 출발점이 되기도 합니다.

    CHAPTER 08

    평가 — 라벨이 없는 현실에서

    "정답 데이터가 없어서 평가를 못 한다"는 말은 사실이 아닙니다. 약한 라벨은 이미 쌓여 있습니다.

    어디서 라벨을 얻는가

    • 사건 기록 — 2편의 incidents 테이블. 사건 발생 시각과 영향 서비스가 곧 라벨입니다.
    • 사람 피드백 — "유용함/노이즈" 버튼. 정밀도를 직접 측정하는 유일한 수단입니다.
    • 포스트모템 — "우리가 X시간 늦게 알았다"는 기록이 재현율의 근거가 됩니다.
    • 합성 주입 — 스테이징에서 인위적 부하·장애를 만들어 탐지 여부를 확인합니다.

    시간 허용 오차를 둔 평가

    이상탐지 평가는 일반 분류와 다릅니다. 정확한 포인트가 아니라 사건 구간을 맞히면 성공으로 봐야 합니다. 장애가 03:10에 시작됐는데 탐지가 03:13이면 실무적으로 성공입니다.

    evals/detect_eval.py — 구간 기반 평가
    TOLERANCE = timedelta(minutes=10)

def evaluate(detections, incidents):
    matched, late = set(), []
    for inc in incidents:
        # 사건 시작 전후 허용 구간 안에 탐지가 있으면 성공
        hits = [d for d in detections
                if d.service == inc.service
                and inc.opened_at - TOLERANCE <= d.at <= inc.opened_at + TOLERANCE]
        if hits:
            matched.add(inc.id)
            late.append((min(h.at for h in hits) - inc.opened_at).total_seconds())

    recall = len(matched) / max(len(incidents), 1)
    # 어떤 사건에도 매칭되지 않은 탐지 = 오탐 후보(진짜 조기탐지일 수도 있으므로 검토 필요)
    unmatched = [d for d in detections if not near_any(d, incidents, TOLERANCE)]
    return {
        "recall": recall,
        "alerts_per_day": len(detections) / days_covered,
        "unmatched_ratio": len(unmatched) / max(len(detections), 1),
        "median_lead_sec": np.median(late) if late else None,   # 음수면 조기 탐지
    }

    주목할 지표는 median_lead입니다. 사건보다 먼저 탐지했다면 음수가 되고, 이것이 이상탐지의 진짜 가치입니다. "사건과 동시에 울리는 탐지기"는 이미 알고 있는 것을 반복할 뿐입니다.

    섀도 모드 운영

    1. 새 탐지 규칙·모델은 알림을 보내지 않고 기록만 2~4주
    2. 주간으로 "이 기간 탐지 수"와 "실제 사건 매칭"을 확인
    3. 하루 알림 수가 목표치(예: 담당자 1인당 5건) 이하로 떨어지면 활성화
    4. 활성화 후 첫 2주는 피드백 수집을 집중적으로
    하지 말아야 할 평가

    공개 이상탐지 벤치마크 점수로 운영 도입을 결정하지 마세요. 데이터 성격이 다르고, 많은 벤치마크가 실제 운영 조건(계절성, 배포 이벤트, 극단적 불균형)을 반영하지 않습니다. 자기 환경의 지난 3개월 데이터로 재생 평가하는 것이 유일하게 믿을 만한 방법입니다.

    CHAPTER 09

    운영 — 드리프트와 비용

    탐지기는 만든 날이 가장 정확합니다. 그 뒤로는 관리 대상이 됩니다.

    드리프트가 생기는 이유

    • 정상의 변화 — 트래픽 성장, 아키텍처 변경, 캐시 도입으로 기준선 자체가 달라집니다.
    • 지표 의미 변화 — 같은 이름의 지표가 다른 것을 재게 되는 경우(계측 코드 변경).
    • 장애의 학습 — 롤링 윈도로 기준선을 갱신하면, 장애 상태가 점점 정상으로 편입됩니다.

    마지막 항목이 특히 위험합니다. 만성적으로 느린 서비스가 기준선에 흡수되어 더 이상 아무것도 탐지되지 않는 상태가 됩니다. 방지책은 기준선 학습 시 사건 구간을 제외하는 것입니다. 2편의 사건 기록이 여기서도 쓰입니다.

    기준선 학습에서 장애 구간 제외
    async def fit_baseline(series: str, scope, weeks: int = 4):
    hist = await scope.fetch_series(series, weeks=weeks)

    # 확인된 사건 구간은 '정상'의 정의에서 빼야 한다
    bad = await scope.sql("""
        SELECT opened_at, coalesce(closed_at, opened_at + interval '1 hour')
        FROM incidents WHERE tenant = :tenant AND opened_at > now() - :w
    """, {"w": timedelta(weeks=weeks)})

    clean = [p for p in hist if not any(s <= p.at <= e for s, e in bad)]

    # 데이터가 너무 많이 빠졌다면 학습하지 말고 경고 — 조용한 실패 방지
    if len(clean) < 0.7 * len(hist):
        metrics.baseline_skipped.labels(series).inc()
        raise InsufficientCleanHistory(series)

    return seasonal_baseline(np.array([p.value for p in clean]))

    CHAPTER 11

    정리 — 도입 순서와 점검

    이 편의 내용을 실제로 적용하는 순서입니다.

    단계별 도입

    1. 1단계 — 포화형 지표를 전부 예측 기반 경보로 전환(PromQL 수준). 가장 싸고 효과가 즉시 보입니다
    2. 2단계 — 핵심 서비스 지표에 계절 기준선 탐지 도입, 섀도 모드 2주
    3. 3단계 — 배포 전후 비교 기반 회귀 탐지 추가(변경 이력과 결합)
    4. 4단계 — 탐지 결과를 사건 파이프라인에 연결하고 에이전트 조사 입력으로 사용
    5. 5단계 — 필요성이 입증되면 파운데이션 모델을 핵심 지표에 한정 적용

    안티패턴 6선

    1. 모든 지표에 탐지 적용 — 기저율이 알림 수를 감당 불가로 만듭니다.
    2. 평균±3σ — 꼬리가 두꺼운 운영 지표에서 오탐과 미탐을 동시에 만듭니다.
    3. 계절성 무시 — 월요일 아침마다 울리는 탐지기는 결국 무시됩니다.
    4. 장애 구간을 기준선에 포함 — 만성 문제가 정상으로 학습됩니다.
    5. 벤치마크 점수로 도입 결정 — 자기 데이터로 재생 평가가 유일한 근거입니다.
    6. 탐지 결과를 알림으로 직행 — 지속 조건·히스테리시스·집계 없이 보내면 노이즈가 됩니다.
