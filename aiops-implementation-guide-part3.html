    CHAPTER 01

    에이전트를 나눠야 할 때, 나누면 안 될 때

    멀티 에이전트는 성능 개선 기법이 아니라 구조적 제약을 푸는 기법입니다. 제약이 없으면 비용만 늘어납니다.

    먼저 알아야 할 반직관적 사실

    2025~2026년의 여러 벤치마크와 프로덕션 보고가 같은 방향을 가리킵니다.

    • 같은 도구와 같은 토큰 예산을 주면 단일 에이전트가 멀티 에이전트와 비등하거나 더 나은 경우가 많습니다. 과거에 보고된 멀티 에이전트의 우위는 상당 부분 "더 많은 연산을 썼기 때문"으로 설명됩니다.
    • 멀티 에이전트가 주는 정확도 향상은 크지 않은데(보고에 따라 수 %p 수준) 비용은 대략 2배 이상으로 뜁니다.
    • 실패는 프롬프트 버그가 아니라 구조적입니다. 역할 오해와 작업 중복, 검증 생략, 오케스트레이터의 컨텍스트 누적이 반복적으로 관찰되는 실패 유형입니다.

    그래서 판단 기준은 "더 똑똑해질까"가 아니라 다음 두 가지여야 합니다.

    분업이 정당한 두 가지 이유

    ① 컨텍스트 격리 — 한 하위 작업이 토큰을 대량으로 먹어서 본체의 컨텍스트를 오염시킬 때. 예: 로그 3만 줄을 훑어 에러 패턴만 뽑는 작업.
    ② 실제 병렬성 — 서로 의존하지 않는 작업을 동시에 돌려 지연을 줄일 수 있을 때. 예: 사건에 묶인 서비스 4개를 동시에 조사.
    이 둘 중 하나도 해당하지 않으면 단일 에이전트에 도구를 더 주는 편이 거의 항상 낫습니다.

    AIOps에서의 구체적 판단

    상황권장이유
    단일 서비스 파드 장애단일 에이전트도구 3~4회 호출로 끝남. 분업은 지연만 추가
    5개 서비스가 얽힌 사건조사 서브에이전트 병렬서비스별 조사는 독립적이고 동시 실행 가능
    로그 대량 분석서브에이전트로 격리원문은 서브에 두고 요약만 본체로 반환
    조치 제안의 타당성 검토검증 에이전트 추가생성과 검증을 분리하면 근거 없는 단정이 줄어듦
    반복되는 단순 알림 분류작은 모델 단일 호출에이전트 루프 자체가 과잉
    비용의 비선형성

    오케스트레이터는 모든 워커의 결과를 컨텍스트에 쌓습니다. 워커가 4개를 넘어가면 컨텍스트 한계에 자주 부딪히고, 분해·집계를 위한 추가 호출이 워커 호출 위에 얹힙니다. 테스트에서 사건당 몇백 원이던 것이 실제 트래픽에서 감당 못 할 수준으로 뛰는 사고가 여기서 납니다. 워커 수 상한과 사건당 예산은 코드로 강제하세요.

    CHAPTER 02

    오케스트레이션 패턴과 실패 유형

    패턴은 많지만 운영 영역에서 실제로 쓸 만한 것은 넷입니다. 나머지는 대부분 과잉입니다.

    패턴구조적합한 작업주된 실패
    순차 파이프라인고정된 단계를 차례로분류 → 조사 → 요약처럼 순서가 정해진 흐름앞 단계 오류가 뒤로 전파(단계별 출력 검증 필요)
    팬아웃·팬인독립 작업 병렬 후 취합서비스별·노드별 동시 조사일부 실패 처리 누락, 취합 시 컨텍스트 폭주
    오케스트레이터-워커런타임에 하위 작업을 결정해 배분사건 유형을 미리 알 수 없는 조사오케스트레이터가 병목이자 단일 장애점
    생성-검증(메이커-체커)만든 결과를 다른 에이전트가 비판조치 제안처럼 정확도가 속도보다 중요한 곳비용 2배 이상. 검증자가 생성자에 동조하는 경향

    토론(debate) 패턴을 권하지 않는 이유

    여러 에이전트가 논쟁해 합의하는 방식은 매력적으로 들리지만, 운영에서는 두 가지 문제가 큽니다. 첫째, 에이전트들이 다수 의견에 동조해 틀린 합의를 만듭니다. 둘째, 3개 에이전트로 5라운드를 돌면 호출이 15회가 되어 비용과 지연이 감당이 안 됩니다. 장애 대응처럼 90초 안에 답이 필요한 상황에는 맞지 않습니다.

    실패를 줄이는 설계 규칙

    • 출력 계약을 강하게 — 각 에이전트는 정해진 JSON 스키마로만 반환합니다. 자연어로 주고받으면 역할 오해가 늘어납니다.
    • 서브에이전트는 한 가지 일만 — 조사면 조사, 검증이면 검증. 서브가 다시 서브를 부르게 하지 마세요. 깊이는 1단계로 제한합니다.
    • 부분 실패를 명시적으로 처리 — 워커 4개 중 1개가 실패했을 때 무엇을 할지 코드에 적혀 있어야 합니다. "그냥 무시"도 명시적 선택이어야 합니다.
    • 취합은 요약본으로 — 워커의 원문이 아니라 정해진 크기의 요약만 오케스트레이터로 올립니다.
    • 단계별 타임아웃 — 전체 예산을 단계에 나눠 배분하고, 초과하면 그 단계 결과 없이 진행합니다.
    CHAPTER 03

    AIOps에 맞는 4역할 구성

    2편의 단일 조사 에이전트를 확장하는 가장 실용적인 형태입니다. 각 역할은 서로 다른 크기의 모델을 씁니다.

    1. 분류기(Triage) — 사건을 유형·심각도로 분류하고 조사할지 결정. 작은 모델, 단일 호출, 루프 없음
    2. 조사자(Investigator) — 도구를 호출하며 가설을 좁힘. 서비스가 여럿이면 병렬 서브에이전트. 큰 모델
    3. 검증자(Critic) — 조사 결과의 근거가 결론을 지지하는지만 검사. 중간 모델, 도구 없음
    4. 보고자(Reporter) — 온콜이 읽을 형식으로 정리. 작은 모델, 정해진 템플릿
    app/agent/pipeline.py — 역할 분리와 예산 배분
    async def handle_incident(inc: Incident) -> Report:
    budget = Budget(tokens=120_000, seconds=120)

    # 1) 분류 — 조사할 가치가 있는지 먼저 판단한다(비용 방어선)
    tri = await triage(inc, model="small", budget=budget.slice(0.05))
    if tri.action == "skip":
        return Report.minimal(inc, reason=tri.reason)   # 과거 동일 사건 링크만 첨부

    # 2) 조사 — 서비스가 여러 개일 때만 팬아웃. 아니면 단일 에이전트
    targets = inc.affected_services[:4]                  # 워커 수 상한
    if len(targets) > 1:
        subs = await asyncio.gather(*[
            investigate_service(inc, s, model="large",
                                budget=budget.slice(0.60 / len(targets)))
            for s in targets
        ], return_exceptions=True)
        # 부분 실패는 버리지 말고 기록한다 — "조사 못 한 영역"도 정보다
        findings = [s for s in subs if not isinstance(s, Exception)]
        failed  = [t for t, s in zip(targets, subs) if isinstance(s, Exception)]
    else:
        findings, failed = [await investigate(inc, budget=budget.slice(0.60))], []

    # 3) 종합 — 원문이 아니라 요약만 올린다(컨텍스트 폭주 방지)
    merged = await synthesize([f.digest() for f in findings],
                             model="large", budget=budget.slice(0.20))

    # 4) 검증 — 도구 없이 '근거가 결론을 지지하는가'만 본다
    verdict = await critic(merged, model="medium", budget=budget.slice(0.10))
    if verdict.status == "unsupported":
        merged.confidence = "low"
        merged.warnings.append(verdict.reason)

    # 5) 보고 — 형식만 맞추는 일이라 작은 모델로 충분하다
    return await report(merged, failed_targets=failed,
                        model="small", budget=budget.rest())
    검증자 프롬프트 — 동조를 막는 문장이 핵심
    당신은 장애 조사 결과를 검토하는 검증자입니다. 새로운 조사는 하지 마십시오.

출력: {"status": "supported|partial|unsupported", "reason": "...", "missing": [...]}
    도입 순서

    네 역할을 한 번에 만들지 마세요. 분류기 → 보고자 → 검증자 → 병렬 조사 순서를 권합니다. 분류기는 비용을 즉시 줄이고, 보고자는 사람의 만족도를 즉시 올립니다. 병렬 조사는 가장 복잡하고 효과는 가장 늦게 나타납니다.

    CHAPTER 04

    모델 라우팅 — 모든 일에 큰 모델을 쓰지 않기

    비용의 대부분은 "작은 모델로 충분한 일에 큰 모델을 쓴 것"에서 나옵니다. 라우팅은 가장 효과가 확실한 최적화입니다.

    작업별 난이도 분류

    작업필요 능력권장 모델 급
    알림 분류·중복 판정패턴 인식소형(3~8B) 또는 임베딩+규칙
    로그 요약·에러 패턴 추출요약소형~중형(8~14B)
    도구 호출 계획, 다단계 추론추론·도구 사용대형(27B 이상 또는 상용 API)
    근거-결론 검증비판적 판단중형~대형
    보고서 형식 정리형식 변환소형
    고객 대면 문구 작성표현력중형 이상(검토 필수)

    세 가지 라우팅 방식

    • 정적 라우팅 — 작업 종류로 모델을 고정합니다. 가장 단순하고 예측 가능해 여기서 시작하는 것이 맞습니다.
    • 캐스케이드 — 작은 모델이 먼저 시도하고, 확신도가 낮거나 스키마 검증에 실패하면 큰 모델로 승급합니다. 평균 비용은 줄지만 최악 지연은 늘어납니다. 사용자가 기다리는 경로에는 주의해서 적용하세요.
    • 분류기 라우팅 — 작은 모델이 난이도를 먼저 판정해 경로를 정합니다. 유연하지만 분류 오류가 전체 품질을 좌우합니다.
    app/agent/router.py — 정적 + 캐스케이드 조합
    ROUTES = {
    "triage":   ModelSpec("local/qwen3-8b",  max_tokens=512),
    "summarize":ModelSpec("local/qwen3-8b",  max_tokens=1024),
    "investigate":ModelSpec("local/qwen3-27b", max_tokens=4096, tools=True),
    "critic":   ModelSpec("local/qwen3-27b", max_tokens=1024),
    "report":   ModelSpec("local/qwen3-8b",  max_tokens=1024),
}
ESCALATION = {"local/qwen3-8b": "local/qwen3-27b",
              "local/qwen3-27b": "api/frontier"}      # 최후 수단

async def call(task: str, messages, schema=None, allow_escalate=True):
    spec = ROUTES[task]
    out = await llm(spec, messages, schema=schema)

    # 승급 조건은 '느낌'이 아니라 검증 가능한 신호여야 한다
    needs_up = (out.schema_error or out.confidence == "low"
                or out.finish_reason == "length")
    if needs_up and allow_escalate and spec.name in ESCALATION:
        metrics.escalations.labels(task).inc()
        return await llm(ModelSpec(ESCALATION[spec.name]), messages, schema=schema)
    return out
    승급률을 지표로 보세요

    캐스케이드의 건강 지표는 승급률입니다. 30%를 넘으면 작은 모델이 그 작업에 부적합하다는 뜻이므로 아예 큰 모델로 고정하는 편이 총비용이 낮습니다(작은 모델 호출이 낭비되므로). 5% 미만이면 더 작은 모델로 내려볼 여지가 있습니다.

    라우팅 비용 시뮬레이터

    모든 작업을 대형 모델로 처리할 때와, 라우팅했을 때의 차이를 봅니다. 상대 비용 단위는 대형 모델 1.0 기준입니다.

    –
    월 비용(전부 대형, 상대값)
    –
    월 비용(라우팅 적용)
    –
    절감률

    상대값이라 통화 단위가 없습니다. 실제 계산에는 2편의 비용 계산기에 이 절감률을 곱해 쓰세요.

    프리픽스 캐싱 — 라우팅만큼 중요한 절약

    에이전트 루프는 매 호출마다 같은 시스템 프롬프트와 같은 도구 정의를 다시 보냅니다. 서빙 엔진이 이 공통 앞부분(prefix)의 계산을 재사용하면 비용과 지연이 크게 줄어듭니다. 이를 살리려면 프롬프트 구성에 규칙이 필요합니다.

    • 변하지 않는 것(시스템 프롬프트, 도구 정의, 조직 상수)을 맨 앞에 두고 절대 순서를 바꾸지 않습니다.
    • 타임스탬프·사건 ID처럼 매번 바뀌는 값을 앞부분에 넣지 마세요. 캐시가 전부 무효화됩니다.
    • 도구 목록을 사건마다 동적으로 재정렬하지 마세요. 같은 순서를 유지합니다.
    CHAPTER 05

    로컬 LLM 서빙 — 엔진 선택과 운영

    고객 데이터를 외부로 보낼 수 없는 환경에서는 선택이 아니라 전제입니다. 다행히 2026년의 선택지는 충분히 성숙했습니다.

    엔진 비교

    엔진강점약점적합
    vLLM생태계·모델 지원 폭이 가장 넓고 배포 사례가 많음. 하드웨어 종류도 가장 다양공유 프리픽스가 많은 워크로드에서는 SGLang에 밀릴 수 있음기본 선택. 모델을 자주 바꾸거나 NVIDIA 외 하드웨어도 쓰는 경우
    SGLangRadixAttention 프리픽스 캐시가 기본. 구조화 출력·함수 호출이 설계에 내장지원 모델 범위와 기여자 수가 vLLM보다 작음에이전트 루프·RAG처럼 앞부분이 반복되는 워크로드
    Ollama설치와 실행이 가장 간단동시 요청 처리량이 약함개발·실험. 프로덕션 조사 워커에는 부적합
    TensorRT-LLMNVIDIA 하드웨어에서 최고 성능컴파일·튜닝에 시간이 들고 유연성이 낮음모델이 고정되고 처리량이 절대적일 때

    참고로 Hugging Face의 TGI는 유지보수 모드로 들어갔고, 공식 권장도 vLLM 또는 SGLang입니다. 기존에 TGI를 쓰고 있다면 이전 계획을 세우는 것이 좋습니다.

    에이전트 워크로드의 특성

    운영 에이전트는 같은 시스템 프롬프트 + 같은 도구 정의를 매 호출 반복합니다. 이 형태는 프리픽스 캐시의 이득이 가장 큰 패턴입니다. 벤치마크에 따라 SGLang이 공유 컨텍스트 워크로드에서 vLLM 대비 상당한 처리량 우위를 보인다는 보고가 있으므로, 에이전트 전용 서버라면 두 엔진을 실제 프롬프트로 직접 비교해볼 가치가 있습니다. (vLLM도 프리픽스 캐싱을 지원하므로 옵션을 켜고 비교해야 공정합니다.)

    서빙 실행 예시 — 도구 호출을 켜는 것이 핵심
    # vLLM: 에이전트용으로 띄울 때 빠뜨리면 안 되는 옵션들
vllm serve Qwen/Qwen3-27B-Instruct \
  --port 8000 \
  --enable-auto-tool-choice \            # 도구 호출 활성화
  --tool-call-parser hermes \            # 모델에 맞는 파서 지정
  --max-model-len 32768 \                # 컨텍스트: KV 캐시를 가장 많이 먹는 값
  --gpu-memory-utilization 0.90 \
  --enable-prefix-caching                # 에이전트 루프에 필수

# SGLang: 프리픽스 캐시가 기본이고 구조화 출력이 강하다
python -m sglang.launch_server \
  --model-path Qwen/Qwen3-27B-Instruct \
  --port 30000 \
  --mem-fraction-static 0.85 \
  --context-length 32768 \
  --tool-call-parser qwen

    모델 선택 기준

    • 도구 호출을 제대로 하는가 — 운영 에이전트에서는 이것이 지식량보다 중요합니다. 벤치마크 점수보다 실제 도구 호출 성공률을 직접 재세요.
    • 구조화 출력이 안정적인가 — JSON 스키마를 반복해서 지키는지. 서빙 엔진의 제약 디코딩(constrained decoding)을 함께 켜면 크게 개선됩니다.
    • 컨텍스트 길이 — 운영 조사에서는 32K면 대체로 충분합니다. 컨텍스트를 늘리는 것보다 도구 결과를 요약하는 편이 정확도와 비용 모두에 유리합니다.
    • 라이선스 — 고객사에 제공하는 서비스에 쓰려면 상업적 이용 조건을 반드시 확인하세요.
    단일 장비 환경의 현실

    워크스테이션급 장비 한 대(통합 메모리 대용량 구성 포함)로 운영 에이전트를 돌리는 구성은 충분히 현실적입니다. 다만 데이터센터 GPU 대비 메모리 대역폭이 낮아 토큰 생성 속도에서 차이가 납니다. 그래서 단일 장비에서는 "큰 모델 하나"보다 중형 모델 + 라우팅 + 프리픽스 캐시 조합이 체감 성능이 좋습니다. 조사 1건이 90초를 넘기기 시작하면 모델을 키우지 말고 호출 수와 출력 길이부터 줄이세요.

    CHAPTER 06

    메모리 산정 — 우리 장비로 돌아갈까

    "모델 크기 × 2바이트"만 계산하고 띄웠다가 동시 요청에서 터지는 일이 흔합니다. KV 캐시를 함께 계산해야 합니다.

    계산식

    필요 메모리는 크게 세 덩어리입니다.

    • 가중치 = 파라미터 수 × 파라미터당 바이트 (FP16은 2, FP8/INT8은 1, INT4는 0.5)
    • KV 캐시 = 토큰당 KV 바이트 × 컨텍스트 길이 × 동시 요청 수
      토큰당 KV 바이트 = 2(K와 V) × 레이어 수 × KV 차원 × 바이트. GQA를 쓰는 모델은 KV 차원이 작아 훨씬 유리합니다.
    • 기타 = 활성값·CUDA 그래프·단편화 등으로 1~3GB 정도를 여유로 둡니다

    VRAM 산정기

    일반적인 GQA 모델 기준 근사치입니다. 실제 값은 모델 구조에 따라 달라지므로 여유를 두고 판단하세요.

    가중치 양자화

    –
    가중치
    –
    KV 캐시
    –
    합계(여유 포함)

    메모리가 모자랄 때의 순서

    1. 컨텍스트 길이를 줄인다 — 128K를 32K로 줄이면 KV 캐시가 4분의 1이 됩니다. 대부분의 운영 조사에는 32K로 충분합니다.
    2. KV 캐시를 양자화한다 — KV를 FP8로 두면 캐시 사용량이 절반이 됩니다. 품질 영향은 보통 작습니다.
    3. 가중치를 양자화한다 — INT8은 품질 손실이 대체로 작고, INT4는 작업에 따라 도구 호출 정확도가 떨어질 수 있으니 반드시 평가로 확인하세요.
    4. 모델을 한 단계 줄인다 — 27B에서 8B로 내리고 라우팅으로 어려운 작업만 외부/상위 모델에 보냅니다.
    5. 동시성을 제한한다 — 큐를 두고 동시 요청 수를 고정하는 편이, 메모리 부족으로 전체가 죽는 것보다 낫습니다.
    운영 팁

    서빙 서버도 관측 대상입니다. 대기 큐 길이, 프리픽스 캐시 적중률, 토큰 생성 속도, 요청 거절 수를 대시보드에 올리세요. 특히 캐시 적중률이 갑자기 떨어지면 누군가 프롬프트 앞부분에 가변 값을 넣었다는 신호입니다.

    CHAPTER 07

    컨텍스트 엔지니어링 심화

    긴 컨텍스트를 쓸 수 있다는 것과 써야 한다는 것은 다릅니다. 넣을수록 정확도가 떨어지는 구간이 존재합니다.

    컨텍스트를 늘렸는데 나빠지는 이유

    • 중간 정보 소실 — 긴 입력에서는 가운데 위치한 정보가 덜 반영되는 경향이 관찰됩니다. 중요한 근거는 앞이나 뒤에 배치하세요.
    • 주의 분산 — 관련 없는 로그가 섞이면 모델이 엉뚱한 단서를 붙잡습니다. 필터링이 요약보다 먼저입니다.
    • 비용·지연 — 입력 토큰은 거의 선형으로 비용과 첫 토큰 지연에 반영됩니다.

    도구 결과 다이제스트 설계

    2편에서 도구는 결과를 요약해 반환한다고 했습니다. 구체적으로 어떤 형태여야 하는지가 여기서 중요해집니다.

    app/agent/digest.py — 로그를 모델에 넣기 전에 접는다
    def digest_logs(lines: list[str], max_groups: int = 8) -> dict:
    # 1) 가변 부분을 지워 패턴화한다(타임스탬프·ID·숫자)
    patterns = defaultdict(lambda: {"count": 0, "sample": None, "first": None})
    for l in lines:
        key = re.sub(r"\d+", "#", re.sub(r"[0-9a-f]{8,}", "<id>", l))[:160]
        p = patterns[key]
        p["count"] += 1
        p["sample"] = p["sample"] or l          # 원문 1줄은 보존(근거용)
        p["first"] = p["first"] or extract_ts(l)

    # 2) 빈도순 상위 N개만. 나머지는 개수만 알린다
    top = sorted(patterns.items(), key=lambda kv: -kv[1]["count"])[:max_groups]
    return {
        "total_lines": len(lines),
        "groups": [{"pattern": k, "count": v["count"],
                    "first_seen": v["first"], "sample": v["sample"]} for k, v in top],
        "other_groups": max(0, len(patterns) - max_groups),
    }

    로그 3만 줄이 이 함수를 지나면 보통 20~40줄로 줄어듭니다. 중요한 것은 정보 손실 방식이 예측 가능하다는 점입니다. 모델이 "샘플 원문"으로 근거를 인용할 수 있고, "other_groups"로 놓친 영역이 있다는 것도 압니다.

    계층내용수명
    작업 메모리현재 사건의 도구 결과와 가설조사 종료 시 폐기

    CHAPTER 08

    RAG 고도화 — 런북과 과거 사건 제대로 쓰기

    2편에서 붙인 단순 벡터 검색은 금방 한계에 부딪힙니다. 운영 문서에는 고유명사와 오류 코드가 많기 때문입니다.

    하이브리드 검색이 필요한 이유

    벡터 검색은 의미가 비슷한 문서를 잘 찾지만, CrashLoopBackOff나 ORA-01555 같은 정확히 일치해야 하는 토큰에 약합니다. 반대로 키워드 검색(BM25)은 이런 토큰에 강하고 의역에 약합니다. 둘을 합치고 순위를 재조정하는 것이 표준 구성입니다.

    app/rag/search.py — 키워드 + 벡터 + 리랭킹
    async def search_knowledge(query: str, tenant: str, k: int = 5) -> list[Doc]:
    # 1) 두 경로로 각각 넉넉히 뽑는다
    kw  = await db.bm25_search(query, tenant, limit=20)
    vec = await db.vector_search(embed(query), tenant, limit=20)

    # 2) RRF(Reciprocal Rank Fusion): 점수 스케일이 달라도 합칠 수 있다
    fused = defaultdict(float)
    for rank, d in enumerate(kw):  fused[d.id] += 1 / (60 + rank)
    for rank, d in enumerate(vec): fused[d.id] += 1 / (60 + rank)

    # 3) 신선도 보정: 6개월 지난 런북은 감점(운영 문서는 빨리 낡는다)
    for doc_id in fused:
        age_days = docs[doc_id].age_days
        fused[doc_id] *= 0.7 if age_days > 180 else 1.0

    top = sorted(fused, key=fused.get, reverse=True)[:12]

    # 4) 리랭커로 질의-문서 관련도를 다시 판정해 상위 k개만 남긴다
    return await reranker.top_k(query, [docs[i] for i in top], k=k)

    운영 문서 청킹 규칙

    • 절차는 자르지 않는다 — 런북의 단계 목록을 중간에서 끊으면 모델이 절반짜리 절차를 제안합니다. 제목 단위로 자르세요.
    • 메타데이터를 붙인다 — 서비스명, 테넌트, 최종 수정일, 작성자. 검색 필터와 신선도 판정에 씁니다.
    • 과거 사건은 구조화해서 — 증상·원인·조치·재발방지 네 필드로 저장하면 검색 품질이 크게 올라갑니다. 자유 서술 포스트모템 전체를 넣는 것보다 낫습니다.
    • 출처를 반드시 반환 — 문서 제목과 링크가 없으면 담당자가 검증할 수 없고, 결국 신뢰하지 않게 됩니다.
    가장 효과 큰 한 가지

    새 사건이 열릴 때 유사 과거 사건 3건을 자동으로 붙이는 기능입니다. 구현은 며칠이면 되고, 반복 장애가 많은 환경에서는 에이전트 조사보다 먼저 답을 주는 경우가 많습니다. 증상 텍스트 + 서비스 + 알림 조합으로 검색하면 충분합니다.

    CHAPTER 09

    평가 심화 — 좋아졌다는 것을 증명하기

    2편의 골든 데이터셋을 제대로 굴리는 방법입니다. 평가가 부실하면 모든 개선이 추측이 됩니다.

    LLM 심판(LLM-as-judge)을 신뢰할 수 있게 만드는 법

    • 판정 범위를 좁힌다 — "답변 품질을 1~10으로 매겨라"는 재현성이 낮습니다. "제시된 원인이 정답 원인과 같은 것을 가리키는가: 예/아니오"처럼 이진 판정이 훨씬 안정적입니다.
    • 루브릭을 준다 — 무엇이 같은 원인인지 기준을 예시로 제시합니다. "DB 커넥션 풀 고갈"과 "DB 연결 실패"를 같다고 볼지 미리 정하세요.
    • 위치 편향을 제거한다 — 두 답변을 비교할 때 순서를 바꿔 두 번 돌리고 결과가 뒤집히면 무승부로 처리합니다.
    • 심판을 검증한다 — 사람이 라벨링한 30건으로 심판의 정확도를 먼저 재세요. 심판이 80% 미만이면 그 심판의 결과로 모델을 비교하면 안 됩니다.
    • 심판 모델을 고정한다 — 심판 모델을 바꾸면 과거 점수와 비교할 수 없습니다. 버전을 기록하세요.

    평가 종류를 나눠서 본다

    구분측정 대상주기
    단위 평가도구 호출 인자가 정확한가, 스키마를 지키는가커밋마다(빠르고 결정적)
    회귀 평가골든 사건 30~50건의 원인 일치율·비용·단계 수PR마다
    온라인 평가실제 사건의 채택률, 피드백, 승급률주간
    안전 평가프롬프트 인젝션·권한 우회 시도에 대한 반응릴리스 전
    표본 수 감각

    골든 사건 30건에서 정확도가 60%에서 66%로 올랐다면, 그것은 2건 차이입니다. 우연일 가능성이 큽니다. 작은 데이터셋에서는 몇 %p 차이를 개선이라고 부르지 마세요. 의미 있는 판단을 하려면 케이스를 늘리거나, 같은 케이스를 여러 번 돌려 분산을 함께 보고해야 합니다.

    evals/judge.py — 위치 편향 제거와 이진 판정
    async def judge_cause(predicted: str, actual: str) -> bool:
    prompt = f"""두 원인 설명이 같은 근본 원인을 가리키는지 판정하십시오.

    [판정 기준]
    - 표현이 달라도 같은 구성요소의 같은 고장이면 '같음'
    - 상하 관계(증상 vs 원인)는 '다름'. 예: "5xx 증가"(증상) vs "커넥션 풀 고갈"(원인)
    - 확신이 서지 않으면 '다름'으로 판정

    A: {{a}}
    B: {{b}}
    출력: {{"same": true|false, "reason": "한 줄"}}"""

    # 순서를 바꿔 두 번 판정 — 일치할 때만 결과를 인정한다
    r1 = await judge_llm(prompt.format(a=predicted, b=actual))
    r2 = await judge_llm(prompt.format(a=actual, b=predicted))
    return r1["same"] and r2["same"]

    파인튜닝 — 언제, 무엇을

    대부분의 팀에서 파인튜닝은 마지막에서 두 번째 선택지입니다. 순서를 건너뛰면 비싸고 되돌리기 어렵습니다.

    시도 순서

    1. 프롬프트·출력 스키마 개선 — 비용 0, 즉시 되돌릴 수 있음. 대부분의 문제가 여기서 해결됩니다
    2. 도구·컨텍스트 보강 — 틀린 답의 상당수는 모델 능력이 아니라 정보 부족 때문입니다
    3. RAG 개선 — 조직 고유 지식 문제는 학습이 아니라 검색으로 푸는 것이 정석입니다
    4. 모델 교체·라우팅 — 더 나은 공개 모델이 자주 나옵니다. 교체 비용이 학습보다 쌉니다
    5. 파인튜닝 — 위 네 가지를 다 했는데도 특정 작업이 반복적으로 실패할 때

    파인튜닝이 실제로 유효한 경우

    목적방법기대 효과
    출력 형식·문체 고정소량 SFT(LoRA)프롬프트 길이 감소, 형식 오류 감소
    사내 용어·서비스명 이해LoRA + RAG 병행고유명사 처리 개선(지식 자체는 RAG가 담당)
    큰 모델의 판단을 작은 모델로 이전증류(distillation)비용·지연 대폭 감소. 분류·요약 작업에 특히 효과적
    새로운 사실 주입—권장하지 않음. 사실은 RAG로. 학습으로 넣으면 갱신이 불가능해집니다

    CHAPTER 11

    신뢰성 — 확률적 시스템을 예측 가능하게

    LLM은 비결정적입니다. 그 위에 운영 시스템을 올리려면 결정적인 껍데기가 필요합니다.

    다섯 가지 껍데기

    • 구조화 출력 강제 — 서빙 엔진의 제약 디코딩이나 스키마 강제 기능을 켜서 애초에 형식 오류가 나올 수 없게 합니다. 파싱 실패 후 재시도보다 훨씬 쌉니다.
    • 도구 호출 검증 — 모델이 준 인자를 그대로 실행하지 말고 타입·범위·권한을 코드에서 검사합니다. 실패 시 사람이 읽을 수 있는 오류 메시지를 모델에 돌려주면 스스로 고칩니다.
    • 단계·시간·토큰 예산 — 2편에서 만든 예산을 단계별로 쪼개 배분합니다. 어느 한 단계가 전체를 잡아먹지 못하게 합니다.
    • 재시도 정책 — 네트워크·레이트리밋은 지수 백오프로 재시도하되, 모델의 논리 오류는 재시도하지 않습니다(같은 결과가 나옵니다). 대신 승급하거나 사람에게 넘깁니다.
    • 재현성 — temperature를 낮추고 seed를 기록하며, 프롬프트·모델·도구 정의 버전을 사건 기록에 남깁니다. 사고 조사 때 "그때 무엇이 돌았는지"를 복원할 수 있어야 합니다.
    app/agent/guard.py — 도구 인자 검증과 자기 수정 루프
    async def safe_tool_call(call, tenant) -> dict:
    spec = TOOLS[call.name]
    try:
        args = spec.schema.validate(call.args)          # 타입·필수값·범위
    except ValidationError as e:
        # 모델이 고칠 수 있도록 구체적으로 알려준다
        return {"error": f"인자 오류: {e.message}. 기대 형식: {spec.schema.hint()}"}

    if not permissions.allows(tenant, spec, args):
        return {"error": "권한 없음. 다른 방법으로 확인하십시오."}   # 거부도 정보다

    try:
        return await asyncio.wait_for(spec.fn(**args), timeout=spec.timeout)
    except asyncio.TimeoutError:
        return {"error": f"{spec.timeout}초 초과. 조회 범위를 줄여 다시 시도하십시오."}
    거부와 실패도 컨텍스트다

    도구 호출이 막혔을 때 예외를 던져 루프를 죽이지 마세요. 에이전트에게 왜 막혔는지 알려주면 다른 경로로 조사를 이어갑니다. 실제로 이 한 가지 변경이 조사 완료율을 크게 올리는 경우가 많습니다.

    정리 — 조합 예시와 점검

    지금까지의 선택지를 두 가지 현실적인 구성으로 묶었습니다.

    구성 A · 온프렘 단일 장비

    • 서빙: vLLM 또는 SGLang 한 대, 중형 모델(8B급)과 대형 모델(27B급) 2종을 메모리에 맞춰 운용
    • 라우팅: 분류·요약·보고는 8B, 조사·검증은 27B 고정. 승급 없음(외부 전송 불가 환경)
    • 컨텍스트: 32K, 프리픽스 캐시 필수, 도구 결과는 다이제스트로 압축
    • 동시성: 큐로 4~8 제한. 조사 1건 90초 목표
    • 평가: 골든 사건 30건 + 주간 온라인 지표

    구성 B · 하이브리드

    • 고객 데이터가 포함된 작업은 로컬 모델, 익명화 가능한 작업은 상용 API
    • 게이트웨이에서 마스킹·라우팅·비용 집계를 일괄 처리(테넌트별 태그 필수)
    • 캐스케이드 승급을 허용하되 승급률과 외부 전송량을 매일 감시
    • 계약·규정상 금지된 테넌트는 설정이 아니라 코드에서 외부 경로를 차단

    1편은 무엇을 쌓을지, 2편은 어떻게 만들지, 3편은 어떻게 더 싸고 정확하게 만들지를 다뤘습니다. 세 편을 관통하는 원칙은 하나입니다. 확률적인 부분은 작게 두고, 그 주변을 결정적으로 감싼다. 데이터 규율, 권한 경계, 예산, 평가, 되돌리기. 이것들이 단단하면 모델과 프레임워크는 언제든 교체할 수 있습니다.
