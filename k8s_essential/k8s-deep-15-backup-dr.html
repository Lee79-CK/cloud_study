스냅샷·백업·DR

“백업은 있습니다”와 “복구할 수 있습니다”는 다른 말입니다. 스냅샷은 원본과 같은 스토리지·같은 리전·같은 계정에 있어 원본과 함께 사라질 수 있고, 백업은 데이터만 있고 그 데이터를 쓰던 Kubernetes 리소스가 없을 수 있으며, 둘 다 있어도 다른 클러스터의 StorageClass·Ingress·IAM이 달라 복원이 멈출 수 있습니다. 이 편은 VolumeSnapshot의 원리와 일관성, Velero와 벤더 백업 서비스, 크로스 리전·크로스 클러스터 복구, RPO·RTO 설계를 다루고, EKS의 네임스페이스를 kubeadm 클러스터로 실제로 옮겨 봅니다.

이 백업 방식으로 이 재해에서 살아남나?

보호 방식과 재해 종류를 고르고 숫자를 넣으면, 복구할 수 있는지, 잃는 데이터의 최대 시간(RPO), 복구에 걸리는 시간(RTO)의 단계별 내역이 나옵니다. 숫자는 고객 환경 값으로 바꿔 쓰세요.

읽는 법과 목표

쉬운 말로 스냅샷은 같은 집 서랍에 넣어 둔 사진첩입니다. 실수로 지운 사진은 금방 찾지만, 집에 불이 나면 함께 탑니다. 백업은 은행 금고에 맡긴 사본이고, DR(재해 복구)은 “집이 통째로 없어지면 어느 집에서, 몇 시간 안에, 어떤 순서로 살림을 다시 차릴지”까지 정한 이사 계획입니다. RPO는 “최대 몇 시간 치 기억을 잃어도 되나”, RTO는 “몇 시간 안에 다시 살 수 있어야 하나”입니다.

이 편을 마치면 할 수 있는 것

  • VolumeSnapshotClass·VolumeSnapshot·VolumeSnapshotContent로 스냅샷을 만들고 복원하며, 스냅샷이 어디에 저장되는지(토폴로지) 설명할 수 있습니다.
  • 크래시 일관성과 애플리케이션 일관성을 구분하고, 훅·그룹 스냅샷·DB 네이티브 백업으로 필요한 일관성을 확보할 수 있습니다.
  • Velero의 구조(서버·node-agent·백업 저장소)와 볼륨 보호 방식(CSI 스냅샷·데이터 무버·fs-backup)을 고를 수 있습니다.
  • AWS Backup for EKS·Azure Backup for AKS·Backup for GKE·OpenShift OADP를 비교할 수 있습니다.
  • RPO·RTO에서 출발해 DR 전략을 설계하고, 복구 리허설로 실제 RTO를 측정할 수 있습니다.

무엇을 지키나: 백업의 세 층

층무엇주요 수단빠지면
클러스터 상태etcd 전체(모든 리소스)etcd 스냅샷(2·3편), 매니지드는 벤더 책임컨트롤 플레인 재구축 불가(셀프 관리형). 단, 같은 클러스터를 되살리는 용도이지 다른 클러스터로 옮기는 용도는 아님
애플리케이션 리소스네임스페이스의 Deployment·Service·ConfigMap·Secret·PVC·CR 등GitOps 저장소(원본), Velero·벤더 백업(실제 상태)데이터는 있어도 앱을 다시 올릴 정의가 없음. 수동으로 바꾼 설정이 사라짐
영구 데이터PV 안의 데이터스냅샷, 스냅샷 데이터 이동, 파일 백업, DB 네이티브 백업앱은 뜨지만 빈 데이터
시니어 포인트: GitOps는 백업이 아니고, 백업은 GitOps가 아니다 GitOps 저장소는 “원래 이래야 한다”를 담고, 백업은 “실제로 이랬다”를 담습니다. 운영 중 사람이 바꾼 설정, 오퍼레이터가 만든 리소스, 자동 생성된 Secret(인증서·토큰)은 저장소에 없습니다. 반대로 백업만 있으면 무엇이 의도된 상태였는지 알 수 없습니다. DR 계획에는 둘 다 필요하고, 복원 순서(저장소로 기반을 깔고 → 백업으로 데이터와 실제 상태를 올림)를 정해 두어야 합니다.

VolumeSnapshot과 스냅샷 토폴로지

세 객체 (11편의 PV·PVC·StorageClass와 같은 구조)

객체범위PV 쪽 대응역할
VolumeSnapshotClass클러스터StorageClass드라이버, deletionPolicy(Delete·Retain), 파라미터(예: 증분·태그)
VolumeSnapshot네임스페이스PVC“이 PVC의 스냅샷을 찍어 주세요”라는 요청
VolumeSnapshotContent클러스터PV실제 백엔드 스냅샷(snapshotHandle)을 가리킴
  • 설치. 스냅샷 CRD와 snapshot-controller는 CSI 드라이버와 별도로 설치합니다(12편). EKS는 snapshot-controller 애드온, AKS·GKE는 기본 제공, OpenShift는 플랫폼이 제공합니다.
  • 복원. 새 PVC의 dataSource에 VolumeSnapshot을 지정하면 provisioner가 스냅샷에서 디스크를 만듭니다. 원본보다 크게 만들 수는 있지만 작게는 안 됩니다.
  • 다른 클러스터로 가져오기. 백엔드 스냅샷 ID를 알면, 대상 클러스터에 snapshotHandle을 적은 VolumeSnapshotContent를 직접 만들어(미리 프로비저닝된 스냅샷) 복원할 수 있습니다. 같은 클라우드·같은 리전·접근 권한이 전제입니다.
  • 그룹 스냅샷. 여러 PVC를 같은 시점에 찍는 VolumeGroupSnapshot은 업스트림에서 베타 단계이며, 드라이버 지원이 필요합니다. 데이터와 로그가 다른 볼륨에 있는 DB에 의미가 큽니다(3장). Velero 1.17이 이를 지원합니다.

일관성: 크래시 vs 애플리케이션

쉬운 말로 스냅샷은 전원 플러그를 뽑은 순간의 디스크 사진입니다(크래시 일관성). 데이터베이스는 대부분 이 상태에서도 스스로 복구하지만, 메모리에만 있던 내용은 없고, 디스크가 여러 개면 각 사진의 찍힌 순간이 미세하게 달라 맞지 않을 수 있습니다. 애플리케이션 일관성은 “잠깐 멈추고 정리한 뒤 찍은 사진”입니다.
수준방법장점주의
크래시 일관그냥 스냅샷앱 수정 없음, 빠름DB가 복구 로그를 재생해야 함. 볼륨이 여럿이면 시점 불일치
다중 볼륨 크래시 일관VolumeGroupSnapshot데이터·로그 볼륨이 같은 시점드라이버 지원 필요(베타)
파일 시스템 일관백업 전 fsfreeze 또는 sync 훅, 후에 해제디스크 버퍼 정리freeze 동안 쓰기 멈춤. 해제 실패 시 장애
애플리케이션 일관DB 기능으로 체크포인트·백업 모드 진입 후 스냅샷(Velero 사전·사후 훅)복원 직후 바로 사용DB별 명령, 훅 실패 처리
DB 네이티브 백업pgBackRest·Barman(CloudNativePG)·mysqldump·mongodump, WAL·binlog 아카이브특정 시점 복구(PITR), 버전·플랫폼 이동DB마다 다른 도구, 복원 시간(16편)
Velero 훅으로 백업 전후 명령 실행 (Pod 어노테이션)
metadata:
  annotations:
    pre.hook.backup.velero.io/container: app
    pre.hook.backup.velero.io/command: '["/bin/sh","-c","psql -U postgres -c CHECKPOINT; sync"]'
    pre.hook.backup.velero.io/on-error: Fail                # 훅 실패면 백업 실패로
    post.hook.backup.velero.io/command: '["/bin/sh","-c","echo backup-done"]'
# fsfreeze가 필요하면 볼륨을 마운트한 특권 사이드카에서 fsfreeze -f / -u 를 실행하는 방식을 씀
시니어 포인트: 데이터베이스는 데이터베이스의 방식으로 운영 DB의 1차 보호는 DB 네이티브 백업(연속 WAL 아카이브 + 정기 베이스 백업)이고, 볼륨 스냅샷과 Velero는 “클러스터와 함께 빠르게 되돌리는 2차 수단”으로 두는 것이 안전합니다. 네이티브 백업은 특정 시점 복구와 다른 버전·다른 플랫폼으로의 복원을 지원하지만, 스냅샷은 같은 스토리지 계열로만 돌아갈 수 있습니다. 16편에서 CloudNativePG로 이 조합을 구성합니다.

Velero 해부

구성 요소

  • velero 서버(Deployment): Backup·Restore·Schedule CR을 처리하고 리소스를 JSON으로 모아 객체 저장소에 올립니다.
  • node-agent(DaemonSet): 볼륨 데이터를 옮길 때만 필요합니다(fs-backup, 데이터 무버). 1.17부터는 실제 전송을 Pod 단위 마이크로서비스로 분리해 Windows 노드까지 지원합니다.
  • BackupStorageLocation(BSL): 리소스와 데이터 저장소(S3·Blob·GCS·MinIO 등). VolumeSnapshotLocation(VSL): 클라우드 네이티브 스냅샷 위치(플러그인 방식일 때).
  • 플러그인: 클라우드별 객체 저장소·스냅샷 플러그인(AWS·Azure·GCP). CSI 지원은 1.14부터 Velero 본체에 통합되었습니다.

볼륨 데이터를 지키는 네 가지 방법

방법어떻게데이터가 남는 곳다른 리전·클러스터 복원쓸 때
CSI 스냅샷VolumeSnapshot을 만들고 그 참조만 백업스토리지 백엔드(원본과 같은 곳)같은 리전·계정·스토리지만빠른 롤백, 같은 클러스터 복구
CSI 스냅샷 데이터 이동스냅샷에서 임시 볼륨을 만들어 node-agent가 Kopia로 객체 저장소에 업로드객체 저장소(증분·중복 제거)어디로든(스토리지 종류가 달라도)DR, 클라우드 간·온프렘 이전(실습)
fs-backup(Kopia)실행 중인 Pod의 볼륨 파일을 직접 읽어 업로드객체 저장소어디로든스냅샷이 없는 스토리지(NFS, hostPath, 일부 온프렘)
클라우드 네이티브 스냅샷(플러그인)클라우드 API로 직접 스냅샷클라우드 스냅샷같은 클라우드, 복사 필요CSI 이전 방식 호환
  • restic 퇴장. 1.17에서 restic 경로의 새 백업이 제거되었고, 옛 restic 백업의 복원은 1.19까지 지원됩니다. restic 백업만 있는 고객은 1.19 전에 Kopia로 새 백업을 쌓아 두어야 합니다.
  • 1.18. 동시 백업, 데이터 무버의 캐시 볼륨 지정(노드 임시 디스크 고갈 방지) 등이 들어왔습니다.
  • 어떤 볼륨을 어떻게. 볼륨 정책(ConfigMap)으로 StorageClass·크기·볼륨 종류별로 스냅샷·fs-backup·제외를 정할 수 있습니다. 기본 동작을 모르고 쓰면 “백업은 완료인데 데이터가 없는” 사고가 납니다(10장).
  • 복원 시 변환. StorageClass 매핑 ConfigMap과 리소스 수정자(resource modifiers, JSON 패치)로 대상 클러스터에 맞게 바꿉니다. 실습의 핵심입니다.
  • 보안. 백업에는 Secret이 들어갑니다. 버킷 접근 권한이 곧 비밀 접근 권한입니다. 버킷 암호화, 접근 제한, 변경 불가(Object Lock) 설정을 함께 설계하세요.

벤더 백업 서비스 비교

RPO·RTO 설계와 DR 전략

RPO는 백업 주기와 복제 지연이, RTO는 “대상 환경 준비 + 리소스 복원 + 데이터 복원 + 앱 기동·검증 + 트래픽 전환”의 합이 정합니다. 맨 위 계산기가 이 합을 보여 줍니다. 대부분의 RTO 초과는 데이터 복원 처리량과 사람이 결정하는 시간(누가 DR을 선언하나)에서 생깁니다.

전략평소 상태RPO 경향RTO 경향비용Kubernetes 구현
백업·복원DR 리전에 백업만백업 주기(시간~일)시간 단위낮음Velero 데이터 무버·벤더 백업 교차 리전 복사, 복원 때 클러스터 생성
파일럿 라이트DR 클러스터 최소 구성 + 데이터 복제분~시간수십 분~시간중간대기 클러스터(노드 0~최소) + GitOps 동기화 + DB 복제
웜 스탠바이DR 클러스터가 작은 규모로 실행 중초~분분높음양쪽 클러스터 GitOps, DB 비동기 복제, DNS 전환
액티브-액티브두 리전이 함께 서비스거의 0(데이터 설계에 따라)거의 0가장 높음전역 LB(7편), 멀티 리전 DB, 멀티클러스터(10편)
함정: 재해 종류마다 답이 다르다 실수로 지운 네임스페이스는 같은 클러스터의 스냅샷으로 몇 분 안에 돌아오지만, 랜섬웨어나 버그로 데이터가 조용히 망가진 경우는 망가지기 전 시점의 백업이 남아 있어야 하고(보존 기간·변경 불가 보관), 계정 침해는 다른 계정에 복사본이 있어야 합니다. 요구 사항 문서에 “어떤 재해에 대한 RPO·RTO인가”를 반드시 적으세요.

kubectl config use-context lab-eks

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata: {name: snap-1}

kubectl -n shop-dr wait volumesnapshot/snap-1 --for=jsonpath='{.status.readyToUse}'=true --timeout=600s
SRCZ=$(kubectl get pv $(kubectl -n shop-dr get pvc data-db-0 -o jsonpath='{.spec.volumeName}') -o jsonpath='{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}')
OTHER=$(kubectl get nodes -o jsonpath='{.items[*].metadata.labels.topology\.kubernetes\.io/zone}' | tr ' ' '\n' | sort -u | grep -v "$SRCZ" | head -1)
echo "원본 존 $SRCZ → 복원 존 $OTHER"

apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: from-snap}
spec:
  storageClassName: gp3-wfc
  dataSource: {name: snap-1, kind: VolumeSnapshot, apiGroup: snapshot.storage.k8s.io}
  accessModes: ["ReadWriteOnce"]
  resources: {requests: {storage: 10Gi}}
---
apiVersion: v1
kind: Pod
metadata: {name: check}
spec:
  nodeSelector: {topology.kubernetes.io/zone: $OTHER}
  containers: [{name: c, image: busybox:1.36, command: ["sh","-c","head -2 /data/log; sleep 3600"], volumeMounts: [{name: d, mountPath: /data}]}]

과제

현장 사례

스냅샷만 있었는데 계정 침해로 함께 삭제됐다

원인. 볼륨 스냅샷을 매일 찍고 있었지만 같은 계정·같은 리전에만 있었습니다. 침해된 자격 증명으로 볼륨과 스냅샷이 함께 삭제됐습니다.

교훈. 백업의 최소 요건은 다른 장애 도메인(다른 계정·리전)과 변경 불가 보관입니다. AWS Backup 볼트 잠금, S3 Object Lock, 교차 계정 복사를 검토하세요.

DB가 복원은 됐는데 데이터가 맞지 않았다

원인. 데이터 볼륨과 WAL 볼륨을 따로 크래시 일관 스냅샷으로 찍어, 두 볼륨의 시점이 어긋났습니다.

교훈. 여러 볼륨에 걸친 DB는 그룹 스냅샷이나 DB 네이티브 백업으로 보호하세요(3장).

백업은 “Completed”인데 복원하니 볼륨이 비어 있다

원인. 볼륨 보호 방식을 정하지 않아, 스냅샷을 지원하지 않는 NFS 볼륨은 아무 방식으로도 백업되지 않았습니다. Velero는 리소스만 백업하고 성공으로 표시했습니다.

교훈. 백업 성공 상태가 아니라 백업 상세(볼륨 목록)와 복원 시험으로 확인하세요. 볼륨 정책으로 StorageClass별 방식을 명시합니다.

다른 클러스터로 복원하다 절반에서 멈췄다

원인. 대상 클러스터에 앱이 쓰는 CRD와 오퍼레이터가 없어 CR 복원이 실패했고, StorageClass 이름이 달라 PVC가 Pending이었습니다.

교훈. DR 대상 클러스터는 GitOps로 기반(오퍼레이터·CRD·StorageClass·네트워크)을 먼저 깔고, 백업은 앱과 데이터만 올리는 순서로 설계하세요.

Velero를 올렸더니 옛 백업을 복원할 수 없다

원인. 오랫동안 restic 경로로 백업했고, 복원 지원이 끝난 버전으로 올렸습니다. 보존 기간 안의 옛 백업이 사실상 쓸 수 없게 됐습니다.

교훈. 백업 도구 업그레이드는 복원 호환성을 확인하는 변경입니다. 새 형식 백업이 보존 기간만큼 쌓인 뒤에 옛 형식 지원이 끝나는 버전으로 올리세요.

목표 RTO 4시간, 첫 리허설 14시간

원인. 데이터 복원 처리량이 예상의 3분의 1이었고, 사설 레지스트리 접근 권한이 DR 리전에 없었으며, DNS 변경 권한자가 연락되지 않았습니다.

교훈. RTO는 기술보다 권한·연락망·결정 절차에서 늘어납니다. 리허설로만 발견됩니다.

백업 버킷 접근 권한이 사실상 모든 비밀에 대한 접근이었다

상황. 분석 팀이 비용 보고용으로 백업 버킷 읽기 권한을 받았는데, 그 안에 모든 네임스페이스의 Secret이 들어 있었습니다.

교훈. 백업 저장소는 가장 민감한 저장소로 취급하세요. 별도 계정, 최소 권한, 암호화, 접근 감사, 필요하면 Secret 제외와 외부 비밀 관리(19편)를 함께 설계합니다.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. 백업은 클러스터 상태(etcd)·애플리케이션 리소스·영구 데이터의 세 층이며, GitOps 저장소와 백업은 서로를 대신하지 못합니다.
  2. VolumeSnapshot은 PV·PVC·StorageClass와 같은 구조이고, 스냅샷은 원본과 같은 스토리지·리전·계정에 남으므로 그 자체로는 DR이 아닙니다.
  3. 크래시 일관 스냅샷으로 부족하면 훅·그룹 스냅샷·DB 네이티브 백업으로 애플리케이션 일관성을 확보합니다.
  4. Velero는 CSI 스냅샷·데이터 이동·fs-backup(Kopia)을 고를 수 있고(restic은 1.17에서 백업 제거), 벤더 서비스(AWS Backup for EKS, Azure Backup for AKS, Backup for GKE, OADP)는 같은 벤더 안의 복원에 강합니다.
  5. RPO·RTO는 재해 종류별로 정하고, 크로스 클러스터 복원은 StorageClass 매핑·리소스 수정자·기반 선설치로 풀며, 리허설로만 실제 RTO를 알 수 있습니다.

다음 편 · 16편 스테이트풀 워크로드 운영 종합 (Level 2 마지막)

StatefulSet의 볼륨 템플릿·순서 보장·v1.37의 Recreate 롤아웃 전략과 PVC 자동 삭제 정책, 데이터베이스 오퍼레이터(CloudNativePG, Strimzi, Redis 오퍼레이터)의 스토리지 요구와 벤더별 권장 구성, 미사용 PVC·스냅샷 수명 같은 스토리지 비용 관리, 그리고 Level 2 전체를 묶는 스토리지 트러블슈팅 플레이북을 다룹니다. CloudNativePG 클러스터를 두 벤더에 배포해 장애 조치 시간과 볼륨 동작을 비교합니다.
