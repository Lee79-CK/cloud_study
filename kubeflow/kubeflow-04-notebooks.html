이번 편에서 얻을 것

1편의 노선도에서 두 번째 정거장, 탐색과 실험입니다. 1편의 지은이 겪은 “제 노트북에서는 잘 돼요” 문제를, 모두가 같은 이미지와 같은 저장소 위에서 일하는 방식으로 바꿔 봅니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 노트북 하나를 만들 때 Notebook, StatefulSet, Pod, Service, VirtualService, PVC가 각각 어떤 역할로 생기는지 설명할 수 있습니다.
  • 만들기 화면의 각 항목이 어떤 YAML로 바뀌는지 알고, 이미지, 자원, 볼륨, GPU를 상황에 맞게 고를 수 있습니다.
  • 노트북을 멈추거나 다시 시작할 때 무엇이 남고 사라지는지 알고, 작업을 잃지 않는 습관을 들입니다.
  • PodDefault로 비밀 값을 안전하게 주입하고, 노트북에서 첫 모델을 학습해 결과를 PVC에 저장합니다.

1Kubeflow Notebooks의 구성

노트북 서버는 JupyterLab, VS Code(code-server), RStudio 같은 개발 환경을 Kubernetes Pod로 띄운 것입니다. 브라우저에서 접속하지만 실제 계산은 클러스터 안에서 일어나서, 내 PC가 아니라 클러스터의 CPU, 메모리, GPU, 저장소를 씁니다. Kubeflow Notebooks는 이 노트북 서버를 사용자가 직접 만들고 관리하게 해 주는 구성요소 묶음입니다.

구성요소하는 일
Jupyter Web App대시보드의 Notebooks 화면. 노트북 목록과 만들기 화면(spawner)을 제공하고, 제출하면 Notebook 리소스와 PVC를 만듭니다
Notebook ControllerNotebook 리소스를 보고 실제 StatefulSet, Service, VirtualService를 만들고 관리하는 Operator. 오래 쓰지 않는 노트북을 멈추는 기능(컬링)도 여기에 있습니다
Volumes Web App, PVC Viewer ControllerVolumes 화면. PVC를 만들고 지우며, 안의 파일을 브라우저로 둘러볼 수 있게 합니다
TensorBoards Web App, TensorBoard ControllerPVC나 오브젝트 스토리지의 학습 로그를 TensorBoard 서버로 띄웁니다
예제 노트북 이미지바로 쓸 수 있게 준비된 JupyterLab, VS Code, RStudio 이미지 모음
26.03.1에서 달라진 점

Kubeflow Notebooks v1.11은 예전의 kubeflow/kubeflow 저장소에서 kubeflow/notebooks 저장소로 분리된 뒤 나온 첫 릴리스이고, 이를 처음 포함한 배포판이 26.03.1입니다(26.03에는 v1.10이 들어 있었습니다). 웹 앱과 컨트롤러 이미지는 ghcr.io/kubeflow/notebooks/...로 옮겨 갔고, 예제 노트북 이미지는 계속 ghcr.io/kubeflow/kubeflow/notebook-servers/...에 있습니다. 사내 이미지 미러를 쓴다면 두 경로를 모두 챙겨야 합니다.

2노트북 하나가 만드는 것

맨 위의 해부도가 노트북 한 대 뒤에 생기는 리소스입니다. 2편에서 배운 Operator 패턴이 그대로 보입니다. 사용자는 Notebook이라는 주문서 하나만 내고, Notebook 컨트롤러가 나머지를 만들어 상태를 맞춥니다. 해부도에서 중지됨을 눌러 보세요. Pod만 사라지고 나머지는 남습니다.

리소스누가 만드나중지하면노트북을 지우면
Notebook만들기 화면 (사용자)남음. 중지 표시 주석이 붙음사라짐
StatefulSetNotebook 컨트롤러남음. 복제본 수가 0이 됨함께 사라짐
PodStatefulSet사라짐사라짐
Service, VirtualServiceNotebook 컨트롤러남음함께 사라짐
작업 공간 PVC만들기 화면 (사용자)남음기본적으로 남음. 따로 지워야 함
 
# 노트북 하나에 딸린 리소스를 한 번에 보기
kubectl get notebooks,statefulsets,pods,svc,virtualservices,pvc -n kubeflow-user-example-com

# 노트북 Pod의 이름은 StatefulSet 규칙에 따라 이름 뒤에 -0이 붙습니다
kubectl logs my-first-notebook-0 -n kubeflow-user-example-com -c my-first-notebook
StatefulSet을 쓰는 이유

노트북은 Pod가 다시 만들어져도 같은 이름과 같은 저장소를 가져야 합니다. StatefulSet은 Pod에 고정된 이름(이름-0)을 주고, 죽으면 같은 이름으로 다시 만들어 같은 PVC를 다시 붙입니다. 복제본은 언제나 1개이고, 중지는 이 숫자를 0으로 내리는 것입니다.

3만들기 화면 따라 하기

대시보드의 Notebooks 화면에서 New Notebook을 누르면 나오는 만들기 화면(spawner)을 단순화했습니다. 왼쪽에서 값을 바꾸면 오른쪽에 만들기 화면이 실제로 제출하는 Notebook YAML과 점검 결과가 바로 바뀝니다. 실제 화면의 항목 이름과 기본값은 관리자 설정에 따라 다를 수 있습니다.

    나만의 이미지 만들기
    
  
    팀 표준 패키지를 미리 넣은 이미지를 만들어 두면, 모두가 같은 환경에서 시작하고 노트북을 열 때마다 pip install을 반복하지 않아도 됩니다. 예제 이미지를 기반으로 하면 Kubeflow가 요구하는 조건을 자동으로 만족합니다.
    

    FROM ghcr.io/kubeflow/kubeflow/notebook-servers/jupyter-scipy:<설치 버전 태그>
# 예제 이미지는 jovyan 사용자로 끝나므로, 패키지 설치는 그대로 해도 됨
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt
    
  
    예제 이미지를 쓰지 않고 처음부터 만든다면, 공식 문서가 요구하는 조건을 모두 지켜야 합니다.
    
  
    
    
    조건이유안 지키면
    
    
      
    8888 포트로 HTTP 서비스Service와 VirtualService가 이 포트로 요청을 보냄CONNECT를 눌러도 연결되지 않음
    
      
    NB_PREFIX 환경 변수의 경로 아래에서 응답노트북은 /notebook/네임스페이스/이름/ 경로로 열리고, 그 경로를 이 변수로 알려 줌빈 화면이나 404
    
      
    응답 헤더에 Access-Control-Allow-Origin: *대시보드가 노트북 화면을 iframe으로 감쌈대시보드 안에서 화면이 막힘
    
      
    jovyan 사용자(UID 1000), 홈 /home/jovyan으로 실행작업 공간 PVC가 /home/jovyan에 붙고 권한도 이 사용자 기준홈 폴더 쓰기 권한 오류
    
      
    빈 PVC가 /home/jovyan에 붙어도 정상 시작처음 만든 PVC는 비어 있음. 이미지가 홈에 넣어 둔 파일은 가려짐시작 직후 죽거나 설정 파일이 없다는 오류
    
        
  
    
  
    
    홈 폴더에 넣은 파일은 보이지 않습니다
    
    마지막 조건이 가장 많이 실수하는 부분입니다. 이미지를 만들 때 /home/jovyan에 예제 파일이나 설정을 넣어도, 실행할 때 그 위에 PVC가 덮이므로 보이지 않습니다. 팀이 공유할 파일은 /opt 같은 다른 경로에 넣고, 패키지는 홈이 아닌 이미지의 Python 환경에 설치하세요.
    
  
    

    


    
  
    5무엇이 남고 무엇이 사라지나
    
  
    노트북을 중지하거나, 노드가 재시작되거나, 이미지를 바꿔 다시 만들면 Pod는 새로 만들어집니다. 이때 살아남는 것은 PVC에 있던 것뿐입니다. 작업을 잃는 사고 대부분이 이 표 하나로 예방됩니다.
    
  
    
    
    무엇을 어디에Pod가 다시 만들어지면권장
    
    
      
    /home/jovyan 아래의 노트북 파일, 결과남음 (작업 공간 PVC)모든 작업 결과는 여기에
    
      
    /home/jovyan/data의 데이터 볼륨남음 (데이터 PVC)여러 노트북이 함께 읽는 데이터셋
    
      
    pip install로 설치한 패키지사라짐 (이미지의 Python 환경에 설치됨)자주 쓰면 이미지에 넣기
    
      
    pip install --user로 설치한 패키지남음 (~/.local은 홈 안)임시로는 편하지만, 이미지를 바꾸면 버전 충돌의 원인이 됨
    
      
    /tmp 등 다른 경로의 파일사라짐임시 파일만
    
      
    커널 메모리의 변수, 학습 중이던 모델사라짐중간 결과는 체크포인트로 저장 (2편 4장)
    
        
  
    
  
    
    작업 공간 볼륨은 한 번에 한 노트북만
    
    대부분의 블록 스토리지는 ReadWriteOnce라서, 같은 작업 공간 PVC를 두 노트북이 동시에 쓸 수 없습니다. 두 번째 노트북은 “Multi-Attach error”로 시작하지 못합니다. 여러 노트북이 함께 보는 데이터는 ReadWriteMany를 지원하는 StorageClass로 만든 데이터 볼륨이나 오브젝트 스토리지에 두세요.
    
  
    

    


    
  
    6PodDefault로 설정 주입
    
  
    노트북에서 사내 S3에 접근하려면 접근 키가 필요합니다. 노트북 코드에 키를 적으면 노트북 파일과 함께 퍼져 나갑니다. PodDefault는 라벨이 맞는 Pod가 만들어지는 순간 웹훅이 끼어들어 환경 변수, 볼륨, Secret을 넣어 주는 Kubeflow 리소스입니다. 관리자나 팀 리더가 네임스페이스에 한 번 만들어 두면, 사용자는 만들기 화면의 설정 항목에서 체크만 하면 됩니다.
    
  
    1단계: 비밀 값은 Secret으로
    

    kubectl create secret generic s3-credentials -n kubeflow-user-example-com \
  --from-literal=AWS_ACCESS_KEY_ID='키' \
  --from-literal=AWS_SECRET_ACCESS_KEY='비밀키'
    
  
    2단계: 그 Secret을 주입하는 PodDefault
    

    apiVersion: kubeflow.org/v1alpha1
kind: PodDefault
metadata:
  name: s3-access
  namespace: kubeflow-user-example-com
spec:
  desc: "사내 S3 접근 정보"           # 만들기 화면에 보이는 이름
  selector:
    matchLabels:
      s3-access: "true"             # 이 라벨이 붙은 Pod에만 적용
  env:
  - name: AWS_ENDPOINT_URL
    value: "https://s3.internal.example.com"
  - name: AWS_ACCESS_KEY_ID
    valueFrom:
      secretKeyRef: {name: s3-credentials, key: AWS_ACCESS_KEY_ID}
  - name: AWS_SECRET_ACCESS_KEY
    valueFrom:
      secretKeyRef: {name: s3-credentials, key: AWS_SECRET_ACCESS_KEY}
    
  
    만들기 화면에서 이 설정을 고르면 Notebook에 s3-access: "true" 라벨만 붙습니다. 3장 시뮬레이터에서 체크해 보면 YAML에 라벨 한 줄만 생기는 것을 볼 수 있습니다. 실제 환경 변수는 Pod가 만들어질 때 웹훅이 넣으므로, 확인하려면 Notebook이 아니라 Pod를 봐야 합니다.
    

    kubectl get poddefaults -n kubeflow-user-example-com
kubectl get pod my-first-notebook-0 -n kubeflow-user-example-com -o yaml | grep -A2 AWS_
    
  
    
    Pipelines 접근용 PodDefault
    
    설치 구성에 따라 사용자 네임스페이스에는 노트북에서 Kubeflow Pipelines API를 호출할 수 있게 해 주는 PodDefault(access-ml-pipeline)가 미리 들어 있을 수 있습니다. 5편에서 노트북으로 파이프라인을 제출할 때 이 설정을 켜게 됩니다.
    
  
    

    

    
  
    7실습: 첫 모델 학습
    
  
    3편에서 만든 클러스터에서 노트북을 하나 만들고, 손글씨 숫자 이미지를 분류하는 모델을 학습해 PVC에 저장합니다. GPU 없이 몇 초면 끝나는 작은 실습이지만, 환경 확인, 학습, 저장, 다시 불러오기라는 기본 흐름은 큰 모델과 같습니다.
    
  
      
    
    1. 노트북 만들기
      대시보드에서 네임스페이스가 kubeflow-user-example-com인지 확인하고, Notebooks 화면에서 New Notebook을 누릅니다. 이름 my-first-notebook, 이미지 jupyter-scipy, CPU 1, 메모리 2Gi, GPU 없음, 작업 공간 볼륨 새로 만들기로 설정하고 만듭니다.
      2.

    os.cpu_count()는 내 몫이 아닙니다
    
    첫 셀의 CPU 수는 노트북에 할당된 CPU가 아니라 노드 전체의 코어 수입니다. scikit-learn의 n_jobs=-1이나 PyTorch DataLoader의 워커 수를 이 숫자로 정하면, CPU limits보다 훨씬 많은 프로세스가 떠서 스로틀링으로 오히려 느려집니다. 그래서 학습 셀에서는 requests에 맞춰 n_jobs=2처럼 직접 정했습니다.

    8운영자가 알아야 할 것
    
  
    잊힌 노트북 멈추기: 컬링
    
  
    노트북은 쓰다 말고 그냥 두기 쉽습니다. GPU 노트북 하나가 주말 내내 켜져 있으면 그 GPU는 아무도 못 씁니다. Notebook 컨트롤러에는 일정 시간 활동이 없는 노트북을 자동으로 멈추는 컬링 기능이 있지만 기본으로 꺼져 있습니다. 컨트롤러의 환경 변수로 켭니다.
    
  
    
    
    환경 변수뜻기본값
    
    
      
    ENABLE_CULLING컬링 사용 여부false
    
      
    CULL_IDLE_TIME이 시간(분) 동안 활동이 없으면 멈춤1440 (하루)
    
      
    IDLENESS_CHECK_PERIOD활동 여부를 확인하는 간격(분)1
    
        
  
    
  
    컨트롤러는 Jupyter의 커널 활동 기록을 보고 판단하므로, VS Code나 RStudio 이미지는 같은 방식으로 판단되지 않을 수 있습니다. 멈춘 노트북은 Pod만 사라지고 PVC는 남으니, 사용자는 START로 언제든 이어서 작업할 수 있습니다. 설정은 3편의 원칙대로 원본 매니페스트를 고치지 말고 kustomize 패치로 덧씌우세요.
    

  
    만들기 화면을 팀에 맞게
    
  
    만들기 화면의 이미지 목록, 기본 볼륨 크기, CPU와 메모리 기본값, limits 배수, GPU 종류, GPU 노드로 보내는 toleration과 affinity 선택지는 kubeflow 네임스페이스의 jupyter-web-app-config로 시작하는 ConfigMap 안 spawner_ui_config.yaml에 들어 있습니다. 운영자가 할 일은 대개 다음과 같습니다.
    
  
      
    
    • 이미지 목록을 팀 표준 이미지로 바꾸고, 사용자가 임의 이미지를 입력하지 못하게 할지 정합니다.
      • 
    
    • GPU 노드의 taint에 맞는 toleration 묶음을 미리 만들어, 사용자가 이름만 고르게 합니다(2편 8장).
      • 
    
    • 기본 작업 공간 크기와 StorageClass를 정합니다.
      • 
  
    

  
    할당량과 권한
    
  
    3편에서 프로필에 resourceQuotaSpec을 적었다면, 그 네임스페이스의 노트북 requests 합이 할당량을 넘을 때 만들기가 실패합니다. 또 노트북 Pod는 프로필이 만든 default-editor 서비스 계정으로 실행되어, 노트북 안에서 같은 네임스페이스의 리소스를 만들고 지울 수 있습니다. 노트북에서 kubectl이나 Kubeflow SDK로 학습 작업을 제출할 수 있는 이유이자, 노트북 하나가 팀 공간 전체에 영향을 줄 수 있는 이유이기도 합니다.
    

    


    
  
    9Notebooks v2 미리 보기
    
  
    Kubeflow는 Notebooks v2, 이름하여 Workspaces를 준비하고 있습니다. 26.03.1에는 Workspaces 매니페스트가 정식 출시 전 단계 버전으로 포함되어 있고, 설치 안내에서도 아직 개발 중인 기능으로 표시됩니다. 지금 운영에는 v1을 쓰되, 방향은 알아 두세요. 아래 내용은 현재 설계 기준이라 정식 출시 전에 바뀔 수 있습니다.
    
  
    
    
    구분v1 (Notebook)v2 (Workspace)
    
    
      
    사용자가 만드는 것Pod 설계도 전체가 들어간 Notebook관리자가 준비한 선택지 중 무엇을 쓸지만 적은 Workspace
    
      
    관리자가 정의하는 것만들기 화면의 ConfigMapWorkspaceKind라는 리소스에 이미지 선택지, Pod 구성 선택지, 컬링 정책 등을 정의
    
      
    이미지 업데이트사용자마다 이미지 문자열을 직접 바꿔야 함관리자가 선택지를 새 버전으로 바꾸고 사용자를 옮겨 갈 수 있게 하는 방향
    
      
    화면Jupyter Web App새 Workspaces 화면
    
        
  
    
  
    핵심 변화는 “사용자가 Pod를 직접 설계하던 방식”에서 “관리자가 준비한 메뉴에서 고르는 방식”으로의 이동입니다. 운영하는 쪽에서는 이미지 보안 패치와 표준화가 쉬워지고, 사용자 쪽에서는 고를 것이 줄어듭니다.
    

    


    
  
    10노트북의 자리와 한계
    
  
    노트북은 데이터를 들여다보고, 아이디어를 빠르게 시험하고, 결과를 그림으로 보는 데 최고의 도구입니다. 하지만 모든 일을 노트북에서 하려고 하면 1편의 문제들이 그대로 돌아옵니다.
    
  
    
    
    하려는 일노트북에서 하면더 나은 자리
    
    
      
    데이터 탐색, 시각화, 작은 실험가장 잘 맞음노트북 (이번 편)
    
      
    몇 시간 이상 걸리는 학습브라우저를 닫거나 컬링되면 끊기고, 실패해도 재시도가 없으며, 그동안 GPU를 혼자 점유TrainJob (7편)
    
      
    매일 반복하는 전처리, 학습, 평가누군가 셀을 순서대로 눌러야 하고 실행 기록이 남지 않음Pipelines (5·6편)
    
      
    하이퍼파라미터 조합 수십 개반복문이 노트북 자원 안에서 순서대로 돌아감Katib (8편)
    
      
    모델을 API로 제공노트북을 서버처럼 켜 두게 됨KServe (9편)
    
        
  
    
  
    좋은 습관은 노트북을 “다른 곳에 일을 시키는 조종석”으로 쓰는 것입니다. 노트북에서 코드를 다듬고, 무거운 일은 파이프라인이나 TrainJob으로 제출하고, 결과만 노트북으로 가져와 봅니다. 다음 편부터 그 방법을 배웁니다.
