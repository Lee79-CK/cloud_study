1모듈이란

사실 여러분은 처음부터 모듈을 쓰고 있었다

Terraform에서 모듈은 .tf 파일이 들어 있는 디렉터리 하나입니다. 3편부터 terraform plan을 실행한 그 디렉터리도 모듈이며, 이를 루트 모듈(root module)이라 부릅니다. 루트 모듈이 module 블록으로 다른 디렉터리를 부르면, 불려온 쪽이 자식 모듈(child module)입니다. 자식 모듈도 또 다른 모듈을 부를 수 있습니다.

루트 모듈자식 모듈
정체terraform 명령을 실행하는 디렉터리module 블록으로 불려오는 디렉터리
state하나의 state를 가짐 (backend 설정은 여기에만)자기 state 없음. 부모 state 안에 module.이름. 접두사로 기록
provider 설정여기서 설정설정하지 않고 부모에게서 받는다 (7장)
입력tfvars·환경변수·CLImodule 블록의 인자
출력terraform output, 다른 도구부모가 module.이름.출력으로 참조
비유프로그램의 main 함수라이브러리 함수

왜 모듈인가

재사용

VPC 구성 하나를 모듈로 만들면 고객 20곳, 환경 3개에 같은 코드를 씁니다. 버그는 한 번 고치고 버전을 올리면 끝납니다.

표준 강제

“기본 보안 그룹 규칙 제거”, “암호화 필수”, “표준 태그” 같은 조직 규칙을 모듈 안에 고정하면, 모듈을 쓰는 모든 곳이 자동으로 표준을 따릅니다.

추상화

호출자는 “2개 AZ에 /16 대역 VPC”만 말하면 되고, 서브넷 계산·라우팅·연결 같은 세부는 몰라도 됩니다. 리소스 15개가 입력 5개로 줄어듭니다.

경계와 리뷰

모듈의 입력·출력이 경계가 되므로, 변경의 영향 범위가 분명해지고 리뷰가 쉬워집니다. 네트워크팀은 모듈을, 서비스팀은 호출 코드를 담당하는 식의 분업도 가능합니다.

2module 블록 문법

함수 호출처럼 생겼고, 함수 호출처럼 동작한다

module "vpc" {
  # 메타 인자 (Terraform이 해석)
  source  = "terraform-aws-modules/vpc/aws" # 어디서 가져올지 (필수)
  version = "~> 6.0"                        # 레지스트리 소스에서만

  # 입력 변수 (자식 모듈의 variable 블록에 대응)
  name = "custa-prd"
  cidr = "10.20.0.0/16"
  azs  = ["ap-northeast-2a", "ap-northeast-2c"]

  # 선택 메타 인자
  # count / for_each = …   여러 번 호출
  # depends_on       = […]  모듈 전체에 대한 명시적 의존 (가급적 피함)
  # providers        = { aws = aws.us_east_1 }  프로바이더 전달 (7장)
}

# 자식 모듈의 출력 참조
output "vpc_id" {
  value = module.vpc.vpc_id
}
인자설명
source모듈 위치. 리터럴 문자열(1.15부터 const 변수 사용 가능, 6장). 4장 참고
version레지스트리 소스의 버전 제약. Git 등 다른 소스에는 쓸 수 없고 ?ref=를 쓴다
입력 인자들자식 모듈의 variable 이름과 같은 이름. default 없는 변수는 반드시 넘겨야 함
count / for_each모듈 자체를 여러 번 호출 (0.13+). 주소는 module.vpc["dev"], module.vpc[0]
depends_on모듈 전체가 다른 리소스 뒤에 실행되도록. 모듈 안 data 소스까지 apply 시점으로 미뤄질 수 있어 plan에 미정 값이 번진다(3편 10장). 가능하면 입력 값 참조로 의존을 표현
providers자식 모듈에 넘길 프로바이더 설정 지정 (7장)

init이 모듈에 하는 일

terraform init            # 소스에서 모듈을 내려받아 .terraform/modules/ 에 둔다
cat .terraform/modules/modules.json   # 어떤 이름(Key)의 모듈이 어디(Source)에서 와서 어디(Dir)에 있는지
terraform init -upgrade   # 버전 제약 범위 안에서 모듈(과 프로바이더)을 최신으로 다시 받기
terraform get             # 모듈만 내려받기 (init의 일부)

로컬 경로 모듈(./modules/vpc, ../../modules/vpc)은 복사하지 않고 그 자리를 그대로 읽습니다. 그래서 모듈 파일을 고치면 init 없이 바로 plan에 반영됩니다. 새 module 블록을 추가하거나 source를 바꾸면 다시 init해야 합니다(Module not installed 오류).

자식 모듈의 리소스는 module.<호출 이름>.이 앞에 붙은 주소로 부모 state에 기록됩니다. 모듈을 for_each로 부르면 module.vpc["dev"].aws_vpc.this처럼 됩니다. 호출 이름(module "vpc"의 vpc)을 바꾸면 주소 전체가 바뀌어 모든 리소스가 삭제·재생성 대상이 됩니다. 그래서 이름 변경은 반드시 moved와 함께 합니다(10장).

3입력·출력 계약

모듈의 variable과 output은 내부 구현이 아니라 “공개 API”다

모듈을 쓰는 사람은 모듈 안의 리소스를 보지 않고, 변수와 출력만 봅니다. 따라서 모듈 설계의 대부분은 계약 설계입니다. 좋은 계약은 쓰기 쉽고, 잘못 쓰기 어렵고, 오래 바뀌지 않습니다.

원칙좋은 예나쁜 예
필수 입력은 최소로, 나머지는 합리적 기본값name만 필수, cidr_block = "10.0.0.0/16"·az_count = 2 기본값변수 25개가 전부 필수
의도를 묻는다, 구현을 묻지 않는다az_count = 2, enable_nat_gateway = truepublic_subnet_cidrs, route_table_names… 호출자가 서브넷 계산까지 해야 함
타입을 정확히map(object({...})), optional()type = any 남발
문 앞에서 검사CIDR 형식·크기·AZ 수 validation (4편)잘못된 값이 AWS API 오류로 늦게 발견
표준은 입력으로 열지 않는다암호화·기본 SG 잠금은 모듈 안에 고정enable_encryption = false를 허용
태그는 받아서 합친다tags = map(string)를 받아 모든 리소스에 merge태그를 받지 않음 → 비용 귀속 불가
출력은 다음 단계가 필요한 것ID, ARN, 맵(AZ → 서브넷 ID), NAT 공인 IP리소스 객체 통째로 출력(value = aws_vpc.this) → 내부 구현이 계약이 됨
출력 모양을 약속1.15 type = map(string)상황에 따라 리스트였다 맵이었다 하는 출력

무엇이 호출자를 깨뜨리는가

모듈을 고칠 때 이 변경이 기존 호출 코드를 깨뜨리는지(breaking) 판단해야 버전 번호를 올바르게 올릴 수 있습니다. 시맨틱 버저닝(MAJOR.MINOR.PATCH)에서 깨뜨리는 변경은 MAJOR, 기능 추가는 MINOR, 버그 수정은 PATCH를 올립니다. 아래 변경들을 판정해 보세요.

breaking change 판정기

“리소스 교체”도 breaking이다

변수와 출력이 그대로여도, 모듈 안 리소스의 주소를 바꾸거나(이름 변경, count → for_each) 교체를 유발하는 인자를 바꾸면 호출자의 plan에 대량 삭제·재생성이 나옵니다. 인터페이스는 같아도 운영 관점에서는 MAJOR급 변경입니다. 주소 변경은 모듈 안에 moved 블록을 함께 넣어 호출자가 아무것도 하지 않아도 되게 만드는 것이 모듈 작성자의 예의입니다.

5버전 고정 전략

모듈 버전이 움직이면, 내가 아무것도 안 했는데 plan이 바뀐다

잠금 파일은 모듈을 잠그지 않는다

3편의 .terraform.lock.hcl은 프로바이더만 기록합니다. 모듈 버전은 오직 version 제약과 ?ref=로만 고정됩니다. version = "~> 6.0"이라면, 모듈 작성자가 6.7.0을 내놓은 다음 날 누군가 init -upgrade를 하거나 CI가 깨끗한 환경에서 init하는 순간 새 버전이 들어옵니다. Git 소스에 ?ref=를 빼먹으면 기본 브랜치의 그날 최신 커밋이 들어옵니다.

방식예재현성권장 상황
정확한 버전version = "6.6.1"높음운영 환경 루트 모듈. 업그레이드는 PR로 의도적으로
패치 허용version = "~> 6.6.0"중간개발·검증 환경, 신뢰하는 내부 모듈
마이너 허용version = "~> 6.0"낮음예제·실습. 운영에서는 비권장
Git 태그?ref=v1.2.0높음 (태그를 다시 붙이지 않는다는 전제)사내 Git 모듈의 일반적 방식

업그레이드는 자동 PR로

Renovate·Dependabot은 Terraform 모듈·프로바이더 버전을 인식해 “6.6.1 → 6.7.0” PR을 만들어 줍니다. PR의 CI에서 plan을 돌려 변경 내용을 보고 병합합니다. 고정의 안정성과 최신화를 동시에 얻는 방법입니다(12편).

모듈 쪽 제약은 넓게

모듈 자신의 required_providers는 >= 6.0처럼 최소 요구만 적습니다. 모듈이 ~> 6.10.0처럼 좁게 잡으면, 그 모듈을 쓰는 루트가 다른 모듈과 함께 쓸 수 있는 프로바이더 버전이 없어지는 충돌이 생깁니다. 정확한 고정은 루트의 잠금 파일이 담당합니다.

6동적 모듈 소스 (1.15)

const 변수로 source와 version에 변수를 쓴다

1.14까지 source와 version은 반드시 리터럴이어야 했습니다. 모듈은 terraform init 때 내려받는데, 일반 변수는 그 뒤에야 평가되기 때문입니다. 1.15는 변수에 const = true를 붙여 “이 값은 init 시점에 확정할 수 있다”고 선언하면 모듈 의존성에 쓸 수 있게 했습니다.

variable "modules_ref" {
  description = "공통 모듈 저장소의 태그. 고객사마다 다른 버전을 쓸 수 있게"
  type        = string
  default     = "vpc-v1.2.0"
  const       = true # init 시점에 확정되는 값
}

module "vpc" {
  source = "git::https://git.example.com/iac/modules.git//vpc?ref=${var.modules_ref}"

  name = "custa-prd"
}
규칙내용
선언variable 블록에 const = true
쓸 수 있는 곳module의 source·version 등 init 단계에서 필요한 값
함께 쓸 수 없는 것sensitive, ephemeral (서로 배타적)
참조 제한source에서 const가 아닌 변수나 local을 참조하면 init에서 오류
중첩 모듈자식 모듈의 source에 변수를 쓰려면 그 자식 모듈의 해당 입력 변수도 const = true로 선언되어 있어야 함
값이 바뀌면다른 모듈 소스가 되므로 다시 terraform init 필요
편리함과 재현성 사이

MSP에서는 “고객 A는 vpc-v1.2, 고객 B는 아직 vpc-v1.1” 같은 단계적 업그레이드를 tfvars 한 줄로 관리할 수 있어 유용합니다. 반면 source 문자열이 코드에서 바로 보이지 않게 되므로, 리뷰어가 “이 PR이 어느 버전의 모듈을 쓰는가”를 tfvars까지 찾아봐야 합니다. 고객·환경별 버전을 표로 문서화하고, 기본값은 검증된 버전으로 둡니다. OpenTofu는 1.8부터 비슷한 목적의 “초기 평가(early evaluation)”를 제공하지만 문법이 달라, 두 도구를 오가는 코드라면 주의가 필요합니다.

7프로바이더와 모듈

자식 모듈은 프로바이더를 “요구”하고, 루트가 “설정”해서 넘겨준다

자식 모듈: 요구만 선언
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 6.0"
      # 별칭 프로바이더를 받아야 하는 모듈이라면:
      # configuration_aliases = [aws.us_east_1]
    }
  }
}
# provider "aws" { ... } 블록은 두지 않는다
루트: 설정하고 전달
provider "aws" {
  region = "ap-northeast-2"
}

provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"
}

module "cdn" {
  source = "../../modules/cdn"
  providers = {
    aws           = aws
    aws.us_east_1 = aws.us_east_1
  }
}
규칙이유
자식 모듈에 provider 블록을 두지 않는다모듈 안에 provider 설정이 있으면 그 모듈에 count·for_each·depends_on을 쓸 수 없고, 모듈 블록을 지울 때 리소스를 지울 프로바이더도 함께 사라져 삭제가 불가능해지는 문제가 생깁니다(레거시 패턴).
별칭이 없는 기본 프로바이더는 자동으로 상속providers를 생략하면 루트의 기본 aws가 그대로 전달됩니다.
별칭 프로바이더는 명시적으로 전달모듈은 configuration_aliases로 필요한 별칭을 선언하고, 루트는 providers 맵으로 넘깁니다.
AWS 프로바이더 6.x의 리소스별 region

AWS 프로바이더 6.0부터 대부분의 리소스에 region 인자가 생겨, 리전마다 별칭 프로바이더를 만들지 않고도 리소스 단위로 리전을 지정할 수 있게 되었습니다. 멀티 리전 모듈이 훨씬 단순해집니다. 다만 계정이 다르거나(assume_role) 자격증명이 다르면 여전히 별칭 프로바이더가 필요합니다.

10모듈로 리팩터링

이미 운영 중인 리소스를 지우지 않고 모듈 안으로 옮긴다

4편의 코드처럼 루트에 직접 만든 리소스를 모듈로 정리하고 싶을 때, 코드만 옮기면 주소가 바뀌어 삭제·재생성이 됩니다. 5편에서 예고한 대로 moved 블록이 해법입니다. 아래는 실습 C에서 실제로 얻은 결과입니다.

# 이전: 루트에 직접
# resource "terraform_data" "cache" { input = "v1" }

# 이후: 모듈로 옮기고, 주소 변경을 선언
module "cache" {
  source = "../../modules/cache"
  value  = "v1"
}

moved {
  from = terraform_data.cache
  to   = module.cache.terraform_data.this
}
# moved가 있을 때 (실측)
  # terraform_data.cache has moved to module.cache.terraform_data.this
Plan: 0 to add, 0 to change, 0 to destroy.

# moved를 빼먹었을 때 (실측)
  # terraform_data.cache will be destroyed
  # (because terraform_data.cache is not in configuration)
  # module.cache.terraform_data.this will be created
Plan: 1 to add, 0 to change, 1 to destroy.
상황moved 블록
루트 리소스 → 모듈 안from = aws_vpc.main / to = module.network.aws_vpc.this
모듈 호출 이름 변경from = module.vpc / to = module.network (모듈 안 모든 리소스가 함께 이동)
모듈을 for_each로 전환from = module.vpc / to = module.vpc["dev"]
모듈 안에서 리소스 이름 변경모듈 코드 안에 from = aws_vpc.main / to = aws_vpc.this → 모든 호출자에 자동 적용
모듈 밖으로 꺼내기from = module.network.aws_vpc.this / to = aws_vpc.main

moved 블록은 적용 후에도 한동안 남겨 두는 것이 좋습니다. 같은 코드를 쓰는 다른 환경(stg, prd)이나 다른 고객사가 아직 이전 버전에 있을 수 있기 때문입니다. 모든 곳이 적용된 것을 확인한 뒤 지웁니다.

11공개 모듈 활용

바퀴를 다시 만들지 않되, 남의 바퀴를 무턱대고 달지도 않는다

# 레지스트리에서 가장 많이 쓰이는 VPC 모듈 중 하나 (6.x는 AWS 프로바이더 6 기준)
module "vpc_public" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"

  name            = "iaclab-dev-compare"
  cidr            = "10.30.0.0/16"
  azs             = ["ap-northeast-2a", "ap-northeast-2c"]
  public_subnets  = ["10.30.0.0/24", "10.30.1.0/24"]
  private_subnets = ["10.30.10.0/24", "10.30.11.0/24"]

  enable_nat_gateway = false
}

같은 VPC를 만드는 공개 모듈과 우리 모듈을 비교하면 설계 차이가 보입니다. 공개 모듈은 수많은 사용자를 위해 서브넷 CIDR을 호출자가 직접 주게 하고(유연성), 수백 개의 선택 기능(VPN 게이트웨이, 플로 로그, 엔드포인트, IPv6…)을 변수로 엽니다. 우리 모듈은 조직 표준을 위해 CIDR 계산을 모듈 안에 숨기고 선택지를 줄였습니다(일관성). 어느 쪽이 정답이 아니라, 목적이 다릅니다.

mkdir -p ~/iac-lab-modules/label && cd ~/iac-lab-modules
git init -b main
cat > label/main.tf <<'TF'
variable "name" {
  type = string
}

output "id" {

}
TF
git add -A && git commit -m "label v1" && git tag label-v1.0.0
sed -i 's/lbl-/label-/' label/main.tf          # 출력 형식을 바꾸는 breaking change
git commit -am "label v2: 접두사 변경" && git tag label-v2.0.0

2단계: 같은 모듈의 두 버전을 동시에 쓰기

mkdir -p ~/iac-lab/terraform/06-git-source && cd ~/iac-lab/terraform/06-git-source
cat > main.tf <<'TF'
module "old" {
  source = "git::file:///home/<사용자>/iac-lab-modules//label?ref=label-v1.0.0"
  name   = "web"
}

module "new" {
  source = "git::file:///home/<사용자>/iac-lab-modules//label?ref=label-v2.0.0"
  name   = "web"
}

output "old" { value = module.old.id }
output "new" { value = module.new.id }
TF
sed -i "s#/home/<사용자>#$HOME#" main.tf
terraform init       # Downloading git::file://…?ref=label-v1.0.0 for old… / …v2.0.0 for new…
terraform apply -auto-approve
cat .terraform/modules/modules.json | jq .
ls .terraform/modules/old   # 저장소 전체가 복사되고 // 뒤의 label 디렉터리를 모듈로 사용
# 실측 출력
new = "label-web"
old = "lbl-web"

같은 저장소의 같은 모듈이라도 ref가 다르면 서로 다른 코드입니다. 실제 MSP 공통 모듈 저장소(사내 GitLab 등)라면 git::https://…나 git::ssh://…로 바꾸기만 하면 됩니다. 이제 main 브랜치에 새 커밋을 올려도, 태그를 쓰는 호출자는 영향을 받지 않습니다. 반대로 ?ref=를 지우고 init -upgrade 하면 그날의 main이 들어옵니다. 직접 확인해 보세요.

3단계: 리소스를 모듈 안으로 옮기기 (moved)

mkdir -p ~/iac-lab/modules/cache ~/iac-lab/terraform/06-moved && cd ~/iac-lab/terraform/06-moved
cat > main.tf <<'TF'
resource "terraform_data" "cache" {
  input = "v1"
}
TF
terraform init && terraform apply -auto-approve
terraform state list                  # terraform_data.cache

cat > ../../modules/cache/main.tf <<'TF'
variable "value" {
  type = string
}

resource "terraform_data" "this" {
  input = var.value
}

output "id" {
  value = terraform_data.this.id
}
TF

cat > main.tf <<'TF'
module "cache" {
  source = "../../modules/cache"
  value  = "v1"
}

moved {
  from = terraform_data.cache
  to   = module.cache.terraform_data.this
}
TF
terraform init                        # 새 module 블록이 생겼으므로 init 필요
terraform plan                        # has moved to … 0 to add, 0 to change, 0 to destroy (10장 실측)
terraform apply -auto-approve
terraform state list                  # module.cache.terraform_data.this

moved 블록을 잠시 지우고 plan을 해 보면 “1 to add, 1 to destroy”가 나옵니다(10장 실측). 운영 리소스였다면 서버 교체입니다. 확인 후 다시 넣어 두세요.

공통 모듈 저장소 + 고객별 라이브 저장소

모듈은 하나의 저장소(iac-modules)에서 버전 태그로 배포하고, 고객마다 “어떤 모듈 버전을 어떤 값으로 부르는지”만 담은 라이브 저장소를 둡니다. 모듈 수정과 고객 적용이 분리되어, 한 고객에서 검증한 버전을 다른 고객에 순차 적용할 수 있습니다(25편).

버전 매트릭스 관리

“고객 A는 vpc-v1.3, B는 v1.2, C는 v1.1”을 표로 관리하고, 지원 중단할 구버전을 정합니다. 1.15의 const 변수로 버전을 tfvars에 두면 이 표를 코드로 만들 수 있습니다. Renovate로 버전 갱신 PR을 고객 저장소마다 자동 생성하면 누락이 줄어듭니다.

조직 표준은 모듈에 굽는다

보안 점검에서 자주 지적되는 항목(기본 보안 그룹 규칙, 암호화 미적용, 퍼블릭 접근, 태그 누락)을 모듈 기본 동작으로 만들면, 신규 고객 구축 시 점검 지적이 처음부터 사라집니다. 예외가 필요하면 변수로 열되, 이름에 위험을 드러냅니다(allow_public_access).

고객 고유 요구는 모듈 밖에서

한 고객만의 특수 요구를 공통 모듈에 if로 넣기 시작하면 god module이 됩니다. 고객 라이브 저장소에서 공통 모듈의 출력을 받아 추가 리소스를 붙이는 방식으로 해결합니다(모듈 조합).

CHANGELOG와 업그레이드 가이드

모듈의 MAJOR 버전을 올릴 때는 “무엇이 바뀌었고, 호출자는 무엇을 해야 하는가(필요한 moved, 바뀐 변수)”를 CHANGELOG에 씁니다. 업그레이드는 고객의 dev → stg → prd 순서로, plan 결과를 변경 요청서에 첨부합니다.

모듈도 코드 리뷰와 테스트를

공통 모듈의 버그는 모든 고객에 퍼집니다. examples/를 CI에서 plan(가능하면 apply·destroy)하고, terraform test(10편)로 계약을 검증합니다. 모듈 저장소의 병합 권한은 소수에게만 줍니다.

과제 1. VPC 모듈에 S3 게이트웨이 엔드포인트 추가

enable_s3_endpoint(bool, 기본 true) 입력을 추가하고, 켜져 있으면 aws_vpc_endpoint(Gateway 유형, S3)를 만들어 모든 프라이빗 라우팅 테이블에 연결하세요. 게이트웨이 엔드포인트는 무료이며, NAT 없이도 프라이빗 서브넷에서 S3에 접근하게 해 줍니다. 이 변경은 MAJOR, MINOR, PATCH 중 무엇일까요?

힌트와 해설
resource "aws_vpc_endpoint" "s3" {
  count = var.enable_s3_endpoint ? 1 : 0

  vpc_id            = aws_vpc.this.id
  service_name      = "com.amazonaws.${data.aws_region.current.region}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = values(aws_route_table.private)[*].id
  tags              = merge(var.tags, { Name = "${var.name}-s3" })
}

기본값이 있는 입력 추가 + 새 리소스이므로 인터페이스 관점에서는 MINOR입니다. 단, 기본값이 true라서 업그레이드하는 모든 호출자의 plan에 엔드포인트 생성이 나타납니다. 무료이고 무해하지만, “업그레이드만 했는데 리소스가 생긴다”는 점을 CHANGELOG에 적어야 합니다. 보수적으로 가려면 기본값을 false로 두고 다음 MAJOR에서 true로 바꿉니다. data "aws_region" "current" {}를 모듈에 추가하는 것도 잊지 마세요.
