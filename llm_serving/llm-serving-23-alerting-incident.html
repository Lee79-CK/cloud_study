01시작하기 전에

경보 시스템의 품질은 “얼마나 많이 잡나”가 아니라 “울렸을 때 사람이 무엇을 할지 아는가”로 잽니다.

학습 목표

  1. 좋은 경보의 조건(대응 가능·증상 중심·등급·담당·런북)을 설명하고 기존 경보를 평가할 수 있다.
  2. Alertmanager의 경로 트리·묶기·억제·침묵·수신자로 경보 흐름을 설계할 수 있다.
  3. LLM 서빙의 층별 경보 목록을 증상(호출)과 원인(티켓)으로 나눠 만들 수 있다.
  4. 대표 장애 열 가지의 확인·완화·원인 조사·복구 확인 절차(런북)를 작성할 수 있다.
  5. 장애 대응 역할·등급·소통·완화 우선 원칙과 비난 없는 사후 검토를 운영할 수 있다.
  6. 경보 품질 지표로 노이즈를 줄이고, LLM 보조 분석을 안전한 범위에서 활용할 수 있다.
이 편의 비유: 건물 화재 경보 체계

연기 감지기마다 따로 소방서에 전화하면 화재 한 번에 전화가 수십 통 옵니다. 그래서 층별 감지를 묶어 한 건으로 보고하고(묶기), 전기가 나가 생긴 감지기 오류는 정전 경보가 대신하며(억제), 공사 중인 층은 미리 꺼 둡니다(침묵). 소방관은 건물마다 진입 경로와 소화전 위치가 적힌 대응 매뉴얼(런북)을 들고 출동하고, 불을 끈 뒤에는 누구 탓이 아니라 “무엇이 불을 키웠나”를 기록합니다(사후 검토).

사람을 깨우는 경보는 비쌉니다. 그만한 가치가 있는 것만 호출로 보냅니다.

억제는 라벨이 맞아야 동작한다

억제 규칙의 equal은 원인·증상 경보가 같은 라벨 값을 가져야 짝을 짓습니다. 엔진 다운 경보에는 namespace만 있고 지연 경보에는 model_name만 있다면 억제가 동작하지 않습니다. 20편의 표준 라벨을 경보 규칙에서도 일관되게 유지해야 하는 이유입니다(실습 23-1).

    06장애 대응 절차

    장애 중 가장 중요한 원칙: 원인보다 완화가 먼저. 사용자의 고통을 먼저 멈추고, 원인은 그다음에 찾습니다.

    등급기준 (예)대응
    SEV1주요 서비스 전면 중단, 데이터 유출 의심, 여러 고객 영향즉시 호출, 장애 지휘자 지정, 고객 공지, 30분 간격 상황 공유
    SEV2일부 기능·고객 영향, SLO 빠른 소진당직 대응, 필요 시 지휘자, 영향 고객 공지
    SEV3영향 작음·우회 가능업무시간 티켓
    역할하는 일
    장애 지휘자판단·우선순위·역할 분배. 직접 고치지 않음
    운영 담당진단·완화 작업 실행
    소통 담당고객·내부 공지, 상태 페이지 갱신
    기록 담당시각별 사건·결정 기록 (사후 검토의 원자료)

    LLM 서빙의 대표 완화 수단

    • 되돌리기: 직전 오버레이·이미지로 롤백(7편 스냅샷, 25편 카나리). 배포 직후 장애의 1순위.
    • 우회: 다른 레플리카·다른 클러스터, 허용 테넌트에 한해 외부 공급자 폴백(12편).
    • 부하 줄이기: 흐름 제어로 낮은 우선순위부터 거절(11편), 게이트웨이 한도 일시 강화(12편), max_tokens 상한 축소.
    • 용량 늘리기: 최대 레플리카 상향, 배치 작업 선점(8·18편).
    • 기능 끄기: 추측 디코딩·LoRA·특정 모델 일시 중지(16편) — 문제가 기능 조합일 때.

    07사후 검토

    “누가 실수했나”가 아니라 “어떤 조건이 실수를 가능하게 했나”를 찾습니다.

    markdown · 사후 검토 양식
    # 사후 검토: <제목>  (SEV<n>, <날짜>)
## 요약          — 무슨 일이, 누구에게, 얼마나 (영향 요청 수·고객·SLO 예산 사용량)
## 시간표        — 발생 · 감지(경보) · 대응 시작 · 완화 · 복구 (각 시각과 근거 지표·트레이스)
## 감지          — 어떤 경보가 울렸나, 사용자 신고가 먼저였나, 늦었다면 왜
## 원인          — 직접 원인 / 기여 요인 (설정·용량·절차·관측의 빈틈)
## 잘된 점 / 아쉬운 점
## 조치 항목     — 담당·기한·추적 티켓 (경보 개선·런북 보완·자동화·용량)
## 배운 것       — 다른 서비스·고객에도 적용할 것
    • 핵심 지표: 감지까지 시간(MTTD), 대응 시작까지(MTTA), 복구까지(MTTR), 사용자 신고가 경보보다 먼저였던 비율.
    • 조치 항목 추적: 사후 검토의 가치는 조치 항목이 끝까지 완료되는가로 결정됩니다. 월간으로 완료율을 봅니다.
    • 근거: 시간표는 기억이 아니라 지표·트레이스·로그(20·21편)·경보 기록으로 채웁니다.

    08노이즈 줄이기와 AIOps

    울려도 아무도 행동하지 않는 경보는 진짜 경보를 묻어 버립니다.

    방법내용
    경보 품질 지표주당 호출 수, 호출 중 실제 조치한 비율, 같은 경보 반복 횟수, 업무시간 외 호출 수 (실습 23-5)
    정기 정리한 달간 아무도 행동하지 않은 경보는 등급을 내리거나 삭제. 새 경보는 런북과 함께만 추가
    구조로 줄이기묶기·억제·증상 중심 호출 (히어로 시뮬레이터)
    이상 탐지고정 임계값이 어려운 지표(트래픽 패턴 등)에 쓰되, 오탐이 많아 호출보다 정보·티켓 등급에서 시작
    상관 분석토폴로지(노드 → Pod → 모델 → 테넌트)로 여러 경보를 한 사건으로 묶기
    LLM 보조 분석경보 묶음을 받아 요약·관련 대시보드·런북 후보를 제시 (아래 원칙)
    LLM 보조 분석의 안전 원칙
    • 읽기 전용부터: 요약·후보 제시까지만. 재시작·롤백 같은 조치는 사람 승인 후, 그것도 정해진 런북 안에서만.
    • 근거 표시: 요약에는 어떤 경보·지표·로그를 봤는지 함께 적어 사람이 검증할 수 있게.
    • 데이터 범위: 경보·지표 메타데이터 중심. 고객 프롬프트·응답은 넣지 않음(21·22편). 외부 모델을 쓴다면 데이터 정책 확인(12편).
    • 평가: 지난 장애 기록으로 요약·제안의 정확도를 주기적으로 점검(22편 판정 방식).

    실습 23-6은 Alertmanager 웹훅으로 받은 경보 묶음을 랩 엔진이 한국어 장애 요약으로 바꾸는 간단한 예입니다.

    09MSP 관점

    여러 고객의 경보를 한 당직팀이 받으면서도, 고객별 계약과 소통을 지켜야 합니다.

    • 테넌트 라벨로 경로 분기: 고객별 SLA 등급에 따라 호출·티켓 경로와 반복 간격을 다르게. 고객 전용 채널로 동시 통지가 필요한 계약도 경로 트리에서 처리합니다.
    • SLA 시계: 고객 계약의 대응 시작·복구 시간 약속을 경보 시각 기준으로 측정하고 월간 보고(26편)에 포함합니다.
    • 상태 페이지·공지 양식: 장애 등급별 고객 공지 문안을 미리 준비해 소통 담당이 바로 쓰게 합니다.
    • 표준 런북: 고객 환경이 달라도 같은 엔진·같은 지표 체계(20편)라면 런북을 공유할 수 있습니다. 고객별 차이(엔드포인트·연락처·데이터 정책)만 부록으로.
    • 정기 장애 훈련: 분기마다 고객 환경 하나를 골라 실습 23-4 같은 훈련을 하고 결과를 고객과 공유하면 신뢰를 쌓을 수 있습니다.

    10흔한 오해

    경보와 장애 대응에 대해 자주 듣는 말들.

    11실습

    랩용 웹훅 수신기로 Alertmanager 경로·묶기·억제를 확인하고, LLM 서빙 원인 경보를 추가한 뒤, 장애 훈련으로 감지부터 사후 검토까지 한 바퀴 돌립니다.

    • 훈련(23-4)은 엔진을 내렸다 올리므로, RAG 플랫폼 등 다른 사용자가 엔진을 쓰지 않는 시간에 합니다.

    """Prometheus의 ALERTS 시계열로 경보별 발생 시간과 호출 등급 비중을 본다. 사용: python alert_review.py [Prometheus 주소]"""
import json, sys, urllib.parse, urllib.request
prom = sys.argv[1] if len(sys.argv) > 1 else "http://localhost:9090"
def q(expr):
    url = f"{prom}/api/v1/query?query={urllib.parse.quote(expr)}"
    return json.load(urllib.request.urlopen(url))["data"]["result"]
rows = q('sum by (alertname, severity) (count_over_time(ALERTS{alertstate="firing"}[7d]))')
rows.sort(key=lambda r: -float(r["value"][1]))
step = 30   # 규칙 평가 간격(초)에 맞춤 — 표본 수 × 간격 ≈ 울린 시간
print(f"{'경보':<28}{'등급':<8}{'울린 시간(분)':>14}")
for r in rows[:20]:
    m = r["metric"]; minutes = float(r["value"][1]) * step / 60
    print(f"{m.get('alertname',''):<28}{m.get('severity',''):<8}{minutes:>14.0f}")
pages = sum(float(r["value"][1]) for r in rows if r["metric"].get("severity") == "page")
total = sum(float(r["value"][1]) for r in rows) or 1
print(f"\n호출 등급 비중 {pages/total*100:.0f}%  — 오래 울렸는데 아무도 조치하지 않은 경보는 등급 조정·삭제 후보")

    14정리와 체크리스트

    핵심 여섯 문장. 이것으로 Level 4가 끝납니다.

    1. 호출은 증상으로, 원인은 티켓으로. 모든 호출 경보에는 런북이 붙는다.
    2. Alertmanager의 묶기·억제·침묵으로 장애 하나가 알림 하나가 되게 하고, 억제를 위해 라벨을 일관되게 유지한다.
    3. LLM 서빙 경보는 층별로: 서비스 SLO·엔진·품질·용량·하드웨어·라우팅·게이트웨이·비용·관측 자체.
    4. 런북은 확인 → 완화 → 원인 → 복구 확인 → 재발 방지, 장애 중에는 원인보다 완화가 먼저.
    5. 사후 검토는 비난 없이, 근거 자료로, 조치 항목 완료까지. MTTD·MTTA·MTTR을 추적한다.
    6. 경보 품질을 정기 점검하고, LLM 보조 분석은 읽기 전용·근거 표시·데이터 범위 제한에서 시작한다.
