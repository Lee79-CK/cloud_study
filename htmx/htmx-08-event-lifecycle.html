이벤트 생명주기: htmx의 모든 순간에 끼어들기

Level 1에서는 속성만으로 화면을 만들었습니다. 그러나 "모든 요청에 추적용 ID를 붙이고 싶다", "저장 안 한 폼이 있으면 이동을 막고 싶다", "React 컴포넌트에게 방금 무엇이 바뀌었는지 알려 주고 싶다"는 요구는 속성 하나로 풀 수 없습니다. htmx는 요청의 모든 단계마다 DOM 이벤트를 발생시키고, 그 이벤트의 detail.ctx로 요청 자체를 읽고 고칠 수 있게 합니다. 이번 편은 그 지도를 완성합니다.

02

이벤트 전체 지도

htmx 4의 이벤트 이름은 htmx:단계:동작[:세부] 규칙을 따릅니다. 아래 표는 htmx 4.0.1 소스에 있는 이벤트 이름을 모두 모아 다섯 묶음으로 나눈 것입니다. "취소"는 preventDefault()를 부르면 그 뒤 단계가 멈추는지를 소스로 확인한 결과입니다.

묶음이벤트발생 요소취소쓰임
요소 초기화htmx:before:init / after:inithtmx 속성이 있는 요소before만 (초기화 안 함)요소별 준비 작업
htmx:before:process / after:process처리를 시작한 루트-새 내용이 들어온 뒤 공통 작업 (2.x의 htmx:load 자리)
htmx:before:cleanup / after:cleanuphtmx가 초기화했던 요소-요소가 사라지기 전 정리 (12편 아일랜드 언마운트)
요청htmx:config:request요청 요소○ (요청 없음, finally도 없음)헤더·본문·주소·확인 문구 수정
htmx:confirm요청 요소○ (기본 창 대신 직접 처리)사용자 정의 확인 창 (4편)
htmx:before:request요청 요소○보내기 직전 마지막 점검, 진행 표시 시작
htmx:before:response요청 요소○ (본문을 읽지 않음)상태·헤더만 보고 판단
htmx:after:request요청 요소○ (스왑 안 함)응답 텍스트까지 읽은 뒤
htmx:finally:request요청 요소-성공·실패·취소 무관하게 마지막
스왑htmx:before:swap요청 요소○ (스왑 전체 취소)detail.tasks로 스왑 작업 수정
htmx:before:settle / after:settle스왑 대상-교체 직후·정착 후 (5편)
htmx:after:swap / finally:swap요청 요소-모든 작업 완료 후
htmx:before:viewTransition / after:viewTransition요청 요소-전환 효과 전후 (5편)
히스토리htmx:before:history:update / after:history:update / after:history:push / after:history:replacedocumentbefore만주소 기록 전후 (7편)
htmx:before:history:restoredocument○뒤로 가기 복원 전 (캐시 확장이 사용)
오류·기타htmx:response:error / htmx:error요청 요소-6편: 응답이 있는 오류 / 없는 오류
htmx:abort요소-이 이벤트를 요소에 보내면 진행 중 요청을 중단

요청 묶음의 이벤트는 모두 요청 요소에서 발생해 위로 버블링되므로, 전역 동작은 document에 리스너 하나로 겁니다. 4편에서 본 대로 요청 요소가 이미 문서에서 떨어져 있으면 htmx는 대신 document에 발생시킵니다. 또 htmx가 만드는 이벤트는 모두 cancelable: true, composed: true(섀도 DOM 경계 통과)입니다.

"시작에서 켜고 끝에서 끄는" 코드(진행 표시, 버튼 잠금)는 취소 지점을 알아야 짝이 맞습니다. 소스와 측정으로 확인한 사실은 두 가지입니다. config:request에서 취소하면 finally:request가 오지 않습니다. 확인 창에서 취소하면 before:request 없이 finally:request만 옵니다(확인 단계가 try 블록 안에 있음). 그래서 랩은 before:request에서 요청 상태(ctx)를 Set에 넣고, finally:request에서 "있으면 뺀다"로 짰습니다. 두 취소 경로 모두에서 표시줄이 켜진 채 남지 않습니다.

04

htmx 4는 모든 요청 이벤트에 같은 요청 상태 객체 detail.ctx를 넘깁니다. 4.0.1 소스의 #createRequestContext가 만드는 필드와, 요청이 진행되며 추가되는 필드입니다.

confirmhx-confirm 문구config:request (확인 단계 전)

request.bodyconfig:request 시점에는 FormData. 이후 GET이면 쿼리로, 아니면 URLSearchParams로 변환config:request (body.set())
request.signal, request.abort(), request.timeout중단 신호, 중단 함수, 제한 시간hx-config나 config:request

참고로 4.0.1 소스는 부스트된 요소의 hx-boost 값을 HCON으로 ctx에 병합합니다. 즉 hx-boost:inherited="target:#main swap:innerHTML"처럼 쓰면 부스트 링크의 대상과 스왑 방식을 한 번에 정할 수 있습니다.

05

요청 고쳐 쓰기

체크한 항목만큼 이벤트 리스너가 요청을 고칩니다. "보내기"를 누르고 서버가 실제로 받은 것과 화면에 들어간 것을 비교하세요.

요청 고쳐 쓰기 실험실 (htmx 4.0.1 실동작)

버튼: hx-post="/demo/rw" name="memo" value="원본"
서버가 받은 것

        
#rw-out (화면에 들어간 것)
아직 없음

      

    

  

  
마지막 항목을 켜면 모의 서버가 X-Maint: on 헤더를 붙여 응답하고, 리스너가 before:response에서 취소해 본문을 읽지도 스왑하지도 않습니다. 게이트웨이가 점검 중 신호를 헤더로 보낼 때 이렇게 처리할 수 있습니다. 확인 문구 항목은 랩의 "저장하지 않은 변경 보호"가 쓰는 바로 그 방법입니다.

  
핵심 패턴


document.addEventListener('htmx:config:request', (e) => {
  const { ctx } = e.detail;
  ctx.request.headers['X-Request-ID'] = crypto.randomUUID();   // 헤더
  ctx.request.body.set('tenant', currentTenant());            // 본문 (이 시점엔 FormData)
  if (needsConfirm(ctx)) ctx.confirm = '정말 진행할까요?';     // 확인 단계로 넘김
});
document.addEventListener('htmx:before:swap', (e) => {
  for (const task of e.detail.tasks) { /* task.type: 'main' | 'oob' | 'partial', task.fragment, task.target, task.swapSpec */ }
});

요소 생명주기 이벤트

  
요청과 별개로, htmx가 요소를 "살리고" "정리하는" 순간에도 이벤트가 납니다. 통합 포털에서는 React·Vue 아일랜드를 마운트·언마운트할 시점으로 중요합니다.

  

    
이벤트언제측정·근거

    
      
htmx:before:process → … → htmx:after:process페이지 로드 시 body, 스왑 후 새로 들어온 요소마다측정: 로드 시 before:process@body로 시작해 after:process@body로 끝남. 스왑 후에는 새 요소 단위로 발생

      
htmx:before:init / after:init그 사이 htmx 속성이 있는 요소 하나하나측정: 버튼 9개에 각각 한 쌍

      
htmx:before:cleanup / after:cleanuphtmx가 초기화한 요소가 교체로 사라질 때htmx 속성이 없는 일반 요소에는 발생하지 않음 (측정)

    
  

  
2.x의 htmx:load는 4.x에서 htmx:after:process로 바뀌었고, htmx.onLoad(callback)도 이 이벤트를 듣도록 바뀌었습니다(공식 What's New, 소스 확인). "새 내용이 들어올 때마다 실행할 코드"는 htmx.onLoad(el => …)로 등록하면 되고, 콜백에는 처리된 루트 요소가 넘어옵니다. 다만 htmx 속성이 하나도 없는 조각(순수 텍스트·표)에도 after:process가 오는지, cleanup이 오는지는 위 표처럼 다르니, 아일랜드처럼 "반드시 정리해야 하는" 대상은 12편에서 웹 컴포넌트의 disconnectedCallback에 맡깁니다.

A. 요청 ID: 화면의 오류와 서버 로그를 잇기

  
클라이언트는 config:request에서 crypto.randomUUID()로 만든 ID를 붙이고, 서버는 그 값을 검증(16진수·하이픈 8~64자)한 뒤 응답 헤더와 로그에 남깁니다. 오류 토스트에는 앞 8자리를 보여 줍니다. 측정 결과, 클라이언트가 보낸 ID와 응답 헤더의 ID가 같았고 서버 로그에서 같은 rid=가 검색됐습니다. 7편에서 "핵심 헤더가 빠진다"고 측정했던 뒤로 가기 복원 요청에도 이 헤더는 붙었습니다. 복원 요청도 config:request를 거치기 때문입니다.

  
apps/server/src/app.js (①-1)


app.use((req, res, next) => {
  const rid = req.get('X-Request-ID');
  req.id = /^[0-9a-f-]{8,64}$/i.test(rid ?? '') ? rid : randomUUID();
  res.set('X-Request-ID', req.id);
  next();
});


  
B. 진행 표시줄과 저장하지 않은 변경 보호

  
진행 표시줄은 요약 카드처럼 data-quiet 영역에서 시작한 요청을 빼서, 5초 폴링 때마다 깜빡이지 않게 했습니다(측정: 폴링 중 표시줄 켜짐 0회, VM 상세 클릭 시 1회). 변경 보호는 메모 편집 폼과 알림 설정 폼에 data-guard를 달고, 입력이 생기면 폼의 JS 속성 __dirty를 켭니다. DOM 속성(data-dirty)을 쓰지 않은 이유는 5편의 모핑이 서버 HTML에 없는 속성을 지우기 때문입니다. 알림 설정 폼은 입력할 때마다 모핑되므로 DOM 속성으로 표시하면 검증 응답이 올 때마다 표시가 사라집니다.
