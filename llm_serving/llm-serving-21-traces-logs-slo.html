트레이스·로그와
SLO 운영

20편의 지표는 “전체가 어떤가”를 보여 줍니다. 그런데 “이 고객의 이 요청은 왜 8초 걸렸나”에는 답하지 못합니다. 이번 편은 트레이스로 요청 하나가 게이트웨이·라우터·엔진에서 각각 얼마를 썼는지 따라가고, 로그를 구조화해 트레이스와 잇고, 20편의 기록 규칙 위에 SLO·오류 예산·소진율 경보를 세워 “얼마나 나빠지면 사람이 움직여야 하나”를 정합니다.

01시작하기 전에

관측의 목적은 데이터를 모으는 것이 아니라, 사용자가 느끼기 전에 알고 빠르게 원인에 도달하는 것입니다.

학습 목표

  1. 지표·트레이스·로그의 역할 분담과 서로를 잇는 방법(트레이스 ID·예시)을 설명할 수 있다.
  2. OpenTelemetry의 SDK·OTLP·Collector·문맥 전파·샘플링을 설명하고 서빙 스택에 적용할 수 있다.
  3. vLLM·게이트웨이·라우터의 트레이스 속성(GenAI 규약 포함)으로 요청 지연을 분해할 수 있다.
  4. LLM 서빙 로그에 남길 것과 남기지 말 것을 정하고, 트레이스와 연결할 수 있다.
  5. 가용성·TTFT·토큰 간 지연 SLI와 SLO를 설계하고 오류 예산을 계산할 수 있다.
  6. 다중 창 소진율 경보를 기록 규칙 위에 구성하고, 예산 정책으로 운영할 수 있다.
이 편의 비유: 택배 추적과 서비스 약속

지표는 “오늘 전체 배송의 95%가 이틀 안에 도착”이라는 통계, 트레이스는 송장 번호로 본 내 택배의 이동 기록(집하 → 터미널 → 배송), 로그는 각 지점의 상세 작업 일지입니다. SLO는 “한 달 동안 99.5%를 이틀 안에”라는 약속이고, 오류 예산은 그 약속 안에서 늦어도 되는 0.5%의 여유입니다. 예산이 빠르게 줄어들면(소진율이 높으면) 지금 당장 움직여야 하고, 천천히 줄면 다음 주 회의 안건이면 충분합니다.

02세 신호의 역할 분담

세 신호는 서로 대신할 수 없고, 서로를 가리키도록 이어 둘 때 가장 강합니다.

신호답하는 질문강점약점LLM 서빙 예
지표 (20편)전체가 어떤가, 언제부터 나빠졌나싸고 오래 보관, 경보·SLO의 기반개별 요청을 모름, 라벨 수 제한모델별 TTFT p95, 대기열, KV 사용률
트레이스이 요청이 어디서 시간을 썼나구간별 지연, 서비스 간 인과양이 많아 샘플링 필요게이트웨이 → 라우터 → 엔진(대기·Prefill·Decode) 구간
로그정확히 무슨 일이 있었나오류 메시지·상세 맥락구조화하지 않으면 검색이 어려움, 개인정보 위험엔진 오류, 게이트웨이 접근 기록, 감사 로그
  • 잇는 고리 ① 트레이스 ID: 게이트웨이·엔진 로그에 트레이스 ID를 남기면 로그에서 트레이스로, 트레이스에서 로그로 이동할 수 있습니다.
  • 잇는 고리 ② 예시(exemplar): 히스토그램 지표에 대표 요청의 트레이스 ID를 붙이면, “p99가 튄 순간”의 그래프에서 바로 그 요청의 트레이스로 들어갈 수 있습니다(지원하는 수집기·백엔드에서).
  • 잇는 고리 ③ 공통 속성: 테넌트·모델·변형 이름을 세 신호 모두 같은 키로 남깁니다(20편 표준 라벨).

04OpenTelemetry 기본

트레이스를 “만들고, 보내고, 모으는” 표준. 벤더와 무관하게 같은 형식으로 흐릅니다.

구성 요소역할운영 포인트
SDK·계측애플리케이션 안에서 스팬을 만듦 (자동·수동)엔진·게이트웨이는 내장 기능을 켜고, 앱은 SDK로 상위 스팬을 만듦
OTLP전송 형식 (gRPC 4317 · HTTP 4318)모든 구성 요소가 Collector로 OTLP를 보내게 통일
Collector받기 → 처리(속성 추가·삭제·샘플링·배치) → 보내기백엔드를 바꿔도 앱 설정은 그대로. 민감 속성 제거를 여기서
문맥 전파W3C traceparent 헤더로 트레이스 ID를 다음 서비스에 전달프록시가 헤더를 지우지 않는지 확인. 엔진은 받은 헤더를 부모로 삼음
샘플링앞단(요청 시작 시 확률) · 뒷단(완료 후 오류·느린 요청 우선 보관)LLM은 요청이 길고 비싸므로 “오류·느린 요청은 전부, 나머지는 일부”가 실용적 (Collector의 tail sampling)
백엔드저장·검색·시각화 (Tempo·Jaeger 등)보존 기간, 지표·로그와의 연결

GenAI 의미 규약

OpenTelemetry는 생성형 AI 호출을 위한 속성 이름(gen_ai.*)을 정하고 있습니다. 작업 이름(gen_ai.operation.name), 공급자(gen_ai.provider.name), 요청·응답 모델, 입력·출력·캐시 토큰 사용량(gen_ai.usage.*), 종료 사유 등이 대표적입니다. 규약은 아직 발전 중이라 버전에 따라 이름이 바뀌기도 하므로, 20편의 지표처럼 Collector에서 표준 이름으로 맞추는 층을 두면 안전합니다. 프롬프트·응답 본문을 속성으로 담는 옵션은 기본으로 끕니다(6장).

vLLM은 요청마다 스팬 하나를 만들고, 그 안에 지연 분해 속성(대기 시간, Prefill·Decode 시간, 모델 실행 시간 등 vLLM 고유의 gen_ai.latency.*)과 토큰 사용량을 담습니다. 20편의 히스토그램이 “분포”를 준다면, 이 속성들은 “문제의 그 요청”에서 같은 분해를 보여 줍니다. vLLM 이미지에 OpenTelemetry 패키지가 포함되어 있는지는 버전마다 다르므로 실습 21-2에서 먼저 확인합니다.

06로그

LLM 로그의 가장 큰 위험은 “너무 적게”가 아니라 “프롬프트를 너무 많이” 남기는 것입니다.

로그남길 것남기지 말 것 (기본)
게이트웨이 접근 로그시각, 트레이스 ID, 테넌트·키 ID, 모델, 상태 코드, 입력·출력 토큰, 지연, 폴백 여부프롬프트·응답 본문, 공급자 키, 개인정보
엔진 로그기동·설정(“기본값이 아닌 인자”), 경고·오류, 선점·OOM, 요청 ID요청 본문 (vLLM의 요청 로그는 최근 버전에서 기본 꺼짐 — 켜더라도 길이 제한)
감사 로그키 발급·폐기, 정책 변경, 관리 API 호출, 어댑터 등록 (12·16편)—
디버깅용 본문 로그합의된 테넌트·기간에만, 마스킹 후, 짧은 보존상시 수집
  • 구조화: JSON 한 줄 로그로 남겨야 검색·집계가 됩니다. 필드 이름은 지표·트레이스와 같은 키(테넌트·모델·트레이스 ID)로.
  • 수집: 노드의 컨테이너 로그를 수집기(Fluent Bit·Grafana Alloy·OTel Collector의 파일 로그 수신기 등)로 모아 로그 저장소(Loki·OpenSearch 등)로 보냅니다.
  • 보존: 운영 로그 수 주, 감사 로그는 계약·규정에 따라. 본문이 섞일 수 있는 로그는 짧게.
  • 비용: 요청마다 큰 로그를 남기면 저장 비용이 GPU 비용에 근접할 수 있습니다. 지표로 충분한 것은 로그로 남기지 않습니다.

07LLM 서빙의 SLI·SLO

SLI는 “좋은 사건 ÷ 전체 사건”으로 정의할 수 있어야 합니다. 그래야 오류 예산을 계산할 수 있습니다.

SLI좋은 사건측정 위치SLO 예 (30일)
가용성서버 오류(5xx)·타임아웃이 아닌 응답게이트웨이 (사용자에 가까움)99.5%
TTFT첫 토큰이 X초 이내 (X는 히스토그램 버킷 경계)엔진 히스토그램 또는 게이트웨이95%가 2.5초 이내
토큰 간 지연토큰 간격이 Y초 이내엔진 히스토그램99%가 0.1초 이내
완료 품질 (22편)형식 준수·정답 등 평가 통과온라인 평가별도 정의
  • 무엇을 나쁜 사건에서 뺄까: 클라이언트 오류(400)는 빼고, 한도 초과(429)는 정책에 따라(정당한 한도면 제외, 용량 부족 때문이면 포함). 이 규칙을 SLO 문서에 명시합니다.
  • 요청 크기: 아주 긴 입력의 TTFT는 원래 깁니다. 입력 길이 구간별로 SLO를 나누거나, 일정 길이 이상은 TTFT SLO에서 제외하는 규칙을 둡니다(19편 워크로드 카드).
  • 단위: 모델별·테넌트 등급별로 SLO를 다르게 둘 수 있습니다(12편 등급).

08오류 예산과 소진율 경보

“SLI가 목표 아래로 떨어지면 경보”는 너무 시끄럽거나 너무 늦습니다. 예산을 태우는 속도로 경보합니다.

오류 예산 = 1 − SLO 목표 (99.5%면 0.5%) 나쁜 비율 = 1 − SLI (지금 창에서) 소진율 = 나쁜 비율 ÷ 오류 예산 (1이면 기간 끝에 예산을 딱 다 씀) 예산 사용 비율 ≈ 소진율 × (지속 시간 ÷ SLO 기간)
경보긴 창 · 짧은 창소진율 기준의미대응
긴급 11시간 · 5분14.41시간에 30일 예산의 2%를 씀호출(페이지)
긴급 26시간 · 30분66시간에 5%호출
일반 11일 · 2시간3하루에 10%티켓
일반 23일 · 6시간13일에 10%티켓

긴 창과 짧은 창을 둘 다 넘을 때만 울립니다. 긴 창은 “충분히 나빴다”를, 짧은 창은 “지금도 나쁘다”를 확인해, 이미 끝난 장애로 계속 울리는 것을 막습니다. 히어로 계산기로 장애의 크기·길이에 따라 어느 경보가 먼저 울리는지 확인해 보세요. 경보의 전달·대응 절차는 23편에서 다룹니다.

09SLO 운영

SLO는 대시보드 숫자가 아니라 팀의 의사결정 규칙입니다.

운영 요소내용
예산 정책예산이 충분하면 새 모델·설정 배포를 진행, 소진되면 신뢰성 작업 우선·위험한 변경 보류. 미리 합의
정기 검토주간: 예산 소진 추이·주요 장애. 분기: SLO 목표·SLI 정의가 사용자 경험과 맞는지
배포와의 연결카나리(25편)의 판단 기준을 SLI로. 새 버전이 예산을 빠르게 태우면 자동 되돌리기
도구Sloth·Pyrra처럼 SLO 정의에서 기록·경보 규칙을 생성하는 도구를 쓰면 실수가 줄어듦
보고월간 SLO 달성률·예산 사용·주요 사건을 고객 보고서로 (26편)

10MSP 관점

SLO는 고객 계약(SLA)과 내부 운영 목표 사이의 완충지대입니다.

  • SLA보다 엄격한 SLO: 계약 SLA가 99%라면 내부 SLO는 99.5%로 두어, SLA 위반 전에 대응할 여유를 만듭니다.
  • 고객별 SLI: 게이트웨이에서 테넌트별로 SLI를 계산하면, 한 고객만 겪는 문제(그 고객의 긴 입력, 그 고객의 한도)를 구분할 수 있습니다.
  • 외부 공급자 구간: 외부 API 지연은 MSP가 통제할 수 없으므로 SLA에서 분리하거나 별도 SLI로 둡니다. 트레이스로 구간을 증명할 수 있어야 합니다.
  • 트레이스·로그의 데이터 주권: 고객 데이터가 담길 수 있으므로 저장 위치·보존·접근 권한을 계약과 맞춥니다.

11흔한 오해

트레이스·로그·SLO에 대해 자주 듣는 말들.

12실습

OTel Collector와 Tempo를 세우고, vLLM 트레이스를 켜서 내가 만든 트레이스 ID로 요청 하나를 찾아 지연을 분해합니다. 로그에 프롬프트가 새지 않는지 확인하고, 20편 기록 규칙 위에 TTFT SLO의 소진율 경보를 만들어 실제로 울려 봅니다.

실습 환경 전제
  • 20편의 kube-prometheus-stack(monitoring 네임스페이스, 릴리스 이름 kps), 7편 랩, bench Pod.
  • 차트 값 키·서비스 이름은 차트 버전에 따라 다르므로 helm show values와 kubectl get svc로 확인해 맞춥니다.

실습 21-3 · 내 트레이스 ID로 요청 하나 따라가기

python · trace_probe.py (bench Pod에서)
"""traceparent 헤더를 직접 만들어 요청을 보내고, Tempo에서 그 트레이스를 찾아 스팬과 gen_ai 속성을 출력한다.
사용: python trace_probe.py [엔진·게이트웨이 주소] [Tempo 주소]"""
import json, os, sys, time, urllib.request
base = sys.argv[1] if len(sys.argv) > 1 else "http://llm-engine:8000"
tempo = sys.argv[2] if len(sys.argv) > 2 else "http://tempo.monitoring.svc:3200"
trace_id, span_id = os.urandom(16).hex(), os.urandom(8).hex()
body = json.dumps({"model": "qwen3-8b", "max_tokens": 64,
                   "messages": [{"role": "user", "content": "트레이스 실험입니다. 한 문장으로 답해 주세요. /no_think"}]}).encode()
req = urllib.request.Request(base + "/v1/chat/completions", body, {
    "Content-Type": "application/json", "traceparent": f"00-{trace_id}-{span_id}-01"})   # 01 = 샘플링함
t0 = time.perf_counter(); urllib.request.urlopen(req, timeout=120).read()
print(f"trace_id={trace_id}  클라이언트 측 지연 {(time.perf_counter() - t0) * 1000:.0f} ms")
def val(v): return next(iter(v.values())) if isinstance(v, dict) and v else v
for i in range(12):                                   # 뒷단 샘플링 대기(decision_wait) 때문에 잠시 기다림
    time.sleep(5)
    try: data = json.load(urllib.request.urlopen(f"{tempo}/api/traces/{trace_id}", timeout=10))
    except Exception: continue
    for b in data.get("batches", []):
        svc = {a["key"]: val(a["value"]) for a in b.get("resource", {}).get("attributes", [])}.get("service.name")
        for ss in b.get("scopeSpans", b.get("instrumentationLibrarySpans", [])):
            for s in ss.get("spans", []):
                dur = (int(s["endTimeUnixNano"]) - int(s["startTimeUnixNano"])) / 1e6
                print(f"\n[{svc}] {s['name']}  {dur:.0f} ms")
                for a in s.get("attributes", []):
                    if a["key"].startswith("gen_ai"): print(f"   {a['key']} = {val(a['value'])}")
    break
else:
    print("Tempo에서 찾지 못함: Collector 로그와 엔진의 otlp 설정을 확인")

실습 21-5 · TTFT SLO 소진율 경보

yaml · slo-ttft-rules.yaml (SLO: 95%가 2.5초 이내, 예산 5%)
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: { name: slo-ttft, namespace: monitoring }
spec:
  groups:
  - name: slo-ttft.sli
    interval: 30s
    rules:
    # 나쁜 비율 = 1 − (2.5초 이하 요청 ÷ 전체). le는 20편에서 확인한 실제 버킷 경계
    - record: slo:ttft_bad_ratio:rate5m
      expr: 1 - sum by (model_name) (rate(vllm:time_to_first_token_seconds_bucket{le="2.5"}[5m])) / clamp_min(sum by (model_name) (rate(vllm:time_to_first_token_seconds_count[5m])), 1e-9)
    - record: slo:ttft_bad_ratio:rate30m
      expr: 1 - sum by (model_name) (rate(vllm:time_to_first_token_seconds_bucket{le="2.5"}[30m])) / clamp_min(sum by (model_name) (rate(vllm:time_to_first_token_seconds_count[30m])), 1e-9)
    - record: slo:ttft_bad_ratio:rate1h
      expr: 1 - sum by (model_name) (rate(vllm:time_to_first_token_seconds_bucket{le="2.5"}[1h])) / clamp_min(sum by (model_name) (rate(vllm:time_to_first_token_seconds_count[1h])), 1e-9)
    - record: slo:ttft_bad_ratio:rate6h
      expr: 1 - sum by (model_name) (rate(vllm:time_to_first_token_seconds_bucket{le="2.5"}[6h])) / clamp_min(sum by (model_name) (rate(vllm:time_to_first_token_seconds_count[6h])), 1e-9)
  - name: slo-ttft.alerts
    rules:
    - alert: LLMTTFTBudgetBurnFast
      expr: slo:ttft_bad_ratio:rate1h > (14.4 * 0.05) and slo:ttft_bad_ratio:rate5m > (14.4 * 0.05)
      labels: { severity: page, slo: ttft }
      annotations: { summary: "TTFT SLO 예산을 1시간에 2% 이상 소진 중 ({{ $labels.model_name }})" }
    - alert: LLMTTFTBudgetBurnSlow
      expr: slo:ttft_bad_ratio:rate6h > (6 * 0.05) and slo:ttft_bad_ratio:rate30m > (6 * 0.05)
      labels: { severity: page, slo: ttft }
      annotations: { summary: "TTFT SLO 예산을 6시간에 5% 이상 소진 중 ({{ $labels.model_name }})" }
    # 랩 확인용: 짧은 창으로 바로 울려 보기 (운영에는 넣지 않음)
    - alert: LLMTTFTBudgetBurnLabDemo
      expr: slo:ttft_bad_ratio:rate5m > (6 * 0.05)
      for: 1m
      labels: { severity: info, slo: ttft, lab: "true" }
      annotations: { summary: "랩 시연용: 최근 5분 TTFT 나쁜 비율 {{ $value | humanizePercentage }}" }

실습 21-6 · 오류 예산 패널

PromQL · 30일 남은 예산 (데이터가 30일 쌓여야 정확)
1 - (
  (1 - sum by (model_name) (increase(vllm:time_to_first_token_seconds_bucket{le="2.5"}[30d]))
     / sum by (model_name) (increase(vllm:time_to_first_token_seconds_count[30d])))
  / 0.05
)

20편 “서비스 개요” 대시보드에 이 값을 게이지로 추가하면, 9장의 예산 정책(예산이 남았으면 배포 진행, 소진되면 보류)을 대시보드 하나로 운영할 수 있습니다. 30일 창의 무거운 쿼리는 기록 규칙으로 하루 단위 집계를 만들어 두는 편이 좋습니다.

14확인 퀴즈

9문제.

15정리와 체크리스트

핵심 여섯 문장.

  1. 지표는 전체, 트레이스는 요청 하나, 로그는 정확한 사건. 트레이스 ID·예시·공통 속성으로 서로를 잇는다.
  2. OpenTelemetry는 SDK·OTLP·Collector·W3C 문맥 전파로 벤더와 무관하게 흐르고, LLM은 “오류·느린 요청 전부 + 나머지 일부” 뒷단 샘플링이 실용적이다.
  3. vLLM 스팬은 요청당 하나에 토큰·지연 분해 속성을 담고, 게이트웨이·라우터 스팬과 이어 구간별 원인을 찾는다.
  4. 로그에는 메타데이터, 본문은 기본 금지. 카나리 문자열 시험을 배포 점검에 넣는다.
  5. SLI = 좋은 사건 ÷ 전체 사건. 오류 예산 = 1 − 목표, 소진율 = 나쁜 비율 ÷ 예산.
  6. 다중 창 소진율 경보(14.4·6·3·1)로 예산을 의미 있게 태울 때만 사람을 깨우고, 예산 정책으로 배포를 결정한다.
