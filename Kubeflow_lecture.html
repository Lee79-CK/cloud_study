01 — 문제 정의

여기서 실패한 것은 모델링 실력이 아닙니다. 실패한 것은 재현성, 자원 관리, 자동화, 추적성, 배포 일관성 — 즉 엔지니어링 인프라입니다. 이 다섯 가지를 시스템으로 해결하려는 분야가 바로 MLOps입니다.

02 — 기초 개념

MLOps 기초 개념

MLOps는 ML + Dev + Ops. DevOps의 원칙(자동화·버전관리·CI/CD·모니터링)을 머신러닝에 적용한 것입니다. 다만 ML에는 DevOps에 없는 변수가 하나 더 있습니다 — 데이터.

DevOps — 관리 대상 2개
  • 코드 → Git으로 버전 관리
  • 인프라 → IaC로 버전 관리
  • 테스트가 결정적(deterministic): 같은 입력 = 같은 출력
  • 배포 후 코드는 스스로 나빠지지 않음
MLOps — 관리 대상 4개
  • 코드 + 인프라 + 데이터 + 모델
  • 테스트가 확률적: 정확도 91% "정도"
  • 배포 후 모델은 시간이 지나면 나빠짐 (데이터 드리프트)
  • 학습 환경과 서빙 환경의 피처 계산이 달라지는 문제(training/serving skew)
비유로 이해하기

일반 소프트웨어는 시계입니다. 한번 잘 조립하면 계속 정확히 돌아갑니다. ML 모델은 화분입니다. 심어놓고 끝이 아니라, 물(새 데이터)을 주고 상태(성능)를 보고 시들면 다시 심어야(재학습) 합니다. MLOps는 이 화분을 위한 자동 관수 시스템입니다.

ML 시스템의 진짜 구성비

Google의 유명한 논문 "Hidden Technical Debt in Machine Learning Systems"의 핵심 그림입니다. 실제 프로덕션 ML 시스템에서 모델 코드가 차지하는 비중은 놀랍도록 작습니다.

MLOps 성숙도 3단계

본인 팀이 어디에 있는지 판단하는 기준입니다. Kubeflow는 Level 1~2로 가기 위한 도구입니다.

구분Level 0 — 수동Level 1 — 학습 자동화Level 2 — CI/CD 자동화
작업 방식노트북 수동 실행파이프라인이 학습을 자동 수행코드 커밋 → 파이프라인 자동 빌드/배포
재학습 주기몇 달에 한 번, 사람이 판단스케줄 또는 트리거 기반드리프트 감지 시 자동 트리거
배포되는 것모델 파일 (.pkl)학습 파이프라인 전체파이프라인 + 컴포넌트 CI

Kubeflow 역할—Pipelines, Katib, Training Operator+ KServe, Model Registry, GitOps 연동
현실 조언

Level 0에서 바로 Level 2를 시도하면 대부분 실패합니다. 순서는 ① 학습 코드를 노트북에서 스크립트로 분리 → ② 파이프라인으로 묶기 → ③ 서빙 자동화 → ④ 모니터링/재학습 트리거입니다. Kubeflow 도입도 이 순서로 하세요.

03 — 비교

일반 MLOps 스택 vs Kubeflow

"MLOps 하려면 MLflow 쓰면 되는 거 아니에요?" — 자주 나오는 질문입니다. 차이를 정확히 이해하려면 어느 계층의 문제를 푸는 도구인지를 봐야 합니다.

흔히 쓰는 "조립형" 스택

많은 팀이 필요한 도구를 하나씩 붙여 씁니다. 이것도 완전히 정당한 방식입니다.

필요 기능조립형 스택에서 쓰는 도구Kubeflow의 대응 모듈
실험 추적MLflow Tracking, W&BKFP Metadata (MLMD) + Model Registry
워크플로 스케줄링Airflow, Dagster, PrefectKubeflow Pipelines
하이퍼파라미터 튜닝Optuna, Ray TuneKatib
분산 학습torchrun, Ray Train, HorovodTraining Operator
모델 서빙FastAPI + Docker, BentoML, TritonKServe

핵심 차이 3가지

① 실행 주체가 다르다

MLflow는 기록 도구입니다 — 학습을 어디서 돌릴지는 내 문제입니다. Kubeflow는 실행 플랫폼입니다 — "GPU 1장, 메모리 16Gi 주고 이 컨테이너 돌려"까지 책임집니다.

② 단위가 컨테이너다

Airflow의 Task는 보통 Python 함수(같은 워커 환경 공유). KFP의 Component는 항상 독립 컨테이너 = 독립 Pod입니다. 단계마다 다른 라이브러리 버전, 다른 GPU 요구가 가능합니다.

③ Kubernetes에 종속된다

이건 장점이자 비용입니다. K8s 클러스터가 없으면 시작 자체가 안 되고, 운영에는 Istio/cert-manager/스토리지 지식이 필요합니다. K8s가 이미 있는 조직에서 압도적으로 유리합니다.

언제 Kubeflow를 쓰고, 언제 쓰지 말아야 하나

쓰지 마세요
  • 팀이 1~3명이고 모델도 1~2개 — 오버엔지니어링입니다
  • Kubernetes 운영 경험이 팀에 전혀 없음
  • 학습이 노트북에서 10분이면 끝남
  • 클라우드 매니지드(SageMaker, Vertex AI)로 충분하고 비용도 괜찮음
  • MLflow + Airflow로 이미 잘 돌아가고 불만이 없음
쓰세요
  • 이미 사내 Kubernetes 클러스터를 운영 중
  • 여러 팀이 GPU를 공유하고 자원 분쟁이 발생
  • 온프레미스 / 폐쇄망 요구사항이 있음 (금융·공공·제조)
  • 학습 잡이 분산 학습이 필요한 규모
  • 클라우드 벤더 종속을 피하고 싶음
  • 모델이 10개 이상이고 재학습이 주기적으로 필요

04 — 선행 지식

먼저 알아야 할 Kubernetes 최소 지식

Kubeflow를 이해하려면 K8s 전문가가 될 필요는 없습니다. 그러나 이 6개 개념은 반드시 알아야 합니다. 이것만 알면 Kubeflow 문서가 읽히기 시작합니다.

01 Pod

컨테이너 1개(또는 몇 개)를 감싼 K8s의 최소 실행 단위. 파이프라인의 한 단계 = Pod 1개입니다. Pod은 일회용이라 죽으면 안에 있던 파일도 사라집니다. 그래서 산출물은 반드시 외부 저장소(S3/MinIO/PVC)에 써야 합니다.

02 Namespace

클러스터 안의 논리적 폴더. Kubeflow에서는 사용자 1명 = Namespace 1개가 기본 원칙입니다. 내 노트북, 내 파이프라인 실행, 내 모델이 모두 내 Namespace 안에 격리됩니다.

03 PVC (PersistentVolumeClaim)

Pod이 죽어도 살아남는 디스크 요청서. "20Gi 주세요"라고 쓰면 K8s가 볼륨을 붙여줍니다. 노트북의 /home/jovyan 이 바로 PVC입니다.

04 Resource requests / limits

requests는 "최소 보장", limits는 "최대 허용". GPU는 nvidia.com/gpu: 1 처럼 요청하며 GPU는 분할 불가이므로 requests=limits로 고정됩니다.

05 CRD & Operator ★

Kubeflow를 이해하는 열쇠입니다. CRD는 K8s에 새 리소스 타입을 추가하는 기능이고, Operator는 그 리소스를 보고 실제 작업을 하는 컨트롤러입니다. PyTorchJob, InferenceService, Experiment는 전부 Kubeflow가 추가한 CRD입니다.

06 Istio (서비스 메시)

모든 Pod에 사이드카를 붙여 트래픽을 통제합니다. Kubeflow는 이걸로 "A 사용자는 B의 노트북에 접근 불가"를 강제하고, KServe는 이걸로 카나리 트래픽 분할을 구현합니다. Kubeflow 장애의 상당수가 Istio 관련입니다.

CRD + Operator 를 비유로

CRD는 주문서 양식을 새로 만드는 것이고, Operator는 그 주문서를 읽는 주방장입니다. 내가 "PyTorchJob: 워커 4개, GPU 각 1장" 이라는 주문서를 제출하면(kubectl apply), Training Operator라는 주방장이 그것을 읽고 실제로 Pod 5개(마스터 1 + 워커 4)를 만들고 서로 통신하도록 환경변수를 세팅해줍니다. 나는 "무엇을 원하는지"만 선언하고, "어떻게 만드는지"는 Operator가 처리합니다. 이것이 K8s의 선언적(declarative) 모델입니다.

# 내 네임스페이스의 Pod 상태 — 가장 많이 쓰는 명령
kubectl get pods -n kubeflow-user-example-com

# Pod이 왜 안 뜨는지 확인 (Events 섹션을 반드시 볼 것)
kubectl describe pod <pod-name> -n <namespace>

# 컨테이너 로그 (학습 실패 원인 1순위 확인 경로)
kubectl logs <pod-name> -n <namespace> -f
kubectl logs <pod-name> -c main -n <namespace>   # 사이드카가 있을 때 컨테이너 지정

# 자원 사용량 (metrics-server 필요)
kubectl top pods -n <namespace>
kubectl top nodes

kubectl get crd | grep -E 'kubeflow|kserve|serving'

05 — 구조

Kubeflow 전체 아키텍처

Kubeflow의 공식 정의는 "Kubernetes 위에서 ML 워크플로를 간단하고, 이식 가능하고, 확장 가능하게 만드는 오픈소스 플랫폼"입니다. 풀어 쓰면 ML에 필요한 K8s Operator 모음집 + 통합 UI입니다.

요청 하나가 흐르는 경로

"노트북 만들기" 버튼을 눌렀을 때 실제로 벌어지는 일을 따라가면 아키텍처가 몸에 익습니다.

모든 요청은 단일 진입점을 통과합니다. 쿠키에 유효한 세션이 없으면 Dex(OIDC) 로그인 페이지로 리다이렉트됩니다.

인증 후 헤더 주입

인증에 성공하면 게이트웨이가 kubeflow-userid: user@example.com 헤더를 요청에 붙입니다. 이후 모든 컴포넌트는 이 헤더로 "누구인지"를 판단합니다.

Central Dashboard → Jupyter Web App

대시보드는 iframe으로 각 앱을 붙이는 껍데기입니다. 실제 노트북 생성 폼은 jupyter-web-app 이라는 별도 서비스가 제공합니다.

Notebook CR 생성

Web App은 K8s API에 kind: Notebook 리소스를 만듭니다. 여기서 웹 애플리케이션의 역할은 끝입니다.

Notebook Controller가 감지

컨트롤러가 새 Notebook CR을 보고 StatefulSet + Service + PVC를 생성합니다. Istio가 사이드카를 주입합니다.

AuthorizationPolicy 적용

내 Namespace의 노트북에는 "kubeflow-userid가 나와 일치하는 요청만 통과" 정책이 걸립니다. 그래서 남의 노트북 URL을 직접 쳐도 403이 납니다.

이해의 핵심

Kubeflow의 모든 기능은 이 패턴을 따릅니다: UI(또는 SDK)가 CR을 만들고 → Controller가 그것을 실제 K8s 리소스로 변환. 이 패턴을 알면 UI 없이 kubectl apply 만으로도 Kubeflow를 100% 쓸 수 있다는 것도 이해됩니다. 실제로 GitOps 자동화는 이 방식으로 합니다.

Profile CR을 하나 만들면 Profiles Controller가 다음을 자동으로 세팅합니다.

왜 로컬 Jupyter보다 나은가

로컬 / 공용 GPU 서버
  • "제 노트북에선 되는데요" 문제 상시 발생
  • GPU 점유를 슬랙으로 조율

  • 이미지 태그로 환경이 고정 → 누구나 동일 환경
  • GPU는 K8s 스케줄러가 배분 (쿼터로 상한 강제)

09 — 모듈 상세 · Pipelines · 핵심 모듈

Kubeflow Pipelines (KFP v2)

Kubeflow에서 하나만 배운다면 이것입니다. 다른 모듈을 안 쓰더라도 KFP만으로도 MLOps Level 1에 도달할 수 있습니다. 한 문장으로: "Python 함수를 컨테이너로 만들어, DAG 순서대로 K8s에서 실행하고, 모든 입출력을 기록하는 시스템"입니다.

5개 용어부터 정리

용어정체비유
Component파이프라인의 한 단계. 컨테이너 1개 = Pod 1개로 실행됨레시피의 한 조리 단계
Pipeline컴포넌트들의 연결 관계(DAG)를 정의한 것레시피 전체
Run파이프라인을 특정 파라미터로 실제 1회 실행한 인스턴스오늘 실제로 요리한 기록
Experiment관련된 Run들을 묶는 폴더"김치찌개 개선 프로젝트"
Artifact컴포넌트가 만든 산출물(데이터셋·모델·메트릭). 자동으로 저장·추적됨중간 결과물과 완성품

첫 파이프라인 — 3단계로 이해하기

KFP v2의 문법은 v1과 크게 달라졌습니다. v2를 기준으로 배우세요 (v1의 ContainerOp, func_to_container_op는 폐기 예정입니다).

# pip install kfp==2.9.0
from kfp import dsl, compiler

# ── 컴포넌트 = 컨테이너에서 실행될 독립 함수 ──────────────────

@dsl.component(packages_to_install=["pandas==2.2.2", "scikit-learn==1.5.0"])
def split_data(
    raw: Input[Dataset],            # 입력 아티팩트
    train: Output[Dataset],         # 출력 아티팩트 (경로는 KFP가 주입)
    test: Output[Dataset],
    test_size: float = 0.2,
):
    import pandas as pd
    from sklearn.model_selection import train_test_split

    df = pd.read_csv(raw.path)                       # .path 로 로컬 경로 접근
    tr, te = train_test_split(df, test_size=test_size, random_state=42)
    tr.to_csv(train.path, index=False)
    te.to_csv(test.path, index=False)

    # 메타데이터를 붙이면 UI에서 확인 가능 + 계보 추적에 활용
    train.metadata["rows"] = len(tr)

@dsl.component(packages_to_install=["pandas==2.2.2", "scikit-learn==1.5.0", "joblib"])
def train_model(
    train: Input[Dataset],
    model: Output[Model],
    metrics: Output[Metrics],               # 스칼라 메트릭 (UI에서 Run 간 비교 가능)
    cm: Output[ClassificationMetrics],      # 혼동행렬/ROC 시각화
    n_estimators: int = 200,
    max_depth: int = 8,
) -> float:
    import pandas as pd, joblib
    from sklearn.ensemble import RandomForestClassifier
    from sklearn.model_selection import cross_val_predict
    from sklearn.metrics import roc_auc_score, confusion_matrix

    df = pd.read_csv(train.path)
    X, y = df.drop(columns=["label"]), df["label"]

    clf = RandomForestClassifier(n_estimators=n_estimators,
                                 max_depth=max_depth, random_state=42)
    pred = cross_val_predict(clf, X, y, cv=5, method="predict_proba")[:, 1]
    auc = float(roc_auc_score(y, pred))

    clf.fit(X, y)
    joblib.dump(clf, model.path)             # 모델 파일 저장

    # 메트릭 기록 → KFP UI의 Run 비교 테이블에 컬럼으로 나타난다
    metrics.log_metric("auc", auc)
    metrics.log_metric("n_rows", len(df))
    cm.log_confusion_matrix(["neg", "pos"],
                            confusion_matrix(y, (pred > 0.5)).tolist())

    model.metadata["framework"] = "sklearn"
    model.metadata["auc"] = auc
    return auc                               # 조건 분기에 쓰기 위해 값도 반환

Artifact vs Parameter — 가장 흔한 실수

기억할 규칙

Parameter(int, str, float, bool, list, dict)는 값이 메타데이터 DB에 그대로 저장됩니다. 여기에 DataFrame을 JSON으로 넣으면 DB가 터지고 UI가 멈춥니다.

Artifact(Dataset, Model, Metrics, HTML, Markdown)는 파일이 오브젝트 스토리지에 저장되고 DB에는 경로만 남습니다. 데이터·모델은 예외 없이 Artifact를 쓰세요.

캐싱 — KFP의 숨은 킬러 기능

KFP는 (컴포넌트 이미지 + 코드 해시 + 입력값)이 이전 실행과 동일하면 그 단계를 건너뛰고 이전 산출물을 그대로 연결합니다. 전처리 3시간짜리 파이프라인을 디버깅할 때, 마지막 단계만 고쳐서 재실행하면 몇 초 안에 그 지점까지 도달합니다. 단, 두 가지를 주의하세요.

  • 외부 상태를 읽는 컴포넌트는 캐시를 끄세요. "오늘의 데이터를 DB에서 조회"하는 컴포넌트는 입력값이 같아도 결과가 달라야 합니다.
  • 랜덤성이 있는 학습은 캐시를 끄는 편이 안전합니다. 재현이 필요하다면 시드를 파라미터로 노출하세요.

Training Operator — 분산 학습

GPU 1장으로 3일 걸리는 학습을 GPU 8장으로 나눠 돌리려면, 8개 프로세스가 서로를 찾아 통신해야 합니다. Training Operator는 그 "서로를 찾는" 과정(랑데부, 환경변수 세팅, 포트 개방, 재시작)을 대신 처리합니다.

지원하는 CRD

PyTorchJob

가장 많이 씁니다. DDP / FSDP / DeepSpeed 모두 이걸로 실행. MASTER_ADDR, WORLD_SIZE, RANK를 자동 주입.

TFJob

TensorFlow. Chief / Worker / PS / Evaluator 역할 구분. TF_CONFIG를 자동 생성.

XGBoostJob

부스팅 모델의 분산 학습. 정형 데이터 대용량 학습에 사용.

MPIJob

Horovod 등 MPI 기반. mpirun 실행을 위한 hostfile을 자동 구성.

PaddleJob / JAXJob

해당 프레임워크 사용 시. 구조는 PyTorchJob과 유사.

TrainJob 신규

Kubeflow Trainer v2에서 도입된 통합 API. 프레임워크별 CRD를 하나로 추상화하는 방향.

@dsl.component(base_image="python:3.11-slim",
               packages_to_install=["kubernetes==30.1.0"])
def run_distributed_training(
    image: str, epochs: int, workers: int, gpus_per_worker: int,
    namespace: str, job_name: str,
) -> str:
    import time
    from kubernetes import client, config
    config.load_incluster_config()
    api = client.CustomObjectsApi()

    def replica(n):
        return {
            "replicas": n, "restartPolicy": "OnFailure",
            "template": {
              "metadata": {"annotations": {"sidecar.istio.io/inject": "false"}},
              "spec": {"containers": [{
                  "name": "pytorch", "image": image,
                  "command": ["torchrun",
                              f"--nproc_per_node={gpus_per_worker}",
                              "/app/train.py", f"--epochs={epochs}"],
                  "resources": {"limits": {"nvidia.com/gpu": gpus_per_worker}},
              }]}
            },
        }

    body = {
        "apiVersion": "kubeflow.org/v1", "kind": "PyTorchJob",
        "metadata": {"name": job_name, "namespace": namespace},
        "spec": {"pytorchReplicaSpecs": {
            "Master": replica(1), "Worker": replica(workers)}},
    }
    api.create_namespaced_custom_object(
        "kubeflow.org", "v1", namespace, "pytorchjobs", body)

    # 완료 폴링 — 이 컴포넌트는 CPU만 쓰므로 대기 비용이 저렴하다
    while True:
        st = api.get_namespaced_custom_object_status(
            "kubeflow.org", "v1", namespace, "pytorchjobs", job_name)
        conds = {c["type"]: c["status"]
                 for c in st.get("status", {}).get("conditions", [])}
        if conds.get("Succeeded") == "True":
            return "succeeded"
        if conds.get("Failed") == "True":
            raise RuntimeError(f"PyTorchJob {job_name} 실패")
        time.sleep(20)

# pipeline.py — 프로덕션 재학습 파이프라인
from kfp import dsl, compiler, kubernetes
from kfp.dsl import Input, Output, Dataset, Model, Metrics

BASE = "registry.company.com/ml/base:py311-1.2.0"   # 공통 이미지 (버전 고정)


@dsl.component(base_image=BASE)
def ingest(source_uri: str, out: Output[Dataset]) -> int:
    import pandas as pd
    df = pd.read_parquet(source_uri)
    df.to_parquet(out.path)
    out.metadata["rows"] = len(df)
    out.metadata["source"] = source_uri
    return len(df)


@dsl.component(base_image=BASE)
def preprocess(raw: Input[Dataset],
               train: Output[Dataset], holdout: Output[Dataset]):
    import pandas as pd
    from sklearn.model_selection import train_test_split
    df = pd.read_parquet(raw.path)

    # ★ 전처리 로직은 사내 패키지로 분리해 서빙과 공유한다 (skew 방지)
    from company_ml.features import build_features
    df = build_features(df)

    tr, ho = train_test_split(df, test_size=0.2, stratify=df["label"],
                              random_state=42)
    tr.to_parquet(train.path); ho.to_parquet(holdout.path)


@dsl.component(base_image=BASE)
def train_model(train: Input[Dataset], model: Output[Model],
                metrics: Output[Metrics],
                n_estimators: int = 400, learning_rate: float = 0.05):
    import pandas as pd, joblib, json, os
    from lightgbm import LGBMClassifier
    df = pd.read_parquet(train.path)
    X, y = df.drop(columns=["label"]), df["label"]

    clf = LGBMClassifier(n_estimators=n_estimators,
                         learning_rate=learning_rate, random_state=42)
    clf.fit(X, y)

    os.makedirs(model.path, exist_ok=True)              # KServe는 디렉토리를 기대
    joblib.dump(clf, os.path.join(model.path, "model.joblib"))
    with open(os.path.join(model.path, "features.json"), "w") as f:
        json.dump(list(X.columns), f)                    # 피처 순서 고정 (중요)

    metrics.log_metric("train_rows", len(df))
    model.metadata["framework"] = "lightgbm"


@dsl.component(base_image=BASE)
def evaluate(model: Input[Model], holdout: Input[Dataset],
             metrics: Output[Metrics]) -> float:
    import pandas as pd, joblib, os
    from sklearn.metrics import roc_auc_score, f1_score
    clf = joblib.load(os.path.join(model.path, "model.joblib"))
    df = pd.read_parquet(holdout.path)
    X, y = df.drop(columns=["label"]), df["label"]
    proba = clf.predict_proba(X)[:, 1]

    auc = float(roc_auc_score(y, proba))
    metrics.log_metric("holdout_auc", auc)
    metrics.log_metric("holdout_f1", float(f1_score(y, proba > 0.5)))
    return auc


@dsl.component(base_image=BASE, packages_to_install=["requests"])
def notify_slack(status: dsl.PipelineTaskFinalStatus, webhook: str):
    """ExitHandler용. status는 KFP가 자동 주입한다 (직접 넘기지 않는다)."""
    import requests
    text = (f"[churn-e2e] 상태={status.state} "
            f"job={status.pipeline_job_name} "
            f"error={status.error_message or '-'}")
    requests.post(webhook, json={"text": text}, timeout=10)

@dsl.pipeline(name="churn-e2e",
              description="수집→검증→학습→평가→게이트→등록→배포")
def churn_pipeline(
    source_uri: str,
    model_name: str = "churn-classifier",
    version: str = "1.3.0",
    auc_gate: float = 0.87,
    min_rows: int = 50000,
    slack_webhook: str = "",
):
    """실패해도 항상 알림이 가도록 ExitHandler로 전체를 감싼다"""
    notify = notify_slack(webhook=slack_webhook)
    with dsl.ExitHandler(notify, name="always-notify"):

        ing = ingest(source_uri=source_uri)
        ing.set_caching_options(False)          # 외부 데이터는 캐시 금지

        val = validate_data(raw=ing.outputs["out"], min_rows=min_rows)

        # 검증 통과 시에만 이후 단계 진행
        with dsl.If(val.outputs["Output"] == True, name="data-ok"):

            pre = preprocess(raw=ing.outputs["out"])
            pre.set_cpu_limit("8").set_memory_limit("32Gi")

            tr = train_model(train=pre.outputs["train"])
            tr.set_memory_limit("32Gi").set_cpu_limit("8")
            tr.set_accelerator_type("nvidia.com/gpu").set_accelerator_limit(1)
            tr.set_retry(num_retries=2, backoff_duration="120s")
            tr.set_caching_options(False)
            kubernetes.add_toleration(tr, key="nvidia.com/gpu",
                                      operator="Exists", effect="NoSchedule")

            ev = evaluate(model=tr.outputs["model"],
                          holdout=pre.outputs["holdout"])

            # ★ 품질 게이트 — 이 조건이 자동 배포의 안전장치다
            with dsl.If(ev.outputs["Output"] >= auc_gate, name="quality-gate"):
                # register: 모델을 Model Registry에 등록하고 최종 URI를 반환 (13장 참고)
                rg = register(model=tr.outputs["model"],
                              model_name=model_name, version=version,
                              auc=ev.outputs["Output"])
                dp = deploy(model_uri=rg.output, model_name=model_name,
                            canary_percent=10)
                dp.after(rg)


if __name__ == "__main__":

# 데이터 검증은 "쓰레기 데이터로 학습된 모델의 자동 배포"를 막는 유일한 방어선이다.

@dsl.component(base_image=BASE,
               packages_to_install=["pandas==2.2.2"])
def validate_data(raw: Input[Dataset],
                  report: Output[dsl.HTML],       # UI에 렌더링되는 리포트
                  min_rows: int = 50000,
                  max_null_ratio: float = 0.05) -> bool:
    import pandas as pd
    df = pd.read_parquet(raw.path)
    issues = []

    # 1) 행 수 검사 — 데이터 파이프라인 장애 감지
    if len(df) < min_rows:
        issues.append(f"행 수 부족: {len(df):,} < {min_rows:,}")

    # 2) 필수 컬럼 존재
    required = {"customer_id", "label", "tenure", "monthly_charges"}
    missing = required - set(df.columns)
    if missing:
        issues.append(f"필수 컬럼 누락: {sorted(missing)}")

    # 3) 결측 비율
    for col in df.columns:
        ratio = df[col].isna().mean()
        if ratio > max_null_ratio:
            issues.append(f"{col} 결측률 {ratio:.1%} 초과")

    # 4) 레이블 분포 급변 (데이터 파이프라인 버그의 대표 증상)
    if "label" in df.columns:
        pos = df["label"].mean()
        if not (0.02 <= pos <= 0.40):
            issues.append(f"양성 비율 이상: {pos:.2%}")

    # 5) 중복 키
    if "customer_id" in df.columns:
        dup = df["customer_id"].duplicated().sum()
        if dup:
            issues.append(f"중복 customer_id {dup:,}건")

    ok = len(issues) == 0
    rows = "".join(f"<li>{i}</li>" for i in issues) or "<li>이상 없음</li>"
    with open(report.path, "w") as f:
        f.write(f"<h3>데이터 검증: {'PASS' if ok else 'FAIL'}</h3>"
                f"<p>행 {len(df):,} / 컬럼 {len(df.columns)}</p><ul>{rows}</ul>")

    print(f"validation ok={ok} issues={issues}")
    return ok
@dsl.component(base_image=BASE,
               packages_to_install=["kubernetes==30.1.0"])
def deploy(model_uri: str, model_name: str,
           canary_percent: int = 10) -> str:
    """InferenceService를 생성하거나 기존 것을 새 버전으로 업데이트한다"""
    import os, time
    from kubernetes import client, config
    from kubernetes.client.rest import ApiException

    config.load_incluster_config()
    api = client.CustomObjectsApi()
    ns = open("/var/run/secrets/kubernetes.io/serviceaccount/namespace").read()

    spec = {
        "apiVersion": "serving.kserve.io/v1beta1",
        "kind": "InferenceService",
        "metadata": {"name": model_name, "namespace": ns,
                     "annotations": {"autoscaling.knative.dev/target": "10"}},
        "spec": {"predictor": {
            "serviceAccountName": "default-editor",
            "minReplicas": 2, "maxReplicas": 10,
            "canaryTrafficPercent": canary_percent,
            "model": {
                "modelFormat": {"name": "sklearn"},
                "storageUri": model_uri,
                "resources": {"requests": {"cpu": "1", "memory": "2Gi"},
                              "limits": {"cpu": "2", "memory": "4Gi"}},
            },
        }},
    }

    args = ("serving.kserve.io", "v1beta1", ns, "inferenceservices")
    try:
        api.create_namespaced_custom_object(*args, spec)
        print("InferenceService 생성")
    except ApiException as e:
        if e.status != 409:
            raise
        api.patch_namespaced_custom_object(*args, model_name, spec)
        print(f"기존 서비스를 canary {canary_percent}%로 업데이트")

    # Ready 대기 — 여기서 실패하면 파이프라인이 실패해야 한다
    for _ in range(60):
        st = api.get_namespaced_custom_object_status(*args, model_name)
        conds = {c["type"]: c["status"]
                 for c in st.get("status", {}).get("conditions", [])}
        if conds.get("Ready") == "True":
            url = st["status"]["url"]
            print(f"배포 완료: {url}")
            return url
        time.sleep(10)
    raise TimeoutError("InferenceService Ready 실패 — describe isvc로 확인")

현장에서 실제로 마주치는 증상들입니다. 제목을 눌러 원인과 해결책을 확인하세요. 거의 모든 항목이 "Kubeflow 문제"가 아니라 "Kubernetes 문제"라는 점에 주목하세요.

진단: kubectl describe pod <pod> → Events 섹션을 봅니다.

원인별 해결:

  • Insufficient nvidia.com/gpu → GPU가 모두 점유 중. 유휴 노트북을 컬링하거나 우선순위(PriorityClass)를 조정
  • exceeded quota → Profile의 ResourceQuota 초과. kubectl describe quota -n <ns>
  • node(s) had untolerated taint → GPU 노드에 taint가 있음. tolerations 추가
  • pod has unbound PersistentVolumeClaims → StorageClass 문제. kubectl get pvc,sc

원인: Istio 사이드카(istio-proxy)가 종료되지 않아 Pod 전체가 Completed로 전환되지 않습니다. Kubeflow 초보자가 가장 많이 겪는 문제입니다.

해결: Job Pod 템플릿에 annotations: {sidecar.istio.io/inject: "false"}를 추가합니다. Katib Trial, PyTorchJob, Argo Workflow 모두 동일합니다.

확인: kubectl get pod <pod> -o jsonpath='{.spec.containers[*].name}' 로 istio-proxy가 있는지 봅니다.

원인 1 — 파라미터에 대용량 데이터: DataFrame이나 큰 JSON을 str 파라미터로 넘기면 메타데이터 DB에 전문이 저장됩니다. 반드시 Artifact로 바꾸세요.

원인 2 — Run이 수만 건 누적: MySQL이 비대해집니다. 오래된 Run과 Argo Workflow CR을 주기적으로 정리하세요. ttlStrategy를 설정하면 자동 삭제됩니다.

원인 3 — MinIO 디스크 포화: 아티팩트가 계속 쌓입니다. 오브젝트 라이프사이클 정책으로 30~90일 후 삭제하도록 설정합니다.

원인: ① import를 함수 밖에 썼다 ② packages_to_install에 패키지를 안 넣었다 ③ 폐쇄망이라 pip이 실패했다.

권장 해결: 프로덕션에서는 packages_to_install을 쓰지 마세요. 매 실행마다 pip이 도는 것은 느리고 불안정합니다. 필요한 패키지를 미리 포함한 커스텀 base_image를 만들어 태그로 고정하는 것이 정답입니다.

진단 순서: ① kubectl describe isvc 의 conditions ② storage-initializer 컨테이너 로그(모델 다운로드) ③ kserve-container 로그(모델 로딩).

빈발 원인: S3 자격증명 누락(serviceAccountName 확인) · 파일명 규칙 불일치(sklearn은 model.joblib) · storageUri가 파일이 아닌 디렉토리를 가리켜야 함 · scikit-learn 버전 불일치로 pickle 로딩 실패.

원인: pip install이 컨테이너 내부에 설치되며, PVC로 보존되는 것은 /home/jovyan뿐입니다.

해결: 임시로는 pip install --target=/home/jovyan/.local/lib/python3.11/site-packages. 근본 해결은 커스텀 이미지입니다. 이 문제가 반복된다면 이미지를 만들 시점이라는 신호입니다.

이건 버그가 아니라 설계입니다. Profiles의 멀티테넌시가 정상 작동하는 것입니다.

협업하려면: UI의 "Manage Contributors"로 초대하거나, RoleBinding + AuthorizationPolicy를 함께 만듭니다. 둘 중 하나만 만들면 UI는 보이는데 API가 403이 나는 혼란스러운 상태가 됩니다.

가장 큰 원인: KFP v1 → v2 마이그레이션. ContainerOp, func_to_container_op, dsl.Condition이 dsl.If로 바뀌는 등 호환성이 깨지는 변경이 있습니다.

예방: ① 스테이징 클러스터에서 먼저 검증 ② manifests 버전을 반드시 태그로 고정 ③ 업그레이드 전 MySQL·MLMD·MinIO를 백업 ④ 컴파일된 IR YAML을 Git에 보관해 롤백 가능하게 유지.

현실적인 조합

실무에서는 배타적 선택이 아니라 조합이 흔합니다. 자주 보이는 패턴은 KFP(실행 오케스트레이션) + MLflow(실험 추적 UI) + KServe(서빙) + Prometheus/Grafana(관측)입니다. Kubeflow의 모든 모듈을 다 쓸 필요는 없습니다. KFP와 KServe만으로도 대부분의 조직은 충분합니다.

학습 로드맵 & 최종 퀴즈

4주 학습 계획

1주차 — Kubernetes 기초

Pod / Deployment / Service / PVC / CRD 개념. kubectl 로 실제 리소스를 만들고 삭제하며 손에 익힙니다. kind로 로컬 클러스터 구성.

2주차 — KFP만 집중

KFP standalone 설치 → 컴포넌트 3개짜리 파이프라인 작성 → Artifact와 Parameter 차이 체감 → 캐싱 동작 확인 → 조건 분기와 병렬 반복 실습.

3주차 — 학습과 서빙

Katib으로 HPO 1회 실행 → PyTorchJob으로 2노드 분산 학습 → KServe로 모델 배포 후 curl 호출 → 카나리 10%를 걸고 롤백까지 경험.

4주차 — 통합과 운영

E2E 파이프라인 완성(품질 게이트 포함) → 정기 실행 스케줄 등록 → 일부러 실패시켜 트러블슈팅 → 모니터링 대시보드 구성.

실습 체크리스트

직접 해봐야 아는 것들입니다. 항목을 눌러 완료 표시하세요.

  • ☐kind로 로컬 K8s 클러스터를 만들고 kubectl get nodes가 동작하게 했다
  • ☐KFP를 설치하고 UI에 접속했다
  • ☐컴포넌트 2개를 연결한 파이프라인을 컴파일해 실행했다
  • ☐일부러 import를 함수 밖에 써서 NameError를 재현해봤다
  • ☐Artifact로 데이터를 전달하고 UI에서 산출물을 확인했다
  • ☐같은 파이프라인을 두 번 실행해 캐싱이 동작하는 것을 확인했다
  • ☐dsl.If로 품질 게이트를 만들어 배포가 차단되는 것을 확인했다
  • ☐Katib Experiment를 실행해 최적 파라미터를 얻었다
  • ☐PyTorchJob으로 워커 2개 분산 학습을 성공시켰다
  • ☐KServe로 모델을 배포하고 curl로 예측을 받았다
  • ☐카나리 트래픽 10%를 걸고 다시 0%로 롤백했다
  • ☐정기 실행(recurring run)을 등록해 자동 재학습을 확인했다
  • ☐Pod이 Pending인 원인을 describe로 스스로 찾아냈다

FINAL 01

정답 C. 컴포넌트는 서로 다른 Pod이므로 메모리도 로컬 디스크도 공유하지 않습니다(A, D 불가). B는 문법적으로는 동작하지만 메타데이터 DB에 데이터 전문이 저장되어 시스템을 망가뜨립니다. Artifact는 오브젝트 스토리지를 경유하며, 계보 추적까지 자동으로 남습니다.
FINAL 02
Katib Trial이 학습을 끝냈는데도 Job이 Complete되지 않고 Running으로 남아 있습니다. 가장 유력한 원인은?
정답 B. Kubeflow 초보자가 가장 자주 겪는 문제입니다. Job 계열 워크로드의 Pod 템플릿에 sidecar.istio.io/inject: "false" 어노테이션을 붙이세요. 참고로 A(지표 이름 오타)는 다른 증상을 만듭니다 — Trial은 정상 종료되지만 observation이 비어 최적값을 찾지 못합니다.
FINAL 03
"Kubeflow를 도입했는데 팀이 안 쓴다"는 상황에서 가장 먼저 점검할 것은?
정답 B. MLOps 도구 도입 실패의 대부분은 기술 문제가 아니라 도입 순서와 동기 부여의 문제입니다. "GPU를 기다리는 시간이 아깝다"는 고통이 있으면 Notebooks + 쿼터부터, "재학습이 귀찮다"는 고통이 있으면 KFP recurring run부터 시작하세요. 사용자가 첫 성공 경험을 빠르게 얻는 것이 무엇보다 중요합니다.
