심층 해부

기초 강의가 "OpenShift는 무엇이 다른가"에 답했다면, 이 강의는 "그래서 안에서 무슨 일이 벌어지고 있는가"에 답합니다. API 요청이 etcd에 닿기까지의 경로, MachineConfig가 노드를 재부팅시키는 메커니즘, OVN 논리 스위치를 통과하는 패킷의 홉, Operator의 reconcile 루프까지 — 콘솔 뒤편의 동작 원리를 열어서 봅니다.

난이도 ★★★ 심화 22개 섹션 인터랙티브 데모 8종 종합 퀴즈 15문항 읽기 약 150분 기준 OCP 4.14~4.16
선행 지식 — 이 강의는 Pod/Deployment/Service/Ingress를 직접 다뤄본 경험, oc CLI 기본 사용, SCC와 Operator의 존재 이유를 이해하고 있다고 가정합니다. 위 내용이 낯설다면 기초 강의를 먼저 보시는 것을 권합니다. 반대로 이미 프로덕션 클러스터를 운영 중이라면 관심 섹션부터 골라 읽어도 무방하게 구성했습니다.
SECTION 01

API 요청의 생애 — 컨트롤 플레인 내부

oc create -f pod.yaml를 실행하면 무슨 일이 벌어질까요? 초보 단계에서는 "API 서버에 보내면 스케줄러가 노드에 배치한다" 정도로 충분합니다. 하지만 프로덕션에서 원인 불명의 거부(403, admission webhook denied)를 디버깅하려면 요청이 통과하는 여섯 개의 관문을 정확히 알아야 합니다.

인증 — OpenShift만의 OAuth 계층

바닐라 Kubernetes에는 사용자 객체가 없습니다. 인증서의 CN을 사용자 이름으로, O를 그룹으로 해석하는 관습이 있을 뿐입니다. OpenShift는 여기에 클러스터 내장 OAuth 서버를 얹어 User, Identity, Group, OAuthAccessToken을 실제 API 리소스로 만들었습니다.

인증 주체(subject)의 세 갈래 — 로그 해석의 기본
# 1) 사람 사용자 — OAuth 서버가 발급한 토큰
oc whoami          # → cheolkyu
oc whoami --show-token   # → sha256~AbCd...  (OAuthAccessToken)

# 2) ServiceAccount — 워크로드용. 이름 규칙이 고정되어 있다
#    system:serviceaccount:<namespace>:<name>
oc whoami --as=system:serviceaccount:app-prod:builder

# 3) 노드 — kubelet은 Node 인가 모드로 제한된다
#    system:node:worker-01  (그룹: system:nodes)

# 감사 로그에서 실제 주체 확인 — 403 디버깅의 출발점
oc adm node-logs --role=master --path=kube-apiserver/audit.log \
  | jq 'select(.responseStatus.code==403)
      | {user:.user.username, verb:.verb, res:.objectRef.resource, ns:.objectRef.namespace}'
토큰 접두사가 알려주는 것

sha256~로 시작하면 OAuth 사용자 토큰, eyJ로 시작하면 JWT(ServiceAccount 바운드 토큰)입니다. OCP 4.11 이후 SA 토큰은 기본적으로 바운드 토큰(수명·audience 제한)이라 Secret에 영구 저장된 예전 토큰과 동작이 다릅니다. 외부 시스템에 SA 토큰을 붙여 쓰다가 만료로 깨지는 사고가 여기서 자주 나옵니다.

인가 — SubjectAccessReview로 추측을 끝내기

"권한이 있는 것 같은데 왜 안 되지?"를 논쟁하지 마십시오. API 서버에 직접 물어보면 됩니다. oc auth can-i는 SubjectAccessReview API의 얼굴이며, 실제 인가 결정 로직을 그대로 태웁니다. 

# 내가 이 행위를 할 수 있는가
oc auth can-i create pods -n app-prod

# 특정 사용자/SA를 대신해서 검사 (impersonate 권한 필요)
oc auth can-i delete deployments -n app-prod \
  --as=dev-kim --as-group=team-a

# 해당 네임스페이스에서 내가 가진 모든 권한 목록
oc auth can-i --list -n app-prod
# 역방향 조회 — OpenShift 전용. 감사 대응에 매우 유용
oc adm policy who-can delete pods -n app-prod
oc adm policy who-can use scc privileged

# 특정 SA가 어떤 SCC를 받게 될지 조회
oc adm policy scc-subject-review \
  -z system:serviceaccount:app-prod:default -f pod.yaml

# 이미 실행 중인 Pod가 어떤 SCC로 승인됐는지
oc get pod mypod -o jsonpath='{.metadata.annotations.openshift\.io/scc}'
apiVersion: authorization.k8s.io/v1
kind: SubjectAccessReview
spec:
  user: dev-kim
  groups: ["team-a"]
  resourceAttributes:
    namespace: app-prod
    verb: create
    group: apps
    resource: deployments
# status.allowed / status.reason 으로 결정과 근거를 반환한다.
# 사내 셀프서비스 포털에서 "이 사용자 권한 있나?"를 조회할 때
# 이 API를 호출하는 것이 정석 패턴이다.

Admission — 여기서 대부분의 "이상한 일"이 벌어진다

Admission 단계는 Mutating이 먼저, Validating이 나중입니다. 이 순서 때문에 "내가 쓴 YAML과 실제 저장된 객체가 다르다"는 현상이 생깁니다. OpenShift에서 가장 흔한 예가 SCC입니다. SCC는 Mutating 단계에서 Pod에 runAsUser, seLinuxOptions, fsGroup을 주입합니다.

Admission과 Quota 검증은 Pod 생성 시점에 걸립니다. Deployment를 만들면 API 서버는 Deployment 객체만 검증하므로 created가 뜹니다. 실제 거부는 ReplicaSet 컨트롤러가 Pod를 만들려 할 때 발생하고, 그 에러는 ReplicaSet의 이벤트에만 남습니다. oc describe deploy가 아니라 oc describe rs 또는 oc get events --sort-by=.lastTimestamp를 보십시오.

API 서버는 상태를 갖지 않는다 — Watch와 informer

컨트롤 플레인 확장성의 핵심은 모든 컨트롤러가 폴링이 아니라 Watch로 동작한다는 점입니다. etcd에 객체가 저장되면 API 서버가 watch 스트림으로 이벤트를 팬아웃하고, 각 컨트롤러의 informer가 로컬 캐시를 갱신한 뒤 작업 큐에 넣습니다. 이 구조를 이해하면 다음 두 가지가 설명됩니다.

  • resourceVersion 충돌 — 두 컨트롤러가 같은 객체를 동시에 수정하면 the object has been modified 에러가 납니다. 그래서 Operator는 항상 재시도 루프를 가집니다(섹션 14).
  • API 서버 부하는 watch 수에 비례 — 노드 수백 대 규모에서는 informer가 만드는 watch 커넥션과 LIST 폭풍이 실제 병목입니다. 커스텀 컨트롤러를 잘못 만들면 (예: reconcile마다 전체 LIST) 클러스터 전체가 느려집니다.
MLOps 관점 메모

대규모 학습 잡을 큐잉하는 시스템(Kueue, Volcano, Ray)은 초당 수백 개의 Pod를 생성·삭제합니다. 이때 병목은 GPU가 아니라 API 서버와 etcd가 되는 경우가 많습니다. 잡 단위를 잘게 쪼개기 전에 apiserver_request_duration_seconds와 etcd fsync 지연을 먼저 보십시오.

SECTION 02

MCO와 RHCOS — 노드는 어떻게 변경되는가

OpenShift에서 노드에 SSH로 들어가 /etc/sysctl.conf를 고치면 다음 재부팅에 원복됩니다. RHCOS는 불변(immutable) 지향 OS이고, 노드 설정의 유일한 진실은 MachineConfig 객체입니다. 이것을 이해하지 못하면 커널 파라미터 하나 바꾸는 데 며칠을 씁니다.

MachineConfig는 병합된다 — rendered config의 정체

핵심 개념입니다. 사용자가 만든 MachineConfig는 직접 적용되지 않습니다. controller가 같은 풀에 속한 모든 MC를 metadata.name의 사전순으로 병합해 rendered-worker-<hash>라는 단일 config를 만들고, MCD는 그것만 봅니다. 그래서 관례적으로 이름 앞에 99-, 50- 같은 숫자 접두사를 붙여 우선순위를 통제합니다.

Degraded 복구 절차

MCP가 DEGRADED=True가 되면 롤링이 전면 중단됩니다. 순서는 ① oc describe mcp worker에서 degraded 노드 이름 확인 → ② 해당 노드의 MCD 로그 확인 → ③ 대개 "파일이 이미 존재하고 내용이 다름" 이슈이므로 overwrite: true를 추가하거나 노드에서 수동 생성한 파일을 제거 → ④ oc annotate node <n> machineconfiguration.openshift.io/state=Done --overwrite는 최후의 수단이며 원인을 모른 채 쓰면 설정 드리프트를 남깁니다.

SECTION 03

CVO와 업그레이드 전략

OpenShift 업그레이드가 바닐라와 결정적으로 다른 지점은 클러스터가 스스로를 업그레이드한다는 것입니다. Cluster Version Operator(CVO)가 릴리스 이미지에 담긴 매니페스트를 순서대로 적용하고, 30여 개의 second-level operator가 각자 담당 컴포넌트를 갱신합니다. 관리자가 하는 일은 목표 버전을 지정하고, 멈춘 지점을 진단하는 것입니다.

ClusterVersion과 ClusterOperator — 두 개의 체온계

EUS-to-EUS 업그레이드 — 워커 재부팅을 한 번으로

4.14 → 4.16처럼 마이너를 두 단계 올릴 때, 순진하게 하면 워커 노드가 두 번 재부팅됩니다. 노드가 100대라면 재부팅 시간만 며칠입니다. EUS-to-EUS 절차는 워커 풀을 pause한 상태로 컨트롤 플레인만 두 번 올린 뒤, 마지막에 워커를 한 번만 재부팅하는 기법입니다.

EUS-to-EUS (4.14 → 4.16) 절차 요약
# 0) 전제: 모든 co가 정상, etcd 백업 완료, MCP degraded 없음
oc get co | grep -v "True.*False.*False"   # 비어 있어야 정상

# 1) 워커 풀 정지 — 이것이 핵심
oc patch mcp worker --type=merge -p '{"spec":{"paused":true}}'
# infra, storage 등 커스텀 풀도 모두 정지시켜야 한다

# 2) 4.15로 (컨트롤 플레인만 갱신됨)
oc adm upgrade channel eus-4.16
oc adm upgrade --to=4.15.30
# 완료 대기 — clusterversion Available=True, Progressing=False

# 3) 4.16으로
oc adm upgrade --to=4.16.7

# 4) 워커 풀 해제 → 이제 한 번만 재부팅된다
oc patch mcp worker --type=merge -p '{"spec":{"paused":false}}'

# 주의사항
# - kubelet은 API 서버보다 최대 2 마이너 낮은 것까지만 지원(skew).
#   4.14 kubelet + 4.16 apiserver = 정확히 한계선이므로 3단계 이상 건너뛰기는 불가.
# - 풀이 정지된 동안 보안 패치와 인증서 갱신도 노드에 반영되지 않는다.
#   기간을 최소화하고, 정지 상태로 방치하지 말 것.
업그레이드 전 반드시 확인할 세 가지

① 제거된 API — oc get apirequestcounts로 향후 삭제될 API를 아직 쓰는 워크로드를 찾습니다. 4.x에서 AdminAckRequired 조건이 뜨면 관리자가 명시적으로 ack하지 않으면 업그레이드가 시작조차 안 됩니다.
② Operator 호환성 — OLM으로 설치한 오퍼레이터는 목표 OCP 버전을 지원하는 채널로 미리 옮겨야 합니다. oc get csv -A와 각 오퍼레이터의 호환 매트릭스를 대조하십시오.
③ 인증서 만료 — 클러스터가 오래 정지되어 있었다면 kubelet 서빙 인증서가 만료돼 노드가 NotReady로 떨어질 수 있습니다. oc get csr에 Pending이 쌓였는지 확인하십시오.

API 폐기 대응 — 업그레이드 차단 해제
# 다음 버전에서 제거될 API를 아직 호출하는 주체 찾기
oc get apirequestcounts -o json | jq -r '.items[]
  | select(.status.removedInRelease != null)
  | "\(.metadata.name) removedIn=\(.status.removedInRelease)"'

# 누가 호출하는지까지 확인
oc get apirequestcounts <name> -o json \
  | jq -r '.status.currentHour.byNode[].byUser[] | .username' | sort -u

# 확인 완료 후 관리자 ack (버전별 키 이름은 릴리스 노트 참조)
oc -n openshift-config patch cm admin-acks --type=merge \
  -p '{"data":{"ack-4.15-kube-1.29-api-removals-in-4.16":"true"}}'
SECTION 04

etcd 운영과 재해복구

클러스터의 모든 상태는 etcd 안에 있습니다. 노드가 다 죽어도 etcd 백업이 있으면 복구되고, etcd가 깨지면 노드가 다 살아 있어도 클러스터는 없습니다. 그런데 etcd는 디스크 지연에 병적으로 민감합니다. OpenShift 성능 문제의 상당수가 여기서 시작됩니다.

etcd가 요구하는 것 — 숫자로 기억하기

< 10ms
fsync p99
가장 중요한 단일 지표. 이걸 넘으면 리더 선출이 불안정해진다.
< 50ms
peer RTT p99
마스터 간 네트워크 지연. 스트레치 클러스터 설계의 제약.
8 GiB
DB 크기 상한
기본 quota. 초과 시 클러스터가 읽기 전용으로 잠긴다.
3 또는 5
멤버 수
홀수 필수. 5개는 지연이 늘어 보통 3개가 최적.

etcd는 반드시 전용 디스크에

컨테이너 이미지 pull, 로그 쓰기, 다른 워크로드와 같은 디스크를 공유하면 fsync가 튑니다. 베어메탈은 NVMe 전용 볼륨, 퍼블릭 클라우드는 io2/Premium SSD 등급을 씁니다. 네트워크 스토리지(NFS, iSCSI)에 etcd를 올리는 것은 지원 대상이 아닙니다. 마스터 노드에 워크로드를 올리는 SNO 환경에서 "이유 없이 느린 클러스터"의 원인은 대부분 여기입니다.

  name: etcd-backup
  namespace: openshift-etcd
spec:
  schedule: "0 */6 * * *"
  concurrencyPolicy: Forbid

  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          hostNetwork: true
          serviceAccountName: etcd-backup
          nodeSelector:
            node-role.kubernetes.io/master: ""
          tolerations:
          - key: node-role.kubernetes.io/master
            operator: Exists
            effect: NoSchedule
          containers:
          - name: backup
            image: registry.redhat.io/rhel9/support-tools
            command: ["/bin/sh","-c"]
            args:
              - chroot /host /usr/local/bin/cluster-backup.sh /var/backup/etcd &&
                find /host/var/backup/etcd -mtime +7 -delete
            securityContext:
              privileged: true
            volumeMounts:
            - name: host
              mountPath: /host
          volumes:
          - name: host

#   oc adm policy add-scc-to-user privileged -z etcd-backup -n openshift-etcd

# 대량 삭제 직후에는 수동 실행이 필요할 수 있다.

oc rsh -n openshift-etcd etcd-master-0

  etcdctl defrag --command-timeout=30s
  # 리더는 마지막에 처리. defrag 중 해당 멤버는 응답하지 않는다.

# NOSPACE 알람이 떴다면 defrag 후 알람 해제까지 해야 한다
  etcdctl alarm list
  etcdctl alarm disarm

복구 시나리오별 대응

가장 다행인 경우입니다. 2/3 쿼럼이 살아 있어 클러스터는 정상 동작합니다. 절차는 죽은 멤버를 etcd에서 제거 → Machine 객체 삭제(IPI) 또는 노드 재프로비저닝(UPI) → Secret 3종 삭제 → 새 노드 조인 순입니다.

핵심은 etcdctl member remove를 먼저 해서 etcd가 3-멤버 구성을 기대하지 않게 만드는 것입니다. 그리고 openshift-etcd 네임스페이스에서 해당 노드의 etcd-peer-*, etcd-serving-*, etcd-serving-metrics-* Secret을 삭제해야 새 인증서가 발급됩니다. 이걸 빼먹으면 새 멤버가 TLS 핸드셰이크에서 계속 실패합니다.

클러스터 API가 응답하지 않습니다. restore-etcd 절차(재해복구)를 타야 합니다. 살아남은 마스터 1대에서 /usr/local/bin/cluster-restore.sh를 백업 파일과 함께 실행하면 해당 노드가 단일 멤버 etcd로 부팅하고, 나머지 마스터를 순차적으로 다시 조인시킵니다.

중요: 복구는 백업 시점으로 시계를 되돌립니다. 백업 이후 생성된 리소스는 모두 사라집니다. 또한 복구 후에는 kubelet 서빙 인증서 CSR을 수동 승인해야 노드가 Ready가 됩니다 (oc get csr | grep Pending → oc adm certificate approve). 이 절차는 리허설 없이 실전에서 처음 하면 반드시 실수합니다. 테스트 클러스터에서 최소 한 번은 해보십시오.

etcdserver: mvcc: database space exceeded. 쓰기가 전부 거부됩니다. 원인은 대개 특정 리소스의 폭증입니다 — 완료된 Job/Pod 누적, Event, 대용량 Secret/ConfigMap, 또는 커스텀 컨트롤러가 남긴 CR입니다.

대응: ① compact + defrag + alarm disarm으로 일단 쓰기를 회복 → ② 무엇이 공간을 먹는지 파악(etcdctl get / --prefix --keys-only를 prefix별로 세어 봅니다) → ③ 근본 원인 제거(Job의 ttlSecondsAfterFinished 설정, 컨트롤러 버그 수정). Event는 기본 3시간 후 정리되므로 Event가 원인이라면 누군가 대량 이벤트를 만들고 있다는 뜻입니다.

백업만큼 중요한 것 — 복구 리허설

백업 스크립트를 CronJob으로 돌려놓고 안심하는 조직이 많습니다. 그런데 실제 복구에 필요한 static_kuberesources 파일이 빠져 있거나, 오브젝트 스토리지 자격증명이 클러스터 안에만 있어서(클러스터가 죽으면 접근 불가) 무용지물인 사례가 흔합니다. 분기마다 격리된 테스트 클러스터에서 실제 복구를 수행하고 RTO를 측정하십시오.

oc rsh -n openshift-ovn-kubernetes -c ovnkube-controller $POD \
  ovs-vsctl show | grep -A3 geneve
MTU는 OVN 트러블슈팅의 첫 번째 용의자

Geneve 캡슐화는 100바이트를 가져갑니다. 물리 MTU 1500이면 Pod MTU는 1400입니다. "작은 요청은 되는데 큰 응답에서 멈춘다", "TLS 핸드셰이크는 되는데 그 다음이 안 된다"는 증상은 거의 항상 MTU 불일치입니다. 클라우드 환경에서 jumbo frame(9000)을 쓰면서 노드 MTU만 올리고 클러스터 MTU를 안 바꾸는 실수가 잦습니다.

확인: oc get network.operator cluster -o jsonpath='{.spec.defaultNetwork.ovnKubernetesConfig.mtu}'
변경은 무중단 마이그레이션 절차가 별도로 있으며(migration.mtu 필드), 단순 patch하면 클러스터 네트워크가 끊어집니다.

SDN에서 OVN으로 넘어온 사람이 놓치는 차이

① iptables가 아니다 — iptables-save에 Pod 규칙이 없습니다. OVS 플로우를 보십시오.
② kube-proxy가 없다 — Service 부하분산도 OVN 로드밸런서로 처리됩니다.
③ NetworkPolicy 성능 특성이 다르다 — SDN은 정책 수가 늘면 iptables 체인이 선형 증가했지만 OVN은 port group과 address set으로 묶어 처리해 확장성이 훨씬 좋습니다. 다만 정책 변경 시 northd 컴파일 부하가 걸리므로, 수천 개 정책을 한 번에 적용하면 순간적으로 반영이 지연됩니다.

SECTION 06

트래픽 정책과 Egress 제어

엔터프라이즈 도입 심사에서 가장 자주 나오는 질문이 "컨테이너가 어떤 IP로 나가느냐"입니다. 기존 방화벽·IPS 정책이 출발지 IP 기반으로 짜여 있는데, Pod IP는 매번 바뀌고 노드 IP로 SNAT되니 앱 단위 정책을 쓸 수 없기 때문입니다. OpenShift는 이 문제를 EgressIP로 풉니다.

NetworkPolicy — 기본은 전면 허용이다

네임스페이스에 NetworkPolicy가 하나도 없으면 모든 트래픽이 허용됩니다. 하나라도 생기면 해당 방향(ingress/egress)에 대해 선택된 Pod는 화이트리스트 모드로 전환됩니다. 정책은 서로 OR로 합산되며, 명시적 deny 규칙은 존재하지 않습니다.

DEMO 04NetworkPolicy 평가 시뮬레이터
적용할 정책을 토글하고 트래픽 시나리오를 고르면 허용/차단과 그 근거를 판정합니다.
# ① 전면 차단 — 모든 정책 설계의 출발점
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: app-prod }
spec:
  podSelector: {}          # 네임스페이스 전체 Pod
  policyTypes: [Ingress]
---
# ② Router 허용 — 이걸 빼면 Route가 503을 뱉는다 (가장 흔한 실수)
kind: NetworkPolicy
metadata: { name: allow-from-openshift-ingress, namespace: app-prod }
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          # 이 라벨은 OpenShift가 관리한다. 직접 붙이지 말 것.
          policy-group.network.openshift.io/ingress: ""
---
# ③ 모니터링 허용 — 빼면 메트릭이 조용히 사라진다
kind: NetworkPolicy
metadata: { name: allow-from-monitoring, namespace: app-prod }
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          network.openshift.io/policy-group: monitoring
# AdminNetworkPolicy (ANP) — 클러스터 스코프. OCP 4.14+ (GA 4.16)
# NetworkPolicy와 결정적 차이:
#   · 네임스페이스 소유자가 무력화할 수 없다 (거버넌스용)
#   · 명시적 Deny와 우선순위(priority)가 있다
#   · Pass 액션으로 "아래 NetworkPolicy에게 판단을 넘김"이 가능
apiVersion: policy.networking.k8s.io/v1alpha1
kind: AdminNetworkPolicy
metadata: { name: tenant-isolation }
spec:
  priority: 10              # 낮을수록 먼저 평가
  subject:
    namespaces:
      matchLabels: { tenant: team-a }
  ingress:
  - name: allow-monitoring
    action: Allow
    from:
    - namespaces:
        matchLabels: { kubernetes.io/metadata.name: openshift-monitoring }
  - name: deny-other-tenants
    action: Deny
    from:
    - namespaces:
        matchExpressions:
        - { key: tenant, operator: Exists }
  - name: delegate-rest
    action: Pass    # 나머지는 각 팀의 NetworkPolicy가 결정
    from:
    - namespaces: {}

# 평가 순서: ANP(priority 순) → NetworkPolicy → BaselineAdminNetworkPolicy
# EgressFirewall — OpenShift 전용. 네임스페이스별 외부 목적지 제어.
# 이름이 반드시 'default'여야 하고 네임스페이스당 1개만 허용된다.
apiVersion: k8s.ovn.org/v1
kind: EgressFirewall
metadata: { name: default, namespace: app-prod }
spec:
  egress:
  # 규칙은 위에서 아래로, 첫 매칭에서 종료 (NetworkPolicy와 다르다!)
  - type: Allow
    to: { dnsName: registry.redhat.io }
  - type: Allow
    to: { cidrSelector: 10.0.0.0/8 }      # 사내망
    ports:
    - { protocol: TCP, port: 443 }
  - type: Deny
    to: { cidrSelector: 0.0.0.0/0 }        # 그 외 전부 차단

# 주의 1: dnsName은 DNS 해석 결과 IP를 주기적으로 갱신한다.
#         CDN처럼 IP가 자주 바뀌는 목적지는 누락 구간이 생길 수 있다.
# 주의 2: 노드 IP(호스트 네트워크)로 나가는 트래픽은 대상이 아니다.
# 주의 3: EgressFirewall은 NetworkPolicy egress와 별개 레이어다.
#         둘 다 있으면 양쪽 모두 통과해야 한다.
# EgressIP — 특정 네임스페이스/Pod의 외부 나가는 트래픽에 고정 IP 부여.
# 방화벽 정책을 앱 단위로 쓸 수 있게 만드는 기능. 도입 심사 필수 항목.

# 1) EgressIP를 할당할 노드에 라벨 부여

SECTION 07

Ingress 샤딩과 라우터 튜닝

기본 설치에는 default IngressController 하나가 있고, 모든 Route가 여기로 모입니다. 트래픽이 늘거나 내부/외부 트래픽을 분리해야 하거나 테넌트별로 라우터를 나눠야 할 때 IngressController를 추가로 만드는 것(샤딩)이 정답입니다.

샤딩의 두 가지 축

🏷️
routeSelector — Route 라벨 기준

Route에 type: internal 라벨을 붙이면 해당 샤드가 담당합니다. 앱 개발자가 라벨을 붙여야 하므로 협의가 필요합니다.

📦
namespaceSelector — 네임스페이스 기준

플랫폼 팀이 네임스페이스에 라벨을 붙여 통제합니다. 테넌트 격리에는 이 방식이 안전합니다.

내부 전용 라우터 샤드 추가
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: internal
  namespace: openshift-ingress-operator
spec:
  # 이 샤드가 서비스할 와일드카드 도메인. default와 반드시 달라야 한다.
  domain: internal.apps.ocp.example.com
  replicas: 3
    namespaceSelector:
    matchLabels:
      router-shard: internal
  endpointPublishingStrategy:
    type: LoadBalancerService
    loadBalancer:
      # 사내망 LB만 붙인다 (클라우드에서는 internal LB로 프로비저닝됨)
      scope: Internal
  # 라우터 Pod를 인프라 노드에 고정
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
  tuningOptions:
    threadCount: 4              # HAProxy 워커 스레드 (기본 4)
    maxConnections: 50000
    clientTimeout: 30s
    serverTimeout: 30s
    tunnelTimeout: 1h        # WebSocket 유지 시간
  logging:
    access:
      destination: { type: Container }   # 액세스 로그 활성화

# 중요: default 컨트롤러에도 반대 조건을 넣어야 Route가 중복 노출되지 않는다.
#   spec.namespaceSelector.matchExpressions:
#     - {key: router-shard, operator: NotIn, values: [internal]}
# 이걸 빼먹으면 하나의 Route가 두 샤드에 동시 admit되어 예측 불가한 라우팅이 된다.

SECTION 08

고성능 네트워킹 — SR-IOV, NUMA, PerformanceProfile

5G RAN, 금융 거래 시스템, 고성능 추론 서버는 "패킷이 도착한다"로는 부족합니다. 지연 지터를 마이크로초 단위로 통제해야 합니다. OpenShift는 이를 위해 커널 튜닝, CPU 핀닝, NUMA 정렬, 커널 우회 네트워킹을 하나의 선언적 API로 묶어 제공합니다.

보조 네트워크 — Multus

Pod는 기본적으로 CNI 하나만 붙습니다. Multus는 메타 CNI로서 Pod에 추가 인터페이스를 붙여 줍니다. NetworkAttachmentDefinition(NAD)이 "어떤 네트워크를 어떻게 붙일지"를 정의합니다. 

# 사내 VLAN에 Pod를 직접 붙이는 가장 흔한 패턴 (레거시 연동용)
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: vlan100-net
  namespace: app-prod
spec:
  config: |
    {
      "cniVersion": "0.3.1",
      "type": "macvlan",
      "master": "eno1.100",
      "mode": "bridge",
      "ipam": {
        "type": "whereabouts",
        "range": "192.168.100.0/24",
        "range_start": "192.168.100.50",
        "range_end": "192.168.100.99",
        "gateway": "192.168.100.1"
      }
    }
# whereabouts는 클러스터 전역 IPAM. host-local과 달리 노드 간 중복을 막는다.
# 주의: macvlan은 같은 호스트의 부모 인터페이스와 통신하지 못한다(하드웨어 특성).
#       노드 자신과 통신해야 하면 ipvlan 또는 bridge를 검토할 것.
# SR-IOV: NIC의 PF를 여러 VF로 쪼개 Pod에 직접 할당. 커널 스택을 우회한다.
# 전제: SR-IOV Network Operator 설치 + BIOS에서 VT-d/IOMMU 활성화
#       + 커널 인자 intel_iommu=on iommu=pt (MachineConfig로)

# ① VF 풀 정의 — 어느 노드의 어느 NIC을 몇 개로 쪼갤지
apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetworkNodePolicy
metadata: { name: policy-mlx-fast, namespace: openshift-sriov-network-operator }
spec:
  resourceName: mlxfast            # Pod가 요청할 리소스 이름
  nodeSelector:
    feature.node.kubernetes.io/network-sriov.capable: "true"
  numVfs: 16
  nicSelector:
    vendor: "15b3"                 # Mellanox
    pfNames: ["ens5f0#0-15"]
  deviceType: netdevice           # 또는 vfio-pci (DPDK용)
  isRdma: true                    # RoCE / GPUDirect RDMA

# ② 그 풀을 쓰는 네트워크 정의 (NAD를 자동 생성해준다)
---
kind: SriovNetwork
metadata: { name: sriov-fast, namespace: openshift-sriov-network-operator }
spec:
  resourceName: mlxfast
  networkNamespace: app-prod       # NAD가 생성될 네임스페이스
  vlan: 100
  ipam: |
    { "type": "whereabouts", "range": "192.168.200.0/24" }

# 주의: NodePolicy 적용은 노드 재부팅을 유발한다(드라이버 재바인딩).
#       MCP와 동일하게 maxUnavailable을 고려해 계획할 것.
# PerformanceProfile — Node Tuning Operator가 제공.
# 커널 인자, tuned 프로파일, KubeletConfig, RT 커널을 한 번에 조율한다.
apiVersion: performance.openshift.io/v2
kind: PerformanceProfile
metadata: { name: low-latency }
spec:
  cpu:
    # isolated: 워크로드 전용. 커널 스레드/IRQ가 여기 들어오지 않는다.
    isolated: "4-23,28-47"
    # reserved: OS와 kubelet, 인프라 Pod용
    reserved: "0-3,24-27"
  hugepages:
    defaultHugepagesSize: "1G"
    pages:
    - { size: "1G", count: 16, node: 0 }   # NUMA 노드 지정
  numa:

    # 않으면 Pod를 아예 배치하지 않는다 (Topology Affinity Error)
    topologyPolicy: "single-numa-node"
  realTimeKernel:
    enabled: true
  globallyDisableIrqLoadBalancing: true
  nodeSelector:
    node-role.kubernetes.io/worker-rt: ""

#   oc debug node/... -- chroot /host tuned-adm active
# 전용 CPU를 받으려면 Guaranteed QoS + 정수 CPU가 필수 조건이다.
apiVersion: v1
kind: Pod

  name: dpdk-app
  annotations:

    cpu-quota.crio.io: "disable"
spec:
  runtimeClassName: performance-low-latency
  containers:
  - name: app
    image: registry.example.com/dpdk-app:v1
    resources:

                cpu: "8"              # 정수여야 한다. "8000m"도 가능하나 소수는 불가

Guaranteed QoS가 아니면 CPU 핀닝은 일어나지 않는다

cpuManagerPolicy: static을 켜도 조건을 만족하지 않으면 Pod는 조용히 공유 풀에 들어갑니다. 조건은 ① QoS가 Guaranteed(requests == limits, CPU·메모리 모두), ② CPU 요청이 정수입니다. cpu: "500m"은 아무리 static 정책이어도 전용 코어를 받지 못합니다. "튜닝했는데 지연이 그대로"의 1번 원인입니다.

GPU 학습 잡에도 그대로 적용된다

멀티 GPU 학습에서 NCCL 성능이 기대만큼 안 나올 때, GPU와 NIC이 서로 다른 NUMA 노드에 있는 경우가 많습니다. topologyPolicy: single-numa-node를 적용하면 kubelet이 GPU·NIC·CPU·메모리를 같은 NUMA에 정렬해 배치합니다. 대신 정렬 불가 시 Pod가 TopologyAffinityError로 실패하므로, restricted나 best-effort부터 단계적으로 적용하는 편이 안전합니다. 검증은 nvidia-smi topo -m으로 합니다.

ODF — Ceph를 클러스터 안에서 운영한다는 것

OpenShift Data Foundation은 Rook Operator로 Ceph를 클러스터 내부에 배치해 블록(RBD), 파일(CephFS), 오브젝트(RGW/NooBaa) 세 가지를 한 번에 제공합니다. 편리하지만 Ceph를 운영한다는 사실이 사라지지는 않습니다.

제공 방식AccessMode적합한 워크로드주의점
RBD (블록)RWO, RWX(raw block)DB, 단일 쓰기 상태 저장노드 장애 시 재부착에 시간 소요
CephFS (파일)RWX공유 아티팩트, 모델 저장소, CI 캐시메타데이터 서버(MDS)가 병목. 소파일 대량 처리에 취약
RGW / NooBaa (오브젝트)S3 API백업 대상, 모델 레지스트리, 로그 저장ObjectBucketClaim으로 버킷 프로비저닝
ODF 도입 시 반드시 계산할 것

실사용 용량 = 원시 용량 ÷ 3입니다(기본 3-way replication). 30TiB 디스크를 넣으면 쓸 수 있는 건 10TiB입니다. 여기에 Ceph는 nearfull(85%)을 넘으면 경고, full(95%)이면 쓰기를 거부하므로 실질 가용량은 더 줄어듭니다.

또한 ODF 노드는 CPU·메모리를 상당히 먹습니다(OSD당 대략 2 CPU / 5GiB 이상). 워커 노드에 ODF와 애플리케이션을 섞어 올리면 스토리지 지연이 애플리케이션 부하에 따라 흔들립니다. 프로덕션에서는 스토리지 전용 노드 3대 이상을 권장합니다.

백업과 DR 설계

etcd 백업은 클러스터를 되살립니다. 하지만 애플리케이션 데이터는 되살리지 못합니다. 두 가지는 완전히 다른 축이고, 둘 다 필요합니다.

etcd 백업이 지키는 것
  • 클러스터 자체의 구성 (노드, 오퍼레이터, 인증서)
  • 모든 K8s 객체의 정의 (Deployment, ConfigMap, Secret)
  • RBAC, 네트워크 정책
  • PV 안의 실제 데이터는 포함되지 않음
애플리케이션 백업(OADP)이 지키는 것
  • 네임스페이스 단위 객체 + PV 데이터
  • 다른 클러스터로 마이그레이션 가능
  • 선택적 복원 (특정 앱만)
  • 클러스터 인프라 구성은 포함되지 않음

복원 시 자주 걸리는 지점

① 이미지 풀 실패 — 원본 클러스터의 내부 레지스트리 주소를 참조하는 이미지는 다른 클러스터에서 못 받습니다. 외부 레지스트리를 쓰거나 이미지 마이그레이션을 병행하십시오.
② Route 호스트명 충돌 — 백업된 Route의 도메인이 새 클러스터의 와일드카드와 다릅니다. spec.host를 비워 백업하거나 복원 후 패치가 필요합니다.
③ Secret과 SA 토큰 — SA 토큰은 새 클러스터에서 재발급되어야 하므로 백업에서 제외하는 편이 낫습니다.
④ StorageClass 이름 불일치 — 대상 클러스터에 같은 이름의 SC가 없으면 PVC가 Pending에 머뭅니다. Velero의 changeStorageClass 플러그인으로 매핑하십시오.

RBAC 심층과 커스텀 SCC 작성

기초 강의에서 SCC가 "Pod의 권한을 심사한다"는 것을 봤습니다. 여기서는 직접 SCC를 만들고 안전하게 부여하는 방법, 그리고 RBAC의 집계(aggregation) 메커니즘을 다룹니다.

ClusterRole 집계 — 기본 역할을 확장하는 정석

커스텀 SCC 작성 — privileged를 주지 않고 문제를 푸는 법

"컨테이너가 root로 실행되어야 한다"는 요구에 privileged SCC를 주는 것은 호스트를 넘기는 것과 같습니다. 필요한 최소 권한만 담은 SCC를 만드는 것이 정답입니다. 

# 예: 레거시 앱이 UID 0으로 /etc에 쓰기를 해야 하지만, 호스트 접근은 불필요한 경우
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: legacy-root-only
priority: 10            # restricted-v2(null)보다 우선 선택된다

# --- 허용하는 것 ---
runAsUser:
  type: RunAsAny          # root 허용
allowPrivilegeEscalation: true

# --- 명시적으로 거부하는 것 (privileged와의 결정적 차이) ---
allowPrivilegedContainer: false
allowHostNetwork: false
allowHostPorts: false
allowHostPID: false
allowHostIPC: false
allowHostDirVolumePlugin: false   # hostPath 금지 — 가장 중요
readOnlyRootFilesystem: false

# --- capability는 화이트리스트로 ---
requiredDropCapabilities:
  - ALL
allowedCapabilities:
  - CHOWN
  - SETUID
  - SETGID
  - DAC_OVERRIDE

seLinuxContext: { type: MustRunAs }
fsGroup: { type: MustRunAs }
supplementalGroups: { type: RunAsAny }
volumes:
  - configMap
  - downwardAPI
  - emptyDir
  - persistentVolumeClaim
  - projected
  - secret
# hostPath를 목록에서 뺀 것이 핵심. 이것만으로 위험도가 크게 낮아진다.
# ❌ 절대 하지 말 것 — 네임스페이스의 모든 SA에 부여됨

SCC와 Pod Security Admission의 공존

Kubernetes 표준인 PSA가 OCP 4.11부터 함께 동작합니다. 둘은 서로 다른 단계에서 일합니다 — SCC는 Mutating(값을 채워줌), PSA는 Validating(검증만). 그래서 SCC는 통과했는데 PSA가 거부하는 상황이 생깁니다.

# ① ClusterResourceQuota (OpenShift 전용)
#    테넌트가 소유한 "모든 네임스페이스 합계"에 상한을 둔다.
#    Project를 셀프서비스로 만들게 허용하면서도 총량을 통제하는 유일한 방법.
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata: { name: team-a-total }
spec:
  selector:
    labels:
      matchLabels: { tenant: team-a }
  quota:
    hard:
      requests.cpu: "200"
      requests.memory: 400Gi
      limits.cpu: "400"
      requests.nvidia.com/gpu: "8"
      persistentvolumeclaims: "100"
      requests.storage: 10Ti
      count/routes.route.openshift.io: "50"
      pods: "500"
---
# ② ResourceQuota — 네임스페이스별 상한 (표준 K8s)
apiVersion: v1
kind: ResourceQuota
metadata: { name: ns-quota, namespace: team-a-prod }
spec:
  hard:
    requests.cpu: "80"
    requests.memory: 160Gi
  # 스코프로 우선순위별 분리도 가능
  scopeSelector:
    matchExpressions:
    - { operator: In, scopeName: PriorityClass, values: [high-priority] }
---
# ③ LimitRange — 개별 컨테이너의 기본값과 최대값
#    이걸 안 넣으면 requests 없는 Pod가 BestEffort로 들어와 노드를 흔든다.
apiVersion: v1
kind: LimitRange
metadata: { name: ns-limits, namespace: team-a-prod }
spec:
  limits:
  - type: Container
    default:        { cpu: "500m", memory: 512Mi }   # limits 기본값
    defaultRequest: { cpu: "100m", memory: 128Mi }   # requests 기본값
    max:            { cpu: "16",   memory: 64Gi }
    min:            { cpu: "10m",  memory: 32Mi }
  - type: PersistentVolumeClaim
    max: { storage: 2Ti }
ResourceQuota가 있으면 requests는 필수가 된다

네임스페이스에 requests.cpu 쿼터가 걸려 있으면, requests를 명시하지 않은 Pod는 생성 자체가 거부됩니다(must specify requests.cpu). LimitRange로 기본값을 함께 주지 않으면 기존 배포가 전부 깨집니다. 두 리소스는 항상 세트로 배포하십시오.

한 클러스터에 다 넣으려는 시도가 항상 옳지는 않습니다. 다음 중 하나라도 해당하면 클러스터 분리가 총비용이 더 낮습니다 — ① 규제상 물리 격리가 요구됨, ② 업그레이드 일정을 팀별로 달리 가야 함, ③ 커널 튜닝 요구가 상충함(RT 커널 vs 일반), ④ 신뢰 경계가 조직 외부까지 확장됨. 다만 클러스터가 늘면 관리 부담이 곱셈으로 증가하므로, 반드시 ACM 같은 플릿 관리 도구와 GitOps를 먼저 갖추십시오(섹션 15). // reconcile의 계약: 몇 번 호출되어도 결과가 같아야 한다(멱등).
// 이벤트가 아니라 "현재 상태"를 보고 판단할 것.

func (r *ModelServerReconciler) Reconcile(ctx context.Context,
    req ctrl.Request) (ctrl.Result, error) {

    log := log.FromContext(ctx)

    // 1) CR 조회. 없으면 삭제된 것 → 조용히 종료
    var ms mlv1alpha1.ModelServer
    if err := r.Get(ctx, req.NamespacedName, &ms); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 2) 삭제 처리 — finalizer로 외부 리소스 정리
    if !ms.DeletionTimestamp.IsZero() {
        return r.handleDeletion(ctx, &ms)
    }

    // 3) 원하는 상태를 계산하고 서버사이드 적용
    //    CreateOrUpdate 대신 SSA(Apply)가 드리프트 처리에 더 견고하다
    deploy := r.buildDeployment(&ms)
    if err := ctrl.SetControllerReference(&ms, deploy, r.Scheme); err != nil {
        return ctrl.Result{}, err
    }
    if err := r.Patch(ctx, deploy, client.Apply,
        client.FieldOwner("ml-operator"), client.ForceOwnership); err != nil {
        return ctrl.Result{}, err
    }

    // 4) status 갱신 — spec과 분리된 subresource로
    ms.Status.ObservedGeneration = ms.Generation
    ms.Status.ReadyReplicas = observed.Status.ReadyReplicas
    meta.SetStatusCondition(&ms.Status.Conditions, metav1.Condition{
        Type:    "Ready",
        Status:  metav1.ConditionTrue,
        Reason:  "AllReplicasReady",
        Message: "model server is serving",
    })
    if err := r.Status().Update(ctx, &ms); err != nil {
        // 충돌은 정상이다. 재큐잉하면 informer가 최신 객체를 준다.
        return ctrl.Result{Requeue: true}, nil
    }
    return ctrl.Result{}, nil
}

// 소유 리소스를 감시하면 드리프트가 자동 복구된다
func (r *ModelServerReconciler) SetupWithManager(mgr ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(mgr).
        For(&mlv1alpha1.ModelServer{}).
        Owns(&appsv1.Deployment{}).
        Owns(&corev1.Service{}).
        Complete(r)
}

용량 설계 — 노드 하나가 실제로 주는 것

# ① 전략 선택

oc label node worker-a100-01 nvidia.com/mig.config=all-1g.10gb

학습 잡은 탐욕적입니다. 큐에 들어온 잡이 가용 GPU를 전부 잡으면 서빙 Pod가 확장하지 못합니다. 실무에서 쓰는 분리 장치는 세 겹입니다 — ① 노드풀 분리(taint로 서빙 전용 GPU 노드 확보), ② PriorityClass(서빙 > 학습, preemption 허용), ③ Kueue의 ClusterQueue 쿼터로 팀·용도별 GPU 상한 설정입니다. 이 중 하나만 해도 대형 사고는 막히지만, 세 개를 다 하면 예측 가능해집니다.

실전 케이스 다섯 개

첫 명령은 언제나 oc describe pod <name>의 Events입니다. 스케줄러가 이유를 문장으로 남깁니다.

  • Insufficient cpu/memory — 노드 여유 부족. oc describe node의 Allocated resources 확인. 오토스케일러가 있으면 그 로그도.
  • node(s) had untolerated taint — toleration 누락. 가장 흔한 원인.
  • node(s) didn't match Pod's node affinity/selector — 네임스페이스의 openshift.io/node-selector 어노테이션이 자동 주입되고 있을 수 있습니다(섹션 13).
  • pod has unbound immediate PersistentVolumeClaims — PVC가 Pending. StorageClass 존재·기본값·프로비저너 로그를 봅니다.
  • TopologyAffinityError — single-numa-node 정책에서 정렬 실패(섹션 8).
  • Events가 비어 있다 — 스케줄러가 아직 보지 못한 것. Pod 자체가 안 만들어졌을 수 있으므로 oc describe rs로 올라가 쿼터/Admission 거부를 확인합니다.

현재 컨테이너의 로그는 이미 사라졌으므로 --previous가 핵심입니다.

oc logs <pod> --previous
oc logs <pod> -c <init-container>    # init 컨테이너 실패도 흔하다
oc get pod <pod> -o jsonpath='{.status.containerStatuses[*].lastState}' | jq

exitCode로 원인을 좁힙니다 — 137은 OOMKilled(메모리 limit 상향 또는 앱 튜닝), 139은 SegFault, 143은 SIGTERM(정상 종료 신호를 못 처리), 1은 애플리케이션 자체 오류입니다.

로그가 정말 아무것도 없다면 실행 자체가 안 된 것입니다. SCC 때문에 UID가 강제 변경되어 파일 권한 오류가 났거나(Permission denied), 이미지의 USER와 runAsUser가 충돌한 경우입니다. oc debug deploy/<name> --as-root=false -- sh로 같은 SCC 조건에서 셸을 띄워 직접 확인하는 것이 가장 빠릅니다.

503은 라우터가 백엔드를 못 찾았다는 뜻입니다. 순서대로 좁힙니다.

# ① Route가 admit 되었는가 (샤딩 문제)
oc get route myapp -o jsonpath='{.status.ingress[*].conditions}' | jq
# ② Service의 셀렉터가 Pod를 잡고 있는가 — Endpoints가 비면 여기가 원인
oc get endpoints myapp
# ③ Route의 targetPort가 Service 포트와 맞는가 (이름 vs 번호 혼동 주의)
oc get route myapp -o jsonpath='{.spec.port}'
# ④ NetworkPolicy가 라우터를 막고 있는가 ← 실무 1순위 원인 (섹션 6)
oc get networkpolicy -n app-prod
# ⑤ Pod의 readinessProbe가 실패 중인가 (Ready가 아니면 Endpoints에서 빠진다)
oc get pod -l app=myapp -o wide

참고로 502는 백엔드가 잘못된 응답을 준 것(대개 TLS 종료 방식 불일치 — edge인데 백엔드가 HTTPS를 기대하는 경우), 504는 타임아웃(섹션 7의 timeout 어노테이션)입니다.

oc describe node의 Conditions에서 사유를 봅니다. 흔한 세 갈래입니다.

  • DiskPressure — 이미지가 쌓여 디스크가 찼습니다. kubelet의 이미지 GC가 못 따라가는 상황. crictl rmi --prune으로 응급 처치, 근본적으로는 imageGCHighThresholdPercent 조정이나 디스크 증설.
  • MemoryPressure — systemReserved가 부족합니다. 워크로드가 노드 OS 몫까지 먹은 상태.
  • kubelet이 죽거나 인증서 만료 — oc adm node-logs <node> -u kubelet. 클러스터가 오래 정지되었다면 oc get csr | grep Pending을 확인하고 oc adm certificate approve로 승인합니다.

노드가 완전히 응답 없다면 oc debug node/도 실패합니다. 이때는 콘솔/IPMI로 접근하거나, IPI 환경이면 Machine 객체를 삭제해 재프로비저닝하는 것이 빠릅니다. 단 마스터 노드라면 반드시 etcd 멤버 제거를 먼저 하십시오(섹션 4).

"느리다"는 증상은 층을 나눠 격리해야 합니다. 순서는 아래에서 위로 올라갑니다.

  1. etcd fsync — 여기가 원인이면 다른 모든 곳이 느려 보입니다(섹션 4). 반드시 먼저 확인.
  2. API 서버 지연 — apiserver_request_duration_seconds p99. 동시에 apiserver_current_inflight_requests가 한계에 붙어 있는지, 특정 사용자/컨트롤러가 LIST를 남발하는지(apiserver_request_total을 verb="LIST"로 필터) 확인합니다.
  3. DNS — CoreDNS 지연이 애플리케이션 지연으로 나타납니다. coredns_dns_request_duration_seconds와 CoreDNS Pod의 CPU throttling 확인. Pod의 ndots:5 기본값 때문에 외부 도메인 조회가 5회 실패 후 성공하는 고전적 문제도 여기 있습니다(dnsConfig로 완화).
  4. CPU throttling — container_cpu_cfs_throttled_seconds_total. limits를 너무 낮게 잡은 Pod는 여유가 있어도 강제로 대기합니다. 지연 민감 서비스에서 가장 자주 발견되는 실제 원인입니다.
  5. 노드 포화 — node_load1 / 코어 수, 디스크 IO 대기.

실습 과제 — 순서대로 해보면 남는다

테스트 클러스터에서 ① 백업 → ② 네임스페이스 몇 개 생성 → ③ 마스터 2대를 의도적으로 정지 → ④ cluster-restore.sh로 복구 → ⑤ CSR 승인 → ⑥ 2단계에서 만든 네임스페이스가 사라졌음을 확인. RTO를 측정해 기록하십시오. 이 과제를 한 번 해두면 실제 장애 때 판단 속도가 달라집니다.

root로 실행해야 하는 임의의 이미지를 골라 ① privileged로 일단 띄워 보고 ② 실제로 필요한 capability와 권한만 남긴 커스텀 SCC를 작성 → ③ 전용 SA에 RoleBinding으로 부여 → ④ scc-subject-review로 사전 검증 → ⑤ hostPath를 뺐는데도 앱이 동작함을 확인. "왜 privileged가 위험한가"를 몸으로 이해하는 과제입니다.

3-tier 앱(web/api/db)을 배포한 뒤 ① default-deny를 걸어 전부 끊고 → ② Route가 503이 되는 것 확인 → ③ 라우터 허용 정책 추가 → ④ 계층 간 통신만 최소 허용 → ⑤ 모니터링 허용을 빼먹었을 때 메트릭이 사라지는 것까지 확인. 마지막으로 ovn-nbctl acl-list로 정책이 ACL로 어떻게 번역되었는지 보십시오.

Operator SDK로 간단한 CRD(예: EchoService — 문자열을 받아 Deployment+Service+Route를 만드는 것)를 설계해 ① make run으로 로컬 개발 → ② status conditions 구현 → ③ CR을 삭제하면 하위 리소스가 GC되는지 확인(ownerReference) → ④ Deployment를 손으로 수정했을 때 컨트롤러가 되돌리는지 확인 → ⑤ 번들로 만들어 사내 CatalogSource에 등록. 여기까지 하면 OperatorHub의 오퍼레이터들이 어떻게 동작하는지 보이기 시작합니다.

① NFD + GPU Operator 설치 → ② nvidia-smi Pod로 검증 → ③ time-slicing으로 GPU 1장을 4개로 쪼개 개발용 노트북 여러 개 띄우기 → ④ vLLM을 KServe로 배포하고 Route timeout 문제를 재현·수정 → ⑤ ServiceMonitor로 vLLM 메트릭 수집 → ⑥ KEDA로 큐 길이 기반 오토스케일 구성. MLOps 관점에서 이 강의 내용을 한 줄로 꿰는 과제입니다.

마지막으로 — 이 강의를 다 읽은 뒤에

OpenShift 심화의 본질은 기능 암기가 아니라 "이 동작의 주체가 누구인가"를 아는 것입니다. 노드 설정을 바꾸는 주체는 MCO, 오퍼레이터를 갱신하는 주체는 CVO, 논리 네트워크를 계산하는 주체는 northd, Pod의 보안 필드를 채우는 주체는 SCC admission입니다. 장애가 났을 때 "무엇이 잘못됐지"보다 "이걸 관리하는 컨트롤러가 무엇이고, 그 로그가 어디 있지"를 먼저 묻는 습관이 이 강의에서 남기고 싶은 유일한 것입니다.
