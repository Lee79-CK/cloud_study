Trustee · Attestation & Secret Delivery

“이 서버, 진짜 믿을 수 있어?”
그 질문에 기계적으로 답하는 3개의 서비스

비밀 값을 아무 서버에나 주면 안 됩니다. 그런데 “이 서버가 안전한 상태인지” 사람이 눈으로 확인할 수는 없죠. Trustee는 CPU가 하드웨어로 서명한 증거를 받아, 미리 등록한 정답지와 비교하고, 통과한 경우에만 비밀 값을 풀어주는 원격 증명(Remote Attestation) 서버 묶음입니다. 이 강의는 그 3개 서비스 — AS, KBS, RVPS — 를 처음 보는 사람도 끝까지 따라올 수 있게 설계했습니다.

AS · Attestation Service KBS · Key Broker Service RVPS · Reference Value Provider Service 인터랙티브 데모 4종 도해 9종 예상 학습 시간 90분
SECTION 01

왜 Trustee가 필요한가

먼저 “해결하려는 문제”를 이해하면, 3개 서비스가 왜 굳이 3개로 쪼개져 있는지가 자연스럽게 보입니다.

데이터를 보호하는 세 가지 상태

우리는 이미 두 가지는 잘 하고 있습니다. 디스크를 암호화하고(저장 중), TLS로 통신을 암호화합니다(전송 중). 문제는 세 번째입니다. 프로그램이 실제로 계산을 하려면 데이터를 평문으로 메모리에 올려야 합니다. 이 순간에는 호스트 운영체제 관리자, 하이퍼바이저 관리자, 클라우드 사업자 직원이 메모리를 덤프하면 다 보입니다.

TEE가 등장했지만, 문제가 하나 남는다

최신 CPU는 TEE (Trusted Execution Environment, 신뢰 실행 환경)를 제공합니다. Intel TDX (Trust Domain Extensions), AMD SEV-SNP (Secure Encrypted Virtualization - Secure Nested Paging) 같은 기술이죠. 가상 머신 메모리를 CPU가 암호화해서, 하이퍼바이저조차 안을 못 보게 만듭니다. 이렇게 만든 가상 머신을 CVM (Confidential Virtual Machine, 기밀 가상 머신)이라고 부릅니다.

그런데 여기서 결정적인 질문이 남습니다. “내 워크로드가 진짜 그 CVM 안에서 돌고 있다는 걸, 밖에서 어떻게 확인하지?” 악의적인 관리자가 그냥 일반 VM을 띄워놓고 “나 TEE야”라고 거짓말하면 어떡할까요?

🛂
공항 입국 심사 비유. 여권(증거)은 발급 국가가 위조 못 하게 서명해 두었습니다. 심사관은 여권의 서명을 검증하고(1단계), 그 다음 얼굴·비자·블랙리스트 같은 기준과 비교합니다(2단계). 둘 다 통과해야 입국 도장을 받고, 그 도장을 보여줘야 면세점 물건(비밀 값)을 살 수 있습니다. Trustee는 정확히 이 구조를 소프트웨어로 구현한 것입니다.

그래서 Trustee가 하는 일 (한 문장 요약)

게스트가 보낸 하드웨어 증거(Evidence)의 서명을 검증하고, 미리 등록된 기준값(Reference Values)과 비교해서, 정책을 통과했을 때만 비밀 값(Secret / Resource)을 암호화해서 돌려준다.

이 한 문장에 3개 서비스가 이미 다 들어있습니다. 서명 검증 = AS, 기준값 관리 = RVPS, 비밀 전달 = KBS. Trustee는 이 세 서비스를 담은 하나의 오픈소스 프로젝트 이름입니다. CNCF (Cloud Native Computing Foundation)의 CoCo (Confidential Containers) 프로젝트 산하에 있고, Red Hat은 이를 제품화해 OpenShift에서 제공합니다.

Note Trustee는 CoCo를 위해 만들어졌지만 CoCo 전용이 아닙니다. TEE 증거를 검증하고 비밀을 배포해야 하는 어떤 상황에서도 쓸 수 있습니다. 실제로 쿠버네티스 없이 단순 CVM에 시크릿을 내려주는 용도로도 씁니다.
SECTION 02

용어 사전 · 모든 약어의 풀네임

이 분야는 약어가 유난히 많습니다. 카드를 눌러 한국어 설명과 비유를 확인하세요. 뒤 섹션을 읽다가 막히면 여기로 돌아오면 됩니다.

AS
Attestation Service
증거의 서명을 검증하고, 정책에 따라 신뢰 여부를 판정하는 서비스. CoCo 문맥에서는 CoCo-AS라고도 부릅니다.
🛂 여권 진위를 확인하는 심사관
KBS
Key Broker Service
게스트와 실제로 통신하는 유일한 창구. 증명 절차를 진행하고, 통과한 게스트에게 비밀 값을 전달합니다. 검증은 직접 하지 않고 AS에 위임합니다.
🏦 도장을 확인하고 금고를 열어주는 창구 직원
RVPS
Reference Value Provider Service
“정상 상태라면 측정값이 이래야 한다”는 기준값(정답지)을 저장하고 AS에 제공합니다. AS 내장 모듈로도, 별도 프로세스로도 동작합니다.
📋 심사관이 참조하는 대조표
Trustee
(프로젝트 이름 · 약어 아님)
AS + KBS + RVPS + 클라이언트 도구(kbs-client)를 담은 저장소 이름. github.com/confidential-containers/trustee
🏛️ 세 직원이 근무하는 기관 전체
RATS
Remote ATtestation procedureS
IETF RFC 9334로 표준화된 원격 증명 아키텍처. 등장하는 역할 이름(Attester, Verifier, Relying Party 등)이 Trustee 설계의 뼈대입니다.
📐 모두가 따르는 설계 표준
Attester
(RATS 역할)
증명받는 쪽. 자기 상태를 증거로 만들어 제출합니다. Trustee 문맥에서는 게스트 안의 AA와 CDH가 담당합니다.
🧍 심사받는 여행객
Verifier
(RATS 역할)
증거를 평가해 판정하는 쪽. Trustee에서는 AS가 맡습니다.
🛂 심사관
Relying Party
(RATS 역할)
판정 결과를 근거로 실제 행동(비밀 전달, 접근 허용)을 하는 쪽. Trustee에서는 KBS입니다.
🏦 도장을 보고 물건을 내주는 상점
Endorser
(RATS 역할)
하드웨어 제조사. 칩에 심어둔 키로 증거에 서명할 수 있게 보증서(인증서 체인)를 발급합니다. Intel, AMD, IBM 등.
🏭 여권을 발급한 국가
Evidence
(증거)
게스트가 제출하는 하드웨어 서명 데이터 덩어리. 측정값, 플랫폼 정보, 논스, 사용자 데이터가 들어갑니다. TDX/SGX에서는 Quote라고 부릅니다.
📄 위조 불가 여권 페이지
Claims
(클레임 · 주장값)
증거를 파싱해서 뽑아낸 개별 항목들. 예: tdx.mrtd, tdx.rtmr0, snp.measurement. 정책은 이 클레임을 보고 판단합니다.
📝 여권에서 뽑아낸 이름·생년월일 필드
Measurement
(측정값)
펌웨어·커널·initrd·설정 같은 부팅 구성 요소를 해시로 요약한 값. 1바이트만 바뀌어도 해시가 완전히 달라집니다.
🔖 소포에 붙인 봉인 스티커의 지문
Reference Value
(기준값 · Golden Value)
“정상이라면 측정값이 이 값이어야 한다”는 기대값. 빌드 파이프라인에서 산출해 RVPS에 등록합니다.
📋 대조표에 적힌 정답
Nonce
Number used once
KBS가 매번 새로 발급하는 일회성 난수. 게스트가 이 값을 증거 안에 넣어 서명하므로, 옛날 증거를 재사용하는 재생 공격(Replay Attack)을 막습니다.
🎟️ 오늘 날짜가 찍힌 번호표
TCB
Trusted Computing Base
“이것만은 믿어야 하는” 최소 구성 요소의 집합. TEE의 목표는 TCB를 최대한 작게 만들어 신뢰해야 할 대상을 줄이는 것입니다.
🧱 무너지면 다 끝나는 주춧돌
TEE
Trusted Execution Environment
CPU가 메모리를 암호화·격리해 만든 보호 실행 영역. 호스트 관리자도 안을 볼 수 없습니다.
🔒 벽이 불투명한 회의실
TDX
Intel Trust Domain Extensions
Intel의 VM 단위 기밀 컴퓨팅 기술. 보호 대상 VM을 Trust Domain(TD)이라 부릅니다. 측정 레지스터로 MRTD와 RTMR을 씁니다.
🏢 Intel식 불투명 회의실
SEV-SNP
AMD Secure Encrypted Virtualization - Secure Nested Paging
AMD의 VM 단위 기밀 컴퓨팅 기술. 메모리 암호화에 무결성 보호(페이지 스왑·재매핑 공격 방어)를 추가했습니다.
🏢 AMD식 불투명 회의실
SGX
Intel Software Guard Extensions
프로세스 안에 작은 보호 영역(Enclave)을 만드는 1세대 방식. 애플리케이션을 고쳐야 해서, 요즘 컨테이너 분야는 VM 단위인 TDX/SEV-SNP를 선호합니다.
🗄️ 방 안의 작은 금고
MRTD
Measurement Register of Trust Domain
Intel TDX에서 TD 초기 이미지(펌웨어)의 측정값을 담는 레지스터. 부팅 후에는 변경되지 않습니다.
🧾 출생 증명서 — 태어난 순간의 모습
RTMR
Runtime Measurement Register
TDX에서 부팅 이후 추가로 확장(extend)되는 측정 레지스터. 커널, initrd, 커널 파라미터 등이 누적 기록됩니다. RTMR0~3이 있습니다.
📔 부팅 과정을 적은 항해 일지
PCR
Platform Configuration Register
TPM(Trusted Platform Module)의 측정 레지스터. Azure의 vTPM 기반 증명 방식에서 등장합니다.
📔 TPM 버전의 항해 일지
VCEK
Versioned Chip Endorsement Key
AMD SEV-SNP에서 개별 칩과 펌웨어 버전에 묶인 서명 키. 인증서는 AMD의 KDS(Key Distribution Service)에서 받아옵니다.
✒️ 그 칩만의 인감
DCAP
Data Center Attestation Primitives
Intel의 데이터센터용 증명 방식. 인증서를 로컬에 캐시해(PCCS) 외부 의존을 줄입니다. TDX Quote 검증에 사용됩니다.
🗂️ 사내에 둔 인증서 캐비닛
CVM
Confidential Virtual Machine
TEE로 보호되는 가상 머신. CoCo에서는 파드가 이 CVM 안에서 실행됩니다.
🔒 잠긴 방에 놓인 서버
CoCo
Confidential Containers
쿠버네티스 파드를 CVM 안에서 실행시켜 주는 CNCF 프로젝트. Kata Containers를 기반으로 하고, 증명은 Trustee에 맡깁니다.
📦 기밀 파드 런타임
AA
Attestation Agent
게스트(CVM) 안에서 증거를 수집해 KBS에 제출하는 에이전트. guest-components 프로젝트 소속입니다.
🧍 심사창구에 서는 여행객 본인
CDH
Confidential Data Hub
게스트 안에서 비밀 값을 요청·복호화·캐시해 워크로드에 전달하는 컴포넌트. 애플리케이션이 직접 KBS를 몰라도 되게 해줍니다.
🛎️ 방까지 물건을 가져다주는 컨시어지
OPA
Open Policy Agent
CNCF 정책 엔진. AS와 KBS의 정책은 OPA의 Rego 언어로 작성합니다.
⚖️ 규칙을 실행하는 판사
Rego
(OPA 정책 언어 · 약어 아님)
OPA 전용 선언형 정책 언어. input(들어온 클레임)과 data(기준값)를 비교해 allow 같은 결과를 만듭니다.
📜 판사가 읽는 법조문
JWT
JSON Web Token
서명된 JSON 토큰 형식. AS가 발급하는 Attestation Token이 이 형식입니다. 헤더.페이로드.서명 3부분을 점으로 이어 붙입니다.
🎫 위조 방지 입장 도장
EAT / EAR
Entity Attestation Token / EAT Attestation Result
증명 결과를 표준 형식으로 표현하려는 IETF 규격. Trustee는 토큰 형식으로 자체 CoCo 형식과 표준 Ear 형식을 모두 지원합니다.
🌐 국제 표준 규격의 도장
JWE
JSON Web Encryption
JSON 기반 암호화 형식. KBS는 게스트가 보낸 공개키로 비밀 값을 이 형식으로 감싸 보냅니다. 그래서 중간에서 가로채도 못 읽습니다.
✉️ 수신자만 열 수 있는 봉인 편지
in-toto
(공급망 무결성 프레임워크 · 약어 아님)
빌드 과정을 서명된 링크 메타데이터로 증명하는 표준. RVPS가 기준값을 신뢰할 수 있는 출처로부터 받아들일 때 쓰는 형식 중 하나입니다.
🧾 부품마다 붙은 제조 이력서
initdata
(초기화 데이터 · 약어 아님)
파드 시작 시 CVM에 주입되는 설정 묶음(정책, KBS 주소, 인증서 등). 이 값의 해시가 측정에 포함되므로, 설정 변조도 증명 단계에서 잡힙니다.
📨 봉인 안에 같이 넣은 지시서
ORAS
OCI Registry As Storage
컨테이너 레지스트리를 일반 파일 저장소로 쓰는 도구. kbs-client 바이너리를 이 방식으로 내려받습니다.
📮 레지스트리를 택배 보관함처럼
KMS
Key Management System
키를 안전하게 보관·순환하는 시스템(HashiCorp Vault, Azure Key Vault 등). KBS는 비밀 저장소로 KMS를 백엔드로 연결할 수 있습니다.
🏦 진짜 금고실
Tip 처음부터 다 외우려 하지 마세요. 실무에서 반드시 입에 붙어야 하는 건 6개입니다 — Evidence(증거), Measurement(측정값), Reference Value(기준값), Claims(클레임), Token(증명 토큰), Resource(자원 = 비밀 값).
SECTION 03

RATS 모델과 Trustee 역할 매핑

Trustee 문서는 RATS 용어를 그대로 씁니다. 이 매핑표 하나만 머리에 넣어두면 공식 문서가 훨씬 쉽게 읽힙니다.

RATS (Remote ATtestation procedureS)는 IETF가 RFC 9334로 정리한 원격 증명 표준 아키텍처입니다. “누가 증거를 만들고, 누가 검증하고, 누가 그 결과를 신뢰해서 행동하는가”를 역할로 분리해 놓았습니다. Trustee의 컴포넌트 분리는 이 역할 분리를 그대로 따른 결과입니다.

흔한 오해 “기준값은 Intel이나 AMD가 알려주는 것”이라고 생각하기 쉽습니다. 아닙니다. 제조사(Endorser)는 칩의 서명을 검증할 인증서만 제공합니다. 커널·initrd·펌웨어 이미지의 측정 기준값은 워크로드를 빌드한 여러분이 만들어 RVPS에 등록해야 합니다. 이 구분을 놓치면 “왜 검증이 계속 실패하지?”에서 헤매게 됩니다.
SECTION 04

전체 아키텍처 한눈에

여기서 그림 한 장을 확실히 이해하면 나머지 섹션은 “세부 확대”일 뿐입니다.

SECTION 05

AS · 증거를 검증한다

AS (Attestation Service, 증명 서비스)는 RATS의 Verifier입니다. 딱 두 단계만 합니다.

1단계 · Verifier Driver (하드웨어별 검증 드라이버)

하드웨어마다 증거 형식과 서명 방식이 다릅니다. 그래서 AS는 플랫폼별 드라이버를 각각 가지고 있습니다. 실무에서는 “우리 하드웨어에 맞는 드라이버가 지원되는가”와 “인증서 조회 경로가 열려 있는가”를 먼저 확인해야 합니다.

2단계 · 정책 엔진 (OPA · Rego)

서명이 진짜여도 내용이 기대와 다르면 거부해야 합니다. 예를 들어 누가 커널에 악성 모듈을 끼워 넣었다면, 서명은 정상이지만 RTMR 측정값이 달라집니다. 이 비교를 하는 게 Attestation Policy이고, OPA (Open Policy Agent)의 Rego 언어로 씁니다. 

# AS 증명 정책 — 게스트가 보낸 클레임(input)을 기준값(data)과 비교
# input : 증거에서 파싱된 클레임
# data  : RVPS 가 제공한 기준값
# 결과  : allow = true / false
package policy

default allow = false

# 1) TDX 플랫폼이어야 한다

    input.tee == "tdx"
    # 2) TD 초기 이미지 측정값이 등록된 기준값 목록에 있어야 한다
    input.tdx.quote.body.mr_td in data.reference.mr_td
    # 3) 커널·initrd 측정값도 기준값과 일치해야 한다
    input.tdx.quote.body.rtmr1 in data.reference.rtmr1
    input.tdx.quote.body.rtmr2 in data.reference.rtmr2
    # 4) 디버그 모드로 부팅된 TD 는 거부한다
    input.tdx.quote.body.tcb_svn != null
}

SECTION 06

RVPS · 정답지를 관리한다

RVPS (Reference Value Provider Service, 기준값 제공 서비스)는 세 컴포넌트 중 가장 단순하지만, 실무에서 가장 많이 문제를 일으키는 부분입니다. 정답지가 틀리면 아무것도 통과하지 못하니까요.

기준값은 어디서 오는가

AS는 “측정값 7f3e9a...가 정상인지”를 스스로 알 방법이 없습니다. 누군가 “정상 커널을 빌드했을 때 나오는 값은 7f3e9a...다”라고 알려줘야 합니다. 그 “누군가”가 여러분의 빌드 파이프라인이고, 그 값을 보관하는 창고가 RVPS입니다.

SECTION 07

KBS · 비밀을 내어준다

KBS (Key Broker Service, 키 중개 서비스)는 게스트가 유일하게 직접 말을 거는 상대입니다. 검증은 AS에 맡기고, 자기는 대화 진행과 비밀 전달에 집중합니다.

KBS Attestation Protocol · 3막 구성

프로토콜은 HTTP 기반이고 엔드포인트가 딱 세 개입니다. 순서가 정해져 있어서, 순서를 어기면 거부됩니다.

엔드포인트메서드하는 일
/kbs/v0/authPOST대화 시작. 게스트가 자기 TEE 종류와 프로토콜 버전을 알린다. KBS는 세션 ID와 논스를 발급한다
/kbs/v0/attestPOST게스트가 논스를 포함해 서명한 증거와 일회용 공개키를 제출한다. KBS→AS 검증 후 증명 토큰을 응답
/kbs/v0/resource/{repo}/{type}/{tag}GET토큰(또는 세션 쿠키)을 제시해 실제 비밀 값을 요청한다. 응답은 게스트 공개키로 암호화됨
Interactive · 증명 프로토콜 시뮬레이터

도해 6. 시나리오 버튼을 바꾸면 실패 경로도 볼 수 있습니다. 실패는 증거 단계와 자원 정책 단계 두 곳에서 따로 발생합니다.

왜 논스(Nonce)가 필요한가 논스가 없다면 공격자는 예전에 캡처한 정상 증거를 그대로 다시 보내 통과할 수 있습니다(재생 공격). KBS가 매번 새 난수를 주고, 게스트가 그 난수를 증거 안에 넣어 CPU에게 서명받기 때문에 “이 증거는 방금 만들어진 것”이 증명됩니다.
왜 게스트가 공개키를 같이 보내는가 KBS가 비밀 값을 평문 HTTP 응답으로 보내면 중간 경로에서 노출됩니다. 그래서 게스트는 증명 시점에 일회용 키 쌍을 만들어 공개키를 함께 제출하고(이 공개키 해시도 증거에 포함), KBS는 그 공개키로 비밀을 JWE (JSON Web Encryption)로 감싸 보냅니다. 결과적으로 TEE 안의 개인키만 그 비밀을 열 수 있습니다.

자원 경로 · Resource URI

KBS에 저장되는 비밀 값을 Resource(자원)라고 부릅니다. 주소 체계는 아주 단순합니다.

kbs:///{repository}/{type}/{tag}
  • repository — 논리적 묶음. 팀·환경·테넌트 단위로 나눕니다. 기본값 default
  • type — 자원 종류. 예: db, enckey, credential
  • tag — 개별 이름. 예: password, key.pem

호스트와 포트를 비워 kbs:///로 쓰는 것이 관례입니다. 자원을 특정 IP에 묶지 않기 위해서고, 실제 접속 주소는 게스트 설정(aa_kbc_params)에서 별도로 지정합니다.

자원 정책 · KBS Resource Policy

AS 정책이 “이 게스트를 믿을 수 있나”를 판단한다면, KBS 정책은 “이 게스트가 이 자원을 가져갈 자격이 있나”를 판단합니다. 같은 Rego 언어를 쓰지만 목적이 다릅니다. 이 구분이 처음엔 헷갈리니 표로 정리합니다.

SECTION 08

게스트 측 컴포넌트 · AA와 CDH

Trustee만 알면 절반입니다. 반대편에서 말을 거는 상대도 알아야 로그를 읽을 수 있습니다. 이들은 Trustee가 아니라 CoCo의 guest-components 프로젝트에 있습니다.

Attester 역할
AA · Attestation Agent
CPU 드라이버에 Quote를 요청해 증거를 만들고, KBS와 증명 프로토콜을 수행합니다. KBS 주소는 커널 파라미터 agent.aa_kbc_params=cc_kbc::https://kbs.example.com 형태로 주입됩니다.
비밀 소비자
CDH · Confidential Data Hub
워크로드가 비밀을 필요로 할 때 대신 KBS에서 받아오고, 복호화해서 파일·환경변수 형태로 전달합니다. 게스트 안에서 http://127.0.0.1:8006/cdh/resource/{repo}/{type}/{tag}로 노출됩니다.
🛎️
호텔 비유로 정리. 손님(워크로드)은 프런트가 어디 있는지도 모릅니다. 벨보이(CDH)에게 “금고에 있는 서류 좀”이라고 말하면, 벨보이가 신분 확인(AA를 통한 증명)을 거쳐 금고 관리자(KBS)에게서 서류를 받아 방까지 가져다줍니다. 손님은 절차를 몰라도 됩니다.

사례 ② 암호화된 컨테이너 이미지

컨테이너 이미지 자체가 지식재산인 경우가 있습니다(독자 알고리즘, 모델 코드). 이미지 레이어를 암호화해두면 레지스트리 관리자도 내용을 못 봅니다. 그러면 복호화 키는 누가 주죠? 증명을 통과한 게스트에게만 KBS가 줍니다.

사례 ③ LLM 모델 가중치와 추론 데이터 보호 (LLMOps)

파인튜닝한 모델 가중치는 수억 원짜리 자산이고, 추론 요청에는 고객 개인정보가 들어갑니다. GPU 노드를 남의 인프라에서 빌려 쓸 때 이 두 가지를 어떻게 지킬까요?

모델 보호
가중치 복호화 키
암호화된 모델 파일을 오브젝트 스토리지에 두고, 복호화 키만 KBS에 등록. 승인된 추론 이미지가 승인된 TEE에서 뜰 때만 키를 받습니다.
데이터 보호
추론 입력·출력
추론이 CVM 안에서 수행되므로 프롬프트와 응답이 호스트에 노출되지 않습니다. 규제 산업(금융·의료)의 필수 요건을 충족시킵니다.
GPU 확장
Confidential GPU
NVIDIA H100 이후 세대는 GPU 자체의 기밀 컴퓨팅 모드와 증명을 지원합니다. CPU 증거와 GPU 증거를 함께 검증하는 구성으로 확장됩니다.
MLOps 관점 정리 모델 레지스트리에 “암호화된 아티팩트”를, Trustee에 “복호화 키”를, RVPS에 “허용된 추론 런타임 이미지의 측정값”을 각각 등록하는 구조가 됩니다. 결국 모델 배포 파이프라인과 기준값 등록 파이프라인이 하나로 묶여야 운영이 지속 가능합니다.

사례 ④ 코드 서명 키 보호 (공급망 보안)

CI 파이프라인이 아티팩트에 서명하려면 개인키가 필요합니다. 그런데 CI 러너는 보통 공유 인프라입니다. 서명 작업을 CVM 안에서 수행하고, 서명 키는 증명 후에만 KBS에서 받아오게 하면 “빌드 서버가 털려도 서명 키는 안 털린다”가 성립합니다. Tekton Chains 등에서 실제로 쓰이는 패턴입니다.

사례 ⑤ 다자간 데이터 협업 (Multi-party Computation 유형)

A사와 B사가 각자의 고객 데이터를 합쳐 분석하고 싶지만, 서로에게 원본을 보여주긴 싫습니다. 합의된 분석 코드를 담은 이미지의 측정값을 양측이 각자 RVPS에 등록하고, 그 코드가 실행되는 CVM에만 각자의 데이터 복호화 키를 내려줍니다. 코드가 한 줄이라도 바뀌면 측정값이 달라져 키를 못 받으므로, 코드 그 자체가 계약서 역할을 합니다.

🤝
핵심 통찰. 위 다섯 사례는 전부 같은 구조입니다 — “정해진 코드가 정해진 환경에서 돌 때만 비밀을 준다.” Trustee가 하는 일은 그 조건문을 사람의 신뢰가 아니라 하드웨어 서명으로 판정하는 것뿐입니다.

트러블슈팅 · 증상별 원인 지도

실무에서 마주치는 순서대로 정리했습니다. 로그를 볼 컨테이너를 정확히 고르는 게 절반입니다.

증상가장 흔한 원인확인할 곳
401 Unauthorized
at /kbs/v0/attest		 증거 검증 실패. 하드웨어 인증서 체인 조회 실패(PCCS/KDS 미도달)이거나, 논스 불일치, 또는 증명 정책이 측정값을 거부 AS 컨테이너 로그 → 정책 평가 결과 라인
403 Forbidden
at /kbs/v0/resource/...		 증명은 통과했지만 자원 정책이 거부. 경로 오타이거나 Rego 규칙이 그 경로를 허용하지 않음 get-resource-policy로 현재 정책 확인
404 Not Found 자원이 등록되지 않음. repository/type/tag 3단 경로 중 하나가 틀림 KBS 자원 디렉터리 또는 get-resource
측정값 불일치 노드 이미지·커널·initrd·커널 파라미터가 변경됨. 기준값 갱신 누락 rvps-tool query로 등록된 기준값 확인
파드가 ContainerCreating에서 멈춤 CDH가 KBS에 도달하지 못함. aa_kbc_params 주소 오류, DNS 미해결, 방화벽, TLS 인증서 불신 kata-agent · CDH 게스트 로그
앱이 sealed.fakejws...를 그대로 받음 CDH 프로세스가 안 떴음. guest_components_procs=confidential-data-hub 누락 파드 어노테이션의 커널 파라미터
토큰 만료 오류 duration_min이 너무 짧거나 게스트-Trustee 간 시간 동기화(NTP) 불일치 양쪽 시스템 시간 비교
일반 런타임에서도 비밀이 나옴 가장 위험한 상태. 증명 정책이 allow = true로 남아있음 AS 정책 파일 즉시 교체
PoC 검증 시 반드시 넣을 음성 테스트(Negative Test) “되는 것”만 확인하면 아무것도 증명하지 못합니다. 최소 세 가지를 반드시 실패시켜 보세요 — ① 일반(비 CoCo) 런타임클래스로 같은 파드 기동 → 비밀 획득 실패해야 함. ② 승인되지 않은 이미지 다이제스트로 기동 → 실패해야 함. ③ 기준값을 일부러 틀린 값으로 바꿔 등록 → 실패해야 함. 이 세 개가 전부 실패해야 “보호가 실제로 작동한다”고 보고할 수 있습니다.

SECTION 15

학습 체크리스트

항목을 눌러 체크하세요. 이 목록을 다 설명할 수 있으면 팀 내에서 Trustee 담당자 역할을 할 수 있습니다.

개념 이해

  • 데이터의 세 가지 상태를 말하고, Confidential Computing이 어느 것을 다루는지 설명할 수 있다
  • RATS의 다섯 역할과 Trustee 컴포넌트를 서로 매핑할 수 있다
  • Evidence · Measurement · Reference Value · Claims · Token의 차이를 구분한다
  • AS의 2단계 검증이 각각 어떤 질문에 답하는지 설명할 수 있다
  • 기준값을 하드웨어 제조사가 주지 않는 이유를 설명할 수 있다
  • 논스와 게스트 공개키가 각각 어떤 공격을 막는지 말할 수 있다
  • AS 증명 정책과 KBS 자원 정책의 목적 차이를 설명할 수 있다

실습 역량

  • Docker Compose로 KBS·AS·RVPS를 띄우고 연결을 확인했다
  • 관리자 키 쌍을 만들고 kbs-client로 자원을 등록해 봤다
  • Rego 자원 정책을 직접 수정해 403을 유도했다가 다시 통과시켜 봤다
  • RVPS에 기준값을 등록하고 query로 확인해 봤다
  • Sealed Secret 문자열을 만들어 파드에 주입해 봤다
  • KbsConfig 필드가 각각 어떤 ConfigMap을 가리키는지 안다

운영 준비

  • HTTPS 활성화와 관리 API 인증을 운영 기준으로 설정했다
  • 기본 증명 정책(allow = true)을 측정값 비교 정책으로 교체했다
  • 노드 이미지 갱신 시 기준값을 먼저 등록하는 절차를 문서화했다
  • 음성 테스트 3종(일반 런타임·미승인 이미지·틀린 기준값)을 통과시켰다
  • 증상별 로그 확인 위치(KBS · AS · CDH)를 팀에 공유했다
