Module 01

모니터링과 옵저버빌리티는 다릅니다

Datadog을 배우기 전에 "무엇을 보려는 것인가"부터 정리합니다.

많은 입문자가 Datadog을 "그래프 그려주는 툴"로 이해하고 시작합니다. 그러면 반드시 벽에 부딪힙니다. 대시보드는 100개가 되었는데 정작 장애 때 원인을 못 찾는 상황이 생깁니다. 출발점은 두 단어의 차이를 아는 것입니다.

📊모니터링 (Monitoring)

이미 알고 있는 문제를 감시합니다. "CPU가 90% 넘으면 알려줘." 질문이 미리 정해져 있고, 답을 대시보드에 고정해 둡니다.

→ Known unknowns

🔍옵저버빌리티 (Observability)

예상하지 못한 문제를 사후에 파헤칠 수 있는 능력입니다. "왜 오늘만 서울 리전 안드로이드 사용자의 결제가 느렸나?" 미리 만든 대시보드가 없어도 데이터를 새로 쪼개 물어볼 수 있어야 합니다.

→ Unknown unknowns

옵저버빌리티가 성립하려면 충분히 세밀한 데이터와 그 데이터를 자유롭게 쪼갤 수 있는 축(=태그)이 필요합니다. Datadog의 설계 전체가 이 두 가지를 중심으로 돌아갑니다. 뒤에서 태그를 유난히 강조하는 이유가 여기 있습니다.

관측 데이터의 네 기둥 — MELT

업계에서는 관측 데이터를 네 종류로 나눕니다. 각각 답할 수 있는 질문이 다릅니다.

종류정체답할 수 있는 질문비용 특성
Metrics
지표		시간별 숫자 (CPU 62%, 초당 요청 340건)"지금 정상인가?" "어제보다 나빠졌나?"저렴 · 압축 잘 됨
Events
이벤트		시점의 사건 (배포됨, Pod 재시작됨)"언제부터 나빠졌나? 그때 뭘 했나?"저렴
Logs
로그		애플리케이션이 남긴 텍스트 기록"정확히 어떤 에러가 났나?"비쌈 · 양이 폭발
Traces
트레이스		요청 1건이 서비스들을 통과한 전체 경로"느린 구간이 어느 서비스·어느 쿼리인가?"중간 · 샘플링 필요
실무 감각

이 네 개를 같은 태그로 묶어 서로 오갈 수 있느냐가 관측 플랫폼의 진짜 실력입니다. "CPU 그래프에서 튀는 구간 클릭 → 그 시각 그 호스트의 느린 트레이스 → 그 트레이스가 남긴 로그"로 3초 안에 이동하는 것. Datadog이 비싼 값을 받는 이유가 정확히 이 상관관계(correlation)입니다.

골든 시그널 — 무엇부터 봐야 하나

지표가 수천 개라도 처음 볼 것은 정해져 있습니다. Google SRE의 4가지 골든 시그널부터 잡으면 90%는 커버됩니다.

⏱ Latency

응답 시간. 평균이 아니라 p95 / p99를 봅니다. 평균은 거짓말을 합니다.

📈 Traffic

초당 요청 수(RPS), QPS. 부하의 크기.

❌ Errors

5xx 비율, 예외 발생률. 실패의 비율.

🌡 Saturation

CPU·메모리·디스크·커넥션 풀이 얼마나 꽉 찼는지. 한계까지의 여유.

Module 02

Datadog이란 무엇인가

한 문장 정의, 아키텍처, 그리고 SaaS라는 선택이 의미하는 것.

한 문장 정의

Datadog은 서버·컨테이너·클라우드·애플리케이션·로그·사용자 브라우저에서 데이터를 모아, 검색·시각화·알림·보안 분석까지 한 화면에서 처리하는 완전 관리형(SaaS) 관측 플랫폼입니다. 직접 설치·운영하는 서버는 없고, 각 호스트에 Agent만 깔면 됩니다.

데이터는 이렇게 흐릅니다

Collect
Agent

호스트/컨테이너에 상주. 시스템 지표, 로그, 트레이스, 통합(Integration) 데이터를 수집

Ship
Intake

HTTPS로 Datadog 사이트(예: US1)에 전송. 아웃바운드 443만 열면 됨

Store
Backend

시계열 DB + 로그 인덱스 + 트레이스 저장소에 태그와 함께 적재

Use
Web UI / API

대시보드·모니터·노트북·Watchdog 이상탐지, Terraform/API 자동화

중요한 특징 하나. 클라우드 리소스 지표는 Agent 없이도 수집됩니다. AWS·Azure·GCP에 IAM 역할(또는 App Registration)을 연결해 두면 Datadog이 클라우드 API를 주기적으로 호출해 RDS, Load Balancer, Azure SQL 같은 매니지드 서비스 지표를 끌어옵니다. Agent는 "내가 OS 레벨에 접근할 수 있는 것"에, 클라우드 인테그레이션은 "매니지드 서비스"에 씁니다.

Datadog 사이트(리전)를 반드시 먼저 정하세요

Datadog은 데이터를 저장할 리전을 계정 생성 시 고릅니다. US1, US3, US5, EU1, AP1(일본), AP2, US1-FED 등이 있고, 나중에 변경이 불가능합니다. Agent 설정의 site 값이 여기에 맞아야 데이터가 들어옵니다. 국내 기업은 데이터 주권·지연 이슈로 AP1(도쿄) 또는 US1을 주로 검토합니다. 금융·공공처럼 국내 리전이 요구되면 SaaS 자체가 제약이 되므로 초기에 컴플라이언스 검토가 필요합니다.

첫 삽 뜨기 전 체크

① 어떤 사이트(리전)에 계정을 만들 것인가 ② 조직/팀을 어떻게 쪼갤 것인가(Multi-Org) ③ 태그 표준을 누가 정할 것인가 ④ 월 예산 상한과 담당자는 누구인가. 이 네 가지를 안 정하고 시작한 조직은 6개월 뒤 태그가 뒤죽박죽인 대시보드 300개와 예상의 3배 청구서를 받습니다.

Module 03

Agent와 데이터 수집 경로

Agent는 무엇을 하고, Agent 없이 데이터를 보내는 방법은 무엇인가.

Datadog Agent는 Go로 작성된 경량 프로세스입니다(보통 메모리 100MB 내외). 단일 프로세스가 아니라 역할별 서브 프로세스 묶음이라는 점을 알면 트러블슈팅이 쉬워집니다.

🧩 Core Agent

15초마다 시스템 지표 수집, Integration(Check) 실행, 백엔드 전송. 문제 생기면 agent status부터 봅니다.

🐕 Trace Agent

APM 트레이스를 8126 포트로 수신 → 샘플링 → 전송.

📮 DogStatsD

8125/UDP로 커스텀 메트릭 수신. 애플리케이션이 "fire-and-forget"으로 지표를 던지는 창구.

📜 Logs Agent

파일/컨테이너 stdout·journald를 tail하여 로그 전송. 기본 비활성 → 명시적으로 켜야 함.

🔐 Security Agent

런타임 위협 탐지(CWS), 컴플라이언스 점검(CSPM). eBPF 기반.

⚙️ Process Agent

프로세스 목록, 컨테이너 정보, 네트워크 연결(NPM) 수집.

Integration = 미리 만들어진 수집기 850종+

Datadog의 실질적인 힘은 Integration 카탈로그입니다. PostgreSQL, Redis, Nginx, Kafka, Kubernetes, Istio, Elasticsearch, NVIDIA DCGM 등 수백 개 미들웨어에 대해 "무엇을 지표로 뽑아야 하는지" + "기본 대시보드" + "권장 모니터"가 세트로 제공됩니다. 직접 exporter를 찾고 대시보드 JSON을 수입해 올 필요가 없다는 것이 핵심 차별점입니다.

Autodiscovery — 컨테이너 세상의 필수 개념

Kubernetes에서 Pod는 계속 죽고 태어나며 IP가 바뀝니다. 정적 설정 파일에 IP를 적어두는 방식은 통하지 않습니다. Datadog Agent는 kubelet/컨테이너 런타임을 관찰해 "redis 이미지를 쓰는 컨테이너가 떴다 → redis 체크를 자동으로 붙인다"를 수행합니다. 설정은 Pod 어노테이션 또는 Agent의 conf.d 자동 템플릿으로 지정합니다. 

# deployment.yaml — Pod에 어노테이션만 붙이면 Agent가 알아서 붙습니다
metadata:
  annotations:
    # ad.datadoghq.com/<컨테이너_이름>.checks
    ad.datadoghq.com/redis.checks: |
      {
        "redisdb": {
          "init_config": {},
          "instances": [{
            "host": "%%host%%",   # 템플릿 변수 → 실제 Pod IP로 치환
            "port": "6379"
          }]
        }
      }
    # 로그도 함께 수집 (source가 파서를 결정하므로 정확히 적을 것)
    ad.datadoghq.com/redis.logs: '[{"source":"redis","service":"cart-cache"}]'
# 지표가 안 올라올 때 순서대로 확인하는 3개 명령
sudo datadog-agent status          # API 키 유효? 각 체크 성공/실패?
sudo datadog-agent configcheck     # 어떤 체크가 어떤 설정으로 로드됐나
sudo datadog-agent check postgres   # 특정 체크를 즉시 1회 실행 → 원시 결과 확인

# Kubernetes에서는
kubectl exec -it <datadog-agent-pod> -- agent status
kubectl exec -it <datadog-agent-pod> -- agent configcheck

경로쓰는 상황주의점
클라우드 인테그레이션RDS·ALB·Azure SQL 등 매니지드 서비스클라우드 API 호출 비용 발생(특히 AWS CloudWatch GetMetricData)
DogStatsD앱 내부 비즈니스 지표 (주문 수, 큐 길이)UDP라 유실 가능. 카디널리티 폭발 주의

HTTP APICI 결과, 배치 잡, 외부 시스템 지표레이트 리밋 존재. 대량 전송은 Agent 경유가 유리
OpenTelemetry와의 관계

흔한 오해: "Datadog은 독자 규격이라 OTel과 안 맞다." 지금은 아닙니다. Datadog Agent가 OTLP 수신기를 내장하고 있어 OTel SDK로 계측한 앱의 트레이스/지표/로그를 그대로 받습니다. 권장 전략은 계측은 OpenTelemetry 표준으로, 백엔드는 Datadog으로입니다. 이렇게 하면 나중에 백엔드를 바꿀 때 애플리케이션 코드를 다시 손대지 않아도 됩니다. 락인을 줄이는 가장 실용적인 방법입니다.

Module 04

메트릭의 5가지 타입

"왜 내 숫자가 그래프에서 이상하게 나오지?"의 90%는 타입을 잘못 골라서입니다.

같은 데이터를 보내도 어떤 타입으로 선언했는지에 따라 저장·집계 방식이 완전히 달라집니다. 아래 실습에서 동일한 원시 데이터가 타입별로 어떻게 변하는지 직접 확인해 보세요.

Lab 01

메트릭 타입 시뮬레이터

상황: 10초 동안 주문 API가 5번 호출되었고, 각 응답 시간(ms)은 아래와 같습니다.
원시 데이터 → [120, 340, 95, 880, 210]  ·  flush 간격 10초

타입의미대표 예시골라야 할 때
COUNT구간 내 합계주문 건수, 에러 건수"몇 번 일어났나"를 셀 때
GAUGE순간 값 (마지막 값 유지)CPU %, 메모리, 큐 길이"지금 얼마인가"를 볼 때
RATE초당 변화량초당 요청 수속도를 볼 때 (COUNT를 .as_rate()로 대체 가능)
HISTOGRAMAgent에서 통계 계산 후 전송 (avg·max·p95 등)응답 시간 분포단일 호스트 기준 분포로 충분할 때
DISTRIBUTION원시 값을 백엔드로 보내 전체 호스트 통합 백분위 계산전 클러스터 p99 지연여러 호스트를 합친 정확한 p99가 필요할 때
가장 흔한 실수

HISTOGRAM의 p95를 여러 호스트에 걸쳐 평균 내면 그 값은 틀립니다. "호스트별 p95의 평균"은 "전체 p95"가 아닙니다. 백분위를 클러스터 전체로 봐야 하면 반드시 DISTRIBUTION을 쓰세요. 다만 DISTRIBUTION은 커스텀 메트릭 과금 단위가 커서 비용이 더 듭니다. 정확도와 비용의 트레이드오프입니다.

from datadog import initialize, statsd

initialize(statsd_host='localhost', statsd_port=8125)

# COUNT — 몇 번 일어났나
statsd.increment('orders.created', tags=['env:prod', 'payment:card'])

# GAUGE — 지금 값
statsd.gauge('queue.pending', 42, tags=['env:prod', 'queue:inference'])

# HISTOGRAM — Agent가 통계 계산
statsd.histogram('order.latency', 340, tags=['env:prod'])

# DISTRIBUTION — 전역 백분위가 필요할 때
statsd.distribution('inference.latency', 128.4, tags=['model:llama-3-8b'])

Datadog을 잘 쓰는 조직과 못 쓰는 조직의 차이는 대시보드 수가 아니라 태그 규율에서 갈립니다.

env

카디널리티 — 태그가 비용을 폭발시키는 지점

커스텀 메트릭의 과금 단위는 "메트릭 이름"이 아니라 메트릭 이름 × 태그 값의 고유 조합 수입니다. 이것을 카디널리티라고 합니다. 계산해 보면 왜 위험한지 바로 보입니다.

태그 설계고유 조합 수판정
env(3) × service(20) × region(3)180개안전
위 + host(200)36,000개주의 — 필요한지 검토
위 + user_id(50만)180억개즉시 중단. 청구서 재난
절대 태그로 쓰지 말아야 할 것

user_id, session_id, request_id, trace_id, 이메일, 전체 URL 경로(/order/48213), 타임스탬프. 값의 종류가 무한히 늘어나는 것은 태그가 아닙니다. 이런 정보는 로그나 트레이스의 속성(attribute)으로 넣으세요. 로그·트레이스는 고카디널리티를 감당하도록 설계되어 있고, 메트릭은 그렇지 않습니다.

URL은 /order/{id}처럼 반드시 정규화해서 넣습니다.

로그 관리

비용이 가장 잘 터지는 영역입니다. 구조를 이해하면 90% 절감이 가능합니다.

Datadog 로그의 핵심 개념은 수집(Ingest)과 인덱싱(Index)이 별도로 과금된다는 것입니다. 이 분리를 이해하는 것이 로그 비용 통제의 전부입니다.

Step 1
Ingest

모든 로그를 받아들임. GB 단위 과금(저렴). 이 단계에서는 검색 불가

Step 2
Pipeline

파싱·필드 추출·민감정보 마스킹·태그 부여

Step 3
Index

검색 가능하게 저장. 건수 × 보관기간 과금(비쌈)

Step 4
Archive

S3/Blob에 원본 보관. 필요시 재수집(Rehydrate)

SLO와 에러 예산

"몇 % 장애까지 허용할 것인가"를 숫자로 합의하는 도구.

모니터는 "지금 이상한가"를 봅니다. SLO는 "이번 달 우리는 약속을 지키고 있는가"를 봅니다. 관점이 완전히 다르고, 둘 다 필요합니다.

SLI

측정 지표. "성공한 요청 / 전체 요청"

SLO

목표치. "30일간 99.9%"

Error Budget

허용 실패량. 99.9%면 30일에 43분 12초

에러 예산이 팀 문화를 바꾸는 방식

에러 예산이 남아 있으면 배포 속도를 올리고, 다 쓰면 안정화에 집중합니다. "언제 신규 기능을 멈추고 기술 부채를 갚을지"를 감정 논쟁이 아니라 숫자로 결정하게 만듭니다. Datadog SLO 화면은 남은 예산과 소진 속도(burn rate)를 보여주고, burn rate 알림으로 "이 속도면 3일 내 예산 소진"을 미리 경고할 수 있습니다.

# Terraform으로 SLO 정의 — 코드로 관리하면 리뷰가 가능해집니다
resource "datadog_service_level_objective" "checkout_availability" {
  name        = "Checkout API 가용성"
  type        = "metric"
  description = "5xx가 아닌 응답의 비율"

  query {
    numerator   = "sum:trace.http.request.hits{env:prod,service:checkout-api,!http.status_class:5xx}.as_count()"
    denominator = "sum:trace.http.request.hits{env:prod,service:checkout-api}.as_count()"
  }

  thresholds {
    timeframe = "30d"
    target    = 99.9
    warning   = 99.95
  }

  tags = ["team:platform", "tier:critical"]
}

# Burn rate 알림 — 예산 소진 속도가 너무 빠르면 경고
resource "datadog_monitor" "slo_burn" {
  name  = "[SLO] Checkout 에러 예산 소진 속도 이상"
  type  = "slo alert"
  query = "burn_rate(\"${datadog_service_level_objective.checkout_availability.id}\").over(\"1h\").long_window(\"1h\").short_window(\"5m\") > 14.4"
  # burn rate 14.4 = 1시간에 한 달 예산의 2%를 소진하는 속도
}

비교 매트릭스 — 볼 항목을 골라보세요

점수는 일반적 상황에서의 상대 비교이며, 조직 규모·기존 자산·팀 역량에 따라 순위는 달라집니다.

주요 경쟁 구도를 한 문단씩

Prometheus + Grafana + Loki + Tempo (오픈소스 스택)

라이선스 비용 0, 데이터는 내 손안에, 커스터마이징 무한. Kubernetes 생태계의 사실상 표준입니다. 대가는 운영 부담입니다. Prometheus의 장기 저장(Thanos/Mimir), 고가용성, 로그 스택(Loki), 트레이싱(Tempo)을 각각 붙이고 업그레이드하고 스케일링해야 합니다. 상관관계 분석은 직접 대시보드로 엮어야 하고 UX는 Datadog보다 거칩니다. 전담 플랫폼 엔지니어가 1명 이상 있고 대규모라면 TCO가 역전됩니다.

Grafana Cloud

위 스택의 매니지드 버전. Datadog보다 저렴하고 오픈소스 호환(PromQL·LogQL 유지)이라 락인이 약합니다. 다만 통합 카탈로그의 깊이, 자동 상관관계, Watchdog 같은 이상탐지 성숙도는 Datadog이 앞섭니다. "Prometheus로 이미 지표를 쌓았고 운영만 남기고 싶다"면 가장 자연스러운 선택입니다.

New Relic

사용자 수 + 데이터량 기준 과금이라 호스트가 많고 사용자가 적으면 Datadog보다 훨씬 저렴할 수 있습니다. 무료 티어도 관대합니다. 반면 NRQL이라는 자체 쿼리 언어 학습이 필요하고, 인프라 모니터링의 깊이는 Datadog이 앞선다는 평이 많습니다. 호스트 수가 많은 조직에서 진지하게 비교할 후보입니다.

Dynatrace

OneAgent 하나로 자동 발견·자동 계측하고, Davis AI가 근본 원인을 자동 지목합니다. 대규모 엔터프라이즈 · 복잡한 레거시 · 자동화된 RCA가 필요하면 강력합니다. 가장 비싸고 유연성(커스텀 지표, 임의 쿼리)이 Datadog보다 낮습니다.

CloudWatch / Azure Monitor (클라우드 네이티브)

해당 클라우드 안에서는 마찰이 없고 저렴합니다. IAM 통합, 매니지드 서비스 지표 즉시 사용. 문제는 멀티클라우드와 온프레미스입니다. Azure + KT Cloud + 온프렘이 섞인 환경에서 Azure Monitor만 쓰면 나머지가 사각지대가 됩니다. APM·로그 분석 UX도 Datadog보다 떨어집니다. 단일 클라우드에 완전히 고정된 워크로드는 굳이 Datadog을 얹을 필요가 없습니다.

Elastic Stack (ELK)

로그 검색·분석에서 여전히 강력하고 셀프호스팅이 가능합니다. 폐쇄망 요구가 있을 때 유력합니다. 다만 Elasticsearch 클러스터 운영(샤드, 힙, 인덱스 수명주기)은 만만치 않으며 APM·인프라 영역은 상대적으로 약합니다.

Splunk

보안(SIEM)과 대규모 로그 분석의 오랜 강자. 규제 산업의 감사 요구에 강합니다. 비용이 매우 높고 인프라·APM 관측은 Datadog·Dynatrace가 우세합니다.

SigNoz / Uptrace / OpenObserve (OTel 네이티브 신흥)

OpenTelemetry를 1급 시민으로 다루는 오픈소스 대안. 셀프호스팅 시 비용이 극적으로 낮습니다. 단 생태계 성숙도, 통합 개수, 엔터프라이즈 지원은 아직 격차가 있습니다.

🔔 02:47 — PagerDuty 알림: [prod] checkout-api 5xx 에러율 4.2% (임계값 1%)

Step 1 · 영향 범위 확인 (30초)

알림 메시지에 있는 서비스 대시보드 링크를 엽니다. 확인할 것 세 가지: 에러율이 오르는 중인가 안정됐나 / 전체 서비스인가 특정 엔드포인트인가 / 사용자 트래픽은 정상인가. APM Service Page의 Errors by Resource에서 POST /checkout/confirm 하나만 튀는 것을 확인했습니다.

Step 2 · 시간축을 배포와 겹쳐보기 (30초)

그래프 위에 배포 이벤트가 세로선으로 표시됩니다(Module 13에서 이벤트를 보냈기 때문). 02:31에 v2.4.0 배포가 있었고 그 직후부터 에러가 시작됐습니다. 여기서 이미 롤백 의사결정이 가능합니다. 원인 규명보다 사용자 영향 차단이 먼저입니다.

Step 3 · 버전으로 쪼개 확증 (30초)

Step 4 · 근본 원인 (롤백 후, 여유 있게)

실패한 트레이스 하나를 엽니다. Flame Graph에서 payment-gateway 호출 스팬이 3,000ms 후 타임아웃. 스팬에 연결된 로그를 열면 connection pool exhausted. DBM으로 넘어가 보면 v2.4.0이 추가한 쿼리가 인덱스를 타지 않아 커넥션을 오래 점유했습니다.

  • Synthetic 테스트를 CI에 넣어 배포 전 결제 플로우 검증
  • SLO 에러 예산 소모량 기록 — 다음 스프린트 우선순위 근거로 사용

안티패턴과 도입 체크리스트

실패하는 조직들이 공통적으로 하는 8가지와, 첫 90일 체크리스트.

흔한 안티패턴 8가지

❌ 태그 표준 없이 시작

ENV:PROD, env:production, Environment:prod가 공존하면 그룹핑이 깨지고 6개월 뒤엔 되돌리기 어렵습니다. 첫 주에 문서화하고 CI에서 검증하세요.

❌ 모든 로그를 인덱싱

가장 비싼 실수. 제외 필터 없이 containerCollectAll: true를 켜는 순간 청구서가 정해집니다.

❌ 알림 남발

모니터 300개, 하루 알림 200건 → 팀이 무음 처리 → 실제 장애를 놓침. 알림은 사람이 즉시 행동할 것만.

❌ 대시보드 복제

서비스마다 복사하면 관리 불가. 템플릿 변수 하나로 해결됩니다.

❌ 고카디널리티 태그

user_id를 메트릭 태그로. 청구서가 자릿수 단위로 뜁니다.

❌ no data 미설정

Agent가 죽으면 알림도 안 옵니다. 가장 조용한 재난입니다.

❌ UI로만 관리

모니터·대시보드를 클릭으로만 만들면 리뷰도 롤백도 불가능. Terraform으로 코드화하세요.

❌ 원인에만 알림

"CPU 높음"은 사용자에게 아무 의미 없을 수 있습니다. 증상(에러율·지연)에 알림, 원인은 대시보드로.
