11편Neutron 1: 네트워크 모델

“VM은 떴는데 접속이 안 돼요.” 클라우드 운영 문의의 절반은 네트워크입니다. 이번 편은 Neutron의 객체들(네트워크·서브넷·포트·라우터·플로팅 IP·보안 그룹)이 어떻게 이어져 VM의 길을 만드는지, 그리고 VM이 IP와 SSH 키를 받는 DHCP·메타데이터의 경로를 다룹니다. 패킷이 실제로 어떻게 흐르는지(OVN)는 12편에서 이어집니다.

섹션 1

이 편의 목표

  1. 네트워크 · 서브넷 · 포트 · 라우터 · 플로팅 IP · 보안 그룹의 관계를 그림으로 설명한다.
  2. 프로바이더 네트워크와 테넌트(셀프서비스) 네트워크의 차이와 물리망 매핑(physnet)을 설명한다.
  3. VM이 인터넷과 통신하는 데 필요한 요소를 짚고, “접속이 안 된다”를 요소별로 진단한다.
  4. 보안 그룹 규칙을 읽고 패킷 허용 여부를 판정한다.
  5. 포트 보안과 allowed-address-pairs로 VIP(가상 IP) 같은 요구를 안전하게 처리한다.
  6. DHCP와 메타데이터(169.254.169.254) 경로를 설명하고, MTU 문제를 계산으로 찾는다.

이 편의 비유: 아파트 단지의 배선과 경비

네트워크는 동마다 깔린 내부 랜, 서브넷은 그 랜의 주소표, 포트는 벽의 랜 콘센트, 라우터는 동과 바깥을 잇는 관리실 공유기, 플로팅 IP는 세대별 대표 전화번호, 보안 그룹은 콘센트마다 붙은 출입 통제기입니다. DHCP는 입주 때 주소를 알려 주는 관리실, 메타데이터는 입주 안내 봉투(열쇠·이름표)를 주는 창구입니다.

섹션 2

Neutron이 하는 일

Neutron(Networking 서비스)은 프로젝트마다 격리된 가상 네트워크를 API로 만들고 관리합니다. Neutron 자신은 “무엇이 어떻게 연결되어야 하는지”를 기록하고, 실제 패킷 처리는 백엔드가 합니다. RHOSO의 백엔드는 OVN입니다(ML2/OVN).

구성 요소하는 일RHOSO에서 어디에
neutron-server (Neutron API)REST API, DB 기록, 정책 판단, OVN Northbound DB에 논리 설계도 기록OCP Pod (NeutronAPI)
OVN NB/SB DB · ovn-northd논리 설계도 → 노드별 실행 규칙 번역OCP Pod (3편)
ovn-controller각 노드에서 규칙을 OVS에 프로그래밍. 라우팅·NAT·보안 그룹·DHCP 응답까지 처리컴퓨트 노드 컨테이너, (게이트웨이 역할 시) OCP 노드 Pod
OVN 메타데이터 에이전트VM의 169.254.169.254 요청을 Nova 메타데이터로 중계컴퓨트 노드 컨테이너

ML2/OVS 시절과 다른 점

예전 ML2/OVS 구성에서는 DHCP 에이전트, L3(라우터) 에이전트, 메타데이터 에이전트가 따로 있고 네트워크 노드에 네임스페이스(qdhcp-, qrouter-)가 잔뜩 생겼습니다. ML2/OVN에서는 DHCP·라우팅·NAT·보안 그룹을 ovn-controller가 흐름 규칙으로 직접 처리합니다. 그래서 RHOSO에는 DHCP 에이전트·L3 에이전트가 없고, 인터넷에서 찾은 옛 문서의 명령(qrouter 네임스페이스 확인 등)이 그대로 맞지 않습니다.

섹션 3

객체 관계도

객체를 누르면 뜻, 주요 속성, 만드는 명령이 나옵니다.

│ 라우터 게이트웨이 (SNAT)
│ 라우터 인터페이스 (서브넷 게이트웨이 10.0.0.1 · 10.0.1.1)
│ 포트 (가상 NIC)

객체를 눌러 보세요.

관계를 한 문장으로 (2편 복습 + 확장)

네트워크는 L2 영역이고, 그 위에 서브넷(IP 대역)이 하나 이상 있습니다. VM은 포트로 네트워크에 붙고, 포트에 IP와 보안 그룹이 달립니다. 다른 서브넷·외부로 가려면 라우터가 필요하며, 라우터는 인터페이스로 서브넷에, 게이트웨이로 외부 네트워크에 붙습니다. 외부에서 VM으로 들어오려면 플로팅 IP가 VM 포트의 고정 IP와 1:1로 연결되어야 합니다.

섹션 4

프로바이더 vs 테넌트 네트워크

구분프로바이더 네트워크테넌트(셀프서비스) 네트워크
누가 만드나관리자 (물리망 정보 필요)사용자 누구나
물리망과의 관계실제 물리망(VLAN·플랫)에 직접 연결물리망 위에 터널(Geneve)로 감싼 가상망
네트워크 종류flat (태그 없음), vlan (VLAN ID 지정)geneve (RHOSO 기본)
라우팅물리 라우터·방화벽이 게이트웨이 (Neutron 라우터 없이도 가능)Neutron 라우터 필요
쓰임외부 네트워크(플로팅 IP 공급), 기존 사내망 직결, 고성능·레거시 연동고객별 내부망, 자유로운 대역(겹쳐도 됨)
필요한 협업네트워크팀의 스위치 VLAN 설정거의 없음 (tenant 망만 준비, 3편)

물리망 이름(physnet)과 브리지 매핑

프로바이더 네트워크를 만들 때 지정하는 --provider-physical-network datacentre의 datacentre는 실제 장치 이름이 아니라 논리 이름(physnet)입니다. 각 노드는 브리지 매핑(datacentre:br-ex)으로 “이 이름의 망은 내 br-ex 브리지(그리고 거기 연결된 NIC)로 나간다”를 압니다. 물리망 하나에 브리지 하나만 매핑할 수 있습니다.

# 관리자: VLAN 120을 쓰는 프로바이더 네트워크 (외부망 겸용)
openstack network create --external \
   --provider-network-type vlan --provider-physical-network datacentre \
   --provider-segment 120 public
openstack subnet create --network public --subnet-range 203.0.113.0/24 \
   --gateway 203.0.113.1 --allocation-pool start=203.0.113.10,end=203.0.113.200 \
   --no-dhcp public-subnet

# 사용자: 테넌트 네트워크 (종류·VLAN 지정 불필요)
openstack network create app-net
openstack subnet create --network app-net --subnet-range 10.0.0.0/24 app-subnet

공유와 RBAC

관리자가 만든 네트워크를 여러 프로젝트에 쓰게 하려면 --share(모두에게) 또는 네트워크 RBAC(특정 프로젝트에만)를 씁니다. MSP 환경에서는 “고객 전용 프로바이더 VLAN”을 그 고객 프로젝트에만 공유하는 데 유용합니다.

openstack network rbac create --target-project <고객 프로젝트> --action access_as_shared --type network cust-a-vlan200
openstack network rbac create --target-project <고객 프로젝트> --action access_as_external --type network public

고정 IP는 포트가 갖는다

VM에 IP를 “고정”하고 싶다는 요청은, 실제로는 포트에 원하는 IP를 지정하는 것입니다. 포트를 먼저 만들고(openstack port create --network app-net --fixed-ip subnet=app-subnet,ip-address=10.0.0.50 db-port) 그 포트로 VM을 만들면, VM을 지웠다 다시 만들어도 포트를 재사용해 같은 IP를 유지할 수 있습니다.

섹션 6

포트 해부

포트는 Neutron의 가장 중요한 객체입니다. VM NIC뿐 아니라 라우터 인터페이스, 플로팅 IP, 메타데이터 같은 내부 장치도 모두 포트로 표현됩니다.

속성뜻
mac_address · fixed_ipsMAC 주소, 서브넷별 IP
device_owner · device_id누가 이 포트를 쓰나(아래 표)와 그 ID(예: 인스턴스 UUID)
security_groups · port_security_enabled적용된 보안 그룹, 위조 방지 사용 여부 (섹션 9·10)
binding:host_id어느 노드에 연결되었나 (10편 ⑧단계)
binding:vnic_typenormal(OVS 일반), direct(SR-IOV), direct-physical(NIC 통째) 등
binding:vif_type실제 연결 방식(ovs, vhostuser 등). binding_failed면 바인딩 실패
statusACTIVE(연결됨) · DOWN(연결 안 됨 또는 미사용) · BUILD
allowed_address_pairs이 포트로 추가 허용할 IP·MAC (섹션 10)

device_owner 사전

값을 눌러 보세요.

openstack port list --server web-01 --long
openstack port list --network app-net --device-owner network:router_interface
openstack port show <포트 ID> -c binding_host_id -c binding_vif_type -c status -c security_group_ids

섹션 7

라우터 · SNAT · 플로팅 IP

라우터의 두 면

  • 인터페이스: 내부 서브넷에 붙는 다리. 그 서브넷의 게이트웨이 IP(.1)를 가집니다. 여러 서브넷을 붙이면 서로 라우팅됩니다.
  • 외부 게이트웨이: 외부 네트워크에 붙는 다리. 외부 IP 하나를 가지며, 내부 VM이 밖으로 나갈 때 이 IP로 주소를 바꿉니다(SNAT). 그래서 플로팅 IP 없이도 VM은 나갈 수는 있지만, 밖에서 들어올 수는 없습니다.

플로팅 IP

플로팅 IP는 외부 IP를 VM 포트의 고정 IP에 1:1로 연결합니다(들어오는 쪽은 목적지 변환, 나가는 쪽은 출발지 변환). VM 안에서는 플로팅 IP가 보이지 않고 고정 IP만 보이는 것이 정상입니다. 필요한 조건: VM 서브넷이 라우터 인터페이스로, 그 라우터가 외부 게이트웨이로 플로팅 IP의 외부망에 붙어 있어야 합니다.

기능무엇
플로팅 IP외부 IP ⇄ 내부 고정 IP, 모든 포트 1:1
포트 포워딩외부 IP의 특정 포트만 내부 IP:포트로 (플로팅 IP 하나를 여러 VM이 나눠 씀)
SNAT 끄기라우터 게이트웨이 --disable-snat: 내부 주소 그대로 외부로 라우팅 (사내망 직결 등)
 
openstack router create r1
openstack router set --external-gateway public r1
openstack router add subnet r1 app-subnet
openstack floating ip create public
openstack server add floating ip web-01 203.0.113.10
openstack floating ip port forwarding create --internal-ip-address 10.0.0.16 --port <내부 포트 ID> \
   --internal-protocol-port 22 --external-protocol-port 2222 --protocol tcp 203.0.113.10

OVN에서 라우터는 어디서 도나

OVN의 라우터는 특정 서버 하나에 있는 것이 아니라 모든 관련 노드에 분산된 논리 라우터입니다. 같은 프로젝트의 서브넷 간 라우팅은 VM이 있는 컴퓨트 노드에서 바로 처리됩니다. 외부로 나가는 SNAT·플로팅 IP는 구성에 따라 게이트웨이 섀시(OCP 노드·네트워커 노드, 3편)에서 처리되거나, 분산 플로팅 IP를 켜고 컴퓨트 노드가 외부망에 붙어 있으면 컴퓨트 노드에서 바로 처리됩니다. 자세한 패킷 경로는 12편.

섹션 8

연결성 진단기: 무엇이 빠지면 무엇이 안 되나

아래 구성 요소를 켜고 끄면 네 가지 통신 시험의 결과와 이유가 바뀝니다. “접속이 안 돼요” 문의를 받으면 이 순서대로 확인하면 됩니다.

섹션 9

보안 그룹

보안 그룹은 포트 단위의 상태 저장(stateful) 방화벽입니다. 규칙은 “허용 목록”만 있고, 어느 규칙에도 맞지 않는 트래픽은 버려집니다. 나간 연결의 응답은 자동으로 허용됩니다(stateful).

규칙 칸뜻
방향 (ingress / egress)VM으로 들어오는 / VM에서 나가는
이더 타입 (IPv4 / IPv6)규칙은 버전별로 따로
프로토콜 · 포트 범위tcp 22, udp 53, icmp 등. 비우면 전부
원격 IP 접두어 (remote IP prefix)상대 주소 범위 (예: 0.0.0.0/0, 192.168.10.0/24)
원격 그룹 (remote group)“이 보안 그룹에 속한 포트들”을 상대로 지정. IP가 바뀌어도 규칙 유지

기본 보안 그룹 (default)

프로젝트마다 자동으로 생기는 default 그룹은 나가는 트래픽 전부 허용, 같은 default 그룹 멤버끼리 들어오는 트래픽 허용, 그 밖의 들어오는 트래픽은 차단입니다. 그래서 새 VM에 외부에서 SSH가 안 되는 것이 정상이며, 22번 규칙을 추가해야 합니다. 2편에서 본 대로 Kubernetes NetworkPolicy와 기본값이 반대입니다.

보안 그룹 규칙 평가기

openstack security group create web-sg
openstack security group rule create --ingress --protocol tcp --dst-port 22 --remote-ip 192.168.10.0/24 web-sg
openstack security group rule create --ingress --protocol tcp --dst-port 443 --remote-ip 0.0.0.0/0 web-sg
openstack security group rule create --ingress --protocol tcp --dst-port 8080 --remote-group web-sg web-sg
openstack server add security group web-01 web-sg
openstack security group rule list web-sg --long

흔한 실수

  • 규칙을 고쳤는데 VM에 그 그룹이 붙어 있지 않음 (보안 그룹은 VM이 아니라 포트에 붙음, VM에 NIC가 둘이면 각각 확인).
  • SSH를 0.0.0.0/0에 열어 둠 → 무차별 대입 공격 대상. 관리망·배스천(jump) 호스트로 좁히세요.
  • ping이 안 된다고 네트워크 장애로 판단 → ICMP 규칙이 없을 뿐인 경우가 많음.

섹션 10

포트 보안과 allowed-address-pairs

포트 보안(기본 켜짐)은 보안 그룹과 함께 위조 방지를 합니다. 포트에 등록된 MAC·IP가 아닌 주소로 나가는 패킷을 버립니다. 그래서 한 VM이 다른 VM의 IP를 사칭하거나, 등록되지 않은 IP로 통신하는 것을 막습니다.

그런데 VIP가 필요하다면

keepalived(VRRP)로 두 VM이 가상 IP(VIP)를 주고받는 고가용성 구성이나, VM이 라우터·방화벽 역할을 하는 경우에는 포트에 등록되지 않은 IP를 써야 합니다. 이때 포트 보안을 끄지 말고, allowed-address-pairs로 필요한 주소만 추가 허용합니다.

# 1) VIP용 포트를 만들어 IP를 확보 (다른 VM에 자동 할당되지 않게)
openstack port create --network app-net --fixed-ip ip-address=10.0.0.100 vip-port
# 2) 두 VM의 포트에 VIP를 허용 주소로 추가
openstack port set --allowed-address ip-address=10.0.0.100 <web-01 포트>
openstack port set --allowed-address ip-address=10.0.0.100 <web-02 포트>
# 3) VRRP(프로토콜 112) 통신 허용 규칙
openstack security group rule create --ingress --protocol 112 --remote-group web-sg web-sg
# 4) 외부 노출이 필요하면 VIP 포트에 플로팅 IP 연결
openstack floating ip set --port vip-port 203.0.113.20
방법보안언제
allowed-address-pairs필요한 주소만 열림, 보안 그룹 유지VIP, 일부 추가 주소 (권장)
포트 보안 끄기 (--disable-port-security)위조 방지·보안 그룹 모두 해제. 먼저 보안 그룹을 모두 떼야 가능VM이 라우터·방화벽·NFV 장비 역할을 하며 임의 주소를 중계할 때

MSP 관점

고객이 “포트 보안 꺼 주세요”라고 요청하면 바로 끄지 말고 목적을 물으세요. 대부분 VIP 때문이고 allowed-address-pairs로 해결됩니다. 포트 보안을 끄면 그 VM은 같은 네트워크에서 다른 주소를 사칭할 수 있으므로, 보안 책임 범위를 문서로 남깁니다.

섹션 11

DHCP

VM은 부팅 때 DHCP로 IP·게이트웨이·DNS·MTU 등을 받습니다(10편 ⑭단계). ML2/OVN에서는 별도 DHCP 서버가 없고, VM이 있는 컴퓨트 노드의 ovn-controller가 DHCP 요청을 가로채 서브넷 정보로 직접 응답합니다. 그래서 DHCP 에이전트 장애 같은 것이 없고, 대신 해당 노드의 ovn-controller와 포트 바인딩이 정상이어야 합니다.

DHCP로 전달되는 것출처
IP 주소포트의 고정 IP (Neutron이 이미 정해 둠)
게이트웨이·서브넷 마스크서브넷 설정
DNS 서버·도메인서브넷 dns_nameservers, 네트워크 DNS 설정
MTU네트워크 MTU (섹션 13)
추가 경로서브넷 host routes, 메타데이터 경로가 필요한 경우

DHCP를 끈 서브넷의 VM은?

IP는 Neutron이 포트에 이미 정해 두었지만 VM이 그 사실을 알 방법이 없습니다. 이 경우 VM은 설정 드라이브(config drive)의 네트워크 정보로 cloud-init이 정적 설정을 하거나, 이미지에 미리 설정해 두어야 합니다. 보통 테넌트망은 DHCP를 켜 둡니다.

섹션 13

MTU 계산기

MTU는 한 번에 보낼 수 있는 패킷의 최대 크기입니다. 테넌트망은 Geneve 터널로 감싸지므로 그 머리말만큼 VM이 쓸 수 있는 크기가 줄어듭니다. MTU가 어긋나면 “ping과 SSH 접속은 되는데 큰 파일 전송이나 웹 페이지가 멈추는” 이상한 장애가 납니다.

Neutron은 global_physnet_mtu(물리망 MTU)에서 터널 머리말만큼 빼 네트워크 MTU를 자동 계산합니다. OVN의 Geneve는 IPv4 기준 약 58바이트를 씁니다. 실제 값은 openstack network show <망> -c mtu로 확인하세요.

섹션 14

RHOSO의 Neutron

컨트롤 플레인: neutron 칸

neutron:
  apiOverride: { route: {} }
  template:
    databaseInstance: openstack
    secret: osp-secret
    replicas: 3
    networkAttachments: [internalapi]
    customServiceConfig: |                 # ML2 기본값을 바꿀 때만 (예)
      [DEFAULT]
      global_physnet_mtu = 9000
      [ml2]
      tenant_network_types = geneve
      [ml2_type_vlan]
      network_vlan_ranges = datacentre:100:299
  ovn:
    template:
      ovnController:
        nicMappings:
          datacentre: ospbr                      # OCP 노드에서 physnet → 인터페이스 (게이트웨이 역할 시)

학습용으로 단순화했습니다. physnet 이름(datacentre)과 VLAN 범위는 환경에 맞게, 컨트롤 플레인·데이터 플레인 양쪽이 같은 이름을 쓰도록 맞춥니다.

데이터 플레인: 브리지 매핑

컴퓨트(·네트워커) 노드의 브리지 매핑은 NodeSet의 Ansible 변수로 지정하고, 노드 네트워크 템플릿(3편 edpm_network_config_template)에 그 브리지를 만들어 둡니다.

nodeTemplate:
  ansible:
    ansibleVars:
      edpm_ovn_bridge_mappings: ["datacentre:br-ex"]   # physnet → OVS 브리지
      # edpm_network_config_template 안에 br-ex 브리지와 연결할 NIC 정의

사용자 권한(member)으로 프로젝트 안에서 외부 접속 가능한 웹 서버를 만드는 전체 순서입니다. 외부망(public)은 관리자가 미리 만들어 두었다고 가정합니다. 21편(첫 인스턴스 띄우기)에서 그대로 실행합니다.

섹션 20

정리와 다음 편

오늘의 핵심 여덟 문장

  • Neutron은 가상 네트워크를 기록하고, 실제 처리는 OVN이 한다. RHOSO에는 DHCP·L3 에이전트가 없다.
  • 네트워크(L2) → 서브넷(IP) → 포트(NIC·IP·보안 그룹) → 라우터(인터페이스·게이트웨이) → 플로팅 IP가 VM의 길이다.
  • 프로바이더는 관리자가 물리 VLAN·플랫에 직결, 테넌트는 사용자가 Geneve 터널 위에 자유롭게. physnet 이름은 브리지 매핑으로 실제 브리지에 연결된다.
  • 라우터 게이트웨이의 SNAT로 나갈 수는 있지만, 들어오려면 플로팅 IP(또는 포트 포워딩)가 필요하다.
  • 보안 그룹은 허용 목록·상태 저장, 기본은 들어오는 것 차단. 규칙은 포트에 붙은 그룹에만 적용된다.
  • VIP는 포트 보안을 끄지 말고 allowed-address-pairs로 필요한 주소만 연다.
  • DHCP는 ovn-controller가 직접 응답, 메타데이터는 노드의 ovnmeta 네임스페이스 → 에이전트 → nova-metadata.
  • 테넌트망 MTU는 물리망 MTU − Geneve 머리말. 어긋나면 큰 패킷만 멈춘다.
