Tempo 구축·운영 실전고객사 규모에 맞게 띄우고, 나누고, 오래 굴리기

운영 설계의 출발점은 "피크 때 초당 몇 MB가 들어오는가"입니다. 아래 배포 계획기에 고객사의 수집량과 가용 영역 수를 넣으면, 공식 크기 산정 가이드를 바탕으로 Kafka 파티션 수와 부품별 인스턴스 수, 자원 규모가 계산됩니다.

live-store 가용 영역

부품별 수치는 Tempo 공식 문서 "Size the cluster"의 예시 값(distributor 10MB/s당 1개, live-store 6~10MB/s당 1개, querier 1~2MB/s당 1개, 파티션당 피크 약 10MB/s 등)을 옮긴 것입니다. 실제 필요량은 트레이스 구조와 조회 패턴에 따라 크게 달라지므로 출발점으로만 쓰세요.

1

실습: monolithic Tempo 띄우기

노트북 한 대에서 3.0의 전체 흐름을 보는 실습입니다. monolithic 모드라 Kafka가 필요 없습니다. 객체 스토리지로 MinIO(S3 호환)를 쓰고, metrics-generator가 만든 메트릭은 Prometheus로, 조회는 Grafana로 합니다. 트레이스는 3편에서 쓴 HotROD가 만들어 줍니다. 네 파일을 한 폴더에 받아 docker compose up -d로 띄우세요.


    

  

  

    
실습용 설정입니다

    
MinIO 계정이 설정 파일에 그대로 있고, Grafana는 로그인 없이 관리자 권한으로 열립니다. 운영에서는 객체 스토리지 자격 증명을 IAM 역할(IRSA, Workload Identity 등)이나 Secret으로 주입하고, Grafana는 사내 IdP와 연결하세요.

  







  
2
동작 확인 순서

  
3편 Jaeger 실습과 마찬가지로 데이터가 흐르는 순서대로 확인합니다. HotROD(http://localhost:8080)에서 버튼을 몇 번 누른 뒤 진행하세요.

  

    
확인 순서명령·위치정상이라면

    
      
1. Tempo가 준비됐나curl -s localhost:3200/readyready 응답

      
2. 스팬을 받고 있나curl -s localhost:3200/metrics | grep tempo_distributor_spans_received_total클릭할 때마다 증가. tempo_discarded_spans_total은 늘지 않음

      
3. 바로 조회되나 (live-store)Grafana(http://localhost:3000) → Explore → Tempo → TraceQL { }방금 만든 트레이스가 보임. 이 시점엔 아직 객체 스토리지에 없음

      
4. 블록이 쌓이나MinIO 콘솔(http://localhost:9001) → tempo 버킷single-tenant/블록ID/ 폴더에 meta.json, data.parquet 등이 생김

      
5. 메트릭이 만들어지나Prometheus(http://localhost:9090)에서 traces_spanmetrics로 검색호출 수·지연 시간 메트릭이 보임. Grafana Explore의 Service Graph 탭에 서비스 관계도가 그려짐

    
  

  

    
테넌트 폴더 이름이 single-tenant인 이유

    
멀티테넌시를 켜지 않으면 모든 데이터가 기본 테넌트 single-tenant로 저장됩니다. 5장에서 멀티테넌시를 켜면 X-Scope-OrgID 헤더 값마다 폴더가 따로 생깁니다. 블록 폴더 구조와 파일의 의미는 4편 6장을 참고하세요.

  

  

    
5편 쿼리를 실제로 돌려 보세요

    
HotROD의 서비스 이름(frontend, customer, driver, route, redis-manual, mysql)으로 바꿔서 5편 레시피를 실행해 보세요. 예: { resource.service.name = "customer" } | quantile_over_time(duration, .95). TraceQL metrics는 Grafana Explore에서 쿼리 유형을 메트릭으로 두고 실행합니다.

  







  
3
Kubernetes: microservices 배포

  
Tempo 공식 Helm 차트는 grafana-community 저장소로 옮겨졌습니다. 옛 grafana/helm-charts 저장소를 참조하는 자료라면 저장소 주소부터 확인하세요.

  

    
차트배포 모드기준 버전잘 맞는 곳

    
      
tempomonolithic3.0.0 (앱 3.0.3)PoC, 개발, 소규모 고객사

      
tempo-distributedmicroservices3.7.0 (앱 3.0.3)운영, 대용량, 멀티테넌트 공용 플랫폼

    
  

  

    

    

    

  

  

    
가장 중요한 규칙: 세 숫자를 맞춘다

    
Kafka 파티션 수 = block-builder 수 = (영역당) live-store 수. block-builder는 순번(ordinal)으로 파티션을 하나씩 맡습니다(block-builder-0 → 파티션 0). 셋이 어긋나면 어떤 파티션은 블록이 만들어지지 않거나 최근 데이터가 조회되지 않습니다. tempo-mixin에는 이를 잡는 TempoBlockBuildersPartitionsMismatch, TempoLiveStoresPartitionsUnowned 경보가 있습니다. 공식 문서는 block-builder 수를 live-store 수에 맞춰 자동으로 따라가게 하는 방법으로 KEDA, Grafana rollout-operator의 미러링 기능, 또는 고정 개수를 제시합니다.

  







  
4
Kafka 설계

  
Tempo는 모든 트레이스 데이터를 토픽 하나(ingest.kafka.topic)에 씁니다. 설계할 것은 사실상 파티션 수, 보존 기간, 인증 세 가지입니다.

  

    
항목권장이유

    
      
파티션 수피크 약 10MB/s당 1개에서 출발, 성장 여유를 더함block-builder·live-store 확장 상한. 나중에 늘리면 live-store 확장 절차(pending → active)가 필요 (4편)

      
토픽 생성다른 서비스와 Kafka를 공유하면 직접 생성자동 생성 옵션(auto_create_topic_default_partitions)은 브로커 전체의 기본 파티션 수(num.partitions)를 바꿔 다른 토픽에도 영향

      
토픽 보존수 시간~하루 정도로 짧게장기 저장은 객체 스토리지가 맡음. block-builder·live-store가 장애 후 따라잡을 시간만 확보하면 됨

      
인증ingest.kafka.sasl_username, sasl_password관리형 Kafka(MSK, Confluent 등) 연결 시

      
제품Apache Kafka, Redpanda, WarpStream 등 Kafka 호환공식 예제는 Redpanda, 문서는 WarpStream도 언급

    
  


ingest:
  kafka:
    address: kafka-0.kafka.svc:9092,kafka-1.kafka.svc:9092
    topic: tempo-traces
    # 운영에서는 토픽을 직접 만들고 아래 두 줄은 쓰지 않는 편이 안전
    # auto_create_topic_enabled: true
    # auto_create_topic_default_partitions: 12

  

    
새로 띄운 live-store가 30분 동안 준비가 안 된다면

    
트래픽이 전혀 없는 새 배포에서는 live-store가 따라잡아야 할 Kafka 기준점이 없어 live_store.readiness_max_wait(기본 30분)까지 준비 상태가 되지 않을 수 있습니다. 공식 문서가 밝힌 정상 동작이며, 트래픽이 흐르기 시작하면 해소됩니다.

  







  
5
멀티테넌시와 overrides

  
MSP가 Tempo 하나로 여러 고객사를 받으려면 테넌트로 나눕니다. multitenancy_enabled: true를 켜면 쓰기와 읽기 모든 요청에 X-Scope-OrgID 헤더가 있어야 하고, 데이터는 객체 스토리지에서 테넌트별 폴더로 분리됩니다. 고객사 쪽 OTel Collector에서 헤더를 붙여 보냅니다.


exporters:
  otlp/tempo:
    endpoint: tempo-distributor.observability:4317
    headers:
      X-Scope-OrgID: customer-a      # 고객사(테넌트) ID

  
Grafana에서는 고객사별 Tempo 데이터 소스를 만들고 HTTP 헤더에 같은 값을 넣습니다. 헤더를 누구나 바꿔 보낼 수 있으므로, 실제 격리는 앞단 게이트웨이나 인증 프록시가 테넌트를 확인하고 헤더를 붙이는 구조로 보장해야 합니다.


  
overrides: 테넌트별 한도

  
overrides는 테넌트마다 수집량, 트레이스 크기, 보존 기간, 메트릭 생성 등을 따로 정하는 설정입니다. overrides.defaults가 기본값이고, 테넌트별 값은 별도 파일(per_tenant_override_config)에 두면 재시작 없이 주기적으로 다시 읽습니다(기본 10초).

  

    
테넌트별 설정은 defaults를 물려받지 않습니다

    
테넌트 항목을 하나 만들면 그 테넌트는 그 항목에 적은 값만 씁니다. 공식 이전 가이드는 이 점을 들어 "모든 테넌트 항목에 명시적으로 넣으라"고 강조하고, Helm 차트도 테넌트 블록마다 모든 값을 적으라고 안내합니다. 수집 한도만 바꾸려고 테넌트 항목을 만들었다가 메트릭 생성이나 보존 기간이 빠지는 실수가 흔합니다. 아래 생성기는 그래서 각 테넌트에 전체 값을 모두 적습니다.

  

  

    

      
Basic수집 5MB/s · 트레이스 최대 2MB · 보존 7일 · 메트릭 생성 없음

      
Standard수집 15MB/s · 트레이스 최대 5MB · 보존 14일 · span-metrics · 시계열 5만

      
Premium수집 40MB/s · 트레이스 최대 10MB · 보존 30일 · span-metrics + service-graphs · 시계열 20만

    

    
테넌트 ID요금제보존 기간 조정비고

    

    

    

    
요금제 값은 설명을 위한 예시입니다. 3.0은 옛 평평한(범위 없는) 형식을 거부하므로 위처럼 ingestion:, global:, compaction:, metrics_generator: 범위로 묶은 형식을 씁니다.

  

  

    
한도를 넘으면 나오는 오류의미조정할 값

    
      
RATE_LIMITED테넌트 수집 속도 초과 (distributor에서 즉시 거부)ingestion.rate_limit_bytes, burst_size_bytes

      
TRACE_TOO_LARGE트레이스 하나가 최대 크기 초과global.max_bytes_per_trace (기본 5MB)

      
LIVE_TRACES_EXCEEDEDlive-store에 동시에 살아 있는 트레이스가 너무 많음ingestion.max_traces_per_user (기본 1만)

    
  







  
6
metrics-generator와 카디널리티

  
metrics-generator는 트레이스에서 RED 메트릭(span-metrics)과 서비스 관계도(service-graphs)를 만들어 Prometheus·Mimir로 remote write 합니다. 3편 Jaeger의 spanmetrics 커넥터와 같은 역할이고, 5편 TraceQL metrics와 달리 미리 만들어 두므로 장기 대시보드와 경보에 적합합니다. microservices 모드에서는 Kafka에서 직접 읽으며, 어떤 프로세서를 켤지는 테넌트별 overrides의 metrics_generator.processors로 정합니다.

  
운영에서 가장 자주 터지는 문제는 카디널리티 폭증입니다. 메트릭 레이블(차원)에 값의 종류가 많은 속성을 넣으면 시계열 수가 곱셈으로 늘어납니다. 아래에서 차원과 보호 장치를 바꿔 보세요.

  

    

    

    

    
0

    

  

  

    
보호 장치 (overrides)하는 일

    
      
max_active_series테넌트가 만들 수 있는 활성 시계열 총량 상한

      
max_cardinality_per_label (3.0)레이블 하나가 가질 수 있는 값 종류를 제한. 한 레이블이 예산 전체를 먹는 것을 막음

      
span_name_sanitization (3.0, 실험적)DRAIN 알고리즘으로 스팬 이름의 가변 부분을 <_>로 바꿈. GET /users/123 같은 이름이 하나로 묶임. 계측을 못 고치는 고객사에 유용

      
filter_policies헬스 체크 같은 잡음 스팬을 메트릭에서 제외. 3.0부터 service-graphs에도 적용

      
span_multiplier_key (3.0)head 샘플링 비율이 담긴 속성을 지정하면 메트릭 수치를 실제 트래픽 규모로 보정

    
  


overrides:
  defaults:
    metrics_generator:
      processors: [span-metrics, service-graphs]
      max_active_series: 100000
      max_cardinality_per_label: 500
      span_name_sanitization: "enabled"
      processor:
        span_metrics:
          dimensions: [http.route]         # 레이블로 추가할 속성. user.id 같은 값은 절대 넣지 않기
          filter_policies:
            - exclude:
                match_type: regex
                attributes:
                  - key: span.http.route
                    value: "/health.*|/metrics"







  
7
보존·압축·삭제·전용 열

  

    
작업설정·도구포인트

    
      
보존 기간전역 block_retention(기본 336h = 14일), 테넌트별 overrides.<테넌트>.compaction.block_retention테넌트 값이 0s면 전역 값을 따름. 고객사 계약별 보존 기간을 overrides로 구현

      
압축backend scheduler(1개) + backend worker(여러 개)블록이 밀리면 worker를 늘림. 이전 기간처럼 블록이 급증한 뒤에는 한동안 늘렸다가 줄임

      
삭제 요청tempo-cli redact → 스케줄러가 블록을 다시 씀진행 상황은 /status/backendscheduler에서 확인

      
전용 열storage.trace.block.parquet_dedicated_columns 또는 테넌트별 overridestempo-cli analyse blocks로 크고 자주 쓰이는 속성 확인. 설정 이후 만들어지는 블록부터 적용

      
블록 형식storage.trace.block.version3.0 기본 vParquet4. vParquet5로 바꾸면 새 블록만 v5, 기존 블록은 그대로 읽음

    
  







  
8
Tempo 자체 모니터링

  
Tempo 저장소의 operations/tempo-mixin에는 공식 대시보드와 경보 규칙이 들어 있습니다. 3.0 구조에 맞춰 ingester·compactor 경보는 없어지고 live-store·block-builder·backend 경보로 바뀌었습니다. 먼저 걸어 둘 경보를 추렸습니다.

  

    
수집tempo_distributor_spans_received_total
tempo_discarded_spans_total{reason}

    
Kafka 쓰기tempo_distributor_kafka_write_bytes_total
..._kafka_write_latency_seconds

    
지연(lag)tempo_ingest_group_partition_lag_seconds

    
블록tempo_block_builder_fetch_records_total
..._fetch_errors_total

    
최근 조회tempo_live_store_ready
tempo_live_store_records_dropped_total

  

  

    
tempo-mixin 경보무엇을 알려 주나

    
      
TempoBlockBuilderPartitionLagWarning/Criticalblock-builder가 Kafka를 못 따라감 → 객체 스토리지 반영 지연

      
TempoLiveStorePartitionLagWarning, TempoLiveStoreAllMembersLagginglive-store 지연 → 최근 데이터 조회 오류(3.0 기본 fail_on_high_lag)

      
TempoLiveStoresPartitionsUnowned주인 없는 파티션 → 최근 데이터 공백

      
TempoBlockBuildersPartitionsMismatchblock-builder 수와 파티션 수 불일치

      
TempoBackendSchedulerJobsFailureRateHigh압축·보존 작업 실패 증가

      
TempoCompactionTooManyOutstandingBlocks압축이 밀려 블록 수 급증 → 조회 느려짐

      
TempoMetricsGeneratorServiceGraphsDroppingSpans서비스 그래프가 스팬을 버림 (짝을 못 찾거나 한도 초과)

      
TempoBadOverridesoverrides 파일 오류로 새 설정이 반영되지 않음

Tempo Vulture: 종단 간 시험기

    
Vulture는 distributor에 트레이스를 직접 써 넣고 query-frontend로 다시 읽어 전체 경로를 검증하는 공식 도구입니다. 고객사별 Tempo에 하나씩 붙여 두면 "수집은 되는데 조회가 안 되는" 문제를 사용자보다 먼저 알 수 있습니다. 확인할 지표는 tempo_vulture_trace_total(증가)과 tempo_vulture_trace_error_total(0 유지)입니다.

  







  
9
2.x에서 3.0으로 옮기기

  
monolithic이라면 간단합니다. tempo-cli migrate config --mode=monolithic old.yaml > new.yaml로 설정을 변환하고 바이너리를 올린 뒤, 과거 트레이스가 조회되는지 확인하면 됩니다. microservices는 3.0을 2.x 옆에 나란히 띄우고 트래픽을 옮기는 방식입니다. 3.0에서 2.x로 그 자리에서 되돌리는 방법은 없으니, 2.x를 정리하기 전까지가 되돌릴 수 있는 구간입니다. 체크하며 진행해 보세요.

  

  

  

  

    
과거 데이터는 어떻게 보이나

    
3.0은 2.x가 쓴 RF3 블록과 3.0의 RF1 블록을 모두 자동으로 읽으므로 TraceQL 검색과 Trace ID 조회는 전체 기간에 대해 동작합니다. 단, TraceQL metrics는 RF1 블록만 읽습니다. 2.x에서 metrics-generator의 local-blocks 프로세서를 쓰지 않았다면 메트릭 쿼리는 3.0 전환 이후 데이터만 보입니다. 고객사에 미리 알려 두세요.

정리와 다음 편

  
    
    
  1. 설계의 출발점은 피크 수집량입니다. 파티션은 피크 약 10MB/s당 1개에서 시작하고, 파티션 수 = block-builder 수 = 영역당 live-store 수를 지킵니다.
    2. 
    
  2. Helm 차트는 grafana-community 저장소의 tempo(monolithic)와 tempo-distributed(microservices)입니다.
    3. 
    
  3. 멀티테넌시는 X-Scope-OrgID로 나누고, 테넌트별 한도는 overrides로 정하며, 테넌트 항목은 defaults를 물려받지 않으므로 모든 값을 적습니다.
    4. 
    
  4. metrics-generator는 카디널리티가 생명입니다. 차원을 신중히 고르고 max_active_series, max_cardinality_per_label, 스팬 이름 정리로 막습니다.
    5. 
    
  5. 2.x → 3.0은 monolithic은 설정 변환 후 교체, microservices는 나란히 배포 → 압축 끄기 → 검증 → 트래픽 전환 → 2.x 정리 → 압축 켜기 순서입니다.

7편 · 신호 연결과 장애 조사 실전

    
트레이스만으로는 "왜"까지 가기 어렵습니다. Grafana에서 트레이스와 로그(Loki), 메트릭의 exemplar, 프로파일(Pyroscope)을 서로 오가게 연결하고, Jaeger 쪽 연결 방식과 비교한 뒤, "응답 지연 급증" 장애를 처음부터 끝까지 조사하는 시뮬레이션을 합니다. Tempo·Jaeger의 MCP 서버로 LLM 에이전트가 트레이스를 조사 도구로 쓰는 AIOps 연동도 다룹니다.
