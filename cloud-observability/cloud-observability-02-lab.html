Cloud 모니터링·로깅 실전 강의 2편 (Level 1. 전체 지도)

실습 랩 구축
노트북 위의 하이브리드 클라우드

고객사 Kubernetes, 온프레미스 서버, MSP 중앙 관제 클러스터, 오브젝트 스토리지를 한 대의 머신에 축소해 옮깁니다. 이 랩은 18편까지 계속 쓰이므로, 오늘 만드는 모든 것은 파일로 남겨 언제든 다시 만들 수 있게 합니다.

대상: 1~2년차 클라우드 엔지니어 형식: 단계별 구축 실습 예상 소요: 2~3시간 기준: kind v0.32, Kubernetes 1.36
오늘 완성할 랩 구성 요소를 누르면 역할, 접속 주소, 사용하는 편이 표시됩니다

구성 요소를 선택하세요

파란 화살표 A~D는 데이터가 오가는 네트워크 경로입니다. 각 경로는 2장에서 자세히 설명합니다.

0시작하기 전에

1편에서 그린 지도를 실제로 손에 잡히는 환경으로 옮기는 편입니다. 무엇을 준비해야 하고 어디까지 하면 끝인지 먼저 확인합니다.

학습 목표

  1. 하이브리드 클라우드의 구성 요소를 kind, Multipass, 컨테이너로 축소 재현하고 각각이 현실의 무엇에 해당하는지 설명할 수 있다.
  2. 클러스터 간, VM과 클러스터 간, 클러스터와 스토리지 간의 세 가지 네트워크 경로를 구성하고 점검할 수 있다.
  3. S3 호환 오브젝트 스토리지를 띄우고 이후 편에서 쓸 버킷을 미리 준비할 수 있다.
  4. OpenTelemetry Demo를 배포하고 장애 주입 플래그의 위치를 안다.
  5. 랩 전체를 설정 파일과 스크립트로 관리해 언제든 삭제하고 다시 만들 수 있다.

원칙: 손으로 만든 것은 파일로 남긴다

클러스터 설정, VM 초기화 스크립트, Helm values, 점검 스크립트를 모두 ~/obs-lab 폴더에 파일로 저장하고 Git으로 관리합니다. 실습 중에 망가뜨려도 삭제 후 몇 분 안에 같은 상태로 되돌릴 수 있고, 이 습관은 고객사 환경을 코드로 관리하는 실무와 그대로 이어집니다.

1랩 설계: 현실과의 대응

랩의 모든 구성 요소는 MSP 현장의 무언가를 흉내 냅니다. 대응 관계를 알고 실습하면 랩에서 배운 것이 고객사 환경으로 바로 옮겨집니다.

랩 구성 요소현실에서의 역할재현하는 것단순화한 것
edge (kind)고객사 A의 AKS, EKS, OCP멀티 노드, DaemonSet 수집, 네임스페이스 분리, MSA 워크로드관리형 컨트롤 플레인, 클라우드 로드밸런서, 노드 자동 확장

cust-a-web, cust-a-db (Multipass)고객사 온프레미스 서버systemd 서비스, 패키지 설치, 에이전트 배포, 클러스터 밖에서 들어오는 수집 경로방화벽 장비, 프록시, 수백 대 규모

클러스터를 하나만 만들지 않고 hub와 edge로 나눈 이유가 중요합니다. 실제 MSP에서는 관측 데이터를 만드는 곳(고객사)과 저장하고 보는 곳(관제 센터)이 거의 항상 다릅니다. 이 둘이 분리돼 있어야 "고객사에서 중앙으로 어떻게 보내는가", "고객사별로 데이터를 어떻게 나누는가", "중앙이 멈추면 고객사 쪽 데이터는 어떻게 되는가" 같은 실무 질문을 실습할 수 있습니다.

2네트워크 경로 3가지

관측 시스템 장애의 상당수는 도구가 아니라 네트워크 경로에서 생깁니다. 랩의 경로를 먼저 이해하면 이후 편에서 "데이터가 안 들어온다"를 스스로 진단할 수 있습니다.

경로 A: edge 파드에서 hub로

kind 노드는 사실 Docker 컨테이너이고, 두 클러스터의 노드는 모두 kind라는 Docker 네트워크에 붙어 있습니다. Docker의 사용자 정의 네트워크는 컨테이너 이름으로 서로를 찾을 수 있게 내장 DNS를 제공하므로, edge의 파드는 hub-control-plane:30999처럼 hub 노드 이름과 NodePort로 바로 접근할 수 있습니다. 현실에서는 고객사 VNet과 관제 센터 사이의 VPN이나 Private Link에 해당합니다.

경로 B: 온프레미스 VM에서 hub로

Multipass VM은 Docker 네트워크가 아니라 별도의 가상 브리지에 있어서 kind 노드에 직접 닿지 못합니다. 그래서 hub 클러스터를 만들 때 extraPortMappings로 hub 노드의 NodePort를 호스트의 같은 포트 번호에 연결하고, VM은 자신의 기본 게이트웨이(곧 호스트)의 그 포트로 데이터를 보냅니다. 현실에서는 고객사 데이터센터에서 방화벽 정책을 열어 관제 센터의 공개 수신 엔드포인트로 보내는 구조와 같습니다.

경로 C: hub에서 오브젝트 스토리지로

SeaweedFS 컨테이너도 kind 네트워크에 붙여 두면 hub의 파드가 http://lab-s3:8333으로 접근할 수 있습니다. 스토리지를 클러스터 안이 아닌 밖에 두는 이유는 현실의 S3나 Blob Storage가 클러스터 밖의 관리형 서비스이기 때문입니다. 클러스터를 지우고 다시 만들어도 저장된 데이터가 남는다는 장점도 있습니다.

경로 D: 내 브라우저에서 랩으로

점선 화살표는 관리 경로입니다. 데모 쇼핑몰은 kubectl port-forward로, hub의 UI는 호스트 포트로 접속합니다. 데이터 흐름이 아니므로 그림에서 점선으로 구분했습니다.

보안 메모

extraPortMappings에서 listenAddress: "0.0.0.0"을 쓰면 호스트의 모든 네트워크 인터페이스에 포트가 열립니다. 랩 머신이 회사 네트워크나 공용 와이파이에 연결돼 있다면 같은 네트워크의 다른 사람도 접근할 수 있습니다. 랩 용도로만 쓰고, 필요하면 Multipass 브리지 IP로 좁히거나 호스트 방화벽으로 막으세요.

4Step 1. 호스트 준비

도구를 설치하고, 여러 kind 클러스터와 VM이 함께 돌 수 있도록 커널 설정과 방화벽을 손봅니다.

작업 폴더와 기본 점검

mkdir -p ~/obs-lab/{kind,vm,apps,scripts} && cd ~/obs-lab
git init -q

# cgroup v2 확인: "cgroup2fs"가 출력되어야 합니다 (macOS는 건너뜀)
stat -fc %T /sys/fs/cgroup/

Kubernetes 1.35부터 cgroup v1 지원이 제거되기 시작했고, kind의 최신 노드 이미지도 같은 방향을 따릅니다. Ubuntu 22.04 이후 버전은 기본이 cgroup v2이므로 대부분 문제없습니다.

커널 한도 상향 (Linux)

kind 클러스터를 여러 개 띄우면 각 노드가 파일 변경 감시(inotify)를 많이 사용해 "too many open files" 오류가 나기 쉽습니다. 미리 한도를 올려 둡니다.

sudo tee /etc/sysctl.d/99-obs-lab.conf >/dev/null <<'EOF'
fs.inotify.max_user_watches = 524288
fs.inotify.max_user_instances = 512
EOF
sudo sysctl --system | grep inotify

Docker와 Multipass를 함께 쓸 때의 방화벽 설정

같은 Linux 호스트에서 둘을 함께 쓰면 자주 만나는 문제가 있습니다. Docker는 설치될 때 iptables의 FORWARD 정책을 DROP으로 바꾸는데, 이 때문에 Multipass VM의 트래픽이 호스트를 지나 인터넷으로 나가지 못합니다. 증상은 VM 안에서 apt가 멈추거나 cloud-init의 패키지 설치가 실패하는 것입니다. VM을 만들기 전에 Multipass 브리지 트래픽을 허용해 둡니다.

# Multipass 브리지 이름 확인 (기본 qemu 드라이버는 mpqemubr0)
ip -br link | grep -E 'mpqemubr|mpbr'

sudo iptables -I DOCKER-USER -i mpqemubr0 -j ACCEPT
sudo iptables -I DOCKER-USER -o mpqemubr0 -j ACCEPT

# ufw를 쓰고 있다면 VM에서 호스트로 들어오는 트래픽도 허용
sudo ufw status | grep -q active && sudo ufw allow in on mpqemubr0
재부팅하면 사라집니다

위 iptables 규칙은 메모리에만 있습니다. 랩 머신을 재부팅한 뒤 VM 인터넷이 다시 안 되면 이 두 줄을 다시 실행하거나, 10장의 lab-start.sh에 넣어 둔 것을 쓰세요.

5Step 2. kind 클러스터 2개

hub에는 포트 레지스트리의 포트를 모두 매핑하고, edge에는 노드 라벨로 고객사 정보를 붙입니다.

hub 클러스터 설정

~/obs-lab/kind/hub.yaml

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: hub
nodes:
- role: control-plane
  image: kindest/node:v1.36.1
  labels:
    lab.role: hub
  extraPortMappings:            # 포트 레지스트리 (3장)
  - { containerPort: 30999, hostPort: 30999, listenAddress: "0.0.0.0" }  # probe
  - { containerPort: 30090, hostPort: 30090, listenAddress: "0.0.0.0" }  # Prometheus
  - { containerPort: 30093, hostPort: 30093, listenAddress: "0.0.0.0" }  # Alertmanager
  - { containerPort: 30300, hostPort: 30300, listenAddress: "0.0.0.0" }  # Grafana
  - { containerPort: 30100, hostPort: 30100, listenAddress: "0.0.0.0" }  # Loki push
  - { containerPort: 30920, hostPort: 30920, listenAddress: "0.0.0.0" }  # OpenSearch

6Step 3. 오브젝트 스토리지

Loki, Tempo, Mimir, Thanos는 모두 데이터를 오브젝트 스토리지에 저장합니다. S3 호환 스토리지를 클러스터 밖에 띄우고 이후 편에서 쓸 버킷을 미리 만듭니다.

왜 MinIO가 아닌가

커리큘럼을 처음 설계할 때는 MinIO를 쓸 계획이었지만, 실습을 준비하며 현재 상태를 확인한 결과 다른 도구로 바꿨습니다. MinIO는 2025년 5월 커뮤니티판 관리 콘솔 기능을 축소했고, 2025년 10월 커뮤니티판 바이너리와 Docker 이미지 배포를 중단했으며, 2025년 12월 3일 유지보수 모드로 전환한 뒤 2026년 2월 12일 "더 이상 유지되지 않음"으로 표시되었고 2026년 4월 25일 저장소가 보관(archived) 처리되었습니다.

지금 MinIO 커뮤니티판을 쓰려면 소스에서 직접 빌드해야 하고, 보안 취약점이 나와도 패치를 직접 만들어야 합니다. 1편에서 다룬 EOL과 같은 문제입니다. 랩에서는 SeaweedFS를 씁니다. Apache 2.0 라이선스이고 2012년부터 개발된 프로젝트이며, weed mini 명령 하나로 S3 게이트웨이와 관리 UI를 포함한 단일 노드 구성을 띄울 수 있어 실습에 적합합니다.

MSP 실무 과제

운영 중인 고객사에 MinIO 커뮤니티판이 있다면, Promtail과 같은 수준의 전환 대상 목록에 올려야 합니다. 대안으로는 SeaweedFS, Garage, Ceph RGW, 그리고 클라우드 관리형 스토리지가 있고, 데이터 이전은 rclone 같은 도구로 동기화한 뒤 개수와 체크섬을 비교하는 방식이 일반적입니다. 오픈소스 선택에서 "지금 유명한가"만큼 "누가 계속 유지하는가"가 중요하다는 사례로 기억해 두세요.

8Step 5. OTel Demo 배포

edge 클러스터에 고객사 애플리케이션 역할을 할 OpenTelemetry Demo를 설치합니다. 관측 백엔드는 우리가 직접 만들 것이므로 데모에 포함된 백엔드는 끕니다.

OpenTelemetry Demo란

OpenTelemetry 프로젝트가 관리하는 가상의 천체 망원경 쇼핑몰(Astronomy Shop)입니다. Go, Java, .NET, Python, Node.js, Rust, PHP 등 여러 언어로 작성된 서비스가 Kafka, 캐시, PostgreSQL과 함께 동작하며, 모든 서비스가 OpenTelemetry로 계측되어 있습니다. 부하 생성기가 계속 쇼핑 트래픽을 만들고, flagd 기반 기능 플래그로 장애를 켜고 끌 수 있어 관측 실습의 표준 교보재로 쓰입니다.

values 파일

데모 차트는 기본적으로 Jaeger, Prometheus, Grafana, OpenSearch를 함께 설치합니다. 이 시리즈에서는 이것들을 우리가 hub에 직접 구축하므로 꺼 두고, 데모의 Collector는 받은 데이터를 일단 로그로만 출력(debug 익스포터)하도록 바꿉니다. 3편부터 이 목적지를 하나씩 hub로 바꿔 나갑니다.

~/obs-lab/apps/otel-demo-values.yaml

# 데모에 포함된 백엔드 끄기: hub에 직접 구축할 것이므로
jaeger:
  enabled: false
prometheus:
  enabled: false
grafana:
  enabled: false
opensearch:
  enabled: false

# 데모 Collector는 유지하되, 출력은 당분간 debug로만
opentelemetry-collector:
  config:
    service:
      pipelines:
        traces:
          exporters: [debug, spanmetrics]   # spanmetrics는 내부 연결용이라 유지
        metrics:
          exporters: [debug]
        logs:
          exporters: [debug]
차트 버전에 따라 키가 다를 수 있습니다

데모 차트는 자주 업데이트됩니다. 설치 전에 helm show values open-telemetry/opentelemetry-demo | less로 opentelemetry-collector.config.service.pipelines 아래의 실제 익스포터 이름을 확인하세요. 특히 traces 파이프라인에 spanmetrics 커넥터가 있는지 확인해야 합니다. metrics 파이프라인이 spanmetrics를 입력으로 받는데 traces 파이프라인에서 빼 버리면 Collector가 설정 오류로 시작하지 못합니다.

설치

helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update
helm search repo open-telemetry/opentelemetry-demo       # CHART VERSION을 기록

DEMO_CHART_VER=위에서_확인한_버전
echo "export DEMO_CHART_VER=$DEMO_CHART_VER" >> ~/obs-lab/lab.env

helm install otel-demo open-telemetry/opentelemetry-demo \
  --kube-context kind-edge \
  --namespace otel-demo --create-namespace \
  --version $DEMO_CHART_VER \
  -f ~/obs-lab/apps/otel-demo-values.yaml

kubectl --context kind-edge -n otel-demo get pods -w     # 모두 Running이 될 때까지 (5~10분)

데모 차트는 버전 간 업그레이드를 지원하지 않는다고 공식 문서에 명시돼 있습니다. 새 버전으로 바꿀 때는 helm uninstall 후 다시 설치합니다. 그래서 설치한 차트 버전을 lab.env에 기록해 두는 것입니다.

쇼핑몰 접속과 장애 주입 화면

kubectl --context kind-edge -n otel-demo port-forward svc/frontend-proxy 8080:8080

이 터미널은 열어 둔 채로 브라우저에서 접속합니다.

  • http://localhost:8080/ 쇼핑몰. 상품을 장바구니에 담고 결제까지 해 보세요.
  • http://localhost:8080/feature 기능 플래그 화면. 장애 주입 스위치가 모여 있습니다. 오늘은 둘러보기만 하고 켜지 마세요.

텔레메트리가 만들어지고 있는지 확인

kubectl --context kind-edge -n otel-demo logs \
  -l app.kubernetes.io/name=opentelemetry-collector --tail=20
정상이면 debug 익스포터가 받은 데이터의 개수를 주기적으로 출력합니다. 트레이스, 메트릭, 로그 세 종류가 모두 보이면 됩니다. 
info  Traces   {"kind": "exporter", "data_type": "traces", "name": "debug", "resource spans": 4, "spans": 37}
info  Metrics  {"kind": "exporter", "data_type": "metrics", "name": "debug", "resource metrics": 9, "data points": 412}
info  Logs     {"kind": "exporter", "data_type": "logs", "name": "debug", "resource logs": 3, "log records": 18}
출력 형식은 Collector 버전에 따라 조금 다를 수 있습니다. 숫자가 계속 바뀌며 찍힌다면 부하 생성기가 트래픽을 만들고, 모든 서비스가 OTLP로 Collector에 데이터를 보내고 있다는 뜻입니다.

바로 이 지점이 1편에서 말한 "데이터는 만들어지고 있지만 아직 아무도 보지 않는" 상태입니다. 이 시리즈의 남은 16편은 이 흐름을 저장하고, 연결하고, 알림으로 바꾸고, 원인 분석까지 이어 가는 과정입니다.

#!/usr/bin/env bash
# 랩 상태 점검. 모든 항목이 OK면 실습을 시작해도 됩니다.
set -u
source ~/obs-lab/lab.env
FAIL=0
ok(){ printf "  \033[32m[ OK ]\033[0m %s\n" "$1"; }
ng(){ printf "  \033[31m[ NG ]\033[0m %s\n" "$1"; FAIL=1; }

echo "1. Kubernetes 클러스터"
for c in hub edge; do
  total=$(kubectl --context kind-$c get nodes --no-headers 2>/dev/null | wc -l)
  ready=$(kubectl --context kind-$c get nodes --no-headers 2>/dev/null | awk '$2=="Ready"' | wc -l)
  if [ "$total" -gt 0 ] && [ "$total" -eq "$ready" ]; then ok "$c 노드 $ready/$total Ready"; else ng "$c 노드 $ready/$total Ready"; fi
done

echo "2. 오브젝트 스토리지"
buckets=$(docker run --rm --network kind \
  -e AWS_ACCESS_KEY_ID=$S3_ACCESS_KEY -e AWS_SECRET_ACCESS_KEY=$S3_SECRET_KEY -e AWS_DEFAULT_REGION=us-east-1 \
  amazon/aws-cli --endpoint-url $S3_ENDPOINT_INTERNAL s3 ls 2>/dev/null | wc -l)
[ "$buckets" -ge 9 ] && ok "lab-s3 버킷 $buckets개" || ng "lab-s3 버킷 $buckets개 (9개 기대)"

echo "3. 온프레미스 VM"
for vm in cust-a-web cust-a-db; do
  if multipass info $vm 2>/dev/null | grep -q 'Running'; then ok "$vm 실행 중"
  else ng "$vm 실행 중 아님 (경량 구성이면 cust-a-db는 무시)"; fi
done

echo "4. 네트워크 경로"
code=$(multipass exec cust-a-web -- curl -s -m 5 -o /dev/null -w '%{http_code}' http://$HUB_HOST:30999 2>/dev/null)
[ "$code" = "200" ] && ok "경로 B: VM → hub ($code)" || ng "경로 B: VM → hub ($code)"
code=$(kubectl --context kind-edge run lc-$RANDOM --rm -i --restart=Never --quiet \
  --image=curlimages/curl -- curl -s -m 5 -o /dev/null -w '%{http_code}' http://hub-control-plane:30999 2>/dev/null)
[ "$code" = "200" ] && ok "경로 A: edge → hub ($code)" || ng "경로 A: edge → hub ($code)"

echo "5. OTel Demo"
bad=$(kubectl --context kind-edge -n otel-demo get pods --no-headers 2>/dev/null | awk '$3!="Running" && $3!="Completed"' | wc -l)
all=$(kubectl --context kind-edge -n otel-demo get pods --no-headers 2>/dev/null | wc -l)
[ "$all" -gt 0 ] && [ "$bad" -eq 0 ] && ok "파드 $all개 모두 정상" || ng "비정상 파드 $bad개 / 전체 $all개"
seen=$(kubectl --context kind-edge -n otel-demo logs -l app.kubernetes.io/name=opentelemetry-collector --tail=300 2>/dev/null | grep -Eci 'traces|spans')
[ "$seen" -gt 0 ] && ok "Collector가 트레이스 수신 중" || ng "Collector 로그에 트레이스 흔적 없음"

echo
[ $FAIL -eq 0 ] && echo "랩 정상. 실습을 시작하세요." || echo "NG 항목을 12장 트러블슈팅에서 확인하세요."
exit $FAIL
chmod +x ~/obs-lab/scripts/lab-check.sh

12트러블슈팅

랩 구축에서 자주 막히는 지점입니다. 증상을 눌러 원인과 해결 방법을 확인하세요.

kind create cluster가 "too many open files" 또는 노드 NotReady로 실패Step 2

inotify 한도가 부족한 경우가 대부분입니다. Step 1의 sysctl 설정을 적용했는지 sysctl fs.inotify.max_user_instances로 확인하세요. 실패한 클러스터는 kind delete cluster --name edge로 지운 뒤 다시 만듭니다.

노드 이미지가 cgroup 관련 오류로 시작하지 않음Step 2

호스트가 cgroup v1인 경우입니다. Kubernetes 1.35 이상 노드 이미지는 cgroup v1 지원을 빼는 방향이므로, cgroup v2를 기본으로 쓰는 최신 배포판을 쓰는 것이 근본적인 해결입니다.

Multipass VM 생성이 시간 초과, VM 안에서 apt가 멈춤Step 4

Docker가 FORWARD 정책을 DROP으로 바꿔 VM 트래픽이 막힌 경우입니다. Step 1의 DOCKER-USER 규칙을 적용하세요. 브리지 이름이 mpqemubr0가 아니라면 ip -br link로 실제 이름을 확인해 바꿔 넣습니다.

VM에서 호스트 30999로 접속하면 시간 초과경로 B

세 가지를 차례로 확인합니다. 호스트에서 curl localhost:30999가 200이면 포트 매핑은 정상입니다. 그다음 sudo ufw status로 방화벽이 VM 브리지를 막고 있는지 봅니다. 마지막으로 hub를 만들 때 listenAddress를 127.0.0.1로 잘못 적지 않았는지 docker port hub-control-plane으로 확인합니다. 포트 매핑을 고치려면 hub를 다시 만들어야 합니다.

edge 파드에서 hub-control-plane 또는 lab-s3 이름을 찾지 못함경로 A, C

kind 노드는 Docker 내장 DNS를 통해 같은 네트워크의 컨테이너 이름을 찾습니다. docker network inspect kind로 두 클러스터 노드와 lab-s3가 모두 같은 네트워크에 있는지 확인하세요. lab-s3를 --network kind 없이 만들었다면 docker network connect kind lab-s3로 붙일 수 있습니다. 급하면 docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' hub-control-plane으로 IP를 얻어 쓸 수 있지만, IP는 재시작하면 바뀔 수 있습니다.

OTel Demo 파드가 Pending 또는 OOMKilledStep 5

Pending이면 kubectl describe pod의 Events에서 자원 부족 메시지를 확인합니다. 호스트(또는 Docker Desktop)의 메모리가 부족한 경우이므로 경량 구성으로 줄이거나 cust-a-db VM을 멈춰 여유를 만드세요. 특정 파드만 OOMKilled라면 values 파일에서 해당 구성 요소의 메모리 상한을 올릴 수 있습니다.

데모 Collector가 CrashLoopBackOffStep 5

대부분 파이프라인 설정 오류입니다. kubectl logs에서 "connector ... used as receiver but not used as exporter" 같은 메시지가 보이면 values 파일의 익스포터 목록이 차트의 기본 설정과 맞지 않는 것입니다. helm show values로 기본 파이프라인을 확인한 뒤, 백엔드 익스포터(otlp, otlphttp/prometheus, opensearch 등)만 빼고 나머지는 남기세요.

호스트 포트 8333, 8080, 30xxx가 이미 사용 중전체

sudo ss -ltnp | grep 8333처럼 어떤 프로그램이 쓰는지 확인합니다. 그 프로그램을 멈출 수 없다면 랩의 포트 번호를 바꾸고, 바꾼 번호를 포트 레지스트리 표에 직접 메모해 두세요.

S3 명령이 SignatureDoesNotMatch 또는 AccessDeniedStep 3

source ~/obs-lab/lab.env를 하지 않아 접근 키 변수가 비어 있는 경우가 흔합니다. echo $S3_ACCESS_KEY로 확인하세요. 컨테이너를 처음 띄울 때와 다른 키를 쓰고 있다면 관리 UI(localhost:23646)에서 사용자를 확인합니다.

15정리와 다음 편

오늘의 핵심

  1. hub는 MSP 관제 센터, edge는 고객사 Kubernetes, Multipass VM은 온프레미스 서버, SeaweedFS는 S3/Blob 역할입니다. 데이터를 만드는 곳과 보는 곳을 분리해야 실무 질문을 실습할 수 있습니다.
  2. 경로 A는 Docker 네트워크 이름 해석, 경로 B는 extraPortMappings와 호스트 게이트웨이, 경로 C는 클러스터 밖 스토리지입니다. probe와 lab-check.sh로 언제든 점검할 수 있습니다.
  3. MinIO 커뮤니티판은 2026년 4월 저장소가 보관 처리되었습니다. 오픈소스는 기능만큼 유지 주체와 배포 상태를 함께 봐야 합니다.
  4. OTel Demo는 지금 데이터를 만들고 있지만 아무도 보지 않는 상태입니다. 3편부터 이 데이터의 목적지를 하나씩 만들어 갑니다.
  5. 모든 구성은 ~/obs-lab의 파일로 남겼으므로 망가지면 지우고 다시 만들면 됩니다.

다음 편 예고: 3편 Prometheus 해부

Kubernetes에 올리기 전에, Prometheus를 가장 날것의 형태로 만나 봅니다. cust-a-web VM에 Prometheus와 node_exporter를 바이너리로 직접 설치하고 systemd 서비스로 등록한 뒤, Pull 방식 스크레이핑이 실제로 어떻게 동작하는지, TSDB가 디스크에 무엇을 쓰는지, 라벨 하나가 시계열 수를 어떻게 바꾸는지 눈으로 확인합니다. Prometheus 3.x에서 달라진 점도 함께 다룹니다.
