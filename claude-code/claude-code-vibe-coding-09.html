settings 파일 지도와 우선순위

우선순위범위파일누구에게
1 (최상)관리형조직이 배포하는 managed-settings.json 등조직 전체. 아무도 덮어쓸 수 없음 (24편)
2명령줄--permission-mode, --allowedTools, --settings 등그 실행만
3로컬 프로젝트.claude/settings.local.json나 · 이 저장소 (Git 제외)
4공유 프로젝트.claude/settings.json팀 (Git으로 공유)
5사용자~/.claude/settings.json나 · 모든 프로젝트
권한 규칙은 “합쳐지고, deny가 이긴다” 일반 설정 값은 위쪽 범위가 아래쪽을 덮어쓰지만, 권한 규칙은 모든 범위에서 모여 함께 평가됩니다. 그리고 어느 범위에서든 deny면 다른 범위의 allow로 풀 수 없습니다. 사용자 설정이 허용해도 프로젝트 설정이 막으면 막히고, 그 반대도 마찬가지입니다. 관리형 deny는 --allowedTools로도 못 풉니다.

설정 파일의 /path 같은 경로 규칙이 어디를 기준으로 해석되는지도 파일마다 다릅니다(7장). 무엇이 어느 파일에서 왔는지는 /permissions가 규칙마다 출처 파일을 보여 줍니다.

💾 영구 승인은 어디에?

Git 저장소 루트의 .claude/settings.local.json에 규칙으로 저장됩니다(worktree라면 메인 체크아웃). 그동안 무심코 누른 승인이 여기에 쌓여 있으니 가끔 /permissions로 정리하세요.

💬 승인·거절에 메모 달기

권한 요청에서 Yes나 No로 이동한 뒤 Tab을 누르면 메모 칸이 열립니다. No + 메모는 거절 이유로 Claude에게 전달되어, Claude가 그 이유를 반영해 계속 일합니다.

🔢 한 번만 승인되는 요청

규칙이 무엇을 허용하게 될지 화면에 다 보여 줄 수 없는 경우에는 “다시 묻지 않기” 선택지가 없습니다. 필요하면 /permissions에서 직접 규칙을 추가합니다.

🛠️ /permissions

모든 규칙과 출처 파일, 최근 거절 기록을 보고 추가·삭제합니다. Claude가 일하는 중에 바꿔도 다음 도구 호출부터 적용됩니다.

규칙 문법

규칙은 도구 또는 도구(지정자) 형식입니다. 평가 순서는 deny → ask → allow이고, 이 순서에서 처음 맞는 것이 결과를 정합니다. 규칙이 얼마나 구체적인지는 순서를 바꾸지 못합니다. 그래서 넓은 deny Bash(aws *) 안에서 좁은 allow Bash(aws s3 ls)로 예외를 낼 수 없습니다.

규칙뜻
Bash · Bash(*)모든 Bash 명령. deny에 두면 도구 자체가 Claude의 컨텍스트에서 사라짐
Bash(npm run build)정확히 그 명령 하나
Bash(npm run *)npm run으로 시작하는 모든 명령 (뒤에 아무것도 없는 npm run도)
Bash(ls:*)Bash(ls *)와 같음 (끝에서만 인정)
Read(./.env)현재 폴더의 .env 읽기
Edit(/docs/**)프로젝트의 docs 아래 편집 (7장의 기준점 주의)
WebFetch(domain:example.com)example.com으로의 가져오기. *.example.com은 하위 도메인만
mcp__github · mcp__github__*github MCP 서버의 모든 도구 (12편)
Agent(Explore)특정 서브에이전트 사용 (13편)
Bash(run_in_background:true)deny·ask 전용: 입력 매개변수 값으로 매칭

와일드카드 *는 하위 명령 뒤에

쓴 규칙맞는 것안 맞는 것
Bash(npm run *)npm run build, npm run test --watch, npm runnpm install
Bash(git * main)git merge main, git push origin main, git -c …=<프로그램> diff maingit log
Bash(ls *)ls -la, lslsof
Bash(ls*)ls -la, lsof
allow 규칙에서 *를 하위 명령 앞에 두지 마세요 * 앞의 글자까지가 규칙을 제한합니다. Bash(git *)는 모든 git 명령을 허용하고, Bash(git * main)은 프로그램을 실행시키는 -c 옵션까지 통과시킵니다. Claude Code도 이런 allow 규칙에 시작 시 경고를 냅니다.

규칙 테스터

규칙 목록을 만들고 명령을 넣어 결과를 확인하세요. 범위(scope)를 다르게 줘도 deny가 이기는 것, 복합 명령이 나뉘어 평가되는 것을 볼 수 있습니다. 작업 폴더는 ~/vibe-lab, 모드는 Manual로 가정한 학습용 단순화 버전입니다.

Bash 규칙의 한계

Bash 규칙은 Claude가 쓴 명령 글자를 봅니다. Claude Code는 복합 명령(&&, ||, ;, |, &, 줄바꿈)을 나눠 하위 명령마다 검사하고, timeout·time·nice·nohup·stdbuf·command·builtin·플래그 없는 xargs 같은 감싸개를 벗긴 뒤 맞춰 봅니다. 하지만 같은 프로그램을 다른 모양으로 부르면 맞지 않습니다.

deny 규칙막는 것못 막는 것
Bash(curl *)curl https://example.com/usr/bin/curl …, sh -c 'curl …'
Bash(rm *)rm -rf build//bin/rm -rf build/, bash -c 'rm -rf build/'
Bash(git push *)git push origin maingit -C . push …, git -c push.default=current push …
그래서 deny 규칙은 “보안 경계”가 아닙니다 deny·ask 규칙은 Claude가 보통 쓰는 형태의 호출을 막는 장치이지, 프로그램 둘레의 보안 벽이 아닙니다. 명령 글자와 상관없이 막아야 하면 샌드박스(8장)로 파일·네트워크를 OS에서 막거나, PreToolUse Hook(11편)으로 전체 명령을 직접 검사하세요. 그리고 가장 확실한 방법은 Claude Code가 도는 환경에 운영 자격 증명 자체를 두지 않는 것입니다(3편).
읽기 전용 명령은 늘 통과

ls, cat, grep, find, head, tail, wc, diff, git의 읽기 형태 등은 어떤 모드에서도 묻지 않고 실행됩니다. 이 목록은 바꿀 수 없고, 묻게 하려면 ask나 deny 규칙을 추가합니다.

리다이렉트도 파일 규칙으로

> file, >> file, tee의 대상은 Edit 규칙과 보호 경로로, < file은 Read 규칙으로 검사됩니다. Bash(git commit *)가 허용해도 출력 파일까지 허용하진 않습니다.

환경 실행기 주의

npx, docker exec, devbox run은 감싸개로 벗겨지지 않습니다. Bash(docker exec *)를 허용하면 그 뒤의 어떤 명령이든 허용됩니다. 안쪽 명령까지 적은 정확한 규칙을 쓰세요.

파일 경로 규칙

Read·Edit 규칙은 gitignore 문법을 쓰고, 경로 앞부분이 기준점을 정합니다.

모양기준예
//경로파일 시스템 루트 (진짜 절대 경로)Read(//etc/**)
~/경로홈 디렉토리Read(~/.ssh/**)
/경로그 설정 파일의 기준점 (프로젝트 설정이면 작업 폴더, 사용자 설정이면 ~/.claude)Edit(/src/**)
경로 · ./경로현재 폴더Read(./.env)
흔한 실수 두 가지 ① /Users/alice/file은 절대 경로가 아닙니다. 슬래시 하나는 설정 파일 기준이므로 절대 경로는 //Users/alice/file. ② 사용자 설정에 Read(/secrets/**)를 넣으면 프로젝트가 아니라 ~/.claude/secrets를 막습니다. 모든 프로젝트에 적용하려면 ~/나 //로 쓰세요.
Read deny는 Edit·Write도 막음

Read(./.env)를 막으면 같은 경로에 쓰거나 새로 만드는 것도 막힙니다(NotebookEdit 제외).

파일 이름만 쓰면 어느 깊이든

Read(.env)는 Read(**/.env)와 같아서 현재 폴더 아래 모든 .env에 적용됩니다.

Write 규칙은 쓰지 않음

경로 규칙은 Read(…)와 Edit(…)만 검사합니다. Write(docs/**)는 무시되니 Edit(docs/**)로.

스크립트는 못 막음

Read·Edit deny는 Claude의 파일 도구와 cat·sed·리다이렉트 같은 인식된 명령에 적용되지만, Python 스크립트가 직접 파일을 여는 것은 막지 못합니다. 그건 샌드박스의 일입니다.

8 / 15

샌드박스

샌드박스는 Bash(와 PowerShell, Monitor) 명령과 그 모든 자식 프로세스가 닿을 수 있는 파일과 네트워크를 운영체제 수준에서 제한합니다. 명령 글자가 아니라 실제 행동을 막으므로, Python 스크립트가 직접 파일을 열거나 sh -c로 감싸도 같은 경계를 넘지 못합니다.

플랫폼구현준비
macOSSeatbelt설치할 것 없음
Linux · WSL2bubblewrap + socatsudo apt-get install bubblewrap socat
WSL1 · 네이티브 Windows지원 안 함WSL2에서 실행 (3편)

/sandbox로 켭니다. 기본값으로 샌드박스 안의 명령은 작업 폴더에만 쓸 수 있고, 새 네트워크 도메인에 처음 접속할 때 승인을 요청합니다. 빠진 의존성은 /sandbox의 Dependencies 탭에 나옵니다.

🟢 자동 허용 모드

샌드박스 안에서 돌 수 있는 명령은 묻지 않고 실행됩니다. 경계 자체가 안전장치가 되어 승인 피로를 줄여 줍니다. 그래도 명시적인 ask·deny 규칙은 지켜집니다.

🔵 일반 권한 모드

경계는 같고, 명령은 평소처럼 권한 흐름을 거칩니다.

샌드박스 경계 체험

설정 예

{ "sandbox": { "enabled": true, "failIfUnavailable": true, "allowUnsandboxedCommands": false, "filesystem": { "denyRead": ["~/.ssh", "~/.aws", "~/.kube"] }, "network": { "allowedDomains": ["github.com", "*.github.com"] } } }
키뜻
failIfUnavailable샌드박스를 못 켜면(의존성 없음 등) 경고만 하고 그냥 실행하는 대신 실패하게 함
allowUnsandboxedCommands샌드박스 때문에 실패한 명령을 Claude가 dangerouslyDisableSandbox로 밖에서 다시 시도하는 탈출구. false면 닫힘
excludedCommands샌드박스 밖에서 실행할 명령(예: docker). 이 명령들은 일반 권한 흐름을 따름
filesystem.allowWrite / denyRead쓰기 허용 경로 추가, 읽기 금지 경로
network.allowedDomains / deniedDomains나가는 연결 허용·금지 목록. 둘 다 맞으면 금지가 이김
권한 규칙과 샌드박스는 겹쳐 쓴다 권한은 어떤 도구를 쓸 수 있나(Bash, Read, Edit, WebFetch, MCP 전부)를, 샌드박스는 Bash 계열 명령이 실제로 어디에 닿나를 정합니다. 공식 문서도 두 겹을 함께 쓰라고 권합니다. 프롬프트 인젝션이 Claude의 판단을 속여도 샌드박스 제한은 그대로 남기 때문입니다. 단, 샌드박스는 MCP 서버를 자동으로 가두지 않으며 컨테이너·최소 권한 자격 증명·코드 리뷰를 대신하지도 않습니다.

작업 폴더·신뢰·모드 잠금

📂 추가 폴더

--add-dir 경로, 세션 중 /add-dir, 설정의 additionalDirectories. 추가된 폴더는 작업 폴더와 같은 규칙을 따릅니다. 파일 접근만 늘릴 뿐 그 폴더의 설정을 모두 가져오지는 않습니다.

🚧 밖은 아예 못 읽게 · 못 쓰게

permissions.blockReadsOutsideWorkingDirectories를 켜면 파일 도구가 작업 폴더 밖 경로를 모든 모드에서 거부합니다. 쓰기 쪽 짝인 permissions.blockWritesOutsideWorkingDirectories(v2.1.314+)는 Write·Edit·NotebookEdit가 작업 폴더 밖에 쓰는 것을 모든 권한 모드에서 거부합니다. 둘 다 파일 도구 기준이라 Bash 명령은 샌드박스(이 편 뒷부분)로 막습니다.

🤝 저장소 설정과 신뢰

프로젝트 .claude/settings.json의 allow 규칙과 추가 폴더는 그 폴더를 신뢰한다고 승인한 뒤에만 적용됩니다. deny·ask는 제한만 하므로 바로 적용됩니다. 남의 저장소가 허용을 몰래 넓히지 못하게 하는 장치입니다.

🔒 모드 잠그기

permissions.disableBypassPermissionsMode나 permissions.disableAutoMode를 "disable"로 두면 그 모드를 쓸 수 없습니다. 관리형 설정에서 가장 유용하지만, 개인이 스스로를 잠글 수도 있습니다.
