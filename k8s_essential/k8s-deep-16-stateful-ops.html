Level 2 스토리지, 16편 (마지막)

스테이트풀 워크로드 운영 종합

11~15편에서 볼륨이 생기고, 붙고, 빨라지고, 복제되고, 백업되는 원리를 봤습니다. 이 편은 그 위에서 실제로 데이터베이스와 메시지 큐를 운영하는 이야기입니다. StatefulSet의 순서·볼륨 템플릿·보존 정책과 v1.37의 Recreate 전략, 그리고 StatefulSet을 쓰지 않고 스스로 Pod와 PVC를 관리하는 데이터베이스 오퍼레이터가 장애 조치 시간을 어떻게 바꾸는지 비교합니다. 비용 관리와 Level 2 전체를 묶는 트러블슈팅 플레이북으로 스토리지 레벨을 마칩니다.

증상을 고르고 질문에 답해 가면 원인 후보와 확인 명령, 고치는 방법, 관련 편이 나옵니다. 11~15편의 진단표를 하나의 길로 이은 것입니다.

0

읽는 법과 목표

쉬운 말로 StatefulSet은 “번호표를 단 직원들”입니다. 직원 0번, 1번, 2번이 각자 자기 서랍(PVC)을 갖고, 퇴사했다 다시 와도 같은 번호와 같은 서랍을 받습니다. 데이터베이스 오퍼레이터는 여기서 한 걸음 더 나아가 “직원 중 팀장이 쓰러지면 부팀장을 팀장으로 올리고, 새 직원을 뽑아 서랍을 복사해 주는” 인사팀 역할까지 자동으로 해 줍니다.

이 편을 마치면 할 수 있는 것

  • StatefulSet의 볼륨 템플릿·Pod 관리 정책·업데이트 전략·PVC 보존 정책을 운영 요구에 맞게 설정하고, v1.37 Recreate 전략의 쓰임을 설명할 수 있습니다.
  • CloudNativePG·Strimzi·Redis·MongoDB 오퍼레이터의 스토리지 요구를 알고 벤더별 권장 구성을 설계할 수 있습니다.
  • 스토리지 복제와 애플리케이션 복제의 장애 조치 시간 차이를 설명하고 측정할 수 있습니다.
  • 미사용 PVC·고아 디스크·스냅샷 수명을 관리해 스토리지 비용을 줄일 수 있습니다.
  • Level 2 전체를 묶은 플레이북으로 스토리지 장애를 단계별로 진단할 수 있습니다.

StatefulSet 정밀 해부

기능내용운영 포인트
안정된 이름Pod 이름 <sts>-<번호>, 헤드리스 Service로 <pod>.<svc> DNS클러스터 멤버 목록·리더 선출에 사용. 6편 헤드리스 Service
volumeClaimTemplatesPod마다 PVC <템플릿>-<sts>-<번호> 생성템플릿을 고쳐도 기존 PVC는 바뀌지 않음(확장은 PVC를 하나씩 패치, 11편)
podManagementPolicyOrderedReady(기본, 0부터 차례로) / Parallel(동시에)멤버가 서로 순서를 요구하지 않으면 Parallel이 기동·복구가 빠름
ordinals.start번호 시작값 지정클러스터 간 이전 때 번호 겹침 방지
PVC 보존 정책whenDeleted·whenScaled: Retain(기본) / Delete. 1.32 GA축소 후 남은 PVC가 비용을 만들고, 다시 늘리면 옛 데이터가 그대로 붙음(10장 사례)
minReadySecondsReady 후 이 시간 동안 유지돼야 가용으로 침롤링 업데이트 속도 조절
노드 장애 시같은 이름 Pod가 둘이 되면 안 되므로 자동 대체하지 않음12편 out-of-service 테인트, 14편 Longhorn 정책
운영형 StatefulSet 뼈대
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: db}
spec:
  serviceName: db
  replicas: 3
  podManagementPolicy: Parallel
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain               # 실수로 STS를 지워도 데이터 보존
    whenScaled: Delete                # 축소한 레플리카의 PVC는 정리(복제가 있는 앱에 한해)
  updateStrategy:
    type: RollingUpdate
    rollingUpdate: {partition: 0}     # 번호가 partition 이상인 Pod만 갱신 → 카나리
  selector: {matchLabels: {app: db}}
  template:
    metadata: {labels: {app: db}}
    spec:
      terminationGracePeriodSeconds: 60
      topologySpreadConstraints:
      - {maxSkew: 1, topologyKey: topology.kubernetes.io/zone, whenUnsatisfiable: DoNotSchedule, labelSelector: {matchLabels: {app: db}}}
      containers: [{name: db, image: "...", volumeMounts: [{name: data, mountPath: /var/lib/data}]}]
  volumeClaimTemplates:
  - metadata: {name: data}
    spec: {storageClassName: gp3-wfc, accessModes: ["ReadWriteOncePod"], resources: {requests: {storage: 50Gi}}}
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: db}
spec: {maxUnavailable: 1, selector: {matchLabels: {app: db}}}
시니어 포인트: 존 분산과 WaitForFirstConsumer는 한 쌍 존 분산 제약을 걸어도 StorageClass가 Immediate면 디스크가 먼저 임의 존에 생겨 충돌합니다(11편). 반대로 WaitForFirstConsumer + 존 분산이면 레플리카마다 다른 존에 디스크가 생기고, 이후 각 Pod는 자기 존에 고정됩니다. 존 하나에 노드가 모자라면 그 레플리카만 영원히 Pending이 되므로 존별 노드 여유를 노드 그룹 설계에 넣으세요.

업데이트 전략과 v1.37 Recreate

전략동작장점약점
RollingUpdate(기본)번호가 큰 Pod부터 하나씩 지우고 새로 만들어 Ready를 기다림. partition으로 일부만항상 일부가 서비스 중새 Pod가 영원히 Ready가 안 되면(잘못된 이미지·설정) 멈춘 채 대기. 고쳐도 그 Pod를 사람이 지워야 진행되던 오래된 문제
OnDelete템플릿만 바꾸고, 사람이(또는 오퍼레이터가) Pod를 지울 때 새 버전으로완전한 수동 통제자동화 도구가 필요
Recreate(1.37 알파)모든 Pod를 지우고 완전히 종료된 뒤 podManagementPolicy에 따라 새로 만듦멈춘 롤아웃을 기다리지 않음. 버전이 섞이면 안 되는 앱(스키마·프로토콜 비호환)에 적합업데이트 동안 전체 중단. 기능 게이트 StatefulSetRecreateStrategy 필요

Recreate는 Deployment의 같은 이름 전략을 StatefulSet에 가져온 것입니다. 잘못된 이미지로 롤아웃이 멈췄을 때 템플릿을 고치기만 하면 진행되고, 두 버전이 동시에 떠 있으면 안 되는 레거시 클러스터형 애플리케이션을 안전하게 바꿀 수 있습니다. 동시에 노드당 하나씩 줄이는 maxUnavailable(롤링 업데이트에서 한 번에 여러 Pod 갱신) 기능도 별도 기능 게이트로 진행 중이니, 사용하는 버전에서 단계를 확인하세요. 7장 실습 2에서 lab-native에 기능 게이트를 켜고 두 전략을 비교합니다.

함정: StatefulSet 업데이트는 데이터 마이그레이션이 아니다 StatefulSet은 Pod를 바꿀 뿐, 데이터 스키마나 클러스터 멤버십 변경을 이해하지 못합니다. PostgreSQL 메이저 업그레이드, Kafka 프로토콜 버전 변경, Redis 클러스터 리샤딩 같은 작업은 앱이나 오퍼레이터가 순서를 지켜야 합니다. 이것이 상태 있는 서비스에 오퍼레이터를 쓰는 가장 큰 이유입니다.
3

DB 오퍼레이터와 장애 조치

왜 오퍼레이터는 StatefulSet을 안 쓰기도 하나

CloudNativePG는 StatefulSet 없이 Pod와 PVC를 직접 만들고, Strimzi는 자체 StrimziPodSet을 씁니다. StatefulSet의 순서 규칙과 “같은 이름은 하나만” 보장이 데이터베이스의 실제 요구(지금 누가 프라이머리인가, 어느 레플리카를 먼저 갱신하나, 장애 난 인스턴스를 어떻게 다시 만드나)와 맞지 않기 때문입니다. 오퍼레이터는 앱의 상태를 알고 결정합니다.

스토리지 복제 vs 애플리케이션 복제

노드가 죽었을 때 단일 Pod + 블록 디스크는 그 디스크가 떨어지기를 기다려야 합니다(12편의 분리 지연과 StatefulSet 교착). 반면 데이터베이스가 스스로 복제하면 다른 노드의 레플리카가 자기 디스크를 이미 붙이고 있으므로, 승격만 하면 됩니다. 분산 스토리지(14편)는 그 중간입니다. 아래 비교기에 예시 시간을 넣었습니다. 7장 실습 1에서 실제로 잽니다.

오퍼레이터별 스토리지 요구와 벤더 권장 구성

오퍼레이터Pod 관리스토리지 요구클라우드 권장온프렘 권장주의
CloudNativePG (PostgreSQL)Pod·PVC 직접 관리낮은 fsync 지연(13편), WAL 분리, RWOgp3(IOPS 조정)·io2 / Premium SSD v2 / Hyperdisk Balanced, WFC + 존 분산로컬 디스크(TopoLVM·LocalPV) + 앱 복제가 문서상 권장되는 구성, 또는 Ceph RBDNFS 금지(13편). WAL 볼륨 용량 경보

Redis·Valkey 오퍼레이터StatefulSet 기반이 일반적작은 용량. 캐시면 영속 불필요, 영속(AOF·RDB)이면 fsync 지연 민감캐시는 emptyDir, 영속은 작은 블록 디스크로컬 디스크AOF 위의 NFS·느린 디스크는 지연 급증(10장 사례)
MongoDB 오퍼레이터(공식·Percona)StatefulSet 기반 레플리카 셋WiredTiger 랜덤 I/O, 저널블록 디스크(IOPS 조정), 멤버별 존 분산로컬 디스크 + 레플리카 셋, 또는 Ceph RBD백업은 전용 도구(PBM 등)로 객체 저장소에
Strimzi KafkaNodePool 스토리지 예
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaNodePool
metadata:
  name: brokers
  labels: {strimzi.io/cluster: my-kafka}
spec:
  replicas: 3
  roles: [broker]
  storage:
    type: jbod
    volumes:
    - {id: 0, type: persistent-claim, size: 500Gi, class: gp3-throughput, deleteClaim: false}

# Kafka CR의 rack.topologyKey: topology.kubernetes.io/zone 으로 파티션 레플리카를 존에 분산
현장 메모: 관리형 서비스와의 비교표를 같이 내라 고객이 “Kubernetes 위에 DB를 올릴까, 관리형 DB(RDS·Azure Database·Cloud SQL)를 쓸까” 물으면, 장애 조치 시간·백업·업그레이드·비용·인력 다섯 항목으로 비교표를 내는 것이 MSP의 역할입니다. 오퍼레이터는 클라우드 중립성과 비용에서, 관리형 서비스는 운영 부담에서 유리합니다. 공용 PaaS로 여러 고객에게 DB를 제공한다면 이 편의 스토리지 설계(존 분산, 로컬 vs 네트워크 디스크, 백업 위치)가 상품의 SLA를 결정합니다.

Level 2 스토리지 트러블슈팅 플레이북

맨 위 진단 트리의 내용을 한 장 표로 펼쳤습니다. 단계는 볼륨이 Pod에 닿기까지의 순서(11·12편)를 따르고, 그 뒤에 성능(13편), 분산 스토리지(14편), 백업·복원(15편), 앱 계층(이 편)이 이어집니다.

1. 프로비저닝PVC PendingPVC 이벤트, StorageClass provisioner, CSIDriver드라이버·기본 SC 없음, 권한·할당량11·12

실습 3. 스토리지 비용 점검 보고서

storage-waste.sh [일수]
#!/usr/bin/env bash
DAYS=${1:-30}; NOW=$(date +%s)
echo "== $DAYS일 넘게 안 쓴 PVC (Unused 조건, 1.37)"
kubectl get pvc -A -o json | jq -r --argjson now $NOW --argjson d $DAYS '.items[] | . as $p | (.status.conditions // [])[]
  | select(.type=="Unused" and .status=="True") | select(($now - (.lastTransitionTime|fromdateiso8601)) > ($d*86400))
  | "\($p.metadata.namespace)/\($p.metadata.name)\t\($p.spec.resources.requests.storage)\t\(.lastTransitionTime)"'
echo "== Released PV (Retain으로 남은 것)"
kubectl get pv -o json | jq -r '.items[] | select(.status.phase=="Released") | "\(.metadata.name)\t\(.spec.capacity.storage)\t\(.spec.storageClassName)"'
echo "== StatefulSet 레플리카 수를 넘는 번호의 PVC"
kubectl get sts -A -o json | jq -r '.items[] | .metadata.namespace as $ns | .metadata.name as $n | .spec.replicas as $r
  | (.spec.volumeClaimTemplates // [])[] | "\($ns) \(.metadata.name)-\($n) \($r)"' | while read ns prefix r; do
  kubectl -n "$ns" get pvc -o name | sed 's#.*/##' | grep -E "^$prefix-[0-9]+$" | while read p; do
    i=${p##*-}; [ "$i" -ge "$r" ] && echo "$ns/$p (replicas=$r)"; done; done
echo "== $DAYS일 넘은 VolumeSnapshot"
kubectl get volumesnapshot -A -o json 2>/dev/null | jq -r --argjson now $NOW --argjson d $DAYS '.items[]
  | select(($now - (.metadata.creationTimestamp|fromdateiso8601)) > ($d*86400))
  | "\(.metadata.namespace)/\(.metadata.name)\t\(.status.restoreSize // "?")\t\(.metadata.creationTimestamp)"'
echo "== (AWS) 미부착 상태인 Kubernetes 생성 EBS"
aws ec2 describe-volumes --filters Name=status,Values=available Name=tag-key,Values=kubernetes.io/created-for/pvc/name \
  --query 'Volumes[].[VolumeId,Size,CreateTime]' --output text 2>/dev/null

현장 사례

잘못된 이미지 하나로 StatefulSet 배포가 하루 동안 멈췄다

원인. 오타가 난 이미지 태그로 롤링 업데이트가 마지막 번호 Pod에서 멈췄고, 태그를 고친 뒤에도 그 Pod를 아무도 지우지 않아 진행되지 않았습니다.

교훈. 배포 파이프라인에 “StatefulSet 롤아웃 정체 감지 → 해당 Pod 삭제” 단계를 두거나, 버전 혼재가 허용되지 않는 앱은 Recreate(1.37 알파, 기능 성숙 후) 또는 오퍼레이터를 쓰세요.

축소했다가 늘렸더니 몇 달 전 데이터가 나타났다

원인. 기본 보존 정책(Retain) 때문에 축소된 레플리카의 PVC가 남아 있었고, 다시 늘리자 같은 번호 Pod가 옛 PVC를 그대로 붙였습니다. 그동안 디스크 비용도 계속 나갔습니다.

교훈. 복제가 있는 앱은 whenScaled: Delete, 아니면 축소 절차에 PVC 정리를 넣으세요.

노드 그룹 업그레이드 중 Kafka 파티션이 대량으로 복제 부족

원인. 로컬 NVMe 위 브로커들을 업그레이드하면서 노드가 동시에 여러 대 교체되어, 여러 브로커가 데이터를 처음부터 다시 받았습니다.

교훈. PDB(maxUnavailable 1), 랙(존) 인식 배치, 한 번에 한 브로커씩 교체하고 복제 부족 파티션이 0이 된 뒤 다음으로 넘어가는 절차가 필요합니다(14편 재구축 창).

장애 조치는 20초 만에 됐는데 서비스는 10분 동안 오류

원인. 앱의 커넥션 풀이 옛 프라이머리 IP로의 연결을 붙잡고 재연결하지 않았습니다.

교훈. 앱은 오퍼레이터의 읽기·쓰기 Service(-rw)를 쓰고, 커넥션 풀 검증·재시도 설정을 갖추거나 커넥션 풀러(PgBouncer, CNPG Pooler)를 앞에 두세요. 장애 조치 측정은 앱 기준으로 합니다.

PostgreSQL이 갑자기 멈췄다: WAL 볼륨 가득

원인. 객체 저장소 자격 증명이 만료되어 WAL 아카이브가 계속 실패했고, 아카이브되지 못한 WAL이 쌓여 WAL 볼륨이 가득 찼습니다.

교훈. WAL 아카이브 실패와 WAL 볼륨 사용률은 DB 정지의 선행 지표입니다. 둘 다 경보로 두세요.

Redis 지연이 주기적으로 튄다

원인. AOF 영속을 켠 Redis를 공유 파일 시스템 위에 두어, 매초 fsync가 네트워크 왕복이 되어 지연이 튀었습니다.

교훈. 캐시 용도면 영속을 끄거나 emptyDir, 영속이 필요하면 블록 디스크로 옮기세요(13편).

스냅샷 비용이 볼륨 비용을 넘었다

원인. 시간마다 스냅샷을 찍는 정책에 보존 기간이 없었고, VolumeSnapshotClass의 deletionPolicy가 Retain이라 Kubernetes 객체를 지워도 클라우드 스냅샷이 남았습니다.

교훈. 스냅샷은 만들 때 지울 날짜를 같이 정하세요. 백업 도구의 TTL·수명 주기 정책과 스냅샷 클래스 정책을 함께 점검합니다(15편).

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. StatefulSet은 안정된 이름·Pod별 PVC·순서를 주며, PVC 보존 정책(1.32 GA)과 존 분산 + WaitForFirstConsumer 조합이 운영의 기본입니다.
  2. RollingUpdate의 멈춘 롤아웃 문제를 v1.37 Recreate(알파)가 해결하지만 업데이트 동안 전체 중단이 따릅니다.
  3. 데이터베이스 오퍼레이터는 앱 상태를 알고 승격·스위치오버·백업을 하므로, 노드 장애 때 디스크 분리 대기 없이 수십 초 안에 장애 조치가 가능합니다.
  4. 오퍼레이터마다 스토리지 요구(낮은 fsync 지연, 높은 순차 처리량, WAL 분리, 존 분산)가 다르며, 공유 파일 시스템은 피합니다.
  5. 미사용 PVC·고아 디스크·스냅샷 수명을 정기 보고서로 관리하고, Level 2 플레이북으로 장애를 단계별로 진단합니다.

다음 편 · 17편 인증 지형: 누가 요청했는가 (Level 3 RBAC과 접근 제어 시작)

x509, ServiceAccount 토큰(바운드·프로젝티드), OIDC, 웹훅, 구조화된 인증 설정, Pod 인증서와 Cluster Trust Bundles까지 인증 경로를 모두 정리하고, EKS 액세스 엔트리(aws-auth 이후), AKS Entra ID 통합, GKE IAM·Google 그룹, OpenShift OAuth 서버, Rancher 인증 프록시를 비교합니다. kubeconfig exec 플러그인의 동작과 토큰 수명, 비상용(브레이크글라스) 계정 설계도 다룹니다.
