서빙 프레임워크
지형과 선택

7편 랩에서는 Deployment와 kustomize로 엔진을 직접 운영했습니다. 모델이 하나일 때는 그것으로 충분합니다. 모델이 열 개가 되고, 고객이 다섯 곳이 되고, 노드가 수십 대가 되면 누군가가 반복 작업을 대신해 줘야 합니다. 이번 편은 그 “누군가” 후보들 — KServe, llm-d, NVIDIA Dynamo, Ray Serve, 클라우드 매니지드 서비스 — 이 각각 무엇을 대신해 주고, 무엇은 여전히 우리 몫으로 남기는지를 비교하고, 조직 규모·모델 수·테넌트 수로 고르는 결정 트리를 만듭니다.

누가 무엇을 맡는가

01시작하기 전에

프레임워크 선택은 기술 선택이 아니라 “운영 책임을 어디까지 넘길 것인가”의 선택입니다.

학습 목표

  1. 서빙 프레임워크가 대신해 주는 열 가지 책임(배포·로딩·확장·라우팅·버전·관측 등)을 나열하고, 선택지별로 누가 맡는지 그릴 수 있다.
  2. KServe·llm-d·NVIDIA Dynamo·Ray Serve의 핵심 리소스와 구성 요소, 강점과 약점을 설명할 수 있다.
  3. 클라우드 매니지드 서비스(Bedrock·SageMaker·Vertex AI·Azure AI Foundry)가 넘겨받는 책임과 남기는 책임을 구분할 수 있다.
  4. 조직 규모·모델 수·테넌트 수·GPU 규모·팀 역량으로 프레임워크를 고르는 결정 트리를 적용할 수 있다.
  5. 직접 Deployment에서 프레임워크로 넘어가는 단계적 이전 경로와 MSP 표준 스택을 설계할 수 있다.
  6. 같은 모델을 직접 Deployment와 KServe로 띄워 생성되는 객체·운영 방식·성능 차이를 비교할 수 있다.
이 편의 비유: 식당 운영 방식

직접 Deployment는 사장이 주방·홀·재고·회계를 다 하는 동네 식당입니다. KServe는 표준 매뉴얼과 POS를 갖춘 프랜차이즈 본부 시스템, llm-d·Dynamo는 대형 주방을 위한 전문 동선 설계(전처리 구역·조리 구역 분리, 재료 재활용 동선), Ray Serve는 여러 코스 요리를 파이썬 레시피로 엮는 셰프 중심 주방, 매니지드 서비스는 공유 주방 임대입니다. 어느 쪽이든 “메뉴를 정하고 손님 약속(SLO)을 지키는 책임”은 끝까지 우리에게 남습니다.

03직접 Deployment

가장 단순하고, 가장 투명하고, 생각보다 오래 버티는 선택지.

충분한 경우
  • 모델 1~3개, 트래픽이 예측 가능
  • 팀이 쿠버네티스에 익숙하고 추가 컨트롤러를 늘리고 싶지 않음
  • 엔진 옵션을 세밀하게 통제해야 함(벤치마크·튜닝 단계)
  • 망분리 등으로 외부 컨트롤러 도입 심사가 무거움
한계가 오는 신호
  • 모델·버전이 늘어 매니페스트 복붙이 늘어남
  • 트래픽 변동으로 수동 증감이 잦아짐
  • 카나리·롤백을 사람이 하고 있음
  • 레플리카 간 부하 쏠림·캐시 낭비가 보임

직접 Deployment로 가더라도 결국 붙이게 되는 것들이 있습니다: 추론 지표 기반 오토스케일러(KEDA 등, 18편), 추론 인지 라우팅(Gateway API Inference Extension, 11편), AI 게이트웨이(12편), 관측 스택(20~21편). 이것들을 하나씩 붙이다 보면 프레임워크가 해 주는 일을 손으로 다시 만드는 셈이 됩니다. 그 지점이 프레임워크를 검토할 때입니다.

04KServe

쿠버네티스 모델 서빙의 표준 CRD. 예측 모델과 생성 모델을 한 플랫폼에서 다루며, LLM 쪽은 llm-d를 기반으로 다시 설계되었습니다.

KServe는 CNCF 인큐베이팅 프로젝트로, Kubeflow의 서빙 구성 요소이기도 합니다. 2026년 들어 생성 AI 중심으로 크게 바뀌었습니다. v0.16에서 LLM 전용 리소스 LLMInferenceService가 들어왔고, v0.17(2026년 3월)에서 이를 프로덕션 준비 단계로 올리며 llm-d를 기반으로 한 “GenAI 우선” 구조를 선언했습니다. 이후 v0.18에서 Ray 없는 멀티노드 추론·LWS 기반 오토스케일링·Responses API 라우팅·llm-d v0.6 통합이, v0.19에서 LLMInferenceService용 로컬 모델 캐시와 분산 트레이싱이 추가되는 등 빠르게 발전하고 있습니다(10월 현재 v0.21 RC 진행 중).

핵심 리소스

리소스역할LLM 서빙에서
InferenceService모델 하나의 서빙을 선언 (predictor·transformer 등)단일 레플리카 묶음의 LLM 서빙. 사용자 정의 컨테이너로 vLLM을 직접 지정 가능
ServingRuntime · ClusterServingRuntime엔진 컨테이너 템플릿 (Hugging Face 런타임 등)엔진 설정 표준화. 플랫폼팀이 런타임을, 모델팀이 InferenceService를 관리하는 분업
LLMInferenceService · LLMInferenceServiceConfigLLM 전용. llm-d 기반으로 InferencePool·Endpoint Picker·HTTPRoute를 대신 만들어 줌캐시 인지 라우팅, P/D 분리, 멀티노드, LoRA. 10·11편과 연결
LocalModelCache 계열노드 로컬 디스크에 모델을 미리 받아 두기콜드 스타트 단축(13편). 최근 LLMInferenceService에도 확장
InferenceGraph여러 모델을 그래프로 연결전처리·후처리 파이프라인 (LLM보다는 예측 모델에서 주로)

배포 모드

  • Standard 모드(예전 이름 RawDeployment): 평범한 Deployment·Service·HPA를 만듭니다. Knative가 필요 없어 운영이 단순하고, LLM 서빙에서 가장 많이 쓰입니다.
  • Knative 모드(예전 Serverless): 요청 기반 자동 확장과 0으로 축소. 콜드 스타트가 긴 LLM과는 궁합이 나쁠 때가 많습니다(18편).
KServe를 고르는 이유와 대가

이유: 표준 CRD 하나로 모델팀이 셀프서비스할 수 있고, 예측 모델(분류·추천 등)과 LLM을 같은 체계로 운영하며, Kubeflow·Red Hat OpenShift AI 같은 플랫폼과 이어지고, LLM 쪽은 llm-d의 최신 라우팅·분리 서빙을 CRD로 받을 수 있습니다. 대가: cert-manager·Gateway(또는 Ingress)·KServe 컨트롤러 같은 구성 요소가 늘고, 릴리스가 빠르며 LLM 리소스는 아직 알파 API 버전이라 업그레이드 때 매니페스트 변경이 생길 수 있습니다.

05llm-d

“vLLM 여러 개를 하나의 지능적인 서빙 시스템으로”. 분산 추론의 잘 닦인 경로를 제공하는 프로젝트.

llm-d는 Red Hat·Google Cloud·IBM Research·CoreWeave·NVIDIA가 시작해 2026년 3월 CNCF Sandbox가 된 쿠버네티스 네이티브 분산 추론 프레임워크입니다(1편). 단일 CRD 하나로 모든 것을 감추기보다, 검증된 구성(“잘 닦인 경로”)과 구성 요소들을 제공하는 방식입니다. v0.7부터 예전의 ModelService Helm 차트 대신 kustomize 기반 구성을 기본으로 바꾸었습니다.

구성 요소하는 일자세히
vLLM (엔진)실제 추론4편
추론 스케줄러 (Endpoint Picker)Gateway API Inference Extension의 EPP 구현. 큐 길이·KV 사용률·프리픽스 캐시 위치를 점수로 매겨 레플리카 선택11편
P/D 분리Prefill 전용·Decode 전용 Pod 무리와 KV 전송(NIXL 등)10편
KV 캐시 관리·인덱싱클러스터 전체에서 어떤 Pod가 어떤 프리픽스를 가졌는지 추적, 오프로딩 계층10·15편
대규모 전문가 병렬대형 MoE의 멀티노드 배치 (LWS 사용)17편
벤치마크 도구경로별 성능 검증 도구19편
KServe와 llm-d는 경쟁 관계가 아니다

KServe의 LLMInferenceService는 llm-d를 바탕으로 만들어졌고, InferencePool과 Endpoint Picker를 대신 만들어 줍니다. 그래서 “llm-d를 직접 구성하느냐, KServe의 CRD를 통해 쓰느냐”의 선택에 가깝습니다. 직접 구성은 세밀한 통제가, KServe 경유는 표준 API와 셀프서비스가 장점입니다. 10편에서 llm-d를 직접 해부하며 이 차이를 실습합니다.

06NVIDIA Dynamo

여러 엔진을 백엔드로 두고, 데이터센터 규모의 분산 추론을 조율하는 NVIDIA의 프레임워크.

Dynamo는 vLLM·SGLang·TensorRT-LLM을 백엔드 엔진으로 쓰면서, 그 위의 분산 추론 기능을 제공합니다. 2026년 1.0이 나왔고, 쿠버네티스에서는 Dynamo 오퍼레이터가 전체 추론 파이프라인을 DynamoGraphDeployment(DGD)로 선언하게 해 줍니다. 최근 버전은 etcd 없이 쿠버네티스 네이티브(EndpointSlice) 서비스 디스커버리를 기본으로 쓰고, 목표 SLA를 주면 프로파일링 후 최적 구성을 만들어 주는 요청 리소스(DGDR)와 SLA 플래너도 제공합니다.

구성 요소하는 일
FrontendOpenAI 호환 HTTP 입구, 전처리
RouterKV 캐시 인지 라우팅 (어느 워커가 프리픽스를 가졌는지)
Prefill · Decode 워커엔진(vLLM·SGLang·TRT-LLM) 위의 분리 서빙 워커
Planner부하·SLA를 보고 Prefill·Decode 워커 수를 조정
KVBM (KV 블록 관리자)GPU·CPU·스토리지 계층 KV 캐시 관리
NIXLGPU 간·노드 간 KV 전송 라이브러리 (llm-d·vLLM도 사용)
언제 Dynamo인가

NVIDIA GPU 중심의 대규모 클러스터에서 P/D 분리·KV 라우팅·SLA 기반 자동 구성을 한 벤더 스택으로 받고 싶을 때, TensorRT-LLM을 엔진으로 쓰고 싶을 때(5편), NVIDIA AI Enterprise 지원과 함께 가고 싶을 때입니다. 반대로 AMD·인텔 가속기가 섞이거나, Gateway API·KServe 같은 쿠버네티스 표준 API 중심으로 플랫폼을 짜고 싶다면 llm-d·KServe 쪽이 자연스럽습니다.

07Ray Serve

파이썬으로 서빙 로직을 조립하는 범용 분산 서빙 프레임워크.

Ray Serve는 Ray 분산 런타임 위의 서빙 라이브러리입니다. LLM용으로 vLLM 엔진을 감싼 Ray Serve LLM API를 제공하고, 쿠버네티스에서는 KubeRay의 RayService로 배포합니다. 강점은 파이썬 코드로 여러 모델과 로직을 하나의 애플리케이션으로 엮는 것입니다. 예를 들어 “분류 모델 → 조건에 따라 작은 LLM 또는 큰 LLM → 후처리”를 하나의 서비스 그래프로 만들고 단계별로 다르게 확장할 수 있습니다.

맞는 곳
  • 파이썬 개발자 중심 팀, 복합 파이프라인
  • 배치 추론·데이터 처리(Ray Data)와 서빙을 함께
  • 이미 Ray로 학습·데이터 처리를 하는 조직
주의할 곳
  • Ray 클러스터라는 또 하나의 분산 시스템을 운영해야 함
  • 쿠버네티스 표준 API(Gateway API·DRA·Kueue)와의 결합이 간접적
  • 단일 LLM 대규모 서빙만 필요하면 과한 추상화

08매니지드 서비스

GPU·엔진·확장을 클라우드에 넘기고, 우리는 모델 선택과 API 사용에 집중하는 길.

서비스대표 방식클라우드가 맡는 것우리에게 남는 것

14실습

7편 랩의 같은 모델(Qwen3-8B FP8)을 KServe InferenceService(Standard 모드)로 띄워, 직접 Deployment와 무엇이 같고 무엇이 다른지 확인합니다.

실습 환경 전제
  • 7편 랩(llmsvc-lab, model-cache PVC에 Qwen3-8B-FP8, bench Pod)이 준비되어 있어야 합니다.
  • KServe와 cert-manager는 클러스터 공용 구성 요소입니다. 이미 설치되어 있다면 재설치하지 말고 버전만 확인하세요. 새로 설치한다면 실습 후 제거 여부를 정합니다.
  • GPU가 하나이므로 랩 엔진(./lab.sh down)을 먼저 내립니다. 랩 네임스페이스의 GPU 쿼터(1)도 이를 강제합니다.
  • 버전·Helm 값 이름은 설치 시점의 KServe 문서를 기준으로 하세요(아래는 v0.18 이후 차트 구조 기준 예시).

실습 9-1 · KServe 설치 (Standard 모드)

bash
# 0) 이미 있는지 확인
kubectl get crd | grep -E "serving.kserve.io|cert-manager.io" || echo "없음"

# 1) cert-manager (없을 때만, 버전은 cert-manager 릴리스에서 최신 확인)
CM=<cert-manager 버전, 예: v1.x.y>
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/$CM/cert-manager.yaml
kubectl -n cert-manager wait --for=condition=Available deploy --all --timeout=5m

# 2) KServe CRD와 컨트롤러 (Standard 모드 = Knative 없이 Deployment·Service·HPA)
KS=<KServe 안정 버전, 예: v0.20.x>
helm install kserve-crd oci://ghcr.io/kserve/charts/kserve-crd --version $KS -n kserve --create-namespace
helm install kserve oci://ghcr.io/kserve/charts/kserve-resources --version $KS -n kserve \
  --set kserve.controller.deploymentMode=Standard
kubectl -n kserve get pods -o wide
kubectl get crd | grep serving.kserve.io        # inferenceservices, servingruntimes, llminferenceservices …

컨트롤러 이미지가 arm64를 지원하지 않는 태그라 GB10 노드에서 실패한다면, 컨트롤러를 x86 노드(P3)에 두도록 노드 셀렉터를 지정합니다(차트의 컨트롤러 nodeSelector 값). 외부 노출은 KServe가 만드는 Ingress 대신 7편의 Gateway·HTTPRoute를 그대로 쓸 것이므로, 차트에 ingress 생성 비활성화 옵션이 있다면 함께 지정합니다.

실습 9-2 · 같은 모델을 InferenceService로

yaml · isvc-qwen3-8b-fp8.yaml
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: qwen3-8b-fp8
  namespace: llmsvc-lab
  annotations:
    serving.kserve.io/deploymentMode: Standard
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 1                         # 오토스케일링은 18편에서
    deploymentStrategy: { type: Recreate } # GPU 1장: 지원되지 않는 버전이면 이 줄 삭제 후 수동 교체
    nodeSelector: { llm-lab/role: gpu-serving }
    tolerations: [ { key: nvidia.com/gpu, operator: Exists, effect: NoSchedule } ]
    containers:
    - name: kserve-container
      image: vllm/vllm-openai:v0.31.0      # 7편과 같은 이미지 (arm64 미지원이면 NGC 이미지)
      command: ["vllm", "serve", "/models/Qwen/Qwen3-8B-FP8",
                "--served-model-name", "qwen3-8b", "--port", "8080",
                "--gpu-memory-utilization", "0.35", "--max-model-len", "8192"]
      env:
      - { name: HF_HUB_OFFLINE, value: "1" }
      ports: [ { containerPort: 8080, protocol: TCP } ]
      resources:
        requests: { cpu: "4", memory: 16Gi }
        limits:   { cpu: "12", memory: 48Gi, nvidia.com/gpu: 1 }
      readinessProbe: { httpGet: { path: /health, port: 8080 }, periodSeconds: 5 }
      startupProbe:   { httpGet: { path: /health, port: 8080 }, periodSeconds: 10, failureThreshold: 180 }
      volumeMounts:
      - { name: models, mountPath: /models, readOnly: true }
      - { name: shm, mountPath: /dev/shm }
    volumes:
    - { name: models, persistentVolumeClaim: { claimName: model-cache, readOnly: true } }
    - { name: shm, emptyDir: { medium: Memory, sizeLimit: 8Gi } }

yaml · (선택) 게이트웨이로 노출 — HTTPRoute를 isvc로 돌리기
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: llm-openai, namespace: llmsvc-lab }
spec:
  parentRefs: [ { name: lab-gw } ]
  rules:
  - matches: [ { path: { type: PathPrefix, value: /v1 } } ]
    backendRefs: [ { name: qwen3-8b-fp8-predictor, port: 80 } ]   # 7편의 llm-engine 대신
    timeouts: { request: 600s }

이 한 줄 교체가 12장 “이전 경로”의 핵심입니다. 앱이 보는 주소와 모델 이름(qwen3-8b)은 그대로이고, 뒤의 서빙 방식만 바뀌었습니다. NetworkPolicy의 allow-gateway-to-engine은 app: llm-engine 라벨을 대상으로 하므로, KServe Pod에도 적용하려면 정책의 Pod 선택자를 넓히거나 isvc에 라벨을 추가해야 합니다. 이런 “주변 설정의 따라오기”가 프레임워크 이전에서 가장 자주 빠뜨리는 부분입니다.

17정리와 체크리스트

핵심 여섯 문장.

  1. 프레임워크는 성능이 아니라 운영 책임을 바꾼다. 같은 엔진이면 숫자는 같고, 배포·확장·라우팅·교체의 방식이 달라진다.
  2. 직접 Deployment는 모델 1~3개까지 충분하다. 오토스케일러·추론 라우팅·카나리를 손으로 붙이기 시작하면 프레임워크를 검토할 때다.
  3. KServe는 표준 CRD와 셀프서비스, LLM 쪽은 llm-d 기반 LLMInferenceService로 진화했다. Standard 모드가 LLM 서빙의 기본이다.
  4. llm-d는 분산 추론의 잘 닦인 경로, Dynamo는 NVIDIA 중심의 분산 추론 프레임워크, Ray Serve는 파이썬 파이프라인 조립에 강하다.
  5. 매니지드도 게이트웨이·관측·거버넌스는 우리 몫으로 남는다.
  6. 이전은 단계적으로: 게이트웨이로 앱이 보는 API를 고정하고, 아래층을 되돌릴 수 있게 바꾼다.
