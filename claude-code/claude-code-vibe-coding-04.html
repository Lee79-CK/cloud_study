프롬프트의기술

바이브 코딩에서 프롬프트는 사실상 소스 코드입니다. 요구사항을 Claude가 오해할 수 없는 지시로 바꾸고, 계획을 먼저 받아 비평하고, 일을 작게 쪼개고, 스스로 검증하게 만드는 법을 익힙니다.

모호한 요청을 6요소를 갖춘 프롬프트로 고쳐 쓴다
Plan 모드로 계획을 받고, 결함을 찾아 고친 뒤 실행시킨다
Claude가 스스로 통과·실패를 판단할 검증 수단을 함께 준다
실패하는 프롬프트 패턴을 알아보고 대화 중 방향을 바로잡는다
프롬프트 점검기

아무 요청이나 써 보세요. 6요소가 들어 있는지 간단한 규칙으로 점검합니다.

단어 패턴으로 판단하는 학습용 점검기입니다. 실제 품질을 보장하지는 않습니다.

프롬프트가 결과를 정하는 이유

공식 모범 사례 문서는 거의 모든 팁이 하나의 제약에서 나온다고 말합니다. 컨텍스트 창은 빨리 차고, 찰수록 성능이 떨어진다는 것입니다. 모호한 프롬프트는 이 귀한 공간을 추측과 왕복 대화로 채웁니다.

또 하나: Claude는 일이 끝나 보이면 멈춥니다. 실행해 볼 검사가 없으면 “끝나 보인다”가 유일한 신호가 되고, 그때부터 여러분이 검증 루프가 됩니다. 실수 하나하나가 여러분이 발견해 주기를 기다리는 것이죠. 통과·실패를 돌려주는 무언가를 주면 루프가 스스로 닫힙니다.

🧠 Claude가 잘하는 것

의도를 추론하고, 코드를 읽어 맥락을 찾고, 여러 파일에 걸친 변경을 조율하는 것. 어떤 파일을 읽을지, 어떤 명령을 실행할지 일일이 지시할 필요는 없습니다(2편의 “위임하라, 지시하지 말고”).

🙈 Claude가 못 하는 것

여러분의 머릿속을 읽는 것. 어떤 서버가 운영인지, 무엇을 건드리면 안 되는지, 언제 “완료”인지, 팀이 어떤 방식을 쓰는지는 말해 주지 않으면 그럴듯한 추측으로 채웁니다.

이번 편의 핵심 공식 좋은 결과 = 분명한 목표 × 필요한 맥락 × 지켜야 할 제약 × 스스로 돌릴 수 있는 검증. 어느 하나라도 0이면 결과도 흔들립니다.

좋은 프롬프트의 6요소

1편의 4요소(목표·맥락·제약·검증)에 공식 문서가 강조하는 두 가지를 더합니다. 범위(어느 파일·어느 상황)와 근거·패턴(답을 찾을 곳, 따라 할 예시)입니다.

요소질문예시 표현
🎯 목표무엇을 얻고 싶은가“check_disk.sh에 JSON 출력 옵션을 추가해줘”
📍 범위어디를, 어떤 상황을“@scripts/check_disk.sh만”, “임계값을 넘은 마운트가 없을 때도”
🗺️ 맥락누가, 어디서, 왜 쓰나“RHEL 9 서버에서 cron으로 매일 돌고, 결과는 모니터링 수집기가 읽어”
🧭 근거·패턴무엇을 보고 따라 할까“ping_all.sh의 출력 방식을 따라”, “git 기록을 보고 왜 이렇게 됐는지 정리해”
🚧 제약하면 안 되는 것“외부 패키지 설치 금지”, “기존 텍스트 출력은 그대로”, “고치지 말고 보고만”
✅ 검증완료를 무엇으로 증명하나“빈 결과와 85% 사례를 실행해서 출력을 보여줘”, “테스트 돌리고 통과할 때까지 고쳐”
모든 프롬프트에 6요소가 필요한 것은 아닙니다 공식 문서도 탐색할 때는 모호한 프롬프트가 유용할 수 있다고 말합니다. “이 파일에서 뭘 개선하겠어?” 같은 질문은 여러분이 생각지 못한 점을 드러냅니다. 원칙은 되돌리기 어렵거나 범위가 클수록 더 구체적으로입니다.

“검증까지 해줘” 패턴

검증 수단은 대화 안에서 Claude가 읽을 수 있는 신호면 무엇이든 됩니다. 테스트, 빌드 종료 코드, 린터, 출력을 기준 파일과 비교하는 스크립트, 디자인과 비교할 스크린샷. 그리고 성공했다고 말하게 하지 말고 증거를 보여 달라고 하세요. 실행한 명령과 결과, 테스트 출력, 스크린샷. 증거를 보는 것이 직접 다시 돌려 보는 것보다 빠르고, 지켜보지 않은 세션에도 통합니다.

검증의 사다리

위로 갈수록 설정이 더 들지만, 사람이 지켜보지 않아도 올바르게 끝날 가능성이 커집니다.

1
프롬프트 안에서

“구현한 뒤 테스트를 돌리고, 실패하면 통과할 때까지 고쳐. 마지막에 테스트 출력을 보여줘.” 오늘 당장 모든 작업에 쓸 수 있습니다. (이번 편)

2
세션 목표 /goal

검사를 세션의 완료 조건으로 걸면 별도 평가자가 매 턴 뒤 다시 확인하고, 조건이 풀릴 때까지 Claude가 계속 일합니다. (19편)

3
결정적 관문 Stop Hook

검사 스크립트가 통과할 때까지 턴이 끝나지 못하게 막습니다. 사람의 기억이 아니라 시스템이 보장합니다. (11편)

4
두 번째 의견

검증용 서브에이전트나 동적 워크플로우가 새로운 컨텍스트에서 결과를 반박해 봅니다. 일한 에이전트가 자기 채점을 하지 않게 합니다. (13·18편)

증상을 숨기지 말고 원인을 고치게 하세요 “빌드가 실패해”라고만 하면 에러를 무시하거나 검사를 꺼서 “통과”시키는 길도 열려 있습니다. 공식 예시처럼 “에러 내용은 이것이다. 고치고 빌드가 성공하는지 확인해. 에러를 억제하지 말고 근본 원인을 고쳐”라고 쓰세요. 테스트를 약하게 고쳐서 통과시키는 것도 같은 함정입니다.

탐색 → 계획 → 구현 → 커밋

바로 코딩부터 시키면 엉뚱한 문제를 푸는 코드가 나올 수 있습니다. 공식 문서가 권하는 흐름은 Plan 모드로 조사와 실행을 분리하는 네 단계입니다.

🔍
1. 탐색 (Plan 모드)

Shift+Tab으로 상태 줄에 ⏸ plan mode on이 보일 때까지 누르거나 claude --permission-mode plan으로 시작합니다. Claude는 파일을 읽고 질문에 답하지만 아무것도 바꾸지 않습니다.

scripts 폴더와 servers.txt를 읽고, 서버 점검이 어떤 흐름으로 돌아가는지 이해해줘. 결과를 어디로 출력하는지도 확인해.
📝
2. 계획 (Plan 모드)

자세한 구현 계획을 요청합니다. Ctrl+G를 누르면 계획을 텍스트 에디터에서 직접 고칠 수 있습니다. 한 번만 계획하려면 프롬프트 앞에 /plan을 붙여도 됩니다.

check_disk.sh에 --json 옵션을 넣고 싶어. 어떤 파일을 바꿔야 하고, 기존 텍스트 출력과 어떻게 공존시킬지, 어떻게 검증할지 계획을 세워줘.
🛠️
3. 구현

계획을 승인하면 Plan 모드를 빠져나옵니다. 승인 선택지는 “Yes, and use auto mode”, “Yes, manually approve edits”, “No, keep planning”입니다. 그다음 계획대로 구현하고 검증하게 합니다.

계획대로 구현해. 임계값 0과 95로 각각 실행해서 텍스트와 JSON 출력을 모두 보여주고, JSON은 python3 -m json.tool로 유효한지 확인해.
📦
4. 커밋

설명적인 메시지로 커밋하고 필요하면 PR을 만들게 합니다(7편).

변경 내용을 설명하는 메시지로 커밋해줘.

계획이 필요할까? 판단 게임

공식 문서의 기준: diff를 한 문장으로 설명할 수 있으면 계획은 건너뛰세요. 계획은 접근법이 불확실할 때, 여러 파일을 바꿀 때, 낯선 코드를 고칠 때 가장 쓸모 있습니다.

6 / 15

계획을 비평하는 법

Plan 모드의 가치는 계획을 읽고 고칠 때 나옵니다. 계획을 볼 때 확인할 다섯 가지입니다.

① 범위

요청하지 않은 파일이나 재작성이 들어 있지 않은가?

② 제약

설치 금지, 운영 금지 같은 제약을 어기는 단계가 없는가?

③ 모호함

두 해석이 가능한 결정이 그냥 넘어가지 않았는가?

④ 검증

“확인한다”가 아니라 무엇을 실행해 무엇을 볼지 적혀 있는가? 빈 경우·오류 경우도?

⑤ 되돌리기

배포·삭제처럼 되돌리기 어려운 단계가 끼어 있지 않은가?

실습: 이 계획의 문제를 찾아보세요

요청: “check_disk.sh에 --json 옵션을 추가해줘. 외부 패키지는 설치하지 말고, 기존 텍스트 출력은 유지해.” 아래는 Claude가 내놓았다고 가정한 계획입니다. 문제가 있다고 생각하는 줄에 표시를 누르고 “채점”하세요.

계획을 고치는 세 가지 방법 “No, keep planning”을 고르고 무엇을 바꿀지 말하기, Ctrl+G로 계획을 에디터에서 직접 고치기, 또는 문제가 많다면 /clear 후 제약을 더 분명히 쓴 프롬프트로 다시 시작하기.

작게 쪼개기

1편의 사이클을 기억하세요. 작게, 자주. 한 바퀴 = 커밋 하나. 큰 요청을 한 번에 던지면 컨텍스트가 빨리 차고, 어디서 틀어졌는지 찾기 어렵고, 되돌리기도 어렵습니다. 좋은 조각은 세 조건을 만족합니다: 혼자 실행해 확인할 수 있고, 한 문장으로 설명되고, 다음 조각의 토대가 된다.

큰 요청
고객사 서버 상태를 보여주는 웹 대시보드 만들어줘. 핑, 디스크, 메모리, 인증서 만료까지 다 보여주고, 문제가 있으면 슬랙으로 알림도 보내고, 고객사별로 로그인해서 자기 서버만 보게 해줘.
이 다섯 조각이 이 과정 5편 이후 실습의 실제 순서입니다. 1~2번이 5편, 알림은 19편, 인증과 고객 분리는 운영화 단계에서 다룹니다. 특히 5번(로그인·권한)은 1편의 🔴 영역이라 AI 페어 프로그래밍 기어로 진행합니다.
프롬프트 한 번, diff 하나 각 조각을 끝낼 때마다 실행해서 확인하고 커밋한 뒤 다음 조각으로 넘어가세요. 주제가 완전히 바뀌면 /clear로 새로 시작하는 편이 낫습니다. 필요한 맥락은 커밋 기록과 CLAUDE.md(8편)에 남아 있습니다.

맥락을 넣는 다섯 가지 방법

📎 @파일 멘션

코드가 어디 있는지 설명하는 대신 @scripts/check_disk.sh처럼 지정합니다. Tab으로 자동 완성되고, 답하기 전에 먼저 읽힙니다.

🖼️ 이미지 붙여넣기

에러 대화상자, 대시보드 화면, 화이트보드 사진을 끌어다 놓거나 Ctrl+V(Mac도 Cmd가 아니라 Ctrl)로 붙여 넣습니다. UI 작업은 “이 디자인대로 만들고, 결과 스크린샷을 원본과 비교해서 차이를 고쳐”가 공식 예시입니다.

🔗 URL

문서와 API 레퍼런스 주소를 줍니다. 자주 쓰는 도메인은 /permissions로 허용해 두면 매번 묻지 않습니다(9편).

🚰 파이프로 넣기

cat error.log | claude -p "이 에러 설명해줘"처럼 셸에서 바로 넘깁니다. 대화형 세션이 아니라 한 번 실행하는 모드입니다(19편).

🧲 직접 가져오게 하기

“kubectl get events로 직접 확인해”처럼 Claude가 필요한 것을 스스로 가져오게 합니다. 처음 보는 CLI도 “foo-cli --help로 사용법을 익힌 뒤 써”라고 하면 배워서 씁니다.

❓ 곁가지 질문은 /btw

잠깐 확인할 질문은 /btw로 하면 답이 대화 기록에 남지 않아 컨텍스트가 늘지 않습니다.

CLI가 가장 컨텍스트 효율적입니다 공식 문서는 외부 서비스와 일할 때 gh, aws, gcloud 같은 CLI 도구를 쓰라고 권합니다. 인프라 엔지니어라면 이미 가진 kubectl, az, terraform, openstack CLI가 그대로 Claude의 손이 됩니다. 단, 그 CLI가 어떤 계정과 컨텍스트로 로그인돼 있는지는 늘 의식하세요(3편).
로그를 통째로 붙여넣지 마세요 2편의 컨텍스트 시뮬레이터에서 봤듯, 대화에 붙여넣은 수천 줄은 압축 전까지 그대로 남습니다. 파일로 저장해 두고 “@logs/app.log에서 ERROR 줄만 시간순으로 정리해”라고 하는 편이 훨씬 가볍습니다. 고객 정보가 있는 로그는 마스킹 먼저.

Claude에게 인터뷰 받기

무엇을 원하는지 아직 흐릿한 큰 기능이라면, 직접 완벽한 프롬프트를 쓰려 하지 말고 Claude에게 인터뷰를 받으세요. 공식 문서가 권하는 방법입니다. Claude가 객관식 질문 도구(AskUserQuestion)로 여러분이 미처 생각하지 못한 구현 방식, 화면, 예외 상황, 트레이드오프를 묻고, 마지막에 명세서를 씁니다.

[무엇을 만들고 싶은지 한두 문장]을 만들고 싶어. AskUserQuestion 도구로 나를 자세히 인터뷰해줘. 기술 구현, 화면과 사용 흐름, 예외 상황, 걱정되는 점, 트레이드오프를 물어봐. 뻔한 질문은 하지 말고, 내가 생각 못 했을 어려운 부분을 파고들어. 다 다뤘다고 판단되면 완성된 명세를 SPEC.md로 써줘.

명세가 완성되면 새 세션을 열어 구현합니다. 인터뷰로 찬 컨텍스트 대신 구현에만 집중한 깨끗한 컨텍스트에서, 글로 된 명세를 참고하게 됩니다. 좋은 명세는 그 자체로 완결적입니다: 관련 파일과 인터페이스를 이름으로 적고, 범위 밖을 명시하고, 기능이 동작함을 증명하는 끝에서 끝까지의 검증 단계로 끝납니다.

도구무엇을 하나언제
Esc하던 행동을 멈춤. 컨텍스트는 유지엉뚱한 파일을 열기 시작할 때 바로
그냥 입력멈추지 않고 대기열에 수정 지시방향만 살짝 틀 때
Esc 두 번 · /rewind대화·코드·둘 다를 이전 체크포인트로 복원, 또는 일부만 요약잘못된 길로 몇 걸음 갔을 때
“방금 거 되돌려”Claude가 스스로 변경을 되돌림마지막 변경만 취소할 때
/clear컨텍스트를 완전히 비우고 새로 시작관련 없는 작업으로 넘어갈 때, 두 번 교정해도 안 될 때
두 번의 법칙 한 세션에서 같은 문제로 두 번 이상 바로잡았다면 컨텍스트가 실패한 시도들로 어지러워진 상태입니다. /clear로 새로 시작하고, 지금까지 배운 것을 반영한 더 구체적인 프롬프트를 쓰세요. 깨끗한 세션 + 더 나은 프롬프트가 교정이 쌓인 긴 세션보다 거의 항상 낫습니다.
체크포인트의 한계 체크포인트는 Claude의 파일 편집 도구로 바뀐 것만 추적합니다. Bash 명령이나 외부 프로세스로 바뀐 것은 잡지 못하므로 Git을 대신하지 못합니다. 그래서 위험해 보이는 시도 전에는 커밋부터 해 두세요(7편).
