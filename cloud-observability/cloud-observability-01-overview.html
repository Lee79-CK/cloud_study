Cloud 모니터링·로깅 실전 강의 1편 (Level 1. 전체 지도)

2026 Observability
전체 지도

장애 하나를 네 개의 창으로 들여다보는 것부터 시작합니다. 메트릭, 로그, 트레이스, 프로파일이 각각 무엇을 알려주고 무엇을 놓치는지 알면, 수십 개의 오픈소스 이름이 하나의 지도로 정리됩니다.

1모니터링과 관측성

둘은 경쟁 관계가 아니라 포함 관계입니다. 관측성은 모니터링이 대답하지 못하는 질문까지 다룹니다.

자동차로 비유하면

모니터링(Monitoring)은 자동차 계기판입니다. 속도, 연료, 엔진 온도처럼 미리 정해 둔 항목을 보여 주고, 경고등이 켜지면 무언가 잘못됐다고 알려 줍니다. 하지만 계기판은 "왜 엔진 온도가 올라갔는가"라는 질문에는 답하지 못합니다.

관측성(Observability)은 정비소의 진단 장비입니다. 차에 연결하면 수백 개의 센서 기록, 오류 코드, 부품별 동작 기록을 꺼내 볼 수 있고, 처음 보는 고장이라도 데이터를 뒤져 원인을 좁혀 갈 수 있습니다.

원래 관측성은 제어 이론에서 온 말로, "외부로 나오는 출력만 보고 시스템 내부 상태를 얼마나 잘 추론할 수 있는가"를 뜻합니다. 소프트웨어에서 출력은 곧 텔레메트리(Telemetry), 즉 시스템이 스스로 내보내는 측정 데이터입니다.

미리 아는 문제와 처음 보는 문제

두 개념의 차이를 가장 잘 보여 주는 것은 질문의 종류입니다.

구분모니터링관측성
다루는 질문미리 예상한 문제 (Known Unknowns)
"CPU가 90%를 넘었나?"		예상하지 못한 문제 (Unknown Unknowns)
"왜 특정 고객사의 결제만 느린가?"
작동 방식임곗값과 대시보드를 미리 만들어 두고 감시풍부한 데이터를 남겨 두고 사후에 자유롭게 질의
핵심 산출물알림, 상태 대시보드원인 분석 경로 (메트릭에서 로그, 트레이스로 이동)
데이터 요구요약된 숫자로 충분맥락이 붙은 상세 데이터와 신호 간 연결 정보
잘 맞는 환경구성 요소가 적고 변화가 느린 시스템MSA, Kubernetes, 멀티클라우드처럼 구성 요소가 많고 자주 바뀌는 시스템
관측성은 모니터링을 대체하지 않습니다

장애를 알아차리는 일은 여전히 모니터링의 몫입니다. 관측성은 알아차린 다음 원인을 찾는 시간을 줄여 줍니다. 그래서 이 시리즈도 2단계인 메트릭과 알림부터 쌓아 올립니다.

왜 지금 더 중요해졌나

VM 몇 대에 모놀리식 애플리케이션 하나를 운영하던 시절에는 서버에 SSH로 접속해 로그 파일을 열어 보면 원인을 찾을 수 있었습니다. 지금 MSP 엔지니어가 마주하는 환경은 다릅니다.

  • 파드는 사라집니다. 장애 난 파드가 재시작되면 그 안의 로그도 함께 사라집니다. 외부로 미리 수집해 두지 않으면 증거가 없습니다.
  • 요청은 여러 서비스를 거칩니다. 한 번의 결제가 10개 서비스를 통과한다면, 어느 서비스가 범인인지 찾는 일 자체가 어려운 문제가 됩니다.
  • 환경이 섞여 있습니다. AKS, EKS, OCP, 온프레미스 VM이 한 고객사 안에 공존하면 도구마다 따로 보는 방식으로는 전체 그림을 그릴 수 없습니다.
  • 데이터는 비쌉니다. 모든 것을 다 저장하면 관측 비용이 인프라 비용을 위협합니다. 무엇을 어디에 얼마나 남길지 설계해야 합니다.

2네 가지 신호

관측 데이터는 크게 네 종류로 나뉩니다. 이 강의 전체에서 색으로 구분해 표시하니 지금 색과 함께 기억해 두세요.

메트릭 (Metrics)

무엇이, 언제, 얼마나 나빠졌나?

정체
일정 간격으로 측정한 숫자의 시계열. 이름과 라벨, 타임스탬프, 값으로 구성
강점
저장 비용이 낮고 쿼리가 빠름. 알림과 추세 분석에 최적
약점
개별 요청의 맥락이 없음. 라벨 조합이 폭증하면 비용 급증
대표 도구
Prometheus, Mimir, Thanos

로그 (Logs)

그 순간 무슨 일이 있었나?

정체
특정 시점에 발생한 사건을 기록한 텍스트 또는 구조화된 레코드
강점
가장 풍부한 맥락. 오류 메시지, 파라미터, 사용자 정보까지 담김
약점
양이 가장 많아 저장과 검색 비용이 큼. 형식이 제각각
대표 도구
Loki, OpenSearch, Elasticsearch

트레이스 (Traces)

요청이 어디를 거쳤고 어디서 시간이 사라졌나?

정체
하나의 요청이 여러 서비스를 지나는 경로. 작업 단위인 스팬(Span)의 트리
강점
MSA에서 병목 위치를 한눈에 보여 줌. 서비스 의존 관계 파악
약점
애플리케이션 계측이 필요. 모두 저장하면 비싸서 샘플링 설계 필요
대표 도구
Tempo, Jaeger

프로파일 (Profiles)

어떤 함수가 CPU와 메모리를 쓰고 있나?

정체
코드의 함수별 자원 사용량을 주기적으로 표본 추출한 데이터
강점
코드 줄 단위까지 원인을 좁힘. 성능 개선과 비용 절감에 직결
약점
상대적으로 새로운 신호라 도입 사례와 운영 노하우가 적음
대표 도구
Pyroscope

여기에 이벤트(Events)를 보조 신호로 더합니다. 배포, 설정 변경, 파드 재시작, 알림 발생처럼 "무언가 바뀌었다"는 기록입니다. 장애 원인의 상당수는 변경에서 시작되기 때문에, 그래프 위에 배포 시점을 겹쳐 보는 것만으로도 조사 시간이 크게 줄어듭니다.

같은 사건, 네 가지 데이터 형태

실제로 저장되는 모양을 보면 신호별 비용 차이가 직관적으로 이해됩니다. 아래는 앞의 결제 장애에서 나온 데이터입니다.

# 메트릭: Prometheus 노출 형식 (한 줄 = 하나의 시계열의 현재 값)
http_server_requests_total{service="payment",method="POST",status="500"} 1832

# 로그: 구조화된 JSON 한 건
{"ts":"2026-10-08T14:02:11Z","level":"error","service":"payment",
 "msg":"db pool exhausted","waiting":143,"trace_id":"4bf92f3577b34da6..."}

# 트레이스: 스팬 하나 (OTLP를 단순화)
{"trace_id":"4bf92f...","span_id":"00f067aa","parent":"a3ce929d",
 "name":"pool.acquire","duration_ms":2300,"service.name":"payment"}

# 프로파일: 콜 스택별 샘플 수 (접힌 스택 형식)
main;payment.Charge;retryWithBackoff;pool.tryAcquire 4102
main;payment.Charge;order.Validate 2950

메트릭은 요청이 백만 건이어도 시계열 하나의 숫자만 올라갑니다. 반면 로그와 트레이스는 요청 수에 비례해 데이터가 늘어납니다. 그래서 일반적으로 메트릭은 넓게, 로그는 골라서, 트레이스는 샘플링해서 저장하는 설계가 기본이 됩니다.

카디널리티(Cardinality): 메트릭 비용의 숨은 폭탄

메트릭의 비용은 요청 수가 아니라 라벨 값의 조합 수에 비례합니다. service 10개 × status 5개면 시계열 50개지만, 여기에 user_id 라벨을 붙여 사용자가 10만 명이면 시계열이 500만 개가 됩니다. 사용자 ID, 주문 번호, 요청 URL 전체처럼 값이 무한히 늘어나는 정보는 메트릭 라벨이 아니라 로그나 트레이스에 넣어야 합니다. 이 원칙은 Loki의 로그 라벨에도 똑같이 적용되며 3편과 8편에서 자세히 다룹니다.

계층을 나눠 생각하면 좋은 점

계층으로 보면 "Loki 대신 OpenSearch"처럼 같은 층 안에서의 교체와 "Alloy와 OTel Collector를 둘 다 써야 하나"처럼 역할이 겹치는 경우가 바로 보입니다. 같은 층의 도구는 대체 관계이거나 역할 분담 관계이고, 다른 층의 도구는 조합 관계입니다.

문서의 아키텍처 다이어그램도 같은 구조입니다. 수집 대상에서 Prometheus가 메트릭을 스크레이핑하고, Alloy나 OpenTelemetry Collector가 로그와 트레이스를 모아 Loki와 Tempo로 보내며, Grafana가 모든 저장소를 한 화면에서 조회합니다. 규모가 커지면 Mimir나 Thanos, 오브젝트 스토리지가 저장 계층 뒤에 붙습니다.

Alloy와 OTel Collector는 같은 층에 있습니다

Grafana Alloy는 OpenTelemetry Collector의 배포판 중 하나로, Collector의 컴포넌트에 Prometheus 스크레이핑과 Loki 전송 같은 Grafana 생태계 기능을 더한 것입니다. 그래서 반드시 둘 다 설치할 필요는 없습니다. Grafana 중심이면 Alloy, 여러 벤더 백엔드로 보내는 표준 파이프라인이 중심이면 OTel Collector를 먼저 검토하고, 복합 환경에서는 노드 에이전트와 중앙 게이트웨이처럼 역할을 나눠 둘 다 쓰기도 합니다. 11편에서 세 가지 배치 패턴을 실습합니다.

Alloy수집PrometheusLokiTempo조회Grafana

LGTM은 Loki, Grafana, Tempo, Mimir의 머리글자입니다. 문서에서는 Mimir 자리에 Prometheus를 두고 시작해 규모가 커질 때 Mimir나 Thanos로 확장하는 방식을 권합니다. 한 회사(Grafana Labs)가 주도하는 도구들이라 설정 방식과 라벨 체계가 비슷하고, Grafana 안에서 메트릭, 로그, 트레이스 사이를 이동하는 기능이 가장 매끄럽습니다.

강점

  • 세 신호를 한 화면에서 연결해 조사 (3장의 흐름이 기본 동작)
  • Loki는 로그 본문을 인덱싱하지 않아 저장 비용이 상대적으로 낮음
  • Kubernetes와 MSA 환경에 맞춘 문서와 Helm 차트가 풍부

약점과 주의

  • 복잡한 전문 검색과 보안 분석은 OpenSearch 계열보다 약함
  • Grafana, Loki, Tempo, Mimir는 AGPLv3 라이선스 (9장)
  • Loki 라벨 설계를 잘못하면 성능과 비용이 급격히 나빠짐

맞는 고객사: Kubernetes 위의 MSA, 운영 인력이 적어 한 화면에서 끝내고 싶은 팀, 장애 분석 중심의 로그 활용.

OTel SDK계측OTel Collector / Alloy전달Prometheus·MimirLokiTempo조회Grafana

저장과 조회는 1번과 같지만, 데이터를 만들고 모으는 방식을 OpenTelemetry 표준으로 정한 것이 핵심 차이입니다. 1번이 "어디에 저장하고 무엇으로 보는가"를 정한 조합이라면, 2번은 "애플리케이션이 어떤 형식으로 데이터를 내보내는가"까지 정한 조합입니다.

강점

  • 계측 코드가 특정 벤더에 묶이지 않아 백엔드 교체가 쉬움
  • 여러 고객사, 여러 클라우드에서 같은 속성 이름을 강제할 수 있음
  • AIOps 연계 시 데이터 형식이 일관돼 자동화가 쉬움 (17편)

약점과 주의

  • 애플리케이션 팀의 계측 참여가 필요 (자동 계측으로 부담 완화)
  • Collector 파이프라인 설계와 운영이라는 새 업무가 생김
  • 표준 자체가 빠르게 발전 중이라 버전 관리가 필요

맞는 고객사: 멀티클라우드, 대규모 플랫폼, 상용 APM에서 벗어나려는 조직, 고객사가 많은 MSP 중앙 관제.

Prometheus메트릭Grafana/Fluent Bit로그OpenSearch조회OpenSearch Dashboards

메트릭은 Prometheus로, 로그는 Fluent Bit로 모아 OpenSearch에 저장합니다. OpenSearch는 Elasticsearch 7.10을 기반으로 AWS가 시작해 현재 리눅스 재단 산하 OpenSearch Software Foundation이 관리하는 검색 엔진으로, Apache 2.0 라이선스입니다.

강점

  • 로그의 모든 필드를 인덱싱해 복잡한 조건 검색과 집계가 강력
  • 보안 분석, 감사 로그 조회, 이상 탐지 플러그인 등 보안 기능
  • 대기업 SI와 공공 환경에서 익숙한 구조, 라이선스 부담이 적음

약점과 주의

  • 인덱스 때문에 저장 공간과 메모리 요구가 큼
  • 샤드, 매핑, 인덱스 수명주기 관리 등 운영 난도가 높음
  • 메트릭과 로그 UI가 나뉘어 신호 간 이동이 덜 매끄러움

맞는 고객사: VM과 Kubernetes가 섞인 대기업, 보안관제팀이 로그를 직접 조회하는 조직, 감사 대응이 중요한 금융·공공.

Prometheus메트릭Grafana/Beats·Logstash로그Elasticsearch조회Kibana

Elasticsearch, Logstash, Kibana로 구성된 전통적인 ELK Stack에 메트릭용 Prometheus를 더한 형태입니다. 새로 고르기보다는 이미 가진 것을 지키며 메트릭을 보강할 때의 선택지입니다.

강점

  • 쌓아 둔 대시보드, 알림, 파서, 운영 노하우를 그대로 활용
  • 전문 검색과 분석 기능이 성숙함
  • 운영 인력의 학습 비용이 거의 없음

약점과 주의

  • 라이선스가 버전과 배포판에 따라 다름 (9장). 반드시 확인
  • OpenSearch와 마찬가지로 저장 비용과 운영 부담이 큼
  • 오래된 버전을 유지 중이라면 업그레이드 경로 자체가 과제

맞는 고객사: ELK를 수년간 운영해 자산이 많은 조직, 레거시 시스템 중심 환경.

신규 환경의 기본은 Prometheus + Grafana + Loki + Grafana Alloy + OpenTelemetry입니다. 여기에 MSA라면 Tempo, 대규모·멀티클러스터라면 Mimir나 Thanos, 보안·감사 로그라면 OpenSearch, 성능 분석이라면 Pyroscope를 더합니다. 처음부터 전부 설치하는 것이 아니라 메트릭, 로그, 트레이스, 중앙화, AIOps 연계 순서로 쌓아 가는 것이 이 시리즈의 진행 순서이기도 합니다.

7로그 저장소 미리보기

조합의 성격과 운영비를 가장 크게 가르는 것은 로그 저장소입니다. 차이의 뿌리는 인덱싱 방식 하나입니다.

도서관에 비유해 보겠습니다. OpenSearch와 Elasticsearch는 책의 모든 단어에 대해 "이 단어는 몇 쪽에 나온다"는 색인을 만들어 두는 방식(역색인, Inverted Index)입니다. 어떤 단어로 찾아도 즉시 나오지만, 색인 자체가 책만큼 두꺼워질 수 있습니다. Loki는 책장 라벨(장르, 저자, 연도)만 색인하고 본문은 압축해서 보관합니다. 라벨로 책장을 좁힌 다음 그 안의 책을 빠르게 훑어 읽는 방식이라 색인이 아주 작습니다.

Loki: 라벨만 인덱싱

{app="payment", ns="shop", env="prod"}
  청크 1 (압축된 원문 1,200줄)
  청크 2 (압축된 원문 1,350줄)
{app="cart", ns="shop", env="prod"}
  청크 1 (압축된 원문 980줄)

"db pool exhausted"를 찾으려면 라벨로 범위를 좁힌 뒤 청크를 읽으며 필터링합니다. 범위를 좁히지 않고 전체를 검색하면 느려집니다.

OpenSearch: 모든 필드와 단어를 인덱싱

"exhausted" → 문서 #1832, #1840, #2011
"pool" → 문서 #1832, #1833, #1840 ...
waiting: 143 → 문서 #1832
level: error → 문서 #1832, #1834 ...

9라이선스 기초

MSP는 오픈소스를 고객에게 서비스 형태로 제공하는 경우가 많아 라이선스를 정확히 알아야 합니다. 겁먹을 필요도, 무시할 필요도 없습니다.

먼저 짚어 둘 점

이 장은 엔지니어가 알아야 할 기본 개념을 설명할 뿐 법률 자문이 아닙니다. 실제 계약과 서비스 설계에서는 회사의 오픈소스 정책과 법무 검토를 따르세요.

두 가지 라이선스 성격

Apache 2.0은 허용형(Permissive) 라이선스입니다. 상업적으로 사용, 수정, 재배포할 수 있고, 저작권 고지와 라이선스 사본을 함께 제공하면 됩니다. 수정한 코드를 공개할 의무가 없습니다.

AGPLv3는 강한 카피레프트(Copyleft) 라이선스입니다. GPL과 마찬가지로 수정한 프로그램을 배포하면 소스를 공개해야 하는데, 여기에 하나가 더 붙습니다. 수정한 프로그램을 네트워크를 통해 다른 사용자가 이용하게 하면 그 사용자에게도 수정된 소스를 받을 수 있는 방법을 제공해야 합니다. 클라우드 서비스 시대에 "배포하지 않고 서비스로만 제공"하는 우회를 막기 위한 조항입니다.

아래 상황은 일반적인 해석의 방향을 보여 주기 위한 예입니다. 각 항목을 펼쳐 보세요.

수정하지 않은 Grafana와 Loki를 고객사 Kubernetes에 설치해 운영 대행한다

AGPL의 소스 제공 의무는 프로그램을 수정했을 때 생기는 것이 핵심입니다. 공식 바이너리나 이미지를 수정 없이 사용하는 경우에는 일반적으로 추가 의무가 생기지 않는다고 해석됩니다. 대시보드 JSON, 설정 파일, 알림 규칙을 작성하는 것은 프로그램 수정이 아닙니다.

Loki 소스를 고쳐 자체 빌드한 이미지를 여러 고객에게 서비스로 제공한다

AGPL의 네트워크 조항이 적용되는 대표적인 경우입니다. 서비스를 이용하는 사용자가 수정된 소스를 받을 수 있도록 해야 할 수 있습니다. 수정이 꼭 필요하다면 업스트림에 기여해 공식 버전에 반영되게 하는 것이 가장 깔끔한 방법입니다.

고객사의 오픈소스 정책이 AGPL 사용 자체를 금지한다

라이선스의 실제 의무와 별개로, 조직 정책이 우선합니다. 이 경우 로그는 Fluent Bit와 OpenSearch, 메트릭 장기 저장은 Thanos처럼 Apache 2.0 구성 요소 중심으로 설계하는 3번 조합 계열이 현실적인 답이 됩니다. 시각화 도구도 정책 검토 대상에 포함해야 합니다.

Grafana 플러그인을 직접 개발해 고객에게 제공한다

플러그인이 Grafana의 코드를 수정하는지, 공개된 플러그인 인터페이스로만 동작하는지에 따라 판단이 달라질 수 있습니다. 사업 모델과 관련된 부분이므로 법무 검토 대상입니다.

12흔한 오해 6가지

신입 엔지니어가 자주 하는 오해와 바로잡은 내용입니다.

"Prometheus에 로그도 넣으면 되지 않나요?"

Prometheus는 숫자 시계열 전용 저장소입니다. 로그 문장을 라벨에 넣으면 값이 매번 달라 카디널리티가 폭발합니다. 로그에서 숫자를 뽑아 메트릭으로 만드는 것은 가능하지만(9편 로그 기반 메트릭), 로그 자체는 로그 저장소에 둡니다.

"Loki는 전문 검색이 안 된다"

됩니다. 다만 라벨로 범위를 좁힌 다음 원문을 훑는 방식이라 검색 범위가 넓을수록 느려집니다. "안 된다"가 아니라 "쿼리 설계가 성능을 좌우한다"가 정확합니다.

"Alloy와 OTel Collector를 둘 다 깔아야 한다"

Alloy는 OTel Collector의 배포판이라 대부분의 역할이 겹칩니다. 하나로 시작하고, 역할 분리가 필요할 때 조합합니다.

"OpenTelemetry가 Prometheus를 대체한다"

OpenTelemetry는 데이터를 만들고 모으는 표준이고, 저장소가 아닙니다. 설문에서도 응답자의 65%가 둘 모두에 투자하고 있었습니다. Prometheus 3.x는 OTLP 메트릭을 직접 받을 수 있어 오히려 둘의 결합이 강해지고 있습니다.

"AGPL이라 회사에서 못 쓴다"

수정 없이 사용하는 경우 일반적으로 추가 의무가 생기지 않습니다. 다만 조직 정책이 금지하면 정책이 우선이고, 수정해서 서비스로 제공할 계획이라면 법무 검토가 필요합니다.

"처음부터 전부 깔아 두면 나중에 편하다"

쓰지 않는 구성 요소도 업그레이드, 보안 패치, 장애 대응의 대상입니다. 메트릭과 알림이 안정된 다음 로그, 그다음 트레이스 순서로 쌓아야 각 단계에서 운영 노하우가 생깁니다.

  1. 모니터링은 장애를 알아차리게 하고, 관측성은 처음 보는 장애의 원인을 찾게 합니다. 둘은 포함 관계입니다.
  2. 메트릭은 무엇이 얼마나, 로그는 무슨 일이, 트레이스는 어디서, 프로파일은 어떤 코드가를 답합니다. 이벤트는 계기를 알려 줍니다.
  3. 신호를 이어 주는 공통 라벨, trace_id, Exemplar, 시간이 갖춰져야 관측성이 완성됩니다. 라벨 표준이 도구 선택보다 먼저입니다.
  4. 신규 구축의 기본은 Prometheus + Grafana + Loki + Alloy + OpenTelemetry이고, Tempo, Mimir/Thanos, OpenSearch, Pyroscope는 요구에 따라 더합니다.
  5. Promtail과 Grafana Agent는 EOL입니다. 설문 수치는 시장점유율이 아니며, 라이선스는 수정 여부와 조직 정책을 함께 봅니다.

다음 편 예고: 2편 실습 랩 구축

하이브리드 클라우드를 노트북 한 대에 축소해 옮깁니다. kind 클러스터 두 개(중앙 관제와 고객사 역할), Multipass VM 두 대(온프레미스 서버 역할), S3 호환 오브젝트 스토리지 MinIO, 그리고 장애를 일부러 일으킬 수 있는 샘플 MSA 앱 OpenTelemetry Demo를 설치합니다. 이 랩은 18편까지 계속 사용하므로, 다음 편 전에 Docker가 동작하는 RAM 16GB 이상(권장 32GB)의 실습 머신을 준비해 두세요.
