Knative 운영의 특이점

일반 쿠버네티스 운영과 다른 점은 두 가지입니다. 첫째, 업그레이드 주기가 빠릅니다. 분기마다 새 버전이 나오고 각 버전의 지원 기간은 약 6개월이라, 1년만 손 놓아도 지원 범위를 벗어납니다. 둘째, 데이터 경로에 Knative 컴포넌트가 끼어 있습니다. 게이트웨이, activator, queue-proxy가 흔들리면 고객 서비스가 바로 영향을 받습니다.

설치 방식과 고가용성

항목Knative OperatorYAML 직접 적용벤더 Operator
설정 관리KnativeServing·KnativeEventing 한 장에 선언. GitOps에 적합ConfigMap과 Deployment를 직접 패치. 변경 이력이 흩어짐벤더 CR과 콘솔. 허용 범위 안에서만 변경
업그레이드spec.version 한 줄 변경새 YAML 적용 + 사후 작업 직접 실행벤더 채널 업데이트
자원·복제 조정spec.deployments, spec.high-availabilityDeployment 직접 수정 (업그레이드 때 덮임)벤더가 허용한 필드
권장 대상업스트림 운영의 기본값학습, 특수한 커스터마이징OpenShift 등 벤더 플랫폼
운영용 KnativeServing 예시
apiVersion: operator.knative.dev/v1beta1
kind: KnativeServing
metadata:
  name: knative-serving
  namespace: knative-serving
spec:
  version: "1.23"
  high-availability:
    replicas: 2                 # 컨트롤 플레인 복제 (리더 선출)
  ingress:
    kourier:
      enabled: true
  deployments:
    - name: activator           # 데이터 경로: 넉넉히
      resources:
        - container: activator
          requests: {cpu: 300m, memory: 256Mi}
          limits: {memory: 1Gi}
    - name: controller          # 서비스·Revision 수에 비례해 메모리 증가
      resources:
        - container: controller
          requests: {cpu: 100m, memory: 256Mi}
          limits: {memory: 1Gi}
  podDisruptionBudgets:
    - name: activator-pdb
      minAvailable: 1
  config:
    network:
      ingress-class: "kourier.ingress.networking.knative.dev"
      external-domain-tls: "Enabled"
      http-protocol: "Redirected"
    domain:
      "apps.customer-a.example.com": ""
    autoscaler:
      max-scale-limit: "50"
    gc:
      min-non-active-revisions: "10"
    features:
      secure-pod-defaults: "AllowRootBounded"

데이터 경로 먼저

Kourier 게이트웨이와 activator는 2개 이상, 서로 다른 노드·영역에 배치하고 PDB를 둡니다. 노드 점검이나 클러스터 오토스케일러의 축소로 동시에 내려가지 않게 합니다.

컨트롤 플레인은 리더 선출

controller와 autoscaler는 복제해도 한 번에 하나가 일합니다. 복제의 목적은 처리량이 아니라 장애 시 빠른 인계입니다.

시스템 노드 분리

knative-serving·knative-eventing·게이트웨이 Pod를 전용 시스템 노드 풀에 두면, 고객 워크로드 폭주가 Knative 자체를 흔드는 일을 막을 수 있습니다.

설정은 Git에

KnativeServing·KnativeEventing을 GitOps 저장소에서 관리하면 고객사별 설정 차이가 한눈에 보이고, 재구축도 저장소 하나로 끝납니다.

업그레이드 전략

Knative 업그레이드의 가장 중요한 규칙은 마이너 버전을 한 번에 하나씩 올리는 것입니다. 1.19에서 1.23으로 가려면 1.20, 1.21, 1.22를 차례로 거칩니다. 중간 버전에서만 수행되는 저장 형식 변환 같은 작업을 건너뛰면 문제가 생길 수 있기 때문입니다.

  1. 사전 점검

    대상 버전의 릴리스 노트에서 최소 쿠버네티스 버전, 기본값 변경, 폐기 기능을 확인합니다. 네트워킹 플러그인(net-kourier 등)과 Eventing 확장(eventing-kafka-broker 등)도 같은 버전이 나왔는지 봅니다.

  2. 스테이징에서 먼저

    운영과 같은 설정의 스테이징 클러스터에서 업그레이드하고, 대표 서비스의 배포·트래픽 분할·0개 축소·이벤트 배달을 시험합니다. 이 시험을 스크립트로 만들어 두면 분기마다 재사용됩니다.

  3. 순서대로 적용

    Serving과 Eventing 본체, 그리고 확장을 같은 마이너 버전으로 맞춥니다. Operator라면 spec.version을 한 단계 올리고 Ready를 확인한 뒤 다음 단계로 갑니다.

  4. 사후 확인

    모든 ksvc·Trigger의 Ready, 게이트웨이 응답, activator 오류율, Kafka 컨슈머 랙을 확인합니다. YAML로 설치했다면 릴리스에 포함된 사후 작업(post-install job)을 실행했는지 확인합니다.

데이터 경로가 재시작된다

업그레이드하면 activator와 게이트웨이가 롤링 재시작됩니다. 복제가 2개 이상이고 PDB가 있으면 대체로 무중단이지만, 장시간 연결(WebSocket, 스트리밍)은 끊길 수 있습니다. 또한 queue-proxy 이미지가 바뀌므로 각 서비스의 Pod도 순차적으로 교체됩니다. 고객사와 합의한 유지보수 창에 진행하세요.

업그레이드 계획기

현재 버전과 목표 버전을 고르면 거쳐야 할 단계와 각 단계에서 특히 확인할 변경을 보여 줍니다. 이 강의에서 다룬 변경만 표시하므로, 실제 계획에는 각 버전 릴리스 노트 전체를 확인하세요.

    관측성: 무엇을 볼까

    v1.19부터 Knative의 메트릭과 추적은 OpenTelemetry 기반입니다. 수집기(OpenTelemetry Collector)로 받아 Prometheus·Grafana나 사용 중인 관측성 백엔드로 보내는 구성이 일반적입니다. 메트릭 이름은 버전에 따라 바뀔 수 있으므로, 대시보드를 만들 때는 각 컴포넌트의 실제 노출 메트릭을 확인하세요. 무엇을 봐야 하는지는 계층별로 정리하면 명확합니다.

    계층핵심 신호알람 기준 예시
    게이트웨이요청 수, 5xx 비율, 지연 시간 분포5분간 5xx 비율이 기준치 초과
    activator처리 중·대기 요청, 오류, Pod 재시작대기 요청이 계속 쌓임, 재시작 발생
    autoscalerRevision별 원하는 Pod 수와 실제 Pod 수, panic 모드 여부원하는 수와 실제 수의 차이가 오래 지속 (노드·쿼터 부족 신호)
    Revision · 앱queue-proxy의 요청 지연, 동시성, 앱 오류서비스별 SLO 위반
    컨트롤 플레인controller·webhook 가용성, 재조정 지연Deployment 사용 불가 복제 > 0
    Eventing배달 실패, DLS 유입 수, Kafka 컨슈머 랙DLS 유입 발생, 랙 지속 증가
    리소스 상태Ready가 아닌 ksvc·Trigger 수Ready=False가 10분 이상
    컴포넌트 가용성 알람 (kube-state-metrics)
    groups:
  - name: knative-system
    rules:
      - alert: KnativeComponentUnavailable
        expr: |
          kube_deployment_status_replicas_unavailable{
            namespace=~"knative-serving|knative-eventing|kourier-system"

    Ready가 아닌 리소스 점검 스크립트
    #!/usr/bin/env bash
# CronJob이나 점검 도구에서 주기 실행
for kind in ksvc trigger broker; do
  kubectl get $kind -A -o json | jq -r '
    .items[] | select(
      (.status.conditions // [])
      | map(select(.type=="Ready" and .status!="True")) | length > 0
    ) | "\(.kind) \(.metadata.namespace)/\(.metadata.name)"'
done

    멀티테넌시 설계

    여러 고객사(또는 한 고객사의 여러 팀)를 한 클러스터에 담을 때의 기본 설계입니다. 시리즈 곳곳에서 나온 격리 장치를 한곳에 모았습니다.

    격리 대상장치나온 곳
    작업 공간테넌트별 네임스페이스, 네임스페이스 라벨로 소유 표시-
    권한RBAC: 자기 네임스페이스의 Knative 리소스만. knative-serving·knative-eventing 쓰기는 운영자만4편
    자원ResourceQuota·LimitRange. queue-proxy 사이드카 요청량까지 포함해 계산 (8장)3편
    확장 상한Revision별 max-scale, 클러스터 상한 max-scale-limit3편
    네트워크NetworkPolicy 기본 차단 + Knative 시스템 네임스페이스 허용, 내부 서비스는 cluster-local4편
    도메인config-domain의 라벨 셀렉터로 테넌트별 도메인, DomainMapping과 ClusterDomainClaim으로 점유 방지2편
    이벤트테넌트별 Broker, KafkaNamespaced로 데이터 플레인 분리, EventPolicy로 발신자 제한5·6편
    비용 가시성네임스페이스 단위 사용량 집계(Pod·시간, GPU·시간)로 고객사별 청구 근거8편
    테넌트별 도메인 (config-domain)
    # KnativeServing spec.config.domain 아래에 두거나 config-domain ConfigMap에
"apps.customer-a.example.com": |
  selector:
    tenant: customer-a
"apps.customer-b.example.com": |
  selector:
    tenant: customer-b
"apps.msp-default.example.com": ""        # 셀렉터 없는 기본 도메인
    클러스터를 나눌 때

    규제 요건(데이터 분리 의무), 서로 다른 Knative 버전이 필요한 고객, GPU처럼 비싼 자원을 독점해야 하는 고객은 네임스페이스 격리보다 전용 클러스터가 맞습니다. 공유 클러스터는 운영 효율이 좋고, 전용 클러스터는 격리와 일정 자율성이 좋습니다. 계약 단계에서 어느 쪽인지 분명히 하세요.

    쿼터 계산기

    Knative Pod에는 앱 컨테이너 외에 queue-proxy가 함께 뜹니다. 테넌트 ResourceQuota를 앱 요청량만으로 잡으면 피크 때 Pod가 생성되지 못하고 3편의 "원하는 Pod 수와 실제 수의 차이"가 생깁니다. 값을 넣어 필요한 쿼터를 계산해 보세요. queue-proxy 기본 요청량은 config-deployment의 설정값을 확인해 넣으세요.

    배포 중 겹침 여유가 필요한 이유

    새 Revision을 배포하면 옛 Revision이 내려가기 전에 새 Revision의 Pod가 먼저 뜹니다(4편의 카나리, 3편의 initial-scale). 그 순간에는 두 Revision의 Pod가 함께 쿼터를 씁니다. 여유가 없으면 배포가 Pending에서 멈춥니다.

    백업과 재해 복구

    원본은 Git

    ksvc, Trigger, Broker, DomainMapping, KnativeServing 설정의 원본을 GitOps 저장소에 둡니다. 클러스터는 언제든 다시 만들 수 있는 "결과물"이 됩니다. status나 webhook이 채운 값은 저장하지 않습니다.

    이미지는 다이제스트로

    재구축 시 같은 이미지를 받으려면 레지스트리 복제와 다이제스트 기록이 필요합니다. 태그만 남겨 두면 재구축 후 다른 이미지가 뜰 수 있습니다(2편).

    이벤트는 Kafka에

    Broker가 Kafka 기반이면 미배달 이벤트는 토픽에 남습니다. Kafka의 복제·미러링이 이벤트 계층의 재해 복구가 됩니다. 인메모리 Broker는 복구 대상 자체가 없습니다.

    트래픽 전환은 DNS로

    대기 클러스터에 같은 설정을 올려 두고 DNS 가중치나 상태 확인 기반 장애 조치로 넘깁니다. 0개 축소 덕분에 대기 클러스터의 평소 비용이 낮다는 점이 Knative의 숨은 장점입니다.

    클러스터에서 깨끗한 ksvc YAML 뽑기 (Git 이관용)
    kubectl get ksvc -n customer-a -o json | jq '
  .items[] | del(.status, .metadata.uid, .metadata.resourceVersion,
    .metadata.generation, .metadata.creationTimestamp, .metadata.managedFields,
    .metadata.annotations["serving.knative.dev/creator"],
    .metadata.annotations["serving.knative.dev/lastModifier"])'

    책임 분담과 운영 계약

    Knative는 플랫폼(MSP)과 앱(고객사 개발팀)의 경계가 YAML 한 장 안에 섞여 있습니다. 어노테이션 하나가 비용과 장애에 영향을 주므로, 누가 무엇을 책임지는지 계약과 문서에 분명히 적어야 합니다.

    영역MSP고객사 개발팀
    Knative 설치·업그레이드·패치책임일정 합의
    게이트웨이·activator 가용성책임 (SLA 대상)-
    클러스터 전역 설정 (config-*)책임변경 요청

    시리즈를 마치며

    1. Knative는 쿠버네티스 위의 요청 중심 계층입니다. Serving, Eventing, Functions가 각각 배포, 이벤트, 개발 경험을 맡습니다.
    2. Serving의 핵심은 불변 Revision과 Route의 분리, 그리고 queue-proxy·activator·autoscaler가 만드는 요청 기반 확장입니다.
    3. Eventing의 핵심은 CloudEvents, Broker·Trigger, 최소 한 번 배달과 DLS, 그리고 운영용 영속 Broker입니다.
    4. 적합도는 트래픽 모양, 상태, 프로토콜, 기동 시간으로 판단하고, 플랫폼마다 다른 래핑과 버전 시차를 확인합니다.
    5. 운영은 한 단계씩 업그레이드, 데이터 경로 고가용성, 계층별 관측, 쿼터와 책임 분담으로 완성됩니다.

    다음에 공부하면 좋은 것

    KServe로 모델 서빙을 깊게 파거나, OpenTelemetry로 이벤트 흐름 전체를 추적해 보세요. Gateway API 기반 네트워킹과 Knative의 RequestReply 같은 로드맵 기능이 정식화되는 흐름도 지켜볼 만합니다. 무엇보다 실제 고객사 서비스 하나를 골라 파일럿을 진행해 보는 것이 가장 좋은 다음 단계입니다.

    Knative 강의 시리즈 10편(완결). Knative v1.23을 기준으로 작성했습니다. Operator 필드, 메트릭 이름, 사후 작업 절차, queue-proxy 기본 자원값은 버전과 설치 방식에 따라 다를 수 있으니 실무에서는 공식 문서와 클러스터의 실제 값을 함께 확인하세요.
