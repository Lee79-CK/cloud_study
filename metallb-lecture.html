Chapter 01

왜 pending에 멈추는가

먼저 쿠버네티스는 로드밸런서를 만들 능력이 없다는 사실부터 받아들여야 합니다. 정확히 말하면, 쿠버네티스는 "로드밸런서를 만들어 달라"고 요청서를 작성하는 것까지만 합니다. 실제로 만드는 건 클라우드 제공자입니다.

클라우드에서 벌어지는 일

EKS에서 type: LoadBalancer 서비스를 만들면 이런 릴레이가 일어납니다.

type=LoadBalancer

온프레미스 클러스터에는 2번을 담당할 사람이 없습니다. 요청서는 잘 접수됐지만 처리할 부서가 없어서, Service는 영원히 <pending> 상태로 대기실에 앉아 있게 됩니다.

비유 — 없는 부서로 보낸 결재

사내 시스템에 "법인카드 발급"을 신청했다고 상상해 보세요. 신청서(Service)는 정상적으로 등록됐고 상태는 "처리 중"입니다. 그런데 우리 회사에는 재무팀이 없습니다. 신청서는 잘못된 게 없지만, 아무도 카드를 만들어 주지 않습니다. MetalLB는 이 회사에 재무팀을 새로 만들어 넣는 일입니다.

MetalLB의 정의

MetalLB는 베어메탈(온프레미스) 쿠버네티스 클러스터를 위한 로드밸런서 구현체입니다. 하는 일은 딱 두 가지로 요약됩니다.

역할 1 — 주소 할당

IP를 나눠준다

관리자가 미리 등록해 둔 IP 주소 풀에서 하나를 꺼내 Service의 EXTERNAL-IP로 기록합니다. <pending>이 풀리는 순간이 바로 이 단계입니다.

역할 2 — 주소 광고

그 IP가 여기 있다고 알린다

IP를 적어두기만 하면 아무 의미가 없습니다. 사내 네트워크 장비들에게 "이 IP로 오는 트래픽은 이 노드로 보내라"고 알려줘야 합니다. ARP 또는 BGP를 씁니다.

가장 흔한 오해

MetalLB는 트래픽을 직접 분산하지 않습니다. nginx나 HAProxy처럼 패킷을 받아 여러 백엔드로 뿌리는 프록시가 아닙니다. MetalLB는 "이 IP의 위치"만 알려주고 빠지며, 실제 Pod 단위 분산은 그 뒤에서 kube-proxy(iptables/IPVS)나 eBPF가 담당합니다. MetalLB = 주소 관리자 + 광고판이라고 기억하세요.

Chapter 02

Service 타입 다시 보기

MetalLB를 이해하려면 Service 타입들이 서로 대체 관계가 아니라 겹겹이 쌓이는 관계라는 점을 알아야 합니다. LoadBalancer 타입은 NodePort를 포함하고, NodePort는 ClusterIP를 포함합니다.

타입접근 가능 범위주소 형태한계
ClusterIP 클러스터 내부만 10.96.0.0/12 가상 IP 외부에서 접근 불가
NodePort 모든 노드의 특정 포트 노드IP:31820 포트 번호가 30000~32767로 못생김. 노드 IP를 외부에 노출. 노드 죽으면 그 주소도 죽음
LoadBalancer 전용 외부 IP 192.168.1.240:80 구현체(클라우드 또는 MetalLB)가 있어야 동작
Ingress HTTP/HTTPS 경로 기반 도메인 + 경로 L7 전용. 자기 자신도 외부 노출 수단이 필요

"NodePort로 버티면 안 되나요?"

초보 단계에서 가장 자연스러운 질문입니다. 실제로 소규모 테스트 환경은 NodePort로 굴러갑니다. 문제는 서비스 개수가 늘어날 때 생깁니다.

  • 주소가 서비스마다 다른 포트로 흩어집니다. 서비스 A는 :31820, B는 :30455 — 문서화 지옥이 열립니다.
  • 노드 IP에 종속됩니다. 노드를 교체하면 접속 주소가 바뀌고, 앞단에 별도 L4 장비를 세워 주소를 고정해야 합니다.
  • 80/443을 쓸 수 없습니다. 브라우저 사용자에게 포트 번호를 안내해야 합니다.
  • DNS를 붙이기 어렵습니다. A 레코드는 포트를 담지 못합니다.

MetalLB는 이 모든 문제를 "서비스마다 표준 포트를 쓰는 고유 IP를 하나씩"이라는 방식으로 해결합니다.

Ingress와의 관계 — 자주 헷갈리는 부분

Ingress Controller(예: ingress-nginx)도 결국 클러스터 안에서 도는 Pod입니다. 그 Pod가 외부에서 트래픽을 받으려면 자기 자신부터 외부 노출이 필요합니다. 그래서 실무 구성은 대부분 "MetalLB가 Ingress Controller에게 IP 1개를 주고, 그 뒤로 수십 개 도메인을 Ingress가 분기"하는 형태입니다. 둘은 경쟁 관계가 아니라 아래위로 붙는 조합입니다. 

# LoadBalancer IP는 딱 1~2개만 쓰고, 그 뒤는 Ingress가 도메인으로 분기
Internet / 사내망
      │
      ▼
192.168.1.240  ← MetalLB가 할당한 IP (ingress-nginx Service)
      │
   ┌──┴──────────────┬──────────────────┐
   ▼                 ▼                  ▼
shop.corp.local   api.corp.local    admin.corp.local
   │                 │                  │
 shop-svc          api-svc           admin-svc   (모두 ClusterIP)
IP 절약 + 인증서 통합 관리 + L7 라우팅. HTTP 워크로드의 기본형입니다.
# 서비스 30개 = IP 30개. 사내 IP 예산이 먼저 고갈됩니다.
192.168.1.240 → shop-svc
192.168.1.241 → api-svc
192.168.1.242 → admin-svc
192.168.1.243 → ...

# 단, 아래 경우는 이 방식이 "맞습니다":
#  - TCP/UDP 서비스 (MySQL 3306, Redis 6379, DNS 53, syslog 514)
#  - 클라이언트 IP를 그대로 봐야 하는 서비스
#  - HTTP가 아닌 프로토콜 전반 (gRPC 스트리밍, MQTT 등)
L4 서비스에는 오히려 이 방식이 정답입니다. Ingress는 HTTP만 다루기 때문입니다.
Chapter 03

MetalLB 구성요소

MetalLB는 놀랄 만큼 단순합니다. Pod 두 종류와 CRD 몇 개가 전부입니다. 이 구조를 외워두면 나중에 장애가 났을 때 어디를 봐야 하는지 바로 알 수 있습니다.

동작하는 두 개의 Pod

Deployment · 클러스터에 1개

controller

IP 할당 담당. LoadBalancer 타입 Service가 생기는지 감시하다가, IPAddressPool에서 IP를 하나 골라 status.loadBalancer.ingress에 기록합니다. 네트워크에 직접 관여하지 않으므로 어느 노드에 떠 있어도 무관합니다.

DaemonSet · 모든 노드에 1개씩

speaker

IP 광고 담당. 호스트 네트워크를 직접 쓰며(hostNetwork: true) ARP 응답을 보내거나 BGP 세션을 맺습니다. 실제 트래픽이 들어오는 통로를 만드는 쪽이라 장애 조사는 거의 항상 여기서 시작합니다.

기억법

controller = 명부에 이름 적는 사람 (사무직, 한 명이면 충분) · speaker = 확성기 든 사람 (현장직, 노드마다 한 명씩 필요)

설정은 전부 CRD로

과거 버전(0.12 이하)은 ConfigMap에 설정을 몰아넣었지만, 0.13부터는 CRD 방식으로 바뀌었습니다. 오래된 블로그를 따라 하다 "적용했는데 아무 반응이 없다"면 대개 이 차이 때문입니다.

CRD역할필수 여부
IPAddressPool나눠줄 IP 대역 정의필수
L2Advertisement해당 풀을 ARP/NDP로 광고L2 모드에서 필수
BGPPeer피어링할 라우터 정보BGP 모드에서 필수
BGPAdvertisement해당 풀을 BGP로 광고 (+ 커뮤니티·경로속성)BGP 모드에서 필수
BFDProfile장애 감지 시간 단축 (BGP 보조)선택
CommunityBGP 커뮤니티 값 별칭 정의선택
가장 흔한 초기 실수

IPAddressPool만 만들고 끝내는 경우입니다. 이러면 EXTERNAL-IP는 붙지만 ping도 안 되고 접속도 안 됩니다. IP를 "장부에 적기"만 하고 "광고"를 안 했기 때문입니다. L2Advertisement(또는 BGPAdvertisement)를 반드시 함께 만들어야 합니다.

IP가 붙는 전체 과정

1. 사용자         : type=LoadBalancer Service 생성
2. controller     : "미할당 LB 서비스 발견"
3. controller     : IPAddressPool에서 사용 가능한 IP 탐색
                    (이미 쓰는 IP·예약 IP 제외, sharing key 검사)
4. controller     : svc.status.loadBalancer.ingress = 192.168.1.240 기록
                    → kubectl get svc 에서 <pending> 이 사라지는 시점
5. speaker(전 노드): "우리가 광고할 IP가 생겼다" 인지
6. speaker        : memberlist로 리더 1대를 선출 (L2 모드)
7. 리더 speaker    : ARP로 "192.168.1.240 = 내 MAC" 이라고 응답 시작
8. 스위치         : MAC 테이블 갱신 → 트래픽이 리더 노드로 유입
9. kube-proxy     : NodePort/iptables 규칙에 따라 실제 Pod로 DNAT
4번까지가 controller의 일, 5번부터가 speaker의 일입니다. 증상별로 어느 Pod 로그를 볼지 판단하는 기준이 됩니다.

# 누가 리더인지 (L2 모드) — 이벤트에 nodeAssigned 로 남습니다
kubectl describe svc web | grep -i -A2 announc

# 할당 실패 원인 추적
kubectl -n metallb-system logs deploy/controller | tail -30

Chapter 04

Layer 2 모드 원리

Layer 2 모드는 추가 장비도, 네트워크팀 협조도 필요 없는 방식입니다. 그래서 90% 이상의 첫 도입이 이 모드로 시작합니다. 원리는 ARP 하나로 설명됩니다.

먼저 ARP를 정확히 이해하기

같은 네트워크(브로드캐스트 도메인) 안에서 통신하려면, IP 주소만으로는 부족하고 MAC 주소를 알아야 합니다. ARP는 그 MAC을 물어보는 프로토콜입니다.

비유 — 사무실에서 사람 찾기

사무실 한가운데서 "192.168.1.240 계신 분 손 들어주세요!"라고 외치는 게 ARP 요청(브로드캐스트)입니다. 해당하는 사람이 "저요, 제 자리는 저기입니다"라고 답하는 게 ARP 응답입니다. 이후 모두가 그 자리를 기억(ARP 캐시)해 두고 직접 찾아갑니다.

MetalLB의 Layer 2 모드는 이 상황에서 실제로는 그 IP를 가진 사람이 없는데, 노드 한 대가 대신 손을 들어주는 것입니다. 이것이 전부입니다.

핵심: 리더는 오직 한 대

두 노드가 동시에 손을 들면 스위치의 MAC 테이블이 계속 흔들려서(MAC flapping) 통신이 깨집니다. 그래서 MetalLB speaker들은 memberlist 기반 가십 프로토콜로 IP별 리더 1대를 선출하고, 그 리더만 ARP에 응답합니다.

이 사실에서 Layer 2 모드의 성질이 그대로 유도됩니다.

결과 1

진짜 분산은 아니다

모든 인바운드 트래픽이 리더 노드 한 대의 NIC를 통과합니다. 대역폭 상한 = 노드 1대의 NIC 성능.

결과 2

고가용성은 된다

리더가 죽으면 남은 speaker가 새 리더를 뽑고 즉시 ARP를 다시 광고합니다. 보통 수 초 내 복구.

결과 3

같은 L2망이어야 한다

ARP는 라우터를 넘지 못합니다. 노드와 클라이언트(또는 게이트웨이)가 같은 서브넷에 있어야 합니다.

면접에도 나오는 포인트

"MetalLB Layer 2 모드는 로드밸런싱을 하나요?" → 인바운드 진입점은 단일 노드이므로 노드 간 부하분산은 하지 않습니다. 다만 그 노드에 도착한 뒤 kube-proxy가 여러 Pod로 분산하므로, Pod 레벨 분산은 되고 노드 레벨 분산은 안 된다가 정확한 답입니다. 서비스가 여러 개면 IP별로 리더가 다르게 뽑히므로 서비스 단위로는 자연스럽게 흩어집니다.

직접 눌러보는 패킷 추적

아래 시뮬레이터는 클라이언트가 curl http://192.168.1.240을 실행했을 때 패킷이 지나가는 길을 그대로 재현합니다. 모드를 바꿔 두 방식을 비교해 보고, 리더 노드에 장애를 내서 복구 과정도 확인해 보세요.

L2 모드에서 여러 번 요청을 보내도 언제나 같은 노드(리더)로만 들어갑니다. 반면 BGP 모드로 바꾸면 요청마다 서로 다른 노드로 분산됩니다. 이 한 가지 차이가 두 모드를 가르는 본질입니다.

Layer 2 모드 설정 예시

apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: prod-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.1.240-192.168.1.250   # 범위 표기
  - 192.168.1.128/28              # CIDR 표기도 가능
  autoAssign: true      # false면 명시적으로 요청한 서비스만 사용
  avoidBuggyIPs: true   # .0 과 .255 를 건너뜀 (구형 장비 호환)
이 대역은 반드시 DHCP 범위 밖이어야 하며, 다른 장비가 쓰지 않는 IP여야 합니다.
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: prod-l2
  namespace: metallb-system

  ipAddressPools:

Chapter 05

BGP 모드 원리

Layer 2 모드의 두 가지 한계 — 단일 노드 병목과 같은 서브넷 제약 — 을 해결하는 것이 BGP 모드입니다. 대신 네트워크 장비에 설정을 넣어야 하므로 네트워크팀과의 협의가 필수입니다.

BGP를 30초로 이해하기

BGP(Border Gateway Protocol)는 라우터끼리 "내가 이 IP 대역으로 가는 길을 알고 있다"고 알려주는 프로토콜입니다. 인터넷 전체가 이걸로 굴러갑니다.

비유 — 길 안내판 등록

ARP가 "사무실에서 손 들기"였다면, BGP는 지역 도로공사에 "우리 건물로 가는 길은 이쪽입니다"라는 안내판을 정식 등록하는 일입니다. 등록된 안내판은 다른 지역에서도 보이기 때문에 같은 사무실(서브넷)에 있지 않아도 찾아올 수 있습니다.

게다가 같은 목적지로 가는 길을 3개 등록할 수도 있습니다. 그러면 도로공사는 차량을 세 길로 나눠 보냅니다. 이게 ECMP(Equal-Cost Multi-Path)이고, BGP 모드가 진짜 부하분산이 되는 이유입니다.

동작 흐름

01각 노드의 speaker가
라우터와 BGP 세션 수립
→
02"192.168.1.240/32는
나(노드IP)를 통해 갈 수 있다" 광고
→
03라우터는 동일 비용 경로
N개를 라우팅 테이블에 등록
→
04플로우 해시로
노드별 트래픽 분산

위 04장 시뮬레이터에서 BGP 모드를 누르고 요청을 여러 번 보내보면 노드가 매번 바뀌는 것을 눈으로 확인할 수 있습니다.

설정 예시

  peerPort: 179

  password: "bgp-secret"  # MD5 인증 (Secret 참조 방식 권장)
  nodeSelectors:            # 이 피어와 세션 맺을 노드 한정
  - matchLabels:
      rack: "rack-a"

경로 개수와 실제 분산 여부를 따로 확인하는 습관이 중요합니다.

BGP 모드의 숨은 함정: 플로우 재해싱

ECMP는 보통 (출발IP, 출발포트, 목적IP, 목적포트, 프로토콜) 5-튜플을 해시해서 경로를 고릅니다. 문제는 노드가 추가·제거되면 해시 대상 경로 수가 바뀌어 기존 연결까지 다른 노드로 재배치된다는 점입니다.

  • 진행 중이던 TCP 세션이 자기를 모르는 노드로 도착 → 연결 끊김(RST)
  • 단순 HTTP API는 재시도로 넘어가지만, WebSocket·gRPC 스트림·긴 파일 업로드는 체감 장애가 됩니다

완화 방법:

  • 라우터가 지원하면 Resilient ECMP / consistent hashing 활성화
  • 노드 증감을 잦게 하지 않기 (스케일 인/아웃을 트래픽 한가한 시간대로)
  • 클라이언트 측 재시도·재연결 로직을 전제로 설계
  • 세션 유지가 결정적으로 중요하면 오히려 L2 모드 + 애플리케이션 레벨 세션 관리를 고려

처음부터 BGP를 고집하지 마세요. L2 모드로 시작해 서비스 노출 흐름을 안정화하고, 대역폭이나 랙 분리가 실제 병목이 됐을 때 BGP로 전환하는 것이 일반적입니다. MetalLB는 같은 IPAddressPool을 유지한 채 Advertisement 리소스만 교체하면 되므로 전환 비용이 크지 않습니다.

Chapter 06

설치와 필수 설정

0단계 — IP 대역 확보가 먼저입니다

기술적으로는 kubectl apply 한 번이면 끝이지만, 실무에서 가장 오래 걸리는 건 IP 대역을 받아오는 일입니다. 네트워크 담당자에게 이렇게 요청하세요.

요청 템플릿

"쿠버네티스 서비스 노출용으로 노드와 동일한 서브넷에서 DHCP 할당 범위 밖의 연속된 IP N개를 예약해 주세요. 해당 IP는 특정 서버에 고정되지 않고 노드 간에 이동합니다(gratuitous ARP 발생). 스위치에서 port security / DHCP snooping / dynamic ARP inspection이 걸려 있으면 예외 처리가 필요합니다."

  • 노드와 같은 서브넷이어야 합니다 (L2 모드). 다른 서브넷 IP를 넣으면 IP는 붙지만 통신이 안 됩니다.
  • DHCP 범위와 겹치면 언젠가 IP 충돌로 간헐적 장애가 납니다. 가장 찾기 어려운 유형입니다.
  • 필요 개수 산정: (Ingress Controller 1~2개) + (L4로 노출할 서비스 수) + 여유 30%

      Local + L2 모드의 함정
      

        L2 모드에서 externalTrafficPolicy: Local을 쓰면 MetalLB는
        해당 서비스의 Pod가 실제로 떠 있는 노드 중에서만 리더를 뽑습니다.
        그래서 정상 동작합니다. 하지만 Pod가 특정 노드 1대에만 있으면 사실상 그 노드에 고정되고,
        그 Pod가 죽는 순간 리더도 이동해야 하므로 순간 단절이 생깁니다.
        Local 정책을 쓸 때는 topologySpreadConstraints나 DaemonSet으로
        Pod를 여러 노드에 고르게 배치하는 것이 함께 가야 합니다.
      

    


    
패턴 4 — Ingress Controller 앞에 붙이기

    

      

        
      

      

        

# helm install ingress-nginx ingress-nginx/ingress-nginx -f values.yaml
controller:
  kind: DaemonSet              # 모든 노드에 배치 → Local 정책과 궁합이 좋음
  service:
    type: LoadBalancer
    externalTrafficPolicy: Local
    annotations:
      metallb.io/loadBalancerIPs: "192.168.1.240"
  config:
    use-forwarded-headers: "true"
    compute-full-forwarded-for: "true"

        
이 조합이면 애플리케이션은 X-Forwarded-For로 실제 클라이언트 IP를 받습니다.

먼저 계층을 나눠서 보기

    

      

        
계층하는 일대표 도구

        
          

            주소 확보 · 광고
L2/L3		
            외부 IP를 만들고 "여기로 오라"고 알림
            MetalLB, kube-vip, Cilium LB IPAM, 클라우드 CCM
          

          

            패킷 분산
L4		
            도착한 패킷을 여러 Pod로 나눔
            kube-proxy(iptables/IPVS), Cilium eBPF, NLB

L7		
            도메인·경로·헤더로 분기, TLS 종료

      이 표에서 얻어야 할 결론
      

        MetalLB는 nginx의 경쟁자가 아니라 nginx의 전제조건입니다.
        온프레미스에서 ingress-nginx를 쓰려면 그 앞에 IP를 붙여줄 무언가가 필요하고,
        그 자리가 MetalLB의 자리입니다. 두 개를 "둘 중 하나 고르기"로 접근하면 계속 헷갈립니다.

도구계층동작 방식강점약점 · 주의

        
        
          

            MetalLB
            L2/L3
            IP 풀 할당 + ARP 또는 BGP 광고
            설치 간단, 표준 Service API 그대로, 벤더 중립, 사실상 온프렘 표준
            L2 모드는 단일 노드 병목. L7 기능 없음. IP 대역 사전 확보 필요
          

          

            kube-vip
            L2/L3
            VIP 관리 (ARP/BGP) + 컨트롤플레인 HA
            API 서버 VIP까지 한 번에 해결. 설치형 클러스터 부트스트랩에 유리
            서비스 LB 기능은 MetalLB보다 얇음. 문서·사례 상대적으로 적음
          

          

            HAProxy / Nginx + Keepalived
클러스터 외부 VM		
            L4/L7
            외부 장비가 NodePort로 프록시, VRRP로 VIP 이중화
            쿠버네티스에 아무것도 설치 안 함. 네트워크팀에게 익숙한 구조
            서비스 추가마다 수동 설정. 자동화 부재. 관리 대상 VM 증가
          

          

            NodePort 단독
            L4
            모든 노드의 고포트 개방
            추가 설치 없음. 테스트에 즉시 사용 가능
            포트 파편화, 노드 IP 노출, 80/443 불가, DNS 연동 어려움
          

          

            Cilium
LB IPAM + BGP Control Plane		
            L2/L3/L4
            CNI가 IP 할당·광고·분산을 eBPF로 통합 처리
            kube-proxy 대체 가능, 고성능, 구성요소 단일화, 관측성 우수
            Cilium을 CNI로 써야 함. eBPF·커널 버전 요건. 학습 곡선
          

          

            Calico BGP
            L3
            Service IP 대역을 CNI가 직접 BGP 광고
            이미 Calico + BGP 환경이면 추가 설치 불필요
            IP 풀 관리·공유 IP 등 LB 편의 기능은 MetalLB보다 부족
          

          

            OpenELB
            L2/L3
            MetalLB와 유사 (ARP/BGP/VIP 모드)
            중국 내 생태계·KubeSphere 연동
            커뮤니티 규모와 자료가 MetalLB보다 작음
          

          

            F5 BIG-IP + CIS
            L4/L7
            전용 하드웨어 ADC를 컨트롤러가 자동 설정
            기업용 기능 총집합(WAF, SSL 오프로드, 정교한 헬스체크), 벤더 지원
            고비용. 장비 종속. 팀 내 전문 인력 필요
          

          

            AWS NLB / ELB
            L4
            CCM이 클라우드 API로 LB 프로비저닝
            완전 관리형, 무한 확장, 사용량 과금
            클라우드 전용. 온프렘에서 사용 불가. 트래픽 비용 발생
          

          

            AWS ALB / GCP HTTP(S) LB
            L7
            Ingress/Gateway 리소스를 클라우드 LB로 변환
            관리형 L7 + WAF·인증 연동
            클라우드 전용. 어노테이션 방언이 많음
          

          

            ingress-nginx / Traefik
            L7
            클러스터 내 프록시 Pod가 HTTP 라우팅
            도메인·경로 분기, TLS 종료, IP 절약
            자기 자신이 외부 IP를 필요로 함 → 온프렘에서는 MetalLB와 함께 사용
          

          

            Gateway API + Envoy
            L7
            차세대 표준 라우팅 API 구현체
            역할 분리 명확, 표현력 높음, Ingress의 후계 표준
            여전히 하부에 L4 노출 수단 필요. 생태계 성숙 중
          

        
      

    


    
MetalLB vs 클라우드 LB — 사고방식의 차이

    

      

        클라우드 LB
        
"주문하면 나온다"

        

          LB 인스턴스 자체가 클러스터 밖에 별도로 생성됩니다. 헬스체크, TLS, 로깅, 오토스케일이
          모두 관리형입니다. 대신 과금되고, 생성에 수십 초~수 분이 걸립니다.
        

      

      

        MetalLB
        
"주소만 빌려준다"

        

          별도 LB 인스턴스가 없습니다. 노드 자신이 그 IP의 주인 행세를 합니다.
          즉시 할당되고 비용이 0이지만, 헬스체크·TLS·L7은
          쿠버네티스 쪽(Probe, Ingress)에서 직접 챙겨야 합니다.
        

      

    


    
그래서 무엇을 선택할까

    

      

        Case 1
        
온프렘 · 학습/개발/스테이징

        
MetalLB L2 모드 + ingress-nginx. 30분 안에 끝나고 유지보수도 거의 없습니다.

      

      

        Case 2
        
온프렘 · 운영, 트래픽 큼, 멀티랙

        
MetalLB BGP 모드 또는 Cilium BGP. 네트워크팀 협업이 전제입니다.

      

      

        Case 3
        
이미 Cilium을 CNI로 쓰는 중

        
Cilium LB IPAM + BGP Control Plane을 먼저 검토하세요. 구성요소를 줄일 수 있습니다.

      

      

        Case 4
        
WAF·컴플라이언스·벤더 지원 필수

        
F5 등 상용 ADC + CIS. 금융·공공에서 흔한 선택입니다.

      

      

        Case 5
        
컨트롤플레인 VIP도 함께 필요

        
kube-vip(API VIP) + MetalLB(서비스 LB) 병행이 흔한 조합입니다.

      

      

        Case 6
        
클러스터에 아무것도 못 넣는 정책

        
외부 HAProxy + Keepalived. 대신 서비스 추가 자동화를 별도로 마련하세요.

            수 초~수십 초가 걸릴 수 있습니다. 스위치의 ARP aging time을 줄이면 개선됩니다

      08퍼블릭 클라우드 VM에서 동작하지 않음
      

        

          EC2·GCE 같은 환경에서는 클라우드 네트워크가 등록되지 않은 IP의 ARP 응답을 차단합니다
          (source/destination check, anti-spoofing). MetalLB L2 모드는 원칙적으로 동작하지 않습니다.
        

        

          클라우드 위에서 굳이 자체 클러스터를 굴려야 한다면 클라우드 LB를 쓰거나,
          BGP를 지원하는 별도 오버레이 구성을 검토해야 합니다.
          MetalLB는 "내가 L2 네트워크를 통제할 수 있는 환경"이 전제입니다.

    정리
    

      MetalLB의 전부는 두 문장입니다. 첫째, IP 풀에서 주소를 꺼내 Service에 적어준다.
      둘째, 그 주소가 어느 노드에 있는지 ARP 또는 BGP로 알린다.
      나머지 모든 개념 — 리더 선출, ECMP, strictARP, externalTrafficPolicy — 는
      이 두 문장에서 파생되는 세부사항입니다.
    

    

      다음 학습으로는 Ingress Controller / Gateway API(L7 라우팅),
      Cilium BGP Control Plane(CNI 통합 방식),
      kube-proxy IPVS와 eBPF 데이터플레인을 이어서 보면
      온프레미스 쿠버네티스 네트워킹의 전체 그림이 완성됩니다.
