압축 방식 고르기

위 표에서 브로틀리(br)가 JS에서는 gzip보다 오히려 컸습니다. compression 1.8.2 소스를 보면 실시간 압축의 브로틀리 품질 기본값이 4(최대 11)입니다. 요청마다 압축하므로 CPU를 아끼려는 설정입니다.

대상권장이유
동적 HTML 조각실시간 gzip(또는 낮은 품질 br)요청마다 내용이 달라 미리 압축할 수 없음. 낮은 품질에서는 gzip과 br 차이가 작음(측정)
정적 JS·CSS빌드할 때 최고 품질 br·gzip 파일을 만들어 두고 그대로 전송한 번만 압축하므로 최고 품질을 써도 됨. 20편 배포 파이프라인에서
1KB 미만 응답압축 안 함 (Express threshold)압축 머리말과 CPU가 이득보다 큼
SSE·스트리밍압축 안 함4절

FastAPI는 1KB 미만 요약 조각(298B)까지 압축했습니다. Starlette GZipMiddleware는 첫 본문 조각이 끝 조각일 때만 크기 기준을 적용하는데, 랩의 통합 미들웨어(@app.middleware("http"))를 거치면 본문이 스트리밍 조각으로 전달되어 기준이 적용되지 않았습니다. 작은 응답의 압축은 손해가 작으므로 그대로 두었습니다.

04

SSE와 압축의 충돌

압축기는 효율을 위해 데이터를 모았다가 내보냅니다. 한 번 열어 두고 조금씩 흘려보내는 SSE와는 정반대 성질입니다.

Express 설정/events 응답 머리측정
SSE 압축 (COMPRESS_SSE=on, 실습용)Content-Encoding: gzip재시작 이벤트·첫 요약·15초 ping이 있었는데도 18초 동안 받은 바이트 10 (gzip 머리말뿐). 조회 전용 사용자 화면은 재시작 3번 모두 5초 안에 갱신 안 됨
SSE 제외 (기본)압축 없음상대 화면 갱신까지 30~90ms (클릭 포함)
FastAPI (Starlette 기본 제외)압축 없음44~71ms
apps/server/src/app.js (압축 미들웨어)
app.use(compression({
  threshold: 1024,
  filter: (req, res) => {
    if (process.env.COMPRESS_SSE !== 'on' && String(res.getHeader('Content-Type') ?? '').startsWith('text/event-stream')) return false;
    return compression.filter(req, res);
  },
}));

compression은 res.flush()를 제공하므로 SSE 프레임마다 flush하는 방법도 있지만, 메시지가 작아 압축 이득이 거의 없고 빼먹기 쉬워 제외가 낫습니다. Starlette 1.10.0의 GZipMiddleware는 소스의 DEFAULT_EXCLUDED_CONTENT_TYPES에 text/event-stream이 들어 있어 기본으로 제외합니다. 리버스 프록시(Nginx 등)에서 압축하는 경우도 같은 주의가 필요하며, 10편에서 X-Accel-Buffering: no를 보낸 것도 같은 맥락입니다.

정적 파일 캐시 정책

같은 페이지에 두 번째로 들어갈 때 정적 파일(htmx, 확장, 공유 런타임, 아일랜드 번들, CSS) 17개가 어떻게 처리되는지 측정했습니다.

설정정적 파일 응답 헤더재방문 시 17개문제
Express 17편까지 (maxAge: 0)public, max-age=0 + ETag304 재검증 17건 (네트워크 왕복 17번)지연이 큰 망에서 느림 (재방문 차트 준비 1,996ms)
FastAPI 17편까지 (지정 없음)ETag·Last-Modified만17건 모두 요청 없이 캐시 (추정 신선도)빠르지만, 배포 후에도 옛 파일을 쓸 수 있음 (언제까지인지 브라우저 마음)
18편 두 서버해시 파일명: public, max-age=31536000, immutable / 나머지: no-cache304 15건 + 캐시 2건해시가 없는 15개는 20편에서 해시 파일명으로 바꾸면 요청 0

Cache-Control이 없으면 브라우저는 Last-Modified로부터 "얼마나 오래 신선하다고 볼지"를 스스로 추정합니다(휴리스틱 캐시). FastAPI 쪽이 재방문에서 더 빨랐던 이유이지만, 배포 직후 htmx나 아일랜드 번들을 바꿨는데 일부 사용자가 옛 파일을 계속 쓰는 사고로 이어집니다. 그래서 정책을 명시했습니다.

apps/server/src/app.js (정적 파일)
const HASHED = /\/(shared\/chunks|console\/assets)\//;
app.use(express.static(join(here, '..', 'public'), {
  index: false,
  setHeaders(res, path) {
    res.setHeader('Cache-Control', HASHED.test(path.replaceAll('\\', '/')) ? 'public, max-age=31536000, immutable' : 'no-cache');
  },
}));

이름에 내용 해시가 있는 파일(Vite가 만든 chunks/react-BbggMMhK.js, 콘솔의 assets/index-*.js)은 내용이 바뀌면 이름도 바뀌므로 영원히 캐시해도 안전합니다. 이름이 고정된 파일은 매번 ETag로 확인(no-cache는 "저장하지 말라"가 아니라 "쓰기 전에 확인하라")합니다.

06

htmx 응답과 브라우저 캐시

10편의 hx-ptag는 "바뀐 게 없으면 304, 스왑하지 않음"이었습니다. 이번 측정에서 Express에서만, 한 번 바뀐 뒤부터 304가 사라지는 현상이 나왔습니다.

활동 기록이 한 번 바뀐 뒤 30초 (폴링 3번)CDP가 본 상태htmx가 본 상태섹션 요소 교체
FastAPI304, 304, 304304, 304, 3040번
Express (수정 전)200, 200, 200200, 200, 2003번 (같은 내용을 다시 스왑)
Express (수정 후)304, 304, 304304, 304, 3040번

원인은 세 가지가 겹친 것입니다. ① Express는 200 응답에 자동으로 약한 ETag를 붙입니다. ② 브라우저는 그 응답을 HTTP 캐시에 저장하고, 다음 fetch에 If-None-Match를 스스로 붙입니다(페이지 스크립트와 CDP의 요청 머리에는 보이지 않음). ③ 서버가 hx-ptag 판단으로 304를 보내면 브라우저는 이를 "캐시 재검증 성공"으로 받아 저장해 둔 200을 fetch에 돌려줍니다. 결국 htmx는 200을 받아 같은 HTML을 매번 다시 스왑했습니다. FastAPI는 동적 응답에 ETag를 붙이지 않아 생기지 않았습니다.

apps/server/src/app.js (htmx 요청 판별 미들웨어 안)
// 18편: htmx 응답은 브라우저 HTTP 캐시에 저장하지 않는다
if (req.htmx) res.set('Cache-Control', 'no-store');

htmx 조각은 대부분 개인화되어 있고(사용자·권한별), 같은 URL이 전체·부분 두 응답을 내므로(2편 Vary) 브라우저 캐시로 얻는 이득이 거의 없습니다. 두 서버 모두 htmx 응답의 기본값을 no-store로 두고, 캐시할 이유가 있는 라우트만 직접 덮어쓰게 했습니다. 10편 preload는 브라우저 HTTP 캐시가 아니라 확장 메모리에 응답을 들고 있으므로 영향이 없습니다(회귀 테스트 통과).

측정은 Express(FastAPI도 같은 경향: 첫 방문 FCP 948ms / 1,476ms)이며, LCP 요소가 두 화면 모두 첫 글자 블록이라 FCP와 LCP가 같게 나왔습니다. 해석은 이렇습니다.

  • 첫 콘텐츠: htmx 포털은 서버가 완성된 HTML을 보내므로 JS를 기다리지 않고 그립니다. SPA는 JS를 받아 실행한 뒤에야 그리므로 약 600ms 늦었습니다.
  • 전체 JS 양: 이 화면에는 React 차트 아일랜드가 있어 htmx 포털도 공유 React 런타임(15편)을 받습니다. 그래서 JS 전송량이 SPA와 비슷합니다. 게다가 랩은 11편부터 아일랜드 번들을 레이아웃에서 모든 페이지에 싣기 때문에, 아일랜드가 없는 화면도 같은 JS를 받습니다. 아일랜드가 있는 페이지에서만 번들을 싣도록 나누면 그런 화면의 JS는 htmx와 확장(gzip 약 30KB)으로 줄어듭니다(20편에서 페이지별 번들 목록과 함께).
  • 화면 전환: 다른 VM으로 이동은 두 쪽 모두 서버 왕복 한 번(htmx: 상세 조각, SPA: 라우트 전환 후 htmx 영역의 조각)이라 차이가 없습니다.
  • CLS: SPA는 JS가 내용을 채우며 약간 밀렸고(0.007), htmx 포털은 서버 HTML 그대로라 0이었습니다. 둘 다 좋은 기준(0.1 이하) 안입니다.
  • 클릭 이벤트 지연: Event Timing으로 잰 클릭 처리 시간(INP의 재료)은 둘 다 32~64ms로 기준(200ms) 안입니다. 네트워크 왕복은 INP에 들어가지 않습니다.
측정 방법

Playwright로 Chrome 153을 띄우고 CDP Network.emulateNetworkConditions(지연 150ms, 내려받기 200KB/s)와 Emulation.setCPUThrottlingRate(4배)를 걸었습니다. LCP·CLS·Event Timing은 페이지에 미리 심은 PerformanceObserver로, "차트까지"는 섀도 DOM 안 차트 선이 나타날 때까지, 전송량은 CDP loadingFinished의 합으로 쟀습니다. 실제 사용자 지표(RUM)는 20편에서 다룹니다.
