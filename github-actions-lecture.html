SECTION 01

CI/CD는 왜 필요한가

GitHub Actions 문법을 외우기 전에, 이 도구가 대신해 주는 "사람의 반복 노동"이 무엇인지부터 짚습니다.

수동 배포 시대의 하루

자동화가 없던 팀의 배포는 대략 이런 모습입니다. 개발자가 코드를 다 짜면 슬랙에 "머지 부탁드립니다"를 남기고, 누군가 로컬에서 git pull 후 테스트를 돌립니다. 통과하면 npm run build, 결과물을 압축해서 서버에 scp로 올리고, SSH로 접속해 서비스를 재시작합니다.

이 과정에는 세 가지 구조적 문제가 있습니다.

재현 불가능

"제 노트북에서는 되는데요"의 근원. 사람마다 Node 버전, 환경변수, 설치된 패키지가 다릅니다.

느린 피드백

버그를 넣은 커밋과 그것을 발견하는 시점 사이가 며칠씩 벌어집니다. 늦게 발견할수록 고치는 비용이 커집니다.

지식의 사유화

배포 절차가 특정 선임의 머릿속에만 있습니다. 그 사람이 휴가를 가면 배포가 멈춥니다.

CI와 CD, 정확히 무엇이 다른가

CI (지속적 통합)

모든 커밋마다 자동으로 빌드 + 테스트를 돌려 "지금 main 브랜치는 정상"이라는 사실을 늘 보장합니다. 결과물은 "합격/불합격" 신호입니다.

CD (지속적 배포/전달)

CI를 통과한 산출물을 자동으로 배포합니다. 사람의 승인 버튼을 거치면 Delivery, 승인 없이 끝까지 가면 Deployment입니다.

💡 면접 단골 질문

"Continuous Delivery와 Continuous Deployment의 차이는?" → 프로덕션 반영 직전에 사람의 수동 승인(manual approval)이 있으면 Delivery, 파이프라인이 승인 없이 프로덕션까지 자동으로 밀어넣으면 Deployment입니다. GitHub Actions에서는 environment의 required reviewers 설정으로 이 둘을 구분합니다(섹션 10에서 다룹니다).

SECTION 02

GitHub Actions 한눈에 보기

"이벤트가 발생하면 워크플로가 실행된다." 이 문장 하나가 전부입니다.

한 문장 정의

GitHub Actions는 GitHub 저장소에서 발생하는 이벤트를 감지해, 저장소 안에 정의된 자동화 스크립트를 클라우드 가상머신에서 실행해 주는 서비스입니다. 별도의 CI 서버를 세우고 관리할 필요가 없고, 파이프라인 정의가 애플리케이션 코드와 같은 저장소·같은 브랜치에 함께 버전 관리됩니다.

왜 GitHub Actions인가

서버 관리가 0

Jenkins처럼 마스터 서버를 세우고, 플러그인 버전을 맞추고, 디스크가 찼는지 감시할 필요가 없습니다. GitHub가 매 실행마다 깨끗한 VM을 새로 줍니다.

코드와 같은 곳에

PR 하나에 애플리케이션 변경과 파이프라인 변경을 같이 담고, 같이 리뷰하고, 같이 롤백할 수 있습니다.

마켓플레이스

2만 개 이상의 재사용 Action이 공개돼 있습니다. "SSH 배포", "Slack 알림" 같은 기능을 uses: 한 줄로 가져다 씁니다.

깊은 GitHub 통합

PR 체크, 상태 배지, Deployments, Environments, OIDC 토큰까지 별도 연동 없이 기본 제공됩니다.

⚠ 반대로 약한 지점

퍼블릭 저장소는 무료지만 프라이빗 저장소는 실행 시간(minutes) 과금이며, macOS 러너는 Linux 대비 10배 단가입니다. 또 GitHub 자체 장애가 나면 파이프라인도 함께 멈춥니다. 폐쇄망(air-gapped) 환경에서는 GitHub Actions를 쓸 수 없어 GitHub Enterprise Server + self-hosted runner 조합이 필요합니다.

SECTION 03

핵심 구성요소 6가지

Workflow · Event · Job · Step · Action · Runner. 이 6개 단어의 포함 관계만 정확히 잡으면 문서를 혼자 읽을 수 있습니다.

용어한 줄 정의기억할 포인트
Workflow
워크플로		자동화 프로세스 하나 전체.github/workflows/ 아래 YAML 파일 1개 = 워크플로 1개. 저장소에 여러 개 둘 수 있고, 서로 독립적으로 실행됩니다.
Event
이벤트		워크플로를 깨우는 신호on: 절에 씁니다. push, pull_request, schedule(크론), workflow_dispatch(수동) 등 40여 종.
Job
잡		하나의 러너에서 실행되는 Step 묶음Job = VM 1대. 기본은 전부 병렬. needs:로 의존성을 걸어야 순차가 됩니다. Job끼리 디스크를 공유하지 않습니다.
Step
스텝		Job 안의 실행 단위 한 줄위→아래 순차. 같은 VM이라 파일과 환경변수가 이어집니다. run:(셸 명령) 또는 uses:(Action 호출) 둘 중 하나입니다.
Action
액션		재사용 가능한 실행 패키지남이 만든 걸 uses: owner/repo@version으로 씁니다. 직접 만들 수도 있습니다(섹션 12). Actions(서비스명)와 Action(부품)은 다른 말입니다.
Runner
러너		Job이 실제로 돌아가는 머신GitHub이 주는 GitHub-hosted(매번 새 VM)와 내가 준비하는 self-hosted가 있습니다(섹션 13).
🚨 신입이 가장 많이 틀리는 지점

"build Job에서 만든 dist/ 폴더가 deploy Job에 그대로 있을 것"이라고 착각합니다. 없습니다. Job마다 완전히 새 VM이 뜹니다. 파일을 넘기려면 upload-artifact → download-artifact를 반드시 거쳐야 합니다. Jenkins의 단일 워크스페이스에 익숙한 분일수록 자주 겪는 함정입니다.

SECTION 04

첫 워크플로 만들기

파일 하나만 만들면 끝입니다. 아래 코드의 각 줄을 클릭해 무슨 뜻인지 확인해 보세요.

Step 1 — 파일 위치는 고정입니다

tree 저장소 루트 기준
my-app/
├── src/
├── package.json
└── .github/
    └── workflows/          # ← 이 경로여야만 GitHub이 인식합니다
        ├── ci.yml
        ├── deploy.yml
        └── nightly.yml
⚠ 경로 오타 주의

.github/workflow/ (s 누락), .githubs/, github/workflows/ (점 누락) — 전부 인식되지 않습니다. 그리고 에러 메시지도 나오지 않습니다. Actions 탭이 텅 비어 있다면 십중팔구 경로 문제입니다. 확장자는 .yml과 .yaml 둘 다 됩니다.

Step 2 — 최소 워크플로를 해부합니다

아래 코드에서 밑줄 있는 부분을 클릭하면 오른쪽에 설명이 나타납니다.

클릭한 요소 설명
여기를 클릭하세요
왼쪽 코드에서 밑줄 표시된 키워드를 클릭하면, 그 키워드가 무엇을 뜻하고 어떤 값이 올 수 있는지 이 자리에 나타납니다.

Step 3 — 커밋하면 바로 실행됩니다

규칙 1 — 들여쓰기는 스페이스만, 탭 금지

✓ 올바름 (스페이스 2칸)

··build:
····runs-on: ubuntu-latest
✗ 오류 (탭 문자 사용)

→→runs-on: ubuntu-latest

에디터에서 "Insert Spaces" 설정을 켜두세요. VS Code 기준 우측 하단 상태표시줄에서 바꿀 수 있습니다.

규칙 2 — 자료형 세 가지만 알면 됩니다

yaml 자료형 3종
# ① 스칼라(Scalar) — 값 하나
name: My Workflow          # 문자열
timeout-minutes: 30         # 숫자
fail-fast: false             # 불리언

# ② 리스트(Sequence) — 여러 값. 두 가지 표기법이 동일합니다
branches:                    # 블록 스타일
  - main
  - develop
branches: [main, develop]      # 플로우 스타일 (같은 의미)

# ③ 맵(Mapping) — 키:값 묶음
with:
  node-version: '20'
  cache: 'npm'

규칙 3 — 따옴표는 언제 붙이나

상황예시이유
버전 번호node-version: '20'따옴표가 없으면 숫자 20. '20.10'은 따옴표 없이 쓰면 20.1로 잘립니다.
on, yes, novalue: 'on'YAML 1.1에서 불리언 true로 해석될 수 있습니다.
콜론 + 공백 포함run: 'echo a: b'따옴표가 없으면 새 키로 파싱됩니다.
*로 시작paths: ['**/*.js']*는 YAML 앵커 참조 문자입니다.
일반 영문 문자열name: Build App따옴표 불필요. 붙여도 무방합니다.

SECTION 06

트리거(on) 완전 정복

"언제 실행할 것인가". 이걸 정교하게 잡는 것만으로 불필요한 실행 시간(=요금)의 70%가 줄어듭니다.

이벤트를 골라 보세요

트리거 선택기
아래 이벤트를 클릭하면 해당 YAML과 사용 시점이 표시됩니다

필터로 실행 범위를 좁히기

branches, paths, tags 필터는 실무에서 가장 자주 쓰는 최적화입니다. 문서만 고쳤는데 전체 테스트가 20분씩 돌아가는 낭비를 막아 줍니다.

yaml 경로·브랜치 필터
on:
  push:
    branches:
      - main
      - 'release/**'        # release/1.0, release/2.0/hotfix 모두 매칭
    branches-ignore:
      - 'experimental/**'   # branches와 동시 사용 불가 (택1)
    paths:
      - 'src/**'
      - 'package*.json'
    paths-ignore:
      - '**.md'              # 문서만 바뀌면 실행 안 함
      - 'docs/**'
    tags:
      - 'v*.*.*'             # v1.2.3 형태 태그
패턴매칭 대상주의
*/를 제외한 0자 이상feature/*는 feature/a는 되지만 feature/a/b는 안 됩니다.
**/ 포함 0자 이상feature/**는 하위 경로 전부 매칭됩니다.
+1자 이상드물게 사용합니다.
!부정(제외)같은 배열 안에서 - '!main' 형태로 씁니다.
🚨 paths-ignore와 Required Check의 충돌

paths-ignore로 워크플로가 아예 실행되지 않으면, 브랜치 보호 규칙에서 "필수 통과(required)"로 지정한 체크가 영원히 pending 상태가 되어 PR을 머지할 수 없습니다. 해결책은 같은 이름의 더미 잡을 만들어 if로 건너뛰게 하거나(빈 실행 후 성공 처리), dorny/paths-filter 액션으로 워크플로는 항상 실행하되 안에서 분기하는 방식입니다.

pull_request vs pull_request_target

pull_request (기본값)

PR의 머지 결과 커밋을 체크아웃합니다. 외부 포크에서 온 PR은 secrets에 접근할 수 없고 GITHUB_TOKEN도 읽기 전용입니다. 안전합니다.

pull_request_target (위험)

base 브랜치의 워크플로를 쓰면서 secrets에 접근 가능합니다. 여기서 PR 코드를 체크아웃해 실행하면 모든 시크릿이 외부인에게 유출됩니다.

🚨 실제로 자주 터지는 보안 사고

pull_request_target + actions/checkout에 ref: ${{ github.event.pull_request.head.sha }}를 지정하는 조합은 절대 금지입니다. 공격자가 PR에 악성 npm postinstall 스크립트를 넣기만 하면 저장소의 모든 시크릿을 외부로 빼낼 수 있습니다. 포크 PR에 라벨을 붙이거나 코멘트를 남기는 등 코드를 실행하지 않는 용도로만 쓰세요.

수동 실행: workflow_dispatch

yaml 입력값 있는 수동 트리거
on:
  workflow_dispatch:
    inputs:
      environment:
        description: '배포 대상 환경'
        required: true
        default: 'staging'
        type: choice          # choice / string / boolean / environment
        options: [staging, production]
      dry_run:
        description: '실제 배포 없이 검증만'
        type: boolean
        default: true

jobs:
  deploy:
    runs-on: ubuntu-latest

Secrets와 Variables의 차이

Secrets

암호화 저장. 저장 후 다시 볼 수 없습니다(덮어쓰기만 가능). 로그에 출력하면 자동 *** 마스킹. API 키, 비밀번호, 인증서.

Variables

평문 저장. UI에서 값 확인 가능. 로그에 그대로 노출. API 엔드포인트 URL, 리전 이름, 이미지 태그 접두사 같은 비밀 아닌 설정값.

  uses: actions/cache@v4

두 가지 재사용 방식

Composite Action

Step 묶음을 재사용합니다. uses:로 부르며, 부르는 쪽 Job 안에서 실행됩니다. 러너 지정 불가.
→ "Node 설치 + 캐시 + 의존성 설치" 같은 부분 단위.

Reusable Workflow

Job 전체를 재사용합니다. jobs.x.uses:로 부르며, 자기 러너를 갖습니다. secrets 전달 가능.
→ "빌드→스캔→배포" 같은 파이프라인 단위.

yaml .github/actions/setup-app/action.yml
name: 'Setup Application'
description: 'Node 설치, 캐시 복원, 의존성 설치를 한 번에'

inputs:
  node-version:
    description: '사용할 Node.js 버전'
    required: false
    default: '20'

  cache-hit:

    - id: setup
      uses: actions/setup-node@v4

    runs-on: ubuntu-latest

      - run: npm test

    needs: test

        }

            steps {
                sh 'npm ci'
                sh 'npm test'
            }
        }

    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run lint

  # ───────── 2. 다중 버전 테스트 ─────────
  test:
    name: Test (Node ${{ matrix.node }})
    runs-on: ubuntu-latest
    timeout-minutes: 20
    strategy:
      fail-fast: false
      matrix:
        node: [18, 20, 22]
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_PASSWORD: testpass
          POSTGRES_DB: testdb
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }}, cache: 'npm' }
      - run: npm ci
      - name: Run tests
        run: npm test -- --coverage
        env:
          DATABASE_URL: postgres://postgres:testpass@localhost:5432/testdb
      - name: Upload coverage
        if: matrix.node == 20
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/

  # ───────── 3. 보안 스캔 ─────────
  security:
    name: Security scan
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm audit --audit-level=high
        continue-on-error: true
      - name: Trivy filesystem scan
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'fs'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'

  # ───────── 4. 이미지 빌드 & 푸시 ─────────
  build-image:
    name: Build & push image
    needs: [lint, test, security]
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      image: ${{ steps.meta.outputs.tags }}
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Generate tags
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=,format=short
            type=ref,event=branch
            type=raw,value=latest,enable={{is_default_branch}}

      - name: Build and push
        id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ───────── 5. 스테이징 배포 (자동) ─────────
  deploy-staging:
    needs: build-image
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com
    steps:
      - uses: azure/setup-kubectl@v4
      - name: Configure kubeconfig
        run: |
          mkdir -p ~/.kube
          echo "$KUBE_CONFIG" | base64 -d > ~/.kube/config
        env:
          KUBE_CONFIG: ${{ secrets.KUBE_CONFIG_B64 }}
      - name: Rolling update
        run: |
          kubectl -n staging set image deployment/app \
            app=${{ needs.build-image.outputs.image }}
          kubectl -n staging rollout status deployment/app --timeout=180s

  # ───────── 6. 프로덕션 배포 (승인 필요) ─────────
  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production          # Settings에서 Required reviewers 설정
      url: https://example.com
    steps:
      - uses: azure/setup-kubectl@v4
      - run: |
          mkdir -p ~/.kube && echo "$KUBE_CONFIG" | base64 -d > ~/.kube/config
          kubectl -n prod set image deployment/app \
            app=${{ needs.build-image.outputs.image }}
          kubectl -n prod rollout status deployment/app --timeout=300s
        env:
          KUBE_CONFIG: ${{ secrets.KUBE_CONFIG_B64 }}

  # ───────── 7. 결과 알림 ─────────
  notify:
    needs: [deploy-production]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - name: Send Slack message
        uses: slackapi/slack-github-action@v2
        with:
          webhook: ${{ secrets.SLACK_WEBHOOK }}
          webhook-type: incoming-webhook
          payload: |
            text: "배포 ${{ needs.deploy-production.result }} · ${{ github.repository }}@${{ github.sha }}"
✅ 이 파이프라인에서 배울 점
  • needs: [lint, test, security] — 세 검증을 병렬로 돌리고 모두 통과해야 다음으로 갑니다. 순차 실행 대비 시간이 1/3로 줄어듭니다.
  • outputs로 이미지 태그를 배포 Job에 전달합니다. 태그를 다시 계산하지 않으므로 빌드한 것과 배포한 것이 반드시 일치합니다.
  • environment: production 한 줄로 승인 게이트가 생깁니다.
  • if: always()인 notify Job은 실패했을 때도 실행되어 알림이 누락되지 않습니다.
SECTION 16

베스트 프랙티스와 보안

돌아가게 만드는 것과 잘 돌아가게 만드는 것은 다릅니다.

속도 최적화 5가지

기법효과와 방법
1. 병렬화lint·test·보안스캔은 서로 독립적입니다. needs를 걸지 말고 병렬로 두세요. 순차 12분 → 병렬 5분.
2. 캐시setup-*의 cache 옵션부터. npm 설치 90초 → 10초. Docker는 cache-from: type=gha.
3. concurrencyPR에 연속 push할 때 이전 실행을 취소합니다. 낭비되던 러너 시간이 그대로 절약됩니다.
4. paths 필터README만 고쳤는데 전체 파이프라인이 도는 것을 막습니다. 모노레포라면 dorny/paths-filter로 변경된 서비스만 빌드.
5. 얕은 체크아웃actions/checkout은 기본이 fetch-depth: 1입니다. 히스토리가 필요 없다면 그대로 두세요. (0으로 바꾸면 전체 히스토리를 받아 느려집니다)

보안 체크리스트

  • 최소 권한: 워크플로 최상단에 permissions: contents: read를 두고, 필요한 Job에서만 권한을 엽니다.
  • 서드파티 액션은 SHA 고정: @v1 태그는 언제든 다른 커밋을 가리킬 수 있습니다. 조직 정책으로 허용된 액션 목록을 지정할 수도 있습니다.
  • 입력값을 셸에 직접 보간 금지: ${{ github.event.* }}는 반드시 env:를 거쳐 전달합니다(섹션 8).
  • pull_request_target에서 PR 코드 실행 금지: 시크릿 전체가 유출됩니다.
  • 퍼블릭 저장소에 self-hosted 러너 연결 금지.
  • OIDC 사용: 클라우드 장기 액세스 키를 시크릿에 저장하지 않습니다.
  • 시크릿 로그 노출 확인: base64로 인코딩된 값은 마스킹을 우회할 수 있습니다. 디버깅 시 echo로 시크릿을 찍지 마세요.
  • Dependabot 활성화: Action 버전과 의존성 업데이트를 자동으로 받습니다.

가독성과 유지보수

이렇게 하세요

· 모든 스텝에 name: 붙이기
· 워크플로 하나당 목적 하나 (ci.yml / release.yml 분리)
· 복잡한 셸 로직은 scripts/*.sh로 빼고 run: ./scripts/deploy.sh
· timeout-minutes 항상 지정
· 3곳 이상에서 반복되면 재사용 워크플로로 추출

피하세요

· 200줄짜리 run: | 블록
· continue-on-error: true 남발 (실패를 숨김)
· latest 태그 의존 (ubuntu-latest, @main)
· 시크릿을 env:로 워크플로 전역에 노출
· 하나의 거대한 워크플로에 모든 것을 담기

💡 비용 감각

프라이빗 저장소에서 Linux 러너는 분당 과금, Windows는 2배, macOS는 10배입니다. 매트릭스를 무심코 늘리면 비용이 곱으로 증가합니다. OS 3종 × 버전 4종 = 12 Job이고, 각각 10분이면 한 번 push에 120분이 소모됩니다. PR에서는 대표 조합 하나만 돌리고, 전체 매트릭스는 야간 스케줄이나 릴리스 태그에서만 돌리는 분리 전략이 표준입니다.
