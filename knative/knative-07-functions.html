Knative Functions

지금까지는 컨테이너 이미지를 직접 만들어 Service에 넣었습니다. Functions는 그 앞 단계까지 대신합니다. 함수 하나만 작성하면 이미지 빌드, 레지스트리 업로드, Knative 배포, 이벤트 구독까지 func 명령 몇 개로 끝납니다.

기준 버전 Knative v1.23 선수 지식: 2편, 5편 예상 학습 시간 80~100분

함수가 해 주는 일

일반 Knative 서비스를 만드는 과정과 함수를 만드는 과정을 비교해 보면 차이가 분명합니다.

Knative Service 직접 만들기

  • HTTP 서버 코드 작성 (라우팅, 포트, 헬스 체크)
  • Dockerfile 작성과 이미지 빌드
  • 레지스트리 로그인과 push
  • ksvc YAML 작성과 apply
  • 이벤트를 받으려면 Trigger YAML 별도 작성

Knative Function

  • func create로 뼈대 생성
  • Handle 함수 하나만 채움
  • func deploy 한 번으로 빌드·push·배포
  • func subscribe로 이벤트 구독 선언
  • HTTP 서버, 헬스 체크, CloudEvents 파싱은 템플릿이 담당

함수 프로젝트 들여다보기

템플릿은 크게 두 종류입니다. http 템플릿은 일반 HTTP 요청을, cloudevents 템플릿은 CloudEvent를 받고 돌려줍니다(5편의 답장). 언어와 템플릿을 바꿔 가며 func create가 만드는 파일을 열어 보세요. 지원 언어는 Go, Node.js, TypeScript, Python, Quarkus, Spring Boot, Rust입니다.

생성 명령

템플릿 버전에 따라 모양이 다를 수 있다

func는 언어별 템플릿을 계속 개선하고 있습니다. 예를 들어 Python 템플릿은 최근 ASGI 기반의 클래스 구조로 바뀌었고, Go 템플릿도 인스턴스 구조체에 Handle 메서드를 다는 형태로 정리됐습니다. 위 예시는 이해를 돕기 위한 대표 형태이므로, 실제 작업에서는 func create로 생성된 파일과 그 안의 주석을 기준으로 삼으세요.

원격 빌드
--remote		클러스터 안의 Tekton 파이프라인이 Git 저장소를 받아 빌드·배포개발자 PC에 아무것도 없어도 됨. 빌드 환경 통일클러스터에 Tekton과 권한 설정 필요. 레지스트리 자격 증명을 클러스터에 둬야 함
MSP 관점의 선택

고객사 개발자 PC 환경이 제각각이라면 원격 빌드로 빌드 환경을 클러스터에 통일하는 편이 지원 부담이 적습니다. 반대로 개발자가 소수이고 빠른 반복이 중요하면 host 또는 pack 로컬 빌드가 편합니다. 어느 쪽이든 빌드팩 이미지와 베이스 이미지 출처를 고객사 보안 정책에 맞게 사설 레지스트리로 미러링하는 것을 권합니다.

이벤트 구독: func subscribe

cloudevents 템플릿 함수는 Broker에서 이벤트를 받는 것이 보통입니다. 5편에서는 Trigger YAML을 따로 썼지만, 함수에서는 구독을 func.yaml에 선언해 두면 배포할 때 Trigger가 함께 만들어집니다.

bash
# func.yaml에 구독 선언 추가 (아직 클러스터 변경 없음)
func subscribe --source default --filter type=com.mycorp.order.created

# 배포할 때 Trigger가 함께 생성됨
func deploy

kubectl get trigger
답장으로 다음 함수 깨우기

cloudevents 함수가 CloudEvent를 반환하면 Broker로 돌아가 다른 함수의 Trigger를 깨웁니다. 함수 A는 order.created를 받아 order.scored를 반환하고, 함수 B는 order.scored를 구독하는 식으로 5~6편의 코레오그래피를 함수만으로 만들 수 있습니다. 반환 type이 자기 구독 필터에 걸리지 않게 주의하세요.

7 / 14

배포 대상: knative vs raw

v1.21부터 func deploy --deployer raw 옵션이 생겼습니다. Knative Serving이 없는 클러스터에도 함수를 일반 쿠버네티스 Deployment와 Service로 배포할 수 있습니다. 토글로 결과를 비교해 보세요.

생성되는 리소스

    얻는 것과 잃는 것

      raw는 언제 쓰나

      Knative Serving을 설치할 수 없는 고객사 클러스터(규제, 운영 정책, 관리형 플랫폼 제약)에서도 함수 개발 경험만은 통일하고 싶을 때 씁니다. 같은 함수 코드를 개발 클러스터에서는 Knative로, 특정 운영 클러스터에서는 raw로 배포하는 식입니다. 0개 축소, Revision, 트래픽 분할은 포기해야 하므로, 필요하면 HPA나 KEDA를 따로 붙여야 합니다.

      팀과 CI에 넣기

      func.yaml은 Git에

      함수 코드와 func.yaml을 함께 커밋하면 빌드·배포 설정이 코드와 함께 버전 관리됩니다. 레지스트리 주소나 네임스페이스처럼 환경마다 다른 값은 CI에서 플래그나 환경 변수로 덮어씁니다.

      CI에서 func build

      CI 러너에서 func build로 이미지를 만들고 push한 뒤, 배포는 GitOps 저장소의 이미지 태그만 바꾸는 방식이 4편의 "배포와 출시 분리"와 잘 맞습니다.

      사내 템플릿 저장소

      func repository로 회사 표준 템플릿(로깅 형식, 추적 설정, 보안 헤더 포함)을 등록하면 모든 함수가 같은 출발점에서 시작합니다. MSP가 고객사에 제공할 만한 부가가치입니다.

      시크릿은 참조로

      func config envs와 func config volumes로 Secret·ConfigMap을 참조하게 하세요. func.yaml에 비밀 값을 직접 적으면 Git에 그대로 남습니다.

      레지스트리 준비

      자주 만나는 문제

      func build가 "cannot connect to Docker daemon"
      pack·s2i 빌더는 로컬 컨테이너 엔진이 필요합니다. Docker나 Podman을 켜거나, 지원 언어라면 host 빌더(--builder host)를, 아니면 원격 빌드를 쓰세요. Podman이면 소켓 경로를 DOCKER_HOST로 알려 줘야 할 수 있습니다.
      배포는 됐는데 Pod가 ImagePullBackOff
      클러스터 노드가 레지스트리에 접근하지 못하는 경우입니다. 사설 레지스트리라면 imagePullSecret을 네임스페이스 기본 ServiceAccount에 연결하세요. 2편에서 봤듯 controller의 다이제스트 조회도 레지스트리 접근이 필요합니다.
      첫 빌드가 너무 오래 걸림
      Buildpacks는 첫 빌드에 빌더 이미지와 의존성을 내려받습니다. 두 번째부터는 캐시를 씁니다. 회사망에서는 빌더 이미지를 사내 레지스트리로 미러링하면 크게 빨라집니다.
      func invoke는 되는데 Broker 이벤트는 안 옴
      구독 필터의 type 철자, Broker 이름(--source), 그리고 func subscribe 후 다시 deploy했는지 확인하세요. subscribe는 func.yaml만 고치고 클러스터는 deploy 때 바뀝니다.
      함수가 무한히 자기 자신을 깨움
      반환하는 CloudEvent의 type이 자기 구독 필터와 같은 경우입니다. 반환 type을 다르게 하거나, 답장이 필요 없으면 이벤트를 반환하지 마세요.

      정리와 다음 편

      1. Knative Functions는 개발자 경험 도구이며, 결과물은 평범한 Knative Service(또는 Deployment)입니다.
      2. 템플릿은 http와 cloudevents 두 종류이고, 여러 언어를 지원합니다.
      3. func.yaml에 빌드·실행·배포·구독 설정이 모두 들어가며 Git으로 관리합니다.
      4. 개발 사이클은 create → run → invoke → deploy → subscribe입니다.
      5. 빌더는 pack, s2i, host, 그리고 Tekton 기반 원격 빌드 중 환경에 맞게 고릅니다.
      6. --deployer raw로 Serving 없는 클러스터에도 배포할 수 있지만, 0개 축소와 Revision은 사라집니다.
      7. Lambda 대비 강점은 이식성과 표준, 약점은 클러스터 운영 부담입니다.
