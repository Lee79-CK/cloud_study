1왜 변수인가

하드코딩이 MSP에서 비싼 이유

3편 실습 B 코드에서 환경이나 고객에 따라 달라질 값을 찾아보면 7가지가 나옵니다: 리전, 프로젝트·환경 이름, 담당자, 만료일, 인스턴스 유형, 허용할 IP, 서버 수. 이 값들이 코드에 박혀 있으면 두 가지 일이 벌어집니다. 고객이 늘 때마다 디렉터리를 복사해 숫자만 바꾸는 일이 생기고(1편 14장 안티패턴 9번), 시간이 지나면 복사본마다 미묘하게 다른 버그가 고쳐지거나 남아 있게 됩니다.

입력 변수 variable

바깥에서 들어오는 값. 함수의 매개변수. 타입과 허용 범위를 선언하고, 값은 tfvars·환경변수·명령행으로 받는다.

로컬 값 locals

코드 안에서 계산해 이름을 붙인 값. 함수의 지역 변수. 바깥에서는 바꿀 수 없다.

출력 값 output

바깥으로 내보내는 값. 함수의 반환값. 사람·스크립트·다른 모듈·Ansible이 읽는다.

변수로 빼는 것도 지나치면 독

모든 인자를 변수로 만들면 코드는 “아무것도 정하지 않는 껍데기”가 되고, 결정은 수십 줄짜리 tfvars로 흩어집니다. 기준은 간단합니다. 환경·고객마다 실제로 달라지는 값만 변수로, 조직 표준이라 바뀌면 안 되는 값(암호화 켜기, IMDSv2 필수)은 코드에 고정합니다. 표준을 강제하는 것도 IaC의 역할입니다.

자동 변환 규칙

Terraform은 기대 타입과 다른 값이 오면 가능한 범위에서 자동으로 바꿉니다. 편리하지만 의도치 않은 결과의 원인이 되기도 합니다. 아래 결과는 모두 실제 평가 값입니다.

빈 값의 함정과 convert() (1.15)

문법상 {}는 “빈 객체”이고 []는 “빈 튜플”입니다. 빈 맵이나 빈 리스트를 쓸 리터럴 문법이 따로 없습니다. 대부분은 문맥에 따라 자동 변환되지만, 비교 연산처럼 자동 변환이 일어나지 않는 곳에서 문제가 됩니다. 1.15에서 추가된 convert(값, 타입)은 원하는 타입을 명시해 이 모호함을 없앱니다. 변환할 수 없는 값이면 오류를 냅니다.

tolist·tomap과 convert의 차이

tolist()·tomap()·toset()은 바깥 껍데기만 정합니다. 요소 타입은 추론에 맡깁니다. convert()는 set(list(number))처럼 중첩된 전체 타입을 한 번에 지정할 수 있습니다. 1.15 미만에서는 Call to unknown function 오류가 나므로, 이 함수를 쓰는 코드는 required_version을 >= 1.15 이상으로 두어야 합니다.

variable "instance_type" {
  description = "(지원 중단) 예전 단일 서버 구성용"
  type        = string
  default     = null

누군가 아직 instance_type = "t3.small"을 tfvars에 넣어 두었다면 plan 때 경고가 뜹니다. 갑자기 변수를 지워 “Value for undeclared variable”로 깨뜨리는 대신, 한 주기 동안 경고로 알려 주고 다음 정리 때 제거하는 점진적 변경이 가능해졌습니다. 고객사 여러 곳이 같은 코드를 쓰는 MSP에서 특히 유용합니다. 실습 B에 그대로 들어 있습니다.

4validation

잘못된 값은 API까지 가기 전에, plan의 첫 단계에서 막는다

validation이 없으면 잘못된 값은 프로바이더가 클라우드 API를 호출할 때에야 발견됩니다. 그때는 이미 다른 리소스 일부가 만들어진 뒤일 수 있고, 오류 메시지도 클라우드 API의 것이라 이해하기 어렵습니다. validation은 plan을 시작하기 전에, 우리 말로 된 메시지로 막습니다.

variable "allowed_cidrs" {
  type     = list(string)
  default  = []
  nullable = false

  validation {                                     # 규칙 1: 형식
    condition     = alltrue([for c in var.allowed_cidrs : can(cidrhost(c, 0))])
    error_message = "allowed_cidrs의 모든 값은 203.0.113.0/24 같은 CIDR 형식이어야 합니다."
  }
  validation {                                     # 규칙 2: 정책
    condition     = !contains(var.allowed_cidrs, "0.0.0.0/0")
    error_message = "실습 환경에서 0.0.0.0/0 전체 공개는 허용하지 않습니다."
  }
}
패턴condition 예용도
목록 중 하나contains(["dev","stg","prd"], var.env)환경 이름, 허용 리전·인스턴스 계열
정규식can(regex("^[a-z][a-z0-9-]{1,20}$", var.project))이름 규칙
형식 검사 함수can(cidrhost(var.cidr, 0))CIDR, 날짜(formatdate), JSON(jsondecode)
모든 요소alltrue([for x in var.list : ...])리스트·맵의 각 항목 검사
범위var.size >= 8 && var.size <= 100디스크 크기, 개수 상한
다른 변수 참조 (1.9+)var.env != "prd" || var.multi_az“운영계면 Multi-AZ 필수” 같은 조합 규칙
can()과 try()

can(식)은 식이 오류 없이 평가되면 true, 오류면 false를 돌려줍니다. 그래서 “이 값이 CIDR로 해석되는가?”를 묻는 데 씁니다. try(식1, 식2, …)은 오류 없이 평가되는 첫 번째 식의 값을 돌려주므로 “없으면 기본값”에 씁니다. 둘 다 평가 중의 오류만 잡습니다. 존재하지 않는 변수 이름 같은 정적 오류는 잡지 못합니다.

검증기 — 실습 B의 validation 규칙을 그대로 옮겼습니다

validation · precondition · check, 무엇이 다른가

validation은 입력 변수 하나의 값을 검사합니다(이번 편). precondition / postcondition은 리소스·data·output의 lifecycle 안에 두고 “이 AMI는 x86_64여야 한다”처럼 리소스 수준의 가정을 검사합니다. check 블록은 apply 후 “웹 서버가 200을 응답하는가”처럼 실패해도 apply를 막지 않는 상시 점검입니다. 뒤의 두 가지는 11편에서 다룹니다.

2편 .gitignore와의 관계

2편에서 *.tfvars를 Git에서 제외하고 *.example.tfvars만 허용했습니다. 그래서 이 강의의 실습은 dev.example.tfvars를 커밋하고, 각자 terraform.tfvars로 복사해 자기 값을 넣는 방식을 씁니다. 회사에서 환경별 tfvars를 Git으로 관리하려면 비밀이 없는 값만 넣는다는 조건으로 envs/*.tfvars를 예외로 허용하는 식으로 규칙을 바꿉니다. 비밀은 어떤 경우에도 tfvars에 넣지 않습니다.

선언되지 않은 변수에 값을 주면

문자열 템플릿

문자열 안의 ${ }는 값을 삽입하고(interpolation), %{ }는 조건·반복 지시자(directive)입니다. 지시자 옆의 ~는 그쪽의 공백·줄바꿈을 지웁니다(strip marker).

3편에서 user_data를 heredoc으로 코드 안에 썼습니다. 길어지면 읽기 어렵고 셸 문법 강조도 안 됩니다. templatefile(경로, 변수맵)은 별도 파일을 읽어 같은 템플릿 문법으로 렌더링합니다. 템플릿 안에서는 넘겨준 변수맵의 키만 보이고, var.나 local.은 쓸 수 없습니다. 파일 확장자는 관례상 .tftpl입니다.

셸 변수와 충돌할 때: $${ }

템플릿 엔진은 ${로 시작하는 모든 것을 자기 것으로 해석합니다. 셸의 ${HOME}을 그대로 남기려면 $${HOME}으로 씁니다. $HOME이나 $(hostname)처럼 중괄호가 없는 형태는 그대로 통과합니다. 위 템플릿의 $(hostname)이 렌더링 후에도 남는 이유입니다. 마찬가지로 %{는 %%{로 이스케이프합니다.

splat 표현식 [*]

리스트[*].속성은 [for x in 리스트 : x.속성]의 줄임입니다. count로 만든 리소스 목록에서 속성만 뽑을 때 많이 씁니다(aws_instance.web[*].id). for_each로 만든 리소스는 맵이므로 values(aws_instance.web)[*].id처럼 먼저 값 목록으로 바꿉니다. 단일 값에 [*]를 붙이면 null이면 빈 리스트, 아니면 원소 하나짜리 리스트가 되는데, count로 0개 또는 1개 만드는 리소스와 one()을 조합할 때 유용합니다.

자주 쓰는 패턴: 중첩 구조 펼치기

# 서버마다 여러 포트를 연다 → (서버, 포트) 쌍의 평평한 맵이 필요하다
locals {
  server_ports = { web1 = [80, 443], web2 = [80] }

  pairs = merge([
    for srv, ports in local.server_ports : {
      for p in ports : "${srv}-${p}" => { server = srv, port = p }
    }
  ]...)
  # → { "web1-80" = {...}, "web1-443" = {...}, "web2-80" = {...} }
}
# resource "..." "rule" { for_each = local.pairs  ... each.value.port ... }

바깥 for가 서버별 맵의 리스트를 만들고, merge(...)의 ...(인자 펼치기)가 그 리스트를 여러 인자로 풀어 하나의 맵으로 합칩니다. flatten()으로 리스트를 만든 뒤 {for x in ... : key => x}로 바꾸는 방법도 같은 결과를 냅니다. 보안 그룹 규칙, 서브넷×라우팅 테이블 연결처럼 “조합”이 필요한 곳에 거의 반드시 등장합니다.

12dynamic 블록

리소스가 아니라 리소스 안의 “중첩 블록”을 반복 생성한다

count·for_each는 리소스 전체를 여러 개 만듭니다. 리소스 하나 안에 같은 중첩 블록(ingress {}, filter {}, setting {})을 여러 번 써야 할 때는 dynamic 블록을 씁니다.

variable "ami_filters" {
  type = map(list(string))
  default = {
    name         = ["al2023-ami-2023.*-x86_64"]
    architecture = ["x86_64"]
  }
}

data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]

  dynamic "filter" {                    # 만들 중첩 블록 이름
    for_each = var.ami_filters           # 반복할 컬렉션
    content {                           # 블록 하나의 내용
      name   = filter.key                 # 반복 변수 이름 = 블록 이름 (iterator로 변경 가능)
      values = filter.value
    }
  }
}
dynamic은 최후의 수단에 가깝다

dynamic 블록은 코드를 읽기 어렵게 만듭니다. 반복 대상이 고정되어 있다면 그냥 블록을 여러 번 쓰는 편이 낫습니다. 또 3편에서 본 것처럼 보안 그룹 규칙은 ingress {} 중첩 블록보다 별도 리소스(aws_vpc_security_group_ingress_rule) + for_each가 권장됩니다. dynamic이 빛나는 곳은 “개수가 입력에 따라 달라지는 중첩 블록”이 그 리소스의 유일한 표현 수단일 때, 그리고 재사용 모듈(6편)에서입니다.

  # (because index [2] is out of range for count)
  # terraform_data.by_each["api"] will be destroyed
  # (because key ["api"] is not in for_each map)
Plan: 0 to add, 1 to change, 2 to destroy.

실제로 빼고 싶었던 것은 “api” 하나인데, count 쪽은 [1]을 batch로 바꾸고 [2]를 지우는 계획을 세웠습니다. 이것이 서버였다면 멀쩡한 batch 서버가 지워지고 api 서버가 batch로 이름만 바뀐 셈입니다. for_each 쪽은 정확히 api 하나만 지웁니다. 위 출력은 실제 plan 결과를 그대로 옮긴 것입니다.

추가 실험 1

terraform plan -var='names=["cache","web","api","batch"]' — 맨 앞에 넣으면 count는 모든 번호가 하나씩 밀려 4개 전부가 바뀝니다. for_each는 cache 하나만 추가합니다.

추가 실험 2

terraform plan -var='names=["web","web","api"]' — count는 web이 두 개, for_each는 toset()이 중복을 없애 하나. 중복이 의미 있는 데이터라면 for_each 키 설계를 다시 해야 합니다.

terraform destroy -auto-approve
