RHOSO 강의 30 / 33편 Level 4 · 설계와 고급 주제 (마지막 편) 기준: “Adopting a RHOSP 17.1 deployment” 가이드

30편마이그레이션과 채택

새 클라우드를 세우는 일보다 흔한 것은 이미 돌아가는 것을 옮기는 일입니다. 기존 RHOSP 17.1 고객은 RHOSO 18로 넘어와야 하고, VMware 같은 다른 플랫폼의 VM도 OpenStack으로 옮겨 옵니다. 이번 편은 Red Hat이 제공하는 채택(adoption) 절차의 큰 흐름과 되돌릴 수 없는 지점, 다른 플랫폼 VM 이전 방법, 그리고 MSP가 수백 대 이전 프로젝트를 웨이브로 나눠 운영하는 법을 다룹니다.

섹션 1

이 편의 목표

  1. 이전의 네 가지 길(채택 · 병렬 구축 이전 · 타 플랫폼 이전 · 재구축)을 구분한다.
  2. RHOSP 17.1 → RHOSO 18 채택의 단계·소요·영향을 설명한다.
  3. 되돌릴 수 없는 지점과 채택 중 지켜야 할 규칙을 안다.
  4. 채택 준비 체크리스트와 지원되지 않는 구성을 확인한다.
  5. VMware 등 다른 플랫폼 VM을 변환·이전하는 방법을 고른다.
  6. 대규모 이전을 웨이브·컷오버 런북·하이퍼케어로 운영한다.

이 편의 비유: 영업 중인 가게 이사

채택은 건물은 그대로 두고 관리 사무실만 새 건물로 옮기는 이사입니다(컴퓨트 노드·VM은 제자리, 컨트롤 플레인만 OpenShift로). 타 플랫폼 이전은 다른 건물의 짐을 하나씩 포장해 옮기는 이사(VM 변환)입니다. 어느 쪽이든 “언제까지는 되돌릴 수 있고, 언제부터는 앞으로만 가야 하는지”를 미리 알아야 합니다.

섹션 2

이전의 네 가지 길

길무엇을장점단점
① 채택 (adoption)RHOSP 17.1의 컨트롤 플레인을 RHOSO로 옮기고, 같은 컴퓨트 노드를 그 자리에서 18로 올림하드웨어·VM·데이터 그대로, VM 중단 최소절차가 길고 지원 범위 확인 필요, 되돌릴 수 없는 지점 존재
② 병렬 구축 후 이전새 RHOSO를 세우고 VM·볼륨을 OpenStack→OpenStack으로 옮김 (os-migrate 등)구성을 새로 설계, 단계적·되돌리기 쉬움하드웨어 두 벌 필요, VM별 중단, IP 변경 가능
③ 타 플랫폼 이전VMware·Hyper-V 등의 VM 디스크를 변환해 RHOSO로 (virt-v2v·VMware 이전 키트)앱 수정 없이 이전드라이버·부팅 방식 차이, VM별 중단, 변환 시간
④ 재구축 (replatform)앱을 새 VM·IaC(Heat·Terraform·Ansible)로 다시 배포하고 데이터만 이전깨끗한 구성, 자동화 자산 확보앱팀 참여·시간 필요

실제 프로젝트는 섞어서

17.1 고객이라면 ①이 기본이지만, 지원되지 않는 구성이 있으면 ②로 갑니다. VMware 고객은 대부분 ③이지만, 오래된 OS나 자동화가 잘 된 앱은 ④가 더 쌉니다. VM마다 길을 고르는 것이 섹션 7의 선택기입니다.

섹션 3

채택(adoption) 개요

채택은 RHOSP 17.1 컨트롤 플레인을 RHOSO 18.0으로 옮긴 뒤, 데이터 플레인을 제자리 업그레이드하는 과정입니다. 문서는 그 범위를 데이터센터 업그레이드에 준하는 일로 보라고 합니다.

주제가이드 요점
원칙17.1의 컨트롤·데이터 플레인 호스트는 채택 내내 켜져 있고 동작함. 원래 DB는 수정하지 않고 복사해 옴
지원되지 않는 것BGP 환경의 데이터 플레인 채택, FIPS 환경 채택 (그 밖에 기술 미리보기 기능은 채택 맥락에서 시험되지 않음 — 목록 확인)
계획 지침사용자 지정 설정을 메이저 릴리스마다 재검토(여러 OpenStack 릴리스를 건너뜀), 대표 스테이징 환경에서 RHEL 업데이트·채택 검증, 데이터 플레인 위치에 Satellite로 버전 고정된 패키지 제공, 운영에는 스테이징에서 시험한 콘텐츠 사용
DCNDCN 채택은 추가 작업이 있음 (29편에서 본 17.1 DCN → 18.0.3 업그레이드 미지원 주의와 함께 버전별 확인)
채택 후데이터 플레인 노드는 RHEL 9.2 상태 → 최신 유지보수 릴리스로 업데이트(26편) 필요

섹션 4

채택 단계와 되돌릴 수 없는 지점

단계를 누르면 내용·영향·주의가 나옵니다. 초록 테두리는 되돌릴 수 있는 구간, 빨간 테두리는 되돌릴 수 없는 구간입니다.

단계를 눌러 보세요.

되돌릴 수 없는 지점

컨트롤 플레인 채택까지는 “17.1 컨트롤 플레인 서비스를 다시 켜고, OpenShift에 만든 새 리소스를 지우는” 방식으로 되돌릴 수 있습니다. 하지만 RHOSO가 데이터 플레인 노드를 건드리는 순간부터는 앞으로만 가야 합니다. 그 뒤에 17.1 서비스를 다시 켜면 두 컨트롤 플레인이 같은 워크로드를 관리해 데이터 손상·통제 상실이 생길 수 있다고 가이드가 경고합니다. 이 지점 직전에 “계속 진행” 판단 회의를 두세요.

섹션 5

영향과 규칙

채택 중 지킬 규칙

  • DB 이전부터 데이터 플레인 채택 전까지 API가 꺼져 있거나 기동 중 → 고객 셀프서비스 중단 공지
  • 데이터 플레인 채택 전까지 새 VM을 배치할 컴퓨트가 없음
  • 데이터 플레인 채택이 끝날 때까지 네트워크 변경 금지
  • 17.1 쪽에서는 DB·메시징 노드를 멈추되, Compute·Storage·Networker 역할 노드는 멈추지 않음

데이터 플레인 연결 영향 (가이드의 시나리오)

17.1의 OVN 게이트웨이 위치 → 18.0에서영향
17.1 컨트롤러 → OCP가 맡는 게이트웨이트래픽 경로가 새 호스트로 바뀌어 L3 중단 가능
17.1 컨트롤러 → 18.0 네트워커 노드트래픽 경로가 그대로라 L2·L3 연결 손실 없음
17.1 네트워커 → 18.0 네트워커 노드L2·L3 연결 손실 없음
L3를 프로바이더망으로 처리L2·L3 연결 손실 없음

외부 통신 영향이 걱정되면 게이트웨이를 네트워커 노드로 유지하는 설계를 먼저 검토하세요(29편 네트워커 노드).

섹션 13

과제 (반나절)

  1. 채택 적합성 평가: 가상의 17.1 고객 환경(게이트웨이 위치, BGP·FIPS 사용 여부, Ceph 구성, 사용자 지정 설정)을 정하고 섹션 3·5·6으로 채택 가능 여부와 위험을 정리하세요.
  2. 되돌림 판단 회의 자료: 섹션 4의 되돌릴 수 없는 지점 직전에 확인할 항목(서비스 검증 결과, 남은 위험, 계속·중단 기준)을 한 장으로 쓰세요.
  3. VM 분류: VMware VM 10대의 예시 목록(OS·크기·중단 허용·자동화 여부)을 만들고 섹션 7 선택기로 이전 방식을 분류하세요.
  4. 웨이브 계획: 섹션 8 계산기로 300대 이전 일정을 세우고, 파일럿 웨이브 구성을 정하세요.
  5. 랩 실습: 랩에 VM 하나를 다른 하이퍼바이저(또는 다른 프로젝트)에서 이미지로 옮겨 21편 시나리오로 검증하고, 컷오버 런북(섹션 9)을 실제 명령으로 채우세요.

섹션 15

정리와 Level 4 마무리

오늘의 핵심 여덟 문장

  • 이전의 길은 채택 · 병렬 구축 이전 · 타 플랫폼 이전 · 재구축, VM마다 고른다.
  • 채택은 17.1 컨트롤 플레인을 RHOSO로 옮기고 데이터 플레인을 제자리 업그레이드, 데이터센터 업그레이드급 작업.
  • 단계: TLS-e → DB·백엔드 → 컨트롤 플레인 → 컴퓨트 FFU → 네트워커. 원래 DB는 복사만 하고 수정하지 않는다.
  • 데이터 플레인을 건드리기 전까지만 되돌릴 수 있다. 이후 17.1 서비스를 다시 켜면 이중 관리로 손상 위험.
  • 채택 중 API 중단·새 VM 배치 불가·네트워크 변경 금지, Compute·Storage·Networker 노드는 멈추지 않는다.
  • BGP·FIPS 환경 채택은 지원되지 않음, 게이트웨이 위치에 따라 L3 영향이 다르다. 스테이징·Satellite로 검증.
  • 타 플랫폼은 virt-v2v·이전 키트로 변환하되 OS·부팅·드라이버·IP 의존을 먼저 확인, 오래된 것은 재구축.
  • 대규모 이전은 평가 → 설계 → 파일럿 → 웨이브 → 하이퍼케어 → 종료, 가장 큰 위험은 모르는 의존 관계.
