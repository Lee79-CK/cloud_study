Terraform & Ansible 강의 · Level 4 Ansible 심화·운영 · 20편 / 26편 · 시리즈 목차

같은 결과를, 누가 돌려도, 빠르게 실행 환경과 규모 — Execution Environment(ansible-builder·ansible-navigator), forks·파이프라이닝·strategy·async/poll·팩트 캐시, 수백 대 운영, 멱등성 깨짐 진단

13~19편의 플레이북은 각자의 노트북에 설치한 ansible-core·컬렉션·Python 라이브러리 위에서 돌았습니다. 사람마다 boto3 버전이 다르고, 누구는 hvac가 없고, CI 러너에는 또 다른 버전이 깔려 있습니다. 이번 편은 그 모두를 하나의 컨테이너 이미지로 묶는 Execution Environment(EE)로 “누가 돌려도 같은 결과”를 만들고, 서버가 수백 대가 되었을 때 어디에 시간이 드는지를 직접 재 봅니다. 파이프라이닝과 연결 재사용을 모두 끄면 같은 일이 14.3초에서 56.8초가 되고, 컨트롤 노드 CPU 하나로는 forks를 아무리 올려도 20초 밑으로 내려가지 않는다는 것을 숫자로 확인합니다.

재현성

EE 이미지 = ansible-core + 컬렉션 + Python·OS 의존성, 태그로 고정

성능

연결(파이프라이닝·재사용) → 병렬(forks·strategy) → 대기(async) → 수집(팩트)

1“내 PC에서는 됐는데”

지금까지의 실행 환경이 사람마다 다른 지점들

구성 요소이 강의에서 쓴 것사람·러너마다 달라지면
ansible-core2.21.5 (13편)2.18 이하는 2.19+ 템플릿 규칙이 달라 결과가 다르다(13편 9장)
컬렉션community.general 13.5.0, amazon.aws 11.4.0 … (16~19편)모듈 인자·기본값·지원 중단이 다르다(17편 postgresql_set)
Python 라이브러리boto3·botocore(18편), hvac(19편), psycopg2(17편)“Failed to import the required Python library” — 한 사람만 실패
OS 도구openssh, session-manager-plugin(18편), gitSSM 연결이 어떤 PC에서만 안 됨
설정ansible.cfg, vault 클라이언트 스크립트(19편)경로·권한 차이

Terraform에서는 required_version과 잠금 파일(.terraform.lock.hcl)이 도구·프로바이더 버전을 고정했습니다(3·6편). Ansible에는 잠금 파일이 없고(16편 8장) 의존성이 Python·OS 수준까지 내려가므로, 실행 환경 자체를 이미지로 고정하는 것이 같은 효과를 내는 방법입니다.

AAP·AWX와의 관계

Red Hat Ansible Automation Platform과 AWX(21편)는 잡을 실행할 때 반드시 EE를 씁니다. 노트북에서 ansible-navigator로 쓰던 이미지를 그대로 AWX의 잡 템플릿에 지정하면, 개발과 중앙 실행이 같은 환경이 됩니다. Red Hat은 지원되는 기본 이미지(ee-minimal 등)를 Automation Hub 레지스트리로 제공합니다.

3ansible-builder

정의 파일 네 개로 이미지를 만든다

~/iac-lab/ansible/ee/ ├── execution-environment.yml # 무엇을 기반으로, 무엇을 넣을지 ├── requirements.yml # 컬렉션 (버전 고정) ├── requirements.txt # Python 라이브러리 └── bindep.txt # OS 패키지
execution-environment.yml
---
# 20편: iac-lab 실행 환경 (ansible-builder 3.x 형식)
version: 3

images:
  base_image:
    name: quay.io/centos/centos:stream9

dependencies:
  python_interpreter:
    package_system: python3.12            # ansible-core 2.21은 Python 3.12 이상 (13편)
    python_path: /usr/bin/python3.12
  ansible_core:
    package_pip: ansible-core==2.21.5
  ansible_runner:
    package_pip: ansible-runner
  galaxy: requirements.yml                # 컬렉션 (16~19편)
  python: requirements.txt                # 컬렉션이 쓰는 Python 라이브러리
  system: bindep.txt                      # OS 패키지
  exclude:                                # 컬렉션이 선언했지만 실행에 필요 없는 의존성 (introspect로 확인)
    python:
      - pytest-mock                       # community.postgresql 의 테스트용
      - azure-identity                    # community.hashi_vault 의 Azure 인증용 (쓰지 않음)
    system:
      - cryptsetup                        # community.crypto 의 LUKS 모듈용 (쓰지 않음)

additional_build_files:
  - src: ../tools/vault-env-client        # 19편 CI용 Vault 비밀번호 클라이언트
    dest: tools

additional_build_steps:
  append_final:
    - COPY _build/tools/vault-env-client /usr/local/bin/vault-env-client
    - RUN chmod 755 /usr/local/bin/vault-env-client
    # 18편 aws_ssm 연결에 필요한 Session Manager 플러그인 (AWS 공식 RPM)
    - RUN dnf install -y https://s3.amazonaws.com/session-manager-downloads/plugin/latest/linux_64bit/session-manager-plugin.rpm && dnf clean all
    - LABEL org.opencontainers.image.title="iac-lab-ee" org.opencontainers.image.version="2026.10.1"

options:
  package_manager_path: /usr/bin/dnf
  tags:
    - iac-lab-ee:2026.10.1

컬렉션은 자기 requirements.txt·bindep.txt를 갖고 있고, ansible-builder는 이것을 모두 합쳐 설치합니다. 그대로 두면 이미지가 커지고 쓰지 않는 라이브러리의 취약점까지 떠안습니다. introspect 결과를 보고 dependencies.exclude로 필요 없는 것을 빼거나(위 정의 파일), 내 bindep.txt와 겹치는 것(psycopg2)을 정리했습니다.

cd ~/iac-lab/ansible/ee
ansible-builder create -f execution-environment.yml -c context        # 빌드 컨텍스트만 생성 (실측: Complete!)
ansible-builder build  -f execution-environment.yml -c context \
  -t registry.example.internal/iaclab/iac-lab-ee:2026.10.1            # podman 또는 docker 필요
podman push registry.example.internal/iaclab/iac-lab-ee:2026.10.1
생성된 context/Dockerfile — 시작 부분 (실측, 전체 100줄)
ARG EE_BASE_IMAGE="quay.io/centos/centos:stream9"
ARG PYCMD="/usr/bin/python3.12"
ARG PYPKG="python3.12"
ARG PKGMGR_PRESERVE_CACHE=""
ARG ANSIBLE_GALAXY_CLI_COLLECTION_OPTS=""
ARG ANSIBLE_GALAXY_CLI_ROLE_OPTS=""
ARG ANSIBLE_INSTALL_REFS="ansible-core==2.21.5 ansible-runner"
ARG PKGMGR="/usr/bin/dnf"

# Base build stage
FROM $EE_BASE_IMAGE AS base
USER root
ENV PIP_BREAK_SYSTEM_PACKAGES=1
ARG EE_BASE_IMAGE
ARG PYCMD
ARG PYPKG
ARG PKGMGR_PRESERVE_CACHE
ARG ANSIBLE_GALAXY_CLI_COLLECTION_OPTS
ARG ANSIBLE_GALAXY_CLI_ROLE_OPTS
ARG ANSIBLE_INSTALL_REFS
ARG PKGMGR

COPY _build/scripts/ /output/scripts/
COPY _build/scripts/entrypoint /opt/builder/bin/entrypoint
RUN $PKGMGR install $PYPKG -y ; if [ -z $PKGMGR_PRESERVE_CACHE ]; then $PKGMGR clean all; fi
RUN /output/scripts/pip_install $PYCMD
RUN $PYCMD -m pip install --no-cache-dir $ANSIBLE_INSTALL_REFS
생성된 context/Dockerfile — 최종 단계
# Final build stage
FROM base AS final
ENV PIP_BREAK_SYSTEM_PACKAGES=1
ARG EE_BASE_IMAGE
ARG PYCMD
ARG PYPKG
ARG PKGMGR_PRESERVE_CACHE
ARG ANSIBLE_GALAXY_CLI_COLLECTION_OPTS
ARG ANSIBLE_GALAXY_CLI_ROLE_OPTS
ARG ANSIBLE_INSTALL_REFS
ARG PKGMGR

RUN /output/scripts/check_ansible $PYCMD

COPY --from=galaxy /usr/share/ansible /usr/share/ansible

COPY --from=builder /output/ /output/
RUN /output/scripts/install-from-bindep && rm -rf /output/wheels
RUN chmod ug+rw /etc/passwd
RUN mkdir -p /runner && chgrp 0 /runner && chmod -R ug+rwx /runner
WORKDIR /runner
RUN $PYCMD -m pip install --no-cache-dir 'dumb-init==1.2.5'
COPY _build/tools/vault-env-client /usr/local/bin/vault-env-client
RUN chmod 755 /usr/local/bin/vault-env-client
RUN dnf install -y https://s3.amazonaws.com/session-manager-downloads/plugin/latest/linux_64bit/session-manager-plugin.rpm && dnf clean all
LABEL org.opencontainers.image.title="iac-lab-ee" org.opencontainers.image.version="2026.10.1"
RUN rm -rf /output
LABEL ansible-execution-environment=true
USER 1000
ENTRYPOINT ["/opt/builder/bin/entrypoint", "dumb-init"]
CMD ["bash"]
생성된 단계 (다단계 빌드)하는 일
base기본 이미지 + Python 3.12 + ansible-core 2.21.5 + ansible-runner
galaxyrequirements.yml의 컬렉션을 /usr/share/ansible/collections에 설치
builder컬렉션·사용자 의존성을 introspect로 합치고(exclude 반영) wheel 준비
final설치 확인(check_ansible), 의존성 설치, append_final 단계(vault 클라이언트·SSM 플러그인·라벨), USER 1000으로 실행
기본 이미지와 태그

예시는 CentOS Stream 9에 Python 3.12를 설치하는 방식입니다. AAP 구독 고객은 Red Hat이 지원하는 ee-minimal 계열을 기본 이미지로 쓰면 보안 패치·지원을 받을 수 있습니다. 어느 쪽이든 이미지 태그는 latest가 아니라 날짜·버전으로 고정하고(12편 액션 SHA 고정과 같은 원칙), 기본 이미지 보안 업데이트를 반영한 재빌드를 정기 작업으로 둡니다. 이미지도 10편처럼 trivy로 스캔합니다(trivy image).

4ansible-navigator

ansible-playbook 자리에서, EE 안에서 실행하고 기록을 남긴다

~/iac-lab/ansible/ansible-navigator.yml (팀 공통 설정, 저장소에 커밋)
---
# 20편: 팀 공통 실행 방식 — 모두 같은 실행 환경 이미지로
ansible-navigator:
  execution-environment:
    enabled: true
    image: registry.example.internal/iaclab/iac-lab-ee:2026.10.1   # 사내 레지스트리 (태그 고정)
    pull:
      policy: missing
    environment-variables:
      pass:
        - AWS_PROFILE
        - ANSIBLE_VAULT_PASS_PRD
    volume-mounts:
      - src: ~/.ansible-vault
        dest: /runner/.ansible-vault
        options: ro
  mode: stdout
  playbook-artifact:
    enable: true
    save-as: "artifacts/{playbook_name}-{time_stamp}.json"
  logging:
    level: warning
    file: artifacts/ansible-navigator.log
ansible-navigator run playbooks/site_webdb.yml                  # 설정의 EE 이미지 안에서 실행
ansible-navigator run playbooks/site_webdb.yml --ee false       # EE 없이 (로컬 설치로) — 이 강의 검증 환경
ansible-navigator run playbooks/site.yml -m interactive         # 터미널 UI: 플레이·태스크·호스트를 탐색
ansible-navigator collections                                    # 이미지 안의 컬렉션 목록 (EE 필요)
ansible-navigator images                                         # 이미지 정보·포함된 패키지
ansible-navigator replay artifacts/site_webdb-….json            # 지난 실행 결과를 다시 탐색
# 실측 (EE 끈 상태, 20작업 × 3대)

설정왜
execution-environment.image (태그 고정)팀원·CI가 같은 이미지. 이미지를 바꾸는 것은 PR로
environment-variables.pass컨테이너 안으로 넘길 환경 변수만 명시 (AWS_PROFILE, 19편 Vault 키 변수)
volume-mounts (읽기 전용)Vault 키·SSH 키 디렉터리를 이미지에 넣지 않고 실행 시에만
playbook-artifact실행 결과 전체를 JSON으로 — 변경 증적, 장애 분석, replay. 단 no_log를 빠뜨린 비밀도 그대로 남으므로(19편 4장) 보관 위치·권한 관리

6forks와 컨트롤 노드

forks를 올리면 빨라진다 — 컨트롤 노드가 버틸 때까지만

# 실측: 60대(로컬 연결) × "1초 걸리는 작업" 하나, 컨트롤 노드 vCPU 1개
forks=5     29.6초
forks=20    20.0초
forks=60    20.6초      ← 더 올려도 빨라지지 않는다

# 실측: 같은 60대, "아무것도 안 하는 작업"
forks=5     16.0초
forks=60    17.7초      ← 작업이 없어도 16초: 호스트마다 모듈을 준비·실행하는 컨트롤 노드 CPU 비용

호스트 하나·태스크 하나마다 컨트롤 노드는 프로세스를 띄우고 모듈을 묶어 보내고 결과를 해석합니다(13편 2장). 이 실측 환경에서 그 비용은 대략 호스트·태스크당 CPU 0.27초였고, vCPU가 하나라 60대면 약 16초가 forks와 무관하게 듭니다. forks는 “원격에서 기다리는 시간”을 겹치게 할 뿐 컨트롤 노드의 CPU 일을 줄이지 못합니다.

실행 시간 추정기 — 실측으로 맞춘 간단한 모형 (대기 시간 + 컨트롤 노드 CPU 시간)

forks 정하기설명
시작점기본 5는 작다. 컨트롤 노드 vCPU × 5~10 정도에서 시작해 측정으로 조정
메모리fork마다 Python 프로세스 — 수십~백 MB. forks 100이면 수 GB
대상 쪽 한계같은 패키지 저장소·API를 동시에 두드리면 상대가 느려지거나 제한(throttle, 8장)
컨트롤 노드를 키운다수백 대 정기 실행이라면 CI 러너·AWX 실행 노드(21편)의 vCPU를 늘리는 것이 forks보다 효과적

7SSH: 파이프라이닝·연결 재사용

가장 싸고 효과가 큰 손잡이

# 실측: SSH 노드 3대 × ping 작업 20개
파이프라이닝 켬 + 연결 재사용(ControlPersist) :  14.3초     ← 2편 ansible.cfg 설정
파이프라이닝 끔 + 연결 재사용                 :  16.8초

파이프라이닝 끔 + 재사용 끔                   :  56.8초     ← 4배 느림
설정줄이는 것주의
pipelining = True (ssh_connection)모듈을 파일로 올리고 지우는 SSH 왕복 (13편 2장 -vvv 실측)sudoers의 requiretty가 켜져 있으면 become 실패 (요즘 배포판 기본은 꺼짐)
ControlPersist (기본 60초)태스크마다 새 SSH 연결·인증소켓 경로 길이 제한(control_path), 키를 바꿔도 열린 연결이 재사용됨(13·19편)
ssh_args에 -o ControlPersist=300s긴 플레이에서 연결 유지보안 정책상 장시간 세션을 막는 고객도 있다

SSM 연결(18편)은 태스크마다 세션을 새로 열고 S3를 거쳐 파일을 주고받아 SSH보다 훨씬 느립니다. SSM 환경에서 태스크 수를 줄이는 것(반복을 목록 인자로, 파일 여러 개를 템플릿 하나로)이 SSH보다 더 큰 효과를 냅니다.

8strategy·serial·throttle

누가 먼저 끝나도 되나, 몇 대씩 바꾸나, 동시에 몇 개까지

strategy.yml — 태스크마다 느린 호스트가 다르다
- name: 전략 비교
  hosts: fleet[0:8]
  gather_facts: false
  strategy: "{{ strat | default('linear') }}"
  vars:
    n: "{{ inventory_hostname[3:] | int }}"
  tasks:
    - name: 작업 1 (어떤 호스트는 3초)
      ansible.builtin.command: "sleep {{ 3 if (n | int) % 3 == 0 else 1 }}"
      changed_when: false
    - name: 작업 2 (다른 호스트가 3초)
      ansible.builtin.command: "sleep {{ 3 if (n | int) % 3 == 1 else 1 }}"
      changed_when: false
    - name: 작업 3 (또 다른 호스트가 3초)
      ansible.builtin.command: "sleep {{ 3 if (n | int) % 3 == 2 else 1 }}"
      changed_when: false
# 실측 (9대, forks 9)
strategy=linear   15.7초      ← 태스크마다 가장 느린 호스트(3초)를 모두가 기다림: 3+3+3
strategy=free     10.2초      ← 각자 자기 속도로: 3+1+1
serial.yml — 카나리 1대 → 3대 → 50%씩, 실패하면 멈춤
- name: 롤링 배포 실험
  hosts: fleet[0:9]
  gather_facts: false
  serial: [1, 3, "50%"]            # 카나리 1대 → 3대 → 나머지의 50%씩
  max_fail_percentage: 0           # 배치에서 하나라도 실패하면 이후 배치 중단
  tasks:
    - name: 배포 (srv06 은 실패하도록)
      ansible.builtin.command: "{{ 'false' if inventory_hostname == 'srv06' else 'true' }}"
      changed_when: false
# 실측 (10대)
PLAY [롤링 배포 실험]   ok: [srv01]                                  ← 배치 1: 1대
PLAY [롤링 배포 실험]   ok: [srv02] [srv03] [srv04]                  ← 배치 2: 3대
PLAY [롤링 배포 실험]   ok: [srv05] [srv07] [srv08] [srv09]          ← 배치 3: 남은 10대의 50% = 5대
                        fatal: [srv06]: FAILED!
NO MORE HOSTS LEFT                                                   ← max_fail_percentage: 0 → 중단
#   srv10 은 실행되지 않았다 (RECAP에 9대)
throttle.yml — 특정 태스크만 동시 실행 수 제한
- name: Throttle 실험
  hosts: fleet[0:9]
  gather_facts: false
  tasks:
    - name: 외부 API 호출 흉내 (동시에 2개까지만)
      ansible.builtin.command: sleep 1
      changed_when: false
      throttle: 2
# 실측 (10대, forks 10)
throttle=2   :  8.1초       ← 2대씩 5번
throttle 없음:  4.3초
도구쓰는 때주의
strategy: linear (기본)태스크 순서가 모든 호스트에서 맞아야 할 때(클러스터, 앞 태스크 결과를 다른 호스트가 참조)가장 느린 호스트가 전체 속도
strategy: free서로 독립된 서버 수백 대의 정기 구성출력이 섞여 읽기 어렵고, run_once·hostvars 참조 순서가 보장되지 않음
serial운영 서비스 무중단 배포 — 로드밸런서 뒤 서버를 나눠서(카나리)배치마다 핸들러가 돈다. 배치 크기와 서비스 용량(남은 서버가 부하를 감당?)을 함께
max_fail_percentage, any_errors_fatal실패가 퍼지기 전에 멈춤0이면 한 대 실패로 중단 (실측)
throttle외부 API·DB 마이그레이션·라이선스 서버처럼 동시 접속을 제한해야 하는 태스크만forks보다 작게 동작
order호스트 순서(inventory, sorted, shuffle…)serial과 함께 “어느 서버부터”

9async·poll

오래 걸리는 작업을 걸어 두고 다른 일을 한다 — 그리고 연결 시간 제한을 피한다

async.yml
- name: Async·poll 실험
  hosts: fleet[0:4]
  gather_facts: false
  tasks:
    - name: "오래 걸리는 작업을 시작만 하고 넘어간다 (예: 대용량 백업, 패키지 캐시 갱신)"
      ansible.builtin.command: sleep 20
      async: 60          # 최대 60초까지 허용
      poll: 0            # 기다리지 않고 바로 다음 태스크로
      register: long_job
      changed_when: false

    - name: 그동안 다른 작업
      ansible.builtin.command: sleep 10
      changed_when: false

    - name: 시작해 둔 작업이 끝났는지 확인
      ansible.builtin.async_status:
        jid: "{{ long_job.ansible_job_id }}"
      register: job
      until: job.finished
      retries: 20
      delay: 3
# 실측 (5대, forks 5)
오래 걸리는 작업 6초 + 다른 작업 3초 :  순서대로 12.0초  /  async 11.0초
오래 걸리는 작업 20초 + 다른 작업 10초:  순서대로 32.8초  /  async 28.4초

이론상 async는 “6+3”을 “max(6,3)”로 줄이지만, 실측 이득은 생각보다 작았습니다. 상태 확인(async_status)도 호스트마다 모듈을 실행하는 태스크라 재시도마다 컨트롤 노드 CPU를 쓰고(6장), 이 환경은 vCPU가 하나였기 때문입니다. 작업이 길수록(20초+10초) 이득이 커졌습니다. async의 더 중요한 쓰임은 속도보다 안정성입니다.

쓰임설정
SSH·SSM 세션 시간 제한보다 긴 작업 (대용량 백업, OS 업데이트, 데이터 마이그레이션)async: 3600, poll: 15 — 연결을 끊고 15초마다 확인
걸어 두고 다른 일 (위 실험)poll: 0 + 나중에 async_status + until
재부팅async 대신 ansible.builtin.reboot 모듈 (돌아올 때까지 기다림)
주의poll: 0으로 건 작업의 결과는 async_status로 확인하지 않으면 실패를 놓친다. 결과 파일이 원격 ~/.ansible_async/에 쌓이므로 확인 후 정리(mode: cleanup)

# 실측: SSH 3대 × 작업 20개
팩트 수집 안 함                :  14.3초
팩트 수집 (매번 전체)          :  15.1초

11수백 대 운영 팁

고객 서버 수백 대에 정기 구성을 돌릴 때 실제로 부딪히는 것들

문제방법
한 번에 다 돌리면 위험하고 느리다그룹·환경으로 나눠 실행(--limit), 운영은 serial 롤링, 정기 점검은 strategy: free
일부 서버만 실패했다 — 다시 돌려야 할 대상은?실패 호스트 목록을 남겨(retry_files_enabled = True → site.retry) --limit @site.retry로 재실행. 멱등하므로 전체 재실행도 안전하지만 시간이 든다
꺼져 있거나 응답 없는 서버 몇 대 때문에 전체가 늦어진다timeout(연결 시간 제한)을 짧게, UNREACHABLE은 따로 보고. 동적 인벤토리 필터로 꺼진 서버를 애초에 제외(18편)
반복(loop)이 많은 태스크가 느리다목록 인자를 받는 모듈은 한 번에(package name: [목록]), sysctl 같은 것은 파일 하나 + 한 번 적용(과제 1). SSM 환경에서 특히 효과적
외부 시스템(패키지 저장소, API)이 몰려서 느리다throttle, 사내 미러 저장소, 패키지 캐시 서버
실행 기록·결과 분석navigator 아티팩트, JSON 콜백, AWX 잡 기록(21편) — “몇 대가 changed였나”를 매일 추적하면 드리프트·멱등성 문제가 보인다
타사 실행 가속기 (Mitogen 등)큰 속도 향상을 주기도 하지만 지원하는 ansible-core 버전 범위가 좁다. 2.19+의 템플릿 엔진 변경 이후 호환성을 반드시 확인하고, 운영 기본값으로 쓰기 전에 EE 안에서 시험
사람마다 다른 결과EE 이미지와 navigator 설정을 저장소에 (2~4장)

12멱등성이 깨지는 패턴 진단

2회차 changed가 0이 아니면, 그 태스크를 이 목록과 대조한다

broken.yml — 깨진 패턴 6가지
---
# 20편: 멱등성이 깨지는 대표 패턴 (두 번째 실행에도 changed가 나온다)
- name: 멱등성이 깨지는 패턴
  hosts: node1
  become: true
  tasks:
    - name: P1 조회 명령인데 changed로 보고
      ansible.builtin.command: cat /etc/hostname

    - name: P2 파일 끝에 덧붙이기 (실행할 때마다 한 줄씩 늘어남)
      ansible.builtin.shell: echo "net.core.somaxconn=1024" >> /tmp/idem-sysctl.conf

    - name: P3 템플릿에 실행 시각
      ansible.builtin.copy:
        dest: /tmp/idem-motd
        content: "관리: Ansible / 마지막 적용 {{ ansible_facts['date_time']['iso8601'] }}\n"
        mode: "0644"

    - name: P4 비밀번호 해시를 매번 새 salt로
      ansible.builtin.user:
        name: idemuser
        password: "{{ 'Lab-Only-Pass-1' | password_hash('sha512') }}"

    - name: P5 서비스를 매번 재시작
      ansible.builtin.service:
        name: cron
        state: restarted
      failed_when: false

    - name: P6 파일 만들기를 touch로 (매번 시각 갱신)

        path: /tmp/idem-marker
        state: touch
        mode: "0644"
fixed.yml — 같은 일을 멱등하게
---
# 같은 일을 멱등하게
- name: 멱등하게 고친 패턴
  hosts: node1
  become: true
  vars:
    idem_password_salt: "iaclabsalt0001"   # 실제로는 Vault 변수 (19편)
  tasks:
    - name: P1 조회 명령은 changed_when false
      ansible.builtin.command: cat /etc/hostname
      changed_when: false

    - name: P2 원하는 줄이 있도록 (상태 선언)
      ansible.builtin.lineinfile:
        path: /tmp/idem-sysctl.conf
        regexp: '^net\.core\.somaxconn='
        line: net.core.somaxconn=1024
        create: true
        mode: "0644"

    - name: P3 내용이 바뀔 때만 바뀌는 문구
      ansible.builtin.copy:
        dest: /tmp/idem-motd
        content: "관리: Ansible (수동 수정 금지)\n"
        mode: "0644"

    - name: P4 고정 salt (또는 update_password on_create)
      ansible.builtin.user:
        name: idemuser
        password: "{{ 'Lab-Only-Pass-1' | password_hash('sha512', idem_password_salt) }}"

    - name: P5 실행 상태만 선언, 재시작은 핸들러로
      ansible.builtin.service:
        name: cron
        state: started
      failed_when: false

    - name: P6 touch 하되 시각은 보존 (없을 때만 생성)
      ansible.builtin.file:
        path: /tmp/idem-marker
        state: touch
        mode: "0644"
        access_time: preserve
        modification_time: preserve

고객 수십 곳을 같은 도구로

EE는 MSP 표준 도구 상자

MSP 공통 EE(사내 컬렉션 16편 + 검증된 외부 컬렉션 + 보조 도구)를 월 단위로 빌드·스캔·태그합니다. 고객 저장소는 navigator 설정에서 이미지 태그만 지정하고, 업그레이드는 8편 승격 흐름(랩 → 개발계 고객 → 운영계)으로.

고객별 EE는 예외로만

고객이 특정 컬렉션 버전(예: 오래된 네트워크 장비용)을 요구하면 그 고객만 별도 EE를 둡니다. 공통 이미지를 고객 사정으로 묶어 두지 않습니다.

성능 기준선

고객별 정기 실행의 “대상 수, 소요 시간, 2회차 changed 수, 실패 수”를 기록해 두면 이상을 바로 알 수 있습니다. 갑자기 느려졌다면 profile_tasks로 원인 태스크를, changed가 늘었다면 12장 진단표로.

운영 변경은 serial + 카나리

고객 운영 서버 설정 변경은 serial: [1, 10%, 25%]처럼 카나리부터, max_fail_percentage 0으로 시작합니다. 첫 배치 후 서비스 확인 태스크(15편 until)를 두면 문제가 한 대에서 멈춥니다.

망분리 고객

EE 이미지를 고객 내부 레지스트리로 반입하면 컬렉션·Python 패키지를 서버마다 설치할 필요가 없습니다. Galaxy·PyPI에 닿지 않는 환경(16편 7장)의 가장 깔끔한 해법입니다.

컨트롤 노드 크기는 비용 항목

수백 대 고객의 정기 작업 시간이 길다면 실행 노드의 vCPU가 병목인지 먼저 측정합니다(6장). 사람의 대기 시간과 작업 창(점검 시간대)을 고려하면 실행 노드를 키우는 비용이 더 싼 경우가 많습니다.
