이번 편의 기준

NVIDIA의 Confidential Containers 참조 아키텍처는 가중치를 암호화된 상태로 두고 하드웨어로 보호되는 영역 안에서만 복호화하는 것을 기본 그림으로 제시합니다. 이번 편은 이 그림을 MSP가 실제로 구성할 때 필요한 선택지와 주의점으로 풀어냅니다. 매니페스트와 스크립트는 구조를 보여주기 위한 예시이며, 실제 필드와 옵션은 사용하는 버전의 문서를 따르세요.

3

가중치 보호 방식 고르기

가중치를 TEE까지 암호화된 채로 가져오는 방법은 크게 세 가지입니다.

📦A. 암호화된 컨테이너 이미지

가중치를 이미지 레이어에 넣고 레이어를 암호화합니다. CoCo가 TEE 안에서 이미지를 받으며(guest pull) KBS에서 키를 받아 복호화합니다(5편 9장). 앱 수정이 필요 없습니다.

🗄️B. 암호화된 가중치 파일

가중치 파일을 암호화해 오브젝트 스토리지나 볼륨에 둡니다. 파드 안의 init 컨테이너가 ASR로 키를 받아 복호화한 뒤 vLLM이 읽습니다. 모델과 이미지를 분리할 수 있습니다.

🌊C. 로딩 중 복호화

모델 로더가 암호화된 파일을 읽으면서 바로 메모리에 복호화합니다. 평문 사본이 디스크에 남지 않고 시간도 아낄 수 있지만, 로더나 서빙 엔진 쪽 개발이 필요합니다.

4

키 설계: 봉투 암호화

수백 GB 파일을 KBS가 직접 다루지는 않습니다. 대신 봉투 암호화(envelope encryption)를 씁니다.

비유: 금고 열쇠를 넣은 작은 봉투

큰 창고(가중치 파일)는 창고 열쇠(DEK, 데이터 암호화 키)로 잠급니다. 창고 열쇠는 작은 봉투에 넣어 은행 대여금고(KBS)에 맡깁니다. 창고는 어디에 있든, 누가 지키든 상관없습니다. 열쇠를 받으려면 은행 창구에서 증명을 통과해야 하니까요. 창고를 다른 곳으로 옮겨도(스토리지 이전) 열쇠 관리 방식은 바뀌지 않습니다.

키무엇을 암호화하나어디에 있나누가 만드나
DEK (데이터 키)가중치 파일 자체KBS 리소스로 등록 (또는 KEK로 감싸 파일 옆에 저장)모델 소유자의 암호화 도구 (신뢰 환경)

설계 원칙
  • 모델 버전마다 다른 DEK: 한 버전의 키가 새도 다른 버전은 안전합니다. 버전 교체가 곧 키 교체가 됩니다.
  • 저장소로 환경·고객 분리: 리소스 정책을 저장소 단위로 쓰기 쉬워집니다(6편 9장).
  • 모델 소유자가 암호화: 모델 개발사와 운영 고객이 다르다면, 개발사가 직접 암호화하고 DEK를 개발사가 통제하는 KBS(또는 개발사 정책이 적용된 KBS)에 등록하는 구성이 4편·1편의 "가중치 주인" 요구에 맞습니다.

6

vLLM 기밀 파드 구성

방식 B(암호화된 가중치 파일)를 기준으로, 기밀 파드 하나를 조립해 봅니다. KServe 없이 Deployment로 먼저 구성하면 구조가 잘 보입니다.

apiVersion: apps/v1 kind: Deployment metadata: name: llm-prod spec: replicas: 2 template: metadata: annotations: # 5편 8장: 에이전트 정책 + AA·CDH 설정 (workload = "llm-prod" 이름표 포함) io.katacontainers.config.hypervisor.cc_init_data: "<gzip+base64 Init-Data>" spec: runtimeClassName: kata-qemu-nvidia-gpu-tdx # GPU + TDX 기밀 VM (이름은 설치 버전 확인) initContainers: - name: fetch-and-decrypt image: registry.example.com/model-fetcher@sha256:… # digest 고정 command: ["/bin/sh", "/scripts/fetch.sh"] volumeMounts: [{ name: models, mountPath: /models }] containers: - name: vllm image: registry.example.com/vllm@sha256:… # digest 고정 args: ["--model", "/models/llama70b-v3", "--tensor-parallel-size", "4"] # 요청 내용 로깅은 끈다 (옵션 이름은 vLLM 버전마다 다름 → 11장) resources: limits: nvidia.com/pgpu: 4 # GPU 리소스 이름은 GPU Operator 설정에 따라 다름 memory: 320Gi # 5장 계산기로 산정 (파드 VM 메모리 = 이 값 기준) volumeMounts: [{ name: models, mountPath: /models, readOnly: true }] volumes: - name: models emptyDir: { medium: Memory } # TEE 안 메모리(tmpfs). 디스크를 쓰려면 CoCo 보호 스토리지 기능 사용

구조를 보여주는 예시입니다. RuntimeClass 이름, GPU 리소스 이름, 보호 스토리지 설정 방법은 설치한 Kata·GPU Operator·CoCo 버전의 문서를 확인하세요.

볼륨 선택 주의

Kata 환경에서 일반 디스크 기반 볼륨은 구성에 따라 호스트의 디스크를 공유하는 방식으로 연결될 수 있습니다. 그곳에 평문 가중치를 쓰면 TEE를 우회해 호스트에 평문이 남습니다. 평문은 TEE 안의 메모리(medium: Memory)나 CoCo의 보호 스토리지 기능으로만 다루고, 볼륨 종류마다 데이터가 실제로 어디에 저장되는지 반드시 확인하세요.

init 컨테이너가 하는 일

#!/bin/sh — /scripts/fetch.sh (흐름을 보여주는 의사 코드) set -eu CDH=http://127.0.0.1:8006/cdh/resource # 1) 증명을 통과해야만 받을 수 있는 리소스들 (CDH가 필요하면 AA로 증명부터 진행) DEK=$(curl -sf $CDH/llm-prod/model-key/llama70b-v3) S3_CRED=$(curl -sf $CDH/llm-prod/storage/read-cred) # 2) 암호화된 가중치 조각을 내려받는다 (암호문이므로 경로가 노출되어도 안전) download-shards --cred "$S3_CRED" s3://models/llama70b-v3.enc/ /tmp/enc/ # 3) TEE 안에서 복호화해 /models 에 쓴다 (인증 태그로 변조 여부 확인) decrypt-shards --key "$DEK" --in /tmp/enc/ --out /models/llama70b-v3/ rm -rf /tmp/enc/ # 4) 키는 로그에 남기지 않는다. 해시만 남겨 버전을 확인 echo "model llama70b-v3 ready: $(cat /models/llama70b-v3/manifest.sha256)"

download-shards, decrypt-shards는 설명용 가상의 도구입니다. 실제로는 인증 암호화(AES-GCM 등)를 조각 단위로 적용하는 사내 도구나 검증된 라이브러리를 씁니다.

여기서 지켜야 할 것
  • 인증 암호화를 쓴다: 복호화와 함께 위변조를 검사해야 바꿔치기한 가중치(백도어 모델)를 걸러낼 수 있습니다.
  • 키와 평문은 TEE 밖으로 내보내지 않는다: 환경 변수 출력, 디버그 로그, 임시 파일 위치를 점검합니다.
  • init 컨테이너도 정책 대상이다: genpolicy로 만드는 에이전트 정책에 init 컨테이너의 이미지와 명령도 포함됩니다.
7

KServe로 옮기기

KServe 강의에서 본 InferenceService도 결국 파드를 만듭니다. 그래서 같은 요소(RuntimeClass, Init-Data 어노테이션, init 컨테이너, 볼륨)를 InferenceService에 넣으면 됩니다. 다만 KServe가 파드에 자동으로 추가하는 것들을 의식해야 합니다.

apiVersion: serving.kserve.io/v1beta1 kind: InferenceService metadata: name: llm-prod annotations: serving.kserve.io/deploymentMode: RawDeployment # 사이드카가 적은 방식 권장 io.katacontainers.config.hypervisor.cc_init_data: "<gzip+base64 Init-Data>" spec: predictor: runtimeClassName: kata-qemu-nvidia-gpu-tdx initContainers: [ … 6장의 fetch-and-decrypt … ] containers: - name: kserve-container image: registry.example.com/vllm@sha256:… args: ["--model", "/models/llama70b-v3"] resources: { … } volumes: [ … ]

구조 예시입니다. 어노테이션이 파드까지 전달되는 방식, predictor에 넣을 수 있는 필드는 KServe 버전 문서를 확인하세요.

🧩자동 추가 컨테이너

KServe는 스토리지 초기화(storage-initializer) init 컨테이너나, 서버리스 모드의 queue-proxy 사이드카를 넣을 수 있습니다. 이들도 TEE 안에서 돌고 에이전트 정책의 대상입니다. 방식 B에서는 storageUri 대신 직접 만든 init 컨테이너로 내려받기와 복호화를 함께 처리하면 구성이 단순해집니다.

📜정책은 "최종 파드"로 만든다

genpolicy는 실제로 만들어질 파드 스펙을 기준으로 정책을 만들어야 합니다. KServe가 덧붙이는 컨테이너·환경 변수·볼륨까지 반영된 최종 파드 스펙을 스테이징에서 뽑아 정책 생성 입력으로 쓰는 절차를 파이프라인에 넣으세요(8편 5장).

MSP 관점: 서버리스 모드와 기밀 환경

0으로 축소(scale to zero)는 비용에는 좋지만, 기밀 파드는 기동 시간이 깁니다(9장). 첫 요청이 수 분을 기다리게 될 수 있으므로, 기밀 추론에서는 최소 복제본을 유지하는 RawDeployment 방식이 운영상 다루기 쉽습니다.

8

모델 키 리소스 정책

6편에서 배운 리소스 정책을 이 구성에 맞게 씁니다. 모델 키는 가장 중요한 리소스이므로 조건을 모두 겁니다.

# llm-prod.rego (학습용 예시) package policy import rego.v1 default allow = false approved_models := {"llama70b-v3", "llama70b-v4"} # 8편: 전환 중에는 두 버전 allow if { data.plugin == "resource" path := data["resource-path"] path[0] == "llm-prod" path[1] == "model-key" approved_models[path[2]] # 승인된 모델 버전만 cpu := input["submods"]["cpu0"] cpu["ear.status"] == "affirming" # CPU TEE 건강 input["submods"]["gpu0"]["ear.status"] == "affirming" # GPU도 건강 (4편·6편 11장) cpu["ear.veraison.annotated-evidence"]["init_data_claims"]["workload"] == "llm-prod" }

경로 인덱스, Init-Data 클레임 구조, GPU submod 이름은 Trustee 버전과 Init-Data 작성 방식에 따라 다를 수 있습니다. GPU가 여러 장이면 모든 GPU submod를 확인하도록 작성합니다.

이 정책이 막아주는 것
  • GPU CC가 꺼진 노드에서 뜬 파드 → gpu0 조건에서 거부
  • 미승인 커널·디버그 모드 → cpu0 판정에서 거부
  • 같은 이미지로 띄운 다른 워크로드 → Init-Data 이름표에서 거부
  • 제거된 옛 모델 버전 요청 → 승인 목록에서 거부
9

기동 시간 분석

기밀 추론 파드는 일반 파드보다 늦게 뜹니다. 어느 단계가 길고 무엇으로 줄일 수 있는지 보세요.

단계별 상대적인 크기를 보여주는 학습용 그림이며 실제 시간이 아닙니다. 모델 크기, 스토리지, 네트워크, GPU 수에 따라 크게 달라지므로 PoC에서 단계별로 측정하세요.

10

확장·버전·키 교체 운영

📈확장 (스케일 아웃)

새 파드가 서비스에 들어오기까지 오래 걸리므로, 트래픽 증가를 예측해 미리 늘리거나 최소 여유 복제본을 유지합니다. 오토스케일러의 기준 지표와 대기 시간을 기밀 파드 기동 시간에 맞게 조정하세요.

💾노드 캐시는 암호문으로

가중치 다운로드 시간을 줄이려 노드에 캐시를 두는 것은 괜찮습니다. 단 암호화된 파일을 캐시해야 합니다. 평문 캐시를 노드에 두는 순간 모든 보호가 무너집니다.

🔄모델 버전 교체

새 모델 버전은 새 DEK, 새 KBS 경로를 갖습니다. 8편의 릴리스 번들에 "모델 키 경로와 리소스 정책의 승인 모델 목록"을 포함시키고, 추가 → 배포 → 제거 순서로 진행합니다.

🔑키 교체

DEK를 바꾸려면 가중치를 새 키로 다시 암호화해야 합니다. 그래서 키 교체는 보통 "같은 모델의 새 버전 배포"로 처리하는 것이 깔끔합니다. KEK를 쓰는 구성이라면 KEK만 교체하고 DEK를 다시 감싸는 방식도 가능합니다.

🏢여러 고객사 서빙

여러 고객의 요청을 한 파드에서 처리하면 KV 캐시·프리픽스 캐시를 통한 정보 유추 위험이 있습니다(1편 시나리오 F). 고객사별로 파드(즉 기밀 VM)를 나누고, KBS 저장소와 Init-Data 이름표도 고객사별로 분리하는 것이 기본입니다.

🧯장애 대응

8편 11장의 런북을 그대로 씁니다. 여기에 "GPU 판정이 affirming이 아님"(CC 모드 꺼짐, 드라이버·RIM 불일치) 분기를 추가하세요.

로그와 관측

기밀 파드 안에서 무엇을 내보내도 되는지가 1편 시나리오 C(로그에 다 있었다)를 막는 마지막 관문입니다. OpenTelemetry 강의에서 다룬 신호들을 기준으로 정리합니다.

신호내보내도 되는 것내보내면 안 되는 것
메트릭요청 수, 지연 시간, 토큰 수, GPU 사용률, 큐 길이, 오류율고객별 매우 세밀한 레이블(사용자 ID 등)은 신중히
로그요청 ID, 상태 코드, 처리 시간, 모델 버전, 오류 유형프롬프트, 출력, 시스템 프롬프트, 키, 토큰 원문
트레이스단계별 시간(토큰화, 프리필, 디코드), 모델 이름프롬프트·출력이 담긴 속성(attribute), RAG 문서 내용
덤프·디버그-코어 덤프, 메모리 덤프 (운영 정책상 금지)
서빙 엔진의 요청 로깅

서빙 엔진은 버전에 따라 요청 내용을 로그로 남기는 기능의 기본값과 옵션 이름이 다릅니다. vLLM도 마찬가지이니, 사용하는 버전에서 요청·프롬프트 로깅이 꺼져 있는지 실제 로그를 보고 확인하세요. 게이트웨이, 사이드카, 로깅 라이브러리의 디버그 레벨도 함께 점검해야 합니다.

구축 체크리스트

13

오해 바로잡기

오해기밀 파드 안에 있으니 어떤 볼륨에 가중치를 풀어도 된다.
사실볼륨 종류에 따라 데이터가 호스트 디스크에 저장될 수 있습니다. 평문은 TEE 안 메모리나 보호 스토리지에만 둡니다.
오해가중치를 암호화해 두면 GPU 쪽은 신경 쓰지 않아도 된다.
사실복호화한 가중치는 GPU 메모리에 평문으로 올라갑니다. GPU CC가 꺼져 있으면 호스트가 읽을 수 있으므로 리소스 정책에서 GPU 판정까지 요구해야 합니다.
오해KServe의 storageUri로 받으면 알아서 안전하다.
사실저장소에서 받는 것 자체는 괜찮지만, 받은 파일이 평문이라면 저장 위치와 경로가 모두 보호되어야 합니다. 암호문으로 받고 TEE 안에서 복호화하는 흐름을 분명히 설계하세요.
오해모델 키 하나로 모든 버전을 암호화하면 관리가 편하다.
사실편하지만 한 번 새면 모든 버전이 노출되고, 키 교체가 전체 재암호화가 됩니다. 버전마다 DEK를 나누는 편이 운영도 보안도 낫습니다.

확인 퀴즈

보기를 누르면 바로 정답과 해설이 나옵니다.

15

정리와 다음 편

  1. 목표는 가중치가 TEE 밖에서는 늘 암호문, 증명을 통과한 GPU 기밀 파드 안에서만 평문이 되는 것입니다.
  2. 가중치 보호는 암호화 이미지, 암호화 파일, 로딩 중 복호화 중에서 모델 크기·교체 빈도·개발 여력으로 고릅니다. MSP 환경에서는 암호화 파일 방식이 무난합니다.
  3. 키는 봉투 암호화로 설계하고, 모델 버전마다 다른 DEK와 KBS 경로를 둡니다.
  4. 평문은 TEE 안 메모리나 보호 스토리지에만 두고, 위치에 따라 VM 메모리·디스크 예산을 잡습니다.
  5. vLLM 파드·KServe InferenceService에는 기밀 RuntimeClass, Init-Data, init 컨테이너를 넣고, 정책은 최종 파드 스펙으로 만듭니다.
  6. 모델 키 리소스 정책은 CPU·GPU 판정, Init-Data 이름표, 승인 모델 목록을 모두 확인합니다.
  7. 기동 시간이 길므로 암호문 노드 캐시, 병렬 처리, 최소 복제본으로 운영하고, 로그에는 프롬프트·출력을 남기지 않습니다.

10편 예고: 엔드투엔드 신뢰 사슬

지금까지는 "서버 쪽이 키를 받아도 되는가"를 Trustee가 판단했습니다. 그런데 프롬프트를 보내는 사용자는 무엇을 믿고 보낼까요? 10편에서는 TLS를 TEE 안에서 종료하는 방법, 클라이언트가 직접 증명을 확인하고 접속하는 방식(증명된 TLS), 투명성 로그, 그리고 관측 데이터를 통한 유출 경로를 막는 설계를 다룹니다.

TEE·Trustee 강의 시리즈 9편. 매니페스트, 스크립트, 정책, 계산기는 구조와 원리를 보여주기 위한 학습용 예시입니다. RuntimeClass·GPU 리소스 이름, 보호 스토리지 설정, KServe 필드, vLLM 옵션은 사용하는 버전의 공식 문서를 확인하세요.
