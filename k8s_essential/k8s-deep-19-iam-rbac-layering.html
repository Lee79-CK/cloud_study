벤더별 RBAC 레이어링: 클라우드 IAM과 Kubernetes RBAC의 중첩

18편의 RBAC만 보면 매니지드 클러스터의 권한을 절반만 본 것입니다. EKS·AKS·GKE에서는 클라우드 IAM이 클러스터 위에 한 층, 벤더 인가기가 RBAC 옆에 또 한 층 있고, 세 층이 서로 합쳐집니다. RBAC 바인딩을 지웠는데도 여전히 접근이 되거나, 클라우드 계정 관리자가 클러스터 권한을 스스로 만들 수 있는 이유가 여기 있습니다. OpenShift는 Project·SCC가, Rancher는 3계층 역할이 RBAC을 감쌉니다. 이 편은 다섯 플랫폼의 층 구조를 해부하고, 18편의 조직 역할 모델을 각 플랫폼에 매핑해 중복 허용과 충돌을 표로 정리합니다.

기준: Kubernetes v1.37 · EKS 액세스 엔트리 · AKS Azure RBAC · GKE IAM · OpenShift 4.x · Rancher 2.x 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

읽는 법과 목표

쉬운 말로 매니지드 Kubernetes는 건물(클러스터)이 큰 단지(클라우드 계정) 안에 있는 것과 같습니다. 단지 관리소(클라우드 IAM)는 “누가 이 건물 열쇠를 받을 수 있나”와 “누가 건물 출입 명단을 고칠 수 있나”를 정하고, 건물에는 관리소가 붙인 출입 규칙(벤더 인가기)과 건물 자체의 출입 규칙(RBAC)이 함께 붙어 있습니다. 두 규칙 중 하나라도 통과시키면 들어갈 수 있습니다. 그리고 관리소 직원은 마음만 먹으면 출입 명단에 자기 이름을 적을 수 있습니다.

이 편을 마치면 할 수 있는 것

  • 클라우드·플랫폼 제어(①), 벤더 인가기(②), Kubernetes RBAC(③)의 세 층과 합집합 규칙으로 매니지드 클러스터의 실제 권한을 판단할 수 있습니다.
  • EKS 액세스 엔트리·액세스 정책, AKS Azure RBAC, GKE IAM의 범위와 한계를 비교하고 언제 RBAC을 함께 쓸지 정할 수 있습니다.
  • OpenShift의 Project·self-provisioner·cluster-reader·SCC, Rancher의 3계층 역할이 RBAC으로 어떻게 내려가는지 설명할 수 있습니다.
  • 조직 역할 모델을 다섯 플랫폼에 매핑하고, 중복 허용·충돌·메타 권한을 표로 정리할 수 있습니다.
  • 층별로 “누가 무엇을 할 수 있나”를 조회하는 감사 명령을 쓸 수 있습니다.

② 벤더 인가기Kubernetes API 요청을 RBAC과 별도로 허용액세스 정책(클러스터·네임스페이스 범위)Azure RBAC for Kubernetes(켠 경우)IAM 역할(container.*)— (SCC가 Pod 생성 시 별도 판정)— (역할 템플릿을 RBAC으로 변환해 내려보냄)

규칙 세 줄

  1. ②와 ③은 합집합. 어느 한쪽이 허용하면 허용입니다. 거부 규칙이 없으므로 한 층에서 권한을 빼도 다른 층이 주고 있으면 여전히 허용됩니다(중복 허용).
  2. ①은 ②③ 위에 있다. ①에서 액세스 엔트리·역할 할당·IAM 바인딩을 바꿀 수 있는 사람은 스스로 클러스터 관리자가 될 수 있습니다. 클러스터 RBAC 감사만으로는 이 사람을 찾을 수 없습니다.
  3. ①의 우회 경로를 막는다. AKS의 로컬 관리자 자격 증명, EKS의 클러스터 생성자 관리자 권한, GKE의 기본 역할(Owner·Editor) 같은 “층을 건너뛰는 문”을 먼저 닫습니다.

EKS: IAM → 액세스 정책 → RBAC

17편에서 본 것처럼 EKS 인증은 IAM 주체입니다. 인증된 IAM 주체는 액세스 엔트리로 클러스터와 연결되고, 권한은 두 가지 방법으로 받습니다: 액세스 정책(EKS 인가기, ②)과 Kubernetes 그룹(RBAC, ③). 둘 다 지정할 수 있고 결과는 합집합입니다.

액세스 정책대략 대응하는 RBAC범위 지정
AmazonEKSClusterAdminPolicycluster-admin클러스터
AmazonEKSAdminPolicyadmin클러스터 또는 네임스페이스 목록
AmazonEKSEditPolicyedit클러스터 또는 네임스페이스 목록
AmazonEKSViewPolicyview(Secret 제외)클러스터 또는 네임스페이스 목록
AmazonEKSAdminViewPolicy클러스터 전체 읽기(Secret 포함)클러스터
  • 정책은 고정 목록. AWS가 정의한 정책만 쓸 수 있어 resourceNames나 특정 서브리소스만 같은 세밀한 권한은 표현할 수 없습니다. 그런 역할(18편 developer·ci-deployer)은 Kubernetes 그룹 + RBAC으로 줍니다.
  • 인증 모드. CONFIG_MAP(aws-auth만) → API_AND_CONFIG_MAP → API(액세스 엔트리만). aws-auth의 매핑과 액세스 엔트리가 함께 있으면 둘 다 유효하니, 이전 후 aws-auth 항목을 정리하고 API 모드로 바꿉니다.
  • 메타 권한(①). eks:CreateAccessEntry·eks:AssociateAccessPolicy를 가진 IAM 주체는 자기에게 ClusterAdmin을 붙일 수 있습니다. 이 IAM 권한을 가진 사람이 곧 잠재적 클러스터 관리자입니다.
  • 클러스터 생성자. 생성 시 bootstrapClusterCreatorAdminPermissions로 만든 사람에게 관리자 엔트리가 붙습니다. 운영 클러스터는 이를 끄거나, 생성 후 명시적 관리자 엔트리로 바꾸세요.
  • 노드도 엔트리. 노드 역할은 EC2_LINUX 같은 유형의 액세스 엔트리로 연결되어 system:nodes 그룹을 받습니다.
EKS 층별 조회
aws eks describe-cluster --name lab-eks --query 'cluster.accessConfig'          # 인증 모드, 생성자 권한
aws eks list-access-entries --cluster-name lab-eks
aws eks describe-access-entry --cluster-name lab-eks --principal-arn $ARN --query 'accessEntry.kubernetesGroups'
aws eks list-associated-access-policies --cluster-name lab-eks --principal-arn $ARN
kubectl -n kube-system get cm aws-auth -o yaml 2>/dev/null                      # 남은 옛 매핑
# ① 메타 권한 보유자 찾기: IAM 정책 시뮬레이터 또는 Access Analyzer로 eks:CreateAccessEntry 허용 주체 조회
aws iam simulate-principal-policy --policy-source-arn $ARN --action-names eks:CreateAccessEntry eks:AssociateAccessPolicy

AKS: Azure RBAC for Kubernetes vs Kubernetes RBAC

구성인증인가권한을 바꾸는 곳
로컬 계정(Entra 없음)인증서RBAC클러스터 안
Entra ID + Kubernetes RBACEntraRBAC(그룹 객체 ID로 바인딩)클러스터 안(GitOps로 관리 가능)
Entra ID + Azure RBAC for KubernetesEntraAzure 역할 할당(②) + RBAC(③) 합집합Azure(포털·CLI·IaC, 활동 로그에 기록)
Azure 역할(②)대응범위
Azure Kubernetes Service RBAC Cluster Admincluster-admin클러스터
Azure Kubernetes Service RBAC Adminadmin(네임스페이스 안 RBAC 관리 포함)클러스터 또는 …/namespaces/<ns>
Azure Kubernetes Service RBAC Writeredit에 가까움(Secret 읽기 포함, RBAC 관리 제외)클러스터 또는 네임스페이스
Azure Kubernetes Service RBAC Readerview(Secret·RBAC 객체 제외)클러스터 또는 네임스페이스
사용자 정의 역할(dataActions)리소스·동작 단위 조합같음(이름 단위 제한은 불가)

①층의 두 문

  • Azure Kubernetes Service Cluster User Role: 사용자용 kubeconfig를 받을 권한(listClusterUserCredential). 이것만으로는 아무것도 못 하고, ②③이 실제 권한을 정합니다.
  • Azure Kubernetes Service Cluster Admin Role(그리고 이를 포함하는 Contributor·Owner): 로컬 관리자 자격 증명(listClusterAdminCredential)을 받을 수 있습니다. 로컬 계정이 켜져 있으면 이것이 Entra·Azure RBAC·RBAC을 모두 건너뛰는 cluster-admin 인증서입니다. 그래서 --disable-local-accounts가 핵심입니다.

무엇을 고를까

Azure RBAC은 권한을 Azure 쪽(활동 로그·PIM·조건부 액세스·관리 그룹 상속)에서 관리하고 싶을 때, Kubernetes RBAC은 GitOps로 클러스터와 함께 관리하고 다른 클라우드와 같은 모델을 쓰고 싶을 때 맞습니다. 둘을 함께 켤 수도 있지만, 그러면 한 사람의 권한을 확인하려면 두 곳을 모두 봐야 합니다. Azure 역할 할당은 반영에 수 분이 걸릴 수 있어 장애 중 권한 변경이 즉시 적용되지 않는 점도 런북에 적어 두세요.

AKS 층별 조회
AKS_ID=$(az aks show -g rg-lab -n lab-aks --query id -o tsv)
az aks show -g rg-lab -n lab-aks --query '{aad:aadProfile, localAccountsDisabled:disableLocalAccounts}'
az role assignment list --scope $AKS_ID --include-inherited -o table          # ①② 클러스터 범위(상속 포함)
az role assignment list --scope $AKS_ID/namespaces/team-dev -o table           # ② 네임스페이스 범위
kubectl get rolebinding,clusterrolebinding -A -o wide | grep -iE '[0-9a-f]{8}-[0-9a-f]{4}'   # ③ 객체 ID 주체

GKE: IAM과 RBAC의 합집합

GKE는 Kubernetes API 요청마다 IAM과 RBAC을 모두 확인하고, 둘 중 하나라도 허용하면 통과시킵니다. IAM 권한 이름이 API와 1:1로 대응합니다(container.pods.get, container.secrets.list …).

IAM 역할Kubernetes 안 권한(②)범위쓰임
roles/container.admin모든 것프로젝트(또는 폴더·조직 상속)플랫폼 관리자
roles/container.developer대부분 쓰기(Secret 포함)프로젝트주의: 프로젝트 안 모든 클러스터
roles/container.viewer읽기(Secret 제외)프로젝트감사·모니터링
roles/container.clusterViewer클러스터 목록·자격 증명만(API 권한 거의 없음)프로젝트RBAC으로 세밀하게 줄 사람의 기본 IAM
기본 역할 Owner·Editor·ViewerEditor는 container 쓰기 대부분 포함프로젝트운영 프로젝트에서 사람에게 주지 말 것
  • IAM은 네임스페이스를 모른다. IAM 역할은 프로젝트 단위라 특정 네임스페이스로 좁힐 수 없습니다. 그래서 권장 패턴은 “IAM은 clusterViewer, 권한은 RBAC”입니다.
  • 그룹. Google Groups for RBAC를 켜면 gke-security-groups@도메인 아래의 그룹을 RBAC 주체로 쓸 수 있습니다(17편).
  • 메타 권한. 프로젝트 IAM 정책을 바꿀 수 있는 사람(resourcemanager.projects.setIamPolicy)은 자신에게 container.admin을 줄 수 있습니다. 조직 정책·폴더 상속까지 확인해야 합니다.
GKE 층별 조회
PROJECT=$(gcloud config get-value project)
gcloud projects get-iam-policy $PROJECT --flatten='bindings[].members' \
  --filter='bindings.role:(roles/container. OR roles/owner OR roles/editor)' --format='table(bindings.role,bindings.members)'
gcloud container clusters describe lab-gke --location asia-northeast3-a --format='value(authenticatorGroupsConfig)'
kubectl get clusterrolebinding,rolebinding -A -o wide | grep -E '@'          # ③ 이메일 주체

OpenShift: Project·추가 역할·SCC

요소무엇RBAC과의 관계운영 포인트
Project네임스페이스를 감싼 개념. oc new-project로 만들면 요청자가 그 Project의 adminProject 요청 템플릿이 RoleBinding·쿼터·NetworkPolicy를 만들어 줌요청 템플릿에 기본 거부 NetworkPolicy(9편)·쿼터를 넣는 것이 정석
self-provisionerProject를 스스로 만들 수 있는 ClusterRole기본으로 system:authenticated:oauth에 바인딩 → 로그인한 모두가 Project 생성기업 환경은 바인딩 주체를 비우고 자동 복원을 끔
cluster-reader클러스터 전체 읽기(Secret 제외)집계 역할(aggregate-to-cluster-reader)감사자 역할
basic-user, admin·edit·view업스트림과 같은 계열 + OpenShift 리소스(Route, BuildConfig, ImageStream) 포함집계 역할edit의 Secret·SA 가장 주의는 18편과 같음
SCCPod가 쓸 수 있는 보안 설정(특권, 루트, hostPath, UID 범위)SCC 사용 권한도 RBAC: securitycontextconstraints에 use 동사Pod를 만든 주체 또는 Pod의 SA가 사용 권한을 가진 SCC 중에서 선택(21편에서 PSA와 비교)
OpenShift에서 RBAC과 SCC 함께 보기
oc get clusterrolebinding self-provisioners -o yaml | grep -A3 subjects
# 기업 환경: 셀프 프로비저닝 끄기(자동 복원도 끔)
oc patch clusterrolebinding.rbac self-provisioners -p '{"subjects": null}'
oc annotate clusterrolebinding.rbac self-provisioners 'rbac.authorization.kubernetes.io/autoupdate=false' --overwrite

oc adm policy who-can use scc privileged                  # 특권 SCC를 쓸 수 있는 주체
oc adm policy add-scc-to-user anyuid -z legacy-app -n team-dev   # 내부적으로 system:openshift:scc:anyuid 역할 바인딩 생성
oc get rolebinding -n team-dev | grep scc
oc auth can-i use scc/privileged --as=system:serviceaccount:team-dev:legacy-app

Rancher: 글로벌·클러스터·프로젝트 3계층

계층기본 역할다운스트림에 생기는 것
글로벌Administrator, Standard User(클러스터 생성 가능), User-Base(로그인만), 사용자 정의 글로벌 역할Administrator는 모든 다운스트림에서 cluster-admin. 나머지는 Rancher 자체 기능 권한
클러스터Cluster Owner, Cluster Member, 사용자 정의(역할 템플릿)ClusterRoleBinding(Owner → cluster-admin 등)
프로젝트Project Owner, Project Member, Read-only, 사용자 정의프로젝트에 속한 각 네임스페이스마다 RoleBinding. 네임스페이스를 프로젝트에 넣거나 빼면 바인딩도 따라 생성·삭제
  • 역할 템플릿. Rancher 역할은 RoleTemplate 객체이며 다운스트림에서는 ClusterRole로 만들어집니다. 사용자 정의 템플릿으로 18편 developer 같은 역할을 만들 수 있습니다.
  • 주체는 Rancher 사용자 ID. 다운스트림 바인딩의 주체는 u-xxxxx 같은 Rancher 사용자나 IdP 그룹 문자열이며, 요청은 Rancher가 가장(impersonation)해 보냅니다(17편).
  • 직접 만든 RBAC과 공존. 다운스트림에서 kubectl로 직접 만든 바인딩도 유효하지만 Rancher UI에 보이지 않고, Rancher에서 사용자를 지워도 사라지지 않습니다. 권한 출처가 두 곳이 됩니다.
  • 메타 권한. Rancher Administrator와 클러스터·프로젝트 Owner(구성원 관리 권한)는 다른 사람에게 역할을 줄 수 있습니다. Rancher 자체의 감사 로그를 함께 수집하세요(22편).

who-can-everywhere.sh — “이 사람은 어디서 권한을 받나”
#!/usr/bin/env bash
# 사용: ./who-can-everywhere.sh <IAM-ARN|Entra-objectId|email|OpenShift 그룹>
P=$1
echo "== EKS ②: 액세스 정책";      aws eks list-associated-access-policies --cluster-name lab-eks --principal-arn "$P" 2>/dev/null | jq -r '.associatedAccessPolicies[] | "\(.policyArn | split("/")[-1])  \(.accessScope.type) \(.accessScope.namespaces // [])"'
echo "== EKS ③: Kubernetes 그룹";   aws eks describe-access-entry --cluster-name lab-eks --principal-arn "$P" 2>/dev/null | jq -r '.accessEntry.kubernetesGroups[]?'
echo "== AKS ①②: 역할 할당";        az role assignment list --assignee "$P" --all -o tsv --query "[?contains(scope,'managedClusters')].[roleDefinitionName,scope]" 2>/dev/null
echo "== GKE ①②: IAM";              gcloud projects get-iam-policy "$(gcloud config get-value project 2>/dev/null)" --flatten='bindings[].members' --filter="bindings.members:$P" --format='value(bindings.role)' 2>/dev/null
for ctx in lab-native lab-rke2 lab-ocp lab-eks lab-aks lab-gke; do
  kubectl config get-contexts "$ctx" >/dev/null 2>&1 || continue
  echo "== $ctx ③: RBAC 바인딩"
  kubectl --context "$ctx" get rolebinding,clusterrolebinding -A -o json | jq -r --arg p "$P" '.items[] | select(any(.subjects[]?; .name==$p or (.name|tostring|contains($p)))) | "\(.kind) \(.metadata.namespace // "-")/\(.metadata.name) → \(.roleRef.name)"'
done

현장 사례

프로젝트 Editor 한 줄로 모든 GKE 클러스터에 쓰기 권한

원인. 데이터 분석가들에게 BigQuery 작업을 위해 프로젝트 기본 역할 Editor를 줬는데, 같은 프로젝트의 운영 GKE 클러스터들에 대한 Kubernetes 쓰기 권한까지 함께 생겼습니다. RBAC 감사에는 아무것도 나오지 않았습니다.

교훈. 운영 클러스터는 전용 프로젝트에 두고, 기본 역할(Owner·Editor)을 사람에게 주지 마세요. GKE 권한 감사에는 항상 IAM을 포함합니다.

Contributor가 로컬 관리자 인증서로 AKS를 장악했다

원인. 리소스 그룹 Contributor를 가진 외주 인력이 az aks get-credentials --admin으로 로컬 관리자 kubeconfig를 받았습니다. Entra·Azure RBAC 설정과 무관하게 cluster-admin이었습니다.

교훈. --disable-local-accounts와 함께, 클러스터 리소스에 대한 Contributor·Owner 할당을 최소화하세요(실습 2).

IAM 관리자가 액세스 엔트리로 스스로 cluster-admin이 됐다

원인. 계정의 IAM 관리 권한을 가진 사람이 디버깅을 이유로 자신에게 ClusterAdminPolicy 액세스 엔트리를 붙였습니다. 클러스터 RBAC 감사에는 보이지 않았고, CloudTrail에만 기록이 있었습니다.

교훈. ①층 메타 권한(eks:CreateAccessEntry·AssociateAccessPolicy)을 SCP·권한 경계로 좁히고, 해당 API 호출을 경보로 두세요(22편).

팀 이동 후에도 이전 팀 네임스페이스를 관리할 수 있었다

원인. 오프보딩 절차가 RBAC RoleBinding만 지웠고, Azure RBAC의 네임스페이스 범위 Admin 할당이 남아 있었습니다.

교훈. 층별 회수 체크리스트와 who-can-everywhere.sh 같은 통합 조회 도구를 두세요(7장).

OpenShift에 주인 없는 Project가 수백 개

원인. self-provisioner 기본값 때문에 로그인한 누구나 Project를 만들었고, 쿼터 없는 테스트 Project가 자원을 점유했습니다.

교훈. self-provisioner를 끄고 Project 생성을 요청 절차(또는 GitOps)로 바꾸거나, 요청 템플릿에 쿼터·기본 정책을 넣으세요.

한 앱을 위해 연 privileged SCC가 다른 워크로드에도 쓰였다

원인. 레거시 앱을 위해 default SA에 privileged SCC를 줬고, 같은 네임스페이스의 모든 Pod(기본 SA 사용)가 특권으로 뜰 수 있게 되었습니다.

교훈. SCC는 전용 SA에만, 가능한 가장 좁은 SCC(anyuid 등)로. oc adm policy who-can use scc를 정기 점검하세요(21편).

Rancher에서 사용자를 지웠는데 다운스트림 접근이 남았다

원인. 그 사용자의 권한 일부가 다운스트림 클러스터에 kubectl로 직접 만든 RoleBinding(사용자 IdP 이름 기준)과 클러스터 자체 OIDC 연결로 주어져 있었습니다. Rancher는 자기가 만든 바인딩만 지웁니다.

교훈. Rancher를 쓰면 Rancher를 유일한 권한 원천으로 정하고, 다운스트림 직접 RBAC을 금지·감시하세요.

장애 중 권한을 줬는데 몇 분간 반영되지 않았다

원인. AKS Azure RBAC 역할 할당이 전파되는 데 시간이 걸렸고, 담당자는 설정이 잘못된 줄 알고 여러 번 바꿨습니다.

교훈. 장애 대응용 권한은 미리 준비된 그룹에 사람을 넣는 방식(PIM 등)으로, 반영 지연을 런북에 적어 두세요.

이 편의 핵심 다섯 줄

  1. 매니지드 클러스터의 권한은 ① 클라우드·플랫폼 제어, ② 벤더 인가기, ③ Kubernetes RBAC의 세 층이며, ②와 ③은 합집합이고 ①은 ②③을 바꿀 수 있는 메타 권한입니다.
  2. EKS는 IAM 주체를 액세스 엔트리로 연결하고 액세스 정책(②)과 Kubernetes 그룹(③)으로 권한을 주며, 액세스 엔트리를 만들 수 있는 IAM 권한이 곧 잠재적 관리자 권한입니다.
  3. AKS는 Azure RBAC for Kubernetes와 RBAC 중 고르거나 함께 쓰고, 로컬 계정을 닫아 Cluster Admin 자격 증명 우회를 막아야 합니다.
  4. GKE는 IAM과 RBAC의 합집합이며 IAM은 프로젝트 단위라 네임스페이스로 좁힐 수 없으므로 “IAM은 clusterViewer, 권한은 RBAC”이 기본입니다.
  5. OpenShift는 Project·self-provisioner·cluster-reader·SCC(use 동사), Rancher는 글로벌·클러스터·프로젝트 역할 템플릿이 RBAC으로 내려가며, 권한 원천을 하나로 정하고 층별 회수 절차를 둬야 합니다.
