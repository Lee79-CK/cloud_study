Terraform & Ansible 강의 · Level 4 Ansible 심화·운영 · 22편 / 26편 (Level 4 마지막) · 시리즈 목차

리눅스 밖의 세계도 같은 원칙으로 네트워크·Windows·Kubernetes 자동화 — cisco·junos resource module, Windows 모듈과 WinRM/SSH, kubernetes.core로 매니페스트·Kustomize·Helm, 각각의 함정

MSP가 맡는 고객 환경에는 리눅스 서버만 있지 않습니다. 스위치·방화벽·라우터, Windows 서버, 그리고 Kubernetes 클러스터가 함께 있습니다. Ansible은 이 셋을 같은 플레이북·인벤토리·Vault·AWX로 다룰 수 있지만, 모듈이 어디서 실행되고, 무엇이 멱등성을 책임지는지가 리눅스와 다릅니다. 이번 편은 세 영역을 실제로 돌려 보며 그 차이에서 생기는 함정을 확인합니다. 특히 네트워크 resource module의 overridden이 목록에 없는 인터페이스를 꺼 버리고, 두 번째 실행에도 계속 shutdown을 보내는 것을 실측으로 보여 줍니다.

네트워크

장비에 Python 없음 — 모듈은 컨트롤 노드에서 돌고 CLI·NETCONF로 명령을 보낸다

Windows

Python 대신 PowerShell — WinRM 또는 OpenSSH, 경로·인코딩·재부팅이 다르다

Kubernetes

서버가 아니라 API — 선언한 상태를 API에 맞추고, 실제 수렴은 클러스터가 한다

이번 편의 목표와 실측 방법

이번 편을 마치면

  • 네트워크 자동화의 연결 방식(network_cli·netconf·httpapi)과 resource module의 state 8가지를 구분해 씁니다.
  • merged·replaced·overridden의 차이를 장비에 보내는 명령으로 설명하고, overridden의 위험을 압니다.
  • Windows의 WinRM·OpenSSH 연결과 인증 방식을 고르고, 경로·재부팅·인코딩 같은 Windows 고유의 함정을 피합니다.
  • kubernetes.core로 매니페스트·Kustomize·Helm을 배포하고, API 대상 자동화의 멱등성·드리프트·diff 특성을 압니다.
영역실측 방법한계
네트워크 (cisco.ios 11.6.0, junipernetworks.junos 11.0.0, ansible.netcommon 8.7.1)실제 장비 대신 SSH로 IOS 명령 일부를 흉내 내는 가짜 장비(Python·paramiko, 인터페이스 설정만)를 만들어 network_cli로 접속. parsed·rendered는 장비 없이 실행실제 IOS의 모든 동작을 재현하지는 않는다. 단, 4장의 overridden 동작은 모듈 코드에서 원인을 확인해 가짜 장비 탓이 아님을 검증
Windows (ansible.windows 3.8.0, community.windows 3.3.0)Windows 호스트가 없어 플레이북 문법·lint·모든 모듈 인자를 모듈 문서와 대조, YAML 경로 함정·pywinrm 누락은 실제 실행Windows에서의 실행 결과는 문서 기준
Kubernetes (kubernetes.core 6.6.0, Python kubernetes 37.0.1)k3s v1.37.1 컨트롤 플레인(kubelet 없이)에 실제 배포·멱등성·드리프트·diff·Kustomize노드가 없어 파드는 뜨지 않는다(READY 0/2). Helm 실행 파일을 받을 수 없어 helm 모듈은 오류 메시지까지만

3네트워크: resource module

“명령을 보내라”가 아니라 “이 인터페이스들은 이런 상태여야 한다”

예전 네트워크 자동화는 ios_config: lines: [...]처럼 명령 줄을 보내는 방식이었습니다. 14편의 command 모듈처럼 장비의 현재 상태를 모르므로 멱등성을 사람이 챙겨야 했습니다. resource module(ios_interfaces, ios_vlans, ios_acls, junos_interfaces …)은 현재 설정을 읽어 구조화된 데이터로 만들고(have), 원하는 상태(want)와 비교해 필요한 명령만 만듭니다. 이때 state가 “비교 방식”을 정합니다.

state의미장비 접속
gathered현재 설정을 구조화된 데이터로 읽기예
merged적은 속성만 더하거나 바꾼다. 적지 않은 것은 그대로예
replaced적은 리소스(인터페이스)에 한해 적은 대로 맞춘다 — 그 리소스의 적지 않은 속성은 지운다예
overridden장비 전체를 적은 대로 — 목록에 없는 리소스는 기본값으로 되돌린다예
deleted적은 리소스(없으면 전체)의 설정을 지운다예
rendered장비에 보낼 명령(XML)만 만든다아니오
parsed설정 텍스트(백업 파일)를 구조화된 데이터로아니오
purged (일부 모듈)리소스 자체를 완전히 제거예
iface.yml — 같은 원하는 상태를 세 가지 state로
- name: 인터페이스 설정 — state 비교
  hosts: ios
  gather_facts: false
  vars:
    wanted:
      - name: GigabitEthernet0/0      # 설명은 적지 않고 MTU만
        mtu: 9000
      - name: GigabitEthernet0/2
        description: NEW-WEB
        enabled: true
  tasks:
    - name: "인터페이스 ({{ st }})"
      cisco.ios.ios_interfaces:
        config: "{{ wanted }}"
        state: "{{ st }}"
      register: r
    - name: 장비에 보낸 명령
      ansible.builtin.debug:
        var: r.commands

state 비교 — 시작 설정은 같고 state만 바꿔 실행한 실측 결과

# 시작 설정 (가짜 장비의 기본값)
interface GigabitEthernet0/0      description UPLINK-TO-CORE    no shutdown
interface GigabitEthernet0/1      description OLD-SERVER        no shutdown
interface GigabitEthernet0/2                                     shutdown
# 원하는 상태: Gi0/0 은 MTU 9000 (설명은 적지 않음), Gi0/2 는 설명 NEW-WEB + 켜기. Gi0/1 은 목록에 없음

4네트워크: overridden의 함정 외

“목록에 없는 것”을 어떻게 다루는지가 사고를 가른다

# 실측: overridden 1회차가 보낸 명령
interface GigabitEthernet0/1          ← 목록에 없던 인터페이스
no description OLD-SERVER
shutdown                              ← 운영 중이던 서버 포트가 꺼진다
interface GigabitEthernet0/0
no description UPLINK-TO-CORE
mtu 9000
interface GigabitEthernet0/2
description NEW-WEB
no shutdown

# 실측: overridden 2회차·3회차 — 이미 꺼진 Gi0/1 에 계속 shutdown
r.commands: ["interface GigabitEthernet0/1", "shutdown"]      changed=1   (매번)
# 원인 확인: cisco.ios 11.6.0 의 interfaces 설정 비교 코드 (발췌)
        elif not want and self.state == "overridden":
            self.addcmd(have, "enabled", False)          ← 현재 상태와 무관하게 항상 shutdown 추가
        elif not want and self.state == "deleted":
            if have_enabled:                             ← deleted 는 켜져 있을 때만
                self.addcmd(have, "enabled", False)
overridden은 “전체 설정 대장”이 있을 때만

overridden은 그 장비의 모든 인터페이스를 목록에 적었을 때만 안전합니다. 목록이 일부뿐이면 나머지 포트를 꺼서 장애를 냅니다(실측: 운영 서버 포트 Gi0/1 shutdown). 또 이 버전에서는 목록에 없는 인터페이스에 대해 매번 shutdown을 보내 2회차 changed가 0이 되지 않았습니다(코드로 확인 — 14편 이후의 기준으로 보면 결함). 실무 원칙: 평소 변경은 merged, 특정 포트를 완전히 맞출 때 replaced, overridden은 장비 전체 설정을 소스 오브 트루스(넷박스 등)에서 생성하는 성숙한 환경에서만, 그것도 먼저 rendered·check로 명령을 검토한 뒤 씁니다.

장비 없이: parsed와 rendered

offline.yml (IOS)
- name: 장비 없이 — parsed 와 rendered
  hosts: localhost
  gather_facts: false
  vars:
    ansible_network_os: cisco.ios.ios
    ansible_connection: ansible.netcommon.network_cli   # 연결 방식은 지정하되, parsed·rendered는 실제로 접속하지 않는다
  tasks:
    - name: 백업해 둔 설정 텍스트를 구조화된 데이터로 (parsed)
      cisco.ios.ios_interfaces:
        running_config: "{{ lookup('ansible.builtin.file', 'r1-backup.cfg') }}"
        state: parsed
      register: p

    - name: 구조화된 데이터를 장비 명령으로 (rendered)
      cisco.ios.ios_interfaces:
        config:
          - name: GigabitEthernet0/3
            description: DB-REPLICA
            mtu: 9000
            enabled: true
        state: rendered
      register: rd

    - name: 결과
      ansible.builtin.debug:
        msg:
          parsed: "{{ p.parsed }}"
          rendered: "{{ rd.rendered }}"
junos_rendered.yml
- name: Junos — 같은 의도를 Junos 형식으로 (장비 없이)
  hosts: localhost
  gather_facts: false
  vars:
    ansible_network_os: junipernetworks.junos.junos
    ansible_connection: ansible.netcommon.netconf
  tasks:
    - name: 구조화된 데이터 → Junos 설정 (rendered)
      junipernetworks.junos.junos_interfaces:
        config:
          - name: ge-0/0/3
            description: DB-REPLICA
            mtu: 9000
            enabled: true
        state: rendered
      register: rd

    - name: 결과
      ansible.builtin.debug:
        var: rd.rendered
# 실측: IOS parsed (백업 파일 → 데이터) / rendered (데이터 → 명령)
parsed:   [{description: UPLINK-TO-CORE, enabled: true, name: GigabitEthernet0/0},
           {description: OLD-SERVER, enabled: true, name: GigabitEthernet0/1}]
rendered: ["interface GigabitEthernet0/3", "description DB-REPLICA", "mtu 9000", "no shutdown"]

# 실측: Junos rendered — 같은 의도가 NETCONF XML 로
<nc:interfaces …><nc:interface><nc:name>ge-0/0/3</nc:name><nc:description>DB-REPLICA</nc:description>
<nc:mtu>9000</nc:mtu><nc:enable/></nc:interface></nc:interfaces>

rendered는 변경 요청서에 붙일 “장비에 들어갈 명령”을 장비 없이 만들 수 있고, parsed는 백업 파일을 데이터로 바꿔 15편 필터로 비교·보고서를 만들 수 있습니다. 같은 데이터 모델(name·description·mtu·enabled)이 IOS에서는 CLI 명령으로, Junos에서는 NETCONF XML로 바뀌는 것이 resource module의 장점입니다.

junipernetworks.junos 설치

Juniper 컬렉션은 ansible 14.5.0 패키지에 포함되어 있지 않아(실측: 패키지 안에 없음) GitHub 릴리스 태그(v11.0.0)에서 설치했습니다. 네트워크 컬렉션은 벤더·커뮤니티 유지보수 상태가 제각각이므로, 고객 장비 플랫폼별로 컬렉션의 최근 릴리스와 지원 OS 버전을 먼저 확인하고 EE에 고정합니다(16·20편).

backup.yml — 변경 전 백업
- name: 설정 백업 (변경 전 습관)
  hosts: ios
  gather_facts: false
  tasks:
    - name: 실행 중 설정을 컨트롤 노드에 저장
      cisco.ios.ios_config:
        backup: true
        backup_options:
          dir_path: ./backups
          filename: "{{ inventory_hostname }}-{{ lookup('ansible.builtin.pipe', 'date +%Y%m%d') }}.cfg"
# 실측
changed: [r1]                                  ← 백업 태스크는 매번 changed 로 보고된다 (정기 실행 보고에서 걸러 볼 것)
$ ls backups/  →  r1-20261023.cfg

5네트워크 운영 수칙

서버보다 실수의 반경이 크다 — 장비 하나가 수백 대의 통신을 끊는다

수칙방법
변경 전 백업은 습관모든 변경 플레이의 첫 태스크로 ios_config backup (위 실측)
보낼 명령을 먼저 본다rendered 또는 check 모드 → 변경 요청서에 첨부
되돌릴 장치Junos commit confirmed(정해진 시간 안에 확인이 없으면 자동 롤백) — junos_config의 confirm 옵션. IOS는 archive·configure replace
저장IOS는 running-config만 바꾸면 재부팅 시 사라진다 → ios_config save_when: modified
관리 경로부터 잃지 않기관리 인터페이스·ACL·AAA 변경은 마지막에, 장비 한 대씩(serial: 1), 콘솔 접근 확보 후

10Kubernetes의 함정

“Ansible이 맞췄다”와 “클러스터가 그렇게 됐다”는 다르다

함정설명대책
API에 맞춘 것 ≠ 서비스가 뜬 것실측: Deployment는 changed·ok인데 READY 0/2. Ansible은 객체를 만들었을 뿐wait: true + wait_condition, 또는 k8s_info로 readyReplicas 확인(15편 until)
HPA와 replicas 싸움실측처럼 Ansible은 replicas를 2로 되돌린다 — HPA가 늘린 값도 되돌려 버린다HPA를 쓰는 Deployment는 매니페스트에서 replicas를 빼거나 HPA만 관리
목록 정의의 diff 미표시실측 (8장 B)검토가 중요한 리소스는 태스크를 나누거나 loop로 하나씩
CRD 순서CRD와 그 CR을 한 번에 적용하면 “no matches for kind”CRD 적용 → wait(Established) → CR
Secret매니페스트에 평문, diff·결과에 값이 나옴no_log·diff: false(19편), 외부 비밀(External Secrets 등)로 클러스터가 직접 가져오게
컨텍스트 착오kubeconfig의 현재 컨텍스트가 운영 클러스터태스크마다 context·kubeconfig 명시, 운영 kubeconfig는 AWX 자격증명(21편)으로만

네트워크는 “읽기”부터

고객 네트워크 자동화는 gathered·백업·parsed로 현황 보고서를 만드는 것부터 시작합니다. 장비별 설정 표준(NTP·SNMP·로그 서버·배너)과의 차이를 보고하고, 쓰기는 merged로 저위험 항목부터. 네트워크팀이 rendered 결과를 검토하는 절차를 둡니다.

Windows는 GPO와 경계를 나눈다

도메인 환경에서는 GPO가 이미 많은 설정을 강제합니다. Ansible이 같은 레지스트리를 바꾸면 GPO가 되돌립니다. GPO가 관리하는 것과 Ansible이 관리하는 것(역할 설치·앱 배포·서버별 설정)을 표로 합의합니다.

Kubernetes는 플랫폼 팀의 도구를 존중

고객이 Argo CD·Helm을 쓰고 있다면 Ansible은 클러스터 준비(네임스페이스·RBAC·쿼터·GitOps 설치)와 클러스터 밖 연동(DNS·인증서·모니터링 등록)을 맡습니다. 앱 매니페스트를 두 도구가 관리하지 않게 합니다.

하나의 EE, 하나의 AWX

네트워크(ansible-pylibssh·ncclient), Windows(pywinrm·Kerberos), Kubernetes(kubernetes·helm) 의존성을 MSP 공통 EE에 넣고(20편), AWX에서 자격증명 유형만 다르게 하면 세 영역이 같은 감사·RBAC 체계에 들어옵니다(21편).

장비·OS 버전 대장

네트워크 컬렉션·Windows 모듈은 장비 OS·Windows 버전에 따라 동작이 다릅니다. gathered·팩트로 버전 대장을 자동으로 만들어(15편 보고서), 컬렉션 업그레이드 전 영향 범위를 판단합니다.

시험 환경

네트워크는 Containerlab·가상 장비(cEOS·vJunos 등), Windows는 평가판 VM, Kubernetes는 kind·k3s로 랩을 만듭니다. 이 편처럼 장비가 없을 때는 rendered·parsed·문서 대조로 최대한 검증하되, 운영 적용 전에는 반드시 실장비 시험을 거칩니다.
