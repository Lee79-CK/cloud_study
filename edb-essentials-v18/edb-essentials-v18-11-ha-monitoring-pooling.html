비유: 조종사와 부조종사

스트리밍 복제는 부조종사가 조종사의 모든 조작을 실시간으로 따라 하는 것입니다. Failover Manager는 "조종사가 정말 쓰러졌는지"를 관제탑(witness)과 함께 확인하고 부조종사에게 조종간을 넘기는 규정입니다. 무전이 끊겼을 뿐인데 두 사람이 동시에 조종간을 잡으면 안 되므로, 고립된 쪽이 스스로 손을 떼게 하는 것이 펜싱입니다.

2장

스트리밍 복제

주 서버의 walsender 프로세스가 WAL을 실시간으로 보내고, 스탠바이의 walreceiver가 받아 기록하며, startup 프로세스가 재생합니다(2편 프로세스 표). 클러스터 전체가 바이트 단위로 같아지는 물리 복제입니다.

스탠바이 만들기

# 주 서버 준비: 복제 역할, pg_hba.conf의 replication 항목 (10편 pg_basebackup과 같음)
# wal_level = replica (기본), max_wal_senders 여유, hot_standby = on (스탠바이 쪽, 기본)

# 스탠바이 서버에서 (빈 데이터 디렉터리)
pg_basebackup -h db01 -p 5444 -U repl_user \
  -D /var/lib/edb/as18/data -Xstream -P -R -C -S standby_db02
sudo systemctl start edb-as-18
  • -R — standby.signal 파일을 만들고 primary_conninfo(주 서버 접속 정보)를 postgresql.auto.conf에 적어 줍니다.
  • -C -S 이름 — 주 서버에 복제 슬롯을 만들고 그 슬롯을 쓰도록 설정합니다(4장).

상태 확인

-- 주 서버에서: 스탠바이별 진행 위치와 지연
SELECT application_name, client_addr, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       write_lag, flush_lag, replay_lag
FROM   pg_stat_replication;

-- 스탠바이에서
SELECT pg_is_in_recovery();                         -- t
SELECT status, sender_host FROM pg_stat_wal_receiver;
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
시험 포인트

스트리밍 복제는 클러스터 전체를 복제합니다(특정 DB·테이블만 불가). 스탠바이는 읽기 전용이고, 같은 메이저 버전이어야 합니다. 스탠바이 모드 신호는 standby.signal, 일회성 복구는 recovery.signal(10편)입니다. 복제 지연은 주 서버의 pg_stat_replication으로 봅니다.

용어: 스탠바이 쿼리 충돌

스탠바이에서 긴 조회를 돌리는 동안, 주 서버의 VACUUM이 그 조회가 보던 행을 치우는 WAL이 도착하면 충돌이 생깁니다. 스탠바이는 max_standby_streaming_delay(기본 30초)만큼 기다린 뒤 조회를 취소합니다. hot_standby_feedback = on으로 충돌을 줄일 수 있지만, 그 대가로 주 서버의 청소가 늦어집니다(8편 2장).

3장

동기 복제와 synchronous_commit

기본은 비동기 복제입니다. 주 서버는 자기 디스크에 WAL을 쓰면 바로 커밋을 응답하고, 스탠바이로는 뒤따라 보냅니다. 빠르지만 주 서버가 갑자기 사라지면 아직 전송되지 않은 마지막 커밋 몇 건을 잃을 수 있습니다. 동기 복제는 스탠바이가 받았다는 확인까지 기다려 이 손실을 막습니다.

# 주 서버 postgresql.conf — 스탠바이의 application_name으로 지정
synchronous_standby_names = 'FIRST 1 (db02, db03)'   # 목록 순서대로 우선, 1대의 확인을 기다림
# synchronous_standby_names = 'ANY 1 (db02, db03)'   # 둘 중 아무거나 먼저 응답한 1대
synchronous_commit = on

synchronous_commit 단계 비교

단계를 고르면 COMMIT이 어디까지 기다리는지, 무엇이 보장되는지 보여 줍니다. synchronous_standby_names가 설정되어 있다고 가정합니다.

동기 스탠바이가 죽으면 쓰기가 멈춘다

동기 복제에서 확인을 줄 스탠바이가 하나도 없으면, 주 서버의 커밋은 무한정 기다립니다. 그래서 동기 복제는 보통 스탠바이를 2대 이상 두고 ANY 1이나 FIRST 1로 한 대만 확인받게 구성합니다. 반대로 synchronous_standby_names가 비어 있으면 synchronous_commit = on이어도 로컬 디스크 기록만 기다리는 비동기 복제입니다.

4장

복제 슬롯과 승격

복제 슬롯

스탠바이가 잠시 끊겼다 돌아왔을 때 필요한 WAL을 주 서버가 이미 지웠다면 다시 따라갈 수 없습니다. 복제 슬롯은 "이 스탠바이가 받아 갈 때까지 WAL을 지우지 마라"는 예약입니다.

SELECT pg_create_physical_replication_slot('standby_db02');
SELECT slot_name, slot_type, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM   pg_replication_slots;
SELECT pg_drop_replication_slot('standby_db02');   -- 쓰지 않는 슬롯은 반드시 삭제
버려진 슬롯이 디스크를 채운다

스탠바이를 없앴는데 슬롯을 지우지 않으면, 주 서버는 그 슬롯을 위해 WAL을 영원히 보관해 결국 pg_wal 디스크가 가득 찹니다. 논리 복제 슬롯은 8편의 xmin horizon도 붙잡아 VACUUM까지 막습니다. max_slot_wal_keep_size로 슬롯이 붙잡을 수 있는 WAL의 상한을 정해 두세요(초과하면 슬롯이 무효화되어 스탠바이를 다시 만들어야 하지만, 주 서버는 살아남습니다).

승격과 옛 주 서버

pg_ctl promote -D /var/lib/edb/as18/data      # 스탠바이에서
SELECT pg_promote();                         # SQL로 (PG12+)

승격된 스탠바이는 새 타임라인으로 쓰기를 시작합니다(10편 7장). 옛 주 서버는 그 사이 새 주 서버에 없는 WAL을 일부 가지고 있을 수 있어 그대로 스탠바이로 붙일 수 없습니다. pg_rewind로 갈라진 부분을 되감아 맞추거나, pg_basebackup으로 새로 만듭니다. pg_rewind를 쓰려면 wal_log_hints = on 또는 데이터 체크섬이 켜져 있어야 합니다(PG18 initdb 기본으로 충족, 3편).

시험 포인트

"주 서버에 WAL이 계속 쌓여 디스크가 찼다" → 비활성 복제 슬롯(또는 10편의 아카이브 실패)을 의심합니다. 승격은 pg_ctl promote나 pg_promote(), 옛 주 서버 재합류는 pg_rewind입니다.

5장

논리 복제

물리 복제가 "디스크 블록의 변경"을 보낸다면, 논리 복제는 "어느 테이블의 어느 행이 어떻게 바뀌었는가"를 보냅니다. 그래서 테이블 단위로 고를 수 있고, 다른 메이저 버전 사이에서도 동작합니다.

-- 원본(발행자): wal_level = logical (재시작 필요)
CREATE PUBLICATION sales_pub FOR TABLE orders, customers;
CREATE PUBLICATION paid_pub  FOR TABLE orders WHERE (status = 'PAID');   -- 행 필터 (PG15+)

-- 대상(구독자): 테이블 구조는 미리 만들어 둬야 함
CREATE SUBSCRIPTION sales_sub
  CONNECTION 'host=db01 port=5444 dbname=sales user=repl_user'
  PUBLICATION sales_pub;

대상 서버읽기 전용 스탠바이읽기·쓰기 가능한 일반 서버
버전같은 메이저 버전다른 메이저 버전 가능

시험 포인트

논리 복제는 PUBLICATION(발행)과 SUBSCRIPTION(구독)으로 구성되고, 원본에 wal_level = logical이 필요합니다. DDL은 복제되지 않는다는 점이 자주 나옵니다. 2편의 logical replication launcher가 구독용 작업 프로세스를 관리합니다.

6장

EDB Failover Manager (EFM)

스트리밍 복제만으로는 장애를 감지하고 스탠바이를 승격하는 일을 사람이 해야 합니다. EDB Failover Manager는 주·스탠바이 구조에서 이를 자동화하는 EDB의 고가용성 도구로, PostgreSQL과 EPAS 모두에 쓸 수 있습니다. 히어로의 극장이 EFM의 동작입니다.

구성

  • 에이전트 — 각 서버에서 EFM 에이전트(Java 프로그램)가 돌며, 서로 JGroups로 통신해 상태를 확인합니다. 주 에이전트, 하나 이상의 스탠바이 에이전트, 그리고 선택적인 witness 에이전트로 이뤄집니다.
  • witness 노드 — DB 없이 판단에만 참여하는 노드입니다. 데이터 노드가 두 대(주+스탠바이 1)뿐일 때 "누가 정말 사라졌나"를 다수결로 정하기 위해 필요하며, 데이터 노드가 세 대 이상이면 따로 두지 않아도 됩니다.
  • 클라이언트 연결 전환 — 가상 IP(VIP)를 새 주 서버로 옮기거나, PgBouncer·Pgpool-II·로드 밸런서와 연동해 애플리케이션이 새 주 서버로 붙게 합니다.
# 설정 파일 (/etc/edb/efm-버전/)
efm.properties   # DB 접속 정보, is.witness, virtual.ip, 장애 판단 시간 등
efm.nodes        # 클러스터 구성원 주소 목록

# 운영 명령
efm cluster-status efm            # 클러스터 상태, 각 노드 역할·LSN·동기 여부
efm promote efm -switchover       # 계획된 역할 전환 (옛 주 서버는 스탠바이로)
efm allow-node efm 10.0.1.13      # 새 노드 참여 허용
efm stop-cluster efm              # 모든 에이전트 중지 (DB는 그대로)
시험 포인트

EFM은 주-스탠바이(스트리밍 복제) 구조의 자동 장애 조치 도구입니다. 장애 시 가장 최신 상태의 스탠바이를 승격하려 하지만, 비동기 복제라면 데이터 손실 가능성은 남습니다. witness는 데이터 노드가 둘일 때 필요합니다. 네트워크에서 고립된 주 서버가 스스로 DB를 멈추게 하는 설정(stop.isolated.primary)이 split-brain 방지의 핵심입니다.

7장

EDB Postgres Distributed (PGD)

EFM 구조에서는 쓰기를 받는 서버가 언제나 한 대이고, 장애 조치에 수십 초 정도가 걸립니다. EDB Postgres Distributed는 여러 노드가 모두 쓰기를 받을 수 있는(multi-master, active-active) 분산 구조로, 노드 하나가 사라져도 거의 끊김 없이 다른 노드로 이어 가는 것을 목표로 합니다.

  • 논리 복제 기반 — 노드끼리 변경을 논리 복제로 주고받습니다. 그래서 노드별 메이저 업그레이드를 하나씩 진행하는 무중단 업그레이드가 가능합니다.
  • 충돌 처리 — 두 노드에서 같은 행을 동시에 바꾸면 충돌이 생기므로, 충돌 감지·해결 규칙과 이를 피하는 설계가 필요합니다.
  • 합의와 연결 라우팅 — Raft 합의로 그룹의 상태를 결정하고, 애플리케이션 연결을 알맞은 노드로 보내는 라우팅 구성요소를 둡니다.
  • 커밋 범위 — 트랜잭션마다 몇 개 노드의 확인을 받을지 등 내구성 수준을 정할 수 있습니다.

PGD는 EDB Postgres Extended(PGE)와 EPAS에서 쓰며(1편), 세부 구성요소 이름과 아키텍처 선택지는 버전에 따라 바뀌므로 공식 문서를 기준으로 확인하세요. 이 시험에서는 EFM과의 차이를 구분하는 수준이면 충분합니다.

Postgres Enterprise Manager (PEM)

PEM은 EDB의 웹 기반 모니터링·관리 도구입니다. 여러 서버의 Postgres를 한 화면에서 보고, 임계치 알림을 받고, 성능 문제를 분석합니다.

  • PEM 서버 — 수집한 데이터를 저장하는 Postgres 데이터베이스와 웹 화면으로 구성됩니다.
  • PEM 에이전트 — 감시 대상 서버마다 설치되어 OS와 DB 지표를 정해진 주기로 수집(probe)해 PEM 서버로 보냅니다.
  • 기능 — 대시보드, 알림(이메일·웹훅 등), 쿼리 분석(SQL Profiler), 성능 진단, 설정 튜닝 도우미, 용량 추세 분석, 로그 분석 등.

1편의 Hybrid Manager도 여러 환경의 Postgres 관측 기능을 제공합니다. 이 시험에서는 PEM이 "에이전트 기반 중앙 모니터링·관리 도구"라는 점을 기억하면 됩니다.

시험 포인트: 도구 역할 한 줄 정리

EFM = 주-스탠바이 자동 장애 조치 · PGD = 다중 쓰기 분산 고가용성 · PEM = 모니터링·관리 · PgBouncer = 커넥션 풀링 · Pgpool-II = 풀링 + 읽기 분산 · Barman / pgBackRest = 백업·PITR(10편). 선택지에서 이 역할을 바꿔 놓은 문장이 함정으로 나옵니다.
