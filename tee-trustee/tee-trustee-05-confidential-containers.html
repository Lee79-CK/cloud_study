Confidential Containers 전체 지도

지금까지 배운 TEE, 원격 증명, GPU 보호를 Kubernetes 파드 한 개에 담으면 무엇이 필요할까요? 그 답이 CoCo입니다. 이번 편에서는 부품 하나하나의 이름과 자리를 지도로 그립니다.

파드 해부도: 어디까지가 믿을 수 있는 영역인가 (부품을 눌러보세요)일반 컨테이너
호스트 · 클러스터 쪽
파드 VM
0

시작하기 전에

1~4편은 하드웨어와 원리의 이야기였습니다. 이번 편부터는 그 위에 올라가는 소프트웨어로 넘어갑니다. 실제 고객 환경은 대부분 Kubernetes이고, 운영팀은 "VM을 만든다"가 아니라 "파드를 배포한다"고 생각합니다. 그래서 TEE를 파드 단위로 쓸 수 있게 만드는 Confidential Containers(CoCo)가 이 시리즈의 소프트웨어 중심이 됩니다.

🎯이번 편을 마치면

  • CoCo 파드의 부품 이름과 자리를 지도로 그릴 수 있습니다.
  • 기밀 파드가 뜨는 8단계를 설명할 수 있습니다.
  • 에이전트 정책과 Init-Data가 왜 필요한지 말할 수 있습니다.
  • 이미지와 시크릿을 TEE 안으로 안전하게 들여오는 방법을 고를 수 있습니다.
  • 베어메탈 방식과 peer pods 방식의 차이를 설명할 수 있습니다.

🔗이어지는 개념

  • 1편 9장의 TCB 스택에서 "기밀 컨테이너" 탭이 바로 이번 편입니다.
  • 2편 12장 보고서의 MRCONFIGID·HOST_DATA가 8장에서 쓰입니다.
  • 3편의 Attestation Agent와 RCAR가 5장, 10장에서 실제 모습으로 나옵니다.
  • KServe 강의의 InferenceService도 결국 파드이므로 9편에서 이 지도 위에 올라갑니다.
1

CoCo가 지키려는 것

CoCo의 목표를 한 문장으로 하면 이렇습니다. "Kubernetes 파드를 기밀 VM 안에서 실행해서, 인프라 운영자뿐 아니라 클러스터 관리자도 파드 안의 데이터를 볼 수 없게 한다."

여기서 중요한 단어는 클러스터 관리자입니다. 일반 기밀 VM 위에 Kubernetes를 올리면 하이퍼바이저와 클라우드 운영자는 막을 수 있지만, kubectl exec 권한이 있는 클러스터 관리자는 여전히 파드 안에 들어갈 수 있습니다(1편 9장). CoCo는 이 사람까지 TCB에서 빼려고 합니다.

등장인물하는 일CoCo에서 믿는가
인프라 운영자서버, 하이퍼바이저, 호스트 OS 관리 (클라우드 사업자, MSP)믿지 않음
클러스터 운영자Kubernetes 컨트롤 플레인, 노드, 네트워크 관리믿지 않음
워크로드 소유자파드를 만들고, 데이터와 키의 주인 (고객사, 모델 개발사)믿음 (본인)
이미지 제공자컨테이너 이미지를 빌드하고 서명서명으로 검증
Trustee 운영자KBS·AS·RVPS 운영과 정책 관리워크로드 소유자 쪽이어야 함 (3편 13장)

CoCo 문서는 이런 역할을 페르소나(persona)로 나눠 신뢰 모델을 설명합니다. 같은 회사의 같은 사람이 여러 역할을 맡을 수도 있지만, 역할별로 "누구를 믿지 않는가"를 분명히 해야 설계가 흔들리지 않습니다.

MSP에게 이 표가 의미하는 것

MSP는 보통 표의 첫 두 줄, 인프라 운영자와 클러스터 운영자입니다. CoCo를 도입한다는 것은 고객에게 "우리가 클러스터를 운영하지만, 우리도 파드 안은 못 본다"고 약속하는 것입니다. 그 약속이 진짜가 되려면 6~10장의 장치들이 모두 제대로 설정되어야 합니다.

2

출발점: Kata Containers

CoCo는 맨땅에서 시작하지 않았습니다. Kata Containers라는, 파드를 가벼운 VM 안에서 실행하는 기존 오픈소스 런타임 위에 지어졌습니다.

비유: 사무실 세 가지
  • 일반 컨테이너(runc): 큰 사무실을 칸막이로 나눈 것. 같은 건물 관리인(호스트 커널)이 모든 칸을 관리하고, 칸막이를 넘으면 옆 칸이 보입니다.
  • Kata Containers: 팀마다 독립 사무실을 준 것. 벽이 튼튼해서 옆 팀은 못 넘어옵니다. 하지만 사무실 벽은 투명 유리라 건물 관리인(하이퍼바이저)은 밖에서 다 봅니다.
  • Confidential Containers: 독립 사무실의 벽을 불투명 유리로 바꾸고, 출입 기록을 공증받는 것. 건물 관리인은 전기를 끊을 수는 있지만 안은 못 봅니다.
구분runcKataCoCo
격리 단위리눅스 네임스페이스·cgroup파드마다 VM파드마다 기밀 VM
커널호스트 커널 공유파드 전용 게스트 커널파드 전용 게스트 커널 (측정됨)
호스트가 메모리를 보나봄봄못 봄
컨테이너 이미지호스트가 받아서 펼침호스트가 받아서 공유TEE 안에서 받음 (guest pull)
원격 증명없음없음있음 (Attestation Agent ↔ Trustee)
막아주는 상대다른 파드 (일부)다른 파드, 컨테이너 탈출다른 파드, 호스트, 클러스터 관리자
3

RuntimeClass: 한 줄의 스위치

개발자 입장에서 CoCo의 시작은 매우 간단합니다. 파드 정의에 runtimeClassName 한 줄을 넣는 것입니다. Kubernetes는 이 이름을 보고 "이 파드는 일반 runc가 아니라 특정 Kata 런타임으로 띄워라"라고 노드에 전달합니다.

apiVersion: v1 kind: Pod metadata: name: llm-inference spec: runtimeClassName: kata-qemu-tdx # ← 이 한 줄이 "TDX 기밀 VM에서 띄워라" containers: - name: vllm image: registry.example.com/vllm@sha256:3f1a… # 태그 대신 digest로 고정 (7장)
RuntimeClass 예뜻
kata-qemu-tdxIntel TDX 기밀 VM에서 실행
kata-qemu-snpAMD SEV-SNP 기밀 VM에서 실행
kata-qemu-nvidia-gpu-tdx / -snpGPU를 붙인 기밀 VM (12장)
kata-qemu-coco-devTEE 하드웨어 없이 CoCo 흐름을 연습하는 개발용 (보호 없음)
kata-remotepeer pods 방식으로 클라우드 기밀 VM에 실행 (11장)

RuntimeClass 이름은 설치 방법과 버전에 따라 달라질 수 있습니다. 클러스터에서 kubectl get runtimeclass로 실제 이름을 확인하세요.

한 줄의 무게

이 한 줄은 클러스터 관리자도 바꿀 수 있습니다. 관리자가 몰래 runtimeClassName을 지우면 파드는 일반 runc로 떠버립니다. 그러면 어떻게 될까요? TEE가 아니므로 증명에 실패하고, Trustee가 키를 주지 않습니다. 파드는 떠 있지만 암호화된 모델을 열 수 없는 빈 껍데기가 됩니다. CoCo의 보안은 "설정이 바뀌지 않는다"가 아니라 "설정이 바뀌면 키를 못 받는다"에 기대고 있습니다. 이 원리가 이번 편 전체에 반복됩니다.

4

기밀 파드가 뜨기까지

kubectl apply부터 애플리케이션이 모델 키를 받을 때까지를 8단계로 나눴습니다. 각 단계가 호스트 쪽에서 일어나는지 TEE 안에서 일어나는지 눈여겨보세요.

흐름의 핵심

1~3단계는 믿지 않는 쪽(호스트, 클러스터)이 진행합니다. 그래서 이들이 무엇을 바꿔치기하더라도 3단계의 측정과 5단계의 정책 검사, 6·8단계의 증명에서 걸리도록 설계되어 있습니다. 믿지 않는 쪽에게 일을 시키되, 결과를 TEE 안에서 확인하는 구조입니다.

5

게스트 안의 구성 요소

기밀 파드 VM 안에는 내 컨테이너 말고도 CoCo가 넣어둔 작은 구성 요소들이 있습니다. CoCo 프로젝트에서는 이들을 묶어 guest components라고 부릅니다.

🤖kata-agent

게스트 안에서 컨테이너를 실제로 만들고 실행하는 관리자입니다. 호스트의 kata shim이 보내는 요청(컨테이너 생성, 실행, 로그 등)을 받아 처리합니다. 호스트의 요청을 받는 창구이므로 에이전트 정책으로 단속합니다(7장).

🧾Attestation Agent (AA)

3편의 Attester 소프트웨어입니다. 칩에게 증거를 만들어 달라고 요청하고, RCAR 대화로 Trustee의 KBS와 증명을 진행해 토큰을 받습니다.

🗄️Confidential Data Hub (CDH)

TEE 안의 "기밀 데이터 창구"입니다. KBS에서 리소스를 받아오고, 봉인된 시크릿을 풀고, 이미지 복호화 키를 가져오고, 보호 스토리지를 준비하는 일을 맡습니다. 필요하면 AA를 통해 증명부터 진행합니다.

🔌API Server REST (ASR)

내 컨테이너가 CDH와 AA를 쓸 수 있도록 파드 안의 로컬 주소로 열어둔 작은 REST 창구입니다. 앱은 이 주소로 "모델 키 주세요"라고 요청하면 됩니다(10장).

📦이미지 처리 (image-rs)

컨테이너 이미지를 TEE 안에서 내려받고, 서명을 검증하고, 암호화된 레이어를 복호화하는 라이브러리입니다(9장).

🖥️내 컨테이너

vLLM 같은 추론 서버입니다. 위의 구성 요소 덕분에 앱은 TEE나 증명을 깊이 몰라도, 로컬 주소로 키를 요청하거나 봉인된 시크릿을 평범한 파일처럼 읽을 수 있습니다.

비유: 대사관

기밀 파드 VM을 외국에 있는 대사관이라고 생각해 보세요. kata-agent는 현지 관청(호스트)의 요청을 받는 민원 창구로, 규정(정책)에 맞지 않는 요청은 거절합니다. AA는 본국(Trustee)에 "우리는 진짜 대사관"이라고 증명하는 담당관이고, CDH는 본국에서 온 외교 행낭(시크릿)을 받아 여는 담당관입니다. ASR은 대사관 직원(앱)이 이 담당관들에게 내선 전화로 연락하는 번호입니다.

6

호스트를 믿지 않으면 생기는 문제

CoCo 파드에서도 호스트와 클러스터는 여전히 일을 합니다. 파드를 배치하고, VM을 띄우고, 네트워크와 볼륨을 연결하고, 로그를 수집합니다. 문제는 이 일꾼들을 믿지 않는다는 점입니다. 어떤 구멍들이 생기는지 하나씩 봅시다.

호스트·클러스터가 하는 일믿지 않으면 생기는 위험CoCo의 대응
kata shim이 kata-agent에 요청 전달"이 컨테이너에서 bash 실행해" 같은 요청으로 TEE 안을 들여다봄에이전트 정책 (7장)
파드 정의(어노테이션, 환경 변수) 전달설정을 몰래 바꿔 공격자 서버로 연결하게 함Init-Data 측정 (8장)
컨테이너 이미지 다운로드이미지를 바꿔치기하거나 이미지 안의 모델을 훔쳐봄guest pull, 서명·암호화 이미지 (9장)
Secret, ConfigMap 전달etcd와 API 서버를 통해 관리자가 내용을 봄봉인된 시크릿, KBS 직접 요청 (10장)
볼륨 마운트호스트 디스크에 쓴 데이터가 평문으로 남음보호 스토리지, VM 안 암호화
로그 수집 (kubectl logs)앱이 찍은 로그가 호스트를 거쳐 나감로그 설계 + 정책으로 제한 (1편 시나리오 C)
네트워크 연결파드로 들어오고 나가는 트래픽을 엿봄TLS를 파드 안에서 종료 (2편 10장)
패턴: 일은 시키되 검사는 안에서

표의 오른쪽 열은 모두 같은 발상입니다. 호스트가 가져온 것은 TEE 안에서 검사하고(정책, 서명, 측정), 호스트를 거쳐야 하는 것은 암호화된 채로만 통과시킵니다(봉인 시크릿, 암호화 이미지, TLS).

7

에이전트 정책: 호스트의 요청을 단속하기

호스트의 kata shim은 TEE 밖에 있지만, 게스트의 kata-agent에게 여러 종류의 API 요청을 보낼 수 있습니다. 에이전트 정책(agent policy)은 kata-agent가 TEE 안에서 이 요청들을 검사하도록 하는 규칙입니다. OPA의 정책 언어인 Rego로 씁니다.

직접 해보기: 정책에 따라 호스트 요청이 어떻게 처리되나

정책은 어떻게 생겼나

아래는 원리를 보여주기 위한 아주 작은 예입니다. "관리용 요청은 허용, 셸 실행은 기본 거부, 승인된 이미지만 생성 허용"이라는 뜻입니다.

package agent_policy # 파드 관리에 필요한 기본 요청은 허용 default CreateSandboxRequest := true default StartContainerRequest := true # kubectl exec 같은 명령 실행은 기본 거부 default ExecProcessRequest := false # 컨테이너 생성은 승인된 이미지 digest일 때만 default CreateContainerRequest := false CreateContainerRequest if { input.OCI.Annotations["io.kubernetes.cri.image-name"] == "registry.example.com/vllm@sha256:3f1a…" }

학습용으로 단순화한 정책입니다. 실제 정책은 훨씬 길고, 입력 필드 이름은 Kata 버전에 따라 다를 수 있습니다.

정책을 손으로 쓰지 않는 법: genpolicy

실제 정책은 컨테이너 생성 요청의 수많은 필드(명령어, 환경 변수, 마운트, 권한)를 하나하나 확인해야 해서 손으로 쓰기 어렵습니다. Kata의 genpolicy 도구는 Kubernetes YAML을 읽고 "이 파드라면 이런 요청만 와야 한다"는 정책을 자동으로 만들어 줍니다.

  1. 이미지를 태그가 아니라 digest로 고정한 파드 YAML을 준비합니다.
  2. genpolicy로 정책을 생성합니다.
  3. 생성된 정책을 사람이 검토하고 필요하면 조정합니다. 자동 생성 결과는 출발점이지 정답이 아닙니다.
  4. 정책을 Init-Data에 넣어 파드와 함께 배포합니다(8장).
정책이 있다고 끝이 아니다

정책은 호스트를 거쳐 파드와 함께 전달됩니다. 관리자가 정책을 느슨하게 바꿔치기하면 어떻게 될까요? 그래서 정책은 반드시 측정되어야 하고, Trustee가 "승인된 정책으로 시작한 파드인가"를 확인해야 합니다. 이것이 다음 장의 Init-Data입니다.

8

Init-Data: 측정되는 설정

기밀 파드에는 게스트 이미지에 미리 넣어두기 어려운 설정이 필요합니다. 어느 KBS에 접속할지, 어떤 에이전트 정책을 쓸지, 이미지를 어디서 받을지 같은 것들입니다. CoCo에서는 이런 설정을 Init-Data라는 TOML 파일로 묶어 파드 어노테이션으로 전달합니다.

version = "0.1.0" algorithm = "sha384" # Init-Data 전체의 해시를 계산할 알고리즘 [data] "policy.rego" = '''…에이전트 정책…''' "aa.toml" = '''…Attestation Agent 설정 (KBS 주소 등)…''' "cdh.toml" = '''…Confidential Data Hub 설정 (KBS 주소, 이미지 설정 등)…'''

이 파일을 gzip으로 압축하고 base64로 인코딩해서 파드의 io.katacontainers.config.hypervisor.cc_init_data 어노테이션에 넣습니다.

핵심: Init-Data의 해시가 증명에 들어간다

  1. Init-Data 전체의 해시를 계산합니다.
  2. 기밀 VM을 시작할 때 이 해시를 하드웨어 레지스터에 기록합니다. TDX는 MRCONFIGID, SEV-SNP는 HOST_DATA입니다. 2편 12장 보고서 탐색기에서 "측정과 별도로 정책에 활용"한다고 했던 바로 그 칸입니다. vTPM 기반 환경에서는 AA가 시작 후 PCR에 확장합니다.
  3. 게스트의 AA는 받은 Init-Data의 해시가 레지스터 값과 같은지 확인하고, 다르면 파드 시작을 거부합니다.
  4. 원격 증명 때 AS는 보고서 속 해시와 Init-Data를 대조하고, 그 내용을 토큰에 담습니다. KBS의 리소스 정책은 이를 보고 키를 줄지 결정합니다.

직접 해보기: 관리자가 Init-Data를 몰래 바꾼다면

학습용 간이 해시입니다. 실제로는 TOML에 지정한 SHA-384 등을 사용합니다.

"KBS 주소를 바꾸는" 공격은 왜 실패할까?

공격자가 Init-Data의 KBS 주소를 자기 서버로 바꾸면, 파드는 공격자의 KBS와 증명을 진행합니다. 공격자의 KBS는 진짜 모델 키를 갖고 있지 않으니 줄 수가 없습니다. 반대로 진짜 KBS에는 이 파드가 접속하지 않거나, 접속하더라도 Init-Data 해시가 승인값과 달라 거부됩니다. 다만 파드가 공격자가 준 가짜 설정이나 가짜 키를 진짜로 믿고 쓰는 위험은 남습니다. 그래서 진짜 KBS의 정책은 물론, 9편과 10편에서 볼 클라이언트 쪽 검증까지 함께 설계해야 합니다.

이미지 보호

LLM 서빙에서는 컨테이너 이미지 자체가 보호 대상인 경우가 많습니다. 모델 가중치를 이미지에 함께 넣거나, 추론 서버 코드에 영업비밀이 있을 수 있기 때문입니다.

CoCo는 호스트 쪽에 nydus snapshotter라는 구성 요소를 두어, 호스트는 이미지를 받는 시늉만 하고 실제 다운로드는 게스트 안에서 일어나게 합니다.

✍️서명된 이미지

이미지 제공자가 서명하고, TEE 안에서 서명을 검증합니다. 검증 정책과 공개키는 KBS에서 받아오므로, 호스트가 검증 기준을 바꿀 수 없습니다. "우리가 빌드한 이미지만 뜬다"를 보장합니다.

🔒암호화된 이미지

이미지 레이어를 암호화해 레지스트리에 올립니다. 복호화 키는 KBS에 있고, 증명에 성공한 TEE만 받습니다. 레지스트리 운영자도, 노드도, 이미지를 훔친 사람도 내용을 볼 수 없습니다. 모델 가중치를 이미지에 넣어 배포할 때 특히 유용합니다.

🔑인증된 레지스트리

비공개 레지스트리 접속 정보도 Kubernetes Secret 대신 KBS에서 받아 TEE 안에서만 씁니다.

📌digest 고정

태그(:latest)는 가리키는 이미지가 바뀔 수 있습니다. 정책과 서명 검증은 digest(@sha256:…) 기준으로 해야 의미가 있습니다.

10

시크릿 다루기

추론 서버에는 모델 복호화 키, 벡터 DB 비밀번호, 외부 API 키 같은 시크릿이 필요합니다. 일반 Kubernetes Secret은 etcd에 저장되고 API 서버를 거쳐 전달되므로 클러스터 관리자가 볼 수 있습니다. CoCo에서 쓸 수 있는 방법을 비교해 보세요.

# 컨테이너 안에서 로컬 ASR 창구로 KBS 리소스 요청 (예시) $ curl http://127.0.0.1:8006/cdh/resource/default/model-key/v1 # → 필요하면 CDH가 AA를 통해 증명을 먼저 진행하고, # KBS가 TEE 공개키로 암호화해 보낸 키를 TEE 안에서 풀어 돌려줌

경로 형식은 저장소/종류/태그입니다. 포트와 경로는 CoCo 버전에 따라 다를 수 있습니다.

12

GPU 파드 연결하기

4편의 GPU 기밀 컴퓨팅을 CoCo 파드에 연결하면 다음과 같이 맞물립니다.

  1. 노드 준비: NVIDIA GPU Operator가 노드의 GPU를 CC 모드로 설정하고, GPU를 VM에 넘길 수 있게(VFIO) 준비합니다.
  2. 런타임 설치: kata-deploy Helm 차트가 GPU용 기밀 RuntimeClass와 GPU 드라이버가 들어간 게스트 이미지를 설치합니다.
  3. 파드 배포: 파드는 GPU용 기밀 RuntimeClass를 지정하고 GPU 리소스를 요청합니다. GPU는 파드 VM 안으로 직접 연결됩니다.
  4. 증명: 파드 VM 안에서 AA가 CPU 증거와 GPU 증거를 함께 모아 Trustee에 제출합니다(4편 9장).
  5. 사용 준비: 증명이 끝나면 GPU를 사용 준비 상태로 바꾸고, 모델 키를 받아 가중치를 GPU에 올립니다.
이름이 비슷한 RuntimeClass 주의

GPU용 Kata 설치에는 기밀용과 비기밀용 RuntimeClass가 함께 들어올 수 있습니다. 예를 들어 이름 끝에 -tdx, -snp가 없는 GPU RuntimeClass는 기밀 VM이 아닐 수 있습니다. 운영 매니페스트에서 RuntimeClass 이름을 반드시 확인하고, 증명 정책이 마지막 방어선이 되게 하세요.

13

설치 지도

7편에서 직접 구축하기 전에, 무엇을 어떤 순서로 설치하는지 큰 그림만 잡아둡니다.

  1. 하드웨어·호스트 준비

    TDX 또는 SEV-SNP가 켜진 BIOS, 지원 커널·펌웨어. GPU를 쓴다면 4편 10장 체크리스트까지.

  2. Kubernetes 클러스터

    containerd 기반의 일반 클러스터. 기밀 파드를 띄울 노드에 라벨을 붙입니다.

  3. Kata·CoCo 런타임

    kata-deploy Helm 차트로 RuntimeClass, shim, 게스트 커널·이미지를 노드에 설치합니다. OpenShift에서는 sandboxed containers 오퍼레이터가 이 역할을 합니다. 클라우드 관리형 Kubernetes에서는 peer pods 구성(cloud-api-adaptor)을 씁니다.

  4. (GPU) NVIDIA GPU Operator

    GPU CC 모드와 VFIO 연결을 관리합니다.

  5. Trustee

    KBS·AS·RVPS를 클러스터 밖이나 신뢰할 수 있는 위치에 설치합니다. Helm, 오퍼레이터, Docker Compose 방식이 있습니다. 6편에서 해부하고 7편에서 구축합니다.

  6. 워크로드

    RuntimeClass, digest 고정 이미지, genpolicy로 만든 정책을 담은 Init-Data, 봉인된 시크릿 또는 KBS 리소스 경로를 갖춘 파드를 배포합니다.

14

오해와 MSP 운영 포인트

오해RuntimeClass만 바꾸면 기밀 컨테이너가 된다.
사실RuntimeClass는 시작일 뿐입니다. 에이전트 정책, Init-Data, guest pull, 시크릿 전달, 증명 정책이 함께 있어야 클러스터 관리자를 TCB에서 뺄 수 있습니다.
오해CoCo 파드에서는 kubectl logs도 안전하다.
사실로그는 호스트를 거쳐 나갑니다. 앱이 프롬프트를 로그에 찍으면 그대로 노출됩니다. 로그 설계가 먼저이고, 정책으로 로그 읽기를 제한할 수도 있습니다.
오해Kubernetes Secret에 키를 넣어도 TEE 안에서 쓰니 괜찮다.
사실Secret은 etcd와 API 서버를 거치므로 클러스터 관리자가 볼 수 있습니다. 봉인된 시크릿이나 KBS 직접 요청을 써야 합니다.
오해genpolicy가 만든 정책은 그대로 운영에 써도 된다.
사실자동 생성 정책은 출발점입니다. 반드시 검토하고, 이미지 digest가 고정되어 있는지 확인해야 합니다.
MSP 운영 포인트
  • 장애 대응: kubectl exec로 들어가 보는 습관이 통하지 않습니다. 앱이 내보내는 지표와 안전한 로그만으로 진단할 수 있게 관측 설계를 미리 해야 합니다.
  • 배포 파이프라인: 이미지 digest → genpolicy → 검토 → Init-Data → Trustee 기준값 등록까지가 하나의 릴리스 단위가 됩니다. 이미지를 바꾸면 정책과 기준값도 함께 바뀝니다(8편).
  • 권한 분리: 클러스터 관리 권한(MSP)과 Init-Data·Trustee 정책 승인 권한(고객)을 분리해야 고객에게 한 약속이 지켜집니다.
  • 비용: 파드마다 VM이 생기므로 메모리 오버헤드와 시작 시간이 늘어납니다. peer pods는 파드 수만큼 클라우드 VM 비용이 발생합니다.

용어 사전

17

정리와 다음 편

  1. CoCo는 파드를 기밀 VM에서 실행해 인프라 운영자와 클러스터 관리자까지 TCB에서 빼는 것을 목표로 합니다.
  2. Kata Containers 위에 지어졌고, 개발자는 runtimeClassName 한 줄로 시작합니다. 설정이 바뀌면 키를 못 받는 구조로 안전을 지킵니다.
  3. 게스트 안에는 kata-agent, AA, CDH, ASR, image-rs가 있고, 각각 요청 단속, 증명, 기밀 데이터 처리, 앱용 창구, 이미지 처리를 맡습니다.
  4. 에이전트 정책은 호스트가 보내는 요청을 TEE 안에서 단속하며, genpolicy로 만들고 사람이 검토합니다.
  5. Init-Data는 정책과 KBS 설정을 담고, 그 해시가 MRCONFIGID·HOST_DATA에 기록되어 증명으로 확인됩니다.
  6. 이미지는 guest pull로 TEE 안에서 받고, 서명·암호화로 바꿔치기와 유출을 막습니다.
  7. 시크릿은 일반 Secret 대신 봉인된 시크릿이나 KBS 직접 요청을 씁니다.
  8. 배포 방식은 베어메탈과 peer pods가 있으며, GPU 기밀 컴퓨팅은 주로 베어메탈에서 GPU Operator와 함께 씁니다.

6편 예고: Trustee 아키텍처 해부

이번 편에서 AA와 CDH가 "KBS에 요청한다"고만 했던 그 상대를 열어봅니다. KBS·AS·RVPS가 각각 어떤 내부 구조를 가지는지, 3편의 RCAR가 실제 API로 어떻게 오가는지, 증명 정책과 리소스 정책을 Rego로 어떻게 쓰는지, 그리고 이번 편 8장의 Init-Data 정보가 토큰에 어떻게 담겨 리소스 정책에서 쓰이는지를 다룹니다.

TEE·Trustee 강의 시리즈 5편. RuntimeClass 이름, 어노테이션, API 경로, 정책 필드는 CoCo·Kata 버전에 따라 다를 수 있습니다. 예시 코드와 시뮬레이션은 학습용으로 단순화했습니다. 실제 구축 시 사용하는 버전의 공식 문서를 확인하세요.
