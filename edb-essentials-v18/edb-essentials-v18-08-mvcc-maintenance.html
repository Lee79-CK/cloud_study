MVCC와 유지보수

1장

  
MVCC의 원리

  
MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)는 한 행의 여러 버전을 동시에 보관해서, 각 트랜잭션이 자기 시점의 버전을 읽게 하는 방식입니다. 그 결과 읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않습니다. 같은 행을 동시에 수정하려는 쓰기끼리만 서로 기다립니다.

  
튜플 헤더의 두 숫자

  
2편 10장에서 본 튜플(행 버전) 헤더에는 트랜잭션 ID(XID) 두 개가 들어 있습니다.

  

    
필드의미

    
      
xmin이 버전을 만든 트랜잭션의 ID

      
xmax이 버전을 지우거나 대체한 트랜잭션의 ID (없으면 0)

      
ctid이 버전의 물리적 위치 (페이지, 줄 번호). UPDATE되면 새 버전을 가리킴

    


SELECT ctid, xmin, xmax, * FROM accounts;   -- 숨은 시스템 컬럼을 직접 볼 수 있음
SELECT txid_current();                      -- 현재 트랜잭션 ID (PG13+: pg_current_xact_id())

  
    
    
  • INSERT — 새 버전을 만들고 xmin에 자기 XID를 적습니다.
    • 
    
  • DELETE — 행을 지우지 않고, 현재 버전의 xmax에 자기 XID를 적습니다.
    • 
    
  • UPDATE — DELETE + INSERT입니다. 옛 버전의 xmax에 표시하고, 새 버전을 따로 씁니다.
    • 
  

  
어떤 트랜잭션이 버전을 볼 수 있는지는 스냅샷(그 순간 어떤 트랜잭션이 커밋됐는지의 목록)과 xmin·xmax를 비교해 판단합니다. 간단히 말해 "만든 트랜잭션이 내 스냅샷 기준으로 커밋됐고, 지운 트랜잭션은 아직 커밋되지 않았거나 없으면" 보입니다. 커밋 여부는 2편의 pg_xact/에 기록되어 있습니다.

  

    시험 포인트
    
"PostgreSQL에서 UPDATE는 기존 행을 그 자리에서 덮어쓴다"는 틀린 문장입니다. 새 버전을 추가하고 옛 버전은 dead tuple로 남습니다. 그래서 UPDATE가 많은 테이블일수록 VACUUM이 중요합니다. Oracle은 옛 값을 undo 영역에 따로 보관하는 방식이라, Oracle 경험자가 자주 헷갈리는 부분입니다.

  

  

    용어: HOT 업데이트 (Heap-Only Tuple)
    
UPDATE가 인덱스에 걸린 컬럼을 바꾸지 않고, 새 버전이 같은 페이지에 들어갈 공간이 있으면 인덱스를 고치지 않고 페이지 안에서만 버전을 연결합니다. 인덱스 쓰기가 줄어 훨씬 빠릅니다. 자주 UPDATE되는 테이블은 fillfactor를 90 정도로 낮춰 페이지에 여유 공간을 남기면 HOT 비율을 높일 수 있습니다. 비율은 pg_stat_user_tables.n_tup_hot_upd로 확인합니다.

  







  
2장

  
dead tuple과 bloat

  
어떤 트랜잭션도 더 이상 볼 수 없게 된 옛 버전을 dead tuple이라고 합니다. 그대로 두면 테이블과 인덱스가 실제 데이터보다 훨씬 커지는데, 이를 bloat(팽창)라고 부릅니다. 스캔할 페이지가 늘어 느려지고, 캐시 효율이 떨어지고, 디스크를 낭비합니다.


SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_vacuum, last_autovacuum, last_analyze, last_autoanalyze
FROM   pg_stat_user_tables
ORDER  BY n_dead_tup DESC
LIMIT  10;

  
dead tuple이 치워지지 않는 원인

  
VACUUM은 "아직 누군가 볼 수도 있는" 버전은 지우지 못합니다. 히어로의 5단계에서 본 상황입니다. 가장 오래된 스냅샷이 기준선(xmin horizon)이 되어, 그보다 뒤에 죽은 버전은 모두 남습니다.

  

    
원인찾는 법

    
      
오래 실행 중인 트랜잭션·쿼리pg_stat_activity의 xact_start, backend_xmin

      
idle in transaction 세션 (BEGIN 후 방치)state = 'idle in transaction'. 5편 idle_in_transaction_session_timeout으로 예방

      
사용하지 않는 복제 슬롯pg_replication_slots의 xmin, active (11편)

      
커밋되지 않은 2단계 커밋 트랜잭션pg_prepared_xacts

      
hot_standby_feedback을 켠 스탠바이의 긴 쿼리스탠바이의 pg_stat_activity (11편)

    


-- 가장 오래된 트랜잭션 찾기
SELECT pid, usename, state, now() - xact_start AS xact_age, backend_xmin, left(query, 60)
FROM   pg_stat_activity
WHERE  backend_xmin IS NOT NULL
ORDER  BY xact_start
LIMIT  5;

  

    현장 사례: "VACUUM을 돌렸는데 용량이 그대로예요"
    
MSP에서 가장 흔한 DB 문의 중 하나입니다. 원인은 대개 두 가지입니다. 첫째, 일반 VACUUM은 공간을 OS에 돌려주지 않고 재사용 가능하게만 표시합니다(3장). 둘째, 며칠째 idle in transaction 상태인 세션이 있어 VACUUM이 아무것도 지우지 못했을 수 있습니다. VACUUM VERBOSE 출력의 "dead row versions cannot be removed yet" 숫자를 확인하고, 위 쿼리로 범인을 찾으세요.

  







  
3장

  
VACUUM과 VACUUM FULL

  

    
VACUUMVACUUM FULL

    
      
하는 일dead tuple 공간을 재사용 가능으로 표시, FSM·VM 갱신, 오래된 XID 동결테이블을 새 파일로 통째로 다시 씀, 인덱스도 재생성

      
디스크 공간OS에 돌려주지 않음 (테이블 끝부분의 빈 페이지만 잘라냄)OS에 돌려줌

      
잠금SHARE UPDATE EXCLUSIVE — 읽기·쓰기와 함께 실행 가능ACCESS EXCLUSIVE — 끝날 때까지 조회도 불가

      
추가 공간거의 없음테이블+인덱스 크기만큼 여유 공간 필요

      
운영 중 사용언제든 (autovacuum이 자동으로)유지보수 창에서만, 드물게

    


VACUUM orders;                        -- 한 테이블
VACUUM (VERBOSE, ANALYZE) orders;     -- 결과 출력 + 통계 갱신
VACUUM (PARALLEL 4) orders;           -- 인덱스 정리를 병렬로
VACUUM (FREEZE) orders;               -- 적극적으로 동결 (5장)
VACUUM;                               -- 현재 DB의 모든 테이블
VACUUM FULL orders;                   -- 주의: 테이블 잠금

# 쉘 도구 (enterprisedb 사용자)
vacuumdb -p 5444 --all --analyze-in-stages --jobs=4

  

    시험 포인트
    
"테이블 파일 크기를 줄여 OS에 공간을 돌려주는 것은?" → VACUUM FULL(또는 CLUSTER). "운영 중 서비스를 멈추지 않고 실행할 수 있는 것은?" → 일반 VACUUM. VACUUM은 트랜잭션 블록 안에서 실행할 수 없습니다. 서비스를 멈추지 않고 bloat를 줄여야 한다면 pg_repack 같은 온라인 재구성 확장을 검토합니다.

  

  

    비유: 주차장 정리
    
VACUUM은 떠난 차의 자리에 "빈자리" 표지를 세워 다음 차가 쓰게 하는 것입니다. 주차장 넓이는 그대로입니다. VACUUM FULL은 모든 차를 새 주차장으로 빈틈없이 옮기고 옛 주차장을 반납하는 것이라, 옮기는 동안 아무도 드나들 수 없습니다.

  







  
4장

  
autovacuum

  
autovacuum launcher(2편)가 autovacuum_naptime(기본 1분)마다 데이터베이스를 돌며, 변경량이 기준을 넘은 테이블에 worker를 보내 VACUUM과 ANALYZE를 수행합니다. autovacuum은 끄지 않는 것이 원칙입니다.

  
언제 동작하나


VACUUM  기준 = autovacuum_vacuum_threshold (50)  + autovacuum_vacuum_scale_factor (0.2)  × 행 수
ANALYZE 기준 = autovacuum_analyze_threshold (50) + autovacuum_analyze_scale_factor (0.1) × 행 수
INSERT  기준 = autovacuum_vacuum_insert_threshold (1000) + autovacuum_vacuum_insert_scale_factor (0.2) × 행 수

  
기본값은 "행의 약 20%가 dead가 되면 VACUUM"입니다. 1천만 행 테이블이면 200만 행이 죽어야 동작하므로, 큰 테이블일수록 너무 늦게 돕니다. PostgreSQL 18은 이런 큰 테이블을 위해 VACUUM 기준의 상한인 autovacuum_vacuum_max_threshold를 추가했습니다(기본 1억).


  
autovacuum 동작 시점 계산기

  

    

      

      

      

      

    

    

  


-- 큰 테이블만 더 자주 돌게 테이블 단위로 조정
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01,
                        autovacuum_analyze_scale_factor = 0.005);
ALTER TABLE orders RESET (autovacuum_vacuum_scale_factor);   -- 되돌리기

  

    
파라미터기본값의미

    
      
autovacuumon전체 켜기·끄기. 꺼도 wraparound 방지용 VACUUM은 강제로 실행됨

      
autovacuum_max_workers3동시에 도는 worker 수

      
autovacuum_naptime1minDB별 점검 주기

      
autovacuum_vacuum_cost_limit / _cost_delay-1(=200) / 2msI/O 부하 조절. 한도만큼 일하면 잠시 쉼. 빠르게 치우려면 limit을 올림

      
log_autovacuum_min_duration10min오래 걸린 autovacuum 기록 (5편)

    

  

    시험 포인트
    
autovacuum은 VACUUM만이 아니라 ANALYZE도 자동으로 수행합니다. 기준식의 기본값(threshold 50, scale factor 0.2 / 0.1)과 "테이블 단위로 ALTER TABLE ... SET으로 바꿀 수 있다"는 점이 자주 나옵니다. 진행 중인 VACUUM은 pg_stat_progress_vacuum 뷰로 확인합니다.

  







  
5장

  
트랜잭션 ID wraparound

  
트랜잭션 ID는 32비트 숫자라 약 42억 개에서 한 바퀴를 돕니다. 비교는 원형으로 이뤄져서, 어떤 XID 기준으로 약 21억 개 앞은 "과거", 21억 개 뒤는 "미래"로 봅니다. 아주 오래된 행을 그대로 두면 언젠가 그 행의 xmin이 "미래"로 뒤집혀 커밋된 데이터가 갑자기 안 보이게 됩니다. 이것이 wraparound 문제입니다.

  
이를 막는 것이 VACUUM의 동결(freeze)입니다. 충분히 오래된 행에 "모든 트랜잭션에게 보이는 과거"라는 표시를 해 두면, 그 행은 XID 비교에서 빠집니다.

  

    
    

      

      

    

  


-- 데이터베이스별·테이블별 나이 확인 (정기 감시 대상)
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
SELECT relname, age(relfrozenxid) FROM pg_class WHERE relkind = 'r' ORDER BY 2 DESC LIMIT 10;

  

    
파라미터기본값의미

    
      
vacuum_freeze_min_age5천만이보다 오래된 행은 VACUUM이 동결

      
vacuum_freeze_table_age1억 5천만테이블 나이가 이보다 많으면 VACUUM이 전체 페이지를 훑는 적극 모드로 동작

      
autovacuum_freeze_max_age2억이 나이를 넘으면 autovacuum이 꺼져 있어도 wraparound 방지 VACUUM을 강제 실행 (변경 시 재시작)

    

  

    한계에 가까워지면
    
남은 여유가 약 4천만 트랜잭션 아래로 내려가면 서버가 경고를 로그와 클라이언트에 보내기 시작하고, 더 가까워지면 데이터 보호를 위해 새 트랜잭션 ID 할당을 거부합니다. 이 상태가 되면 쓰기 작업이 모두 멈추므로 장애와 다름없습니다. 원인은 대부분 2장의 "오래 열린 트랜잭션"이나 "버려진 복제 슬롯"이라 VACUUM이 동결을 못 한 경우입니다. 나이 감시를 MSP 모니터링 항목에 반드시 넣으세요.

  







  
6장

  
ANALYZE와 통계

  
2편 8장의 옵티마이저는 "이 조건에 맞는 행이 몇 개쯤일까"를 추정해 실행 계획을 고릅니다. 그 추정의 근거가 통계이며, ANALYZE가 테이블에서 표본을 뽑아 수집합니다.


ANALYZE orders;                        -- 한 테이블
ANALYZE;                               -- 현재 DB 전체
ANALYZE orders (customer, status);     -- 일부 컬럼만

-- 수집된 통계 보기
SELECT attname, null_frac, n_distinct, most_common_vals, histogram_bounds
FROM   pg_stats
WHERE  tablename = 'orders' AND attname = 'status';

  

    
pg_stats 컬럼의미

    
      
null_fracNULL 비율

      
n_distinct서로 다른 값의 수 (음수면 행 수 대비 비율)

      
most_common_vals / _freqs자주 나오는 값과 빈도

      
histogram_bounds나머지 값의 분포 구간

      
correlation물리적 저장 순서와 값 순서의 상관관계 (인덱스 스캔 비용 추정에 사용)

    

  
    
    
  • 통계 상세도 — default_statistics_target(기본 100). 분포가 복잡한 컬럼은 ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;으로 따로 높입니다.
    • 
    
  • 확장 통계 — 컬럼끼리 상관관계가 강하면(예: 시·군·구) 옵티마이저가 행 수를 크게 틀립니다. CREATE STATISTICS s1 (dependencies) ON city, district FROM addr;
    • 
    
  • 대량 적재 직후 — autovacuum이 돌기 전에 쿼리가 들어오면 옛 통계로 엉뚱한 계획이 나옵니다. 적재 스크립트 마지막에 ANALYZE를 넣으세요.
    • 
  

  

    시험 포인트
    
통계는 pg_statistic 카탈로그에 저장되고 사람이 읽기 좋은 형태는 pg_stats 뷰입니다. VACUUM은 통계를 갱신하지 않지만 VACUUM ANALYZE는 둘 다 합니다. 메이저 업그레이드 후 통계가 없으면 성능이 급락했는데, PostgreSQL 18의 pg_upgrade는 통계를 보존합니다(10편).

  







  
7장

  
EXPLAIN 기초


EXPLAIN SELECT ...;            -- 계획만 (실행 안 함)
EXPLAIN ANALYZE SELECT ...;    -- 실제로 실행하고 측정. DML이면 데이터가 바뀌니 BEGIN ... ROLLBACK으로 감싸기
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) SELECT ...;

인덱스 유지보수와 잠금


REINDEX INDEX orders_pkey;                 -- 인덱스 재생성 (쓰기 차단)
REINDEX INDEX CONCURRENTLY orders_pkey;    -- 서비스 중 재생성 (PG12+, 느리지만 막지 않음)
REINDEX TABLE CONCURRENTLY orders;
CREATE INDEX CONCURRENTLY ON orders (customer);   -- 운영 중 인덱스 추가의 표준
CLUSTER orders USING orders_created_idx;   -- 인덱스 순서로 테이블 재정렬 (전체 잠금)

-- 한 번도 안 쓰인 인덱스 찾기 (쓰기만 느리게 하는 후보)
SELECT indexrelid::regclass, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM   pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC;

  
유지보수 작업과 잠금

  

    
작업잠금동시에 조회동시에 쓰기

    
      
VACUUM, ANALYZESHARE UPDATE EXCLUSIVE가능가능

      
CREATE INDEX CONCURRENTLY, REINDEX CONCURRENTLYSHARE UPDATE EXCLUSIVE가능가능

      
CREATE INDEXSHARE가능불가

      
VACUUM FULL, CLUSTER, ALTER TABLE ... SET TABLESPACE, 대부분의 ALTER TABLEACCESS EXCLUSIVE불가불가

    


-- 누가 누구를 막고 있나
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, state, left(query, 60)
FROM   pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

  

    ALTER TABLE 한 줄이 서비스를 멈추는 이유
    
ACCESS EXCLUSIVE 잠금은 획득을 기다리는 동안에도 뒤에 오는 모든 조회를 줄 세웁니다. 긴 쿼리가 테이블을 쓰고 있는 상태에서 ALTER TABLE을 실행하면, ALTER가 기다리는 사이 새 SELECT들까지 전부 막혀 장애처럼 보입니다. 운영 DDL 전에는 SET lock_timeout = '5s';를 걸어 오래 기다리지 않고 실패하게 하세요(5편).

  

  
EPAS는 워크로드를 분석해 인덱스 후보를 추천하는 Index Advisor 기능도 제공합니다. 설정 방법은 EDB 문서의 Index Advisor 항목을 참고하세요.
