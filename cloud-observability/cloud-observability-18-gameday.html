Cloud 모니터링·로깅 실전 강의 18편 (Level 6. AIOps와 종합, 마지막 편)

종합 실습과 GameDay

17편 동안 만든 관측 플랫폼을 처음부터 다시 세우고, 일부러 장애 다섯 가지를 일으켜 시간을 재며 대응합니다. 마지막으로 이 시리즈의 결과를 MSP가 고객사에 내놓는 표준 산출물 네 가지로 정리합니다.

대상: 1~2년차 클라우드 엔지니어 형식: 종합 실습 3개 + GameDay 5종 예상 소요: 하루 (구축 4~6시간 + GameDay 3시간) 기준: 1~17편 전체
GameDay 진행판시나리오를 고르고 주입과 동시에 시작을 누르세요. 탐지, 원인, 영향, 조치, 기록을 확인할 때마다 표시하면 걸린 시간과 점수가 남습니다. 기록은 이 브라우저에 저장됩니다.

0시작하기 전에

이 편은 새 기술을 배우지 않습니다. 지금까지 배운 것을 한 번에 다시 해 보고, 압박 속에서 실제로 쓸 수 있는지 시험합니다.

학습 목표

  1. Git에 남긴 설정만으로 하이브리드 관측 플랫폼 전체를 처음부터 다시 세울 수 있다.
  2. GameDay를 설계하고 진행하며, 탐지 시간과 대응 품질을 측정할 수 있다.
  3. 다섯 가지 대표 장애에서 알맞은 신호, 도구, 조치를 고를 수 있다.
  4. 알림 보강과 MCP 도구가 대응을 얼마나 빠르게 하는지(또는 어디서 막히는지) 평가할 수 있다.
  5. 아키텍처 정의서, 라벨 표준, 알림 정책, 런북을 고객사에 낼 수 있는 형태로 작성할 수 있다.
이 편의 검증 범위

GameDay 주입기(gameday.sh)는 문법 검사(bash -n)와, 시나리오 2가 고객사 B의 Alloy 설정에 덧붙이는 블록의 alloy validate를 통과했습니다. 시나리오 1과 같은 성격의 장애(결제 오류율 30%)를 로컬 스택에 실제로 넣어, 9편의 Loki Ruler 알림이 Alertmanager를 거쳐 17편 보강기의 사건 묶음이 되기까지 110초가 걸리는 것을 쟀습니다. 이때 Tempo가 내려가 있어 묶음에 트레이스 대신 "Connection refused"가 기록된 것도 그대로 실었습니다. 나머지 시나리오의 기대 수치는 15편(입구 단절 버퍼링), 16편(카디널리티 폭증, 디스크 유실)의 실측을 인용했으며, kind와 VM 전체 환경에서 다섯 시나리오를 처음부터 끝까지 실행하지는 못했습니다.

3GameDay 진행 방법

GameDay는 일부러 장애를 일으켜 사람, 도구, 절차를 함께 시험하는 훈련입니다. 목적은 누가 잘했는지가 아니라 어디가 막히는지 찾는 것입니다.

역할하는 일
진행자시나리오를 비밀로 고르고 gameday.sh로 주입, 시각 기록, 끝나면 복구
대응자 (1~2명)알림을 받은 것처럼 대응. 시나리오 내용을 모르는 상태로 시작
관찰자대응자가 무엇을 열어 보고 어디서 멈췄는지 기록 (사후 검토의 재료)

채점 (시나리오당 10점)

항목2점1점0점
탐지알림으로 목표 시간 안에목표 시간을 넘기거나 대시보드를 보다 발견진행자가 알려 줌
원인근거 신호(지표, 로그 줄, span, 프로파일)를 들어 특정방향은 맞으나 근거 없음틀림
영향고객사, 서비스, 기간, 잃은 데이터를 말함일부없음
조치올바른 조치(4장)와 복구 확인조치는 했으나 확인 안 함잘못된 조치(예: labeldrop)
기록사후 검토 양식(Lab 3) 작성메모만없음

사후 검토는 비난 없는(blameless) 방식으로 합니다. "누가 놓쳤나"가 아니라 "무엇이 그 사람을 놓치게 했나(알림 문구, 대시보드 위치, 런북 부재)"를 찾아 고칠 목록으로 남깁니다.

근거가 되는 실측

S1과 같은 성격의 장애(결제 오류율 30%)를 로컬 스택에 넣자 Loki Ruler의 PaymentErrorLogsHigh가 울려 보강 묶음이 만들어지기까지 110초가 걸렸습니다(9편 규칙: 5분 동안 30줄 초과, for: 1m, 평가 간격 30초, Alertmanager 대기 5초). S2의 폐기 패턴과 labeldrop의 함정, S5의 "버킷에 올라간 것은 남는다"는 16편, S4의 "단절 동안의 데이터는 재전송으로 메워진다(150초 실측)"는 15편의 결과입니다. S4에서 입구가 2시간 이상 끊기면 고객사 쪽 WAL 보관 시간을 넘어 실제로 잃는다는 점도 영향 보고에 넣습니다.

5AIOps 도구로 대응하기

같은 시나리오를 세 가지 방식으로 대응해 걸린 시간을 비교하는 것이 이 GameDay의 두 번째 목적입니다.

방식첫 근거까지잘 맞는 시나리오한계
사람만 (Grafana 클릭)알림 확인 후 대시보드, Explore를 오가며 수 분모두숙련도에 따라 편차가 큼
보강 묶음 (17편)알림과 동시에 (실측: 주입 110초 뒤 묶음 도착, 오류 로그 82줄이 한 패턴으로)S1, S3처럼 서비스 단위 알림서비스 라벨이 없는 알림(S4, S5, 디스크)은 보강하지 않음. 한 출처가 죽으면 그 부분이 빔(실측: Tempo 중단으로 트레이스 항목 실패)
MCP 대화 (17편)질문 한 번에 도구 몇 번S1의 "어느 span이 느린가", S2의 "어느 서비스가 늘었나"를 대화로 좁힐 때읽기 전용이라 조치는 사람. 플랫폼 장애(S4, S5)에는 도구 자체가 같이 아픔

S4, S5는 관제 플랫폼 자체의 장애입니다. 이때 AIOps 도구도 같은 저장소를 보므로 함께 눈이 멉니다. 16편의 메타 모니터링(hub Prometheus 로컬 평가, 외부 데드맨)이 사람에게 직접 알리는 경로가 그래서 필요합니다. GameDay 결과표에 "도구가 도움이 되었나, 방해가 되었나"를 한 줄씩 남겨 챗봇 개선 과제로 넘기세요.

# 알림 정책

## 심각도
| 심각도 | 의미 | 대상 | 응답 목표 |

| ShopHighLatencyWithErrors | Prometheus | critical | 6 |
| PaymentErrorLogsHigh, LogsSilent, UnmaskedCardNumber | Loki Ruler | warning, critical | 9 |

진행자는 아래 주입기로 시나리오를 넣고, 대응자는 히어로의 진행판에서 시간을 잽니다.

~/obs-lab/scripts/gameday.sh 펼치기 
#!/usr/bin/env bash
# GameDay 장애 주입기 (18편). 사용법: gameday.sh <s1|s2|s3|s4|s5> <inject|restore|status>
# 주입 시각을 ~/obs-lab/gameday/log.tsv에 남겨 탐지 시간(MTTD) 계산에 씁니다.
set -euo pipefail
source ~/obs-lab/lab.env
S=${1:?시나리오 s1~s5}; A=${2:?inject|restore|status}
LOG=~/obs-lab/gameday/log.tsv; mkdir -p "$(dirname "$LOG")"
stamp() { printf '%s\t%s\t%s\n' "$(date -u +%FT%TZ)" "$S" "$A" >> "$LOG"; echo "[$(date +%T)] $S $A"; }
faults_vm()   { multipass exec cust-a-web -- sudo bash -c "printf '$1' > /etc/lab-app/faults"; }
faults_edge() { kubectl --context kind-edge -n shop create configmap lab-app-faults --from-literal=faults="$1" \
                  --dry-run=client -o yaml | kubectl --context kind-edge apply -f - >/dev/null; }

case "$S:$A" in
  # S1. 결제 지연 배포: 2.14.0 배포 후 지연 20배와 오류 6% (1편 히어로, 4편 Lab 4, 13편)
  s1:inject)  faults_vm 'payment_version=2.14.0\npayment_latency_factor=20\npayment_error_rate=0.06\n'
              faults_edge $'payment_version=2.14.0\npayment_latency_factor=20\npayment_error_rate=0.06'; stamp ;;
  s1:restore) faults_vm '# 정상\n'; faults_edge '# 정상'; stamp ;;

  # S2. 카디널리티 폭증: 고객사 B 서버에 user_id 라벨 지표 (16편 Lab 2)
  s2:inject)  multipass transfer ~/obs-lab/vm/bomb/bomb.py cust-b-app:/tmp/bomb.py
              multipass exec cust-b-app -- bash -c 'nohup python3 /tmp/bomb.py >/dev/null 2>&1 &'
              multipass exec cust-b-app -- sudo bash -c 'cat >> /etc/alloy/config.alloy <<CFG

// GAMEDAY-S2 BEGIN (gameday.sh가 추가, restore 때 삭제)
prometheus.scrape "gameday_bomb" {
  targets         = [{ __address__ = "localhost:8010", host = "cust-b-app" }]
  scrape_interval = "15s"
  forward_to      = [prometheus.remote_write.msp.receiver]
}
// GAMEDAY-S2 END
CFG
alloy validate /etc/alloy/config.alloy && systemctl restart alloy'; stamp ;;
  s2:restore) multipass exec cust-b-app -- sudo bash -c "sed -i '/GAMEDAY-S2 BEGIN/,/GAMEDAY-S2 END/d' /etc/alloy/config.alloy && systemctl restart alloy; pkill -f /tmp/bomb.py || true"; stamp ;;

  # S3. 로그 수집 중단: cust-a-web의 Alloy 정지 (8편, 9편 LogsSilent)
  s3:inject)  multipass exec cust-a-web -- sudo systemctl stop alloy; stamp ;;
  s3:restore) multipass exec cust-a-web -- sudo systemctl start alloy; stamp ;;

  # S4. 관제 센터 입구 장애: 통합 입구 0대 (15편, 16편 TenantDataAbsent)
  s4:inject)  kubectl --context kind-hub -n ingress scale deploy/msp-ingress --replicas=0; stamp ;;
  s4:restore) kubectl --context kind-hub -n ingress scale deploy/msp-ingress --replicas=2; stamp ;;

  # S5. 저장소 디스크 유실: Mimir PVC 삭제, flush 없이 (16편 Lab 5의 반대)
  s5:inject)  kubectl --context kind-hub -n metrics delete sts mimir --wait
              kubectl --context kind-hub -n metrics delete pvc data-mimir-0; stamp ;;
  s5:restore) kubectl --context kind-hub apply -f ~/obs-lab/apps/hub/mimir-k8s.yaml
              kubectl --context kind-hub -n metrics rollout status sts/mimir --timeout=5m; stamp ;;

  *:status)   column -t -s $'\t' "$LOG" | tail -20 ;;
  *) echo "알 수 없는 조합: $S $A"; exit 1 ;;
esac
chmod +x ~/obs-lab/scripts/gameday.sh

1편의 히어로는 "결제가 느려졌다"는 한 문장에서 시작해 메트릭, 로그, 트레이스, 프로파일을 오가는 조사 흐름을 그림으로 보여 줬습니다. 18편이 끝난 지금, 그 흐름의 모든 단계가 실제로 동작하는 구성 요소로 바뀌었습니다.

Level무엇을 얻었나
1. 기초 (1~2편)전체 지도와 재현 가능한 실습 랩
2. 메트릭과 알림 (3~6편)Prometheus, PromQL, Kubernetes 모니터링, Grafana와 Alertmanager의 고객사 라우팅
3. 통합 로깅 (7~10편)Loki, Alloy, LogQL, 감사 로그를 위한 OpenSearch와 Fluent Bit
4. 트레이스와 신호 연결 (11~13편)OpenTelemetry 게이트웨이, Tempo와 신호 연결, 프로파일과 eBPF
5. 대규모 운영 (14~16편)Mimir 중앙화, 하이브리드 수집과 통합 입구, 운영, 비용, 보안
6. AIOps와 종합 (17~18편)AI가 읽을 수 있는 데이터, 읽기 전용 도구, GameDay와 표준 산출물

시리즈 내내 지킨 원칙은 하나입니다. "작성자가 실행해 본 것과 못 해 본 것을 구분해 적는다." 각 편의 검증 범위 상자에 적은 미검증 항목(주로 kind와 VM 위의 실제 설치, Grafana 화면)은 여러분의 랩에서 처음 확인되는 것들입니다. 결과가 다르면 그것이 가장 값진 사후 검토 재료입니다. 전체 목록과 버전, 포트, 버킷은 시리즈 목차에 모아 두었습니다.

Cloud 모니터링·로깅 실전 강의 18편(마지막). 2026년 10월 기준으로 작성되었습니다. GameDay 주입기는 문법 검사와 Alloy 블록 검사를, S1 성격 장애의 탐지 시간(110초)은 로컬 스택 실측을 근거로 했으며, kind와 VM 전체 환경에서 다섯 시나리오를 끝까지 실행하지는 못했습니다.
