Terraform & Ansible 강의 · Level 3 Ansible 기초 · 16편 / 26편 · 시리즈 목차

한 번 잘 만들어 여러 곳에서 역할과 컬렉션 — role 구조와 실행 순서, 입력 계약(argument_specs), Galaxy·Automation Hub, FQCN, requirements.yml, ansible-lint, 재사용 설계 원칙

15편의 web2.yml은 잘 동작하지만 160줄짜리 파일 하나입니다. 다른 고객사, 다른 플레이북에서 쓰려면 복사해야 하고, 복사본은 곧 서로 달라집니다. 6편에서 Terraform 코드를 모듈로 나눴던 것과 똑같은 이유로, Ansible 코드는 역할(role)로 나누고, 역할·모듈·플러그인을 묶어 배포할 때는 컬렉션(collection)을 씁니다. 이번 편은 web2를 nginx_site 역할로 쪼개고, 그 역할을 다시 사내 컬렉션 iaclab.platform으로 빌드해 FQCN으로 불러 쓰기까지 실제로 실행합니다.

역할

defaults·tasks·handlers·templates·meta를 정해진 디렉터리에. 플레이북은 roles: 한 줄.

컬렉션

namespace.name으로 역할·모듈·플러그인을 묶은 배포 단위. 버전이 있다.

관문

argument_specs로 입력 검증, requirements.yml로 의존성 고정, ansible-lint로 품질.

2역할 디렉터리 구조

정해진 이름의 디렉터리에 두면 Ansible이 알아서 찾는다 — 디렉터리를 눌러 보세요

cd ~/iac-lab/ansible && mkdir -p roles && cd roles
ansible-galaxy role init nginx_site
#   실측: - Role nginx_site was created successfully
#   생성된 파일: README.md, defaults/main.yml, handlers/main.yml, meta/main.yml,
#                tasks/main.yml, tests/inventory, tests/test.yml, vars/main.yml
#   (templates/·files/ 는 만들어 주지 않으므로 필요하면 직접)

디렉터리를 선택하세요

각 디렉터리의 main.yml이 진입점입니다. tasks/main.yml에서 다른 파일을 import·include해 나눌 수 있습니다.

Ansible이 역할을 찾는 위치: 플레이북 옆 roles/ → ansible.cfg의 roles_path → 기본 경로(~/.ansible/roles 등). 이 강의는 역할을 프로젝트 루트의 roles/에 두므로 ansible.cfg에 roles_path = roles, collections_path = collections를 추가했습니다(실측: 추가 전에는 ansible-lint가 “The role 'nginx_site' was not found”).

왜 접두사가 필요한가

Ansible 변수는 플레이 전체에서 하나의 이름 공간을 공유합니다. 역할 A의 port와 역할 B의 port는 같은 변수이고, 한쪽이 다른 쪽을 덮어씁니다. 15편 실습의 web_port, locations를 역할로 옮기며 모두 nginx_site_로 바꾼 이유입니다. ansible-lint는 역할 변수에 역할 이름 접두사가 없으면 경고합니다(var-naming[no-role-prefix]).

4실행 순서와 import·include

역할은 언제 실행되고, 몇 번 실행되는가

/tmp/ord/order.yml — app·monitor 역할은 둘 다 base 역할에 의존 (meta/main.yml의 dependencies)
- name: 실행 순서 실험
  hosts: localhost
  connection: local
  gather_facts: false
  pre_tasks:
    - name: pre_tasks
      ansible.builtin.debug:
        msg: pre
  roles:
    - app
    - monitor
    - role: app
      vars:
        param: second
  tasks:
    - name: tasks
      ansible.builtin.debug:
        msg: tasks
    - name: include_role (동적)
      ansible.builtin.include_role:
        name: monitor
  post_tasks:
    - name: post_tasks
      ansible.builtin.debug:
        msg: post
# 실측: 태스크·핸들러 실행 순서
TASK [pre_tasks]
TASK [base : base 역할 태스크 (param=없음)]          ← 의존 역할이 먼저 (app의 의존)
TASK [app : app 역할 태스크 (param=없음)]
TASK [monitor : monitor 역할 태스크 (param=없음)]    ← monitor도 base에 의존하지만 base는 다시 실행되지 않음
TASK [app : app 역할 태스크 (param=second)]          ← 같은 역할이라도 매개변수가 다르면 다시 실행
TASK [tasks]
TASK [include_role (동적)]
TASK [monitor : monitor 역할 태스크 (param=없음)]    ← include_role은 중복 제거 대상이 아니어서 다시 실행
RUNNING HANDLER [app : app 핸들러]                   ← 핸들러는 roles+tasks 구역이 끝난 뒤, post_tasks 전에
RUNNING HANDLER [base : base 핸들러]
RUNNING HANDLER [monitor : monitor 핸들러]
TASK [post_tasks]
호출 방식성격특징쓰는 때
roles:정적, 플레이 시작 시 로드pre_tasks 다음, tasks 전에 실행. 같은 역할·같은 매개변수는 한 번만(중복 제거, allow_duplicates: true로 해제)플레이의 주된 구성
import_role정적 (플레이 해석 시 펼쳐짐)tasks 중간 원하는 위치에. 태그·when이 안의 모든 태스크에 붙는다. --list-tasks에 보인다. loop 불가순서를 정밀하게 제어
include_role동적 (실행 시점에 결정)loop·조건부 실행·변수로 역할 이름 지정 가능. 태그·when은 include 자체에만. 중복 제거 안 됨(실측)조건·반복으로 역할을 고를 때 (실습 B)
tasks 파일 나누기도 같은 규칙

역할 안에서도 import_tasks(정적)와 include_tasks(동적)가 같은 차이를 가집니다. nginx_site의 tasks/main.yml은 install·configure·verify를 import_tasks로 불러 태그(nginx_site_install 등)가 안의 모든 태스크에 붙게 했습니다. 실행 출력의 태스크 이름 앞에 nginx_site :가 붙어 어느 역할의 태스크인지 보입니다.

5실습 A: web2 → 역할

160줄 플레이북이 역할 + 8줄 플레이북이 된다

roles/nginx_site/ ├── README.md ├── defaults/main.yml # 3장 ├── vars/Debian.yml RedHat.yml # 3장 (main.yml은 지움 — include_vars로 계열별 로드) ├── meta/main.yml argument_specs.yml ├── tasks/main.yml install.yml configure.yml verify.yml ├── handlers/main.yml └── templates/site.conf.j2 index.html.j2 # 15편 템플릿에서 변수 이름만 바꿈
tasks/main.yml
---
- name: 배포판 계열별 내부 변수 불러오기
  ansible.builtin.include_vars:
    file: "{{ ansible_facts['os_family'] }}.yml"

- name: 입력 값 검증 (argument_specs가 못 잡는 범위 조건)
  ansible.builtin.assert:
    that:
      - nginx_site_port | int >= 1024
      - nginx_site_port | int <= 65535
      - nginx_site_locations | length > 0
    fail_msg: "nginx_site_port는 1024~65535, nginx_site_locations는 1개 이상 (현재 port={{ nginx_site_port }})"
    quiet: true

- name: 설치
  ansible.builtin.import_tasks: install.yml
  tags: [nginx_site, nginx_site_install]

- name: 설정과 콘텐츠
  ansible.builtin.import_tasks: configure.yml
  tags: [nginx_site, nginx_site_config]

- name: 확인
  ansible.builtin.import_tasks: verify.yml
  when: nginx_site_verify | bool
  tags: [nginx_site, nginx_site_verify]
tasks/install.yml
---
- name: 패키지 설치
  ansible.builtin.package:
    name: "{{ ['nginx'] + nginx_site_extra_packages }}"
    state: present

- name: 배포판 기본 사이트 끄기
  ansible.builtin.file:
    path: "{{ __nginx_site_default_site }}"
    state: absent
  when:
    - nginx_site_disable_default | bool
    - __nginx_site_default_site | length > 0
  notify: nginx_site 설정 변경
tasks/verify.yml
---
- name: 응답이 올 때까지 재시도
  ansible.builtin.uri:
    url: "http://127.0.0.1:{{ nginx_site_port }}/health"
    return_content: true
  register: __nginx_site_health
  until: __nginx_site_health.status == 200 and nginx_site_title in __nginx_site_health.content
  retries: 5
  delay: 2
  changed_when: false
handlers/main.yml
---
- name: Nginx 다시 읽기 (nginx_site)
  ansible.builtin.service:
    name: nginx
    state: reloaded

tasks/configure.yml

13MSP 현장 팁

고객사 수십 곳에 같은 품질의 구성을

사내 컬렉션 = MSP 표준 구성

chrony, sshd 하드닝, 로그 전송, 모니터링 에이전트, nginx_site 같은 역할을 msp.platform 컬렉션 하나로 묶고 버전을 붙여 배포합니다. 고객 저장소는 requirements.yml에서 버전만 지정합니다. Terraform 공통 모듈 저장소(6·10편)와 같은 운영 모델입니다.

고객 차이는 인벤토리 변수로만

역할 코드에 고객별 분기(when: customer == 'custa')를 넣지 않습니다. 차이는 defaults를 덮어쓰는 group_vars로 표현하고, 표현할 수 없다면 역할에 새 입력을 추가(MINOR 버전)합니다.

argument_specs는 고객 실수 방지 장치

고객사 담당자가 인벤토리 변수를 직접 고치는 경우가 있습니다. 타입·필수·선택지 검증이 있으면 잘못된 값은 아무것도 바꾸기 전에 명확한 메시지로 멈춥니다. 공통 역할에는 필수로 둡니다.

Automation Hub를 쓰는 고객

AAP 구독 고객은 인증 컬렉션의 지원을 받을 수 있으므로, 같은 기능이라면 커뮤니티 컬렉션보다 인증 컬렉션을 우선합니다. 사설 허브가 있다면 MSP 사내 컬렉션도 그곳에 게시해 고객 승인 절차를 따릅니다.

업그레이드는 고객별로 단계적으로

공통 컬렉션 새 버전은 MSP 랩 → 개발계 고객 → 운영계 순서로 requirements.yml 버전을 올립니다(8편 승격 흐름과 동일). CHANGELOG에 MAJOR 변경을 명확히 적습니다.

역할 README와 argument_specs를 인수인계 문서로

ansible-doc -t role이 명세에서 문서를 만들어 주므로, 역할 문서가 코드와 어긋나지 않습니다. 고객 인수인계 패키지에 “사용한 역할·버전·변수 목록”을 넣습니다.

과제 1. chrony 역할

14·15편 과제의 chrony 플레이북을 roles/chrony 역할로 만드세요. defaults(chrony_servers 목록), 계열별 vars(설정 경로·서비스 이름), 템플릿, 핸들러, argument_specs, README. ansible-lint production 통과와 2회차 changed=0이 완료 조건입니다.

과제 2. 역할 의존성

nginx_site 역할의 meta/main.yml dependencies에 chrony 역할을 넣으면 실행 순서가 어떻게 바뀌나요? 두 플레이북이 모두 nginx_site를 쓸 때 chrony는 몇 번 실행되나요? 4장 실험처럼 확인하세요. 그리고 이 의존성이 바람직한 설계인지 의견을 쓰세요.

해설

의존 역할은 먼저 한 번 실행되고 같은 플레이 안에서는 중복 제거됩니다. 하지만 “웹 사이트가 시간 동기화에 의존한다”는 것은 기능적 의존이 아니라 운영 표준이므로, 의존성보다는 플레이북에서 두 역할을 나란히 나열하는 편이 결합이 낮습니다. meta 의존성은 “이 역할이 없으면 동작할 수 없는” 경우에만 씁니다.

과제 3. 여러 사이트를 loop로

한 서버에 사이트 두 개(포트 8080, 8081)를 올리세요. include_role과 loop(loop_control.loop_var로 이름 충돌 방지)를 쓰고, 핸들러가 두 번 실행되지 않는지 확인하세요. import_role로는 왜 안 되나요?

힌트

include_role: name: nginx_site + vars: nginx_site_name: "{{ site.name }}" … + loop: "{{ sites }}" + loop_control: loop_var: site. import_role은 정적이라 loop를 쓸 수 없습니다(4장 표).

과제 4. 컬렉션 1.1.0 릴리스

nginx_site에 nginx_site_client_max_body_size(기본 "1m") 입력을 추가하고, argument_specs·README·템플릿을 고친 뒤 컬렉션을 1.1.0으로 빌드하세요. requirements.yml에서 버전을 바꿔 재설치하고 2회차 changed=0을 확인합니다. 이 변경은 왜 MINOR인가요?

과제 5. 외부 역할 평가

Galaxy(또는 GitHub)에서 nginx 관련 인기 역할 하나를 골라 11장 점검표와 안티패턴 표로 평가하세요: 변수 접두사, defaults/vars 구분, argument_specs 유무, 지원 OS, 마지막 릴리스, 테스트 유무. 고객 운영에 쓸 수 있을까요?
