왜 Knative인가

요청이 오면 늘어나고, 아무도 안 쓰면 0개까지 줄어드는 애플리케이션. 쿠버네티스 위에서 이걸 가능하게 만드는 Knative의 큰 그림을 그려 봅니다.

기준 버전 Knative v1.23 대상: 1~2년차 클라우드·AI 엔지니어 예상 학습 시간 60~80분

먼저 직접 눌러 보세요

Knative 서비스 하나가 요청에 따라 Pod 수를 바꾸는 모습입니다.

Activator Pod가 0개이거나 모자랄 때 요청을 잠시 붙잡아 두는 대기실
0실행 중인 Pod
0처리 중인 요청
0Activator 대기 요청
0누적 처리 완료
Pod 0개. 요청이 없으니 사용하는 자원도 0입니다.

시뮬레이션은 이해를 위해 시간을 압축했습니다. Pod 1개당 동시 요청 2개를 목표로 늘어나고, 요청이 끊긴 뒤 5초가 지나면 0개로 줄어듭니다. 실제 기본값에서는 요청이 끊긴 뒤 0개가 되기까지 대략 60~90초가 걸립니다.

서버리스, 정확히 무엇인가

위 시뮬레이터에서 본 동작이 바로 서버리스(Serverless)의 핵심입니다. 이름 때문에 "서버가 없다"로 오해하기 쉽지만, 서버는 분명히 있습니다. 정확한 뜻은 "서버를 내가 신경 쓰지 않는다"입니다. 몇 대를 띄울지, 언제 늘리고 줄일지, 아무도 안 쓸 때 꺼 둘지를 플랫폼이 대신 판단합니다.

서버리스라고 부를 수 있는 플랫폼에는 보통 네 가지 성질이 있습니다.

요청에 따라 자동 확장

들어오는 요청량을 보고 인스턴스 수를 스스로 늘리고 줄입니다. 운영자가 "몇 대"를 정하지 않습니다.

0개까지 축소 (Scale to Zero)

아무 요청이 없으면 인스턴스를 전부 내립니다. 쓰지 않는 시간에는 CPU·메모리를 전혀 차지하지 않습니다.

이벤트 기반 실행

HTTP 요청뿐 아니라 "파일이 올라왔다", "메시지가 도착했다" 같은 사건이 코드를 깨웁니다.

쓴 만큼만 비용

퍼블릭 클라우드에서는 실제 실행 시간만큼 과금되고, 자체 클러스터에서는 남는 자원을 다른 워크로드가 씁니다.

택시로 이해하는 서버리스

자가용 = 항상 켜진 서버

  • 안 타도 주차비와 보험료가 나갑니다 (24시간 켜진 VM·Pod).
  • 사람이 몰리면 차가 한 대뿐이라 못 태웁니다 (수동 확장).
  • 대신 문 열면 바로 출발합니다 (지연 없음).

택시 = 서버리스

  • 탄 만큼만 냅니다 (요청이 있을 때만 실행).
  • 사람이 몰리면 택시가 여러 대 옵니다 (자동 확장).
  • 다만 부르고 나서 도착까지 기다려야 합니다. 이것이 콜드 스타트(Cold Start)입니다.
기억할 트레이드오프

0개까지 줄이면 자원은 아끼지만, 다음 첫 요청은 Pod가 새로 뜰 때까지 기다립니다. 이 시리즈 3편에서 콜드 스타트를 줄이는 설정(최소 Pod 수 유지 등)을 자세히 다룹니다. 시뮬레이터에서 Pod가 0개일 때 요청을 보내 보면, 요청이 Activator에 잠시 머무는 모습으로 이 대기를 볼 수 있습니다.

함수형 서버리스 vs 컨테이너형 서버리스

서버리스는 크게 두 갈래로 나뉩니다. 하나는 함수 단위로 코드를 올리는 FaaS, 다른 하나는 컨테이너 이미지를 그대로 올리는 방식입니다. Knative는 두 번째 갈래의 대표 주자이고, 그 위에 함수형 경험(Knative Functions)도 얹었습니다.

비교 항목함수형 (FaaS)컨테이너형 (Knative 계열)
올리는 것함수(코드 조각)와 설정HTTP를 받는 컨테이너 이미지
언어·라이브러리제공자가 지원하는 런타임 위주. 컨테이너 이미지를 지원하는 경우도 제공자의 실행 규약을 따라야 함컨테이너에 담기면 무엇이든 가능. 포트 하나로 HTTP만 받으면 됨
실행 시간상한이 뚜렷함 (예: AWS Lambda 최대 15분)요청 단위 타임아웃. Knative 기본 300초이고 운영자가 상한 조정 가능
이식성낮음. 제공자의 이벤트 형식과 API에 묶이기 쉬움높음. 같은 이미지와 YAML을 어느 쿠버네티스에서도 사용
대표 예AWS Lambda, Azure Functions, Google Cloud Run functionsKnative, Google Cloud Run, Azure Container Apps
잘 맞는 일짧은 이벤트 처리, 클라우드 서비스 간 접착 코드웹 API, 마이크로서비스, 모델 추론 서버, 기존 앱의 서버리스 전환
핵심 차이 한 줄

FaaS는 "내 코드를 플랫폼 모양에 맞추는" 방식이고, 컨테이너형은 "이미 있는 컨테이너를 그대로 서버리스로 굴리는" 방식입니다. MSP 입장에서는 고객사가 이미 컨테이너로 만든 앱을 고치지 않고 서버리스 운영으로 옮길 수 있다는 점이 큽니다.

Knative는 쿠버네티스를 대체하지 않습니다. 쿠버네티스가 이미 가진 Deployment, Pod, Service를 그대로 쓰면서, 그 위에 "요청 중심으로 생각하는 층"을 하나 더 얹습니다. 실제로 Knative 서비스를 만들면 그 아래에서 평범한 Deployment가 생기는 것을 5장에서 직접 확인합니다.

Knative 한 장 지도

한 문장으로 정의하면, Knative는 쿠버네티스 위에 얹는 서버리스·이벤트 기반 애플리케이션 계층입니다. 쿠버네티스에 새로운 리소스 종류(CRD)를 추가해 "Knative Service" 같은 새 단어를 가르치고, 컨트롤러가 그 단어를 Deployment·Pod 같은 기존 리소스로 번역해 줍니다.

Knative는 세 덩어리로 나뉘며, 각각 따로 설치할 수 있습니다. 아래 상자를 눌러 보세요.

네트워킹 레이어 (플러그인 선택): Kourier · Istio · Contour · Gateway API 구현체
쿠버네티스: Deployment, Pod, Service, CRD, 컨트롤러 메커니즘
설치 조합은 자유

Serving만 설치해서 "자동 확장되는 웹 서비스 플랫폼"으로 쓰는 경우가 가장 많습니다. Eventing만 따로 설치해 이벤트 라우터로만 쓰는 팀도 있고, Functions는 Serving 위에서 쓰는 개발자 도구에 가깝습니다. v1.21부터는 Functions로 만든 함수를 Serving 없이 일반 Deployment로 배포하는 옵션도 생겼습니다.

kubectl apply 한 번에 생기는 것들

3장의 Knative YAML을 적용하면 클러스터 안에서 무슨 일이 벌어질까요? 사용자가 만든 리소스는 단 하나지만, Knative 컨트롤러가 그 아래에 여러 리소스를 자동으로 만들어 냅니다. 버튼을 눌러 순서대로 따라가 보세요.

    파란 테두리 사용자가 직접 만든 것 보라 Knative 내부 리소스 초록 평범한 쿠버네티스 리소스 주황 네트워킹·외부 노출

    여기서 꼭 가져갈 개념은 세 가지입니다.

    Configuration은 "지금 원하는 최신 설정"이고, Revision은 그 설정이 바뀔 때마다 찍히는 변경 불가능한 스냅샷입니다. 그리고 Route는 "어느 Revision에 트래픽을 몇 퍼센트 보낼지"를 정합니다. 설정과 트래픽이 분리되어 있기 때문에, 새 버전을 배포해 놓고 트래픽은 천천히 옮기는 일이 자연스러워집니다. 2편에서 이 네 가지 리소스를 하나씩 해부합니다.

    6 / 13

    요청 하나의 여행

    사용자가 curl http://hello.default.example.com을 보냈을 때 요청이 거치는 길입니다. 점선 상자는 항상 거치는 곳이 아니라 Pod가 0개이거나 모자랄 때만 끼어드는 곳입니다.

    클라이언트브라우저, curl, 다른 서비스
    ›
    네트워킹 레이어Kourier 등이 호스트 이름을 보고 Revision을 고름
    ›
    ActivatorPod가 없으면 요청을 붙잡고 확장을 요청
    ›
    queue-proxy모든 Pod에 붙는 사이드카. 동시 요청 수를 세어 보고
    ›
    user-container여러분의 앱. HTTP만 받으면 됨

    Knative Pod 안을 들여다보면 컨테이너가 두 개입니다. 하나는 여러분의 앱(user-container)이고, 다른 하나는 Knative가 자동으로 끼워 넣는 queue-proxy입니다. queue-proxy가 "지금 동시에 몇 개의 요청을 처리 중인가"를 재서 Autoscaler에게 알려 주고, Autoscaler는 이 숫자로 Pod 수를 결정합니다. 시뮬레이터에서 Pod 수가 바뀐 원리가 바로 이것입니다.

    지원하는 프로토콜

    Knative Serving은 HTTP/1.1, HTTP/2, gRPC, WebSocket을 다룹니다. 반대로 HTTP가 아닌 원시 TCP·UDP 서비스(게임 서버, DB 프로토콜 등)는 대상이 아닙니다. 10장의 "안 맞는 경우"에서 다시 짚습니다.

    7 / 13

    Knative가 걸어온 길

    역사를 알면 "왜 이런 구조가 됐는지"와 "왜 벤더마다 버전이 다른지"가 이해됩니다.

    1. 2018

      Google 주도로 공개

      Pivotal, IBM, Red Hat, SAP 등이 함께 시작했습니다. 처음에는 Serving, Eventing, Build 세 덩어리였습니다.

    2. 2019

      Build가 독립해 Tekton으로

      이미지 빌드 기능이 CI/CD 파이프라인 프로젝트 Tekton으로 떨어져 나갔습니다. 지금도 Knative와 Tekton은 기반 패키지를 공유합니다. 같은 해 Google Cloud Run이 Knative API 규격으로 정식 출시됐습니다.

    3. 2020

      상용 배포판의 등장

      Red Hat OpenShift Serverless 등 벤더 제품이 Knative를 감싸 출시되기 시작합니다. 한편 Google 중심 거버넌스에 대한 커뮤니티의 우려도 커졌습니다.

    4. 2021

      v1.0 출시

      운영 환경에서 써도 된다는 신호인 1.0이 나왔습니다. 이후 분기마다 마이너 버전이 나오고, 각 버전은 약 6개월간 지원됩니다.

    5. 2022

      CNCF 인큐베이팅 프로젝트로 합류

      중립 재단으로 옮겨 가며 거버넌스 논란이 정리되고 기여 기업이 늘었습니다.

    6. 2025

      CNCF 졸업 (Graduated)

      10월, 쿠버네티스·Prometheus와 같은 최상위 성숙도 등급을 받았습니다. 비슷한 시기에 메트릭과 트레이싱이 OpenCensus에서 OpenTelemetry로 완전히 전환됐습니다.

    7. 2026

      보안 기본값 강화와 v1.23

      v1.22부터 Pod 보안 기본값(secure-pod-defaults)이 AllowRootBounded로 바뀌었고, 이 강의의 기준인 v1.23에서는 Eventing이 EndpointSlice로 옮겨 가는 등 최신 쿠버네티스 흐름에 맞춰지고 있습니다.

    MSP 실무 포인트: 버전 시차

    업스트림은 분기마다 새 버전을 내지만, 벤더 제품은 검증을 거쳐 몇 버전 뒤를 따라갑니다. 예를 들어 OpenShift Serverless 1.37은 Knative 1.17 기반입니다. 고객사 문서를 볼 때 "제품 버전"과 "내부 Knative 버전"을 따로 확인하는 습관이 필요합니다. 9편에서 플랫폼별로 비교합니다.

    생태계 속 Knative

    Knative는 혼자 일하지 않습니다. 강의를 듣다 보면 계속 마주칠 이웃 프로젝트들과의 관계를 미리 정리해 둡니다.

    Eventing의 공용어

    CloudEvents

    이벤트를 담는 표준 봉투 형식입니다. Knative Eventing의 모든 이벤트가 이 형식을 따르기 때문에, 어느 시스템에서 왔든 같은 방식으로 다룰 수 있습니다.

    Functions의 빌드 엔진

    Cloud Native Buildpacks

    Dockerfile 없이 소스 코드만 보고 언어를 알아내 컨테이너 이미지를 만들어 줍니다.

    한 뿌리에서 나온 형제

    Tekton

    옛 Knative Build에서 독립한 CI/CD 파이프라인 도구입니다. Functions의 클러스터 내부 빌드에도 쓰입니다.

    Knative 위에 지은 집

    KServe

    AI 모델 서빙 플랫폼입니다. 서버리스 배포 모드에서 Knative를 써서 추론 서버를 0개까지 줄이고 버전별 카나리 배포를 합니다.

    교체 가능한 부품

    Kourier · Istio · Contour · Gateway API

    Knative가 트래픽을 실제로 나르는 데 쓰는 네트워킹 레이어입니다. 가벼운 걸 원하면 Kourier, 이미 서비스 메시가 있으면 Istio를 고르는 식입니다.

    비교 대상이자 보완재

    KEDA

    큐 길이 같은 외부 지표로 기존 Deployment를 0개까지 줄이는 도구입니다. Knative는 HTTP 요청 중심, KEDA는 메시지·배치 중심이라고 기억하면 됩니다. 6편에서 비교합니다.

    첫 실습: 내 노트북에서 0개 축소 보기

    Knative 공식 퀵스타트 플러그인을 쓰면 로컬 kind 클러스터에 Knative Serving·Eventing과 Kourier가 한 번에 설치됩니다. 학습용 환경이니 마음껏 부수고 다시 만드세요.

    준비물

    Docker(또는 호환 런타임), kind, kubectl이 필요합니다. Docker에 CPU 3개, 메모리 3GB 이상을 할당해 두는 것을 권장합니다. 회사 노트북이라면 프록시나 보안 정책 때문에 이미지 다운로드가 막히는 경우가 있으니 미리 확인하세요.

    1. kn CLI와 퀵스타트 플러그인 설치

      macOS·Linux에서 Homebrew를 쓰는 경우입니다. 다른 환경은 GitHub 릴리스 페이지에서 바이너리를 받으면 됩니다.

      bash
      brew install knative/client/kn
brew install knative-extensions/kn-plugins/quickstart

# 설치 확인
kn version
kn quickstart --help

    2. kind 클러스터에 Knative 설치

      명령 하나로 클러스터 생성부터 Serving, Kourier, Eventing 설치까지 끝납니다. 몇 분 걸립니다.

      bash
      kn quickstart kind

# 무엇이 설치됐는지 확인
kubectl get pods -n knative-serving
kubectl get pods -n kourier-system
kubectl get pods -n knative-eventing

    3. 첫 Knative 서비스 배포

      3장에서 본 YAML과 똑같은 일을 kn 명령 한 줄로 합니다.

      bash
      kn service create hello \
  --image ghcr.io/knative/helloworld-go:latest \
  --port 8080 \
  --env TARGET=World

# 출력된 URL로 호출
curl http://hello.default.127.0.0.1.sslip.io
# Hello World!

      퀵스타트는 sslip.io라는 와일드카드 DNS를 써서, 별도 DNS 설정 없이 로컬 주소로 접속하게 해 줍니다.

    4. 0개로 줄어드는 순간 지켜보기

      터미널을 하나 더 열어 Pod를 실시간으로 관찰합니다. 호출을 멈추고 1~2분 기다리면 Pod가 Terminating을 거쳐 사라집니다. 그 상태에서 다시 curl을 보내면 응답이 살짝 늦게 오는데, 이것이 콜드 스타트입니다.

      bash
      kubectl get pod -l serving.knative.dev/service=hello -w

# Pod 안의 컨테이너 2개 확인 (user-container, queue-proxy)
kubectl get pod -l serving.knative.dev/service=hello \
  -o jsonpath='{.items[0].spec.containers[*].name}'

    5. 설정을 바꿔 새 Revision 만들기

      환경 변수 하나만 바꿔도 새 Revision이 생깁니다. 5장의 "다시 배포" 버튼과 같은 일입니다.

      bash
      kn service update hello --env TARGET=Knative
kn revisions list

# 맛보기: 두 Revision에 트래픽 반반 (4편에서 자세히)
kn service update hello \
  --traffic hello-00001=50 \
  --traffic @latest=50

for i in $(seq 1 6); do curl -s http://hello.default.127.0.0.1.sslip.io; done

    6. Knative가 만든 리소스 직접 보기

      5장의 트리를 실제 클러스터에서 확인합니다.

      bash
      kubectl get ksvc,configuration,revision,route
kubectl get deployment,podautoscaler
kubectl get ingresses.networking.internal.knative.dev

    7. 정리

      bash
      kn service delete hello
kind delete cluster --name knative

    이럴 땐 다른 도구가 낫습니다

    항상 높은 트래픽이 꾸준히 들어오는 서비스
    0개로 줄어들 일이 없으니 서버리스의 비용 이점이 사라집니다. 다만 Revision과 트래픽 분할이 필요해서 Knative를 쓰는 팀도 있습니다. 이 경우 최소 Pod 수(min-scale)를 높게 잡고 씁니다.
    상태를 직접 저장하는 서비스 (DB, 캐시, 메시지 브로커)
    Knative Pod는 언제든 사라지고 다시 생길 수 있다고 가정합니다. 상태 저장 워크로드는 StatefulSet이나 오퍼레이터로 운영하고, Knative 서비스는 그 앞에서 상태 없이 동작하게 설계하세요.
    수십 분 이상 도는 배치 작업
    요청 하나를 오래 붙잡는 구조는 타임아웃과 맞지 않습니다. 쿠버네티스 Job, Argo Workflows, KEDA ScaledJob이 더 자연스럽습니다.
    콜드 스타트를 절대 허용할 수 없는 서비스
    첫 요청 지연이 SLA 위반이 되는 결제 승인 같은 경우입니다. min-scale로 최소 1개 이상을 유지하거나 일반 Deployment를 고려합니다. 특히 수십 GB 모델을 올리는 LLM 추론은 콜드 스타트가 분 단위가 될 수 있어 신중해야 합니다.
    HTTP가 아닌 프로토콜 (원시 TCP·UDP)
    게임 서버, SIP, 데이터베이스 와이어 프로토콜 등은 Knative Serving의 대상이 아닙니다. 일반 Deployment와 LoadBalancer 서비스를 쓰세요.

    정리와 다음 편

    1. 서버리스는 "서버가 없다"가 아니라 "서버 수와 수명을 플랫폼이 관리한다"는 뜻입니다.
    2. Knative는 컨테이너형 서버리스입니다. 컨테이너에 담긴 HTTP 앱이면 언어와 상관없이 올라갑니다.
    3. 순수 쿠버네티스에 없는 0개 축소, 요청 보존, 요청 기반 확장, Revision, 트래픽 분할을 한 리소스로 제공합니다.
    4. 구성요소는 Serving, Eventing, Functions 셋이며, 아래에 교체 가능한 네트워킹 레이어가 있습니다.
    5. Knative Service 하나가 Configuration, Revision, Route와 그 아래 평범한 Deployment·Pod를 만들어 냅니다.
    6. 요청은 네트워킹 레이어, (필요할 때) Activator, queue-proxy를 거쳐 앱에 도착합니다.
    7. 2025년 CNCF를 졸업한 성숙한 프로젝트이며, 벤더 제품은 업스트림보다 몇 버전 뒤를 따라간다는 점을 기억하세요.

    다음 편: Serving 해부

    Service, Configuration, Revision, Route 네 가지 CRD의 관계를 YAML 수준에서 뜯어보고, controller·webhook·autoscaler·activator가 각각 무슨 일을 하는지, 네트워킹 레이어 네 가지를 어떻게 고르는지, DomainMapping으로 내 도메인을 붙이는 법까지 다룹니다.
