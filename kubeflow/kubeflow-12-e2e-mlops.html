이번 편에서 얻을 것

1편에서 지은과 민수가 겪은 여섯 가지 문제, 재현성, 추적, 자원 공유, 튜닝, 서빙, 그리고 모델이 시간이 지나며 나빠지는 문제를 모두 체계로 해결한 모습을 완성합니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 데이터 준비부터 카나리 배포까지 이어지는 지속적 학습 파이프라인을 설계하고, 각 단계가 몇 편의 무엇인지 연결할 수 있습니다.
  • 데이터 검증과 모델 검증이라는 두 개의 관문을 두고, 실패해도 알림과 정리가 반드시 일어나게 만들 수 있습니다.
  • 컴포넌트, 파이프라인, 서빙 설정을 Git 저장소로 관리하고, CI와 GitOps로 클러스터에 반영하는 흐름을 만들 수 있습니다.
  • 재학습을 일정, 데이터 도착, 성능 저하로 깨우는 방법과 환경 분리를 설계하고, 팀의 MLOps 성숙도를 점검할 수 있습니다.

2저장소 구조

재현성의 마지막 조각은 “무엇이 운영 중인가”를 Git이 말해 주게 하는 것입니다. 추천팀의 저장소를 이렇게 나눴습니다. 폴더를 누르면 역할이 나옵니다.

3파이프라인 전체 코드

컴포넌트는 6편 6장의 방식대로 버전이 붙은 YAML로 불러오고, 파이프라인 파일은 연결만 담습니다. 맨 위 재생기의 그래프가 이 코드입니다. 각 컴포넌트의 속은 앞 편들에서 만든 것을 다듬어 씁니다.

from kfp import dsl, components

C = lambda p: components.load_component_from_file(f"components/{p}.yaml")
run_spark       = C("run_spark/v1.0.0")        # 10편 7장: SparkApplication 만들고 기다림
validate_data   = C("validate_data/v1.2.0")    # 이번 편 4장
train_trainjob  = C("train_trainjob/v2.0.0")   # 7편 9장: TrainJob 만들고 기다림
evaluate        = C("evaluate/v1.2.0")         # 5편
register_model  = C("register_model/v1.1.0")   # 9편 3장
deploy_canary   = C("deploy_canary/v1.0.0")    # 이번 편 5장
smoke_test      = C("smoke_test/v1.0.0")
notify          = C("notify/v1.0.0")

@dsl.pipeline(name="reco-ct", description="추천 모델 지속적 학습")
def reco_ct(date: str, threshold: float = 0.95, num_nodes: int = 2,
            queue: str = "reco-queue"):
    done = notify(channel="#reco-ml", run_id=dsl.PIPELINE_JOB_ID_PLACEHOLDER)
    with dsl.ExitHandler(exit_task=done):                         # 6편: 무슨 일이 있어도 알림
        feats = run_spark(date=date)
        feats.set_caching_options(False)                          # 매일 새 데이터
        check = validate_data(features_uri=feats.outputs["features_uri"])

        train = train_trainjob(features_uri=feats.outputs["features_uri"],
                               num_nodes=num_nodes, queue=queue).after(check)
        train.set_retry(num_retries=2, backoff_duration="5m")   # 스팟 회수 대비, 체크포인트 전제

        ev = evaluate(model_uri=train.outputs["model_uri"],
                      features_uri=feats.outputs["features_uri"])

        with dsl.If(ev.outputs["accuracy"] >= threshold, name="quality-gate"):
            reg = register_model(model_name="digits-classifier",
                                 model_uri=train.outputs["model_uri"],
                                 accuracy=ev.outputs["accuracy"],
                                 data_date=date,
                                 run_id=dsl.PIPELINE_JOB_ID_PLACEHOLDER)
            dep = deploy_canary(model_name="digits-classifier",
                                version=reg.outputs["version"], percent=10)
            smoke_test(isvc="digits").after(dep)
  • run_id 자리 표시자: dsl.PIPELINE_JOB_ID_PLACEHOLDER는 실행될 때 실제 실행 ID로 바뀝니다. 이 값을 레지스트리 메타데이터와 알림에 넣어, 모델 버전에서 실행 기록으로, 알림에서 실행 화면으로 바로 갈 수 있게 합니다.
  • 큐 이름을 인자로: Kueue 라벨(11편)은 파이프라인 단계 Pod가 아니라 그 단계가 만드는 TrainJob에 붙어야 합니다. 그래서 큐 이름을 컴포넌트 인자로 넘겨 TrainJob을 만들 때 라벨로 붙입니다.
  • 출력 이름: features_uri, model_uri, accuracy, version 같은 출력 이름은 이 예의 약속입니다. 팀 컴포넌트 라이브러리에서 입출력 이름을 계약처럼 문서화해 둡니다(6편 6장).

4데이터 검증 단계

나쁜 데이터로 학습한 모델은 정확도 검사를 통과할 수도 있습니다. 평가 데이터도 같이 나쁘면 그렇습니다. 그래서 학습 전에 데이터 자체를 검사하는 첫 번째 관문을 둡니다. 실패하면 학습에 GPU를 쓰기 전에 멈춥니다.

검사예잡아내는 사고
스키마필요한 열이 모두 있고 타입이 맞는가상류 시스템이 열 이름을 바꿈
행 수 범위어제의 50%에서 150% 사이인가수집 장애로 반나절치만 들어옴
결측 비율주요 열의 빈 값이 2% 이하인가로그 형식 변경으로 값이 비어 들어옴
분포주요 피처의 분포가 기준 기간과 크게 다르지 않은가데이터 드리프트, 또는 단위가 바뀜(원에서 천 원으로)
레이블클래스 비율이 정상 범위인가레이블 생성 로직의 버그
 
@dsl.component(base_image="registry.example.com/reco/validate:1.2.0")
def validate_data(features_uri: str, min_rows: int = 100000, max_null_ratio: float = 0.02):
    import pandas as pd
    df = pd.read_parquet(features_uri, columns=["user_id", "events", "avg_score", "label"])
    problems = []
    if len(df) < min_rows:
        problems.append(f"행 수 {len(df)} < {min_rows}")
    null_ratio = df.isna().mean().max()
    if null_ratio > max_null_ratio:
        problems.append(f"결측 비율 {null_ratio:.3f} > {max_null_ratio}")
    if problems:
        raise ValueError("데이터 검증 실패: " + "; ".join(problems))   # 단계 실패 → 이후 단계 실행 안 됨

규칙이 많아지면 Great Expectations 같은 데이터 검증 도구를 컴포넌트 안에서 씁니다. 규칙 파일도 Git에 둡니다. 피처가 수십 GB라면 이 검사도 Spark 단계 안에서 집계로 하는 편이 낫습니다.

5등록과 카나리 배포 단계

관문 2를 통과한 모델은 등록되고, 곧바로 운영 InferenceService에 카나리 10%로 올라갑니다. 9편에서 손으로 한 일을 컴포넌트로 만든 것입니다.

@dsl.component(base_image="python:3.11", packages_to_install=["kubernetes"])
def deploy_canary(model_name: str, version: str, percent: int, isvc: str = "digits",
                  namespace: str = "kubeflow-user-example-com"):
    from kubernetes import client, config
    config.load_incluster_config()
    api = client.CustomObjectsApi()
    patch = {"spec": {"predictor": {
        "canaryTrafficPercent": percent,
        "model": {"storageUri": f"model-registry://{model_name}/{version}"}}}}
    api.patch_namespaced_custom_object("serving.kserve.io", "v1beta1", namespace,
                                       "inferenceservices", isvc, patch)
  • 이 컴포넌트는 9편 5장의 방법 2(model-registry:// 주소)를 가정합니다. 그 기능이 없다면 레지스트리에서 아티팩트 위치를 읽어 storageUri에 넣습니다.
  • smoke_test는 새 버전에 몇 개의 고정 입력을 보내 응답 형식과 값의 범위를 확인합니다. 실패하면 파이프라인이 실패하고, ExitHandler의 notify가 canaryTrafficPercent를 0으로 되돌리고 알리게 만들 수 있습니다.
  • 9편 6장처럼 카나리 비율 분배는 KServe 서버리스 모드를 전제로 합니다.
GitOps와 함께라면 누가 InferenceService를 바꾸나

7장의 GitOps에서는 Git이 진실의 원천입니다. 파이프라인이 클러스터의 InferenceService를 직접 고치면 Argo CD가 Git과 다르다고 보고 되돌릴 수 있습니다. 둘 중 하나로 정하세요. 파이프라인이 Git 저장소에 변경 요청(PR)을 만드는 방식이 감사에는 가장 좋고, InferenceService의 storageUri와 카나리 필드만 Argo CD가 무시하게 설정하고 파이프라인이 직접 고치는 방식이 가장 빠릅니다.

6승격은 따로

reco-ct 파이프라인은 카나리 10%까지만 합니다. 100%로의 승격은 실제 트래픽에서 일정 시간 지켜본 뒤 판단해야 하므로, 밤새 도는 학습 파이프라인과 분리합니다.

판단 기준예시 규칙어디서 보나
오류율카나리의 5xx 비율이 기존 버전보다 높지 않다KServe와 Istio 지표 (15편)
지연 시간p95 응답 시간이 기존의 120% 이내같은 지표
예측 분포예측 클래스 비율이 기존 버전과 크게 다르지 않다예측 로그 집계
업무 지표추천 클릭률이 떨어지지 않는다업무 대시보드. 보통 하루 이상 필요
승격 방식방법어울리는 곳
사람 승인카나리 결과를 담은 PR을 사람이 승인해 병합하면 Argo CD가 100%로 반영규제가 있는 업무, 처음 도입할 때
자동 승격관측 지표를 보는 별도 파이프라인이나 점진 배포 도구가 기준 충족 시 자동으로 승격, 미달 시 되돌림모델 교체가 잦고 지표가 잘 정의된 곳

7CI/CD와 GitOps

1편 2장의 MLOps 성숙도 레벨 2는 “파이프라인 코드 자체도 CI로 시험하고 CD로 배포한다”였습니다. 코드를 고친 뒤 클러스터의 반복 실행이 새 버전으로 바뀌기까지를 따라가 봅니다.

8재학습을 깨우는 방법

방식어떻게장점주의
일정반복 실행(6편 7장)으로 매일 새벽 2시가장 단순하고 예측 가능데이터가 늦게 오면 빈 데이터로 학습. 검증 단계가 막아 줘야 함
데이터 도착데이터 적재가 끝나면 Argo Events나 사내 스케줄러가 KFP API로 실행을 만듦데이터와 학습이 어긋나지 않음이벤트 경로와 권한 구성이 필요
성능 저하관측 도구가 드리프트나 업무 지표 하락을 감지하면 경보가 실행을 만듦필요할 때만 학습해 비용 절감감지 기준이 잘못되면 너무 자주 또는 너무 늦게

처음에는 일정으로 시작하고, 데이터 지연 사고가 나면 데이터 도착 방식을, 학습 비용이 문제가 되면 성능 저하 방식을 더합니다. 어떤 방식이든 같은 파이프라인 버전을 다른 인자로 부르는 것뿐이라, 파이프라인 코드는 바뀌지 않습니다.

9환경 나누기

환경어디데이터배포 대상누가 바꾸나
개발팀원 개인 프로필 네임스페이스표본없음각자

13확인 퀴즈

여덟 문제입니다.

14정리와 다음 편

  1. 지속적 학습 파이프라인은 데이터 준비, 데이터 검증, 학습, 모델 검증, 등록, 카나리 배포로 이어지고, ExitHandler가 무슨 일이 있어도 알립니다.
  2. 관문은 둘입니다. 학습 전의 데이터 검증이 GPU 낭비와 나쁜 모델을 막고, 등록 전의 성능 관문이 나쁜 모델의 운영 진입을 막습니다.
  3. 학습 파이프라인은 카나리까지만, 승격은 실제 트래픽을 지켜본 뒤 따로 합니다. 튜닝은 매일이 아니라 가끔 하고 결과를 Git에 고정합니다.
  4. 컴포넌트, 파이프라인, 서빙 설정을 Git이 관리하고, CI가 시험하고 빌드하며, Argo CD가 클러스터에 반영하면 MLOps 성숙도 레벨 2입니다.
  5. 재학습은 일정, 데이터 도착, 성능 저하로 깨우고, 같은 파이프라인 YAML을 환경마다 다른 인자와 네임스페이스로 씁니다.

현장에서 쓰이는 장면

  • 금융. 매일 새벽 지속적 학습이 돌되, 데이터 검증과 성능 관문 두 개가 나쁜 모델의 운영 진입을 막습니다.
  • 제조. 신제품 라인이 추가될 때 파이프라인 인자만 바꿔 같은 파이프라인을 재사용합니다.
  • MSP. 고객사의 MLOps 성숙도를 10장의 점검표로 진단해 다음 분기 과제를 제안합니다(16편).
