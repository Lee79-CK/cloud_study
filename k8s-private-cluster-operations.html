    01

    클러스터 아키텍처 설계

    몇 개의 클러스터를, 어떤 크기의 노드로, 어떤 IP 대역으로 만들 것인가. 나중에 바꾸기 가장 어려운 결정들입니다.

    결정 1 — 클러스터를 몇 개로 나눌 것인가

    "하나의 큰 클러스터"와 "여러 개의 작은 클러스터"는 취향 문제가 아니라 장애 반경(blast radius)과 운영 인건비의 교환입니다.

    기준대형 단일 클러스터다중 소형 클러스터
    자원 효율높음. 빈 공간을 서로 메움낮음. 클러스터마다 여유분과 애드온 중복
    장애 반경매우 큼. etcd 하나가 전사를 세움작음. 하나 죽어도 나머지는 생존
    업그레이드한 번에 전사 리스크카나리 클러스터로 단계적 검증 가능
    멀티테넌시RBAC·쿼터·NetworkPolicy로 강하게 격리 필요클러스터 경계가 곧 격리
    운영 부담낮음(하나만 잘 보면 됨)높음. 반드시 GitOps로 형상 통일 필요
    실무 기본값

    대부분의 사내 환경은 환경별(prod / stg / dev) + 등급별(일반 / 규제·망분리) 분리가 무난합니다. 여기에 "운영자용 관리 클러스터" 하나를 더 두고 Argo CD·모니터링 장기 저장소·백업 저장소를 올리면, 운영 클러스터가 죽어도 관측과 복구 수단은 살아 있습니다. 관측 스택을 감시 대상과 같은 클러스터에만 두는 것이 가장 흔한 실수입니다.

    결정 2 — 노드 규격

    같은 총량이면 큰 노드 소수와 작은 노드 다수 중 무엇이 나을까요.

    큰 노드 (예: 64c / 512GB)
    • 노드당 오버헤드(kubelet, CNI, 로그 수집 DaemonSet) 비율이 낮아 효율적
    • 대형 파드(대용량 JVM, 학습 작업) 수용 가능
    • 한 대가 죽으면 파드 100개 이상이 동시에 재스케줄 → 순간 부하 폭발
    • 노드당 파드 한계(기본 110)에 먼저 막혀 CPU가 남을 수 있음
    작은 노드 (예: 16c / 128GB)
    • 장애 시 영향 범위가 작고 롤링 업그레이드가 부드러움
    • DaemonSet이 노드 수만큼 늘어 오버헤드·API 부하 증가
    • 같은 총량 대비 노드 수가 많아 관리 대상 급증
    • 단편화로 큰 파드가 들어갈 자리를 못 찾는 일이 잦음
    계산 습관

    노드 스펙을 정할 때는 항상 가용 자원 = 물리 자원 − 시스템 예약 − kube 예약 − eviction 임계값으로 계산하세요. 64코어 노드에서 실제 파드가 쓸 수 있는 건 60코어 남짓입니다. 이 차이를 무시하고 용량을 계산하면 항상 예상보다 일찍 꽉 찹니다.

    kubelet 예약 설정 (노드당 반드시 지정)
    # /var/lib/kubelet/config.yaml
systemReserved:            # OS, sshd, 에이전트 몫
  cpu: "1000m"
  memory: "2Gi"
  ephemeral-storage: "10Gi"
kubeReserved:              # kubelet, 컨테이너 런타임 몫
  cpu: "1000m"
  memory: "2Gi"
evictionHard:              # 이 밑으로 가면 파드를 쫓아냄
  memory.available: "1Gi"
  nodefs.available: "10%"
  imagefs.available: "15%"
evictionSoft:              # 유예 시간을 주고 완만하게 정리
  memory.available: "2Gi"
evictionSoftGracePeriod:
  memory.available: "2m"
maxPods: 110              # Pod CIDR 마스크와 반드시 함께 계산
serializeImagePulls: false
registryPullQPS: 10

    결정 3 — IP 대역 설계 (되돌리기 가장 어려움)

    Pod CIDR과 Service CIDR은 클러스터를 재설치하지 않으면 사실상 변경 불가입니다. 게다가 사내망이므로 다른 시스템과 겹치면 안 되고, 나중에 클러스터 간 통신이나 사내망 라우팅을 붙일 때 충돌합니다.

    • --cluster-cidr (Pod 전체 대역)에서 --node-cidr-mask-size만큼 잘라 노드마다 하나씩 배분합니다.
    • 노드당 /24를 주면 노드당 파드 IP는 254개, 이때 maxPods: 110은 여유가 있습니다.
    • 총 노드 수 = 2(mask − cidr). 10.200.0.0/16 + /24 ⇒ 최대 256노드. 300대로 늘리는 순간 막힙니다.
    Pod CIDR 용량 계산기

    클러스터 대역과 노드당 마스크를 넣으면 수용 가능한 노드 수와 파드 수를 계산합니다.

    사내 IP 협의 체크리스트
    • Pod CIDR / Service CIDR / 노드 대역 / MetalLB VIP 풀 — 네 종류를 사전에 문서로 확보
    • 사내 다른 시스템, VPN, 파트너망과 중복 여부 확인 (특히 흔한 10.0.0.0/8 충돌)
    • 향후 3년 노드 증설을 감안해 최소 2배 여유 확보
    • 클러스터를 여러 개 만들 계획이면 클러스터마다 다른 대역을 미리 할당해 둘 것

    결정 4 — 실패 도메인을 레이블로 표현하기

    쿠버네티스는 우리 데이터센터의 랙 구조를 모릅니다. 알려주지 않으면 파드 3개를 같은 랙, 심하면 같은 스위치 아래에 몰아넣습니다. 노드 레이블이 곧 가용성 설계입니다.

    노드 레이블 표준 (설치 시 자동 부여되게 할 것)
    $ kubectl label node worker-a-013 \
    topology.kubernetes.io/zone=rack-a \
    topology.kubernetes.io/region=dc-seoul-1 \
    node.example.com/power-feed=feed-1 \
    node.example.com/switch=leaf-a-02 \
    node.example.com/pool=app \
    node.example.com/generation=gen3-64c

# 파드는 이 레이블 위에서 균등 분산된다
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule     # 랙 분산이 안 되면 아예 대기
  labelSelector:
    matchLabels: {app: payment-api}
- maxSkew: 2
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway     # 노드 분산은 되면 좋고
  labelSelector:
    matchLabels: {app: payment-api}
    자주 겪는 사고

    "레플리카 3개인데 랙 전원 하나 내려갔더니 서비스가 죽었다." 원인은 대부분 topologySpread나 podAntiAffinity가 없어서 3개가 같은 랙에 있던 것입니다. 중요 서비스는 배포 후 실제로 어느 노드에 떠 있는지 확인하는 습관을 들이세요. kubectl get pod -o wide -l app=payment-api 한 줄이면 됩니다.

    설치 도구 선택

    표준이자 학습용 최적. 쿠버네티스 공식 부트스트랩 도구로, 인증서 생성·컨트롤 플레인 구성·업그레이드 경로를 모두 표준대로 제공합니다.

    • 장점: 문서와 커뮤니티가 가장 풍부하고, 문제가 나도 원인이 명확합니다. 인증서 갱신(kubeadm certs renew), 업그레이드(kubeadm upgrade)가 잘 정리돼 있습니다.
    • 단점: OS 준비, 런타임 설치, CNI, LB, 노드 300대 반복 작업은 직접 자동화해야 합니다.
    • 추천: 소수 클러스터를 깊게 이해하며 운영할 때, Ansible을 이미 잘 쓰고 있을 때.

    kubeadm을 감싼 Ansible 플레이북 모음. 온프레미스 대규모 설치의 사실상 표준 중 하나입니다.

    • 장점: 인벤토리 파일에 노드 300대를 적으면 OS 튜닝·런타임·CNI·애드온까지 한 번에. 오프라인(에어갭) 설치 지원.
    • 단점: 변수 계층이 깊어 "왜 이 값이 이렇게 들어갔는지" 추적이 어렵고, 실행 시간이 깁니다. 버전 업그레이드 시 플레이북 자체의 호환성도 검증 대상입니다.
    • 추천: 폐쇄망 대규모 신규 구축, Ansible 운영 문화가 있는 조직.

    단일 바이너리형 배포판. 컨테이너 런타임, CNI(기본 Canal), Ingress, Helm 컨트롤러가 포함돼 있고 CIS 보안 프로파일을 기본 지원합니다.

    • 장점: 설치가 매우 단순하고 에어갭 이미지 번들 제공. systemd 서비스 하나로 컨트롤 플레인이 뜹니다. 정부·금융 규제 환경에서 선호됩니다.
    • 단점: 표준 kubeadm과 파일 경로·설정 방식이 달라 일반 문서를 그대로 적용하기 어렵습니다. 벤더 릴리스 주기에 종속됩니다.
    • 추천: 인력이 적고 보안 기준을 빠르게 충족해야 하는 조직, 엣지·지사 다수 클러스터.

    쿠버네티스 전용 불변(immutable) OS. SSH도 셸도 없고 gRPC API로만 관리합니다.

    • 장점: 공격 표면이 극단적으로 작고, 노드 설정 드리프트가 원천적으로 없습니다. 업그레이드는 이미지 교체 방식이라 되돌리기 쉽습니다.
    • 단점: 기존 서버 관리 방식(에이전트 설치, 커널 모듈, 사내 백신·감사 툴)과 충돌하기 쉽습니다. 문제 발생 시 노드에 들어가서 볼 수 없다는 점이 초기에는 큰 장벽입니다.
    • 추천: 신규 구축이고, 사내 서버 표준을 새로 정의할 수 있는 권한이 있을 때.

    Q. 클러스터 CIDR이 10.244.0.0/16, node-cidr-mask-size가 /24인 클러스터에 노드를 260번째로 추가했습니다. 어떤 일이 벌어질까요?

    정답: 2번. /16을 /24로 자르면 256개 블록이 끝입니다. 257번째 노드부터 controller-manager가 PodCIDR을 배정하지 못하고, 노드는 Ready처럼 보여도 CNI가 IP를 못 줘서 파드가 ContainerCreating/Pending에 머뭅니다. 로그에는 CIDR 할당 실패 메시지가 남습니다. 이 상태는 재설치 없이 고치기 매우 어렵기 때문에 설계 단계에서 2배 여유를 두라는 것입니다.

    컨트롤 플레인과 etcd

    클러스터가 "느리다"는 신고의 뿌리는 거의 항상 여기 있습니다. 온프레미스에서는 이 계층이 전부 내 책임입니다.

    요청 하나가 지나가는 길

    운영자가 kubectl apply를 치면 무슨 일이 벌어지는지 정확히 알아야 어디가 느린지 짚을 수 있습니다.

    1. 인증(Authentication) — 인증서 또는 OIDC 토큰으로 "누구인가"를 판별
    2. 인가(Authorization) — RBAC이 "이 동작이 허용되는가"를 판별
    3. Admission — Mutating 웹훅이 값을 바꾸고, Validating 웹훅이 거부 여부를 결정. 여기 걸린 외부 웹훅이 느리면 클러스터 전체가 느려집니다
    4. etcd 쓰기 — Raft 합의 후 과반 노드 디스크에 fsync. 디스크 지연이 그대로 API 지연
    5. watch 전파 — 스케줄러·컨트롤러·kubelet이 watch로 변경을 수신하고 각자 동작
    가장 위험한 단일 실패점

    Admission 웹훅(정책 엔진, 사이드카 주입기, 이미지 검증기)을 failurePolicy: Fail로 걸어두고 그 파드가 죽으면 클러스터에 아무것도 생성되지 않습니다. 최소한 namespaceSelector로 kube-system을 제외하고, 웹훅 자체는 다중 레플리카 + PDB로 보호하고, timeoutSeconds를 5초 이하로 줄이세요. 신규 웹훅은 반드시 Ignore로 시작해 관측 후 Fail로 승격합니다.

    HA 구성: stacked etcd vs external etcd

    Stacked (기본 권장)

    컨트롤 플레인 노드 3대 각각에 etcd를 함께 올립니다.

    • 서버 3대로 끝나 구축·관리가 단순
    • 노드 1대 손실 = apiserver 1개 + etcd 멤버 1개 동시 손실
    • etcd 전용 디스크(NVMe)를 반드시 분리
    External

    etcd 3대를 별도 서버로 분리합니다.

    • 컨트롤 플레인 부하와 etcd 부하가 서로 간섭하지 않음
    • 서버 6대 이상, 인증서·네트워크 구성 복잡도 증가
    • 노드 1,000대 이상, 또는 etcd를 여러 클러스터가 공유할 때 고려
    홀수 규칙

    etcd는 과반(quorum)으로 동작하므로 멤버 수는 항상 홀수여야 합니다. 4대는 3대와 내결함성이 같으면서 쓰기 지연만 늘어나는 최악의 선택입니다. 7대 이상은 합의 비용이 커져 오히려 느려집니다. 실무 정답은 대부분 3, 아주 크면 5입니다.

    etcd 쿼럼 계산기

    멤버 수를 바꿔가며 몇 대까지 죽어도 클러스터가 쓰기를 계속할 수 있는지 확인하세요.

    API 서버 튜닝

    대규모에서 apiserver가 죽는 가장 흔한 이유는 클라이언트가 던지는 대량 LIST 요청입니다. 파드 1.5만 개인 클러스터에서 kubectl get pods -A를 반복 호출하는 스크립트 하나가 컨트롤 플레인을 마비시킬 수 있습니다.

    kube-apiserver 주요 플래그
    # 동시 요청 제한 — 노드 300대 기준 시작점
--max-requests-inflight=1500
--max-mutating-requests-inflight=500

# API Priority and Fairness: 특정 클라이언트가 전체를 굶기지 못하게 한다
--enable-priority-and-fairness=true

# watch 캐시를 키워 etcd 직접 조회를 줄인다
--default-watch-cache-size=1000
--watch-cache-sizes=pods#5000,nodes#1000,endpointslices#2000

# 이벤트는 오래 둘 이유가 없다. etcd 용량의 주범
--event-ttl=1h

# 감사 로그 (11장에서 상세)
--audit-policy-file=/etc/kubernetes/audit-policy.yaml
--audit-log-maxsize=200 --audit-log-maxbackup=10

# etcd 압축 주기
--etcd-compaction-interval=5m
    API Priority and Fairness(APF)를 실제로 쓰는 법

    APF는 요청을 FlowSchema(누구의 요청인가)와 PriorityLevelConfiguration(얼마나 많은 몫을 줄 것인가)으로 나눠 처리합니다. 특정 배치 잡이 API를 독점하는 상황을 막는 유일한 표준 수단입니다.

    배치 작업용 저순위 레벨 만들기

kind: PriorityLevelConfiguration
metadata: {name: batch-low}
spec:
  type: Limited
  limited:
    nominalConcurrencyShares: 10      # 전체 몫 중 작은 비중
    limitResponse:

    확인용 지표: apiserver_flowcontrol_rejected_requests_total(거부됨), apiserver_flowcontrol_current_inqueue_requests(대기 중). 대기가 늘면 해당 flow의 클라이언트를 찾아 호출 패턴을 고치는 게 정석입니다.

    etcd 운영 — 여기가 심장입니다

    etcd는 모든 쓰기를 과반 노드의 디스크에 fsync한 뒤에야 성공으로 응답합니다. 따라서 etcd 성능은 곧 디스크 지연이고, 디스크 지연은 곧 클러스터 전체의 응답 속도입니다.

    지표의미건강한 값넘으면
    etcd_disk_wal_fsync_duration_seconds p99WAL 디스크 기록 지연< 10ms리더 선출 반복, API 타임아웃
    etcd_disk_backend_commit_duration_seconds p99DB 커밋 지연< 25ms쓰기 전반 지연
    etcd_network_peer_round_trip_time_seconds p99멤버 간 RTT< 50ms합의 실패, 랙 간 지연 의심
    etcd_server_leader_changes_seen_total리더 교체 횟수시간당 0디스크/네트워크 불안정
    etcd_mvcc_db_total_size_in_bytesDB 크기< 4GB쿼터 초과 시 전체 쓰기 중단
    etcd_server_proposals_failed_total합의 실패0쿼럼 불안정
    etcd 디스크 요구사항 — 타협 금지
    • 전용 NVMe/SSD. OS 디스크·컨테이너 이미지 디스크와 물리적으로 분리
    • 네트워크 스토리지(NFS, iSCSI, Ceph RBD) 위에 etcd를 올리지 말 것. fsync 지연으로 반드시 사고가 납니다
    • 가상 머신이면 스토리지 캐시 정책과 다른 VM의 IO 간섭(noisy neighbor)을 확인
    • 디스크 IO 스케줄러와 ionice로 etcd 프로세스 우선순위를 높이는 것도 실효가 있습니다
    etcd 상태 점검 3종 세트 — 온콜 시 첫 명령
    # 컨트롤 플레인 노드에서 실행. 환경변수로 인증서 경로를 잡아둔다
export ETCDCTL_API=3
export ETCDCTL_CACERT=/etc/kubernetes/pki/etcd/ca.crt
export ETCDCTL_CERT=/etc/kubernetes/pki/etcd/server.crt
export ETCDCTL_KEY=/etc/kubernetes/pki/etcd/server.key
export EP=https://127.0.0.1:2379

# 1) 멤버와 리더 확인 — IS LEADER 열이 정확히 하나여야 정상
$ etcdctl --endpoints=$EP endpoint status --write-out=table
$ etcdctl --endpoints=$EP member list -w table

# 2) 건강 상태와 DB 크기
$ etcdctl --endpoints=$EP endpoint health
$ etcdctl --endpoints=$EP endpoint status -w json | jq '.[].Status.dbSize'

# 3) 알람 확인 — NOSPACE가 떠 있으면 이미 쓰기가 막힌 상태
$ etcdctl --endpoints=$EP alarm list

# 무엇이 etcd를 채웠는지 (키 개수 상위 확인)
$ etcdctl --endpoints=$EP get / --prefix --keys-only \
    | grep -v '^$' | cut -d/ -f3,4 | sort | uniq -c | sort -rn | head -20
    DB가 꽉 찼을 때: 압축(compaction)과 조각모음(defrag) 절차

    etcd는 모든 변경의 이전 버전(revision)을 보관합니다. 압축은 오래된 리비전을 논리적으로 지우고, 조각모음은 그렇게 비워진 공간을 실제로 파일 크기에서 회수합니다. 압축만 하면 디스크 사용량은 줄지 않습니다.

    NOSPACE 알람 해제까지의 전체 절차
    # 0) 반드시 스냅샷부터. 이 순서를 어기지 말 것
$ etcdctl --endpoints=$EP snapshot save /backup/before-defrag.db

# 1) 현재 리비전 확인 후 그 지점까지 압축
$ REV=$(etcdctl --endpoints=$EP endpoint status -w json | jq -r '.[0].Status.header.revision')
$ etcdctl --endpoints=$EP compact $REV

# 2) 조각모음은 반드시 "한 번에 한 멤버씩". 해당 멤버는 수 초~수십 초 응답 불가
$ etcdctl --endpoints=https://10.10.1.11:2379 defrag
#    → 완료 확인 후 다음 멤버, 리더는 마지막에
$ etcdctl --endpoints=https://10.10.1.12:2379 defrag
$ etcdctl --endpoints=https://10.10.1.13:2379 defrag

# 3) 알람 해제
$ etcdctl --endpoints=$EP alarm disarm
$ etcdctl --endpoints=$EP alarm list   # 비어 있어야 정상
    절대 하지 말 것

    모든 멤버에 동시에 defrag를 실행하면 쿼럼이 깨져 클러스터 전체가 멈춥니다. 자동화 스크립트를 짤 때 병렬 실행이 되지 않도록 명시적으로 순차 처리하고, 각 단계 사이에 endpoint health 확인을 넣으세요.

    근본 원인 제거가 더 중요합니다. DB를 부풀리는 3대 주범은 ① 무한히 쌓이는 Event(--event-ttl=1h로 해결) ② 컨트롤러 버그로 매초 업데이트되는 리소스(대개 status 갱신 루프) ③ 대량의 Secret/ConfigMap(특히 Helm 릴리스 시크릿 누적, helm history 제한으로 해결)입니다.

    etcd 백업과 복구 — 연 1회는 반드시 실제로 해볼 것

    백업 스크립트가 도는 것과 복구가 되는 것은 완전히 다른 문제입니다. 복구를 한 번도 해보지 않은 백업은 백업이 아닙니다.

    백업: CronJob 또는 systemd timer로 30분마다

set -euo pipefail
TS=$(date +%Y%m%d-%H%M%S)
DEST=/var/backups/etcd
SNAP=$DEST/etcd-$TS.db

etcdctl --endpoints=https://127.0.0.1:2379 snapshot save "$SNAP"

# 무결성 검증까지 해야 백업이다 (hash, revision, total key 확인)
etcdutl snapshot status "$SNAP" -w table

# 원격 오브젝트 스토리지로 전송 — 같은 랙에만 두면 의미가 없다

# 로컬은 7일치만 보관
find $DEST -name 'etcd-*.db' -mtime +7 -delete

    Q. 새벽에 "kubectl 명령이 5초 이상 걸린다"는 신고가 들어왔습니다. 가장 먼저 확인할 지표는?

    정답: 2번. API 지연은 ① etcd 디스크 지연 ② Admission 웹훅 지연 ③ 특정 클라이언트의 LIST 폭주, 이 세 가지가 대부분입니다. 그중 가장 흔하고 파급이 큰 것이 etcd 디스크입니다. etcd_disk_wal_fsync_duration_seconds p99가 평소 3ms에서 80ms로 뛰었다면 원인은 쿠버네티스가 아니라 디스크입니다. 다음으로 apiserver_admission_webhook_admission_duration_seconds와 apiserver_request_duration_seconds를 verb·resource별로 쪼개 보세요.

    네트워킹: CNI · 로드밸런서 · DNS

    클라우드가 대신 해주던 부분이 가장 크게 비는 영역입니다. 트래픽이 들어오는 길을 직접 만들어야 합니다.

    CNI 선택

    iptables/eBPF 기반, BGP로 사내 라우터와 직접 피어링할 수 있다는 점이 온프레미스에서 결정적입니다. 파드 IP를 사내망에 그대로 광고하면 오버레이(VXLAN/IPIP) 없이 통신해 성능 손실과 MTU 문제가 사라집니다.

    • 강점: 성숙한 NetworkPolicy, BGP 지원, 대규모 실적, 문제 발생 시 자료가 많음
    • 주의: iptables 모드에서 서비스가 수천 개를 넘으면 규칙 갱신이 느려짐 → eBPF 데이터플레인 또는 IPVS 병행 검토
    • 운영 포인트: calicoctl node status로 BGP 피어 상태 확인, IPPool 블록 크기와 노드 수의 관계 주의

    eBPF 기반으로 kube-proxy를 완전히 대체할 수 있습니다. 서비스가 많을수록 iptables 대비 이점이 커지고, Hubble로 파드 간 흐름을 실제로 눈으로 볼 수 있다는 점이 운영에서 큰 무기입니다.

    • 강점: L7 정책(HTTP 메서드/경로 단위), 흐름 가시성, 대규모 서비스 성능, 클러스터 간 연결(Cluster Mesh)
    • 주의: 커널 버전 의존성이 큽니다. 사내 표준 OS 커널이 낮으면 기능이 제한되거나 아예 안 됩니다. 도입 전 커널 요구사항 확인이 첫 단계
    • 운영 포인트: cilium status, cilium connectivity test, Hubble UI로 정책 차단 흐름 추적

    가장 단순한 오버레이. 배우기 쉽고 잘 죽지 않지만 NetworkPolicy를 지원하지 않습니다.

    • 적합: 개발용 소규모, 정책이 필요 없는 단일 팀 클러스터
    • 부적합: 멀티테넌시, 규제 대응, 네트워크 격리가 요구되는 운영 환경
    • 정책이 필요해지는 순간 CNI를 바꿔야 하고, 그것은 사실상 클러스터 재구축입니다

    CNI 교체는 전체 파드 재시작 + IP 대역 변경을 동반합니다. 운영 중 교체는 사실상 신규 클러스터 구축 후 마이그레이션입니다. PoC 단계에서 NetworkPolicy·성능·커널 호환성을 반드시 검증하세요.

    MTU — 온프레미스 네트워크 장애 1위

    VXLAN은 50바이트, IPIP는 20바이트의 헤더 오버헤드가 있습니다. 물리 MTU가 1500인데 CNI MTU를 1500으로 두면 큰 패킷만 조용히 유실됩니다. 증상이 "가끔 느리다", "큰 응답만 타임아웃", "TLS 핸드셰이크는 되는데 데이터 전송에서 멈춤"처럼 나타나 원인 찾기가 매우 어렵습니다. 점보 프레임(9000)을 쓴다면 스위치·본딩·NIC 전 구간이 동일해야 합니다.

    MTU 실측
    # 조각화 금지(DF) 플래그로 실제 통과 크기 확인. 1472 성공 = MTU 1500
$ ping -M do -s 1472 -c 3 <다른 노드 IP>
$ ping -M do -s 1422 -c 3 <다른 노드 IP>   # VXLAN 환경 파드 간

# 파드 안에서 실제 인터페이스 MTU 확인
$ kubectl run mtu-test --rm -it --image=nicolaka/netshoot -- ip link show eth0

    MetalLB — L2 모드

    한 노드가 VIP의 ARP에 응답합니다. 스위치 설정이 필요 없어 도입이 쉽지만 모든 트래픽이 그 노드 한 대를 통과하고, 장애 시 ARP 갱신까지 수 초 끊깁니다.

    MetalLB — BGP 모드

    여러 노드가 라우터에 경로를 광고해 ECMP로 분산됩니다. 성능·가용성 모두 우수하지만 네트워크팀과의 협업(AS 번호, 피어 IP, 광고 대역)이 필수입니다. 운영 환경 권장.

    kube-vip / 물리 LB

    kube-vip는 apiserver VIP까지 함께 처리할 수 있어 HAProxy+Keepalived를 대체합니다. 이미 F5·A10 같은 장비가 있다면 NodePort로 받아 장비에서 분산하는 구성이 가장 안정적입니다.

  addresses: ["10.60.10.0/24"]     # 네트워크팀에서 받은 전용 대역
  autoAssign: false                 # 실수로 아무나 가져가지 못하게
---
apiVersion: metallb.io/v1beta1
kind: BGPPeer

  myASN: 64512

    CoreDNS — 규모가 커지면 반드시 문제가 되는 곳

    파드 1.5만 개가 각자 DNS를 조회합니다. 게다가 리눅스의 기본 ndots:5 설정 때문에 api.internal.example.com 같은 이름 하나를 찾는 데 검색 도메인을 붙인 조회가 4~5번 실패한 뒤에야 성공합니다. 즉 실제 DNS 부하는 애플리케이션이 생각하는 것의 5배입니다.

    대규모 클러스터용 CoreDNS Corefile
    .:53 {
    errors
    health { lameduck 10s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
        max_concurrent 2000       # 기본 1000은 대규모에서 부족
        policy sequential           # 사내 DNS 우선순위가 있을 때
    }
    cache 30 {
        success 9984 30
        denial 9984 5          # NXDOMAIN도 캐시해야 부하가 준다
    }
    loop
    reload
    loadbalance
}
    NodeLocal DNSCache 도입

    노드마다 DNS 캐시 DaemonSet을 띄워 대부분의 조회를 로컬에서 끝냅니다. CoreDNS 부하가 크게 줄고 conntrack 소모와 UDP 타임아웃 문제도 완화됩니다. 노드 100대 이상이면 사실상 필수입니다.

    애플리케이션 측 ndots 조정

    외부 도메인을 많이 부르는 파드는 dnsConfig.options: [{name: ndots, value: "2"}]로 불필요한 조회를 없앨 수 있습니다. FQDN 끝에 점을 붙이는 것(example.com.)도 즉효약입니다.

    DNS 장애 판별 3단계
    1. coredns_dns_request_duration_seconds p99와 coredns_forward_healthcheck_broken_total 확인 — 상류(사내 DNS)가 원인인지 판별
    2. 파드 안에서 nslookup kubernetes.default(클러스터 내부)와 외부 도메인을 각각 시도 — 내부/외부 어느 쪽 문제인지 분리
    3. 노드에서 conntrack -S로 insert_failed 증가 확인 — UDP conntrack 경합이면 NodeLocal DNSCache가 답

    Ingress 운영 핵심

    • 리로드 폭풍: NGINX Ingress는 Ingress 리소스가 바뀔 때마다 설정을 다시 만듭니다. 수백 개 Ingress가 있는 클러스터에서 배포가 몰리면 CPU가 튀고 순간 지연이 생깁니다. worker-processes 조정과 Ingress 개수 자체를 줄이는 설계(호스트 단위 통합)를 함께 검토하세요.
    • 타임아웃 계층: 클라이언트 → LB → Ingress → Service → 애플리케이션 각 단계 타임아웃이 바깥쪽이 더 길게 설정돼야 합니다. 역전되면 원인 불명의 502/504가 발생합니다.
    • graceful 종료: 파드가 종료될 때 Endpoint 제거와 프로세스 종료가 동시에 일어나면 진행 중 요청이 끊깁니다. preStop: sleep 5~10 + 애플리케이션의 graceful shutdown + terminationGracePeriodSeconds 조합이 정석입니다.
    • 인증서: cert-manager를 사내 CA(또는 Vault)와 연동해 자동 갱신하세요. 폐쇄망에서 Let's Encrypt를 쓸 수 없으니 사내 ACME 또는 CA Issuer 구성이 필요합니다.

    Q. 특정 서비스 호출이 "평소엔 멀쩡한데 응답 크기가 큰 요청만 타임아웃"됩니다. 가장 유력한 원인은?

    정답: 2번. 작은 패킷은 통과하고 큰 패킷만 사라지는 것은 MTU 불일치의 교과서적 증상입니다. 오버레이 헤더를 감안하지 않은 CNI MTU 설정, 또는 경로 중간 장비의 MTU가 더 작은데 ICMP "Fragmentation Needed"가 방화벽에서 차단되어 Path MTU Discovery가 실패하는 경우입니다. ping -M do -s로 임계 크기를 이분 탐색하면 몇 분 안에 확인됩니다.

    백엔드 선택

    등급별 StorageClass

    reclaimPolicy: Delete의 위험

    기본값 Delete는 PVC를 지우면 실제 데이터도 즉시 삭제합니다. 네임스페이스를 잘못 지우거나 Argo CD가 프루닝하는 순간 운영 DB가 사라집니다. 운영 등급 StorageClass는 Retain으로 만들고, 삭제는 운영자가 수동으로 확인 후 수행하도록 절차를 분리하세요. 또한 중요한 PVC에는 kubernetes.io/pvc-protection이 붙어 있는지, Argo CD 앱에 Prune=false 예외가 걸려 있는지 확인합니다.

    StatefulSet 운영에서 실제로 겪는 것들

    파드가 Pending이고 이벤트에 "volume node affinity conflict"가 보일 때

    PV가 특정 노드/랙에만 존재하는데 스케줄러가 다른 노드를 골랐거나, 이미 만들어진 PV의 노드 어피니티와 파드의 제약이 충돌한 상황입니다.

    확인 순서
    $ kubectl describe pod <pod> | tail -20              # 이벤트 원문 확인
$ kubectl get pvc -n <ns>                            # Bound 여부
$ kubectl get pv <pv> -o yaml | grep -A10 nodeAffinity
$ kubectl get sc <sc> -o yaml | grep volumeBindingMode

    근본 해결은 volumeBindingMode: WaitForFirstConsumer입니다. Immediate면 파드 위치와 무관하게 볼륨이 먼저 만들어져 이런 충돌이 반복됩니다.

    노드가 죽었는데 StatefulSet 파드가 Terminating에서 안 넘어갈 때

    쿠버네티스는 노드와 연락이 끊겼을 때 그 노드에서 파드가 정말 죽었는지 알 수 없습니다. RWO 볼륨을 두 곳에서 동시에 쓰면 데이터가 깨지므로, 확신이 없으면 일부러 기다립니다. 이것은 버그가 아니라 안전장치입니다.

    위험한 명령

    kubectl delete pod --force --grace-period=0는 apiserver에서 기록만 지울 뿐 실제 프로세스를 죽이지 않습니다. 노드가 살아 돌아오면 같은 볼륨을 두 프로세스가 쓰는 스플릿 브레인이 발생합니다. 반드시 노드 전원이 실제로 내려갔음을 확인(iDRAC/IPMI 등)한 뒤에만 사용하세요.

    정석은 노드가 복구 불가임을 확인한 후 kubectl delete node <node>로 노드 객체를 제거하는 것입니다. 그러면 파드가 정리되고 볼륨이 해제됩니다. 자동화가 필요하면 하드웨어 상태를 실제로 확인하는 펜싱(fencing) 연동이 전제입니다.

    PVC 확장
    # 1) StorageClass에 allowVolumeExpansion: true 가 있어야 한다
$ kubectl patch pvc data-postgres-0 -n db \
    -p '{"spec":{"resources":{"requests":{"storage":"500Gi"}}}}'

# 2) 진행 상태 확인 — FileSystemResizePending이면 파드 재시작이 필요
$ kubectl describe pvc data-postgres-0 -n db | grep -A5 Conditions

# 3) StatefulSet의 volumeClaimTemplates는 수정 불가하므로
#    기존 PVC를 개별 확장한 뒤, 템플릿은 다음 재생성 때 반영되도록 관리
$ kubectl delete sts postgres -n db --cascade=orphan
#    → 템플릿 수정 후 재생성. 파드는 살아 있고 PVC도 유지된다

    축소는 불가능합니다. 잘못 크게 잡으면 새 PVC를 만들어 데이터를 옮기는 것 외에 방법이 없습니다.

    스토리지 모니터링에서 꼭 봐야 할 것
    • kubelet_volume_stats_available_bytes — PVC별 잔여 용량. 90% 경고, 95% 긴급
    • kubelet_volume_stats_inodes_free — 용량은 남아도 inode가 고갈되면 쓰기 실패. 작은 파일이 많은 워크로드에서 실제로 발생
    • CSI 컨트롤러 파드 재시작 횟수 — 조용히 죽어 있으면 신규 PVC가 전부 Pending
    • 백엔드 자체 지표(Ceph OSD 상태, 리밸런싱 진행률) — 쿠버네티스 지표만 봐서는 원인이 안 보입니다

    스케줄링과 리소스 관리

    물리 서버가 자동으로 늘어나지 않는 환경에서는 "잘 배치하는 것"이 곧 비용 절감이고 가용성입니다.

    requests와 limits가 실제로 하는 일

    CPU메모리
    requests스케줄링 기준이자 경합 시 최소 보장량(cgroup weight)스케줄링 기준. 실제 사용을 제한하지 않음
    limits초과 시 스로틀링. 죽지는 않지만 느려짐초과 시 즉시 OOMKilled. 유예 없음
    미설정 시노드 자원을 무제한 경쟁노드 메모리를 다 먹고 다른 파드까지 축출시킴
    CPU limit은 신중하게

    CPU limit은 CFS 쿼터로 100ms 단위 주기마다 사용량을 자릅니다. 멀티스레드 애플리케이션(특히 JVM, Go)은 짧은 순간에 여러 코어를 쓰다가 주기 초반에 쿼터를 소진하고 남은 시간 동안 강제로 멈춥니다. 평균 사용률은 30%인데 p99 지연이 튀는 전형적 원인입니다. container_cpu_cfs_throttled_periods_total을 확인하고, 지연에 민감한 서비스는 limit을 넉넉히 주거나 아예 제거(단, requests는 반드시 설정)하는 선택지를 검토하세요. 반대로 메모리 limit은 반드시 설정합니다 — 메모리는 스로틀이 없어 노드 전체를 위험에 빠뜨립니다.

    배치 제어 도구 정리

    nodeSelector / nodeAffinity

    "어떤 노드에 갈 수 있는가". GPU 노드, 특정 세대 하드웨어, 라이선스가 있는 노드로 제한할 때 씁니다. required는 강제, preferred는 가중치.

    taint / toleration

    "이 노드는 아무나 오지 마라". 노드 쪽에서 거는 방어입니다. GPU·infra 노드에 taint를 걸고 해당 워크로드만 toleration을 갖게 하는 것이 표준 패턴입니다.

    podAntiAffinity

    "같은 앱끼리 붙지 마라". 강력하지만 대규모에서 스케줄링 비용이 큽니다. 노드 수백 대 × 파드 수천 개면 스케줄러가 느려지므로 topologySpread를 우선 검토하세요.

    topologySpreadConstraints

    "랙/노드에 고르게 펴라". antiAffinity보다 표현력이 좋고 비용이 낮습니다. 현대 클러스터의 기본 도구입니다.

    테넌트 격리 4단계

    1. 자원 격리 — ResourceQuota / LimitRange

    네임스페이스가 쓸 수 있는 총량을 제한하고, 개별 파드의 기본값·최댓값을 강제합니다. 이게 없으면 한 팀이 클러스터 전체 자원을 요청해 버릴 수 있습니다.

    2. 권한 격리 — RBAC

    팀은 자기 네임스페이스만. 클러스터 범위 리소스(CRD, ClusterRole, PV)는 플랫폼팀만. cluster-admin 배포는 감사 대상입니다.

    3. 네트워크 격리 — NetworkPolicy

    기본이 전체 허용이므로 기본 차단 정책부터 깔고 필요한 통신만 여는 방식으로 갑니다.

    4. 실행 격리 — Pod Security / 정책 엔진

    특권 컨테이너, hostPath, hostNetwork를 막습니다. 이것이 뚫리면 위 세 개는 의미가 없습니다.

    GitOps 기반 배포 운영

    클러스터가 여러 개가 되는 순간, 사람이 kubectl로 관리하는 방식은 반드시 무너집니다.

    왜 GitOps가 온프레미스에서 더 중요한가

    • 재구축 가능성: 클러스터가 통째로 날아가도 Git이 있으면 복원할 수 있습니다. 관리형 서비스가 없는 환경에서 이건 생존 수단입니다.
    • 드리프트 제거: "누가 언제 손으로 바꿨는지 모르는 설정"이 온프레미스 장애의 큰 축입니다. 자동 동기화가 이를 원천 차단합니다.
    • 감사 대응: 누가 무엇을 언제 왜 바꿨는지가 PR 이력으로 남습니다. 규제 환경에서 특히 강력합니다.
    • 다중 클러스터 일관성: 클러스터 5개에 같은 정책을 적용하는 유일하게 지속 가능한 방법입니다.

    Argo CD ApplicationSet: 클러스터 40개에 같은 플랫폼 스택 배포
    apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: {name: platform-stack, namespace: argocd}
spec:
  generators:
  - matrix:
      generators:
      - clusters:                       # 등록된 클러스터를 자동 순회
          selector:
            matchLabels: {env: prod}
      - list:
          elements:
          - {component: cilium}
          - {component: ingress-nginx}
          - {component: monitoring}
  template:
    metadata:
      name: '{{name}}-{{component}}'
    spec:
      project: platform
      source:
        repoURL: https://git.example.com/platform-gitops.git
        targetRevision: main
        path: 'platform/{{component}}'
        helm:
          valueFiles: [values.yaml, '../../clusters/{{name}}/values/{{component}}.yaml']
      destination: {server: '{{server}}', namespace: '{{component}}'}
      syncPolicy:
        automated: {prune: true, selfHeal: true}
        syncOptions: [CreateNamespace=true, ServerSideApply=true]
        retry:
          limit: 5
          backoff: {duration: 30s, factor: 2, maxDuration: 10m}
    selfHeal과 prune의 양날

    selfHeal: true는 긴급 상황에서 운영자가 수동으로 한 조치를 자동으로 되돌립니다. 장애 대응 중 "분명히 replicas를 늘렸는데 다시 줄어든다"는 혼란이 여기서 옵니다. 긴급 조치 시에는 앱의 자동 동기화를 먼저 끄거나, 아예 Git에 커밋하는 문화를 만드세요. prune: true는 Git에서 지운 것을 클러스터에서도 지웁니다. PVC나 CRD에는 argocd.argoproj.io/sync-options: Prune=false로 예외를 걸어 사고를 막습니다.

    규모가 커지면 Prometheus 한 대로는 안 됩니다

    노드 100대, 활성 시계열 200만 개 수준까지는 잘 버팁니다. 메모리는 대략 활성 시계열 100만 개당 3~5GB를 잡습니다.

    • 한계: 보관 기간이 로컬 디스크에 묶임, HA를 하려면 동일 설정 2대를 띄우고 중복 데이터를 감수해야 함, 재시작 시 WAL 재생 시간이 길어짐
    • 이 단계에서 할 일: 스크랩 간격 조정(30s), 불필요한 지표 drop, 보관 기간 15일 고정

    기존 Prometheus에 사이드카를 붙여 오브젝트 스토리지로 블록을 올리는 방식. 구성 변경이 가장 적어 온프레미스에서 채택률이 높습니다.

    • 구성: Sidecar(업로드) + Store Gateway(과거 조회) + Querier(통합 질의) + Compactor(다운샘플링) + Ruler(전역 규칙)
    • 장점: 여러 클러스터의 Prometheus를 하나의 Querier로 묶어 전역 뷰 제공. MinIO 같은 사내 S3 호환 스토리지와 잘 맞음
    • 주의: Compactor는 버킷당 반드시 1개만 실행해야 합니다. 중복 실행 시 블록이 손상됩니다. 그리고 장기 조회 성능은 Store Gateway 캐시 튜닝에 크게 좌우됩니다

    수평 확장을 전제로 설계된 시계열 저장소. 수집·조회·규칙 컴포넌트가 분리돼 있고 테넌트 단위 격리가 기본입니다.

    • 장점: 초대형 규모(수천만 시계열), 테넌트별 한도 설정, 조회 캐시 계층이 잘 갖춰짐
    • 단점: 컴포넌트가 많아 운영 부담이 큽니다. 소규모 팀이 도입하면 모니터링 시스템 자체가 장애 원인이 됩니다
    • 적합: 전사 관측 플랫폼을 별도 팀이 운영하는 조직

    단일 바이너리 또는 클러스터 모드 모두 지원. 같은 데이터를 훨씬 적은 자원으로 저장하는 것이 최대 강점입니다.

    로깅과 트레이싱

    로그는 용량 계획을 안 하면 반드시 스토리지를 터뜨립니다. 온프레미스에서는 디스크가 무한하지 않습니다.

    로그가 흘러가는 길

    컨테이너의 stdout/stderr → 컨테이너 런타임이 /var/log/pods/에 파일로 기록 → 노드의 수집 에이전트(DaemonSet)가 읽어 파싱·라벨링 → 중앙 저장소로 전송 → 조회. 애플리케이션은 파일이 아니라 stdout으로 로그를 내보내야 합니다. 파일에 쓰면 수집기가 못 보고, 사이드카를 붙이면 자원만 두 배로 듭니다.

    노드 디스크 방어

    컨테이너 로그 로테이션을 설정하지 않으면 로그 하나가 노드 디스크를 다 채워 DiskPressure로 그 노드의 모든 파드가 축출됩니다. kubelet 설정에 containerLogMaxSize: 50Mi, containerLogMaxFiles: 3을 반드시 넣으세요. 노드당 로그 상한 = 50Mi × 3 × 파드 수로 계산해 디스크를 잡습니다.

    • 주의: 레이블 카디널리티가 곧 성능입니다. pod나 trace_id를 레이블로 만들면 스트림이 폭발해 Loki가 죽습니다. 레이블은 namespace, app, level 수준으로 제한하고 나머지는 본문 검색으로 처리하세요.
    • 전문 검색이 약합니다. "전체 기간에서 이 문자열" 같은 조회에는 부적합합니다.

    전문 검색과 복잡한 집계가 필요할 때. 보안 감사, 장기 분석에 강합니다.

    • 필수 설정: ILM(Index Lifecycle Management)으로 hot → warm → cold → delete 단계를 정의하지 않으면 반드시 디스크가 터집니다.
    • 샤드 설계: 샤드 하나당 30~50GB가 적정. 샤드를 너무 잘게 나누면 마스터 노드 부하가 커집니다.
    • 비용: 인덱싱 때문에 원본 대비 저장량이 늘어나고, 노드도 많이 필요합니다. Loki 대비 몇 배의 자원을 각오해야 합니다.

    • 샘플링이 핵심입니다. 100% 수집은 감당이 안 됩니다. 테일 샘플링으로 에러가 있거나 느린 트레이스만 남기면 비용을 1/50로 줄이면서 필요한 것은 다 잡습니다.
    • 로그에 trace_id를 남기고 Grafana에서 지표 → 트레이스 → 로그로 이동하게 연결하면 조사 시간이 극적으로 줄어듭니다.

    암기가 아니라 판단을 묻는 질문들입니다. 각 답변 아래의 "면접관이 보는 것"이 실제 평가 기준입니다.

    Q01큰 클러스터 하나와 작은 클러스터 여러 개, 무엇을 기준으로 결정합니까?아키텍처

    기술 선호가 아니라 장애 반경, 규제 요건, 운영 인력 세 축으로 결정합니다. 첫째, 한 클러스터가 죽었을 때 멈추는 서비스의 범위가 조직이 감내할 수 있는 수준인지. 둘째, 망분리·개인정보처럼 물리적 분리가 요구되는 워크로드가 있는지. 셋째, 클러스터가 늘어나면 반드시 GitOps로 형상을 통일해야 하는데 그 역량과 인력이 있는지.

    실무 기본값은 환경 분리(prod/stg/dev) + 규제 등급 분리 + 관리 클러스터 1개입니다. 관리 클러스터에 Argo CD와 관측 스택의 장기 저장소를 두면, 운영 클러스터가 통째로 죽어도 관측과 복구 수단이 살아 있습니다. 반대로 팀 단위로 클러스터를 쪼개는 것은 대개 실패합니다. 자원 효율이 급격히 나빠지고 애드온 관리 부담이 팀 수만큼 늘어나기 때문입니다. 팀 격리는 클러스터가 아니라 네임스페이스 + 쿼터 + NetworkPolicy + 정책 엔진으로 푸는 것이 맞습니다.

    면접관이 보는 것 — "여러 개가 좋다/하나가 좋다"의 단정이 아니라, 조직 상황을 조건으로 삼아 답하는지. 관측 스택을 감시 대상과 분리해야 한다는 지점을 스스로 짚는지.

    Q02Pod CIDR과 node-cidr-mask-size는 어떻게 정합니까? 잘못 정하면 어떻게 됩니까?아키텍처

    수용 가능한 노드 수는 2^(node-cidr-mask-size − cluster-cidr-mask)입니다. 10.244.0.0/16에 /24를 쓰면 256노드가 상한이고, 257번째 노드부터는 controller-manager가 PodCIDR을 배정하지 못해 노드가 Ready로 보여도 파드가 IP를 못 받습니다. 그리고 이 값은 운영 중 변경이 사실상 불가능합니다. 클러스터 재구축이 필요합니다.

    정하는 순서는 이렇습니다. ① 3년치 목표 노드 수의 2배를 잡는다 ② 노드당 maxPods를 정하고 그보다 여유 있는 마스크를 고른다(maxPods 110이면 /25로도 되지만 /24가 안전) ③ 사내망·VPN·파트너망과 겹치지 않는 대역을 네트워크팀과 문서로 확정한다 ④ 향후 만들 클러스터들의 대역까지 미리 예약한다. Service CIDR도 같은 원칙이고, MetalLB VIP 풀은 별도 대역으로 잡습니다.

    Calico처럼 IPPool 블록 크기를 별도로 갖는 CNI를 쓴다면 그 블록 크기도 함께 계산해야 합니다. 노드당 블록이 부족하면 다른 노드의 블록을 빌려 쓰면서 라우팅 경로가 지저분해집니다.

    면접관이 보는 것 — 되돌릴 수 없는 결정이라는 인식, 그리고 사내 네트워크팀과의 협의를 설계 과정에 포함시키는지.

    Q03클러스터 규모를 키울 때 가장 먼저 한계에 부딪히는 곳은 어디입니까?아키텍처

    공식 상한은 5,000노드·15만 파드지만 현실에서 먼저 막히는 지점은 따로 있습니다. 순서대로 ① etcd 디스크 성능 — 객체가 늘수록 쓰기 지연이 전체 API 지연이 됩니다 ② apiserver의 watch/LIST 부하 — 파드 수만 개 규모에서 전체 LIST를 반복하는 클라이언트 하나가 컨트롤 플레인을 마비시킵니다 ③ kube-proxy iptables 규칙 갱신 — 서비스 수천 개에서 규칙 재작성이 초 단위로 늘어납니다 ④ Pod CIDR 소진 ⑤ 롤링 업그레이드 소요 시간 — 노드 1,000대면 물리적으로 며칠이 걸립니다.

    대응은 각각 다릅니다. etcd는 전용 NVMe와 압축·조각모음, apiserver는 watch 캐시 확대와 APF, kube-proxy는 IPVS 또는 eBPF 전환, 업그레이드는 병렬 배치 크기 조정입니다. 그리고 어느 지점이 한계에 가까운지를 분기마다 지표로 확인하는 습관이 중요합니다.

    면접관이 보는 것 — 문서상의 숫자를 외운 게 아니라, 실제로 무엇이 먼저 아픈지를 경험적으로 아는지.

    Q04etcd 멤버는 왜 홀수여야 합니까? 5대는 3대보다 안전합니까?컨트롤 플레인·etcd

    etcd는 Raft 합의를 쓰므로 쓰기가 성공하려면 과반(N/2 + 1)의 동의가 필요합니다. 3대는 과반이 2라 1대 손실을 견디고, 4대는 과반이 3이라 역시 1대만 견딥니다. 즉 4대는 3대와 내결함성이 같으면서 합의에 참여할 노드만 늘어 쓰기 지연이 커지는 순수한 손해입니다. 그래서 홀수를 씁니다.

    5대는 2대 손실을 견디므로 내결함성은 확실히 높습니다. 다만 모든 쓰기가 3대의 디스크에 fsync돼야 하므로 쓰기 지연이 늘고, 멤버 간 네트워크 왕복도 늘어납니다. 실무 판단은 이렇습니다. 랙이 3개 이상이고 노드가 수백 대 수준이면 3대로 충분합니다. 5대를 고려하는 경우는 ① 랙/전원 도메인이 5개 이상이고 동시에 2개가 나갈 시나리오가 현실적이거나 ② 유지보수 중(1대 down)에도 1대 추가 장애를 견뎌야 하는 요건이 있을 때입니다.

    더 중요한 것은 멤버를 서로 다른 실패 도메인에 두는 것입니다. 3대가 모두 같은 랙, 같은 전원 계통에 있으면 홀수든 짝수든 의미가 없습니다.

    면접관이 보는 것 — 4대가 왜 나쁜지 정확히 설명하는지, 그리고 멤버 수보다 배치가 중요하다는 점을 언급하는지.

    Q05etcd DB 크기가 계속 커집니다. 원인과 대응을 설명하세요.컨트롤 플레인·etcd

    etcd는 모든 변경의 이전 리비전을 보관하므로, 변경이 잦으면 실제 데이터보다 히스토리가 훨씬 커집니다. 기본 쿼터(2GB)를 넘으면 NOSPACE 알람이 뜨고 클러스터 전체 쓰기가 중단됩니다. 파드 생성도, 스케일도, 아무것도 안 됩니다.

    대응은 두 단계입니다. 즉시 조치는 스냅샷 확보 → 현재 리비전까지 compact → 멤버를 한 대씩 순차적으로 defrag → alarm disarm입니다. 압축만 하면 논리적으로만 지워지고 파일 크기는 안 줄기 때문에 조각모음이 필요합니다. 여기서 절대 하지 말아야 할 것은 모든 멤버 동시 defrag입니다. 쿼럼이 깨져 클러스터가 멈춥니다.

    근본 대응이 더 중요합니다. 원인 상위 3가지는 ① Event 누적 — --event-ttl=1h로 해결 ② 컨트롤러의 status 갱신 루프 — 특정 CRD가 초당 수십 번 업데이트되는 버그가 흔합니다. 키 접두사별 개수를 세어 범인을 찾습니다 ③ Helm 릴리스 시크릿 누적 — --history-max로 제한합니다. 그리고 --auto-compaction-retention과 --quota-backend-bytes=8589934592를 미리 설정해 두고, DB 크기를 상시 모니터링합니다.

    면접관이 보는 것 — compact와 defrag의 차이를 정확히 아는지, 순차 실행의 필요성을 아는지, 증상 완화가 아니라 원인 제거까지 말하는지.

    Q06etcd 3대 중 2대가 동시에 죽었습니다. 어떻게 대응합니까?컨트롤 플레인·etcd

    쿼럼을 잃었으므로 모든 쓰기가 중단됩니다. 다만 중요한 사실이 있습니다. 이미 실행 중인 파드는 계속 동작합니다. kubelet은 로컬 상태로 컨테이너를 유지하고, 이미 프로그래밍된 kube-proxy 규칙과 CNI 경로도 유지됩니다. 그래서 첫 번째 판단은 "서비스가 죽은 게 아니라 변경이 막힌 것"임을 인지하고 불필요한 재시작·드레인·롤아웃을 즉시 중단시키는 것입니다. 이 상황에서 누군가 파드를 재시작하면 그 파드는 다시 못 뜹니다.

    다음으로 복구 가능성부터 확인합니다. 죽은 2대가 하드웨어 문제인지 프로세스 문제인지, 데이터 디렉터리가 살아 있는지. 데이터가 온전하다면 그냥 기동해서 쿼럼을 되찾는 것이 가장 빠르고 데이터 손실이 없습니다.

    데이터가 손상됐다면 스냅샷 복구로 갑니다. ① 남은 1대에서 스냅샷을 뜨거나 최신 백업을 선택 ② 세 노드 모두 apiserver·etcd 정적 파드를 내림 ③ 데이터 디렉터리를 지우지 말고 이름만 변경해 보관 ④ 각 노드에서 자기 이름·peer URL로 snapshot restore, 이때 --initial-cluster-token을 새로 지정 ⑤ etcd 기동 → health 확인 → apiserver 기동 ⑥ 검증. 스냅샷 시점 이후의 변경은 사라지므로, 그 사이 배포는 Argo CD 동기화로 되살리고 PVC·Secret 수동 변경분은 따로 확인해야 합니다.

    면접관이 보는 것 — 워크로드는 살아 있다는 사실을 아는지(당황 여부의 척도), 그리고 복구 순서에서 "데이터 디렉터리 보존"과 "토큰 갱신"을 언급하는지.

    Q07kubectl 응답이 5초 이상 걸립니다. 어떻게 원인을 좁혀 갑니까?컨트롤 플레인·etcd

    • 자원: apiserver 파드의 CPU·메모리, 그리고 apiserver_current_inflight_requests가 상한에 붙어 있는지.

    면접관이 보는 것 — 지표 이름을 구체적으로 대는지, 그리고 "재시작"이 아니라 원인 격리로 가는지.

    Q08API Priority and Fairness는 무엇이고 언제 씁니까?컨트롤 플레인·etcd

    APF는 apiserver로 들어오는 요청을 FlowSchema(어떤 주체의 어떤 요청인가)로 분류하고 PriorityLevelConfiguration(각 분류에 얼마의 동시 처리 몫을 줄 것인가)으로 제한하는 기능입니다. 예전의 단순한 max-inflight 제한은 "누가 보낸 요청인지" 구분하지 못해, 배치 잡 하나가 전체 슬롯을 먹으면 kubelet의 정상 요청까지 막혔습니다. APF는 이를 공정 큐로 해결합니다.

    실무에서 쓰는 시나리오는 세 가지입니다. ① 특정 팀의 CI/CD나 배치 작업이 API를 독점하지 못하게 저순위 레벨로 격리 ② 시스템 컴포넌트(kubelet, scheduler)의 몫을 보장해 장애 시에도 클러스터 제어권을 유지 ③ 장애 조사 중 폭주하는 클라이언트를 즉시 격리하는 응급 수단.

    모니터링 지표는 apiserver_flowcontrol_rejected_requests_total(거부), apiserver_flowcontrol_current_inqueue_requests(대기), apiserver_flowcontrol_request_wait_duration_seconds(대기 시간)입니다. 다만 APF는 증상 완화 수단이라는 점을 분명히 해야 합니다. 근본은 그 클라이언트가 왜 전체 LIST를 반복하는지 고치는 것, 즉 informer/watch 기반으로 전환하게 하는 것입니다.

    면접관이 보는 것 — 기능 설명에 그치지 않고 "왜 max-inflight로는 부족한가"를 설명하는지, 그리고 근본 해결과 완화를 구분하는지.

    Q09Admission 웹훅이 클러스터를 죽일 수 있다고 합니다. 어떻게 안전하게 운영합니까?컨트롤 플레인·etcd

    웹훅은 모든 생성·변경 요청의 경로에 끼어 있습니다. failurePolicy: Fail인 웹훅의 백엔드가 죽으면 그 대상 범위의 모든 쓰기가 실패합니다. 최악은 웹훅이 자기 자신의 네임스페이스도 대상으로 잡는 경우입니다. 웹훅 파드가 죽으면 그 파드를 다시 띄우는 것조차 막혀 자기 복구가 불가능한 교착에 빠집니다.

    안전 설계 원칙은 이렇습니다.

    • namespaceSelector로 kube-system과 웹훅 자신의 네임스페이스를 반드시 제외
    • timeoutSeconds를 5초 이하로. 기본 10초는 apiserver 지연으로 직결됩니다
    • rules의 대상 리소스를 최소화. 모든 리소스를 잡는 와일드카드는 금물
    • 웹훅 백엔드는 다중 레플리카 + PDB + 노드 분산 + 고순위 PriorityClass
    • 신규 웹훅은 failurePolicy: Ignore로 배포해 지연·오류율을 관측한 뒤 Fail로 승격
    • objectSelector로 레이블 기반 대상 축소도 유효한 수단

    교착에 빠졌을 때의 탈출 방법도 알아 둬야 합니다. 컨트롤 플레인에서 kubectl delete validatingwebhookconfiguration <name>으로 웹훅 등록 자체를 지우는 것입니다. 이 명령이 필요할 상황을 대비해 비상 접근 수단(break-glass kubeconfig)을 별도로 보관합니다.

    면접관이 보는 것 — 자기 참조 교착을 아는지, 그리고 "웹훅 등록 삭제"라는 탈출구를 알고 있는지.

    Q10온프레미스에서 CNI를 고르는 기준을 설명하세요.네트워크

    네 가지를 순서대로 봅니다. ① 커널 버전 — Cilium의 주요 기능은 상대적으로 최신 커널을 요구합니다. 사내 표준 OS를 바꿀 수 없다면 여기서 선택지가 먼저 좁혀집니다 ② 파드 IP를 사내망에 노출해야 하는가 — 레거시 시스템이 파드에 직접 접근해야 한다면 BGP로 라우팅하는 Calico가 자연스럽습니다 ③ 서비스 규모 — 서비스가 수천 개를 넘으면 iptables 갱신 지연이 실측 가능한 수준이 되므로 eBPF나 IPVS가 필요합니다 ④ 정책 요구 수준 — L3/L4면 어느 쪽이든 되지만, HTTP 메서드·경로 단위 통제가 필요하면 Cilium이나 서비스 메시입니다.

    추가로 반드시 고려할 것은 운영 가시성입니다. 네트워크 문제는 원인을 못 찾으면 며칠이 갑니다. Cilium의 Hubble처럼 "어떤 정책이 어떤 흐름을 떨어뜨렸는지" 보여주는 도구가 있으면 조사 시간이 극적으로 줄어듭니다.

    그리고 반드시 덧붙여야 할 말은 CNI 교체는 사실상 클러스터 재구축이라는 점입니다. 전체 파드 재시작과 IP 대역 변경을 동반합니다. 그래서 PoC 단계에서 정책·성능·커널 호환성을 실제 부하로 검증하는 것이 선택 자체보다 중요합니다.

    면접관이 보는 것 — 유행하는 제품 이름이 아니라 제약 조건에서 출발하는지. 교체 비용을 아는지.

    Q11kube-proxy의 iptables, IPVS, eBPF 모드를 비교하세요.네트워크

    iptables 모드는 서비스마다 규칙 체인을 만들고, 규칙 매칭이 선형에 가깝습니다. 서비스가 늘면 규칙 수가 폭증하고, 무엇보다 규칙을 갱신할 때 전체를 다시 쓰는 방식이라 서비스 수천 개에서는 갱신에 수 초가 걸립니다. 이 지연 동안 새 엔드포인트가 반영되지 않아 배포 중 간헐적 오류가 납니다.

    IPVS 모드는 커널의 로드밸런서를 쓰므로 해시 테이블 기반이라 서비스 수에 따른 조회 성능 저하가 거의 없고, rr·lc·sh 같은 분산 알고리즘도 선택할 수 있습니다. 다만 conntrack에 의존하는 점은 같고, 일부 엣지 케이스(NodePort와 방화벽 상호작용)에서 iptables 규칙이 여전히 필요합니다.

    eBPF(Cilium kube-proxy replacement)는 kube-proxy 자체를 대체하고 소켓 레벨에서 로드밸런싱을 수행합니다. 서비스 수 확장성이 가장 좋고, conntrack 부담도 자체 맵으로 완화됩니다. 대가는 커널 요구사항과 디버깅 방식의 변화입니다. iptables -L로 보이지 않으니 cilium CLI와 Hubble에 익숙해져야 합니다.

    판단 기준은 단순합니다. 서비스 수백 개 수준이면 iptables로 충분하고, 수천 개를 넘거나 배포 중 지연이 관측되면 IPVS나 eBPF로 옮길 시점입니다.

    면접관이 보는 것 — "성능이 좋다" 수준이 아니라, 규칙 갱신 지연이라는 구체적 실패 양상을 아는지.

    Q12"큰 응답만 타임아웃"되는 증상을 어떻게 진단합니까?네트워크

    MTU 불일치를 최우선으로 의심합니다. 작은 패킷은 통과하고 큰 패킷만 사라지는 것이 이 문제의 서명입니다. 원인은 대개 셋입니다. ① 오버레이 헤더(VXLAN 50B, IPIP 20B)를 감안하지 않고 CNI MTU를 물리 MTU와 같게 설정 ② 경로 중간 장비의 MTU가 더 작은데 방화벽이 ICMP "Fragmentation Needed"를 차단해 Path MTU Discovery가 실패 ③ 본딩·VLAN 구간의 MTU 불일치.

    진단은 ping -M do -s <크기>로 DF 플래그를 세워 이분 탐색합니다. 노드 간, 파드 간을 각각 측정해 어느 구간에서 값이 줄어드는지 확인하면 문제 구간이 특정됩니다. 파드 안에서 ip link show eth0으로 실제 적용된 MTU도 확인합니다.

    해결은 CNI 설정의 MTU를 물리 MTU에서 오버레이 오버헤드를 뺀 값으로 맞추는 것입니다. 점보 프레임을 쓴다면 NIC·본딩·스위치·라우터 전 구간이 동일해야 하며, 한 구간만 1500이면 전체가 그 값에 묶입니다. 참고로 이 증상은 TLS 핸드셰이크는 성공하고 데이터 전송에서 멈추는 형태로도 나타나 애플리케이션 문제로 오인되기 쉽습니다.

    면접관이 보는 것 — 애플리케이션 레벨로 시선이 가지 않고 L3/L2로 내려가는지. 실제 측정 명령을 아는지.

    Q13externalTrafficPolicy를 Local로 두는 이유와 부작용은?네트워크

    Cluster(기본값)는 어느 노드로 들어온 트래픽이든 클러스터 내 임의의 파드로 다시 전달합니다. 부하는 고르게 퍼지지만 SNAT이 일어나 클라이언트 실제 IP가 사라지고 홉이 하나 늘어납니다. Local은 트래픽을 받은 노드에 있는 파드로만 보냅니다. 클라이언트 IP가 보존되고 홉이 줄어 지연도 낮아집니다.

    부작용은 해당 노드에 파드가 없으면 트래픽이 버려진다는 점입니다. 그리고 노드별 파드 수가 다르면 부하가 불균등해집니다. 노드 A에 파드 1개, 노드 B에 파드 3개인데 LB가 노드 단위로 균등 분산하면 A의 파드가 3배의 부하를 받습니다.

    그래서 Local을 쓸 때는 반드시 함께 가야 하는 것들이 있습니다. ① Ingress Controller를 DaemonSet으로 돌리거나 노드마다 최소 1개가 뜨도록 topologySpread 적용 ② LB의 헬스체크가 healthCheckNodePort를 보도록 구성 — MetalLB나 외부 LB가 파드 없는 노드를 자동으로 제외하게 하는 핵심 장치입니다 ③ PDB로 롤링 업데이트 중 특정 노드의 파드가 0이 되지 않게 보호.

    클라이언트 IP가 꼭 필요한데 이 구성이 부담스럽다면, L7 계층에서 X-Forwarded-For나 PROXY 프로토콜로 해결하는 선택지도 있습니다.

    면접관이 보는 것 — 장점만이 아니라 healthCheckNodePort까지 언급하는지. 실제로 502를 겪어본 사람만 아는 부분입니다.

    Q14대규모 클러스터에서 DNS가 느려집니다. 무엇을 확인하고 어떻게 개선합니까?네트워크

    확인 순서는 ① coredns_dns_request_duration_seconds p99와 요청량 추이 ② coredns_forward_healthcheck_broken_total — 상류 사내 DNS가 문제인지 판별 ③ 파드 내부에서 클러스터 내부 이름과 외부 도메인을 각각 조회해 어느 쪽이 느린지 분리 ④ 노드에서 conntrack -S의 insert_failed 증가 확인 — UDP conntrack 경합이면 재시도 타임아웃(5초)이 발생해 체감 지연이 큽니다.

    개선은 세 방향입니다. ① NodeLocal DNSCache 도입 — 노드 100대 이상이면 사실상 필수입니다. 대부분의 조회를 로컬에서 끝내고 상류로는 TCP를 써서 UDP conntrack 문제를 우회합니다 ② CoreDNS의 cache 확대와 denial 캐시 활성화, max_concurrent 상향 ③ 애플리케이션 측에서 FQDN 끝에 점을 붙이거나 dnsConfig로 ndots를 낮추기. 그리고 CoreDNS 자체는 HPA나 cluster-proportional-autoscaler로 노드 수에 비례해 확장하도록 둡니다.

    면접관이 보는 것 — ndots의 존재를 아는지. 이걸 아는 사람과 모르는 사람의 DNS 문제 해결 속도가 완전히 다릅니다.

    한 번에 default-deny를 적용하면 DNS부터 막혀 전 서비스가 죽습니다. 단계적으로 갑니다.

    2. 정책 초안 생성: 수집한 흐름에서 네임스페이스·앱 단위 허용 규칙을 도출합니다. 도구로 자동 생성한 뒤 사람이 검토하는 방식이 현실적입니다.
    3. DNS 예외를 표준 세트로: 모든 네임스페이스에 default-deny와 allow-dns를 한 쌍으로 배포하는 템플릿을 만듭니다. 이걸 분리하면 반드시 사고가 납니다.
    4. 비운영 환경부터: dev → stg에서 최소 2주 관찰. 이 기간에 나오는 차단 로그가 곧 누락된 규칙입니다.
    5. 운영은 네임스페이스 단위로: 한 번에 전체가 아니라 팀 하나씩, 롤백 가능한 단위로 적용합니다.
    6. 모니터링 상시화: 차단된 흐름을 대시보드로 만들어 두면 이후 신규 배포에서 발생하는 문제를 즉시 잡습니다.

    추가로 챙길 것은 egress입니다. 외부 API·DB·레거시 시스템으로 나가는 트래픽을 막으면 영향이 크므로, CIDR 기반 예외를 먼저 정의합니다. 그리고 kube-system과 모니터링 네임스페이스의 스크랩 경로를 반드시 허용해야 합니다. 안 그러면 Prometheus가 지표를 못 가져와 관측이 눈멀게 됩니다.

    면접관이 보는 것 — DNS 함정과 모니터링 스크랩 경로를 미리 언급하는지. 두 가지 모두 실제로 사고를 낸 사람만 챙깁니다.

    Q16운영용 StorageClass를 설계할 때 무엇을 신경 씁니까?스토리지

    네 가지 필드가 사고를 가르는 지점입니다.

    • reclaimPolicy: 기본값 Delete는 PVC를 지우면 데이터도 즉시 사라집니다. 네임스페이스 오삭제나 GitOps 프루닝 한 번에 운영 DB가 날아갑니다. 운영 등급은 반드시 Retain으로 만들고, 실제 삭제는 운영자가 별도 승인 절차로 수행합니다.
    • volumeBindingMode: WaitForFirstConsumer가 기본 선택입니다. 파드가 갈 노드를 정한 뒤 볼륨을 만들어야 토폴로지 충돌(volume node affinity conflict)이 생기지 않습니다. Immediate는 다중 랙 환경에서 반드시 문제를 만듭니다.
    • allowVolumeExpansion: true로 켜둡니다. 나중에 켜려면 기존 PV에는 소급 적용되지 않는 경우가 있어 처음부터 켜는 것이 안전합니다. 축소는 불가능하다는 점을 사용자에게 명확히 안내해야 합니다.
    • 등급 분리: fast-retain(NVMe, Retain), standard-delete(HDD, Delete, 개발용), shared-rwx(CephFS/NFS)처럼 성능과 정책이 조합된 등급을 만들어 두고, 기본 StorageClass는 가장 안전한 것으로 지정합니다.

    추가로 챙길 것은 ResourceQuota의 requests.storage와 persistentvolumeclaims 개수 제한입니다. 스토리지는 한 번 소비되면 회수가 어려우므로 CPU·메모리보다 더 엄격하게 관리해야 합니다.

    면접관이 보는 것 — Retain을 기본으로 두는 이유를 실제 사고 시나리오로 설명하는지.

    Q17노드가 죽었는데 StatefulSet 파드가 Terminating에서 안 넘어갑니다. 왜 그렇고 어떻게 합니까?스토리지

    쿠버네티스는 노드와 통신이 끊겼을 때 그 노드에서 파드가 실제로 종료됐는지 확인할 방법이 없습니다. RWO 볼륨을 두 곳에서 동시에 마운트하면 파일시스템이 깨지므로, 확신이 없으면 새 파드를 만들지 않고 기다립니다. 이건 버그가 아니라 데이터를 지키는 설계입니다.

    따라서 절차는 "노드가 정말 죽었는지 물리적으로 확인"이 먼저입니다. iDRAC/iLO/IPMI로 전원 상태를 보거나, 스토리지 쪽에서 해당 노드의 세션이 끊겼는지 확인합니다. 확인된 뒤에야 kubectl delete node <node>로 노드 객체를 제거합니다. 그러면 파드가 정리되고 볼륨이 해제되어 다른 노드에서 다시 뜹니다.

    kubectl delete pod --force --grace-period=0는 apiserver의 기록만 지울 뿐 실제 프로세스를 죽이지 않습니다. 노드가 사실은 네트워크만 끊겼던 것이라면, 되살아난 순간 같은 볼륨을 두 프로세스가 쓰는 스플릿 브레인이 발생합니다. 데이터베이스라면 복구 불가능한 손상으로 이어집니다.

    자동화가 필요하다면 펜싱(fencing)이 전제입니다. 하드웨어 전원 제어나 스토리지 레벨의 접근 차단을 실제로 수행한 뒤 노드를 제거하는 컨트롤러를 두는 것입니다. 이 장치 없이 강제 삭제를 자동화하면 언젠가 데이터를 잃습니다.

    면접관이 보는 것 — force delete의 위험을 정확히 아는지. 이 질문 하나로 스테이트풀 운영 경험 여부가 드러납니다.

    Q18RWX 볼륨이 필요하다는 요청을 받았습니다. 어떻게 대응합니까?스토리지

    먼저 정말 필요한지 되묻습니다. RWX 요청의 상당수는 ① 여러 파드가 같은 파일을 읽어야 함(→ ConfigMap, 이미지에 포함, 오브젝트 스토리지로 해결 가능) ② 업로드 파일 공유(→ S3 호환 오브젝트 스토리지가 정답) ③ 레거시 애플리케이션이 공유 디렉터리를 전제(→ 이 경우만 진짜 RWX)입니다. 앞의 둘은 RWX 없이 더 좋은 구조로 풀립니다.

    진짜 필요하다면 선택지는 CephFS, NFS, 일부 CSI의 RWX 지원입니다. 각각의 주의점은 이렇습니다. CephFS는 메타데이터 서버(MDS)가 병목이 되기 쉬워 작은 파일이 많은 워크로드에서 성능이 급격히 떨어집니다. NFS는 도입이 쉽지만 서버가 단일 장애점이 되고 파일 락 동작이 애플리케이션 기대와 다른 경우가 많습니다. 어느 쪽이든 데이터베이스를 RWX 위에 올리는 것은 금지해야 합니다.

    운영 관점에서 반드시 모니터링할 것은 inode 소진(kubelet_volume_stats_inodes_free)입니다. 공유 볼륨은 작은 파일이 무한히 쌓이는 경향이 있어 용량은 남아도 inode가 먼저 고갈되는 일이 실제로 자주 발생합니다.

    면접관이 보는 것 — 요청을 그대로 수행하지 않고 요구사항을 되짚는 태도. 플랫폼 엔지니어의 핵심 역량입니다.

    Q19QoS 클래스는 무엇이고, 노드 메모리가 부족할 때 축출 순서는 어떻게 됩니까?스케줄링

    세 가지입니다. Guaranteed는 모든 컨테이너에서 requests와 limits가 CPU·메모리 모두 같은 값일 때. Burstable은 requests가 하나라도 설정됐지만 Guaranteed 조건은 아닐 때. BestEffort는 아무것도 설정하지 않았을 때입니다.

    노드가 메모리 압박에 빠지면 kubelet은 BestEffort → Burstable(requests 초과 사용량이 큰 순) → Guaranteed 순으로 축출합니다. 정확히는 requests 대비 실제 사용량의 초과분이 클수록 먼저 축출되므로, requests를 정직하게 설정한 파드가 보호받습니다.

    실무에서 구분해야 할 중요한 차이가 있습니다. OOMKilled와 Evicted는 다릅니다. OOMKilled는 컨테이너가 자기 메모리 limit을 넘어 커널이 죽인 것으로, 노드 상태와 무관하며 같은 노드에서 재시작합니다. Evicted는 노드 전체가 부족해 kubelet이 파드를 쫓아낸 것으로, 다른 노드로 재스케줄됩니다. 원인과 대응이 완전히 다르므로 지표에서 반드시 구분해서 봐야 합니다.

    운영 권고는 이렇습니다. 중요 서비스는 Guaranteed 또는 requests를 실사용에 가깝게 맞춘 Burstable로. BestEffort는 언제 죽어도 되는 워크로드에만. 그리고 LimitRange로 기본값을 강제해 아무 설정 없는 파드가 클러스터에 들어오지 못하게 합니다.

    면접관이 보는 것 — OOMKilled와 Evicted를 구분하는지. 이 둘을 섞어 말하면 실전 경험이 얕다는 신호입니다.

    Q20CPU limit을 설정해야 합니까, 하지 말아야 합니까?스케줄링

    정답이 하나가 아니라 워크로드 성격에 따라 다르다는 것이 핵심입니다.

    CPU limit은 CFS 쿼터로 동작합니다. 100ms 주기마다 할당량을 주고, 다 쓰면 남은 시간 동안 프로세스를 멈춥니다. 멀티스레드 애플리케이션은 짧은 순간에 여러 코어를 동시에 쓰기 때문에 평균 사용률이 20~30%인데도 주기적으로 스로틀에 걸립니다. 결과는 p99 지연 급등이고, 평균 지표만 보면 절대 원인을 못 찾습니다.

    그래서 실무 기준은 이렇습니다. 지연에 민감한 온라인 서비스는 limit을 넉넉히 주거나 아예 설정하지 않고, requests만 정확히 설정해 스케줄링과 최소 보장을 확보합니다. 배치·백그라운드 작업은 다른 워크로드를 방해하지 않도록 limit을 설정합니다. 멀티테넌트 클러스터에서 신뢰할 수 없는 워크로드는 limit이 필요합니다.

    단, 메모리 limit은 항상 설정합니다. 메모리에는 스로틀링이 없어서 한 파드가 노드 전체 메모리를 먹으면 다른 파드까지 축출되기 때문입니다.

    판단 근거는 지표로 만듭니다. container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total이 10%를 넘는 파드 목록을 대시보드로 만들어 두면, limit 조정 대상을 데이터로 결정할 수 있습니다.

    면접관이 보는 것 — 무조건 설정하라는 교과서적 답이 아니라, 스로틀링 메커니즘을 이해하고 워크로드별로 나눠 판단하는지.

    Q21노드 드레인이 진행되지 않습니다. 원인과 대응은?스케줄링

    가장 흔한 원인은 PDB입니다. replicas: 1인데 minAvailable: 1이면 그 파드는 영원히 축출할 수 없어 드레인이 무한 대기합니다. kubectl get pdb -A에서 ALLOWED DISRUPTIONS가 0인 항목을 찾으면 즉시 확인됩니다.

    그다음 원인들은 ① 파드가 갈 자리가 없음 — 클러스터 용량 부족이거나 노드 어피니티·토폴로지 제약으로 대체 노드가 없는 경우 ② PVC 토폴로지 제약 — 볼륨이 특정 노드에 묶여 있음 ③ terminationGracePeriodSeconds가 매우 긴 파드 ④ 컨트롤러 없는 고아 파드 — 이건 --force가 필요하지만 데이터 손실 여부를 확인한 뒤에만.

    대응은 원인별로 다릅니다. PDB 문제라면 임시로 replicas를 늘려 여유를 만드는 것이 가장 안전합니다. PDB를 지우는 것은 최후의 수단이고, 지웠다면 반드시 복구합니다. 용량 문제라면 저순위 워크로드를 먼저 비우거나 드레인 배치 크기를 줄입니다.

    예방이 본질입니다. 업그레이드 전 사전 점검 스크립트로 ① disruptionsAllowed=0인 PDB ② replicas: 1인 Deployment ③ PDB가 아예 없는 중요 서비스를 목록화해 미리 조치합니다. 이 점검 없이 300노드 드레인을 시작하면 중간에 반드시 멈춥니다.

    면접관이 보는 것 — 사후 대응만이 아니라 사전 점검 자동화를 말하는지.

    Q22podAntiAffinity와 topologySpreadConstraints, 언제 무엇을 씁니까?스케줄링

    podAntiAffinity는 "같은 도메인에 두 개 이상 두지 마라"는 이진적 제약입니다. 표현이 강력하지만 스케줄링 시 모든 후보 노드에 대해 기존 파드를 조회해야 해서 계산 비용이 큽니다. 노드 수백 대에 파드 수천 개인 클러스터에서 필수(required) 안티어피니티를 남발하면 스케줄링 지연이 눈에 띄게 늘어납니다.

    topologySpreadConstraints는 "도메인 간 개수 차이를 maxSkew 이내로 유지하라"는 균형 제약입니다. 3개 랙에 5개 레플리카를 2/2/1로 배치하는 것처럼 비대칭 상황도 자연스럽게 표현되고, 계산 비용도 더 낮습니다. 그래서 현대적인 기본 선택은 topologySpread입니다.

    실무 조합은 이렇습니다. 랙 단위 분산은 topologyKey: topology.kubernetes.io/zone + maxSkew: 1 + whenUnsatisfiable: DoNotSchedule(진짜 중요하면 배치 못 해도 대기), 노드 단위 분산은 topologyKey: kubernetes.io/hostname + maxSkew: 1 + ScheduleAnyway(되면 좋고). 안티어피니티는 "이 두 종류 워크로드는 절대 같은 노드에 두면 안 된다" 같은 서로 다른 앱 간 배제에 남겨 두는 것이 좋습니다.

    주의할 점은 DoNotSchedule이 너무 엄격하면 롤링 업데이트 중 새 파드가 자리를 못 찾아 배포가 멈출 수 있다는 것입니다. minDomains와 nodeAffinityPolicy를 함께 검토하고, 배포 전 실제로 재시작 테스트를 해봐야 합니다.

    면접관이 보는 것 — 성능 비용 차이를 아는지, 그리고 DoNotSchedule이 배포를 막을 수 있다는 부작용을 언급하는지.

    Q23노드가 갑자기 죽으면 그 위의 파드는 언제 다른 노드로 옮겨집니까?스케줄링

    생각보다 오래 걸리고, 그 시간은 여러 타이머의 합입니다.

    1. kubelet이 상태를 보고하지 못함 → controller-manager가 node-monitor-grace-period(기본 40초) 동안 기다린 뒤 노드를 NotReady로 표시
    2. 노드에 node.kubernetes.io/not-ready:NoExecute taint가 붙음
    3. 파드에는 기본적으로 tolerationSeconds: 300(5분)이 자동 부여되어 있어, 5분간 축출되지 않고 버팁니다
    4. 5분이 지나면 파드가 삭제되고, 컨트롤러가 새 파드를 만들어 스케줄링
    5. 새 노드에서 이미지 풀 + 컨테이너 기동 + readiness 통과까지 추가 시간

    즉 기본 설정으로는 약 6분 이상이 걸립니다. 여기에 StatefulSet + RWO 볼륨이면 볼륨 detach/attach 시간이 더 붙고, 앞서 말한 것처럼 노드 객체를 지우기 전까지는 아예 재생성되지 않을 수도 있습니다.

    줄이려면 중요 워크로드의 tolerationSeconds를 30~60초로 낮춥니다. 다만 일시적 네트워크 단절에도 파드가 대량 이동하는 부작용이 있으므로, 클러스터 전체 기본값을 낮추기보다 특정 워크로드에만 적용하는 것이 안전합니다. 근본적으로는 이 6분 동안 서비스가 유지되도록 레플리카를 여러 랙에 분산해 두는 것이 답입니다. 한 노드가 죽어도 나머지가 트래픽을 받으면 재스케줄 시간은 문제가 되지 않습니다.

    면접관이 보는 것 — 타이머 구조를 알고 있는지, 그리고 "빨리 옮기기"보다 "옮겨지는 동안 버티기"가 정답이라는 관점을 갖는지.

    Q24노드 300대 클러스터의 마이너 버전 업그레이드를 설계하세요.운영·업그레이드

    사전(D-7): ① 제거 예정 API 사용 여부 스캔(pluto/kubent, apiserver_requested_deprecated_apis 지표) ② 애드온 호환성 표 작성 — CNI, CSI, Ingress, cert-manager, Argo CD, metrics-server, 정책 엔진 각각의 지원 버전 확인 ③ 드레인을 막을 PDB와 단일 레플리카 워크로드 목록화 ④ etcd 스냅샷 + 검증 ⑤ 스테이징 클러스터에서 동일 절차 리허설.

    순서는 버전 스큐 규칙을 따릅니다. 컨트롤 플레인(apiserver → controller-manager/scheduler) → kubelet → kube-proxy. kubelet은 apiserver보다 최대 3 마이너까지 낮아도 되므로, 컨트롤 플레인을 먼저 올리고 워커는 나눠서 진행할 수 있습니다. 마이너 버전은 반드시 한 단계씩, 건너뛰기 금지.

    실행: 컨트롤 플레인은 1대씩, 각 단계 후 etcd health와 API 응답을 확인합니다. 워커 300대는 랙별로 나눠 동시 드레인을 전체의 5% 이내로 제한하고, 각 노드마다 ① drain ② 패키지 교체 ③ kubelet 재시작 ④ Ready 대기 ⑤ uncordon ⑥ 클러스터 상태 확인(Pending 파드 급증 시 즉시 중단)의 루프를 돕니다.

    롤백 계획: 컨트롤 플레인은 etcd 스냅샷 복구가 유일한 실질 롤백입니다. 그래서 컨트롤 플레인 업그레이드 직전 스냅샷이 결정적입니다. 워커는 이전 버전 패키지로 되돌리면 되므로 리스크가 낮습니다.

    관측: 업그레이드 중 반드시 볼 지표는 Pending 파드 수, API 에러율, 서비스 SLI, 노드 Ready 비율입니다. 알람은 미리 침묵시키되 만료 시간을 반드시 지정합니다.

    면접관이 보는 것 — 절차 나열이 아니라 "중단 조건"과 "롤백 수단"을 명시하는지.

    Q25어느 날 아침 모든 kubectl 명령이 인증 오류로 실패합니다. 무엇을 의심합니까?운영·업그레이드

    확인은 kubeadm certs check-expiration 또는 openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -dates입니다. 노드의 kubelet 클라이언트 인증서도 별도로 확인해야 합니다.

    복구는 각 컨트롤 플레인 노드에서 kubeadm certs renew all → kubelet 재시작 → 정적 파드 재기동(매니페스트를 잠시 옮겼다 되돌림) → 운영자 kubeconfig(admin.conf) 갱신입니다. 노드의 kubelet 인증서가 만료됐다면 rotateCertificates: true 설정을 확인하고, 이미 만료된 경우 bootstrap-kubelet.conf로 재부트스트랩이 필요할 수 있습니다.

    예방책이 답의 핵심입니다. ① apiserver_client_certificate_expiration_seconds로 만료 30일 전 알람 ② 월간 점검 체크리스트에 만료일 확인 포함 ③ 무엇보다 분기별 정기 업그레이드를 하면 그때마다 인증서가 자동 갱신되므로, 정기 업그레이드 자체가 최선의 인증서 관리 전략입니다. 여기에 CA 인증서(기본 10년) 만료일도 문서에 기록해 두어야 합니다. 10년은 길어 보이지만 인수인계가 몇 번 지나면 아무도 모르게 됩니다.

    면접관이 보는 것 — 복구 절차보다 예방 체계를 말하는지. 그리고 CA 만료까지 생각이 미치는지.

    Q26etcd 스냅샷과 Velero, 무엇을 언제 씁니까? 둘 다 있으면 충분합니까?운영·업그레이드

    etcd 스냅샷은 클러스터 전체 상태의 시점 복사본입니다. 클러스터 자체가 망가졌을 때(쿼럼 손실, 컨트롤 플레인 손상) 되살리는 수단이고, 복구는 전부 아니면 전무입니다. 네임스페이스 하나만 되살리는 데는 쓸 수 없습니다.

    Velero는 리소스를 논리적으로 백업합니다. 네임스페이스 단위 선택 복구, 다른 클러스터로의 이관, PV 스냅샷 연계가 가능합니다. "팀 하나가 실수로 네임스페이스를 지웠다" 같은 상황의 정답입니다.

    하지만 둘 다 있어도 충분하지 않습니다. 빠진 것이 둘 있습니다.

    • Git(선언적 형상): 실제로 가장 자주 쓰는 복구 수단입니다. GitOps가 갖춰져 있으면 리소스 복구는 동기화 한 번이고, 백업 복구보다 빠르고 안전합니다.
    • 애플리케이션 데이터의 일관성 백업: Velero의 볼륨 스냅샷은 파일시스템 시점 복사일 뿐, 실행 중인 DB의 트랜잭션 일관성을 보장하지 않습니다. PostgreSQL·MySQL은 반드시 DB 고유 도구(WAL 아카이빙, XtraBackup 등)로 별도 백업해야 합니다.

    그리고 무엇보다 복구를 실제로 해보지 않은 백업은 백업이 아닙니다. 분기마다 스테이징에서 etcd 복구와 Velero 복구를 수행하고, 걸린 시간을 기록해 그것을 실제 RTO로 삼아야 합니다.

    면접관이 보는 것 — 도구 비교에 그치지 않고 Git과 DB 백업이라는 빠진 계층을 스스로 채우는지.

    Q2740개 팀이 한 클러스터를 씁니다. 멀티테넌시를 어떻게 설계합니까?보안

    네 축을 모두 채워야 하고, 하나라도 비면 나머지가 무력화됩니다.

    • 자원: 네임스페이스별 ResourceQuota(CPU/메모리/스토리지/PVC 개수/LoadBalancer 개수)와 LimitRange(기본값과 상한). 쿼터가 없으면 한 팀이 클러스터 전체를 요청해 버립니다.
    • 권한: RBAC은 사람이 아니라 IdP 그룹에 부여합니다. 팀은 자기 네임스페이스 범위만, 클러스터 범위 리소스(CRD, PV, ClusterRole)는 플랫폼팀만. ServiceAccount는 워크로드별로 분리하고 default SA 사용을 정책으로 금지합니다.
    • 네트워크: 네임스페이스별 default-deny + DNS 예외를 표준 세트로 배포. 팀 간 통신은 명시적 허용만.
    • 실행: Pod Security Admission을 네임스페이스 레이블로 restricted 적용. 특권 컨테이너, hostPath, hostNetwork, hostPID를 막습니다. 이게 뚫리면 위 세 개는 의미가 없습니다.

    여기에 정책 엔진(Kyverno/Gatekeeper)으로 조직 규칙을 코드화합니다. 사내 레지스트리만 허용, owner 레이블 필수, requests 없는 파드 금지 같은 것들입니다. 도입은 반드시 Audit → 위반 공유 → 신규 네임스페이스부터 Enforce → 전면 적용 순서로 갑니다.

    마지막으로 온보딩 자동화가 실질적인 성패를 가릅니다. 네임스페이스·쿼터·RBAC·NetworkPolicy·정책 레이블이 한 번에 생성되는 템플릿을 GitOps로 관리하면, 40개 팀이 400개가 되어도 일관성이 유지됩니다. 수작업 온보딩은 반드시 누락을 만듭니다.

    덧붙여 노드 수준 격리가 필요한 워크로드(신뢰할 수 없는 코드, 규제 대상)는 별도 노드 풀 + taint로 물리적으로 분리하거나, 아예 별도 클러스터로 보내는 것이 맞습니다.

    면접관이 보는 것 — 네 축을 균형 있게 말하는지, 그리고 온보딩 자동화라는 운영 현실을 언급하는지.

    Q28Secret 관리 전략을 설명하세요. Git에 어떻게 넣습니까?보안

    먼저 알아야 할 사실은 쿠버네티스 Secret이 기본적으로 base64 인코딩일 뿐 암호화가 아니라는 것입니다. etcd에 평문에 가깝게 저장되고, 해당 네임스페이스에 get secrets 권한이 있으면 누구나 읽습니다.

    계층별로 조치합니다.

    • 저장 시 암호화: apiserver의 EncryptionConfiguration으로 etcd 저장 시 암호화를 활성화합니다. 가능하면 KMS 프로바이더로 외부 키 관리와 연동합니다. 설정 후 기존 Secret을 다시 써야(kubectl get secrets -A -o json | kubectl replace -f -) 실제로 암호화됩니다.
    • 접근 통제: Secret에 대한 list 권한은 사실상 그 네임스페이스의 모든 비밀을 읽는 권한입니다. 개별 get으로 제한하고, 감사 로그에서 Secret 접근을 별도 추적합니다.
    • Git 저장: 원본을 Git에 두지 않는 것이 최선입니다. External Secrets Operator로 Vault·사내 비밀 저장소를 원본으로 삼고 클러스터에는 참조만 둡니다. 부득이 Git에 넣어야 하면 Sealed Secrets(클러스터 공개키로 암호화, 해당 클러스터만 복호화 가능)나 SOPS(age/KMS 키로 암호화)를 씁니다.
    • 주입 방식: 환경변수보다 파일 마운트가 낫습니다. 환경변수는 프로세스 목록·크래시 덤프·로그에 노출되기 쉽습니다.
    • 로테이션: 만료·교체 주기를 정하고 자동화합니다. ESO는 원본이 바뀌면 자동 동기화하므로 로테이션이 훨씬 쉬워집니다.
    • 토큰 최소화: 필요 없는 파드는 automountServiceAccountToken: false로 SA 토큰 마운트 자체를 끕니다.

    면접관이 보는 것 — "Secret은 암호화가 아니다"라는 전제에서 출발하는지, 그리고 Git 저장 문제를 구체적 도구로 풀어내는지.

    Q29Prometheus가 OOM으로 계속 죽습니다. 어떻게 접근합니까?관측성

    거의 항상 카디널리티 문제입니다. 메모리 사용량은 대체로 활성 시계열 수에 비례하고(대략 100만 시계열당 3~5GB), 시계열은 레이블 조합마다 하나씩 생깁니다. user_id, request_id, trace_id처럼 값의 종류가 무한한 레이블 하나가 시계열을 수백만 개로 폭발시킵니다.

    진단: ① prometheus_tsdb_head_series 추이를 봅니다. 계단식으로 뛰는 시점이 있으면 그때 배포된 무언가가 범인입니다 ② topk(20, count by (__name__)({__name__=~".+"}))로 지표별 시계열 수 상위를 확인 ③ /api/v1/status/tsdb에서 레이블별 통계 확인 ④ job별로 집계해 어느 팀이 유발했는지 특정.

    대응: 즉시 조치는 metric_relabel_configs로 고카디널리티 레이블을 labeldrop하거나 무거운 지표를 drop하는 것입니다. 임시 파드 이름처럼 계속 바뀌는 값은 정규식으로 정규화합니다. 히스토그램 버킷은 특히 무거우므로 필요한 버킷만 keep합니다.

    예방: ServiceMonitor에 sampleLimit과 labelLimit을 걸어두면 문제 있는 타깃만 실패하고 Prometheus 전체는 살아남습니다. 그리고 팀별로 "지표 예산"을 정하고 대시보드로 공개하면, 지표 설계에 대한 책임이 생겨 근본적으로 개선됩니다.

    구조적 대응: 규모 자체가 커진 것이라면 샤딩(hashmod으로 타깃 분할)과 장기 저장소(Thanos/Mimir/VictoriaMetrics) 도입이 답입니다. 특히 VictoriaMetrics는 같은 데이터를 훨씬 적은 메모리로 처리하므로 온프레미스에서 좋은 선택지입니다.

    면접관이 보는 것 — 메모리를 늘리는 것으로 끝내지 않고, 원인 지표를 찾아 잘라내고 재발 방지 장치를 거는 데까지 가는지.

    Q30온콜이 알람 피로에 시달립니다. 알람 체계를 어떻게 다시 설계하겠습니까?관측성

    기준을 하나로 정합니다. "지금 사람이 개입하지 않으면 상황이 나빠지는가." 그렇다면 페이지(호출), 아니면 티켓이나 대시보드입니다. "노드 CPU 80%"는 페이지가 아닙니다. 그 자체로는 아무 일도 일어나지 않기 때문입니다.

    원인이 아니라 증상으로 알람합니다. "파드 재시작", "디스크 70%", "메모리 높음" 같은 원인 지표는 수십 개가 동시에 울려 소음이 됩니다. 대신 "결제 API 에러율이 SLO 예산을 시간당 14배로 소진 중"처럼 사용자 영향으로 알람하면, 하나의 알람이 하나의 실제 문제에 대응합니다. 원인 지표는 조사할 때 대시보드에서 보면 됩니다.

    SLO 소진율(burn rate) 기반이 현재까지 가장 좋은 방식입니다. 짧은 창(5분)에서 빠른 소진과 긴 창(1시간)에서 지속적 소진을 조합해 알람하면, 순간적인 스파이크에는 울리지 않고 진짜 문제만 잡습니다. 다중 창·다중 소진율 방식이 표준입니다.

    소음 제거 장치: Alertmanager의 group_by로 같은 원인의 알람을 묶고, inhibit_rules로 파생 알람을 억제합니다. "노드가 죽었으면 그 위 파드 알람은 억제" 하나만으로도 소음의 상당 부분이 사라집니다. 정기 작업 전에는 만료 시간을 명시한 침묵을 겁니다.

    운영 루프: 매주 발화한 알람을 리뷰합니다. 발화했지만 아무 조치도 필요 없었던 알람은 임계값을 조정하거나 삭제하고, 장애가 났는데 울리지 않은 알람은 새로 만듭니다. 그리고 모든 페이지 알람에는 런북 URL이 있어야 합니다. 런북을 못 쓰겠다면 그건 애초에 페이지가 아니어야 한다는 신호입니다.

    면접관이 보는 것 — 임계값 조정 같은 지엽적 답이 아니라 "증상 기반 + SLO + 억제 + 주간 리뷰"라는 체계로 답하는지. 그리고 런북 없는 알람은 알람이 아니라는 원칙을 갖는지.
