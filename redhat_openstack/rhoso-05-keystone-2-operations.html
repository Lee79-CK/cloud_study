5편Keystone 2: 실전 운영

4편에서 토큰이 만들어지는 원리를 봤다면, 이번 편은 운영 현장의 질문들입니다. 회사 계정(AD·LDAP)으로 로그인하게 해 달라, SSO로 붙여 달라, CI 파이프라인용 계정은 어떻게 주나, 이 사용자는 왜 403이 나나, 서비스 비밀번호를 바꿔도 되나. 하나씩 RHOSO 방식으로 답합니다.

섹션 1

이 편의 목표

  1. 신원 저장소 세 가지(SQL · LDAP · 페더레이션)의 차이와 선택 기준을 설명한다.
  2. LDAP·AD를 도메인별 드라이버로 붙이는 원리와 RHOSO 절차(Secret + extraMounts)를 설명한다.
  3. OIDC 페더레이션의 로그인 흐름과 매핑(mapping) 규칙을 읽는다.
  4. 자동화용 애플리케이션 크레덴셜을 역할 제한·만료·접근 규칙과 함께 설계한다.
  5. oslo.policy 규칙을 읽고 평가하며, 정책 덮어쓰기의 위험과 RHOSO에서의 위치를 안다.
  6. 서비스 계정의 역할과 “배포 후 osp-secret 서비스 비밀번호 변경 금지” 경고의 이유를 설명한다.
  7. 권한 거부(401·403)를 정해진 순서로 추적해 원인을 좁힌다.

4편 비유 이어서: 출입 관리 데스크의 실무

4편에서 출입 데스크(Keystone)가 방문증(토큰)을 발급하는 원리를 봤습니다. 이번 편은 데스크 운영 실무입니다. 직원 명부를 인사팀 시스템과 연결하기(LDAP), 그룹사 출입증을 인정해 주기(페더레이션), 택배 기사용 제한 출입증 만들기(애플리케이션 크레덴셜), 층별 출입 규칙 고치기(정책), 시설 관리 직원 출입증 관리(서비스 계정), 그리고 “왜 못 들어가나요?” 민원 처리(디버깅)입니다.

섞어 쓰는 것이 정상

도메인마다 다른 저장소를 쓸 수 있습니다. 전형적인 구성은 Default 도메인 = SQL(admin, 서비스 계정, 비상용 계정), 고객·사내 도메인 = LDAP 또는 페더레이션입니다. 서비스 계정을 외부 저장소에 두면 외부 시스템 장애가 곧 OpenStack 전체 장애가 되므로, 서비스 계정은 항상 SQL 도메인에 둡니다.

섹션 4

LDAP 연동의 원리: 도메인별 드라이버

LDAP은 회사의 사용자·그룹 정보를 나무 구조로 저장하는 디렉터리 프로토콜입니다. Microsoft AD(Active Directory), Red Hat IdM(FreeIPA 기반) 등이 LDAP으로 조회할 수 있습니다.

어떻게 동작하나

  1. keystone.conf에 [identity] domain_specific_drivers_enabled = True를 켭니다.
  2. Keystone은 /etc/keystone/domains 디렉터리에서 keystone.<도메인 이름>.conf 파일을 찾습니다. 파일이 있는 도메인은 그 파일의 설정(LDAP)을 쓰고, 없는 도메인은 기본(SQL)을 씁니다.
  3. 사용자가 그 도메인으로 로그인하면 Keystone이 서비스용 계정(bind DN)으로 LDAP에 접속해 사용자를 찾고, 사용자의 비밀번호로 다시 접속(bind)해 비밀번호를 확인합니다.
  4. 그룹 소속도 LDAP에서 읽습니다. 하지만 역할 할당은 Keystone DB에 저장합니다. 그래서 “LDAP 그룹 openstack-cust-a-dev에 a-web 프로젝트 member를 준다”처럼 그룹 단위로 할당하면, 이후 사람 관리는 LDAP 쪽에서 끝납니다.

읽기 전용이 원칙

현재 Keystone의 LDAP 드라이버는 읽기 전용입니다. OpenStack에서 LDAP 도메인의 사용자를 만들거나 비밀번호를 바꿀 수 없고, 그 일은 원래 디렉터리 시스템에서 합니다. MSP 입장에서는 “계정 관리 책임을 고객 디렉터리 쪽에 둔다”는 장점이 됩니다.

섹션 6

  
RHOSO에서 LDAP 붙이기

  
RHOSO 공식 절차는 세 단계입니다: ① OpenStack에 도메인 만들기 → ② 설정 파일을 Secret으로 만들기 → ③ OpenStackControlPlane에서 Secret을 Keystone Pod에 마운트. 2편에서 배운 “결과물이 아니라 CR을 고친다” 원칙 그대로입니다.

  
# ① 도메인 생성 (openstackclient Pod)
openstack domain create cust-a

# ② 위 생성기 결과를 파일로 저장한 뒤 Secret 생성 — 파일 이름이 곧 도메인 연결 키
oc create secret generic keystone-domains -n openstack \
   --from-file=keystone.cust-a.conf
#   도메인이 여럿이면 --from-file 을 여러 번 (keystone.cust-b.conf …)

# ③ OpenStackControlPlane 수정 (학습용으로 핵심만 표시)
spec:
  keystone:
    template:
      customServiceConfig: |
        [identity]
        domain_specific_drivers_enabled = True
      extraMounts:                          # Secret을 Pod 안 파일로 끼워 넣는 장치
      - name: v1
        region: r1
        extraVol:
        - propagation: [Keystone]
          extraVolType: Conf
          volumes:
          - name: keystone-domains
            secret: { secretName: keystone-domains }
          mounts:
          - name: keystone-domains
            mountPath: /etc/keystone/domains
            readOnly: true

  
구조는 RHOSO 문서의 LDAP 절차를 따랐습니다. 기존 customServiceConfig·extraMounts 값이 있다면 덮어쓰지 말고 합쳐서 적어야 합니다(덮어쓰면 다른 설정이 사라짐).

  
확인과 역할 연결

  
openstack user list --domain cust-a          # LDAP 사용자가 보이면 연결 성공 (user_filter 적용 결과)
openstack group list --domain cust-a
openstack role add --group openstack-cust-a-dev --group-domain cust-a \
   --project a-web --project-domain cust-a member
openstack --os-user-domain-name cust-a --os-username kim token issue   # 사용자로 직접 로그인 시험

  

    
증상흔한 원인

    
      
user list가 비어 있음user_tree_dn·user_filter·user_objectclass 불일치, bind 계정 권한 부족

      
목록은 나오는데 로그인만 401사용자 비밀번호 bind 실패, 계정 비활성 판정(user_enabled_* 설정 오류)

      
간헐적 401 · 느린 로그인LDAP 서버 응답 지연, page_size 미설정, referral 추적

      
연결 자체 실패 (인증서 오류)Keystone Pod가 LDAP 서버 CA를 신뢰하지 않음 → RHOSO의 사용자 정의 CA 번들 설정으로 추가

    
  

  

    
현장 팁: 먼저 ldapsearch로 검증

    
설정을 Keystone에 넣기 전에, 작업 PC에서 같은 bind 계정·같은 경로·같은 필터로 ldapsearch를 돌려 원하는 사용자와 그룹이 나오는지 먼저 확인하세요. Keystone 로그로 LDAP 문제를 추적하는 것보다 훨씬 빠릅니다. 그리고 그 bind 계정의 비밀번호 만료 정책을 꼭 확인하세요. bind 계정이 만료되는 날 그 도메인 전원이 로그인하지 못합니다.

  







  
섹션 7

  
OIDC 페더레이션: 로그인을 IdP에 맡기기

  
페더레이션은 Keystone이 비밀번호를 직접 확인하지 않고, 믿을 수 있는 외부 IdP(신원 제공자, 예: Red Hat build of Keycloak)가 “이 사람은 확인됐다”고 보증한 결과를 받아들이는 방식입니다. 프로토콜은 OIDC(OpenID Connect)나 SAML을 씁니다. RHOSO 18 문서는 Red Hat SSO 기술과의 OIDC 페더레이션, 여러 IdP(멀티 렐름) 구성, CLI에서 페더레이션 사용자 인증까지 다룹니다.

매핑 규칙 읽기

  
# 학습용 매핑 예: Keycloak 그룹 openstack-cust-a 소속이면 Keystone 그룹 federated-cust-a 로 연결
[
  {
    "local": [
      { "user":  { "name": "{0}", "email": "{1}" } },
      { "group": { "name": "federated-cust-a", "domain": { "name": "cust-a" } } }
    ],
    "remote": [
      { "type": "OIDC-preferred_username" },               # {0}
      { "type": "OIDC-email" },                            # {1}
      { "type": "OIDC-groups", "any_one_of": ["openstack-cust-a"] }   # 조건
    ]
  }
]

  
remote는 IdP가 준 정보(이름은 mod_auth_openidc 설정의 접두어 규칙에 따라 달라짐), local은 Keystone에서 쓸 사용자·그룹입니다. {0}, {1}은 remote 목록의 순서입니다. 조건(any_one_of)에 맞지 않으면 로그인이 거부됩니다.

  
# Keystone 쪽 객체 만들기 (개념 순서)
openstack identity provider create --remote-id https://sso.example.com/realms/cust-a kcidp
openstack mapping create --rules mapping.json cust-a-mapping
openstack federation protocol create openid --mapping cust-a-mapping --identity-provider kcidp
openstack group create --domain cust-a federated-cust-a
openstack role add --group federated-cust-a --group-domain cust-a --project a-web --project-domain cust-a member

  
RHOSO에서는 이와 함께 Apache용 페더레이션 설정을 담은 Secret을 Keystone에 연결하고, keystone 설정([federation], [openid])과 Horizon의 WebSSO 설정을 customServiceConfig로 넣습니다. 세부 항목은 RHOSO “Configuring security services”의 페더레이션 장을 따릅니다.

  

    
페더레이션 사용자의 CLI 사용

    
페더레이션 사용자는 Keystone 비밀번호가 없으므로 평범한 password 방식으로 CLI를 쓸 수 없습니다. 방법은 둘입니다. ① clouds.yaml에서 OIDC 인증 방식(예: v3oidcpassword, v3oidcclientcredentials)을 쓰거나, ② 웹으로 로그인한 뒤 애플리케이션 크레덴셜을 만들어 CLI·자동화에 쓰는 것입니다(다음 섹션). 실무에서는 ②가 간편해서 많이 씁니다.

  







  
섹션 8

  
애플리케이션 크레덴셜: 자동화용 제한 출입증

  
애플리케이션 크레덴셜은 사용자가 자기 권한의 일부를 떼어 프로그램에게 빌려주는 전용 열쇠입니다. ID와 비밀(secret) 한 쌍으로 이뤄집니다.

  

    
특징내용왜 좋은가

    
      
프로젝트에 묶임만든 시점의 프로젝트 범위로만 동작다른 프로젝트로 번질 수 없음

      
역할 일부만--role로 내가 가진 역할 중 일부만 부여 (지정 안 하면 현재 역할 전부)CI에는 member만, 모니터링에는 reader만

      
만료일--expiration잊혀진 자격 증명이 영원히 살아 있지 않음

      
제한 모드(기본)기본값은 이 자격 증명으로 또 다른 앱 크레덴셜이나 trust를 만들 수 없음. --unrestricted로 풀 수 있으나 권장하지 않음유출돼도 권한 복제를 막음

      
접근 규칙--access-rules로 허용할 서비스·HTTP 메서드·경로를 지정“서버 목록 조회만” 같은 초정밀 제한

      
비밀번호와 독립사용자 비밀번호를 바꿔도 계속 동작정기 비밀번호 변경이 파이프라인을 깨지 않음

      
주인과 운명 공동체주인 사용자가 그 프로젝트 역할을 잃거나 삭제되면 함께 무효퇴사자 정리가 자동으로 따라옴. 대신 개인 계정이 아닌 전용 서비스 사용자로 만드는 것이 안정적

      
비밀은 한 번만secret은 생성할 때 한 번만 보여 주고 다시 조회 불가Vault·CI 비밀 저장소에 바로 보관

    
  

  

    
애플리케이션 크레덴셜 설계기

    

      

        
        
        
        

      

      

    

  

  

    
trust와는 무엇이 다른가

    
trust는 “A 사용자가 B 사용자(주로 서비스)에게 자기 대신 일할 권한을 위임”하는 장치로, Heat 같은 서비스가 내부적으로 씁니다. 애플리케이션 크레덴셜은 “사람이 프로그램에게 열쇠를 주는” 장치입니다. 운영자가 직접 다룰 일은 대부분 애플리케이션 크레덴셜입니다.

  







  
섹션 9

  
정책 다루기: 읽기 · 검증 · 덮어쓰기

  
정책은 코드 안에 있다 (policy-in-code)

  
각 서비스의 기본 정책 규칙은 서비스 코드에 들어 있습니다. policy.yaml 파일은 기본값과 다르게 하고 싶은 규칙만 적는 덮어쓰기 파일입니다. JSON 형식 정책 파일은 사용 중단되었고 YAML을 씁니다.

  
규칙 문법

  

    
표현뜻

    
      
role:reader토큰에 reader 역할이 있으면 참

      
project_id:%(project_id)s토큰의 프로젝트가 대상 자원의 프로젝트와 같으면 참 (“내 것”)

      
rule:이름다른 이름 붙은 규칙을 가져다 씀 (예: rule:admin_api)

      
and · or · not · 괄호조건 조합

      
@ / !항상 허용 / 항상 거부

    
  

  
또한 규칙마다 범위 종류(scope_types)가 정해져 있어, [oslo_policy] enforce_scope = True이면 맞지 않는 범위의 토큰(예: 프로젝트 전용 API에 시스템 범위 토큰)은 규칙과 상관없이 거부됩니다. enforce_new_defaults = True는 예전 규칙 대신 새 기본 규칙(reader·member·admin 체계)을 쓰게 합니다. 범위 종류는 policy.yaml로 바꿀 수 없습니다.


  

    
정책 규칙 평가기

    

      

        
        
토큰에 할당된 역할:

        

        
        

      

      

    

  


  
도구 상자

  
# 서비스 Pod 안에서 (예: nova-api Pod)
oslopolicy-sample-generator --namespace nova      # 기본 규칙 전체를 주석과 함께 출력
oslopolicy-policy-generator --namespace nova      # 현재 덮어쓰기까지 반영한 실효 규칙
oslopolicy-list-redundant --namespace nova        # 기본값과 똑같아서 필요 없는 덮어쓰기 찾기
oslopolicy-checker --policy policy.yaml --access token.json --rule os_compute_api:servers:index
                                                  # 토큰 정보(JSON)로 규칙 판정 시험


  
RHOSO에서 정책을 덮어쓴다는 것

  

    
먼저 역할 설계로 풀 수 없는지 확인

    
정책 덮어쓰기는 업그레이드 때마다 다시 검증해야 하고, 서비스 간 규칙이 어긋나면 찾기 어려운 403을 만듭니다. Red Hat의 RHOSO 작업 기록에서도 API 정책 커스터마이즈는 기본 지원 범위가 아니라 별도 지원 예외가 필요한 영역으로 다뤄집니다. 운영 환경에서 정책을 바꾸기 전에 반드시 Red Hat 지원 범위를 확인하세요.

  

  
기술적으로는 서비스 CR을 통해 policy.yaml을 Pod에 전달합니다. 서비스마다 방식이 다를 수 있으며, 대표적으로 서비스 템플릿의 defaultConfigOverwrite(파일 내용을 직접 넣기)나 extraMounts(ConfigMap·Secret 마운트) + customServiceConfig의 [oslo_policy] policy_file 지정 조합이 쓰입니다. 정확한 필드는 oc explain으로 그 서비스에서 확인하세요.

  
# 개념 예: Nova API에 덮어쓰기 규칙 하나 전달 (필드는 버전별 확인)
spec:
  nova:
    template:
      apiServiceTemplate:
        defaultConfigOverwrite:
          policy.yaml: |
            "os_compute_api:os-console-output": "role:reader and project_id:%(project_id)s"







  
섹션 10

  
서비스 계정 관리

  
4편에서 본 service 프로젝트에는 nova, glance, neutron, cinder, placement 같은 서비스 사용자가 있습니다. 이들은 두 가지 일을 합니다.

  
    
    
  • 토큰 검증: 각 서비스의 keystonemiddleware가 사용자 토큰을 검증할 때 자기 서비스 계정으로 Keystone에 접속합니다.
    • 
    
  • 서비스 간 호출: 예를 들어 Nova가 Neutron에 포트를 요청하거나 Placement에 자원을 보고할 때 서비스 계정을 씁니다.
    • 
  

  
openstack user list --project service --long      # 서비스 계정 목록
openstack role assignment list --project service --names
oc get keystoneservice -n openstack               # 어느 Operator가 어떤 서비스 사용자를 요청했나

  
비밀번호는 osp-secret에

  
서비스 계정 비밀번호는 설치 전에 만든 osp-secret(Kubernetes Secret)의 키들(AdminPassword, NovaPassword, GlancePassword, NeutronPassword, CinderPassword, PlacementPassword …)에서 옵니다. Operator가 이 값으로 Keystone 사용자를 만들고, 같은 값을 서비스 설정에도 넣습니다.

  

    
가장 중요한 경고: 배포 후 osp-secret의 서비스 비밀번호를 임의로 바꾸지 말 것

    
RHOSO 18.0 배포 문서는 컨트롤 플레인을 배포한 뒤에는 서비스 비밀번호를 바꿀 수 없다고 경고합니다. osp-secret에서 값을 바꾸면 서비스 설정은 새 비밀번호로 다시 만들어지지만 Keystone 안의 비밀번호는 갱신되지 않아, 서비스가 Keystone 인증에 실패하고 장애가 납니다. 증상은 그 서비스의 모든 API가 503 또는 401을 내고, 로그에 keystonemiddleware의 “Identity server rejected authorization” 류 메시지가 찍히는 것입니다.

  

  

    
해야 할 것하지 말아야 할 것

    
      
osp-secret을 설치 시 충분히 강한 무작위 값으로 생성하고 안전하게 백업배포 후 osp-secret 서비스 비밀번호 변경

      
보안 점검의 교체 요구는 Red Hat 문서·지원으로 공식 절차가 있는지 먼저 확인 (릴리스 노트 확인)openstack user set --password로 서비스 계정 비밀번호를 직접 변경

      
openstack 네임스페이스 Secret 읽기 권한 최소화서비스 계정 비활성화·삭제, 역할 추가·제거

      
서비스 계정의 인증 실패 로그 모니터링서비스 계정을 LDAP·페더레이션 도메인으로 옮기기

    
  

  
참고: 무중단 비밀번호 교체를 위해 “두 개의 자격 증명을 동시에 유효하게 두는” 방식(예: 서비스 계정에 애플리케이션 크레덴셜 사용)이 개선 방향으로 논의되어 왔습니다. 설치한 버전에서 어떤 방식이 지원되는지는 해당 FR의 릴리스 노트를 확인하세요.

계정 보안 정책: [security_compliance]

  
보안 점검에서 흔히 요구하는 “로그인 실패 잠금, 비밀번호 만료·복잡도·재사용 금지”는 keystone.conf의 [security_compliance]로 설정합니다. RHOSO에서는 Keystone의 customServiceConfig에 넣습니다.

  

    
설정뜻예

    
      
lockout_failure_attempts · lockout_duration연속 실패 N회 시 잠금, 잠금 유지 시간(초)5 · 1800

      
password_expires_days비밀번호 유효 기간90

      
unique_last_password_count최근 N개 비밀번호 재사용 금지5

      
minimum_password_age바꾼 뒤 최소 유지 일수 (재사용 금지 우회 방지)1

      
password_regex · password_regex_description비밀번호 복잡도 규칙과 사용자에게 보여 줄 설명12자 이상, 숫자·대문자 포함 등

      
change_password_upon_first_use관리자가 만든 계정은 첫 로그인 때 비밀번호 변경 강제True

      
disable_user_account_days_inactiveN일 동안 로그인 없으면 비활성화90

    
  

  
keystone:
  template:
    customServiceConfig: |
      [security_compliance]
      lockout_failure_attempts = 5
      lockout_duration = 1800
      password_expires_days = 90
      unique_last_password_count = 5

  

    
반드시 알아야 할 예외 두 가지

    
    
      
  • SQL 도메인 사용자에게만 적용됩니다. LDAP·페더레이션 사용자의 잠금·만료는 디렉터리·IdP의 정책을 따릅니다.
    • 
      
  • 서비스 계정·admin이 잠기거나 만료되면 클라우드 전체 장애입니다. 이런 계정에는 사용자 옵션 ignore_lockout_failure_attempts, ignore_password_expiry, ignore_change_password_upon_first_use를 켜서 정책에서 제외합니다. 정책을 켜기 전에 예외 대상 목록부터 만드세요.
    • 
    

  

  
openstack user set --ignore-lockout-failure-attempts --ignore-password-expiry nova   # 개념 예: 서비스 계정 예외 처리







  
섹션 12

  
MSP 권한 설계 실전

  
4편 과제 5에서 그린 초안을 다듬어 봅시다. 고객사 3곳, 네 부류의 사람(고객 관리자, 고객 개발자, MSP 관제, MSP 운영자)을 가정합니다.

  

    
부류권장 설계이유

    
      
고객 개발자고객 도메인의 그룹(예: cust-a-dev) → 해당 프로젝트 member. 그룹은 고객 LDAP·IdP에서 관리사람의 입퇴사는 고객이 자기 디렉터리에서 처리

      
고객 관리자고객 도메인의 cust-a-admins 그룹 → 고객의 모든 프로젝트에 상속 member(+필요 시 reader 감사 그룹). admin 역할은 주지 않음admin은 사실상 클라우드 전체 관리자(4편). 사용자 관리 요구는 고객 디렉터리 그룹 관리로 충족

      
MSP 관제(NOC)Default 도메인 그룹 msp-noc → 각 고객 도메인에 상속 reader모든 고객 자원을 읽기만, 새 프로젝트에도 자동 적용

      
MSP 운영자소수 인원만 msp-ops 그룹 → admin (프로젝트 admin + 필요 시 시스템 범위)변경 작업은 승인된 소수만, 작업 기록 남기기

      
자동화전용 서비스 사용자 + 고객 프로젝트별 애플리케이션 크레덴셜(역할 제한·만료)개인 계정과 분리, 유출 시 범위 제한

      
비상용(break-glass)Default 도메인 SQL 계정 1~2개, 강한 비밀번호 봉인 보관, 사용 시 기록LDAP·IdP 장애 때도 들어갈 수 있는 마지막 문

    
  

  

    
“고객이 자기 사용자를 직접 관리하고 싶다”에 대한 답

    
OpenStack에서 고객에게 Keystone 사용자 관리 권한을 안전하게 떼어 주는 것은 오랫동안 어려운 문제였습니다(admin을 주면 너무 넓기 때문). 가장 깔끔한 답은 고객 도메인을 고객의 LDAP·IdP에 연결하고, 그룹 소속은 고객이 자기 시스템에서 관리하게 하는 것입니다. 최신 업스트림에는 도메인 관리자용 역할(manager) 페르소나가 추가되는 등 개선이 진행 중이지만, 설치한 RHOSO 버전에서의 지원 여부는 문서로 확인한 뒤 써야 합니다.

정리와 다음 편

  
오늘의 핵심 여덟 문장

  
    
    
  • 신원 저장소는 도메인마다 고를 수 있다. 서비스·관리자·비상용 계정은 SQL, 사람 계정은 LDAP·페더레이션.
    • 
    
  • LDAP은 도메인별 드라이버(keystone.<도메인>.conf)로 붙이고, RHOSO에서는 Secret + extraMounts + customServiceConfig로 넣는다. 역할 할당은 Keystone DB에 남는다.
    • 
    
  • 페더레이션은 비밀번호를 IdP가 확인하고, Keystone은 매핑 규칙으로 IdP 정보를 사용자·그룹으로 바꾼다. CLI는 OIDC 인증 방식이나 앱 크레덴셜로.
    • 
    
  • 자동화에는 애플리케이션 크레덴셜: 프로젝트 고정, 역할 일부, 만료, 기본 제한 모드, 접근 규칙, 비밀은 한 번만.
    • 
    
  • 정책은 코드에 있고 policy.yaml은 차이만 적는다. enforce_scope·enforce_new_defaults를 이해하고, 덮어쓰기 전에 역할 설계와 지원 범위부터 확인한다.
    • 
    
  • 배포 후 osp-secret의 서비스 비밀번호를 바꾸면 장애가 난다. 서비스 계정은 건드리지 않는다.
    • 
    
  • [security_compliance]는 SQL 사용자에게만 적용되며, 서비스·admin 계정은 예외 옵션으로 보호한다.
    • 
    
  • 403은 실효 역할 → 토큰 범위 → 정책 규칙 → 서비스 로그 순서로 좁힌다.
    •
