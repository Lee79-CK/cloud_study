온프렘 분산 스토리지: Rook-Ceph · Longhorn · OpenEBS

클라우드에서는 디스크가 망가져도 벤더가 고칩니다. 온프렘에서는 우리가 클라우드의 스토리지 팀입니다. 노드가 죽으면 데이터 복제본을 어디에 다시 만들지, 디스크를 갈 때 무엇을 먼저 할지, 재구축 동안 네트워크가 버틸지를 직접 결정해야 합니다. 이 편은 온프렘·RKE2·OpenShift 고객에서 가장 많이 만나는 세 가지, Ceph(Rook·ODF), Longhorn, OpenEBS를 구조부터 장애 동작까지 비교하고, RKE2에서 노드를 강제로 꺼 Longhorn이 레플리카를 복구하는 과정을 직접 봅니다.

기준: Rook v1.20 · Ceph Squid 19.2 / Tentacle 20.2 · Longhorn v1.13 · OpenEBS 4.x 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

읽는 법과 목표

쉬운 말로 분산 스토리지는 중요한 서류를 여러 지점 금고에 복사해 두는 은행입니다. 한 지점이 문을 닫아도 다른 지점에서 서류를 꺼낼 수 있고, 문 닫은 지점이 오래 열리지 않으면 남은 지점들이 서류를 다시 복사해 복사본 수를 맞춥니다. 문제는 복사하는 동안 지점 사이 도로(네트워크)가 막히고, 그 사이 또 한 지점이 문을 닫으면 위험해진다는 점입니다. Ceph는 큰 은행 본점 체계, Longhorn은 서류마다 담당 직원을 붙이는 소규모 체계, OpenEBS LocalPV는 “복사 없이 지점 금고 하나에만” 두는 방식입니다.

이 편을 마치면 할 수 있는 것

  • Ceph의 MON·MGR·OSD·MDS·RGW와 CRUSH·풀·PG를 설명하고, Rook으로 배포·운영(디스크 교체, 유지보수 플래그)할 수 있습니다.
  • ODF가 Rook·Ceph·NooBaa를 어떻게 묶은 제품인지 설명하고 지원 경계를 구분할 수 있습니다.
  • Longhorn의 엔진·레플리카·스냅샷·백업 구조와 V1·V2 데이터 엔진의 차이를 설명할 수 있습니다.
  • OpenEBS의 LocalPV(Hostpath·LVM·ZFS)와 Mayastor를 용도에 맞게 고를 수 있습니다.
  • 노드 장애·디스크 교체·리밸런싱 때 세 시스템의 동작과 네트워크 요구를 예측하고, 재구축 시간을 계산할 수 있습니다.

왜 분산 스토리지인가, 무엇을 고르나

온프렘에서 PVC를 쓰는 방법은 크게 넷입니다: 기존 SAN·NAS의 CSI 드라이버(NetApp Trident, Dell·HPE·Pure 드라이버, vSphere CSI), 노드 로컬 디스크(LocalPV·TopoLVM), 노드 디스크를 묶은 분산 스토리지(Ceph·Longhorn·Mayastor), 그리고 외부 Ceph 클러스터 연결. 이 편은 세 번째를 다룹니다. 기존 스토리지 장비가 있다면 그 CSI 드라이버가 가장 단순한 답일 수 있다는 점을 먼저 확인하세요.

Ceph 아키텍처와 Rook 운영

구성 요소역할쉬운 말로운영 포인트
MON클러스터 지도(어떤 OSD가 살아 있나, CRUSH 규칙)를 관리, 과반수 합의본점 이사회홀수(3·5). 과반이 죽으면 클러스터 전체 정지
MGR지표·대시보드·오케스트레이션 모듈본점 관리실활성·대기 2개
OSD디스크 하나를 맡아 데이터 저장·복제·복구(BlueStore)지점 금고디스크당 하나, OSD당 메모리 목표 수 GiB
MDSCephFS의 메타데이터파일 목록 담당13편의 CephFS 병목 지점
RGWS3 호환 객체 게이트웨이객체 창구15편 백업 대상으로도 사용

데이터는 어떻게 흩어지나: 풀·PG·CRUSH

  • 풀(pool). 복제 정책 단위입니다. 복제 풀은 size 3(사본 3개), min_size 2(최소 2개가 살아 있어야 쓰기 허용)가 표준입니다. 이레이저 코딩 풀은 k+m 조각으로 나눠 공간 효율이 좋지만 CPU·지연 비용이 큽니다.
  • PG(배치 그룹). 객체를 바로 OSD에 매핑하지 않고, 수백 개의 PG로 묶은 뒤 PG를 OSD에 배치합니다. 복구·리밸런싱도 PG 단위로 일어납니다. PG 수는 오토스케일러가 조정합니다.
  • CRUSH. 중앙 목록 없이 계산으로 위치를 정하는 규칙입니다. 장애 도메인을 host·rack·zone으로 정하면 사본이 서로 다른 호스트(또는 랙)에 놓입니다. 기본은 host입니다.
  • 용량 경계. OSD 사용률이 nearfull(기본 85%)이면 경고, backfillfull(90%)이면 재배치 중단, full(95%)이면 쓰기 전면 중단입니다. 3복제라면 원시 용량의 1/3에서 이 여유까지 빼야 실사용 용량입니다.

Rook이 하는 일

Rook은 Ceph를 Kubernetes 위에서 돌리는 오퍼레이터입니다. CephCluster CR 하나로 MON·MGR·OSD를 배치하고, CephBlockPool·CephFilesystem·CephObjectStore CR로 풀과 서비스를 만들며, Ceph CSI 드라이버로 StorageClass를 제공합니다. v1.20부터 CSI 드라이버는 별도의 ceph-csi-operator와 차트로 관리되어, 업그레이드 순서(Rook 오퍼레이터 → CSI 드라이버 → 클러스터)를 지켜야 합니다. 지원 Ceph 버전은 Squid(19.2)와 Tentacle(20.2)입니다.

Rook CR의 뼈대
apiVersion: ceph.rook.io/v1
kind: CephCluster
metadata: {name: rook-ceph, namespace: rook-ceph}
spec:
  cephVersion: {image: quay.io/ceph/ceph:v19.2.3}    # 지원 버전·패치 확인
  dataDirHostPath: /var/lib/rook
  mon: {count: 3, allowMultiplePerNode: false}
  mgr: {count: 2}
  network:
    provider: host                                   # 또는 Multus로 public·cluster 네트워크 분리
  storage:
    useAllNodes: false
    nodes:
    - name: storage-1
      devices: [{name: "nvme1n1"}, {name: "nvme2n1"}]
---
apiVersion: ceph.rook.io/v1
kind: CephBlockPool
metadata: {name: replicapool, namespace: rook-ceph}
spec:
  failureDomain: host
  replicated: {size: 3, requireSafeReplicaSize: true}
툴박스에서 자주 쓰는 명령
T="kubectl -n rook-ceph exec deploy/rook-ceph-tools --"
$T ceph status                 # HEALTH_OK·WARN·ERR, 복구 진행
$T ceph osd tree               # 호스트별 OSD와 up/down·in/out
$T ceph osd df                 # OSD별 사용률(nearfull 확인)
$T ceph df                     # 풀별 실사용 용량
$T ceph health detail          # 경고의 구체 원인
$T ceph osd set noout          # 계획된 유지보수 전 (끝나면 unset)

OpenShift Data Foundation과의 관계

ODF는 Rook·Ceph·Ceph CSI에 객체 게이트웨이 NooBaa(Multicloud Object Gateway)를 더해 Red Hat이 지원하는 제품입니다. 같은 Ceph라도 운영 방식이 다릅니다.

관점업스트림 Rook-CephODF
설치·업그레이드Helm·매니페스트, 버전을 직접 고름OperatorHub 구독, OpenShift 버전과 호환표로 묶임
배포 모드내부(클러스터 안), 외부 Ceph 연결Internal(클러스터 노드 디스크), Internal-Attached(로컬 디스크 자동 탐색), External(기존 Ceph)
객체 스토리지RGWRGW + NooBaa(여러 백엔드를 묶는 게이트웨이)
설정 자유도Ceph 옵션을 직접 조정지원 범위 안에서만. 지원 밖 튜닝은 지원 계약에 영향
요구 자원구성에 따라스토리지 노드당 상당한 CPU·메모리 요구(문서의 최소 사양 확인). 보통 전용 인프라 노드에 배치
대안—단일 노드·엣지에는 LVM Storage(TopoLVM), 기존 SAN에는 벤더 CSI
시니어 포인트: “Ceph를 아는가”가 지원 계약보다 먼저다 ODF는 설치와 업그레이드를 쉽게 해 주지만, 장애가 났을 때 ceph health detail을 읽고 PG 상태를 해석하는 것은 여전히 운영자 몫입니다. MSP가 ODF 고객을 맡는다면 툴박스 접근 절차와 Ceph 기본 진단(이 편 2장 명령)을 런북에 넣어 두세요. 업스트림 Rook의 문서와 동작이 대부분 그대로 적용됩니다.

Longhorn: 레플리카·스냅샷 모델

쉬운 말로 Longhorn은 볼륨마다 전담 관리자(엔진)를 붙이고, 그 관리자가 여러 노드에 있는 복사본(레플리카)에 동시에 씁니다. 관리자는 볼륨을 쓰는 Pod와 같은 노드에서 일하고, 복사본 하나가 고장 나면 다른 노드에 새 복사본을 만듭니다.
개념내용
엔진(engine)볼륨을 쓰는 노드에서 동작하는 컨트롤러. 쓰기를 모든 레플리카에 동기로 보냄. V1은 노드에 iSCSI 장치로 노출
레플리카(replica)다른 노드 디스크에 있는 볼륨 사본(기본 3). 같은 노드에 두지 않는 안티 어피니티가 기본(설정으로 존 단위도 가능)
instance-manager노드마다 엔진·레플리카 프로세스를 담는 Pod
스냅샷볼륨 안의 시점 기록(차이 디스크의 사슬). 클러스터 안에 저장되므로 백업이 아님
백업·백업 대상스냅샷을 S3·NFS 같은 외부 대상으로 복사. 정기 작업(recurring job)으로 자동화(15편)
데이터 지역성엔진과 같은 노드에 레플리카 하나를 두도록 노력(best-effort) 또는 강제(strict-local)
RWX볼륨마다 share-manager Pod가 NFSv4로 내보냄. 그 Pod가 단일 장애점이자 성능 병목
용량 과다 할당얇은 할당이라 실제 사용량보다 많이 약속할 수 있음. 과다 할당 비율·최소 여유 비율 설정이 안전장치

V1과 V2 데이터 엔진

  • V1은 오랫동안 써 온 엔진입니다. 파일 시스템 위의 희소 파일에 데이터를 두고 iSCSI로 노드에 붙입니다. 1.11부터 여러 레플리카에서 동시에 받아 오는 병렬 재구축으로 복구 시간이 줄었습니다.
  • V2는 SPDK 기반으로 블록 디스크(NVMe 권장)를 직접 다루는 엔진입니다. 1.11에서 기술 미리보기, 1.12에서 GA, 1.13에서 무중단 업그레이드와 인터럽트 모드가 들어왔습니다. 대신 instance-manager에 전용 CPU 코어(1.13 기본 2개)와 대용량 페이지, 새 커널(5.19 이상, 6.7 이상 권장)이 필요하고, 일부 기능(예: 암호화, V2 백킹 이미지)은 V1과 다릅니다.
  • 한 클러스터에는 하나의 엔진만 켜는 것이 권장입니다. 둘을 켜면 노드마다 instance-manager가 둘이 되어 예약 자원이 겹칩니다.

OpenEBS: LocalPV와 Mayastor

엔진구조복제잘 맞는 곳주의

현장 사례

Ceph가 갑자기 모든 쓰기를 멈췄다

원인. OSD 하나가 full 비율(95%)에 닿았습니다. 전체 사용률은 70%였지만 OSD 크기가 섞여 있고 PG 분포가 고르지 않아 일부 OSD만 먼저 가득 찼습니다.

대응. 임시로 full 비율을 조금 올려 숨통을 틔우고, 불필요한 데이터를 지운 뒤 OSD를 추가하고 밸런서를 켰습니다.

교훈. 경보는 전체 사용률이 아니라 가장 꽉 찬 OSD 기준으로, nearfull보다 앞서(예: 75%) 걸어 두세요.

노드 패치 때마다 클러스터가 몇 시간씩 느려진다

원인. 노드를 재부팅할 때 noout 없이 진행해, 10분을 넘긴 노드의 OSD가 out 처리되고 대규모 백필이 일어났다가 노드가 돌아오면 다시 반대로 옮겨졌습니다.

교훈. 계획된 유지보수는 noout → 한 장애 도메인씩 → HEALTH_OK 확인 → 다음 순서로. Rook을 쓰면 OSD PDB가 동시 드레인을 막아 줍니다.

두 노드를 동시에 재부팅했더니 클러스터가 멈췄다

원인. MON이 세 노드에 하나씩 있었는데 둘이 동시에 내려가 과반수가 깨졌습니다. 스토리지 전체가 응답하지 않았습니다.

교훈. MON·Longhorn 레플리카처럼 과반·복제에 기대는 구성은 동시에 하나씩만 내립니다. OS 패치 자동화의 동시성 설정을 확인하세요.

Longhorn 볼륨이 노드 하나 장애로 사라졌다

원인. 노드가 모자라자 누군가 replica-soft-anti-affinity를 켰고, 새 볼륨의 레플리카 세 개가 한 노드의 두 디스크에 몰려 있었습니다. 그 노드가 죽자 볼륨의 모든 사본이 사라졌습니다.

교훈. 레플리카 배치는 정기 점검 항목입니다. soft 설정은 끄고, 노드가 모자라면 복제 수를 줄이는 대신 노드를 늘리세요.

1GbE에서 Longhorn 재구축이 서비스를 마비시켰다

원인. 노드 교체 후 수 TiB 재구축이 서비스 트래픽과 같은 1GbE를 가득 채워, 다른 볼륨의 쓰기 지연이 수백 ms로 뛰었습니다.

대응. 재구축 동시성을 낮추고, 10GbE 스토리지 네트워크를 Multus로 분리했습니다.

교훈. 재구축 트래픽은 장애 때 가장 크게 생깁니다. 평상시 대역폭이 아니라 7장 계산기의 재구축 시나리오로 네트워크를 설계하세요.

디스크를 갈았는데 새 OSD가 생기지 않는다

원인. 교체 디스크에 이전 시스템의 파티션과 LVM 흔적이 남아 있었습니다. Rook은 데이터 보호를 위해 비어 있지 않은 디스크를 쓰지 않습니다.

교훈. 디스크 교체 런북에 파티션·LVM·장치 매퍼 흔적 제거 단계를 넣고, 지울 장치를 두 번 확인하는 절차를 두세요.

LocalPV 위 단일 DB가 노드와 함께 사라졌다

원인. 성능 때문에 OpenEBS Hostpath에 단일 인스턴스 데이터베이스를 두었는데, 노드 디스크가 고장 났습니다. 복제도 백업도 없었습니다.

교훈. LocalPV는 앱이 복제하는 워크로드 전용입니다. 단일 인스턴스라면 복제 스토리지나 15편의 백업이 전제입니다.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. Ceph는 MON(과반 합의)·OSD(디스크)·MGR·MDS·RGW와 풀·PG·CRUSH로 블록·파일·객체를 모두 제공하며, Rook이 이를 Kubernetes 위에서 운영하고 ODF가 이를 제품화합니다.
  2. Longhorn은 볼륨마다 엔진과 레플리카를 두는 단순한 구조이며, V2 데이터 엔진이 1.12에서 GA, 1.13에서 무중단 업그레이드를 얻었습니다. 장애 동작은 대기 시간·Pod 삭제 정책·안티 어피니티 설정이 좌우합니다.
  3. OpenEBS는 LocalPV(Hostpath·LVM·ZFS)와 Mayastor로 단순해졌고, LocalPV는 앱이 복제하는 워크로드에만 씁니다.
  4. 노드 장애 때 분산 스토리지는 대기 후 재구축하며, 재구축 시간(데이터 ÷ 대역폭)이 곧 두 번째 장애에 노출되는 위험 창입니다. 복제 수 + 1 이상의 노드와 10GbE 이상, 분리된 스토리지 네트워크가 기본입니다.
  5. 유지보수는 noout·한 도메인씩·상태 확인, 용량 경보는 가장 꽉 찬 OSD 기준, 디스크 교체는 흔적 제거까지 런북에 적어야 합니다.
