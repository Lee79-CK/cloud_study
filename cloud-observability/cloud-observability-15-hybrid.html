Cloud 모니터링·로깅 실전 강의 15편 (Level 5. 대규모 운영)

하이브리드 클라우드 수집 설계

지금까지는 고객사 A 하나였습니다. 실제 MSP는 온프레미스, AWS, Azure가 섞인 고객사 여럿을 받고, 고객사마다 네트워크 정책과 데이터 반출 조건이 다릅니다. 고객사 B를 처음부터 온보딩하면서 "고객사가 늘어나도 무너지지 않는 수집 구조"를 만듭니다.

대상: 1~2년차 클라우드 엔지니어 형식: 개념 + 실습 5개 예상 소요: 4~5시간 기준: Alloy 1.20, ansible-core 2.21, nginx 1.24
고객사 온보딩 설계 도우미새 고객사의 조건을 고르면 이 강의의 구성 요소 중 무엇을 어떻게 조합할지 제안합니다. 각 제안은 이 편과 앞 편의 해당 장으로 이어집니다.

0시작하기 전에

14편에서 고객사가 관제 센터로 밀어 올리는 구조를 만들었습니다. 이번에는 그 입구를 하나로 모으고 인증을 붙인 뒤, 조건이 다른 두 번째 고객사를 받습니다.

학습 목표

  1. 고객사별 환경, 네트워크, 데이터 반출 조건에 따라 수집 구조를 설계할 수 있다.
  2. 관제 센터에 단일 입구를 두고, 고객사 인증으로 테넌트를 강제해 사칭을 막을 수 있다.
  3. Prometheus가 없는 고객사에 Alloy 하나로 로그, 메트릭, 프로파일을 수집할 수 있다.
  4. AWS, Azure, GCP의 메트릭과 로그를 가져오는 구성과 권한을 설계하고, OpenShift 내장 모니터링과 공존시킬 수 있다.
  5. 중계 서버, 프록시, 디스크 버퍼로 막힌 네트워크와 일시 단절에 대응할 수 있다.
  6. 데이터 반출이 제한된 고객사의 예외 설계를 고를 수 있다.
  7. Ansible 역할로 수집기를 검증 게이트와 함께 일괄 배포할 수 있다.
이 편의 검증 범위

nginx 1.24로 통합 입구를 실제로 띄워 Mimir 3.2.2, Loki 3.7.8, Pyroscope 2.3.2 앞에 두고 시험했습니다. 고객사 B 자격 증명으로 고객사 A의 테넌트 헤더를 사칭해 보내도 데이터가 B 테넌트로만 들어가는 것, 인증 없음과 틀린 비밀번호의 401, 질의 경로 차단(404), 입구를 150초 끊었을 때 Alloy가 재시도로 빈 구간 없이 메우는 것(실패 0, 재시도 3,535 샘플)을 확인했습니다. Ansible 역할은 ansible-core 2.21.5로 세 서버의 설정을 렌더링해 각각 alloy validate를 통과시켰고, 그 과정에서 변수 우선순위 함정을 실제로 겪었습니다. 클라우드 메트릭 설정은 Alloy 1.20.1의 문법 검사만 통과했고 실제 AWS, Azure 계정으로는 시험하지 못했습니다. Kubernetes 위의 입구 배포와 새 VM 생성도 실행하지 못했습니다.

1하이브리드 수집의 네 가지 질문

고객사를 받을 때마다 다음 네 질문에 답하고, 답의 조합으로 구성을 정합니다. 히어로의 도우미가 이 표를 따라 제안합니다.

질문선택지영향
1. 무엇이 어디에 있나온프레미스 VM, Kubernetes, 클라우드 관리형 서비스(RDS, Azure SQL 등)VM은 에이전트, Kubernetes는 DaemonSet과 Operator(5, 8편), 관리형 서비스는 클라우드 API(4장)
2. 어떻게 나가나서버마다 아웃바운드, 중계 서버 한 대, 프록시, 불가중계와 버퍼(5장), 관제 센터 입구 하나(2장)
3. 무엇을 내보내도 되나전체, 요약, 알림만14편의 요약 전송, 반출 제한 설계(6장)
4. 누가 운영하나MSP가 수집기까지, 고객사가 수집기를 운영하고 MSP는 받기만배포 자동화(7장)와 책임 경계 문서

2hub 통합 입구

지금까지 고객사는 Mimir(30080), Loki(30100), OTLP 게이트웨이(30317, 30318)에 각각 따로 보냈고, 테넌트는 보내는 쪽이 붙인 X-Scope-OrgID 헤더를 그대로 믿었습니다. 7, 11, 14편에서 반복해서 "운영에서는 입구에서 인증 후 헤더를 강제"라고 미뤄 둔 것을 이번에 만듭니다.

경로보내는 곳신호
/api/v1/pushMimir메트릭 (Remote Write)
/loki/api/v1/pushLoki로그
/pyroscope/...Pyroscope (접두어를 떼고 전달)프로파일 (13편에서 미룬 VM 경로)
/v1/traces, /v1/metrics, /v1/logsOTLP 게이트웨이(11편)OTLP
/ready입구 자신 (인증 없음)연결 점검 (2편 probe 역할)
그 밖404질의 API는 입구에 열지 않음

인증으로 테넌트를 정하는 원리

map $remote_user $tenant {      # 기본 인증 사용자 이름 → 테넌트
  default  "";
  cust-a   cust-a;
  cust-b   cust-b;
}
...
location = /api/v1/push { proxy_set_header X-Scope-OrgID $tenant; proxy_pass http://mimir...; }

proxy_set_header는 보내는 쪽이 붙인 같은 이름의 헤더를 버리고 입구가 정한 값으로 바꿉니다. 작성 중 고객사 B의 자격 증명으로 X-Scope-OrgID: cust-a를 붙여 메트릭(Alloy), 로그(curl), 프로파일(Python SDK)을 보냈더니, 세 저장소 모두에서 데이터가 cust-b 테넌트에만 들어갔고 cust-a에는 하나도 없었습니다. 수집기 설정을 실수하거나 악의로 바꿔도 다른 고객사 데이터에 섞이지 않습니다.

OTLP 경로는 아직 완전히 강제되지 않습니다

OTLP 게이트웨이(11, 12, 14편)는 고객사를 리소스 속성 customer로 나누므로, 입구가 붙인 헤더를 쓰지 않습니다. 완전히 강제하려면 게이트웨이 수신기에 include_metadata: true를 켜고 라우팅 연결기의 조건을 요청 헤더(request["X-Scope-OrgID"]) 기준으로 바꿔야 합니다. 이 랩은 메트릭, 로그, 프로파일 경로만 강제하고 OTLP는 기존 방식(에이전트가 붙인 속성 + 누락 시 unknown)을 유지합니다.

운영에서는 TLS가 필수

기본 인증은 비밀번호가 base64로 실려 가므로 평문 HTTP에서는 의미가 없습니다. 이 랩은 내부 네트워크라 HTTP를 썼지만, 운영에서는 입구 앞에 인증서를 붙이고(로드밸런서, Ingress, 또는 nginx의 TLS), 고객사별 클라이언트 인증서(mTLS)나 토큰으로 바꾸는 것도 검토합니다.

4클라우드 메트릭, 로그, OpenShift

RDS, ELB, Azure SQL처럼 서버에 에이전트를 설치할 수 없는 관리형 서비스는 클라우드 사업자의 모니터링 API로 가져옵니다.

클라우드수집 방법권한주의
AWSAlloy prometheus.exporter.cloudwatch (YACE 기반), 또는 독립 YACECloudWatch 읽기, 태그 조회 (Lab 5의 정책)GetMetricData는 지표 수만큼 과금. 태그로 대상을 좁히고 수집 간격을 길게(5분)
AzureAlloy prometheus.exporter.azure구독 범위의 Monitoring Reader 역할을 가진 서비스 주체API 호출 한도. 자원 종류별로 나눠 수집
관리형 PrometheusAMP, Azure Managed Prometheus (5편 5장)원격 읽기, 질의 권한이미 거기 있는 데이터는 Grafana 데이터소스로 직접 보는 것도 선택지

클라우드 API 수집기는 어디에 둘지가 중요합니다. 고객사 계정 안(중계 서버)에 두면 자격 증명이 고객사 밖으로 나가지 않고, MSP 쪽에 두면 고객사 계정에 교차 계정 역할(AWS의 AssumeRole, Azure의 다중 테넌트 앱)을 만들어야 합니다. 보안 담당자와 함께 고르되, 이 강의는 자격 증명을 고객사 안에 두는 쪽을 기본으로 합니다.

GCP

GCP의 Cloud Monitoring 지표는 Alloy의 prometheus.exporter.gcp로 가져옵니다. 프로젝트에 roles/monitoring.viewer 역할을 가진 서비스 계정을 만들고, 지표 접두어(compute.googleapis.com/instance/cpu 등)와 사용자 라벨 필터로 대상을 좁힙니다. Cloud Monitoring API도 호출량에 따라 과금되므로 5분 간격을 기본으로 합니다.

클라우드 로그

관리형 서비스의 로그는 각 클라우드의 로그 서비스에 모이므로, "로그 서비스 → 스트리밍 서비스 → Alloy 수신기"의 경로로 가져옵니다.

클라우드클라우드 쪽 설정Alloy 컴포넌트
AWSCloudWatch Logs 구독 필터 → Kinesis Data Firehose → HTTP 엔드포인트loki.source.awsfirehose (HTTP 수신, 공개 엔드포인트와 인증 키 필요)
Azure자원의 진단 설정 → Event Hubsloki.source.azure_event_hubs (Kafka 프로토콜로 읽음)
GCPCloud Logging 싱크 → Pub/Sub 주제와 구독loki.source.gcplog (pull)

~/obs-lab/vm/alloy/cloud-more.alloy (GCP 메트릭, 세 클라우드의 로그)

// ---------- GCP: Cloud Monitoring 메트릭 (서비스 계정: roles/monitoring.viewer) ----------
prometheus.exporter.gcp "gcp" {
  project_ids      = [sys.env("GCP_PROJECT_ID")]
  metrics_prefixes = ["compute.googleapis.com/instance/cpu", "cloudsql.googleapis.com/database"]
  extra_filters    = ["compute.googleapis.com:metadata.user_labels.\"msp-customer\"=\"cust-b\""]
  request_interval = "5m"
}

// ---------- 클라우드 로그 ----------
// AWS: CloudWatch Logs → 구독 필터 → Kinesis Data Firehose → HTTP 엔드포인트(이 수신기)
loki.source.awsfirehose "aws" {
  http {
    listen_address = "0.0.0.0"
    listen_port    = 9999
  }
  forward_to = [loki.write.msp.receiver]
}

// Azure: 진단 설정 → Event Hubs → 이 수신기 (Kafka 프로토콜)
loki.source.azure_event_hubs "azure" {
  fully_qualified_namespace = sys.env("AZURE_EVENTHUB_NAMESPACE") + ".servicebus.windows.net:9093"
  event_hubs                = ["msp-logs"]
  forward_to                = [loki.write.msp.receiver]
  authentication {
    mechanism         = "connection_string"
    connection_string = sys.env("AZURE_EVENTHUB_CONNECTION_STRING")
  }
}

// GCP: Cloud Logging 싱크 → Pub/Sub → 이 수신기 (pull)
loki.source.gcplog "gcp" {
  pull {
    project_id   = sys.env("GCP_PROJECT_ID")
    subscription = "msp-logs-sub"
  }
  forward_to = [loki.write.msp.receiver]
}

loki.write "msp" {
  endpoint {
    url = sys.env("MSP_INGRESS") + "/loki/api/v1/push"
    basic_auth {
      username = "cust-b"
      password = sys.env("MSP_INGEST_PASSWORD")
    }
  }
  external_labels = { customer = "cust-b", source = "cloud" }
}

prometheus.scrape "gcp" {
  targets         = prometheus.exporter.gcp.gcp.targets
  scrape_interval = "5m"
  scrape_timeout  = "2m"
  forward_to      = [prometheus.remote_write.msp.receiver]
}

prometheus.remote_write "msp" {
  endpoint {
    url = sys.env("MSP_INGRESS") + "/api/v1/push"
    basic_auth {
      username = "cust-b"
      password = sys.env("MSP_INGEST_PASSWORD")
    }
  }
  external_labels = { customer = "cust-b", source = "cloud" }
}

위 설정은 작성 중 Alloy v1.20.1의 validate를 통과했습니다(실제 클라우드 계정으로는 시험하지 못함). AWS의 Firehose는 MSP 쪽에서 HTTP 엔드포인트를 받아야 하므로, 15편의 통합 입구 뒤에 두거나 고객사 계정 안의 중계 서버를 공개 엔드포인트로 노출해야 합니다. 어느 쪽이든 Firehose의 접근 키 헤더로 인증합니다. 로그는 메트릭보다 양이 훨씬 많으므로, 구독 필터와 싱크 필터에서 필요한 로그 그룹, 심각도만 먼저 거르는 것이 비용의 핵심입니다.

OpenShift 고객사: 내장 모니터링과의 공존

OpenShift에는 Prometheus, Alertmanager, Thanos Querier로 된 플랫폼 모니터링이 이미 들어 있고, 그 운영 주체는 클러스터 운영 정책을 따릅니다. 5편 5장에서 말한 대로 여기에 커뮤니티 Prometheus Operator나 kube-prometheus-stack을 따로 설치하면 CRD가 충돌합니다. 대신 내장 스택에 Remote Write 설정을 더해 MSP 입구로 요약을 보내고, 로그는 OpenShift Logging의 ClusterLogForwarder로 보냅니다.

OpenShift 고객사의 내장 스택 연동 (예)

# OpenShift 고객사: 내장 모니터링 스택이 MSP 입구로 요약을 보냄 (커뮤니티 Operator를 추가 설치하지 않음, 5편 5장)
apiVersion: v1
kind: Secret
metadata: { name: msp-ingest, namespace: openshift-monitoring }
stringData: { user: cust-c, password: "<입구 비밀번호>" }
---
apiVersion: v1
kind: ConfigMap
metadata: { name: cluster-monitoring-config, namespace: openshift-monitoring }
data:
  config.yaml: |
    prometheusK8s:
      externalLabels:
        customer: cust-c
        cluster: ocp-prod
      remoteWrite:
        - url: https://msp-ingress.example.com/api/v1/push
          basicAuth:
            username: { name: msp-ingest, key: user }
            password: { name: msp-ingest, key: password }
          writeRelabelConfigs:
            - sourceLabels: [__name__]
              regex: '.+:.+|up|ALERTS|kube_pod_container_status_restarts_total|kube_deployment_status_replicas_available'
              action: keep
---
# OpenShift Logging 6.x: 애플리케이션, 인프라 로그를 MSP 입구의 Loki 경로로 (필드는 설치된 버전에서 oc explain으로 확인)
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata: { name: msp, namespace: openshift-logging }
spec:
  serviceAccount: { name: msp-log-forwarder }
  outputs:
    - name: msp-loki
      type: loki
      loki:
        url: https://msp-ingress.example.com
        authentication:
          username: { key: user, secretName: msp-ingest }
          password: { key: password, secretName: msp-ingest }
  pipelines:
    - name: to-msp
      inputRefs: [application, infrastructure]
      outputRefs: [msp-loki]

플랫폼 Prometheus의 설정은 openshift-monitoring의 cluster-monitoring-config로만 바꿀 수 있고, 고객사 애플리케이션의 메트릭(사용자 워크로드 모니터링)은 openshift-user-workload-monitoring의 user-workload-monitoring-config에 같은 형식으로 Remote Write를 줍니다. ClusterLogForwarder는 Logging 버전에 따라 API 그룹과 필드가 바뀌어 왔으므로(5.x의 logging.openshift.io/v1에서 6.x의 observability.openshift.io/v1로), 고객사 클러스터에서 oc explain clusterlogforwarder.spec.outputs로 확인한 뒤 적용합니다. 이 매니페스트는 YAML 문법만 확인했고 OpenShift에서 실행하지는 못했습니다.

prometheus.remote_write는 WAL에 쌓아 두고 연결이 돌아오면 다시 보냅니다. 로그도 loki.source.file의 읽은 위치 기록 덕분에 재시작 후 이어 읽습니다.

실측: 입구 150초 단절

Alloy(중계 역할)가 15초마다 수집해 입구로 보내는 중에 입구 nginx를 150초 동안 멈췄다가 다시 켰습니다. Alloy는 그 사이 재시도를 계속했고(prometheus_remote_storage_samples_retried_total 3,535), 실패로 버린 샘플은 0이었습니다. 복구 1분 뒤 Mimir에서 5분 구간을 15초 간격으로 조회하니 점 20개가 빈 구간 없이 이어졌습니다. 고객사 관점에서는 "잠깐 끊긴 것"이 데이터 손실로 이어지지 않았습니다. 다만 WAL이 보관하는 시간(기본 2시간 정도)보다 길게 끊기면 그 이상은 잃으므로, 입구 장애 알림(6편 Watchdog, 이 편 Lab 4)을 둡니다.

아웃바운드가 아예 불가능한 고객사(폐쇄망)는 수집 데이터를 관제 센터로 보낼 수 없습니다. 이 경우 고객사 안에 관측 스택을 통째로 두고(Prometheus, Loki, Grafana를 고객사 안에), MSP는 원격 접속 절차로 그 Grafana를 보는 방식이 되며, 이 시리즈의 중앙 구조와는 별도의 운영 모델입니다.

6데이터 반출이 제한된 고객사

14편 7장에서 예고한 예외 설계입니다. "운영 데이터는 우리 밖으로 나가면 안 된다"는 계약을 가진 고객사(공공, 금융 일부)를 위한 선택지입니다.

방식무엇이 나가나MSP가 할 수 있는 것
알림과 서비스 요약만 반출ALERTS와 서비스 단위 기록 규칙, 호스트 식별 라벨 제거장애 감지, SLO 보고. 원인 조사는 고객사 안에서
Thanos 사이드카 + 고객사 버킷질의 결과만 (데이터는 고객사 버킷에)VPN으로 고객사 안의 Thanos Querier에 질의

반출 제한 고객사의 prometheus.yml (예)

# 데이터 반출이 제한된 고객사: 알림 상태와 서비스 수준 요약만, 호스트 식별 라벨은 지우고 보냄
remote_write:
  - url: http://HUB_HOST:30999/api/v1/push
    basic_auth: { username: cust-c, password_file: /etc/prometheus/msp-ingest-password }
    write_relabel_configs:
      - source_labels: [__name__]
        regex: 'ALERTS|service:.+:.+'
        action: keep
      - regex: 'instance|host|pod|node'
        action: labeldrop

첫 번째 방식의 Remote Write 예입니다. 이름이 ALERTS이거나 service:로 시작하는 기록 규칙만 남기고, instance, host, pod, node 라벨을 지웁니다. 작성 중 promtool check config로 문법을 확인했습니다. 어떤 라벨을 지울지는 계약서의 "식별 가능 정보" 정의에 맞춰 고객사와 합의합니다.

7Ansible로 일괄 배포

고객사가 늘면 서버마다 Alloy 설정을 손으로 고칠 수 없습니다. 8편 13장에서 예고한 대로 Ansible 역할 하나로 모든 고객사 서버에 배포합니다.

파일역할
inventory.yml고객사별 그룹(cust_a, cust_b)과 서버, 서버별 로그 파일, 고객사별 조건(메트릭 직접 수집 여부, eBPF 프로파일링)
group_vars/all.yml모든 고객사 공통: 입구 주소, Alloy 버전, 비밀번호(ansible-vault로 암호화)
roles/alloy_agent/tasks/install.ymlapt 저장소, 버전 고정 설치, 그룹 권한, eBPF 서버의 root 실행
roles/alloy_agent/tasks/config.yml템플릿 렌더링 → alloy validate → 통과하면 배치 → 재시작
roles/alloy_agent/templates/config.alloy.j2조건에 따라 메트릭, 프로파일 블록을 넣고 빼는 설정 틀

설정 작업은 3, 4편의 검증 게이트와 같은 순서입니다. 새 파일로 렌더링하고, 검증이 실패하면 거기서 멈춰 기존 설정은 그대로 둡니다. 서버 수백 대에 잘못된 설정이 한꺼번에 퍼지는 것을 막는 장치입니다.

실측으로 겪은 함정: 변수 우선순위

처음에 "기본값"으로 send_host_metrics: false를 group_vars/all.yml에 두고, 고객사 B 그룹에서만 인벤토리 파일 안에 true로 덮어썼습니다. 그런데 렌더링된 고객사 B의 설정에 메트릭 블록이 없었습니다. Ansible은 인벤토리 파일 안의 그룹 변수보다 group_vars/ 디렉터리의 all 변수를 더 높은 우선순위로 적용하기 때문입니다. 기본값을 역할의 defaults/main.yml(가장 낮은 우선순위)로 옮겨 해결했습니다. "기본값은 역할 defaults에, 고객사별 값은 group_vars/고객사 또는 인벤토리에"를 팀 규칙으로 정해 두세요.

증상을 눌러 원인과 해결 방법을 확인하세요.

입구 nginx가 시작하지 않음: host not found in upstreamLab 1

설정의 업스트림 서비스 중 하나가 클러스터에 없습니다. 7, 11, 13, 14편의 서비스가 모두 있는지 확인하고, 없는 신호의 location은 지웁니다.

올바른 비밀번호인데 401Lab 1

htpasswd의 해시 형식 문제입니다. 알파인 nginx는 bcrypt($2y$)를 읽지 못합니다. openssl passwd -apr1로 만든 $apr1$ 형식을 씁니다(작성 중 시험한 형식).

데이터가 엉뚱한 테넌트에 들어감, 또는 테넌트 없음 오류Lab 1, 3

nginx의 map에 그 사용자가 없으면 테넌트가 빈 문자열이 되어 저장소가 거부합니다. 사용자를 추가할 때 htpasswd와 map을 함께 고칩니다. 입구를 거치지 않고 개별 포트로 직접 보내는 수집기가 남아 있지 않은지도 확인합니다.

Pyroscope 전송이 404Lab 3

입구의 location /pyroscope/와 proxy_pass ...:4040/의 끝 슬래시가 접두어를 떼는 역할을 합니다. 둘 중 하나가 빠지면 Pyroscope가 /pyroscope/... 경로를 모릅니다. 수집기 쪽 주소는 .../pyroscope(끝 슬래시 없음)입니다.

Ansible로 렌더링한 설정에 기대한 블록이 없음Lab 3

7장의 변수 우선순위 함정입니다. ansible-inventory -i inventory.yml --host cust-b-app로 그 서버에 실제로 적용되는 변수 값을 확인합니다.

Ansible validate 단계에서 실패하고 배치가 멈춤Lab 3

의도된 동작입니다. 실패 메시지의 줄 번호를 렌더링된 .new 파일에서 찾아 템플릿을 고칩니다. 기존 설정과 서비스는 그대로 돌고 있습니다.

고객사 B 서버에서 아무것도 안 감 (ufw 적용 후)Lab 2

입구 주소가 IP로 정확한지, DNS(53) 허용이 있는지, Alloy의 엔드포인트가 30999를 가리키는지 확인합니다. 설치 전에 막았다면 apt 저장소에 닿지 못합니다.

CloudWatch 수집이 비어 있거나 AccessDeniedLab 5

오늘의 핵심

  1. 고객사마다 환경, 네트워크, 반출, 운영 주체의 네 가지 질문에 답하고 그 조합으로 구성을 정합니다.
  2. 관제 센터 입구를 하나로 모으고 고객사 인증으로 테넌트를 강제합니다(실측: 사칭 헤더가 무시되고 자기 테넌트에만 저장).
  3. Prometheus가 없는 고객사는 서버당 Alloy 하나로 로그, 메트릭, 프로파일을 보냅니다.
  4. 관리형 클라우드 서비스는 각 클라우드의 모니터링 API(메트릭)와 로그 스트리밍(Firehose, Event Hubs, Pub/Sub)으로 가져오되 권한, 비용, 한도를 먼저 설계합니다. OpenShift는 내장 스택에 Remote Write를 더합니다.
  5. 중계 서버와 버퍼로 막힌 네트워크와 일시 단절에 대응합니다(실측: 150초 단절에도 빈 구간 없음).
  6. 반출 제한 고객사는 알림과 요약만, 또는 데이터를 고객사 안에 두는 예외 설계를 씁니다.
  7. Ansible 역할로 렌더링 → 검증 → 배치를 자동화하고, 변수 우선순위를 규칙으로 정합니다.
