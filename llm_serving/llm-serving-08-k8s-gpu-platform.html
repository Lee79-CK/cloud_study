Kubernetes 위의
GPU 플랫폼

비싼 GPU를 누구에게, 얼마나, 어떤 순서로 나눠 줄 것인가. 1편 7계층의 L2를 깊게 들어갑니다. 정수 개수로 GPU를 세던 Device Plugin에서 속성으로 고르는 DRA로의 전환, 한 GPU를 여럿이 쓰는 타임 슬라이싱·MPS·MIG가 LLM 서빙에 맞는 경우와 아닌 경우, 노드 풀과 토폴로지, 그리고 Kueue로 서빙과 배치·학습 작업을 한 클러스터에 공존시키는 법까지. 7편에서 미뤄 둔 “기존 RAG 플랫폼과 GPU를 함께 쓰는 방법”의 답도 여기서 정리합니다.

선행 7편 랩 읽는 시간 약 100분 실습 약 150분 기준 2026년 10월 · Kubernetes 1.34~1.37
GPU 요청이 Pod에 닿기까지

    01시작하기 전에

    GPU 스케줄링 정책은 곧 비용 정책입니다. 놀고 있는 GPU 한 장은 매달 수백만 원입니다.

    학습 목표

    1. Device Plugin과 DRA의 할당 경로를 단계별로 설명하고, DRA가 해결하는 한계와 아직 남은 제약을 말할 수 있다.
    2. DeviceClass·ResourceSlice·ResourceClaim·ResourceClaimTemplate와 CEL 선택자로 “조건에 맞는 GPU”를 요청할 수 있다.
    3. 타임 슬라이싱·MPS·MIG·DRA 공유의 격리 수준과 LLM 서빙 적합성을 비교하고, MIG 프로파일로 모델 배치를 계산할 수 있다.
    4. GB10의 통합 메모리가 GPU 공유에 주는 제약을 설명하고, 메모리 예산을 세울 수 있다.
    5. 노드 풀·라벨·테인트·토폴로지 인지 스케줄링으로 GPU 종류별 배치를 설계할 수 있다.
    6. Kueue로 서빙과 배치·학습 작업의 할당량·우선순위·선점을 설계하고, 단일 GPU에서 대기열을 동작시킬 수 있다.
    이 편의 비유: 회의실 예약

    Device Plugin은 “회의실 1개 주세요”만 말할 수 있는 예약 시스템입니다. 어떤 회의실인지(크기·화면·층)는 고를 수 없고, 반만 쓰는 것도 안 됩니다. DRA는 “10명 이상, 화상회의 장비 있는 방, 같은 층의 방 두 개”처럼 조건으로 예약하게 해 줍니다. 타임 슬라이싱은 한 방을 30분씩 번갈아 쓰는 것, MPS는 한 방에 두 팀이 같이 들어가 각자 일하는 것, MIG는 방에 벽을 세워 진짜 작은 방 여러 개로 나누는 것입니다. 그리고 Kueue는 예약 대기 명단과 팀별 사용 한도를 관리하는 총무팀입니다.

    02GPU가 Pod에 닿는 두 경로

    무엇이 바뀌었는지는 경로를 나란히 놓으면 보입니다.

    관점Device Plugin (확장 자원)DRA (Dynamic Resource Allocation)
    요청 방식resources.limits: nvidia.com/gpu: 1 — 정수 개수ResourceClaim으로 장치 클래스·속성 조건(CEL)·개수를 선언
    장치 정보스케줄러는 개수만 앎. 종류는 노드 라벨(GFD)로 간접 지정드라이버가 ResourceSlice로 장치별 속성(제품명, 메모리, 아키텍처, PCIe 위치 등)을 공개, 스케줄러가 직접 보고 고름
    할당 결정 주체스케줄러는 노드만 고르고, 어느 GPU인지는 kubelet·플러그인이 정함스케줄러가 노드와 장치를 함께 결정해 클레임에 기록
    공유같은 GPU를 여러 Pod가 쓰려면 플러그인 설정(타임 슬라이싱·MPS)으로 “가짜 개수”를 광고여러 Pod가 하나의 클레임을 공유하거나, 소비 가능 용량·분할 장치로 표현
    설정 전달환경 변수·노드 단위 설정클레임에 장치별 설정을 담아 드라이버가 준비 단계에서 적용
    우선순위·선점Pod 우선순위·선점과 함께 동작NVIDIA 문서 기준, DRA 자원에 대한 선점은 쿠버네티스가 지원하지 않음 (설계 시 주의)
    성숙도수년간 표준코어 API는 Kubernetes v1.34에서 GA(resource.k8s.io/v1). 세부 기능과 드라이버 성숙도는 기능별로 다름
    전환은 “둘 중 하나”가 아니라 “노드별로”

    한 노드에서 Device Plugin과 DRA 드라이버가 같은 GPU를 동시에 광고하면 이중 할당이 생깁니다. 그래서 전환은 보통 노드 단위로 합니다(GPU Operator는 노드 라벨로 구성 요소를 끌 수 있음). 최신 쿠버네티스(1.36~1.37)에서는 DRA 드라이버가 예전 방식의 nvidia.com/gpu: 1 요청도 처리할 수 있게 하는 확장 자원 호환 기능이 들어와, 기존 매니페스트를 그대로 두고 전환하는 길이 열리고 있습니다. 클러스터 버전별 상태는 반드시 확인하세요.

    03DRA 리소스 모델 해부

    네 가지 리소스와 하나의 표현식 언어(CEL)만 알면 DRA 매니페스트가 읽힙니다.

    리소스누가 만드나역할비유
    DeviceClass관리자·드라이버 설치 시장치의 종류(예: gpu.nvidia.com, mig.nvidia.com)와 기본 선택 조건·설정“회의실”이라는 범주
    ResourceSliceDRA 드라이버 (노드마다)노드에 있는 장치 목록과 장치별 속성·용량 공개건물의 회의실 목록표
    ResourceClaim사용자“이런 조건의 장치 N개”라는 요청. 할당 결과가 status에 기록됨. 여러 Pod가 하나를 공유 가능예약 신청서
    ResourceClaimTemplate사용자Pod마다 클레임을 자동으로 만들어 주는 틀 (Deployment에 주로 사용)신청서 양식
    yaml · 조건으로 GPU 고르기 (Kubernetes 1.34+, resource.k8s.io/v1)
    apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata: { name: gpu-16g-plus, namespace: llmsvc-lab }
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          selectors:
          - cel:
              # 메모리 16GiB 이상인 GPU만 (속성 이름·형식은 ResourceSlice로 확인)
              expression: "device.capacity['gpu.nvidia.com'].memory.compareTo(quantity('16Gi')) >= 0"
---
# Pod(또는 Deployment의 Pod 템플릿)에서 사용
apiVersion: v1
kind: Pod
metadata: { name: dra-demo, namespace: llmsvc-lab }
spec:
  resourceClaims:
  - name: gpu
    resourceClaimTemplateName: gpu-16g-plus
  containers:
  - name: app
    image: nvcr.io/nvidia/cuda:13.0.1-base-ubuntu24.04
    command: ["nvidia-smi", "-L"]
    resources:
      claims: [ { name: gpu } ]          # limits의 nvidia.com/gpu 대신

    알아 둘 DRA 기능들

    기능무엇을 하나LLM 서빙에서의 쓰임상태
    CEL 선택자속성·용량 조건으로 장치 선택“80GB 이상”, “Hopper 이상”, “특정 드라이버 버전 이상”코어(GA)
    우선순위 목록 (firstAvailable)“H200이 있으면 H200, 없으면 H100 두 장”처럼 대안 순서 지정혼합 GPU 클러스터에서 유연한 배치버전별 확인 (베타 이상 진행 중)
    클레임 공유여러 Pod가 같은 ResourceClaim 참조같은 GPU를 쓰는 사이드카·보조 프로세스코어
    소비 가능 용량장치 하나를 용량 단위로 여러 클레임이 나눠 씀공유 GPU의 논리적 몫 표현1.36부터 기본 활성(그 전은 기능 게이트)
    분할 가능 장치장치를 겹치지 않는 조각으로 동적으로 나눠 할당NVIDIA 드라이버의 동적 MIG(H100 이상)기능 게이트 필요, 드라이버별
    확장 자원 호환DRA 드라이버가 nvidia.com/gpu: N 요청도 처리기존 매니페스트 유지한 채 전환1.36~1.37에서 진행 (버전 확인)
    관리자 접근사용 중인 장치에 모니터링용으로 접근진단·관측 도구버전별 확인
    NVIDIA DRA 드라이버 도입 전 확인
    • NVIDIA의 DRA 드라이버는 kubernetes-sigs로 옮겨져 dra-driver-nvidia-gpu로 개발되며, 전체 GPU·기존 MIG 장치 할당이 공식 지원(GA)입니다. 동적 MIG는 H100 이상에서, 분할 가능 장치 기능을 켠 클러스터에서 동작합니다(A100은 MIG 모드를 자유롭게 켜고 끌 수 없어 첫 릴리스 대상에서 제외).
    • NVIDIA 문서 기준 요구 사항은 Kubernetes v1.34.2 이상, NVIDIA 드라이버 580 이상입니다.
    • GPU Operator가 DRA 드라이버를 관리하는 방식(GPUCluster 리소스)도 생겼지만, 기존 설치에서의 제자리 이전은 지원되지 않는 경로가 있으니 문서를 확인합니다.
    • DRA 자원에는 쿠버네티스 선점이 적용되지 않는다는 점은 서빙(높은 우선순위)과 배치(낮은 우선순위)를 섞는 설계에서 중요합니다. 선점이 필요한 공존 시나리오는 아직 Device Plugin + Kueue 쪽이 다루기 쉽습니다(8장).

    04GPU 공유 전략

    공유는 GPU를 아끼지만, 무엇을 격리하지 못하는지 알아야 사고가 안 납니다.

    방식원리연산 격리메모리 격리장애 격리지원 GPULLM 서빙 적합성
    전용 할당Pod 하나가 GPU 전체완전완전완전모두기본값. 7B 이상 생성 모델 서빙
    타임 슬라이싱Device Plugin이 GPU 하나를 N개로 광고, 컨텍스트를 시간 분할없음 (번갈아 실행)없음없음대부분개발·데모·저부하 소형 모델. 지연 SLO가 있는 서빙엔 부적합
    MPS여러 프로세스가 하나의 GPU 컨텍스트를 공유해 동시에 실행. 프로세스별 연산 비율·메모리 한도 설정 가능부분 (비율 제한)부분 (한도 설정)약함 (한 프로세스 오류가 다른 쪽에 영향 가능)Volta 이후 대부분 (장비별 확인)소형 모델 여러 개, 임베딩·리랭커 동거
    MIG하드웨어로 GPU를 최대 7개 인스턴스로 분할 (연산 유닛·메모리·캐시·대역폭까지)완전완전강함A100·H100·H200·B200 등 데이터센터 GPU (L4·GB10은 미지원)임베딩·리랭커·소형 모델의 멀티테넌시. 큰 LLM에는 조각이 작음
    DRA 공유클레임 공유, 소비 가능 용량 등으로 공유를 API에 표현드라이버·설정에 따름드라이버·설정에 따름설정에 따름드라이버 지원 장치공유 의도를 명시적으로 관리하는 차세대 방식
    vGPU (가상화)하이퍼바이저가 GPU를 VM에 분할시간 분할 또는 MIG 기반있음VM 단위라이선스 필요VM 기반 고객 환경. 이 시리즈 범위 밖

    LLM 서빙에서 공유가 까다로운 이유

    1. 엔진은 메모리를 미리 통째로 잡는다(2·4편). vLLM은 기동 시 지정 비율만큼 KV 풀을 확보하므로, 두 엔진이 같은 GPU를 공유하면 비율 합이 1을 넘는 순간 나중에 뜬 쪽이 실패합니다. 타임 슬라이싱은 이를 전혀 막아 주지 않습니다.
    2. Decode는 메모리 대역폭을 다 쓰고 싶어 한다(2편). 두 엔진이 번갈아 또는 동시에 돌면 각자의 TPOT가 거의 두 배가 됩니다. 처리량 합은 비슷할 수 있지만 지연 SLO는 무너집니다.
    3. CUDA 그래프·커널 캐시가 GPU 상태에 의존합니다. 시간 분할 전환 비용과 캐시 오염으로 전체 효율도 떨어질 수 있습니다.

    그래서 원칙은 단순합니다. 생성 모델 서빙은 전용 할당(필요하면 MIG 큰 조각), 공유는 소형 모델·임베딩·개발·저부하 용도. 공유를 쓸 때는 메모리 예산을 사람이 직접 관리합니다(6장).

    05MIG 분할 서빙 비교

    MIG는 “GPU 한 장을 작은 GPU 여러 장으로” 만드는 하드웨어 기능입니다. 어떤 모델이 어느 조각에 들어가고, 쪼개면 전체 처리량이 어떻게 되는지 계산해 봅니다.

    MIG 프로파일 이름 3g.40gb는 “연산 조각 3개(전체 7개 중) + 메모리 40GB”를 뜻합니다. 메모리 대역폭도 대략 메모리 조각 비율만큼 나뉩니다. 랩 장비(GB10, P3의 RTX A400)는 MIG를 지원하지 않으므로, 이 장의 비교는 계산기로 하고, 실습 8-5에서 MIG 지원 GPU를 쓸 수 있을 때의 절차를 제공합니다.

    MIG 배치 계산기

    GPU와 MIG 구성을 고르고 모델을 정하면, 조각마다 모델이 들어가는지와 Decode 처리량의 대략적인 합을 전체 GPU 1개로 쓸 때와 비교합니다. 2편의 단순 대역폭 모델(배치 8, 컨텍스트 2K)을 쓴 교육용 추정입니다.

    06GB10 통합 메모리와 공유

    GB10에서는 “GPU 메모리”라는 칸막이가 없습니다. 공유의 모든 위험이 메모리 예산으로 모입니다.

    • MIG 없음: 하드웨어 격리 공유가 불가능합니다. 남는 선택지는 전용 할당, 타임 슬라이싱, (지원 여부를 확인한) MPS입니다.
    • 메모리를 CPU와 공유: 128GB는 OS, 쿠버네티스 구성 요소, 컨테이너의 CPU 메모리, 그리고 각 엔진의 GPU 메모리가 함께 쓰는 하나의 풀입니다. 엔진의 gpu-memory-utilization은 이 풀에 대한 비율이므로, 여러 엔진의 비율 합과 나머지 사용량을 사람이 맞춰야 합니다.
    • 메모리 지표 부재: nvidia-smi와 DCGM의 GPU 메모리 사용량이 “지원 안 됨”으로 나와, GPU 메모리 대시보드로 공유 상태를 볼 수 없습니다. 노드 메모리(free, node-exporter)와 엔진 지표(KV 사용률)로 대신 봅니다.
    • 대역폭 경쟁: 0.273TB/s의 작은 대역폭을 나눠 쓰므로, 동시에 Decode하면 두 엔진 모두 TPOT가 크게 나빠집니다.

    GB10 메모리 예산 계산기

    한 GB10 노드에서 동시에 돌릴 것들의 몫을 넣어, 128GB 안에 안전하게 들어가는지 확인합니다.
    OS·시스템RAG 엔진랩 엔진호스트 엔진컨테이너 CPU 메모리초과분

    07노드 풀·라벨·토폴로지

    어떤 워크로드가 어떤 GPU에 가야 하는지, 그리고 여러 GPU가 필요할 때 어떻게 “가까이” 놓을지.

    GPU Feature Discovery 라벨

    GPU Operator에 포함된 GPU Feature Discovery(GFD)가 노드에 GPU 정보를 라벨로 붙입니다. Device Plugin 방식에서는 이 라벨이 “어떤 GPU인가”를 고르는 유일한 수단입니다.

    라벨 (예)의미쓰임
    nvidia.com/gpu.productGPU 제품명모델별 노드 셀렉터
    nvidia.com/gpu.memoryGPU 메모리(MiB)“80GB 노드” 같은 조건 (GB10은 값이 다르게 보일 수 있음)
    nvidia.com/gpu.count노드의 GPU 수텐서 병렬용 다중 GPU 노드
    nvidia.com/cuda.driver.major드라이버 메이저 버전CUDA 13 이미지 배치 조건(4편)
    nvidia.com/gpu.compute.major연산 능력(아키텍처)FP8 지원 세대 이상만(6편)
    nvidia.com/mig.capable · mig.strategyMIG 가능 여부·전략MIG 노드 구분

    노드 풀 설계

    노드 풀은 “같은 종류의 노드 묶음”을 라벨·테인트로 표현한 것입니다. 클라우드에서는 관리형 노드 그룹이나 Karpenter NodePool로, 온프레미스에서는 라벨·테인트 규칙으로 만듭니다.

    풀GPU테인트올라가는 워크로드
    cpu-general없음없음게이트웨이, 관측, 앱, 측정 클라이언트
    gpu-smallL4, 또는 MIG 조각nvidia.com/gpu=present:NoSchedule임베딩·리랭커·소형 모델
    gpu-servingH100·H200 (NVLink 8장 노드)같음 + pool=serving:NoSchedule생성 모델 서빙 (전용)
    gpu-batch여유 GPU·스팟pool=batch:NoSchedule평가·양자화·배치 추론·파인튜닝 (Kueue 관리)
    GPU 노드에는 반드시 테인트

    테인트가 없으면 GPU가 필요 없는 일반 Pod가 GPU 노드의 CPU·메모리를 차지해, 정작 GPU Pod가 CPU 부족으로 뜨지 못하는 일이 생깁니다. GPU를 쓰는 Pod만 톨러레이션을 갖게 합니다. 7편 랩의 매니페스트가 nvidia.com/gpu 톨러레이션을 갖고 있는 이유입니다.

    토폴로지 인지 배치

    • 노드 안: 텐서 병렬은 같은 NVLink 도메인(같은 노드)의 GPU끼리(3편). Device Plugin의 GPU 개수 요청은 대개 같은 노드에서 충족되지만, 어떤 GPU 쌍이 NVLink로 직접 연결됐는지까지 고르려면 DRA 속성(PCIe 루트 등)이 도움이 됩니다.
    • 노드 사이: 멀티노드 인스턴스(17편)는 같은 랙·같은 네트워크 블록에 모이는 것이 좋습니다. Kueue의 토폴로지 인지 스케줄링(TAS)은 노드 라벨로 블록·랙·호스트 계층을 정의하고 워크로드를 가까이 배치합니다. LeaderWorkerSet 배치 개선도 계속되고 있습니다.
    • GPU와 NIC 정렬: P/D 분리나 멀티노드 통신에서는 GPU와 같은 PCIe 스위치 아래의 고속 NIC를 함께 할당하는 것이 성능에 중요합니다. DRA가 여러 장치의 정렬 조건을 표현하는 방향으로 발전하고 있습니다.

    08Kueue: 서빙과 배치의 공존

    쿠버네티스 스케줄러는 “지금 넣을 자리가 있나”만 봅니다. 누구에게 얼마까지, 어떤 순서로를 정하는 것은 Kueue의 일입니다.

    Kueue는 쿠버네티스 SIG가 만드는 작업 대기열·할당량 관리자입니다. 원래 배치·학습 작업용이었지만 Deployment·StatefulSet 같은 서빙 워크로드도 함께 관리하는 방향으로 넓어졌고, 토폴로지 인지 스케줄링, 여러 클러스터에 작업을 나눠 보내는 MultiKueue, LeaderWorkerSet 지원이 계속 성숙하고 있습니다. 2026년 7월 v0.19.0이 나왔고 API는 v1beta2입니다.

    개념역할단일 GPU 랩에서
    ResourceFlavor자원의 “종류”를 노드 라벨·테인트와 연결 (예: pgx-gb10, h100-sxm)pgx 하나
    ClusterQueue종류별 할당량(nominalQuota), 선점 정책, 대상 네임스페이스GPU 1, CPU·메모리 상한
    LocalQueue네임스페이스 안에서 사용자가 작업을 넣는 큐. ClusterQueue를 가리킴llmsvc-lab의 gpu 큐
    WorkloadKueue가 작업 하나를 추상화한 객체. 승인(admission)되면 Pod가 실제로 생성·스케줄됨엔진 Deployment, 양자화 Job 등
    WorkloadPriorityClassKueue 안의 우선순위. 선점 판단에 사용서빙 높음 · 배치 낮음
    Cohort · 빌려 쓰기여러 ClusterQueue가 남는 할당량을 빌려 쓰고 돌려받는 묶음, 공정 분배(멀티 팀·멀티 테넌트에서)

    단일 GPU 대기열 시뮬레이터

    GPU 할당량 1인 ClusterQueue에 워크로드를 차례로 넣어 봅니다(체크한 순서가 제출 순서). 우선순위가 높은 워크로드가 들어오면 낮은 워크로드는 선점되어 대기열로 돌아갑니다(선점 정책: 같은 큐 안에서 낮은 우선순위 선점).
    승인됨 (GPU 사용 중)
    대기 (Pod 미생성)
    이벤트

    Kueue가 해 주지 않는 것

    Kueue는 자기가 승인한 워크로드만 센다

    Kueue의 할당량은 논리적 장부입니다. Kueue가 관리하지 않는 Pod(예: 기존 RAG 플랫폼)가 GPU를 쓰고 있어도 Kueue는 모릅니다. 그러면 Kueue는 할당량이 남았다고 보고 작업을 승인하고, 실제 Pod는 GPU가 없어 Pending에 머뭅니다. GPU를 쓰는 모든 워크로드를 Kueue 아래에 두거나, Kueue가 관리할 GPU 노드를 따로 분리해야 장부와 현실이 맞습니다.

    설치와 설정

    bash · Kueue 설치 (버전은 릴리스 페이지에서 최신 확인)
    KUEUE=v0.19.0
kubectl apply --server-side -f https://github.com/kubernetes-sigs/kueue/releases/download/$KUEUE/manifests.yaml
kubectl -n kueue-system wait --for=condition=Available deploy/kueue-controller-manager --timeout=5m
kubectl api-resources | grep kueue.x-k8s.io        # 제공되는 API 버전 확인 (v1beta2)

    서빙(Deployment)을 Kueue로 관리하려면 Pod·Deployment 통합을 켜야 합니다. 이 통합은 Pod 생성 웹훅을 쓰므로 관리 대상 네임스페이스를 라벨로 좁혀 기존 RAG 플랫폼에 영향이 없게 합니다. 설정 키 이름은 설치한 버전의 문서를 확인하세요.

    yaml · kueue-system/kueue-manager-config 의 controller_manager_config.yaml 중 일부

integrations:
  frameworks:
  - "batch/job"
  - "pod"                              # Deployment 통합에 필요
  - "deployment"
  - "leaderworkerset.x-k8s.io/leaderworkerset"   # 17편 멀티노드 서빙에서
    yaml · 8편 랩용 Kueue 리소스 (kueue.yaml)
    apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata: { name: pgx-gb10 }

    09RAG 플랫폼과 GPU 함께 쓰기

    7편에서 미뤄 둔 질문의 답. GB10 한 장을 기존 RAG 플랫폼과 랩이 함께 써야 할 때의 선택지입니다.

    방법어떻게장점위험·비용권장 상황
    ① 시간으로 나누기실습할 때 RAG 엔진을 0으로 줄였다가 복구가장 안전, 설정 변경 없음RAG 플랫폼 중단 시간RAG가 개발·테스트용이고 실습 시간이 정해진 경우 (기본 권장)
    ② Kueue 대기열RAG 엔진·랩 엔진·배치 작업 모두 Kueue 관리, 우선순위로 자동 양보·선점규칙이 시스템에 들어감, 이후 멀티 테넌트 설계의 연습RAG 플랫폼 매니페스트에 라벨 추가 필요, Kueue 운영공존이 일상이 될 때, 배치 작업이 많을 때
    ③ 타임 슬라이싱 + 메모리 예산GPU를 2개로 광고, 두 엔진의 메모리 비율을 6장 계산기로 맞춤동시에 둘 다 떠 있음격리 없음, 대역폭 경쟁으로 둘 다 느려짐, 비율을 잘못 잡으면 한쪽 기동 실패둘 다 저부하 기능 확인용일 때
    ④ 랩을 다른 GPU로P3의 RTX A400(4GB)에서 소형 모델·DRA 실습PGX를 건드리지 않음4GB라 0.6B급 모델만, 성능 실습엔 부적합DRA·스케줄링 기능 실습(실습 8-2)
    이 판단은 고객사에서도 그대로 반복된다

    “GPU 한두 장으로 개발팀 여러 개가 함께 쓰고 싶다”는 요청은 MSP 현장에서 흔합니다. 답의 구조는 같습니다. 격리가 필요하면 전용 또는 MIG, 효율이 우선이고 서로 믿는 팀이면 대기열(Kueue)과 시간 분할, 동시 실행이 꼭 필요하면 타임 슬라이싱·MPS에 메모리 예산과 SLO 포기를 함께 합의합니다.

    PGX를 건드리지 않는 DRA 실습(P3의 RTX A400)을 중심으로, 공유·대기열을 단계별로 확인합니다. 클러스터 공용 설정을 바꾸는 실습은 “선택”으로 표시했고 모두 되돌리는 절차를 포함합니다.

    • 7편 랩이 준비되어 있어야 합니다(./lab.sh preflight로 확인).

    실습 8-3 · (선택) PGX 타임 슬라이싱과 메모리 예산

    GPU 하나를 2개로 광고하게 해 RAG 엔진과 랩 엔진을 동시에 띄우고, 각각 혼자일 때와 TPOT를 비교합니다. 클러스터 공용 설정(ClusterPolicy)을 바꾸는 작업이므로 먼저 8-1에서 기존 Device Plugin 설정이 있는지 확인하고, 있다면 그 ConfigMap에 항목을 추가하는 방식으로 합니다.

    yaml · time-slicing-config.yaml
    apiVersion: v1
kind: ConfigMap
metadata: { name: time-slicing-config, namespace: gpu-operator }
data:
  pgx-ts2: |-                       # 노드 라벨로 선택할 설정 이름
    version: v1
    flags: { migStrategy: none }
    sharing:
      timeSlicing:
        renameByDefault: false
        failRequestsGreaterThanOne: true
        resources:
        - name: nvidia.com/gpu
          replicas: 2
    bash · 적용 (PGX 노드에만)과 되돌리기
    kubectl apply -f time-slicing-config.yaml
# ClusterPolicy가 이 ConfigMap을 참조하게 함 (기본 설정 이름은 지정하지 않아 다른 노드는 영향 없음)
kubectl patch clusterpolicies.nvidia.com/cluster-policy --type merge \
  -p '{"spec":{"devicePlugin":{"config":{"name":"time-slicing-config"}}}}'
PGX=<PGX 노드 이름>
kubectl label node $PGX nvidia.com/device-plugin.config=pgx-ts2 --overwrite
sleep 60; kubectl get node $PGX -o jsonpath='{.status.allocatable.nvidia\.com/gpu}'; echo "  ← 2"

    실습 8-5 · MIG 분할 서빙 비교 (MIG 지원 GPU가 있을 때)

    랩 장비에는 MIG가 없으므로, 5장 계산기로 예측을 먼저 하고, 클라우드나 고객사의 A100·H100·H200 노드를 쓸 수 있을 때 아래 절차로 실측합니다.

    1. 예측: 5장 계산기에서 H100 + all-1g.10gb + 임베딩 소형 모델, 그리고 all-3g.40gb + Qwen3-8B FP8의 “조각별 합계 vs 전체 1개” 처리량을 기록합니다.
    2. MIG 적용: GPU Operator의 MIG 관리자는 노드 라벨로 프로파일을 바꿉니다. 예: kubectl label node <노드> nvidia.com/mig.config=all-1g.10gb --overwrite. 상태는 nvidia.com/mig.config.state 라벨로 확인(success). GPU에서 실행 중인 Pod가 있으면 적용이 막히므로 비워 둡니다.
    3. 자원 확인: MIG 전략이 mixed면 nvidia.com/mig-1g.10gb 같은 자원 이름으로, single이면 nvidia.com/gpu로 광고됩니다. DRA 드라이버를 쓰면 mig.nvidia.com 장치 클래스로 요청합니다.
    4. 측정: 조각마다 엔진 하나씩 띄워 동시에 engine_bench.py를 돌리고 합계를 냅니다. 같은 GPU를 MIG 없이 엔진 하나로 썼을 때와 비교합니다.
    5. 되돌리기: nvidia.com/mig.config=all-disabled로 라벨을 바꿉니다.

    기대 결과: 작은 모델 여러 개(임베딩·리랭커·소형 생성 모델)는 MIG 조각에서 격리와 높은 총 활용률을 얻고, 큰 생성 모델은 조각이 작아 KV 공간이 부족하거나 처리량 합이 전체 1개보다 낮아지는 경향이 나타납니다.

    9문제.

    15정리와 체크리스트

    핵심 여섯 문장.

    1. Device Plugin은 개수, DRA는 조건. DRA는 드라이버가 공개한 장치 속성으로 스케줄러가 노드와 장치를 함께 고른다. 코어는 1.34에서 GA, 세부 기능과 드라이버 성숙도는 따로 확인한다.
    2. DRA 자원에는 선점이 적용되지 않는다. 서빙과 배치를 우선순위로 섞는 설계는 이 제약을 감안한다.
    3. 생성 모델 서빙은 전용 할당이 기본이다. 타임 슬라이싱은 격리가 없고, MPS는 부분 격리, MIG는 하드웨어 격리지만 조각이 작다.
    4. GB10은 MIG가 없고 메모리를 CPU와 공유한다. 공유는 사람이 세운 메모리 예산 위에서만 가능하다.
    5. 노드 풀은 라벨·테인트로, 토폴로지는 NVLink 도메인과 랙 단위로 설계한다. GPU 노드에는 반드시 테인트를 건다.
    6. Kueue는 할당량·우선순위·선점의 장부다. GPU를 쓰는 모든 워크로드가 Kueue 아래에 있어야 장부와 현실이 맞는다.
