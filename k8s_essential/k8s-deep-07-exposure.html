클러스터 외부 노출: LoadBalancer 컨트롤러와 Ingress의 세대 교체

type: LoadBalancer 한 줄은 EKS에서는 클래식 LB를, LB 컨트롤러를 깔면 NLB를, AKS에서는 공유 Standard LB의 새 프런트엔드를, GKE에서는 패스스루 LB를, 온프렘에서는 영원한 pending을 만듭니다. 그 위의 L7 계층은 2026년 3월 ingress-nginx 은퇴로 세대 교체 중입니다. 이 편은 요청이 어디서 몇 번 넘어가는지, 클라이언트 IP가 어디서 사라지는지, 헬스 체크가 무엇을 보는지, 돈이 어디서 나가는지를 같은 앱으로 비교합니다.

읽는 법과 목표

    
쉬운 말로
    클러스터를 건물로 보면, L4 로드밸런서는 건물 정문 경비실입니다. 손님이 어느 출입문(포트)으로 왔는지만 보고 안으로 들여보냅니다. L7 로드밸런서·Ingress·Gateway는 로비 안내 데스크입니다. 손님이 들고 온 서류(HTTP 경로·호스트 이름)를 읽고 어느 부서로 보낼지 정합니다. 이 편은 경비실이 손님을 바로 사무실까지 데려다주는지(IP 대상), 일단 아무 층에나 내려놓는지(인스턴스 대상), 그리고 안내 데스크 업체가 바뀌는 중(ingress-nginx 은퇴)이라는 이야기를 다룹니다.

    

      
이 편을 마치면 할 수 있는 것

      
    
        
  • LoadBalancer Service를 실제 LB로 바꾸는 주체(CCM, LB 컨트롤러, MetalLB 등)를 환경별로 짚고, loadBalancerClass로 원하는 구현을 고를 수 있습니다.
    • 
        
  • 인스턴스 대상과 IP 대상의 홉 수, 출발지 IP, 헬스 체크, 롤링 업데이트 중 오류 차이를 설명할 수 있습니다.
    • 
        
  • EKS·AKS·GKE·온프렘의 L4·L7 선택지를 비교하고, 고객 요구(출발지 IP, TLS 위치, 비용, 내부 전용)에 맞는 조합을 고를 수 있습니다.
    • 
        
  • ingress-nginx 은퇴의 의미를 정확히 설명하고, 어노테이션 목록부터 시작하는 이전 계획을 세울 수 있습니다.
    • 
        
  • LB 수와 비용, 고아 리소스, 쿼터 같은 운영 위험을 점검할 수 있습니다.

LoadBalancer Service의 계약

    

      
Kubernetes는 type: LoadBalancer에 대해 “외부 LB를 만들고, 그 주소를 status.loadBalancer.ingress에 적어라”는 계약만 정의합니다. 누가 그 일을 하는지는 클러스터마다 다르고, 아무도 하지 않으면 EXTERNAL-IP는 영원히 <pending>입니다. 3편 스모크 테스트에서 kubeadm·RKE2·OpenShift Local이 pending이었던 이유입니다.

    

    

      
필드·개념역할운영 포인트

      
        
loadBalancerClass어느 컨트롤러가 이 Service를 맡을지 지정. 비우면 클라우드 CCM의 기본 서비스 컨트롤러 몫EKS에서 service.k8s.aws/nlb를 지정하면 CCM 대신 LB 컨트롤러가 처리. 클러스터에 컨트롤러가 둘 이상일 때 충돌 방지

        
allocateLoadBalancerNodePortsfalse면 NodePort를 할당하지 않음IP 대상 LB는 NodePort가 필요 없으므로 꺼서 노드 포트 노출을 줄임

        
loadBalancerSourceRangesLB에 접근할 수 있는 출발지 대역클라우드 방화벽·보안 그룹 규칙으로 번역됨. 구현마다 적용 위치가 다름

        
externalTrafficPolicy·healthCheckNodePort6편. Local이면 엔드포인트 있는 노드만 헬스 체크를 통과노드 경유(인스턴스 대상) LB에서만 의미가 큼

        
status.loadBalancer.ingressLB의 IP 또는 호스트 이름, ipModeAWS는 호스트 이름, Azure·GCP·MetalLB는 IP

        
spec.loadBalancerIP고정 IP 지정(폐기됨)구현별 어노테이션(예: Azure 공용 IP 이름, MetalLB의 주소 지정)으로 대체

        
혼합 프로토콜한 Service에 TCP·UDP 포트 함께1.26 GA지만 클라우드 LB가 지원하는지는 구현마다 다름

      
    

    
시니어 포인트: ipMode가 노드 안 처리를 바꾼다
    LB가 패킷의 목적지를 LB IP 그대로 노드에 보내는 경우(VIP 방식, GCP 패스스루·Azure·MetalLB)에는 kube-proxy가 LB IP 규칙으로 받아야 하고, 클러스터 안의 Pod가 LB IP를 부르면 kube-proxy가 노드 안에서 바로 처리(단축)해 버립니다. 반대로 LB가 프록시처럼 목적지를 바꿔 보내는 경우(Proxy 방식)에는 클러스터 안에서 LB IP를 불러도 실제 LB를 거쳐야 TLS 종료·프록시 프로토콜이 제대로 동작합니다. status.loadBalancer.ingress[].ipMode는 이 차이를 kube-proxy에게 알려 주는 필드이고, 1.32에서 GA가 됐습니다.

인스턴스 대상 vs IP 대상

    
쉬운 말로
    인스턴스 대상은 경비실이 손님을 “아무 층”(노드의 NodePort)에 내려 주면 그 층 안내원(kube-proxy)이 다시 사무실을 찾아 주는 방식입니다. IP 대상은 경비실이 사무실 주소(Pod IP)를 직접 알고 바로 데려다주는 방식입니다. 한 번 덜 넘어가고, 경비실이 사무실 문이 열려 있는지(헬스 체크)도 직접 확인합니다.

    

      
관점인스턴스(노드) 대상IP(Pod) 대상

      
        
경로LB → 노드:NodePort → kube-proxy → Pod(다른 노드일 수 있음)LB → Pod IP

        
요구 조건없음(어디서나)LB가 Pod IP에 닿아야 함: VPC 직결 CNI(EKS VPC CNI, Azure CNI Pod Subnet), GKE NEG, 또는 오버레이라도 클라우드가 지원하는 경우

        
출발지 IPCluster 정책이면 노드에서 SNAT로 손실. Local이면 보존LB 종류에 따라: L4 패스스루면 보존 가능, L7 프록시면 X-Forwarded-For로 전달

        
헬스 체크노드를 봄(Cluster: NodePort, Local: healthCheckNodePort). Pod 상태와 어긋날 수 있음Pod를 직접 봄

        
부하 분산 정확도LB는 노드 단위로 나누고 kube-proxy가 다시 나눔(이중 분산)Pod 단위로 정확

        
롤링 업데이트kube-proxy 규칙 갱신 속도에 좌우LB 대상 등록·해제 지연에 좌우. 준비 게이트·preStop 필요(12장 두 번째 사례)

        
대상 수노드 수(작음)Pod 수(대상 그룹 한도·등록 API 호출량 주의)

      
    

    

      
준비 게이트: “LB가 준비됐다”를 Pod Ready에 포함시키기

      
IP 대상에서는 새 Pod가 Kubernetes 기준으로 Ready가 되어도, 클라우드 LB가 그 Pod를 대상으로 등록하고 헬스 체크를 통과하기까지 수십 초가 걸립니다. 그 사이 롤링 업데이트가 옛 Pod를 지우면 LB에 건강한 대상이 하나도 없는 순간이 생깁니다. Pod 준비 게이트는 “LB에서도 건강하다”는 조건을 Pod의 Ready 조건에 추가해 이 틈을 막습니다. AWS LB 컨트롤러(네임스페이스 레이블 elbv2.k8s.aws/pod-readiness-gate-inject=enabled)와 GKE NEG(cloud.google.com/load-balancer-neg-ready)가 이 방식을 씁니다.

AWS: CCM 기본 동작과 AWS Load Balancer Controller

    
쉬운 말로
    EKS에는 경비실을 세우는 업체가 둘 있습니다. 기본으로 들어 있는 오래된 업체(CCM의 서비스 컨트롤러)는 아무 설정 없이 Service를 만들면 구형 경비실(Classic LB)을 세웁니다. 새 업체(AWS Load Balancer Controller)는 직접 설치해야 하지만 신형 L4 경비실(NLB)과 L7 안내 데스크(ALB)를 세우고, 사무실까지 바로 데려다주는 IP 대상도 지원합니다.

    

      
구성만드는 LB대상언제

      
        
아무것도 설치 안 함 + LoadBalancer ServiceClassic LB(레거시)인스턴스권장하지 않음. 3편 스모크 테스트의 lab-eks가 이 상태

        
LBC + Service(aws-load-balancer-type: external 또는 loadBalancerClass: service.k8s.aws/nlb)NLBinstance 또는 ipL4, TCP·UDP·TLS, 고정 IP(EIP) 필요 시

        
LBC + Ingress(ingressClassName: alb)ALBinstance 또는 ipHTTP 라우팅, ACM 인증서, WAF

        
LBC + Gateway APIALB(HTTPRoute·GRPCRoute) / NLB(TCP·UDP·TLSRoute)ip 중심신규 구성. v3.1에서 GA

        
EKS Auto ModeNLB·ALB(내장 컨트롤러)ipLB 컨트롤러 설치·업그레이드를 AWS가 맡음

      
    

    

      
알아 둘 운영 포인트

      
    
        
  • 버전 계열. 컨트롤러는 v3 계열이 현재 유지보수 대상이고 v2 계열은 2026년 1월 v2.17.1을 끝으로 동결됐습니다. v3는 Gateway API CRD가 없으면 Gateway 컨트롤러를 자동으로 끄므로, Ingress·Service만 쓰는 기존 구성은 그대로 옮겨집니다. 고객 클러스터의 컨트롤러 버전을 인벤토리에 넣으세요(1편 공동 책임).
    • 
        
  • NLB IP 대상의 출발지 IP. NLB는 인스턴스 대상에서는 클라이언트 IP를 보존하지만, IP 대상의 TCP·TLS 리스너는 기본값이 보존 꺼짐입니다. 대상 그룹 속성 preserve_client_ip.enabled=true를 켜거나 프록시 프로토콜 v2를 쓰세요.
    • 
        
  • 등록 해제 지연. 대상 그룹의 등록 해제 지연(기본 300초) 동안 LB는 종료 중인 Pod에 기존 연결을 유지하려 합니다. Pod의 종료 유예 시간이 더 짧으면 연결이 끊깁니다. 준비 게이트, preStop 지연, 등록 해제 지연 값을 함께 맞춥니다.
    • 
        
  • ALB 하나에 여러 앱. Ingress마다 ALB가 생기면 비용이 늘어납니다. alb.ingress.kubernetes.io/group.name으로 여러 Ingress를 ALB 하나에 묶을 수 있습니다(9장 계산기). 다만 같은 그룹의 Ingress끼리는 규칙 충돌·권한 경계를 공유하게 됩니다.
    • 
        
  • 서브넷 태그와 보안 그룹. 컨트롤러는 kubernetes.io/role/elb(공개)·kubernetes.io/role/internal-elb(내부) 태그로 서브넷을 고르고, LB 보안 그룹과 노드·Pod 보안 그룹 규칙을 자동 관리합니다. 사람이 콘솔에서 고친 규칙은 덮어써질 수 있습니다.

Azure: Standard LB, App Routing, Application Gateway for Containers

    

      
L4: 클러스터마다 하나의 Standard LB

      
    
        
  • 공유 LB. AKS는 클러스터마다 Azure Standard LB를 하나(공개용 kubernetes, 내부용 kubernetes-internal) 두고, LoadBalancer Service마다 프런트엔드 IP와 규칙을 추가합니다. Service마다 LB가 새로 생기는 AWS·GCP와 비용 구조가 다릅니다.
    • 
        
  • 패스스루. Azure LB는 패킷을 프록시하지 않고 목적지 LB IP 그대로 노드에 전달합니다(플로팅 IP). 클라이언트 IP가 보존되며, Cluster 정책에서는 노드에서 SNAT, Local에서는 끝까지 보존됩니다.
    • 
        
  • 자주 쓰는 어노테이션. 내부 LB service.beta.kubernetes.io/azure-load-balancer-internal: "true", 미리 만든 공용 IP service.beta.kubernetes.io/azure-pip-name, 헬스 프로브 경로 service.beta.kubernetes.io/azure-load-balancer-health-probe-request-path.
    • 
        
  • 백엔드 풀 방식. 노드 NIC 기준 또는 노드 IP 기준(nodeIP)으로 구성할 수 있으며, 대형 클러스터에서 LB 갱신 속도에 영향을 줍니다.
    •

GCP: L4 패스스루와 NEG, GKE Gateway

    

      
L4

      
    
        
  • 외부 패스스루 Network LB. LoadBalancer Service는 클라이언트 IP를 바꾸지 않는 패스스루 LB를 만들고, 패킷은 목적지 LB IP 그대로 노드에 도착합니다(ipMode VIP). Cluster 정책에서는 노드에서 SNAT, Local에서는 보존됩니다. 최근 버전은 백엔드 서비스 기반 구현(cloud.google.com/l4-rbs: "enabled")을 씁니다.
    • 
        
  • 내부 LB. networking.gke.io/load-balancer-type: "Internal". 대형 클러스터에서는 L4 내부 LB 서브세팅을 켜면 모든 노드 대신 일부 노드만 백엔드로 넣어 한도 문제를 피합니다.
    • 
        
  • Service마다 전달 규칙. LB Service 하나가 클라우드 전달 규칙(forwarding rule)을 만들고, 이것이 시간당 과금·쿼터 단위입니다.
    • 
      

      
L7: 컨테이너 네이티브 부하 분산

      
    
        
  • NEG. Pod IP:포트를 LB 백엔드로 직접 등록하는 GCP 리소스입니다. VPC-native(5편)라 가능한 IP 대상 방식이며, Service에 cloud.google.com/neg: '{"ingress": true}'를 붙이거나 Gateway가 자동으로 만듭니다. kubectl get svcneg로 보입니다.
    • 
        
  • GKE Ingress(gce, gce-internal 클래스): Google 관리형 L7 LB를 만드는 기존 방식. 헬스 체크·타임아웃 등은 BackendConfig CRD로.
    • 
        
  • GKE Gateway 컨트롤러: gke-l7-global-external-managed(전역 외부), gke-l7-regional-external-managed(리전 외부), gke-l7-rilb(리전 내부) 등 GatewayClass로 LB 종류를 고릅니다. 리전 관리형 클래스는 VPC에 프록시 전용 서브넷이 있어야 합니다(12장 사례). 헬스 체크는 HealthCheckPolicy, 백엔드 설정은 GCPBackendPolicy로 합니다. 클러스터에서 Gateway API를 켜야 합니다(--gateway-api=standard).

온프렘 L4: MetalLB, kube-vip, Cilium LB IPAM

    
쉬운 말로
    클라우드에는 경비실을 세워 주는 업체가 있지만, 온프렘에는 없습니다. 그래서 노드 중 하나가 “이 대표 주소는 저예요”라고 동네에 외치거나(ARP 응답, L2 방식), 동네 라우터에게 “이 주소로 오는 건 저희 노드들로 보내 주세요”라고 경로를 알립니다(BGP 방식).

    

      
구현주소 관리광고 방식특징쓰는 곳

      
        
MetalLBIPAddressPoolL2(ARP·NDP, 리더 노드 하나) / BGP(ECMP로 여러 노드)가장 널리 쓰임. v0.16 계열은 BGP 백엔드로 frr-k8s를 기본으로 씀. L2는 리더 노드 하나로 몰리고 장애 전환이 수 초kubeadm, RKE2, OpenShift(MetalLB 오퍼레이터)

        
kube-vip설정·ConfigMap·클라우드 프로바이더ARP(리더 선출) / BGP컨트롤 플레인 API 엔드포인트 VIP와 Service LB를 한 도구로. 소규모·엣지에 인기kubeadm HA 앞단, RKE2

        
Cilium LB IPAMCiliumLoadBalancerIPPoolL2 알림(CiliumL2AnnouncementPolicy) / BGP 컨트롤 플레인CNI와 한 몸. DSR·Maglev(6편)와 결합. 별도 도구 불필요Cilium 쓰는 클러스터(5편 실습 2)

        
RKE2 servicelb노드 IP 사용노드 포트 직접 열기K3s 계열의 단순 구현. RKE2에서는 기본 꺼짐(enable-servicelb)테스트·단일 노드

      
    

    

      
L2 방식과 BGP 방식의 운영 차이

      
    
        
  • L2. Service IP 하나당 노드 하나가 응답하므로 그 노드가 병목입니다. 노드가 죽으면 다른 노드가 GARP로 “이제 제가 주인”이라고 알리는데, 스위치·방화벽의 ARP 캐시 때문에 전환이 늦어질 수 있습니다. 같은 L2 구간에 클라이언트·게이트웨이가 있어야 합니다.
    • 
        
  • BGP. 라우터가 여러 노드로 ECMP 분산하고 노드 장애는 BGP 세션 종료로 빠르게 반영됩니다. 대신 네트워크 팀과 AS 번호·피어링·경로 필터를 협의해야 하고, Calico BGP(5편)와 같은 노드에서 함께 쓸 때 충돌을 피하는 설계가 필요합니다.
    • 
        
  • Local 정책과의 조합. externalTrafficPolicy: Local이면 MetalLB L2는 엔드포인트가 있는 노드에서만 응답하고, BGP는 엔드포인트가 있는 노드만 경로를 광고합니다. 출발지 IP 보존과 고른 부하 분산을 동시에 얻는 온프렘의 정석 조합입니다.
    •

L7 세대 교체: Ingress 컨트롤러 지형

    

      
ingress-nginx 은퇴가 정확히 뜻하는 것

      
    
        
  • 무엇이 끝났나. 2025년 11월 은퇴가 발표됐고, 2026년 3월로 커뮤니티 프로젝트 kubernetes/ingress-nginx의 유지보수가 끝났습니다. 새 릴리스와 보안 수정이 더는 나오지 않습니다. 이미 돌고 있는 컨트롤러가 멈추는 것은 아닙니다.
    • 
        
  • 무엇이 끝나지 않았나. Ingress API 자체는 폐기되지 않았습니다(기능 동결). F5가 만드는 별개의 NGINX Ingress Controller(nginx/kubernetes-ingress)도 계속 유지됩니다. 이름이 비슷해 고객과의 대화에서 자주 혼동됩니다.
    • 
        
  • 왜 위험한가. 2025년 3월의 심각한 취약점(CVE-2025-1974, 어드미션 웹훅을 통한 원격 코드 실행 계열)처럼, Ingress 컨트롤러는 클러스터에서 가장 많이 노출되고 가장 큰 권한(모든 네임스페이스의 Secret 읽기)을 가진 구성 요소 중 하나입니다. 패치가 없는 상태로 두는 것은 시간이 갈수록 커지는 위험입니다.
    • 
        
  • 벤더 대응. RKE2는 1.36부터 신규 기본을 Traefik으로 바꾸고 1.37 커뮤니티판에서 ingress-nginx 단독 선택지를 없앴습니다. AKS는 관리형 NGINX에 2026년 11월까지 보안 패치를 제공하며 Gateway API(Istio 기반) 구현을 후속으로 GA했습니다. 업스트림은 이전 도구 Ingress2Gateway 1.0(2026-03)을 냈습니다.
    • 
      

      
컨트롤러 고르기

      
조건을 눌러 걸러 보세요. 여러 조건을 누르면 모두 만족하는 것만 남습니다.

    

    

    

    
시니어 포인트: Ingress 컨트롤러 교체가 아니라 API 전환으로 보라
    ingress-nginx를 다른 Ingress 컨트롤러로 바꾸면 어노테이션 방언만 바뀌고 같은 문제가 다음 은퇴 때 반복됩니다. 이번 이전을 Gateway API로의 전환 기회로 쓰면, 컨트롤러를 바꿔도 라우팅 정의(HTTPRoute)는 대부분 그대로 남습니다. 다만 Gateway API 표준에 없는 기능(인증 연동, 속도 제한, 본문 크기 등)은 여전히 구현별 정책 리소스가 필요합니다. 8편에서 설계를 다룹니다.

    

      
OpenShift Router와 Route

      
OpenShift는 Ingress 컨트롤러 시장과 별개로 HAProxy 기반 Router(IngressController 오퍼레이터가 관리)와 Route API를 기본으로 씁니다. Ingress 객체를 만들면 OpenShift가 Route로 변환해 줍니다. Router는 Service를 거치지 않고 엔드포인트로 직접 연결하며, 베어메탈에서는 Router Pod가 노드 네트워크를 쓰고 앞단에 keepalived VIP나 MetalLB를 둡니다. Gateway API는 OpenShift Service Mesh(Istio) 기반으로 제공되며, 버전별 지원 단계를 확인하세요.

  .items[] | . as $i | (.metadata.annotations // {}) | keys[]
  | select(startswith("nginx.ingress.kubernetes.io/"))
  | "\(.)"' | sort | uniq -c | sort -rn

# 위험 신호: 임의 설정 조각을 쓰는 Ingress
kubectl get ingress -A -o json | jq -r '.items[] | select(.metadata.annotations // {} | keys[] | test("snippet"))
  | "\(.metadata.namespace)/\(.metadata.name)"' | sort -u

# IngressClass와 기본 클래스
kubectl get ingressclass -o custom-columns=NAME:.metadata.name,CONTROLLER:.spec.controller,DEFAULT:.metadata.annotations.ingressclass\.kubernetes\.io/is-default-class

비용과 운영

    

      
LB 수가 비용을 정한다

      
AWS와 GCP는 LoadBalancer Service·Ingress마다 별도의 LB(또는 전달 규칙)가 생기고, 각각 시간당 기본 요금이 붙습니다. Azure는 클러스터당 LB 하나를 공유하지만 프런트엔드 IP·규칙 수와 공용 IP가 비용 단위입니다. 앱 30개를 각자 LoadBalancer로 노출하는 것과 L7 게이트웨이 하나로 묶는 것은 비용이 크게 다릅니다. 단가는 리전·시점마다 다르니 기본값을 고객 환경 값으로 바꿔 쓰세요.

    

    

      

        

        

        

        

      

      

      

    

    

      
운영 점검 목록

      
    
        
  • 고아 LB. 클러스터를 먼저 지우면 컨트롤러가 LB를 지울 기회를 잃습니다. Service에는 service.kubernetes.io/load-balancer-cleanup 파이널라이저가 붙어 정리를 보장하려 하지만, 컨트롤러가 사라지면 소용없습니다. 클러스터 삭제 전 LoadBalancer Service·Ingress·Gateway를 먼저 지우고, 태그로 남은 LB·보안 그룹·공용 IP를 찾으세요(3편 8장 규칙).
    • 
        
  • 쿼터. 계정·구독·프로젝트별 LB 수, 공용 IP 수, 전달 규칙 수, 대상 그룹 수 한도가 있습니다. IP 대상은 Pod 수만큼 대상이 생기므로 대상 그룹 한도에 더 빨리 닿습니다.
    • 
        
  • 인증서. 클라우드 L7(ALB·AGC·GKE)은 클라우드 인증서 서비스(ACM, Key Vault, Certificate Manager)와, 클러스터 안 컨트롤러는 cert-manager와 묶는 것이 일반적입니다. 인증서가 어디서 갱신되는지가 장애 지점을 정합니다.
    • 
        
  • DNS. LB 주소가 바뀌는 변경(LB 재생성, 이전)은 DNS 전환을 동반합니다. external-dns로 자동화하더라도 소유권과 TTL을 설계하세요.
    • 
        
  • 클라이언트 IP 기반 기능. 접근 제어·속도 제한·감사 로그가 클라이언트 IP에 의존한다면, 이 편의 비교기로 그 IP가 실제로 Pod까지 오는지 먼저 확인하세요.

6편 실습 0의 svc-lab 앱(agnhost netexec, 3개 레플리카)을 그대로 씁니다. 이 앱은 /clientip로 자기가 본 출발지 주소를, /hostname으로 Pod 이름을 돌려줍니다. 환경마다 같은 다섯 가지를 측정해 마지막 표에 채웁니다: 홉 구성, Pod가 본 출발지 IP, 헬스 체크 대상, Pod 삭제 시 오류 여부, 생성된 LB 수. 클라우드 실습이 끝나면 반드시 LB 리소스를 먼저 지우고 클러스터를 지우세요. 현장 사례

    
EKS에 Classic LB가 수십 개 생겨 있었다

      
원인. LB 컨트롤러를 설치하지 않은 채 팀마다 LoadBalancer Service를 만들어, CCM이 앱마다 Classic LB를 만들었습니다. 비용은 쌓였고 클라이언트 IP는 보이지 않았습니다.

      
대응. LB 컨트롤러를 설치하고 어노테이션 또는 loadBalancerClass로 NLB로 옮긴 뒤, HTTP 앱은 ALB 그룹이나 Gateway 하나로 묶었습니다.

      
교훈. EKS 표준 구성에는 LB 컨트롤러 설치가 포함되어야 합니다. 3편 스모크 테스트에서 LB가 “assigned”라고 안심하면 안 되는 이유입니다.

    

    
NLB IP 대상으로 바꾼 뒤 배포 때마다 502

      
원인. 새 Pod가 Ready가 되자마자 옛 Pod가 지워졌는데, 새 Pod는 아직 대상 그룹 헬스 체크를 통과하지 못한 상태였습니다. 반대로 지워지는 Pod는 등록 해제 지연 동안 연결을 받다가 먼저 종료됐습니다.

      
대응. 네임스페이스에 준비 게이트 주입 레이블을 붙이고, Pod에 preStop 지연(예: 15초)과 그보다 긴 종료 유예 시간을 주고, 등록 해제 지연을 앱 특성에 맞게 줄였습니다.

      
교훈. IP 대상은 “LB가 Pod를 직접 본다”는 장점만큼 Kubernetes 수명 주기와 LB 수명 주기를 맞추는 책임이 생깁니다.

    

    
클러스터를 지웠는데 VPC가 지워지지 않는다

      
원인. LoadBalancer Service와 Ingress를 남긴 채 클러스터를 삭제해, 컨트롤러가 만든 LB·보안 그룹·네트워크 인터페이스가 남았습니다. 이것들이 서브넷을 붙잡고 있어 VPC 삭제가 실패했고 LB 요금도 계속 나갔습니다.

      
교훈. 클러스터 삭제 절차의 첫 단계는 노출 리소스 삭제와 LB 소멸 확인입니다. Terraform으로 관리한다면 Kubernetes 리소스와 클라우드 리소스의 삭제 순서를 명시하세요.

    

    
GKE 리전 Gateway가 만들어지지 않는다

      
원인. gke-l7-regional-external-managed 클래스를 썼는데 VPC에 그 리전의 프록시 전용 서브넷이 없었습니다. Gateway 상태 메시지에만 이유가 나와 있었습니다.

      
교훈. 관리형 L7은 클러스터 밖 네트워크 전제 조건(프록시 서브넷, 방화벽 규칙의 헬스 체크 대역)을 가집니다. Gateway의 status 조건을 먼저 읽으세요.

    

    
MetalLB L2 장애 전환이 1분 넘게 걸린다

      
원인. 광고 노드가 죽은 뒤 새 노드가 GARP를 보냈지만, 앞단 방화벽이 GARP를 무시하고 ARP 캐시 만료까지 옛 MAC으로 보냈습니다.

      
대응. 방화벽의 GARP 수용 설정을 바꾸고, 핵심 서비스는 BGP 모드로 옮겼습니다.

      
교훈. L2 모드의 전환 시간은 클러스터가 아니라 주변 네트워크 장비가 정합니다. 도입 전 장애 전환 시험을 고객 망에서 하세요.

    

    
snippet 어노테이션 때문에 이전 일정이 밀렸다

      
상황. ingress-nginx 이전을 계획했는데, 일부 Ingress가 configuration-snippet으로 헤더 조작·리다이렉트·인증을 직접 NGINX 문법으로 넣고 있었습니다.

      
대응. snippet마다 실제로 하는 일을 기능 단위(헤더 추가, 리다이렉트, 인증 연동)로 풀어 HTTPRoute 필터와 구현 정책으로 다시 만들었습니다. 이 과정에서 보안상 위험한 설정 몇 개를 없앴습니다.

      
교훈. 8장의 인벤토리에서 snippet 사용 Ingress 목록을 가장 먼저 뽑으세요. 이전 일정의 대부분이 여기서 결정됩니다.

    

    
AKS App Routing NGINX의 지원 종료 일정

      
상황. 여러 고객 AKS 클러스터가 App Routing 애드온의 관리형 NGINX를 씁니다. Microsoft의 보안 패치 제공은 2026년 11월까지입니다.

      
대응. 클러스터마다 App Routing Gateway API(Istio 기반)나 AGC로의 이전 일정을 잡고, Key Vault 인증서 연동 방식 차이(현재 CSI 드라이버 경유)를 먼저 검증했습니다.

      
교훈. 관리형 애드온도 업스트림 은퇴의 영향을 받습니다. 1편 인벤토리에 Ingress·Gateway 구현과 지원 종료일을 추가하세요.

  1. LoadBalancer Service는 계약일 뿐이며, 구현은 CCM·LB 컨트롤러·MetalLB 등이 맡고 loadBalancerClass로 고릅니다. 구현이 없으면 pending입니다.
    2. 
        
  2. 인스턴스 대상은 어디서나 되지만 이중 분산과 SNAT·노드 헬스 체크를, IP 대상은 정확한 분산과 Pod 헬스 체크를 주는 대신 LB와 Pod 수명 주기 정렬(준비 게이트·preStop)을 요구합니다.
    3. 
        
  3. EKS는 LB 컨트롤러(v3, Gateway API GA)를 설치해야 제대로 쓰고, AKS는 공유 Standard LB와 App Routing(NGINX → Gateway API)·AGC, GKE는 패스스루 L4와 NEG 기반 Gateway가 축입니다.
    4. 
        
  4. 온프렘 L4는 MetalLB·kube-vip·Cilium LB IPAM이며, L2는 단순하지만 노드 병목과 ARP 전환 지연이, BGP는 빠르고 분산되지만 네트워크 팀 협업이 필요합니다.
    5. 
        
  5. ingress-nginx는 2026년 3월로 유지보수가 끝났고, 이전은 어노테이션 인벤토리에서 시작하며, 컨트롤러 교체보다 Gateway API 전환으로 접근하는 것이 다음 은퇴를 대비하는 길입니다.
    6. 
      

    

    

      
다음 편 · 8편 Gateway API 전환 설계

      
GatewayClass·Gateway·HTTPRoute·GRPCRoute·TLSRoute의 역할 분리 모델(인프라 팀과 앱 팀의 경계), ReferenceGrant로 네임스페이스 경계를 넘는 방법, 구현체(Envoy Gateway, Cilium, Istio, NGINX Gateway Fabric, Kong)와 벤더 구현(GKE, AWS LBC, AKS AGC·App Routing, OpenShift) 비교, 그리고 이 편의 이전 계획을 실제 Gateway 설계로 완성합니다. 카나리 가중치·헤더 라우팅 실습을 Native와 GKE에서 진행합니다.
