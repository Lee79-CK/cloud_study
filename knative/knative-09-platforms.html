플랫폼별 Knative 래핑 현황

같은 Knative라도 고객사 플랫폼에 따라 설치 방식, 버전, 덧붙은 기능, 지원 범위가 모두 다릅니다. 주요 벤더가 Knative를 어떻게 감싸 제공하는지 비교하고, 고객사마다 어떤 길로 접근할지 판단하는 기준을 세웁니다.

기준 시점 2026년 10월 · 업스트림 v1.23 선수 지식: 1~8편 예상 학습 시간 70~90분
이 편의 정보는 빨리 낡습니다

벤더 제품의 버전, 지원 상태, 이름은 수시로 바뀝니다. 아래 내용은 2026년 10월 초에 공개 문서로 확인한 것이며, 고객사 제안이나 설계에 쓰기 전에는 반드시 각 벤더의 최신 릴리스 노트와 수명 주기 정책을 다시 확인하세요.

1 / 16

왜 래핑 현황을 알아야 하나

MSP는 한 플랫폼만 다루지 않습니다. A 고객사는 OpenShift, B 고객사는 GKE, C 고객사는 온프레미스 쿠버네티스를 씁니다. 1~8편에서 배운 Knative 지식은 모두 같지만, 각 플랫폼에서 마주치는 현실은 다릅니다.

버전이 다르다

업스트림은 분기마다 새 버전을 내지만 벤더 배포판은 검증 기간만큼 뒤처집니다. 강의에서 배운 기능이 고객사 플랫폼에는 아직 없을 수 있습니다.

설정하는 곳이 다르다

업스트림은 ConfigMap을 직접 고치지만, Operator나 벤더 콘솔을 쓰는 플랫폼에서는 그 위의 리소스나 화면에서 바꿔야 합니다. 직접 고치면 되돌려집니다.

제공 범위가 다르다

Serving만 주는 곳, Eventing까지 주는 곳, Functions와 워크플로까지 묶어 주는 곳이 있습니다. 빠진 부분은 직접 설치하거나 벤더의 다른 제품으로 메웁니다.

지원 책임이 다르다

벤더 배포판은 장애 시 벤더 지원을 받지만 벤더가 허용한 구성만 지원합니다. 업스트림은 자유롭지만 지원 책임이 MSP에 있습니다.

플랫폼 지도

플랫폼을 눌러 무엇을 감싸 주는지, 무엇을 덧붙이는지, MSP 관점의 주의점은 무엇인지 확인하세요. 초록은 제공, 주황은 부분·조건부, 회색 취소선은 미제공입니다.

4 / 16

Red Hat OpenShift Serverless

가장 완성도 높은 상용 Knative 배포판입니다. OperatorHub에서 OpenShift Serverless Operator를 설치하고 KnativeServing, KnativeEventing, KnativeKafka 리소스로 구성합니다. 2026년 10월 기준 최신 공개 릴리스 노트는 1.37이며, 내부적으로 Knative Serving·Eventing 1.17과 Kourier 1.17을 사용합니다.

구성OpenShift Serverless에서는
네트워킹Kourier가 기본이며 OpenShift Route와 연동. Service Mesh 연동은 별도 구성이고, 1.37에서 Service Mesh 3.x 연동이 기술 프리뷰로 추가
EventingKnative Eventing과 Kafka용 구성(Kafka Broker, KafkaSource, KafkaSink)을 함께 지원
Functionskn func 기반. OpenShift Pipelines(Tekton)로 클러스터 내 빌드. 1.37에서 Python 런타임이 GA
워크플로OpenShift Serverless Logic(SonataFlow 기반 Serverless Workflow)을 별도 주기로 릴리스
설정 방법knative-serving ConfigMap을 직접 고치지 말고 KnativeServing의 spec.config에 적어야 Operator가 덮어쓰지 않음
업그레이드OLM 채널(stable, 버전별 채널)로 관리. OpenShift 버전과의 지원 조합을 수명 주기 표에서 확인
MSP 체크포인트

업스트림 1.23과 6버전 차이가 납니다. 이 강의 4편의 secure-pod-defaults 기본값 변경(1.22), 7편의 raw 배포(1.21) 같은 기능은 OpenShift Serverless 1.37에는 아직 해당하지 않습니다. 고객사 문서를 볼 때는 "제품 버전"과 "내부 Knative 버전"을 따로 확인하세요.

Google: Cloud Run과 GKE용 Knative serving

Google에는 이름이 비슷한 두 갈래가 있어 혼동이 잦습니다.

Cloud Run (완전 관리형)

  • 클러스터 없이 컨테이너를 올리는 Google의 서버리스 서비스
  • Knative를 그대로 돌리지는 않지만 Knative Serving v1 형식의 리소스를 받아들임
  • 이벤트는 Eventarc, 함수는 Cloud Run functions로 연결

Knative serving (GKE용)

  • 고객의 GKE 클러스터에 Google이 관리·지원하는 Knative Serving을 설치
  • Cloud Run과 별개 제품. 콘솔에서도 따로 관리
  • GKE Enterprise 플릿과 Cloud Service Mesh 기반. Google Cloud 밖 GKE 클러스터도 대상
항목GKE용 Knative serving
설치플릿에서 Knative serving 기능을 켜고, 클러스터마다 CloudRun 커스텀 리소스(operator.run.cloud.google.com)를 배포
사전 조건GKE 클러스터를 먼저 만들어 둬야 함. 권장 메시인 Cloud Service Mesh는 vCPU 4개 이상 머신 타입을 요구
범위Serving 중심. 예전의 "Events for Knative serving"은 폐기되어 Eventarc로 대체
버전 확인kubectl get all -n knative-serving -o 'go-template={{index .metadata.labels "serving.knative.dev/release"}}'
GKE Standard에 업스트림을 직접 깔아도 된다

Google 관리형 Knative serving은 플릿·메시 구성이 전제라 무겁게 느껴질 수 있습니다. Eventing이나 최신 업스트림 기능이 필요하다면 GKE Standard 클러스터에 Knative Operator로 직접 설치하는 선택지도 있습니다. 이때 지원 책임은 MSP에 있습니다.

6 / 16

IBM Cloud Code Engine

IBM은 Knative 창립 멤버 중 하나이고, Code Engine은 그 경험을 완전 관리형으로 만든 서비스입니다. 내부는 Kubernetes, Knative, Istio, Tekton 같은 오픈소스로 구성되지만 사용자는 클러스터를 보지 않고 "프로젝트" 안에 애플리케이션, 배치 작업, 함수를 올립니다.

제공 단위

애플리케이션(HTTP, 0개 축소), 작업(배치), 함수, 그리고 소스에서 이미지를 만드는 빌드를 한곳에서 다룹니다.

확장

Knative처럼 동시 요청 수 기준으로 늘리고 요청이 없으면 0개로 줄입니다. 3편의 개념이 그대로 적용됩니다.

이벤트

IBM Cloud 서비스(객체 저장소 등)의 이벤트 구독으로 앱이나 작업을 깨웁니다. Knative Eventing 리소스를 직접 다루는 방식은 아닙니다.

MSP 관점

운영 부담은 가장 적지만 IBM Cloud에 묶입니다. 고객사가 IBM Cloud를 주력으로 쓴다면 자체 Knative 운영보다 Code Engine이 합리적일 수 있습니다.

7 / 16

Alibaba Cloud Knative (ACK · ACS)

Alibaba Cloud는 ACK(관리형 쿠버네티스)와 ACS(컨테이너 컴퓨트 서비스)에 Knative를 애드온으로 제공합니다. Serving 컴포넌트를 Alibaba Cloud가 관리해 주며, Eventing과 Functions도 구성요소로 안내합니다. 릴리스 노트는 각 버전이 호환되는 커뮤니티 Knative 버전과 필요한 쿠버네티스 버전을 함께 명시합니다(예: 커뮤니티 1.16.3 호환 버전은 클러스터 1.30 이상, 최신 계열은 1.31 이상).

클라우드 연동

Kourier 외에 Alibaba Cloud의 게이트웨이 제품과 연동하는 선택지를 제공합니다. 로드밸런서, 인증서, 모니터링이 클라우드 서비스와 묶입니다.

콜드 스타트 완화

저사양 예약 인스턴스나 워밍업 풀처럼 3편의 콜드 스타트 문제를 완화하는 부가 기능을 제공합니다. 정확한 기능명과 지원 버전은 릴리스 노트에서 확인하세요.

버전 추적

커뮤니티 버전 대비 몇 버전 뒤를 따라가며, 업그레이드는 애드온 버전 단위입니다. 클러스터 쿠버네티스 버전 요구 조건을 먼저 맞춰야 합니다.

MSP 관점

중국·아시아 리전에 진출한 고객사에서 만나게 됩니다. 문서가 여러 언어로 제공되지만 언어별 갱신 시점이 다를 수 있어, 버전 정보는 최신 날짜의 문서를 기준으로 삼으세요.

8 / 16

VMware Tanzu

Tanzu Application Platform(TAP)은 Cloud Native Runtimes라는 이름으로 Knative를 포함했습니다. Contour 네트워킹과 함께 TAP의 공급망(빌드·배포 자동화) 끝단에서 앱을 실행하는 역할이었습니다.

Broadcom 인수 이후 Tanzu 포트폴리오는 단계적으로 정리되고 있습니다. Tanzu Platform SaaS는 2025년 5월에 판매·사용이 종료됐고, 같은 시기 1세대 Tanzu Platform SKU들도 판매 종료되어 후속 제품으로 바뀌었습니다. 남은 제품군은 Cloud Foundry 계열 프라이빗 PaaS와 AI 워크로드 쪽으로 재편되는 흐름입니다.

TAP 기반 고객사라면

Cloud Native Runtimes 위에서 돌던 워크로드는 결국 Knative Service이므로, ksvc YAML 자체는 다른 Knative 플랫폼(업스트림, OpenShift Serverless 등)으로 옮기기 쉽습니다. 어려운 부분은 TAP 공급망, Contour 의존 설정, 인증서 구성입니다. 계약 갱신 시점 전에 이전 계획을 세우고, 1~8편의 표준 Knative 방식으로 옮기는 것을 권합니다.

관리형이 없는 곳: EKS · AKS · 국내 CSP · 온프레미스

AWS EKS와 Azure AKS에는 Knative 관리형 애드온이 없습니다. 국내 CSP의 관리형 쿠버네티스나 온프레미스 클러스터도 마찬가지로 업스트림을 직접 설치합니다. 이때 플랫폼마다 챙길 연결 고리가 있습니다.

관리형 Knative가 없는 플랫폼에서는 "검증된 Knative 설치·운영 패키지"가 그 자체로 서비스 상품이 됩니다. Operator 설정, 네트워킹·인증서·DNS 연동, 모니터링(10편)을 표준화해 두면 여러 고객사에 반복 적용할 수 있습니다.

10 / 16

버전 시차와 기능 확인기

강의에서 배운 기능이 고객사 플랫폼에 있을지 확인해 보세요. 플랫폼의 내부 Knative 버전과 기능이 도입된 업스트림 버전을 비교합니다. 벤더가 별도로 백포트하거나 다르게 제공하는 경우가 있으므로, 결과는 "확인이 필요한 출발점"으로 쓰세요.

"Knative 호환"의 진짜 의미

벤더 자료에 "Knative 호환"이라는 표현이 나오면 어디까지 호환인지 따져 봐야 합니다. 같은 말이 전혀 다른 수준을 가리킬 수 있습니다.

수준뜻예
업스트림 그대로커뮤니티 릴리스를 그대로 설치. 모든 리소스와 설정이 같음Knative Operator로 직접 설치
검증된 배포판업스트림 코드에 패치·통합을 더함. 리소스 형식은 같고 버전은 뒤처짐OpenShift Serverless, ACK Knative
API 형식 호환Knative Service 같은 리소스 형식을 받아들이지만 내부 구현은 다름. 일부 필드·어노테이션 미지원 가능Cloud Run

이식성 시험법

고객사에 "나중에 플랫폼을 바꿔도 된다"고 말하려면, 실제 서비스 YAML 한 벌을 두 플랫폼에 올려 보세요. 오토스케일링 어노테이션, 트래픽 분할, 도메인 설정, 이벤트 연결 중 어디서 손을 대야 하는지가 곧 진짜 전환 비용입니다. Eventing은 플랫폼 간 차이가 가장 큰 영역입니다.

실습: Operator로 업스트림 설치

퀵스타트 대신, 실제 고객사 클러스터에서 쓰는 방식인 Knative Operator로 설치합니다. kind 클러스터나 테스트용 관리형 클러스터에서 진행하세요. 설치 경로와 지원 버전은 설치 시점의 공식 문서로 확인하세요.

  1. Operator 설치

    bash
    kubectl apply -f https://github.com/knative/operator/releases/download/knative-v1.23.0/operator.yaml
kubectl get deployment knative-operator -n default

  2. KnativeServing 선언: 설정은 spec.config에

    bash
    kubectl create namespace knative-serving
cat <<'EOF' | kubectl apply -f -
apiVersion: operator.knative.dev/v1beta1
kind: KnativeServing
metadata:
  name: knative-serving
  namespace: knative-serving
spec:
  version: "1.23"
  ingress:
    kourier:
      enabled: true
  config:
    network:
      ingress-class: "kourier.ingress.networking.knative.dev"
    domain:
      "apps.mycorp.test": ""
    autoscaler:
      max-scale-limit: "50"
    features:
      secure-pod-defaults: "AllowRootBounded"
EOF
kubectl get knativeserving -n knative-serving -w

  3. Operator가 ConfigMap을 관리하는지 확인

    ConfigMap을 직접 고친 뒤 잠시 기다리면 Operator가 spec.config의 값으로 되돌리는 것을 볼 수 있습니다. 2편에서 말한 함정을 직접 확인하는 단계입니다.

    bash
    kubectl get cm config-autoscaler -n knative-serving -o jsonpath='{.data.max-scale-limit}'; echo
kubectl patch cm config-autoscaler -n knative-serving --type merge -p '{"data":{"max-scale-limit":"999"}}'
sleep 30
kubectl get cm config-autoscaler -n knative-serving -o jsonpath='{.data.max-scale-limit}'; echo

  4. KnativeEventing 선언

    bash
    kubectl create namespace knative-eventing
cat <<'EOF' | kubectl apply -f -
apiVersion: operator.knative.dev/v1beta1
kind: KnativeEventing
metadata:
  name: knative-eventing
  namespace: knative-eventing
spec:
  version: "1.23"
EOF
kubectl get knativeeventing -n knative-eventing

  5. 어느 플랫폼에서든 버전 확인하는 법

    bash
    # 공통: 실제 설치된 Knative 릴리스 라벨
kubectl get deploy -n knative-serving \
  -o custom-columns=NAME:.metadata.name,RELEASE:.metadata.labels.app\\.kubernetes\\.io/version

# Operator 리소스가 있다면
kubectl get knativeserving,knativeeventing -A

# OpenShift Serverless: 설치된 Operator 버전
oc get csv -n openshift-serverless

    라벨 이름은 설치 방식과 버전에 따라 다를 수 있습니다. 결과가 비면 kubectl get deploy controller -n knative-serving -o yaml | grep -i version으로 찾아보세요.

정리와 다음 편

  1. Knative는 업스트림 직접 설치, 벤더 배포판, Knative 기반 완전 관리형, API 호환 관리형 네 형태로 만납니다.
  2. OpenShift Serverless 1.37은 Knative 1.17 기반으로, 업스트림과 여러 버전 차이가 납니다.
  3. Google은 완전 관리형 Cloud Run과 GKE용 Knative serving이 별개 제품이며, 후자는 Serving 중심입니다.
  4. IBM Code Engine은 Knative 기반 완전 관리형, Alibaba는 커뮤니티 호환 버전을 명시한 관리형 애드온입니다.
  5. Tanzu는 포트폴리오가 정리되는 중이라 Cloud Native Runtimes 사용 고객은 이전 계획이 필요합니다.
  6. EKS·AKS·국내 CSP·온프레미스는 업스트림 직접 설치이며, LB·DNS·인증서·레지스트리 연동이 핵심입니다.
  7. Operator로 설치했다면 설정은 spec.config에. "Knative 호환"은 수준을 따져 보세요.

다음 편(완결): 설치·운영 실전, MSP 관점

Operator와 YAML 설치의 운영 차이, 분기 릴리스에 맞춘 업그레이드 전략, OpenTelemetry 기반 관측성, 자주 만나는 장애의 트러블슈팅 플레이북, 멀티테넌시 설계, 그리고 고객사 도입 체크리스트로 시리즈를 마무리합니다.

Knative 강의 시리즈 9편. 2026년 10월 초 기준 공개 문서(Red Hat OpenShift Serverless 1.37 릴리스 노트, Google Cloud Knative serving 문서, IBM Cloud Code Engine 소개, Alibaba Cloud Knative 릴리스 노트, Broadcom 지식 문서)를 바탕으로 정리했습니다. 벤더 제품의 버전과 지원 상태는 빠르게 바뀌므로 사용 전 각 벤더의 최신 문서를 확인하세요.
