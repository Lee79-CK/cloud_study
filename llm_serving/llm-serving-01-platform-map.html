01시작하기 전에

이번 편이 시리즈 전체에서 맡는 역할과, 다 읽고 나면 할 수 있어야 하는 것들.

이 시리즈는 26편으로 LLM 서빙 플랫폼의 개념 → 서빙 엔진 → 설계·구축 → 튜닝 → 모니터링 → 운영·MSP 전략을 차례로 다룹니다. 1편은 나머지 25편이 붙을 “벽에 거는 지도”입니다. 세부 기술은 얕게 훑고, 대신 어떤 문제가 어느 층에서 생기고 어느 편에서 풀리는지를 연결하는 데 집중합니다.

학습 목표

  1. 모델 학습(training)과 추론(inference)이 자원·비용·운영 측면에서 어떻게 다른지 설명할 수 있다.
  2. “모델 하나 띄우기”와 “서빙 플랫폼”의 차이를 플랫폼이 답해야 하는 질문 목록으로 설명할 수 있다.
  3. 서빙 플랫폼의 7계층과 각 층의 대표 기술, 계층을 가로지르는 관심사(보안·비용·용량)를 그릴 수 있다.
  4. 요청 하나가 클라이언트에서 GPU까지 갔다 돌아오는 경로와, 각 구간에서 생기는 지연·장애를 짚을 수 있다.
  5. 셀프호스팅·상용 API(Claude·OpenAI·Gemini)·하이브리드 중 어떤 구성이 맞는지 판단 기준을 세우고 대략의 손익분기를 계산할 수 있다.
  6. 자신의 실습 환경(또는 고객사 환경)을 7계층 지도 위에 올려 비어 있는 층을 찾을 수 있다.

미리 알고 있으면 좋은 것

Kubernetes의 Pod·Deployment·Service 개념, 컨테이너 이미지, REST API 호출(curl), 간단한 Python. 몰라도 읽을 수는 있지만 12장 실습이 조금 버겁게 느껴질 수 있습니다. 신경망이나 트랜스포머 수식은 필요 없습니다. 필요한 만큼은 2편에서 플랫폼 엔지니어 눈높이로 다시 설명합니다.

이 편 전체를 관통하는 비유: 레스토랑

모델 학습은 요리사를 몇 달간 훈련시키는 일이고, 추론은 그 요리사가 매일 손님 주문을 받아 요리를 내는 영업입니다. 서빙 엔진은 주방 그 자체(화구·조리 순서·동시에 몇 접시를 굽는지), 서빙 플랫폼은 주방을 포함한 식당 전체 — 예약 시스템, 홀 매니저, 재료 창고, 위생 점검, 매출 정산까지입니다. 맛있는 요리 한 접시를 만드는 것과 식당을 운영하는 것은 다른 기술입니다.

02학습과 추론은 다른 세계

같은 GPU를 쓰지만 목적도, 자원 패턴도, 장애의 의미도 완전히 다릅니다.

많은 인프라 엔지니어가 처음 AI 플랫폼을 맡을 때 “GPU 클러스터를 운영한다”는 하나의 일로 생각합니다. 하지만 학습 클러스터와 추론 플랫폼은 마치 배치 데이터 웨어하우스와 온라인 결제 시스템만큼 성격이 다릅니다.

왜 추론이 엔지니어의 주 무대가 되었나

대부분의 조직은 거대 모델을 직접 학습하지 않습니다. 공개된 오픈 웨이트 모델(Qwen, Llama, DeepSeek, Gemma, gpt-oss 계열 등)을 가져오거나 상용 API를 씁니다. 학습은 소수의 연구 조직이 하지만, 추론은 모델을 쓰는 모든 조직이 매일 합니다. 그래서 “GPU를 잘 굴려 토큰을 싸고 빠르고 안정적으로 내놓는 일”이 클라우드·MSP 엔지니어의 새로운 핵심 업무가 되었습니다.

추론 한 번은 실제로 무슨 일을 하나

2편에서 깊게 다룰 내용을 미리 요약하면, LLM은 다음 토큰 하나를 예측하는 일을 반복하는 기계입니다. 이 반복은 성격이 다른 두 단계로 나뉩니다.

  1. 토큰화(Tokenize) — 입력 문장을 모델이 아는 정수 토큰열로 바꿉니다. 한국어는 영어보다 같은 의미에 토큰이 더 많이 드는 경우가 흔합니다.
  2. Prefill — 입력 토큰 전체를 한꺼번에 GPU에 넣어 계산하고, 그 결과를 KV 캐시에 저장합니다. 입력이 길수록 오래 걸리고, 연산(FLOPS)을 많이 씁니다. 사용자가 느끼는 “첫 글자가 나오기까지의 시간(TTFT)”은 주로 여기서 결정됩니다.
  3. Decode — 토큰을 하나씩 생성합니다. 토큰 하나를 만들 때마다 모델 가중치 전체와 KV 캐시를 메모리에서 읽어야 해서 메모리 대역폭이 병목입니다. 토큰과 토큰 사이 간격(TPOT/ITL)이 여기서 결정됩니다.
  4. 디토큰화·스트리밍 — 생성된 토큰을 글자로 바꿔 SSE(Server-Sent Events) 등으로 클라이언트에 흘려보냅니다.

03모델 하나 띄우기 vs 플랫폼

첫날의 명령어 한 줄이 30일 뒤 어떤 질문들로 돌아오는지 따라가 봅니다.

1일차: 놀랍도록 쉽다

요즘 서빙 엔진은 정말 잘 만들어져 있습니다. GPU가 붙은 서버에서 아래 한 줄이면 OpenAI 호환 API 서버가 뜨고, 기존 OpenAI SDK 코드를 주소만 바꿔 그대로 쓸 수 있습니다.

bash · 단일 서버에서 모델 띄우기
vllm serve Qwen/Qwen3-8B --port 8000

# 다른 터미널에서
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen3-8B","messages":[{"role":"user","content":"안녕?"}]}'

데모는 성공했고, 팀장님도 만족했습니다. 문제는 여기서부터입니다.

플랫폼의 정의 (이 시리즈에서 쓰는 뜻)

LLM 서빙 플랫폼은 여러 모델을 여러 소비자에게, 정해진 품질(SLO)과 비용 안에서, 셀프서비스로 제공하는 공통 기반입니다. 핵심 단어는 다섯 개입니다: 여러 모델(수명주기 관리), 여러 소비자(멀티테넌시), SLO(측정 가능한 약속), 비용(계측과 배분), 셀프서비스(사람이 병목이 되지 않음).

성숙도 자가 진단

지금 운영 중이거나 고객사에서 본 환경을 떠올리며 해당하는 항목에 체크해 보세요. 성숙도 단계가 아래에 표시됩니다.

0단계 · 실험개인 서버에서 손으로 띄운 모델
1단계 · 컨테이너화재현 가능한 배포, 아직 수동 운영
2단계 · 관측되는 서비스지표와 단일 진입점이 생김
3단계 · 플랫폼자동 확장, 비용 배분, SLO
4단계 · 하이브리드 플랫폼정책 기반 라우팅과 안전한 모델 수명주기
항목을 체크하면 현재 단계와 다음 단계로 가기 위해 볼 편을 알려 드립니다.

04플랫폼 7계층 해부

아래에서 위로 쌓이는 7개 층과, 모든 층을 세로로 관통하는 관심사들.

네트워크를 OSI 7계층으로 나눠 보면 장애 위치를 빨리 찾을 수 있듯이, 서빙 플랫폼도 층으로 나눠 보면 “이 문제는 어디서 풀어야 하는가”가 명확해집니다. 아래 구분은 표준 규격이 아니라 이 시리즈가 쓰는 정리 틀입니다. 제품에 따라 두 층을 한 번에 담당하기도 합니다(예: llm-d는 프레임워크와 라우팅 층에 걸쳐 있음).

각 층을 펼치면 역할 · 대표 기술 · 이 층이 답하는 질문 · 흔한 실수 · 다루는 편이 나옵니다.

L1하드웨어와 인프라GPU, 메모리, 인터커넥트, 네트워크, 스토리지, 전력·냉각›

모든 것의 바닥입니다. LLM 서빙에서 하드웨어를 고를 때 가장 중요한 숫자는 GPU 연산 성능(TFLOPS)보다 GPU 메모리 용량(모델과 KV 캐시가 들어가는가)과 메모리 대역폭(Decode 속도의 상한)인 경우가 많습니다.

대표 구성 요소
  • GPU: NVIDIA L4 · A100 · H100 · H200 · B200, 개발용 GB10(DGX Spark 계열), AMD Instinct, Google TPU 등
  • GPU 간 연결: NVLink/NVSwitch(노드 내), InfiniBand·RoCE(노드 간)
  • 모델 저장소: NVMe 로컬 디스크, NFS/병렬 파일시스템, S3 호환 오브젝트 스토리지
  • 전력·냉각: B200급은 GPU당 1kW 안팎, 랙 전력 설계가 병목이 되기도 함
이 층이 답하는 질문
  • 이 모델이 몇 장의 GPU에 들어가는가?
  • 여러 GPU를 묶을 때 통신이 병목이 되지 않는가?
  • 수십 GB 가중치를 얼마나 빨리 읽어 올 수 있는가?
흔한 실수
  • 연산 성능만 보고 GPU를 고른 뒤 메모리 부족으로 모델이 안 들어감
  • 노드 간 텐서 병렬을 일반 이더넷 위에서 시도함

다루는 편: 3편(하드웨어 지형), 17편(분산 서빙과 네트워크), 이번 편 7장(미리보기)

L2클러스터와 GPU 스케줄링Kubernetes, GPU Operator, Device Plugin·DRA, MIG·시분할, Kueue, LeaderWorkerSet›

비싼 GPU를 누구에게, 얼마나, 어떤 순서로 나눠 줄지 정하는 층입니다. 오늘날 대부분의 서빙 플랫폼은 Kubernetes를 기반으로 하며, GPU는 일반 CPU·메모리와 달리 쪼개 쓰기 어렵고 하나하나가 비싸기 때문에 스케줄링 정책이 비용을 좌우합니다.

대표 기술
  • NVIDIA GPU Operator: 드라이버, 컨테이너 툴킷, Device Plugin, DCGM Exporter, GPU Feature Discovery를 한 번에 설치·관리
  • Device Plugin → DRA: “GPU 1개”를 정수로 요청하던 방식에서 속성(메모리, 모델, MIG 프로파일)으로 요청하는 Dynamic Resource Allocation으로 이동 중
  • GPU 공유: MIG(하드웨어 분할), Time-slicing(시분할), MPS(프로세스 공유)
  • Kueue: 배치·학습 작업과 서빙의 대기열·쿼터 관리
  • LeaderWorkerSet(LWS): 여러 노드에 걸친 한 모델 인스턴스를 하나의 단위로 관리
이 층이 답하는 질문
  • 서빙 Pod가 올바른 GPU 노드에 뜨는가?
  • 작은 모델 여러 개가 GPU 한 장을 나눠 쓸 수 있는가?
  • 학습 작업이 서빙 GPU를 빼앗지 않는가?
흔한 실수
  • 시분할로 GPU를 공유하면서 메모리 격리가 안 된다는 사실을 잊음 (한 Pod의 OOM이 이웃을 죽임)
  • GPU 노드에 일반 워크로드가 올라가 GPU가 놀고 있음 (taint/toleration 누락)

다루는 편: 7편(실습 랩), 8편(Kubernetes 위의 GPU 플랫폼), 17편(멀티노드)

L3서빙 엔진vLLM, SGLang, TensorRT-LLM, llama.cpp·Ollama 등›

GPU 위에서 실제로 모델을 실행하는 프로그램입니다. 레스토랑 비유로는 주방입니다. 여러 요청을 묶어 한꺼번에 계산하는 연속 배칭, KV 캐시를 블록 단위로 관리하는 PagedAttention, 같은 앞부분을 재사용하는 프리픽스 캐싱, 양자화 커널, 추측 디코딩 등 성능의 대부분이 이 층에서 나옵니다.

대표 엔진
  • vLLM: 사실상의 표준 오픈소스 엔진. PyTorch Foundation 호스팅 프로젝트. 가장 넓은 모델·하드웨어 지원, OpenAI 호환 서버 내장
  • SGLang: RadixAttention 기반 프리픽스 재사용과 빠른 스케줄러로 에이전트·멀티턴 워크로드에 강함
  • TensorRT-LLM: NVIDIA의 최적화 엔진. 최신 NVIDIA GPU에서 최고 성능을 노릴 때
  • llama.cpp · Ollama: CPU·노트북·엣지용 경량 실행. 프로덕션 멀티테넌트보다는 개발·개인용
이 층이 답하는 질문
  • GPU 한 장으로 초당 몇 토큰을 낼 수 있는가?
  • 동시에 몇 요청까지 받아도 지연이 견딜 만한가?
  • 이 모델 아키텍처·양자화 형식을 지원하는가?
흔한 실수
  • 기본값 그대로 운영 (최대 컨텍스트 길이, 메모리 활용률 등이 워크로드와 안 맞음)
  • 엔진 버전을 고정하지 않아 재배포 때 동작이 바뀜

다루는 편: 4편(vLLM 해부), 5편(엔진 비교), 6편(양자화·포맷), 14~16편(튜닝)

L4서빙 프레임워크 (오케스트레이션)KServe, llm-d, NVIDIA Dynamo, Ray Serve, 직접 Deployment›

엔진은 “한 프로세스”입니다. 프레임워크는 그 프로세스를 여러 개 띄우고, 모델을 가져오고, 버전을 바꾸고, 늘리고 줄이는 일을 Kubernetes 리소스로 선언하게 해 줍니다. 레스토랑으로 치면 여러 주방(지점)을 열고 닫는 본사 운영팀입니다.

대표 기술
  • KServe: InferenceService CRD로 모델 서빙을 선언. LLM 전용 리소스(LLMInferenceService)로 llm-d와 통합
  • llm-d: vLLM 레플리카 무리를 클러스터 단위로 조율. 캐시 인지 라우팅, Prefill/Decode 분리, 분산 KV 캐시, 멀티노드 전문가 병렬. 2026년 3월 CNCF Sandbox 합류
  • NVIDIA Dynamo: NVIDIA의 분산 추론 프레임워크. P/D 분리와 KV 캐시 전송 최적화
  • Ray Serve: Python 중심의 범용 서빙, 복합 파이프라인에 강함
  • 직접 Deployment + Service: 모델이 한두 개면 충분히 합리적인 출발점
이 층이 답하는 질문
  • 새 모델 버전을 무중단으로 교체할 수 있는가?
  • 모델 가중치를 어디서 어떻게 가져오는가?
  • 레플리카 수를 무엇을 기준으로 바꾸는가?
흔한 실수
  • 모델이 하나뿐인데 가장 무거운 프레임워크부터 도입해 운영 부담만 커짐
  • CPU 사용률 기반 HPA를 그대로 씀 (LLM 부하를 반영하지 못함)

다루는 편: 9편(프레임워크 선택), 10편(llm-d 해부), 13편(모델 로딩), 18편(오토스케일링)

L5라우팅과 게이트웨이Gateway API Inference Extension, Endpoint Picker, AI 게이트웨이(LiteLLM, Envoy AI Gateway 등)›

요청이 들어오는 정문입니다. 두 가지 다른 일을 합니다. 하나는 정책(누가 들어올 수 있나, 얼마나 쓸 수 있나, 어느 모델·프로바이더로 보낼까), 다른 하나는 지능형 부하 분산(같은 모델의 여러 레플리카 중 어디로 보내야 가장 빠른가)입니다.

대표 기술
  • Gateway API Inference Extension(GAIE): Kubernetes Gateway API에 추론 전용 리소스(InferencePool 등)를 더한 표준. Endpoint Picker(EPP)가 큐 길이·KV 캐시 상태·LoRA 어댑터를 보고 Pod를 고름
  • AI 게이트웨이: LiteLLM, Envoy AI Gateway, Kong AI Gateway 등. 셀프호스팅 모델과 Claude·OpenAI·Gemini API를 하나의 OpenAI 호환 엔드포인트로 묶고 키·쿼터·폴백·사용량 계측

일반 L7 로드밸런서는 요청 하나하나의 무게(입력 길이, 캐시 적중 여부)를 모릅니다. 라운드로빈으로 나누면 한 Pod에 긴 요청이 몰리고 캐시도 깨집니다. 이것이 “추론 인지” 라우팅이 따로 필요한 이유입니다.

이 층이 답하는 질문
  • 이 요청은 어떤 모델·어떤 프로바이더로 가야 하는가?
  • 이 테넌트는 아직 쿼터가 남아 있는가?
  • 셀프호스팅이 과부하일 때 어디로 넘길 것인가?
흔한 실수
  • 스트리밍 응답인데 게이트웨이 타임아웃을 일반 API처럼 30초로 둠
  • 팀마다 상용 API 키를 직접 발급해 사용량·비용 추적이 불가능해짐

다루는 편: 11편(Inference Gateway), 12편(AI 게이트웨이), 24편(보안·멀티테넌시)

L6관측과 거버넌스DCGM Exporter, 엔진 메트릭, OpenTelemetry GenAI, Prometheus·Grafana·Loki·Tempo, 가드레일, 감사›

플랫폼이 약속을 지키고 있는지 보여 주는 층입니다. LLM 서빙의 관측은 일반 웹 서비스보다 한 겹이 더 있습니다. 시스템이 빠르고 살아 있는지(성능·가용성)뿐 아니라 답변이 쓸 만한지(품질·안전)와 얼마가 드는지(토큰·비용)까지 봐야 합니다.

성능·가용성
  • GPU: DCGM Exporter (사용률, 메모리, 전력, XID 에러)
  • 엔진: vLLM·SGLang 메트릭 (TTFT, TPOT, 큐 대기, KV 사용률, 캐시 적중)
  • 요청 추적: OpenTelemetry 트레이스, GenAI 시맨틱 컨벤션
품질·안전
  • 입출력 가드레일 (PII, 프롬프트 인젝션, 유해 콘텐츠)
  • 샘플링 평가, 모델 교체 시 회귀 테스트
  • 감사 로그 (누가 어떤 데이터로 무엇을 물었나)
비용
  • 테넌트·모델별 입력/출력 토큰
  • GPU 시간 → 토큰당 비용 환산
  • 예산 알림, 차지백 리포트

흔한 실수: 프롬프트 전문을 그대로 로그로 남겨 개인정보·비용 문제를 만듦 / GPU 사용률 하나로 용량을 판단함

다루는 편: 20편(GPU 관측), 21편(메트릭·로그·트레이스), 22편(품질·안전), 23편(SLO·비용)

05요청 하나의 여정

클라이언트가 보낸 질문 하나가 GPU까지 내려갔다가 토큰이 되어 돌아오는 7단계.

장애 대응의 절반은 “어디서 느려졌나, 어디서 끊겼나”를 찾는 일입니다. 아래 단계를 하나씩 눌러 각 구간이 하는 일과 실제 현장에서 자주 깨지는 지점을 확인하세요. 오른쪽 패널의 지연 예산은 상황(시나리오)에 따라 바뀝니다.

    단계를 선택하세요

    이 예산에서 꼭 기억할 것
    • 짧은 챗에서도 전체 시간의 대부분은 Decode입니다. 출력이 길수록 TPOT가 체감 속도를 좌우합니다.

    민감도 기반

    폴백 (Failover)

    셀프호스팅이 과부하이거나 장애일 때 상용 API로 넘김. 반대로 API 장애·레이트 리밋 때 로컬로 넘기기도 합니다. 데이터 등급 정책과 충돌하지 않게 설계해야 합니다.

    버스트 오프로드

    평상시 부하는 보유 GPU로, 예측 못 한 폭주분만 API나 GPU 클라우드로. GPU를 피크에 맞춰 사지 않아도 됩니다.

    지금 업계가 움직이는 여섯 방향

    1. 분리 서빙(Disaggregated Serving): 성격이 다른 Prefill과 Decode를 서로 다른 GPU 무리에 맡겨 각각 최적화합니다. 대규모 서비스에서 표준 패턴이 되어 가고 있습니다(10편).
    2. KV 캐시가 하나의 저장 계층으로: GPU 메모리에만 두던 KV 캐시를 CPU 메모리·로컬 SSD로 내리고, 클러스터 전체에서 어느 레플리카가 어떤 캐시를 가졌는지 추적해 라우팅합니다(15편).
    3. Kubernetes 네이티브 추론 API: 추론을 일반 웹 트래픽이 아닌 별도 워크로드로 다루는 표준(GAIE, LWS, DRA)이 정착 중입니다(8·11편).
    4. 저정밀 연산의 일상화: FP8은 기본 선택지가 되었고, Blackwell 세대에서는 FP4 계열이 실전에 쓰입니다(6편).
    5. MoE와 대형 공개 모델: 전체 파라미터는 크지만 토큰당 일부만 계산하는 MoE 모델이 많아져 전문가 병렬(EP)과 멀티노드 서빙이 중요해졌습니다(17편).
    6. 에이전트 워크로드: 사람이 아니라 프로그램이 LLM을 연속 호출합니다. 요청 수가 폭증하고 앞부분 재사용률이 높아져 캐시·라우팅·작업 단위 관측의 중요성이 커졌습니다(15·21편).

    """한 가지 프롬프트를 여러 엔드포인트에 스트리밍으로 보내 TTFT·TPOT·전체 시간을 잰다."""
import os, time, statistics
from openai import OpenAI

PROMPT = "쿠버네티스에서 여러 팀이 GPU를 나눠 쓸 때 고려할 점을 다섯 문장으로 설명해 줘."
RUNS = 3

TARGETS = {
    "local-vllm": dict(base_url="http://localhost:8000/v1", api_key="EMPTY",
                       model="Qwen/Qwen3-0.6B",
                       extra={"chat_template_kwargs": {"enable_thinking": False}}),
    "claude": dict(base_url="https://api.anthropic.com/v1/",
                   api_key=os.getenv("ANTHROPIC_API_KEY"), model=os.getenv("CLAUDE_MODEL")),
    "openai": dict(base_url="https://api.openai.com/v1",
                   api_key=os.getenv("OPENAI_API_KEY"), model=os.getenv("OPENAI_MODEL")),
    "gemini": dict(base_url="https://generativelanguage.googleapis.com/v1beta/openai/",
                   api_key=os.getenv("GEMINI_API_KEY"), model=os.getenv("GEMINI_MODEL")),
}

def one_run(client, cfg):
    kwargs = dict(model=cfg["model"], max_tokens=300, stream=True,
                  messages=[{"role": "user", "content": PROMPT}])
    if cfg.get("extra"):
        kwargs["extra_body"] = cfg["extra"]
    t0 = time.perf_counter()
    try:  # 사용량(토큰 수)을 스트림 끝에 받아 오기. 지원하지 않는 곳이면 옵션 없이 재시도
        stream = client.chat.completions.create(stream_options={"include_usage": True}, **kwargs)
    except Exception:
        t0 = time.perf_counter()
        stream = client.chat.completions.create(**kwargs)
    first = last = None
    chunks, usage = 0, None
    for ev in stream:
        if getattr(ev, "usage", None):
            usage = ev.usage
        if not ev.choices:
            continue
        d = ev.choices[0].delta
        text = (d.content or "") if d else ""
        text += (getattr(d, "reasoning_content", None) or getattr(d, "reasoning", None) or "") if d else ""
        if text:
            now = time.perf_counter()
            first = first or now
            last = now
            chunks += 1
    end = time.perf_counter()
    n_out = usage.completion_tokens if usage and usage.completion_tokens else chunks
    ttft = (first - t0) if first else float("nan")
    tpot = ((last - first) / (n_out - 1)) if first and n_out > 1 else float("nan")
    return ttft, tpot, end - t0, n_out

def main():
    print(f"{'대상':<12}{'TTFT(s)':>10}{'TPOT(ms)':>10}{'전체(s)':>10}{'출력토큰':>10}")
    for name, cfg in TARGETS.items():
        if not cfg["api_key"] or not cfg["model"]:
            print(f"{name:<12}  건너뜀: API 키 또는 모델 이름이 없음")
            continue
        client = OpenAI(base_url=cfg["base_url"], api_key=cfg["api_key"], timeout=120)
        try:
            runs = [one_run(client, cfg) for _ in range(RUNS)]
        except Exception as e:
            print(f"{name:<12}  실패: {e}")
            continue
        med = lambda i: statistics.median(r[i] for r in runs)
        print(f"{name:<12}{med(0):>10.3f}{med(1)*1000:>10.1f}{med(2):>10.2f}{int(med(3)):>10}")

if __name__ == "__main__":
    main()

    2. 세 번 반복한 값이 얼마나 흔들리나요? 한 번 잰 숫자로 결론을 내리면 안 되는 이유가 19편 벤치마크 랩의 주제입니다.
    3. 코드에서 바뀐 것은 base_url과 model뿐입니다. 이 점이 AI 게이트웨이(12편)를 가능하게 만드는 동시에, 게이트웨이 없이 두면 키와 사용량이 팀마다 흩어지는 이유이기도 합니다.

    5. 셀프호스팅·매니지드·상용 API·하이브리드 중 선택은 데이터 통제, 품질 요구, 사용량, 운영 역량으로 정하고, 숫자로 손익분기를 확인한다.
