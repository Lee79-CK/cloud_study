2편에서는 코드를 그대로 따라 쳤습니다. 이번 편은 그 코드를 한 글자씩 읽을 수 있게 만드는 편입니다. 블록이 무엇으로 이루어지는지, Terraform이 그것을 어떻게 그래프로 바꾸고 어떤 순서로 API를 호출하는지, plan 출력의 기호 하나하나가 무슨 뜻인지 익힌 뒤, 비용 0원 docker 실습과 AWS S3·EC2 실습으로 직접 확인합니다.

이번 편의 목표와 실습 지도

이번 편을 마치면

  • HCL 블록의 구조(블록 타입·라벨·본문·인자·중첩 블록)를 이름으로 가리키며 읽을 수 있습니다.
  • terraform, provider, resource, data, output 블록이 각각 무엇을 하는지, 리소스 주소와 참조 문법을 설명할 수 있습니다.
  • init → plan → apply → destroy 각 단계에서 Terraform 내부와 디스크·클라우드에 무슨 일이 일어나는지 압니다.
  • plan 출력의 + - ~ -/+ +/- <= 기호, forces replacement, (known after apply)를 해석할 수 있습니다.
  • 암시적 의존과 명시적 의존(depends_on)의 차이를 알고, 숨은 의존성을 찾아낼 수 있습니다. 1.16의 terraform graph -format=mermaid로 그래프를 그립니다.
  • AWS에 S3 버킷과 EC2 한 대를 코드로 만들고, 변경 유형별 plan을 관찰한 뒤 지웁니다.

1HCL 문법 해부

Terraform 코드는 전부 “블록”과 “인자” 두 가지로 이루어진다

HCL(HashiCorp Configuration Language)은 사람이 읽고 쓰기 쉬운 설정 언어입니다. 문법 요소는 많지 않습니다. 블록(block)은 무언가를 담는 상자이고, 인자(argument)는 상자 안에 이름 = 값으로 적는 설정입니다. 블록 안에 다른 블록이 들어갈 수도 있습니다(중첩 블록). 아래 코드에서 점선으로 표시된 부분을 눌러 보세요.

# 웹 서버 한 대 — 주석은 #, //, /* */ 세 가지
resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.micro"
  vpc_security_group_ids = [aws_security_group.web.id]

  user_data = <<-EOT
    #!/bin/bash
    echo "bucket=${aws_s3_bucket.site.bucket}" > /tmp/info
  EOT

  root_block_device {
    volume_size = 8
    encrypted   = true
  }

  tags = { Name = "iac-lab-ep03-web" }

  depends_on = [aws_vpc_security_group_egress_rule.all_out]
}

토큰을 눌러 보세요

점선 상자로 표시된 부분마다 HCL 문법에서의 이름과 역할을 설명합니다. 이 열한 가지만 알면 Terraform 코드의 90%를 읽을 수 있습니다.

HCL과 JSON

같은 내용을 main.tf.json처럼 JSON으로도 쓸 수 있습니다. 사람이 쓰기엔 불편하지만, 다른 프로그램이 Terraform 코드를 생성할 때 유용합니다. 반대로 terraform show -json은 plan·state를 JSON으로 내보내, 정책 검사나 비용 추정 도구가 읽을 수 있게 합니다(10·12편).

2참조와 값의 종류

블록끼리는 “주소”로 서로를 가리킨다

Terraform의 모든 블록은 고유한 주소(address)를 가집니다. 다른 블록의 값을 쓰고 싶으면 그 주소에 속성 이름을 붙여 참조합니다. 이 참조가 곧 의존성이 됩니다.

참조 대상문법예다루는 편
관리 리소스<타입>.<이름>.<속성>aws_instance.web.public_ip이번 편
데이터 소스data.<타입>.<이름>.<속성>data.aws_ami.al2023.id이번 편
입력 변수var.<이름>var.instance_type4편
로컬 값local.<이름>local.common_tags4편
모듈 출력module.<이름>.<출력>module.vpc.vpc_id6편
반복 중 위치count.index, each.key, each.value"web-${count.index}"4편
경로·작업공간path.module, path.root, terraform.workspace"${path.module}/files/init.sh"4·8편
자기 자신self.<속성> (프로비저너·postcondition 안에서만)self.private_ip11편

인자(argument)와 속성(attribute)

리소스 문서에는 두 목록이 있습니다. Argument Reference는 여러분이 넣는 값(입력), Attribute Reference는 리소스가 만들어진 뒤 꺼내 쓸 수 있는 값(출력)입니다. ami, instance_type은 인자이고, id, arn, public_ip는 속성입니다. 인자로 넣은 값도 같은 이름의 속성으로 다시 읽을 수 있습니다.

속성 중 상당수는 클라우드가 만들어 주기 전까지 값을 알 수 없습니다. 그래서 plan에는 (known after apply)로 표시됩니다. 이런 값을 다른 리소스가 참조하면, 그 리소스의 해당 인자도 plan 단계에서는 미정으로 남습니다.

값의 종류 (자세한 내용은 4편)

타입예메모
string"t3.micro"숫자처럼 보여도 따옴표가 있으면 문자열
number8, 0.5정수·실수 구분 없음
booltrue, false따옴표 없음
list(...) / tuple["a", "b"]순서 있음, 인덱스 [0]
set(...)보안 그룹 ID 목록 등순서·중복 없음, 인덱스 접근 불가

terraform console로 직접 만져 보기

apply한 디렉터리에서 terraform console을 실행하면 state의 값과 표현식을 대화형으로 평가할 수 있습니다. aws_instance.web.public_ip, upper("hello"), [for s in ["a","b"] : "${s}-1"] 같은 식을 넣어 보세요. 4편에서 표현식을 배울 때 가장 많이 쓰는 도구입니다. exit로 빠져나옵니다.

3terraform 블록과 잠금 파일

이 코드가 무엇으로, 어떤 버전으로 실행되어야 하는지 선언한다

versions.tf
terraform {
  required_version = "~> 1.16.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws" # registry.terraform.io/hashicorp/aws 의 줄임
      version = "~> 6.0"
    }
    random = { source = "hashicorp/random", version = "~> 3.7" }
    http   = { source = "hashicorp/http", version = "~> 3.4" }
  }

  # backend "s3" { ... }   ← state 저장 위치. 5편에서 추가
}

프로바이더 소스 주소

source는 [호스트/]네임스페이스/타입 형식입니다. 호스트를 생략하면 공개 레지스트리 registry.terraform.io입니다. 네임스페이스는 만든 주체이고, 타입은 리소스 이름의 접두사가 됩니다. hashicorp/aws 프로바이더의 리소스는 모두 aws_로 시작하고, kreuzwerker/docker의 리소스는 docker_로 시작합니다. 사내 프라이빗 레지스트리라면 registry.example.com/team/foo처럼 호스트를 씁니다. 레지스트리의 배지도 확인하세요. Official(HashiCorp 관리), Partner(벤더 관리), Community(개인·커뮤니티)로 신뢰 수준과 유지보수 주체가 다릅니다.

버전 제약 연산자

표기의미허용 예쓰는 곳
= 6.10.0 또는 6.10.0정확히 그 버전6.10.0만문제 버전을 피해 핀 고정할 때
!= 6.11.0그 버전 제외버그 있는 버전 회피다른 제약과 함께
>= 6.0이상6.0, 7.3 …재사용 모듈의 최소 요구(6편)
>= 6.0, < 7.0범위6.x 전부명시적 범위
~> 6.0오른쪽 끝 자리만 올라갈 수 있음6.0 이상 7.0 미만루트 코드의 프로바이더
~> 6.10.0패치만6.10.x보수적 고정
~> 1.16.0패치만1.16.xrequired_version
~>의 함정

~> 6.0과 ~> 6.0.0은 다릅니다. 앞의 것은 6.x 전체(마이너 업데이트 허용), 뒤의 것은 6.0.x만 허용합니다. “오른쪽 끝에 적은 자리만 올라갈 수 있다”로 외우세요. 메이저 버전이 바뀌는 업그레이드(예: AWS 프로바이더 5 → 6)는 동작이 바뀌는 변경이 많아 반드시 업그레이드 가이드를 읽고 의도적으로 올립니다.

잠금 파일 .terraform.lock.hcl 들여다보기

# 이 파일은 terraform init이 관리합니다. 직접 수정하지 마세요.
provider "registry.terraform.io/hashicorp/aws" {
  version     = "6.xx.x"          # 실제로 선택된 정확한 버전
  constraints = "~> 6.0"          # 코드에 적힌 제약
  hashes = [
    "h1:AbCd...=",                  # 현재 플랫폼 패키지 내용의 해시
    "zh:0123ab...",                  # 레지스트리가 공개한 플랫폼별 zip 해시
    ...
  ]
}

잠금 파일이 있으면 terraform init은 제약 범위 안에 더 새 버전이 있어도 잠금 파일의 버전을 그대로 설치하고, 내려받은 파일의 해시가 맞는지 검증합니다. 공급망 공격이나 “어제와 다른 프로바이더” 문제를 막는 장치입니다. 의도적으로 올리고 싶을 때만 terraform init -upgrade를 실행하고, 잠금 파일 변경분을 리뷰받아 커밋합니다.

팀원이 다른 OS를 쓴다면

macOS(arm64)에서 init하면 잠금 파일에는 그 플랫폼의 h1: 해시만 들어갈 수 있습니다. 이 파일을 리눅스 CI나 Windows 동료가 쓰면 체크섬 불일치 오류가 납니다. 처음부터 팀이 쓰는 플랫폼을 모두 등록해 두세요.

terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 -platform=windows_amd64

4provider 블록

“어느 클라우드의, 어느 리전에, 어떤 기본값으로” 연결할지

providers.tf
provider "aws" {
  region = "ap-northeast-2"

  default_tags {
    tags = {
      Project   = "iac-lab"
      Episode   = "03"
      Owner     = "hong-gildong"
      ManagedBy = "terraform"
      Expire    = "2026-10-31"
    }
  }
}

provider 블록은 프로바이더 플러그인에 넘겨 줄 연결 설정입니다. 자격증명은 여기에 쓰지 않고 2편에서 설정한 프로필·환경(AWS_PROFILE)에서 읽게 둡니다. provider 블록을 아예 생략하면 모든 설정이 기본값(환경변수 등)으로 채워집니다. 2편의 random·local 프로바이더처럼 설정할 것이 없는 프로바이더는 블록 없이도 동작합니다.

별칭(alias): 같은 프로바이더를 여러 설정으로

한 코드에서 두 리전이나 두 계정을 다뤄야 할 때가 있습니다. 대표적인 예가 CloudFront용 ACM 인증서로, 배포는 서울 리전이어도 인증서는 반드시 us-east-1에 만들어야 합니다.

provider "aws" {                       # 기본 프로바이더 (별칭 없음)
  region = "ap-northeast-2"
}

provider "aws" {
  alias  = "us_east_1"                  # 두 번째 설정
  region = "us-east-1"
}

resource "aws_acm_certificate" "cdn" {
  provider          = aws.us_east_1        # 메타 인자: 어느 설정을 쓸지
  domain_name       = "www.example.com"
  validation_method = "DNS"
}

별칭 없는 블록이 기본이며, provider 인자를 쓰지 않은 리소스는 모두 기본 설정을 씁니다. MSP 현장에서는 “운영 계정 + 공유 서비스 계정”처럼 계정이 다른 경우에도 assume_role과 별칭을 조합합니다(25편).

Azure는 어떻게 다른가

provider "azurerm" {
  features {}           # 필수 블록 (리소스 삭제 시 동작 등 세부 옵션)
  # subscription_id: ARM_SUBSCRIPTION_ID 환경변수 (2편)
}

# 기본 태그 기능도 없어서 태그는 리소스마다 넣는다 (4편에서 locals로 공통화).

5resource 블록

Terraform이 생성·변경·삭제의 전 생애를 책임지는 대상

resource "타입" "이름"에서 타입은 프로바이더가 정한 것(aws_instance)이고, 이름은 여러분이 붙이는 코드 안의 별명(web)입니다. 둘을 합친 aws_instance.web이 리소스 주소이며 state에 이 주소로 기록됩니다. 이름은 클라우드 콘솔에 보이는 이름(Name 태그)과 아무 관계가 없다는 점이 처음에 가장 헷갈리는 부분입니다.

구분예설명
필수 인자aws_vpc_security_group_ingress_rule의 security_group_id, docker_container의 name·image문서에 Required. 빠지면 Missing required argument
선택 인자instance_type, tags문서에 Optional. 생략 시 프로바이더·클라우드 기본값
중첩 블록root_block_device {}, metadata_options {}문서의 별도 소제목으로 설명
계산되는 속성id, arn, public_ipapply 후에만 알 수 있음
메타 인자depends_on, count, for_each, provider, lifecycle어느 리소스 타입에나 쓸 수 있는 Terraform 자체 인자

메타 인자 지도

depends_on

참조로 드러나지 않는 의존을 명시. 이번 편 10장.

provider

별칭 프로바이더 선택. 이번 편 4장.

count / for_each

같은 리소스를 여러 개. 4편.

lifecycle

교체 순서, 삭제 방지, 변경 무시, 사전·사후 조건. 11편.

provisioner / connection

생성 후 명령 실행. 최후의 수단. 11편.

import / moved / removed

별도 블록. 기존 리소스 흡수·이름 변경·관리 중단. 9편.

레지스트리 문서 읽는 법

  1. registry.terraform.io에서 프로바이더를 찾고, 버전 선택 상자를 내 잠금 파일 버전에 맞춥니다. 최신 문서와 내 버전의 인자가 다를 수 있습니다.
  2. Example Usage로 감을 잡고, Argument Reference에서 Required/Optional을 확인합니다.
  3. 인자 설명에 “forces new resource” 또는 그런 뜻의 문구가 있는지 봅니다. 그 인자를 바꾸면 교체(삭제 후 재생성)가 일어납니다.
  4. Attribute Reference에서 다른 리소스가 쓸 수 있는 값을 확인합니다.
  5. 맨 아래 Import 절은 기존 리소스를 가져올 때(9편), Timeouts 절은 오래 걸리는 리소스(RDS 등)에 씁니다.
같은 일을 하는 리소스가 둘일 때

프로바이더가 발전하면서 한 기능을 표현하는 방법이 여러 개가 됩니다. 보안 그룹 규칙을 aws_security_group 안의 ingress {} 블록으로 쓸 수도 있고, 별도 리소스 aws_vpc_security_group_ingress_rule로 쓸 수도 있습니다. 현재 권장은 별도 리소스입니다. 규칙마다 독립된 주소와 태그를 가지고, 다른 코드가 같은 보안 그룹에 규칙을 추가해도 서로 덮어쓰지 않기 때문입니다. 한 보안 그룹에 두 방식을 섞으면 서로 지우고 다시 만드는 싸움이 벌어집니다. 이번 실습은 별도 리소스 방식을 씁니다.

6data 블록

만들지 않고 읽기만 한다 — 바깥 세계의 정보를 코드로 가져오는 창

data.tf
# 지금 누구로 접속했는가 — apply 전 계정 확인용 (2편 습관)
data "aws_caller_identity" "me" {}
data "aws_region" "current" {}

# 리전마다 하나씩 있는 기본 VPC
data "aws_vpc" "default" {
  default = true
}

# 최신 Amazon Linux 2023 AMI (리전마다 ID가 다르므로 하드코딩하지 않는다)
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
  filter {
    name   = "architecture"
    values = ["x86_64"]
  }
}

# 클라우드가 아닌 데이터 소스: 내 PC의 공인 IP
data "http" "my_ip" {
  url = "https://checkip.amazonaws.com"
}

most_recent의 양날

most_recent = true는 실행할 때마다 “지금 가장 최신”을 고릅니다. AWS가 새 AMI를 내놓은 다음 날 plan을 하면 AMI ID가 바뀌고, ami는 교체를 유발하는 인자라서 멀쩡한 서버를 지우고 다시 만드는 계획이 나옵니다. 실습에서는 괜찮지만 운영에서는 AMI ID를 변수로 고정하거나 lifecycle { ignore_changes = [ami] }를 씁니다(11편). 1편 5장의 “실무 멱등성”과 같은 이야기입니다.

data 소스와 MSP의 경계

고객사 네트워크팀이 관리하는 VPC 안에 MSP가 서버를 놓는 경우가 흔합니다. 이때 VPC를 resource로 선언하면 남의 것을 내 코드가 소유하게 되어, 내 destroy가 고객 네트워크를 지우려 합니다. 내가 만들지 않은 것은 data로 읽는다가 원칙입니다. 소유 경계가 코드에 그대로 드러납니다.

7output과 파일 구성

결과를 밖으로 꺼내는 창구, 그리고 파일을 나누는 관례

outputs.tf
output "account_id" {
  description = "apply한 AWS 계정 (실습 계정인지 확인)"
  value       = data.aws_caller_identity.me.account_id
}

output "web_url" {
  description = "웹 서버 주소"
  value       = "http://${aws_instance.web.public_ip}"
}
terraform output                 # 모든 출력
terraform output -raw web_url    # 따옴표 없는 값 → 스크립트에서 사용
curl -s "$(terraform output -raw web_url)"
terraform output -json           # 기계가 읽는 형식 → 23편 Ansible 연계의 재료

출력은 사람에게 결과를 보여주는 동시에, 모듈의 반환값(6편)이자 다른 도구(Ansible 인벤토리 등)에 넘기는 계약이기도 합니다. 출력 설계는 4편에서 자세히 다룹니다.

파일 구성 관례

03-aws-first/ ├── versions.tf # terraform 블록 (버전·프로바이더 요구) ├── providers.tf # provider 블록 ├── data.tf # data 블록 ├── main.tf # resource 블록 (커지면 network.tf, compute.tf 처럼 주제별로) ├── outputs.tf # output 블록 ├── variables.tf # 입력 변수 (4편부터) └── .terraform.lock.hcl

Terraform은 파일 이름에 의미를 두지 않으므로 이것은 순전히 사람을 위한 관례입니다. 하지만 HashiCorp 스타일 가이드와 대부분의 공개 모듈이 이 구성을 따르기 때문에, 처음 보는 고객사 리포에서도 “버전은 versions.tf에 있겠지”라고 바로 찾을 수 있게 됩니다. 단 하나의 예외는 override.tf와 *_override.tf로, 다른 파일의 내용을 덮어쓰는 특수 파일입니다. 혼란을 주므로 쓰지 않습니다(2편 .gitignore에서 제외한 이유).

-out으로 만든 plan 파일 안에는 변수와 속성 값이 평문으로 들어 있을 수 있습니다. 2편 .gitignore에 *.tfplan을 넣은 이유입니다. 또 plan을 저장한 뒤 다른 사람이 먼저 apply해 state가 바뀌면, 저장된 plan은 “오래된 계획(stale)”으로 거부됩니다. 이 안전장치 덕분에 CI에서 “리뷰한 plan 그대로 apply” 흐름을 만들 수 있습니다(12편).

-target과 -auto-approve는 비상용

-target=주소는 그래프의 일부만 적용합니다. 장애 복구 같은 예외 상황용이며, 습관적으로 쓰면 코드와 실제가 어긋난 채로 남습니다. Terraform도 사용 시 경고를 출력합니다. -auto-approve는 확인 질문을 생략하므로, 사람이 plan을 이미 리뷰한 CI 단계 외에는 쓰지 않습니다.

10의존성 그래프

Terraform은 코드를 그래프로 바꾸고, 그래프를 따라 병렬로 걷는다

plan과 apply를 할 때 Terraform은 모든 블록을 노드로, 참조 관계를 화살표로 하는 방향성 비순환 그래프(DAG)를 만듭니다. 그다음 들어오는 화살표가 없는 노드부터 처리하고, 끝난 노드에 의존하던 노드를 이어서 처리합니다. 서로 의존하지 않는 노드는 동시에 처리합니다(기본 최대 10개, -parallelism=N). destroy는 같은 그래프를 거꾸로 걷습니다. 인스턴스를 먼저 지우고, 그다음 보안 그룹을 지웁니다.

암시적 의존 (implicit)

한 블록이 다른 블록의 속성을 표현식에서 참조하면 자동으로 의존이 생깁니다. 문자열 안의 ${...}도 참조입니다. 대부분의 의존은 이것으로 충분하고, 이것이 권장 방식입니다.

명시적 의존 (depends_on)

어떤 리소스가 다른 리소스의 값을 쓰지는 않지만 그것이 먼저 존재해야 제대로 동작할 때 씁니다. 대표적인 경우가 “권한·네트워크 규칙이 먼저 적용되어야 하는데, ID를 참조할 일은 없는” 관계입니다.

이번 실습의 숨은 의존성

EC2 인스턴스는 보안 그룹의 ID를 참조합니다(암시적 의존). 하지만 아웃바운드 규칙은 별도 리소스라서 인스턴스가 참조하지 않습니다. 그러면 Terraform은 인스턴스 생성과 아웃바운드 규칙 생성을 동시에 진행할 수 있습니다. 그런데 Terraform으로 만든 보안 그룹은 AWS 기본값인 “모든 아웃바운드 허용” 규칙을 지운 상태로 시작합니다. 인스턴스가 부팅하자마자 user_data로 dnf install nginx를 실행하는 순간 아웃바운드 규칙이 아직 없으면 패키지 설치가 실패하고, 웹 서버는 영영 뜨지 않습니다. 운이 좋으면 성공하고 운이 나쁘면 실패하는, 가장 찾기 어려운 종류의 버그입니다. depends_on이 이 경쟁 상태를 없앱니다.

Terraform 그래프의 화살표는 “A는 B에 의존한다(A → B)” 방향으로 그려집니다. 실행은 화살표의 반대 방향, 즉 B가 먼저입니다. 1.7부터 기본 terraform graph는 리소스 간 관계만 간추려 보여주며, 프로바이더·내부 노드까지 포함한 전체 그래프는 -type=plan으로 볼 수 있습니다.

depends_on 사용 원칙

  • 참조로 해결할 수 있으면 참조를 쓴다. 실습 A에서 컨테이너 이름을 문자열로 하드코딩하는 대신 docker_container.cache.name을 참조하면 depends_on이 필요 없어집니다.
  • 왜 필요한지 주석을 단다. 이유 없는 depends_on은 나중에 누구도 지우지 못하는 미신이 됩니다.
  • 너무 넓게 걸지 않는다. 모듈 전체에 depends_on을 걸면 그 모듈의 data 소스까지 apply 시점으로 미뤄져 plan에 (known after apply)가 번지고, 불필요한 교체 계획이 나올 수 있습니다.
  • 순서만 보장하지 준비 완료는 보장하지 않는다. depends_on은 “생성 API 호출이 끝난 뒤”를 보장할 뿐, 그 안의 서비스가 요청을 받을 준비가 되었는지는 모릅니다.
순환 의존 (Error: Cycle)

A가 B를 참조하고 B가 A를 참조하면 그래프에 고리가 생겨 Terraform이 순서를 정할 수 없습니다. 흔한 예는 “웹 보안 그룹이 DB 보안 그룹을 인라인 규칙에서 참조하고, DB 보안 그룹도 웹을 참조”하는 경우입니다. 해결은 보안 그룹은 규칙 없이 만들고, 규칙을 별도 리소스로 분리해 고리를 끊는 것입니다. 5장에서 별도 규칙 리소스를 권장한 또 하나의 이유입니다.

실험 1. 참조로 바꾸기

실험 4. 거꾸로 걷기

14MSP 현장 팁

고객사 코드를 읽고 변경을 리뷰할 때 이번 편 내용이 쓰이는 곳

변경 리뷰는 plan 요약 줄부터

고객사 변경 요청의 PR을 볼 때 코드 diff보다 먼저 plan의 Plan: X to add, Y to change, Z to destroy를 봅니다. 요청 내용이 “태그 추가”인데 destroy가 1 이상이면, 코드가 의도와 다르다는 신호입니다. 승인 기록에 plan 전문을 첨부하는 것이 감사 대응의 핵심 증적입니다.

교체를 유발하는 인자 목록 만들기

자주 다루는 리소스(EC2, RDS, 보안 그룹, ALB)의 “forces replacement” 인자를 팀 위키에 정리해 두면 변경 위험도 판단이 빨라집니다. 예: 보안 그룹 name·description, RDS engine·identifier, EC2 ami·user_data(옵션에 따라)·subnet_id.

리소스 이름 짓기 규칙

코드 안의 리소스 이름은 state 주소가 되므로 나중에 바꾸려면 moved 블록이 필요합니다(9편). 타입명을 반복하지 않고(aws_instance.web ○, aws_instance.web_instance ×), 하나뿐이면 this나 main을 쓰는 커뮤니티 관례가 있습니다.

남의 것은 data, 내 것은 resource

고객 네트워크팀의 VPC·서브넷·Route53 존, 보안팀의 KMS 키는 data로 읽습니다. 책임 경계가 코드에 드러나야 계약 범위 밖의 리소스를 실수로 바꾸거나 지우지 않습니다.

AMI·이미지는 고정한다

운영 고객사에서 most_recent로 AMI를 고르면, 평범한 태그 변경 PR의 plan에 갑자기 서버 교체가 섞여 나옵니다. AMI ID는 변수로 명시하고, 이미지 갱신은 별도 변경 요청으로 다룹니다.

리전·계정 확인 출력

모든 루트 모듈에 account_id·region 출력을 두는 팀 규칙은 비용이 거의 없고 사고 예방 효과가 큽니다. CI는 이 값이 해당 환경의 기대값과 다르면 apply를 중단하게 만들 수 있습니다(12편).

과제 1. 블록 해부 받아쓰기

실습 B의 aws_vpc_security_group_ingress_rule.http_from_me 블록에서 다음을 찾아 적으세요: 블록 타입, 라벨 2개, 리소스 주소, 인자 6개, 그중 다른 블록을 참조하는 인자, 그 참조가 만드는 의존 2개.

정답

블록 타입 resource, 라벨 "aws_vpc_security_group_ingress_rule"·"http_from_me", 주소 aws_vpc_security_group_ingress_rule.http_from_me. 인자: security_group_id, cidr_ipv4, from_port, to_port, ip_protocol, description. 참조 인자: security_group_id(→ aws_security_group.web)와 cidr_ipv4(문자열 삽입 → data.http.my_ip). 문자열 안의 ${}도 의존을 만든다는 점이 포인트입니다.

과제 2. 숨은 의존성 찾기

다음 상황에서 숨은 의존성은 무엇이고, 어떻게 표현해야 할까요? “EC2 인스턴스에 IAM 인스턴스 프로파일을 붙이고, user_data에서 aws s3 cp로 버킷의 파일을 내려받는다. 버킷 읽기 권한은 aws_iam_role_policy로 역할에 붙인다.”

해설

인스턴스는 인스턴스 프로파일을 참조하고, 프로파일은 역할을 참조하지만, 권한 정책(aws_iam_role_policy)은 아무도 참조하지 않습니다. 정책이 붙기 전에 인스턴스가 부팅하면 aws s3 cp가 AccessDenied로 실패합니다. 인스턴스에 depends_on = [aws_iam_role_policy.read_bucket]을 추가하고 이유를 주석으로 남깁니다. IAM은 전파 지연까지 있어서, 실무에서는 user_data에 재시도 로직도 넣습니다. 이번 편의 아웃바운드 규칙과 정확히 같은 유형입니다.

과제 3. 교체 예측 퀴즈

문서를 찾아보고, 다음 변경이 ~인지 -/+인지 예측한 뒤 plan으로 확인하세요(apply하지 말 것). ① 버킷의 bucket 이름 변경 ② 인바운드 규칙의 to_port를 8080으로 ③ 인스턴스 root_block_device.volume_size를 10으로 ④ provider의 default_tags에 태그 하나 추가.

해설

① -/+: 버킷 이름은 바꿀 수 없음. ② ~: 별도 규칙 리소스(aws_vpc_security_group_ingress_rule)는 규칙 수정 API를 써서 제자리 변경을 지원합니다. 예전 방식의 aws_security_group_rule은 거의 모든 인자가 교체를 유발했습니다. 같은 일을 하는 리소스라도 변경 동작이 다르다는 것이 5장에서 별도 규칙 리소스를 권한 또 하나의 이유입니다. ③ ~: EBS 볼륨은 온라인 확장 가능. 단 OS 안에서 파일시스템 확장은 따로 해야 함(Ansible 영역!). ④ 태그를 지원하는 모든 리소스에 ~가 뜹니다. 기본 태그 변경 하나가 수십 개 리소스의 변경으로 보이는 이유입니다.
