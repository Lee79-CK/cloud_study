이번 편에서 얻을 것

1편 노선도의 네 번째 정거장, 학습입니다. 2편 5장에서 분산 학습의 원리를 맛보았다면, 이번에는 실제로 돌립니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 분산 학습이 필요한 상황을 판단하고, 데이터 병렬과 모델 병렬 계열 중 무엇이 맞는지 고를 수 있습니다.
  • TrainingRuntime과 TrainJob이 각각 누구의 몫이고 어떤 필드를 정하는지 설명하고, 예전 PyTorchJob을 TrainJob으로 옮길 수 있습니다.
  • Kubeflow SDK로 2노드 PyTorch 분산 학습을 제출하고, 로그와 환경 변수로 각 프로세스의 순번을 확인할 수 있습니다.
  • TrainJob이 JobSet과 Pod로 바뀌는 과정, Istio와 네트워크 주의점, 체크포인트와 장애 처리, 파이프라인과의 연결을 압니다.

1언제 분산 학습인가

분산 학습은 공짜가 아닙니다. 코드가 복잡해지고, GPU끼리 통신하는 시간이 생기고, 실패할 지점이 늘어납니다. 먼저 정말 필요한지 따져 봅니다.

상황판단방식
GPU 한 장에 들어가고, 학습도 몇 시간이면 끝남분산할 필요 없음단일 GPU. 파이프라인 단계나 단일 노드 TrainJob
GPU 한 장에 들어가지만 학습이 너무 오래 걸림데이터를 나눠 빨리 끝내기데이터 병렬(PyTorch DDP)
모델이 GPU 한 장에 들어가지 않음모델 자체를 나눠야 함FSDP, DeepSpeed ZeRO, 텐서·파이프라인 병렬
큰 LLM의 미세 조정먼저 LoRA 같은 경량 기법으로 한 장에 넣을 수 있는지 확인LoRA로 안 되면 FSDP나 DeepSpeed
방식무엇을 나누나통신Trainer 런타임
DDP (데이터 병렬)데이터. 모델은 GPU마다 통째로 복사스텝마다 기울기 전체를 all-reducetorch-distributed
FSDP가중치, 기울기, 옵티마이저 상태를 GPU마다 조각으로필요할 때 조각을 모으고 흩음. DDP보다 많음torch-distributed
DeepSpeed ZeROFSDP와 비슷하게 단계별로 조각화, CPU나 NVMe로 내리기도단계에 따라 다름deepspeed-distributed
텐서·파이프라인 병렬층 안의 행렬, 또는 층 묶음을 GPU마다매우 많음. 빠른 연결(NVLink, InfiniBand) 필요프레임워크(Megatron 등)를 담은 런타임

이번 편은 가장 흔한 DDP를 중심으로 다룹니다. 맨 위의 그림이 DDP 한 스텝의 흐름입니다.

2Training Operator에서 Trainer로

Kubeflow의 예전 학습 구성요소인 Training Operator(v1)는 프레임워크마다 리소스가 따로 있었습니다. PyTorchJob, TFJob, MPIJob, XGBoostJob, JAXJob 등입니다. Trainer v2는 이것을 하나의 TrainJob으로 통일하고, 프레임워크와 인프라 설정은 런타임으로 분리했습니다. 두 API는 서로 호환되지 않으므로, 예전 자료의 YAML은 그대로 쓸 수 없습니다.

구분Training Operator v1Trainer v2
사용자 리소스프레임워크별 CRD (PyTorchJob 등)TrainJob 하나
인프라 설정사용자가 Job마다 Pod 템플릿 전체를 작성관리자가 런타임에 한 번 정의, 사용자는 이름으로 참조
실행 기반Operator가 Pod를 직접 관리Kubernetes의 JobSet 위에서 동작
데이터와 모델 준비사용자 코드가 알아서초기화 단계(initializer)가 학습 전에 내려받아 공유
Python에서프레임워크별 SDK통합 Kubeflow SDK의 TrainerClient
큐 스케줄링별도 구성Kueue와 함께 쓰도록 설계 (11편)

PyTorchJob을 TrainJob으로 옮기기

PyTorchJob에서TrainJob에서
pytorchReplicaSpecs.Master와 Worker의 replicastrainer.numNodes 하나 (마스터와 워커 구분 없음)
nprocPerNodetrainer.numProcPerNode
컨테이너의 image, command, args, envtrainer.image, command, args, env
컨테이너의 resourcestrainer.resourcesPerNode
Pod 템플릿의 nodeSelector, tolerations, volumes 등관리자가 런타임에 정의. 개별 조정이 필요하면 TrainJob의 Pod 템플릿 덮어쓰기 기능 사용

3런타임과 TrainJob

Trainer v2의 핵심 아이디어는 역할 분리입니다. 플랫폼 관리자는 “우리 회사에서 PyTorch 분산 학습은 이런 이미지, 이런 네트워크 설정, 이런 노드에서 돈다”를 런타임으로 정의합니다. 데이터 과학자는 런타임 이름을 고르고 코드와 규모만 정합니다.

리소스범위누가담는 것
ClusterTrainingRuntime클러스터 전체플랫폼 관리자모든 팀이 공유하는 표준 학습 환경
TrainingRuntime네임스페이스 하나팀 관리자그 팀에만 필요한 학습 환경
TrainJob네임스페이스 하나데이터 과학자코드, 이미지, 노드 수, 자원, 데이터 위치

커뮤니티가 관리하는 기본 ClusterTrainingRuntime으로 torch-distributed, deepspeed-distributed, jax-distributed, mlx-distributed, xgboost-distributed 등이 있고, LLM 미세 조정용 런타임도 있습니다. 클러스터에 무엇이 있는지는 직접 확인합니다.

4실습: SDK로 분산 학습

  
4편의 손글씨 숫자 데이터를 작은 신경망으로 학습하되, 두 노드에 나눠 DDP로 돌립니다. GPU가 없으면 CPU용 통신 방식(gloo)으로 자동 전환되도록 써서, 3편의 kind 클러스터에서도 분산 학습의 모든 과정을 확인할 수 있습니다. 4편의 노트북에서 실행합니다.

  
1단계: 학습 함수. 모든 import를 함수 안에 둡니다

  
def train_digits_ddp():
    import os, torch, torch.distributed as dist
    from torch import nn
    from torch.utils.data import DataLoader, TensorDataset
    from torch.utils.data.distributed import DistributedSampler
    from torch.nn.parallel import DistributedDataParallel as DDP
    from sklearn.datasets import load_digits

    backend = "nccl" if torch.cuda.is_available() else "gloo"
    dist.init_process_group(backend=backend)       # 주소와 순번은 환경 변수에서 읽음
    rank, world = dist.get_rank(), dist.get_world_size()
    local_rank = int(os.environ.get("LOCAL_RANK", 0))
    device = torch.device(f"cuda:{local_rank}" if torch.cuda.is_available() else "cpu")
    print(f"rank {rank}/{world}, local_rank {local_rank}, device {device}")

    X, y = load_digits(return_X_y=True)
    ds = TensorDataset(torch.tensor(X, dtype=torch.float32) / 16.0, torch.tensor(y))
    sampler = DistributedSampler(ds, num_replicas=world, rank=rank, shuffle=True, seed=42)
    loader = DataLoader(ds, batch_size=64, sampler=sampler)  # 프로세스마다 다른 조각

    net = nn.Sequential(nn.Linear(64, 128), nn.ReLU(), nn.Linear(128, 10)).to(device)
    model = DDP(net, device_ids=[local_rank] if device.type == "cuda" else None)
    opt = torch.optim.Adam(model.parameters(), lr=1e-3)

    for epoch in range(10):
        sampler.set_epoch(epoch)                    # 에폭마다 섞는 순서를 바꿈
        for xb, yb in loader:
            opt.zero_grad()
            loss = nn.functional.cross_entropy(model(xb.to(device)), yb.to(device))
            loss.backward()                         # 여기서 기울기를 모든 프로세스와 맞춤
            opt.step()
        if rank == 0:
            print(f"epoch {epoch} loss {loss.item():.4f}")

    if rank == 0:                                   # 저장은 대표 한 프로세스만
        torch.save(model.module.state_dict(), "/tmp/digits-ddp.pt")  # 실무에서는 PVC나 S3
    dist.destroy_process_group()

  
2단계: TrainerClient로 제출하고 로그 보기

  
from kubeflow.trainer import TrainerClient, CustomTrainer

client = TrainerClient()
for r in client.list_runtimes():                     # 쓸 수 있는 런타임 확인
    print(r.name)

job = client.train(
    runtime=client.get_runtime("torch-distributed"),
    trainer=CustomTrainer(
        func=train_digits_ddp,
        num_nodes=2,
        resources_per_node={"cpu": 2, "memory": "4Gi"},  # kind 실습: GPU 없이
        packages_to_install=["scikit-learn"],
    ),
)
client.wait_for_job_status(job)
for line in client.get_job_logs(job, follow=True):
    print(line)

  
로그에서 rank 0/4처럼 순번과 전체 프로세스 수를 확인하세요. 노드가 둘이고 노드마다 프로세스가 몇 개인지에 따라 전체 수가 정해집니다. 손실은 rank 0만 출력하므로 한 줄씩만 보입니다.

  

    GPU 없이 numProcPerNode가 auto일 때
    
기본 런타임의 노드당 프로세스 수는 auto입니다. GPU가 있으면 GPU 수만큼 뜨지만, GPU가 없을 때는 CPU 자원에 따라 정해질 수 있습니다. 그래서 실습에서는 CPU를 2로 작게 주고, 로그의 world 값으로 실제 프로세스 수를 확인합니다. 원하는 수가 있으면 TrainJob의 numProcPerNode로 직접 정하세요. SDK 함수와 인자 이름은 Kubeflow SDK 버전에 따라 조금 다를 수 있습니다.

Trainer가 넣어 주는 환경 변수

  
PyTorch 런타임에서는 Trainer가 torchrun이 읽는 값들을 PET_로 시작하는 환경 변수로 넣고, torchrun이 이를 바탕으로 프로세스마다 RANK, LOCAL_RANK, WORLD_SIZE를 정해 줍니다. 맨 위 그림에서 GPU를 눌러 보면 프로세스별 값을 볼 수 있습니다.

  

    
변수누가뜻

    
      
PET_NNODESTrainer노드 수 (numNodes)

      
PET_NPROC_PER_NODETrainer노드당 프로세스 수

      
PET_NODE_RANKTrainer이 노드의 순번 (0부터)

      
PET_MASTER_ADDR, PET_MASTER_PORTTrainer순번 0 노드의 주소와 포트. 모든 프로세스가 여기로 모여 서로를 찾음

      
RANK, LOCAL_RANK, WORLD_SIZEtorchrun전체 순번, 노드 안 순번, 전체 프로세스 수. 학습 코드가 읽는 값

    
  






  
6네트워크와 Istio

  
분산 학습은 프로세스들이 서로 직접, 여러 포트로, 대량의 데이터를 주고받습니다. 웹 요청을 다루도록 만들어진 서비스 메시와는 잘 맞지 않습니다.

  

    프로필 네임스페이스에는 Istio 사이드카가 붙습니다
    
3편에서 본 것처럼 Kubeflow의 사용자 네임스페이스는 Istio 사이드카 주입이 켜져 있습니다. 학습 Pod에 사이드카가 붙으면 프로세스 간 통신이 막히거나, 사이드카가 끝나지 않아 학습이 끝나도 Pod가 Completed가 되지 않는 문제가 생길 수 있습니다. 그래서 학습 런타임의 Pod 템플릿에 sidecar.istio.io/inject: "false" 주석을 두어 사이드카를 빼는 구성이 흔합니다. 사이드카를 빼면 Istio 정책의 보호도 빠지므로, 네임스페이스 단위 NetworkPolicy로 보완합니다(13편).

7LLM 미세 조정

  
LLM 미세 조정에는 학습 코드 외에 큰 준비물이 둘 필요합니다. 수 GB에서 수백 GB의 사전 학습 모델과 데이터셋입니다. 노드마다 따로 내려받으면 느리고 낭비입니다. Trainer는 학습 전에 초기화 단계(initializer)가 Hugging Face나 S3에서 모델과 데이터셋을 공유 저장소로 한 번만 내려받고, 학습 노드들이 그것을 함께 읽게 합니다.

  
초기화와 미세 조정 런타임을 쓰는 예 (개념을 보여 주는 단순화한 코드)


from kubeflow.trainer import (TrainerClient, BuiltinTrainer, TorchTuneConfig, Initializer,
                              HuggingFaceModelInitializer, HuggingFaceDatasetInitializer)

client = TrainerClient()
job = client.train(
    runtime=client.get_runtime("torchtune-llama3.2-1b"),     # 이름은 list_runtimes로 확인
    initializer=Initializer(
        model=HuggingFaceModelInitializer(storage_uri="hf://meta-llama/Llama-3.2-1B-Instruct",
                                          access_token="..."),   # 실무에서는 Secret으로
        dataset=HuggingFaceDatasetInitializer(storage_uri="hf://tatsu-lab/alpaca"),
    ),
    trainer=BuiltinTrainer(config=TorchTuneConfig(
        resources_per_node={"gpu": 1},
    )),
)

  
    
    
  • BuiltinTrainer는 학습 코드를 직접 쓰지 않고, 런타임에 들어 있는 미세 조정 방법(예: TorchTune 레시피)을 설정만으로 쓰는 방식입니다. 직접 짠 코드를 쓰려면 4장의 CustomTrainer를 씁니다.

  • 모델 접근 토큰처럼 비밀 값은 코드에 적지 말고 Secret을 참조하게 합니다.

  • 먼저 2편 5장의 계산기로 메모리를 어림하세요. LoRA로 GPU 한 장에 들어간다면 분산보다 그쪽이 훨씬 단순합니다.
    • 
    
  • 위 코드의 클래스와 런타임 이름은 SDK와 Trainer 버전에 따라 다를 수 있습니다. 실제로는 공식 예제를 출발점으로 삼으세요.

8장애와 체크포인트

  
노드가 많을수록 그중 하나가 실패할 확률도 커집니다. DDP는 모든 프로세스가 함께 걸어가는 방식이라, 하나가 멈추면 나머지도 통신에서 기다리다 멈춥니다. 그래서 실패를 다루는 기본 전략은 “묶음 전체를 다시 시작하고, 체크포인트에서 이어 간다”입니다.

  

    
원칙방법

    
      
묶음 단위 재시작JobSet의 실패 정책으로 묶음 전체를 다시 시작하는 횟수를 런타임에서 정합니다

      
체크포인트는 모두가 볼 수 있는 곳에ReadWriteMany PVC나 오브젝트 스토리지. 노드 한 대의 로컬 디스크는 안 됨

      
쓰기는 한 프로세스만rank 0만 저장하고, 시작할 때는 모든 프로세스가 같은 체크포인트를 읽음

      
적당한 간격너무 자주 저장하면 학습이 느려지고, 너무 드물면 잃는 시간이 큼. 2편 2장 계산기로 간격을 정함

      
안전한 저장임시 이름으로 쓴 뒤 이름 바꾸기(2편 11장)

    
  

  
스팟이나 선점형 GPU를 쓰면 비용은 크게 줄지만 중단이 잦습니다. 체크포인트에서 이어 가는 코드가 없다면 스팟은 쓰지 않는 편이 낫습니다.






  
9파이프라인과 연결

  
5편과 6편의 파이프라인에서 train 단계를 분산 학습으로 바꾸려면, 파이프라인 단계 안에서 TrainJob을 제출하고 끝날 때까지 기다리는 컴포넌트를 씁니다. 파이프라인 단계 Pod도 프로필의 서비스 계정으로 실행되어, 같은 네임스페이스에 TrainJob을 만들 수 있습니다.


@dsl.component(base_image="python:3.11", packages_to_install=["kubeflow"])
def distributed_train(num_nodes: int) -> str:
    from kubeflow.trainer import TrainerClient, CustomTrainer
    def train_fn():
        ...                                    # 4장의 학습 함수
    client = TrainerClient()
    job = client.train(runtime=client.get_runtime("torch-distributed"),
                       trainer=CustomTrainer(func=train_fn, num_nodes=num_nodes))
    client.wait_for_job_status(job)            # 끝날 때까지 이 단계가 기다림
    return job

  
학습 결과 모델은 TrainJob이 PVC나 오브젝트 스토리지에 저장하게 하고, 다음 단계가 그 위치를 받아 평가합니다. 이 연결을 끝까지 이어 붙이는 종합 실습은 12편에서 합니다.

13정리와 다음 편

  
    
    
  1. 분산 학습은 필요할 때만. 모델이 한 장에 들어가면 DDP, 안 들어가면 FSDP나 DeepSpeed, LLM은 먼저 LoRA로 한 장에 넣을 수 있는지 봅니다.
    2. 
    
  2. Trainer v2는 프레임워크별 CRD를 TrainJob 하나로 통일하고, 인프라 설정은 관리자의 런타임으로 분리했습니다. 예전 PyTorchJob과는 호환되지 않습니다.
    3. 
    
  3. TrainJob은 JobSet과 초기화 Job, 학습 노드 Pod로 바뀌고, Trainer가 PET_ 환경 변수로 노드 수와 순번, 마스터 주소를 넣어 torchrun이 프로세스별 RANK를 정합니다.
    4. 
    
  4. 사용자 네임스페이스의 Istio 사이드카는 분산 통신과 잘 맞지 않아 학습 Pod에서는 흔히 뺍니다. NCCL 로그와 공유 메모리, 노드 간 네트워크를 점검합니다.
    5. 
    
  5. 장애는 묶음 단위로 다시 시작하고, 모두가 볼 수 있는 곳의 체크포인트에서 이어 갑니다. 저장은 rank 0만 합니다.
    6. 
  

    
현장에서 쓰이는 장면

  
  • LLM. 사내 문서로 sLLM을 미세 조정할 때 초기화 단계가 모델을 한 번만 내려받아 노드 네 대가 함께 씁니다.
  • 제조. GPU 한 장으로 사흘 걸리던 비전 모델 학습을 노드 두 대 DDP로 반나절에 끝냅니다.
  • 연구소. Training Operator v1 시절의 PyTorchJob 예제를 쓰던 연구실이 2장의 대응표로 TrainJob으로 옮깁니다.
