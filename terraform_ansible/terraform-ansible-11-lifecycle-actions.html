Terraform & Ansible 강의 · Level 2 Terraform 심화·운영 · 11편 / 26편 · 시리즈 목차

언제, 어떤 순서로, 무엇을 지키며 라이프사이클·액션·프로비저너 — 교체 순서, 삭제 방지, 조건과 점검, 1.14·1.16 액션, 프로비저너를 피해야 하는 이유

Terraform은 기본적으로 “선언한 대로 만든다”만 압니다. 하지만 운영에서는 어떻게 바꾸는지가 더 중요할 때가 많습니다. 끊김 없이 교체하려면 새것을 먼저 만들어야 하고, 운영 DB는 실수로라도 지워지면 안 되며, 어떤 속성은 다른 시스템이 바꾸니 무시해야 하고, 만들기 전에 지켜야 할 가정은 코드로 확인해야 합니다. 3편부터 “11편에서”로 미뤄 온 질문들에 답하는 편입니다.

어떻게 바꿀까

create_before_destroy · replace_triggered_by · ignore_changes

무엇을 지킬까

prevent_destroy · destroy = false · precondition · postcondition · check

무엇을 더 할까

액션(1.14, 1.16 destroy 이벤트) · 프로비저너(최후의 수단)

0들어가며

이번 편의 목표와 실습 지도

이번 편을 마치면

  • 교체가 일어날 때 기본 순서(삭제 → 생성)와 create_before_destroy(생성 → 삭제)의 차이를 실행 순서로 설명하고, 이름 충돌·의존 전파 같은 함정을 피할 수 있습니다.
  • replace_triggered_by, -replace, ignore_changes를 언제 쓰는지 압니다.
  • 삭제 방지 네 가지 — prevent_destroy, 1.16의 lifecycle { destroy = false }, removed, 클라우드의 삭제 보호 — 의 차이를 실측 결과로 구분합니다.
  • precondition·postcondition과 check 블록으로 가정과 보장을 코드에 적고, 실패 시점(plan/apply)과 결과(오류/경고)를 예측합니다.
  • 액션(1.14)과 1.16의 destroy 이벤트·on_failure를 이해하고, 프로비저너 대신 쓸 수 있는 경우를 판단합니다.
  • 프로비저너가 “최후의 수단”인 이유를 실측으로 확인하고 대안(user_data·Packer·Ansible·액션)을 고릅니다.

교체 순서, replace_triggered_by, ignore_changes, prevent_destroy·destroy = false, 조건·check, 프로비저너 결과는 호환 엔진에서 실제로 실행한 출력입니다. 실습 B 코드는 AWS 프로바이더(6.70)로 validate를 통과했습니다. 액션은 Terraform 전용 기능이라 실행하지 못했고, 공식 문서와 HashiCorp 발표를 기준으로 작성했습니다.

1lifecycle 한눈에

리소스 블록 안의 lifecycle은 “Terraform이 이 리소스를 다루는 방식”을 바꾼다

resource "aws_security_group" "web" {
  # ... 인자들

  lifecycle {
    create_before_destroy = true                      # 교체 순서
    prevent_destroy       = false                     # 삭제 계획을 오류로 막기
    ignore_changes        = [tags["LastScanned"]]     # 이 속성의 차이는 무시
    replace_triggered_by  = [aws_launch_template.web] # 저것이 바뀌면 나도 교체

    precondition { # 만들기·바꾸기 전에 확인할 가정
      condition     = var.env != "prd" || var.multi_az
      error_message = "운영계는 Multi-AZ여야 합니다."
    }
    postcondition { # 만든 뒤 보장할 결과
      condition     = self.vpc_id != ""
      error_message = "VPC에 속해야 합니다."
    }
  }
}
설정도입한 줄 요약장
create_before_destroy초기교체 시 새것을 먼저 만들고 옛것을 지운다2
prevent_destroy초기이 리소스를 지우는 plan을 오류로 거부5
ignore_changes초기지정한 속성의 실물·코드 차이를 무시4
replace_triggered_by1.2참조한 리소스·속성이 바뀌면 함께 교체3
precondition · postcondition1.2가정과 보장을 조건으로 (실패하면 오류)6
action_trigger1.14 (destroy 이벤트·on_failure는 1.16)리소스 이벤트에 프로바이더 액션을 묶는다8
destroy1.16 (resource 블록), 1.7 (removed 블록)Terraform이 이 리소스를 지우지 못하게5
lifecycle에는 변수를 쓸 수 없다 (대부분)

create_before_destroy·prevent_destroy·ignore_changes 같은 값은 의존 그래프를 만들 때 필요해서 리터럴만 허용됩니다. “운영계에서만 prevent_destroy”를 변수로 켜고 끌 수 없는 이유입니다(OpenTofu는 1.12부터 prevent_destroy에 같은 모듈의 변수 참조를 허용). Terraform에서는 환경별 디렉터리(8편)에서 리소스를 감싼 모듈의 변형을 쓰거나, 클라우드 쪽 삭제 보호(deletion_protection)를 변수로 켜는 방식으로 대신합니다(7편 RDS). precondition·postcondition의 condition은 일반 표현식이라 변수를 쓸 수 있습니다.

2교체 순서: create_before_destroy

plan의 -/+ 와 +/- 는 순서가 반대다

교체 순서 비교 — 버튼을 눌러 단계별로 보세요

# 실측: 같은 변경(triggers_replace v1 → v2)에 대한 실제 실행 순서
terraform_data.plain: Destroying... [id=d23f257b-…]          # 기본: 먼저 지운다

함정원인해결
이름 충돌새것과 옛것이 잠시 공존하므로, 이름이 유일해야 하는 리소스(보안 그룹 name, IAM 역할, ALB 대상 그룹 name)는 생성이 실패한다name_prefix로 Terraform이 고유 접미사를 붙이게 하거나, 이름에 무작위 접미사(random_id)·버전을 넣는다
의존 전파A에 create_before_destroy를 켜면 A가 의존하는 B에도 자동으로 적용되고 state에 기록된다. B에서 false로 되돌릴 수 없다(순환이 되므로)의존 관계를 이해하고 켠다. 대개 문제없지만 B가 이름 고정 리소스라면 B도 이름 전략이 필요
한도·비용교체 동안 두 개가 공존 (대형 인스턴스, IP 한도)짧게 끝나는 리소스에 적용. 대규모 교체는 블루·그린으로 설계
교체가 아닌 변경제자리 변경(~)에는 아무 영향 없음교체(-/+)가 일어나는 리소스에만 의미가 있다
3편 함정의 답

3편에서 보안 그룹 description을 바꾸면 교체가 일어나는데, 그 보안 그룹을 쓰는 인스턴스가 있으면 “먼저 삭제”가 DependencyViolation으로 실패하며 삭제 대기 시간이 끝날 때까지 오래 멈춘다고 했습니다. 해법이 바로 name_prefix + create_before_destroy입니다. 새 보안 그룹을 만들고 → 인스턴스(또는 네트워크 인터페이스)가 새 것을 쓰도록 제자리 변경 → 옛 보안 그룹은 더 이상 쓰이지 않으니 삭제됩니다. 실습 B에서 직접 합니다.

“저것이 바뀌면 나도 새로” 와 “지금 이것만 새로”

resource "aws_launch_template" "web" {
  # 이미지·user_data가 바뀌면 새 버전
}

resource "aws_autoscaling_group" "web" {

  # terraform_data.config will be updated in-place
replace_triggered_byterraform apply -replace=주소

4ignore_changes

Terraform이 이 속성의 주인이 아님을 선언한다

resource "aws_autoscaling_group" "web" {
  desired_capacity = 2

  lifecycle {
    ignore_changes = [desired_capacity] # 오토스케일링이 바꾸는 값
  }
}

resource "aws_instance" "web" {
  lifecycle {
    ignore_changes = [ami, tags["PatchGroup"]] # 새 AMI로 갈아엎지 않기(7편), 패치 도구가 붙이는 태그
  }
}
# 실측: input을 ignore_changes에 넣은 리소스는 값이 바뀌어도 plan에 나타나지 않는다
#   (같은 변경에서 다른 리소스들은 교체·변경이 계획됨)
잘 쓰는 곳위험한 곳
다른 시스템이 관리하는 값: 오토스케일링 수량, 다른 팀 도구의 태그, 콘솔에서 운영팀이 바꾸는 것으로 합의한 값(9편 드리프트 “무시”), 생성 후 바뀌는 초기 값(비밀번호 초기값 등)보안 속성(보안 그룹 규칙, 암호화)을 무시하면 드리프트를 영원히 못 본다. ignore_changes = all은 “만들고 지우기만 하고 바꾸지는 않는다”는 뜻이라 사실상 관리 포기. 쓰려면 사유를 주석으로
태그만 무시하고 싶다면

리소스마다 ignore_changes = [tags]를 쓰면 우리 태그 표준까지 관리하지 못합니다. 다른 도구가 붙이는 특정 태그 키만 무시하려면 9편에서 본 AWS 프로바이더의 ignore_tags { keys = [...] key_prefixes = [...] }를 provider 수준에서 쓰는 편이 정확합니다.

5삭제 방지 네 가지

이름은 비슷하지만 막는 것도, 막는 방법도 다르다

장치어디에삭제가 계획되면블록을 통째로 지우면쓰는 때
prevent_destroy = trueresource의 lifecycleplan 오류로 거부 (실측)보호도 함께 사라져 삭제된다 (실측)state 버킷(5편), 운영 DB처럼 절대 지우면 안 되는 것
lifecycle { destroy = false } (1.16)resource의 lifecycleTerraform이 이 리소스를 지우지 않는다. 호환 엔진(OpenTofu 1.12+, 같은 문법)에서는 삭제 대신 state에서만 제거(forget)로 계획됨 (실측)—지우지 말고 남겨 두어야 하는 리소스를 관리하는 동안
removed { … lifecycle { destroy = false } }별도 블록 (5·9편)—state에서만 빠지고 실물은 남는다관리 이관, 다른 state로 넘기기
클라우드 삭제 보호 (deletion_protection 등)리소스 인자Terraform은 계획하지만 AWS API가 거부여전히 AWS가 거부Terraform 밖(콘솔·CLI)의 실수까지 막아야 할 때. 변수로 켜고 끌 수 있음(7편)
# 실측 1: prevent_destroy가 있는 리소스를 지우려는 plan
Error: Resource instance cannot be destroyed
Resource instance terraform_data.guarded has prevent_destroy set, but the plan calls for this resource to be destroyed.
To proceed, either disable prevent_destroy for this resource or exclude …

# 실측 2: 그 resource 블록을 통째로 지우고 plan → 보호가 사라졌다
  # terraform_data.guarded will be destroyed
  # (because terraform_data.guarded is not in configuration)

# 실측 3: lifecycle { destroy = false } 리소스를 destroy (호환 엔진)
  # terraform_data.db will be removed from the … state but will not be destroyed
Plan: 0 to add, 0 to change, 1 to destroy, 1 to forget.

# 실측 4: destroy = false 리소스가 교체되면 (호환 엔진)
  # terraform_data.db must be replaced - older instance will not be destroyed (lifecycle.destroy = false)
./+ forget and then create replacement
실측 4가 보여 주는 함정: 고아 리소스

destroy = false인 리소스가 교체되면, 옛 실물은 지워지지 않은 채 state에서만 빠지고 새것이 만들어집니다. 운영 DB라면 “데이터는 옛 DB에 남아 있고 Terraform은 빈 새 DB를 관리하는” 상황이 됩니다. 이 설정은 “실수로 지우지 않기”에는 좋지만 교체를 막아 주지는 않습니다. 교체 자체를 막아야 하면 prevent_destroy(교체도 삭제를 포함하므로 오류)와 plan 리뷰의 “-/+ 금지” 규칙(9편)을 함께 씁니다.

Terraform 1.16의 정확한 동작은 문서로 확인

Terraform 1.16 변경 이력은 이 기능을 “리소스가 삭제되지 않도록 막는다”고만 적고 있습니다. 위 실측 3·4는 같은 문법을 먼저 도입한 OpenTofu에서의 결과이므로, Terraform 1.16에서 plan 표시와 세부 동작이 같은지는 운영에 쓰기 전에 직접 확인하세요. 1.15 이하에서 resource 블록에 이 설정을 쓰면 오류가 납니다.

권장 조합(운영 DB): 클라우드 삭제 보호(deletion_protection = true) + prevent_destroy = true + 최종 스냅숏(skip_final_snapshot = false) + plan 리뷰 규칙. 하나만으로는 부족합니다. 7편 15장의 “운영 DB 보호 3종 세트”가 이것입니다.

6precondition·postcondition

“이 리소스는 이런 가정 위에서 만들어진다”를 코드로

terraform/11-lifecycle/a2/main.tf (실습 A)
variable "instance_type" {
  type    = string
  default = "t3.micro"
}

variable "arch" {
  type    = string
  default = "x86_64"
}

# AMI 조회 결과를 흉내 낸다 (실제로는 data "aws_ami")
resource "terraform_data" "ami" {
  input = { id = "ami-0abc", architecture = var.arch }
}

resource "terraform_data" "web" {
  input = { type = var.instance_type, ami = terraform_data.ami.output.id }

  lifecycle {
    # 만들기 전에 확인하는 가정
    precondition {
      condition     = terraform_data.ami.output.architecture == "x86_64"
      error_message = "t3 계열에는 x86_64 AMI가 필요합니다. 현재: ${terraform_data.ami.output.architecture}"
    }

    # 만든 뒤 보장해야 하는 결과 (self로 자기 속성 참조)
    postcondition {
      condition     = self.output.type != "t3.nano"
      error_message = "t3.nano는 메모리가 부족해 nginx가 불안정합니다."
    }
  }
}

8액션 (1.14 · 1.16)

선언형 도구에 들어온 “명령형 작업” — 단, 프로바이더가 정의한 것만

Terraform은 “상태를 선언하고 맞춘다”는 모델이라 “캐시를 비워라”, “함수를 한 번 호출해라”, “알림을 보내라” 같은 일회성 작업을 표현할 방법이 없었습니다. 그래서 프로비저너나 null_resource + 스크립트를 썼죠. 1.14에서 추가된 액션(action)은 프로바이더가 정의한 명령형 작업을 Terraform 흐름 안에서 실행합니다. 액션은 리소스 state를 바꾸지 않습니다.

# 액션 선언: 프로바이더가 제공하는 작업 종류 + 설정
action "aws_lambda_invoke" "notify_team" {
  config {
    function_name = "deployment-notifier"
    payload = jsonencode({
      message = "web 서버 구성이 바뀌었습니다"
    })
  }
}

resource "aws_instance" "web" {
  # ...

  lifecycle {
    # 이벤트에 액션을 묶는다
    action_trigger {
      events     = [after_create, after_update]
      actions    = [action.aws_lambda_invoke.notify_team]
      on_failure = continue # 1.16: 알림 실패는 배포를 막지 않는다
    }
  }
}
terraform plan  -invoke=action.aws_lambda_invoke.notify_team   # 이 액션만 실행하는 계획 (다른 리소스는 제외)
terraform apply -invoke=action.aws_lambda_invoke.notify_team   # 승인 후 실행 → "Actions: 1 to invoke"
요소내용
실행 방법① CLI의 -invoke로 단독 실행(승인 절차 포함) ② action_trigger로 리소스 이벤트에 연결
이벤트before_create, after_create, before_update, after_update (1.14) + before_destroy, after_destroy (1.16)
condition참일 때만 실행 (예: 운영계에서만 알림)
on_failure (1.16)halt(기본: 중단, taint 안 함) · continue(경고만 남기고 계속) · taint(중단하고 리소스를 다음 apply에 교체 대상으로)
caller (1.16)액션 설정에서 호출한 리소스의 값을 참조 (액션 하나를 여러 리소스가 공유)
제공 프로바이더AWS 프로바이더가 가장 많음: aws_lambda_invoke, aws_cloudfront_create_invalidation, aws_sns_publish, aws_ec2_stop_instance, aws_sfn_start_execution 등. azurerm도 일부 제공. 프로바이더 문서의 Actions 항목 확인
destroy 시점 액션의 제약 (1.16)

삭제 직전 최종 백업, 삭제 후 자산 관리 시스템(CMDB) 기록 정리처럼 유용하지만, ① 액션 설정과 조건이 plan 시점에 모두 알려져야 하고, ② ephemeral 값은 쓸 수 없으며, ③ resource 블록을 통째로 지우면 그 안의 action_trigger도 사라져 액션이 실행되지 않습니다. 그래서 먼저 count = 0으로 삭제를 적용하고(액션 실행), 다음 변경에서 블록을 지우는 두 단계로 진행합니다.

on_failure 고르기예
halt배포 후 스모크 테스트 액션: 실패하면 멈춰야 한다
continue알림·캐시 데우기: 실패해도 배포 자체는 성공
taint새 서버 등록 액션이 실패: 이 서버는 믿을 수 없으니 다음에 새로 만든다
Ansible과의 관계 (23편 예고)

HashiCorp 문서는 액션의 용도로 “Ansible 플레이북 같은 Terraform 밖의 자동화 실행”을 듭니다. 서버 생성 직후 구성 작업을 시작시키는 연결 고리로, 프로비저너 대신 쓸 수 있는 정식 경로입니다. 23편 Terraform + Ansible 통합에서 인벤토리 전달 방식과 함께 비교합니다.

보안 그룹을 “사용 중”으로 만들기 위해 인스턴스 대신 연결되지 않은 네트워크 인터페이스(ENI)를 씁니다. ENI는 인스턴스에 붙이지 않으면 비용이 없습니다. 6편 네트워크(06-network)의 SSM 값을 읽으므로 네트워크가 남아 있어야 합니다.

resource "aws_security_group" "web" {

    create_before_destroy = true
  }
}

resource "aws_network_interface" "web" {
  subnet_id       = local.subnet_id
  security_groups = [aws_security_group.web.id]

13흔한 오류와 해결

lifecycle·조건·액션·프로비저너에서 실제로 만나는 문제 14가지

14MSP 현장 팁

고객사 운영 리소스의 “어떻게 바꾸는가”를 표준화하기

교체 위험 리소스 목록

고객사별로 “교체되면 서비스 영향이 있는 리소스 종류”(DB, 로드밸런서, 고정 IP, 보안 그룹)를 목록으로 만들고, 공통 모듈에서 그 리소스들에 create_before_destroy·prevent_destroy·이름 전략을 기본으로 넣습니다. 리뷰어는 이 목록의 리소스에 -/+가 보이면 무조건 멈춥니다.

ignore_changes에는 반드시 사유

ignore_changes는 드리프트를 영원히 숨깁니다. 모든 ignore_changes 옆에 “누가 이 값을 관리하는가”를 주석으로 적게 하고, 분기마다 목록을 검토합니다. 사유 없는 ignore_changes는 리뷰에서 반려합니다.

precondition으로 계약 조건 코드화

“운영계는 Multi-AZ”, “운영 DB는 삭제 방지 켬”, “허용 리전만” 같은 고객 계약·보안 기준을 precondition으로 넣으면, 위반하는 변경은 plan 단계에서 고객 언어로 된 메시지와 함께 막힙니다. 12편의 정책(Sentinel·OPA)으로 가기 전 단계의 가벼운 정책입니다.

check는 운영 대시보드의 재료

check 블록(엔드포인트 응답, 인증서 만료 임박, 백업 보존 기간)을 매일 드리프트 점검과 함께 돌리면 고객별 “인프라 건강 보고”가 됩니다. 실패해도 막지 않으므로 운영 환경에 부담 없이 넣을 수 있습니다.

프로비저너가 보이면 개선 백로그로

인수한 고객 코드에 remote-exec 프로비저너가 있다면 9편의 보안 백로그처럼 기록하고, user_data·Ansible·액션으로 옮기는 계획을 세웁니다. 특히 프로비저너 때문에 22번 포트와 공인 IP가 열려 있다면 보안 우선순위가 높습니다.

새 기능은 버전과 함께 기록

destroy = false·destroy 액션·on_failure는 1.16, 액션은 1.14입니다. 공통 모듈에 이런 기능을 쓰면 required_version을 올리고 CHANGELOG에 적어, 낮은 버전을 쓰는 고객 저장소가 init 단계에서 바로 알 수 있게 합니다.

과제 1. 7편 모듈에 교체 전략 넣기

7편 ALB 모듈의 보안 그룹과 대상 그룹, app-servers 모듈의 보안 그룹에 name_prefix + create_before_destroy를 적용하세요. 대상 그룹 이름은 32자 제한이 있으므로 name_prefix는 6자 이하만 허용됩니다(프로바이더 제약) — 어떻게 해결할까요? 10편의 테스트를 고쳐 통과시키세요.

힌트

대상 그룹은 name_prefix = "web-"처럼 짧은 접두사를 쓰거나, random_id를 이름에 넣고 대상 그룹 설정이 바뀔 때 random_id도 바뀌게 keepers를 연결합니다. 이름 규칙(label)과 충돌하므로 6편 3장의 “계약 변경” 여부도 판단하세요. 기존 리소스의 name → name_prefix 변경은 그 자체로 교체입니다.

과제 2. 운영계 계약 조건

7편 rds-postgres 모듈에 변수 env를 추가하고, precondition으로 “env가 prd면 multi_az와 deletion_protection이 모두 true”를 강제하세요. 10편 방식으로 expect_failures = [aws_db_instance.this] 테스트도 작성합니다.

과제 3. check로 ALB 상태 감시

7편 07-app 루트에 7장의 check 블록(ALB /health 200 확인)을 추가하고, 7편 실습 중 web 서버 두 대를 모두 중지했을 때 plan에서 경고가 나는지 확인하세요(비용이 드는 실습이므로 7편 실습 시간 안에).

과제 4. 프로비저너 걷어내기

다음 코드를 프로비저너 없이 다시 쓰세요: aws_instance + remote-exec로 sudo dnf install -y nginx 실행, connection은 공인 IP와 SSH 키. 바뀐 설계에서 보안 그룹과 키 페어는 어떻게 달라지나요?

해설

user_data로 설치(7편 템플릿 방식) → SSH 키·22번 인바운드·공인 IP가 필요 없어지고 서버를 프라이빗 서브넷에 둘 수 있습니다. 설치 내용이 바뀌면 user_data_replace_on_change = true로 교체. 무거운 구성은 Packer 이미지나 Ansible로. 보안 그룹에서 22번 규칙, aws_key_pair, associate_public_ip_address가 사라집니다.

18정리와 다음 편

한 장으로 다시 보기

교체 순서

기본은 삭제 → 생성(-/+). create_before_destroy는 생성 → 삭제(+/-), 옛것은 deposed. 이름 유일 리소스는 name_prefix와 짝. 의존 리소스에 전파.

트리거와 무시

replace_triggered_by는 영구 규칙, -replace는 일회 명령. ignore_changes는 주인이 다른 속성에만, 사유와 함께.

삭제 방지 네 가지

prevent_destroy(plan 오류, 블록 지우면 사라짐), destroy = false(1.16, 지우지 않음 — 교체 시 고아 주의), removed(관리 이관), 클라우드 삭제 보호(콘솔 실수까지).

조건과 점검

precondition은 전, postcondition은 후(이미 반영됨). 값이 미정이면 apply 때 검사. check는 경고만, 범위 data 소스.

액션

프로바이더 정의 명령형 작업. -invoke 또는 action_trigger. 1.16: destroy 이벤트, on_failure(halt·continue·taint), caller.

프로비저너

plan에 안 보이고, 한 번만 돌고, 실패하면 taint. user_data·Packer·Ansible·액션이 먼저, 정말 필요하면 terraform_data + 멱등 명령.
