기억이자 금고 State 완전 이해 — 구조, 원격 백엔드와 잠금, state 명령, 민감 값의 진화, 유출 사고

Terraform은 state 없이는 자기가 무엇을 만들었는지 기억하지 못합니다. 그리고 그 기억 안에는 데이터베이스 비밀번호와 접속 정보가 평문으로 들어 있을 수 있습니다. 이번 편은 이 파일을 열어 구조를 보고, 여러 사람이 안전하게 공유하도록 원격 백엔드와 잠금을 걸고, 꺼내 보거나 고칠 때 쓰는 명령과, 애초에 비밀을 state에 남기지 않는 최신 방법을 다룹니다.

잃으면: 기억상실

state가 사라지면 Terraform은 클라우드에 있는 리소스를 “모르는 것”으로 보고 전부 새로 만들려 합니다. 이름 충돌, 중복 과금, 고아 리소스가 따라옵니다(1편 6장 시나리오 5).

새면: 금고 문이 열림

state가 공개되면 인프라 지도 전체와 그 안의 비밀이 함께 노출됩니다. 고객사 state라면 MSP의 계약·보안 사고가 됩니다.

0들어가며

이번 편의 목표와 실습 지도

이번 편을 마치면

  • state가 하는 세 가지 일(대응 기록, 의존성 기억, 성능 캐시)과 파일 구조(serial, lineage, resources, sensitive_attributes 등)를 설명할 수 있습니다.
  • 로컬 state의 한계를 알고 S3(네이티브 잠금 use_lockfile)·Azure Blob·GCS 원격 백엔드를 구성할 수 있습니다.
  • 로컬에서 원격으로, 원격에서 원격으로 state를 안전하게 옮기고, 이전 버전으로 복구할 수 있습니다.
  • state list/show/mv/rm/pull/push와 코드 기반 대안(moved·removed·import)을 상황에 맞게 고를 수 있습니다.
  • 민감 값 처리의 진화 — sensitive → ephemeral(1.10) → write-only 인자(1.11) → terraform_data의 store 블록(1.16) — 를 “state에 무엇이 남는가” 기준으로 비교할 수 있습니다.
  • state 유출 사고의 전형적인 경로와 예방·대응 절차를 압니다.

1state는 무엇을 기억하는가

“클라우드에 다 있는데 왜 따로 기록해야 하나?”에 대한 답

① 코드와 실물의 대응

코드의 aws_instance.web["web1"]이 클라우드의 i-0abc123…라는 연결 고리. 이것이 없으면 Terraform은 수천 개 인스턴스 중 어느 것이 “내 것”인지 알 수 없습니다. 태그는 누구나 바꿀 수 있고 모든 리소스가 태그를 지원하지도 않습니다.

② 코드에서 사라진 것의 기억

코드에서 블록을 지우면 Terraform은 state를 보고 “예전에 내가 만든 이것을 지워야 한다”고 판단합니다. 의존 관계도 기록되어 있어서, 코드에서 사라진 리소스를 어떤 순서로 지울지도 압니다. Ansible이 할 수 없는 일입니다(1편 6장).

③ 성능을 위한 캐시

리소스 수백 개를 매번 처음부터 찾지 않고, 기록된 ID로 바로 조회(refresh)합니다. 아주 큰 환경에서는 -refresh=false로 조회조차 건너뛰고 state를 믿기도 합니다(위험을 알고 쓰는 옵션).

“진실의 원천”이라는 말의 정확한 뜻

1편에서 IaC의 진실의 원천은 Git의 코드라고 했습니다. state는 “무엇이 있어야 하는가”의 원천이 아니라, “Terraform이 무엇을 관리하고 있는가”의 원천입니다. 코드(원하는 상태)와 클라우드(실제 상태) 사이를 이어 주는 장부이고, 이 장부가 틀리면 plan 전체가 틀립니다. 그래서 state는 사람이 손으로 고치는 파일이 아니라, Terraform 명령으로만 다루는 파일입니다.

직접 편집 금지

state JSON을 편집기로 열어 고치는 것은 최후의 최후 수단입니다. 내부 형식은 공개된 계약이 아니라 바뀔 수 있고, 한 글자의 실수가 다음 apply에서 리소스 삭제·재생성으로 이어집니다. 9장의 명령과 코드 블록으로 해결되지 않는 상황은 거의 없습니다. 꼭 손대야 한다면 반드시 state pull로 백업하고, serial을 1 올린 뒤 state push로 올립니다.

3serial·lineage·백업

state를 엉뚱한 것으로 덮어쓰지 못하게 하는 두 개의 숫자

serial — 판 번호

state가 바뀔 때마다 1씩 올라갑니다. 더 낮은 번호의 state로 덮어쓰려 하면 거부됩니다. “어제 받아 둔 사본을 실수로 올려서 오늘의 변경을 날리는” 사고를 막습니다.

lineage — 족보

state가 처음 만들어질 때 정해지는 UUID로, 평생 바뀌지 않습니다. 다른 lineage의 state로 덮어쓰려 하면 거부됩니다. “개발계 state를 운영계 위치에 올리는” 사고를 막습니다.

-force는 보호장치를 끄는 스위치

terraform state push -force는 두 검사를 모두 건너뜁니다. 이전 버전으로 의도적으로 되돌리는 복구 상황(14장)에서만, 무엇을 덮어쓰는지 알 때 씁니다. 되돌린 뒤에는 반드시 terraform plan -refresh-only로 실제와의 차이를 확인합니다.

4로컬 state의 한계

혼자 쓰는 실습 디렉터리를 넘어서는 순간 생기는 네 가지 문제

공유 불가

state가 내 노트북에만 있으면 동료가 같은 환경을 apply할 수 없습니다. 각자 다른 state를 갖게 되는 순간 리소스가 중복 생성됩니다. Git에 올리는 것은 2편에서 막은 이유(비밀 노출, 병합 충돌) 때문에 답이 아닙니다.

동시 실행 사고

두 사람이 같은 state로 동시에 apply하면 나중에 저장한 쪽이 앞의 변경 기록을 덮어씁니다. 덮어써진 리소스는 클라우드에는 있지만 state에는 없는 고아가 됩니다(5장 시뮬레이터).

보안

노트북 디스크의 평문 파일은 분실·백업 동기화·악성코드에 노출됩니다. 접근 기록도 남지 않습니다.

내구성

디스크가 고장 나거나 디렉터리를 실수로 지우면 끝입니다. 이력도 직전 한 판(.backup)뿐입니다.

5잠금 (locking)

한 번에 한 사람만 state를 바꾸게 하는 장치

시뮬레이터 — 엔지니어 A와 B가 같은 환경에 거의 동시에 apply한다

엔지니어 A — 보안 그룹 규칙 추가
원격 state (S3)
엔지니어 B — 인스턴스 유형 변경

버튼을 눌러 두 경우를 비교하세요.

잠금이 걸리는 명령

state를 쓸 수 있는 모든 명령이 잠금을 잡습니다: plan(refresh 결과 기록을 위해), apply, destroy, import, state mv/rm/push, refresh. apply는 “yes” 입력을 기다리는 동안에도 잠금을 쥐고 있습니다. 확인 프롬프트를 띄워 둔 채 점심을 먹으러 가면 팀 전체가 멈춥니다.

# 다른 사람이 잠금을 쥐고 있을 때
Error: Error acquiring the state lock
Lock Info:
  ID:        5f2c1d7e-…
  Path:      iac-lab-tfstate-123456789012/iac-lab/dev/04-playground/terraform.tfstate
  Operation: OperationTypeApply
  Who:       hong@laptop
  Created:   2026-10-21 05:12:44 UTC

terraform plan -lock-timeout=120s      # 최대 2분 동안 잠금이 풀리기를 기다림 (CI에서 유용)
terraform force-unlock 5f2c1d7e-…      # 잠금 강제 해제 (아래 경고)
force-unlock 전에 반드시 확인할 세 가지

① Lock Info의 Who에게 연락해 실행 중이 아님을 확인했다. ② CI 파이프라인 실행 목록에서 해당 환경의 작업이 없음을 확인했다. ③ 프로세스가 비정상 종료(노트북 절전, 네트워크 끊김, Ctrl+C 두 번)되어 잠금이 남은 것이 확실하다. 실행 중인 apply의 잠금을 풀면 그 apply의 결과 기록과 내 변경이 서로 덮어써 위 시뮬레이터의 “잠금 없음” 결과가 그대로 재현됩니다.

S3 잠금의 진화

방식설정상태
DynamoDB 테이블 잠금dynamodb_table = "tf-locks"지원 중단(deprecated). 1.11부터 경고, 향후 제거 예정. 별도 테이블 생성·권한 관리가 필요했음
S3 네이티브 잠금use_lockfile = true1.10에서 도입, 1.11에서 정식(GA). S3의 조건부 쓰기로 state 옆에 .tflock 파일을 만들어 잠금. 추가 리소스 불필요

기존 DynamoDB 방식을 쓰는 고객사라면 두 설정을 동시에 켠 상태로 한 번 terraform init -reconfigure 한 뒤, 모든 사용자·CI가 새 설정을 쓰게 되면 dynamodb_table을 제거하는 순서로 옮깁니다. 이 S3 잠금은 “S3 Object Lock(객체 잠금)” 기능과는 아무 관련이 없으며 일반 버킷에서 동작합니다.

6S3 백엔드

AWS 환경의 표준 원격 state 저장소

backend.tf — 모든 값을 적은 형태

  backend "s3" {
    bucket       = "iac-lab-tfstate-123456789012"              # state 전용 버킷

  }
}

왜 코드 블록이 더 나은가

state mv·state rm은 실행하는 순간 공유 state가 바뀝니다. 리뷰도 기록도 없고, 다른 사람이 아직 옛 코드로 plan하면 엉뚱한 결과가 나옵니다. moved·removed 블록은 PR로 리뷰되고, plan에 “무엇이 어디로 옮겨진다/관리에서 빠진다”가 표시되며, 모든 환경(dev·stg·prd)에서 같은 코드로 같은 변경이 재현됩니다. 명령은 일회성 긴급 조치나 다른 state 사이 이동처럼 코드로 표현할 수 없는 경우에 씁니다.

실측: state mv만 하고 코드를 안 바꾸면

$ terraform state mv terraform_data.after terraform_data.later
Successfully moved 1 object(s).

$ terraform plan          # 코드에는 여전히 "after"가 있다
  # terraform_data.after will be created
  # terraform_data.later will be destroyed
  # (because terraform_data.later is not in configuration)
Plan: 1 to add, 0 to change, 1 to destroy.

state의 주소와 코드의 주소는 항상 함께 움직여야 합니다. 이것이 서버였다면 “이름만 바꾸려다 서버를 지우고 새로 만드는” 계획입니다.

실측: moved 블록으로 이름 바꾸기

# 코드의 리소스 이름을 after → renamed 로 바꾸고, 아래 블록 추가
moved {
  from = terraform_data.after
  to   = terraform_data.renamed
}

$ terraform plan
  # terraform_data.after has moved to terraform_data.renamed
Plan: 0 to add, 0 to change, 0 to destroy.

실측: removed 블록으로 관리만 중단

removed {
  from = terraform_data.renamed
  lifecycle {
    destroy = false       # 실물은 그대로 두고 state에서만 뺀다
  }
}

$ terraform plan
  # terraform_data.renamed will be removed from the state but will not be destroyed
Plan: 0 to add, 0 to change, 0 to destroy, 1 to forget.

removed를 apply한 뒤에는 블록을 지워도 됩니다. MSP에서는 “고객이 직접 관리하기로 한 리소스를 우리 코드에서 넘겨줄 때”, “다른 팀의 state로 리소스를 옮길 때(이쪽은 removed, 저쪽은 import)”에 씁니다.

① sensitive — 커튼 (4편 복습)

실습 A에서 본 그대로입니다. 화면에는 (sensitive value)로 나오지만 state에는 평문으로, 그것도 input과 output 두 곳에 저장됩니다. sensitive_attributes는 “이 경로의 값은 민감하다”는 표시일 뿐 값을 숨기지 않습니다.

ephemeral 값은 쓸 수 있는 곳이 제한됩니다: 다른 ephemeral 변수·출력·리소스, provider 설정(인증 토큰 등), provisioner·connection, 그리고 ③의 write-only 인자. 일반 리소스 인자에 넣으면 Ephemeral value not allowed 오류가 납니다. 또 ephemeral 리소스는 실행할 때마다 값이 다시 만들어지므로(위 random_password는 매번 새 비밀번호), “한 번 정해지면 유지”가 필요할 때는 ③이나 ④와 조합합니다.

③ write-only 인자 — 보내고 잊는다 (1.11)

ephemeral "random_password" "db" {
  length = 20
}

# 1) 비밀번호를 Secrets Manager에 저장 (write-only 인자라 state에 남지 않음)
resource "aws_secretsmanager_secret" "db" {
  name = "iac-lab/dev/db-password"
}
resource "aws_secretsmanager_secret_version" "db" {
  secret_id                = aws_secretsmanager_secret.db.id
  secret_string_wo         = ephemeral.random_password.db.result
  secret_string_wo_version = 1 # 비밀번호를 바꾸고 싶을 때 2로 올린다
}

# 2) 같은 값을 DB에 설정 (역시 write-only)
resource "aws_db_instance" "app" {
  # ... engine, instance_class 등 ...
  username            = "app"
  password_wo         = ephemeral.random_password.db.result
  password_wo_version = aws_secretsmanager_secret_version.db.secret_string_wo_version
}

write-only 인자(_wo로 끝나는 이름이 관례)는 apply 때 리소스에 값을 넘기지만 plan·state 어디에도 저장하지 않습니다. 그래서 Terraform은 값이 바뀌었는지 알 수 없고, 대신 짝이 되는 _wo_version 숫자를 state에 저장해 “버전이 올랐으면 다시 보낸다”로 변경을 표현합니다. 위 예처럼 ephemeral 비밀번호는 매번 새로 만들어지지만, 버전이 그대로면 리소스로 다시 보내지 않으므로 DB 비밀번호가 실행마다 바뀌지 않습니다.

모든 리소스가 write-only 인자를 지원하는 것은 아닙니다. 프로바이더 문서에서 Write-Only 표시를 확인하세요. 그리고 가장 좋은 방법은 비밀번호를 Terraform이 아예 다루지 않는 것입니다. RDS의 manage_master_user_password = true는 AWS가 비밀번호를 만들어 Secrets Manager에 넣고 순환까지 해 주므로, Terraform state에는 비밀의 위치(ARN)만 남습니다.

④ store 블록 — 의도적으로, 통제하며 보관한다 (1.16)

ephemeral "random_password" "initial" {
  length = 20
}

resource "terraform_data" "initial_password" {
  store {
    input     = ephemeral.random_password.initial.result # write-only: ephemeral 값을 받을 수 있다
    sensitive = true                                     # → store.sensitive_output 에 저장 (false면 store.output)
    version   = 1                                        # 이 숫자가 바뀔 때만 저장 값을 갱신
    # replace = true  ← 저장 값이 바뀔 때 리소스를 교체로 처리
  }
}

output "initial_password" {
  value     = terraform_data.initial_password.store.sensitive_output
  sensitive = true
}

store 블록은 ①~③과 방향이 반대입니다. ephemeral 값을 state에 저장합니다. 왜 필요할까요? ephemeral 리소스는 매번 새 값을 만들기 때문에, “최초 1회 생성한 값을 계속 같은 값으로 써야 하는” 경우(초기 관리자 비밀번호를 다른 리소스 여러 곳에 쓰고, 출력으로 운영자에게 한 번 전달하는 등)에 그 값을 붙잡아 둘 곳이 없었습니다. store는 그 보관을 명시적인 선택으로 만들고, sensitive로 표시하고, version으로 언제 바뀌는지 통제합니다.

즉 store를 쓰면 그 값은 다시 state 보안(11장)에 의존하게 됩니다. 판단 기준은 이렇습니다: 비밀을 외부 비밀 저장소로 보낼 수 있다면 ③, 저장소가 대신 관리해 준다면 그것(RDS 관리형 비밀번호 등), 정말 Terraform이 기억해야만 한다면 ④.

11state 보안과 유출 사고

state가 새는 경로는 생각보다 단순하고, 반복된다

보안 연구와 버그 바운티 보고에서 공개된 .tfstate 파일은 반복해서 등장하는 단골 항목입니다. 아래는 특정 회사의 사건이 아니라, 반복적으로 보고되는 유형을 재구성한 시나리오입니다. 각 유형의 “막는 장치”가 이 강의의 어느 부분에 있는지 함께 표시했습니다.

유형 1. Git 저장소에 커밋된 state가장 흔함

초기에 로컬 state로 시작한 프로젝트를 Git에 올리면서 terraform.tfstate까지 커밋. 나중에 파일을 지워도 커밋 이력에 영원히 남는다. 저장소가 공개로 바뀌거나 외주사에 공유되는 순간 노출.

결과DB 비밀번호, IAM 액세스 키(코드로 키를 만든 경우), 내부 IP·도메인 구조 전부
막는 장치2편 .gitignore, gitleaks pre-commit, 처음부터 원격 백엔드. 이미 커밋했다면 이력 정리보다 비밀 교체가 먼저

유형 2. 공개 설정된 state 버킷설정 실수

정적 웹사이트용으로 공개한 버킷에 state도 함께 두거나, 디버깅 중 버킷 정책을 넓게 열어 두고 잊음. 자동 스캐너가 흔한 이름(*-tfstate, *-terraform)의 버킷을 끊임없이 찾는다.

결과익명으로 state 다운로드
막는 장치state 전용 버킷, 퍼블릭 접근 차단(계정 수준까지), TLS 강제 정책, 실습 B의 버킷 구성

유형 3. 웹 서버·CDN 경로에 함께 배포된 state배포 실수

배포 스크립트가 작업 디렉터리를 통째로 웹 루트나 CDN 원본 버킷에 동기화. /terraform.tfstate, /terraform.tfstate.backup이 URL로 열린다.

결과누구나 브라우저로 다운로드
막는 장치로컬 state 사용 금지, 배포 대상 디렉터리와 IaC 디렉터리 분리, 동기화 제외 규칙

유형 4. 과도한 읽기 권한과 CI 로그내부 노출

“읽기만 하니까 괜찮다”며 개발자 전원에게 state 버킷 읽기 권한을 주거나, CI 로그에 terraform show·output -json 결과를 그대로 남김. terraform_remote_state로 다른 팀 state를 읽게 하면서 그 state 전체 읽기 권한을 줌.

결과내부자·외주 인력·로그 보관 시스템으로 비밀 확산
막는 장치경로 단위 최소 권한, CloudTrail 데이터 이벤트, 출력 sensitive 표시, 12장의 remote_state 대안, 10장의 비밀 미저장

유출이 의심될 때의 대응 순서

  1. 차단: 공개 경로 제거(버킷 정책 복구, 파일 삭제, 저장소 비공개 전환). 단, 이미 복사되었다고 가정한다.
  2. 비밀 교체가 최우선: state 안의 모든 비밀(DB 비밀번호, 액세스 키, 토큰, 개인키)을 새로 발급하고 옛 것을 폐기. Git 이력 정리는 그다음이다.
  3. 악용 흔적 조사: CloudTrail에서 노출된 키의 사용 기록, 낯선 리전·IP의 API 호출, 새 IAM 사용자·키 생성 여부. 공개 저장소에 노출된 AWS 키는 자동 스캐너에 매우 빨리 발견되는 것으로 널리 알려져 있으며, AWS도 노출을 탐지하면 해당 키에 격리 정책을 붙이고 알려 줍니다.
  4. 고객 보고: MSP라면 계약상 보안 사고 통지 의무를 확인하고 고객 보안 담당과 즉시 공유.
  5. 재발 방지: 원인 유형에 맞는 장치를 추가하고 회고 문서화.
state 보안 체크리스트 (복사해서 쓰세요)

□ state는 원격 백엔드에만 (로컬·Git 금지) □ 버킷 퍼블릭 차단·TLS 강제·기본 암호화 □ 버전닝 + 수명 주기 □ 경로 단위 최소 권한, 읽기 권한도 통제 □ 접근 기록(CloudTrail 데이터 이벤트) □ state에 비밀을 넣지 않는 설계(ephemeral·write-only·외부 관리) □ 출력은 sensitive 표시 □ CI 로그에 state·plan 내용을 남기지 않음 □ plan 파일 커밋 금지 □ 유출 시 비밀 교체 절차 문서화

닭과 달걀 문제

state를 저장할 버킷도 Terraform으로 만들고 싶은데, 그 버킷을 만드는 코드의 state는 어디에 둘까요? 표준 해법은 부트스트랩입니다. ① 버킷 코드를 로컬 state로 apply ② 버킷이 생기면 그 코드에 backend 블록을 추가해 자기 자신의 state를 방금 만든 버킷으로 옮김(선택). 이 버킷은 이후 모든 편에서 계속 씁니다.

terraform {
  required_version = "~> 1.16.0"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}

provider "aws" {
  region = "ap-northeast-2"
  default_tags {
    tags = { Project = "iac-lab", ManagedBy = "terraform", Purpose = "tfstate" }
  }
}

data "aws_caller_identity" "me" {}

locals {
  # 계정 ID를 붙여 전 세계에서 유일한 이름을 만든다
  bucket_name = "iac-lab-tfstate-${data.aws_caller_identity.me.account_id}"
}

resource "aws_s3_bucket" "state" {
  bucket = local.bucket_name

  # state 버킷은 terraform destroy로 지워지면 안 된다 (11편)
  lifecycle {
    prevent_destroy = true
  }
}

resource "aws_s3_bucket_versioning" "state" {
  bucket = aws_s3_bucket.state.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "state" {
  bucket = aws_s3_bucket.state.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256" # 고객사 운영이라면 aws:kms + 고객 관리형 키 검토
    }
  }
}

resource "aws_s3_bucket_public_access_block" "state" {
  bucket                  = aws_s3_bucket.state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_ownership_controls" "state" {
  bucket = aws_s3_bucket.state.id
  rule {
    object_ownership = "BucketOwnerEnforced"
  }
}

resource "aws_s3_bucket_policy" "state" {
  bucket = aws_s3_bucket.state.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "DenyInsecureTransport"
      Effect    = "Deny"
      Principal = "*"
      Action    = "s3:*"
      Resource  = [aws_s3_bucket.state.arn, "${aws_s3_bucket.state.arn}/*"]
      Condition = { Bool = { "aws:SecureTransport" = "false" } }
    }]
  })
  # 퍼블릭 차단 설정이 먼저 적용된 뒤 정책을 건다
  depends_on = [aws_s3_bucket_public_access_block.state]
}

resource "aws_s3_bucket_lifecycle_configuration" "state" {
  bucket = aws_s3_bucket.state.id
  rule {
    id     = "expire-old-state-versions"
    status = "Enabled"
    filter {}
    noncurrent_version_expiration {
      noncurrent_days = 90 # 이전 판은 90일 보관
    }
    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }
  # 버전닝이 켜진 뒤에 수명 주기 규칙을 건다
  depends_on = [aws_s3_bucket_versioning.state]
}

output "state_bucket" {
  value = aws_s3_bucket.state.bucket
}

복구는 “장부를 되돌리는 것”이지 “인프라를 되돌리는 것”이 아니다

S3 버전 복구는 state를 예전 판으로 바꿀 뿐 클라우드는 그대로입니다. 장부와 실물이 어긋난 상태가 되므로, 복구 직후의 plan은 매우 신중하게 읽어야 합니다. 복구가 필요한 상황은 대개 “state가 깨졌거나 잘못 덮어써진 경우”이고, 그때는 가장 최근의 정상 판을 고르는 것이 핵심입니다.

6편 이후의 실습 state는 이 버킷에 둡니다. 저장되는 데이터가 KB 단위라 비용은 사실상 0입니다. 강의를 모두 마친 뒤 정리할 때는 prevent_destroy를 false로 바꾸고, 버킷 안의 모든 객체 버전까지 지운 다음(버전닝 버킷은 객체만 지워서는 비워지지 않음) destroy합니다. 이 절차는 강의 마지막에 다시 안내합니다.

16MSP 현장 팁

고객사 state를 맡는다는 것의 무게

state 버킷을 어느 계정에 둘까

고객 계정 안: 데이터 주권이 명확하고 계약 종료 시 그대로 인계. 대신 고객마다 버킷·권한 설정을 반복. MSP 중앙 계정: 관리가 한곳에 모이지만 고객 비밀이 MSP 계정에 쌓이고, 계약 종료 시 이전 작업이 필요. 많은 MSP가 “고객 계정 안 + 표준 부트스트랩 모듈”을 택합니다(25편).

state는 고객 데이터다

고객 DB 비밀번호와 네트워크 구조가 들어 있을 수 있으므로 계약서의 고객 정보 보호 조항이 그대로 적용됩니다. 접근자 목록, 접근 기록 보관 기간, 퇴사자 권한 회수 절차를 문서화하세요. 보안 인증 심사에서 자주 묻는 항목입니다.

접근 기록 켜 두기

CloudTrail의 S3 데이터 이벤트를 state 버킷에만 켜면 누가 언제 state를 읽고 썼는지 남습니다. 버킷 하나에 한정하면 비용 부담도 작습니다. 이상 접근(업무 시간 외, 낯선 주체) 알림까지 걸면 유출을 조기에 잡을 수 있습니다.

잠금 해제는 절차로

force-unlock은 “누가, 왜, 누구 확인을 받고” 했는지 티켓에 남기는 절차로 만드세요. 새벽 장애 대응 중 남의 apply 잠금을 풀어 state를 깨뜨리는 사고는 실제로 자주 일어납니다.

key 규칙과 권한 경계를 일치

<고객>/<환경>/<구성요소> key 규칙을 정하면 IAM 정책도 같은 경로 단위로 쓸 수 있습니다. 운영(prd) 경로는 CI 역할만 쓰기 가능, 사람은 읽기도 제한하는 식으로 운영계를 보호합니다.

인수인계·종료 체크리스트

고객 계약 종료 시: state 최신본과 버전 이력 인계 범위 합의, MSP 측 사본·로컬 백업 폐기 확인, state 안 비밀 교체 권고, MSP 계정의 접근 권한 회수. state를 넘기지 않으면 고객은 import로 처음부터 다시 흡수해야 합니다.

예시
terraform state pull | jq -r '
