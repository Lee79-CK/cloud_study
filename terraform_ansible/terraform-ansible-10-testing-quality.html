Terraform & Ansible 강의 · Level 2 Terraform 심화·운영 · 10편 / 26편 · 시리즈 목차

기계가 먼저 읽게 하라 테스트와 코드 품질 — fmt·validate, tflint, trivy·checkov, terraform test(mock·통합), terraform-docs, pre-commit

6~9편에서 만든 모듈은 이제 여러 환경과 고객이 함께 씁니다. 모듈 한 줄을 고칠 때마다 사람이 plan을 일일이 읽어 “이게 무엇을 깨뜨리는가”를 판단하기는 어렵습니다. 이번 편은 그 판단의 상당 부분을 기계에 맡기는 관문들을 세웁니다. 그리고 실제로 이 강의의 모듈에 테스트와 스캐너를 돌려, 7편 RDS 모듈의 숨은 버그 하나를 찾아 고칩니다.

정적 검사

fmt · validate · tflint. 몇 초, 커밋할 때마다.

보안 스캔

trivy · checkov. 위험한 설정을 코드 단계에서.

테스트

terraform test. mock으로 논리를, 실제 apply로 통합을.

이번 편의 목표와 실습 지도

이번 편을 마치면

  • 품질 관문의 층(포맷 → 문법 → 린트 → 보안 → 단위 테스트 → 통합 테스트)과 각 층이 잡는 것, 어디서 돌릴지를 설명할 수 있습니다.
  • tflint와 AWS 규칙 플러그인을 설정하고 결과를 해석·예외 처리할 수 있습니다.
  • trivy와 checkov 결과를 “고친다 / 정당한 예외 / 오탐”으로 분류하고, 이유를 남긴 인라인 예외를 씁니다.
  • terraform test의 run·assert·variables·expect_failures·module·run 출력 참조를 씁니다.
  • mock_provider·mock_data·override_*로 클라우드 없이 모듈 논리를 테스트하고, 통합 테스트와 구분합니다.
  • terraform-docs와 pre-commit으로 이 모든 것을 커밋 단계에 묶습니다.

이번 편을 만들며 AWS 프로바이더(6.70)를 검증 환경에 설치할 수 있게 되어, 3·4·5·6·7·9편의 모든 AWS 실습 코드를 실제 프로바이더 스키마로 validate해 전부 통과하는 것을 확인했습니다. 이 편의 테스트 결과(통과·실패 출력), tflint·trivy(0.76.1)·checkov(3.3.30) 결과, terraform-docs 출력도 모두 실제 실행 결과입니다. 실행은 Terraform과 같은 테스트 문법을 지원하는 호환 엔진으로 했고, 1.15 전용 문법(출력 type)만 그때 잠시 걷어 냈습니다.

1품질 관문의 층

빠르고 싼 검사를 먼저, 느리고 비싼 검사를 나중에 — 층을 눌러 보세요

층을 선택하세요

위로 갈수록 빠르고 자주, 아래로 갈수록 느리고 드물게 돌립니다. 각 층은 아래 층이 잡을 수 없는 것을 잡습니다.

plan 리뷰를 대체하는 것이 아니다

이 관문들은 사람의 plan 리뷰를 없애지 않습니다. 기계가 반복적이고 기계적인 실수(포맷, 오타, 잘못된 인스턴스 유형, 암호화 누락, 계약 위반)를 걸러 주면, 사람은 “이 변경이 의도한 것인가”라는 판단에 집중할 수 있습니다. 12편의 CI가 이 관문들을 PR마다 자동으로 돌립니다.

2fmt와 validate

가장 싸고, 가장 자주, 가장 많이 잡는 두 명령

terraform fmt -check -diff -recursive    # 고치지 않고 차이만 보고, 다르면 종료 코드 3 (CI용)
terraform fmt -recursive                 # 실제로 고침 (pre-commit 훅이 하는 일)
terraform init -backend=false            # validate에는 프로바이더 스키마가 필요. 백엔드 연결은 불필요
terraform validate

3tflint

validate가 통과시키는 “문법은 맞지만 틀린” 코드를 잡는다

.tflint.hcl (리포 루트, 2편 설정에 AWS 규칙 추가)
config {
  # 로컬 경로 모듈 호출까지 따라 들어가 검사한다
  call_module_type = "local"
}

plugin "terraform" {
  enabled = true
  preset  = "recommended"
}

plugin "aws" {
  enabled = true
  version = "0.49.0"
  source  = "github.com/terraform-linters/tflint-ruleset-aws"
}
tflint --init                                  # 플러그인 설치 (GitHub 릴리스, 서명 검증)
tflint --recursive --config="$(pwd)/.tflint.hcl"   # 모든 하위 디렉터리
tflint --chdir=modules/vpc                     # 한 디렉터리만

일부러 문제를 넣은 파일에 tflint 0.64.0 + AWS 규칙 0.49.0을 실제로 돌린 결과입니다. validate는 이 파일을 통과시킵니다.

resource "aws_instance" "legacy" {
  # tflint-ignore: aws_instance_previous_type # 고객 라이선스가 이 유형에 묶여 있음 (2026-12 교체 예정)
  instance_type = "t2.medium"
}
플러그인 설치가 막힐 때

tflint --init은 플러그인 서명을 sigstore로 검증합니다. 사내 프록시·망분리 환경에서 검증 서버에 닿지 못하면 설치가 실패합니다. 이때는 GitHub 릴리스의 플러그인 zip을 받아 ~/.tflint.d/plugins/github.com/terraform-linters/tflint-ruleset-aws/0.49.0/에 풀어 두면 됩니다(이 강의 검증 환경에서도 이 방법을 썼습니다). 받은 파일의 체크섬은 릴리스의 checksums.txt와 대조하세요.

4보안 스캔: trivy·checkov

코드 단계에서 잡는 잘못된 설정 — 그리고 결과를 읽는 법

trivy(Aqua Security)와 checkov(Prisma Cloud)는 Terraform 코드를 읽어 보안 모범 사례에 어긋나는 설정을 찾는 정적 분석기입니다. 둘 다 오픈소스이고 규칙 수백 개를 내장합니다. 이 강의의 7편 모듈에 실제로 돌린 결과를 아래에서 직접 분류해 보세요.

실측 결과 분류 — 각 발견 항목을 어떻게 처리할지 고른 뒤 확인하세요

모듈checkov 3.3.30 (실패/통과)trivy 0.76.1 (실패)
vpc3 / 111 (플로 로그 MEDIUM)
alb7 / 192 (퍼블릭 노출 HIGH, HTTP 리스너 CRITICAL)
app-servers5 / 320
rds-postgres6 / 222 (성능 개선 도우미 LOW, IAM 인증 MEDIUM)

같은 코드에 두 스캐너가 다른 결과를 냅니다. checkov는 규칙이 더 많고 운영 모범 사례(모니터링·로그)까지 보며, trivy는 심각도 등급이 분명하고 보안 핵심에 집중하는 편입니다. 둘 중 하나를 표준으로 정하거나, trivy를 높은 심각도 관문으로·checkov를 참고 리포트로 쓰는 식으로 역할을 나눕니다.

예외는 이유와 함께, 리소스 옆에

#trivy:ignore:AWS-0053
resource "aws_lb" "this" {
  #checkov:skip=CKV2_AWS_28:WAF는 25편 MSP 표준 구성에서 별도 모듈로 붙인다
  name               = var.name
  load_balancer_type = "application"
  internal           = false
  # ...
}

실측: 위 두 줄을 추가하자 checkov는 “Skipped checks: 1”, trivy는 AWS-0053이 빠지고 AWS-0054(HTTP 리스너) 하나만 남았습니다. 예외를 전역 설정 파일에 몰아 두면 “어디에, 왜”가 사라지므로, 리소스 옆에 이유를 적는 방식을 기본으로 합니다. 예외에는 만료일이나 관련 티켓 번호를 적어 두면 감사 때 설명이 쉽습니다.

trivy config --severity HIGH,CRITICAL modules/          # 높은 심각도만 (CI 관문)
trivy config --skip-check-update modules/alb            # 규칙 갱신 없이 내장 규칙으로 (오프라인)
checkov -d modules/ --framework terraform --compact --quiet
checkov -d modules/ --skip-check CKV_AWS_126,CKV_AWS_135  # 조직 정책상 제외하는 규칙

5terraform test 기초

Terraform 언어로 쓰는 Terraform 테스트 (1.6+)

terraform test는 .tftest.hcl 파일을 찾아 그 안의 run 블록들을 차례로 실행합니다. 각 run은 모듈에 대해 plan 또는 apply를 하고, assert로 결과를 검사합니다. 테스트가 apply로 만든 리소스는 테스트가 끝나면 Terraform이 역순으로 지웁니다. 테스트 파일은 모듈 루트나 tests/ 디렉터리에 둡니다.

요소설명
run "이름" { }테스트 한 단계. 위에서 아래로 순서대로 실행, 앞 run의 state를 이어받는다
command = plan | apply기본은 apply. 논리 검사는 plan으로 충분하고 빠르다
variables { }파일 수준(모든 run 공통) 또는 run 수준(그 run만 덮어씀). 테스트 파일의 변수가 가장 높은 우선순위
assert { condition, error_message }검사. 리소스 속성, output.이름, 지역 값 등 모듈 안의 값을 참조
expect_failures = [var.x]“이 검사가 실패해야 정상” — 변수 validation, precondition, check 블록이 제대로 막는지 테스트
module { source = "…" }이 run에서는 테스트 대상 대신 다른 모듈(준비용 도우미)을 실행
run.이름.출력앞 run의 출력을 다음 run의 변수로 (준비 → 검사 연결)
plan_options { mode, refresh, replace, target }refresh-only, 교체 지정 등 plan 옵션
providers = { … }run별로 쓸 프로바이더 설정 지정 (별칭)
state_key, parallelrun이 쓸 내부 state 지정, 독립된 run의 병렬 실행 (파일의 test { parallel = true }와 함께)
# 가장 작은 테스트: label 모듈 (프로바이더 없음, plan만)
variables {
  project = "custa"
  env     = "dev"
  owner   = "hong-gildong"
}

run "name_with_component" {
  command = plan

  variables {
    component = "web"
  }

  assert {
    condition     = output.name == "custa-dev-web"
    error_message = "이름 규칙은 project-env-component 여야 합니다."
  }
}

run "rejects_unknown_env" {
  command = plan

  variables {
    env = "prod"
  }

  expect_failures = [var.env] # validation이 막아야 테스트 통과
}
cd ~/iac-lab/modules/label
terraform init
terraform test                                   # tests/*.tftest.hcl 과 루트의 *.tftest.hcl 모두
terraform test -filter=tests/unit.tftest.hcl     # 특정 파일만
terraform test -verbose                          # run마다 plan·state 내용까지 출력

6mock 프로바이더와 override

클라우드 없이, 자격증명 없이, 몇 초 만에 — 단위 테스트 (1.7+)

mock_provider를 선언하면 그 테스트 파일에서는 진짜 프로바이더 대신 가짜가 응답합니다. 리소스를 “만들면” 계산되는 속성(ID 등)에 임의 값을 채워 주고, data 소스는 빈 값이나 지정한 기본값을 돌려줍니다. 클라우드 API를 전혀 부르지 않으므로 자격증명이 없어도 되고 비용도 없습니다.

mock_provider "aws" {
  # data 소스가 돌려줄 값을 정한다 (리전·AZ처럼 모듈 논리가 기대는 값)
  mock_data "aws_availability_zones" {
    defaults = {
      names = ["ap-northeast-2a", "ap-northeast-2b", "ap-northeast-2c"]
    }
  }

  # 특정 리소스의 계산 속성을 고정한다 (지정하지 않으면 임의 문자열)
  mock_resource "aws_vpc" {
    defaults = {
      id = "vpc-0mock000000000001"
    }
  }
}

run "uses_fixed_vpc_id" {
  command = apply

  assert {
    condition     = output.vpc_id == "vpc-0mock000000000001"
    error_message = "mock_resource 기본값이 출력에 반영되어야 합니다."
  }
}
도구범위쓰임
mock_provider테스트 파일의 해당 프로바이더 전체클라우드 없는 단위 테스트
mock_resource / mock_data그 프로바이더의 특정 리소스·data 종류 전부계산 속성·조회 결과 고정
override_resource / override_data특정 주소 하나 (파일 또는 run 안에 선언)“이 data 소스만 이 값을 돌려준다” (진짜 프로바이더와 함께도 가능)
override_module자식 모듈 호출 하나의 출력무거운 하위 모듈을 건너뛰고 출력만 흉내
mock이 알려 주지 않는 것

가짜 프로바이더는 AWS의 실제 규칙을 모릅니다. 존재하지 않는 AMI, 이미 쓰는 이름, 권한 부족, 서비스 한도, 리전에 없는 인스턴스 유형은 통과합니다. mock 테스트가 증명하는 것은 모듈의 논리(분기·계산·기본값·계약)까지이고, “실제로 만들어지는가”는 7장의 통합 테스트가 증명합니다. 또 프로바이더가 계산하는 중첩 블록은 mock에서 빈 목록이 되므로, 그 값을 [0]으로 꺼내는 코드는 테스트에서 실패합니다. 12장에서 이것이 실제 버그를 찾아냅니다.

주제설명
정리(cleanup)테스트 파일 단위로 끝나면 만든 리소스를 모두 destroy. 중간에 강제 종료되거나 삭제가 실패하면 실물이 남으므로, 통합 테스트는 전용 샌드박스 계정에서 돌리고 태그·만료일을 붙인다(2편 9장)
비용·시간RDS·EKS 같은 느리고 비싼 리소스의 통합 테스트는 매 PR이 아니라 야간·릴리스 전으로. VPC처럼 무료이고 빠른 것은 PR마다도 가능
파일 분리단위(mock)와 통합(실제)을 다른 파일로 두고 -filter로 골라 실행. mock_provider는 선언된 파일에만 적용된다
병렬test { parallel = true } + 독립된 run. 서로 다른 state를 쓰는 run만 동시에 실행된다
결과 보고CI 화면에 결과를 붙이려면 JUnit XML 출력 옵션(-junit-xml=파일)을 쓴다(12편)
백엔드 지정 (실험)run 블록에 backend 블록을 두어 매번 빈 state로 시작하지 않고 오래 유지되는 테스트 인프라를 재사용하는 기능, 그리고 skip_cleanup·terraform test cleanup이 개발 중입니다. 2026년 10월 현재 알파 빌드의 실험 기능(1.17 alpha)이라 정식 버전에서는 쓸 수 없습니다. 정식 출시되면 “공유 VPC는 남겨 두고 그 위의 앱만 매번 테스트” 같은 흐름이 가능해집니다
Terratest와의 관계

terraform test 이전에는 Go로 테스트를 쓰는 Terratest가 사실상 표준이었습니다. 지금도 “만든 뒤 HTTP 요청을 보내 응답을 확인”처럼 Terraform 바깥의 동작을 검증하는 끝단(E2E) 테스트에는 Terratest나 일반 스크립트가 유용합니다. 모듈의 논리·계약 검증은 이 강의처럼 terraform test로 충분하고, 팀이 Go를 몰라도 됩니다.

8모듈 테스트 전략

무엇을 테스트하고, 무엇은 테스트하지 않는가

테스트할 것예 (이 강의 모듈)방법
계산·분기 논리서브넷 CIDR 계산, NAT 끔/단일/AZ별 분기, 이름 규칙mock + plan, assert
안전한 기본값RDS 삭제 방지·암호화·비공개·관리형 비밀번호, NAT 기본 꺼짐mock + plan, 변수 없이 기본값 검사
입력 검증(계약)잘못된 이름·CIDR·AZ 수, 서브넷 1개expect_failures
표준 보호표준 태그를 덮어쓸 수 없음plan, output 검사
출력 계약출력 이름·모양·개수mock + apply, output 검사
실제 생성 가능성VPC·엔드포인트가 실제 리전에서 만들어지는가통합 테스트 (야간)

테스트하지 않을 것

프로바이더가 이미 보장하는 것(“aws_vpc를 선언하면 VPC가 생긴다”), 입력을 그대로 출력하는 것, 리소스 인자 하나하나의 값 복사. 이런 테스트는 코드를 바꿀 때마다 같이 고쳐야 해서 유지 비용만 늘어납니다.

버그를 고칠 때마다 테스트 하나

모듈에서 버그가 나오면, 그 버그를 재현하는 테스트를 먼저 쓰고(실패 확인) 고칩니다(통과 확인). 12장의 RDS 출력 버그가 그 예입니다. 같은 버그가 다시 들어오는 것을 영구히 막습니다.

어디서 돌리나무엇을시간
저장할 때 (편집기)fmt, validate1초
커밋할 때 (pre-commit)fmt, validate, tflint, terraform-docs, trivy(높은 심각도), gitleaks수 초~수십 초
PR마다 (CI)위 전부 + mock 단위 테스트 + checkov 리포트 + plan1~3분
야간·릴리스 전통합 테스트 (샌드박스 계정)수 분~수십 분

15MSP 현장 팁

공통 모듈 저장소의 품질 관문을 운영하기

공통 모듈은 테스트 없이 병합하지 않는다

공통 모듈의 버그는 모든 고객사로 퍼집니다. 모듈 저장소의 병합 조건에 “mock 단위 테스트 통과, trivy HIGH·CRITICAL 0(또는 사유 있는 예외), tflint 통과, README 갱신”을 넣고 브랜치 보호 규칙으로 강제합니다.

보안 기준을 코드로 합의

고객사 보안 담당과 “어떤 스캐너 규칙을 필수로, 어떤 것을 예외로” 정한 목록을 저장소에 둡니다(.checkov.yaml, trivy 설정). 보안 점검 때마다 같은 논쟁을 반복하지 않게 됩니다.

통합 테스트 전용 계정

통합 테스트는 고객 계정이 아니라 MSP의 샌드박스 계정에서, 예산 알림과 정리 자동화를 걸고 돌립니다. 테스트가 실패해 리소스가 남는 경우를 대비해 태그 기반 주간 정리 작업을 둡니다.

고객 리포에도 최소 관문

고객별 라이브 저장소(8편)에는 fmt·validate·tflint·trivy와 plan만 둬도 충분합니다. 테스트는 모듈 저장소에서, 라이브 저장소는 “올바른 값으로 올바른 버전을 부르는가”를 plan으로 확인합니다.

스캐너 버전도 고정

스캐너는 규칙이 자주 추가됩니다(이번 검증에서도 최근 추가된 규칙 CKV_AWS_394가 보였습니다). 버전을 고정하지 않으면 어느 날 아무 변경 없이 CI가 실패합니다. 버전을 고정하고, 업그레이드는 PR로 결과 차이를 보고 합니다.

테스트는 문서다

테스트 파일의 run 이름과 error_message는 “이 모듈이 무엇을 보장하는가”의 목록입니다. 인수인계 때 README보다 테스트 파일이 더 정확한 사양서가 됩니다.

18과제

실습 A~C를 마친 뒤에 풀어 보세요

과제 1. VPC 플로 로그 옵션 추가 + 테스트 먼저

VPC 모듈에 enable_flow_logs(기본 false)를 추가하세요. 켜면 CloudWatch Logs 로그 그룹(보존 기간 변수), IAM 역할, aws_flow_log를 만듭니다. 테스트를 먼저 쓰세요: “기본값이면 플로 로그 리소스 0개”, “켜면 1개이고 보존 기간이 입력값과 같다”. 테스트가 실패하는 것을 확인한 뒤 구현해 통과시킵니다. 그다음 checkov·trivy 결과에서 플로 로그 항목이 어떻게 바뀌는지 확인하세요.

힌트

스캐너는 기본값 false인 경로를 여전히 실패로 볼 수 있습니다. 모듈은 기본값을 false로 두고(비용), 고객 라이브 저장소에서 true로 켜는 구조라면 모듈의 해당 줄에 “호출자가 켬, 운영 환경 tfvars에서 강제” 사유로 예외를 둡니다. 플로 로그는 로그 저장 비용이 들므로 실습 후 끕니다.

과제 2. ALB 모듈 테스트

7편 ALB 모듈에 mock 테스트를 작성하세요. 검사할 것: 허용 CIDR 수만큼 인바운드 규칙, ALB 이름 27자 이상이면 거부, 서브넷 1개면 거부, drop_invalid_header_fields가 켜져 있음.

과제 3. override_data로 AMI 고정

app-servers 모듈 테스트에서 override_data로 data.aws_ami.al2023의 id를 고정하고, 서버 3대일 때 web3가 첫 번째 서브넷에 배치되는지(7편 6장의 순환 배치) 검사하세요.

힌트

override_data { target = data.aws_ami.al2023 values = { id = "ami-0test" } }. 서브넷은 변수로 ["subnet-a","subnet-b"]를 주고 aws_instance.this["web3"].subnet_id == "subnet-a"를 검사합니다.

과제 4. 스캐너 결과를 보고서로

checkov를 -o json으로, trivy를 --format json으로 실행해 결과를 합친 뒤 “모듈 / 규칙 / 심각도 / 판단(고침·예외·오탐) / 사유” 표(CSV)로 만드는 스크립트를 작성하세요. 13장의 분류를 그대로 옮기면 됩니다.

과제 5. 테스트가 잡는 breaking change

6편 3장의 breaking change 판정기 항목 중 세 가지(필수 변수 추가, 출력 모양 변경, validation 강화)를 VPC 모듈에 실제로 적용해 보고, 지금의 단위 테스트가 각각을 잡는지 확인하세요. 잡지 못하는 것이 있다면 그것을 잡는 테스트를 추가하세요.

해설

필수 변수 추가는 테스트 파일의 변수에 없으므로 모든 run이 실패해 바로 드러납니다. validation 강화는 경계값을 검사하는 run이 있을 때만 잡힙니다(az_count = 4가 통과해야 한다는 run을 추가). 출력 모양 변경은 length(output.public_subnet_ids) == 2 같은 검사로는 리스트·맵 모두 통과할 수 있으므로, output.public_subnet_ids["ap-northeast-2a"]처럼 키 접근을 검사해야 잡힙니다. 계약을 테스트로 표현할 때는 “모양”까지 검사해야 한다는 교훈입니다.
