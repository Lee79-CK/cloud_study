GPU는 클러스터에서 가장 비싸고 가장 다툼이 많은 자원입니다. 한 장을 여럿이 나눠 쓰고, 분산 학습이 반쯤만 뜬 채 GPU를 붙잡는 일을 막고, 팀마다 몫을 나누되 놀고 있는 몫은 빌려 쓰게 하는 방법을 다룹니다.

이번 편에서 얻을 것

7편에서 분산 학습의 일부 노드만 뜨고 나머지는 Pending인 문제를, 6편과 8편에서 병렬 실행이 할당량을 넘기는 문제를 예고만 했습니다. 이번 편에서 해결합니다. 이 편을 마치면 다음을 할 수 있습니다.

  • GPU Operator의 구성요소를 알고, GPU가 Kubernetes 자원으로 보이기까지의 과정과 노드 라벨을 설명할 수 있습니다.
  • time-slicing, MPS, MIG의 차이를 알고 쓰임에 맞게 골라, MIG 구성을 직접 계획할 수 있습니다.
  • 분산 학습이 반쯤만 배치되는 문제의 원인과, Kueue, Volcano 같은 해결책을 설명할 수 있습니다.
  • Kueue의 ResourceFlavor, ClusterQueue, LocalQueue로 팀별 GPU 몫과 빌려 쓰기, 선점을 설계하고 TrainJob, Katib, 파이프라인을 큐에 연결할 수 있습니다.

1GPU가 클러스터에 보이기까지

노드에 GPU 카드를 꽂는 것만으로 Pod가 GPU를 쓸 수 있는 것은 아닙니다. 드라이버, 컨테이너 런타임 연동, 장치 플러그인이 모두 맞물려야 합니다. NVIDIA GPU Operator는 이것들을 모두 Kubernetes 위의 컨테이너로 설치하고 관리합니다.

구성요소하는 일
드라이버노드에 NVIDIA 드라이버를 컨테이너로 설치. 노드 OS에 미리 설치된 드라이버를 쓰게 할 수도 있음
Container Toolkit컨테이너 런타임이 GPU 장치와 드라이버 라이브러리를 컨테이너 안에 연결하게 해 줌
장치 플러그인GPU를 nvidia.com/gpu라는 자원으로 Kubernetes에 알리고, Pod에 장치를 배정. time-slicing과 MPS 설정도 여기서
GPU Feature DiscoveryGPU 모델, 메모리, 개수 등을 노드 라벨로 붙임(예: nvidia.com/gpu.product, nvidia.com/gpu.memory)
DCGM ExporterGPU 사용률, 메모리, 온도 등을 Prometheus 지표로 내보냄(9장, 15편)
MIG Manager노드 라벨에 적은 구성대로 MIG 분할을 적용(3장)
Validator설치가 끝나면 GPU를 실제로 쓸 수 있는지 시험
 
kubectl get pods -n gpu-operator                          # 설치 네임스페이스는 구성에 따라 다름
kubectl describe node <gpu-노드> | grep -A3 nvidia.com/gpu   # 용량과 할당 가능량
kubectl get nodes -L nvidia.com/gpu.product,nvidia.com/gpu.count

2편에서 쓴 nvidia.com/gpu.present=true 같은 라벨도 이 구성요소들이 붙입니다. 3편의 kind 클러스터에서 GPU 실습을 하지 않은 이유가 이것입니다. kind 노드는 컨테이너라서 이 체계를 갖추기가 번거롭습니다.

2GPU 한 장을 나눠 쓰는 법

기본 상태에서 GPU는 정수로만 배정됩니다. 노트북에서 가끔 쓰는 정도인데 80GB GPU 한 장을 통째로 쥐고 있으면 낭비입니다. 나눠 쓰는 방법은 셋입니다.

방식원리메모리 보호성능 격리지원 GPU어울리는 곳
통째로한 장을 한 컨테이너가 독점완전완전모두학습, 큰 모델 서빙
time-slicing여러 프로세스가 시간을 나눠 번갈아 씀. 한 장을 여러 개로 부풀려 알림없음. 한 프로세스가 메모리를 다 쓰면 다른 쪽이 CUDA OOM없음대부분노트북, 개발, 가벼운 추론
MPS여러 프로세스의 작업을 한 GPU에서 동시에 실행클라이언트별 한도 설정 가능부분적대부분작은 추론 여러 개
MIGGPU를 하드웨어 수준에서 최대 7개의 독립 인스턴스로 분할완전완전A100, H100, H200 등 데이터센터 GPU여러 팀의 추론, 격리가 필요한 멀티테넌시

time-slicing 설정 예 (장치 플러그인 설정, 단순화)

version: v1
sharing:
  timeSlicing:
    resources:
    - name: nvidia.com/gpu
      replicas: 4           # GPU 1장을 nvidia.com/gpu 4개로 알림
time-slicing은 칸막이가 아닙니다

4개로 나뉘어 보이지만 메모리는 공유합니다. 노트북 하나가 GPU 메모리를 다 잡으면 같은 GPU의 다른 노트북들이 CUDA out of memory로 죽습니다. 그리고 4개를 요청한 Pod도 실제로는 GPU 1장을 나눠 쓰는 것이라 4배 빠르지 않습니다. 학습과 운영 서빙에는 쓰지 않고, 노트북과 개발용 노드 풀에만 적용하는 것이 안전합니다.

3MIG 나눠 보기

MIG는 GPU의 연산 장치를 7조각(compute slice), 메모리를 8조각으로 나누고, 그 조각들을 묶어 인스턴스를 만듭니다. 인스턴스 이름의 3g.40gb는 연산 3조각과 메모리 40GB라는 뜻입니다. H100 80GB 한 장을 어떻게 나눌지 계획해 보세요. 만든 조각을 누르면 지웁니다.

연산 조각 (7개)

메모리 (80GB)

실제 MIG에는 조각을 놓을 수 있는 위치에 대한 규칙이 더 있어서, 합계가 맞아도 만들 수 없는 조합이 있습니다. GPU 모델별로 가능한 프로필은 nvidia-smi mig -lgip로 확인하세요.

  • 적용: 노드에 nvidia.com/mig.config=all-1g.10gb 같은 라벨을 붙이면 MIG Manager가 그 구성으로 GPU를 나눕니다. 구성을 바꾸는 동안 그 노드의 GPU 작업은 멈춰야 합니다.
  • single 전략: 노드의 모든 GPU를 같은 프로필로 나누고, 조각을 그냥 nvidia.com/gpu로 알립니다. 사용자는 몰라도 됩니다.
  • mixed 전략: 여러 프로필을 섞고, 조각을 nvidia.com/mig-3g.40gb 같은 별도 자원 이름으로 알립니다. Pod가 어떤 크기를 원하는지 그 이름으로 요청합니다.

4DRA 미리 보기

지금까지의 방식은 GPU를 “nvidia.com/gpu 몇 개”라는 숫자로만 요청합니다. “메모리 40GB 이상인 H100 하나” 같은 조건을 말할 수 없고, 나눠 쓰는 방식은 노드 단위로 미리 정해 둬야 합니다. DRA(Dynamic Resource Allocation)는 Kubernetes 1.34에서 정식 기능이 된 새로운 장치 할당 방식으로, Pod가 ResourceClaim으로 장치의 조건을 적고, 장치 드라이버가 그에 맞는 장치를 골라 배정합니다.

구분장치 플러그인DRA
요청 방식resources.limits의 정수ResourceClaim에 조건(모델, 메모리, 속성)
나눠 쓰기노드 단위로 미리 구성요청에 따라 동적으로
여러 Pod가 한 장치 공유time-slicing 등 우회 방법같은 ResourceClaim을 여러 Pod가 참조
지금널리 쓰이는 기본NVIDIA의 DRA 드라이버 등 생태계가 자라는 중

Kubeflow 구성요소와 Kueue가 DRA를 얼마나 지원하는지는 버전마다 빠르게 바뀌고 있습니다. 당장은 장치 플러그인 방식으로 운영하되, 새 클러스터를 설계할 때는 DRA 지원 여부를 확인할 항목에 넣으세요.

5반쯤 뜬 분산 학습 문제

Kubernetes의 기본 스케줄러는 Pod를 하나씩 따로 배치합니다. 노드 2대짜리 TrainJob의 Pod 둘이 서로 한 묶음이라는 것을 모릅니다. 그래서 GPU가 부족하면 하나만 뜨고 하나는 Pending이 되며, 먼저 뜬 Pod는 짝을 기다리며 GPU를 쥐고 놀게 됩니다. 두 작업이 동시에 이렇게 되면 서로의 GPU를 기다리는 교착 상태가 됩니다.

맨 위 시뮬레이터에서 방식을 기본 스케줄러만으로 바꾸고 교착 장면을 눌러 시간을 진행해 보세요. 그다음 Kueue로 바꿔 같은 장면을 다시 보세요.

해결책방식특징
Kueue작업 전체의 자원이 할당량과 빈 자원 안에 들어갈 때만 작업을 들여보냄(admission). 들여보낸 뒤 Pod 배치는 기본 스케줄러가기본 스케줄러를 그대로 두고 그 앞에 문지기를 세움. 팀별 몫, 빌려 쓰기, 선점까지. Kubernetes SIG 프로젝트로 Trainer, JobSet과 함께 쓰도록 설계
Volcano별도 스케줄러가 PodGroup의 최소 Pod 수가 모두 배치될 수 있을 때만 배치(gang scheduling)배치 단계에서 직접 묶음을 보장. HPC 계열 기능이 풍부. 스케줄러를 바꾸는 부담
coscheduling 플러그인기본 스케줄러에 묶음 배치 플러그인을 추가가볍지만 큐와 할당량 기능은 없음
Kueue의 묶음 보장에 대한 정확한 이해

Kueue는 할당량 계산상 작업 전체가 들어갈 때만 들여보내므로 대부분의 반쯤 뜬 상황을 막습니다. 다만 할당량은 남는데 노드 조각화로 실제 배치가 안 되는 경우까지 막으려면, 정해진 시간 안에 모든 Pod가 준비되지 않으면 작업을 물렸다가 다시 시도하게 하는 설정(waitForPodsReady)을 켭니다.

6Kueue의 개념

Kueue는 Kubernetes의 작업 큐 관리 프로젝트입니다. 작업을 바로 실행하지 않고 큐에 세워 두었다가, 할당량과 우선순위를 보고 들여보냅니다. 설치 구성에 따라 Kubeflow 배포판과 별도로 설치해야 할 수 있습니다.

리소스범위누가뜻
ResourceFlavor클러스터관리자자원의 종류. 어떤 노드 라벨과 taint를 가진 노드 묶음인지(예: H100 노드, 스팟 노드)
ClusterQueue클러스터관리자팀이나 조직의 몫. 종류별 할당량(nominalQuota), 빌려 쓸 수 있는 한도, 선점 규칙
cohortClusterQueue들의 묶음관리자같은 cohort의 ClusterQueue끼리 남는 몫을 빌려 주고 빌려 씀
LocalQueue네임스페이스관리자나 팀네임스페이스의 작업이 들어가는 입구. 하나의 ClusterQueue를 가리킴
Workload네임스페이스Kueue가 자동 생성큐에 선 작업 하나. 들여보내지면(admitted) 실제 Pod가 만들어짐
WorkloadPriorityClass클러스터관리자작업의 우선순위. 선점 판단에 쓰임

추천팀의 몫을 정하는 예 (단순화)

예시의 team-reco는 13편에서 만들 팀 프로필의 네임스페이스입니다. 3편의 기본 설치 그대로라면 kubeflow-user-example-com으로 읽으세요.

apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: h100
spec:
  nodeLabels:
    nvidia.com/gpu.product: NVIDIA-H100-80GB-HBM3
  tolerations:
  - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: reco
spec:
  namespaceSelector: {}
  cohort: ml-platform                 # 검색팀 큐와 같은 묶음
  preemption:
    reclaimWithinCohort: Any            # 빌려 준 몫을 돌려받을 때 선점
    withinClusterQueue: LowerPriority   # 팀 안에서는 우선순위로
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: h100
      resources:
      - {name: cpu, nominalQuota: 64}
      - {name: memory, nominalQuota: 512Gi}
      - {name: nvidia.com/gpu, nominalQuota: 8, borrowingLimit: 8}
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: LocalQueue
metadata:
  name: reco-queue
  namespace: team-reco
spec:
  clusterQueue: reco
  • nominalQuota는 그 팀이 보장받는 몫, borrowingLimit는 남의 놀고 있는 몫을 더 빌려 쓸 수 있는 한도입니다. 맨 위 시뮬레이터의 두 팀은 각각 8장을 보장받고, 서로의 남는 몫을 빌려 씁니다.
  • 빌려 쓴 상태에서 원래 주인이 작업을 넣으면, reclaimWithinCohort 설정에 따라 빌려 간 작업을 선점해 돌려줍니다. 선점된 작업은 큐로 돌아가 다시 기다리므로, 체크포인트에서 이어 가는 코드(2편, 7편)가 있어야 손해가 적습니다.
  • 3편 8장의 프로필 ResourceQuota는 “이 이상 못 쓴다”는 상한이고, Kueue는 “줄을 세워 차례로, 남는 것은 빌려서”입니다. 함께 쓰되 서로 모순되지 않게 숫자를 맞춥니다.
  • Kueue의 API 버전과 필드 이름은 Kueue 버전에 따라 바뀌므로, 설치한 버전의 문서를 확인하세요.

7Kubeflow와 Kueue 잇기

작업을 큐에 세우는 방법은 대개 같습니다. 작업에 kueue.x-k8s.io/queue-name 라벨로 LocalQueue 이름을 붙이면, Kueue가 그 작업을 붙잡아 두었다가(suspend) 차례가 오면 풀어 줍니다.

Kubeflow 작업큐에 세우는 법
TrainJob (7편)TrainJob의 metadata.labels에 queue-name 라벨. Trainer v2는 처음부터 Kueue와 함께 쓰도록 설계되어, TrainJob 전체(노드 전부)가 하나의 Workload로 다뤄짐
Katib Trial (8편)trialSpec이 Job이나 TrainJob이므로, 그 템플릿의 metadata.labels에 queue-name 라벨. parallelTrialCount를 크게 잡아도 큐가 몫만큼만 들여보냄
파이프라인 단계 (5, 6편)단계 Pod는 Argo가 만드는 일반 Pod이므로, Kueue의 Pod 통합을 켜고 kfp-kubernetes의 add_pod_label로 해당 단계에 라벨을 붙임. GPU를 쓰는 단계에만 거는 것이 보통
Spark (10편)driver와 executor Pod에 라벨을 붙이는 방식 등 Kueue가 지원하는 통합 방식을 확인해 적용
Notebooks (4편)노트북은 끝이 없는 작업이라 큐와 잘 맞지 않음. 대신 노트북 전용 노드 풀, time-slicing, 컬링으로 관리하는 경우가 많음
 
# TrainJob을 큐에 세우기

8토폴로지를 아는 배치

7편에서 노드 간 통신이 분산 학습의 병목이라고 했습니다. 같은 TrainJob의 노드들이 같은 랙, 같은 고속 네트워크 묶음(InfiniBand 스위치 아래 등)에 모여 있으면 훨씬 빠릅니다. Kueue의 토폴로지 인식 스케줄링은 노드 라벨로 데이터센터의 계층(블록, 랙, 호스트)을 정의해 두고, 작업이 원하는 수준에서 모여 배치될 때만 들여보냅니다. 작업에는 “반드시 같은 랙” 또는 “가능하면 같은 랙” 같은 요구를 주석으로 적습니다.

클라우드에서는 같은 배치 그룹(placement group)이나 같은 영역의 고속 네트워크 노드 풀을 쓰는 것이 같은 효과를 냅니다. 큰 분산 학습을 자주 한다면 노드 풀 설계 단계에서 이것부터 정하세요.

9GPU 비용과 관측

GPU 운영의 가장 흔한 낭비는 “할당은 되어 있는데 쓰지 않는 GPU”입니다. DCGM Exporter의 지표로 이것을 찾아냅니다.

낭비찾는 법대책
잊힌 GPU 노트북GPU 사용률(DCGM_FI_DEV_GPU_UTIL)이 몇 시간째 0인 노트북 Pod컬링(4편), 노트북은 time-slicing 노드 풀로
데이터를 기다리는 학습사용률이 낮고 들쭉날쭉DataLoader 워커와 /dev/shm(2편), 데이터 위치
너무 큰 GPU에 작은 모델메모리 사용(DCGM_FI_DEV_FB_USED)이 전체의 일부MIG 조각이나 작은 GPU 노드 풀
반쯤 뜬 분산 학습Running인데 사용률 0인 학습 Pod와 Pending 짝Kueue(5장)
비싼 GPU를 팀이 독점팀별 GPU 시간 집계Kueue 몫과 빌려 쓰기, 팀별 비용 보고(16편)

스팟이나 선점형 GPU는 비용을 크게 줄이지만 중간에 회수됩니다. Kueue에서 스팟 노드를 별도 ResourceFlavor로 두고, 체크포인트에서 이어 가는 학습과 Katib Trial, Spark executor처럼 다시 해도 되는 작업을 그쪽으로 보내는 설계가 흔합니다.

13정리와 다음 편

  1. GPU Operator가 드라이버, 런타임 연동, 장치 플러그인, 라벨, 지표, MIG 구성을 한꺼번에 관리합니다.
  2. time-slicing은 칸막이 없는 시간 나누기, MPS는 동시 실행과 메모리 한도, MIG는 하드웨어 수준의 격리입니다. 학습과 운영 서빙에는 통째로나 MIG를 씁니다.
  3. 기본 스케줄러는 Pod를 하나씩 배치해 분산 학습이 반쯤만 뜨고 GPU를 붙잡는 교착이 생깁니다. Kueue는 작업 전체가 들어갈 때만 들여보내 이를 막습니다.
  4. ResourceFlavor는 자원의 종류, ClusterQueue는 팀의 몫, LocalQueue는 네임스페이스의 입구입니다. cohort로 남는 몫을 빌려 쓰고, 선점으로 돌려받습니다.
  5. TrainJob, Katib Trial, 파이프라인 단계는 queue-name 라벨로 큐에 섭니다. GPU 낭비는 DCGM 지표로 찾아 컬링, MIG, 큐로 줄입니다.

현장에서 쓰이는 장면

  • 연구소. 연구실 열 곳의 GPU 다툼을 Kueue의 몫과 빌려 쓰기로 정리하고, 반쯤 뜬 분산 학습으로 GPU가 노는 일을 없앱니다.
  • 제조. 추론 서버 여러 개를 MIG로 나눈 한 장의 GPU에 올려 비용을 줄입니다.
  • MSP. 고객사 GPU 사용률 보고서를 DCGM 지표로 만들어 매월 비용 절감 제안의 근거로 씁니다.
