추측 디코딩과
고급 기능

2편의 결론은 “Decode는 메모리 대역폭에 묶여 있다”였습니다. 한 토큰을 만들 때마다 가중치 전체를 읽어야 하니, GPU 연산은 대부분 놉니다. 추측 디코딩은 그 남는 연산으로 여러 토큰을 한 번에 검증해, 같은 가중치 읽기로 토큰을 여러 개 얻는 기법입니다. 출력 품질은 그대로이면서 TPOT를 줄입니다. 이번 편은 그 원리와 “언제 이기고 언제 지는지”, 방법별 선택을 다루고, 같은 엔진의 다른 고급 기능 — LoRA 멀티 어댑터, 구조화 출력·툴 콜링 — 이 성능에 주는 영향을 측정합니다.

01시작하기 전에

추측 디코딩은 “작은 모델이 빠르게 답안을 쓰고, 큰 모델이 한 번에 채점하는” 방식입니다.

학습 목표

  1. 초안 제안과 병렬 검증, 거절 샘플링으로 품질이 유지되는 이유를 설명할 수 있다.
  2. 수락률·추측 토큰 수·초안 비용·배치 크기로 이득을 계산하고, 손해가 나는 조건을 말할 수 있다.
  3. n-gram·접미사·드래프트 모델·EAGLE·MTP 등 방법을 비교해 워크로드에 맞게 고를 수 있다.
  4. vLLM에서 추측 디코딩을 켜고 수락률 지표로 효과를 측정·조정할 수 있다.
  5. LoRA 멀티 어댑터 서빙의 구조·설정·오버헤드를 설명하고 측정할 수 있다.
  6. 구조화 출력·툴 콜링이 지연에 주는 영향을 측정하고 줄이는 방법을 제시할 수 있다.
이 편의 비유: 신입이 초안을 쓰고 팀장이 결재

팀장(큰 모델)이 한 문장씩 직접 쓰면 문장마다 서류 전체(가중치)를 다시 펼쳐야 합니다. 신입(초안 모델)이 다음 몇 문장을 빠르게 써 오면, 팀장은 서류를 한 번만 펼쳐 여러 문장을 한꺼번에 검토합니다. 맞는 데까지는 그대로 통과, 틀린 곳부터는 팀장이 고쳐 씁니다. 최종 문서는 팀장이 혼자 쓴 것과 같습니다. 신입이 팀장 스타일을 잘 알수록(수락률) 빨라지고, 팀장이 이미 결재 서류에 파묻혀 있으면(큰 배치) 검토할 여유가 없어 오히려 느려집니다.

02추측 디코딩의 원리

한 번의 가중치 읽기로 여러 토큰을 “검증”하는 것이 핵심입니다.

  1. 초안 제안가벼운 제안자(작은 모델·예측 헤드·입력 문자열 매칭)가 다음 토큰 k개를 빠르게 제안합니다.
  2. 병렬 검증큰 모델이 [현재 토큰 + 초안 k개]를 한 번의 순전파로 처리해, 각 위치에서 자기라면 어떤 토큰을 냈을지 확률을 얻습니다. Prefill처럼 여러 토큰을 한 번에 처리하므로 가중치 읽기는 한 번입니다.
  3. 수락·거절앞에서부터 초안을 큰 모델의 분포와 비교해 수락하고, 처음 거절된 위치에서 큰 모델의 분포로 토큰 하나를 새로 뽑습니다(거절 샘플링). 그래서 매 스텝 최소 1개, 최대 k+1개의 토큰을 얻습니다.
  4. 품질 보존이 수락 규칙은 출력 분포가 큰 모델 단독과 같도록 설계되어 있어 “손실 없는” 가속입니다. 다만 수치 연산 순서가 달라 같은 시드에서도 아주 드물게 다른 문장이 나올 수 있다는 점(2편 배치 불변성)은 같습니다.
토큰 하나의 수락 확률 α, 추측 토큰 수 k 일 때 스텝당 기대 토큰 수 E = (1 − α^(k+1)) ÷ (1 − α) 예) α = 0.7, k = 3 → E ≈ 2.53 토큰 / 스텝 속도 향상 ≈ E ÷ (검증 스텝 시간 ÷ 일반 스텝 시간 + 초안 비용)

메모리 병목일 때 검증 스텝 시간은 일반 스텝과 거의 같으므로(가중치 읽기 한 번), 초안 비용이 작으면 속도 향상은 E에 가까워집니다. 반대로 연산 병목일 때는 k+1개 토큰을 계산하는 비용이 그대로 드러나 이득이 사라집니다. 이것이 3장의 주제입니다.

03언제 빨라지고 언제 느려지나

추측 디코딩은 “남는 연산”을 쓰는 기법입니다. 연산이 남지 않으면 이득도 없습니다.

조건이득 방향이유
작은 배치 (낮은 동시성)크게 이득메모리 병목이라 검증 비용이 거의 공짜
큰 배치 + 짧은 문맥 (높은 동시성)이득 감소 → 손해 가능검증하는 k+1개 토큰의 연산 때문에 연산 병목으로 넘어가면 그 연산이 그대로 비용. 수락률이 낮거나 초안 비용이 크면 처리량이 오히려 떨어질 수 있음
큰 배치 + 긴 문맥이득 유지되는 경우 많음요청마다 읽어야 할 KV가 커서 큰 배치에서도 메모리 병목이 유지됨. 같은 KV 읽기로 여러 토큰을 검증하므로 이득이 남음 (긴 문맥에서 추측 디코딩이 유리하다는 연구 결과와 같은 방향)
출력이 입력을 많이 반복 (편집·요약·코드 수정·RAG 인용)n-gram·접미사 방식이 크게 이득입력에서 그대로 베끼는 구간의 수락률이 매우 높음
자유 작문·창작·높은 temperature수락률 낮음 → 이득 작음다음 토큰 예측이 어려움
대역폭이 작은 GPU (GB10 등)상대적으로 이득 큼더 큰 배치까지 메모리 병목이 유지되어 연산 여유가 큼
초안 모델이 큼이득 감소초안 생성 자체의 시간·메모리·KV가 듦
TTFT약간 손해드래프트 모델이 있으면 그 모델의 Prefill도 필요
GB10이 추측 디코딩에 유리한 이유

2편의 루프라인으로 보면, 연산 성능 대비 메모리 대역폭이 작은 장비일수록 “연산이 남는 구간”이 넓습니다. GB10은 대역폭이 0.273TB/s로 작아 단일 사용자 TPOT가 느린 대신, 같은 가중치 읽기로 여러 토큰을 검증하는 추측 디코딩의 효과가 데이터센터 GPU보다 더 큰 배치까지 이어질 수 있습니다. 히어로 계산기에서 GPU를 바꿔 같은 배치의 결과를 비교해 보고, 실습 16-3에서 실측합니다.

04방법 지도

초안을 “누가, 무엇으로” 만드느냐에 따라 나뉩니다. vLLM은 --speculative-config의 method로 고릅니다.

방법 (method)초안을 만드는 것추가 모델강한 곳약한 곳
n-gram (ngram)입력(프롬프트)에서 최근 토큰열과 같은 부분을 찾아 그 뒤를 제안없음편집·요약·RAG 인용·코드 수정 등 입력 반복자유 작문
접미사 디코딩 (suffix)입력과 이전 출력들의 접미사 트리로 패턴 매칭없음 (Arctic Inference 필요)에이전트처럼 비슷한 출력이 반복되는 워크로드별도 패키지 의존
드래프트 모델 (draft_model)같은 토크나이저의 작은 모델작은 모델 (메모리·KV 추가)범용초안 비용이 커서 이득이 제한적
EAGLE·EAGLE-3 (eagle, eagle3)대상 모델의 은닉 상태를 입력으로 받는 1층짜리 가벼운 헤드대상 모델 전용 헤드 (작음)범용 대화·코드에서 가장 널리 쓰이는 선택모델별 학습된 헤드가 필요
MTP (mtp 계열)모델 자체에 내장된 다중 토큰 예측 층없음 (모델에 포함)MTP를 갖춘 모델(DeepSeek 계열 등)지원 모델 한정
Medusa대상 모델에 붙인 여러 예측 헤드헤드—EAGLE 계열에 밀리는 추세
최신 블록 단위 드래프터 (dflash, dspark 등)여러 토큰을 블록으로 한꺼번에 제안하는 새 드래프터대상 모델 전용긴 추측 길이새로 나온 방법, 버전별 지원 확인

고르는 순서

  1. 모델에 MTP가 있으면 MTP부터. 추가 모델 없이 높은 수락률을 기대할 수 있습니다.
  2. 대상 모델용 EAGLE-3 헤드가 공개되어 있으면 EAGLE-3. vLLM 프로젝트의 Speculators 라이브러리가 학습 도구와 사전 학습된 헤드를 제공하고, Qwen3-8B용 EAGLE-3 헤드도 공개되어 있습니다(실습에 사용).
  3. 워크로드가 입력을 많이 반복하면 n-gram(또는 접미사)을 함께 검토. 모델 없이 거의 공짜로 이득을 얻습니다.
  4. 우리 도메인(한국어 상담 등)에서 수락률이 낮으면 우리 데이터로 EAGLE-3 헤드를 직접 학습하는 것을 검토합니다(Speculators). 6편의 “보정 데이터는 우리 데이터로”와 같은 원리입니다.

05추측 디코딩 운영

켜는 것은 설정 한 줄, 유지하는 것은 지표와 버전 관리입니다.

speculative-config: '{"method":"eagle3","model":"/models/RedHatAI/Qwen3-8B-speculator.eagle3","num_speculative_tokens":3}'

# n-gram (추가 모델 없음)
# speculative-config: '{"method":"ngram","num_speculative_tokens":4,"prompt_lookup_max":4,"prompt_lookup_min":2}'
운영 항목내용
수락률 지표엔진 /metrics의 추측 디코딩 지표(제안 토큰 수·수락 토큰 수·위치별 수락)로 “수락률”과 “스텝당 평균 수락 길이”를 계산. 워크로드가 바뀌면 함께 바뀜
추측 토큰 수 k수락률이 높으면 k를 늘리고, 낮으면 줄임. 너무 크면 거절될 토큰의 검증 연산만 늘어남. 보통 2~5에서 실측으로 선택

06LoRA 멀티 어댑터 서빙

베이스 모델 하나에 고객·업무별 어댑터 여러 개를 얹어, GPU 한 벌로 여러 “맞춤 모델”을 서빙합니다.

LoRA 어댑터는 베이스 가중치에 더하는 작은 저랭크 행렬입니다. vLLM은 한 배치 안에서 요청마다 다른 어댑터를 적용하는 전용 커널로, 어댑터가 다른 요청들도 함께 배치합니다. 앱은 요청의 model 필드에 어댑터 이름을 넣어 고릅니다.

설정의미운영 포인트
--enable-loraLoRA 기능 켜기켜기만 해도 일부 버퍼·커널 경로가 추가됨. 쓰지 않으면 끔
--max-loras한 배치에 동시에 올릴 수 있는 어댑터 수 (GPU 슬롯)요청이 섞이는 어댑터 수에 맞춤. 넘치면 대기
--max-lora-rank허용하는 최대 랭크가장 큰 어댑터 기준. 클수록 버퍼·연산 증가
--max-cpu-lorasCPU에 캐시해 둘 어댑터 수GPU 슬롯보다 많은 어댑터를 빠르게 교체
--lora-modules 이름=경로기동 시 등록할 어댑터정적 등록. 6편 레지스트리 경로 사용
런타임 등록 API실행 중 어댑터 추가·제거 (환경 변수로 허용 필요)관리 경로이므로 게이트웨이로 노출 금지(4·7편). 등록 권한 통제
  • 성능: 어댑터를 쓰는 요청은 추가 행렬 곱 때문에 TPOT가 조금 늘고, 한 배치에 서로 다른 어댑터가 많을수록 효율이 떨어집니다. 실습 16-4에서 어댑터 없음·1개·4개 혼합을 비교합니다.
  • 라우팅: 레플리카가 여럿이면 어댑터가 이미 올라간 레플리카로 보내는 LoRA 친화도 점수(11편)가 효과적입니다.
  • MSP: 고객별 파인튜닝 결과를 어댑터로 받으면 베이스 모델 하나로 여러 고객을 서빙할 수 있습니다. 어댑터는 고객 데이터로 학습된 산출물이므로 6편의 반입 심사(safetensors만, 출처·해시 기록)와 테넌트별 접근 통제를 적용합니다.

07구조화 출력·툴 콜링의 비용

09MSP 관점

고급 기능은 상품의 차별화 요소이자, 관리하지 않으면 원가를 흔드는 요소입니다.

  • 저지연 상품: 추측 디코딩을 켠 레플리카를 “저지연 등급”으로, 끈 레플리카를 “처리량 등급”으로 구분해 게이트웨이(12편)에서 테넌트 등급별로 라우팅할 수 있습니다.
  • 맞춤 모델 상품: 고객 어댑터를 베이스 모델 공유 풀에서 서빙하면 전용 GPU 없이 맞춤 모델을 제공할 수 있습니다. 어댑터 수·랭크 상한과 반입 절차를 계약에 넣습니다.
  • 요청 옵션 정책: n, max_tokens, logprobs, 이미지 수 같은 비용 증폭 옵션은 게이트웨이에서 등급별 상한을 둡니다.
  • 검증 표준: 추측 디코딩·LoRA를 켜거나 버전을 바꿀 때 6편 품질 평가와 14편 SLO 측정을 함께 돌리는 것을 표준 절차로 둡니다.

DOC = " ".join(r.choice("노드 파드 쿼터 지연 처리량 메모리 대역폭 캐시 배치 스케줄러 게이트웨이 장애 알림 예산".split()) for _ in range(350))

TASKS = {
  "free": "쿠버네티스에서 GPU 노드를 운영할 때 주의할 점을 자세히 설명해 줘.",

  "code": f"다음 파이썬 코드에 타입 힌트만 추가해서 전체를 다시 출력해 줘:\n{CODE}",
}
def spec_counts():
    txt = urllib.request.urlopen(a.base + "/metrics", timeout=10).read().decode()
    c = {"draft": 0.0, "acc": 0.0, "drafts": 0.0}
    for l in txt.splitlines():
        if l.startswith("#") or "spec_decode" not in l or "per_pos" in l: continue
        name, val = l.split("{")[0].split(" ")[0], float(l.rsplit(" ", 1)[1])
        if "num_draft_tokens" in name: c["draft"] += val
        elif "num_accepted_tokens" in name: c["acc"] += val
        elif "num_drafts" in name: c["drafts"] += val
    return c
async def one(prompt):
    t0 = time.perf_counter(); first = last = None; usage = None
    s = await cli.chat.completions.create(model="qwen3-8b", max_tokens=a.max_tokens, temperature=0, stream=True,
        stream_options={"include_usage": True}, messages=[{"role": "user", "content": prompt + " /no_think"}])
    async for ev in s:
        if getattr(ev, "usage", None): usage = ev.usage
        if ev.choices and ev.choices[0].delta and ev.choices[0].delta.content:
            now = time.perf_counter(); first = first or now; last = now
    n = usage.completion_tokens if usage else 1
    return (last - first) / max(n - 1, 1) * 1000, n
async def main():
    for task, prompt in TASKS.items():
        for c in a.conc:
            before = spec_counts(); t0 = time.perf_counter()
            res = await asyncio.gather(*[one(prompt) for _ in range(c)])
            wall = time.perf_counter() - t0; after = spec_counts()
            d = {k: after[k] - before[k] for k in after}
            row = {"label": a.label, "task": task, "conc": c,
                   "tpot_ms": round(statistics.median(x[0] for x in res), 1),

                   "accept_rate": round(d["acc"] / d["draft"], 3) if d["draft"] else None,
                   "mean_accepted_per_draft": round(d["acc"] / d["drafts"], 2) if d["drafts"] else None}
            print(json.dumps(row, ensure_ascii=False))
            open("/results/spec.jsonl", "a").write(json.dumps(row, ensure_ascii=False) + "\n")
asyncio.run(main())

python · make_lora.py (Qwen3-8B 형상의 빈 LoRA 어댑터 생성)
import json, os, sys, numpy as np
from safetensors.numpy import save_file
OUT, R = sys.argv[1] if len(sys.argv) > 1 else "/models/lora", 16
H, Q_OUT, KV_OUT, LAYERS = 4096, 4096, 1024, 36          # Qwen3-8B: 은닉 4096, KV 헤드 8 × 128
for name in ["cust-a", "cust-b", "cust-c", "cust-d"]:
    d = os.path.join(OUT, name); os.makedirs(d, exist_ok=True)
    rng = np.random.default_rng(abs(hash(name)) % 2**32); t = {}
    for i in range(LAYERS):
        for proj, out in [("q_proj", Q_OUT), ("v_proj", KV_OUT)]:
            p = f"base_model.model.model.layers.{i}.self_attn.{proj}"
            t[f"{p}.lora_A.weight"] = (rng.standard_normal((R, H)) * 0.01).astype(np.float16)
            t[f"{p}.lora_B.weight"] = np.zeros((out, R), dtype=np.float16)   # B=0 → 출력은 베이스와 동일
    save_file(t, os.path.join(d, "adapter_model.safetensors"))
    json.dump({"peft_type": "LORA", "task_type": "CAUSAL_LM", "r": R, "lora_alpha": 32, "lora_dropout": 0.0,
               "target_modules": ["q_proj", "v_proj"], "bias": "none", "fan_in_fan_out": False,
               "base_model_name_or_path": "Qwen/Qwen3-8B"}, open(os.path.join(d, "adapter_config.json"), "w"))
    print("만듦:", d)

14정리와 체크리스트

핵심 여섯 문장.

  1. 추측 디코딩은 남는 연산으로 여러 토큰을 한 번에 검증하는 손실 없는 가속이다.
  2. 기대 토큰 = (1 − α^(k+1)) ÷ (1 − α). 수락률과 초안 비용이 이득을 정한다.
  3. 메모리 병목에서 이기고 연산 병목에서 진다. 짧은 문맥·큰 배치·낮은 수락률이 손해 조건이고, 긴 문맥과 대역폭이 작은 GB10은 이득 구간이 넓다.
  4. MTP → EAGLE-3 → n-gram(입력 반복 워크로드) 순으로 검토하고, 수락률 지표로 k를 조정한다. 헤드는 대상 모델과 짝으로 관리한다.
  5. LoRA는 베이스 하나로 여러 맞춤 모델을 제공하지만, 켜는 것만으로도·섞일수록 오버헤드가 있다. 어댑터는 반입 심사 대상이다.
  6. 구조화 출력은 스키마를 고정해 재사용하고, n·logprobs·max_tokens 같은 비용 증폭 옵션은 게이트웨이에서 상한을 둔다.
