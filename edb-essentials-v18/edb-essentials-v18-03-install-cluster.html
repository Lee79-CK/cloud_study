1장

설치 방식 한눈에

EPAS를 서버에 올리는 방법은 여러 가지입니다. 시험과 실무에서 가장 기본이 되는 것은 리눅스 패키지 설치이고, 이 편도 그 방식을 중심으로 설명합니다.

리눅스 패키지 (RPM/DEB)

EDB 리포지터리를 등록하고 dnf·apt로 설치합니다. 이 편의 주제이며 시험의 기본 전제입니다.

Windows 설치 관리자

그래픽 설치 관리자로 설치합니다. Oracle 호환 모드 선택, 포트, 서비스 이름을 화면에서 고릅니다.

컨테이너·쿠버네티스

EDB의 쿠버네티스 오퍼레이터나 Hybrid Manager로 배포합니다. 운영 자동화에 적합합니다.

자동화 도구

EDB의 배포 자동화 도구(TPA 등)로 여러 서버를 같은 구성으로 설치합니다. 고가용성 구성에서 주로 씁니다.

시험 포인트: 설치와 초기화는 별개의 단계

리눅스 패키지 설치는 프로그램만 설치할 뿐 데이터베이스 클러스터를 만들지 않습니다. 패키지 설치 후 설정 스크립트나 initdb로 클러스터를 따로 초기화해야 서버를 시작할 수 있습니다. 반면 Windows 그래픽 설치 관리자는 설치 과정에서 initdb까지 실행합니다.

2장

패키지 설치 전 준비

서버와 OS

실습은 RHEL 9 호환 배포판(Rocky Linux 9, AlmaLinux 9, Oracle Linux 9) 기준입니다. EPAS는 Debian·Ubuntu, SLES 계열도 지원하지만 패키지 관리자와 경로가 다릅니다(3장 비교표). 지원 OS 목록은 버전마다 바뀌니 EDB 문서의 플랫폼 호환표를 확인하세요.

의존 패키지 저장소 활성화

EPAS의 일부 의존 패키지는 기본 저장소가 아닌 RHEL의 CodeReady Builder(Rocky·Alma에서는 CRB) 저장소에 있습니다. 설치 전에 켜 둡니다.

# RHEL 9 (구독 등록된 서버)
ARCH=$(/bin/arch)
sudo subscription-manager repos --enable "codeready-builder-for-rhel-9-${ARCH}-rpms"

# Rocky Linux 9 / AlmaLinux 9
sudo dnf -y install dnf-plugins-core
sudo dnf config-manager --set-enabled crb

클라우드의 RHEL 이미지는 같은 저장소가 다른 이름(예: codeready-builder-for-rhel-9-rhui-rpms)으로 제공되기도 합니다. 사용하는 이미지의 문서를 확인하세요.

EDB 리포지터리 등록

EDB 웹사이트의 리포지터리 페이지에 로그인하면, 계정의 구독 토큰이 포함된 등록 명령을 OS별로 보여 줍니다. 그 명령을 복사해 실행하는 것이 가장 정확합니다. 형태는 대략 다음과 같습니다.

# 형태 예시 — 실제 명령은 EDB 리포지터리 페이지에서 복사
export EDB_SUBSCRIPTION_TOKEN='발급받은_토큰'
curl -1sSLf "https://downloads.enterprisedb.com/$EDB_SUBSCRIPTION_TOKEN/enterprise/setup.rpm.sh" | sudo -E bash

# 등록 확인: EDB 저장소가 목록에 보이면 성공
dnf repolist | grep -i enterprisedb
토큰은 비밀번호처럼 다루세요

구독 토큰이 있으면 누구나 그 계정의 권한으로 EDB 패키지를 받을 수 있습니다. 쉘 이력, 공개 저장소의 스크립트, 티켓 본문에 토큰을 그대로 남기지 않도록 주의합니다. MSP 환경에서는 고객사별 토큰을 비밀 관리 도구에 보관하는 것이 안전합니다.

3장

패키지 설치와 설치 결과

서버 패키지 이름은 edb-as<버전>-server 형식입니다. 18 버전이면 edb-as18-server입니다.

sudo dnf -y install edb-as18-server

이 메타 패키지가 서버 본체, 클라이언트 도구, contrib 확장 등 필요한 하위 패키지를 함께 설치합니다. 필요한 구성요소만 골라 설치할 수도 있습니다.

설치 후 생기는 것들

  • 운영체제 사용자 enterprisedb — 서버 프로세스를 실행하고 데이터 디렉터리를 소유하는 계정입니다. 기본 쉘은 bash, 홈 디렉터리는 /var/lib/edb/as18입니다. 비밀번호가 없으므로 보통 sudo su - enterprisedb로 전환해 씁니다.
  • systemd 유닛 파일 edb-as-18.service — /usr/lib/systemd/system/에 설치되며, 데이터 디렉터리 위치(PGDATA)가 여기에 적혀 있습니다.
  • 실행 파일과 설정 스크립트 — /usr/edb/as18/bin/ 아래에 psql, pg_ctl, initdb, 초기화 스크립트 edb-as-18-setup 등이 설치됩니다.

기본 경로 비교

구성요소기본 위치
시험 포인트: 이름의 하이픈 위치

패키지는 edb-as18-server(버전 앞에 하이픈 없음), 서비스와 스크립트는 edb-as-18, edb-as-18-setup(버전 앞에 하이픈), 경로는 /usr/edb/as18입니다. 선택지에서 이 조합을 섞어 놓는 경우가 있으니 눈에 익혀 두세요.

4장

클러스터 초기화: 두 가지 모드

이제 데이터 디렉터리를 만들 차례입니다. RHEL 계열에서는 EDB가 제공하는 설정 스크립트를 쓰는 것이 표준입니다. 이 스크립트는 유닛 파일에 적힌 PGDATA 위치에, enterprisedb 사용자 권한으로 initdb를 실행해 줍니다.

sudo PGSETUP_INITDB_OPTIONS="-E UTF-8" /usr/edb/as18/bin/edb-as-18-setup initdb

PGSETUP_INITDB_OPTIONS 환경변수에 적은 값은 그대로 initdb 옵션으로 전달됩니다. 옵션을 주지 않으면 기본값으로 초기화됩니다.

Oracle 호환 모드와 PostgreSQL 모드

EPAS의 initdb는 기본적으로 클러스터를 Oracle 호환 모드(Redwood 모드)로 만듭니다. PostgreSQL 방식으로 만들려면 EPAS 전용 옵션 --no-redwood-compat를 줍니다. 이 선택은 클러스터를 만들 때 정해지며, 두 모드는 기본 데이터베이스와 슈퍼유저 이름부터 다릅니다.

항목Oracle 호환 모드 (기본)PostgreSQL 모드
initdb 옵션없음 (기본값)--no-redwood-compat
기본 데이터베이스edbpostgres
기본 슈퍼유저enterprisedbpostgres
Oracle 호환 딕셔너리 뷰포함미포함
Oracle식 데이터 타입 변환적용미적용
날짜 표시 형식Oracle 문법과 호환되는 형식PostgreSQL 기본 형식
EDB 권장EPAS의 모든 기능을 쓰려면 이 모드일부 호환 기능만 사용 가능
시험 포인트

"EPAS 클러스터를 PostgreSQL 모드로 만들려면?" → --no-redwood-compat. "Oracle 호환 모드 클러스터의 기본 DB와 슈퍼유저는?" → edb와 enterprisedb. 옛 문서에 나오는 --redwood-like는 별개의 옵션이니 혼동하지 마세요.

용어: initdb

새 데이터베이스 클러스터를 만드는 명령입니다. 지정한 디렉터리에 2편에서 본 하위 디렉터리와 설정 파일을 만들고, 시스템 카탈로그를 채우고, template1·template0 같은 기본 데이터베이스를 생성합니다. 대상 디렉터리는 없거나 비어 있어야 하며, 서버를 실행할 운영체제 사용자(enterprisedb)로 실행해야 합니다. root로는 실행할 수 없습니다.

initdb를 직접 실행하는 경우

데이터 디렉터리를 하나 더 만들거나(예: 같은 서버에 포트가 다른 두 번째 클러스터), 설정 스크립트 없이 테스트할 때는 initdb를 직접 실행합니다.

sudo su - enterprisedb
/usr/edb/as18/bin/initdb -D /var/lib/edb/as18/data2 -E UTF-8

이렇게 직접 실행하면 마지막에 다음과 같은 경고가 나올 수 있습니다.

initdb: warning: enabling "trust" authentication for local connections
initdb: hint: You can change this by editing pg_hba.conf or using the option -A,
or --auth-local and --auth-host, the next time you run initdb.

인증 방식을 지정하지 않으면 로컬 접속을 비밀번호 없이 허용하는 trust로 설정된다는 뜻입니다. 실습이라도 --auth-local=peer --auth-host=scram-sha-256처럼 명시하는 습관을 들이세요. 인증 방식은 7편에서 자세히 다룹니다.

주요 initdb 옵션 정리

옵션의미나중에 바꿀 수 있나
-D, --pgdata데이터 디렉터리 위치서버 중지 후 이동 가능(유닛 파일·SELinux 수정 필요)
-E, --encodingtemplate 데이터베이스의 기본 인코딩이후 DB마다 다른 인코딩으로 생성 가능(template0 사용), 기존 DB는 변경 불가

--locale-provider로케일을 누가 제공하나: libc(OS), icu, builtin(PG17+)DB 생성 시 지정
-U, --username초기 슈퍼유저 이름이름 변경은 가능하나 권장하지 않음
-W, --pwprompt초기 슈퍼유저 비밀번호를 입력받음나중에 ALTER ROLE로 설정 가능
-A, --auth-local, --auth-hostpg_hba.conf의 초기 인증 방식pg_hba.conf 편집 후 reload
-X, --waldirWAL 디렉터리를 다른 위치에 둠(pg_wal이 심볼릭 링크가 됨)서버 중지 후 옮길 수 있음
--wal-segsizeWAL 세그먼트 크기(MB, 2의 거듭제곱)pg_resetwal로만 가능(권장하지 않음)

시험 포인트: PostgreSQL 18의 체크섬 기본값 변화

PostgreSQL 17까지는 initdb에 -k를 줘야 데이터 체크섬이 켜졌지만, 18부터는 기본으로 켜지고 끄려면 --no-data-checksums를 줍니다. 현재 상태는 SHOW data_checksums;로 확인합니다. 체크섬은 디스크나 스토리지 장애로 페이지가 손상된 것을 읽는 순간 감지해 줍니다.

6장

서비스 시작과 첫 접속

systemd로 서비스 관리

sudo systemctl start edb-as-18      # 시작
sudo systemctl enable edb-as-18     # 부팅 시 자동 시작
sudo systemctl status edb-as-18     # 상태 확인
sudo systemctl stop edb-as-18       # 중지
sudo systemctl restart edb-as-18    # 재시작

운영 서버에서는 enable을 빠뜨리지 않도록 주의하세요. 서버 재부팅 후 DB가 올라오지 않아 장애로 이어지는 흔한 원인입니다.

첫 접속

sudo su - enterprisedb
psql edb

enterprisedb 운영체제 사용자로 전환하면, 같은 이름의 데이터베이스 슈퍼유저로 로컬 소켓을 통해 접속됩니다. 접속되면 먼저 이 세 가지를 확인합니다.

SELECT version();          -- EnterpriseDB Advanced Server 18.x 문자열 확인
SHOW data_directory;       -- 데이터 디렉터리 위치
SHOW port;                 -- 5444 확인
\l                         -- 데이터베이스 목록 (edb, template0, template1 등)

슈퍼유저 비밀번호 설정

처음에는 enterprisedb 데이터베이스 사용자에 비밀번호가 없습니다. 원격 접속이나 도구 연결을 하려면 설정합니다. psql의 \password는 비밀번호를 화면과 쉘 이력에 남기지 않고 암호화해서 보내므로 가장 안전합니다.

edb=# \password enterprisedb
Enter new password for user "enterprisedb":
Enter it again:

원격 접속을 열려면 세 곳을 봐야 한다

  • listen_addresses — 서버가 어느 네트워크 주소에서 연결을 받을지 정합니다. PostgreSQL 기본값은 localhost이므로, 설치 직후 SHOW listen_addresses;로 확인하고 필요하면 바꿉니다. 변경은 재시작이 필요합니다(5편).
  • pg_hba.conf — 어떤 주소의 어떤 사용자에게 어떤 인증 방식으로 접속을 허용할지 정합니다(7편).
  • OS 방화벽 — sudo firewall-cmd --permanent --add-port=5444/tcp && sudo firewall-cmd --reload
현장 사례: "설치는 됐는데 앱에서 접속이 안 돼요"

MSP 현장에서 가장 흔한 설치 직후 문의입니다. 오류 메시지로 원인을 구분할 수 있습니다. "Connection refused"면 listen_addresses나 방화벽, 서버 미기동을 봅니다. "no pg_hba.conf entry for host"면 pg_hba.conf 규칙이 없는 것이고, "password authentication failed"면 비밀번호나 인증 방식 문제입니다. 클라이언트가 5432 포트로 붙고 있지 않은지도 반드시 확인하세요.

데이터 디렉터리를 다른 곳에 두려면

운영에서는 데이터를 별도 디스크(예: /data)에 두는 경우가 많습니다. 유닛 파일을 /etc/systemd/system/으로 복사해 PGDATA와 PIDFile 경로를 바꾸고, SELinux가 켜진 서버라면 새 디렉터리에 올바른 보안 컨텍스트를 지정해야 합니다.

# 1) 유닛 파일 재정의 (패키지 업데이트에 덮어쓰이지 않도록 /etc에)
sudo systemctl edit edb-as-18
#   [Service]
#   Environment=PGDATA=/data/edb/as18
#   PIDFile=/data/edb/as18/postmaster.pid

# 2) SELinux 컨텍스트를 기본 데이터 디렉터리와 같게
sudo semanage fcontext --add --equal /var/lib/edb/as18/data /data/edb/as18
sudo restorecon -rv /data/edb/as18

# 3) 초기화 후 시작
sudo systemctl daemon-reload
sudo /usr/edb/as18/bin/edb-as-18-setup initdb
sudo systemctl start edb-as-18

EDB 문서는 유닛 파일을 /etc/systemd/system/에 복사해 수정하는 방식을 안내합니다. systemctl edit의 오버라이드 방식도 같은 효과를 냅니다.

7장

pg_ctl과 서버 제어

pg_ctl은 PostgreSQL 계열의 기본 서버 제어 도구입니다. systemd가 없는 환경, 두 번째 클러스터, 컨테이너 안에서 주로 쓰며, systemd 유닛도 내부적으로 서버 프로세스를 이런 방식으로 제어합니다. enterprisedb 사용자로 실행합니다.

export PATH=/usr/edb/as18/bin:$PATH
export PGDATA=/var/lib/edb/as18/data      # 지정하면 -D 생략 가능

pg_ctl start -l /var/lib/edb/as18/startup.log   # 시작 (-l: 시작 로그 파일)
pg_ctl status                                   # 실행 여부와 PID
pg_ctl reload                                   # 설정 파일 다시 읽기 (재시작 없음)
pg_ctl restart -m fast                          # 재시작
pg_ctl stop -m fast                             # 중지 (-m: 종료 모드)
pg_ctl promote                                  # 스탠바이를 주 서버로 승격 (11편)

systemd 서비스를 pg_ctl로 섞어 제어하지 마세요

systemctl로 띄운 서버를 pg_ctl로 멈추면 systemd는 서비스가 비정상 종료됐다고 판단해 상태가 꼬이거나 자동 재시작을 시도할 수 있습니다. 한 서버는 한 가지 방법으로 일관되게 제어하는 것이 원칙입니다.

용어: reload와 restart

reload는 서버를 멈추지 않고 설정 파일만 다시 읽게 합니다(postmaster에 SIGHUP 신호). 연결은 끊기지 않습니다. restart는 서버를 완전히 내렸다 올리므로 모든 연결이 끊깁니다. shared_buffers, port, max_connections처럼 서버 시작 때만 적용되는 파라미터는 restart가 필요합니다. 어떤 파라미터가 어느 쪽인지는 5편의 핵심 주제입니다.

8장

종료 모드 3종: smart · fast · immediate

서버를 멈추는 방식은 세 가지입니다. 모드를 눌러 연결된 세션과 진행 중인 트랜잭션에 무슨 일이 생기는지 비교하세요.


  

  

    시험 포인트
    
pg_ctl stop의 기본 모드는 fast입니다. immediate는 체크포인트 없이 즉시 끝내므로 다음 시작 때 WAL을 재생하는 크래시 복구가 일어납니다(2편 6장의 장애 시뮬레이션과 같은 원리). 신호 대응도 함께 외워 두세요: SIGTERM = smart, SIGINT = fast, SIGQUIT = immediate.

  

  

    비유: 도서관 폐관 방식
    
smart는 "새 손님은 받지 않고, 안에 있는 손님이 모두 스스로 나갈 때까지 기다린 뒤 정리하고 닫는다", fast는 "지금 하던 대출 처리는 취소하고 손님을 모두 내보낸 뒤 정리하고 닫는다", immediate는 "정리 없이 당장 불을 끄고 나간다. 다음 날 아침 장부를 보고 어제 상태를 맞춘다"입니다.
