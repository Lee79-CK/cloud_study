1편에서 지은과 민수가 부딪힌 문제의 절반은 기술이 아니라 말이 통하지 않아서 생겼습니다. 지은은 “GPU 메모리가 부족해요”라고 했는데 민수는 노드 메모리를 늘렸고, 민수는 “Pod가 Pending이에요”라고 했는데 지은은 그게 무슨 뜻인지 몰랐습니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 모델, 학습, 손실, 배치, 에폭, 스텝, 체크포인트가 무엇인지 설명하고, 학습 작업의 크기와 저장 공간을 어림할 수 있습니다.

A부

인프라 엔지니어를 위한 ML 기초

수식 없이, 인프라를 설계하고 운영하는 데 필요한 만큼만 다룹니다. 목표는 데이터 과학자의 요청을 자원과 저장 공간과 시간으로 번역하는 것입니다.

1모델과 학습의 정체

모델은 입력을 받아 예측을 내놓는 함수입니다. 함수 안에는 숫자가 잔뜩 들어 있는데, 이것을 가중치(또는 파라미터)라고 부릅니다. 70억 파라미터 모델이라는 말은 이 숫자가 70억 개라는 뜻입니다.

학습은 이 숫자들을 맞추는 과정입니다. 처음에는 아무렇게나 정한 숫자로 예측하고, 정답과 얼마나 틀렸는지(손실)를 계산하고, 손실이 줄어드는 방향으로 숫자를 조금 고칩니다. 이것을 수없이 반복합니다. 이 “조금씩 고치기”의 방법을 경사하강법, 한 번에 얼마나 고칠지를 학습률이라고 합니다.

가장 작은 모델로 직접 해 봅시다. 기온으로 아이스크림 판매량을 예측하는 모델입니다. 가중치는 기울기와 절편, 단 두 개입니다. 먼저 슬라이더로 직접 선을 맞춰 보고, 그다음 학습 버튼을 눌러 기계가 맞추는 과정을 보세요.

학습률
스텝 0손실(평균 제곱 오차) 0

분홍색 세로선이 예측과 정답의 차이, 즉 오차입니다. 학습은 이 선들의 길이를 전체적으로 줄이는 일입니다. 학습률을 바꿔 보면 세 가지를 확인할 수 있습니다. 너무 작으면 한참 걸리고, 적당하면 빠르게 안정되고, 너무 크면 정답을 지나쳐 오히려 손실이 폭발합니다.

인프라 엔지니어에게 이것이 왜 중요한가

실제 모델은 가중치가 두 개가 아니라 수십억 개이고, 데이터는 13개가 아니라 수백만 건입니다. 하지만 하는 일은 똑같습니다. 예측, 손실 계산, 가중치 수정의 반복. 이 반복 한 번 한 번이 엄청난 양의 행렬 곱셈이라서 GPU가 필요하고, 반복 횟수가 많아서 학습이 몇 시간, 며칠씩 걸립니다. 학습률이 잘못되면 GPU 수백 시간을 쓰고도 쓸모없는 모델이 나옵니다. 데이터 과학자가 같은 학습을 여러 번 다시 돌리는 이유 중 하나입니다.

학습 데이터, 검증 데이터, 테스트 데이터

모델이 학습 데이터만 외워 버리면 새 데이터에서는 엉망이 됩니다. 이것을 과적합이라고 합니다. 그래서 데이터를 보통 셋으로 나눕니다. 학습 데이터로 가중치를 맞추고, 검증 데이터로 학습 도중 성능을 확인하며 하이퍼파라미터를 고르고, 테스트 데이터로 마지막에 딱 한 번 최종 성능을 잽니다. 시험 범위를 공부(학습)하고, 모의고사(검증)를 보고, 실제 시험(테스트)을 치르는 것과 같습니다.

2배치, 에폭, 스텝

학습 로그와 설정에 가장 자주 나오는 세 단어입니다. 이것만 알면 학습이 얼마나 걸릴지, 체크포인트를 얼마나 자주 만들지 어림할 수 있습니다.

용어뜻비유
배치가중치를 한 번 고치기 전에 함께 보는 데이터 묶음. 배치 크기 32는 32건을 보고 한 번 고친다는 뜻문제집에서 한 번에 푸는 문제 수
스텝배치 하나를 처리하고 가중치를 한 번 고치는 단위. 이터레이션이라고도 함채점하고 오답 노트를 쓰는 한 번
에폭전체 학습 데이터를 처음부터 끝까지 한 번 다 본 것문제집 한 권을 한 바퀴 다 푼 것
전역 배치GPU 여러 장으로 학습할 때 모든 GPU가 한 스텝에 함께 보는 데이터 수. GPU당 배치 × GPU 수여러 학생이 나눠 푼 문제를 모아 한 번에 채점

숫자를 넣어 계산해 보세요. 데이터 과학자에게 “에폭 3번, GPU당 배치 32, GPU 4장”이라는 말을 들었을 때 머릿속에서 바로 할 수 있어야 하는 계산입니다.

스텝당 시간은 모델과 GPU에 따라 크게 다릅니다. 실제로는 학습을 잠깐 돌려 로그에 찍히는 값을 넣으세요. 데이터를 불러오는 시간, 검증 시간, 체크포인트 저장 시간은 빠져 있습니다.

GPU를 늘리면 에폭당 스텝이 줄어듭니다

GPU 4장으로 데이터를 나눠 보면 전역 배치가 4배가 되고, 에폭당 스텝 수는 4분의 1이 됩니다. 그래서 같은 에폭을 더 짧은 시간에 끝냅니다. 다만 GPU끼리 결과를 맞추는 통신 시간이 추가되므로 정확히 4배 빨라지지는 않습니다. 이 통신이 5장에서 다룰 NCCL과 네트워크 이야기로 이어집니다.

3학습과 추론은 다른 일

학습은 가중치를 만드는 일이고, 추론은 만들어진 가중치로 예측만 하는 일입니다. 같은 모델이라도 인프라에 요구하는 것이 완전히 다릅니다. Kubeflow에서 학습은 Trainer가, 추론은 KServe가 맡는 이유이기도 합니다.

4체크포인트

체크포인트는 학습 도중의 상태를 통째로 저장한 파일입니다. 게임의 세이브 파일과 같습니다. 학습이 사흘 걸리는데 이틀째에 노드가 재시작되면, 체크포인트가 없으면 처음부터, 있으면 마지막 저장 지점부터 다시 시작합니다.

체크포인트에 들어 있는 것

  • 모델 가중치: 지금까지 학습된 숫자들. 추론에는 이것만 있으면 됩니다.
  • 옵티마이저 상태: Adam 같은 옵티마이저가 가중치마다 따로 들고 있는 보조 값. 가중치보다 몇 배 큽니다. 이어서 학습하려면 반드시 필요합니다.
  • 진행 위치: 몇 번째 에폭, 몇 번째 스텝까지 했는지, 학습률 스케줄이 어디까지 왔는지.
  • 난수 상태: 데이터를 섞는 순서 등을 똑같이 이어 가기 위한 값.

그래서 “모델 파일”과 “학습 재개용 체크포인트”는 크기가 크게 다릅니다. 스토리지를 설계할 때 이 차이를 놓치면 디스크가 금방 찹니다. 계산해 보세요.

학습 재개용 체크포인트는 Adam 옵티마이저와 혼합 정밀도 학습 기준으로 파라미터당 약 12~16바이트로 어림했습니다. 설정에 따라 달라지므로 실제 크기는 첫 체크포인트로 확인하세요.

체크포인트를 어디에 두느냐가 인프라의 몫입니다

컨테이너 안에 저장하면 Pod가 사라질 때 함께 사라집니다. 반드시 PVC나 오브젝트 스토리지처럼 Pod 밖에 남는 곳에 저장해야 합니다. 그리고 저장 도중 Pod가 죽으면 반쯤 쓰인 파일이 남을 수 있으므로, 임시 이름으로 쓴 뒤 이름을 바꾸는 방식이 안전합니다. 11장의 코드에서 실제 모습을 봅니다.

5GPU와 분산 학습

GPU는 단순한 계산 수천 개를 동시에 처리하는 칩입니다. 딥러닝의 계산은 거의 전부 거대한 행렬 곱셈이라 GPU에 딱 맞습니다. 인프라 입장에서 GPU에 대해 꼭 알아야 할 것은 세 가지입니다.

첫째, 병목은 대개 GPU 메모리입니다

GPU에는 노드의 RAM과 별개인 자체 메모리(VRAM)가 있습니다. 모델이 이 메모리에 올라가지 않으면 아무리 빠른 GPU라도 학습도 추론도 할 수 없습니다. 무엇이 GPU 메모리를 채우는지 보면 이렇습니다.

  • 추론: 가중치, 그리고 LLM이라면 대화 길이와 동시 요청 수에 비례해 커지는 KV 캐시.
  • 학습: 가중치, 기울기, 옵티마이저 상태, 중간 계산값(활성값). 전체 미세 조정은 추론보다 몇 배 더 필요합니다.

그래서 정밀도를 낮추는 양자화(BF16을 INT8, INT4로)나, 가중치 일부만 학습하는 LoRA 같은 기법이 중요합니다. 대략 어떤 GPU에 올라가는지 어림해 보세요.

아주 거친 어림값입니다. 추론은 가중치에 20% 여유를, LoRA는 30% 여유를 더했고, 전체 미세 조정은 정밀도 설정과 상관없이 혼합 정밀도 Adam 기준 파라미터당 약 16바이트에 활성값 여유 20%를 더했습니다. LLM 추론의 KV 캐시는 동시 사용자와 문맥 길이에 따라 수십 GB가 더 필요할 수 있습니다. 여러 장이 필요하다고 나오면 모델을 GPU 여러 장에 나누는 기법이 필요합니다(7편).

둘째, 소프트웨어 버전이 맞아야 합니다

GPU를 쓰려면 노드의 NVIDIA 드라이버, 컨테이너 이미지 안의 CUDA 런타임, 그 위의 PyTorch 버전이 서로 호환되어야 합니다. 1편에서 지은의 코드가 서버에서 다르게 동작한 이유 중 하나입니다. 일반적으로 이미지의 CUDA 버전은 노드 드라이버가 지원하는 버전보다 높으면 안 됩니다. Kubernetes에서는 보통 NVIDIA GPU Operator가 드라이버와 장치 플러그인을 관리합니다(11편).

셋째, 분산 학습은 통신이 핵심입니다

모델이나 데이터가 커서 GPU 한 장으로 부족하면 여러 장, 여러 노드로 나눕니다. 나누는 방식은 크게 두 가지입니다.

방식무엇을 나누나언제 쓰나
데이터 병렬모델은 GPU마다 통째로 복사하고, 데이터를 나눠 처리. 스텝마다 기울기를 서로 맞춤모델이 GPU 한 장에 들어가지만 학습을 빨리 끝내고 싶을 때. 가장 흔함
모델 병렬 계열 (FSDP, 텐서·파이프라인 병렬)가중치와 옵티마이저 상태 자체를 여러 GPU에 쪼개 나눠 가짐모델이 GPU 한 장에 들어가지 않을 때. 대형 LLM 학습

어느 쪽이든 GPU끼리 결과를 끊임없이 주고받습니다. 이 통신을 맡는 라이브러리가 NCCL이고, 같은 노드 안에서는 NVLink, 노드 사이에서는 InfiniBand나 고속 이더넷을 탑니다. 노드 간 네트워크가 느리면 GPU를 늘려도 학습이 빨라지지 않습니다. 네트워크 설계가 인프라 엔지니어의 몫인 이유입니다.

분산 학습 프로세스는 서로를 어떻게 찾을까

각 프로세스는 자기 순번(RANK), 전체 프로세스 수(WORLD_SIZE), 대장 노드의 주소(MASTER_ADDR, MASTER_PORT)를 알아야 합니다. PyTorch의 실행 도구인 torchrun이 이 값들로 프로세스를 띄웁니다. 직접 하면 노드마다 값을 손으로 맞춰야 하지만, Kubeflow Trainer는 TrainJob을 받으면 노드 수와 순번, 마스터 주소를 자동으로 환경 변수로 넣어 줍니다. 7편에서 자세히 봅니다.

6컨테이너와 이미지

“제 노트북에서는 잘 돼요” 문제의 해법이 컨테이너입니다. 코드가 돌아가는 데 필요한 모든 것, 즉 운영체제 라이브러리, Python 버전, pip 패키지, CUDA 런타임까지 한 덩어리로 굳혀 둔 것을 컨테이너 이미지라고 하고, 그 이미지를 실제로 실행한 것이 컨테이너입니다. 이미지는 요리법이 적힌 밀키트, 컨테이너는 그 밀키트로 실제 만든 요리입니다. 같은 밀키트로 만들면 어느 주방에서든 같은 맛이 납니다.

이미지는 Dockerfile이라는 설명서로 만들고, 만든 이미지는 레지스트리라는 저장소에 올려 두면 Kubernetes가 거기서 내려받아 실행합니다.

학습용 이미지를 만드는 Dockerfile 예시

# CUDA와 PyTorch가 이미 들어 있는 공식 이미지에서 출발
FROM pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # 버전을 고정한 목록
COPY train.py .
CMD ["python", "train.py"]
데이터 과학자가 지킬 세 가지

첫째, requirements.txt에 패키지 버전을 정확히 적으세요(torch==2.8.0처럼). 둘째, 이미지 태그에 latest를 쓰지 말고 reco-train:1.4처럼 버전을 붙이세요. latest는 언제든 내용이 바뀌어 재현성이 깨집니다. 셋째, 데이터와 모델 파일은 이미지에 넣지 마세요. 이미지가 수십 GB로 커지고 데이터가 바뀔 때마다 다시 만들어야 합니다. 데이터는 9장의 스토리지에 둡니다.

7Kubernetes가 일하는 방식

Kubernetes에는 “이걸 실행해”라고 명령하지 않습니다. “이런 상태가 되기를 원해”라고 적어서 제출하면, Kubernetes가 실제 상태를 그쪽으로 계속 맞춥니다. 이것을 선언형이라고 합니다. 원하는 상태를 적은 문서가 YAML 매니페스트입니다.

Kubeflow가 Kubernetes 네이티브라는 말이 바로 이것입니다.

9자원 요청과 스토리지

  
requests와 limits

  
Pod는 필요한 CPU와 메모리를 두 가지 숫자로 적습니다. requests는 “최소 이만큼은 보장해 주세요”이고, 스케줄러가 노드를 고를 때 이 값을 봅니다. limits는 “이 이상은 쓰지 않겠습니다”라는 상한입니다. 두 값을 넘었을 때 벌어지는 일이 자원마다 다릅니다.

  

    
자원limits를 넘으면ML에서 흔한 장면

    
      
CPU죽지 않고 느려짐(스로틀링)데이터 로딩이 느려져 GPU가 놀고 있음

      
메모리(RAM)컨테이너가 강제 종료됨. 상태는 OOMKilled, 종료 코드 137데이터셋을 한꺼번에 메모리에 올렸을 때

      
GPUlimits에 정수로만 적고, 적은 장수만 그 컨테이너가 독점GPU를 적지 않으면 아예 GPU가 보이지 않음

    
  

  

    OOMKilled와 CUDA out of memory는 다른 문제입니다
    
1편의 지은과 민수처럼 가장 많이 엇갈리는 지점입니다. OOMKilled는 노드의 RAM, 즉 Pod의 메모리 limits를 넘어 Kubernetes가 컨테이너를 죽인 것입니다. 해결은 메모리 limits를 올리거나 데이터를 나눠 읽는 것입니다. CUDA out of memory는 GPU 자체의 메모리가 부족해 Python 코드 안에서 난 에러입니다. Pod는 Error나 CrashLoopBackOff로 보이고, 로그에 이 문구가 찍힙니다. 해결은 배치 크기를 줄이거나, 정밀도를 낮추거나, 더 큰 GPU나 분산 학습을 쓰는 것입니다. 메모리 limits를 아무리 올려도 해결되지 않습니다.

  

  
GPU는 nvidia.com/gpu라는 이름의 자원으로 요청합니다. GPU 장치 플러그인이 노드의 GPU를 이 이름으로 Kubernetes에 알려 주기 때문입니다. 기본 상태에서는 0.5장처럼 쪼개 요청할 수 없고, 한 장을 여러 Pod가 나눠 쓰려면 MIG나 time-slicing 같은 별도 구성이 필요합니다(11편).


  
데이터는 어디에 두나

  
컨테이너 안에 쓴 파일은 Pod가 사라지면 함께 사라집니다. 남겨야 하는 것은 반드시 바깥 저장소에 둬야 합니다.

  

    
저장 위치수명어울리는 용도

    
      
컨테이너 내부 디스크컨테이너와 함께 사라짐임시 파일

      
emptyDirPod와 함께 사라짐. 같은 Pod의 컨테이너끼리 공유임시 캐시, 그리고 메모리 기반으로 만들어 /dev/shm 확장

      
PVC (PersistentVolumeClaim)Pod가 사라져도 남음체크포인트, 노트북 작업 폴더, 자주 읽는 데이터셋

      
오브젝트 스토리지 (S3 호환)독립적으로 계속 남음원본 데이터셋, 완성된 모델 파일, 파이프라인 아티팩트

    
  

  
PVC를 만들 때는 접근 모드를 고릅니다. ReadWriteOnce(RWO)는 한 노드에서만 읽고 쓸 수 있고, 블록 스토리지 대부분이 이 방식입니다. ReadWriteMany(RWX)는 여러 노드가 동시에 읽고 쓸 수 있어, 여러 노드에 걸친 분산 학습이 같은 데이터와 체크포인트 폴더를 공유할 때 필요합니다. NFS나 분산 파일 시스템처럼 RWX를 지원하는 StorageClass가 있어야 합니다. 어떤 StorageClass가 있는지는 인프라 담당자에게 물어보세요.

  

    PyTorch DataLoader가 bus error로 죽는다면
    
PyTorch DataLoader는 num_workers를 1 이상으로 주면 워커 프로세스끼리 공유 메모리(/dev/shm)로 데이터를 주고받습니다. 그런데 컨테이너의 기본 공유 메모리는 64MB 정도로 작아서 “bus error”나 “DataLoader worker killed” 에러가 납니다. 메모리 기반 emptyDir을 /dev/shm에 붙이면 해결됩니다. 8장 YAML의 dshm 볼륨이 바로 이것입니다.

11학습 코드가 Job이 되기까지

  
지은의 학습 코드를 Kubernetes에서 안전하게 돌리려면 세 가지가 맞물려야 합니다. 체크포인트로 이어 달릴 수 있는 코드, 환경을 굳힌 이미지, 자원과 저장소를 적은 YAML입니다.

  
1단계: 중간에 죽어도 이어서 학습하는 train.py (데이터 과학자의 몫)


import os, torch

CKPT = "/ckpt/last.pt"                        # PVC가 붙는 경로
model = build_model()
opt = torch.optim.AdamW(model.parameters(), lr=args.lr)
start_epoch = 0

if os.path.exists(CKPT):                       # 재시작이라면 이어서
    state = torch.load(CKPT)
    model.load_state_dict(state["model"])
    opt.load_state_dict(state["optimizer"])     # 옵티마이저 상태까지 복원
    start_epoch = state["epoch"] + 1

for epoch in range(start_epoch, args.epochs):
    train_one_epoch(model, opt)
    torch.save({"model": model.state_dict(),
                "optimizer": opt.state_dict(),
                "epoch": epoch}, CKPT + ".tmp")
    os.replace(CKPT + ".tmp", CKPT)            # 저장 중에 죽어도 이전 파일은 안전

15정리와 다음 편

  
    
    
  1. 학습은 예측, 손실 계산, 가중치 수정의 반복입니다. 배치는 한 번에 보는 묶음, 스텝은 한 번의 수정, 에폭은 전체 데이터 한 바퀴입니다. GPU를 늘리면 전역 배치가 커지고 에폭당 스텝이 줄어듭니다.
    2. 
    
  2. 학습과 추론은 다른 일입니다. 학습은 끝이 있는 작업(Job, TrainJob), 추론은 계속 떠 있는 서버(Deployment, InferenceService)이고, GPU 메모리 요구도 크게 다릅니다.
    3. 
    
  3. 체크포인트에는 가중치뿐 아니라 옵티마이저 상태가 들어 있어 모델 파일보다 훨씬 큽니다. 반드시 Pod 밖의 저장소에 둡니다.
    4. 
    
  4. Kubernetes는 원하는 상태를 적어 제출하면 컨트롤러가 실제 상태를 맞추는 방식으로 일하고, Kubeflow의 Operator도 같은 자리에서 일합니다.
    5. 
    
  5. OOMKilled는 RAM limits 초과, CUDA out of memory는 GPU 메모리 부족입니다. Pending은 대부분 원하는 자원을 줄 노드가 없다는 뜻이고, describe의 Events가 답을 알려 줍니다.
    6. 
  

    
현장에서 쓰이는 장면

  
  • 제조. 공장 비전 모델의 데이터 과학자가 “GPU 메모리 40GB가 필요하다”고 하면, 인프라 담당자는 5장 계산기로 어떤 GPU가 몇 장 필요한지 바로 답합니다.
  • 금융. 감사 담당자가 “이 모델은 어떤 환경에서 학습됐나”를 물으면, 이미지 태그와 체크포인트 메타데이터가 답이 됩니다.
  • 연구소. 학생의 학습 Pod가 죽었을 때 OOMKilled(RAM)와 CUDA OOM(GPU)을 구별할 수 있으면 조교의 하루가 절반으로 줄어듭니다.
