Cloud 모니터링·로깅 실전 강의 16편 (Level 5. 대규모 운영, 마지막 편)

운영, 용량, 비용, 보안

관제 센터는 이제 고객사 둘, 저장소 다섯, 수집기 수십 개를 가진 하나의 플랫폼입니다. 이 플랫폼이 조용히 고장 나거나, 한 고객사의 실수가 모두의 비용이 되거나, 디스크 하나에 데이터가 사라지지 않도록 플랫폼 자체를 운영합니다. 중심 실습은 실제로 재현한 카디널리티 폭증 사고입니다.

대상: 1~2년차 클라우드 엔지니어 형식: 개념 + 실습 5개 예상 소요: 4시간 기준: Mimir 3.2.2, Prometheus 3.13.1
사고 재생: user_id 라벨 하나가 일으킨 일작성 중 실제로 재현한 사고를 단계별로 다시 봅니다. 숫자는 모두 Mimir 3.2.2와 Prometheus 3.13.1에서 나온 값입니다.

0시작하기 전에

Level 5의 마지막 편입니다. 지금까지 만든 것을 "고객사에게 파는 서비스"로 운영하기 위해 필요한 일을 다룹니다.

학습 목표

  1. 관측 플랫폼 자체를 감시하는 메트릭과 알림(메타 모니터링)을 설계하고 단위 테스트할 수 있다.
  2. 신호별 용량을 실측 기반으로 산정하고 고객사 등급별 보존 정책을 정할 수 있다.
  3. 카디널리티 예산을 테넌트, 지표 단위로 걸고, 폭증을 탐지하고 올바르게 대응할 수 있다.
  4. 고객사별 사용량을 측정해 비용을 배분(쇼백, 차지백)할 수 있다.
  5. Grafana 조직, 저장소 테넌트, 비밀 관리, 감사 로그로 접근을 통제할 수 있다.
  6. 백업과 DR의 범위(무엇이 어디에 있는가)를 알고 복구 훈련과 업그레이드 순서를 계획할 수 있다.
이 편의 검증 범위

Mimir 3.2.2와 Prometheus 3.13.1로 카디널리티 폭증을 실제로 재현했습니다. 지표당 한도 초과로 샘플 11,750개가 폐기되는 과정, 잘못된 응급 처치(labeldrop)가 오류 없이 데이터를 틀어 버리는 현상, 올바른 처치(drop) 후 폐기가 멈추는 것, sample_limit 방어가 대상 전체를 내리는 것, Mimir 카디널리티 분석 API를 확인했습니다. 플랫폼 감시 규칙은 promtool test rules를 통과했고, overrides-exporter의 테넌트 한도 메트릭과 고객사별 사용량 메트릭을 확인했으며, 인제스터 로컬 디스크를 지운 뒤 오브젝트 스토리지에서 과거 데이터를 다시 조회하는 복구 훈련을 실행했습니다. Grafana 조직 분리(Lab 4)는 Grafana를 실행하지 못해 API 문서에 맞춰 작성했습니다.

1메타 모니터링

관제 시스템이 고장 나면 고객사 장애도 보이지 않습니다. 그래서 관제 시스템을 감시하는 관제, 메타 모니터링이 필요합니다.

감시 대상핵심 메트릭실패하면
고객사 쪽 Prometheus, Alloyprometheus_remote_storage_samples_failed_total, ..._pending, loki_write_dropped_entries_total고객사 데이터가 중앙에 오지 않음
통합 입구파드 Ready, 응답 코드 비율 (nginx 메트릭 노출 시)모든 고객사 수신 중단

Lokiloki_discarded_samples_total{reason} (7편)로그 폐기
Tempo, Pyroscope, OTLP 게이트웨이수신 거부, 내보내기 실패(otelcol_exporter_send_failed_*, 11편)트레이스, 프로파일 유실
Alertmanager 자체Watchdog과 외부 데드맨(6편)알림이 아예 안 감

누가 감시자를 감시하나

메타 모니터링을 감시 대상과 같은 경로에 두면 함께 죽습니다. Mimir의 ruler로 "Mimir가 데이터를 버린다" 알림을 평가하면 Mimir가 아플 때 그 알림도 아픕니다. 그래서 이 시리즈는 플랫폼 감시 규칙을 hub의 kube-prometheus-stack Prometheus에서 로컬로 평가하고, hub Alertmanager → 6편의 외부 데드맨 순서로 이중화합니다. hub Prometheus가 Mimir, Loki 등의 메트릭을 ServiceMonitor로 직접 수집하고 있으므로(7편부터) 추가 설치가 없습니다.

Mimir, Loki, Tempo는 각각 공식 "mixin"(대시보드와 알림 규칙 묶음)을 제공합니다. 처음부터 다 만들기보다 mixin을 가져와 고객사 라벨과 임계값만 맞추는 것이 현실적입니다. 이 편의 Lab 1은 그 위에 MSP에 특화된 규칙 네 개를 더합니다.

2용량 산정과 보존 정책

용량은 표의 숫자보다 내 환경에서 잰 비율로 산정합니다. 같은 지표도 라벨 구성, 수집 간격, 압축률이 환경마다 다르기 때문입니다.

신호크기를 정하는 것잴 메트릭이 시리즈의 실측 근거
메트릭 (Mimir)활성 시계열 × 수집 빈도 × 보존cortex_ingester_active_series, process_resident_memory_bytes ÷ 시계열 수 (시계열당 메모리)요약 전송 8.6% (14편)
로그 (Loki)하루 바이트 × 압축 후 비율 × 보존, 스트림 수loki_distributor_bytes_received_total, 버킷 크기작은 청크 문제 (7편)
트레이스 (Tempo)초당 span × 평균 크기 × 샘플링 비율 × 보존tempo_distributor_bytes_received_total꼬리 샘플링 보관 16% (12편)
프로파일 (Pyroscope)프로세스 수 × 프로파일 종류 × 보존distributor 수신 바이트표본 간격, 앱 부하에 비례 (13편)
감사 로그 (OpenSearch)하루 문서 × 문서 크기 × (1 + 레플리카) × 보존_cat/indices의 store.sizeISM 정책 (10편)

신호기본프리미엄근거
메트릭 요약90일13개월전년 동월 비교, 연간 용량 보고
운영 로그14일30일장애 조사 기간

프로파일7일14일배포 전후 비교
감사 로그계약, 법령 기준 (흔히 1년 이상, 스냅샷 보관)10편 1장

보존은 저장소마다 테넌트별로 설정합니다. Mimir는 런타임 설정의 compactor_blocks_retention_period(14편), Loki는 runtimeConfig의 retention_period(7편), Tempo는 테넌트 overrides, OpenSearch는 고객사별 ISM 정책입니다. 오브젝트 스토리지 버킷의 수명주기 규칙은 반드시 앱의 보존보다 길게 두거나 두지 않습니다. 버킷이 먼저 지우면 앱의 인덱스가 사라진 블록이나 청크를 가리켜 질의 오류가 납니다.

S3가 아닌 오브젝트 스토리지

이 랩은 S3 호환(SeaweedFS)을 썼지만, Mimir, Loki, Tempo, Pyroscope는 모두 Azure Blob과 Google Cloud Storage를 직접 지원합니다. Mimir를 예로 들면 common.storage.backend를 azure(계정 이름, 키 또는 관리 ID, 컨테이너 이름)나 gcs(버킷 이름, 서비스 계정)로 바꾸고 나머지 구조는 그대로입니다. 고객사가 Azure 중심이면 관제 센터를 Azure에 두고 Blob을 쓰는 것이 데이터 이동 비용상 유리할 수 있습니다.

3카디널리티 예산

메트릭 플랫폼 비용과 장애의 가장 흔한 원인은 값이 끝없이 늘어나는 라벨(사용자 ID, 요청 ID, URL 원문)입니다. 7편의 Loki 스트림, 3편의 Prometheus에서 본 문제가 중앙 Mimir에서는 "모든 고객사가 함께 쓰는 자원"을 먹는다는 점에서 더 위험합니다.

방어선설정동작
1. 계측 표준라벨 설계 규칙 (4, 8편)값이 무한한 정보는 라벨 금지
2. 수집 단계metric_relabel_configs의 drop, sample_limit, label_limit문제 지표를 버리거나, 대상당 표본 수를 넘으면 그 수집 전체를 실패시킴
3. 전송 단계write_relabel_configs (14편 요약 전송)중앙에는 필요한 것만
4. 중앙 테넌트 한도max_global_series_per_user고객사 전체 예산
5. 중앙 지표 한도max_global_series_per_metric지표 하나가 고객사 예산을 다 먹지 못하게

4, 5번이 걸리면 Mimir는 넘치는 새 시계열의 샘플을 400으로 거부하고, Prometheus는 이를 재시도해도 소용없는 오류로 보고 버립니다. 기존 시계열은 계속 받으므로 다른 지표가 갑자기 끊기지는 않지만, 그 고객사의 새 지표가 들어오지 못하는 상태가 됩니다. 그래서 한도에 닿기 전에(예: 80%) 경고하는 것이 예산 운영의 핵심입니다(Lab 1의 TenantSeriesBudget80).

실측: labeldrop은 응급 처치가 아니라 사고입니다

문제 지표에서 user_id 라벨만 지우면(action: labeldrop) 시계열 2,000개가 이름과 나머지 라벨이 같은 하나로 겹칩니다. Prometheus 3.13.1은 이것을 오류로 내지 않았고(up=1, 수집 오류 없음, 중복 표본 카운터 0), 겹친 시계열에는 첫 사용자의 값 2만 남았습니다. 같은 시각 실제 합계(shop_checkout_total)는 4,652였습니다. 카운터에서 라벨을 지우는 것은 합계가 아니라 임의의 한 값을 남깁니다. 올바른 응급 처치는 지표를 통째로 버리는 action: drop이고, 근본 해결은 계측 코드를 고쳐 합계 지표만 내는 것입니다.

5접근 통제, 비밀, 감사

세 겹의 접근 통제

층무엇을 막나이 시리즈의 장치
수신다른 고객사로 데이터 쓰기통합 입구의 인증 → 테넌트 강제 (15편)
저장다른 고객사 데이터 읽기모든 저장소의 X-Scope-OrgID 테넌트, OpenSearch 역할(10편)
조회 화면다른 고객사 데이터소스 사용Grafana 조직 분리 (Lab 4)

Grafana의 데이터소스 권한(누가 어떤 데이터소스로 질의할 수 있는가)은 Enterprise와 Cloud 기능입니다. 오픈소스 Grafana에서는 같은 조직 안의 모든 사용자가 그 조직의 데이터소스를 쓸 수 있으므로, 고객사마다 조직을 따로 만들고 그 조직에 자기 테넌트 데이터소스만 두는 것이 확실한 분리 방법입니다. 관제 센터 운영자는 MSP 조직에서 테넌트 연합 데이터소스(14편)로 전체를 봅니다. 대시보드는 조직마다 복제해야 하므로 6편처럼 코드(ConfigMap, API)로 관리해야 감당할 수 있습니다. 조직 안에서는 팀과 폴더 권한(보기, 편집)으로 고객사 담당자와 MSP 엔지니어의 권한을 나눕니다.

비밀 관리

  • 목록: S3 접근 키(7, 12~14편), OpenSearch 계정(10편), 입구 비밀번호(15편), Grafana 관리자, 클라우드 자격 증명(15편).
  • 보관: Git에는 평문으로 두지 않습니다. Kubernetes는 External Secrets Operator로 Vault나 클라우드 비밀 저장소에서 가져오거나 Sealed Secrets로 암호화해 Git에 둡니다. VM은 ansible-vault(15편).
  • 교체: 입구 비밀번호는 새 값과 옛 값을 htpasswd에 함께 두고 → Ansible로 수집기를 새 값으로 → 옛 값 삭제 순서로 중단 없이 바꿉니다. 교체 주기와 담당자를 운영 점검표에 둡니다.

감사 로그

1. 문제 앱과 예산

~/obs-lab/vm/bomb/bomb.py

#!/usr/bin/env python3
"""cardinality-bomb: user_id를 라벨로 쓰는 잘못된 계측을 흉내 냄 (16편 Lab 2)
요청할 때마다 새 사용자가 늘어나, 1분에 약 600개의 새 시계열이 생깁니다."""
import http.server, random, time, threading
users = {}
lock = threading.Lock()
def grow():
    n = 0
    while True:
        with lock:
            for _ in range(10):
                n += 1
                users[f"u{n}"] = users.get(f"u{n}", 0) + random.randint(1, 3)
        time.sleep(1)
class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        with lock:
            lines = ["# TYPE shop_checkout_by_user_total counter"]
            lines += [f'shop_checkout_by_user_total{{user_id="{u}"}} {v}' for u, v in users.items()]
            lines += ["# TYPE shop_checkout_total counter", f"shop_checkout_total {sum(users.values())}"]
        body = ("\n".join(lines) + "\n").encode()
        self.send_response(200); self.send_header("Content-Type", "text/plain; version=0.0.4"); self.end_headers(); self.wfile.write(body)
    def log_message(self, *a): pass
threading.Thread(target=grow, daemon=True).start()
http.server.ThreadingHTTPServer(("0.0.0.0", 8010), H).serve_forever()

고객사 담당자에게 Grafana를 열어 줄 수 있도록 고객사마다 조직을 만들고 그 조직에 자기 테넌트 데이터소스만 둡니다.

~/obs-lab/scripts/grafana-orgs.sh

#!/usr/bin/env bash
# 고객사마다 Grafana 조직을 만들고, 그 조직에 자기 테넌트 데이터소스만 넣음 (Grafana OSS)
set -euo pipefail
G=http://localhost:30300; AUTH="admin:lab-admin-change-me"
for c in cust-a cust-b; do
  oid=$(curl -s -u "$AUTH" -H 'Content-Type: application/json' -X POST $G/api/orgs -d "{\"name\":\"$c\"}" | jq -r '.orgId // empty')
  [ -z "$oid" ] && oid=$(curl -s -u "$AUTH" "$G/api/orgs/name/$c" | jq -r .id)
  echo "$c → orgId $oid"
  for ds in "Mimir:prometheus:http://mimir.metrics.svc:8080/prometheus" "Loki:loki:http://loki-gateway.logging.svc"; do
    IFS=: read -r name type url1 url2 <<< "$ds"; url="$url1:$url2"
    curl -s -u "$AUTH" -H "X-Grafana-Org-Id: $oid" -H 'Content-Type: application/json' -X POST $G/api/datasources \
      -d "{\"name\":\"$name ($c)\",\"type\":\"$type\",\"access\":\"proxy\",\"url\":\"$url\",
           \"jsonData\":{\"httpHeaderName1\":\"X-Scope-OrgID\"},\"secureJsonData\":{\"httpHeaderValue1\":\"$c\"}}" | jq -c '{message, name}'
  done
done

Remote Write 400: per-metric series limit exceeded (err-mimir-max-series-per-metric)Lab 2

작성 중 실제로 본 오류입니다. 카디널리티 분석 API로 범인 라벨을 찾고, 수집 단계에서 그 지표를 drop한 뒤 계측을 고칩니다. 정말 필요한 성장이라면 그 테넌트의 max_global_series_per_metric을 올립니다.

err-mimir-max-series-per-user운영

테넌트 전체 예산을 넘었습니다. 어느 지표가 늘었는지 카디널리티 API의 label_names, Prometheus TSDB 상태로 찾습니다. 여러 지표가 고르게 늘었다면 고객사 규모가 커진 것이니 계약과 예산을 다시 봅니다.

labeldrop 후 그래프 값이 이상하게 작아짐Lab 2

cortex_limits_overrides 메트릭이 없음Lab 1

overrides-exporter가 실행되지 않습니다. 단일 바이너리는 -target=all,overrides-exporter, 분산 배포는 차트의 overrides_exporter를 켭니다. 메트릭은 런타임 설정에 그 테넌트의 값이 있을 때만 나옵니다(작성 중 확인).

카디널리티 API가 오류Lab 2

-querier.cardinality-analysis-enabled=true가 필요합니다. 테넌트 헤더도 함께 보냅니다.

오늘의 핵심

  1. 관제 시스템을 감시하는 규칙은 감시 대상과 다른 경로(hub Prometheus 로컬 평가 + 외부 데드맨)에 둡니다. 규칙도 단위 테스트합니다.
  2. 용량은 내 환경에서 잰 비율로, 보존은 고객사 등급과 계약으로 정하고 저장소마다 테넌트별로 설정합니다. 버킷 수명주기는 앱 보존보다 짧으면 안 됩니다.
  3. 카디널리티 예산은 계측, 수집, 전송, 테넌트, 지표의 다섯 겹입니다. 폭증 시 labeldrop은 조용히 값을 틀어 버리고(실측 4,652 → 2), drop이 올바른 응급 처치입니다.
  4. 고객사별 사용량(시계열, 바이트)을 재야 비용을 설명하고 배분할 수 있습니다.
  5. 오픈소스 Grafana에서는 조직으로 고객사를 나눕니다. 비밀은 Git 밖에서 관리하고 교체 절차를 둡니다.
  6. 과거 데이터는 버킷에, 최근 데이터는 인제스터에 있습니다(실측: 로컬 디스크를 지워도 과거 조회 가능). 업그레이드는 받는 쪽부터, 하나씩, 되돌릴 길을 남기고.

Level 5를 마치며

14~16편으로 관측 데이터를 중앙에 모으고(14편), 조건이 다른 고객사를 받고(15편), 그 플랫폼을 서비스로 운영하는 방법(16편)을 다뤘습니다. 이제 남은 것은 이 데이터를 사람 대신 읽는 일과, 전 과정을 한 번에 다시 해 보는 일입니다.

다음 편 예고: 17편 AIOps를 위한 관측 데이터 설계 (Level 6 시작)

LLM 기반 장애 분석 도구가 관측 데이터를 제대로 쓰려면 사람보다 더 엄격한 데이터 표준이 필요합니다. 17편에서는 service.name, customer 같은 식별자 표준을 다시 점검하고, 알림에 관련 정보(대시보드, 런북, 최근 배포, 같은 서비스의 최근 오류 로그)를 붙이는 알림 보강(Enrichment)을 만들고, Prometheus, Loki, Tempo API를 LLM의 도구로 노출하는 방법과 Grafana MCP 서버, 그리고 이 도구들에 줄 읽기 전용 권한을 설계합니다. 실습은 Alertmanager 웹훅을 받는 Python 수신기가 관련 메트릭, 로그, 트레이스를 자동으로 모아 하나의 사건 묶음으로 만드는 것입니다.
