1편 신입 클라우드·AI 엔지니어를 위한 인증·인가 시리즈

비밀번호를 주지 않고 권한만 빌려주는 법

OAuth 2.0은 "이 앱이 내 캘린더를 읽어도 좋다"는 허락을, 내 비밀번호를 넘기지 않고 전달하는 표준입니다. 이 강의에서는 왜 이런 게 필요했는지부터 시작해서, 실무에서 쓰는 네 가지 흐름과 각각의 실제 HTTP 요청까지 따라가 봅니다.

예상 학습 시간 40~60분 사전 지식: HTTP 요청/응답, JSON 실습 요소 7개

일정 관리 앱에 내 구글 캘린더를 연결하려 합니다. 두 가지 방법 중 하나를 골라 보세요.

00

OAuth가 없던 시절

2000년대 후반, 어떤 서비스가 내 주소록을 읽어서 "이미 가입한 친구"를 찾아주려면 방법이 하나뿐이었습니다. 그 서비스 화면에 내 지메일 아이디와 비밀번호를 그대로 입력하는 것이죠. 서비스는 그 계정으로 직접 로그인해서 주소록을 긁어 왔습니다. 이걸 비밀번호 안티패턴이라고 부릅니다.

당시에는 다들 그러려니 했지만, 지금 보면 문제가 한두 개가 아닙니다.

권한을 쪼갤 수 없다

주소록만 읽게 하고 싶었는데, 비밀번호를 가진 서비스는 메일을 읽고 보내고 지울 수도 있습니다. 계정 비밀번호를 바꾸거나 탈퇴시킬 수도 있고요. "읽기만"이라는 개념 자체가 없습니다.

되돌릴 방법이 없다

그 서비스만 끊고 싶어도 방법이 없습니다. 비밀번호를 바꾸면 같은 비밀번호를 준 다른 서비스 다섯 개가 동시에 멈춥니다. 권한 회수가 전부 아니면 전무입니다.

사고가 연쇄된다

그 서비스의 DB가 털리면 내 구글 계정도 같이 털립니다. 한 곳의 사고가 다른 회사 계정으로 번집니다. 비밀번호를 평문으로 저장해 둔 곳이라면 더 말할 것도 없습니다.

2단계 인증과 공존할 수 없다

OTP나 생체 인증을 켜는 순간, 아이디와 비밀번호만 아는 서비스는 로그인에 실패합니다. 보안을 강화할수록 연동이 깨지는 구조입니다.

OAuth는 이 네 가지를 한 번에 해결하려고 만들어졌습니다. 핵심 아이디어는 간단합니다. 비밀번호 대신, 기한이 있고 범위가 정해진 증표를 발급한다. 그 증표를 액세스 토큰이라고 부릅니다.

현실의 비유: 발레파킹 키

고급 차량에는 발레파킹 전용 키가 따로 있습니다. 시동은 걸리지만 최고 속도가 제한되고, 트렁크와 글러브 박스는 열리지 않습니다. 주차 요원에게 필요한 건 딱 그만큼이니까요. 액세스 토큰이 바로 이 발레파킹 키입니다. 마스터 키(비밀번호)는 내 주머니에 그대로 있습니다.

용어 정리: 인증과 인가는 다릅니다

둘 다 영어 약자가 auth로 시작해서 신입 때 가장 많이 헷갈리는 부분입니다. 확실히 갈라 두고 가겠습니다.

구분인증 (Authentication)인가 (Authorization)
질문너는 누구냐?너는 무엇을 해도 되느냐?

가장 흔한 오해

"구글로 로그인" 버튼을 OAuth라고 부르는 경우가 많은데, 엄밀히 말하면 그건 OAuth 위에 얹은 OpenID Connect입니다. OAuth 2.0 명세 자체에는 "이 사용자가 누구인가"를 알려주는 기능이 없습니다. 토큰을 받았다는 사실만으로 사용자의 신원을 단정하면 취약점이 됩니다. 이 부분은 2편에서 제대로 다룹니다.

01

네 명의 등장인물

OAuth 문서를 읽다가 막히는 첫 번째 지점은 대개 역할 이름입니다. 등장인물은 넷뿐이고, 이 강의 전체에서 각자 고유한 색을 달고 다닙니다. 색만 봐도 지금 누가 무슨 말을 하는지 알 수 있도록요.

리소스 소유자

Resource Owner

데이터의 주인. 대부분의 경우 사람, 즉 사용자 본인입니다. 권한을 빌려줄지 말지 최종 결정하는 사람입니다.

예) 내 캘린더의 주인인 나

클라이언트

Client

권한을 빌리려는 앱. 이름이 헷갈리는데, 여기서 클라이언트는 "사용자"가 아니라 "인가 서버의 고객인 애플리케이션"이라는 뜻입니다.

예) 일정 관리 SaaS, 모니터링 대시보드

인가 서버

Authorization Server

사용자를 로그인시키고, 동의를 받고, 토큰을 발급하는 주체. OAuth의 심장입니다.

예) 구글 계정 서버, Keycloak, Cognito

리소스 서버

Resource Server

실제 데이터를 가진 API 서버. 요청에 담긴 토큰을 검증해서 통과시킬지 말지 결정합니다.

예) 구글 캘린더 API
인가 서버와 리소스 서버가 꼭 다른 서버일 필요는 없습니다

구글처럼 규모가 큰 곳은 분리되어 있지만, 사내 서비스에서는 하나의 애플리케이션이 두 역할을 겸하는 경우도 많습니다. 중요한 건 물리적 서버 개수가 아니라 역할이 분리되어 있다는 개념입니다. 토큰을 발급하는 쪽과 토큰을 검증해서 데이터를 주는 쪽은 책임이 다릅니다.

클라이언트의 두 종류

같은 "앱"이라도 비밀을 지킬 수 있느냐에 따라 취급이 완전히 달라집니다. 뒤에 나오는 PKCE를 이해하려면 이 구분이 먼저 필요합니다.

기밀 클라이언트 비밀 보관 가능

코드가 서버에서만 돌아가는 앱입니다. 백엔드 서버, 배치 작업, 서버 사이드 렌더링 웹앱 등. 소스 코드와 설정 파일이 사용자에게 노출되지 않으므로 client_secret을 안전하게 보관할 수 있습니다.

공개 클라이언트 비밀 보관 불가

코드가 사용자 기기에서 돌아가는 앱입니다. 브라우저 SPA, 모바일 앱, 데스크톱 앱, CLI 도구. 아무리 숨겨도 개발자 도구나 앱 디컴파일로 다 꺼낼 수 있습니다. 여기에 비밀번호나 시크릿을 넣으면 안 됩니다.

실무에서 자주 나오는 사고

React SPA를 만들면서 백엔드 예제 코드를 그대로 복사해 client_secret을 프론트엔드 환경 변수에 넣는 경우가 정말 많습니다. 빌드된 JS 번들에 그대로 박혀 나가기 때문에 누구나 꺼낼 수 있습니다. 공개 클라이언트는 시크릿 없이 동작하도록 설계해야 하고, 그 빈자리를 메우는 장치가 4장의 PKCE입니다.

02

꼭 알아야 할 용어

여기 있는 열두 개만 알면 실무 문서의 90%는 읽힙니다. 지금 다 외울 필요는 없고, 뒤 장에서 막힐 때 돌아와서 펼쳐 보세요.

client_id 앱의 공개 신분증 번호

인가 서버에 앱을 등록하면 발급되는 식별자입니다. 브라우저 주소창에 그대로 노출되는 값이라 비밀이 아닙니다. 남이 안다고 해서 문제가 생기지 않도록 설계되어 있습니다.

client_secret 앱임을 증명하는 비밀번호

앱이 "나는 진짜 그 앱이다"라고 증명할 때 쓰는 값입니다. 서버 대 서버 통신에서만 사용하고, 기밀 클라이언트만 가질 수 있습니다. 브라우저나 모바일 앱에는 절대 넣지 않습니다.

사고가 나면 인가 서버 콘솔에서 시크릿을 재발급(rotate)하는 것이 표준 대응입니다.

redirect_uri 승인 결과가 돌아올 주소

인가 서버가 작업을 마친 뒤 사용자를 다시 보낼 앱의 주소입니다. 앱 등록 시 미리 지정해 두고, 요청에 온 값과 문자열 단위로 정확히 일치할 때만 허용해야 합니다.

느슨하게 검증하면 공격자가 redirect_uri=https://evil.com을 끼워 넣어 인가 코드를 자기 서버로 배달시킬 수 있습니다. 와일드카드 허용, 하위 경로 허용, 앞부분만 비교하는 방식 모두 위험합니다.

response_type 무엇을 돌려받을지 지정

code면 인가 코드를 받겠다는 뜻이고, token이면 액세스 토큰을 브라우저로 바로 받겠다는 뜻입니다. 후자는 폐기된 Implicit 방식이라 지금은 사실상 code만 씁니다.

scope 빌리려는 권한의 범위

공백으로 구분한 문자열 목록입니다. 인가 서버마다 이름이 다르며, 동의 화면에 사람이 읽을 수 있는 문장으로 번역되어 표시됩니다.

# 구글
scope=https://www.googleapis.com/auth/calendar.readonly

# 깃허브
scope=repo:status read:org

# 자체 구축(Keycloak 등)에서 흔히 쓰는 형태
scope=orders:read orders:write invoices:read
state 요청과 응답을 묶는 끈

앱이 만든 예측 불가능한 랜덤 문자열입니다. 요청에 실어 보내면 인가 서버가 그대로 돌려주고, 앱은 돌아온 값이 자기가 보낸 값과 같은지 확인합니다.

이걸 빠뜨리면 로그인 CSRF에 노출됩니다. 공격자가 자기 계정의 인가 코드를 피해자 브라우저로 흘려보내, 피해자가 공격자 계정에 연결되도록 만드는 공격입니다. 세션에 저장했다가 콜백에서 비교하고, 한 번 쓰면 버립니다.

인가 코드 authorization code 토큰으로 바꿀 교환권

수명이 아주 짧고(보통 10초~10분) 한 번만 쓸 수 있는 임시 문자열입니다. 그 자체로는 아무 데이터에도 접근할 수 없고, 오직 토큰 엔드포인트에서 액세스 토큰으로 교환하는 데만 쓰입니다.

access_token 실제 출입증

API를 호출할 때 Authorization: Bearer <토큰> 헤더에 담아 보내는 값입니다. 수명이 짧습니다(보통 5분~1시간). 유출되더라도 피해 기간이 제한되도록 일부러 짧게 잡습니다.

형식은 명세가 강제하지 않습니다. 의미 없는 랜덤 문자열일 수도 있고(불투명 토큰), 안에 정보가 담긴 JWT일 수도 있습니다. 어느 쪽이든 앱 입장에서는 그냥 문자열로 취급하고 열어 보려 하지 않는 것이 원칙입니다.

refresh_token 재발급용 열쇠

액세스 토큰이 만료됐을 때 사용자를 다시 로그인시키지 않고 새 토큰을 받아오는 데 씁니다. 수명이 길어서(며칠~몇 달) 액세스 토큰보다 훨씬 민감합니다. 반드시 서버 측에 암호화해서 보관합니다.

요즘은 리프레시 토큰을 쓸 때마다 새 것으로 바꿔 발급하고(rotation), 이미 쓴 토큰이 다시 들어오면 탈취로 간주해 해당 계정의 토큰을 전부 무효화하는 방식이 권장됩니다.

Bearer 소지자 토큰

"가진 사람이 곧 주인"이라는 뜻입니다. 지하철 승차권처럼, 누가 들고 있든 유효하면 통과시킵니다. 편리한 대신 유출에 취약하므로 HTTPS는 선택이 아니라 필수이고, 로그·URL·리퍼러에 토큰이 남지 않게 관리해야 합니다.

인가 엔드포인트 /authorize 사람이 방문하는 곳

브라우저 주소창으로 접속하는 URL입니다. 사용자에게 로그인 화면과 동의 화면을 보여줍니다. 이 구간을 프론트 채널이라고 부르며, 브라우저를 거치므로 URL에 담긴 값은 히스토리·서버 로그·리퍼러 헤더에 남을 수 있다고 가정해야 합니다.

토큰 엔드포인트 /token 서버끼리 통신하는 곳

앱의 백엔드가 직접 HTTPS로 POST하는 API입니다. 사용자의 브라우저를 거치지 않으므로 백 채널이라고 부릅니다. 토큰처럼 민감한 값은 반드시 이 구간으로만 오갑니다.

03

인가 코드 흐름

Authorization Code Grant. OAuth 2.0에서 가장 중요하고 가장 많이 쓰이는 흐름입니다. 이 하나만 제대로 이해하면 나머지는 변주에 가깝습니다. 아래 다이어그램에서 다음을 눌러 여덟 단계를 따라가 보세요. 각 단계마다 실제로 오가는 HTTP 요청이 함께 표시됩니다.

왜 토큰을 바로 주지 않고 코드를 한 번 거칠까

신입 엔지니어가 가장 많이 던지는 질문입니다. 인가 서버가 5단계에서 액세스 토큰을 바로 주면 왕복이 한 번 줄어들 텐데, 왜 굳이 코드를 주고 다시 교환하게 할까요. 이유는 세 가지입니다.

  1. 토큰이 브라우저를 지나가지 않게 하려고. 5단계는 브라우저 리다이렉트, 즉 URL입니다. URL은 브라우저 히스토리에 남고, 프록시와 웹 서버 액세스 로그에 남고, 그 페이지에서 다른 사이트로 나갈 때 리퍼러 헤더에 실려 갈 수도 있습니다. 여기에 실리는 값이 수명 10초짜리 일회용 코드인 것과 한 시간짜리 액세스 토큰인 것은 위험도가 완전히 다릅니다.
  2. 앱의 신원을 확인하려고. 7단계의 토큰 교환은 서버 대 서버 통신이고, 여기서 client_secret을 함께 보냅니다. 인가 서버는 코드를 가져온 쪽이 정말 등록된 그 앱인지 확인할 수 있습니다. 코드만 훔쳐도 시크릿이 없으면 토큰으로 바꿀 수 없습니다.
  3. 리프레시 토큰을 안전하게 전달하려고. 수명이 긴 리프레시 토큰은 브라우저에 절대 노출되면 안 됩니다. 백 채널에서만 오갑니다.
한 줄 요약

프론트 채널(브라우저, URL)에는 훔쳐도 쓸모가 적은 것만 보내고, 백 채널(서버 대 서버)에서 진짜 값을 주고받습니다. OAuth 설계의 핵심 감각입니다.

04

PKCE — 시크릿 없는 앱을 지키는 법

PKCE는 "픽시"라고 읽습니다. Proof Key for Code Exchange의 약자입니다. 앞 장에서 인가 코드가 안전한 이유로 "코드를 훔쳐도 client_secret이 없으면 토큰으로 못 바꾼다"를 들었는데, 모바일 앱과 SPA에는 그 시크릿이 없습니다. 그러면 코드를 훔친 사람이 그대로 토큰을 받아 갈 수 있습니다.

공격은 이렇게 일어납니다

모바일 앱은 보통 myapp://callback 같은 커스텀 URL 스킴으로 인가 코드를 돌려받습니다. 문제는 iOS와 안드로이드가 같은 스킴을 등록한 앱이 여러 개일 때 어느 앱에 전달할지를 보장하지 않는다는 점입니다.

  1. 공격자가 myapp:// 스킴을 똑같이 등록한 악성 앱을 사용자 기기에 설치시킵니다.
  2. 사용자가 정상 앱에서 로그인을 시작하고, 인가 서버에서 정상적으로 동의합니다.
  3. 인가 서버가 myapp://callback?code=ABC로 리다이렉트합니다.
  4. OS가 이 URL을 악성 앱에 전달합니다. 인가 코드가 공격자 손에 들어갑니다.
  5. 악성 앱이 client_id(공개값)와 훔친 코드로 토큰을 받아 갑니다. 끝.

PKCE의 해결책: 매번 일회용 자물쇠를 만든다

요청을 시작할 때마다 앱이 랜덤 문자열 code_verifier를 만들어 자기 메모리에만 보관합니다. 그리고 그것을 SHA-256으로 해시한 값 code_challenge를 인가 요청에 실어 보냅니다. 나중에 코드를 토큰으로 바꿀 때 원본 code_verifier를 함께 제출해야 하고, 인가 서버는 다시 해시해서 처음 받은 값과 같은지 확인합니다.

해시는 되돌릴 수 없으므로, 공격자가 인가 요청 URL과 인가 코드를 모두 훔쳐도 code_verifier는 알 수 없습니다. 자물쇠는 봤지만 열쇠는 정상 앱 메모리 안에 있는 셈입니다.

직접 만들어 보기

버튼을 누르면 브라우저의 Web Crypto API로 실제 값을 생성합니다. 실무 코드에서 하는 계산과 완전히 동일합니다.

아직 생성 안 됨
↓ SHA-256 해시 후 base64url 인코딩
아직 생성 안 됨
S256

인가 요청에는 이렇게 실립니다

// 1단계: 인가 요청 (프론트 채널) — 자물쇠만 보낸다
GET /authorize?response_type=code
  &client_id=mobile-app-2024
  &redirect_uri=myapp://callback
  &scope=orders:read
  &state=xyz789
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256

// 2단계: 토큰 교환 (백 채널) — 열쇠 원본을 제출한다
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=myapp://callback
&client_id=mobile-app-2024
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
이제는 모든 클라이언트의 기본값입니다

처음에는 모바일 앱을 위한 확장이었지만, OAuth 2.1 초안과 최신 보안 권고(BCP)에서는 기밀 클라이언트를 포함한 모든 인가 코드 흐름에 PKCE를 적용하라고 권고합니다. 백엔드 서버라도 인가 코드가 중간에서 주입되는 공격을 막아 주기 때문입니다. 새로 만드는 시스템이라면 고민 없이 켜 두세요.

plain 방식은 쓰지 마세요

code_challenge_method에는 S256과 plain 두 가지가 있습니다. plain은 해시 없이 원본을 그대로 보내는 방식이라 아무것도 보호하지 못합니다. SHA-256을 구현할 수 없는 극히 예외적인 환경을 위한 하위 호환 옵션일 뿐입니다.

05

클라이언트 자격 증명 흐름

Client Credentials Grant. 지금까지는 "사용자를 대신해서"가 전제였는데, 이 흐름에는 사용자가 없습니다. 프로그램이 자기 자신의 권한으로 API를 부르는 경우입니다.

클라우드 운영 업무에서 실제로 가장 자주 마주치는 흐름이기도 합니다. 예를 들어 야간 배치가 고객사 리소스 사용량을 수집한다거나, 모니터링 시스템이 알람 API를 호출한다거나, 정산 서비스가 결제 API를 부르는 상황입니다. 이때 "동의 화면"을 띄울 사람이 없습니다. 눌러 줄 사람이 없으니까요.

그래서 흐름이 극단적으로 단순해집니다. 브라우저도, 리다이렉트도, 인가 코드도 없습니다.

# 요청: 앱이 자기 신분증과 비밀번호를 내밀고 토큰을 달라고 한다
POST /oauth2/token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic bW9uaXRvcmluZy1qb2I6czNjcjN0   # client_id:client_secret 을 base64

grant_type=client_credentials&scope=metrics:read+alerts:write

# 응답
HTTP/1.1 200 OK
Content-Type: application/json

{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "metrics:read alerts:write"
}

끝입니다. 요청 한 번, 응답 한 번. 리프레시 토큰은 발급되지 않습니다. 사용자 동의가 없는 흐름이라 만료되면 그냥 같은 요청을 다시 보내면 되기 때문입니다.

운영에서 주의할 점

토큰을 매 요청마다 새로 받지 마세요

API 호출 1000번에 토큰 발급 1000번을 하는 코드를 꽤 자주 봅니다. 인가 서버에 불필요한 부하가 걸리고, 레이트 리밋에 걸려 서비스가 멈추기도 합니다. expires_in을 보고 메모리에 캐시했다가 만료 30~60초 전에 갱신하세요.

시크릿은 코드에 넣지 마세요

깃 저장소에 client_secret이 올라가는 사고는 지금도 매일 일어납니다. 시크릿 매니저나 볼트에서 런타임에 주입하고, 정기적으로 교체할 수 있도록 두 개의 시크릿을 동시에 유효하게 두는 무중단 교체 절차를 준비해 두세요.

역할마다 클라이언트를 분리하세요

배치, 모니터링, 정산이 모두 하나의 client_id를 공유하면 한 곳의 시크릿 유출이 전체 권한 유출이 됩니다. 감사 로그에서 누가 호출했는지 구분할 수도 없습니다. 워크로드 단위로 나누고 필요한 스코프만 부여하세요.

더 나은 대안이 있으면 그쪽을 쓰세요

클라우드 환경이라면 장기 시크릿 대신 워크로드에 붙은 신원을 쓰는 방식(쿠버네티스 서비스 계정 토큰 연동, OIDC 페더레이션 등)이 더 안전합니다. 보관할 비밀 자체가 사라지기 때문입니다. 3편에서 자세히 다룹니다.

06

기기 인가 흐름

Device Authorization Grant. 스마트 TV에서 넷플릭스를 로그인할 때, 혹은 터미널에서 aws sso login이나 gh auth login을 칠 때 마주치는 그 화면입니다. "브라우저에서 이 주소로 접속하고 아래 코드를 입력하세요"라고 나오는 흐름이죠.

쓰는 이유는 단순합니다. 입력이 불편하거나 브라우저가 없는 기기가 있기 때문입니다. TV 리모컨으로 비밀번호를 치는 건 고통스럽고, SSH로 접속한 서버에는 띄울 브라우저가 없습니다. 그래서 인증만 내 휴대폰이나 노트북으로 넘깁니다.

# 1. 기기가 코드 두 개를 요청한다
POST /device_authorization
client_id=cli-tool

# 응답
{
  "device_code": "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",   # 기기가 쓸 값
  "user_code": "WDJB-MJHT",                                  # 사람이 읽고 입력할 값
  "verification_uri": "https://auth.example.com/device",
  "expires_in": 900,
  "interval": 5                                             # 폴링 간격(초)
}

# 2. 기기가 화면에 안내를 띄운다
#    "https://auth.example.com/device 에 접속해 WDJB-MJHT 를 입력하세요"

# 3. 그동안 기기는 5초마다 토큰 엔드포인트를 두드린다
POST /token
grant_type=urn:ietf:params:oauth:grant-type:device_code
&device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS
&client_id=cli-tool

# 사용자가 아직 승인 전이면
{ "error": "authorization_pending" }
# 너무 자주 물어보면
{ "error": "slow_down" }          # interval을 5초 늘리고 계속
# 사용자가 승인하면
{ "access_token": "...", "token_type": "Bearer", "expires_in": 3600 }
사용자 코드는 짧고 읽기 쉬워야 합니다

user_code에 흔히 대문자와 숫자 일부만 쓰고 0/O, 1/I 같은 헷갈리는 글자를 빼는 이유가 여기 있습니다. 대신 짧은 만큼 무차별 대입에 약하므로, 인가 서버는 시도 횟수를 제한하고 유효 시간을 짧게(보통 15분) 잡아야 합니다.

기억해 둘 피싱 위험

이 흐름은 "낯선 코드를 입력하는 행위"를 사용자에게 정상적인 것으로 학습시킵니다. 공격자가 자기 기기로 코드를 발급받은 뒤 그 코드를 피해자에게 보내 입력하게 만들면, 피해자 계정 권한이 공격자 기기로 넘어갑니다. 그래서 승인 화면에 "어떤 기기가 요청했는지"를 분명히 보여주고, 사용자가 직접 시작한 요청인지 한 번 더 확인시키는 설계가 필요합니다.

07

사라진 방식들

레거시 시스템을 인수인계받거나 오래된 블로그 글을 읽다 보면 지금은 쓰지 않는 흐름이 나옵니다. 왜 폐기됐는지 알아 두면 "이 코드는 고쳐야 한다"를 근거 있게 설명할 수 있습니다.

암묵적 흐름 (Implicit Grant)

인가 코드 없이, 인가 서버가 리다이렉트할 때 액세스 토큰을 URL 프래그먼트에 바로 담아 주는 방식입니다. 예전 SPA는 백엔드가 없어서 토큰 교환을 할 수 없었기에 이 방식이 만들어졌습니다.

# 이런 URL로 돌아옵니다
https://myapp.com/callback#access_token=eyJhbGci...&token_type=Bearer&expires_in=3600

문제는 명확합니다. 액세스 토큰이 브라우저 주소창에 노출되고, 히스토리에 남고, 브라우저 확장 프로그램이 읽을 수 있습니다. 리프레시 토큰을 줄 수 없어 만료될 때마다 사용자를 다시 인가 서버로 보내야 하고, 코드 주입 공격을 막을 방법도 없습니다. 지금은 PKCE를 적용한 인가 코드 흐름이 SPA에서도 완벽히 동작하므로 쓸 이유가 없습니다.

리소스 소유자 비밀번호 흐름 (ROPC)

사용자가 앱 화면에 아이디와 비밀번호를 직접 입력하면, 앱이 그것을 토큰 엔드포인트로 보내 토큰으로 바꾸는 방식입니다.

POST /token
grant_type=password&username=alice&password=hunter2&client_id=legacy-app

보시다시피 0장에서 설명한 비밀번호 안티패턴으로 되돌아간 것입니다. 앱이 사용자 비밀번호를 그대로 보게 되므로 OAuth를 쓰는 의미가 사라집니다. 2단계 인증과 공존할 수 없고, 소셜 로그인 같은 외부 인증과도 연동되지 않습니다. 명세에서도 마이그레이션 목적의 예외로만 허용했고, 현재 권고는 명확히 "쓰지 말 것"입니다.

흐름상태왜 그런가대신 쓸 것
Authorization Code + PKCE표준사용자를 대신하는 모든 경우의 정답—
Client Credentials표준사용자가 없는 서버 간 통신—
Device Code표준입력이 불편하거나 브라우저가 없는 기기—
Refresh Token표준만료된 액세스 토큰 갱신용—
Implicit폐기토큰이 URL에 노출, 리프레시 불가Authorization Code + PKCE
Password (ROPC)폐기앱이 비밀번호를 직접 취급, 2단계 인증 불가Authorization Code + PKCE

그래서 내 상황에는 무엇을 써야 하나

세 가지만 물어보면 답이 나옵니다. 아래에서 직접 골라 보세요.

08

스코프 설계

스코프는 OAuth에서 가장 과소평가되는 부분입니다. 흐름은 정해진 대로 구현하면 되지만, 스코프는 우리 서비스의 권한 모델을 직접 설계하는 일이라 정답이 없습니다. 잘못 설계하면 나중에 되돌리기가 매우 어렵습니다. 이미 발급된 토큰과 이미 연동된 앱들이 전부 깨지기 때문입니다.

설계 원칙 네 가지

1. 읽기와 쓰기를 반드시 나눈다

가장 기본이면서 가장 효과가 큽니다. orders 하나만 두면 주문 목록을 보여주는 대시보드도 주문을 취소할 권한을 갖게 됩니다. orders:read와 orders:write로 나누면 대부분의 연동 앱은 읽기만 요청하게 되고, 사고의 파급 범위가 크게 줄어듭니다.

2. 이름은 사용자가 아니라 개발자를 위한 것이다

calendar.events.readonly처럼 리소스와 동작이 드러나는 이름을 씁니다. 사용자에게 보여줄 문장("내 일정을 볼 수 있습니다")은 동의 화면에서 따로 번역합니다. 이 둘을 섞어서 스코프 이름을 한글 문장으로 만드는 실수를 하면 나중에 다국어 지원에서 곤란해집니다.

3. 너무 잘게 쪼개지 않는다

권한을 50개로 쪼개면 동의 화면이 스크롤 두 페이지가 되고, 사용자는 읽지 않고 그냥 승인합니다. 아무도 읽지 않는 동의 화면은 보안 장치가 아니라 요식 행위입니다. 사용자가 의미를 이해할 수 있는 단위가 적절한 입자 크기입니다. 보통 리소스 종류 × (읽기/쓰기) 정도면 충분합니다.

4. 나중에 추가할 수는 있어도 빼기는 어렵다

스코프를 추가하는 건 쉽습니다. 기존 토큰은 그대로 동작하고, 새 권한이 필요한 앱만 다시 동의를 받으면 됩니다. 하지만 기존 스코프를 없애거나 의미를 좁히면 이미 연동된 앱이 전부 깨집니다. 처음에 좁게 시작해서 넓히는 방향이 언제나 안전합니다.

점진적 인가 (Incremental Authorization)

가입 시점에 모든 권한을 한꺼번에 요구하지 말고, 그 기능을 실제로 쓰려는 순간에 추가로 요청하는 방식입니다. "파일 내보내기" 버튼을 누를 때 비로소 드라이브 쓰기 권한에 동의를 받는 식이죠. 사용자 입장에서는 왜 그 권한이 필요한지 맥락이 분명해서 동의율이 올라가고, 서비스 입장에서는 불필요한 권한을 들고 있지 않아도 됩니다.

    1편 정리

    여기까지 왔다면 OAuth 2.0 문서를 읽을 기본기는 갖춘 것입니다. 핵심만 다시 짚고 가겠습니다.

    • 01OAuth는 비밀번호를 넘기지 않고, 범위와 기한이 정해진 액세스 토큰으로 권한만 위임하는 표준이다.
    • 02등장인물은 넷. 리소스 소유자(사용자), 클라이언트(앱), 인가 서버, 리소스 서버.
    • 03민감한 값은 백 채널(서버 대 서버)로만 오간다. 브라우저를 지나는 프론트 채널에는 훔쳐도 쓸모가 적은 일회용 코드만 싣는다.
    • 04시크릿을 숨길 수 없는 공개 클라이언트는 PKCE로 코드 탈취를 막는다. 이제는 모든 클라이언트의 기본값이다.
    • 05사용자가 없는 서버 간 통신은 Client Credentials, 입력이 불편한 기기는 Device Code를 쓴다.
    • 06Implicit와 ROPC는 폐기됐다. 둘 다 Authorization Code + PKCE로 대체한다.
    • 07OAuth는 인가만 다룬다. "이 사용자가 누구인가"는 아직 아무도 대답하지 않았다.

    2편에서 이어집니다

    마지막 항목이 2편의 출발점입니다. 액세스 토큰을 받았다는 사실만으로 "이 사람은 앨리스다"라고 판단하면 왜 취약점이 되는지, 그 문제를 풀기 위해 OAuth 위에 얹은 OpenID Connect가 무엇인지 다룹니다. id_token의 JWT 구조를 한 줄씩 뜯어보고, 서명 검증에 쓰는 JWKS와 .well-known/openid-configuration 문서를 실제로 열어 봅니다. 토큰을 어디에 저장해야 하는지, 로그아웃이 왜 그렇게 어려운지도 함께 살펴봅니다.
