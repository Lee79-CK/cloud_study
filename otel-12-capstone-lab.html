세 언어, 하나의 트레이스, 네 번의 장애

지금까지 배운 것을 한 시스템 위에서 전부 돌려봅니다. Node.js BFF가 Java 주문 서비스와 Python 추천 서비스를 부르는 작은 시스템입니다. 정상 상태를 먼저 확인한 뒤, 장애 네 건을 직접 조사합니다. 단서를 열어 원인을 찾고, 마지막에는 매번 같은 질문에 답합니다. "이건 누가 고칠 문제인가?"

SECTION 01

데모 시스템과 계측 구성

히어로의 각 박스를 누르면 계측 방식이 나옵니다. 요약하면, 세 서비스가 서로 다른 방식으로 계측되지만 같은 규칙을 따릅니다. 이것이 11편 경계 계약서의 효과입니다.

공통 규칙

service.name은 <도메인>-<역할>, 커스텀 속성은 acme. 접두사, 환경은 dev. 모두 11편 계약서대로입니다.

파이프라인

DaemonSet Agent가 k8s 메타데이터와 테넌트 속성을 붙이고, Gateway가 테일 샘플링 후 백엔드로 보냅니다. 7~9편 구성 그대로입니다.

개발팀이 한 일

어노테이션, 로그 포맷, 핵심 구간 수동 Span 몇 개. 나머지는 인프라가 흡수했습니다. 8편의 목표가 달성된 상태입니다.

SECTION 02

실습 환경 구성

로컬 쿠버네티스 클러스터 하나로 전체를 재현할 수 있습니다. 8편의 롤아웃 순서대로 뒤에서부터 세웁니다.

클러스터 준비

kind나 minikube 등 로컬 클러스터를 만듭니다. 노드 1~2개면 충분합니다.

kind create cluster --name otel-lab

백엔드 설치

트레이스·메트릭·로그를 받을 저장소와 조회 도구를 설치합니다. 오픈소스 스택을 Helm으로 올리거나, 학습 목적이라면 올인원 이미지를 써도 됩니다. 핵심은 OTLP를 받을 수 있는 엔드포인트가 하나 있는 것입니다.

cert-manager와 Operator

8편 설치 절차 그대로입니다. 웹훅이 정상 등록됐는지 반드시 확인합니다.

kubectl get mutatingwebhookconfiguration | grep opentelemetry

Collector와 Instrumentation

아래에서 받을 수 있는 매니페스트에 Gateway, Agent, Instrumentation CR이 들어 있습니다. Gateway에는 확인용 debug 익스포터가 함께 켜져 있습니다.

데모 서비스 배포

세 서비스의 Deployment에 주입 어노테이션이 붙어 있습니다. 이미지 이름은 자리표시자이므로 직접 빌드한 이미지로 바꾸세요.

트래픽 발생과 확인

BFF에 요청을 반복해서 보내고, 백엔드에서 세 서비스를 가로지르는 트레이스가 보이는지 확인합니다.

kubectl -n demo port-forward svc/bff-gateway 8080:80
for i in $(seq 1 200); do curl -s localhost:8080/home > /dev/null; done
실습 매니페스트 묶음

Namespace, Instrumentation CR, Agent·Gateway Collector, 데모 서비스 3개를 하나의 YAML로 묶었습니다. 학습용 뼈대이므로 이미지 이름과 백엔드 주소는 환경에 맞게 바꿔야 합니다.

SECTION 03

정상 상태 확인

장애를 조사하려면 정상이 어떤 모습인지 먼저 알아야 합니다. 아래는 GET /home 요청 하나가 만든 트레이스입니다. Span을 눌러 속성과 그 속성을 붙인 주체를 확인하세요.

trace_id 4bf92f3577b34da6a3ce929d0e0e4736 · 총 182ms · Span 9개 · 서비스 3개 Node.jsJavaPython

확인 체크 포인트

  • 한 트레이스 안에 세 서비스가 모두 있다 — 컨텍스트 전파가 서비스 경계를 넘었습니다 (2편)
  • CLIENT Span 아래에 다음 서비스의 SERVER Span이 붙어 있다 — traceparent가 헤더로 전달됐습니다
  • k8s.* 속성이 모든 Span에 있다 — Agent의 k8sattributes가 동작합니다 (8편)
  • recommend 내부가 빈 구간 없이 채워져 있다 — 수동 Span 덕분입니다 (5편)
  • 이 trace_id로 로그를 검색하면 세 서비스의 로그가 모두 나온다 — 로그 연결이 동작합니다 (5편·9편)

다섯 가지가 모두 확인되면 장애 조사를 시작할 준비가 된 것입니다. 이 트레이스를 머릿속에 기준으로 두고, 아래 장애들에서 무엇이 달라졌는지를 찾으면 됩니다.

SECTION 04

장애 조사 실습

네 건의 장애가 들어왔습니다. 각 건마다 단서를 열어보고, 원인을 고르고, 원인을 고칠 담당을 판정하세요. 단서는 몇 개를 열어도 괜찮지만, 적게 열고 맞힐수록 실전 감각이 좋다는 뜻입니다.

조사 순서의 정석

메트릭으로 어디가 이상한지 범위를 좁히고 → 트레이스로 어느 구간인지 찾고 → 로그로 왜 그런지 확인하고 → 변경 이력과 파이프라인 상태로 앱 문제인지 인프라 문제인지 가릅니다. 1편에서 말한 "신호는 연결될 때 강해진다"가 이 흐름입니다.

SECTION 05

조사 결과

네 건의 판정 결과입니다.

네 건이 가르쳐 주는 것

개발팀 쪽 장애의 공통점

원인이 배포 직후에 나타나고, 단서가 애플리케이션 텔레메트리 안에 있습니다. 수동 Span, 비즈니스 속성, 로그의 구체적 값이 결정적입니다. 자동 계측만 있었다면 찾기 어려웠을 것입니다.

플랫폼팀 쪽 장애의 공통점

앱 텔레메트리는 정상인데 결과가 이상합니다. 단서가 인프라 변경 이력과 파이프라인 자기 지표에 있습니다. 7편의 자기 관측이 없었다면 원인을 영영 몰랐을 것입니다.

판정 기준 한 줄

"데이터가 만들어질 때 이미 틀렸는가, 만들어진 뒤에 틀어졌는가." 만들어질 때 틀렸다면 개발팀, 흘러가는 도중에 틀어졌다면 플랫폼팀입니다. 1편 경계선의 가장 간결한 표현이기도 합니다.

SECTION 06

강의 전체 회고 — 경계선의 최종 모습

1편 히어로의 7단계 파이프라인을 다시 가져왔습니다. 이번에는 각 단계가 몇 편에서 다뤄졌고, 최종적으로 누가 책임지는지가 채워져 있습니다.

1편과 무엇이 달라졌나

1편에서는 가운데 세 단계(SDK, OTLP 전송, 대시보드)가 회색지대였습니다. 지금은 각 활동마다 A가 한쪽에 있습니다. SDK는 주입·버전을 플랫폼팀이, 선언을 개발팀이. 전송은 플랫폼팀이. 대시보드는 템플릿을 플랫폼팀이, 서비스 SLO를 개발팀이. 경계선은 사라지지 않았지만, 선이 어디를 지나는지는 모두가 압니다.

SECTION 07

실제 도입의 첫 30일

강의가 끝나고 월요일에 바로 시작할 수 있는 순서입니다. 11편 로드맵의 0·1단계에 해당합니다.

주차플랫폼팀개발팀산출물
1주검증 클러스터에 이 편의 실습 환경 재현1편·2편 공동 학습, 파일럿 서비스 후보 제시동작하는 실습 환경
2주운영 클러스터에 Operator·Gateway·Agent, 자기 관측 알림파일럿 서비스의 로그 JSON·trace_id 적용RACI·계약서 v0 (11편 생성기)
3주파일럿 네임스페이스에 Instrumentation CR어노테이션 적용, 오버헤드 기준선 측정엔드투엔드 트레이스 확인
4주파일럿 결과로 체크리스트 보완핵심 구간 수동 Span 2~3개, 금지 속성 테스트온보딩 체크리스트 v1, 확산 계획
이 편의 장애 조사를 팀 훈련으로

실습 환경에서 네 장애를 실제로 일으켜 보세요. 추천 서비스에 필터를 빼는 코드를 배포하고, 게이트웨이에서 헤더를 지우고, 메트릭에 사용자 ID를 넣고, 백엔드를 잠시 내립니다. 개발팀과 플랫폼팀이 함께 원인을 찾는 연습을 한 번 해두면, 운영에서 같은 일이 생겼을 때 누가 먼저 무엇을 볼지가 이미 몸에 익어 있습니다.
