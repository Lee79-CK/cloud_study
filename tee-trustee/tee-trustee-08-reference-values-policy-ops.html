참조값과 정책 운영

기밀 컴퓨팅은 한 번 구축하고 끝나는 시스템이 아닙니다. 이미지 한 줄, 커널 패치 하나, 펌웨어 업데이트 하나가 모두 측정값을 바꾸고, 측정값이 바뀌면 키가 나오지 않습니다. 이번 편은 "안전하면서도 멈추지 않는" 운영 방법을 다룹니다.

릴리스 시뮬레이터: 무엇을 바꿨고, 무엇을 함께 바꿨나변경 없음

예: "이미지 수정"만 켜 보세요. 그다음 빨간 칸을 하나씩 함께 갱신해 배포가 성공할 때까지 맞춰 보세요.

0

시작하기 전에

7편에서 Trustee를 띄우고 정책과 참조값을 직접 넣어 봤습니다. 그때 여러 번 "운영에서는 다르다"고 미뤄둔 것이 있습니다. 참조값을 어디서 얻는지, 누가 서명하는지, 정책을 어떻게 바꾸는지, 그리고 업데이트할 때 서비스가 멈추지 않게 하려면 어떻게 해야 하는지입니다. 이번 편은 그 "운영의 기술"입니다.

🎯이번 편을 마치면

  • 참조값의 종류와 출처, 얻는 방법을 설명할 수 있습니다.
  • 어떤 변경이 어떤 측정값·승인값을 바꾸는지 예측할 수 있습니다.
  • 이미지·정책·Init-Data·참조값을 하나의 릴리스로 묶을 수 있습니다.
  • 정책 변경을 리뷰하고 테스트하는 기준을 세울 수 있습니다.
  • "추가 → 배포 → 제거" 순서로 무중단 전환을 설계할 수 있습니다.
  • 키가 안 나올 때의 장애 대응 순서를 따를 수 있습니다.

🔗이어지는 개념

  • 2편 11장의 측정 사슬: 무엇이든 바뀌면 값이 바뀝니다.
  • 3편 8장의 TCB 유예 정책을 운영 절차로 구체화합니다.
  • 5편 7·8장의 에이전트 정책과 Init-Data가 릴리스의 일부가 됩니다.
  • 6편의 RVPS, 증명 정책, 리소스 정책이 운영 대상입니다.
1

왜 운영이 어려운가

기밀 컴퓨팅의 보안은 "정확히 승인한 것만 통과시킨다"는 원리에서 나옵니다. 그런데 이 원리는 운영 관점에서 보면 "승인하지 않은 변경은 모두 장애가 된다"는 뜻이기도 합니다.

비유: 지문 출입 시스템

사무실 출입문이 지문으로 열린다고 해봅시다. 아주 안전합니다. 그런데 직원이 손가락을 다쳐 지문이 조금 바뀌면 문이 안 열립니다. 새 직원이 오면 미리 등록해야 하고, 퇴사자는 지워야 합니다. 등록 담당자가 아무 지문이나 등록해 주면 보안이 무너지고, 등록을 너무 까다롭게 하면 아무도 출근을 못 합니다. 참조값 운영이 정확히 이 문제입니다.

이번 편의 한 문장

측정값을 바꾸는 모든 변경은 "참조값·승인값을 먼저 추가하고, 배포하고, 옛 값을 나중에 지운다"는 하나의 릴리스 절차로 다뤄야 합니다.

2

참조값의 종류와 출처

"참조값"이라고 뭉뚱그려 말하지만, 실제로는 출처도 등록 위치도 다른 여러 값이 있습니다.

표를 보면 참조값은 세 군데에 흩어져 있습니다. 하드웨어·부팅 관련 값은 RVPS(증명 정책이 사용), 워크로드 관련 값은 Init-Data와 리소스 정책, 이미지 관련 값은 에이전트 정책입니다. 그래서 한 가지 변경이 여러 곳의 수정을 요구하게 됩니다.

3

계산할까, 실측할까

참조값을 얻는 방법은 크게 두 가지입니다.

🧮계산 (사전 계산)

펌웨어 파일, 커널, initrd, 커맨드라인, VM 설정(vCPU 수 등)을 입력으로 넣어 "이걸로 부팅하면 측정값이 이렇게 나온다"를 미리 계산합니다. SEV-SNP는 sev-snp-measure 같은 공개 도구가 널리 쓰입니다.

  • 장점: 하드웨어 없이 빌드 단계에서 만들 수 있고, 입력 파일과 함께 재현·검증할 수 있습니다.
  • 단점: 하이퍼바이저 설정 하나만 달라도 실제 값과 어긋납니다. 계산 방식이 펌웨어·도구 버전에 따라 바뀔 수 있습니다.

📏실측 (골든 측정)

신뢰할 수 있는 환경에서 실제로 기밀 VM을 띄우고, 그 증거에서 측정값을 뽑아 참조값으로 삼습니다.

  • 장점: 실제 환경과 정확히 일치합니다. 계산 도구가 없는 구성에도 쓸 수 있습니다.
  • 단점: 측정하는 환경이 이미 오염되어 있으면 오염된 값을 승인하게 됩니다. "무엇이 들어 있어서 이 값이 나왔는가"를 설명하기 어렵습니다.
실측의 함정: 도둑의 지문을 등록하기

실측은 "지금 이 서버에서 나오는 값이 정상"이라고 가정합니다. 만약 그 서버의 게스트 이미지가 이미 변조되어 있었다면, 변조된 값을 정상으로 등록하게 됩니다. 지문 등록 날 도둑이 직원 행세를 하고 와서 자기 지문을 등록하는 셈입니다. 그래서 실측을 쓰더라도 격리된 빌드 환경에서 처음 측정하고, 가능하면 계산값과 교차 확인하는 것이 좋습니다.

현실적인 조합

공식 배포판(예: Kata·CoCo 게스트 이미지)을 쓴다면 배포판 쪽에서 계산·공개한 값이나 도구를 우선 활용하고, 우리가 직접 바꾼 부분(Init-Data, 이미지)은 우리 파이프라인에서 계산합니다. 클라우드에서 펌웨어를 제공받는다면 클라우드 사업자가 공개하는 펌웨어 측정값 정보를 확인합니다. 어느 경우든 "이 값이 어디서 왔는지"를 기록해 두는 것이 핵심입니다(6장).

4

무엇을 바꾸면 무엇이 바뀌나

운영자가 가장 자주 받는 질문은 "이거 바꾸면 증명 깨져요?"입니다. 아래 표에서 변경 행을 눌러 영향을 받는 값과 함께 해야 할 일을 확인하세요.

흔한 구성을 기준으로 단순화했습니다. 어떤 값이 어디에 측정되는지는 플랫폼(TDX·SNP), 펌웨어, Kata 버전에 따라 다를 수 있습니다.

놓치기 쉬운 두 가지
  • VM 크기 변경: SEV-SNP는 측정값에 vCPU 수와 종류가 들어갑니다. "파드 리소스만 늘렸는데 증명이 깨졌다"는 일이 생길 수 있습니다.
  • 이미지만 바꿨을 때: 펌웨어·커널 측정값은 그대로입니다. 하지만 에이전트 정책이 digest를 고정하고 있다면 정책 → Init-Data → 리소스 정책이 줄줄이 바뀌어야 합니다.
5

기밀 릴리스 번들

위의 연쇄를 사람이 매번 기억해서 맞추는 것은 불가능합니다. 그래서 측정값과 승인값에 영향을 주는 모든 것을 하나의 릴리스 단위로 묶어 파이프라인이 함께 만들고, 함께 검토하고, 함께 배포하도록 합니다. 이 강의에서는 이것을 기밀 릴리스 번들이라고 부르겠습니다.

  1. 빌드

    컨테이너 이미지를 빌드하고 digest를 확정합니다. 이미지에 서명합니다(5편 9장).

  2. 에이전트 정책 생성

    digest로 고정된 파드 YAML에서 genpolicy로 정책을 만듭니다. 이전 릴리스와의 차이(diff)를 사람이 읽을 수 있게 남깁니다.

  3. Init-Data 생성

    정책과 KBS 설정을 Init-Data로 묶고 해시를 계산합니다. 이 해시가 리소스 정책에 들어갈 승인값입니다.

  4. 참조값 준비

    게스트 펌웨어·커널이 바뀌었다면 측정값을 계산(또는 실측)하고, 출처 정보와 함께 서명합니다.

  5. 리뷰와 승인

    정책 diff, Init-Data 해시, 참조값 변경을 하나의 변경 요청(PR)으로 올리고, 고객 보안 담당자 등 정해진 승인자가 승인합니다(8장).

  6. 승인값 추가

    RVPS에 새 참조값을 등록하고, 리소스 정책에 새 Init-Data 승인값을 추가합니다. 옛 값은 아직 지우지 않습니다(9장).

  7. 배포와 확인

    새 파드를 배포하고, 증명 토큰이 affirming인지, 키를 정상적으로 받았는지 확인합니다.

  8. 옛 값 제거

    옛 버전 파드가 모두 사라진 뒤 옛 참조값과 승인값을 제거합니다. 이 단계를 빼먹으면 옛 버전(취약할 수 있는)이 영원히 통과합니다.

MSP 관점: 배포 도구에 녹이기

이미 GitOps(Argo CD, Flux 등)나 CI 파이프라인을 운영하고 있다면, 위 단계를 별도 수작업이 아니라 파이프라인 단계로 넣는 것이 좋습니다. 특히 2~3단계(정책·Init-Data 생성)와 6단계(승인값 추가)를 자동화하면 "이미지만 바꿔서 장애"가 대부분 사라집니다. 단, 6단계의 실행 권한은 승인 절차를 거친 경우에만 동작하도록 묶어야 합니다.

6

서명과 출처, 역할 분리

참조값은 "무엇을 믿을지"를 정하는 값입니다. 그래서 누가 그 값을 넣을 수 있는지가 곧 보안의 핵심입니다. 6편에서 RVPS가 서명된 메시지를 기대한다고 했던 이유가 여기 있습니다.

출처(provenance)란

출처 정보는 "이 값은 어떤 소스 코드를, 어떤 빌드 시스템이, 언제, 어떤 설정으로 만들었는가"를 기록한 증명서입니다. 소프트웨어 공급망 보안에서 쓰는 SLSA, in-toto 같은 체계가 이런 기록을 표준화합니다. 참조값에 출처가 붙어 있으면, 나중에 "이 커널 해시는 왜 승인되어 있지?"라는 질문에 답할 수 있습니다.

비유: 원산지 증명서

수입 식품의 성분표(참조값)만 보고는 믿을 수 없습니다. 어느 공장에서, 언제, 어떤 공정으로 만들었는지 적힌 원산지 증명서(출처)와, 그 증명서에 찍힌 공인 기관의 도장(서명)이 있어야 통관(등록)됩니다. 그리고 도장을 찍는 사람과 통관을 허가하는 사람은 다른 사람이어야 합니다.

역할 분리: 한 사람이 다 하지 않게

역할 (3편 RATS 대응)하는 일가진 권한
빌드 시스템 (Reference Value Provider)이미지·게스트를 빌드하고 측정값·출처를 만들어 서명서명 키 (KMS·HSM 안에 보관)
정책 승인자 (Verifier·RP Owner)정책 diff와 참조값 변경을 검토하고 승인저장소 승인 권한
Trustee 운영자승인된 변경을 Trustee에 반영, 가용성 관리KBS 관리자 인증 (파이프라인을 통해서만)
클러스터 운영자 (MSP)파드 배포, 노드·펌웨어 관리Kubernetes 권한 (Trustee 권한 없음)

7편에서 본 것처럼 rvps-tool이 KBS 관리자 권한과 분리되어 있다는 점을 활용하면, 빌드 시스템은 참조값만 등록할 수 있고 리소스 정책은 건드릴 수 없게 나눌 수 있습니다.

7

정책을 코드로

정책, 참조값, Init-Data는 모두 텍스트 파일입니다. 그러니 애플리케이션 코드처럼 Git으로 관리하고, 리뷰하고, 테스트하고, 파이프라인으로 배포해야 합니다.

저장소 구조 예시

confidential-policy/ ├── resource-policies/ │ └── llm-prod.rego # KBS 리소스 정책 ├── attestation-policies/ # (기본 정책을 바꾼 경우만) ├── reference-values/ │ └── guest-2026.10.json # 측정값 + 출처 정보 ├── initdata/ │ └── llm-prod/initdata.toml # 에이전트 정책·AA·CDH 설정 ├── tests/ │ └── llm-prod_test.rego # 허용·거부 테스트 ├── releases/ │ └── 2026-10-03.yaml # 이번 릴리스 번들의 목록과 해시 └── CODEOWNERS # 정책 변경은 고객 보안팀 승인 필수

거부 테스트를 먼저 쓴다

정책 테스트에서 가장 중요한 것은 "막혀야 하는 것이 막히는가"입니다. 허용 테스트만 있으면 정책이 실수로 느슨해져도 테스트는 모두 통과합니다.

# tests/llm-prod_test.rego (학습용 예시) package policy_test import rego.v1 import data.policy # 거부되어야 하는 경우: 판정이 warning test_deny_warning if { not policy.allow with input as {"submods": {"cpu0": {"ear.status": "warning"}}} with data.plugin as "resource" with data["resource-path"] as ["llm-prod", "model-key", "v1"] } # 거부되어야 하는 경우: 다른 팀 저장소 test_deny_other_repo if { not policy.allow with input as affirming_token with data.plugin as "resource" with data["resource-path"] as ["finance", "db-password", "v1"] } # 허용되어야 하는 경우 test_allow_prod if { policy.allow with input as affirming_token with data.plugin as "resource" with data["resource-path"] as ["llm-prod", "model-key", "v1"] }

입력 구조와 경로 표현은 학습용으로 단순화했습니다. 실제 테스트 데이터(fixture)는 배포한 Trustee 버전이 만드는 토큰 모양과 같아야 하며, 테스트에 쓴 정책 엔진 버전도 기록해 두는 것이 좋습니다.

파이프라인에서 자동으로 확인할 것

  • opa test로 정책 테스트 실행. 거부 테스트가 하나도 없으면 실패 처리.
  • Init-Data TOML에서 해시를 다시 계산해, 리소스 정책에 적힌 승인값과 맞는지 확인.
  • 에이전트 정책에 고정된 이미지 digest가 이번 릴리스의 digest와 같은지 확인.
  • 참조값 파일에 출처 정보와 서명이 있는지, 서명이 유효한지 확인.
  • "위험 패턴" 검사: default allow = true, ExecProcessRequest := true, != "contraindicated" 같은 표현이 새로 들어오면 경고.
8

정책 변경 리뷰 연습

여러분이 고객 보안팀의 승인자라고 생각하고, 아래 변경 요청을 승인할지 반려할지 판단해 보세요.

9

무중단 전환: 추가 → 배포 → 제거

새 버전(B)으로 바꿀 때 순서를 틀리면 장애가 납니다. 데이터베이스 스키마 변경에서 쓰는 "확장 후 축소(expand and contract)"와 같은 원리입니다. 시나리오를 골라 단계를 넘겨 보세요.

KBS·RVPS에 승인된 버전:

규칙 세 줄
  1. 추가가 먼저: 새 버전의 참조값과 승인값을 배포 전에 등록합니다.
  2. 확인 후 진행: 소수의 새 파드로 증명과 키 수령을 확인한 뒤 나머지를 배포합니다.
  3. 제거는 마지막, 그러나 반드시: 옛 파드가 모두 사라진 뒤 옛 값을 지웁니다. 지우지 않으면 취약한 옛 버전이 계속 통과합니다.
10

펌웨어·드라이버 업데이트 운영

서버 펌웨어나 마이크로코드 업데이트는 TCB 버전을 바꿉니다(3편 8장). 우리 이미지와 상관없이 일어나는 변경이라 따로 절차가 필요합니다.

  1. 공지 확인

    칩 제조사 보안 공지를 확인하고, 고객 환경의 서버 세대가 대상인지, 얼마나 심각한지 평가합니다.

  2. 유예 기간 선언

    패치 전 버전을 일정 기간 warning으로 허용하는 정책(또는 정책 예외)을 승인받아 적용합니다. 유예 시작·종료일을 정책 파일 주석과 변경 기록에 남깁니다.

  3. 순차 패치

    노드를 하나씩 비우고(drain) 펌웨어를 올립니다. 패치된 노드에서 새 파드가 affirming을 받는지 확인합니다.

  4. 유예 종료

    모든 노드가 패치되면 정책을 다시 엄격하게 바꿉니다. 이 단계를 잊으면 유예가 영구 허용이 됩니다.

책임이 갈리는 지점

펌웨어 업데이트는 보통 인프라 운영자(MSP나 클라우드)가 하고, 증명 정책·리소스 정책은 고객(또는 고객이 승인한 주체)이 관리합니다. 즉 MSP 혼자서는 이 절차를 끝낼 수 없습니다. 패치 일정과 유예 정책 승인을 함께 잡는 협의 절차를 계약이나 운영 합의서에 넣어 두는 것이 좋습니다. GPU 드라이버·펌웨어 업데이트도 NVIDIA RIM 반영 여부를 확인해야 한다는 점만 다를 뿐 같은 구조입니다.

11

장애 대응 런북: "새 파드가 키를 못 받아요"

기밀 환경에서 가장 흔한 장애입니다. 질문을 따라가며 원인을 좁혀 보세요.

절대 하지 말 것

급하다고 리소스 정책을 --allow-all이나 기본 정책으로 바꿔 "일단 살리는" 조치는 하지 마세요. 7편에서 본 것처럼 그 순간 가짜 환경도 키를 받습니다. 대신 직전 릴리스로 롤백하거나, 원인이 된 특정 값만 승인 절차를 거쳐 추가하세요. 비상 절차 자체를 미리 고객과 합의해 두면 새벽에 판단을 서두르지 않아도 됩니다.

오해 바로잡기

오해참조값은 한 번 넣으면 끝이다.
사실이미지, 커널, 펌웨어, 드라이버가 바뀔 때마다 갱신해야 합니다. 그리고 옛 값을 지우는 것까지가 갱신입니다.
오해실제 서버에서 측정한 값이니 가장 정확하고 안전하다.
사실정확하지만 안전하다는 보장은 없습니다. 측정 환경이 오염되어 있었다면 오염된 값을 승인하게 됩니다.
오해장애가 나면 정책을 잠깐 풀어서 살리면 된다.
사실정책을 푸는 순간 보호가 사라집니다. 롤백이나 승인된 값 추가로 해결해야 합니다.
오해허용 테스트가 다 통과하면 정책은 안전하다.
사실정책이 느슨해져도 허용 테스트는 통과합니다. 거부 테스트가 있어야 느슨해진 것을 잡을 수 있습니다.
오해MSP가 모든 운영을 맡으면 고객은 편하고 안전하다.
사실편하지만, 정책과 참조값까지 MSP가 단독으로 바꿀 수 있다면 고객 입장에서 MSP가 다시 TCB에 들어옵니다. 승인 권한 분리가 필요합니다.

확인 퀴즈

보기를 누르면 바로 정답과 해설이 나옵니다.

16

정리와 다음 편

  1. 측정값을 바꾸는 모든 변경은 장애가 될 수 있으므로, 릴리스 절차로 다뤄야 합니다.
  2. 참조값은 RVPS(펌웨어·커널), 리소스 정책(Init-Data), 에이전트 정책(이미지 digest)에 흩어져 있습니다.
  3. 참조값은 계산하거나 실측합니다. 실측은 측정 환경이 오염되지 않았다는 전제가 필요합니다.
  4. 이미지·정책·Init-Data·참조값·승인값을 기밀 릴리스 번들로 묶어 함께 만들고 함께 배포합니다.
  5. 참조값에는 출처와 서명이 붙어야 하고, 만드는 사람·승인하는 사람·반영하는 사람을 나눕니다.
  6. 정책은 코드로 관리하고, 거부 테스트를 반드시 포함합니다.
  7. 전환은 추가 → 배포 → 제거 순서로 하고, 장애 때 정책을 푸는 대신 롤백합니다.

9편 예고: 기밀 LLM 추론 파이프라인 구축

지금까지 배운 것을 모두 모읍니다. 모델 가중치를 암호화해 저장하고, 증명에 성공한 GPU 기밀 파드만 복호화 키를 받아 가중치를 GPU에 올리는 전체 흐름을 vLLM과 KServe 기준으로 설계합니다. 암호화 방식 선택(이미지 암호화 vs 가중치 파일 암호화), 키 수령과 복호화 위치, 시작 시간과 성능, 그리고 이번 편의 릴리스 번들이 추론 서비스 배포에 어떻게 녹아드는지 다룹니다.

TEE·Trustee 강의 시리즈 8편. 영향 분석표, 정책·테스트 예시, 역할 분담은 흔한 구성을 기준으로 단순화한 학습용 예시입니다. 실제 측정 범위와 정책 입력 구조는 플랫폼과 Trustee·Kata 버전에 따라 다르므로 운영 설계 시 해당 버전의 문서를 확인하세요.
