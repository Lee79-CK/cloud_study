이번 편의 지도

이번 편이 끝나면 여러분의 PC에 "통합 포털의 축소판"이 돌아갑니다. 앞으로 편마다 새 기능을 이 저장소에 덧붙이게 되므로, 구조를 왜 이렇게 잡는지 이해하고 넘어가는 것이 코드를 따라 치는 것보다 중요합니다.

apps/server
Express 5 + Eta 템플릿. 전체 페이지와 HTML 조각을 응답하고, htmx 배포본·CSS·아일랜드 번들을 정적 파일로 제공. 이 시리즈의 주 서버
apps/server-py
FastAPI + Jinja2. 같은 URL, 같은 HTML, 같은 동작을 내는 대안 서버. Python 팀이라면 이쪽을 주 서버로 써도 됨
apps/react-islands
Vite 8 + React 19. 빌드 결과를 서버의 public/islands/react로 바로 내보냄
apps/vue-islands
Vite 8 + Vue 3.5. 빌드 결과를 서버의 public/islands/vue로 바로 내보냄

1편 커리큘럼에서 "shell / react-app / vue-app / fragment-server" 네 덩어리로 예고했던 구조를 실제 폴더 이름으로 옮긴 것입니다. 셸 페이지와 조각 서버는 한 서버(apps/server)가 함께 맡습니다. 둘을 처음부터 쪼개면 인증·세션·템플릿을 두 번 만들어야 해서 초반 학습 부담만 커지기 때문입니다. 여러 팀의 서버를 게이트웨이 뒤에 나눠 두는 구조(패턴 C)는 15편에서 이 저장소를 확장해 만듭니다.

준비물과 버전 검증

"최신 버전을 쓰세요"는 아무것도 말해 주지 않습니다. 아래 표의 버전은 2026-11-06에 npm·PyPI 레지스트리에서 직접 조회했고, 이 조합으로 저장소를 새로 설치·빌드·실행해 브라우저 테스트까지 통과한 것입니다.

런타임: Node.js와 Python

Node.js는 2026년 10월 28일에 26 버전이 Active LTS로 승격되었고, 24 버전은 그보다 앞선 10월 20일 유지보수(Maintenance) 단계로 넘어갔습니다. 새 프로젝트라면 지원 기간이 2029년 4월까지로 가장 긴 Node.js 26 LTS를 권장합니다. 사내 표준이 24라면 그대로 써도 이 랩은 문제없이 동작합니다.

최소 요구 버전은 22.12입니다. 이 숫자는 임의로 정한 것이 아니라 의존성의 engines 필드에서 나옵니다. Vite 8.3.6과 두 Vite 플러그인은 ^20.19.0 || >=22.12.0을, 개발 스크립트에 쓰는 concurrently 10은 >=22를 요구합니다. Node 20은 2026년 4월 30일에 지원이 끝났으니 20.19를 쓸 이유도 없습니다. 이 랩은 Node 22.23.4 환경에서도 실제로 설치·빌드·실행을 검증했습니다.

Node.js 출시 일정이 바뀝니다

Node.js 26은 "짝수 버전만 LTS"라는 기존 규칙의 마지막 버전입니다. 27부터는 1년에 한 번(4월) 메이저 버전을 내고 10월에 LTS로 승격하며, 모든 버전이 LTS가 됩니다. CI와 컨테이너 기본 이미지의 버전 정책을 세울 때 참고하세요.

Python은 FastAPI 0.162.0과 uvicorn 0.54.0이 >=3.10을 요구하므로 3.10 이상이면 되고, 3.12 이상을 권장합니다. 이 랩은 Python 3.12.3으로 검증했습니다.

저장소 구조 설계

폴더 구조는 곧 소유권 지도입니다. 1편의 철칙 "DOM의 한 영역에는 주인이 하나"를 파일 시스템에도 그대로 적용합니다.

htmx-portal-lab/ 최종 구조
htmx-portal-lab/
├─ package.json            # npm workspaces 루트 + 통합 스크립트
├─ package-lock.json       # 정확한 의존성 트리 고정 (커밋 대상)
├─ .gitignore
├─ README.md
└─ apps/
   ├─ server/              # Express 5 + Eta (주 서버)
   │  ├─ package.json
   │  ├─ scripts/copy-vendor.js   # htmx 배포본을 public/vendor로 복사
   │  ├─ src/app.js        # 라우트·미들웨어
   │  ├─ src/data.js       # 인메모리 저장소 + 상태 전이 규칙
   │  ├─ views/            # layout / pages / partials
   │  └─ public/           # 정적 파일
   │     ├─ css/app.css
   │     ├─ vendor/htmx/   # (생성됨) htmx.min.js, ext/
   │     └─ islands/       # (생성됨) Vite 빌드 결과
   ├─ server-py/           # FastAPI + Jinja2 (대안 서버)
   ├─ react-islands/       # Vite + React
   └─ vue-islands/         # Vite + Vue

설계 결정 네 가지

결정이유대안과 트레이드오프
npm workspaces 모노레포한 번의 npm install로 세 Node 패키지를 설치하고, 공통 의존성(vite)은 루트 node_modules에 한 벌만 둠pnpm·Turborepo가 더 빠르지만 추가 도구 학습이 필요. 이 시리즈는 기본 npm만으로 충분
아일랜드는 서버의 public으로 직접 빌드서버가 빌드 결과를 정적 파일로 제공하면 되므로 개발 중에도 프록시 설정이 필요 없음Vite 개발 서버의 HMR(즉시 반영)을 못 씀. 대신 빌드 감시(--watch)로 저장 후 새로고침
htmx를 npm으로 받아 서버가 제공버전이 package-lock.json에 고정되고, 외부 CDN 장애·차단과 무관하게 동작CDN이 더 간편하지만 버전 고정과 SRI를 직접 챙겨야 함 (4절)
빌드 결과물은 커밋하지 않음public/vendor, public/islands는 설치·빌드로 언제든 재생성배포 파이프라인에서 반드시 빌드 단계를 거쳐야 함 (20편)

  04
  
htmx를 들여오는 세 가지 방법

  
htmx는 스크립트 파일 하나라서 들여오는 방법이 여럿입니다. 통합 포털에서는 선택이 운영 안정성에 직결되므로 세 방법을 비교하고 하나를 고릅니다.


  

    
방법장점단점이 랩의 판단

    
      
① npm 설치 + 서버가 정적 제공lock 파일로 버전 고정, 외부 의존 없음, 사내망·폐쇄망에서도 동작설치 후 파일을 정적 경로로 옮기는 한 단계가 필요채택

      
② CDN + 정확한 버전 + SRI설치 없이 바로 사용, 브라우저 캐시 공유 가능성CDN 장애·차단에 영향받음, 버전·해시 관리를 사람이 해야 함5분 실습·프로토타입용

      
③ 번들러에서 import아일랜드 번들과 함께 묶을 수 있음 (dist/htmx.esm.js 제공)셸의 기반 라이브러리가 특정 앱 번들에 묶임. React 번들이 늦게 로드되면 셸 전체가 늦어짐셸에는 쓰지 않음

    
  


  
③을 피하는 이유를 조금 더 설명하면, 통합 포털에서 htmx는 모든 페이지의 기반이고 React·Vue 번들은 일부 페이지의 손님입니다. 기반을 손님의 짐 속에 넣으면, 손님이 없는 페이지에서도 그 짐을 받아야 하거나 기반이 두 벌 실리는 문제가 생깁니다.


  
① 채택한 방법: copy-vendor 스크립트

  
apps/server/scripts/copy-vendor.js



  
서버 패키지의 postinstall 스크립트로 등록해 두었으므로 npm install이 끝나면 자동으로 실행됩니다. htmx 4.0.1 패키지는 exports 필드가 없어 require.resolve('htmx.org/package.json')으로 설치 위치를 안전하게 찾을 수 있습니다. 확장 파일이 들어 있는 dist/ext 폴더도 함께 복사해 두면 3편 이후 확장을 쓸 때 경로만 추가하면 됩니다.


  
② CDN을 쓴다면: 버전 고정 + SRI

  
CDN 파일이 중간에 바뀌거나 변조되면 브라우저가 실행을 거부하도록 SRI 해시를 붙입니다. 아래 해시는 npm 배포본 htmx.org@4.0.1/dist/htmx.min.js로 직접 계산한 값입니다.

  
CDN 사용 시 (htmx 4.0.1 고정)


<script src="https://unpkg.com/htmx.org@4.0.1/dist/htmx.min.js"
        integrity="sha384-Qp9rdC8H7EqOoX+nR0P3RPG2Noji+qdwJlGpfzwQJsfOpp3sGwIdSP9xO3+UlEhn"
        crossorigin="anonymous"></script>

  
해시를 직접 검증하는 명령


# CDN이 주는 파일의 해시를 계산해 위 값과 같은지 확인
curl -s https://unpkg.com/htmx.org@4.0.1/dist/htmx.min.js \
  | openssl dgst -sha384 -binary | openssl base64 -A


  

    
htmx 2.x와 4.x를 한 페이지에 함께 올리지 말 것

    
두 버전 모두 전역 window.htmx를 만들고 문서 전체의 hx-* 속성을 처리합니다. 둘을 한 페이지에 올리면 나중에 로드된 쪽이 전역 객체를 덮고, 같은 요소에 이벤트 처리기가 이중으로 걸려 요청이 두 번 나갈 수 있습니다. 기존 레거시 페이지가 2.x를 쓰고 있다면 페이지 단위로 버전을 나누고, 이전은 1편에서 소개한 upgrade-check 도구로 진행하세요. 레이아웃 템플릿에서 htmx를 한 곳에서만 불러오도록 해 두는 것이 가장 확실한 예방책입니다.

Express 5 서버 만들기

  
서버 코드는 두 파일입니다. data.js는 저장소와 상태 전이 규칙, app.js는 HTTP 처리. 이 분리는 나중에 인메모리 저장소를 실제 클라우드 API 호출로 바꿀 때 app.js를 건드리지 않기 위한 것입니다.

삭제 응답이 204가 아니라 200인 이유

  
REST 관례로는 본문 없는 삭제 성공에 204 No Content를 씁니다. 하지만 htmx 4의 noSwap 기본값은 [204, 304]라서 204 응답은 스왑 자체를 하지 않습니다. 그러면 hx-swap="outerHTML"로 지우려던 행이 화면에 그대로 남습니다. 빈 본문을 200으로 돌려주면 "빈 내용으로 행을 교체", 즉 행이 사라집니다. 반대로 "아무것도 바꾸지 마"라는 뜻을 전하고 싶을 때는 204가 정확한 도구입니다.


  

    
Express 5에서 달라진 점 (4.x 경험자용)

    
이 랩 코드와 관련된 변화만 추리면 세 가지입니다. 첫째, async 핸들러의 예외가 자동으로 오류 처리기로 갑니다(4.x에서는 직접 next(err)를 불러야 했음). 둘째, 라우터가 path-to-regexp 8을 쓰므로 와일드카드는 /*splat처럼 이름을 붙여야 하고 정규식 문법 일부가 제한됩니다. 셋째, Node 18 이상이 필요합니다. 이 랩의 Express 5.3.0은 router 2.2.0과 path-to-regexp 8.x를 사용합니다.

여기서 판단 기준을 HX-Request가 아니라 HX-Request-Type으로 잡은 이유가 드러납니다. hx-boost로 이동하는 요청도 htmx가 보내므로 HX-Request: true가 붙지만, 대상이 body 전체라서 htmx 4는 HX-Request-Type: full을 보냅니다. HX-Request만 보고 조각을 돌려주면 boost 이동 시 화면 전체가 행 몇 줄로 바뀌는 사고가 납니다. htmx 4.0.1 소스는 대상이 document.body이거나 hx-select로 일부를 골라 쓰는 요청이면 full, 나머지는 partial로 정합니다.


  
Vary 헤더: 캐시에게 알려 주기

  
같은 URL이 요청 헤더에 따라 다른 내용을 응답하면, 중간의 캐시(브라우저 캐시, CDN, 리버스 프록시)는 그 사실을 모르면 엉뚱한 응답을 재사용할 수 있습니다. 조각을 캐시해 두었다가 주소창 요청에 그 조각을 내주면 사용자는 레이아웃 없는 맨 HTML 몇 줄을 보게 됩니다. Vary: HX-Request, HX-Request-Type은 "이 응답은 이 두 헤더 값에 따라 달라지니 따로 캐시하라"는 표시입니다.

  
실제 응답 헤더 확인


curl -sI http://localhost:3000/vms | grep -i vary
# Vary: HX-Request, HX-Request-Type

# 조각 요청을 흉내 내기
curl -s "http://localhost:3000/vms?q=db" -H "HX-Request: true" -H "HX-Request-Type: partial"

  

    
브라우저 뒤로 가기와도 관련 있습니다

    
htmx 4는 뒤로 가기 때 페이지를 다시 요청해 복원합니다(HX-History-Restore-Request: true 헤더가 붙음). 그래서 "주소창 요청에는 반드시 전체 페이지를 준다"는 규칙을 지켜 두면 히스토리 복원도 자연스럽게 동작합니다. 캐싱 전략 전체는 18편에서 다룹니다.

왜 Vite 개발 서버(HMR)를 쓰지 않나

    
Vite 개발 서버를 쓰면 저장 즉시 화면이 바뀌는 HMR을 누릴 수 있지만, 그러려면 Express가 Vite 개발 서버의 모듈 경로를 프록시하거나 개발·운영의 스크립트 태그를 다르게 렌더링해야 합니다. 통합 포털의 주인공은 서버 템플릿이므로, 이 시리즈는 "서버가 만든 페이지를 브라우저로 본다"는 운영과 같은 경로를 개발에서도 유지합니다. 아일랜드 개발이 본격화되는 12편에서 Vite 백엔드 통합(manifest 기반)을 선택지로 다시 다룹니다.

HTMX 디버깅은 "어떤 요청이 나갔고, 무엇이 돌아왔고, 어디에 들어갔나" 세 질문으로 끝납니다. 세 질문에 답하는 도구를 하나씩 손에 익힙니다.


  
질문 1·2: 무엇이 오갔나 — 네트워크 탭

  
    
    
  1. F12로 개발자 도구를 열고 Network(네트워크) 탭을 선택합니다.
    2. 
    
  2. 필터에서 Fetch/XHR을 고릅니다. htmx 4는 내부적으로 fetch()를 쓰므로 htmx 요청은 모두 여기에 모입니다.
    3. 
    
  3. 요청 하나를 눌러 Headers에서 요청 헤더(HX-Request, HX-Request-Type, HX-Source, HX-Target)를, 응답 헤더에서 Vary·HX-Trigger를 확인합니다.
    4. 
    
  4. Response 탭에서 서버가 보낸 HTML 조각 원문을 봅니다. 화면에 이상하게 들어갔다면 대부분 여기서 원인이 보입니다.
    5. 
    
  5. Initiator 탭은 어떤 스크립트가 요청을 일으켰는지 보여 줍니다. htmx 요청이면 htmx.min.js가 찍힙니다.
    6. 
  


  
질문 3: 어디에 들어갔나 — htmx 이벤트 로그

  
레이아웃의 설정을 {"logAll": true}로 바꾸면 htmx가 내부 이벤트를 모두 콘솔에 출력합니다. htmx 4.0.1 소스에서 확인한 형식은 htmx: 이벤트이름과 함께 대상 요소·상세 객체를 남기는 방식입니다. 오류가 담긴 이벤트는 logAll과 상관없이 항상 console.error로 출력됩니다.

  
views/layout.eta 한 줄 수정 (관찰할 때만)


<meta name="htmx-config" content='{"logAll": true}'>

  
또는 브라우저 콘솔에서 즉석으로


htmx.version            // '4.0.1'
htmx.config.logAll = true
htmx.config.noSwap      // [204, 304]  ← 1편에서 배운 기본값을 직접 확인
// 특정 이벤트만 보고 싶다면
document.addEventListener('htmx:after:swap', e => console.log('스왑:', e.target))


  
서버 쪽 관찰: 로그 한 줄의 해부

  
서버 로그


POST   /vms/api-01/restart → 200 (3.5ms) [htmx:partial] source=button target=tr
GET    /vms/api-01/row → 200 (2.1ms) [htmx:partial] source=tr target=tr

  
두 줄이 1편 5절의 비교 플레이어를 실제로 재현합니다. 첫 줄은 버튼(source=button)이 행(target=tr)을 대상으로 재시작을 요청한 것이고, 둘째 줄은 서버가 돌려준 "재시작 중" 행이 1.5초 뒤 스스로(source=tr) 상태를 재확인한 것입니다. id가 없는 요소는 태그 이름만 찍힙니다. 디버깅 편의를 위해 중요한 요소에 id를 주는 습관이 여기서 보상받습니다.

증상원인해결

    
      
상단에 "htmx 로드 실패"postinstall이 실행되지 않아 public/vendor/htmx가 없음 (--ignore-scripts 설치 등)node apps/server/scripts/copy-vendor.js를 직접 실행

npm install에서 EBADENGINE 경고Node가 22.12 미만Node 26 LTS(또는 24)로 업그레이드

      
/lab의 React·Vue 상자가 비어 있음아일랜드를 빌드하지 않음npm run build:islands 후 새로고침. 네트워크 탭에서 /islands/...js가 404인지 확인

      
검색해도 아무 변화 없음입력창의 name="q" 누락 또는 hx-target 선택자 오타네트워크 탭에서 요청 URL에 q=가 붙는지, 응답이 200인지 확인

      
삭제했는데 행이 남음서버가 204를 돌려줌 (htmx 4 기본 noSwap)빈 본문의 200으로 응답

      
삭제 카운터가 안 오름HX-Trigger에 target을 빼서 이미 떨어져 나간 버튼에서 이벤트가 발생{"vmRemoved": {..., "target": "#vm-app"}}처럼 받을 요소 지정

      
이벤트 리스너가 반응하지 않음htmx 2 이벤트 이름(htmx:afterSwap) 사용htmx 4 이름(htmx:after:swap)으로 변경

FastAPI에서 htmx·CSS가 404루트에서 npm install·빌드를 하지 않아 공유 public이 비어 있음루트에서 npm install && npm run build:islands

정리와 다음 편

  
    
    
  1. 이 랩은 Node.js 22.12 이상(26 LTS 권장)에서 동작하며, 최소 버전은 Vite 8과 concurrently 10의 engines 요구에서 나왔다.
    2. 
    
  2. htmx는 npm으로 정확한 버전(4.0.1)을 설치해 서버가 직접 제공한다. CDN을 쓴다면 버전 고정과 SRI가 필수이고, 2.x와 4.x를 한 페이지에 함께 올리지 않는다.
    3. 
    
  3. 템플릿은 레이아웃·페이지·조각 세 층으로 나누고, 페이지가 조각을 include해 같은 HTML을 두 번 쓰지 않는다. 출력은 기본적으로 이스케이프한다.
    4. 
    
  4. 같은 URL이 전체 페이지와 조각을 함께 낼 때는 HX-Request-Type: partial로 판단하고 Vary 헤더를 붙인다.
    5. 
    
  5. React·Vue 아일랜드는 Vite 8(rolldownOptions)로 서버의 public에 빌드하고, 필요한 페이지에서만 불러온다. 스왑과 함께 쓰는 생명주기는 12편 과제로 남겨 둔다.
    6.
