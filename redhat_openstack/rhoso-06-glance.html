6편Glance: 이미지 서비스

모든 VM은 이미지에서 태어납니다. 어떤 포맷으로 올리느냐에 따라 부팅이 3초가 되기도 3분이 되기도 하고, 이미지에 붙인 속성 한 줄이 VM이 놓일 서버를 바꾸기도 합니다. 이번 편은 VM의 “원판”을 관리하는 Glance를 다룹니다.

약 100분예상 학습 시간
1~5편 이수세 개의 문, 토큰·역할
시뮬레이터 포함속성 → 배치 결과
다음 편7편 Cinder 1: 구조

섹션 1

이 편의 목표

  1. Glance가 하는 일과 하지 않는 일을 구분하고, 이미지·스냅샷·볼륨의 차이를 설명한다.
  2. qcow2 · raw · ISO 등 디스크 포맷의 차이와 저장소에 맞는 포맷 선택(특히 Ceph에서 raw가 유리한 이유)을 설명한다.
  3. qemu-img로 이미지를 점검·변환하고, 가상 크기와 실제 크기를 읽는다.
  4. 이미지의 상태, 공개 범위, 프로젝트 간 공유 절차를 설명한다.
  5. 가져오기(import) 방식(glance-direct, web-download, copy-image)과 변환 플러그인을 설명한다.
  6. hw_* 등 이미지 속성이 VM 장치 구성과 Nova 스케줄링에 미치는 영향을 예측한다.
  7. RHOSO Glance의 split·single 구조, 다중 저장소, 그리고 이미지 서명·검증을 설명한다.

이 편의 비유: 붕어빵 틀 보관소

이미지는 붕어빵 틀, VM은 그 틀로 찍어 낸 붕어빵입니다. Glance는 틀을 보관하고 이름표(속성)를 붙여 빌려주는 틀 보관소입니다. 붕어빵을 직접 굽지는 않습니다(그건 Nova). 같은 틀에서 붕어빵 백 개를 빨리 찍으려면 틀이 굽는 기계 가까이, 바로 쓸 수 있는 모양으로 있어야 합니다. 이것이 포맷과 저장소 선택이 중요한 이유입니다.

섹션 2

Glance가 하는 일

하는 일하지 않는 일
이미지의 목록·속성(메타데이터) 관리 (DB에 기록)VM 실행 (Nova)
이미지 데이터를 저장소(store)에 넣고 꺼내 주기 (Ceph·Swift·Cinder·파일 등)실행 중인 VM의 디스크 관리 (Nova·Cinder)
업로드·가져오기, 포맷 변환 같은 가져오기 작업(task)이미지 안의 OS 설정 변경 (사용자가 빌드 도구로)
공개 범위·공유·보호 같은 접근 관리저장소 자체의 용량·복제 관리 (Ceph 등)

1편의 요청 흐름 6단계에서 nova-compute가 “이미지를 받는다”고 했던 그 부분이 Glance입니다. 컴퓨트 노드는 카탈로그의 internal 엔드포인트(3편 ②번 문)로 Glance에 접근하고, 저장소가 Ceph라면 아예 Glance를 거치지 않고 Ceph에서 직접 복제하기도 합니다(섹션 9).

섹션 3

디스크 포맷과 컨테이너 포맷

이미지에는 포맷 정보가 두 개 붙습니다. 디스크 포맷(disk_format)은 디스크 데이터가 어떤 모양으로 저장됐는지, 컨테이너 포맷(container_format)은 그 디스크를 다른 정보와 함께 감쌌는지입니다. 컨테이너 포맷은 대부분 bare(감싸지 않음)를 씁니다.

디스크 포맷뜻장점주의
qcow2QEMU의 기본 포맷. 실제로 쓴 부분만 파일 크기를 차지(씬 프로비저닝), 압축·백킹 파일 지원파일이 작아 전송·보관이 쉬움. 배포판 클라우드 이미지 대부분이 qcow2Ceph RBD 저장소에서는 복제(CoW)가 안 되어 매 부팅마다 변환·전체 복사가 일어남
raw디스크 내용 그대로. 포맷 정보 없음가장 단순하고 빠름. Ceph RBD에서 즉시 복제(CoW) 가능파일이 가상 크기만큼 큼(희소 파일이 아니면). 업로드 시간·용량 증가
isoCD/DVD 이미지OS 설치, 복구 부팅 매체설치형 부팅용. 일반 VM 원판으로는 비효율
vmdkVMware 디스크VMware에서 가져올 때 원본KVM용으로는 raw·qcow2로 변환 권장
vhd · vhdxHyper-V 디스크Hyper-V에서 가져올 때 원본변환 권장
vdi · ploop · aki/ari/amiVirtualBox·Virtuozzo·예전 AWS 형식—거의 쓰지 않음

포맷 이름은 “선언”일 뿐

--disk-format raw라고 적고 qcow2 파일을 올리면 Glance 기록과 실제 내용이 어긋납니다. 예전에는 부팅 실패나 손상으로 이어졌고, 보안 문제의 원인이 되기도 했습니다. 2024년 qcow2 관련 취약점(CVE-2024-32498) 이후 Glance·Nova·Cinder에 실제 디스크 형식을 검사하는 장치가 강화되었습니다. 올리기 전에 qemu-img info로 실제 형식을 확인하는 습관이 가장 확실합니다.

포맷 선택 도우미

1. Glance 저장소(백엔드)는?

2. Nova 인스턴스 디스크는 어디에?

3. 용도는?

세 질문에 답하면 추천 포맷이 표시됩니다.

섹션 4

변환과 점검: qemu-img

qemu-img는 디스크 이미지를 점검하고 변환하는 표준 도구입니다. 이미지를 올리기 전에는 반드시 한 번 돌려 보세요.

# ① 실제 형식과 크기 확인
$ qemu-img info rhel-9.6-x86_64-kvm.qcow2
image: rhel-9.6-x86_64-kvm.qcow2
file format: qcow2                 ← 실제 형식 (선언과 일치해야 함)
virtual size: 10 GiB (10737418240 bytes)   ← VM이 보게 될 디스크 크기 = 필요한 최소 루트 디스크
disk size: 912 MiB              ← 파일이 실제로 차지하는 크기
Format specific information:
    compat: 1.1
    (backing file 항목이 보이면 다른 파일에 의존하는 이미지 → 그대로 올리면 안 됨)

# ② qcow2 → raw 변환 (Ceph RBD 저장소용)
$ qemu-img convert -p -f qcow2 -O raw rhel-9.6-x86_64-kvm.qcow2 rhel-9.6.raw

# ③ 이상 여부 점검 (qcow2)
$ qemu-img check rhel-9.6-x86_64-kvm.qcow2

# ④ 해시 확인 (배포처가 공개한 값과 비교)
$ sha256sum rhel-9.6-x86_64-kvm.qcow2
크기 용어뜻어디에 쓰이나
virtual size (가상 크기)VM 안에서 보이는 디스크 크기Glance의 virtual_size. 플레이버 루트 디스크·이미지 min_disk가 이보다 작으면 부팅 실패
disk size / size (실제 크기)파일이 실제 차지하는 크기Glance의 size. 저장소 용량·쿼터·업로드 시간

이미지 손질 도구 (libguestfs)

이미지 안의 내용을 VM을 띄우지 않고 고칠 때는 libguestfs 도구를 씁니다. virt-customize(패키지 설치, 비밀번호·SSH 키 설정, 파일 주입), virt-sparsify(빈 공간 정리로 크기 줄이기), virt-sysprep(호스트별 고유 정보 제거)가 대표적입니다. 골든 이미지 파이프라인(섹션 13)의 기본 재료입니다.

섹션 6

업로드와 가져오기(import)

이미지를 Glance에 넣는 방식은 두 가지입니다. 예전부터 쓰던 직접 업로드(클라이언트가 데이터를 바로 저장소로 흘려보냄)와, 새로 표준이 된 가져오기(Interoperable Image Import)입니다. 가져오기는 데이터를 먼저 받아 둔 뒤 작업(task)으로 처리하기 때문에 변환·검사 같은 단계를 끼워 넣을 수 있습니다.

가져오기 방식데이터는 어디서쓰임새
glance-direct클라이언트가 Glance 스테이징 영역에 올린 뒤 가져오기 실행작업 PC에 있는 파일
web-downloadGlance가 URL에서 직접 내려받음배포처 공식 이미지를 PC를 거치지 않고 바로
copy-image이미 있는 이미지를 다른 저장소로 복사다중 저장소(엣지 사이트 등)에 퍼뜨리기
클라이언트
openstack · glance CLI
Glance API
이미지 기록스테이징 영역
가져오기 작업
플러그인 (변환 등)
저장소
Ceph · Swift · Cinder …
# 직접 업로드 (가장 흔한 방식)
openstack image create --disk-format raw --container-format bare \
   --file rhel-9.6.raw --property os_distro=rhel rhel-9.6

# web-download 가져오기 (glance 클라이언트 예)
glance image-create-via-import --name fedora-cloud \
   --disk-format qcow2 --container-format bare \
   --import-method web-download --uri https://example.org/Fedora-Cloud.qcow2

# 다중 저장소에서 다른 저장소로 복사
glance image-import <이미지 ID> --import-method copy-image --stores edge-site-1
glance import-info              # 이 클라우드에서 켜진 가져오기 방식 확인

가져오기 플러그인

플러그인하는 일
image_conversion가져오는 이미지를 지정한 포맷(보통 raw)으로 자동 변환. Ceph 환경에서 사용자가 qcow2를 올려도 raw로 저장되게 할 때
inject_metadata가져오는 모든 이미지에 정해진 속성을 자동으로 붙임 (예: 출처 표시)
image_decompression압축된 이미지를 풀어서 저장

web-download의 보안

web-download는 Glance가 사용자가 준 URL로 접속하는 기능입니다. 막지 않으면 내부망 주소를 넣어 내부 시스템을 찌르는 공격(SSRF)에 쓰일 수 있습니다. Glance의 [import_filtering_opts]로 허용 스킴(http·https), 허용 포트, 금지 호스트를 제한하고, Glance Pod가 외부 URL에 나가려면 프록시 설정이 필요한지도 확인하세요.

섹션 7

속성과 메타데이터

이미지에는 key=value 형태의 속성(property)을 자유롭게 붙일 수 있습니다. 그중 일부는 Nova가 읽어 VM의 가상 하드웨어를 정하거나, 어디에 배치할지에 영향을 줍니다. 속성을 누르면 설명이 나옵니다.

속성을 눌러 보세요.

openstack image set --property hw_qemu_guest_agent=yes --property hw_firmware_type=uefi golden-rhel9
openstack image set --min-disk 20 --min-ram 2048 golden-rhel9     # 최소 요구: 작은 플레이버 거부
openstack image unset --property hw_scsi_model golden-rhel9
openstack image show golden-rhel9 -c properties -f yaml

이미지 속성 vs 플레이버 추가 속성(extra specs)

CPU 고정, 휴즈페이지 같은 일부 설정은 이미지 속성(hw_cpu_policy)과 플레이버 추가 속성(hw:cpu_policy) 양쪽에서 요청할 수 있습니다. 이름 표기가 다르다는 점(밑줄 vs 콜론)에 주의하세요. 둘이 서로 모순되게 요청하면 생성이 실패합니다. 원칙적으로 자원 크기·성능 등급은 플레이버, 그 OS가 필요로 하는 장치 특성은 이미지에 두는 것이 관리하기 쉽습니다(9·10편).

섹션 8

이미지 속성과 스케줄링: 속성 한 줄이 서버를 바꾼다

Nova 스케줄러는 VM을 놓을 곳을 정할 때 이미지 속성도 읽습니다. 아래 시뮬레이터에서 이미지 속성을 바꾸고 네 대의 컴퓨트 노드 중 어디가 통과하는지 보세요. 실제 필터 이름과 동작은 9·10편(Nova)에서 깊게 다룹니다.

이미지 속성 → 배치 후보 시뮬레이터

“No valid host”의 숨은 원인

사용자는 플레이버만 보고 “자원이 남는데 왜 안 뜨지?”라고 묻습니다. 그런데 이미지에 architecture=aarch64나 trait:…=required 같은 속성이 붙어 있으면 후보가 크게 줄어듭니다. “No valid host” 문의를 받으면 플레이버뿐 아니라 이미지 속성도 확인하세요: openstack image show <이미지> -c properties.

섹션 9

저장소(백엔드)와 다중 저장소

Glance는 이미지 데이터를 직접 품지 않고 저장소(store)에 맡깁니다. RHOSO 문서 기준으로 다중 저장소 설정에 쓸 수 있는 종류는 file, http, rbd, swift, cinder, s3입니다.

저장소데이터 위치장점주의
rbd (Ceph RBD)Ceph 풀 (예: images)Nova·Cinder도 Ceph를 쓰면 복사 없이 즉시 복제(CoW)로 부팅·볼륨 생성이 빠름이 이점은 raw 이미지일 때만. Ceph 접속 설정(8편)
cinder이미지마다 Cinder 볼륨이미 있는 블록 스토리지(상용 어레이 등)를 그대로 활용Cinder 백엔드 성능·기능에 종속
swift / s3오브젝트 스토리지대용량·저렴한 보관부팅 시 컴퓨트로 다운로드 필요
file (NFS 공유 등)Pod에 마운트된 디렉터리단순RHOSO에서는 single 레이아웃이어야 함(섹션 10). 공유 스토리지 가용성에 종속
http외부 웹 서버읽기 전용 참조쓰기 불가

왜 Ceph에서는 raw인가: 복사 없는 복제(CoW)

raw + Ceph

Nova가 VM 디스크를 만들 때 Ceph 안에서 이미지의 스냅샷을 가리키는 복제본을 만듭니다. 실제 데이터 복사가 없으므로 10GB든 100GB든 몇 초 만에 디스크가 생기고, 공간도 바뀐 부분만 씁니다.

qcow2 + Ceph

Ceph는 qcow2 내부 구조를 이해하지 못하므로, 컴퓨트 노드가 이미지를 내려받아 raw로 변환한 뒤 Ceph에 다시 통째로 씁니다. 부팅마다 시간·네트워크·공간이 크게 듭니다. 그래서 Ceph 환경에서는 이미지를 raw로 올리거나 가져오기 변환 플러그인을 켭니다.

다중 저장소 (multistore)

한 Glance가 여러 저장소를 동시에 쓸 수 있습니다. enabled_backends에 이름:종류 쌍을 나열하고 [glance_store] default_backend로 기본을 정합니다. 이미지가 어느 저장소에 있는지는 이미지 속성 stores에 나타납니다.

# 개념 예 (RHOSO 문서의 다중 저장소 예를 단순화)
[DEFAULT]
enabled_backends = ceph-0:rbd,ceph-1:rbd,swift-0:swift
[glance_store]
default_backend = ceph-0
[ceph-0]
rbd_store_ceph_conf = /etc/ceph/ceph-0.conf
rbd_store_pool = images
rbd_store_user = openstack
store_description = "중앙 사이트 Ceph"
glance stores-info                                   # 사용 가능한 저장소 목록
openstack image create … --store ceph-1 …            # 특정 저장소에 업로드 (클라이언트 지원 시)
glance image-import <ID> --import-method copy-image --stores ceph-1   # 다른 저장소로 복사
openstack image show <ID> -c properties | grep stores

다중 저장소의 대표 용도는 엣지·분산 사이트(DCN)입니다. 각 사이트에 Ceph를 두고, 이미지를 필요한 사이트 저장소로 복사해 두면 그 사이트의 VM이 원격 다운로드 없이 빠르게 뜹니다(29편).

섹션 10

RHOSO의 Glance

split과 single: 두 가지 배치 방식

레이아웃구성언제
split (기본)외부 API(public 엔드포인트용)와 내부 API(internal 엔드포인트용) Pod가 따로 뜸Ceph RBD, Swift, Cinder 등 대부분의 저장소
singleAPI 하나가 public·internal을 모두 처리NFS·file 저장소에서는 반드시 single (여러 Pod가 같은 파일 공유에 접근하므로 split이 성립하지 않음)

split은 3편 “세 개의 문”이 Glance에서 실제로 Pod 단위로 나뉜 모습입니다. 외부 사용자 요청과 내부 서비스(Nova·Cinder) 요청을 다른 Pod가 처리하므로, 내부 전용으로만 허용하고 싶은 기능(예: 저장 위치 정보 노출처럼 Ceph 복제에 필요하지만 외부에 보이면 위험한 정보)을 내부 API에만 둘 수 있습니다.

OpenStackControlPlane의 glance 칸

glance:
  apiOverrides:
    default:
      route: {}                         # public 엔드포인트 = Route
  template:
    databaseInstance: openstack
    secret: osp-secret
    keystoneEndpoint: default            # 카탈로그에 등록할 glanceAPI (여러 개일 때 하나 지정)
    storage:
      storageRequest: 10G                # Pod별 작업 공간(가져오기 스테이징·캐시) PVC
    customServiceConfig: |
      [DEFAULT]
      enabled_backends = default_backend:rbd
      [glance_store]
      default_backend = default_backend
      [default_backend]
      rbd_store_ceph_conf = /etc/ceph/ceph.conf
      rbd_store_pool = images
      rbd_store_user = openstack
    glanceAPIs:
      default:
        type: split                       # NFS·file이면 single
        replicas: 3                       # 문서 예시는 0: 백엔드를 구성해야 활성화
        networkAttachments: [storage]       # 저장소 접근용 storage 망

학습용으로 단순화한 예시입니다. Ceph 접속 파일(ceph.conf, keyring)을 Pod에 넣는 방법은 extraMounts로 하며 8편에서 다룹니다.

replicas: 0으로 시작하는 이유

RHOSO 배포 문서의 컨트롤 플레인 예시에서 Glance API는 replicas: 0과 “백엔드를 구성해야 서비스가 활성화된다”는 주석으로 시작합니다. 저장소 없이 Glance를 띄우면 이미지를 받아도 둘 곳이 없기 때문입니다. 저장소를 설정한 뒤 운영 환경에서는 3개 정도로 올리는 것이 일반적입니다. 설치 후 “Glance가 없다”는 문의의 흔한 원인입니다.

여러 glanceAPI 두기

glanceAPIs는 이름이 붙은 여러 개의 API를 가질 수 있습니다. 예를 들어 split 레이아웃의 Ceph용 API와 single 레이아웃의 NFS용 API를 따로 두거나, 가용 영역(AZ)·엣지 사이트마다 자기 저장소를 쓰는 API를 둘 수 있습니다. 카탈로그에는 keystoneEndpoint로 지정한 하나가 등록됩니다. 이미 배포된 API의 레이아웃(split↔single)은 바꾸기 어렵기 때문에, 변경이 필요하면 새 glanceAPI를 추가하는 방식으로 접근합니다.

oc get glance,glanceapi -n openstack
oc get pods -n openstack | grep glance        # 예: glance-default-external-api-0, glance-default-internal-api-0
oc get route,svc -n openstack | grep glance
oc logs -n openstack <glance API Pod> --all-containers --tail=50

섹션 11

서명과 검증: 이 이미지는 진짜인가

골든 이미지가 중간에 바뀌지 않았다는 것을 어떻게 보장할까요? 두 단계가 있습니다.

장치무엇을 보장방법
해시 (os_hash_algo · os_hash_value)업로드·다운로드 중 깨지지 않았음Glance가 자동 계산 (기본 sha512). 예전 checksum(md5)도 함께 표시
이미지 서명믿을 수 있는 사람이 만든 원본 그대로임만든 사람이 개인키로 서명, 인증서는 Barbican에 보관, Glance·Nova가 공개키로 검증

서명 흐름

  1. 이미지 제작자가 개인키로 이미지 데이터의 해시에 서명합니다.
  2. 서명용 인증서를 Barbican(키 관리 서비스, 14편)에 올리고 그 UUID를 얻습니다.
  3. 이미지를 올릴 때 서명 속성 네 개를 함께 붙입니다.
  4. Glance가 업로드 시 서명을 검증해, 맞지 않으면 이미지를 받아들이지 않습니다.
  5. Nova에서 [glance] verify_glance_signatures = True를 켜면 부팅할 때 다시 검증합니다. 저장소에서 누군가 바꿔치기했어도 잡아냅니다.
openstack image create --disk-format raw --container-format bare --file golden.raw \
   --property img_signature="$(cat golden.sig.b64)" \
   --property img_signature_hash_method=SHA-256 \
   --property img_signature_key_type=RSA-PSS \
   --property img_signature_certificate_uuid=<Barbican 인증서 UUID> \
   golden-rhel9-signed

비유: 택배 봉인 테이프와 발송인 도장

해시는 봉인 테이프입니다. 뜯기거나 찢겼는지는 알 수 있지만, 누가 붙였는지는 모릅니다. 서명은 발송인 도장입니다. 진짜 그 발송인이 보낸 상자인지 확인할 수 있습니다. 규제가 있는 고객(금융·공공)은 “공급망 보안” 요구로 서명까지 요청하는 경우가 많습니다.

섹션 12

크기·개수 제한과 정리

제한뜻참고
image_size_cap이미지 하나의 최대 크기업스트림 기본 1 TiB. 넘으면 업로드 거부(413)
통합 제한 (unified limits)프로젝트별 총 이미지 용량, 이미지 개수, 업로드·스테이징 중 용량Glance가 Keystone 통합 제한을 쓰도록 설정한 경우(use_keystone_limits). 항목 예: image_size_total, image_count_total
속성 개수 제한이미지 하나에 붙일 수 있는 속성 수image_property_quota

정리 정책: 누가, 무엇을, 언제

  • 인스턴스 스냅샷은 이미지로 쌓입니다. 백업 목적이라면 Cinder 백업이나 별도 백업 솔루션을 안내하고, 스냅샷 보존 기간을 정합니다.
  • 구버전 골든 이미지는 바로 지우지 말고 --hidden으로 목록에서 숨긴 뒤, 사용 중인 인스턴스가 없을 때 삭제합니다. Ceph에서는 그 이미지로 만든 VM 디스크가 남아 있으면 이미지를 지울 수 없는 경우가 있습니다(복제본이 원본 스냅샷에 의존).
  • queued·killed 상태로 남은 실패 이미지는 정기적으로 찾아 정리합니다.
openstack image list --status queued
openstack image list --property image_type=snapshot --long     # 인스턴스 스냅샷 찾기
openstack server list --all-projects --image <이미지 ID>        # 이 이미지로 만든 VM이 남았는지

MSP 관점: 이미지는 비용이다

고객 프로젝트의 스냅샷 이미지는 저장소 용량을 차지하므로, 과금(32편)이나 쿼터 정책과 연결해야 합니다. “스냅샷은 몇 개까지, 며칠 보관”을 서비스 약관에 명시해 두면 분쟁을 줄일 수 있습니다.

섹션 18

정리와 다음 편

오늘의 핵심 여덟 문장

  • Glance는 이미지의 목록·속성·데이터 보관·가져오기를 맡고, VM 실행은 하지 않는다. 인스턴스 스냅샷도 이미지다.
  • qcow2는 작고 유연하며, raw는 단순하고 빠르다. Ceph RBD에서는 raw여야 복사 없는 복제(CoW)가 된다.
  • 올리기 전 qemu-img info로 실제 형식, 가상 크기, 백킹 파일을 확인한다. 선언과 실제가 다르면 거부되거나 문제가 된다.
  • 공개 범위는 private·shared·community·public. 공유는 멤버 추가 + 상대 수락.
  • 가져오기는 glance-direct·web-download·copy-image이며, image_conversion 플러그인으로 raw 자동 변환이 가능하다. web-download는 접속 대상 제한이 필요하다.
  • hw_* 같은 이미지 속성은 가상 장치와 배치 후보를 바꾼다. “No valid host”면 이미지 속성도 확인한다.
  • RHOSO Glance는 기본 split(외부·내부 API 분리), NFS·file은 single. 예시 replicas는 0이며 저장소를 구성해야 활성화된다.
  • 해시는 무결성, 서명은 출처를 보장한다. 인증서는 Barbican, 부팅 시 검증은 Nova 설정.
