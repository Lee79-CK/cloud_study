섹션 1

이 편의 목표

  1. RHOSO 랩의 세 가지 구성 방식(공식 최소, 가상화 랩, 업스트림 개발 도구)의 차이와 용도를 안다.
  2. RHOSO 18.0의 OpenShift·데이터 플레인 최소 요구 사항을 확인하고 자원을 계산한다.
  3. 랩 토폴로지와 격리망 주소 계획(3편 규칙)을 세운다.
  4. 선행 Operator(NMState, MetalLB, cert-manager, Cluster Observability, 저장소)를 설치·확인한다.
  5. OpenStack Operator를 설치하고 초기화 리소스(OpenStack CR)로 준비 상태를 확인한다.
  6. openstack 네임스페이스와 osp-secret을 만든다.

이 편의 비유: 집 짓기 전 터 다지기

집(RHOSO)을 짓기 전에 땅(서버)을 고르고, 측량해서 구획을 나누고(주소 계획), 상하수도·전기 같은 기반 설비(선행 Operator)를 들이고, 건축 회사(OpenStack Operator)와 계약하고, 열쇠 꾸러미(osp-secret)를 만들어 두는 단계입니다. 이 단계의 실수(땅 크기 부족, 구획 겹침)는 나중에 고치기가 매우 어렵습니다.

섹션 7

가상화 호스트 준비 (B안)

물리 서버(RHEL 9 + KVM/libvirt)에서 VM들을 띄웁니다. 핵심은 세 가지입니다: 중첩 가상화(컴퓨트 VM 안에서 다시 VM을 돌림), 망 분리(OCP 기본망과 RHOSO 격리망 트렁크), 충분한 디스크 속도.

# ① 중첩 가상화 확인·활성화 (Intel 예, AMD는 kvm_amd)
cat /sys/module/kvm_intel/parameters/nested           # Y 또는 1 이면 켜짐
echo "options kvm_intel nested=1" | sudo tee /etc/modprobe.d/kvm-nested.conf   # 재부팅 또는 모듈 재적재

# ② 망: 리눅스 브리지 두 개 (예시 이름)
#   br-ocp   : OCP 기본망 (DHCP·DNS·인터넷)
#   br-osp   : RHOSO 트렁크 — ctlplane은 태그 없이, internalapi·storage·tenant는 VLAN 태그로 같은 브리지에 흐름
nmcli con add type bridge ifname br-osp con-name br-osp ipv4.method manual ipv4.addresses 192.168.122.1/24
#   (외부망 실습용으로 br-osp 위에 VLAN 인터페이스나 별도 브리지를 두고, NAT로 인터넷 연결)

# ③ VM 만들기: OCP VM은 Agent ISO로 부팅(섹션 8), 컴퓨트 VM은 RHEL 9.x 설치
virt-install --name compute-0 --vcpus 8 --memory 16384 --cpu host-passthrough \
  --disk size=80,bus=virtio --network bridge=br-osp,model=virtio \
  --os-variant rhel9.4 --location <RHEL ISO> …

가상화 랩의 요령

  • 컴퓨트 VM은 --cpu host-passthrough로 VT 기능이 안으로 전달되게 합니다. 아니면 그 안의 VM이 매우 느린 에뮬레이션으로 돌거나 아예 안 뜹니다.
  • VM 디스크는 NVMe·SSD 위에 둡니다. Galera·etcd는 디스크 지연에 민감합니다.
  • 단계마다 VM 스냅샷을 떠 두면(“Operator 설치 직후”, “컨트롤 플레인 직후”) 실험하다 망가져도 빨리 되돌릴 수 있습니다.
  • VLAN 태그가 브리지를 통과하는지(리눅스 브리지는 기본적으로 태그 프레임을 그대로 전달) 18편에서 ping으로 확인합니다.

섹션 8

OpenShift 클러스터 설치 개요

OCP 설치 자체는 OpenShift 문서의 영역이지만, RHOSO를 위해 꼭 지켜야 할 점들이 있습니다. 랩에서는 Agent-based Installer로 compact 3노드를 만드는 방식이 간단합니다.

항목RHOSO를 위한 주의
버전RHOSO가 지원하는 OCP 버전으로 고정 (현재 문서 4.18). 설치 프로그램 기본값이 최신이라 그대로 쓰면 지원 밖 버전이 깔릴 수 있음
토폴로지compact: controlPlane.replicas: 3, compute.replicas: 0 (컨트롤 플레인 노드가 워커 역할도 함)
NIC설치 시에는 첫 NIC(OCP 기본망)만 구성. 두 번째 NIC(RHOSO 격리망)는 18편에서 NMState로
시간·DNS모든 노드 NTP 동기화(4편: 토큰 시간), API·인그레스 와일드카드 DNS(*.apps.<도메인>) — RHOSO 공개 엔드포인트가 Route이기 때문
레지스트리registry.redhat.io 접근(pull secret) 또는 미러 레지스트리(비연결 환경)
 
# install-config.yaml 핵심만 (학습용)
apiVersion: v1
baseDomain: lab.example.com
metadata: { name: rhoso }
controlPlane: { name: master, replicas: 3 }
compute: [ { name: worker, replicas: 0 } ]   # compact
networking:
  machineNetwork: [ { cidr: 10.0.0.0/24 } ]      # OCP 기본망 (RHOSO 격리망과 겹치지 않게!)
  networkType: OVNKubernetes
platform:
  baremetal: { apiVIPs: [10.0.0.5], ingressVIPs: [10.0.0.7] }
pullSecret: '…'
sshKey: '…'

# 설치 후 확인
oc get nodes                  # 3대 Ready
oc get clusterversion         # 버전이 계획과 같은지
oc get co | grep -v 'True.*False.*False'   # 비정상 클러스터 오퍼레이터가 없는지

Agent-based Installer는 이 파일과 agent-config.yaml(노드별 MAC·IP, rendezvous IP)로 부팅 ISO를 만듭니다. 상세 절차와 버전 고정 방법은 OCP 설치 문서와 Red Hat 지식 문서(특정 OCP 버전 설치)를 따르세요.

가장 흔한 첫 실수: 주소 겹침

OCP의 machineNetwork·Pod 망·Service 망과 RHOSO 격리망(ctlplane 192.168.122.0/24, 172.17~19.x 등)이 겹치면 18편 이후 원인 모를 통신 장애가 납니다. 섹션 6 표를 OCP 설치 전에 확정하세요.

섹션 10

스토리지 클래스 준비

RHOSO 컨트롤 플레인 Pod들이 쓸 PVC를 만들어 줄 StorageClass가 필요합니다. 문서는 SSD·NVMe 기반을 권장하고, 마땅한 것이 없으면 LVM Storage(LVMS) Operator를 쓰라고 안내합니다. 랩에서는 각 OCP 노드의 두 번째 디스크(250GB)를 LVMS로 묶는 방식이 가장 쉽습니다.

# LVMS 설치 후 LVMCluster (학습용 최소 예)
cat <<EOF | oc apply -f -
apiVersion: lvm.topolvm.io/v1alpha1
kind: LVMCluster
metadata: { name: lvmcluster, namespace: openshift-storage }
spec:
  storage:
    deviceClasses:
    - name: vg1
      default: true
      thinPoolConfig: { name: thin-pool-1, sizePercent: 90, overprovisionRatio: 10 }
      deviceSelector: { paths: [ /dev/vdb ] }      # 각 노드의 추가 디스크 (환경에 맞게)
EOF
oc get lvmcluster -n openshift-storage           # Ready
oc get storageclass                              # 예: lvms-vg1 (default)

LVMS는 노드 로컬 저장소

16편에서 본 대로 LVMS PVC는 그 노드에 묶입니다. 랩에는 충분하지만, 운영에서 노드를 교체하거나 오래 잃으면 그 PVC를 쓰는 Pod(Galera·RabbitMQ 등)를 다른 노드로 옮길 수 없습니다. 운영 설계에서는 ODF 같은 공유 스토리지와 비교해 결정합니다(27편).

섹션 11

OpenStack Operator 설치

RHOSO의 모든 서비스 Operator(keystone-operator, nova-operator …)는 OpenStack Operator 하나를 설치하고 초기화하면 함께 올라옵니다(2편).

# ① 네임스페이스 · OperatorGroup · Subscription (RHOSO 문서의 CLI 절차)
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Namespace
metadata: { name: openstack-operators }
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata: { name: openstack, namespace: openstack-operators }
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata: { name: openstack-operator, namespace: openstack-operators }
spec:
  name: openstack-operator
  channel: stable-v1.0
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual        # 업데이트를 사람이 승인 (26편 유지보수와 연결)
EOF

# ② 수동 승인이면 설치 계획(InstallPlan)을 승인
oc get installplan -n openstack-operators
oc patch installplan <이름> -n openstack-operators --type merge -p '{"spec":{"approved":true}}'

# ③ 설치 완료 확인
oc wait csv -n openstack-operators \
  -l operators.coreos.com/openstack-operator.openstack-operators="" \
  --for jsonpath='{.status.phase}'=Succeeded

# ④ 초기화 리소스 하나 만들기 → 서비스 Operator들이 시작됨
cat <<EOF | oc apply -f -
apiVersion: operator.openstack.org/v1beta1
kind: OpenStack
metadata: { name: openstack, namespace: openstack-operators }
EOF
oc wait openstack/openstack -n openstack-operators --for condition=Ready --timeout=500s
oc get pods -n openstack-operators              # 여러 *-operator-controller-manager Pod

자동 승인 vs 수동 승인

Subscription의 installPlanApproval을 Automatic으로 두면 새 Operator 버전이 나오는 즉시 올라가고, 그 결과 RHOSO 서비스 업데이트가 계획 없이 시작될 수 있습니다. 운영에서는 Manual로 두고 유지보수 창에서 승인하는 것이 일반적입니다(26편). RHOSO 버전과 Operator·OpenStackVersion CR의 대응은 Red Hat 지식 문서로 확인합니다.

섹션 13

osp-secret 만들기

osp-secret은 관리자·서비스 계정·DB root 비밀번호와 몇 가지 암호화 키를 담는 Secret입니다(5편: 서비스 계정). 문서는 각 값을 32자 무작위 문자열을 base64로 인코딩해 넣도록 안내하고, 다음처럼 한 번에 생성하는 예를 제공합니다.

# RHOSO 문서 예를 따른 생성 (일부 키만 표시 — 전체 목록은 문서 참조)
cat <<EOF > openstack_service_secret.yaml
apiVersion: v1
kind: Secret
metadata: { name: osp-secret, namespace: openstack }
type: Opaque
data:
  AdminPassword: $(tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32 | base64)
  DbRootPassword: $(tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32 | base64)
  # 같은 방식으로: AodhPassword BarbicanPassword CeilometerPassword CinderPassword DesignatePassword
  #              GlancePassword HeatPassword IronicPassword IronicInspectorPassword ManilaPassword
  #              NeutronPassword NovaPassword PlacementPassword SwiftPassword … (설치 버전 문서의 전체 목록)
  MetadataSecret: $(tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32 | base64)
  HeatAuthEncryptionKey: $(tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32 | base64)   # 반드시 32자
  BarbicanSimpleCryptoKEK: $(python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode('UTF-8'))" | base64)
EOF
oc create -f openstack_service_secret.yaml -n openstack
oc describe secret osp-secret -n openstack           # 키 이름과 크기만 확인 (값은 보이지 않음)

세 가지 경고

  • 배포 후 서비스 비밀번호를 바꾸지 마세요. 문서 경고대로, 컨트롤 플레인 배포 후 osp-secret의 서비스 비밀번호를 바꾸면 Keystone 쪽은 바뀌지 않아 서비스가 멈춥니다(5편).
  • HeatAuthEncryptionKey는 정확히 32자여야 합니다. 다른 비밀번호를 늘리더라도 이 값은 32자로 둡니다.
  • BarbicanSimpleCryptoKEK는 Barbican이 모든 비밀을 감싸는 마스터 키입니다(14편). 이 파일을 안전한 곳에 따로 백업하세요. 잃으면 암호화된 데이터를 열 수 없습니다.

데이터 플레인용 비밀(Ansible SSH 키 dataplane-ansible-ssh-private-key-secret, 마이그레이션 SSH 키 nova-migration-ssh-key, libvirt 비밀 등)은 20편에서 만듭니다.

섹션 19

정리와 다음 편

오늘의 핵심 여덟 문장

  • 랩은 공식 최소(지원 구성 축소판) · 가상화 랩(학습) · 업스트림 도구(개발) 중 목적에 맞게. 절차는 공식 문서 기준으로.
  • OCP는 3노드 베어메탈, 문서 기준 버전(현재 4.18)으로 고정, 워커당 64GB·16코어·120+250GB SSD·NIC 2개.
  • 컴퓨트 노드는 VT 켜진 x86, 호스트용 6GB+VM 메모리, 스왑 4GB, 디스크 50GB+.
  • 주소 계획은 3편 규칙(.10 / .30~.70 / .80~.90 / .100~), OCP 망과 겹치지 않게 설치 전에 확정.
  • 선행 Operator: NMState · MetalLB · cert-manager · Cluster Observability · 저장소(LVMS 등).
  • OpenStack Operator: openstack-operators 네임스페이스, stable-v1.0, 수동 승인 권장, OpenStack 초기화 CR → Ready.
  • openstack 네임스페이스는 특권 레이블, 서비스 배치는 레이블·Topology로 조절.
  • osp-secret: 32자 무작위 base64, HeatAuthEncryptionKey 32자 고정, KEK 백업, 배포 후 서비스 비밀번호 변경 금지.
