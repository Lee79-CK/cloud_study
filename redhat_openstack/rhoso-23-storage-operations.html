23편스토리지 운영

스토리지는 운영에서 가장 조용히 문제가 커지는 영역입니다. 용량은 매일 조금씩 차오르고, 백업은 실패해도 아무도 모르다가 복구가 필요한 날 드러나며, error 상태 볼륨은 쌓여 쿼터를 잡아먹습니다. 이번 편은 7·8편의 구조 지식을 매일·매주·매월의 운영 습관으로 바꿉니다.

약 110분예상 학습 시간
6·7·8편 이수Glance·Cinder·Ceph
시뮬레이터·계산기 3종Ceph, 씬, 백업
다음 편24편 네트워크 운영 심화

섹션 1

이 편의 목표

  1. ceph df·ceph osd df를 읽고 실제 남은 용량(MAX AVAIL)과 위험 시점을 판단한다.
  2. nearfull·full 경보에 대한 대응 순서를 안다.
  3. Cinder의 씬 프로비저닝·과다 할당 설정을 이해하고 위험을 계산한다.
  4. 볼륨 타입·QoS를 상품처럼 운영하고 변경·퇴역 절차를 안다.
  5. 스냅샷과 백업을 구분해 정책을 세우고 복구 연습을 한다.
  6. error·deleting 등에 멈춘 볼륨을 안전하게 정리한다.
  7. 이미지 수명 주기와 Glance 캐시, 그리고 스토리지 증설 절차를 수행한다.

이 편의 비유: 물류 창고 관리

Ceph는 창고 건물, OSD는 선반, Cinder 볼륨은 고객이 예약한 보관 칸입니다. 예약(씬 프로비저닝)은 실제 짐보다 많이 받을 수 있지만, 한 선반이 꽉 차면 창고 전체가 입고를 멈춥니다(full). 매일 선반 높이를 보고, 오래된 짐(고아·error 볼륨)을 치우고, 귀중품은 다른 창고에 사본을 두고(백업), 꽉 차기 전에 선반을 늘립니다(증설).

섹션 3

Ceph 용량 읽기

값뜻주의
RAW: SIZE · AVAIL · %RAW USED모든 OSD 디스크 합계 기준사본 3개가 반영되기 전의 물리 수치
POOL: STORED사용자가 실제로 저장한 양 (사본 1개 기준)볼륨 크기의 합이 아니라 실제 쓰인 양 (씬)
POOL: USED사본까지 포함해 디스크를 차지한 양 (≈ STORED × 3)—
POOL: MAX AVAIL이 풀에 앞으로 더 쓸 수 있는 양 (사본 1개 기준)가장 꽉 찬 OSD가 full에 닿는 시점으로 계산 → 전체 평균보다 훨씬 작을 수 있음
임계값 (기본)OSD 사용률무슨 일이 일어나나
nearfull85%HEALTH_WARN 경보. 아직 정상 동작 — 증설·정리 착수 시점
backfillfull90%그 OSD로의 데이터 재배치(복구·재균형) 중단 → 장애 복구가 막힘
full95%클러스터 전체 쓰기 중단 — VM 디스크 I/O가 멈춤
 
ceph -s                                       # HEALTH, 용량 요약
ceph df detail                                # 풀별 STORED·USED·MAX AVAIL, 쿼터
ceph osd df tree                              # OSD별 %USE, VAR(평균 대비), PGS — 편차 확인
ceph osd pool autoscale-status                # 풀별 PG 수 자동 조정 상태
ceph balancer status                          # OSD 간 고르게 퍼뜨리는 balancer 동작 여부
rbd du -p volumes | tail -1                   # 할당(PROVISIONED) 대 실제(USED)

nearfull 대응 순서

  1. 원인 파악: 전체가 찼나, 일부 OSD만 찼나(ceph osd df의 VAR). 일부만이면 balancer·가중치 문제.
  2. 쓸모없는 데이터 정리: 고아·error 볼륨(섹션 8), 오래된 스냅샷, 쓰지 않는 이미지(섹션 9), Ceph 휴지통(deferred deletion).
  3. 증설(섹션 10): 리밸런싱에 시간이 걸리므로 nearfull에서 시작해야 full 전에 끝납니다.
  4. 임계값을 잠시 올리는 것(ceph osd set-nearfull-ratio 등)은 시간을 버는 응급 조치일 뿐입니다. full을 넘기면 복구가 매우 어렵습니다.

외부 Ceph는 보통 스토리지팀이 운영합니다. RHOSO 운영자는 위 명령을 읽을 수 있는 권한(또는 대시보드·경보 공유)을 받아 두고, 대응 책임 분담을 문서로 정해 두세요.

섹션 4

Ceph 용량 시뮬레이터

OSD 8개(각 4 TiB, 사본 3개)인 클러스터입니다. 데이터를 넣고, OSD 사이 편차를 키우고, 증설·재균형을 해 보세요. MAX AVAIL이 가장 꽉 찬 OSD에 끌려 다니는 모습을 볼 수 있습니다. (학습용 단순 모델)

섹션 5

Cinder 용량과 씬 프로비저닝

Ceph RBD 볼륨은 씬 프로비저닝이라, 100GB 볼륨을 만들어도 실제로 쓴 만큼만 공간을 차지합니다. 그래서 Cinder 스케줄러는 “할당된 크기 합계”를 실제 용량보다 크게 허용합니다(과다 할당 비율).

설정 (cinder 백엔드)뜻
max_over_subscription_ratio할당 합계 / 실제 용량의 상한. 이 값을 넘으면 스케줄러가 그 풀을 후보에서 뺌 (7편 CapacityFilter)
reserved_percentage풀 용량 중 새 볼륨에 내주지 않고 남겨 둘 비율
thin_provisioning_support 등 (보고값)드라이버가 씬을 지원하는지 스케줄러에 알림
 
openstack volume backend pool list --long        # 풀별 total·free·provisioned 용량, 비율
openstack volume service list                    # 백엔드별 cinder-volume 상태
# 설정은 19편 cinderVolumes.<백엔드>.customServiceConfig 의 [백엔드] 섹션에

섹션 6

볼륨 타입·QoS 정책 운영

볼륨 타입(7편)은 고객에게는 상품 메뉴입니다. 메뉴는 적고 명확하게, 바꿀 때는 기존 고객 영향을 고려합니다.

예시 타입백엔드QoS용도
standard (기본)Ceph HDD·혼합 풀front-end total_iops_sec=1000일반 업무
ssdCeph SSD 풀total_iops_sec_per_gb=30, 최소값DB
encryptedCeph SSD + LUKS (14편)ssd와 같음규제 데이터
cust-a-dedicated (비공개)고객 전용 풀계약값특정 고객만 (--private + 접근 허용)
운영 작업명령영향
QoS 값 변경openstack volume qos set --property total_iops_sec=2000 std-qosfront-end QoS는 새로 연결될 때 적용 → 기존 연결 VM은 분리·재연결(또는 VM 재시작) 후 반영
고객 전용 타입openstack volume type create --private … · volume type set --project <ID>그 프로젝트에만 보임
타입 변경 (retype)openstack volume set --type ssd --retype-policy on-demand vol1백엔드가 바뀌면 데이터 이동(시간·부하), 7편
기본 타입 지정Cinder default_volume_type 설정타입 없이 만든 볼륨에 적용
타입 퇴역비공개로 전환 → 사용 볼륨을 retype → 사용 0이면 삭제사용 중인 타입은 삭제 불가

QoS로 “시끄러운 이웃” 막기

공유 Ceph에서 QoS가 없으면 한 고객의 대량 작업(백업·배치)이 다른 고객 VM의 디스크 지연을 키웁니다. 모든 공개 타입에 상한 QoS를 기본으로 걸고, 더 높은 성능은 상위 타입(상품)으로 판매하는 방식이 MSP에서 흔합니다.

백업 정책 계산기

복구 연습 없는 백업은 백업이 아니다

Cinder에는 자체 백업 일정 기능이 없어 보통 cron·Ansible·외부 도구로 돌립니다. 그만큼 실패를 놓치기 쉽습니다. 매일 실패한 백업(volume backup list --status error)을 확인하고, 매월 무작위 볼륨 하나를 새 볼륨으로 복원해 VM에 붙여 확인하는 연습을 일정에 넣으세요. 복원 소요 시간도 기록해 고객 RTO 약속의 근거로 씁니다(27편).

섹션 8

멈춘 볼륨 정리

8편에서 상태별 복구 원칙을 배웠습니다. 운영에서는 이것을 정기 점검(sweep)으로 바꿉니다: “전환 상태에 1시간 넘게 있는 볼륨”을 찾아 하나씩 처리합니다. 표의 행을 누르면 처리 방법이 나옵니다.

행을 눌러 보세요.

# 정기 점검: 전환·오류 상태 볼륨 찾기 (관리자)
for s in error error_deleting deleting creating attaching detaching reserved maintenance; do
  openstack volume list --all-projects --status $s -f value -c ID -c Name -c Status
done
# 상태를 실제와 맞추기 (원인 확인 후에만!)
openstack volume set --state available <볼륨>           # reset-state
openstack volume set --detached <볼륨>                  # 연결 상태 기록만 정정
openstack volume delete --force <볼륨>                  # 강제 삭제 (백엔드까지 지우려 시도)
openstack volume snapshot set --state available <스냅샷>

세 가지 금지 (8편 복습)

  • 원인을 모른 채 상태만 바꾸지 않는다 — 실제로 연결된 볼륨을 available로 만들면 두 VM이 같은 디스크를 쓸 수 있습니다.
  • Ceph에서 rbd rm으로 직접 지우지 않는다 — Cinder 기록과 어긋나고 스냅샷·클론 관계가 깨집니다.
  • DB를 직접 고치지 않는다 — 지원 절차와 API 명령으로 해결합니다.

Glance 이미지 캐시

Glance API Pod가 자주 요청되는 이미지를 로컬 디스크에 사본으로 두어 백엔드 읽기를 줄이는 기능입니다. RHOSO에서는 OpenStackControlPlane의 glance 템플릿에 imageCache.size를 지정해 켜고, 주기 작업 대신 이미지를 즉시 캐시에 올리도록 요청(queue)할 수 있습니다.

glance:
  template:
    imageCache:
      size: 10Gi                 # 캐시 크기 (Pod별 저장소)
    storage:
      storageRequest: 10Gi

캐시가 필요한 경우와 아닌 경우

Glance·Nova가 같은 Ceph를 쓰는 기본 구성에서는 VM 디스크가 Ceph 안에서 바로 복제되므로(6편) Glance 캐시의 이득이 작습니다. 캐시는 이미지 다운로드가 실제로 일어나는 구성 — 컴퓨트 로컬 디스크, 원격 사이트(DCN, 29편), 느린 백엔드 — 에서 효과가 큽니다. 캐시 관리 명령은 클라이언트 버전에 따라 openstack cached image … 또는 glance cache-* 형태입니다.

섹션 16

  
정리와 다음 편

  
오늘의 핵심 여덟 문장

  
    
    
  • Ceph의 “더 쓸 수 있는 양”은 MAX AVAIL이며 가장 꽉 찬 OSD가 결정한다. 평균 사용률만 보면 늦는다.
    • 
    
  • nearfull 85% → backfillfull 90% → full 95%. full이면 클러스터 전체 쓰기가 멈추므로 nearfull에서 증설을 시작한다.
    • 
    
  • 편차가 크면 balancer, 데이터가 많으면 정리 + 증설. 임계값 올리기는 시간 벌기일 뿐.
    • 
    
  • RBD는 씬이라 Cinder가 max_over_subscription_ratio만큼 과다 할당한다. 실제 사용률이 오르면 순식간에 찬다.
    • 
    
  • 볼륨 타입은 상품: 기본 QoS 상한, 고객 전용 비공개 타입, front-end QoS 변경은 재연결 후 반영.
    • 
    
  • 스냅샷은 같은 백엔드, 백업은 다른 저장소. 백업 메타데이터를 내보내 두고, 매월 복구 연습.
    • 
    
  • 멈춘 볼륨은 정기 점검 → 원인 확인 → API로 상태 정정·강제 삭제. Ceph·DB 직접 수정 금지.
    • 
    
  • 이미지는 숨김 → 비활성 → 삭제로 퇴역, Glance 캐시는 다운로드가 일어나는 구성에서 효과.
    •
