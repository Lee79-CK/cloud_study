Service·kube-proxy와 그 대체재

Service의 가상 IP는 어느 네트워크 카드에도 붙어 있지 않습니다. 패킷이 그 주소로 향하는 순간 누군가가 가로채 진짜 Pod 주소로 바꿔 줄 뿐입니다. 그 “누군가”가 iptables 규칙인지, nftables 맵인지, IPVS 테이블인지, eBPF 프로그램인지, OVN 로드밸런서인지에 따라 성능도, 출발지 IP도, 장애 때 봐야 할 곳도 달라집니다. 이 편은 같은 Service를 다섯 가지 구현으로 덤프해서 읽습니다.

기준: Kubernetes v1.37 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 120분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

읽는 법과 목표

    
쉬운 말로
    Service는 회사의 대표 전화번호입니다. 손님은 대표 번호(ClusterIP)로 전화하고, 교환대가 지금 자리에 있는 직원(Pod) 중 한 명에게 돌려 줍니다. 교환대 역할을 누가 하느냐가 이 편의 주제입니다. kube-proxy는 노드마다 앉은 교환원이 규칙표(iptables·nftables)를 보고 돌려 주는 방식이고, Cilium은 전화기 자체에 자동 연결 기능(eBPF)을 넣어 교환원을 없앤 방식이며, OVN-K는 사내 전화망(가상 스위치)에 연결 규칙을 심은 방식입니다.

    

      
4·5편처럼 점선 밑줄 용어는 마우스를 올리거나 누르면 설명이 나오고, 14장 사전에 모여 있습니다.

      
이 편을 마치면 할 수 있는 것

      
    
        
  • ClusterIP·NodePort·LoadBalancer 요청이 iptables·IPVS·nftables·eBPF·OVN에서 각각 어떤 규칙을 거쳐 Pod에 닿는지 덤프를 보고 설명할 수 있습니다.
    • 
        
  • EndpointSlice의 조건(ready·serving·terminating)과 힌트가 트래픽 분배에 어떻게 쓰이는지 설명할 수 있습니다.
    • 
        
  • externalTrafficPolicy·internalTrafficPolicy·trafficDistribution·세션 어피니티의 조합이 출발지 IP, 부하 분산, 지역성, 장애 동작에 주는 영향을 예측할 수 있습니다.
    • 
        
  • kube-proxy가 없는 클러스터(Cilium, GKE Dataplane V2, AKS Cilium, OpenShift)에서 Service 장애를 구현별 도구로 진단할 수 있습니다.
    • 
        
  • IPVS 폐기와 nftables 전환 흐름에 맞춰 고객 클러스터의 kube-proxy 모드 이전 계획을 세울 수 있습니다.
    •

Service를 정밀하게

    

      
누가 무엇을 하나

      
Service 하나가 동작하려면 서로 다른 네 주체가 협업합니다. 장애가 났을 때 “어느 주체의 일이 안 됐나”로 쪼개는 것이 진단의 출발점입니다.

    

    

      
주체하는 일잘못되면

      
        
API 서버ClusterIP와 NodePort 번호를 할당(Service CIDR, 기본 NodePort 범위 30000~32767)IP 고갈, 포트 충돌로 Service 생성 실패

        
EndpointSlice 컨트롤러selector에 맞는 Pod를 찾아 EndpointSlice에 주소·상태를 기록엔드포인트 없음(selector·레이블 불일치, Pod 미준비)

        
프록시 구현노드마다 가상 IP → Pod IP 변환 규칙을 프로그래밍(kube-proxy, Cilium, OVN-K 등)규칙 누락·지연, 특정 노드에서만 실패

        
클라우드 컨트롤러type: LoadBalancer에 외부 LB를 만들고 IP를 status에 기록(CCM, LB 컨트롤러)EXTERNAL-IP pending(3편 스모크 테스트의 kubeadm·RKE2)

      
    

    
종류별 정리

    

      
종류무엇이 생기나쉬운 말로주의

      
        
ClusterIP클러스터 안에서만 통하는 가상 IP사내 대표 번호노드 밖에서는 라우팅되지 않음(VPC 직결 CNI라도)

        
NodePortClusterIP + 모든 노드의 같은 포트모든 지점 건물에 같은 내선 번호nftables 모드는 localhost(127.0.0.1)의 NodePort를 받지 않음(5장)

        
LoadBalancerNodePort + 외부 LB(구현은 클라우드·MetalLB 등)외부 고객용 대표 번호LB가 노드로 보내느냐 Pod로 바로 보내느냐는 구현마다 다름(7편)

        
Headless (clusterIP: None)가상 IP 없이 DNS가 Pod IP 목록을 직접 반환대표 번호 없이 직원 직통 번호부프록시를 거치지 않음. StatefulSet·클라이언트 측 분산에 사용

        
ExternalNameDNS CNAME만 생성다른 회사 번호로 착신 전환프록시 규칙 없음. TLS 인증서 이름 불일치 주의

      
    

    

      
최근 버전에서 달라진 것

      
    
        
  • Service CIDR 확장. ServiceCIDR·IPAddress API가 1.33에서 GA가 되어, 클러스터를 다시 만들지 않고도 Service 대역을 추가할 수 있습니다. 예전에는 API 서버 플래그 하나로 고정이라 대역 고갈이 재구축 사유였습니다.
    • 
        
  • LoadBalancer ipMode. LB가 패킷의 목적지를 LB IP 그대로 노드에 보내는지(VIP), 프록시처럼 바꿔서 보내는지(Proxy)를 status에 표시해, kube-proxy가 LB IP를 노드 안에서 단축 처리할지 결정합니다. 7편에서 다룹니다.
    • 
        
  • spec.externalIPs 폐기 수순. 1.36에서 폐기와 제거 계획이 공지됐습니다. 아무 IP나 Service에 붙일 수 있어 트래픽 가로채기에 악용될 수 있던 필드입니다. 오래된 온프렘 매니페스트를 점검하세요.
    • 
        
  • Endpoints API 폐기 예고. 1.33부터 Endpoints 대신 EndpointSlice를 쓰라는 경고가 나옵니다(2장).
    •

EndpointSlice: 프록시가 읽는 단 하나의 진실

    
쉬운 말로
    EndpointSlice는 교환대에 붙어 있는 “지금 근무 중인 직원 명단”입니다. 명단은 100명 단위 쪽지로 나뉘어 있고, 각 이름 옆에 “근무 중/곧 퇴근/퇴근 중” 표시와 “이 직원은 A동 손님 담당” 같은 메모(힌트)가 붙습니다. 모든 교환대 구현은 이 명단만 보고 연결합니다.

    

      
    
        
  • 쪼개진 명단. Service 하나에 슬라이스가 여러 개일 수 있습니다(기본 슬라이스당 최대 100개). Pod 하나가 바뀌어도 그 슬라이스만 갱신되어, 엔드포인트가 수천 개인 Service에서도 API 서버와 프록시의 부담이 작습니다. 옛 Endpoints 객체는 한 Service의 모든 주소를 한 객체에 담아 대형 Service에서 큰 부하를 만들었고, 1,000개를 넘으면 잘립니다.
    • 
        
  • 세 가지 조건. ready(트래픽 받아도 됨), serving(준비 상태지만 종료 중일 수도 있음), terminating(종료 중). 프록시는 기본으로 ready만 쓰고, 모든 엔드포인트가 종료 중일 때는 serving인 종료 중 엔드포인트로라도 보내 연결 끊김을 줄입니다. 롤링 업데이트 중 순간적인 503을 줄이는 장치입니다.
    • 
        
  • 힌트. 토폴로지 인식 라우팅·trafficDistribution이 켜지면 컨트롤러가 각 엔드포인트에 “어느 존(zone)·노드가 써야 하는지” 힌트를 붙이고, 프록시는 자기 존·노드와 맞는 엔드포인트만 고릅니다(8장).
    • 
        
  • 누가 쓰나. EndpointSlice 컨트롤러(selector 있는 Service), 미러링 컨트롤러(selector 없이 Endpoints를 직접 쓴 Service를 슬라이스로 복사), 그리고 서비스 메시·Gateway 구현체 같은 외부 컨트롤러가 직접 슬라이스를 만들기도 합니다(endpointslice.kubernetes.io/managed-by 레이블로 구분).
    • 
      

    

    
EndpointSlice 읽기
kubectl get endpointslices -l kubernetes.io/service-name=web -o wide
kubectl get endpointslices -l kubernetes.io/service-name=web -o yaml \
  | yq '.items[].endpoints[] | {"ip": .addresses[0], "node": .nodeName, "zone": .zone, "cond": .conditions, "hints": .hints}'

    
함정: Endpoints를 읽는 오래된 도구
    모니터링 스크립트, 사내 대시보드, 오래된 인그레스 컨트롤러가 아직 Endpoints 객체를 읽는 경우가 있습니다. 엔드포인트가 1,000개를 넘는 Service에서는 그 도구가 잘린 목록을 보게 되고, Endpoints 폐기가 진행되면 아예 동작하지 않게 됩니다. 고객 클러스터의 RBAC에서 endpoints 읽기 권한을 가진 ServiceAccount 목록을 뽑아 보면 이전 대상을 찾을 수 있습니다(18편의 who-can 활용).

kube-proxy iptables 모드: 규칙 체인 읽기

    
쉬운 말로
    iptables 모드의 kube-proxy는 노드마다 “이 번호로 오면 저 표를 봐라”는 이정표를 줄줄이 세웁니다. 패킷은 이정표를 위에서부터 차례로 읽다가 맞는 곳에서 목적지를 바꿉니다(DNAT). Pod 셋 중 하나를 고를 때는 주사위를 굴립니다(1/3, 남은 것 중 1/2, 마지막은 무조건).

    
체인 지도

    

      
체인역할쉬운 말로

      
        
KUBE-SERVICES모든 ClusterIP·LB IP의 입구. 목적지 IP·포트로 Service별 체인에 분기안내 데스크

        
KUBE-SVC-<해시>Service 하나. 확률 규칙으로 엔드포인트 하나를 고름부서 대표 번호

        
KUBE-SEP-<해시>엔드포인트 하나. Pod IP:포트로 DNAT직원 내선

        
KUBE-NODEPORTSNodePort 입구지점 건물 내선 안내

        
KUBE-EXT-<해시>외부에서 들어온 트래픽(NodePort·LB) 처리. 정책이 Cluster면 SNAT 표시 후 KUBE-SVC로외부 손님 응대 창구

        
KUBE-SVL-<해시>externalTrafficPolicy: Local일 때 이 노드의 엔드포인트만이 건물 직원에게만 연결

        
KUBE-MARK-MASQ / KUBE-POSTROUTING나중에 출발지를 노드 IP로 바꿀(masquerade) 패킷에 표시하고, 나갈 때 실제로 바꿈“회신은 지점 번호로” 도장

      
    

    
Service 하나를 따라가는 명령
CIP=$(kubectl -n svc-lab get svc web -o jsonpath='{.spec.clusterIP}')
sudo iptables-save -t nat | grep -- "-d $CIP/32"                  # KUBE-SERVICES → KUBE-SVC-xxx
SVC=$(sudo iptables-save -t nat | grep -- "-d $CIP/32" | grep -o 'KUBE-SVC-[A-Z0-9]*' | head -1)
sudo iptables -t nat -L "$SVC" -n -v                               # probability 0.333 / 0.5 / 나머지
sudo iptables-save -t nat | grep -A2 "^-A KUBE-SEP" | grep DNAT     # 실제 Pod IP:포트
sudo conntrack -L -d "$CIP" 2>/dev/null | head                      # 변환된 연결 기록 (conntrack 패키지 필요)
curl -s localhost:10249/proxyMode; echo                            # 현재 모드
curl -s localhost:10249/metrics | grep -E 'kubeproxy_sync_proxy_rules_(duration_seconds_(sum|count)|iptables_total)'

    

      
비용과 한계

      
    
        
  • 선형 탐색. KUBE-SERVICES는 Service 수만큼, KUBE-SVC는 엔드포인트 수만큼 규칙이 길어집니다. Service 수천 개, 엔드포인트 수만 개 규모에서는 첫 패킷 지연과 CPU가 늘어납니다.
    • 
        
  • 규칙 갱신 비용. 예전에는 매번 전체 테이블을 다시 썼고, 최근 버전은 바뀐 부분만 쓰도록 최적화됐지만 그래도 대형 클러스터에서 동기화 시간(kubeproxy_sync_proxy_rules_duration_seconds)이 수 초까지 늘어납니다. 그동안 새 엔드포인트로 트래픽이 가지 않습니다.
    • 
        
  • conntrack 의존. 첫 패킷만 규칙을 타고, 이후 패킷은 conntrack 기록으로 처리됩니다. conntrack 표가 가득 차면 새 연결이 조용히 버려집니다(12장).
    • 
        
  • 엔드포인트가 없을 때. 해당 ClusterIP로 오는 연결을 REJECT해 즉시 “연결 거부”를 돌려줍니다. 타임아웃이 아니라 거부가 보이면 엔드포인트 없음부터 의심하세요.
    •

IPVS 모드와 그 퇴장

    
쉬운 말로
    IPVS는 리눅스 커널에 원래 들어 있던 전용 부하 분산기입니다. 이정표를 줄줄이 읽는 대신 해시 표에서 바로 찾기 때문에 대형 클러스터에서 iptables보다 빨랐습니다. 하지만 관리할 사람이 줄었고, 같은 장점을 가진 nftables 모드가 생기면서 퇴장 절차에 들어갔습니다.

    

      
    
        
  • 동작. 모든 ClusterIP를 노드의 더미 인터페이스 kube-ipvs0에 붙이고, IPVS 가상 서버 → 실제 서버(Pod) 표를 만듭니다. ipvsadm -Ln으로 보입니다. 라운드 로빈 외에 최소 연결 등 여러 분산 알고리즘을 고를 수 있었던 것이 고유 장점입니다. 다만 SNAT·필터링 같은 일부는 여전히 iptables(ipset)에 기대므로 두 기술을 함께 디버깅해야 했습니다.
    • 
        
  • 폐기 일정. 1.35에서 공식 폐기되어 IPVS 모드로 시작하면 경고 로그가 찍힙니다. 업스트림 계획은 이 모드를 켜는 기능 게이트를 1.40에서 기본 꺼짐, 1.43에서 완전 잠금으로 바꿔 사실상 제거하는 것입니다. 별도 저장소로 옮겨 유지하는 안은 접었습니다.
    • 
        
  • 이전 대상. 업스트림 권장은 nftables 모드입니다. Calico를 함께 쓴다면 Calico 데이터플레인도 nftables로 맞추거나, 아예 eBPF 데이터플레인으로 kube-proxy를 없애는 선택지가 있습니다.
    • 
      

    

    
현장 메모: 인벤토리에 “kube-proxy 모드” 칸을 추가
    성능 때문에 IPVS로 바꿔 둔 온프렘·초기 매니지드 클러스터가 적지 않습니다. 1편의 버전 인벤토리에 kube-proxy 모드를 함께 기록하고, IPVS인 클러스터는 1.40 이전에 이전 계획을 세우세요. 이전은 ConfigMap의 mode 변경과 DaemonSet 재시작으로 끝나지만, 순간적인 연결 재설정이 있으므로 유지보수 창에서 합니다(11장 실습 1과 같은 절차).

nftables 모드: 맵으로 한 번에 찾기

    
쉬운 말로
    nftables 모드는 이정표를 한 줄씩 읽는 대신 “번호 → 갈 곳” 사전(맵)을 펼쳐 한 번에 찾습니다. Service가 수천 개여도 찾는 시간이 거의 같고, 바뀐 항목만 고쳐 쓸 수 있습니다.

    

      
    
        
  • 상태. 1.33에서 GA. 1.37에서 기본값을 iptables에서 nftables로 바꾸는 작업이 Alpha로 시작됐지만, 1.37의 기본값은 아직 iptables입니다. 커널 5.13 이상이 필요합니다(3편 기준선의 Ubuntu 24.04는 충족).
    • 
        
  • 구조. kube-proxy가 자기 전용 테이블(ip kube-proxy, IPv6는 ip6 kube-proxy)을 소유하고, service-ips·service-nodeports 같은 판정 맵(verdict map)에서 목적지로 바로 Service 체인을 찾습니다. 엔드포인트 선택은 numgen random mod N으로 한 번에 합니다. 다른 도구의 규칙과 섞이지 않는 독립 테이블이라는 점도 iptables 모드와의 큰 차이입니다.
    • 
      

    

    

      
iptables 모드와 다른 동작영향

      
        
localhost NodePort 미지원노드에서 curl 127.0.0.1:<NodePort>로 확인하던 헬스 체크·스크립트가 실패합니다. 노드 IP로 바꿔야 합니다.

        
NodePort를 받는 주소의 기본값노드의 모든 IP가 아니라 기본 주소에서만 NodePort를 받는 쪽으로 기본값이 바뀌었습니다. 보조 IP로 NodePort를 쓰던 구성은 nodePortAddresses 설정이 필요합니다.

        
다른 방화벽 도구와의 관계iptables로 직접 넣은 규칙과 kube-proxy 규칙의 상대 순서에 기대던 운영 스크립트는 다시 검증해야 합니다. 테이블이 분리되어 우선순위가 hook priority로 정해집니다.

        
진단 명령iptables-save 대신 nft list table ip kube-proxy, nft list map ip kube-proxy service-ips

      
    

    
nftables 모드 덤프 읽기

Cilium·eBPF 대체: 교환원을 없애다

    
쉬운 말로
    Cilium의 kube-proxy 대체(KPR)는 애플리케이션이 대표 번호로 전화를 거는 순간, 전화기 안에서 바로 직원 번호로 바꿔 거는 방식입니다(소켓 수준 변환). 교환대를 거치지 않으니 빠르고, 직원 쪽에서는 손님 번호가 그대로 보입니다.

    

      
세 가지 경로

    

    

      
경로어디서 변환하나효과

      
        
소켓 로드밸런싱Pod 안 프로세스가 connect()할 때 cgroup eBPF 훅에서 ClusterIP를 Pod IP로 바꿈패킷 단위 DNAT·conntrack이 필요 없음. 클러스터 내부 트래픽의 대부분

        
tc(트래픽 제어) 훅노드 인터페이스에 붙은 eBPF가 NodePort·LB·외부 트래픽 처리NodePort·LoadBalancer, hostPort

        
XDP 가속(선택)NIC 드라이버 직후에서 처리가장 빠른 NodePort·LB 처리. 지원 NIC 필요

      
    

    

      
추가 기능

      
    
        
  • DSR. 외부 요청을 다른 노드의 Pod로 보낼 때, 응답은 그 Pod의 노드가 클라이언트에게 직접 돌려줍니다. 원래 출발지 IP가 보존되고 왕복 경로가 짧아집니다. 네이티브 라우팅이 필요하고 일부 클라우드 환경에서는 제약이 있습니다.
    • 
        
  • Maglev 해싱. 백엔드가 바뀌어도 기존 연결이 같은 Pod로 가도록 일관 해싱을 씁니다. 노드가 여러 대인 LB 앞단에서 유용합니다.
    • 
        
  • Service가 없는 엔드포인트. 백엔드가 없으면 연결 시점에 바로 오류를 돌려줘 타임아웃 대기를 줄입니다.
    • 
      

      
벤더 안의 KPR

      
    
        
  • GKE Dataplane V2: kube-proxy가 아예 없고 노드의 anetd(Cilium 기반 에이전트)가 Service를 처리합니다. GKE 문서는 kube-proxy가 업스트림에서 먼저 구현하는 Service 신기능이 Dataplane V2에는 늦게 들어올 수 있다고 명시합니다. 1.37 기능을 쓰려 할 때 확인할 지점입니다.
    • 
        
  • AKS Cilium 데이터플레인: 마찬가지로 kube-proxy가 없고, 사용자가 KPR 세부 설정(DSR, XDP 등)을 바꿀 수 없습니다.
    • 
        
  • 자체 설치 Cilium: 위 기능을 모두 고를 수 있는 대신 커널 요구사항과 업그레이드를 직접 책임집니다.
    •

OVN-Kubernetes의 Service (OpenShift)

    
쉬운 말로
    OVN-K는 가상 사내 전화망의 각 층 교환기(논리 스위치)와 건물 출입구(게이트웨이 라우터)에 “이 대표 번호는 이 직원들에게”라는 연결 규칙(OVN 로드밸런서)을 심어 둡니다. kube-proxy는 없습니다.

    

      
    
        
  • 구현. Service마다 OVN 로드밸런서 객체가 생기고, 클러스터 내부용은 노드별 논리 스위치에, NodePort·외부용은 노드의 게이트웨이 라우터에 붙습니다. 변환은 결국 각 노드 OVS의 흐름 규칙과 conntrack으로 실행됩니다.
    • 
        
  • 이름 규칙. 로드밸런서 이름이 Service_<네임스페이스>/<이름>_TCP_cluster, ..._node_router_<노드> 같은 형식이라, 문제의 Service를 찾기 쉽습니다.
    • 
        
  • 헤어핀. Pod가 자기 자신이 뒤에 있는 Service를 호출하면(헤어핀), 응답이 돌아올 수 있도록 특별한 SNAT 주소를 씁니다. 패킷 캡처에서 낯선 출발지가 보이면 이것일 수 있습니다.
    • 
        
  • 진단 도구. ovn-nbctl lb-list(설계도 쪽), ovn-trace·ovnkube-trace(가상 경로 추적), ovs-appctl dpctl/dump-conntrack(실제 연결). OVN 인터커넥트 구조에서는 노드마다 데이터베이스가 있으므로, 문제가 난 노드의 ovnkube-node Pod에서 조회해야 합니다.
    •

트래픽 정책과 지역성

    
쉬운 말로
    Service에는 “어느 직원에게 연결할지” 고르는 규칙이 네 가지 있습니다. 외부 손님은 들어온 건물 직원에게만 연결할지(externalTrafficPolicy), 내부 직원끼리는 같은 층 직원에게만 연결할지(internalTrafficPolicy), 가까운 직원을 우선할지(trafficDistribution), 한 번 연결된 손님은 같은 직원에게 계속 연결할지(sessionAffinity)입니다.

    

      
설정값효과대가

      
        
externalTrafficPolicyCluster(기본) / LocalLocal: 외부 트래픽을 들어온 노드의 Pod에만 보내고 원래 출발지 IP 보존. 엔드포인트가 없는 노드는 LB 헬스 체크(healthCheckNodePort)에 실패해 LB가 빼 줌Pod가 고르게 퍼져 있지 않으면 부하 쏠림. LB가 헬스 체크를 지원하지 않으면 트래픽 유실

        
internalTrafficPolicyCluster(기본) / LocalLocal: 클러스터 내부 트래픽을 같은 노드의 엔드포인트로만. 노드 로컬 캐시·에이전트(DaemonSet)에 적합같은 노드에 엔드포인트가 없으면 그냥 실패(대체 없음)

        
trafficDistributionPreferSameZone / PreferSameNode (PreferClose는 PreferSameZone의 폐기된 별칭)가까운 엔드포인트를 우선하고, 없으면 다른 곳으로 대체. 존 간 데이터 전송 비용·지연 감소존별 Pod 수가 불균형하면 일부 Pod에 부하 쏠림

        
세션 어피니티None / ClientIP (기본 유지 3시간)같은 클라이언트 IP는 같은 Pod로SNAT 뒤에서는 모든 요청이 같은 IP로 보여 한 Pod에 몰림. NAT 게이트웨이·Cluster 정책과 함께 쓰면 의미가 없어지기 쉬움

        
토폴로지 인식 라우팅(어노테이션)service.kubernetes.io/topology-mode: Auto존별 CPU 용량에 비례해 힌트를 배분. 안전 조건이 맞지 않으면 힌트를 붙이지 않음동작 조건이 복잡해 기대와 다를 수 있음. 신규 설정은 trafficDistribution 권장

      
    

    

      
trafficDistribution은 1.33에서 GA가 됐고, 의미가 모호했던 PreferClose를 대체하는 PreferSameZone과 새 값 PreferSameNode가 1.35에서 GA가 됐습니다. 힌트는 EndpointSlice에 기록되며, 존 정보는 노드의 topology.kubernetes.io/zone 레이블에서 옵니다. 매니지드에서는 CCM이 채우지만, kubeadm 기준선에서는 직접 붙여야 동작합니다(11장 실습 4).

      
시뮬레이터: 어떤 Pod가 후보가 되나

      
존 두 개, 노드 세 대인 클러스터입니다. 요청이 어디서 시작하는지와 정책을 바꿔 보면, 후보가 되는 Pod가 초록색으로 표시되고 출발지 IP 보존 여부와 주의점이 나옵니다.

    

    

      
요청 출발

함정: Local 정책과 롤링 업데이트
    externalTrafficPolicy: Local인 Service에서 노드의 마지막 Pod가 종료되는 순간, LB 헬스 체크가 그 노드를 빼기 전까지 들어온 요청은 갈 곳이 없습니다. 2장에서 본 종료 중 엔드포인트 처리(serving·terminating)가 이 틈을 줄여 주지만, LB 헬스 체크 주기·임계값과 Pod의 종료 유예 시간(preStop 지연)을 함께 맞춰야 완전히 막을 수 있습니다. 7편에서 LB 쪽 설정과 함께 다룹니다.

현장 사례

    
DNS 조회가 가끔 5초씩 걸린다

      
증상. 대부분 빠른데 간헐적으로 정확히 5초 지연이 생깁니다.

      
원인. glibc 리졸버가 A·AAAA 질의를 같은 UDP 소켓으로 동시에 보내는데, 두 패킷이 conntrack에 동시에 등록되려다 하나가 버려지는 경쟁 조건이 iptables 기반 Service(CoreDNS ClusterIP)에서 알려져 있습니다. 버려진 질의는 리졸버 타임아웃(5초) 뒤 재시도됩니다.

      
대응. NodeLocal DNSCache로 노드 로컬 캐시를 두거나(10편), Pod dnsConfig에 single-request-reopen 옵션을 주거나, conntrack을 거치지 않는 eBPF 소켓 로드밸런싱으로 옮깁니다.

      
교훈. “정확히 5초”는 DNS 타임아웃의 지문입니다. Service 구현과 conntrack을 함께 의심하세요.

    

    
트래픽 피크 때 새 연결만 조용히 실패한다

      
원인. 노드의 conntrack 표가 가득 찼습니다. 커널 로그에 nf_conntrack: table full, dropping packet이 남아 있었습니다. 짧은 연결을 대량으로 맺는 배치 작업이 같은 노드에 몰려 있었습니다.

      
대응. kube-proxy의 conntrack 설정(conntrack.maxPerCore)과 노드 sysctl을 조정하고, 해당 워크로드에 연결 재사용(keep-alive)을 적용했습니다. conntrack 사용률을 노드 지표 경보에 추가했습니다.

      
교훈. iptables·nftables·OVN 모두 conntrack에 기대고, eBPF 구현도 자체 연결 표를 가집니다. 연결 표 사용률은 어떤 구현에서든 감시 대상입니다.

    

    
방화벽 허용 목록이 갑자기 안 맞는다 (출발지 IP)

      
상황. 외부 파트너 시스템이 고객 앱으로 호출할 때 출발지 IP로 허용 목록을 관리하는데, 앱 로그에는 노드 IP만 찍혔습니다.

      
원인. LoadBalancer Service가 externalTrafficPolicy: Cluster(기본)라 노드에서 SNAT되었습니다.

      
대응. Local로 바꾸고, Pod를 노드에 고르게 퍼뜨리는 토폴로지 분산을 넣고, LB 헬스 체크 설정을 확인했습니다. LB 종류에 따라서는 프록시 프로토콜이나 X-Forwarded-For가 대안입니다(7편).

      
교훈. 출발지 IP 보존은 Service 정책·LB 종류·CNI 구현의 조합으로 결정됩니다. 8장 시뮬레이터로 먼저 확인하세요.

    

    
nftables로 바꿨더니 노드 헬스 체크 스크립트가 실패한다

      
원인. 노드에서 curl 127.0.0.1:<NodePort>로 앱을 확인하던 모니터링 스크립트가 있었습니다. nftables 모드는 localhost NodePort를 지원하지 않습니다.

      
대응. 노드 IP로 호출하도록 스크립트를 바꿨습니다.

      
교훈. 모드 전환은 kube-proxy만의 일이 아닙니다. 노드에서 NodePort·ClusterIP를 직접 부르는 주변 스크립트와 방화벽 규칙을 먼저 목록화하세요.

    

    
internalTrafficPolicy: Local로 바꾼 뒤 일부 Pod만 로그 전송 실패

      
상황. 노드마다 도는 로그 수집기(DaemonSet) 앞의 Service에 Local을 걸어 노드 간 트래픽을 줄였습니다. 그런데 새로 추가한 노드 풀의 Pod만 로그 전송이 실패했습니다.

      
원인. 새 노드 풀에 테인트가 있어 수집기 DaemonSet이 그 노드에 뜨지 않았습니다. Local 정책은 대체 경로 없이 실패합니다.

      
교훈. internalTrafficPolicy: Local은 “모든 노드에 엔드포인트가 반드시 있다”는 가정 위에서만 안전합니다. 대체가 필요하면 trafficDistribution: PreferSameNode가 맞는 선택입니다.

    

    
대형 클러스터에서 배포 직후 몇 초간 503

      
원인. Service 수천 개짜리 iptables 모드 클러스터에서 kube-proxy 규칙 동기화가 수 초씩 걸려, 새 Pod가 Ready가 된 뒤에도 일부 노드는 옛 엔드포인트로 보내고 있었습니다.

      
대응. nftables 모드로 전환해 동기화 시간을 줄이고, 앱에 preStop 지연을 넣어 종료되는 Pod가 규칙에서 빠질 시간을 벌었습니다.

      
교훈. kubeproxy_sync_proxy_rules_duration_seconds는 대형 클러스터의 배포 안정성 지표입니다. 2편의 컨트롤 플레인 지표와 함께 대시보드에 두세요.

AWS Load Balancer Controller(NLB·ALB, 인스턴스 대상 vs IP 대상), Azure LB·Application Gateway for Containers, GKE L4·L7과 NEG, 온프렘의 MetalLB·kube-vip·Cilium LB IPAM을 비교하고, ingress-nginx 은퇴 이후의 Ingress 컨트롤러 지형을 정리합니다. 출발지 IP 보존, 헬스 체크, ipMode, 비용 차이를 같은 앱으로 측정합니다.
