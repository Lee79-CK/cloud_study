클러스터 생명주기 운영 비교

Kubernetes는 약 4개월마다 새 버전이 나오고, 각 버전은 1년 남짓만 지원됩니다. 즉 MSP가 맡은 모든 클러스터는 1년에 서너 번 업그레이드해야 하는 시스템입니다. 업그레이드는 컨트롤 플레인과 노드, 노드 OS, 그 위의 애드온과 워크로드가 함께 움직이는 일이고, 그 과정에서 노드가 비워지고(드레인) Pod가 옮겨 갑니다. 이 편은 kubeadm·RKE2·OpenShift·EKS·AKS·GKE의 업그레이드 방식, 불변 노드 OS, 노드 교체 전략과 PDB, 오토스케일러 세 종류, v1.37의 Node Lifecycle Conditions를 비교하고, PDB를 건 워크로드로 세 클라우드에서 노드 풀 업그레이드를 해 중단 시간을 잽니다.

기준: Kubernetes v1.37 · 2026-10 벤더 문서 작성 기준일: 2026-10-24 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

읽는 법과 목표

쉬운 말로 클러스터 업그레이드는 손님이 묵고 있는 호텔을 영업을 멈추지 않고 리모델링하는 일입니다. 먼저 프런트(컨트롤 플레인)를 고치고, 그다음 객실(노드)을 한 층씩 비워 고칩니다. 객실을 비울 때는 손님(Pod)을 다른 층으로 옮겨야 하는데, “같은 단체 손님은 최소 몇 명은 늘 묵고 있어야 한다”는 약속(PDB)을 지켜야 합니다. 객실 자체를 새 건물로 통째로 바꾸는 방식(불변 OS·노드 교체)이 요즘의 표준이고, 손님 수에 맞춰 객실을 늘리고 줄이는 일은 오토스케일러가 합니다.

Level 4는 세 편입니다: 23편 생명주기, 24편 관측·멀티클러스터·GitOps, 25편 종합(벤더 선택 매트릭스와 MSP 운영 플레이북).

이 편을 마치면 할 수 있는 것

  • 버전 차이 허용 범위(skew)와 업그레이드 순서를 지켜 여러 마이너 버전을 건너는 계획을 세울 수 있습니다.
  • 여섯 플랫폼의 업그레이드 방식·채널·유지보수 창을 비교하고 고객별 정책을 정할 수 있습니다.
  • Bottlerocket·Azure Linux·COS·RHCOS·SLE Micro·Talos의 운영 차이를 설명할 수 있습니다.
  • 서지·블루그린 교체와 PDB의 상호작용을 이해하고, 드레인이 막히는 조건과 벤더별 동작을 예측할 수 있습니다.
  • Cluster Autoscaler·Karpenter·Node Auto-Provisioning을 비교하고, 업그레이드·통합(consolidation)이 워크로드에 주는 영향을 관리할 수 있습니다.

노드 OS: 불변 OS 비교

쉬운 말로 예전 노드는 집에 가구를 하나씩 들여놓고 고치는 방식(패키지 설치·패치)이었습니다. 불변 OS는 가구가 붙박이인 조립식 집입니다. 바꾸고 싶으면 새 조립식 집으로 통째로 교체하고, 문제가 생기면 이전 집으로 바로 되돌립니다. 집 안에서 몰래 무언가를 바꾸기 어려워 보안에 유리하지만, 대신 “집 안에서 직접 손보기”(SSH 디버깅, 커널 모듈 설치)가 어렵습니다.

BottlerocketEKS(Auto Mode 기반 포함)A/B 파티션 이미지 교체, 자동 롤백관리 컨테이너·API 기반, 기본 셸 없음설정은 API·사용자 데이터(TOML). dm-verity로 무결성 검증

드레인·PDB·노드 교체 전략

  • 드레인은 노드를 스케줄 불가(cordon)로 만든 뒤 Pod를 축출(Eviction) API로 하나씩 내보냅니다. 축출은 PDB를 확인하므로, 허용된 중단 수가 0이면 거부되고 드레인은 기다립니다.
  • PDB는 minAvailable 또는 maxUnavailable로 “동시에 자발적으로 내려갈 수 있는 수”를 정합니다. Ready가 아닌 Pod의 처리 방식은 unhealthyPodEvictionPolicy(AlwaysAllow 권장)로 정합니다.
  • 막히는 전형. 레플리카 1개에 minAvailable 1, 또는 레플리카 3개에 minAvailable 3. 허용 중단이 늘 0이라 노드를 영원히 비울 수 없습니다.
  • 서지 vs 블루그린. 서지는 새 노드를 몇 개 먼저 만들고 옛 노드를 차례로 비웁니다(비용 적음, 시간 김). 블루그린은 새 풀을 통째로 만들고 옮긴 뒤 일정 시간 지켜보고(소크) 옛 풀을 지웁니다(되돌리기 쉬움, 일시적 비용 두 배).
플랫폼PDB 때문에 드레인이 막히면
kubeadm·RKE2kubectl drain이 계속 재시도(타임아웃 옵션 지정 가능). RKE2 Plan은 드레인 옵션 설정
EKS 관리형 노드 그룹일정 시간(약 15분) 안에 못 비우면 업데이트 실패. 강제 옵션을 쓰면 PDB를 무시하고 진행
AKS드레인 타임아웃(기본 30분, 설정 가능) 후 실패, 실패 노드 처리 방식(cordon 유지 등) 설정 가능
GKEPDB를 최대 약 1시간 존중한 뒤 강제로 축출하고 진행
OpenShift(MCO)드레인을 계속 재시도하며 경보(드레인 오류). 풀 업데이트가 멈춤
Karpenter·Auto ModePDB와 karpenter.sh/do-not-disrupt 어노테이션을 존중. 노드 교체가 지연

PDB와 노드 교체 시뮬레이터

레플리카가 노드에 고르게 퍼져 있다고 보고, 노드를 차례로 비울 때 최소 가용 Pod 수와 드레인 시간을 계산합니다. 허용 중단이 0이면 막히고, 플랫폼별로 그다음에 무슨 일이 일어나는지 보여 줍니다.

5

v1.37 Node Lifecycle Conditions

노드가 “지금 드레인 중인가, 정비 예정인가, 우아한 종료 중인가”를 알려 주는 공통 신호가 그동안 없었습니다. 테인트·레이블·어노테이션·클라우드 고유 API가 제각각 일부를 표현했고, 스토리지 오퍼레이터(14편 Rook 등)는 드레인을 스스로 추측해야 했습니다. v1.37은 Kubernetes가 소유하는 노드 생명주기 조건을 알파로 도입했습니다(KEP-5683, 기능 게이트 NodeLifecycleConditions, 기본 꺼짐).

조건의미
MaintenancePlanned노드에 변경이 예정됨. 워크로드에 영향이 있으면 정비 전에 드레인
MaintenanceInProgress하드웨어·소프트웨어 반영, 복구, 퇴역, 디버깅 등 정비 진행 중
Drained(+ 드레인 진행 중 조건)관리자가 정한 드레인 기준을 만족함(Drained), 그리고 드레인이 진행 중임을 나타내는 조건. 정확한 이름은 공식 문서의 조건 표 참고
GracefulNodeShutdownInProgress우아한 노드 종료가 진행 중(DaemonSet 컨트롤러와의 충돌 같은 문제를 풀기 위한 신호)
  • 1.37에서는 신호만. 관리자나 권한을 받은 정비 컨트롤러가 조건을 쓰고 지웁니다. 핵심 컨트롤러는 아직 이 값을 읽고 동작을 바꾸지 않으며, 기존 cordon·drain·테인트는 그대로 써야 합니다.
  • 왜 중요한가. 정비 도구, 오토스케일러, 스토리지 오퍼레이터, 배치 스케줄러가 같은 신호를 보고 서로 맞는 결정을 내릴 기반입니다. 이후 릴리스에서 드레인·우아한 종료·정비 흐름을 개선하는 데 쓰일 예정입니다.
  • MSP 관점. 고객의 정비 자동화(노드 교체 스크립트)를 만들고 있다면, 지금부터 이 조건을 “쓰는 쪽”으로 맞춰 두면 생태계가 따라올 때 연동이 쉬워집니다.

실습: PDB를 건 워크로드로 세 벤더 노드 풀 업그레이드

같은 워크로드(6 레플리카, PDB maxUnavailable 1, readiness·preStop 설정)를 lab-eks·lab-aks·lab-gke에 배포하고, 호스트에서 LoadBalancer 주소로 0.2초마다 요청을 보내며 노드 풀을 교체합니다. 벤더가 제공하는 노드 풀 업그레이드가 가능하면 그것을, 새 버전이 없으면 “새 노드 풀 추가 + 옛 노드 드레인”(수동 블루그린)으로 같은 상황을 만듭니다. 실패 요청 수와 가장 긴 중단 구간을 비교합니다. LoadBalancer는 과금되므로 실습 후 바로 지웁니다.

실습 0. 워크로드와 측정 도구

upg-app.yaml — 세 클러스터 공통
apiVersion: v1
kind: Namespace
metadata: {name: upg-lab}
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: web, namespace: upg-lab}
spec:
  replicas: 6
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      terminationGracePeriodSeconds: 30
      topologySpreadConstraints:
      - {maxSkew: 1, topologyKey: kubernetes.io/hostname, whenUnsatisfiable: ScheduleAnyway, labelSelector: {matchLabels: {app: web}}}
      containers:
      - name: web
        image: registry.k8s.io/e2e-test-images/agnhost:2.52
        args: ["netexec", "--http-port=8080"]
        ports: [{containerPort: 8080}]
        readinessProbe: {httpGet: {path: /hostname, port: 8080}, periodSeconds: 2, failureThreshold: 1}
        lifecycle: {preStop: {sleep: {seconds: 10}}}      # 엔드포인트에서 빠질 시간(6·7편)
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: web, namespace: upg-lab}

  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector: {matchLabels: {app: web}}

  type: LoadBalancer

측정: 호스트에서 요청 보내기와 분석
deploy(){ kubectl --context $1 apply -f upg-app.yaml; kubectl --context $1 -n upg-lab rollout status deploy/web
  until LB=$(kubectl --context $1 -n upg-lab get svc web -o jsonpath='{.status.loadBalancer.ingress[0].hostname}{.status.loadBalancer.ingress[0].ip}') && [ -n "$LB" ]; do sleep 5; done; echo "$LB"; }
probe(){ # probe 컨텍스트 LB → 백그라운드로 기록
  while true; do c=$(curl -s -o /dev/null -m 2 -w '%{http_code}' http://$2/hostname); echo "$(date +%s.%N | cut -c1-14) $c"; sleep 0.2; done > probe-$1.log & echo $! > probe-$1.pid; }
stopprobe(){ kill $(cat probe-$1.pid); }
an(){ awk 'BEGIN{prev=0;gap=0;mx=0}{n++; if($2!="200"){f++; if(!gap)gs=$1; gap=1} else if(gap){d=$1-gs; if(d>mx)mx=d; gap=0}} END{printf "요청 %d, 실패 %d (%.2f%%), 가장 긴 중단 %.1f초\n", n,f,100*f/n,mx}' probe-$1.log; }
nodes(){ kubectl --context $1 get nodes -w -o custom-columns=T:.metadata.creationTimestamp,NAME:.metadata.name,VER:.status.nodeInfo.kubeletVersion,READY:.status.conditions[-1].status > nodes-$1.log & }

# 공통 대안: 수동 블루그린 — 새 풀이 준비된 뒤 옛 노드를 하나씩 비움(PDB 존중)
bluegreen_drain(){ for n in $(kubectl --context $1 get nodes -l "$2" -o name); do
  kubectl --context $1 cordon $n; kubectl --context $1 drain $n --ignore-daemonsets --delete-emptydir-data --timeout=600s; done; }

현장 사례

PDB 하나 때문에 노드 업그레이드가 며칠째 멈췄다

원인. 레플리카 3개 Deployment에 minAvailable 3을 걸어 허용 중단이 항상 0이었습니다. AKS 노드 풀 업그레이드가 드레인 타임아웃으로 실패를 반복했습니다.

교훈. 업그레이드 전 “허용 중단 0” PDB 목록을 뽑아 고치세요(7장 명령). 정책(21편)으로 minAvailable = replicas를 막을 수도 있습니다.

업그레이드 직후 Helm 릴리스가 갱신되지 않았다

원인. 제거된 API 버전을 쓰는 매니페스트가 릴리스 기록에 남아 있어, 새 버전 클러스터에서 Helm이 기존 릴리스를 해석하지 못했습니다.

교훈. 업그레이드 전 pluto·kubent로 클러스터와 Helm 릴리스를 모두 검사하고, 필요하면 릴리스의 API 버전을 먼저 바꾸세요.

GKE 자동 업그레이드가 업무 시간에 노드를 교체했다

원인. 릴리스 채널 클러스터에 유지보수 창을 정하지 않아, 업무 시간에 노드 풀 업그레이드가 진행되었습니다.

교훈. 유지보수 창과 제외 기간(행사·결산 기간)을 고객 일정에 맞춰 설정하세요. AKS의 계획된 유지보수, EKS Auto Mode의 중단 예산도 같은 역할입니다.

EKS 연장 지원 비용이 청구서에서 발견됐다

원인. 업그레이드를 미루다 표준 지원이 끝나 연장 지원 요금이 자동으로 붙었습니다.

교훈. 고객별 클러스터 버전과 지원 종료일을 인벤토리(1편)에 두고, 분기마다 업그레이드 계획을 세우세요.

OpenShift 워커 풀이 몇 달째 일시 정지 상태였다

원인. 장애 대응 중 워커 MachineConfigPool을 일시 정지했다가 해제를 잊었습니다. 인증서·설정 갱신이 쌓이고 다음 업그레이드가 막혔습니다.

교훈. 풀 일시 정지는 기한과 담당자를 함께 기록하고, 정지된 풀을 경보로 두세요.

불변 OS로 바꾸자 보안 에이전트가 동작하지 않았다

원인. 노드에 직접 설치되던 에이전트가 커널 모듈을 빌드해야 했는데, Bottlerocket·COS에서는 불가능했습니다.

교훈. OS 전환 전 에이전트의 지원 OS·eBPF 방식 여부를 확인하세요(3장 현장 메모).

Karpenter 통합 때문에 배치 작업이 계속 재시작됐다

원인. 사용률이 낮아 보이는 노드를 통합이 계속 비우면서, 몇 시간짜리 배치 작업이 중간에 축출되었습니다.

교훈. 긴 작업에는 karpenter.sh/do-not-disrupt, NodePool에는 중단 예산(6장)을 두세요.

kubeadm에서 kubelet을 먼저 올려 노드가 붙지 않았다

원인. 자동 패키지 업데이트가 워커의 kubelet을 컨트롤 플레인보다 높은 버전으로 올려, 버전 차이 정책을 어겼습니다.

교훈. kubelet·kubeadm 패키지는 버전 고정(hold)하고, 순서(컨트롤 플레인 먼저)를 자동화하세요.

단일 레플리카 서비스가 노드 교체마다 끊겼다

원인. 레플리카 1개라 PDB로도 보호할 수 없었고, 노드가 교체될 때마다 몇십 초씩 서비스가 끊겼습니다.

교훈. 업그레이드 중에도 살아 있어야 하는 서비스는 최소 2개 이상 + 노드 분산 + PDB. 상태 있는 단일 인스턴스는 16편의 오퍼레이터 복제를 검토하세요.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. 업그레이드는 마이너 버전 하나씩, 컨트롤 플레인 → 애드온 → 노드 순서이며, kubelet은 최대 세 마이너까지 낮을 수 있어 노드 교체를 묶는 전략이 가능합니다. 폐기 API 점검과 백업이 선행 조건입니다.
  2. kubeadm·RKE2는 제자리, OpenShift는 CVO·MCO의 이미지 교체, EKS·AKS·GKE는 노드 교체(서지·블루그린) 방식이며, 채널·유지보수 창·지원 기간이 플랫폼마다 다릅니다.
  3. Bottlerocket·COS·RHCOS·Talos 같은 불변 OS는 보안·일관성이 좋지만 에이전트·커널 모듈·디버깅 경로를 다시 설계해야 합니다.
  4. 드레인은 PDB를 존중하므로 허용 중단 0인 PDB는 업그레이드를 막고, 막힌 뒤의 동작은 벤더마다 다릅니다(실패·강제 진행·재시도). v1.37 Node Lifecycle Conditions는 이 생명주기를 알리는 공통 신호의 첫걸음입니다.
  5. Cluster Autoscaler는 노드 그룹 단위, Karpenter는 인스턴스 단위·통합·드리프트, NAP는 노드 풀 자동 생성이며, 중단 예산·do-not-disrupt로 업그레이드·통합의 영향을 통제합니다.
