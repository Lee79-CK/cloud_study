Terraform & Ansible 강의 · Level 4 Ansible 심화·운영 · 21편 / 26편 · 시리즈 목차

누가, 언제, 무엇을 실행했는지 남는 곳 AWX / Ansible Automation Platform — 중앙 실행, 프로젝트·인벤토리·자격증명·잡 템플릿·워크플로, RBAC·감사, 스케줄, Event-Driven Ansible로 알림 → 자동 조치

지금까지 플레이북은 엔지니어의 노트북이나 CI 러너에서 실행되었습니다. 고객이 “어제 밤 누가 운영 서버 설정을 바꿨나요?”라고 물으면 답하기 어렵고, 고객 운영팀에게 “이 작업만 직접 실행할 수 있게” 해 줄 방법도 없습니다. AWX와 그 상용판인 Ansible Automation Platform(AAP)은 플레이북 실행을 한곳으로 모아 권한·자격증명·실행 기록을 관리합니다. 이번 편은 그 구성 요소를 코드(awx.awx)로 정의하고, 마지막으로 Event-Driven Ansible로 모니터링 알림을 받아 사람 없이 장애를 조치하는 흐름을 실제로 돌립니다 — nginx를 강제로 죽인 뒤 Alertmanager 형식 알림을 보내면 약 3초 만에 복구되는 것을 확인했습니다.

중앙 실행

잡 템플릿 = 플레이북 + 인벤토리 + 자격증명 + EE. 실행은 버튼·API·스케줄로

통제

조직·팀·역할(RBAC), 자격증명은 보이지 않게, 모든 실행은 기록

이벤트

알림 → 룰북 조건 → 조치 플레이북 → 확인 → 기록 (실측)

이번 편의 목표와 실측 범위

이번 편을 마치면

  • 중앙 실행이 필요한 이유를 CI(12편)와 비교해 설명합니다.
  • AWX와 AAP의 현재 상태(버전·지원·구성 요소)를 알고 고객 환경에 맞게 선택합니다.
  • 조직·프로젝트·인벤토리·자격증명·EE·잡 템플릿·워크플로·스케줄·알림의 관계를 설명하고, awx.awx 컬렉션으로 코드화합니다.
  • 고객별 조직·팀·역할로 RBAC를 설계하고 감사 요구에 답합니다.
  • ansible-rulebook으로 알림 → 조치 흐름을 만들고, 자동 조치의 안전장치를 설계합니다.
항목실측 여부
Event-Driven Ansible: ansible-rulebook 1.3.2 + ansible.eda 2.13.0(alertmanager 소스) → 조치 플레이북 → 복구, throttle실제 실행 (Java 21, drools 엔진, 13편부터의 랩 node1)
AWX 구성 코드 (awx.awx 컬렉션 모듈 13개 태스크)문법·ansible-lint 통과 + 모든 모듈 인자를 모듈 문서와 대조(문제 0건) — AWX 서버가 없어 적용은 못 함
AWX 서버·AAP 설치, UI, RBAC 동작, 스케줄 실행Kubernetes·구독이 필요해 실행하지 못함 → 공식 문서·릴리스 정보 기준

1왜 중앙 실행인가

노트북 → CI → 자동화 컨트롤러

노트북 (13~20편)CI 파이프라인 (12편)AWX / AAP
실행 기록각자 터미널파이프라인 로그 (보관 기간 제한)모든 잡의 출력·이벤트·누가·언제·무엇으로 — 검색 가능
자격증명각자 PC에CI 비밀암호화 저장, 사용자는 값을 보지 못하고 쓰기만
권한서버 접속 권한 = 실행 권한저장소·환경 권한조직·팀·잡 템플릿 단위 역할 (고객 운영팀에게 실행만)
트리거사람Git 이벤트사람(UI·API)·스케줄·워크플로·이벤트(EDA)·CI에서 API 호출
동적 인벤토리각자매 실행인벤토리 소스 동기화·캐시 (18편)
실행 환경로컬 설치러너 이미지EE 지정 (20편)
잘 맞는 일개발·시험코드 변경과 함께 배포운영 작업(정기·요청형·장애 조치), 고객 셀프서비스, 감사가 필요한 변경
CI와 AWX는 경쟁이 아니라 역할 분담

흔한 조합: PR 검사(lint·check)는 CI, 병합 후 실제 적용은 CI가 AWX API로 잡 템플릿을 실행(awx CLI·awx.awx.job_launch), 정기 점검·장애 조치는 AWX 스케줄·EDA. Terraform은 12편 CI가, 서버 구성은 AWX가 담당하고, 23편에서 둘을 하나의 흐름으로 묶습니다.

2AWX와 AAP의 현재

2026년 10월 기준 — 고객에게 제안하기 전에 확인할 것

AWX (오픈소스)Ansible Automation Platform (Red Hat)
최신 버전24.6.1 (2024-07-02), AWX Operator 2.19.1. 이후 대규모 구조 개편(서비스 분리)으로 릴리스가 중단된 상태 — 저장소 README가 이를 명시2.6 (2025-10-01 GA), 이후 정기 패치 릴리스. 2.5와 함께 Full Support가 2026-10-01까지, Maintenance 2단계가 2028-10-01까지
구성 요소컨트롤러(웹 UI·API·작업 엔진). EDA는 별도 프로젝트(eda-server)플랫폼 게이트웨이(통합 UI·인증·RBAC, 2.5+), 자동화 컨트롤러 4.7, 자동화 허브 4.11, EDA 컨트롤러 1.2, Ansible Lightspeed(AI 도우미)

적합랩, 사내 검증, 소규모 내부 자동화고객 운영 환경, 감사·지원 계약이 필요한 곳
버전 조합 주의

AAP 2.6 릴리스 노트의 구성 요소 표에 적힌 ansible-core는 2.16입니다. 이 강의 EE(20편)는 2.21.5이므로, AAP에서 쓰려면 ① Red Hat 지원 EE 위에 필요한 컬렉션만 얹거나 ② 직접 만든 EE를 쓰되 지원 범위 밖임을 고객과 합의해야 합니다. 2.19+의 템플릿 변화(13편 9장)가 있으므로 같은 플레이북을 두 ansible-core 버전에서 모두 시험해 둡니다. 또 2.6부터 컬렉션 공통 환경 변수 접두사가 AAP_로 통일되고, 개별 서비스 API 경로(/api/v2/users 등)는 게이트웨이 경로로 옮겨 가는 중입니다 — 오래된 연동 스크립트를 점검하세요.

AWX 릴리스 재개 여부와 AAP 패치 버전은 바뀔 수 있으므로, 도입 시점에 AWX 저장소의 README·포럼 공지와 AAP 릴리스 노트·수명 주기 페이지를 다시 확인하세요.

3구성 요소 지도

객체를 누르면 역할과, 이 강의의 어느 편과 대응하는지 나옵니다

객체를 선택하세요

AWX의 모든 것은 조직 안에 있고, 실행의 단위는 잡 템플릿입니다. 잡 템플릿 = 프로젝트의 플레이북 + 인벤토리 + 자격증명 + 실행 환경 + 옵션.

조직: custa # 고객 하나 = 조직 하나 (테넌트 경계) ├── 팀: custa-ops, msp-engineers # 사람은 팀으로 권한을 받는다 ├── 프로젝트: custa-ansible ── Git # 플레이북·역할·인벤토리 디렉터리 ├── 인벤토리: custa-prd │ └── 소스: Git의 inventories/custa-prd (aws_ec2 + constructed, 18편) ├── 자격증명: SSH(Machine) · Vault · AWS · Git # 값은 암호화, 사용자는 볼 수 없음 ├── 실행 환경: iac-lab-ee:2026.10.1 # 20편 ├── 잡 템플릿: custa-prd-site, custa-prd-site-check ├── 워크플로: custa-prd-change (점검 → 승인 → 적용) ├── 스케줄: 매일 08:00 점검 └── 알림: 실패 시 메신저·메일

4구성을 코드로 (awx.awx)

콘솔에서 클릭으로 만든 설정은 4편의 “클릭 인프라”와 같은 문제를 갖는다

playbooks/awx_config.yml
---
# 21편: AWX/AAP 구성을 코드로 (awx.awx 컬렉션) — 콘솔 클릭 대신 이 플레이북을 PR로 관리
- name: AWX 구성 (고객 custa)
  hosts: localhost
  connection: local
  gather_facts: false
  module_defaults:
    group/awx.awx.controller:
      controller_host: "{{ lookup('ansible.builtin.env', 'CONTROLLER_HOST') }}"
      controller_oauthtoken: "{{ lookup('ansible.builtin.env', 'CONTROLLER_OAUTH_TOKEN') }}"
  vars:
    org: custa
    ee_image: registry.example.internal/iaclab/iac-lab-ee:2026.10.1
  tasks:
    - name: 조직 (고객 하나 = 조직 하나)
      awx.awx.organization:
        name: "{{ org }}"
        description: 고객 custa (MSP 관리)
        state: present

    - name: 실행 환경 (20편 EE)
      awx.awx.execution_environment:
        name: iac-lab-ee
        image: "{{ ee_image }}"
        pull: missing
        organization: "{{ org }}"

    - name: 프로젝트 (Git 저장소)
      awx.awx.project:
        name: custa-ansible
        organization: "{{ org }}"
        scm_type: git
        scm_url: https://git.example.internal/msp/custa-ansible.git
        scm_branch: main
        scm_update_on_launch: true
        credential: custa-git-readonly
        default_environment: iac-lab-ee

    - name: 자격증명 — 서버 접속 (SSH 키는 AWX가 암호화 보관)
      awx.awx.credential:
        name: custa-svc-ansible-ssh
        organization: "{{ org }}"
        credential_type: Machine
        inputs:
          username: svc-ansible
          ssh_key_data: "{{ lookup('ansible.builtin.file', '~/.ssh/custa_svc_ansible') }}"
          become_method: sudo
      no_log: true

    - name: 자격증명 — Ansible Vault (19편 vault-id)
      awx.awx.credential:
        name: custa-vault-prd
        organization: "{{ org }}"
        credential_type: Vault
        inputs:
          vault_id: prd
          vault_password: "{{ lookup('ansible.builtin.env', 'ANSIBLE_VAULT_PASS_PRD') }}"
      no_log: true

    - name: 자격증명 — AWS (18편 동적 인벤토리용, 읽기 전용 역할)
      awx.awx.credential:
        name: custa-aws-readonly
        organization: "{{ org }}"
        credential_type: Amazon Web Services
        inputs:
          username: "{{ lookup('ansible.builtin.env', 'CUSTA_AWS_ACCESS_KEY_ID') }}"
          password: "{{ lookup('ansible.builtin.env', 'CUSTA_AWS_SECRET_ACCESS_KEY') }}"
      no_log: true

    - name: 인벤토리
      awx.awx.inventory:
        name: custa-prd
        organization: "{{ org }}"

    - name: 인벤토리 소스 — 저장소의 동적 인벤토리 디렉터리 (18편 aws-dev-dyn 구조)
      awx.awx.inventory_source:
        name: custa-prd-from-git
        inventory: custa-prd
        source: scm
        source_project: custa-ansible
        source_path: inventories/custa-prd
        credential: custa-aws-readonly
        update_on_launch: true
        overwrite: true

    - name: 잡 템플릿 — 웹+DB 구성 (17편 플레이북)
      awx.awx.job_template:
        name: custa-prd-site
        organization: "{{ org }}"
        project: custa-ansible
        inventory: custa-prd
        playbook: playbooks/site_webdb.yml
        execution_environment: iac-lab-ee
        credentials:
          - custa-svc-ansible-ssh
          - custa-vault-prd
        diff_mode: true
        forks: 20
        ask_limit_on_launch: true
        survey_enabled: false

    - name: 잡 템플릿 — 점검 모드 (매일 드리프트 확인용)
      awx.awx.job_template:
        name: custa-prd-site-check
        organization: "{{ org }}"
        project: custa-ansible
        inventory: custa-prd
        playbook: playbooks/site_webdb.yml
        execution_environment: iac-lab-ee
        credentials:
          - custa-svc-ansible-ssh
          - custa-vault-prd
        job_type: check
        diff_mode: true

    - name: 매일 아침 점검 스케줄 (KST 08:00 = UTC 23:00)
      awx.awx.schedule:
        name: custa-prd-daily-check
        unified_job_template: custa-prd-site-check
        rrule: "DTSTART:20261101T230000Z RRULE:FREQ=DAILY;INTERVAL=1"
        state: present

    - name: 워크플로 — 점검 → (승인) → 적용 → 결과 알림
      awx.awx.workflow_job_template:
        name: custa-prd-change
        organization: "{{ org }}"
        inventory: custa-prd
        workflow_nodes:
          - identifier: check
            unified_job_template:
              name: custa-prd-site-check
              type: job_template
            related:
              success_nodes:
                - identifier: approve
          - identifier: approve
            unified_job_template:
              name: 고객 승인 대기
              type: workflow_approval
              timeout: 86400
            related:
              success_nodes:
                - identifier: apply
          - identifier: apply
            unified_job_template:
              name: custa-prd-site
              type: job_template

    - name: 권한 — 고객 운영팀은 실행만, MSP 엔지니어는 관리
      awx.awx.role:
        team: "{{ item.team }}"
        role: "{{ item.role }}"
        job_templates: [custa-prd-site, custa-prd-site-check]
        state: present
      loop:
        - { team: custa-ops, role: execute }
        - { team: msp-engineers, role: admin }
      loop_control:
        label: "{{ item.team }} → {{ item.role }}"
# 검증 (AWX 서버 없이 할 수 있는 것)
$ ansible-playbook playbooks/awx_config.yml --syntax-check       → playbook: playbooks/awx_config.yml
$ ansible-lint playbooks/awx_config.yml                          → Passed … profile 'production'

# 실측: ansible-lint는 awx.awx 모듈의 잘못된 인자를 잡지 못했다 (일부러 wrong_option을 넣어도 통과)
#   → 모듈 문서(ansible-doc -j)와 태스크 인자를 직접 대조하는 스크립트로 확인

awx.awx.execution_environment   사용  4개 인자 모두 유효
awx.awx.project                 사용  8개 인자 모두 유효
awx.awx.credential (×3)         사용  4개 인자 모두 유효
awx.awx.inventory_source        사용  8개 인자 모두 유효
awx.awx.job_template (×2)       사용 11개 / 9개 인자 모두 유효
awx.awx.schedule · workflow_job_template · role   모두 유효
문제 인자 수: 0
# role 모듈의 role 선택지: admin, read, member, execute, adhoc, update, use, approval, auditor, …
# job_template 모듈의 job_type 선택지: run, check
원칙이유
AWX 설정 저장소를 따로 두고 PR로 변경누가 어떤 권한·스케줄을 바꿨는지 Git에 남는다(AWX 활동 기록과 이중으로)
module_defaults의 group/awx.awx.controller모든 모듈에 접속 정보를 한 번에. 토큰은 환경 변수(CI 비밀)로
자격증명 태스크는 모두 no_log19편 4장 — 비밀이 AWX에 넣는 순간 출력으로 새지 않게
이름으로 참조ID 대신 이름(credential: custa-vault-prd) → 다른 AWX(검증·운영)에도 같은 코드 적용
대규모·전체 내보내기awx export(awxkit CLI, 24.6.1)로 현재 설정을 뽑아 코드화의 출발점으로. Red Hat은 infra.aap_configuration 같은 구성 코드화 컬렉션도 제공

5잡 템플릿과 워크플로

실행 단위를 설계한다

# 21편: 모니터링 알림 → 자동 조치 (Event-Driven Ansible)
- name: 웹 서버 장애 알림 자동 조치
  hosts: web
  sources:
    # Prometheus Alertmanager 웹훅을 받는 소스 플러그인
    - ansible.eda.alertmanager:
        host: 0.0.0.0
        port: 5050
        data_alerts_path: alerts           # 알림 묶음에서 개별 알림 목록 위치
        data_host_path: labels.instance    # 이 값이 인벤토리 호스트 이름 → 조치 대상
        data_path_separator: .
  rules:
    - name: Nginx 다운 → 재시작 시도
      condition: event.alert.labels.alertname == "NginxDown" and event.alert.status == "firing"
      # 같은 서버에 대한 같은 알림은 5분에 한 번만 조치 (알림 폭주·조치 반복 방지)
      throttle:
        once_within: 5 minutes
        group_by_attributes:
          - event.alert.labels.instance
      action:
        run_playbook:
          name: playbooks/remediate_nginx.yml
          extra_vars:
            alert_name: NginxDown

    - name: 해결 알림은 기록만
      condition: event.alert.status == "resolved"
      action:
        debug:
          msg: "해결 알림 수신: {{ event.alert.labels.alertname }} @ {{ event.alert.labels.instance }}"

    - name: 알 수 없는 알림은 사람에게
      condition: event.alert.labels.alertname is defined and event.alert.labels.alertname != "NginxDown" and event.alert.status == "firing"
      action:
        print_event:
          pretty: true
playbooks/remediate_nginx.yml
---
# 21편: 알림으로 실행되는 조치 플레이북 — 진단 → 조치 → 확인 → 기록
- name: Nginx 자동 조치
  hosts: all              # 룰북이 알림의 instance 로 대상을 한정한다
  become: true
  gather_facts: false
  vars:
    remediate_port: 8080
  tasks:
    - name: 진단 — nginx 프로세스가 있는가
      ansible.builtin.command: pgrep -x nginx
      register: diag
      changed_when: false
      failed_when: false

    - name: 조치 — 설정 검사 후 시작 (14편 검사 핸들러와 같은 원칙)
      when: diag.rc != 0
      block:
        - name: 설정 검사
          ansible.builtin.command: nginx -t
          changed_when: false

        - name: Nginx 시작
          ansible.builtin.service:
            name: nginx
            state: started

    - name: 확인 — 응답이 오는가
      ansible.builtin.uri:
        url: "http://127.0.0.1:{{ remediate_port }}/health"
      register: check
      until: check.status == 200
      retries: 5
      delay: 2

    - name: 기록 — 언제 무엇을 했나 (티켓·메신저 연동 자리)
      ansible.builtin.lineinfile:
        path: /var/log/iaclab-remediation.log
        line: >-
          {{ now(utc=true).isoformat() }} {{ inventory_hostname }} alert={{ alert_name | default('manual') }}
          action={{ 'started' if diag.rc != 0 else 'none' }} result=http-{{ check.status }}
        create: true
        mode: "0644"
      changed_when: false

만나 본 문제 두 가지 (실측)

① 처음에는 웹훅을 /로 보내 405를 받았습니다. alertmanager 소스는 POST /{endpoint}(예: /alerts)만 받고 /는 GET 상태 확인용입니다. Alertmanager 설정의 webhook url도 http://eda:5050/alerts처럼 경로까지 적습니다. ② 다음에는 조치 플레이북이 root@127.0.0.1 Permission denied로 실패했습니다. 룰북의 run_playbook은 ansible-runner의 별도 작업 디렉터리에서 실행되어 프로젝트의 ansible.cfg(remote_user·키 경로)를 찾지 못했기 때문입니다. ANSIBLE_CONFIG를 지정해 해결했고, 운영에서는 연결 변수를 인벤토리(group_vars)에 두거나 EDA 컨트롤러의 run_job_template으로 컨트롤러 자격증명을 쓰는 것이 확실합니다.

고객 수십 곳을 하나의 자동화 플랫폼에서

고객 = 조직, 경계는 엄격히

고객마다 조직을 나누고 자격증명·인벤토리·프로젝트를 조직 밖에서 공유하지 않습니다. 실행 노드도 고객망 접근이 필요한 경우 고객별 실행 노드(메시 노드)를 고객망 안에 둡니다.

고객 셀프서비스 메뉴

“사용자 추가”, “nginx 다시 읽기”, “디스크 정리” 같은 저위험 작업을 survey가 있는 잡 템플릿으로 만들고 고객 운영팀에 execute만 줍니다. MSP 요청 처리 시간이 줄고, 모든 실행이 기록됩니다.

변경 관리와 연결

운영 변경은 워크플로(점검 → 승인 → 적용)로, 승인 노드의 승인자를 고객 변경 승인권자로. 잡 ID를 변경 티켓에 남기면 감사 대응이 쉬워집니다.

자동 조치는 등급제로

10장 판정처럼 “자동”, “승인 후 자동”, “알림만”으로 나눠 고객과 합의하고 SLA 문서에 넣습니다. 첫 달은 모든 규칙을 debug·알림만으로 돌려 오탐을 본 뒤 단계적으로 자동화합니다.

AIOps와의 접점

EDA의 이벤트 소스에 모니터링·로그 분석 시스템의 알림을 연결하면, 탐지(모니터링) → 판단(규칙) → 조치(플레이북) → 기록(티켓)의 고리가 생깁니다. 판단을 사람이 승인하는 단계를 두면 LLM 기반 분석 결과를 조치 후보로 제시하는 구조로도 확장할 수 있습니다.

플랫폼 자체도 코드로

AWX/AAP 설정(4장)과 EE(20편)와 룰북을 각각 저장소로 관리하고 CI로 적용합니다. 플랫폼을 다시 설치해도 설정을 재현할 수 있어야 재해 복구가 됩니다.

과제 1. AWX 랩 설치

k3s 또는 kind에 11장 매니페스트로 AWX 24.6.1을 설치하고, 4장 awx_config.yml을 실제로 적용하세요(EE 이미지는 20편 과제 2에서 빌드한 것, 인벤토리 소스는 2편 랩 인벤토리로 바꿔서). 적용을 두 번 해 changed가 0이 되는지 확인합니다 — awx.awx 모듈도 멱등해야 합니다.

과제 2. 고객 셀프서비스 템플릿

“운영 계정 추가” 잡 템플릿을 만드세요: survey로 사용자 이름(정규식 검증)·SSH 공개 키·sudo 여부를 받고, 17편 base_users 역할을 그 사용자에 대해서만 적용합니다. 고객 팀에는 execute만 주고, 입력 검증을 survey와 플레이북 assert 양쪽에 두는 이유를 정리합니다.

과제 3. 실패 시 롤백 워크플로

4장 워크플로의 apply 노드 실패 경로에 “이전 버전 태그로 다시 적용” 잡과 알림을 연결하세요. 프로젝트 브랜치를 실행 시 지정(ask_scm_branch_on_launch)하는 방법과 비교해 장단점을 씁니다.

과제 4. 디스크 가득 참 자동 조치

“DiskAlmostFull” 알림에 대해 ① 오래된 로그 압축·삭제(15편 find + 조건) ② 그래도 90% 이상이면 사람에게 알림, 을 하는 룰북 규칙과 조치 플레이북을 작성하세요. 10장 판정기로 이 조치의 등급을 매기고, 지우면 안 되는 경로를 어떻게 보호할지 설계합니다.

과제 5. 다른 이벤트 소스

ansible.eda의 url_check 소스로 웹 응답을 직접 감시하는 룰북을 만들어, Alertmanager 없이도 9장 실습과 같은 조치가 일어나게 하세요. 감시와 조치를 같은 시스템이 하는 구조의 위험(감시가 죽으면 조치도 멈춤)을 정리합니다.

기록·자격증명 숨김·RBAC·스케줄·이벤트. CI는 검사와 트리거, AWX는 실행.

현재 (2026-10)

AWX 24.6.1 이후 릴리스 중단(개편 중), AAP 2.6(게이트웨이·EDA·Lightspeed). ansible-core 버전 조합 확인.

객체

조직 → 팀·프로젝트·인벤토리(소스)·자격증명·EE → 잡 템플릿 → 워크플로·스케줄·알림.

코드로

awx.awx 모듈 13개 태스크, 인자 전부 문서 대조(실측: lint는 인자를 못 잡음). 비밀은 no_log.

RBAC·감사

고객 운영팀 execute, MSP admin, 감사 auditor. 프로젝트 쓰기 권한 = 자격증명 접근 가능성.

EDA

소스 → 조건 → 동작. 실측: 알림 3초 만에 복구, throttle로 3건 → 1회. 경로(/alerts)·ANSIBLE_CONFIG 함정.
