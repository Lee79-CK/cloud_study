이 편의 비유: 같은 메뉴, 다른 주방

네 엔진은 모두 “토큰을 굽는 주방”이지만 설계 철학이 다릅니다. vLLM은 어떤 재료든 받는 대형 주방, SGLang은 단골손님의 지난 주문을 기억해 밑준비를 재활용하는 주방, TensorRT-LLM은 특정 브랜드 화구에 맞춰 조리 도구를 모두 맞춤 제작한 주방, llama.cpp·Ollama는 캠핑장에서도 펼칠 수 있는 이동식 주방입니다. 어느 주방이 “제일 좋은가”는 메뉴와 손님, 그리고 그 주방을 누가 관리하느냐에 달려 있습니다.

03SGLang 해부

“구조화된 LLM 프로그램을 효율적으로 실행하자”에서 출발해, 대규모 프로덕션 서빙 엔진이 된 프로젝트.

SGLang은 LMSYS 연구진이 2024년 논문 SGLang: Efficient Execution of Structured Language Model Programs와 함께 공개했습니다. 원래 목적은 여러 번의 LLM 호출이 이어지는 “프로그램”(에이전트, 다단계 추론, 구조화 출력)을 빠르게 실행하는 것이었고, 그 핵심 장치가 RadixAttention과 압축 유한상태기계 기반 구조화 출력이었습니다. 지금은 DeepSeek·Qwen·Kimi 등 대형 모델의 출시 당일 지원과 대규모 전문가 병렬로 잘 알려져 있습니다.

① 프런트엔드·API

OpenAI 호환 API(채팅·완성·임베딩·Responses 등)와 자체 네이티브 API를 제공합니다. v0.5.17부터 네트워크 입구부터 토큰화된 요청을 스케줄러에 넘기기까지의 앞단을 다중 스레드 Rust로 옮기는 작업이 시작되었습니다. v0.5.20부터 Responses API의 결과 저장이 기본 꺼짐으로 바뀌는 등 기본값 변화가 잦으니 릴리스 노트 확인이 필수입니다. 여러 레플리카 앞에 두는 캐시 인지 라우터(모델 게이트웨이)도 프로젝트 안에서 함께 제공됩니다.

② 스케줄러: 오버헤드 없는 스케줄링

SGLang의 스케줄러는 CPU가 다음 배치를 준비하는 작업을 GPU 실행과 겹쳐(overlap) GPU가 쉬는 틈을 없애는 데 공을 들였습니다. vLLM의 비동기 스케줄링과 같은 목표입니다. 대기열 정책에 최장 프리픽스 일치 우선(LPM) 같은 캐시 인지 정책이 있어, 캐시를 많이 재사용할 수 있는 요청을 먼저 배치에 넣어 적중률을 끌어올립니다.

③ KV 캐시: RadixAttention

vLLM은 KV를 고정 크기 블록으로 나누고 “꽉 찬 블록”에 해시를 붙여 재사용합니다. SGLang은 지금까지 처리한 토큰 시퀀스들을 기수 트리(radix tree)로 관리합니다. 새 요청이 오면 트리를 따라 내려가며 가장 긴 공통 앞부분을 찾고, 그만큼의 KV를 재사용합니다. 트리 잎부터 오래된 것을 지우는(LRU) 방식으로 공간을 회수합니다.

위에서 보듯 관리 단위(블록 대 토큰)에서 오는 차이는 작습니다. vLLM도 블록 크기 단위로 거의 모든 공통 앞부분을 재사용하고, 요청마다 마지막 불완전 블록(평균 블록 절반 크기)만 다시 계산할 뿐입니다. 실제 운영에서 의미 있는 차이는 다음 세 가지에서 나옵니다.

  • 스케줄링이 캐시를 아는가: SGLang은 대기열 정렬 자체에 캐시 적중을 반영합니다. 동시에 많은 에이전트 세션이 섞인 상황에서 적중률 차이가 커집니다.
  • 축출 정책: v0.5.17에는 에이전트·강화학습 워크로드를 위해 요청에 세션 ID를 붙여, 활성 세션이 아직 참조하는 앞부분은 쉽게 지우지 않는 기능이 opt-in으로 들어갔습니다.
  • 계층형 캐시(HiCache): GPU에서 밀려난 KV를 CPU 메모리·SSD 계층으로 내려 보관했다가 다시 올리는 구조입니다. vLLM의 KV 오프로딩과 같은 문제를 푸는 SGLang의 방식입니다(15편).

④ 실행·커널

FlashInfer·FlashAttention 계열·Triton·Blackwell용 전용 MLA 커널 등 여러 어텐션 백엔드를 쓰고, torch.compile과 CUDA 그래프를 적극 활용합니다. 2026년 들어 조각(piecewise) CUDA 그래프가 기본이 되었고(v0.5.10), 이후 “끊을 수 있는(breakable)” CUDA 그래프가 기본 캡처 경로가 되었습니다(v0.5.15). 추측 디코딩은 개선된 Spec V2 경로가 기본입니다.

⑤ 분산·확장

대형 MoE의 대규모 전문가 병렬(DeepEP 등), 어텐션 데이터 병렬, P/D 분리, 컨텍스트 병렬에서 앞서 나가는 편입니다. v0.5.21에서는 P/D 인스턴스가 재시작 없이 Prefill과 Decode 역할을 바꿀 수 있게 되었습니다. GB200·GB300 랙 단위 서빙 사례도 활발히 공개하고 있습니다.

⑥ 생태계·운영

  • 릴리스 정책: 2026년 초 버전 체계를 정비해 0.X.Y에서 X가 오르면 큰 변화(릴리스 노트 필독), Y가 오르면 2~3주 주기의 비파괴적 개선, post 번호는 긴급 수정으로 구분합니다. 새 모델 지원은 먼저 nightly 이미지에 들어갔다가 검증 후 정식 릴리스로 올라옵니다.
  • 상위 플랫폼: llm-d와 NVIDIA Dynamo가 SGLang을 엔진으로 지원하고, NVIDIA NGC에도 SGLang 컨테이너가 있습니다(DGX Spark 지원 포함).
  • 그 밖: 확산 모델(이미지·영상) 서빙을 위한 SGLang Diffusion, TPU용 백엔드 등 범위를 넓히고 있습니다.

04TensorRT-LLM 해부

“모델을 엔진 파일로 컴파일해서 돌린다”던 엔진이, PyTorch 위에서 NVIDIA 커널을 총동원하는 구조로 완전히 바뀌었습니다.

가장 중요한 변화부터

오래된 자료의 TensorRT-LLM은 이런 순서였습니다: 체크포인트 변환 → trtllm-build로 GPU·배치 크기·길이에 맞춘 TensorRT 엔진 파일 생성(모델당 수십 분) → 그 엔진을 서빙. 이 흐름은 이제 과거입니다.

  • 1.0: PyTorch 기반 구조가 안정화되어 기본값이 되었고, LLM API가 안정 API로 선언되었습니다.
  • 1.2: TensorRT 백엔드가 제거되었습니다. PyTorch가 유일한 실행 백엔드이며, trtllm-build·trtllm-refit·trtllm-prune CLI와 모델별 변환 스크립트도 사라졌습니다. 같은 릴리스에서 DGX Spark 단일 노드가 베타로 지원되었습니다(Qwen3-8B·14B·32B, Llama 3.x, gpt-oss 등 검증).
  • 1.3 (RC 단계): 2026년 9월 기준 Triton 기반 MoE 백엔드 사용 중단 예고 등 정리가 계속되고 있고, 10월 중순 1.4 RC가 시작되었습니다.

그래서 커리큘럼의 “컴파일형 최적화”라는 표현은 이제 이렇게 읽어야 합니다. 미리 빌드한 엔진 파일이 아니라, NVIDIA가 직접 만든 커널(어텐션의 XQA·TRT-LLM 생성 커널, CUTLASS GEMM, MoE 커널 등), 커널 자동 튜너, torch.compile과 조각 CUDA 그래프를 PyTorch 실행 위에 조합한 구조입니다. 인터넷의 “TensorRT-LLM은 빌드가 30분 걸린다”는 글은 1.2 이전 이야기입니다.

여섯 축으로 본 TensorRT-LLM

운영자가 알아야 할 설정 차이

  • KV 메모리 비율의 의미: kv_cache_free_gpu_memory_fraction은 “가중치를 올리고 남은 메모리 중” KV에 쓸 비율입니다. vLLM(전체 대비)·SGLang(정적 할당 비율)과 기준이 달라, 같은 0.9라도 실제 KV 크기가 다릅니다. 특히 GB10처럼 메모리를 CPU와 공유하는 장비에서 기본값을 그대로 쓰면 시스템 메모리 대부분을 잡아 다른 프로세스를 압박할 수 있으니 낮게 설정합니다.
  • 설정 방식: 세부 옵션은 YAML 파일(--config 또는 --extra_llm_api_options)로 넘깁니다. 1.2부터 명시적 CLI 옵션이 YAML 값보다 우선하도록 바뀌었습니다. 이전 버전에서 쓰던 배포 스크립트를 옮길 때 주의합니다.
  • 릴리스 리듬: 거의 매주 RC가 나오고 안정판은 그보다 드물게 나옵니다. 프로덕션은 안정판 또는 NGC 릴리스 컨테이너의 검증된 태그를 씁니다.
  • 모델 지원 범위: NVIDIA가 배포 가이드를 내는 주요 모델(gpt-oss, Qwen3 계열, DeepSeek, Kimi, GLM, Nemotron 등)은 매우 빠르고 깊게 최적화되지만, 지원 목록 밖의 모델은 vLLM보다 늦거나 없을 수 있습니다.
언제 TensorRT-LLM을 검토하나

NVIDIA 최신 GPU(Hopper·Blackwell) 위에서 지원 목록 안의 대형 모델을 대규모로 서빙하고, 몇 퍼센트의 처리량 차이가 큰 비용 차이로 이어지는 경우입니다. 또는 고객이 NVIDIA AI Enterprise·NIM 기반 지원 계약을 원하는 경우입니다. 반대로 다양한 모델을 자주 바꾸거나, AMD·인텔 가속기가 섞여 있거나, 운영 인력이 범용 도구에 익숙한 환경이라면 vLLM·SGLang이 총비용 면에서 유리한 경우가 많습니다.

05TGI의 현재

한때 표준 중 하나였던 엔진이 스스로 유지보수 모드를 선언했습니다. 기존 고객사 환경에서 여전히 만나게 되므로 알아 둘 필요가 있습니다.

Hugging Face의 Text Generation Inference(TGI)는 연속 배칭, 텐서 병렬, 플래시·페이지드 어텐션, OpenTelemetry·Prometheus 같은 운영 기능을 일찍 갖추고 SageMaker·Inference Endpoints 등에서 널리 쓰였습니다. 2025년 12월부터 유지보수 모드로 전환되어, 작은 버그 수정·문서·가벼운 유지보수 PR만 받습니다. 공식 문서는 앞으로 vLLM·SGLang, 그리고 llama.cpp·MLX 같은 로컬 엔진을 쓰도록 권합니다.

기존 TGI 환경을 맡았을 때
  • 신규 도입은 하지 않습니다. 새 모델·새 GPU 지원과 보안 수정이 언제까지 이어질지 보장되지 않습니다.
  • 이전 계획을 세웁니다. TGI도 OpenAI 호환 Messages 경로를 제공하므로, 앱이 그 경로를 쓰고 있다면 vLLM·SGLang으로 엔진만 바꾸고 게이트웨이(12편)에서 경로를 맞추는 방식으로 앱 변경을 최소화할 수 있습니다. TGI 고유 API(/generate 등)를 쓰는 앱은 호출부 수정이 필요합니다.
  • 이전 전후로 3편 방식의 SLO 벤치마크와 품질 회귀 테스트를 돌려 같은 약속을 지키는지 확인합니다.

06llama.cpp와 Ollama

데이터센터 GPU가 없는 곳에서 LLM을 돌리는 사실상의 표준. 플랫폼 엔지니어가 “쓰지 말아야 할 곳”까지 알아야 하는 엔진입니다.

llama.cpp
  • C/C++로 작성된 추론 엔진과 GGUF 모델 파일 형식. 의존성이 거의 없어 어디서나 빌드됩니다.
  • CPU(x86·Arm), Apple Metal, CUDA, ROCm, Vulkan 등 거의 모든 하드웨어. GPU에 올릴 층 수(-ngl)를 정해 CPU와 나눠 실행할 수 있습니다.
  • 다양한 정수 양자화(Q8_0, Q6_K, Q5_K_M, Q4_K_M 등)로 큰 모델을 작은 메모리에 올립니다.
  • llama-server가 OpenAI 호환 API와 웹 UI를 제공합니다. 동시 처리는 “슬롯”(-np) 단위이며, 전체 컨텍스트(-c)를 슬롯 수로 나눠 쓰는 구조라 동시성을 늘리면 요청당 컨텍스트가 줄어듭니다. KV 양자화(-ctk, -ctv)도 지원합니다.
Ollama
  • llama.cpp 계열(GGML) 기술 위에 모델 라이브러리·다운로드·버전 관리·자동 로딩/언로딩을 얹은 “로컬 LLM 런타임 + 패키지 관리자”.
  • ollama run qwen3:8b 한 줄로 내려받아 실행. Modelfile로 프롬프트·파라미터를 묶어 배포합니다.
  • 자체 API와 함께 OpenAI 호환 경로(/v1), Anthropic 호환 API도 제공합니다.
  • 요청이 없으면 일정 시간 뒤 모델을 메모리에서 내리고(keep_alive), 동시 요청 수·동시 로드 모델 수를 환경 변수로 조절합니다.

09선택 기준과 선택 도우미

커리큘럼의 네 기준(GPU 세대, 모델 아키텍처, 운영 복잡도, 커뮤니티 속도)에 비용·보안을 더해 판단합니다.

여섯 가지 기준

  1. GPU 세대와 벤더: NVIDIA Blackwell에서 NVFP4를 최대한 쓰려면 TensorRT-LLM과 각 엔진의 Blackwell 전용 커널 지원 상태가 중요합니다. AMD·인텔·CPU가 섞이면 vLLM·SGLang·llama.cpp로 좁혀집니다. Ampere(A100) 세대는 세 데이터센터 엔진 모두 성숙합니다.
  2. 모델 아키텍처와 출시 당일 지원: 새 모델(특히 MLA·희소 어텐션·선형 어텐션·하이브리드 구조)은 엔진마다 지원 시점과 최적화 수준이 다릅니다. 모델 제작사의 “권장 서빙 방법”과 각 엔진의 쿡북·레시피를 확인합니다.
  3. 운영 복잡도: 우리 팀이 이미 아는 엔진, 우리가 쓰는 상위 플랫폼(KServe·llm-d·Dynamo)이 지원하는 엔진이 운영 비용을 크게 줄입니다. 엔진 종류가 늘면 지표·로그·업그레이드 절차도 그만큼 늘어납니다.
  4. 커뮤니티 속도와 안정성: 빠른 릴리스는 새 모델 지원을 앞당기지만 기본값 변경도 잦습니다. 릴리스 정책(버전 체계, RC·nightly 운용)과 호환성 공지를 읽습니다.
  5. 비용: 같은 SLO에서의 토큰당 비용(3편). 엔진 차이로 처리량이 10% 달라지면 GPU 10%가 달라집니다. 반면 운영 인력·장애 비용도 비용입니다.
  6. 보안·공급망·지원: 이미지 출처(공식·NGC), CVE 대응 속도, 상용 지원 필요 여부, 라이선스.

14실습

같은 GB10 노드, 같은 Qwen3-8B로 vLLM·SGLang·TensorRT-LLM을 차례로 띄우고, 클러스터 안의 측정 Pod에서 같은 스크립트로 잽니다. llama.cpp는 호스트에서 비교 기준선으로 돌립니다.

실습 환경 전제와 주의
  • GB10 GPU 노드(arm64), 네임스페이스 llmsvc-lab, 인터넷 접근 가능. GPU가 하나이므로 엔진은 한 번에 하나씩 띄웁니다.
  • Qwen3-8B는 TensorRT-LLM 1.2 릴리스 노트에서 DGX Spark 검증 모델로 명시되어 있어 세 엔진 모두에서 시도하기 좋습니다. 그래도 GB10 지원은 엔진마다 베타·초기 단계일 수 있으니, 기동이 안 되는 엔진은 오류 내용을 기록하는 것 자체를 결과로 삼으세요.
  • 이미지 태그와 arm64 지원은 4편 실습 4-1과 같은 방법으로 먼저 확인합니다. 각 엔진의 NGC 컨테이너(nvcr.io/nvidia/vllm, nvcr.io/nvidia/sglang, nvcr.io/nvidia/tensorrt-llm/release)는 DGX 계열 지원이 명시된 경우가 많아 GB10에서 출발점으로 좋습니다.
  • GB10의 절대 성능은 이 실습의 관심사가 아닙니다. 같은 조건을 만드는 과정과 결과를 해석하는 과정이 목표입니다.

"""엔진 중립 벤치마크: 단일 요청 지연, 동시성 스윕, 공유 프리픽스 효과를 측정해 JSON으로 저장한다.
사용: python engine_bench.py --base http://llm-engine:8000/v1 --label vllm"""
import argparse, asyncio, json, random, statistics, time
from openai import AsyncOpenAI

ap = argparse.ArgumentParser()
ap.add_argument("--base", required=True); ap.add_argument("--label", required=True)
ap.add_argument("--model", default=None); ap.add_argument("--out", type=int, default=256)
args = ap.parse_args()
cli = AsyncOpenAI(base_url=args.base, api_key="EMPTY", timeout=900)
EXTRA = {"ignore_eos": True}        # 지원하지 않는 엔진이면 자동으로 빼고 재시도
WORDS = "노드 파드 쿼터 지연 처리량 메모리 대역폭 캐시 배치 스케줄러 게이트웨이 장애 알림 예산".split()

async def one(prompt, max_tokens, system=None):
    global EXTRA
    msgs = ([{"role": "system", "content": system}] if system else []) + \
           [{"role": "user", "content": prompt + " /no_think"}]
    kw = dict(model=args.model, messages=msgs, max_tokens=max_tokens, stream=True,
              stream_options={"include_usage": True})
    t0 = time.perf_counter(); first = last = None; chunks = 0; usage = None
    try:
        stream = await cli.chat.completions.create(**kw, extra_body=EXTRA or None)
    except Exception:
        EXTRA = {}; t0 = time.perf_counter()
        stream = await cli.chat.completions.create(**kw)
    async for ev in stream:
        if getattr(ev, "usage", None): usage = ev.usage
        if ev.choices and ev.choices[0].delta and ev.choices[0].delta.content:
            now = time.perf_counter(); first = first or now; last = now; chunks += 1
    n = usage.completion_tokens if usage and usage.completion_tokens else chunks
    p = usage.prompt_tokens if usage else None
    if first is None: return None
    return {"ttft": first - t0, "tpot": (last - first) / max(n - 1, 1), "out": n, "in": p, "e2e": last - t0}

def med(xs): return statistics.median(xs) if xs else float("nan")
def p95(xs): xs = sorted(xs); return xs[min(len(xs) - 1, int(.95 * len(xs)))] if xs else float("nan")
def rnd_text(seed, n): r = random.Random(seed); return " ".join(r.choice(WORDS) for _ in range(n))

async def main():
    if not args.model:
        args.model = (await cli.models.list()).data[0].id
    res = {"label": args.label, "model": args.model}
    await one("워밍업", 16); await one("워밍업 두 번째", 16)

    # A. 단일 요청
    rs = [await one(f"{i}번째: 쿠버네티스 GPU 운영 체크리스트를 길게 써 줘.", args.out) for i in range(3)]
    rs = [r for r in rs if r]
    res["single"] = {"ttft_ms": med([r["ttft"] for r in rs]) * 1e3, "tpot_ms": med([r["tpot"] for r in rs]) * 1e3,
                     "out_tokens": med([r["out"] for r in rs]), "in_tokens": rs[0]["in"],
                     "ignore_eos": bool(EXTRA)}
    print("[A]", res["single"])

    # B. 동시성 스윕 (닫힌 루프)
    res["sweep"] = []
    for c in [1, 4, 16, 32]:
        t0 = time.perf_counter()
        rs = await asyncio.gather(*[one(f"{rnd_text(c*100+i, 60)} 위 메모를 요약해 줘.", args.out) for i in range(c)])
        rs = [r for r in rs if r]; wall = time.perf_counter() - t0
        row = {"conc": c, "tok_s": sum(r["out"] for r in rs) / wall,
               "tpot_ms": med([r["tpot"] for r in rs]) * 1e3, "ttft_p95_ms": p95([r["ttft"] for r in rs]) * 1e3}
        res["sweep"].append(row); print("[B]", row)

    # C. 공유 프리픽스: 같은 긴 시스템 프롬프트 + 다른 질문 vs 매번 다른 시스템 프롬프트
    shared = "너는 사내 인프라 운영 도우미다. 다음은 운영 규정이다. " + rnd_text(7, 1200)
    same = [await one(f"질문 {i}: 규정 요약 한 줄", 32, system=shared) for i in range(6)]
    diff = [await one(f"질문 {i}: 규정 요약 한 줄", 32, system=f"[{i}] " + rnd_text(1000 + i, 1200)) for i in range(6)]
    res["prefix"] = {"first_ttft_ms": same[0]["ttft"] * 1e3,
                     "shared_rest_ttft_ms": med([r["ttft"] for r in same[1:]]) * 1e3,
                     "unique_ttft_ms": med([r["ttft"] for r in diff]) * 1e3,
                     "prefix_in_tokens": same[0]["in"]}
    print("[C]", res["prefix"])
    json.dump(res, open(f"/tmp/result_{args.label}.json", "w"), ensure_ascii=False, indent=1)
    print("저장:", f"/tmp/result_{args.label}.json")

asyncio.run(main())

핵심 여섯 문장.

  1. 주요 엔진은 서로 닮아 간다. 연속 배칭·페이지 KV·프리픽스 재사용·P/D 분리는 공통이고, 차이는 철학·성숙도·우리 조합에서의 실측에서 난다.
  2. SGLang은 기수 트리와 캐시 인지 스케줄링으로 에이전트·멀티턴에 강하고, 대형 MoE 분산에서 앞서 나간다.
  3. TensorRT-LLM은 1.2부터 PyTorch 기반이 유일한 경로이며, NVIDIA 자체 커널과 NVFP4 최적화, Dynamo·Triton·NIM 생태계가 강점이다. NVIDIA 전용이다.
  4. TGI는 유지보수 모드다. 신규 도입하지 말고 기존 환경은 이전 계획을 세운다.
  5. llama.cpp·Ollama는 엣지·개발·이기종 장비의 표준이지만, 대규모 멀티테넌트 서빙의 근거로 쓰면 안 된다.
  6. 엔진 비교는 공정성 체크리스트를 통과해야 의미가 있고, MSP는 “표준 하나 + 승인된 예외 + 네 가지 계약(API·지표·배포·품질)”으로 엔진을 관리한다.
