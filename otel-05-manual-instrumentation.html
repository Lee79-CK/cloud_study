자동 계측이 끝나는 곳에서 시작하기

자동 계측은 시스템의 구조를 보여줍니다. HTTP가 들어왔고, DB를 거쳤고, 외부 API를 불렀다. 하지만 "왜 이 주문이 실패했는지", "재고 할당에 얼마가 걸렸는지"는 여전히 깜깜합니다. 코드의 의미를 아는 사람은 개발자뿐이고, 그래서 수동 계측은 위임할 수 없는 작업입니다.

3개 언어 동시 대조 Span 설계 판단 트리 메트릭 vs 속성 분류 연습 컨텍스트 이어붙이기
같은 요청, 같은 243ms를 두 가지로 본 모습

SECTION 01

수동 계측이 필요한 순간

수동 계측은 많이 할수록 좋은 것이 아닙니다. 자동 계측이 남긴 빈칸 중 실제로 답이 필요한 곳만 채우는 작업입니다.

1. 비즈니스 구간의 소요 시간

재고 할당, 할인 계산, 정책 검증처럼 라이브러리 호출이 아닌 내부 로직. 트레이스에서 "부모의 빈 시간"으로만 보이는 구간입니다.

2. 도메인 의미를 담은 속성

주문 채널, 결제 수단, 고객 등급. 이 값이 있어야 "모바일 결제만 느리다" 같은 질문에 답할 수 있습니다.

3. 실패의 진짜 의미

재고 부족으로 주문을 거절하면 HTTP는 200일 수 있습니다. 자동 계측은 이를 성공으로 봅니다.

4. 비즈니스 지표

초당 주문 수, 결제 수단별 실패율. 인프라 지표로는 절대 알 수 없는 값입니다.

5. 끊긴 컨텍스트 복구

자체 스레드풀, 메시지 큐, 커스텀 비동기 처리. 자동 계측이 따라가지 못하는 경계입니다.

6. 미지원 라이브러리

사내 자체 구현 RPC, 레거시 통신 방식. 애초에 에이전트가 인식하지 못합니다.

API와 SDK를 구분해서 의존하세요

수동 계측 코드는 OTel API 패키지에만 의존해야 합니다. SDK는 실행 시점에 에이전트나 래퍼가 제공합니다. 애플리케이션 코드가 SDK를 직접 의존하면 버전 충돌이 생기고, 계측을 끈 환경에서 앱이 뜨지 않는 상황이 생깁니다. API만 쓰면 SDK가 없을 때 모든 호출이 아무 일도 하지 않고 지나갑니다(no-op).

SECTION 02

Span 직접 만들기

Tracer를 얻고, Span을 시작하고, 현재 컨텍스트로 만들고, 반드시 끝냅니다. 이 네 단계가 전부이며, "반드시 끝낸다"가 가장 중요합니다.

Tracer 획득 — 애플리케이션당 한 번

Tracer 이름은 보통 모듈·패키지 이름을 씁니다. 백엔드에서 어느 코드가 만든 Span인지 구분하는 데 쓰입니다.

Java
import io.opentelemetry.api.GlobalOpenTelemetry;
import io.opentelemetry.api.trace.*;

// 클래스마다 만들지 말고 상수로 한 번만
private static final Tracer TRACER =
    GlobalOpenTelemetry.getTracer("com.acme.order", "1.4.2");
Python
from opentelemetry import trace

# 모듈 최상단에서 한 번만
tracer = trace.get_tracer("com.acme.order", "1.4.2")
Node.js
const { trace, SpanStatusCode, SpanKind } = require('@opentelemetry/api');

// 모듈 최상단에서 한 번만
const tracer = trace.getTracer('com.acme.order', '1.4.2');

Span 생성과 종료

Java — try-with-resources와 finally를 반드시 짝으로
Span span = TRACER.spanBuilder("allocate-inventory")
    .setSpanKind(SpanKind.INTERNAL)
    .startSpan();

try (Scope scope = span.makeCurrent()) {
    // 이 블록 안에서 만들어지는 Span은 자동으로 자식이 됩니다
    return allocator.allocate(items);
} catch (Exception e) {
    span.recordException(e);
    span.setStatus(StatusCode.ERROR);
    throw e;
} finally {
    span.end();   // 이걸 빼먹으면 Span이 영영 전송되지 않습니다
}
Python — 컨텍스트 매니저가 종료와 예외 기록을 대신해 줍니다
with tracer.start_as_current_span("allocate-inventory") as span:
    # 블록을 벗어나면 자동으로 span.end() 호출
    # 예외가 나면 자동으로 recordException + ERROR 상태
    return allocator.allocate(items)

# 데코레이터 방식도 있습니다
@tracer.start_as_current_span("allocate-inventory")
def allocate(items):
    return allocator.allocate(items)
Node.js — startActiveSpan이 컨텍스트를 묶어 줍니다
return tracer.startActiveSpan('allocate-inventory',
  { kind: SpanKind.INTERNAL },
  async (span) => {
    try {
      return await allocator.allocate(items);
    } catch (err) {
      span.recordException(err);
      span.setStatus({ code: SpanStatusCode.ERROR });
      throw err;
    } finally {
      span.end();   // 콜백 방식이어도 end()는 직접 호출해야 합니다
    }
  });
가장 흔한 사고 — 종료되지 않은 Span

end()를 호출하지 않으면 그 Span은 전송되지 않고 메모리에만 남습니다. 요청이 들어올 때마다 쌓이므로 결국 메모리 누수가 됩니다. Java와 Node.js는 finally를 반드시 쓰고, Python은 컨텍스트 매니저나 데코레이터를 쓰면 이 문제가 구조적으로 사라집니다. 코드 리뷰 체크리스트에 "모든 startSpan에 대응하는 end가 있는가"를 넣어두세요.

현재 컨텍스트로 만드는 것의 의미

Span을 현재 컨텍스트로 활성화해야 그 안에서 발생하는 모든 Span이 자식이 됩니다. 자동 계측이 만드는 DB Span도, 내가 만드는 하위 Span도 마찬가지입니다. 활성화를 빼먹으면 Span은 생기지만 트레이스 트리에서 엉뚱한 위치에 붙거나 고아가 됩니다.

SECTION 03

속성 · 이벤트 · 상태

Span을 만들었으면 이제 그 안에 의미를 담습니다. 2편의 데이터 모델이 여기서 코드로 나타납니다.

Java
// 속성 — 이 요청에서만 의미 있는 값
span.setAttribute("acme.order.channel", channel);
span.setAttribute("acme.order.item_count", items.size());
span.setAttribute("acme.customer.tier", tier);

// 이벤트 — Span 진행 중 특정 시점의 기록
span.addEvent("stock.shortage",
    Attributes.of(AttributeKey.stringKey("acme.sku"), sku));

// 상태 — 비즈니스 실패를 명시적으로 표시
if (!result.ok()) {
    span.setStatus(StatusCode.ERROR, "insufficient stock");
}
Python
from opentelemetry.trace import Status, StatusCode

# 속성
span.set_attribute("acme.order.channel", channel)
span.set_attribute("acme.order.item_count", len(items))
span.set_attribute("acme.customer.tier", tier)

# 이벤트
span.add_event("stock.shortage", {"acme.sku": sku})

# 상태
if not result.ok:
    span.set_status(Status(StatusCode.ERROR, "insufficient stock"))
Node.js
// 속성
span.setAttribute('acme.order.channel', channel);
span.setAttribute('acme.order.item_count', items.length);
span.setAttribute('acme.customer.tier', tier);

// 이벤트
span.addEvent('stock.shortage', { 'acme.sku': sku });

// 상태
if (!result.ok) {
  span.setStatus({ code: SpanStatusCode.ERROR,
                   message: 'insufficient stock' });
}
속성 이름은 자체 네임스페이스로

2편의 규칙 그대로입니다. acme. 같은 회사 접두사를 쓰고, http.·db. 같은 표준 네임스페이스는 침범하지 않습니다. 그리고 값의 가짓수가 요청 수에 비례해 늘어나는 값은 넣지 마세요. 주문 ID, 사용자 ID, UUID가 대표적입니다. 6편에서 왜 이게 비용 사고로 이어지는지 다룹니다.

비즈니스 실패를 ERROR로 표시할 것인가

이건 판단이 필요한 문제입니다. 재고 부족은 시스템 오류가 아니라 정상적인 비즈니스 흐름입니다. 이걸 전부 ERROR로 찍으면 에러율 대시보드가 의미를 잃습니다.

권장 · 속성으로 표현

상태는 UNSET으로 두고 acme.order.result=rejected, acme.reject.reason=out_of_stock 같은 속성을 붙입니다. 필요하면 나중에 이 속성으로 조회합니다.

주의 · ERROR 남용

ERROR는 "시스템이 요청을 처리하지 못했다"를 뜻해야 합니다. 정상적인 거절까지 ERROR로 찍으면 알림이 계속 울리고, 결국 아무도 알림을 안 보게 됩니다.

이 기준을 조직 차원에서 한 번 정해두는 것이 11편의 경계 계약서에 들어갈 항목입니다. 팀마다 다르게 판단하면 서비스 간 에러율 비교가 불가능해집니다.

SECTION 04

커스텀 메트릭

트레이스는 개별 요청의 사연을, 메트릭은 전체 추세를 보여줍니다. 비즈니스 지표는 대부분 메트릭 쪽입니다.

Java — 계측기도 상수로 한 번만 만듭니다
private static final Meter METER =
    GlobalOpenTelemetry.getMeter("com.acme.order");

private static final LongCounter ORDERS =
    METER.counterBuilder("acme.orders.placed")
         .setDescription("주문 생성 건수")
         .setUnit("{order}")
         .build();

private static final DoubleHistogram AMOUNT =
    METER.histogramBuilder("acme.order.amount")
         .setUnit("KRW")
         .build();

// 사용
Attributes attrs = Attributes.of(
    AttributeKey.stringKey("acme.order.channel"), channel,
    AttributeKey.stringKey("acme.payment.method"), method);
ORDERS.add(1, attrs);
AMOUNT.record(order.total(), attrs);
Python
from opentelemetry import metrics

meter = metrics.get_meter("com.acme.order")

orders = meter.create_counter(
    "acme.orders.placed",
    unit="{order}",
    description="주문 생성 건수")

amount = meter.create_histogram(
    "acme.order.amount", unit="KRW")

# 사용
attrs = {"acme.order.channel": channel,
         "acme.payment.method": method}
orders.add(1, attrs)
amount.record(order.total, attrs)
Node.js
const { metrics } = require('@opentelemetry/api');

const meter = metrics.getMeter('com.acme.order');

const orders = meter.createCounter('acme.orders.placed', {
  unit: '{order}',
  description: '주문 생성 건수',
});

const amount = meter.createHistogram('acme.order.amount',
  { unit: 'KRW' });

// 사용

                'acme.payment.method': method };
orders.add(1, attrs);
amount.record(order.total, attrs);
메트릭 속성은 트레이스 속성보다 훨씬 위험합니다

트레이스는 샘플링돼서 일부만 저장되지만, 메트릭은 속성 조합마다 시계열이 하나씩 영구히 만들어집니다. acme.order.channel은 값이 서너 개라 안전하지만 acme.order.id를 넣는 순간 주문 수만큼 시계열이 생깁니다. 메트릭 속성은 값의 가짓수를 손가락으로 셀 수 있을 때만 추가하세요.

메트릭으로 할 것과 Span 속성으로 할 것

각 항목이 어디에 속하는지 골라보세요.

초당 주문 생성 건수
주문 ID (요청마다 고유)
결제 수단별 실패 횟수
이 주문이 거절된 구체적 사유 문구
처리 대기 큐의 현재 적체량
이 요청에 담긴 상품 개수
둘 다 하는 경우도 많습니다

"응답 시간"은 Span에도 기록되고 Histogram 메트릭으로도 기록됩니다. 트레이스는 왜 느렸는지를, 메트릭은 얼마나 자주 느린지를 알려주기 때문입니다. Exemplar를 쓰면 메트릭 그래프에서 바로 해당 트레이스로 넘어갈 수도 있습니다(2편).

SECTION 05

로그와 트레이스 연결하기

신호 연결의 핵심은 로그에 trace_id가 찍히는 것 하나입니다. 이것만 되면 트레이스 화면에서 해당 요청의 로그만 골라 볼 수 있습니다.

Java — 에이전트가 MDC에 넣어주고, 출력 패턴은 개발자가 씁니다
<!-- logback-spring.xml -->
<pattern>
  %d{ISO8601} %-5level [%X{trace_id:-},%X{span_id:-}] %logger - %msg%n
</pattern>

// 코드에서는 평소처럼 로깅하면 됩니다
log.warn("재고 부족: sku={}, 요청={}", sku, qty);

// JSON 로깅을 쓴다면 trace_id를 별도 필드로 두는 편이 조회에 유리합니다
Python — 환경 변수로 켜고 포맷에 필드를 추가합니다
# 환경 변수
OTEL_PYTHON_LOG_CORRELATION=true

# 로깅 포맷에 필드 추가
logging.basicConfig(
    format="%(asctime)s %(levelname)s "
           "[%(otelTraceID)s,%(otelSpanID)s] %(message)s")

# 코드에서는 평소처럼
logger.warning("재고 부족: sku=%s, 요청=%s", sku, qty)

# 직접 꺼내 쓰고 싶다면
ctx = trace.get_current_span().get_span_context()
trace_id = format(ctx.trace_id, "032x")
Node.js — pino·winston 계측을 쓰거나 직접 주입합니다
// 자동 계측이 pino·winston에 trace_id를 넣어줍니다
logger.warn({ sku, qty }, '재고 부족');

// 직접 꺼내 쓰는 방법
const span = trace.getActiveSpan();
if (span) {
  const { traceId, spanId } = span.spanContext();
  logger.warn({ sku, qty, trace_id: traceId, span_id: spanId },
              '재고 부족');
}
엔지니어와의 접점

개발자가 할 일은 로그 출력에 trace_id 필드를 넣는 것까지입니다. 그 로그를 어떻게 수집하고(stdout 읽기 vs OTLP 직접 전송), 어느 백엔드에 저장하고, 트레이스 화면과 어떻게 연동할지는 엔지니어 영역입니다. 다만 로그 포맷은 사전에 합의해야 합니다. 구조화된 JSON 로그로 통일하면 파싱 규칙을 서비스마다 만들 필요가 없습니다.

Span Event와 로그 중 무엇을 쓸 것인가

기준Span Event로그
조회 방식트레이스 화면에서 Span 열어 확인로그 검색으로 전체 조회 가능
샘플링Span이 버려지면 함께 사라짐보통 전량 보관
적합한 내용이 요청의 흐름 안에서만 의미 있는 시점 기록사후에 통계·검색이 필요한 기록
비용Span 크기 증가로그 저장 비용

실무 기준을 하나 제시하면 이렇습니다. 나중에 "이런 일이 몇 번 있었나"를 세어볼 것 같으면 로그, 특정 요청을 들여다볼 때만 필요하면 Event. 예외는 두 곳 모두에 남기는 편이 안전합니다.

SECTION 06

Baggage — 전 구간에 값 흘려보내기

테넌트 ID나 요청 출처처럼 여러 서비스에서 공통으로 필요한 값을 호출 인자로 일일이 넘기지 않고 컨텍스트에 실어 보내는 장치입니다.

Java
// 값 넣기 — 이후 하위 호출에 자동으로 실려 나갑니다
Baggage updated = Baggage.current().toBuilder()
    .put("acme.tenant.id", tenantId)
    .build();

try (Scope scope = updated.makeCurrent()) {
    orderService.place(req);
}

// 다른 서비스에서 꺼내 쓰기
String tenant = Baggage.current().getEntryValue("acme.tenant.id");
Python
from opentelemetry import baggage, context

# 값 넣기
ctx = baggage.set_baggage("acme.tenant.id", tenant_id)
token = context.attach(ctx)
try:
    order_service.place(req)
finally:
    context.detach(token)

tenant = baggage.get_baggage("acme.tenant.id")
Node.js
const { propagation, context } = require('@opentelemetry/api');

// 값 넣기
const bag = propagation.createBaggage({

// 꺼내 쓰기
const entry = propagation.getBaggage(context.active())
                         ?.getEntry('acme.tenant.id');
Baggage 사용 시 반드시 지킬 것 세 가지

1. 민감정보 금지 — Baggage는 HTTP 헤더로 나갑니다. 외부 API를 호출하면 그쪽 서버까지 값이 전달됩니다.
2. 자동으로 Span 속성이 되지 않습니다 — 필요하면 각 서비스에서 명시적으로 속성에 복사해야 합니다.
3. 크기를 작게 — 모든 요청의 모든 홉에 헤더로 붙으므로, 값이 커지면 네트워크 비용이 됩니다. 키 한두 개 정도로 제한하세요.

SECTION 07

끊긴 컨텍스트 이어붙이기

2편과 4편에서 반복해 나온 그 문제입니다. 이제 실제로 고치는 코드를 봅니다.

Java — 스레드풀 경계
// 잘못된 코드 — 컨텍스트가 넘어가지 않습니다
executor.submit(() -> processAsync(order));

// 방법 1 · 작업을 감싸기
executor.submit(Context.current().wrap(() -> processAsync(order)));

// 방법 2 · Executor 자체를 감싸기 (권장)
ExecutorService traced = Context.taskWrapping(executor);
traced.submit(() -> processAsync(order));

// CompletableFuture 체인에서도 같은 원리가 적용됩니다
Context ctx = Context.current();
CompletableFuture.supplyAsync(() -> ctx.wrap(task).call(), executor);
Python — 스레드·프로세스 경계
import contextvars
from concurrent.futures import ThreadPoolExecutor

# 잘못된 코드 — 컨텍스트가 넘어가지 않습니다
executor.submit(process_async, order)

# 올바른 코드 — 컨텍스트를 복사해 함께 전달
ctx = contextvars.copy_context()
executor.submit(ctx.run, process_async, order)

# asyncio는 대부분 자동으로 따라갑니다
await asyncio.gather(*[process(o) for o in orders])

# multiprocessing은 프로세스가 분리되므로 이 방법이 통하지 않습니다
# 이 경우 trace_id를 인자로 넘겨 수신 측에서 새 Span을 만들고 Link로 연결합니다
Node.js — 콜백·이벤트 경계
const { context } = require('@opentelemetry/api');

// 잘못된 코드 — 나중에 실행될 때 컨텍스트가 없습니다
emitter.on('order.done', handler);

// 올바른 코드 — 현재 컨텍스트를 콜백에 묶습니다
const ctx = context.active();
emitter.on('order.done', context.bind(ctx, handler));

// 블록 전체를 특정 컨텍스트에서 실행
context.with(ctx, () => {
  queue.push(job);
});

// async/await와 Promise 체인은 대부분 자동으로 따라갑니다
판별하는 법

"이 코드가 지금 당장 실행되는가, 나중에 실행되는가"를 물어보세요. 나중에 실행되는 코드(콜백, 스레드풀 작업, 큐에 넣은 작업)는 실행 시점에 현재 컨텍스트가 이미 다른 것으로 바뀌어 있습니다. 그래서 등록하는 시점의 컨텍스트를 붙잡아 함께 넘겨야 합니다. 세 언어의 해법이 이름만 다를 뿐 전부 같은 일을 합니다.

SECTION 08

메시지 큐 — 주입과 추출

HTTP는 자동 계측이 헤더를 알아서 넣고 꺼냅니다. 메시지 큐는 라이브러리와 구성에 따라 그렇지 않은 경우가 많아 직접 해야 합니다.

생산자 — 컨텍스트 주입

Java
TextMapSetter<Headers> setter = (headers, key, value) ->
    headers.add(key, value.getBytes(StandardCharsets.UTF_8));

Span span = TRACER.spanBuilder("order-created publish")
    .setSpanKind(SpanKind.PRODUCER).startSpan();
try (Scope s = span.makeCurrent()) {
    // 현재 컨텍스트를 메시지 헤더에 씁니다
    GlobalOpenTelemetry.getPropagators().getTextMapPropagator()
        .inject(Context.current(), record.headers(), setter);
    producer.send(record);
} finally { span.end(); }
Python
from opentelemetry.propagate import inject
from opentelemetry.trace import SpanKind

with tracer.start_as_current_span(
        "order-created publish", kind=SpanKind.PRODUCER):
    headers = {}
    inject(headers)          # 현재 컨텍스트를 dict에 씀
    producer.send(
        "order-created",
        value=payload,
        headers=[(k, v.encode()) for k, v in headers.items()])
Node.js
const { propagation, context, SpanKind } = require('@opentelemetry/api');

await tracer.startActiveSpan('order-created publish',
  { kind: SpanKind.PRODUCER }, async (span) => {
    try {
      const carrier = {};
      propagation.inject(context.active(), carrier);
      await producer.send({
        topic: 'order-created',
        messages: [{ value: payload, headers: carrier }],
      });
    } finally { span.end(); }
  });

소비자 — 컨텍스트 추출

Java
TextMapGetter<Headers> getter = new TextMapGetter<>() { /* 생략 */ };

Context extracted = GlobalOpenTelemetry.getPropagators()
    .getTextMapPropagator()
    .extract(Context.current(), record.headers(), getter);

Span span = TRACER.spanBuilder("order-created process")
    .setParent(extracted)                // 부모로 연결
    .setSpanKind(SpanKind.CONSUMER)
    .startSpan();
try (Scope s = span.makeCurrent()) {
    handle(record);
} finally { span.end(); }
Python
from opentelemetry.propagate import extract

headers = {k: v.decode() for k, v in msg.headers}
ctx = extract(headers)

with tracer.start_as_current_span(
        "order-created process",
        context=ctx,                     # 부모로 연결
        kind=SpanKind.CONSUMER):
    handle(msg)
Node.js
const parentCtx = propagation.extract(context.active(), message.headers);

tracer.startActiveSpan('order-created process',
  { kind: SpanKind.CONSUMER },
  parentCtx,                             // 부모로 연결
  async (span) => {

배치 소비라면 부모 대신 Link

한 번에 100건을 꺼내 처리한다면 부모를 하나로 정할 수 없습니다. 억지로 첫 메시지를 부모로 삼으면 트레이스가 왜곡됩니다. 이럴 때는 소비자 Span을 새 트레이스의 루트로 만들고, 각 메시지에서 추출한 컨텍스트를 Link로 연결합니다. 2편에서 Link가 왜 존재하는지 설명한 그 상황이 바로 여기입니다.

SECTION 09

얼마나 계측할 것인가

수동 계측을 배우고 나면 대부분 과하게 넣습니다. 메서드마다 Span을 만들면 트레이스가 수백 줄이 되고, 읽을 수 없게 되고, 비용이 오릅니다.

Span을 만들어야 할지 판단하기

질문에 답해 가며 판단 기준을 익혀보세요.

실무 기준

적당한 수준

요청 하나당 수동 Span 3~7개 정도. 각 Span이 "이 요청이 거친 의미 있는 단계" 하나에 대응합니다. 트레이스 화면을 열었을 때 한눈에 흐름이 읽혀야 합니다.

과한 수준

요청 하나당 수십~수백 개. 메서드마다, 루프 반복마다 Span을 만든 경우입니다. 정보량은 늘었지만 읽을 수 없고, 전송 비용과 저장 비용이 함께 오릅니다.

하지 말아야 할 것

  • 루프 안에서 Span 생성 — 1000번 도는 루프가 Span 1000개를 만듭니다. 루프 전체를 하나의 Span으로 감싸고 반복 횟수를 속성으로 넣으세요
  • 마이크로초 단위 작업 계측 — Span 생성 비용이 측정 대상보다 큽니다
  • getter·setter 같은 사소한 메서드 — 정보 가치가 없습니다
  • 이미 자동 계측된 구간 중복 계측 — DB 호출을 다시 감싸면 Span이 두 겹이 됩니다
  • Span 이름에 동적 값 넣기 — "process-order-8f3a"처럼 만들면 같은 작업을 묶어 볼 수 없습니다
엔지니어가 먼저 발견하는 경우가 많습니다

과도한 계측은 개발자보다 엔지니어가 먼저 알아챕니다. 특정 서비스의 데이터량만 유독 튀거나 Collector 큐가 적체되기 때문입니다. 이때 필요한 것은 "줄이세요"가 아니라 "요청당 Span 수가 다른 서비스 평균의 20배입니다"라는 구체적 숫자입니다. 이런 데이터를 뽑아 공유하는 것이 9편에서 다룰 Collector 자체 관측의 역할입니다.
