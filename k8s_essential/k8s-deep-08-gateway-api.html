Gateway API 전환 설계

Ingress는 하나의 객체에 인프라 설정과 앱 라우팅을 섞고, 표준에 없는 것은 어노테이션 방언으로 채웠습니다. Gateway API는 이를 누가 무엇을 소유하는가로 쪼갰습니다. 인프라 팀은 GatewayClass와 Gateway를, 앱 팀은 Route를 갖고, 둘 사이의 경계는 allowedRoutes와 ReferenceGrant가 지킵니다. 이 편은 그 경계를 설계하고, 구현체를 고르고, 7편에서 세운 ingress-nginx 이전 계획을 실제 Gateway 구성으로 완성합니다.

기준: Gateway API v1.6 · Envoy Gateway v1.7 · Kubernetes v1.37 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 150분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

이 Route는 Gateway에 붙을까?

인프라 팀이 infra 네임스페이스에 공유 Gateway를 두고, 앱 팀이 자기 네임스페이스에서 HTTPRoute를 만드는 가장 흔한 구성입니다. 조건을 바꾸면 컨트롤러가 Route와 Gateway에 적어 줄 상태 조건(status condition)을 그대로 보여 줍니다. “Route를 만들었는데 아무 일도 안 일어난다”의 원인 대부분이 여기 있습니다.

읽는 법과 목표

    
쉬운 말로
    큰 건물의 출입 관리를 떠올려 보세요. 건물주(인프라 제공자)는 어떤 경비 업체를 쓸지 정하고(GatewayClass), 관리사무소(클러스터 운영자)는 정문과 출입 규칙을 만들며(Gateway), 입주사(앱 팀)는 “우리 회사 손님은 몇 층 어느 방으로”라는 안내판만 붙입니다(Route). 입주사가 정문을 마음대로 바꿀 수 없고, 남의 회사 방으로 손님을 보내려면 그 회사의 서면 허락(ReferenceGrant)이 필요합니다. Ingress는 이 셋을 한 장의 종이에 섞어 쓰던 방식이었습니다.

    

      
이 편을 마치면 할 수 있는 것

      
    
        
  • GatewayClass·Gateway·ListenerSet·Route·ReferenceGrant의 소유 관계를 고객 조직에 맞게 설계하고, RBAC으로 그 경계를 강제할 수 있습니다.
    • 
        
  • Route가 붙지 않거나 백엔드가 500을 돌려줄 때 상태 조건(Accepted·ResolvedRefs·Programmed)으로 원인을 바로 짚을 수 있습니다.
    • 
        
  • 표준(Standard) 기능과 구현 정책을 구분하고, 이식성을 지키는 구성 계층을 나눌 수 있습니다.
    • 
        
  • Envoy Gateway·Cilium·Istio·NGINX Gateway Fabric·Kong과 GKE·AWS·AKS·OpenShift 구현을 비교해 선택할 수 있습니다.
    • 
        
  • 7편의 ingress-nginx 인벤토리를 바탕으로 토폴로지·CRD 채널·정책 매핑·병행 운영을 포함한 이전 설계서를 쓸 수 있습니다.
    •

왜 Gateway API인가

    

      
Ingress의 한계Gateway API의 답

      
        
한 객체에 인프라 설정(LB 종류, 인증서)과 앱 라우팅이 섞임GatewayClass·Gateway(인프라)와 Route(앱)를 분리하고 RBAC으로 나눠 소유

        
표준에 없는 기능은 컨트롤러별 어노테이션 방언헤더 매칭·가중치·리다이렉트·재작성·미러링·CORS를 표준 필드로. 나머지는 정해진 위치의 정책 리소스로

        
HTTP(S)만HTTPRoute·GRPCRoute·TLSRoute·TCPRoute·UDPRoute

        
네임스페이스 경계를 넘는 참조 불가allowedRoutes로 연결 허용 범위를, ReferenceGrant로 교차 참조 허락을 명시

        
어떤 기능이 지원되는지 알 수 없음적합성 테스트와 구현이 공개하는 지원 기능 목록

        
클러스터 내부(동서) 트래픽은 범위 밖Route의 부모를 Service로 두는 메시 연동(GAMMA)

      
    

    

      
버전과 채널

      
Gateway API는 Kubernetes 본체와 별도로 CRD로 배포되고 자체 버전을 가집니다. Standard 채널은 안정 기능만, Experimental 채널은 실험 기능까지 담습니다. 이 구분은 운영에 직접 영향을 줍니다(10장 첫 사례).

    

    

      
버전시기주요 변화

      
        
v1.02023-10GatewayClass·Gateway·HTTPRoute가 GA

        
v1.1~v1.42024~2025GRPCRoute GA, 메시(GAMMA) 지원, 타임아웃·재시도 등 기능 확장, BackendTLSPolicy 등의 단계적 졸업

        
v1.52026-02릴리스 트레인 방식 도입. ListenerSet, TLSRoute v1, HTTPRoute CORS 필터, 클라이언트 인증서 검증, TLS 오리지네이션 인증서 선택이 Standard로. ReferenceGrant v1. 실험 채널 CRD를 Standard 위에 덮어 설치하지 못하게 막는 안전 업그레이드 VAP 포함

        
v1.62026-06TCPRoute·UDPRoute가 Standard(v1)로. 새 실험 리소스는 별도 그룹(gateway.networking.x-k8s.io)과 X 접두사(XBackend 등)로 분리

      
    

    
시니어 포인트: CRD는 클러스터에 하나뿐이다
    Gateway API CRD는 클러스터 전역 리소스라, 한 클러스터에 구현체가 여럿 있어도 CRD 버전과 채널은 하나입니다. 누가 CRD를 설치·업그레이드하는지(사람, 구현체 Helm 차트, 벤더 애드온, OpenShift Ingress Operator, RKE2 번들)를 먼저 정하지 않으면, 한 구현체를 올리다 다른 구현체를 깨뜨립니다. 7장 표에 환경별 CRD 관리 주체를 정리했습니다.

  


  
  

    
2

    
리소스 모델과 역할 분리

    

      
리소스범위소유자하는 일쉬운 말로

      
        
GatewayClass클러스터인프라 제공자(플랫폼 팀·벤더)어느 컨트롤러가 Gateway를 구현할지(controllerName)와 공통 설정(parametersRef)경비 업체 계약

        
Gateway네임스페이스클러스터 운영자진입점 하나: 리스너(포트·프로토콜·호스트 이름·TLS 인증서)와 어떤 Route를 받을지(allowedRoutes)정문과 출입 규칙

        
ListenerSet네임스페이스운영자가 위임한 팀공유 Gateway에 리스너를 덧붙임(v1.5 Standard). 팀별 도메인·인증서를 Gateway를 고치지 않고 추가정문 옆 전용 출입구

        
HTTPRoute 등 Route네임스페이스앱 개발자호스트·경로·헤더 매칭과 필터, 백엔드 Service로 분배층별 안내판

        
ReferenceGrant네임스페이스(대상 쪽)참조를 받는 쪽다른 네임스페이스의 Route·Gateway가 내 Service·Secret을 참조해도 된다는 허락서면 허락서

        
정책(Policy) 리소스네임스페이스운영자 또는 앱 팀Gateway·Route·Service에 붙어 표준 밖 기능을 설정(BackendTLSPolicy는 표준, 나머지는 구현별)특별 지침서

      
    

    

      
RBAC으로 경계 강제하기

      
역할 분리는 문서가 아니라 권한으로 강제해야 합니다. 앱 팀에는 자기 네임스페이스의 Route 쓰기 권한만 주고, Gateway·GatewayClass·ReferenceGrant 쓰기는 주지 않습니다. 가장 놓치기 쉬운 것은 네임스페이스 레이블 수정 권한입니다. allowedRoutes가 레이블 셀렉터로 연결을 허용한다면, 자기 네임스페이스에 레이블을 붙일 수 있는 팀은 스스로 공유 Gateway에 들어올 수 있습니다.

    

    
앱 팀용 Role 예 (18편에서 RBAC 설계 전체를 다룸)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: gateway-route-author
rules:
- apiGroups: ["gateway.networking.k8s.io"]
  resources: ["httproutes", "grpcroutes"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
- apiGroups: ["gateway.networking.k8s.io"]
  resources: ["gateways", "gatewayclasses"]
  verbs: ["get", "list", "watch"]             # 읽기만: 어디에 붙을 수 있는지 확인용
---
# 팀 네임스페이스마다 RoleBinding으로 연결. namespaces 리소스의 patch 권한은 주지 않는다.
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: {name: team-a-routes, namespace: team-a}
roleRef: {apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: gateway-route-author}
subjects: [{kind: Group, name: team-a-devs, apiGroup: rbac.authorization.k8s.io}]

Route 연결 규칙과 ReferenceGrant

    
쉬운 말로
    Route가 실제로 트래픽을 받으려면 두 관문을 통과해야 합니다. 첫째, 정문(Gateway 리스너)이 “그 네임스페이스의 안내판은 받는다”고 허락해야 하고(allowedRoutes), 안내판에 적힌 건물 이름(hostname)이 정문 이름과 겹쳐야 합니다. 둘째, 안내판이 가리키는 방(backend)이 다른 회사 소유라면 그 회사의 허락서(ReferenceGrant)가 있어야 합니다.

    

      
단계규칙실패하면 상태 조건

      
        
부모 지정Route의 parentRefs가 Gateway(필요하면 sectionName으로 특정 리스너, port로 포트)를 가리킴Accepted=False, NoMatchingParent

        
네임스페이스 허용리스너 allowedRoutes.namespaces.from: Same(기본값) / All / Selector(레이블)Accepted=False, NotAllowedByListeners

        
종류 허용allowedRoutes.kinds와 리스너 프로토콜(HTTPS 리스너엔 HTTPRoute, TLS 패스스루엔 TLSRoute 등)Accepted=False, NotAllowedByListeners

        
호스트 이름 교집합리스너 hostname(예: *.apps.example.com)과 Route hostnames가 겹쳐야 함Accepted=False, NoMatchingListenerHostname

        
백엔드 참조다른 네임스페이스 Service를 가리키면 그 네임스페이스에 ReferenceGrant 필요ResolvedRefs=False, RefNotPermitted. 해당 규칙은 HTTP 500을 돌려줌

        
인증서 참조Gateway가 다른 네임스페이스의 TLS Secret을 쓰려면 그쪽에 ReferenceGrant리스너 ResolvedRefs=False, Gateway Programmed 영향

      
    

    

      
여러 Route가 같은 요청에 맞을 때

      
Gateway 하나에 여러 팀의 Route가 붙으면 같은 요청에 여러 규칙이 맞을 수 있습니다. 우선순위는 표준으로 정해져 있습니다: ① Exact 경로 일치 → ② 더 긴 PathPrefix → ③ 메서드 일치 → ④ 헤더 매칭이 더 많은 쪽 → ⑤ 쿼리 매칭이 더 많은 쪽. 그래도 같으면 먼저 만들어진 Route, 그다음 네임스페이스/이름 알파벳 순입니다. 즉 같은 호스트·경로를 두 팀이 쓰면 먼저 만든 팀이 이깁니다. 이것은 사고이자 보안 문제입니다(10장 네 번째 사례).

      
ReferenceGrant 읽는 법

    

    
team-b의 Service를 team-a의 HTTPRoute가 써도 된다는 허락 (team-b에 만든다)
apiVersion: gateway.networking.k8s.io/v1
kind: ReferenceGrant
metadata:
  name: allow-team-a-routes
  namespace: team-b               # 참조를 '받는' 쪽에 둔다
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: team-a             # 누가
  to:
  - group: ""
    kind: Service                 # 무엇을 (name을 적으면 특정 Service만)

    
시니어 포인트: 허락은 받는 쪽이 한다
    ReferenceGrant가 참조하는 쪽이 아니라 참조받는 쪽 네임스페이스에 있는 이유는, 남의 리소스를 쓰겠다는 선언만으로 접근이 열리면 안 되기 때문입니다. 공용 인증서 네임스페이스의 와일드카드 인증서를 여러 Gateway가 쓰는 구성이 대표 사례이며, 이때 인증서 네임스페이스의 ReferenceGrant 쓰기 권한이 곧 “누가 회사 도메인 인증서를 쓸 수 있는가”를 정합니다. 1.5부터 ReferenceGrant는 v1입니다.

표준 밖: 구현 정책

    

      
속도 제한, 외부 인증, WAF, 요청 본문 크기, 접근 로그 형식처럼 표준에 없는 기능은 구현이 제공하는 정책 리소스로 설정합니다. 이 리소스는 Gateway·Route·Service에 targetRef로 붙습니다(정책 첨부). 이식성의 경계가 바로 여기입니다.

    

    

      
구현대표 정책 리소스무엇을 하나

      
        
Envoy GatewayClientTrafficPolicy, BackendTrafficPolicy, SecurityPolicy, EnvoyExtensionPolicy클라이언트 쪽 연결·TLS·IP 감지 / 백엔드 재시도·속도 제한·서킷 브레이커 / 외부 인증·JWT·CORS·IP 허용 / Wasm·외부 처리

        
IstioAuthorizationPolicy, RequestAuthentication, DestinationRule, EnvoyFilter인가·JWT 검증 / 연결 풀·이상 감지 / 저수준 Envoy 수정

        
CiliumCiliumNetworkPolicy(L7), CiliumEnvoyConfigL7 정책, Envoy 직접 설정. 1.20에서 Gateway 외부 인증 지원

        
NGINX Gateway FabricClientSettingsPolicy, UpstreamSettingsPolicy, ObservabilityPolicy, NginxProxy본문 크기·keepalive / 업스트림 설정 / 추적 / 데이터 플레인 전역 설정

B. 팀별 Gateway팀 네임스페이스마다 Gateway(같은 GatewayClass)격리·장애 영역 분리, 팀별 TLS·정책LB·프록시 수만큼 비용규제 분리, 트래픽 큰 팀

  - matches: [{headers: [{name: x-canary, value: "true"}]}]
    backendRefs: [{name: web-v2, port: 80}]
  - backendRefs: [{name: web-v1, port: 80, weight: 90}, {name: web-v2, port: 80, weight: 10}]
EOF
kubectl -n team-a get gateway shared -w            # Programmed까지 수 분
GW=$(kubectl -n team-a get gateway shared -o jsonpath='{.status.addresses[0].value}')
for i in $(seq 1 200); do curl -s http://$GW/hostname; echo; done | sed -E 's/-[a-z0-9]+-[a-z0-9]+$//' | sort | uniq -c
curl -s -H 'x-canary: true' http://$GW/hostname; echo

현장 사례

    
구현체 하나를 올렸더니 다른 구현체가 멈췄다

      
원인. 한 클러스터에 두 Gateway 구현이 있었고, 한쪽 Helm 업그레이드가 Gateway API CRD를 다른 버전·채널로 덮어썼습니다. 다른 구현이 기대하던 필드가 사라져 조정이 실패했습니다.

      
교훈. CRD 설치를 구현체 차트에서 떼어 내 클러스터 단위로 한 곳에서 관리하세요. v1.5 이후에는 안전 업그레이드 VAP가 일부 위험한 덮어쓰기를 막아 주지만, 그것을 끄고 설치하는 일이 없도록 절차를 문서화하세요.

    

    
Route를 만들었는데 트래픽이 안 간다 (오류도 없다)

      
원인. Gateway 리스너의 allowedRoutes를 지정하지 않아 기본값 Same이 적용됐고, 앱 팀의 Route는 다른 네임스페이스에 있었습니다. kubectl apply는 성공했고, Route status에만 Accepted=False가 남았습니다.

      
교훈. Gateway API 장애 진단의 첫 명령은 로그가 아니라 kubectl get httproute -o yaml의 status입니다. 플랫폼 팀은 Route의 Accepted=False를 경보로 만들어 두면 좋습니다.

    

    
교차 네임스페이스 백엔드만 500을 돌려준다

      
원인. 공용 인증 서비스 네임스페이스의 Service를 여러 팀 Route가 가리켰는데, 새 팀에 대한 ReferenceGrant가 없었습니다. 표준에 따라 해당 규칙은 500을 응답했습니다.

      
교훈. ReferenceGrant는 공용 서비스 팀의 “온보딩 체크리스트” 항목입니다. 허락 범위를 Service 이름까지 좁혀 두세요.

    

    
다른 팀의 호스트 이름을 가로챘다

      
상황. 공유 Gateway에서 한 팀이 실수로 다른 팀과 같은 호스트·경로의 Route를 만들었습니다. 우선순위 규칙상 먼저 만든 Route가 이겼지만, 기존 팀이 Route를 다시 만드는 순간 트래픽이 뒤집혔습니다.

      
대응. 네임스페이스별 허용 호스트 이름을 ValidatingAdmissionPolicy로 강제하고, 큰 팀은 전용 ListenerSet으로 분리했습니다.

      
교훈. 공유 Gateway의 보안 경계는 allowedRoutes만으로는 부족합니다. 호스트 이름 소유권을 정책으로 정의해야 합니다.

    

    
관리형 Gateway에서 카나리 단계가 반영되기 전에 다음 단계로 넘어갔다

      
원인. 롤아웃 도구가 30초 간격으로 가중치를 올렸는데, 클라우드 관리형 L7 LB는 설정 반영에 수 분이 걸렸습니다. 지표 분석이 실제로는 이전 비율의 트래픽을 보고 판단했습니다.

      
교훈. 가중치 변경의 반영 지연은 구현마다 다릅니다(실습 4 과제). 롤아웃 단계 간격과 분석 창을 구현에 맞춰 설계하세요.

    

    
OpenShift에서 Gateway를 만들었는데 아무 일도 없다

      
원인. Gateway를 앱 네임스페이스에 만들었습니다. OpenShift 구현은 Gateway가 openshift-ingress에 있어야 합니다. 다른 클러스터에서는 기존 OpenShift Service Mesh 2.x 구독 때문에 경량 OSSM 3 설치가 실패했고, 4.19에서는 그 실패가 조용히 지나갔습니다(4.20부터 ingress ClusterOperator가 Degraded로 보고).

      
교훈. 벤더 구현은 업스트림 표준 위에 배치 규칙과 선행 조건을 얹습니다. 7장 표의 “주의점” 열을 고객 환경 점검표로 쓰세요.

정리, 다음 편, 참고 자료

    

      
이 편의 핵심 다섯 줄

      
    
        
  1. Gateway API는 GatewayClass(인프라 제공자)·Gateway와 ListenerSet(운영자·위임 팀)·Route(앱 팀)·ReferenceGrant(참조받는 쪽)로 소유권을 나누고, 그 경계는 RBAC과 네임스페이스 레이블 권한으로 강제해야 합니다.
    2. 
        
  2. Route는 parentRefs·allowedRoutes(기본 Same)·호스트 이름 교집합을 통과해야 붙고, 교차 네임스페이스 백엔드는 ReferenceGrant 없이는 500이 됩니다. 진단은 status 조건부터 봅니다.
    3. 
        
  3. v1.5에서 ListenerSet·TLSRoute·CORS·ReferenceGrant v1이, v1.6에서 TCPRoute·UDPRoute가 Standard가 됐고, 실험 리소스는 별도 그룹으로 분리됐습니다. CRD는 클러스터에 하나이므로 관리 주체를 정해야 합니다.
    4. 
        
  4. 표준 밖 기능은 구현 정책으로 설정하며, 매니페스트를 표준 Route·Gateway·구현 정책 세 층으로 나누면 이식성을 지킬 수 있습니다.
    5. 
        
  5. 벤더 구현(GKE·AWS LBC·AKS AGC·App Routing·OpenShift)은 데이터 플레인 위치, CRD 관리 주체, 배치 규칙, 반영 지연이 다르므로 이전 설계서에 이를 명시해야 합니다.
    6. 
      

    

    

      
다음 편 · 9편 NetworkPolicy와 네트워크 보안 계층

      
게이트웨이까지 들어온 트래픽이 클러스터 안에서 어디까지 갈 수 있는지를 다룹니다.
