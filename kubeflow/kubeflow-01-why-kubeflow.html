왜 Kubeflow인가

모델 하나가 데이터 과학자의 노트북을 떠나 실제 서비스가 되기까지, 그 길에는 생각보다 많은 정거장이 있습니다. 이번 편에서는 그 길 전체를 노선도로 그려 보고, 각 정거장에서 Kubeflow가 무엇을 맡는지 살펴봅니다.

이번 편에서 얻을 것

이번 편은 설치도, 명령어도 없는 지도 그리기 시간입니다. 앞으로 15편 동안 다룰 내용이 전체 그림의 어디에 놓이는지 머릿속에 자리를 잡아 두는 것이 목표입니다. 이 편을 마치면 다음을 할 수 있습니다.

  • ML 모델을 운영하는 일이 왜 일반 소프트웨어 운영보다 까다로운지, 그래서 MLOps가 왜 필요한지 설명할 수 있습니다.
  • ML 생애주기의 여덟 정거장을 말하고, 각 정거장을 맡는 Kubeflow 구성요소를 짝지을 수 있습니다.
  • Kubeflow가 하나의 프로그램이 아니라 여러 서브프로젝트의 모음이라는 점과, 설치 방식 세 가지의 차이를 압니다.
  • MLflow, Airflow, Ray, 클라우드 관리형 서비스와 비교해 Kubeflow가 맞는 상황과 맞지 않는 상황을 판단할 수 있습니다.
읽는 요령

처음 보는 용어가 나와도 멈추지 말고 계속 읽으세요. 이 편에 나오는 용어는 모두 12장 용어 사전에 정리해 두었습니다. 배경이 서로 다른 분들이 함께 듣는 강의라, 인프라 쪽 용어와 ML 쪽 용어를 모두 풀어 설명합니다.

1이야기로 시작하기

온라인 쇼핑몰 회사의 추천팀을 상상해 봅시다. 데이터 과학자 지은은 상품 추천 모델을 만들고, 인프라 엔지니어 민수는 그 모델을 서비스에 올리는 일을 맡았습니다. 두 사람이 겪는 일을 한 장면씩 넘겨 보세요.

ML 코드는 빙산의 일각

2015년 Google 연구진은 논문 「Hidden Technical Debt in Machine Learning Systems」에서, 실제 운영되는 ML 시스템에서 모델 학습 코드가 차지하는 부분은 아주 작고, 나머지 대부분은 데이터 수집과 검증, 설정 관리, 자원 관리, 서빙 인프라, 모니터링 같은 주변 시스템이라고 지적했습니다. 아래 그림이 그 비율을 거칠게 보여 줍니다. 가운데 파란 칸이 지은이 3주 동안 만든 부분입니다.

칸의 크기는 개념적인 비율입니다. 정확한 측정값이 아니라, 주변 시스템이 훨씬 크다는 점을 보여 주는 그림입니다.

그래서 “모델을 잘 만드는 것”과 “모델로 서비스를 잘 운영하는 것”은 다른 기술입니다. 앞의 것은 데이터 과학의 영역이고, 뒤의 것이 이 강의가 다루는 MLOps의 영역입니다.

2MLOps란 무엇인가

MLOps(Machine Learning Operations)는 ML 모델을 만들고, 배포하고, 운영하고, 다시 개선하는 전 과정을 안정적이고 반복 가능하게 만드는 방법과 문화입니다. 개발과 운영을 하나로 잇는 DevOps의 원칙을 ML에 적용한 것이지만, 그대로 옮겨 올 수는 없습니다. ML에는 일반 소프트웨어에 없는 성질이 있기 때문입니다.

일반 소프트웨어는 손대지 않으면 그대로이지만, ML 모델은 손대지 않아도 시간이 지나면 나빠집니다. 그래서 ML은 “한 번 배포”가 아니라 “계속 다시 만드는” 체계가 필요합니다.

MLOps 성숙도 3단계

Google이 제시한 MLOps 성숙도 모델이 업계에서 널리 쓰입니다. 우리 팀이 지금 어디에 있는지, 어디로 가려는지 가늠하는 잣대로 유용합니다. 슬라이더를 움직여 보세요.

레벨 0레벨 1레벨 2

지은과 민수의 팀은 레벨 0에 있습니다. 대부분의 조직이 여기서 출발합니다. Kubeflow는 레벨 1로 올라가는 데 필요한 부품 대부분을 제공하고, 레벨 2는 Kubeflow에 GitOps와 CI/CD 도구를 함께 엮어 만듭니다(12편).

3ML 생애주기 한 바퀴

ML 생애주기는 직선이 아니라 고리입니다. 모델을 배포하면 끝나는 것이 아니라, 모니터링에서 성능 저하를 발견하면 다시 데이터 준비로 돌아갑니다. 맨 위 노선도의 여덟 정거장을 하나씩 눌러 보세요. 각 정거장에서 하는 일, 도구 없이 할 때 생기는 일, Kubeflow가 맡는 부분을 정리했습니다.

Pipelines는 정거장이면서 선로입니다

노선도에서 파이프라인화는 하나의 정거장이지만, 실제로 Kubeflow Pipelines는 다른 정거장들을 순서대로 이어 자동으로 달리게 하는 선로 역할도 합니다. 데이터 준비, 학습, 튜닝, 등록을 각각 파이프라인의 한 단계로 넣어 한 번에 실행하는 식입니다.

4Kubeflow란 무엇인가

Kubeflow는 Kubernetes 위에서 ML 생애주기의 각 단계를 담당하는 오픈소스 프로젝트들의 모음입니다. 하나의 거대한 프로그램이 아니라, 노트북, 파이프라인, 학습, 튜닝, 모델 레지스트리 같은 일을 각각 맡는 서브프로젝트들이 모인 생태계입니다. 클라우드 네이티브 오픈소스 재단인 CNCF의 인큐베이팅 프로젝트이기도 합니다.

이름은 Kubernetes와 flow를 합친 말입니다. 처음에는 TensorFlow 작업을 Kubernetes에서 쉽게 돌리려는 목적에서 출발했지만, 지금은 PyTorch, JAX, Hugging Face 모델 등 프레임워크와 상관없이 쓰입니다.

네 가지 설계 철학

Kubernetes 네이티브

모든 기능이 Kubernetes 리소스로 표현됩니다. kubectl, GitOps, RBAC처럼 이미 쓰는 Kubernetes 도구와 운영 방식을 그대로 씁니다.

이식성

온프레미스, AWS, Azure, GCP 어디서든 같은 방식으로 동작합니다. 특정 클라우드에 묶이지 않습니다.

조합형

전부 설치할 필요가 없습니다. 파이프라인만, 학습만, 필요한 서브프로젝트만 골라 쓸 수 있습니다.

확장성

노트북 한 대 규모의 실험부터 GPU 수백 장에 걸친 분산 학습까지 같은 도구로 다룹니다.

Kubernetes 네이티브가 정확히 무슨 뜻인가요?

Kubernetes는 원래 Pod, Deployment, Service 같은 기본 리소스만 압니다. 여기에 “분산 학습 작업” 같은 새 리소스 종류를 추가하는 방법이 CRD(Custom Resource Definition)이고, 그 리소스를 실제로 처리하는 전담 프로그램이 Operator(컨트롤러)입니다.

식당에 비유하면, CRD는 새로 만든 주문서 양식이고 Operator는 그 주문서만 전담해서 처리하는 직원입니다. 사용자가 “GPU 2장짜리 노드 2대로 학습해 줘”라는 TrainJob 주문서(YAML)를 내면, Trainer라는 전담 직원이 주문서를 읽고 학습 Pod를 만들고, 상태를 계속 지켜보며 주문서 내용과 맞춥니다. Kubeflow의 거의 모든 구성요소가 이 방식으로 움직입니다.

걸어온 길

  1. 2017년 12월KubeCon North America에서 Google이 처음 공개했습니다. TensorFlow 작업을 Kubernetes에서 쉽게 돌리는 것이 출발점이었습니다.
  2. 2018년 5월KubeCon Europe 2018에서 첫 버전 0.1을 발표했습니다.
  3. 2020년 3월1.0 정식 버전이 나왔습니다.
  4. 2021년모델 서빙을 맡던 KFServing이 KServe로 이름을 바꾸고 독립 프로젝트가 되었습니다. Kubeflow 배포판에는 계속 함께 들어갑니다.
  5. 2023년 7월CNCF 인큐베이팅 프로젝트로 합류했습니다.
  6. 2024년Spark Operator가 Kubeflow 산하 프로젝트가 되었습니다.
  7. 2025년Training Operator의 후속인 Trainer v2와, 여러 구성요소를 하나로 다루는 통합 Kubeflow SDK가 등장했습니다.
  8. 2026년 3월연.월 형식의 캘린더 버전으로 바꾼 첫 릴리스 26.03이 나오고, 묶음 배포판의 이름이 Kubeflow Community Distribution으로 정리되었습니다. 이후 패치에서 Model Registry가 Kubeflow Hub로 이름을 바꿨습니다. 이 강의의 기준 시점입니다.

5Kubeflow 전체 지도

이제 Kubeflow를 이루는 부품들을 층별로 펼쳐 봅시다. 위층일수록 사용자가 직접 만나는 것이고, 아래층일수록 보이지 않는 곳에서 받쳐 주는 것입니다. 각 이름을 누르면 역할과 비유, 다루는 리소스, 이 시리즈에서 자세히 배우는 편을 볼 수 있습니다.

서브프로젝트와 배포판의 관계

Pipelines, Trainer, Katib 같은 서브프로젝트는 각자 별도의 저장소와 릴리스 주기를 가집니다. Community Distribution은 이들을 서로 잘 맞는 버전 조합으로 묶고, Istio, Dex 같은 기반 구성요소와 함께 한 번에 설치할 수 있게 검증한 묶음입니다. 26.03 배포판은 Kubernetes 1.34 이상을 기준으로 하고, Pipelines 2.16, Spark Operator 2.5 등을 포함합니다.

6코드 맛보기

지금 이해할 필요는 없습니다. 앞으로 다룰 것들이 어떻게 생겼는지 얼굴만 익혀 둡시다. 각 코드의 문법은 해당 편에서 한 줄씩 풀어 봅니다.

Pipelines: Python 함수 두 개를 단계로 이어 붙인 파이프라인 (5편)

from kfp import dsl

@dsl.component(base_image="python:3.12")
def prepare_data() -> str:
    return "s3://ml-data/clicks/2026-10.csv"   # 정제된 데이터 위치

@dsl.component(base_image="python:3.12")
def train(data_path: str) -> float:
    print(f"{data_path} 로 학습합니다")
    return 0.92                                  # 검증 정확도

@dsl.pipeline(name="hello-mlops")
def pipeline():
    data = prepare_data()
    train(data_path=data.output)   # 앞 단계의 출력이 다음 단계의 입력

각 함수가 독립된 컨테이너에서 실행되고, 두 단계 사이에 무엇이 오갔는지 자동으로 기록됩니다. 1장 이야기의 “셀 실행 순서에 따라 결과가 달라지는” 문제가 이렇게 사라집니다.

Trainer: 인프라 엔지니어가 쓰는 YAML 주문서 (7편)

apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: recommender-train
spec:
  runtimeRef:
    name: torch-distributed       # 미리 정의된 PyTorch 분산 학습 틀
  trainer:
    image: registry.example.com/recommender-train:1.4
    numNodes: 2                    # 노드 2대에 나눠 학습
    resourcesPerNode:
      limits:
        nvidia.com/gpu: 2         # 노드마다 GPU 2장

Kubeflow SDK: 같은 학습을 데이터 과학자는 Python으로 (10편)

from kubeflow.trainer import TrainerClient, CustomTrainer

def train_fn():
    # 여기에 평소 쓰던 PyTorch 학습 코드를 넣습니다
    ...

client = TrainerClient()
client.train(
    runtime=client.get_runtime("torch-distributed"),
    trainer=CustomTrainer(func=train_fn, num_nodes=2),
)
같은 일, 두 가지 입구

인프라 엔지니어는 YAML과 kubectl로, 데이터 과학자는 Python SDK로 같은 TrainJob을 만듭니다. 결과물은 똑같은 Kubernetes 리소스입니다. 서로 다른 배경의 두 사람이 같은 플랫폼 위에서 일할 수 있게 해 주는 것, 이것이 Kubeflow가 노리는 지점입니다.

7설치 방식 고르기

Kubeflow를 쓰는 방법은 크게 세 가지입니다. 어떤 방식을 고르느냐에 따라 운영 부담과 쓸 수 있는 기능이 크게 달라집니다.

Community Distribution

모든 서브프로젝트와 기반 구성요소(Istio, Dex, cert-manager 등)를 검증된 버전 조합으로 한 번에 설치합니다. kustomize 매니페스트로 배포합니다.

멀티테넌시, 로그인, 대시보드가 모두 들어 있는 완전한 플랫폼. 대신 구성요소가 많아 운영 부담이 가장 큽니다.

서브프로젝트 단독 설치

Pipelines만, Trainer만, KServe만처럼 필요한 것만 골라 설치합니다. 각 프로젝트가 단독 설치 방법을 제공합니다.

가볍고 빠르지만, 로그인과 사용자 격리 같은 플랫폼 기능은 직접 구성해야 합니다.

버전 주기를 미리 알아 두세요

Community Distribution은 1년에 두 번 정도 기본 릴리스를 내고, 커뮤니티 지원은 각 릴리스당 대략 6개월입니다. 직접 운영한다면 반년마다 업그레이드할 각오와 절차가 필요하다는 뜻입니다. 상용 배포판을 검토하는 이유 중 하나가 이것입니다.

9사용 사례

Kubeflow가 실제로 어떤 상황에서 쓰이는지 다섯 가지 장면으로 봅시다. 각 사례에서 어떤 구성요소가 쓰이는지 색으로 표시했습니다. 노선도의 색과 같습니다.

10Kubeflow가 맞지 않는 경우

좋은 도구 소개는 “쓰지 말아야 할 때”를 함께 말해야 합니다. Kubeflow는 구성요소가 많고, 그만큼 운영할 것도 많습니다. 다음 상황이라면 더 가벼운 선택지부터 검토하세요.

운영 부담을 과소평가하지 마세요

Kubeflow 도입이 실패하는 흔한 이유는 기능 부족이 아니라 운영 부담입니다. 설치는 하루면 끝나지만, 반년마다 오는 업그레이드, 구성요소별 보안 패치, 사용자 인증 연동, 스토리지 관리가 계속 이어집니다. 도입 전에 “누가, 얼마나 시간을 들여 운영할 것인가”를 먼저 정하세요. 16편에서 MSP 관점의 운영 체계를 다룹니다.

13확인 퀴즈

여섯 문제로 이번 편을 점검해 봅시다. 답을 고르면 바로 해설이 나옵니다.

14정리와 다음 편

  1. ML 시스템에서 학습 코드는 작은 일부입니다. 데이터, 자원, 배포, 모니터링을 둘러싼 시스템이 훨씬 크고, 이것을 체계로 만드는 일이 MLOps입니다.
  2. ML 모델은 손대지 않아도 시간이 지나면 나빠집니다. 그래서 CI, CD에 더해 지속적 학습(CT)이 필요합니다.
  3. ML 생애주기는 데이터 준비, 탐색, 파이프라인화, 학습, 튜닝, 등록, 서빙, 모니터링으로 이어져 다시 처음으로 돌아가는 고리입니다.
  4. Kubeflow는 하나의 프로그램이 아니라 각 정거장을 맡는 서브프로젝트들의 모음이며, 모두 CRD와 Operator라는 Kubernetes 방식으로 동작합니다.
  5. 전체 배포판, 단독 설치, 상용 배포판 중 무엇을 고를지는 기능 범위, 멀티테넌시 필요성, 운영 인력에 달려 있습니다. 작은 팀이라면 더 가벼운 도구가 맞을 수 있습니다.
다음 편, Level 1 입문

2편: 서로의 언어 배우기

인프라 엔지니어를 위한 ML 기초(학습과 추론, 에폭, 체크포인트, GPU가 하는 일)와 데이터 과학자를 위한 Kubernetes 기초(Pod, CRD, Operator, 네임스페이스, PVC)를 함께 다룹니다. 3편에서 직접 설치하기 전에, 서로 다른 배경의 수강생이 같은 출발선에 서는 편입니다.

이 시리즈의 KServe, OAuth/OIDC, Knative, OpenTelemetry 강의와 이어지는 부분은 해당 편에서 연결해 안내합니다.

Kubeflow 강의 시리즈 1편. 2026년 10월 기준 공개 자료와 Kubeflow Community Distribution 26.03을 바탕으로 작성했습니다. 버전과 이름이 자주 바뀌는 프로젝트이므로 실제 작업 전에는 kubeflow.org 공식 문서를 함께 확인하세요.
