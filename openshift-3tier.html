SECTION 01

3-Tier를 OpenShift 리소스로 매핑하기

3-tier 아키텍처는 20년 넘은 고전적 패턴입니다. WAS 서버 몇 대, 웹 서버 몇 대, DB 한 대 — 이것을 컨테이너 플랫폼으로 옮길 때 가장 먼저 할 일은 "기존의 무엇이 새로운 무엇에 대응되는가"를 정확히 매핑하는 것입니다. 이 매핑이 어긋나면 나머지 모든 설계가 흔들립니다.

같은 목표를 K8s와 OpenShift에서 각각 어떻게 달성하는지 좌우로 나란히 보여주는 패널이 계속 나옵니다. 핵심 메시지는 하나입니다 — OpenShift는 Kubernetes를 대체하지 않고 그 위에 얹힙니다. 여기 나오는 모든 K8s 매니페스트는 OpenShift에서 그대로 동작합니다. 다만 OpenShift가 제공하는 추가 리소스를 쓰면 더 짧고 안전하게 같은 일을 할 수 있습니다.

왜 계층을 나누는가 — 컨테이너 시대의 이유

📈
독립 확장

정적 자원 트래픽과 API 부하는 증가 패턴이 다릅니다. web은 2→10으로, app은 3→5로 각자 스케일합니다.

🔒
격리 경계

DB는 app에서만 접근 가능해야 합니다. NetworkPolicy의 경계선이 곧 계층 경계입니다.

🔄
배포 주기 분리

프론트엔드는 하루 5번, API는 주 1번, DB 스키마는 월 1번. 각자의 릴리스 사이클을 가집니다.

가장 흔한 초기 설계 실수 — 계층을 한 Pod에 담기

"어차피 같이 뜨는데 컨테이너 3개를 한 Pod에 넣으면 안 되나요?" — 안 됩니다. Pod는 스케일링·재시작·배치의 최소 단위입니다. 한 Pod에 담으면 web만 늘릴 수 없고, API가 죽으면 nginx도 함께 재시작되며, DB가 Pod와 함께 옮겨 다닙니다. 사이드카(로그 수집기, 서비스 메시 프록시)처럼 생명주기를 반드시 공유해야 하는 경우에만 한 Pod에 여러 컨테이너를 둡니다.

SECTION 02

Project 전략과 초기 세팅

OpenShift의 Project는 Kubernetes Namespace에 어노테이션과 RBAC 자동 설정을 얹은 것입니다. 실체는 같지만 생성 방식과 부수 효과가 다릅니다.

Kubernetes
kubectl create namespace shop-prod

# 컨텍스트 전환은 별도
kubectl config set-context --current \
  --namespace=shop-prod

# RBAC은 직접 만들어야 한다
kubectl create rolebinding dev-admin \
  --clusterrole=admin --user=dev-kim \
  -n shop-prod
  • 네임스페이스 생성은 클러스터 관리자 권한이 필요
  • 생성자에게 자동 부여되는 권한 없음
  • 표시 이름·설명 개념 없음
OpenShift
oc new-project shop-prod \
  --display-name="쇼핑몰 운영" \
  --description="3-tier 주문관리 (운영)"

# 생성과 동시에 자동 전환됨
oc project shop-dev   # 전환

# 권한 부여도 한 줄
oc adm policy add-role-to-user \
  admin dev-kim -n shop-prod
  • 일반 사용자도 셀프서비스 생성 가능 (self-provisioner)
  • 생성자에게 admin 역할 자동 부여
  • Project 템플릿으로 기본 쿼터·정책 자동 주입 가능

환경 분리 — 어떻게 나눌 것인가

전략구성장점단점
Project 분리 권장shop-dev / shop-stage / shop-prodRBAC·쿼터·정책을 환경별로 다르게. 실수로 운영 건드릴 확률 낮음매니페스트에 네임스페이스 오버레이 필요
계층별 Project 분리shop-web / shop-api / shop-db팀이 다르면 권한 분리가 깔끔계층 간 Service DNS가 길어지고 NetworkPolicy가 복잡해짐
클러스터 분리dev 클러스터 / prod 클러스터완전한 격리. 업그레이드 일정 분리 가능운영 비용 증가. GitOps 필수

이 강의는 환경별 Project 분리 + 한 Project 안에 3계층을 기준으로 진행합니다. 가장 흔하고, NetworkPolicy로 계층 격리가 충분히 가능한 구성입니다.

초기 세팅 — 여기까지가 "배포 전 준비"
# ① Project 생성
oc new-project shop-prod --display-name="쇼핑몰 운영"

# ② 팀 권한 부여 — 역할의 의미를 정확히 알고 줄 것
oc adm policy add-role-to-user admin  lead-park  -n shop-prod  # 팀원 초대 가능
oc adm policy add-role-to-user edit   dev-kim    -n shop-prod  # 배포 가능, RBAC 변경 불가
oc adm policy add-role-to-user view   audit-lee  -n shop-prod  # 읽기. Secret은 제외

# ③ 애플리케이션 전용 ServiceAccount
#    default SA를 쓰지 말 것. 나중에 권한을 좁힐 수 없게 된다.
oc create sa shop-web -n shop-prod
oc create sa shop-api -n shop-prod
oc create sa shop-db  -n shop-prod

# ④ 공통 라벨 정책을 미리 정한다 (모든 리소스에 일관 적용)
#    app.kubernetes.io/* 는 K8s 표준 권장 라벨이다.
#      app.kubernetes.io/part-of: shop        ← 콘솔에서 하나의 앱으로 묶여 보인다
#      app.kubernetes.io/name: shop-api
#      app.kubernetes.io/component: backend
#      app.kubernetes.io/version: 1.4.2
#      tier: web | app | db                   ← NetworkPolicy 셀렉터로 사용

# ⑤ 확인
oc get project shop-prod -o yaml | head -20
oc policy who-can create deployments -n shop-prod
콘솔 토폴로지 뷰를 활용하려면 라벨이 필요하다

OpenShift 웹 콘솔의 Topology 화면은 app.kubernetes.io/part-of 라벨로 리소스를 하나의 애플리케이션 그룹으로 묶어 그려 줍니다. 또 app.openshift.io/connects-to: shop-api 어노테이션을 web Deployment에 붙이면 web → api 화살표가 자동으로 그려집니다. 운영 인계나 리뷰 때 시각적 설명 비용을 크게 줄여 주므로 처음부터 붙여 두는 것을 권합니다. 바닐라 K8s에는 이 기능이 없습니다. OCP

SECTION 03

이미지 만들기 — 세 가지 방법

바닐라 Kubernetes에는 이미지를 만드는 기능이 아예 없습니다. 클러스터는 이미 만들어진 이미지를 받아서 실행할 뿐입니다. OpenShift는 여기서 갈라집니다 — 클러스터 안에서 소스로부터 이미지를 빌드할 수 있습니다.

방법동작3-tier에서의 적합도
S2I (Source-to-Image) OCPGit 소스 + 빌더 이미지 → 실행 가능한 이미지. Dockerfile 불필요App 계층(Spring Boot)에 매우 적합. Web도 가능
Docker 전략 공통리포의 Dockerfile로 빌드 (OpenShift에서는 buildah가 실행)세밀한 제어가 필요할 때. 멀티스테이지 빌드
외부 CI 공통GitHub Actions/GitLab CI 등에서 빌드 → 레지스트리 푸시대기업 표준. 이미 CI가 있다면 그대로 사용
 
# Java 소스만 있으면 된다. Dockerfile도 CI 파이프라인도 없이.
oc new-app \
  registry.redhat.io/ubi9/openjdk-17~https://git.example.com/shop/api.git \
  --name=shop-api \
  --context-dir=/ \
  -l app.kubernetes.io/part-of=shop,tier=app

# 위 한 줄이 만드는 것들:
#   ImageStream  shop-api        ← 빌드 산출물 추적
#   ImageStream  openjdk-17      ← 빌더 이미지 추적
#   BuildConfig  shop-api        ← 빌드 정의
#   Deployment   shop-api        ← 배포
#   Service      shop-api        ← 내부 노출

# 빌드 로그 실시간 확인
oc logs -f bc/shop-api

# 소스 변경 후 재빌드
oc start-build shop-api --follow

# 로컬 디렉터리에서 바로 빌드 (Git 푸시 없이 테스트)
oc start-build shop-api --from-dir=. --follow

# ⚠️ 실전 주의: new-app이 만든 Deployment는 기본 설정이라
#    프로브·리소스·보안 설정이 없다. 프로토타이핑에는 훌륭하지만
#    운영에는 섹션 6의 매니페스트로 교체해야 한다.
# shop-web/Dockerfile — 멀티스테이지. OpenShift 제약을 처음부터 반영한 예시
FROM registry.access.redhat.com/ubi9/nodejs-20 AS builder
WORKDIR /opt/app-root/src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # → /opt/app-root/src/dist

FROM registry.access.redhat.com/ubi9/nginx-124
# UBI nginx 이미지는 이미 비루트(1001)로 실행되도록 만들어져 있다.
# 직접 nginx:alpine 등을 쓰면 섹션 12의 SCC 문제를 만나게 된다.
COPY --from=builder /opt/app-root/src/dist /opt/app-root/src
COPY nginx.conf /opt/app-root/etc/nginx.d/shop.conf
EXPOSE 8080                # 1024 미만 포트는 비루트가 바인딩 못 한다
CMD ["nginx", "-g", "daemon off;"]

# --- OpenShift에서 이 Dockerfile로 빌드 ---
oc new-build --strategy=docker --binary --name=shop-web \
  -l app.kubernetes.io/part-of=shop,tier=web
oc start-build shop-web --from-dir=. --follow

# --- 바닐라 K8s라면 ---
# podman build -t quay.example.com/shop/web:1.4.2 .
# podman push quay.example.com/shop/web:1.4.2
# → 빌드 서버가 별도로 필요하다
# BuildConfig를 매니페스트로 관리하는 형태 (GitOps 대상)
apiVersion: build.openshift.io/v1
kind: BuildConfig
metadata:
  name: shop-api
  namespace: shop-dev
  labels:
    app.kubernetes.io/part-of: shop
    tier: app
spec:
  source:
    type: Git
    git:
      uri: https://git.example.com/shop/api.git
      ref: main
    contextDir: /
    # 사설 리포지터리라면 SSH 키 Secret 참조
    sourceSecret: { name: git-ssh-key }
  strategy:
    type: Source
    sourceStrategy:
      from:
        kind: ImageStreamTag
        name: openjdk-17:latest
      # 빌드 시점 환경변수 (Maven 옵션 등)
      env:
      - { name: MAVEN_ARGS, value: "-DskipTests package" }
      - { name: MAVEN_MIRROR_URL, value: "https://nexus.example.com/repository/maven-public/" }
  output:
    to:
      kind: ImageStreamTag
      name: shop-api:latest
  resources:
    limits: { cpu: "2", memory: 4Gi }   # 빌드 Pod의 자원. 없으면 노드를 흔든다
  successfulBuildsHistoryLimit: 5
  failedBuildsHistoryLimit: 5
  triggers:
  - type: ConfigChange
  - type: ImageChange              # 빌더 이미지 업데이트 시 자동 재빌드
  - type: GitHub                   # 웹훅
    github: { secretReference: { name: github-webhook-secret } }

# 웹훅 URL 확인 (Git 리포지터리에 등록할 주소)
#   oc describe bc shop-api | grep -A2 "Webhook GitHub"
# ImageStream — OpenShift 고유. "이미지에 대한 추상 참조"다.
# 바닐라 K8s는 Deployment에 이미지 태그를 직접 박는다.
#   image: quay.example.com/shop/api:1.4.2
# 이 방식의 문제: 태그가 같아도 내용이 바뀔 수 있고(mutable tag),
#                 롤백하려면 이전 digest를 알아야 한다.

apiVersion: image.openshift.io/v1
kind: ImageStream
metadata:
  name: shop-api
  namespace: shop-prod
spec:
  lookupPolicy: { local: true }   # Deployment에서 짧은 이름으로 참조 가능
  tags:
  - name: "1.4.2"
    from:
      kind: DockerImage
      name: quay.example.com/shop/api:1.4.2
        importPolicy: { scheduled: true }   # 15분마다 원본 변경 확인
    referencePolicy: { type: Local }    # digest로 고정해 참조
  - name: stable                        # 별칭 태그. 승격(promotion)에 사용
    from: { kind: ImageStreamTag, name: "1.4.2" }

# 태그 승격 — dev에서 검증된 이미지를 prod로 (재빌드 없이!)
oc tag shop-dev/shop-api:latest shop-prod/shop-api:stable

# 롤백 — 이전 태그로 되돌리기
oc tag shop-prod/shop-api:1.4.1 shop-prod/shop-api:stable

# 이력 확인
oc describe is shop-api
oc get istag shop-api:stable -o jsonpath='{.image.dockerImageReference}'
ImageStream을 쓸 것인가, 말 것인가

현실적인 판단 기준입니다.

쓰는 것이 유리한 경우 — 클러스터 안에서 빌드하는 경우, 환경 간 이미지 승격(dev→stage→prod)을 재빌드 없이 하고 싶은 경우, 이미지 업데이트 시 자동 재배포(ImageChange 트리거)를 원하는 경우.

안 쓰는 것이 나은 경우 — 이미 성숙한 외부 CI가 있고 GitOps로 Argo CD가 배포를 담당하는 경우입니다. 이때 ImageStream은 Git이 진실이라는 GitOps 원칙과 충돌합니다(클러스터가 스스로 이미지를 바꾸므로). Argo CD를 쓴다면 이미지 태그를 Git에 직접 쓰고 ImageStream은 생략하는 편이 단순합니다.

태그 latest를 운영에 쓰지 말 것

운영 환경에서 latest는 "지금 무엇이 돌고 있는지 아무도 모른다"는 뜻입니다. Pod가 재시작되는 순간 다른 이미지가 뜰 수 있고, 롤백 대상을 특정할 수 없습니다. 운영은 반드시 불변 태그(1.4.2) 또는 digest(@sha256:...)로 고정하십시오. imagePullPolicy도 IfNotPresent가 기본값이 되도록 태그를 고정하는 것이 pull 부하를 줄입니다.

SECTION 04

DB 계층 — PostgreSQL StatefulSet

가장 아래부터 쌓습니다. DB가 없으면 API가 뜰 이유가 없기 때문입니다. DB는 3계층 중 유일하게 상태를 가지므로 Deployment가 아니라 StatefulSet을 씁니다.

왜 Deployment가 아니라 StatefulSet인가

특성DeploymentStatefulSet
Pod 이름랜덤 (shop-api-7d9f-xk2p)순서 고정 (shop-db-0, shop-db-1)
스토리지모든 Pod가 같은 PVC 공유 (또는 없음)volumeClaimTemplates로 Pod마다 전용 PVC
재시작 시새 이름, 새 IP같은 이름, 같은 PVC 재부착
기동 순서동시순차 (0 → 1 → 2)
DNSService 이름만Pod별 안정적 DNS (shop-db-0.shop-db)
단일 인스턴스라도 StatefulSet이 맞다

replicas가 1이어도 StatefulSet을 쓰는 이유는 PVC의 생명주기 때문입니다. Deployment + PVC 조합에서 롤링 업데이트가 일어나면, 새 Pod가 뜨려 하는데 기존 Pod가 아직 RWO 볼륨을 잡고 있어 Multi-Attach error로 교착됩니다. StatefulSet은 기본 전략이 OnDelete에 가까운 순차 교체라 이 문제가 없습니다. Deployment로 DB를 올려야 한다면 반드시 strategy.type: Recreate로 바꿔야 합니다.

        - name: POSTGRESQL_DATABASE
          valueFrom: { configMapKeyRef: { name: shop-db-config, key: database } }
        - name: POSTGRESQL_USER
          valueFrom: { secretKeyRef: { name: shop-db-secret, key: username } }
        - name: POSTGRESQL_PASSWORD
          valueFrom: { secretKeyRef: { name: shop-db-secret, key: password } }
        - name: POSTGRESQL_ADMIN_PASSWORD
          valueFrom: { secretKeyRef: { name: shop-db-secret, key: admin-password } }

        - { name: POSTGRESQL_SHARED_BUFFERS,    value: "1GB" }

          initialDelaySeconds: 10
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3

          exec: { command: ["/usr/libexec/check-container", "--live"] }
          initialDelaySeconds: 120   # 대용량 DB의 복구 시간을 감안해 넉넉히
          periodSeconds: 30
          timeoutSeconds: 10
          failureThreshold: 3

        - { name: initdb, mountPath: /opt/app-root/src/postgresql-start }
        securityContext:
          allowPrivilegeEscalation: false
          capabilities: { drop: [ALL] }
          runAsNonRoot: true
          seccompProfile: { type: RuntimeDefault }
      volumes:

      # 종료 시 정상 셧다운 시간 확보 — 체크포인트가 끝나야 한다

  - metadata: { name: data }
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: gp3-csi   # 환경에 맞게. reclaimPolicy=Retain 권장
      resources: { requests: { storage: 100Gi } }

#   jdbc:postgresql://shop-db.shop-prod:5432/shopdb (다른 네임스페이스)

# 복제 구성(Primary/Replica)으로 확장하면 Headless가 필수가 된다.
# 애플리케이션이 shop-db-0(쓰기)와 shop-db-1(읽기)를 구분해야 하기 때문.
컨테이너 DB를 운영에 쓸 것인가 — 정직한 판단

이 강의는 학습을 위해 컨테이너 PostgreSQL을 씁니다. 실제 운영에서는 세 갈래를 검토하십시오.

  • 외부 관리형 DB(RDS, Azure Database, 온프렘 DBA 관리 서버) — 가장 흔하고 안전한 선택. 클러스터에는 Service의 ExternalName 타입이나 Endpoints를 직접 정의해 연결합니다.
  • Operator 기반(CloudNativePG, Crunchy Postgres, EDB Postgres for Kubernetes) — 자동 페일오버, 백업, 복제, 마이너 업그레이드를 오퍼레이터가 담당합니다. 클러스터 안에서 운영할 거라면 단독 StatefulSet보다 이쪽이 정답에 가깝습니다.
  • 단독 StatefulSet — 개발·검증 환경, 또는 데이터 손실을 감수할 수 있는 워크로드에 한정.
외부 DB에 연결하는 경우 — 두 가지 방법
# 방법 A: ExternalName — DNS CNAME으로 위임 (가장 단순)
apiVersion: v1
kind: Service
metadata: { name: shop-db, namespace: shop-prod }
spec:
  type: ExternalName
  externalName: pgprod.db.example.com
# 애플리케이션은 여전히 "shop-db:5432"로 접속하면 된다.
# → 환경별로 이 Service만 바꾸면 앱 설정은 그대로 유지된다.
# 제약: NetworkPolicy로 통제할 수 없다(클러스터 밖이므로 EgressFirewall 영역).

---
# 방법 B: Endpoints 수동 정의 — IP로 직접 지정
apiVersion: v1
kind: Service
metadata: { name: shop-db, namespace: shop-prod }
spec:
  ports: [{ port: 5432, targetPort: 5432 }]
  # selector 없음! → Endpoints를 직접 만들어야 한다
---
apiVersion: v1
kind: Endpoints
metadata: { name: shop-db, namespace: shop-prod }  # Service와 이름 동일
subsets:
- addresses: [{ ip: 10.20.30.40 }]
  ports: [{ port: 5432 }]

SECTION 06

App 계층 — API Deployment 설계

App 계층은 무상태(stateless)입니다. 어떤 Pod가 요청을 받아도 결과가 같아야 하고, 아무 때나 죽여도 되어야 합니다. 이 성질이 확보되면 스케일링과 무중단 배포가 자연스럽게 따라옵니다.

운영 수준 Deployment의 필수 구성 요소

JVM 애플리케이션의 고전적 함정 — 컨테이너 메모리 인식

JVM은 기본적으로 호스트 전체 메모리를 기준으로 힙 크기를 정하려 합니다. 노드가 64GiB인데 컨테이너 limit이 2GiB라면, JVM은 힙을 16GiB까지 늘리려다 cgroup 한계를 넘어 OOMKilled(exitCode 137)로 죽습니다.

JDK 10+ 는 UseContainerSupport가 기본 활성이라 cgroup을 인식하지만, 기본 MaxRAMPercentage가 25%라 2GiB limit에서 힙이 512MiB밖에 안 됩니다. 명시적으로 -XX:MaxRAMPercentage=70 정도를 지정하십시오. 나머지 30%는 메타스페이스, 스레드 스택, 네이티브 버퍼가 씁니다.

DeploymentConfig는 이제 쓰지 않는다

예전 OpenShift 문서에는 DeploymentConfig(DC)가 자주 등장합니다. Deployment보다 먼저 나온 OpenShift 고유 리소스로, ImageChange 트리거와 배포 훅(mid/pre/post)을 제공했습니다. OCP 4.14부터 deprecated이며 신규 개발에는 표준 Deployment를 씁니다. 이유는 명확합니다 — 생태계 도구(Helm, Kustomize, Argo CD, HPA)가 모두 Deployment를 전제로 만들어져 있습니다. 기존 DC가 있다면 Deployment로 마이그레이션하고, 필요했던 훅 기능은 initContainer나 Argo CD Hook, Tekton Task로 대체하십시오.

가장 파괴적인 실수 — livenessProbe에 DB 체크를 넣기

Spring Boot의 기본 /actuator/health는 DB, Redis, 디스크 등 모든 의존성을 종합해 판단합니다. 이걸 livenessProbe에 그대로 쓰면 어떤 일이 벌어질까요?

DB가 30초간 느려지는 순간 → 모든 API Pod의 liveness가 실패 → API Pod 전체가 동시에 재시작 → 재시작한 Pod들이 일제히 DB에 커넥션을 요청 → DB가 더 느려짐 → 무한 반복. 일시적 성능 저하가 전면 장애로 증폭되는 전형적인 패턴입니다.

규칙 — liveness는 오직 "이 프로세스가 응답하는가"만 봅니다. 의존성 상태는 readiness의 몫입니다. Spring Boot 2.3+ 는 이를 위해 /actuator/health/liveness(프로세스만)와 /actuator/health/readiness(의존성 포함)를 분리해 제공합니다.

# application.yaml — liveness/readiness 그룹 분리 활성화
management:
  endpoint:
    health:
      probes: { enabled: true }
      show-details: when-authorized
      group:
        readiness:
          # DB가 죽으면 트래픽을 받지 않는다 (재시작은 하지 않는다)
          include: [readinessState, db]
        liveness:
          # 프로세스 상태만. 의존성을 절대 넣지 않는다.
          include: [livenessState]
  endpoints:
    web:
      exposure: { include: [health, info, prometheus] }

# --- 파라미터 의미 ---
#   initialDelaySeconds : 첫 검사까지 대기. startupProbe가 있으면 불필요.
#   periodSeconds       : 검사 주기
#   timeoutSeconds      : 응답 대기 한계 (기본 1초 — 너무 짧다. 3초 권장)
#   successThreshold    : 성공 판정에 필요한 연속 성공 횟수 (liveness는 1 고정)
#   failureThreshold    : 실패 판정에 필요한 연속 실패 횟수
#
# 감지까지 걸리는 최대 시간 = periodSeconds × failureThreshold + timeoutSeconds
#   readiness 5s × 3 + 3s = 최대 18초 후 Endpoints에서 제거
startupProbe가 해결하는 문제

startupProbe가 없던 시절에는 딜레마가 있었습니다. Spring Boot가 뜨는 데 90초가 걸린다면 livenessProbe.initialDelaySeconds를 120초로 잡아야 합니다. 그런데 그러면 운영 중 앱이 hang됐을 때도 120초를 기다려야 감지됩니다.

startupProbe는 이 둘을 분리합니다. 기동 중에는 startupProbe만 동작하고, 한 번 성공하면 그 이후로는 다시 실행되지 않습니다. 그때부터 liveness가 periodSeconds: 15, failureThreshold: 3 같은 짧은 주기로 감시할 수 있습니다. 기동은 관대하게, 운영 중에는 민감하게 — 이것이 정답입니다.

SECTION 08

Service와 계층 간 내부 통신

Pod IP는 재시작마다 바뀝니다. Service는 그 위에 고정된 이름과 가상 IP를 얹어 "누가 뜨고 지든 이 이름으로 부르면 된다"를 보장합니다. 3-tier에서 계층 간 결합은 전적으로 Service를 통합니다.

app/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: shop-api
  namespace: shop-prod
  labels: { app.kubernetes.io/part-of: shop, tier: app }
  annotations:
        # OCP 전용: 클러스터 CA가 서명한 TLS 인증서를 자동 발급·자동 갱신
    service.beta.openshift.io/serving-cert-secret-name: shop-api-tls
spec:
  type: ClusterIP           # 기본값. 클러스터 내부에서만 접근 가능
  selector:
    app.kubernetes.io/name: shop-api   # Pod 라벨과 일치해야 한다
  ports:
  - name: http            # 이름 필수! ServiceMonitor가 이 이름을 참조한다
    port: 8080            # Service가 노출하는 포트
    targetPort: http      # Pod의 포트 "이름"
    protocol: TCP

Service 타입과 3-tier에서의 선택

타입노출 범위3-tier에서
ClusterIP클러스터 내부만app, db 계층의 정답. web도 ClusterIP + Route 조합

OpenShift에는 kube-proxy가 없다

바닐라 K8s에서 Service의 부하분산은 각 노드의 kube-proxy가 iptables(또는 IPVS) 규칙을 관리해 처리합니다. OVN-Kubernetes를 쓰는 OpenShift에서는 OVN 로드밸런서가 그 역할을 합니다.

실무적 차이는 디버깅 방법입니다. iptables-save | grep <clusterIP>로 규칙을 찾는 습관은 OpenShift에서 통하지 않습니다. 대신 OVN 로드밸런서 테이블을 봅니다. 다만 일상 운영에서는 이 차이를 의식할 필요가 거의 없습니다 — oc get endpoints가 정상이면 그 아래는 플랫폼이 알아서 합니다.

# ② readinessProbe — "새 Pod가 진짜 준비됐는지" 판단 근거
# 이게 없으면 kubelet은 컨테이너 프로세스가 뜨는 즉시 Ready로 표시한다.

# ③ graceful shutdown — 종료되는 Pod가 처리 중인 요청을 끝내게 한다
lifecycle:
  preStop:
    exec: { command: ["/bin/sh", "-c", "sleep 10"] }
terminationGracePeriodSeconds: 45
# + 애플리케이션 설정: server.shutdown=graceful
preStop에 sleep을 넣는 이유 — 경쟁 조건 해소

Pod 삭제가 시작되면 두 가지 일이 동시에, 병렬로 일어납니다.

  1. kubelet이 컨테이너에 SIGTERM을 보낸다
  2. Endpoints 컨트롤러가 이 Pod를 Endpoints에서 제거하고, 그 변경이 라우터·OVN 로드밸런서까지 전파된다

문제는 2번이 느리다는 것입니다. 전파에 수 초가 걸리는 동안 애플리케이션은 이미 종료를 시작했고, 그 사이 도착한 요청은 Connection refused가 됩니다.

preStop의 sleep 10은 SIGTERM 전송을 10초 지연시킵니다. 그동안 애플리케이션은 정상 동작하면서 Endpoints 제거가 전파되기를 기다립니다. 10초 후 SIGTERM을 받고, graceful shutdown으로 진행 중인 요청만 마무리한 뒤 종료합니다. 이 한 줄이 배포 중 5xx 에러의 대부분을 제거합니다.

Web 계층 — 프론트엔드 배포

Web 계층은 두 가지 일을 합니다. 정적 자원 서빙(HTML/JS/CSS)과 API 리버스 프록시입니다. 두 번째가 중요한 이유는 브라우저의 CORS 제약을 회피하고, API를 외부에 직접 노출하지 않아도 되게 만들기 때문입니다.

브라우저 → https://shop.apps.ocp.example.com/단일 도메인
↓ Route (TLS 종료)
nginx — / 정적 파일, /api/ 프록시shop-web :8080
↓ 내부 ClusterIP (TLS 없음 또는 mTLS)
Spring Boot APIshop-api :8080
왜 API를 별도 Route로 노출하지 않는가

API에 별도 도메인(api.shop.example.com)을 주면 브라우저가 교차 출처 요청으로 판단해 CORS 헤더 설정, preflight 요청, 쿠키 SameSite 문제가 줄줄이 따라옵니다. 같은 도메인 아래 /api/ 경로로 프록시하면 이 모든 것이 사라집니다.

모바일 앱이나 외부 파트너가 API를 직접 호출해야 한다면 그때 별도 Route를 추가하되, 인증·레이트리밋을 반드시 함께 설계하십시오. 웹 프론트엔드 전용이라면 프록시 방식이 정답입니다.

        root /opt/app-root/src;

        gzip on;
        gzip_types text/plain text/css application/javascript application/json image/svg+xml;
        gzip_min_length 1024;

        add_header X-Content-Type-Options nosniff always;
        add_header X-Frame-Options DENY always;
        add_header Referrer-Policy strict-origin-when-cross-origin always;

        location = /healthz {
            access_log off;
            return 200 "ok\n";

        location ~* \.(js|css|woff2|png|jpg|svg)$ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }

        # index.html은 절대 캐시하지 않는다 (배포해도 구버전이 뜨는 원인)
        location = /index.html {
            add_header Cache-Control "no-store, must-revalidate";
        }

        # API 프록시
        location /api/ {
            proxy_pass http://shop-api:8080/api/;
            proxy_http_version 1.1;
            proxy_set_header Host              $host;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto;
            proxy_connect_timeout 5s;
            proxy_read_timeout    60s;
            # 스트리밍 응답(SSE)이 있다면
            proxy_buffering off;
        }

        # SPA 라우팅 — 없는 경로는 index.html로
        location / {
            try_files $uri $uri/ /index.html;
        }
    }

여기가 OpenShift와 바닐라 Kubernetes의 차이가 가장 극명한 지점입니다. 바닐라에서는 Ingress Controller 설치, 와일드카드 DNS 등록, TLS 인증서 관리를 직접 해야 합니다. OpenShift는 설치 시점에 이 셋이 모두 구성되어 있습니다.

Kubernetes — Ingress
# 0) 사전 작업 (수 시간~수 일)
#    - Ingress Controller 설치 (nginx/traefik)
#    - LoadBalancer 또는 NodePort 노출
#    - DNS 레코드 등록
#    - cert-manager 설치 + ClusterIssuer 구성

apiVersion: networking.k8s.io/v1

Route는 경로 기반 라우팅이 약하다

Route에도 spec.path가 있지만 prefix 매칭만 지원하고, Ingress처럼 하나의 객체에 여러 경로 규칙을 담을 수 없습니다. 경로마다 Route를 따로 만들어야 합니다.

복잡한 경로 라우팅이 필요하다면 세 가지 선택지가 있습니다 — ① 이 강의처럼 nginx에서 프록시(가장 단순하고 흔함), ② Ingress 객체를 사용(OpenShift가 Route로 자동 변환), ③ 서비스 메시(OpenShift Service Mesh)의 VirtualService. 3-tier 규모에서는 ①이 정답입니다.

SECTION 12

SCC 대응 — 컨테이너를 OpenShift에 맞추기

Docker Hub에서 받은 이미지가 "쿠버네티스에서는 되는데 OpenShift에서는 안 된다"는 경험, OpenShift를 처음 쓰는 팀이 거의 반드시 겪습니다. 원인은 하나 — Security Context Constraints입니다.

OpenShift의 기본 전제 — 컨테이너는 임의의 비루트 UID로 실행된다

기본 SCC인 restricted-v2는 Pod에 네임스페이스마다 다른, 예측 불가능한 UID(예: 1000750000)를 할당합니다. 이미지의 USER 지시자는 무시됩니다.

왜 이렇게 하는가? 컨테이너 탈출 취약점이 발생해도 호스트에서 의미 있는 권한을 갖지 못하게 하기 위해서입니다. 바닐라 K8s는 아무것도 지정하지 않으면 root(UID 0)로 실행됩니다 — 편하지만 위험합니다. 이 차이가 OpenShift의 보안 철학입니다.

전형적인 실패와 원인

이미지가 USER node(UID 1000)를 가정하고 /app 디렉터리를 chown node:node로 만들어 뒀는데, 실제 실행 UID는 1000750000입니다. 소유자가 아니므로 쓰기 실패.

해결 — 쓰기가 필요한 경로의 그룹을 root(GID 0)로 만들고 그룹 쓰기 권한을 줍니다. OpenShift는 임의 UID를 할당하되 보조 그룹은 항상 0이기 때문입니다.

# Dockerfile
RUN mkdir -p /app/data /app/logs \
 && chgrp -R 0 /app \
 && chmod -R g=u /app        # 그룹 권한을 소유자와 동일하게
USER 1001                     # 기본값 표시용 (OCP에서는 덮어써짐)

이 두 줄이 "OpenShift 호환 이미지"의 핵심 관용구입니다. Red Hat UBI 기반 이미지는 이미 이렇게 되어 있으므로 문제가 없습니다.

공식 nginx 이미지는 80번 포트에서 리스닝합니다. 1024 미만 포트는 CAP_NET_BIND_SERVICE 권한이 필요한데, restricted-v2는 모든 capability를 제거합니다.

해결 — 포트를 8080 같은 비특권 포트로 바꿉니다. Service가 8080을 80으로 매핑하면 외부에서는 아무 차이가 없습니다.

# nginx.conf
listen 8080;
# pid 파일과 임시 경로도 쓰기 가능한 곳으로
pid /tmp/nginx.pid;
client_body_temp_path /tmp/client_body;
proxy_temp_path /tmp/proxy;

# 또는 UBI nginx 이미지를 쓰면 이 모든 게 이미 되어 있다
#   registry.access.redhat.com/ubi9/nginx-124

할당된 UID가 /etc/passwd에 없어서 발생합니다. 대부분은 무해하지만, 일부 애플리케이션(Java의 일부 라이브러리, Git, SSH)은 사용자 이름을 조회하다 실패합니다.

해결 — nss_wrapper를 쓰거나, /etc/passwd를 쓰기 가능하게 만들어 엔트리포인트에서 동적으로 추가합니다.

# Dockerfile
RUN chgrp 0 /etc/passwd && chmod g=u /etc/passwd

# entrypoint.sh
if ! whoami &>/dev/null && [ -w /etc/passwd ]; then
  echo "app:x:$(id -u):0:app user:${HOME}:/sbin/nologin" >> /etc/passwd
fi
exec "$@"

블록 스토리지(RWO)는 fsGroup이 지정되면 마운트 시 볼륨 소유 그룹을 변경해 줍니다. restricted-v2는 fsGroup: MustRunAs로 네임스페이스 범위의 GID를 자동 할당하므로 대개 자동 해결됩니다.

문제가 되는 것은 NFS 등 공유 파일시스템입니다. 서버 측 no_root_squash 설정이나 고정 UID/GID 정책과 충돌합니다. 이때는 supplementalGroups로 NFS 익스포트가 허용하는 GID를 명시하고, 그 GID를 허용하는 커스텀 SCC를 만듭니다.

securityContext:
  supplementalGroups: [5555]   # NFS 익스포트의 그룹
  fsGroup: 5555
# → 이 GID를 허용하는 커스텀 SCC 필요 (RunAsAny 또는 명시적 범위)

"일단 privileged 주고 넘어가자"의 대가

급할 때 oc adm policy add-scc-to-user privileged -z myapp로 넘어가는 팀이 많습니다. 이것은 호스트 커널에 대한 사실상 전권을 주는 것입니다 — hostPath로 노드 파일시스템 접근, hostNetwork로 네트워크 스택 접근, 모든 capability. 컨테이너 하나가 뚫리면 노드 전체가 뚫립니다.

또한 한 번 이렇게 나가면 되돌리기가 매우 어렵습니다. 보안 감사에서 가장 먼저 지적받는 항목이며, 금융권 심사에서는 그 자체로 부적합 판정 사유가 됩니다.

올바른 순서 — ① 이미지를 고칠 수 있는가? (대부분 가능. 위 아코디언 참고) → ② 안 되면 정확히 필요한 권한만 담은 커스텀 SCC를 만들고 전용 SA에만 부여 → ③ privileged는 정말 최후의 수단.

불가피한 경우 — 최소 권한 커스텀 SCC
# 예: 레거시 이미지가 UID 1001 고정을 요구하지만 호스트 접근은 불필요한 경우
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata: { name: shop-legacy-uid }
priority: 5

# 허용하는 것 — 고정 UID만
runAsUser:
  type: MustRunAsRange
  uidRangeMin: 1001
  uidRangeMax: 1001

# 거부하는 것 — privileged와의 결정적 차이가 여기 있다
allowPrivilegedContainer: false
allowHostDirVolumePlugin: false   # hostPath 금지 ← 가장 중요
allowHostNetwork: false
allowHostPorts: false
allowHostPID: false
allowHostIPC: false
allowPrivilegeEscalation: false
requiredDropCapabilities: [ALL]

seLinuxContext: { type: MustRunAs }
fsGroup: { type: MustRunAs }
supplementalGroups: { type: RunAsAny }
volumes: [configMap, downwardAPI, emptyDir, persistentVolumeClaim, projected, secret]

---
# 부여는 전용 SA에만. 절대 그룹 전체에 주지 말 것.
apiVersion: rbac.authorization.k8s.io/v1

metadata: { name: use-legacy-scc, namespace: shop-prod }

- apiGroups: [security.openshift.io]
  resources: [securitycontextconstraints]
  resourceNames: [shop-legacy-uid]
  verbs: [use]

- { kind: ServiceAccount, name: shop-legacy }

SCC와 Pod Security Admission은 함께 동작한다

K8s 표준인 PSA가 OCP 4.11부터 SCC와 동시에 적용됩니다. 역할이 다릅니다 — SCC는 Mutating 단계에서 값을 채워 주고, PSA는 Validating 단계에서 검증만 합니다.

실무적 의미는 이렇습니다. 이 강의의 매니페스트처럼 allowPrivilegeEscalation: false, runAsNonRoot: true, capabilities.drop: [ALL], seccompProfile: RuntimeDefault를 명시적으로 써 두면 SCC의 restricted-v2도, PSA의 restricted 프로파일도 동시에 만족합니다. 보너스로 그 매니페스트는 바닐라 Kubernetes에서도 그대로 동작합니다. 이식성과 보안을 동시에 얻는 방법입니다.

차단은 거절이 아니라 드롭이다

NetworkPolicy로 막힌 트래픽은 Connection refused가 아니라 무응답(타임아웃)으로 나타납니다. 애플리케이션 입장에서는 "연결이 안 된다"가 아니라 "매우 느리다"로 보입니다. 그래서 정책 실수는 성능 문제로 오인되기 쉽습니다.

커넥션 타임아웃을 짧게(3~5초) 설정해 두면 이런 상황을 빨리 발견할 수 있습니다. Spring Boot라면 spring.datasource.hikari.connection-timeout=5000, nginx라면 proxy_connect_timeout 5s입니다.

OpenShift가 추가로 제공하는 통제 수단

NetworkPolicy는 K8s 표준이라 양쪽 모두 동일합니다. OpenShift는 여기에 세 가지를 더합니다.

  • EgressFirewall — 네임스페이스 단위 외부 목적지 제한. DNS 이름으로 지정 가능 (NetworkPolicy는 IP만 가능). "registry.redhat.io만 허용" 같은 정책을 쓸 수 있습니다.
  • EgressIP — 이 네임스페이스가 외부로 나갈 때 고정 출발지 IP를 부여. 기존 방화벽이 IP 기반 정책을 쓰는 엔터프라이즈에서 사실상 필수입니다.
  • AdminNetworkPolicy — 클러스터 관리자가 강제하는 정책. 네임스페이스 소유자가 무력화할 수 없고 명시적 Deny를 쓸 수 있습니다.
SECTION 14

스케일링 · PDB · 쿼터

3계층은 각자 다른 속도로 늘어납니다. web은 동시 접속자 수에, app은 요청 처리량에, db는 보통 늘지 않고 수직으로만 커집니다. 이 비대칭을 설계에 반영하는 것이 이 섹션의 목표입니다.

hpa.yaml — web과 app에 각각 다른 기준
# ═══ web — 동시 접속에 반응. 가볍고 빠르게 늘린다 ═══
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: shop-web, namespace: shop-prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: shop-web }
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies: [{ type: Percent, value: 100, periodSeconds: 30 }]
    scaleDown:
      stabilizationWindowSeconds: 300
      policies: [{ type: Percent, value: 50, periodSeconds: 60 }]

---
# ═══ app — 메모리도 함께 본다. 늘리는 속도는 보수적으로 ═══
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: shop-api, namespace: shop-prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: shop-api }
  minReplicas: 3
    maxReplicas: 8   # DB 커넥션 한계에서 역산한 값. 아래 계산 참고.
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }
  - type: Resource
    resource:
      name: memory
      target: { type: Utilization, averageUtilization: 80 }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies: [{ type: Pods, value: 2, periodSeconds: 60 }]
    scaleDown:
      stabilizationWindowSeconds: 600   # JVM 워밍업 비용을 고려해 길게
      policies: [{ type: Pods, value: 1, periodSeconds: 120 }]

# ═══ DB 커넥션에서 maxReplicas 역산하기 — 반드시 해야 하는 계산 ═══
#   PostgreSQL max_connections     : 200
#   관리·백업·모니터링 예약        : -20
#   애플리케이션 가용               : 180
#   Pod당 HikariCP maximumPoolSize : 20
#   → 최대 Pod = 180 / 20 = 9
#   → 롤링 배포 시 maxSurge 1을 감안해 maxReplicas = 8
#
# 이 계산을 안 하면 트래픽 급증 시 HPA가 Pod를 늘리다가
# "FATAL: sorry, too many clients already"로 전면 장애가 난다.
# 부하가 커질수록 더 크게 실패하는 최악의 형태다.
#
# 더 큰 규모가 필요하면 PgBouncer 같은 커넥션 풀러를 앞에 두어
# Pod 수와 DB 커넥션 수를 분리한다.
pdb.yaml — 노드 작업 중에도 서비스를 지킨다
# PDB는 "자발적 중단"(노드 drain, 클러스터 업그레이드, Descheduler)으로부터 보호한다.
# 노드 장애 같은 비자발적 중단은 막지 못한다.
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: shop-web, namespace: shop-prod }

    matchLabels: { app.kubernetes.io/name: shop-web }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: shop-api, namespace: shop-prod }
spec:
  # HPA로 replicas가 변하는 워크로드는 비율(%)이 안전하다
  maxUnavailable: "25%"
  selector:
    matchLabels: { app.kubernetes.io/name: shop-api }

#    노드 drain이 영원히 멈춘다. 클러스터 업그레이드가 통째로 막힌다.
#    이것이 "MCP가 UPDATING에서 몇 시간째 멈춤"의 대표적 원인이다.
#
# 단일 인스턴스 DB의 선택지:
#   ① PDB를 아예 만들지 않는다 (짧은 다운타임 허용)
#   ② maxUnavailable: 1 로 두어 drain을 허용한다
#   ③ 복제 구성으로 replicas를 2 이상으로 만든 뒤 PDB를 건다  ← 정석

부하 테스트 없이 HPA를 켜지 말 것

HPA는 지표를 보고 반응할 뿐, 애플리케이션의 실제 병목이 어디인지 모릅니다. CPU가 아니라 DB 커넥션, 외부 API 응답, 디스크 IO가 병목이라면 Pod를 늘려도 처리량이 늘지 않고 DB만 더 괴롭힙니다.

순서는 이렇습니다 — ① 단일 Pod의 처리 한계를 부하 테스트로 측정 (k6, JMeter, hey) → ② 그때 어떤 지표가 먼저 포화되는지 확인 → ③ 그 지표를 HPA 기준으로 사용 → ④ maxReplicas를 하위 의존성(DB 커넥션)에서 역산.

SECTION 15

관측성 — 로그 · 메트릭 · 알림

3-tier의 관측성에서 가장 중요한 질문은 "장애가 어느 계층에서 시작됐는가"입니다. 사용자는 "느리다"고만 말합니다. 계층별 지표를 나란히 볼 수 있어야 원인을 특정할 수 있습니다.

모니터링 스택 — 구축이냐, 설정이냐

바닐라 Kubernetes에서 Prometheus 스택을 갖추려면 kube-prometheus-stack Helm 차트 설치, 스토리지 구성, Grafana 배포, Alertmanager 라우팅 설정, RBAC 조정을 직접 해야 합니다. 보통 며칠에서 몇 주가 걸립니다.

OpenShift는 Prometheus + Alertmanager + Thanos + 콘솔 대시보드가 이미 실행 중입니다. 사용자 워크로드 모니터링(UWM)만 켜면 애플리케이션 메트릭도 같은 스택에서 수집됩니다. "구축"이 아니라 "설정" 수준의 작업입니다. OCP

# PostgreSQL도 마찬가지 (postgres_exporter)

# ① Targets 화면: Console → Observe → Targets → shop-api가 UP인지

# OpenShift Pipelines (Tekton) — 3-tier 앱의 표준 파이프라인
apiVersion: tekton.dev/v1
kind: Pipeline
metadata: { name: shop-api-pipeline, namespace: shop-cicd }
spec:
  params:
  - { name: git-url,      type: string }
  - { name: git-revision, type: string, default: main }
  - { name: image,        type: string }
  workspaces:
  - { name: source }
  - { name: maven-cache }
  - { name: dockerconfig }
  tasks:
  - name: clone
    taskRef: { name: git-clone, kind: ClusterTask }
    workspaces: [{ name: output, workspace: source }]
    params:
    - { name: url,      value: "$(params.git-url)" }
    - { name: revision, value: "$(params.git-revision)" }

  # 병렬 실행 — runAfter가 같으면 동시에 시작된다
  - name: unit-test
    runAfter: [clone]
    taskRef: { name: maven, kind: ClusterTask }
    workspaces:
    - { name: source,     workspace: source }
    - { name: maven-repo, workspace: maven-cache }
    params: [{ name: GOALS, value: [test] }]
  - name: sast
    runAfter: [clone]
    taskRef: { name: sonarqube-scanner }
    workspaces: [{ name: source, workspace: source }]

  - name: build
    runAfter: [unit-test, sast]
    taskRef: { name: buildah, kind: ClusterTask }
    workspaces:
    - { name: source,       workspace: source }
    - { name: dockerconfig, workspace: dockerconfig }
    params: [{ name: IMAGE, value: "$(params.image)" }]

  # 이미지 취약점 스캔 — 통과해야 배포된다
  - name: image-scan
    runAfter: [build]
    taskRef: { name: trivy-scanner }
    params:
    - { name: IMAGE_PATH, value: "$(params.image)" }
    - { name: ARGS, value: ["--severity", "HIGH,CRITICAL", "--exit-code", "1"] }

  # 배포 방식 A: 직접 배포 (GitOps를 쓰지 않는 경우)
  - name: deploy-dev
    runAfter: [image-scan]
    taskRef: { name: openshift-client, kind: ClusterTask }

  finally:

# pg_dump 기반 논리 백업 — 이식성이 좋고 부분 복원이 가능하다
apiVersion: batch/v1
kind: CronJob
metadata: { name: shop-db-backup, namespace: shop-prod }
spec:
  schedule: "0 3 * * *"            # 매일 03:00
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        metadata:
          labels: { tier: app }   # NetworkPolicy상 DB 접근이 가능한 계층으로
        spec:
          restartPolicy: Never
          serviceAccountName: shop-db
          containers:
          - name: backup
            image: registry.redhat.io/rhel9/postgresql-16:latest
            command: ["/bin/bash", "-c"]
            args:
              - |
                set -euo pipefail
                TS=$(date +%Y%m%d-%H%M%S)
                FILE=/backup/shopdb-${TS}.dump
                echo "backup start: ${FILE}"
                pg_dump -h shop-db -U "$PGUSER" -d shopdb \
                        -Fc -Z6 -f "${FILE}"
                ls -lh "${FILE}"
                # 7일 이상 된 백업 정리
                find /backup -name 'shopdb-*.dump' -mtime +7 -delete
                echo "backup done"
            env:
            - name: PGUSER
              valueFrom: { secretKeyRef: { name: shop-db-secret, key: username } }
            - name: PGPASSWORD
              valueFrom: { secretKeyRef: { name: shop-db-secret, key: password } }
            resources:
              requests: { cpu: "200m", memory: 512Mi }
              limits:   { cpu: "1",    memory: 2Gi }
            securityContext:
              allowPrivilegeEscalation: false
              capabilities: { drop: [ALL] }
            volumeMounts:
            - { name: backup, mountPath: /backup }
          volumes:
          - name: backup
            persistentVolumeClaim: { claimName: shop-db-backup }

3-Tier에서 자주 나오는 케이스

502는 중간 프록시가 백엔드로부터 잘못된 응답을 받았다는 뜻입니다. 3-tier에서는 프록시가 두 군데(Route의 HAProxy, web의 nginx)라 어느 쪽인지 먼저 갈라야 합니다.

oc rsh deploy/shop-web curl -sv http://shop-api:8080/api/health
# 여기가 성공하면 → Route↔web 구간 문제 (TLS 종료 방식 불일치가 흔함)
# 여기가 실패하면 → web↔api 구간 문제

주요 원인 — ① Route가 edge인데 Pod가 HTTPS만 받는 경우 (또는 그 반대), ② nginx의 proxy_pass 주소 오타, ③ API가 기동 중이라 연결은 되는데 응답을 못 주는 상태, ④ 응답 헤더 크기가 프록시 버퍼를 초과.

무중단 3대 조건 중 하나가 빠진 상태입니다. 순서대로 확인하십시오.

  1. maxUnavailable: 0인가? 1이면 배포 중 용량이 줄어듭니다.
  2. readinessProbe가 있는가? 없으면 프로세스가 뜨자마자 트래픽이 들어옵니다.
  3. preStop sleep이 있는가? 없으면 Endpoints 제거 전파 전에 애플리케이션이 죽습니다. 이것이 가장 흔한 누락입니다.
  4. 애플리케이션이 graceful shutdown을 지원하는가? (server.shutdown=graceful)
  5. terminationGracePeriodSeconds가 preStop + 요청 처리 시간보다 긴가?

검증은 배포 중 0.3초 간격으로 curl을 돌려 non-200을 세는 것입니다(섹션 9 참고). "체감상 괜찮다"가 아니라 숫자로 확인하십시오.

oc logs deploy/shop-api --previous          # 죽기 직전 로그
oc logs deploy/shop-api -c wait-for-db      # initContainer
oc get pod <pod> -o jsonpath='{.status.containerStatuses[*].lastState}' | jq

exitCode로 원인을 좁힙니다 — 137은 OOMKilled (JVM MaxRAMPercentage 확인, 섹션 6), 143은 SIGTERM 미처리, 1은 애플리케이션 예외입니다.

로그가 정말 아무것도 없다면 실행 전 단계에서 실패한 것입니다. SCC 때문에 UID가 바뀌어 파일 권한 오류가 났을 가능성이 큽니다(섹션 12). 확인: oc debug deploy/shop-api -- sh로 같은 조건의 셸을 띄워 id와 대상 경로의 권한을 봅니다.

또 하나 흔한 것이 startupProbe 부족입니다. Spring Boot가 90초 걸리는데 failureThreshold × periodSeconds가 60초면 기동 도중 계속 죽입니다.

API Pod 수 × 커넥션 풀 크기가 PostgreSQL의 max_connections를 넘었습니다. HPA가 켜져 있으면 트래픽이 몰릴수록 더 크게 실패하는 최악의 형태입니다.

oc rsh shop-db-0 psql -U shopapp -d shopdb -c \
  "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
oc rsh shop-db-0 psql -U shopapp -d shopdb -c "SHOW max_connections;"
oc get hpa shop-api -n shop-prod

단기 조치 — HPA maxReplicas를 낮추거나 HikariCP maximumPoolSize를 줄입니다.
근본 대책 — 섹션 14의 역산 공식으로 상한을 재설계하고, 규모가 더 필요하면 PgBouncer를 앞에 두어 Pod 수와 DB 커넥션 수를 분리합니다. idle 커넥션이 쌓이는 경우라면 idle-timeout과 max-lifetime 설정도 함께 확인하십시오.

가장 자주 발견되는 실제 원인은 CPU throttling입니다. 노드에 여유가 있어도 컨테이너 limits에 걸려 강제로 대기합니다.

# PromQL — throttled 비율
sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="shop-prod"}[5m]))
  / sum by (pod) (rate(container_cpu_cfs_periods_total{namespace="shop-prod"}[5m]))

# 커넥션 풀 대기 (app → db 병목의 직접 지표)
hikaricp_connections_pending{namespace="shop-prod"}

# JVM GC 시간
rate(jvm_gc_pause_seconds_sum{namespace="shop-prod"}[5m])

순서대로 배제하십시오 — ① CPU throttling → ② 커넥션 풀 대기 → ③ 느린 쿼리(pg_stat_activity) → ④ GC 압박 → ⑤ DNS 지연(ndots 문제, 섹션 8) → ⑥ 노드 자원 포화.

3-tier에서 환경 간 차이를 만드는 요인은 정해져 있습니다. 체크리스트로 확인하십시오.

  • NetworkPolicy — dev에는 없고 prod에만 있는 경우가 압도적으로 많습니다. 1순위 확인.
  • ResourceQuota / LimitRange — prod의 쿼터에 걸려 Pod가 안 뜹니다. Deployment는 성공하고 Pod만 없으므로 oc describe rs를 봐야 합니다.
  • SCC — dev에서 넉넉한 SCC를 부여해 두고 prod에서 안 준 경우.
  • Secret 값 — 환경별로 다른데 prod 값이 잘못됨.
  • 이미지 태그 — dev는 latest, prod는 고정 태그라 실제로 다른 코드가 도는 경우.
  • 리소스 limits — prod가 더 빡빡해서 OOM 또는 throttling.
# 환경 간 차이 한눈에 비교
diff <(oc get all,networkpolicy,quota -n shop-dev -o name | sort) \
     <(oc get all,networkpolicy,quota -n shop-prod -o name | sort)

이 강의에 나온 Deployment, Service, StatefulSet, ConfigMap, Secret, NetworkPolicy, HPA, PDB, ServiceMonitor는 전부 Kubernetes 표준입니다. OpenShift 고유 리소스는 Route, BuildConfig, ImageStream, SCC, ClusterResourceQuota 정도입니다.

즉 여기서 배운 것의 80%는 어느 Kubernetes 배포판에서도 통합니다. 그리고 섹션 12에서 다룬 securityContext를 명시적으로 쓰는 습관은, 그 매니페스트를 바닐라와 OpenShift 양쪽에서 그대로 동작하게 만들어 줍니다. 이식성을 잃지 않으면서 플랫폼의 편의를 취하는 것이 가장 좋은 자리입니다.
