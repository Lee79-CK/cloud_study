9편Nova 1: 컴퓨트 구조

“이 서버에 VM을 몇 대 더 올릴 수 있나?”, “왜 자원이 남는데 No valid host인가?”, “cell0에 기록된 인스턴스는 뭔가?” Nova를 운영하면 매일 받는 질문입니다. 이번 편은 Nova의 분업 구조와, 자원 재고를 관리하는 Placement, 그리고 VM이 놓일 곳을 정하는 스케줄러를 해부합니다.

약 110분예상 학습 시간
1~8편 이수요청 흐름, 이미지·볼륨
시뮬레이터·계산기스케줄러, 용량, 플레이버
다음 편10편 Nova 2: 생명주기 심화

섹션 1

이 편의 목표

  1. nova-api · scheduler · conductor · compute와 Placement의 분업을 설명한다.
  2. 셀(cell0 · cell1)과 API DB·셀 DB·메시지 큐의 관계를 설명한다.
  3. Placement의 자원 제공자 · 자원 클래스 · 인벤토리 · 할당 · trait를 읽고 남은 용량을 계산한다.
  4. 과다 할당 비율과 예약값을 설계하고 RHOSO에서 설정하는 위치를 안다.
  5. 스케줄링의 사전 필터 → Placement 후보 → 필터 → 가중치 흐름으로 배치 결과를 예측한다.
  6. 플레이버와 extra specs를 설계하고 고객용 카탈로그를 만든다.

이 편의 비유: 호텔 객실 배정

Nova는 호텔입니다. 손님(VM)이 “트윈룸, 바다 전망”(플레이버·속성)을 예약하면 프런트(nova-api)가 접수하고, 객실 관리 시스템(Placement)이 “조건에 맞는 빈 방 목록”을 주며, 배정 담당(scheduler)이 그중 최적의 방을 고르고, 지배인(conductor)이 일을 조율하며, 각 층 층 담당(nova-compute)이 방을 실제로 준비합니다. 큰 호텔은 건물을 여러 동(셀)으로 나눠 운영합니다.

섹션 2

Nova가 하는 일

Nova가 하는 일다른 서비스에 맡기는 일
VM(인스턴스)의 생성·삭제·시작·정지·재시작·크기 변경·이전이미지 보관 → Glance (6편)
어느 컴퓨트 노드에 둘지 결정 (스케줄링)자원 재고 장부 → Placement (이 편)
하이퍼바이저(libvirt·KVM)에 VM 정의·실행 지시가상 네트워크·포트 → Neutron (11·12편)
임시 디스크·콘솔·메타데이터 제공영구 볼륨 → Cinder (7·8편)
플레이버·쿼터·서버 그룹 관리인증 → Keystone (4·5편)

1편의 “인스턴스 생성 8단계”를 다시 떠올려 보세요. 그 흐름의 거의 모든 단계가 Nova 내부 구성 요소 사이의 일입니다. 이번 편은 그 구성 요소들을, 10편은 생성 이후의 생애주기를 다룹니다.

섹션 3

구성 요소와 Placement

구성 요소를 누르면 하는 일, RHOSO에서의 모습, 멈췄을 때 증상이 나옵니다.

구성 요소를 눌러 보세요.

conductor가 있는 이유

컴퓨트 노드는 수백 대까지 늘어나고, VM을 직접 돌리는 곳이라 보안상 가장 노출된 위치입니다. 그래서 Nova는 컴퓨트 노드가 DB에 직접 접속하지 못하게 하고, 모든 DB 작업을 메시지 큐를 통해 conductor에게 부탁하게 합니다(3편: Galera는 컴퓨트 노드에 노출되지 않음). conductor는 또 VM 생성·이전처럼 여러 단계가 필요한 작업을 처음부터 끝까지 조율합니다.

섹션 4

셀(cell) 구조

셀은 Nova를 크게 확장하기 위해 컴퓨트 노드들을 묶고, 그 묶음마다 DB와 메시지 큐를 따로 두는 구조입니다(Cells v2). 모든 Nova 배포는 최소 두 개의 셀을 가집니다.

구성무엇을 담나RHOSO 기본 구성에서
API DB (nova_api)전역 정보: 플레이버, 쿼터, 키페어, 서버 그룹, 어느 인스턴스·호스트가 어느 셀에 있는지(매핑), 요청 명세Galera openstack
cell0배치에 실패한 인스턴스의 기록만 (컴퓨트 노드 없음)DB는 Galera openstack, conductor 있음
cell1실제 컴퓨트 노드와 그 위 인스턴스의 상세 기록DB는 Galera openstack-cell1, 큐는 RabbitMQ rabbitmq-cell1, conductor·noVNC 프록시
상위 conductor (super conductor)여러 셀에 걸친 조율(어느 셀로 보낼지 등)cell0 쪽 conductor가 이 역할

cell0의 정체

스케줄러가 “No valid host”로 VM을 어디에도 놓지 못하면, 그 인스턴스는 어느 셀에도 속할 수 없습니다. 그래도 사용자는 그 실패한 인스턴스를 목록에서 보고 지울 수 있어야 하므로, Nova는 이런 인스턴스를 cell0에 기록합니다. ERROR 상태의 인스턴스 중 호스트가 비어 있는 것은 대개 cell0에 있습니다.

셀을 여러 개 두는 이유

  • 규모: 셀마다 DB·큐가 따로 있어, 컴퓨트 노드가 수천 대로 늘어도 한 DB·큐에 부하가 몰리지 않습니다.
  • 장애 격리: 한 셀의 DB나 큐가 멈춰도 다른 셀의 VM 관리는 계속됩니다.
  • 대부분의 중소규모 환경은 cell1 하나로 충분합니다. 셀 추가는 큰 설계 결정이므로 29편(아키텍처 변형)에서 다룹니다.

호스트 매핑: 새 컴퓨트 노드는 셀에 “등록”되어야 한다

새 컴퓨트 노드가 서비스를 시작해도, API DB에 “이 호스트는 cell1 소속”이라는 매핑이 생기기 전까지는 스케줄러가 쓸 수 없습니다. 이 등록을 호스트 발견(discover_hosts)이라고 합니다. RHOSO에서는 데이터 플레인 배포의 nova 단계 이후 Operator가 이 과정을 처리하도록 되어 있지만, 노드를 추가했는데 배치가 안 된다면 가장 먼저 확인할 항목입니다(섹션 13).

섹션 5

Placement 해부

Placement는 “누가 무엇을 얼마나 가지고 있고, 얼마나 쓰고 있나”를 기록하는 자원 재고 장부 서비스입니다. 원래 Nova 안에 있다가 독립했습니다. Nova뿐 아니라 Neutron(대역폭), Cyborg(가속기) 같은 서비스도 이 장부를 씁니다.

개념뜻예
자원 제공자 (resource provider)자원을 가진 주체. 보통 컴퓨트 노드 하나. 그 아래 NUMA 노드·GPU 같은 중첩 제공자를 둘 수 있음compute-0.example.com
자원 클래스자원의 종류. 표준 클래스와 사용자 정의(CUSTOM_)VCPU, PCPU, MEMORY_MB, DISK_GB, VGPU, CUSTOM_FPGA
인벤토리제공자가 가진 자원 클래스별 수량과 규칙total, reserved, allocation_ratio, min_unit, max_unit, step_size
할당 (allocation)누가(consumer = 보통 인스턴스 UUID) 어떤 제공자에서 얼마를 쓰고 있나인스턴스 A: VCPU 4, MEMORY_MB 8192, DISK_GB 40
trait제공자가 가진 특성 (6편)HW_CPU_X86_AVX2, COMPUTE_STATUS_DISABLED, CUSTOM_GPU_A100
Placement 집계 (aggregate)제공자들의 묶음. Nova의 호스트 집계·가용 영역과 연결됨az1의 호스트들

가장 중요한 공식

사용 가능 용량 = (total − reserved) × allocation_ratio, 남은 용량 = 사용 가능 용량 − used. 그리고 VM 하나가 요청하는 양은 min_unit 이상, max_unit 이하여야 합니다(예: 64코어 노드의 VCPU max_unit은 보통 64라서, 과다 할당 비율이 커도 VM 하나에 64개 넘는 vCPU는 줄 수 없음).

openstack resource provider list
openstack resource provider inventory list <제공자 UUID>
openstack resource provider usage show <제공자 UUID>
openstack resource provider trait list <제공자 UUID>
openstack resource provider allocation show <인스턴스 UUID>
openstack allocation candidate list --resource VCPU=4 --resource MEMORY_MB=8192 --required HW_CPU_X86_AVX2

섹션 6

용량 계산기: 이 노드에 몇 대 더?

컴퓨트 노드 한 대의 실제 자원, 예약값, 과다 할당 비율, 그리고 플레이버를 넣으면 Placement가 보는 용량과 “더 들어갈 수 있는 VM 수”를 계산합니다. 병목이 되는 자원이 강조됩니다.

섹션 7

과다 할당과 예약 설계

과다 할당 비율 (allocation ratio)

VM은 보통 할당받은 vCPU를 늘 100% 쓰지 않습니다. 그래서 물리 코어보다 더 많은 vCPU를 나눠 주는 과다 할당이 가능합니다. 메모리는 사정이 다릅니다. 실제로 모자라면 VM이 강제 종료되거나 노드 전체가 느려지므로 매우 보수적으로 잡습니다.

자원업스트림 초기 기본값흔한 운영 선택주의
CPU (cpu_allocation_ratio)4.0 (initial_cpu_allocation_ratio)일반 업무 2~8, 성능 등급 1.0, CPU 고정 VM은 별도(PCPU)너무 높이면 CPU 대기(steal)로 VM이 느려짐
메모리 (ram_allocation_ratio)1.01.0 유지가 원칙1을 넘기면 메모리 부족 시 VM 강제 종료(OOM) 위험
디스크 (disk_allocation_ratio)1.0로컬 씬 디스크면 소폭 상향 가능Ceph에 두면 노드 로컬 디스크는 의미가 작아짐(8편)

예약 (reserved)

  • reserved_host_memory_mb: 호스트 OS와 컨테이너(nova_compute, ovn_controller, libvirt 등)용으로 떼어 두는 메모리. 업스트림 기본은 512MB로 작으므로, 운영 환경에서는 노드 규모와 HCI 여부(8편, Ceph OSD 메모리)를 고려해 늘립니다.
  • reserved_host_cpus, reserved_host_disk_mb: 같은 발상의 CPU·디스크 예약.

VCPU와 PCPU

CPU 고정(10편)을 쓰려면 노드의 CPU를 둘로 나눕니다. [compute] cpu_shared_set은 일반 VM이 나눠 쓰는 코어(Placement에 VCPU로 보고), cpu_dedicated_set은 고정 전용 코어(Placement에 PCPU로 보고, 과다 할당 없음)입니다. 6편 시뮬레이터에서 “전용 코어가 있는 호스트만 통과”한 이유가 이것입니다.

RHOSO에서는 어디에 설정하나

컴퓨트 노드의 nova.conf 값은 데이터 플레인으로 전달합니다. 모든 NodeSet에 공통이면 기본 nova-extra-config ConfigMap에 파일을 추가하는 것이 가장 간단합니다. 기본 nova 데이터 플레인 서비스가 이 ConfigMap을 참조하므로, 별도 서비스를 만들 필요가 없습니다. NodeSet마다 다르게 하려면 8편처럼 사용자 정의 서비스를 만듭니다.

apiVersion: v1
kind: ConfigMap
metadata:
  name: nova-extra-config
  namespace: openstack
data:
  25-nova-allocation.conf: |             # 파일 이름: 숫자-서비스-기능.conf (숫자가 클수록 나중에 적용)
    [DEFAULT]
    cpu_allocation_ratio = 4.0
    ram_allocation_ratio = 1.0
    reserved_host_memory_mb = 16384
    [compute]
    cpu_shared_set = 4-63
    cpu_dedicated_set = # CPU 고정용 코어가 있다면

이 파일들은 컴퓨트 노드의 nova_compute 컨테이너 안 /etc/nova/nova.conf.d/에 추가됩니다. 적용하려면 새 OpenStackDataPlaneDeployment가 필요합니다. 이미 있는 ConfigMap 내용은 지우지 말고 파일을 추가하세요.

MSP 관점: 비율은 상품이다

과다 할당 비율은 기술 설정이면서 동시에 서비스 등급입니다. “표준 등급은 CPU 4:1, 프리미엄은 1:1”처럼 정하고, 등급별로 호스트 집계·플레이버를 나누면(10편) 고객에게 성능 차이를 설명하고 가격을 다르게 매길 수 있습니다.

섹션 8

스케줄링의 세 단계

단계누가무엇을
① 사전 필터 + Placement 후보nova-scheduler → Placement요청을 Placement 질문으로 바꿉니다: “VCPU 4, MEMORY_MB 8192, DISK_GB 40이 남고, 필요한 trait가 있고, 금지 trait(예: COMPUTE_STATUS_DISABLED)가 없고, 이 가용 영역 집계에 속한 제공자는?” 이 단계에서 대부분의 후보가 걸러집니다. 결과는 할당 후보 목록입니다.
② 필터nova-schedulerPlacement가 판단하지 못하는 조건을 하나씩 확인: 서비스가 살아 있나(ComputeFilter), 이미지 속성(ImagePropertiesFilter, 6편), 서버 그룹 규칙(Affinity·AntiAffinity), 플레이버 추가 속성 대 호스트 능력, NUMA·PCI 같은 세부 배치 등
③ 가중치와 확정nova-scheduler → Placement남은 호스트에 점수를 매겨(남은 메모리·CPU, 서버 그룹 선호 등) 1등을 고르고, Placement에 할당을 기록(claim)합니다. 동시에 같은 자리를 노린 요청이 있으면 실패한 쪽은 다음 후보로 재시도합니다.
대표 필터확인하는 것대표 가중치높은 점수 조건
ComputeFilternova-compute가 up이고 enabledRAMWeigher남은 메모리가 많을수록 (기본: 분산 배치)
ComputeCapabilitiesFilter플레이버 추가 속성 대 호스트 능력CPUWeigher남은 vCPU가 많을수록
ImagePropertiesFilter아키텍처·하이퍼바이저 종류DiskWeigher남은 디스크가 많을수록
ServerGroupAffinity/AntiAffinityFilter같은 호스트로 / 다른 호스트로ServerGroupSoftAffinity·AntiAffinityWeighersoft 정책 선호
NUMATopologyFilter · PciPassthroughFilterNUMA·CPU 고정·휴즈페이지, PCI 장치 (10편)BuildFailureWeigher최근 생성 실패가 많은 호스트는 감점
AggregateInstanceExtraSpecsFilter플레이버 속성 대 호스트 집계 메타데이터(가중치 배수)배수를 음수로 하면 반대(채워 넣기)

어떤 필터가 켜져 있는지는 [filter_scheduler] enabled_filters로 정해지며, 버전·배포 기본값에 따라 다릅니다. 가용 영역 확인은 최근 버전에서 Placement 사전 필터 방식이 기본입니다.

분산(spread) vs 채우기(pack)

기본 가중치는 남은 자원이 많은 곳에 먼저 놓아 VM을 고르게 퍼뜨립니다(장애 영향 분산, 성능 여유). 반대로 ram_weight_multiplier를 음수로 하면 꽉 찬 곳부터 채워 빈 노드를 남깁니다(전력 절감, 큰 VM 자리 확보). 고객 서비스는 보통 분산이 안전하고, 비용 최적화가 중요한 내부 환경은 채우기를 고려합니다.

섹션 9

스케줄러 시뮬레이터

컴퓨트 노드 5대에 VM 하나를 놓아 봅니다. 플레이버와 조건을 바꾸면 각 노드가 ① Placement → ② 필터 → ③ 가중치 중 어디서 탈락하는지, 누가 선택되는지 보여 줍니다.

플레이버의 칸

칸뜻주의
vcpus · ram (MB)가상 CPU 수, 메모리Placement에 VCPU(또는 PCPU)·MEMORY_MB로 요청됨

카탈로그 설계 원칙

    
    
      
  • 이름 규칙: 계열.크기(예: g1.medium)처럼 이름만 보고 비율과 크기를 알 수 있게.
    • 
      
  • 적은 수로 시작: 계열 3~4개 × 크기 4~5개면 대부분 충분. 플레이버가 많으면 자원 조각(남은 자투리)이 늘어납니다.
    • 
      
  • 비율을 노드에 맞추기: 노드의 코어:메모리 비율(예: 64코어·512GB → 1:8)과 주력 계열 비율이 너무 다르면 한쪽 자원만 남는 낭비가 생깁니다(섹션 6 계산기로 확인).
    • 
      
  • 플레이버는 고치지 않는다: 이미 쓰는 플레이버의 크기는 바꿀 수 없습니다(삭제 후 재생성만 가능). 새 버전을 만들고 이전 것은 비공개로 돌려 퇴역시킵니다.

  apiOverride: { route: {} }

섹션 12

  
재고 확인 실습

  
운영자가 매주 들여다볼 명령들입니다. 출력은 예시 형태입니다.

  
# ① 컴퓨트 서비스와 하이퍼바이저
$ openstack compute service list --service nova-compute
| Host                  | Zone | Status  | State |
| compute-0.example.com | az1  | enabled | up    |
| compute-2.example.com | az1  | disabled| up    |   ← 점검 중 (새 배치 안 받음)

$ openstack hypervisor list --long
| Hypervisor Hostname   | vCPUs Used | vCPUs | Memory MB Used | Memory MB |
| compute-0.example.com | 180        | 64    | 401408         | 515072    |   ← vCPUs는 물리 기준, Used는 할당 합계

# ② Placement 관점 (과다 할당·예약 반영)
$ openstack resource provider list
$ openstack resource provider inventory list <UUID>
$ openstack resource provider usage show <UUID>
$ openstack resource provider trait list <UUID> | grep -E 'AVX|CUSTOM|DISABLED'

# ③ “이 플레이버가 들어갈 곳이 있나?”를 Placement에 직접 물어보기
$ openstack allocation candidate list --resource VCPU=8 --resource MEMORY_MB=32768 --resource DISK_GB=80

# ④ 셀과 호스트 매핑 (nova-manage가 있는 Nova Pod에서)
$ nova-manage cell_v2 list_cells
$ nova-manage cell_v2 list_hosts

# ⑤ 장부 정합성 점검: 고아 할당 찾기 (읽기 전용 모드로 먼저)
$ nova-manage placement audit --verbose

  

    
hypervisor list와 Placement 숫자가 다른 이유

    
hypervisor list의 vCPUs는 물리 수량이라 과다 할당을 반영하지 않습니다. 그래서 “vCPUs 64, 사용 180”처럼 사용량이 더 커 보일 수 있습니다. 실제로 “더 들어갈 수 있나”는 Placement의 (total − reserved) × allocation_ratio − used로 판단합니다.

섹션 17

  
정리와 다음 편

  
오늘의 핵심 여덟 문장

  
    
    
  • Nova는 api(접수) · scheduler(배정) · conductor(조율·DB 대리) · compute(실행), 그리고 자원 장부 Placement로 나뉜다.
    • 
    
  • 컴퓨트 노드는 DB에 직접 붙지 않고 conductor를 거친다.
    • 
    
  • 셀 구조: API DB(전역·매핑) + cell0(배치 실패 기록) + cell1(실제 노드). RHOSO는 cell1에 전용 Galera·RabbitMQ를 둔다.
    • 
    
  • 새 컴퓨트 노드는 셀에 호스트 매핑되어야 쓰인다.
    • 
    
  • Placement 용량 = (total − reserved) × allocation_ratio − used. hypervisor list의 물리 숫자와 헷갈리지 않는다.
    • 
    
  • CPU는 과다 할당 가능(초기 기본 4.0), 메모리는 1.0이 원칙. 고정 코어는 PCPU로 분리.
    • 
    
  • 스케줄링은 사전 필터·Placement 후보 → 필터 → 가중치 → 할당 기록. 기본 가중치는 분산 배치.
    • 
    
  • 플레이버는 적은 수, 명확한 이름, 노드 비율과 정렬. 쓰는 플레이버는 고치지 말고 새로 만든다. RHOSO 컴퓨트 설정은 nova-extra-config(공통) 또는 사용자 정의 서비스(NodeSet별).
    •
