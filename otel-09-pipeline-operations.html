SECTION 01

무엇을 남길 것인가

결론부터 말하면, 대부분의 트레이스는 아무도 보지 않습니다. 정상 요청의 트레이스는 수백만 건이 쌓여도 열람되는 비율이 극히 낮습니다. 반면 에러와 느린 요청의 트레이스는 장애 대응 때 반드시 필요합니다.

반드시 남긴다

에러 · 느린 요청

장애 분석의 핵심. 비율로는 적지만 가치는 압도적입니다.

대표성만 남긴다

정상 요청

"평소 모습"을 비교하는 기준선으로 일부만 있으면 충분합니다.

버린다

노이즈

헬스체크, 프로브, 메트릭 스크레이프 요청. 정보 가치가 없습니다.

메트릭은 샘플링하지 않습니다

이 편의 샘플링은 트레이스 이야기입니다. 메트릭은 이미 집계된 값이라 샘플링할 대상이 아니고, 비용 관리는 6편의 카디널리티 통제와 10편의 보존 정책으로 합니다. 로그는 필터링은 하되 샘플링은 신중하게 — 로그는 "몇 번 일어났나"를 세는 용도로도 쓰이기 때문입니다.

1편 회색지대의 해소

"개발자는 100%를 원하고 비용은 엔지니어가 부담한다." 테일 샘플링은 이 갈등의 기술적 해법입니다. 개발자가 실제로 필요로 하는 것은 100%가 아니라 '필요한 트레이스가 반드시 있는 것'이기 때문입니다. 에러·지연 트레이스를 전부 남기면 개발자의 요구는 충족되고, 정상 트레이스를 줄이면 비용 문제가 해결됩니다.

SECTION 02

헤드 샘플링과 테일 샘플링

둘의 차이는 언제 결정하느냐 하나입니다. 그 차이가 모든 것을 바꿉니다.

기준헤드 샘플링테일 샘플링
결정 시점트레이스가 시작될 때트레이스가 끝난 뒤
결정 근거trace_id 해시 — 내용을 모름에러 여부, 지연 시간, 속성 — 내용을 봄
결정 위치SDK (앱 안)Gateway Collector
에러 트레이스샘플링 비율만큼만 남음전부 남길 수 있음
비용매우 쌈 — 버린 건 아예 전송 안 함전량을 Gateway까지 보내야 하고 메모리에 보관해야 함
구성 복잡도환경 변수 두 개Gateway + loadbalancing + 용량 계획
둘을 함께 쓸 때 반드시 알아야 할 것

SDK에서 10% 헤드 샘플링을 하고 Gateway에서 테일 샘플링을 하면, 테일 샘플링은 그 10%만 볼 수 있습니다. 나머지 90%는 이미 앱에서 버려졌기 때문입니다. 에러 트레이스 90%가 Gateway에 도착하기도 전에 사라집니다. 테일 샘플링을 쓰려면 SDK는 always_on 또는 높은 비율로 설정해야 합니다. 8편에서 Instrumentation CR에 샘플러를 설정했다면, 테일 샘플링 도입과 함께 그 값을 올려야 합니다.

그럼 언제 헤드 샘플링만으로 충분한가

  • 트래픽이 적어 전량 저장이 부담스럽지 않을 때 — 이 경우 샘플링 자체가 필요 없습니다
  • 트래픽이 매우 많아 Gateway가 전량을 감당할 수 없을 때 — 헤드로 먼저 줄이고 테일로 한 번 더
  • 도입 초기, Gateway를 아직 운영할 여력이 없을 때 — 일단 헤드로 시작하고 나중에 전환
SECTION 03

테일 샘플링 설계

정책을 여러 개 걸고, 하나라도 "남긴다"고 하면 남깁니다. OR 조건이라고 생각하면 됩니다. 

tail_sampling:
  decision_wait: 10s               # 트레이스가 끝났다고 판단하기까지 기다리는 시간
  num_traces: 100000               # 메모리에 동시에 보관할 최대 트레이스 수
  expected_new_traces_per_sec: 2000
  policies:
    # 1. 에러는 전부
    - name: keep-errors
      type: status_code
      status_code: { status_codes: [ERROR] }

    # 2. 1초 넘게 걸린 것은 전부
    - name: keep-slow
      type: latency
      latency: { threshold_ms: 1000 }

    # 3. 결제 같은 핵심 거래는 전부 — 개발팀 요청 반영
    - name: keep-payment
      type: string_attribute
      string_attribute:
        key: http.route
        values: [/payments, /checkout]

    # 4. 나머지는 5%만
    - name: baseline
      type: probabilistic
      probabilistic: { sampling_percentage: 5 }

주요 정책 종류

정책남기는 조건실무 용도
status_code에러 상태인 Span이 있음에러 트레이스 전량 보존
latency전체 소요 시간이 임계값 초과느린 요청 보존
string_attribute특정 속성이 지정 값과 일치핵심 거래·VIP 테넌트 보존
numeric_attribute숫자 속성이 범위 안큰 금액 거래 보존
probabilistictrace_id 기반 비율정상 트래픽의 대표 표본
rate_limiting초당 개수 상한폭주 시 비용 상한선
span_countSpan 수가 범위 안비정상적으로 긴 트레이스 탐지
ottl_conditionOTTL 조건식위 정책으로 표현 안 되는 복합 조건
and · composite여러 조건 조합 · 비율 배분"테넌트 A의 에러만" 같은 복합 규칙
개발팀과의 협의 창구

3번 정책처럼 "이 경로는 반드시 남겨주세요"라는 요청을 받는 공식 창구를 만드세요. 요청을 정책 목록에 추가하는 절차가 있으면, 개발팀은 "샘플링 때문에 트레이스가 없다"고 불평하는 대신 필요한 것을 구체적으로 요청하게 됩니다. 6편 마무리에서 개발자에게 "9편을 훑어보라"고 한 이유가 이것입니다.

decision_wait의 함정

Gateway는 "이 트레이스가 끝났다"를 알 수 없습니다. 그래서 첫 Span을 받은 뒤 decision_wait만큼 기다리고 판단합니다.

너무 짧으면

긴 트레이스의 뒷부분 Span이 도착하기 전에 판단합니다. 지연 판단이 틀어지고, 늦게 온 Span은 이미 결정된 트레이스에 붙거나 버려집니다.

너무 길면

그동안 모든 트레이스를 메모리에 들고 있어야 합니다. 메모리 사용량이 대기 시간에 정비례해 늘어납니다.

실무 기준은 서비스의 p99 응답 시간보다 조금 길게입니다. 대부분 요청이 1초 안에 끝나는 서비스라면 5~10초면 충분하고, 배치나 비동기 처리가 섞여 있다면 더 길게 잡아야 합니다.

SECTION 04

loadbalancing — 테일 샘플링을 성립시키는 장치

7편에서 "Agent에 테일 샘플링을 걸면 트레이스가 조각난다"고 했습니다. Gateway를 여러 개 띄워도 같은 문제가 생깁니다. 해법은 같은 trace_id를 항상 같은 Gateway로 보내는 것입니다.

2단 Gateway 구성

# ── Agent 쪽 (또는 1단 Gateway) — 라우팅만 담당 ──
exporters:
  loadbalancing:
    routing_key: traceID
    protocol:
      otlp:
        tls: { insecure: false }
        sending_queue: { enabled: true, queue_size: 5000 }
    resolver:
      k8s:
        service: otel-sampler-headless.observability   # 헤드리스 서비스
        ports: [4317]

# ── 2단 Gateway — 테일 샘플링 담당 (레플리카 N개) ──
service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, tail_sampling, batch]
      exporters:  [otlp/backend]

헤드리스 서비스가 필요한 이유

일반 서비스는 요청마다 아무 파드로 분산합니다. loadbalancing은 파드 IP 목록을 직접 알아야 해시로 고정 배정할 수 있으므로 헤드리스 서비스를 씁니다. 엔드포인트 조회 권한도 RBAC에 필요합니다.

스케일링 시 잠깐 흔들립니다

Gateway 레플리카가 늘거나 줄면 해시 배정이 바뀝니다. 그 순간 진행 중이던 트레이스 일부가 두 Gateway로 나뉩니다. HPA를 쓴다면 스케일 이벤트가 너무 잦지 않게 안정화 구간을 두세요.

spanmetrics는 샘플링 전에

7편의 spanmetrics 커넥터로 RED 지표를 만든다면, 테일 샘플링 전의 전량 데이터로 계산해야 합니다. 샘플링 후에 계산하면 에러가 전부 남고 정상이 5%만 남은 데이터를 기준으로 하므로 에러율이 실제보다 수십 배 높게 나옵니다. Agent 단계에서 계산하거나, Gateway에서 샘플링 파이프라인과 별도로 분기시키세요.

SECTION 05

OTTL — 데이터를 고치는 언어

OpenTelemetry Transformation Language. Collector 안에서 데이터를 조건부로 수정·삭제·추출하는 표현식입니다. 6편에서 말한 "2차 방어선"의 실체가 여기 있습니다.

기본 형태

transform:
  error_mode: ignore               # 한 문장이 실패해도 나머지는 계속
  trace_statements:
    - context: span                # span · resource · spanevent 중 무엇을 다룰지
      statements:
        - 함수(대상, 인자...) where 조건

한 줄이 동작 + 대상 + 선택적 조건입니다. SQL의 UPDATE ... WHERE와 비슷하게 읽으면 됩니다. error_mode: ignore를 꼭 넣으세요. 기본값은 오류 시 데이터를 버리는 쪽이라, 예상 못 한 형태의 데이터가 오면 조용히 유실됩니다.

레시피를 고르면 OTTL 문장과 변환 전후 데이터가 표시됩니다.

  SECTION 06
  
멀티테넌트 — MSP의 핵심 과제

  

    여러 고객사의 텔레메트리가 하나의 파이프라인을 지나갑니다.
    섞이면 안 되고, 한 고객사의 폭주가 다른 고객사에 영향을 주면 안 됩니다.
  


  
1단계 · 테넌트 식별

  

    모든 것의 출발점은 "이 데이터가 어느 고객사 것인가"를 아는 것입니다.
    가장 안정적인 방법은 네임스페이스를 테넌트 경계로 삼는 것입니다.
    앱이 스스로 테넌트를 선언하게 하면 누락과 위조가 생깁니다.
  


# Agent — k8sattributes가 붙인 네임스페이스로 테넌트 속성 부여
transform/tenant:
  error_mode: ignore
  trace_statements:
    - context: resource
      statements:
        - set(attributes["acme.tenant"], "customer-a")
            where IsMatch(attributes["k8s.namespace.name"], "^customer-a-")
        - set(attributes["acme.tenant"], "customer-b")
            where IsMatch(attributes["k8s.namespace.name"], "^customer-b-")
        - set(attributes["acme.tenant"], "unassigned")
            where attributes["acme.tenant"] == nil

  
네임스페이스 이름 규칙을 테넌트 접두사로 통일해 두면 이 규칙이 간단해집니다. 네임스페이스 레이블을 k8sattributes로 가져와 쓰는 방식도 있습니다.

백프레셔 — 막히면 뒤로 전파된다

  

    백엔드가 느려지면 Gateway 큐가 쌓이고, 가득 차면 Gateway가 Agent의 요청을 거부하고,
    Agent 큐가 쌓이고, 결국 앱 SDK의 큐가 차서 앱에서 데이터를 버리기 시작합니다.
    이 연쇄를 막으려면 각 단계에 충분한 큐를 두고, 무엇보다 큐 사용률을 감시해서 앞단에 도달하기 전에 알아야 합니다.
  


  
영속 큐 — 재시작해도 잃지 않기


extensions:
  file_storage/queue:
    directory: /var/lib/otelcol/queue

exporters:
  otlp/backend:
    endpoint: ...
    sending_queue:
      enabled: true
      storage: file_storage/queue     # 메모리 대신 디스크
      queue_size: 10000

service:
  extensions: [file_storage/queue]

  

    기본 큐는 메모리에 있어서 Collector가 재시작하면 대기 중이던 데이터가 사라집니다.
    디스크 큐를 쓰면 재시작 후 이어서 전송합니다.
    쿠버네티스에서는 PersistentVolume이 필요하므로 Gateway를 StatefulSet으로 운영하는 편이 자연스럽습니다.
  


  
Gateway 스케일링

  
    
    
  • CPU 기준 HPA가 가장 무난합니다. 메모리 기준은 테일 샘플링 보관량 때문에 오르내림이 커서 불안정합니다
    • 
    
  • 테일 샘플링 Gateway는 스케일 이벤트마다 트레이스 재배정이 일어나므로 안정화 구간을 길게 두세요
    • 
    
  • PodDisruptionBudget으로 동시에 내려가는 Gateway 수를 제한하세요
    • 
    
  • 노드 분산을 위해 topologySpreadConstraints나 anti-affinity를 거세요
    • 
  










  SECTION 08
  
보안

  

    텔레메트리 파이프라인은 모든 서비스의 내부 동작이 흐르는 통로입니다.
    누구나 여기에 데이터를 넣을 수 있거나 가로챌 수 있다면 심각한 문제입니다.
  


  

    

      
위협대책구현

      
        
구간 도청전송 암호화Agent ↔ Gateway ↔ 백엔드 구간 TLS, 가능하면 mTLS

        
위조 데이터 주입수신 인증Gateway 리시버에 인증 익스텐션(bearer token, OIDC 등)

        
테넌트 간 침범테넌트 강제 부여앱이 보낸 테넌트 값을 신뢰하지 말고 Agent에서 네임스페이스 기준으로 덮어쓰기

        
무단 접근네트워크 격리NetworkPolicy로 Collector 포트 접근 주체 제한

        
시크릿 노출설정 분리백엔드 인증 정보는 Secret에 두고 ${env:...}로 참조

        
민감정보 유출2차 필터링5절의 OTTL 레시피 — 금지 키 삭제, 패턴 마스킹

      
    

  



# Gateway 리시버에 인증 적용
extensions:
  bearertokenauth/server:
    token: ${env:OTEL_INGEST_TOKEN}

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
        tls:
          cert_file: /certs/tls.crt
          key_file:  /certs/tls.key
          client_ca_file: /certs/ca.crt     # mTLS — 클라이언트 인증서 검증
        auth:
          authenticator: bearertokenauth/server


  

    테넌트 값은 앱을 믿지 마세요
    

      앱이 acme.tenant=customer-b를 스스로 붙여 보내면, 고객사 A의 앱이 고객사 B의 데이터 공간에 쓸 수 있게 됩니다.
      테넌트 속성은 Agent에서 네임스페이스 기준으로 강제로 덮어써야 합니다.
      6절의 변환 규칙이 set으로 무조건 덮어쓰는 이유입니다.
    

  










  SECTION 09
  
증상으로 원인 찾기

  
이 편의 주제와 관련해 운영 중 자주 만나는 상황들입니다.


  

    

      
테일 샘플링으로 에러를 전부 남기도록 했는데 에러 트레이스가 여전히 10%만 보입니다

      

        
        
        
        
      

    

    

      
spanmetrics로 만든 에러율 대시보드가 실제보다 20배쯤 높게 나옵니다

      

        
        
        
        
      

    

    

      
트래픽이 몰리는 시간대에만 트레이스가 조각나 보입니다. 그때 Gateway HPA가 동작합니다

      

        
        
        
        
      

    

    

      
decision_wait를 10초에서 60초로 늘렸더니 Gateway가 OOM으로 계속 죽습니다

      

        
        
        
        
      

    

    

      
OTTL 변환을 추가한 뒤로 특정 서비스의 데이터만 사라졌습니다. 에러 로그도 거의 없습니다

      

        
        
        
        
      

    

    

      
백엔드 점검 시간에 앱 쪽 로그에 "export failed, dropping spans"가 쏟아집니다

9편 핵심 정리

  
    
    
  • 테일 샘플링은 "100%를 원하는 개발자"와 "비용을 부담하는 엔지니어"의 갈등을 기술로 푸는 방법입니다
    • 
    
  • 테일 샘플링을 쓰려면 SDK 샘플러를 올려야 합니다. 헤드에서 버린 것은 테일이 볼 수 없습니다
    • 
    
  • 여러 Gateway를 쓰면 loadbalancing + 헤드리스 서비스로 같은 trace_id를 한곳에 모읍니다
    • 
    
  • decision_wait는 메모리와 정비례합니다. p99보다 조금 길게
    • 
    
  • spanmetrics는 샘플링 전 데이터로 계산합니다
    • 
    
  • OTTL에는 반드시 error_mode: ignore, 조건으로 대상을 좁히세요
    • 
    
  • 테넌트는 네임스페이스 기준으로 Agent에서 강제 부여하고, 격리 수준은 고객사별로 문서화합니다
    • 
    
  • 큐 사용률을 감시해 백프레셔가 앱까지 전파되기 전에 알아야 합니다
    •
