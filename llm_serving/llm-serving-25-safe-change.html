안전한 변경
GitOps·카나리·업그레이드

23편의 사후 검토를 모아 보면 많은 장애가 “무언가를 바꾼 직후”에 일어납니다. LLM 플랫폼은 바꿀 것이 특히 많습니다. 모델과 리비전, 정밀도, 어댑터, 엔진 버전과 수십 개의 설정, 채팅 템플릿과 프롬프트, 라우팅 정책, 그리고 GPU 드라이버까지. 이번 편은 이 변경들을 Git으로 선언하고(GitOps), 배포 전에 거르고(게이트), 일부 트래픽에 먼저 내보내 지연·품질 SLI로 자동 판정하고(카나리), 실패하면 바로 되돌리는 절차로 묶습니다.

01시작하기 전에

변경을 줄이는 것이 아니라, 변경을 안전하게 자주 할 수 있게 만드는 것이 목표입니다.

학습 목표

  1. LLM 플랫폼의 변경 종류별 위험·감지 방법·배포 방식·되돌리기 난이도를 정리할 수 있다.
  2. GitOps로 오버레이·정책·대시보드를 선언하고, 변경을 검토 가능한 단위(PR)로 만들 수 있다.
  3. 배포 전 게이트(정적 검사·정책·품질 평가·SLO 용량·지표 점검·기동 시간·서명)를 자동화할 수 있다.
  4. LLM 특성(세션 고정·캐시·워밍업·추가 GPU·표본 수)을 반영한 카나리를 설계할 수 있다.
  5. 지연·오류·품질 SLI로 카나리를 자동 판정하고 실패 시 자동으로 되돌릴 수 있다.
  6. vLLM·GPU 드라이버·쿠버네티스·CRD 업그레이드의 표준 절차와 순서를 작성할 수 있다.
이 편의 비유: 신메뉴 출시

신메뉴(새 모델·설정)는 레시피를 문서로 남기고(GitOps), 주방에서 시식으로 먼저 거른 뒤(배포 전 게이트), 일부 매장·일부 손님에게만 먼저 내놓습니다(카나리). 남긴 양·불만·조리 시간(SLI)을 보고 기준에 못 미치면 바로 원래 메뉴로 돌아갑니다(되돌리기). 단골손님은 같은 방문 중에는 같은 메뉴를 받게 합니다(세션 고정). 주방 설비 교체(드라이버·엔진 업그레이드)는 영업이 적은 시간에, 매장 하나씩 합니다.

03GitOps

“지금 무엇이 돌고 있나”의 답이 Git에 있고, 클러스터는 그 답을 따라가는 구조.

원칙LLM 플랫폼에서
선언7편 kustomize 오버레이(모델·정밀도·엔진 설정), 게이트웨이 정책, 기록·경보 규칙(20~23편), 대시보드 JSON, 테넌트 템플릿(24편)을 모두 저장소에
검토모든 변경은 PR. 설정 한 줄이라도 측정 근거(14편 결과 표)를 PR에 첨부
자동 동기화와 드리프트 감지누군가 kubectl로 직접 바꾸면 Git과의 차이로 감지·복원. 장애 중 임시 조치도 나중에 Git에 반영
감사Git 이력 = 변경 감사 로그 (24편). 누가·언제·무엇을·왜(PR 설명)
승격개발 → 스테이징 → 운영 오버레이로 같은 변경을 단계적으로 (디렉터리 또는 브랜치)
  • 도구: Argo CD(애플리케이션 단위 UI·동기화)와 Flux(컨트롤러 조합) 둘 다 널리 쓰입니다. 이 편 실습은 Argo CD와 같은 계열의 Argo Rollouts(카나리)를 씁니다.
  • 비밀: 저장소에는 비밀을 넣지 않습니다. 외부 비밀 저장소 연동 리소스만 넣습니다(24편).
  • 순서: CRD(GAIE·KEDA·Prometheus Operator)를 먼저, 그것을 쓰는 리소스를 나중에 동기화하도록 동기화 순서(sync wave)를 지정합니다.
  • GPU 자원의 현실: Git에 레플리카 수를 적어 두면 KEDA(18편)와 충돌합니다. 자동 확장 대상의 레플리카 필드는 GitOps 비교에서 제외합니다.

04배포 전 게이트

카나리는 마지막 방어선입니다. 거를 수 있는 것은 배포 전에 거릅니다.

게이트무엇을 막나도구·편언제
빌드·스키마문법 오류, 잘못된 필드kustomize build + 스키마 검증PR마다
정책latest 태그, 관리 API 노출, 쿼터 없는 네임스페이스스크립트 또는 정책 엔진(Kyverno·Gatekeeper)PR마다
무결성서명 안 된 모델·이미지해시 목록 서명(24), 다이제스트모델·이미지 변경 PR
품질 회귀평가 세트 기준 미달quick_eval(6), 규칙·판정(22)모델·정밀도·템플릿·엔진 변경
성능 회귀SLO 용량 감소, 기동 시간 증가slo_probe·tune_report(14), 타임라인(13)엔진·설정 변경
관측 호환지표 이름 변경으로 대시보드·경보·확장 깨짐metric_inventory(20)엔진 버전 변경
보안 회귀본문 로그·인젝션 유출카나리 문자열(21), 인젝션 세트(24)로깅·템플릿·모델 변경

GPU가 필요한 게이트(품질·성능)는 비용이 크므로 변경 종류에 따라 선택적으로 돌립니다. 결과 파일을 PR에 붙이는 것까지 자동화하면 검토자가 근거를 보고 승인할 수 있습니다(실습 25-2).

05LLM 카나리 설계

일반 웹 서비스의 카나리와 같아 보이지만, LLM에는 고려할 것이 더 있습니다.

고려 사항이유설계
트래픽 나누는 기준비율·테넌트·헤더·모델 이름내부 사용자 → 일부 테넌트 → 비율 순서. HTTPRoute 가중치(Gateway API)로
세션 고정멀티턴 대화가 버전 사이를 오가면 답 스타일이 바뀌고 캐시도 깨짐 (15편)세션·사용자 단위 해시로 같은 버전에 고정 (헤더 기반 경로·EPP 세션 친화)
추가 GPU카나리 레플리카는 GPU를 더 씀용량 여유가 없으면 기존 레플리카 하나를 카나리로 교체(용량 감소 감수)
워밍업새 Pod의 첫 요청은 느림(컴파일·캐시 냉각, 13편)준비 후 워밍업 요청, 분석 시작 전 대기
표본 수작은 악화는 많은 요청이 있어야 보임 (22편)히어로 계산기로 단계별 최소 시간 결정
품질 SLI의 지연판정 평가는 비동기라 늦게 나옴지연·오류는 단계마다, 품질은 마지막 단계 전 확인
GAIE·llm-d에서InferencePool 단위로 엔진 묶음새 버전용 InferencePool을 따로 두고 HTTPRoute 가중치로 나눔 (모델 이름 재작성 기능은 llm-d 쪽, 11편)

06자동 판정

카나리를 사람이 대시보드로 보고 판단하면 느리고 일관되지 않습니다. 판정 기준을 코드로 적습니다.

판정 지표방식주의
오류율카나리 Pod의 5xx·실패 비율 < 기준요청이 적으면 0/0 → 최소 표본 조건
TTFT·ITL p95카나리 < 절대 기준, 또는 안정 버전 대비 +x% 이내워밍업 구간 제외, 같은 시간대 비교
형식 준수·잘림 (22)카나리 >= 안정 버전 − 허용 폭응답 본문 검사 결과가 버전 라벨을 갖고 있어야 함
안전 판정 (22)위험 판정률이 기준 이하표본 기반이면 시간 필요
자원KV 사용률·선점·재시작 없음원인 지표는 “실패”보다 “보류” 판단에
  • 세 가지 결과: 통과·실패 외에 “판단 불가(데이터 부족)”를 둡니다. 판단 불가가 반복되면 단계를 길게 하거나 비율을 키웁니다.
  • 버전 라벨: 지표에 버전(파드 템플릿 해시·변형 이름)이 붙어 있어야 카나리만 골라 볼 수 있습니다. 20편 PodMonitor의 라벨 변환에 추가합니다(실습 25-3).
  • 도구: Argo Rollouts(분석 템플릿 + Gateway API 트래픽 플러그인), Flagger(Gateway API·지표 분석) 등이 이 판정을 자동화합니다.

07섀도·블루그린·A/B

카나리 말고도 쓸 수 있는 방식들. 상황에 따라 고릅니다.

방식방법장점대가LLM에서 쓰임
섀도 (미러링)실제 요청을 복사해 새 버전에도 보내고 응답은 버림사용자 영향 0, 실제 트래픽으로 비교GPU 비용 두 배, 부작용 있는 호출(도구)은 위험큰 모델 교체 전 지연·품질 비교
블루그린새 버전을 완전히 띄운 뒤 한 번에 전환즉시 되돌리기잠시 GPU 두 배GPU 여유가 있을 때의 엔진 업그레이드
카나리비율을 단계적으로위험 노출 최소, 자동 판정시간, 약간의 추가 GPU대부분의 변경

롤링Pod를 하나씩 교체추가 자원 거의 없음판정 없이 퍼짐위험이 낮은 설정 변경, GPU 여유 없을 때

08되돌리기

“되돌릴 수 있는가”는 배포 전에 확인합니다. 배포 후에 알게 되면 늦습니다.

상황되돌리는 법걸리는 시간
카나리 중 실패자동 중단 → 가중치 0 → 카나리 Pod 축소즉시 (안정 버전이 그대로 떠 있음)
전체 배포 후 발견Git 되돌리기(revert) → 동기화엔진 기동 시간 (13편). 이전 버전을 잠시 남겨 두면 단축
모델 교체 후 발견이전 모델 리비전으로 되돌리기이전 가중치가 캐시에 남아 있어야 빠름 (13편 노드 캐시 보존 정책)
드라이버·Operator 후 발견이전 드라이버 버전으로 노드별 재설치재부팅 포함, 길다 → 노드 하나씩 진행이 필수
CRD 업그레이드 후 발견CRD는 쉽게 되돌릴 수 없음 (저장 버전 변환)사전 백업·스테이징 검증이 유일한 대책

LLM 서빙 엔진은 대부분 상태가 없어(KV 캐시는 버려도 됨) 되돌리기가 비교적 쉽습니다. 어려운 것은 되돌리는 데 걸리는 시간(기동)과 클러스터 공용 구성 요소(드라이버·CRD)입니다. 이 둘은 단계적 적용과 사전 검증으로만 위험을 줄일 수 있습니다.

09플랫폼 업그레이드 표준 절차

모델·설정보다 드물지만 영향이 큰 변경. 순서와 점검표를 고정합니다.

  1. 호환표 확인엔진 버전 ↔ CUDA·드라이버 ↔ GPU Operator ↔ 쿠버네티스 ↔ GAIE·llm-d·KServe CRD ↔ 게이트웨이. 릴리스 노트의 “깨지는 변경”·지표 변경 항목.
  2. 스테이징 검증같은 구성의 스테이징(또는 운영의 한 노드·한 레플리카)에서 4장 게이트 전체: 스모크·지표 점검·평가·SLO 용량·기동 시간.
  3. 변경 공지와 유지보수 창고객 공지, 23편 경보 침묵, 되돌리기 계획과 판단 기준을 미리 기록.
  4. 아래층부터, 하나씩드라이버·Operator는 노드 하나씩(cordon → drain → 업그레이드 → 검증 Pod → uncordon), CRD는 호환 순서대로, 엔진은 카나리로.
  5. 배포 후 관찰21·22편 SLI를 최소 하루, 큰 변경은 일주일 집중 관찰. 지표 이름 변경은 기록 규칙에서 흡수(20편).
  6. 기록변경 기록·결과·발견 사항을 다음 업그레이드 점검표에 반영.
GPU 노드가 하나뿐일 때

랩의 GB10처럼 GPU 노드가 하나면 드라이버 업그레이드는 곧 서비스 중단입니다. 유지보수 창, 외부 공급자 폴백(허용 테넌트, 12편), “준비 중” 응답 같은 대체 경로를 계획에 넣습니다. 운영 환경이라면 N+1 노드(17·18편)가 업그레이드 가능성의 전제입니다.

10MSP 관점

변경 관리는 고객 신뢰의 핵심 절차이자, MSP 운영 성숙도를 보여 주는 지표입니다.

  • 변경 등급: 표준 변경(사전 승인된 저위험 — 한도 조정 등), 일반 변경(검토 필요 — 모델·엔진), 긴급 변경(장애 대응). 등급별 승인·공지 절차를 계약에 둡니다.
  • 고객 공지: 모델·엔진 변경은 품질·응답 스타일에 영향이 있으므로 사전 공지와 오프라인 평가 결과 요약을 함께 보냅니다.
  • 유지보수 창: 정기 창을 계약에 명시하고, 그 시간의 SLO 집계 제외 여부를 정합니다(21편).
  • 변경 지표: 배포 빈도, 변경 후 장애 비율, 복구 시간, 변경부터 배포까지 걸린 시간을 월간 보고(26편)에 넣으면 운영 품질을 숫자로 보여 줄 수 있습니다.
  • 고객별 단계 적용: 공용 엔진 변경은 내부 → 표준 등급 고객 → 프리미엄 고객 순서로 단계를 둡니다.

#!/usr/bin/env bash
# 사용: ./gate.sh [변경된 오버레이 디렉터리...]   결과는 gate-report.md (PR 설명에 붙임)
set -uo pipefail
OVS=${*:-$(ls -d 30-serving/overlays/*/)}
R=gate-report.md; FAIL=0
echo "# 배포 전 게이트 결과 ($(date +%F' '%T))" > $R
for ov in $OVS; do
  echo -e "\n## ${ov}" >> $R
  if out=$(kubectl kustomize "$ov" 2>&1); then echo "- 빌드: 통과" >> $R; else echo "- 빌드: **실패** \`$out\`" >> $R; FAIL=1; continue; fi
  if command -v kubeconform >/dev/null; then
    echo "$out" | kubeconform -strict -ignore-missing-schemas -summary >/tmp/kc.txt 2>&1 \
      && echo "- 스키마: 통과" >> $R || { echo "- 스키마: **실패** ($(tail -1 /tmp/kc.txt))" >> $R; FAIL=1; }
  fi
  echo "$out" | grep -nE 'image: .*:(latest|main|nightly)\b' >/tmp/img.txt \
    && { echo "- 이미지 태그: **실패** (고정되지 않은 태그) $(cat /tmp/img.txt | tr '\n' ' ')" >> $R; FAIL=1; } || echo "- 이미지 태그: 통과" >> $R
  echo "$out" | grep -q 'VLLM_SERVER_DEV_MODE' && [[ "$ov" != *lab* && "$ov" != *sleep* ]] \
    && { echo "- 관리 API: **실패** (개발용 엔드포인트가 켜져 있음, 4·13편)" >> $R; FAIL=1; } || echo "- 관리 API: 통과" >> $R
  echo "$out" | grep -q 'VLLM_ALLOW_RUNTIME_LORA_UPDATING' \
    && echo "- 런타임 어댑터 등록: 경고 (16편, 노출 경로 확인)" >> $R
done
echo -e "\n결론: $([ $FAIL = 0 ] && echo '정적 게이트 통과 — GPU 게이트(품질·성능)는 변경 종류에 따라 25-4로' || echo '실패 항목 수정 필요')" >> $R
cat $R; exit $FAIL

import json, sys, time, threading, urllib.request
gw, secs = sys.argv[1], int(sys.argv[2]) if len(sys.argv) > 2 else 600
ok = err = 0; lock = threading.Lock(); end = time.time() + secs
def worker():
    global ok, err
    while time.time() < end:
        body = json.dumps({"model": "qwen3-8b", "max_tokens": 32, "messages": [{"role": "user", "content": "ping"}]}).encode()
        try:
            urllib.request.urlopen(urllib.request.Request(gw + "/v1/chat/completions", body,
                {"Content-Type": "application/json", "x-lab-app": "sim"}), timeout=60).read()
            with lock: ok += 1
        except Exception:
            with lock: err += 1
for _ in range(6): threading.Thread(target=worker, daemon=True).start()
while time.time() < end:
    time.sleep(15); print(f"{time.strftime('%T')} 성공 {ok} 실패 {err}", flush=True)

  2. GitOps로 “무엇이 돌고 있나”를 Git에 두고, PR로 검토하고, 드리프트를 감지한다. 자동 확장 필드는 비교에서 뺀다.
  3. 배포 전 게이트(빌드·정책·무결성·품질·성능·지표 호환·보안)로 거를 수 있는 것은 미리 거른다.
  4. LLM 카나리는 세션 고정·워밍업·추가 GPU·표본 수를 고려하고, 버전 라벨이 붙은 SLI로 자동 판정·자동 중단한다.
  5. 되돌리기 시간 = 기동 시간. 안정 버전을 카나리 동안 유지하고, 이전 가중치 캐시를 보존한다.
  6. 플랫폼 업그레이드는 호환표 → 스테이징 → 공지·침묵 → 아래층부터 하나씩 → 관찰 → 기록의 고정 절차로.
