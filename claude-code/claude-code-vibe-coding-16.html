인수인계받은 저장소

이번 편의 실습 저장소 acme-ops-legacy는 가상의 고객사 ACME의 운영 스크립트입니다. 디스크·서비스 점검, DB 백업, 백업 정리, HTML 보고서를 매일 새벽 2시에 root로 돌립니다. MSP 현장에서 흔히 만나는 모양을 일부러 재현했고, 커밋 네 개짜리 역사도 들어 있습니다. 11장의 블록으로 직접 만들 수 있습니다.

📖 읽기 먼저

처음 몇 시간은 아무것도 고치지 않습니다. Plan 모드(4편)로 열어 Claude도 편집하지 못하게 합니다.

🔍 근거와 함께

Claude의 설명은 그럴듯해도 틀릴 수 있습니다. 모든 주장에 파일:줄과 확인 명령을 요구합니다.

지도 그리기

운영 스크립트의 지도는 진입점에서 시작합니다. 웹앱이라면 라우터, 배치라면 cron입니다. 상자를 눌러 각 파일의 역할과 발견된 문제를 보세요. 빨간 테두리는 위험이 있는 파일, 점선은 아무도 부르지 않는 코드입니다.

지도는 Explore에게 맡기기 파일이 많다면 13편처럼 “Explore 서브에이전트로 cron 진입점부터 호출 관계를 따라가서, 파일마다 역할 한 줄과 호출하는 파일 목록을 표로 줘. very thorough로.” 탐색 출력은 서브에이전트에 두고 요약만 받습니다. 결과는 mermaid 다이어그램으로 docs/ARCHITECTURE.md에 남기게 할 수 있습니다(8장).

백업은 어떻게 동작해?

“mysqldump로 압축 백업하고, 실패하면 set -e로 중단됩니다.” → 틀렸습니다. set -e는 주석 처리되어 있고, 켜져 있어도 파이프 때문에 못 잡습니다(7장).

✅ 이렇게 물으면

백업이 어떻게 동작하는지 설명해줘. 모든 주장에 파일:줄을 붙이고, 코드에서 직접 확인한 것과 추측한 것을 나눠서 표시해. 확인 방법이 명령으로 가능하면 그 명령도 적어줘.
“추측”과 “확인” 분리

Claude 스스로 확신도를 나누게 하면 검증할 곳이 보입니다.

읽기 전용 명령으로 확인

grep -rn send_alert ., bash -n, git log -p처럼 아무것도 바꾸지 않는 명령으로 주장을 검증합니다.

“없다”도 검증

“legacy/old_backup.sh는 아무도 안 부른다”는 grep 결과(0건)와 cron·문서까지 확인해야 합니다. 다른 서버의 crontab이 부를 수도 있습니다.

모를 때는 모른다고

“확인할 수 없는 것은 확인할 수 없다고 말해”를 붙이면 그럴듯한 빈칸 채우기가 줄어듭니다.

Git 역사로 “왜”를 찾기

코드는 무엇을 하는지 말해 주지만, 왜 그렇게 됐는지는 역사에 있습니다. 모범 사례 문서도 Claude가 Git 역사를 보며 “왜 이렇게 되어 있는지” 답하게 하는 것을 권합니다.

backup/backup_db.sh 의 set -e 가 왜 주석 처리됐는지 git 역사에서 찾아줘. 그 결정 때문에 지금 생긴 위험이 있으면 설명하고, 당시 문제를 다르게 풀 방법도 제안해.
Claude가 찾는 것
● Bash(git log --oneline -- backup/backup_db.sh) 93b97e6 temp: disable set -e, dump fails on replica 1234fb3 initial import from acme-ops-01 ● Bash(git show 93b97e6) ● 2022-11-03 새벽, “replica에서 mysqldump 경고로 실패”해서 임시로 끈 것입니다. “temp”였지만 3년째 그대로입니다. 그리고 1년 뒤 보관 기간이 7일 → 3일로 줄었습니다(2cba597). 두 변경이 겹쳐, 덤프가 실패해도 빈 백업이 “성공”으로 기록되고 3일 뒤엔 좋은 백업이 모두 지워질 수 있습니다.
유용한 질문들

고치기 전에 테스트로 감싸기

특성화 테스트(characterization test)는 “올바른 동작”이 아니라 지금의 동작을 기록하는 테스트입니다. 이상해 보이는 동작도 일단 고정합니다. 그래야 고친 뒤 테스트가 실패할 때 “의도한 변화”인지 “사고”인지 구분할 수 있습니다.

1
지금 동작을 고정

report의 파싱·집계, services 목록 읽기, rotate의 “오래된 파일만 지움”을 테스트 5개로. 원본에서 전부 통과(확인함).

2
고칠 동작을 테스트로 먼저

“BACKUP_DIR가 비면 아무것도 지우지 않고 실패한다”. 원본에서 실패(확인함: find가 /를 대상으로 호출됨).

3
최소 수정

변수 가드·따옴표·숫자 검사 세 줄. 다른 것은 건드리지 않습니다.

4
전부 통과

6개 모두 통과(확인함). 커밋 메시지에 위험 목록 번호를 적습니다.

위험한 동작은 가짜로 바꿔서 테스트 “빈 변수일 때 / 를 지우는지” 확인하려고 진짜로 돌리면 안 됩니다. 테스트는 가짜 find를 PATH 맨 앞에 두고, 호출됐는지만 기록합니다. 그래서 수정 전 코드로 돌려도 실제 삭제는 일어나지 않습니다. Claude에게 테스트를 맡길 때도 “실제로 지우거나 원격에 접속하는 명령은 가짜로 대체해”를 꼭 붙이세요.

큰 저장소에서

코드 인텔리전스 플러그인

공식 문서의 팁: 언어별 code intelligence 플러그인을 설치하면 Claude가 정확한 “정의로 이동”, “참조 찾기”를 씁니다. grep보다 정확합니다(15편 설치 방법).

영역별로 나눠 묻기

한 세션에 저장소 전체를 담으려 하지 말고, 영역마다 질문하고 결과를 docs에 남긴 뒤 /clear(6편).

하위 폴더 CLAUDE.md와 rules

8편처럼 영역마다 CLAUDE.md를 두거나 .claude/rules/의 paths로 그 영역을 다룰 때만 로드. 모노레포 설정은 공식 “Monorepos and large repos” 문서.

병렬 조사

독립적인 영역은 13·14편처럼 서브에이전트나 agent view로 동시에 조사하고 요약을 모읍니다.

여러 저장소
