7편Cinder 1: 블록 스토리지 구조

VM을 지워도 남아 있어야 하는 데이터는 어디에 둘까요? 답은 Cinder 볼륨입니다. 이번 편은 볼륨이 만들어지고, 알맞은 스토리지에 배정되고, VM에 연결되고, 스냅샷·백업·이전되는 전 과정을 구성 요소 단위로 해부합니다.

약 100분예상 학습 시간
1~6편 이수세 개의 문, 이미지 포맷
시뮬레이터 2종스케줄러·QoS
다음 편8편 Cinder 2: 백엔드와 Ceph

섹션 1

이 편의 목표

  1. cinder-api · scheduler · volume · backup의 역할과, 하나가 멈추면 무엇이 안 되는지 설명한다.
  2. 볼륨 생성 요청이 스케줄러의 필터·가중치를 거쳐 특정 백엔드 풀에 배정되는 과정을 설명한다.
  3. 볼륨 타입과 extra specs로 “어떤 등급의 스토리지에 만들지”를 설계한다.
  4. QoS의 front-end·back-end 차이와 용량 비례 IOPS 계산을 설명한다.
  5. 볼륨이 VM에 연결(attach)되는 흐름과 전송 프로토콜(iSCSI·FC·NVMe-TCP·NFS·RBD)의 차이를 설명한다.
  6. 스냅샷·클론·백업·전송·확장·타입 변경을 상황에 맞게 고른다.
  7. 부팅 볼륨과 데이터 볼륨, 그리고 임시 디스크의 차이와 설계 기준을 설명한다.

이 편의 비유: 외장 하드 대여점

Cinder는 외장 하드 대여점입니다. 손님(사용자)이 “500GB짜리 SSD 하나”를 주문하면 접수 창구(api)가 받고, 배정 담당(scheduler)이 어느 창고(백엔드·풀)에 재고가 있는지 보고 고르고, 창고 관리자(volume)가 실제로 꺼내 준비합니다. 손님 컴퓨터(VM)에 꽂는 일은 배달 기사(Nova·os-brick)가 하고, 정기적으로 사본을 다른 금고에 보관(backup)하는 직원도 있습니다. 하드는 컴퓨터를 버려도 남습니다.

섹션 2

Cinder가 하는 일과 기본 용어

Cinder(Block Storage 서비스)는 VM에 붙였다 뗐다 할 수 있는 블록 장치(볼륨)를 셀프서비스로 제공합니다. Cinder 자신은 데이터를 저장하지 않습니다. 실제 저장은 Ceph, 상용 스토리지 어레이, NFS 같은 백엔드가 하고, Cinder는 그 백엔드를 드라이버로 조종하는 관리자입니다.

섹션 3

네 개의 구성 요소

Cinder는 1편에서 본 OpenStack 공통 패턴(API + 워커 + DB + 메시지 큐)을 그대로 따릅니다. 구성 요소를 누르면 하는 일, RHOSO에서의 모습, 멈췄을 때 증상이 나옵니다.

구성 요소를 눌러 보세요.

요청이 흐르는 길

사용자 → cinder-api(REST, 권한·쿼터 확인, DB 기록) → RabbitMQ → cinder-scheduler(어느 백엔드·풀?) → RabbitMQ → cinder-volume(드라이버로 백엔드 조종) → 백엔드. 백업은 cinder-api → cinder-backup → 백업 저장소. 2편의 장애 분류법대로 “접수(API)가 안 되는가, 지시가 안 가는가(큐), 현장(volume)이 실패하는가”를 나눠 보면 됩니다.

섹션 5

볼륨 타입과 extra specs

볼륨 타입은 사용자에게 보여 주는 스토리지 등급 메뉴입니다. 사용자는 “gold”, “standard” 같은 이름만 고르고, 그 이름 뒤에 붙은 extra specs(추가 속성)가 스케줄러에게 “어떤 백엔드·풀이어야 하는지”를 알려 줍니다.

extra spec 예뜻
volume_backend_name=ceph이 이름의 백엔드에만 만들기 (가장 많이 씀)
multiattach="<is> True"여러 VM에 동시 연결 가능한 볼륨 (클러스터 파일 시스템 필요)
thin_provisioning_support="<is> True"씬 프로비저닝을 지원하는 풀만 (백엔드가 보고하는 능력과 비교)
RESKEY:availability_zones=az1이 타입은 특정 가용 영역에서만 만들 수 있게
replication_enabled="<is> True"복제 기능이 켜진 백엔드만 (재해 복구, 29편)
벤더 전용 키 (예: netapp:…)드라이버가 읽어 볼륨 생성 옵션으로 사용 (압축, 중복 제거 등)
 
# 관리자: 등급 메뉴 만들기
openstack volume type create --property volume_backend_name=ceph --description "Ceph SSD" ceph-ssd
openstack volume type create --property volume_backend_name=netapp-gold gold
openstack volume type create --private --property volume_backend_name=netapp-gold cust-a-gold
openstack volume type set --project <고객 프로젝트> cust-a-gold     # 비공개 타입을 특정 고객에게만 공개
openstack volume type list --long
openstack volume backend capability show cinder-volume-ceph-0@ceph       # 백엔드가 보고하는 능력(비교 대상)

기본 타입을 꼭 정하세요

사용자가 타입을 지정하지 않으면 기본 볼륨 타입(설정의 default_volume_type, 지정이 없으면 __DEFAULT__)이 쓰입니다. 기본 타입이 아무 백엔드나 허용하면 예상치 못한 스토리지에 볼륨이 생길 수 있습니다. 운영 환경에서는 기본 타입이 의도한 백엔드를 가리키도록 설정하세요.

섹션 6

스케줄러 시뮬레이터: 어느 풀에 만들어질까

cinder-scheduler는 Nova 스케줄러와 비슷하게 필터로 후보를 거르고 가중치로 순위를 매깁니다. 기본 필터는 가용 영역(AvailabilityZoneFilter), 용량(CapacityFilter), 능력(CapabilitiesFilter)이고, 기본 가중치는 남은 용량(CapacityWeigher)입니다. 아래에서 조건을 바꿔 보세요.

씬 프로비저닝과 과다 할당

씬 프로비저닝 풀은 실제로 쓴 만큼만 공간을 차지하므로, 물리 용량보다 많이 “약속”할 수 있습니다. 얼마나 더 약속할지는 max_over_subscription_ratio(예: 2.0이면 물리 용량의 2배까지)로, 비상 여유는 reserved_percentage로 정합니다. 약속이 실제가 되는 순간(모두가 꽉 채우는 순간) 스토리지가 가득 차 쓰기가 멈추므로, 실제 사용률 모니터링(25편)이 필수입니다.

섹션 7

QoS: 성능 상한과 하한

한 고객의 대량 작업이 같은 스토리지를 쓰는 다른 고객을 느리게 만드는 현상을 시끄러운 이웃(noisy neighbor)이라고 합니다. QoS 규격(QoS specs)은 볼륨의 IOPS·처리량에 상한(또는 백엔드에 따라 보장 하한)을 걸어 이를 막습니다.

consumer (누가 적용하나)뜻특징
front-end컴퓨트 노드의 하이퍼바이저(libvirt)가 VM 디스크 입출력을 제한백엔드 종류와 무관하게 동작. Ceph에서 흔히 사용
back-end스토리지 백엔드가 자체 기능으로 제한·보장드라이버가 지원해야 함. 최소 보장(min IOPS) 같은 고급 기능은 주로 여기
both양쪽 모두에 전달키 이름이 양쪽에서 해석될 수 있어야 함
front-end 키 예뜻
total_iops_sec · read_iops_sec · write_iops_sec초당 입출력 횟수 상한
total_bytes_sec · read_bytes_sec · write_bytes_sec초당 처리량(바이트) 상한
total_iops_sec_per_gb 등 _per_gb용량에 비례하는 상한 (큰 볼륨일수록 높게)
total_iops_sec_per_gb_min 등 _min용량 비례 계산 결과의 최저값 (작은 볼륨도 최소한은 보장)

용량 비례 QoS 계산기

# QoS 규격을 만들고 볼륨 타입에 연결
openstack volume qos create --consumer front-end \
   --property total_iops_sec_per_gb=10 --property total_iops_sec_per_gb_min=500 gold-qos
openstack volume qos associate gold-qos gold
openstack volume qos list

QoS는 볼륨 타입에 연결되므로, 등급 메뉴(타입) 하나에 “어떤 스토리지 + 어떤 성능 한도”가 함께 정의됩니다. front-end QoS는 보통 볼륨을 새로 연결할 때 적용되므로, 이미 연결된 볼륨은 다시 연결해야 반영될 수 있습니다.

섹션 8

볼륨 연결(attach) 흐름

볼륨을 VM에 꽂는 일은 Cinder 혼자 하지 않습니다. Nova가 주도하고, Cinder는 “이 볼륨에 이렇게 접속하라”는 정보를 주며, 실제 연결은 컴퓨트 노드의 os-brick 라이브러리가 합니다.

전송 프로토콜

프로토콜연결 방식노드 준비
iSCSIIP 네트워크로 SCSI 명령 전달. 노드가 로그인해 블록 장치를 얻음iscsid 실행, 다중 경로(multipathd) 권장

NFS공유 파일 시스템 위의 파일을 디스크로 사용별도 준비 거의 없음

연결은 두 군데에서 일어난다

VM에 볼륨을 붙이는 연결은 컴퓨트 노드에서 일어납니다. 그런데 “이미지로부터 볼륨 만들기”, “볼륨 백업”, “볼륨으로 이미지 만들기”처럼 Cinder·Glance가 직접 볼륨 데이터를 읽고 쓰는 작업은 cinder-volume·backup이 도는 곳, 즉 RHOSO에서는 OCP 노드에서 연결이 일어납니다. 그래서 iSCSI·FC·NVMe-TCP 백엔드를 쓰면 OCP 노드에도 준비가 필요합니다(섹션 12).

섹션 9

볼륨 상태값

볼륨 상태를 누르면 뜻, 오래 머물 때의 원인, 첫 확인 방법이 나옵니다. 2편의 상태값 사전을 Cinder 쪽으로 확장한 것입니다.

상태를 눌러 보세요.

상태 강제 변경은 최후의 수단

관리자는 openstack volume set --state available처럼 DB의 상태 값을 강제로 바꿀 수 있습니다. 하지만 이것은 기록만 바꿀 뿐 백엔드나 컴퓨트 노드의 실제 연결 상태는 바꾸지 않습니다. 실제로 VM에 붙어 있는 볼륨을 available로 바꾸면 두 VM이 같은 디스크에 쓰는 사고가 날 수 있습니다. 반드시 실제 상태(백엔드, 컴퓨트 노드의 연결)를 확인한 뒤에 씁니다.

섹션 10

스냅샷 · 클론 · 백업 · 전송 · 확장 · 타입 변경

작업무엇을 하나어디에 생기나주의
스냅샷그 순간의 볼륨 사본같은 백엔드원본에 의존. 원본 백엔드가 고장 나면 함께 잃음. 스냅샷이 있으면 원본 삭제 불가(--cascade 제외). 사용 중 볼륨은 --force 필요(충돌 일관성)

스냅샷에서 볼륨스냅샷 시점으로 새 볼륨같은 백엔드복구·테스트 환경 만들기
이미지에서 볼륨Glance 이미지로 부팅 가능한 볼륨볼륨 백엔드Ceph + raw면 즉시 복제(6편). 이미지-볼륨 캐시로 반복 생성 가속 가능
백업볼륨 데이터를 다른 저장소로 복사백업 저장소 (Swift·Ceph·NFS·S3 등)원본 스토리지가 망가져도 복구 가능. 증분(--incremental) 지원
볼륨 전송볼륨 소유권을 다른 프로젝트로 넘김그대로 (데이터 이동 없음)available 상태여야 함. 요청 ID와 인증 키를 받는 쪽에 전달

타입 변경 (retype)볼륨 타입 바꾸기 (예: standard → gold)필요하면 다른 백엔드로 이동백엔드가 바뀌면 데이터 이동(--retype-policy on-demand), 시간 소요
이전 (migrate)같은 타입 그대로 다른 백엔드·호스트로 이동대상 백엔드관리자 작업. 스토리지 교체·정리 시
 
# 스냅샷과 스냅샷에서 복원
openstack volume snapshot create --volume db-data [--force] db-data-snap-1026
openstack volume create --snapshot db-data-snap-1026 --size 100 db-data-test

# 백업 (전체 → 증분)과 복원
openstack volume backup create --name db-data-full [--force] db-data
openstack volume backup create --name db-data-inc1 --incremental [--force] db-data
openstack volume backup restore db-data-inc1 db-data-restored

# 다른 프로젝트로 소유권 이전
openstack volume transfer request create db-data               # → id, auth_key 출력 (받는 쪽에 안전하게 전달)
openstack volume transfer request accept --auth-key <KEY> <ID>   # 받는 프로젝트에서

# 확장과 타입 변경
openstack volume set --size 200 db-data
openstack volume set --type gold --retype-policy on-demand db-data

스냅샷과 백업, 한 문장 구분

스냅샷은 같은 서랍 안의 복사본, 백업은 다른 금고에 넣은 복사본입니다. 실수로 지운 파일을 빨리 되살리는 데는 스냅샷이 좋지만, 스토리지 자체가 망가지는 사고에는 백업만이 답입니다. 고객에게 “스냅샷이 있으니 백업은 필요 없다”는 설명은 절대 하지 마세요.

MSP 설계 팁

“VM을 실수로 지웠는데 데이터를 살려 주세요”는 흔한 문의입니다. 중요한 업무 데이터는 데이터 볼륨에 분리해 두면 VM이 사라져도 볼륨은 남습니다. 루트 디스크까지 보존해야 하는 고객에게는 부팅 볼륨을 쓰되 삭제 시 볼륨 보존 여부를 명확히 정하세요. Ceph 환경에서는 임시 디스크도 Ceph에 둘 수 있어 라이브 마이그레이션이 쉬워지는 등, 백엔드 구성에 따라 선택지가 달라집니다(9·10편).

섹션 12

RHOSO의 Cinder

RHOSO에서 달라진 점

  • 백엔드마다 별도 cinder-volume 서비스(Pod)를 둡니다. 여러 백엔드를 쉽게 추가할 수 있고, 새 백엔드를 배포해도 이미 돌고 있는 백엔드에는 영향이 없습니다.
  • 모든 볼륨 서비스에 한꺼번에 적용되는 전역 customServiceConfig·nodeSelector는 없습니다. 백엔드별로 각각 적습니다.
  • cinder-volume·cinder-backup은 OCP 노드의 Pod로 돕니다. 컴퓨트 노드에는 Cinder 서비스가 없습니다(연결용 iscsid·multipathd·NVMe 모듈은 데이터 플레인 배포 때 자동으로 켜짐).

OpenStackControlPlane의 cinder 칸

cinder:
  apiOverride: { route: {} }
  template:
    databaseInstance: openstack
    secret: osp-secret
    cinderAPI:
      replicas: 3
      # override.service.internal … (MetalLB, 3편과 같은 패턴)
    cinderScheduler:
      replicas: 1
    cinderBackup:
      networkAttachments: [storage]
      replicas: 0                       # 백업 저장소를 구성한 뒤 올림 (권장 3 이상)
    cinderVolumes:                        # 백엔드마다 하나씩, 각각 replicas 1
      ceph:
        networkAttachments: [storage]
        replicas: 1
        customServiceConfig: |
          [DEFAULT]
          enabled_backends = ceph
          [ceph]
          volume_backend_name = ceph
          volume_driver = cinder.volume.drivers.rbd.RBDDriver
          # Ceph 접속 항목은 8편
      netapp-iscsi:
        networkAttachments: [storage]
        replicas: 1
        customServiceConfigSecrets: [netapp-secret]   # 어레이 비밀번호 등은 Secret으로
        customServiceConfig: |
          [netapp-iscsi]
          volume_backend_name = netapp-gold
          # 벤더 드라이버 항목…

학습용으로 단순화했습니다. 배포 문서 예시도 cinderBackup·cinderVolumes를 replicas: 0(“백엔드를 구성해야 활성화”)으로 시작합니다. Red Hat 이슈 기록 기준 권장값은 백업 3개 이상, 볼륨은 백엔드(컨테이너)당 1개입니다.

OCP 노드 준비: MachineConfig

프로토콜OCP 노드에 필요한 것방법
iSCSIiscsid 서비스 (노드당 하나만 — OCP 일반 용도·CSI·RHOSO가 공유)MachineConfig로 iscsid 활성화
다중 경로multipathd와 /etc/multipath.confMachineConfig로 파일 생성·서비스 활성화
NVMe-TCPnvme 커널 모듈MachineConfig로 모듈 로드

MachineConfig를 적용하면 노드가 재부팅된다

MachineConfig로 노드 설정을 바꾸면 OCP가 노드를 순서대로 재부팅합니다. RHOSO 컨트롤 플레인이 이미 운영 중이라면 3편의 “한 번에 한 노드” 원칙과 맞물려 계획된 작업 창이 필요합니다. RHOSO 문서도 적용 전 OCP 관리자와 협의하라고 안내합니다. 특정 노드에서만 Cinder를 돌린다면 MachineConfigPool로 적용 범위를 그 노드들로 좁힙니다.

노드 고정이 필요한 경우

LVM 백엔드처럼 데이터가 특정 노드의 디스크에만 있는 경우, 또는 FC처럼 특정 하드웨어가 있는 노드에서만 동작하는 경우에는 그 백엔드의 cinder-volume을 레이블 기반 nodeSelector로 해당 노드에 고정합니다(호스트 이름이 아니라 레이블로 지정).

oc get pods -n openstack | grep cinder
oc logs -n openstack <cinder-volume Pod> --all-containers --tail=50
oc get machineconfig | grep -i cinder

쿼터와 물리 용량은 다른 이야기

쿼터는 “이 프로젝트가 얼마까지 신청할 수 있나”이고, 풀 용량은 “스토리지에 실제로 얼마가 남았나”입니다. 모든 프로젝트의 쿼터 합이 물리 용량보다 큰 것은 흔한 일(과다 판매)이므로, 풀 사용률 알림을 반드시 걸어 두세요. 쿼터 초과 오류와 용량 부족(CapacityFilter 실패) 오류는 메시지로 구분됩니다.

섹션 18

정리와 다음 편

오늘의 핵심 여덟 문장

  • Cinder는 볼륨을 셀프서비스로 제공하는 관리자이고, 데이터는 백엔드에 있으며 드라이버로 조종한다.
  • api(접수) → scheduler(배정) → volume(현장), 그리고 backup(다른 금고). 위치는 host@backend#pool로 표시된다.
  • 스케줄러는 가용 영역·용량·능력 필터와 남은 용량 가중치로 풀을 고른다. 씬 프로비저닝은 과다 할당 비율로 조절한다.
  • 볼륨 타입 = 등급 메뉴. extra specs(특히 volume_backend_name)로 백엔드를, QoS 연결로 성능 한도를 정한다.
  • QoS는 front-end(하이퍼바이저)와 back-end(스토리지)가 있고, _per_gb와 _min으로 용량 비례 한도를 만든다.
  • 연결은 Nova 주도 + Cinder 접속 정보 + os-brick 실행. iSCSI·FC·NVMe-TCP는 노드 준비가 필요하고, RBD는 libvirt가 Ceph에 직접 붙는다.
  • 스냅샷은 같은 서랍, 백업은 다른 금고. 전송은 소유권 이전, retype은 등급 변경, migrate는 위치 이동.
  • RHOSO는 백엔드마다 cinder-volume Pod, 설정은 백엔드별로, iSCSI·다중 경로·NVMe는 MachineConfig(노드 재부팅)로 OCP 노드를 준비한다.
