02

CSRF: SameSite만으로는 부족한 경우

6편부터 세션 쿠키는 SameSite=Lax입니다. Lax는 "다른 사이트"에서 온 POST에 쿠키를 붙이지 않습니다. 그런데 사이트는 등록 가능 도메인(eTLD+1) 기준이라 포트와 하위 도메인이 달라도 같은 사이트입니다.

공격 페이지 (다른 포트의 정적 서버에서 제공)
<h1>경품 당첨! (공격자 페이지)</h1>
<form id="f" method="post" action="http://localhost:3000/vms/web-01/restart"></form>
<script>document.getElementById('f').submit();</script>
공격 페이지 주소포털과의 관계방어 전 (CSRF_CHECK=off)방어 후
http://127.0.0.1:3999/다른 사이트쿠키 미전송 → 로그인 화면, web-01 실행 중 그대로403, Sec-Fetch-Site=cross-site
http://localhost:3999/같은 사이트, 다른 출처쿠키 전송 → web-01 재시작됨403, Sec-Fetch-Site=same-site

운영 환경으로 바꿔 말하면, portal.msp.example의 세션은 같은 회사의 wiki.msp.example이나 dev.msp.example에 공격 코드가 하나라도 올라오면 위험합니다. 그래서 상태를 바꾸는 요청에는 출처 확인을 더합니다.

apps/server/src/app.js (CSRF 미들웨어)
app.use((req, res, next) => {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method) || process.env.CSRF_CHECK === 'off') return next();
  const site = req.get('Sec-Fetch-Site');                 // 최신 브라우저가 자동으로 붙임 (위조 불가: 금지된 헤더)
  const origin = req.get('Origin');
  const self = `${req.protocol}://${req.get('host')}`;
  const bad = site ? !['same-origin', 'none'].includes(site) : (origin && origin !== self);
  if (bad) return res.status(403).type('text').send('Forbidden: cross-origin request');
  next();
});

Sec-Fetch-Site는 브라우저가 붙이는 Fetch Metadata 헤더로, 페이지 스크립트가 바꿀 수 없습니다. htmx 요청은 같은 출처의 fetch라 same-origin, 주소창 입력은 none입니다. 이 헤더를 보내지 않는 오래된 브라우저를 위해 Origin 비교를 대체로 둡니다. 두 헤더가 모두 없는 요청(curl 같은 비브라우저 도구)은 통과시키는데, CSRF는 피해자 브라우저가 쿠키를 싣고 가는 공격이라 비브라우저 요청은 이 방어의 대상이 아닙니다. 토큰 기반 CSRF 방어(동기화 토큰)도 유효한 대안이며, 그 경우 8편 htmx:config:request나 9편의 확장에서 헤더로 실어 보내면 됩니다.

03

CSP와 nonce

Content-Security-Policy는 "이 페이지에서 무엇을 실행·로드해도 되는가"를 브라우저에 알립니다. XSS가 생겨도 피해를 줄이는 두 번째 방어선입니다.

curl -sI localhost:3000/login (발췌)
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-/nNt0YIvHy0ZX57exyz/nw==' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Cross-Origin-Opener-Policy: same-origin
지시어랩 값이유
script-src'self' 'nonce-…' 'unsafe-eval'같은 출처 파일 + 이 응답의 nonce를 가진 인라인(15편 import map). 'unsafe-eval'은 hx-on(9편)·hx-live·hx-vals js:가 Function으로 식을 실행하기 때문 → 4절에서 제거
style-src'self' 'unsafe-inline'htmx가 넣는 지시자 <style>(includeIndicatorCSS), Vue 사용자 정의 요소의 <style>, 템플릿의 style 속성
connect-src'self'fetch·SSE·WebSocket을 같은 출처로 (10편 WebSocket도 측정상 정상)
frame-ancestors'none'클릭재킹 방지 (다른 사이트가 포털을 iframe에 넣지 못함)

nonce는 요청마다 새로 만든 무작위 값입니다. 공격자가 HTML을 주입해도 그 응답의 nonce를 미리 알 수 없으므로 주입된 <script>는 실행되지 않습니다. htmx 4.0.1은 스왑한 조각 안의 <script>를 새 스크립트 요소로 다시 만들어 실행하는데, htmx.config.inlineScriptNonce를 설정하지 않으면 nonce를 붙이지 않으므로(소스 #processScripts) 조각 속 인라인 스크립트도 CSP에 막힙니다. 랩은 조각에 인라인 스크립트를 쓰지 않으므로 이 설정을 두지 않았습니다.

CSP를 켜며 고친 곳

운영 콘솔(14편)의 index.html은 정적 파일이라 nonce를 붙일 수 없었습니다. 서버가 응답할 때 <script type="importmap">에 그 응답의 nonce를 끼워 넣도록 했고, Express 정적 미들웨어가 /console/에 index.html을 직접 내보내지 않게 index: false를 주었습니다. 그 뒤 포털·랩 점검·콘솔의 모든 기능(차트, Vue 요약, hx-on 복사, hx-live, SSE, WebSocket)을 돌려 CSP 위반이 0건인 것을 확인했습니다.

04

hx-csp: unsafe-eval 없이

htmx 4.0.1 배포본에는 hx-csp 확장이 들어 있습니다. 소스 머리말이 밝히는 세 겹의 기능을 랩 /lab/csp(CSP에 'unsafe-eval' 없음)에서 측정했습니다.

기능 (소스)동작측정 (확장 켬 / 끔)
nonce 관문모든 htmx 요소에 hx-nonce가 페이지 nonce와 같아야 함. 아니면 hx 속성을 모두 지우고 htmx:security:strip주입된 hx-get·hx-on: 속성 제거, 요청 0건 / 끄면 주입된 hx-get 요청 1건 발생
응답 nonce 승격같은 출처 응답이면 응답 CSP 헤더의 nonce를 페이지 nonce로 바꿔 끼움. 서버는 조각마다 자기 응답 nonce를 찍으면 됨서버 조각의 "다시" 버튼(응답 nonce)이 정상 동작
도난 방지응답에 페이지 nonce가 그대로 있으면 지움 (서버는 페이지 nonce를 알 수 없으므로 도난으로 간주)훔친 nonce 요소: 속성 제거 (사유 missing-nonce)
safeEval (safeEval: true)hx-on 등의 식을 Function 대신 nonce 스크립트 주입으로 실행 → 'unsafe-eval' 불필요hx-on 실행됨 / 끄면 EvalError(CSP 위반 script-src eval)

hx-csp 실험 (iframe 안에 엄격 CSP 메타 + htmx 4.0.1 + hx-csp 실동작)

모의 서버가 응답마다 새 nonce의 CSP 헤더를 보낸다

실험 상자는 이 강의 파일 안의 iframe에 script-src 'nonce-…' 메타 CSP를 걸고 같은 htmx·hx-csp 원본을 실행합니다. ③을 누른 뒤 주입된 버튼을 눌러 보고, 확장을 끈 상태와 비교해 보세요.

도입 비용

nonce 관문은 모든 htmx 요소에 서버가 nonce를 찍어야 동작합니다. 랩 전체(수십 개 템플릿, 두 템플릿 엔진)에 바로 적용하지 않고 /lab/csp에서 먼저 검증한 이유입니다. 상속(hx-nonce:inherited)으로 한 번에 찍으면 편하지만, 그 영역에 주입된 요소도 nonce를 상속받아 관문이 무력해지므로 쓰지 않습니다. 도입 순서는 ① 지금처럼 nonce + 'unsafe-eval' CSP ② 새 화면부터 hx-nonce 찍기 ③ 전체가 찍히면 hx-csp + safeEval로 'unsafe-eval' 제거 순이 현실적입니다.

05

XSS: 서버 조각의 이스케이프

htmx 앱에서 XSS의 주 무대는 서버 템플릿입니다. 조각이 곧 HTML이므로, 사용자 입력이 이스케이프 없이 들어가면 hx-* 속성까지 살아납니다.

위치안전한 출력위험한 출력랩 점검
Eta<%= 값 %> (이스케이프)<%~ 값 %> (그대로)<%~는 include·이미 렌더링한 조각·업스트림 조각에만
Jinja2{{ 값 }} (자동 이스케이프){{ 값 | safe }}| safe는 업스트림 조각(15편)에만
hx-on·hx-vals js: 안 값값을 data-*에 두고 식에서 읽기 (9편)식 문자열에 서버 값을 끼워 넣기이름 복사 버튼이 data-name 사용
JSON 응답application/json + nosniffHTML로 해석될 수 있는 응답 형식데이터 API 확인

측정: VM 메모에 <img src=x onerror="document.title='pwned'"> <b>굵게?</b>를 저장하자 화면에는 그 글자가 그대로 보였고 img 요소는 0개, 페이지 제목도 그대로였습니다(Express·FastAPI 동일). 15편 게이트웨이의 업스트림 조각은 "같은 회사 팀이 만든 신뢰 경계 안의 HTML"이라는 전제로 그대로 끼웁니다. 그 전제가 깨질 수 있다면(외부 업체 서비스 등) 그 영역에 4절의 hx-csp 관문이 특히 효과적입니다. 업스트림은 포털 페이지의 nonce를 모르므로, 업스트림 조각 속 htmx 속성은 포털이 승격해 주지 않는 한 살아나지 않기 때문입니다.

06

htmx가 기본으로 막는 것

기본값 (4.0.1 소스)의미측정
config.mode: 'same-origin'htmx 요청의 fetch 모드. 다른 출처 URL은 브라우저가 요청 자체를 거부CSP 없는 페이지에서 hx-get="http://127.0.0.1:3101/…": 네트워크 요청 0건, htmx:error TypeError: Failed to fetch
inlineScriptNonce 미설정조각 속 <script>를 재생성할 때 nonce를 붙이지 않음 → CSP가 있으면 실행 안 됨(3절)
hx-ignore그 아래는 htmx가 처리하지 않음11편 측정

2.x의 selfRequestsOnly·allowEval·allowScriptTags 같은 설정은 4.0.1 기본 설정 목록에 없습니다. 출처 제한은 fetch의 mode로, eval 제한은 CSP와 hx-csp로 옮겨 갔다고 보면 됩니다. 외부 API를 일부러 불러야 한다면 hx-config로 그 요소만 모드를 바꾸고, 그 API는 CORS로 허용해야 합니다.

증상원인해결

    
      
SameSite=Lax인데 CSRF가 됨같은 사이트(다른 포트·하위 도메인)의 공격 페이지Fetch Metadata·Origin 확인

      
CSP를 켜자 콘솔 SPA가 빈 화면정적 index.html의 인라인 import map에 nonce 없음서버가 응답 때 nonce 주입

      
CSP를 켜자 hx-on이 동작 안 함'unsafe-eval' 없음허용하거나 hx-csp + safeEval

      
hx-csp를 켜자 모든 htmx가 멈춤페이지의 script[nonce]가 없거나 요소에 hx-nonce 없음htmx 스크립트 태그에 nonce, 서버가 요소마다 hx-nonce

      
hx-nonce를 상속으로 한 번에 찍음주입된 요소도 상속받아 관문 무력화요소마다 찍기

정리와 다음 편

  
    
    
  1. SameSite=Lax는 다른 사이트만 막는다. 같은 사이트의 다른 출처(측정: localhost:3999)는 Fetch Metadata·Origin 확인으로 막는다.
    2. 
    
  2. CSP는 요청마다 nonce. htmx 포털에서 남는 예외는 hx-on 계열의 eval과 인라인 스타일이다.
    3. 
    
  3. hx-csp는 nonce 관문·승격·도난 방지·safeEval로 HTML 주입을 막고 unsafe-eval을 없앤다. 대신 모든 htmx 요소에 nonce를 찍어야 한다.
    4. 
    
  4. htmx 4는 기본으로 같은 출처에만 요청하고(mode same-origin), 조각 속 스크립트에 nonce를 붙이지 않는다.
    5. 
    
  5. 게이트웨이와 업스트림 사이 신뢰는 서명·만료·대상을 가진 짧은 수명의 신원 주장으로.
    6.
