01시작하기 전에

콜드 스타트는 “기다리면 되는 시간”이 아니라, 자동 확장·장애 복구·멀티모델 공유의 가능 여부를 정하는 값입니다.

기동 시간이 결정하는 것

  • 자동 확장(18편): 트래픽이 늘어 레플리카를 추가해도, 새 Pod가 5분 뒤에 준비되면 그 5분간의 요청은 기존 레플리카가 감당하거나 실패합니다. 기동이 느릴수록 더 일찍, 더 많이 늘려 둬야 해 GPU가 낭비됩니다.
  • 장애 복구: 노드·Pod 장애 후 서비스가 돌아오는 시간(RTO)의 대부분이 엔진 기동입니다.
  • 0으로 축소와 모델 교체: 쓰지 않는 모델을 내려 GPU를 아끼려면, 다시 올리는 시간이 사용자가 참을 수 있는 범위여야 합니다.
  • 업그레이드·설정 변경: 롤링 업데이트 한 번에 레플리카 수 × 기동 시간만큼 용량이 줄어 있습니다.
2025~2026년에 생긴 도구들
  • 쿠버네티스 이미지 볼륨: OCI 이미지를 볼륨으로 마운트하는 기능이 v1.35에서 기본 활성(베타), v1.36(2026년 4월)에서 GA가 되었습니다. containerd 2.1 이상이 필요합니다. 모델 가중치를 컨테이너 이미지처럼 레지스트리로 배포할 수 있습니다.
  • vLLM v0.31.0: 가중치를 GPU에 상주시키는 vllm preload, 초기화된 엔진을 CRIU로 저장·복원하는 vllm snapshot(실험) 추가(4편).
  • llm-d Fast Model Actuation(FMA): v0.9에서 잘 닦인 경로로 추가. vLLM 재우기·깨우기와 모듈을 미리 적재한 런처로 교체·확장을 수초~수십 초로 줄입니다. 같은 릴리스의 ModelExpress는 가중치를 디스크 대신 GPU 간 RDMA로 옮깁니다.

학습 목표

  1. 콜드 스타트를 스케줄링·이미지·가중치 전달·로딩·엔진 초기화 단계로 나눠 측정할 수 있다.
  2. 이미지 사전 배포·미러·P2P·지연 로딩의 효과와 한계를 설명할 수 있다.
  3. 가중치 전달 방식(허브·PVC·오브젝트 스토리지 스트리밍·이미지 볼륨·노드 캐시·P2P)을 비교해 고를 수 있다.
  4. 컴파일 캐시·CUDA 그래프·최적화 레벨이 기동 시간과 실행 성능에 주는 영향을 설명할 수 있다.
  5. 재우기·깨우기, 가중치 상주, 스냅샷, 런처(FMA)가 무엇을 건너뛰는지와 각각의 대가를 설명할 수 있다.
  6. 자동 확장·장애 복구·모델 교체 시나리오별로 기동 전략과 쿠버네티스 설정을 설계할 수 있다.
이 편의 비유: 식당 개점 준비

새 지점을 여는 일(콜드 스타트)은 주방 설비 반입(이미지), 식재료 입고(가중치 전달), 냉장고 정리(로딩), 조리 도구 세팅과 시운전(컴파일·그래프 캡처)으로 이루어집니다. 설비를 미리 깔아 두거나(사전 배포), 식재료를 근처 창고에 두거나(노드 캐시), 시운전 기록을 남겨 다음엔 건너뛰거나(컴파일 캐시) 할 수 있습니다. 가장 빠른 방법은 문을 닫지 않고 불만 꺼 두는 것(재우기)이지만, 그동안에도 임대료(메모리)는 나갑니다.

03이미지 계층

엔진 이미지는 CUDA·torch·커널 라이브러리를 품어 수~십수 GB입니다. 새 노드에서는 이것만으로 몇 분이 걸립니다.

방법원리효과주의
사전 배포 (pre-pull)GPU 노드마다 DaemonSet으로 이미지를 미리 받아 둠이미 있는 노드에서는 구간 2가 0디스크 사용·이미지 GC 정책, 버전 바뀔 때 다시 배포
레지스트리 미러·프록시 캐시사내(또는 같은 리전) 레지스트리에 캐시대역폭↑, 외부 의존·요금 제한 회피캐시 미스 첫 회는 그대로
P2P 배포노드끼리 레이어를 나눠 받음 (Dragonfly·Spegel 등)동시에 많은 노드가 받을 때 레지스트리 병목 해소추가 구성 요소 운영

이미지 다이어트필요 없는 아키텍처 커널·도구 제거크기 자체 감소공식 이미지 대비 유지 부담, 4편 버전 고정 원칙
가중치를 이미지에서 분리엔진 이미지와 모델을 별도로 배포 (4장)엔진 이미지는 공유·재사용, 모델만 교체— (기본 원칙)
모델을 엔진 이미지에 굽지 않는다

“모델까지 넣은 이미지 하나”는 단순해 보이지만, 모델·엔진 중 하나만 바뀌어도 수십 GB 이미지를 다시 만들고 다시 받아야 합니다. 엔진 이미지는 공유, 모델은 별도 경로(PVC·스토리지·이미지 볼륨)로 전달하는 것이 기본입니다. 7편 랩이 이미 이 구조입니다.

04가중치 전달

수십~수백 GB의 가중치를 어디에 두고 어떻게 노드까지 가져오나.

방식첫 기동같은 노드 재기동새 노드운영 포인트
기동 때마다 허브에서 받기느림 (인터넷 대역폭)느림 (emptyDir면 다시)느림1~6편 실습 방식. 운영 금지 (요금 제한·재현성)
노드 로컬 PVC 캐시한 번 받기빠름 (로컬 디스크)그 노드에 다시 받아야 함7편 랩. 노드 고정, 노드 수만큼 복사본
공유 스토리지 (NFS·RWX)공유 볼륨에서 읽기네트워크 읽기바로 가능대용량 동시 읽기 시 스토리지가 병목
오브젝트 스토리지 + 스트리밍 로더S3 등에서 병렬 스트리밍하며 바로 GPU로같음 (캐시 없음)바로 가능vLLM의 Run:ai 스트리머(--load-format runai_streamer) 등. 스토리지·네트워크 대역폭이 곧 속도

노드 로컬 캐시 관리자컨트롤러가 지정 노드들에 미리 받아 둠빠름미리 받아 둔 노드면 빠름KServe LocalModelCache 등. 스케줄링을 캐시 노드로 유도

이미지 볼륨으로 모델 전달하기

yaml · 이미지 볼륨 예시 (Kubernetes 1.36+, containerd 2.1+)
volumes:
- name: weights
  image:
    reference: registry.example.com/models/qwen3-8b-fp8@sha256:<다이제스트>   # 태그 대신 다이제스트
    pullPolicy: IfNotPresent
containers:
- name: engine
  args: ["vllm", "serve", "/models/qwen3-8b-fp8", "--served-model-name", "qwen3-8b"]
  volumeMounts:
  - { name: weights, mountPath: /models/qwen3-8b-fp8, readOnly: true }   # 이미지 볼륨은 읽기 전용
  - { name: hf-cache, mountPath: /tmp/hf }                                 # 쓰기가 필요한 캐시는 별도 emptyDir

모델 이미지는 FROM scratch에 가중치 파일만 복사해 만들거나, 6편의 ModelPack·ORAS 같은 OCI 아티팩트 도구로 만듭니다(런타임이 해당 아티팩트 형식을 마운트할 수 있는지 확인). 이미지 GC가 큰 모델 이미지를 지우지 않도록 노드 디스크 여유와 GC 임계값도 함께 설계합니다.

05가중치 로딩

노드에 도착한 파일을 GPU 메모리까지 옮기는 구간. 포맷과 로더가 속도를 바꿉니다.

로딩 방식 (vLLM --load-format 등)특징맞는 곳
safetensors (기본)메모리 매핑으로 읽어 GPU로 복사. 운영체제 페이지 캐시에 남아 있으면 재기동이 빨라짐기본값
스트리밍 로더 (Run:ai Model Streamer)여러 스레드로 파일을 동시에 읽어 바로 GPU로 보냄. 로컬 디스크와 S3·GCS 등 오브젝트 스토리지 지원오브젝트 스토리지에서 직접 로딩, 빠른 NVMe를 꽉 채워 읽고 싶을 때
fastsafetensorsGPUDirect Storage 등을 활용해 디스크 → GPU 경로를 단축GDS를 지원하는 스토리지·드라이버
미리 분할한 가중치 (sharded state)텐서 병렬 랭크별로 미리 나눠 저장해 각 GPU가 자기 몫만 읽음큰 모델 + 큰 TP에서 로딩 시간 단축
tensorizer 등 직렬화 형식로딩에 최적화된 직렬화 포맷도구 체인이 맞을 때
  • 페이지 캐시의 착시: 같은 노드에서 연달아 재기동하면 파일이 메모리 페이지 캐시에 남아 있어 로딩이 매우 빠르게 보입니다. 측정할 때는 “첫 기동(차가운 디스크)”과 “재기동(따뜻한 캐시)”을 구분해 기록하세요.
  • 양자화가 로딩도 줄인다: FP8은 BF16의 절반, 4비트는 4분의 1을 읽습니다(6편). 온라인 양자화는 반대로 로딩 때 변환 시간이 더해집니다.
  • GB10의 통합 메모리: CPU와 GPU가 같은 메모리를 쓰므로 “디스크 → 호스트 메모리 → GPU 메모리” 복사의 일부가 필요 없지만, 같은 128GB 안에서 페이지 캐시와 모델이 공간을 나눠 쓴다는 점은 기억해야 합니다(8편 메모리 예산).

06엔진 초기화

가중치를 다 올린 뒤에도 vLLM은 성능을 위해 몇 가지 “준비 운동”을 합니다(4편 6장).

준비 단계줄이는 방법대가
torch.compile컴파일 캐시를 영구 볼륨에 두어 같은 모델·설정·버전이면 재사용 (vLLM 캐시 디렉터리를 PVC로)버전·옵션이 바뀌면 캐시 무효. 캐시 디렉터리 관리
CUDA 그래프 캡처캡처할 배치 크기 목록을 실제 트래픽에 맞게 줄이기, -O1목록 밖 배치 크기는 패딩 또는 그래프 없이 실행
둘 다-O0 또는 --enforce-eager매 요청의 TPOT를 영구히 손해. 개발·디버깅 외 비권장
메모리 프로파일링·KV 할당최대 배치·컨텍스트를 실제 요구에 맞추기너무 줄이면 동시성 상한이 낮아짐
워밍업준비 직후 몇 개의 요청으로 커널 캐시를 데움 (첫 사용자 요청이 느리지 않게)준비 시간이 그만큼 늘어남. 프로브와 함께 설계
“기동은 느려도 되는가”를 먼저 정한다

레플리카가 고정이고 재기동이 드물다면 기동 시간보다 실행 성능이 중요하므로 -O2 그대로가 맞습니다. 자동 확장·0으로 축소·잦은 교체가 필요하다면 먼저 캐시·재사용(7장)으로 기동을 줄이고, 그래도 부족할 때만 최적화 레벨을 낮추는 순서로 갑니다.

07프로세스 재사용: 재우기·상주·스냅샷

가장 빠른 기동은 기동하지 않는 것입니다. 이미 준비된 것을 다시 쓰는 방법들.

방법건너뛰는 것남는 시간대가·제약
vLLM 재우기 1단계 (sleep level 1)로딩·컴파일·그래프 전부. 가중치를 CPU 메모리로 내리고 KV를 비움깨우기: 가중치를 GPU로 다시 복사하는 시간 (수십 GB에 수 초 수준)프로세스와 CPU 메모리를 계속 점유. GB10은 CPU·GPU 메모리가 같은 풀이라 메모리가 실제로 비지 않음
vLLM 재우기 2단계 (level 2)컴파일·그래프 (가중치는 버림)가중치 재로딩메모리를 더 비우지만 깨우기가 느림
가중치 상주 (vllm preload, v0.31)엔진 재시작 시 가중치 읽기·양자화엔진 초기화만상주 프로세스가 GPU 메모리를 점유. 설정 변경·크래시 후 재기동에 유리
엔진 스냅샷 (vllm snapshot, 실험)초기화 전체 (CRIU로 프로세스 상태 복원)복원 시간실험 단계, 단일 GPU(TP1) 중심. 드라이버·버전 일치 필요
런처 (llm-d FMA)파이썬 모듈 적재, Pod 스케줄링·이미지 받기새 인스턴스의 로딩·초기화 (웜 스타트: 수십 초)런처 Pod 상주, FMA 컨트롤러 운영
FMA 핫 스타트위 전부 (잠든 인스턴스를 깨움)깨우기 시간잠든 인스턴스가 CPU 메모리 점유, GPU 배정이 맞아야 핫 경로
Pod 스냅샷 (llm-d 가이드)다운로드·초기화복원현재 GKE Sandbox(gVisor) 기반 구현

FMA의 “듀얼 Pod”

재우기·깨우기는 “프로세스는 살아 있는데 GPU는 비어 있는” 상태를 만들지만, 쿠버네티스는 GPU를 Pod 단위로 할당하므로 이 상태를 표현하기 어렵습니다. FMA는 GPU를 예약하는 요청자 Pod와 vLLM 프로세스를 띄우는 런처 Pod를 분리해(듀얼 Pod), 요청자 Pod가 생기면 컨트롤러가 그 GPU에 잠든 인스턴스를 깨우거나(핫), 런처에서 새 인스턴스를 띄웁니다(웜). 요청자 Pod 수를 KEDA로 조절하면 0으로 축소와 빠른 복귀를 함께 얻습니다(18편). FMA는 llm-d-incubation에서 개발 중인 구성 요소로, CRD와 컨트롤러를 따로 설치합니다.

08쿠버네티스 쪽 설정

기동 시간을 측정했으면, 쿠버네티스가 그 시간을 “장애”로 오해하지 않게 맞춥니다.

설정권장이유
startupProbe실패 허용 시간 = 측정한 최악 기동 시간 × 1.5 정도짧으면 기동 중 재시작 무한 반복 (첫 기동은 다운로드·컴파일로 특히 김)
readinessProbe/health + (선택) 워밍업 완료 후 준비첫 사용자 요청이 컴파일·캐시 냉각 비용을 내지 않게
이미지 pullPolicyIfNotPresent + 다이제스트 고정매번 레지스트리 확인·재다운로드 방지
노드 친화성캐시가 있는 노드를 선호 (preferred affinity)로컬 캐시·이미지가 있는 노드로 가면 기동이 빨라짐
우선순위·선점서빙 Pod에 높은 PriorityClass노드가 부족할 때 배치 작업을 밀어내고 빨리 자리 확보 (8편)
롤링 업데이트maxSurge로 새 Pod를 먼저 띄울 GPU 여유가 있는지 확인. 없다면 maxUnavailable로 한 번에 하나씩업데이트 동안 줄어드는 용량 = 레플리카 × 기동 시간
PodDisruptionBudget노드 유지보수 시 한꺼번에 내려가지 않게기동이 느릴수록 동시 재기동이 치명적
이미지 GC 임계값모델·엔진 이미지가 자주 지워지지 않게 디스크 여유와 함께지워지면 다음 기동이 다시 콜드

10MSP 관점

기동 시간은 SLA 문구와 단가에 직접 들어갑니다.

  • RTO를 계약에 쓸 때: “장애 시 15분 내 복구”라면 측정한 최악 기동 시간 + 노드 확보 시간이 그 안에 들어와야 합니다. 들어오지 않으면 N+1 레플리카 비용을 단가에 반영합니다.
  • 0으로 축소 상품: 사용량이 적은 고객 모델을 재워 두면 GPU를 공유할 수 있어 단가를 낮출 수 있지만, “첫 요청 지연”을 SLO에 명시해야 합니다.
  • 웜 풀 비용: 런처·잠든 인스턴스·사전 배포 이미지는 “아무것도 안 하는 동안에도” 메모리·디스크를 씁니다. 그 비용과 기동 시간 단축의 가치를 비교해 고객 등급별로 다르게 적용합니다.
  • 표준 측정: 고객 환경마다 실습 13-1의 타임라인 측정을 표준 점검 항목으로 두면, “왜 느린가”를 감이 아니라 구간별 숫자로 설명할 수 있습니다.

실습 13-1 · 기동 타임라인 측정 (기준선)

python · startup_timeline.py (작업 머신에서)
"""Pod 이벤트·상태와 vLLM 로그 시각을 합쳐 기동 타임라인을 만든다.
사용: python startup_timeline.py [네임스페이스] [Pod 라벨 선택자]   (기본: llmsvc-lab app=llm-engine)"""
import json, re, subprocess, sys
from datetime import datetime

ns = sys.argv[1] if len(sys.argv) > 1 else "llmsvc-lab"
sel = sys.argv[2] if len(sys.argv) > 2 else "app=llm-engine"
k = lambda *a: subprocess.run(["kubectl", "-n", ns, *a], capture_output=True, text=True, check=True).stdout
ts = lambda s: datetime.fromisoformat(s.replace("Z", "+00:00"))

pod = json.loads(k("get", "pod", "-l", sel, "-o", "json"))["items"][-1]
name, t0 = pod["metadata"]["name"], ts(pod["metadata"]["creationTimestamp"])
marks = [("Pod 생성", t0)]
for c in pod["status"].get("conditions", []):
    marks.append((f"조건 {c['type']}", ts(c["lastTransitionTime"])))
for cs in pod["status"].get("containerStatuses", []):
    st = cs.get("state", {}).get("running", {}).get("startedAt")
    if st: marks.append(("컨테이너 시작", ts(st)))
ev = json.loads(k("get", "events", "--field-selector", f"involvedObject.name={name}", "-o", "json"))["items"]
for e in ev:
    t = e.get("lastTimestamp") or e.get("eventTime")
    if t and e["reason"] in ("Scheduled", "Pulling", "Pulled"):
        marks.append((f"이벤트 {e['reason']}: {e['message'][:70]}", ts(t)))
PAT = [("API 서버 시작", r"vLLM API server|Starting vLLM"), ("가중치 로딩 완료", r"Loading weights took|Model loading took"),
       ("컴파일 완료", r"torch\.compile takes|Compil(ation|ing).*(took|finished)"), ("그래프 캡처 완료", r"Graph capturing finished"),
       ("엔진 초기화 완료", r"init engine.*took"), ("HTTP 준비", r"Application startup complete")]
for line in k("logs", name, "--timestamps").splitlines():
    stamp, _, msg = line.partition(" ")
    for label, p in PAT:
        if re.search(p, msg, re.I):
            sec = re.search(r"(\d+(\.\d+)?) ?(s|sec|seconds)", msg)
            marks.append((f"{label}" + (f"  (로그상 {sec.group(1)}s)" if sec else ""), ts(stamp[:26] + "+00:00" if stamp.endswith("Z") else stamp)))
            break
print(f"Pod {name}")
for label, t in sorted(marks, key=lambda x: x[1]):
    print(f"{(t - t0).total_seconds():8.1f}s  {label}")

import time, json, urllib.request
B = "http://llm-engine:8000"
def call(method, path, body=None, timeout=600):
    req = urllib.request.Request(B + path, method=method, data=json.dumps(body).encode() if body else None,
                                 headers={"Content-Type": "application/json"})
    t0 = time.perf_counter(); r = urllib.request.urlopen(req, timeout=timeout); r.read()
    return time.perf_counter() - t0
ask = lambda: call("POST", "/v1/chat/completions", {"model": "qwen3-8b", "max_tokens": 16,
                   "messages": [{"role": "user", "content": "핑 /no_think"}]})

print(f"재우기 (level 1)      {call('POST', '/sleep?level=1')*1000:8.0f} ms")

print(f"깨운 뒤 첫 요청       {ask()*1000:8.0f} ms")

15정리와 체크리스트

핵심 여섯 문장. 이것으로 Level 2가 끝납니다.

  1. 기동 시간은 자동 확장·장애 복구·모델 교체의 가능성을 정한다. 먼저 구간별로 측정한다.
  2. 이미지는 사전 배포·미러·P2P로, 모델은 이미지와 분리해 노드 캐시·스트리밍·이미지 볼륨으로 전달한다.
  3. 로딩은 포맷과 로더가 좌우하고, 페이지 캐시 때문에 첫 기동과 재기동을 구분해 측정해야 한다.
  4. 컴파일 캐시는 영구 볼륨에 두고, 최적화 레벨을 낮추는 것은 마지막 수단이다(실행 성능을 영구히 잃음).
  5. 재우기·상주·스냅샷·런처는 기동을 건너뛴다. 대가는 상주 메모리이며, GB10은 통합 메모리라 재우기의 이득이 제한적이다.
  6. 쿠버네티스 설정은 측정값을 따른다: startupProbe, 캐시 노드 친화성, 롤링 업데이트, PDB, 이미지 GC.
