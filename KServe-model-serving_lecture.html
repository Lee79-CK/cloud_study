모델 파일 하나를 실제 서비스로 만들려면 오토스케일링, 라우팅, 롤아웃, GPU 스케줄링, 모델 다운로드를 전부 직접 짜야 합니다. KServe는 그 전부를 InferenceService 한 장의 YAML 뒤로 숨깁니다. 이 강의는 KServe v0.20 기준으로, 예측형 모델부터 LLM까지 서빙 전 과정을 다룹니다.

두 흐름의 차이가 이 강의의 뼈대입니다. 예측형은 게이트웨이가 아무 파드에나 보내면 되지만, 생성형은 어느 파드에 보내느냐가 응답 속도를 몇 배 바꿉니다. 왜 그런지는 14장에서 다룹니다.

01

모델 하나 띄우는 데 왜 이렇게 많은 게 필요한가

KServe를 배우기 전에, KServe가 없을 때 무엇을 직접 해야 하는지부터 보는 게 빠릅니다.

학습이 끝난 모델 파일이 S3에 하나 올라가 있다고 합시다. 이걸 사내 서비스가 호출할 수 있는 HTTP 엔드포인트로 만들어야 합니다. 쿠버네티스를 안다면 머릿속에 이런 목록이 떠오를 겁니다.

모델을 파드 안으로

S3에서 받아와야 합니다. 이미지에 구워 넣을까요, initContainer로 받을까요? 자격증명은 어디에 둘까요?

추론 서버 컨테이너

sklearn이면 어떤 서버? PyTorch면? 프레임워크마다 서버가 다르고 API 모양도 제각각입니다.

오토스케일링

HPA를 붙일까요? CPU 기준으로? GPU 모델이면 CPU 사용률은 의미가 없는데요.

라우팅과 배포

Service, Ingress, 그리고 새 모델 버전을 10%만 태워 보려면 트래픽 분할도 필요합니다.

헬스체크

모델 로딩에 3분 걸리는데 livenessProbe가 먼저 죽이면? startupProbe를 따로 잡아야 합니다.

관측

추론 지연시간, 요청 수, 모델별 에러율. 메트릭을 직접 뽑아 노출해야 합니다.

이 목록을 YAML로 옮기면 Deployment + Service + HPA + Ingress + ConfigMap + ServiceAccount, 못해도 150줄입니다. 그리고 모델이 늘어날 때마다 이 150줄을 복사합니다. 모델이 40개면 6000줄짜리 저장소가 생깁니다.

KServe는 이 반복을 CRD 하나로 접습니다. 직접 만드는 대신 무엇을 원하는지만 선언하고, 나머지는 컨트롤러가 만들게 하는 방식입니다.

같은 모델, 두 가지 방법탭을 눌러 비교해 보세요
sklearn-iris-manual.yaml — 전체의 약 1/3
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sklearn-iris
spec:
  replicas: 2

        args: ["--model_dir=/mnt/models", "--http_port=8080"]

이 14줄이 Deployment, Service, 스토리지 초기화 컨테이너, 오토스케일러, 라우트, 메트릭 엔드포인트를 전부 만들어 냅니다. 카나리를 붙이려면 아래에 네 줄을 더합니다(10장).

KServe가 실제로 대신해 주는 것

직접 하면KServe에서는
모델 다운로드 코드 작성storageUri 한 줄. s3://, gs://, hf://, pvc://, oci:// 지원
프레임워크별 추론 서버 이미지 관리modelFormat 이름만 적으면 맞는 ServingRuntime이 붙음
HPA 규칙 튜닝동시 요청 수 기준 스케일, 0까지 축소도 옵션
Ingress 가중치 수정으로 카나리canaryTrafficPercent 숫자 하나
모델마다 API 스펙이 다름V1 / Open Inference Protocol / OpenAI 호환으로 통일
LLM 라우팅을 직접 구현KV 캐시 인지 라우팅이 기본 탑재 (14장)
KServe는 추론 엔진이 아닙니다.

실제로 텐서를 굴리는 건 vLLM, Triton, TorchServe 같은 런타임입니다. KServe는 그 위에서 수명주기·확장·라우팅·거버넌스를 담당하는 관리 층입니다. 이 구분을 처음에 잡아 두면 나머지가 전부 쉬워집니다.

KServe의 현재 위치

KServe는 2025년 11월 CNCF Incubating 프로젝트가 되었습니다. 원래 Kubeflow의 KFServing으로 시작해 독립한 프로젝트이고, 지금은 예측형 AI와 생성형 AI를 하나의 플랫폼에서 다루는 것을 목표로 합니다. 이 강의의 기준은 v0.20.0(2026년 8월 6일)입니다.

02

전체 그림: 컨트롤 플레인과 데이터 플레인

KServe를 이해하는 가장 빠른 축은 "YAML을 읽고 리소스를 만드는 쪽"과 "실제 요청을 처리하는 쪽"을 나누는 것입니다.

컨트롤 플레인 control plane

사용자가 만든 CRD를 읽고, 그에 맞는 쿠버네티스 리소스(Deployment, Service, HPA, HTTPRoute…)를 만들고 상태를 맞춥니다. 요청이 한 건도 없어도 계속 돌아갑니다.

대표 주자: kserve-controller-manager

데이터 플레인 data plane

실제 추론 요청이 흐르는 경로입니다. 게이트웨이 → (스케줄러) → 추론 파드 → 응답. 컨트롤러가 죽어도 데이터 플레인은 계속 요청을 처리합니다.

대표 주자: vLLM 파드, Triton 파드, Envoy

이 둘이 분리돼 있다는 점이 운영에서 중요합니다. 컨트롤러 파드를 재시작해도 서비스 중인 모델은 멀쩡합니다. 반대로 말하면, 컨트롤러가 죽어 있으면 새 배포나 스케일 변경만 안 됩니다.

v0.17부터 컨트롤러가 셋으로 쪼개졌다

예전 KServe는 컨트롤러 하나가 전부를 담당했습니다. v0.17에서 모듈형 구조로 바뀌면서 세 개의 독립 컴포넌트가 되었습니다. 이건 설치 방법과 업그레이드 절차를 통째로 바꾼 변화라 반드시 알아야 합니다.

컴포넌트담당 CRD언제 필요한가
kserve (코어)
필수		 InferenceService, ServingRuntime, ClusterServingRuntime, InferenceGraph, TrainedModel 항상. 예측형 모델 서빙의 본체이고, 다른 컴포넌트도 이걸 전제로 합니다.
llmisvc
LLM용		 LLMInferenceService, LLMInferenceServiceConfig LLM을 본격적으로 서빙할 때. KV 캐시 인지 라우팅, prefill/decode 분리, 멀티노드 추론이 여기에 들어 있습니다.
localmodel
선택		 LocalModelCache, LocalModelNode, LocalModelNodeGroup 모델이 수십 GB라 파드 기동마다 다시 받는 게 견딜 수 없을 때. 노드 로컬 디스크에 캐시합니다.
초보자를 위한 지름길.

전통 ML만 한다면 kserve만 설치하세요. LLM을 다룬다면 kserve + llmisvc. 모델 로딩 시간이 문제가 되기 전까지는 localmodel은 건드리지 않아도 됩니다.

요청이 지나가는 경로 — 두 갈래

예측형 경로

게이트웨이(Istio 또는 Gateway API)가 호스트명으로 InferenceService를 찾고, 파드로 넘깁니다. 파드 안에는 보통 두 개의 컨테이너가 있습니다. 모델을 내려받는 스토리지 이니셜라이저와 실제 추론 서버입니다. 로드밸런싱은 평범한 라운드로빈이면 충분합니다. 요청마다 계산량이 비슷하니까요.

생성형 경로

여기서 이야기가 달라집니다. LLM 요청은 길이도, 계산량도, "이 파드가 이미 갖고 있는 캐시"도 전부 제각각입니다. 그래서 KServe는 앞단에 두 층을 더 놓습니다.

  • Envoy AI Gateway — 요청 수가 아니라 토큰 수로 한도를 겁니다. LLM에서는 요청 1건의 비용이 100배까지 차이 나기 때문입니다.
  • EPP(Endpoint Picker Pod) — GIE가 정의한 확장점으로, 어느 파드가 이 요청을 가장 싸게 처리할지 실시간으로 채점합니다.
llm-d가 뭔가요?

LLMInferenceService의 속은 llm-d 프레임워크입니다. KServe는 llm-d의 스케줄러·라우터를 쿠버네티스 CRD로 감싸서, 사용자가 YAML 한 장으로 쓰게 만들어 줍니다. 이름이 낯설어도 직접 만질 일은 거의 없습니다.

차트가 왜 열 개인가

  
CRD와 컨트롤러를 분리하는 것은 쿠버네티스 오퍼레이터의 오래된 관행입니다. CRD를 지우면 그 CRD로 만든 모든 리소스가 함께 지워지므로, helm uninstall 한 번에 서비스 중인 모델이 전부 날아가는 사고를 막으려고 따로 뗍니다. 여기에 컴포넌트가 셋이니 3×2(full/minimal) = 6개의 CRD 차트, 그리고 리소스 차트 4개가 됩니다.


  

    

      
차트들어 있는 것

      
kserve-crd / -minimalInferenceService 등 코어 CRD. minimal은 OpenAPI 검증 스키마를 뺀 경량판

      
kserve-llmisvc-crd / -minimalLLMInferenceService CRD (스키마가 커서 full은 213KB)

      
kserve-localmodel-crd / -minimal모델 캐시 CRD

      
kserve-resources코어 컨트롤러, 웹훅, RBAC, inferenceservice-config ConfigMap

      
kserve-llmisvc-resourcesllmisvc 컨트롤러와 웹훅

      
kserve-localmodel-resources캐시 컨트롤러 + 노드 에이전트 DaemonSet

      
kserve-runtime-configsClusterServingRuntime 목록과 LLMIsvc 기본 설정 템플릿

    

  


  

    full과 minimal, 뭘 고르나요?
    
처음엔 full을 쓰세요. YAML을 잘못 썼을 때 kubectl apply 단계에서 이유를 알려 줍니다. minimal은 검증을 건너뛰므로 잘못된 값이 컨트롤러까지 가서 이상한 에러로 터집니다. minimal은 CRD 용량과 API 서버 메모리가 빡빡한 대규모 클러스터에서 쓰는 선택지입니다.

modelFormat: {name: sklearn}이라고만 썼는데 어떻게 알맞은 이미지가 뜨는지, 그 중간 단계입니다.


  
ServingRuntime은 "이 포맷을 처리할 수 있는 서버는 이 이미지, 이 인자, 이 포트"를 적어 둔 템플릿입니다. 클러스터 전체에 적용되는 ClusterServingRuntime과, 네임스페이스 안에서만 쓰는 ServingRuntime 두 가지가 있습니다.


  

    
ClusterServingRuntime 예시 (요약)


apiVersion: serving.kserve.io/v1alpha1
kind: ClusterServingRuntime
metadata:
  name: kserve-sklearnserver
spec:
  annotations:
    prometheus.kserve.io/port: '8080'
  supportedModelFormats:          # ← 매칭의 핵심
  - name: sklearn
    version: "1"
    autoSelect: true             # false면 runtime: 으로 직접 지정해야 함
    priority: 1                  # 같은 포맷을 여러 런타임이 지원할 때 우선순위
  protocolVersions: [v1, v2]
  containers:
  - name: kserve-container
    image: kserve/sklearnserver:v0.20.0
    args:
    - --model_name={{.Name}}
    - --model_dir=/mnt/models
    resources:
      requests: {cpu: "1", memory: "2Gi"}

    4. 
    
  4. protocolVersion을 지정했다면 그 프로토콜을 지원하는 런타임만 후보가 됩니다.

Knative 모드 vs Standard 모드

    
  

  
KServe 도입에서 가장 되돌리기 어려운 결정입니다. 클러스터 전체 기본값이 되고, 의존성 스택이 통째로 달라집니다.


  

    

      
Knative 모드 serverless

      
isvc가 Knative Service로 변환됩니다. 요청이 없으면 파드를 0개까지 줄이고, 요청이 오면 다시 띄웁니다. 리비전 단위 트래픽 분할이 공짜로 따라옵니다.

      
추가 설치: Knative Serving + Istio(또는 Kourier)

    

    

      
Standard 모드 raw k8s

      
평범한 Deployment + Service + HPA를 만듭니다. 예전 이름은 RawDeployment. 쿠버네티스를 아는 사람이라면 무슨 일이 일어나는지 전부 보입니다.

      
추가 설치: Gateway API 또는 Ingress 컨트롤러

    

  


  

    

      
항목Knative 모드Standard 모드

      
0까지 축소가능 — 유휴 모델의 GPU를 반납기본적으로 불가 (KEDA를 붙이면 가능)

      
오토스케일링 기준동시 요청 수(KPA). 추론 워크로드에 잘 맞음CPU·메모리·커스텀 메트릭(HPA)

      
카나리리비전 기반, canaryTrafficPercent 한 줄v0.20부터 spec.canary로 지원

      
요청 경로activator·queue-proxy 홉이 추가됨게이트웨이 → 파드. 홉이 짧음

      
GPU 워크로드0→1 복귀에 모델 로딩 시간이 그대로 노출됨파드를 상주시켜 예측 가능하게 운영

      
운영 난이도Knative까지 알아야 함. 장애 시 층이 하나 더익숙한 Deployment 디버깅 그대로

오토스케일링: CPU 사용률로는 안 되는 이유

    
  

  
추론 워크로드는 일반 웹 서버와 스케일 신호가 다릅니다. KServe는 네 가지 스케일러를 제공하고, 워크로드에 따라 정답이 갈립니다.


  
왜 CPU 사용률이 나쁜 신호일까요. GPU 추론 파드는 GPU가 100% 타고 있어도 CPU는 15%일 수 있습니다. 반대로 요청이 큐에 30개 쌓여 사용자가 5초씩 기다리는데 CPU는 여유로울 수 있습니다. 실제 압력은 동시 요청 수, 큐 깊이, KV 캐시 점유율에 나타납니다.


  

    
스케일러신호0까지 축소주 용도

HPACPU · 메모리 · 커스텀 메트릭불가Standard 모드의 기본

    
KEDA프로메테우스 등 외부 메트릭가능큐 깊이·토큰 처리량 기준 스케일

    
WVA (Workload Variant Autoscaler)KV 캐시 점유율 + 큐 깊이가능 (KEDA 경유)LLM 전용. LLMInferenceService에서

LLM 전용: WVA

  
WVA는 프로메테우스에서 KV 캐시 사용률과 큐 깊이를 계속 읽어, 서버가 포화에 가까워졌는지 판단합니다. 그리고 필요한 레플리카 수를 wva_desired_replicas라는 메트릭으로 내보냅니다. 실제 스케일은 HPA나 KEDA가 그 값을 읽어 수행합니다.

  
WVA의 흥미로운 점은 variant 개념입니다. 같은 모델이라도 "A100 4장 TP=4"와 "H100 2장 TP=2"는 비용이 다른 별개의 변형입니다. variantCost에 상대 비용을 적어 두면, 수요가 늘 때 싼 변형부터 늘리고 줄일 때 비싼 변형부터 줄입니다.

  

    
wva-scaling.yaml


spec:
  scaling:
    minReplicas: 1
    maxReplicas: 10
    wva:
      variantCost: "15.0"          # 기본값 10.0. 낮을수록 먼저 늘어난다
      keda:
        pollingInterval: 30
        cooldownPeriod: 300
        idleReplicaCount: 0       # 유휴 시 0까지
        fallback:
          failureThreshold: 3
          replicas: 2            # 메트릭 파이프라인이 죽어도 2개는 유지

  

  
fallback은 반드시 넣으세요.
프로메테우스가 잠깐 죽으면 메트릭이 0으로 보일 수 있습니다. fallback이 없으면 오토스케일러가 "수요 없음"으로 판단해 프로덕션 파드를 0으로 줄일 수 있습니다.

  
v0.19부터 오토스케일링 리소스의 건강 상태가 ScalingReady, PrefillScalingReady 조건으로 서비스 상태에 바로 드러납니다. HPA나 ScaledObject를 따로 들여다보지 않아도 kubectl describe 한 번으로 보입니다.

카나리 배포: 새 모델을 10%에게만

    
  

  
모델 교체는 코드 배포보다 위험합니다. 문법 오류처럼 명확히 터지지 않고, 조용히 정확도만 떨어지기 때문입니다.


  
그래서 새 모델은 전체 트래픽의 일부만 받게 하고, 지표를 본 뒤 올립니다. KServe는 배포 모드에 따라 두 가지 방식을 제공합니다.


  

    
    
  

  

    
isvc의 storageUri를 바꾸면 새 리비전이 생깁니다. canaryTrafficPercent를 주면 그 비율만 새 리비전으로 갑니다.

    

      
canary-knative.yaml


spec:
  predictor:
    canaryTrafficPercent: 10       # 새 리비전이 10%
    model:
      modelFormat: {name: sklearn}
      storageUri: "s3://models/iris-v2"  # 바뀐 부분

    

    
확인 방법: kubectl get isvc의 PREV와 LATEST 열에 트래픽 비율이 그대로 보입니다. 되돌리려면 canaryTrafficPercent: 0, 승격하려면 그 필드를 지우면 됩니다.

  

  

    
v0.20에서 Standard 모드에도 카나리가 생겼습니다. spec.canary 목록에 이름과 트래픽 비율을 적으면 각 카나리가 자기 Deployment와 Service를 갖습니다.

    

      
canary-standard.yaml


spec:
  predictor:
    model:
      modelFormat: {name: sklearn}
      storageUri: "gs://bucket/models/sklearn/model"
    minReplicas: 4
  canary:
  - trafficPercent: 25
    predictor:
      name: v2
      model:
        modelFormat: {name: sklearn}
        storageUri: "gs://bucket/models/sklearn/model-2"

    

    
    
      
  • 레플리카 수는 트래픽 비율에서 유도됩니다. 위 예에서 stable 4개면 카나리는 그 25% 수준입니다.
    • 
      
  • 승격은 재시작 없이 이루어집니다. stable predictor 이름을 카나리 Deployment로 돌려 붙이는 방식이라 파드가 새로 뜨지 않습니다.
    • 
      
  • 롤백은 canary 항목을 지우면 됩니다. 남은 리소스는 자동 정리됩니다.
    •

InferenceGraph: 모델 여러 개를 엮기

    
  

  
실제 서비스는 모델 하나로 안 끝납니다. 언어를 먼저 감지하고, 그에 맞는 분류기로 보내고, 결과 두 개를 합치는 식이죠.


  
이걸 애플리케이션 코드로 짜면 모델 토폴로지가 서비스 코드에 박힙니다. InferenceGraph는 그 연결을 별도의 CRD로 빼내, 모델 구성만 바꿔 배포할 수 있게 합니다.


  
네 가지 라우터 타입

  

    
타입동작대표 용례

Switch조건이 맞는 첫 스텝 하나만 실행입력 값에 따라 다른 모델로 분기

Splitter가중치대로 하나에만 보냄 (합 100)A/B 테스트, 점진적 트래픽 이동

Batcher — 작은 요청을 묶어서 처리

  
GPU는 요청 1건을 처리하나 32건을 한 번에 처리하나 걸리는 시간이 크게 다르지 않습니다. 개별 요청이 드문드문 들어오는 상황이라면, 짧은 시간 모아서 한 배치로 넘기는 편이 처리량이 훨씬 좋습니다.

  

    
batcher.yaml


spec:
  predictor:
    batcher:
      maxBatchSize: 32       # 최대 몇 건까지 묶을지

KV 캐시 인지 라우팅: 이 강의의 핵심

    
  

  
"어느 파드로 보낼까"를 잘 고르는 것만으로 첫 토큰 지연이 몇 배 줄어듭니다. 왜 그런지부터 봅시다.


  
먼저: KV 캐시가 뭔가

  
LLM이 토큰을 하나 만들 때마다, 앞의 모든 토큰에 대한 계산 결과(Key와 Value 텐서)가 필요합니다. 매번 처음부터 다시 계산하면 길이가 길어질수록 제곱으로 느려지므로, 계산해 둔 K/V를 GPU 메모리에 보관합니다. 이것이 KV 캐시입니다.


  
여기서 중요한 성질이 나옵니다. 어떤 요청의 프롬프트 앞부분이 이전 요청과 같다면, 그 부분의 KV는 이미 계산돼 있습니다. 다시 계산할 필요가 없습니다.


  

    
멀티턴 대화
3번째 질문의 프롬프트는 1·2번째 대화 전체를 포함합니다. 앞의 90%가 이미 계산돼 있습니다.

    
RAG
같은 문서 청크를 여러 질문이 공유합니다. 문서 부분의 KV를 재사용할 수 있습니다.

    
공통 시스템 프롬프트
모든 요청이 같은 2000토큰 시스템 프롬프트로 시작한다면, 그 2000토큰은 딱 한 번만 계산하면 됩니다.

  


  

    하지만 캐시는 파드마다 따로 있습니다.
    
파드 4개 중 1번이 그 대화의 캐시를 갖고 있는데 라운드로빈이 3번으로 보내면, 3번은 프롬프트를 처음부터 전부 다시 계산합니다(프리필). 프롬프트가 8000토큰이면 이 낭비는 수 초짜리입니다. 라우터가 캐시 상태를 모르면 캐시가 있으나마나입니다.

큰 모델 굴리기: prefill/decode 분리와 병렬화

    
  

  
GPU 한 장에 안 들어가는 모델, 그리고 한 파드 안에서 서로 다른 성격의 작업이 섞여 낭비되는 문제를 다룹니다.


  
prefill과 decode는 다른 일이다

  

    

      
Prefill (프리필)

      
입력 프롬프트 전체를 한 번에 읽어 KV 캐시를 채우는 단계. 토큰 수천 개를 병렬로 처리하므로 연산(FLOPs) 집약적입니다. GPU 코어를 꽉 채웁니다.

      
이 단계의 길이가 곧 TTFT(첫 토큰까지 시간)입니다.

    

    

      
Decode (디코드)

      
토큰을 하나씩 뽑는 단계. 매 스텝마다 모델 가중치 전체와 KV 캐시를 읽어야 해서 메모리 대역폭 집약적입니다. 연산 유닛은 놀고 있습니다.

      
이 단계의 속도가 곧 초당 토큰 수입니다.

    

  


  
둘을 같은 파드에 두면 어떻게 될까요. 긴 프롬프트 하나가 프리필을 도는 동안, 그 파드에서 디코드 중이던 다른 요청들이 끊깁니다. 사용자 입장에서는 토큰이 흐르다가 뚝 멈추는 현상으로 보입니다.


  
분리하면 각 단계를 독립적으로 스케일하고, 서로 다른 GPU를 쓸 수도 있습니다. 대신 프리필이 만든 KV 캐시를 디코드 파드로 전송해야 합니다. KServe는 이 전송에 NixlConnector와 RDMA(RoCE)를 씁니다.

  prefill:                   # ← 이 블록이 있으면 분리 모드
    replicas: 2
    template:
      spec:
        containers:
          - name: vllm
            resources: {limits: {nvidia.com/gpu: "1"}}
  router:
    gateway: {managed: {}}
    route: {httpRoute: {}}
    scheduler: {pool: {}}

병렬화: 모델을 여러 GPU에 쪼개기

  

    
방식무엇을 쪼개나언제 쓰나

    
Tensor Parallelism (TP)한 레이어의 행렬을 여러 GPU에 나눠 계산모델이 GPU 한 장의 메모리에 안 들어갈 때. 노드 안에서 씁니다(GPU 간 통신이 잦아 NVLink가 필요)

    
Data Parallelism (DP)모델 전체 복제본을 여러 개처리량을 늘릴 때. 사실상 레플리카 늘리기

    
Data-Local Parallelism노드당 GPU 수를 고정NUMA 친화도를 맞춰 노드 간 통신을 줄일 때

    
Expert Parallelism (EP)MoE 모델의 전문가들을 여러 GPU에Mixture-of-Experts 구조 모델을 서빙할 때

  


  

    
multi-node.yaml


spec:
  model:
    uri: hf://meta-llama/Llama-3.1-70B-Instruct
  replicas: 8
  parallelism:
    tensor: 4          # 노드 안 GPU 4장에 레이어를 쪼갠다
    data: 8            # 전체 복제본 8벌
    dataLocal: 4       # 노드당 GPU 4장
  template:
    spec:
      containers:
        - name: vllm
          resources: {limits: {nvidia.com/gpu: "4"}}
  worker:                  # 리더 외의 워커 파드 스펙
    spec:
      containers:
        - name: vllm
          resources: {limits: {nvidia.com/gpu: "4"}}

  

  
멀티노드 배포는 내부적으로 LeaderWorkerSet으로 구현됩니다. 리더 파드 1개와 워커 파드 N개가 한 덩어리로 스케일되고, 하나가 죽으면 그룹 전체가 재시작됩니다. 모델 파라미터가 노드에 걸쳐 있으니 당연한 동작입니다.

    v0.16 이하에서 v0.17 이상으로는 helm upgrade가 통하지 않습니다.
    
차트가 하나에서 열 개로 재편됐기 때문입니다. 공식 업그레이드 가이드의 단계별 마이그레이션을 따라야 하고, 반드시 비운영 환경에서 먼저 검증하세요.

  

  
마이그레이션의 핵심은 CRD를 살려 둔 채 릴리스만 갈아 끼우는 것입니다. Helm이 CRD를 지우지 않도록 보존 어노테이션을 붙였다가, 끝나면 떼는 방식입니다.

  

    
upgrade-pattern.sh (개념)


# 1) CRD가 삭제되지 않도록 보존 어노테이션
for crd in $(kubectl get crd -o name | grep kserve); do
  kubectl annotate "$crd" helm.sh/resource-policy=keep --overwrite
done

# 2) 새 구조의 CRD 차트 설치/업그레이드
helm upgrade -i kserve-crd oci://ghcr.io/kserve/charts/kserve-crd \
  --version v0.20.0 --namespace kserve --create-namespace

# 3) llmisvc를 쓴다면 함께
helm upgrade -i kserve-llmisvc-crd oci://ghcr.io/kserve/charts/kserve-llmisvc-crd \
  --version v0.20.0 --namespace kserve

# 4) 리소스 차트들 업그레이드 … (생략)

# 5) 보존 어노테이션 제거
for crd in $(kubectl get crd -o name | grep kserve); do
  kubectl annotate "$crd" helm.sh/resource-policy- --overwrite
done

파드가 Init:0/1에서 넘어가지 않는다
    

      
스토리지 이니셜라이저가 모델을 받는 중이거나, 받지 못하고 있습니다.

      
확인


kubectl logs <pod> -c storage-initializer -f

      
    
        
  • 진행 중 — 대용량 모델이면 정상입니다. 6장의 캐시 기법을 검토하세요.
    • 
        
  • AccessDenied / 403 — ServiceAccount에 자격증명이 안 붙었거나 버킷 권한 부족.
    • 
        
  • NoSuchKey / 404 — storageUri 경로 오타. 디렉터리를 가리켜야 하는데 파일을 가리켰거나 그 반대.
    • 
        
  • 디스크 부족 — emptyDir 기본 크기가 노드 디스크에 묶여 있습니다. 대형 모델은 PVC를 쓰세요.

No such file or directory: '/mnt/models'
    

      
스토리지 이니셜라이저가 아예 주입되지 않았다는 뜻입니다. 순서대로 확인하세요.

      
    
        
  1. 네임스페이스에 control-plane 라벨이 붙어 있지 않은지. 웹훅이 이런 네임스페이스를 의도적으로 건너뜁니다.
    2. 
        
  2. 커스텀 컨테이너를 쓴다면 이름이 kserve-container인지.
    3. 
        
  3. 커스텀 컨테이너에 STORAGE_URI 환경변수를 줬는지.
    4. 
        
  4. 웹훅 파드가 살아 있는지, 인증서가 만료되지 않았는지(kubectl get validatingwebhookconfiguration).
    5. 
      

    

  


  
isvc가 READY=False인데 파드는 Running이다
    

      
파드는 떴지만 라우팅이나 준비 조건이 안 맞는 상태입니다.

      
확인


kubectl get isvc <name> -o jsonpath='{.status.conditions}' | jq
kubectl describe isvc <name> | tail -40

      
    
        
  • IngressReady=False — 게이트웨이나 HTTPRoute 문제. Gateway 리소스가 주소를 받았는지 확인.
    • 
        
  • readinessProbe 실패 — 모델은 로딩됐는데 헬스 경로가 다릅니다. 커스텀 서버라면 /v1/models/<name> 또는 /v2/health/ready를 구현했는지.
    • 
        
  • Knative 모드 — activator 경유 여부, 리비전 상태를 함께 확인(kubectl get revision).
    • 
      

    

  


  
런타임을 못 찾는다 — No matching runtime
    

      
    
        
  • kubectl get clusterservingruntimes가 비어 있다면 kserve-runtime-configs 차트를 설치하지 않은 것입니다. 가장 흔한 원인입니다.
    • 
        
  • modelFormat.name 철자 확인. sklearn이지 scikit-learn이 아닙니다.
    • 
        
  • protocolVersion: v2를 줬는데 그 런타임이 v2를 지원하지 않는 경우.
    • 
        
  • 같은 포맷을 여러 런타임이 같은 priority로 지원하면 모호성 오류가 납니다. runtime:으로 직접 지정하세요.
    • 
      

    

  


  
GPU 파드가 Pending에서 안 움직인다
    

      
확인


kubectl describe pod <pod> | grep -A10 Events
kubectl get nodes -o custom-columns='NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu'

      
    
        
  • Insufficient nvidia.com/gpu — 남은 GPU가 없습니다. 다른 워크로드가 점유 중이거나 클러스터 오토스케일러가 노드를 못 띄우고 있습니다.
    • 
        
  • taint 불일치 — GPU 노드에 taint가 있는데 파드에 toleration이 없습니다.
    • 
        
  • 멀티노드(LWS) — 리더+워커가 동시에 스케줄 가능해야 그룹이 뜹니다. 부분 배치만 가능하면 전체가 Pending입니다.
    • 
        
  • DRA 사용 시 — ResourceClaim이 만족되지 않았을 수 있습니다. kubectl get resourceclaims로 확인.
    • 
      

    

  


  
LLM 응답이 느리다 — TTFT가 튄다
    

      
14장·15장의 내용이 전부 여기서 만납니다. 확인 순서를 권합니다.

      
    
        
  1. 프리픽스 캐시 적중률이 낮다면 EPP 라우팅이 어긋난 것입니다. EPP 파드가 살아 있는지, 스케줄링 프로파일의 가중치가 적절한지 확인.
    2. 
        
  2. KV 캐시 사용률이 포화면 캐시가 계속 밀려나고 있습니다. 레플리카를 늘리거나 v0.20의 kvCacheOffloading을 검토.
    3. 
        
  3. 큐 깊이 상승 — 오토스케일이 못 따라갑니다. WVA 임계값과 KEDA 폴링 주기를 조정.
    4. 
        
  4. 긴 프롬프트가 섞여 있다 — 프리필이 디코드를 밀어냅니다. P/D 분리를 검토(단 15장의 경고 참고).
    5. 
        
  5. 모델이 방금 뜬 파드 — 워밍업 중일 수 있습니다. startup probe와 워밍업 요청을 설정하세요.
    6. 
      

    

  


  
롤링 업데이트 때 응답이 중간에 끊긴다
    

      
v0.19의 우아한 종료 설정이 적용되지 않았거나, 시간이 부족한 경우입니다.

      
    
        
  • terminationGracePeriodSeconds가 60 미만이면 vLLM의 드레인 시간이 부족합니다.
    • 
        
  • 매우 긴 생성(수천 토큰)을 다룬다면 이 값을 120 이상으로 늘리세요.
    • 
        
  • preStop의 15초 sleep은 EPP가 라우팅을 멈추기 위한 시간입니다. 이걸 없애면 종료 중인 파드로 새 요청이 들어갑니다.
    • 
      

    

  


  
업그레이드 후 CRD 관련 에러가 쏟아진다
    

      
    
        
  • v0.16 이하에서 단순 helm upgrade를 시도한 경우가 대부분입니다. 17장의 마이그레이션 절차로 되돌아가세요.
    • 
        
  • ClusterStorageContainer CRD가 삭제됐다면 스토리지 설정이 통째로 사라집니다. v0.19에서 이를 막는 수정이 들어갔지만, 그 이전 버전에서 업그레이드한다면 백업이 필수입니다.
    • 
        
  • minimal CRD로 설치한 클러스터에서 변환 웹훅이 필요한 상황이 생길 수 있습니다. v0.19부터 minimal 설치에서도 변환 웹훅이 활성화됩니다.
    • 
      

    

  


  
메트릭이 프로메테우스에 안 잡힌다
    

      
    
        
  • ServingRuntime의 prometheus.kserve.io/port, /path 어노테이션 확인.
    • 
        
  • ServiceMonitor의 셀렉터가 KServe가 만든 Service의 라벨과 맞는지. v0.19부터 spec.labels가 워크로드 Service로 전파되므로 이걸 셀렉터 키로 쓰면 편합니다.
    • 
        
  • Knative 모드에서는 queue-proxy가 별도 포트로 메트릭을 냅니다. 두 소스를 모두 수집해야 그림이 완성됩니다.
    • 
      

    

  


  
트래픽 분할 그룹이 Degraded로 뜬다 (llmisvc)
    

      
v0.20의 GroupDegraded 조건입니다. 그룹 멤버 중 일부가 준비되지 않았다는 뜻인데, 서비스 자체의 Ready는 유지됩니다. 즉 추론은 계속 됩니다.

      
    
        
  • 새로 올린 버전의 파드가 뜨지 못하고 있는지 확인. 모델 다운로드나 GPU 부족이 흔한 원인입니다.
    • 
        
  • 여러 llmisvc가 같은 모델 라우팅 이름을 쓰면 충돌 경고가 납니다. 이름을 유일하게 맞추세요.
