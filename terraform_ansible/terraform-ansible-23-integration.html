Terraform & Ansible 강의 · Level 5 통합·MSP 실전 · 23편 / 26편 · 시리즈 목차

바통을 어디서, 어떻게 넘길 것인가 Terraform + Ansible 통합 패턴 — 핸드오프 4가지(출력 → 인벤토리, cloud-init/user_data, Terraform ansible 프로바이더, AWX 트리거), local-exec 안티패턴, 책임 경계 그리기

1편 12장에서 “Terraform은 서버를 만들고, Ansible은 서버 안을 구성한다”고 나눴습니다. 그 사이에는 반드시 넘겨주는 순간이 있습니다 — 어떤 서버가 생겼는지, 어디로 접속하는지, 언제 구성을 시작할지. 이 바통을 잘못 넘기면 Terraform plan이 매번 변경을 보이거나, 플레이북 변경이 무시되거나, 구성이 한 번 실패했다고 서버가 통째로 다시 만들어집니다. 이번 편은 네 가지 넘기는 방법과 하지 말아야 할 방법을 모두 실제로 돌려 보고, 무엇을 어느 도구가 맡을지 경계를 긋습니다.

Ansible

이번 편의 목표와 실측 범위

이번 편을 마치면

  • 네 가지 핸드오프의 동작·장단점을 설명하고 상황에 맞게 고릅니다.
  • cloud-init을 Terraform으로 만들고 스키마로 검사하며, ansible-pull로 서버가 스스로 구성하게 할 수 있습니다.
  • Terraform 안에서 플레이북을 실행하는 방식(ansible_playbook 리소스, local-exec)의 함정을 실측으로 설명합니다.
  • “무엇을 Terraform이, 무엇을 Ansible이(또는 cloud-init·Packer·GitOps·AWX가)” 할지 책임 경계표를 만듭니다.

2① 출력 → 인벤토리

가장 단순하다 — 그리고 파일을 누가 만드느냐가 중요하다

h1/main.tf — 출력(가)과 local_file(나) 두 가지
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# 검증용: 7편 module.app.instances 와 같은 모양의 값 (실제로는 aws_instance 결과)
locals {
  instances = {
    web1 = { private_ip = "10.10.10.25", id = "i-0a1b2c3d4e5f60001", az = "ap-northeast-2a" }
    web2 = { private_ip = "10.10.11.37", id = "i-0a1b2c3d4e5f60002", az = "ap-northeast-2b" }
  }
  inventory = {
    web = {
      hosts = {
        for name, i in local.instances : name => {
          ansible_host                = i.private_ip
          ansible_aws_ssm_instance_id = i.id
          az                          = i.az
        }
      }
      vars = {
        db_host = "iaclab-dev-app-db.abcdefghijkl.ap-northeast-2.rds.amazonaws.com"
        db_port = 5432
      }
    }
  }
}

# 방법 ①-가: 출력으로 넘기고, 받는 쪽이 파일을 만든다 (7·13편)
output "ansible_inventory_yaml" {
  value = yamlencode(local.inventory)
}

# 방법 ①-나: apply 할 때 Terraform이 파일까지 쓴다
resource "local_file" "inventory" {
  filename        = "${path.module}/../inventory/terraform.yml"
  content         = yamlencode(local.inventory)
  file_permission = "0644"
}
# 실측
$ tofu apply                                   → local_file.inventory 생성
$ ansible-inventory -i ../inventory/terraform.yml --graph
@all:
  |--@web:
  |  |--web1
  |  |--web2

# 실측: 누군가 생성된 파일에 한 줄을 덧붙이면
$ tofu plan
  # local_file.inventory will be created          ← 내용이 다르면 “없는 것”으로 보고 다시 만든다
Plan: 1 to add, 0 to change, 0 to destroy.
(가) 출력 → 받는 쪽이 파일 생성(나) local_file로 Terraform이 생성
파일 위치Ansible 저장소·AWX 프로젝트 등 쓰는 쪽이 정함Terraform을 실행한 머신의 디스크 — CI 러너에서 apply하면 러너가 사라질 때 함께 사라진다
드리프트없음 (출력은 state의 값)파일을 손대거나 다른 머신에서 plan하면 매번 “will be created” (실측) — 9편 드리프트 점검의 잡음
추천○ — terraform output -raw … > inventory/…를 CI 단계로로컬 랩 외에는 피한다
이 방식의 한계와 다음 단계

출력 파일은 “apply한 순간의 사실”입니다. 오토스케일링·교체로 서버가 바뀌면 낡습니다(18편 1장). 그래서 MSP 표준은 호스트 목록은 동적 인벤토리(18편), 서버가 아닌 값(DB 주소·비밀 ARN)은 출력 JSON을 group_vars로(18편 5장 ⑤)입니다. 출력 → 파일은 그 “값” 부분에 남습니다.

3② cloud-init / user_data

부팅할 때 서버 스스로 — 최소한만 하고, 나머지는 Ansible이 당겨 오게

h2/main.tf — cloudinit_config로 user_data 만들기
terraform {
  required_providers {
    cloudinit = {
      source  = "hashicorp/cloudinit"
      version = "~> 2.3"
    }
  }
}

variable "ansible_repo" {
  description = "서버가 스스로 구성을 당겨 올 Git 저장소 (읽기 전용)"
  type        = string
  default     = "https://git.example.internal/msp/custa-ansible.git"
}

variable "role_tag" {
  description = "이 서버의 역할 — ansible-pull 이 실행할 플레이북을 고른다"
  type        = string
  default     = "web"
}

# 방법 ②: 부팅 시 최소한만 (cloud-init) + 나머지는 Ansible이 당겨 오게 (ansible-pull)
data "cloudinit_config" "web" {
  gzip          = false
  base64_encode = false

  part {
    content_type = "text/cloud-config"
    # 첫 줄 #cloud-config: MIME 형식이 아니어도(단독 user_data) 인식되고, cloud-init schema 로 검사할 수 있다
    content = "#cloud-config\n${yamlencode({
      timezone = "Asia/Seoul"
      packages = ["git", "python3", "ansible-core"]
      users = [
        "default",
        {
          name                = "svc-ansible"
          groups              = ["wheel"]
          sudo                = "ALL=(ALL) NOPASSWD:ALL"
          ssh_authorized_keys = ["ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIExampleKeyForLabOnly svc-ansible"]
        }
      ]
      write_files = [{
        path        = "/etc/iaclab/role"
        content     = "${var.role_tag}\n"
        permissions = "0644"
      }]
      runcmd = [
        ["ansible-pull", "-U", var.ansible_repo, "-C", "main", "-i", "localhost,", "playbooks/pull-${var.role_tag}.yml"],
      ]
    })}"
  }
}

output "cloud_config" {
  description = "검사용: MIME 묶음 안의 cloud-config 부분"
  value       = data.cloudinit_config.web.part[0].content
}

output "user_data" {
  value = data.cloudinit_config.web.rendered
}

cloud-init의 오타는 서버를 만든 뒤에야 콘솔 로그(/var/log/cloud-init-output.log)에서 발견되고, 그 사이 서버는 “반쯤 구성된” 상태로 운영에 들어갑니다. Terraform 출력에서 cloud-config를 뽑아 cloud-init schema로 검사하는 단계를 10편의 pre-commit·CI에 넣으면 apply 전에 잡을 수 있습니다(과제 1).

ansible-pull: 서버가 구성을 당겨 온다

playbooks/pull-web.yml (Git 저장소에 있는 플레이북)
---
# ansible-pull 로 서버가 스스로 실행하는 플레이북 (접속 없이 localhost)
- name: 부팅 후 자기 구성 (pull)
  hosts: localhost
  connection: local
  become: true
  gather_facts: false
  vars:
    pull_role: "{{ lookup('ansible.builtin.file', '/etc/iaclab/role', errors='ignore') | default('unknown', true) }}"
  tasks:
    - name: 역할 표시 파일
      ansible.builtin.copy:
        dest: /tmp/iaclab-pulled.txt
        content: "role={{ pull_role }} configured-by=ansible-pull\n"
        mode: "0644"
# 실측 (로컬 Git 저장소에서)
$ ansible-pull -U file:///tmp/t23/pullrepo -C main -i localhost, playbooks/pull-web.yml

changed: [localhost]

부팅 시 구성 시작 방식동작장단점
ansible-pull (위)서버가 Git에서 플레이북을 받아 자기 자신에 실행. cron·systemd 타이머로 주기 실행 가능중앙 서버·인바운드 접속 불필요(오토스케일링에 잘 맞음). 대신 서버마다 Git 읽기 권한·Ansible 설치가 필요하고, 실행 기록이 흩어진다
AWX 프로비저닝 콜백user_data에서 curl -X POST https://awx/api/v2/job_templates/ID/callback/ -d host_config_key=… → AWX가 그 서버만 대상으로 잡 실행기록·자격증명은 AWX에 모인다(21편). AWX가 서버에 접속할 수 있어야 한다
이미지에 굽기 (Packer + Ansible 프로비저너)미리 구성한 골든 이미지로 부팅 — cloud-init은 서버별 값만부팅이 빠르고 매번 같다(불변 인프라). 변경마다 이미지 재빌드 필요. 보안 기준(17편 기반 역할)은 이미지에, 서버별 설정은 Ansible로 나누는 것이 흔한 조합
user_data에 비밀을 넣지 않는다

user_data는 인스턴스 메타데이터로 서버 안에서 누구나 읽을 수 있고, Terraform state에도 그대로 들어갑니다(5편). 비밀은 부팅 후 Secrets Manager·Vault에서 가져오게 하고(19편), user_data에는 “어디서 가져올지”만 둡니다. 또 user_data가 바뀌면 AWS는 인스턴스 교체나 중지가 필요한 경우가 많으므로(user_data_replace_on_change, 11편), 자주 바뀔 설정은 user_data가 아니라 Ansible 쪽에 둡니다.

4③ Terraform ansible 프로바이더

두 가지 쓰임 — 인벤토리 기록(18편)과 apply 중 플레이북 실행(여기)

h3/main.tf — ansible_playbook 리소스
terraform {
  required_providers {
    ansible = {
      source  = "ansible/ansible"
      version = "~> 1.5"
    }
  }
}

variable "release" {
  type    = string
  default = "2026.10.1"
}

# 방법 ③: Terraform apply 안에서 플레이북 실행 (ansible 프로바이더의 ansible_playbook 리소스)
resource "ansible_playbook" "web1" {
  playbook   = "${path.module}/site-min.yml"
  name       = "node1"
  replayable = false # 처음 한 번만 실행 (true면 apply 할 때마다)

  extra_vars = {
    ansible_host                 = "127.0.0.1"
    ansible_port                 = "2221"
    ansible_user                 = "ansible"
    ansible_ssh_private_key_file = "/root/iac-lab/lab/keys/lab_ed25519"
    ansible_ssh_common_args      = "-o StrictHostKeyChecking=no"
    release                      = var.release
  }
}

output "playbook_stdout_tail" {
  value = join("\n", slice(split("\n", ansible_playbook.web1.ansible_playbook_stdout), 0, 8))
}
# 실측 1: replayable = true
$ tofu apply      → ansible_playbook.web1: Creation complete after 2s    (node1 에 실제로 실행됨)
$ tofu plan
  # ansible_playbook.web1 has been deleted
  # ansible_playbook.web1 will be created
Plan: 1 to add, 0 to change, 0 to destroy.            ← 아무것도 안 바꿔도 plan 이 매번 변경을 보인다

# 실측 2: replayable = false
$ tofu plan -detailed-exitcode   → exit=0, No changes.
$ (site-min.yml 의 내용을 바꾼 뒤) tofu plan -detailed-exitcode
exit=0, No changes.                                   ← 플레이북이 바뀌어도 모른다
$ tofu plan -var release=2026.11.0
  ~ update in-place                                   ← 리소스 인자(extra_vars)가 바뀔 때만 다시 실행

# 실측 3: state 에 남는 것
ansible_playbook_stdout = <<-EOT …                    ← 플레이북 출력 전체
args = [ "ansible_ssh_private_key_file='/root/iac-lab/lab/keys/lab_ed25519'", … ]
extra_vars = { … }                                    ← extra_vars 에 비밀을 넣으면 state 에 평문
문제왜 문제인가
replayable=true면 plan이 항상 변경12편의 drift 워크플로(-detailed-exitcode)가 매일 “변경 있음”을 보고 → 진짜 드리프트를 놓친다
replayable=false면 플레이북 변경 무시Ansible 코드를 고쳐도 Terraform은 다시 실행하지 않는다. 우회하려면 플레이북 해시를 인자로 넘겨야 하는데(과제 2), 그 순간 Terraform이 배포 도구가 된다
출력·인자가 state에5편 state 보안 문제가 플레이북 출력·변수로 확대
실행 위치apply하는 머신(CI 러너)에서 대상 서버로 SSH가 닿아야 한다 — 7편처럼 프라이빗 서브넷이면 불가
그래도 쓸 만한 곳

ansible 프로바이더의 ansible_host·ansible_group(인벤토리를 state에 기록)은 18편 5장 ③처럼 쓸 만합니다. ansible_playbook은 일회성 랩·데모, 또는 “이 리소스가 처음 생길 때 한 번만 해야 하는 초기화”처럼 범위가 좁고 반복이 필요 없는 일에만 둡니다.

문제결과
생성할 때 한 번만 실행 (②)Ansible의 핵심인 “반복 실행해 상태를 유지”가 사라진다. 구성 드리프트를 고칠 길이 없다
실패 → tainted → 교체 (③④)패키지 저장소 장애 하나로 다음 apply가 운영 서버를 지우고 새로 만든다. DB 서버라면 데이터 손실
서버 준비 시점을 모른다인스턴스 “생성 완료”는 SSH 준비 완료가 아니다 — 경쟁 상태로 간헐적 실패(실패하면 ③으로)
실행 환경이 Terraform 실행 머신ansible.cfg·EE·Vault·네트워크 경로가 Terraform 쪽 환경에 묶인다(실측 ①의 인터프리터 경고). CI 러너에서 프라이빗 서버로 SSH가 닿아야 한다
기록·권한구성 기록이 Terraform 로그에 섞이고, 서버 접속 키가 Terraform 실행 권한과 합쳐진다
대신 이렇게

Terraform apply가 끝나면 거기서 멈춘다 → 다음 단계(CI 잡, AWX 잡, 서버의 ansible-pull·콜백)가 구성을 맡는다. Ansible 쪽에서는 첫 태스크로 ansible.builtin.wait_for_connection, cloud-init을 쓰는 서버면 cloud-init status --wait로 준비를 기다린다. 구성이 실패해도 Terraform 리소스는 멀쩡하고, 고친 뒤 Ansible만 다시 돌리면 된다.

항목을 선택하세요

원칙 세 가지: ① 클라우드 API로 만드는 것은 Terraform ② OS 안에서 바뀌는 것은 Ansible(또는 이미지에 굽기) ③ 같은 것을 두 도구가 관리하지 않는다 — 둘이 관리하면 서로 되돌리며 드리프트를 만든다.

경계가 흐려지는 곳정하는 방법
보안 그룹 vs 호스트 방화벽둘 다 쓰되 역할을 나눔: 보안 그룹 = 네트워크 경계(Terraform), 호스트 방화벽 = 서버 기본 거부(Ansible, 17편). 같은 규칙을 양쪽에서 “관리 대상”으로 두지 않는다
DB 파라미터 vs DB 안의 객체파라미터 그룹·인스턴스 = Terraform(7편), 계정·권한·스키마 = Ansible(17편)·애플리케이션 마이그레이션
user_data vs Ansibleuser_data는 “Ansible이 들어올 수 있게”까지(계정·키·에이전트·ansible-pull), 그 뒤는 Ansible
Kubernetes클러스터·노드 그룹 = Terraform, 부트스트랩(네임스페이스·RBAC·GitOps 설치) = Ansible/Terraform, 앱 = GitOps(22편 10장)
비밀저장소·접근 정책 = Terraform, 값의 사용 = Ansible 룩업(19편), 값의 교체 = 비밀 저장소의 자동 교체

user_data는 작게, 버전을 붙여

고객마다 다른 긴 셸 스크립트 user_data는 관리가 안 됩니다. MSP 표준 cloud-init 템플릿(계정·에이전트·콜백) 하나에 변수만 바꾸고, 템플릿에 버전 주석을 남겨 어떤 서버가 어떤 부트스트랩으로 떴는지 추적합니다.

구성 실패와 인프라 실패를 분리 보고

파이프라인 결과를 “Terraform 단계 실패”와 “AWX 구성 단계 실패”로 나눠 알림을 보내면 담당(클라우드/OS)이 바로 정해집니다. 8장 흐름의 장점입니다.

오토스케일링 고객

ASG 인스턴스는 Terraform이 개별로 만들지 않으므로(18편 과제 3) 출력·ansible 프로바이더 방식이 맞지 않습니다. 이미지 굽기 + cloud-init + 콜백(또는 ansible-pull)으로 “스스로 구성되는 서버”를 만드는 것이 정석입니다.

13과제

실측을 마친 뒤에 풀어 보세요

과제 1. cloud-init 검사를 CI에

7편 app-servers 모듈의 user_data를 3장처럼 cloudinit_config로 바꾸고, PR 워크플로(12편)에 “plan 후 출력의 cloud-config를 뽑아 cloud-init schema로 검사”하는 단계를 추가하세요. 일부러 오타를 넣어 PR이 실패하는지 확인합니다.

과제 2. ansible_playbook을 쓰겠다면

4장의 ansible_playbook 리소스에서 플레이북이 바뀌면 다시 실행되도록 extra_vars에 filemd5(path)를 넣어 보세요. 그런 다음 이 방식이 8장 흐름과 비교해 무엇을 잃는지(기록, 실행 위치, 드리프트 관리) 정리합니다.

과제 3. provisioner 걷어내기

local-exec가 붙은 aws_instance가 있는 코드에서, 서버를 바꾸지 않고 provisioner만 제거하는 절차를 쓰세요(plan이 “No changes”여야 함). 그 서버의 구성을 Ansible(AWX 잡)로 옮기고 첫 실행에서 changed가 0이 되도록(=이미 같은 상태) 역할을 맞춥니다.

힌트

provisioner 블록은 state의 리소스 속성이 아니므로 제거해도 plan에 변경이 없습니다(실측해 보세요). 단 tainted 상태라면 먼저 terraform untaint로 교체 계획을 없앤 뒤 진행합니다.

과제 4. 콜백으로 스스로 구성되는 서버

21편 과제 1의 AWX에 프로비저닝 콜백을 켠 잡 템플릿을 만들고, 3장 cloud-init의 runcmd를 ansible-pull 대신 콜백 curl로 바꾸세요. host_config_key는 어디에 보관하고(19편), AWX는 그 서버에 어떻게 접속하나요(18편 SSM)?

과제 5. 책임 경계표 작성

여러분이 맡은 고객(또는 2편 랩 + 7편 AWS 구성)에 대해 7장 항목 전체를 표로 채우고, 각 항목의 “변경 요청이 오면 어느 저장소의 PR로 반영하는가”까지 적으세요. 25편 멀티 고객 운영의 입력이 됩니다.

14정리와 다음 편

한 장으로 다시 보기

① 출력 → 인벤토리

출력은 받는 쪽이 파일로. local_file은 다른 머신·손 수정에서 매번 “will be created”(실측). 호스트는 동적으로, 값만 출력으로.

② cloud-init

#cloud-config 헤더(실측), schema 검사로 오타·타입 오류 사전 차단(실측). ansible-pull·콜백·이미지 굽기. user_data에 비밀 금지.

③ ansible 프로바이더

인벤토리 기록은 유용. ansible_playbook은 replayable=true면 plan이 항상 변경, false면 플레이북 변경 무시, 출력·인자가 state에(실측).

④ AWX 트리거

CI → AWX API(actionlint 통과, awxkit은 setuptools<81 필요 — 실측), AAP 프로바이더(validate·스키마 실측), Terraform 1.14 액션, 콜백·EDA.

local-exec 금지

한 번만 실행, 변경 미감지, 실패 → tainted → 서버 교체(실측), 준비 시점·실행 환경·기록 문제.

경계

API로 만드는 것은 Terraform, OS 안은 Ansible(또는 이미지), 둘이 같은 것을 관리하지 않는다. 경계표를 계약에.
