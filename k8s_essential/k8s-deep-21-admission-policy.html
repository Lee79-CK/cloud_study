Level 3 RBAC과 접근 제어, 21편

어드미션 제어와 정책 엔진

RBAC은 “누가 Pod를 만들 수 있나”만 정합니다. “어떤 Pod를 만들 수 있나”는 정하지 못합니다. 18편에서 개발자가 강한 ServiceAccount를 빌려 쓴 것도, 20편에서 자동 마운트 금지를 강제하지 못한 것도 그 때문입니다. 그 빈자리를 채우는 것이 어드미션 제어입니다. 이 편은 웹훅이 클러스터 전체를 멈추게 할 수 있는 이유와 그 장애 반경, 웹훅을 없애는 CEL 정책(ValidatingAdmissionPolicy·MutatingAdmissionPolicy), Pod Security Admission과 OpenShift SCC의 대응, Kyverno와 Gatekeeper의 선택, 벤더가 미리 걸어 둔 제약을 다루고, 같은 세 규칙을 CEL 정책과 Kyverno로 구현해 성능과 장애 동작을 비교합니다.

기준: Kubernetes v1.37 · VAP(1.30 GA) · MAP(1.36 GA) · Kyverno 1.1x · Gatekeeper 3.x 작성 기준일: 2026-10-24 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

이 배포는 어디서 막히나: 어드미션 파이프라인 시뮬레이터

개발자 bob(18편)이 team-dev에 Deployment를 만드는 요청입니다. Pod 템플릿의 내용과 클러스터에 걸린 통제를 고르면, 요청이 변경(mutating) → 스키마 검증 → 검증(validating) 단계를 지나고, 이어서 컨트롤러가 Pod를 만들 때 다시 검사받는 과정까지 어디서 바뀌고 어디서 막히는지 보여 줍니다. Kyverno 웹훅을 “다운”으로 바꾸고 failurePolicy를 바꿔 보면 장애 반경을 체감할 수 있습니다. 규칙은 8장 실습의 세 규칙과 같습니다.

0

읽는 법과 목표

쉬운 말로 RBAC이 “이 사람은 택배를 보낼 수 있다”를 정한다면, 어드미션은 우체국 창구의 검사대입니다. 상자 안에 금지 물품(특권 컨테이너)이 있는지, 보내는 곳 주소(이미지 레지스트리)가 허용된 곳인지, 송장(레이블)이 붙어 있는지 확인하고, 빠진 것은 붙여 주기도(변경) 합니다. 검사대를 바깥 업체(웹훅)에 맡기면 그 업체가 문을 닫는 순간 창구 전체가 멈출 수 있습니다. 그래서 요즘은 검사 규칙을 창구 안에 직접 적어 두는 방식(CEL 정책)이 늘었습니다.

이 편을 마치면 할 수 있는 것

  • 어드미션 단계의 순서와 내장 플러그인·웹훅·CEL 정책의 위치를 설명할 수 있습니다.
  • 웹훅의 failurePolicy·timeout·selector·matchConditions로 장애 반경을 설계할 수 있습니다.
  • ValidatingAdmissionPolicy·MutatingAdmissionPolicy로 웹훅 없이 정책을 구현할 수 있습니다.
  • PSA 세 단계와 OpenShift SCC를 대응시키고, Kyverno와 Gatekeeper 중 고객에 맞는 것을 고를 수 있습니다.
  • GKE Autopilot·EKS Auto Mode·AKS 정책 애드온·OpenShift 기본 SCC가 미리 걸어 둔 제약을 알고, 감사 → 경고 → 거부 순서로 정책을 도입할 수 있습니다.
1

어드미션 단계와 순서

1인증·인가(17~19편). 여기서 통과해야 어드미션이 시작됩니다.RBAC 통과 = “만들 수 있는 사람”
2변경(mutating) 단계. 내장 플러그인(ServiceAccount 기본값, DefaultStorageClass 등) → MutatingAdmissionPolicy → 변경 웹훅. 웹훅은 reinvocationPolicy로 다른 변경 뒤에 다시 불릴 수 있습니다.예: 레이블 기본값, 자동 마운트 끄기, 사이드카 주입
3스키마 검증. 객체가 API 스키마에 맞는지 확인합니다.
4검증(validating) 단계. 내장 플러그인(PodSecurity, ResourceQuota, LimitRanger의 검증 부분, NodeRestriction 등) → ValidatingAdmissionPolicy → 검증 웹훅. 하나라도 거부하면 요청 실패.변경은 이 단계에서 일어나지 않음. 검증 웹훅은 병렬로 호출
5저장. etcd에 기록되고, 컨트롤러가 그 객체를 보고 동작합니다.
시니어 포인트: Deployment는 통과했는데 Pod가 안 생기는 이유 정책을 Pod에만 걸면, 사용자가 만든 Deployment는 통과하고 그 뒤 ReplicaSet 컨트롤러가 Pod를 만들 때 거부됩니다. 사용자에게는 오류가 안 보이고, ReplicaSet 이벤트에만 “FailedCreate”가 남습니다. 그래서 정책은 Pod 템플릿을 가진 상위 리소스(Deployment·StatefulSet·DaemonSet·Job·CronJob)에도 걸어야 합니다. Kyverno는 이를 자동으로 만들어 주고(autogen), CEL 정책은 직접 표현해야 합니다(3장).
2

웹훅의 동작과 장애 반경

설정의미장애 반경에 미치는 영향
failurePolicy웹훅이 응답하지 않거나 오류일 때: Fail(요청 거부) / Ignore(통과)Fail: 웹훅이 죽으면 해당 리소스 생성이 모두 멈춤. Ignore: 웹훅이 죽으면 정책이 조용히 꺼짐
timeoutSeconds응답 대기(최대 30초, 기본 10초)느린 웹훅은 모든 해당 요청을 그만큼 늦춤. kubectl·컨트롤러 타임아웃 연쇄
namespaceSelector·objectSelector웹훅을 부를 대상 범위kube-system과 웹훅 자신의 네임스페이스는 제외해야 교착을 피함
matchConditions(CEL)API 서버가 미리 걸러 필요한 요청만 웹훅으로호출 수·지연 감소. 노드·시스템 SA 요청 제외에 유용
rules(리소스·동작)어떤 리소스의 어떤 동작에*로 모든 리소스를 잡으면 리스(Lease)·이벤트까지 웹훅을 거쳐 컨트롤 플레인 전체가 느려짐
sideEffectsdry-run 요청 처리 가능 여부None이 아니면 dry-run이 거부됨
함정: 웹훅이 자기 자신을 고치지 못하게 막는 교착 정책 엔진 웹훅이 failurePolicy: Fail로 모든 Pod 생성을 검사하는데, 엔진 Pod가 모두 죽었다고 해 봅시다. 엔진을 다시 띄우려면 Pod를 만들어야 하고, Pod를 만들려면 엔진이 응답해야 합니다. 엔진의 네임스페이스를 selector에서 빼 두지 않았다면 클러스터는 스스로 회복하지 못합니다. 이때의 비상 조치는 kubectl delete validatingwebhookconfiguration …(웹훅 설정 삭제)이며, 이 절차를 런북에 적어 두세요. 매니지드 클러스터에서는 웹훅이 노드 관련 요청까지 막아 노드가 NotReady가 된 사례도 있습니다.
안전한 웹훅 설정의 뼈대
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata: {name: policy-engine}
webhooks:
- name: validate.policy.example.com
  failurePolicy: Fail                      # 보안 정책은 Fail, 대신 아래로 반경을 줄임
  timeoutSeconds: 5
  sideEffects: None
  admissionReviewVersions: ["v1"]
  namespaceSelector:
    matchExpressions:
    - {key: kubernetes.io/metadata.name, operator: NotIn, values: ["kube-system", "policy-engine"]}
  matchConditions:
  - name: exclude-system-users
    expression: "!request.userInfo.username.startsWith('system:node:') && !request.userInfo.username.startsWith('system:kube-')"
  rules:
  - {apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE", "UPDATE"], resources: ["pods"], scope: "Namespaced"}
  clientConfig: {service: {namespace: policy-engine, name: webhook, path: /validate}}

ValidatingAdmissionPolicy와 MutatingAdmissionPolicy

두 기능 모두 CEL 표현식을 API 서버 안에서 실행합니다. 네트워크 호출이 없으니 웹훅이 죽을 일도, TLS 인증서가 만료될 일도 없습니다. VAP는 1.30에서, MAP는 1.36에서 GA가 되었습니다.

구성 요소역할
Policy(VAP·MAP)무엇을 검사·변경할지: matchConstraints, matchConditions, variables, validations(또는 mutations), failurePolicy
Binding어디에 적용할지(네임스페이스·객체 선택자), 어떤 파라미터로, 어떤 동작으로(validationActions: [Deny | Warn | Audit])
Param(선택)ConfigMap이나 CRD로 값(허용 레지스트리 목록 등)을 분리해 정책 재사용
CEL 변수object, oldObject, request, params, namespaceObject, authorizer(“이 사용자가 X를 할 수 있나” 질의)
MAP 변경 방식ApplyConfiguration(부분 객체를 서버 측 적용 방식으로 병합) 또는 JSONPatch
VAP: 허용 레지스트리 + Pod 템플릿을 가진 모든 워크로드
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: {name: allowed-registries}
spec:
  failurePolicy: Fail
  paramKind: {apiVersion: v1, kind: ConfigMap}
  matchConstraints:
    resourceRules:
    - {apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE", "UPDATE"], resources: ["pods"]}
    - {apiGroups: ["apps"], apiVersions: ["v1"], operations: ["CREATE", "UPDATE"], resources: ["deployments", "statefulsets", "daemonsets"]}
    - {apiGroups: ["batch"], apiVersions: ["v1"], operations: ["CREATE", "UPDATE"], resources: ["jobs", "cronjobs"]}
  variables:
  - name: spec                             # 리소스 종류마다 Pod 스펙 위치가 다름 (Kyverno autogen이 대신 하는 일)
    expression: "object.kind == 'Pod' ? object.spec : (object.kind == 'CronJob' ? object.spec.jobTemplate.spec.template.spec : object.spec.template.spec)"
  - name: containers
    expression: "variables.spec.containers + (has(variables.spec.initContainers) ? variables.spec.initContainers : []) + (has(variables.spec.ephemeralContainers) ? variables.spec.ephemeralContainers : [])"
  - name: allowed
    expression: "params.data.allowed.split(',')"
  validations:
  - expression: "variables.containers.all(c, variables.allowed.exists(p, c.image.startsWith(p)))"
    messageExpression: "'허용되지 않은 레지스트리: ' + variables.containers.filter(c, !variables.allowed.exists(p, c.image.startsWith(p))).map(c, c.image).join(', ')"
    reason: Forbidden
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata: {name: allowed-registries-teams}
spec:
  policyName: allowed-registries
  validationActions: [Deny]                # 도입 초기엔 [Warn, Audit]
  paramRef: {name: allowed-registries, namespace: policy-params, parameterNotFoundAction: Deny}
  matchResources:
    namespaceSelector: {matchLabels: {policy.lab/enforced: "true"}}
MAP: 레이블이 없는 Pod에 자동 마운트 끄기 (20편에서 못 한 강제)
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata: {name: no-automount-by-default}
spec:
  matchConstraints:
    resourceRules:
    - {apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE"], resources: ["pods"]}
  matchConditions:
  - name: not-opted-in
    expression: "!has(object.metadata.labels) || !('policy.lab/needs-api-token' in object.metadata.labels)"
  failurePolicy: Fail
  reinvocationPolicy: IfNeeded
  mutations:
  - patchType: ApplyConfiguration
    applyConfiguration:
      expression: "Object{spec: Object.spec{automountServiceAccountToken: false}}"
---
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata: {name: no-automount-teams}
spec:
  policyName: no-automount-by-default
  matchResources:
    namespaceSelector: {matchLabels: {policy.lab/enforced: "true"}}
현장 메모: authorizer로 “누가”까지 검사하기 18편 실습 3의 “강한 SA 빌려 쓰기”는 VAP의 authorizer로 막을 수 있습니다. 예: Pod의 serviceAccountName이 team-operator이면 요청자가 그 SA에 대해 사용자 정의 동사 use를 가졌는지 authorizer.group('').resource('serviceaccounts').namespace(ns).name(sa).check('use').allowed()로 확인하는 패턴입니다(authorizer는 요청한 사용자 기준으로 질의합니다. authorizer.serviceAccount(…)는 그 SA 자신의 권한을 묻는 것이니 혼동하지 마세요). 실습 2의 보너스 규칙에서 구현합니다.

Pod Security Admission과 OpenShift SCC

PSA는 PodSecurityPolicy(1.25 제거)의 후속으로, 네임스페이스 레이블 하나로 Pod 보안 표준(PSS)의 세 단계 중 하나를 적용하는 내장 플러그인입니다. 단계마다 enforce(거부)·audit(감사 로그)·warn(경고) 모드를 따로 줄 수 있습니다.

단계막는 것(요약)대응하는 OpenShift SCC
privileged아무것도 막지 않음privileged
baseline특권 컨테이너, 호스트 네임스페이스(hostNetwork·hostPID·hostIPC), hostPath, hostPort, 위험한 capabilities 추가, AppArmor·SELinux 우회, /proc 마운트 변경, 위험한 sysctl대략 anyuid·nonroot 계열(루트 허용 여부는 다름)
restrictedbaseline + 루트 실행 금지(runAsNonRoot), 권한 상승 금지(allowPrivilegeEscalation: false), capabilities 전부 제거(NET_BIND_SERVICE만 추가 허용), seccomp RuntimeDefault 이상, 허용된 볼륨 종류만restricted-v2(OpenShift 기본, 무작위 UID 범위 할당)
PSA 레이블과 단계적 도입
kubectl label ns team-dev \
  pod-security.kubernetes.io/enforce=baseline  pod-security.kubernetes.io/enforce-version=v1.37 \
  pod-security.kubernetes.io/warn=restricted   pod-security.kubernetes.io/audit=restricted --overwrite
# 적용 전 영향 확인: 기존 Pod 중 restricted를 어기는 것 목록(서버 dry-run)
kubectl label --dry-run=server --overwrite ns team-dev pod-security.kubernetes.io/enforce=restricted

PSA와 SCC는 어떻게 함께 도나

  • SCC가 주 집행. OpenShift는 Pod 생성자(또는 Pod의 SA)가 use 권한을 가진 SCC 중에서 우선순위에 따라 하나를 골라 Pod를 허용하고, 필요하면 UID·SELinux 레이블 같은 값을 채워 넣습니다(변경 역할도 함).
  • PSA 레이블 자동 동기화. OpenShift는 네임스페이스의 SA들이 쓸 수 있는 SCC에 맞춰 PSA 레이블을 자동으로 맞추는 동기화 컨트롤러를 둡니다. 그래서 같은 클러스터에서도 네임스페이스마다 PSA 단계가 달라 보일 수 있습니다. 시스템 네임스페이스(openshift-*)는 동기화 대상이 아닙니다.
  • SCC가 없는 플랫폼에서는 PSA가 기본선이고, 그보다 세밀한 규칙(레지스트리·레이블·SA)은 VAP나 정책 엔진으로 더합니다.

Kyverno vs OPA Gatekeeper

항목KyvernoOPA GatekeeperCEL 정책(VAP·MAP)
언어YAML 패턴·JMESPath, 최근 CEL 기반 정책 종류도 제공Rego(ConstraintTemplate) + 파라미터(Constraint), CEL 엔진 지원CEL
실행 위치웹훅(별도 Pod)웹훅(별도 Pod), 템플릿에서 VAP 생성 기능API 서버 안
변경(mutate)강함(패치, 기본값, 자동 생성 규칙)Assign·AssignMetadata 등 제한적MAP(1.36 GA)
생성(generate)네임스페이스 생성 시 NetworkPolicy·RoleBinding 자동 생성 등없음없음
이미지 서명 검증지원(cosign·Notary)외부 연동 필요없음(외부 데이터 호출 불가)
기존 리소스 감사백그라운드 스캔 → PolicyReportaudit 컨트롤러 → Constraint 상태Audit 동작은 요청 시점만(기존 리소스 스캔 없음)

정책 운영: 감사 → 경고 → 거부

  1. 현황 파악(Audit). VAP는 validationActions: [Audit]로 감사 로그에, Kyverno는 Audit 모드 + 백그라운드 스캔으로 PolicyReport에, Gatekeeper는 dryrun + audit으로 위반 목록을 만듭니다. 기존 위반을 고칠 시간을 줍니다.
  2. 사용자에게 알리기(Warn). kubectl에 경고가 표시됩니다. 배포 파이프라인에서 경고를 실패로 취급할지 정합니다.
  3. 거부(Deny·Enforce). 네임스페이스 레이블로 범위를 정해 팀 단위로 켭니다.
  4. 예외 관리. 예외는 정책 안의 조건(레이블·네임스페이스)으로 표현하고, 사유·만료일을 함께 기록합니다. Kyverno는 PolicyException 리소스를 제공합니다.
  5. 정책도 코드로 시험. kubectl apply --dry-run=server로 실제 API 서버에서 판정, kyverno test·gator verify로 단위 테스트를 CI에 넣습니다.
  6. 비상 해제. 정책 엔진 장애 시 웹훅 설정 삭제 절차, VAP 바인딩을 Warn으로 내리는 절차를 런북에 둡니다(22편 브레이크글라스와 함께).

T(){ # T 기대(ok|deny) 설명 -- kubectl 인자...
  local exp=$1 desc=$2; shift 3
  if out=$(kubectl -n policy-lab "$@" --dry-run=server 2>&1); then got=ok; else got=deny; fi
  [ "$got" = "$exp" ] && echo "PASS $desc" || echo "FAIL $desc → $got: $(echo "$out" | tail -1)"; }
run_tests(){
  T ok   "허용 레지스트리 Pod"      -- run ok1 --image=registry.k8s.io/e2e-test-images/agnhost:2.52
  T deny "docker.io 이미지 Pod"      -- run bad1 --image=docker.io/library/busybox:1.36
  T deny "특권 Pod"                  -- run bad2 --image=registry.k8s.io/e2e-test-images/agnhost:2.52 --overrides='{"spec":{"containers":[{"name":"c","image":"registry.k8s.io/e2e-test-images/agnhost:2.52","securityContext":{"privileged":true}}]}}'
  T deny "레이블 없는 Deployment"    -- create deployment bad3 --image=registry.k8s.io/e2e-test-images/agnhost:2.52
  T deny "docker.io Deployment"      -- create deployment bad4 --image=docker.io/library/nginx:1.27
  kubectl -n policy-lab create deployment ok2 --image=registry.k8s.io/e2e-test-images/agnhost:2.52 --dry-run=client -o yaml \
   | kubectl label --local -f - team=web cost-center=cc-100 -o yaml | kubectl -n policy-lab apply --dry-run=server -f - >/dev/null 2>&1 \
   && echo "PASS 레이블 있는 Deployment" || echo "FAIL 레이블 있는 Deployment"; }
run_tests                                                   # 정책 없음: 'deny' 기대가 모두 FAIL로 나오는 것이 정상(기준선)

  variables:
  - name: spec

  - name: sa
    expression: "has(variables.spec.serviceAccountName) ? variables.spec.serviceAccountName : 'default'"
  validations:
  - expression: "!(variables.sa in ['team-operator']) || authorizer.group('').resource('serviceaccounts').namespace(object.metadata.namespace).name(variables.sa).check('use').allowed()"
    messageExpression: "'ServiceAccount ' + variables.sa + ' 을(를) 사용할 권한(use)이 없습니다.'"

9

현장 사례

느린 웹훅 하나로 노드들이 NotReady가 됐다

원인. 감사용 웹훅이 모든 리소스(*)의 UPDATE를 30초 타임아웃·Fail로 검사했고, 웹훅 서버가 느려지자 kubelet의 Lease 갱신까지 지연되어 노드가 NotReady로 판정되었습니다.

교훈. 웹훅 대상은 필요한 리소스만, Lease·이벤트·노드 요청은 matchConditions로 제외, 타임아웃은 짧게.

정책 엔진이 자기 자신을 되살리지 못했다

원인. 노드 교체 중 엔진 Pod가 모두 내려갔는데, 엔진의 네임스페이스가 웹훅 대상에서 빠져 있지 않아 엔진 Pod 생성도 웹훅 호출 실패로 거부되었습니다.

교훈. 엔진 네임스페이스·kube-system 제외는 필수. 비상시 웹훅 설정 삭제 절차를 런북에.

엔진 장애 동안 특권 Pod가 배포됐다

원인. 가용성 걱정으로 failurePolicy를 Ignore로 두었고, 엔진이 내려간 몇 시간 동안 모든 정책이 꺼진 상태였습니다. 아무도 알아채지 못했습니다.

교훈. 보안 핵심 규칙(특권·호스트 접근)은 PSA나 VAP처럼 API 서버 안에서 돌게 하고, 엔진은 보조 기능에. 엔진 가용성 경보를 두세요.

Deployment는 성공했는데 Pod가 하나도 안 떴다

원인. 새로 만든 VAP가 Pod에만 걸려 있어, 사용자의 Deployment는 통과하고 ReplicaSet 컨트롤러의 Pod 생성만 거부되었습니다. 사용자는 이유를 몰랐습니다.

교훈. Pod 템플릿을 가진 상위 리소스에도 같은 규칙을(3장 variables 패턴, Kyverno autogen).

PSA restricted를 켰더니 모니터링이 멈췄다

원인. 클러스터 전체 기본값을 restricted로 바꾸면서 node-exporter(hostNetwork·hostPath)와 로그 수집 DaemonSet이 있는 네임스페이스를 예외로 두지 않았습니다.

교훈. 시스템·에이전트 네임스페이스는 privileged·baseline 레이블로 명시하고, 바꾸기 전 서버 dry-run으로 영향 목록을 뽑으세요.

nginx 하나 띄우려고 default SA에 anyuid를 줬다

원인. OpenShift에서 루트로 동작하는 이미지가 restricted-v2에 막히자, 개발자가 네임스페이스의 default SA에 anyuid를 부여했습니다. 그 뒤 네임스페이스의 모든 Pod가 루트로 실행될 수 있게 되었습니다.

교훈. 비루트 이미지(예: nginx-unprivileged)를 쓰거나, 꼭 필요하면 전용 SA에만 가장 좁은 SCC를(19편).

Autopilot에 보안 에이전트를 설치할 수 없었다

원인. 고객사 표준 보안 에이전트가 특권 DaemonSet이었고, GKE Autopilot이 거부했습니다.

교훈. Autopilot·Auto Mode 같은 제약형 모드를 제안하기 전에 고객의 필수 에이전트 목록과 벤더 허용 목록을 대조하세요.

두 변경 정책이 서로를 되돌렸다

원인. Kyverno 변경 규칙과 새로 도입한 MutatingAdmissionPolicy가 같은 필드(리소스 요청 기본값)를 다르게 설정했고, 재호출 정책 때문에 결과가 요청마다 달랐습니다.

교훈. 한 필드의 변경 주체는 하나로. 이전 기간에는 대상 범위를 겹치지 않게 나누세요.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. 어드미션은 인가 뒤 변경 → 스키마 검증 → 검증 순으로 동작하며, Pod 템플릿을 가진 상위 리소스까지 정책을 걸어야 사용자에게 거부가 보입니다.
  2. 웹훅은 failurePolicy·timeout·selector·matchConditions가 장애 반경을 정하고, 엔진 네임스페이스·kube-system 제외와 비상 해제 절차가 필수입니다.
  3. VAP(1.30 GA)와 MAP(1.36 GA)는 CEL을 API 서버 안에서 실행해 웹훅의 가용성·지연 문제를 없애며, authorizer로 “누가”까지 검사할 수 있습니다.
  4. PSA 세 단계는 OpenShift의 privileged·anyuid 계열·restricted-v2 SCC에 대응하고, 정책 엔진은 기존 리소스 감사·자동 생성·이미지 서명이 필요할 때 Kyverno나 Gatekeeper로 더합니다.
  5. GKE Autopilot·EKS Auto Mode·AKS Azure Policy·OpenShift SCC의 기본 제약을 먼저 확인하고, 정책은 감사 → 경고 → 거부 순서로 도입합니다.

다음 편 · 22편 감사·최소 권한·침해 대응 (Level 3 마지막)

감사 정책 작성과 벤더 감사 로그(CloudWatch·Azure Monitor·Cloud Logging·OpenShift audit)의 보존·비용, RBAC 분석 도구(rbac-tool, kubectl-who-can, rakkess, KubiScan)로 과잉 권한 찾기, 실제 권한 상승 경로(SA 토큰 탈취 → 노드 접근 → 클러스터 장악, 가장 악용)와 비밀 관리(KMS 저장 암호화, External Secrets, Vault)를 다룹니다. 의도적으로 과잉 권한을 심은 클러스터에서 공격 경로를 재현한 뒤 최소 권한으로 봉쇄하고, 감사 로그로 탐지 규칙을 작성합니다.
