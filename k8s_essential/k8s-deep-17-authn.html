Level 3 RBAC과 접근 제어, 17편 (시작)

인증 지형: 누가 요청했는가

Kubernetes에는 “사용자” 객체가 없습니다. API 서버는 요청마다 인증서·토큰·헤더를 보고 이 요청을 보낸 것이 누구이며 어느 그룹에 속하는지를 그때그때 판단합니다. 그 판단이 틀리면 18편부터 다룰 RBAC이 아무리 정교해도 소용이 없습니다. 이 편은 x509부터 ServiceAccount 토큰, OIDC와 구조화된 인증 설정, Pod 인증서까지 인증 경로를 모두 정리하고, EKS·AKS·GKE·OpenShift·Rancher가 이를 어떻게 감싸는지, 토큰 수명과 비상용 계정을 어떻게 설계하는지 다룹니다. 실습에서는 Keycloak 하나를 kubeadm·RKE2·OpenShift에 연결해 그룹이 각 플랫폼에서 어떻게 보이는지 비교합니다.

기준: Kubernetes v1.37 · AuthenticationConfiguration v1 작성 기준일: 2026-10-23 예상 학습: 이론 150분 + 실습 180분 점선 밑줄 용어는 누르거나 올리면 쉬운 설명이 나옵니다

자격 증명 종류를 고르면 클라이언트가 그것을 얻는 방법, API 서버가 확인하는 방법, 최종적으로 만들어지는 사용자 정보(이름·그룹), 그리고 수명·취소 가능성 같은 운영 특성이 나옵니다.

자격 증명
0

읽는 법과 목표

쉬운 말로 인증은 건물 입구에서 신분증을 확인하는 일, 인가(RBAC)는 그 사람이 어느 층에 들어갈 수 있는지 확인하는 일입니다. Kubernetes의 경비원(API 서버)은 직원 명부를 갖고 있지 않습니다. 대신 신분증 발급처(인증서 기관, 회사 로그인 시스템, 클라우드 계정)를 믿고, 신분증에 적힌 이름과 소속 부서(그룹)를 그대로 받아들입니다. 그래서 “어느 발급처를 믿을지”와 “신분증이 언제 만료되는지”가 보안의 핵심입니다.

Level 3은 6편입니다: 17편 인증, 18편 RBAC 모델, 19편 벤더별 IAM과 RBAC의 겹침, 20편 ServiceAccount와 워크로드 아이덴티티, 21편 어드미션 제어와 정책, 22편 감사·최소 권한·침해 대응.

이 편을 마치면 할 수 있는 것

  • 요청이 인증 → 인가 → 어드미션을 거치는 순서와, 인증 결과인 사용자 정보(이름·UID·그룹·추가 정보)를 설명할 수 있습니다.
  • x509, ServiceAccount 토큰, OIDC, 웹훅, 인증 프록시, Pod 인증서의 특성(수명·취소·그룹 출처)을 비교할 수 있습니다.
  • 구조화된 인증 설정으로 여러 OIDC 발급자와 CEL 클레임 매핑을 구성할 수 있습니다.
  • EKS 액세스 엔트리, AKS Entra ID, GKE IAM·Google 그룹, OpenShift OAuth, Rancher 인증 프록시를 비교할 수 있습니다.
  • kubeconfig exec 플러그인과 토큰 수명을 이해하고, 브레이크글라스 계정을 설계할 수 있습니다.
1

요청 하나가 거치는 길

1TLS 연결. 클라이언트가 API 서버 인증서를 확인합니다(kubeconfig의 CA). 클라이언트 인증서가 있으면 이 단계에서 함께 제시됩니다.
2인증. API 서버가 인증기들을 차례로 시도합니다(클라이언트 인증서, 베어러 토큰: ServiceAccount·OIDC·웹훅, 인증 프록시 헤더). 하나라도 성공하면 그 결과를 쓰고, 모두 실패하면 401(또는 익명 허용 시 system:anonymous)입니다.
3사용자 정보. 결과는 이름(username), UID, 그룹 목록, 추가 정보(extra)입니다. 인증된 모든 요청에는 그룹 system:authenticated가 자동으로 붙습니다.
4가장(impersonation). 요청에 Impersonate-User 같은 헤더가 있으면, 인증된 사용자가 그 가장 권한이 있는지 확인한 뒤 신원을 바꿉니다(18·22편).
5인가. RBAC·Node·웹훅 인가기가 “이 사용자·그룹이 이 동사·리소스를 할 수 있나”를 판단합니다(18편).
6어드미션. 변경·검증 정책을 거쳐 etcd에 저장됩니다(21편).
지금 나는 누구인가
kubectl auth whoami                         # SelfSubjectReview: API 서버가 본 내 이름·그룹·extra
kubectl auth whoami -o yaml
kubectl auth can-i --list                   # 그 신원으로 할 수 있는 일(18편)
시니어 포인트: 그룹은 인증기가 정한다 Kubernetes에는 그룹 객체가 없습니다. 인증서의 O 필드, 토큰의 groups 클레임, 웹훅 응답, 클라우드 매핑이 그룹을 만들고 RBAC은 그 문자열을 그대로 믿습니다. 그래서 그룹 이름을 누가 만들 수 있는가가 곧 권한 경계입니다. 사용자가 스스로 그룹을 만들 수 있는 IdP(셀프 서비스 그룹)를 연결하면, 누구나 cluster-admins 같은 그룹을 만들어 권한을 얻을 수 있습니다. 클레임에 접두사를 붙이는 이유가 여기 있습니다(5장).

x509 클라이언트 인증서와 CSR

  • 규칙. 클러스터 CA가 서명한 인증서의 Subject CN이 이름, O(여러 개 가능)가 그룹입니다. O=system:masters는 RBAC을 거치지 않는 최고 권한이라 어떤 바인딩으로도 줄일 수 없습니다.
  • CSR API. CertificateSigningRequest에 signerName: kubernetes.io/kube-apiserver-client와 expirationSeconds를 넣어 요청하고, 승인(approve) 권한이 있는 사람이 승인하면 컨트롤러 매니저가 서명합니다. 승인 권한 자체가 강력한 권한입니다.
  • 취소 불가. Kubernetes는 클라이언트 인증서 폐기 목록을 확인하지 않습니다. 유출되면 만료까지 유효하므로, 사람에게 장기 인증서를 주지 마세요. 쓴다면 짧은 expirationSeconds로.
  • kubeadm의 변화(1.29). admin.conf는 이제 system:masters가 아니라 kubeadm:cluster-admins 그룹(RBAC으로 cluster-admin 바인딩)을 쓰고, system:masters 인증서는 super-admin.conf로 분리되었습니다. super-admin.conf는 비상용으로 오프라인 보관하는 것이 권장입니다(9장).
짧은 수명의 사용자 인증서 발급 (실습용)
openssl req -new -newkey rsa:2048 -nodes -keyout dana.key -out dana.csr -subj "/CN=dana/O=dev-team"
kubectl apply -f - <<EOF
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata: {name: dana}
spec:
  request: $(base64 -w0 dana.csr)
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 3600            # 1시간
  usages: [client auth]
EOF
kubectl certificate approve dana
kubectl get csr dana -o jsonpath='{.status.certificate}' | base64 -d > dana.crt
openssl x509 -in dana.crt -noout -subject -enddate

ServiceAccount 토큰

종류만드는 법특징
바운드 토큰(프로젝티드)kubelet이 TokenRequest API로 받아 Pod에 프로젝티드 볼륨으로 넣음(11편 kube-api-access)대상(audience)·만료가 있고 Pod 객체에 묶여 Pod가 지워지면 무효. kubelet이 만료 전에 갱신
TokenRequest 직접kubectl create token <sa> --duration 10m --audience ...외부 시스템 연동·디버깅용 짧은 토큰
레거시 Secret 토큰kubernetes.io/service-account-token 타입 Secret만료 없음. 1.24부터 자동 생성 안 함, 오래 안 쓴 것은 정리 기능이 동작

토큰 서명 키는 기본적으로 API 서버가 들고 있지만, 1.36에서 외부 서명기(KMS·HSM 등)로 서명을 넘기는 기능이 GA가 되어 키를 클러스터 밖에 둘 수 있습니다. ServiceAccount 발급자(issuer)의 공개 키를 외부에 공개하면, 클라우드 IAM이 이 토큰을 믿게 할 수 있습니다. 이것이 IRSA·워크로드 아이덴티티의 원리이며 20편에서 깊게 다룹니다.

토큰 안 들여다보기
kubectl create token default --duration 10m | cut -d. -f2 | tr '_-' '/+' | base64 -d 2>/dev/null | jq .
# iss(발급자), aud(대상), exp(만료), kubernetes.io.pod(묶인 Pod 정보가 있으면) 확인
kubectl get secret -A --field-selector type=kubernetes.io/service-account-token   # 남아 있는 레거시 토큰 찾기

OIDC와 구조화된 인증 설정

예전에는 --oidc-issuer-url, --oidc-username-claim 같은 API 서버 플래그로 발급자 하나만 연결할 수 있었습니다. 구조화된 인증 설정(AuthenticationConfiguration, --authentication-config)은 1.34에서 GA(apiserver.config.k8s.io/v1)가 되었고 다음을 지원합니다.

  • 여러 발급자: 사내 IdP와 CI(GitHub Actions 등) 발급자를 동시에.
  • CEL 클레임 매핑: 이름·그룹·UID·extra를 표현식으로 만들기(예: 그룹 앞의 “/” 제거, 이메일 도메인으로 그룹 추가).
  • 검증 규칙: 클레임 검증(claimValidationRules, 예: email_verified)과 결과 사용자 검증(userValidationRules, 예: system: 접두사 금지).
  • 재시작 없는 재적용: 파일을 바꾸면 API 서버가 다시 읽습니다.
  • 발급자 탐색 URL 분리, 전용 CA: 사설 IdP 연결.

기존 --oidc-* 플래그와는 함께 쓸 수 없습니다. 매니지드 서비스는 이 파일을 직접 고칠 수 없으므로 벤더 기능(7장)을 씁니다.

AuthenticationConfiguration 예 (실습에서 사용)
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
jwt:
- issuer:
    url: https://KC_HOST:8443/realms/k8s
    audiences: [kubernetes]
    certificateAuthority: |
      -----BEGIN CERTIFICATE-----
      ...(Keycloak을 서명한 CA)...
      -----END CERTIFICATE-----
  claimValidationRules:
  - expression: 'has(claims.email_verified) && claims.email_verified == true'
    message: email must be verified
  claimMappings:
    username:
      claim: preferred_username
      prefix: "oidc:"                         # 내부 계정(system:…)과 섞이지 않게
    groups:
      expression: 'has(claims.groups) ? claims.groups.map(g, "oidc:" + (g.startsWith("/") ? g.substring(1) : g)) : []'
    uid:
      claim: sub
  userValidationRules:
  - expression: "!user.username.startsWith('system:')"
    message: username cannot use the reserved system: prefix
  - expression: "user.groups.all(g, !g.startsWith('system:'))"
    message: groups cannot use the reserved system: prefix

클레임 매핑 시뮬레이터

ID 토큰 클레임(JSON)과 매핑 방식을 바꿔 보면, API 서버가 만들 사용자 정보와 검증 결과가 나옵니다. 실습에서 Keycloak 그룹이 각 플랫폼에서 어떻게 보이는지 미리 예측하는 데 씁니다. (완전한 CEL 평가기가 아니라 자주 쓰는 패턴을 흉내 낸 것입니다.)

Pod 인증서와 ClusterTrustBundle

쉬운 말로 ServiceAccount 토큰은 “이 Pod는 이 계정입니다”라는 쪽지라 상대에게 보여 줘야 하고, 받은 쪽은 쪽지를 Kubernetes에 확인해야 합니다. Pod 인증서는 Pod가 들고 다니는 신분증(x509)이라, 서로 TLS로 바로 신원을 확인할 수 있습니다(메시 없이 mTLS). ClusterTrustBundle은 “어느 발급처의 신분증을 믿을지”를 모두에게 나눠 주는 공용 게시판입니다.
기능무엇상태쓰임
ClusterTrustBundle클러스터 범위 CA 번들 객체. 서명자별로 게시, Pod에 프로젝티드 볼륨(clusterTrustBundle)으로 자동 갱신 파일 제공1.29 알파 → 1.33 베타 → 1.37 GA(certificates.k8s.io/v1)사설 CA 배포, API 서버 서빙 CA 배포, Gateway의 클라이언트 인증서 검증 CA(Gateway API에서 참조 제안)
Pod 인증서(PodCertificateRequest)kubelet이 Pod 대신 서명자에게 인증서를 요청하고 podCertificate 프로젝티드 볼륨으로 키·인증서를 넣고 갱신1.34 알파 → 1.35 베타(기본 꺼짐). v1 승격 진행 중이므로 사용하는 버전의 API·기능 게이트 확인메시 없는 Pod 간 mTLS, 외부 시스템에 x509로 신원 증명. 서명자(컨트롤러)는 별도로 구현·설치
프로젝티드 볼륨에서의 모습 (개념)
volumes:
- name: certs
  projected:
    sources:
    - clusterTrustBundle:                   # 믿을 CA 번들
        signerName: example.com/workload-ca
        labelSelector: {matchLabels: {trust: workload}}
        path: ca.pem
    - podCertificate:                       # 이 Pod의 키·인증서(서명자가 발급)
        signerName: example.com/workload-ca
        keyType: ECDSAP256
        credentialBundlePath: credentials.pem

exec 플러그인은 kubectl이 요청을 보내기 전에 외부 프로그램을 실행해 자격 증명을 받는 방식입니다. 프로그램은 ExecCredential(client.authentication.k8s.io/v1) JSON으로 토큰(또는 클라이언트 인증서)과 expirationTimestamp를 돌려주고, kubectl은 만료 전까지 이를 재사용합니다. 대화형 로그인이 필요한지(interactiveMode), 클러스터 정보를 넘길지(provideClusterInfo)도 kubeconfig에 적습니다.

exec 플러그인 kubeconfig 예 (OIDC, kubelogin)
users:
- name: oidc-alice
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1
      command: kubectl
      args: [oidc-login, get-token,
             --oidc-issuer-url=https://KC_HOST:8443/realms/k8s,
             --oidc-client-id=kubernetes,
             --certificate-authority=/path/ca.pem]
      interactiveMode: IfAvailable         # 브라우저 로그인이 필요하면 사용
# 플러그인이 stdout으로 돌려주는 것:
# {"apiVersion":"client.authentication.k8s.io/v1","kind":"ExecCredential",
#  "status":{"token":"eyJ...","expirationTimestamp":"2026-10-23T10:15:00Z"}}

브레이크글라스 계정 설계

쉬운 말로 브레이크글라스는 “비상시 유리를 깨고 꺼내는 열쇠”입니다. 평소 로그인 시스템(IdP)이 고장 나거나 잘못 설정되어 아무도 들어가지 못할 때만 쓰는, 별도 경로의 최고 권한 계정입니다. 쓰는 순간 모두가 알아야 하고, 쓴 뒤에는 바로 바꿔야 합니다.

원칙

  1. 독립성. 평소 IdP·SSO·Rancher 같은 중간 계층에 의존하지 않는 경로.
  2. 봉인. 오프라인 보관(금고·비밀 관리 시스템의 별도 정책), 두 사람 승인으로 꺼냄.
  3. 감시. 사용 즉시 경보(감사 로그 규칙, 22편).
  4. 사용 후 교체. 인증서·자격 증명 회전.
  5. 정기 시험. 분기마다 실제로 들어가 본다(복구 리허설처럼).
환경브레이크글라스 수단주의
kubeadmsuper-admin.conf(system:masters) 오프라인 보관, 평소에는 admin.conf도 쓰지 않음취소 불가 → 노출 시 CA 회전 계획 필요
RKE2서버 노드의 관리자 kubeconfig(rke2.yaml), 노드 접근 자체를 봉인노드 SSH가 사실상 브레이크글라스
EKS별도 계정(또는 별도 IAM 역할)의 액세스 엔트리 + 클러스터 관리자 정책, 하드웨어 MFA클러스터 생성자 관리자 권한을 의도적으로 관리. aws-auth만 쓰던 시절의 잠김 사고 방지
AKS별도 Entra 비상 계정(조건부 액세스 예외, PIM) 그룹을 클러스터 관리자에, 로컬 계정은 비활성 유지 또는 일시 활성화 절차Entra 자체 장애 대비가 필요하면 로컬 계정 일시 활성화 절차를 문서화
GKE별도 Google 계정·서비스 계정에 클러스터 관리자 IAM, 키는 오프라인조직 정책으로 서비스 계정 키 생성이 막혀 있을 수 있음
OpenShift설치 시 생성된 system:admin kubeconfig(인증서) 오프라인 보관kubeadmin(임시 비밀번호)은 IdP 구성 후 삭제
Rancher다운스트림 클러스터의 ACE 또는 클러스터 자체 관리자 kubeconfigRancher 서버 장애 시 경로

실습: Keycloak 하나를 kubeadm·RKE2·OpenShift에 연결하기

호스트에서 Keycloak을 HTTPS로 띄우고, 같은 발급자 주소(issuer)로 세 클러스터를 연결합니다. 토큰의 iss 값이 발급자 설정과 글자 하나까지 같아야 하므로, 모든 VM이 닿을 수 있는 호스트의 LAN IP를 발급자 주소로 씁니다. 같은 사용자(alice·bob)가 각 플랫폼에서 어떤 이름·그룹으로 보이는지를 표로 비교하는 것이 목표입니다.

실습 0. Keycloak 준비

(1) 사설 CA와 서버 인증서, Keycloak 실행

openssl req -x509 -newkey rsa:2048 -nodes -days 365 -keyout ca.key -out ca.pem -subj "/CN=lab-oidc-ca"
openssl req -newkey rsa:2048 -nodes -keyout kc-key.pem -out kc.csr -subj "/CN=$HOSTIP"
printf "subjectAltName=IP:$HOSTIP\nextendedKeyUsage=serverAuth\n" > ext.cnf
openssl x509 -req -in kc.csr -CA ca.pem -CAkey ca.key -CAcreateserial -days 365 -out kc.pem -extfile ext.cnf
chmod 644 kc-key.pem && cd ../..

KCV=26.4                                                  # Keycloak 최신 버전 확인 후 고정
docker run -d --name kc -p 8443:8443 \

  --https-certificate-file=/certs/kc.pem --https-certificate-key-file=/certs/kc-key.pem \

# 기존 htpasswd 공급자가 있다면 identityProviders 목록에 함께 넣어야 함(병합 패치는 목록을 덮어씀)

# 웹 콘솔 → 로그인 화면에서 keycloak 선택 → alice 로그인 → 오른쪽 위 메뉴 'Copy login command'
oc login --token=sha256~... --server=https://api.crc.testing:6443
oc whoami; oc whoami --show-token | cut -c1-12
oc --context lab-ocp get users,identities                  # User 'alice', Identity 'keycloak:<sub>'
oc --context lab-ocp get groups                            # 그룹 클레임으로 만들어진 Group 객체(platform-admins, dev-team)
oc --context lab-ocp adm policy add-cluster-role-to-group cluster-reader platform-admins
oc --context lab-ocp get oauthaccesstokens                 # 발급된 토큰과 만료
비교표로 정리 플랫폼(kubeadm·RKE2·OpenShift) × 항목(alice의 이름, 그룹 표기, 매핑을 정하는 곳, 변경 반영 방식(파일 재적용·API 서버 재시작·OAuth 재시작), 토큰 수명, 취소 방법, RBAC 바인딩에 쓴 그룹 이름)을 채우세요. 같은 IdP에서도 그룹 문자열이 플랫폼마다 달라진다는 것이 이 실습의 핵심 결론입니다. kubernetes 클라이언트의 그룹 매퍼 full.path를 false로 바꾸고 kubeadm·RKE2 결과를 다시 비교해 보세요(OpenShift용 클라이언트는 처음부터 false로 둔 이유도 적어 두세요).

실습 4. 선택: EKS에 OIDC 공급자 연결

EKS는 aws eks associate-identity-provider-config로 외부 OIDC 공급자를 연결할 수 있지만, 발급자가 인터넷에서 접근 가능하고 공인 CA 인증서를 써야 합니다. 공인 도메인의 Keycloak이 있다면 usernamePrefix·groupsPrefix를 지정해 연결하고, 액세스 엔트리 기반 IAM 사용자와 OIDC 사용자가 같은 클러스터에서 어떻게 공존하는지 확인하세요.

정리

실습 후에는 API 서버 플래그와 설정 파일을 원래대로 돌리거나(다음 편들이 OIDC 사용자를 쓰므로 유지해도 됩니다), 실습용 ClusterRoleBinding oidc-platform-admins, kc-admins, kc-admins-path를 지우세요. Keycloak 컨테이너와 CA 키는 18~22편 실습에서 다시 씁니다.

현장 사례

퇴사자의 kubeconfig가 1년 동안 유효했다

원인. 사람마다 클러스터 CA로 1년짜리 클라이언트 인증서를 발급해 주었고, 퇴사자 인증서를 막을 방법이 없었습니다(Kubernetes는 클라이언트 인증서 폐기를 확인하지 않음).

교훈. 사람은 IdP(OIDC·클라우드 IAM)로, 인증서는 컴포넌트와 봉인된 비상 계정만. 이미 발급했다면 CA 회전 계획을 세우세요.

aws-auth ConfigMap 한 줄 실수로 모두가 잠겼다

원인. EKS의 aws-auth ConfigMap을 수정하다 YAML 들여쓰기를 망가뜨려 IAM 매핑 전체가 무효가 되었고, 클러스터 생성 역할 외에는 아무도 접근하지 못했습니다.

교훈. 인증 모드를 API로 옮겨 액세스 엔트리(AWS API로 관리, 감사 기록)로 바꾸고, 비상용 액세스 엔트리를 따로 두세요(19편).

OIDC를 붙였는데 모든 사람이 Forbidden

원인. Keycloak 그룹이 “/platform-admins”처럼 경로로 오는데 RBAC은 “platform-admins”로 바인딩했습니다. 접두사 설정까지 겹쳐 실제 그룹은 “oidc:/platform-admins”였습니다.

교훈. 바인딩 전에 kubectl auth whoami로 실제 그룹 문자열을 확인하세요. CEL로 정규화하거나 IdP에서 경로 표기를 끕니다(실습 2).

이메일을 사용자 이름으로 썼더니 남의 신원을 얻을 수 있었다

원인. 사용자가 프로필에서 이메일을 바꿀 수 있는 IdP였고, 이메일 검증 없이 email 클레임을 이름으로 매핑했습니다. 관리자 이메일로 바꾼 사용자가 그 권한을 얻었습니다.

교훈. 이름은 변경 불가능한 클레임(sub) 또는 검증된 클레임으로, 검증 규칙(email_verified)과 접두사를 함께 쓰세요. 사용자가 만들 수 있는 그룹도 같은 위험이 있습니다.

CI 로그에 찍힌 토큰으로 클러스터가 침해됐다

원인. CI가 만료 없는 레거시 ServiceAccount 토큰을 변수로 쓰고 있었고, 디버그 로그에 그 토큰이 출력되었습니다.

교훈. CI는 OIDC 제휴(CI가 발급한 짧은 토큰을 구조화된 인증 설정으로 신뢰)나 짧은 TokenRequest로 바꾸고, 레거시 토큰 Secret을 정리하세요(20편).

조건부 액세스 정책 변경 후 AKS 관리자가 아무도 못 들어갔다

원인. Entra 조건부 액세스 정책이 잘못 적용되어 관리자 그룹 전원이 토큰을 받지 못했고, 로컬 계정은 비활성화되어 있었습니다.

교훈. 조건부 액세스에서 제외된 비상 계정을 두고, 로컬 계정 일시 활성화 절차를 문서화하세요(9장).

OpenShift 설치 후 kubeadmin이 몇 달째 살아 있었다

원인. IdP 연결 후 임시 관리자 kubeadmin을 지우지 않았고, 그 비밀번호가 설치 로그 디렉터리에 그대로 있었습니다.

교훈. IdP 연결과 관리자 그룹 바인딩을 확인한 직후 oc delete secrets kubeadmin -n kube-system. 설치 산출물(auth 디렉터리)은 봉인 보관하세요.

점프 호스트의 공용 계정에서 다른 사람의 토큰이 쓰였다

원인. 여러 엔지니어가 점프 호스트의 같은 OS 계정을 썼고, kubelogin 토큰 캐시가 홈 디렉터리에 남아 다음 사람이 그대로 이전 사람의 신원으로 작업했습니다. 감사 로그의 이름이 실제 작업자와 달랐습니다.

교훈. 점프 호스트는 개인 계정으로, 토큰 캐시는 사람마다 분리하세요. 감사 로그가 의미를 가지려면 인증이 사람 단위여야 합니다(22편).

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. Kubernetes는 사용자 객체 없이 요청마다 인증기 체인으로 이름·그룹을 정하며, 그룹 문자열을 누가 만들 수 있는지가 곧 권한 경계입니다.
  2. x509는 취소할 수 없어 사람에게 부적합하고, ServiceAccount는 Pod에 묶인 바운드 토큰이 표준이며 레거시 토큰은 정리 대상입니다.
  3. 구조화된 인증 설정(1.34 GA)은 여러 OIDC 발급자, CEL 클레임 매핑, 검증 규칙을 제공하고, ClusterTrustBundle은 1.37에서 GA, Pod 인증서는 승격이 진행 중입니다.
  4. EKS 액세스 엔트리, AKS Entra ID, GKE IAM·Google 그룹, OpenShift OAuth, Rancher 인증 프록시는 그룹의 출처와 토큰 수명이 서로 다르므로 플랫폼별 그룹 매핑표가 필요합니다.
  5. exec 플러그인과 짧은 토큰을 기본으로 하고, 독립 경로·봉인·감시·회전·정기 시험을 갖춘 브레이크글라스 계정을 설계합니다.

다음 편 · 18편 RBAC 모델 완전 해부

Role·ClusterRole·RoleBinding·ClusterRoleBinding의 조합 규칙과 aggregated ClusterRole, 동사·리소스·서브리소스(pods/exec, pods/portforward)·resourceNames·nonResourceURLs의 함정, escalate·bind·impersonate 동사로 막는 권한 상승, 기본 ClusterRole(system:*, admin·edit·view)의 실제 범위를 다룹니다. 이 편의 OIDC 그룹으로 조직 역할 다섯 가지(플랫폼 관리자·팀 리드·개발자·CI 봇·감사자)를 모델링하고 kubectl auth can-i --list로 검증합니다.
