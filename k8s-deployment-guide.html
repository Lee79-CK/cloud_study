목차
    01

    왜 Pod가 아니라 Deployment인가

    Pod를 직접 만들어도 앱은 뜹니다. 그런데 운영에서는 아무도 그렇게 하지 않습니다. 이유는 딱 세 가지입니다.

    Pod는 컨테이너를 실행하는 가장 작은 단위지만, 일회용입니다. 노드가 죽으면 그 위의 Pod도 같이 사라지고 아무도 다시 만들어주지 않습니다. 개수를 늘리려면 사람이 YAML을 복사해야 하고, 이미지 버전을 바꾸려면 지우고 새로 만들어야 해서 그 사이 서비스가 끊깁니다.

    Deployment는 이 세 가지를 대신해 줍니다. 자가 치유(죽으면 다시 만듦), 스케일링(숫자만 바꾸면 됨), 무중단 업데이트와 롤백(이미지를 바꾸면 알아서 순차 교체).

    3단 계층 구조

    각 층을 눌러보세요
    계층을 선택하면 설명이 여기에 표시됩니다.

    명령형 vs 선언형

    명령형 — "이렇게 해"

    kubectl run, kubectl scale처럼 사람이 매번 동작을 지시합니다. 기록이 남지 않고, 누가 무엇을 바꿨는지 알 수 없습니다.

    선언형 — "이 상태여야 해"

    YAML에 원하는 상태를 적고 kubectl apply 합니다. 파일이 곧 문서이자 형상관리 대상이고, 클러스터가 알아서 그 상태로 수렴시킵니다.

    컨트롤 루프

    쿠버네티스 컨트롤러는 1초에도 수차례 "원하는 상태(spec) ↔ 실제 상태(status)"를 비교하고 차이를 줄이는 동작을 반복합니다. 히어로의 슬라이더에서 숫자를 올리면 Pod가 늘어난 것이 바로 이 루프입니다. YAML을 쓴다는 건 명령이 아니라 목표치를 등록하는 일입니다.

    02

    YAML 한 장 뜯어보기

    실무에서 쓰는 Deployment 전체입니다. 아무 줄이나 눌러보세요. 그 필드가 무엇이고, 빼면 어떻게 되는지 바로 설명이 뜹니다.

    필드 탐색기

    줄 클릭 · 색은 필드 그룹

    4개의 최상위 블록

    모든 쿠버네티스 오브젝트는 같은 뼈대를 씁니다. 이 네 개만 기억하면 Deployment든 Service든 구조가 똑같이 보입니다.

    블록역할헷갈리는 점
    apiVersion이 오브젝트를 해석할 API 그룹과 버전Deployment는 항상 apps/v1. v1은 Pod·Service·ConfigMap용
    kind오브젝트 종류대소문자 구분. deployment는 오류
    metadata이름, 네임스페이스, 라벨, 어노테이션여기의 labels는 Deployment 자신의 라벨. Pod 라벨이 아님
    spec원하는 상태 전부Pod 설계도는 spec.template 안에 또 한 겹 들어 있음
    YAML 문법에서 신입이 가장 많이 깨지는 곳

    ① 탭 문자 금지 — 반드시 스페이스 2칸. 편집기에서 탭을 스페이스로 바꿔두세요. ② 들여쓰기 한 칸 차이로 다른 필드가 됩니다. ③ 값에 콜론이나 #이 들어가면 따옴표로 감쌉니다. ④ 버전 번호 1.20은 숫자로 읽혀 1.2가 될 수 있으니 "1.20"처럼 문자열로 씁니다.

    03

    apiVersion · kind · metadata

    오브젝트의 신분증에 해당하는 부분입니다. 짧지만 라벨 설계는 나중에 운영 난이도를 좌우합니다.

    apiVersion: apps/v1          # Deployment는 apps 그룹의 v1
kind: Deployment
metadata:
  name: web-api               # 네임스페이스 안에서 유일해야 함 (소문자, 숫자, - 만)
  namespace: shop-prod        # 생략하면 kubectl의 현재 컨텍스트 네임스페이스
  labels:                     # 셀렉터/검색/과금 집계용 키-값
    app: web-api
    tier: backend
    env: prod
  annotations:                # 셀렉터로는 못 쓰는 부가 정보 (긴 값 가능)
    owner: "platform-team@example.com"
    kubernetes.io/change-cause: "image bump to 1.8.2"

    metadata.name 이름 규칙

    • 소문자 영문·숫자·하이픈만. 253자 이하, 시작과 끝은 영숫자 (RFC 1123)
    • 같은 네임스페이스 + 같은 kind 안에서 유일. 다른 네임스페이스라면 같은 이름 가능
    • 생성 후 변경 불가. 이름을 바꾸려면 지우고 새로 만드는 것과 같습니다
    • Pod 이름은 여기서 파생됩니다 → web-api-7d9f4c8b6d-x2klm = Deployment명 + ReplicaSet 해시 + 랜덤

    labels 라벨은 나중의 나를 살린다

    라벨은 단순한 태그가 아니라 선택의 기준입니다. Service가 어떤 Pod로 트래픽을 보낼지, NetworkPolicy가 어떤 Pod를 막을지, 모니터링이 어떤 단위로 묶을지 전부 라벨로 결정됩니다. 팀 표준을 미리 정해두세요.

    권장 키예시 값용도
    app.kubernetes.io/nameweb-api애플리케이션 이름 (공식 권장 키)
    app.kubernetes.io/instanceweb-api-prod같은 앱의 여러 배포본 구분
    app.kubernetes.io/version"1.8.2"앱 버전
    app.kubernetes.io/part-ofshop상위 시스템
    env / tier / teamprod / backend / payments조직 내부 분류, 비용 집계
    labels와 annotations 구분

    labels는 검색·선택용이라 길이 제한(63자)이 있고 셀렉터에서 씁니다. annotations는 선택에 쓰지 못하는 대신 길이가 자유로워 배포 커밋 해시, 담당자, 툴 설정 같은 걸 넣습니다. 롤아웃 이력에 사유를 남기는 kubernetes.io/change-cause가 대표적입니다.

    04

    spec.replicas 와 spec.selector

    Deployment가 "내 Pod"를 알아보는 방법입니다. 여기서 실수하면 배포 자체가 거부되거나, 남의 Pod를 빼앗아 옵니다.

    spec.replicas 몇 개를 유지할까

    • 기본값 1. 운영 서비스는 최소 2 이상 — 노드 하나가 빠져도 살아남아야 합니다
    • 0도 유효합니다. 오브젝트는 남기고 Pod만 내리는 "일시 정지" 용도로 씁니다
    • HPA(오토스케일러)를 붙였다면 YAML에서 replicas 필드를 빼세요. 남겨두면 apply 할 때마다 HPA가 늘려놓은 수를 되돌려 버립니다
    kubectl scale deployment/web-api --replicas=5        # 즉시 조절 (명령형)
kubectl get deploy web-api                            # READY 3/5 → 원하는 수 5, 준비된 수 3
    READY 3/5가 뜻하는 것

    왼쪽은 준비 완료된 Pod, 오른쪽은 원하는 개수입니다. 숫자가 다르다면 스케줄 대기(노드 자원 부족), 이미지 pull 중, readiness probe 실패 중 하나입니다. kubectl get pods와 kubectl describe pod의 Events를 순서대로 보세요.

    spec.selector 내 Pod를 고르는 조건

    Deployment는 자기가 만든 Pod를 이름이 아니라 라벨로 추적합니다. spec.selector.matchLabels에 적은 조건이 spec.template.metadata.labels에 반드시 포함되어야 하고, 그렇지 않으면 API 서버가 생성 자체를 거부합니다.

    셀렉터 매칭 실험실

    값을 바꿔 결과를 확인
    :
    :
    selector는 만든 뒤 바꿀 수 없습니다

    spec.selector는 불변(immutable) 필드입니다. 이미 떠 있는 Deployment의 셀렉터를 수정해서 apply 하면 field is immutable 오류가 납니다. 바꿔야 한다면 새 이름으로 만들고 트래픽을 옮긴 뒤 옛것을 지우는 방식이 안전합니다. 그래서 라벨 설계는 처음에 신중해야 합니다.

    matchExpressions — 조건식으로 고르기

    selector:
  matchLabels:
    app: web-api
  matchExpressions:                 # matchLabels와 AND 조건
    - key: tier
      operator: In                  # In, NotIn, Exists, DoesNotExist
      values: [backend, api]
    05

    spec.template — Pod 설계도

    Deployment YAML의 8할은 여기입니다. template 아래는 Pod 정의와 완전히 동일한 문법입니다.

    spec.template은 "Pod를 찍어낼 틀"입니다. apiVersion과 kind만 빠졌을 뿐, 그 아래 metadata와 spec은 Pod 오브젝트와 똑같습니다. 그래서 Pod YAML을 읽을 줄 알면 Deployment의 절반은 이미 아는 셈입니다.

    spec:
  template:                        # ← 여기부터 아래는 전부 "Pod 정의"
    metadata:
      labels:                      # selector와 반드시 매칭
        app: web-api
        version: v2
      annotations:
        prometheus.io/scrape: "true"
    spec:                          # ← Pod의 spec (Deployment의 spec이 아님)
      serviceAccountName: web-api-sa
      terminationGracePeriodSeconds: 30
      containers: [...]
      initContainers: [...]
      volumes: [...]
      nodeSelector: {...}
    spec이 두 번 나오는 이유

    바깥 spec은 Deployment의 원하는 상태(몇 개, 어떤 방식으로 교체), 안쪽 template.spec은 Pod 하나의 정의(무슨 컨테이너, 어떤 볼륨)입니다. 들여쓰기를 잘못해 containers를 바깥 spec에 두면 unknown field 오류가 납니다.

    template이 바뀌면 새 버전이 만들어진다

    Deployment는 spec.template의 내용을 해시로 요약해 ReplicaSet 이름에 붙입니다. template 안의 무엇이든 바뀌면 새 ReplicaSet이 생기고 롤아웃이 시작됩니다. 반대로 replicas만 바꾸면 기존 ReplicaSet의 개수만 조정되고 롤아웃은 일어나지 않습니다.

    바꾼 필드롤아웃 발생결과
    template.spec.containers[].image발생새 ReplicaSet 생성 후 순차 교체
    template.metadata.labels / annotations발생값 한 글자만 달라도 전체 Pod 재생성
    template.spec.containers[].resources발생Pod 재생성 필요
    spec.replicas없음기존 Pod 유지, 개수만 증감
    참조 중인 ConfigMap의 내용없음envFrom이면 재시작 전까지 반영 안 됨 (아래 참고)
    ConfigMap을 고쳤는데 앱이 그대로일 때

    ConfigMap 수정은 Deployment의 template을 건드리지 않으므로 롤아웃이 일어나지 않습니다. 환경변수로 주입했다면 Pod를 새로 만들어야 반영됩니다. 실무에서는 kubectl rollout restart deployment/web-api를 쓰거나, template annotations에 설정 해시를 넣어 자동으로 롤아웃되게 만듭니다.

    06

    containers — 실제로 무엇을 실행할지

    이미지, 포트, 환경변수, 실행 명령. 앱과 직접 맞닿는 필드들입니다.

    containers:
  - name: web-api                      # Pod 안에서 유일한 이름 (로그 조회 시 -c 값)
    image: registry.example.com/shop/web-api:1.8.2
    imagePullPolicy: IfNotPresent      # Always | IfNotPresent | Never
    command: ["/app/server"]           # 이미지의 ENTRYPOINT를 덮어씀
    args: ["--port=8080", "--mode=prod"]  # CMD를 덮어씀
    ports:
      - name: http                     # 15자 이하, Service에서 이름으로 참조 가능
        containerPort: 8080            # 컨테이너가 실제로 listen 하는 포트
        protocol: TCP
    env:
      - name: LOG_LEVEL
        value: "info"                  # 값은 항상 문자열
      - name: DB_HOST
        valueFrom:
          configMapKeyRef: { name: web-api-config, key: db.host }
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef: { name: web-api-secret, key: password }
      - name: POD_IP                   # 클러스터가 채워주는 값
        valueFrom:
          fieldRef: { fieldPath: status.podIP }
    envFrom:                           # ConfigMap 전체를 한 번에 환경변수로
      - configMapRef: { name: web-api-common }
    volumeMounts:
      - name: config-vol
        mountPath: /etc/app
        readOnly: true

    image 태그 하나가 장애를 만든다

    작성 방식평가이유
    nginx금지:latest로 해석. 노드마다 다른 버전이 뜰 수 있음
    nginx:latest금지같은 태그의 내용이 언제든 바뀜 → 재현 불가, 롤백 불가
    nginx:1.27.3권장버전 고정. 대부분의 팀 표준
    nginx@sha256:9b1d...가장 안전다이제스트 고정. 내용이 100% 동일함을 보장
    latest + imagePullPolicy: Always 조합의 함정

    태그를 생략하거나 :latest를 쓰면 pull 정책이 자동으로 Always가 됩니다. Pod가 재시작될 때마다 내용이 달라질 수 있어 "어제는 됐는데 오늘 안 되는" 전형적인 장애가 생기고, rollout undo를 해도 같은 태그라 이전 이미지로 못 돌아갑니다.

    command / args Docker와 매핑

    • command = Dockerfile의 ENTRYPOINT를 덮어씀
    • args = Dockerfile의 CMD를 덮어씀
    • 둘 다 생략하면 이미지에 정의된 것이 그대로 실행됩니다. 특별한 이유가 없으면 건드리지 않는 것이 정답
    • 쉘 문법(|, &&, 변수 확장)이 필요하면 ["/bin/sh","-c","..."] 형태로 감싸야 합니다

    ports 선언은 문서일 뿐

    containerPort를 안 써도 통신은 됩니다

    containerPort는 방화벽을 여는 설정이 아니라 정보 표기에 가깝습니다. 적지 않아도 Pod IP로 접근됩니다. 그래도 적는 이유는 ① 사람이 읽을 문서가 되고 ② Service의 targetPort에서 이름으로 참조할 수 있기 때문입니다. 포트를 바꿔도 Service를 고칠 필요가 없어집니다.

    # Deployment 쪽
ports:
  - name: http
    containerPort: 8080
---
# Service 쪽 — 숫자 대신 이름으로 연결
apiVersion: v1
kind: Service
metadata: { name: web-api }
spec:
  selector:
    app: web-api          # Deployment의 template labels와 일치해야 함
  ports:
    - port: 80            # 클러스터 내부에서 호출할 포트
      targetPort: http    # 컨테이너 포트 "이름"

    initContainers — 본 컨테이너 전에 할 일

    initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ["sh","-c","until nc -z db 5432; do echo waiting; sleep 2; done"]

    순서대로 하나씩 실행되고 전부 성공해야 본 컨테이너가 시작합니다. DB 마이그레이션, 설정 파일 내려받기, 의존 서비스 대기에 씁니다. 실패하면 Pod는 Init:Error 또는 Init:CrashLoopBackOff 상태로 멈춥니다.

    07

    resources — 요청량과 상한

    스케줄링, 비용, 장애 복구 우선순위가 전부 이 네 줄에서 결정됩니다.

    resources:
  requests:            # 스케줄러가 노드를 고를 때 쓰는 "예약량"
    cpu: "250m"        # 250 밀리코어 = 0.25 vCPU
    memory: "256Mi"
  limits:              # 이 이상은 못 쓰는 "상한"
    cpu: "500m"
    memory: "512Mi"

    단위 읽는 법

    표기의미메모
    1000mCPU 1코어m = 밀리. 0.5와 500m은 같은 값
    256Mi256 × 1024² 바이트메모리는 Mi / Gi(2진)를 쓰는 게 표준
    256M256 × 1000² 바이트Mi보다 약 5% 작음. 섞어 쓰면 계산이 틀어집니다
    1Gi1024Mi메모리 단위는 대소문자 구분 (mi는 오류)
    CPU와 메모리는 초과했을 때 결과가 다릅니다

    CPU 초과 → 쓰로틀링. 느려지지만 죽지는 않습니다. 메모리 초과 → 즉시 OOMKilled로 컨테이너가 강제 종료되고 재시작됩니다. 그래서 메모리 limit은 실제 사용량에 여유를 두고 잡아야 하고, CPU limit은 과하게 조이면 지연만 늘어납니다.

    QoS 클래스 계산기

    값을 넣으면 등급이 바뀝니다

    얼마로 잡아야 할까

    • requests: 평상시 사용량에 맞춥니다. 너무 크게 잡으면 노드 자원을 예약만 하고 놀려 비용이 새고, 너무 작으면 노드가 과밀해져 서로를 방해합니다
    • limits.memory: 피크 사용량 + 30~50% 여유. JVM이라면 힙 설정과 같이 계산해야 합니다
    • limits.cpu: 지연에 민감한 API 서버는 생략하거나 넉넉히. 배치 작업은 다른 워크로드를 지키기 위해 걸어둡니다
    • 실측이 먼저입니다 → kubectl top pod, VPA의 추천값, Prometheus의 P95 사용량을 근거로 조정하세요

    08

    probe — 살아있는지, 받을 준비가 됐는지

    세 가지 probe는 이름이 비슷하지만 하는 일이 완전히 다릅니다. 이걸 혼동하면 배포할 때마다 오류가 튑니다.

    readinessProbe — 트래픽 받을 준비

    실패하면 Service 엔드포인트에서 제외됩니다. 컨테이너는 그대로 살아 있고, 성공하면 다시 합류합니다. 롤아웃에서 "준비됨" 판정 기준이기도 합니다.

    livenessProbe — 살아있는지

    실패가 누적되면 컨테이너를 죽이고 재시작합니다. 데드락처럼 프로세스는 떠 있는데 응답이 없는 상황을 복구하는 용도입니다.

    startupProbe — 초기 기동 유예

    성공할 때까지 다른 두 probe를 잠시 꺼둡니다. 기동이 느린 앱이 liveness에 걸려 무한 재시작하는 걸 막습니다.

    startupProbe:                    # 최대 5 x 30 = 150초까지 기동 대기
  httpGet: { path: /healthz, port: http }
  failureThreshold: 30
  periodSeconds: 5

readinessProbe:
  httpGet:
    path: /readyz                # DB 연결 등 의존성까지 확인하는 엔드포인트
    port: http
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 2
  successThreshold: 1            # readiness만 2 이상 설정 가능
  failureThreshold: 3

livenessProbe:
  httpGet:
    path: /healthz               # 의존성 검사는 넣지 말 것 (자신만 확인)
    port: http
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3            # 3번 연속 실패 → 재시작
    필드기본값의미
    initialDelaySeconds0컨테이너 시작 후 첫 검사까지 대기 시간
    periodSeconds10검사 주기
    timeoutSeconds1응답 대기 한계. 넘으면 실패 1회로 집계
    failureThreshold3연속 실패 몇 번에 조치할지
    successThreshold1연속 성공 몇 번에 정상 판정 (liveness/startup은 1 고정)

    probe 타임라인 시뮬레이터

    재생 후 앱을 고장내 보세요
    t = 0s 상태: 대기 Service 연결: 끊김 재시작: 0회
    가장 흔한 사고: liveness에 의존성 검사를 넣는 것

    liveness 경로에서 DB를 확인하면, DB가 잠깐 느려질 때 모든 Pod가 동시에 재시작합니다. 복구 중인 DB에 재접속 폭풍이 몰리며 장애가 커집니다. 의존성 확인은 readiness에, liveness는 프로세스 자체의 건강만 보도록 나누세요. 그리고 기동이 느린 앱에는 initialDelaySeconds를 늘리기보다 startupProbe를 쓰는 편이 안전합니다.

    09

    strategy — 어떻게 교체할 것인가

    maxSurge와 maxUnavailable 두 숫자가 배포 속도와 서비스 안정성을 동시에 결정합니다.

    spec:
  strategy:
    type: RollingUpdate            # 기본값. 또는 Recreate
    rollingUpdate:
      maxSurge: 25%                # 원하는 개수보다 몇 개까지 더 만들 수 있나
      maxUnavailable: 25%          # 준비된 Pod가 몇 개까지 모자라도 되나
  minReadySeconds: 10              # 준비 후 이 시간 동안 죽지 않아야 "사용 가능"으로 인정
  progressDeadlineSeconds: 600     # 이 시간 안에 진전이 없으면 롤아웃 실패 처리
  revisionHistoryLimit: 10         # 롤백용으로 보관할 이전 ReplicaSet 개수
    RollingUpdate

    새 Pod를 조금씩 띄우고 옛 Pod를 조금씩 내립니다. 무중단이지만 두 버전이 잠시 공존하므로 DB 스키마 호환성이 필요합니다.

    Recreate

    옛 Pod를 전부 내린 뒤 새 Pod를 띄웁니다. 다운타임이 생기지만 버전 공존이 불가능한 앱(단일 DB 락, 비호환 마이그레이션)에 씁니다.

    롤링 업데이트 시뮬레이터

    한 단계씩 진행해보기
    허용 총 Pod 5 · 최소 가용 3 가용 4

    두 숫자를 어떻게 정할까

    설정성격언제 쓰나
    surge 25% / unavail 25%기본값. 무난한 속도대부분의 서비스
    surge 1 / unavail 0가장 안전, 가장 느림용량 여유가 없으면 안 되는 핵심 API. 항상 replicas 만큼 가용
    surge 100% / unavail 0가장 빠름, 자원 2배 필요배포 창이 짧고 노드 여유가 충분할 때
    surge 0 / unavail 1추가 자원 없이 교체노드 자원이 빠듯한 환경. 용량이 잠시 줄어듦
    둘 다 0은 불가

    maxSurge와 maxUnavailable을 동시에 0으로 두면 새 Pod를 만들 수도, 옛 Pod를 지울 수도 없어 롤아웃이 영원히 멈춥니다. API 서버가 이 조합을 거부합니다. 또한 퍼센트 계산에서 maxSurge는 올림, maxUnavailable은 내림이 적용된다는 점도 기억해 두세요.

    롤아웃 조작 명령

    kubectl set image deploy/web-api web-api=registry/web-api:1.8.3 --record
kubectl rollout status deploy/web-api          # 완료될 때까지 진행 상황 출력
kubectl rollout pause  deploy/web-api          # 카나리처럼 중간에 멈추기
kubectl rollout resume deploy/web-api
kubectl rollout history deploy/web-api         # 리비전 목록
kubectl rollout undo    deploy/web-api                      # 직전 버전으로
kubectl rollout undo    deploy/web-api --to-revision=3      # 특정 리비전으로
kubectl rollout restart deploy/web-api         # 이미지 그대로 Pod만 순차 재생성
    안전한 배포의 실제 조합

    롤링 업데이트만으로는 부족합니다. readinessProbe가 있어야 "준비됨"을 정확히 판정하고, minReadySeconds가 있어야 켜지자마자 죽는 Pod를 걸러내며, PodDisruptionBudget이 있어야 노드 정리 작업 중에도 최소 대수가 유지됩니다. 세 개가 같이 있어야 진짜 무중단입니다.

    운영에서 더 쓰게 되는 필드들

    처음엔 없어도 뜨지만, 장애를 한 번 겪으면 반드시 추가하게 되는 설정입니다.

    종료를 우아하게 — terminationGracePeriodSeconds와 preStop

    spec:
  template:
    spec:
      terminationGracePeriodSeconds: 30    # SIGTERM 후 SIGKILL까지의 유예 (기본 30)
      containers:
        - name: web-api
          lifecycle:
            preStop:
              exec:
                command: ["sh","-c","sleep 5"]   # 엔드포인트 제거가 퍼질 시간 확보

    Pod를 지우면 엔드포인트 제거와 SIGTERM 전달이 거의 동시에 일어납니다. 프록시 설정이 모든 노드에 퍼지기까지 짧은 시차가 있어, 이미 종료 중인 Pod로 요청이 몇 건 더 들어옵니다. preStop에서 몇 초 버텨주면 이 502를 없앨 수 있습니다. 그리고 앱은 SIGTERM을 받으면 새 요청은 거절하되 처리 중인 요청은 끝내고 종료하도록 구현되어야 합니다.

    보안 기본값 — securityContext

    spec:
  template:
    spec:
      securityContext:               # Pod 전체에 적용
        runAsNonRoot: true
        runAsUser: 10001
        fsGroup: 10001
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: web-api
          securityContext:           # 컨테이너 단위가 우선
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }

    배치 제어 — 어느 노드에 어떻게 퍼뜨릴까

    spec:
  template:
    spec:
      nodeSelector:                       # 가장 단순한 노드 지정
        node-role: application
      tolerations:                        # taint가 걸린 노드에도 배치 허용
        - key: dedicated
          operator: Equal
          value: gpu
          effect: NoSchedule
      topologySpreadConstraints:          # 가용영역에 고르게 분산
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: web-api }
      affinity:
        podAntiAffinity:                  # 같은 앱 Pod끼리 다른 노드로
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector:
                  matchLabels: { app: web-api }
    required와 preferred

    requiredDuringScheduling...은 조건을 못 맞추면 Pod가 Pending으로 멈춥니다. preferred...는 가능하면 지키고 안 되면 그냥 배치합니다. 노드가 적은 클러스터에서 required를 걸었다가 배포가 통째로 막히는 경우가 흔하니, 처음에는 preferred로 시작하세요.

    볼륨 붙이기

    spec:
  template:
    spec:
      volumes:
        - name: config-vol
          configMap: { name: web-api-config }
        - name: secret-vol
          secret: { secretName: web-api-secret, defaultMode: 0400 }
        - name: cache-vol
          emptyDir: { sizeLimit: 500Mi }       # Pod 생명주기와 함께 사라짐
      containers:
        - name: web-api
          volumeMounts:
            - { name: config-vol, mountPath: /etc/app, readOnly: true }
            - { name: cache-vol,  mountPath: /tmp/cache }

    필드기본값쓰는 이유
    minReadySeconds0준비 직후 죽는 Pod를 롤아웃 성공으로 오인하지 않게
    progressDeadlineSeconds600멈춘 롤아웃을 실패로 표시해 CI가 감지할 수 있게
    revisionHistoryLimit10롤백 가능 범위. 0이면 롤백 불가
    pausedfalsetrue면 template을 바꿔도 롤아웃하지 않음 (여러 변경 묶기)
