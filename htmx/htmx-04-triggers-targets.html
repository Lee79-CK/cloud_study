02

트리거 문법 해부

공식 레퍼런스가 정리한 형식은 <이벤트>[<필터>] <수식어들> [, ...]입니다. 쉼표로 여러 트리거를 나열하고, 각 트리거는 이벤트 이름, 대괄호 필터, 공백으로 구분된 수식어로 이루어집니다.

트리거 하나를 분해하면
hx-trigger="keyup[key === 'Enter'] from:body once, every 5s [document.visibilityState === 'visible']"

수식어는 HCON으로 파싱된다

htmx 4는 hx-trigger, hx-swap, hx-vals 같은 설정형 속성을 HCON이라는 작은 설정 언어로 읽습니다(소스 첫머리의 주석). 키:값 쌍을 공백이나 쉼표로 나열하고, 값만 있는 단어는 true가 됩니다. 그래서 delay:300ms는 {delay: "300ms"}, once는 {once: true}입니다.

공백이 든 선택자는 반드시 감싸기 (조용히 실패함)

hx-trigger="submit from:closest form"은 HCON에서 {from: "closest", form: true}로 쪼개집니다. "closest"라는 선택자는 아무것도 찾지 못하므로 이벤트가 영영 연결되지 않고, 콘솔 경고도 없습니다. 공식 레퍼런스는 공백이나 쉼표가 든 from·target 값을 작은따옴표, 큰따옴표, 또는 <.../>로 감싸라고 안내합니다. 세 형태를 htmx 4.0.1로 직접 시험한 결과, 감싸지 않은 쪽만 요청이 나가지 않았습니다.

동작하지 않음
<div hx-get="/x" hx-trigger="submit from:closest form">
동작함 (세 가지 모두)
hx-trigger="submit from:'closest form'"
hx-trigger='submit from:"closest form"'
hx-trigger="submit from:<closest form/>"

2.x 문서나 블로그의 예제를 옮겨 올 때 가장 자주 밟는 함정입니다. 2.x는 from:closest form처럼 감싸지 않아도 동작했기 때문입니다.

자동 입력은 "web-server" 10글자를 치고 0.7초 멈춘 뒤, 마지막 글자를 지웠다가 같은 글자를 다시 치고, 값을 바꾸지 않는 방향키를 두 번 누릅니다. 트리거로 keyup을 쓴 이유는 방향키처럼 값이 바뀌지 않는 키 입력도 이벤트를 만들기 때문입니다. 결과를 읽는 법은 이렇습니다. changed만 붙은 칸은 방향키 두 번을 걸러 냅니다. changed delay 칸은 멈춤 시점에 한 번 보낸 뒤, 지웠다 다시 친 결과가 마지막으로 보낸 값과 같으므로 두 번째 요청을 생략해 총 1회가 됩니다. throttle은 간격마다 최대 한 번 보냅니다.

changed는 "언제" 비교하나 (소스 확인)

htmx 4.0.1에서 changed 검사는 지연·스로틀이 끝난 뒤 실제로 요청을 보내기 직전에 실행되며, 직전에 통과한 값과 비교합니다. 그래서 수식어 없이 changed만 쓰면 "바로 앞 이벤트의 값"과, delay와 함께 쓰면 "마지막으로 보낸 요청의 값"과 비교하는 셈이 됩니다. 검색창에서 changed delay 조합이 특히 효과적인 이유입니다.

수식어동작 (htmx 4.0.1)대표 용도
[필터]이벤트 이름 바로 뒤 대괄호 안의 JS 식이 참일 때만. 이벤트 속성(key, shiftKey 등)을 이름만으로 참조keyup[key === 'Enter'], click[shiftKey]

소스에서 확인한 미묘한 규칙 하나

htmx 4.0.1은 새 이벤트가 들어오면 같은 요소의 다른 트리거에 걸려 있던 지연·스로틀 대기도 함께 취소합니다(every 제외). 9절의 검색 폼처럼 input changed delay:300ms, change changed를 한 요소에 같이 걸어도, 셀렉트를 바꾸는 순간 진행 중이던 타이핑 지연이 정리되어 요청이 겹치지 않습니다.

필터와 hx-on, js: 값은 내부적으로 JS 코드를 평가합니다. 공식 문서도 보안 고려사항을 따로 안내하고 있으며, CSP(콘텐츠 보안 정책)를 엄격히 쓰는 환경에서는 제약이 생깁니다. 17편에서 hx-csp 확장과 함께 다룹니다.

04

특수 이벤트: load, revealed·intersect, every

DOM에 없는 이벤트를 htmx가 만들어 주는 것들입니다. 지연 로딩, 무한 스크롤, 폴링이 모두 여기서 나옵니다.

이벤트언제수식어
load요소가 htmx에 처리될 때 즉시 (리스너 없이 바로 실행)delay:와 조합해 "1.5초 뒤 한 번" (3편 전환 중 행)
intersect요소가 보이는 영역에 들어올 때마다root:, rootMargin:, threshold:, from:
revealedintersect와 같되 첫 번째 한 번만 (관찰 종료)위와 같음
every 시간간격마다. 요소가 문서에서 사라지면 타이머 자동 정리간격 뒤 [필터]로 조건부 폴링

마지막 줄(센티널)이 상자 안에서 보이면 자기 자신을 "다음 5건 + 새 센티널"로 교체합니다. 4페이지(20건)에서 서버가 센티널을 빼고 응답하면 멈춥니다.

스크롤 상자 안에서는 root:가 필요하다 (랩에서 실제로 겪은 일)

revealed의 기본 기준은 브라우저 창(뷰포트)입니다. 랩의 VM 표는 높이가 제한된 스크롤 상자(.table-scroll) 안에 있는데, 이 상자의 아래쪽이 창 밖에 걸쳐 있으면 상자를 끝까지 스크롤해도 센티널은 "창 안"에 들어오지 않아 다음 페이지가 영영 오지 않았습니다. hx-trigger="revealed root:.table-scroll"로 기준을 상자로 바꾸자 15 → 30 → 45 → 48건이 정상적으로 이어졌습니다.

every 2s [window.pollOn], refreshNow from:document
서버 시각 (폴링)
--:--:--
요청 0회

일시정지하면 필터 [window.pollOn]이 거짓이 되어 타이머는 돌지만 요청은 나가지 않습니다. 랩에서는 이 자리에 document.visibilityState === 'visible'을 넣어, 탭이 숨겨지면 폴링을 멈춥니다.

2.x와 다른 점: 286 상태 코드로 폴링 멈추기는 없다

htmx 2.0.11 소스에는 응답 코드 286을 받으면 폴링을 멈추는 코드가 있지만, htmx 4.0.1 소스에는 286 처리가 없습니다. 4.x에서 every 타이머가 멈추는 조건은 요소가 문서에서 사라질 때입니다. 그래서 하이퍼미디어답게 서버가 폴링 속성이 없는 HTML로 그 요소를 교체하면 폴링이 끝납니다. 3편의 "전환 중" 행이 load delay:1.5s로 한 번 다시 묻고, 실행 중이 되면 폴링 속성이 없는 행으로 바뀌는 것도 같은 원리입니다.

05

from:과 이벤트의 경로

서버가 HX-Trigger 응답 헤더로 이벤트를 보내면, 페이지의 다른 요소가 from:으로 그 이벤트를 듣고 스스로 갱신할 수 있습니다. 랩의 요약 카드가 이 방식으로 재시작·삭제 직후 바로 바뀝니다. 그런데 이벤트가 어디서 발생하는지 정확히 알아야 from:을 제대로 고를 수 있습니다.

상황이벤트가 발생하는 곳 (htmx 4.0.1)듣는 쪽 선택
HX-Trigger에 target 지정 없음, 요청 요소가 문서에 있음요청을 보낸 요소. 위로 버블링되어 body·document까지 전달from:body 또는 from:document
HX-Trigger에 target 지정 없음, 요청 요소가 스왑으로 사라짐document (htmx.trigger가 연결 끊긴 요소 대신 document로 보냄)from:document만 받음. from:body는 놓침
HX-Trigger의 이벤트 값에 "target": "#vm-app"해당 선택자로 찾은 요소그 요소 또는 조상

두 번째 줄이 핵심입니다. 랩의 재시작 버튼은 응답으로 자기 행이 통째로 교체되므로, 응답 헤더가 처리되는 시점(스왑 이후)에는 이미 문서에서 떨어져 있습니다. 브라우저 테스트에서 vmChanged 이벤트를 body와 document 양쪽에서 기다렸더니 document에서만 잡혔습니다. 공식 레퍼런스는 "HX-Trigger 이벤트는 body로 보내지므로 from:body로 들으라"고 안내하지만, 요청 요소가 교체되는 패턴에서는 from:document가 안전합니다. 그래서 랩의 요약 카드는 vmChanged from:document를 씁니다.

정정: 1편·2편의 설명

1편 6절과 2편에서 "문서에서 떨어져 나간 요소의 이벤트는 위로 전파되지 않으므로 받을 요소를 target으로 지정한다"고 설명했습니다. htmx 4.0.1의 htmx.trigger() 소스를 다시 보면, 대상이 문서에 연결되어 있지 않을 때 이벤트를 document에 대신 발생시킵니다. 따라서 정확한 설명은 "#vm-app에 단 리스너는 받지 못하지만 document 리스너는 받는다"입니다. 1·2편 코드의 target: "#vm-app" 지정 자체는 여전히 올바른 해결책입니다.

나머지 특수값도 정리해 둡니다. from:self는 자식에서 버블링된 이벤트를 무시하고 요소 자신의 이벤트만, from:outside는 요소 바깥 어디서든 발생한 이벤트를 듣습니다(드롭다운 바깥 클릭으로 닫기 등). htmx가 만드는 이벤트는 composed: true로 발생하므로 섀도 DOM 경계도 넘어갑니다. 12편 웹 컴포넌트 아일랜드에서 이 성질을 씁니다.

06

요청 동기화와 중복 방지

htmx 4.0.1은 요소마다 요청 대기열을 하나씩 둡니다. 요청이 진행 중일 때 같은 요소에서 또 요청이 생기면 어떻게 될까요? 아래 실험은 응답이 1.2초 걸리는 모의 서버에 버튼을 0.15초 간격으로 세 번 누릅니다.

hx-sync 전략 비교기 (htmx 4.0.1 실동작)

각 상자의 "3연타"를 누르거나 전체 실행
기본값
(hx-sync 없음 = queue first)

            전략진행 중에 새 요청이 오면 (소스의 RequestQueue)3연타 결과쓰는 곳
            기본값 queue first대기열이 비어 있으면 하나만 대기, 나머지 버림2번 실행 (1번째 + 2번째 대기분)대부분의 버튼
            drop새 요청을 버림1번 실행"저장" 같은 멱등이 아닌 동작
            abort새 요청을 버리고, 이후 다른 요청이 오면 이 요청을 취소당하게 함-폼 제출 중 검증 요청 정리
            replace진행 중인 요청을 취소하고 대기열을 비운 뒤 새 요청 실행마지막 것만 완료, 앞의 것은 취소검색 (늦게 온 옛 결과가 최신을 덮는 것 방지)
            queue last / queue all대기열을 마지막 하나로 교체 / 모두 쌓음queue all: 3번 순서대로순서가 중요한 기록

            hx-sync 값은 선택자:전략 형식입니다. 선택자로 여러 요소가 대기열 하나를 공유하게 만들 수 있습니다. 예를 들어 폼 안의 입력칸과 제출 버튼이 모두 hx-sync="closest form:abort"를 쓰면 폼 하나의 대기열로 묶입니다. 선택자 없이 replace처럼 전략만 써도 됩니다.

            랩에서 측정한 더블클릭의 결과

            재시작 버튼에서 hx-disable을 빼고 더블클릭했더니 서버 로그에 POST /vms/api-01/restart → 200 다음 POST /vms/api-01/restart → 409가 찍혔습니다. 기본 대기열 규칙이 두 번째 클릭을 대기시켰다가 첫 요청이 끝나자 보낸 것입니다. 서버의 상태 전이 규칙(실행 중만 재시작) 덕분에 이중 재시작은 막혔지만, 규칙이 없는 동작이었다면 두 번 실행됐을 것입니다. hx-disable="this"를 넣자 요청은 1번만 나갔습니다. 서버 규칙과 클라이언트 중복 방지를 둘 다 두는 것이 정답입니다.

            2.x와 다른 점: hx-disable의 의미가 바뀌었다

            htmx 2의 hx-disable은 "이 영역의 htmx 처리를 끈다"였고, "요청 중 비활성화"는 hx-disabled-elt였습니다. htmx 4에서 hx-disable은 요청 중 지정한 요소에 disabled 속성을 붙이는 속성이 되었고, 처리 끄기는 hx-ignore로 이름이 바뀌었습니다. 4.0.1 소스에서 같은 요소가 여러 요청에 걸려도 참조 횟수를 세어 마지막 요청이 끝날 때 풀어 주는 것을 확인했습니다.

            값 더하기: hx-include와 hx-vals

            값 더하기 관찰기 (htmx 4.0.1 실동작)

            결과는 오른쪽에 표시
            필터 폼 (id="f7")

            속성형식규칙 (htmx 4.0.1 소스)
            hx-include확장 선택자 (#f7, closest form, [name=q] 등)찾은 요소와 그 하위의 name 있는 입력을 추가. 이미 포함된 입력은 중복으로 넣지 않음. 폼 검증(reportValidity) 대상에도 포함

            2.x와 다른 점

            2.x의 hx-vars는 제거되었고, 계산값은 hx-vals="js:..."로 씁니다. 또 hx-vals의 기본 형식이 HCON이 되어 hx-vals="page:2"처럼 짧게 쓸 수 있습니다. JSON도 여전히 받습니다. 그리고 4.x에서 hx-include·hx-vals도 자동 상속되지 않으므로 부모에 둘 때는 :inherited가 필요합니다.

            랩에서는 검색어와 상태를 하나의 <form id="filters">에 넣고 폼 자신에 hx-get을 달았습니다. 폼 자신이 GET 요청의 주체이면 폼 전체가 포함되므로(3편 규칙) 두 값이 자연스럽게 함께 갑니다. 폼 밖의 "현재 조건으로 새로고침" 버튼만 hx-include="#filters"를 씁니다.

            08

            로딩 표시와 확인 창

            hx-indicator

            요청 중에는 "인디케이터" 요소에 htmx-request 클래스가 붙습니다. hx-indicator가 없으면 요청 요소 자신이 인디케이터입니다. htmx 4는 시작할 때 다음 CSS를 문서에 넣어 두므로, 별도 CSS 없이 class="htmx-indicator"만 달면 요청 중에만 보이는 요소가 됩니다(설정 includeIndicatorCSS로 끌 수 있음).

            htmx 4.0.1이 자동으로 넣는 CSS (소스 발췌)
            .htmx-indicator { opacity:0; visibility:hidden }
.htmx-request .htmx-indicator, .htmx-request.htmx-indicator { opacity:1; visibility:visible; transition:opacity 200ms ease-in }

            같은 인디케이터를 여러 요청이 동시에 쓰면 htmx가 횟수를 세어 마지막 요청이 끝날 때 클래스를 뗍니다. 그래서 검색과 무한 스크롤이 같은 "불러오는 중" 표시를 공유해도 깜빡이지 않습니다.

            hx-confirm과 htmx:confirm

            hx-confirm="메시지"는 기본으로 window.confirm()을 띄웁니다. 그 직전에 htmx는 htmx:confirm 이벤트를 발생시키는데, 상세 객체에 issueRequest()와 dropRequest() 두 함수가 들어 있습니다. 이벤트에서 preventDefault()를 부르면 기본 창이 뜨지 않고, htmx는 둘 중 하나가 호출될 때까지 기다립니다. 이 구조 덕분에 <dialog>나 사내 디자인 시스템의 모달로 확인 창을 바꾸는 코드가 열 줄 남짓입니다.

            views/layout.eta (추가된 스크립트)
            const dialog = document.getElementById('confirm-dialog');
document.addEventListener('htmx:confirm', (e) => {
  e.preventDefault();                                   // 기본 window.confirm 막기
  const { ctx, issueRequest, dropRequest } = e.detail;
  document.getElementById('confirm-message').textContent = ctx.confirm;   // hx-confirm의 문구
  dialog.returnValue = '';
  dialog.addEventListener('close', () => {
    dialog.returnValue === 'ok' ? issueRequest() : dropRequest();
  }, { once: true });
  dialog.showModal();
});

            메시지를 textContent로 넣은 점에 주목하세요. hx-confirm 문구에 VM 이름처럼 데이터가 섞이므로 innerHTML을 쓰면 XSS 통로가 됩니다. 또 hx-confirm 값이 js:로 시작하면 htmx는 창 대신 그 JS 식의 결과로 진행 여부를 정합니다. 확인은 인디케이터·hx-disable보다 먼저 처리되므로(소스 순서), 사용자가 고민하는 동안 버튼이 비활성화되지 않습니다.

            2. 검색은 input changed delay: + hx-sync="this:replace", 스크롤 반응은 throttle, 지연 로딩은 load/revealed, 폴링은 every 간격 [조건].
              3. 
    
            3. htmx 4에서 폴링은 요소가 문서에서 사라질 때 멈춘다(286 없음). 서버가 폴링 속성 없는 HTML로 교체하는 것이 하이퍼미디어식 종료다.
              4. 
    
            4. HX-Trigger 이벤트는 요청 요소에서 발생하고, 그 요소가 사라졌으면 document에서 발생한다. 요청 요소가 교체되는 패턴에서는 from:document가 안전하다.
              5. 
    
            5. 기본 대기열은 queue first라 더블클릭이 두 번 실행될 수 있다. hx-disable과 서버 상태 규칙을 함께 둔다.
              6. 
  
            
  
            
    
            다음 편 · 5편 스왑의 모든 것
            
    
            hx-swap 수식어(swap·settle 지연, scroll·show, focus-scroll, transition, swapEmpty, strip), OOB 스왑과 <hx-partial>의 차이, 내장 모핑(innerMorph/outerMorph)으로 입력 상태 보존, View Transitions API. 랩에서는 모니터링 설정 폼을 모핑으로 바꾸고, 행 교체에 전환 효과를 붙입니다.
