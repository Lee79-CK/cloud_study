AIOps 구현 가이드 8편 · 검증과 회복탄력성

목차

    신입·초보 클라우드 엔지니어를 위한 기술 강의 · 2026년판 · 8편(최종)

    검증과 회복탄력성우리 시스템이 정말 작동하는지 증명하기

    일곱 편에 걸쳐 만든 시스템에는 한 가지 공통된 약점이 있습니다. 고장나도 조용하다는 것입니다. 탐지기가 멈춰도, 알림이 안 가도, 에이전트가 헛돌아도 화면은 평화롭습니다. 마지막 편은 그것을 깨뜨리는 방법입니다.

    실패 모드→파이프라인 회복탄력성→장애 주입→ 합성 사건→게임데이→자동화 승격
    예상 학습 80분시나리오 생성기 포함시리즈 종합 정리1~7편을 전제로 함
    이 편의 출발 문장

    알림이 오지 않는 것은 두 가지를 뜻합니다. 아무 일도 없거나, 알림 시스템이 죽었거나. 이 둘을 구분할 수 없다면 그 시스템은 관측 시스템이 아닙니다.

    CHAPTER 01

    조용한 실패의 목록

    AIOps 스택은 계층이 많고, 각 계층이 서로 다른 방식으로 조용히 고장납니다.

    계층조용한 실패겉으로 보이는 모습
    수집컬렉터가 죽거나 큐가 막힘"알림이 줄었다" — 개선으로 오해
    라벨·규약새 서비스에 테넌트 라벨 누락사건이 안 묶이고 고아 알림으로 흩어짐
    저장보존 정책 변경으로 조회 구간이 사라짐장애 조사 시점에야 발견
    탐지기준선 갱신 실패로 낡은 기준 사용계속 동작하는 것처럼 보임(6편)
    상관토폴로지 그래프가 갱신되지 않음사건이 잘게 쪼개짐
    에이전트도구 하나가 항상 타임아웃조사 품질만 조금 낮아진 것처럼 보임
    조치승인 알림이 채널 변경으로 도달 안 함승인 대기 상태로 방치
    알림 전달웹훅 토큰 만료, 채널 삭제완전한 무음 — 가장 위험

    공통 특징

    위 실패들은 모두 에러를 내지 않습니다. 프로세스는 살아 있고, 대시보드는 초록색이고, 로그에는 아무 문제가 없습니다. 그래서 일반적인 헬스체크로는 잡히지 않습니다. 필요한 것은 "정상이면 반드시 일어나야 하는 일"을 확인하는 장치입니다.

    두 가지 검증 방식

    ① 능동 검증 — 일부러 문제를 만들고 시스템이 반응하는지 본다(장애 주입, 합성 사건).
    ② 지속 검증 — 정상 상태에서 반드시 흐르는 신호가 끊기면 알린다(하트비트, 데드맨 스위치).
    둘 다 필요합니다. 지속 검증은 상시 안전망이고, 능동 검증은 주기적 건강검진입니다.

    CHAPTER 02

    데드맨 스위치와 독립 경로

    가장 먼저 만들어야 할 장치입니다. 다른 모든 검증보다 우선합니다.

    데드맨 스위치

    원리는 단순합니다. 항상 발생하는 알림을 하나 만들고, 그것이 도착하지 않으면 경보합니다. 알림 경로 전체가 살아 있는지를 알림 자체로 확인하는 방식입니다.

    항상 켜져 있는 알림 + 외부 감시
    # 1) 항상 발화하는 규칙
groups:
- name: watchdog
  rules:
  - alert: Watchdog
    expr: vector(1)          # 조건 없이 항상 참
    labels: { severity: none, tenant: acme }
    annotations:
      summary: "알림 파이프라인 생존 신호"

# 2) 이 알림을 외부 서비스(우리 인프라 밖)로 보낸다
#    핵심: 감시자는 감시 대상과 같은 인프라에 있으면 안 된다
receivers:
- name: deadmansswitch
  webhook_configs:
    - url: https://external-heartbeat.example/ping/acme
      send_resolved: false

# 3) 외부 서비스가 N분간 핑을 못 받으면 사람에게 연락(SMS·전화)

    계층별 하트비트

    알림 경로뿐 아니라 각 계층에 "정상이면 반드시 일어나는 일"을 정의하고 감시합니다.

    계층생존 신호경보 조건
    수집테넌트별 수신 데이터 포인트 수N분간 0 또는 평소의 20% 미만
    파이프라인컬렉터 전송 성공 카운터실패율 증가, 큐 적체
    탐지기준선 마지막 갱신 시각주기의 2배를 초과
    사건 생성일간 사건 수24시간 연속 0(정말 평화로울 수도 있으나 확인 필요)
    에이전트조사 성공률, 도구별 성공률특정 도구 실패율 급증
    조치승인 요청 대비 응답 수응답 없는 요청 누적
    독립 경로 원칙

    이 알림들만큼은 감시 대상 시스템을 거치지 않아야 합니다. 자체 관측 스택으로 자체 관측 스택을 감시하면, 그것이 죽는 순간 알림도 함께 죽습니다. 외부 상태 감시 서비스, 다른 클라우드 계정, 또는 최소한 별도 클러스터에 두세요. 5편의 "AI 사고 시 알림 경로 분리"와 같은 원칙입니다.

    합성 모니터링

    실제 사용자 경로를 모방한 요청을 주기적으로 보내는 방식입니다. 관측 대상이 조용할 때도 경로 전체가 살아 있음을 능동적으로 확인합니다. MSP 환경에서는 특히 유용한데, 고객사 트래픽이 적은 시간대에 장애가 발생하면 트래픽 기반 지표로는 아무것도 보이지 않기 때문입니다.

    CHAPTER 03

    카오스 엔지니어링 기초

    무작정 서버를 끄는 것이 아닙니다. 가설을 세우고, 범위를 정하고, 중단 기준을 두는 실험입니다.

    실험의 네 요소

    1. 정상 상태 가설 — "결제 성공률은 99.9% 이상을 유지한다"처럼 측정 가능한 정상 정의
    2. 주입할 장애 — 파드 종료, 네트워크 지연, CPU 포화, 의존 서비스 오류 등 현실적으로 일어날 수 있는 것
    3. 블라스트 레이디어스 — 영향 범위를 미리 제한(한 네임스페이스, 트래픽의 5%, 특정 시간대)
    4. 중단 기준 — "정상 상태 가설이 깨지면 즉시 중단"을 실험 시작 전에 합의하고 자동화

    도구

    쿠버네티스 환경에서는 CNCF 생태계의 카오스 플랫폼들이 널리 쓰입니다. 대표적으로 Chaos Mesh와 LitmusChaos가 있고, 둘 다 실험을 CRD로 선언하고 결과를 메트릭으로 내보내는 구조입니다. 클라우드 제공자들도 자체 장애 주입 서비스를 제공합니다. 선택 기준은 대개 다음과 같습니다.

    • 세밀한 네트워크 장애(지연·패킷 손실·파티션)가 중요하면 네트워크 CRD가 풍부한 쪽
    • 실험 카탈로그와 워크플로 UI로 팀이 함께 쓰는 것이 중요하면 그쪽에 맞는 플랫폼
    • 관리형 인프라(RDS, 로드밸런서 등)에 주입하려면 클라우드 제공자 서비스
    시작은 스테이징에서, 그러나 목표는 운영

    스테이징에서만 하는 카오스 실험은 절반의 가치입니다. 스테이징에는 실제 트래픽도, 실제 데이터 양도, 실제 온콜도 없기 때문입니다. 다만 운영에서 시작하지는 마세요. 스테이징에서 절차와 중단 기준을 다듬고, 블라스트 레이디어스를 아주 작게 잡아 업무 시간에 사람이 지켜보는 상태로 운영에 진입하는 것이 순서입니다.

    CHAPTER 04

    AIOps 스택을 대상으로 한 실험

    보통의 카오스 실험이 애플리케이션을 대상으로 한다면, 여기서는 관측·자동화 시스템 자체를 공격합니다.

    주입확인할 것흔히 발견되는 문제
    컬렉터 파드 종료버퍼링·재전송, 데이터 공백 크기, 하트비트 발화버퍼 미설정으로 데이터 영구 손실
    저장소 응답 지연 주입질의 타임아웃 처리, 에이전트 도구의 폴백에이전트가 타임아웃 없이 무한 대기
    알림 웹훅 차단재시도, 대체 경로, 데드맨 스위치재시도 없이 조용히 유실
    테넌트 라벨 제거unknown 격리 동작, 알림 발화(4편)다른 테넌트에 섞여 들어감
    LLM 엔드포인트 중단조사 실패가 사건 처리를 막지 않는지(3편)조사 실패로 사건 생성 자체가 중단
    MCP 도구 하나만 실패부분 실패 처리, 대체 조사 경로루프가 같은 도구를 계속 재시도하며 예산 소진
    시간 왜곡(클럭 스큐)상관분석 시간창, 사건 병합시간창 밖으로 밀려 사건이 쪼개짐
    대량 알림 폭주 주입큐 완충, 중복제거, 회로 차단기수신부 과부하로 전체 정지
    실험 정의 예시 — 선언형 카오스 + 정상 상태 프로브
    # 목적: 컬렉터가 5분간 죽어도 데이터 공백이 2분을 넘지 않아야 한다(버퍼 검증)
kind: PodChaos
metadata: { name: collector-outage, namespace: chaos }
spec:
  action: pod-kill
  mode: fixed
  value: "1"                          # 블라스트 레이디어스: 한 개만
  selector:
    namespaces: [observability]
    labelSelectors: { app: otel-gateway }
  duration: "5m"

# 정상 상태 프로브: 실험 중 지속 확인, 깨지면 자동 중단
probes:
  - name: no-long-gap
    type: promQL
    query: 'time() - max(timestamp(up{job="critical-service"})) < 120'
    interval: 30s
  - name: watchdog-alive
    type: http
    url: https://external-heartbeat.example/status/acme
    expect: "ok"
    실험 중에는 자동조치를 끄세요

    주입한 장애에 에이전트가 반응해 실제 조치를 실행하면 실험이 사고가 됩니다. 실험 시작 시 해당 범위의 자동화를 5편의 킬 스위치로 중단하고, 에이전트의 제안까지만 관찰하세요. 자동조치 자체를 검증하려면 8장의 별도 절차를 씁니다.

    CHAPTER 05

    합성 사건 — 파이프라인 전 구간 검증

    장애 주입이 인프라를 흔든다면, 합성 사건은 사건 처리 경로를 흔듭니다. 훨씬 안전하고 자주 돌릴 수 있습니다.

    두 가지 방법

    • 합성 알림 주입 — 정해진 형태의 알림을 웹훅으로 밀어 넣고, 정규화→중복제거→상관→사건 생성→조사→통지까지 흐르는지 확인합니다. 운영 환경에서도 synthetic=true 라벨을 붙이면 안전하게 돌릴 수 있습니다.
    • 과거 사건 리플레이 — 2편의 이벤트 테이블에서 실제 장애의 알림 시퀀스를 그대로 재생합니다. "지금 코드로 이 장애를 다시 겪는다면 어떻게 처리될까"를 답해 줍니다. 회귀 검증에 가장 강력합니다.
    tests/synthetic_incident.py — 전 구간 종단 검증
    @pytest.mark.e2e
async def test_end_to_end_incident_flow():
    # 1) 상류 3개 서비스에 전파되는 형태의 알림 묶음을 주입
    burst = synth.deploy_regression_burst(tenant="canary", service="payment-api",
                                          fanout=["checkout", "order", "gateway"],
                                          labels={"synthetic": "true"})
    await webhook.post_all(burst)

    # 2) 사건이 '하나로' 생성되는지 — 상관분석 검증
    inc = await wait_for_incident(tenant="canary", timeout=60)
    assert inc is not None, "사건이 생성되지 않음 — 파이프라인 단절"
    assert len(inc.events) == len(burst), "일부 알림이 사건에 묶이지 않음"
    assert inc.root_service == "payment-api", "원인 후보 지목 실패"

    # 3) 조사 결과에 근거가 붙는지 — 에이전트·도구 검증
    h = await wait_for_hypothesis(inc.id, timeout=120)
    assert len(h.evidence) >= 2, "근거 없는 결론 — 도구 실패 의심"

    # 4) 통지가 실제로 도달했는지 — 알림 경로 검증(가장 자주 깨지는 곳)
    assert await notification_delivered(inc.id, channel="#canary-ops")

    # 5) 소요 시간 회귀 확인
    assert inc.time_to_hypothesis < 120, f"조사 지연 회귀: {inc.time_to_hypothesis}s"

    주기와 범위

    검증주기환경
    합성 알림 1건(경로 생존 확인)15분~1시간마다운영(카나리 테넌트)
    종단 사건 흐름배포마다 + 일 1회스테이징
    과거 사건 리플레이 세트주 1회 + 주요 변경 시스테이징
    인프라 장애 주입월 1~2회스테이징 → 제한된 운영
    게임데이분기 1회운영(계획된 시간)
    카나리 테넌트를 검증 전용으로

    4편에서 만든 카나리 테넌트를 합성 사건 전용 공간으로 쓰면, 운영 파이프라인을 실제로 통과시키면서도 고객사에는 아무 영향이 없습니다. 합성 사건은 통계에서 제외되도록 라벨로 구분하는 것만 잊지 마세요. (MTTR 지표가 합성 사건으로 오염되는 실수가 흔합니다.)

    CHAPTER 06

    게임데이 — 사람까지 포함한 검증

    시스템은 통과해도 사람이 못 하는 경우가 많습니다. 게임데이는 그 간극을 찾는 자리입니다.

    진행 방식

    1. 준비(1~2주 전) — 시나리오 설계, 참가자·역할 확정, 중단 기준 합의, 고객사 영향 가능성 검토와 필요 시 사전 고지
    2. 브리핑(당일 시작) — 목표 공유. 단, 무엇을 주입할지는 대응자에게 알리지 않습니다(그것이 검증의 핵심)
    3. 실행 — 진행자가 장애를 주입하고, 관찰자가 타임라인을 기록합니다. 대응자는 평소대로 대응합니다
    4. 중단 또는 복구 — 중단 기준에 걸리면 즉시 멈추고 복구합니다
    5. 회고(당일 또는 익일) — 무엇이 늦었고, 어떤 정보가 없었고, 어떤 문서가 틀렸는지 기록합니다
    6. 후속 — 발견 사항을 티켓으로 만들고 다음 게임데이에서 재확인합니다

    역할

    • 진행자 — 시나리오를 주입하고 실험을 통제. 중단 권한을 가집니다
    • 대응자 — 실제 온콜 담당자. 가능하면 그 고객사를 잘 모르는 사람을 넣으세요(4편의 공통 온콜 검증)
    • 관찰자 — 시각과 행동을 기록. 대응자를 돕지 않습니다
    • 안전 담당 — 고객 영향 여부만 감시하며, 위험 시 즉시 중단을 요구합니다

    CHAPTER 10

    시리즈 정리 — 여덟 편의 지도

    전체를 한 장으로 요약합니다. 다시 볼 때 어디를 펴야 할지의 안내이기도 합니다.

    편주제핵심 메시지
    1편7계층 아키텍처AIOps는 제품이 아니라 아키텍처. 데이터 계층 없이 AI부터 사면 실패한다
    2편사건 파이프라인·조사 에이전트 구현사건을 1급 엔티티로. 수신과 처리를 분리하고, 도구는 읽기 전용으로
    3편멀티 에이전트·로컬 서빙·평가분업은 컨텍스트 격리나 병렬성이 필요할 때만. 도구 설계가 모델보다 중요하다
    4편MSP 멀티테넌트 운영격리는 규칙이 아니라 기본값. 코드에 고객사 이름이 없어야 확장된다
    5편보안·거버넌스에이전트는 권한을 가진 사용자. 프롬프트는 보안 통제가 아니다
    6편예측·이상탐지어려움은 모델이 아니라 기저율에 있다. 대상을 좁히고 집계해서 사건으로
    7편비용·데이터 엔지니어링관측 데이터는 자산이 아니라 재고. 조회될 때만 가치가 생긴다
    8편검증·회복탄력성고장나도 조용한 시스템. 정상이면 반드시 일어나는 일을 감시하라

    1년 로드맵으로 재배치

    1. 1~3개월 — 수집 표준화와 알림 노이즈 정리(1·7편). 데드맨 스위치 구축(8편). SLO 알림 전환(1·6편)
    2. 4~6개월 — 사건 파이프라인과 상관분석 구현(2편). 컨텍스트 계층 채우기. 읽기 전용 조사 에이전트 투입
    3. 7~9개월 — 보안 기본선 적용(5편). 멀티테넌트 격리와 온보딩 자동화(4편). 합성 사건 검증 도입(8편)
    4. 10~12개월 — 가역 조치부터 자동화 승격(2·8편). 라우팅과 비용 최적화(3·7편). 이상탐지 고도화(6편). 첫 게임데이

    마지막으로

    여덟 편을 관통하는 원칙을 하나만 남긴다면 이것입니다. 확률적인 부분은 작게 두고, 그 주변을 결정적으로 감싼다.

    수집 규약, 권한 경계, 예산 상한, 승인 게이트, 감사 기록, 되돌리는 방법, 그리고 멈추는 스위치. 이것들이 단단하면 그 안에서 어떤 모델을 쓰든, 어떤 프레임워크로 바꾸든 안전합니다. 반대로 이것들이 없으면 아무리 좋은 모델도 통제되지 않는 위험이 됩니다.

    그리고 AIOps의 목표는 처음부터 끝까지 같습니다. 사람을 대체하는 것이 아니라, 사람이 판단을 시작하는 지점을 앞당기는 것입니다. 새벽 3시에 42건의 알림을 읽는 대신 근거가 붙은 사건 하나를 읽게 만드는 것. 그것으로 충분히 큰 변화입니다.
