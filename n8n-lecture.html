워크플로우 자동화란 무엇인가

도구 이름을 외우기 전에, 이 도구가 대신해 주는 노동이 정확히 어떤 종류인지부터 봅니다.

신입으로 들어가서 처음 맡는 일은 대체로 이런 모양입니다. 고객사에서 폼을 제출하면 → 담당자가 그걸 보고 → 스프레드시트에 옮겨 적고 → 조건에 따라 슬랙에 알리고 → 확인 메일을 보내고 → 하루 끝에 요약을 보고합니다. 기술적으로 어려운 건 하나도 없습니다. 그냥 사람이 계속 붙어 있어야 한다는 게 문제입니다.

이런 일은 코드로 짤 수 있습니다. 실제로 많은 팀이 짭니다. 문제는 그다음입니다. 인증 토큰이 만료되면? API가 한 번 500을 뱉으면? 3번째 단계에서 실패했을 때 1~2단계를 다시 돌리면 중복이 생기는데, 그건 누가 막나요? 스크립트 10개가 서버 어딘가의 크론탭에 흩어져 있고 짠 사람이 퇴사하면?

워크플로우 자동화 툴은 이 "시스템과 시스템 사이를 잇는 접착제 코드"를 눈에 보이는 형태로 관리하기 위해 나왔습니다. 세 가지를 대신해 줍니다.

연결을 대신한다

Slack, Notion, Salesforce, Postgres… 각각의 인증 방식과 API 규격을 미리 구현해 둔 부품(노드)으로 제공합니다. OAuth 흐름을 직접 짤 일이 없습니다.

흐름을 눈에 보이게 한다

어떤 순서로 무엇이 실행되는지가 캔버스 위 그림으로 남습니다. 인수인계 문서가 곧 실행되는 코드 그 자체입니다.

실행 이력을 남긴다

언제 몇 번 돌았고, 어디서 실패했고, 그때 데이터가 무엇이었는지 전부 저장됩니다. 재실행 버튼 하나로 그 지점부터 다시 돌릴 수 있습니다.

이 범주의 도구는 흔히 iPaaS(Integration Platform as a Service)라고 부릅니다. Zapier, Make, Power Automate, Workato가 여기 속합니다. n8n도 같은 자리에 서 있지만, 이 강의 내내 반복해서 나올 결정적인 차이가 하나 있습니다. n8n은 당신의 서버에 직접 설치해서 돌릴 수 있습니다.

먼저 짚고 갈 구분. 자동화 도구는 크게 두 갈래입니다. 하나는 앱 통합형(n8n·Zapier·Make): 이벤트가 오면 여러 SaaS를 오가며 처리합니다. 다른 하나는 데이터 오케스트레이션형(Airflow·Dagster·Prefect): 매일 밤 테라바이트급 배치를 순서대로 돌립니다. 둘은 겉모습만 비슷하고 쓰임이 완전히 다릅니다. 08장에서 정확히 갈라 보겠습니다.
01

n8n의 정체

이름 읽는 법부터 라이선스의 함정까지. 면접에서 물어봐도 답할 수 있을 만큼만.

n8n은 "엔에이트엔"으로 읽습니다. nodemation(node + automation)에서 n과 n 사이에 여덟 글자가 있어서 붙은 이름입니다. i18n(internationalization)이나 k8s(kubernetes)와 똑같은 축약 방식입니다.

2019년 독일 베를린에서 얀 오버하우저(Jan Oberhauser)가 시작했고, 지금은 노드 기반 캔버스 + 코드 삽입 + 자체 호스팅이라는 세 축으로 자리를 잡았습니다. n8n 스스로는 이걸 이렇게 표현합니다. "코드의 유연함을 노코드의 속도로."

노드 기반 캔버스

드래그로 노드를 놓고 선으로 잇습니다. 마우스만으로 웹훅 수신 → 조건 분기 → 슬랙 발송까지 만듭니다.

막히면 코드로 탈출

Code 노드에 JavaScript나 Python을 그대로 씁니다. 노코드 툴의 흔한 한계인 "이건 안 되네"가 거의 없습니다.

내 서버에서 돌린다

Docker 한 줄로 사내망에 띄웁니다. 고객 개인정보나 사내 DB가 외부 SaaS를 거치지 않습니다.

AI가 1급 시민

LangChain 기반 AI Agent 노드, 벡터 스토어, MCP 연동이 기본 탑재입니다. 별도 애드온이 아닙니다.

라이선스: "오픈소스"라고 부르면 안 되는 이유

이 부분은 실무에서 실제로 문제가 되니 정확히 알아 두세요. n8n은 Sustainable Use License라는 자체 라이선스를 씁니다. 회사에서는 이를 fair-code라고 부르는데, 요점은 이렇습니다.

항목내용
소스 공개GitHub에 전부 공개되어 있습니다. 읽고, 고치고, 파생물을 만들 수 있습니다.
자체 호스팅무제한 실행, 무료. 서버비만 내면 됩니다.
사내 업무 사용자사 CRM ↔ 내부 DB 동기화 같은 내부 목적은 전면 허용됩니다.
컨설팅·구축 대행고객사 n8n 워크플로우를 만들어 주고 돈을 받는 건 허용됩니다.
화이트라벨 재판매n8n을 자기 브랜드로 감싸 파는 건 금지입니다.
호스팅 서비스 판매n8n을 띄워 두고 접근권을 파는 사업은 별도 상용 라이선스가 필요합니다.
OSI 공인 오픈소스사용 목적에 제한이 있으므로 OSI 정의상 오픈소스가 아닙니다. n8n도 스스로 그렇게 부르지 않습니다.
에이전시·SI에서 자주 걸리는 지점. 기술 설정은 똑같은데 법적으로는 다릅니다. "고객사 서버에 n8n을 깔아 주고 워크플로우를 만들어 준다"는 괜찮습니다. "우리 서버에 n8n을 띄워 두고 고객에게 월 구독료를 받는다"는 안 됩니다. 제안서를 쓰기 전에 확인하세요.

n8n 2.0 — 2025년 12월의 방향 전환

2023년 7월 1.0 이후 2년 넘게 미뤄 뒀던 깨지는 변경(breaking change)을 한 번에 반영한 버전이 2.0입니다. 화려한 신기능 릴리스가 아니라 보안·안정성 강화 릴리스였다는 점이 핵심입니다. 신입이 지금 처음 배운다면 처음부터 2.x를 기준으로 익히면 됩니다.

  • 태스크 러너 기본 활성화 — Code 노드가 격리된 환경에서 실행됩니다. 기본적으로 서버 환경변수에 접근할 수 없습니다.
  • 위험한 노드 기본 비활성 — 임의 명령을 실행하는 Execute Command, Local File Trigger는 꺼진 채로 시작합니다.
  • Save와 Publish 분리 — 저장해도 운영에 바로 반영되지 않습니다. Publish를 눌러야 라이브가 됩니다. 실수로 운영을 깨뜨릴 일이 줄었습니다.
  • 릴리스 채널 이름 변경 — latest/next → stable/beta.
  • --tunnel 옵션 제거 — 로컬 웹훅 테스트는 ngrok이나 Cloudflare Tunnel을 쓰세요.

n8n은 이후 연 1~2회 메이저 릴리스 주기를 예고했습니다. 3.0은 2026년 10월 예정이며, 자체 호스팅은 Docker 기반 배포가 요구사항이 됩니다. 운영 중이라면 업그레이드 전 마이그레이션 리포트를 꼭 돌리세요.

02

핵심 개념 7가지

이 일곱 개만 정확히 알면 n8n 문서와 커뮤니티 글의 90%가 읽힙니다.

1. 워크플로우 (Workflow)

노드들과 그 연결선을 묶은 하나의 단위. 화면에 보이는 캔버스 한 장이 워크플로우 하나입니다. 내부적으로는 그냥 JSON 파일입니다. 그래서 복사·붙여넣기로 통째로 공유할 수 있고, Git에 커밋할 수도 있습니다.

워크플로우는 Active / Inactive 상태를 가집니다. Active가 되어야 웹훅 URL이 살아나고 스케줄이 돌기 시작합니다. 에디터에서 수동 실행(Test workflow)은 Inactive 상태에서도 됩니다.

실무 팁. 캔버스에서 노드를 선택하고 Ctrl+C 하면 JSON이 클립보드에 복사됩니다. 커뮤니티에서 받은 JSON을 캔버스에 Ctrl+V 하면 그대로 붙습니다. 템플릿 공유가 이렇게 쉬워서 n8n 생태계가 빨리 자랐습니다.
2. 노드 (Node) — 다섯 가지 종류

작업 하나를 담당하는 상자. n8n에는 400개 이상의 기본 노드가 있습니다. 외워야 할 건 개별 노드 이름이 아니라 다섯 가지 분류입니다. 이 강의의 색깔은 처음부터 끝까지 이 분류를 따릅니다.

트리거 앱 연동 흐름 제어 데이터·코드 AI
모든 워크플로우는 트리거로 시작합니다. 예외 없습니다. 트리거가 없으면 워크플로우는 스스로 돌 수 없고, 캔버스에도 "트리거를 추가하세요" 안내가 뜹니다. 트리거 노드는 왼쪽 모서리가 둥근 모양이라 시각적으로도 구분됩니다.
3. 연결 (Connection)과 실행 순서

노드의 오른쪽 점(출력)에서 다음 노드의 왼쪽 점(입력)으로 선을 끕니다. n8n은 이 선을 따라 왼쪽에서 오른쪽으로 순차 실행합니다.

기억할 규칙 세 가지:

  • 한 노드의 출력에서 여러 갈래로 선을 뻗을 수 있습니다. 이 경우 각 갈래가 순서대로 실행됩니다(동시가 아닙니다).
  • IF 노드는 출력이 true / false 두 개, Switch 노드는 여러 개입니다.
  • 여러 갈래를 다시 합칠 땐 Merge 노드를 씁니다. 그냥 선을 한 노드에 두 개 꽂으면 그 노드가 두 번 실행됩니다.
초보자가 가장 많이 하는 실수. 분기한 두 갈래를 Merge 없이 한 노드에 그냥 꽂아 놓고 "왜 슬랙 메시지가 두 번 오지?" 하고 당황합니다. 합류에는 Merge를 쓰세요.
4. 아이템 (Item) — 가장 중요한 개념

여기서 막히는 사람이 제일 많습니다. 시간을 들여 읽으세요.

n8n에서 노드 사이를 오가는 데이터는 항상 배열입니다. 그 배열의 원소 하나를 아이템이라고 부릅니다. 형태는 고정입니다.

노드 사이를 흐르는 데이터의 진짜 모양
[
  { "json": { "name": "김민준", "amount": 128000 } },
  { "json": { "name": "이서연", "amount": 42000 } },
  { "json": { "name": "박지훈", "amount": 250000 } }
]

아이템 하나는 json 키를 반드시 갖고, 파일을 다룰 땐 binary 키가 추가됩니다. 그리고 이 배열의 길이가 곧 다음 노드의 실행 횟수입니다.

위 데이터가 Slack 노드로 들어가면 슬랙 메시지가 3개 갑니다. 한 번이 아닙니다. 이걸 "노드는 아이템마다 반복 실행된다"고 표현합니다. 루프를 직접 짤 필요가 없다는 뜻이기도 하고, 모르면 스팸을 보낸다는 뜻이기도 합니다.

이 규칙 하나로 설명되는 것들. "왜 메일이 50통 갔지?" → 아이템이 50개였습니다. "왜 아무것도 안 돌았지?" → 아이템이 0개였습니다(빈 배열이면 다음 노드는 스킵됩니다). "여러 건을 한 번에 묶어 보내고 싶다" → Aggregate 노드로 하나로 합치세요.
5. 표현식 (Expression)

앞 노드의 데이터를 다음 노드 설정칸에 꽂아 넣는 문법입니다. 이중 중괄호를 씁니다.

표현식 기본형
// 현재 아이템의 필드 참조
{{ $json.name }}
{{ $json.order.amount }}

// 특정 노드의 출력 참조 (노드 이름 그대로)
{{ $('Webhook').item.json.email }}

// 자바스크립트를 그대로 쓸 수 있습니다
{{ $json.amount >= 100000 ? 'VIP' : '일반' }}
{{ $json.name.trim().toUpperCase() }}
{{ $json.amount.toLocaleString('ko-KR') }}원

// 날짜는 Luxon 라이브러리
{{ $now.toFormat('yyyy-MM-dd') }}
{{ $now.plus({ days: 7 }).toISO() }}

자주 쓰는 내장 변수: $json(현재 아이템), $node/$()(다른 노드), $now(현재 시각), $itemIndex(반복 인덱스), $execution.id(실행 ID), $vars(전역 변수, 유료 플랜).

04장에 직접 쳐 볼 수 있는 놀이터를 준비했습니다.

6. 실행 (Execution)

워크플로우가 처음부터 끝까지 한 번 도는 것이 실행 1회입니다. 노드가 3개든 40개든, 아이템이 1개든 500개든 실행은 1회입니다.

이게 n8n 과금의 핵심이자 Zapier·Make와 갈라지는 지점입니다. Zapier는 액션 단계마다 task를, Make는 모듈 실행마다 operation을 셉니다. 같은 일을 해도 청구서 자릿수가 달라집니다. 09장에서 직접 계산해 보겠습니다.

실행에는 두 종류가 있습니다:

  • Manual — 에디터에서 "Test workflow"를 눌러 도는 것. 각 노드 출력이 화면에 다 보입니다. 개발용.
  • Production — 활성화된 트리거로 자동으로 도는 것. Executions 탭에 기록이 쌓입니다.

실패한 실행은 목록에서 골라 실패 지점부터 재시도(Retry)할 수 있습니다. 이게 크론 + 셸 스크립트 조합 대비 가장 큰 실무적 이점입니다.

7. 자격증명 (Credential)

API 키, OAuth 토큰, DB 비밀번호를 워크플로우와 분리해서 따로 저장하는 공간입니다. 한 번 등록하면 여러 워크플로우가 같은 자격증명을 참조합니다.

  • DB에 저장될 때 N8N_ENCRYPTION_KEY로 암호화됩니다. 이 키를 잃어버리면 모든 자격증명이 복호화 불가가 되니 반드시 백업하세요.
  • 워크플로우 JSON을 내보내도 자격증명 값은 포함되지 않습니다. 참조 ID만 들어갑니다. 그래서 안심하고 공유할 수 있습니다.
  • OAuth2 서비스(Google, Slack 등)는 n8n이 인증 화면까지 띄워 줍니다. 리다이렉트 URL만 각 서비스 콘솔에 등록하면 됩니다.

팀 단위로 쓸 땐 자격증명 공유 범위를 프로젝트별로 나눌 수 있고, 더 세밀한 역할 기반 접근 제어(RBAC)는 상위 플랜 기능입니다.

여기서 배울 네 가지

아이템 배열은 갈라진다

IF 노드에 3개가 들어가면 true 출력과 false 출력으로 나뉘어 나갑니다. 복제되는 게 아니라 분배됩니다. 합은 항상 3입니다.

노드는 아이템 수만큼 돈다

Slack 노드에 2개가 들어가면 API 호출이 2번 나갑니다. 외부 API 호출량은 실행 횟수가 아니라 아이템 수로 계산하세요.

Merge는 다시 합친다

전체는 실행 1회

방금 6개 노드가 총 12번 동작했지만 n8n 과금 기준으로는 execution 1회입니다. 이게 09장 계산기의 전제입니다.

반복 처리: 루프를 직접 짜야 할 때

대부분은 자동 반복으로 충분하지만, 아래 상황에서는 명시적 루프가 필요합니다.

  • API 레이트 리밋 회피 — 1000건을 한 번에 쏘면 429가 납니다. Loop Over Items(구 Split In Batches)로 50건씩 끊고 사이에 Wait를 넣습니다.
  • 페이지네이션 — 다음 페이지 커서가 있는 동안 계속 도는 구조. HTTP Request 노드에 페이지네이션 옵션이 내장돼 있어 간단한 건 노드 설정만으로 됩니다.
  • 대용량 메모리 절약 — 10만 건을 한 배열로 들고 있으면 컨테이너가 죽습니다. 배치로 잘라 처리하세요.
Schedule→ HTTP Request→ Loop Over Items · 배치 50→ Postgres Insert→ Wait 2s↺ 루프로 되돌아감

서브워크플로우: 함수처럼 쓰기

노드가 40개를 넘어가면 캔버스가 지옥이 됩니다. 공통 로직은 별도 워크플로우로 빼고 Execute Sub-workflow 노드로 호출하세요. 인자를 넘기고 결과를 돌려받는 게 함수 호출과 같습니다.

"슬랙 알림 포맷팅", "고객 등급 판정", "에러를 지라 티켓으로" 같은 조각을 서브워크플로우로 만들어 두면 팀 전체가 재사용합니다. AI 에이전트가 도구로 호출할 대상으로도 쓰입니다(07장).

표현식 다루기

직접 쳐 보세요. 오른쪽 데이터를 대상으로 실시간 평가됩니다.

아래 샘플 데이터가 $json에 들어 있다고 가정합니다. 중괄호 안에는 자바스크립트 표현식이면 무엇이든 들어갑니다.

$json — 현재 아이템
{
  "name": "김민준",
  "email": "minjun@example.com",
  "tier": "gold",
  "order": {
    "id": "A-1024",
    "amount": 128000,
    "items": [
      { "sku": "KB-01", "qty": 2, "price": 49000 },
      { "sku": "MS-07", "qty": 1, "price": 30000 }
    ]
  }
}
실무에서 제일 많이 쓰는 다섯 가지 패턴. 값이 없을 때 대비한 {{ $json.nickname || $json.name }}, 옵셔널 체이닝 {{ $json.order?.coupon?.code }}, 배열 합계 {{ $json.order.items.reduce((s,i)=>s+i.price*i.qty,0) }}, 조건 분기 {{ $json.tier==='gold' ? '우선 배송' : '일반 배송' }}, 날짜 포맷 {{ $now.toFormat('yyyy-MM-dd HH:mm') }}.
표현식 vs Code 노드. 표현식은 값 하나를 만드는 데 씁니다. 아이템 배열 전체를 재구성하거나, 여러 줄 로직이 필요하거나, 반복문이 들어가면 Code 노드로 옮기세요. 표현식 안에 삼항 연산자를 세 번 중첩하고 있다면 이미 늦었습니다.

Code 노드로 넘어가는 지점

Code 노드 · Run Once for All Items 모드
// 들어온 모든 아이템을 한 번에 다룹니다
const out = [];

for (const item of $input.all()) {
  const o = item.json.order;
  const total = o.items.reduce((s, i) => s + i.price * i.qty, 0);

  out.push({
    json: {
      orderId: o.id,
      customer: item.json.name,
      total,
      // 배송비 정책을 여기서 계산
      shipping: total >= 50000 ? 0 : 3000,
      grade: total >= 100000 ? 'VIP' : 'STANDARD',
    },
  });
}

// 반드시 [{ json: {...} }] 형태로 반환해야 합니다
return out;

Python도 쓸 수 있습니다(Pyodide 기반이라 일부 패키지만 지원). 다만 2.0부터 Code 노드는 격리된 태스크 러너에서 돌기 때문에 서버 환경변수나 파일시스템에 기본적으로 접근할 수 없습니다. 보안상 올바른 기본값이지만, 1.x에서 마이그레이션할 때 흔히 깨지는 지점이기도 합니다.

운영용 구성 — Postgres를 붙인 docker-compose

기본값인 SQLite는 실행 이력이 쌓이면 느려지고 동시성에 약합니다. 진짜 운영이라면 Postgres를 붙이세요.

docker-compose.yml
services:
  postgres:
    image: postgres:16
    restart: always
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n"]
      interval: 10s
      retries: 5

  n8n:
    image: docker.n8n.io/n8nio/n8n:2.30.5   # 버전 고정 권장
    restart: always
    ports:
      - "5678:5678"
    environment:
      # --- 데이터베이스 ---
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      # --- 보안 ---
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_SECURE_COOKIE: "true"
      # --- 외부 접속 주소 (웹훅 URL 생성에 사용) ---
      N8N_HOST: automation.mycompany.com
      N8N_PROTOCOL: https
      WEBHOOK_URL: "https://automation.mycompany.com/"
      # --- 시간대 ---
      GENERIC_TIMEZONE: Asia/Seoul
      TZ: Asia/Seoul
      # --- 실행 이력 정리 (안 하면 DB가 계속 붑니다) ---
      EXECUTIONS_DATA_PRUNE: "true"
      EXECUTIONS_DATA_MAX_AGE: 336          # 시간 단위 = 14일
      EXECUTIONS_DATA_SAVE_ON_SUCCESS: none  # 성공 건은 저장 안 함
    volumes:
      - n8ndata:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  pgdata:
  n8ndata:
가장 흔한 자체 호스팅 사고 1위. 실행 이력을 정리하지 않아 DB가 수십 GB로 부풀고 에디터가 느려지는 경우입니다. 위 EXECUTIONS_DATA_* 세 줄을 처음부터 넣어 두세요. 성공 이력까지 다 남길 이유는 거의 없습니다.

첫 워크플로우 만들기 — 5단계

단계 1

트리거를 놓는다

캔버스에서 + → "On a schedule" 선택 → 매일 오전 9시로 설정. 트리거가 없으면 시작할 수 없습니다.

단계 2

데이터를 가져온다

HTTP Request 노드 추가 → GET → 공개 API 주소 입력. 예를 들어 환율이나 날씨 API. 인증이 필요 없는 걸로 시작하세요.

단계 3

여기서 한 번 실행해 본다

"Test workflow"를 눌러 응답이 어떤 모양인지 먼저 눈으로 확인합니다. 다음 노드의 표현식은 이 실제 데이터를 보고 씁니다. 상상해서 쓰면 반드시 틀립니다.

단계 4

가공하고 내보낸다

Edit Fields (Set)로 필요한 값만 추리고, Slack 또는 Gmail 노드에 표현식으로 꽂습니다. 왼쪽 데이터 패널에서 필드를 드래그해서 입력칸에 떨구면 표현식이 자동 생성됩니다.

단계 5

저장하고 게시한다

Save로 저장한 뒤 Publish를 눌러야 운영에 반영됩니다(2.0부터 분리됨). 이제 Executions 탭에 매일 기록이 쌓입니다.

06

운영과 트러블슈팅

만드는 건 하루, 안 깨지게 유지하는 건 그다음 1년. 신입이 여기서 실력 차이가 납니다.

에러 처리 — 네 개의 손잡이

기능어디에 있나언제 쓰나
Retry On Fail 노드 설정 → Settings 일시적 네트워크 오류나 429 대응. 시도 횟수와 간격을 지정합니다. 외부 API 호출 노드에는 기본으로 켜 두세요.
On Error 노드 설정 → Settings 실패해도 멈추지 않고 계속하거나, 별도 에러 출력으로 흘려보냅니다. 100건 중 3건 실패를 무시하고 나머지를 처리할 때.
Error Trigger 별도 워크플로우의 트리거 "에러 전담 워크플로우"를 하나 만들어 두고, 실패 정보를 슬랙·지라로 보냅니다. 실행 ID와 에러 메시지가 자동으로 넘어옵니다.
Stop And Error 노드로 추가 비즈니스 규칙 위반 시 일부러 실패시킵니다. "재고가 음수면 진행하지 말고 실패로 기록" 같은 경우.
Error Trigger→ Edit Fields · 에러 요약→ IF · 심각도 판정→ Slack #alerts+ Jira 티켓 생성

이 워크플로우를 하나 만들어 두고, 각 워크플로우 설정의 "Error Workflow"에 지정하면 전사 공통 알림 체계가 됩니다.

멱등성 — 두 번 돌아도 괜찮게

재시도는 축복이자 저주입니다. 5개 노드 중 4번째에서 실패해 재실행하면 1~3번 노드가 다시 돕니다. 3번이 "결제 승인"이었다면 큰일입니다.

  • 외부에 부수효과를 만드는 노드(결제, 메일 발송, 주문 생성)는 가능한 한 뒤쪽에 배치합니다.
  • 처리한 ID를 DB나 시트에 기록하고, 시작 부분에서 "이미 처리했나?"를 확인하는 IF를 둡니다.
  • 외부 API가 idempotency key를 지원하면 $execution.id를 헤더로 넘깁니다.
  • 워크플로우를 읽기 단계 / 판단 단계 / 쓰기 단계로 나눠 두면 재실행 범위를 통제하기 쉽습니다.

폴링 대신 웹훅 — 비용과 지연을 동시에 잡는 한 수

5분마다 "새 메일 왔니?"를 물어보는 스케줄 트리거는 한 달에 약 8,640회 실행됩니다. n8n Cloud Starter의 월 2,500회 한도를 열흘이면 다 씁니다. 대부분은 "새 거 없음"이라는 헛수고입니다.

해당 서비스가 웹훅을 지원한다면 무조건 웹훅으로 바꾸세요. 실행 횟수는 실제 이벤트 수만큼으로 줄고, 반응 지연도 5분에서 1초 이하로 떨어집니다. 이 한 가지 습관이 Cloud 요금제 두 단계 차이를 만듭니다.

규모가 커질 때: 큐 모드

기본 구성은 하나의 프로세스가 에디터·웹훅 수신·실행을 전부 담당합니다. 동시 실행이 늘면 여기가 병목입니다. 큐 모드는 역할을 쪼갭니다.

main

에디터 UI를 서빙하고 트리거를 감시합니다. 실행할 작업을 큐에 넣습니다.

redis

작업 큐 역할. main과 worker 사이의 중개자입니다.

worker × N

큐에서 꺼내 실제로 실행합니다. 부하가 늘면 컨테이너 수만 늘리면 됩니다.

큐 모드 핵심 환경변수
EXECUTIONS_MODE=queue
QUEUE_BULL_REDIS_HOST=redis
QUEUE_BULL_REDIS_PORT=6379

# worker 컨테이너는 이렇게 띄웁니다
docker run ... docker.n8n.io/n8nio/n8n worker

# 트래픽이 몰리는 웹훅은 전용 프로세스로 분리할 수도 있습니다
docker run ... docker.n8n.io/n8nio/n8n webhook

보안 점검 목록

  • 공개 웹훅을 그대로 두지 마세요. n8n 웹훅 URL은 추측하기 어려운 문자열이지만 그건 인증이 아닙니다. Webhook 노드의 Authentication에서 Header Auth나 Basic Auth를 켜고, 가능하면 HMAC 서명을 검증하세요.
  • 인스턴스를 인터넷에 그냥 노출하지 마세요. 리버스 프록시 뒤에 두고 HTTPS를 강제하고, 관리 화면은 VPN이나 IP 제한 뒤로 넣습니다.
  • 2.0의 기본값을 되돌리지 마세요. Execute Command를 다시 켜야 한다면 정말 필요한지 두 번 생각하세요. 워크플로우 편집 권한이 곧 서버 셸 권한이 됩니다.
  • 암호화 키와 DB를 함께 백업합니다. 둘 중 하나만 있으면 복구가 안 됩니다.
  • 커뮤니티 노드는 검증 후 설치. npm 패키지를 그대로 로드하는 구조입니다. 운영 인스턴스에는 신중하게.
  • 로그에 비밀값이 찍히지 않게 하세요. Code 노드에서 자격증명을 그대로 출력하는 습관은 실행 이력에 고스란히 남습니다.

버전 관리와 환경 분리

워크플로우는 JSON이므로 이론상 Git에 넣을 수 있습니다. 다만 Git 연동과 개발/운영 환경 분리는 Business 이상 유료 기능입니다. 커뮤니티 에디션에서 팀으로 쓴다면 현실적인 대안은 이렇습니다.

  • n8n 인스턴스를 dev / prod 두 개로 나눠 띄우고, JSON을 내보내기·가져오기로 승격합니다.
  • REST API를 써서 내보내기·가져오기를 스크립트로 자동화합니다. n8n으로 n8n을 배포하는 워크플로우를 만드는 팀도 많습니다.
  • 환경별로 달라지는 값(URL, 채널명)은 워크플로우에 하드코딩하지 말고 환경변수나 Variables로 뺍니다.
07

AI 에이전트 만들기

n8n이 최근 2년 사이 가장 많이 쓰이게 된 이유. 워크플로우 툴이 에이전트 런타임이 됐습니다.

기존 자동화는 정해진 순서대로 흐릅니다. 조건 분기가 있어도 경로는 미리 다 그려져 있습니다. AI 에이전트는 다릅니다. 무엇을 할지 모델이 결정합니다. "이 문의를 처리해"라고 하면 모델이 스스로 "먼저 주문 DB를 조회하고, 배송사 API를 확인하고, 답변을 작성하자"고 계획을 세웁니다.

n8n의 AI Agent 노드는 LangChain을 기반으로 이 구조를 그대로 캔버스에 올렸습니다. 다른 노드와 달리 아래쪽에 여러 개의 연결점이 달려 있는 게 특징입니다.

Chat Model — 두뇌

OpenAI, Anthropic, Google, Mistral, 또는 Ollama로 로컬 모델. 사내망에서 데이터를 밖으로 안 내보내려면 Ollama + 자체 호스팅 조합이 유일한 선택지입니다.

Memory — 대화 기억

이전 턴을 기억합니다. 간단하게는 인메모리 버퍼, 운영에서는 Redis나 Postgres에 세션별로 저장합니다.

Tools — 손발

모델이 호출할 수 있는 도구. HTTP Request, 계산기, SQL 조회, 벡터 검색, 그리고 다른 n8n 워크플로우까지 도구로 붙일 수 있습니다. 이게 강력합니다.

MCP — 표준 도구 연결

Model Context Protocol 서버를 도구로 붙입니다. 2026년 5월부터는 노드 패널에서 서버를 고르고 로그인만 하면 되는 방식이 추가돼 수동 설정이 필요 없어졌습니다.

패턴 1 — 사내 문서 RAG 챗봇

두 개의 워크플로우로 나눕니다. 하나는 문서를 색인하고, 하나는 질문에 답합니다.

색인 파이프라인 (하루 1회)

Schedule→ Google Drive · 문서 목록→ Extract from File→ Text Splitter→ Embeddings→ Vector Store 저장

응답 파이프라인 (질문이 올 때마다)

Chat Trigger→ AI Agent ·도구· Vector Store 검색 HTTP Request → Slack 답변

패턴 2 — 사람이 승인하는 자동화

완전 자동은 위험한 영역이 있습니다. 환불, 계약, 대외 발송 같은 것들. Human-in-the-loop 노드는 워크플로우를 멈추고 슬랙이나 메일로 승인을 요청한 뒤, 사람이 버튼을 누르면 이어서 실행합니다.

Webhook · 환불 요청→ AI Agent · 사유 분류→ IF · 금액 5만원 초과?→ Slack 승인 대기→ 결제 API 환불
AI 워크플로우를 처음 만들 때의 조언. 에이전트에게 모든 걸 맡기지 마세요. 판단이 필요한 한 단계만 AI에게 주고 나머지는 결정적(deterministic)인 노드로 구성하는 편이 훨씬 안정적입니다. "분류만 AI, 나머지는 IF/Switch"가 실무에서 가장 자주 성공하는 형태입니다.
비용 함정. AI 노드는 n8n 실행 횟수와 별개로 모델 API 요금이 따로 나갑니다. 아이템 100개짜리 배열에 AI 노드를 물리면 모델 호출이 100번 나갑니다. 배치로 묶거나, 앞단에서 필터링해 대상을 줄이세요.

다른 툴과 비교

"n8n이 제일 좋다"는 답은 이 강의에 없습니다. 축이 무엇인지부터 정리합니다.

도구를 비교할 때 실제로 결과를 가르는 축은 여섯 개입니다.

  1. 데이터가 어디에 머무는가 — 자체 호스팅 가능 여부. 규제 산업에서는 이 한 줄이 나머지를 전부 무효화합니다.
  2. 무엇에 과금하는가 — 실행 단위냐, 단계 단위냐. 워크플로우가 복잡할수록 격차가 벌어집니다.
  3. 코드로 탈출할 수 있는가 — 노코드 한계에 부딪혔을 때 우회로가 있는지.
  4. 누가 쓰는가 — 마케터가 직접 만드는가, 엔지니어가 만드는가.
  5. 어떤 작업량을 다루는가 — 이벤트 몇 건이냐, 테라바이트 배치냐.
  6. 운영 부담을 누가 지는가 — 서버 관리·업그레이드·모니터링을 벤더가 하는가 내가 하는가.

n8n을 쓰지 말아야 할 때

도구를 잘 아는 건 안 쓸 때를 아는 것이기도 합니다.

  • 팀에 서버를 돌볼 사람이 아무도 없을 때. 자체 호스팅의 "무료"는 라이선스 비용만 무료입니다. 업그레이드·백업·장애 대응은 누군가의 시간입니다. 그럴 바엔 Zapier가 쌉니다.
  • 비개발 직군이 스스로 만들어야 할 때. n8n은 JSON과 API 개념을 요구합니다. 마케팅팀이 직접 자동화를 만들고 유지해야 한다면 Zapier나 Make가 현실적입니다.
  • 초저지연이 필요할 때. 밀리초 단위 응답이 필요한 실시간 처리는 워크플로우 엔진이 아니라 서비스 코드로 짜야 합니다.
  • 대용량 데이터 변환이 본체일 때. 수백만 행 조인은 n8n이 아니라 dbt·Spark·SQL의 일입니다. n8n은 그것들을 호출하는 데 쓰세요.
  • 이미 잘 돌아가는 20줄짜리 스크립트가 있을 때. 굳이 옮기지 마세요. 자동화 툴의 가치는 연결이 많아질수록 커집니다.

비용 계산기

과금 단위 차이가 실제 청구서에서 어떻게 벌어지는지 슬라이더로 확인해 보세요.

같은 업무라도 세는 방식이 다릅니다. n8n은 워크플로우 실행 횟수를, Zapier는 액션 단계 수 × 실행 횟수를, Make는 모듈 실행 수 × 실행 횟수를 셉니다. 단계 수를 늘려 보면 격차가 어디서 생기는지 바로 보입니다.

이 계산기는 개략 추정입니다. 2026년 중반 각 벤더의 공개 가격을 기준으로 한 단순화된 모델이며, 실제 청구액은 구간별 플랜 계단, 환율, 초과분 정책, 연간 결제 할인에 따라 달라집니다. 트리거 단계 과금 여부 등 세부 규칙도 벤더마다 다릅니다. 의사결정 전에 반드시 각 벤더의 가격 페이지에서 현재 조건을 확인하세요.

#증상원인과 해결
1슬랙 메시지가 수십 개 갔다들어온 아이템 수만큼 노드가 반복 실행됐습니다. 앞에서 Aggregate나 Limit으로 줄이거나, 애초에 필터링하세요.
2아무 일도 일어나지 않는다아이템이 0개입니다. 빈 배열이 들어오면 이후 노드는 조용히 건너뜁니다. 각 노드의 출력 개수를 앞에서부터 확인하세요.
3에디터에선 되는데 운영에선 안 된다워크플로우를 게시하지 않았거나 비활성 상태입니다. 2.0부터 Save와 Publish가 분리됐습니다.
4웹훅 URL이 동작하지 않는다테스트 URL과 운영 URL이 다릅니다. 테스트 URL은 에디터에서 수신 대기 중일 때만 살아 있습니다. 운영에는 Production URL을 등록하세요.
5노드를 두 개 연결했는데 두 번 실행된다합류에 Merge를 쓰지 않았습니다. 한 노드 입력에 선을 두 개 꽂으면 각각에 대해 실행됩니다.
6실행 횟수가 폭발했다1~5분 간격 폴링 트리거를 쓰고 있습니다. 웹훅으로 바꾸거나 주기를 늘리세요. 이게 Cloud 요금 초과의 최대 원인입니다.
7DB가 계속 커지고 에디터가 느려진다실행 이력을 정리하지 않았습니다. EXECUTIONS_DATA_PRUNE과 최대 보관 기간을 설정하세요.
8업그레이드 후 자격증명이 다 깨졌다암호화 키가 바뀌었습니다. N8N_ENCRYPTION_KEY를 고정하지 않고 볼륨을 새로 만들면 이렇게 됩니다. 복구 불가이므로 백업이 유일한 예방책입니다.
9표현식이 계속 undefined를 뱉는다실제 데이터 구조를 확인하지 않고 필드명을 추측했습니다. 앞 노드를 한 번 실행해 출력 JSON을 눈으로 본 다음 필드를 드래그해서 넣으세요.
10노드가 60개인데 아무도 못 고친다서브워크플로우로 쪼개지 않았습니다. 20개를 넘으면 분리를 고민할 시점입니다. Sticky Note로 캔버스에 설명을 남기는 것도 습관으로 들이세요.
