감사·최소 권한·침해 대응

17~21편에서 인증·인가·어드미션을 쌓았습니다. 이 편은 공격자의 눈으로 그 벽을 넘어 보고, 다시 수비수의 눈으로 막습니다. 공격은 대개 한 번의 큰 구멍이 아니라 작은 권한을 이어 붙인 사슬입니다. 침해된 Pod의 토큰 하나가 Secret 열람으로, 다시 노드 접근으로, 끝내 클러스터 장악으로 이어집니다. 이 편은 그 사슬을 단계별로 재현하고, 각 고리를 최소 권한·정책·격리로 끊으며, 감사 로그로 탐지하는 법을 다룹니다. Level 3의 모든 편이 여기서 하나의 공격·방어 이야기로 묶입니다.

침해된 Pod에서 클러스터 장악까지: 어디서 끊나

왼쪽에서 방어 수단을 켜면, 아래 공격 사슬에서 그 고리가 끊깁니다(초록색). 하나라도 끊기면 그 뒤로는 진행하지 못합니다. 각 고리에는 어느 편에서 다룬 통제인지 적혀 있습니다. 목표는 가장 적은 방어로 사슬을 끊는 지점을 찾는 것입니다.

0

읽는 법과 목표

쉬운 말로 도둑은 보통 현관을 부수지 않습니다. 열린 창문(침해된 앱)으로 들어와, 서랍에서 찾은 열쇠(SA 토큰)로 다른 방을 열고, 그 방에서 찾은 마스터키(노드·비밀)로 건물 전체를 엽니다. 최소 권한은 방마다 열쇠를 다르게 두는 것, 감사 로그는 건물 곳곳의 CCTV, 탐지 규칙은 “새벽 3시에 금고 방문이 열리면 경보”라는 설정입니다. 침해 대응은 도둑이 든 걸 알았을 때 무엇을 먼저 잠그고, 어디까지 털렸는지 CCTV로 확인하는 절차입니다.

이 편을 마치면 할 수 있는 것

  • 토큰 탈취 → Secret → 노드 → 클러스터로 이어지는 상승 경로를 이해하고 각 고리를 끊는 통제를 짚을 수 있습니다.
  • rbac-tool·kubectl-who-can·rakkess·KubiScan으로 과잉 권한을 찾아 줄일 수 있습니다.
  • 감사 정책을 단계·수준·리소스별로 작성하고, 벤더 감사 로그의 보존·비용을 설계할 수 있습니다.
  • 위험 행위(exec, 토큰 생성, 가장, 비밀 대량 열람)에 대한 탐지 규칙을 쓸 수 있습니다.
  • 저장 암호화(KMS), External Secrets, Vault로 비밀을 관리하고, 침해 대응 플레이북을 실행할 수 있습니다.
1

권한 상승 경로의 해부

아래는 침해된 평범한 앱 Pod에서 시작하는 대표 경로입니다. 각 고리는 그 자체로는 작은 권한이지만, 이어지면 클러스터 장악이 됩니다. 괄호 안은 그 고리를 끊는 통제와 관련 편입니다.

#고리공격자가 하는 일끊는 통제
0초기 접근앱 취약점(RCE, SSRF)으로 Pod 안에서 코드 실행앱 보안(범위 밖), 이미지 스캔·서명(21편)
1SA 토큰 획득/var/run/secrets/…/token을 읽어 API 서버 호출자동 마운트 끄기(20편), MAP 강제(21편)
2권한 정찰SelfSubjectRulesReview로 내 권한 확인, API 탐색default SA에 권한 주지 않기(18편), 최소 권한(2장)
3비밀 열람get/list secrets로 다른 자격 증명·토큰 수집Secret 권한 최소화, 저장 암호화·외부 비밀(6장)
4측면 이동얻은 토큰·비밀로 다른 네임스페이스·클라우드(20편 워크로드 아이덴티티 오남용) 접근네임스페이스 격리, 신뢰 조건 정확히(20편), NetworkPolicy(9편)
5SA 빌리기Pod 생성 권한으로 강한 SA의 Pod를 띄움(18편 실습 3)어드미션으로 serviceAccountName 제한(21편), 강한 SA 격리
6노드 접근특권·hostPath·hostPID Pod로 노드 파일 시스템·kubelet 장악, 또는 nodes/proxy·execPSA restricted(21편), nodes/proxy 금지(18편)
7노드의 모든 비밀노드에 떠 있는 다른 Pod의 토큰·마운트된 Secret을 모두 수집(kubelet)민감 워크로드 전용 노드(테인트·노드 격리), 특권 차단
8클러스터 장악수집한 강한 토큰(또는 가장 권한)으로 cluster-admin 상당의 작업, 지속성 확보(웹훅·CronJob 심기)최소 권한, 가장 제한(18편), 감사·탐지(3·5장)
시니어 포인트: 한 고리만 끊어도 사슬은 멈춘다 완벽한 보안은 불가능하지만, 이 사슬은 어느 한 고리만 끊어도 그 뒤로 진행하지 못합니다. 자동 마운트를 끄면 1에서, Secret 권한을 없애면 3에서, PSA restricted면 6에서 멈춥니다. MSP가 고객 클러스터를 받으면 “모든 것을 완벽히”가 아니라 가장 비용이 적고 끊기 쉬운 고리부터(보통 1·3·6) 끊는 것이 현실적입니다. 맨 위 시뮬레이터로 최소 방어 집합을 찾아보세요.

최소 권한: 과잉 권한 찾기

도구·방법무엇을 찾나비고
kubectl auth can-i --list특정 주체(--as)로 할 수 있는 모든 것내장. 가장으로 역할 검증(18편)
kubectl-who-can특정 동사·리소스를 할 수 있는 모든 주체(역방향)“누가 secrets를 지울 수 있나”
rakkess주체 하나의 리소스×동사 접근 행렬한눈에 보는 매트릭스
rbac-tool권한 시각화, who-can, 정책 생성(실사용 기반), 위험 권한 분석audit2rbac과 함께 실사용 최소 역할 만들기
KubiScan위험 역할·바인딩, 탈취 시 치명적인 SA, 상승 가능 주체침해 평가에 유용
audit2rbac감사 로그에서 주체가 실제로 쓴 권한만으로 최소 역할 생성과잉 권한을 실사용 기준으로 줄이기

가장 먼저 봐야 할 것

  • cluster-admin·* 바인딩. Group·User·SA에 cluster-admin 또는 * 역할을 준 ClusterRoleBinding. 사람은 IdP 그룹 하나만, SA는 거의 없어야 합니다.
  • 위험 동사(18편). secrets get/list, pods/exec, serviceaccounts/token, nodes/proxy, escalate·bind·impersonate, 웹훅·CSR 승인.
  • default SA에 붙은 권한. 어떤 네임스페이스의 default에도 권한이 없어야 합니다(상승 경로 1·2).
  • system:authenticated·system:unauthenticated 바인딩. 모든 로그인 사용자(또는 비인증)에게 준 권한.
  • 탈취 시 치명적인 SA. 강한 권한을 가진 SA가 어느 네임스페이스에 있고 그 네임스페이스에 Pod를 만들 수 있는 사람이 누구인지(상승 경로 5).
내장 도구만으로 하는 1차 점검
# cluster-admin을 가진 주체
kubectl get clusterrolebindings -o json | jq -r '.items[] | select(.roleRef.name=="cluster-admin") | .metadata.name as $n | .subjects[]? | "\($n): \(.kind)/\(.name)"'
# 모든 인증 사용자에게 준 권한
kubectl get clusterrolebindings,rolebindings -A -o json | jq -r '.items[] | select(.subjects[]?.name | test("system:(authenticated|unauthenticated)")) | "\(.kind) \(.metadata.name) → \(.roleRef.name)"'
# 위험 권한을 누가 가지나 (가장으로 확인하거나 who-can)
for v in "get secrets" "create pods/exec" "create serviceaccounts/token" "get nodes/proxy" "impersonate users"; do
  echo "== $v"; kubectl auth can-i $v --list 2>/dev/null | head -1; done
# default SA에 붙은 바인딩
kubectl get rolebindings,clusterrolebindings -A -o json | jq -r '.items[] | select(.subjects[]? | .kind=="ServiceAccount" and .name=="default") | "\(.metadata.namespace // "-")/\(.metadata.name) → \(.roleRef.name)"'

감사 로그 설계

쉬운 말로 감사 로그는 API 서버 앞에 둔 CCTV입니다. 다만 모든 장면을 4K로 녹화하면 저장 비용이 폭발하므로, “어느 구역을 얼마나 자세히 찍을지”(감사 정책)를 정합니다. 금고 방(비밀·RBAC 변경)은 요청과 응답까지 자세히, 복도(목록 조회)는 지나갔다는 기록만, 화장실(헬스 체크)은 아예 안 찍습니다.
감사 수준(level)기록 범위
None기록 안 함(헬스 체크, 리스 갱신 등 소음)
Metadata누가·언제·무엇을·어디서(요청자·동사·리소스·결과). 본문 제외
RequestMetadata + 요청 본문(무엇을 만들려 했나)
RequestResponseRequest + 응답 본문. 가장 자세하고 가장 큼
  • 단계(stage). 각 요청은 RequestReceived → ResponseStarted → ResponseComplete(→ Panic) 단계를 거칩니다. 보통 ResponseComplete만 기록하고, omitStages로 RequestReceived를 빼 양을 절반으로 줄입니다.
  • 규칙은 위에서 아래로 첫 일치. 소음(None)을 먼저 걸러 내고, 민감 리소스를 자세히, 나머지는 Metadata로 받는 구조가 정석입니다.
  • 설정 위치. 셀프 관리형은 API 서버에 --audit-policy-file·--audit-log-path(또는 webhook 백엔드) 플래그로. 매니지드는 콘솔·IaC로 켜고 벤더 로그 저장소로 보냅니다(4장). 매니지드는 정책을 세밀하게 바꾸지 못하는 경우가 많습니다.
  • 비밀은 로그에도 샌다. Secret·ConfigMap에 RequestResponse를 걸면 비밀 값이 로그에 남습니다. 민감 리소스는 Metadata로.
감사 정책 예 (kubeadm --audit-policy-file)
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: ["RequestReceived"]
rules:
# 1) 소음 제거: 읽기 전용 시스템 요청, 헬스 체크
- level: None
  users: ["system:kube-scheduler", "system:kube-controller-manager", "system:apiserver"]
- level: None
  nonResourceURLs: ["/healthz*", "/readyz*", "/livez*", "/version", "/metrics"]
- level: None
  resources: [{group: "coordination.k8s.io", resources: ["leases"]}]
  verbs: ["get", "update"]
# 2) 비밀·RBAC 변경: 자세히(단, 비밀 '값'은 Metadata로 막음)
- level: Metadata
  resources: [{group: "", resources: ["secrets", "configmaps"]}]
- level: RequestResponse
  resources:
  - {group: "rbac.authorization.k8s.io", resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]}
  - {group: "admissionregistration.k8s.io"}      # 웹훅·정책 변경
  - {group: "certificates.k8s.io", resources: ["certificatesigningrequests"]}
# 3) 위험 서브리소스
- level: Request
  resources: [{group: "", resources: ["pods/exec", "pods/attach", "pods/portforward", "serviceaccounts/token"]}]
# 4) 쓰기 전반은 Metadata
- level: Metadata
  verbs: ["create", "update", "patch", "delete", "deletecollection"]
# 5) 나머지 읽기는 기록 안 함(양 조절) — 필요하면 Metadata로
- level: None
  verbs: ["get", "list", "watch"]

벤더 감사 로그와 보존·비용

환경감사 로그정책 제어보존·비용 포인트

현장 메모: “보존 기간이 탐지 능력을 정한다” 침해는 몇 주~몇 달 뒤에 드러나는 경우가 많습니다. 감사 로그 보존이 7일이면 그 이전의 침투 경로를 재구성할 수 없습니다. 비용 때문에 전부 오래 둘 수는 없으니, 민감 작업(비밀·RBAC·exec·토큰)은 길게(예: 1년, 저비용 저장소로), 일반 로그는 짧게 두는 2단계 보존을 설계하세요. 규제 산업이면 보존 기간이 요구 사항에 명시됩니다.
5

탐지 규칙 작성

감사 로그는 탐지로 이어질 때 가치가 있습니다. 로그 쿼리 알림, Falco(런타임·시스템 콜), 또는 SIEM 상관 분석으로 구현합니다. 아래는 상승 경로(1장)의 각 고리에 대응하는 대표 신호입니다.

신호무엇을 잡나(경로)audit 로그에서 보는 것
pods/exec·attach컨테이너 침투·토큰 수집(6)objectRef.subresource=exec, verb=create, 사람·SA 주체
serviceaccounts/token 생성토큰 직접 발급(8)objectRef.resource=serviceaccounts, subresource=token, create
impersonate 사용가장 악용요청 헤더에서 온 impersonatedUser·Groups가 로그에 기록
secrets 대량 열람비밀 수집(3)짧은 시간에 한 주체의 secrets get/list 급증
RBAC·웹훅·CSR 변경지속성·상승(8)clusterrolebindings create, webhookconfiguration create, csr approve
default SA의 API 호출침해된 앱(1·2)user.username=system:serviceaccount:*:default가 API를 부름
anonymous·403 급증정찰user=system:anonymous, responseStatus.code=403 반복

시니어 포인트: 런타임 탐지와 감사 로그는 다른 층을 본다 감사 로그는 API 서버를 거친 행위만 봅니다. 노드에서 토큰 파일을 읽거나(상승 1), 컨테이너가 셸을 띄우거나, 호스트 파일 시스템을 뒤지는 것은 API를 거치지 않으므로 audit에 안 남습니다. 이런 노드·컨테이너 내부 행위는 Falco 같은 런타임 보안(eBPF·시스템 콜)으로 봅니다. 둘은 겹치지 않는 사각을 서로 메웁니다. 고객 환경에 감사 로그만 있다면 노드 단계(6~7)의 탐지 공백을 알려 주세요.

비밀 관리: 저장 암호화·외부 비밀

계층무엇막는 위협한계
저장 암호화(etcd)API 서버가 Secret을 etcd에 쓰기 전 암호화(EncryptionConfiguration). KMS v2로 외부 키 사용etcd 디스크·백업 유출클러스터 안에서 Secret을 읽을 수 있는 주체에게는 그대로 평문. RBAC이 여전히 1차 방어
External Secrets Operator외부 비밀 저장소(Vault·클라우드 Secrets Manager·KMS)의 값을 Secret으로 동기화비밀을 Git·매니페스트에 두지 않음, 중앙 회전결국 클러스터 안에 Secret으로 존재. RBAC·저장 암호화 병행
Secrets Store CSI Driver외부 저장소의 비밀을 Pod에 파일로 마운트(동기화 Secret 선택)Secret 객체 없이 Pod에만 전달 가능Pod 안에서는 평문 파일. 드라이버·프로바이더 운영
클라우드 비밀 + 워크로드 아이덴티티앱이 SDK로 클라우드 Secrets Manager를 직접 읽음(20편 신원)Kubernetes Secret 자체를 안 만듦앱 수정 필요, 클라우드 종속
봉인된 비밀(Sealed Secrets)공개 키로 암호화한 값을 Git에 저장, 클러스터가 복호화GitOps에 비밀을 안전하게복호화 키 관리, 회전

- resources: ["secrets"]
  providers:

      endpoint: unix:///var/run/kms/socket.sock

# kubectl get secrets -A -o json | kubectl replace -f -
  • 매니지드의 저장 암호화. EKS는 KMS 키로 Secret 봉투 암호화(클러스터 생성 시 또는 이후 연결), AKS는 KMS etcd 암호화(Key Vault), GKE는 애플리케이션 계층 비밀 암호화(Cloud KMS), OpenShift는 etcd 암호화 활성화. 모두 켜는 것이 기준선입니다.
  • 그래도 RBAC이 먼저. 저장 암호화는 디스크·백업 유출을 막지만, Secret을 읽을 권한이 있는 토큰을 탈취하면 소용없습니다(상승 3). 비밀 열람 권한 최소화가 1차입니다.
7

침해 대응 플레이북

  1. 격리(Contain). 침해된 Pod를 바로 지우지 말고 격리합니다: NetworkPolicy로 이그레스 차단(9편), 노드 cordon, 필요하면 네임스페이스 분리. 증거(메모리·디스크)를 보존합니다.
  2. 자격 증명 무효화(Eradicate). 침해된 SA의 토큰을 무효화합니다. 바운드 토큰은 Pod 삭제로 무효(20편)되고, 레거시 토큰은 Secret 삭제, 유출된 클라우드 자격 증명은 회전. 관련 사용자 자격 증명(17편)도 재발급합니다.
  3. 범위 파악(Scope). 감사 로그로 그 주체·토큰이 언제부터 무엇을 했는지 재구성합니다(5장 쿼리). 가장·토큰 생성·비밀 열람·RBAC 변경을 추적합니다.
  4. 지속성 제거. 공격자가 심었을 수 있는 것: 새 ClusterRoleBinding, 웹훅, CronJob, 추가 SA·토큰, 변조된 이미지. 변경 이력(감사 로그·GitOps diff)과 대조합니다.
  5. 복구(Recover). GitOps에서 의도된 상태로 되돌리고(15편 백업과 함께), 신뢰할 수 없으면 클러스터를 재구축합니다. etcd·노드가 장악됐다면 재구축이 기본입니다.
  6. 교훈(Lessons). 끊긴 고리와 끊지 못한 고리를 1장 사슬에 대입해, 최소 권한·정책·탐지 규칙을 보강합니다. 브레이크글라스(17편) 사용 여부도 점검합니다.
함정: 토큰을 무효화하기 전에 지우면 안 되는 것 침해된 Pod를 급히 삭제하면 바운드 토큰은 무효화되지만 증거와 범위 파악 단서(프로세스·메모리·열린 연결)도 사라집니다. 순서는 ① 네트워크 격리 → ② 증거 확보 → ③ 토큰·자격 증명 무효화 → ④ 삭제입니다. 자동화된 “침해 Pod 자동 삭제”는 포렌식을 방해할 수 있으니 격리 우선으로 설계하세요.

현장 사례

침해된 웹 앱의 default 토큰으로 클러스터가 정찰됐다

원인. API를 안 쓰는 앱에 default 토큰이 마운트돼 있었고, 누군가 편의로 default SA에 view를 줬습니다. RCE로 들어온 공격자가 토큰으로 전체 구조를 파악하고 비밀이 든 ConfigMap을 찾았습니다.

교훈. 자동 마운트 끄기(고리 1) + default SA 무권한(고리 2)이 가장 싸고 효과 큰 두 조치입니다.

개발자 편의용 pods 생성 권한이 네임스페이스 장악으로

원인. 앱 SA에 디버깅용으로 pods 생성을 줬는데, 같은 네임스페이스에 admin SA가 있어(배포 도구) 그 SA로 Pod를 띄워 권한을 빌렸습니다(고리 5).

교훈. 강한 SA는 전용 네임스페이스로, serviceAccountName은 어드미션으로 제한(21편).

감사 로그 보존이 3일이라 침투 경로를 재구성 못 했다

원인. 비용 때문에 CloudWatch 보존을 3일로 두었는데, 침해가 2주 뒤 드러나 초기 침투와 측면 이동 기록이 모두 사라졌습니다.

교훈. 민감 작업은 저비용 장기 저장소로 길게 보존하는 2단계 설계(4장).

비밀을 RequestResponse로 감사해 로그에 평문이 남았다

원인. “모든 것을 자세히” 감사하려고 Secret에 RequestResponse를 걸어, 감사 로그 저장소에 모든 비밀 값이 평문으로 쌓였습니다. 로그 접근 권한이 곧 비밀 접근이 됐습니다.

교훈. 민감 리소스는 Metadata로. 감사 로그 저장소도 비밀만큼 보호하세요.

감사 로그만 믿다가 노드 단계 공격을 놓쳤다

원인. 특권 Pod가 노드의 다른 Pod 토큰을 수집했는데(고리 7), 이 행위는 API를 거치지 않아 audit에 남지 않았습니다. 탐지가 전혀 없었습니다.

교훈. 노드·컨테이너 내부는 런타임 보안(Falco 등)으로. PSA로 특권을 막아 애초에 고리 6을 끊습니다.

침해 Pod를 급히 지워 포렌식이 불가능해졌다

원인. 자동화 규칙이 의심 Pod를 즉시 삭제해, 공격 범위를 파악할 메모리·연결 정보가 사라졌습니다.

교훈. 격리 → 증거 확보 → 무효화 → 삭제 순서(7장). 자동 삭제 대신 자동 격리로.

저장 암호화를 켰는데도 비밀이 유출됐다

원인. etcd 저장 암호화는 켜 두었지만, 탈취된 토큰에 secrets get 권한이 있어 API로 평문을 그대로 읽었습니다.

교훈. 저장 암호화는 디스크·백업 유출용입니다. 비밀 열람 권한 최소화가 1차 방어(6장).

퇴사한 관리자가 심어 둔 웹훅으로 지속성이 유지됐다

원인. 침해(또는 내부자)로 심긴 변경 웹훅이 특정 네임스페이스의 Pod에 역방향 셸 사이드카를 주입하고 있었습니다. RBAC 점검에서는 안 보였습니다.

교훈. 지속성 점검에 웹훅·CronJob·추가 SA를 포함하고, 웹훅·RBAC 변경을 감사 경보로(5장). GitOps diff와 대조.

Level 3 정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. 권한 상승은 작은 권한의 사슬이며(토큰 → 비밀 → SA 빌리기 → 노드 → 클러스터), 어느 한 고리만 끊어도 멈춥니다. 가장 싼 고리(자동 마운트·Secret·특권)부터 끊습니다.
  2. 과잉 권한은 kubectl auth can-i, who-can, rakkess, rbac-tool, KubiScan, audit2rbac으로 찾고, cluster-admin·위험 동사·default SA·모든 인증 사용자 바인딩을 먼저 봅니다.
  3. 감사 정책은 소음 제거 → 민감 리소스 자세히(단 비밀 값은 Metadata) → 쓰기 Metadata 구조로 짜고, 벤더 로그는 보존·비용을 2단계로 설계합니다.
  4. exec·토큰 생성·가장·비밀 대량 열람·RBAC/웹훅 변경·default SA 호출을 탐지 규칙으로 만들되, 노드·컨테이너 내부는 런타임 보안으로 보완합니다.
  5. 저장 암호화와 외부 비밀은 비밀을 보호하지만 RBAC이 1차이며, 침해 대응은 격리 → 증거 → 무효화 → 범위 → 지속성 제거 → 복구 순서로 합니다.
