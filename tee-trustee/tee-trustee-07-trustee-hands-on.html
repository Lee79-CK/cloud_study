시작하기 전에

6편에서 Trustee 내부 구조를 지도로 그렸습니다. 이번 편은 그 지도를 손으로 따라가는 실습입니다. 실습 대부분은 TEE 하드웨어 없이 할 수 있습니다. Trustee는 컨테이너 묶음으로 실행되므로 호스트에 기밀 컴퓨팅 하드웨어나 GPU가 필요 없기 때문입니다.

🧰준비물

  • 인터넷이 되는 리눅스 호스트 (VM이어도 충분)
  • Docker Engine과 Compose 플러그인
  • git, curl, openssl
  • ORAS CLI (kbs-client 바이너리를 받는 데 사용)
  • (Part C) 테스트용 Kubernetes 클러스터와 kubectl, helm

⚠️실습 안전 수칙

  • 이 실습 환경은 평가용입니다. 운영 환경에 그대로 쓰지 마세요.
  • 리소스에는 진짜 키나 비밀번호를 넣지 마세요. openssl rand로 만든 시험용 값만 씁니다.
  • 실습 중 --allow-all 정책을 잠시 쓰는데, 일부러 "위험한 상태"를 보여주기 위해서입니다. 실습 후 반드시 되돌립니다.
  • 명령 옵션은 Trustee 버전에 따라 바뀔 수 있습니다. 막히면 --help부터 확인하세요.

실습 지도

🅰️Part A · 로컬 Trustee

실습 1~3. Docker Compose로 KBS·AS·RVPS를 띄우고, kbs-client를 설치하고, 첫 요청이 정책에 의해 거부되는 것을 확인합니다.

🅱️Part B · 정책 실험

실습 4~8. 관리자 인증을 이해하고, 리소스를 등록하고, 리소스 정책과 참조값을 바꿔가며 결과를 관찰합니다.

🅲Part C · 클러스터 연결

10~11장. Kubernetes에 Helm이나 오퍼레이터로 올리는 방법, CoCo 파드가 Trustee를 찾아가도록 연결하는 설정을 봅니다.

실습의 핵심 관찰 포인트

이 실습에서 가장 중요한 장면은 "거부"입니다. TEE가 없는 노트북에서 보내는 요청은 가짜 증거(샘플 증명자)를 쓰기 때문에, 제대로 설정된 Trustee라면 거부해야 정상입니다. 거부를 확인하는 것이 곧 Trustee가 제대로 동작한다는 증거입니다. 반대로 "허용"이 나오는 순간이 오면, 그때가 바로 위험한 설정이라는 신호입니다.

실습 1: Trustee 띄우기

Trustee 저장소에는 KBS, AS, RVPS를 함께 띄우는 docker-compose.yml이 들어 있습니다.

1-1. 저장소를 받고 실행하기

git clone https://github.com/confidential-containers/trustee.git && cd trustee docker compose up -d

처음 실행하면 이미지를 내려받느라 몇 분 걸릴 수 있습니다. 명령이 끝난 뒤에도 서비스가 요청을 받을 준비가 되기까지 몇 초가 더 필요할 수 있습니다.

# 예상 출력 (형식은 버전에 따라 조금 다를 수 있음) [+] Running 4/4 ✔ Network trustee_default Created ✔ Container trustee-rvps-1 Started ✔ Container trustee-as-1 Started ✔ Container trustee-kbs-1 Started

1-2. 세 컨테이너가 떴는지 확인하기

docker compose ps # 예상 출력: KBS만 바깥(8080)으로 열려 있다는 점에 주목 NAME IMAGE STATUS PORTS trustee-as-1 .../attestation-service Up - trustee-kbs-1 .../kbs Up 0.0.0.0:8080->8080/tcp trustee-rvps-1 .../rvps Up -
6편 지도와 맞춰 보기

포트가 열린 것은 KBS 하나뿐입니다. 6편에서 "게스트는 KBS하고만 대화한다, KBS가 Trustee의 정문"이라고 했던 구조가 그대로 보입니다. AS와 RVPS는 Docker 내부 네트워크에서만 KBS와 이야기합니다.

1-3. KBS가 응답하는지 확인하기

curl -X POST http://127.0.0.1:8080/kbs/v0/attest

본문이 비어 있으니 오류 응답이 오는 것이 정상입니다. 어떤 HTTP 응답이든 오기만 하면 KBS가 살아 있다는 뜻입니다. "connection refused"가 나오면 컨테이너가 안 떴거나 8080 포트가 열리지 않은 것입니다. 이 경로가 3편 RCAR의 Attestation 단계 주소라는 것도 기억해 두세요. 연결 확인 외에는 curl로 KBS를 직접 두드리기보다 kbs-client를 쓰는 것이 좋습니다.

1-4. 설정 파일은 어디에 있나

구성 요소설정 파일 위치 (저장소 기준)여기서 바꾸는 것 (예)
KBSkbs/config/docker-compose/kbs-config.tomlHTTPS, 관리자 인증, 플러그인·저장소
ASkbs/config/as-config.json토큰 수명, 토큰 크기, 정책 엔진
RVPSkbs/config/rvps.json참조값 저장 방식, 추출기

설정 파일은 시작할 때 읽히므로, 바꾼 뒤에는 docker compose restart로 다시 시작해야 합니다. 로그를 더 자세히 보고 싶으면 RUST_LOG=debug를 담은 env 파일을 만들어 docker compose --env-file debug.env up으로 실행합니다.

실습 2: kbs-client 설치

kbs-client는 Trustee를 설정하고 시험 요청을 보내는 명령줄 도구입니다. 두 가지 방법으로 설치할 수 있습니다.

방법 A. ORAS로 바이너리 받기 (가장 간단)

oras pull ghcr.io/confidential-containers/staged-images/kbs-client:latest chmod +x kbs-client ./kbs-client --help

방법 B. 소스에서 빌드하기

git clone https://github.com/confidential-containers/trustee.git cd trustee/kbs make CLI_FEATURES=sample_only cli sudo make install-cli
sample_only의 뜻

이 옵션은 하드웨어 증명자(TDX, SNP 등)를 빼고 샘플 증명자만 넣어 빌드합니다. 그래서 의존성이 적고 아무 PC에서나 빌드됩니다. ORAS로 받은 바이너리도 TEE 안에서 리소스를 받는 용도로는 쓸 수 없습니다. 실제 TEE 안에서 kbs-client로 리소스를 받아야 한다면 이 옵션을 빼고 빌드해야 하지만, CoCo 파드에서는 kbs-client 대신 5편 10장의 ASR·CDH 방식을 쓰는 것이 원칙입니다.

실습 3: 첫 요청, 첫 거부

아직 아무 리소스도 등록하지 않았지만, 일단 요청을 보내봅니다. 경로는 아무거나 써도 됩니다.

./kbs-client --url http://127.0.0.1:8080 get-resource --path my_repo/resource_type/123abc
# 예상 출력 WARN kbs_protocol::client::rcar_client: Authenticating with KBS failed. Perform a new RCAR handshake: ErrorInformation { error_type: "https://github.com/confidential-containers/kbs/errors/PolicyDeny", detail: "Access denied by policy", } Error: request unauthorized
이 거부가 "성공"인 이유

오류처럼 보이지만 이 결과는 실습의 정상 결과입니다. 출력을 해석해 보면 이렇습니다.

  1. rcar_client: kbs-client가 3편의 RCAR 대화를 시작했습니다. KBS에 정상적으로 닿았다는 뜻입니다.
  2. kbs-client의 get-resource는 TEE 밖에서는 샘플 증명자로 가짜 증거를 만들어 보냅니다.
  3. KBS가 증거를 AS에 넘겼고, AS가 판정해 토큰을 만들었습니다.
  4. KBS의 기본 리소스 정책은 샘플 증명자에서 온 요청을 거부합니다(6편 9장). 그래서 PolicyDeny가 나왔습니다.

즉 요청은 KBS → AS → 정책 엔진까지 6편의 생산 라인을 모두 통과했고, 마지막 관문에서 막혔습니다. 리소스가 아직 없는데도 "리소스 없음"이 아니라 "정책 거부"가 먼저 나오는 점도 눈여겨보세요. 정책 검사가 리소스 조회보다 앞에 있습니다.

실습 4: 관리자 인증

리소스 등록이나 정책 변경 같은 관리 작업은 보호되어 있습니다. kbs-client의 config 하위 명령에는 관리자 인증 정보를 함께 넘겨야 합니다.

문서마다 방식이 다를 수 있다

Trustee는 관리자 인증 방식을 바꾸는 중입니다. CoCo 문서 중 일부(KBS Client Tool, Policies 페이지)는 관리자 토큰 파일(--admin-token-file)을 안내하고, Docker Compose 설치 페이지는 자동 생성되는 관리자 키 쌍(개인키 kbs/config/private.key)을 안내합니다. 쓰는 버전에 어떤 방식이 들어 있는지 ./kbs-client config --help로 먼저 확인하세요.

방식kbs-client 옵션 (예)준비
관리자 토큰config --admin-token-file <파일>Trustee 배포 전에 토큰을 정해 두고, 설치 가이드가 안내하는 위치의 파일을 지정
관리자 키 쌍 (이전 방식)config --auth-private-key kbs/config/private.keyDocker Compose가 자동 생성. 직접 만들려면 아래 명령
# (키 쌍 방식) 자동 생성된 키를 직접 만든 키로 바꾸고 싶을 때 openssl genpkey -algorithm ed25519 > kbs/config/private.key openssl pkey -in kbs/config/private.key -pubout -out kbs/config/public.pub docker compose restart

아래 실습에서는 관리자 인증 부분을 $ADMIN이라는 변수로 줄여 쓰겠습니다. 환경에 맞게 하나를 골라 두세요.

# 관리자 토큰 방식이라면 ADMIN="--admin-token-file /path/to/admin-token" # 키 쌍 방식이라면 ADMIN="--auth-private-key kbs/config/private.key" KBS=http://127.0.0.1:8080
MSP 관점

이 파일 하나가 모든 정책과 리소스를 바꿀 수 있는 권한입니다. 실습에서는 저장소 폴더에 그냥 놓여 있지만, 운영에서는 이 권한을 누가 가지느냐가 3편 13장의 운영 모델을 결정합니다. 고객이 키 결정권을 가지는 모델이라면 이 인증 정보는 MSP 엔지니어의 노트북에 있으면 안 됩니다.

실습 5: 리소스 등록

시험용 "모델 키"를 하나 만들어 KBS에 등록합니다. 6편 9장에서 정한 대로 저장소/종류/태그 경로를 씁니다.

# 1) 시험용 키 만들기 (진짜 키를 넣지 말 것!) openssl rand -hex 32 > model-key.txt cat model-key.txt # 2) KBS에 등록 ./kbs-client --url $KBS config $ADMIN set-resource \ --path llm-prod/model-key/v1 --resource-file model-key.txt

정상 등록되면 특별한 오류 없이 끝납니다. 이제 다시 요청해 봅니다.

./kbs-client --url $KBS get-resource --path llm-prod/model-key/v1 # 결과: 여전히 PolicyDeny. 리소스가 생겼어도 기본 정책이 샘플 증거를 거부하므로.
비유로 정리

금고에 물건을 넣었다고 해서 아무에게나 꺼내 주지는 않습니다. 창구 규칙(리소스 정책)이 "신분증이 위조면 안 된다"고 되어 있는 한, 가짜 신분증(샘플 증거)을 낸 손님은 물건이 있어도 받을 수 없습니다. 다음 실습에서 그 규칙을 일부러 바꿔 봅니다.

실습 6: 리소스 정책 실험

이번 실습의 하이라이트입니다. 리소스 정책을 바꿔가며 같은 요청이 어떻게 다르게 처리되는지 봅니다. 로컬 환경의 요청은 모두 샘플 증거라는 점을 기억하세요.

실험 A. 모두 허용하면? (위험한 상태 체험)

./kbs-client --url $KBS config $ADMIN set-resource-policy --allow-all ./kbs-client --url $KBS get-resource --path llm-prod/model-key/v1 # 결과: 리소스가 출력된다. 출력이 base64로 인코딩되어 있다면 디코딩해서 model-key.txt와 비교
방금 일어난 일

TEE가 전혀 없는 노트북이, 가짜 증거만으로 "모델 키"를 받아갔습니다. Trustee가 아무리 정교해도 리소스 정책 한 줄이 모든 보호를 무력화할 수 있다는 것을 몸으로 확인한 셈입니다. 운영 환경에서 이 상태가 되면 1편의 "가짜 금고" 시나리오가 그대로 재현됩니다.

실험 B. affirming을 요구하면?

./kbs-client --url $KBS config $ADMIN set-resource-policy --affirming ./kbs-client --url $KBS get-resource --path llm-prod/model-key/v1 # 결과: PolicyDeny. 샘플 증거는 affirming 판정을 받지 못하므로.

실험 C. 내가 쓴 정책 넣어보기

6편 9장에서 읽었던 Rego를 직접 써서 넣어 봅니다. 아래는 "실습용 저장소(lab)에 한해서만 샘플 증거를 허용하고, 그 밖의 저장소는 affirming을 요구하는" 정책입니다. 경로에 따라 규칙이 갈리는 것을 확인하는 것이 목적입니다.

# lab-policy.rego (실습 전용 · 운영 금지) package policy import rego.v1 default allow = false # 1) 실습 저장소는 샘플 증거도 허용 allow if { data.plugin == "resource" data["resource-path"][0] == "lab" } # 2) 그 밖의 저장소는 affirming일 때만 allow if { data.plugin == "resource" data["resource-path"][0] != "lab" input["submods"]["cpu0"]["ear.status"] == "affirming" }

학습용 예시입니다. 정책 입력에서 경로의 각 부분을 가리키는 방식(인덱스 등)은 Trustee 버전의 정책 문서와 기본 정책 파일을 보고 맞추세요.

openssl rand -hex 16 > lab-secret.txt ./kbs-client --url $KBS config $ADMIN set-resource --path lab/demo/v1 --resource-file lab-secret.txt ./kbs-client --url $KBS config $ADMIN set-resource-policy --policy-file lab-policy.rego ./kbs-client --url $KBS get-resource --path lab/demo/v1 # → 허용 ./kbs-client --url $KBS get-resource --path llm-prod/model-key/v1 # → PolicyDeny

실습 정리: 반드시 되돌리기

./kbs-client --url $KBS config $ADMIN set-resource-policy --affirming # 또는 6편 9장의 Init-Data 바인딩 정책처럼 더 엄격한 정책으로

실습 7: 참조값 등록

참조값은 AS가 증거를 판정할 때 쓰는 "정상 기준표"입니다(6편 4장). 로컬 실습에서는 진짜 TEE 증거가 없으므로 참조값으로 affirming 판정을 받아내지는 못하지만, 등록하고 조회하는 흐름을 익혀 둘 수 있습니다.

방법 A. kbs-client로 간단한 값 넣기

./kbs-client --url $KBS config $ADMIN set-sample-reference-value test-kernel-hash abc123 ./kbs-client --url $KBS config $ADMIN get-reference-values

이 방법은 sample 추출기를 쓰며, 요청은 KBS의 관리 경로를 거쳐 RVPS로 전달됩니다. 기본은 문자열 하나를 담은 목록으로 저장되고, 옵션으로 단일 값, 숫자, 참·거짓 형식을 지정할 수 있습니다.

방법 B. rvps-tool로 직접 등록하기

더 복잡한 참조값은 RVPS에 직접 붙는 rvps-tool을 씁니다. 이 도구는 KBS 관리자 권한과 분리되어 있어, 빌드 파이프라인 같은 "참조값 공급자"에게 따로 줄 수 있습니다.

# 도구 빌드 cd trustee/rvps && make # 테스트용 (서명되지 않은) sample 메시지 만들기 cat << EOF > sample { "test-binary-1": ["reference-value-1", "reference-value-2"] } EOF provenance=$(cat sample | base64 --wrap=0) cat << EOF > message { "version": "0.1.0", "type": "sample", "payload": "$provenance" } EOF # Docker Compose 환경의 RVPS 주소는 보통 127.0.0.1:50003 rvps-tool register --path ./message --addr 127.0.0.1:50003 rvps-tool query --addr 127.0.0.1:50003
운영에서 달라지는 점

RVPS는 원래 서명된 메시지로 참조값을 받기를 기대합니다. 위의 sample 메시지는 테스트용입니다. 운영에서는 빌드 파이프라인이 측정값을 계산하고 서명해서 등록하는 흐름을 만들어야 하며, 이것이 8편의 주제입니다.

Kubernetes로 옮기기

Docker Compose는 시작점으로 좋지만, 운영에는 Helm이나 Trustee 오퍼레이터가 권장됩니다.

⛵Helm

차트 값(values)으로 KBS·AS·RVPS 구성, 관리자 인증, 정책 파일을 넘깁니다. GitOps 도구로 차트를 관리하는 MSP 환경에 잘 맞습니다.

🤖오퍼레이터

KbsConfig 커스텀 리소스가 여러 ConfigMap과 Secret을 묶어 Trustee 구성을 선언합니다. Red Hat 배포판은 TrusteeConfig 하나로 CPU·GPU 증명 정책, 리소스 정책 ConfigMap까지 자동으로 만들어 줍니다.

CoCo 파드와 연결하기

Trustee가 준비되면 CoCo 파드가 그 주소를 알도록 연결합니다. 5편 8장의 Init-Data가 그 역할을 합니다.

# initdata.toml 의 연결 부분 (5편 8장 복습) version = "0.1.0" algorithm = "sha384" [data] "aa.toml" = ''' [token_configs.kbs] url = "https://kbs.example.internal:8080" # 증명할 KBS ''' "cdh.toml" = ''' [kbc] name = "cc_kbc" url = "https://kbs.example.internal:8080" # 리소스를 받을 KBS ''' "policy.rego" = '''…genpolicy로 만든 에이전트 정책…'''

이 TOML을 gzip·base64로 인코딩해 파드의 io.katacontainers.config.hypervisor.cc_init_data 어노테이션에 넣습니다. KBS를 HTTPS로 운영한다면, 게스트가 그 인증서를 신뢰할 수 있도록 하는 설정도 Init-Data에 함께 넣어야 합니다(설정 키는 버전 문서 확인).

하드웨어 없이 연결 연습하기

TEE 하드웨어가 없는 클러스터라면 개발용 RuntimeClass(kata-qemu-coco-dev 등)로 CoCo 파드의 흐름을 연습할 수 있습니다. 이 파드는 진짜 TEE가 아니므로 증거도 진짜가 아닙니다. 따라서 affirming을 요구하는 정책이라면 거부되는 것이 정상입니다. 실습에서 "파드 → KBS 연결"만 확인하고 싶다면 7장의 lab 저장소처럼 실습 전용 경로를 두는 방법을 쓸 수 있습니다.

# 연결 확인용 시험 파드 (개념 예시) apiVersion: v1 kind: Pod metadata: name: kbs-wiring-test annotations: io.katacontainers.config.hypervisor.cc_init_data: <gzip+base64 Init-Data> spec: runtimeClassName: kata-qemu-coco-dev # 하드웨어 없는 연습용 containers: - name: test image: registry.example.com/curl@sha256:… # 값을 그대로 출력하지 않고 해시만 출력해서 확인 command: ["sh", "-c", "curl -s http://127.0.0.1:8006/cdh/resource/lab/demo/v1 | sha256sum; sleep 3600"]
값이 아니라 해시를 출력하는 이유

시험용 값이라도 로그에 비밀을 그대로 찍는 습관은 들이지 않는 것이 좋습니다. 1편 시나리오 C(로그에 다 있었다)를 기억하세요. 등록할 때 만든 파일의 해시(sha256sum lab-secret.txt)와 파드 로그의 해시가 같으면 연결이 성공한 것입니다.

16

정리와 다음 편

  1. Trustee는 docker compose up -d 한 번으로 TEE 하드웨어 없이 띄울 수 있고, 바깥에 열리는 것은 KBS(8080)뿐입니다.
  2. 로컬의 kbs-client 요청은 샘플 증거를 쓰므로, 기본 정책이나 affirming 정책에서 PolicyDeny가 나오는 것이 정상입니다.
  3. 관리 작업에는 관리자 인증이 필요하며, 버전에 따라 관리자 토큰 또는 관리자 키 쌍 방식입니다.
  4. --allow-all 실험은 리소스 정책 한 줄이 모든 보호를 무력화할 수 있음을 보여줍니다. 실습 후 반드시 되돌립니다.
  5. 참조값은 kbs-client(간단한 값)나 rvps-tool(직접·복잡한 값)로 등록하며, 운영에서는 서명된 메시지를 써야 합니다.
  6. 운영에는 Helm이나 오퍼레이터를 쓰고, HTTPS·버전 고정·토큰 수명·고가용성을 갖춥니다.
  7. CoCo 파드는 Init-Data의 aa.toml·cdh.toml로 Trustee를 찾아갑니다.

8편 예고: 참조값과 정책 운영

이번 편에서 "운영에서는 다르다"고 미뤄둔 것들을 다룹니다. 빌드 파이프라인에서 측정값을 계산하고 서명해 RVPS에 등록하는 흐름, 이미지 digest·에이전트 정책·Init-Data·참조값을 하나의 릴리스로 묶는 방법, 정책을 코드로 관리하고 테스트하는 방법, 그리고 펌웨어나 커널을 업데이트할 때 증명이 일제히 실패하지 않도록 단계적으로 전환하는 운영 절차입니다.

TEE·Trustee 강의 시리즈 7편. 명령과 출력은 CoCo 공식 문서와 NVIDIA 빠른 시작 문서를 기준으로 정리했으며, 일부 출력과 정책 예시는 학습용으로 단순화했습니다. Trustee는 빠르게 변하므로 실제 실습 시 사용하는 버전의 --help와 문서를 함께 확인하세요.
