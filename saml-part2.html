1

전체 흐름 따라가기

다음 단계 버튼으로 한 칸씩 넘기세요. 각 단계의 실제 메시지와 주의점이 아래에 나타납니다.

가장 흔한 시나리오부터 봅니다. 사용자가 사내 위키 주소를 직접 입력해서 들어왔고, 아직 로그인 세션이 없는 상황입니다. 서비스 쪽에서 흐름이 시작되기 때문에 이를 SP-initiated SSO라고 부릅니다.

먼저 기억할 한 가지 — SP와 IdP는 서로 네트워크로 직접 연결되지 않아도 됩니다. 모든 메시지는 브라우저의 리다이렉트와 폼 전송으로 전달됩니다. 이걸 프론트 채널(front-channel) 통신이라고 하며, 사내망의 IdP와 인터넷의 SaaS가 연동될 수 있는 이유이기도 합니다.

2

시작점이 둘이다

어디서 흐름이 시작되느냐에 따라 보안 성질이 달라집니다.

서비스에서 시작하는 방식

사용자가 서비스 주소로 먼저 들어옵니다. SP가 AuthnRequest를 만들어 IdP로 보내고, 그 요청 ID를 자기 세션에 기억해 둡니다. 나중에 돌아온 응답의 InResponseTo가 그 ID와 맞는지 대조할 수 있습니다.

인증 서버에서 시작하는 방식

사용자가 IdP의 앱 목록 화면(Okta 대시보드, Entra ID의 My Apps 등)에서 아이콘을 클릭합니다. IdP는 요청받은 적 없이 Assertion을 만들어 SP의 ACS URL로 바로 POST합니다.

IdP-initiated가 위험한 이유 — SP 입장에서는 “내가 요청하지도 않은 로그인 응답”이 날아든 것이라, 정상 응답인지 공격자가 밀어 넣은 것인지 구분할 근거가 부족합니다. 공격자가 자기 계정의 유효한 Assertion을 캡처해 피해자 브라우저에서 강제로 제출시키면, 피해자가 공격자 계정으로 로그인된 상태가 됩니다. 이 상태에서 피해자가 문서를 올리면 그 문서는 공격자 손에 들어갑니다. 그래서 가능하면 SP-initiated를 쓰고, IdP-initiated는 꼭 필요한 곳만 켜두는 것이 원칙입니다.

실무에서는 두 방식이 섞여 있는 경우가 많습니다. 사용자는 보통 북마크로 서비스에 직접 들어가지만(SP-initiated), 신규 입사자 온보딩에서는 IdP 포털의 앱 목록을 안내하기 때문입니다(IdP-initiated). 연동을 설계할 때 “이 앱은 어느 쪽을 쓰게 할 것인가”를 먼저 정해두면 나중에 디버깅이 훨씬 쉬워집니다.

3

오가는 메시지 두 통

요청과 응답, 그리고 응답 안의 상태 코드.

SP가 IdP에게 보내는 로그인 요청

생각보다 단출합니다. 사용자가 누구인지는 적지 않습니다. “누군가 우리 서비스에 오려고 하니 확인해 달라”는 내용이 전부입니다.

<samlp:AuthnRequest
    ID="_req_88b1"
    IssueInstant="2026-09-18T01:22:05Z"
    Destination="https://sso.mycompany.com/idp/SSO"
    AssertionConsumerServiceURL="https://app.example.com/saml/acs"
    ProtocolBinding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST">
  <saml:Issuer>https://app.example.com/sp</saml:Issuer>
  <samlp:NameIDPolicy Format="...:emailAddress" AllowCreate="true"/>
</samlp:AuthnRequest>
ID
SP가 기억해 두는 요청 번호. 응답의 InResponseTo와 대조합니다
Destination
이 요청을 받아야 할 IdP 주소. 다른 IdP로 전달되는 것을 막습니다
ACS URL
응답을 돌려받을 주소. IdP는 메타데이터에 등록된 값과 같은지 확인해야 합니다
ProtocolBinding
응답을 어떤 방식으로 보낼지 지정. 대개 HTTP-POST입니다
여기서 IdP가 반드시 해야 할 일 — 요청에 적힌 ACS URL을 그대로 믿으면 안 됩니다. 등록된 주소 목록에 없는 URL이 들어왔는데도 그리로 Assertion을 보내면, 공격자가 자기 서버로 증명서를 받아 갈 수 있습니다. 화이트리스트 검증이 필수입니다.

IdP가 돌려주는 응답

바깥 껍데기가 Response이고, 그 안에 1편에서 뜯어본 Assertion이 들어 있습니다. 서명은 Response 전체에 걸 수도, Assertion에만 걸 수도, 둘 다에 걸 수도 있습니다.

<samlp:Response ID="_resp_92f1" InResponseTo="_req_88b1"
                Destination="https://app.example.com/saml/acs">
  <saml:Issuer>https://sso.mycompany.com/idp</saml:Issuer>
  <ds:Signature> ... </ds:Signature>
  <samlp:Status>
    <samlp:StatusCode Value="...:status:Success"/>
  </samlp:Status>
  <saml:Assertion> ... 1편에서 본 그 내용 ... </saml:Assertion>
</samlp:Response>
서명 위치는 3편의 핵심 주제입니다. “Response에 서명이 있으니 통과”라고 판단했다가 안쪽 Assertion이 바꿔치기된 것을 놓치는 공격이 존재합니다. 지금은 “서명이 어디에 걸렸는지를 따지는 게 중요하다”는 감각만 가져가시면 됩니다.

로그인이 실패했을 때 오는 코드

인증 실패도 정상적인 SAML 응답으로 돌아옵니다. HTTP 401이 아니라 Status 안의 코드로 이유를 알려줍니다. 장애 대응할 때 가장 먼저 봐야 할 값입니다.

StatusCode의미주로 이럴 때
Success인증 성공정상
Requester요청한 쪽(SP) 잘못Issuer 불일치, 등록 안 된 ACS URL, 잘못된 요청 형식
Responder응답하는 쪽(IdP) 문제IdP 내부 오류, 사용자 계정 비활성
AuthnFailed인증 실패비밀번호 틀림, MFA 실패
NoPassive조용한 인증 불가IsPassive 요청인데 로그인 화면이 필요한 상황
InvalidNameIDPolicy식별자 형식 불일치SP는 이메일을 요구했는데 IdP 설정이 다른 형식일 때

바인딩 세 가지

같은 메시지를 무엇에 실어 보낼 것인가의 선택.

1편에서 바인딩은 “전송 수단”이라고 했습니다. 이제 왜 요청과 응답이 서로 다른 수단을 쓰는지 보겠습니다. 이유는 의외로 단순합니다. 길이 때문입니다.

URL 뒤에 붙여 보내기

메시지를 압축해서 URL 쿼리스트링에 담고, 302 리다이렉트로 브라우저를 보냅니다. 브라우저 주소창에 그대로 보이는 방식입니다.

HTTP/1.1 302 Found
Location: https://sso.mycompany.com/idp/SSO
   ?SAMLRequest=fZJPb8IwDMW%2FSpV7m6R%2FKERQiSFNQtq0aew...
   &RelayState=%2Fwiki%2Fops-runbook
   &SigAlg=http%3A%2F%2Fwww.w3.org%2F2001%2F04%2Fxmldsig-more%23rsa-sha256
   &Signature=Qm9iIHdhcyBoZXJl...
주로 쓰는 곳
AuthnRequest (SP → IdP)
인코딩
Deflate 압축 → Base64 → URL 인코딩
서명 방식
XML 안이 아니라 쿼리 파라미터로 따로 붙음
한계
URL 길이 제한. Assertion처럼 큰 문서는 담기 어렵습니다

자동 제출되는 HTML 폼으로 보내기

IdP가 hidden 필드에 값을 넣은 HTML 폼을 내려주고, 자바스크립트가 즉시 제출합니다. 사용자 눈에는 흰 화면이 잠깐 깜빡이는 것으로만 보입니다.

<body onload="document.forms[0].submit()">
  <form method="POST" action="https://app.example.com/saml/acs">
    <input type="hidden" name="SAMLResponse" value="PHNhbWxwOl..."/>
    <input type="hidden" name="RelayState" value="/wiki/ops-runbook"/>
  </form>
</body>
주로 쓰는 곳
Response / Assertion (IdP → SP)
인코딩
Base64만. 압축하지 않습니다
서명 방식
XML 문서 안에 ds:Signature로 포함
장점
길이 제한이 사실상 없고, 주소창 기록·리퍼러에 남지 않습니다
그래서 조합이 이렇게 굳어졌습니다 — 요청은 짧으니 Redirect로, 응답은 크고 민감하니 POST로. 연동 가이드 대부분이 이 조합을 전제로 쓰여 있습니다.

내용 대신 보관함 번호표만 보내기

IdP가 Assertion 자체를 브라우저에 주지 않고, 짧은 참조값(Artifact)만 건넵니다. SP는 그 번호표를 들고 IdP에 직접 서버 대 서버로 접속해서 실물을 받아옵니다.

1) IdP → 브라우저 → SP :  SAMLart=AAQAAM9w7Rz...  (짧은 참조값)
2) SP  →  IdP  (직접 통신, SOAP)  :  "이 번호표의 실물을 주세요"
3) IdP →  SP   (직접 통신)        :  <saml:Assertion> ... </saml:Assertion>
장점
Assertion이 브라우저를 거치지 않아 노출 위험이 낮습니다
단점
SP와 IdP 사이에 직접 통신 경로(백 채널)가 필요합니다
현실
방화벽·네트워크 제약 때문에 SaaS 연동에서는 거의 쓰이지 않습니다
쓰이는 곳
금융·공공처럼 보안 요구가 높고 양쪽 망이 연결된 환경
면접 포인트 — “세 가지 바인딩을 아느냐”보다 “왜 Artifact는 실무에서 잘 안 쓰이느냐”를 설명할 수 있는 쪽이 훨씬 인상적입니다. 답은 프론트 채널만으로 동작한다는 SAML의 장점을 Artifact가 포기하기 때문입니다.

실습: Redirect 바인딩 인코딩 파이프라인

1편의 Base64 디코더가 통하지 않던 이유를 직접 확인합니다.

HTTP-Redirect 바인딩은 URL에 담아야 하므로 크기를 줄여야 합니다. 그래서 세 단계를 거칩니다. 아래에서 실제로 변환을 실행하고, 각 단계에서 길이가 어떻게 변하는지 보세요.

왜 압축을 먼저 하나 — XML은 태그가 반복되는 구조라 압축률이 아주 좋습니다. 보통 원본의 3분의 1 이하로 줄어듭니다. 압축 없이 Base64만 하면 오히려 길이가 33% 늘어나서 URL 제한에 걸립니다. 순서가 바뀌면 안 되는 이유입니다.
디코딩할 때의 함정 — Redirect로 온 SAMLRequest를 Base64만 풀면 알아볼 수 없는 바이트가 나옵니다. URL 디코딩 → Base64 디코딩 → Deflate 해제 순으로 되돌려야 XML이 보입니다. 표준 zlib이 아니라 헤더 없는 raw deflate라는 점도 도구를 고를 때 주의할 부분입니다.

RelayState — 원래 가려던 곳 기억하기

작지만 사용자 경험을 좌우하는 값입니다.

사용자가 운영 런북 페이지 링크를 받아 클릭했는데 로그인이 필요합니다. 로그인을 마친 뒤 홈 화면으로 떨어진다면 링크를 다시 찾아 눌러야 합니다. 이 불편을 없애는 값이 RelayState입니다. SAML 메시지 바깥에 붙어 다니는, 단순한 문자열 하나입니다.

https://wiki.example.com/ops-runbook
    보안 주의 — RelayState는 서명 대상이 아니거나, 서명되더라도 내용 검증은 SP의 몫입니다. 여기에 외부 주소가 들어오면 로그인 직후 사용자를 공격자 사이트로 보내는 오픈 리다이렉트가 됩니다. 반드시 자기 도메인 내부 경로인지 검사하거나, 값 자체를 서버 세션에 저장해 두고 키만 주고받는 방식을 쓰세요.
    IdP-initiated에서는 사용자가 어디로 가려 했는지 알 수 없으므로 RelayState가 비어 있거나, IdP 설정에 적어 둔 고정 페이지 값이 들어갑니다. 2장에서 “원래 페이지 복귀가 고정된다”고 했던 이유가 이것입니다.
    7

    로그아웃은 왜 이렇게 어려운가

    SAML 운영에서 가장 자주 포기하게 되는 기능.

    로그인은 한 번으로 여러 서비스를 열었는데, 로그아웃은 그렇게 되지 않습니다. 이유는 세션이 여러 곳에 흩어져 있기 때문입니다. IdP에 하나, 그리고 로그인한 SP마다 하나씩. SLO(Single Logout)는 이 세션들을 한꺼번에 끊으려는 시도입니다.

    브라우저를 순회시키는 방식

    IdP가 로그인된 SP들을 하나씩 리다이렉트로 돌면서 로그아웃 요청을 전달합니다. 사용자 화면이 여러 사이트를 빠르게 거쳐 갑니다.

    IdP → SP1 (로그아웃) → IdP → SP2 (로그아웃) → IdP → SP3 ... → 완료 화면
    장점
    별도 네트워크 경로가 필요 없습니다
    깨지는 지점
    중간의 한 SP가 응답하지 않으면 그 뒤 SP들은 로그아웃되지 않고 흐름이 멈춥니다
    또 깨지는 지점
    사용자가 순회 도중 탭을 닫으면 나머지는 그대로 로그인 상태로 남습니다

    서버끼리 직접 알리는 방식

    IdP가 각 SP의 로그아웃 엔드포인트를 서버에서 직접 호출합니다. 사용자 브라우저는 관여하지 않습니다.

    장점
    사용자 행동과 무관하게 동작하고, 실패를 IdP가 인지할 수 있습니다
    전제 조건
    IdP에서 모든 SP로 직접 접속 가능한 네트워크 경로
    현실
    사내 IdP가 인터넷 SaaS를 호출해야 하므로 방화벽 정책이 필요하고, 지원하지 않는 SP도 많습니다
    MSP 실무에서의 현실적인 답 — SLO를 완벽하게 만들려고 시간을 쓰기보다, 세션 수명을 짧게 가져가는 쪽이 대체로 효과적입니다. 퇴사자·사고 대응처럼 즉시 차단이 필요한 상황에서는 SLO에 기대지 말고 IdP에서 계정을 비활성화하고 세션을 무효화하세요. 다만 SP에 이미 발급된 세션 쿠키는 그 SP의 만료 정책을 따르므로, 중요한 서비스일수록 세션 유효시간을 짧게 잡아두는 설계가 필요합니다.
    8

    장애 났을 때 어디를 보는가

    증상을 눌러 원인과 확인 순서를 펼쳐 보세요.

    SAML 장애는 대부분 같은 몇 가지 원인에서 반복됩니다. 증상만 보고 어느 단계가 깨졌는지 짚을 수 있으면 대응 시간이 크게 줄어듭니다. 아래는 현장에서 가장 자주 마주치는 것들입니다.

    가장 먼저 할 일은 언제나 같습니다 — 브라우저 개발자 도구에서 Network 탭을 열고 “Preserve log”를 켠 다음 로그인을 다시 시도하세요. 리다이렉트가 여러 번 일어나기 때문에 이 옵션을 켜지 않으면 기록이 지워집니다. 그다음 SAMLRequest와 SAMLResponse 값을 꺼내 디코딩하면, 문제가 요청 쪽인지 응답 쪽인지가 거의 바로 드러납니다.
    9

    이해도 점검

    7문항입니다. 답을 고르면 바로 해설이 나옵니다.

    아직 푼 문제가 없습니다

    2편에서 챙겨 갈 것

    • SP와 IdP는 직접 통신하지 않는다. 모든 메시지는 브라우저가 실어 나르는 프론트 채널 방식이다.
    • SP-initiated는 요청 ID를 대조할 수 있어 안전하고, IdP-initiated는 그 대조가 원천적으로 불가능하다.
    • AuthnRequest에 적힌 ACS URL을 IdP가 무조건 믿으면 안 된다. 등록된 주소인지 확인해야 한다.
    • 요청은 Redirect(압축+URL), 응답은 POST(폼) — 길이와 민감도 때문에 굳어진 조합이다.
    • Redirect 바인딩은 Deflate → Base64 → URL 인코딩 순서이고, 되돌릴 때는 역순이다.
    • RelayState는 검증되지 않은 외부 입력으로 다뤄야 한다. 오픈 리다이렉트의 흔한 통로다.
    • SLO는 자주 깨진다. 즉시 차단이 필요하면 IdP 계정 비활성화와 짧은 세션 수명으로 대응하는 편이 현실적이다.
    • 장애 대응의 출발점은 Preserve log를 켜고 SAMLRequest·SAMLResponse를 디코딩해 보는 것이다.

    3편에서는

    지금까지 “검증해야 한다”고 여러 번 미뤄 둔 이야기를 정면으로 다룹니다. 서명이 걸린 위치를 속이는 XML Signature Wrapping, IdP의 개인키가 유출됐을 때 벌어지는 Golden SAML, 그리고 SP가 반드시 확인해야 할 검증 항목 체크리스트를 순서대로 정리합니다. 인증서 만료와 롤오버 절차도 여기서 다룹니다.
