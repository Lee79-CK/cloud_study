텔레메트리 파이프라인 위에 경계선을 긋는 법

OpenTelemetry 도입이 어그러지는 이유는 기술이 어려워서가 아닙니다. 앱 코드부터 대시보드까지 이어지는 한 줄기 파이프라인에서 어디까지가 개발자의 일이고 어디부터가 클라우드 엔지니어의 일인지 아무도 정하지 않은 채 시작하기 때문입니다. 이 강의는 그 경계선을 먼저 그립니다.

왼쪽 끝은 순수하게 개발자의 코드, 오른쪽 끝은 순수하게 엔지니어의 인프라입니다. 문제는 가운데 세 지점 — SDK 설정, OTLP 전송, 대시보드 — 이 어느 쪽도 완전히 소유하지 않는다는 점입니다. 이 강의 전체가 바로 그 가운데를 다룹니다.

SECTION 01

왜 지금 OpenTelemetry인가

결론부터 말하면, OpenTelemetry(이하 OTel)는 계측(instrumentation)과 백엔드를 분리하는 표준입니다. 한 번 계측해 두면 데이터를 어디로 보낼지는 나중에, 코드를 건드리지 않고 바꿀 수 있습니다.

표준이 없던 시절의 비용

2020년경의 전형적인 상황을 떠올려 봅시다. 고객사 A는 Datadog, 고객사 B는 New Relic, 고객사 C는 자체 구축한 Jaeger를 씁니다. MSP 입장에서는 같은 Spring Boot 애플리케이션에 서로 다른 벤더 에이전트를 세 번 붙이는 작업이 됩니다. 그리고 고객사 A가 비용 문제로 벤더를 바꾸겠다고 하면, 앱 개발팀의 코드 수정 일정부터 잡아야 합니다.

벤더 에이전트 방식의 문제

계측 코드가 특정 벤더의 라이브러리에 묶입니다. 벤더를 바꾸려면 애플리케이션 코드와 빌드 파이프라인을 모두 손봐야 하고, 이건 인프라 작업이 아니라 개발 프로젝트가 됩니다.

OTel 방식

앱은 OTLP라는 표준 형식으로 내보내기만 합니다. 목적지 변경은 Collector 설정 파일 한 줄 수정으로 끝나고, 이건 엔지니어의 운영 작업입니다.

MSP 관점에서의 실익

고객사마다 백엔드가 달라도 계측 표준과 운영 절차는 하나로 통일할 수 있습니다. 엔지니어는 고객사별로 Collector 설정만 다르게 가져가고, 앱 개발팀에게 주는 온보딩 가이드는 전 고객사 공통이 됩니다. 신규 고객사 온보딩 시간이 줄어드는 지점이 바로 여기입니다.

OTel이 실제로 제공하는 것

  • 명세(Specification) — 신호가 어떤 모양이어야 하는지 정의한 문서. 구현이 아니라 규칙입니다.
  • API — 라이브러리 개발자가 의존하는 최소 인터페이스. SDK가 없으면 아무 일도 하지 않습니다(no-op).
  • SDK — API의 실제 구현체. 샘플링, 배치, 전송을 담당합니다. 애플리케이션이 선택해서 넣습니다.
  • 계측 라이브러리 — Spring, Django, Express 같은 프레임워크에 자동으로 훅을 거는 코드 모음.
  • OTLP — gRPC/HTTP 기반 전송 규약. 이것 덕분에 SDK와 백엔드가 서로를 몰라도 됩니다.
  • Collector — 텔레메트리를 받고, 가공하고, 내보내는 독립 프로세스. 엔지니어의 주 무대입니다.
API와 SDK를 나눈 이유

API가 no-op 기본값을 갖기 때문에, 오픈소스 라이브러리가 OTel API로 계측 코드를 심어도 그 라이브러리를 쓰는 애플리케이션이 OTel을 안 쓰면 아무 비용이 발생하지 않습니다. 이 설계가 있어서 생태계 전체가 OTel을 내장하는 방향으로 움직일 수 있었습니다.

SECTION 02

모니터링과 관측 가능성은 무엇이 다른가

자주 나오는 구분이지만 실무 감각으로 옮겨 놓지 않으면 말장난으로 끝납니다. 핵심은 질문을 미리 정해 두었는가입니다.

모니터링 — 예상한 질문에 답한다

CPU가 80%를 넘었는가, 5xx 비율이 1%를 넘었는가. 물어볼 질문을 미리 정하고 그에 맞는 지표와 임계값을 세팅합니다. 답이 빠르고 비용이 예측 가능합니다.

관측 가능성 — 예상 못한 질문에 답한다

"특정 고객사 테넌트에서만, 결제 API가, 오후 2시 이후에 느린 이유"처럼 사전에 정의한 적 없는 질문을 사후에 던질 수 있는 상태. 데이터가 충분히 세밀해야 가능합니다.

네 가지 상황으로 나눠 보기

각 칸을 눌러 실제 사례를 확인하세요.

알고 있고, 알고 있다고 아는 것

대시보드에 이미 올려둔 것들. 모니터링의 영역.

예: API 서버 CPU 사용률, 초당 요청 수, DB 커넥션 풀 사용량. 클라우드 엔지니어가 세팅하는 기본 대시보드가 여기에 해당합니다.

모른다는 것을 아는 것

궁금한데 지표가 없는 것. 추가 계측으로 해결.

예: "결제 모듈 안에서 외부 PG 호출이 차지하는 시간이 얼마지?" 질문은 명확하지만 데이터가 없습니다. 개발자가 수동 계측으로 Span을 추가하면 해결됩니다(5편).

알고 있지만 인지하지 못한 것

데이터는 있는데 아무도 안 보는 것.

예: 로그에 이미 타임아웃 재시도가 하루 4만 건 찍히고 있는데 알림이 없어 아무도 모릅니다. 신호를 연결하고 SLO를 거는 일(11편)이 여기를 메웁니다.

모른다는 것조차 모르는 것

진짜 장애가 사는 곳. 관측 가능성이 필요한 이유.

예: 특정 고객사 테넌트만, 특정 리전의 노드에 스케줄링됐을 때만, 커넥션 재사용이 깨져 지연이 3배가 됩니다. 이런 조합은 사전에 대시보드로 만들 수 없습니다. 고카디널리티 속성이 붙은 분산 트레이스가 있어야 사후에 파고들 수 있습니다.

그런데 여기서 갈등이 시작됩니다

"사후에 아무 질문이나 던지려면 데이터가 세밀해야 한다"는 개발자의 요구와, "세밀할수록 저장 비용이 기하급수로 늘어난다"는 엔지니어의 현실이 정면으로 충돌합니다. 이 충돌을 관리하는 것이 샘플링 정책이고, 9편과 10편의 주제입니다. 지금 기억할 것은 이 긴장이 구조적이며, 감정 문제가 아니라 협상 대상이라는 점입니다.

SECTION 03

네 가지 신호

OTel은 텔레메트리를 신호(signal) 단위로 나눠 정의합니다. 각 신호는 서로 다른 질문에 답하도록 설계되었고, 진짜 가치는 이들이 하나의 문맥으로 연결될 때 나옵니다.

Trace 요청이 어디에서 시간을 썼는가 Stable

하나의 요청이 여러 서비스를 거치며 남기는 작업 단위(Span)의 나무 구조입니다. 사용자가 주문 버튼을 눌렀을 때 BFF → 주문 서비스 → 재고 서비스 → DB로 이어지는 호출이 각각 얼마나 걸렸는지 하나의 화면에서 보여줍니다.

  • Span — 이름, 시작·종료 시각, 속성, 상태를 가진 작업 하나
  • Trace ID — 전체 요청을 식별하는 값. 모든 Span이 공유
  • 컨텍스트 전파 — 서비스 간에 traceparent 헤더로 Trace ID를 넘기는 일. 이게 끊기면 트레이스가 조각납니다

MSP 현장에서 가장 자주 마주치는 증상이 "트레이스가 두 조각으로 나뉘어 보인다"입니다. 원인은 보통 코드 레벨의 컨텍스트 유실(개발자 영역)이거나 프록시·게이트웨이가 헤더를 지운 것(엔지니어 영역)입니다.

Metric 비율·건수·백분위가 시간에 따라 어떻게 변했는가 Stable

일정 주기로 집계된 숫자 시계열입니다. 개별 요청의 사연은 없지만 전체 추세를 싸게 오래 보관할 수 있습니다. 알림과 SLO의 기반이 되는 신호입니다.

  • Counter — 누적만 증가 (총 요청 수, 에러 수)
  • UpDownCounter — 증가·감소 모두 (활성 커넥션 수, 큐 길이)
  • Histogram — 값의 분포 (응답 시간 p50/p95/p99)
  • Gauge — 특정 시점의 관측값 (현재 메모리 사용량)

메트릭 비용은 저장한 데이터 크기가 아니라 시계열 개수로 결정됩니다. 속성 하나를 잘못 붙이면 시계열이 수천 배로 늘어납니다. 6편에서 자세히 다룹니다.

Log 애플리케이션이 무슨 일이 있었다고 말했는가 Stable

시점과 메시지를 가진 기록입니다. 가장 익숙하지만 OTel에서의 위치는 조금 다릅니다. OTel은 로그를 새로 만들기보다 기존 로깅 체계를 감싸서 Trace ID를 붙이는 접근을 택했습니다.

  • Logback, Python logging, Pino 같은 기존 라이브러리를 그대로 쓰되 trace_id·span_id를 주입
  • 그 결과 트레이스 화면에서 해당 요청의 로그만 바로 필터링 가능
  • 수집 경로는 두 가지 — SDK가 직접 전송하거나, 컨테이너 stdout을 Collector가 파일에서 읽어가거나

"어느 경로로 로그를 모을 것인가"는 대표적인 회색지대입니다. 정하지 않고 두면 팀마다 제각각 구현하고, 나중에 통합이 안 됩니다.

Profile 어떤 코드가 CPU와 메모리를 썼는가 Alpha

실행 중인 프로세스의 스택을 주기적으로 샘플링해 자원을 소모한 함수를 드러내는 신호입니다. 2026년 3월 Profiling SIG가 public alpha를 공식화했고, Collector는 v0.148.0부터 이 데이터를 다룹니다.

  • 트레이스가 "이 구간이 느리다"까지 알려준다면, 프로파일은 "그 구간에서 이 함수가 CPU를 먹었다"까지 내려갑니다
  • 샘플이 캡처된 시점의 Trace·Span과 연결되도록 설계되어, 느린 Span에서 코드로 바로 이동할 수 있습니다
  • 기존에는 벤더마다 독자 에이전트와 포맷을 썼는데, 이를 표준화한 것이 이번 신호의 의미입니다
도입 판단

alpha 단계는 API가 예고 없이 바뀔 수 있다는 뜻입니다. 고객사 운영 환경에 기본으로 넣을 단계는 아니고, 별도 검증 환경에서 평가하는 정도가 적절합니다. 10편에서 도입 기준을 따로 다룹니다.

신호는 따로 있을 때보다 연결됐을 때 강해집니다

실제 장애 대응은 보통 이렇게 흐릅니다. 메트릭 알림이 울리고(p99 지연 급증) → 그 시간대의 느린 트레이스를 찾아 어느 서비스 구간인지 좁히고 → 해당 Span의 Trace ID로 로그를 필터링해 예외 메시지를 확인합니다. 이 이동이 매끄러우려면 세 신호가 같은 Trace ID와 같은 리소스 속성을 공유해야 합니다. 그래서 2편의 시맨틱 컨벤션이 중요합니다.

SECTION 04

데이터는 어떤 경로로 흐르는가

히어로의 7단계를 이제 기술적으로 풀어봅니다. 이 흐름도를 머릿속에 정확히 그려두면 앞으로 나올 모든 내용이 "이 그림의 어느 지점 이야기인가"로 정리됩니다.

Collector를 왜 중간에 두는가

애플리케이션 SDK가 백엔드로 직접 보내는 구성도 가능합니다. 다만 그렇게 하면 다음이 전부 애플리케이션 책임이 됩니다.

  • 백엔드 주소·인증 정보를 앱이 알고 있어야 함 → 백엔드 교체 시 앱 재배포
  • 백엔드가 잠시 죽으면 앱이 재시도와 버퍼링을 감당해야 함
  • 민감정보 마스킹, 샘플링 정책 변경이 코드 변경이 됨
  • 쿠버네티스 메타데이터(파드명, 네임스페이스)를 앱이 스스로 알아내야 함

Collector를 끼우면 이 모든 것이 인프라 설정 영역으로 넘어옵니다. 앱은 "옆에 있는 Collector로 보낸다"만 알면 됩니다. 이것이 경계선의 물리적 실체입니다.

Agent와 Gateway

Agent — 노드마다 하나

쿠버네티스에서는 DaemonSet으로 각 노드에 배치합니다. 앱과 물리적으로 가까워 전송이 빠르고, 노드·파드 메타데이터를 붙이기 좋습니다. 7·8편의 주제.

Gateway — 클러스터당 소수

Deployment로 띄워 여러 Agent의 데이터를 모읍니다. 테일 샘플링처럼 한 트레이스의 모든 Span을 한곳에서 봐야 하는 처리를 여기서 합니다. 9편의 주제.

애플리케이션이 실제로 설정하는 것

자동 계측을 쓰면 개발자가 만질 것은 사실상 환경 변수 몇 개입니다. 아래는 언어와 무관하게 동일하게 동작하는 표준 변수들입니다. 

# 이 서비스의 이름 — 모든 신호에 리소스 속성으로 붙습니다
OTEL_SERVICE_NAME=order-api

# 어디로 보낼 것인가 — 보통 같은 노드의 Collector
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317
OTEL_EXPORTER_OTLP_PROTOCOL=grpc

# 서비스를 식별하는 추가 속성
OTEL_RESOURCE_ATTRIBUTES=service.version=1.4.2,deployment.environment=prod

# 샘플링 — 부모 결정을 따르되 루트는 10%만
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1
여기서 첫 번째 경계 질문

위 변수들을 누가 정하고 누가 넣습니까? OTEL_SERVICE_NAME은 개발팀이 정할 일이지만, 조직 전체 명명 규칙을 어기면 트레이스가 깨집니다. OTEL_EXPORTER_OTLP_ENDPOINT는 엔지니어가 제공하는 주소이고, OTEL_TRACES_SAMPLER_ARG는 비용을 부담하는 쪽이 결정해야 합니다. 하나의 설정 블록 안에 세 가지 소유권이 섞여 있습니다. 이것이 회색지대가 생기는 구조적 이유입니다.

포트 참고 — OTLP/gRPC는 4317, OTLP/HTTP는 4318이 표준입니다. 언어 SDK의 기본 프로토콜이 달라서 실무에서 자주 헷갈리는 지점입니다(4편).

SECTION 06

2026년 현재 위치

기술 선택에서 가장 중요한 질문은 "이게 지금 프로덕션에 써도 되는가"입니다. OTel은 그 답을 성숙도 라벨로 명시합니다.

2019
OpenTracing과 OpenCensus가 합쳐지다

경쟁하던 두 표준이 하나로 통합되며 OpenTelemetry가 출범했습니다. 표준이 둘이면 표준이 아니라는 문제를 정면으로 해결한 사건입니다.

2021 — 2024
트레이스 → 메트릭 → 로그 순으로 안정화

신호마다 experimental → stable 단계를 따로 밟았습니다. 그래서 같은 SDK 안에서도 신호별 성숙도가 달랐던 시기가 있었습니다.

2026년 3월
프로파일 신호가 public alpha 진입

Profiling SIG가 네 번째 신호의 공개 알파를 발표했고, Collector v0.148.0부터 관련 수신·처리 기능이 들어갔습니다.

2026년 5월
CNCF Graduated 프로젝트로 승격

Kubernetes, Prometheus와 같은 등급이 되었습니다. 고객사 기술 검토 자리에서 "성숙도가 검증되지 않았다"는 반론을 받을 일이 사실상 사라졌습니다.

신호별 성숙도

신호답하는 질문상태프로덕션 도입
Trace요청 경로에서 시간이 어디로 갔나Stable권장
Metric비율·건수·p99가 어떻게 변했나Stable권장
Log애플리케이션이 무엇을 말했나Stable권장
Profile어떤 코드가 자원을 썼나Alpha검증 환경에서 평가
성숙도 라벨 읽는 법

Stable은 하위 호환을 약속한다는 뜻입니다. 마이너 버전을 올려도 컴파일·런타임 오류가 나지 않아야 합니다. Beta는 동작하지만 바뀔 수 있고, Alpha는 프로토타입 용도입니다. 고객사에 제안서를 쓸 때 이 라벨을 그대로 인용하면 기술 리스크 설명이 훨씬 수월해집니다.
