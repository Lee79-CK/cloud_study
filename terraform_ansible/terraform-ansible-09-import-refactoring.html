Terraform & Ansible 강의 · Level 2 Terraform 심화·운영 · 9편 / 26편 · 시리즈 목차

이미 있는 것을 코드로 기존 인프라 가져오기와 리팩터링 — import 블록, 코드 생성, terraform query, 드리프트, moved·removed

MSP가 새 고객사를 맡을 때, 인프라는 대개 빈 계정이 아니라 몇 년 동안 콘솔로 쌓인 리소스 더미입니다. 그것을 지우고 새로 만들 수는 없습니다. 운영 중인 서비스이기 때문입니다. 이번 편은 실물은 그대로 두고 장부(state)와 설계도(코드)만 새로 만드는 방법, 즉 기존 리소스를 Terraform 관리로 흡수하는 실전 절차를 다룹니다. 1편 1장의 “클릭 운영의 하루”를 끝내는 실제 작업입니다.

import

실물을 state에 연결. 실물은 바뀌지 않는다.

moved · removed

실물은 두고 코드 구조·관리 범위를 바꾼다.

refresh-only

실물이 코드 밖에서 바뀐 것(드리프트)을 찾는다.

0들어가며

이번 편의 목표와 실습 지도

이번 편을 마치면

  • import 블록으로 기존 리소스를 state에 연결하고, plan의 “will be imported”, “1 to import” 표시를 해석할 수 있습니다.
  • -generate-config-out으로 코드 초안을 만들고, 그대로 쓰면 안 되는 부분을 정리할 수 있습니다.
  • for_each import(1.7+)와 1.16의 모듈 안 import 블록을 씁니다.
  • 1.14의 terraform query로 관리되지 않는 리소스를 찾고 대량으로 가져오는 흐름을 압니다.
  • 콘솔로 만들어진 고객사 리소스를 흡수하는 8단계 절차를 실행하고, 목표인 “가져온 직후 변경 0”을 확인합니다.
  • plan -refresh-only와 -detailed-exitcode로 드리프트를 찾고, 수용·되돌림·무시 중 무엇을 할지 판단합니다.
  • 가져온 리소스를 moved로 모듈 안에 넣고, removed로 관리 범위에서 넘겨줍니다.

실측 표시

import 블록·코드 생성·for_each import·불일치 import·moved와 import가 겹칠 때의 동작은 내장 리소스(terraform_data)로 호환 엔진에서 실제로 실행한 결과입니다. 모듈 안 import 블록은 Terraform 1.16 기능이라 호환 엔진에서는 실행할 수 없었고(오류로 거부됨을 확인), 공식 발표 내용을 기준으로 작성했습니다. AWS 실습 B는 이 강의 제작 환경에서 실행할 수 없었으므로 처음 실행할 때 결과를 확인하세요.

1import가 하는 일

장부에 한 줄 적는 것 — 실물도 코드도 저절로 생기지 않는다

5편에서 state는 “코드의 주소 ↔ 실물의 ID”를 잇는 장부라고 했습니다. import는 이 장부에 새 줄을 적는 일입니다. “코드의 aws_security_group.legacy_web은 클라우드의 sg-0123…이다.” 그 결과로 Terraform은 그 실물을 자기 것으로 인식하고, 이후 plan에서 코드와 비교하기 시작합니다.

import 전import 후
클라우드의 실물있음그대로 (import는 실물을 바꾸지 않는다)
state없음주소 ↔ ID 기록 + 현재 속성
코드직접 써야 함직접 써야 함 (또는 4장의 생성 기능으로 초안)
다음 plan—코드 ↔ 실물 비교. 다르면 코드 쪽으로 바꾸려 한다
가장 위험한 순간은 import 직후의 apply

코드가 실물을 정확히 묘사하지 못한 채 import하면, 다음 apply가 실물을 코드대로 “고친다”. 운영 중인 보안 그룹 규칙이 지워지거나 DB가 교체될 수 있습니다. 그래서 흡수 작업의 목표는 “가져온 직후 plan의 변경이 0”입니다. 실물을 개선하는 것은 그다음, 별도의 변경으로 합니다. 이 순서를 지키는 것이 이번 편 전체의 핵심입니다.

Terraform 밖의 생성 도구

Terraformer 같은 오픈소스 생성기, AWS CloudFormation의 IaC 생성기(CloudFormation 템플릿 생성) 등 계정 전체를 훑어 코드를 만들어 주는 도구도 있습니다. 시작점으로는 유용하지만 생성 코드는 대개 리소스마다 하드코딩된 값이 가득한 “사진”이라, 모듈·변수 구조로 다시 짜는 작업이 필요합니다. 도구의 유지보수 상태와 지원 프로바이더 버전도 먼저 확인하세요. 이 강의는 Terraform 자체 기능만으로 진행합니다.

3import 블록과 plan 읽기

두 줄짜리 블록 하나, 그리고 plan에 새로 생기는 표시들

import {
  to = aws_security_group.legacy_web # 코드의 주소 (resource 블록이 있어야 함, 4장의 생성 기능 제외)
  id = "sg-0123456789abcdef0"        # 프로바이더가 이해하는 실물 ID (리소스마다 형식이 다름)
}

resource "aws_security_group" "legacy_web" {
  name        = "legacy-web"
  description = "legacy web sg"
  vpc_id      = "vpc-0abc..."
}

4코드 초안 생성과 정리

생성된 코드는 “사진”이다 — 설계도로 다시 그려야 한다

import 블록만 쓰고 그 대상의 resource 블록을 쓰지 않은 채 -generate-config-out을 붙여 plan하면, Terraform이 실물의 현재 속성을 읽어 resource 블록 초안을 파일로 만들어 줍니다. 아래는 실습 A에서 실제로 생성된 파일입니다.

$ terraform plan -generate-config-out=generated.tf
  # terraform_data.legacy will be imported
  # (config will be generated)
  # (imported from "legacy-web-sg")
Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.
Warning: Config generation is experimental

$ cat generated.tf
# __generated__ by Terraform
# Please review these resources and move them into your main configuration files.

# __generated__ by Terraform from "legacy-web-sg"
resource "terraform_data" "legacy" {
  input            = null
  triggers_replace = null
}

(호환 엔진에서는 머리말이 “by OpenTofu”로 표시되었습니다.)

내장 리소스라 짧지만, AWS 리소스라면 수십 줄이 나옵니다. 생성 코드는 “현재 실물의 모든 속성을 그대로 적은 것”이라 다음을 정리해야 합니다.

정리 대상예어떻게
null·기본값 인자input = null, force_destroy = false, bucket_prefix = null지운다 (기본값과 같으면 생략해도 plan 변화 없음)
하드코딩된 참조vpc_id = "vpc-0abc…", security_group_id = "sg-…"다른 리소스·data·변수 참조로 바꾼다 (aws_security_group.legacy_web.id)
인라인 블록과 별도 리소스 중복보안 그룹의 ingress·egress 목록이 생성됨별도 규칙 리소스를 쓴다면 인라인 목록을 지운다(지워도 기존 규칙은 그대로 — 지정하지 않으면 관리하지 않음). 두 방식을 섞지 않는다(3편 5장)
계산 전용 속성arn, id, owner_id생성기가 대부분 빼 주지만, 남아 있으면 “설정할 수 없는 인자” 오류 → 지운다
반복 구조aws_…_rule.r_0, r_1, r_2for_each 리소스 + for_each import로 다시 쓴다 (5장)
태그제각각인 태그우선 실물 그대로. 표준 태그 적용은 “변경 0” 확인 다음 단계에서
파일 위치generated.tf내용을 주제별 파일로 옮기고 generated.tf는 삭제. 이미 있으면 생성 명령이 실패하므로 재생성 전 삭제
생성 기능의 한계

Terraform은 생성 기능이 아직 실험적이라는 경고를 냅니다. 프로바이더에 따라 서로 배타적인 인자를 함께 생성해 validate가 실패하기도 하고, API에서 읽을 수 없는 값(비밀번호 등)은 채우지 못합니다. for_each·count 대상과 모듈 안 대상은 생성하지 않습니다. 생성은 “빈 화면에서 시작하지 않게 해 주는 도구”일 뿐입니다.

5for_each·모듈 안 import

같은 종류 여러 개, 그리고 재사용 모듈이 품는 가져오기

for_each import (1.7+)

locals {
  legacy_sgs = { web = "sg-0aaa", db = "sg-0bbb" } # 키 → 실물 ID
}

import {
  for_each = local.legacy_sgs
  to       = aws_security_group.legacy[each.key] # 리소스의 for_each 키와 같은 키
  id       = each.value
}

resource "aws_security_group" "legacy" {
  for_each = local.legacy_sgs
  # ...
}
# 실측 (내장 리소스로 같은 구조)
  # terraform_data.sg["db"] will be imported
  # (imported from "sg-0bbb")
  # terraform_data.sg["web"] will be imported
  # (imported from "sg-0aaa")
Plan: 2 to import, 0 to add, 0 to change, 0 to destroy.
Apply complete! Resources: 2 imported, 0 added, 0 changed, 0 destroyed.

4편에서 배운 for_each 규칙이 그대로 적용됩니다. import의 for_each에 넣는 맵의 키는 plan 시점에 알려져야 하고, 리소스의 for_each 키와 일치해야 합니다. 발견 단계에서 얻은 ID 목록을 맵으로 만들 때, 키는 사람이 읽을 수 있는 이름(역할·용도)으로 짓습니다. 그 키가 영구적인 state 주소가 되기 때문입니다.

모듈 안 import 블록 (1.16)

1.15까지 import 블록은 루트 모듈에만 둘 수 있었습니다. 그래서 공통 모듈로 기존 리소스를 흡수하려면, 모듈을 쓰는 모든 루트가 module.x.aws_s3_bucket.this 같은 모듈 내부 주소를 알고 import 블록을 따로 써야 했습니다. 1.16부터는 모듈 작성자가 리소스 옆에 import 블록을 함께 둘 수 있고, 호출자는 기존 리소스의 이름만 넘기면 됩니다.

modules/legacy-bucket/main.tf (실습 B에서 사용)
# 이미 존재하는 버킷을 "가져와서" 관리하는 모듈 (1.16: 모듈 안 import 블록)
variable "existing_bucket_name" {
  description = "가져올 기존 버킷 이름"
  type        = string
}

variable "tags" {
  description = "버킷 태그"
  type        = map(string)
  default     = {}
}

resource "aws_s3_bucket" "this" {
  bucket = var.existing_bucket_name
  tags   = var.tags
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id

  versioning_configuration {
    status = "Enabled"
  }
}

# 호출자는 버킷 이름만 넘기면 된다. 모듈 내부 주소를 알 필요가 없다
import {
  to = aws_s3_bucket.this
  id = var.existing_bucket_name
}

import {
  to = aws_s3_bucket_versioning.this
  id = var.existing_bucket_name
}

output "bucket" {
  value = aws_s3_bucket.this.bucket
}
# 호출하는 쪽: 모듈 내부 주소를 몰라도 된다
module "archive_bucket" {
  source = "../../modules/legacy-bucket"

  existing_bucket_name = "legacy-archive-123456789012"
  tags                 = { Owner = "kim-legacy" }
}
조건설명
프로바이더가 import를 지원대상 리소스의 문서에 Import 절이 있어야 한다
ID가 plan 시점에 알려짐변수·고정 값. 같은 apply에서 만들어지는 리소스의 속성은 안 됨
설정이 실물을 정확히 묘사아니면 import와 동시에 변경이 계획된다(3장 불일치 사례)
모듈 인스턴스마다 평가count·for_each로 부른 모듈, 중첩 모듈도 인스턴스별로 각자의 ID로 가져온다
이미 관리 중이면대상이 이미 state에 있으면 import 블록은 무시된다(실측). 그래서 모듈 안에 import 블록을 계속 남겨 두어도, 처음 쓰는 고객에게만 가져오기가 일어난다
Terraform 1.16 전용 기능

OpenTofu(1.13)에서 같은 코드를 실행하면 모듈 안 import 블록을 Invalid import configuration 오류로 거부합니다(실측). 고객사가 OpenTofu를 쓰거나 Terraform 1.15 이하라면, 기존처럼 루트에서 to = module.archive_bucket.aws_s3_bucket.this로 import 블록을 씁니다. 모듈의 required_version을 >= 1.16으로 올려 두면 잘못된 버전에서의 사용을 init 단계에서 막을 수 있습니다.

6terraform query (1.14)

“무엇이 Terraform 밖에 있는가”를 코드로 검색하고, import 코드를 한 번에 만든다

import 블록을 쓰려면 먼저 ID를 알아야 합니다. 리소스가 수백 개면 콘솔과 CLI로 ID를 모으는 것부터가 일입니다. 1.14에서 추가된 terraform query는 .tfquery.hcl 파일의 list 블록으로 프로바이더에게 리소스 목록을 물어보고, 결과를 바로 import·resource 블록으로 생성할 수 있게 합니다.

discover.tfquery.hcl (일반 .tf 파일에는 provider 설정이 있어야 함)
list "aws_instance" "legacy_web" {
  provider = aws

  config {
    filter {
      name   = "tag:Owner"
      values = ["kim-legacy"]
    }
    filter {
      name   = "instance-state-name"
      values = ["running"]
    }
  }

  limit = 50
}
terraform query                                   # 결과를 화면에: 주소, 식별 값(계정·ID·리전), Name 태그
terraform query -generate-config-out=generated.tf # import 블록(identity 사용) + resource 블록 생성
# generated.tf 정리 → terraform plan (n to import, 0 to change 목표) → terraform apply
알아둘 점설명
프로바이더 지원이 필요list는 프로바이더가 “목록 조회(list resource)”를 구현한 리소스 종류만 가능합니다. 지원하지 않으면 Invalid list resource 오류. AWS 프로바이더는 지원 종류를 늘려 가는 중이므로 쓰려는 버전의 문서에서 List Resources 항목을 확인하세요
읽기 전용query 자체는 아무것도 바꾸지 않고 state에도 쓰지 않습니다. 발견용 스크립트처럼 안심하고 돌릴 수 있습니다
생성 결과는 identity 기반 import1.12의 식별자 import 형식으로 생성됩니다. 이름은 legacy_web_0, _1처럼 번호가 붙으므로, 정리 단계에서 의미 있는 이름이나 for_each 구조로 바꿉니다
필터가 핵심계정 전체를 한 번에 가져오지 말고 태그·상태·VPC 같은 필터로 범위를 좁혀 “이번 PR로 흡수할 묶음”을 만듭니다 (7장 2·3단계)
query가 없을 때의 발견 방법

태그로: aws resourcegroupstaggingapi get-resources(태그가 붙은 것만). 전 리전: AWS Resource Explorer. 구성 이력과 규정 준수: AWS Config의 리소스 인벤토리. 종류별 CLI: aws ec2 describe-security-groups --filters Name=vpc-id,Values=…. MSP는 고객사 인수 시 이 결과를 스프레드시트로 정리해 “흡수 대상 / 제외 / 폐기” 분류부터 고객과 합의합니다(7장).

7흡수 실전 절차 8단계

고객사의 콘솔 인프라를 코드로 옮기는 표준 절차 — 단계를 눌러 체크리스트를 확인하세요

절대 규칙 세 가지

① 가져오는 PR과 바꾸는 PR을 섞지 않는다. 가져오는 PR의 plan은 “n to import, 0 to add, 0 to change, 0 to destroy”여야 한다. ② plan에 교체(-/+)나 삭제가 하나라도 있으면 멈춘다. 코드가 실물을 잘못 묘사한 것이다. ③ 흡수가 끝나면 콘솔 쓰기 권한을 회수한다. 그러지 않으면 다음 주부터 드리프트가 다시 쌓인다(10장).

8실습 A: import 메커니즘 (0원)

내장 리소스로 import의 모든 동작을 먼저 손에 익힌다

terraform_data도 import를 지원합니다(ID만 가져오고 입력 값은 비어 있음). 클라우드 없이 import 블록의 동작을 확인하기에 충분합니다. 아래 다섯 단계는 모두 실제 실행 결과입니다.

mkdir -p ~/iac-lab/terraform/09-basics && cd ~/iac-lab/terraform/09-basics

  id = "cache-001"
}

resource "terraform_data" "cache" {
  input = "redis"

관찰 1: “1 to import, 1 to change”

가져오면서 동시에 바꾸겠다는 뜻입니다. 실물(입력 없음)과 코드(input = "redis")가 다르기 때문입니다. 실제 리소스였다면 7장 규칙 ②에 따라 멈추고, 코드를 실물에 맞춘 뒤 다시 plan해야 합니다.

관찰 2: 남아 있는 import 블록

apply 후 import 블록을 지우지 않아도 plan은 No changes였습니다. 이미 관리 중인 주소의 import는 무시됩니다(실측: ID를 다른 값으로 바꿔 놓아도 경고 없이 무시). 기록으로 남겨도 되지만, 틀린 ID가 남아 있어도 알려 주지 않으므로 흡수 PR 병합 후 정리하는 편이 깔끔합니다.

terraform destroy -auto-approve                     # 내장 리소스라 실물 없음, 정리만

10드리프트 감지와 처리

흡수는 한 번, 드리프트와의 싸움은 계속

흡수가 끝난 뒤에도 누군가 콘솔에서 무언가를 바꿉니다. 1편 6장의 드리프트입니다. Terraform은 plan을 할 때마다 refresh로 실물을 읽으므로 드리프트를 볼 수 있지만, 일반 plan은 “코드 변경”과 “드리프트”를 한 화면에 섞어 보여 줍니다. 드리프트만 따로 보려면 -refresh-only를 씁니다.

# 누군가 콘솔에서 버킷 태그를 바꿨다고 하자
aws s3api put-bucket-tagging --bucket legacy-reports-$(aws sts get-caller-identity --query Account --output text) \
  --tagging 'TagSet=[{Key=Owner,Value=lee-changed}]'

terraform plan -refresh-only          # 코드는 보지 않고, state와 실물의 차이만
#   Note: Objects have changed outside of Terraform
#   ~ resource "aws_s3_bucket" "reports" {
#       ~ tags = { ~ "Owner" = "kim-legacy" -> "lee-changed" }
#   This is a refresh-only plan, so Terraform will not take any actions to undo these.
명령하는 일
terraform plan -refresh-only드리프트만 보여 줌. 아무것도 바꾸지 않음
terraform apply -refresh-only실물의 현재 값을 state에만 반영(드리프트 수용의 첫 단계). 클라우드는 바꾸지 않음. 예전 terraform refresh 명령의 안전한 대체
terraform plan -detailed-exitcode종료 코드로 결과 구분: 0 = 변경 없음, 1 = 오류, 2 = 변경 있음. 스크립트·CI에서 드리프트 알림에 사용
terraform plan -refresh=false반대로 refresh를 생략(빠르지만 드리프트를 못 봄). 대규모 환경의 특수 용도

드리프트를 발견했을 때의 세 갈래

판단 연습 — 상황마다 어떻게 처리할지 고른 뒤 펼쳐 보세요

처리절차언제
수용 (실물이 맞다)코드를 실물에 맞게 고치는 PR → plan이 변경 0인지 확인 → (필요시 apply -refresh-only)장애 대응 중 필요한 변경이었고 앞으로도 유지해야 할 때
되돌림 (코드가 맞다)그대로 terraform apply → 실물이 코드대로 복원권한 없는 변경, 실수, 보안 기준 위반
무시 (Terraform이 볼 일이 아니다)lifecycle { ignore_changes = [속성] }오토스케일링이 바꾸는 개수, 다른 시스템이 관리하는 태그처럼 바뀌는 것이 정상인 속성(11편)

정기 드리프트 감시

#!/usr/bin/env bash
# drift-check.sh — 매일 아침 CI 스케줄로 실행 (12편에서 파이프라인으로)
set -uo pipefail
cd "$1"
terraform init -input=false -backend-config=backend/dev.s3.tfbackend >/dev/null
terraform plan -refresh-only -detailed-exitcode -input=false -no-color > drift.txt 2>&1
case $? in
  0) echo "드리프트 없음: $1" ;;
  2) echo "드리프트 발견: $1"; cat drift.txt   # 여기서 메신저·티켓으로 알림
     exit 2 ;;
  *) echo "점검 실패: $1"; cat drift.txt; exit 1 ;;
esac

refresh-only plan은 읽기 전용이므로 운영 환경에도 안심하고 매일 돌릴 수 있습니다(state 잠금은 잡으므로 다른 실행과 겹치지 않게 시간을 정합니다). HCP Terraform 같은 플랫폼은 이 점검을 “상태 평가(health assessment)” 기능으로 제공합니다. 25편 MSP 운영에서 고객사 전체의 드리프트 리포트로 확장합니다.

11리팩터링: moved·removed

가져온 코드를 모듈 구조로 다듬고, 관리 범위를 조정한다

흡수 직후의 코드는 실물을 그대로 옮긴 평평한 리소스 목록입니다. 이제 5·6편에서 배운 도구로 실물을 건드리지 않고 구조를 바꿉니다.

7단계: 가져온 버킷을 모듈로, 두 번째 버킷은 모듈이 직접 가져오기

# main.tf: aws_s3_bucket.reports / aws_s3_bucket_versioning.reports 블록을 지우고 아래로 교체
# imports.tf: reports 버킷 관련 import 블록 두 개도 지운다 (이미 가져왔으므로)

module "reports_bucket" {
  source = "../../modules/legacy-bucket"

  existing_bucket_name = "legacy-reports-123456789012"
  tags                 = { Owner = "kim-legacy" }
}

moved {
  from = aws_s3_bucket.reports
  to   = module.reports_bucket.aws_s3_bucket.this
}

moved {
  from = aws_s3_bucket_versioning.reports
  to   = module.reports_bucket.aws_s3_bucket_versioning.this
}

# 아직 관리하지 않던 두 번째 버킷: 모듈 안의 import 블록이 가져온다 (1.16)
module "archive_bucket" {
  source = "../../modules/legacy-bucket"

  existing_bucket_name = "legacy-archive-123456789012"
  tags                 = { Owner = "kim-legacy" }
}
terraform init        # 새 module 블록
terraform plan
#   # aws_s3_bucket.reports has moved to module.reports_bucket.aws_s3_bucket.this
#   # aws_s3_bucket_versioning.reports has moved to module.reports_bucket.aws_s3_bucket_versioning.this
#   # module.archive_bucket.aws_s3_bucket.this will be imported
#   # module.archive_bucket.aws_s3_bucket_versioning.this will be imported
#   Plan: 2 to import, 0 to add, 0 to change, 0 to destroy.   (6단계의 태그 PR을 적용했다면 ~ 가 섞일 수 있음)
terraform apply

reports 버킷은 moved로 옮겨졌고, 모듈 안의 import 블록은 이미 관리 중인 대상이므로 무시됩니다. archive 버킷은 모듈 안 import 블록으로 새로 가져와집니다. 같은 구조를 내장 리소스로 재현한 실측에서 “moved 1 + 1 to import, 0 to change”가 나왔습니다(모듈 안 import 대신 루트의 import 블록으로 대체해 확인). 1.16 이전이라면 archive용 import 블록을 루트에 to = module.archive_bucket.aws_s3_bucket.this로 직접 써야 합니다.

8단계: 관리 이관 — SSM 파라미터를 고객 앱팀에 넘긴다

# main.tf에서 aws_ssm_parameter.feature_flag 블록과 그 import 블록을 지우고:
removed {
  from = aws_ssm_parameter.feature_flag

  lifecycle {
    destroy = false # 실물은 남기고 우리 state에서만 뺀다
  }
}
terraform plan     # → 1 to forget (5편 9장). 0 to destroy 인지 반드시 확인
terraform apply
aws ssm get-parameter --name /legacy/app/feature_flag --query Parameter.Value   # "on" — 실물은 그대로
도구실물state쓰는 때
import그대로추가콘솔 리소스 흡수, 다른 state에서 넘겨받기
moved그대로주소 변경이름 변경, 모듈 안팎 이동, count ↔ for_each
removed + destroy = false그대로제거관리 이관, 다른 state로 넘기기(받는 쪽은 import)
removed (destroy 생략·true)삭제제거코드에서 블록을 지우는 것과 같지만 의도를 명시
1.16의 새 옵션: 리소스 lifecycle의 destroy = false

1.16부터 일반 resource 블록의 lifecycle에도 destroy = false를 쓸 수 있게 되어, 리소스가 Terraform에 의해 삭제되는 것을 막을 수 있습니다. 관리를 계속하면서 삭제만 막는다는 점에서 removed(관리 중단)와 다르고, 기존의 prevent_destroy(삭제 계획 자체를 오류로 막음)와의 차이는 11편에서 비교합니다.

14MSP 현장 팁

고객사 인프라 인수 프로젝트로서의 흡수 작업

흡수는 견적이 필요한 프로젝트

리소스 수, 종류, 문서화 수준, 콘솔 변경 빈도에 따라 공수가 크게 다릅니다. 인벤토리(6장의 발견)를 먼저 하고 “흡수 대상 / 코드화 제외 / 폐기 권고” 분류표로 범위와 일정을 합의하세요. 전부를 코드로 만드는 것이 목표가 아닐 수도 있습니다.

변경 0의 PR이 신뢰를 만든다

첫 흡수 PR의 plan이 “n to import, 0 to change”인 것을 고객에게 보여 주면, “Terraform을 도입해도 운영이 흔들리지 않는다”는 가장 강력한 증거가 됩니다. 개선 PR은 그 신뢰 위에서 하나씩 승인받습니다.

계층 순서로 흡수

네트워크(VPC·서브넷·라우팅) → 보안(보안 그룹·IAM) → 데이터(RDS·S3) → 컴퓨트(EC2·ALB) 순서가 일반적입니다. 아래 계층을 먼저 코드로 만들어야 위 계층이 참조할 수 있고(7편 SSM 패턴), 영향이 큰 계층일수록 신중하게 다룹니다.

발견한 문제는 기록만, 수정은 나중에

흡수 중 0.0.0.0/0 규칙, 암호화되지 않은 볼륨, 주인 없는 리소스를 계속 발견하게 됩니다. 그 자리에서 고치지 말고 “보안 개선 백로그”로 기록해 고객 보고서에 넣습니다. MSP의 가치가 드러나는 결과물입니다.

콘솔 권한 회수와 예외 절차

흡수한 범위는 IAM 정책으로 콘솔 쓰기를 막고(읽기는 허용), 긴급 시 예외 절차(브레이크 글래스 역할 + 사후 코드 반영 기한)를 문서화합니다. 이것 없이는 드리프트가 다시 쌓입니다.

공통 모듈에 import를 담기 (1.16)

여러 고객사에 같은 종류의 레거시(예: 로그 버킷, 기본 보안 그룹)가 있다면, 모듈 안 import 블록으로 “이 모듈을 쓰면 기존 리소스를 자동으로 가져온다”는 흡수 경로를 표준화할 수 있습니다. 고객마다 import 블록을 다시 쓰지 않아도 됩니다.

과제 1. 7편 리소스를 콘솔로 만들고 흡수하기

7편의 ALB 모듈이 만드는 것 중 보안 그룹과 대상 그룹(비용 없음)만 콘솔로 직접 만든 뒤, 실습 B와 같은 절차로 modules/alb를 쓰는 루트에 흡수해 보세요. 모듈을 수정하지 않고 루트의 import 블록(to = module.alb.aws_security_group.alb)만으로 가능해야 합니다. ALB 본체는 만들지 않습니다(시간당 과금).

힌트

대상 그룹 import ID는 ARN입니다. 모듈이 만드는 이름(${var.name}-tg), 포트, 상태 확인 설정과 콘솔에서 만든 값이 정확히 같아야 “0 to change”가 나옵니다. 이름이 다르면 대상 그룹은 교체(-/+)가 계획됩니다. 계획에 ALB·리스너 생성(+)이 함께 나오는 것은 정상이므로, 그 부분은 -target 없이 plan만 보고 확인한 뒤 실습을 마칩니다.

과제 2. 규칙 키 이름 바로잡기

실습 B 6단계에서 http_any 규칙이 더는 “any”가 아니게 되었습니다. 키를 http_office로 바꾸되 규칙이 삭제·재생성되지 않게 하세요.

해설

locals의 키를 바꾸고 moved { from = aws_vpc_security_group_ingress_rule.legacy_web["http_any"] to = aws_vpc_security_group_ingress_rule.legacy_web["http_office"] }. imports.tf의 for_each 맵 키도 함께 바꾸거나, 흡수가 끝났으므로 그 import 블록을 지웁니다. plan은 “has moved to”만 나와야 합니다.

과제 3. 드리프트 점검 자동화

10장의 drift-check.sh를 06-network, 09-import 두 디렉터리에 대해 반복 실행하는 스크립트로 만들고, 일부러 보안 그룹 태그를 콘솔에서 바꾼 뒤 종료 코드 2가 나오는지 확인하세요. cron이나 GitHub Actions 스케줄로 매일 돌리려면 무엇이 더 필요할까요?

생각할 점

CI에서 돌리려면 장기 키 없이 AWS에 인증하는 방법(OIDC, 12편), 읽기 전용 역할(드리프트 점검은 쓰기 권한 불필요), 결과 알림 채널, 그리고 같은 시간에 사람이 apply하지 않도록 하는 잠금 대기(-lock-timeout)가 필요합니다.

과제 4. 대량 흡수 설계 (terraform query)

“고객사 dev 계정에 Owner=kim-legacy 태그가 붙은 EC2 30대가 있고, 역할별로 web·batch로 나뉘어 있다”고 가정하고, query 파일과 흡수 후 최종 코드 구조(for_each 맵의 키 설계 포함)를 설계해 보세요. 실제로 EC2를 만들 필요는 없습니다.

해설 요지

list 블록 두 개(필터: tag:Owner=kim-legacy + tag:Role=web/batch)로 나눠 query → 생성된 _0~_n 리소스를 역할별 for_each 리소스(키는 Name 태그)로 재구성 → identity 기반 import 블록도 for_each로 묶음 → “30 to import, 0 to change” 확인. 장기적으로는 7편 과제 1처럼 ASG로 옮길지(불변 인프라) 고객과 논의합니다.

과제 5. 다른 state로 리소스 넘기기

09-import의 보안 그룹과 규칙을 07-app 쪽 state로 옮기는 상황을 가정하고, 두 PR(보내는 쪽 removed, 받는 쪽 import)의 내용과 적용 순서를 쓰세요. 어느 순간에도 실물이 삭제되거나, 두 state가 동시에 관리하지 않아야 합니다.

해설

순서: ① 받는 쪽 PR을 준비하되 병합하지 않음 → ② 보내는 쪽에서 removed { … destroy = false } 적용(1 to forget, 이제 아무도 관리하지 않음) → ③ 받는 쪽 import 적용(n to import, 0 to change). ②와 ③ 사이에는 관리 공백이 생기므로 짧게 유지합니다. 반대 순서(받는 쪽 먼저)로 하면 두 state가 같은 실물을 관리하는 위험한 상태가 됩니다(5편 소유권 원칙). 5편 9장 상황별 선택기의 “다른 state로 옮기기”와 같은 절차입니다.

18정리와 다음 편

한 장으로 다시 보기

import는 장부에 한 줄

실물은 바뀌지 않는다. 코드는 직접 쓰거나 생성 초안을 정리한다. 목표는 가져온 직후 “0 to change”.

방법의 진화

CLI import → import 블록(1.5) → for_each(1.7) → identity(1.12) → query 대량 발견(1.14) → 모듈 안 import(1.16).

생성 코드는 사진

null·기본값 삭제, 하드코딩 참조를 참조로, 인라인 규칙 제거, 반복은 for_each로. 생성은 실험적 기능.

8단계와 세 규칙

범위 합의 → 발견 → 묶기 → 코드화 → 변경 0 → 적용 → 개선 → 권한 회수. 가져오기와 바꾸기를 섞지 않고, -/+는 무조건 멈춘다.

드리프트

plan -refresh-only로 따로 보고, -detailed-exitcode로 매일 점검. 수용·되돌림·무시(ignore_changes) 중 판단.

리팩터링

moved로 모듈 안으로, removed + destroy = false로 관리 이관. 이미 관리 중인 대상의 import 블록은 무시된다.
