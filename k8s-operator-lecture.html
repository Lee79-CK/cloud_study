CHAPTER 01

왜 Operator가 필요할까

Day-1은 쉽습니다. 문제는 Day-2입니다.

입사 첫 주, 선배가 이렇게 말합니다. "PostgreSQL을 쿠버네티스에 올려줘." 여러분은 열심히 검색해서 StatefulSet, Service, PVC, ConfigMap, Secret YAML을 만들고 kubectl apply를 실행합니다. Pod가 Running이 됩니다. 성공입니다.

이것을 Day-1(설치)이라고 부릅니다. 그런데 그 다음 주부터 이런 일들이 벌어집니다.

지금까지 이런 일은 사람이 위키에 적힌 운영 문서(Runbook)를 보면서 손으로 처리했습니다. 새벽 3시에 알람이 울리면 담당자가 노트북을 열고, 문서 7페이지를 펼치고, 명령어를 하나씩 입력했죠.

Operator의 한 줄 정의

Operator = 운영자(사람)의 지식과 절차를, 클러스터 안에서 24시간 돌아가는 프로그램으로 옮겨놓은 것. 쿠버네티스 공식 문서에서는 "쿠버네티스 API를 확장해 애플리케이션과 그 컴포넌트를 관리하는 소프트웨어 확장"이라고 정의합니다.

비유: 자동차 정비와 자율주행

수동 YAML

부품을 직접 사서 조립합니다. 무엇이 어디에 들어가는지 다 알아야 하고, 고장나면 직접 고칩니다.

Helm 차트

완성차를 주문합니다. 색상·옵션만 고르면 조립된 채로 배송됩니다. 하지만 운전은 여전히 내가 합니다.

Operator

자율주행차입니다. 목적지(원하는 상태)만 말하면, 차선 이탈·급정거·경로 재탐색을 차가 알아서 합니다.

역사 한 스푼

Operator 패턴은 2016년 CoreOS(현 Red Hat)의 엔지니어들이 etcd와 Prometheus를 쿠버네티스에서 운영하며 만들어낸 개념입니다. "우리 팀에서 가장 뛰어난 운영자(operator)가 하는 일을 코드로 쓰자"는 아이디어에서 이름이 붙었습니다.

CHAPTER 02

쿠버네티스의 심장, 컨트롤 루프

Operator를 이해하려면 먼저 쿠버네티스가 왜 그렇게 동작하는지 알아야 합니다.

명령형(Imperative) vs 선언형(Declarative)

옛날 방식은 명령형이었습니다. "서버 A에 접속해서, 프로세스를 3개 띄워라." 문제는 프로세스 하나가 죽으면 아무도 모른다는 것입니다. 명령은 이미 끝났으니까요.

쿠버네티스는 선언형입니다. "나는 항상 3개가 떠 있기를 원한다"고 선언만 합니다. 그 상태를 유지하는 책임은 쿠버네티스가 집니다.

명령형 · 한 번의 사건

docker run --name web -d nginx
→ 컨테이너가 죽어도 아무 일도 일어나지 않음. 사람이 알아채고 다시 실행해야 함.

선언형 · 지속되는 계약

replicas: 3
→ 컨테이너가 죽으면 몇 초 안에 새 것이 생김. 아무도 명령하지 않았는데도.

spec과 status: 쿠버네티스의 모든 리소스가 가진 두 얼굴

쿠버네티스의 거의 모든 오브젝트는 spec과 status라는 두 필드를 가집니다. 이 두 개의 차이가 Operator의 전부라고 해도 과언이 아닙니다.

필드누가 쓰나의미예시
spec사람 (또는 상위 컨트롤러)원하는 상태 · 목표 · 희망사항replicas: 3
status컨트롤러 (시스템)실제 상태 · 현재 관측된 사실readyReplicas: 2
외우세요

spec은 내가 쓰고, status는 읽기만 한다. status를 손으로 고치면 컨트롤러가 다음 순간 다시 덮어씁니다. status는 "성적표"이지 "목표"가 아닙니다.

컨트롤러 = 무한 루프

쿠버네티스 안에는 kube-controller-manager라는 프로세스가 있고, 그 안에 수십 개의 컨트롤러가 각자 아래의 세 단계를 영원히 반복합니다. 이것을 Reconciliation Loop(조정 루프)라고 부릅니다.

중요한 성질 · Level-triggered

쿠버네티스 컨트롤러는 "이벤트가 발생했을 때만" 동작하는 게 아니라(edge-triggered), 주기적으로 현재 상태를 다시 확인합니다(level-triggered). 그래서 컨트롤러가 잠깐 죽었다 살아나거나, 이벤트를 하나 놓쳐도 결국 정상 상태로 수렴합니다. 이 "결국 맞춰진다"는 성질을 최종 일관성(eventual consistency)이라고 합니다.

직접 돌려보는 조정 루프

아래 시뮬레이터에서 왼쪽(원하는 상태)을 바꾸거나, 오른쪽에서 Pod를 강제로 죽여보세요. 가운데 루프가 차이를 감지하고 무엇을 하는지 로그로 확인할 수 있습니다. 이것이 모든 쿠버네티스 컨트롤러와 Operator가 하는 일의 전부입니다.

방금 배운 것

"status를 손으로 수정" 버튼을 눌러보셨나요? 잠시 후 컨트롤러가 다시 원래대로 되돌립니다. 선언형 시스템에서 사람이 실제 상태를 직접 건드리는 것은 의미가 없습니다. 바꾸고 싶다면 spec을 바꿔야 합니다. Operator를 쓸 때도 똑같습니다.

CHAPTER 03

Operator = CRD + 컨트롤러

공식이 딱 하나뿐입니다. 이 등식만 기억하면 됩니다.

핵심 공식

Operator = CRD (새로운 명사) + Custom Controller (그 명사를 돌보는 프로그램)

CRD: 쿠버네티스에 새 단어를 가르치기

쿠버네티스는 태어날 때부터 Pod, Service, Deployment 같은 단어들을 알고 있습니다. 하지만 PostgresCluster나 KafkaTopic은 모릅니다.

CRD(CustomResourceDefinition)는 "쿠버네티스야, 앞으로 WebApp이라는 새로운 리소스 종류가 있을 거야. 이런 필드들을 가질 수 있어"라고 사전에 새 단어를 등록하는 것입니다.

CRD를 등록하면 그 순간부터 마법처럼 이런 게 됩니다.

terminal
# CRD 등록 전 — 쿠버네티스가 모르는 단어
$ kubectl get webapps
error: the server doesn't have a resource type "webapps"

# CRD 등록
$ kubectl apply -f webapp-crd.yaml
customresourcedefinition.apiextensions.k8s.io/webapps.apps.example.com created

# 이제 kubectl이 알아듣습니다. 내장 리소스와 완전히 똑같이 동작합니다.
$ kubectl get webapps
$ kubectl describe webapp my-blog
$ kubectl explain webapp.spec
$ kubectl get webapp my-blog -o yaml
감동 포인트

CRD를 만들면 RBAC, kubectl, 라벨 셀렉터, watch, 감사 로그, GitOps 도구까지 전부 공짜로 따라옵니다. 쿠버네티스 API의 모든 인프라를 내 애플리케이션 개념에 그대로 재사용하는 것 — 이것이 CRD의 진짜 가치입니다.

CRD 예시 (실제 YAML)
webapp-crd.yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  # 이름은 반드시 <복수형>.<group> 형식이어야 합니다
  name: webapps.apps.example.com
spec:
  group: apps.example.com
  scope: Namespaced        # 또는 Cluster
  names:
    kind: WebApp            # YAML에 쓰는 이름
    plural: webapps         # kubectl get webapps
    singular: webapp
    shortNames: [wa]      # kubectl get wa
  versions:
  - name: v1alpha1
    served: true            # API로 제공할지
    storage: true           # etcd에 저장할 버전 (딱 하나만 true)
    subresources:
      status: {}            # /status 서브리소스 활성화 (권장!)
    schema:
      openAPIV3Schema:      # 스키마 = 입력값 검증 규칙
        type: object
        properties:
          spec:
            type: object
            required: [image]
            properties:
              image:
                type: string
              replicas:
                type: integer
                minimum: 1       # 0 이하는 API 서버가 거부
                maximum: 10
                default: 1
              domain:
                type: string
          status:
            type: object
            properties:
              readyReplicas: { type: integer }
              url:           { type: string }
    # kubectl get 결과에 보여줄 추가 컬럼
    additionalPrinterColumns:
    - { name: Ready,  type: integer, jsonPath: .status.readyReplicas }
    - { name: URL,    type: string,  jsonPath: .status.url }
    - { name: Age,    type: date,    jsonPath: .metadata.creationTimestamp }
my-blog.yaml
# 이제 개발자는 이 10줄만 쓰면 됩니다.
# Deployment도, Service도, Ingress도 몰라도 됩니다.
apiVersion: apps.example.com/v1alpha1
kind: WebApp
metadata:
  name: my-blog
  namespace: default
spec:
  image: ghcr.io/acme/blog:1.4.2
  replicas: 3
  domain: blog.acme.io
terminal
$ kubectl apply -f my-blog.yaml
webapp.apps.example.com/my-blog created

$ kubectl get webapps
NAME      READY   URL                    AGE
my-blog   3       https://blog.acme.io   42s

# Operator가 뒤에서 알아서 만들어 놓은 것들
$ kubectl get deploy,svc,ingress -l app=my-blog
NAME                      READY   UP-TO-DATE   AVAILABLE
deployment.apps/my-blog   3/3     3            3

NAME              TYPE        CLUSTER-IP     PORT(S)
service/my-blog   ClusterIP   10.96.31.7     80/TCP

ingress.networking.k8s.io/my-blog   nginx   blog.acme.io   10.0.1.5
흔한 오해

"CRD를 만들면 Operator를 만든 것이다" → 아닙니다. CRD만 등록하면 그 리소스는 etcd에 저장만 되는 메모장일 뿐입니다. 아무 일도 일어나지 않습니다. 그 CR을 읽고 실제로 무언가를 만드는 컨트롤러가 있어야 비로소 Operator입니다.

CRD

클래스(설계도). 클러스터에 한 번 등록. kubectl get crd로 확인.

CR

인스턴스(실물). 사용자가 여러 개 생성. my-blog, my-shop…

Controller

CR을 보고 일하는 Pod. 보통 Deployment로 배포되어 계속 떠 있음.

CHAPTER 04

Operator의 내부 구조

Operator Pod 안에서 실제로 무슨 일이 벌어지는지 열어봅니다.

"watch 한다"는 말이 자주 나오는데, 실제로는 API 서버를 1초마다 계속 조회하는 게 아닙니다. 그러면 클러스터가 죽습니다. 대신 Informer라는 정교한 구조를 씁니다.

구성 요소역할왜 필요한가
InformerAPI 서버와 watch 연결을 유지하며 변경을 받아옴폴링 대신 푸시 방식이라 API 서버 부하가 거의 없음
Cache클러스터 오브젝트의 로컬 사본을 메모리에 유지Reconcile에서 Get 할 때마다 네트워크를 타지 않음
WorkQueue처리할 오브젝트 키(namespace/name)를 담는 큐같은 오브젝트가 100번 바뀌어도 한 번만 처리 (중복 제거)
Reconciler실제 비즈니스 로직. 개발자가 구현"이 CR이 원하는 상태가 되도록 만들어라"
ClientAPI 서버에 쓰기 작업 수행Deployment/Service 등을 실제로 생성·수정
가장 중요한 규칙 · 멱등성 (Idempotency)

Reconcile 함수는 같은 입력에 대해 몇 번을 실행해도 결과가 같아야 합니다. 큐에서 이벤트가 중복되거나, Operator가 재시작되거나, 주기적 재동기화가 일어나면 같은 CR에 대해 Reconcile이 수백 번 호출됩니다.

❌ "Deployment를 생성한다" → 두 번째 호출에서 AlreadyExists 에러
✅ "Deployment가 없으면 만들고, 있으면 원하는 모습과 비교해 다르면 고친다"

더 깊이 · Reconcile은 왜 "무엇이 바뀌었는지"를 알려주지 않을까?

Reconcile 함수가 받는 인자는 ctrl.Request 하나뿐이고, 그 안에는 네임스페이스와 이름밖에 없습니다. "replicas가 3에서 5로 바뀌었다" 같은 델타 정보는 주지 않습니다.

이것은 실수가 아니라 의도된 설계입니다. 만약 델타에 의존하면, 이벤트를 하나라도 놓쳤을 때 상태가 영원히 어긋납니다. 반면 "이름만 받고 현재 상태를 처음부터 다시 확인"하는 방식은 중간에 무슨 일이 있었든 항상 올바른 결과로 수렴합니다.

이것이 앞에서 말한 level-triggered 설계이며, 쿠버네티스가 견고한 이유입니다.

CHAPTER 05

YAML vs Helm vs Operator

셋 중 무엇을 써야 하나요? 답은 "상황에 따라"입니다. 그 상황을 구체적으로 봅니다.

많은 사람이 "Helm과 Operator 중 뭐가 더 좋냐"고 묻습니다. 잘못된 질문입니다. 둘은 경쟁 관계가 아니라 서로 다른 층위에 있습니다.

한 줄 요약

Helm은 설치 도구(패키지 매니저)이고, Operator는 운영 주체(상주 프로그램)입니다.
Helm은 helm install 순간에만 일하고 끝납니다. Operator는 그 이후로 계속 살아서 일합니다. 실제로 많은 Operator가 Helm 차트로 설치되기도 합니다. 둘 다 쓰는 게 정상입니다.

같은 상황, 세 가지 대응

적합한 대상일회성 · 학습용Stateless 앱, 사내 표준 배포Stateful · 복잡한 도메인
현장에서의 선택 기준

"이 앱을 운영하는 데 위키 문서가 필요한가?" 를 물어보세요.
· 문서가 필요 없다 (그냥 이미지 바꿔 배포하면 끝) → Helm이면 충분
· "장애 시 A를 하고 B를 확인한 뒤 C를 실행" 같은 절차 문서가 있다 → Operator 후보
· 이미 훌륭한 오픈소스 Operator가 있다 (Postgres, Kafka, Redis…) → 직접 만들지 말고 가져다 쓰기

신입이 저지르기 쉬운 실수

Operator는 멋져 보이지만 공짜가 아닙니다. 단순한 Stateless 웹 앱에 Operator를 만들면 Deployment 하나로 끝날 일을 위해 Go 코드 2,000줄과 CI/CD, 테스트, 버전 관리, 보안 패치를 떠안게 됩니다. Helm으로 충분하면 Helm을 쓰세요.

CHAPTER 06

Operator 역량 레벨 5단계

"이 Operator는 어디까지 해주나요?"를 판단하는 업계 표준 척도입니다.

Operator Framework에서 정의한 Capability Level은 Operator의 성숙도를 5단계로 나눕니다. 오픈소스 Operator를 도입할 때 이 레벨을 먼저 확인하면 "얼마나 믿고 맡길 수 있는지" 감이 옵니다. 아래 항목을 클릭해보세요.

1
Basic Install · 기본 설치 CR을 만들면 애플리케이션이 설치되고 설정이 적용된다. 여기까지는 Helm과 큰 차이가 없다.
할 수 있는 것 · 리소스 프로비저닝, 설정 파라미터 반영
못 하는 것 · 업그레이드, 백업, 장애 대응
예시 · 사내에서 처음 만든 WebApp Operator
2
Seamless Upgrades · 무중단 업그레이드 애플리케이션 버전 업그레이드와 Operator 자신의 업그레이드를 안전하게 처리한다.
추가되는 것 · 순서가 보장된 롤링 업그레이드, 마이그레이션 스크립트 실행, 이전 버전 CR 자동 변환(conversion webhook)
실무 의미 · spec.version만 바꾸면 나머지는 Operator가 알아서
3
Full Lifecycle · 전체 수명주기 백업, 복구, 페일오버, 스케일링 같은 Day-2 운영 작업을 Operator가 수행한다.
추가되는 것 · 스케줄 백업, PITR 복구, Primary 장애 시 자동 승격, 복제 재구성
실무 의미 · 여기서부터 진짜 Operator의 가치가 나옵니다. 운영 문서를 코드로 옮긴 지점
예시 · CloudNativePG, Strimzi(Kafka)
4
Deep Insights · 심층 관측 메트릭·알림·로그·이벤트를 노출하고, 워크로드의 건강 상태를 스스로 분석한다.
추가되는 것 · Prometheus 메트릭 export, ServiceMonitor/PrometheusRule 자동 생성, 상세한 status conditions
실무 의미 · Operator가 대시보드와 알람까지 함께 세팅해줌
5
Auto Pilot · 자율 운영 수평/수직 오토스케일링, 설정 자동 튜닝, 이상 감지와 자가 치료, 스케줄링 최적화까지 수행한다.
추가되는 것 · 부하 기반 자동 스케일, 자동 파라미터 튜닝, 이상 탐지 후 자동 교정
현실 · 이 레벨에 도달한 Operator는 극소수입니다. 목표로 삼되 처음부터 노리지 마세요.
도입 판단 팁

오픈소스 Operator를 고를 때는 Capability Level + 최근 커밋 활동 + 프로덕션 레퍼런스 세 가지를 봅니다. Level 1~2에 머무는 Operator라면, 굳이 Operator를 도입하는 대신 잘 만든 Helm 차트 + GitOps 조합이 더 나을 수 있습니다.

my-certificate.yaml
apiVersion: cert-manager.io/v1
kind: Certificate           # ← CRD로 추가된 새 리소스
metadata:
  name: blog-tls
  namespace: default
spec:
  secretName: blog-tls-secret   # 발급된 인증서를 여기 저장
  duration: 2160h              # 90일
  renewBefore: 360h           # 만료 15일 전 자동 갱신
  dnsNames:
    - blog.acme.io
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer

Step 2 · API 타입 정의하기 (webapp_types.go)

여기가 CRD의 원본입니다. Go 구조체를 쓰면 make manifests가 OpenAPI 스키마가 담긴 CRD YAML을 자동으로 만들어줍니다. 주석의 // +kubebuilder:가 스키마 규칙이 됩니다.

api/v1alpha1/webapp_types.go
package v1alpha1

import metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"

// WebAppSpec — 사용자가 "원하는 상태"를 쓰는 곳
type WebAppSpec struct {
    // 컨테이너 이미지. 필수 값.
    // +kubebuilder:validation:Required
    Image string `json:"image"`

    // 복제 개수. 1~10 사이, 기본값 1.
    // +kubebuilder:validation:Minimum=1
    // +kubebuilder:validation:Maximum=10
    // +kubebuilder:default=1
    // +optional
    Replicas *int32 `json:"replicas,omitempty"`

    // 컨테이너 포트. 기본값 8080.
    // +kubebuilder:default=8080
    // +optional
    Port int32 `json:"port,omitempty"`
}

// WebAppStatus — 컨트롤러가 "실제 상태"를 보고하는 곳
type WebAppStatus struct {
    // 준비된 파드 수
    ReadyReplicas int32 `json:"readyReplicas,omitempty"`

    // 표준 조건 배열. 쿠버네티스 관례를 따르세요.
    // +optional
    Conditions []metav1.Condition `json:"conditions,omitempty"`
}

// ↓ 이 마커들이 CRD의 옵션을 결정합니다
// +kubebuilder:object:root=true
// +kubebuilder:subresource:status
// +kubebuilder:resource:shortName=wa
// +kubebuilder:printcolumn:name="Image",type=string,JSONPath=`.spec.image`
// +kubebuilder:printcolumn:name="Ready",type=integer,JSONPath=`.status.readyReplicas`
// +kubebuilder:printcolumn:name="Age",type=date,JSONPath=`.metadata.creationTimestamp`
type WebApp struct {
    metav1.TypeMeta   `json:",inline"`
    metav1.ObjectMeta `json:"metadata,omitempty"`

    Spec   WebAppSpec   `json:"spec,omitempty"`
    Status WebAppStatus `json:"status,omitempty"`
}

// +kubebuilder:object:root=true
type WebAppList struct {
    metav1.TypeMeta `json:",inline"`
    metav1.ListMeta `json:"metadata,omitempty"`
    Items           []WebApp `json:"items"`
}

func init() { SchemeBuilder.Register(&WebApp{}, &WebAppList{}) }
왜 Replicas는 포인터(*int32)인가?

Go에서 int32의 기본값은 0입니다. 그러면 "사용자가 0을 명시했다"와 "아무것도 안 썼다"를 구분할 수 없습니다. 포인터로 만들면 nil이 "미지정"을 뜻하게 됩니다. 쿠버네티스 API 전반에서 쓰이는 관례입니다.

Step 3 · 컨트롤러 구현하기 (webapp_controller.go)

이 파일이 Operator의 두뇌입니다. 한 줄씩 읽어보세요.

internal/controller/webapp_controller.go
// ── RBAC 마커: 이 주석이 그대로 Role YAML로 생성됩니다 ──
// +kubebuilder:rbac:groups=apps.example.com,resources=webapps,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=apps.example.com,resources=webapps/status,verbs=get;update;patch
// +kubebuilder:rbac:groups=apps,resources=deployments,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=core,resources=services,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=core,resources=events,verbs=create;patch

func (r *WebAppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    log := logf.FromContext(ctx)

    // ─── ① 대상 CR 읽기 ───────────────────────────────
    // req에는 namespace/name만 들어 있습니다. 나머지는 직접 조회.
    var app appsv1alpha1.WebApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        if apierrors.IsNotFound(err) {
            // 이미 삭제됨. 하위 리소스는 OwnerReference 덕분에
            // 쿠버네티스가 자동 정리합니다. 조용히 종료.
            return ctrl.Result{}, nil
        }
        return ctrl.Result{}, err  // 일시적 오류 → 자동 재시도(백오프)
    }

    // ─── ② 원하는 Deployment 모습을 계산 ─────────────────
    desired := r.buildDeployment(&app)

    // ③ 소유 관계 설정 — 매우 중요!
    //    CR이 삭제되면 이 Deployment도 함께 자동 삭제됩니다(GC).
    if err := ctrl.SetControllerReference(&app, desired, r.Scheme); err != nil {
        return ctrl.Result{}, err
    }

    // ─── ④ 없으면 만들고, 있으면 비교해서 고친다 (멱등성의 핵심) ───
    var current appsv1.Deployment
    err := r.Get(ctx, client.ObjectKeyFromObject(desired), &current)
    switch {
    case apierrors.IsNotFound(err):
        log.Info("Deployment 생성", "name", desired.Name)
        if err := r.Create(ctx, desired); err != nil {
            return ctrl.Result{}, err
        }
    case err != nil:
        return ctrl.Result{}, err
    default:
        // 실제와 원하는 모습이 다른 부분만 교정 (드리프트 교정!)
        if *current.Spec.Replicas != *desired.Spec.Replicas ||
            current.Spec.Template.Spec.Containers[0].Image != app.Spec.Image {
            current.Spec.Replicas = desired.Spec.Replicas
            current.Spec.Template.Spec.Containers[0].Image = app.Spec.Image
            log.Info("드리프트 감지 → 교정")
            if err := r.Update(ctx, &current); err != nil {
                return ctrl.Result{}, err  // 충돌이면 재시도됨
            }
        }
    }

    // ─── ⑤ status 갱신 — 값이 실제로 변했을 때만! ──────────
    if app.Status.ReadyReplicas != current.Status.ReadyReplicas {
        app.Status.ReadyReplicas = current.Status.ReadyReplicas
        meta.SetStatusCondition(&app.Status.Conditions, metav1.Condition{
            Type:    "Available",
            Status:  metav1.ConditionTrue,
            Reason:  "DeploymentReady",
            Message: "모든 복제본이 준비되었습니다",
        })
        // 반드시 Status().Update() — 일반 Update()는 spec까지 덮어씁니다
        if err := r.Status().Update(ctx, &app); err != nil {
            return ctrl.Result{}, err
        }
    }

    // ⑥ 성공 종료. 다음 변경 이벤트가 오면 다시 호출됩니다.
    return ctrl.Result{}, nil
}
buildDeployment 헬퍼
// 순수 함수: CR을 받아 "원하는 Deployment 모습"을 반환.
// 클러스터에 접근하지 않으므로 단위 테스트가 아주 쉽습니다.
func (r *WebAppReconciler) buildDeployment(
    app *appsv1alpha1.WebApp,
) *appsv1.Deployment {

    labels := map[string]string{
        "app.kubernetes.io/name":       "webapp",
        "app.kubernetes.io/instance":   app.Name,
        "app.kubernetes.io/managed-by": "webapp-operator",
    }

    replicas := int32(1)
    if app.Spec.Replicas != nil {
        replicas = *app.Spec.Replicas
    }

    return &appsv1.Deployment{
        ObjectMeta: metav1.ObjectMeta{
            Name:      app.Name,          // CR과 같은 이름/네임스페이스
            Namespace: app.Namespace,
            Labels:    labels,
        },
        Spec: appsv1.DeploymentSpec{
            Replicas: &replicas,
            Selector: &metav1.LabelSelector{MatchLabels: labels},
            Template: corev1.PodTemplateSpec{
                ObjectMeta: metav1.ObjectMeta{Labels: labels},
                Spec: corev1.PodSpec{
                    Containers: []corev1.Container{{
                        Name:  "app",
                        Image: app.Spec.Image,
                        Ports: []corev1.ContainerPort{{
                            ContainerPort: app.Spec.Port,
                        }},
                        // 실무에서는 probe와 resources를 반드시 넣으세요
                        ReadinessProbe: &corev1.Probe{
                            ProbeHandler: corev1.ProbeHandler{
                                HTTPGet: &corev1.HTTPGetAction{
                                    Path: "/healthz",
                                    Port: intstr.FromInt32(app.Spec.Port),
                                },
                            },
                        },
                    }},
                },
            },
        },
    }
}
SetupWithManager — 무엇을 감시할지 등록
func (r *WebAppReconciler) SetupWithManager(mgr ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(mgr).
        // 주 감시 대상: WebApp CR
        For(&appsv1alpha1.WebApp{}).

        // 내가 소유한 Deployment/Service도 감시.
        // 누군가 Deployment를 손으로 수정하면 → OwnerReference를 따라
        // 부모 WebApp의 Reconcile이 자동 호출됩니다. (자동 교정의 비밀)
        Owns(&appsv1.Deployment{}).
        Owns(&corev1.Service{}).

        // 동시 Reconcile 개수. 기본 1 → 처리량이 부족하면 늘립니다.
        WithOptions(controller.Options{MaxConcurrentReconciles: 3}).
        Named("webapp").
        Complete(r)
}

방금 확인한 것

kubectl scale로 Deployment를 7개로 바꿨는데 3개로 되돌아왔습니다. 왜냐하면 Owns(&appsv1.Deployment{}) 때문에 Deployment 변경이 부모 WebApp의 Reconcile을 트리거했고, Reconcile이 "spec에는 3이라고 적혀 있는데?" 하며 교정했기 때문입니다. 이것이 Operator의 자동 복구가 작동하는 원리 전부입니다.

make run과 make deploy의 차이가 뭔가요?

make run은 컨트롤러 바이너리를 여러분의 노트북에서 실행하고, ~/.kube/config를 통해 원격 클러스터의 API 서버에 접속합니다. 코드를 바꾸면 재시작만 하면 되니 개발 중에는 이 방식이 훨씬 빠릅니다. 브레이크포인트 디버깅도 가능합니다.

make deploy는 컨트롤러를 컨테이너 이미지로 빌드해서 클러스터 안에 Deployment로 띄웁니다. 이때부터는 ServiceAccount의 RBAC 권한이 실제로 적용되므로, 로컬에서는 잘 되던 것이 클러스터에서 forbidden으로 실패하는 일이 흔합니다. RBAC 마커를 빠뜨렸는지 확인하세요.

CHAPTER 11

Reconcile 함수 해부

반환값 하나로 재시도 전략이 결정됩니다. 여기서 실수하면 클러스터가 아파합니다.

반환값의 의미

반환값의미언제 쓰나
ctrl.Result{}, nil성공. 재큐 안 함할 일을 다 끝냈을 때 (대부분의 경우)
ctrl.Result{}, err실패. 지수 백오프로 재시도일시적 오류 (네트워크, 충돌). 5ms → 10ms → … 최대 1000초
{RequeueAfter: 30*time.Second}, nil30초 뒤 다시 호출외부 작업 완료를 기다릴 때 (백업 진행 중 등)
ctrl.Result{}, nil + 로그영구적 오류는 재시도 금지사용자 입력이 잘못된 경우. status와 Event로 알리고 종료
신입이 가장 많이 하는 실수

"이미지 이름이 잘못됨" 같은 사용자 잘못인데 return err을 하면, 큐가 영원히 재시도하며 로그를 폭격합니다. 고쳐질 수 없는 오류는 status.conditions에 이유를 기록하고 nil을 반환하세요. spec이 수정되면 어차피 새 이벤트가 옵니다.

Finalizer · 외부 리소스 정리하기

CR을 삭제할 때, 클러스터 안의 하위 리소스는 OwnerReference로 자동 정리됩니다. 하지만 클러스터 밖의 것(AWS S3 버킷, 외부 DNS 레코드, 라이선스 서버 등록)은 아무도 지워주지 않습니다. 이때 필요한 것이 Finalizer입니다.

Finalizer 표준 패턴
const finalizerName = "webapp.apps.example.com/finalizer"

// Reconcile 안에서, CR을 읽은 직후에 이 블록을 넣습니다
if !app.DeletionTimestamp.IsZero() {
    // ── 삭제 진행 중 ──
    if controllerutil.ContainsFinalizer(&app, finalizerName) {
        // 1) 외부 리소스 정리. 반드시 멱등하게!
        if err := r.cleanupExternalResources(ctx, &app); err != nil {
            return ctrl.Result{}, err   // 성공할 때까지 재시도
        }
        // 2) 정리 끝 → finalizer 제거 → 실제 삭제 진행
        controllerutil.RemoveFinalizer(&app, finalizerName)
        if err := r.Update(ctx, &app); err != nil {
            return ctrl.Result{}, err
        }
    }
    return ctrl.Result{}, nil   // 삭제 중이므로 여기서 종료
}

// ── 정상 경로: finalizer가 없으면 추가 ──
if !controllerutil.ContainsFinalizer(&app, finalizerName) {
    controllerutil.AddFinalizer(&app, finalizerName)
    if err := r.Update(ctx, &app); err != nil {
        return ctrl.Result{}, err
    }
}

status.conditions 제대로 쓰기

사용자가 kubectl describe로 "왜 안 되는지" 알 수 있게 하는 것은 Operator의 UX입니다. 쿠버네티스는 표준 Condition 형식을 정해두었으니 그대로 따르세요.

conditions 예시
status:
  conditions:
  - type: Ready              # 최종 사용자가 볼 요약 상태
    status: "False"          # True / False / Unknown
    reason: ImagePullFailed  # CamelCase, 기계가 읽는 코드
    message: "이미지 nginx:99.9 를 가져올 수 없습니다"   # 사람이 읽는 설명
    lastTransitionTime: "2026-08-06T02:31:00Z"
    observedGeneration: 4   # 어느 spec 버전을 보고 판단한 것인지
  - type: Progressing
    status: "True"
    reason: Reconciling
    message: "Deployment 롤아웃 대기 중 (2/3)"
observedGeneration 트릭

metadata.generation은 spec이 바뀔 때마다 증가합니다. status.observedGeneration에 "내가 처리한 generation"을 기록해두면, 사용자는 generation == observedGeneration인지 보고 "내가 방금 바꾼 설정이 반영되었는지"를 확실히 알 수 있습니다.

CHAPTER 12

실무 패턴과 안티패턴

코드 리뷰에서 지적받기 전에 미리 알아두면 좋은 것들.

안티패턴 7가지

1. Reconcile에서 sleep

time.Sleep(30s)은 워커 스레드를 통째로 막습니다. 다른 CR들이 전부 대기합니다.
→ 대신 RequeueAfter를 반환하세요.

2. 매 루프마다 status 쓰기

status 변경은 다시 watch 이벤트를 발생시킵니다 → 무한 루프 → CPU 폭주.
→ 값이 실제로 변했을 때만 업데이트.

3. cluster-admin 권한 부여

Operator가 탈취되면 클러스터 전체가 넘어갑니다.
→ RBAC 마커로 필요한 리소스·verb만 최소 권한 부여.

4. 실행 순서 가정

"먼저 A가 만들어졌을 것"이라는 전제는 깨집니다. Reconcile은 언제든 처음부터 다시 호출됩니다.
→ 매번 현재 상태를 확인하고 시작.

5. 메모리에 상태 저장

Operator Pod는 언제든 재시작됩니다. 전역 변수의 진행 상황은 사라집니다.
→ 모든 상태는 CR의 status나 ConfigMap에.

6. 하위 리소스 전체 덮어쓰기

HPA가 조정한 replicas를 매번 되돌리면 HPA와 싸웁니다.
→ 관리할 필드만 비교·수정. 또는 Server-Side Apply 사용.

7. 에러를 삼키기

if err != nil { return ctrl.Result{}, nil }는 재시도를 막고 조용히 실패합니다.
→ 일시적 오류는 err를 반환, 영구 오류는 status에 기록.

보너스. 관측 가능성 확보

Reconcile 횟수·소요시간·에러율 메트릭은 controller-runtime이 기본 제공합니다.
→ ServiceMonitor를 붙여 대시보드를 만들어두세요.

PostgreSQL, MySQL, Kafka, Redis, MongoDB, Elasticsearch, Prometheus, Grafana, cert-manager… 대부분 이미 훌륭한 Operator가 있습니다. 직접 만들면 그 팀의 수년치 운영 경험을 처음부터 다시 쌓는 일입니다.

2. 우리 앱이 Stateless인가?
상태가 없다면 Deployment + HPA + Helm으로 99% 해결됩니다.

3. 운영 절차 문서가 실제로 존재하는가?
코드로 옮길 지식이 없다면, Operator는 그냥 복잡한 YAML 생성기입니다.

4. Go를 유지보수할 사람이 팀에 계속 있을 것인가?
만든 사람이 퇴사하면 아무도 손대지 못하는 Operator가 클러스터 핵심에 박혀 있게 됩니다. 이것이 실무에서 가장 흔한 실패 사례입니다.

정리와 다음 단계

이 강의의 핵심 5줄

  1. 쿠버네티스의 모든 것은 spec(원하는 상태)과 status(실제 상태)의 차이를 좁히는 무한 루프다.
  2. Operator = CRD(새 리소스 타입) + Custom Controller(그것을 돌보는 프로그램)다.
  3. Helm은 설치 순간에만 일하고, Operator는 설치 이후 계속 살아서 일한다. 둘은 함께 쓸 수 있다.
  4. Reconcile 함수는 멱등해야 한다. "없으면 만들고, 있으면 비교해서 고친다."
  5. 이미 좋은 Operator가 있으면 만들지 말고 가져다 쓴다. 만드는 것은 장기 유지보수 약속이다.
