27편고가용성과 장애 대응

지금까지 각 편에서 “이게 죽으면 이렇게 된다”를 조각조각 배웠습니다(16편 과반수, 24편 게이트웨이, 23편 Ceph full…). 이번 편은 그 조각을 모아 설계 단계에서 장애 영역을 나누고, 컴퓨트 노드가 죽으면 VM을 자동으로 살리고, 큰 장애가 났을 때 누가 무엇을 어떤 순서로 할지 정하고, 그 결과를 고객 약속(SLA)으로 바꾸는 법을 다룹니다.

약 120분예상 학습 시간
10·16·23·24·26편 이수
랙 시뮬레이터·시나리오·SLA 계산기포스트모템 도우미
다음 편28편 보안 강화

섹션 1

이 편의 목표

  1. 장애 영역(노드·랙·사이트)별로 RHOSO 구성 요소를 어떻게 배치할지 설계한다.
  2. 계층별 고가용성 장치와 MSP·고객 책임 분담을 설명한다.
  3. RHOSO Instance HA의 동작(감지·펜싱·대피)과 요건·한계를 안다.
  4. 고객 워크로드를 안티 어피니티·AZ·로드밸런서로 이중화하도록 안내한다.
  5. 대규모 장애 시나리오별 첫 15분과 복구 순서를 갖춘다.
  6. 사고 지휘 체계와 비난 없는 사후 검토를 운영한다.
  7. 가용성 계산으로 SLA·RTO·RPO를 현실적으로 정한다.

이 편의 비유: 병원의 비상 체계

병원은 전원이 두 계통이고(장애 영역 분리), 환자가 쓰러지면 다른 병상으로 즉시 옮기며(Instance HA), 대형 사고 때는 지휘관·의료진·홍보 담당이 역할을 나누고(사고 지휘), 끝나면 무엇이 잘못됐는지 탓하지 않고 기록해 개선합니다(포스트모템). 그리고 “응급실 대기 30분 이내” 같은 약속(SLA)은 이 모든 것이 실제로 받쳐 줄 수 있을 때만 합니다.

섹션 2

장애 영역과 랙 시뮬레이터

장애 영역은 “하나의 원인으로 함께 죽는 범위”입니다. 서버 한 대, 같은 전원·스위치를 쓰는 랙 하나, 데이터센터 하나. 배치에 따라 랙 하나의 장애가 “버티는 일”이 되기도, “전면 장애”가 되기도 합니다.

장애 영역RHOSO에서 나누는 방법
노드OCP 3노드에 클러스터 구성원 분산(16편), 컴퓨트 N+1 여유(26편), Instance HA(섹션 4)
랙 (전원·ToR 스위치)OCP 노드를 랙마다 하나씩, 컴퓨트를 랙별로 나눠 AZ·호스트 집계(10편), Ceph CRUSH 장애 영역을 rack으로, 스위치·전원 이중화
사이트 (데이터센터)단일 RHOSO로는 사이트 장애를 견디기 어려움 → 사이트별 독립 클라우드 + 앱·데이터 복제, 또는 분산 구성(DCN, 29편). 백업은 다른 사이트에(26편)

섹션 3

계층별 고가용성과 책임 분담

계층RHOSO·MSP가 하는 것고객이 해야 하는 것
컨트롤 플레인서비스 replicas 3, Galera·RabbitMQ·OVN DB 과반수(16편), MetalLB VIP 전환, Operator 자동 복구—
컴퓨트N+1 용량, Instance HA(장애 시 VM 재생성), 라이브 마이그레이션으로 계획 작업중요 서비스는 VM 여러 대 + 안티 어피니티 서버 그룹
네트워크게이트웨이 섀시 2~3대(24편), 분산 라우팅, 스위치·NIC 이중화(bond)여러 VM 앞에 로드밸런서(14편), 상태 검사
스토리지Ceph 3사본·장애 영역 설계, 용량 관리(23편)볼륨 백업·스냅샷 정책, 앱 수준 데이터 복제(DB 복제)
사이트다른 사이트 백업 보관, (상품에 따라) DR 사이트다중 리전 배포 설계, DR 절차 연습

“클라우드는 VM 하나를 영원히 살려 주는 곳이 아니다”

OpenStack은 VM 하나가 아니라 많은 VM으로 된 서비스가 장애를 견디도록 설계된 플랫폼입니다. Instance HA는 단일 VM의 중단 시간을 줄여 주지만 무중단을 보장하지 않습니다. 이 책임 분담을 계약과 온보딩 안내(22편)에 명확히 적어야 장애 때 분쟁이 없습니다.

섹션 4

인스턴스 HA (Instance HA)

RHOSO의 Instance HA 서비스는 기본 설치되는 infra-operator가 관리합니다. 컴퓨트 노드가 응답하지 않으면 그 노드를 확실히 끄고(펜싱), 그 위의 VM을 다른 노드에서 다시 만듭니다(대피·evacuate). 단계를 넘겨 보세요.

요건·설정내용
펜싱 (필수)대피 대상 컴퓨트마다 펜싱 에이전트(IPMI·Redfish·BareMetalHost 등)를 fencingSecret에 정의. 펜싱 없이 대피하면 죽은 줄 알았던 노드가 살아 있어 같은 디스크를 두 VM이 쓰는 사고가 날 수 있음
공유 스토리지VM 디스크가 Ceph 등 공유 저장소에 있어야 데이터를 유지한 채 다른 노드에서 재생성. 로컬 디스크면 이미지에서 새로 만들어 데이터가 사라짐
대상 고르기기본은 모든 컴퓨트·VM이 대상이지만, 태그(이미지·플레이버·호스트 집계)로 중요 VM만 대피하도록 좁힐 수 있음
안전장치한 VM의 대피가 5번 실패하면 그 노드 대피를 멈춤(FORCE_ENABLE로 무시 가능), 한꺼번에 너무 많은 노드가 실패하면 대피를 멈추는 임계값 등
결과 확인기본적으로 대피 API 요청이 받아들여지면 성공으로 간주 → 실제 VM ACTIVE 여부는 운영자가 확인(경보 연동)
 
# InstanceHa CR (개념 예 — 필드는 “Configuring high availability for instances” 문서 기준)
apiVersion: instanceha.openstack.org/v1beta1
kind: InstanceHa
metadata: { name: instanceha, namespace: openstack }
spec:
  openStackCloud: default                   # 대피 API를 부를 접속 정보
  openStackConfigMap: openstack-config
  openStackConfigSecret: openstack-config-secret
  fencingSecret: fencing-secret               # 노드별 펜싱 에이전트 (IPMI·Redfish·BMH)
  instanceHaConfigMap: instanceha-config     # 대상 태그, 임계값, 대기 시간 등 파라미터

oc get instanceha -n openstack ; oc logs -n openstack deploy/instanceha-… -f

Instance HA가 해 주지 않는 것

  • 무중단이 아님: VM은 재부팅된 것처럼 다시 시작합니다(메모리 내용 손실, 부팅 시간).
  • 앱 정합성: 갑작스러운 정지 후 DB 복구 등은 게스트·앱 몫입니다.
  • 용량: 남은 노드에 자리가 없으면 대피가 실패합니다 → N+1 용량(26편 계산기)이 전제.
  • 반드시 랩에서 노드를 실제로 죽여 보는 시험(섹션 10)으로 펜싱부터 확인하세요.

최고AZ 분산 + LB + DB 복제 + 다른 사이트 백업랙 장애에도 계속, 사이트 장애는 DR 절차

섹션 7

사고 지휘 체계

큰 장애에서 가장 흔한 실패는 기술이 아니라 혼란입니다. 모두가 동시에 명령을 치고, 고객 문의가 엔지니어에게 쏟아지고, 누가 무엇을 바꿨는지 아무도 모릅니다. 역할을 미리 정해 둡니다.

역할하는 일하지 않는 일
사고 지휘관 (IC)심각도 선언, 우선순위·결정, 사람 배정, 다음 업데이트 시각 약속직접 명령 치기 (손이 묶이면 전체를 못 봄)
기술 리드원인 조사·복구 작업 지휘, 변경은 한 번에 하나, 결과 보고고객 응대
커뮤니케이션 담당고객·내부 공지(정해진 주기), 상태 페이지, 문의 창구추측성 원인 공유
기록자시각별 사건·결정·명령 기록 (포스트모템 재료)—
심각도기준 (예)대응
SEV1다수 고객 서비스 중단 (VM 통신 불가, 스토리지 정지)즉시 IC 선언, 전원 소집, 30분마다 고객 공지, 경영진 보고
SEV2일부 고객 영향 또는 관리 기능 중단 (API 불가, 새 VM 생성 불가)IC 선언, 관련 팀 소집, 1시간마다 공지
SEV3영향 미미, 이중화가 버티는 중 (노드 1대, 구성원 1개)업무 시간 내 처리, 추가 장애 대비 감시 강화
SEV4잠재 위험 (경고성 경보)티켓

섹션 15

  
정리와 다음 편

  
오늘의 핵심 여덟 문장

  
    
    
  • 장애 영역은 노드·랙·사이트. OCP 노드는 랙마다 하나, 컴퓨트는 랙별 AZ, Ceph CRUSH는 rack 단위가 기본 방향.
    • 
    
  • 고가용성은 MSP(플랫폼)와 고객(워크로드)의 분담. 단일 VM은 노드 장애를 피할 수 없다.
    • 
    
  • Instance HA는 감지 → 펜싱 → 대피 → 재생성. 펜싱과 공유 스토리지, N+1 용량이 전제이며 무중단이 아니다.
    • 
    
  • 고객 이중화는 안티 어피니티 서버 그룹 · AZ · LB 상태 검사 · 오토스케일 · 데이터 복제.
    • 
    
  • 대규모 장애는 시나리오별 첫 15분과 복구 순서를 미리 정해 둔다.
    • 
    
  • 사고 때는 IC·기술 리드·커뮤니케이션·기록자로 역할을 나누고, 심각도 기준과 공지 주기를 지킨다.
    • 
    
  • 사후에는 비난 없는 포스트모템: 사실 타임라인, 여러 번의 왜, 담당자·기한 있는 조치.
    • 
    
  • SLA는 직렬은 곱, 이중화는 1−(1−a)ⁿ으로 계산하고, 측정 가능한 SLI와 실측 RTO·RPO 위에서만 약속한다.
    •
