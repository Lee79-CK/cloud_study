노드 한 대가 실제로 잡아먹는 IP

“Pod IP를 어디서 받느냐”는 결국 주소 계획 문제입니다. 벤더를 고르고 값을 바꿔 보면, 노드당 최대 Pod 수와 서브넷·주소 범위를 얼마나 쓰는지가 계산됩니다. 각 벤더의 공개된 규칙을 단순화한 모델이라 실제와 몇 개 차이가 날 수 있지만, 규모 판단에는 충분합니다.

읽는 법과 4편 핵심 복습

이 편을 읽는 법

CNI 이야기는 약어가 많습니다. 본문에서 CNI처럼 점선 밑줄이 그어진 말은 마우스를 올리거나 눌러서 정식 명칭과 쉬운 설명을 볼 수 있고, 같은 내용이 15장 용어·약어 사전에 모여 있습니다. 각 장 첫머리의 초록색 “쉬운 말로” 상자는 그 장의 핵심을 비유로 먼저 잡아 줍니다.

4편 핵심 다섯 가지

이 편은 4편(네트워크 모델과 CNI 원리)의 개념 위에 서 있습니다. 4편을 아직 보지 않았다면 아래 다섯 줄만 먼저 확인하세요.

  1. 네트워크 모델. 모든 Pod는 고유 IP를 갖고, 다른 노드의 Pod와 NAT 없이 통신하며, 노드의 에이전트(kubelet 등)도 Pod와 NAT 없이 통신할 수 있어야 합니다. Kubernetes는 이 결과만 요구하고 방법은 CNI에 맡깁니다.
  2. Pod 안쪽 배선. Pod는 자기만의 네트워크 공간(netns)을 갖고, veth 한 쌍으로 노드와 이어집니다. 노드 쪽 끝이 브리지에 꽂히는지, 라우팅 테이블로 처리되는지, eBPF 프로그램이 받는지가 CNI마다 다릅니다.
  3. CNI 스펙. 컨테이너 런타임이 Pod를 만들 때 CNI 플러그인 실행 파일을 ADD로, 지울 때 DEL로, 점검할 때 CHECK로 호출합니다. 설정은 노드의 /etc/cni/net.d/, 실행 파일은 /opt/cni/bin/에 있습니다.
  4. IPAM. 어떤 IP를 줄지 정하는 부분입니다. 노드마다 블록을 나눠 주는 방식(host-local, Calico 블록), 클라우드에서 받아 오는 방식(VPC CNI, Azure CNI)이 있습니다.
  5. 노드 사이 전달. 다른 노드의 Pod로 가는 패킷은 캡슐화(오버레이)하거나, 라우팅 테이블에 경로를 넣거나, 처음부터 네트워크가 아는 IP를 쓰는 방식으로 전달됩니다. 이 편의 1장이 바로 이 선택을 다룹니다.

이 편을 마치면 할 수 있는 것

  • 여섯 가지 구현(Flannel·Canal·Calico·Cilium·OVN-Kubernetes·클라우드 CNI)의 IP 배정, 노드 간 전달, 정책 강제, Service 처리 방식을 비교 설명할 수 있습니다.
  • EKS·AKS·GKE·OpenShift·RKE2의 기본 CNI가 왜 그것인지, 바꿀 수 있는지, 바꾸면 무엇을 잃는지 설명할 수 있습니다.
  • 고객 요구(IP 여유, 규모, 보안 통제, 성능, 관측)를 받아 오버레이와 VPC 직결 중 하나를 고르고 근거를 댈 수 있습니다.
  • EKS의 Pod IP 고갈을 진단하고 prefix delegation, WARM 설정, custom networking 중 알맞은 해법을 고를 수 있습니다.
  • MTU 문제를 캡슐화 오버헤드 계산으로 설명하고 예방할 수 있습니다.

두 갈래: 오버레이와 VPC 직결

쉬운 말로 아파트 단지(클러스터)에 사는 사람(Pod)에게 주소를 주는 방법은 두 가지입니다. 하나는 단지 안에서만 통하는 동·호수를 따로 매기고, 단지 밖으로 편지를 보낼 땐 단지 대표 주소가 적힌 봉투에 다시 넣는 방식(오버레이)입니다. 다른 하나는 처음부터 우체국(클라우드 네트워크)에 정식 주소를 등록해 주는 방식(VPC 직결)입니다. 앞쪽은 주소가 넉넉하지만 봉투를 한 번 더 써야 하고, 뒤쪽은 우체국이 바로 알아보지만 정식 주소가 금방 동납니다.

데이터플레인 기술: iptables·nftables·eBPF·OVS

쉬운 말로 CNI가 “누가 어디로 가도 되는지”를 실제로 집행하는 장치를 데이터플레인이라고 합니다. iptables는 위에서부터 차례로 읽는 긴 규칙 목록, nftables는 그 목록을 정리해 빨리 찾게 만든 새 버전, eBPF는 커널 안에 작은 프로그램을 심어 바로 판단하게 하는 방식, OVS는 소프트웨어로 만든 스위치에 흐름 규칙을 넣는 방식입니다.
기술동작 방식강점약점쓰는 곳
iptables커널 netfilter 훅에 규칙 체인을 걸고 순서대로 비교어디서나 있음, 도구 풍부규칙 수에 비례해 느려지고 갱신이 통째로 일어남. 서비스·정책이 수천 개면 부담kube-proxy 기본, Calico 기본 데이터플레인, Flannel, VPC CNI SNAT
nftables같은 netfilter 위에서 집합(set)·맵으로 규칙을 묶어 조회대규모에서 iptables보다 빠르고 부분 갱신 가능도구·운영 경험이 아직 적음kube-proxy nftables 모드(1.37에서 기본값 전환 작업이 Alpha로 시작), Calico nftables 데이터플레인
eBPF커널 네트워크 경로의 여러 지점에 작은 프로그램을 붙이고, 상태는 BPF 맵에 둠규칙 수와 무관하게 빠른 조회, kube-proxy 대체, 원래 출발지 IP 보존·DSR, 흐름 관측커널 버전 의존, 다른 eBPF 도구와 충돌 가능, 디버깅에 새 도구 필요Cilium, Calico eBPF 모드, GKE Dataplane V2, AKS Cilium 데이터플레인, VPC CNI 네트워크 정책 에이전트
OVS / OVN노드마다 소프트웨어 스위치(OVS)를 두고, OVN이 논리 스위치·라우터를 흐름 규칙으로 번역해 내려줌논리 네트워크 모델이 풍부(멀티테넌트, 이그레스 IP, 다중 네트워크)구성 요소가 많고 내부 구조가 깊음OpenShift OVN-Kubernetes
시니어 포인트: 데이터플레인이 바뀌면 진단 도구가 바뀐다 iptables 기반 클러스터에서는 iptables-save와 conntrack으로 대부분을 설명할 수 있었습니다. eBPF 데이터플레인에서는 같은 명령을 쳐도 규칙이 거의 보이지 않고, cilium-dbg·bpftool·Hubble로 봐야 합니다. OVN-K에서는 ovn-nbctl·ovs-ofctl이 필요합니다. 고객 클러스터의 장애 대응 런북은 “어느 데이터플레인인가”부터 분기해야 합니다. 1편의 지문 스크립트 4·5번 항목이 이 판별을 해 줍니다.

Flannel과 Canal: 단순함의 기준점

쉬운 말로 Flannel은 “Pod끼리 통하게만” 해 주는 가장 단순한 CNI입니다. 출입 통제(NetworkPolicy)는 하지 않습니다. Canal은 Flannel로 길을 놓고 Calico를 경비원으로 붙인 조합입니다.

Flannel

  • IP 배정. 노드마다 Pod 대역의 한 조각(기본 /24)을 줍니다. kubeadm의 --pod-network-cidr를 쪼개 노드의 spec.podCIDR로 받는 방식(Kubernetes IPAM)이 기본입니다.
  • 전달. 기본 백엔드는 VXLAN(flannel.1 인터페이스, UDP 8472). 모든 노드가 같은 L2 구간에 있으면 캡슐화 없는 host-gw도 쓸 수 있습니다.
  • 정책. 없습니다. NetworkPolicy 객체를 만들어도 아무 일도 일어나지 않습니다. 3편 스모크 테스트에 Flannel 단독 환경이 있었다면 NOT-enforced가 나왔을 것입니다.
  • 쓰임. K3s 기본, 학습, 엣지. 단순해서 장애 지점이 적다는 것이 가장 큰 장점입니다.

Canal

Canal은 별도 제품이 아니라 Flannel(전달) + Calico Felix(정책)를 한 DaemonSet에 묶은 배포 형태입니다. RKE2가 기본으로 쓰고, 3편 lab-rke2에서 rke2-canal Pod 안에 calico-node와 kube-flannel 컨테이너가 함께 있는 것을 볼 수 있습니다. Calico의 BGP·IPAM은 쓰지 않으므로, Calico 고유 기능 중 경로 광고·IP 풀 관리는 Canal에서 쓸 수 없습니다.

Calico: 경로를 광고하는 CNI

쉬운 말로 Calico는 각 노드가 “내 집 Pod 주소는 이 범위야”라고 주변 라우터와 다른 노드에 알리는(BGP) 방식으로 출발했습니다. 그래서 캡슐화 없이도 Pod끼리 통하게 만들 수 있고, 필요하면 VXLAN·IPIP로 감쌀 수도 있습니다. 정책 집행은 iptables, nftables, eBPF 중에서 고릅니다.

IPAM: 블록 단위 배정

Calico는 IP 풀(예: 10.244.0.0/16)을 기본 /26 블록(64개 주소)으로 잘라 노드에 친화(affinity)시켜 나눠 줍니다. 노드의 Pod가 늘면 블록을 하나 더 가져가고, 다른 노드 블록에서 빌려 쓰기도 합니다. 그래서 Kubernetes의 node.spec.podCIDR와 실제 Pod IP가 일치하지 않을 수 있습니다. 이 사실은 6편(Service)과 9편(정책)에서 대역 기반 규칙을 쓸 때 함정이 됩니다.

BGP 규모: 전체 메시에서 라우트 리플렉터로

기본 설정은 모든 노드가 서로 BGP 세션을 맺는 전체 메시(node-to-node mesh)입니다. 세션 수가 노드 수의 제곱에 비례해 늘어나므로, 대략 100~200노드를 넘기면 일부 노드(또는 물리 라우터)를 라우트 리플렉터로 지정하고 나머지는 그것과만 세션을 맺게 바꿉니다. 물리 스위치와 BGP를 맺으면 사내망이 Pod IP를 직접 알게 되어, 오버레이 없이도 VPC 직결과 비슷한 효과를 냅니다.

데이터플레인 선택

  • iptables: 기본값. 가장 오래 검증됨.
  • nftables: kube-proxy nftables 모드와 짝을 맞출 때.
  • eBPF: kube-proxy를 대체하고, 외부에서 들어온 요청의 원래 출발지 IP를 보존하며, DSR을 지원합니다. 켜려면 kube-proxy를 비활성화하고 API 서버 주소를 Calico에 직접 알려 줘야 합니다(kube-proxy 없이 Service IP를 쓸 수 없으므로).

벤더 안의 Calico

Calico는 CNI 전체가 아니라 정책 엔진만 벤더에 들어가는 경우가 많습니다. GKE의 레거시 데이터플레인(Dataplane V2가 아닌 클러스터)의 NetworkPolicy, AKS의 Calico 네트워크 정책 옵션, EKS에서 VPC CNI와 함께 정책 엔진으로 쓰는 구성이 그렇습니다. 이 경우 IP 배정과 전달은 벤더 CNI가, 정책은 Calico가 맡습니다.

Cilium: 커널 안에서 판단하는 CNI

쉬운 말로 Cilium은 리눅스 커널 안에 작은 프로그램(eBPF)을 심어, 패킷이 지나가는 순간 바로 “이 Pod는 누구고 어디로 가도 되나”를 판단합니다. IP 주소가 아니라 Pod의 레이블로 만든 신원 번호로 판단한다는 점이 다른 CNI와 가장 다릅니다.

핵심 개념

  • 신원(identity) 기반 정책. 같은 레이블 조합을 가진 Pod들은 같은 숫자 신원을 받고, 정책은 신원끼리의 허용 관계로 BPF 맵에 저장됩니다. Pod IP가 바뀌어도 정책을 다시 계산할 필요가 적어, Pod가 자주 생겼다 사라지는 대규모 클러스터에 유리합니다.
  • kube-proxy 대체(KPR). Service의 가상 IP 변환을 eBPF로 처리합니다. 소켓 수준에서 목적지를 바꿔 conntrack을 거치지 않는 경로도 있습니다. GKE Dataplane V2와 AKS Cilium 데이터플레인이 kube-proxy 없이 동작하는 이유입니다.
  • L7 정책. HTTP 경로·메서드, gRPC, Kafka 토픽 수준의 정책을 노드의 Envoy 프록시를 거쳐 집행합니다. DNS 이름(FQDN) 기반 이그레스 정책도 지원합니다.
  • Hubble. eBPF가 본 흐름을 모아 “누가 누구에게, 어떤 정책 판정으로” 통신했는지 보여 주는 관측 계층입니다.

GKE Dataplane V2와 AKS Azure CNI Powered by Cilium은 모두 Cilium 기반이지만, 벤더가 설정을 고정한 관리형 배포입니다. 사용자가 Cilium 설정 값이나 버전을 바꿀 수 없고, CiliumNetworkPolicy 같은 확장 CRD를 쓸 수 있는 범위도 벤더가 정합니다. Hubble 같은 관측 기능도 벤더 상품(AKS의 ACNS, GKE Dataplane V2 관측 기능)으로 따로 켭니다. 같은 Cilium이라도 자체 설치와 벤더 내장은 운영 방식이 다르다는 점을 고객에게 분명히 설명해야 합니다.

함정: eBPF끼리의 충돌 eBPF 데이터플레인 위에 다른 eBPF 기반 도구(보안 에이전트, 네트워크 관측 도구)를 얹으면 같은 커널 훅을 두고 충돌할 수 있습니다. GKE 문서는 Dataplane V2 노드에 사용자 eBPF 프로그램 설치를 지원하지 않으며, 다른 eBPF 도구가 Service 연결을 깨뜨린 사례를 명시합니다. 보안 에이전트를 도입하기 전에 그 도구가 어떤 훅을 쓰는지 확인하세요.

OVN-Kubernetes: 가상 스위치로 짠 네트워크 (OpenShift)

쉬운 말로 OVN-Kubernetes는 노드마다 소프트웨어 스위치(OVS)를 두고, 클러스터 전체를 “노드별 스위치 + 클러스터 라우터 + 바깥으로 나가는 문”으로 이루어진 가상 회사 네트워크처럼 설계합니다. 설계도(OVN)를 그리면 각 노드 스위치에 규칙이 자동으로 내려갑니다.

구조

  • 논리 토폴로지. 노드마다 논리 스위치(그 노드의 Pod 서브넷), 클러스터 라우터, 노드마다 외부로 나가는 게이트웨이 라우터가 있습니다. Pod 간 다른 노드 통신은 Geneve로 캡슐화됩니다.
  • 노드 단위 컨트롤 플레인. 최신 OVN-K는 노드마다 OVN 데이터베이스와 컨트롤러를 두는 “인터커넥트” 구조라, 중앙 데이터베이스 하나가 병목이던 예전 구조보다 확장성과 장애 격리가 좋아졌습니다.
  • OpenShift 기본값. 클러스터 네트워크 10.128.0.0/14(노드당 /23), Service 172.30.0.0/16이 설치 기본값이고, OVN-K 내부용으로 100.64.0.0/16(join), 100.88.0.0/16(transit) 같은 대역을 씁니다. 이 내부 대역이 사내망과 겹치면 설치 시 바꿔야 합니다.
  • MTU. Geneve와 선택적 IPsec 여유를 위해 노드 MTU에서 100바이트를 뺀 값을 기본으로 씁니다.

Amazon VPC CNI (EKS): 네트워크 카드에서 IP를 빌려 오는 CNI

쉬운 말로 EC2 인스턴스는 네트워크 카드(ENI)를 몇 장까지 꽂을 수 있고, 카드 한 장에는 IP를 몇 개까지 달 수 있는지 정해져 있습니다. VPC CNI는 이 카드에 여분 IP를 미리 달아 두었다가 Pod가 생길 때마다 하나씩 나눠 줍니다. 그래서 Pod IP가 곧 VPC의 진짜 IP이고, 노드에 올릴 수 있는 Pod 수가 인스턴스 크기에 묶입니다.

동작 순서

  1. 노드마다 aws-node DaemonSet이 돌고, 그 안의 ipamd가 EC2 API로 ENI를 붙이고 보조 IP를 받아 웜 풀에 쌓아 둡니다.
  2. Pod가 생기면 CNI 플러그인이 웜 풀에서 IP 하나를 꺼내 Pod에 주고, 노드 라우팅 테이블에 그 Pod로 가는 경로를 넣습니다.
  3. 다른 노드의 Pod로 가는 패킷은 캡슐화 없이 VPC가 바로 전달합니다. VPC가 그 IP의 주인이 어느 ENI인지 알기 때문입니다.
  4. Pod가 VPC 밖(인터넷)으로 나갈 때는 기본으로 노드 IP로 SNAT됩니다(AWS_VPC_K8S_CNI_EXTERNALSNAT로 조정).

노드당 최대 Pod 수 공식

최대 Pod = ENI 수 × (ENI당 IP 수 − 1) + 2. ENI마다 첫 IP는 ENI 자신의 주소라 빼고, hostNetwork로 도는 aws-node·kube-proxy 두 개를 더합니다. 예를 들어 t3.large는 ENI 3장 × IP 12개라 3 × 11 + 2 = 35입니다. 3편 lab-eks의 노드가 정확히 이 값을 가집니다. 맨 위 계산기에서 인스턴스를 바꿔 보세요.

AKS의 네 가지 네트워크 모델

쉬운 말로 AKS는 “Pod 주소를 VNet에서 직접 줄 것인가, 따로 매길 것인가”에 대해 네 가지 답을 갖고 있었고, 지금은 그중 두 가지(Overlay, Pod Subnet)를 권장합니다. 그 위에 “누가 패킷을 처리하나”를 Azure 기본 방식과 Cilium 중에서 고릅니다.

데이터플레인과 정책 엔진

  • Azure CNI Powered by Cilium(--network-dataplane cilium): Overlay나 Pod Subnet과 함께 쓰며, kube-proxy 없이 eBPF로 Service와 NetworkPolicy를 처리합니다. 3편 lab-aks가 이 구성입니다.
  • Azure Network Policy Manager(NPM): iptables 기반의 기존 정책 엔진. Windows 노드 지원이 2026년 9월 30일로 끝났고, Linux도 Cilium 정책으로 이전하라는 안내가 나와 있습니다. 대규모(250노드·2만 Pod 초과)는 지원하지 않습니다.
  • Calico: AKS가 설치해 주는 정책 엔진 옵션. Calico의 확장 기능은 AKS가 테스트·지원하지 않는 범위가 있습니다.
  • ACNS: Cilium 데이터플레인 위에서 Hubble 기반 흐름 관측, FQDN 필터링, 노드 간 암호화 등을 제공하는 유료 부가 기능입니다.

최대 Pod 수

AKS의 노드당 Pod 상한은 어떤 모델이든 250이며 지원 요청으로도 올릴 수 없습니다. 기본값은 모델·배포 방식마다 다릅니다(레거시 Azure CNI는 30, kubenet은 110, Overlay는 대개 더 높게 잡음). 노드 풀을 만들 때 --max-pods로 정하고, 나중에 바꾸려면 새 노드 풀이 필요합니다.

현장 메모: 은퇴 일정 두 개를 고객 로드맵에 AKS 고객 중 kubenet이나 Azure NPM을 쓰는 클러스터가 있다면, 은퇴 일정(kubenet 2028-03-31, NPM Windows 2026-09-30·Linux는 Cilium 이전 권고)을 1편의 버전 인벤토리 대시보드에 함께 올려 두세요. 둘 다 클러스터 재생성이나 노드 풀 교체를 동반하는 이전이라, 업그레이드 일정과 묶어 계획해야 비용이 덜 듭니다.

GKE: VPC-native와 Dataplane V2

쉬운 말로 GKE는 노드 서브넷에 Pod 전용 “보조 주소 칸”을 하나 붙이고, 노드마다 그 칸에서 한 블록씩 잘라 줍니다(별칭 IP). Pod IP는 VPC가 아는 진짜 주소지만, 노드 서브넷의 주 주소는 쓰지 않습니다. 그리고 블록은 최대 Pod 수의 두 배 크기로 잘라 줍니다.

주소 규칙

  • 노드당 블록 = 최대 Pod 수의 2배 이상인 가장 작은 2의 거듭제곱. 기본 최대 110 Pod → 256개 → /24. 최대 32 Pod로 줄이면 /26(64개). 두 배인 이유는 Pod가 교체될 때 IP를 바로 재사용하지 않도록 여유를 두기 위해서입니다.
  • Pod 보조 범위 크기가 노드 수 상한을 정합니다. /21 범위에 /24 블록이면 노드 8대가 끝입니다. 오토스케일러가 노드를 더 못 늘리는 장애의 흔한 원인입니다(13장).
  • 범위가 모자라면. 노드 풀마다 다른 Pod 범위를 붙이는 방식(discontiguous multi-Pod CIDR)으로 나중에 대역을 더할 수 있고, 노드 풀의 최대 Pod 수를 줄여 블록을 작게 할 수도 있습니다.
  • Service 대역은 별도 보조 범위이거나 GKE 관리 대역입니다.

Dataplane V2

  • Cilium 기반 eBPF 데이터플레인으로, kube-proxy 대신 Service를 처리하고 NetworkPolicy를 항상 강제합니다(별도 애드온 불필요). Autopilot은 기본이고, Standard는 클러스터 생성 때만 켤 수 있으며 기존 클러스터를 전환할 수 없습니다.
  • Dataplane V2가 아닌 레거시 데이터플레인에서는 NetworkPolicy를 Calico로 집행합니다. 같은 GKE라도 클러스터 생성 시점에 따라 정책 엔진이 다를 수 있다는 뜻입니다.
  • 운영 주의점: 노드 에이전트(anetd)가 상황에 따라 vCPU 2~3개까지 쓸 수 있고, 사용자 eBPF 프로그램 설치를 지원하지 않으며, 조각난 ICMP 패킷은 버려집니다. 초대형 규모 모드는 네트워크 정책 강제를 끕니다.
  • 정책 로깅과 흐름 관측(--enable-dataplane-v2-flow-observability), 지표(--enable-dataplane-v2-metrics)는 선택 기능입니다.

RKE2의 CNI 선택

RKE2는 cni 설정으로 canal(기본), cilium, calico, flannel, 그리고 Multus(다른 CNI와 함께 추가 네트워크)를 고릅니다. 1.37.0+rke2r1 기준 번들 버전은 Cilium 1.20.1, Calico v3.32.2, Flannel v0.28.9입니다.

  • 왜 Canal이 기본인가. 정책 강제(Calico)와 단순한 전달(Flannel VXLAN)의 조합이 가장 많은 환경에서 별 조정 없이 동작하기 때문입니다. 온프렘 물리망과 BGP를 맺을 필요도, 커널 버전을 따질 필요도 없습니다.
  • 바꾸는 방법. 번들 차트의 값은 HelmChartConfig로 덮어씁니다(예: rke2-cilium에 kubeProxyReplacement 설정). CNI 종류 자체는 클러스터 생성 전에 정해야 하며, 운영 중 교체는 재구축에 가깝습니다.
  • Cilium을 고를 때. kube-proxy 대체를 원하면 RKE2의 kube-proxy를 비활성화하는 설정을 함께 넣어야 합니다. 둘 다 켜 두면 Service 처리가 두 겹이 됩니다.

  • GKE가 별칭 IP인 이유. VPC 직결의 장점(방화벽·흐름 로그·LB 직접 대상)을 유지하면서 주 서브넷 고갈을 피하는 절충입니다. 대가는 보조 범위 크기 계획입니다.
  • OpenShift가 OVN-K인 이유. 멀티테넌트 격리, 이그레스 IP, 다중 네트워크처럼 엔터프라이즈 온프렘에서 요구하는 논리 네트워크 기능을 플랫폼 기본으로 제공하려는 선택입니다.
  • RKE2가 Canal인 이유. 어떤 온프렘 망에서도 조정 없이 동작하는 단순함 + 정책 강제라는 최소 보안 기준입니다.

현장 사례

EKS 새 노드에서 Pod가 ContainerCreating에 멈췄다

증상. 노드는 Ready인데 새 Pod 이벤트에 failed to assign an IP address to container가 반복됩니다.

원인. 노드 50대가 /24 서브넷 세 개를 쓰고 있었는데, 기본 WARM_ENI_TARGET 때문에 실제 Pod 수의 두세 배를 웜 풀로 잡고 있어 서브넷의 남은 IP가 0이었습니다.

대응. 단기로 WARM_IP_TARGET·MINIMUM_IP_TARGET을 설정해 웜 풀을 줄였고, 중기로 VPC에 100.64.0.0/16 보조 CIDR을 붙여 custom networking으로 Pod 서브넷을 분리했습니다.

교훈. EKS 서브넷 크기는 “Pod 수”가 아니라 “Pod 수 + 웜 풀”로 계획해야 합니다. 서브넷 남은 IP에 경보를 거세요.

prefix delegation을 켰는데 InsufficientCidrBlocks

원인. 오래 쓴 서브넷이라 빈 주소가 군데군데 흩어져 있어, 연속된 /28 블록을 찾지 못했습니다. 남은 IP 수만 보면 충분해 보였습니다.

대응. 새 서브넷에 prefix 전용 CIDR 예약(subnet CIDR reservation)을 걸고 노드 그룹을 그 서브넷으로 옮겼습니다.

교훈. prefix 모드는 “남은 IP 수”가 아니라 “연속된 /28 수”가 기준입니다. 새 서브넷에서 시작하는 것이 가장 안전합니다.

작은 요청은 되는데 큰 응답만 멈춘다 (MTU)

상황. 온프렘 Calico VXLAN 클러스터의 Pod가 IPsec VPN 너머 사내 시스템을 호출할 때, 헬스 체크는 성공하는데 TLS 핸드셰이크(큰 인증서)와 큰 응답에서 연결이 멈췄습니다.

원인. Pod MTU 1450(노드 1500 − VXLAN 50)인데 VPN 구간 실제 MTU가 1400이었고, 경로 MTU 발견에 필요한 ICMP “조각화 필요” 메시지가 방화벽에서 막혀 있었습니다.

대응. Calico MTU를 1350으로 낮추고, 방화벽에 ICMP type 3 code 4를 허용했습니다.

교훈. MTU는 경로 전체에서 가장 작은 구간 기준입니다. 1장 도구로 오버헤드를 계산하고, “큰 패킷만 실패”라는 증상을 MTU 의심 신호로 기억하세요.

GKE 오토스케일러가 노드를 더 못 만든다

원인. Pod 보조 범위를 /21로 만들었고 노드 풀 최대 Pod가 기본 110이라 노드당 /24 블록이 필요했습니다. 노드 8대에서 범위가 바닥났습니다.

대응. 새 보조 범위를 추가해 새 노드 풀에 붙이고(discontiguous multi-Pod CIDR), 실제 밀도에 맞춰 새 노드 풀의 최대 Pod를 64로 낮춰 블록을 /25로 줄였습니다.

교훈. GKE는 “최대 Pod × 2”만큼 블록을 자르므로 최대 Pod 설정이 곧 주소 소비 설정입니다.

AKS 은퇴 일정이 업그레이드 계획을 뒤집었다

상황. kubenet과 Azure NPM을 쓰는 AKS 클러스터 여러 개의 버전 업그레이드를 계획하던 중, 두 기능의 은퇴 일정이 확인됐습니다.

대응. 업그레이드를 그대로 진행하지 않고, Overlay + Cilium 데이터플레인으로 이전하는 작업과 묶어 노드 풀 교체 횟수를 줄였습니다. 정책은 Cilium 정책으로 재검증했습니다.

교훈. CNI 모델 은퇴는 버전 업그레이드보다 영향이 큽니다. 1편의 인벤토리에 CNI 모델과 정책 엔진을 버전과 같은 무게로 기록하세요.

보안 에이전트를 깔았더니 Service 호출이 간헐적으로 실패한다

원인. eBPF 데이터플레인(Dataplane V2·Cilium) 노드에 다른 eBPF 기반 네트워크 관측 도구를 설치해, 같은 커널 훅을 두고 프로그램이 충돌했습니다.

교훈. eBPF 데이터플레인 클러스터에는 eBPF 도구 도입 전 호환성 확인을 변경 관리 항목으로 넣으세요. GKE는 사용자 eBPF 프로그램을 지원하지 않는다고 명시합니다.

온프렘 Calico 300노드에서 경로 수렴이 느려졌다

원인. 기본 BGP 전체 메시를 그대로 두어 노드마다 수백 개 BGP 세션을 유지하고 있었습니다. 노드 재시작 때 경로 수렴이 느려지고 BIRD CPU가 튀었습니다.

대응. 노드 세 대를 라우트 리플렉터로 지정하고 전체 메시를 끈 뒤, 랙 스위치와도 리플렉터를 통해 경로를 교환했습니다.

교훈. Calico BGP는 규모에 따라 토폴로지를 바꿔야 하는 설정입니다. 노드 100~200대를 넘기기 전에 설계를 바꾸세요.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. CNI의 차이는 IP 출처(오버레이 대역·VPC 주소·보조 범위), 노드 간 전달(캡슐화·라우팅·VPC 직접), 데이터플레인(iptables·nftables·eBPF·OVS) 세 축으로 정리됩니다.
  2. VPC 직결은 클라우드 네트워크 기능을 Pod 단위로 쓰게 해 주지만 주소를 소비하고, 오버레이는 주소를 아끼지만 외부에서 Pod가 보이지 않습니다.
  3. EKS의 노드당 Pod 수와 주소 소비는 ENI 한도와 웜 풀 설정이 정하고, prefix delegation·custom networking·웜 풀 조정이 각각 다른 고갈 문제를 풉니다.
  4. 벤더 내장 Cilium(GKE DPv2, AKS Cilium)은 자체 설치 Cilium과 운영 방식이 다르며, 대부분의 매니지드에서 CNI 교체는 생성 시점에만 가능하거나 지원을 잃습니다.
  5. MTU는 경로에서 가장 작은 구간 기준이고, “큰 패킷만 실패”는 MTU 문제의 신호입니다.
