Inference Gateway
Gateway API Inference Extension

10편에서 llm-d Router가 레플리카마다 점수를 매겨 요청을 보내는 것을 봤습니다. 이번 편은 그 아래에 있는 쿠버네티스 표준을 정면으로 다룹니다. 모델 서버 Pod 묶음을 나타내는 InferencePool, 요청의 우선순위를 나타내는 InferenceObjective, 게이트웨이와 대화하며 엔드포인트를 고르는 Endpoint Picker(EPP), 그리고 이것들이 기존 Ingress·서비스 메시·AI 게이트웨이와 어떻게 층을 이루는지까지.

01시작하기 전에

“게이트웨이가 어느 Pod로 보낼지 묻는 표준 방법”. 이 한 줄이 Gateway API Inference Extension(GAIE)의 정체입니다.

2026년 8월 이후 바뀐 것 (오래된 자료와 다른 점)
  • GAIE v1.6.0(2026년 8월)에서 완전한 기능의 EPP, 본문 기반 라우팅(BBR), 지연 예측기 구성 요소가 llm-d 저장소로 옮겨졌습니다. GAIE는 이제 표준 명세·CRD·적합성 시험에 집중하고, 적합성 시험용 참조 구현으로 경량 EPP(lwepp)를 제공합니다.
  • 같은 릴리스에서 알파 API였던 InferenceObjective, InferenceModelRewrite, EndpointPickerConfig가 GAIE에서 제거되어 llm-d로 이전되었습니다. 커리큘럼의 “InferenceObjective”는 개념은 그대로지만, 이제 llm-d 쪽 API로 다룹니다.
  • InferencePool은 v1.0부터 GA(inference.networking.k8s.io/v1)이고, v1.6에서 endpointPickerRef가 선택 사항이 되었습니다(사용자가 EPP를 직접 배포하지 않는 구현을 위해).
  • 이 편은 “표준 API(GAIE)”와 “그 구현(llm-d Router·각 게이트웨이)”을 구분해서 설명합니다.

학습 목표

  1. 일반 L4·L7 로드밸런서가 LLM 추론에서 부족한 이유를 지표로 설명할 수 있다.
  2. InferencePool의 필드(선택자·포트·EPP 참조·실패 모드)와 HTTPRoute 연결을 읽고 쓸 수 있다.
  3. 요청 우선순위(Objective)와 흐름 제어가 과부하 때 무엇을 지키는지 설명할 수 있다.
  4. EPP의 동작(ext_proc 프로토콜, 데이터 수집, 필터·점수·선택 파이프라인)을 그리고, 가중치 조정의 효과를 예측할 수 있다.
  5. EPP 장애 시 FailOpen·FailClose의 차이와 고가용성 구성을 설명할 수 있다.
  6. Ingress·서비스 메시·AI 게이트웨이·Inference Gateway의 층 관계를 그리고, 구현체를 고를 수 있다.
이 편의 비유: 병원 접수처

일반 로드밸런서는 “빈 진료실 아무 데나” 보내는 안내원입니다. Inference Gateway의 EPP는 각 진료실의 대기 인원(대기열), 남은 침상(KV 캐시), 이 환자의 이전 진료 기록이 있는 방(프리픽스 캐시), 필요한 장비가 있는 방(LoRA)을 보고 보내는 접수처입니다. InferencePool은 “내과 진료실 묶음”, Objective는 “응급·일반·예약 환자” 구분이고, 흐름 제어는 병원이 꽉 찼을 때 응급 환자부터 받는 규칙입니다.

02일반 로드밸런서로 부족한 이유

LLM 요청은 크기도, 걸리는 시간도, 재사용할 상태도 요청마다 다릅니다.

GAIE는 이 차이를 메우기 위해 “어느 Pod로 보낼지”의 결정을 게이트웨이 밖의 추론 전용 구성 요소(EPP)에 위임하는 표준 방법을 정의합니다. 게이트웨이는 TLS·라우팅·관측 같은 자기 일을 하고, 엔드포인트 선택만 EPP에 묻습니다.

04InferencePool 해부

“이 라벨의 Pod들이 이 포트로 같은 모델을 서빙하고, 엔드포인트 선택은 저 EPP에게 물어라.”

yaml · InferencePool (GAIE v1)
apiVersion: inference.networking.k8s.io/v1
kind: InferencePool
metadata: { name: qwen3-8b-pool, namespace: llmsvc-lab }
spec:
  selector:
    matchLabels: { app: llm-engine }       # 모델 서버 Pod 라벨과 정확히 일치해야 함
  targetPorts:
  - number: 8000                           # 모델 서버 포트
  endpointPickerRef:                       # v1.6부터 선택 사항 (구현체가 지원할 때만 생략)
    name: qwen3-8b-epp                     # EPP Service 이름
    port: { number: 9002 }                 # EPP의 ext_proc gRPC 포트
    failureMode: FailOpen                  # EPP 무응답 시: FailOpen(게이트웨이가 직접 분배) / FailClose(요청 실패)
yaml · HTTPRoute가 Service 대신 InferencePool을 가리킴 (gateway 모드)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: llm-openai, namespace: llmsvc-lab }
spec:
  parentRefs: [ { name: inference-gateway } ]     # GAIE를 지원하는 구현체의 Gateway
  rules:
  - matches: [ { path: { type: PathPrefix, value: /v1 } } ]
    backendRefs:
    - group: inference.networking.k8s.io
      kind: InferencePool
      name: qwen3-8b-pool
    timeouts: { request: 600s }
필드·상태의미운영 포인트
selector풀에 속할 Pod. Service의 선택자와 같은 개념Prefill·Decode처럼 역할이 다른 Pod를 섞지 않도록 라벨 설계 (10편)
targetPorts모델 서버 포트 (여러 개 가능)한 Pod에 여러 엔진 랭크가 있는 데이터 병렬 구성에서 여러 포트
appProtocol모델 서버와의 프로토콜 (gRPC 지원 추가)엔진의 gRPC 인터페이스를 쓸 때
endpointPickerRefEPP Service 참조, 포트, 실패 모드EPP를 사용자가 운영하는 구성에서는 필수로 생각
status.parents각 Gateway(부모)별 수용 여부·조건“Accepted”, “ResolvedRefs”, 잘못된 확장 참조 등으로 문제 진단

05InferenceObjective와 우선순위

풀이 여유로울 때는 모두가 빠릅니다. 우선순위는 “꽉 찼을 때 누구를 먼저”를 정하는 장치입니다.

GAIE 초기에는 InferenceModel이 “모델 이름 + 중요도(criticality)”를 함께 표현했습니다. v1.0에서 이것이 InferenceObjective로 바뀌며 “요청의 서빙 목표(우선순위)”만 담당하게 되었고, 모델 이름 매칭·변경은 InferenceModelRewrite로 분리되었습니다. 그리고 v1.6에서 둘 다 알파 API인 채로 GAIE에서 빠져 llm-d로 옮겨졌습니다. 개념은 같습니다.

  • Objective: “이 종류의 요청은 우선순위 N”. 요청은 헤더(예: x-gateway-inference-objective)로 자기 Objective를 밝힙니다. 게이트웨이나 AI 게이트웨이(12편)가 테넌트·API 키에 따라 이 헤더를 붙이는 구성이 자연스럽습니다.
  • 흐름 제어(Flow Control): EPP가 풀의 포화도를 감지해, 포화되면 요청을 바로 보내지 않고 우선순위 대역별 대기열에 넣습니다. 높은 대역부터 내보내고, 같은 대역 안에서는 공정성 정책(테넌트별 몫 등)으로 순서를 정하며, 더 버틸 수 없으면 낮은 우선순위부터 거절합니다. 최근 버전은 SLO 기한 기반 정렬, 진행 중 요청 중단 같은 정책도 갖추고 있습니다.

흐름 제어 시뮬레이터

풀의 동시 처리 용량을 100으로 두고, 세 등급(실시간·일반·배치)의 요청이 섞여 들어옵니다. 우선순위 흐름 제어가 있을 때와 없을 때(먼저 온 순서)를 비교합니다. 대기열 용량은 50입니다.

06Endpoint Picker 해부

게이트웨이가 “이 요청 어디로?”라고 물으면, EPP는 수집해 둔 Pod 상태로 답합니다.

게이트웨이와 EPP의 대화: ext_proc

  1. 게이트웨이가 요청을 EPP로 넘김Envoy의 외부 처리(ext_proc) gRPC 스트림으로 요청 헤더와 본문을 EPP에 보냅니다. 스트리밍 본문을 다루는 전이중 모드도 명세에 포함됩니다.
  2. EPP가 본문을 해석파서(OpenAI 형식, vLLM gRPC 등 교체 가능)가 모델 이름·프롬프트·LoRA 어댑터 같은 정보를 꺼냅니다.
  3. 스케줄링: 필터 → 점수 → 선택수집해 둔 Pod 상태로 후보를 거르고 점수를 매겨 하나(또는 P/D면 두 개)를 고릅니다. 포화 시에는 흐름 제어 대기열로 보냅니다.
  4. 선택 결과 반환고른 엔드포인트(Pod IP:포트)를 헤더와 동적 메타데이터로 게이트웨이에 돌려주면, 게이트웨이는 그 Pod로 직접 요청을 보냅니다(Service를 거치지 않음).
  5. 응답 경로응답 헤더·본문도 EPP를 거칠 수 있어, 사용량 집계·프리픽스 기록 갱신 같은 후처리 플러그인이 동작합니다.

엔진의 지표 이름이 바뀌면 EPP가 상태를 못 읽어 사실상 무작위 분배가 됩니다(10편 운영 표). 엔진 업그레이드 때 EPP 설정의 지표 매핑도 함께 확인해야 하는 이유입니다.

EPP 점수 놀이터

Pod 세 개의 상태와 점수 가중치를 바꿔 보며 어느 Pod가 선택되는지 봅니다. 각 점수는 0~1로 정규화해 가중합합니다(대기열은 짧을수록, KV 사용률은 낮을수록, 프리픽스 일치는 높을수록 높은 점수). 실제 EPP 플러그인의 계산식과는 다른 개념 모델입니다.

07장애 시 동작과 고가용성

EPP는 모든 요청이 지나가는 결정 지점입니다. 죽었을 때 어떻게 할지 미리 정해야 합니다.

설정EPP 무응답 시장점단점맞는 곳
FailOpen게이트웨이가 풀의 Pod들에 자체 방식(라운드로빈 등)으로 분배서비스는 계속됨그동안 캐시·부하 인지 이점이 사라지고, 흐름 제어·우선순위도 꺼짐가용성이 최우선인 일반 서비스
FailClose요청 실패 (5xx)정책(우선순위·테넌트 공정성) 우회가 없음EPP 장애가 곧 서비스 장애EPP의 정책 집행이 계약상 중요한 경우, 테넌트 격리

장애 모드 시뮬레이터

  • EPP 레플리카를 2개 이상으로 둡니다. llm-d는 EPP의 액티브-액티브 고가용성을 지원합니다(10편). standalone 모드에서는 프록시가 EPP Pod 안에 있으므로 Pod 수가 곧 입구의 수입니다.
  • EPP 자체의 자원: 요청마다 점수 계산·프리픽스 해시를 하므로 높은 RPS에서는 CPU가 병목이 됩니다. EPP의 지연 지표(스케줄링 시간)를 대시보드에 둡니다.
  • “조용한 장애”: 지표 수집 실패는 에러 없이 라우팅 품질만 떨어뜨립니다. 캐시 적중률·Pod 간 부하 편차를 경보 대상으로 둡니다(20~21편).

08본문 기반 라우팅과 다중 모델

OpenAI 호환 API는 모델 이름이 URL이 아니라 요청 본문(JSON) 안에 있습니다. 그래서 일반 경로 라우팅으로는 모델별로 나눌 수 없습니다.

본문 기반 라우팅(BBR)은 게이트웨이 앞단에서 요청 본문의 model 필드를 읽어 헤더로 꺼내 주는 구성 요소입니다. 그러면 HTTPRoute가 헤더 조건으로 모델별 InferencePool을 고를 수 있습니다. v1.6부터 BBR 구현은 llm-d 쪽에 있습니다.

yaml · 모델 이름으로 두 풀 나누기 (BBR이 모델 이름 헤더를 넣어 준다고 가정, 헤더 이름은 구현 문서 확인)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: llm-by-model, namespace: llmsvc-lab }
spec:
  parentRefs: [ { name: inference-gateway } ]
  rules:
  - matches:
    - path: { type: PathPrefix, value: /v1 }
      headers: [ { name: X-Gateway-Model-Name, value: qwen3-8b } ]
    backendRefs: [ { group: inference.networking.k8s.io, kind: InferencePool, name: qwen3-8b-pool } ]
  - matches:
    - path: { type: PathPrefix, value: /v1 }
      headers: [ { name: X-Gateway-Model-Name, value: qwen3-0.6b } ]
    backendRefs: [ { group: inference.networking.k8s.io, kind: InferencePool, name: qwen3-small-pool } ]
  • LoRA 어댑터는 같은 베이스 모델의 같은 풀 안에서 처리하는 것이 보통입니다. EPP의 LoRA 친화도 점수가 어댑터가 이미 올라간 Pod를 고릅니다(16편).
  • 모델 이름 바꾸기·트래픽 나누기: 앱이 부르는 이름(예: chat-default)을 실제 모델 버전으로 바꾸거나, 새 버전에 일부만 보내는 기능은 예전 InferenceModelRewrite가 맡던 일입니다. 지금은 llm-d 쪽 API나 AI 게이트웨이(12편)에서 다룹니다. 어느 층에서 할지는 한 곳으로 정해 두세요.

실습 11-5 · EPP 장애 실험

python · status_loop.py (bench Pod에서 30초 동안 상태 코드 집계)
import sys, time, json, urllib.request, urllib.error, collections
base, model = sys.argv[1], sys.argv[2]
c = collections.Counter(); end = time.time() + 30
while time.time() < end:
    req = urllib.request.Request(base + "/chat/completions", json.dumps({"model": model, "max_tokens": 4,
          "messages": [{"role": "user", "content": "ping"}]}).encode(), {"Content-Type": "application/json"})
    try:
        c[urllib.request.urlopen(req, timeout=5).status] += 1
    except urllib.error.HTTPError as e:
        c[e.code] += 1
    except Exception as e:
        c[type(e).__name__] += 1
    time.sleep(0.2)
print(dict(c))

앱(외부)은 7편과 같은 게이트웨이 주소를 부르고, 그 뒤에서 Envoy Gateway → lab-pool 프록시 → EPP가 고른 Pod 순으로 갑니다. NetworkPolicy(7편)가 envoy-gateway-system에서 lab-pool 프록시 Pod로의 접근을 허용하는지 확인하세요(기존 정책은 app: llm-engine만 허용). ./lab.sh smoke의 게이트웨이 항목으로 동작을 확인합니다.

실습 11-7 · (읽기) gateway 모드와 우선순위

  • kubectl explain inferencepool.spec.endpointPickerRef로 필드 설명을 읽고, 4장의 HTTPRoute(backendRef: InferencePool) 예시와 비교합니다. Envoy Gateway 자체를 gateway 모드로 쓰는 구성은 12편 Envoy AI Gateway 설치 후 진행합니다.
  • llm-d 문서에서 Objective(우선순위)와 흐름 제어 설정 방법을 찾아, 5장 시뮬레이터의 세 등급(실시간·일반·배치)을 어떤 설정으로 표현할지 적어 봅니다. 우선순위 효과는 풀이 포화될 때만 나타나므로 GPU 한 장 랩에서는 시뮬레이터로 대신합니다.

16정리와 체크리스트

핵심 여섯 문장.

  1. GAIE는 “게이트웨이가 엔드포인트 선택을 추론 전용 구성 요소에 묻는 표준”이다. InferencePool이 GA API이고, 완전한 EPP·BBR 구현은 v1.6부터 llm-d에 있다.
  2. InferencePool = 선택자 + 포트 + EPP 참조 + 실패 모드. HTTPRoute는 Service 대신 InferencePool을 백엔드로 가리킨다.
  3. 우선순위(Objective)와 흐름 제어는 포화 때 무엇을 지킬지 정한다. 높은 대역 먼저, 같은 대역 안은 공정하게, 버틸 수 없으면 낮은 쪽부터 거절한다.
  4. EPP는 ext_proc로 요청을 받아 필터·점수·선택을 한다. 엔진 지표 이름이 바뀌면 라우팅 품질이 조용히 떨어진다.
  5. FailOpen은 가용성, FailClose는 정책 집행을 택한다. EPP는 두 개 이상, 조용한 장애는 캐시 적중률·부하 편차로 잡는다.
  6. AI 게이트웨이는 “누가·얼마나”, Inference Gateway는 “어느 Pod로”. 한 제품이 둘 다 해도 개념은 나눠 둔다.
