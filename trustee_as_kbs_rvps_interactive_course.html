01

왜 Trustee가 필요한가?

“저장할 때”와 “전송할 때”뿐 아니라 “실행 중인 데이터”도 보호해야 하기 때문입니다.

💾

Data at Rest

디스크, DB, 백업에 저장된 데이터. 디스크 암호화나 DB 암호화로 보호합니다.

🌐

Data in Transit

네트워크를 이동하는 데이터. TLS, mTLS, VPN 등으로 보호합니다.

⚙️

Data in Use

CPU와 메모리에서 처리 중인 데이터. TEE 기반 Confidential Computing이 보호하려는 영역입니다.

문제: 디스크와 네트워크가 암호화되어도, 실행 중인 VM의 메모리를 클라우드 관리자나 손상된 호스트가 볼 수 있다면 민감정보가 노출될 수 있습니다.
TEE는 “잠긴 방”을 만들고, Trustee는 “그 방이 진짜 잠겼고 내부 상태가 정상인지 확인한 뒤 열쇠를 건네는 시스템”입니다.

TEE(Trusted Execution Environment)

CPU·펌웨어·가상화 기술을 이용해 워크로드의 메모리와 실행 상태를 외부로부터 격리하는 보호 환경입니다.

  • 호스트 OS나 하이퍼바이저가 완전히 신뢰되지 않아도 보호 목표를 가짐
  • AMD SEV-SNP, Intel TDX, IBM Secure Execution 등이 대표 예
  • “암호화됨”만으로 충분하지 않고, 현재 상태가 정상인지 증명해야 함

원격 증명(Remote Attestation)

멀리 떨어진 서버가 자신의 하드웨어·부팅·런타임 상태에 대한 증거를 보내고, 검증자가 신뢰 여부를 판정하는 절차입니다.

  • 증거가 제조사 신뢰 체인에 의해 서명되었는지 확인
  • 실제 측정값이 승인된 기준값과 일치하는지 확인
  • 오래된 증거 재사용을 막기 위해 새 challenge/nonce와 결합

03

Trustee의 3대 핵심 구성요소

논리적으로는 세 역할이며, 배포 방식에 따라 한 프로세스에 내장되거나 별도 서비스로 구성될 수 있습니다.

🔎
Attestation Service

AS — 증거 검사관

TEE가 보낸 하드웨어 Evidence를 검증하고, TCB Claim을 추출한 뒤, 기준값과 정책에 따라 Attestation Token을 만듭니다.

  • 제조사 서명·인증 체인 확인
  • 플랫폼별 Verifier 실행
  • RVPS 기준값과 비교
  • EAR 형식 판정 토큰 생성
🗝️
Key Broker Service

KBS — 현관·금고 관리자

Guest가 접속하는 Trustee의 Front Door입니다. AS 판정과 Resource Policy를 확인하고 조건을 만족할 때만 비밀을 전달합니다.

  • KBS Protocol과 보안 채널
  • Challenge 기반 freshness
  • Resource URI·정책 판정
  • 파일·Vault·KMS·HSM 연계
📏
Reference Value Provider Service

RVPS — 정상 기준값 관리자

정상 이미지·커널·펌웨어·런타임 등이 가져야 하는 기준 측정값을 수집·저장하고 AS에 제공합니다.

  • Reference Value 등록·조회
  • Manifest 형식에서 값 추출
  • 버전별 기준값 관리
  • 서명된 공급 메시지 활용
암기법: RVPS가 “정답지”를 관리하고 → AS가 “채점”하며 → KBS가 “합격자에게만 열쇠”를 줍니다.

05

AS 상세 — “증거가 진짜이며 정상인가?”

AS는 크게 Verifier와 Attestation Policy의 두 층으로 생각하면 쉽습니다.

🧾

1. Verifier: 진위 확인

플랫폼별 이진 Evidence를 해석하여 제조사 서명·인증서 체인을 확인하고 TCB Claim을 추출합니다.

  • Evidence가 해당 하드웨어에서 생성되었는가?
  • 서명과 endorsement가 유효한가?
  • nonce가 요청한 최신 값과 연결되었는가?
  • 측정 레지스터·보안 버전·디버그 상태는 무엇인가?
⚖️

2. Attestation Policy: 정상성 판단

추출한 Claim을 RVPS의 Reference Value와 비교하고, 어떤 항목을 신뢰 판단에 반영할지 정책으로 계산합니다.

  • 승인된 펌웨어·커널·init-data인가?
  • 필수 보안 옵션이 켜져 있는가?
  • 허용된 런타임 부팅 흐름인가?
  • 결과를 EAR trust tier로 표현

🧪 기준값 비교 실습

실제 값은 긴 해시이지만, 이해를 위해 짧은 문자열로 단순화했습니다.

두 값을 비교해 보세요.

Trustee가 증명할 수 있는 주요 플랫폼 예

AMD SEV-SNPIntel TDXIntel SGX Azure vTPM + SNP/TDXIBM Secure Execution ARM CCAHygon CSVNVIDIA GPU
중요: “Evidence의 서명이 유효하다”와 “워크로드 상태가 안전하다”는 다른 질문입니다. Verifier는 진위를 확인하고, Policy는 안전 기준 충족 여부를 판단합니다.
06

KBS 상세 — “어떤 비밀을 누구에게 줄 것인가?”

KBS는 Trustee의 Front Door이며, 증명과 비밀 전달을 하나의 안전한 의사결정 흐름으로 연결합니다.

🚪

Protocol 종단점

Guest의 AA/CDH가 연결하는 서버입니다. 최신 Evidence와 결합된 보안 채널을 구성합니다.

📜

Resource Policy

AS Token, Resource URI, TEE 종류, 워크로드 Claim 등을 보고 요청 허용 여부를 결정합니다.

🗄️

Secret Backend

로컬 파일, 외부 플러그인, Vault/OpenBao, Azure Key Vault, PKCS#11 HSM 등의 비밀을 제공합니다.

🧪 KBS 정책 판정 실습

아래 교육용 정책은 “Affirming + 승인 TEE + prod 경로”일 때만 허용합니다.

조건을 선택하고 정책을 평가해 보세요.

Resource URI 이해

kbs:///default/key/1

부분예의미
Schemekbs:///Trustee/KBS Resource임을 표시
Repositorydefault논리 저장소 또는 테넌트 구분
Typekey리소스 종류
Tag1개별 이름·버전·식별자

공식 문서의 전체 형식은 kbs://<host>:<port>/<repository>/<type>/<tag>이며, 실제로는 host/port 결합을 피하기 위해 경로 중심으로 쓰는 경우가 많습니다.

07

RVPS 상세 — “정상 상태의 정답지는 무엇인가?”

Reference Value는 단순 허용 목록이 아니라, 빌드·배포·업데이트 수명주기와 연결되는 신뢰의 기준입니다.

1
신뢰 가능한 빌드
승인된 이미지·커널·펌웨어를 빌드하고 측정값을 생성합니다.
2
Reference Value 발행
공급망에서 값과 provenance를 만들고 가능하면 서명합니다.
3
RVPS 등록
Extractor가 manifest를 해석하여 AS가 사용할 기준값으로 저장합니다.
4
AS에서 비교
Evidence에서 추출한 TCB Claim과 기준값을 Attestation Policy로 비교합니다.
5
버전 전환·폐기
패치 시 새 값을 추가하고 전환 기간 후 취약·구버전 값을 제거합니다.

좋은 기준값 운영

  • 빌드 파이프라인이 자동 생성하고 서명
  • 환경(dev/stg/prod)과 버전별 분리
  • 롤백 기간을 고려한 다중 값 허용
  • 변경 승인·감사 이력 유지
  • 취약 버전은 신속히 폐기

나쁜 기준값 운영

  • 운영자가 채팅으로 받은 해시를 수동 등록
  • 모든 버전 값을 영구 허용
  • 개발 기준값을 운영에 그대로 사용
  • 빌드 출처·서명 확인 없이 ingest
  • RVPS 백업·복구 계획이 없음
업데이트 함정: 정상 커널을 패치하면 측정값이 달라질 수 있습니다. Reference Value를 먼저 안전하게 등록하지 않으면 새 워크로드가 모두 증명 실패할 수 있습니다.

문지기 1: “건물 안전검사”

건물 자체가 안전한지 검사합니다. 어떤 사람이 어느 방에 들어갈지는 아직 판단하지 않습니다.

AS Policy

문지기 2: “방별 출입권한”

안전검사를 통과한 건물 안에서도 사람·업무·방에 따라 접근 권한을 다르게 적용합니다.

KBS Policy 
# 교육용 개념 예시 — 실제 배포 시 해당 Trustee 버전의 input schema를 확인하세요.
package policy
import rego.v1

default allow := false

allow if {
  input.attestation_status == "affirming"
  input.tee in {"snp", "tdx"}
  startswith(input.resource_path, "prod/payment/")
}
운영 금지: allow-all은 연결 테스트 외에는 안전한 정책이 아닙니다. “TEE를 사용했다”는 사실만 확인하고 TCB 정상성을 보장하지 않는 정책도 운영 비밀에는 부족할 수 있습니다.

10

기본 사용 방법과 단계별 실습

명령은 공식 문서의 현재 예를 토대로 정리했습니다. 실제 실행 전 사용 중인 릴리스의 --help와 문서를 확인하세요.

관리자 준비

Trustee 배포 → Admin 인증키 → Resource·Reference Value·Policy 등록

Guest 준비

TEE Runtime → KBS URI 설정 → AA/CDH가 KBS에 접근 가능하도록 네트워크 구성

검증

정상 Guest 성공 → 변조·구버전·잘못된 Resource 실패를 모두 테스트

용도: Docker Compose는 개발자 평가·PoC의 빠른 시작점입니다. 실제 하드웨어 증명 검증은 지원 TEE 환경과 Guest 설정이 추가로 필요합니다.
git clone https://github.com/confidential-containers/trustee.git
cd trustee
docker compose up -d
# 상태와 로그 확인
docker compose ps
docker compose logs -f

# 디버그 로그를 켜고 시작하는 예
printf 'RUST_LOG=debug\n' > debug.env
docker compose --env-file debug.env up

Docker Compose 구성은 시작 시 KBS, AS, RVPS 설정 파일을 읽습니다. 설정을 변경한 뒤에는 docker compose restart가 필요할 수 있습니다.

ORAS로 KBS Client 받기

oras pull ghcr.io/confidential-containers/staged-images/kbs-client:latest
chmod +x kbs-client
./kbs-client --help

소스에서 빌드하기

git clone https://github.com/confidential-containers/trustee.git
cd trustee/kbs
make CLI_FEATURES=sample_only cli
sudo make install-cli
차이: sample_only 빌드는 관리·시험에 가볍지만, Enclave 내부에서 실제 하드웨어 Attester를 사용해 Resource를 가져오는 용도에는 필요한 기능이 빠질 수 있습니다.

비밀 파일 등록

# 예: 비밀 파일 준비
printf 'SuperSecret-Change-Me' > db-password.txt

# 현재 문서 계열 예시
kbs-client --url http://KBS_HOST:8080 config \
  --auth-private-key ./kbs/config/private.key \
  set-resource \
  --path prod/db/password \
  --resource-file ./db-password.txt
CLI 버전 주의: 릴리스에 따라 Admin 인증 옵션이 --auth-private-key 또는 --admin-token-file 형태로 나타날 수 있습니다. 설치한 바이너리의 kbs-client config --help를 기준으로 사용하세요.

Guest 내부 CDH를 통한 요청 예

# Confidential Containers Pod 내부에서
curl http://127.0.0.1:8006/cdh/resource/prod/db/password

이 REST 호출은 Pod 네트워크 네임스페이스에 노출된 CDH로 요청합니다. CDH/AA가 증명을 수행하고 Trustee가 허용해야 실제 Resource가 반환됩니다.

Reference Value 등록·조회

kbs-client --url http://KBS_HOST:8080 config \
  --admin-token-file ADMIN_TOKEN \
  set-sample-reference-value kernel_digest sha384:APPROVED_VALUE

kbs-client --url http://KBS_HOST:8080 config \
  --admin-token-file ADMIN_TOKEN \
  get-reference-values

정책 등록

kbs-client --url http://KBS_HOST:8080 config \
  --admin-token-file ADMIN_TOKEN \
  set-attestation-policy --policy-file ./attestation.rego

kbs-client --url http://KBS_HOST:8080 config \
  --admin-token-file ADMIN_TOKEN \
  set-resource-policy --policy-file ./resource.rego
테스트 순서: 처음부터 운영 비밀로 확인하지 말고, 가짜 Test Resource로 정상 허용·변조 거부·경로 거부를 모두 확인한 뒤 운영 키를 연결하세요.

Pod Annotation으로 KBS URI 전달하는 개념 예

apiVersion: v1
kind: Pod
metadata:
  name: trustee-demo
  annotations:
    io.katacontainers.config.hypervisor.kernel_params: >-
      agent.aa_kbc_params=cc_kbc::http://KBS_IP:8080
spec:
  runtimeClassName: kata-qemu-coco-dev
  containers:
    - name: app
      image: your-registry/example:latest
  • KBS_IP는 Guest에서 접근 가능한 주소여야 하며 localhost를 사용하면 안 됩니다.
  • 운영에서는 init-data로 AA와 CDH 설정에 KBS URI를 전달하는 방식을 함께 검토합니다.
  • RuntimeClass는 실제 플랫폼(SNP, TDX, SE, GPU 등)에 맞게 선택합니다.
  • 네트워크 방화벽, DNS, 인증서, 프록시를 Guest 관점에서 확인합니다.
이 실습의 한계: Docker에서 Trustee를 실행하는 것만으로 실제 Remote Attestation이 완성되는 것은 아닙니다. 지원 TEE 하드웨어, Guest Attestation Agent, 올바른 Reference Value와 Policy가 함께 구성되어야 합니다.

💳

금융·결제 처리

결제 키나 개인정보 처리용 키를 승인된 TCB·정책의 결제 워크로드에만 제공합니다.

🧬

민감한 유전체·의료 데이터의 복호화 키를 검증된 분석 환경에서만 사용할 수 있게 합니다.

🌍

다기관 공동 분석

데이터 제공자가 인프라 운영자를 완전히 신뢰하지 않아도 승인된 코드·환경임을 확인하고 키를 제공합니다.

적용 여부 판단 질문

Trustee가 특히 유용한 경우
  • 클라우드·호스트 관리자를 신뢰 경계 밖에 두고 싶다
  • 비밀을 이미지·Manifest에 미리 넣고 싶지 않다
  • 실행 환경의 측정 상태에 따라 키를 줄지 결정해야 한다
  • TEE CPU뿐 아니라 GPU·Device 증명도 결합하고 싶다
다른 도구만으로 충분할 수 있는 경우
  • 호스트와 관리자를 완전히 신뢰하고 일반 Secret 주입만 필요하다
  • 실행 중 데이터 보호 요구가 없다
  • 단순 애플리케이션 ID·RBAC만으로 접근제어가 충분하다
  • TEE 하드웨어·운영 복잡성을 감당하기 어렵다

장애 진단 순서

비밀 요청 실패를 “네트워크 → 증거 → 기준값 → 정책 → Backend” 순으로 나누면 빠르게 원인을 찾을 수 있습니다.

1. KBS에 연결 자체가 안 됩니다.
Guest에서 KBS 주소·포트에 접근 가능한지, localhost를 잘못 사용하지 않았는지, DNS·방화벽·프록시·TLS 인증서를 확인합니다. Host가 아니라 Guest 네트워크 관점에서 테스트합니다.
2. Evidence 검증이 실패합니다.
TEE RuntimeClass가 실제 하드웨어와 맞는지, 펌웨어·커널·Quote/Report 생성 기능이 정상인지, 제조사 endorsement 조회가 가능한지, Trustee가 해당 플랫폼 verifier를 포함한 이미지인지 확인합니다.
3. 업데이트 후 Attestation이 전부 실패합니다.
새 커널·펌웨어·Guest 이미지로 측정값이 바뀌었지만 RVPS에 새 Reference Value가 등록되지 않았을 가능성이 큽니다. 구·신 버전 전환 기간과 정책을 확인합니다.
4. AS는 성공했는데 KBS가 Resource를 거부합니다.
Attestation Token의 status, Resource URI, TEE 종류, init-data claim 등이 KBS Resource Policy 조건과 맞는지 확인합니다. AS 정책과 KBS 정책을 혼동하지 마세요.
5. Policy는 허용인데 Resource가 없습니다.
Resource path 오타, repository/type/tag 경로, 파일 backend mount, Vault/Key Vault/HSM 권한, 플러그인 설정과 timeout을 확인합니다.
6. Docker Compose에서는 되는데 운영 환경에서 안 됩니다.
PoC의 sample attester·allow 정책·평문 HTTP·로컬 filesystem이 운영의 실제 TEE·엄격 정책·TLS·외부 KMS로 바뀌면서 발생한 차이를 비교합니다. 환경별 설정 차이를 표로 만들어 확인하세요.
7. 토큰이 너무 커서 HTTP 오류가 발생합니다.
장치가 많은 Guest는 Attestation Token이 커질 수 있습니다. 공식 문서의 AS 설정에서 verbose token 옵션과 HTTP 헤더 한계를 검토합니다.

이해도 퀴즈

각 문항을 클릭하면 바로 해설이 표시됩니다.

1. 승인된 정상 측정값을 관리하는 구성요소는?
RVPS는 Reference Value를 관리하고 AS에 제공합니다.
2. Guest가 연결하는 Trustee의 Front Door는?
KBS가 Guest 요청을 받고 증명과 Resource 전달을 중개합니다.
3. AS가 주로 생성하는 결과는?
AS는 Evidence를 검증하고 TCB 상태를 나타내는 EAR Attestation Token을 반환합니다.
4. “prod/payment/key를 이 워크로드에 줄 것인가?”를 판단하는 것은?
특정 Resource의 전달 여부는 KBS Resource Policy가 결정합니다.
5. Reference Value가 새 커널과 맞지 않으면?
측정값이 바뀌었는데 새 기준값이 없으면 정상 업데이트도 거부될 수 있습니다.
6. Fresh nonce가 필요한 가장 큰 이유는?
새 challenge와 Evidence를 결합하여 오래된 증거의 replay를 어렵게 합니다.
7. Docker Compose 실습만으로 실제 TEE 증명이 완성되는가?
Trustee 서버 실행 외에도 지원 하드웨어, Guest AA/CDH, 기준값, 정책이 필요합니다.
8. Secret Backend가 될 수 없는 것은?
Secret Backend는 파일, KMS, Vault, HSM 등 비밀 저장·조회 시스템입니다.
9. AS Verifier와 Policy의 올바른 구분은?
진위 검증과 정상성 판단을 분리하면 플랫폼 코드와 런타임 정책을 유연하게 관리할 수 있습니다.
10. 가장 안전한 운영 원칙은?
정책·기준값·관리키를 엄격히 관리하고 필요한 비밀만 허용해야 합니다.

초보자를 위한 용어 사전

검색창에 “증거”, “키”, “정책”, “TEE” 등을 입력해 보세요.

Trustee
TEE 증명과 조건부 비밀 전달을 제공하는 구성요소 집합.
TEE
실행 중 데이터와 코드를 보호하는 하드웨어 기반 격리 환경.
Remote Attestation
원격 시스템이 자신의 보안 상태를 증거로 증명하는 절차.
Evidence
TEE가 생성한 서명된 상태 증명 자료. 플랫폼에 따라 Report·Quote 등으로 불림.
Endorsement
Evidence의 진위를 검증할 수 있도록 제조사·플랫폼이 제공하는 신뢰 자료.
TCB
시스템 보안을 보장하기 위해 신뢰해야 하는 하드웨어·펌웨어·소프트웨어 기반.
Claim
Evidence에서 추출된 보안 버전, 측정값, 디버그 상태 등의 속성.
Measurement
부팅 구성요소나 설정을 해시 등으로 측정한 값.
Reference Value
정상·승인된 시스템이 가져야 하는 기준 측정값.
Attestation Token
AS가 Evidence 검증 후 생성하는 표준화된 판정 결과.
EAR
Entity Attestation Result. Trustee AS가 사용하는 Attestation Result 표현 형식.
Nonce / Challenge
매 요청마다 새로 만드는 값. Evidence의 최신성을 확인하고 재전송 공격을 줄임.
Policy
증명 결과 계산이나 비밀 전달 허용 여부를 정하는 규칙.
OPA / Rego
정책을 코드로 평가하는 엔진과 정책 언어. Trustee의 두 정책에 사용됨.
Resource
KBS가 조건부로 제공하는 키, 비밀번호, 인증서, 토큰 등의 비밀.
AA
Attestation Agent. Guest 내부에서 하드웨어 Evidence를 얻고 증명 절차에 참여.
CDH
Confidential Data Hub. Guest에서 비밀·암호화 이미지 등 민감 작업을 처리.
KBS
증명 흐름을 중개하고 정책에 따라 Resource를 전달하는 Trustee의 Front Door.
AS
Evidence를 검증하고 Attestation Token을 생성하는 서비스.
RVPS
Reference Value를 수집·저장·제공하는 서비스.
KBC
Guest 측에서 Key Broker와 통신하는 클라이언트 계층 또는 구현.
