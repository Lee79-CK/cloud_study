02

hx-boost

hx-boost는 평범한 <a href>와 <form action>을 htmx 요청으로 바꿉니다. 링크·폼 자체는 그대로이므로 JavaScript가 꺼져 있어도 동작하는, 가장 쉬운 점진적 향상(progressive enhancement)입니다.

부스트가 바꾸는 것 (4.0.1 소스)값
요청 주소·메서드링크는 href로 GET, 폼은 action·method (제출 버튼의 formaction·formmethod 우선)
대상hx-target이 없으면 body
주소 기록hx-push-url·hx-replace-url이 없으면 push
스크롤본 스왑에 show:top이 기본으로 붙음 (hx-swap="show:none"으로 끔)
요청 헤더HX-Boosted: true, 대상이 body이므로 HX-Request-Type: full
body 교체 방식body에 outerHTML을 쓰면 outerSync로 바뀌어 body 요소 자체는 유지 (5편)
htmx 4에서는 :inherited가 필수

2.x에서는 <nav hx-boost="true"> 하나로 안의 링크가 모두 부스트됐습니다. 4.x는 상속이 명시적이라 <nav hx-boost:inherited="true">로 써야 합니다. 특정 링크만 빼려면 그 링크에 hx-boost="false"를 답니다. 소스의 #maybeBoost는 값이 "false"면 부스트하지 않습니다.

부스트 대상 판별기 (htmx 4.0.1 실동작)

아래 링크들은 hx-boost:inherited="true"인 div 안에 있다. 누르지 않고 판별 결과만 본다
<a href="page2.html"> 같은 출처 일반 링크1
<a href="page2.html" target="_blank">2
<a href="report.csv" download>3
<a href="#s9"> 같은 페이지 앵커4
<a href="https://example.com/"> 다른 출처5
<a href="page2.html" hx-boost="false">6
<form method="dialog">
<form action="save" method="post">
오른쪽 상자는 hx-boost="true" (:inherited 없음)인 div 안의 일반 링크입니다.
<a href="page2.html">9

판별 규칙은 소스의 #shouldBoost 그대로입니다. 링크는 target이 비었거나 _self이고, download가 없고, #로 시작하지 않고, 같은 출처여야 합니다. 폼은 method="dialog"가 아니고 같은 출처여야 합니다. 오른쪽 상자의 결과가 4.x의 명시적 상속을 확인시켜 줍니다.

03

부스트와 스크립트

부스트 이동은 문서를 새로 불러오지 않고 <body>만 바꿉니다. 그래서 "언제 다시 실행되는가"가 전체 새로고침과 다릅니다. 랩에서 실제로 측정한 결과입니다.

스크립트 위치부스트 이동 시측정·근거
<head>의 스크립트다시 실행 안 됨htmx는 응답의 <head>에서 제목만 꺼내고 나머지는 버린다(#makeFragment)
<body> 안의 일반 인라인 스크립트매번 다시 실행스왑한 조각의 스크립트를 새 요소로 바꿔 실행(#processScripts). 최상위 const·let이 있으면 두 번째부터 "already declared" 오류
<body> 안의 type="module" 외부 스크립트첫 방문만 실행같은 URL의 모듈은 브라우저 모듈 맵에서 한 번만 평가. 랩 점검 페이지를 두 번째로 부스트 방문하자 React 상자가 비어 있었다
window·document 변수유지테스트에서 이동 전 window에 넣은 표식이 이동 후에도 남아 있었다(같은 문서)

그래서 랩은 두 가지를 바꿨습니다. 첫째, 레이아웃과 VM 페이지의 인라인 스크립트(확인 대화상자, 전역 오류 토스트, 삭제 카운터)를 /js/portal.js로 옮겨 <head>에서 defer로 한 번만 불러옵니다. document에 건 리스너가 이동할 때마다 쌓이지 않고, 대화상자 요소처럼 이동 때마다 새로 그려지는 것은 리스너 안에서 그때그때 찾습니다. 6편에서 302 나쁜 예가 일으켰던 "Identifier 'dialog' has already been declared" 오류도 이 변경 뒤 같은 테스트에서 사라졌습니다. 둘째, 랩 점검 링크에는 hx-boost="false"를 달았습니다. 아일랜드 모듈이 첫 방문에만 실행되는 문제는 12편에서 웹 컴포넌트로 근본적으로 해결하고, 그때 이 예외를 지웁니다.

04

주소 기록: push와 replace

방법값의미
hx-push-urltrue / false / 경로새 기록 항목 추가. 뒤로 가기로 돌아올 수 있음
hx-replace-url같음현재 기록 항목의 주소만 교체
응답 헤더 HX-Push-Url·HX-Replace-Url같음요소 속성보다 우선 (6편)
hx-status:코드="push:..."같음상태 코드별로 덮어씀 (6편)

true는 "이 요청의 주소"를 기록한다는 뜻인데, 4.0.1 소스는 이때 응답의 최종 URL(response.url, 리다이렉트를 따라간 뒤의 주소)을 우선 씁니다. 서버가 302로 다른 주소로 보냈다면 그 도착 주소가 기록됩니다. 앵커(#...)가 붙은 요청이면 앵커도 함께 기록됩니다.

상황선택이유
상세 패널 열기, 메뉴 이동push사용자가 "다른 곳에 갔다"고 느끼는 이동. 뒤로 가기로 돌아올 수 있어야 함
검색어·필터 변경replace타이핑마다 기록이 쌓이면 뒤로 가기가 쓸모없어짐 (6편 HX-Replace-Url)
탭 전환, 정렬 변경상황에 따라 replace공유하고 싶은 상태면 기록하되 기록 수는 늘리지 않음
저장·삭제 같은 동작기록 안 함뒤로 가기가 동작을 되돌리는 것처럼 보이면 안 됨
05

주소로 화면을 재현하라

주소를 기록하는 순간 서버에 약속이 생깁니다. "이 주소를 주소창에 넣으면 지금과 같은 화면을 주겠다." 이 약속을 지키지 못하면 새로고침·공유·새 탭·뒤로 가기가 모두 어긋납니다.

3편에서 만든 /vms/web-01의 전체 페이지는 레이아웃 + 상세 하나뿐이었습니다. 그런데 이번 편에서 목록의 VM 링크를 누르면 목록은 그대로 둔 채 상세 패널만 바뀌고 주소가 /vms/web-01이 됩니다. 이 상태에서 새로고침하면 목록이 사라진 다른 화면이 나오는 셈입니다. 그래서 전체 페이지를 "목록 + 상세가 열린 패널"로 바꿨습니다.

apps/server/src/app.js (GET /vms/:name)
const activity = store.activityPage(vm);
if (wantsFragment(req)) {
  // 주소를 push하는 상세 조각에 <title>을 넣어 탭 제목도 함께 바꾼다 (htmx가 스왑 후 document.title에 적용)
  return send(res, part('./partials/doc-title', { text: `${vm.name} · VM 관리` }) + part('./partials/vm-detail', { vm, activity }));
}
// 주소창·새로고침·뒤로 가기로 /vms/web-01을 열면 "목록 + 상세가 열린 패널"을 한 번에 그린다
const page = store.paginate(store.search('', ''), 1);
const more = page.nextPage ? '/vms?' + new URLSearchParams({ q: '', status: '', page: page.nextPage }) : null;
render(res, './pages/vms', { title: `${vm.name} · VM 관리`, list: page.items, more, q: '', status: '', total: page.total,
                             sum: store.summary(), detail: { vm, activity } });

VM 페이지 템플릿은 it.detail이 있으면 aside 안에 상세 조각을 include하고, 없으면 안내 문구를 둡니다. 같은 조각 템플릿을 페이지와 조각 응답이 함께 쓰는 2편의 원칙이 여기서도 그대로 통합니다. 3편의 pages/vm.eta는 더 이상 쓰지 않아 지웠습니다.

한계와 다음 단계

지금은 상세 주소에 검색 조건이 담기지 않아, "db"로 검색한 상태에서 web-01을 열고 새로고침하면 목록은 검색 전 상태로 나옵니다. 상세 주소에 목록 상태까지 담으려면 /vms/web-01?q=db처럼 쿼리를 이어 붙이고 서버가 그것을 반영하면 됩니다. 이 개선은 15편 통합 셸의 라우팅 규칙을 정할 때 함께 다룹니다.

06

뒤로 가기: 다시 요청하는 복원

htmx 2는 이동할 때마다 화면 스냅샷을 localStorage에 저장했다가 뒤로 가기 때 꺼내 썼습니다. htmx 4는 기본으로 아무것도 저장하지 않고, 뒤로 가기 때 그 주소를 서버에 다시 요청합니다. 1편에서 말한 "서드파티 스크립트와의 충돌이 사라진" 이유가 이것입니다.

① 기록 표시htmx가 처음 주소를 기록할 때 현재 항목에 {htmx: true} 상태를 찍어 둠
② 뒤로 가기 감지Navigation API의 navigate(traverse)를 가로채거나, 없으면(파이어폭스 등) popstate
③ htmx:before:history:restore취소 가능. 확장이 여기서 캐시를 꺼냄
④ 다시 요청GET 현재 주소 + HX-History-Restore-Request: true
⑤ 교체대상은 [hx-history-elt] 요소 또는 body, 방식은 outerSync
실측: 복원 요청에는 HX-Request가 없다

브라우저로 뒤로 가기를 하며 요청 헤더를 기록해 보니, 복원 요청에는 HX-History-Restore-Request: true와 HX-Request-Type: full만 있고 HX-Request·HX-Current-URL·HX-Source가 없었습니다. 4.0.1 소스의 htmx.ajax()가 옵션의 request 객체로 요청 정보를 통째로 교체하면서 기본 헤더가 빠지는 것으로 보입니다. "htmx 요청인가"를 HX-Request만으로 판단하는 서버는 복원 요청을 일반 페이지 요청으로 봅니다. 화면 응답은 어차피 전체 페이지라 문제없지만, 6편의 인증 미들웨어처럼 htmx 여부로 응답을 바꾸는 코드는 영향을 받습니다. 랩은 두 헤더 중 하나라도 있으면 htmx 요청으로 보도록 고쳤고, 그 결과 세션이 끝난 뒤 뒤로 가기를 하면 401 + HX-Redirect로 로그인 화면(?next=는 복원하려던 주소)으로 정확히 이동했습니다. htmx를 올릴 때 이 동작이 바뀌었는지 다시 확인하세요.

설정·속성효과
htmx.config.history = true (기본)위 방식으로 복원
htmx.config.history = "reload"복원 시 페이지 전체 새로고침
htmx.config.history = falsehtmx가 주소 기록·복원을 하지 않음
hx-history-eltbody 대신 이 요소만 복원 대상으로 (응답에서도 같은 요소만 골라 씀)
07

hx-history-cache 확장

"뒤로 가기마다 서버에 요청하기 싫다"면 4.x 배포본의 hx-history-cache 확장을 씁니다. 2.x 방식처럼 화면을 저장해 두되, 저장소는 sessionStorage(탭 단위)입니다.

켜는 방법 (htmx 다음에 불러오기만 하면 전역 등록)
<script src="/vendor/htmx/htmx.min.js"></script>
<script src="/vendor/htmx/ext/hx-history-cache.js" defer></script>

htmx 4의 확장은 스크립트를 불러오면 htmx.registerExtension()으로 전역 등록됩니다. 2.x의 hx-ext 속성은 필요 없고, 대신 htmx.config.extensions에 이름 목록을 적으면 그 목록에 있는 확장만 허용됩니다. 확장 소스에서 확인한 기본 설정은 htmx.config.historyCache = { size: 10, refreshOnMiss: false, disable: false, swapStyle: 'outerSync' }입니다.

랩에서 측정한 결과

확장을 켠 상태로 "web" 검색 → web-01 열기 → web-02 열기 → 뒤로 가기를 했더니, 복원 요청이 한 건도 나가지 않고 web-01 상세가 돌아왔으며 검색창의 "web"도 복원됐습니다(확장이 입력값·스크롤을 저장해 둠). sessionStorage에는 htmx-history-<id> 항목들과 색인이 생겼습니다.

보안 주의: 세션이 끝나도 캐시된 화면은 보인다

같은 측정에서 뒤로 가기 직전에 세션을 만료시켰는데도 캐시에서 web-01 상세가 그대로 복원됐습니다. 서버에 묻지 않으니 인증 검사도 없습니다. 운영 포털의 고객 정보·청구 화면처럼 민감한 페이지는 hx-history="false" 요소를 페이지에 두어 저장 대상에서 빼거나(확장의 저장 함수가 이 요소가 있으면 저장하지 않음), 확장 자체를 쓰지 않는 편이 안전합니다. 로그아웃 때 sessionStorage를 비우는 것도 함께 고려하세요. 그래서 랩은 이 확장을 레이아웃에 주석으로만 넣어 두었습니다.

08

Ctrl+클릭 문제와 우회

진짜 링크(<a href>)로 바꾼 이유 중 하나는 Ctrl·Cmd+클릭으로 새 탭에서 여는 브라우저 기본 동작을 살리기 위해서였습니다. 그런데 측정해 보니 htmx 4.0.1에서는 그렇게 되지 않았습니다.

링크 (Ctrl+클릭)새 탭현재 탭
목록의 VM 링크 (hx-get + href)열리지 않음변화 없음 (htmx 요청도 없음)
부스트된 메뉴 링크열리지 않음변화 없음
hx-boost="false"인 메뉴 링크열림변화 없음

원인은 소스에서 바로 보입니다. 트리거 리스너가 먼저 #shouldCancel로 링크 클릭의 기본 동작을 막고(preventDefault), 그 뒤 요청 처리 단계에서 수정 키가 눌린 클릭(#isModifierKeyClick)이면 요청을 포기합니다. 요청도 안 보내고 기본 동작도 막힌 상태가 되는 것입니다. 수정 키 클릭을 존중하려는 코드가 있는 것으로 보아 의도된 동작은 아닌 것 같습니다. 가운데 버튼 클릭은 click이 아닌 auxclick 이벤트라 영향받지 않습니다.

apps/server/public/js/portal.js (우회 코드)
document.addEventListener('click', (e) => {
  if (e.button !== 0 || !(e.ctrlKey || e.metaKey || e.shiftKey)) return;
  const link = e.target.closest?.('a[href]');
  if (link) e.stopPropagation();
}, true);

document의 캡처 단계에서 수정 키 클릭을 멈추면 이벤트가 링크에 걸린 htmx 리스너까지 내려가지 않으므로 브라우저 기본 동작(새 탭)이 살아납니다. 우회 후 같은 측정에서 세 링크 모두 새 탭이 열렸고, 새 탭의 /vms/web-03은 5절의 "목록 + 상세" 전체 페이지로 정상 표시됐습니다. 코드 주석에 "htmx를 올릴 때 다시 확인하고 고쳐졌으면 지울 것"을 남겨 두었습니다.

명시적 상속

1편부터 "htmx 4는 상속이 명시적"이라고 반복했습니다. 이번 편에서 규칙을 소스(#attributeValue) 기준으로 완전히 정리합니다.

표기위치의미
hx-속성="값"요소 자신그 요소에만 적용. 자식에게 물려주지 않음
hx-속성:inherited="값"조상자기 자신과 모든 자손에게 적용. 자손이 같은 속성을 직접 가지면 자손의 값이 이김
hx-속성:append="값"자손가장 가까운 상속 값 뒤에 ,값을 덧붙임 (hx-include 같은 목록형 속성에 유용)
hx-속성:inherited:append="값"중간 조상위에서 물려받은 값에 덧붙이면서, 그 결과를 다시 아래로 물려줌
htmx.config.implicitInheritance = true전역2.x처럼 :inherited 없이도 상속 (이전 기간용 다리)

상속 실험실 (htmx 4.0.1 실동작)

각 상자의 버튼을 눌러 응답이 어디에 들어가는지, 무엇이 전송되는지 확인
부모: hx-target="#inh-a-t"
#inh-a-t (부모가 가리킨 곳)
부모: hx-target:inherited="#inh-b-t"
#inh-b-t (부모가 가리킨 곳)
부모: hx-target:inherited="#inh-c-t" 자식: hx-target="#inh-c-own"
#inh-c-t (부모)
#inh-c-own (자식 자신)
부모: hx-include:inherited="#inh-f1" 자식: hx-include:append="#inh-f2"
#inh-d-t
전역 설정을 켜고 첫 상자를 다시 눌러 보세요
상자결과 (측정)
1 (부모에 그냥 hx-target)응답이 버튼 자신을 바꿈. HX-Target: button. 전역 설정을 켜면 #inh-a-t로 감
2 (부모에 :inherited)#inh-b-t로 감
3 (부모 :inherited + 자식 직접 지정)자식이 이김: #inh-c-own
4 (hx-include:inherited + :append):append 버튼은 region=seoul&team=ops, 덧붙임 없는 버튼은 region=seoul만
