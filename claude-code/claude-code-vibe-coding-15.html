플러그인묶어서 나누기

10~13편에서 vibe-lab 안에 하나씩 만든 런북 Skill, 가드 Hook, 리뷰어·조사관, k8s-ro MCP. 이제 이것을 msp-toolkit이라는 한 꾸러미로 묶어, 동료가 명령 한 줄로 설치하고 업데이트를 받게 합니다.

단독 설정과 플러그인 중 무엇이 맞는지, 무엇을 넣고 뺄지 판단한다
plugin.json과 표준 디렉토리 구조로 플러그인을 만든다
플러그인이 되면 바뀌는 이름과 제한되는 필드를 안다
사내 마켓플레이스를 만들어 팀 저장소에서 자동 설치되게 한다
~ — msp-toolkit
1 / 16

플러그인이란, 언제 만드나

플러그인은 Skill·서브에이전트·Hook·MCP 서버를 담은 디렉토리에, 이름을 붙이는 plugin.json(매니페스트)을 더한 것입니다. Claude Code는 이 디렉토리를 한 단위로 읽어서, 동료와 나누거나 여러 프로젝트에 설치하거나 마켓플레이스에 올릴 수 있게 합니다.

공식 문서의 기준은 단순합니다. Skill·에이전트·Hook·MCP는 모두 프로젝트나 홈 디렉토리에서 단독으로 동작합니다. 한 프로젝트, 또는 나 혼자 쓰는 동안은 단독 설정을 유지하세요. 팀과 나누거나, 여러 프로젝트에 깔거나, 버전을 붙여 배포하고 싶을 때 플러그인으로 만듭니다.

상황알맞은 것
vibe-lab 한 저장소에서만, 팀원도 그 저장소를 쓴다단독 설정을 .claude/에 커밋
나 혼자 모든 프로젝트에서~/.claude/의 개인 설정
고객사별 저장소 수십 개에 같은 가드·런북을플러그인
팀이 버전을 맞춰 쓰고 업데이트를 받아야플러그인 + 마켓플레이스

무엇을 넣고 무엇을 빼나

지금까지 만든 것을 하나씩 분류해 보세요. 플러그인에는 여러 프로젝트에서 그대로 통하는 것을 넣고, 저장소마다 다른 것은 그 저장소에 남깁니다. 이 강의의 판단 기준입니다.

플러그인 구조

위치내용
.claude-plugin/plugin.json매니페스트. name만 필수(공백 없이), description·version·author
skills/<이름>/SKILL.mdSkill (10편)
commands/예전 형식. 새 플러그인은 skills/
agents/서브에이전트 파일 하나씩 (13편)
hooks/hooks.json최상위 "hooks" 키. 모양은 settings의 hooks와 같음 (11편)
.mcp.jsonMCP 서버 정의 (12편)
.claude-plugin/ 안에는 plugin.json만 가장 흔한 실수입니다. skills/를 .claude-plugin/ 안에 넣으면 로드되지 않습니다. 구성 요소 디렉토리는 플러그인 루트(그 디렉토리를 --plugin-dir에 넘기는 곳)에 둡니다. 또 플러그인 루트는 그 플러그인의 디렉토리이지 ~/.claude/가 아닙니다.

경로 자리표시자

${CLAUDE_PLUGIN_ROOT}

플러그인이 설치된 디렉토리. Hook·MCP·Skill에서 함께 넣은 스크립트를 가리킬 때. 업데이트마다 경로가 바뀌므로 하드코딩 금지.

${CLAUDE_PLUGIN_DATA}

업데이트해도 남는 플러그인 데이터 디렉토리. 설치한 의존성·캐시·생성 파일용.

exec 형식 권장

11편처럼 Hook은 "command": "python3", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/…"]. 경로에 공백이 있어도 안전합니다.

userConfig

설치할 때 사용자에게 값을 물을 수 있습니다(예: 웹훅 URL). /plugin으로 설치할 때 대화창이 뜨고, 나중에는 /plugin configure 이름.

msp-toolkit 둘러보기

이번 실습에서 만들 마켓플레이스 저장소입니다. 파일을 눌러 보세요. 청록은 새로 쓰는 파일, 흰색은 10~13편에서 옮겨 온 파일입니다. JSON은 파싱, frontmatter는 YAML 해석, Hook·MCP가 가리키는 스크립트 경로가 실제로 있는지까지 확인했습니다.

5 / 16

이름이 바뀐다

플러그인의 Skill과 에이전트에는 플러그인 이름이 접두어로 붙습니다. 그래서 두 플러그인이 각자 runbook을 가져도 충돌하지 않습니다. 권한 규칙·Hook matcher·서브에이전트 tools에 쓰던 이름도 함께 바꿔야 합니다.

Hook에는 접두어가 없습니다 → 두 번 실행 주의 옛 설정을 그대로 둔 채 플러그인을 켜면, Skill과 에이전트는 접두어 덕분에 따로 공존하지만(/runbook과 /msp-toolkit:runbook), 같은 Hook은 settings와 플러그인에서 한 번씩, 두 번 실행됩니다. 플러그인이 동작하는 걸 확인했으면 .claude/의 원본과 settings의 hooks를 지우세요.
6 / 16

플러그인에서 달라지는 규칙

플러그인 서브에이전트는 hooks·mcpServers·permissionMode를 무시

보안상의 제한입니다(13편). 그래서 13편에서 조사관 frontmatter에 인라인으로 넣었던 k8s-ro를, msp-toolkit에서는 플러그인의 .mcp.json으로 옮겼습니다. 대가로 k8s-ro 도구가 메인 대화에도 보입니다. 꼭 조사관 전용이어야 한다면 그 에이전트 파일을 .claude/agents/로 복사해 쓰는 것이 공식 안내입니다.

플러그인 MCP 도구 이름

mcp__plugin_<플러그인>_<서버>__<도구>. msp-toolkit의 get_pods는 mcp__plugin_msp-toolkit_k8s-ro__get_pods. 12편의 mcp__k8s-ro__* 규칙과 Hook matcher는 이 이름에 맞지 않으니 함께 바꿔야 합니다. 정확한 이름은 /mcp에서 확인.

Skill 이름 바꾸기

Skill frontmatter의 name이 마지막 칸이 됩니다. name: rb면 /msp-toolkit:rb. 다른 명령과 겹치지 않으면 /rb로도 부를 수 있습니다.

skillOverrides는 플러그인에 안 먹힘

10편의 skillOverrides는 플러그인 Skill에 적용되지 않습니다. 끄려면 /plugin에서 플러그인 자체를 비활성화합니다.

7 / 16

개발하며 테스트하기

마켓플레이스 없이도 플러그인을 바로 써 볼 수 있습니다. 공식 문서의 점검 순서를 따라가세요.

1
검사

매니페스트와 모든 Skill·에이전트·명령 파일의 frontmatter를 검사합니다. --strict면 경고도 실패로.

claude plugin validate ~/msp-claude-plugins/plugins/msp-toolkit
2
한 세션만 불러오기

설치하지 않고, 설정에도 남기지 않습니다. 여러 개면 플래그를 반복. 고친 뒤에는 세션 안에서 /reload-plugins.

cd ~/vibe-lab claude --plugin-dir ~/msp-claude-plugins/plugins/msp-toolkit
3
/plugin 관리 화면

Installed 탭에서 찾은 구성 요소를, Errors 탭에서 로드 실패 이유(commands path not found 등)를 봅니다.

4
구성 요소별 확인

Skill은 /msp-toolkit:runbook, MCP는 /mcp, Hook은 그 이벤트를 일으킨 뒤 claude --debug 로그.

5
정말 효과가 있나

로드된다고 Claude가 의도대로 움직이는 건 아닙니다. claude plugin eval은 테스트 케이스를 플러그인이 있을 때와 없을 때로 돌려 차이를 채점합니다(10편 기준선 비교의 자동화).

--plugin-dir에 마켓플레이스 루트를 넘기면 --plugin-dir는 플러그인 하나의 루트를 받습니다. ~/msp-claude-plugins처럼 마켓플레이스 루트를 넘기면 marketplace.json을 읽지 않아 plugins/ 아래가 로드되지 않을 수 있습니다(최신 버전은 플러그인 폴더 모음을 읽기도 합니다). 헷갈리면 플러그인 폴더를 직접 가리키세요. Anthropic의 plugin-dev 플러그인을 설치하면 /plugin-dev:create-plugin으로 Claude가 설계·생성·검사를 함께 해 줍니다.
8 / 16

마켓플레이스로 나누기

① 카탈로그

저장소 루트의 .claude-plugin/marketplace.json에 이름·소유자·플러그인 목록(name, source)

② 호스팅

GitHub·GitLab·사내 Git에 push. 개발 중엔 로컬 경로도 가능

③ 추가

/plugin marketplace add 소유자/저장소 또는 Git URL·경로

④ 설치

/plugin install 플러그인@마켓플레이스. 셸에선 claude plugin install

{ "name": "msp-claude-plugins", "owner": { "name": "MSP 운영팀" }, "plugins": [ { "name": "msp-toolkit", "source": "./plugins/msp-toolkit", "description": "MSP 운영용 런북 Skill, 운영 변경 가드 Hook, …" } ] }
source의 모양

같은 저장소 안이면 "./plugins/이름". 다른 저장소면 {"source":"github","repo":"org/repo"}나 {"source":"url","url":"https://…git"}.

예약된 이름

claude-plugins-official, anthropic-plugins, agent-skills 등은 Anthropic 전용이고, 공식을 흉내 낸 이름도 막힙니다.

공식 마켓플레이스

claude-plugins-official에서 skill-creator(10편), plugin-dev 등을 설치할 수 있습니다.

마켓플레이스 없이

몇 명에게만 줄 거라면 디렉토리나 .zip을 건네고 --plugin-dir로 써도 됩니다.

9 / 16

팀과 조직에 배포

저장소의 .claude/settings.json에 마켓플레이스와 켤 플러그인을 적어 두면, 팀원이 그 폴더를 신뢰하는 순간 마켓플레이스가 추가되고 플러그인이 설치됩니다. 조직 전체라면 같은 키를 관리형 설정에 넣습니다(24편).

{ "extraKnownMarketplaces": { "msp-claude-plugins": { "source": { "source": "git", "url": "https://git.example.com/msp/msp-claude-plugins.git" } } }, "enabledPlugins": { "msp-toolkit@msp-claude-plugins": true } }
키 이름 규칙

extraKnownMarketplaces의 키는 marketplace.json의 name과 같아야 합니다. enabledPlugins는 플러그인@마켓플레이스.

자동 업데이트

마켓플레이스 항목에 "autoUpdate": true를 주면 새 버전을 자동으로 받습니다.

신뢰가 먼저

저장소 설정의 플러그인 자동 설치는 그 폴더를 신뢰한 뒤에 일어납니다(9편). 모르는 저장소의 settings가 플러그인을 들여오는 것을 막는 장치입니다.

클라우드 세션

사용자 설정에서만 켠 플러그인이나 저장소 settings의 플러그인은 클라우드 세션에 그대로 따라가지 않을 수 있습니다(10편). 클라우드에서도 필요하면 조직 관리형 설정이나 계정 쪽 배포를 확인하세요.

10 / 16

버전과 업데이트

version을 적으면

사용자는 여러분이 version을 바꿀 때까지 그 버전에 머뭅니다. 고친 내용을 내보내려면 version을 올리고 push합니다.

의미 있는 번호

Hook이 새로 막는 명령이 생기면 동료의 작업이 갑자기 멈출 수 있습니다. 동작이 바뀌는 변경은 부 버전 이상을 올리고 README에 적으세요.

캐시와 경로

설치된 플러그인은 복사본에서 돕니다. 그래서 스크립트는 ${CLAUDE_PLUGIN_ROOT}로 찾고, 오래 남길 데이터는 ${CLAUDE_PLUGIN_DATA}에.

변경 기록

7편처럼 PR로 바꾸고 리뷰받으세요. 가드 Hook의 정규식 하나가 팀 전체의 Bash를 막을 수 있습니다.

버전을 언제 적고 언제 생략할지의 세부 규칙은 공식 문서 “Release a new version”을 확인하세요.

실습: msp-toolkit 만들고 배포

10~13편 실습 파일이 ~/vibe-lab에 있다고 가정합니다. 아래 블록은 vibe-lab에서 파일을 옮겨 오고 새 파일을 써서, 위 4장의 구조를 그대로 만듭니다(이 블록으로 같은 파일이 만들어지는 것을 확인했습니다).
