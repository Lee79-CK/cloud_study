측정으로 찾은 것: TLS를 끝내는 게이트웨이 뒤의 403

    
운영에서는 게이트웨이가 HTTPS를 끝내고 포털에는 HTTP로 넘깁니다. 이때 Express는 req.protocol을 http로 보아, 17편 CSRF 검사의 "같은 출처" 계산이 http://…가 됩니다. X-Forwarded-Proto: https와 Origin: https://…로 로그인을 재현하자 403이 났습니다(최신 브라우저는 Sec-Fetch-Site를 먼저 보아 통과하지만, Origin만 보내는 클라이언트는 막힘. 6편 safeNext의 출처 비교도 같은 영향). TRUST_PROXY=1로 Express가 앞단 프록시 한 단계를 믿게 하자 303(정상 로그인)이 되었습니다. FastAPI는 uvicorn의 --proxy-headers와 --forwarded-allow-ips로 같은 일을 합니다. 프록시 수를 실제보다 크게 잡으면 클라이언트가 보낸 헤더까지 믿게 되므로 정확히 설정합니다.

  

  
또 하나, 공식 Node 이미지의 USER node처럼 이름으로 사용자를 지정하면 Kubernetes의 runAsNonRoot가 그 사용자가 루트가 아님을 확인할 수 없어 컨테이너를 거부합니다. 그래서 Dockerfile에 숫자 UID(USER 1000, Python은 10001)를 썼습니다.

관측 1: 서버 지표

  
Express는 prom-client 15.1.3, FastAPI는 prometheus-client 0.26.0으로 같은 이름의 지표를 Prometheus 텍스트 형식으로 냅니다. 업무 포트와 다른 METRICS_PORT(기본 9464)의 /metrics에서만 노출합니다.

  

    
지표라벨무엇을 보나

    
      
portal_http_request_duration_seconds (히스토그램)method, route, status, htmx라우트별 지연. htmx는 partial·full·none으로 조각 요청과 페이지 요청을 나눔

      
portal_flag_served_totalflag, impl16편 경로별 레거시·새 구현 응답 수 → 걷어 내기 판단

      
portal_shadow_compare_totalflag, result(match·mismatch·error)16편 그림자 비교 불일치율

      
portal_sse_connections (게이지)-10편 SSE 연결 수

      
portal_web_vitals_seconds, portal_web_vitals_clsname, page, rating8절 RUM

    
  

  
route 라벨에는 실제 경로(/vms/web-01)가 아니라 라우트 템플릿(/vms/:name)을 넣습니다. 실제 경로를 넣으면 VM 수만큼 시계열이 늘어납니다. FastAPI의 템플릿은 /vms/{name} 모양이라 처음에는 두 서버의 라벨이 달랐고, :name 모양으로 바꿔 맞췄습니다. 측정: 그림자 비교 모드에서 고객사 1~3을 열자 두 서버 모두 result="match" 2, result="mismatch" 1(16편의 누리로지스 VM 수 차이).

18편의 Web Vitals는 실험실 측정(Lab)이었습니다. 실제 사용자 환경의 값(Field)은 브라우저가 직접 재서 보내야 합니다. web-vitals 6.2.3을 import map("web-vitals")으로 연결하고, 페이지를 떠날 때 navigator.sendBeacon('/rum', …)으로 모아 보냅니다. 레이아웃은 <body data-page="/vms/:name">로 라우트 템플릿을 알려 주어, 서버 지표와 같은 단위로 묶입니다. 서버는 라벨 값을 정해진 모양으로만 받고(page가 이상하면 other), 한 번에 20개까지만 처리합니다.

  

    
부스트 이동이 있는 앱의 RUM 해석

    
부스트·htmx 스왑은 새 페이지 로드가 아니므로, web-vitals의 LCP·FCP·TTFB는 처음 로드한 페이지 기준으로 한 번만 나옵니다. 반면 CLS와 INP는 그 문서에서 일어난 모든 상호작용에 누적됩니다. 그래서 page="/vms"로 들어와 부스트로 여러 화면을 다닌 세션의 INP는 /vms에 기록됩니다. 측정에서도 새 탭으로 연 /vms/:name에는 LCP·FCP·TTFB·INP가, 부스트로 옮겨 다닌 탭에는 처음 페이지인 /login·/vms로 CLS가 쌓였습니다. 화면 전환 속도는 RUM보다 7절의 htmx="partial" 서버 지연 지표가 더 직접적입니다.

  

  
/rum은 로그인 전에도 받습니다(로그인 화면의 지표도 필요). 같은 출처의 sendBeacon은 Sec-Fetch-Site: same-origin이라 17편 CSRF 검사를 통과합니다. CSP 아래에서도 위반 0건이었습니다.
