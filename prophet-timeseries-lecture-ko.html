예측은 마법이 아니라
더하기입니다.

Prophet은 시계열을 네 조각으로 쪼갠 뒤 다시 더해서 미래를 그립니다. 조각의 이름만 알면 이 도구의 90%를 이해한 셈입니다. 아래 방정식의 각 항을 눌러 끄고 켜 보세요 — 예측선이 어떻게 만들어지는지 눈으로 확인할 수 있습니다.

The Decomposable Model — 클릭해서 항을 켜고 끄기
y(t) = + + +
g(t) · 추세
s(t) · 주간+연간
h(t) · 휴일 효과
εt · 설명 못 한 잔차

2년치 일별 매출을 모사한 가상 데이터입니다. 네 조각을 모두 켜면 우리가 현실에서 마주치는 ‘지저분한’ 그래프가 되고, 하나씩 끄면 각 조각의 정체가 드러납니다.

01

시계열 예측이 실제로 푸는 문제

회귀 문제와 무엇이 다른지부터 정리하고 넘어갑니다.

일반적인 지도학습에서는 X(특성)로 y(정답)를 맞힙니다. 데이터 순서는 보통 의미가 없어서 train/test를 무작위로 섞어도 됩니다. 시계열은 다릅니다. 순서 자체가 정보이고, 우리가 가진 특성은 사실상 ‘시각’ 하나뿐인 경우가 많습니다.

구분일반 지도학습시계열 예측
입력여러 개의 특성 열시각 t + (선택) 외생변수
데이터 분할무작위 셔플 가능시간순으로만 분할 (미래 유출 금지)
샘플 독립성i.i.d. 가정자기상관 존재 — 어제가 오늘을 설명
평가k-fold CVrolling-origin CV (cutoff를 밀어가며)
목표보간(interpolation)외삽(extrapolation) — 본 적 없는 구간

거의 모든 시계열은 네 성분으로 설명된다

1920년대 고전 통계에서 나온 ‘시계열 분해(decomposition)’ 아이디어입니다. Prophet은 이 낡고 검증된 발상을 현대적으로 다시 구현한 도구입니다.

g(t) · Trend

장기 추세

서비스가 커지는가 줄어드는가. 계단처럼 꺾이는 지점(변화점)이 어디인가. 예측의 방향을 결정하는 가장 중요한 항.

s(t) · Seasonality

주기적 패턴

주말에 오르고 월요일에 죽는 주간 패턴, 여름·연말에 몰리는 연간 패턴처럼 반복되는 파동.

h(t) · Holiday

불규칙 이벤트

설날·추석·블랙프라이데이처럼 날짜가 매년 이동하고 주기 함수로는 못 잡는 일회성 충격.

εt · Noise

잔차

모델이 설명 못 한 나머지. 이 안에 아직 패턴이 보이면 모델을 더 손봐야 한다는 신호입니다.

기억할 것

실무에서 예측 정확도를 가장 크게 흔드는 건 화려한 모델이 아니라 g(t)의 방향입니다. 추세를 반대로 잡으면 나머지를 아무리 잘 맞혀도 예측은 실패합니다.

02

Prophet의 정체: 예측을 ‘곡선 맞추기’로 바꾼 도구

Meta(당시 Facebook) Core Data Science 팀이 2017년에 공개한 오픈소스입니다.

탄생 배경: 예측 수요는 폭발하는데 전문가는 부족했다

사내에서 “이 지표 다음 분기 어떻게 될까요?” 같은 요청은 끝없이 들어오는데, ARIMA 차수를 고를 수 있는 통계 전문가는 소수였습니다. 그래서 팀은 목표를 이렇게 잡았습니다.

  • 기본값이 쓸 만해야 한다 — 통계 배경이 없는 분석가도 바로 돌릴 수 있게
  • 튜닝 손잡이가 사람의 언어여야 한다 — “p, d, q”가 아니라 “휴일 효과”, “추세 유연성”
  • 사람이 개입할 여지를 남긴다 — 논문에서 말하는 analyst-in-the-loop. 도메인 지식(이번 프로모션, 새 공휴일)을 모델에 직접 주입할 수 있어야 한다
  • 수천 개 시계열을 자동으로 돌리고, 이상한 것만 사람이 본다

핵심 설계 결정: 시간을 ‘특성’으로 쓰는 회귀 문제

ARIMA 계열은 “어제 값으로 오늘 값을 설명”하는 자기회귀 방식입니다. Prophet은 방향을 완전히 틀어서 시각 t를 입력으로 하는 곡선 적합(curve fitting) 문제로 봅니다. 이 선택 하나에서 Prophet의 장점과 단점이 모두 따라 나옵니다.

장점

결측·불규칙에 강함

이전 값에 의존하지 않으므로 며칠 데이터가 비어도 그냥 그 행을 빼고 학습하면 됩니다. 관측 간격이 불규칙해도 동작합니다.

장점

임의 구간 예측

한 번 적합한 곡선에 t만 넣으면 되므로 3일 뒤, 3년 뒤를 같은 방식으로 계산합니다. 재귀 예측이 필요 없습니다.

장점

해석 가능

plot_components() 한 줄로 “주말 +18%, 추석 +40%” 같은 설명을 만들 수 있습니다. 보고서에 그대로 쓸 수 있는 예측 근거입니다.

단점

자기상관을 안 씀

“어제 갑자기 급등” 같은 최신 정보를 즉시 반영하지 못합니다. 단기(1~7일) 예측에서 ARIMA·부스팅에 밀리는 주된 이유입니다.

한 줄 정의

Prophet = Stan으로 MAP 추정하는, 변화점이 있는 일반화가법모형(GAM). 즉 딥러닝도 아니고 ARIMA도 아닌, 해석 가능한 회귀 모델입니다.

03

추세 g(t): 변화점(changepoint)이라는 발명

Prophet에서 가장 중요하고, 가장 자주 잘못 튜닝되는 부분입니다.

두 가지 성장 곡선

1) 조각별 선형(piecewise linear) — 기본값 growth='linear'. 직선을 여러 개 이어붙여 꺾이는 추세를 표현합니다.

# k: 기본 성장률, m: 절편
# s_j: j번째 변화점의 시각, delta_j: 그 시점에서 성장률이 변하는 양
g(t) = (k + sum(delta_j for s_j < t)) * t + (m + offset)

# delta에 Laplace(0, tau) 사전분포를 준다  → tau = changepoint_prior_scale
# tau가 작으면: 대부분의 delta가 0으로 눌린다  → 뻣뻣한 추세
# tau가 크면  : delta가 자유롭게 커진다        → 출렁이는 추세

2) 로지스틱(logistic) — growth='logistic'. 시장 크기처럼 상한이 존재할 때 S자 곡선으로 포화시킵니다. 이때는 데이터프레임에 cap 열(상한)이 반드시 있어야 하고, 필요하면 floor(하한)도 줍니다. growth='flat'은 추세를 고정합니다.

변화점은 어디에 놓이나

  • 기본값: 학습 데이터 앞쪽 80% 구간에 25개의 후보 변화점을 균등 배치 (n_changepoints=25, changepoint_range=0.8)
  • 뒤쪽 20%를 비워두는 이유: 데이터 끝부분의 잡음을 ‘새로운 추세’로 착각하면 미래 예측이 엉뚱한 방향으로 발사됩니다
  • 후보 25개를 다 쓰는 게 아니라, L1 성격의 사전분포가 필요 없는 변화점의 delta를 0으로 눌러버립니다 (자동 선택)

Prophet의 delta 사전분포가 Laplace이므로, MAP 추정은 곧 L1 규제가 걸린 조각별 선형 회귀입니다. 이 데모는 실제로 그 L1 좌표하강법을 브라우저에서 풀어 그립니다(잡음은 고정 시드).

핵심 교훈

학습 MAE는 τ가 커질수록 계속 좋아집니다. 하지만 미래 오차는 U자입니다. 학습 오차만 보고 τ를 올리는 것이 Prophet 최악의 실수입니다. 반드시 9장의 교차검증으로 골라야 합니다.

04

계절성 s(t): 푸리에 급수로 파동을 그린다

“주말에 오른다”를 모델에 어떻게 알려줄까요? 사인·코사인을 몇 개 더하는 것으로 해결합니다.

주간 패턴을 표현하는 가장 단순한 방법은 요일 더미변수 7개를 넣는 것입니다. 그런데 연간 패턴에 같은 방식을 쓰면 365개 변수가 필요해집니다. Prophet은 대신 주기 P를 갖는 사인·코사인 쌍을 N개만 더해 매끄러운 파동을 만듭니다. 

# P: 주기 (연간 365.25, 주간 7, 일간 1)
# N: fourier_order — 파동을 몇 겹 쌓을지
s(t) = sum( a_n * cos(2*pi*n*t/P) + b_n * sin(2*pi*n*t/P) )   for n = 1..N

# 학습되는 파라미터는 2N개. 사전분포는 Normal(0, sigma)
#   sigma = seasonality_prior_scale (기본 10.0 = 거의 규제 없음)
# 기본값:  연간 N=10 (20개 파라미터),  주간 N=3 (6개),  일간 N=4
실습 2 · fourier_order를 올리면 무슨 일이 생기나

정답 곡선은 ‘연말에 급등하고 여름에는 낮은’ 전형적인 리테일 패턴입니다. N=1은 부드러운 사인파 하나라 급등을 놓치고, N을 과하게 올리면 없는 요철까지 만들어냅니다.

덧셈이냐 곱셈이냐: seasonality_mode

매출이 100 → 1000으로 커지면 주말 효과도 보통 “+20”이 아니라 “+20%”로 함께 커집니다. 이때 seasonality_mode='multiplicative'로 바꾸면 계절성이 추세에 곱해집니다.

사용자 정의 계절성

기본 제공되는 연간/주간/일간 외에 월간, 분기, 격주 패턴을 직접 추가할 수 있습니다. 근무일과 주말에 서로 다른 주간 패턴을 주는 ‘조건부 계절성’도 가능합니다.

m = Prophet(weekly_seasonality=True, yearly_seasonality=20)
m.add_seasonality(name='monthly', period=30.5, fourier_order=5)
m.add_seasonality(name='quarterly', period=91.3, fourier_order=3,
                  prior_scale=5)   # 이 계절성만 따로 규제
m.fit(df)
# 평일과 주말의 일중 패턴이 완전히 다른 서비스
def is_weekend(ds):
    return ds.weekday() >= 5

df['weekend'] = df['ds'].apply(is_weekend)
df['weekday'] = ~df['weekend']

m = Prophet(weekly_seasonality=False)
m.add_seasonality('daily_weekday', period=1, fourier_order=6, condition_name='weekday')
m.add_seasonality('daily_weekend', period=1, fourier_order=6, condition_name='weekend')
m.fit(df)   # future 데이터프레임에도 같은 불리언 열이 있어야 함
05

휴일 h(t)와 불확실성 구간

주기 함수로 잡을 수 없는 ‘날짜가 움직이는 사건’을 다루는 방법.

휴일은 사실 ‘더미변수 모음’이다

설날은 매년 양력 날짜가 바뀌므로 연간 사인파로는 절대 표현되지 않습니다. Prophet은 각 휴일마다 더미변수를 만들고 계수 κ를 학습합니다. 앞뒤 며칠까지 영향을 퍼뜨릴 수도 있습니다 (lower_window=-2, upper_window=2 → 총 5일 창). 

from prophet import Prophet

m = Prophet()
m.add_country_holidays(country_name='KR')   # 설날·추석·삼일절 ... 자동
m.fit(df)

# 어떤 휴일이 적용됐는지 확인
print(m.train_holiday_names)
import pandas as pd

promo = pd.DataFrame({
    'holiday': 'big_sale',
    'ds': pd.to_datetime(['2024-11-11', '2025-11-11', '2026-11-11']),
    'lower_window': -1,   # 전날부터 영향
    'upper_window': 2,    # 이틀 뒤까지 여운
})
outage = pd.DataFrame({
    'holiday': 'outage',
    'ds': pd.to_datetime(['2025-03-14']),
    'lower_window': 0, 'upper_window': 0,
})
events = pd.concat([promo, outage])

m = Prophet(holidays=events, holidays_prior_scale=10.0)
m.fit(df)
# 미래 시점의 이벤트 날짜를 반드시 함께 넣어야 예측에 반영된다.
# 과거에만 있고 미래에 없으면, 모델은 그 효과를 학습만 하고 쓰지 못한다.
m = Prophet(holidays=events)
m.add_country_holidays(country_name='KR')
m.fit(df)

future = m.make_future_dataframe(periods=90)
fcst = m.predict(future)
fcst[['ds', 'yhat', 'big_sale', 'holidays']].tail()
자주 터지는 함정

일회성 장애·품절·이벤트를 휴일로 등록하지 않으면, 그 급락을 모델은 추세 변화로 오해합니다. 데이터가 깨진 날은 휴일로 등록하거나 y = None으로 비우세요. Prophet은 결측을 그냥 건너뜁니다.

불확실성 구간(yhat_lower / yhat_upper)의 정체

Prophet이 내놓는 구간은 세 가지 원천을 합친 값입니다. 특히 첫 번째가 Prophet만의 특징입니다.

  1. 미래 추세의 불확실성 — “과거에 이 정도 빈도·크기로 추세가 꺾였으니, 미래에도 비슷하게 꺾일 것”이라고 가정해 변화점을 무작위로 시뮬레이션합니다. 그래서 τ를 키우면 구간이 눈에 띄게 넓어집니다.
  2. 관측 잡음 ε — 잔차의 산포
  3. 계절성의 불확실성 — 기본은 꺼져 있습니다. mcmc_samples>0으로 MCMC를 돌릴 때만 포함됩니다(대신 매우 느립니다)
실습 4 · interval_width와 구간의 의미
Interactive

기본값 interval_width=0.8은 80% 구간입니다. 95%가 아니라는 점을 보고서에 꼭 명시하세요. 구간은 ‘예측이 얼마나 믿을 만한가’가 아니라 ‘모델 가정 안에서의 산포’일 뿐입니다.

import pandas as pd

raw = pd.read_csv('raw.csv')
df = (raw
      .rename(columns={'date': 'ds', 'revenue': 'y'})
      .assign(ds=lambda d: pd.to_datetime(d['ds']).dt.tz_localize(None),
              y=lambda d: pd.to_numeric(d['y'], errors='coerce'))
      .groupby('ds', as_index=False)['y'].sum()      # 중복 집계
      .sort_values('ds')
      .reset_index(drop=True))

# 빠진 날짜를 명시적으로 드러내기(값은 NaN으로 둔다)
full = pd.DataFrame({'ds': pd.date_range(df.ds.min(), df.ds.max(), freq='D')})
df = full.merge(df, on='ds', how='left')
print(df.y.isna().sum(), '개 결측 — Prophet이 알아서 건너뜁니다')
# Prophet은 이상치에 "적당히" 강하지만, 추세 끝부분의 이상치는 치명적이다.
# 원인을 아는 이상치 → 휴일로 등록.  원인을 모르는 이상치 → NaN으로 제거.

q1, q3 = df.y.quantile([0.25, 0.75])
iqr = q3 - q1
mask = (df.y < q1 - 3*iqr) | (df.y > q3 + 3*iqr)
print(df.loc[mask, ['ds', 'y']])          # 먼저 눈으로 확인!

df.loc[mask, 'y'] = None                     # 삭제가 아니라 결측 처리
# 주의: 계절성 피크(연말 급증)를 이상치로 지우면 모델이 바보가 된다
import numpy as np

# y의 분포가 오른쪽으로 심하게 치우쳤거나 분산이 값에 비례해 커질 때
df['y'] = np.log1p(df['y'])       # log(1+y): y=0도 안전

m = Prophet().fit(df)
fcst = m.predict(m.make_future_dataframe(90))

# 원래 단위로 되돌리기 (구간도 함께!)
for c in ['yhat', 'yhat_lower', 'yhat_upper']:
    fcst[c] = np.expm1(fcst[c])

# 참고: 로그 공간의 additive 계절성 = 원 공간의 multiplicative 계절성
# 논리적 상한이 있을 때만 logistic을 쓴다 (예: 전체 가입 가능 인구)
df['cap'] = 50000          # 상수도 되고, 시간에 따라 변하는 열도 된다
df['floor'] = 0

m = Prophet(growth='logistic').fit(df)

future = m.make_future_dataframe(periods=365)
future['cap'] = 50000      # future에도 반드시 다시 넣어야 한다!
future['floor'] = 0
fcst = m.predict(future)

증상별 처방전

그래프를 보고 “이상하다”고 느꼈을 때 무엇을 만질지 찾는 표입니다. 항목을 눌러 펼쳐 보세요.

예측선이 과거의 꺾임을 전혀 따라가지 못하고 뻣뻣하다

changepoint_prior_scale을 올립니다(0.05 → 0.1 → 0.3). 그래도 안 되면 changepoint_range를 0.9로 늘려 최근 구간에도 변화점을 허용합니다.

미래 예측이 비현실적으로 급등/급락하며 발사된다

τ가 너무 큰 대표 증상입니다. 내립니다(0.05 → 0.01). 데이터 끝부분에 프로모션·장애 같은 일시적 사건이 있다면 그걸 휴일로 등록하는 것이 근본 처방입니다. 상한이 명확하면 growth='logistic'도 고려하세요.

계절성 파동이 실제보다 과장돼 출렁인다

seasonality_prior_scale을 10 → 1 → 0.1로 낮추거나, yearly_seasonality의 fourier_order를 10 → 5로 줄입니다.

값이 커질수록 실제 파동은 커지는데 모델 파동은 일정하다

seasonality_mode='multiplicative'로 바꾸거나 y에 로그 변환을 적용합니다.

1년치 데이터인데 연간 패턴이 이상하게 그려진다

주기를 한 번도 온전히 못 본 상태입니다. yearly_seasonality=False로 끄세요. 최소 2주기(2년)를 권장합니다.

불확실성 구간이 실제 변동을 못 담는다(자꾸 벗어난다)

interval_width=0.95로 올려 보고하되, 근본 원인은 보통 모델 부적합입니다. 잔차를 그려서 남은 패턴(요일·이벤트)을 찾아 회귀변수로 추가하세요.

import itertools, numpy as np, pandas as pd
from prophet import Prophet
from prophet.diagnostics import cross_validation, performance_metrics

grid = {
    'changepoint_prior_scale': [0.001, 0.01, 0.05, 0.1, 0.5],
    'seasonality_prior_scale': [0.01, 0.1, 1.0, 10.0],
    'seasonality_mode': ['additive', 'multiplicative'],
}
keys, vals = zip(*grid.items())
combos = [dict(zip(keys, v)) for v in itertools.product(*vals)]

rows = []
for params in combos:                       # 40개 조합
    m = Prophet(**params).fit(df)
    cv = cross_validation(m, initial='730 days', period='30 days',
                          horizon='30 days', parallel='processes')
    p = performance_metrics(cv, rolling_window=1)
    rows.append({**params, 'rmse': p['rmse'].values[0], 'mape': p['mape'].values[0]})

best = pd.DataFrame(rows).sort_values('rmse').head()
print(best)
import optuna
from prophet import Prophet

def objective(trial):

        'changepoint_prior_scale': trial.suggest_float('cps', 1e-3, 0.5, log=True),

    }

study.optimize(objective, n_trials=40, n_jobs=1)

검증: 시계열에서 k-fold는 반칙이다

미래 데이터로 과거를 예측하는 순간, 오차는 거짓이 됩니다.

rolling-origin 교차검증 개념

Prophet의 cross_validation()은 cutoff를 뒤로 밀면서 매번 “그 시점까지의 데이터만”으로 학습하고, 이후 horizon 구간을 예측해 실제와 비교합니다. 실제 운영에서 매달 모델을 다시 학습하는 상황을 그대로 재현한 것입니다. 

전체 데이터 ├──────────────────────────────────────────────┤

fold 1  [====== initial(학습) ======]▶[horizon]
                    cutoff ↑
fold 2  [====== initial + period ==========]▶[horizon]
                              cutoff ↑
fold 3  [====== initial + 2*period ==============]▶[horizon]
                                     cutoff ↑

initial : 첫 학습 구간 길이   (권장: horizon의 3배 이상, 계절 주기의 2배 이상)
period  : cutoff를 미는 간격  (기본: horizon / 2)
horizon : 매번 예측할 미래 길이 (실제 업무에서 필요한 예측 기간과 동일하게!)
from prophet.diagnostics import cross_validation, performance_metrics

cv = cross_validation(
    m,
    initial='1095 days',    # 3년으로 시작
    period='90 days',       # 분기마다 cutoff 이동
    horizon='90 days',      # 분기 예측 성능을 본다
    parallel='processes',   # 'threads' | 'processes' | 'dask'
)
cv.head()   # ds, yhat, yhat_lower, yhat_upper, y, cutoff

perf = performance_metrics(cv)     # horizon 구간별로 집계
perf[['horizon', 'mae', 'rmse', 'mape', 'coverage']].head()
# MAE   : 평균 절대 오차. 단위가 y와 같아 설명하기 쉽다.
# RMSE  : 큰 오차에 더 민감. 이상치가 중요한 문제에 적합.
# MAPE  : 퍼센트 오차. y가 0에 가까우면 폭발하므로 주의.
# MDAPE : MAPE의 중앙값 버전. 이상치에 덜 흔들림.
# SMAPE : MAPE의 대칭 버전.
# coverage : 실제값이 [yhat_lower, yhat_upper] 안에 들어온 비율.
#            interval_width=0.8 이면 0.8 근처가 정상. 0.5라면 구간이 너무 좁다는 뜻.

# 반드시 함께 볼 기준선(baseline): 계절 나이브
#   "7일 전 값을 그대로 예측" 보다 못하다면 모델을 쓸 이유가 없다.
baseline_mae = (df['y'] - df['y'].shift(7)).abs().mean()
print('seasonal naive MAE:', round(baseline_mae, 2))
from prophet.plot import plot_cross_validation_metric

fig = plot_cross_validation_metric(cv, metric='mape')
# x축=예측 시점까지의 거리, y축=오차.
# 보통 우상향한다 = 멀리 볼수록 부정확하다.
# 이 곡선을 보고 "우리는 며칠까지 신뢰할 수 있다"를 정한다.
절대 금지

train_test_split(shuffle=True), KFold, 그리고 전체 데이터로 스케일링/이상치 제거 후 분할. 세 가지 모두 미래 정보 유출(data leakage)이며, 실제보다 훨씬 좋은 가짜 성능을 만듭니다.

용어 정리

위 표의 ‘모델’과 라이브러리를 혼동하지 마세요. statsforecast(Nixtla)는 ARIMA·ETS·Theta를 매우 빠르게 구현한 라이브러리, darts·sktime은 여러 모델을 같은 API로 감싼 프레임워크, pytorch-forecasting·GluonTS는 딥러닝 예측 툴킷입니다. Prophet도 darts와 sktime 안에서 하나의 모델로 호출할 수 있습니다.

선택 흐름: 다섯 개 질문

Q1

기준선을 먼저 만들었나?

계절 나이브 → ETS/AutoARIMA 순으로 30분 안에 돌려 보세요. 놀랄 만큼 자주 이깁니다.

Q2

예측 근거를 설명해야 하나?

예 → Prophet. “추석 +32%, 주말 +18%”처럼 항별 기여도를 그대로 보고할 수 있는 도구는 흔치 않습니다.

Q3

예측 구간이 며칠인가?

1~7일 단기 → ARIMA·LightGBM 우세. 수주~수개월 중장기 → Prophet의 영역.

Q4

시계열이 몇 개인가?

1~100개 → Prophet 병렬 학습으로 충분. 1만 개 이상 → statsforecast 또는 LightGBM 글로벌 모델.

Q5

쓸 만한 외생변수가 있나?

많다 → 부스팅. 없고 시간 정보만 있다 → Prophet이 가장 가성비 좋은 출발점.

실전 조합

Prophet으로 추세·계절·휴일을 분해하고, 그 잔차를 LightGBM으로 학습하는 하이브리드가 현업에서 자주 통합니다.

한계와 비판: 정직하게 짚고 가기

Prophet을 오래 쓴 사람들이 공통으로 지적하는 지점들입니다.

  • 자기상관을 모델링하지 않는다. 어제 값이 오늘 값에 주는 정보를 구조적으로 버립니다. 그래서 잔차에 자기상관이 그대로 남고, 단기 예측이 약합니다.
  • 여러 벤치마크에서 정확도가 상위권이 아니다. M4·M5 같은 대회와 여러 비교 실험에서 AutoARIMA·ETS·부스팅 계열이 Prophet보다 나은 결과를 낸 사례가 많습니다. Prophet의 가치는 최고 정확도가 아니라 기본값의 견고함과 해석성에 있습니다.
  • 추세 반응이 느리다. 변화점 후보가 앞쪽 80%에만 있으므로, 최근에 생긴 구조 변화(예: 정책 변경 직후)를 늦게 따라갑니다. 이건 버그가 아니라 ‘미래로 잡음을 외삽하지 않겠다’는 의도적 설계입니다.
  • 불확실성 구간을 과신하기 쉽다. 계절성 불확실성은 기본적으로 제외되고, 추세 구간은 “과거와 비슷한 빈도로 꺾인다”는 가정에 의존합니다. coverage 지표로 항상 검증하세요.
  • 대규모에서 느리다. Stan 기반이라 시계열 하나에 수백 ms~수 초가 걸립니다. 시계열 수만 개를 매일 돌리면 statsforecast(수십 배 빠름) 쪽이 현실적입니다.
  • 신기능 개발 속도가 둔화됐다. 성숙·안정 단계로, 새로운 모델링 기능이 활발히 추가되지는 않습니다. 최신 상황은 GitHub 저장소와 PyPI 릴리스 노트를 확인하세요.
  • 기본값이 만들어내는 착시. 1년 미만 데이터에 연간 계절성이 켜지거나, 주 5일 데이터에 주말 예측이 나오는 등 “그럴듯하지만 틀린” 결과가 쉽게 나옵니다.
균형 잡힌 결론

Prophet은 훌륭한 두 번째 모델입니다. 첫 번째는 나이브 기준선, 마지막은 문제에 맞는 최적 모델이고, Prophet은 그 사이에서 “데이터가 무슨 모양인지”를 사람에게 가장 빨리 설명해 주는 도구입니다. 분해 결과를 보고 얻은 통찰(주말 효과, 추석 효과, 추세 꺾임)은 이후 어떤 모델을 쓰더라도 특성 설계에 그대로 재활용됩니다.

[원천 DB/웨어하우스]
        │  일 1회 적재
        ▼
[1] 데이터 검증        ← 스키마, 결측률, 중복 ds, 급격한 분포 변화
        ▼
[2] 전처리             ← ds/y 정규화, 이상치 → 휴일 또는 NaN
        ▼
[3] 학습 + 교차검증    ← 후보 파라미터 소수만 재확인 (매일 풀 그리드 X)
        ▼
[4] 챌린저 비교        ← 계절 나이브 / 이전 챔피언 모델과 CV 지표 비교
        ▼
[5] 승격 or 중단       ← 기준 미달이면 이전 모델 유지 + 알림
        ▼
[6] model.json 저장    ← 아티팩트 저장소(레지스트리) + 파라미터·지표 기록
        ▼
[7] 예측 저장 / 서빙   ← 예측 테이블 적재, 필요 시 API
        ▼

한 장 요약

이 페이지만 캡처해 두면 됩니다.

모델

y(t) = g(t) + s(t) + h(t) + εt

  • g(t) 조각별 선형/로지스틱 + 변화점, 손잡이는 changepoint_prior_scale
  • s(t) 푸리에 급수, 손잡이는 fourier_order와 seasonality_mode
  • h(t) 휴일 더미 + 앞뒤 창(window)
  • ε 잔차 — 여기 패턴이 남아 있으면 아직 할 일이 있다

최소 작업 순서

  1. 계절 나이브 기준선 MAE 기록
  2. ds/y 정리 → 결측은 비워두기 → 이상치는 휴일 또는 NaN
  3. Prophet() 기본값 + add_country_holidays('KR')로 1차 적합
  4. plot_components()로 분해를 눈으로 확인 (여기서 도메인 지식과 대조)
  5. cross_validation() + performance_metrics()로 기준선과 비교
  6. τ, 계절성 규제, 모드만 그리드 서치
  7. model_to_json()으로 저장 → 파이프라인화 → coverage와 롤링 오차 모니터링

기억할 세 문장

  • 학습 오차를 보고 튜닝하면 반드시 실패한다.
  • Prophet의 강점은 정확도가 아니라 설명 가능한 분해다.
  • 기준선을 이기지 못하는 모델은 배포하지 않는다.
