SECTION 01

데이터 모델이 곧 경계 계약이다

조직에서 OTel이 굴러가지 않는 가장 흔한 이유는 Collector 설정 실수가 아니라 같은 것을 서로 다르게 부르는 일입니다.

A팀은 서비스 이름을 order-api로, B팀은 OrderService로, C팀은 order_api_prod로 붙입니다. 셋 다 문법적으로는 정상이고 어느 도구도 에러를 내지 않습니다. 그런데 "결제 실패율이 높은 서비스 top 5"를 뽑는 쿼리를 쓰는 순간, 같은 서비스가 세 개로 나뉘어 집계됩니다. 운영 6개월 차에 이걸 발견하면 이미 쌓인 데이터는 되돌릴 수 없습니다.

개발자에게 데이터 모델이란

내가 Span에 넣는 값이 나중에 누가 어떻게 조회할지를 결정합니다. 이름을 마음대로 지으면 내 데이터만 검색에서 빠집니다.

엔지니어에게 데이터 모델이란

대시보드·알림·비용 최적화가 전부 속성 이름을 전제로 만들어집니다. 표준이 없으면 서비스마다 별도 쿼리를 유지해야 합니다.

MSP 관점

고객사가 열 곳이면 명명 규칙이 열 가지가 될 수 있습니다. 공통 대시보드 템플릿 하나로 모든 고객사를 커버하려면 속성 이름만큼은 고객사를 가로질러 통일돼야 합니다. 이건 협상 대상이 아니라 표준 준수 문제이고, 그래서 시맨틱 컨벤션이 존재합니다.

SECTION 02

Span 해부

Span은 트레이스를 이루는 최소 단위입니다. 아래는 실제 Span 하나를 JSON으로 펼친 모습입니다. 필드를 클릭하면 각각이 무엇이고 누가 채우는지 오른쪽에 표시됩니다.

// 주문 API가 받은 HTTP 요청 하나 { "name": "POST /orders", "kind": "SPAN_KIND_SERVER", "traceId": "4bf92f3577b34da6...", "spanId": "00f067aa0ba902b7", "parentSpanId": "a1b2c3d4e5f60718", "startTimeUnixNano": 1758512400000000000, "endTimeUnixNano": 1758512400243000000, "status": { "code": "STATUS_CODE_ERROR", "message": "upstream timeout" }, "attributes": { "http.request.method": "POST", "http.route": "/orders", "http.response.status_code": 504, "acme.order.channel": "mobile" }, "events": [ { "name": "exception", "attributes": { "exception.type": "TimeoutException" } } ], "links": [], "resource": { "service.name": "order-api", "k8s.pod.name": "order-api-7d9f-x2k4" } }

필드를 선택하세요

왼쪽 JSON에서 하이라이트된 키를 클릭하면 설명이 표시됩니다.

한 가지만 미리 말해두면, 이 Span 안에는 세 종류의 작성자가 섞여 있습니다. SDK가 자동으로 채우는 값, 개발자가 의도해서 넣은 값, Collector가 나중에 덧붙이는 값입니다. 이 구분이 곧 1편의 경계선입니다.

SpanKind — 다섯 가지 역할

많이들 지나치지만 kind는 대시보드 동작에 직접 영향을 줍니다. 백엔드는 이 값을 보고 "서비스 맵에서 어느 쪽 화살표인지"를 판단하고, 서비스 단위 지연 계산에서 중복을 제거합니다.

Kind의미예시보통 누가 생성
SERVER외부 요청을 받아 처리HTTP 요청 핸들러, gRPC 서버자동 계측
CLIENT외부로 동기 호출HTTP 클라이언트, DB 쿼리자동 계측
PRODUCER비동기 메시지 발행Kafka produce, SQS send자동 + 수동 보강
CONSUMER비동기 메시지 수신Kafka consume자동 + 수동 보강
INTERNAL프로세스 내부 작업비즈니스 로직 구간개발자 수동 계측
Event와 Link의 차이

Event는 같은 Span 안에서 일어난 시점 기록입니다. 예외 발생, 캐시 미스 같은 것이 여기 들어갑니다. Link는 다른 트레이스의 Span을 가리키는 참조입니다. 메시지 큐에서 100건을 배치로 처리할 때, 소비자 Span 하나가 100개의 생산자 Span을 Link로 걸면 부모-자식 관계를 억지로 만들지 않고도 연결을 표현할 수 있습니다.

SECTION 03

컨텍스트 전파 — 트레이스가 끊기는 지점

분산 트레이스가 이어지는 원리는 의외로 단순합니다. 서비스 A가 서비스 B를 호출할 때 HTTP 헤더에 자기 Trace ID와 Span ID를 실어 보내고, B는 그 값을 자기 Span의 부모로 삼습니다. 그게 전부입니다.

W3C Trace Context 표준

히어로의 해부기에서 본 그 형식입니다. 네 부분이 하이픈으로 이어집니다. 

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             └┬┘ └──────────────┬───────────────┘ └───────┬──────┘ └┬┘
              version         trace-id (16바이트)      parent-id     flags
                                                       (호출자 Span)  (샘플링)
  • version — 현재는 00만 존재합니다
  • trace-id — 32자리 16진수. 전부 0이면 무효로 취급됩니다
  • parent-id — 16자리 16진수. 나를 호출한 쪽의 Span ID입니다
  • trace-flags — 최하위 비트가 sampled 플래그. 01이면 "이 트레이스는 기록 대상"

함께 다니는 헤더가 하나 더 있습니다. tracestate는 벤더별 추가 정보를 담는 키-값 목록으로, 이기종 시스템이 섞여 있을 때 각자의 문맥을 잃지 않게 해줍니다. 그리고 OTel에는 Baggage라는 별도 개념이 있는데, 테넌트 ID처럼 애플리케이션이 직접 정한 값을 전 구간에 흘려보내는 용도입니다. 다만 Baggage에 넣은 값은 자동으로 Span 속성이 되지 않으며, 외부로 나가는 요청에도 실리므로 민감정보를 넣으면 안 됩니다.

B3 헤더를 만나면

Zipkin 계열 시스템은 b3 또는 X-B3-TraceId 헤더를 씁니다. 기존 시스템과 섞이는 전환기에는 전파기(propagator)를 여러 개 동시에 등록해 들어올 땐 둘 다 읽고 나갈 땐 둘 다 쓰도록 설정합니다. 이 설정은 보통 엔지니어가 Instrumentation 리소스에서 지정합니다(8편).

전파가 끊기는 다섯 가지 상황

카드를 눌러 원인과 담당자를 확인하세요. 실무 제보의 대부분이 이 다섯 가지 안에 들어갑니다.

스레드풀에 작업을 넘기면 끊긴다

요청 처리 도중 ExecutorService나 별도 스레드로 넘기면 부모 Span 정보가 사라집니다.

컨텍스트는 스레드 로컬에 저장됩니다. 다른 스레드는 그 값을 보지 못합니다. Java는 Context.current().wrap(runnable)로 감싸거나 계측된 Executor를 쓰고, Python은 contextvars, Node.js는 AsyncLocalStorage가 이 역할을 합니다. 5편에서 언어별로 다룹니다.

개발자
인그레스나 WAF가 헤더를 지운다

외부에서 들어온 요청의 traceparent가 게이트웨이를 지나면서 사라집니다.

일부 프록시·WAF는 화이트리스트에 없는 헤더를 제거합니다. 엔지니어가 traceparent, tracestate, baggage를 통과 허용 목록에 넣어야 합니다. 서비스 메시를 쓴다면 메시 설정도 함께 확인합니다.

엔지니어
메시지 큐를 건너면 끊긴다

Kafka로 메시지를 보내고 컨슈머가 받는 순간 새 트레이스가 시작됩니다.

HTTP와 달리 큐에는 자동으로 헤더가 실리지 않는 경우가 많습니다. 생산자가 메시지 헤더에 컨텍스트를 주입(inject)하고 소비자가 추출(extract)해야 합니다. 배치 소비라면 부모-자식 대신 Link를 쓰는 편이 정확합니다.

개발자
계측 안 된 서비스가 중간에 끼어 있다

A → B → C 중 B가 레거시라 트레이스가 A와 C로 쪼개집니다.

B가 헤더를 그냥 통과만 시켜도 A와 C는 이어집니다. 자체 Span이 안 생길 뿐입니다. 레거시에 손대기 어렵다면 최소한 헤더 패스스루만 요청하는 것이 현실적인 합의점입니다.

공동 협의
샘플링 플래그가 중간에 뒤집힌다

일부 Span만 저장되어 트레이스가 구멍 난 채로 보입니다.

서비스마다 다른 샘플러를 쓰면 생깁니다. parentbased_* 계열 샘플러를 쓰면 부모의 결정을 그대로 따르므로 트레이스가 온전히 남거나 온전히 버려집니다. 조직 전체가 같은 샘플러 종류를 쓰는 것이 원칙입니다.

개발자 (정책은 엔지니어)
클럭이 어긋나 순서가 뒤엉킨다

자식 Span이 부모보다 먼저 시작한 것으로 보입니다.

노드 간 시계 차이 때문입니다. 트레이스 자체는 끊기지 않지만 폭포수 화면이 읽기 어려워집니다. NTP 동기화 상태 점검이 답이고, 이건 명백히 인프라 영역입니다.

SECTION 05

로그 데이터 모델

OTel의 LogRecord는 새로운 로깅 프레임워크가 아닙니다. 기존 로그를 표준 구조에 담아 트레이스와 이어붙이기 위한 그릇입니다.

필드의미채우는 주체
Timestamp사건이 실제로 일어난 시각로깅 라이브러리
ObservedTimestamp수집기가 관측한 시각Collector
SeverityNumber / SeverityText숫자 등급과 원본 문자열로깅 라이브러리
Body메시지 본문. 문자열 또는 구조체개발자
Attributes구조화된 부가 정보개발자
TraceId / SpanId어느 요청의 로그인가SDK 자동 주입
Resource어느 서비스·파드의 로그인가SDK + Collector

SeverityNumber를 숫자로 정의한 이유

WARN, WARNING, W, 4 — 같은 뜻인데 표기가 제각각입니다. OTel은 1~24 범위의 숫자를 정해두고, 원본 문자열은 SeverityText에 따로 보관합니다. 덕분에 "ERROR 이상만 보여줘"라는 필터가 모든 언어·프레임워크에서 동일하게 동작합니다.

로그가 들어오는 두 갈래 경로

SDK 직접 전송

애플리케이션이 OTLP로 로그를 바로 보냅니다. Trace 연결이 가장 정확하지만, 앱이 전송 실패를 감당해야 하고 stdout 기반 도구와 어긋납니다.

stdout 수집

앱은 평소대로 표준 출력에 찍고, Collector가 노드의 로그 파일을 읽어갑니다. 쿠버네티스에서 가장 흔한 구성이며 앱 부담이 없습니다. 대신 trace_id를 로그 본문에 찍어둬야 연결됩니다.

1편의 회색지대 재등장

이 두 경로 중 무엇을 표준으로 할지는 엔지니어가 정해 문서로 공지해야 합니다. 정하지 않으면 팀마다 다르게 구현하고, 나중에 로그 파이프라인을 두 벌 유지하게 됩니다. 실무 기본값은 stdout 수집이며, 개발자에게 요구할 것은 딱 하나 — 로그 포맷에 trace_id 필드를 넣어달라는 것입니다.

SECTION 06

Resource와 Attribute — 1편의 숙제에 답하기

둘 다 키-값 쌍입니다. 문법적으로 구분이 없습니다. 그런데 소유권과 비용 구조가 완전히 다릅니다.

Resource — 누가 보냈는가

텔레메트리를 만들어낸 주체의 정체입니다. 프로세스가 사는 동안 변하지 않고, 그 프로세스의 모든 신호에 동일하게 붙습니다. 값의 종류가 유한합니다.

Attribute — 무슨 일이 있었는가

개별 Span·메트릭·로그마다 다른 값이 붙습니다. 요청마다 달라지므로 카디널리티가 여기서 폭발합니다.

실무 판별법은 간단합니다. "이 값이 프로세스가 살아 있는 동안 바뀌는가?" 안 바뀌면 Resource, 요청마다 바뀌면 Attribute입니다.

직접 분류해 보기

SECTION 07

시맨틱 컨벤션

속성 이름과 의미를 표준화한 규약입니다. 이게 있어야 서비스마다 쿼리를 따로 짤 필요가 없습니다.

효과를 체감하는 방법

컬럼형 저장소에 데이터가 들어간다고 생각해 봅시다. 모든 서비스가 http.response.status_code라는 같은 이름을 쓰면, 이 값은 단일 컬럼이 됩니다. "지난 한 시간 서비스별 에러율"은 서비스 수와 무관하게 하나의 GROUP BY로 끝납니다. 이름이 제각각이면 서비스마다 필드 매핑 테이블을 유지해야 하고, 신규 서비스가 들어올 때마다 대시보드를 고쳐야 합니다.

이름 짓는 규칙

  • 전부 소문자, 점(.)으로 네임스페이스를 구분합니다
  • 네임스페이스 안의 단어는 밑줄(_)로 잇습니다 — http.response.status_code
  • 표준 네임스페이스(http, db, k8s 등)에 임의 속성을 추가하지 않습니다
  • 회사 고유 속성은 자체 네임스페이스를 씁니다 — acme.order.channel
  • 배열 값을 담는 속성은 복수형으로 씁니다

흔한 실수와 표준 표기

httpMethod→http.request.method 카멜케이스는 OTel 규약이 아닙니다. 점 구분 네임스페이스를 씁니다.
status→http.response.status_code 네임스페이스 없는 일반 명사는 다른 의미와 충돌합니다. DB 상태인지 HTTP 상태인지 알 수 없습니다.
http.url = /orders/8f3a-9c21→http.route = /orders/{id} 실제 ID를 넣으면 요청마다 새 시계열이 생깁니다. 라우트 템플릿을 넣어야 합니다.
env→deployment.environment.name 약어는 팀마다 다르게 해석됩니다. 표준 속성이 이미 정의돼 있으면 그것을 씁니다.
http.custom_tenant→acme.tenant.id 표준 네임스페이스를 침범하면 향후 표준이 같은 이름을 정의할 때 충돌합니다.

속성 이름이 바뀌면 어떻게 되나

표준도 개정됩니다. 실제로 deployment.environment는 나중에 deployment.environment.name으로 바뀌었습니다. OTel은 이를 위해 Schema URL이라는 장치를 둬서 데이터가 어느 버전 규약을 따르는지 표시하게 합니다. MSP 관점에서 중요한 것은 하나입니다 — SDK·에이전트 버전을 올릴 때 속성 이름이 바뀔 수 있으니, 대시보드가 깨지는지 검증 환경에서 먼저 확인해야 합니다. 1편의 회색지대 "SDK 버전 정책"이 필요한 진짜 이유가 이것입니다.

AI 워크로드를 운영한다면

LLM·에이전트 호출을 계측하려는 경우, GenAI 컨벤션은 2026년 5월 전용 저장소로 옮겨졌고 아직 변동이 잦습니다. 지금 도입한다면 참조 커밋을 고정해 두고, 속성 이름을 코드에 흩뿌리지 말고 상수 한 곳에 모아두는 편이 안전합니다. 이름이 바뀌었을 때 고칠 지점이 한 곳으로 줄어듭니다.

엔지니어가 준비할 방어선

규약은 반드시 어겨집니다. 그래서 엔지니어 쪽에도 2차 방어선이 필요합니다. Collector 단계에서 처리할 수 있으며, 구체적인 설정은 9편에서 다룹니다.

  • 금지 속성 키를 아예 제거하는 변환 규칙
  • 허용되지 않은 service.name 패턴을 감지해 알림
  • 속성 개수·길이 상한을 걸어 비정상 데이터 차단
  • 카디널리티 급증 감지 — 새 시계열 생성 속도를 모니터링
