컨트롤 플레인 해부와 벤더별 구현 차이

kubectl 한 줄은 API 서버 안에서 열두 개의 관문을 지나 etcd에 닿습니다. 그 관문마다 벤더가 다른 부품을 끼워 넣었고, 매니지드에서는 일부 관문이 아예 보이지 않습니다. 이 편은 요청 하나를 끝까지 따라가며 어디서 무엇이 실패할 수 있고, 그것을 어떤 벤더에서 어떻게 볼 수 있는지를 정리합니다.

요청 하나를 끝까지 따라가기

요청 종류를 고르면 그 요청이 실제로 지나는 단계가 켜지고, 건너뛰는 단계는 흐려집니다. 단계를 누르면 그 단계에서 일어나는 일, 실패했을 때의 모습, 벤더별 차이, 지켜볼 지표가 나옵니다.

이 편의 목표

1편에서 “매니지드에서는 할 수 없는 것” 표를 봤습니다. 이 편은 그 표의 이유를 설명합니다. 컨트롤 플레인이 어떻게 생겼는지 알아야 무엇을 벤더에 맡겼는지, 맡긴 뒤에도 무엇이 여전히 내 책임인지 구분할 수 있습니다.

  • kube-apiserver의 처리 단계를 순서대로 말할 수 있고, HTTP 상태 코드만 보고 어느 단계에서 실패했는지 짚을 수 있습니다.
  • APF(API Priority and Fairness)가 왜 인가보다 먼저 동작하는지, LIST가 왜 비싼지 설명하고, 컨트롤 플레인 부하의 원인을 찾을 수 있습니다.
  • etcd의 리비전·컴팩션·디프래그·쿼터의 관계를 이해하고, 백업·복구 절차를 kubeadm·RKE2·OpenShift·Talos별로 실행할 수 있습니다.
  • EKS·AKS·GKE의 컨트롤 플레인에서 보이는 것과 보이지 않는 것, 그리고 컨트롤 플레인에서 노드로 가는 네트워크 경로가 왜 웹훅 장애의 원인이 되는지 설명할 수 있습니다.
  • kubeadm·Cluster API·eksctl·openshift-install·RKE2·Talos·Terraform 중 고객 환경에 맞는 생성 도구를 고르고, 생성 도구와 운영 도구가 어긋날 때의 위험을 설명할 수 있습니다.

etcd 토폴로지: stacked와 external

kubeadm은 두 가지를 지원합니다. stacked는 각 컨트롤 플레인 노드에 etcd 멤버를 함께 두는 기본 방식으로 노드 수가 적고 구성이 단순하지만, 노드 하나를 잃으면 API 서버와 etcd 멤버를 동시에 잃습니다. external은 etcd를 별도 노드 3·5대로 분리해 장애 영역과 디스크 I/O를 떼어 놓는 방식으로, 대형 클러스터나 디스크 경합이 큰 환경에 맞습니다. kubeadm은 새 멤버를 합류시킬 때 etcd learner 모드를 써서, 아직 데이터를 따라잡지 못한 멤버가 쿼럼 계산에 들어가 쿼럼을 깨는 위험을 줄입니다.

컨트롤러 매니저와 스케줄러: 조정 루프와 리더 선출

컨트롤러와 스케줄러는 모두 같은 패턴으로 움직입니다. informer가 API 서버를 watch해 로컬 캐시를 유지하고, 바뀐 객체의 키를 작업 큐에 넣고, 워커가 큐에서 꺼내 “원하는 상태와 실제 상태의 차이”를 메우는 API 요청을 보냅니다. 이 요청들도 사용자 요청과 똑같이 요청 경로 전체를 지나고 APF 대상이 됩니다.

  • 리더 선출. 여러 인스턴스 중 하나만 일하도록 kube-system의 Lease 객체(kube-controller-manager, kube-scheduler)를 주기적으로 갱신합니다. 리더가 죽으면 Lease 만료(기본 15초) 뒤 다른 인스턴스가 넘겨받으므로, 그동안 새 Pod 배정과 컨트롤러 동작이 잠시 멈춥니다.
  • 자기 자신의 API 호출 한도. 컨트롤러 매니저는 기본 --kube-api-qps 20, burst 30, 스케줄러는 설정 파일의 clientConnection qps 50, burst 100이 기본입니다. 대형 클러스터에서 Pod 생성이 몰리면 이 한도가 병목이 되어 “스케줄링이 느리다”로 나타납니다.
  • 벤더 차이. Native·RKE2는 이 값과 컨트롤러별 동시성(--concurrent-deployment-syncs 등)을 직접 조정합니다. 매니지드는 조정할 수 없고, EKS는 Provisioned 티어별로 Pod 스케줄링 처리량을 공개해 이 한도를 상품화했습니다.

RKE2·OpenShift·Talos는 모두 stacked 계열이고, 매니지드는 내부 구조를 공개하지 않습니다. 대신 EKS는 컨트롤 플레인 용량을 티어로 노출하기 시작했습니다(5장).

APF와 컨트롤 플레인 부하

API Priority and Fairness는 API 서버의 동시 처리 용량을 seat라는 단위로 나누고, 요청을 우선순위 수준별로 격리하는 장치입니다. 1.29에서 GA가 됐고 모든 배포 방식에서 켜져 있습니다.

세 가지 개념

  • 전체 seat. 업스트림 기본값은 --max-requests-inflight(400)와 --max-mutating-requests-inflight(200)의 합인 600 seat이며, API 서버 인스턴스마다 따로 계산됩니다.
  • PriorityLevelConfiguration. 전체 seat를 수준별로 나눈 몫입니다. 기본으로 exempt, system, node-high, leader-election, workload-high, workload-low, global-default, catch-all이 있습니다. 한 수준이 넘쳐도 다른 수준은 영향을 받지 않는 것이 핵심입니다.
  • FlowSchema. 요청자·동사·리소스를 보고 어느 수준으로 보낼지 정하는 규칙입니다. 같은 수준 안에서는 flow(대개 사용자 단위)별로 공정 큐잉을 해, 한 사용자가 수준 전체를 독점하지 못하게 합니다.

LIST가 비싼 이유

APF는 요청마다 비용을 추정합니다. 단일 GET은 1 seat지만, LIST는 반환할 것으로 예상되는 객체 수에 비례해 최대 10 seat까지 차지하고, watch는 시작할 때 초기 이벤트 전송 비용을 따로 계산합니다. 네임스페이스 구분 없이 전체 Pod를 주기적으로 LIST하는 컨트롤러나 모니터링 에이전트가 컨트롤 플레인 부하의 가장 흔한 원인인 이유입니다. 정석은 informer(watch + 로컬 캐시)를 쓰는 것이고, 1.33부터는 스트리밍 LIST 응답, 1.37에서는 etcd RangeStream이 대형 LIST의 메모리 비용을 더 낮췄습니다.

watch 캐시와 일관 읽기

API 서버는 리소스별로 etcd를 watch하며 메모리 캐시를 유지하고, 대부분의 LIST·watch를 여기서 응답합니다. 최신 버전에서는 resourceVersion을 지정하지 않은 ‘최신 상태’ LIST도 캐시가 최신임을 확인한 뒤 캐시에서 응답할 수 있습니다. 이 캐시가 API 서버 재시작 때 한꺼번에 다시 채워지면서 etcd에 부하 폭주를 일으키던 문제를, 1.37에서 Stable로 마무리된 watch 캐시 초기화 안정화 작업과 RangeStream이 함께 줄입니다.

etcd 3.7에서 달라진 것

  • RangeStream RPC. 대형 범위 읽기를 바이트 기준 청크로 나눠 스트리밍합니다. Kubernetes 1.37의 EtcdRangeStream 기능 게이트(Beta, 기본 켜짐)와 짝을 이루며, 둘 다 갖춰졌을 때만 동작합니다. API 서버가 etcd 지원 여부를 감지해 없으면 기존 방식으로 돌아갑니다. 동작 여부는 etcd_request_duration_seconds_count{operation="listStream"}이 0보다 큰지로 확인합니다.
  • v2 저장소 제거. v3 전환 이후 남아 있던 레거시 v2 저장소가 사라졌습니다. 아주 오래된 클러스터를 업그레이드할 때 확인 대상입니다.
  • keys-only 최적화. 키만 조회할 때 값을 디스크에서 읽지 않고 인메모리 인덱스만 봅니다. 위 진단 명령이 더 가벼워졌습니다.

RKE2 v1.37.0+rke2r1은 etcd v3.7.1을 번들합니다. kubeadm은 버전별 기본 etcd 이미지를 따르므로 kubeadm upgrade plan 출력에서 etcd 버전을 확인하세요.

배포판의 컨트롤 플레인

OpenShift: 오퍼레이터가 운영하는 컨트롤 플레인

OpenShift 컨트롤 플레인은 업스트림 구성 요소에 OpenShift 고유 API 서버들이 더해진 구조입니다. kube-apiserver 옆에 Route·Project 같은 OpenShift API를 제공하는 openshift-apiserver, OAuth 관련 API를 제공하는 oauth-apiserver가 집계 API로 붙습니다. 그리고 각 구성 요소마다 전담 오퍼레이터(kube-apiserver-operator, etcd-operator 등)가 있어서 인증서 교체, 설정 반영, 버전 교체를 스스로 수행합니다. 전체를 지휘하는 것이 Cluster Version Operator입니다.

  • 설정은 CR로만. API 서버 플래그를 직접 고치지 않고 APIServer, Authentication, OAuth 같은 클러스터 설정 CR을 바꾸면 오퍼레이터가 정적 Pod를 다시 굴립니다. 노출되지 않은 설정은 바꿀 수 없습니다.
  • 상태는 ClusterOperator로. oc get clusteroperators에서 Available·Progressing·Degraded를 보는 것이 OpenShift 컨트롤 플레인 점검의 첫 단계입니다.
  • etcd는 오퍼레이터가 멤버를 관리. 멤버 교체·인증서·디프래그 일부를 오퍼레이터가 처리하지만, 백업 실행과 외부 보관은 여전히 운영자 몫입니다.

RKE2: 단일 바이너리와 내장 etcd

RKE2는 하나의 rke2 바이너리가 서버(컨트롤 플레인) 또는 에이전트(워커) 역할을 합니다. 서버 노드는 etcd·API 서버·스케줄러·컨트롤러 매니저를 정적 Pod로 띄우고, 노드 합류를 위한 supervisor API(9345 포트)를 따로 엽니다. 새 노드는 토큰으로 9345에 접속해 인증서와 설정을 받은 뒤 6443을 씁니다.

  • 설정 파일 하나. /etc/rancher/rke2/config.yaml에 CNI, TLS SAN, CIS 프로파일, etcd 스냅샷 정책, 컴포넌트 추가 인자(kube-apiserver-arg 등)를 선언합니다. 매니지드와 달리 API 서버 플래그를 바꿀 수 있습니다.
  • etcd 스냅샷 기본 제공. 12시간마다·5개 보관이 기본이고 S3 업로드를 붙일 수 있습니다. 스냅샷 기록은 클러스터 안의 ETCDSnapshotFile 리소스로도 보입니다.
  • 토큰이 곧 복구 키. 서버 토큰은 노드 합류뿐 아니라 데이터스토어 안의 부트스트랩 데이터를 암호화하는 데도 쓰여, 스냅샷 복구 때 필요합니다. 토큰을 잃으면 스냅샷이 있어도 복구가 어려워집니다.

Talos Linux: API로만 다루는 노드

Talos에는 SSH도 셸도 패키지 관리자도 없습니다. 노드 OS와 Kubernetes 구성 전체가 하나의 머신 설정 YAML로 선언되고, talosctl이 mTLS로 노드 API를 호출해 적용합니다.

  • talosctl gen config로 설정 생성 → apply-config로 노드에 적용 → 첫 컨트롤 플레인 노드에서 한 번만 talosctl bootstrap으로 etcd를 시작합니다.
  • etcd 멤버십은 Talos가 관리합니다. 노드를 리셋하면 멤버에서 빠지고, 진단은 talosctl etcd members, talosctl logs etcd로 합니다.
  • OS 업그레이드(talosctl upgrade)와 Kubernetes 업그레이드(talosctl upgrade-k8s)가 분리되어 있습니다.
  • 운영자 습관이 가장 크게 바뀌는 배포판입니다. “노드에 들어가서 확인한다”가 불가능하므로 관측 체계가 먼저 갖춰져 있어야 합니다.

- level: Metadata

현장 사례

GKE 비공개 클러스터에서 웹훅만 타임아웃

상황. 비공개 GKE 클러스터에 정책 엔진을 설치했더니 Pod 생성이 전부 context deadline exceeded로 실패했습니다. 정책 엔진 Pod는 Running이었습니다.

원인. 웹훅 서버가 9443 포트에서 대기했는데, 컨트롤 플레인에서 노드로 허용된 포트는 기본적으로 443과 10250 정도뿐이었습니다. 노드 → API 서버 방향은 멀쩡해 다른 모든 것이 정상으로 보였습니다.

대응. 컨트롤 플레인 대역에서 노드의 웹훅 포트로 가는 방화벽 규칙을 추가하거나, 웹훅을 443으로 노출했습니다. 같은 문제가 EKS에서는 클러스터 보안 그룹 규칙, AKS에서는 konnectivity 경로 이상으로 나타납니다.

교훈. 웹훅을 도입할 때는 “Pod가 떴는가”가 아니라 “API 서버가 그 포트에 닿는가”를 검증 항목으로 넣으세요.

웹훅 Pod 하나가 죽자 클러스터 전체 배포가 멈췄다

상황. 모든 네임스페이스의 Pod 생성을 검사하는 웹훅(failurePolicy: Fail, 레플리카 1)의 노드가 다운되자, 어떤 Pod도 만들 수 없게 됐습니다. 웹훅 자신의 Deployment가 새 Pod를 만들려 해도 그 생성 요청이 같은 웹훅을 거쳐야 해서 영원히 실패했습니다.

원인. namespaceSelector가 웹훅 자신의 네임스페이스와 kube-system을 제외하지 않았고, 레플리카와 PDB가 없었습니다. 교착 상태입니다.

대응. 웹훅 설정을 지워 우선 복구한 뒤, 웹훅 네임스페이스와 kube-system을 제외하고, 레플리카 3 + PDB + 토폴로지 분산, timeoutSeconds 축소를 적용했습니다. 단순한 필드 규칙은 VAP로 옮겼습니다.

교훈. Fail 정책의 웹훅은 컨트롤 플레인의 일부로 취급해야 합니다. 매니지드에서는 이 웹훅이 사실상 내가 운영하는 유일한 컨트롤 플레인 구성 요소입니다.

EKS Standard 클러스터의 DB가 8GB에 다가간다

상황. 데이터 파이프라인 고객의 EKS 클러스터에서 apiserver_storage_size_bytes 합계가 꾸준히 늘었습니다. 상위 리소스는 워크플로 엔진의 CR, Helm 릴리스 Secret, Event였습니다.

원인. 실행마다 CR이 생기고 지워지지 않았고, 수백 개 릴리스가 Helm 이력을 기본값으로 쌓고 있었습니다. Standard 모드 DB 한도는 8GB입니다.

대응. 워크플로 CR에 TTL 정리를 걸고, Helm --history-max를 낮추고, 오래된 ReplicaSet 이력을 줄였습니다. 성장 추세가 계속되자 Provisioned 티어(DB 16GB)를 비용과 함께 검토했습니다. 티어로 올리면 다시 Standard로 내려가기 전 크기를 줄여야 한다는 점도 함께 기록했습니다.

교훈. 매니지드에서도 etcd 크기는 내 워크로드가 만드는 내 문제입니다. 저장 크기 지표에 경보를 거세요.

어느 날 아침 kubeadm 클러스터에 kubectl이 안 붙는다

상황. 1년 넘게 업그레이드 없이 운영한 온프렘 kubeadm 클러스터에서 x509: certificate has expired가 나며 API 접근이 끊겼습니다.

원인. kubeadm이 발급하는 컨트롤 플레인 인증서의 유효 기간은 1년입니다. kubeadm upgrade 때 자동 갱신되지만, 업그레이드를 하지 않으면 그대로 만료됩니다. kubelet 클라이언트 인증서는 자동 회전되므로 노드는 멀쩡해 보이는 경우가 많습니다.

대응. kubeadm certs check-expiration으로 확인 후 kubeadm certs renew all, 컨트롤 플레인 정적 Pod 재시작, admin.conf 재배포.

교훈. 업그레이드는 버전 문제가 아니라 인증서 수명 관리이기도 합니다. 만료 30일 전 경보를 모든 Native·배포판 클러스터에 거세요. RKE2도 인증서 수명과 자동 교체 조건을 확인해야 합니다.

RKE2 스냅샷은 있었는데 복구할 수 없었다

상황. 단일 서버 노드 RKE2 클러스터의 디스크가 손상됐습니다. 자동 스냅샷은 정상적으로 돌고 있었습니다.

원인. 스냅샷이 같은 노드의 같은 디스크에만 저장되어 있었고, 서버 토큰도 그 노드에만 있었습니다.

대응. 다른 백업 시스템의 오래된 VM 이미지로 부분 복구했습니다. 이후 S3 업로드, 토큰의 비밀 저장소 보관, 분기별 복구 리허설을 표준화했습니다.

교훈. “기본 제공 스냅샷”은 공동 책임 칸입니다(1편). 백업은 다른 장애 영역에 있고, 복구 리허설을 해 본 것만 백업입니다.

GKE zonal 클러스터 업그레이드 시간에 CI/CD가 줄줄이 실패

상황. 매주 같은 시간대에 배포 파이프라인이 API 연결 실패로 깨졌습니다.

원인. 비용 때문에 zonal로 만든 GKE 클러스터에 유지보수 창이 업무 시간으로 잡혀 있었고, 컨트롤 플레인 업그레이드·크기 조정 동안 API가 몇 분씩 끊겼습니다.

대응. 운영 클러스터를 regional로 재구성하고, 남은 zonal 클러스터는 유지보수 창을 야간으로 옮기고 파이프라인에 재시도를 넣었습니다.

교훈. 매니지드라도 컨트롤 플레인의 이중화 여부는 내가 고른 옵션입니다. 견적 단계에서 SLA와 함께 설명해야 할 항목입니다.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. API 서버의 처리 순서는 인증 → 감사 → 위장 → APF → 인가 → 디코딩 → 변경 어드미션 → 검증 → 검증 어드미션 → 저장이며, 상태 코드로 실패 단계를 짚을 수 있습니다.
  2. APF는 인가보다 먼저 seat를 점유하고, LIST는 최대 10 seat를 쓰므로 컨트롤 플레인 부하의 주범은 대개 내 클라이언트입니다.
  3. etcd는 컴팩션(논리)과 디프래그(물리)를 구분해야 하고, 쿼터 초과는 쓰기 정지로 이어지며, 스냅샷은 CA·키와 함께여야 복구됩니다.
  4. 매니지드의 핵심 차이는 컨트롤 플레인에서 노드로 가는 경로(ENI·konnectivity)와 관찰 수단이며, 웹훅이 이 경로의 가장 흔한 피해자입니다.
  5. 생성 도구는 상태를 어디에 기억하는지와 day-2 방식으로 고르고, 만든 도구와 고치는 도구를 일치시켜야 합니다.
