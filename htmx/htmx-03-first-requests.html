02

다섯 동사와 VM 기능

htmx 4.0.1 소스가 인식하는 동사 속성은 hx-get, hx-post, hx-put, hx-patch, hx-delete, 그리고 새 HTTP 메서드용 hx-query입니다. 이 시리즈는 앞의 다섯 개를 HTTP 의미대로 씁니다.

hx-get조회상세 보기, 편집 폼 받기, 더 보기. 서버 상태를 바꾸지 않는다
hx-post생성·동작태그 추가, 재시작 같은 "명령"
hx-put통째로 교체메모 전체를 새 내용으로 저장
hx-patch일부만 수정VM의 모니터링 필드 하나만 변경
hx-delete삭제VM 삭제, 태그 삭제

파라미터는 어디에 실리나

소스 코드의 판단은 한 줄입니다. 메서드가 GET 또는 DELETE이면 "쿼리 파라미터를 쓰는 요청"으로 분류합니다. 이 분류가 두 가지를 결정합니다.

구분GET · DELETEPOST · PUT · PATCH
값이 실리는 곳URL 쿼리 문자열 (?q=db)요청 본문
본문 형식본문 없음application/x-www-form-urlencoded. 파일 입력이 있거나 hx-encoding="multipart/form-data"면 multipart
둘러싼 form 포함포함하지 않음 (요소 자신이 form일 때만)포함함 (elt.form 또는 가장 가까운 상위 form)
왜 DELETE는 폼 값을 안 싣나

HTTP 명세상 DELETE 요청 본문에는 정해진 의미가 없어서 서버·프록시가 무시하거나 거부할 수 있습니다. htmx는 DELETE를 GET처럼 취급해 값을 쿼리에 싣고, 둘러싼 폼도 자동으로 끌어오지 않습니다. 그래서 삭제할 대상은 /vms/web-01/tags/db처럼 URL 경로에 담는 것이 정석입니다. 필요하면 hx-include로 명시적으로 넣을 수 있습니다(4편).

서버에서 본문을 읽으려면

2편의 서버는 GET·POST·DELETE에 본문이 필요 없었기 때문에 본문 파서가 없었습니다. 이번 편부터 PUT·PATCH·POST에 폼 값이 실리므로 Express에는 express.urlencoded() 미들웨어를, FastAPI에는 Form() 매개변수와 python-multipart 패키지를 추가합니다. FastAPI는 urlencoded 본문을 읽을 때도 이 패키지가 필요합니다.

apps/server/src/app.js (추가된 부분)
// ①-2 폼 본문 파싱: htmx 4는 POST·PUT·PATCH 본문을 application/x-www-form-urlencoded로 보낸다
app.use(express.urlencoded({ extended: false }));
03

기본 트리거 규칙

hx-trigger를 쓰지 않으면 htmx가 요소 종류를 보고 이벤트를 정합니다. htmx 4.0.1 소스의 규칙은 세 줄입니다.

htmx 4.0.1 소스 발췌 (#initializeTriggers)
let trigger = hxTrigger || (elt.matches("form") ? "submit" :
    elt.matches("input:not([type=button]):not([type=submit]),select,textarea") ? "change" :
        "click");
요소기본 트리거실무에서 의미하는 것
<form>submitEnter 키와 제출 버튼 모두 동작. 이번 편의 태그 추가와 메모 저장이 이 방식
<input> (버튼 종류 제외), <select>, <textarea>change텍스트 입력은 포커스를 잃거나 Enter를 칠 때 발생. 체크박스·셀렉트는 바꾸는 즉시 발생
그 밖의 모든 요소clickbutton, a, div, tr 등

htmx가 막아 주는 브라우저 기본 동작

htmx는 요청을 보낼 때 브라우저의 기본 동작이 겹치지 않도록 다음 경우에 preventDefault()를 호출합니다(소스의 #shouldCancel). 폼 제출 이벤트, 폼 안의 제출 버튼 클릭(타입이 submit·image이거나 타입 없는 button), 링크 클릭이 해당합니다. 그래서 hx-post를 단 폼이 페이지를 새로고침하지 않고, hx-get을 단 링크가 주소를 이동하지 않습니다.

폼 안의 "취소" 버튼

메모 편집 폼의 취소 버튼에 type="button"을 꼭 붙인 이유입니다. <button>의 기본 타입은 submit이라서 타입을 생략하면 취소 버튼을 눌러도 폼의 hx-put이 함께 발동할 수 있습니다. 폼 안에서 제출이 아닌 버튼은 항상 type="button".

트리거를 바꾸는 방법(지연·조건·폴링·화면 진입 등)은 4편의 주제입니다. 이번 편에서는 기본값만으로 모든 기능을 만듭니다.

05

hx-target: 어디에 넣나

대상을 지정하지 않으면 요청을 보낸 요소 자신이 대상입니다. 단, hx-boost로 가로챈 링크·폼은 body가 대상입니다(소스의 #resolveTarget). 대상을 지정할 때는 일반 CSS 선택자 외에 htmx 전용 확장 선택자를 쓸 수 있습니다.

값찾는 요소이번 편 사용처
#detail 등 CSS 선택자문서 전체에서 첫 번째 일치VM 이름 → #detail
this요소 자신메모 편집 폼 → this
closest 선택자자신 포함 가장 가까운 조상closest .memo, closest .tags, closest tr, closest li
find 선택자하위에서 첫 번째 일치-
next / previous바로 다음·이전 형제 요소-
next 선택자 / previous 선택자문서 순서상 앞·뒤로 훑어 처음 일치하는 요소-
body, document, window해당 객체주로 hx-trigger의 from:에서 사용 (4편)
host섀도 DOM의 호스트 요소12편 웹 컴포넌트 아일랜드에서 사용

왜 closest가 통합에 중요한가

태그 블록에는 id가 없습니다. 대신 각 버튼이 closest .tags로 자기가 속한 블록을 찾아갑니다. 같은 태그 블록 템플릿이 한 화면에 여러 번 나와도(VM 여러 개를 비교하는 화면 등) 각 버튼은 자기 블록만 교체합니다. id에 의존하면 id 중복 문제가 생기지만, 상대 선택자는 템플릿을 어디에 넣든 그대로 동작합니다. 여러 팀의 조각을 한 포털에 모으는 통합 프로젝트에서는 이 성질이 특히 중요합니다.

2.x와 다른 점: 대상은 상속되지 않는다

htmx 2에서는 부모에 단 hx-target이 자식에게 자동으로 적용되었습니다. htmx 4에서는 hx-target:inherited="..."로 명시해야 합니다. 상속을 기대하고 부모에만 대상을 달면 자식 요청은 자기 자신을 대상으로 삼아, 버튼이 응답 HTML로 바뀌어 버리는 증상이 나타납니다. 4절의 관찰기 상자들이 명시적 상속의 예입니다.

선택자가 아무것도 찾지 못하면 htmx는 콘솔에 htmx: '#stage' on hx-target did not match any element 형태의 경고를 남기고 스왑하지 않습니다(6절 실험실의 "id 없음" outerHTML 뒤에 직접 확인 가능). "버튼을 눌렀는데 아무 일도 없다"면 네트워크 탭에 요청이 있는지, 콘솔에 대상 관련 경고가 있는지부터 확인하세요.

이 목록과 별칭은 htmx 4.0.1 소스의 #insertContent와 #normalizeSwapStyle에서 확인한 것입니다. 목록에 없는 값을 쓰면 확장이 처리하지 않는 한 "Unknown swap style" 오류가 납니다. 확장으로 새 스왑 방식을 추가하는 방법은 10편에서 다룹니다.

빈 응답은 어떻게 처리되나

소스의 규칙은 이렇습니다. 응답에 요소나 글자가 있으면 스왑합니다. 응답이 완전히 비어 있으면, 그 응답에 <hx-partial> 같은 부가 조각이 없을 때만 스왑합니다(빈 내용으로 교체). 그래서 2편의 VM 삭제는 빈 200 응답 + outerHTML로 행이 사라졌습니다. 반면 "부가 조각만 보내고 본 대상은 그대로 두고 싶다"면 본문 없이 hx-partial만 보내면 됩니다. 이 기본 판단은 swap 수식어 swapEmpty로 바꿀 수 있습니다(5편). delete는 내용 여부와 무관하게 항상 실행됩니다.

07

조각 설계 원칙 다섯 가지

htmx 속성은 클라이언트 쪽의 절반일 뿐입니다. 나머지 절반은 서버가 "어떤 모양의 HTML을 돌려주느냐"입니다. 이번 편 기능을 만들며 적용한 원칙을 먼저 정리합니다.

원칙뜻이번 편 적용
1. 응답 모양 = 대상 + 스왑의 계약outerHTML이면 응답은 대상과 같은 종류의 요소 하나, innerHTML이면 대상의 내용물메모 편집 폼(form.memo) ↔ 메모 보기(div.memo)가 서로를 outerHTML로 교체. 둘 다 클래스 memo를 가져 closest .memo가 양쪽에서 동작
2. 의심되면 블록 통째로바뀐 한 조각만 정교하게 보내기보다, 그 조각을 둘러싼 의미 단위 전체를 다시 그린다태그 추가·삭제 모두 .tags 블록 전체를 응답. 입력창 초기화·오류 표시·빈 목록 처리가 템플릿 하나로 끝남
3. 검증 실패 = 4xx + 같은 폼오류 메시지와 사용자가 입력한 값을 담은 폼을 다시 보낸다메모 500자 초과, 잘못된 태그 → 422. htmx 4는 4xx도 스왑하므로 별도 설정 불필요
4. 부수 효과는 함께 실어 보내기본 대상 외에 바뀌어야 할 곳은 같은 응답의 <hx-partial>로메모·태그·모니터링 변경 시 "최근 활동" 맨 위에 새 줄 삽입 (afterbegin)
5. 같은 URL, 페이지와 조각조각을 주는 URL도 주소창으로 열면 완전한 페이지가 된다/vms/web-01은 htmx 요청엔 상세 조각, 주소창엔 레이아웃 포함 상세 페이지
422를 쓰는 이유

400(잘못된 요청)은 요청 형식 자체가 깨졌을 때, 422(처리할 수 없는 내용)는 형식은 맞지만 내용이 규칙에 어긋날 때 씁니다. 상태 코드를 정확히 쓰면 htmx 쪽에서도 구분할 수 있습니다. htmx 4는 HTTP 오류 응답에 htmx:response:error 이벤트를 발생시키므로, 나중에 "저장 실패 시 토스트 띄우기" 같은 공통 처리를 이벤트 하나로 붙일 수 있습니다(8편). 2.x를 쓴다면 4xx가 기본으로 스왑되지 않으므로 이 패턴을 쓰려면 설정 변경이 필요합니다.
