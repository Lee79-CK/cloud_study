CHAPTER 01

RHOSO를 한 문장으로 말하면?

OpenStack의 관리 기능(Control Plane)을 OpenShift 위에서 컨테이너로 실행하고, 실제 VM은 외부 RHEL 서버(Data Plane)에서 실행하는 Red Hat의 프라이빗 클라우드 플랫폼입니다.

🏢

OpenShift

OpenStack API·DB·메시지 큐·스케줄러 같은 관리 서비스가 사는 건물

🧠

OpenStack

VM·네트워크·스토리지를 요청받고 조정하는 클라우드 두뇌

🖥️

RHEL Data Plane

KVM과 네트워크 에이전트가 실제로 VM을 실행하는 작업 현장

절대 먼저 외울 것RHOSO는 “OpenShift 안에서 VM을 실행하는 제품”이 아닙니다. OpenShift는 주로 OpenStack 컨트롤 플레인을 호스팅하고, 사용자 VM은 대체로 외부 RHEL Compute 노드에서 실행됩니다.

RHOSO의 이름 풀기

Red Hat+OpenStack Services+on OpenShift
  • OpenStack: 컴퓨팅·네트워크·스토리지를 API로 제공하는 IaaS 소프트웨어
  • OpenShift: Kubernetes 기반 컨테이너 플랫폼
  • RHOSO: OpenShift의 Operator 패턴을 이용해 OpenStack 관리 서비스를 배포·운영
CHAPTER 02

왜 기존 RHOSP에서 RHOSO로 바뀌었을까?

기존 OpenStack도 VM을 잘 만들었지만, 수많은 관리 서비스를 설치·업그레이드·복구하는 과정이 매우 복잡했습니다. RHOSO는 이 관리 영역을 Kubernetes/OpenShift 방식으로 바꿉니다.

예전 접근: 서버 역할 중심

Controller 노드에 여러 서비스를 설치하고, Pacemaker 같은 HA 도구와 구성 관리 도구를 조합했습니다.

사람이 “어느 서버에 어떤 서비스가 있는지”를 많이 의식

RHOSO 접근: 선언과 조정 중심

원하는 상태를 CR(Custom Resource)에 적으면 Operator가 실제 상태를 관찰하고 맞춥니다.

사람은 “원하는 결과”를 선언하고 플랫폼이 반복 조정

변화의 핵심 5가지

1. 컨테이너 네이티브

OpenStack 관리 서비스가 OpenShift 워크로드로 실행됩니다.

2. Operator 자동화

설치·업데이트·장애 복구를 반복 가능한 선언형 방식으로 관리합니다.

3. Control/Data 분리

관리 서비스와 VM 실행 서버의 생명주기를 더 명확히 분리합니다.

4. Ansible 기반 현장 구성

Operator가 데이터 플레인 RHEL 노드에 필요한 작업을 실행합니다.

5. OpenShift 관측성 활용

Pod 상태, 로그, Prometheus 지표, Alertmanager 등을 함께 활용합니다.

6. 확장 단위 명확화

비슷한 Compute 노드를 NodeSet으로 묶고 변경을 Deployment CR로 실행합니다.

초보자가 느끼는 어려움의 정체OpenStack 용어와 Kubernetes/OpenShift 용어가 동시에 나오기 때문입니다. 하지만 두 세계를 “클라우드 기능”과 “그 기능을 운영하는 플랫폼”으로 분리하면 이해가 빨라집니다.

그럼 OpenShift와 Operator는?

🏛️OpenShift = 행정동

교무실·배정실·보안실 등 관리 부서가 안정적으로 근무하는 건물

🤖Operator = 자동 교감

“배정실 3개 유지”라고 적으면 부족한 배정실을 다시 열어 원하는 상태를 유지

📄CR = 운영 주문서

어떤 부서를 몇 개 만들고 어떤 설정을 적용할지 적는 YAML 문서

CR과 명령서의 차이일반 스크립트는 “이 명령을 한 번 실행해”에 가깝습니다. CR은 “최종적으로 이 상태가 계속 유지되어야 해”에 가깝습니다.

CHAPTER 07

Operator, CRD, CR, Reconciliation

RHOSO를 이해하려면 OpenShift 전문가가 될 필요는 없지만, 아래 네 단어는 반드시 알아야 합니다.

Operator

특정 소프트웨어를 설치·설정·운영하는 자동 관리자

CRD

Kubernetes에 새 자원 종류를 가르치는 설계 규칙

CR

CRD 규칙에 맞춰 작성한 실제 자원 주문서

Reconciliation

현재 상태와 원하는 상태의 차이를 계속 줄이는 반복 과정

자원무엇을 표현?쉽게 비유

NetConfig데이터센터 네트워크의 이름·VLAN·서브넷학교 도로·복도 설계도

네트워크 기초: 이름부터 나누기

RHOSO 네트워크가 어려운 이유는 “플랫폼 관리용 네트워크”와 “사용자 VM용 네트워크”가 동시에 나오기 때문입니다.

CHAPTER 09

스토리지 기초: 무엇을 어디에 저장하나?

종류OpenStack 서비스비유주요 용도
ImageGlance빈 컴퓨터를 만드는 OS 설치 USBVM 부팅 템플릿
Ephemeral DiskNova/Compute교실에 붙어 있는 임시 책상VM 수명과 함께 사라질 수 있는 로컬 디스크
Block VolumeCinder분리 가능한 외장 SSDDB·업무 데이터, VM과 독립된 영구 디스크
Shared FileManila여러 사람이 함께 쓰는 공유 폴더NFS/CephFS 등 파일 공유
ObjectSwift 또는 S3 호환번호표가 붙은 대형 창고 상자백업, 로그, 미디어, 비정형 데이터

Ceph가 자주 등장하는 이유

Ceph는 여러 서버의 디스크를 하나의 분산 저장소처럼 묶고, 장애가 나도 데이터를 복제·분산해 사용할 수 있게 합니다. RHOSO에서는 외부 Red Hat Ceph Storage를 Glance, Cinder, Nova의 저장소 백엔드로 연계할 수 있습니다.

Glance + Ceph RBD

VM 이미지 파일을 분산 블록 장치로 저장

Cinder + Ceph RBD

사용자 볼륨을 분산 저장

Nova + Ceph RBD

인스턴스 디스크를 공유형 분산 저장소에 배치 가능

중요한 분리OpenShift Control Plane 자체의 PVC 저장소와, OpenStack 사용자가 쓰는 VM/볼륨 저장소는 목적과 장애 영향도가 다릅니다. 둘을 같은 “스토리지”라고 뭉뚱그리면 장애 분석이 어려워집니다.
CHAPTER 10

RHOSO 배포 전체 흐름

실제 구축은 많은 사전 조건이 필요하지만, 큰 흐름은 아래 9단계로 정리할 수 있습니다.

요구사항·지원 매트릭스 확인
RHOSO 버전, 지원 RHOCP/RHEL/Ceph 조합, 하드웨어 인증, 구독, 용량을 확인합니다.
물리 네트워크·IP·DNS·NTP 설계
provisioning, ctlplane, internalapi, tenant, storage, external의 VLAN/MTU/라우팅을 계획합니다.
RHOCP 클러스터 준비
RHOSO Control Plane을 호스팅할 사전 구축된 OpenShift 클러스터와 스토리지, LoadBalancer, DNS를 준비합니다.
OpenStack Operator 설치
OperatorHub/OLM을 통해 OpenStack Operator를 설치하고 필요한 namespace와 Secret을 준비합니다.
NetConfig 생성
데이터 플레인 네트워크의 이름, VLAN, CIDR, IP 풀, DNS 도메인을 선언합니다.
OpenStackControlPlane 생성
Keystone, Nova, Neutron, Glance, Cinder API, DB, RabbitMQ 등 Control Plane 서비스를 생성합니다.
OpenStackDataPlaneNodeSet 생성
Compute 등 RHEL 노드의 IP, SSH, 네트워크, 역할, 적용할 서비스를 정의합니다.
OpenStackDataPlaneDeployment 실행
Operator가 Ansible 실행 환경을 이용해 RHEL 노드를 구성하고 Control Plane과 연결합니다.
검증 및 사용자 자원 준비
서비스·하이퍼바이저·네트워크·스토리지 상태 확인 후 Project, Image, Flavor, Network를 만들고 테스트 VM을 생성합니다.

배포 시뮬레이터

실제 구축에서 네트워크가 가장 먼저인 이유Control Plane Pod가 정상이어도 RHEL Data Plane과 ctlplane/internalapi/storage 경로가 맞지 않으면 Ansible, API, VM 네트워크, 스토리지 연결이 연쇄적으로 실패합니다.
CHAPTER 11

핵심 YAML을 읽는 법

아래 예시는 구조 이해를 위한 개념용 축약 예시입니다. 실제 운영 배포 파일로 그대로 사용하지 말고 공식 문서와 환경별 값에 맞춰 작성해야 합니다.

1) OpenStackControlPlane — 관리 서비스 주문서

개념용 YAML
apiVersion: core.openstack.org/v1beta1
kind: OpenStackControlPlane
metadata:
  name: openstack
  namespace: openstack
spec:
  secret: osp-secret
  storageClass: your-storage-class
  keystone:
    enabled: true
  nova:
    enabled: true
  neutron:
    enabled: true
  glance:
    enabled: true
  cinder:
    enabled: true

읽는 법: “openstack namespace에 openstack이라는 Control Plane을 만들고, 공통 Secret과 StorageClass를 사용하며 주요 서비스를 활성화하라.”

2) OpenStackDataPlaneNodeSet — 비슷한 서버 그룹

개념용 YAML
apiVersion: dataplane.openstack.org/v1beta1
kind: OpenStackDataPlaneNodeSet
metadata:
  name: compute-set-a
  namespace: openstack
spec:
  env:
    - name: ANSIBLE_FORCE_COLOR
      value: "True"
  nodes:
    edpm-compute-0:
      hostName: compute-0.example.com
      ansible:
        ansibleHost: 192.0.2.10
    edpm-compute-1:
      hostName: compute-1.example.com
      ansible:
        ansibleHost: 192.0.2.11
  services:
    - bootstrap
    - download-cache
    - configure-network
    - validate-network
    - install-os
    - configure-os
    - run-os

읽는 법: “compute-set-a라는 그룹에 Compute 두 대가 있고, 이 순서의 서비스 작업을 적용하라.”

3) OpenStackDataPlaneDeployment — 실제 작업 시작

개념용 YAML
apiVersion: dataplane.openstack.org/v1beta1
kind: OpenStackDataPlaneDeployment
metadata:
  name: deploy-compute-set-a
  namespace: openstack
spec:
  nodeSets:
    - compute-set-a

읽는 법: “compute-set-a NodeSet에 정의된 구성을 지금 실행하라.”

YAML 검토 포인트apiVersion과 필드는 설치된 Operator 버전에 따라 달라질 수 있습니다. 샘플을 복사하기 전에 반드시 해당 RHOSO 릴리스의 CRD와 공식 예제를 확인하십시오.

CHAPTER 14

VM 생성 버튼을 누르면 내부에서는?

1. 인증
사용자가 Keystone에서 Token을 받고, Project와 Role 권한이 확인됩니다.
2. Nova API 요청
Image, Flavor, Network, Key Pair, Security Group 정보와 함께 VM 생성 요청이 들어갑니다.
3. 자원 후보 찾기
Placement가 CPU·RAM·장치 재고를 제공하고 Nova Scheduler가 정책과 가용 자원을 비교합니다.
4. 네트워크 Port 생성
Neutron이 VM NIC용 Port, IP, Security Group 정책을 준비합니다.
5. 이미지/볼륨 준비
Glance에서 부팅 이미지를 가져오거나 Cinder 부팅 볼륨을 준비합니다.
6. Compute 노드 실행
선택된 RHEL Compute에서 nova-compute가 libvirt/KVM을 통해 VM을 생성합니다.
7. 네트워크 연결
OVN/OVS가 Port와 가상 네트워크 흐름을 구성하고 DHCP·라우팅·ACL이 적용됩니다.
8. 상태 보고
VM 상태가 BUILD에서 ACTIVE로 바뀌며 API와 Dashboard에 표시됩니다.

FAQ: Pod가 Running이면 서비스가 정상 아닌가요?

아닙니다. 프로세스가 살아 있어도 DB 인증 실패, 메시지 큐 연결 실패, 잘못된 Endpoint, TLS 오류로 API 기능이 실패할 수 있습니다. Pod 상태와 실제 API 기능 테스트를 함께 해야 합니다.

FAQ: OpenStack CLI가 되면 Data Plane도 정상인가요?

아닙니다. Keystone과 API가 정상이라는 뜻에 가깝습니다. Compute, Network, Storage 기능은 별도 검증해야 합니다.

왕초보 실습 시나리오

목표: “웹 서버 VM 2대 + 데이터 볼륨 + 외부 접속”을 만들고, 장애 하나를 직접 찾아봅니다.

실습 토폴로지

외부 사용자→Floating IP→lab-router→lab-net→web01 / web02→Cinder Volume

Lab A — 정상 구성

  1. Project/User/Role 생성
  2. Image와 Flavor 준비
  3. Network/Subnet/Router 생성
  4. Key Pair와 Security Group 생성
  5. VM 2대 생성
  6. Floating IP 할당
  7. Cinder Volume 생성 및 연결
  8. nginx 설치 후 HTTP 접속

Lab B — 장애 주입

  1. 80/tcp Security Group 규칙 삭제
  2. 외부 HTTP 접속 실패 확인
  3. VM 상태, Floating IP, Port 상태 확인
  4. Security Group 규칙 비교
  5. 80/tcp 규칙 복구
  6. 접속 재검증 및 장애 보고서 작성

볼륨 실습 명령

Cinder Volume
openstack volume create --size 10 web-data
openstack server add volume web01 web-data
openstack volume show web-data
openstack server show web01

실습 완료 조건

  • 왜 Image와 Flavor가 필요한지 설명할 수 있다.
  • Fixed IP와 Floating IP의 차이를 설명할 수 있다.
  • Security Group과 물리 방화벽의 위치 차이를 설명할 수 있다.
  • VM 생성 실패 시 Control Plane과 Data Plane을 나눠 점검한다.
  • NodeSet과 DataPlaneDeployment의 역할 차이를 말할 수 있다.

CHAPTER 22

검색 가능한 용어 사전

Availability Zone
사용자가 워크로드 위치를 선택할 수 있게 하는 논리적 가용 영역.
Cell
Nova를 확장하기 위해 Compute와 DB/메시징 영역을 나누는 단위.
Cloud-init
VM 첫 부팅 시 SSH Key, 사용자, 스크립트 등을 적용하는 초기화 도구.
CR
Custom Resource. Operator에게 원하는 상태를 전달하는 실제 Kubernetes 자원.
CRD
Custom Resource Definition. Kubernetes에 새로운 자원 종류를 정의.
Data Plane
실제 VM·패킷·스토리지 I/O를 처리하는 외부 RHEL 노드 영역.
Endpoint
OpenStack 서비스 API에 접속하는 URL과 인터페이스 정보.
Flavor
VM의 vCPU, RAM, 기본 디스크 규격.
Floating IP
외부에서 접근하도록 VM Fixed IP에 연결하는 이동 가능한 IP.
Image
VM을 부팅하는 OS 템플릿.
NodeSet
같은 유형·구성·역할의 Data Plane 노드를 묶은 CR.
OpenStackControlPlane
RHOSO Control Plane 전체 서비스 구성을 선언하는 대표 CR.
OpenStackDataPlaneDeployment
NodeSet에 정의된 Ansible 기반 구성을 실제 실행하는 CR.
Operator
소프트웨어 운영 지식을 코드로 구현한 Kubernetes 자동 관리자.
OVN
논리 네트워크, 라우팅, ACL 등의 제어 상태를 관리하는 SDN 구성요소.
OVS
각 노드에서 실제 패킷을 전달하는 소프트웨어 가상 스위치.
Placement
Compute 자원 재고와 할당을 추적하는 서비스.
Port
Neutron 네트워크에 연결되는 논리 NIC 접점.
Project
사용자, 권한, Quota, VM/네트워크/볼륨을 분리하는 자원 경계.
Provider Network
물리 VLAN/Flat 네트워크와 직접 매핑되는 OpenStack 네트워크.
Reconciliation
Operator가 원하는 상태와 실제 상태를 비교해 지속적으로 맞추는 과정.
Security Group
VM Port에 적용되는 상태 기반 가상 방화벽 규칙 집합.
SRBAC
Scope와 Role을 바탕으로 세분화한 OpenStack 보안 권한 모델.
Tenant Network
프로젝트별 격리된 가상 네트워크. Overlay 기술을 사용할 수 있음.
Token
Keystone 인증 후 API 요청에 사용하는 제한된 수명의 증표.
Volume
VM과 독립적으로 유지할 수 있는 Cinder 블록 디스크.
