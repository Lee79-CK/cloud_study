이번 편에서 얻을 것

1편 노선도의 세 번째 정거장이자, 다른 정거장들을 잇는 선로입니다. 이번 편과 다음 편 두 번에 걸쳐 Kubeflow Pipelines(KFP)를 다룹니다. 이번 편은 개념과 구조, 다음 편은 실전 작성 패턴입니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 컴포넌트, 파이프라인, 실행, 실험, 아티팩트, 파라미터의 관계를 설명할 수 있습니다.
  • 세 종류의 컴포넌트를 구별하고, 값을 파라미터로 넘길지 아티팩트로 넘길지 판단할 수 있습니다.
  • 4편의 노트북 실습을 세 단계 파이프라인으로 바꾸고, 컴파일해 노트북에서 제출할 수 있습니다.
  • 제출한 파이프라인이 IR YAML, Argo Workflow, Pod로 바뀌는 과정과 캐시가 동작하는 원리를 알고, 실패했을 때 어디를 볼지 압니다.

1왜 파이프라인인가

4편의 노트북은 잘 돌아갔습니다. 그런데 매주 새 데이터로 다시 학습해야 한다면 어떨까요? 누군가 노트북을 열어 셀을 순서대로 눌러야 하고, 지난주와 이번 주에 무엇이 달랐는지는 기억에 의존합니다. 1편의 지은이 겪은 재현성과 추적의 문제가 그대로 돌아옵니다. 파이프라인은 노트북의 셀 묶음을 이름 있는 단계로 나누고, 단계 사이에 무엇이 오가는지 명시해, 사람 없이도 똑같이 반복 실행되게 만든 것입니다.

구분노트북 셀파이프라인 단계
실행 환경노트북 하나의 커널. 모든 셀이 같은 환경단계마다 독립된 컨테이너. 단계마다 다른 이미지와 자원 가능
단계 사이의 데이터메모리의 변수. 순서가 바뀌면 결과도 바뀜명시된 입력과 출력. 자동으로 저장소를 거쳐 전달
기록사람이 남기지 않으면 없음실행마다 입력, 출력, 로그, 아티팩트가 자동 기록
반복 실행사람이 셀을 다시 눌러야 함버튼 하나, API 한 번, 또는 예약 실행
같은 계산의 반복매번 다시 계산입력이 같으면 캐시된 결과를 재사용
병렬셀은 순서대로서로 의존하지 않는 단계는 동시에 실행

2핵심 개념

KFP의 화면과 API에 나오는 개념들입니다. 이름을 누르면 정의와 비유, 대시보드에서 보이는 곳이 나옵니다. 공장 비유로 통일했습니다.

Experiment가 두 개입니다

KFP의 Experiment는 실행(Run)을 묶는 폴더이고, 8편에서 다룰 Katib의 Experiment는 하이퍼파라미터 튜닝 작업 하나입니다. 이름만 같고 전혀 다른 것이라, 대시보드 메뉴에서도 따로 나옵니다.

3컴포넌트 세 종류

컴포넌트는 파이프라인의 한 단계이고, 실행되면 컨테이너 하나가 됩니다. 만드는 방법이 세 가지 있습니다. 탭을 눌러 비교하세요.

4파라미터와 아티팩트

단계 사이에 오가는 값은 두 종류입니다. 파라미터는 숫자, 문자열, 불리언, 작은 리스트나 딕셔너리처럼 작은 값이고, 메타데이터 DB에 직접 저장됩니다. 아티팩트는 데이터셋, 모델, 리포트처럼 파일로 다루는 큰 결과물이고, 오브젝트 스토리지(26.03부터 SeaweedFS)에 저장되며 메타데이터 DB에는 그 위치와 정보만 기록됩니다.

구분파라미터아티팩트
함수에서 쓰는 법lr: float처럼 일반 타입. 반환값 -> float도 출력 파라미터Input[Dataset], Output[Model]처럼 감싼 타입. .path로 파일을 읽고 씀
저장 위치메타데이터 DB오브젝트 스토리지, DB에는 위치(URI)와 메타데이터
크기작아야 함큰 파일도 가능
계보 추적값만 남음어떤 실행이 만들고 어디에 쓰였는지 연결됨
대표 타입str, int, float, bool, list, dictDataset, Model, Metrics, ClassificationMetrics, HTML, Markdown, Artifact

판단해 봅시다. 각 값을 파라미터와 아티팩트 중 어디로 넘기는 게 좋을까요?

5실습 코드 한 줄씩

4편의 노트북을 세 단계로 나눕니다. 데이터를 불러와 나누는 load_data, 모델을 학습하는 train, 정확도를 재는 evaluate입니다. 표시가 있는 줄을 누르면 오른쪽에 설명이 나옵니다. 4편의 노트북에서 새 노트북 파일을 만들어 그대로 입력하면 됩니다(노트북을 만들 때 Pipelines 접근 허용 설정을 켜 두세요).


    

  

  

    가장 중요한 한 가지: 파이프라인 함수 안은 실행이 아니라 설계입니다
    
digits_pipeline 안에서 load_data(...)를 부르면 데이터가 불러와지지 않습니다. 대신 “이런 단계가 있다”는 작업(PipelineTask)이 그래프에 추가되고, 그 작업의 출력을 다음 작업의 입력으로 넘기는 순간 둘 사이에 화살표가 그려집니다. 그래서 파이프라인 함수 안에서는 if, for, print 같은 일반 Python 코드가 생각대로 동작하지 않습니다. 조건과 반복은 KFP 전용 문법으로 써야 하며, 6편에서 다룹니다.

  

  

    packages_to_install은 실행할 때마다 인터넷에서 설치합니다
    
편리하지만 단계가 시작될 때마다 pip 설치가 일어나 느리고, 인터넷이 막힌 폐쇄망에서는 실패합니다. 실습에서는 괜찮지만, 실무에서는 필요한 패키지를 미리 넣은 이미지를 base_image로 지정하는 컨테이너형 컴포넌트가 낫습니다(3장 두 번째 탭).

  






  
6컴파일과 제출

  
방법 1: 컴파일해서 화면으로 올리기

  
코드 맨 끝 줄의 컴파일러가 digits_pipeline.yaml을 만듭니다. 이 파일을 내려받아 대시보드의 Pipelines 화면에서 Upload pipeline으로 올리고, Create run으로 실행합니다. 실행할 때 파이프라인 함수의 인자(test_size, n_estimators)를 입력하는 칸이 나옵니다.

  
방법 2: 노트북에서 바로 제출하기

  
노트북에 Pipelines 접근 허용(PodDefault access-ml-pipeline)이 켜져 있으면, 주소와 인증 토큰을 따로 주지 않아도 kfp.Client()가 클러스터 안의 Pipelines API를 찾아갑니다. 다중 사용자 환경이므로 실행을 만들 네임스페이스는 꼭 지정합니다.

  
import kfp

client = kfp.Client()      # 노트북 안: 주소와 토큰은 PodDefault가 마련
run = client.create_run_from_pipeline_package(
    "digits_pipeline.yaml",
    arguments={"n_estimators": 300},     # 기본값을 바꿀 인자만
    run_name="rf-300",
    experiment_name="digits",             # 없으면 새로 만듦
    namespace="kubeflow-user-example-com",
)
print(run.run_id)

  
컴파일 파일 없이 함수를 바로 넘기는 create_run_from_pipeline_func도 있습니다. 다만 무엇이 실행되었는지 파일로 남기려면 컴파일한 YAML을 Git에 함께 두는 습관이 좋습니다.

  
제출한 뒤 확인하기

  
대시보드의 Runs 화면에서 방금 만든 rf-300 실행을 엽니다. 세 단계가 그래프로 보이고, 각 상자를 누르면 입력과 출력, 로그, 아티팩트를 볼 수 있습니다. evaluate 단계의 Visualizations나 출력 아티팩트에서 accuracy 지표가 보이면 성공입니다. 같은 실험 안의 여러 실행을 골라 Compare runs를 누르면 지표를 나란히 비교할 수 있습니다.

  

    클러스터 밖에서 제출하려면
    
내 PC에서 제출하려면 3편의 포트 포워딩 주소(http://localhost:8080/pipeline)와 서비스 계정 토큰을 kfp.Client(host=..., existing_token=...)로 넘기는 방식이 있습니다. 다만 이것은 서비스 계정 토큰을 게이트웨이 밖에서 받아 주도록 oauth2-proxy를 구성했을 때만 동작합니다(3편에서 소개한 설치 옵션). 실습에서는 노트북에서 제출하는 방식이 가장 간단합니다.

  






  
7IR YAML 읽기

  
컴파일 결과는 KFP의 중간 표현(IR, Intermediate Representation)이라는 YAML입니다. Python 코드를 몰라도 이 파일만 있으면 파이프라인을 실행할 수 있고, 특정 실행 엔진에 묶이지 않은 형식이라 같은 파일을 다른 KFP 호환 실행 환경(예: Google Vertex AI Pipelines)에서도 쓸 수 있습니다. 실습 결과를 단순화한 모습입니다.


pipelineInfo:
  name: digits-training
root:
  inputDefinitions:                        # 파이프라인 인자와 기본값
    parameters:
      n_estimators: {parameterType: NUMBER_INTEGER, defaultValue: 200}
      test_size: {parameterType: NUMBER_DOUBLE, defaultValue: 0.2}
  dag:
    tasks:
      train:
        dependentTasks: [load-data]           # 데이터 전달에서 자동으로 추론된 순서
        inputs:
          artifacts:
            train_data:
              taskOutputArtifact: {producerTask: load-data, outputArtifactKey: train_data}
components:
  comp-train:
    outputDefinitions:
      artifacts:
        model: {artifactType: {schemaTitle: system.Model}}
deploymentSpec:
  executors:
    exec-train:
      container:
        image: python:3.11                    # 실제 파일에는 실행 명령과 함수 코드도 들어 있음
        resources:                           # set_cpu_limit, set_memory_limit의 결과
          resourceCpuLimit: '2'               # SDK 버전에 따라 표기가 조금 다를 수 있음
          resourceMemoryLimit: 2G

  
    
    
  • root.dag.tasks는 그래프입니다. 어느 작업이 어느 작업의 출력을 받는지가 여기 적힙니다.
    • 
    
  • components는 각 단계의 입출력 정의, deploymentSpec은 각 단계를 어떤 이미지와 명령으로 실행할지입니다.
    • 
    
  • lightweight 컴포넌트의 함수 코드는 deploymentSpec의 실행 명령 안에 문자열로 통째로 들어갑니다. 그래서 컴포넌트 함수 안에서 바깥의 import나 변수를 쓰면 실행할 때 찾지 못합니다. 실습 코드에서 import를 함수 안에 둔 이유입니다.
    • 
  






  
8실행 뒤에서 일어나는 일

  
실행을 제출하면 API 서버가 IR을 Argo Workflow라는 Kubernetes 리소스로 바꿔 내 네임스페이스에 만들고, Argo가 단계마다 Pod를 띄웁니다. 단계 하나가 실행되는 과정을 따라가 보세요.

  

    

      
KFP API 서버kubeflow

      
Argo 컨트롤러Workflow 실행

      
driver입력 확정, 캐시 확인

      
executor Podlauncher와 내 코드

      
SeaweedFS아티팩트 파일

      
메타데이터 DBMLMD

    

    

    

  

  
# 실행 하나는 Argo Workflow 하나
kubectl get workflows -n kubeflow-user-example-com

# 그 Workflow가 만든 Pod들. 이름에 driver나 impl이 들어간 Pod가 보입니다
kubectl get pods -n kubeflow-user-example-com | grep digits-training

# 내 함수의 출력은 executor Pod의 main 컨테이너 로그에
kubectl logs <executor-pod-이름> -n kubeflow-user-example-com -c main

  

    2편의 지식이 그대로 쓰입니다
    
단계가 시작되지 않으면 Pod가 Pending인지, 이미지를 못 받는지, OOMKilled인지 2편의 방법대로 봅니다. 파이프라인은 결국 Pod들의 묶음이고, 할당량과 자원 요청, 노드 선택도 똑같이 적용됩니다.

  






  
9캐시

  
KFP는 단계를 실행하기 전에, 같은 컴포넌트 정의와 같은 입력으로 성공한 기록이 있는지 확인합니다. 있으면 실행을 건너뛰고 그때의 출력을 그대로 씁니다. 캐시는 기본으로 켜져 있습니다. 직전 실행이 test_size 0.2, n_estimators 200이었다고 하고, 조건을 바꿔 보세요.

  

    

      

      

      
      
    

    

    

  

  
    
    
  • 캐시는 입력 값뿐 아니라 컴포넌트 정의(이미지, 명령, 함수 코드)까지 봅니다. 코드를 고치면 그 단계부터 다시 실행됩니다.
    • 
    
  • 앞 단계가 다시 실행되면 새 아티팩트가 만들어지므로, 그것을 받는 뒤 단계도 입력이 달라져 다시 실행됩니다.
    • 
    
  • 현재 시각이나 외부 데이터베이스처럼 입력에 드러나지 않는 것을 읽는 단계는 캐시가 잘못된 결과를 돌려줄 수 있습니다. 이런 단계는 task.set_caching_options(False)로 캐시를 끄고, 실행 전체는 제출할 때 enable_caching=False로 끌 수 있습니다.
    • 
  






  
10로컬에서 먼저 돌려 보기

  
오타 하나 고치려고 매번 클러스터에 제출하면 느립니다. KFP SDK에는 컴포넌트와 파이프라인을 내 PC나 노트북 안에서 바로 실행해 보는 로컬 실행 기능이 있습니다. SubprocessRunner는 컨테이너 없이 현재 Python 환경(기본으로는 임시 가상 환경)에서, DockerRunner는 로컬 Docker에서 실행합니다.


from kfp import local
local.init(runner=local.SubprocessRunner())

# 파이프라인 함수를 그냥 부르면 로컬에서 실행됩니다
result = digits_pipeline(n_estimators=50)

# 컴포넌트 하나만 시험할 수도 있습니다

14정리와 다음 편

  
    
    
  1. 컴포넌트는 컨테이너 하나로 실행되는 단계이고, 파이프라인은 컴포넌트를 입출력으로 이은 그래프입니다. 실행(Run)은 실험(Experiment)으로 묶입니다.
    2. 
    
  2. 작은 값은 파라미터, 파일로 다룰 결과물은 아티팩트입니다. 아티팩트는 .path로 읽고 쓰며, 오브젝트 스토리지에 저장되고 계보가 남습니다.
    3. 
    
  3. 파이프라인 함수 안은 실행이 아니라 설계입니다. 컴포넌트 호출은 그래프에 작업을 추가하고, 출력 연결이 실행 순서를 정합니다.
    4. 
    
  4. Python 코드는 플랫폼 중립적인 IR YAML로 컴파일되고, API 서버가 이를 Argo Workflow로 바꿔 단계마다 driver와 executor Pod를 띄웁니다.
    5. 
    
  5. 같은 컴포넌트 정의와 같은 입력이면 캐시가 결과를 재사용합니다. 입력에 드러나지 않는 것을 읽는 단계는 캐시를 끕니다.
    6. 
  

    
현장에서 쓰이는 장면

  
  • 제조. 매주 신제품 이미지가 쌓이면 같은 파이프라인을 다시 실행해 모델을 갱신하고, 실행 기록이 “언제 어떤 데이터로 만들었나”의 답이 됩니다.
  • 금융. 감사 요청에 파이프라인 실행 ID와 아티팩트 계보를 그대로 제출합니다.
  • 스타트업. 노트북 셀 80개를 세 단계 파이프라인으로 나눈 것만으로 새 팀원이 하루 만에 학습을 재현합니다.
