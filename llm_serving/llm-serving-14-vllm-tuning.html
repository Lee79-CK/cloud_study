vLLM 파라미터
튜닝 실전

Level 2에서 플랫폼을 세웠습니다. 이제 엔진 하나를 끝까지 짜냅니다. 튜닝의 목표는 “처리량 최대”가 아니라 3편의 SLO를 지키면서 처리할 수 있는 양(Goodput)을 최대로 만드는 것입니다. 메모리 비율·최대 길이·KV 정밀도로 KV 공간을 정하고, 동시 실행 상한으로 TPOT를, 토큰 예산으로 TTFT와 ITL의 균형을, 최적화 레벨로 스텝 오버헤드를 다룹니다. 한 번에 하나씩, 측정으로.

01시작하기 전에

튜닝은 감이 아니라 실험입니다. 목표 함수, 고정할 것, 바꿀 것, 잴 것을 먼저 정합니다.

튜닝의 네 가지 원칙

  1. 목표는 SLO 하의 Goodput: 3편에서 정의한 “TTFT p95·TPOT p95 목표를 지킨 요청만 센 처리량”을 최대로 만듭니다. 처리량만 올리면 대개 지연이 무너지고, 지연만 낮추면 GPU가 놉니다.
  2. 워크로드를 고정: 입력·출력 길이 분포, 도착 패턴, 공통 프롬프트 비율을 실제 서비스와 비슷하게 정하고 실험 내내 바꾸지 않습니다. 워크로드가 바뀌면 최적 설정도 바뀝니다.
  3. 한 번에 하나: 두 개를 동시에 바꾸면 어느 쪽 효과인지 모릅니다. 바꾼 값과 결과를 7편 스냅샷처럼 모두 기록합니다.
  4. 기본값을 존중: vLLM 기본값은 많은 경우 이미 좋은 출발점입니다. 기본값보다 나은지 측정으로 증명된 것만 바꿉니다.

학습 목표

  1. 주요 파라미터가 어떤 지표를 어떤 메커니즘으로 움직이는지 지도를 그릴 수 있다.
  2. 메모리 비율·최대 길이·KV 정밀도로 KV 공간과 최대 동시성을 계산하고 조정할 수 있다.
  3. 동시 실행 상한을 KV 공간과 TPOT SLO라는 두 한계로 정할 수 있다.
  4. 토큰 예산(Chunked Prefill)과 긴 Prefill 제어 옵션으로 TTFT와 ITL의 균형을 맞출 수 있다.
  5. 최적화 레벨·CUDA 그래프 크기·비동기 스케줄링의 효과를 측정할 수 있다.
  6. 스윕 스크립트로 설정을 체계적으로 바꿔 가며 SLO 하 최대 처리량을 찾고, 근거와 함께 기본 설정을 갱신할 수 있다.
이 편의 비유: 오디오 믹서

튜닝은 믹서의 여러 노브를 한 번에 하나씩 돌리며 소리(지표)를 듣는 일입니다. 볼륨(동시 실행 상한)을 올리면 소리는 커지지만(처리량) 어느 순간 찢어지고(TPOT 위반), 저음(토큰 예산)을 키우면 묵직해지지만(TTFT 단축) 다른 소리를 덮습니다(ITL 튐). 그리고 공연장(워크로드)이 바뀌면 같은 설정이 다르게 들립니다.

03튜닝 절차 7단계

순서가 중요합니다. 앞 단계가 뒤 단계의 한계를 정하기 때문입니다.

  1. 목표와 워크로드 정의SLO(예: TTFT p95 ≤ 2초, TPOT p95 ≤ 60ms), 입력·출력 길이 분포, 공통 프롬프트 비율, 목표 도착률. 서비스 로그(12편 게이트웨이 사용량)에서 가져옵니다.
  2. 기준선현재 설정으로 3편 방식의 열린 루프 스윕을 돌려 “SLO를 지키는 최대 도착률(SLO 용량)”을 잽니다. 이후 모든 변경은 이 숫자와 비교합니다.
  3. 메모리 (KV 공간)정밀도(6편)·KV 정밀도·최대 길이·메모리 비율로 KV 토큰 수를 정합니다. 동시성의 천장이 여기서 정해집니다.
  4. 동시 실행 상한KV 천장과 TPOT SLO 중 낮은 쪽에 맞춥니다(5장, 히어로 계산기).
  5. 토큰 예산과 긴 Prefill입력이 긴 요청이 섞인 워크로드에서 TTFT와 ITL p99의 균형을 맞춥니다(6장).
  6. 실행 최적화최적화 레벨, CUDA 그래프 캡처 크기, 비동기 스케줄링, API 서버 수(7장).
  7. 검증과 기록긴 시간(30분 이상) 혼합 부하, 품질 회귀(6편 quick_eval), 기동 시간(13편) 확인 후 기본 오버레이를 갱신하고 근거를 남깁니다.

04메모리: 비율·길이·KV 정밀도

KV 공간은 동시성의 천장입니다. 2편의 공식을 튜닝 노브와 연결합니다.

KV 공간(GB) ≈ GPU 메모리 × gpu-memory-utilization − 가중치 − 활성값·런타임 여유 KV 토큰 수 = KV 공간 ÷ 토큰당 KV 크기 (2편: 층 × KV 헤드 × 헤드 차원 × 2 × 바이트) 최대 동시성 ≈ KV 토큰 수 ÷ 요청당 평균 문맥 (입력 + 출력)
  • gpu-memory-utilization: 전용 GPU라면 0.9 안팎이 기본입니다. GB10처럼 메모리를 CPU·다른 프로세스와 공유하면 8편 메모리 예산으로 정합니다(랩은 RAG 플랫폼과 공존을 위해 0.35). 올릴수록 KV가 늘지만 OS·다른 프로세스 몫이 줄어듭니다.
  • max-model-len: 서비스가 실제로 쓰는 최대 문맥보다 크게 잡을 이유가 없습니다. 크게 잡으면 기동 시 프로파일링이 더 큰 활성값을 예약하고, 긴 요청 하나가 KV를 독식할 수 있습니다. 게이트웨이(12편)에서 입력 길이 상한을 함께 걸어 두세요.
  • KV 정밀도 fp8: KV 공간이 두 배가 되어 동시성·프리픽스 캐시가 늘어납니다. 대부분의 모델에서 품질 손실이 작지만, 긴 문맥·추론 작업은 6편 방식으로 확인합니다.
  • 가중치 정밀도(6편): BF16 → FP8이면 가중치가 절반이 되어 같은 비율에서 KV 공간이 그만큼 늘어납니다. 8B 모델 기준 약 8GB가 KV로 돌아옵니다.
로그로 확인

vLLM은 기동 시 KV 캐시 토큰 수와 “최대 문맥 길이 기준 최대 동시성”을 로그에 찍습니다(4편 실습). 메모리 관련 설정을 바꿀 때마다 이 두 숫자를 기록하면, 계산과 실제가 맞는지 바로 확인할 수 있습니다.

05동시 실행 상한

--max-num-seqs는 “동시에 몇 명의 토큰을 함께 구울지”입니다. 너무 낮아도, 너무 높아도 Goodput이 떨어집니다.

설정무슨 일이 생기나증상
너무 낮음GPU가 더 함께 처리할 수 있는데 대기열에서 기다림TPOT는 좋은데 TTFT(대기 시간)가 길고 처리량이 낮음, GPU 대역폭 여유
적정KV 공간과 TPOT SLO 안에서 최대한 함께 처리TPOT가 SLO 근처, 대기열 짧음, 선점 거의 없음
너무 높음 (KV 쪽)KV 블록이 모자라 실행 중 요청을 선점 → 다시 계산(4편)선점 카운터 증가, 처리량 정체, 꼬리 지연 급증
너무 높음 (TPOT 쪽)배치가 커져 한 스텝이 길어짐 (2편 루프라인)처리량은 늘지만 TPOT가 SLO 초과 → Goodput 하락

그래서 출발점은 max-num-seqs ≈ min(KV 공간 한계, TPOT SLO 한계)입니다. 히어로 계산기가 이 두 한계를 보여 줍니다. 그다음 실측(실습 14-4)으로 미세 조정합니다. TPOT 한계 쪽이 묶여 있다면 상한을 올려도 Goodput이 늘지 않으므로, 더 빠른 GPU·양자화·추측 디코딩(16편)·레플리카 추가(18편)를 검토합니다. KV 쪽이 묶여 있다면 4장의 메모리 노브가 답입니다.

상한을 낮추는 것도 정책이다

max-num-seqs를 낮추면 넘치는 요청은 엔진 대기열에서 기다립니다. 대기열이 길어지면 TTFT SLO가 무너지므로, 대기열 길이를 지표로 보고 레플리카를 늘리거나(18편), 게이트웨이·흐름 제어(11·12편)에서 우선순위대로 받도록 합니다. “엔진이 받을 수 있는 만큼만 받고 나머지는 앞단에서 관리”가 원칙입니다.

06토큰 예산과 긴 Prefill

긴 입력이 섞인 워크로드에서 가장 효과가 큰 노브. 긴 요청의 TTFT와 진행 중 요청의 ITL을 맞바꿉니다.

토큰 예산 맞교환 계산기

Decode 중인 요청 b개가 있는 엔진에 긴 입력 요청 하나가 들어올 때, 토큰 예산(--max-num-batched-tokens)에 따라 그 요청의 Prefill 완료 시간(대략 TTFT)과 진행 중 요청이 겪는 가장 긴 토큰 간격(ITL 꼬리)이 어떻게 바뀌는지 봅니다. 2편의 단순 모델입니다.
긴 요청 Prefill 완료 (초, 왼쪽 축)진행 중 요청 ITL 꼬리 (ms, 오른쪽 축)
긴 요청 Prefill 완료—
진행 중 요청 ITL 꼬리—
평상시 TPOT—

긴 Prefill을 다루는 보조 노브

  • 긴 Prefill 임계값(--long-prefill-token-threshold): 한 요청이 한 스텝에 가져갈 Prefill 토큰 상한. v0.31.0에서는 대기 중인 Prefill 수에 따라 적응하도록 바뀌었습니다(4편).
  • 부분 Prefill 동시 수(--max-num-partial-prefills, --max-long-partial-prefills): 여러 요청의 Prefill을 동시에 조각내 진행할지, 긴 요청은 몇 개까지 동시에 진행할지. 긴 요청 하나가 짧은 요청들을 줄 세우는 현상을 줄입니다(옵션 이름·지원 범위는 버전 문서 확인).
  • 근본 해결: 긴 입력 비중이 크고 ITL SLO가 엄격하면 P/D 분리(10편)를 검토합니다. 토큰 예산은 같은 GPU 안에서의 타협이고, P/D는 GPU를 나눠 간섭 자체를 없앱니다.

07실행 최적화

스텝 하나에 붙는 고정 오버헤드를 줄이는 노브들. 작은 모델·작은 배치에서 효과가 큽니다.

노브효과대가언제 만지나
-O 레벨 (기본 -O2)컴파일·CUDA 그래프로 커널 실행 오버헤드 제거기동 시간·약간의 메모리 (13편)기본값 유지가 원칙. -O0은 디버깅용

실습 14-1 · 워크로드와 SLO 정의

python · slo_probe.py (50-tools/scripts에 추가)
"""열린 루프 SLO 측정: 포아송 도착으로 duration초 동안 요청을 보내고 TTFT·TPOT·ITL 꼬리·Goodput을 기록한다.
사용: python slo_probe.py --label CFG --rate 2 [--duration 60] [--long-ratio 0.2]"""
import argparse, asyncio, json, random, time
from openai import AsyncOpenAI

ap = argparse.ArgumentParser()
ap.add_argument("--base", default="http://llm-engine:8000/v1"); ap.add_argument("--model", default="qwen3-8b")
ap.add_argument("--label", required=True); ap.add_argument("--rate", type=float, required=True)
ap.add_argument("--duration", type=float, default=60); ap.add_argument("--out", type=int, default=128)
ap.add_argument("--in-words", type=int, default=300); ap.add_argument("--long-ratio", type=float, default=0.0)
ap.add_argument("--long-words", type=int, default=6000)
ap.add_argument("--ttft-slo", type=float, default=3000); ap.add_argument("--tpot-slo", type=float, default=100)
ap.add_argument("--result", default="/results/sweep.jsonl")
a = ap.parse_args()
cli = AsyncOpenAI(base_url=a.base, api_key="EMPTY", timeout=600)
W = "노드 파드 쿼터 지연 처리량 메모리 대역폭 캐시 배치 스케줄러 게이트웨이 장애 알림 예산 토큰 모델".split()
rnd = random.Random(42)

async def one(i):
    n = a.long_words if rnd.random() < a.long_ratio else a.in_words
    text = " ".join(rnd.choice(W) for _ in range(n))
    t0 = time.perf_counter(); first = last = None; gaps = []; cnt = 0
    try:
        s = await cli.chat.completions.create(model=a.model, max_tokens=a.out, stream=True,
            messages=[{"role": "user", "content": f"[{i}] {text}\n위 메모를 요약해 줘. /no_think"}],
            extra_body={"ignore_eos": True})
        async for ev in s:
            if ev.choices and ev.choices[0].delta and ev.choices[0].delta.content:
                now = time.perf_counter()
                if first is None: first = now
                else: gaps.append(now - last)
                last = now; cnt += 1
    except Exception as e:
        return {"err": type(e).__name__}
    if first is None: return {"err": "no_tokens"}
    return {"ttft": (first - t0) * 1000, "tpot": (last - first) / max(cnt - 1, 1) * 1000,
            "itl_max": max(gaps) * 1000 if gaps else 0, "tok": cnt}

def pct(xs, p):
    xs = sorted(xs); return xs[min(len(xs) - 1, int(p * len(xs)))] if xs else float("nan")

async def main():
    tasks, t_end, i = [], time.perf_counter() + a.duration, 0
    while time.perf_counter() < t_end:
        tasks.append(asyncio.create_task(one(i))); i += 1
        await asyncio.sleep(rnd.expovariate(a.rate))
    t_send = time.perf_counter()
    rs = await asyncio.gather(*tasks); wall = time.perf_counter() - t_send + a.duration
    ok = [r for r in rs if "err" not in r]
    good = [r for r in ok if r["ttft"] <= a.ttft_slo and r["tpot"] <= a.tpot_slo]
    row = {"label": a.label, "rate": a.rate, "sent": len(rs), "errors": len(rs) - len(ok),
           "ttft_p50": pct([r["ttft"] for r in ok], .5), "ttft_p95": pct([r["ttft"] for r in ok], .95),
           "tpot_p50": pct([r["tpot"] for r in ok], .5), "tpot_p95": pct([r["tpot"] for r in ok], .95),
           "itl_p99": pct([r["itl_max"] for r in ok], .99), "out_tok_s": sum(r["tok"] for r in ok) / wall,
           "goodput_frac": len(good) / max(len(rs), 1), "goodput_rps": len(good) / a.duration}
    print(json.dumps(row, ensure_ascii=False))
    with open(a.result, "a") as f: f.write(json.dumps(row, ensure_ascii=False) + "\n")

asyncio.run(main())

14확인 퀴즈

9문제.

15정리와 체크리스트

핵심 여섯 문장.

  1. 튜닝의 목표는 SLO 하의 Goodput이고, 워크로드를 고정한 채 한 번에 하나씩 바꾼다.
  2. 순서: 메모리 → 동시 실행 상한 → 토큰 예산 → 실행 최적화 → 검증. 앞 단계가 뒤 단계의 한계를 정한다.
  3. KV 공간 = 메모리 비율·가중치 정밀도·KV 정밀도·최대 길이로 정해지는 동시성의 천장이다.
  4. max-num-seqs ≈ min(KV 한계, TPOT SLO 한계). TPOT 한계가 묶이면 더 많은 GPU·양자화·추측 디코딩이 답이다.
  5. 토큰 예산은 긴 요청 TTFT와 진행 중 요청 ITL의 맞교환이다. 근본 해결은 P/D 분리.
  6. 원인 지표(대기·KV 사용률·선점·CPU 스로틀링)를 결과 지표와 함께 보고, 최종안은 긴 시간·품질 회귀로 검증해 근거와 함께 승격한다.
