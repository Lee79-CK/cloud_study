Terraform & Ansible 강의 · Level 4 Ansible 심화·운영 · 19편 / 26편 · 시리즈 목차

비밀은 저장소에도, 화면에도, 로그에도 남지 않게 비밀과 권한 — Ansible Vault(파일·변수·vault-id), 출력 유출 차단, become 전략, SSH 키 수명 관리, HashiCorp Vault·AWS Secrets Manager·Azure Key Vault 연계

13~18편은 편의를 위해 몇 가지를 미뤄 두었습니다. 랩 DB 비밀번호는 인벤토리에 평문으로, 운영자 sudo는 비밀번호 없이, SSH 키는 한 번 만들고 그대로, RDS 마스터 비밀번호는 “권한이 있다고 치고” 조회했습니다. 이번 편은 그 빚을 갚습니다. 비밀을 저장할 때(Vault 암호화·외부 저장소), 쓸 때(no_log·diff), 권한을 올릴 때(become), 접속 수단을 관리할 때(SSH 키 교체)의 원칙을 모두 실제로 실행해 확인합니다. 특히 4장에서는 비밀이 출력으로 새는 경로 여섯 가지를 일부러 재현해, 비밀번호가 한 번의 실행에서 네 번 화면에 찍히는 것을 보여 줍니다.

저장

vault.yml 암호화, 환경별 vault-id, 외부 저장소(Vault·Secrets Manager·Key Vault)

사용

no_log, loop_control.label, diff: false — 출력·로그로 새지 않게

권한

become 비밀번호도 Vault로, SSH 키는 수명과 교체 절차를 갖고

  • Ansible Vault로 파일과 개별 값을 암호화하고, vars/vault 분리 패턴으로 무엇이 비밀인지 코드에서 드러나게 합니다.
  • vault-id로 환경별 키를 나누고, 비밀번호 파일·클라이언트 스크립트(CI)·rekey·커밋 전 검사를 운영합니다.

2Ansible Vault 기본

AES256으로 암호화한 파일 — 저장소에는 암호문만, 실행할 때만 복호화

ansible-vault create  vault.yml                 # 새 암호화 파일 (편집기가 열림)
ansible-vault encrypt vault.yml                 # 기존 평문 파일을 암호화
ansible-vault view    vault.yml                 # 내용 보기
ansible-vault edit    vault.yml                 # 복호화 → 편집 → 다시 암호화
ansible-vault decrypt vault.yml                 # 평문으로 되돌림 (거의 쓰지 않는다)
ansible-vault rekey   vault.yml                 # 비밀번호(키) 교체
ansible-vault encrypt_string --name 변수 '값'   # 값 하나만 암호화해 YAML에 넣기

3vault-id 운영

환경마다 다른 키, 사람과 CI가 다른 방법으로 키를 건넨다

원칙방법
환경별 키dev·stg·prd를 서로 다른 vault-id(키)로. 개발자는 dev 키만, prd 키는 운영 파이프라인과 소수만 (8편 계정 분리와 같은 생각)
키는 저장소 밖에~/.ansible-vault/lab.pass 권한 600, 저장소의 .gitignore와 무관한 위치
기본 키는 ansible.cfg에vault_identity_list = lab@~/.ansible-vault/lab.pass — 매번 --vault-id를 쓰지 않아도 된다
CI는 클라이언트 스크립트키를 파일로 두지 않고 CI 비밀 → 환경 변수 → 스크립트가 출력 (아래)
# 실측: 키 없이 17편 플레이북 실행 (vault.yml을 인벤토리가 읽는 순간 실패)
$ ansible-playbook playbooks/site_webdb.yml
[ERROR]: Attempting to decrypt but no vault secrets found.

# 여러 키를 한 번에 — 파일과 클라이언트 스크립트 혼용 (실측)
$ ANSIBLE_VAULT_PASS_PRD="…" ansible-playbook playbooks/vault_ids.yml \
    --vault-id lab@~/.ansible-vault/lab.pass --vault-id prd@tools/vault-env-client
    msg: lab=23자, prd=30자                     ← 값 자체는 출력하지 않는다

# prd 키 없이 (실측) — 문자열 암호화 값은 "쓸 때" 실패
[ERROR]: … Attempt to use undecryptable variable: Decryption failed (no vault secrets were found that could decrypt).
tools/vault-env-client (CI용 비밀번호 클라이언트)
#!/usr/bin/env bash
# Vault 비밀번호 클라이언트: --vault-id 이름에 맞는 환경 변수에서 비밀번호를 읽는다 (CI용)
#   ansible-playbook --vault-id prd@tools/vault-env-client.sh …
#   → ANSIBLE_VAULT_PASS_PRD 의 값을 출력
# 파일 이름이 -client 로 끝나야(확장자 제외) Ansible이 --vault-id 인자를 넘겨준다
set -euo pipefail
id=""
while [[ $# -gt 0 ]]; do
  case "$1" in
    --vault-id) id="$2"; shift 2 ;;
    *) shift ;;
  esac
done
var="ANSIBLE_VAULT_PASS_$(echo "${id:-default}" | tr '[:lower:]-' '[:upper:]_')"
if [[ -z "${!var:-}" ]]; then
  echo "환경 변수 ${var} 가 없습니다" >&2
  exit 1
fi
printf '%s\n' "${!var}"

파일 이름이 -client로 끝나면(확장자 제외) Ansible이 --vault-id 이름 인자를 넘겨 주므로, 스크립트 하나로 여러 환경 키를 처리할 수 있습니다. 이름이 다르면 인자 없이 호출되어 어느 키인지 알 수 없습니다.

# 실측: 키 교체 (퇴사자·유출 의심 시) — 복사본으로 시험
$ ansible-vault rekey --vault-id lab@~/.ansible-vault/lab.pass --new-vault-id lab@/tmp/lab-new.pass /tmp/rk.yml
Rekey successful
$ ansible-vault view --vault-id lab@~/.ansible-vault/lab.pass /tmp/rk.yml
[ERROR]: Failed to view '/tmp/rk.yml': Decryption failed (no vault secrets were found that could decrypt).   ← 옛 키는 더 이상 안 된다
rekey가 하지 못하는 일

rekey는 암호화 키를 바꿀 뿐, 안에 든 비밀 값(DB 비밀번호)은 그대로입니다. 키가 유출되었다면 공격자는 이미 옛 파일을 복호화했을 수 있으므로 ① rekey ② 비밀 값 자체 교체(DB 비밀번호 변경 → 9장처럼 플레이북으로 반영) ③ Git 이력의 옛 암호문은 옛 키로 여전히 열린다는 점을 기억하고 값 교체를 반드시 함께 합니다.

tools/check-vault-encrypted.sh — 암호화되지 않은 vault 파일 커밋 방지 (실측: 평문 파일에서 rc=1)
#!/usr/bin/env bash
# pre-commit 훅: 이름이 vault*.yml 인데 암호화되지 않은 파일이 커밋되는 것을 막는다
status=0
for f in "$@"; do
  if [[ "$(basename "$f")" == vault*.yml || "$(basename "$f")" == vault*.yaml ]]; then
    if ! head -1 "$f" | grep -q '^\$ANSIBLE_VAULT;'; then
      echo "암호화되지 않은 vault 파일: $f  (ansible-vault encrypt $f)" >&2
      status=1
    fi
  fi
done
exit $status
# .pre-commit-config.yaml 에 추가 (10편 설정에 이어서)
  - repo: local
    hooks:
      - id: vault-encrypted
        name: vault*.yml 은 암호화되어 있어야 한다
        entry: tools/check-vault-encrypted.sh
        language: script
        files: (^|/)vault[^/]*\.ya?ml$

4출력으로 새는 비밀

암호화해서 저장해도, 실행 화면과 CI 로그에서 그대로 보일 수 있다

playbooks/leak_demo.yml
---
# 19편: 비밀이 출력으로 새는 경로와 막는 방법 (컨트롤 노드에서만 실행)
- name: 비밀 유출 경로 실험
  hosts: localhost
  connection: local
  gather_facts: false
  vars_files:
    - ../inventory/group_vars/lab/vault.yml
  vars:
    db_users:
      - { name: app, password: "{{ vault_postgresql_app_password }}" }
  tasks:
    - name: (1) 반복 항목이 그대로 출력된다
      ansible.builtin.debug:
        msg: "계정 {{ item.name }} 처리"
      loop: "{{ db_users }}"

    - name: (2) loop_control.label 로 출력 항목을 줄인다
      ansible.builtin.debug:
        msg: "계정 {{ item.name }} 처리"
      loop: "{{ db_users }}"
      loop_control:
        label: "{{ item.name }}"

    - name: (3) 명령 결과(register)에 비밀이 섞인다
      ansible.builtin.command: "echo connected with {{ vault_postgresql_app_password }}"
      register: out
      changed_when: false

    - name: (4) 같은 명령 + no_log
      ansible.builtin.command: "echo connected with {{ vault_postgresql_app_password }}"
      changed_when: false
      no_log: true

    - name: (5) 비밀이 든 파일 — diff에 그대로 보인다
      ansible.builtin.copy:
        dest: /tmp/leak_demo.pgpass
        content: "db:5432:app:app:{{ vault_postgresql_app_password }}\n"
        mode: "0600"

    - name: (6) 같은 파일 + diff false
      ansible.builtin.copy:
        dest: /tmp/leak_demo2.pgpass
        content: "db:5432:app:app:{{ vault_postgresql_app_password }}\n"
        mode: "0600"
      diff: false
# 실측: ansible-playbook playbooks/leak_demo.yml --diff -v   (실제 비밀번호를 〈비밀번호〉로 바꿔 표시)
TASK [(1) 반복 항목이 그대로 출력된다]
ok: [localhost] => (item={'name': 'app', 'password': '〈비밀번호〉'}) =>          ← 노출 ①
TASK [(2) loop_control.label 로 출력 항목을 줄인다]
ok: [localhost] => (item=app) =>                                                 ← 막힘
TASK [(3) 명령 결과(register)에 비밀이 섞인다]

    censored: 'the output has been hidden due to the fact that ''no_log: true'' was specified for this result'

노출 횟수: 4

③이 말해 주는 것: “명령 제한 sudo”와 Ansible become은 맞지 않는다

Ansible은 모듈을 실행하기 위해 sudo로 셸과 Python을 띄웁니다. sudoers에서 특정 명령만 허용한 계정은 become이 실패합니다. 선택지는 ① 자동화 계정에는 전체 sudo(비밀번호 또는 NOPASSWD)를 주고 그 계정 자체를 강하게 통제(키 관리·접속 출발지 제한·감사 로그) ② 제한된 계정은 become 없이 sudo 명령을 직접 실행(④처럼 — 멱등성·모듈 이점은 잃음). 15편 실습의 “deploy에 nginx 다시 읽기만 위임”은 사람·배포 도구가 쓰는 계정을 위한 것이고, Ansible 자동화 계정의 설계와는 다르다는 점을 구분하세요.

플레이 전체 become 대신 필요한 곳만14~17편 역할은 플레이 become: true였지만, 조회 태스크는 become 없이도 된다. 최소 권한

---
# 19편: SSH 키 교체 — 새 키 추가 → 새 키로 접속 확인 → 옛 키 제거 → 옛 키 거부 확인
- name: SSH 키 교체
  hosts: node1
  become: true
  vars:
    rot_user: svc-rot
    key_dir: "{{ playbook_dir }}/../../lab/keys"
    old_key: "{{ key_dir }}/svc-rot_2025"
    new_key: "{{ key_dir }}/svc-rot_{{ rot_tag }}"
    rot_tag: "2026q4"
    ssh_test: >-
      ssh -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=no
      -o ControlPath=none -p {{ ansible_port }}
  tasks:
    - name: 1) 새 키 만들기 (컨트롤 노드)
      community.crypto.openssh_keypair:
        path: "{{ new_key }}"
        type: ed25519
        comment: "{{ rot_user }}-{{ rot_tag }}"
      delegate_to: localhost
      become: false

    - name: 2) 새 키 추가 (옛 키는 아직 유지)
      ansible.posix.authorized_key:
        user: "{{ rot_user }}"
        key: "{{ lookup('ansible.builtin.file', new_key + '.pub') }}"
        state: present

    - name: 3) 새 키로 접속되는지 확인 (실패하면 여기서 멈추고 옛 키는 그대로)
      ansible.builtin.command: "{{ ssh_test }} -i {{ new_key }} {{ rot_user }}@{{ ansible_host }} true"
      delegate_to: localhost
      become: false
      changed_when: false

    - name: 4) 옛 키 제거 (목록을 새 키 하나로)
      ansible.posix.authorized_key:
        user: "{{ rot_user }}"
        key: "{{ lookup('ansible.builtin.file', new_key + '.pub') }}"
        exclusive: true
        state: present

    - name: 5) 옛 키가 거부되는지 확인
      ansible.builtin.command: "{{ ssh_test }} -i {{ old_key }} {{ rot_user }}@{{ ansible_host }} true"
      delegate_to: localhost
      become: false
      register: old_try
      changed_when: false
      failed_when: old_try.rc == 0
# 실측 (svc-rot 계정, 옛 키 svc-rot-2025 → 새 키 svc-rot-2026q4)
TASK [1) 새 키 만들기 (컨트롤 노드)]                 changed: [node1 -> localhost]
TASK [2) 새 키 추가 (옛 키는 아직 유지)]             changed: [node1]
TASK [3) 새 키로 접속되는지 확인 …]                  ok: [node1 -> localhost]
TASK [4) 옛 키 제거 (목록을 새 키 하나로)]           changed: [node1]
TASK [5) 옛 키가 거부되는지 확인]                    ok: [node1 -> localhost]

Ansible 자신이 쓰는 키를 바꿀 때

이 실습은 별도 계정(svc-rot)으로 했습니다. Ansible이 지금 접속에 쓰는 계정의 키를 바꿀 때는 ① 3단계 확인을 반드시 통과한 뒤 4단계로 ② 4단계 후 인벤토리·CI의 키(ansible_ssh_private_key_file, CI 비밀)를 같은 변경에서 교체 ③ ControlPersist로 열린 연결이 남아 있으면 옛 키가 “아직 되는 것처럼” 보이므로(13편 실측) 확인 단계는 이 플레이북처럼 ControlPath=none으로 새 연결을 맺어야 합니다.

        run: |
          ansible-playbook -i inventories/custa-prd playbooks/site.yml \
            --vault-id prd@tools/vault-env-client

GitHub Actions는 등록된 비밀 값을 로그에서 자동으로 가리지만(***), Ansible 출력에 비밀이 변형되어(base64, 일부만, 다른 줄로 나뉘어) 나오면 가리지 못합니다. 4장의 no_log·diff:false가 CI에서도 1차 방어선입니다.

11MSP 현장 팁

고객 수십 곳의 비밀을 다루는 운영 원칙

고객마다 키, 환경마다 키

vault-id를 custa_prd, custa_dev처럼 고객×환경으로 나눕니다. 한 고객 키가 유출되어도 다른 고객에 번지지 않고, 담당자 변경 시 해당 고객 키만 rekey하면 됩니다.

고객의 비밀 저장소를 쓴다

고객이 이미 Secrets Manager·Key Vault·HashiCorp Vault를 운영한다면 MSP 저장소에 사본을 두지 말고 고객 저장소에서 조회합니다. 비밀의 소유권과 교체 책임이 고객에게 남고, 계약 종료 시 MSP 쪽을 정리하기 쉽습니다.

퇴사·담당 변경 체크리스트

① 해당 인원 계정 absent(17편) ② 개인 SSH 키 제거(exclusive) ③ 알고 있던 Vault 키 rekey + 핵심 비밀 값 교체 ④ 외부 저장소 접근 권한 회수 ⑤ CI 비밀 교체. 이 순서를 플레이북·절차서로 만들어 둡니다.

비밀 교체 주기를 계약에

DB 비밀번호·자동화 키·Vault 키의 교체 주기와 방식을 고객 보안 기준과 맞춰 SLA·운영 절차서에 적습니다. 자동 교체(Secrets Manager rotation)가 가능한 것은 자동으로, 나머지는 9장 방식의 플레이북으로.

로그도 비밀처럼

CI 로그·ansible.log·AWX 잡 출력(21편)의 보관 기간과 열람 권한을 정합니다. no_log를 빠뜨린 태스크 하나가 수년치 로그에 비밀을 남길 수 있으므로, ansible-lint 사용자 규칙이나 코드 리뷰 체크리스트에 “비밀 변수를 쓰는 태스크는 no_log”를 넣습니다.

sudo 정책은 고객 기준을 따른다

금융·공공 고객은 NOPASSWD를 허용하지 않는 경우가 많습니다. 그때는 ansible_become_password를 Vault로, 접속 출발지 제한과 세션 기록(17편 로그 전송)을 함께 제안합니다.

14과제

실습을 마친 뒤에 풀어 보세요

과제 1. prd vault-id 추가

8편 구조대로 inventories/custa-prd/group_vars/all/vault.yml을 prd vault-id로 암호화하고, lab 키만 가진 사람이 prd 인벤토리로 실행하면 어떤 오류가 나는지, prd 키만 가진 CI가 lab 파일을 건드리지 않는지 확인하세요.

과제 2. no_log 누락 탐지

이름이 vault_로 시작하는 변수를 쓰는 태스크인데 no_log: true가 없으면 실패하는 간단한 검사 스크립트(또는 ansible-lint 사용자 규칙)를 만들어 pre-commit에 넣으세요. 16·17편 역할 전체에 돌려 보세요.

힌트

ansible-lint는 rules/ 디렉터리의 사용자 규칙(Python)을 -r 옵션이나 설정으로 불러옵니다. 간단히는 YAML을 읽어 태스크의 문자열 값에 vault_가 있고 no_log가 없으면 보고하는 파이썬 스크립트로 시작하세요. register한 값을 다음 태스크에서 debug하는 경우는 잡기 어렵다는 한계도 정리합니다.

과제 3. sudo 비밀번호 고객 시나리오

17편 base_users의 운영자 그룹을 NOPASSWD 없이 바꾸고(변수로 선택 가능하게), Ansible 실행 계정은 Vault의 become 비밀번호로 동작하도록 인벤토리를 구성하세요. 비밀번호를 바꿨을 때 어떤 순서로 적용해야 Ansible이 스스로 잠기지 않을까요?

해설

① 서버의 계정 비밀번호 변경(옛 비밀번호로 become하여 user 모듈의 password에 새 해시) → ② 같은 실행이 끝나기 전에는 옛 비밀번호로 계속 동작 → ③ Vault의 ansible_become_password를 새 값으로 바꿔 커밋. 순서를 바꾸면 ①을 실행할 수 없습니다. 16편처럼 한 대 먼저 적용합니다.

과제 4. 서버가 직접 비밀을 가져가게

애플리케이션이 실행 중에 DB 비밀번호를 필요로 한다면, Ansible이 설정 파일에 비밀번호를 써 넣는 대신 서버가 Secrets Manager에서 직접 읽게 할 수 있습니다. 7편 인스턴스 역할에 필요한 권한(Terraform), 애플리케이션 시작 스크립트(Ansible 템플릿), 비밀 교체 시 동작을 설계하고 두 방식을 비교하세요.

과제 5. Vault 동적 DB 비밀

OpenBao(또는 HashiCorp Vault)의 database 시크릿 엔진을 17편 PostgreSQL에 연결해, 요청할 때마다 1시간짜리 DB 계정을 발급받는 구성을 만들어 보세요. Ansible에서는 community.hashi_vault.vault_read로 database/creds/역할을 읽습니다. 고정 비밀번호와 비교한 장단점을 정리합니다.
