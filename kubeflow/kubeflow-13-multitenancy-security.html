이번 편에서 얻을 것

Level 4는 Kubeflow를 운영하는 사람의 과정입니다. 그 첫 편은 여러 사람과 여러 팀, 여러 기계가 안전하게 함께 쓰는 법입니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 네임스페이스 공유와 클러스터 분리 중 조직과 고객에 맞는 테넌시 모델을 고를 수 있습니다.
  • Dex나 oauth2-proxy에 기업 IdP를 연결하고, 기본 계정과 정적 비밀번호를 없앨 수 있습니다.
  • Istio 정책, Kubernetes RBAC, 프로필 역할이 각각 무엇을 막는지 설명하고, 사람과 기계의 접근 권한을 설계할 수 있습니다.
  • Pod 보안 표준, 입장 정책, NetworkPolicy, 비밀 값 관리, 공급망 보안으로 한 팀의 실수가 다른 팀에 번지지 않게 할 수 있습니다.

1테넌시 모델 고르기

테넌트는 플랫폼을 함께 쓰는 단위, 보통 팀이나 고객입니다. Kubeflow의 기본 모델은 3편의 프로필, 즉 테넌트마다 네임스페이스 하나입니다. 하지만 이것이 유일한 답은 아닙니다.

모델격리 강도비용과 운영어울리는 경우
프로필(네임스페이스) 공유논리적 격리. 같은 노드와 커널, 같은 Kubeflow 제어부, 같은 레지스트리를 공유가장 저렴하고 GPU를 나눠 쓰기 좋음(11편)같은 회사 안의 여러 팀. 서로 어느 정도 신뢰할 수 있음
노드 풀 분리를 더한 공유같은 클러스터지만 민감한 팀은 전용 노드에서만 실행중간. taint와 Kueue ResourceFlavor로 구현민감 데이터를 다루는 팀이 하나둘 있을 때
테넌트별 클러스터강한 격리. 제어부, 노드, 저장소가 모두 따로클러스터 수만큼 운영 부담과 비용서로 다른 회사(고객사), 규제 요건, 데이터 반출 금지
MSP라면 고객사는 클러스터로 나누세요

프로필 기반 격리는 “같은 조직 안의 팀”을 위한 설계입니다. 대시보드, 레지스트리, 일부 시스템 구성요소가 공유되고, 커널을 같이 쓰므로 컨테이너 탈출 같은 사고의 피해 범위가 클러스터 전체입니다. 서로 다른 고객사를 한 Kubeflow에 프로필로 나눠 담는 것은 권하지 않습니다. 고객사마다 클러스터(또는 최소한 별도 Kubeflow 설치)를 두고, 그 안에서 고객사의 팀들을 프로필로 나누는 2단 구조가 안전합니다. 16편에서 운영 관점으로 다시 다룹니다.

2보안의 여섯 층

한 층만으로는 충분하지 않습니다. 한 층이 뚫려도 다음 층이 막도록 겹겹이 둡니다. 각 층을 누르면 Kubeflow에서 무엇이 그 일을 하는지 볼 수 있습니다.

3인증: 기업 로그인 연결

3편의 user@example.com과 12341234는 운영에서 가장 먼저 없앨 것입니다. 사용자 계정은 회사의 신원 제공자(IdP: Keycloak, Entra ID, Okta, Google Workspace 등)가 관리하게 하고, Kubeflow는 그것을 믿게 만듭니다. 방법은 둘입니다.

방법구성장점주의
Dex를 거쳐 연결oauth2-proxy → Dex → 기업 IdP. Dex에 connector를 추가OIDC, LDAP, SAML 등 다양한 IdP를 Dex가 중개. 여러 IdP를 동시에 붙일 수 있음Dex라는 구성요소 하나를 더 운영
기업 IdP에 직접 연결oauth2-proxy가 기업 OIDC IdP를 직접 사용. Istio의 토큰 검증 설정도 그 IdP의 발급자로구성요소가 줄고 흐름이 단순IdP가 OIDC를 지원해야 함. 토큰의 이메일 클레임 등 형식을 맞춰야 함

Dex에 사내 OIDC IdP를 연결하는 설정 예 (단순화)

enablePasswordDB: false                     # 정적 사용자(user@example.com) 끄기
connectors:
- type: oidc
  id: corp
  name: 사내 SSO
  config:
    issuer: https://sso.example.com/realms/corp
    clientID: kubeflow
    clientSecret: $CORP_CLIENT_SECRET          # Secret에서 환경 변수로
    redirectURI: https://kubeflow.example.com/dex/callback
    scopes: [openid, profile, email, groups]
    insecureEnableGroups: true              # 그룹 클레임 전달
  • 이메일이 신분증입니다. 3편 8장처럼 프로필의 owner와 기여자는 로그인 이메일과 정확히 같아야 합니다. IdP가 내보내는 이메일 형식(대소문자, 별칭 도메인)을 먼저 확인하세요.
  • SAML만 지원하는 IdP라면 Dex의 SAML connector를 씁니다. SAML과 OIDC의 차이는 이 시리즈의 SAML 강의와 OAuth/OIDC 강의를 참고하세요.
  • HTTPS가 전제입니다. 3편 10장의 보안 쿠키 때문에 외부 주소는 HTTPS여야 합니다. 인증서는 cert-manager로 자동 갱신합니다(14편).
  • 퇴사자 처리: IdP에서 계정을 막아도 이미 발급된 세션은 만료 전까지 살아 있습니다. oauth2-proxy의 세션 수명을 정하고, 프로필 기여자 목록도 함께 정리하는 절차를 둡니다.

4인가: Istio, RBAC, 프로필

로그인한 사람이 무엇을 할 수 있는지는 세 겹으로 정해집니다. 맨 위 검문소 그림의 2번과 3번이 이것입니다.

검문소무엇을 보나무엇을 막나
Istio AuthorizationPolicy요청 헤더의 사용자(kubeflow-userid)가 그 네임스페이스에 접근이 허용된 사람인지다른 팀 네임스페이스의 노트북, 모델 서버 같은 웹 서비스로의 요청
Kubernetes RBAC그 사용자에게 그 네임스페이스에서 그 동작(조회, 생성, 삭제)이 허락되었는지. 대시보드 앱들이 SubjectAccessReview로 물어봄권한 없는 리소스 생성과 변경
프로필과 KFAM누가 소유자이고 누가 기여자인지를 관리하고, 위 둘의 규칙을 만들어 줌직접 막지는 않음. 규칙의 원천
역할 (ClusterRole)누구에게할 수 있는 일
kubeflow-admin프로필 소유자네임스페이스 안의 모든 Kubeflow 리소스와, 기여자 관리
kubeflow-edit편집 권한 기여자노트북, 파이프라인, TrainJob 등을 만들고 지우기. 기여자 관리는 불가
kubeflow-view보기 권한 기여자조회만
  • 대시보드의 Manage Contributors로 기여자를 추가하면 RoleBinding과 AuthorizationPolicy가 하나씩 생깁니다(3편 8장). 둘 중 하나만 손으로 지우면 “화면은 열리는데 만들 수 없음” 같은 어긋난 상태가 됩니다.
  • 사람이 많아지면 개인 단위 기여자 관리가 버겁습니다. IdP 그룹을 쓰고 싶다면, 설치한 버전이 그룹 기반 접근을 어디까지 지원하는지 먼저 확인하고, 지원 범위를 벗어나면 그룹 대상 RoleBinding과 AuthorizationPolicy를 GitOps로 직접 관리하는 방식을 씁니다.
  • 프로필 자체를 누가 만들 수 있는지도 정해야 합니다. 사용자가 스스로 만드는 등록 흐름을 끄고, 플랫폼 팀이 Git으로 프로필을 만드는 방식이 운영에 안전합니다.

5기계의 접근

파이프라인 단계, CI 서버, Argo CD, 노트북 안의 SDK처럼 사람이 아닌 주체도 플랫폼을 씁니다. 기계에게 사람 계정의 비밀번호를 주지 않습니다. 기계는 서비스 계정과 그 토큰으로 접근합니다.

기계신분권한 설계
노트북과 파이프라인 단계 Pod프로필 네임스페이스의 default-editor 서비스 계정자기 네임스페이스의 편집. 노트북에서 SDK가 동작하는 이유(4편 8장)
노트북에서 Pipelines API 호출access-ml-pipeline PodDefault가 넣어 주는, Pipelines 전용 대상(audience)으로 발급된 서비스 계정 토큰그 토큰은 Pipelines API에만 쓰이고 다른 곳에는 쓸 수 없음
클러스터 밖의 CI가 파이프라인 실행전용 서비스 계정의 토큰. oauth2-proxy가 Kubernetes 서비스 계정 토큰을 받아 주도록 구성되어 있어야 함(3편에서 본 설치 옵션)필요한 네임스페이스의 실행 생성만. 토큰은 짧은 수명으로 발급
Argo CD (12편)Argo CD의 서비스 계정관리 대상 네임스페이스의 정해진 리소스만. 클러스터 관리자 권한 금지
Trainer, Katib 등 컨트롤러각 구성요소의 서비스 계정설치 매니페스트가 정한 권한. 임의로 넓히지 않음
토큰은 짧게, 대상은 좁게

오래가는 토큰을 Secret에 만들어 두는 방식보다, 필요할 때 짧은 수명과 특정 대상(audience)으로 발급하는 방식(투영된 서비스 계정 토큰, TokenRequest)이 안전합니다. 토큰이 새어도 쓸 수 있는 곳과 시간이 좁아집니다.

6워크로드 격리

프로필 소유자는 자기 네임스페이스에 Pod를 만들 수 있습니다. 노트북에서 임의의 이미지로 Pod를 만들 수도 있다는 뜻입니다. 그 Pod가 노드의 파일 시스템이나 권한을 가져가지 못하게 막는 것이 Pod 보안 표준(PSS)입니다.

수준막는 것Kubeflow에서
privileged아무것도쓰지 않음. 시스템 네임스페이스 일부만 예외로 검토
baseline특권 컨테이너, 호스트 네트워크와 경로, 위험한 권한사용자 네임스페이스의 최소 기준
restrictedbaseline에 더해 root 실행, 권한 상승, 기본 seccomp 미사용 등목표. Istio CNI로 특권 init 컨테이너가 사라졌고(3편), KFP 2.16에서 단계 Pod의 runAsNonRoot 지정이 가능해짐(5편). 구성요소별 준수 상황은 릴리스 노트로 확인
 
# 네임스페이스에 적용 (경고로 먼저 시험하고, 문제없으면 강제)
kubectl label ns team-reco pod-security.kubernetes.io/warn=restricted
kubectl label ns team-reco pod-security.kubernetes.io/enforce=baseline

입장 정책으로 조직 규칙 강제하기

PSS가 막지 않는 조직의 규칙은 입장 정책(admission policy)으로 강제합니다. Kubernetes 내장 ValidatingAdmissionPolicy, Kyverno, OPA Gatekeeper 등을 씁니다. 예를 들어 사내 레지스트리의 이미지만 허용하는 규칙입니다.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: allowed-registries
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - {apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE"], resources: ["pods"]}
  validations:
  - expression: "object.spec.containers.all(c, c.image.startsWith('registry.example.com/'))"
    message: "사내 레지스트리의 이미지만 쓸 수 있습니다"
# 적용 대상 네임스페이스는 ValidatingAdmissionPolicyBinding으로 지정

다른 쓸 만한 규칙으로는 “GPU를 요청하는 작업은 Kueue 큐 라벨이 있어야 한다”(11편), “latest 태그 금지”(2편), “InferenceService는 자원 limits 필수” 등이 있습니다. 규칙을 새로 걸 때는 먼저 감사(경고) 모드로 며칠 돌려 기존 작업이 얼마나 걸리는지 봅니다. 사이드카, initContainer 같은 Kubeflow 구성요소가 넣는 컨테이너 이미지도 규칙에 걸리지 않는지 확인하세요.

7네트워크 격리

Istio 정책은 사이드카가 붙은 Pod로 들어오는 요청만 지킵니다. 그런데 7편, 8편, 10편에서 분산 학습, Katib Trial, Spark Pod는 사이드카를 뺐습니다. 이 Pod들은 Kubernetes NetworkPolicy로 지켜야 합니다.

팀 네임스페이스의 기본 차단과 필요한 허용 (단순화)

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: team-reco
spec:
  podSelector: {}                 # 모든 Pod에 대해
  policyTypes: [Ingress]           # 들어오는 연결을 기본 차단
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-ns-and-platform
  namespace: team-reco
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: {}              # 같은 네임스페이스 (분산 학습 노드끼리)
    - namespaceSelector:
        matchLabels: {kubernetes.io/metadata.name: istio-system}   # 게이트웨이
    - namespaceSelector:
        matchLabels: {kubernetes.io/metadata.name: kubeflow}       # 컨트롤러, 지표 수집 등
  • 나가는 연결(Egress)까지 막으면 더 안전하지만, DNS, 오브젝트 스토리지, 이미지 레지스트리, 패키지 저장소, 모델 저장소 등 허용할 곳을 빠짐없이 적어야 합니다. 한꺼번에 막지 말고 하나씩 넓혀 가세요.
  • NetworkPolicy는 클러스터의 CNI가 지원해야 동작합니다. 3편에서 본 것처럼 Cilium 같은 CNI는 Istio와 함께 쓸 때 추가 설정이 필요할 수 있습니다.
  • Kubeflow 배포판의 시스템 네임스페이스용 NetworkPolicy가 설치에 포함되어 있는지도 확인하세요.

8비밀 값과 데이터

대상위험대책
S3 키, Hugging Face 토큰노트북 코드, 이미지, Git에 새어 나감Secret과 PodDefault(4편), 원본은 Vault나 클라우드 비밀 관리 서비스에 두고 External Secrets Operator로 가져오기. etcd 암호화
팀별 데이터다른 팀이 버킷을 읽음팀마다 버킷이나 경로, 팀마다 다른 자격 증명. 클라우드라면 Pod 단위 신원(워크로드 아이덴티티)으로 키 없이
파이프라인 아티팩트공유 아티팩트 저장소에서 다른 팀의 데이터셋과 모델이 보임설치 구성이 네임스페이스별 저장소 경로와 자격 증명을 쓰는지 확인하고, 다른 팀 사용자로 직접 시험
모델 레지스트리여러 팀이 하나의 레지스트리를 공유(9편)쓰기 권한 범위 확인, 모델 이름에 팀 접두사, 민감 모델은 별도 레지스트리
모델 서버 엔드포인트외부에 인증 없이 열림외부 노출은 게이트웨이의 인증을 거치게 하고, 내부 호출은 Istio 정책으로 허용 대상을 좁힘
노트북 작업 공간민감 데이터 사본이 개인 PVC에 쌓임데이터 등급별 노드 풀과 네임스페이스, 보존 기간 정책

14정리와 다음 편

  1. 프로필 격리는 같은 조직의 팀을 위한 것입니다. 서로 다른 고객사는 클러스터나 설치를 나누고, 그 안의 팀을 프로필로 나눕니다.
  2. 인증은 기업 IdP에 맡기고 정적 계정을 없앱니다. 이메일이 프로필과 맞물리는 신분증입니다.
  3. 인가는 Istio 정책(웹 요청), RBAC(리소스 조작), 프로필 역할(규칙의 원천)이 겹쳐 지킵니다. 기계는 전용 서비스 계정과 짧고 좁은 토큰으로.
  4. PSS와 입장 정책이 위험한 Pod와 조직 규칙 위반을 막고, 사이드카 없는 학습 Pod는 NetworkPolicy가 지킵니다.
  5. 비밀 값은 비밀 관리 서비스에서, 데이터와 아티팩트는 팀별 경로와 자격 증명으로. 다른 팀 계정으로 직접 시험해 봐야 격리를 믿을 수 있습니다.
