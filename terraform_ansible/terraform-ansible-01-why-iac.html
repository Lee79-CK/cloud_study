설계도와 건물이 어긋나는 순간 왜 IaC인가 — 클릭 운영의 한계와 Terraform·Ansible의 역할 분담

인프라는 결국 “누가, 언제, 무엇을, 왜 바꿨는가”의 기록입니다. 콘솔 클릭은 그 기록을 남기지 않습니다. 이번 편은 도구 문법을 배우기 전에, 코드로 인프라를 다룬다는 것이 어떤 사고방식의 전환인지, 그리고 Terraform과 Ansible이 각각 어떤 문제를 맡는지 지도를 그리는 시간입니다.

1클릭 운영의 하루

도구 이야기 전에, 우리가 실제로 겪는 문제부터

MSP 2년차 엔지니어 민준 씨는 고객사 12곳을 맡고 있습니다. 대부분의 리소스는 처음 계약할 때 선배가 콘솔에서 만들었고, 설정 내역은 위키 문서 몇 장과 엑셀 시트에 남아 있습니다. 어느 화요일을 따라가 봅시다.

09:10

A사에서 “개발계와 똑같은 검증계를 하나 더 만들어 달라”는 요청. 개발계 화면을 탭 두 개로 띄워 놓고 VPC, 서브넷 4개, 라우팅 테이블, 보안그룹 9개를 하나씩 복제한다. 오후 2시까지 걸린다.

14:30

검증계에서 애플리케이션이 DB에 붙지 않는다. 한 시간 뒤, 개발계 보안그룹에는 위키에 없는 규칙 하나가 더 있었다는 사실을 발견. 누가 언제 추가했는지는 아무도 모른다.

16:00

B사 보안 점검 회신 마감. “지난 분기 방화벽 정책 변경 이력과 승인 근거를 제출하라.” CloudTrail에서 API 호출 기록은 찾았지만, 왜 바꿨는지와 누가 승인했는지는 메신저 대화를 뒤져야 한다.

23:40

C사 장애 호출. 웹 서버 디스크가 가득 찼다. 급한 마음에 콘솔에서 인스턴스 타입과 볼륨 크기를 키운다. 해결. 그런데 이 변경은 어디에도 기록되지 않았다. 석 달 뒤 누군가 “원래 설정”으로 서버를 다시 만들면 같은 장애가 재발한다.

이 하루에 등장한 문제들은 개인의 실수라기보다 방식의 한계입니다. 다섯 가지로 이름을 붙여 두면 앞으로 모든 편에서 “이 기능은 어떤 고통을 줄이려고 생겼는가”를 짚을 수 있습니다.

① 재현 불가 (Unreproducible)

똑같은 환경을 다시 만들 수 없습니다. 검증계·DR 환경·신규 고객 환경을 만들 때마다 사람의 기억과 눈썰미에 기댑니다.

② 드리프트 (Configuration Drift)

문서(또는 의도)와 실제가 시간이 갈수록 어긋납니다. 장애 대응 중 임시 조치가 영구 설정이 되는 것이 가장 흔한 경로입니다.

③ 감사 불가 (Unauditable)

클라우드 API 로그는 “무엇이 바뀌었는지”는 알려주지만 “왜, 누구의 승인으로”는 알려주지 않습니다. 보안 인증 심사와 고객 보고에서 매번 비용이 발생합니다.

④ 확장 불가 (Unscalable)

서버 10대일 때 30분 걸리는 작업은 300대일 때 15시간이 됩니다. 사람의 손은 선형으로만 늘어나고, 반복할수록 실수 확률도 올라갑니다.

⑤ 지식의 사람 종속 (Bus factor = 1)

“그건 김 과장님만 알아요.” 담당자가 휴가를 가거나 퇴사하면 그 고객사의 운영 지식도 함께 사라집니다. 버스 팩터(bus factor)는 몇 명이 버스에 치이면 프로젝트가 멈추는지를 뜻하는 냉소적 지표입니다.

이 다섯 가지를 한 문장으로

클릭 운영에서 인프라의 진실은 클라우드 콘솔 속 현재 상태 하나뿐이고, 그 상태가 왜 그렇게 되었는지는 사람의 머릿속에만 있습니다. IaC는 진실의 원천(source of truth)을 버전 관리되는 코드로 옮기는 일입니다.

계산기는 작업 시간만 보여줍니다. 실제로 더 비싼 것은 오류 한 건이 만드는 장애와 감사 대응·인수인계에 드는 시간입니다. 보안 그룹 규칙 하나를 잘못 열어 둔 채 몇 달이 지나는 사고는 작업 시간 계산에 잡히지 않습니다.

2IaC란 무엇인가

정의, 원칙, 그리고 30년의 짧은 역사

IaC(Infrastructure as Code, 코드형 인프라)는 서버·네트워크·스토리지·클라우드 서비스 같은 인프라를 사람이 손으로 설정하는 대신, 기계가 읽을 수 있는 정의 파일(코드)로 기술하고 도구가 그 정의대로 만들고 고치게 하는 방식입니다. 핵심은 “코드로 쓴다”가 아니라, 코드로 썼기 때문에 소프트웨어 개발이 수십 년간 쌓아 온 관행—버전 관리, 코드 리뷰, 테스트, 자동 배포—를 인프라에 그대로 쓸 수 있게 된다는 점입니다.

흔한 오해: 셸 스크립트도 IaC 아닌가요?

넓게 보면 맞습니다. 하지만 일반적으로 IaC라고 부를 때는 단순 자동화를 넘어 다음 성질을 기대합니다. 같은 코드를 여러 번 실행해도 결과가 같고(멱등성), 현재 상태와 원하는 상태의 차이를 계산해 필요한 것만 바꾸며(수렴), 변경 전에 무엇이 바뀔지 미리 보여줍니다(plan/check). 4장과 5장에서 셸 스크립트가 왜 여기서 어려움을 겪는지 직접 실험합니다.

IaC의 6가지 원칙

버전 관리

모든 인프라 정의는 Git에 있습니다. 변경은 커밋이고, 이력은 곧 변경 대장입니다.

리뷰 가능

변경은 Pull Request로 올라오고, 동료가 diff와 plan 결과를 보고 승인합니다. 승인 기록이 그대로 감사 증적이 됩니다.

재현 가능

같은 코드와 같은 입력이면 같은 인프라가 나옵니다. 환경 복제는 변수 파일 하나 차이입니다.

멱등·수렴

몇 번을 실행해도 결과가 같고, 어긋난 상태는 원하는 상태로 되돌려집니다.

테스트 가능

문법 검사, 정적 분석, 보안 스캔, 단위 테스트를 배포 전에 돌립니다. 10편과 20편에서 다룹니다.

자기 문서화

코드가 곧 최신 문서입니다. 위키는 낡지만, 실제로 배포에 쓰이는 코드는 낡을 수 없습니다.

짧은 역사: 손에서 코드로

~1990년대

수작업과 셸 스크립트. 서버는 물리 장비였고, 설치 절차서와 스크립트가 전부였습니다.

1993

CFEngine(Mark Burgess). “원하는 상태로 수렴한다”는 개념을 처음 체계화한 구성관리 도구.

2005 · 2009

Puppet, Chef. 에이전트가 서버마다 상주하며 중앙 서버에서 받은 정의대로 설정을 맞추는 1세대 대중화 도구.

2011

AWS CloudFormation. 클라우드 리소스 자체를 템플릿으로 선언하는 프로비저닝의 시작. 같은 해 Salt 등장.

2012

Ansible(Michael DeHaan). 에이전트 없이 SSH만으로 동작하는 단순함으로 빠르게 확산. 2015년 Red Hat이 인수.

2014

Terraform 0.1(HashiCorp). 하나의 언어(HCL)로 여러 클라우드를 다루는 프로비저닝 도구. 2021년 1.0으로 안정화.

2018 · 2020

Pulumi(범용 프로그래밍 언어로 IaC), Crossplane(Kubernetes 컨트롤러로 IaC), 2020년 Azure Bicep.

2023 · 2024

HashiCorp가 Terraform 라이선스를 MPL 2.0에서 BUSL 1.1로 변경(2023년 8월). 커뮤니티가 마지막 MPL 버전에서 포크한 OpenTofu가 2024년 1월 첫 정식 버전 출시.

2025 · 2026

IBM의 HashiCorp 인수 완료(2025년 2월)로 Terraform과 Ansible이 같은 회사 아래로. OpenTofu는 CNCF 샌드박스 합류(2025년 4월). Terraform MCP 서버·AI 어시스턴트 등 AI 지원 IaC가 본격화(26편).

3프로비저닝 vs 구성관리

이 강의 전체를 관통하는 가장 중요한 구분

프로비저닝(Provisioning)은 인프라 자원을 존재하게 만드는 일입니다. VPC를 만들고, 서브넷을 나누고, 가상 머신과 관리형 DB를 생성하고, 로드밸런서를 붙입니다. 대상은 클라우드나 하이퍼바이저의 API이고, 결과물은 “생성·변경·삭제되는 객체”입니다.

구성관리(Configuration Management)는 이미 존재하는 서버의 내부를 원하는 상태로 맞추는 일입니다. 사용자 계정을 만들고, 패키지를 설치하고, 설정 파일을 배포하고, 서비스를 띄웁니다. 대상은 운영체제이고, 접근 경로는 SSH나 WinRM입니다.

비유하자면 프로비저닝은 건물을 짓고 방을 나누는 일, 구성관리는 방에 가구를 들이고 배선을 정리하는 일입니다. 둘 다 할 줄 아는 도구도 많지만, 각자 잘하는 쪽이 분명합니다.

4선언형 vs 절차형

“무엇이 되어야 하는가”와 “무엇을 해라”의 차이

절차형(Procedural, 명령형 Imperative)은 수행할 동작의 순서를 적습니다. “서버를 만들어라, 그다음 태그를 붙여라.” 실행 시점의 현재 상태를 모르기 때문에, 같은 스크립트를 두 번 돌리면 서버가 두 번 만들어집니다.

선언형(Declarative)은 최종적으로 존재해야 할 모습을 적습니다. “웹 서버가 2대 있어야 한다.” 도구가 현재 상태를 조사해 차이를 계산하고, 그 차이만큼만 행동합니다. 이미 2대 있다면 아무것도 하지 않습니다.

절차형: 셸 스크립트 + AWS CLI실행할 때마다 2대씩 늘어남
#!/usr/bin/env bash
# 웹 서버 2대를 만든다
for i in 1 2; do
  aws ec2 run-instances \
    --image-id ami-0abc1234example \
    --instance-type t3.micro \
    --tag-specifications "ResourceType=instance,Tags=[{Key=Name,Value=web-$i}]"
done
선언형: Terraform (HCL)몇 번 실행해도 2대
resource "aws_instance" "web" {
  count         = 2
  ami           = "ami-0abc1234example"
  instance_type = "t3.micro"
  tags = { Name = "web-${count.index + 1}" }
}
“선언형 모듈을 절차적 순서로”: Ansible (YAML)각 태스크는 원하는 상태를 선언
- name: 웹 서버 기본 구성
  hosts: web
  become: true
  tasks:
    - name: nginx 설치
      ansible.builtin.package:
        name: nginx
        state: present        # "설치해라"가 아니라 "설치되어 있어야 한다"
    - name: nginx 기동 및 부팅 시 자동 시작
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
Ansible은 선언형인가, 절차형인가?

둘 다입니다. 각 태스크(모듈 호출)는 선언형입니다. state: present는 “없으면 설치하고, 있으면 그대로 둔다”는 뜻입니다. 하지만 태스크들은 위에서 아래로 순서대로 실행되므로 플레이북 전체는 절차적입니다. 그래서 순서를 잘못 짜면(설정 파일을 배포하기 전에 서비스를 시작하는 등) 결과가 달라집니다. 반면 Terraform은 리소스 사이의 참조 관계로 의존성 그래프를 스스로 만들고, 순서를 직접 정하지 않습니다.

5멱등성과 수렴

“몇 번을 실행해도 같은 결과” — IaC에서 가장 많이 듣게 될 단어

멱등성(Idempotency)은 원래 수학 용어로, 어떤 연산을 한 번 적용하든 여러 번 적용하든 결과가 같은 성질입니다. f(f(x)) = f(x). 절댓값 함수가 대표적입니다. |−3|은 3이고, ||−3||도 3입니다.

인프라에서 멱등성은 “같은 작업을 다시 실행해도 이미 원하는 상태라면 아무것도 바꾸지 않는다”는 뜻입니다. 이 성질이 있어야 안심하고 재실행할 수 있고, 실패한 작업을 처음부터 다시 돌릴 수 있고, 정기적으로 실행해 어긋난 설정을 되돌릴 수 있습니다.

수렴(Convergence)은 멱등한 작업을 반복 적용하면 시스템이 원하는 상태로 다가가 거기서 멈추는 성질입니다. 드리프트가 생겨도 다음 실행에서 원래대로 돌아옵니다.

멱등성을 깨는 대표 범인

  
Ansible의 command·shell 모듈은 무엇을 실행하는지 모르기 때문에 항상 changed로 보고합니다. 피할 수 없을 때는 creates/removes(특정 파일이 있으면 건너뜀)나 changed_when으로 멱등성을 보완합니다(14·20편). Terraform에서는 local-exec 프로비저너나 매번 값이 바뀌는 함수(timestamp() 등)가 비슷한 문제를 만듭니다.

  
수학적 멱등성과 실무 멱등성

  
엄밀히 말하면 실무 도구는 “원하는 상태에 대한 멱등성”을 보장합니다. 예를 들어 state: latest로 패키지를 지정하면, 저장소에 새 버전이 올라오는 순간 같은 코드가 다른 결과를 냅니다. 그래서 운영 환경에서는 버전을 고정(pinning)하는 것이 원칙입니다. 이 원칙은 Terraform의 provider 버전, Ansible의 컬렉션 버전에도 그대로 적용됩니다.

Ansible에는 왜 state 파일이 없을까?

  
Ansible은 매번 실행할 때 대상 서버에 접속해 그 자리에서 실제 상태를 조사하고(facts 수집, 모듈별 현재 상태 확인), 원하는 상태와 다르면 고칩니다. 별도의 기록이 필요 없는 대신 다음 한계가 생깁니다.

  
    
    
  • 지운 것을 모릅니다. 플레이북에서 “nginx 설치” 태스크를 지워도 서버에서 nginx가 사라지지 않습니다. 제거하려면 state: absent 태스크를 명시적으로 써야 합니다. Terraform은 코드에서 리소스를 지우면 state에 남은 기록을 근거로 삭제 계획을 세웁니다.
    • 
    
  • 관리하지 않는 것은 보지 않습니다. 플레이북에 없는 설정 파일을 누가 바꿔도 Ansible은 알 길이 없습니다.
    • 
    
  • 반대로 state 유실·잠금·손상 같은 문제가 아예 없습니다. 이것이 Ansible이 진입장벽이 낮은 이유이기도 합니다.
    • 
  

  
state 파일은 왕관의 보석

  
Terraform state에는 리소스 ID뿐 아니라 DB 비밀번호 같은 민감 값이 평문으로 들어갈 수 있습니다. 그래서 state는 Git이 아닌 암호화된 원격 백엔드(S3, Azure Blob 등)에 두고, 동시 실행을 막는 잠금을 겁니다. 민감 값을 state에 남기지 않는 방법(ephemeral 값, write-only 속성, 1.16의 store 블록)과 함께 5편에서 깊게 다룹니다.

7불변 인프라 vs 가변 인프라

  
서버를 고쳐 쓸 것인가, 새로 만들어 갈아 끼울 것인가

  

  
가변 인프라(Mutable Infrastructure)는 한 번 만든 서버를 계속 고쳐 씁니다. 패치하고, 설정을 바꾸고, 패키지를 올립니다. 전통적인 운영 방식이고, Ansible 같은 구성관리 도구가 빛나는 영역입니다.

  
불변 인프라(Immutable Infrastructure)는 배포된 서버를 절대 고치지 않습니다. 바꿀 것이 생기면 새 이미지로 새 서버를 만들고, 트래픽을 옮긴 뒤, 옛 서버를 버립니다. 컨테이너가 대표적인 예이고, VM에서는 골든 이미지(Packer 등으로 미리 구워 둔 이미지)와 오토스케일링 그룹 교체로 구현합니다.

  

  

    
Pets(애완동물) — 가변의 상징
이름이 있고(db-master-01), 아프면 정성껏 치료합니다. 대체 불가능합니다. 시간이 지나며 손을 탄 설정이 쌓여 아무도 똑같이 재현할 수 없는 눈송이 서버(Snowflake Server)가 됩니다.

    
Cattle(가축) — 불변의 상징
번호로 불리고(web-7f3a), 아프면 교체합니다. 모두 같은 이미지에서 태어났기 때문에 한 대를 버려도 서비스는 그대로입니다. 비유가 다소 거칠지만 업계에서 널리 쓰는 표현입니다.

  

  

    
관점가변 인프라불변 인프라

    
변경 방법기존 서버에 패치·설정 적용새 이미지로 새 서버 생성 후 교체

    
드리프트쌓이기 쉬움 (정기 수렴으로 관리)원천적으로 적음 (교체 시 초기화)

    
롤백되돌리는 작업을 다시 수행이전 이미지로 다시 교체

    
배포 속도작은 변경은 빠름이미지 빌드 시간 필요

    
상태 데이터서버에 있어도 됨서버 밖(DB, 오브젝트 스토리지)으로 분리 필수

    
잘 맞는 곳DB 서버, 레거시 앱, 온프레미스 VM, 고객사 지정 서버, 네트워크 장비무상태 웹/API 서버, 컨테이너 워크로드, 오토스케일링 대상

    
도구 조합Terraform(생성) + Ansible(지속 구성)Packer+Ansible(이미지 굽기) + Terraform(교체 배포)

  

  
MSP 현실: 대부분 섞여 있다

  
고객사 환경은 이상적이지 않습니다. 무상태 웹 계층은 불변으로 가져가도, DB 서버·라이선스가 묶인 상용 솔루션 서버·온프레미스 VM은 가변으로 관리해야 합니다. 중요한 것은 “어느 쪽이 정답인가”가 아니라 계층마다 어느 방식을 쓰는지 명시적으로 정하는 것입니다. 흥미롭게도 Ansible은 양쪽 모두에서 쓰입니다. 가변 서버를 지속 관리할 때, 그리고 불변 이미지를 구울 때.

Push vs Pull

  
Ansible은 기본적으로 컨트롤 노드가 서버로 밀어 넣는 Push 방식입니다. Puppet·Chef는 서버의 에이전트가 주기적으로 중앙에서 설정을 당겨오는 Pull 방식입니다. Push는 단순하고 즉시 실행되며, Pull은 서버가 스스로 계속 수렴합니다. Ansible에도 ansible-pull이 있고, AWX/AAP 스케줄로 정기 실행하면 Pull에 가까운 효과를 낼 수 있습니다(21편).







  
10라이선스와 생태계

  
Terraform과 OpenTofu, 그리고 IBM 아래 모인 두 도구

  

  
무슨 일이 있었나

  
2023년 8월, HashiCorp는 Terraform을 포함한 자사 제품의 라이선스를 오픈소스 라이선스인 MPL 2.0에서 BUSL 1.1(Business Source License)로 바꿨습니다. 마지막 MPL 버전은 Terraform 1.5.7입니다. 이에 반발한 커뮤니티와 기업들이 1.5.x 계열에서 포크해 OpenTofu를 만들었고, Linux Foundation 아래에서 2024년 1월 첫 정식 버전(1.6.0)을 냈습니다. OpenTofu는 2025년 4월 CNCF 샌드박스 프로젝트로 채택되었는데, CNCF 기본 라이선스인 Apache 2.0이 아닌 MPL 2.0을 예외로 승인받았습니다. 한편 IBM은 2025년 2월 HashiCorp 인수를 마무리했고, 이미 Red Hat을 통해 Ansible을 보유하고 있었기 때문에 두 도구는 같은 회사 소속이 되었습니다.

“이 작업은 어느 도구로?”에 대한 이 강의의 기본 답

API로 생성·삭제되는, 수명이 있는 객체는 Terraform. 그 안에 들어가 상태를 맞추는 일은 Ansible. Kubernetes 클러스터 안의 워크로드는 GitOps. 그리고 하나의 대상은 하나의 도구만 소유한다.

    과제 4. 사고 실험: state 파일이 사라졌다
    

      
Terraform으로 관리하던 웹 서버 3대와 보안그룹이 있습니다. 누군가 실수로 state 파일을 지웠습니다. 코드는 그대로입니다. 이 상태에서 terraform apply를 실행하면 어떻게 될까요? 그리고 어떻게 복구해야 할까요?

      
해설

        
Terraform은 state가 없으므로 “아무것도 관리하고 있지 않다”고 판단하고 모든 리소스를 새로 만들려고 합니다. 결과는 서버 3대가 더 생기거나(중복), 이름이 고유해야 하는 리소스(보안그룹 이름, S3 버킷 등)에서 “이미 존재함” 오류로 실패합니다. 기존 리소스는 더 이상 Terraform이 모르는 고아가 됩니다.

        
복구: ① 원격 백엔드의 버전 관리(S3 버전닝)에서 이전 state 복원이 최선. ② 불가능하면 import 블록으로 기존 리소스를 하나씩 state에 다시 연결(9편). 교훈: state는 원격 백엔드 + 버전닝 + 잠금이 필수입니다(5편).

핵심 1. 진실의 원천을 옮긴다

핵심 2. 두 질문으로 도구를 고른다

핵심 3. 멱등·수렴·plan
몇 번을 실행해도 같은 결과, 어긋나면 되돌아옴, 바꾸기 전에 미리 봄. 이 세 성질이 깨지는 코드는 IaC의 이점을 잃습니다.

    
핵심 4. 세 가지 상태
코드·state·실제. 드리프트는 실제가 코드에서 벗어난 것이고, 가장 흔한 원인은 장애 대응 중 수동 조치입니다.

Terraform은 BUSL 1.1, OpenTofu는 MPL 2.0, Ansible은 GPL v3. 일반 MSP 운영은 문제가 적지만, 호스팅 상품화는 검토 대상입니다.
