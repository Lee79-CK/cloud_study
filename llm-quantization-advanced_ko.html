01

정밀도 해부: 스케일 하나가 결정하는 것들

양자화 함수는 세 줄이면 쓸 수 있다. 문제는 그 세 줄에 들어가는 스케일을 어떻게 정하고, 몇 개의 가중치가 그 스케일을 공유하게 할지다. 여기서 품질의 절반이 결정된다.

아핀 양자화의 정확한 정의

실수 텐서 w를 정수 q로 보내는 표준 형태는 아핀(affine) 변환이다. 스케일 s와 제로포인트 z가 전부다.

# 양자화 (quantize) q = clamp( round(w / s) + z, q_min, q_max ) # 역양자화 (dequantize) — 커널이 실제로 하는 일 ŵ = s · (q − z) # 비대칭(asymmetric), b비트 부호 없는 정수라면 s = (max(w) − min(w)) / (2^b − 1) z = round(−min(w) / s) # 대칭(symmetric), b비트 부호 있는 정수라면 s = max(|w|) / (2^(b−1) − 1) z = 0

대칭 방식에서 분모가 2^(b-1)이 아니라 2^(b-1) − 1인 이유는 INT4의 표현 범위가 [-8, 7]로 비대칭이기 때문이다. -8을 버리고 [-7, 7]만 쓰는 것이 관례다. 16개 중 15개만 쓰므로 표현력을 조금 낭비하지만, 대신 제로포인트를 저장하지 않아도 되고 커널에서 곱셈 시 부호 처리가 단순해진다. 이 사소해 보이는 선택이 4비트에서는 실제로 측정 가능한 차이를 만든다.

왜 제로포인트가 사라지면 커널이 빨라지는가

ŵ·x = s(q−z)·x = s·q·x − s·z·x. 제로포인트가 있으면 뒤쪽 보정항 s·z·Σx를 따로 계산해 빼야 한다. 대칭 양자화는 이 항이 아예 없어서 INT4×INT4 누산을 그대로 텐서코어에 넘길 수 있다. Marlin 계열 고속 커널이 대칭·그룹 방식을 선호하는 이유다.

절대최대값(absmax)은 최적이 아니다

스케일을 정할 때 가장 흔한 방법은 max(|w|)를 쓰는 것이다. 하지만 이건 클리핑 오차를 0으로 만드는 대신 반올림 오차를 최대화하는 극단적 선택이다. 총 오차는 두 항의 합이다.

E_total(c) = E_round(c) + E_clip(c) E_round ∝ (c / (2^(b−1)−1))² / 12 ← 격자 간격의 제곱, c가 커지면 증가 E_clip = ∫|w|>c (|w| − c)² p(w) dw ← 잘라낸 꼬리의 제곱, c가 커지면 감소 # 최적 클리핑 임계값 c*는 두 항의 합을 최소화하는 지점 # 정규분포 가중치 + 4bit이면 대략 c* ≈ 2.5σ ~ 3.2σ (absmax는 보통 4σ 이상)

실무에서는 이 c*를 해석적으로 풀지 않고 격자 탐색으로 찾는다. AWQ의 clip search, GPTQ 구현체의 MSE observer, llm-compressor의 MSEObserver가 모두 같은 일을 한다: 스케일 후보를 0.5×absmax부터 1.0×absmax까지 20단계로 쓸어보고, 그룹별로 재구성 오차가 가장 작은 값을 고른다. 비용은 캘리브레이션 시간 몇 분, 이득은 4비트에서 PPL 0.05~0.2 정도. 공짜에 가까운 개선이다.

세분화(granularity): 누가 스케일을 공유하는가

스케일 하나를 몇 개의 가중치가 나눠 쓰는지가 두 번째 축이다. 공유 범위가 좁아질수록 품질은 좋아지고 메모리 오버헤드와 커널 복잡도는 늘어난다.

세분화스케일 개수추가 비트/가중치4bit 품질실무 위치
per-tensor1≈ 0❌ 붕괴활성화 정적 양자화에만
per-channel (출력 채널)행 개수≈ 0.004△ 8bit는 충분W8A8의 표준
per-group g=128행×(열/128)+0.125 (fp16 scale)◎ 4bit 표준GPTQ·AWQ 기본값
per-group g=64/322~4배 많음+0.25 ~ +0.5◉ 3bit 이하에서 필수NF4(64), 저비트
micro-block g=16/32매우 많음+0.5 (E4M3 scale)◉NVFP4 / MXFP4
방향을 틀리면 아무 효과가 없다

그룹은 반드시 축소(reduction) 축, 즉 행렬 곱에서 합해지는 방향으로 잘라야 한다. Y = XW^T에서 W의 입력 차원 방향이다. 출력 차원 방향으로 그룹을 자르면 커널이 부분합마다 다른 스케일을 곱해야 해서 역양자화를 누산 루프 안으로 끌어들이게 되고, 속도 이득이 사라진다. 직접 구현할 때 가장 흔히 틀리는 지점이다.

유효 bpw는 항상 직접 계산하라

# 4bit 대칭 + group 128 + fp16 스케일 bpw = 4 + 16/128 = 4.125 # 4bit 비대칭 + group 128 + fp16 스케일 + fp16 제로포인트 bpw = 4 + 16/128 + 16/128 = 4.25 # NF4 + group 64 + double quantization (스케일을 다시 8bit로, 256개마다 fp32 하나) bpw = 4 + 8/64 + 32/(64·256) ≈ 4.127 # NVFP4: 4bit 값 + 16개마다 E4M3 스케일 + 텐서당 FP32 bpw = 4 + 8/16 = 4.5 # MXFP4: 4bit 값 + 32개마다 E8M0 스케일 bpw = 4 + 8/32 = 4.25

"4비트 모델"이라고 적혀 있어도 실제로는 4.1~4.5비트다. 70B 모델에서 0.4비트 차이는 3.5GB다. GPU 한 장에 들어가는지 안 들어가는지가 여기서 갈린다.

직접 구현해 보기

라이브러리를 쓰기 전에 한 번은 손으로 써 보는 게 좋다. 아래 코드는 그룹 단위 아핀 양자화와 MSE 최적 스케일 탐색을 처음부터 구현한 것이다.

# 그룹 단위 아핀 양자화 — 라이브러리 없이
import torch

def quantize_group(W: torch.Tensor, bits=4, group=128, sym=True):
    """
    W: (out_features, in_features) — 그룹은 in_features(축소 축) 방향으로 자른다
    반환: 역양자화된 W_hat, 스케일, 제로포인트
    """
    O, I = W.shape
    assert I % group == 0, "in_features가 group으로 나누어져야 합니다"
    Wg = W.reshape(O, I // group, group).float()      # (O, n_groups, group)

    if sym:
        qmax = 2 ** (bits - 1) - 1                    # INT4 -> 7  (-8은 버림)
        scale = Wg.abs().amax(dim=-1, keepdim=True) / qmax
        scale = scale.clamp(min=1e-8)
        zero = torch.zeros_like(scale)
        q = (Wg / scale).round().clamp(-qmax - 1, qmax)
    else:
        qmax = 2 ** bits - 1                          # INT4 -> 0..15
        mx = Wg.amax(dim=-1, keepdim=True)
        mn = Wg.amin(dim=-1, keepdim=True)
        scale = ((mx - mn) / qmax).clamp(min=1e-8)
        zero = (-mn / scale).round()
        q = (Wg / scale + zero).round().clamp(0, qmax)

    W_hat = ((q - zero) * scale).reshape(O, I).to(W.dtype)
    return W_hat, scale, zero


def effective_bpw(bits, group, sym, scale_bits=16):
    """실제로 디스크와 VRAM을 차지하는 가중치당 비트"""
    overhead = scale_bits / group * (1 if sym else 2)
    return bits + overhead


W = torch.randn(4096, 4096) * 0.02
W[0, ::997] *= 40                                     # 이상치 주입
for g in (4096, 128, 32):
    W_hat, _, _ = quantize_group(W, bits=4, group=g)
    err = (W - W_hat).pow(2).mean().item()
    sqnr = 10 * torch.log10(W.pow(2).mean() / (W - W_hat).pow(2).mean()).item()
    print(f"group={g:>5}  MSE={err:.3e}  SQNR={sqnr:5.2f} dB  "
          f"bpw={effective_bpw(4, g, True):.3f}")

# absmax 대신 MSE 최적 스케일을 격자 탐색으로 찾는다
# AWQ의 clip search, llm-compressor의 MSEObserver가 하는 일과 동일한 원리
import torch

def search_scale_mse(Wg: torch.Tensor, bits=4, n_grid=20, max_shrink=0.5):
    """
    Wg: (..., group) 마지막 축이 하나의 그룹
    absmax를 1.0으로 두고 max_shrink까지 줄여가며 재구성 오차가 최소인 배율을 고른다
    """
    qmax = 2 ** (bits - 1) - 1
    absmax = Wg.abs().amax(dim=-1, keepdim=True).clamp(min=1e-8)

    best_err = torch.full_like(absmax, float("inf"))
    best_scale = absmax / qmax

    for i in range(n_grid):
        ratio = 1.0 - (i / n_grid) * (1.0 - max_shrink)   # 1.00 -> 0.50
        scale = (absmax * ratio / qmax).clamp(min=1e-8)
        q = (Wg / scale).round().clamp(-qmax - 1, qmax)
        err = ((q * scale - Wg) ** 2).mean(dim=-1, keepdim=True)

        better = err < best_err
        best_err = torch.where(better, err, best_err)
        best_scale = torch.where(better, scale, best_scale)

    return best_scale, best_err

# 어떤 레이어가 양자화에 민감한가 — 혼합 정밀도 결정의 근거
# 이 스크립트 하나로 "왜 이 모델은 4bit에서 무너지는가"의 절반을 설명할 수 있다
import torch, json
from transformers import AutoModelForCausalLM

MODEL = "meta-llama/Llama-3.1-8B-Instruct"
model = AutoModelForCausalLM.from_pretrained(MODEL, dtype=torch.bfloat16, device_map="cpu")

def quantize_group(W, bits=4, group=128):
    O, I = W.shape
    pad = (-I) % group
    if pad:
        W = torch.nn.functional.pad(W, (0, pad))
    Wg = W.reshape(O, -1, group).float()
    qmax = 2 ** (bits - 1) - 1
    s = (Wg.abs().amax(-1, keepdim=True) / qmax).clamp(min=1e-8)
    out = ((Wg / s).round().clamp(-qmax - 1, qmax) * s).reshape(O, -1)
    return out[:, :I]

rows = []
for name, mod in model.named_modules():
    if not isinstance(mod, torch.nn.Linear):
        continue
    W = mod.weight.data.float()
    Wq = quantize_group(W, bits=4, group=128)
    # 상대 프로베니우스 오차: 스케일에 무관해 레이어 간 비교가 가능하다
    rel = ((W - Wq).norm() / W.norm()).item()
    # 첨도: 이상치가 많은 레이어는 값이 크다 (정규분포는 3)
    kurt = ((W - W.mean()) ** 4).mean().item() / (W.var().item() ** 2 + 1e-12)
    rows.append({"layer": name, "rel_err": rel, "kurtosis": kurt,
                 "shape": list(W.shape)})

rows.sort(key=lambda r: -r["rel_err"])
print(f"{'layer':<52}{'rel_err':>10}{'kurtosis':>11}")
for r in rows[:15]:

json.dump(rows, open("layer_sensitivity.json", "w"), indent=1)

곡률과 오차 전파: GPTQ의 뚜껑을 열다

101에서 GPTQ를 "헤시안으로 오차를 흘려보낸다"고 배웠다. 그 문장 안에 있는 목적 함수, 갱신식, 그리고 desc_act 같은 옵션들이 왜 존재하는지를 여기서 유도한다.

목적 함수를 다시 쓰기

양자화의 목표는 "가중치를 원본과 비슷하게 만드는 것"이 아니다. 레이어의 출력을 원본과 비슷하게 만드는 것이다. 이 차이가 모든 것을 바꾼다.

# 순진한 목표 (RTN이 하는 일) min ‖W − Ŵ‖² ← 활성화를 전혀 보지 않는다 # 실제 목표 (레이어 단위 재구성) min ‖WX − ŴX‖²_F X: 캘리브레이션 활성화 (in_features × n_samples) # 2차 테일러 전개 → 헤시안이 등장한다 Ŵ = W + δ 라 두면 ‖(W+δ)X − WX‖²_F = tr(δ X Xᵀ δᵀ) = δᵀ H δ , H = 2·X·Xᵀ # 핵심: 헤시안이 곧 활성화의 2차 통계량이다 # → 자주 크게 활성화되는 입력 차원의 가중치 오차가 더 큰 벌점을 받는다

이것이 캘리브레이션 데이터가 필요한 유일한 이유다. GPTQ는 그래디언트를 쓰지 않는다. 학습도 하지 않는다. 단지 X·Xᵀ라는 in_features × in_features 행렬을 모으기 위해 데이터를 흘려보낸다. 4096차원 레이어라면 4096×4096 = 1600만 개의 원소, fp32로 64MB. 이 행렬 하나가 그 레이어의 "무엇이 중요한가"를 전부 담고 있다.

import torch

def gptq_quantize(W, H, bits=4, group=128, damp=0.01, act_order=True):
    """
    W: (out, in) 원본 가중치 (float32)
    H: (in, in)  캘리브레이션 헤시안 = X @ X.T
    """
    W = W.clone().float()
    O, I = W.shape
    qmax = 2 ** (bits - 1) - 1

    # 1) 죽은 입력 채널 처리 + dampening
    dead = torch.diag(H) == 0
    H[dead, dead] = 1.0
    W[:, dead] = 0.0
    H += torch.eye(I, device=H.device) * (damp * torch.diag(H).mean())

    # 2) act-order: 중요한 열(헤시안 대각 큰 순)을 먼저
    if act_order:
        perm = torch.argsort(torch.diag(H), descending=True)
        W, H = W[:, perm], H[perm][:, perm]
        invperm = torch.argsort(perm)

    # 3) H의 역행렬을 콜레스키로 한 번만 — 이게 GPTQ의 속도 비결
    Hinv = torch.linalg.cholesky(torch.cholesky_inverse(
        torch.linalg.cholesky(H)), upper=True)

    Q = torch.zeros_like(W)
    for j in range(I):
        w = W[:, j]
        d = Hinv[j, j]

        # 그룹 경계에서만 스케일을 새로 계산
        if j % group == 0:
            blk = W[:, j:j + group]
            scale = (blk.abs().amax(dim=1, keepdim=True) / qmax).clamp(min=1e-8)

        q = (w.unsqueeze(1) / scale).round().clamp(-qmax - 1, qmax)
        dq = (q * scale).squeeze(1)
        Q[:, j] = dq

        # 4) 오차를 남은 열로 전파 — 알고리즘의 심장
        err = (w - dq) / d
        W[:, j + 1:] -= err.unsqueeze(1) @ Hinv[j, j + 1:].unsqueeze(0)

    if act_order:
        Q = Q[:, invperm]
    return Q

import torch

class HessianCollector:
    """forward hook으로 X @ X.T 를 누적한다. 메모리는 (in_features)^2 고정."""
    def __init__(self, in_features, device="cuda"):
        self.H = torch.zeros(in_features, in_features, device=device,
                             dtype=torch.float32)
        self.n = 0

    def __call__(self, module, inp, out):
        x = inp[0].detach()
        if x.dim() == 3:                     # (batch, seq, in) -> (tokens, in)
            x = x.reshape(-1, x.shape[-1])
        x = x.float()
        # 온라인 평균: 샘플 수가 달라도 스케일이 일정하게 유지된다
        n_new = x.shape[0]
        self.H *= self.n / (self.n + n_new)
        self.n += n_new
        self.H += (2.0 / self.n) * (x.T @ x)

attention sink

첫 토큰(또는 개행 같은 무의미 토큰)이 어텐션 확률을 대량으로 흡수한다. "주목할 게 없을 때 버리는 곳"이 필요해서다. KV 캐시 양자화를 어렵게 만든다.

QuaRot은 무작위 하다마드를 쓴다. SpinQuant는 회전 행렬 자체를 학습한다 — 슈티펠 다양체(Stiefel manifold) 위에서 케일리 최적화로 직교성을 유지하며 소량의 데이터로 몇 백 스텝 돌린다. 제로샷 정확도에서 고정 하다마드보다 유의미하게 앞선다. 2026년 현재 llm-compressor에는 QuIPModifier(하다마드)와 SpinQuantModifier(R1·R2 지원)가 들어와 있고, FP4 시대에는 전역 회전보다 블록 단위 하다마드가 더 낫다는 결과(MR-GPTQ, BRQ 계열)가 쌓이는 중이다. 마이크로스케일링 블록이 이미 16~32개 단위로 잘려 있기 때문이다.

# 빠른 하다마드 변환과 그 효과 측정 — 개념 확인용
import torch, math

def fwht(x):
    """마지막 축에 대한 빠른 하다마드 변환. len은 2의 거듭제곱이어야 한다."""
    x = x.clone()
    n = x.shape[-1]
    assert n & (n - 1) == 0, "2의 거듭제곱만"
    h = 1
    while h < n:
        x = x.reshape(*x.shape[:-1], n // (2 * h), 2, h)
        a, b = x[..., 0, :], x[..., 1, :]
        x = torch.stack([a + b, a - b], dim=-2).reshape(*x.shape[:-3], n)
        h *= 2
    return x / math.sqrt(n)          # 직교화 (QQᵀ = I)


def randomized_hadamard(x, seed=0):
    """무작위 부호를 곱한 뒤 하다마드 — QuIP#의 RHT"""
    g = torch.Generator(device=x.device).manual_seed(seed)
    signs = torch.randint(0, 2, (x.shape[-1],), generator=g,
                          device=x.device, dtype=x.dtype) * 2 - 1
    return fwht(x * signs), signs


def int_quant_err(x, bits=4):
    qmax = 2 ** (bits - 1) - 1
    s = x.abs().amax(dim=-1, keepdim=True) / qmax
    xq = (x / s).round().clamp(-qmax - 1, qmax) * s
    return (x - xq).pow(2).mean().item()

격자를 버리다: 코드북과 벡터 양자화

지금까지는 모든 방법이 "균등한 격자 위의 한 점"으로 가중치를 보냈다. 2비트 영역에서는 그 가정 자체가 병목이다. 격자를 데이터에 맞게 다시 그리면 무엇이 가능해지는가.

스칼라 양자화의 한계

2비트는 값 4개다. 정규분포를 4개 값으로 표현하면 SQNR이 약 9.3dB에 그친다. 여기서 두 가지 방향으로 탈출할 수 있다.

① 비균등 코드북 (NF4의 길)

격자 간격을 분포에 맞춘다. 정규분포의 분위수에 값을 배치하면 같은 비트로 오차가 줄어든다. NF4, SqueezeLLM의 민감도 기반 k-means가 여기 속한다. 여전히 가중치 하나당 인덱스 하나.

② 벡터 양자화 (VQ)

가중치 여러 개를 묶어서 하나의 코드로 표현한다. 8개를 묶어 16비트 코드로 보내면 2bpw. 고차원 구는 사각격자보다 효율적으로 채울 수 있다는 사실을 이용한다 — 정보이론의 구 채우기 이득.

# 직접 만들어 보면 왜 균등 INT4보다 좋은지 수치로 보인다
import torch
from scipy.stats import norm

def make_nf_codebook(bits=4):
    """정보이론적으로 균등한 분위수 지점 (0을 정확히 포함하도록 비대칭 구성)"""
    n_pos, n_neg = 2 ** (bits - 1), 2 ** (bits - 1) - 1
    offset = 0.5 * (1 / 32 + 1 / 30)
    pos = norm.ppf(torch.linspace(offset, 0.5, n_pos + 1)[1:].numpy())
    neg = norm.ppf(torch.linspace(offset, 0.5, n_neg + 1)[1:].numpy())
    cb = torch.tensor(sorted([-float(v) for v in neg] + [0.0]
                             + [float(v) for v in pos]))
    return cb / cb.abs().max()            # [-1, 1]로 정규화

NF4 = make_nf_codebook(4)
print("NF4 코드북:", [round(v, 4) for v in NF4.tolist()])

def quant_codebook(W, cb, group=64):
    Wg = W.reshape(-1, group)
    s = Wg.abs().amax(-1, keepdim=True).clamp(min=1e-8)
    idx = (Wg / s).unsqueeze(-1).sub(cb.view(1, 1, -1)).abs().argmin(-1)
    return (cb[idx] * s).reshape(W.shape)

def quant_uniform(W, bits=4, group=64):
    Wg = W.reshape(-1, group)
    qmax = 2 ** (bits - 1) - 1
    s = (Wg.abs().amax(-1, keepdim=True) / qmax).clamp(min=1e-8)
    return ((Wg / s).round().clamp(-qmax - 1, qmax) * s).reshape(W.shape)

W = torch.randn(1024, 4096) * 0.02
e_nf = (W - quant_codebook(W, NF4)).pow(2).mean()
e_int = (W - quant_uniform(W)).pow(2).mean()
print(f"INT4 균등  MSE = {e_int:.4e}")
print(f"NF4  코드북 MSE = {e_nf:.4e}   ({100*(1-e_nf/e_int):.1f}% 개선)")

마이크로스케일링: FP4가 표준이 되는 방식

Blackwell 세대에서 4비트는 "메모리 절약 트릭"이 아니라 텐서코어의 기본 연산 정밀도가 됐다. MXFP4와 NVFP4가 어떻게 다르고, 왜 하나는 32개, 다른 하나는 16개를 묶는지.

두 단계 스케일링

FP4 자체는 표현할 수 있는 값이 {0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6} 15개(E2M1)뿐이다. 이걸 실제 텐서에 쓰려면 작은 블록마다 스케일이 필요하고, 그 스케일을 어떤 포맷으로 저장하느냐가 두 표준을 갈랐다.

# MXFP4 — OCP 마이크로스케일링 표준 (다벤더) x̂ᵢ = qᵢ · s⌊i/32⌋ q ∈ FP4(E2M1), s ∈ E8M0 (지수만, 2의 거듭제곱) bpw = 4 + 8/32 = 4.25 # NVFP4 — NVIDIA Blackwell 구현 x̂ᵢ = qᵢ · s⌊i/16⌋ · S q ∈ FP4(E2M1), s ∈ FP8(E4M3), S ∈ FP32 (텐서 전역) bpw = 4 + 8/16 = 4.5 # 왜 NVFP4에 전역 스케일 S가 추가로 필요한가? E4M3의 동적 범위(±448)가 E8M0(2^±127)보다 훨씬 좁다. → 블록 스케일만으로 텐서 전체 범위를 못 덮으므로 FP32 하나로 먼저 정규화한다.
블록 16 vs 32

블록이 작으면 이상치 격리가 잘 된다. NVFP4가 같은 모델·같은 캘리브레이션에서 MXFP4보다 PPL이 낮은 주된 이유다. 대가는 스케일 오버헤드 2배(0.25 → 0.5 bpw).

E8M0 vs E4M3

E8M0은 지수만 있어 역양자화가 비트 시프트로 끝난다 — 하드웨어가 단순하고 NVIDIA 외 가속기에서도 유리하다. E4M3은 가수가 있어 스케일 자체가 정밀하다.

같은 텐서코어

Blackwell에서는 두 포맷이 동일한 FP4 연산 유닛을 쓴다. 체크포인트 레이아웃만 다르다. 즉 포맷 선택은 성능이 아니라 정확도·이식성의 선택이다.

가중치를 4비트로 줄여도 문맥이 128K가 되면 KV 캐시가 GPU 메모리를 다 잡아먹는다. 긴 문맥 서비스에서 진짜 병목은 가중치가 아니다.

W·A 조합 읽는 법

W4A16은 "가중치 4비트, 활성화 16비트"다. 이 표기가 중요한 이유는 속도 이득의 원천이 완전히 다르기 때문이다.

동적 vs 정적 활성화 스케일

동적(per-token): 추론 중 각 토큰의 활성화 절대최대값을 실시간 계산. 캘리브레이션 불필요, 품질 좋음, 커널에 리덕션 한 번 추가.
정적(per-tensor): 캘리브레이션으로 스케일을 미리 고정. 가장 빠르지만, 실사용 분포가 캘리브레이션과 어긋나면 클리핑으로 조용히 망가진다.
기본은 동적이다. 정적은 마지막 몇 %의 지연을 짜낼 때만 쓰고, 반드시 실제 트래픽으로 캘리브레이션하라.

KV 캐시의 산수

KV_bytes = 2 · L · H_kv · d_head · bytes_per_elem · seq_len · batch L = 레이어 수 H_kv = KV 헤드 수 (GQA면 어텐션 헤드보다 훨씬 적다) d_head = 헤드 차원 2 = Key + Value # Llama-3.1-8B: L=32, H_kv=8, d_head=128, BF16(2 bytes) # 토큰 하나당 = 2·32·8·128·2 = 131,072 바이트 = 128 KB # 128K 문맥 1개 세션 ≈ 17 GB (16 GiB) ← BF16 가중치와 맞먹는다 # FP8로 내리면 ≈ 8.6 GB

이 산수의 결론은 분명하다. 동시 사용자 수 × 문맥 길이가 커지는 서비스에서는 가중치 양자화보다 KV 캐시 양자화가 처리량에 더 크게 기여한다. 2026년 vLLM 기준 --kv-cache-dtype fp8은 KV 트래픽 기울기를 BF16의 약 54%까지 내리고, 손익분기가 대략 7K 토큰 부근에 형성된다. 문맥이 그보다 짧으면 FP8의 고정 오버헤드 때문에 오히려 미세하게 느려질 수 있다.

K와 V는 다른 방식으로 양자화해야 한다

KV 캐시 연구가 밝혀낸 가장 실용적인 사실: Key는 채널 방향으로 이상치가 몰려 있고, Value는 상대적으로 균일하다.

Key — per-channel

특정 채널이 항상 큰 값을 갖는다(RoPE 이전에 더 뚜렷). 채널마다 스케일을 두면 같은 비트로 오차가 크게 줄어든다. 단점: 스케일 축이 행렬 곱의 축소 축과 어긋나 커널이 까다로워진다.

Value — per-token

토큰 단위 스케일이 자연스럽다. 새 토큰이 추가될 때 기존 캐시를 건드리지 않아도 되어 증분 갱신에 유리하다. 페이지 단위 캐시 구조와도 잘 맞는다.

여기에 세 가지 보정이 더 붙는다. ① pre-RoPE 양자화 — RoPE 회전이 채널 구조를 뒤섞으므로 그 전에 양자화(KVQuant). ② attention sink 보존 — 첫 토큰의 KV는 FP16으로 남긴다. ③ 최근 토큰 잔여 버퍼 — 최근 몇 십 개 토큰은 원본 정밀도로 두고 나중에 양자화(KIVI).

2026년 현실 점검

프로덕션 엔진(vLLM)에서 기본으로 쓸 수 있는 KV 양자화는 FP8까지다. INT2/INT4 KV(KIVI, KVQuant)는 논문·별도 패치 수준이며 엔진 내부에 통합되어 있지 않다. 또 FP8 KV는 기본값이 무보정 per-tensor(scale=1.0)이므로, 모델에 따라 조용히 품질이 떨어진다. llm-compressor로 k/v 스케일을 캘리브레이션한 체크포인트를 쓰면 per-head 스케일까지 활용할 수 있다. 하이브리드 어텐션 모델은 --kv-cache-dtype-skip-layers sliding_window로 슬라이딩 윈도우 레이어를 제외하는 것이 유리하다.

커널과 산술 강도: 왜 4비트가 항상 빠르지는 않은가

"4비트로 줄였는데 처리량이 오히려 떨어졌다"는 이슈 리포트는 버그가 아니다. 예상된 결과다. 이유를 계산으로 확인해 보자.

디코딩은 메모리 병목, 프리필은 연산 병목

# 산술 강도(arithmetic intensity) = 연산량 / 메모리 이동량 # 디코딩 1스텝, 배치 B, 가중치 P개, 가중치 비트 b FLOPs = 2 · P · B Bytes = P · b/8 ← 배치와 무관! 가중치는 한 번만 읽는다 Intensity = 16·B / b FLOP/byte # H100 SXM 기준 임계 강도 (BF16) 989 TFLOPS / 3.35 TB/s ≈ 295 FLOP/byte # W4A16, b=4 이면 → 임계 배치 B* ≈ 295·4/16 ≈ 74 # B < 74 : 메모리 병목 → 4비트가 4배 유리 # B > 74 : 연산 병목 → BF16 연산으로 되돌리므로 이득 0, 역양자화 비용만 남음

이것이 W4A16의 근본적 한계다. 활성화가 16비트면 곱셈은 결국 FP16 텐서코어에서 일어난다. 가중치를 아무리 줄여도 연산량은 그대로다. 배치가 커지는 프로덕션 서빙에서 진짜 처리량을 얻으려면 활성화도 같이 낮춰야(W8A8, W4A8, W4A4) 한다.

커널을 알아야 하는 이유

같은 GPTQ 체크포인트라도 어떤 커널이 실행되느냐에 따라 처리량이 3배 차이 난다. 엔진 로그에서 커널 이름을 확인하는 습관이 필요하다.

Marlin W4A16 고속 커널

4비트 가중치를 텐서코어 레이아웃에 맞게 미리 재배치해 저장하고, 역양자화를 파이프라인에 융합해 대역폭을 거의 이론치까지 활용한다. 배치가 작을 때 FP16 대비 3~4배.

제약: 대칭 양자화, group_size ∈ {-1, 32, 64, 128}, SM 8.0 이상. desc_act로 열이 뒤섞인 체크포인트는 재정렬 비용이 붙거나 아예 다른 커널로 폴백된다. vLLM 로그에 gptq_marlin 대신 gptq가 보이면 느린 경로다.

Machete Hopper 세대 혼합 정밀도

Hopper의 wgmma 명령과 텐서 메모리 가속기(TMA)를 활용하도록 다시 쓴 혼합 정밀도 GEMM. 중간 배치 구간(16~128)에서 Marlin보다 유리한 경우가 많다. vLLM이 형상과 하드웨어를 보고 자동 선택한다.

FlashInfer 어텐션 + FP4 MoE

어텐션과 MoE 라우팅을 위한 커널 모음. Blackwell의 NVFP4 MoE 경로가 여기 있어서 VLLM_USE_FLASHINFER_MOE_FP4=1 환경변수가 필요하다. 켜지 않으면 폴백 경로로 조용히 느려진다.

CPU/Metal llama.cpp의 SIMD 커널

GGUF의 Q4_K 계열은 블록 구조 자체가 SIMD 레지스터 폭에 맞춰 설계됐다. ARM용 Q4_0_4_4/Q4_0_8_8처럼 재배치 전용 변종이 있는 이유도 같다. Apple Silicon에서는 Metal 셰이더가, x86에서는 AVX2/AVX-512 VNNI가 동원된다.

측정 없이는 아무것도 믿지 마라

양자화 성능 논의에서 가장 흔한 오류는 배치 1 벤치마크로 프로덕션을 판단하는 것이다. 실제 서비스는 continuous batching으로 항상 여러 시퀀스를 동시에 디코딩한다. 반드시 --max-concurrency를 실사용 수준으로 올려 측정하고, 프리필 대 디코딩 비율(입력/출력 길이)도 실제 트래픽과 맞춰라. 요약 서비스(입력 8000, 출력 200)와 대화 서비스(입력 500, 출력 800)는 완전히 다른 최적점을 갖는다.

QAT와 양자화 친화 파인튜닝

PTQ로 회복되지 않는 손실이 남았을 때, 또는 처음부터 4비트 배포가 정해져 있을 때. 학습 쪽에서 양자화를 마주하는 방법들.

가짜 양자화와 STE

round()의 미분은 거의 모든 곳에서 0이다. 그대로 역전파하면 그래디언트가 사라진다. QAT는 이 문제를 직통 추정기(Straight-Through Estimator)로 우회한다 — 순전파에서는 반올림하고, 역전파에서는 반올림이 없었던 것처럼 그래디언트를 통과시킨다.

# 순전파: 실제로 양자화 → 역양자화 (fake quant) ŵ = s · clamp(round(w/s), q_min, q_max) # 역전파: STE — 클리핑 범위 안에서는 그래디언트를 그대로 통과 ∂L/∂w = ∂L/∂ŵ · 1[q_min ≤ w/s ≤ q_max] # 결과: 모델이 "나는 곧 4비트가 된다"는 사실을 알고 수렴한다 가중치가 격자 근처로 모이고, 이상치 채널이 스스로 완화된다

평가: 정확도는 충분한 지표가 아니다

"MMLU 0.3점 차이니까 문제없다"는 판단이 프로덕션에서 실패하는 이유. 양자화 모델을 검증하는 일은 일반적인 모델 평가와 다른 문제다.

집계 지표가 손실을 숨긴다

벤치마크 정확도는 argmax만 본다. 양자화로 어떤 문항은 틀리게 되고 어떤 문항은 우연히 맞게 되면, 평균은 그대로인데 모델의 행동은 크게 바뀐 상태가 된다. Perplexity도 안전하지 않다 — 일부 토큰의 확률 하락이 다른 토큰의 상승으로 상쇄되기 때문이다. 그래서 양자화 검증에는 원본 모델을 기준으로 한 분포 거리 지표가 반드시 함께 필요하다.

지표무엇을 보는가양자화 검증에서의 역할
Perplexity정답 토큰의 로그 확률빠른 회귀 감지용. 이것만으로 결정하지 말 것
KL divergence (vs FP16)전체 출력 분포의 차이핵심 지표. 상쇄가 일어나지 않는다. 토큰별로 분해해 원인 추적 가능
Flip rate / 정답 일치율원본이 맞힌 문항을 양자화 모델도 맞히는가같은 정확도 아래 숨은 행동 변화를 드러낸다
Top-1 일치율탐욕 디코딩에서 같은 토큰을 고르는 비율배포 전 스모크 테스트로 저렴하고 강력하다
과제 평가 (GSM8K, HumanEval, IFEval)실제 능력추론·코딩·지시 이행은 PPL과 상관이 낮다. 반드시 별도 측정
장문맥 (RULER, NIAH)긴 문맥 검색·추론KV 캐시를 양자화했다면 필수. 짧은 평가로는 절대 안 잡힌다
추론 모델의 함정 — 2026년에 새로 알려진 것

공격적인 저비트 양자화는 추론 모델의 사고 사슬을 길게 만들면서 정확도를 떨어뜨린다. 토큰 단위 KL 분해로 보면 발산이 집중되는 곳은 수식 토큰이 아니라 "wait", "but", "alternatively" 같은 망설임·분기 토큰이다. 그리고 이런 위치는 원본 모델이 이미 불확실했던(엔트로피가 높은) 지점과 강하게 상관된다.

실무적 함의: 실패의 상당 부분이 능력 손실이 아니라 결정 실패다 — 중간 단계에서 정답에 도달했는데도 확신하지 못해 계속 탐색한다. 따라서 추론 모델은 ① 정확도와 함께 평균 출력 토큰 수를 반드시 측정하고, ② FP8 이상에서 시작하고, ③ 4비트가 필요하면 출력 길이 예산을 함께 검증하라.

# 두 모델을 순차로 올려 로짓을 비교한다 (동시에 올릴 VRAM이 있으면 더 간단)
import torch, json, numpy as np
from transformers import AutoModelForCausalLM, AutoTokenizer

BASE = "meta-llama/Llama-3.1-8B-Instruct"
QUANT = "./Llama-3.1-8B-Instruct-W4A16"
N_PROMPT, MAX_TOK = 300, 128

tok = AutoTokenizer.from_pretrained(BASE)
prompts = [json.loads(l)["text"] for l in open("eval_prompts.jsonl")][:N_PROMPT]

def collect_logprobs(model_id):
    m = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.bfloat16,
                                             device_map="cuda").eval()
    out = []
    with torch.no_grad():
        for p in prompts:
            ids = tok(p, return_tensors="pt", truncation=True,
                      max_length=MAX_TOK).to("cuda")
            logits = m(**ids).logits[0].float()          # (seq, vocab)
            out.append(torch.log_softmax(logits, dim=-1).cpu())
    del m; torch.cuda.empty_cache()
    return out

lp_base = collect_logprobs(BASE)
lp_quant = collect_logprobs(QUANT)

kls, top1, top5 = [], [], []
for a, b in zip(lp_base, lp_quant):
    p = a.exp()
    # KL(P_base || P_quant) — 기준 모델을 P에 두는 방향이 관례
    kls.append((p * (a - b)).sum(-1).mean().item())
    top1.append((a.argmax(-1) == b.argmax(-1)).float().mean().item())
    t5 = a.topk(5, dim=-1).indices
    top5.append((t5 == b.argmax(-1, keepdim=True)).any(-1).float().mean().item())

print(f"평균 KL          : {np.mean(kls):.5f} nats")
print(f"KL p95           : {np.percentile(kls, 95):.5f} nats")
print(f"Top-1 일치율     : {np.mean(top1):.4f}")
print(f"기준 Top-5 포함율: {np.mean(top5):.4f}")

진단: 증상에서 원인으로

현장에서 실제로 마주치는 증상들과, 그 원인을 좁혀가는 순서. 각 항목을 열어 확인하세요.

증상 4비트 양자화 후 모델이 같은 단어를 반복하거나 의미 없는 문자열을 출력한다

1순위 — lm_head를 양자화했는가. 출력층 오차는 로짓에 직접 반영되고 어휘 크기가 커서 증폭된다. ignore=["lm_head"]를 확인하라. 임베딩도 마찬가지다.

2순위 — 캘리브레이션이 실패했는가. 데이터셋 전처리가 잘못돼 빈 문자열이나 패딩 토큰만 흘러갔다면 헤시안이 무의미해진다. 캘리브레이션 배치를 실제로 디코딩해서 눈으로 확인하라.

3순위 — group_size와 in_features 불일치. 나누어지지 않는데 조용히 패딩된 경우 마지막 그룹의 스케일이 오염된다.

4순위 — 아키텍처 미지원. 새 모델(MoE, 하이브리드 어텐션, 멀티모달)은 라우터·게이트·비전 타워를 양자화 대상에서 빼야 하는 경우가 많다. 라이브러리 예제의 ignore 목록을 그대로 가져오는 게 안전하다.

증상 PPL은 거의 그대로인데 GSM8K/HumanEval만 크게 떨어졌다

전형적인 캘리브레이션 분포 불일치다. 위키텍스트로 캘리브레이션한 뒤 추론·코드 과제를 재는 경우가 대표적이다. 대상 모델의 실제 사용 분포(채팅 + 코드 + 대상 언어)를 섞고 chat template을 적용해서 다시 만들어라.

그래도 회복되지 않으면: ① group_size를 128 → 64로 ② actorder 활성화 ③ AWQ와 GPTQ를 각각 만들어 비교 ④ 그래도 부족하면 W4A16 대신 FP8 W8A8로 후퇴. 추론 모델이라면 평균 출력 토큰 수도 같이 재라 — 정확도 하락이 능력 손실이 아니라 과다 사고 때문일 수 있다.

증상 4비트인데 처리량이 BF16보다 낮다

먼저 커널을 확인하라. vLLM 로그에서 gptq_marlin / compressed-tensors 대신 느린 폴백 커널이 선택됐을 수 있다. 원인은 보통 group_size 비표준값, desc_act 재정렬, 또는 컴퓨트 capability 부족(SM < 8.0)이다.

다음으로 배치를 확인하라. 7장의 산술 강도 그래프대로, 배치가 임계값을 넘으면 W4A16의 이득은 원래 사라진다. 여기서 필요한 것은 더 낮은 가중치 비트가 아니라 활성화 양자화(W8A8/FP8)다.

마지막으로 KV 캐시. 문맥이 길면 가중치가 아니라 KV 트래픽이 지배한다. --kv-cache-dtype fp8이 가중치를 3비트로 내리는 것보다 효과적이다.

증상 짧은 대화는 정상인데 긴 문서를 넣으면 답변 품질이 무너진다

KV 캐시 양자화의 전형적 실패다. 원인 후보: ① 무보정 FP8 KV 스케일(기본값 1.0) ② attention sink 토큰이 양자화됨 ③ 캘리브레이션 시퀀스가 짧아 장문맥 통계가 반영되지 않음.

대응: llm-compressor로 긴 시퀀스(8K+)를 써서 k/v 스케일을 캘리브레이션하고, per-head 전략을 시도하고, 하이브리드 어텐션 모델이면 슬라이딩 윈도우 레이어를 제외하라. 검증은 반드시 RULER 같은 장문맥 벤치로 하라 — 짧은 평가에서는 절대 드러나지 않는다.

증상 QLoRA 파인튜닝은 잘 됐는데 배포 모델의 성능이 학습 때보다 나쁘다

거의 확실히 머지 순서 문제다. 어댑터를 4비트 베이스에 머지하면 양자화 오차 위에 어댑터를 얹은 뒤 다시 양자화하게 되어 오차가 이중으로 쌓인다.

올바른 순서: 4비트로 학습 → BF16 원본에 머지 → 머지된 BF16을 GPTQ/AWQ로 재양자화. 8장의 3단계 스크립트를 그대로 쓰면 된다. 그래도 낙차가 크면 QAT 파인튜닝을 검토하라.

증상 같은 모델의 HF 양자화 체크포인트가 내 환경에서 로드되지 않는다

체크포인트 포맷과 커널 요구사항의 불일치다. 확인 순서: ① config.json의 quantization_config에서 방식·그룹·대칭성 확인 ② 내 GPU의 compute capability(INT4 혼합 정밀도는 SM 8.0+, FP8은 8.9+, FP4는 10.0+) ③ 엔진 버전 ④ MoE 모델이면 전용 환경변수(VLLM_USE_FLASHINFER_MOE_FP4=1 등).

정말 급하면 bitsandbytes로 즉석 로드하고 나중에 제대로 만들어라. 느리지만 거의 모든 환경에서 뜬다.
