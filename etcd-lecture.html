01

etcd는 무엇이고, 쿠버네티스에서 무엇을 하나

먼저 큰 그림. etcd가 없으면 무슨 일이 벌어지는지부터 봅니다.

etcd는 분산 키-값 저장소입니다. 이름은 유닉스의 설정 디렉터리 /etc에 분산(distributed)의 d를 붙인 것으로, 처음부터 "여러 대의 머신이 함께 쓰는 설정 저장소"를 목표로 만들어졌습니다. Go로 작성됐고 CNCF 졸업 프로젝트이며, 뒤에서 배울 Raft 합의 알고리즘으로 여러 노드가 똑같은 데이터를 유지합니다.

쿠버네티스는 이 etcd를 단일 진실 공급원(single source of truth)으로 씁니다. 클러스터에 존재하는 모든 오브젝트가 여기 저장됩니다.

etcd에 들어있는 것과 들어있지 않은 것

신입 엔지니어가 가장 자주 헷갈리는 지점입니다. etcd는 "클러스터의 설계도와 대장부"를 보관하지, "실제로 돌아가는 프로세스"를 보관하지 않습니다.

etcd는 회사의 공식 문서 보관소입니다. "3층에 개발팀 자리를 5개 만든다"는 결재 문서가 여기 보관됩니다. 실제로 책상을 놓고 사람이 앉는 일은 각 노드(kubelet)가 합니다. 문서와 현실이 다르면, 컨트롤러들이 현실을 문서에 맞추려고 계속 일합니다. 이것이 쿠버네티스의 선언형(declarative) 동작 방식이고, etcd는 그 "선언"이 적힌 곳입니다.

etcd가 멈추면 어떻게 되나

많은 사람이 "etcd 죽으면 서비스가 다 죽는다"고 생각하지만, 정확하지 않습니다. 아래를 눌러 확인해 보세요.

왼쪽 항목 중 하나를 누르면 etcd가 완전히 멈춘 상태에서 그 기능이 어떻게 되는지 설명합니다.

정리하면, etcd 장애는 즉각적인 서비스 중단이 아니라 클러스터의 모든 변경·복구 능력 상실입니다. 이미 뜬 Pod는 계속 요청을 처리하지만, 그 뒤로 하나라도 죽으면 아무도 다시 살려주지 못합니다. 그래서 etcd 장애는 "조용히 시작해서 서서히 치명적으로" 번집니다.

기억할 한 문장

etcd는 쿠버네티스에서 상태를 가진 유일한 컴포넌트입니다. apiserver·scheduler·controller-manager는 죽어도 새로 띄우면 끝이지만, etcd 데이터가 사라지면 클러스터 그 자체가 사라집니다.

02

데이터 모델: 키 구조, MVCC, 리스, 워치

etcd를 열어보면 실제로 어떤 모양의 데이터가 들어있는지 봅니다.

키는 경로처럼 보이지만 그냥 문자열입니다

쿠버네티스는 모든 오브젝트를 아래 규칙의 키로 저장합니다.

# 네임스페이스가 있는 리소스 /registry/{리소스}/{네임스페이스}/{이름} → /registry/pods/default/nginx-7c5b8d9f4-x2k9m # 클러스터 범위 리소스 /registry/{리소스}/{이름} → /registry/namespaces/kube-system → /registry/clusterroles/cluster-admin

etcd 자체는 디렉터리 개념이 없습니다. 위 키들은 그냥 슬래시가 들어간 문자열이고, etcd는 정렬된 키 범위 조회를 지원하기 때문에 /registry/pods/default/로 시작하는 키를 한 번에 긁어오는 식으로 "디렉터리처럼" 씁니다. kubectl get pods -n default가 내부적으로 하는 일이 바로 이 범위 조회입니다.

# 선택 대기 중
값을 읽으면 글자가 깨져 보입니다

쿠버네티스는 오브젝트를 JSON이 아니라 protobuf(바이너리)로 직렬화해서 저장합니다. 그래서 etcdctl get으로 값을 꺼내면 알아볼 수 없는 바이트가 섞여 나옵니다. 사람이 읽으려면 auger 같은 디코더를 함께 씁니다. 물론 실무에서 etcd 값을 직접 파헤칠 일은 거의 없고, 있어도 대개 장애 분석 상황입니다.

MVCC와 revision: etcd는 덮어쓰지 않고 쌓습니다

etcd v3는 MVCC(다중 버전 동시성 제어)를 씁니다. 키를 수정해도 이전 값을 즉시 지우지 않고, 새 버전을 추가합니다. 이때 클러스터 전체에 하나뿐인 카운터가 올라가는데 이것이 revision입니다.

  • revision — 클러스터 전역 카운터. 어떤 키든 쓰기가 일어나면 1 증가합니다.
  • create_revision — 그 키가 처음 생성된 시점의 revision.
  • mod_revision — 그 키가 마지막으로 수정된 시점의 revision.
  • version — 그 키가 몇 번 수정됐는지 세는 키 단위 카운터.

revision이 전역이라는 점이 중요합니다. 덕분에 "revision 4180 시점의 클러스터 전체 상태"라는 일관된 스냅샷을 말할 수 있고, "revision 4180 이후에 바뀐 것만 알려줘"라는 요청도 가능합니다. 쿠버네티스의 resourceVersion이 바로 이 revision을 감싼 값입니다.

컴팩션: 무한히 쌓을 수는 없으니

버전이 계속 쌓이면 디스크가 남지 않습니다. 그래서 오래된 revision을 정리하는 컴팩션(compaction)이 필요합니다. 쿠버네티스에서는 kube-apiserver가 이 일을 대신 해줍니다(기본 5분 간격, --etcd-compaction-interval). 컴팩션된 revision보다 오래된 시점을 조회하면 오류가 납니다.

$ etcdctl get /registry/deployments/default/web --rev=1200 Error: etcdserver: mvcc: required revision has been compacted

컴팩션은 "버전 기록을 지우는" 작업이고, 그렇게 생긴 빈 공간을 실제로 파일 시스템에 반환하는 것은 디프래그(defrag)라는 별개 작업입니다. 이 둘의 차이는 6장과 10장에서 다시 나옵니다.

리스(lease): 시간이 지나면 사라지는 키

etcd는 키에 TTL을 직접 걸지 않고, 리스라는 객체에 TTL을 걸고 키를 그 리스에 붙입니다. 리스가 만료되면 붙어 있던 키들이 함께 삭제됩니다. 클라이언트가 살아있는 동안에는 keep-alive 신호를 보내 리스를 갱신합니다.

쿠버네티스에서 대표적인 사용처는 Event 만료입니다. Event는 기본적으로 1시간 뒤 자동으로 사라지는데, 이 만료를 etcd 리스가 처리합니다.

비슷한 이름, 다른 물건

쿠버네티스에 coordination.k8s.io/v1 Lease라는 리소스가 있습니다. kubelet 하트비트와 컨트롤러 리더 선출에 쓰이죠. 이것은 etcd의 리스와 이름만 같고 다른 개념입니다. 쿠버네티스 Lease는 그저 평범한 오브젝트이고, etcd에는 /registry/leases/... 키로 저장됩니다. 면접에서 종종 나오는 함정입니다.

워치(watch): 폴링하지 않고 변경만 받기

etcd는 "이 revision 이후에 이 키 범위에서 일어난 변경을 계속 스트리밍해 줘"라는 요청을 지원합니다. 이것이 워치이고, 쿠버네티스 전체가 이 위에서 돌아갑니다. 스케줄러가 새 Pod를 몇 밀리초 만에 알아채는 이유가 폴링이 아니라 워치이기 때문입니다. 자세한 흐름은 5장에서 다룹니다.

트랜잭션과 낙관적 동시성

etcd는 "조건이 맞으면 쓰고, 아니면 실패시켜라"는 트랜잭션(Txn, compare-and-swap)을 제공합니다. 쿠버네티스는 이것으로 동시 수정 충돌을 막습니다.

  1. 클라이언트 A와 B가 같은 Deployment를 읽습니다. 둘 다 resourceVersion: 4180을 받습니다.
  2. A가 수정해서 저장합니다. apiserver는 "mod_revision이 여전히 4180이면 써라"라는 조건부 쓰기를 보냅니다. 성공. 이제 4192가 됩니다.
  3. B가 수정해서 저장합니다. 조건이 깨졌으므로 실패합니다.
  4. B는 409 Conflict 응답을 받습니다. 흔히 보는 the object has been modified; please apply your changes to the latest version 메시지가 이것입니다.

즉 그 짜증나는 409 오류는 버그가 아니라, etcd 트랜잭션이 데이터를 지켜준 결과입니다.

03

Raft 합의 알고리즘

여러 대가 어떻게 "같은 데이터"를 유지하는가. 이 강의의 핵심입니다.

etcd 클러스터는 3대든 5대든, 모든 멤버가 완전히 같은 데이터를 갖습니다. 그런데 네트워크는 끊기고 디스크는 느려지고 프로세스는 죽습니다. 이런 환경에서 "무엇이 진짜인가"를 다수결로 정하는 규칙이 Raft입니다.

세 가지 역할과 term

  • 리더(Leader) — 클러스터에 단 하나. 모든 쓰기는 리더를 거칩니다. 팔로워에게 주기적으로 하트비트를 보냅니다.
  • 팔로워(Follower) — 리더의 명령을 받아 자기 로그에 복제합니다. 평상시 대부분의 멤버가 이 상태입니다.
  • 후보(Candidate) — 리더 하트비트가 끊겨서 선거에 나선 상태. 잠깐만 존재합니다.

term은 "몇 번째 임기인가"를 나타내는 번호입니다. 선거가 열릴 때마다 1씩 올라가고, 한 term에는 리더가 최대 하나만 존재합니다. 오래된 term의 메시지는 무조건 무시되기 때문에, 죽었다 살아난 옛 리더가 혼란을 일으킬 수 없습니다.

리더 선출은 이렇게 일어납니다

  1. 팔로워가 election timeout(기본 1000ms) 동안 하트비트를 못 받습니다.
  2. 스스로 후보가 되어 term을 +1 하고, 자기 자신에게 투표한 뒤 모두에게 투표를 요청합니다.
  3. 과반의 표를 얻으면 리더가 되어 즉시 하트비트를 보냅니다.
  4. 표가 갈려 아무도 과반을 못 얻으면, 각 노드가 무작위 시간을 기다린 뒤 다시 시도합니다. 타임아웃을 랜덤화하는 이 장치가 무한 재선거를 막습니다.

쓰기 한 건이 처리되는 순서

  1. 클라이언트(=kube-apiserver)가 리더에게 쓰기를 보냅니다. 팔로워에게 보냈다면 리더로 전달됩니다.
  2. 리더가 자기 WAL(로그 파일)에 기록하고 디스크에 확실히 내려씁니다(fsync).
  3. 동시에 팔로워들에게 그 로그 항목을 보냅니다.
  4. 팔로워도 각자 디스크에 기록하고 "받았다"고 응답합니다.
  5. 리더가 과반의 응답을 확인하면 그 항목을 커밋으로 표시합니다.
  6. 커밋된 항목을 실제 저장소(상태 머신)에 적용하고 클라이언트에 성공을 응답합니다.

여기서 2번과 4번의 디스크 쓰기가 etcd 성능의 전부라고 해도 과장이 아닙니다. 6장에서 다시 나옵니다.

learner 멤버

새 멤버를 클러스터에 넣으면 처음엔 데이터를 따라잡느라 느립니다. 이때 곧바로 투표권을 주면 정족수 계산에는 포함되는데 실제로는 뒤처져 있어서 클러스터가 불안해집니다. 그래서 etcd에는 learner(투표권 없는 견습 멤버)가 있습니다. 데이터를 다 따라잡은 뒤 etcdctl member promote로 정식 멤버로 승격시키는 것이 안전한 멤버 추가 방법입니다.

04

몇 대로 구성해야 하나: 정족수와 장애 허용

왜 항상 3대, 5대, 7대일까요. 4대는 왜 3대보다 나쁠까요.

Raft는 모든 결정에 과반(quorum)의 동의를 요구합니다. 멤버가 N개일 때 정족수는 이렇게 계산합니다.

정족수(quorum) = ⌊N / 2⌋ + 1 견딜 수 있는 장애 수 = N − 정족수 = ⌊(N − 1) / 2⌋

과반을 요구하는 이유는 스플릿 브레인 방지입니다. 과반은 정의상 두 그룹에 동시에 존재할 수 없으므로, 네트워크가 갈라져도 리더는 한쪽에만 생깁니다. 나머지 쪽은 쓰기를 거부하며 조용히 대기합니다. 데이터가 두 갈래로 갈라지는 최악의 상황을 이 규칙 하나가 막아줍니다.

핵심은 이렇습니다. 멤버를 홀수에서 짝수로 하나 늘리면 장애 허용은 그대로인데 정족수는 커집니다. 즉 "성공을 위해 동의를 받아야 하는 대수"만 늘어나서 쓰기가 느려지고, 고장 날 수 있는 하드웨어만 하나 늘어납니다. 그래서 항상 홀수입니다.

많을수록 좋은 것이 아닙니다

etcd는 모든 멤버가 모든 데이터를 갖는 복제 클러스터이지, 데이터를 쪼개 나누는 샤딩 클러스터가 아닙니다. 멤버를 늘리면 읽기 처리량과 내구성은 늘지만, 모든 쓰기가 더 많은 노드의 디스크를 기다려야 하므로 쓰기는 반드시 느려집니다. 3대로 시작해서, 여러 AZ에 분산해야 하거나 컨트롤 플레인이 아주 크면 5대로 갑니다. 7대 이상은 흔치 않습니다.

AZ 배치 감각

3개 AZ에 3대를 1:1:1로 놓으면 AZ 하나가 통째로 죽어도 2대가 남아 정족수를 유지합니다. 반대로 AZ 두 곳에 2:1로 놓으면, 2대가 있는 AZ가 죽는 순간 정족수를 잃습니다. 대수만 맞추지 말고 어디에 놓는지까지 봐야 합니다.

05

kube-apiserver와의 관계

etcd에 직접 말을 거는 컴포넌트는 딱 하나입니다.

쿠버네티스 컨트롤 플레인의 규칙은 단순합니다.

etcd에 직접 접근하는 컴포넌트는 kube-apiserver 뿐이다. kube-scheduler ─┐ kube-controller-manager ├─→ kube-apiserver ─→ etcd kubelet / kube-proxy │ kubectl / 오퍼레이터 ─┘

scheduler도, controller-manager도, kubelet도 etcd 주소를 아예 모릅니다. 전부 apiserver의 REST API만 사용합니다. 왜 이렇게 만들었을까요?

  • 인증과 인가 — 누가 무엇을 할 수 있는지(RBAC)를 apiserver가 판단합니다. etcd에 직접 붙으면 이 검사를 전부 우회합니다.
  • 검증과 기본값 — 잘못된 필드를 거르고 기본값을 채우는 일도 apiserver가 합니다.
  • 어드미션 제어 — 사이드카 주입, 정책 검사, 리소스 쿼터 같은 웹훅이 여기서 돕니다.
  • API 버전 변환 — v1beta1로 만들어도 v1로 읽을 수 있게 변환해 주는 계층입니다.
  • 저장 형식 은닉 — 키 구조나 직렬화 방식이 바뀌어도 사용자는 영향받지 않습니다.
etcd에 직접 쓰지 마세요

etcdctl로 /registry 아래 값을 직접 수정하는 것은 기술적으로 가능하지만, 검증·어드미션·워치 캐시를 모두 건너뛰기 때문에 클러스터를 조용히 망가뜨릴 수 있습니다. 읽기(진단 목적)는 괜찮습니다. 쓰기는 최후의 재해 복구 상황에서만, 그것도 백업을 뜬 뒤에 합니다.

list-watch 패턴: 쿠버네티스가 실시간으로 돌아가는 방법

모든 컨트롤러는 같은 패턴으로 동작합니다. 먼저 전체 목록을 한 번 받고(list), 그 다음부터는 변경만 스트리밍으로 받습니다(watch). 아래에서 한 단계씩 따라가 보세요.

워치 캐시: etcd를 지켜주는 방화벽

클러스터에 informer가 수백 개 떠 있다고 해서 etcd에 워치가 수백 개 열리지는 않습니다. apiserver가 리소스 종류별로 etcd 워치를 하나만 열고, 받은 이벤트를 메모리 캐시에 유지하며 모든 클라이언트에게 나눠줍니다. 이 워치 캐시가 없다면 etcd는 진작에 무너졌을 것입니다.

그래서 resourceVersion 파라미터가 성능에 직접 영향을 줍니다.

모니터링 도구나 자체 개발한 오퍼레이터가 큰 리소스를 주기적으로 전체 조회(list)하도록 짜여 있으면 etcd에 상당한 부하가 됩니다. 특히 기본 옵션으로 매초 전체 Pod를 긁는 코드는 대형 클러스터에서 etcd 지연의 흔한 원인입니다. 해법은 informer(list-watch)를 쓰거나, 최소한 resourceVersion=0으로 캐시에서 읽는 것입니다.

410 Gone은 무엇인가

워치를 오래 끊고 있다가 아주 오래된 resourceVersion으로 다시 연결하면, 그 지점의 기록이 이미 컴팩션되어 사라졌을 수 있습니다. 그러면 apiserver가 410 Gone을 돌려주고, informer는 "따라잡기를 포기하고 처음부터 전체 목록을 다시 받는(relist)" 동작을 합니다. 컨트롤러 로그에서 too old resource version을 보게 되는 상황이고, 대개 정상적인 자기 치유 과정입니다.

06

성능: 디스크가 곧 클러스터 속도

etcd 튜닝의 90%는 디스크 이야기입니다. 나머지가 네트워크와 크기 관리입니다.

3장에서 본 쓰기 절차를 다시 떠올려 보세요. 리더와 팔로워가 각자 WAL에 기록하고 fsync를 해야 커밋이 됩니다. fsync는 "OS 버퍼가 아니라 진짜 디스크에 안전하게 저장됐음"을 보장하는 동기 호출이고, 그동안 그 쓰기는 아무것도 진행하지 못합니다.

따라서 디스크 fsync 지연 = etcd 쓰기 지연 = apiserver 응답 지연 = kubectl 체감 속도입니다. HDD에 etcd를 올린 클러스터는 예외 없이 느립니다.

디스크 실전 권장

  • SSD 이상 필수. 로컬 NVMe가 가장 좋습니다.
  • etcd에 디스크를 전용으로. 컨테이너 이미지 풀, 로그 수집, 빌드 캐시와 같은 디스크를 쓰면 그쪽 폭주가 그대로 클러스터 지연이 됩니다.
  • WAL을 분리할 수 있으면 --wal-dir로 별도 디스크에 둡니다. WAL은 순차 쓰기라 다른 IO와 섞이면 특히 손해입니다.
  • 네트워크 파일시스템 금지. NFS 위 etcd는 안정적으로 동작하지 않습니다.
  • 클라우드에서는 IOPS와 처리량이 보장된 볼륨을 씁니다. 버스트 크레딧에 의존하는 볼륨은 크레딧이 소진되는 순간 클러스터가 느려집니다.

네트워크와 타임아웃

멤버 간 왕복 시간(RTT)이 크면 하트비트가 늦게 도착해 불필요한 선거가 열립니다. 이때 조정하는 두 값이 있습니다.

  • --heartbeat-interval (기본 100ms) — 리더가 하트비트를 보내는 주기. 멤버 간 최대 RTT 정도로 맞춥니다.
  • --election-timeout (기본 1000ms) — 이 시간 동안 하트비트가 없으면 선거. 하트비트 간격의 10배 이상으로 둡니다.

둘은 반드시 함께 조정하고, 모든 멤버에 동일하게 설정합니다. 지연이 큰 원거리 구성이라면 값을 키워야 하지만, 그만큼 장애 감지가 늦어집니다.

리전을 넘나드는 etcd는 피하세요

모든 쓰기가 과반의 응답을 기다린다는 사실을 기억하면, 리전 간 100ms 지연이 곧 쓰기 지연이 됩니다. 여러 AZ에 분산하는 것은 권장되지만(같은 리전 내 수 ms), 여러 리전에 걸친 하나의 etcd 클러스터는 일반적으로 권장되지 않습니다. 리전 이중화가 필요하면 클러스터를 나누고 상위에서 페더레이션하는 편이 낫습니다.

DB 크기 관리: 컴팩션과 디프래그

etcd에는 저장소 크기 상한이 있습니다(--quota-backend-bytes, 기본 2GiB, 권장 상한 8GiB). 넘으면 클러스터가 NOSPACE 알람을 걸고 쓰기를 전부 거부합니다. 읽기만 가능한 상태가 되죠. 실제로 자주 겪는 사고입니다.

DB 크기와 NOSPACE 알람

슬라이더로 DB 크기를 늘려보세요

컴팩션은 오래된 revision 기록을 지우는 것이고, 디프래그는 그렇게 비워진 공간을 파일시스템에 실제로 반환하는 것입니다. 컴팩션만 하면 파일 크기는 줄지 않습니다. 디프래그는 그 멤버를 잠시 멈추게 하므로 한 번에 한 멤버씩, 트래픽이 적은 시간에 수행합니다.

etcd를 뚱뚱하게 만드는 흔한 범인들

  • Event 폭주 — CrashLoopBackOff가 대량으로 발생하면 Event가 초당 수백 건 쌓입니다. Event만 별도 etcd로 분리하는 옵션(--etcd-servers-overrides)도 있습니다.
  • 거대한 ConfigMap·Secret — 인증서 번들이나 데이터 파일을 ConfigMap에 넣는 습관. 단일 요청 크기 제한도 기본 1.5MiB로 넉넉하지 않습니다.
  • 정리되지 않은 Job·Pod — 완료된 Job이 수만 개 남아 있는 클러스터가 흔합니다. ttlSecondsAfterFinished를 설정하세요.
  • CRD 남용 — 오퍼레이터가 상태를 초 단위로 업데이트하면 revision이 폭발적으로 늘어납니다.
  • Helm 릴리스 히스토리 — Secret으로 저장되며 무한히 쌓입니다. --history-max를 지정하세요.

고가용성 토폴로지: 스택드 vs 외부

etcd를 컨트롤 플레인 노드에 함께 둘지, 따로 둘지 결정합니다.

kubeadm으로 HA 클러스터를 만들 때 선택하는 두 가지 구성입니다. 아래 토글로 비교해 보세요.

토폴로지 비교

장점

    단점

      스택드 구성에서 노드 하나를 잃으면

      컨트롤 플레인 노드 3대에 etcd가 함께 올라간 구성에서 노드 1대가 죽으면, apiserver 한 대와 etcd 멤버 한 대를 동시에 잃습니다. 3대 중 2대가 남았으니 정족수는 유지되고 클러스터는 정상 동작합니다. 하지만 이제 여유가 없습니다. 한 대만 더 죽으면 정족수를 잃고 쓰기가 멈춥니다. 그래서 스택드 구성에서 노드 복구는 급한 일입니다.

      외부 etcd 구성이라면 컨트롤 플레인 노드가 죽어도 etcd 클러스터는 온전합니다. 반대로 관리할 머신은 최소 6대(컨트롤 플레인 3 + etcd 3)가 되어 비용과 운영 부담이 늘어납니다.

      멤버를 안전하게 교체하는 순서

      1. 먼저 스냅샷 백업을 뜹니다. 예외 없이.
      2. 죽은 멤버를 클러스터에서 제거합니다: etcdctl member remove {ID}
      3. 새 멤버를 learner로 추가합니다: etcdctl member add {이름} --learner --peer-urls=...
      4. 새 노드에서 etcd를 --initial-cluster-state=existing으로 기동합니다.
      5. 데이터를 따라잡았는지 확인한 뒤 승격: etcdctl member promote {ID}
      6. etcdctl endpoint status --cluster -w table로 전체 상태를 확인합니다.
      먼저 제거, 그 다음 추가

      죽은 멤버를 제거하지 않고 새 멤버를 먼저 추가하면 정족수 계산이 순간적으로 불리해집니다. 예를 들어 3대 중 1대가 죽은 상태(살아있는 2, 정족수 2)에서 멤버를 추가하면 총 4대가 되어 정족수가 3으로 올라가는데, 새 멤버는 아직 따라잡지 못했습니다. 그 순간 클러스터는 쓰기를 잃습니다. remove 먼저, add 나중이 원칙입니다.

      HA와 백업은 서로를 대체하지 않습니다

      3노드 HA는 하드웨어 장애를 막아줍니다. 하지만 누군가 kubectl delete ns production을 실행하면 그 삭제는 3대 모두에 완벽하게 복제됩니다. 실수와 논리적 오류를 되돌리는 것은 백업의 일입니다. 반대로 백업만 있으면 복구에 수십 분이 걸립니다. 둘 다 필요합니다.

      백업과 복구

      운영에서 가장 중요한 챕터입니다. 명령을 눌러가며 절차를 익히세요.

      etcd 백업은 스냅샷 한 개 파일로 끝납니다. 멤버 전부가 같은 데이터를 갖고 있으므로 아무 한 멤버에서만 뜨면 됩니다.

      실습: 백업에서 복구까지

      복구가 백업보다 훨씬 어렵습니다

      복구에서 반드시 알아야 할 성질이 있습니다.

      • 복구는 새 클러스터를 만듭니다. snapshot restore는 새 데이터 디렉터리를 만들고 새 클러스터 ID를 부여합니다. 기존 클러스터에 "되돌리기"를 적용하는 것이 아닙니다.
      • 모든 멤버에서 각자 복구해야 합니다. 같은 스냅샷 파일로, 각 노드에 맞는 --name과 --initial-advertise-peer-urls를 주고, --initial-cluster에는 전체 멤버 목록을 동일하게 지정합니다.
      • 순서를 지켜야 합니다. apiserver를 먼저 내리고(스택드라면 매니페스트를 옮겨서), 모든 etcd 멤버를 복구·기동한 다음, apiserver를 올립니다. apiserver가 복구 중인 etcd에 붙으면 상태가 뒤섞입니다.
      • 스냅샷 이후의 변경은 사라집니다. 백업 주기가 복구 시 잃는 데이터의 크기입니다.
      스냅샷이 담지 못하는 것

      etcd 스냅샷은 쿠버네티스 오브젝트만 담습니다. PersistentVolume 안의 실제 데이터, 데이터베이스 내용, 노드의 로컬 파일은 들어있지 않습니다. etcd를 되돌리면 "PVC 오브젝트는 존재하는데 그 안의 데이터는 스냅샷 이후 상태" 같은 불일치가 생깁니다. 상태를 가진 워크로드가 있다면 애플리케이션 수준 백업(볼륨 스냅샷, DB 덤프)이 반드시 함께 있어야 합니다.

      etcdctl과 etcdutl

      etcd 3.5부터 도구가 둘로 나뉘었습니다. 헷갈리기 쉬운 부분입니다.

      도구대상대표 명령
      etcdctl동작 중인 클러스터에 네트워크로 접속get, put, member list, endpoint status, snapshot save, defrag
      etcdutl로컬 파일(스냅샷, 데이터 디렉터리)을 직접 조작snapshot restore, snapshot status, defrag --data-dir

      정리하면 백업은 etcdctl(살아있는 클러스터에서), 복구는 etcdutl(파일에서)입니다. 구버전 습관대로 etcdctl snapshot restore를 쓰면 경고가 나옵니다. 사용 중인 etcd 버전의 문서를 확인하는 것이 가장 확실합니다.

      운영 체크리스트

      • 스냅샷을 자동화합니다. CronJob이나 systemd timer로 최소 하루 1회, 중요 클러스터는 시간 단위로.
      • 스냅샷을 다른 곳에 보관합니다. etcd 노드 로컬 디스크에만 두면 노드와 함께 사라집니다. 오브젝트 스토리지로 올리세요.
      • 복구 리허설을 정기적으로 합니다. 한 번도 복구해 본 적 없는 백업은 백업이 아니라 희망입니다.
      • 백업 성공 여부를 모니터링합니다. 조용히 실패한 백업이 가장 위험합니다.
      • 업그레이드나 대규모 변경 직전에 수동 스냅샷을 하나 더 뜹니다.
      Velero와는 무엇이 다른가

      etcd 스냅샷은 클러스터 전체를 한 시점으로 되돌리는 물리적 백업입니다. 반면 Velero 같은 도구는 apiserver를 통해 오브젝트를 논리적으로 백업하므로 네임스페이스 단위 복구나 다른 클러스터로 이전이 가능하고, 볼륨 스냅샷도 함께 다룹니다. 컨트롤 플레인 재해에는 etcd 스냅샷, 특정 워크로드 실수 복구와 마이그레이션에는 Velero가 맞습니다. 실무에서는 둘 다 씁니다.

      09

      보안: 인증서, 접근 통제, 저장 암호화

      etcd에 접근할 수 있으면 클러스터를 전부 가진 것과 같습니다.

      왜 이 챕터가 중요한가

      etcd를 읽을 수 있다면 모든 네임스페이스의 모든 Secret을 평문으로 볼 수 있습니다. DB 비밀번호, 클라우드 자격 증명, TLS 개인키 전부입니다. RBAC은 apiserver의 기능이므로 etcd 직접 접근에는 아무 효과가 없습니다. etcd 보안은 클러스터 보안의 마지막 방어선이 아니라, 사실상 유일한 방어선입니다.

      두 종류의 TLS

      etcd는 서로 다른 두 통신에 각각 TLS를 씁니다. 둘 다 클라이언트 인증서를 요구하는 상호 TLS(mTLS)로 설정합니다.

      • 클라이언트 ↔ 서버 (포트 2379) — kube-apiserver와 etcdctl이 붙는 경로.
      • 피어 ↔ 피어 (포트 2380) — etcd 멤버들이 Raft 메시지를 주고받는 경로.

      kubeadm으로 만든 클러스터에는 인증서가 /etc/kubernetes/pki/etcd/에 있습니다. 아래에서 각 파일의 역할을 확인하세요.

      인증서 지도

      파일을 눌러 역할을 확인하세요
      파일을 선택하세요

      kubeadm 기본 경로 기준으로 각 인증서가 어떤 통신에 쓰이는지 설명합니다.

      네트워크와 호스트 통제

      • etcd 포트(2379, 2380)는 컨트롤 플레인·etcd 노드끼리만 열립니다. 워커 노드나 사내망 전체에 열려 있다면 즉시 조치 대상입니다.
      • --listen-client-urls를 0.0.0.0으로 두면서 방화벽이 없는 구성은 사고로 이어집니다.
      • etcd 노드에 SSH로 들어갈 수 있는 사람은 클러스터 관리자와 동급입니다. 인증서 파일을 그냥 읽을 수 있으니까요. 계정과 감사 로그를 그 기준으로 관리하세요.
      • etcd는 자체 인증(사용자·역할) 기능도 있지만, 쿠버네티스에서는 클라이언트가 apiserver 하나뿐이라 보통 인증서 기반 통제로 충분합니다.

      저장 데이터 암호화는 etcd가 아니라 apiserver의 일

      가장 흔한 오해입니다. etcd는 데이터를 평문으로 디스크에 씁니다. Secret을 암호화해서 저장하려면 kube-apiserver에 암호화 설정을 붙여야 합니다.

      # EncryptionConfiguration 예시 (apiserver에 --encryption-provider-config로 지정) apiVersion: apiserver.config.k8s.io/v1 kind: EncryptionConfiguration resources: - resources: ["secrets"] providers: - kms: # 가장 권장. 키를 외부 KMS에 보관 name: my-kms endpoint: unix:///var/run/kms.sock - identity: {} # 평문. 마이그레이션 중 읽기용으로 마지막에 둠

      providers는 순서가 의미를 갖습니다. 쓰기에는 항상 첫 번째 provider를 사용하고, 읽기는 목록을 순서대로 시도합니다. 그래서 암호화를 새로 켤 때는 실제 provider를 맨 위에, identity를 아래에 두고, 설정 후 기존 오브젝트를 다시 저장해 암호화를 적용합니다.

      # 설정 적용 후 기존 Secret을 다시 써서 암호화 반영 $ kubectl get secrets --all-namespaces -o json | kubectl replace -f -

      암호화 키를 apiserver 설정 파일에 직접 적는 aescbc/aesgcm 방식은 켜기는 쉽지만, 키가 같은 노드 디스크에 있으니 "노드를 통째로 탈취당하는" 위협에는 큰 도움이 못 됩니다. 가능하면 KMS provider를 쓰고, 디스크 자체 암호화도 별도 계층으로 함께 적용하세요.

      장애 대응: 증상에서 원인으로

      실제 로그에 찍히는 메시지 기준으로 정리했습니다. 당직 중에 열어보는 챕터입니다.

      먼저 상태를 확인하는 세 명령

      # 이후 명령에서 반복될 인증서 옵션을 변수로 $ export E="--cacert=/etc/kubernetes/pki/etcd/ca.crt \ --cert=/etc/kubernetes/pki/etcd/server.crt \ --key=/etc/kubernetes/pki/etcd/server.key" # 1. 멤버 목록과 ID $ etcdctl $E member list -w table # 2. 각 멤버의 상태 — 리더가 누구인지, DB 크기, 뒤처짐 여부 $ etcdctl $E --endpoints=https://10.0.1.11:2379,https://10.0.1.12:2379,https://10.0.1.13:2379 \ endpoint status -w table # 3. 헬스체크와 알람 $ etcdctl $E endpoint health --cluster $ etcdctl $E alarm list

      endpoint status의 표에서 특히 볼 것은 IS LEADER(리더가 정확히 하나인가), RAFT INDEX(멤버 간 차이가 크면 뒤처진 멤버가 있음), DB SIZE, ERRORS 열입니다.

      당직 중 판단 순서

      etcd 문제로 의심되면 순서대로 확인하세요. ① endpoint health로 정족수가 살아있는지 → ② alarm list로 NOSPACE 여부 → ③ fsync·커밋 지연 지표로 디스크 상태 → ④ leader_changes로 선거 반복 여부 → ⑤ 인증서 유효기간. 그리고 무엇을 바꾸기 전에 스냅샷을 뜨세요. 대응 중 상태를 더 망가뜨리는 것이 가장 흔한 2차 사고입니다.
