    CHAPTER 02

    무엇이 실제로 쓰이는가

    절감의 출발점은 압축이나 샘플링이 아니라 사용되지 않는 데이터를 찾는 것입니다.

    쓰이지 않는 데이터는 생각보다 많다

    업계에서 반복해서 나오는 관찰은 수집된 메트릭의 상당 부분이 한 번도 조회되지 않는다는 것입니다. 2026년 옵저버빌리티 커뮤니티 논의에서는 오늘날 수집되는 메트릭의 절반가량이 한 번도 질의되지 않는다는 주장이 나왔습니다. 중요한 것은 정확한 비율이 아니라, 측정해보면 우리 환경에도 비슷한 구간이 있다는 점입니다.

    사용률을 실제로 측정하는 방법

    1. 대시보드·알림 규칙 파싱 — 모든 대시보드 JSON과 알림 규칙에서 참조하는 메트릭 이름을 추출합니다
    2. 질의 로그 수집 — 저장소의 질의 로그에서 지난 90일간 실제로 조회된 메트릭·라벨을 집계합니다
    3. 수집 중인 목록과 대조 — 수집되지만 어디에도 등장하지 않는 항목이 1차 삭제 후보입니다
    4. 삭제 전 유예 — 바로 지우지 말고 30일간 "폐기 예정" 목록으로 공지한 뒤 반응이 없으면 제거합니다
    사용되지 않는 메트릭 찾기 — 개념 스크립트
    # 1) 현재 수집 중인 메트릭 이름
ingested = set(prom.label_values("__name__"))

# 2) 대시보드·알림에서 참조되는 이름
referenced = set()
for d in grafana.list_dashboards():
    referenced |= extract_metric_names(json.dumps(d))       # PromQL 파싱
for r in prom.rules():
    referenced |= extract_metric_names(r.expr)

# 3) 최근 90일 질의 로그에서 실제 조회된 이름
queried = set(query_log.metric_names(days=90))

unused = ingested - referenced - queried
print(f"미사용 후보 {len(unused)}개 / 전체 {len(ingested)}개")

# 4) 시계열 수 기준으로 정렬 — 비용 영향이 큰 것부터 처리
for m in sorted(unused, key=lambda m: -series_count(m))[:30]:
    print(m, series_count(m))
    가치 대비 비용으로 분류하기

    모든 데이터를 네 칸으로 나눠 보세요. 비싸고 많이 쓰는 것(최적화 대상), 비싸고 안 쓰는 것(즉시 제거), 싸고 많이 쓰는 것(그대로), 싸고 안 쓰는 것(나중에). 대부분의 팀이 "비싸고 안 쓰는 것"만 정리해도 목표의 절반을 달성합니다.

    CHAPTER 03

    카디널리티 — 메트릭 비용의 주범

    메트릭에서 비용을 결정하는 것은 데이터 양이 아니라 시계열의 개수입니다.

    폭발의 메커니즘

    시계열 수는 라벨 값의 곱으로 늘어납니다. 라벨 하나를 추가하는 것이 산술적 증가가 아니라 곱셈이라는 점이 핵심입니다.

    카디널리티 계산기

    라벨별 고유값 수를 넣어 보세요. 마지막 라벨을 켜고 끄며 영향을 확인하세요.

    –
    추정 시계열 수
    –
    기본 대비 배수

    라벨 설계 규칙

    • 유한하고 낮은 카디널리티만 — 값 종류가 수십 개를 넘으면 라벨 후보에서 제외합니다.
    • 고유 식별자는 메트릭이 아니라 로그·트레이스로 — 요청 ID, 사용자 ID, 세션 ID가 대표적입니다. 이들은 로그·트레이스에서 훨씬 싸게 다뤄집니다.
    • 파드 이름 주의 — 배포마다 새 시계열이 생깁니다. 디플로이먼트 단위 집계를 기본으로 두고, 파드 단위는 필요할 때만.
    • URL 경로 정규화 — /user/12345가 아니라 /user/{id}로. 정규화하지 않으면 엔드포인트 라벨이 무한해집니다.
    • 에러 메시지를 라벨로 쓰지 않기 — 자유 텍스트는 카디널리티가 통제되지 않습니다.

    파이프라인에서 막기

    규칙을 문서로 두면 언젠가 깨집니다. 수집 파이프라인에서 강제하는 편이 안전합니다. 최근 OpenTelemetry 생태계에는 카디널리티 제한 프로세서가 추가되어, 한도를 넘는 시계열을 잘라내거나 기타 항목으로 접을 수 있습니다. 백엔드가 무너지기 전에 파이프라인에서 멈추는 것이 핵심입니다.

    OTel Collector — 고위험 라벨 제거와 경로 정규화
    processors:
  # 1) 위험 라벨은 아예 제거한다(사후 정리는 불가능하다)
  attributes/strip:
    actions:
      - { key: user.id,     action: delete }
      - { key: request.id,  action: delete }
      - { key: session.id,  action: delete }

  # 2) URL 경로 정규화 — 숫자·UUID를 플레이스홀더로
  transform/normalize:
    metric_statements:
      - context: datapoint
        statements:
          - replace_pattern(attributes["http.route"], "/[0-9]+", "/{id}")
          - replace_pattern(attributes["http.route"], "/[0-9a-f]{8}-[0-9a-f-]+", "/{uuid}")

  # 3) 파드 단위를 디플로이먼트 단위로 접어 시계열 수를 줄인다
  groupbyattrs:
    keys: [service.name, k8s.deployment.name, http.route, http.response.status_code]

  # 4) 그래도 폭발하면 파이프라인에서 한도를 건다(백엔드 보호)
  #    한도 초과분은 버리지 말고 'overflow'로 접어 존재 자체는 남긴다
    히스토그램은 카디널리티 곱셈기

    히스토그램 하나가 버킷 수만큼 시계열을 만듭니다. 라벨 조합 1만 개 × 버킷 12개 = 12만 시계열입니다. 버킷 수를 실제로 쓰는 만큼으로 줄이거나, 지원되는 환경이라면 네이티브 히스토그램(가변 해상도 방식)을 검토하세요. p99를 볼 것도 아니면서 촘촘한 버킷을 두는 경우가 매우 흔합니다.

    CHAPTER 04

    로그 — 가장 크고 가장 줄이기 쉬운 것

    대부분의 조직에서 수집 과금의 최대 항목입니다. 동시에 손대기 가장 쉬운 영역이기도 합니다.

    단계별 절감 레버

    레버방법효과위험
    레벨 정책운영은 WARN·ERROR 기본, DEBUG는 개발·스테이징만매우 큼조사 시 상세도 부족 → 동적 레벨 상향 수단 필요
    구조화JSON 필드로 출력, 중복 텍스트 제거중간(압축률 개선)낮음
    중복 접기같은 패턴 반복을 카운트로 요약큼(헬스체크·리트라이 로그)개별 타임스탬프 손실
    필터링헬스체크, 정상 200 접근 로그 제외큼트래픽 분석 용도가 있으면 메트릭으로 대체
    로그→메트릭"몇 건 발생"만 필요한 로그는 카운터로 변환큼원문이 필요할 때 없음 → 에러는 남기기
    샘플링정상 로그만 N분의 1로큼에러·느린 요청은 반드시 100% 유지
    파이프라인에서 로그 줄이기
    processors:
  # 1) 헬스체크·정적 파일 접근 로그 제거 — 보통 전체의 20~40%
  filter/noise:
    logs:
      log_record:
        - 'attributes["http.route"] == "/healthz"'
        - 'attributes["http.route"] == "/metrics"'
        - 'IsMatch(body, ".*static/.*200.*")'

  # 2) 운영 환경의 DEBUG 제거(개발 환경은 파이프라인 분리)
  filter/level:
    logs:
      log_record:
        - 'severity_number < SEVERITY_NUMBER_INFO and resource.attributes["deployment.environment"] == "prod"'

  # 3) 긴 본문 잘라내기 — 스택트레이스는 앞부분이 대부분의 정보를 담는다
  transform/trim:
    log_statements:
      - context: log
        statements:
          - 'set(body, Substring(body, 0, 4096)) where Len(body) > 4096'

# 4) "몇 건인지"만 필요한 로그는 메트릭으로 바꾼다(count 프로세서/커넥터 활용)
#    예: 로그인 실패 로그 → login_failures_total 카운터
    동적 레벨 상향 수단을 먼저 만드세요

    DEBUG를 끄는 것이 두려운 이유는 "필요할 때 없을까봐"입니다. 특정 서비스의 로그 레벨을 몇 분간 올리는 스위치(설정 리로드 또는 기능 플래그)를 먼저 만들면, 상시 DEBUG 수집을 안심하고 끌 수 있습니다. 이것 하나로 대개 가장 큰 절감이 나옵니다.

    CHAPTER 05

    트레이스 — 샘플링 설계

    트레이스는 "전부 저장"이 거의 항상 낭비입니다. 문제는 무엇을 남길지 어떻게 정하느냐입니다.

    두 가지 방식

    • 헤드 샘플링 — 요청 시작 시점에 확률로 결정. 간단하고 부하가 적지만, 에러 보존을 보장하지 못합니다.
    • 테일 샘플링 — 트레이스가 끝난 뒤 내용을 보고 결정. 에러·느린 요청·희귀 경로를 100% 남길 수 있습니다. 대신 게이트웨이가 트레이스를 모아 두어야 하므로 메모리와 설계 부담이 있습니다.

    실무 기본값은 1편에서 본 조합입니다. 에러·p95 초과·희귀 경로는 전부 남기고, 나머지는 5~15%. 여기에 더해 다음 규칙들이 비용과 가치의 균형을 크게 개선합니다.

    규칙이유
    서비스별 차등 샘플링핵심 결제 경로는 높게, 내부 배치는 낮게. 균일 샘플링은 항상 어딘가에서 과하거나 부족합니다
    저트래픽 서비스는 높게초당 2건인 서비스를 10% 샘플링하면 사실상 아무것도 안 남습니다
    스팬 수 상한루프에서 스팬 수천 개를 만드는 코드가 반드시 있습니다. 트레이스당 상한을 두세요
    스팬 속성 정리큰 페이로드나 SQL 전문을 속성에 넣으면 스팬 크기가 폭증합니다
    스팬 메트릭 생성샘플링으로 버려도 통계는 남기기 위해, 스팬에서 RED 메트릭을 파생시켜 저장합니다
    샘플링해도 통계는 지키기

    트레이스를 1%만 남겨도, 파이프라인에서 모든 스팬으로부터 요청 수·에러율·지연 분포를 먼저 계산해 메트릭으로 저장하면 대시보드와 SLO는 정확도를 유지합니다. 즉 "정확한 통계 + 대표 샘플"이 됩니다. 이 구성을 모르면 샘플링을 올릴 때마다 지표가 흔들려서 결국 샘플링을 못 하게 됩니다.

    CHAPTER 06

    파이프라인이 제어 평면이다

    애플리케이션 코드를 고치지 않고도 수집량·형식·라우팅을 바꿀 수 있는 유일한 지점입니다.

    파이프라인에서 하는 일

    1. 정규화 — 속성 이름 통일(1편 시맨틱 컨벤션). 상관분석과 에이전트 품질의 전제
    2. 감축 — 필터, 샘플링, 중복 접기, 속성 제거
    3. 변환 — 로그→메트릭, 스팬→메트릭, 경로 정규화, 마스킹
    4. 라우팅 — 신호·테넌트·중요도별로 다른 백엔드·티어로 분배
    5. 보호 — 카디널리티 한도, 메모리 제한, 백프레셔
    중요도에 따라 다른 저장소로 라우팅
    connectors:
  routing:
    default_pipelines: [logs/cold]
    table:
      # 에러·보안 로그는 핫 티어(빠른 검색, 짧은 보존)
      - context: log
        condition: 'severity_number >= SEVERITY_NUMBER_ERROR'
        pipelines: [logs/hot]
      - context: log
        condition: 'attributes["category"] == "audit"'
        pipelines: [logs/audit]     # 장기 보존·불변 저장(5편)

service:
  pipelines:
    logs/hot:   { exporters: [loki] }
    logs/cold:  { exporters: [s3/parquet] }      # 객체 스토리지에 컬럼형으로
    logs/audit: { exporters: [s3/audit] }

    플릿 관리

    컬렉터가 수십·수백 대가 되면 설정 배포 자체가 문제가 됩니다. OpenTelemetry 진영에는 에이전트 원격 관리 프로토콜(OpAMP)이 있어, 중앙에서 설정을 배포하고 상태를 수집할 수 있습니다. 4편의 카나리 테넌트 원칙을 여기에도 적용하세요. 수집 설정 변경은 전 고객사 동시 배포 금지입니다.

    듀얼 라이트로 안전하게 바꾸기

    백엔드 교체나 대규모 감축을 할 때는 같은 데이터를 두 곳으로 동시에 보내는 기간을 두세요. 한 달간 새 쪽으로 실제 장애를 조사해 보고, 질의 성능과 데이터 충분성을 확인한 뒤 전환합니다. 파이프라인이 있으면 이 작업이 설정 변경 한 번으로 끝납니다. 이것이 파이프라인을 두는 가장 큰 이유입니다.

    CHAPTER 07

    저장 아키텍처 — 컬럼형과 티어링

    같은 데이터를 어떻게 저장하느냐에 따라 비용이 한 자릿수 배 차이가 납니다.

    왜 컬럼형인가

    로그·트레이스는 사실상 넓은 테이블의 append-only 데이터입니다. 컬럼 단위로 저장하면 같은 종류의 값이 모여 있어 압축률이 크게 올라가고, 질의 시 필요한 컬럼만 읽습니다. ClickHouse나 Parquet 기반 구성에서 원본 대비 한 자릿수 배 이상의 압축이 보고되며, 고카디널리티 필드도 인덱스 폭발 없이 다룰 수 있습니다.

    구성강점부담
    관리형 SaaS운영 부담 0, 즉시 사용수집량·보존 과금이 규모에 따라 급증
    Loki·Mimir·Tempo 자체 운영OTel 친화적, 객체 스토리지 기반으로 저렴운영 인력 필요, 튜닝 지식 요구
    ClickHouse 계열고카디널리티에 강하고 SQL로 신호 간 조인 가능, 압축률 우수스키마·머지·티어링 설계를 직접 해야 함
    객체 스토리지 + Parquet + 쿼리 엔진저장 단가 최저. 대용량 아카이브에 적합질의 지연이 큼. 실시간 조사에는 부적합

    2026년에는 대형 조직이 벤더를 벗어나 Fluent Bit·객체 스토리지·Parquet·쿼리 엔진 조합으로 자체 로그 플랫폼을 구축한 사례들이 공유되고 있습니다. 다만 이것은 전담 인력이 있는 규모에서 성립하는 선택입니다.

    CHAPTER 08

    비용 거버넌스 — 다시 늘어나지 않게

    절감 프로젝트의 진짜 실패는 줄이지 못하는 것이 아니라, 6개월 뒤 원래대로 돌아가는 것입니다.

    비용을 관측 대상으로

    • 수집량·시계열 수를 지표로 — 서비스별·테넌트별·팀별로 일 단위 추적. 4편의 테넌트 집계와 같은 구조입니다
    • 증가율 알림 — "지난주 대비 20% 증가"에 알림. 절대값보다 변화가 신호입니다
    • 신규 시계열 급증 탐지 — 새 배포가 카디널리티를 터뜨리는 것을 당일에 잡습니다
    • 예산과 실적 — 월 예산 대비 소진율을 대시보드에 두고, 초과 예상 시 조기 경보
    카디널리티 급증 감지 규칙
    groups:
- name: telemetry-cost
  rules:
  # 특정 메트릭의 시계열 수가 하루 만에 3배가 되면 배포를 의심한다
  - alert: CardinalitySpike
    expr: |
      sum by (job, __name__) (scrape_series_added)
        > 3 * sum by (job, __name__) (scrape_series_added offset 1d)
    for: 30m
    labels: { severity: warning, category: cost }
    annotations:
      summary: "시계열 급증 — 최근 배포의 라벨 변경 여부 확인"

  # 수집량 예산 소진 속도(6편 번레이트와 같은 발상)
  - alert: IngestBudgetBurn
    expr: sum(rate(otelcol_receiver_accepted_log_records[6h])) * 86400 > daily_log_budget * 1.3
    for: 2h

    규칙내용

    기본값 제한새 서비스 온보딩 시 표준 번들(4편)에 수집 한도와 보존 기본값을 포함시킵니다
    비용 가시화팀·고객사별 사용량을 공개합니다. 보이면 줄어듭니다(쇼백의 효과)
    예외에 만료일"임시로 보존 90일" 같은 예외는 반드시 종료일과 함께
    MSP라면 그대로 상품이 됩니다

    4편의 테넌트별 집계와 결합하면 "고객사별 관측 비용 리포트"가 나옵니다. 고객사 입장에서는 자신들이 무엇을 얼마나 쓰는지 처음 보게 되는 경우가 많고, 절감 제안 자체가 MSP의 부가가치가 됩니다. 계약 갱신 근거로도 유용합니다.

    CHAPTER 09

    90일 절감 프로젝트

    가시성을 잃지 않으면서 순서대로 진행하는 방법입니다.

    0~30일 · 측정과 무손실 절감

    • 비용 구조 파악 — 신호별·서비스별 수집량과 시계열 수를 집계
    • 미사용 메트릭 목록화(2장) 후 30일 폐기 예고
    • 헬스체크·정적 자원 접근 로그 필터링 — 위험이 거의 없고 효과가 큽니다
    • 수집량·시계열 수 대시보드와 증가율 알림 구축

    31~60일 · 구조 개선

    • 고위험 라벨 제거와 URL 정규화(3장), 파이프라인에 카디널리티 한도 적용
    • 운영 DEBUG 로그 중단 — 단, 동적 레벨 상향 수단을 먼저 구축
    • 테일 샘플링 도입 또는 정교화, 스팬 메트릭 파생 설정
    • 히스토그램 버킷 정리, 레코딩 룰로 다운샘플링 집계본 생성

    61~90일 · 저장과 보존

    • 보존 티어 적용 — 핫·웜·콜드 분리, 대시보드를 장기 구간에서 집계본 사용으로 전환
    • 필요 시 콜드 티어를 객체 스토리지·컬럼형으로 이전(듀얼 라이트 검증 후)
    • 분기 정리 루틴과 신규 메트릭 리뷰 규칙을 프로세스로 고정
    • 절감 결과 보고 — 절감액과 함께 가시성 지표(장애 조사 시 데이터 부족 사례 수)를 같이 보고
    반드시 함께 측정할 것

    절감만 보고하면 다음 장애에서 "데이터가 없다"는 말이 나왔을 때 프로젝트 전체가 부정됩니다. "조사 중 데이터 부족으로 막힌 횟수"를 사건 기록에 필드로 추가하고 함께 추적하세요. 이 숫자가 늘지 않았다는 근거가 있어야 절감이 유지됩니다.

    CHAPTER 10

    앞으로 주목할 것

    2026년 시점에서 논의되고 있는 흐름입니다. 당장 도입할 것과 지켜볼 것을 구분해 두세요.

    • 전송 포맷 효율화 — SDK에서 백엔드까지 거치는 형식 변환이 의미 없는 CPU를 소모한다는 문제 제기와, Apache Arrow 기반 컬럼형 전송 프로토콜(OTAP) 논의가 있습니다. 초기 테스트에서 페이로드 축소가 보고되지만 아직 프로덕션 단계는 아닙니다. 지켜볼 것에 해당합니다.
    • 중앙 집중 샘플링 결정 — 가벼운 메타데이터만 먼저 수집해 중앙에서 샘플링을 결정하고, 선택된 것만 전체 데이터를 가져오는 방식이 제안되고 있습니다. 게이트웨이 메모리 부담이 큰 테일 샘플링의 대안이 될 수 있습니다.
    • AI 텔레메트리 증가 — 3편의 LLM 옵저버빌리티 데이터가 새로운 비용 축으로 등장합니다. 프롬프트·응답 전문을 저장할지 여부는 비용과 보안(5편) 양쪽에서 결정해야 합니다.
    • 프로파일링 신호 — 연속 프로파일링이 네 번째 신호로 자리를 잡아가고 있습니다. 가치가 크지만 수집량도 크므로, 도입 시 샘플링 설계를 처음부터 함께 하세요.
    새 신호를 들일 때의 규칙

    어떤 신호든 도입 전에 세 가지를 정하세요. 누가 언제 볼 것인가, 보존은 얼마인가, 비용 상한은 얼마인가. 이 셋이 없으면 새 신호는 예외 없이 "켜두고 아무도 안 보는 비용"이 됩니다.

    CHAPTER 11

    정리 — 안티패턴과 점검

    안티패턴 8선

    1. 일단 다 모으기 — 3개월 뒤 청구서와 노이즈로 돌아옵니다.
    2. 고유 식별자를 메트릭 라벨로 — 시계열 폭발의 1순위 원인입니다.
    3. 측정 없이 감축 — 무엇이 쓰이는지 모른 채 줄이면 필요한 것부터 사라집니다.
    4. DEBUG 상시 수집 — 동적 레벨 상향 수단이 있으면 불필요합니다.
    5. 균일 샘플링 — 저트래픽 서비스는 사실상 관측이 사라집니다.
    6. 샘플링 후 통계 붕괴 — 스팬 메트릭을 파생시키지 않아 지표가 흔들립니다.
    7. 원본 해상도 장기 보존 — 다운샘플링만 해도 저장량이 수십 분의 1이 됩니다.
    8. 절감 후 방치 — 거버넌스가 없으면 6개월 뒤 원상 복구됩니다.

    관측 데이터는 자산이 아니라 재고입니다. 쌓아두는 것 자체에는 가치가 없고, 조회될 때만 가치가 생깁니다. 무엇이 조회되는지 측정하고, 조회되지 않는 것을 줄이고, 다시 늘어나지 않게 관리하는 것. 이것이 이 편 전체의 요약입니다.
