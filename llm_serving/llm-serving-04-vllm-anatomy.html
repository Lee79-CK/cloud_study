01시작하기 전에

엔진 내부 구조를 알면 로그·지표·옵션이 “어디서 나온 숫자인지” 보이기 시작합니다.

이 편은 vLLM v0.31.0(2026년 10월 5일 릴리스)을 기준으로 씁니다. vLLM은 몇 주 간격으로 버전이 올라가고 옵션 이름이 바뀌기도 하므로, 실제 운영에서는 쓰는 버전의 --help와 릴리스 노트를 기준으로 삼아야 합니다. 이 편의 목표는 옵션을 외우는 것이 아니라, 새 옵션을 봤을 때 “이건 어느 컴포넌트를 건드리는 옵션인가”를 판단할 수 있게 되는 것입니다.

학습 목표

  1. vLLM의 프로세스 구조(API 서버·엔진 코어·GPU 워커·DP 코디네이터)를 그리고, TP·DP 설정에 따른 프로세스 수를 계산할 수 있다.
  2. 엔진 코어의 루프에서 스케줄러와 KV 캐시 관리자가 한 스텝마다 무엇을 결정하는지 설명할 수 있다.
  3. 모델 러너·CUDA 그래프·torch.compile·어텐션 백엔드가 성능과 기동 시간에 어떤 영향을 주는지 설명할 수 있다.
  4. OpenAI 호환 서버 안에서 요청이 처리되는 경로와 제공 엔드포인트를 알고, 플랫폼 관점의 보안·운영 주의점을 짚을 수 있다.
  5. 주요 실행 옵션을 범주별로 분류하고, 각 옵션이 3편의 지표(TTFT·TPOT·처리량·메모리)를 어떻게 움직이는지 설명할 수 있다.
  6. 멀티모달·툴 콜링·구조화 출력·추론 출력을 켜고 API로 호출할 수 있다.
이 편의 비유: 식당의 세 구역

API 서버는 홀입니다. 손님(HTTP 요청)을 맞고 주문서를 주방 언어(토큰)로 옮겨 적고, 완성된 요리를 접시에 담아 내갑니다. 엔진 코어는 주방 매니저입니다. 매 순간 어떤 주문을 몇 개 화구에 올릴지(스케줄러), 선반 칸을 어떻게 나눠 줄지(KV 캐시 관리자)를 정합니다. GPU 워커는 화구 앞 요리사입니다. 매니저가 준 작업표대로 실제로 굽습니다. 셋을 다른 방(프로세스)에 둔 이유는, 홀이 아무리 붐벼도 매니저와 요리사의 리듬이 끊기지 않게 하기 위해서입니다.

02vLLM은 무엇인가

연구 프로젝트에서 시작해 서빙 생태계의 공용 부품이 된 엔진.

vLLM은 UC 버클리 Sky Computing Lab에서 PagedAttention 논문(2023)과 함께 공개된 오픈소스 추론·서빙 엔진입니다. 이후 커뮤니티 프로젝트로 성장해 PyTorch Foundation 산하 프로젝트가 되었고, 내부 구조를 처음부터 다시 쓴 V1 아키텍처가 지금의 기본입니다. 이 시리즈에서 “vLLM”이라고 하면 V1 구조를 말합니다.

플랫폼 엔지니어가 vLLM을 기본값으로 고르는 이유

  • 모델 지원 폭: 새 공개 모델이 나오면 대개 출시 당일이나 며칠 안에 지원됩니다. 텍스트·비전·음성·임베딩·리랭커까지 한 엔진으로 서빙할 수 있습니다.
  • 하드웨어 지원 폭: NVIDIA(CUDA 12.9·13.0 빌드), AMD ROCm, Intel XPU, CPU, TPU와 여러 플러그인 백엔드를 지원합니다. v0.31.0 릴리스에는 arm64용 CUDA wheel도 함께 배포됩니다.
  • 표준 인터페이스: OpenAI 호환 API를 기본 제공하고, Responses API와 Anthropic Messages 형식(/v1/messages)까지 받아들입니다. 게이트웨이(12편)와 앱 입장에서 교체가 쉽습니다.
  • 생태계의 기본 부품: KServe, llm-d, NVIDIA Dynamo, AIBrix, KubeAI, Ray Serve 등 대부분의 상위 프레임워크가 vLLM을 엔진으로 씁니다(9·10편). vLLM을 이해하면 그 위의 플랫폼들이 무엇을 조율하는지 보입니다.
빠른 변화는 장점이자 운영 위험

v0.31.0 한 릴리스에만 700개 넘는 커밋이 들어갔고, 옵션 이름 변경·기본값 변경·기능 제거 같은 호환성 변경도 매번 있습니다. 플랫폼 운영의 원칙은 단순합니다. 이미지 태그를 고정하고, 릴리스 노트의 “Breaking Changes” 절을 읽고, 스테이징에서 벤치마크·회귀 테스트를 통과한 뒤 올린다. 업그레이드 절차는 25편에서 다룹니다.

vLLM V1은 관심사를 분리하고 처리량을 높이기 위해 다중 프로세스 구조를 씁니다. 공식 아키텍처 문서가 정리한 네 종류의 프로세스는 다음과 같습니다.

04엔진 코어 루프

엔진 코어는 “받고, 정하고, 돌리고, 정리하고, 보낸다”를 쉬지 않고 반복합니다.

엔진 코어 프로세스는 바쁜 루프(busy loop)를 돌며 요청을 계속 스케줄하고 GPU 워커에 일을 보냅니다. ZMQ 입출력은 백그라운드 스레드가 맡아, 직렬화 작업이 GPU 실행과 겹쳐 진행되도록 합니다. 루프 한 바퀴가 2편에서 말한 “Decode 한 스텝”입니다.

  1. 입력 수신API 서버가 보낸 새 요청(이미 토큰화된 상태)과 취소 요청을 대기열(waiting)에 반영합니다. 클라이언트가 연결을 끊으면 취소가 여기까지 전달되어야 GPU 낭비가 없습니다.
  2. 스케줄스케줄러가 이번 스텝에 처리할 요청과 요청별 토큰 수를 정하고, KV 캐시 관리자에게 블록을 받아 둡니다. 결과물은 “스케줄러 출력” 한 묶음입니다(5장).
  3. 실행실행기가 워커들에게 스케줄러 출력을 전달하고, 워커는 모델 러너로 순전파를 하고 다음 토큰을 샘플링합니다(6장).
  4. 갱신생성된 토큰을 각 요청에 붙이고, 종료 조건(EOS 토큰, 최대 토큰 수 등)을 확인합니다. 끝난 요청의 블록은 반납하되, 꽉 찬 블록은 프리픽스 캐시용으로 해시를 붙여 남겨 둡니다.
  5. 출력 전송새 토큰 ID들을 API 서버로 보냅니다. 글자로 바꾸는 디토큰화와 stop 문자열 판정은 API 서버의 출력 처리기가 합니다. stop 문자열이 나오면 엔진 쪽에 중단을 알립니다.
비동기 스케줄링

단순하게 하면 “스케줄 → GPU 실행 → 결과 확인 → 다음 스케줄” 순서라 CPU가 스케줄하는 동안 GPU가 놉니다. 비동기 스케줄링은 GPU가 현재 스텝을 실행하는 동안 CPU가 다음 스텝을 미리 계획해, 스텝 사이의 빈틈을 줄입니다. 작은 모델·작은 배치에서 TPOT 개선 효과가 크고, 기능 조합에 따라 제약이 있을 수 있어 버전별 기본값과 호환성을 확인해야 합니다. 엔진 코어 CPU가 느리면 바로 이 구간이 TPOT를 깎아 먹습니다. GPU 서버의 CPU를 아끼면 안 되는 이유입니다.

05스케줄러와 KV 캐시 관리자

2편의 연속 배칭과 PagedAttention이 실제로 구현된 곳.

V1 스케줄러의 핵심 아이디어: Prefill과 Decode를 구분하지 않는다

V1 스케줄러는 요청마다 “지금까지 계산한 토큰 수”와 “계산해야 할 토큰 수”만 봅니다. 한 스텝에 각 요청에 몇 토큰을 배정해 그 차이를 줄여 나갈 뿐입니다. 입력 3,000토큰짜리 새 요청에 이번 스텝 1,000토큰을 배정하면 Chunked Prefill이고, 이미 다 따라잡은 요청에 1토큰을 배정하면 Decode입니다. 프리픽스 캐시 적중은 “이미 계산된 토큰”이 처음부터 많은 상태일 뿐이고, 추측 디코딩은 한 요청에 여러 토큰을 배정하는 경우일 뿐입니다. 이 단순한 모델 덕분에 여러 최적화가 한 스케줄러 안에서 자연스럽게 합쳐집니다.

한 스텝을 정하는 규칙

  1. 토큰 예산: 한 스텝에 처리할 수 있는 토큰 수의 상한(--max-num-batched-tokens). 이 예산이 Chunked Prefill 조각의 크기와 활성값 메모리를 정합니다.
  2. 실행 중(running) 요청 먼저: 이미 진행 중인 요청의 Decode 토큰과 남은 Prefill 조각을 먼저 배정합니다. 진행 중인 사용자의 TPOT를 지키기 위해서입니다.
  3. 남은 예산으로 대기(waiting) 요청 받기: 기본은 도착 순서(FCFS), --scheduling-policy priority로 우선순위 방식도 가능합니다. 한 요청이 너무 큰 조각을 가져가지 않도록 하는 임계값(--long-prefill-token-threshold)이 있고, v0.31.0에서는 대기 중인 Prefill 수에 맞춰 이 값이 적응하도록 바뀌었습니다.
  4. 동시 실행 상한: 동시에 배치에 들어갈 요청 수의 상한(--max-num-seqs). v0.31.0에는 실행 상태 진입만 따로 제한하는 --max-num-active-seqs도 추가되었습니다.
  5. KV 블록 확인: 배정한 토큰을 담을 블록이 없으면 그 요청은 이번 스텝에 못 들어갑니다. 실행 중 요청조차 블록이 모자라면 선점이 일어납니다. 가장 나중에 들어온 실행 중 요청의 블록을 회수하고 대기열로 돌려보내, 나중에 다시 계산하게 합니다. v0.31.0에서는 이미 KV 블록을 쥐고 있는 대기 요청을 먼저 스케줄하도록 대기열 처리가 바뀌었습니다.

스케줄러 한 스텝씩 따라가기

시뮬레이터로 해 볼 것: 토큰 예산을 256으로 줄이면 긴 입력(R3)의 Prefill이 여러 스텝에 나뉘어 TTFT가 길어지지만 실행 중 요청의 Decode는 매 스텝 이어집니다. 예산을 8,192로 키우면 R3가 한 번에 들어가 TTFT는 짧아지지만 그 스텝은 무거워집니다(실제로는 그 스텝 동안 다른 요청의 ITL이 튑니다). KV 블록을 200~230 정도로 줄이면 긴 입력의 Prefill이 진행되는 동안 블록이 모자라 선점이 발생합니다. 이것이 3편에서 본 지연 꼬리의 정체입니다.

KV 캐시 관리자

KV 캐시 관리자는 2편의 PagedAttention 블록 풀을 관리합니다. 기동 시 확보한 GPU 메모리를 블록으로 나누고, 요청에 블록을 빌려주고 돌려받습니다.

  • 블록 해시와 프리픽스 캐시: 꽉 찬 블록은 “앞 블록의 해시 + 이 블록의 토큰들 + 추가 키”로 해시를 계산해 등록합니다. 같은 앞부분을 가진 새 요청은 해시를 찾아 그 블록을 재사용합니다. 추가 키에는 LoRA 어댑터, 멀티모달 입력의 해시, cache_salt 등이 들어가 서로 다른 맥락의 블록이 섞이지 않게 합니다. V1에서는 프리픽스 캐싱이 기본으로 켜져 있습니다.
  • 참조 수와 지연 축출: 요청이 끝나도 해시가 붙은 블록은 바로 지우지 않고 “빈 블록 목록”에 넣어 두었다가, 공간이 필요할 때 오래된 것부터 실제로 재사용합니다. 그래서 프리픽스 캐시 적중은 메모리 여유가 있을수록 높아집니다.
  • 하이브리드 KV 캐시: 슬라이딩 윈도우 층, Mamba 같은 상태 공간 층이 섞인 모델은 층 그룹마다 다른 방식으로 캐시를 관리합니다. 2편의 gpt-oss 계산에서 본 차이가 여기서 처리됩니다.
  • KV 커넥터: KV 블록을 CPU 메모리·SSD·다른 노드로 보내고 받는 확장 지점입니다. KV 오프로딩(15편)과 Prefill/Decode 분리(10편)가 이 인터페이스를 씁니다.
MSP 관점: 프리픽스 캐시와 테넌트 격리

여러 고객이 한 엔진을 공유하면, 이론적으로 응답 속도 차이로 “다른 테넌트가 같은 프롬프트를 보냈는지”를 추정하는 타이밍 부채널이 생길 수 있습니다. 요청에 테넌트별 cache_salt를 넣으면 테넌트끼리는 캐시를 공유하지 않게 됩니다. 이 값은 앱이 아니라 게이트웨이가 테넌트 ID로 강제로 주입하는 것이 안전합니다(12·24편). v0.31.0에서는 LoRA 이름과 cache_salt가 충돌하지 않도록 추가 키에 출처 태그를 붙이는 보안 수정도 들어갔습니다.

06워커·모델 러너·어텐션 백엔드

GPU 위에서 실제로 계산이 일어나는 층. 성능과 기동 시간의 대부분이 여기서 정해집니다.

워커가 기동할 때 하는 일

  1. 장치 초기화: 자기 GPU를 잡고, 텐서 병렬이면 다른 워커들과 통신 그룹(NCCL)을 만듭니다.
  2. 가중치 로딩: 모델을 만들면서 동시에 자기 몫의 가중치만 읽어 들입니다. 텐서 병렬 분할과 양자화를 “로딩 후 변환”이 아니라 “초기화하면서” 하는 설계라, 큰 모델도 GPU마다 자기 몫만큼의 메모리만 씁니다.
  3. 메모리 프로파일링: 최대 크기의 가짜 배치로 순전파를 한 번 돌려 활성값 최대치를 잽니다.
  4. KV 캐시 할당: 남은 메모리로 KV 블록 풀을 만듭니다. 2편에서 계산한 그 숫자입니다.
  5. 컴파일과 CUDA 그래프 캡처: torch.compile로 연산을 최적화하고, 자주 쓰는 배치 크기별로 CUDA 그래프를 녹화합니다. 기동 시간이 긴 가장 큰 이유 중 하나입니다.

모델 러너

모델 러너는 스케줄러 출력을 GPU가 먹을 수 있는 텐서로 바꿉니다. 여러 요청의 토큰을 패딩 없이 한 줄로 이어 붙이고, 각 토큰의 위치, 각 요청의 블록 테이블, 새 KV를 쓸 슬롯 위치를 함께 만들어 넘깁니다. 순전파가 끝나면 로짓에서 샘플링을 하고, 구조화 출력이 켜져 있으면 문법에 맞지 않는 토큰을 가립니다. 최근 vLLM에는 다시 설계된 Model Runner V2가 함께 발전하고 있으며, v0.31.0에서 추측 디코딩·사용자 정의 로짓 프로세서 지원 등이 추가되었습니다. 어느 러너가 기본으로 쓰이는지는 버전과 기능 조합에 따라 다르므로 기동 로그로 확인합니다.

CUDA 그래프와 torch.compile: 최적화 레벨

Decode 스텝은 GPU 계산 자체는 짧은데 커널 수백 개를 하나씩 띄우는 CPU 오버헤드가 상대적으로 큽니다. CUDA 그래프는 커널 실행 순서를 한 번 녹화해 두고 통째로 재생해 이 오버헤드를 없앱니다. 대신 배치 크기별로 녹화해야 하고, 녹화에 시간과 약간의 메모리가 듭니다. vLLM은 이 트레이드오프를 -O 최적화 레벨로 묶어 제공합니다.

07OpenAI 호환 서버 해부

플랫폼과 가장 많이 맞닿는 부분. 엔드포인트, 요청 처리 경로, 보안 경계를 정확히 알아야 게이트웨이를 설계할 수 있습니다.

채팅 요청 하나의 서버 내부 경로

  1. HTTP 수신·검증FastAPI 라우터가 요청 본문을 OpenAI 스키마로 검증합니다. --api-key가 설정돼 있으면 여기서 확인합니다.
  2. 채팅 템플릿 렌더링messages와 tools를 모델의 채팅 템플릿으로 하나의 프롬프트 문자열로 만듭니다(2편). --chat-template으로 바꿀 수 있습니다.
  3. 토큰화·멀티모달 처리문자열을 토큰 ID로 바꾸고, 이미지·오디오가 있으면 내려받아 전처리합니다. 입력 길이가 최대 길이를 넘으면 여기서 400 에러가 납니다.
  4. 샘플링 파라미터 확정요청에 없는 값은 모델 저장소의 generation_config.json에서 가져오는 것이 기본 동작입니다(--generation-config). 그래서 같은 요청도 모델에 따라 기본 temperature가 다를 수 있습니다.
  5. 엔진 코어로 전송비동기 엔진 클라이언트가 ZMQ로 엔진 코어에 요청을 넘기고, 출력 스트림을 기다립니다.
  6. 출력 처리토큰 ID를 글자로 바꾸고(디토큰화), stop 문자열을 검사하고, 추론(reasoning) 파서·툴 콜 파서가 켜져 있으면 출력을 reasoning_content·tool_calls 필드로 나눕니다.
  7. 응답 전송스트리밍이면 SSE 청크로, 아니면 완성된 JSON으로 보냅니다. 마지막에 사용량(입력·출력 토큰 수)을 담습니다. 게이트웨이의 계측(12편)은 이 값을 씁니다.

08주요 실행 옵션

수백 개 옵션 중 플랫폼 엔지니어가 반드시 알아야 할 것들을, 어느 컴포넌트를 건드리고 어떤 지표를 움직이는지로 정리합니다.

옵션은 vllm serve <모델> [옵션...]의 인자로 주거나, 같은 이름의 키를 가진 YAML 파일을 --config로 넘길 수 있습니다. 운영에서는 YAML 파일을 ConfigMap으로 관리하면 변경 이력이 남고 리뷰가 쉬워집니다. 기본값은 버전과 GPU에 따라 자동으로 정해지는 것이 많으므로, 기동 로그에 찍힌 최종 설정값을 항상 기록해 두세요.

표시된 “영향” 태그는 그 옵션이 주로 움직이는 지표입니다. 일부 옵션은 버전에 따라 이름이나 기본값이 다를 수 있으므로 사용하는 버전의 vllm serve --help로 최종 확인하세요. 실습 4-6에서 --help=키워드 검색으로 옵션을 찾는 방법을 익힙니다.

옵션 고르기의 출발점

1. 모델이 들어가는가 → --quantization, --kv-cache-dtype, -tp 2. KV 공간이 충분한가 → --gpu-memory-utilization, --max-model-len 3. 지연과 처리량의 균형 → --max-num-batched-tokens, --max-num-seqs 4. 기동 시간 vs 실행 성능 → -O 레벨, 로딩 방식(--load-format), preload 5. 기능 → 툴 콜·추론 파서, 구조화 출력, LoRA, 멀티모달 상한 6. 운영·보안 → --served-model-name, 로깅, 트레이싱, 게이트웨이 뒤 배치

튜닝 실전은 14편에서 이 순서 그대로 벤치마크와 함께 합니다. 이 편에서는 각 옵션이 엔진의 어느 부분을 건드리는지 연결하는 것까지가 목표입니다.

yaml · vllm-qwen.yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: vllm-qwen-config, namespace: llmsvc-lab }
data:
  vllm.yaml: |
    served-model-name: qwen3-8b          # API에서 쓸 이름 (모델 경로를 숨김)
    host: 0.0.0.0
    port: 8000
    gpu-memory-utilization: 0.35         # GB10 통합 메모리 128GB 중 약 35%
    max-model-len: 16384
    enable-auto-tool-choice: true        # 실습 4-4용
    tool-call-parser: hermes
    reasoning-parser: qwen3
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: vllm-qwen, namespace: llmsvc-lab, labels: { app: vllm-qwen } }
spec:
  replicas: 1
  strategy: { type: Recreate }           # GPU 1장: 새 Pod가 뜨기 전에 기존 Pod를 내려야 함
  selector: { matchLabels: { app: vllm-qwen } }
  template:
    metadata: { labels: { app: vllm-qwen } }
    spec:
      runtimeClassName: nvidia
      nodeSelector: { kubernetes.io/arch: arm64 }
      tolerations: [ { key: nvidia.com/gpu, operator: Exists, effect: NoSchedule } ]
      terminationGracePeriodSeconds: 60
      containers:
      - name: vllm
        image: vllm/vllm-openai:v0.31.0  # 4-1 결과에 따라 NGC 이미지로 교체
        command: ["vllm", "serve", "Qwen/Qwen3-8B", "--config", "/config/vllm.yaml"]
        env:
        - { name: HF_HOME, value: /cache }
        ports: [ { containerPort: 8000, name: http } ]
        resources:
          requests: { cpu: "4", memory: 8Gi }
          limits:   { nvidia.com/gpu: 1 }
        startupProbe:                     # 다운로드·로딩·컴파일까지 최대 40분 허용
          httpGet: { path: /health, port: http }
          periodSeconds: 10
          failureThreshold: 240
        readinessProbe:
          httpGet: { path: /health, port: http }
          periodSeconds: 5
          failureThreshold: 3
        livenessProbe:                    # 느슨하게: 과부하를 장애로 오인하지 않도록
          httpGet: { path: /health, port: http }
          periodSeconds: 30
          timeoutSeconds: 10
          failureThreshold: 10
        volumeMounts:
        - { name: config, mountPath: /config }
        - { name: cache, mountPath: /cache }
        - { name: shm, mountPath: /dev/shm }
      volumes:
      - { name: config, configMap: { name: vllm-qwen-config } }
      - { name: cache, emptyDir: {} }     # 재시작마다 재다운로드. 영구 캐시는 13편에서
      - { name: shm, emptyDir: { medium: Memory, sizeLimit: 4Gi } }
---

핵심 여섯 문장.

  1. vLLM V1은 API 서버·엔진 코어·GPU 워커(+DP 코디네이터)로 나뉜 다중 프로세스 구조이며, ZMQ로 통신해 GIL 경합 없이 GPU를 바쁘게 유지한다.
  2. 엔진 코어는 받고·정하고·돌리고·정리하고·보내는 루프를 쉬지 않고 돈다. CPU가 부족하면 이 루프가 느려져 TPOT가 나빠진다.
  3. 스케줄러는 Prefill과 Decode를 구분하지 않고 토큰 예산을 나눈다. 실행 중 요청이 먼저, 남은 예산으로 대기 요청을 받고, KV 블록이 모자라면 선점한다.
  4. KV 캐시 관리자는 블록 해시로 프리픽스 캐시를 기본 제공하며, 테넌트 격리는 게이트웨이가 주입하는 cache_salt로 한다.
  5. 워커는 로딩 → 프로파일링 → KV 할당 → 컴파일·CUDA 그래프 순으로 기동하고, -O 레벨이 기동 시간과 실행 성능을 맞바꾼다.
  6. OpenAI·Responses·Anthropic 형식을 모두 받는 서버이지만 보안 경계는 엔진 밖 게이트웨이에 둔다. 옵션은 “어느 컴포넌트를 건드리는가”로 이해한다.
