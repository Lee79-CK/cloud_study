OpenTelemetry 도입 · 7편
왜 Collector인가 파이프라인 구조 설정 파일 컴포넌트 카탈로그 프로세서 순서 배포 토폴로지 배포판과 빌드 자기 관측 진단 정리
시리즈 7편  ·  엔지니어 트랙 시작  ·  1·2편 선행 권장

앱 밖에서 벌어지는 일

3편부터 6편까지는 애플리케이션 안의 이야기였습니다. 이제 데이터가 앱을 떠난 뒤를 봅니다. Collector는 받고, 가공하고, 내보내는 단순한 구조지만, 이 세 단계를 어떻게 조합하느냐가 비용·보안·신뢰성을 전부 결정합니다. 아래에서 직접 조립해 보세요.

파이프라인 빌더 프로세서 순서 연습 토폴로지 선택기 컴포넌트 카탈로그
신호 종류
RECEIVERS · 받는다
PROCESSORS · 가공한다
EXPORTERS · 내보낸다

      

      

    

  










  SECTION 01
  
Collector를 왜 두는가

  

    앱이 백엔드로 직접 보내도 동작은 합니다.
    Collector를 두는 이유는 책임을 앱에서 인프라로 옮기기 위해서입니다.
  


  
Collector가 없으면 앱이 져야 하는 것들

  

    

      
책임Collector 없을 때Collector 있을 때

      
        
백엔드 주소·인증앱이 알고 있어야 함 → 교체 시 재배포설정 파일 한 줄 수정

        
백엔드 장애 대응앱이 재시도·버퍼링 감당Collector가 큐로 버팀

        
민감정보 마스킹코드 수정 = 배포변환 규칙 수정

        
샘플링 정책 변경전 서비스 재배포Gateway 설정 변경

        
K8s 메타데이터앱이 스스로 알아내야 함자동 부착

        
여러 백엔드로 분기앱에서 다중 전송익스포터 추가

      
    

  


  

    표의 왼쪽 칸은 전부 개발팀에게 일이 생긴다는 뜻이고,
    오른쪽 칸은 전부 엔지니어가 혼자 처리할 수 있다는 뜻입니다.
    1편에서 그은 경계선의 물리적 실체가 바로 이 프로세스입니다.
  


  

    MSP 관점
    

      고객사마다 백엔드가 달라도 앱에 주는 설정은 동일하게 유지할 수 있습니다.
      "옆에 있는 Collector로 보내세요"가 전부이고, 그 뒤는 고객사별 Collector 설정으로 흡수합니다.
      온보딩 문서를 고객사 수만큼 만들지 않아도 되는 이유가 이것입니다.
    

  


  
Collector도 결국 하나의 서비스입니다

  

    잊기 쉬운 사실인데, Collector는 운영해야 하는 또 하나의 컴포넌트입니다.
    죽으면 텔레메트리가 끊기고, 메모리가 부족하면 데이터를 버리고, 설정이 틀리면 조용히 아무것도 안 합니다.
    그래서 8절에서 다룰 자기 관측이 중요합니다.
    "Collector를 누가 감시하는가"는 도입 초기에 반드시 답해야 할 질문입니다.
  










  SECTION 02
  
파이프라인 구조

  

    Collector는 다섯 종류의 부품으로 이뤄집니다.
    이 중 앞의 셋이 실제 데이터 흐름을 만듭니다.
  


  

    
Receiver · 받는다
데이터가 들어오는 입구. OTLP로 밀어넣는 방식(push)과 Prometheus처럼 긁어오는 방식(pull)이 있습니다.

    
Processor · 가공한다
속성 추가·삭제, 필터링, 배치, 샘플링. 순서대로 실행되며 이 순서가 결과를 바꿉니다.

    
Exporter · 내보낸다
백엔드로 전송하는 출구. 여러 개를 동시에 연결해 같은 데이터를 여러 곳으로 보낼 수 있습니다.

  

  

    
Connector · 잇는다
한 파이프라인의 출구를 다른 파이프라인의 입구로 연결합니다. 트레이스를 받아 메트릭을 만들어내는 식의 신호 변환도 합니다.

    
Extension · 곁들인다
데이터 흐름에 관여하지 않는 부가 기능. 헬스체크 엔드포인트, 프로파일링, 인증 등이 여기 해당합니다.

  


  
핵심은 파이프라인 정의입니다

  

    설정 파일에서 컴포넌트를 선언하는 것과 실제로 사용하는 것은 별개입니다.
    service.pipelines에 나열되지 않은 컴포넌트는 정의만 되고 동작하지 않습니다.
    "설정을 넣었는데 적용이 안 된다"는 제보의 절반이 여기서 나옵니다.
  


# 위쪽은 '선언' — 이것만으로는 아무 일도 하지 않습니다
receivers:
  otlp: ...
processors:
  batch: ...
  memory_limiter: ...        # 선언만 하고 파이프라인에 안 넣으면 무용지물
exporters:
  otlp/tempo: ...

# 아래쪽이 '사용' — 실제 데이터 흐름
service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [batch]     # memory_limiter가 빠져 있음
      exporters:  [otlp/tempo]


  

    이름에 슬래시를 붙이는 이유
    

      otlp/tempo, otlp/vendor처럼 같은 종류의 컴포넌트를 여러 개 쓸 때 구분하는 표기입니다.
      슬래시 앞은 컴포넌트 종류, 뒤는 자유롭게 붙이는 별칭입니다.
      백엔드 두 곳으로 동시에 보내거나, 포트가 다른 수신기를 두 개 열 때 씁니다.
    

  










  SECTION 03
  
실제 설정 파일 읽기

  

    히어로의 빌더가 만들어내는 것과 같은 구조입니다.
    실무에서 가장 흔한 Agent 설정을 통째로 보겠습니다.
  



receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318      # Python·Node.js가 주로 쓰는 쪽

processors:
  memory_limiter:                 # 반드시 맨 앞
    check_interval: 1s
    limit_percentage: 80
    spike_limit_percentage: 25

  k8sattributes:                  # 파드·네임스페이스 정보 자동 부착
    passthrough: false
    extract:
      metadata:
        - k8s.namespace.name
        - k8s.pod.name
        - k8s.node.name
        - k8s.deployment.name

  resourcedetection:
    detectors: [env, system]
    timeout: 2s

  batch:                          # 반드시 맨 뒤
    timeout: 5s
    send_batch_size: 1024
    send_batch_max_size: 2048

exporters:
  otlp/gateway:
    endpoint: otel-gateway.observability:4317
    tls:
      insecure: false
    sending_queue:                # 백엔드 장애 시 버티는 장치
      enabled: true
      queue_size: 5000
    retry_on_failure:
      enabled: true
      initial_interval: 5s
      max_elapsed_time: 300s

extensions:
  health_check:
    endpoint: 0.0.0.0:13133

service:
  extensions: [health_check]
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, k8sattributes, resourcedetection, batch]
      exporters:  [otlp/gateway]
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, k8sattributes, resourcedetection, batch]
      exporters:  [otlp/gateway]
  telemetry:                       # Collector 자신의 상태 (8절)
    metrics:
      level: detailed


  

    sending_queue와 retry를 빠뜨리지 마세요
    

      기본 설정만으로 띄우면 백엔드가 잠깐 끊겼을 때 그동안의 데이터가 그냥 사라집니다.
      큐와 재시도는 Collector를 두는 핵심 이유 중 하나인데도
      예제 설정을 그대로 복사하다 빠뜨리는 경우가 많습니다.
      큐가 가득 차면 새 데이터를 거부하므로, 큐 사용률은 반드시 감시 대상에 넣어야 합니다(8절).
    

  










  SECTION 04
  
컴포넌트 카탈로그

  

    수백 개가 있지만 실무에서 반복해 쓰는 것은 이 정도입니다.
  


  

    
    
    
    
    
  


  

    
데이터가 들어오는 입구입니다. push는 앱이 밀어넣는 방식, pull은 Collector가 주기적으로 긁어오는 방식입니다.

    

      
otlp
표준 수신기. gRPC(4317)와 HTTP(4318)를 동시에 열 수 있습니다. 거의 모든 구성의 출발점입니다.

      
prometheus
Prometheus 방식으로 메트릭을 긁어옵니다. 기존 exporter 자산을 그대로 흡수할 수 있습니다.

      
filelog
파일에서 로그를 읽습니다. 쿠버네티스 컨테이너 로그 수집의 기본 수단입니다.

      
hostmetrics
노드의 CPU·메모리·디스크·네트워크 지표를 수집합니다.

      
kubeletstats
kubelet에서 파드·컨테이너 단위 리소스 사용량을 가져옵니다.

      
k8s_cluster
클러스터 수준 상태(디플로이먼트 레플리카 수 등)를 수집합니다. 클러스터당 하나만 띄워야 합니다.

      
jaeger · zipkin
기존 시스템에서 보내던 트레이스를 그대로 받습니다. 마이그레이션 기간에 유용합니다.

      
kafka
Kafka를 텔레메트리 버퍼로 쓸 때 사용합니다. 대규모 환경의 완충 장치입니다.

    

  


  

    
데이터를 가공합니다. 파이프라인에 적은 순서대로 실행되므로 순서가 결과를 바꿉니다(5절).

    

      
memory_limiter
메모리 사용량을 감시해 한계에 가까워지면 데이터를 거부합니다. Collector가 OOM으로 죽는 것을 막는 자기 보호 장치. 항상 맨 앞.

      
batch
데이터를 모아 한 번에 내보냅니다. 전송 효율을 크게 높입니다. 항상 맨 뒤.

      
k8sattributes
파드 IP를 단서로 네임스페이스·파드명·노드명·레이블을 자동으로 붙입니다. 2편에서 말한 Resource 속성의 인프라 부분을 담당합니다.

      
resourcedetection
클라우드 환경(리전·가용영역·인스턴스 ID)과 호스트 정보를 감지해 붙입니다.

      
resource
리소스 속성을 직접 추가·수정·삭제합니다. 테넌트 구분값을 넣을 때 자주 씁니다.

      
attributes
Span·메트릭·로그의 속성을 조작합니다. 민감정보 키 삭제나 해싱에 사용합니다.

      
filter
조건에 맞는 데이터를 통째로 버립니다. 헬스체크 경로 제외가 대표적인 용도입니다.

      
transform
OTTL 표현식으로 데이터를 변형합니다. 가장 유연하지만 가장 복잡하며, 9편에서 집중적으로 다룹니다.

      
tail_sampling
트레이스가 끝난 뒤 내용을 보고 남길지 결정합니다. Gateway에서만 의미가 있습니다(9편).

      
probabilistic_sampler
비율 기반으로 단순하게 걸러냅니다. 내용을 보지 않으므로 가볍습니다.

    

  


  

    
백엔드로 내보냅니다. 하나의 파이프라인에 여러 익스포터를 달아 같은 데이터를 여러 곳에 보낼 수 있습니다.

    

      
otlp
gRPC로 OTLP 전송. Agent → Gateway 구간의 기본값입니다.

      
otlphttp
HTTP로 OTLP 전송. 프록시나 방화벽 환경에서 gRPC가 막힐 때 씁니다.

      
prometheusremotewrite
Prometheus 호환 저장소로 메트릭을 씁니다. 메트릭 전용입니다.

      
loadbalancing
trace_id 기준으로 특정 Gateway 인스턴스에 라우팅합니다. 테일 샘플링을 쓰려면 필수입니다(9편).

      
debug
표준 출력에 데이터를 찍습니다. 파이프라인이 동작하는지 확인하는 가장 빠른 방법입니다.

      
file
파일로 저장합니다. 검증이나 재현 테스트에 유용합니다.

      
kafka
Kafka로 내보냅니다. 백엔드 앞단에 버퍼를 두는 구성에 씁니다.

      
벤더 익스포터
상용 관측 플랫폼 전용 익스포터. 대부분은 OTLP를 직접 받으므로 필요 없는 경우도 많습니다.

    

  


  

    
파이프라인과 파이프라인을 잇습니다. 한쪽에서는 익스포터처럼, 다른 쪽에서는 리시버처럼 동작합니다.

    

      
spanmetrics
트레이스를 보고 요청 수·에러 수·지연 히스토그램을 자동 생성합니다. 앱이 메트릭을 안 내보내도 골든 시그널을 얻을 수 있습니다.

      
routing
속성 값에 따라 서로 다른 파이프라인으로 보냅니다. 멀티테넌트 분기에 씁니다.

      
forward
파이프라인을 단순히 이어붙입니다. 공통 전처리를 한 곳에 모을 때 유용합니다.

      
count
지나가는 데이터의 개수를 메트릭으로 만듭니다. 데이터량 추이를 볼 때 씁니다.

    

    

      spanmetrics는 도입 초기에 특히 유용합니다
      
개발팀이 아직 메트릭 계측을 안 했어도, 트레이스만 들어오면 서비스별 요청 수·에러율·p99 대시보드를 만들 수 있습니다. 다만 샘플링된 트레이스로 계산하면 실제 값과 어긋나므로, 샘플링 전 단계에 배치해야 합니다.

    

  


  

    
데이터 흐름에는 관여하지 않지만 운영에 필요한 기능들입니다.

    

      
health_check
쿠버네티스 liveness·readiness 프로브가 찌를 엔드포인트를 제공합니다. 사실상 필수입니다.

      
pprof
Go 프로파일링 엔드포인트. Collector 자체가 느리거나 메모리를 많이 쓸 때 원인을 찾습니다.

      
zpages
브라우저로 파이프라인 상태를 들여다보는 디버그 페이지입니다.

      
basicauth · oauth2client
백엔드 인증 정보를 익스포터에 제공합니다.

      
file_storage
전송 대기 큐를 디스크에 저장합니다. Collector가 재시작해도 데이터를 잃지 않습니다.

      
headers_setter
들어온 요청의 헤더를 내보내는 요청에 전달합니다. 멀티테넌트 인증 전달에 씁니다.

    

  










  SECTION 05
  
프로세서 순서가 결과를 바꾼다

  

    프로세서는 파이프라인에 적은 순서대로 실행됩니다.
    같은 프로세서를 넣어도 순서가 다르면 다르게 동작합니다.
  


  
왜 순서가 중요한가

  

    

      
batch가 memory_limiter보다 앞

      
배치에 데이터가 쌓인 뒤에야 메모리 검사가 일어납니다. 이미 메모리를 다 쓴 뒤라 보호 장치가 무력해집니다.

    

    

      
filter가 batch보다 뒤

      
버릴 데이터까지 배치에 모았다가 나중에 버립니다. 메모리와 CPU를 낭비합니다.

    

    

      
k8sattributes가 filter보다 뒤

      
네임스페이스 기준으로 필터링하고 싶은데, 필터 시점에는 아직 그 속성이 없습니다. 조건이 아무것도 못 맞춥니다.

    

    

      
권장 순서

      
보호 → 속성 추가 → 걸러내기·변형 → 샘플링 → 배치. 각 단계가 다음 단계의 입력을 준비하는 구조입니다.

    외우는 대신 원리로 기억하세요
    

      memory_limiter는 문지기라 맨 앞,
      batch는 포장이라 맨 뒤입니다.
      그 사이는 "정보를 붙인 다음에 그 정보로 판단한다"는 순서입니다.
      속성을 붙이는 프로세서가 먼저 오고, 그 속성을 보고 거르거나 바꾸는 프로세서가 뒤에 옵니다.
      샘플링은 판단이 끝난 뒤 마지막 결정이라 배치 직전입니다.
    

  










  SECTION 06
  
배포 토폴로지

  

    같은 Collector 바이너리를 어디에 몇 개 띄우느냐의 문제입니다.
    실무에서는 대부분 Agent + Gateway 2단으로 수렴합니다.
  


  

    

      
형태배포 방식잘하는 일한계

      
        
AgentDaemonSet · 노드당 1개앱과 가까워 전송이 빠름. 노드·파드 메타데이터 부착. 노드 로그·메트릭 수집노드 단위라 전체를 보는 처리(테일 샘플링)는 불가

        
GatewayDeployment · 소수테일 샘플링, 중앙 집중 정책, 백엔드 인증 일원화, 멀티테넌트 라우팅단일 장애 지점이 될 수 있어 스케일링·이중화 필요

        
Sidecar파드마다 1개파드 단위 완전 격리. 특정 앱 전용 설정파드 수만큼 리소스 소비. 관리 대상 급증

        
Collector 없음앱 → 백엔드 직접구성이 가장 단순1절 표의 왼쪽 칸을 전부 앱이 감당

      
    

  


  
우리 환경에는 무엇이 맞나

  

    
1. 규모가 어느 정도입니까?

    

      
      
      
    

    
2. 테일 샘플링이나 중앙 정책이 필요합니까?

    

      
      
    

    
두 질문에 답하면 권장 구성이 표시됩니다.

  


  

    Agent만으로 테일 샘플링을 시도하면 안 됩니다
    

      테일 샘플링은 한 트레이스의 모든 Span을 한곳에서 봐야 판단할 수 있습니다.
      Span들이 여러 노드에 흩어져 있으면 각 Agent가 자기가 본 일부만 보고 결정하게 되고,
      결과적으로 트레이스가 조각조각 남습니다.
      그래서 Gateway가 필요하고, 그 앞에 loadbalancing 익스포터로
      같은 trace_id는 같은 Gateway 인스턴스로 보내야 합니다. 9편의 핵심 주제입니다.
    

  










  SECTION 07
  
배포판과 커스텀 빌드

  

    Collector는 하나가 아닙니다. 어떤 컴포넌트를 담았느냐에 따라 여러 배포판이 있습니다.
  


  

    
Core
핵심 컴포넌트만 담은 최소 배포판. OTLP 수신·전송과 기본 프로세서 정도입니다. 실무에는 거의 부족합니다.

    
Contrib
커뮤니티 컴포넌트를 전부 담은 배포판. 대부분 여기서 시작합니다. 대신 이미지가 크고 사용하지 않는 컴포넌트도 함께 들어 있습니다.

    
커스텀 빌드
필요한 컴포넌트만 골라 직접 빌드합니다. 이미지 크기와 공격 표면이 줄어듭니다.

  


  
커스텀 빌드 — ocb

  

    ocb(OpenTelemetry Collector Builder)는 YAML 목록을 받아 Collector 바이너리를 만들어 줍니다.
    운영이 안정화된 뒤 이미지를 줄이고 싶을 때 쓰면 좋습니다.
  


# builder-config.yaml
dist:
  name: acme-otelcol
  output_path: ./_build

receivers:
  - gomod: go.opentelemetry.io/collector/receiver/otlpreceiver v0.x.x

processors:
  - gomod: go.opentelemetry.io/collector/processor/batchprocessor v0.x.x
  - gomod: go.opentelemetry.io/collector/processor/memorylimiterprocessor v0.x.x
  - gomod: github.com/open-telemetry/opentelemetry-collector-contrib/processor/k8sattributesprocessor v0.x.x

exporters:
  - gomod: go.opentelemetry.io/collector/exporter/otlpexporter v0.x.x

# 빌드
$ ocb --config builder-config.yaml


  

    도입 순서 조언
    

      처음부터 커스텀 빌드로 시작하지 마세요.
      contrib로 운영하며 실제로 어떤 컴포넌트를 쓰는지 파악한 뒤 줄이는 것이 순서입니다.
      미리 줄이면 필요한 컴포넌트가 없어서 다시 빌드하는 일이 반복됩니다.
      그리고 커스텀 빌드를 쓰면 버전 업그레이드도 직접 관리해야 한다는 점을 계산에 넣으세요.
    

  


  
버전 관리

  

    Collector는 릴리스 주기가 매우 짧습니다.
    latest 태그를 쓰면 어느 날 갑자기 동작이 바뀔 수 있으므로 반드시 버전을 고정하세요.
    참고로 프로파일 신호 관련 기능은 v0.148.0부터 들어갔습니다.
    업그레이드할 때는 릴리스 노트에서 설정 항목 변경과 폐기 예고를 확인하는 것이 습관이 되어야 합니다.
  










  SECTION 08
  
Collector 자기 관측

  

    "관측 시스템을 누가 관측하는가."
    이 질문에 답하지 못하면 어느 날 조용히 데이터가 사라져도 아무도 모릅니다.
  


  
반드시 봐야 할 지표

  

    

      
지표 계열무엇을 알려주나이상 신호

      
        
receiver accepted / refused받은 것과 거부한 것refused가 0이 아니면 memory_limiter가 동작 중 — 용량 부족

        
processor dropped프로세서가 버린 양필터·샘플링 의도와 일치하는지 확인

        
exporter sent / send_failed내보낸 것과 실패한 것send_failed 증가는 백엔드 장애 또는 인증 만료

        
exporter queue size전송 대기 중인 양계속 증가하면 곧 유실 시작

        
process memory · CPUCollector 자원 사용한도에 근접하면 스케일 아웃 또는 배치 조정

      
    

  


  
자기 관측 설정


service:
  telemetry:
    metrics:
      level: detailed
      # Collector 자신의 메트릭을 OTLP로 내보내거나
      # Prometheus 엔드포인트로 노출합니다
    logs:
      level: info
      encoding: json


  

    자기 자신에게 보내지 마세요
    

      Collector의 메트릭을 그 Collector 자신을 거쳐 백엔드로 보내면,
      Collector가 죽었을 때 "죽었다는 사실을 알려줄 데이터"도 함께 사라집니다.
      Collector 자신의 상태는 별도 경로로 내보내는 것이 원칙입니다.
      Prometheus가 직접 긁어가게 하거나, Agent의 지표는 Gateway로, Gateway의 지표는 백엔드로 직접 보내는 식으로 분리하세요.
    

  


  
알림을 걸어둘 최소 세 가지

  
    
    
  1. Collector 파드가 살아 있는가 — health_check 기반 프로브 실패
    2. 
    
  2. send_failed가 증가하고 있는가 — 백엔드 연결·인증 문제
    3. 
    
  3. refused 또는 queue size가 증가하고 있는가 — 용량 부족, 곧 유실 시작
    4. 
  

  

    이 세 가지만 걸어두면 "데이터가 안 보인다"는 제보를 받기 전에 먼저 알 수 있습니다.
    3편의 트러블슈팅 트리에서 마지막 단계가 "엔지니어 영역"으로 끝났던 이유가 여기 있습니다.

7편 핵심 정리

  
    
    
  • Collector는 책임을 앱에서 인프라로 옮기는 장치입니다. 백엔드 교체·마스킹·샘플링이 전부 설정 작업이 됩니다
    • 
    
  • 구조는 Receiver → Processor → Exporter. 선언만으로는 동작하지 않고 service.pipelines에 넣어야 합니다
    • 
    
  • 프로세서 순서는 memory_limiter 맨 앞, batch 맨 뒤, 그 사이는 "붙인 다음 판단"
    • 
    
  • Agent + Gateway 2단이 실무의 기본형. 테일 샘플링은 Gateway에서만 가능합니다
    • 
    
  • sending_queue와 retry_on_failure를 빠뜨리지 마세요
    • 
    
  • Collector 자신의 상태를 별도 경로로 관측하고 최소 세 가지 알림을 걸어두세요
    •
