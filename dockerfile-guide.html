01

이미지, 컨테이너, 그리고 레이어

Dockerfile을 쓰기 전에 반드시 알아야 할 딱 세 개의 단어

가장 흔한 비유로 시작하겠습니다. Dockerfile은 레시피, 이미지는 그 레시피로 만든 냉동식품, 컨테이너는 그걸 데워서 접시에 담은 한 끼입니다. 레시피 하나로 냉동식품을 여러 개 찍어낼 수 있고, 냉동식품 하나로 여러 끼를 데울 수 있습니다.

레이어(Layer)는 왜 중요한가

이미지는 하나의 통짜 파일이 아니라 여러 겹의 얇은 파일시스템 변경분이 쌓인 구조입니다. 포토샵의 레이어, 또는 투명 필름을 여러 장 겹쳐 하나의 그림을 만드는 것과 같습니다. 이 구조 때문에 Docker에는 초보자를 자주 당황시키는 두 가지 성질이 생깁니다.

재사용된다

레이어는 해시로 식별됩니다. 이미 만든 적 있는 레이어는 다시 만들지 않고 캐시에서 꺼내 씁니다. 그래서 두 번째 빌드가 훨씬 빠릅니다. 서로 다른 이미지가 같은 베이스 레이어를 공유하기도 합니다.

지워지지 않는다

한 번 쌓인 레이어는 되돌릴 수 없습니다. 3번 레이어에서 만든 1GB 파일을 4번 레이어에서 지워도 이미지 용량은 줄지 않습니다. 아래 레이어에 그 파일이 그대로 남아 있기 때문입니다.

핵심 규칙 1

“만들고 → 쓰고 → 지우는” 작업은 반드시 하나의 RUN 안에서 끝내십시오. 레이어는 RUN이 끝나는 순간 스냅샷으로 굳습니다.

02

Dockerfile과 빌드 컨텍스트

docker build . 의 그 점(.)이 무엇인지 아십니까

첫 빌드 명령은 보통 이렇게 배웁니다.

terminal
# -t 는 이미지 이름(tag), 마지막 점(.)은 빌드 컨텍스트 경로
docker build -t myapp:1.0 .

여기서 마지막 점(.)이 Dockerfile의 위치가 아니라 “빌드 컨텍스트”라는 사실이 첫 번째 함정입니다. 빌드 컨텍스트는 Docker 엔진에게 통째로 전송되는 디렉터리입니다. COPY와 ADD는 오직 이 컨텍스트 안의 파일만 볼 수 있습니다. 컨텍스트 바깥의 ../secret.key 같은 경로는 절대 복사할 수 없습니다.

신입이 자주 겪는 일

“빌드가 시작도 안 하고 transferring context: 1.4GB에서 몇 분씩 멈춰요.” → node_modules, .git, venv가 통째로 전송되고 있는 겁니다. .dockerignore가 없어서 생기는 증상이며, 8장에서 해결합니다.

Dockerfile 위치를 따로 지정하려면

# 현재 폴더가 컨텍스트, ./Dockerfile 을 자동으로 찾음
docker build -t myapp:1.0 .
# -f 로 Dockerfile 경로를 명시. 컨텍스트는 여전히 마지막 인자(.)
docker build -f Dockerfile.prod -t myapp:prod .
docker build -f docker/Dockerfile.gpu -t myapp:gpu .
# 컨텍스트는 저장소 루트, Dockerfile 은 하위 서비스에 위치
# → 공통 라이브러리(libs/)도 COPY 할 수 있게 됨
docker build -f services/api/Dockerfile -t api:1.0 .

# Dockerfile 안에서는 루트 기준 경로로 작성
#   COPY libs/         /app/libs/
#   COPY services/api/ /app/

Dockerfile 작성의 기본 규칙 4가지

  • 대문자 명령어 + 소문자 인자가 관례입니다. 문법상 소문자도 되지만 가독성을 위해 지킵니다.
  • 한 줄에 명령어 하나. 길어지면 \로 줄바꿈합니다.
  • 주석은 #로 시작합니다. 단, 첫 줄의 # syntax=는 주석이 아니라 BuildKit 지시자입니다.
  • 파일 이름은 Dockerfile. 확장자가 없습니다. Dockerfile.txt로 저장되지 않게 주의하십시오.

FROM — 모든 것의 시작

FROM <이미지>:<태그> AS <스테이지이름>

# 예시
FROM python:3.12-slim
FROM node:20-alpine AS builder
FROM gcr.io/distroless/static-debian12
FROM scratch                 # 완전히 빈 이미지 (Go 정적바이너리용)
# ── 태그 선택 가이드 ──────────────────────────────
FROM python            # ✗ latest. 어제와 오늘이 다른 이미지가 됨
FROM python:3          # △ 마이너 버전이 멋대로 올라감
FROM python:3.12       # ○ 무난. 패치는 따라감
FROM python:3.12-slim  # ◎ 권장. 약 150MB, 대부분의 웹앱에 충분
FROM python:3.12-alpine # △ 50MB지만 musl libc라 C확장 빌드가 깨질 수 있음

# 용량 감각 (대략)
#   python:3.12         ~1.0 GB   빌드 도구 다 포함
#   python:3.12-slim    ~150 MB   런타임 위주
#   python:3.12-alpine  ~50 MB    musl 기반
#   distroless          ~20 MB    셸조차 없음
# 프로덕션·규제 환경에서는 digest 로 완전 고정
# 같은 태그라도 내용물이 바뀔 수 있지만 digest 는 절대 안 바뀜
FROM python:3.12-slim@sha256:a1b2c3d4e5f6...

# 현재 태그의 digest 확인법
#   docker buildx imagetools inspect python:3.12-slim
#   docker inspect --format='{{index .RepoDigests 0}}' python:3.12-slim
Alpine을 언제 피해야 하나

Alpine은 glibc 대신 musl libc를 씁니다. Python의 numpy, pandas처럼 미리 컴파일된 wheel을 쓰는 패키지는 Alpine용 wheel이 없어 소스에서 직접 컴파일하게 됩니다. 빌드가 20분씩 걸리고 결국 이미지가 slim보다 커지는 역설이 생깁니다. Python은 slim, Go는 alpine 또는 scratch가 안전한 기본값입니다.

RUN — 빌드 시점에 명령 실행

# ✗ 나쁜 예 — 3개 레이어, 캐시된 목록이 낡아서 install 실패 가능
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git

# ◎ 좋은 예 — 1개 레이어, 캐시 정합성 확보, 찌꺼기 제거
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      curl \
      git \
      ca-certificates \
 && rm -rf /var/lib/apt/lists/*

# --no-install-recommends : 권장 패키지 제외. 보통 30~50% 절감
# rm -rf /var/lib/apt/lists/* : 패키지 인덱스 삭제 (~40MB)
# 대화형 프롬프트 방지가 필요하면
#   ENV DEBIAN_FRONTEND=noninteractive  (또는 ARG 로)
# Alpine: --no-cache 하나로 인덱스 정리까지 끝남
RUN apk add --no-cache curl git ca-certificates

# 빌드에만 필요한 패키지는 가상 그룹으로 묶어 통째로 제거
RUN apk add --no-cache --virtual .build-deps gcc musl-dev \
 && pip install --no-cache-dir -r requirements.txt \
 && apk del .build-deps
# ── shell 형식 ── /bin/sh -c 로 감싸서 실행
RUN echo $HOME && ls -al        # 변수 확장·파이프·&& 사용 가능

# ── exec 형식 ── 셸 없이 직접 실행
RUN ["/bin/bash", "-c", "echo hello"]

# RUN 은 보통 shell 형식이 편합니다.
# exec 형식이 결정적으로 중요한 건 CMD/ENTRYPOINT 입니다 (4장).

상황COPYADD권장
로컬 파일/폴더 복사가능가능COPY
로컬 tar.gz 자동 압축 해제불가자동 해제ADD (의도가 명확할 때만)
원격 URL 다운로드불가가능(압축 해제는 안 됨)RUN curl + 체크섬 검증
다른 스테이지에서 가져오기COPY --from=불가COPY
 
COPY requirements.txt /app/
COPY src/ /app/src/
COPY . .                              # 컨텍스트 전체 → WORKDIR

# 소유자를 지정하며 복사 (root로 복사 후 chown 하면 레이어가 2배가 됨)
COPY --chown=appuser:appgroup src/ /app/src/

# 권한까지 지정 (BuildKit)
COPY --chmod=755 entrypoint.sh /usr/local/bin/

# 다른 스테이지의 산출물만 가져오기 (멀티스테이지의 핵심)
COPY --from=builder /app/dist /usr/share/nginx/html

# 다른 이미지에서 바로 가져오기
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
# ✗ 뒤에 슬래시가 없으면 "파일로" 복사됩니다
COPY config.yaml /etc/app      # /etc/app 라는 "파일"이 생김
COPY config.yaml /etc/app/     # /etc/app/config.yaml (의도한 결과)

# ✗ 컨텍스트 바깥은 접근 불가 — 무조건 에러
COPY ../shared/lib /app/lib
  → forbidden path outside the build context
  해결: 컨텍스트를 상위 폴더로 올리고 -f 로 Dockerfile 경로 지정

# ✗ 소스 폴더 자체가 복사될 거라 기대
COPY src/ /app/              # src "내용물"이 /app 바로 아래로 들어감
COPY src/ /app/src/          # /app/src/ 로 폴더째 유지

WORKDIR · EXPOSE · USER · LABEL · HEALTHCHECK

# ✗ RUN cd 는 그 줄에서만 유효합니다. 다음 RUN 은 다시 / 에서 시작
RUN cd /app
RUN npm install          # /app 이 아니라 / 에서 실행됨!

# ◎ WORKDIR 은 이후 모든 명령의 기준 경로를 바꿉니다
WORKDIR /app            # 폴더가 없으면 자동 생성 (mkdir -p 불필요)
RUN npm install
COPY . .                # 목적지 "." 은 /app 을 의미

# 상대경로로 중첩도 가능
WORKDIR /app
WORKDIR backend          # 결과: /app/backend
EXPOSE 8080
EXPOSE 8080/tcp 9090/udp

# ⚠ 오해 금지: EXPOSE 는 포트를 "열지" 않습니다.
#   - 이건 순수한 문서화 + 메타데이터입니다.
#   - 실제 개방은 실행할 때 -p 로 합니다.
#       docker run -p 18080:8080 myapp
#                     ↑호스트   ↑컨테이너
#   - docker run -P (대문자) 는 EXPOSE 된 포트를 랜덤 포트로 자동 매핑
#   - Kubernetes 는 EXPOSE 를 무시합니다. Service/containerPort 로 정의
# 기본값은 root(uid 0). 컨테이너 탈출 시 피해가 커집니다.

── Debian/Ubuntu 계열 ──
RUN groupadd -r -g 10001 app \
 && useradd -r -u 10001 -g app -d /app -s /sbin/nologin app
USER app

── Alpine 계열 ──
RUN addgroup -g 10001 -S app && adduser -u 10001 -S app -G app
USER app

── 이미 존재하는 계정 사용 ──
USER node            # node 공식 이미지에 내장
USER nginx
USER 10001:10001     ◎ K8s runAsNonRoot 와 가장 궁합이 좋음(숫자 UID)

# 순서 주의: USER 이후의 RUN 은 권한이 없어 설치가 실패합니다.
# 설치·chown 을 모두 끝낸 뒤 마지막에 USER 를 선언하십시오.
# OCI 표준 라벨을 쓰면 레지스트리·스캐너가 자동으로 인식합니다
LABEL org.opencontainers.image.title="aiops-portal" \
      org.opencontainers.image.description="AIOps 관리 포털 API" \
      org.opencontainers.image.source="https://git.example.com/aiops/portal" \
      org.opencontainers.image.version="1.4.2" \
      org.opencontainers.image.revision="$GIT_SHA" \
      org.opencontainers.image.licenses="Apache-2.0"

# 조회
#   docker inspect --format='{{json .Config.Labels}}' myapp:1.0 | jq
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s --retries=3 \
  CMD curl -fsS http://localhost:8080/healthz || exit 1

# 옵션 뜻
#   --interval      점검 주기
#   --timeout       이 시간 넘으면 실패로 간주
#   --start-period  기동 유예 시간. 이 동안의 실패는 카운트 안 함
#   --retries       연속 N회 실패 시 unhealthy

# curl 이 없는 슬림/distroless 이미지라면
HEALTHCHECK CMD wget -qO- http://localhost:8080/healthz || exit 1
HEALTHCHECK CMD ["/app/healthcheck"]   # Go 정적 바이너리 동봉

# ⚠ Kubernetes 는 HEALTHCHECK 를 사용하지 않습니다.
#   liveness / readiness / startup Probe 로 따로 정의하십시오.
04

CMD vs ENTRYPOINT

가장 많이 헷갈리는 주제. 조합을 직접 눌러 결과를 확인해 보십시오

둘 다 “컨테이너가 시작될 때 무엇을 실행할지”를 정합니다. 차이는 덮어쓰기 방식입니다. 한 문장으로 정리하면 이렇습니다.

한 줄 정리

ENTRYPOINT = 바꿀 수 없는 실행 파일 · CMD = 바꿀 수 있는 기본 인자. 최종 실행 명령은 ENTRYPOINT + CMD를 이어붙인 것입니다.

Interactive · 실행 명령 조립기
Dockerfile 설정과 docker run 인자를 골라 실제로 실행될 명령을 확인합니다.
Dockerfile 설정
docker run 뒤에 붙인 인자

exec 형식과 shell 형식 — 신호(signal)의 문제

이 차이는 “컨테이너가 종료 명령에 반응하는가”를 결정합니다. 배포 중에 파드가 30초씩 안 죽는 문제의 원인이 대부분 여기 있습니다.

단, exec 형식은 변수 확장이 안 됩니다

CMD ["python", "app.py", "--port=$PORT"]에서 $PORT는 문자 그대로 전달됩니다. 셸이 없기 때문입니다. 변수가 꼭 필요하면 entrypoint.sh 스크립트를 만들고 그 안 마지막 줄에 exec "$@"를 쓰십시오. exec가 있어야 스크립트가 PID 1 자리를 애플리케이션에게 넘겨줍니다.

#!/bin/sh
set -e

# 1) 기동 전 준비 작업
echo "[entrypoint] DB 대기 중..."
until nc -z "$DB_HOST" "$DB_PORT"; do sleep 1; done

# 2) 환경변수 기반 설정 파일 렌더링
envsubst < /app/config.tmpl > /app/config.yaml

# 3) ★ exec 로 CMD 를 실행 — PID 1 을 앱에게 넘김
exec "$@"
COPY --chmod=755 entrypoint.sh /usr/local/bin/entrypoint.sh
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0"]

# 실행 흐름
#   entrypoint.sh 가 준비 작업 → exec "$@" 로 uvicorn 을 PID 1 로 교체
#   docker run myapp python manage.py migrate  ← CMD 만 바꿔 다른 작업 실행 가능

ARG vs ENV

“빌드할 때만 쓰는 값”과 “컨테이너 안에 남는 값”
# ARG: 빌드 시점 변수. 기본값 지정 가능
ARG APP_VERSION=1.0.0
ARG BUILD_DATE

# ENV: 런타임 환경변수
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    TZ=Asia/Seoul

# ARG 값을 ENV 로 넘겨 런타임에도 남기기 (버전 표시 등)
ENV APP_VERSION=${APP_VERSION}

# 빌드
#   docker build --build-arg APP_VERSION=2.1.0 -t myapp:2.1.0 .
# ✗ FROM 이전에 선언한 ARG 는 FROM 이후에 보이지 않습니다
ARG PY_VER=3.12
FROM python:${PY_VER}-slim
RUN echo "버전: ${PY_VER}"      # → 빈 문자열!

# ◎ FROM 이후에 다시 선언해야 합니다 (기본값 없이 재선언하면 값 상속)
ARG PY_VER=3.12
FROM python:${PY_VER}-slim
ARG PY_VER
RUN echo "버전: ${PY_VER}"      # → 3.12 정상 출력

# 규칙 요약
#   FROM 앞의 ARG  = 글로벌 ARG. FROM 라인에서만 쓸 수 있음
#   FROM 뒤의 ARG  = 해당 스테이지 안에서만 유효
#   멀티스테이지면 스테이지마다 다시 선언
# ✗✗ 절대 금지 — 이미지 히스토리에 평문으로 영구 기록됩니다
ARG GITHUB_TOKEN
ENV DB_PASSWORD="P@ssw0rd!"
RUN git clone https://${GITHUB_TOKEN}@github.com/org/private.git
#   docker history myapp  →  토큰이 그대로 노출됨
#   중간 레이어를 지워도 남습니다. 멀티스테이지로도 완전히 못 지웁니다.

# ◎ BuildKit secret mount — 레이어에 절대 기록되지 않음
# syntax=docker/dockerfile:1.7
RUN --mount=type=secret,id=gh_token \
    GITHUB_TOKEN=$(cat /run/secrets/gh_token) \
    && git clone https://${GITHUB_TOKEN}@github.com/org/private.git

# 빌드 명령
#   docker build --secret id=gh_token,env=GITHUB_TOKEN -t myapp .
#   docker build --secret id=gh_token,src=./token.txt  -t myapp .

# SSH 키가 필요하다면
RUN --mount=type=ssh git clone git@github.com:org/private.git
#   docker build --ssh default -t myapp .
확인해 보십시오

지금 만든 이미지에 비밀값이 남았는지 1초 만에 확인하는 방법입니다.

docker history --no-trunc myapp:1.0 | grep -i -E "token|password|secret|key"

레이어 캐시 실험실

빌드가 10분에서 8초로 줄어드는 이유. 직접 눌러 보십시오

Docker는 각 명령어마다 “이 명령이 이전과 똑같은가”를 확인해 캐시를 재사용합니다. 판단 기준은 이렇습니다.

  • RUN — 명령어 문자열이 같은가 (실제 실행 결과가 아니라 글자만 비교합니다)
  • COPY·ADD — 복사 대상 파일의 내용 체크섬과 메타데이터가 같은가
  • 그리고 결정적으로 — 바로 위 레이어가 캐시 히트였는가
캐시의 도미노 법칙

한 레이어가 깨지면 그 아래 모든 레이어가 전부 다시 실행됩니다. 그래서 “자주 바뀌는 것을 최대한 아래에” 두는 것이 Dockerfile 최적화의 전부라고 해도 과언이 아닙니다.

Interactive · 캐시 시뮬레이터
Dockerfile 배치를 고르고, 무엇을 수정했는지 선택하면 각 레이어의 캐시 상태를 계산합니다.
방금 무엇을 수정했습니까?
FROM python:3.12-slim
WORKDIR /app
COPY . .                                    # 소스 1글자만 바꿔도 여기서 캐시 파괴
RUN pip install -r requirements.txt        # → 매번 전체 재설치 (3~10분)
CMD ["python", "app.py"]
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .                    # 의존성 목록만 먼저
RUN pip install --no-cache-dir -r requirements.txt   # 의존성 안 바뀌면 캐시 히트
COPY . .                                    # 자주 바뀌는 소스는 맨 마지막
CMD ["python", "app.py"]

# 결과: 소스만 고쳤을 때 빌드가 5분 → 5초
# syntax=docker/dockerfile:1.7
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .

# 캐시 마운트: 레이어에 포함되지 않으면서 빌드 간에 유지되는 디렉터리
# 의존성이 "바뀌었을 때조차" 변경분만 내려받습니다
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# 다른 언어 예시
#  npm  : --mount=type=cache,target=/root/.npm
#  go   : --mount=type=cache,target=/go/pkg/mod \
#         --mount=type=cache,target=/root/.cache/go-build
#  maven: --mount=type=cache,target=/root/.m2
#  apt  : --mount=type=cache,target=/var/cache/apt,sharing=locked

CI 러너에서 캐시가 항상 비어 있다면

GitHub Actions나 Kubernetes 기반 러너는 매번 새 환경에서 시작하므로 로컬 캐시가 없습니다. 이때는 레지스트리를 캐시 저장소로 사용합니다.

buildx cache
# 레지스트리에 캐시를 저장하고 다음 빌드에서 가져오기
docker buildx build \
  --cache-from type=registry,ref=harbor.example.com/app/myapp:buildcache \
  --cache-to   type=registry,ref=harbor.example.com/app/myapp:buildcache,mode=max \
  -t harbor.example.com/app/myapp:1.0 --push .

# mode=max : 중간 스테이지 캐시까지 저장 (멀티스테이지에 필수)
# GitHub Actions 라면 type=gha 가 더 간편합니다
#   --cache-from type=gha --cache-to type=gha,mode=max

.dockerignore

파일 하나로 빌드 속도, 이미지 크기, 보안이 동시에 좋아집니다

.dockerignore는 .gitignore와 문법이 거의 같습니다. Dockerfile과 같은 위치(컨텍스트 루트)에 둡니다. 효과는 세 가지입니다. ① 컨텍스트 전송량이 줄어 빌드가 빨라지고, ② COPY . .가 쓰레기를 안 담아 이미지가 작아지고, ③ .env·인증서 같은 비밀 파일이 이미지에 섞이는 사고를 막습니다.

코드 리뷰에서 지적받기 전에 스스로 확인할 항목
root로 실행하지 않기

컨테이너의 root는 기본적으로 호스트의 root와 같은 UID입니다. 취약점 하나로 호스트까지 위험해집니다. USER 10001:10001을 마지막에 선언하십시오.

비밀값을 이미지에 굽지 않기

ENV·ARG·COPY .env 모두 히스토리에 남습니다. --mount=type=secret이나 런타임 주입(K8s Secret)을 쓰십시오.

베이스 이미지 최소화

이미지에 없는 패키지는 취약점도 없습니다. slim → distroless 순으로 줄이면 CVE 리포트가 수백 건에서 한 자릿수로 떨어집니다.

버전 고정

latest는 재현이 불가능합니다. 태그를 고정하고, 규제 환경이라면 digest까지 고정하십시오. 패키지도 curl=8.5.0-*처럼 핀 할 수 있습니다.

읽기 전용 파일시스템 대비

운영에서는 readOnlyRootFilesystem: true로 뜨는 경우가 많습니다. 쓰기가 필요한 경로는 /tmp로 몰고 emptyDir을 마운트하도록 설계하십시오.

멀티 아키텍처 빌드

Apple Silicon 노트북에서 만든 이미지가 x86 서버에서 안 도는 이유

컨테이너 이미지는 CPU 아키텍처에 종속됩니다. M 시리즈 맥(arm64)에서 빌드한 이미지를 x86_64 서버에 배포하면 exec format error가 납니다. 반대도 마찬가지입니다. buildx로 여러 아키텍처를 한 번에 빌드하면 해결됩니다. 

# ① QEMU 에뮬레이터 등록 (한 번만)
docker run --privileged --rm tonistiigi/binfmt --install all

# ② 멀티플랫폼 지원 빌더 생성
docker buildx create --name multi --driver docker-container --use
docker buildx inspect --bootstrap

# ③ 두 아키텍처를 한 번에 빌드 후 push
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t harbor.example.com/app/myapp:1.0 \
  --push .

# ⚠ --push 없이 --load 로는 멀티플랫폼 이미지를 로컬에 못 넣습니다
#   로컬 테스트는 한 플랫폼씩
#   docker buildx build --platform linux/arm64 -t myapp:arm --load .
# QEMU 에뮬레이션은 매우 느립니다(5~20배).
# BUILDPLATFORM 을 써서 "빌드는 네이티브로, 출력만 타깃으로" 하십시오.

# syntax=docker/dockerfile:1.7
# --platform=$BUILDPLATFORM : 빌더 자신의 아키텍처로 컴파일 스테이지 실행
FROM --platform=$BUILDPLATFORM golang:1.23-alpine AS builder

# BuildKit 이 자동으로 채워주는 변수들
ARG TARGETOS       # linux
ARG TARGETARCH     # amd64 | arm64
ARG TARGETPLATFORM # linux/arm64
ARG BUILDPLATFORM  # 빌더의 플랫폼

WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -o /out/server ./cmd/server

# 런타임 스테이지는 타깃 플랫폼 이미지 사용 (기본 동작)
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/server /server
ENTRYPOINT ["/server"]

# 결과: arm64 빌드가 QEMU 없이 x86 러너에서 네이티브 속도로 완료
# 레지스트리의 이미지가 어떤 아키텍처를 지원하는지
docker buildx imagetools inspect harbor.example.com/app/myapp:1.0

# 출력 예시
#   Manifests:
#     Platform: linux/amd64
#     Platform: linux/arm64

# 로컬 이미지의 아키텍처
docker image inspect myapp:1.0 --format '{{.Os}}/{{.Architecture}}'

# 노드의 아키텍처 (Kubernetes)
kubectl get nodes -o custom-columns=\
NAME:.metadata.name,ARCH:.status.nodeInfo.architecture

# 특정 아키텍처 노드에만 배포하려면 nodeSelector 사용
#   nodeSelector:
#     kubernetes.io/arch: arm64
이기종 클러스터를 운영한다면

ARM 노드와 x86 노드를 함께 쓰는 클러스터에서는 모든 사내 이미지를 멀티아치로 빌드하는 것을 기본 정책으로 잡는 편이 낫습니다. 그렇지 않으면 스케줄러가 배치한 노드에 따라 파드가 무작위로 CrashLoopBackOff에 빠지고, 원인을 찾는 데 반나절이 걸립니다.

트러블슈팅 15선

실무에서 실제로 마주치는 에러 메시지와 그 원인. 제목을 눌러 펼치십시오
ERROR: failed to solve: failed to compute cache key: failed to calculate checksum of ref ...: "/app.py": not found

원인

세 가지 중 하나입니다. ① 파일이 빌드 컨텍스트 안에 없음, ② .dockerignore가 그 파일을 제외하고 있음, ③ 경로 오타 또는 대소문자 불일치(리눅스는 대소문자를 구분합니다).

해결

확인 순서
# 1) 컨텍스트 루트에서 파일이 실제로 보이는지
ls -la ./app.py

# 2) .dockerignore 가 걸러내고 있진 않은지
grep -n "app" .dockerignore

# 3) 빌드 컨텍스트가 어디인지 재확인
docker build -f docker/Dockerfile -t app .    # 컨텍스트는 "." 이지 "docker/" 가 아님

# 4) 컨텍스트에 실제로 무엇이 들어갔는지 눈으로 보기
docker build --no-cache --progress=plain -t ctx-check . 2>&1 | head -30
잊기 쉬운 규칙

COPY ../shared처럼 컨텍스트 밖은 원천적으로 불가능합니다. 모노레포라면 컨텍스트를 저장소 루트로 올리고 -f로 Dockerfile 경로만 따로 지정하십시오.

원인 1 · 윈도우 줄바꿈(CRLF)

Windows에서 작성한 스크립트의 첫 줄이 #!/bin/sh\r이 됩니다. 리눅스는 /bin/sh\r라는 실행 파일을 찾다가 실패합니다. “파일이 있는데 없다고 한다”는 증상의 90%가 이것입니다.

원인 2 · Alpine에 bash가 없음

#!/bin/bash로 시작하는데 베이스가 Alpine이면 bash가 없습니다. #!/bin/sh를 쓰거나 apk add bash 하십시오.

원인 3 · 실행 권한 없음

# CRLF 제거

원인

이미지 아키텍처와 노드 아키텍처가 다릅니다. M 시리즈 맥(arm64)에서 빌드해서 x86 서버에 올렸거나, 그 반대입니다. ARM 노드와 x86 노드가 섞인 클러스터라면 “어떤 노드에 스케줄되느냐”에 따라 성공하기도 실패하기도 합니다.

두 번째 원인

Go 바이너리를 CGO_ENABLED=1(기본값)로 빌드한 뒤 scratch나 distroless/static에 넣어도 비슷한 증상이 납니다. 동적 링크된 glibc를 못 찾기 때문입니다. CGO_ENABLED=0으로 정적 빌드하십시오.

원인

COPY . .가 의존성 설치보다 위에 있습니다. 소스 코드 한 글자만 바꿔도 그 아래 모든 레이어의 캐시가 무효화됩니다(6장의 도미노 법칙).

수정
# Before
COPY . .
RUN pip install -r requirements.txt

# After
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
COPY . .

# 어떤 단계에서 캐시가 깨졌는지 로그로 확인
docker build --progress=plain -t myapp . 2>&1 | grep -E "CACHED|RUN|COPY"
#   CACHED 표시가 없는 첫 줄이 범인입니다
PermissionError: [Errno 13] Permission denied: '/app/logs/app.log' EACCES: permission denied, mkdir '/app/data'

원인

USER app으로 전환했는데, 그 디렉터리는 root 소유로 만들어졌습니다. COPY는 기본적으로 uid 0으로 복사하고, RUN mkdir도 그 시점의 사용자(보통 root) 소유가 됩니다.

해결
# USER 전환 전에 필요한 디렉터리와 소유권을 모두 준비
RUN mkdir -p /app/logs /app/data \
 && chown -R 10001:10001 /app

COPY --chown=10001:10001 . /app

USER 10001:10001

# ⚠ COPY 후 RUN chown 을 하면 레이어가 두 배가 됩니다(파일이 복제됨).
#    반드시 COPY --chown 을 쓰십시오.

# K8s 에서 readOnlyRootFilesystem: true 라면 애초에 쓰기를 피하고
# 로그는 stdout 으로 내보내는 것이 컨테이너 표준입니다.
#   volumeMounts: - name: tmp / mountPath: /tmp

원인

컨테이너는 PID 1 프로세스가 끝나면 종료됩니다. 데몬 모드로 백그라운드에 보내면 메인 프로세스가 즉시 끝나므로 컨테이너도 함께 죽습니다.

사례별 수정

CMD ["service", "nginx", "start"]           # 같은 문제

CMD ["nginx", "-g", "daemon off;"]           # 포그라운드 유지
CMD ["node", "server.js"]                   # 서버 프로세스가 살아있음

원인

shell 형식 CMD 때문입니다. /bin/sh -c가 PID 1이 되고, 실제 앱은 자식 프로세스가 됩니다. sh는 SIGTERM을 자식에게 전달하지 않으므로 앱은 종료 신호를 영영 받지 못하고, 유예 시간이 지나 SIGKILL로 강제 종료됩니다.

해결
CMD python app.py                       # PID 1 = /bin/sh
CMD ["python", "app.py"]                # PID 1 = python

# 스크립트를 거쳐야 한다면 마지막에 exec 필수
#   exec "$@"

쿠버네티스에서의 영향

롤링 업데이트 때마다 파드가 terminationGracePeriodSeconds(기본 30초)를 꽉 채우고 강제 종료됩니다. 진행 중이던 요청이 끊기고, 배포 시간이 파드 수만큼 늘어납니다.

가장 흔합니다. 앱이 127.0.0.1에만 리스닝하면 컨테이너 내부에서만 접근 가능합니다. 반드시 0.0.0.0에 바인딩하십시오.

# Flask

# Express

# -p 방향 헷갈림 주의

원인

apt-get update가 별도의 RUN 레이어에 있고 그 레이어가 캐시 히트되었습니다. 며칠 전 캐시된 패키지 목록에 적힌 버전이 저장소에서 이미 삭제된 상태입니다. 유명한 “stale cache” 문제입니다.

해결
RUN apt-get update
RUN apt-get install -y curl        # update 는 캐시, install 만 재실행 → 404

RUN apt-get update && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

원인 1 · 출력 버퍼링

Python이 stdout이 터미널이 아닐 때 출력을 버퍼에 모아둡니다. 컨테이너가 죽으면 그 로그는 영영 사라집니다.

원인 2 · 파일로 로그를 씀

컨테이너의 표준 관행은 stdout/stderr로 내보내고 수집은 플랫폼에 맡기는 것입니다. 파일에 쓰면 로그 수집기가 못 읽고, 디스크도 채웁니다.

해결
# Python
ENV PYTHONUNBUFFERED=1
#   또는  CMD ["python", "-u", "app.py"]

# Node.js 는 기본적으로 stdout 이 비버퍼링이라 대개 문제 없음

# Nginx 공식 이미지가 쓰는 기법 — 로그 파일을 stdout 으로 심볼릭 링크
RUN ln -sf /dev/stdout /var/log/nginx/access.log \
 && ln -sf /dev/stderr /var/log/nginx/error.log
