설계 원칙

랩은 한 번 만들고 22편 동안 계속 씁니다. 처음 설계가 나중의 실험 속도를 결정하므로, 다음 다섯 원칙을 지킵니다.

  1. 기준선은 의견이 없어야 한다. kubeadm 클러스터에는 꼭 필요한 것(CNI, metrics-server, 감사, 암호화, 백업)만 넣습니다. 스토리지·Ingress·LB는 일부러 비워 두고, 각 편에서 하나씩 채우며 비교합니다.
  2. 되돌릴 수 있어야 한다. 기준선에는 VM 스냅샷 지점을 세 개(OS 준비 완료, CNI 설치 전, 기준선 완료) 만듭니다. 4편의 CNI 교체 실험, 14편의 스토리지 실험은 이 지점에서 출발합니다.
  3. 같은 질문을 같은 방식으로. 감사 정책, 네임스페이스 이름, 테스트 매니페스트를 여섯 환경에서 똑같이 씁니다. 차이는 환경에서만 나오게 합니다.
  4. 클라우드는 켤 때만 존재한다. 매니지드 클러스터는 설정 파일로 선언해 두고, 실습 때 만들고 끝나면 지웁니다. 30분이면 다시 생깁니다.
  5. 랩도 운영 대상이다. 인증서 만료, etcd 백업, 공개 엔드포인트 접근 제한은 랩에서도 지킵니다. 습관은 랩에서 만들어집니다.

2-2. 모든 노드 공통 준비

스왑 끄기, 커널 모듈과 sysctl, containerd 2.x, kubeadm·kubelet·kubectl 1.37 설치입니다. 세 노드에서 똑같이 실행합니다(multipass exec <노드> -- sudo bash -s < node-prep.sh).

node-prep.sh
#!/usr/bin/env bash
set -euo pipefail
K8S_MINOR=v1.37

# 1) 스왑 끄기 (kubelet 기본값 failSwapOn: true)
swapoff -a
sed -ri '/\sswap\s/s/^#?/#/' /etc/fstab

# 2) 커널 모듈과 sysctl
cat >/etc/modules-load.d/k8s.conf <<EOF
overlay
br_netfilter
EOF
modprobe overlay; modprobe br_netfilter
cat >/etc/sysctl.d/99-k8s.conf <<EOF
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sysctl --system >/dev/null

# 3) containerd 2.x (Docker 저장소의 containerd.io 패키지)
apt-get update -q
apt-get install -yq ca-certificates curl gpg jq
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release; echo $VERSION_CODENAME) stable" \
  >/etc/apt/sources.list.d/docker.list
apt-get update -q && apt-get install -yq containerd.io

# 패키지 기본 설정은 CRI 플러그인을 꺼 두므로 기본 설정을 새로 만든다
containerd config default >/etc/containerd/config.toml
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
systemctl restart containerd
containerd config dump | grep -i systemdcgroup   # true 여야 함

# 4) kubeadm·kubelet·kubectl (pkgs.k8s.io, 마이너별 저장소)
curl -fsSL https://pkgs.k8s.io/core:/stable:/${K8S_MINOR}/deb/Release.key \
  | gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/${K8S_MINOR}/deb/ /" \
  >/etc/apt/sources.list.d/kubernetes.list
apt-get update -q && apt-get install -yq kubelet kubeadm kubectl
apt-mark hold kubelet kubeadm kubectl containerd.io
systemctl enable kubelet

# 5) 확인: cgroup v2 (1.35부터 v1 노드는 기본 거부)
stat -fc %T /sys/fs/cgroup   # cgroup2fs
kubeadm version -o short
설명 containerd의 SystemdCgroup과 kubelet의 cgroupDriver가 어긋나면 컨트롤 플레인 Pod가 이유 없이 재시작을 반복합니다(9장 첫 사례). kubelet은 1.34부터 CRI에서 cgroup 드라이버를 자동으로 알아내지만, 양쪽을 systemd로 명시해 두는 편이 진단이 쉽습니다. 마이너 버전마다 저장소 경로가 다르므로, 다음 업그레이드(23편) 때는 K8S_MINOR를 바꿔 저장소부터 교체합니다.

2-3. 감사 정책과 저장 시 암호화 설정 (cp1)

2편의 감사 정책을 그대로 쓰고, 2편 실습 4에서 평문으로 보였던 Secret을 처음부터 암호화합니다. 랩에서는 aescbc를 쓰고, KMS v2와 키 교체는 22편에서 다룹니다.

cp1에서 (sudo)
mkdir -p /etc/kubernetes/audit /etc/kubernetes/enc /var/log/kubernetes/audit

cat >/etc/kubernetes/audit/audit-policy.yaml <<'EOF'
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
- level: None
  nonResourceURLs: ["/livez*", "/readyz*", "/healthz*"]
- level: None
  users: ["system:kube-proxy"]
  verbs: ["watch"]
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets", "configmaps"]
- level: RequestResponse
  verbs: ["create", "update", "patch", "delete"]
- level: Metadata
EOF

KEY=$(head -c 32 /dev/urandom | base64)
cat >/etc/kubernetes/enc/encryption-config.yaml <<EOF
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: ["secrets"]
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: ${KEY}
  - identity: {}
EOF
chmod 600 /etc/kubernetes/enc/encryption-config.yaml
함정: 이 파일이 곧 모든 Secret의 열쇠 암호화 설정 파일을 잃으면 etcd 백업이 있어도 Secret을 복구할 수 없습니다. 2-9단계의 백업 스크립트가 이 파일을 PKI와 함께 묶어 보관하는 이유입니다.

2-10. 인증서 만료 점검

/usr/local/sbin/k8s-cert-check.sh + 주간 타이머
#!/usr/bin/env bash
# 30일 이내 만료 인증서가 있으면 경고를 journal에 남기고 0이 아닌 코드로 종료
set -uo pipefail
WARN_DAYS=30; rc=0
for c in /etc/kubernetes/pki/*.crt /etc/kubernetes/pki/etcd/*.crt; do
  end=$(openssl x509 -enddate -noout -in "$c" | cut -d= -f2)
  days=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))
  printf '%-55s %4d일\n' "$c" "$days"
  [ "$days" -lt "$WARN_DAYS" ] && { logger -p user.warning "k8s cert $c expires in $days days"; rc=1; }
done
kubeadm certs check-expiration
exit $rc

같은 방식으로 k8s-cert-check.service·.timer를 만들고 OnCalendar=weekly로 둡니다. 2편 10장의 “어느 날 아침 kubectl이 안 붙는다” 사례를 예방하는 최소 장치입니다.

#!/usr/bin/env bash
# 현재 컨텍스트에서 공통 스모크 테스트를 실행하고 한 줄로 요약한다
set -uo pipefail
NS=smoke-$RANDOM; CTX=$(kubectl config current-context)
k(){ kubectl -n "$NS" "$@"; }
kubectl create ns "$NS" >/dev/null
kubectl label ns "$NS" pod-security.kubernetes.io/enforce=restricted >/dev/null
MAN=smoke.yaml
# OpenShift: 고정 UID는 SCC가 거부하므로 제거하고 SCC가 배정하게 둔다 (9장 마지막 사례)
if kubectl api-resources --api-group=config.openshift.io -o name 2>/dev/null | grep -q .; then
  MAN=$(mktemp); sed -E 's/, runAsUser: [0-9]+//' smoke.yaml > "$MAN"
fi
k apply -f "$MAN" >/dev/null

DEP=$(k rollout status deploy/web --timeout=180s >/dev/null 2>&1 && echo OK || echo FAIL)
k wait pod/client --for=condition=Ready --timeout=120s >/dev/null 2>&1
DNS=$(k exec client -- curl -s -m 5 -o /dev/null -w '%{http_code}' http://web:8080 2>/dev/null || echo ERR)

LB=pending
for i in $(seq 1 18); do
  v=$(k get svc web-lb -o jsonpath='{.status.loadBalancer.ingress[0].ip}{.status.loadBalancer.ingress[0].hostname}')
  [ -n "$v" ] && { LB=assigned; break; }; sleep 5
done

PVC=$(k get pvc data -o jsonpath='{.status.phase}')
for i in $(seq 1 18); do [ "$PVC" = Bound ] && break; sleep 5; PVC=$(k get pvc data -o jsonpath='{.status.phase}'); done
SC=$(kubectl get sc -o jsonpath='{range .items[?(@.metadata.annotations.storageclass\.kubernetes\.io/is-default-class=="true")]}{.metadata.name}{end}')

# NetworkPolicy: web으로 들어오는 트래픽을 모두 막은 뒤 다시 호출
k apply -f - >/dev/null <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: deny-web}
spec:
  podSelector: {matchLabels: {app: web}}
  policyTypes: ["Ingress"]
EOF
sleep 10
code=$(k exec client -- curl -s -m 5 -o /dev/null -w '%{http_code}' http://web:8080 2>/dev/null)
[ "$code" = "200" ] && NP="NOT-enforced" || NP="enforced"

MET=$(kubectl top nodes >/dev/null 2>&1 && echo OK || echo FAIL)
printf '%-12s deploy=%-4s svc+dns=%-3s lb=%-8s pvc=%-8s defaultSC=%-22s netpol=%-12s metrics=%s\n' \
  "$CTX" "$DEP" "$DNS" "$LB" "${PVC:-none}" "${SC:-none}" "$NP" "$MET"
kubectl delete ns "$NS" --wait=false >/dev/null

구축 중 자주 막히는 곳

컨트롤 플레인 Pod가 몇 분마다 재시작한다

증상. kubeadm init은 성공했지만 kube-apiserver, etcd가 CrashLoopBackOff 없이 조용히 재시작을 반복하고, kubectl이 간헐적으로 끊깁니다.

원인. containerd의 SystemdCgroup이 false인데 kubelet은 systemd 드라이버를 씁니다. 두 관리자가 같은 cgroup을 다르게 다루면서 컨테이너가 죽습니다.

해결. containerd config dump | grep SystemdCgroup으로 확인하고 true로 바꾼 뒤 containerd·kubelet 재시작. 2-2 스크립트가 이 확인을 포함하는 이유입니다.

kubectl logs·exec가 “tls: internal error”로 실패한다

원인. serverTLSBootstrap: true인데 kubelet 서빙 인증서 CSR이 승인되지 않았습니다. kubelet이 서빙할 인증서가 없어 API 서버의 연결을 받지 못합니다. 새 노드를 추가하거나 인증서가 갱신될 때마다 다시 생깁니다.

해결. 2-8의 승인 명령. 운영이라면 자동 승인기. 이 증상은 2편에서 본 “컨트롤 플레인 → 노드 방향 경로” 문제의 또 다른 얼굴이기도 합니다.

CNI 설치 후 일부 Pod만 외부와 통신이 안 된다

원인. Pod CIDR이 호스트 LAN·VPN·Docker 브리지 대역과 겹쳤습니다. Calico 예제 기본값 192.168.0.0/16을 그대로 쓴 경우가 대부분입니다.

해결. 1장 주소 계획대로 10.244.0.0/16을 쓰고, 이미 만든 클러스터라면 pre-cni 스냅샷으로 돌아가 다시 설치합니다. 운영 클러스터에서 Pod CIDR 변경은 사실상 재구축입니다.

OpenShift Local이 시작 단계에서 멈춘다

원인. 메모리 부족(모니터링을 켰는데 14GiB 미만), 중첩 가상화, 오래된 번들의 인증서 갱신 지연, 또는 VPN 클라이언트의 DNS 가로채기(*.crc.testing 해석 실패)가 흔합니다.

해결. crc start --log-level debug로 멈춘 단계를 확인하고, 메모리를 늘리거나 모니터링을 끄고, VPN을 끈 상태로 재시도합니다.

클라우드 클러스터 생성이 쿼터에서 실패한다

원인. 새 계정·구독·프로젝트의 기본 vCPU 쿼터, 스팟 용량 부족, 리전별 인스턴스 유형 미제공.

해결. EKS는 인스턴스 유형을 여러 개 지정해 두었고(5-1), AKS는 az vm list-usage -l koreacentral -o table, GKE는 gcloud compute regions describe asia-northeast3로 쿼터를 확인해 상향 요청합니다. 스팟 노드가 회수되면 Pod가 재배치되는 것도 관찰 대상입니다(23편).

스모크 테스트에서 client Pod가 OpenShift에서만 뜨지 않는다

원인. 매니페스트에 고정 UID를 지정했는데, 네임스페이스에 할당된 UID 범위 밖이라 SCC가 거부한 경우입니다. OpenShift는 네임스페이스마다 UID 범위를 배정하고 restricted-v2 SCC가 그 범위만 허용합니다.

해결. 7장의 smoke.sh는 OpenShift를 감지하면 이 필드를 자동으로 지웁니다. 직접 매니페스트를 쓸 때는 runAsUser를 지우고 SCC가 배정하게 두거나, 테스트 목적이라면 네임스페이스 범위 안의 값을 씁니다(oc get ns <ns> -o yaml | grep uid-range). 1편 3장 “보안 컨텍스트 전제”가 실제로 깨지는 모습이며, 21편에서 SCC와 PSA를 나란히 다룹니다.
