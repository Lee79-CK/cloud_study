12편Neutron 2: OVN으로 보는 패킷의 여행

11편에서 만든 네트워크·라우터·보안 그룹은 결국 각 노드의 가상 스위치에 들어간 흐름 규칙이 됩니다. 이번 편은 그 번역 과정을 층층이 열어 보고, 패킷 하나가 VM에서 다른 노드의 VM으로, 그리고 인터넷까지 가는 길을 따라갑니다. 마지막으로 ovn-trace로 “패킷이 어디서 버려졌는지” 찾는 법을 익힙니다.

약 120분예상 학습 시간
3·11편 이수격리망·OVN 둘·Neutron 객체
시뮬레이터·분해도패킷 여행 6종, Geneve
다음 편13편 Swift · Manila

섹션 1

이 편의 목표

  1. Neutron 객체가 Northbound DB → ovn-northd → Southbound DB → ovn-controller → OVS 흐름으로 번역되는 과정을 설명한다.
  2. NB·SB의 주요 테이블과 Neutron 객체의 이름 대응을 읽는다.
  3. Geneve 터널의 머리말 구조와 VNI·포트 키의 의미, MTU와의 관계를 설명한다.
  4. 같은 망·다른 노드·다른 망·인터넷 방향(SNAT)·외부에서 들어오기(플로팅 IP)의 패킷 경로를 단계별로 말한다.
  5. 분산 라우팅과 게이트웨이 섀시(중앙 처리)의 차이, 분산 플로팅 IP의 조건을 설명한다.
  6. 보안 그룹이 포트 그룹·ACL·conntrack으로 구현되는 모습을 확인한다.
  7. ovn-nbctl · ovn-sbctl · ovn-trace · ovs-appctl로 통신 장애 지점을 찾는다.

이 편의 비유: 도시 교통 체계

Neutron은 도시 계획서(어디에 길과 교차로가 있어야 하는지), NB DB는 그 계획서의 공식 도면, ovn-northd는 도면을 교통 규칙집으로 바꾸는 번역가, SB DB는 그 규칙집과 “어느 차가 어느 구역에 있는지” 기록하는 관제 센터, ovn-controller는 각 구역의 신호등 관리자, OVS 흐름은 실제 신호등입니다. Geneve 터널은 구역 사이를 잇는 지하 도로입니다.

섹션 2

OVN 큰 그림

Neutron API사용자가 만든 네트워크·포트·라우터·보안 그룹을 Neutron DB에 저장하고, ML2/OVN 드라이버가 NB DB에 논리 설계도로 씁니다. (OCP Pod)
▼ 논리 스위치·라우터·ACL·NAT 기록
Northbound DB“무엇이 있어야 하는가”(의도). 물리 위치 정보가 없습니다. (ovsdbserver-nb Pod, 3개 Raft 클러스터)
▼ ovn-northd가 번역
Southbound DB“어떻게 처리하는가”(논리 흐름) + “어디에 있는가”(어느 노드에 어느 포트가 붙었나). (ovsdbserver-sb Pod)
▼ 각 노드의 ovn-controller가 구독
ovn-controller자기 노드에 필요한 논리 흐름만 받아 OpenFlow 규칙으로 바꾸고, 자기 노드에 붙은 포트를 SB에 보고합니다. (컴퓨트 노드 컨테이너, 게이트웨이 역할 OCP 노드 Pod)
▼ OpenFlow 설치
OVS (br-int)실제 패킷을 처리하는 가상 스위치. 커널 데이터 경로가 빠르게 전달하고, 처음 보는 흐름만 사용자 공간에서 규칙을 찾아 캐시합니다.

핵심 원칙 두 가지

  • Neutron DB가 원본입니다. NB DB는 Neutron이 계속 맞춰 쓰는 사본이므로, NB를 직접 고치면 다음 동기화 때 되돌아가거나 Neutron과 어긋납니다. 어긋났을 때는 Neutron이 제공하는 동기화 도구로 맞춥니다.
  • OVN에는 “라우터 서버”가 따로 없습니다. 라우팅·NAT·DHCP·보안 그룹이 모두 각 노드의 흐름 규칙으로 분산되어 있습니다. 그래서 장애를 볼 때 “어느 노드의 어느 단계에서 버려졌나”를 찾는 것이 핵심입니다.

용어 하나: OVN에서 노드를 섀시(chassis)라고 부릅니다. 컴퓨트 노드, 게이트웨이 역할 노드가 모두 섀시이며, 각 섀시는 SB DB에 자기 이름과 터널 주소(Encap)를 등록합니다.

섹션 6

ovn-controller와 br-int

각 노드의 ovn-controller는 OVS 설정(Open_vSwitch 테이블의 external_ids)을 읽어 자기가 누구이며 어디에 연결해야 하는지 압니다.

external_ids 키뜻예
ovn-remoteSB DB 주소internalapi 망의 MetalLB VIP (3편)
ovn-encap-type · ovn-encap-ip터널 종류와 이 노드의 터널 주소geneve · tenant 망 IP
ovn-bridge-mappingsphysnet → 브리지 (11편)datacentre:br-ex
ovn-cms-options추가 역할 표시enable-chassis-as-gw = 게이트웨이 후보
system-id · hostname섀시 이름노드 재설치 시 중복 섀시 원인

br-int 안에 보이는 것

  • VM 포트(tap…): external_ids:iface-id가 Neutron 포트 UUID와 같아야 ovn-controller가 “내 노드에 그 포트가 있다”고 SB에 보고(바인딩)합니다.
  • 터널 포트(ovn-xxxxxx-0): 다른 섀시마다 하나씩 Geneve 터널.
  • 패치 포트: br-int ↔ br-ex 연결. OVN은 프로바이더 망 포트가 실제로 필요할 때 만듭니다.
# 컴퓨트 노드에서
sudo ovs-vsctl show                                         # br-int, br-ex, 터널 포트
sudo ovs-vsctl get open . external_ids                      # ovn-remote, encap-ip, bridge-mappings
sudo podman exec ovn_controller ovn-appctl -t ovn-controller connection-status   # SB 연결 상태
sudo ovs-ofctl dump-flows br-int | wc -l                    # 설치된 흐름 개수(수천~수만 개가 정상)
sudo ovs-vsctl --columns=name,external_ids find interface external_ids:iface-id=<포트 UUID>

conntrack: 연결을 기억하는 장부

보안 그룹의 상태 저장, NAT의 응답 되돌리기는 리눅스 커널의 연결 추적(conntrack)을 씁니다. OVN은 포트마다 conntrack 구역(zone)을 나눠, 같은 주소를 쓰는 서로 다른 프로젝트의 연결이 섞이지 않게 합니다.

11편 MTU 계산과의 연결

MTU는 IP 패킷 크기 기준이므로, 바깥 이더넷(14)을 뺀 바깥 IP 20 + UDP 8 + Geneve 기본 8 + OVN 옵션 8 + 안쪽 이더넷 14 = 58바이트가 터널 때문에 추가됩니다. 그래서 물리망 1500이면 VM 쪽 MTU는 1442가 됩니다. 터널 패킷이 물리망 MTU를 넘으면 조용히 버려지므로, tenant 망 스위치 MTU는 9000(점보)으로 두는 것이 일반적인 권장입니다.

# 터널 트래픽 눈으로 보기 (컴퓨트 노드, tenant 망 인터페이스)
sudo tcpdump -ni <tenant 인터페이스> udp port 6081 -c 5

섹션 8

논리 파이프라인: 패킷이 지나는 검문소

ovn-northd는 논리 스위치·라우터마다 ingress(들어올 때)와 egress(나갈 때) 파이프라인을 만듭니다. 각 단계(table)는 조건이 맞으면 동작(next, drop, output 등)을 합니다. 대표 단계만 추렸습니다(실제 단계 이름·번호는 OVN 버전에 따라 다름).

파이프라인대표 단계하는 일
논리 스위치 ingressls_in_port_sec_l2/ip포트 보안: 등록된 MAC·IP인가 (11편 섹션 10)
ls_in_acl보안 그룹의 나가는(egress) 규칙 검사 — VM에서 스위치로 들어오는 방향
ls_in_arp_rsp알려진 IP의 ARP에 스위치가 대신 응답 (브로드캐스트 감소)
ls_in_dhcp_*DHCP 요청에 직접 응답 (11편)
ls_in_l2_lkup목적지 MAC으로 출구 포트 결정 (라우터 MAC이면 라우터로)
논리 스위치 egressls_out_acl보안 그룹의 들어오는(ingress) 규칙 검사 — 스위치에서 VM으로 나가는 방향
ls_out_port_sec_l2목적지 포트 보안
논리 라우터lr_in_dnat플로팅 IP의 목적지 변환
lr_in_ip_routing경로 결정, TTL 감소
lr_in_arp_resolve다음 홉 MAC 결정
lr_out_snatSNAT·플로팅 IP의 출발지 변환

방향이 헷갈리는 이유

보안 그룹의 “egress(VM에서 나감)” 규칙은 OVN 스위치 입장에서는 패킷이 들어오는 것이므로 ls_in_acl(from-lport)에서, “ingress(VM으로 들어옴)” 규칙은 스위치에서 VM 쪽으로 나가는 것이므로 ls_out_acl(to-lport)에서 검사됩니다. ovn-trace 출력을 읽을 때 이 뒤집힘을 기억하세요.

섹션 9

패킷 여행 시뮬레이터

시나리오를 고르고 단계를 넘겨 보세요. 어느 노드의 어느 부품에서 무슨 일이 일어나는지, 패킷 머리말이 어떻게 바뀌는지 보여 줍니다. 환경: compute-0(web-01 10.0.0.15, web-02 10.0.0.16), compute-1(web-03 10.0.0.17, db-01 10.0.1.20), 게이트웨이 섀시(OCP 노드), 외부망 203.0.113.0/24.

섹션 10

분산 라우팅과 게이트웨이

트래픽어디서 처리되나이유
동서(east-west): 같은 프로젝트의 다른 서브넷 사이출발 VM이 있는 노드에서 라우팅까지 끝내고 목적지 노드로 바로 터널논리 라우터가 모든 노드에 분산되어 있음 (분산 라우팅)
남북(north-south) SNAT: VM → 인터넷 (플로팅 IP 없음)게이트웨이 섀시(라우터 외부 포트가 바인딩된 노드)라우터 외부 IP 하나를 여러 VM이 공유하므로 한곳에서 연결을 추적해야 함
플로팅 IP (중앙)게이트웨이 섀시분산 플로팅 IP를 쓰지 않는 구성
플로팅 IP (분산)VM이 있는 컴퓨트 노드에서 바로 NAT 후 외부망으로Neutron enable_distributed_floating_ip + 컴퓨트 노드가 외부망 브리지 매핑을 가짐

게이트웨이 섀시와 고가용성

  • 라우터의 외부 포트는 chassisredirect 포트(cr-lrp-…)로 표현되어 한 번에 한 섀시에만 바인딩됩니다.
  • 후보 섀시(게이트웨이 역할 노드)들에 우선순위가 매겨지고(HA_Chassis_Group), 섀시끼리 BFD로 생존을 확인합니다. 현재 섀시가 죽으면 다음 우선순위 섀시로 옮겨 갑니다(수 초 단절).
  • 후보 섀시는 ovn-cms-options=enable-chassis-as-gw로 표시됩니다. RHOSO에서는 OCP 노드의 ovn-controller(OVNController의 nicMappings), 전용 네트워커 NodeSet, 또는 외부망이 연결된 컴퓨트 노드가 될 수 있습니다(3편).
oc exec -n openstack ovsdbserver-nb-0 -- ovn-nbctl --db=unix:/etc/ovn/ovnnb_db.sock list HA_Chassis_Group
oc exec -n openstack ovsdbserver-sb-0 -- ovn-sbctl --db=unix:/etc/ovn/ovnsb_db.sock find Port_Binding type=chassisredirect
openstack network agent list | grep -i gateway       # OVN Controller Gateway agent

설계 판단: 분산 플로팅 IP

분산 플로팅 IP는 게이트웨이 병목과 단일 장애 영향을 줄이지만, 모든 컴퓨트 노드가 외부망(VLAN)에 붙어야 하고 외부 스위치가 플로팅 IP의 MAC이 노드 사이를 옮겨 다니는 것을 배워야 합니다. 고객사 네트워크팀과 외부망 VLAN을 컴퓨트 노드 전체에 트렁크할 수 있는지 먼저 협의하세요(24편).

섹션 11

보안 그룹이 ACL이 되기까지

  1. Neutron 보안 그룹 하나 → NB의 Port_Group 하나(pg_<보안 그룹 UUID>). 그 그룹을 쓰는 포트들이 멤버가 됩니다.
  2. 보안 그룹 규칙 하나 → Port_Group에 붙은 ACL 하나. 동작은 allow-related(허용 + 연결 추적으로 응답도 허용).
  3. 모든 포트는 기본 거부용 그룹(neutron_pg_drop)에도 속해 있어, 허용 ACL보다 낮은 우선순위의 drop ACL이 걸려 있습니다. 그래서 “어느 규칙에도 맞지 않으면 차단”이 됩니다.
  4. 원격 그룹 규칙(--remote-group)은 그 그룹 멤버들의 주소 집합(address set)을 조건에 넣어 표현됩니다. 멤버가 늘면 집합만 갱신됩니다.
  5. ovn-northd가 ACL을 ls_in_acl·ls_out_acl 논리 흐름으로, ovn-controller가 conntrack을 쓰는 OpenFlow로 바꿉니다.
oc exec -n openstack ovsdbserver-nb-0 -- ovn-nbctl --db=unix:/etc/ovn/ovnnb_db.sock list Port_Group | grep -E 'name|ports' | head
oc exec -n openstack ovsdbserver-nb-0 -- ovn-nbctl --db=unix:/etc/ovn/ovnnb_db.sock acl-list pg_<보안그룹UUID_밑줄>
from-lport  1002 (inport == @pg_… && ip4) allow-related                      ← egress 전체 허용
  to-lport  1002 (outport == @pg_… && ip4 && ip4.src == 192.168.10.0/24 && tcp.dst == 22) allow-related
  to-lport  1002 (outport == @pg_… && ip4 && ip4.src == $pg_…_ip4 && tcp.dst == 8080) allow-related  ← 원격 그룹
oc exec -n openstack ovsdbserver-nb-0 -- ovn-nbctl --db=unix:/etc/ovn/ovnnb_db.sock acl-list neutron_pg_drop
from-lport 1001 (inport == @neutron_pg_drop && ip) drop
  to-lport 1001 (outport == @neutron_pg_drop && ip) drop

출력은 예시 형태이며 우선순위 숫자·조건 표현은 버전에 따라 다릅니다. 포트 보안이 꺼진 포트는 보안 그룹 그룹들과 neutron_pg_drop에서 빠집니다.

보안 그룹 로깅

“어떤 규칙에 걸려 버려졌는지” 기록이 필요하면 Neutron의 보안 그룹 로깅(network log) 기능으로 ACL에 로그 표시를 걸 수 있습니다. 로그는 ovn-controller 로그로 남으며, 양이 많아질 수 있으므로 기간·범위를 정해 씁니다(24편, 28편).

섹션 12

ovn-trace 읽기

ovn-trace는 SB DB의 논리 흐름만으로 “이 조건의 패킷이 어떻게 처리될지”를 계산합니다. 실제 패킷을 보내지 않으므로 운영 중에도 안전합니다.

명령 만들기

ovn-trace --db=unix:/etc/ovn/ovnsb_db.sock --summary neutron-<app-net UUID> \
  'inport == "<web-01 포트 UUID>" &&
   eth.src == fa:16:3e:aa:bb:cc && eth.dst == <라우터 포트 MAC> &&
   ip4.src == 10.0.0.15 && ip4.dst == 10.0.1.20 && ip.ttl == 64 &&
   tcp && tcp.dst == 5432'
부분어디서 구하나
데이터패스 (neutron-<네트워크 UUID>)출발 VM의 네트워크 ID
inport출발 VM의 Neutron 포트 UUID
eth.src · ip4.src출발 포트의 MAC·IP (openstack port show)
eth.dst같은 망이면 목적지 VM MAC, 다른 망·외부면 라우터 인터페이스 MAC
ip.ttl라우팅 시뮬레이션을 위해 지정 (보통 64)
출력 옵션보여 주는 것
--summary단계별 요약(무엇을 거쳐 어디로 나갔나). 처음 볼 때
--detailed (기본)각 단계에서 맞은 논리 흐름의 조건·동작
--minimal최종 결과(출력 포트·변환된 머리말)만

결과 판정

  • output("…")로 목적지 포트까지 가면 논리적으로는 정상 → 문제는 아래층(터널·물리망·MTU·VM 안 방화벽)에 있습니다.
  • drop이 나온 단계가 원인: port_sec면 위조 방지·AAP(11편), acl이면 보안 그룹, 라우팅 단계면 경로·라우터 연결.
  • conntrack이 관여하면(ct_next, ct_lb) ovn-trace는 연결 상태를 가정해야 합니다. --ct new(새 연결) 또는 --ct est(이미 성립)로 지정해 두 경우를 각각 봅니다.

ovn-trace와 ofproto/trace의 차이

ovn-trace는 설계도(논리 흐름)를 따라가 보는 것이고, ovs-appctl ofproto/trace br-int …는 특정 노드의 실제 신호등(OpenFlow)을 따라가 보는 것입니다. ovn-trace는 통과하는데 실제로 안 된다면, 그 노드의 ovn-controller가 흐름을 아직 설치하지 못했거나 터널·물리 문제를 의심합니다.

섹션 19

정리와 다음 편

오늘의 핵심 여덟 문장

  • Neutron(원본) → NB(의도) → ovn-northd → SB(논리 흐름 + 위치) → ovn-controller → OVS 흐름. NB를 직접 고치지 않는다.
  • NB 이름 규칙: 스위치·라우터 neutron-<UUID>, 포트는 Neutron UUID, 보안 그룹은 pg_<UUID>.
  • SB의 Port_Binding으로 포트가 어느 섀시에 붙었는지, Chassis·Encap으로 노드·터널 주소를 확인한다.
  • Geneve(UDP 6081)는 VNI(데이터패스)와 옵션(포트 키)을 담고, 58바이트가 추가된다.
  • 동서 트래픽은 출발 노드에서 라우팅까지 끝내고 목적지 노드로 바로 터널. 목적지 쪽 보안 그룹은 목적지 노드의 egress 파이프라인에서 검사된다.
  • SNAT은 게이트웨이 섀시(cr-lrp), 플로팅 IP는 중앙 또는 분산(컴퓨트가 외부망에 붙을 때). 게이트웨이는 우선순위·BFD로 이중화.
  • 보안 그룹 = Port_Group + allow-related ACL, 기본 거부는 neutron_pg_drop, 상태 저장은 conntrack.
  • ovn-trace는 설계를, ofproto/trace는 실제를 따라간다. drop 단계가 원인을 말해 준다.
