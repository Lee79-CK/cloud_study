1편왜 RHOSO인가: OpenStack과 OpenShift의 만남

데이터센터의 서버를 “AWS처럼 셀프서비스로 빌려 쓰는 클라우드”로 바꿔 주는 OpenStack이, 왜 이제 OpenShift 위에서 돌아가게 되었는지. 이 한 편으로 시리즈 전체의 지도를 머릿속에 그립니다.

섹션 2

몸풀기: 클라우드 기초 5분 복습

OpenStack을 이해하려면 먼저 “클라우드”가 정확히 무엇인지 짚고 가야 합니다. 많은 초보자가 “VM이 있으면 클라우드”라고 생각하지만, 그렇지 않습니다.

가상화 ≠ 클라우드

하이퍼바이저(예: KVM, VMware ESXi)는 물리 서버 한 대를 여러 대의 VM으로 쪼개 줍니다. 이것이 가상화입니다. 그런데 가상화만 있는 회사에서는 보통 이런 일이 벌어집니다.

현장 장면: 가상화만 있는 회사

개발팀이 “VM 3대가 필요해요”라고 메일을 보냅니다 → 인프라팀이 결재를 받고 → 빈 서버를 찾아 VM을 만들고 → IP를 엑셀에서 찾아 할당하고 → 방화벽 요청을 따로 넣고 → 3일 뒤 접속 정보를 회신합니다. 기계는 가상화되어 있지만 업무 흐름은 여전히 수작업입니다.

미국 표준기술연구소 NIST는 클라우드를 다섯 가지 특징으로 정의합니다. 이 다섯 개가 “가상화”와 “클라우드”를 가르는 기준입니다.

핵심 한 줄

OpenStack은 “가상화된 데이터센터”를 “셀프서비스 클라우드”로 바꿔 주는 관리·자동화 계층입니다. 실제로 VM을 돌리는 것은 여전히 KVM이고, OpenStack은 그 위에서 누가, 무엇을, 어디에, 얼마나를 관리합니다.

IaaS · PaaS · SaaS: 누가 무엇을 책임지나

클라우드는 “어디까지 대신 관리해 주느냐”에 따라 나뉩니다. 아래 버튼을 눌러 보세요. 호박색은 내가(사용자) 관리, 청록색은 제공자가 관리하는 부분입니다.

책임 분담 비교

사용자가 관리제공자가 관리

OpenStack은 IaaS를 만드는 소프트웨어입니다. 그리고 OpenShift는 그 자체로 PaaS 성격의 플랫폼입니다. RHOSO에서는 재미있게도 PaaS(OpenShift)가 IaaS(OpenStack)의 두뇌를 운영하는 구조가 됩니다. 이 “거꾸로 된 듯한” 관계가 이 시리즈의 핵심 포인트 중 하나입니다.

퍼블릭 · 프라이빗 · 하이브리드

구분설명예
퍼블릭 클라우드사업자의 데이터센터를 여러 회사가 함께 빌려 씀AWS, Azure, GCP, 국내 CSP
프라이빗 클라우드한 조직이 자기 데이터센터에 클라우드를 직접 구축RHOSO, 업스트림 OpenStack, VMware Cloud Foundation
하이브리드 클라우드둘을 함께 쓰고 일관된 방식으로 운영민감 데이터는 사내 RHOSO, 대외 서비스는 퍼블릭

RHOSO는 기본적으로 프라이빗 클라우드를 만드는 제품입니다. 다만 통신사나 MSP처럼 자기 고객에게 서비스를 파는 곳은 RHOSO로 “자체 퍼블릭 클라우드”를 만들기도 합니다.

섹션 3

OpenStack이란 무엇인가

OpenStack은 데이터센터의 서버, 스토리지, 네트워크 장비를 하나의 큰 자원 풀로 묶고, 사용자가 그 자원을 API로 빌려 쓰게 해 주는 오픈소스 클라우드 소프트웨어 모음입니다. 하나의 프로그램이 아니라 역할별로 나뉜 수십 개의 서비스(프로젝트)가 협업하는 구조입니다.

짧은 역사: 왜 이름이 전부 코드네임일까

2010탄생

미국 NASA의 컴퓨트 플랫폼(Nebula, 훗날 Nova)과 Rackspace의 오브젝트 스토리지(Cloud Files, 훗날 Swift)를 합쳐 오픈소스로 공개. 첫 릴리스 이름은 Austin.

2010~2022알파벳 순 릴리스 이름

Austin, Bexar, Cactus … Train(2019), Ussuri, Victoria, Wallaby(2021), Xena, Yoga, Zed. 약 6개월마다 새 버전이 나오고, 이름은 알파벳 순서를 따릅니다.

2021Wallaby → RHOSP 17

Red Hat OpenStack Platform 17.x(마지막 director 기반 버전 17.1 포함)가 이 업스트림 버전을 기반으로 합니다.

20232023.1 “Antelope”: 연도 기반 번호 시작

Z 다음부터는 “연도.회차 + 이름” 형식으로 바뀌었습니다. Antelope는 두 단계를 건너뛰는 업그레이드를 공식 지원하는 첫 SLURP 릴리스이기도 합니다.

2024Antelope → RHOSO 18

RHOSO 18.0은 2023.1 Antelope를 기반으로 하며, 2024년 8월 정식 출시(GA)되었습니다.

2024~2026Caracal, Dalmatian, Epoxy, Flamingo, Gazpacho …

업스트림은 계속 6개월 주기로 발전합니다. 운영 조직은 이 중 주로 SLURP 릴리스나 벤더 제품 기준으로 버전을 고릅니다. 커뮤니티를 이끄는 재단(구 OpenStack Foundation → OpenInfra Foundation)은 2025년 Linux Foundation 산하로 합류했습니다.

비유: 코드네임은 부서 이름

OpenStack 서비스 이름(Nova, Neutron, Cinder…)은 처음엔 외계어 같지만, 큰 회사의 부서 이름이라고 생각하면 쉽습니다. “인사팀(Keystone)에 출입증을 받고, 배치팀(Nova)에 자리를 요청하면, 네트워크팀(Neutron)이 랜선을 꽂아 주고, 자산팀(Cinder)이 사물함을 준다.” 2편에서 이 이름들을 확실히 외우게 됩니다.

핵심 서비스 지도와 AWS 대응표

AWS를 조금이라도 써 봤다면 대응표가 가장 빠른 길입니다. 카드를 누르면 설명이 나옵니다. 위의 필터로 묶음별로 볼 수 있습니다.

OpenStack 서비스 카드

카드를 눌러 보세요.

주의: AWS 대응은 “역할이 비슷하다”는 뜻이지 기능이 똑같다는 뜻은 아닙니다. 예를 들어 Neutron은 VPC보다 훨씬 다양한 네트워크 구성을 허용합니다.

모든 서비스는 같은 모양으로 생겼다

서비스는 많지만 내부 구조는 거의 똑같습니다. 이 패턴만 알면 새 서비스를 만나도 겁먹을 필요가 없습니다.

구성 요소하는 일비유
API 서버 (예: nova-api)HTTP 요청을 받고, 인증·권한을 확인하고, 작업을 접수민원 접수 창구
워커/에이전트 (예: nova-scheduler, nova-compute)실제 작업을 수행. 스케줄링, VM 생성, 볼륨 연결 등현장 작업 부서
데이터베이스 (MariaDB/Galera)“지금 무엇이 어디에 있는지” 상태를 저장장부
메시지 큐 (RabbitMQ)서비스 내부 구성 요소끼리 비동기로 일을 주고받음사내 메신저·업무 지시서
캐시 (memcached)토큰 등 자주 쓰는 데이터를 빠르게 꺼냄책상 위 메모지

왜 이게 중요한가

서비스 간 통신은 주로 REST API(창구 대 창구)로, 서비스 내부 통신은 주로 메시지 큐(사내 메신저)로 이뤄집니다. 장애가 나면 “창구가 안 받는가(API)”, “지시가 전달되지 않는가(큐)”, “장부가 잠겼는가(DB)”를 나눠서 보면 원인의 80%가 좁혀집니다. 이 사고방식은 16편과 Level 3 운영 편에서 반복해서 씁니다.

섹션 4

OpenShift와 Operator 최소 지식

RHOSO를 이해하는 데 필요한 Kubernetes 지식은 생각보다 적습니다. 딱 네 가지만 잡고 가면 됩니다: 컨테이너, Pod, 선언형, Operator.

컨테이너와 Pod

컨테이너는 프로그램과 그 프로그램에 필요한 라이브러리를 한 상자에 담은 실행 단위입니다. VM보다 가볍고 빨리 뜹니다. Kubernetes는 컨테이너를 Pod라는 단위로 묶어 여러 서버에 배치하고 관리합니다. RHOSO에서는 keystone-api, nova-scheduler, glance-api 같은 OpenStack 프로그램이 각각 Pod로 뜹니다.

선언형: “어떻게”가 아니라 “무엇을”

명령형 (예전 방식)

“서버 A에 접속해서, 패키지를 설치하고, 설정 파일을 고치고, 서비스를 재시작해.” 순서대로 지시합니다. 중간에 실패하면 어디까지 됐는지 사람이 확인해야 합니다.

선언형 (Kubernetes 방식)

“keystone API가 3개 떠 있는 상태여야 해.” 원하는 결과만 YAML로 적습니다. 지금 상태와 다르면 시스템이 알아서 맞춥니다.

비유: 에어컨 온도 조절기

“24도로 맞춰 줘”라고 설정하면, 에어컨은 지금 온도를 계속 재고 24도와 다르면 알아서 냉방·송풍을 조절합니다. 사람은 “압축기를 3분 돌려”라고 지시하지 않습니다. 이렇게 원하는 상태와 실제 상태를 비교해 차이를 없애는 반복 작업을 리컨실(reconcile)이라고 부릅니다.

Operator: 숙련된 운영자를 코드로 만든 것

Kubernetes가 기본으로 아는 것은 “Pod를 몇 개 띄워라” 정도입니다. 하지만 데이터베이스나 OpenStack처럼 복잡한 소프트웨어는 “DB 스키마를 먼저 만들고, 사용자 계정을 등록하고, 엔드포인트를 카탈로그에 넣고, 인증서를 연결하고…” 같은 전문 지식이 필요합니다. Operator는 이 운영 노하우를 프로그램으로 만든 것입니다.

  • CRD(Custom Resource Definition): Kubernetes에 새 “명사”를 가르칩니다. 예: OpenStackControlPlane이라는 종류(kind)가 존재한다.
  • CR(Custom Resource): 그 명사로 작성한 실제 주문서(YAML)입니다. 예: “Keystone은 3개, Nova는 켜고, Swift는 끈다.”
  • Operator(컨트롤러): CR을 계속 지켜보며 실제 상태를 주문서에 맞춥니다. 설치(Day 1)뿐 아니라 설정 변경·업데이트·복구(Day 2)까지 합니다.
  • OLM(Operator Lifecycle Manager): OpenShift에서 Operator 자체를 설치·업데이트해 주는 관리자입니다. RHOSO 업데이트도 OLM으로 Operator를 올리는 데서 시작합니다.

직접 해 보기: Operator의 리컨실 루프

원하는 상태 (CR에 적은 것)
kind: KeystoneAPI
spec:
  replicas: 3
실제 상태 (지금 떠 있는 Pod)

사람은 숫자만 바꿉니다. 나머지(생성·삭제·복구)는 Operator가 합니다. 실제 keystone-operator는 여기에 더해 DB 준비, 서비스 카탈로그 등록, 인증서 연결까지 처리합니다.

OpenShift = Kubernetes + 엔터프라이즈 포장

OpenShift Container Platform(RHOCP, OCP)은 Kubernetes를 기반으로 Red Hat이 보안 기본값, 설치·업데이트 자동화, 웹 콘솔, 모니터링, 이미지 레지스트리, OLM 등을 묶어 지원하는 제품입니다. 노드 OS는 RHCOS를 씁니다. RHOSO는 이 OCP를 “OpenStack 두뇌를 올려 둘 운영 기반”으로 사용합니다.

섹션 5

기존 방식: RHOSP director의 구조와 고민

RHOSO가 왜 나왔는지 알려면, 그 전의 RHOSP(Red Hat OpenStack Platform)가 어떻게 생겼는지 봐야 합니다. 현장에는 아직 RHOSP 16·17을 쓰는 곳이 많기 때문에, MSP 엔지니어라면 두 구조를 모두 알아 두는 것이 좋습니다.

OpenStack으로 OpenStack을 설치한다: TripleO

RHOSP의 설치 도구 director는 업스트림 TripleO(OpenStack On OpenStack) 프로젝트를 기반으로 합니다. 이름 그대로 작은 OpenStack으로 큰 OpenStack을 설치합니다.

  • 언더클라우드(undercloud): 설치·관리 전용 서버 1대. 여기에 director가 설치되어 있습니다.
  • 오버클라우드(overcloud): 실제 사용자가 쓰는 클라우드. 보통 컨트롤러 노드 3대 + 컴퓨트 노드 N대 + (선택) Ceph 스토리지 노드로 구성합니다.
  • 컨트롤러 노드 3대에 모든 API·DB·메시지 큐가 Podman 컨테이너로 올라가고, Pacemaker와 HAProxy가 고가용성을 담당합니다.
  • 배포 설정은 수많은 Heat 환경 파일(YAML)로 작성하고 openstack overcloud deploy 명령 한 번으로 전체를 배포합니다.

운영하면서 겪은 고민들

고민무슨 일이 있었나
배포·업데이트가 길고 무겁다설정 하나 바꿔도 전체 스택을 다시 계산·적용하는 경우가 많아 수십 분~수 시간이 걸리고, 중간 실패 시 원인 추적이 어려웠습니다.
컨테이너는 있지만 오케스트레이터가 없다서비스가 컨테이너로 돌아도 “죽으면 다른 노드로 옮겨 다시 띄우기” 같은 자동 관리는 Pacemaker·systemd 조합에 의존했습니다.
전용 컨트롤러 하드웨어컨트롤러 3대를 베어메탈로 따로 준비해야 했고, 다른 용도로 그 자원을 활용하기 어려웠습니다.
노하우가 사람 머리에어떤 템플릿을 어떻게 조합해야 하는지, 업그레이드 순서는 어떤지가 문서와 경험에 의존했습니다.
업스트림의 방향 전환TripleO 업스트림 개발은 2023년 무렵 사실상 종료되었고, 커뮤니티의 관심은 Kubernetes 위에서 OpenStack을 운영하는 방식으로 옮겨 갔습니다.

현장에서 자주 듣는 말

“overcloud deploy 한 번 돌리면 퇴근을 못 한다.” 과장이 섞였지만, 대규모 RHOSP 환경에서 배포와 업그레이드가 운영팀의 가장 큰 부담이었던 것은 사실입니다. RHOSO의 설계 목표 상당수가 이 부담을 줄이는 쪽을 향합니다.

참고로 RHOSP 17.1이 director 기반의 마지막 버전입니다. 17.1 환경을 RHOSO 18로 옮기는 공식 절차를 adoption(채택)이라고 부르며, 이 시리즈 30편에서 다룹니다.

섹션 6

RHOSO 18의 해법

RHOSO의 설계는 한 문장으로 요약됩니다.

RHOSO 한 문장 정의

OpenStack의 컨트롤 플레인은 OpenShift 위에서 Pod로 돌리고 Operator가 관리한다. VM이 실제로 도는 데이터 플레인(컴퓨트 노드)은 OpenShift 밖의 RHEL 9 서버로 두고, Operator가 Ansible을 실행해 설정한다.

컨트롤 플레인과 데이터 플레인

컨트롤 플레인 (두뇌)

요청 접수, 인증, 스케줄링 결정, 상태 기록. Keystone·Nova API·Neutron API·Glance·Cinder·Placement·Horizon 같은 API 서비스와 Galera DB, RabbitMQ, memcached, OVN 데이터베이스. → OpenShift Pod

데이터 플레인 (손발)

실제 VM 실행, 가상 네트워크 패킷 처리. nova-compute, libvirt·QEMU/KVM, OVS·ovn-controller, 메타데이터 에이전트. → RHEL 9 컴퓨트 노드 (EDPM 노드라고도 부름)

왜 컴퓨트 노드는 Pod로 만들지 않았을까?

초보자가 가장 많이 묻는 질문입니다. 이유는 네 가지입니다.

  1. 하드웨어에 깊이 붙어 있어야 한다. KVM, CPU 피닝, 휴즈페이지, SR-IOV, DPDK, GPU 패스스루 같은 기능은 호스트 OS를 직접 세밀하게 튜닝해야 합니다.
  2. VM의 수명은 컨트롤 플레인과 분리되어야 한다. 컨트롤 플레인 Pod가 재시작되거나 OpenShift를 업데이트하는 동안에도 고객의 VM은 계속 돌아야 합니다.
  3. 규모. 컴퓨트 노드는 수십~수백 대까지 늘어납니다. 이들을 모두 OCP 워커로 넣으면 OCP 클러스터 자체의 규모·업데이트 부담이 커집니다.
  4. 검증된 운영 방식의 연속성. RHEL 위에서 KVM을 돌리는 방식은 RHOSP 시절부터 쌓인 검증과 운영 경험이 있습니다. RHOSP 17.1에서 넘어올 때 기존 컴퓨트 노드를 그대로 채택(adopt)할 수도 있습니다.

Operator 계층 구조

RHOSO에는 Operator가 하나가 아니라 여러 개 있습니다. 맨 위에 openstack-operator라는 “메타(총괄) Operator”가 있고, 그 아래 서비스별 Operator가 있습니다.

# 개념도: 사람은 맨 위 CR 하나를 주로 다룬다
OpenStackControlPlane (CR, 사람이 작성)
   └─ openstack-operator (메타 Operator)가 읽고, 서비스별 CR을 만들어 내려보냄
        ├─ KeystoneAPI      → keystone-operator  → keystone Pod
        ├─ Nova             → nova-operator      → nova-api/scheduler/conductor Pod
        ├─ Neutron, OVN*    → neutron/ovn-operator
        ├─ Glance, Cinder   → glance/cinder-operator
        ├─ Galera           → mariadb-operator   → DB Pod
        ├─ RabbitMQ         → rabbitmq 관련 operator
        └─ … (Placement, Horizon, Swift, Octavia, Designate, Barbican, Manila, Heat, Telemetry 등)

OpenStackDataPlaneNodeSet + OpenStackDataPlaneDeployment (CR, 사람이 작성)
   └─ 데이터 플레인 컨트롤러가 Ansible 실행 작업(Ansible Execution Environment)을 만들어
      RHEL 컴퓨트 노드에 SSH로 접속해 설정

개념 이해용으로 단순화한 그림입니다. 실제 Operator 이름과 CR 종류는 19·20편 설치 실습에서 정확히 확인합니다.

주문서는 이렇게 생겼다 (미리보기)

아직 외울 필요는 없습니다. “YAML 몇 장으로 클라우드 전체를 선언한다”는 감만 잡으세요.

# (1) 컨트롤 플레인 주문서 — 개념 이해용으로 대폭 축약
apiVersion: core.openstack.org/v1beta1
kind: OpenStackControlPlane
metadata:
  name: openstack-control-plane
  namespace: openstack
spec:
  secret: osp-secret            # 각 서비스 비밀번호를 담은 Secret
  storageClass: local-storage  # DB·큐 데이터를 저장할 OCP 스토리지
  keystone:
    template:
      replicas: 3
  nova:
    enabled: true
  swift:
    enabled: false            # 필요 없는 서비스는 끈다
# (2) 데이터 플레인 노드 묶음 — 개념 이해용으로 대폭 축약
apiVersion: dataplane.openstack.org/v1beta1
kind: OpenStackDataPlaneNodeSet
metadata:
  name: compute-rack-a
spec:
  preProvisioned: true          # OS가 이미 설치된 RHEL 서버를 사용
  services: [bootstrap, configure-network, install-os, configure-os,
             run-os, install-certs, ovn, neutron-metadata, libvirt, nova, telemetry]
  nodes:
    compute-0: { hostName: compute-0, ansible: { ansibleHost: 192.168.122.100 } }
    compute-1: { hostName: compute-1, ansible: { ansibleHost: 192.168.122.101 } }
---
# (3) "지금 이 노드 묶음에 배포를 실행하라"는 실행 주문서
kind: OpenStackDataPlaneDeployment
spec:
  nodeSets: [compute-rack-a]

services 목록 하나하나가 순서대로 실행되는 Ansible 단계입니다. “노드 묶음(NodeSet)은 무엇을 갖출지, 배포(Deployment)는 언제 실행할지”로 역할이 나뉩니다.

OpenShift 쪽에서 미리 갖춰야 할 부품

부품왜 필요한가
NMState OperatorOCP 노드에 VLAN·브리지 같은 추가 네트워크 인터페이스를 선언형으로 만듭니다. OpenStack 격리 네트워크(내부 API, 스토리지, 테넌트 등)를 붙이는 데 씁니다.

또한 RHOSO는 트래픽 종류별로 네트워크를 분리합니다. 대표적으로 ctlplane(관리·프로비저닝), internalapi(서비스 간 내부 API), storage(VM↔스토리지), storagemgmt(스토리지 내부 복제 등), tenant(VM 간 터널 트래픽), external(외부 공개)입니다. 이 설계는 3편과 18편에서 자세히 봅니다.

“더 간단해졌다”의 정확한 의미

RHOSO는 반복 작업과 운영 절차가 간단해진 것이지, 배울 것이 줄어든 것은 아닙니다. 오히려 OpenStack 지식에 더해 OpenShift(Pod, CR, 네트워크, 스토리지, 업데이트 정책) 지식이 필요해졌습니다. 이 시리즈가 Level 0에서 두 세계의 언어를 먼저 맞추는 이유입니다.

섹션 10

누가, 왜 쓰는가

RHOSO는 “VM을 아주 많이, 여러 팀·고객이 셀프서비스로, 사내 데이터센터에서” 써야 하는 조직에 맞습니다. 대표적인 일곱 가지 사례를 탭으로 정리했습니다.

섹션 11

RHOSO가 맞지 않는 경우와 대안

좋은 엔지니어는 “이 제품이 맞지 않는 곳”도 말할 수 있어야 합니다. RHOSO는 강력하지만 무거운 플랫폼입니다.

선택지잘 맞는 상황RHOSO와의 차이
OpenShift Virtualization컨테이너 중심 조직이 일부 VM을 함께 운영. 앱팀이 VM과 Pod를 같은 방식으로 다루고 싶을 때VM 자체가 OCP 워커에서 KubeVirt로 돌아감. 대규모 멀티테넌트 IaaS(프로젝트·쿼터·테넌트 가상 네트워크·셀프서비스 포털·과금)는 RHOSO가 더 성숙
퍼블릭 클라우드 (AWS 등)규모 변동이 크고, 데이터센터를 직접 운영하기 싫을 때하드웨어·운영 인력 부담 없음. 대신 데이터 위치·장기 비용·규제 측면 검토 필요
VMware vSphere 유지기존 운영 체계·인력이 안정적이고 비용 변화를 감당할 수 있을 때vSphere는 가상화 운영 중심, 셀프서비스 IaaS는 추가 제품 필요. 라이선스 체계 변화가 재검토 계기가 되는 경우가 많음
업스트림 OpenStack 직접 구축강한 내부 OpenStack 팀이 있고 벤더 지원이 필요 없을 때 (Kolla-Ansible, OpenStack-Helm 등)라이선스 비용은 없지만 보안 패치·업그레이드·장애 대응을 모두 자체 책임
다른 벤더 OpenStack 배포판이미 특정 벤더 생태계(예: Canonical)를 쓰고 있을 때설치·운영 방식, 지원 범위, OpenShift와의 통합 수준이 다름
소규모 가상화 (Proxmox 등)서버 몇 대, 단일 팀, 셀프서비스·멀티테넌시가 필요 없을 때훨씬 가볍지만 클라우드 수준의 테넌트 격리·API·과금은 부족

섹션 12

버전과 릴리스 모델

RHOSO 18.0은 하나의 “주 버전” 안에서 정기적으로 새 기능을 추가합니다. 버그 수정 릴리스 사이사이에 Feature Release(FR)가 나오는 구조입니다. 아래 날짜는 Red Hat이 공개한 버전 대응표의 빌드 날짜를 기준으로 한 대략적인 시기입니다.

2024-0818.0.0 GA

정식 출시. 지원 OCP는 4.16. 컨트롤 플레인 Operator 기반 구조, Ansible 데이터 플레인, Prometheus 기반 텔레메트리 도입.

2024-1018.0.3 · FR1

첫 기능 릴리스.

2025-0318.0.6 · FR2

이 버전부터 OCP 4.18 지원. 그 이전 버전은 OCP 4.16만 지원하므로, OCP를 올리기 전에 RHOSO를 먼저 18.0.6 이상으로 올리는 순서가 중요합니다.

2025-0718.0.10 · FR3

Octavia 테넌트 제한 기능(기술 프리뷰) 등 추가. 이 시점부터 기존 OVN BGP 에이전트는 사용 중단 예정(deprecated) 상태가 되었습니다.

2025-1118.0.14 · FR4

신규 배포에서 RabbitMQ Quorum 큐 지원, memcached 인증, VMware Migration Toolkit을 이용한 VMware → OpenStack 이전, IPv6 BGP 동적 라우팅, 컨트롤 플레인 Pod까지 확장된 OVS/OVN 메트릭. 기술 프리뷰로 FWaaS·TAPaaS, Image Mode(bootc) 데이터 플레인.

2026-0318.0.17 · FR5

이후 신기능은 릴리스 노트의 “릴리스 정보” 장에 버전별로 정리됩니다.

2026-0718.0.21 · FR6

가장 최근 기능 릴리스. 2026년 10월 기준 릴리스 노트에는 버그 수정 릴리스 18.0.22까지 올라와 있습니다.

버전은 세 가지 숫자가 따로 있어 헷갈리기 쉽습니다. RHOSO 버전(예: 18.0.21), 그에 맞는 OpenStack Operator 버전(예: 1.21.0), 그리고 클러스터에 실제 적용된 OpenStackVersion CR 값입니다. 현재 버전은 다음 명령으로 확인합니다.

# 지금 배포된 RHOSO 버전과 업데이트 가능한 목표 버전 확인 (설치 후 사용)
$ oc get openstackversion -n openstack

OCP 버전 정책 주의

RHOSO는 OCP 위에서 돌기 때문에 OCP의 지원 기간에도 묶입니다. Red Hat은 RHOSO를 올린 OCP에 연장 ELS를 적용하는 것을 지원하지 않으며, 재배포를 피하려면 이전 짝수 마이너 버전 출시 후 18개월 안에(최대 24개월) 다음 짝수 마이너 버전으로 OCP를 올리도록 안내합니다. 지원되는 정확한 OCP 버전 조합은 Red Hat의 OpenStack 제품 라이프사이클 페이지에서 확인해야 합니다.

현장 팁: 네트워크가 가장 큰 벽

OpenStack 장애의 상당수는 네트워크(VLAN 설정, MTU, 보안 그룹, 라우팅)에서 나옵니다. RHOSO에서는 여기에 OCP 쪽 네트워크(NMState, MetalLB, 추가 네트워크 연결)가 더해집니다. 리눅스 네트워크 기초(ip a, ip route, 브리지, VLAN, MTU)를 지금부터 꾸준히 연습해 두면 Level 1의 Neutron 편과 Level 2 설치 편이 훨씬 쉬워집니다.

섹션 17

정리와 다음 편

오늘의 핵심 일곱 문장

  • 클라우드는 가상화에 셀프서비스·멀티테넌시·탄력성·측정이 더해진 것이고, OpenStack은 이를 만드는 IaaS 소프트웨어 모음이다.
  • OpenStack 서비스는 코드네임(Keystone, Nova, Neutron, Glance, Cinder, Placement…)으로 부르며, 모두 API + 워커 + DB + 메시지 큐 패턴을 따른다.
  • Operator는 원하는 상태(CR)와 실제 상태를 계속 맞추는 프로그램이며, 설치뿐 아니라 운영(Day 2)까지 자동화한다.
  • RHOSP는 언더클라우드의 director로 컨트롤러 3대 + 컴퓨트를 배포했고, 17.1이 마지막 director 버전이다.
  • RHOSO 18은 컨트롤 플레인을 OCP Pod로, 데이터 플레인을 RHEL 9 노드 + Ansible로 운영한다.
  • VM은 여전히 컴퓨트 노드의 KVM에서 돈다. RHOSO는 OpenShift Virtualization과 다른 제품이다.
  • RHOSO 18.0은 FR 단위로 기능이 추가되며, OCP 버전 정책과 함께 업데이트를 계획해야 한다.
