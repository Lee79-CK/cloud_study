전체 지도: 업스트림 Kubernetes와 벤더 지형

같은 ‘Kubernetes 1.37’이라는 이름 아래에서도 EKS, AKS, GKE, OpenShift, RKE2, kubeadm 클러스터는 서로 다른 소켓에 서로 다른 부품을 꽂고, 서로 다른 사람에게 책임을 맡깁니다. 이 편은 25편 전체를 관통하는 질문 하나를 세웁니다. “이 계층은 누가 고르고, 누가 고치고, 누가 책임지는가?”

같은 Kubernetes, 다른 책임선

배포 방식을 고르면 14개 계층의 책임 주체가 바뀝니다. 계층을 누르면 그 배포 방식에서 무엇이 기본으로 들어오고 무엇을 직접 해야 하는지 보입니다. 각 벤더의 대표적인 기본 구성 기준입니다.

내가(운영팀이) 고르고 운영 벤더가 제공, 설정·버전 관리·실행은 공동 벤더가 운영하고 나는 거의 손댈 수 없음
이 탐색기를 읽는 시니어의 시선 보라색(공동) 칸이 가장 위험합니다. 초록에 가까운 벤더 영역은 장애가 나도 벤더가 고치고, 노란 내 영역은 처음부터 내 일이라는 걸 모두가 압니다. 그런데 공동 영역은 “애드온은 AWS가 주니까 AWS가 업데이트하겠지”, “OpenShift 오퍼레이터가 etcd를 관리하니까 백업도 해주겠지” 같은 가정이 쌓이는 곳입니다. 실제 사고의 상당수가 이 칸에서 납니다. 이 시리즈의 네트워크·스토리지·RBAC 편은 대부분 보라색 칸을 다룹니다.

이 시리즈를 듣는 법

이 시리즈는 Deployment나 Service를 처음 배우는 과정이 아닙니다. 이미 클러스터를 운영해 본 사람이 “왜 이 벤더에서는 이렇게 동작하지?”라는 질문에 스스로 답할 수 있게 만드는 과정입니다. 그래서 모든 편이 같은 4단계 틀로 진행됩니다.

Native 기준 동작업스트림 코드와 kubeadm 클러스터에서 그 기능이 실제로 어떻게 동작하는지 패킷·API 호출 수준까지 확인합니다.
벤더별 구현 차이표EKS·AKS·GKE·OpenShift·RKE2가 같은 기능을 어떤 부품으로 바꿔 꽂았는지 표로 비교합니다.
운영상 함정그 차이 때문에 현장에서 실제로 터지는 장애·비용·보안 문제를 정리합니다.
실습Native와 최소 한 개 벤더에서 직접 재현하고 차이를 눈으로 확인합니다.

‘네이티브 Kubernetes’의 정확한 의미

현장에서 “우리는 네이티브 K8s 써요”라는 말은 최소 네 가지 다른 뜻으로 쓰입니다. 이 시리즈에서 비교의 기준선을 정확히 하려면 먼저 이 혼동을 정리해야 합니다.

말하는 사람이 뜻하는 것실제 의미예시이 시리즈에서의 취급
업스트림 소스kubernetes/kubernetes 저장소의 코드 그 자체릴리스 태그 v1.37.0모든 동작의 ‘정답지’
업스트림 바이너리SIG Release가 빌드·서명해 배포한 바이너리와 이미지(registry.k8s.io)kubeadm으로 설치한 클러스터Native 기준선으로 사용
벤더 빌드업스트림에 벤더 패치·백포트를 얹어 다시 빌드한 것v1.37.0-eks-…, -gke.N, +rke2r1, OpenShift의 openshift/kubernetes 포크비교 대상 (차이는 주로 소켓 쪽에서 남)
API 호환Kubernetes API를 말할 줄 알면 다 네이티브라고 부르는 느슨한 용법“우리 PaaS는 K8s 네이티브예요”사용하지 않음

따라서 이 시리즈의 Native는 이렇게 정의합니다. 업스트림 바이너리를 kubeadm으로 조립하고, 네트워크·스토리지·인증·트래픽 노출 부품을 운영자가 직접 골라 꽂은 클러스터. kubeadm을 고른 이유는 그것이 가장 ‘의견이 적은’ 설치기이기 때문입니다. kubeadm은 컨트롤 플레인을 정적 Pod로 띄우고 인증서를 발급하는 데까지만 책임지고, CNI도 CSI도 Ingress도 고르지 않습니다. 비교의 0점으로 쓰기 좋다는 뜻입니다.

코어는 얇아지고, 소켓은 늘었다

지난 10년간 Kubernetes의 가장 일관된 방향은 “특정 구현을 코어 밖으로 밀어내고, 그 자리에 표준 인터페이스를 남기는 것”이었습니다. 이 흐름을 이해하면 벤더 차이가 왜 생기는지가 한 번에 설명됩니다. 코어가 정의한 인터페이스(소켓)는 같지만, 거기에 꽂는 부품은 벤더가 고르기 때문입니다.

소켓 지도: 어디에 무엇이 꽂혀 있나

아래 소켓을 누르면 각 배포 방식이 그 소켓에 기본으로 꽂는 부품이 나옵니다. 25편 내내 이 지도로 돌아옵니다.

벤더 차이를 공부한다는 것의 정확한 뜻 “EKS는 어렵다”, “OpenShift는 무겁다” 같은 인상 비교는 운영에 쓸모가 없습니다. 쓸모 있는 질문은 세 가지뿐입니다. ① 이 소켓에 기본으로 무엇이 꽂혀 있는가, ② 그것을 내가 바꿀 수 있는가(바꾸면 지원을 잃는가), ③ 그 부품의 버전과 설정은 누가 올리는가. 이 세 질문에 답하지 못하면 벤더를 ‘안다’고 말할 수 없습니다.

벤더 지형: 네 가지 배포 모델

벤더 이름 대신 누가 컨트롤 플레인을 돌리고, 누가 노드를 돌리는가로 나누면 지형이 네 덩어리로 정리됩니다. 같은 벤더도 여러 모델에 걸쳐 있다는 점에 주의하세요. 예를 들어 Red Hat은 자체 운영형 OpenShift(B)와 ROSA·ARO 같은 클라우드 매니지드 OpenShift(C에 가까움)를 모두 제공합니다.

모델대표 제품컨트롤 플레인노드내가 바꿀 수 있는 범위잘 맞는 상황
A. 업스트림 조립형kubeadm, Kubespray, Cluster API(+인프라 프로바이더)내가 운영내가 운영전부. 대신 전부 내 책임학습·검증, 특수 하드웨어, 자체 플랫폼 팀이 있는 조직
B. 배포판OpenShift(자체 운영), RKE2, Talos Linux, k0s배포판 도구·오퍼레이터가 구성, 운영 주체는 나내가 운영(OS까지 배포판이 정한 경우 많음)배포판이 허용하는 범위. 벗어나면 지원 상실온프렘·하이브리드, 규제 산업, 벤더 지원 계약이 필요한 곳
C. 매니지드 컨트롤 플레인EKS, AKS, GKE Standard, ROSA·ARO클라우드가 운영(보이지 않음)내가 노드 그룹 단위로 운영노드·애드온·클러스터 옵션. API 서버 플래그는 불가퍼블릭 클라우드의 기본 선택지
D. 완전 관리형GKE Autopilot, EKS Auto Mode, AKS Automatic클라우드클라우드(노드 개념이 흐려짐)워크로드 스펙 위주. 권한·특권 컨테이너 등에 제약운영 인력 최소화, 표준적인 웹·API 워크로드

모델 사이의 회색지대

  • Hosted Control Plane. OpenShift의 HyperShift(Hosted Control Planes)는 컨트롤 플레인을 관리 클러스터 안의 Pod로 띄웁니다. 구조적으로는 매니지드 서비스(C)가 내부에서 하는 일을 고객이 직접 하는 형태라, B와 C의 중간에 놓입니다. 2편에서 해부합니다.
  • 불변 OS형 배포판. Talos Linux는 SSH도 셸도 없이 API로만 노드를 다룹니다. 모델은 B지만, 노드 운영 방식은 오히려 D에 가깝습니다.
  • Rancher. Rancher는 배포판이 아니라 관리 평면입니다. RKE2·K3s뿐 아니라 EKS·AKS·GKE 클러스터도 등록해 인증·RBAC을 위에서 덮어씌웁니다. 그래서 19편(RBAC 레이어링)에서 독립 축으로 다룹니다.

매니지드에서는 할 수 없는 것들

시니어가 Native에서 익힌 운영 기술 중 상당수는 매니지드 환경에서 아예 쓸 수 없습니다. 고객 요구사항을 받을 때 가장 먼저 이 표로 걸러야 합니다.

CNCF Conformance가 보장하는 것과 보장하지 않는 것

EKS·AKS·GKE·OpenShift·RKE2는 모두 CNCF의 Certified Kubernetes 제품입니다. 고객은 종종 이것을 “어디서 돌려도 똑같이 동작한다”는 보증으로 받아들입니다. 정확히는 그렇지 않습니다.

인증의 실제 구조

  • Kubernetes e2e 테스트 중 [Conformance] 태그가 붙은 테스트 묶음이 기준입니다. 이 테스트는 GA API의 동작 계약만 검증하고, 선택적 기능이나 운영 특성은 의도적으로 제외합니다.
  • 벤더는 제품·마이너 버전마다 결과를 cncf/k8s-conformance 저장소에 제출합니다. 즉 인증은 “제품 X의 버전 1.37”처럼 버전 단위입니다.
  • 실행 도구로는 SIG Testing의 Hydrophone과 오래 쓰여 온 Sonobuoy가 있습니다. 7장 실습에서 직접 돌려봅니다.

핵심 문장 하나로 정리하면 이렇습니다. Conformance는 ‘API 계약의 호환’을 보장하지, ‘운영 방식의 동등성’을 보장하지 않습니다. 그리고 이 시리즈가 집중하는 네트워크 정책·스토리지 프로비저닝·인증 통합은 대부분 보장 범위 바깥입니다.

판정 연습: 이건 인증이 보장할까?

항목마다 판단을 골라 보세요. 고르면 근거가 열립니다.

버전·스큐·지원 주기

업스트림의 박자

  • 마이너 버전은 1년에 세 번, 대략 4개월 간격으로 나옵니다. 2026년에는 1.36(4월 22일)과 1.37(8월 26일)이 나왔습니다.
  • 업스트림은 각 마이너를 약 14개월(1년 지원 + 2개월 업그레이드 여유) 동안 패치합니다. 그래서 동시에 패치되는 마이너는 보통 세 개입니다.
  • 기능은 KEP 단위로 Alpha → Beta → Stable(GA)을 거칩니다. Alpha는 기본 꺼짐, Beta는 대개 기본 켜짐(예외 있음), Stable은 기능 게이트가 잠긴 뒤 제거됩니다. 매니지드에서는 Alpha를 사실상 쓸 수 없다는 점을 2장에서 봤습니다.

버전 스큐 정책: 무엇이 무엇보다 앞서면 안 되는가

업그레이드 순서와 혼합 버전 상태의 허용 범위는 업스트림의 Version Skew Policy가 정합니다. 벤더 업그레이드 도구가 내부적으로 지키는 규칙도 결국 이것입니다.

스큐 계산기

업그레이드 중간 상태를 만들어 보고 허용되는지 확인하세요. 예를 들어 API 서버 두 대를 1.37과 1.36으로 두고 kubelet을 1.37로 바꿔 보면 왜 실패하는지 보입니다.

시니어 포인트: 마이너를 건너뛰는 업그레이드는 어디에도 없다 컨트롤 플레인은 어느 벤더든 한 번에 한 마이너씩만 올라갑니다. OpenShift의 EUS→EUS 업그레이드(예: 4.20→4.22)도 컨트롤 플레인은 중간 버전을 거치고, 워커 노드 풀을 일시 정지해 노드 재부팅 횟수만 줄이는 방식입니다. kubelet 3 마이너 스큐 허용도 같은 아이디어입니다. “두 단계 건너뛰기”는 노드 쪽에서만, 스큐 허용 범위 안에서만 가능합니다.

v1.37 기준 변화 지도

1.37은 67개 개선 사항을 담았습니다(Stable 16, Beta 23, Alpha 27, 폐기·제거 1). 전부를 볼 필요는 없습니다. 아래는 그중 네트워크·스토리지·접근 제어·플랫폼 운영에 직접 닿는 것과, 같은 시기 생태계·벤더 쪽에서 일어난 큰 변화만 골라 담은 것입니다. 필터로 축별로 보세요.

함정: Beta라고 다 켜져 있지 않다 1.37의 Pod-Level Resource Managers는 Beta지만 기본 꺼짐이고, HPA scale-to-zero와 Native Histograms는 Beta이면서 기본 켜짐입니다. 그리고 매니지드 벤더는 업스트림 기본값을 그대로 따르지 않을 수 있습니다. “1.37이니까 된다”가 아니라 “이 벤더의 이 플랫폼 버전에서 이 기능 게이트가 켜져 있는가”를 확인해야 합니다.

세 집중 축 미리보기

이 시리즈의 76%는 네트워크·스토리지·RBAC입니다. 세 축 모두 “코어는 API만 정의하고 구현은 벤더가 꽂는” 구조라서, 벤더 차이가 가장 크게 벌어지는 곳입니다. 각 축에서 무엇을 보게 될지 먼저 지도를 그려 둡니다.

네트워크

  • Pod IP를 VPC에서 직접 받는가(EKS VPC CNI), 오버레이를 쓰는가(Canal·OVN-K·AKS Overlay)
  • Service 구현이 iptables·IPVS·nftables인가, eBPF(Cilium·GKE Dataplane V2)나 OVN인가
  • 외부 노출이 클라우드 LB 컨트롤러인가 MetalLB류인가, Ingress에서 Gateway API로 어떻게 넘어가는가
  • NetworkPolicy가 정말 강제되는가, 이그레스는 어디서 통제하는가
4~10편 · 7편

스토리지

  • 기본 StorageClass와 바인딩 모드, 존 토폴로지
  • CSI 드라이버를 누가 설치·업그레이드하나(EKS 애드온, AKS 기본 설치, OpenShift 오퍼레이터)
  • RWX를 어디서 얻나(EFS·Azure Files·Filestore·CephFS·Longhorn)
  • 스냅샷과 백업을 벤더 서비스로 할지 Velero로 할지
11~16편 · 6편

RBAC과 접근 제어

  • 사람의 신원이 클러스터에 들어오는 길(IAM 토큰, Entra ID, Google IAM, OAuth 서버, OIDC)
  • 클라우드 IAM과 K8s RBAC이 겹칠 때 최종 권한은 무엇인가
  • Pod가 클라우드 API를 부르는 신원(IRSA·Pod Identity·Workload Identity·SPIFFE)
  • 벤더가 강제하는 어드미션(SCC·Autopilot 제약)과 내가 얹는 정책 엔진
17~22편 · 6편

cluster-fingerprint.sh
#!/usr/bin/env bash
# 현재 kubeconfig 컨텍스트의 '벤더 지문'을 출력한다. 읽기 전용.
# 요구: kubectl 1.36+, jq, column(util-linux)
set -uo pipefail
echo "### 컨텍스트: $(kubectl config current-context)"

echo; echo "## 1. 서버 버전 (벤더 빌드 접미사 확인)"
kubectl version -o json 2>/dev/null \
  | jq -r '.serverVersion | "gitVersion=\(.gitVersion)  platform=\(.platform)"'

echo; echo "## 2. 노드 지문"
kubectl get nodes -o json | jq -r '.items[] | [
  .metadata.name,
  (.spec.providerID // "-"),
  .status.nodeInfo.osImage,
  .status.nodeInfo.kubeletVersion,
  .status.nodeInfo.containerRuntimeVersion,
  (.metadata.labels["node.kubernetes.io/instance-type"] // "-")
] | @tsv' | column -t -s $'\t'

echo; echo "## 3. 벤더 단서"
labels=$(kubectl get nodes -o json | jq -r '[.items[].metadata.labels | keys[]] | unique | .[]')
grep -q '^eks.amazonaws.com/'    <<<"$labels" && echo "- EKS 노드 레이블"
grep -q '^kubernetes.azure.com/' <<<"$labels" && echo "- AKS 노드 레이블"
grep -q '^cloud.google.com/gke-' <<<"$labels" && echo "- GKE 노드 레이블"
grep -q '^node.openshift.io/'    <<<"$labels" && echo "- OpenShift 노드 레이블"
kubectl api-resources --api-group=config.openshift.io -o name 2>/dev/null | grep -q . \
  && echo "- config.openshift.io API 그룹 존재 → OpenShift"
kubectl get nodes -o jsonpath='{.items[*].metadata.annotations}' | grep -q 'rke2.io/' \
  && echo "- rke2.io 주석 → RKE2"

echo; echo "## 4. 네트워크 데이터플레인 (DaemonSet 이름으로 추정)"
kubectl get ds -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name --no-headers \
  | grep -Ei 'aws-node|cilium|calico|canal|flannel|ovnkube|azure-cns|anetd|kube-proxy|kube-router|antrea' \
  || echo "(알려진 CNI DaemonSet 없음)"

echo; echo "## 5. kube-proxy 모드"
if kubectl -n kube-system get ds kube-proxy >/dev/null 2>&1; then
  kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.config\.conf}' 2>/dev/null \
    | grep -E '^mode:' || echo "mode 값 없음 → Linux 기본값(iptables) 또는 다른 형식의 설정"
else
  echo "kube-proxy DaemonSet 없음 → CNI가 Service 처리를 대체했을 가능성"
fi

echo; echo "## 6. 스토리지·트래픽 클래스"
kubectl get storageclass
kubectl get ingressclass 2>/dev/null
kubectl get gatewayclass 2>/dev/null || echo "(Gateway API CRD 미설치)"

echo; echo "## 7. 나는 누구로 인증되었나"
kubectl auth whoami

echo; echo "## 8. 어드미션 확장 지점"
kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations --no-headers 2>/dev/null | awk '{print $1}'

8

현장 사례

MSP 운영에서 실제로 반복되는 패턴을 재구성한 사례입니다. 각 사례 끝의 교훈은 이후 편에서 기술적으로 풀어냅니다.

연장 지원 요금이 조용히 여섯 배가 된 클러스터

상황. 고객사 개발 계정에 아무도 관리하지 않는 EKS 클러스터 몇 개가 남아 있었습니다. 표준 지원이 끝나자 클러스터는 별도 승인 없이 연장 지원에 들어갔고, 클러스터 관리 요금이 표준 대비 크게 올랐습니다(공개 요금 기준 시간당 0.10달러에서 0.60달러. 최신 요금은 AWS 요금 페이지에서 확인).

원인. EKS는 연장 지원이 기본으로 켜져 있어 표준 지원 종료 시점에 자동 진입합니다. 사고가 아니라 설계된 동작이라 경보도 없었습니다.

교훈. MSP는 고객사 전체 클러스터의 버전 인벤토리와 지원 종료일 대시보드를 가져야 합니다. EKS·AKS·GKE 모두 API로 지원 상태를 조회할 수 있으니 월 1회 자동 보고로 묶으세요. 연장 지원을 끌지 말지도 고객과 명시적으로 합의할 항목입니다.

GKE 1.37 자동 업그레이드가 멈춘 이유

상황. Rapid 채널을 쓰는 검증 클러스터가 1.37로 올라가지 않았습니다. 유지보수 창도 정상이었습니다.

원인. 이 클러스터는 외부 OIDC 로그인을 위해 Identity Service for GKE를 켜 두었습니다. GKE 1.37부터 이 기능은 지원되지 않으며, 켜진 클러스터의 1.37 업그레이드와 생성이 차단됩니다. 대안은 Workforce Identity Federation입니다.

교훈. 매니지드에서 인증 통합 방식은 버전에 묶인 벤더 기능입니다. 인증 경로 변경은 RBAC 바인딩의 주체 이름(사용자·그룹 문자열)까지 바꿀 수 있으므로 업그레이드보다 먼저 별도 프로젝트로 진행해야 합니다. 17·19편에서 다룹니다.

잘 돌아가는 ingress-nginx가 문제인 이유

상황. 고객사 클러스터 다섯 곳(EKS 2, AKS 1, RKE2 2)이 모두 Helm으로 설치한 ingress-nginx를 쓰고 있었고, 장애는 없었습니다.

원인. ingress-nginx는 2026년 3월 업스트림에서 은퇴했습니다. 지금 동작한다는 것은 앞으로의 CVE가 고쳐지지 않는다는 사실을 가리지 못합니다. RKE2는 1.36부터 신규 클러스터 기본 Ingress를 Traefik으로 바꿨고, 1.37 커뮤니티판에서는 ingress-nginx를 독립 컨트롤러로 고르는 옵션 자체를 없앴습니다. 벤더마다 대응 속도가 달라 고객사 안에서 표준이 갈라지기 시작합니다.

교훈. 은퇴는 장애가 아니라 위험의 누적으로 옵니다. Ingress2Gateway 1.0(2026-03)이 나와 있으니 7·8편에서 Gateway API 전환 계획을 클러스터별로 세웁니다. 이때 ingress-nginx 고유 어노테이션의 동작 차이를 먼저 목록화해야 합니다.

OpenShift 고객의 “1.37 기능 쓰고 싶어요”

상황. 고객이 HPA scale-to-zero(1.37 Beta, 기본 켜짐)를 쓰고 싶다며 OpenShift를 최신으로 올려 달라고 요청했습니다.

원인. 최신 OpenShift 4.22의 Kubernetes는 1.35입니다. OpenShift는 업스트림보다 대략 두 마이너 뒤에서 검증된 버전을 제품화합니다. 1.37 기능은 아직 들어오지 않았고, 들어오더라도 OpenShift가 그 기능 게이트를 기본으로 켤지는 별개입니다.

교훈. 기능 요구를 받으면 “K8s 버전 → 벤더 버전 → 기능 게이트 상태 → 벤더 지원 여부” 네 단계로 답해야 합니다. 이 경우 KEDA 같은 기존 대안을 먼저 제시하는 것이 현실적인 답입니다.

같은 매니페스트, 다른 결과: AKS에서 온프렘 RKE2로 옮긴 날

상황. AKS에서 잘 돌던 애플리케이션을 온프렘 RKE2로 옮기자 네 곳에서 동시에 문제가 났습니다.

  • PVC Pending: StorageClass managed-csi가 없음 (11편)
  • Service type: LoadBalancer가 계속 <pending>: L4 LB 구현체 없음 (7편)
  • Pod의 Azure SDK 호출 실패: Workload Identity 웹훅과 어노테이션이 무의미해짐 (20편)
  • 가장 늦게 발견된 것: 서비스 간 호출 일부가 막힘. AKS에서는 네트워크 정책 엔진 없이 만든 클러스터였기 때문에 매니페스트 안의 NetworkPolicy가 한 번도 강제된 적이 없었고, RKE2의 Canal(Calico 정책 엔진)이 처음으로 그 정책을 집행했습니다 (9편)

교훈. 네 번째가 가장 위험합니다. 앞의 셋은 배포 즉시 드러나지만, 정책 강제 여부 차이는 특정 트래픽 경로에서만 드러납니다. 이전 전에 “이 클러스터에서 NetworkPolicy가 실제로 강제되는가”를 테스트로 확인하는 것을 표준 절차로 넣으세요.

정리, 다음 편, 참고 자료

이 편의 핵심 다섯 줄

  1. 이 시리즈의 Native는 “업스트림 바이너리 + kubeadm + 직접 고른 플러그인”이며, 모든 비교의 0점입니다.
  2. Kubernetes 코어는 인터페이스(소켓)를 정의하고, 벤더 차이는 거의 전부 소켓에 무엇을 꽂았는가에서 나옵니다.
  3. 배포 모델은 업스트림 조립형·배포판·매니지드 컨트롤 플레인·완전 관리형의 네 가지이며, 사고는 주로 ‘공동 책임’ 칸에서 납니다.
  4. Conformance는 API 계약 호환을 보장할 뿐, 네트워크 정책·스토리지·인증·트래픽 노출의 동등성은 보장하지 않습니다.
  5. 같은 마이너라도 벤더별 실제 수명은 1~3년으로 다르며, 연장 지원·LTS·EUS는 비용 또는 계약 조건이 붙습니다.

다음 편 · 2편 컨트롤 플레인 해부와 벤더별 구현 차이

kube-apiserver의 요청 경로(인증 → 인가 → 어드미션 → etcd)를 끝까지 추적하고, etcd 운영(컴팩션·디프래그·백업)을 다룹니다. 그리고 EKS·AKS·GKE의 블랙박스 컨트롤 플레인에서 무엇이 보이고 무엇이 안 보이는지, OpenShift Hosted Control Plane과 RKE2 내장 etcd는 어떻게 다른지, 클러스터 생성 도구들(kubeadm·Cluster API·eksctl·openshift-install·Terraform)은 각각 무엇을 대신해 주는지 비교합니다. 이 편의 ‘매니지드에서 할 수 없는 것’ 표가 2편의 출발점입니다.
