코드 한 줄 안 고치고 계측하기

Java 자동 계측은 JVM이 클래스를 로딩하는 순간에 끼어들어 바이트코드를 바꾸는 방식으로 동작합니다. 소스 코드도, 빌드 설정도 건드리지 않습니다. 실행 명령에 인자 하나가 추가될 뿐입니다. 마법처럼 보이지만 원리를 알면 왜 어떤 라이브러리는 안 잡히는지도 함께 이해됩니다.

javaagent 2.3x 기준 설정 빌더 트러블슈팅 의사결정 트리 엔지니어도 8편 전에 읽어두면 좋음
에이전트가 무엇을 하는지 개념적으로 표현한 것입니다

SECTION 01

javaagent는 어떻게 동작하는가

자바에는 java.lang.instrument라는 표준 API가 있습니다. JVM이 클래스를 메모리에 올리기 직전에 그 클래스의 바이트코드를 가로채 수정할 수 있는 공식 통로입니다. OTel 자바 에이전트는 이 통로를 이용합니다.

muzzle을 기억해 두세요

"분명 Spring을 쓰는데 왜 Span이 안 생기지?"의 답이 대부분 여기 있습니다. 에이전트는 라이브러리 버전이 자기가 아는 시그니처와 맞는지 검사하고, 맞지 않으면 에러를 내는 대신 그 계측만 조용히 비활성화합니다. 앱을 망가뜨리지 않기 위한 안전장치이지만, 문제 추적을 어렵게 만드는 원인이기도 합니다. 의심될 때는 디버그 로그를 켜서 어떤 계측이 적용됐는지 직접 확인합니다(8절).

에이전트가 커버하는 범위

Java 에이전트는 수백 개의 라이브러리·프레임워크를 자동으로 인식합니다. 실무에서 마주치는 것들은 거의 포함돼 있다고 봐도 됩니다.

웹 · 프레임워크

Servlet, Spring MVC, Spring WebFlux, JAX-RS, Vert.x, Netty, Tomcat, Jetty, Undertow

데이터 접근

JDBC 전반, HikariCP, JPA/Hibernate, MongoDB, Redis(Lettuce·Jedis), Elasticsearch, Cassandra

통신 · 메시징

Apache HttpClient, OkHttp, Java HttpClient, gRPC, Kafka, RabbitMQ, JMS, AWS SDK

지원 목록은 버전마다 늘어납니다. 특정 라이브러리 지원 여부는 프로젝트의 supported-libraries 문서에서 확인하는 것이 정확합니다.

SECTION 02

붙이는 네 가지 방법

모두 같은 결과를 내지만, 누가 책임지는가가 다릅니다. 이 차이가 1편의 경계선과 직결됩니다.

방법지정 위치장점소유자
-javaagent JVM 인자실행 스크립트가장 직관적, 로컬 테스트에 적합개발자
JAVA_TOOL_OPTIONS환경 변수실행 명령을 안 바꿔도 됨. 컨테이너에 유리개발자 또는 엔지니어
Spring Boot Starterbuild.gradle 의존성빌드 시점 결합, 네이티브 이미지 지원개발자
Operator 자동 주입파드 어노테이션앱 이미지 무수정, 조직 일괄 적용엔지니어

상황별 권장

1. 어디서 실행합니까?

2. 애플리케이션 이미지·빌드를 수정할 수 있습니까?

두 질문에 답하면 권장 방식이 표시됩니다.
MSP 실무에서의 현실적인 순서

개발팀이 먼저 -javaagent로 로컬에서 동작을 확인하고, 운영 배포는 Operator 자동 주입으로 전환하는 흐름이 가장 마찰이 적습니다. 개발자는 "내 앱에서 어떤 Span이 나오는지" 눈으로 확인한 상태가 되고, 엔지니어는 이미지 수정 요청 없이 전체 네임스페이스에 일괄 적용할 수 있습니다. 주입 방식의 구체적 구성은 8편에서 다룹니다.

SECTION 03

5분 실습 — Spring Boot에 붙이기

실제로 한 번 돌려보는 것이 설명 열 줄보다 낫습니다. 로컬에서 바로 따라할 수 있는 순서입니다.

1단계 · 에이전트 JAR 내려받기

# 최신 릴리스의 에이전트 JAR (50~60MB 정도)
curl -L -O https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/latest/download/opentelemetry-javaagent.jar

# 체크섬도 함께 받아 검증하는 습관을 들이세요
curl -L -O https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/latest/download/opentelemetry-javaagent.jar.sha256
sha256sum -c opentelemetry-javaagent.jar.sha256

운영 환경에서는 latest 대신 버전을 고정합니다. 1편의 회색지대 "SDK 버전 정책"이 여기서 실제 문제가 됩니다.

2단계 · Collector 없이 먼저 콘솔로 확인

처음부터 Collector를 붙이면 문제가 생겼을 때 앱 문제인지 파이프라인 문제인지 구분이 안 됩니다. 콘솔 익스포터로 먼저 눈으로 확인하는 것이 훨씬 빠릅니다. 

java -javaagent:./opentelemetry-javaagent.jar \
     -Dotel.service.name=order-api \
     -Dotel.traces.exporter=console \
     -Dotel.metrics.exporter=none \
     -Dotel.logs.exporter=none \
     -jar build/libs/order-api.jar

앱이 뜰 때 [otel.javaagent ...] OpenTelemetry Javaagent started 같은 줄이 보이면 로딩 성공입니다. 이제 API를 한 번 호출하면 콘솔에 Span이 통째로 출력됩니다. 2편에서 본 그 구조 그대로입니다.

3단계 · Collector로 보내기

java -javaagent:./opentelemetry-javaagent.jar \
     -Dotel.service.name=order-api \
     -Dotel.resource.attributes=service.version=1.4.2,deployment.environment.name=dev \
     -Dotel.exporter.otlp.endpoint=http://localhost:4317 \
     -Dotel.exporter.otlp.protocol=grpc \
     -jar build/libs/order-api.jar

4단계 · 컨테이너로 옮기기

Dockerfile에서는 실행 명령을 바꾸는 대신 JAVA_TOOL_OPTIONS를 쓰는 편이 깔끔합니다. 기존 ENTRYPOINT를 손대지 않아도 되기 때문입니다. 

FROM eclipse-temurin:21-jre
COPY opentelemetry-javaagent.jar /otel/javaagent.jar
COPY build/libs/order-api.jar /app/app.jar

ENV JAVA_TOOL_OPTIONS="-javaagent:/otel/javaagent.jar"
# 나머지 설정은 런타임 환경변수로 주입합니다
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
순서를 지키면 디버깅이 쉬워집니다

콘솔 → 로컬 Collector → 운영 Collector 순으로 한 단계씩 늘려가세요. 단계마다 확인하면 문제가 생겼을 때 직전에 바꾼 것 하나만 의심하면 됩니다. 처음부터 운영 환경에 붙이면 원인 후보가 다섯 개로 늘어납니다.

SECTION 04

설정 체계와 빌더

OTel 설정은 같은 항목을 두 가지 표기로 쓸 수 있습니다. 시스템 프로퍼티 otel.service.name과 환경 변수 OTEL_SERVICE_NAME은 같은 값입니다. 점을 밑줄로 바꾸고 대문자로 올리면 됩니다.

우선순위

여러 곳에 같은 설정이 있으면 위쪽이 이깁니다.

  1. 시스템 프로퍼티 — -Dotel.service.name=...
  2. 환경 변수 — OTEL_SERVICE_NAME=...
  3. 선언적 설정 파일 — YAML로 전체 SDK 구성을 기술하는 방식
  4. 에이전트 기본값
쿠버네티스에서 자주 겪는 혼선

Operator가 자동 주입한 환경 변수를, 앱 이미지 안에 하드코딩된 -D 옵션이 덮어써 버리는 경우가 있습니다. "엔지니어는 설정을 바꿨는데 개발자 쪽에서는 반영이 안 된다"는 상황의 전형적 원인입니다. 앱 이미지에는 -D로 OTel 설정을 넣지 않는다를 조직 규칙으로 두면 깔끔해집니다.

설정 빌더

값을 채우면 바로 붙여 쓸 수 있는 환경 변수 블록이 만들어집니다.

  SECTION 06
  
노이즈 줄이기

  

    자동 계측을 켜고 하루가 지나면 대부분 같은 반응이 나옵니다.
    "데이터가 너무 많다." 대개 정말 필요 없는 것이 절반을 차지합니다.
  


  
헬스체크와 메트릭 엔드포인트

  

    쿠버네티스는 liveness·readiness 프로브를 수 초마다 호출합니다.
    파드 하나당 하루 수만 건의 Span이 여기서 나오고, 전부 200 OK입니다.
    가장 먼저 제외해야 할 항목입니다.
  


# 특정 경로를 계측에서 제외
OTEL_INSTRUMENTATION_HTTP_SERVER_CAPTURE_ALL=false
OTEL_INSTRUMENTATION_COMMON_EXPERIMENTAL_CONTROLLER_TELEMETRY_ENABLED=false

# 또는 샘플러 단계에서 걸러내는 방법(권장) — 9편에서 Collector 쪽 처리와 함께 다룹니다

  
경로 제외 설정은 에이전트 버전에 따라 프로퍼티 이름이 달라진 적이 있습니다. 적용 후 실제로 줄었는지 반드시 확인하세요.


  
개별 계측 끄기

  

    특정 라이브러리 계측만 끄고 싶을 때가 있습니다.
    Span이 너무 잘게 쪼개지거나, 성능에 민감한 구간이거나, 이미 다른 방식으로 보고 있는 경우입니다.
  


# 이름 규칙: OTEL_INSTRUMENTATION_<모듈명>_ENABLED
OTEL_INSTRUMENTATION_JDBC_ENABLED=false
OTEL_INSTRUMENTATION_LETTUCE_ENABLED=false

# 반대로 전부 끄고 필요한 것만 켜는 방식
OTEL_INSTRUMENTATION_COMMON_DEFAULT_ENABLED=false
OTEL_INSTRUMENTATION_SPRING_WEBMVC_ENABLED=true
OTEL_INSTRUMENTATION_JDBC_ENABLED=true


  

    순서에 대한 조언
    

      처음부터 세밀하게 끄지 마세요.
      일단 기본값으로 일주일 돌려보고, 실제로 쌓인 데이터를 보고 줄이는 편이 훨씬 정확합니다.
      미리 끄면 나중에 필요했다는 걸 알았을 때 그 기간 데이터가 아예 없습니다.
      단, 헬스체크 제외만큼은 처음부터 하는 게 맞습니다.
    

  


  
로그와 트레이스 연결

  

    자동 계측은 Logback·Log4j의 MDC에 trace_id와 span_id를 자동으로 넣어줍니다.
    다만 로그 출력 포맷에 그 값을 찍도록 패턴을 수정하는 것은 개발자의 몫입니다.
    이걸 안 하면 MDC에는 값이 있는데 로그 파일에는 안 보이는 상태가 됩니다.
  


<!-- logback-spring.xml — JSON 포맷 권장 -->
<pattern>
  %d{ISO8601} %-5level [%X{trace_id:-},%X{span_id:-}] %logger{36} - %msg%n
</pattern>

  

    이 한 줄이 2편에서 말한 "신호 연결"의 실제 구현입니다.
    트레이스 화면에서 느린 Span을 찾고, 그 trace_id로 로그를 필터링하는 흐름이 여기서 완성됩니다.
  










  SECTION 07
  
자동 계측이 못 하는 일

  

    자동 계측은 구조를 보여주지만 의미는 보여주지 못합니다. 한계를 정확히 알아야 5편에서 무엇을 보강할지 판단할 수 있습니다.
  


  

    
비즈니스 구간이 안 보인다
재고 할당, 할인 계산, 정책 검증 같은 내부 로직은 라이브러리 호출이 아니므로 Span이 생기지 않습니다.

    
비즈니스 속성이 없다
주문 채널, 결제 수단, 고객 등급 같은 값은 코드를 쓴 사람만 알 수 있습니다.

    
실패의 의미를 모른다
재고 부족으로 주문을 거절하면 HTTP 200일 수 있습니다. 자동 계측은 이를 성공으로 봅니다.

    
자체 스레드풀에서 끊긴다
직접 만든 Executor에 작업을 넘기면 컨텍스트가 유실됩니다. 계측된 Executor로 감싸야 합니다.

    
사내 프로토콜을 모른다
자체 구현한 RPC나 레거시 통신 방식은 에이전트가 인식하지 못합니다.

    
muzzle이 막는 경우
라이브러리 버전이 지원 범위 밖이면 계측이 조용히 꺼집니다. 버전을 올리거나 수동 계측이 필요합니다.

  


  

    경계선 확인
    

      여기 나열된 여섯 가지는 전부 개발자 영역입니다.
      엔지니어가 Collector를 아무리 잘 구성해도 애초에 만들어지지 않은 데이터를 만들 수는 없습니다.
      반대로 말하면, 개발자가 이 여섯 가지를 처리해 주면
      나머지는 전부 인프라 쪽에서 해결 가능하다는 뜻이기도 합니다.
