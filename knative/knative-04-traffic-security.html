배포와 출시는 다른 일

일반 Deployment에서는 새 이미지를 적용하는 순간 사용자가 새 버전을 만나기 시작합니다. "올린다"와 "보여 준다"가 한 동작입니다. Knative는 이 둘을 떼어 놓습니다.

배포 (Deploy) = 리허설 무대 세우기

  • Configuration이 새 Revision을 만든다
  • Pod가 뜨고 Ready까지 확인된다
  • 관객(사용자)은 아직 모른다

출시 (Release) = 관객 입장시키기

  • Route가 트래픽 비율을 바꾼다
  • 1%, 10%, 50%로 조금씩 열 수 있다
  • 언제든 이전 무대로 관객을 돌려보낼 수 있다
이 분리가 주는 것

출시 판단을 기술 작업과 떼어 놓을 수 있습니다. 배포는 업무 시간에 미리 끝내 두고, 출시는 고객사와 합의한 시간에 트래픽 한 줄로 합니다. 장애 대응도 "다시 빌드해서 재배포"가 아니라 "트래픽 원위치"라 몇 초면 끝납니다.

롤백은 트래픽 한 줄

문제가 생긴 Revision은 지울 필요도, 다시 빌드할 필요도 없습니다. 트래픽만 이전 Revision으로 돌리면 됩니다. 옛 Revision이 0개로 줄어 있었다면 activator가 깨워 주므로, 롤백 직후 몇 초는 콜드 스타트가 있을 수 있습니다.

즉시 롤백
# 지금 트래픽이 어디로 가는지 확인
kn service describe hello

# hello-00001로 100% 원위치
kn service update hello --traffic hello-00001=100

# kubectl만 쓸 수 있는 환경이라면
kubectl patch ksvc hello --type merge -p \
  '{"spec":{"traffic":[{"revisionName":"hello-00001","percent":100}]}}'
롤백 후 함정: latestRevision이 사라진다

위처럼 특정 Revision에 100% 고정하면 traffic에 latestRevision: true가 없어집니다. 이 상태에서 template을 고치면 새 Revision은 만들어지지만 트래픽 0%입니다. 의도한 "배포만 하고 출시는 나중에" 상태이긴 하지만, 모르고 고쳤다면 "배포했는데 왜 반영이 안 되지?"가 됩니다. 정상화되면 다시 --traffic @latest=100으로 돌려 두세요.

MSP 팁: 롤백 대상은 미리 데워 둔다

롤백 순간의 콜드 스타트가 부담스러우면, 출시 후 일정 기간 이전 Revision을 0% + 태그로 남기고 해당 Revision에 min-scale 1을 걸어 둘 수 있습니다. 다만 3편에서 봤듯 min-scale은 Route가 가리키는 Revision에만 적용되므로, 0%라도 traffic 목록에 남겨 두어야 합니다.

5 / 16

자동으로 서서히: rollout-duration

단계를 손으로 넘기기 번거롭다면 Knative 내장 기능이 있습니다. Service에 serving.knative.dev/rollout-duration 어노테이션을 주면, latestRevision: true인 트래픽이 새 Revision으로 넘어갈 때 한 번에 넘기지 않고 지정한 시간에 걸쳐 조금씩 옮깁니다. 클러스터 기본값은 config-network의 rollout-duration입니다.

Service 메타데이터에 지정
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: hello
  annotations:
    serving.knative.dev/rollout-duration: "300s"   # 5분에 걸쳐 이동
spec:
  template:
    # ...

그래프는 개념도입니다. 실제로는 Knative가 짧은 간격으로 작은 비율씩 옮기며, 새 Revision이 늘어난 트래픽을 받을 만큼 Pod를 늘릴 시간을 벌어 줍니다.

rollout-duration은 "자동 판정"이 아니다

이 기능은 시간에 따라 비율만 옮길 뿐, 오류율을 보고 멈추지는 않습니다. 지표 기반으로 진행·중단을 판단하는 진짜 점진적 출시가 필요하면 7장의 Flagger 같은 도구를 붙이거나, 3장처럼 사람이 단계마다 판단해야 합니다.

6 / 16

헤더로 고르는 버전

태그 URL은 편하지만 주소가 달라서, 모바일 앱처럼 주소를 바꾸기 어려운 클라이언트로는 새 버전을 시험하기 어렵습니다. 이때 쓰는 것이 태그 헤더 라우팅입니다. 기능 플래그를 켜면 같은 주소로 요청하면서 Knative-Serving-Tag 헤더로 태그를 지정할 수 있습니다.

bash
# 1. 기능 플래그 켜기
kubectl patch configmap/config-features -n knative-serving --type merge \
  -p '{"data":{"tag-header-based-routing":"enabled"}}'

# 2. 같은 주소, 헤더만 다르게
curl http://hello.default.127.0.0.1.sslip.io
curl -H "Knative-Serving-Tag: canary" http://hello.default.127.0.0.1.sslip.io
쓸 곳과 조심할 곳

사내 테스터 앱이나 QA 자동화에 헤더를 넣어 "직원만 새 버전"을 만들 때 좋습니다. 다만 헤더는 누구나 붙일 수 있으므로, 외부에 공개된 서비스라면 앞단 게이트웨이에서 외부 요청의 이 헤더를 지우거나 아직 공개하면 안 되는 기능은 앱 자체 인증으로 막아야 합니다.

GitOps·자동화 도구와 함께

도구역할Knative와 함께 쓸 때 주의
Argo CD · FluxGit에 있는 ksvc YAML을 클러스터와 동기화webhook이 spec에 기본값(timeoutSeconds 등)을 채워 넣어 Git과 계속 달라 보일 수 있습니다. 기본값을 YAML에 명시하거나 해당 필드를 비교 대상에서 빼는 설정을 둡니다. 트래픽 비율을 Git으로 관리할지, 출시 담당자가 직접 조정할지도 미리 정하세요.
Flagger지표(오류율, 지연)를 보고 카나리 단계를 자동으로 진행하거나 되돌림Knative를 지원하는 공급자 설정이 있습니다. Prometheus 등 지표 저장소가 필요하며, 사용 중인 Flagger 버전의 Knative 지원 범위를 확인하세요.
Tekton · CI 파이프라인빌드 후 새 이미지로 Service를 갱신"배포까지만 자동, 출시는 승인 후" 구조가 Knative와 잘 맞습니다. 파이프라인은 template만 바꾸고 traffic은 건드리지 않게 하세요.
Configuration + Route 분리Service 대신 두 리소스를 직접 사용RBAC로 "개발자는 Configuration만, 출시 담당자는 Route만" 수정하게 나눌 수 있습니다. 규제가 엄격한 고객사의 변경 통제 요구에 쓸 만한 패턴입니다.

HTTPS 자동화

Knative는 서비스가 생길 때마다 URL이 생기므로, 인증서도 자동으로 따라와야 합니다. 이를 위해 cert-manager와 연동합니다. 큰 흐름은 다음과 같습니다.

  1. cert-manager와 발급자(Issuer) 준비

    Let's Encrypt 같은 ACME 발급자나 사내 CA를 ClusterIssuer로 만듭니다.

  2. Knative의 cert-manager 연동 켜기

    설치 방식과 버전에 따라 연동 구성요소(net-certmanager)를 추가로 설치하거나 내장 연동을 사용합니다. 어떤 발급자를 쓸지는 config-certmanager에 적습니다.

  3. 외부 도메인 TLS 활성화

    config-network에서 external-domain-tls를 Enabled로 바꾸면, 각 Route마다 인증서가 요청되고 발급되면 HTTPS URL이 status에 나타납니다. 예전 버전 문서에서는 같은 기능을 auto-tls라고 불렀습니다.

  4. HTTP를 HTTPS로 강제

    config-network의 http-protocol을 Redirected로 두면 HTTP 요청을 HTTPS로 돌려보냅니다.

설정 예시
# config-certmanager (knative-serving 네임스페이스)
data:
  issuerRef: |
    kind: ClusterIssuer
    name: letsencrypt-http01
---
# config-network
data:
  external-domain-tls: "Enabled"
  http-protocol: "Redirected"
  # 네임스페이스 단위 와일드카드 인증서를 쓰려면 (DNS-01 발급자 필요)
  # namespace-wildcard-cert-selector: |
  #   matchExpressions:
  #   - key: "networking.knative.dev/disableWildcardCert"
  #     operator: "NotIn"
  #     values: ["true"]
방식장점주의
서비스별 인증서 (HTTP-01)DNS API 권한 없이 가능. 설정 단순서비스·태그마다 인증서가 생겨 Let's Encrypt 발급 한도에 걸릴 수 있음. 태그 URL도 각각 발급
네임스페이스 와일드카드 (DNS-01)인증서 수가 적고 새 서비스가 바로 HTTPSDNS 공급자 API 자격 증명을 cert-manager에 줘야 함. 권한 관리 필요
직접 준비한 인증서고객사 기업 인증서 사용 가능DomainMapping의 spec.tls.secretName으로 지정. 갱신은 직접 관리
클러스터 내부 구간 암호화

위 설정은 클라이언트와 게이트웨이 사이를 암호화합니다. 게이트웨이와 activator, queue-proxy 사이 같은 클러스터 내부 구간까지 암호화하려면 system-internal-tls, 클러스터 내부 주소용은 cluster-local-domain-tls 설정이 있습니다. 네트워킹 플러그인별 지원 여부와 성숙도가 다르니 도입 전 버전 문서를 확인하세요. 서비스 간 mTLS가 필수 요건이라면 Istio 메시가 더 직접적인 해법입니다.

Pod 보안 기본값

Knative는 처음부터 보수적입니다. PodSpec 필드 중 일부만 허용하고, hostPath 볼륨이나 privileged 같은 위험한 설정은 기본적으로 막습니다(필요하면 config-features의 플래그로 개별 허용). 여기에 더해 secure-pod-defaults가 컨테이너 보안 설정을 자동으로 채워 줍니다.

값무엇을 채우나영향
Disabled아무것도 채우지 않음예전 동작. 보안 설정은 전적으로 사용자 몫
AllowRootBounded
v1.22부터 기본값		권한 상승 금지, 불필요한 리눅스 권한(capabilities) 제거, 런타임 기본 seccomp 프로필 적용. 루트 실행 자체는 막지 않음대부분의 이미지가 그대로 동작하면서 공격 표면이 줄어듦. 특수 권한이 필요한 이미지는 실패할 수 있음
Enabled위 내용에 더해 루트가 아닌 사용자로 실행하도록 강제가장 안전. 루트로 실행되도록 만든 이미지는 기동 실패
업그레이드 체크포인트

v1.21 이하에서 v1.22 이상으로 올리는 고객사 클러스터는 기본값이 바뀌므로, 루트 권한이나 추가 capability가 필요한 워크로드가 있는지 먼저 확인해야 합니다. 당장 확인이 어렵다면 업그레이드 전에 secure-pod-defaults를 Disabled로 명시해 두고, 점검 후 단계적으로 올리는 것이 안전합니다. 실제로 주입되는 필드는 실습 7단계처럼 Pod를 직접 조회해 확인하세요.

노출 범위와 네트워크 정책

2편에서 본 networking.knative.dev/visibility: cluster-local 라벨이 첫 번째 방어선입니다. 외부에 열 필요가 없는 서비스는 기본으로 붙이세요. 두 번째 방어선은 쿠버네티스 NetworkPolicy입니다.

여기서 많이 막히는 지점이 있습니다. 앱 네임스페이스에 "기본 전부 차단" 정책을 걸면 Knative도 같이 막힙니다. 요청은 게이트웨이와 activator를 거쳐 들어오고, autoscaler는 queue-proxy의 지표를 긁어 가야 하기 때문입니다.

앱 네임스페이스에 둘 허용 정책 예시
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-knative-system
  namespace: customer-a
spec:
  podSelector: {}          # 이 네임스페이스의 모든 Pod
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: knative-serving   # activator, autoscaler
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kourier-system    # 게이트웨이
증상으로 기억하기

NetworkPolicy 적용 후 "Pod는 Running인데 Revision이 Ready가 안 된다", "Pod가 0개에서 안 늘어난다", "늘어난 뒤 안 줄어든다" 같은 증상이 나오면 Knative 시스템 네임스페이스에서 오는 트래픽이 막힌 경우가 많습니다. 네트워킹 플러그인을 Istio 등으로 바꿨다면 해당 게이트웨이 네임스페이스로 바꿔 적으세요.

11 / 16

인증·권한·공급망

사용자 인증은 Knative 밖에서

Knative Serving 자체에는 로그인 기능이 없습니다. 앞단 API 게이트웨이, Istio의 JWT 검증(RequestAuthentication·AuthorizationPolicy), 앱 자체의 OIDC 처리 중 하나를 고릅니다. Eventing의 이벤트 전달 인증은 5편에서 다룹니다.

RBAC로 역할 나누기

ksvc를 수정할 수 있으면 트래픽도 바꿀 수 있습니다. 고객사 개발자에게는 자기 네임스페이스의 Knative 리소스만, 클러스터 전역 ConfigMap(knative-serving)은 MSP 운영자만 고칠 수 있게 하세요.

다이제스트 고정 + 서명 검증

Revision이 이미지를 다이제스트로 고정하므로(2편), Kyverno나 Sigstore policy-controller 같은 어드미션 정책으로 "서명된 이미지만 허용"을 걸기 좋습니다. 태그 바꿔치기 공격도 Revision에는 통하지 않습니다.

시크릿은 표준 방식으로

환경 변수나 볼륨으로 Secret을 참조하는 방식은 Deployment와 같습니다. 단, Secret 내용만 바꾸면 template은 그대로라 새 Revision이 생기지 않습니다. 새 값을 반영하려면 Pod 재기동이나 template 변경이 필요합니다.

실습

퀵스타트 kind 클러스터에서 진행합니다. 3장 연습에서 본 흐름을 실제 명령으로 따라갑니다.

  1. v1 배포

    bash
    kn service create hello \
  --image ghcr.io/knative/helloworld-go:latest --port 8080 \
  --env TARGET=v1 --revision-name hello-v1

kn service describe hello

    Revision 이름은 Service 이름으로 시작해야 하므로 hello-v1처럼 지정합니다.

  2. 다크 런치: v2를 0%로 배포하고 태그로 검증

    bash
    # 먼저 트래픽을 v1에 고정 (새 Revision이 자동으로 100%를 가져가지 않도록)
kn service update hello --traffic hello-v1=100

kn service update hello --env TARGET=v2 --revision-name hello-v2 \
  --tag hello-v2=candidate

curl http://hello.default.127.0.0.1.sslip.io              # v1
curl http://candidate-hello.default.127.0.0.1.sslip.io    # v2

  3. 카나리 10% → 50% → 100%

    bash
    kn service update hello --traffic hello-v1=90 --traffic hello-v2=10
for i in $(seq 1 20); do curl -s http://hello.default.127.0.0.1.sslip.io; done | sort | uniq -c

kn service update hello --traffic hello-v1=50 --traffic hello-v2=50
kn service update hello --traffic hello-v2=100

  4. 롤백과 latestRevision 복원

    bash
    kn service update hello --traffic hello-v1=100     # 롤백
kn service update hello --traffic @latest=100      # 다시 최신 추적으로
kn service describe hello

  5. 헤더 라우팅 맛보기

    bash
    kubectl patch configmap/config-features -n knative-serving --type merge \
  -p '{"data":{"tag-header-based-routing":"enabled"}}'

kn service update hello --traffic hello-v1=100 --tag hello-v2=candidate
curl -H "Knative-Serving-Tag: candidate" http://hello.default.127.0.0.1.sslip.io

  6. rollout-duration으로 자동 이동 관찰

    bash
    kn service update hello --traffic @latest=100
kubectl annotate ksvc hello serving.knative.dev/rollout-duration=120s
kn service update hello --env TARGET=v3

# 2분 동안 비율이 바뀌는 모습
watch -n 5 "kubectl get route hello -o jsonpath='{.status.traffic}'"

  7. secure-pod-defaults가 넣은 값 확인

    bash
    kubectl get cm config-features -n knative-serving -o yaml | grep secure-pod-defaults

kubectl get pod -l serving.knative.dev/service=hello \
  -o jsonpath='{.items[0].spec.containers[?(@.name=="user-container")].securityContext}' ; echo

  8. 정리

    bash
    kn service delete hello
kubectl patch configmap/config-features -n knative-serving --type merge \
  -p '{"data":{"tag-header-based-routing":"disabled"}}'

정리와 다음 편

  1. Knative는 배포(Configuration)와 출시(Route)를 분리합니다.
  2. 롤링, 블루그린, 카나리, 다크 런치, 헤더 기반 테스트가 모두 spec.traffic의 모양 차이입니다.
  3. 롤백은 트래픽 한 줄이지만, 고정 후에는 @latest 복원을 잊지 마세요.
  4. rollout-duration은 시간 기반 자동 이동일 뿐, 지표 판단은 Flagger 같은 도구나 사람이 합니다.
  5. HTTPS는 cert-manager 연동과 external-domain-tls로 자동화합니다. 발급 한도와 와일드카드를 고려하세요.
  6. v1.22부터 secure-pod-defaults=AllowRootBounded가 기본입니다. 업그레이드 전 워크로드를 점검하세요.
  7. NetworkPolicy를 걸 때는 Knative 시스템 네임스페이스에서 오는 트래픽을 허용해야 합니다.

다음 편: Eventing 1, CloudEvents와 이벤트 배달 구조

Serving이 "요청에 응답"이라면 Eventing은 "사건에 반응"입니다. CloudEvents 형식을 직접 만들어 보고, Source·Broker·Trigger·Sink가 어떻게 이벤트를 나르는지, 재시도와 Dead Letter Sink로 이벤트를 잃지 않는 법을 다룹니다.

Knative 강의 시리즈 4편. Knative v1.23을 기준으로 작성했습니다. TLS 관련 설정 이름과 cert-manager 연동 방식, secure-pod-defaults가 주입하는 정확한 필드는 버전과 설치 방식에 따라 다를 수 있으니 실무에서는 공식 문서와 클러스터의 실제 값을 함께 확인하세요.
