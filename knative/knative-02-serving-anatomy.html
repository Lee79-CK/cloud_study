네 개의 CRD, 한 장의 관계도

Knative Serving의 사용자용 리소스는 네 가지입니다. 핵심은 "무엇을 실행할지"(Configuration)와 "누구에게 트래픽을 줄지"(Route)가 분리되어 있다는 점입니다. Service는 이 둘을 한 번에 관리하는 편의용 껍데기입니다. 상자를 눌러 각자의 역할을 확인하세요.

spec.template 부분이 내려감spec.traffic 부분이 내려감
상자를 눌러 보세요.
이름 혼동 주의

"Knative Service"와 "쿠버네티스 Service"는 완전히 다른 리소스입니다. 그래서 줄임말 ksvc를 씁니다. 실제로 Knative Service를 만들면 그 아래에 쿠버네티스 Service도 여러 개 생기기 때문에, 대화할 때 어느 쪽인지 꼭 밝히는 습관을 들이세요.

2 / 15

Service YAML 한 줄씩 해부

실무에서 자주 쓰는 필드를 거의 다 넣은 Knative Service입니다. 왼쪽 줄을 누르면 오른쪽에 설명이 나옵니다. 왼쪽 색 띠는 그 줄이 결국 어느 하위 리소스로 내려가는지를 뜻합니다.

Service 자체 Configuration → Revision으로 Route로
"template"이라는 이름의 의미

Deployment의 spec.template이 Pod를 찍어 내는 틀이듯, Knative의 spec.template은 Revision을 찍어 내는 틀입니다. 그래서 template 아래 무엇이든 바뀌면 새 Revision이 생기고, template 밖(traffic 등)만 바뀌면 Revision은 그대로입니다.

3 / 15

Revision: 불변 스냅샷

Revision은 "그 시점의 template 사본"입니다. 한 번 생기면 내용이 바뀌지 않습니다. 이 성질 덕분에 "어제 잘 돌던 버전"이 정확히 무엇이었는지 언제나 다시 꺼낼 수 있습니다.

불변성을 지키는 세 가지 장치

이름은 한 번만

자동 이름은 hello-00001처럼 번호가 붙습니다. 직접 이름(hello-v2)을 주려면 Service 이름으로 시작해야 하고, 같은 이름을 두 번 쓸 수 없습니다.

이미지 태그를 다이제스트로 고정

Revision을 만들 때 controller가 레지스트리에 물어 :latest 같은 태그를 sha256:… 다이제스트로 바꿔 기록합니다. 나중에 태그가 새 이미지를 가리켜도 이 Revision은 옛 이미지를 씁니다.

템플릿을 고칠 수 없음

Revision 객체의 spec을 직접 수정하려 하면 webhook이 거부합니다. 바꾸고 싶으면 Service를 고쳐 새 Revision을 만드는 수밖에 없습니다.

트래픽이 없으면 조용히 대기

트래픽을 받지 않는 Revision은 Pod가 0개로 줄어 자원을 쓰지 않습니다. 롤백할 때 트래픽만 돌려주면 다시 깨어납니다.

MSP 실무에서 자주 터지는 곳: 다이제스트 조회

다이제스트 고정 때문에 knative-serving 네임스페이스의 controller가 이미지 레지스트리에 직접 접속합니다. 노드는 사설 레지스트리에 접근되는데 controller Pod는 프록시·사설 인증서 설정이 없어 Revision 생성이 실패하는 경우가 흔합니다. 이때는 controller에 CA 인증서를 넣거나, config-deployment의 registries-skipping-tag-resolving에 해당 레지스트리를 추가해 조회를 건너뜁니다.

Revision은 언제 지워지나

Revision은 계속 쌓이므로 가비지 컬렉션 규칙이 있습니다. config-gc의 기본값 기준으로, 트래픽을 받는 Revision은 절대 지우지 않습니다. 그 외에는 생성 후 일정 시간(기본 48시간)이 지났고 마지막으로 활성 상태였던 때로부터 일정 시간(기본 15시간)이 지난 것을 정리하되, 비활성 Revision을 최소 20개는 남기고 1000개를 넘지 않게 유지합니다. 롤백 여유를 얼마나 둘지는 고객사 정책에 맞춰 조정하면 됩니다.

Route: 트래픽과 URL

Route는 두 가지를 정합니다. 트래픽 비율과 접속 주소입니다. 트래픽 대상은 두 가지 방식으로 가리킬 수 있습니다. revisionName은 특정 Revision에 고정하고, latestRevision: true는 "준비된 최신 Revision"을 계속 따라갑니다. 여기에 tag를 달면 그 대상만 호출하는 전용 URL이 생깁니다.

아래 편집기로 직접 비율과 태그를 바꿔 보세요. YAML과 URL이 함께 바뀌고, 요청 20개를 보내 실제 분배도 확인할 수 있습니다.

spec.traffic

생성되는 URL

URL은 어떻게 조립되나

기본 규칙은 {서비스}.{네임스페이스}.{도메인}이고, 태그 URL은 앞에 {태그}-가 붙습니다. 이 규칙은 config-network의 domain-template, tag-template에서 바꿀 수 있고, 도메인은 config-domain에서 정합니다. 도메인을 설정하지 않으면 example.com이 붙는데, 실습 환경에서 URL이 example.com으로 나오면 대부분 이 설정을 빠뜨린 것입니다.

클러스터 안에서만 쓰는 서비스

Service에 networking.knative.dev/visibility: cluster-local 라벨을 붙이면 외부 URL이 사라지고 hello.default.svc.cluster.local 같은 내부 주소만 남습니다. 백엔드 API, Eventing의 이벤트 수신자처럼 밖으로 열 필요가 없는 서비스에 기본으로 붙여 두는 것이 안전합니다.

apply 이후 벌어지는 일

쿠버네티스의 모든 컨트롤러는 "원하는 상태를 보고 실제 상태를 맞춘다"는 재조정(Reconcile) 루프로 일합니다. Knative도 같습니다. 한 장의 YAML이 실제 트래픽을 받기까지의 릴레이를 한 단계씩 넘겨 보세요. 위쪽 이름표는 지금 일하는 컴포넌트입니다.

    상태는 아래에서 위로 올라온다

    각 리소스는 status.conditions에 Ready 같은 조건을 기록합니다. Revision이 Ready가 되어야 Configuration이 Ready가 되고, Route가 Ingress 준비를 확인해야 Route가 Ready가 되며, 둘 다 Ready여야 Service가 Ready가 됩니다. 그래서 문제를 찾을 때는 위에서 아래로 내려가며 False인 조건을 쫓으면 됩니다. 12장에서 연습합니다.

    컨트롤 플레인과 데이터 플레인

    controller, webhook, autoscaler, net-kourier-controller는 컨트롤 플레인입니다. 죽어도 이미 돌고 있는 서비스의 요청은 대체로 계속 처리됩니다. 반면 Kourier 게이트웨이, activator, 각 Pod의 queue-proxy는 데이터 플레인이라 요청이 직접 지나갑니다. 운영 환경에서는 데이터 플레인 컴포넌트를 2개 이상 복제하고 PodDisruptionBudget을 확인하세요.

    Activator는 언제 끼어드나

    1편에서 "Activator는 Pod가 0개이거나 모자랄 때만 끼어든다"고 했습니다. 이를 실제로 전환하는 리소스가 ServerlessService(SKS)입니다. SKS는 Revision마다 하나씩 생기는 내부 리소스로, 트래픽 경로를 두 가지 모드 중 하나로 맞춥니다.

    Kourier 게이트웨이요청 수신
    ›
    Activator버퍼링하고 확장 요청
    ›
    Pod (queue-proxy)실제 처리

    SKS는 Revision마다 쿠버네티스 Service를 두 개 만듭니다. hello-00001(공개용)과 hello-00001-private(Pod를 직접 가리키는 내부용)입니다. 모드가 바뀌면 공개용 Service가 가리키는 대상이 activator와 Pod 사이에서 바뀝니다. Pod가 갑자기 늘어날 수 있는 여유분을 정하는 target-burst-capacity 설정이 이 전환 기준에 관여하는데, 3편 오토스케일링에서 숫자와 함께 자세히 다룹니다.

    8 / 15

    네트워킹 레이어 고르기

    Knative는 트래픽을 직접 나르지 않습니다. Route가 만든 Knative 내부 Ingress(KIngress)를 네트워킹 플러그인이 각자의 프록시 설정으로 번역합니다. 어떤 플러그인을 쓸지는 config-network의 ingress-class 값 하나로 정합니다.

    플러그인기반·성격장점고려할 점이럴 때 고름
    KourierKnative 전용으로 만든 Envoy 게이트웨이가볍고 설치가 간단. 퀵스타트 기본값. OpenShift Serverless도 기본으로 사용Knative 트래픽 전용. 서비스 간 mTLS 같은 메시 기능은 없음처음 도입, 메시가 없는 클러스터, 대부분의 일반 용도
    Istio서비스 메시의 인그레스 게이트웨이mTLS, 세밀한 인가 정책, 메시 관측성을 함께 사용무겁고 운영 난도가 높음. 메시 버전과 Knative 버전 호환 확인 필요이미 Istio 메시를 운영 중이거나 서비스 간 mTLS가 필수
    ContourEnvoy 기반 인그레스 컨트롤러Knative 외 일반 인그레스와 함께 하나로 운영 가능Contour 자체 CRD 운영 지식 필요클러스터 인그레스를 이미 Contour로 통일한 경우
    Gateway API쿠버네티스 표준 Gateway API 구현체 위에서 동작 (net-gateway-api)표준 API라 구현체(Envoy Gateway, Istio 등)를 바꾸기 쉬움. 커뮤니티의 장기 방향구현체마다 지원 기능 범위가 달라 사전 검증 필요신규 클러스터에서 표준 기반으로 맞추고 싶을 때
    config-network에서 플러그인 지정
    # 값 예시: kourier.ingress.networking.knative.dev
#        istio.ingress.networking.knative.dev
#        contour.ingress.networking.knative.dev
#        gateway-api.ingress.networking.knative.dev
kubectl patch configmap/config-network -n knative-serving \
  --type merge \
  -p '{"data":{"ingress-class":"kourier.ingress.networking.knative.dev"}}'
    플러그인을 바꾸면

    새 플러그인을 먼저 설치한 뒤 ingress-class를 바꾸면 Route들이 새 플러그인으로 다시 재조정됩니다. 다만 외부 LoadBalancer IP와 DNS가 새 게이트웨이를 가리키도록 바뀌어야 하므로, 운영 중인 고객 환경에서는 유지보수 창을 잡고 진행하세요.

    내 도메인 붙이기: DomainMapping

    자동 URL(hello.default.example.com)은 개발용으로는 좋지만, 고객에게는 api.mycorp.com 같은 주소를 줘야 합니다. 방법은 두 가지입니다.

    config-domain: 클러스터 전체 도메인

    • 모든 서비스의 기본 접미사를 apps.mycorp.com처럼 바꿈
    • 와일드카드 DNS(*.apps.mycorp.com)를 게이트웨이로
    • 개발·스테이징 클러스터에 적합

    DomainMapping: 서비스별 고유 주소

    • 특정 주소 하나를 특정 ksvc에 연결
    • 이름 규칙과 무관한 깔끔한 주소
    • 운영 서비스의 대외 주소에 적합
    domainmapping.yaml
    apiVersion: serving.knative.dev/v1beta1
kind: DomainMapping
metadata:
  name: api.mycorp.com      # 이 이름이 곧 연결할 도메인
  namespace: default
spec:
  ref:
    apiVersion: serving.knative.dev/v1
    kind: Service
    name: hello
    멀티테넌트 클러스터라면: 도메인 점유 문제

    네임스페이스 A의 사용자가 네임스페이스 B가 쓰는 도메인을 가로채 DomainMapping을 만들면 곤란합니다. 그래서 Knative는 ClusterDomainClaim이라는 클러스터 범위 리소스로 "이 도메인은 이 네임스페이스 것"을 정합니다. config-network의 autocreate-cluster-domain-claims 설정이 꺼져 있으면, 클러스터 관리자가 ClusterDomainClaim을 먼저 만들어 줘야 DomainMapping이 Ready가 됩니다. 여러 고객사가 한 클러스터를 나눠 쓰는 MSP 환경에서는 이 설정을 꺼 두고 관리자가 승인하는 방식을 권합니다.

    설정은 ConfigMap에

    Knative Serving의 클러스터 전체 동작은 knative-serving 네임스페이스의 ConfigMap들로 조정합니다. 처음 보면 많아 보이지만, 자주 만지는 것은 아래 8개 정도입니다. 이름을 눌러 무엇을 바꾸는 곳인지 확인하세요.

    함정 두 가지

    첫째, ConfigMap을 열면 _example이라는 긴 키가 보입니다. 이건 주석 모음일 뿐 적용되지 않습니다. 실제 값은 data 아래 별도 키로 적어야 합니다. 둘째, Knative Operator로 설치했다면 ConfigMap을 직접 고쳐도 Operator가 되돌립니다. 이때는 KnativeServing 리소스의 spec.config에 값을 적어야 합니다.

    실습: 클러스터에서 해부하기

    1편의 kn quickstart kind 클러스터를 그대로 씁니다. 지웠다면 다시 만들고 시작하세요.

    1. Revision 이름을 직접 지정해 v1 배포

      bash
      cat <<'EOF' | kubectl apply -f -
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: hello
spec:
  template:
    metadata:
      name: hello-v1
    spec:
      containers:
        - image: ghcr.io/knative/helloworld-go:latest
          ports:
            - containerPort: 8080
          env:
            - name: TARGET
              value: "v1"
EOF
kubectl get ksvc hello

    2. webhook이 채운 기본값과 다이제스트 확인

      bash
      kubectl get revision hello-v1 -o yaml | grep -E 'timeoutSeconds|containerConcurrency|enableServiceLinks'

kubectl get revision hello-v1 \
  -o jsonpath='{.status.containerStatuses[0].imageDigest}{"\n"}'

    정리와 다음 편

    1. Serving의 사용자 리소스는 Service, Configuration, Revision, Route 넷이며, "무엇을 실행할지"와 "트래픽을 어디로"가 분리되어 있습니다.
    2. Service의 template이 바뀌면 새 Revision, traffic만 바뀌면 Route만 바뀝니다.
    3. Revision은 이름, 이미지 다이제스트, 템플릿까지 고정된 불변 스냅샷이고, config-gc 규칙에 따라 정리됩니다.
    4. Route는 비율 분할과 태그 URL을 만들고, URL 규칙과 도메인은 config-network·config-domain이 정합니다.
    5. apply 이후 webhook → controller → autoscaler → 네트워킹 컨트롤러 순서로 릴레이가 일어나고, 상태는 아래에서 위로 올라옵니다.
    6. SKS가 Proxy·Serve 모드를 바꿔 Activator를 경로에 넣고 뺍니다.
    7. 네트워킹 플러그인은 ingress-class 하나로 선택하며, 고유 주소는 DomainMapping과 ClusterDomainClaim으로 다룹니다.

    다음 편: 오토스케일링 심화

    KPA와 HPA의 차이, 동시성과 RPS 목표값, stable·panic 윈도우의 계산 방식, target-burst-capacity가 Activator 모드를 바꾸는 원리, 그리고 min-scale·initial-scale·scale-down-delay로 콜드 스타트를 다루는 법을 시뮬레이터로 직접 실험합니다.

    Knative 강의 시리즈 2편. Knative v1.23을 기준으로 작성했습니다. 컴포넌트 이름, 기본값, 리소스 버전은 릴리스와 설치 방식(YAML, Operator, 벤더 배포판)에 따라 다를 수 있으니 실무에서는 공식 문서(knative.dev)와 클러스터의 실제 값을 함께 확인하세요.
