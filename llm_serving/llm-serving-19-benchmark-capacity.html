01시작하기 전에

벤치마크 숫자는 그 숫자를 만든 조건과 함께일 때만 의미가 있습니다.

학습 목표

  1. 결정하려는 질문(선택·튜닝·용량·회귀·계약)에 맞게 지표·부하·워크로드를 고를 수 있다.
  2. 닫힌 루프·열린 루프·스윕 부하의 차이와 각각의 함정을 설명할 수 있다.
  3. 게이트웨이 사용량에서 입력·출력 분포, 공통 앞부분, 멀티턴 비율을 뽑아 워크로드 카드를 만들 수 있다.
  4. vLLM bench·GuideLLM·inference-perf·llm-d-benchmark의 쓰임을 구분해 고를 수 있다.
  5. 반복 측정과 표본 수로 결과의 신뢰 구간을 제시하고, 두 설정의 차이가 잡음보다 큰지 판단할 수 있다.
  6. 측정한 SLO 용량과 수요 예측으로 분기별 GPU 수를 계산한 용량 계획서를 쓸 수 있다.
이 편의 비유: 자동차 연비 측정

“연비 20km/L”는 도심·고속·적재량·에어컨 조건 없이는 의미가 없습니다. 같은 차를 같은 코스로 여러 번 달려야 믿을 수 있고, 다른 차와 비교하려면 코스와 운전 방식을 똑같이 해야 합니다. 그리고 내년 출장이 두 배가 되면 기름이 얼마나 들지 예측하려면, 올해 연비를 “내년 코스”로 환산해야 합니다. 벤치마크와 용량 계획이 바로 그 일입니다.

04부하 모델

요청을 “어떻게 보내는가”가 결과를 바꿉니다. 3편의 열린 루프·닫힌 루프를 도구 선택의 언어로 다시 봅니다.

부하 모델보내는 방식답하는 질문함정
동기 (synchronous)한 번에 하나최소 지연 (부하 없을 때)운영 성능과 무관
닫힌 루프 (concurrency N)항상 N개가 진행 중이 되도록 응답이 오면 다음을 보냄동시 사용자 N명일 때의 지연·처리량서버가 느려지면 보내는 속도도 줄어 과부하를 숨김 (조정된 누락)
열린 루프 (constant · poisson)정해진 도착률로 응답과 무관하게 보냄도착률 λ에서 SLO를 지키는가클라이언트가 그 속도를 못 내면 결과가 틀림 (도구 용량 확인)
스윕 (sweep)동기 → 최대 처리량 측정 → 그 사이 도착률 여러 단계지연-처리량 곡선과 SLO 용량단계당 시간이 짧으면 안정 상태에 도달 못 함
단계·램프·스파이크시간에 따라 도착률 변경확장 정책·흐름 제어 검증 (18편)단계 사이 여운이 다음 단계 결과에 섞임
재생 (replay)실제 로그의 시각·크기·순서대로“우리 트래픽”에서의 성능로그의 개인정보, 출력 길이 재현(ignore_eos·max_tokens)

용량 계획과 튜닝의 기본은 열린 루프(포아송) 스윕입니다. 실제 사용자는 서버가 느려졌다고 덜 보내지 않기 때문입니다. 닫힌 루프는 “동시 사용자 N명” 같은 업무 요구를 직접 표현할 때 씁니다.

07통계적 신뢰성

한 번 잰 숫자는 운이 섞인 숫자입니다. 특히 꼬리(p99)는 표본이 많아야 안정됩니다.

p99 추정의 흔들림

실제 TTFT 분포(로그 정규 분포, 중앙값 500ms)에서 요청 n개를 뽑아 p50·p99를 계산하는 실험을 20번 반복합니다. 표본이 적으면 p99가 실행마다 크게 흔들리는 것을 봅니다.
p50 (20회)p99 (20회)실제 p99

실무 규칙

  • 워밍업 제외: 처음 몇십 초(컴파일·캐시 냉각, 13편)는 버립니다.
  • 표본 수: p99를 보고하려면 단계마다 최소 수백~천 개 이상의 요청. p95면 그보다 적어도 됩니다.
  • 반복: 같은 조건을 3회 이상 측정해 중앙값과 범위(또는 신뢰 구간)를 보고합니다.
  • 차이 판단: 두 설정의 차이가 반복 간 흔들림보다 작으면 “차이 없음”입니다. 5% 개선이 흔들림 10% 안에 있으면 결론을 내리지 않습니다.
  • 상태 통제: 프리픽스 캐시·페이지 캐시 상태(15·13편), 다른 테넌트의 부하, GPU 온도·전력 제한, 같은 노드의 다른 Pod를 기록하거나 통제합니다.
  • 순서 섞기: A·B 설정을 A A A B B B가 아니라 A B A B A B 순서로 번갈아 측정하면 시간에 따른 환경 변화가 한쪽에 몰리지 않습니다.

08공정성과 검증

5편의 공정성 체크리스트에 “측정 대상이 내가 생각한 대로 동작하는가”를 더합니다.

실제 있었던 일: 똑똑한 라우팅이 동작하지 않았다

한 공개 벤치마크 보고에서는 llm-d의 지능형 라우팅 효과로 보였던 처리량 향상이, 나중에 확인해 보니 EPP가 실제로는 라우팅을 하지 않고(프록시 설정·TLS·EPP 설정·엔진의 프리픽스 캐시 옵션 문제) 단지 Pod 수가 늘어서였던 것으로 정정되었습니다. 결과가 기대와 맞더라도 측정 대상의 동작을 독립적으로 확인해야 합니다.

09용량 계획

측정한 레플리카당 SLO 용량과 수요 예측을 곱하면 GPU 수가 나옵니다. 어려운 것은 “미래의 워크로드”로 환산하는 일입니다.

필요 레플리카 = ⌈ 예측 피크 수요 ÷ (레플리카당 SLO 용량 × 목표 사용률) ⌉ + 여유(N+1) 필요 GPU = 필요 레플리카 × 레플리카당 GPU (17편) 워크로드 환산: 요청당 작업량 ≈ 출력 토큰 + 입력 토큰 × r (r = Prefill 토큰 하나의 상대 비용, 실측으로 보정) 새 용량 ≈ 측정 용량 × (측정 작업량 ÷ 새 작업량)
  • r의 의미: Prefill 토큰은 병렬로 처리되어 Decode 토큰보다 훨씬 쌉니다. 히어로 계산기는 r = 0.1(Prefill 토큰 10개가 Decode 토큰 1개 비용)을 씁니다. 14편 측정에서 입력 길이만 바꾼 두 실험으로 r을 직접 구할 수 있습니다.
  • 환산은 근사입니다. 미래 워크로드가 많이 다르면(긴 문맥 비중이 크게 늘거나 멀티턴이 늘면) 그 워크로드로 다시 측정합니다.
  • 수요 예측: 게이트웨이 사용량의 피크(평균이 아니라 피크 시간대의 분 단위 최대치)와 성장률. 신규 서비스 출시·고객 추가 같은 계단식 증가는 따로 더합니다.
  • 바꿀 수 있는 다른 손잡이: 같은 GPU로 용량을 늘리는 튜닝(14편)·양자화(6편)·캐시(15편)·추측 디코딩(16편)의 효과를 반영하면 구매량이 줄어듭니다. 각 효과는 측정값으로만 반영합니다.

10용량 계획의 운영

용량 계획은 한 번 쓰는 문서가 아니라 주기적으로 갱신하는 운영 절차입니다.

항목내용
검토 주기월간(운영 지표) + 분기(재측정·예측 갱신)
증설 신호피크 시간대 레플리카가 최대에 닿는 날이 늘어남(18편), SLO 달성률 하락, 목표 사용률 초과 일수
조달 리드 타임GPU 서버 조달은 수 주~수 개월. 예측 시점이 그만큼 앞서야 함. 클라우드도 재고·예약 고려
재측정 계기모델·엔진·GPU 변경, 워크로드 변화(입력 길이 분포 변화 등)
문서워크로드 카드, 측정 조건·결과, 환산 가정(r 등), 예측 근거, 결론(분기별 GPU 수·비용)

11MSP 관점

벤치마크와 용량 계획은 MSP가 고객에게 파는 전문성의 핵심입니다.

  • 근거 있는 견적: “GPU 몇 장”이 아니라 “이 워크로드 카드와 이 SLO에서 레플리카당 용량이 이만큼이라 이만큼”으로 제시합니다. 측정 조건이 고객 실제와 다를 때의 위험도 적습니다.
  • 벤치마크 서비스: 고객 후보 모델·GPU를 표준 절차(이 편)로 측정해 주는 것 자체가 상품이 될 수 있습니다.
  • 용량 보장 문구: SLA에 “워크로드 카드 조건에서 SLO 용량 X req/s 보장”처럼 조건을 명시하면, 워크로드가 바뀌었을 때 재협상 근거가 됩니다.
  • 정기 용량 리뷰: 분기별로 사용량·SLO 달성률·용량 예측을 고객에게 보고하고 증설·축소를 제안합니다(26편).

실습 19-1 · 워크로드 카드 만들기

python · workload_card.py (게이트웨이 사용량 → 워크로드 카드)
"""요청별 (시각, 입력 토큰, 출력 토큰[, 세션]) 기록에서 워크로드 카드를 만든다.
입력: JSON 줄 파일 또는 LiteLLM /spend/logs 응답(JSON 배열). 사용: python workload_card.py logs.json"""
import json, sys, statistics, collections
from datetime import datetime
raw = open(sys.argv[1]).read().strip()
rows = json.loads(raw) if raw.startswith("[") else [json.loads(l) for l in raw.splitlines() if l.strip()]
def pick(r, *keys):
    for k in keys:
        if r.get(k) is not None: return r[k]
recs = []
for r in rows:
    t = pick(r, "startTime", "ts", "time"); i = pick(r, "prompt_tokens", "input_tokens"); o = pick(r, "completion_tokens", "output_tokens")
    if t is None or i is None or o is None: continue
    recs.append((datetime.fromisoformat(str(t).replace("Z", "+00:00")), int(i), int(o), pick(r, "session_id", "user")))
def pct(xs, p): xs = sorted(xs); return xs[min(len(xs) - 1, int(p * len(xs)))]
ins, outs = [r[1] for r in recs], [r[2] for r in recs]
per_min = collections.Counter(r[0].replace(second=0, microsecond=0) for r in recs)
by_hour = collections.Counter(r[0].hour for r in recs)
sessions = collections.Counter(r[3] for r in recs if r[3])
print(f"요청 수: {len(recs)}  기간: {min(r[0] for r in recs)} ~ {max(r[0] for r in recs)}")
print(f"입력 토큰 p50/p90/p99: {pct(ins,.5)}/{pct(ins,.9)}/{pct(ins,.99)}  평균 {statistics.mean(ins):.0f}")
print(f"출력 토큰 p50/p90/p99: {pct(outs,.5)}/{pct(outs,.9)}/{pct(outs,.99)}  평균 {statistics.mean(outs):.0f}")
print(f"피크 분당 요청: {max(per_min.values())} (= {max(per_min.values())/60:.2f} req/s), 평균 분당 {statistics.mean(per_min.values()):.1f}")
print("시간대별 요청 비중:", {h: f"{c/len(recs)*100:.0f}%" for h, c in sorted(by_hour.items())})
if sessions: print(f"세션당 요청 수 중앙값: {statistics.median(sessions.values())}, 멀티턴 세션 비율: {sum(1 for v in sessions.values() if v > 1)/len(sessions)*100:.0f}%")

import json, statistics, sys, collections
rows = [json.loads(l) for l in open(sys.argv[1] if len(sys.argv) > 1 else "results/sweep.jsonl")]
by = collections.defaultdict(list)
for r in rows: by[(r["label"], r["rate"])].append(r)
T95 = {2: 4.30, 3: 3.18, 4: 2.78, 5: 2.57}           # t 분포 95% 양측 (n-1 자유도: 1~4)
def ci(xs):
    m = statistics.mean(xs)
    if len(xs) < 2: return m, float("nan")
    return m, T95.get(len(xs), 2.0) * statistics.stdev(xs) / len(xs) ** 0.5
print(f"{'설정':<12}{'도착률':>6}{'n':>3}{'TTFT95 평균±95%CI':>22}{'TPOT95 평균±95%CI':>22}{'Goodput 비율':>14}")
for (label, rate), rs in sorted(by.items()):
    t, tc = ci([r["ttft_p95"] for r in rs]); p, pc = ci([r["tpot_p95"] for r in rs]); g, gc = ci([r["goodput_frac"] for r in rs])
    print(f"{label:<12}{rate:>6}{len(rs):>3}{t:>14.0f} ± {tc:<6.0f}{p:>14.1f} ± {pc:<6.1f}{g:>9.2f} ± {gc:.2f}")

판단: 두 설정의 신뢰 구간이 겹치면 “이 측정으로는 차이를 단정할 수 없음”이 결론입니다. 겹치지 않을 때만 개선을 보고합니다. 3회로 신뢰 구간이 너무 넓다면 측정 시간을 늘리거나 반복 수를 늘립니다(7장 계산기).

16정리와 체크리스트

핵심 여섯 문장. 이것으로 Level 3가 끝납니다.

  3. 워크로드 카드(입력·출력 분포, 공통 앞부분, 멀티턴, 도착 패턴, 기능, SLO)가 결과의 조건이다.
  4. 도구를 하나 표준으로: vLLM bench(회귀·튜닝), GuideLLM(스윕·SLO), inference-perf(공통 앞부분·재생), llm-d-benchmark(자동화).
  5. 반복·표본 수·신뢰 구간으로 차이가 잡음보다 큰지 판단하고, 측정 대상이 생각대로 동작하는지 독립적으로 확인한다.
  6. 용량 = 피크 ÷ (SLO 용량 × 목표 사용률) + 여유, 미래 워크로드로 환산하고 조달 리드 타임만큼 앞서 갱신한다.
