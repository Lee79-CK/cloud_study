Jaeger v2 아키텍처 해부바이너리는 하나, 역할은 설정 파일이 정한다

Jaeger v2에는 jaeger라는 실행 파일이 딱 하나 있습니다. 같은 파일이 어떤 설정을 읽느냐에 따라 수집기도, 조회 서버도, Kafka 소비자도 됩니다. 아래에서 역할을 바꿔 가며 안에서 어떤 부품이 켜지고 꺼지는지 직접 확인해 보세요.

jaeger --config config.yaml
Receivers · 받기
Processors · 가공
Exporters · 내보내기
Extensions · 파이프라인 밖의 기능
부품을 클릭하면 한 줄 설명이 나옵니다. 오른쪽 위 J 표시는 Jaeger가 직접 만든 부품입니다.

      

    

  

  
흐릿한 부품은 이 역할에서 쓰지 않는 것입니다. 부품 목록은 공식 바이너리에 포함된 것 중 대표적인 것만 추렸습니다.







  
1
v1에서 v2로, 무엇이 바뀌었나

  
1편에서 "Jaeger v2는 OTel Collector 위에 다시 만들어졌다"고 했습니다. 실제로 무엇이 달라졌는지 구성도로 비교해 보겠습니다. 버튼으로 v1과 v2를 번갈아 보세요.

  

  

    
    

  


  
한눈에 보는 변경 사항

  

    
구분v1v2

    
      
실행 파일agent, collector, query, ingester, all-in-one 등 역할별 바이너리jaeger 하나. 설정에서 켠 부품이 역할을 결정

      
설정 방식명령행 플래그와 환경 변수 (SPAN_STORAGE_TYPE 등)YAML 설정 파일만 사용. 필요하면 YAML 안에서 ${env:변수}로 참조

      
설정 문법Jaeger 고유OpenTelemetry Collector와 같은 문법

      
앱 계측Jaeger 전용 클라이언트 라이브러리OpenTelemetry SDK (OTLP로 전송)

      
호스트 agentjaeger-agent (UDP로 받아 collector에 전달)OTel Collector를 agent로 쓰는 것을 권장

      
내부 데이터 모델Jaeger 고유 모델OTLP 데이터 모델 중심

      
기능 확장Jaeger 코드를 고쳐야 함Collector 생태계의 receiver·processor를 그대로 조합, 필요하면 커스텀 빌드

    
  


  

    
왜 굳이 다시 만들었을까

    
v1 시절에도 많은 조직이 앞단에 OTel Collector를 두고 그 뒤에 Jaeger collector를 두었습니다. 두 프로그램이 받고, 모으고, 보내는 거의 같은 일을 이중으로 한 셈입니다. v2는 "어차피 같은 일이라면 Collector 프레임워크를 그대로 쓰고, Jaeger만의 기능(저장소 연결, 조회 API, UI, 샘플링 서버)만 부품으로 얹자"는 결정입니다. 그 덕분에 tail sampling, 속성 가공, Kafka 연결 같은 기능을 Jaeger가 따로 구현하지 않고 Collector 생태계에서 가져다 씁니다.

  







  
2
OTel Collector 문법 30초 복습

  
Jaeger v2 설정 파일은 OTel Collector 설정 파일과 문법이 같습니다. 자세한 내용은 OTel 시리즈 7편에서 다뤘으니, 여기서는 Jaeger를 읽는 데 필요한 뼈대만 짚습니다.

  

    
구성 요소하는 일Jaeger에서의 대표 예

    
      
receivers데이터를 받는 입구otlp, jaeger, zipkin, kafka, nop

      
processors받은 데이터를 가공 (묶기, 거르기, 샘플링)batch, memory_limiter, tail_sampling, attributes, adaptive_sampling

      
exporters데이터를 내보내는 출구jaeger_storage_exporter, kafka, otlp, nop

      
connectors한 파이프라인의 출구를 다른 파이프라인의 입구로 연결spanmetrics (스팬 → 메트릭, 3편 SPM에서 사용)

      
extensions데이터 흐름과 별개로 돌아가는 부가 기능jaeger_storage, jaeger_query, remote_sampling, healthcheckv2

      
service위에서 정의한 것 중 실제로 켤 것을 고르고 파이프라인으로 연결service.extensions, service.pipelines.traces

    
  

  

    
초보자가 가장 많이 하는 실수

    
아래쪽에 부품을 정의만 하고 service 절에 적지 않으면 그 부품은 동작하지 않습니다. 오류도 없이 조용히 무시되는 경우가 많아서, "설정했는데 왜 안 되지?"의 1순위 원인입니다. 부품을 추가했다면 반드시 service.pipelines나 service.extensions에도 이름을 적었는지 확인하세요.

  

  
여기서 핵심 질문이 하나 생깁니다. Collector는 원래 데이터를 받아 보내는 도구인데, Jaeger는 저장된 데이터를 읽어서 보여 주는 일도 해야 합니다. 읽기는 파이프라인 흐름에 들어맞지 않습니다. 그래서 Jaeger는 읽기 기능을 extension으로 만들었고, 쓰기(exporter)와 읽기(extension)가 같은 저장소 설정을 공유하도록 저장소 허브를 따로 두었습니다. 이것이 다음 장의 주제입니다.

Jaeger 고유 부품 다섯 가지

  
Jaeger 바이너리에는 OTel 공식 부품에 더해 Jaeger가 직접 만든 부품이 들어 있습니다. 이 다섯 가지만 알면 어떤 Jaeger 설정 파일도 읽을 수 있습니다. 왼쪽 목록에서 하나씩 눌러 보세요.

  

    

    

  

  

    
부품 관계를 한 문장으로

    
jaeger_storage가 저장소에 이름표를 붙여 등록하면, 쓰는 쪽(jaeger_storage_exporter)과 읽는 쪽(jaeger_query)과 샘플링 쪽(remote_sampling의 adaptive 모드)이 모두 그 이름표로 같은 저장소를 가리킵니다.

실행은 이렇게

    
컨테이너로 실행할 때는 설정 파일을 컨테이너 안에 넣고 --config로 경로를 알려 줍니다. 설정 파일 없이 실행하면 바이너리에 내장된 all-in-one 설정(메모리 저장소)으로 뜹니다.


docker run --rm --name jaeger \
  -e OS_URL=http://opensearch:9200 \
  -p 4317:4317 -p 4318:4318 -p 16686:16686 -p 13133:13133 \
  -v $(pwd)/config.yaml:/jaeger/config.yaml \
  jaegertracing/jaeger:2.21.0 \
  --config /jaeger/config.yaml

    
설정 파일을 고치지 않고 값 하나만 바꾸고 싶다면 --set=receivers.otlp.protocols.grpc.endpoint=0.0.0.0:4317처럼 덮어쓸 수도 있습니다. 내장 all-in-one 설정을 빠르게 조정할 때 편리합니다.

  







  
5
배포 토폴로지와 Kafka

  
역할을 어떻게 조합해 배치하느냐가 토폴로지입니다. 공식 문서가 꼽는 확장형 구성은 두 가지이고, 여기에 OTel Collector를 앞에 두는 방식이 더해집니다.

  

    
구성흐름장점주의점

    
      
all-in-onejaeger (수집+조회) → 저장소가장 단순. 외부 저장소를 쓰면 여러 대로 늘릴 수도 있음읽기와 쓰기를 따로 늘리거나 따로 보안 정책을 걸기 어려움

      
직접 저장
direct to storage		collector → 저장소 ← query읽기·쓰기를 독립적으로 확장, 조회 서버만 사내망에 두는 식의 분리 가능저장소가 평균뿐 아니라 최대 트래픽까지 받아 내야 함

      
Kafka 경유
via Kafka		collector → Kafka → ingester → 저장소 ← query트래픽 급증을 Kafka가 흡수해 유실 방지, ingester는 여러 대로 부하 분산Kafka 클러스터 운영 부담, 데이터가 조회되기까지 지연 발생 가능

      
OTel Collector 앞단앱 → OTel Collector(agent·gateway) → Jaeger메트릭·로그와 수집 경로 통합, 파드 정보 부착, tail sampling 샤딩데이터를 한 번 더 풀고 묶는 비용

    
  

  
Jaeger 역할들은 상태를 저장하지 않으므로(stateless) 여러 인스턴스를 나란히 띄울 수 있습니다. 모든 상태는 저장소에 있습니다. 그렇다면 Kafka는 언제 필요할까요? 직접 확인해 봅시다.


  
트래픽 급증 시뮬레이터

  
평소 유입량과 급증 배율을 바꿔 보세요. 저장소는 초당 일정량까지만 쓸 수 있고, collector에는 짧은 급증을 버티는 메모리 큐가 있습니다. 숫자는 개념 이해를 위한 가상 값입니다.

  

    

      
      
      
      
    

    

      
직접 저장

      
Kafka 경유 주황 영역은 대기량 (별도 축)

    

    
유입량저장량저장소 쓰기 한계 (30,000/초)유실Kafka에 쌓인 대기량(lag)

  

  

    
시뮬레이터에서 읽어야 할 것

    
급증이 짧으면 collector 큐만으로 충분합니다. 급증이 길어져 큐가 넘치면, 직접 저장 구성은 그 순간부터 스팬을 버립니다. Kafka 경유 구성은 버리지 않고 쌓아 두었다가 급증이 끝난 뒤 따라잡습니다. 대신 쌓인 만큼 화면에 늦게 보입니다. 즉 Kafka는 "유실 대신 지연"을 택하는 장치입니다. 장애 순간의 트레이스가 가장 중요한데 그 순간에 트래픽이 가장 몰린다는 점을 떠올리면, 대형 고객사에서 Kafka를 두는 이유가 보입니다.

  

  

    
Kafka 구성의 설정 포인트

    
collector 쪽은 저장소 exporter 대신 kafka exporter를, ingester 쪽은 kafka receiver를 씁니다. 두 쪽의 토픽 이름과 인코딩(otlp_proto 등)이 반드시 같아야 합니다. ingester를 여러 대 띄우면 Kafka 파티션 단위로 부하가 자동 분산되므로, ingester 수보다 파티션 수가 적으면 남는 ingester는 놉니다.


collector:  receivers [otlp] → processors [batch] → exporters [kafka]
ingester :  receivers [kafka] → processors [batch] → exporters [jaeger_storage_exporter]
query    :  receivers [nop]   → exporters [nop]      + extensions [jaeger_storage, jaeger_query]

  







  
6
저장소 고르기

  
Jaeger는 저장소를 직접 만들지 않고 기존 데이터베이스에 붙습니다. 공식 문서는 Cassandra, Elasticsearch, OpenSearch를 주요 분산 저장소로 꼽고, 대규모 운영에는 Cassandra보다 OpenSearch(또는 Elasticsearch)를 권장합니다.

  

    
저장소성격잘 맞는 곳주의점

    
      
memory프로세스 메모리개발, 데모, 설정 테스트재시작하면 전부 사라짐

      
Badger내장형 로컬 키-값 저장소단일 노드 운영, 소규모 고객사인스턴스 1대에 묶여 수평 확장 불가

      
OpenSearch
Elasticsearch		검색 엔진대부분의 운영 환경, 태그 기반 자유 검색, Kibana·Dashboards로 직접 분석인덱스 수명 관리(롤오버·ILM·정리 작업) 설계 필요. ES는 7.x·8.x 지원

      
Cassandra분산 키-값 DB이미 Cassandra를 운영하는 조직, ID 조회 위주검색을 Jaeger가 대신 구현해 제약이 있고, 태그마다 색인 쓰기가 추가됨. 장점은 TTL로 보존 관리가 쉬움

      
ClickHouse열 지향 분석 DB대량 데이터 분석, 이미 ClickHouse를 운영하는 조직실험적 기능. storage.clickhouse 기능 게이트로 켜야 하고 스키마가 바뀔 수 있음

      
원격 gRPC외부 저장소 플러그인공식 지원 외 저장소 연결 (예: 커뮤니티 PostgreSQL 구현)플러그인의 성숙도와 유지 보수를 직접 확인해야 함

    
  

  

    
ClickHouse는 아직 실험 단계입니다

    
ClickHouse는 v2.18에 추가되었지만 기능 게이트 뒤에 있는 실험적(experimental) 백엔드입니다. v2.21 문서 기준으로도 실험 단계이므로 운영 도입 전에는 검증 환경에서 충분히 시험하고, 버전 업그레이드 때 스키마 변경 공지를 반드시 확인하세요.

  


  
왜 공식 권장이 Cassandra가 아니라 OpenSearch일까

  
Cassandra는 단건 쓰기가 빠르지만 키-값 저장소라서 "서비스가 payment이고 태그가 X인 트레이스" 같은 검색을 스스로 못 합니다. 그래서 Jaeger가 서비스명·오퍼레이션명·태그마다 별도 색인 레코드를 추가로 써서 검색을 흉내 냅니다. 스팬 하나를 쓰는데 실제로는 여러 번 쓰는 셈(쓰기 증폭)이라 전체 처리량은 OpenSearch와 비슷해지고, 검색 결과가 일관되지 않을 수 있습니다. OpenSearch는 스팬 하나를 한 번 쓰면 색인은 OpenSearch 내부에서 처리합니다. 반면 보존 기간 관리는 Cassandra의 TTL이 훨씬 간단합니다.


  
우리 고객사엔 무엇을? 저장소 선택 도우미

  


  
보관용 저장소(archive)라는 장치

  
주 저장소는 보통 1~2주 정도로 짧게 보관해 비용을 아낍니다. 그런데 장애 보고서에 첨부할 트레이스는 몇 달 보관해야 할 때가 있습니다. Jaeger는 보관용 저장소를 따로 지정할 수 있고, Jaeger UI에서 사람이 직접 "보관" 버튼을 누른 트레이스만 그곳에 복사됩니다. 자동으로 쌓이지 않으니 보존 기간을 길게 잡아도 부담이 적습니다. 4장 설정 예제의 traces_archive가 바로 이것입니다.

8
v1에서 옮겨 오기

  
인수인계 받은 고객사 환경에 v1이 남아 있는 경우가 적지 않습니다. v1은 2025년 말에 지원이 끝났고, v2.14(2026년 1월)부터는 v1 방식의 query·collector·ingester 이미지가 더 이상 배포되지 않습니다. 공식 이전 안내는 Jaeger 문서의 Migration 페이지에서 링크된 가이드를 기준으로 하고, 아래는 MSP 현장에서 쓰기 좋게 순서를 정리한 체크리스트입니다. 진행하면서 체크해 보세요.

  

  

  


  
설정 옮기기 대응표

  

    
v1에서 쓰던 것v2에서는

    
      
jaeger-agent (DaemonSet·사이드카)OTel Collector를 agent로 배치하거나, SDK가 collector로 직접 OTLP 전송

      
SPAN_STORAGE_TYPE, ES_SERVER_URLS 등 환경 변수extensions.jaeger_storage.backends.<이름>.<종류> YAML. 값은 ${env:...}로 주입 가능

      
샘플링 전략 파일 플래그remote_sampling.file.path

      
적응형 샘플링 설정remote_sampling.adaptive + adaptive_sampling processor

      
SPM용 메트릭 저장소 설정jaeger_storage.metric_backends + jaeger_query.storage.metrics

      
관리 포트의 헬스 체크·메트릭헬스 체크 13133 (healthcheckv2), 자체 메트릭 8888 (service.telemetry)

      
이미지 jaegertracing/all-in-one 등jaegertracing/jaeger 하나

    
  

  

    
저장소 데이터는 어떻게 되나요?

    
v2도 같은 종류의 저장소(ES/OpenSearch, Cassandra 등)에 붙으므로 보통은 기존 저장소를 그대로 연결하는 방식으로 옮깁니다. 공식 Cassandra 예제의 keyspace 이름이 jaeger_v1_dc1인 것도 그 흔적입니다. 다만 인덱스 접두사(index_prefix)나 롤오버 설정이 v1과 달라지면 옛 데이터가 조회되지 않을 수 있으니, 병행 운영 기간에 과거 트레이스가 v2 UI에서 보이는지 반드시 확인하세요.

  







  
9
MSP 규모별 설계

  
지금까지의 내용을 고객사 규모에 맞춰 조립하면 이렇습니다. 구체적인 배포와 튜닝은 3편에서 실습합니다.

  

    
소규모·PoC
서비스 수십 개 이하, 트래픽 적음

      
  • all-in-one 한 대
  • 저장소: Badger (데이터 유지) 또는 memory (데모)
  • 백업·보존 기간은 디스크 용량으로 관리
  • 확장이 필요해지면 저장소부터 교체

    
중규모 운영
서비스 수십~수백 개

      
  • collector와 query 분리
  • 저장소: OpenSearch (ILM으로 보존 관리)
  • 앞단에 OTel Collector (파드 정보 부착·민감 정보 제거)
  • 보관용 저장소 분리

    
대규모·다중 고객
트래픽 급증이 잦고 유실이 치명적

      
  • OTel Collector gateway (tail sampling)
  • collector → Kafka → ingester 여러 대
  • OpenSearch 클러스터 + 보관용 저장소
  • query는 인증 프록시 뒤에 별도 배치

  

  

    
보안: Jaeger UI에는 로그인 기능이 없습니다

    
query 역할의 UI와 API는 기본적으로 인증 없이 열립니다. 트레이스에는 URL, 사용자 ID, 내부 호스트명 같은 민감한 정보가 담기기 쉬우므로 인터넷이나 넓은 사내망에 그대로 노출하면 안 됩니다. 앞단에 OAuth2 Proxy 같은 인증 프록시를 두고 사내 IdP와 연결하는 방식이 일반적입니다. OIDC 연동 원리는 이 강의 시리즈의 OAuth/OIDC 강의를 참고하세요. 수집 포트(4317/4318)도 TLS와 접근 제어를 적용하는 것이 좋습니다.

  

  

    
AIOps와의 연결 고리

    
v2.21에 내장된 all-in-one 설정에는 jaeger_query 아래에 AI 에이전트용 MCP 엔드포인트(/api/ai/mcp/)를 켜는 항목이 들어 있습니다. LLM 에이전트가 트레이스를 조회 도구로 쓰게 하는 흐름이 Jaeger 쪽에서도 공식화되고 있다는 뜻입니다. 새로 추가된 기능이라 세부 동작은 버전마다 바뀔 수 있으며, 활용법은 7편에서 다룹니다.

정리와 다음 편

  
    
    
  1. Jaeger v2는 OTel Collector의 배포판입니다. 실행 파일은 jaeger 하나이고, YAML 설정에서 켠 부품이 collector·query·ingester·all-in-one 역할을 결정합니다.
    2. 
    
  2. Jaeger 고유 부품은 jaeger_storage(저장소 허브), jaeger_storage_exporter(쓰기), jaeger_query(조회·UI), remote_sampling(샘플링 전략 서버), adaptive_sampling(확률 자동 계산) 다섯 가지입니다.
    3. 
    
  3. 저장소는 이름표로 연결됩니다. 이름이 한 곳이라도 어긋나면 기동에 실패하거나 엉뚱한 곳을 읽습니다. 부품은 service 절에 적어야 켜집니다.
    4. 
    
  4. 직접 저장은 단순하지만 급증 때 유실 위험이 있고, Kafka 경유는 유실 대신 지연을 택합니다.
    5. 
    
  5. 운영 저장소는 공식 권장대로 OpenSearch/Elasticsearch가 기본값이고, Badger는 단일 노드, ClickHouse는 아직 실험 단계입니다. UI에는 인증이 없으니 반드시 프록시 뒤에 두세요.
    6. 
  

  

    
다음 편

    
3편 · Jaeger 구축·운영 실전

    
Docker Compose로 Jaeger와 OpenSearch를 띄우고 Kubernetes(Helm·OpenTelemetry Operator)로 옮겨 갑니다. 인덱스 롤오버와 ILM으로 보존 기간을 관리하고, 원격·적응형 샘플링을 설정하고, Jaeger UI의 타임라인·트레이스 비교·Critical Path를 읽는 법과 spanmetrics 커넥터로 서비스 성능 모니터링(Monitor 탭)을 켜는 방법까지 실습합니다.
