1장

4단계 계층과 경계

  • 클러스터 — 서버 인스턴스 하나가 관리하는 전체(2편). 역할, 테이블스페이스, 데이터베이스 목록은 클러스터 수준에서 모든 데이터베이스가 공유합니다.
  • 데이터베이스 — 서로 완전히 분리된 객체 모음. 하나의 연결은 하나의 데이터베이스에만 속합니다.
  • 스키마 — 데이터베이스 안의 이름 공간(폴더). 다른 스키마의 객체는 스키마.객체로 자유롭게 함께 쓸 수 있습니다.
  • 객체 — 테이블, 뷰, 인덱스, 시퀀스, 함수 등. 반드시 어떤 스키마에 속합니다.
시험 포인트: 데이터베이스 경계 vs 스키마 경계

SELECT * FROM hr.emp JOIN public.orders ...처럼 같은 데이터베이스의 다른 스키마는 한 쿼리에서 조인할 수 있지만, 다른 데이터베이스의 테이블은 직접 조회할 수 없습니다. 다른 DB의 데이터가 필요하면 postgres_fdw, dblink 같은 확장이나 EPAS의 데이터베이스 링크를 씁니다. 반면 역할(사용자)은 클러스터 공용이라, 한 번 만든 사용자는 모든 데이터베이스에 접속을 시도할 수 있습니다(허용 여부는 권한과 pg_hba.conf가 결정).

비유: 건물 · 층 · 방 · 가구

클러스터는 건물, 데이터베이스는 층, 스키마는 방, 객체는 가구입니다. 같은 층의 방끼리는 문을 열고 오갈 수 있지만(스키마 간 조인), 다른 층으로 가려면 엘리베이터(외부 연결 확장)가 필요합니다. 건물 출입증(역할)과 비상계단(테이블스페이스 = 저장 위치)은 건물 전체가 함께 씁니다.

4장

스키마

스키마는 데이터베이스 안에서 객체를 나누는 이름 공간입니다. 같은 이름의 테이블도 스키마가 다르면 공존할 수 있습니다(hr.emp와 public.emp). 쓰임새는 크게 세 가지입니다.

  • 업무별 분리 — hr, sales, audit처럼 한 DB 안에서 영역을 나눔
  • 권한 경계 — 스키마 단위로 USAGE, CREATE 권한을 줘서 접근을 통제(7편)
  • 여러 애플리케이션 공존 — 앱마다 스키마를 따로 두고 같은 DB를 공유
CREATE SCHEMA hr AUTHORIZATION hr_owner;     -- 소유자 지정
CREATE TABLE hr.emp (empno int PRIMARY KEY, ename text);
ALTER TABLE hr.emp SET SCHEMA archive;       -- 다른 스키마로 이동
DROP SCHEMA archive CASCADE;                 -- 안의 객체까지 모두 삭제 (주의)
\dn+                                         -- psql: 스키마 목록과 권한

특별한 스키마들

스키마설명
publicinitdb가 만드는 기본 스키마. 스키마 없이 만든 객체가 흔히 여기에 들어감
pg_catalog시스템 카탈로그 테이블과 내장 함수. search_path에 없어도 항상 가장 먼저 검색됨
information_schemaSQL 표준 방식의 메타데이터 뷰
pg_temp_N세션별 임시 테이블이 만들어지는 곳
EPAS 시스템 스키마EPAS는 Oracle 호환 객체(DUAL, 딕셔너리 뷰, 내장 패키지)를 위한 시스템 스키마를 두고 있어, 스키마 이름 없이도 이 객체들을 쓸 수 있음
시험 포인트: PostgreSQL 15의 public 스키마 변화

PostgreSQL 14까지는 모든 사용자(PUBLIC)가 public 스키마에 객체를 만들 수 있었습니다. 15부터는 이 CREATE 권한이 기본으로 없어졌고, public 스키마의 소유자도 pg_database_owner(그 DB의 소유자)가 되었습니다. 그래서 새 DB에서 일반 사용자가 CREATE TABLE t (...)를 하면 "permission denied for schema public"이 날 수 있습니다. 필요한 경우 GRANT CREATE ON SCHEMA public TO app_user;로 명시적으로 허용하거나, 전용 스키마를 만들어 줍니다.

5장

search_path 해석기

스키마 이름 없이 emp라고만 쓰면, 서버는 search_path에 적힌 스키마를 앞에서부터 차례로 뒤져 처음 찾은 것을 씁니다. 새 객체를 스키마 없이 만들면 search_path에서 실제로 존재하는 첫 번째 스키마에 만들어집니다. 기본값은 "$user", public이고, $user는 현재 사용자 이름과 같은 스키마를 뜻합니다.

sales 데이터베이스에 있는 스키마와 객체

SHOW search_path;
SET search_path = hr, public;                       -- 이 세션만
ALTER ROLE app_user SET search_path = app, public;  -- 역할 기본값 (5편 우선순위)
SELECT current_schema();                            -- 객체가 만들어질 스키마
SELECT current_schemas(true);                       -- pg_catalog 포함 실제 검색 순서
보안: search_path 가로채기

누구나 객체를 만들 수 있는 스키마가 search_path 앞쪽에 있으면, 악의적인 사용자가 같은 이름의 함수나 테이블을 만들어 다른 사용자의 쿼리를 가로챌 수 있습니다. PostgreSQL 15의 public 스키마 권한 변경이 이 위험을 줄이기 위한 것입니다. SECURITY DEFINER 함수에는 SET search_path를 함수 속성으로 고정하는 것이 권장됩니다.

시너님, 패키지EPAS Oracle 호환 객체 (12편)—

제약조건

CREATE TABLE hr.dept (
  deptno  int  PRIMARY KEY,                       -- 유일 + NOT NULL, 자동으로 B-tree 인덱스
  dname   text NOT NULL UNIQUE                    -- UNIQUE도 인덱스를 자동 생성
);
CREATE TABLE hr.emp (
  empno   int  PRIMARY KEY,
  deptno  int  REFERENCES hr.dept(deptno),        -- 외래 키: 참조하는 쪽엔 인덱스가 자동 생성되지 않음
  sal     numeric(10,2) CHECK (sal > 0)
);
시험 포인트

PRIMARY KEY와 UNIQUE 제약은 인덱스를 자동으로 만들지만, FOREIGN KEY는 참조하는 컬럼(위의 emp.deptno)에 인덱스를 만들지 않습니다. 부모 행 삭제나 조인이 느려지는 흔한 원인이라 직접 인덱스를 만들어 주는 것이 좋습니다. UNLOGGED 테이블은 장애 후 내용이 비워지고 스탠바이로 복제되지 않는다는 점도 자주 나옵니다.

7장

테이블스페이스

PostgreSQL의 테이블스페이스는 데이터 파일을 저장할 디렉터리의 별칭입니다. 특정 테이블이나 인덱스를 다른 디스크(예: 빠른 NVMe)에 두고 싶을 때 씁니다. Oracle의 테이블스페이스처럼 데이터 파일을 미리 할당하거나 용량 한도를 두는 개념은 없습니다.

기본 테이블스페이스위치담는 것
pg_defaultPGDATA/base/따로 지정하지 않은 모든 데이터베이스 객체
pg_globalPGDATA/global/클러스터 공용 시스템 카탈로그

만들고 쓰는 순서

# 1) OS에서 디렉터리 준비 (root) — 비어 있고, enterprisedb 소유, 절대 경로
sudo mkdir -p /nvme/edb/fast
sudo chown enterprisedb:enterprisedb /nvme/edb/fast
sudo chmod 700 /nvme/edb/fast
# SELinux가 켜져 있다면 3편처럼 컨텍스트도 맞춤
-- 2) SQL로 등록 (슈퍼유저)
CREATE TABLESPACE fast_ssd OWNER app_owner LOCATION '/nvme/edb/fast';
GRANT CREATE ON TABLESPACE fast_ssd TO app_owner;   -- 다른 역할이 쓰려면

-- 3) 사용
CREATE TABLE orders_hot (...) TABLESPACE fast_ssd;
CREATE INDEX ON orders (created_at) TABLESPACE fast_ssd;
CREATE DATABASE analytics TABLESPACE fast_ssd;        -- DB의 기본 위치로
SET default_tablespace = fast_ssd;                    -- 이 세션에서 만드는 객체의 기본 위치
SET temp_tablespaces = fast_ssd;                      -- 정렬용 임시 파일 위치

-- 4) 옮기기 (테이블을 새로 쓰며, 끝날 때까지 ACCESS EXCLUSIVE 잠금)
ALTER TABLE orders_hot SET TABLESPACE pg_default;
ALTER TABLE ALL IN TABLESPACE fast_ssd SET TABLESPACE pg_default;

-- 5) 확인과 삭제
\db+
SELECT spcname, pg_tablespace_location(oid) FROM pg_tablespace;
DROP TABLESPACE fast_ssd;     -- 모든 DB에서 비어 있어야 성공

등록하면 PGDATA의 pg_tblspc/ 아래에 테이블스페이스 OID 이름의 심볼릭 링크가 생기고, 지정한 디렉터리 안에 버전별 하위 디렉터리(PG_18_…)가 만들어집니다. 2편 9장에서 본 바로 그 구조입니다.

$ ls -l /var/lib/edb/as18/data/pg_tblspc/
lrwxrwxrwx 1 enterprisedb enterprisedb 16 ... 16390 -> /nvme/edb/fast
$ ls /nvme/edb/fast
PG_18_…
테이블스페이스는 백업 단위가 아니다

테이블스페이스 디렉터리만 따로 백업하거나 다른 서버로 옮겨 붙일 수는 없습니다. 파일의 트랜잭션 상태와 카탈로그 정보는 PGDATA에 있기 때문입니다. 테이블스페이스를 담은 디스크를 잃으면 클러스터 전체가 영향을 받습니다. 또 PGDATA 안에 테이블스페이스 디렉터리를 만들면 경고가 나오며 권장하지 않습니다. 물리 백업(10편)은 테이블스페이스까지 함께 챙겨야 합니다.

현장 판단: 클라우드에서도 테이블스페이스가 필요할까

클라우드 VM에서는 블록 볼륨 하나를 키우는 것이 쉬워서 테이블스페이스를 쓰지 않는 구성이 많습니다. 쓰는 경우는 주로 성능 등급이 다른 볼륨을 섞을 때(뜨거운 테이블은 고성능 볼륨에), 또는 한 볼륨의 최대 크기를 넘을 때입니다. 관리 복잡도가 늘어나므로 필요가 분명할 때만 도입하세요.

시험 포인트

CREATE TABLESPACE는 트랜잭션 블록 안에서 실행할 수 없고, LOCATION은 이미 존재하는 빈 디렉터리의 절대 경로여야 하며 서버 실행 계정 소유여야 합니다. DROP TABLESPACE는 모든 데이터베이스에서 그 테이블스페이스가 비어 있어야 성공합니다. ALTER TABLE ... SET TABLESPACE는 테이블을 다시 쓰므로 잠금과 디스크 공간이 필요합니다.

8장

시스템 카탈로그

PostgreSQL은 모든 객체 정보를 pg_catalog 스키마의 테이블에 저장합니다. psql의 \d 명령도 결국 이 테이블들을 조회하는 SQL입니다(psql -E로 실행하면 실제 쿼리를 보여 줍니다).

카탈로그내용
pg_database데이터베이스 목록 (클러스터 공용)
pg_namespace스키마 목록
pg_class테이블, 인덱스, 시퀀스, 뷰 등 "관계"들. relkind: r 테이블, i 인덱스, S 시퀀스, v 뷰, m 구체화된 뷰, p 파티션 테이블, t TOAST, f 외부 테이블
pg_attribute컬럼 정보
pg_index, pg_constraint인덱스와 제약조건
pg_proc함수·프로시저
pg_roles (pg_authid)역할 (클러스터 공용). pg_authid는 비밀번호 해시 포함, 슈퍼유저만 조회
pg_tablespace테이블스페이스 (클러스터 공용)

같은 질문, 세 가지 조회 방식

질문을 고르면 pg_catalog, information_schema, EPAS Oracle 호환 뷰로 각각 어떻게 조회하는지 보여 줍니다.

크기 확인 함수

SELECT pg_size_pretty(pg_database_size('sales'));          -- DB 전체
SELECT pg_size_pretty(pg_relation_size('hr.emp'));         -- 테이블 본체만
SELECT pg_size_pretty(pg_indexes_size('hr.emp'));          -- 인덱스 합계
SELECT pg_size_pretty(pg_total_relation_size('hr.emp'));   -- 본체 + 인덱스 + TOAST
SELECT pg_size_pretty(pg_tablespace_size('fast_ssd'));     -- 테이블스페이스
SELECT 'hr.emp'::regclass::oid;                            -- 이름 → OID
시험 포인트

pg_relation_size는 테이블 본체만, pg_total_relation_size는 인덱스와 TOAST까지 포함합니다. "테이블이 디스크에서 실제로 차지하는 전체 크기"를 묻는다면 total 쪽이 답입니다.

9장

Oracle 호환 딕셔너리 뷰

Oracle 호환 모드 클러스터에는 Oracle의 데이터 딕셔너리와 같은 이름·구조의 뷰가 들어 있습니다. Oracle DBA가 쓰던 모니터링 쿼리와 스크립트를 크게 고치지 않고 쓸 수 있게 해 줍니다.

접두어보여 주는 범위예
USER_현재 사용자가 소유한 객체USER_TABLES, USER_INDEXES, USER_TAB_COLUMNS
ALL_현재 사용자가 접근할 수 있는 객체ALL_TABLES, ALL_OBJECTS, ALL_VIEWS
DBA_데이터베이스의 모든 객체 (관리자용)DBA_TABLES, DBA_USERS, DBA_OBJECTS
SELECT table_name, tablespace_name FROM user_tables;
SELECT owner, object_name, object_type FROM all_objects WHERE owner = 'HR';
SELECT username FROM dba_users;

결과의 객체 이름은 Oracle처럼 대문자로 표시되는 것이 기본이며, 5편의 edb_redwood_raw_names로 저장된 그대로(소문자) 표시하게 바꿀 수 있습니다. 이 뷰들은 PostgreSQL 모드(--no-redwood-compat)로 만든 클러스터에는 포함되지 않습니다(3편).

시험 포인트

USER_ ⊂ ALL_ ⊂ DBA_ 순으로 범위가 넓어집니다. "내가 만든 테이블 목록"은 USER_TABLES, "내가 조회할 수 있는 모든 테이블"은 ALL_TABLES입니다.
