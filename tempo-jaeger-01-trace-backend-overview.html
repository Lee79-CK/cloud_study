아래 그림은 "주문하기" 버튼 한 번이 만든 트레이스입니다. 842ms 가운데 500ms가 어디서 사라졌는지 한눈에 보이나요? 이 그림을 가능하게 하는 것이 오늘의 주인공, 트레이스 백엔드입니다.

POST /orders trace 4bf92f35…0e4736 · 10 spans · 5 services

막대 길이는 소요 시간, 들여쓰기는 호출 관계입니다. 빗금 막대는 에러가 난 스팬입니다. 2장에서 이 트레이스를 직접 클릭하며 해부합니다.

1

왜 트레이스 백엔드인가

고객사에서 이런 문의가 들어왔다고 해 봅시다. "어제 오후 3시쯤 주문이 몇 건 엄청 느렸다는 민원이 있었어요. 원인이 뭔가요?"

메트릭 대시보드를 열면 p99 지연 시간 그래프에 뾰족한 봉우리가 보입니다. 무언가 느렸다는 건 알 수 있습니다. 로그를 열면 서비스 다섯 개가 각자 남긴 수만 줄이 쏟아집니다. 어느 줄이 "그 느린 주문"의 것인지 이어 붙이기가 어렵습니다.

트레이스는 이 두 신호 사이의 빈칸을 채웁니다. 요청 하나가 여러 서비스를 거치는 동안 남긴 기록을 하나의 ID로 묶어 순서와 소요 시간까지 보여 주기 때문입니다.

신호답해 주는 질문잘 못 하는 것
메트릭얼마나 자주, 얼마나 느리게, 얼마나 많이 실패하는가 (추세·경보)"그 한 건"이 왜 느렸는지
로그한 서비스 안에서 무슨 일이 있었는가 (상세 사건)여러 서비스에 흩어진 사건을 한 요청으로 이어 보기
트레이스요청 하나가 어디를 거쳐 어디서 시간을 썼는가 (경로·인과)장기 추세 (그래서 메트릭과 함께 씁니다)

그런데 트레이스는 애플리케이션이 만들고 끝나는 데이터가 아닙니다. 서비스마다 흩어져 생긴 스팬을 누군가 받아서 모으고, 오래 보관하고, 나중에 조건으로 찾아 줘야 합니다. 이 일을 하는 시스템이 트레이스 백엔드이고, 오픈소스 진영의 대표 주자가 Jaeger와 Grafana Tempo입니다.

OpenTelemetry 시리즈와의 관계

앞선 OpenTelemetry 12편 시리즈는 "트레이스를 만들고 보내는 쪽"(SDK 계측, Collector 파이프라인)을 다뤘습니다. 이번 시리즈는 "트레이스를 받아서 쓰는 쪽"입니다. 계측 방법은 다시 설명하지 않고, 필요할 때 "OTel 몇 편 참고"로 연결합니다.

MSP 엔지니어에게 특히 중요한 이유

MSP는 고객사 애플리케이션 코드를 직접 소유하지 않는 경우가 많습니다. 코드를 몰라도 트레이스가 있으면 서비스 간 호출 구조와 병목 지점을 외부에서 파악할 수 있습니다. 그리고 트레이스 백엔드 자체는 대부분 인프라 팀이 운영하는 시스템입니다. 용량, 비용, 보존 기간, 멀티테넌시 모두 우리 몫입니다.

2

30초 복습: 트레이스와 스팬

백엔드를 이해하려면 백엔드가 받는 데이터의 모양을 알아야 합니다. 핵심만 짚겠습니다. (자세한 데이터 모델은 OTel 시리즈 2편)

  • 트레이스(Trace): 요청 하나의 전체 여정. 128비트 Trace ID 하나로 식별합니다.
  • 스팬(Span): 여정 속 작업 한 조각. 이름, 시작 시각, 소요 시간, 64비트 Span ID, 그리고 자기를 부른 부모 Span ID를 가집니다.
  • 루트 스팬(Root span): 부모가 없는 첫 스팬. 보통 사용자 요청을 처음 받은 곳(게이트웨이 등)입니다.
  • 속성(Attribute): http.request.method=POST 같은 키-값 정보. 검색 조건이 되는 재료입니다.
  • 리소스(Resource): 스팬을 만든 주체 정보. service.name, k8s.pod.name 등.
  • 상태(Status): Unset·Ok·Error 세 가지.

직접 해부하기

막대를 클릭하면 그 스팬에 실제로 담긴 정보가 아래에 나타납니다. 백엔드는 이런 레코드를 하루에 수억~수십억 개 받습니다.

"직접 시간(self time)"이 왜 중요한가

CreateOrder는 818ms나 걸렸지만 그 시간 대부분은 자식 스팬(결제 호출)을 기다린 시간입니다. 스팬 자신이 쓴 시간은 자식 시간을 뺀 나머지입니다. 트레이스를 볼 때 가장 긴 막대가 범인이 아닐 수 있다는 점을 기억하세요. 끝까지 내려가서 "실제로 시간을 쓴 가장 깊은 스팬"을 찾는 것이 요령이고, 3편에서 배울 Jaeger의 Critical Path 기능이 이것을 자동으로 표시해 줍니다.

서비스를 넘나드는 비결: traceparent 헤더

서비스가 다르면 메모리도 프로세스도 다른데, 어떻게 같은 Trace ID로 묶일까요? 호출할 때마다 HTTP 헤더(또는 메시지 헤더)에 W3C Trace Context 형식의 traceparent를 실어 보내기 때문입니다. 이것을 컨텍스트 전파(Context propagation)라고 합니다. 각 부분을 클릭해 보세요.

백엔드 운영자가 자주 만나는 증상: "트레이스가 끊겨요"

중간 서비스 하나가 이 헤더를 전달하지 않으면(프록시가 헤더를 지우거나, 계측 안 된 서비스가 끼어 있으면) 트레이스가 둘로 쪼개집니다. 백엔드에서는 "부모를 찾을 수 없는 스팬"으로 보입니다. 백엔드 문제가 아니라 전파 문제인 경우가 대부분이며, 8편 트러블슈팅에서 판별법을 다룹니다.

3

스팬이 백엔드에 도착하기까지

스팬 하나가 태어나서 화면에 보이기까지 여섯 단계를 거칩니다. 단계 버튼을 누르거나 "자동 재생"으로 흐름을 따라가 보세요. 이 시리즈가 주로 다루는 구간은 5·6단계이고, 4단계는 두 시리즈가 겹치는 경계입니다.

포트 번호 세 개만 기억해 두세요

4317(OTLP gRPC)과 4318(OTLP HTTP)은 Collector와 백엔드 모두가 스팬을 받는 표준 포트입니다. 조회 쪽은 Jaeger UI가 기본 16686, Tempo HTTP API가 기본 3200입니다. 방화벽·보안 그룹·NetworkPolicy 문의에서 가장 많이 확인하는 번호들입니다.

4

백엔드가 하는 다섯 가지 일

트레이스 백엔드의 일은 "받기 → 쌓기 → 찾을 수 있게 정리하기 → 찾기 → 보여 주기"로 나뉩니다. Jaeger와 Tempo의 차이는 대부분 세 번째 일(색인)을 얼마나, 어떻게 하느냐에서 갈라집니다. 탭을 눌러 두 도구가 같은 일을 어떻게 다르게 하는지 비교해 보세요.

5

분산 트레이싱의 계보

옛날 블로그 글과 지금의 공식 문서가 서로 다른 말을 하는 이유는 이 역사에 있습니다. 특히 Jaeger v1 → v2, Tempo 2.x → 3.0 전환 때문에 인터넷 자료의 상당수가 이미 낡았습니다. 항목을 클릭하면 설명이 펼쳐집니다.

    낡은 자료를 알아보는 신호

    문서나 블로그에 jaeger-agent, Jaeger 전용 클라이언트 라이브러리(jaeger-client-*), jaegertracing/all-in-one 이미지가 나오면 v1 시절 자료입니다. Tempo 문서에 ingester, compactor 설정 블록이 나오면 2.x 시절 자료입니다. 둘 다 현재 버전에서는 제거되었습니다.

    6

    두 가지 설계 철학: 색인할 것인가, 말 것인가

    이 장이 1편에서 가장 중요합니다. 두 도구를 가르는 핵심 질문은 하나입니다. "찾기 쉽게 미리 정리해 둘 것인가, 싸게 쌓아 두고 필요할 때 뒤질 것인가?"

    📚

    도서관 방식 · 색인 기반

    책이 들어올 때마다 사서가 제목·저자·주제 카드를 만들어 카드 목록에 꽂습니다. 찾을 때는 카드만 보면 되니 빠릅니다. 대신 카드를 만드는 수고와 카드 보관 공간이 계속 듭니다. 책이 폭증하면 사서와 서가를 더 늘려야 합니다.

    전통적인 Jaeger + Elasticsearch/OpenSearch·Cassandra 구성이 이 방식입니다.

    📦

    물류창고 방식 · 색인 최소화

    들어온 물건을 시간 순으로 상자에 담아 싼 창고에 쌓습니다. 상자 겉면에는 "이 상자에 어떤 송장번호가 들어 있을 수 있는지" 요약표만 붙입니다. 송장번호로 찾으면 금방이지만, "빨간 물건 전부"를 찾으려면 상자를 열어 봐야 합니다. 대신 창고료가 쌉니다.

    Tempo가 객체 스토리지 + Parquet 블록 + 블룸 필터로 구현한 방식입니다.

    "상자를 열어 본다"가 생각보다 빠른 이유

    Tempo는 블록을 Parquet이라는 열(column) 지향 형식으로 저장합니다. "service.name이 payment인 스팬"을 찾을 때 상자 전체가 아니라 service.name 열만 읽으면 됩니다. 자주 쓰는 속성은 전용 열(dedicated column)로 빼 두어 더 빨리 읽게 할 수도 있습니다. 그래서 "색인이 없다"는 말은 "느리다"가 아니라 "검색 비용을 쓰기 시점이 아니라 읽기 시점에 낸다"는 뜻에 가깝습니다. 자세한 구조는 4편에서 봅니다.

        정리와 다음 편

        1. 트레이스는 요청 하나의 여정을 Trace ID로 묶은 기록이고, 메트릭(추세)과 로그(상세) 사이의 빈칸인 경로와 인과를 보여 줍니다.
        2. 스팬은 앱에서 태어나 OTLP로 Collector를 거쳐 백엔드에 도착합니다. 서비스 간 연결은 traceparent 헤더 전파 덕분이며, 끊긴 트레이스는 대개 전파 문제입니다.
        3. 백엔드의 일은 수집·저장·색인·조회·시각화 다섯 가지이고, 두 도구의 차이는 주로 색인 전략에서 나옵니다.
        4. Jaeger는 색인 기반 검색과 독립 UI에서, Tempo는 객체 스토리지 기반의 낮은 비용과 Grafana 연결에서 출발했습니다. 지금은 둘 다 OTLP·OTel 중심이고 경계가 가까워지는 중입니다.
        5. 현재 기준은 Jaeger v2와 Tempo 3.0입니다. jaeger-agent나 Tempo ingester가 나오는 자료는 낡은 자료로 보고 걸러 읽으세요.
