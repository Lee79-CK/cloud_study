Terraform & Ansible 강의 · Level 5 통합·MSP 실전 · 25편 / 26편 · 시리즈 목차

고객 하나를 잘 하는 것에서, 서른을 같은 품질로 MSP 멀티 고객 운영 전략 — 고객별 저장소와 모듈·역할 표준 라이브러리, 태깅과 비용 귀속, 변경 관리(승인·롤백), 드리프트 상시 감시, 감사 증적, 신규 고객 온보딩 템플릿, 흔한 사고와 예방

24편은 고객 하나의 저장소였습니다. MSP의 현실은 고객이 수십이고, 고객마다 계정·요구사항·변경 승인자가 다르며, 엔지니어 한 명이 여러 고객을 맡습니다. 이때 질문이 바뀝니다 — “공통 모듈을 고치면 어느 고객이 영향을 받나?”, “지난달 A사 운영 서버를 누가 왜 바꿨나?”, “신규 고객을 일주일 안에 표준대로 올릴 수 있나?”, “잘못된 계정에 apply하는 사고를 어떻게 막나?”. 이번 편은 이 질문들에 답하는 장치를 실제로 만들고 돌려 봅니다: Git 태그로 버전을 매긴 공통 모듈, 고객별 버전 점검, 신규 고객 저장소를 찍어 내고 나중의 표준 변경까지 반영하는 템플릿, 여러 고객의 드리프트 매트릭스, state 사고 복구, 태그 기반 비용 귀속 리포트, 감사 증적 묶음.

표준화

라이브러리(모듈·역할) + 템플릿 → 고객 저장소는 값만 다르다

가시성

계정 구조가 먼저

저장소 구조보다 먼저 정해야 하는 것은 클라우드 계정 구조입니다. 고객별·환경별 계정(AWS Organizations의 OU), MSP 운영 계정에서 고객 계정으로 역할 위임(8·12편 assume_role·OIDC)이 기본입니다. 계정이 고객 경계와 일치하면 비용·권한·사고 범위가 모두 단순해집니다.

tools/module_versions.py — 고객별 사용 버전 점검
#!/usr/bin/env python3
"""고객 저장소들이 쓰는 공통 모듈 버전과 최신 버전을 비교 (Renovate 같은 도구가 없을 때의 최소 점검)"""
import re, subprocess, sys, pathlib
LIB = "file:///tmp/msp/lib-terraform"           # 실제로는 https://git.example.internal/msp/terraform-modules.git
tags = subprocess.run(["git", "ls-remote", "--tags", LIB.replace("file://", "")], capture_output=True, text=True).stdout
versions = sorted({m.group(1) for m in re.finditer(r"refs/tags/v(\d+\.\d+\.\d+)$", tags, re.M)},
                  key=lambda v: tuple(map(int, v.split("."))))
latest = versions[-1]
print(f"공통 모듈 최신: v{latest}\n")
print("| 고객 | 모듈 | 사용 중 | 상태 |\n|---|---|---|---|")
for repo in sys.argv[1:]:
    for tf in pathlib.Path(repo).rglob("*.tf"):
        if ".terraform" in tf.parts:
            continue
        for m in re.finditer(r'source\s*=\s*"git::[^"]*//modules/([\w-]+)\?ref=v([\d.]+)"', tf.read_text()):
            mod, ver = m.groups()
            major_gap = int(latest.split(".")[0]) - int(ver.split(".")[0])
            state = "최신" if ver == latest else ("MAJOR 차이 — 변경 내역 검토 필요" if major_gap else "업데이트 가능")
            print(f"| {pathlib.Path(repo).name} | {mod} | v{ver} | {state} |")
# 실측

| 고객  | 모듈  | 사용 중 | 상태          |
| custa | label | v1.0.0  | 업데이트 가능 |
| custb | label | v1.1.0  | 최신          |

“호환”과 “영향”은 다르다v1.1.0은 입력 호환(MINOR)이지만 모든 자원의 태그가 바뀌어 올리는 고객의 plan이 전 자원 update를 보인다. CHANGELOG에 “plan 영향”을 따로 적는다
승격 경로MSP 랩 → 내부 시험 고객 → 개발계 고객 → 운영계 고객 (8편 승격과 같은 흐름). 운영계는 변경 창에서
자동 갱신 PRRenovate·Dependabot류가 고객 저장소에 “v1.0.0 → v1.1.0” PR을 만들고, 24편 PR 워크플로가 plan을 붙인다 — 사람은 plan을 보고 승인
지원 범위“최신 MAJOR와 직전 MAJOR만 지원” 같은 규칙으로 오래된 버전이 끝없이 남지 않게

Ansible 역할은 16편처럼 컬렉션(msp.platform)으로 묶어 고객 저장소의 requirements.yml에 정확한 버전으로 고정합니다. EE 이미지(20편)도 같은 원칙 — 고객 저장소의 ansible-navigator.yml에 이미지 태그를 고정합니다.

tools/tag_report.py — 계정 전체 태그 집계 (Resource Groups Tagging API)
#!/usr/bin/env python3
"""계정의 자원을 태그 기준으로 집계: 고객별 자원 수, 필수 태그 누락(=비용 귀속 불가) 목록"""
import boto3, collections, sys
REQUIRED = ["Customer", "Project", "Env", "Owner", "ManagedBy"]
kw = {"region_name": "ap-northeast-2"}
if len(sys.argv) > 1: kw["endpoint_url"] = sys.argv[1]
api = boto3.client("resourcegroupstaggingapi", **kw)
by_customer, missing = collections.Counter(), []
for page in api.get_paginator("get_resources").paginate():
    for r in page["ResourceTagMappingList"]:
        tags = {t["Key"]: t["Value"] for t in r.get("Tags", [])}
        by_customer[tags.get("Customer", "(없음)")] += 1
        lack = [k for k in REQUIRED if k not in tags]
        if lack: missing.append((r["ResourceARN"].split(":")[-1], lack, tags.get("ManagedBy", "-")))
print("| 고객(Customer 태그) | 자원 수 |\n|---|---|")
for k, v in sorted(by_customer.items()): print(f"| {k} | {v} |")
print(f"\n필수 태그 누락 {len(missing)}건 (비용 귀속 불가)\n\n| 자원 | 누락 태그 | ManagedBy |\n|---|---|---|")
for res, lack, mb in missing: print(f"| {res} | {', '.join(lack)} | {mb} |")
# 실측 (moto: custa·custb 를 Terraform 으로 만든 뒤, 콘솔에서 급히 만든 VPC 하나를 흉내)
| 고객(Customer 태그) | 자원 수 |
| (없음)              | 1       |
| custa               | 2       |
| custb               | 2       |

필수 태그 누락 1건 (비용 귀속 불가)
| 자원                     | 누락 태그                                | ManagedBy |
| vpc/vpc-138fc7a33bf5553fc | Customer, Project, Env, Owner, ManagedBy | -         |
비용 귀속 실무방법
비용 할당 태그 활성화AWS 결제 콘솔(관리 계정)에서 Customer·Project·Env 등을 “비용 할당 태그”로 활성화해야 Cost Explorer·CUR에 나타난다. 활성화 이전 비용에는 소급되지 않으므로 고객 온보딩 첫날에
계정 = 고객이면계정별 비용이 곧 고객 비용 — 태그는 서비스·환경 분해용
공유 자원 (공용 NAT·Transit Gateway·로그 수집)사용량 지표(트래픽·로그량)로 배분 규칙을 정하고 문서화. 태그만으로는 나눌 수 없다
태그 없는 자원위 리포트를 매주 → “코드로 흡수(9편) 또는 삭제” 이슈. ManagedBy가 없는 자원은 드리프트 감시에도 안 잡힌다
태그가 바뀌는 순간Customer·Project 값을 바꾸면 비용 보고서가 끊기고 동적 인벤토리 그룹이 바뀐다(18편 3장) — 태그 변경은 MAJOR 급으로 다룬다

tools/fleet_drift.sh
#!/bin/bash
# 모든 고객 × 루트에 대해 plan -detailed-exitcode → 드리프트 매트릭스 (읽기 전용 역할로 실행)
# 사용: fleet_drift.sh <고객 디렉터리>...   결과: Markdown 표 (stdout)
printf '| 고객 | 결과 | 변경 리소스 | 메모 |\n|---|---|---|---|\n'
for d in "$@"; do
  c=$(basename "$d")
  out=$( (cd "$d" && tofu init -input=false -no-color -backend-config="bucket=msp-tfstate" -backend-config="key=$c/dev/core.tfstate" -backend-config="region=ap-northeast-2" >/dev/null 2>&1 \
         && tofu plan -input=false -no-color -var-file=dev.tfvars -detailed-exitcode -out=drift.tfplan) 2>&1 ); code=$?
  case $code in
    0) printf '| %s | ✅ 일치 | 0 | |\n' "$c" ;;
    2) n=$(cd "$d" && tofu show -json drift.tfplan | python3 -c "import json,sys;d=json.load(sys.stdin);print(sum(1 for r in d.get('resource_changes',[]) if r['change']['actions'] not in (['no-op'],['read'])))")
       addrs=$(cd "$d" && tofu show -json drift.tfplan | python3 -c "import json,sys;d=json.load(sys.stdin);print(', '.join(r['address'] for r in d.get('resource_changes',[]) if r['change']['actions'] not in (['no-op'],['read'])))")
       printf '| %s | ⚠️ 드리프트 | %s | %s |\n' "$c" "$n" "$addrs" ;;
    *) msg=$(echo "$out" | grep -m1 -E "Error:" | sed 's/Error: //'); printf '| %s | ❌ 실패 | - | %s |\n' "$c" "$msg" ;;
  esac
done

운영 리듬내용
매일 (자동)전 고객 × 루트 plan(읽기 전용 역할) + Ansible check 잡(21편) → 매트릭스 → 드리프트·실패는 고객 저장소 이슈(24편 drift.yml)
매주 (사람)미해결 드리프트 검토: 코드로 흡수(9편) / 되돌림 / 예외 등록(만료일). “실패”는 권한·계정·잠금 문제라 드리프트보다 먼저 본다
매월 (보고)고객별 드리프트 건수·원인(콘솔 수정·긴급 조치·외부 도구)·해결 시간 → 월간 보고서
병렬 실행고객 수가 많으면 CI 매트릭스(고객별 잡)로 — 한 고객의 실패가 다른 고객 점검을 막지 않게, 각 잡은 그 고객 계정의 읽기 역할만
“실패”를 드리프트로 착각하지 않는다

plan이 실패한 고객은 드리프트 여부를 알 수 없는 상태입니다. 권한 만료·계정 오설정·state 잠금 잔존이 흔한 원인이고, 며칠씩 실패가 계속되면 그동안의 드리프트가 쌓입니다. 매트릭스에서 실패를 별도 색으로 두고, 이틀 연속 실패는 당직이 확인하도록 합니다.

#!/usr/bin/env python3
"""변경 감사 증적 묶음: 누가·언제·무엇을 승인하고 적용했는지 + 산출물 해시 (변조 확인용)"""
import hashlib, json, os, sys, datetime, zipfile
def sha256(p): return hashlib.sha256(open(p, "rb").read()).hexdigest()
plan_json, apply_log, out = sys.argv[1], sys.argv[2], sys.argv[3]
plan = json.load(open(plan_json))
changes = [r for r in plan.get("resource_changes", []) if r["change"]["actions"] not in (["no-op"], ["read"])]
summary = {}
for r in changes: summary["/".join(r["change"]["actions"])] = summary.get("/".join(r["change"]["actions"]), 0) + 1
evidence = {
    "change_id": os.environ.get("CHANGE_ID", "CR-미지정"),
    "repository": os.environ.get("GITHUB_REPOSITORY", "local"),
    "commit": os.environ.get("GITHUB_SHA", "local"),
    "approved_by": os.environ.get("APPROVER", "미기록"),       # GitHub environment 승인자 (API로 조회해 넣는다)
    "applied_at": datetime.datetime.now(datetime.timezone.utc).isoformat(timespec="seconds"),
    "terraform_version": plan.get("terraform_version"),
    "summary": summary,
    "resources": [r["address"] for r in changes],
    "artifacts": {os.path.basename(p): sha256(p) for p in (plan_json, apply_log)},
}
with zipfile.ZipFile(out, "w", zipfile.ZIP_DEFLATED) as z:
    z.writestr("evidence.json", json.dumps(evidence, ensure_ascii=False, indent=2))
    z.write(plan_json, os.path.basename(plan_json)); z.write(apply_log, os.path.basename(apply_log))
print(json.dumps({k: evidence[k] for k in ("change_id", "approved_by", "summary", "artifacts")}, ensure_ascii=False, indent=2))

템플릿을 만들며 만난 함정 (실측)

① 워크플로 파일의 GitHub 식 ${{ … }}는 템플릿 엔진(Jinja)의 {{ … }}와 겹칩니다. 템플릿 처리 대상(.jinja)에 넣으면 깨지므로, 워크플로는 템플릿 변수 없이 ${{ github.repository }}처럼 저장소에서 값을 얻게 바꿨습니다. ② 템플릿 경로를 상대 경로로 생성하면 나중에 copier update가 “Updating is only supported in git-tracked templates”로 실패했습니다 — 템플릿은 Git 저장소 주소(태그)로 참조합니다. ③ 답변 파일(.copier-answers.yml)을 템플릿에 넣지 않으면 update 자체가 불가능합니다.

13과제

여러분 조직에 맞게

과제 1. 저장소·계정 구조 설계서

여러분이 맡은(또는 가상의) 고객 5곳에 대해 2장의 저장소 구성과 계정·OU 구조, MSP 운영 계정의 역할 위임 방식을 한 장으로 그리세요. 고객 계약 종료 시 “저장소 이관 + 권한 회수 + state 이관” 절차까지 적습니다.

과제 2. 공통 모듈 MAJOR 릴리스

vpc 모듈의 변수 이름을 바꾸는 MAJOR 변경(v2.0.0)을 가정하고 ① moved 블록·변수 별칭으로 고객 쪽 변경을 최소화(9편) ② 이주 가이드 ③ 고객별 업그레이드 순서·기한을 담은 릴리스 계획을 작성하세요. 3장 스크립트로 “MAJOR 차이” 고객이 어떻게 표시되는지 확인합니다.

과제 3. 드리프트 매트릭스를 CI로

6장 스크립트를 GitHub Actions 매트릭스(고객별 잡, 고객 계정 읽기 역할 OIDC)로 옮기고, 결과를 모아 하나의 요약 이슈(또는 대시보드 페이지)로 만드세요. 한 고객의 실패가 다른 고객에 영향을 주지 않는지 확인합니다.

과제 4. 템플릿 변경 전파 연습

템플릿 v1.2.0에서 drift 워크플로의 일정을 바꾸고 trivy 예외 파일 형식을 갱신한 뒤, 고객 저장소 3곳에 copier update를 적용하세요. 고객이 손으로 고친 파일과 충돌(.rej)이 나면 어떻게 처리할지 규칙을 정합니다.

과제 5. 사고 회고 템플릿

9장 사고 중 하나를 골라 비난 없는 회고(postmortem) 문서를 써 보세요: 타임라인, 영향(고객·자원·시간), 근본 원인, 탐지 방법, 재발 방지 조치(코드·정책·절차), 담당·기한. 재발 방지 조치는 반드시 “사람의 주의”가 아니라 장치(정책·가드·테스트)로 적습니다.
