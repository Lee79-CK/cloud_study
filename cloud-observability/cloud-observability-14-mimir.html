Cloud 모니터링·로깅 실전 강의 14편 (Level 5. 대규모 운영, 첫 편)

장기 저장과 멀티클러스터

지금 메트릭은 VM, edge, hub의 Prometheus에 7일씩 흩어져 있고, 6편의 Grafana는 고객사 Prometheus에 직접 들어가 질의합니다. 고객사가 열 곳이 되고 보존이 1년이 되면 이 구조는 버티지 못합니다. 고객사가 관제 센터로 밀어 올리는 구조로 바꿉니다.

대상: 1~2년차 클라우드 엔지니어 형식: 개념 + 실습 5개 예상 소요: 4시간 기준: Mimir 3.2.2, Prometheus 3.13
관제 센터로 무엇을, 얼마나 보낼 것인가고객사 수와 Prometheus 규모를 넣으면 중앙 Mimir가 받아야 할 활성 시계열과 초당 샘플, 연간 저장량을 어림합니다. "요약만" 비율은 작성 중 실측(로컬 746개 중 64개만 전송, 약 8.6%)을 썼습니다.
고객사 수20
고객사당 Prometheus3
Prometheus당 시계열200K
수집 간격
중앙 활성 시계열
distributor가 받는 초당 샘플
1년 저장량 (어림)

0시작하기 전에

Level 5의 첫 편입니다. 2편에서 예약해 둔 hub의 30080 포트(Mimir 수신과 조회)와 mimir-blocks, mimir-ruler, mimir-alertmanager 버킷을 이번에 씁니다.

학습 목표

  1. 중앙 장기 저장소가 필요한 이유와 Push(Remote Write) 구조가 MSP에 맞는 이유를 설명할 수 있다.
  2. Remote Write의 동작(큐, 재시도, WAL)과 2.0의 차이, write_relabel_configs로 보낼 데이터를 고르는 법을 안다.
  3. Mimir 3의 구성 요소와 두 가지 구조(클래식, Kafka 기반 ingest storage)를 이해하고 단일 바이너리로 설치할 수 있다.
  4. 고객사별 테넌트, 테넌트별 보존과 한도, 테넌트 연합 질의를 구성할 수 있다.
  5. Prometheus HA 쌍을 중복 제거하고 장애 전환이 어떻게 일어나는지 설명할 수 있다.
  6. 전체 Prometheus, Agent 모드, Alloy, OTLP 게이트웨이 중 수집 쪽을 고르고, Mimir와 Thanos를 비교할 수 있다.
이 편의 검증 범위

Mimir 3.2.2 단일 바이너리를 SeaweedFS에 연결해 띄우고, Prometheus 3.13.1 세 대(HA 쌍 두 대와 Agent 모드 한 대)로 실제로 Remote Write를 보냈습니다. 고객사별 테넌트, Remote Write 2.0 수신, HA 쌍의 중복 제거(중복 샘플 271개 폐기)와 장애 전환(복제본 b → a, 질의 결과에 30초 넘는 빈 구간 없음), 테넌트 연합 질의, OTLP 메트릭 수신, 테넌트별 보존 설정 적재, 요약만 보냈을 때의 시계열 감소(746 → 64)는 모두 실측입니다. 게이트웨이 설정은 Collector contrib 0.162.0으로 검사했습니다. Kubernetes 위의 설치, kube-prometheus-stack의 Remote Write 설정, Grafana 데이터소스는 실행하지 못했습니다.

1왜 중앙 저장소인가

지금 구조의 문제중앙 저장소로 바꾸면
보존 7일. 작년 같은 달과 비교, 연간 용량 보고 불가오브젝트 스토리지에 1년 이상, 고객사별로 다르게
Grafana가 고객사 Prometheus에 직접 접속 (6편 Lab 2의 임시 구조). 고객사 방화벽에 인바운드 허용 필요고객사가 관제 센터로 나가는 연결만 (Push)
고객사마다 데이터소스가 따로. 전체 현황 질의 불가테넌트 연합으로 여러 고객사를 한 질의로
Prometheus를 이중화하면 같은 데이터가 두 벌HA 쌍을 받아 한 벌로 중복 제거
고객사 Prometheus가 죽으면 그 기간 데이터 확인 불가이미 보낸 데이터는 중앙에 남음

고객사 쪽 Prometheus는 사라지지 않습니다. 짧은 보존으로 그 자리에서 수집, 기록 규칙, 알림 평가(6편)를 계속하고, 중앙에는 필요한 것을 밀어 올립니다. 관제 센터와의 연결이 끊겨도 고객사 안의 알림은 동작한다는 6편의 원칙이 그대로 유지됩니다.

2Remote Write

Prometheus가 수집한 샘플을 WAL에서 읽어 원격 저장소로 계속 보내는 기능입니다.

1

WAL에서 읽기

3편의 WAL에 쓰인 샘플을 별도의 읽기 위치로 따라갑니다. 원격이 잠시 끊겨도 WAL에 남아 있는 범위(약 2시간)까지는 다시 보낼 수 있습니다.

2

샤드 큐로 묶기

시계열을 여러 큐(샤드)로 나눠 병렬로 보냅니다. 보내는 속도가 수집 속도를 못 따라가면 샤드 수를 자동으로 늘립니다.

3

재시도

5xx, 429는 재시도하고, 4xx(형식 오류, 한도 위반 중 일부)는 버립니다. 버린 양은 prometheus_remote_storage_samples_failed_total에 남습니다.

Remote Write 2.0

Prometheus 3.x는 2.0 형식을 보낼 수 있습니다(protobuf_message: io.prometheus.write.v2.Request). 라벨 문자열을 표로 모아 중복 없이 보내 대역폭을 줄이고, 메타데이터(타입, 단위, 설명)와 네이티브 히스토그램, Exemplar를 함께 실어 보냅니다(3편 7장). 작성 중 HA 쌍의 한쪽을 2.0으로 보냈는데 Mimir 3.2.2가 정상으로 받았고, 오히려 그쪽이 HA 대표로 선택되어 저장되었습니다. Prometheus 로그에는 "2.0에서는 메타데이터가 항상 함께 가므로 metadata_config.send 설정이 불필요하다"는 경고가 한 줄 남았습니다.

무엇을 보낼 것인가

모든 시계열을 보내면 관제 센터 비용이 고객사 수에 비례해 커집니다. 4편 8장에서 예고한 대로, 중앙에는 기록 규칙의 결과와 꼭 필요한 원본만 보내는 것이 MSP의 기본 전략입니다.

write_relabel_configs:
  - source_labels: [__name__]
    regex: '.+:.+|up|ALERTS|node_filesystem_avail_bytes|node_filesystem_size_bytes'
    action: keep

이름에 콜론이 있는 것(4편의 명명 규칙을 따른 기록 규칙 결과), up, 알림 상태 ALERTS, 장기 추세가 필요한 디스크 용량만 남깁니다. 작성 중 같은 규칙으로 Prometheus 로컬의 시계열 746개 중 64개만 Mimir에 들어갔습니다(약 8.6%). 4편의 기록 규칙 이름이 표준이라는 것이 여기서 또 쓸모가 있습니다. 조사할 때 원본이 필요하면 고객사 Prometheus(7일)를 직접 보거나, 문제 서비스의 원본만 잠시 추가로 보냅니다.

3Mimir 3의 구조

Grafana Mimir는 Prometheus 호환의 수평 확장 저장소입니다(Cortex에서 출발, AGPLv3, 1편 9장). Loki, Tempo와 같은 설계를 공유합니다.

구성 요소하는 일Loki의 비슷한 것
distributor테넌트 확인, 한도, HA 중복 제거, 해시로 ingester 선택Distributor
ingester최근 데이터를 메모리와 WAL에, 2시간 블록으로 오브젝트 스토리지에Ingester
querier, query-frontendPromQL 실행, 분할과 캐시. 3.0부터 Mimir 자체 질의 엔진(MQE)이 기본Querier, Query Frontend

두 가지 구조와 이 랩의 선택

Mimir 3.0은 ingest storage라는 새 구조를 도입했습니다. distributor와 ingester 사이에 Kafka 호환 시스템을 두어 쓰기와 읽기를 독립적으로 확장합니다(Tempo 3과 같은 방향). 기존 구조는 클래식이라 부르며 3.x에서도 지원됩니다. 공식 Helm 차트(mimir-distributed 6.x)는 ingest storage와 데모용 단일 노드 Kafka를 기본으로 켜고 모든 구성 요소를 따로 띄우기 때문에 랩 규모에서는 무겁습니다.

이 랩은 단일 바이너리(-target=all), 클래식 구조를 직접 만든 매니페스트로 띄웁니다. 작성 중 같은 설정으로 Mimir 3.2.2를 실행했고, 단일 바이너리에서도 HA 중복 제거와 테넌트 연합이 모두 동작했습니다. 고객사 수십 곳 규모가 되면 차트로 옮기며, 그때 Kafka를 직접 운영할지(또는 관리형 Kafka) 클래식을 유지할지를 정합니다.

4멀티테넌시와 테넌트 연합

Loki, Tempo, Pyroscope와 똑같이 X-Scope-OrgID 헤더가 테넌트입니다. 이 시리즈는 모든 저장소에서 테넌트 = 고객사로 통일했습니다(cust-a, msp).

기능설정실측
테넌트별 보존런타임 설정의 overrides.<테넌트>.compactor_blocks_retention_periodcust-a 1년, msp 90일 설정이 /runtime_config에 적재됨
테넌트별 한도max_global_series_per_user, ingestion_rate 등한 고객사의 폭주가 다른 고객사를 막지 않게
테넌트 연합 질의tenant_federation.enabled, 헤더에 cust-a|msp결과에 __tenant_id__ 라벨이 붙어 고객사별로 구분됨

런타임 설정은 재시작 없이 다시 읽히므로, 새 고객사를 온보딩할 때 ConfigMap의 runtime.yaml에 한 줄 추가하는 것으로 계약 조건을 반영할 수 있습니다. 연합 질의는 관제 센터의 "전체 고객사 현황" 대시보드에 쓰고, 고객사 담당자에게는 자기 테넌트 데이터소스만 엽니다.

5HA 쌍과 중복 제거

Prometheus를 두 대 띄우면 한 대가 죽어도 수집이 계속되지만, 중앙에는 같은 데이터가 두 벌 갑니다. Mimir의 HA tracker가 그중 한 벌만 받습니다.

1

쌍 알아보기

두 Prometheus는 클러스터 라벨이 같고 복제본 라벨만 다르게 외부 라벨을 붙입니다. 이 랩의 설정은 kube-prometheus-stack의 기본 외부 라벨 이름을 그대로 써서 prometheus(클러스터), prometheus_replica(복제본)입니다.

2

대표 선출

테넌트, 클러스터마다 먼저 도착한 복제본을 대표로 정하고 그 샘플만 저장합니다. 나머지 복제본의 샘플은 성공 응답을 주되 버립니다.

3

장애 전환

대표가 일정 시간(ha_tracker_failover_timeout, 기본 30초) 이상 아무것도 보내지 않으면 다른 복제본으로 대표를 바꿉니다. 저장된 시계열에서 복제본 라벨은 지워지므로 질의하는 쪽은 차이를 모릅니다.

실측

복제본 a(Remote Write 1.0)와 b(2.0)를 함께 띄우자 b가 대표로 선출되었고, a의 샘플은 cortex_distributor_deduped_samples_total{cluster="cust-a-web"}에 271개 폐기로 기록되었습니다. Mimir의 up 결과에는 prometheus_replica 라벨이 없었습니다. b를 강제로 종료하자 1분 안에 대표가 a로 바뀌었고(cortex_ha_tracker_elected_replica_changes_total 2), 그 4분 동안의 기록 규칙 그래프(15초 간격 17개 점)에는 30초 넘는 빈 구간이 없었습니다.

두 복제본의 데이터는 미세하게 다릅니다

두 Prometheus는 서로 다른 순간에 수집하므로 같은 시계열이라도 값과 시각이 조금씩 다릅니다. 대표가 바뀌는 순간 카운터의 rate 그래프에 작은 계단이 생길 수 있습니다. 정상 동작이며, 대표가 자주 바뀌지 않도록 두 복제본의 수집 상태를 함께 감시합니다.

재시작한 Prometheus가 오래된 WAL을 다시 보내거나 시계가 틀린 경우입니다. 테넌트 한도의 out_of_order_time_window를 검토하고, 두 Prometheus의 NTP를 확인합니다.

Remote Write 429 또는 discarded: per_user_series_limit운영

테넌트의 시계열 한도를 넘었습니다. write_relabel_configs가 의도대로 거르는지 먼저 확인하고(필터가 빠지면 수십 배가 됨), 필요하면 런타임 설정으로 그 테넌트의 한도를 올립니다.

HA 쌍인데 데이터가 두 벌, 또는 replica 라벨이 남아 있음Lab 3

Mimir의 ha_cluster_label, ha_replica_label과 Prometheus의 외부 라벨 이름이 다르거나 accept_ha_samples가 꺼진 경우입니다. 이 랩은 kube-prometheus-stack의 기본 이름(prometheus, prometheus_replica)에 맞췄습니다.

대표 복제본이 계속 바뀜운영

대표 쪽의 Remote Write가 자주 밀리는 경우입니다. prometheus_remote_storage_samples_pending, 네트워크 지연을 보고, 필요하면 ha_tracker_failover_timeout을 늘립니다.

테넌트 연합 질의가 오류Lab 5

tenant_federation.enabled가 켜졌는지, 헤더 값이 파이프(|)로 구분됐는지 봅니다. Grafana 데이터소스에서는 헤더 값 전체를 그대로 넣습니다.

Mimir 시작 실패: memberlist, ring 관련 오류Lab 1

단일 바이너리도 내부적으로 링을 씁니다. join_members가 가리키는 headless 서비스가 있는지, 파드 IP를 광고 주소로 쓸 수 있는지 확인합니다. 작성 환경에서는 광고 주소를 127.0.0.1로 지정해 해결했습니다.

Grafana에서 고객사 VM 데이터가 안 보임 (전환 후)Lab 4

VM은 요약만 보내므로 원본 메트릭(예: shop_http_requests_total)은 Mimir에 없습니다. 기록 규칙 이름으로 질의하거나, 필요한 원본을 write_relabel_configs에 더합니다.

오늘의 핵심

  1. 고객사 Prometheus는 그 자리에서 수집, 규칙, 알림을 계속하고, 중앙에는 Remote Write로 밀어 올립니다. 관제 센터에서 고객사 안으로 들어가는 연결이 사라집니다.
  2. 중앙에는 요약(기록 규칙, up, ALERTS)만 보내 비용을 줄입니다(실측 746 → 64). Remote Write 2.0은 Mimir 3.2가 받습니다.
  3. Mimir 3은 Kafka 기반 ingest storage가 새 기본이지만 클래식도 지원하며, 랩은 단일 바이너리 클래식으로 충분합니다.
  4. 테넌트 = 고객사. 보존과 한도는 런타임 설정으로, 전체 현황은 테넌트 연합으로.
  5. HA 쌍은 클러스터 라벨이 같고 복제본 라벨이 다르면 Mimir가 한 벌만 받고, 대표가 죽으면 넘겨받습니다(실측 1분 이내, 빈 구간 없음).
  6. Mimir(Push, 테넌트 내장)와 Thanos(사이드카 Pull, 고객사 버킷)는 네트워크와 데이터 소유권 요구로 고릅니다.

다음 편 예고: 15편 하이브리드 클라우드 수집 설계

지금까지 고객사 A는 VM 두 대와 Kubernetes 하나였습니다. 실제 MSP는 온프레미스, AWS, Azure가 섞인 고객사 여러 곳을 다룹니다. 15편에서는 고객사 B를 추가하는 온보딩을 처음부터 끝까지 해 보며, 클라우드 서비스 메트릭(CloudWatch, Azure Monitor)을 끌어오는 방법, 고객사 쪽 수집기를 Ansible로 일괄 배포하는 방법, 네트워크가 막힌 고객사를 위한 중계 게이트웨이, 13편에서 남겨 둔 VM의 프로파일 경로, 그리고 이번 편의 "데이터가 밖으로 나가면 안 되는 고객사" 예외 설계를 다룹니다.
