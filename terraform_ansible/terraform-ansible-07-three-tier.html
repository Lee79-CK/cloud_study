Level 1의 마지막 편입니다. 지금까지 배운 HCL, 변수, state, 모듈을 모두 써서 실제 서비스 형태의 인프라를 만듭니다. 인터넷에서 들어온 요청은 퍼블릭 서브넷의 ALB만 통과할 수 있고, 웹 서버는 ALB에게서 온 요청만, DB는 웹 서버에게서 온 요청만 받습니다. 계층마다 문이 하나씩, 그 문을 여는 열쇠(보안 그룹)도 하나씩입니다. 이번 편은 처음으로 시간당 비용이 드는 리소스(ALB, RDS)가 등장하므로, 실습 시간 계획과 정리 절차까지 함께 다룹니다.

구성 요소를 선택하세요

요청의 흐름은 내 PC → ALB(퍼블릭) → 웹 서버(프라이빗) → RDS(프라이빗)입니다. 웹 서버와 DB에는 공인 IP가 없어, 인터넷에서 직접 닿을 방법이 아예 없습니다.

계층놓이는 곳받는 트래픽나가는 트래픽
퍼블릭 (ALB)퍼블릭 서브넷 2개 AZ허용 CIDR(내 IP)에서 80VPC 대역의 80 (웹 서버)
애플리케이션 (EC2)프라이빗 서브넷 2개 AZ에 한 대씩ALB 보안 그룹에서 80S3(접두사 목록) 443, VPC 대역의 5432
데이터 (RDS)프라이빗 서브넷 2개 AZ (서브넷 그룹)앱 보안 그룹에서 5432없음
이번 실습의 단순화: 앱과 DB가 같은 프라이빗 서브넷

6편 VPC 모듈에는 퍼블릭·프라이빗 두 종류의 서브넷만 있으므로, 웹 서버와 RDS를 같은 프라이빗 서브넷에 두고 보안 그룹으로만 계층을 나눴습니다. 운영 환경에서는 인터넷·NAT 경로가 전혀 없는 별도의 데이터 서브넷(격리 서브넷)을 두고 DB 서브넷 그룹을 그쪽으로 지정하는 경우가 많습니다. 네트워크 ACL까지 계층별로 나눌 수 있기 때문입니다. VPC 모듈에 세 번째 서브넷 종류를 추가하는 것이 과제 6입니다.

왜 계층을 나누는가

한 계층이 뚫려도 다음 계층은 별도의 문으로 막혀 있습니다(심층 방어). 웹 서버가 취약점으로 장악되어도 그 서버가 갈 수 있는 곳은 DB 포트와 S3 저장소뿐이고, DB는 인터넷과 아예 연결되지 않습니다. 또한 계층마다 확장 방식이 달라(웹은 수평 확장, DB는 수직 확장·읽기 복제본) 따로 다루는 것이 운영에도 유리합니다.

3네트워크 준비

프라이빗 서버는 패키지를 어디서 받는가 — 그리고 모듈 업그레이드 체험

웹 서버는 프라이빗 서브넷에 있어 인터넷으로 나갈 길이 없습니다. 그런데 부팅할 때 dnf install nginx를 해야 합니다. 선택지는 넷입니다.

방법비용열리는 범위이번 실습
NAT 게이트웨이시간당 과금 + 처리 데이터당 과금 + 공인 IPv4인터넷 전체로 나감 (보안 그룹·NACL로 제한)선택 (6편 모듈 enable_nat_gateway)
S3 게이트웨이 엔드포인트무료같은 리전의 S3만기본: Amazon Linux 2023의 패키지 저장소는 리전의 S3에 있으므로 이것만으로 dnf가 동작
인터페이스 엔드포인트 (SSM 등)엔드포인트·AZ마다 시간당 과금지정한 AWS 서비스만사용 안 함 (Session Manager가 필요할 때 18편에서)
없음0없음패키지를 미리 넣은 골든 이미지를 쓰는 불변 인프라(1편 7장)라면 가능
게이트웨이 엔드포인트의 한계

S3 게이트웨이 엔드포인트는 Amazon Linux 저장소에만 해당합니다. Ubuntu·RHEL의 공개 미러, PyPI, Docker Hub처럼 S3 밖의 인터넷 주소는 여전히 막혀 있습니다. 그런 서버라면 NAT나 사내 미러(프록시)가 필요합니다. 또 웹 서버의 IAM 역할에 Session Manager 정책을 붙였지만, SSM 엔드포인트나 NAT가 없으면 에이전트가 AWS에 연결하지 못해 실제 접속은 되지 않습니다. 이번 편에서는 서버에 직접 들어갈 필요가 없도록 user_data만으로 구성합니다.

4보안 그룹 설계

IP가 아니라 “누구에게서 왔는가”로 허용한다

보안 그룹 규칙의 출처(source)에는 CIDR뿐 아니라 다른 보안 그룹을 지정할 수 있습니다(referenced_security_group_id). “앱 보안 그룹은 ALB 보안 그룹이 붙은 것에서 온 80번만 허용”이라고 쓰면, ALB의 IP가 바뀌든 노드가 늘든 규칙을 고칠 필요가 없습니다. 오토스케일링으로 서버가 늘어나도 같은 보안 그룹만 붙이면 DB 접근이 자동으로 허용됩니다.

보안 그룹인바운드아웃바운드모듈
ALB SG허용 CIDR(내 IP) → 80VPC 대역 → 80alb
앱 SGALB SG → 80S3 접두사 목록 → 443, VPC 대역 → 5432app-servers
DB SG앱 SG → 5432없음rds-postgres
VPC 기본 SG없음 (6편 모듈이 모든 규칙 제거)없음vpc

트래픽 판정기 — 출발지와 목적지를 고르세요

순환 참조를 피하는 법

“ALB는 앱 SG로만 나갈 수 있다”(ALB 아웃바운드가 앱 SG 참조)와 “앱은 ALB SG에서만 받는다”(앱 인바운드가 ALB SG 참조)를 둘 다 하고 싶어집니다. 그런데 ALB 모듈이 앱 SG ID를 입력으로 받고, 앱 모듈이 ALB SG ID를 입력으로 받으면 모듈 사이에 순환 의존이 생깁니다(3편 10장 Error: Cycle). 해법은 셋입니다.

해법방법장단점
한쪽은 CIDR로 (이번 실습)ALB 아웃바운드는 VPC 대역 80으로, 앱 인바운드만 ALB SG 참조가장 단순. ALB가 VPC 안의 다른 80 포트에도 갈 수 있지만, 그쪽 인바운드가 막고 있으므로 실질 위험 낮음
규칙을 루트에서두 모듈은 SG만 만들고, 서로를 참조하는 규칙 리소스는 루트에 둔다정확한 최소 권한. 대신 규칙이 모듈 밖으로 흩어짐
SG를 먼저 만드는 모듈“보안 그룹 세트” 모듈이 세 SG를 만들고 ID를 출력, 각 계층 모듈은 SG ID를 입력으로 받음대규모 환경에서 깔끔. 모듈 하나가 늘어남
아웃바운드도 최소 권한으로: 관리형 접두사 목록

앱 SG의 아웃바운드를 0.0.0.0/0으로 열지 않고, AWS가 관리하는 S3 접두사 목록(com.amazonaws.ap-northeast-2.s3)의 443만 허용했습니다. S3의 IP 대역이 바뀌어도 AWS가 목록을 갱신하므로 규칙을 고칠 필요가 없습니다. 장악된 서버가 외부 공격자 서버로 데이터를 빼내는 경로가 원천적으로 막힙니다.

설정이유
이름 26자 제한 validationALB·대상 그룹 이름은 32자가 한도이고 대상 그룹에 -tg를 붙이므로. API 오류보다 먼저, 우리 말로 막는다
서브넷 2개 이상 validationALB는 서로 다른 AZ의 서브넷 2개 이상이 필수
drop_invalid_header_fields = true잘못된 HTTP 헤더를 버려 요청 밀반입(request smuggling) 계열 공격 완화. 보안 점검 도구가 자주 지적하는 항목
상태 확인 /health, 간격 15초, 정상 판정 2회새 서버가 30초 안팎에 트래픽을 받기 시작. 기본값(30초 간격, 5회)보다 실습 대기 시간이 짧다
deregistration_delay = 30서버 교체 시 기존 연결을 기다리는 시간. 기본 300초는 실습에서 destroy를 5분 늦춘다
HTTPS는 어떻게 붙이나 (이번 실습 범위 밖)

운영이라면 HTTP 80은 HTTPS로 넘기는(redirect) 용도로만 쓰고, 443 리스너에 ACM 인증서를 붙입니다. 이를 위해서는 소유한 도메인과 Route 53(또는 외부 DNS) 검증이 필요합니다. 구성은 aws_acm_certificate + DNS 검증 레코드 + aws_acm_certificate_validation + aws_lb_listener(port 443, ssl_policy, certificate_arn) + 80 리스너의 redirect 기본 동작입니다. 25편 MSP 표준 구성에서 다룹니다.

왜 허용 보안 그룹을 맵으로 받는가 (실측)

“DB에 접근할 보안 그룹 목록”이니 list(string)이 자연스러워 보입니다. 그러나 그 목록의 값(앱 SG ID)은 같은 apply에서 새로 만들어지므로 plan 시점에는 모릅니다. 값을 모르는 리스트로 for_each를 돌리면 키를 정할 수 없어 실패합니다(4편 11장). 아래는 같은 구조를 내장 리소스로 재현해 실행한 결과입니다.

# for_each = toset([terraform_data.app_sg.id])  → 리스트(값이 키가 됨)

  on main.tf line 5, in resource "terraform_data" "rule_list":
   5:   for_each = toset([terraform_data.app_sg.id])

그래서 모듈 입력을 allowed_security_groups = { app = "sg-..." } 형태로 설계했습니다. 키는 사람이 정한 고정 이름이고, 값은 나중에 정해져도 됩니다. 모듈 계약을 설계할 때 “이 입력이 for_each에 쓰일 것인가”를 미리 생각해야 하는 이유입니다.

설정모듈 기본값 (운영 안전)실습 루트의 값이유
deletion_protectiontruefalse운영 DB가 terraform destroy로 지워지는 사고 방지. 실습은 정리가 우선
skip_final_snapshotfalse (최종 스냅숏 남김)true운영은 삭제 직전 백업 필수. 실습 스냅숏은 저장 비용만 남긴다

DB는 교체되면 데이터가 사라진다

RDS의 identifier, engine, 서브넷 그룹 이름, db_name 같은 인자는 바꾸면 교체(-/+)를 유발합니다. 웹 서버 교체는 잠깐의 중단이지만 DB 교체는 데이터 손실입니다. 운영 DB 리소스에는 11편의 prevent_destroy를 추가하고, plan에서 DB에 -/+가 보이면 무조건 멈추는 리뷰 규칙을 둡니다. 엔진 버전을 "17"처럼 메이저만 적으면 RDS가 기본 마이너 버전을 고르고, 자동 마이너 업그레이드로 실제 버전이 올라가도 plan에 차이가 생기지 않습니다.

insecure_value를 쓴 이유

AWS 프로바이더의 data "aws_ssm_parameter"는 파라미터 종류와 관계없이 value를 민감 값으로 표시합니다. 서브넷 ID 목록에 sensitive가 붙으면 그 값이 흘러가는 출력마다 sensitive = true가 필요해지고, plan에서 서브넷이 전부 (sensitive value)로 가려져 리뷰가 어려워집니다. String·StringList처럼 비밀이 아닌 파라미터는 insecure_value로 읽어 이 전파를 막습니다. SecureString에는 쓰지 않습니다.

default_tags + label 모듈

루트 provider의 default_tags = module.label.tags 한 줄로 이 state의 모든 리소스에 표준 태그가 붙습니다. 모듈 안 리소스도 같은 provider를 쓰므로 함께 적용됩니다. 모듈은 계층 고유의 Tier·Role·Name만 덧붙입니다.

비용 할당 태그 활성화

태그를 붙여도 결제 콘솔의 비용 할당 태그(Cost allocation tags)에서 활성화해야 Cost Explorer·청구서에서 태그별로 나뉩니다. 활성화 이후 발생분부터 집계되므로 계정을 만들자마자 켜 두는 것이 좋습니다.

표준을 강제하는 세 층

① 코드: label 모듈의 validation(필수 키, 값 형식). ② 계정: AWS Organizations 태그 정책으로 허용 값 지정, SCP로 필수 태그 없는 생성 거부. ③ 점검: AWS Config 규칙(required-tags)으로 위반 리소스 보고. MSP는 ①을 기본으로, 고객사 거버넌스 수준에 따라 ②③을 더합니다.

태그를 쓸 수 없는 리소스

보안 그룹 규칙, 라우팅, 대상 그룹 연결, IAM 정책 연결처럼 태그를 지원하지 않는 리소스도 있습니다. 이런 것은 상위 리소스(보안 그룹, 라우팅 테이블)의 태그로 추적합니다.

기본값 false라 기존 호출자의 plan에는 변화가 없으므로 깔끔한 MINOR입니다. 그러나 07-app에서 DB 서브넷을 바꾸면 aws_db_subnet_group의 서브넷 변경이 일어나는데, 이미 DB가 있는 서브넷 그룹에서 DB가 쓰는 서브넷을 뺄 수는 없어 실패하거나, 서브넷 그룹을 새로 만들면 DB 교체가 필요해집니다. DB를 만든 뒤에는 서브넷 계층을 바꾸기 어렵다는 것, 그래서 네트워크 설계(Day 0)를 먼저 해야 한다는 것(1편 3장)을 체감하는 과제입니다. 실습 DB를 destroy한 상태에서 바꾸면 깔끔하게 적용됩니다.
