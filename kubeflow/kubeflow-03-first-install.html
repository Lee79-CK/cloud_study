첫 설치와 둘러보기

내 PC에 Kubernetes 클러스터를 하나 만들고, 그 위에 Kubeflow 전체를 올립니다. 명령 몇 줄이면 끝나지만, 그 몇 줄 뒤에서 열여덟 층의 탑이 순서대로 쌓입니다. 왜 그 순서인지 알면 설치가 실패했을 때 어디를 볼지도 보입니다.

이번 편에서 얻을 것

1편에서 지도를 그리고, 2편에서 말을 익혔습니다. 이제 직접 손으로 올려 볼 차례입니다. 이 편을 마치면 다음을 할 수 있습니다.

  • 내 장비에 Kubeflow를 올릴 수 있는지 자원을 어림하고, 필요하면 구성요소를 빼서 가볍게 만들 수 있습니다.
  • Community Distribution 저장소의 구조와 kustomize 방식을 이해하고, 설치 순서가 왜 그렇게 정해졌는지 설명할 수 있습니다.
  • kind 클러스터에 26.03.1을 설치하고, 네임스페이스별로 Pod 상태를 확인한 뒤 대시보드에 로그인할 수 있습니다.
  • 로그인 요청이 어떤 구성요소를 거치는지, 프로필이 만드는 사용자 공간이 무엇인지 알고, 자주 만나는 설치 문제를 스스로 풀 수 있습니다.
이번 편의 설치는 학습용입니다

kind 위의 설치는 기본 계정과 기본 비밀번호, HTTP 포트 포워딩을 쓰는 실험 환경입니다. 실제 운영 환경 설치(관리형 Kubernetes, HTTPS, 기업 로그인 연동, 고가용성)는 13편과 14편에서 다룹니다. 또 kind에서는 GPU를 쓰기 어려워서, 이번 편의 모든 실습은 CPU만으로 진행합니다. GPU는 11편에서 다룹니다.

1설치 전에 정할 것

어디에 설치할까

방식장점단점어울리는 경우
kind (이번 편)Docker나 Podman만 있으면 PC 한 대에서 몇 분 만에 클러스터를 만들고 지울 수 있음. 공식 저장소가 kind를 기본으로 테스트노드가 컨테이너라서 GPU, 외부 접속, 고가용성 실습이 어려움학습, 기능 확인, 매니페스트 수정 실험
Minikube, Rancher 등 다른 로컬 도구공식 저장소가 지원 대상으로 명시도구마다 네트워크와 스토리지 설정이 조금씩 다름이미 쓰는 로컬 도구가 있을 때
관리형 Kubernetes (EKS, AKS, GKE)실제 운영과 같은 환경, GPU 노드 사용 가능비용, 클라우드별 조정 필요(예: GKE는 Istio CNI 전용 오버레이)팀 공용 플랫폼, 운영 준비 (14편)

내 장비에 들어갈까

공식 저장소는 전체 설치에 메모리 16GB 이상, CPU 8코어를 권장합니다. 구성요소를 빼면 메모리 4~8GB, CPU 2~4코어에도 올릴 수 있다고 안내합니다. 아래 표의 숫자는 저장소 README가 구성요소별로 제시한 대략적인 요구량입니다. 빼고 싶은 구성요소의 체크를 풀고, 내 장비 사양을 넣어 보세요.

구성요소 수치는 공식 README의 표(실측 사용량과 설정된 requests 중 큰 값)를 옮긴 것으로, 버전에 따라 조금씩 다릅니다. Kubernetes 자체와 운영체제 몫으로 메모리 3GB, CPU 1코어를 따로 더했습니다. Mac이나 Windows의 Docker Desktop을 쓴다면 Docker에 할당한 메모리가 기준입니다.

ARM64 장비라면 미리 확인하세요

Apple Silicon Mac, NVIDIA DGX Spark, AWS Graviton처럼 ARM64(aarch64) 장비에서는 일부 이미지가 linux/arm64용으로 제공되지 않아 “no matching manifest for linux/arm64” 오류가 날 수 있습니다. 공식 저장소도 ARM64 지원이 아직 완전하지 않다고 밝히고 있습니다. 처음 실습이라면 x86_64 장비나 클라우드 VM을 권합니다.

2저장소와 kustomize 읽기

Community Distribution은 설치 프로그램이 아니라 매니페스트 묶음입니다. GitHub의 kubeflow/community-distribution 저장소(예전 이름 kubeflow/manifests)에 모든 구성요소의 YAML이 들어 있고, 이것을 kustomize로 조립해 kubectl로 적용하는 것이 설치의 전부입니다. 폴더를 눌러 역할을 확인하세요.

kustomize 30초 입문

kustomize는 템플릿 문법 없이 YAML을 조립하는 도구입니다. 각 폴더의 kustomization.yaml이 “이 폴더는 어떤 YAML들로 이루어지고, 무엇을 덧씌우는지”를 적습니다. kustomize build 폴더를 실행하면 최종 YAML이 화면에 출력되고, 이것을 파이프(|)로 kubectl apply에 넘깁니다.

가장 중요한 원칙은 하나입니다. 원본 매니페스트를 직접 고치지 않습니다. 바꾸고 싶은 것은 내 폴더에 별도의 kustomization을 만들어 원본을 참조하고, 바꿀 부분만 덧씌웁니다. 그래야 다음 버전이 나왔을 때 참조만 바꿔 업그레이드할 수 있습니다.

내 설정을 덧씌우는 kustomization 예시 (단순화)

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../community-distribution/example      # 원본은 손대지 않고 참조만
patches:
- path: dex-passwords-patch.yaml          # 기본 비밀번호를 내 값으로
images:
- name: ghcr.io/kubeflow/notebooks/jupyter-web-app
  newName: registry.internal/kubeflow/jupyter-web-app   # 사내 미러로 교체

이 방식은 14편의 운영 설치와 업그레이드에서 본격적으로 씁니다. 지금은 “example 폴더 하나를 build하면 전체 설치용 YAML이 나온다”는 것만 기억하세요.

3설치 순서에 담긴 이유

한 줄 설치는 모든 것을 한꺼번에 밀어 넣지만, 공식 README는 구성요소를 하나씩 설치하는 순서도 안내합니다. 맨 위의 탑이 그 순서입니다. 순서에는 세 가지 규칙이 숨어 있습니다.

인증서가 먼저

많은 구성요소가 웹훅을 쓰고, 웹훅은 TLS 인증서가 있어야 동작합니다. 그래서 인증서를 발급하는 cert-manager가 가장 먼저 옵니다.

출입문과 경비가 다음

Istio 게이트웨이, oauth2-proxy, Dex가 먼저 있어야 각 앱이 그 뒤에 경로를 붙이고 보안 정책을 걸 수 있습니다.

틀이 먼저, 내용이 나중

CRD(새 리소스 종류)가 등록되고 준비되어야 그 종류의 리소스를 만들 수 있습니다. 한꺼번에 적용하면 첫 시도에 일부가 실패하는 이유입니다.

사용자 공간은 마지막

프로필은 Profile 컨트롤러와 역할, 보안 정책이 모두 갖춰진 뒤에야 제대로 된 네임스페이스를 만들 수 있습니다.

층구성요소주로 사는 네임스페이스

네임스페이스는 26.03 계열 기준입니다. Kubeflow는 kubeflow에서 kubeflow-system으로 네임스페이스를 옮기는 중이고, 다음 릴리스에서는 KServe가 kserve 네임스페이스로 옮겨 갑니다. 그래서 반드시 설치하려는 릴리스 태그의 README를 따라야 합니다.

4실습: 설치하기

Linux(또는 WSL2) 터미널 기준입니다. 각 단계의 명령을 복사해 실행하고, 끝나면 완료에 표시하세요. 진행 상황은 이 페이지를 열어 둔 동안 유지됩니다.

0 / 9 완료

  1. 준비물 확인

    Git과 컨테이너 실행 도구(Podman 또는 Docker)가 필요합니다. 공식 README는 Podman을 더 권합니다. kind, kubectl, kustomize는 4단계의 스크립트가 검증된 버전으로 설치해 줍니다.

    git --version
podman --version || docker --version

  2. 커널 설정 늘리기

    Kubeflow는 Pod가 아주 많아서 파일 변경 감시(inotify) 한도를 금방 넘깁니다. 이 한도가 낮으면 Pod들이 “too many open files” 류의 오류로 이유 없이 죽습니다. 공식 README가 제시하는 값으로 올립니다. 재부팅 후에도 유지하려면 /etc/sysctl.d/에 같은 값을 적어 두세요.

    sudo sysctl fs.inotify.max_user_instances=2280
sudo sysctl fs.inotify.max_user_watches=1255360

  3. 저장소를 받고 릴리스 태그로 이동

    master 브랜치는 다음 릴리스를 향해 계속 바뀝니다. 강의와 같은 결과를 얻으려면 26.03.1 태그로 이동하고, 이후로는 이 태그의 README를 기준으로 삼으세요.

    git clone https://github.com/kubeflow/community-distribution.git
cd community-distribution
git checkout 26.03.1

  4. kind 클러스터 만들기

    저장소에 들어 있는 스크립트가 지속적으로 테스트된 버전의 kind, kubectl, kustomize를 설치하고, 이름이 kubeflow인 클러스터를 만듭니다. CI가 쓰는 스크립트와 같아서 검증된 조합을 그대로 쓰게 됩니다.

    ./tests/install_KinD_create_KinD_cluster_install_kustomize.sh

  5. kubeconfig 지정

    kubectl이 방금 만든 클러스터를 바라보게 합니다. 2편에서 배운 대로 kubectl get nodes로 노드가 Ready인지 확인해 보세요.

    kind get kubeconfig --name kubeflow > /tmp/kubeflow-config
export KUBECONFIG=/tmp/kubeflow-config
kubectl get nodes

  6. Docker Hub 인증 정보 등록선택

    Docker Hub는 익명 다운로드 횟수를 제한합니다. 설치 중 이미지가 “toomanyrequests”로 실패하면, 로그인한 인증 정보로 Secret을 만들어 두세요.

    docker login
kubectl create secret generic regcred \
    --from-file=.dockerconfigjson=$HOME/.docker/config.json \
    --type=kubernetes.io/dockerconfigjson

  7. 전체 설치

    example 폴더를 build해서 적용합니다. 실패하면 20초 쉬고 다시 시도하는 루프입니다. 첫 몇 번은 실패하는 것이 정상입니다. CRD가 등록되고 준비되기 전에 그 종류의 리소스를 만들려고 하거나, 웹훅 서버가 아직 뜨지 않았기 때문입니다. --server-side는 일부 CRD가 너무 커서 일반 apply가 남기는 기록 주석의 크기 제한을 넘기 때문에 쓰고, --force-conflicts는 다른 관리자가 이미 소유한 필드도 이 설정으로 덮어쓰겠다는 뜻입니다.

    while ! kustomize build example | kubectl apply --server-side --force-conflicts -f -; do echo "Retrying to apply resources"; sleep 20; done

  8. 모든 Pod가 준비될 때까지 기다리기

    적용이 끝나도 이미지를 내려받고 Pod가 뜨기까지 시간이 걸립니다. 장비와 네트워크에 따라 수십 분이 걸릴 수 있습니다. 아래 명령에서 아무것도 나오지 않을 때까지 기다리세요. 5장에서 네임스페이스별로 자세히 봅니다.

    kubectl get pods -A | grep -vE 'Running|Completed'

  9. 포트 포워딩하고 로그인

    Istio 게이트웨이를 내 PC의 8080 포트로 연결합니다. 이 명령은 켜 둔 채로 두고, 브라우저에서 http://localhost:8080을 엽니다. Dex 로그인 화면이 나오면 기본 계정 user@example.com, 비밀번호 12341234로 로그인합니다.

    kubectl port-forward svc/istio-ingressgateway -n istio-system 8080:80
하나씩 설치하는 방법도 있습니다

README의 “Install Individual Components” 절은 맨 위 탑의 순서대로 구성요소를 하나씩 설치하는 명령을 제공합니다. 설치가 계속 실패해서 어디가 문제인지 좁혀야 할 때, 또는 필요한 구성요소만 골라 설치하고 싶을 때 이 방법이 좋습니다. 결과는 한 줄 설치와 같습니다.

5설치 확인

설치가 끝났는지는 네임스페이스별로 확인합니다. 각 네임스페이스에 무엇이 사는지 알면, 문제가 생겼을 때 어디부터 볼지 바로 정할 수 있습니다.

네임스페이스사는 것여기가 고장 나면
cert-manager인증서 발급기다른 구성요소의 웹훅이 동작하지 않아 리소스 생성이 연쇄적으로 실패
istio-systemIstio 제어부, 인그레스 게이트웨이, CNI대시보드에 아예 접속이 안 되거나, 사이드카가 붙지 않아 앱끼리 통신 실패
authDex로그인 화면이 안 뜨거나 로그인이 되지 않음
oauth2-proxyoauth2-proxy로그인 화면으로 이동하지 않거나 로그인 후 계속 되돌아옴
knative-servingKnative ServingKServe 모델 서빙이 준비되지 않음
kubeflow대시보드, Pipelines, Katib, Notebooks, KServe 등 대부분의 Kubeflow 구성요소해당 메뉴만 동작하지 않음
kubeflow-system새 위치로 옮겨 온 구성요소(Trainer가 쓰는 JobSet 등)학습 작업이 시작되지 않음
kubeflow-user-example-com기본 사용자의 작업 공간(프로필 네임스페이스)로그인은 되는데 내 공간이 없음
 
# 공식 README가 안내하는 확인 명령
kubectl get pods -n cert-manager
kubectl get pods -n istio-system
kubectl get pods -n auth
kubectl get pods -n oauth2-proxy
kubectl get pods -n knative-serving
kubectl get pods -n kubeflow
kubectl get pods -n kubeflow-user-example-com

# 설치된 Kubeflow 관련 CRD 훑어보기
kubectl get crd | grep -E 'kubeflow|kserve|knative'
Pipelines의 저장소가 바뀌었습니다

예전 자료에는 Pipelines의 아티팩트 저장소로 MinIO가 나옵니다. 26.03부터는 SeaweedFS가 기본 S3 호환 저장소입니다. kubeflow 네임스페이스에서 MinIO 대신 SeaweedFS Pod가 보여도 정상입니다. 이전 버전에서 업그레이드한다면 MinIO 데이터를 옮기는 작업이 필요합니다.

인증과 권한은 다른 문제입니다

oauth2-proxy와 Dex는 “당신이 누구인가”(인증)를 확인하고, Istio의 AuthorizationPolicy와 Kubernetes RBAC는 “그 사람이 이 네임스페이스에서 무엇을 할 수 있는가”(권한)를 확인합니다. 로그인 화면에서 막히면 앞쪽을, 로그인은 되는데 403이 나면 뒤쪽을 보면 됩니다. OIDC 흐름 자체는 이 시리즈의 OAuth/OIDC 강의에서, Kubeflow의 권한 구조는 13편에서 자세히 다룹니다.

8프로필과 사용자 공간

Kubeflow에서 사용자의 작업 공간은 프로필(Profile)이라는 리소스로 만듭니다. 프로필 하나를 만들면 Profile 컨트롤러가 같은 이름의 네임스페이스와 그 안의 권한, 보안 정책을 한꺼번에 만들어 줍니다. 설치 마지막 층에서 만든 kubeflow-user-example-com도 이렇게 만들어진 공간입니다.

팀 공간을 만드는 Profile 예시

apiVersion: kubeflow.org/v1
kind: Profile
metadata:
  name: team-reco                   # 만들어질 네임스페이스 이름
spec:
  owner:
    kind: User
    name: jieun@example.com         # 로그인 이메일과 정확히 같아야 함
  resourceQuotaSpec:                # 선택: 이 공간 전체의 자원 한도
    hard:
      requests.cpu: "16"
      requests.memory: 64Gi
      requests.nvidia.com/gpu: "2"

프로필 하나가 만드는 것

만들어지는 것하는 일
네임스페이스프로필 이름과 같은 작업 공간. Istio 사이드카 주입 같은 표시가 붙음
소유자 권한 연결 (RoleBinding)owner로 적은 사용자에게 이 네임스페이스의 관리자 역할을 줌
Istio 접근 정책 (AuthorizationPolicy)소유자의 요청이 이 네임스페이스의 앱에 닿을 수 있게 허용
서비스 계정 default-editor, default-viewer노트북이나 파이프라인 Pod가 이 공간 안에서 쓰는 계정
자원 할당량 (ResourceQuota)resourceQuotaSpec을 적었을 때만. 팀 전체가 쓸 수 있는 CPU, 메모리, GPU 상한
 
kubectl get profiles
kubectl get rolebindings,authorizationpolicies,serviceaccounts -n kubeflow-user-example-com
이메일 한 글자가 다르면 공간이 보이지 않습니다

owner의 name은 로그인할 때 쓰는 이메일과 대소문자까지 똑같아야 합니다. 다르면 프로필은 만들어졌는데 그 사용자의 대시보드에 네임스페이스가 나타나지 않습니다. 동료를 내 공간에 초대하려면 대시보드의 Manage Contributors 화면에서 이메일을 추가합니다. 그러면 권한 연결과 접근 정책이 하나씩 더 생깁니다. 다만 그 동료가 로그인할 수 있으려면 Dex에 계정이 있거나 기업 로그인이 연동되어 있어야 합니다(13편).

10접속, 비밀번호, 정리

원격 서버에 설치했다면

포트 포워딩은 명령을 실행한 컴퓨터의 localhost에서만 열립니다. 클라우드 VM이나 사내 서버에 kind를 올렸다면 SSH 터널로 내 PC까지 끌어오세요. 서버에서 포트 포워딩을 켜 둔 상태에서, 내 PC에서 아래 명령을 실행하고 내 브라우저로 localhost:8080을 엽니다.

ssh -L 8080:localhost:8080 사용자@서버주소

NodePort나 HTTP로 열면 안 되는 이유

Jupyter, TensorBoard, Katib 같은 Kubeflow 웹 앱은 보안 쿠키(Secure Cookie)를 씁니다. 보안 쿠키는 HTTPS에서만 전달되기 때문에, localhost가 아닌 주소로 HTTP 접속하면 로그인은 되는 것 같아도 앱들이 제대로 동작하지 않습니다. 다른 사람이 접속하게 하려면 istio-ingressgateway 서비스는 ClusterIP로 두고, 그 앞에 HTTPS 인그레스를 두는 것이 공식 권장입니다. 보안 쿠키를 끄는 설정도 있지만 권하지 않습니다. 운영 환경의 노출 방법은 14편에서 다룹니다.

기본 비밀번호 바꾸기

학습용이라도 다른 사람이 접근할 수 있는 곳이라면 기본 비밀번호부터 바꾸세요. 비밀번호를 bcrypt로 해시한 뒤 Dex의 Secret을 교체합니다. 근본적으로는 정적 비밀번호 대신 기업 로그인(IdP)을 연결하는 것이 권장 방식입니다(13편).

# 1. 비밀번호 해시 만들기 (passlib 패키지 필요)
python3 -c 'from passlib.hash import bcrypt; import getpass; print(bcrypt.using(rounds=12, ident="2y").hash(getpass.getpass()))'

# 2. 기존 Secret을 지우고 새 해시로 다시 만들기
kubectl delete secret dex-passwords -n auth
kubectl create secret generic dex-passwords --from-literal=DEX_USER_PASSWORD='여기에_해시' -n auth

# 3. Dex를 다시 시작
kubectl delete pods --all -n auth

13정리와 다음 편

  1. Community Distribution은 매니페스트 묶음입니다. kustomize로 조립해 kubectl로 적용하며, 원본은 고치지 않고 내 kustomization으로 덧씌웁니다.
  2. 설치 순서는 인증서, 출입문과 경비, 플랫폼, ML 구성요소, 사용자 공간 순입니다. 한꺼번에 적용하면 처음 몇 번 실패하는 것이 정상이라 재시도 루프를 씁니다.
  3. 강의와 같은 결과를 원하면 릴리스 태그(26.03.1)로 이동하고 그 태그의 README를 따릅니다. master는 네임스페이스와 경로가 다를 수 있습니다.
  4. 로그인은 Istio 게이트웨이, oauth2-proxy, Dex를 거쳐 인증되고, Istio 정책과 RBAC로 권한이 확인됩니다. 로그인 문제는 앞쪽, 403은 뒤쪽입니다.
  5. 프로필 하나가 네임스페이스, 권한, 보안 정책, 서비스 계정, 할당량을 만듭니다. 대시보드는 선택된 네임스페이스의 것만 보여 줍니다.
